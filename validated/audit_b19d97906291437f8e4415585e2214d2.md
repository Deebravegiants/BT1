This confirms the vulnerability path: the gem's documented contract states `Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and the handler receives `data.shop` as an authoritative "shop domain of the webhook" [1](#0-0) , used by host apps to route/scope tenant work such as `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [2](#0-1) . But the HMAC only signs the raw body, not the `shop`, `topic`, `webhook_id`, or `api_version` headers.

### Title
Webhook tenant identity (`shop`) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers from the HMAC-covered content, yet `Registry.process` trusts these unauthenticated headers to construct `WebhookMetadata` that is handed to the app's handler as the identified tenant/shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`. For webhook requests, that method returns `@raw_body` alone: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers with no cryptographic binding: [4](#0-3) 

`Registry.process` validates only the HMAC of the body, then unconditionally trusts `request.shop`/`request.topic` to build the `WebhookMetadata` passed to the app-supplied handler: [5](#0-4) 

The identity binding that should hold is: `shop_used_by_handler == shop_that_the_HMAC_actually_authenticates`. Because the HMAC only authenticates bytes of the body (proving the request payload was signed by an entity holding `client_secret`, i.e., Shopify), and never binds the `shop-domain` header, an unprivileged attacker who can deliver an HTTP request to the app's public webhook endpoint can take any previously-observed, Shopify-signed webhook body (e.g., one delivered to their own shop/app installation, which they legitimately receive) and replay it with the `shop-domain` header (and optionally `topic`/`webhook_id`) changed to point at a different, victim shop. Because the signature check only re-hashes the unchanged body, `HmacValidator.validate` still returns true, and `Registry.process` will dispatch the handler believing the event originated from the victim shop.

The documentation explicitly promises this validates the origin ("This will verify the request did indeed come from Shopify") and treats `data.shop` as the trustworthy shop domain for the event [1](#0-0) [6](#0-5) , which is inconsistent with the fact that `shop` is never authenticated.

### Impact Explanation
This breaks the tenant-isolation guarantee host applications rely on: `Registry.process` is the gem's sole abstraction for authenticating and dispatching webhooks, and its documented behavior is to confirm Shopify origin before invoking the handler with shop-scoped data. Because the shop identity is unauthenticated, a malicious actor with access to any one legitimately-signed webhook body (trivially obtainable by installing the app on their own free development store and triggering an event) can forge cross-tenant webhook deliveries, causing the host app to process, store, or act on data attributed to an arbitrary victim shop it has no relationship with — cross-tenant access/confusion at the trust boundary the gem is responsible for enforcing.

### Likelihood Explanation
The webhook endpoint is by design a public, unauthenticated internet endpoint (this is required for Shopify to deliver events). The only gate is `HmacValidator.validate`, which this analysis shows does not bind the `shop` header. Obtaining one authentic signed body requires only a free/development shop with the app installed — trivial for any unprivileged internet user targeting a multi-tenant app built on this gem.

### Recommendation
Extend `Webhooks::Request#to_signable_string` (or add a separate binding check in `Registry.process`) so that the `shop-domain` (and ideally `topic`/`webhook-id`) values are cryptographically bound to the verified signature, or otherwise document/enforce that `Registry.process` callers must independently verify `data.shop` against a known/whitelisted shop before trusting it, rather than presenting `WebhookMetadata#shop` as verified. At minimum, the documentation should be corrected to make clear that only the body — not the shop/topic identity — is authenticated by `Registry.process`.

### Proof of Concept
1. App A operator installs the target Shopify app on their own store `attacker.myshopify.com` and registers for `orders/create` webhooks, legitimately receiving a Shopify-signed request:
   - Headers: `X-Shopify-Hmac-Sha256: <valid HMAC of BODY>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker captures this raw request (body + HMAC header) via their own webhook receiver.
3. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value to the app's public webhook route, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers with no relation between `hmac` and `shop`; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only — unchanged — so validation succeeds.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: <attacker's own order data>, ...)`, and the host app's handler (as shown in the gem's own example, `perform_later(shop_domain: data.shop, ...)`) processes/attributes this forged event as belonging to `victim.myshopify.com`.
