### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` binds solely to the request body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers (`shopify-shop-domain`/`x-shopify-shop-domain`, etc.) and are never part of the signed content. This breaks the equality that host applications implicitly rely on: `shop authenticated by HMAC == shop used for tenant dispatch`. In reality, `shop covered by HMAC` is empty, while `shop acted upon by the handler` is the raw unauthenticated header value.

### Finding Description
`Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` — the raw body only — and compares it against the HMAC header. It never validates that the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers are consistent with anything cryptographically signed: [2](#0-1) 

`Request#hmac` reads `shopify-hmac-sha256`/`x-shopify-hmac-sha256`, and `Request#shop` reads `shopify-shop-domain`/`x-shopify-shop-domain` — both are attacker/carrier-controlled HTTP headers with no cryptographic relationship to each other: [4](#0-3) 

Because `to_signable_string` returns only `@raw_body`: [5](#0-4) 

any request whose body byte-for-byte matches a body that was legitimately signed for shop A's webhook (a merchant/attacker can trivially generate this by installing the app on their own store and triggering a webhook event, since `Context.api_secret_key` computes the same HMAC for identical bodies regardless of shop) will pass `HmacValidator.validate` even when the `shop-domain` header is swapped to shop B. The handler then receives `WebhookMetadata` keyed on the attacker-chosen `shop` value, with a body/signature that was never actually associated with that shop: [6](#0-5) 

This mirrors the reported bug class: a field that is *acted upon* (the reserve address in Tap; here, the `shop` used for tenant routing) is not covered by the authenticity check (the HMAC in Tap's caller contracts; here, the webhook signature), so the trusted state and the acted-upon state diverge.

### Impact Explanation
Any host application built on this gem that uses `WebhookMetadata#shop` (or `Request#shop`) to look up per-tenant secrets, update per-tenant records, or gate behavior by tenant, can be made to process a cryptographically "valid" webhook while attributing it to an arbitrary shop domain of the attacker's choosing. Since HMAC validity is the only authenticity signal exposed by this gem for webhooks, and it does not bind `shop`, this is a cross-tenant confusion primitive: an attacker who controls one legitimately-installed shop can produce a validly-signed body and relabel it as belonging to a different, victim shop.

### Likelihood Explanation
Exploitation requires only:
1. Installing the app on an attacker-controlled shop (available to any unprivileged merchant/developer who can install a public app), and
2. Capturing one legitimate webhook body + HMAC pair from that shop, and
3. Replaying it to the app's webhook endpoint with the `shop-domain` header changed to the victim shop.

No access to `api_secret_key`, access tokens, or any privileged account is required — this is a pure request-crafting exercise once the attacker has any single valid (body, hmac) pair from their own installation, which is trivially attainable by any user who can install the app.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed content, or independently verify that the `shop-domain` header corresponds to a shop that has an active session/installation known to the app for that specific webhook body, before dispatching to the handler. At minimum, document that `Request#shop` is not authenticated by the HMAC and must not be trusted for tenant-sensitive decisions without additional verification (e.g., cross-checking against a shop that legitimately installed the app and correlating via `webhook_id` uniqueness/idempotency tracking, which Shopify's actual webhook infrastructure guarantees but this gem does not itself enforce or validate).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, obtaining a legitimate webhook delivery with body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
2. Attacker sends a POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `shopify-hmac-sha256: H` (unchanged, still valid since body is unchanged)
   - Header `shopify-shop-domain: victim-shop.myshopify.com` (changed)
   - Header `shopify-topic`, `shopify-webhook-id` unchanged or altered as desired (also unauthenticated)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — this succeeds because `B` is unchanged.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host application to process/attribute the webhook as if it originated from `victim-shop.myshopify.com`, despite the signature never having been computed with any binding to that shop.
