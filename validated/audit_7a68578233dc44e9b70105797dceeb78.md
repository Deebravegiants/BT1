### Title
Webhook shop identity not covered by HMAC verification allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body alone, while the `shop` (and `topic`/`webhook-id`) values used downstream to identify the tenant are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then trusts the header-derived `shop` to build `WebhookMetadata`, breaking the identity binding between "bytes verified" and "shop acted on."

### Finding Description
The equality that must hold for a webhook to be trusted as originating from a specific shop is:

`shop used to route/act on the webhook == shop whose bytes were HMAC-verified`

In this gem, that equality does not hold. `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `Request#topic`, and `Request#webhook_id` are read straight from HTTP headers, which are not part of the signed payload at all: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then immediately forwards the unauthenticated header-derived `shop` to the handler as the tenant identity:

</cite> [3](#0-2) 

Because the HMAC is computed with `OpenSSL::HMAC.hexdigest` over `to_signable_string` (body only) using the app's `api_secret_key`, in `HmacValidator`: [4](#0-3) 

...any request with a body that produces a valid signature for the shared secret will pass validation regardless of which `shopify-shop-domain` header accompanies it. An unprivileged user who legitimately installs the app on their own store (a completely normal, unprivileged action) will receive genuinely-signed webhooks from Shopify for their own shop's events. They can capture such a webhook (same raw body, valid HMAC) and replay it to the app's webhook endpoint with the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header rewritten to point at a different, victim shop. `Registry.process` still finds the signature valid (only the body matters) and calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` carrying the attacker-chosen shop value.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to select the tenant context for processing webhook data (the documented and expected usage per `docs/usage/webhooks.md`) can be made to associate attacker-controlled body content with a shop the attacker does not control. This is a cross-tenant data-integrity/confidentiality boundary break driven purely by the gem's own signature-verification logic, satisfying the Critical "cross-tenant access" impact category — the shop-identity binding the HMAC is supposed to provide is not actually enforced by this gem.

### Likelihood Explanation
Likelihood is high for any unprivileged actor who can install the target app on a shop they control (a standard, permitted action for any Shopify merchant), since they can generate arbitrarily many genuinely-signed body/HMAC pairs for their own shop and then freely vary only the shop-identifying headers, which are never covered by the signature check performed by `Utils::HmacValidator`.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) headers in the HMAC-signable string, or otherwise cryptographically bind the shop identity to the request before it is trusted, e.g. modify `Request#to_signable_string` to serialize `shop`, `topic`, and `webhook_id` together with `raw_body`, and update `HmacValidator`/Shopify's signing scheme accordingly (this requires coordinated changes with how Shopify itself signs webhooks, since currently Shopify's HMAC-SHA256 header is computed over the body only per Shopify's own webhook spec — so at minimum, apps consuming this gem must be warned in the docs that `shop`/`topic`/`webhook_id` are unauthenticated and must not be used for tenant routing without additional verification, e.g. cross-checking against known registered shops via a separate authenticated channel).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged workflow).
2. Attacker triggers a webhook event (e.g. `orders/create`) with attacker-controlled body content (order fields they control as a shop owner).
3. Shopify delivers the webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`.
4. Attacker replays this exact body and HMAC header to the same endpoint but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (the unchanged raw body) — validation succeeds.
6. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)`, and the host app processes attacker-controlled data as belonging to `victim-shop.myshopify.com`.
