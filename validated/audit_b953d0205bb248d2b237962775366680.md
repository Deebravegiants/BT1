### Title
Tokens reaching the controller outside measured legs are permanently stranded — no sweep or recovery path exists - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
Analogous to "WJLP can only be unwrapped by Active/Stability Pool, so a holder can't exit", XOXNO's controller can hold user token balances that no unprivileged — or privileged — call can ever return. Every outbound token movement from the controller is a measured balance-delta leg inside a position flow (`withdraw`, `flash_position` collateral/refund lists, router-underspend refunds). Tokens that arrive at the controller via a direct `token.transfer`, or are pushed by a `flash_position` callback but appear in neither `collaterals` nor `refund_assets`, are never credited and never refunded. The docs confirm: "Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint." The same applies to the pool: all fourteen mutators are `#[only_owner]` (the controller), and `cash` is bookkeeping that direct donations don't increase — a direct transfer to the pool is trapped with zero recovery surface, mirroring `unwrapFor` being gated to `_requireCallerIsAPorSP` with no general holder exit.

### Finding Description
- `flash_position` snapshots balances, runs the callback, then only acts on declared lists: `collect_collateral_deposits` credits declared `collaterals`, and `refund_listed_assets` iterates `refund_assets` and calls `refund_controller_balance_delta` per listed asset (`contracts/controller/src/strategies/flash_position.rs:145-148`, `:372-384`). Any other token the callback pushed to the controller is ignored — and the transaction still succeeds, so the user cannot even re-declare retroactively.
- There is no `sweep`/`rescue` entrypoint on the controller at all; every token-out path (`settle_withdraw`, strategy legs) only pays out measured deltas inside an authorized position flow (`contracts/controller/src/positions/supply.rs:173-215`).
- The pool offers no holder-level redemption either: `withdraw`, `supply`, `repay`, `recapitalize`, `claim_revenue` are all `#[only_owner]` with the controller fixed as owner at construction (contracts/pool/README.md "Surface" table), and `cash` crediting happens on the controller's word, so a direct token transfer to the pool raises `token.balance(pool)` without any booked claim against it.

### Impact Explanation
Permanent freezing of user funds. A user who transfers a listed token directly to the controller or pool (easy on Soroban — SAC `transfer` needs only sender auth), or whose `flash_position` receiver pushes a token that is omitted from both `collaterals` and `refund_assets` (e.g., callback delivers an extra output token the integrator forgot to declare), loses those tokens forever. Unlike Yeti's WJLP, where unwrap was merely inconvenient-but-possible via a trove, here there is not even a costly path: no entrypoint, including owner-gated ones, can move an arbitrary controller token balance to a user. The test suite explicitly pins this behavior — `test_migrate_refund_ignores_preexisting_controller_balance` asserts pre-existing controller ETH "must remain (not used as refund or swept)".

### Likelihood Explanation
Requires user/integrator error, so frequency is bounded, but the trigger surface is real: `flash_position` refunds are opt-in per asset and bounded by `max_supply_positions`, so a callback producing more distinct output tokens than declared — or an asset rejected from `refund_assets` by the "listed in debt hub and account spoke" validation — strands the excess in the same transaction that otherwise succeeds. Mistaken direct transfers to well-known contract addresses are a recurring real-world occurrence. Net: Medium, matching the source finding's severity (impaired functionality / unrecoverable funds on a reachable path).

### Recommendation
Add a permissionless recovery entrypoint, e.g. `sweep_stranded(caller, asset, to)`, that transfers `token.balance(controller) - tracked_obligations` — where tracked obligations are simply zero for the controller since every legitimate controller balance is consumed within a single transaction — or at minimum allow `refund_assets` to accept any token address (dropping the hub/spoke listing requirement) and/or emit a clear revert when the callback leaves undeclared positive deltas. For the pool, add an owner-callable `rescue(asset, amount, to)` capped at `balance - cash` so donations aren't burned while backing stays whole.

### Proof of Concept
1. Alice calls `controller::flash_position` with `collaterals = [(USDC, min)]` and `refund_assets = []`. Her receiver swaps the minted debt into USDC plus a bonus token T (or USDC itself partially) and pushes both to `controller`.
2. The call succeeds: USDC delta is measured and deposited; token T delta is neither credited (not declared collateral) nor refunded (not listed in `refund_assets`) — `refund_listed_assets` only iterates the declared list (flash_position.rs:372-384).
3. Alice now has no callable path: `withdraw` pays only measured account supply, `repay`/`recapitalize` move user→pool not controller→user, and no sweep endpoint exists (docs/reference/endpoints.md:86). Token T sits on the controller permanently, as confirmed by the pinned invariant in `test_migrate_refund_ignores_preexisting_controller_balance`.
4. Simpler variant: Bob calls `token::transfer(bob, controller, X)` for a listed asset directly. The balance is immediately unrecoverable — identical stranded state, reachable by any unprivileged address.
