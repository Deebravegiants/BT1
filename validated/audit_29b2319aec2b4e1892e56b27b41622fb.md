## Finding

### Title
Webhook shop/topic/webhook-id identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed straight to the app's webhook handler. The signature therefore never binds the tenant identity (`shop`) to the verified bytes, letting anyone who possesses a single valid `(body, hmac)` pair replay it with a forged `shop-domain`/`topic` header.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler: [1](#0-0) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — none of `shop`, `topic`, `webhook_id`, or `api_version` are included in the signed content, yet those exact fields are read straight from attacker-controlled HTTP headers and forwarded unmodified into the handler payload: [3](#0-2) [4](#0-3) [1](#0-0) 

The identity binding broken is: `shop authenticated (bytes covered by HMAC) == shop used as tenant key (request.shop, from an unverified header)`. Before the request: the HMAC only proves "this body was produced with the app secret for *some* previously issued webhook." After the request: the handler trusts `request.shop`/`request.topic`/`request.webhook_id` as if they were verified, because `HmacValidator.validate` returned `true`.

### Impact Explanation
Any party that can obtain one legitimate `(raw_body, hmac)` pair for the app — e.g., by installing the app on their own store and capturing a webhook Shopify sends them — can resend that exact body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header for a different, victim shop. `HmacValidator.validate` still returns `true` because only the body bytes are checked, so `Registry.process` dispatches the forged `WebhookMetadata` (with attacker-chosen `shop`/`topic`) to the host app's handler as if it came from Shopify for that victim shop. Since most Shopify apps key their per-tenant session/data lookups off the webhook's `shop` field, this enables cross-tenant confusion: data intended for one merchant can be attributed to, or acted upon for, another merchant's session — a cross-tenant access/impact under the accepted Critical/High categories, without needing the app's `client_secret` or any access token.

### Likelihood Explanation
Moderate: the attacker needs at least one previously delivered, HMAC-signed webhook body for the app (trivially obtainable by installing the app themselves, an unprivileged action), plus the ability to send an HTTP request with custom headers to the app's public webhook endpoint. No leaked credentials, TLS interception, or privileged account access is required.

### Recommendation
Include the identity-carrying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind them to the body (e.g., verify `shop` against the caller's known/expected domain before trusting it), instead of computing the signature purely from the raw body while independently trusting the headers.

### Proof of Concept
1. Install the target app on an attacker-controlled development store; the app registers a webhook (e.g., `orders/create`) and Shopify sends a genuine webhook request with a valid `x-shopify-hmac-sha256` for some `raw_body`.
2. Capture that `(raw_body, hmac)` pair.
3. Replay an HTTP POST to the app's webhook endpoint using the captured `raw_body` and `hmac`, but set `x-shopify-shop-domain` to the victim's `*.myshopify.com` domain (and/or change `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the secret; `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed_body, ...)`, tricking the host application into treating the payload as authentic data for the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
