### Title
Webhook shop attribution not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (and `topic`/`webhook_id`) values used to route and attribute the webhook are taken from unauthenticated HTTP headers. The equality that should hold — *the shop the app processes the webhook for == the shop for which Shopify actually signed the payload* — is never enforced, because the `X-Shopify-Shop-Domain` header is not part of the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` only re-computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header value using the app's shared `Context.api_secret_key`: [3](#0-2) 

`Registry.process` validates only that HMAC, then dispatches to the handler using `request.shop` (the unauthenticated header value) to build the `WebhookMetadata` that the host application's handler will act on: [4](#0-3) 

Because `Context.api_secret_key` is a single secret shared across every shop that has installed the app (it is not shop-specific), any legitimately-signed webhook body — e.g., one the attacker triggers on their own installed/dev shop — carries a valid HMAC regardless of which shop's name is later put in the `X-Shopify-Shop-Domain` header. The header is fully attacker-controlled once the raw body and its genuine signature have been captured/replayed, since it plays no role in `to_signable_string`.

### Impact Explanation
This breaks the identity binding `shop-attributed-to-signature == shop header value`, letting an attacker who controls one legitimate tenant (installs the app on their own store) replay a genuinely-signed webhook body while swapping the `shop-domain` header to point at a victim shop. Any host application that relies on `WebhookMetadata#shop` (as constructed at [5](#0-4)  ) to select which tenant's session/data record to update will process spoofed data under the victim shop's identity — a cross-tenant confusion/injection primitive that satisfies the "cross-tenant access" Critical impact bucket, since the gem itself supplies this value as if it were verified.

### Likelihood Explanation
Exploitability only requires the attacker to be able to trigger at least one real webhook delivery to their own app installation (trivial — installing the free/dev version of any app and performing the triggering action, e.g. placing an order) and then relay/replay that raw body with a modified shop-domain header to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or privileged accounts is needed — exactly the "unprivileged internet user" threat model in scope.

### Recommendation
Include the shop domain (and ideally `topic`/`webhook_id`) inside the HMAC-covered signable string, or independently verify that the `shop` header value corresponds to a shop actually associated with the app/installation before constructing `WebhookMetadata`. At minimum, document/require that consumers cross-check `request.shop` against their own installed-shop registry rather than trusting it as authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a legitimate, allowed action).
2. Attacker triggers a webhook (e.g. `orders/create`) on their own shop and captures the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)` and `secret` is the same `api_secret_key` for all shops).
3. Attacker replays the exact same body `B` and `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`, per [6](#0-5) .
5. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, per [5](#0-4) , causing the host app to act on attacker-supplied data attributed to the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
