## Title
Permanent freezing of accumulated protocol fees and inability to change `feeToken` if the fee token's admin blocklists `EvmHost` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.updateHostParamsInternal` refuses to switch the fee token unless the host's balance of the outgoing fee token is exactly zero, and `EvmHost.withdraw` is the only function that can move that balance out. If the fee token is a blocklist-capable stablecoin (e.g. USDC) and its admin ever blocklists the `EvmHost` contract address, both paths become permanently unusable, mirroring the reported Sherlock bug class where a token's centralized admin can brick a contract's exit logic by blocking outbound transfers from a specific address.

### Finding Description
Every unprivileged dispatcher who calls `dispatch()` on `EvmHost` pays protocol fees in the configured `feeToken`, and those fees accumulate on the host contract itself (`IERC20(feeToken).balanceOf(address(this))` grows over time through ordinary, permissionless usage). [1](#0-0) 

The only way those funds leave the host is `withdraw()`, which does a `safeTransfer` *from* the host to a beneficiary:
```solidity
function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
    ...
    IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
    ...
}
``` [2](#0-1) 

Separately, `updateHostParamsInternal` (invoked from `updateHostParams`, itself gated to the `hostManager`) explicitly forbids switching away from the current fee token while the host still holds a non-zero balance of it:
```solidity
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
``` [1](#0-0) 

If a blocklist-enabled ERC-20 (USDC being the canonical example, as in the original report) is configured as the fee token and its admin blocklists the `EvmHost` contract's address, an ERC-20 `transfer`/`transferFrom` *from* that address reverts unconditionally. That breaks both dependent code paths simultaneously:
1. `withdraw()` will always revert for that token, so the accumulated balance can never be swept to a beneficiary.
2. Because `withdraw()` can never reduce the balance to zero, `updateHostParamsInternal`'s `balance != 0` check will never pass, so `feeToken` can never be changed away from the blocklisted token — permanently, since there is no other code path that lets `_hostParams.feeToken` be updated.

This is the same root cause pattern as the reported issue: an external token admin's unilateral blocklisting action against a specific contract address permanently defeats a balance-gated state transition (`remove`/`replace` there, `withdraw`/fee-token-rotation here) that the protocol has no fallback for.

### Impact Explanation
Any fee revenue already accumulated on the host in the blocklisted token becomes permanently frozen — it can be neither withdrawn to governance/relayers nor rescued via a fee-token migration, since the migration itself is blocked by the very balance that cannot be moved. This is a genuine, permanent freezing-of-funds condition on protocol revenue, and it also permanently locks the host into a fee token it can no longer safely operate with (dispatchers keep paying into a token whose proceeds can never be collected).

### Likelihood Explanation
This requires the fee token to be a blocklist-capable stablecoin and its centralized admin to blocklist the specific `EvmHost` contract address — an action outside Hyperbridge's control, exactly as posited in the original report. It is not implausible: `EvmHost.hostParams().feeToken` can be any ERC-20 governance chooses (including USDC-class tokens per the docs' examples), and stablecoin issuers have blocklisted arbitrary contracts before (e.g., due to hacks or sanctions where the flagged funds transited through that address). Likelihood is Medium, matching the severity of the original finding.

### Recommendation
Do not let a `balanceOf(address(this)) != 0` check be a hard blocker with no bypass. Options: allow `updateHostParams` to force-switch `feeToken` while leaving the stranded balance in a separate "legacy fee token" bucket recoverable through a dedicated emergency-sweep path that does not require a plain `transfer` from the frozen address (e.g., an allowance-based pull that a blocklisted-but-not-frozen-forever counterpart could execute, or simply permitting the balance to be abandoned/written off so governance can proceed), or add a circuit-breaker that lets governance zero out/mark the stuck balance as unrecoverable dust so `feeToken` rotation is not permanently gated on it.

### Proof of Concept
1. Governance sets `feeToken = USDC` via `updateHostParams`.
2. Users call `dispatch()` normally over time; protocol fees accrue as USDC balance on the `EvmHost` contract per `evm/src/core/EvmHost.sol` fee-collection logic.
3. Circle (USDC admin) blocklists the `EvmHost` contract address for any reason.
4. `hostManager` calls `withdraw({token: USDC, ...})` — reverts because USDC refuses `transfer` from a blocklisted sender.
5. `hostManager` calls `updateHostParams` with a new `feeToken` — reverts with `CannotChangeFeeToken()` at [1](#0-0)  because `balanceOf(host) != 0` and can never be reduced.
6. The accrued USDC fees are permanently stranded, and the fee token can never be rotated away from USDC.

        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
