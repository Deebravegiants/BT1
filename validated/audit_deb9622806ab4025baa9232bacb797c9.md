### Title
Deposit cap check uses raw `assets` balance while share pricing uses interest-inclusive `total-assets-preview`, allowing the enforced cap to diverge from the vault's real economic size - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar`, and identical logic in `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`)

### Summary
`deposit` enforces `cap-supply` against `(var-get assets)` (the raw on-hand underlying balance), but shares are minted/valued using `total-assets-preview`, which additionally includes unrealized accrued interest (`debt - total-borrowed`). These two quantities are not kept in sync, so the enforced "supply cap" does not actually bound the vault's total economic value used to price shares.

### Finding Description
`deposit` computes the cap check as: [1](#0-0) 

using `current-assets = (var-get assets)`, and asserts `(+ current-assets amount) <= CAP-SUPPLY`.

However the number of shares minted for that same deposit (`inkind`) is computed by `convert-to-shares-preview`, which divides by `total-assets-preview`: [2](#0-1) 

`total-assets-preview` is strictly ≥ `(var-get assets)` whenever there is unrealized interest: [3](#0-2) 

`accrue` updates the borrow `index` and mints treasury shares diluting for the fee-reserve portion of accrued interest, but it never writes the accrued interest back into `(var-get assets)`: [4](#0-3) 

So the identity the cap is supposed to enforce, `TotalVaultValue ≤ cap-supply`, is checked instead as `RawAssetBalance ≤ cap-supply`, i.e.:

`(var-get assets) + amount ≤ cap-supply`  is enforced, while the actual post-deposit economic size is `total-assets-preview() + amount = (var-get assets) + unrealized_interest + amount`, which can already exceed `cap-supply` before any new deposit, and grows further with every deposit that only checks the smaller quantity. This is the same class of bug as the reported issue: two different code paths (the enforcement check vs. the value/share-pricing path) compute "how much is in the vault" differently, letting the cap be silently bypassed by the gap between them (accrued, unswept interest).

### Impact Explanation
This does not create tokens from nothing and does not immediately misprice existing shares (both `total-assets-preview` and `total-supply-preview` grow consistently for accrued interest, and the treasury mint is proportional). The practical effect is limited to the deposit cap (`cap-supply`) not bounding the vault's true value as intended — new depositors can push `total-assets-preview` (and thus the vault's real value, oracle-reported TVL, and downstream debt-cap/utilization computations in `v0-1-data.clar`) beyond the configured `cap-supply` limit indefinitely, since the check only tracks the un-accrued raw balance. This is a governance/parameter-enforcement gap rather than a mechanism causing loss of principal or unclaimed yield to any specific user — the cap being a risk-limiting parameter (deliberately configured by the DAO), and no value is minted from nothing or diverted between users.

### Likelihood Explanation
High likelihood of occurrence mechanically (any vault with nonzero utilization and elapsed time will accumulate a gap between `assets` and `total-assets-preview`), but the divergence is bounded by realistic borrow-interest accrual rates, so it grows slowly relative to `cap-supply`, and does not itself transfer value between users.

### Recommendation
Enforce the deposit cap using the same accounting basis used for share pricing — e.g., check `(+ (total-assets-preview) amount) <= CAP-SUPPLY` instead of `(+ (var-get assets) amount) <= CAP-SUPPLY` in `deposit` across all six vault contracts, so the enforced cap matches the vault's real total value.

### Proof of Concept
1. Vault has `assets = A`, `total-borrowed = B`, and accrues interest over time so `total-debt() = D > B` (unrealized interest `I = D - B > 0`), making `total-assets-preview() = A + I`.
2. Suppose `cap-supply = A + I` (i.e., the vault is already exactly at its intended value cap).
3. A depositor calls `deposit` with `amount = 1`. The check `(<= (+ A amount) CAP-SUPPLY)` passes because it only compares `A + 1` (not `A + I + 1`) against `cap-supply`.
4. The deposit succeeds even though the vault's real value (`total-assets-preview`) was already at, or beyond, `cap-supply` before the deposit, and grows to `A + I + amount`, exceeding the configured cap — demonstrating the two computations of "vault fullness" diverge, exactly as in the referenced report's `maxDeposit`/`afterDeposit` inconsistency.
