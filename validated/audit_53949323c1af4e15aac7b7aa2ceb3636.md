### Title
`Webhooks::Request#topic`/`#api_version` are unsigned headers trusted for dispatch while `HmacValidator` only signs `@raw_body` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `#topic`, `#shop`, and `#api_version` are read straight from attacker-controllable HTTP headers [2](#0-1) . `Utils::HmacValidator.validate` computes/compares the HMAC solely over `to_signable_string` [3](#0-2) , and `Registry.process` then dispatches to a handler keyed by the unsigned `request.topic` once `validate` returns true [4](#0-3) .

### Finding Description
The claimed binding — "topic value acted on by host app == a value inside `to_signable_string`" — is false. `to_signable_string` is exactly `@raw_body`, nothing else [1](#0-0) . `topic`, `shop`, `api_version`, and `webhook_id` are all pulled from `@headers` via `shopify_header`, which is populated straight from the request headers passed to `Request.new`, with no cross-check against the body [5](#0-4) . `HmacValidator.validate`/`validate_signature` only ever hash `verifiable_query.to_signable_string` (the body) against the secret, and compare that to the `hmac` header [6](#0-5) . `Registry.process` trusts this: it validates the HMAC, then looks up and invokes the handler using `request.topic` (unsigned) and passes `request.topic`/`request.api_version` (unsigned) into `WebhookMetadata` for the handler to branch on [4](#0-3) .

Attack flow: the attacker registers their own webhook endpoint on their own development shop (any topic, e.g. `orders/create`) and receives a legitimately, correctly-HMAC'd `(raw_body, hmac)` pair from Shopify using the *victim app's* secret (this is normal, since the app's secret is shared across all shops that install it, and HMAC validation is per-app not per-shop). The attacker then POSTs that exact `raw_body` and `X-Shopify-Hmac-Sha256` header directly to the victim app's single shared webhook-receiving endpoint, but sets `X-Shopify-Topic: shop/redact` (or `app/uninstalled`) instead of the original topic. `HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches, so `validate` returns `true`. `Registry.process` then dispatches to whatever handler is registered for `shop/redact`/`app/uninstalled`, passing the attacker's body as if it were a legitimate redact/uninstall payload for the topic the attacker chose. No code in this gem checks that the topic in the signed payload corresponds to the topic header, because the topic is never in the signed payload at all.

None of the existing guards prevent this: `HmacValidator.validate` only proves the bytes of `@raw_body` were signed by someone holding the secret — it says nothing about which topic that body was originally issued for [7](#0-6) . `Request#initialize` only checks for header *presence*, not correlation with body content [8](#0-7) .

### Impact Explanation
Any app that exposes a single/shared webhook endpoint and dispatches privileged behavior based on `Request#topic` (as `Registry.process` does) can be tricked into running the handler for a sensitive topic (e.g. `shop/redact`, `customers/redact`, `app/uninstalled`) using a body the attacker legitimately obtained for a harmless topic from their own shop. This is a cross-tenant/authentication-bypass style issue: the attacker never needs the app's `client_secret`, only a legitimately-issued webhook for any topic on any shop that has the app installed (including their own). The blast radius depends on what the host's handler does with the topic-driven data — for GDPR-style redact handlers this could trigger deletion or state changes for a merchant, driven entirely by attacker-forged headers.

### Likelihood Explanation
Preconditions: (1) the attacker has installed the app on a shop they control and can receive at least one legitimately-signed webhook (trivial, any developer/attacker can do this), and (2) the host app implements a single endpoint dispatching on `request.topic` per the gem's documented `Registry.process` pattern, and its handler logic for the target topic acts on attacker-influenced body content or simply on the fact the topic fired. This is the gem's own documented usage pattern (`Registry.process`), so it is a realistic, low-cost, repeatable attack — one HTTP replay per attempt, against any app instance using this gem's webhook registry.

### Recommendation
Bind the topic (and ideally shop/api-version) into the signed material, or otherwise validate that the topic asserted in the header matches server-side expectations before dispatch — e.g., have `HmacValidator`/`Registry.process` verify topic against an out-of-band record (such as the webhook_id looked up from Shopify) rather than trusting the `X-Shopify-Topic` header verbatim once HMAC-over-body succeeds. At minimum, document that `Request#topic`/`#api_version`/`#shop` are unauthenticated and must not be used for privileged branching without additional verification.

### Proof of Concept
```ruby
# test/webhooks/topic_confusion_test.rb
require "test_helper"

class TopicConfusionTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
  end

  def test_hmac_validates_regardless_of_forged_topic
    raw_body = '{"id":1,"note":"legit orders/create payload"}'
    secret = ShopifyAPI::Context.api_secret_key
    hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", secret, raw_body)).strip

    forged_request = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "X-Shopify-Topic" => "shop/redact",       # attacker-forged, unsigned
        "X-Shopify-Hmac-Sha256" => hmac,          # valid, from attacker's own orders/create webhook
        "X-Shopify-Shop-Domain" => "victim.myshopify.com",
        "X-Shopify-Api-Version" => "2024-01",
      },
    )

    # Binding under test: topic asserted vs. topic actually signed for.
    assert ShopifyAPI::Utils::HmacValidator.validate(forged_request), "HMAC validates the body regardless of topic"
    assert_equal "shop/redact", forged_request.topic, "Attacker-forged topic is trusted despite not being signed"
  end
end
```
This demonstrates both sides of the equality diverge: `HmacValidator.validate` returns `true` based solely on `raw_body`, while `forged_request.topic` returns the attacker's chosen, unsigned value — confirming topic is never part of `to_signable_string` and is trusted downstream by `Registry.process`.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
