### Title
Cross-Tenant Webhook Forgery via Header Fields Not Covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC of the raw request body only, then trusts the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) headers—none of which are covered by the signature—to decide which tenant/shop the payload belongs to and which handler to invoke.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `HmacValidator.validate` computes the HMAC exclusively over this signable string and compares it to the `hmac` accessor, which is derived from the `shopify-hmac-sha256` header [4](#0-3) [5](#0-4) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read straight from request headers, entirely outside the signed material [2](#0-1) .

`Registry.process` uses exactly this unauthenticated `shop`/`topic` pair as the tenant/routing key after confirming only that the body's HMAC is valid: [3](#0-2) .

The broken identity binding is:
`shop that produced a validly-HMAC'd body` ≠ `shop header value the gem passes to the handler as WebhookMetadata#shop`.

Because a single `api_secret_key` is shared across every shop that installs the app, any merchant who installs the app can trigger legitimate webhook deliveries to their own endpoint (body + valid HMAC), capture that body/HMAC pair, and replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for an arbitrary victim shop domain. `HmacValidator.validate` still passes because it only checks the (attacker-controlled but genuinely-signed) body, and the gem hands the forged shop value straight to the application's webhook handler as the record's tenant.

### Impact Explanation
This lets an attacker who is a legitimate (but unprivileged relative to other tenants) app installer forge webhook events attributed to a shop they do not own—cross-tenant data injection into the consuming application's webhook handling logic (e.g., fabricated `orders/paid`, `app/uninstalled`, or GDPR `customers/redact` events processed under another shop's identity). This is a cross-tenant boundary violation reachable purely through the gem's own webhook verification API.

### Likelihood Explanation
Any user who can install the app on a shop they control (a normal, unprivileged onboarding action) can obtain a validly-signed body/HMAC pair from their own legitimate webhook traffic and replay it with a forged shop header against the shared webhook endpoint. No access to the app's `client_secret`, access tokens, or other shops' credentials is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed material that `HmacValidator` checks—or otherwise require the consuming application to cross-validate the `shop` header against a shop this specific app instance has legitimately installed—so that a body+HMAC signed for one shop cannot be replayed under a different shop's identity. At minimum, document that `Request#shop`/`#topic` are unauthenticated and that host applications must independently verify the shop is one they have on record before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook, e.g. `orders/paid`, to the app.
2. Attacker's own server captures the raw POST body `B` and the header `X-Shopify-Hmac-Sha256: H` from that delivery (`H` is a valid HMAC of `B` under the app's shared `api_secret_key`).
3. Attacker sends a new POST request to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` parses headers/body without complaint (all required headers present) [6](#0-5) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC of `B` and matches `H` — validation passes [7](#0-6) .
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, so the application processes attacker-controlled order/customer data as if it belongs to the victim shop [8](#0-7) .
