### Title
Webhook HMAC Verification Covers Only the Request Body, Not the `shop`/`topic` Headers, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` dispatches incoming webhooks based on the `shop` and `topic` values taken from HTTP headers, but the HMAC signature that is supposed to authenticate the whole webhook request only covers the raw request body. Any unprivileged party who can obtain one legitimately HMAC-signed webhook body (e.g. by installing the target app on their own free/dev store and receiving a real webhook) can replay that exact body with a forged `shop-domain`/`topic` header pointing at a different merchant, and the HMAC check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the bytes that get signed: [1](#0-0) 

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def to_signable_string
  @raw_body
end
```

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, none of them included in `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate_signature` only computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the header-supplied signature: [3](#0-2) 

Since `to_signable_string` returns only `@raw_body`, the signature check verifies nothing about `shop-domain`, `topic`, `webhook-id`, or `api-version`.

`Registry.process` then trusts these unauthenticated header-derived fields to select the handler and to tell the app which merchant/topic the payload belongs to: [4](#0-3) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

The identity binding that should hold is: `bytes verified by HMAC == bytes the handler acts on`. Here, `bytes verified by HMAC == raw_body only`, while `bytes the handler acts on == raw_body + shop + topic + webhook_id + api_version`. The `shop`/`topic` fields are unequal to what is actually authenticated, so an attacker can freely vary them while keeping a validly-signed body.

### Impact Explanation
Any actor who can obtain a single valid `(raw_body, hmac-sha256)` pair for the target app — trivially achievable by creating a free/dev store, installing the app, and letting it receive one real webhook of any topic the app subscribes to — can replay that exact body to the app's webhook endpoint while substituting:
- `x-shopify-shop-domain` (or `shopify-shop-domain`) with a victim merchant's domain, and/or
- `x-shopify-topic` with any topic the app has registered a handler for (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, `customers/data_request`).

The HMAC check still passes (it only verified the body bytes), and the host app's handler executes believing the payload is a legitimate, Shopify-issued event for that victim shop/topic. Depending on the app's handler logic this can trigger cross-tenant actions such as wiping/uninstall cleanup for a victim shop, issuing GDPR redact/erasure flows against a victim's data, or otherwise mutating another tenant's state — a cross-tenant access impact.

### Likelihood Explanation
No secret, token, or privileged access is required — only the ability to install the target app on any store (including a free development store) to harvest one legitimately signed payload, and then send a crafted HTTP request with attacker-chosen headers but the harvested body to the app's public webhook endpoint. The gem itself performs the HMAC check via `Registry.process`/`HmacValidator`, and offers no protection binding the header-derived `shop`/`topic` to the signed bytes, so any app relying on this library's webhook verification "out of the box" is affected.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the signable string (or otherwise cryptographically bind them to the HMAC), matching the semantics of Shopify's actual webhook verification contract, so that spoofing any of these header values invalidates the signature.

### Proof of Concept
1. Install the target app (using this gem) on an attacker-controlled development store; capture a legitimate webhook delivery, e.g. `orders/create`, noting the raw request body `B` and its `X-Shopify-Hmac-Sha256` header value `H` (valid because `H == HMAC-SHA256(secret, B)`).
2. Send a new POST request to the app's webhook endpoint with the exact same body `B` and header `X-Shopify-Hmac-Sha256: H`, but change:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: app/uninstalled` (or any other topic the app has a registered handler for)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(secret, B)` and finds it equal to `H` — validation succeeds.
4. The app's `app/uninstalled` handler is invoked with `shop: "victim-shop.myshopify.com"`, causing the app to run its uninstall/cleanup logic against the victim's tenant data, despite the victim never uninstalling anything.
