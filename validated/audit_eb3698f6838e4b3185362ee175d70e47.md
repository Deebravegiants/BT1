### Title
Webhook shop identity spoofing — HMAC covers only the request body, not the `shop-domain` header used for tenant attribution - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . The `shop-domain` header, read via `Request#shop` [3](#0-2) , is never included in the signed material. Yet `Registry.process` trusts this unauthenticated header as the tenant identity and forwards it straight into the handler's `WebhookMetadata` [4](#0-3) , and `WebhookMetadata.shop` is a plain, unauthenticated `String` field consumed by the app's handler [5](#0-4) .

### Finding Description
The identity binding broken is: `shop header used by handler` ≠ `shop covered by HMAC (none)`. Shopify's webhook HMAC in this library authenticates "this body byte-string was produced with `api_secret_key`" but says nothing about which store the header claims it originated from. An attacker who can obtain **any** genuine `(body, hmac)` pair signed with the app's secret — trivially achievable by installing the app themselves on their own (or a free/trial) Shopify store and capturing one of their own real webhook deliveries — can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g. a victim's store domain). `HmacValidator.validate` will report success because it only checks the body bytes against the HMAC, never the shop header [6](#0-5) , and `Registry.process` then dispatches to the handler believing the event pertains to the spoofed shop [7](#0-6) .

This is a direct instance of the analog class "a field acted on but not covered by the HMAC": the tenant-identifying field (`shop`) is acted upon by application logic keyed off `WebhookMetadata#shop`, but that field carries no cryptographic binding to the authenticated payload.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing, allowing cross-tenant data confusion/injection: an attacker-controlled body (crafted by choosing what events/data occur on their own store, e.g. `app/uninstalled`, `shop/update`, `customers/redact`, or arbitrary custom app webhook payloads) can be attributed to any other merchant's shop domain the attacker chooses, and the host application's handler will process/store/act on it as if it were genuine data for that victim shop. Depending on how the host app keys its persistence and business logic off `data.shop` (which is the documented, intended use of this field — see `MANDATORY_TOPICS` handling for `shop/redact`, `customers/redact`, `customers/data_request` [8](#0-7) ), this can trigger cross-tenant data corruption, spurious deletion/redaction of a victim shop's records, or forced app-uninstall bookkeeping for a shop the attacker doesn't control — a cross-tenant impact.

### Likelihood Explanation
Exploitation requires only: (1) obtaining one genuine `(body, hmac)` pair — attainable by any unprivileged party who installs the app on a store they control (including free/dev stores) and captures one delivered webhook, and (2) sending a raw HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header, no `api_secret_key` or victim credentials required. This is fully reachable through the library's own public API surface (`ShopifyAPI::Webhooks::Registry.process`), which is exactly what host apps are documented to call for every inbound webhook.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the value verified by the HMAC check, or otherwise force the caller to independently authenticate the shop before trusting it — e.g., require the host application to compare `request.shop` against a shop it already has a valid, previously-established session/webhook-registration record for, and reject/flag mismatches. At minimum, `HmacValidator`/`Request#to_signable_string` should be changed (or documented loudly) so that library consumers understand `shop` is not authenticated by the HMAC and must not be trusted as a tenant key without additional verification (e.g., cross-checking against the shop stored for the given `webhook_id`/topic subscription, since Shopify's own webhook delivery guarantees are per-registered-shop).

### Proof of Concept
1. Attacker creates/uses a free Shopify dev store and installs the target app; app registers a webhook (e.g. `app/uninstalled`).
2. Shopify delivers a genuine webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker captures `B` and the HMAC value from their own network traffic (they own this store, so no bypass of any authorization boundary is needed to observe it).
4. Attacker sends a new POST to the same public webhook endpoint with body `B` unchanged, `x-shopify-hmac-sha256` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (it only checks `B` against the HMAC) [9](#0-8) .
6. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` [4](#0-3) , causing the host app to process attacker-controlled event data as belonging to the victim's store.
