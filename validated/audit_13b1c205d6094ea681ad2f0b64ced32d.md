### Title
Webhook `shop` domain is trusted for tenant dispatch but is excluded from the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, while the `shop` value used downstream for tenant identification comes from an unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` straight to the host application's handler as trusted tenant context, without that value ever being covered by the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the whole request "did indeed come from Shopify" and then forwards `request.shop` (the unsigned header) directly into `WebhookMetadata`, which is passed to the app's registered handler as the tenant identifier: [4](#0-3) 

The equality the gem is implicitly asserting is:
`shop bound by HMAC == shop acted upon by the handler`

but in reality:
`shop bound by HMAC (∅, not signed) ≠ shop acted upon by the handler (request.shop, from header)`

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app (it is not shop-specific), an unprivileged internet user who has installed the target app on their own Shopify store can obtain a validly-signed webhook body+HMAC pair for any subscribed topic (e.g., by triggering the corresponding event on their own store, or by controlling the body content sent to a store they own). They can then replay that same body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. The HMAC still validates (it only covers the body), and the handler receives `data.shop` = victim shop, `data.body` = attacker-controlled payload.

This is the exact "field acted on but not covered by the HMAC" analog: the API's own documentation and `WebhookMetadata` struct instruct host apps to use `data.shop` as the tenant key (e.g., `shop_domain: data.shop` in the example handler) for enqueuing tenant-scoped work, database writes, or emails — all while the gem provides zero cryptographic binding between the verified signature and that value.

### Impact Explanation
This breaks the tenant isolation boundary the gem is expected to enforce for webhook processing. A single unprivileged actor who is a legitimate merchant/user of the app (with no elevated privileges, no access token, no `client_secret` beyond what's implicit in installing the app) can inject arbitrary webhook events attributed to any other shop that uses the app, resulting in cross-tenant data manipulation in the host application (e.g., fabricated `orders/create`, `app/uninstalled`, or `shop/redact` events processed against a victim tenant's records). This matches the Critical "cross-tenant access" impact category, since it is a cross-tenant identity/data injection vulnerability rooted entirely in this gem's verification logic.

### Likelihood Explanation
Likelihood is high for any app author who follows the gem's own documented pattern (using `data.shop` from `WebhookMetadata` as the tenant key, as shown in `docs/usage/webhooks.md`). No secret material beyond a legitimate, ordinary app installation is required by the attacker — they only need one shop where the app is installed to obtain a validly-HMAC-signed webhook body, then replay it with a forged shop header. The `HmacValidator` and `Request` classes provide no warning or mechanism preventing this misuse.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the HMAC-verified content, or otherwise cryptographically tie the signature to the full set of header values that the handler relies on — not just the raw body. At minimum, `Request#to_signable_string` should incorporate the shop-domain header (and other trusted headers) so that `HmacValidator.validate` cannot pass for a body that was signed for one shop but replayed with a different shop header. Documentation and the `WebhookMetadata` contract should make explicit that `shop` is only as trustworthy as what is actually covered by the signature.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` (ordinary merchant flow, no privileges needed).
2. Attacker triggers (or otherwise obtains) a legitimately Shopify-signed webhook for a subscribed topic, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker POSTs to the app's webhook endpoint with the *same* body `B` and *same* `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in [5](#0-4)  succeeds because it only checks `H` against `B`.
5. `Registry.process` in [4](#0-3)  calls the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, and the app performs tenant-scoped work as if the event genuinely originated from the victim shop.
