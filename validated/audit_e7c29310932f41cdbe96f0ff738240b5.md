### Title
Escrow accounting in Tron `IntentGatewayV2.placeOrder` credits promised amounts instead of actual tokens received, breaking accounting for fee-on-transfer tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) escrows `reducedInputs[i].amount` (a value derived purely from `order.inputs[i].amount` minus protocol fee) into `_orders[commitment][token]` after calling `safeTransferFrom`, without ever verifying how many tokens the contract actually received. This is the same bug class as the referenced Sherlock finding: for fee-on-transfer (deflationary) ERC20 tokens, the contract credits more escrow than tokens it actually holds.

### Finding Description
In `placeOrder`, the commitment and `reducedInputs` are computed up-front from the user-supplied `order.inputs[i].amount` (lines 356-385) — before any transfer occurs. In the non-predispatch branch: [1](#0-0) 
tokens are pulled via `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then `_orders[commitment][token] += reducedInputs[i].amount` is credited using the pre-computed, promised amount — not the delta of `balanceOf(address(this))` before/after the transfer.

The predispatch branch (lines 416-446) is slightly better in that it reads `balance = IERC20(token).balanceOf(dispatcher)` before sweeping, but it still credits `_orders[commitment][token] += reducedInputs[i].amount` (the promised/reduced amount) rather than the amount actually received by `address(this)` after the sweep transfer — which itself can be taxed again if the token is fee-on-transfer, per the `dispatcherReceived`/`gatewayReceived` double-tax scenario demonstrated in the test suite for the fixed main EVM contract: [2](#0-1) 

This is a regression relative to the fixed `evm/src/apps/IntentGatewayV2.sol`, which explicitly measures `balanceOf` before and after each transfer and mutates `order.inputs[i].amount` to the actual received value before computing the commitment and crediting escrow: [3](#0-2) [4](#0-3) 

The Tron contract never performs this balance-based measurement: [5](#0-4) [6](#0-5) 

### Impact Explanation
`_orders[commitment][token]` is the accounting ledger used by `cancelOrder`/`withdraw` to refund escrowed funds and by the fill/redeem-escrow flow to release settlement funds to solvers/fillers (confirmed via `cancelOrder`'s use of `WithdrawalRequest({commitment, tokens: order.inputs, beneficiary})` and `withdraw(body, true)`): [7](#0-6) 

If a fee-on-transfer token is used as an order input, the contract will hold strictly less of that token than the sum of `_orders[commitment][token]` entries across all orders. This causes an under-collateralization of the escrow ledger relative to actual balances. Any order redeemed/cancelled/filled after other under-collateralized orders exist can outrun the actual token balance, causing either: (a) a revert that permanently freezes that user's/solver's ability to redeem (denial of service / stuck funds), or (b) if the withdraw path uses `transfer` of tracked amounts sequentially, earlier redeemers draining the pool such that later redeemers receive less than entitled or nothing — matching the "late redeemers left without tokens" impact in the original report. This is a fund-freezing/fund-loss bug reachable by any unprivileged user submitting `placeOrder` with a fee-on-transfer input token.

### Likelihood Explanation
Reachable by any external, unprivileged caller in a single transaction (`placeOrder`) — no special privileges required, and fee-on-transfer / deflationary tokens are a documented common token pattern that the project's own test suite for the main EVM contract already anticipates and tests against (see `FeeOnTransferToken` test contract). The Tron variant simply lacks the corresponding fix.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` immediately before and after each `safeTransferFrom`/sweep, use the actual delta as `order.inputs[i].amount` before computing `reducedInputs`, the `commitment` hash, and the `_orders[commitment][token]` credit — for both the direct-transfer branch and the predispatch/sweep branch (including the potential double-taxation case when tokens pass through the call dispatcher).

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and a fee-on-transfer ERC20 token (e.g., 1% fee, as modeled by `FeeOnTransferToken` in the test suite).
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch.
3. Contract executes `safeTransferFrom(user, address(this), 1000e18)`; due to the 1% fee, the contract's actual FOT balance increases by only 990e18.
4. Contract nonetheless sets `_orders[commitment][FOT] += reducedInputs[0].amount` using (approximately) 1000e18 (minus protocol fee if configured), i.e., more than the 990e18 actually held.
5. Repeat with additional orders using the same FOT token; the sum of all `_orders[...][FOT]` entries exceeds `FOT.balanceOf(address(intentGateway))`.
6. When orders are cancelled/filled and `withdraw` attempts to pay out the tracked escrow amounts, the contract cannot satisfy every entry — later redeemers experience reverts (frozen funds) or receive less than their recorded escrow entitlement.

    /// @notice Fee-on-transfer through the predispatch path: escrow reflects actual received.
    function testPlaceOrder_FeeOnTransferToken_Predispatch() public {
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% transfer fee
        fot.mint(user, 10000 * 1e18);

        uint256 predispatchAmount = 1000 * 1e18;
        // After transferring to dispatcher: 1% fee = dispatcher receives 990
        uint256 dispatcherReceived = predispatchAmount - (predispatchAmount * 100) / 10000;
        // After dispatcher transfers to gateway: another 1% fee = gateway receives ~980.1
        uint256 gatewayReceived = dispatcherReceived - (dispatcherReceived * 100) / 10000;

        // Predispatch: send FOT to dispatcher, the "call" is a no-op (empty calls array)
        TokenInfo[] memory predispatchAssets = new TokenInfo[](1);
        predispatchAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: predispatchAmount});

        // The predispatch call is an empty Call[] dispatch (no-op, tokens just sit on dispatcher)
        Call[] memory emptyCalls = new Call[](0);
        bytes memory predispatchCall = abi.encode(emptyCalls);

        // Inputs: expect the FOT that lands on dispatcher after predispatch
        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: dispatcherReceived});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 500 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: predispatchAssets, call: predispatchCall}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), predispatchAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received (double fee-on-transfer)
        assertEq(fot.balanceOf(address(intentGateway)), gatewayReceived, "Gateway should hold double-taxed amount");

        // Reconstruct commitment
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = gatewayReceived; // mutated to actual received
        bytes32 commitment = keccak256(abi.encode(order));

        assertEq(
            intentGateway._orders(commitment, address(fot)),
            gatewayReceived,
            "Escrow should match actual received after double transfer fee"
        );
