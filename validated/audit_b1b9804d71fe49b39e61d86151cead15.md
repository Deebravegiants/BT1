## Title
Webhook shop attribution is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts the `shop` value taken from webhook HTTP headers to attribute an incoming webhook to a tenant, but that header is never included in the HMAC signature that is verified before processing. This breaks the identity binding `shop_verified_by_hmac == shop_attributed_to_event`, letting anyone who can obtain one validly-signed webhook body (e.g. a legitimate merchant using the same multi-tenant app) replay it directly to the app's public webhook endpoint while swapping the `shop-domain` header to point at a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes/verifies the HMAC exclusively against this signable string: [2](#0-1) 

`shop` (and `topic`, `webhook_id`) are read straight from HTTP headers and are not part of the signed content: [3](#0-2) 

`Registry.process` first validates the HMAC, then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's registered handler, without any further binding check between the verified bytes (body) and the unverified header (`shop`): [4](#0-3) 

Because the HMAC only proves "this body was signed with the app's `client_secret`" and says nothing about which shop it came from, an attacker who can obtain one legitimately-signed payload (trivial if the attacker is a merchant who has installed the same multi-tenant app, since Shopify sends them real, validly-signed webhooks for their own shop) can resubmit that exact body to the app's public webhook URL with an arbitrary `X-Shopify-Shop-Domain`/`shopify-shop-domain` header. The signature check still passes (it only checks the body), and the app's handler will process the event as if it belongs to the spoofed shop.

This is the webhook analog of the audited bug: a privileged actor (here, the HMAC-authenticated body) is allowed to change an unrelated, unauthenticated setting (the shop attribution) without any additional verification — the same "acted-on-but-not-covered-by-signature" identity gap.

### Impact Explanation
Any handler that uses `data.shop` (from `WebhookMetadata`) to select which tenant's records to create/update/delete is exposed to cross-tenant data injection or corruption: an attacker-controlled body can be attributed to any other shop using the app, without needing that shop's access token or `client_secret`. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires only: (1) the attacker be a legitimate, unprivileged user of the same multi-tenant app (a normal merchant install, not a privileged account), which yields real, validly HMAC-signed webhook bodies for their own shop; and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with modified headers — no TLS interception, no leaked credentials, and no host cooperation beyond the documented webhook endpoint being internet-reachable, which it must be for Shopify itself to reach it.

### Recommendation
Bind the trusted shop identity to the verified payload instead of an unauthenticated header:
- Include `shop-domain` (and `topic`/`webhook_id`) in the signable string used for HMAC verification, or
- After HMAC verification, cross-check the header-derived `shop` against an independent, authenticated source (e.g. look up the webhook subscription owner via the Admin API using the `webhook_id`) before dispatching to the handler, rather than trusting the header value directly.

### Proof of Concept
1. Attacker installs the target multi-tenant app on their own shop `attacker.myshopify.com` and receives a real webhook, e.g.:
   - Body: `{"id":1,...}`
   - Headers: `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`
2. Attacker resends the identical body and HMAC header to the app's public webhook endpoint, but replaces the domain header:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `Utils::HmacValidator.validate` succeeds because it only checks the body against the HMAC (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the app's handler, which processes attacker-controlled data under the victim's tenant.
