### Title
Withdraw can permanently revert via unguarded `checked_sub().unwrap()` panic when pending PnL and near-full LP redemption interact - (File: `program/src/processor.rs`)

### Summary
`process_withdraw` and `calc_take_pnl` chain several independently-rounded, decimal-normalized quantities into sequential `checked_sub(...).unwrap()` operations when updating `target_orders.calc_pnl_x`/`calc_pnl_y`. Because the "pnl" portion (`delta_x`/`delta_y`) and the "withdrawn" portion (`pc_amount`/`coin_amount`) are computed through independent `normalize_decimal_v2`/`restore_decimal` round-trips (each of which truncates), the two subtracted quantities are not guaranteed to sum to no more than `x1`/`y1`. This is structurally the same bug class as the reported `DIAWhitelistedStaking` issue: a value used for accounting is derived from a formula that can legitimately return a result the code did not anticipate, and an `assert`/`unwrap` guarding a downstream state update then panics, aborting the transaction and blocking the underlying action.

### Finding Description
In `calc_take_pnl`, `diff_x`/`diff_y` (and thus `delta_x`/`delta_y`) are computed purely from the normalized values `x1`,`y1` and `target.calc_pnl_x`/`calc_pnl_y`: [1](#0-0) 
`pc_pnl_amount`/`coin_pnl_amount` (native units) are then derived from `diff_x`/`diff_y` via `restore_decimal`, and used to mutate `*total_pc_without_take_pnl` in place: [2](#0-1) 

Back in `process_withdraw`, `pc_amount`/`coin_amount` are computed from this **already pnl-adjusted** `total_pc_without_take_pnl`, using the user's LP share (`withdraw.amount < amm.lp_amount` is the only bound, enforced at line 1716): [3](#0-2) 

Finally, `target_orders.calc_pnl_x`/`calc_pnl_y` are updated by subtracting **both** the normalized withdrawn amount and `delta_x`/`delta_y` from the *original* (pre-pnl) normalized value `x1`/`y1`, with no `saturating_sub` or explicit error handling: [4](#0-3) 

Because `delta_x` is derived from `x1` via one truncating round-trip (`normalize_decimal_v2` → `restore_decimal` → back to normalized `diff_x`), and `pc_amount` is derived from the pnl-adjusted native total via a *second, independent* rounding path (`checked_sub` in native units, then `exchange_pool_to_token`, then `normalize_decimal_v2` again), the two quantities being subtracted from `x1` are not provably bounded by `x1` in all cases — particularly when `withdraw.amount` approaches `amm.lp_amount` (near-full redemption of the remaining LP supply, which is explicitly allowed as long as `withdraw.amount < amm.lp_amount`) while `pc_decimals`/`coin_decimals` differ from `amm.sys_decimal_value`, amplifying truncation error. When the subtraction underflows, `checked_sub(...).unwrap()` panics, aborting the whole transaction.

### Impact Explanation
Because a panic reverts all state changes, the pool state (`target_orders`, vault balances) remains unchanged after a failed attempt. If no intervening swap or deposit shifts the pool's `x1`/`y1`/`calc_pnl_x`/`calc_pnl_y` relationship, an LP holder whose withdrawal size triggers the underflow will have their withdrawal instruction deterministically fail on every resubmission, effectively freezing their principal and any earned trading fees represented in the pool until an unrelated third-party transaction changes the pool state enough to avoid the underflow. This is a freezing-of-funds condition reachable by an ordinary LP through the public `Withdraw` instruction, with no privileged access required.

### Likelihood Explanation
This requires a specific combination: significant accrued (unclaimed) PnL (`target.calc_pnl_x`/`calc_pnl_y` diverging from current pool ratio) and a withdrawal size close to the full remaining `amm.lp_amount`, plus decimal configurations (`pc_decimals`, `coin_decimals`, `sys_decimal_value`) that make the double-rounding error non-negligible relative to the shrinking safety margin as `withdraw.amount → amm.lp_amount`. This is a realistic but non-trivial precondition (most withdrawals are partial, and the margin is usually well above rounding noise), so likelihood is best characterized as low-to-medium rather than easily/always triggerable in a single crafted transaction.

### Recommendation
Replace the chained `checked_sub(...).unwrap()` calls when updating `target_orders.calc_pnl_x`/`calc_pnl_y` in `process_withdraw`, `process_deposit`, and `process_withdrawpnl` with `checked_sub` returning a proper `AmmError` (e.g., `AmmError::CheckedSubOverflow`) instead of panicking, and/or recompute `pc_amount`/`coin_amount` and `delta_x`/`delta_y` from a single consistent normalized basis so the invariant `withdrawn + pnl_delta <= x1` is provable by construction rather than relying on independent rounding paths to happen to agree.

### Proof of Concept
1. Set up a pool with `pc_decimals` and `coin_decimals` different from each other and from `amm.sys_decimal_value` (a common real-world configuration).
2. Perform swaps to accumulate a meaningful `need_take_pnl_pc`/`need_take_pnl_coin` gap and a divergence between `target_orders.calc_pnl_x/y` and the live pool ratio, so `calc_take_pnl` returns non-zero `delta_x`/`delta_y` on the next `Withdraw`.
3. As the LP holding effectively the entire remaining `amm.lp_amount`, call `Withdraw` with `withdraw.amount` just below `amm.lp_amount` (the only enforced bound, `program/src/processor.rs:1716`).
4. Because `pc_amount`/`coin_amount` are computed from the pnl-reduced pool while `delta_x`/`delta_y` are computed independently from `x1`/`y1`, tune (via repeated small swaps controlling rounding) the values so that `normalize_decimal_v2(pc_amount) + delta_x > x1`, causing the `checked_sub(...).unwrap()` at `program/src/processor.rs:1826` to panic and abort the withdrawal, repeatable on every resubmission until pool state changes.
