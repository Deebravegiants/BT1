### Title
Missing `dest`-domain validation in `TokenExchange.exchange_token` allows `client_secret` exfiltration to an attacker-controlled host — (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`JwtPayload` verifies the JWT's signature and `aud` claim (`aud == Context.api_key`), but never restricts `dest`/`iss` to a Shopify-owned domain. `TokenExchange.exchange_token` takes this unvalidated `dest` value and uses it directly as the HTTP host to which the app's `client_id`/`client_secret` are POSTed via `Clients::HttpClient`, whose base URI is literally `https://#{session.shop}`.

### Finding Description
`JwtPayload#initialize` only checks the HMAC signature (HS256 with `api_secret_key`) and `aud == Context.api_key`; it never validates that `iss`/`dest` end in a trusted Shopify domain (`myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, `shopify.com`) — the same set enforced by `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. [3](#0-2) 

`exchange_token` reads `dest_shop = jwt_payload.shop` and immediately builds `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` — with **no call to `Utils::ShopValidator.sanitize!`** — then passes that session into `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`. [4](#0-3) 

`HttpClient#initialize` sets `@base_uri = "https://#{api_host || session.shop}"`, i.e., the outbound request host is taken verbatim from `session.shop` (== the JWT `dest` claim). [5](#0-4) 

The request body sent to that host includes `client_id` and `client_secret` in plaintext JSON. [6](#0-5) 

Contrast this with the sibling method `migrate_to_expiring_token`, which explicitly calls `Utils::ShopValidator.sanitize!(shop)` before building the session/host used for the same client_secret-bearing request: [7](#0-6) 

This breaks the intended identity binding: `host validated == host that receives the client_secret`. Here, the host that receives `client_secret` is bound only to "whatever string is in the JWT's `dest` claim," not to "a real Shopify-owned domain." Since `JwtPayload` never enforces the latter, any syntactically valid signed token (still requiring the correct `api_secret_key`/`aud`) with a `dest` claim pointing elsewhere is accepted.

### Impact Explanation
If a caller can influence or an app is issued a session/ID token whose `dest` claim is not restricted (JwtPayload places no domain constraint on `iss`/`dest` beyond the HS256 signature and `aud` match), the resulting HTTP POST containing the app's `client_id`/`client_secret` is sent to `https://#{dest}/admin/oauth/access_token`. This is SSRF carrying the app's `client_secret`/credentials to a host determined by an inadequately validated claim, which per the rules maps to High severity ("SSRF with the app's credentials" / "credential leakage ... into ... error output" if the destination logs the request). It's also a direct violation of the "host validated versus host that receives the `client_secret`" identity-binding class called out in scope.

### Likelihood Explanation
Exploitation requires a validly HS256-signed token with the correct `aud` (i.e., one issued for this app) but a `dest` claim value that is not a genuine Shopify domain. This is a real risk surface because: (1) `JwtPayload` deliberately performs `aud` and signature checks but the code explicitly omits any domain allowlist check like the one present in `ShopValidator`, and (2) the sibling function `migrate_to_expiring_token` demonstrates the library authors know this validation is needed for `client_secret`-bearing requests but forgot to apply it to `exchange_token`, showing the omission is a maintenance gap rather than an intentional design choice.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` through `Utils::ShopValidator.sanitize!` (or an equivalent trusted-domain check) before constructing `shop_session`/`HttpClient`, mirroring the pattern already used in `migrate_to_expiring_token`. Additionally, consider having `JwtPayload` itself enforce that `dest`/`iss` are within `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` as part of decoding, so all consumers get this guarantee automatically.

### Proof of Concept
1. Obtain (or have the app receive) a session/ID token that is HS256-signed with the app's `api_secret_key` and has `aud` equal to the app's `api_key`, but with `dest` set to `https://attacker-controlled.example` instead of a `*.myshopify.com` domain (e.g., because a compromised or misconfigured issuing flow forwards attacker-influenced `dest` unchanged).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload.new(token)` succeeds because only signature and `aud` are checked; `dest_shop` becomes `attacker-controlled.example`.
4. `Clients::HttpClient` builds `@base_uri = "https://attacker-controlled.example"` and POSTs a JSON body containing `client_id` and `client_secret` to `https://attacker-controlled.example/admin/oauth/access_token`, exfiltrating the app's `client_secret` to the attacker's host.

        end

        @iss = T.let(payload_hash["iss"], String)
        @dest = T.let(payload_hash["dest"], String)
        @aud = T.let(payload_hash["aud"], String)
        @sub = T.let(payload_hash["sub"], T.nilable(String))
        @exp = T.let(payload_hash["exp"], Integer)
        @nbf = T.let(payload_hash["nbf"], Integer)
        @iat = T.let(payload_hash["iat"], Integer)
        @jti = T.let(payload_hash["jti"], String)
        @sid = T.let(payload_hash["sid"], T.nilable(String))

        raise ShopifyAPI::Errors::InvalidJwtTokenError,
          "Session token had invalid API key" unless @aud == Context.api_key
      end

      sig { returns(String) }
