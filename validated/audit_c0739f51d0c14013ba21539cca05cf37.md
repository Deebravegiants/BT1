### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` reads the shop identity from the `X-Shopify-Shop-Domain` header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. Because the shop identity is never bound to the signature, an attacker who legitimately receives one genuine, signed webhook (by installing the app on their own store) can replay that exact body+HMAC pair while substituting a victim shop's domain in the `shop-domain` header, and the gem will treat it as an authentic, verified webhook for the victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from an unauthenticated header, independent of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string` (the body), never incorporating the shop header: [3](#0-2) 

`Registry.process` performs this HMAC check and then unconditionally forwards `request.shop` — the unauthenticated header — to the application handler as the trusted tenant identifier: [4](#0-3) 

The `WebhookMetadata` struct and gem documentation confirm `shop` is meant to be trusted tenant-identifying data, used by apps (per the documented pattern) to route/store per-shop data such as `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`: [5](#0-4) [6](#0-5) 

This is the same class of bug as the report: an identity/binding field (`squeethEthPrice`'s TWAP window vs. the value actually checked elsewhere) is inconsistent with what is actually verified. Here the binding broken is:
`hmac_valid(body) == true` is treated as implying `shop_header == actual_originating_shop`, but the signature never covers `shop_header`, so these two are not actually bound together.

### Impact Explanation
Because the api_secret_key (HMAC key) is shared across all shops that install a given app, any shop — including one controlled by an attacker who simply installs the target app (an unprivileged action available to any internet user for public apps) — can obtain a validly-signed webhook body+HMAC pair. The attacker can replay that exact body/HMAC to the app's webhook endpoint while swapping the `shop-domain` header to a victim's `myshopify.com` domain. `Registry.process` will validate it successfully (since only the body is checked) and hand the handler attacker-chosen webhook `topic`/`body` data labeled with the victim's shop — a cross-tenant data injection/impersonation into the victim's tenant context. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that: (1) is a public app installable by arbitrary merchants, and (2) uses `data.shop` from `WebhookMetadata` as the trusted shop identifier for routing/storage, which is the pattern explicitly documented by this gem. No credentials beyond having installed the app on an attacker-owned store are required.

### Recommendation
Bind the shop identity into the signed material, or otherwise verify it out-of-band:
- Include the `shop-domain` (and ideally `webhook-id`/`api-version`) header values in `to_signable_string` so they are covered by the HMAC, or
- Cross-check the header's shop domain against an independently-verified source (e.g., confirm a session/registration exists for that shop and topic) before invoking the handler, or
- At minimum, document prominently that `data.shop` in `WebhookMetadata` is NOT cryptographically bound to the HMAC and must not be trusted as a tenant identifier without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over body B>`
   - Body: `B`
3. Attacker captures this request, then replays it to the same endpoint with the header changed:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - Same body `B`, same (still-valid) HMAC header.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `body` against the shared secret's HMAC — the `shop-domain` header is not part of the signable string.
5. The app's handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker-controlled>, ...)` and processes it as if it came from `victim.myshopify.com`.
