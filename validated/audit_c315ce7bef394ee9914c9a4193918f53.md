### Title
Unbounded gas forwarding in `EvmHost.dispatchIncoming` lets a malicious destination module grief relayers and DoS batched message delivery - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchIncoming(PostRequest, address relayer)` forwards an incoming POST request to the destination application's `onAccept()` callback using a raw, gas-unbounded `.call()`. Any attacker can deploy a malicious "app" contract as the request's `to` destination and have its `onAccept` consume near-arbitrary amounts of gas (e.g., an infinite loop bounded only by the 63/64 forwarding rule), exactly mirroring the referenced Sherlock finding where `safeTransferFrom`'s callback is used to force unbounded gas consumption on the caller.

### Finding Description
`dispatchIncoming` performs:
```solidity
(bool success,) = address(destination)
    .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
``` [1](#0-0) 

There is no gas stipend/limit passed to this `.call`, so essentially all remaining gas in the relayer's transaction is forwarded to the destination contract. The same unbounded-gas pattern also exists in the sibling dispatch paths for GET responses and timeouts:
```solidity
(bool success,) = _bytesToAddress(response.request.from)
    .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));
``` [2](#0-1) 
```solidity
(bool success,) = _bytesToAddress(timeout.request.from)
    .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));
``` [3](#0-2) 
```solidity
(bool success,) = _bytesToAddress(timeout.request.from)
    .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));
``` [4](#0-3) 

A grep of `evm/src/**` confirms no gas-limited calls (`gas:`/`gasleft`/`GAS_LIMIT`) exist anywhere in the host/handler dispatch code besides an unrelated paymaster utility, confirming this is a systemic gap rather than an isolated instance.

These dispatch calls are triggered by `HandlerV2` (the ISMP message handler) after a relayer submits a `PostRequestMessage`/`GetResponseMessage`/timeout message with a valid membership proof — i.e., any unprivileged relayer processing any user-submitted cross-chain request reaches this call path. Since `request.to` (and `request.from` for responses/timeouts) is fully attacker-controlled application data coming from the source chain, an attacker can dispatch a POST request whose destination is a contract they control that implements `onAccept()` to burn gas (e.g., a busy-loop, as in the referenced `BadBull` PoC), or which uses reentrant/expensive state writes.

### Impact Explanation
This directly parallels the referenced issue's root cause (unbounded external call gas during settlement/callback execution) applied to Hyperbridge's message-delivery path:
- **Relayer griefing / economic DoS**: A relayer must supply enough gas to survive the malicious callback or the whole batched `handlePostRequests`/`batchCall` transaction reverts (per Sherlock PoC pattern, gas up to ~2.7M+ can be consumed by a trivial busy loop, and unbounded loops can consume far more, up to the full block gas limit). Relayers are only compensated with a pre-agreed relayer fee set at request-dispatch time, so an attacker can make relaying a specific malicious request or an entire batch containing it unprofitable or outright impossible without the relayer either overpaying gas or refusing to relay it.
- **Delivery-route failure for legitimate messages**: Since `HandlerV2` supports `batchCall` for processing multiple requests together, a single malicious request planted in a batch can consume enough gas to starve subsequent legitimate `dispatchIncoming` calls in the same transaction, or force relayers to process malicious and legitimate messages separately at higher cost — degrading the reliability of the message-delivery route.
- Unlike the audited protocol (where the `try/catch` at least contains the failure to the `settleContract` function), `EvmHost.dispatchIncoming` uses a raw `.call` without even an explicit gas cap, making the exposure strictly worse: an attacker-controlled destination can consume essentially all available gas in the relayer's transaction, not just enough to make one branch expensive.

This matches the requested criteria of "a route unable to deliver messages" caused by an unbounded gas external call reachable from a permissionless relayed message.

### Likelihood Explanation
High likelihood: `request.to`/`request.from` are attacker-controlled bytes decoded to an address with no restriction on being a contract with hostile `onAccept`/`onGetResponse`/`onGetTimeout`/`onPostRequestTimeout` implementations, and any user can dispatch a POST request to Hyperbridge targeting an arbitrary destination contract on the receiving chain. No privileged role is required — the request originates from a standard cross-chain dispatch and is delivered by an unprivileged relayer submitting a valid membership proof through `HandlerV2`.

### Recommendation
Apply an explicit gas stipend to all destination callback calls in `EvmHost` (`dispatchIncoming` for both `PostRequest` and `GetResponse`, and both `dispatchTimeOut` overloads), analogous to the audit's fix:
```solidity
uint256 private constant CALLBACK_GAS_LIMIT = /* fixed, safe value */;
(bool success,) = destination.call{gas: CALLBACK_GAS_LIMIT}(
    abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer))
);
```
Ensure the limit is generous enough for legitimate application logic (or configurable per-app/per-message with a maximum cap) but bounded so a single malicious destination cannot consume the entire remaining transaction gas. Apply the same treatment consistently to `onGetResponse`, `onGetTimeout`, and `onPostRequestTimeout` calls in `EvmHost.sol`.

### Proof of Concept
1. Attacker deploys `MaliciousApp` on the destination chain implementing:
```solidity
function onAccept(IncomingPostRequest calldata) external {
    while (true) { _junk += 1; } // consumes ~63/64 of forwarded gas
}
```
2. Attacker dispatches a `PostRequest` on the source chain with `to = address(MaliciousApp)` via the normal dispatch flow.
3. Once the challenge period elapses, any relayer submits the request with a valid membership proof to `HandlerV2`, which verifies the proof and calls `IHost.dispatchIncoming(request, relayer)`.
4. `EvmHost.dispatchIncoming` executes `destination.call(...)` with no gas cap [1](#0-0) , forwarding nearly all remaining gas into `MaliciousApp.onAccept`, which spins until it exhausts that gas.
5. The relayer's transaction either reverts entirely (if using `batchCall` with other legitimate messages bundled) or must be sent with an inflated, attacker-dictated gas limit purely to survive this one malicious request — the same "gain a trading/economic edge by exploding transaction cost" mechanism described in the source report, here degrading Hyperbridge's message-delivery reliability and relayer economics instead of a specific counterparty's settlement.
