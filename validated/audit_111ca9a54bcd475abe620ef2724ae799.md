### Title
Hostile HyperSwap V2 pre-seed can outsize the rebalance budget in `_seedRebalancing`/`_pairRebalance`, letting an attacker's LP capture graduation liquidity at an off-curve price - ([File: packages/contracts/src/Bonding.sol])

### Summary
The external CVE is a TOCTOU: git's symlink check at clone time is stale by the time the hardlink operation actually runs, letting an attacker race a benign file into a malicious symlink between check and use. alt.fun has the same "compute-then-act-later-against-mutable-state" shape in the permissionless two-phase graduation: Phase 1 (`Bonding._enterGraduating` → `_prepareGraduationLiquidity`) freezes `tokensForLP`/`ltFromPair` at the curve's closing price, but Phase 2 (`finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` / `_pairRebalance`) is a separate, permissionless transaction that only *tries* to correct whatever HyperSwap V2 pair state exists at call time, under a swap budget capped by Bonding's own inventory rather than by what is actually needed to restore the cached ratio.

### Finding Description
`triggerGraduation`/the threshold-crossing buy caches `(tokensForLP, ltFromPair)` in `pendingGraduation[token]` at the curve's exact closing price [1](#0-0) . Nothing about `finalizeGraduation` is time-bound or access-controlled, and the HyperSwap V2 `TOKEN/LT` pair can be created and pre-seeded by anyone before Phase 2 runs — `_ensureUniswapV2Pair` will happily return an attacker's pre-created pair [2](#0-1) .

When Phase 2 finally runs, `_seedUniswapV2Direct` only special-cases (1) an empty pool and (2) a pure-donation pre-seed via `skim` [3](#0-2) . For a genuine hostile *mint* pre-seed (attacker calls `pair.mint` themselves to establish a self-owned LP position at an arbitrary ratio), `_seedRebalancing` only takes the "overpower with direct mint" fast path when **both** reserves are below `DIRECT_MINT_PRESEED_BPS` of the cached targets [4](#0-3) . Above that band, it instead calls `_pairRebalance` with `maxSwap = _swapBudget(_ltSwapInventory(lt, protectedLT))` — a budget derived from **Bonding's own graduation inventory**, not from the amount actually required to move the pool back to the cached `tokensForLP/ltFromPair` ratio [5](#0-4) . The natspec itself concedes the captured-share bound "vanishes for any seed that small," i.e. it does **not** hold for larger seeds [6](#0-5) . When the swap budget is insufficient to fully correct an oversized attacker ratio, the subsequent `router.addLiquidity(min=1, min=1)` deposit leg (`_routerDepositAndDispose`, referenced but not further gated by a price check) pulls Bonding's remaining `tokensForLP`/`ltFromPair` inventory at the pool's *then-current* (still attacker-skewed) ratio rather than at the curve-close ratio the cache was designed to preserve.

This is the direct analog of the CVE's race: a check performed at one point in time (curve-close price frozen in Phase 1) is later relied upon by an operation (`addLiquidity`/`pair.swap`) that actually executes against a different, attacker-controlled resource state (the live HyperSwap pair) in a later, unsynchronized transaction — brick-resistance was preserved but price-correctness was not, matching the explicitly in-scope "LP seeded away from the curve close price" impact class.

### Impact Explanation
An attacker who front-runs `finalizeGraduation` with a large enough self-minted LP position on the HyperSwap `TOKEN/LT` pair, sized above `DIRECT_MINT_PRESEED_BPS` and beyond what Bonding's capped `maxSwap` budget can correct, forces the deposit leg to lock LP at the attacker's chosen ratio instead of the curve's closing price. Because the attacker holds LP shares proportional to their own pre-seed plus the resulting pool composition, they can withdraw liquidity post-graduation at a favorable ratio, effectively extracting value from the curve-raised LT and the 250M `LP_RESERVE` tokens that Bonding deposits — a transfer of graduation liquidity value from the protocol/traders to the attacker's LP position.

### Likelihood Explanation
`finalizeGraduation` is explicitly permissionless with no deadline, and creating/minting into a HyperSwap V2 pair before Bonding does is a normal, unprivileged action any address can take; the AGENTS.md doc even frames "hostile mint pre-seed" as an anticipated (but only partially bounded) attack shape. The only missing ingredient for exploitation is sizing the pre-seed pool such that at least one reserve exceeds `DIRECT_MINT_PRESEED_BPS` of the cached target while also exceeding what `_swapBudget`/`_ltSwapInventory` can correct — feasible for any attacker willing to size their own capital relative to the graduating token's curve depth, which is public/computable pre-graduation.

### Recommendation
Bound `_seedRebalancing`/`_pairRebalance`'s deposit leg by an explicit minimum-out / max-slippage check against the cached curve-close ratio (`tokensForLP`/`ltFromPair`) rather than only against the router's raw `quote()`; if the pool cannot be rebalanced within budget to within an acceptable tolerance of that ratio, revert-and-retry-later or fall back to a burn/refund path instead of depositing Bonding's inventory at a still-skewed ratio at `addLiquidity(min=1)`.

### Proof of Concept
1. Attacker watches for a token nearing graduation (public `canGraduate`/`previewLtUntilGraduation`).
2. Right after Phase 1 fires (`TokenGraduating`) and before the keeper's `finalizeGraduation` lands, attacker calls the HyperSwap V2 factory's permissionless `createPair(TOKEN, LT)` (or reuses `_ensureUniswapV2Pair`'s target), then `transfer`s a large, deliberately skewed amount of TOKEN/LT into it and calls `pair.mint(attacker)` to capture LP at that ratio, sized above `DIRECT_MINT_PRESEED_BPS` of the cached `tokensForLP`/`ltFromPair` and beyond `_swapBudget`'s correction capacity.
3. Anyone (or the keeper) calls `Bonding.finalizeGraduation(token)`. `_seedRebalancing`/`_pairRebalance` partially corrects the ratio up to its capped budget; `_routerDepositAndDispose`'s `addLiquidity(min=1,min=1)` then deposits Bonding's remaining inventory at the still-skewed post-swap ratio.
4. Attacker removes liquidity from the pool post-graduation, realizing a ratio more favorable than the curve's closing price at the expense of the protocol-seeded LP.

        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        // Regime 2 — pull any donation pre-seed into this contract so it
        // doesn't pollute the post-swap ratio. Routed to `address(this)`
        // (NOT `lpLock`) so donated TOKEN can be burned and donated LT
        // can be swept to the owner via `_sweepLTToOwner` — `LPLock` has
        // no rescue path, so anything sent there is permanently stuck.
        // No-op on a freshly-created pair (balance == reserves == 0).
        IUniswapV2Pair(pair).skim(address(this));

        // Regime 1 — no LP minted yet (`totalSupply == 0`): a pristine empty
        // pair, or a dust pre-seed from `transfer(pair, dust) + sync()` that
        // leaves reserves non-zero while supply is still zero. Keying on
        // supply rather than reserves routes the dust shape here instead of
        // the rebalance path: with zero supply V2 mints from our amounts
        // alone, so the pool opens at the cached ratio and any dust becomes
        // reserves with no LP claim.
        if (IUniswapV2Pair(pair).totalSupply() == 0) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Regime 3 — mint pre-seed: rebalance, then deposit balanced subset.
        // `lpLock_` re-read from storage inside `_routerDepositAndDispose`.
        // Reserves and token-ordering re-read inside `_seedRebalancing` to
        // keep this function's stack pressure under solc's 16-slot ceiling
        // without `viaIR`.
        return _seedRebalancing(tokenAddress, lt, pair, tokensForLP, ltFromPair, protectedLT);
    }
