### Title
Stale oracle prices survive an intra-transaction oracle reconfiguration during `flash_position` - ([File: contracts/controller/src/context.rs](contracts/controller/src/context.rs))

### Summary
`flash_position` prefetches collateral and debt prices into an invocation-local `Context` before minting debt and invoking the receiver, then reuses those cached prices for the post-callback solvency gate. A receiver can execute an already-ready governance oracle operation during its callback, changing the authoritative price after the cache was populated but before risk is evaluated. The transaction can therefore leave debt priced under the pre-transport oracle snapshot, analogous to accepting a later recursive call using a stale tree after the underlying type has changed.

### Finding Description
`process_flash_position` calls `prefetch_strategy_prices` before entering the guarded funding/callback window, loading the debt asset and every declared collateral token into `Context::token_prices`. [1](#0-0)  `Context::fetch_prices` stores fetched feeds in `token_prices`, and `cached_price` later returns the stored feed without checking that the oracle configuration or answer changed. [2](#0-1) 

Inside the callback window, the controller first mints and forwards debt to the receiver and only then invokes `execute_flash_position`. [3](#0-2)  `mint_and_forward` commits the debt leg through `borrow_into_controller` before the callback is invoked. [4](#0-3) 

The final solvency calculation uses `cached_price` and `cached_market_index` for each stored position. [5](#0-4)  Since the market cache only retains or inserts indexes and has no freshness check against a later oracle change, the same stale collateral and debt prices remain in force after the callback. [6](#0-5)  The post-pool gate then validates `ltv_collateral`, `health_factor`, and the borrow floor from those stale values. [7](#0-6) 

The callback cannot reenter the controller, but governance and the price aggregator are separate contracts, so a receiver contract can call `governance.execute` for a `Ready` operation such as an asset-oracle reconfiguration. The vulnerability is not that the price is manipulated arbitrarily; it is that a legitimate oracle transition occurs after `Context` has snapshotted the old result and is not rechecked before debt is finalized.

### Impact Explanation
An attacker can atomically create a leveraged account that is solvent under the old price but unhealthy under the newly executed oracle configuration. Because the borrowed assets have already been transferred to the receiver, the account can remain with debt that current protocol pricing would have rejected. If the new price lowers collateral value or raises debt value enough, the position becomes immediately liquidatable or insolvent, transferring the loss to suppliers through shortfall or bad-debt socialization.

### Likelihood Explanation
The attack needs a governance oracle operation that is already `Ready` when the flash-position transaction runs, and a receiver contract controlled by the attacker. Both conditions are externally reachable: `flash_position` accepts a caller-selected deployed Wasm receiver, and governance execution of a ready operation is permissionless. Once those conditions exist, the ordering is deterministic because the cache is populated before the callback and the callback executes before the final risk gate. The main limitation is dependence on a pending oracle transition, so this is timing/configuration dependent rather than continuously exploitable.

### Recommendation
After any external callback, invalidate oracle-derived state before final account validation. At minimum, clear or refetch `Context::token_prices` for the debt asset, collateral assets, and refund assets after `invoke_receiver` returns and before collateral merging or `require_post_pool_risk_gates`. Alternatively, record the oracle configuration version or resolved price timestamp before callback execution and require it to match after the callback. The same invalidation should be applied to any strategy callback that can cross a governance-managed pricing boundary.

### Proof of Concept
1. Governance has a ready `ConfigureAssetOracle` operation for collateral token `C`, replacing its source with a lower still-valid price.
2. Attacker deploys `Receiver` implementing `execute_flash_position`.
3. Attacker calls:
   ```text
   controller.flash_position(
       caller = attacker,
       account_id = 0,
       spoke_id = S,
       mode = PositionMode::Multiply,
       debt = HubAssetKey { hub_id: D, asset: D_TOKEN },
       amount = X,
       receiver = Receiver,
       data = encoded_plan,
       collaterals = [(HubAssetKey { hub_id: C, asset: C_TOKEN }, min_C)],
       refund_assets = [],
   )
   ```
4. `prefetch_strategy_prices` caches the old `C_TOKEN` and `D_TOKEN` prices.
5. The controller mints `X` debt and transfers it to `Receiver`.
6. In `Receiver::execute_flash_position`, the receiver calls governance `execute` for the ready oracle operation, then transfers enough `C_TOKEN` to satisfy `min_C`.
7. Finalization merges the received collateral and calculates risk with the stale pre-callback prices.
8. The transaction succeeds even though recalculating with the newly configured oracle would make `ltv_collateral < total_debt` or `health_factor < 1`, leaving newly created debt beyond current risk limits.

pub(crate) fn require_post_pool_risk_gates(env: &Env, cache: &mut Context, account: &Account) {
    if account.debt_free() {
        return;
    }

    let totals = risk::calculate_account_risk_totals(
        env,
        cache,
        &account.supply_positions,
        &account.borrow_positions,

    assert_with_error!(
        env,
        totals.ltv_collateral >= totals.total_debt,
