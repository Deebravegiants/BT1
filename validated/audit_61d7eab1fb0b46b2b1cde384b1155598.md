Confirmed root cause: `TimeoutMessage::Post` timeouts require `validate_state_machine(host, timeout_proof.height)`, which resolves the consensus client's `state_machine(id)` method [1](#0-0) . Every ISMP-connected consensus client pallet gates this on a `SupportedStateMachines` whitelist that returns `Err(UnsupportedStateMachine)` once an entry is removed, e.g. the GRANDPA client's `state_machine()` [2](#0-1)  and its `remove_state_machines` extrinsic [3](#0-2) , plus equivalent Optimism/Tendermint/sync-committee clients.

### Title
Removing a whitelisted state machine permanently strands escrowed relayer fees and undelivered request/response value for that chain - (File: `modules/ismp/clients/grandpa/src/lib.rs`)

### Summary
Consensus-client pallets (GRANDPA, Tendermint, Optimism, Arbitrum, sync-committee) maintain a `SupportedStateMachines` whitelist that gates whether the pallet's `state_machine()` implementation returns a `StateMachineClient` at all. `pallet-ismp`'s core handlers unconditionally call `validate_state_machine` for requests, responses, *and timeouts* before doing anything else, and that function fails outright if the whitelist entry has been removed. This mirrors the analog bug: like `GaugeController.remove_gauge()` erasing a voter's ability to reclaim already-committed weight, `remove_state_machines`/`remove_supported_state_machine` erases the *only* path (timeout) by which value already committed against that chain (escrowed relayer fees, in-flight POST/GET requests) can be unwound.

### Finding Description
`validate_state_machine` is the single gate used by `request::handle`, `response::handle`, and `timeout::handle` [1](#0-0) . It calls `consensus_client.state_machine(proof_height.id.state_id)`, and every consensus-client implementation returns `Err` once the id is missing from its `SupportedStateMachines` map: GRANDPA [2](#0-1) , Tendermint [4](#0-3) , Optimism [5](#0-4) .

Once a state machine is removed via `remove_state_machines` [3](#0-2)  (or `remove_supported_state_machine` for Tendermint [6](#0-5) ), *every* subsequent ISMP message referencing that state machine's id is rejected at `validate_state_machine` before any other logic runs — including `TimeoutMessage::Post`, which is the only mechanism defined for a POST request to be safely reverted and its relayer fee refunded to the payer [7](#0-6) .

Consequently, any POST request already dispatched to (or GET request/response already pending from) a state machine that governance later de-whitelists — for entirely legitimate reasons such as chain deprecation, migration, or replacing one consensus client type with another for the same chain — can neither be delivered (since incoming proofs against that state machine also fail `validate_state_machine`) nor timed out (same gate). The escrowed relayer fee and any dependent application-side escrow (e.g. an `IntentGatewayV2` order awaiting a cross-chain `RefundEscrow`/`RedeemEscrow` message, or a `DispatchGet` cancellation query) is permanently unrecoverable through the protocol's own timeout path, exactly like Alice's voting power being stuck once `G1` is removed from `GaugeController` with no zero-weight/removal path.

### Impact Explanation
Funds already committed to in-flight cross-chain messages targeting a de-whitelisted state machine become permanently frozen with no on-chain recovery path: relayer fees cannot be refunded via timeout, and the destination-side effect (mint, escrow release, refund) can never be delivered. This satisfies "permanent freezing of funds" since no admin override exists to bypass `validate_state_machine` for timeout processing of already-committed requests.

### Likelihood Explanation
The trigger is a single, ordinary, non-malicious governance action — removing a state machine from a consensus-client whitelist, something explicitly documented as routine ("They can always be re-added") [8](#0-7) . Any request dispatched to that chain before removal and still pending (undelivered, unexpired, or with a timeout longer than the time until removal) is affected. Given routine chain migrations/decommissions and non-zero-timeout requests being common, likelihood is Medium-High.

### Recommendation
Decouple the timeout path from the whitelist gate: allow `TimeoutMessage` processing (and specifically the non-membership/timeout check) to proceed using the last known consensus state/state-machine-client logic for a de-whitelisted chain, or require operators to first drain/timeout all pending commitments for a state machine before its whitelist entry can be removed. Alternatively, provide a `force_timeout`/governance-only fallback that refunds escrowed fees for requests whose destination has been removed from the whitelist, mirroring the report's recommendation to allow "zero-weight" (no-op) resolution for removed entities.

### Proof of Concept
1. Dispatch a `PostRequest` (with non-zero `timeout` and non-zero fee) from chain A to chain B, verified via the GRANDPA consensus client, so a `FeeMetadata`/request commitment is stored on A and the fee escrowed. 
2. Before the request is delivered or times out, governance calls `remove_state_machines([B])` on the GRANDPA pallet [3](#0-2) . 
3. Wait past `timeout_timestamp`. Submit `TimeoutMessage::Post` referencing height `{state_id: B, ...}`. 
4. `timeout::handle` calls `validate_state_machine(host, timeout_proof.height)` [9](#0-8) , which now returns `Err(GrandpaError::UnsupportedStateMachine(B))` because `SupportedStateMachines::<T>::contains_key(B)` is false [2](#0-1) . 
5. The timeout call reverts; the escrowed fee (and any dependent app-level escrow) remains locked indefinitely — re-adding B does not help because the request's expected proof/consensus state for B may since have advanced or been pruned, and even if re-added, there is no explicit re-entry path guaranteed to reconcile the stale in-flight request.
