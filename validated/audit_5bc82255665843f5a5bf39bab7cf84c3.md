I have confirmed the root cause. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to that body [2](#0-1) . `HmacValidator.validate` only verifies `hmac` against `to_signable_string` (the raw body) [3](#0-2) , and `Registry.process` passes the unauthenticated `request.shop` straight into the handler payload once that check passes [4](#0-3) .

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the `hmac-sha256` header against the raw request body via `Utils::HmacValidator.validate` [5](#0-4) . The `shop` value the handler receives, however, comes from the separate `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed material [6](#0-5) . Any party who can obtain one legitimately-signed `(raw_body, hmac)` pair for a shop they control can replay that exact body/HMAC pair while substituting a different `shop-domain` header value, and the gem will report the request as valid and attribute it to the attacker-chosen shop.

### Finding Description
The binding that should hold is:
`shop_that_produced(hmac) == shop_attributed_to_the_processed_webhook`

Before the request reaches the host application, `Registry.process` computes:
`hmac_valid = HMAC(secret, raw_body) == received_hmac`

and, if `hmac_valid`, passes `request.shop` (from the header) into `WebhookMetadata` for the handler [7](#0-6) . Since `raw_body` is the only signed field, the equality above does not hold: `hmac` authenticates the body's *contents* but not the *shop* the body is claimed to belong to.

A merchant who installs the app on their own store legitimately receives real webhooks (real body + real valid HMAC, computed with the app's true `api_secret_key`) for their own shop. Because the header is unsigned, that same merchant can resend the identical `raw_body`/`hmac` pair to the app's webhook endpoint while changing only the `shopify-shop-domain` header to name a victim shop. `HmacValidator.validate` still returns `true` (it never looks at the header) [8](#0-7) , and `Registry.process` will invoke the handler with `shop: request.shop` set to the victim's domain [9](#0-8) . Any host application that keys per-tenant storage, cache invalidation, or business logic off `WebhookMetadata#shop` (as the gem's own documentation instructs apps to do [10](#0-9) ) will process attacker-supplied (but validly-HMAC'd) data under a victim tenant's identity.

### Impact Explanation
This breaks the tenant isolation the HMAC check is meant to guarantee: the mechanism that is supposed to prove "this webhook body genuinely originates from Shopify for shop X" can be satisfied while attributing the payload to shop Y instead. This is a cross-tenant integrity issue — an attacker-controlled webhook body (e.g. `orders/create`, `customers/update`, GDPR topics) can be injected into a victim shop's processing pipeline, since only the raw JSON body is checked, not which shop it is claimed to belong to.

### Likelihood Explanation
Exploitation requires only the ability to install the app on any Shopify store (an unprivileged, self-serve action) to obtain a validly-signed body/HMAC pair, plus the ability to POST arbitrary headers to the app's public webhook endpoint — no access token, `client_secret`, or leaked credentials of the target are needed.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signable string that the HMAC covers, or otherwise cryptographically bind the shop identity to the signature (e.g., verify shop domain via a signed claim rather than a bare header) so `to_signable_string` and `HmacValidator.validate` authenticate the full tuple of `(shop, topic, body)`, not just the raw body.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a real webhook (e.g. `orders/create`) so Shopify sends a request with a valid `x-shopify-hmac-sha256` computed over the real `raw_body` using the app's true secret.
2. Capture that `raw_body` and `x-shopify-hmac-sha256` value.
3. Replay a POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` (via `Utils::HmacValidator.validate`) accepts the request as valid [5](#0-4) , and the handler executes with `data.shop == "victim-shop.myshopify.com"` [9](#0-8) , despite the payload never having been produced or authorized for that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
