### Title
Single transaction hitting the program-cache limit aborts an entire otherwise-valid transaction batch, discarding results for unrelated successfully-executed transactions - ([File: svm/src/transaction_processor.rs])

### Summary
`TransactionBatchProcessor::load_and_execute_sanitized_transactions` processes a batch of unrelated, independent transactions sequentially. If, while replenishing the program cache for one transaction, the local `ProgramCacheForTxBatch` sets `hit_max_limit`, the function immediately returns `TransactionError::ProgramCacheHitMaxLimit` for **every** transaction in the batch — including transactions that were processed earlier in the same loop and had already succeeded. This is structurally the same bug class as the reported `LiqFacet::removeLiq` issue: one "bad" unit of work (a paused vault / an oversized program-loading transaction) blocks or discards legitimate, independent work for the rest of the batch instead of only failing the offending item.

### Finding Description
In the per-transaction loop, after `replenish_program_cache` runs for the *current* transaction, the code checks the shared `program_cache_for_tx_batch.hit_max_limit` flag and, if set, discards all previously accumulated `processing_results` and returns an error for the whole batch: [1](#0-0) 

This mirrors the earlier, pre-loop check that also aborts the whole batch before any transaction is processed: [2](#0-1) 

The problem is that `processing_results` for transactions preceding the one that triggered `hit_max_limit` have already been computed and pushed successfully via `processing_results.push(processing_result)` at the bottom of the loop body for prior iterations, and `account_loader` has already applied `update_accounts_for_successful_tx` for them. Nonetheless, the function throws away `processing_results` entirely and returns a fresh vector where every entry is `Err(TransactionError::ProgramCacheHitMaxLimit)`, with `balance_collector` also unconditionally dropped. This is analogous to `removeLiq` iterating over all vaults for a token and letting a single paused vault (an unrelated component) block completion of an otherwise fully satisfiable operation for the other vaults — here, a single transaction's excessive program-loading requirement blocks commitment/visibility of otherwise-valid, already-processed sibling transactions in the same batch.

### Impact Explanation
Because the SVM batch loop is a hot, per-block/per-batch path shared by all unprivileged users' transactions, one transaction in a batch that needs to load enough distinct programs to hit the cache's per-batch limit can cause the entire batch (including unrelated, independently valid transactions from other users) to be discarded/reprocessed with an error, rather than only the offending transaction failing. This creates non-uniform, batch-composition-dependent outcomes for transactions that would otherwise succeed deterministically, and can be used to systematically induce failures for victim transactions bundled in the same processing batch as an attacker-crafted "cache-buster" transaction, similar in kind to the reported vault issue where one paused component denies service to unrelated, otherwise-completable requests.

### Likelihood Explanation
Triggering `hit_max_limit` requires crafting a transaction that references many distinct, not-yet-cached executable programs so that `replenish_program_cache`'s underlying `ProgramCache::extract` reports the per-batch/global cache is full; this is achievable by an unprivileged user submitting a transaction that references numerous different program accounts. Since ordinary batch construction on the leader can place unrelated transactions together with such a transaction, the failure mode is reachable without any special validator/operator role, though it depends on batch composition and program-cache sizing/state at the time.

### Recommendation
Do not discard already-processed `processing_results` when `hit_max_limit` is detected mid-loop. Instead, fail only the transaction that caused the limit to be hit (or stop further processing at that point) while preserving the results already computed for prior transactions in the batch, similar to how the recommendation for `LiqFacet::removeLiq` is to skip only the paused vault and continue processing the rest.

### Proof of Concept
1. Construct a batch containing transaction `T1` (a simple, valid transfer from an unprivileged user) followed by transaction `T2` that references a large number of distinct, uncached executable program accounts sufficient to make `program_cache_for_tx_batch.hit_max_limit` become `true` during `replenish_program_cache` for `T2`.
2. Call `load_and_execute_sanitized_transactions` with `[T1, T2]`.
3. Observe that `T1`, despite being independently valid and already reflected as `Ok(ProcessedTransaction::Executed(..))` in `processing_results` at line 605 of `svm/src/transaction_processor.rs`, is discarded and replaced by `Err(TransactionError::ProgramCacheHitMaxLimit)` for the whole batch at lines 563-574, exactly as it is for `T2`, even though only `T2` was responsible for exceeding the cache limit. [3](#0-2) 

**Note on verification limits:** I was not able to fully trace the internals of `ProgramCache::extract` (in `program-runtime/src/loaded_programs.rs`) that set `hit_max_limit`, since the index did not return the relevant lines for that logic before the tool budget was exhausted. The exact conditions/thresholds that flip `hit_max_limit` to `true` (e.g., cache size limits, per-batch program count) should be confirmed in a full Devin session with complete repository access before treating this as fully proven; the control-flow consequence shown above (discarding prior successful results for the whole batch) is directly supported by the cited code.
