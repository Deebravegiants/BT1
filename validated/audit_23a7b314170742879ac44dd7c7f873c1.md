Audit Report

## Title
Gateway forwards legacy web-API-trigger messages to all DON nodes with no allowlist/authorization check - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`handler.HandleLegacyUserMessage` decodes and validates only the shape, method name, and staleness of an inbound legacy gateway message, then unconditionally forwards the raw request to every node in the configured DON and registers a pending callback — with no sender/topic allowlist or rate-limit check, despite an explicit TODO acknowledging the gap. This lets any client capable of producing a self-signed, well-formed `web_api_trigger` message fan out attacker-controlled requests to an entire DON and occupy callback-table capacity.

## Finding Description
The gateway's public HTTP entry point `gateway.ProcessRequest` decodes the incoming JSON-RPC body, calls `msg.Validate()` (which only checks field lengths/format and recovers the signer address — any keypair, including one generated ad hoc by the caller, produces a valid signature), and then dispatches directly into `h.HandleLegacyUserMessage` for legacy (DON-ID-bearing) requests. Inside `HandleLegacyUserMessage`, the only gates before fan-out are: payload JSON decode success, a non-zero `Timestamp`, and staleness relative to `MaxAllowedMessageAgeSec`, followed by a check that `msg.Body.Method == MethodWebAPITrigger`. Immediately after that method check — annotated with `// TODO: apply allowlist and rate-limiting here` — the handler builds the outbound request via `common.ValidatedRequestFromMessage(msg)`, stores a `savedCallback` keyed by `msg.Body.MessageID`, and loops over `h.donConfig.Members` calling `don.SendToNode` for each one. No comparison against any per-sender or per-topic allowlist, and no rate limiter, is consulted anywhere in this path. This differs from the structurally similar in-DON trigger path `triggerConnectorHandler.processTrigger`, which explicitly checks `trigger.allowedSenders[sender.String()]` and `trigger.rateLimiter.Allow(body.Sender)` before acting on the same `MethodWebAPITrigger` payload — confirming that an allowlist/rate-limit gate is the expected control for this message type, but it is absent on the gateway-facing legacy code path.

## Impact Explanation
Any client able to reach the gateway's HTTP endpoint and produce a self-signed message (no privileged credential needed — `Message.Sign` works with any ECDSA keypair the caller generates) can cause `HandleLegacyUserMessage` to broadcast an attacker-controlled `TriggerRequestPayload` to every DON node and consume a slot in `h.savedCallbacks`, bypassing the allowlist/rate-limit gate that the sibling in-DON handler enforces for the same message type. This is a concrete allowlist-bypass / unauthorized-request-fanout impact affecting DON node resource consumption and callback-table capacity, matching the "allowlist or subscription bypass" and "gateway request impersonation" in-scope impact categories.

## Likelihood Explanation
Likelihood is high: no privileged role, leaked credential, or complex setup is required — only a well-formed, freshly-timestamped `web_api_trigger` message signed with a self-generated key, sent to the gateway's DON-ID-bearing legacy endpoint. The gap is explicitly marked in code via the unimplemented TODO, indicating it was never wired up for this path, and the test suite (`TestHandlerReceiveHTTPMessageFromClient`, `triggerRequest`) demonstrates the handler processing such messages without any allowlist check.

## Recommendation
Implement the allowlist and rate-limiting check flagged by the TODO in `HandleLegacyUserMessage`, mirroring `processTrigger`'s pattern of checking `allowedSenders`/topic authorization and a per-sender rate limiter before constructing `req` or touching `h.savedCallbacks`/`don.SendToNode`. Reject unauthorized or rate-limited senders with an appropriate error response prior to any side effect.

## Proof of Concept
1. Generate an arbitrary ECDSA keypair and sign a `web_api_trigger` legacy `api.Message` with a valid `TriggerRequestPayload` (fresh `Timestamp`), as done in `triggerRequest` in `handler_test.go`.
2. POST it to the gateway HTTP endpoint with a valid DON ID configured in `donConfig`.
3. Observe (via mocked `don.SendToNode`, as in `TestHandlerReceiveHTTPMessageFromClient`) that the handler forwards the request to every configured DON member and registers a callback in `h.savedCallbacks`, regardless of sender identity — no allowlist rejection occurs, confirming the missing gate.
