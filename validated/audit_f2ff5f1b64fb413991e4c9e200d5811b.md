## Analysis

This repository's ZK/EVM architecture is fundamentally different from the Solana Anchor "missing ATA check" bug (which is about SPL `TokenAccount` ownership constraints). However, the underlying bug *class* the report describes — **a value-moving instruction executes without verifying that the destination/authorization actually belongs to the party that is supposed to control it** — maps to a real, independently-verifiable gap in the Emporium external action, where a critical field (`signerAddress`) short-circuits *all* signature verification, and a "minimal" ZK circuit provides *no* cryptographic authorization at all.

### Title
Unauthenticated arbitrary external call from the Emporium contract via zero `signerAddress` and the no-op `MainEVMCircuitMin` proof - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `Hinkal.transact()` is invoked with `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, the proof is checked against `MainEVMCircuitMin`, which performs **no signature, nullifier, or Merkle-root verification at all** [1](#0-0) . Its only public inputs are `outTimeStamp` and `calldataHash`, and `calldataHash` is checked only for **self-consistency** against the caller-supplied `circomData` in `HinkalHelper.performHinkalChecks` [2](#0-1)  — this proves nothing about who authorized the enclosed `externalActionData.externalActionMetadata`.

That metadata is decoded as an `EmporiumStack` containing an arbitrary array of `ops` (endpoint, callData, value) [3](#0-2) . Authorization for these `ops` is supposed to come from `verifyWallet`, but that function **returns immediately, skipping the ECDSA/EIP-712 signature check entirely, whenever `stack.signerAddress == address(0)`** [4](#0-3) . Because `EmporiumStack` is attacker-supplied `abi.decode`d data, the attacker trivially sets `signerAddress = address(0)`.

With `signerAddress == address(0)`, every op falls into the "stateless interaction" branch of `runAction`, where the **Emporium contract itself** (not the attacker) directly executes `op.endpoint.call{value: op.value}(op.callData)`, with the only restriction being that the selector isn't `callHinkalWallet` / `doSendToRelay` [5](#0-4) .

### Finding Description
Combining these two gaps:
1. `formInputForCircom` routes to `formInputEmporiumMin` whenever `erc20TokenAddresses.length == 0` for the Emporium action [6](#0-5) , which never includes `rootHashHinkal`, `signedMessageHash`, nullifiers, or the EdDSA-derived stealth address as public inputs.
2. `MainEVMCircuitMin` only asserts `message = Poseidon(messageSeed)` [1](#0-0)  — an attacker can trivially generate this proof with a self-chosen `messageSeed`, without owning any note, nullifying key, or spending key.
3. `verifyWallet`'s only guard in the `signerAddress == 0` path is the one-time-use `emporiumMessage` nonce [7](#0-6)  — it does not check that `msg.sender` (the caller of `transact`) is entitled to issue these `ops`.
4. Because `erc20TokenAddresses.length == 0`, the post-execution balance-equation loop in `runAction`/`Hinkal.sol` never executes for any token — so **no token accounted for by the balance equation is checked at all**, and any balance held by the Emporium contract (leftover ETH from its `receive()` function, dust from prior transactions, or token balances) is unprotected.

This breaks the intended equality that "every value-affecting op must be tied to `signedMessageHash`/a prover's spending key, or to an EIP-712 signature by `signerAddress`." Here neither binding exists, yet the Emporium contract still performs an arbitrary, attacker-chosen `call`.

### Impact Explanation
This matches the Critical/High classes: **executing calls or moving assets a wallet owner or prover never authorised**, and potential **theft of protocol funds** held in the shared `Emporium` contract (any ETH sent to it via `receive()`, or ERC20 balances it holds transiently). An attacker can direct `op.endpoint` to an ERC20 token and `op.callData` to `transfer(attacker, balance)` (Emporium is the token holder, so no allowance is needed), or drain ETH via `op.endpoint = attacker, op.value = address(this).balance`.

### Likelihood Explanation
High. No privileged role, relay, or admin key is required — any unprivileged EOA can call `Hinkal.transact()` directly (satisfying `circomData.originalSender == msg.sender` when `relay == address(0)` [8](#0-7) ), self-generate the trivial `MainEVMCircuitMin` proof, and craft the `EmporiumStack` with `signerAddress = address(0)`.

### Recommendation
- Remove or gate the `signerAddress == address(0)` bypass in `verifyWallet`; every set of `ops` must be bound to a verified signer (either EIP-712 signature or the full ZK note-ownership proof).
- Do not allow the `MainEVMCircuitMin` / zero-token-array path to authorize arbitrary external calls; require `erc20TokenAddresses`/full circuit verification whenever `ops` can trigger state-changing calls, or bind `calldataHash`/`ops` hash into a signature that is actually checked against a party entitled to spend Emporium's funds.
- Ensure the balance-equation check in `runAction` cannot be trivially bypassed by submitting an empty `erc20TokenAddresses` array while still allowing arbitrary `ops` execution.

### Proof of Concept
Conceptual (I could not execute this against a live deployment, only trace the code paths):
1. Attacker calls `Hinkal.transact(a, b, c, dimensions, circomData)` with:
   - `circomData.erc20TokenAddresses = []`
   - `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`
   - `circomData.externalActionData.externalAddress` = the registered Emporium contract
   - `circomData.externalActionData.externalActionMetadata = abi.encode(EmporiumStack{v:0,r:0,s:0, signerAddress: address(0), ops: [EmporiumOperation(endpoint: <targetToken or attacker>, invokeWallet: false, value: <amount>, callData: <transfer(attacker, amount)> or "")], maxFee:0, deadline: type(uint256).max})`
   - `circomData.calldataHash` set to `CircomDataBuilder.getHashedCalldata(circomData)` so the self-consistency check passes.
2. Attacker supplies a trivial Groth16 proof `(a, b, c)` for `MainEVMCircuitMin`, generated locally with an arbitrary `messageSeed` satisfying `message = Poseidon(messageSeed)` and matching `calldataHash`.
3. `Hinkal.transact` → `HinkalHelper.performHinkalChecks` passes (self-consistent hash, no relay) → `verifyProof` succeeds (trivial circuit) → `_externalTransact` → `EmporiumUpgradeable.runAction` → `verifyWallet` returns immediately (signerAddress==0) → the stateless branch executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract, moving whatever assets it holds.

**Confidence caveat:** I was unable to fully inspect `ExternalActionBaseUpgradeable.sol` (the `onlyAllowedRecipient` modifier on `runAction`) and the full `EmporiumStorage`/factory deployment code to rule out an additional allowlist restricting which `externalAddress`/caller can invoke `runAction`, or confirm exactly what balances the Emporium contract is expected to hold at rest. These would need to be checked in a live/Devin session to fully confirm exploitability and quantify at-risk funds before treating this as fully proven.

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
