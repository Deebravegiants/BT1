### Title
Vault Gateway/Node error responses leak raw internal error strings (persistence-layer/service internals) to unprivileged HTTP clients - ([File: core/capabilities/vault/gw_handler.go])

### Summary
Analogous to CVE-2026-41730 (Spring Data REST serializing the full exception cause chain into HTTP error bodies), the Chainlink Vault request path unconditionally propagates raw `err.Error()` strings from the persistence/service layer (`vaulttypes.SecretsService` / OCR2 KV store) all the way back to the requesting HTTP client through the gateway's JSON-RPC error envelope, instead of returning a generic, sanitized message.

### Finding Description
The node-side Vault gateway handler's `errorResponse` helper places the raw error directly into the JSON-RPC `WireError.Message` field with no redaction for most error codes: [1](#0-0) 

This is invoked from `handleSecretsCreate`, `handleSecretsUpdate`, `handleSecretsDelete`, and `handleSecretsList`, all of which pass through whatever error is returned by `h.secretsService.{CreateSecrets,UpdateSecrets,DeleteSecrets,ListSecretIdentifiers}` under `api.FatalError`/`api.HandlerError` (no message rewriting for these codes): [2](#0-1) 

Only `NodeReponseEncodingError` is explicitly redacted (`err = errors.New(errorCode.String())`); `FatalError`/`HandlerError` are passed through with the underlying error text intact. The underlying secrets/KV-store implementation wraps low-level storage errors with `fmt.Errorf("failed to ... key value store: %w", err)`, which can surface store/DB-specific details: [3](#0-2) 

The internet-facing gateway handler (`core/services/gateway/handlers/vault/handler.go`) that relays the response to the unprivileged HTTP client has a similar `errorResponse` construct that also passes several error codes (`FatalError`, `HandlerError`, `ConflictError`, etc.) through untouched, only special-casing `NodeReponseEncodingError`, `InvalidParamsError`, `UnsupportedMethodError`, and `UserMessageParseError`: [4](#0-3) 

Together, an error message generated deep in the persistence layer (Vault KV store) can flow: `store.WriteSecret`/`store.GetSecret` error → `SecretsService` error → node `GatewayHandler.errorResponse` (`err.Error()`) → gateway response → `gateway.handlers.vault.handler.errorResponse` (passthrough for `FatalError`) → HTTP response body delivered to the calling client.

### Impact Explanation
Exposing raw internal/persistence error text to an unprivileged caller of the Vault HTTP/gateway API can leak backend implementation details (storage backend semantics, internal key formats, limits, config values) that aid further attacks or information disclosure, mirroring the CWE-209 "Information Exposure Through an Error Message" classification. It does not directly give authentication bypass or fund movement, keeping severity comparable to the source advisory (Medium/Low confidentiality impact).

### Likelihood Explanation
Any unprivileged/authenticated client capable of issuing a Vault Create/Update/Delete/List secrets request that triggers a backend failure (e.g., hitting a per-owner secret limit, a duplicate-key condition, or a transient store failure) will receive the raw wrapped error text in the JSON-RPC response, making this trivially triggerable without special privileges — likelihood is High for reachability of the code path, though the practical sensitivity of the leaked string varies.

### Recommendation
Redact/normalize error messages for all non-user-facing error codes (`FatalError`, `HandlerError`, `ConflictError`, etc.) in both `core/capabilities/vault/gw_handler.go`'s `errorResponse` and `core/services/gateway/handlers/vault/handler.go`'s `errorResponse`, logging the full error server-side (already done via `h.lggr.Errorw`) but returning a generic message (e.g., `errorCode.String()`) to the caller, consistent with how `NodeReponseEncodingError` is already handled.

### Proof of Concept
1. Trigger a Vault `secrets_create` request for a secret whose owner has already reached `MaxSecretsPerOwner`, or for a key that already exists.
2. The OCR2 plugin/store layer returns a wrapped error such as `"could not write to key value store: owner %s has reached maximum number of secrets (limit=%d)"` or `"failed to write secret to key value store: %w"`.
3. This error propagates unredacted through `GatewayHandler.errorResponse` (`core/capabilities/vault/gw_handler.go:388-409`) and, on the gateway side, through `handler.errorResponse` (`core/services/gateway/handlers/vault/handler.go:754-801`) under `api.FatalError`, arriving verbatim in the HTTP JSON-RPC error response body to the requesting client.

Note: I could not fully trace the exact wire-level HTTP response formatting/authorization requirements for the internet-facing Vault gateway endpoint (e.g., whether callers must be pre-authorized/allowlisted before reaching `handleSecretsCreate`), since the connecting allowlist/auth-check code (`AuthorizeRequest`/`requestProcessor.ProcessRequest`) was only partially inspected. This should be verified in a follow-up review to confirm the exact privilege level of the caller able to trigger this leak.

func (h *GatewayHandler) handleSecretsCreate(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	vaultCapRequest := vaultcommon.CreateSecretsRequest{}
	if err := json.Unmarshal(*req.Params, &vaultCapRequest); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	h.lggr.Debugw("Processing authorized create secrets request", "request", vaultCapRequest.String())
	vaultCapResponse, err := h.secretsService.CreateSecrets(ctx, &vaultCapRequest)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.FatalError, err)
	}

	jsonResponse, err := toJSONResponse(vaultCapResponse, req.Method)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}
	return jsonResponse
}

func (h *GatewayHandler) errorResponse(
	ctx context.Context,
	gatewayID string,
	req *jsonrpc.Request[json.RawMessage],
	errorCode api.ErrorCode,
	err error,
) *jsonrpc.Response[json.RawMessage] {
	h.requestLogger(req, gatewayID).Errorw("gateway handler error response", "errorCode", errorCode, "error", err)
	h.metrics.requestInternalError.Add(ctx, 1, metric.WithAttributes(
		attribute.String("gateway_id", gatewayID),
		attribute.String("error", errorCode.String()),
	))

	return &jsonrpc.Response[json.RawMessage]{
		Version: jsonrpc.JsonRpcVersion,
		ID:      req.ID,
		Method:  req.Method,
		Error: &jsonrpc.WireError{
			Code:    api.ToJSONRPCErrorCode(errorCode),
			Message: err.Error(),
		},
	}

func (h *handler) errorResponse(
	req jsonrpc.Request[json.RawMessage],
	errorCode api.ErrorCode,
	err error,
	data []byte,
) gwhandlers.UserCallbackPayload {
	switch errorCode {
	case api.FatalError:
	case api.NodeReponseEncodingError:
		h.lggr.Errorw(err.Error(), "requestID", req.ID)
		// Intentionally hide the error from the user
		err = errors.New(errorCode.String())
	case api.InvalidParamsError:
		h.lggr.Errorw("invalid params", "requestID", req.ID, "error", err.Error())
		err = errors.New("invalid params error: " + err.Error())
	case api.UnsupportedMethodError:
		h.lggr.Errorw("unsupported method", "requestID", req.ID, "method", req.Method, "error", err.Error())
		err = errors.New("unsupported method(" + req.Method + "): " + err.Error())
	case api.UserMessageParseError:
		h.lggr.Errorw("user message parse error", "requestID", req.ID, "error", err.Error())
		err = errors.New("user message parse error: " + err.Error())
	case api.NoError:
	case api.UnsupportedDONIdError:
	case api.ConflictError:
	case api.HandlerError:
	case api.LimitExceededError:
	case api.RequestTimeoutError:
	case api.StaleNodeResponseError:
		// Unused in this handler
	}

	// Strip the owner prefix from the json response ID before sending it back to the user
	// This ensures compliance with JSONRPC 2.0 spec, which requires response id to match request id
	index := strings.Index(req.ID, vaulttypes.RequestIDSeparator)
	if index != -1 {
		req.ID = req.ID[index+2:]
	}

	return gwhandlers.UserCallbackPayload{
		RawResponse: h.codec.EncodeNewErrorResponse(
			req.ID,
			api.ToJSONRPCErrorCode(errorCode),
			err.Error(),
			data,
		),
		ErrorCode: errorCode,
	}
}
