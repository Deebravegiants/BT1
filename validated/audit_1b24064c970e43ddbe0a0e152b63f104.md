This maps directly to the reported bug class: an "action" (here, dispatching webhook data as belonging to a given tenant) is taken on a field that is *not* covered by the cryptographic integrity check, exactly the way `transfer()`/`transferFrom()` return values were used without verification in the Solidity report.

### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `#shop` is read directly from the unauthenticated `x-shopify-shop-domain` HTTP header [2](#0-1) . `Utils::HmacValidator.validate` only verifies that `hmac(raw_body, secret) == received_hmac` [3](#0-2) ; it never binds the `shop` header into the signed material. `Registry#process` calls `Utils::HmacValidator.validate(request)` and then, on success, dispatches to the handler using `request.shop` as the tenant identifier without any additional check [4](#0-3) .

### Finding Description
The identity binding that should hold is:
`shop_header == shop_that_the_HMAC_actually_authenticates`

For a genuine Shopify webhook this holds because Shopify sets both consistently. But the gem's own verification logic never checks it — `HmacValidator.validate` recomputes the HMAC over `to_signable_string`, which for `Webhooks::Request` is solely `@raw_body` [5](#0-4) . Since the payload's HMAC is computed by Shopify with the app's `api_secret_key` over the raw body bytes, and the app's `api_secret_key` is shared across *all* shops installed on the same app, any two webhook deliveries from Shopify for different shops but with byte-identical bodies (e.g. two shops firing the same `app/uninstalled` payload shape, or any webhook topic whose JSON body doesn't happen to embed a shop identifier) will produce hmacs that are indistinguishable from one another with respect to which shop they belong to. An entity capable of relaying/replaying webhook bytes it received for its own shop (with a valid HMAC for that exact body, computed by Shopify using the app's shared secret) can then re-POST that same body to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header for a victim shop. `Utils::HmacValidator.validate` still returns `true` because it only checks the raw body against the shared secret — it has no knowledge of, and does not bind, the `shop` header. `Registry#process` accepts this and calls the topic handler with `WebhookMetadata.new(... shop: request.shop ...)` [6](#0-5) , causing the host application's handler logic to act on behalf of a shop it never actually received a message from.

This is the same root cause pattern as the `Vepoch.sol` report: an operation (crediting/mutating state for `rewardToken`/`depositToken`) is performed by trusting a value (`transfer()`'s return) that was never actually checked/bound to the expected outcome. Here, the "value acted upon" is the tenant (`shop`), and it is never bound into the cryptographic check that is supposed to authenticate the whole request.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem is documented to provide via `Utils::HmacValidator.validate(request)` for webhooks: a caller in control of one shop's valid signed webhook body can cause the receiving application to process it as if it came from a different (victim) shop, i.e., cross-tenant confusion/spoofing at the identity layer the gem exposes to host applications. Any host app that follows the gem's documented pattern (`Registry.process` -> handler receives `WebhookMetadata#shop`) and uses that `shop` value to select which tenant's data to mutate is directly exposed, without the host app doing anything wrong per the gem's documented contract.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one validly-signed webhook body for their own shop (i.e., they must be a real, installed merchant on the app — not a fully anonymous internet user) and to be able to send arbitrary HTTP headers to the app's public webhook endpoint, which is trivial since `x-shopify-shop-domain` is a plain header with no additional cryptographic protection. No secret material needs to be recovered; the attacker only needs to relay a body they legitimately received alongside a spoofed header value.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-validated, or otherwise cryptographically/logically tie the claimed `shop` header to the specific delivery, e.g., by validating `shop` against a per-installation record keyed by webhook subscription id rather than trusting the header outright, and by including it (or the resource IDs) in the checked signable material.

### Proof of Concept
1. App receives a legitimate webhook for `attacker-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker re-POSTs the exact same headers/body to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(api_secret_key, B)` [7](#0-6)  — unaffected by the header change — and returns `true`.
4. `Registry#process` calls the handler with `shop: request.shop` = `"victim-shop.myshopify.com"` [4](#0-3) , causing the host app to act on the victim tenant using attacker-supplied (but validly-signed-for-a-different-shop) data.
