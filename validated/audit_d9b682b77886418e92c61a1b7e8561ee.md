### Title
PoA Bridge withdrawal status matched only by `assetId`, causing wrong txHash/status attribution in batch withdrawals with duplicate assets - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
The SDK explicitly supports batch withdrawals where multiple `WithdrawalParams` entries can share the same `assetId` but differ in `destinationAddress` and/or `amount` (e.g. withdrawing USDT to two different addresses in one intent). When polling the PoA bridge for completion status, `describeWithdrawal` matches the correct withdrawal entry in the response list using only the `assetId`, ignoring `destinationAddress`/`amount`, because the bridge's response list is unsorted and cannot be matched by positional `index`.

### Finding Description
`PoaBridge.createWithdrawalIdentifier` assigns each withdrawal a per-route `index`, but `describeWithdrawal` does not use that index to disambiguate results: [1](#0-0) 

```
async describeWithdrawal(...) {
  const response = await this.getWithdrawalStatusWithRetry(args);
  // Response list is unsorted, so we match by assetId instead of index
  const withdrawal = findMatchingWithdrawal(
    response.withdrawals,
    args.withdrawalParams.assetId,
  );
  ...
}
```

The comment itself confirms the matching key is `assetId` only. Since the SDK's batch-withdrawal feature (`processWithdrawal`/`signAndSendWithdrawalIntent`/`waitForWithdrawalCompletion`) allows multiple withdrawal entries with an identical `assetId` (different destination or amount) inside the same intent/tx [2](#0-1) , `findMatchingWithdrawal` cannot uniquely identify which server-side withdrawal record corresponds to which `WithdrawalIdentifier.index` when two or more of them share `assetId`. In that case the function will resolve to the same (or a mismatched) withdrawal record for multiple different indices, so the `txHash`/`status` returned for one destination can actually belong to a different destination's transfer.

This breaks the intended equality: *"the status/txHash reported for withdrawal[i] must be the on-chain outcome of exactly withdrawal[i]"*. Here, the outcome reported can be the on-chain outcome of a sibling withdrawal that happens to share the same `assetId`.

### Impact Explanation
An integrator using `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` for a batch with duplicate `assetId` entries could receive an incorrect `txHash`/`status` mapping between its own withdrawal records and the ones actually reported by the bridge. This can make the integrator credit or mark-as-completed the wrong destination address, or attribute the same on-chain transfer hash to two different withdrawal records — matching the "status or hash misreport making an integrator credit or refund twice" criterion. Because withdrawals in a batch execute atomically as a single intent, an operator has no on-chain way to detect the mismatch besides recognizing the destination each is meant for; the SDK reporting is the primary signal used to reconcile off-chain records.

### Likelihood Explanation
This requires no privileged access or malicious peers — it is triggered purely by using the SDK's own documented batch-withdrawal feature with two or more withdrawal params sharing the same `assetId` but different destinations/amounts (a normal, supported use case, e.g. batching multiple USDT payouts). The unsorted nature of the PoA bridge's response (explicitly acknowledged in the code comment) makes the mismatch a function of response ordering, which is not controlled by the caller and can vary.

### Recommendation
Extend `findMatchingWithdrawal` to disambiguate using additional fields available in the response (e.g. `destinationAddress` and `amount`, or a server-side withdrawal ID/nonce returned per submission) rather than `assetId` alone. If the PoA bridge API does not expose a stable per-request identifier, request one, or fall back to consuming matches without replacement (mark a response entry as "claimed" once matched) so the same response entry cannot be attributed to two different `WithdrawalIdentifier`s in the same batch.

### Proof of Concept
1. Build a batch withdrawal with two params: both `assetId: 'nep141:usdt.tether-token.near'`, but `destinationAddress: 'addrA'` (amount 100) and `destinationAddress: 'addrB'` (amount 200).
2. Call `sdk.processWithdrawal({ withdrawalParams: [paramsA, paramsB] })`.
3. The PoA bridge's withdrawal-status endpoint returns both withdrawals in an unsorted list, both matching `assetId === 'nep141:usdt.tether-token.near'`.
4. `describeWithdrawal` for index 0 (addrA) and index 1 (addrB) both call `findMatchingWithdrawal(response.withdrawals, 'nep141:usdt.tether-token.near')`; without an additional disambiguating key, this can return the same underlying withdrawal record (e.g. addrB's completed transfer) for both indices, causing `waitForWithdrawalCompletion` to report addrB's `txHash` as the completion for addrA's withdrawal as well.

Note: I was unable to inspect the internal implementation of `findMatchingWithdrawal` (its definition was not returned by search) to confirm whether it currently deduplicates already-matched entries; the analysis above is based on the explicit code comment and the confirmed absence of destination/amount in the matching call in `describeWithdrawal`. A Devin session with full file access should verify `findMatchingWithdrawal`'s exact matching/dedup logic before finalizing remediation.

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
	}
