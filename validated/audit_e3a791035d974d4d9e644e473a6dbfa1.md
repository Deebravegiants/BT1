### Title
Session ID trusted from unauthenticated browser cookie enables predictable cross-tenant session hijacking - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` derives the session identifier used to look up a merchant's stored `access_token` directly from a plain, unsigned browser cookie value whenever a JWT session token is not supplied, and this cookie value is itself just the predictable, deterministic session `id` (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`) that the gem computes and hands to the host application to store verbatim. Nothing in this gem cryptographically binds the returned session id to any authenticated request property, so an unprivileged internet user can forge the cookie and cause the host app's session lookup to resolve to a different (target) shop's stored session.

### Finding Description
When `Context.embedded?` is false, or when no `shopify_id_token` is provided even in embedded mode, `current_session_id` falls back to `cookie_session_id(cookies)`, which just returns the raw cookie value with no verification: [1](#0-0) [2](#0-1) 

The value that ends up in that cookie is produced by `Oauth.validate_auth_callback`, which for non-embedded apps sets the cookie's value to `session.id`: [3](#0-2) 

And `session.id` is not a secret or a signed token — it is fully deterministic from public information (the shop domain, and for online sessions the associated user id): [4](#0-3) 

`SessionCookie` is a plain struct with no HMAC or signature field of its own: [5](#0-4) 

The documented usage pattern instructs the host app to store this cookie with plain `cookies[...]=` (not `cookies.signed[...]` or `cookies.encrypted[...]`) and to use the returned session id to fetch the stored `Session` (containing the real `access_token`) from the app's own session repository: [6](#0-5) 

**Broken binding:** the gem implicitly assumes `cookie_value == authenticated_session_id_for_this_browser`, but it never verifies that equality — it only trusts whatever bytes exist in the cookie. Because `session.id` is computed as `"offline_#{shop}"` (fully public/guessable given a target shop's domain, which is public information) or `"#{shop}_#{user_id}"`, an attacker does not need to observe or steal a real cookie; they can simply construct the cookie value for any target shop and have `current_session_id` return it as if it were their own authenticated identifier.

### Impact Explanation
If a host application follows the gem's documented pattern (store/retrieve `Session` objects keyed by the id returned from `SessionUtils.current_session_id`, as shown in `docs/usage/oauth.md`), an attacker can set the `shopify_app_session` cookie to `offline_{victim-shop}.myshopify.com` and have the app resolve and use the victim shop's stored `access_token` for subsequent API calls on the attacker's request — i.e., cross-tenant access to another merchant's data via their access token, without any credential, secret, or prior valid session. This matches the Critical impact category (cross-tenant access / theft of a merchant access token).

### Likelihood Explanation
Exploitability only requires knowledge of the target shop's domain (public information, e.g., `victim-shop.myshopify.com`, discoverable via the storefront) and the ability to set an arbitrary cookie value in a request to the vulnerable app, both trivially available to any unprivileged internet user. No `api_secret_key`, access token, or privileged account is required. The gem's own `current_session_id`/`cookie_session_id` path performs no cryptographic check on the cookie contents.

### Recommendation
Do not use a deterministic, guessable string as the externally-facing session cookie value. Instead:
- Generate a cryptographically random opaque session identifier (unrelated to shop/user id) to store in the cookie, and maintain the shop/user-id-based id only server-side, or
- Sign/HMAC the cookie value (bound to shop + expiry) with `Context.api_secret_key` and verify that signature inside `SessionUtils.cookie_session_id`/`current_session_id` before trusting it, mirroring the binding already done for JWT tokens in `JwtPayload`.

### Proof of Concept
1. A merchant `victim-shop.myshopify.com` has installed the app and has an offline session stored server-side by the host app, keyed by `"offline_victim-shop.myshopify.com"` (per `Session.from`).
2. Attacker sends a request to any endpoint of the host app that resolves the current session via `ShopifyAPI::Utils::SessionUtils.current_session_id`, setting the cookie:
   `shopify_app_session=offline_victim-shop.myshopify.com`
3. `current_session_id` (non-embedded / no JWT branch) returns `"offline_victim-shop.myshopify.com"` unchecked.
4. The host app, following the documented pattern, looks up its `SessionRepository` by that id, retrieves the victim's real `Session` (including `access_token`), and uses it to serve the attacker's request — granting the attacker access to the victim shop's data.

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Auth
    module Oauth
      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
