### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are trusted by handlers without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content solely from the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and handed to the app's webhook handler as trusted tenant/routing metadata.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` accepts the request once `HmacValidator.validate(request)` passes, and then forwards `request.shop` (and `topic`/`webhook_id`/`api_version`) verbatim into `WebhookMetadata`, which the app's handler treats as the authenticated tenant identity: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`verified(hmac) == {shop, topic, webhook_id, api_version, body}`

but the actual binding enforced is:
`verified(hmac) == {body}` while `{shop, topic, webhook_id, api_version}` are parsed-but-unverified.

Because `shop` is not part of the signed content, any request bearing a *valid* HMAC for a given body (e.g., a genuine webhook payload the attacker legitimately received for their own shop, or any body/HMAC pair the attacker can obtain) can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to an arbitrary victim shop. `HmacValidator.validate` still returns `true` because it only checks the body bytes against the secret-derived digest, and the app's handler will process the payload believing it originated from the victim shop — this is exactly the "field acted on but not covered by the HMAC" pattern: the `shop` value that determines *which tenant's* business logic runs is disjoint from the bytes that were actually authenticated.

### Impact Explanation
This crosses a tenant boundary: an attacker who controls or observes any single shop's legitimate webhook deliveries (trivial, since they can install their own low-privilege app/store) can forge a webhook that is attributed to a different, victim shop's domain while still passing HMAC verification. Any handler logic that uses `data.shop` to look up sessions, credentials, or otherwise scope side effects (a documented, expected usage pattern per `docs/usage/webhooks.md`) can be tricked into executing tenant-scoped operations against the wrong merchant — i.e., cross-tenant access facilitated entirely by this gem's failure to bind `shop` into the authenticated payload.

### Likelihood Explanation
High feasibility for anyone who can obtain one legitimately-signed webhook body (e.g., from their own store) — no access token, `client_secret`, or privileged account is required, only the ability to intercept/replay their own webhook traffic and control the `shop-domain` header value sent to the app's callback endpoint.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in `to_signable_string` (or independently re-derive/verify them from a source bound to the HMAC, e.g., encode them into the signed payload the way Shopify signs online-store webhooks), so that any header tampering invalidates the HMAC check in `Utils::HmacValidator.validate`.

### Proof of Concept
1. Attacker's own store `attacker-shop.myshopify.com` receives a legitimate webhook: `raw_body = '{"id":1}'`, `hmac-sha256 = HMAC(secret, raw_body)`, `shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same `raw_body`/`hmac-sha256` to the app's webhook endpoint, but sets `shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` — [1](#0-0)  — so validation succeeds.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id"=>1}, ...)` and performs tenant-scoped work believing it is authorized for `victim-shop.myshopify.com`, even though nothing about that shop's identity was ever cryptographically verified.

          received_signature = verifiable_query.hmac
