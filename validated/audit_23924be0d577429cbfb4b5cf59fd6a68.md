### Title
`EvmHost.dispatch()` uses `block.timestamp` as the Uniswap V2 swap deadline, providing no real deadline protection on ETH→feeToken swaps - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` let any unprivileged caller pay a dispatch fee in native ETH; the host swaps `msg.value` ETH for the exact `fee`/`get.fee` amount of `feeToken()` via Uniswap V2's `swapETHForExactTokens`, passing `block.timestamp` as the `deadline` argument, exactly the anti-pattern the referenced report warns against.

### Finding Description
`dispatch(DispatchPost memory post)` and `dispatch(DispatchGet memory get)` both contain: [1](#0-0) [2](#0-1) 

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```

`swapETHForExactTokens` takes an `amountOut` (the requested `fee`), a `path` (`WETH → feeToken`), a recipient, and a `deadline` after which the router must reject the transaction. Passing `block.timestamp` at call time means the deadline is evaluated at whatever block the transaction eventually lands in — it is always satisfied at execution time, because `block.timestamp` is re-read as the current block's timestamp when the EVM executes the check, not the timestamp the caller observed when building the transaction. This is functionally equivalent to no deadline at all: a validator/relayer/MEV searcher who delays inclusion of the caller's `dispatch()` transaction faces zero on-chain deadline pressure to include it promptly, exactly the bug class described in the referenced report ("never set deadline to `block.timestamp`").

Unlike the PT-V5 report's `LiquidationRouter`/`LiquidationPair`, this path is reached by any unprivileged user of the protocol's core message dispatch — every `IApp`/message sender that funds a POST or GET dispatch with native ETH goes through this exact code, making it a broadly reachable dispatch-path issue rather than a niche liquidator flow.

### Impact Explanation
The `amountOut` (`post.fee`/`get.fee`) is fixed, so the immediate loss is bounded to "how much extra ETH does the caller overpay for a fixed feeToken amount" — the caller supplies `msg.value` as the max ETH input, and the swap can consume up to all of it. If a relayer/validator/searcher delays inclusion of the caller's transaction while the ETH/feeToken price moves unfavorably to the caller (e.g., ETH depreciates against the fee token), the swap still executes at the current (execution-time) price rather than reverting due to staleness, causing the caller to pay materially more ETH (or receive worse execution) than intended for the same `msg.value`, with no on-chain expiry to protect them. Because `dispatch()` is the fee-funding entry point for essentially all outbound ISMP messages funded in native ETH across the protocol, this is a systemic, protocol-wide swap-deadline gap rather than an isolated helper contract.

### Likelihood Explanation
Exploitability requires a party controlling block inclusion (a searcher/validator or a delayed relayer) to intentionally hold the caller's dispatch transaction in the mempool until a more favorable execution moment, similar to the report's PoS-proposer-lookahead scenario. Given `dispatch()` is called on essentially every native-ETH-funded POST/GET request, this exposure is present on the default fee-payment path a very large volume of ordinary dispatchers would use.

### Recommendation
Accept a caller-supplied `deadline` parameter (e.g., add `deadline` to `DispatchPost`/`DispatchGet`, or a separate parameter to `dispatch()`) and forward the caller's intended deadline to `swapETHForExactTokens` instead of `block.timestamp`. Never default to `block.timestamp` inside the transaction itself, since that value is only meaningful when captured at signing time by the caller.

### Proof of Concept
1. Caller A calls `host.dispatch{value: X}(DispatchPost{...fee: F, ...})`, intending to swap up to `X` ETH for `F` fee tokens at the current market rate.
2. A relayer/validator observes the pending transaction but does not include it immediately (e.g., holds it for several blocks while it is profitable to do so, or simply due to network congestion under proposer look-ahead).
3. When the transaction is eventually included, `block.timestamp` inside `dispatch()` is set to the current (future) block's timestamp, so the `deadline` check in `swapETHForExactTokens` always passes regardless of how much time has elapsed since A signed the transaction.
4. If the ETH/feeToken price has moved unfavorably to A during the delay, the swap still executes at the current market price, consuming more of A's `msg.value` than A would have accepted had a real deadline been enforced, with no revert path available to A. [1](#0-0) [2](#0-1)

        if (msg.value > 0) {
