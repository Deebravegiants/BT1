### Title
Webhook HMAC verifies only the request body, not the `shop`/`topic`/`webhook-id` headers, allowing cross-tenant webhook spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Registry.process` validates never covers the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Any party who can obtain one genuine `(body, hmac)` pair for the app (trivially available to an unprivileged user who installs the app on their own shop and receives a real webhook) can replay that exact body/HMAC to the app's public webhook endpoint while freely rewriting the `x-shopify-shop-domain` and `x-shopify-topic` headers. The signature still validates (it only checks the body), but the handler is dispatched with attacker-chosen `shop` and `topic` values.

### Finding Description
The binding that should hold is: `HMAC(body, client_secret) valid` ⇒ `(shop, topic, webhook_id, body)` as delivered by Shopify. Instead the code only enforces `HMAC(body, client_secret) valid` ⇒ `body` genuine; `shop`, `topic`, and `webhook_id` are read straight from attacker-controllable headers and passed unauthenticated into the dispatched `WebhookMetadata`.

- `Request#to_signable_string` signs only `@raw_body`: [1](#0-0) 
- `Request#shop`, `#topic`, `#webhook_id` are taken directly from headers with no cryptographic tie to the body: [2](#0-1) 
- `HmacValidator.validate` / `validate_signature` compute the digest purely from `verifiable_query.to_signable_string`, i.e., the body: [3](#0-2) 
- `Registry.process` validates that body-only HMAC, then immediately trusts the unauthenticated header fields to build `WebhookMetadata` and dispatch the handler: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that has the app installed, a valid `(body, hmac)` pair captured by any shop-owner (including an attacker who installs the app on a store they control) remains valid forever and is not scoped to that shop. Replaying it against the same public webhook endpoint with a forged `shop-domain`/`topic` header passes HMAC validation and reaches the handler as if it originated from the spoofed shop/topic.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-attributed binding: the webhook signature authenticates only the body's origin (any installer of the app), while the tenant (`shop`) and event (`topic`) the host application acts on are taken from unauthenticated headers. A malicious app installer can make the host app process crafted data under another shop's identity/topic (e.g., trigger `app/uninstalled`, `customers/redact`, or other lifecycle handlers attributed to a victim shop), leading to cross-tenant state corruption in the host application without ever needing the victim's credentials.

### Likelihood Explanation
Any user can freely install the app on their own store, which is enough to obtain a legitimate `(body, hmac)` pair for arbitrary chosen topics they can trigger (e.g., re-installing/uninstalling, updating their own resources). No secret, token, or privileged access is required to mount the replay against the shared public webhook endpoint. The complexity is low: capture one webhook, resend with modified headers.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified material, or bind them cryptographically to the body (e.g., verify shop against a known/registered shop list and validate that `webhook_id` is unique and unseen — replay protection), rather than trusting headers independent of the HMAC-covered payload.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture a real webhook delivery, e.g. `POST /webhooks` with body `{}` and header `x-shopify-hmac-sha256: <valid-hmac-for-{}>`.
2. Replay the same request to the app's webhook endpoint, changing only:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic: app/uninstalled` (or any topic the app handles)
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) body against the HMAC: [5](#0-4) 
4. The host app's registered handler is invoked with `data.shop == "victim.myshopify.com"` and `data.topic == "app/uninstalled"`, even though neither value was ever part of the signed payload.
