## Title
Webhook shop/topic identity not covered by HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable content from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read from unauthenticated HTTP headers and are never part of the signed bytes. `ShopifyAPI::Webhooks::Registry.process` validates only that the HMAC over the body is correct, then unconditionally forwards the header-derived `shop` value to the app's handler as the tenant identifier. This breaks the equality `shop verified by HMAC == shop attributed to the webhook payload`, mirroring the reported bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`to_signable_string` — the only input fed into the HMAC comparison — returns solely the raw request body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are pulled straight from headers, completely outside the HMAC's coverage: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the body was signed with the app's secret) and then trusts `request.shop`/`request.topic` as-is to build the metadata handed to the app's business logic: [3](#0-2) 

Because Shopify signs webhooks with a single `client_secret` per app — the same secret is used for every shop that installs that app — any store owner can install the target app on their own (free/dev) store, trigger a webhook whose body they can influence, and legitimately receive a validly-HMAC-signed payload from Shopify. Since the `shop-domain` header is not part of the signed bytes, that attacker can replay the exact same body+HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for any other tenant's shop domain. `HmacValidator.validate` will still succeed because it only checks the raw body against the secret: [4](#0-3) 

The library performs no reconciliation between the "shop that produced a validly-signed body" and the "shop asserted in the header," so the equality that should hold — `hmac_verified_shop == asserted_shop` — is not enforced anywhere in this gem's webhook path.

### Impact Explanation
This directly enables cross-tenant access/impersonation: an unprivileged internet user who can install the target app on their own store (a normal, unprivileged action available to anyone) can craft webhook bodies of their choosing, obtain a genuine app-secret-signed HMAC for that body via legitimate delivery, and then relabel the payload as belonging to any other merchant by changing only the unsigned `shop-domain` header before forwarding it to the app's webhook receiver. Any app that uses `WebhookMetadata#shop` (as returned by this gem) to select which tenant's data to create/update/delete is exposed to cross-tenant data corruption or injection — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likely, since: (1) creating a store and installing an app is available to any unprivileged user; (2) the per-app secret is shared across all shops of that app, so a validly-signed body is trivially obtainable; (3) the gem's `Registry.process` and `Request` classes provide no additional binding between the signed body and the header-derived shop, so any app relying on this gem's default abstractions inherits the gap without any extra work from the attacker beyond a header edit on replay.

### Recommendation
Bind the shop identity into what's verified — e.g., require callers to independently confirm `request.shop` corresponds to a shop with an active, stored session/installation before trusting the payload, or clearly document that `shop`/`topic`/`webhook_id` are untrusted metadata that must be cross-checked against the app's own installation records prior to acting on webhook data, rather than exposing them via `WebhookMetadata` as if they were verified alongside the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store (unprivileged, self-service).
2. Attacker configures the app (or triggers an event) to produce a webhook body containing attacker-chosen field values (e.g., an `orders/create` webhook body referencing arbitrary content).
3. Shopify delivers this webhook to the app's registered endpoint, computing `hmac = HMAC-SHA256(client_secret, raw_body)` — valid, since it is genuinely signed by Shopify for the attacker's own shop.
4. Attacker intercepts/replays this exact `raw_body` + `X-Shopify-Hmac-Sha256` pair to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different topic).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body bytes against the app secret — the modified `shop` header is never part of `to_signable_string`.
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, believing it originated from the victim's store.
