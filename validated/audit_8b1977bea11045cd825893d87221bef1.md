**Rationale:**

The `sorted_keys` function only wraps `serde_json::to_value` + re-serialize; for `serde_json`'s default (non-`preserve_order`) build, `Value::Object` is backed by a `BTreeMap<String, Value>`, so field ordering is deterministic and there is no mechanism for duplicate/near-duplicate keys since struct field names are fixed at compile time (they aren't attacker-supplied map keys). [1](#0-0) 

The structs cited in the question (`IrisCodesJson`, `IrisCodeSharesJson`, `BackendKeysJson`, `Embedding`) only contain `String`/`&str`/`Option<&str>` fields — no raw `f64` fields are serialized through this path, so the NaN/Infinity float-encoding collapse scenario does not apply. [2](#0-1) 

Critically, the actual signed digest is computed directly over the produced JSON bytes (`digest(&SHA256, &json)`), not over some intermediate lossy representation, and `hashes.sign` covers `digest(&SHA256, &hashes_json)` which itself is a `BTreeMap<String,String>` of per-file hex digests. [3](#0-2) [4](#0-3) 

So any injectivity break would require an actual SHA-256 collision on real byte sequences, not a canonicalization quirk. Additionally, the attacker does not control the raw byte values feeding these structs directly — iris/mask codes and shares originate from the ML iris pipeline (`EstimateOutput`) and Galois-ring encoding, not attacker-suppliable arbitrary strings, and backend keys/embeddings come from backend/pipeline outputs, not attacker input. [5](#0-4) 

Given fixed struct schemas, no raw float serialization, and digesting of the literal output bytes (not a non-injective canonical form), there is no reachable path for an unprivileged attacker to construct two semantically distinct structs whose `SerializeWithSortedKeys` output collides while still passing through the real biometric/backend pipeline.
