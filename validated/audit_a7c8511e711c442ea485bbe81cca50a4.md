This confirms the mechanism: `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers [2](#0-1) . `HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string` [3](#0-2) , so the `shop` header is never part of what's cryptographically bound. `Registry.process` validates only the HMAC and then dispatches `request.shop` straight into `WebhookMetadata` for the handler [4](#0-3) .

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The `shop` identity attached to that authenticated payload, however, is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signed material. The binding "HMAC-verified bytes == the shop the payload is attributed to" does not hold.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) . `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from `@headers`, which are attacker-controllable at the transport layer (any values sent by whoever is delivering the HTTP request) [2](#0-1) . `HmacValidator.validate` / `validate_signature` compute and compare the HMAC using `verifiable_query.to_signable_string` and `verifiable_query.hmac` only — no header value, including `shop`, participates in the signature computation [5](#0-4) . `Registry.process` gates entirely on this HMAC check and then forwards `request.shop` unchanged into the `WebhookMetadata` object passed to the app's handler [4](#0-3) .

Equality that should hold but doesn't: `hmac_verified(raw_body) == shop_attribution(raw_body)`. In reality: `hmac_verified(raw_body)` while `shop_attribution` comes from an independent, unauthenticated channel (the header), so the two are decoupled. Any party capable of relaying a genuine, previously-observed `(raw_body, hmac)` pair — e.g., a shop-side proxy, logging/analytics intermediary, or the merchant's own store owner replaying their own webhook payload with a modified `shop-domain` header — can cause the app to process an authentic, HMAC-valid payload under an attacker-chosen `shop` identity of another tenant.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented and demonstrated in the gem's own usage docs and tests [6](#0-5) , [7](#0-6) ) to key session lookups, cache invalidation, or data updates, this decoupling lets a replayed/relayed webhook attribute one tenant's authentic event data to a different tenant's shop identity — a cross-tenant data-integrity break that is directly caused by this gem's `Request`/`HmacValidator` design not binding the identity header into the signed payload.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one legitimate `(raw_body, hmac)` pair, which any shop owner receiving webhooks for their own store already has, and to control the delivery of the HTTP request to the app's webhook endpoint (feasible if delivery isn't restricted to Shopify's IP ranges, or via a MITM/reverse-proxy position). This is a plausible, moderate-likelihood path since the gem itself does nothing to bind the `shop` header to the signed content.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`) header values as part of the signable string used for HMAC computation, or otherwise cryptographically bind them (e.g., derive an expected shop from a previously-known relationship rather than trusting the header verbatim). At minimum, document clearly that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant-sensitive decisions without independent verification.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
2. Attacker (or a relaying intermediary) resends `raw_body: B` with headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-b.myshopify.com` (victim tenant), `x-shopify-topic` unchanged.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — validation succeeds because `to_signable_string` never included the shop header [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed_body, ...)` [8](#0-7) , causing `shop-a`'s authentic payload to be processed under `shop-b`'s identity.
