### Title
Webhook `shop` field is trusted by app handlers but excluded from HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the *body* was signed by the app's `api_secret_key` [2](#0-1) . The `shop` value, however, is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [3](#0-2)  and is not part of the signed bytes.

### Finding Description
`Registry.process` verifies the HMAC and then immediately forwards `request.shop` (the raw, unsigned header) to the app's registered handler as the authoritative shop identity: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) . The gem's own documentation instructs app authors to treat `data.shop` as the tenant identifier for downstream work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [5](#0-4) .

This breaks the intended binding: `hmac_valid(body, api_secret_key) == true` should imply `shop == the tenant that generated body`, but the code only proves `hmac_valid(body, api_secret_key) == true`; `shop` is an independent, unauthenticated header. Because Shopify signs webhooks for *all* shops of an app with the same `api_secret_key`, a party who legitimately receives one authentic webhook (e.g. from their own installed development/test shop) can capture the valid `(raw_body, hmac)` pair and resend it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` because it only recomputes the signature over `@raw_body` [6](#0-5) , and `Registry.process` accepts the forged `shop` value as legitimate and passes it into the handler.

### Impact Explanation
Any app built on this gem that uses `data.shop` from a processed webhook to look up a session/access token, write tenant-scoped records, or otherwise key work by shop (as the documented usage pattern instructs) can be made to attribute attacker-controlled webhook content to a victim shop the attacker does not control. This is a cross-tenant data-integrity/confusion vector rooted entirely in this gem's `Webhooks::Request`/`Registry` implementation, not a misuse of an undocumented API — the gem documents `data.shop` as the field to key work on.

### Likelihood Explanation
Exploitation only requires the attacker to operate any shop that has the target app installed (a normal, unprivileged relationship) in order to capture one genuine `(body, hmac)` pair, then replay it with a modified `shop-domain` header to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the body, so that `to_signable_string` covers every field the handler will treat as authoritative — mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signed string [7](#0-6) . At minimum, document prominently that `data.shop` is unauthenticated and must be cross-checked against a shop the app has an active session for before being trusted.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a real webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid signature of `B` under the app's shared `api_secret_key`).
2. Attacker resends the identical `raw_body: B` and `x-shopify-hmac-sha256: H` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully (all required headers present).
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and returns `true` [8](#0-7) .
5. The handler is invoked with `WebhookMetadata` carrying `shop: "victim.myshopify.com"` and attacker-chosen `body`, even though `victim.myshopify.com` never sent this webhook [9](#0-8) .
