# Vulnerability Analog: BEEFY supermajority threshold can be met with duplicate authority votes, forging a minority as a "supermajority" - (File: evm/src/consensus/EcdsaBeefy.sol, modules/consensus/beefy/verifier/src/lib.rs)

## Summary
The BEEFY consensus clients (`EcdsaBeefy.sol` and its Rust counterpart in `modules/consensus/beefy/verifier/src/lib.rs`) determine whether a commitment has reached the required 2/3+1 supermajority by simply counting the **length** of the submitted votes/signatures array, then separately verifying each vote's authority-set membership via a merkle multi-proof. Neither step enforces that the votes come from **distinct** authorities. This mirrors the HatsSignerGate bug class: a security threshold ("N signers required") is satisfied by counting raw list entries instead of unique, correctly-scoped entries, letting an attacker duplicate an already-valid entry to inflate the count without adding real participation.

## Finding Description
In `EcdsaBeefy.sol::verifyMmrUpdateProof`: [1](#0-0) 

The function computes `sigLen = relayProof.signedCommitment.votes.length` and gates on `checkParticipationThreshold(sigLen, authoritySet.len)`, which only checks `len >= (2*total)/3 + 1`: [2](#0-1) 

It then recovers a signer per vote and builds a `MerkleMultiProof.Leaf[]` keyed by `vote.authorityIndex`, verifying membership against the authority-set root. There is no check that `authorityIndex` values are unique across the `votes` array before or after this loop.

The equivalent Rust verifier has the identical pattern — `signatures_length` gates the threshold, and `authority_indices`/`authority_leaves` are built per signature with no deduplication: [3](#0-2) [4](#0-3) 

This is directly analogous to the HatsSignerGate flaw: `countValidSignatures` counted "any N signatures signed by valid signers" without checking uniqueness, so an invalid actor could pad the count with a repeated valid signature. Here, `checkParticipationThreshold`/`check_participation_threshold` counts "any N votes recovering to a member of the authority set" without checking uniqueness, so a minority of colluding or leaked-key authorities can repeat their own valid `(authorityIndex, signature)` pair multiple times in the `votes`/`signatures` array to inflate `sigLen`/`signatures_length` past the 2/3+1 bar, while the merkle multi-proof step only re-confirms that the (duplicated) authority index is a genuine member — which it is, trivially, since it's the same real authority repeated.

Notably, the codebase already recognizes and defends against this exact bug class elsewhere: the Pharos verifier explicitly deduplicates participant keys before checking stake threshold — [5](#0-4) 
— and the sync-committee verifier has an explicit comment noting the need to prevent inflating the participant count with junk/padding bits: [6](#0-5) 

The BEEFY ECDSA client (both Solidity and Rust) lacks this same protection.

## Impact Explanation
If a minority of the authority set (fewer than 2/3+1 unique signers, potentially with a leaked or coerced single key, or even just a small colluding subset) duplicates its own valid vote entries, both `EcdsaBeefy.sol` and the Rust BEEFY verifier will accept the commitment as having reached supermajority finality. This allows forging a BEEFY finality proof for an MMR root/parachain header set that was never actually finalized by a genuine supermajority, leading to unsound state commitments being accepted by `EvmHost`/`pallet-ismp`, enabling forged message delivery, unauthorized state proofs, and downstream fund theft or unbacked mint via forged cross-chain messages.

## Likelihood Explanation
Exploitation requires only a single crafted consensus proof submission (a `relayed proof` in the threat model), reachable by any unprivileged relayer submitting a BEEFY consensus update — no admin/governance/node compromise is needed beyond controlling (or having leaked) as few as one or a small minority of authority keys, which is a materially weaker bar than the intended 2/3+1 threshold.

## Recommendation
In both `EcdsaBeefy.sol::verifyMmrUpdateProof` and `verify_mmr_update_proof` (Rust), deduplicate `authorityIndex`/`sig.index` before computing `sigLen`/`signatures_length` and before feeding the merkle multi-proof leaves, e.g., reject the proof if any `authorityIndex` repeats — mirroring the `DuplicateParticipant` check already implemented in the Pharos verifier (`verify_validator_membership`).

## Proof of Concept
1. Authority set has `total = 100`, so threshold = `(2*100)/3 + 1 = 67`.
2. Only 10 authorities are actually malicious/compromised and willing to sign a false commitment.
3. Attacker builds `votes`/`signatures` array containing these 10 valid `(authorityIndex, signature)` pairs repeated 7 times each (70 entries total), satisfying `sigLen = 70 >= 67`.
4. `checkParticipationThreshold`/`check_participation_threshold` passes.
5. The merkle multi-proof step succeeds because every `authorityIndex` used, though repeated, genuinely belongs to the authority set root.
6. The consensus client accepts the commitment as validly finalized by supermajority, despite only 10/100 authorities actually having signed. [1](#0-0) [7](#0-6)

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}

	let mmr_root_data = commitment
		.payload
		.get_raw(&MMR_ROOT_PAYLOAD_ID)
		.ok_or(Error::MmrRootHashMissing)?;

	if mmr_root_data.len() != 32 {
		return Err(Error::InvalidMmrRootHashLength { len: mmr_root_data.len() });
	}
	let mmr_root = H256::from_slice(mmr_root_data);

	let commitment_hash = H::keccak256(&commitment.encode());
	let mut authority_leaves: Vec<[u8; 32]> = Vec::new();
	let mut authority_indices = Vec::new();

	for sig in mmr.signed_commitment.signatures.iter() {
		let uncompressed = H::secp256k1_recover(&commitment_hash.0, &sig.signature)
			.map_err(|_| Error::FailedToRecoverPublicKey)?;

		let hashed_uncompressed = H::keccak256(&uncompressed);

		let mut eth_address = [0u8; 20];
		eth_address.copy_from_slice(&hashed_uncompressed.as_ref()[12..]);

		let authority_address_hash = H::keccak256(&eth_address);

		authority_leaves.push(authority_address_hash.into());
		authority_indices.push(sig.index as usize);
	}

	let merkle_proof = MerkleProof::<MerkleHasher<H>>::new(mmr.authority_proof.clone());

	let valid = merkle_proof.verify(
		authority_set.keyset_commitment.into(),
		&authority_indices,
		&authority_leaves,
		authority_set.len as usize,
	);

	if !valid {
		Err(Error::InvalidAuthoritiesProof)?;
	}

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
