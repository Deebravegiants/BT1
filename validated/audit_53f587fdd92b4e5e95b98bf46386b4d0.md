### Title
Front-runnable pool creation via deterministic market-seeded PDAs in `process_initialize2` allows attacker to steal pool creation and set an arbitrary initial price - ([File: program/src/processor.rs])

### Summary
`process_initialize2` derives all of the new pool's core accounts (AMM account, target orders, LP mint, coin vault, pc vault) deterministically from a single, attacker-choosable `market_info` account via `get_associated_address_and_bump_seed` using fixed seeds (`AMM_ASSOCIATED_SEED`, `TARGET_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED`). Because the resulting addresses depend only on `market_info` and `program_id` — not on the caller (`user_wallet_info`) — anyone who observes an in-flight `Initialize2` transaction can front-run it with the same `market_info` seed but their own `init_coin_amount`/`init_pc_amount`, winning the race to create the pool.

### Finding Description
`generate_amm_associated_account` and `generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint` derive addresses purely from `market_info.key` and fixed seed constants [1](#0-0) , and are invoked in `process_initialize2` for the target-orders, LP mint, coin vault, pc vault, and AMM accounts using the same `market_info` seed [2](#0-1) . The code comment on `market_info` explicitly states it is "Just a seed for AMM account. Can be any account." [3](#0-2) , and there is no check binding `market_info` to `user_wallet_info` or verifying the market is a genuine, unclaimed market.

If the derived accounts are still owned by the system program, they are created and initialized for whoever calls first; the pool's initial price is fully controlled by that caller's `init_coin_amount`/`init_pc_amount`, since `x`/`y` (and thus `TargetOrders.check_init`) are computed straight from the initial vault balances the caller supplies [4](#0-3) [5](#0-4) . Once created, any second call using the same `market_info` seed fails with `AmmError::RepeatCreateAmm` in `generate_amm_associated_account`/`generate_amm_associated_spl_token` [6](#0-5) [7](#0-6) .

### Impact Explanation
This is strictly worse than the referenced report's plain DoS: a front-runner does not just cause the legitimate creator's transaction to revert — they permanently seize the pool's identity for that `market_info` seed and set an arbitrary, attacker-favorable initial coin:pc ratio while depositing only the minimal token amounts needed to pass the `InvalidSupply`/`InitLpAmountTooLess` checks. The legitimate creator's `Initialize2` call reverts with `RepeatCreateAmm`/`AlreadyInUse`, and any users who subsequently interact with what they believe is the intended pool are trading/depositing against a maliciously mispriced pool, exposing them to value extraction by the attacker as the price is arbitraged back to fair value. This is a fund-loss/insolvent-pricing issue, not merely a revert.

### Likelihood Explanation
Pool creation transactions are public before confirmation (mempool/gossip visibility), and `Initialize2` accepts arbitrary `init_coin_amount`/`init_pc_amount` and an arbitrary `market_info` seed account with no signature or authorization check tying it to the original creator, making the front-run trivial to execute by any party monitoring pending transactions for a specific token pair/market they want to claim.

### Recommendation
Bind the derived PDAs to the caller's intent, e.g., include `user_wallet_info.key` (or a caller-supplied, freshly-generated nonce/seed committed to in advance) in the seed derivation for `AMM_ASSOCIATED_SEED`/`TARGET_ASSOCIATED_SEED`/`LP_MINT_ASSOCIATED_SEED`/vault seeds, or require `market_info` to be validated as a genuine market account (owned by/derived from the market program) so it cannot be freely chosen as an arbitrary seed by any address. Alternatively, use a commit-reveal scheme for pool creation so the initial price/amounts cannot be front-run.

### Proof of Concept
1. Alice broadcasts `Initialize2` for `market_info = M` with a fair `init_coin_amount`/`init_pc_amount` ratio.
2. Mallory observes the pending transaction, extracts `M`, and submits her own `Initialize2` with the same `market_info = M` but skewed `init_coin_amount`/`init_pc_amount` (e.g., depositing the minimum required amounts at an extreme ratio), with a higher priority fee so it lands first.
3. `generate_amm_associated_account`/`generate_amm_associated_spl_token` create the PDAs for Mallory since they were previously owned by the system program [8](#0-7) ; the pool is initialized at Mallory's chosen price and she receives the initial LP tokens.
4. Alice's transaction lands afterward and reverts with `RepeatCreateAmm`/`AlreadyInUse` since the same PDAs already exist and are owned by the program.
5. Any user or Alice herself who later swaps/deposits into what they think is the fairly-priced pool interacts with Mallory's mispriced pool instead, at Mallory's advantage.
