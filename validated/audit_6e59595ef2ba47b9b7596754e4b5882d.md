## Analysis

The reported bug class (a value used to make security decisions without verifying it's actually bound/covered by the security control) maps directly onto how `ShopifyAPI::Webhooks::Registry` processes inbound webhook requests.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` — the data that is actually covered by the HMAC signature — is **only the raw request body**: [1](#0-0) 

But the `shop` identity that the app relies on to attribute the webhook to a tenant is read straight from an HTTP header, which is never included in the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then immediately hands the (unauthenticated) `shop` header value to the app's handler as the tenant identity: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm this — they only ever operate on `verifiable_query.to_signable_string` (the body, for webhooks), never on the `shop-domain` header: [4](#0-3) 

### Broken identity binding

The equality that should hold is:
`shop_that_produced(hmac_over_body) == shop_delivered_to(handler)`

But since `shop-domain` (and `topic`, `webhook-id`, `api-version`) are **not part of the signed material**, any request whose body+HMAC pair is valid for the app's shared `api_secret_key` (used across *all* merchants of the app) will pass validation regardless of which `shop-domain` header accompanies it. Because Shopify uses the same per-app `client_secret` to HMAC-sign every merchant's webhooks, a webhook body legitimately delivered to shop A's endpoint (with its correct HMAC) can be re-submitted by the attacker to the same public webhook endpoint with the `x-shopify-shop-domain`/`shopify-shop-domain` header swapped to shop B. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` forwards `request.shop` — now shop B — to the handler, which will store/act on data under the wrong tenant.

An unprivileged internet user only needs the ability to install the app on a shop they control (a normal, unprivileged action) to legitimately receive one signed webhook body+HMAC pair, and then replay that request to the app's public webhook endpoint with an attacker-chosen `shop-domain` header — no `api_secret_key`, access token, or privileged access required.

### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw body via `to_signable_string`, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers. `Registry.process` validates the body HMAC and then trusts these headers, including `shop`, to decide which tenant the webhook belongs to.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) , while `Request#shop` is parsed directly from the `shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `HmacValidator.validate` computes and compares the HMAC purely against `verifiable_query.to_signable_string` [4](#0-3) , so the header is never authenticated. `Registry.process` checks only this body HMAC before dispatching `request.shop` to the app's handler as the trusted tenant identifier [3](#0-2) . Since a single `api_secret_key` is shared across all merchants of an app (it's per-app, not per-shop), any valid (body, HMAC) pair obtained from one shop's webhook remains valid when replayed with a different `shop-domain` header.

### Impact Explanation
This breaks the tenant isolation the gem is expected to provide to host applications: an attacker with a legitimately obtained webhook (from a shop they themselves control) can spoof the shop identity of any other merchant using the app, causing the host application to process/store attacker-controlled data under a victim shop's identity — a cross-tenant access issue.

### Likelihood Explanation
Exploitation requires no privileged credentials, access tokens, or the `api_secret_key` — only the ability to install the app once (any unprivileged internet user can do this on their own store) to capture one valid signed webhook, then replay it with a modified header to the app's public webhook endpoint.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` values in the signed/verifiable content (or otherwise cryptographically bind them to the signature), and/or validate that the delivered `shop` corresponds to a shop that has actually installed/authorized the app before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a legitimate webhook delivery: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same request to the app's public webhook endpoint but changes the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` — unaffected by the header change — and succeeds [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host app to act on attacker-controlled data attributed to the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
