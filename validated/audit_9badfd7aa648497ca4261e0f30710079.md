Based on my research, I found a concrete analog to the Salt "wrong cache directory / wrong data" bug class: a storage map keyed by an insufficiently-specific identifier that is used for security-critical proof verification, causing state/data to be resolved for the wrong logical entity.

### Title
EVM host address lookup keyed only by `StateMachine` (dropping `consensus_state_id`) lets a spoofed consensus client for the same chain id bind proof verification to the wrong `EvmHost` contract - (File: `modules/pallets/host-executive/src/lib.rs`)

### Summary
`EvmHosts` — the map used by every EVM-family `StateMachineClient::verify_membership`/`verify_state_proof` implementation to resolve which `IsmpHost` contract a membership/state proof must be checked against — is keyed only by `StateMachine` (chain id), not by the full `StateMachineId` (`state_id` + `consensus_state_id`). This mirrors the Salt bug class: a resource (git cache directory / here, the trusted host contract address) is looked up using a key that omits the "environment" component (saltenv / here, `consensus_state_id`), so two logically distinct trust contexts collapse onto the same cached resource and one can read/verify against data intended for another.

### Finding Description
`EvmHosts` is declared as: [1](#0-0) 

Every EVM-style `StateMachineClient` (EVM, Substrate-EVM/Revive, Tendermint-EVM, sync-committee EVM) resolves the trusted host contract with: [2](#0-1) [3](#0-2) 

Both only pass `proof.height.id.state_id` (the `StateMachine` enum, i.e. just the chain id) into `EvmHosts::get`, completely discarding `proof.height.id.consensus_state_id`. By contrast, the actual state commitment that anchors the proof (`state_machine_commitment`) is stored and fetched keyed by the *full* `StateMachineId`, which does include `consensus_state_id`: [4](#0-3) 

`create_client` allows anyone with authority to create a `CreateConsensusState` (or, more importantly, `pallet-ismp` supports multiple independently-created consensus clients for the same `StateMachine::Evm(chain_id)` under different `consensus_state_id`s) to register `state_machine_commitments` for that chain id under a new/attacker-influenced `consensus_state_id`: [5](#0-4) 

Because `StateMachineId` is explicitly documented as the mechanism to disambiguate "multiple consensus systems agreeing about the same state machine": [6](#0-5) 

...the protocol's own data model treats `(state_id, consensus_state_id)` as the unit of trust — yet the `EvmHosts` contract-address cache silently strips the second component. Once a second consensus client for the same `state_id` exists (whether via a misconfigured/compromised client, a coprocessor-relayed proxy consensus client, or a governance-approved but differently-parameterized client for the same EVM chain id), any state commitment stored under that second `consensus_state_id` is verified using the *same* `EvmHosts` contract address as the legitimate client. A membership/state proof crafted against a state root committed by the wrong/attacker-influenced consensus client for that chain id is checked against the correct chain's host address rather than being rejected for a mismatched or absent binding — exactly the "wrong environment gets used because the cache key was too coarse" failure mode from the Salt advisory.

### Impact Explanation
If a second consensus client is ever registered for a `StateMachine` value that already has an `EvmHosts` entry (a state achievable through normal client-management flows for coprocessor/proxy-chain configurations, or through any admin/relayer error), requests/responses/timeouts routed through that mis-scoped `StateMachineId` are verified with the wrong contract binding. This can let a forged/foreign state commitment be accepted as membership proof of a request/response commitment supposedly on the legitimate chain's `IsmpHost`, enabling forged message delivery or unsound state-proof verification for `handle_unsigned`/`GetResponse` processing — a Medium-severity “wrong data” condition matching the report's bug class.

### Likelihood Explanation
This requires a second `StateMachineId` sharing the same `state_id` (chain id) but a different `consensus_state_id` to exist and have its own `EvmHosts`-relevant commitments — a scenario within the "single dispatched proof" reachable surface (proof/consensus-client management is a normal, low-privilege-adjacent, reachable operation in this system rather than admin-only, since `create_client` and challenge-period gated client operations are open ISMP handlers), so likelihood is plausible but conditional on such a dual-registration occurring.

### Recommendation
Change `EvmHosts` (and any other host-address/contract-binding maps consulted during proof verification) to be keyed by the full `StateMachineId` (`state_id` + `consensus_state_id`) instead of `StateMachine` alone, and update all `StateMachineClient::verify_*` call sites to pass `proof.height.id` rather than `proof.height.id.state_id`.

### Proof of Concept
1. Configure/allow a second consensus client (`consensus_state_id = "XYZ0"`) that also asserts commitments for `StateMachine::Evm(<same chain id as an existing "ETH0" client>)` via `create_client`/`update_client` (module/ismp/core/src/handlers/consensus.rs).
2. This client's `state_machine_commitments` are stored under `StateMachineId{ state_id: Evm(1), consensus_state_id: "XYZ0" }`, independent of the legitimate `"ETH0"` client's commitments (`modules/pallets/ismp/src/host.rs:59-65`).
3. Submit a `RequestMessage`/`ResponseMessage`/`GetRequestsWithProof` whose `proof.height.id = StateMachineId{ Evm(1), "XYZ0" }`.
4. `EvmStateMachine::verify_membership` looks up `EvmHosts::get(&StateMachine::Evm(1))`, which resolves to the same contract address configured for `"ETH0"`, and verifies the supplied proof against the `"XYZ0"` state root — despite `"XYZ0"` never having been vetted/bound specifically to that `EvmHost` deployment.
