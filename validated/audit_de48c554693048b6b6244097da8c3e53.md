### Title
Unrestricted self-relaying of low-value messages allows unbounded `ReputationAsset` minting, letting an attacker rig collator selection - (File: modules/pallets/messaging-incentives/src/lib.rs)

### Summary
The external report describes a Sybil/self-referral attack: `registerPlayer` grants points for every referral with no limit on how many fake accounts can be created or how many times a referral link can be reused, letting an attacker programmatically inflate their own points balance for free. The structurally identical pattern exists in `pallet-messaging-incentives`, where `ReputationAsset` — a token that directly determines parachain **collator selection** — is minted to whoever signed a delivered ISMP message, with no check that the signer is a bonded/registered/legitimate relayer and no cap on how many messages one address may self-dispatch and self-deliver.

### Finding Description
`FeeHandler::on_executed` in `pallet-messaging-incentives` mints `ReputationAsset` to the address recovered from the `signer` field of every successfully executed `Request`/`Response` message, scaled by `max(body_len, 32) × MintPerByte`: [1](#0-0) 

The "relayer" identity is derived purely by recovering the sr25519 signer of the message payload — there is no registration, staking, bonding, or reputation-gating requirement to become "a relayer" for the purposes of this mint: [2](#0-1) 

Any account can generate a keypair, sign a `Request`/`Response` message it constructs (e.g. a cheap, low-value ISMP request routed through `pallet-ismp-demo`/ping or any other module), submit it for delivery/execution, and be recorded as the delivering "relayer." Because the per-byte floor of 32 bytes is applied *per request* rather than per envelope, an attacker can freely repeat this with many minimal-body requests to accumulate mint amounts without limit — this is the on-chain analogue of the report's "automated multi-account registration" and "unrestricted referral usage": there is no limit on how many times the reward-granting action (message delivery) can be repeated by a single actor, and no gate preventing a party from being both the message's originator and its "relayer."

This minted `ReputationAsset` is not cosmetic: `pallet-collator-manager::new_session` ranks and selects the active collator set directly by `ReputationAsset` balance: [3](#0-2) 

So farming this asset via self-relayed spam messages is a path to displacing legitimate collators/validators in the active set — i.e., manipulating who produces blocks and participates in consensus for the chain, not merely inflating a leaderboard score.

### Impact Explanation
Where the original report's impact was capped at "the value of referral loss" (acknowledged as low-severity by the project itself), this Hyperbridge analogue reaches into consensus-security territory: `ReputationAsset` is the sorting key used by `SessionManager::new_session` to pick the collator set on every session rotation. An attacker who can mint unbounded reputation for a controller address they control can force that address into the active collator set ahead of legitimate, honestly-earned collators, undermining the integrity of block production/consensus selection on the affected parachain (gargantua/nexus). This is a Medium/High-severity "unauthorized app action" — an attacker obtains privileged network participation (collator slot) they did not legitimately earn, via unrestricted self-farming of a token gating that privilege.

### Likelihood Explanation
Likelihood is contingent on `MintPerByte` being set to a non-zero value by governance (the pallet ships inert by default), which mirrors the "if referral rewards are ever meaningful" caveat Ludex Labs itself raised in the original report. Once enabled, exploitation only requires the ability to author and self-deliver ISMP `Request`/`Response` messages with a valid signer signature — a capability available to any unprivileged relayer/message submitter, with no bonding, KYC, or per-address rate limit standing in the way, exactly as in the original PoC's loop of automated re-registrations.

### Recommendation
- Require that the "relayer" credited by `on_executed` be a registered/bonded relayer (e.g., cross-reference against a staking/registration pallet) rather than accepting any recovered signature as sufficient proof of a legitimate delivery.
- Apply a per-account or per-session cap on `ReputationAsset` mintable via this path, or rate-limit/aggregate by unique source rather than per-message, closing the same "unrestricted repetition" gap the original report flagged for referrals.
- Consider requiring that minted reputation derive only from messages that also carry a genuine, non-zero fee/payer (i.e., tie the incentive to real economic activity that an attacker cannot costlessly self-generate), analogous to recommending KYC/anti-Sybil measures for the referral case.

### Proof of Concept
Conceptual PoC mirroring the report's loop (no `RegisterPlayerHandler`/`CREATE2` needed on-chain; the equivalent primitive here is self-authored, self-delivered messages):
1. Governance (or an already-live deployment) sets `MintPerByte` to non-zero via `set_mint_per_byte`.
2. Attacker generates an sr25519 keypair `K`, and repeatedly constructs minimal `Request` messages (body length ≤ 32 bytes, hitting the floor) destined for/through the host, signing each with `K` as the `signer`.
3. Attacker submits each message for execution so that `pallet-ismp` invokes `FeeHandler::on_executed`; `relayer_for` recovers `K` from each message's signature and `ReputationAsset::mint_into(&K, amount)` mints reputation to `K` every time, with no ceiling on repetition: [4](#0-3) 
4. Attacker registers `K` (or an account controlling it) as a collator controller; at the next `new_session`, the inflated `ReputationAsset` balance ranks it above legitimate collators, forcing it into the active set: [5](#0-4)

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
