## Title
Integer-division truncation in instruction data cost systematically under-charges compute units in the cost model — ([File: cost-model/src/cost_model.rs])

### Summary
The reported Morpho `VaultV2.forceDeallocate` bug rounds a penalty **down** via `mulDivDown`, letting a user avoid paying (or under-pay) a required cost that should always round in favor of the protocol. The closest reachable analog in agave is `CostModel::get_instructions_data_cost`, which divides instruction data length by a cost-per-byte constant using **floor (truncating) division** instead of rounding up, systematically under-reporting the compute-unit cost attributed to a transaction's instruction data.

### Finding Description
`CostModel::get_instructions_data_cost` computes the CU cost of instruction data as: [1](#0-0) 

```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    transaction.instruction_data_len() / (INSTRUCTION_DATA_BYTES_COST as u16)
}
```

`INSTRUCTION_DATA_BYTES_COST` is itself a truncated compile-time constant: [2](#0-1) 

```rust
/// Number of data bytes per compute units
pub const INSTRUCTION_DATA_BYTES_COST: u64 = 140 /*bytes per us*/ / COMPUTE_UNIT_TO_US_RATIO;
```

With `COMPUTE_UNIT_TO_US_RATIO = 30`, `INSTRUCTION_DATA_BYTES_COST` truncates `140/30 = 4.66…` down to `4`. Then `get_instructions_data_cost` again performs `instruction_data_len / 4` with integer (floor) division. This means:
- Any instruction data length from `0..=3` bytes is charged **exactly `0`** CU, regardless of the true (non-zero) fractional cost.
- Every non-multiple-of-4 data length loses up to `3/4` of a CU unit of cost per instruction — this is the direct analog of the "999 * 1e15 / 1e18 = 0" example in the report: a division that should round in favor of the protocol/network (ceil) instead rounds down (floor), always benefiting the party whose activity is being costed (the transaction sender), never the protocol.

This differs from the other fee-related divisions in the codebase (e.g. `get_prioritization_fee` in `compute-budget/src/compute_budget_limits.rs`, `MicroLamports.div_ceil`) which deliberately round **up** in favor of the network, and from `commission_split`/`burn_percent` computations, which are validator/operator-facing and out of scope. `get_instructions_data_cost` is the one place in the compute-cost accounting path that rounds down and is fully influenced by unprivileged, attacker-controlled input (`instruction_data_len`), matching the "in scope" categories of SVM loading / compute budget / cost model.

The resulting `data_bytes_cost` feeds directly into `TransactionCost::sum()`, which underlies cost-tracker block-inclusion and the fee/priority estimation paths: [3](#0-2) 

### Impact Explanation
Because the division always truncates toward zero, every transaction with instruction data whose length is not a multiple of 4 bytes is charged strictly less compute-unit cost than the model intends, and any transaction with `1..=3` bytes of instruction data is charged **zero** cost for that dimension. This systematically under-prices execution against the cost-tracker's block/account cost limits (`MAX_BLOCK_UNITS`, `MAX_WRITABLE_ACCOUNT_UNITS`), letting senders "smuggle in" free instruction-data bytes and pack a small amount of additional real cost into a block beyond what the cost model accounts for. This is a systemic, attacker-triggerable (any user can control instruction data length) under-accounting of cost rather than a one-off edge case, mirroring the reported vulnerability class of a rounding-down division that "leaks value" (here, leaks compute-cost accounting headroom) in favor of the calling party instead of the network.

### Likelihood Explanation
This requires no privileged access — any transaction sender fully controls `instruction_data_len`, and the truncation triggers on the overwhelming majority of possible data lengths (3 out of every 4 byte-length values, and always for lengths under 4 bytes). It occurs deterministically and identically on all validators (no cross-node divergence), so it is a systemic under-pricing bug rather than a rare, hard-to-hit condition.

### Recommendation
Use ceiling (`div_ceil`) rather than floor division when computing `data_bytes_cost`, consistent with the rounding convention already used for `get_prioritization_fee` (`MicroLamports::div_ceil`) and `calculate_pages_for_bytes` (`saturating_add(page_size - 1).saturating_div(page_size)`), so that instruction data cost is always rounded up in favor of the network/cost-tracker rather than down in favor of the transaction sender.

### Proof of Concept
```rust
// INSTRUCTION_DATA_BYTES_COST = 140 / 30 = 4 (already truncated)
// For any instruction_data_len in 0..=3:
let cost = CostModel::get_instructions_data_cost(&tx_with_data_len(3));
assert_eq!(cost, 0); // charged 0 CU for 3 bytes of instruction data, should be > 0

// For instruction_data_len = 7:
let cost = CostModel::get_instructions_data_cost(&tx_with_data_len(7));
assert_eq!(cost, 1); // true cost is 7/4 = 1.75, rounds down to 1, losing 0.75 CU
```
Repeating this over many instructions/transactions in a block allows senders to include extra instruction-data bytes that are not reflected at all in the cost-tracker's accounting, always in the sender's favor.
