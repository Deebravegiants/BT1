Based on my research, the intent gateway family (`ExtrinsicIntents.sol`) exhibits exactly the analog bug-class pattern described in the report: a function family that is *supposed* to be gated by a permission check, but one member of the family relies only on an implicit/default deny rather than an explicit gate that its siblings enforce.

`onAccept` and `onGetResponse` both explicitly call `_checkRelayer(incoming.relayer)` before processing any request body [1](#0-0) [2](#0-1) . However, `IntentGatewayV2`/`ExtrinsicIntents` does **not** override `onPostRequestTimeout` or `onGetTimeout` at all — a `grep` across `evm/src/apps/intentsv2/*.sol` found no such functions in these contracts. A repo decision note explicitly documents this asymmetry: `onPostRequestTimeout` relies on `HyperApp`'s default (revert-only) implementation instead of the explicit relayer gate the gateway uses elsewhere, and the authors' stated justification is that the gateway "dispatches with no timeout" so the code path is believed unreachable [3](#0-2) .

This is the same bug class as CVE-2023-30583: a security-relevant function (`onPostRequestTimeout`) is left ungated by the same access-control mechanism (`_checkRelayer`) that sibling functions (`onAccept`, `onGetResponse`) enforce, relying instead on an assumption about how the function is invoked rather than an explicit check. In other apps such as `BridgeToken.sol` and `HyperFungibleToken.sol`, `onPostRequestTimeout` **is** explicitly relayer-gated (confirmed by their test suites asserting `UnauthorizedRelayer` reverts for unlisted relayers) [4](#0-3) , showing the intent gateway's omission is inconsistent with the established pattern elsewhere in the codebase.

That said, I could not independently verify at code level (rather than via the decision doc's claim) that IntentGatewayV2 truly dispatches every outgoing post request with `timeout: 0`, which is the load-bearing assumption behind treating this as safe-by-construction — reachability of `onPostRequestTimeout` on this contract depends entirely on that invariant holding for every dispatch call site (including `_cancelFromDest`/`_post`), and a regression in any one of those call sites (e.g., a future code path passing a non-zero timeout, or an upgrade via the `Execute`/`UpgradeContract` governance path) would silently reopen an ungated, host-invokable callback path. Given this dependency on an implicit invariant rather than an explicit, testable gate, and that the report explicitly calls out reliance on "default" behavior over active permission enforcement as the root cause pattern, I am flagging this as the closest analog, though I want to note the severity is bounded by the "dispatches with no timeout" claim, which limits — but does not eliminate — practical reachability today.

#### Title
Missing explicit relayer gate on `onPostRequestTimeout`/`onGetTimeout` in IntentGatewayV2 (relies on unenforced dispatch invariant) - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

#### Summary
`ExtrinsicIntents.sol` (the base implementation behind `IntentGatewayV2`) explicitly gates `onAccept` and `onGetResponse` with `_checkRelayer(incoming.relayer)` before any request processing, but does not implement (or gate) `onPostRequestTimeout`/`onGetTimeout` at all, falling back to `HyperApp`'s default revert-only stubs. Safety currently depends entirely on the undocumented-in-code invariant that the gateway always dispatches with `timeout: 0`.

#### Finding Description
`onAccept` and `onGetResponse` call `_checkRelayer` as the very first line to ensure only the authorized relayer's delivered messages are honored [1](#0-0) [2](#0-1) . No equivalent `onPostRequestTimeout`/`onGetTimeout` override exists in `IntentsBase.sol` or `ExtrinsicIntents.sol`, so any timeout delivered by `EvmHost.dispatchTimeOut` (which is only restricted to the host's `handler`, not to a specific relayer) would hit the base `HyperApp` implementation. This mirrors the fs.openAsBlob() report's pattern: a function that should be covered by the same access-control regime as its siblings, but is not, and instead depends on an implicit assumption (here, "the gateway never dispatches with a nonzero timeout") for safety, per the project's own decision log [3](#0-2) .

#### Impact Explanation
If the "no timeout" invariant is ever violated (e.g., a future code change adds a non-zero timeout to any `_post` call site, or a governance `Execute`/`UpgradeContract` action changes dispatch behavior), an unauthenticated/unlisted relayer could deliver a forged timeout callback to the gateway, since there is no relayer check comparable to `_checkRelayer` protecting that path — potentially unlocking unauthorized escrow refunds analogous to the `BridgeToken`/`HyperFungibleToken` mint-on-timeout risk that those contracts explicitly guard against with the same `_checkRelayer` pattern.

#### Likelihood Explanation
Low-to-moderate: exploitation requires either (a) the dispatch invariant regressing so `timeout != 0`, or (b) governance/upgrade actions introducing a code path that dispatches with a timeout. Given the codebase's continual evolution (evidenced by frequent audit-fix and decision-log entries), and that this gate is enforced only by convention rather than by code, this is a latent risk rather than an immediately exploitable one under current code.

#### Recommendation
Explicitly override `onPostRequestTimeout` and `onGetTimeout` in `ExtrinsicIntents.sol` (or `IntentsBase.sol`) with the same `_checkRelayer(incoming.relayer)` gate used in `onAccept`/`onGetResponse`, rather than relying on the implicit "always timeout=0" invariant. This closes the gap defensively and keeps the access-control model consistent and auditable across all `IApp` callback entry points, matching the explicit gating already present in `BridgeToken.sol`/`HyperFungibleToken.sol`.

#### Proof of Concept
Not directly exploitable under the current known dispatch pattern (all outgoing posts use `timeout: 0`); a concrete PoC would require identifying a call site or future code change that dispatches a `DispatchPost` with a non-zero timeout from the intent gateway, then having a non-authorized relayer submit a timeout proof through `EvmHost.dispatchTimeOut`, invoking the gateway's default (ungated) `onPostRequestTimeout`.
