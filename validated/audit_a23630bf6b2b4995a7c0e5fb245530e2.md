## Title
Webhook shop/topic identity spoofing via HMAC that covers only the raw body — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
Shopify's webhook HMAC is computed and verified solely over the raw JSON body. The `shop-domain`, `topic`, and `webhook-id` HTTP headers — which `ShopifyAPI::Webhooks::Registry.process` treats as authoritative tenant/event identity and forwards unmodified to the app's handler — are never included in the signed data. Any unprivileged user who can obtain one legitimately-signed `(body, hmac)` pair for the app (e.g., by installing the app on their own shop and receiving a real webhook, since the app uses one shared `api_secret_key` for every installed shop) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the request will pass HMAC validation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body for webhook requests) and compares it to the received signature — it never mixes in `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` only checks this body-only HMAC, then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` when building `WebhookMetadata` that is handed to the app's business logic: [4](#0-3) 

The identity binding that should hold is:
`shop_the_HMAC_actually_authenticates == shop_delivered_to_the_handler`

Because the HMAC is computed with the app's single shared `api_secret_key` for *all* installed shops, and covers only the body, this equality does not hold: the `shop` (and `topic`/`webhook_id`) value delivered to the handler is attacker-controlled header data, disconnected from what was actually signed.

### Impact Explanation
This crosses a tenant boundary without needing the app's credentials directly: an attacker who is a legitimate (but unprivileged) installer of the target app on their own store can capture a genuine `(raw_body, hmac)` pair from a webhook Shopify sends them (e.g. `orders/create`, `app/uninstalled`, or any topic whose payload doesn't itself encode the shop domain). They can then submit that identical body+HMAC to the app's webhook endpoint while setting `x-shopify-shop-domain` (and/or `x-shopify-topic`) to a victim shop. `Registry.process` will accept it as HMAC-valid and pass `shop: <victim-shop>` to the handler. If the host app uses this `shop` value to select the tenant's stored session/access token or to key writes (a documented and expected usage pattern per `WebhookMetadata`), the attacker can trigger tenant-confused processing under the victim's identity — a cross-tenant access condition.

### Likelihood Explanation
Likelihood is high: obtaining a valid `(body, hmac)` pair requires nothing more than installing the app on one's own store (a normal, unprivileged action), and no part of this library's webhook verification path checks that the header-supplied shop/topic corresponds to the signed payload.

### Recommendation
Bind the identifying headers into the signed material, or otherwise cryptographically tie the `shop`, `topic`, and `webhook_id` to the verified body — e.g., have `HmacValidator`/`Request#to_signable_string` include these header values in the HMAC input (matching how `Auth::Oauth::AuthQuery#to_signable_string` correctly signs `shop` alongside other fields), or require the caller to independently verify `shop` against the session/access-token that legitimately owns the webhook subscription before trusting it for any tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the exact `raw_body` and the `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker sends a POST to the app's webhook endpoint with:
   - `x-shopify-hmac-sha256`: the captured (still-valid) HMAC
   - Body: the captured `raw_body`, unmodified
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (arbitrary)
   - `x-shopify-topic`: unchanged or also arbitrary
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — this matches, so validation succeeds.
4. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` and dispatched to the app's handler, which then processes/persists data as if it legitimately came from the victim shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
