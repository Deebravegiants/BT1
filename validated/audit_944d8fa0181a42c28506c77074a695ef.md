## Title
Consensus client expiry (`ConsensusClientExpired` / `UnbondingPeriodElapsed`) permanently freezes in-flight requests with no recovery path — analogous to Wormhole guardian-set rotation bricking pending message delivery ([File: evm/src/core/HandlerV2.sol])

### Summary
Hyperbridge's ISMP consensus clients (EVM `HandlerV2.handleConsensus`, and the Rust `update_client`/`is_expired` path) enforce an "unbonding period": if no consensus update is accepted within `unStakingPeriod`/`unbonding_period` of the last successful update, all future consensus updates for that client permanently revert. Because message delivery and timeout-recovery both depend on new `StateCommitment`s produced exclusively through consensus updates, a relayer who withholds (or is economically disincentivized from) submitting a timely consensus update — the exact scenario described in the Wormhole report (fee-set-by-sender, gas spikes causing the relayer to delay) — can cause the client to expire. Once expired, this is explicitly documented as unrecoverable, and any request whose delivery or timeout proof requires a state commitment beyond the last-accepted height can never be produced again, permanently freezing any locked/escrowed funds tied to it.

### Finding Description
`HandlerV2.handleConsensus` gates every consensus update behind an unbonding check: [1](#0-0) 

```solidity

    uint256 delay = block.timestamp - host.consensusUpdateTime();
    if (delay >= host.unStakingPeriod()) revert ConsensusClientExpired();
    ...
```

The error is annotated as unrecoverable: [2](#0-1) 

Because `consensusUpdateTime()` is only advanced by a *successful* `handleConsensus` call, once `delay >= unStakingPeriod` is reached, every subsequent call recomputes the same (or larger) `delay` and reverts again — the client can never accept a new consensus update again. The mirrored Rust path enforces the identical rule via `IsmpHost::is_expired`, called from `update_client`: [3](#0-2) [4](#0-3) 

The docs confirm this is meant to mitigate long-fork attacks, but the practical consequence is that **all future `StateMachineCommitment`s for that consensus client become permanently unobtainable** once expiry triggers. Both message delivery (`handlePostRequests`/`handleGetResponses`, which need a membership proof against a *new* commitment covering the dispatch height) and timeout recovery (`handlePostRequestTimeouts`/`handleGetRequestTimeouts`, which need a non-membership proof against a commitment whose timestamp exceeds the request's `timeout_timestamp`) depend on commitments produced only through `handleConsensus`/`update_client`: [5](#0-4) 

If, at the moment of expiry, no already-stored commitment height has a timestamp past a given in-flight request's `timeout_timestamp`, that request can neither be delivered (no future height will ever be committed) nor timed out (no future non-membership proof can ever be produced). This mirrors the Wormhole report precisely: the relayer/incentive layer lets fees be set by the sender while gas conditions or relayer liveness are outside the protocol's control, and if delivery/finality lags past a hard cliff tied to validator/consensus rotation ("unbonding period" here, guardian-set expiry there), the message becomes permanently stuck — except here there is no way to "revert the state on the sending chain" at all, since even the timeout path requires the very consensus client that has just bricked.

### Impact Explanation
Any `PostRequest`/`GetRequest` dispatched shortly before consensus updates for the relevant client stall for longer than the configured unbonding period becomes permanently frozen: it can never be delivered to its destination, and it can never be timed out to refund the sender/unlock escrowed value on the source chain. Because `ConsensusClientExpired` cannot be cleared (no “unfreeze” path exists — only creating an entirely new consensus client, which does not resurrect the stuck request commitments tied to the old client), this is a permanent freezing-of-funds condition, not merely a delay. This satisfies the "route unable to deliver messages" / "permanent freezing of funds" bar for Medium/High severity.

### Likelihood Explanation
Exploitability does not require malicious intent — a normal gas spike, node outage, or relayer economic disincentive during a busy period is sufficient, exactly the scenario surfaced in the original Wormhole report (sender sets a fixed relayer incentive that becomes unprofitable during a fee spike). Any unprivileged user who dispatches a `PostRequest`/`GetRequest` near the tail end of the unbonding window is exposed; no attacker cooperation is needed, only relayer/consensus liveness lapsing past the configured window.

### Recommendation
- Decouple timeout recovery from the live consensus client: allow non-membership/timeout proofs to be validated against a governance-supplied "last known good" checkpoint or a permissionless emergency path once a client is marked expired, so escrowed funds can still be recovered even after expiry.
- Alternatively, before hard-expiring a client, allow a bounded "grace" window in which only overdue-but-already-in-flight requests can still be finalized/timed out, decoupled from accepting *new* dispatches.
- Surface `unStakingPeriod`/`unbonding_period` proximity as an on-chain queryable signal so integrators (and the relayer network) can proactively force an update, and consider making the unbonding window generously larger than any expected relayer/fee-market outage.

### Proof of Concept
1. Dispatch a `PostRequest` on chain A destined for chain B with `timeout_timestamp = T`.
2. Ensure no relayer submits `handleConsensus` (or `update_client`) for the consensus client bridging A and B for longer than `unStakingPeriod` (e.g., simulate an extended gas spike/relayer outage), such that `block.timestamp - host.consensusUpdateTime() >= host.unStakingPeriod()`.
3. Attempt `handleConsensus` with any subsequent valid proof — it reverts with `ConsensusClientExpired()` per [6](#0-5) ; the client's `consensusUpdateTime()` never advances again, so this reverts forever.
4. Attempt to deliver the original request via `handlePostRequests` — it requires `host.stateMachineCommitment(request.proof.height)` for a height that was never (and now can never be) committed; `StateCommitmentNotFound()` forever.
5. Attempt to time out the request via `handlePostRequestTimeouts` for a height whose timestamp exceeds `T` — no such height was ever committed (or none will be if `T` is beyond the last committed timestamp), so `StateCommitmentNotFound()`/inability to produce the proof persists forever, leaving any locked fee/value on chain A permanently unrecoverable.

    /// Check if the client has expired since the last update
    fn is_expired(&self, consensus_state_id: ConsensusStateId) -> Result<(), Error> {
        let host_timestamp = self.timestamp();
        let unbonding_period = self
            .unbonding_period(consensus_state_id)
            .ok_or(Error::UnnbondingPeriodNotConfigured { consensus_state_id })?;
        let last_update = self.consensus_update_time(consensus_state_id)?;
        if host_timestamp.saturating_sub(last_update) >= unbonding_period {
            Err(Error::UnbondingPeriodElapsed { consensus_state_id })?
        }

        Ok(())
    }
