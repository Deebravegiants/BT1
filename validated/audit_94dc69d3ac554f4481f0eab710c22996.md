Audit Report

## Title
JWT replay-protection check-then-act race allows a single signed trigger request to be executed twice - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks `h.jwtCache.isReplay(claims.ID)` early, then performs workflow-lookup and signer-authorization checks, and only calls `h.jwtCache.recordUsage(claims.ID)` at the very end, right before returning success. Since `isReplay` and `recordUsage` are two separately-locked operations rather than one atomic check-and-set, two concurrent `Authorize` calls carrying the same JWT (`jti`) can both pass the replay check before either records usage, allowing a single one-time-use signed trigger token to authorize two workflow executions.

## Finding Description
`isReplay` takes an `RLock`, checks map membership, and releases the lock; `recordUsage` takes a separate `Lock` afterward, once workflow-ID lookup and signer-authorization checks succeed. There is a window between the `isReplay` check and the `recordUsage` write during which a second `Authorize` call using the identical `jti` will also observe `exists == false` and proceed to be authorized. This defeats the intended one-time-use anti-replay guarantee that the error message explicitly documents ("JWT token has already been used..."). `Authorize` is called from `httpTriggerHandler.authorizeRequest`, itself called from `HandleUserTriggerRequest` — the standard, unauthenticated (pre-signature-verification-aside) code path invoked for every incoming user trigger request to the gateway. No existing lock, mutex, or atomic primitive spans both the read and the write, so the check-then-act gap is real and not mitigated elsewhere in the call chain.

## Impact Explanation
A successful race lets one valid signed JWT trigger a workflow execution twice (or more, with enough concurrent goroutines) instead of exactly once, breaking the anti-replay guarantee that gates HTTP-triggered workflow execution. This is a genuine gateway request-impersonation/replay bypass that can cause an unauthorized duplicate job run to be dispatched to a workflow owner's DON, matching an in-scope Chainlink impact category (unauthorized job run via replay/allowlist bypass).

## Likelihood Explanation
Exploitation requires only sending the same previously valid signed JWT trigger request twice in close succession — no signing key compromise, no elevated privileges, and no malicious node/peer involvement. Any unprivileged client capable of issuing (or replaying) its own already-signed request can attempt the race. The window is small (a handful of map operations) but the underlying check-then-act pattern is a genuine, code-level TOCTOU flaw; existing tests (`TestWorkflowMetadataHandler`'s "JWT replay protection" subtest) only assert sequential replay is rejected and do not exercise the concurrent case, so the race is unguarded in practice.

## Recommendation
Make replay-check and consumption atomic: combine `isReplay` and `recordUsage` into a single method that acquires one lock for the full "check-if-seen, then mark-as-seen" sequence (e.g., mirroring the `CheckAndRecord` pattern used by `core/capabilities/vault/request_replay_guard.go`), and call that single atomic method from `WorkflowMetadataHandler.Authorize` instead of the two separately-locked calls.

## Proof of Concept
1. Obtain one validly signed `workflowExecute` JWT trigger request (a legitimate workflow owner's token).
2. Launch two concurrent calls to `WorkflowMetadataHandler.Authorize` (or, end-to-end, two concurrent `HandleUserTriggerRequest` gateway calls) using the identical JWT/`jti`.
3. Both goroutines call `h.jwtCache.isReplay(claims.ID)` before either calls `h.jwtCache.recordUsage(claims.ID)`; both pass authorization and the workflow trigger is dispatched twice from a single one-time-use token. This can be demonstrated with a Go unit test analogous to `TestRequestReplayGuard_ConcurrentAccess` in `core/capabilities/vault/request_replay_guard_test.go`, but invoking `WorkflowMetadataHandler.Authorize` with the same token from N goroutines and asserting more than one succeeds.
