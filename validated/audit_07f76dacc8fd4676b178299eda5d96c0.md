### Title
Local-only enrollment status determination bypasses backend fraud/dedup verification for user-centric signups - (File: `src/plans/mod.rs`)

### Summary
In `MasterPlan::do_signup`, signups flagged as `user_centric_signup` skip the backend enrollment/verification flow (`enroll_user::Plan::run`) entirely and instead have their `enrollment_status` (`Success`/`Error`) derived purely from the orb-local `signup_reason` value (computed from the local biometric pipeline and local fraud checks). This is analogous to the referenced Compound Governor bug, where a completion/execution flag (`executed`) was set based on an earlier stage of the process rather than on confirmation of the actual terminal action, causing the state machine to report a status that had not actually occurred.

### Finding Description
For normal (non-user-centric) signups, `enrollment_status` is only set to `Success` after the full backend round-trip: `enroll_user::Plan::run` posts the signup via `signup_post::request` and then polls `signup_poll::request` in a loop until the backend explicitly returns `Status::Completed` with `success: true` [1](#0-0) [2](#0-1) . This backend poll is explicitly documented as covering backend-side duplicate detection, inflight-match detection, and backend-detected fraud, in addition to orb-detected fraud [3](#0-2) .

However, for `user_centric_signup` requests, this entire backend confirmation path is skipped. The code directly sets `debug_report.enrollment_status` based solely on the locally-computed `signup_reason` (itself derived from the on-orb `biometric_pipeline` result and `detect_fraud` check), and treats the signup as successful whenever `signup_reason == SignupReason::Normal`: [4](#0-3) 

Here, `success` (and thus `result.success` and the reported `enroll_user::Status::Success`) is determined entirely from local computation, without the equivalent of the `signup_post`/`signup_poll` round-trip that other signups must complete. Just as the `GovernorBravoDelegate` contract marked `executed = true` at the "queue" stage instead of at actual execution, here the "enrollment succeeded" state is marked at the local "pipeline finished, no local fraud detected" stage instead of at actual backend-confirmed enrollment completion.

### Impact Explanation
Because the user-centric-signup success determination bypasses the backend polling step that performs duplicate/inflight-match detection and backend-side fraud detection, a signup can be recorded and reported as `Success` by the orb even though the backend would otherwise have rejected it as a duplicate, an inflight match, or fraud. This creates a state where the local signup record and downstream systems relying on `debug_report.enrollment_status`/`result.success` believe the signup is complete and legitimate, while no backend-side confirmation or dedup/fraud verification occurred — a misattributed/unverified signup condition, and a fraud-check bypass for this signup path.

### Likelihood Explanation
This path is only reachable when `qr_codes.user_data.user_centric_signup` is true and the orb config `ignore_user_centric_signups` is false, which is a legitimate, backend-controlled signup mode (not an attacker-controlled toggle) [5](#0-4) . Any signup routed through this legitimate mode will always skip backend verification, so the condition is deterministic and not merely theoretical, though it is gated on the `user_centric_signup` flag being set by the backend for a given QR code/session.

### Recommendation
For `user_centric_signup` signups, still require an explicit backend confirmation step (equivalent to `signup_post`/`signup_poll`) before setting `enrollment_status` to `Success`, rather than deriving success solely from the local `signup_reason`. At minimum, the backend should be given the opportunity to reject the signup for duplicate/inflight/fraud reasons before the orb commits to reporting `Success`.

### Proof of Concept
1. Configure a signup session where the backend marks `user_centric_signup = true` for the QR code/session (`qr_codes.user_data.user_centric_signup`).
2. Complete the biometric capture and pipeline such that the local fraud checks in `detect_fraud` do not flag anything (`signup_reason == SignupReason::Normal`), even though this same iris/user data would be flagged as a duplicate or fraud by the backend's dedup/fraud logic (which is normally invoked via `signup_post`/`signup_poll`).
3. Observe that `do_signup` takes the `user_centric_signup` branch and marks `debug_report.enrollment_status` as `enroll_user::Status::Success` directly, never calling `enroll_user::Plan::run` (and therefore never calling `signup_post::request`/`signup_poll::request`), at [5](#0-4) .
4. The signup is reported as successful locally despite bypassing the backend verification/fraud-detection round trip that other signup paths are required to pass, as documented at [3](#0-2) .
