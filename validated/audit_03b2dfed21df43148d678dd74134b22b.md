## Title
Webhook HMAC does not cover the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC only over the raw request body, while the `shop` value that the registry hands to application handlers is taken from an unrelated, unsigned header. An attacker who can obtain one genuine, HMAC-valid webhook delivery (e.g. from their own shop where the app is installed) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the app to process the payload as if it came from a different (victim) tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the signed material [2](#0-1) .

`HmacValidator.validate` verifies exactly that signable string (the body) against the `hmac` header using the app's `api_secret_key` [3](#0-2) , so the check only proves "this body was signed by Shopify with this app's secret" — it says nothing about which shop the body is attributed to.

`Registry.process` relies on this same unverified field to build the data passed to the app's handler:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [4](#0-3) 

This is the same bug class as the external report: the check is performed on one value (`raw_body` / `truePayoutSize`), but a different, related value that is actually acted upon (`shop` / `payoutAfterFee`) is not covered by that check, breaking the binding `verified_bytes == acted_upon_identity`.

### Impact Explanation
Because the app's `client_secret` is shared across every shop that installs the app, any attacker who legitimately installs the app on their own shop receives real Shopify webhook deliveries signed with a valid HMAC. That attacker can capture such a delivery and resend the identical body + `hmac` header to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. The `HmacValidator` still validates successfully (it never looked at the shop header), and `Registry.process` dispatches the payload to the handler tagged with the victim's shop. Depending on the handler (e.g., `app/uninstalled`, GDPR `shop/redact`, `customers/redact`, or any state-mutating webhook), this lets the attacker inject cross-tenant events/data attributed to a shop they do not control — data confusion / cross-tenant impact without ever needing the victim's or the app's access token.

### Likelihood Explanation
Medium: it requires the attacker to operate (or have operated) an install of the target app to obtain one genuine signed webhook body, and to know or guess a topic/body combination whose handler produces meaningful impact when misattributed to another shop. No secret, access token, or privileged account is required — only observation of webhooks delivered to the attacker's own tenant.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed material check, or independently verify that the `shop-domain` header corresponds to a shop with a stored, matching install/session before trusting `request.shop` in `Registry.process`. At minimum, document and enforce that handlers must not trust `WebhookMetadata#shop` unless the app additionally maintains a shop allow-list / session lookup keyed by a value corroborated out-of-band, since the current header is fully attacker-controlled once a valid body+HMAC pair for any tenant is obtained.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`.
2. Shopify delivers a legitimate webhook, e.g. `app/uninstalled`, to the app with headers `x-shopify-hmac-sha256: <valid>`, `x-shopify-shop-domain: attacker.myshopify.com`, and some JSON body.
3. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (it only checks the body) [3](#0-2) .
5. `Registry.process` invokes the app's `app/uninstalled` handler with `shop: "victim.myshopify.com"` [4](#0-3) , causing the app to act (e.g., purge session/data) for a shop the attacker never installed the app on.
