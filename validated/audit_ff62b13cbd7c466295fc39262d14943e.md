Based on the investigation, I found a concrete analog matching the bug class: a field trusted by the application logic that is not covered by the HMAC signature verification.

### Title
Webhook `shop` domain is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity using `Utils::HmacValidator.validate(request)`, but the signable string used for that validation is only the raw request body, never the `shop` domain. The `shop` value handed to webhook handlers is instead read from an ordinary HTTP header that carries no cryptographic binding to the HMAC at all.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`hmac` is likewise computed purely from the `hmac-sha256` header and compared against `HMAC-SHA256(secret, raw_body)`: [2](#0-1) 

`shop` is read from a completely separate, unsigned header: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally forwards `request.shop` to the registered handler as the tenant identifier, with no additional check that the shop belongs to the signed payload: [4](#0-3) 

Because the HMAC only binds `secret + raw_body`, and the `shop-domain` header is excluded from that signable string, any request whose body+HMAC pair is valid for *some* shop (e.g., one the attacker legitimately controls, such as their own store where the app is installed) will also pass HMAC validation with the `x-shopify-shop-domain` header rewritten to any other value. `Registry.process` has no mechanism in this gem to detect that the header shop does not match the shop that actually produced the signed body — the equality `shop authenticated == shop acted upon` is never checked in this gem's own code.

### Impact Explanation
Applications built on `ShopifyAPI::Webhooks::WebhookHandler` typically use `WebhookMetadata#shop` to determine which merchant's tenant data (session/access token) the webhook body should be applied against, since this is the only shop-identifying field this gem exposes from a verified webhook request. Because the header is not bound by the HMAC, an attacker who can produce one legitimate signed webhook (e.g., from their own shop, or via replay of an intercepted webhook) can relabel it to any other shop domain and have this gem report it as authenticated for that other shop. This crosses the tenant boundary the HMAC is meant to enforce, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Medium-High: no access token, `client_secret`, or privileged account is required. An attacker only needs a delivery mechanism for their crafted headers/body to the app's webhook endpoint (something normally satisfied since the endpoint is a public HTTP route) and one legitimate signed payload, which is trivial to obtain by installing the app in their own development store and receiving genuine webhooks for it.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook-id`) inside the HMAC-signed material — or, at minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be independently cross-checked by the host application against the tenant that installed the app before being trusted for tenant-scoped operations. Consider exposing a combined verification helper that binds shop+body together rather than validating the body alone.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against the HMAC, ignoring the shop header.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data as if it originated from the victim shop.
