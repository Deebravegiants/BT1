Audit Report

## Title
Unvalidated hex-length subtraction in `normalizeHex` causes a panic (negative `strings.Repeat` count), enabling unauthenticated DoS of the workflow HTTP trigger gateway - (File: `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`)

## Summary
`validateHexInput` only checks that a `workflowID`/`workflowOwner` string is lowercase, at most `expectedLength` characters, and decodable as hex after an optional `0x` strip — it never requires the `0x` prefix to actually be present. `normalizeHex` then computes `expectedHexLength - len(hexStr)` (where `expectedHexLength = length - 2`) and passes that directly into `strings.Repeat`, which panics if the value is negative — exactly what happens when a caller supplies a full-length hex string with no `0x` prefix.

## Finding Description
`validateHexInput` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:267-283`) bounds `len(input) <= expectedLength` and validates hex-decodability of `strings.TrimPrefix(input, "0x")`, but does not require the `0x` prefix to be present: [1](#0-0) 

`resolveWorkflowID` calls `normalizeHex(workflowID, workflowIDLength)` and `normalizeHex(triggerReq.Params.Workflow.WorkflowOwner, workflowOwnerLength)` on user-controlled input, gated only by `validateWorkflowID`/`validateWorkflowOwner` (which call `validateHexInput`), *before* `authorizeRequest` runs: [2](#0-1) [3](#0-2) 

`normalizeHex` computes the padding length as `expectedHexLength - len(hexStr)` and feeds it straight into `strings.Repeat` without validating that the result is non-negative: [4](#0-3) 

If `workflowID` is exactly 66 lowercase hex characters with no `0x` prefix (e.g. `"1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef"`), it passes `validateHexInput` (`len(input) == 66 <= workflowIDLength(66)`; `hex.DecodeString` succeeds since 66 is even). In `normalizeHex`, `strings.TrimPrefix` is a no-op, so `len(hexStr) == 66`, `expectedHexLength = 66-2 = 64`, and `strings.Repeat("0", 64-66)` = `strings.Repeat("0", -2)`, which panics with `"strings: negative Repeat count"`. The same applies to `workflowOwner` with `workflowOwnerLength = 42`. This occurs before `authorizeRequest` (line 106), so no signature/auth check runs first.

## Impact Explanation
This is a reachable, unauthenticated panic in the request-handling path of the gateway's user-facing HTTP trigger endpoint (`workflows.execute`), triggered before any authorization check. `strings.Repeat` panics rather than returning an error, so unless the call stack invoking `HandleUserTriggerRequest` is wrapped in a `recover()`, this crashes the goroutine (and, if unrecovered up the stack, potentially the whole gateway process), denying service to all users of that gateway node. This maps to a Denial-of-Service impact against the gateway. I was unable to fully trace whether the goroutine that ultimately calls `HandleUserTriggerRequest` (via `http_handler.go`) sits under a panic-recovering wrapper, since the relevant caller code was not available in the index within my remaining tool budget — so the "crashes the whole process" claim is a plausible but unconfirmed upper bound. At minimum, the panic is real and occurs on the request-handling path.

## Likelihood Explanation
High. No authentication, signature, allowlisting, or special privilege is required — a single crafted JSON-RPC `workflows.execute` request with a 66-character (or 42-character) all-lowercase-hex `workflowID`/`workflowOwner` field lacking the `0x` prefix is sufficient, and the request format is exactly what any client of the public gateway endpoint is expected to send.

## Recommendation
- Require the `0x` prefix explicitly in `validateHexInput` (reject inputs missing it) instead of allowing `TrimPrefix` to silently no-op.
- In `normalizeHex`, clamp or validate that `expectedHexLength - len(hexStr)` is non-negative before calling `strings.Repeat`, returning an error on mismatch rather than padding blindly.
- Add unit tests submitting exactly-`workflowIDLength`/`workflowOwnerLength` all-hex strings without the `0x` prefix to confirm the handler now returns a normal JSON-RPC error instead of panicking.

## Proof of Concept
Send a `workflows.execute` JSON-RPC request to the gateway's user endpoint:
```json
{
  "jsonrpc": "2.0",
  "id": "1",
  "method": "workflows.execute",
  "params": {
    "workflow": {
      "workflowID": "1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef"
    },
    "input": {}
  }
}
```
`workflowID` is exactly 66 lowercase hex characters, no `0x` prefix. `validateHexInput` accepts it; `resolveWorkflowID` → `normalizeHex(workflowID, 66)` computes `strings.Repeat("0", 64-66)` and panics with `strings: negative Repeat count`. The equivalent PoC applies to `workflowOwner` at 42 characters (no `0x` prefix) via the code path at lines 354-360.

func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}

// normalizeHex normalizes a hex string by stripping 0x prefix, padding with leading zeros, and adding 0x prefix back
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}
