### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw HTTP body, but the `shop` (tenant identifier) that the handler subsequently trusts is read directly from an HTTP header that is never included in the signed material. This breaks the intended binding `hmac == HMAC(secret, body || shop)` down to `hmac == HMAC(secret, body)`, so the `shop` field the application acts on is not authenticated at all.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight out of request headers with no cryptographic tie to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` only ever calls `verifiable_query.to_signable_string`, so it validates the body bytes exclusively: [3](#0-2) 

`Registry.process` performs exactly this check and then forwards the *unauthenticated* `request.shop` value straight into `WebhookMetadata`, which is the only tenant-identifying field handed to the app's `WebhookHandler#handle`: [4](#0-3) [5](#0-4) 

Because the app's `client_secret` (`api_secret_key`) is shared across **every shop that has installed the app**, any merchant that installs the app can trigger genuine Shopify webhooks for their own store and obtain a correctly signed `(body, hmac)` pair. Since the header carrying `shop-domain` is outside the signed scope, that attacker-controlled merchant can replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

This is exactly the "field acted on but not covered by the HMAC" identity-binding gap called out in scope: the equality that should hold is `hmac == HMAC(secret, body ‖ shop)`, but the gem only enforces `hmac == HMAC(secret, body)`.

### Impact Explanation
Any application built on this gem's `Webhooks::Registry`/`Webhooks::Request` combination that uses `WebhookMetadata#shop` to select which tenant/session/database record to update (the documented and expected usage pattern) can be made to attribute an attacker-crafted, HMAC-valid payload to an arbitrary victim shop. This is a cross-tenant data-integrity/confusion issue: a malicious merchant of the same app can inject fabricated "events" (e.g., fake order/customer/inventory data) that the host application will process as if they originated from a different, victim tenant, without ever needing the victim's credentials. This matches the "cross-tenant access" class of impact in scope, since the gem's own primitive fails to bind the authenticated body to the shop it claims to be from.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate (even free-trial) installer of the same public/multi-tenant app — a standard "unprivileged internet user" position relative to the app's other tenants. No access to `client_secret`, no interception of others' traffic, and no privileged account is required; the attacker uses their own store to legitimately obtain a valid `(body, hmac)` pair and simply replays it with a modified header to the app's public webhook endpoint. This is straightforward and repeatable.

### Recommendation
Bind the tenant identity into the signed material the gem verifies, or otherwise fail closed when header-derived identity cannot be corroborated by the signed payload:
- Include `shop` (and ideally `topic`/`webhook_id`) as part of `to_signable_string` in `lib/shopify_api/webhooks/request.rb` so `HmacValidator` verifies them together with the body, matching how Shopify's `X-Shopify-Shop-Domain` is documented to be trusted only in conjunction with signature verification, or
- Cross-check `request.shop` against an independently authenticated source (e.g., the shop stored on the session/API resource fetched using the webhook body) before dispatching to `WebhookHandler#handle`, rather than trusting the header value implicitly in `Registry.process` (`lib/shopify_api/webhooks/registry.rb`).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com`, receiving genuine Shopify webhooks signed with the app's shared `client_secret`.
2. Attacker triggers an event (e.g., updates an order) causing Shopify to POST a webhook to the app's endpoint with a valid `shopify-hmac-sha256` header computed over the raw body.
3. Attacker intercepts/replays this exact request to the same endpoint but changes the `shopify-shop-domain` header to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the tampered headers; `Utils::HmacValidator.validate` calls `to_signable_string`, which returns only `@raw_body` — unchanged and still valid — so validation succeeds: [6](#0-5) 
5. `Registry.process` constructs `WebhookMetadata.new(... shop: request.shop ...)` using the spoofed header value and calls `handler.handle(data: ...)`, causing the host application to process attacker-controlled data as if it belongs to `victim-shop.myshopify.com`.
