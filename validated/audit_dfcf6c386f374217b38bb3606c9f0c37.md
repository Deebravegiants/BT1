### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives its HMAC-signed content (`to_signable_string`) exclusively from the raw request body, while the `shop-domain` and `topic` values used to route the webhook to per-tenant application logic come from unauthenticated HTTP headers. Since a Shopify app's `client_secret` is shared across *all* shops that install the app, any tenant that legitimately receives one authentic `(body, hmac)` pair for their own store can replay that exact pair to the app's public webhook endpoint while forging the `shop-domain`/`topic` headers to claim it belongs to a different shop and event type, causing `ShopifyAPI::Webhooks::Registry.process` to invoke the handler with attacker-chosen tenant/topic identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are read straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only that the supplied `hmac` matches `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., it authenticates the *body bytes*, never the `shop`/`topic` headers: [3](#0-2) 

`Registry.process` trusts this unauthenticated `shop`/`topic` metadata and hands it directly to the app's handler as the tenant/event identity: [4](#0-3) 

Because the `client_secret` used to compute the HMAC is the same for every shop installing a given app, any tenant (an ordinary, unprivileged merchant who installs the app on their own store) can obtain one authentic `(raw_body, hmac-sha256)` pair simply by triggering a real webhook on their own shop and capturing the delivered POST. That exact pair remains a valid signature no matter what `shop-domain`/`topic` header values are sent with it, because those fields were never part of the signed content. The attacker can then send this replayed body+hmac directly to the app's public webhook endpoint with a different `shop-domain` header (a victim shop) and/or a different `topic` header, and `HmacValidator.validate` will accept it. The equality being broken is: *the shop authenticated by the HMAC* (none — the HMAC authenticates only body bytes) *vs. the shop used to key/route business logic* (`request.shop`, taken from an unauthenticated header).

### Impact Explanation
This crosses a tenant boundary without any credential belonging to the victim: an attacker who is a legitimate (but unprivileged) user of the app on their own shop can inject events that the app's business logic will process as though they originated from an arbitrary other shop, with an attacker-chosen topic. Depending on how the host application uses `WebhookMetadata#shop`/`#topic` (e.g. `shop/redact`, `app/uninstalled`, data-mutation topics), this can trigger cross-tenant side effects, corrupt or delete data belonging to a shop the attacker does not own, or trick app logic gated on webhook topic. This satisfies the "cross-tenant access" criterion for Critical impact.

### Likelihood Explanation
Medium-High: the only prerequisite is installing the target app on any shop (a completely unprivileged, self-service action any Shopify merchant/developer can perform) and capturing one legitimately delivered webhook body+HMAC (trivial via a simple logging endpoint or proxy in front of the developer's own webhook receiver). No knowledge of `api_secret_key`, access tokens, or the victim's credentials is required, and no TLS interception of Shopify's traffic to a third party is needed — only observation of traffic the attacker's own server legitimately receives.

### Recommendation
Include the routing-relevant identity fields (`shop-domain`, `topic`, and ideally `webhook_id`) in the HMAC-signed content, or otherwise bind them to the verified body (e.g., require the app to independently confirm the shop against a known/installed-shop list before trusting webhook metadata). At minimum, `to_signable_string` should not be usable to authenticate a request whose `shop`/`topic` headers can be swapped after the fact; document and enforce that this gem's webhook handlers must not treat `shop`/`topic` as authenticated unless they are covered by, or cross-checked against, some other verified value (e.g. a per-installation secret or matching a webhook ID looked up via the Admin API for that specific shop).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers any webhook topic and captures the raw POST the app vendor's endpoint would receive, including `raw_body` and the `X-Shopify-Hmac-Sha256` header — obtainable simply by pointing the webhook subscription at a server the attacker controls (fully legitimate, unprivileged action).
3. Attacker resends the identical `raw_body`/`hmac` pair to the real app's public webhook endpoint, but sets:
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-topic: <topic of choice>`
4. `Utils::HmacValidator.validate` succeeds because it only recomputes the digest over `raw_body` [5](#0-4) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: <attacker-chosen>, shop: "victim-shop.myshopify.com", body: <attacker-chosen>, ...)` [6](#0-5) 
resulting in the app processing an unauthenticated, forged event as if it came from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
