### Title

Accidental XLM/SAC transfers to the controller are permanently stranded - (File: contracts/controller/src/payments.rs)

### Summary

The controller can hold Stellar Asset Contract balances, including native XLM, but its operational ABI exposes no recovery or sweep entrypoint for unsolicited balances. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description

The contract uses balance-delta accounting specifically to preserve pre-existing controller balances. `refund_controller_balance_delta` snapshots the prior balance and transfers out only the positive increase. [5](#0-4) 

Routed strategies similarly snapshot controller balances, cap refunds to the current operation's unused input, and leave prior balances untouched. [6](#0-5) 

Revenue claims also measure only the controller's balance increase produced by the pool call and forward that measured amount. [7](#0-6) 

Consequently, an unprivileged user can invoke the SAC `transfer` method with the controller as recipient and permanently donate tokens to it; later controller operations deliberately avoid consuming that baseline balance.

### Impact Explanation

Any XLM or other listed SAC token sent directly to the controller becomes unrecoverable through the deployed ABI. This permanently freezes the sender's funds because the controller has no entrypoint that can transfer the unsolicited balance back, while its refund paths explicitly preserve pre-existing balances. [8](#0-7) [4](#0-3) 

### Likelihood Explanation

This requires a user or integrating contract to specify the controller as the token recipient by mistake. The probability is moderate for an address-selection or integration error, while the loss is limited to the amount transferred; this aligns with a Medium-severity stranded-funds issue rather than a protocol-wide theft.

### Recommendation

Add an owner- or governance-authorized recovery entrypoint such as `rescue_token(asset, recipient, amount)` for balances held by the controller. The function should be callable only through the existing governance authority and should emit an event identifying the asset, recipient, and recovered amount.

### Proof of Concept

1. An unprivileged user executes a SAC transfer equivalent to `token.transfer(user, controller, amount)` after obtaining the deployed controller address.
2. The controller's token balance increases by `amount`, but no account position, market cash, revenue, refund, or operation-specific delta is associated with the transfer.
3. Subsequent refund paths continue to preserve the pre-existing controller balance instead of sweeping it. [8](#0-7) [9](#0-8) 
4. No controller ABI method permits the user, account owner, or another unprivileged caller to recover the balance. [1](#0-0) [4](#0-3)

/// Refunds only the controller balance increase since `balance_before`,
/// preserving the pre-existing balance; no-op for a nonpositive delta.
pub(crate) fn refund_controller_balance_delta(
    env: &Env,
    asset: &Address,
    balance_before: i128,
    refund_to: &Address,
) {
    let controller = env.current_contract_address();
    let excess = balance_delta_since(env, asset, &controller, balance_before);
    if excess > 0 {
        token::Client::new(env, asset).transfer(&controller, refund_to, &excess);
    }
