Based on the investigation, the closest legitimate nearcore analog to this "unprivileged callback spams an unbounded array" bug class is in the cross-shard receipt/data-dependency machinery, where **any account can force protocol state to grow on a completely different (victim) account without that growth ever being charged against the account's storage stake**.

### Title
Unprivileged accounts can permanently bloat trie state via postponed receipts and `ReceivedData`/`PendingDataCount` entries that are explicitly excluded from storage-stake accounting - (File: `runtime/runtime/src/lib.rs`, `core/store/src/genesis/state_applier.rs`)

### Summary
Any account can send an `ActionReceipt` to any other (`receiver_id`) account with unmet `input_data_ids`. The runtime unconditionally stores the entire receipt as a `PostponedReceipt`, plus a `PendingDataCount` and one `PostponedReceiptId` link per outstanding dependency, all keyed under the *receiver's* account space in the trie [1](#0-0) . This is the same "unprivileged actor pushes attacker-controlled data into someone else's persistent storage" pattern as the reported `onERC721Received`/`_addNft` issue, except here the target is core protocol trie state rather than a Solidity array.

### Finding Description
`process_action_receipt` writes a `PostponedReceiptId` for every unmet `data_id`, and if any dependency is missing it stores the full receipt via `set_postponed_receipt` together with a `PendingDataCount` counter [1](#0-0) . Crucially, this storage is documented as explicitly **excluded** from the per-account storage-usage/staking computation: the `StorageComputer` used to derive expected per-account storage explicitly notes "we don't charge storage for receipts" [2](#0-1) . The wider receipt-matching model (postponed receipt, `PendingDataCount`, `PostponedReceiptId`, `ReceivedData`) is described in the runtime spec, all keyed by the receiver account [3](#0-2) . Because this state is not counted toward the receiving account's locked storage balance, there is no economic backstop tying the size/duration of this state to the account that actually bears the storage burden — mirroring the ERC-721 report's core defect: the entity that pays for cleanup/storage is not the entity that decided to create the data.

### Impact Explanation
An attacker-controlled account can direct arbitrarily many `ActionReceipt`s (each up to the max receipt size) at any victim account, and because postponed-receipt/pending-data state is not charged against the victim's storage stake, this state can accumulate in the trie for the duration that its data dependency remains unresolved (e.g., during cross-shard congestion/bandwidth throttling windows described in the congestion-control spec [4](#0-3) ), imposing real, uncompensated storage/trie-proof costs on the network and the target account, without a proportionate charge to the attacker beyond the ordinary prepaid send/exec gas fees.

### Likelihood Explanation
Reachable by any account submitting ordinary cross-contract-call transactions (no special privilege, access key type, or validator role required) — this is a standard `FunctionCall`/promise-with-callback pattern available to every user, matching the "reachable from a submitted transaction" bar. However, note that under normal protocol operation every action receipt with `output_data_receivers` is guaranteed to eventually produce a matching `Data` receipt — even on failure ("Any receipt with output dependencies will produce data receipts. Even if it fails.") — which bounds the *duration* of the postponed state to shard processing/congestion delays rather than being permanent; this materially limits severity compared to the original unbounded/permanent ERC-721 array-spam pattern.

### Recommendation
Account for postponed-receipt, `PendingDataCount`, and `ReceivedData` trie entries in the storage-usage computation for the account under which they are stored (or otherwise cap/charge for outstanding postponed state per receiver), so that an account cannot be forced to indefinitely and freely carry state written by receipts it did not initiate a matching response to.

### Proof of Concept
1. Attacker account `A` creates a cross-contract call chain such that an `ActionReceipt` destined for victim `V` carries `input_data_ids` referencing a `data_id` whose corresponding `Data` receipt is delayed by directing traffic through a congested/heavily-buffered shard path (per `ReceiptSink`/`try_forward` admission logic [5](#0-4) ).
2. On arrival, `process_action_receipt` stores the full receipt as `PostponedReceipt` plus `PendingDataCount`/`PostponedReceiptId` entries keyed to `V`'s account, none of which count toward `V`'s storage stake [6](#0-5) [2](#0-1) .
3. Repeating this at scale (many receipts, each sized up to the protocol max receipt size) grows global trie state attributable to `V` without a corresponding storage-stake charge to `V` or a fully compensating cost to `A`.

## Processing ActionReceipt

For each incoming [`ActionReceipt`](#actionreceipt) runtime checks whether we have all the [`DataReceipt`s](#datareceipt) (defined as [`ActionsReceipt.input_data_ids`](#input_data_ids)) required for execution. If all the required [`DataReceipt`s](#datareceipt) are already in the [storage](#received-datareceipt), runtime can apply this `ActionReceipt` immediately. Otherwise we save this receipt as a [Postponed ActionReceipt](#postponed-actionreceipt). Also we save [Pending DataReceipts Count](#pending-datareceipt-count) and [a link from pending `DataReceipt` to the `Postponed ActionReceipt`](#pending-datareceipt-for-postponed-actionreceipt). Now runtime will wait for all the missing `DataReceipt`s to apply the `Postponed ActionReceipt`.

#### Postponed ActionReceipt

A Receipt which runtime stores until all the designated [`DataReceipt`s](#datareceipt) arrive.

- **`key`** = `account_id`,`receipt_id`
- **`value`** = `[u8]`

_Where `account_id` is [`Receipt.receiver_id`](#receiver_id), `receipt_id` is [`Receipt.receipt_id`](#receipt_id) and value is a serialized [`Receipt`](#receipt-1) (which type must be [ActionReceipt](#actionreceipt))._

#### Pending DataReceipt Count

A counter which counts pending [`DataReceipt`s](#datareceipt) for a [Postponed Receipt](#postponed-actionreceipt) initially set to the length of missing [`input_data_ids`](#input_data_ids) of the incoming `ActionReceipt`. It's decrementing with every new received [`DataReceipt`](#datareceipt):

- **`key`** = `account_id`,`receipt_id`
- **`value`** = `u32`

_Where `account_id` is AccountId, `receipt_id` is CryptoHash and value is an integer._

#### Pending DataReceipt for Postponed ActionReceipt

We index each pending `DataReceipt` so when a new [`DataReceipt`](#datareceipt) arrives we connect it to the [Postponed Receipt](#postponed-actionreceipt) it belongs to.

- **`key`** = `account_id`,`data_id`
- **`value`** = `receipt_id`

### 3. Data dependencies: postponed receipts and promise results

An action receipt carries `input_data_ids` (`receipt.rs:605`) that must all be
satisfied before it runs. In `process_action_receipt` (`lib.rs:1529`) the runtime
counts how many of those ids are *not* yet in state (`has_received_data`,
`lib.rs:1546`); for each missing one it records a `PostponedReceiptId` link
(`lib.rs:1550`). If `pending_data_count == 0` it executes immediately
(`lib.rs:1561`); otherwise it stores a `PendingDataCount` and the receipt itself as a
**postponed receipt** (`lib.rs:1581`, `set_postponed_receipt`).

When a `Data` receipt arrives (`process_receipt`, `lib.rs:1322`) the runtime writes
`ReceivedData` (`lib.rs:1325`), then, if a `PostponedReceiptId` link exists, decrements
`PendingDataCount`; when it reaches 1→0 it removes the postponed receipt and executes
it (`lib.rs:1357-1391`). On execution, an action receipt's outputs become `Data`
receipts routed to each `output_data_receivers` entry (`lib.rs:1059`), so a
cross-contract call is: caller creates a callback action receipt with an
`input_data_id`, records itself as an `output_data_receiver` on the callee's receipt
(`receipt_manager.rs:111`, `create_action_receipt`), and the callee's return value is
turned into the `Data` receipt that resolves the dependency.

### 4. Forwarding vs buffering (congestion + bandwidth admission)

Every outgoing receipt goes through `ReceiptSink::forward_or_buffer_receipt`
(`congestion_control.rs:162` → `:292`). It computes the receipt's receiver shard,
size, and congestion gas, then calls `try_forward` (`:403`):

1. If `size > max_receipt_size`, size is clamped to `max_receipt_size` for the limit
   comparison (bug workaround for oversized receipts, issue #12606, `:417`).
2. The receiver's `OutgoingLimit` is looked up; a missing entry defaults to
   `{ gas: Gas::MAX, size: 0 }` (`:439`) — since the bandwidth scheduler, a shard may
   send **zero** bytes on a link with no grant.
3. Under `ClampOutgoingGasAdmission` (PV 85) the *admission* gas is clamped to
   `allowed_shard_outgoing_gas` (`:443`), so a single very-expensive receipt cannot be
   blocked forever by the gas limit; pre-85 the full receipt gas is used.
4. Forward iff `forward_limit.gas >= admission_gas && forward_limit.size >= size`
   (`:451`); then the receipt is pushed to `outgoing_receipts` and the limit is
   decremented by the *actual* gas and size (`:453`). Otherwise it is returned
   `NotForwarded` and `buffer_receipt` (`:466`) pushes it onto the outgoing buffer for
   that shard, growing `own_congestion_info` by its size and buffered gas (`:486`).
