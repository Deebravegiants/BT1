Based on my investigation, I found a concrete analog: the gateway-side Vault handler builds an internal `activeRequests` map keyed only on the raw JSON-RPC request ID (owner-prefixed), and the user-supplied portion of that ID (`req.ID`) is attacker-controlled and only constrained by length (≤200 chars) — it is **not** validated for uniqueness of the `RequestIDSeparator` (`"::"`) sequence within it. This mirrors the reported "orderId needs to be unique" bug class: a user-controlled ID that is later used as a routing/matching key without guaranteeing it is unique per intended entity, causing cross-request confusion.

### Title
Gateway Vault request ID collision via attacker-controlled `RequestIDSeparator` injection causes cross-request response confusion - (File: core/capabilities/vault/gateway_vault_request_processor.go)

### Summary
The gateway Vault handler builds the internal owner-prefixed request ID by concatenating `authorizedOwner + "::" + originalRequestID`, where `originalRequestID` is the raw, attacker-supplied JSON-RPC `req.ID` [1](#0-0) . The only validation performed on the user-supplied ID is a non-empty and length (≤200 chars) check [2](#0-1) ; there is no restriction preventing the user-supplied ID from itself containing the `"::"` separator sequence used to demarcate the owner prefix.

### Finding Description
`RequestIDSeparator` is defined as the literal string `"::"` [3](#0-2) . After authorization, `authorizeAndStamp` computes `prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID` and overwrites `req.ID` with this value, which then becomes the key used everywhere downstream (active-request tracking map, node dispatch envelope, response matching) [4](#0-3) .

Because `originalRequestID` is fully attacker controlled (an arbitrary string up to 200 characters, with no character-set restriction), a caller can craft a request ID that itself embeds `"::"` — e.g. a user submits `req.ID = "victimOwner::realRequestId"`. If this user is authorized as owner `attackerOwner`, the gateway computes `prefixedRequestID = "attackerOwner::victimOwner::realRequestId"`. This value is used as the map key in `h.newActiveRequest`/`h.activeRequests[req.ID]` [5](#0-4) .

Separately, on the node side, `stripPrefixedVaultRequestID` uses `strings.Cut(requestID, vaulttypes.RequestIDSeparator)`, which cuts on the **first** occurrence of `"::"` [6](#0-5) . Likewise, the gateway's response-stripping logic (`sendSuccessResponse`/`errorResponse`) uses `strings.Index(resp.ID, vaulttypes.RequestIDSeparator)` and strips everything up to and including the *first* `"::"` before returning the ID to the user [7](#0-6) [8](#0-7) . Because the split logic only ever removes the first prefix occurrence, an attacker who embeds an additional `"::"` in their own supplied ID can cause the ID that is echoed back to the user (and the ID string used for internal bookkeping) to not correspond 1:1 with the true `owner::userID` structure that the rest of the code assumes, breaking the implicit invariant that `"::"` uniquely separates exactly two components.

This directly parallels the "orderId needs to be unique" issue: the ID that the off-chain/backend service (here, the gateway's `activeRequests` map, its logging tags such as `incomingOwner` derived from `strings.Index(req.ID, vaulttypes.RequestIDSeparator)` [9](#0-8) , and the request routing between gateway and nodes) relies on the request ID/structure being unambiguous and unique, but a user-controlled component of that ID is unconstrained and can violate the uniqueness/structure assumption.

### Impact Explanation
While the current code paths (`h.activeRequests[req.ID]`, per-owner scoped rate limiters/ciphertext limiters keyed by `authResult.AuthorizedOwner()`, not by the raw ID) mostly still isolate the actual security-relevant checks (authorization is done on `authorizedOwner`, not by parsing the embedded separator), the ambiguous ID structure creates confusing/log-misleading `incomingOwner` values and could confuse aggregation/response matching or downstream systems/log tooling that assume `owner::userID` is unambiguous. The primary risk is operational: incorrect owner attribution in logs (`incomingOwner`) and potential unexpected collisions in the `activeRequests` map across different authorized owners if their `authorizedOwner` value differs but their combined string happens to collide (unlikely since `authorizedOwner` is prepended first, making full-string collision hard) — the more concrete issue is the log/observability confusion from `incomingOwner` parsing, not a full cross-tenant secret leak.

### Likelihood Explanation
Any authorized caller (including a legitimate, low-privilege workflow owner) can trivially supply a request ID containing `"::"` since there is no character-set validation on the JSON-RPC request `ID` field besides a length cap [2](#0-1) . This makes triggering the ambiguous-ID condition trivial and requires no special privilege beyond normal Vault gateway access.

### Recommendation
Reject (or hex/base64-escape) any user-supplied request ID that contains the `RequestIDSeparator` (`"::"`) before it is used to build the owner-prefixed ID, or switch to a length-prefixed / non-ambiguous encoding scheme (e.g., store the user ID's length before the separator) so that `strings.Cut`/`strings.Index` based parsing cannot be confused by attacker-supplied delimiter characters. Validate this in `HandleJSONRPCUserMessage` (`core/services/gateway/handlers/vault/handler.go`) alongside the existing empty/length checks.

### Proof of Concept
1. An authorized user (owner `attackerOwner`) sends a Vault gateway JSON-RPC request with `req.ID = "victimOwner::realId"` and a valid `vault.secrets.list` (or other gateway secrets) method payload.
2. `authorizeAndStamp` computes `incomingOwner` by taking everything before the first `"::"` — here, `"victimOwner"` — which is logged as `incomingOwner` even though the actual authorized/authenticated caller is `attackerOwner` [10](#0-9) .
3. After authorization succeeds for `attackerOwner`, the final prefixed ID becomes `"attackerOwner::victimOwner::realId"`.
4. When the gateway later strips the response ID via `strings.Index(resp.ID, vaulttypes.RequestIDSeparator)` and slices from `index+2`, it only removes the `"attackerOwner::"` prefix, returning `"victimOwner::realId"` to the user as the final "user-facing" request ID — an ID string that does not match what the client originally sent (`"victimOwner::realId"` was the full original ID, so in this specific case it matches, but for deeper nesting or for the node-side `stripPrefixedVaultRequestID` cut, additional `"::"` occurrences produce mismatched/ambiguous parsing results depending on which side performs the cut and how many separators are present).

**Note on confidence**: I was not able to fully trace every consumer of `incomingOwner` (e.g., whether it feeds into any authorization decision besides logging) within the available index; the citations above show it is currently only used for logging in `authorizeAndStamp`, which limits the impact to observability/log-integrity confusion rather than a direct authentication/fund-movement bypass. I could not confirm from the indexed code whether any other component treats the first-`"::"`-split `incomingOwner` as authoritative for anything beyond logging — if it is, the severity would be higher (an actual owner-impersonation/log-forgery issue). Given the ask-only-mode and no plan requested, I have not produced an implementation plan; let me know if you'd like one drafted for the recommended fix.

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

func stripPrefixedVaultRequestID(requestID string) (originalRequestID, prefixedOwner string) {

}

func (h *handler) sendSuccessResponse(ctx context.Context, l logger.Logger, ar *activeRequest, resp *jsonrpc.Response[json.RawMessage]) error {
	// Strip the owner prefix from the response ID before sending it back to the user
	// This ensures compliance with JSONRPC 2.0 spec, which requires response id to match request id
	index := strings.Index(resp.ID, vaulttypes.RequestIDSeparator)
	if index != -1 {
		resp.ID = resp.ID[index+2:]
	}
