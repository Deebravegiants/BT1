### Title
Webhook Tenant Identity (`shop`) Not Bound to HMAC Signature Enables Cross-Tenant Spoofing - (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw request body, then trusts the `shop` field taken from an HTTP header that is never covered by that signature. Any party who can obtain one validly-signed webhook (e.g. from their own installed/dev shop, using the app's shared `client_secret`-derived HMAC secret exactly as Shopify itself would compute it) can replay that same signed body while swapping the `shopify-shop-domain` / `x-shopify-shop-domain` header to claim it originated from a different (victim) shop, since the header is outside the signed data.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

but the `shop` accessor used for tenant identification is read from an unsigned header: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` using this unauthenticated `shop` value to route the webhook payload to the handler as the acting tenant: [3](#0-2) 

The equality the code implicitly assumes — `hmac_signed_bytes == identity_bytes_acted_on` — does not hold: the HMAC covers only `@raw_body`, while the tenant-binding value (`shop`) is parsed from a header outside the MAC. Any request whose body+HMAC pair is valid (trivially obtainable by any unprivileged user who installs the app on their own store and receives a legitimately Shopify-signed webhook for that store) can be re-delivered to the app's webhook endpoint with an arbitrary `shop` header, and `Registry.process` will accept it and dispatch it under that spoofed shop identity, because nothing in this gem's `process` path re-derives or checks `shop` against the signed content.

### Impact Explanation
This breaks tenant isolation for webhook processing: a webhook payload cryptographically proven only to be "some validly signed body from *a* shop of this app" is treated by the library as authoritative for "*this specific* shop." Any host application that keys shop-scoped side effects (e.g., updating order/inventory records, invalidating sessions, writing entitlements) off `WebhookMetadata#shop` as provided by this gem inherits cross-tenant data injection/cross-tenant access, matching the High/Critical class of cross-tenant access via a broken identity binding.

### Likelihood Explanation
No privileged credentials, TLS interception, or access to the app's `client_secret` are required — an attacker only needs to be able to install the app (or otherwise trigger a legitimately Shopify-delivered webhook) on any shop they control, capture the resulting signed body, and re-POST it to the app's public webhook endpoint with a modified shop header. `Registry.process`'s HMAC check does not detect this because it never covers the header.

### Recommendation
- Short term: Bind `shop` (and other identity-relevant fields such as `topic`/`webhook_id` if used for authorization decisions) into the HMAC-signed payload verification, or independently corroborate the header-derived `shop` against Shopify's out-of-band delivery guarantees (e.g., mTLS/IP allowlisting at the transport layer) before trusting it in `Registry.process`.
- Long term: Treat any field consumed by `WebhookMetadata` that is not part of `to_signable_string` as untrusted, and document/enforce that host applications must not use unsigned headers for tenant-scoping decisions; add invariant tests asserting that mutating any unsigned header while keeping the HMAC valid does not change the resulting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop `attacker.myshopify.com`; Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app's endpoint with body `B` and header `shopify-hmac-sha256: HMAC(secret, B)` per `Webhooks::Request#hmac`/`#to_signable_string` (`lib/shopify_api/webhooks/request.rb:11-13,35-38`).
2. Attacker captures `B` and its valid HMAC.
3. Attacker POSTs the identical body `B` and HMAC to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`), which only checks `B` against the HMAC and succeeds.
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` using the spoofed `victim-shop.myshopify.com` value (`lib/shopify_api/webhooks/registry.rb:198-199`), and the host application's handler processes attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.
