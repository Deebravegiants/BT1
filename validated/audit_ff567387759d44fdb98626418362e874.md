### Title
IntentGatewayV2 (Tron) `instance()` fails open to `address(this)` for unregistered chains, letting a forged cross-chain message drain escrowed funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of `IntentGatewayV2` resolves the trusted peer address for an incoming ISMP message with a fail-open default: any state machine that has no explicit entry in `_instances` is treated as if the peer address were this contract's own address, rather than being rejected. This is the same bug class as the Jet Protocol incident cited in the report: a missing/weak "does this account really belong to the expected counterpart" check lets an attacker-controlled message be accepted as authentic, and that authentication gates `withdraw()`, which pays out escrowed user/solver funds.

### Finding Description
`authenticate()` is the only gate standing between an incoming `RedeemEscrow`/`RefundEscrow` message and `withdraw()`, which releases escrowed tokens to an attacker-chosen beneficiary: [1](#0-0) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

and in `onAccept`: [2](#0-1) 

For any `request.source` that has never been registered via `NewDeployment` (i.e. `_instances[keccak256(source)] == 0`), `instance()` silently returns `address(this)` instead of reverting. `authenticate` then only requires `request.from == address(this)` for that message to be accepted as coming from a "known instance" — even though no instance was ever actually configured for that source chain.

This is a materially weaker check than the hardened EVM implementation, which fails closed: [3](#0-2) 
```solidity
function _instance(bytes calldata stateMachineId) internal view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
```

`withdraw()` itself performs no additional ownership check on the escrow being drained beyond "is `_orders[commitment][token]` non-zero" — it trusts the caller-supplied `WithdrawalRequest.beneficiary` completely once `authenticate` has passed: [4](#0-3) 

So the entire security of escrowed funds for any order whose `source`/peer state machine is not explicitly registered in `_instances` collapses to whether `request.from` happens to equal this contract's own address — a condition an attacker can engineer if they can get a genuinely consensus-proven ISMP message dispatched from *some* chain Hyperbridge tracks, from an address equal to the gateway's own deployment address (e.g. via CREATE2 with a deployer/salt they control on any chain where they can be first to claim that address, or via any chain Hyperbridge adds consensus support for before the gateway team registers/deploys the peer there). This mirrors the Jet Protocol root cause: the code conflates "no explicit record found" with "trust the default/self account," instead of refusing the action, allowing withdrawal against/through an account that was never actually validated as the intended counterpart.

### Impact Explanation
A successful forgery lets an attacker drive `withdraw()` with an arbitrary `WithdrawalRequest{commitment, tokens, beneficiary}` for any order whose escrow commitment they can guess or observe (commitments are public, derivable from `Order` structs emitted on `placeOrder`), redirecting escrowed input tokens (and any accumulated transaction fees) to an attacker-chosen `beneficiary`. This is a direct theft of escrowed user/solver funds — the same class of impact identified in the Jet Protocol incident (arbitrary-account withdrawal), scoped here to the intents/escrow settlement path.

### Likelihood Explanation
Exploitation requires the attacker to get a real, consensus-verified ISMP message accepted by this Tron `IntentGatewayV2` from a state machine that is not in `_instances`, with `from` equal to this contract's own address. This is non-trivial (it is not reachable by simply calling a public function), but it does not require any privileged role — it only requires the existence of an unregistered-but-Hyperbridge-supported chain and control of an address collision on that chain, which is a meaningfully lower bar than compromising governance, a validator set, or a key. Given the fail-closed EVM sibling contract exists specifically to prevent this class of mistake, the fail-open Tron logic looks like an unintentional regression rather than a deliberate design choice, and any operational gap (a peer chain that is supported by Hyperbridge consensus but not yet registered via `NewDeployment` on this Tron deployment) turns this into an immediately exploitable window.

### Recommendation
Make `instance()`/`authenticate()` fail closed on the Tron implementation, matching `IntentsBase._instance()`: revert (e.g. `UnknownInstance`) when `_instances[keccak256(stateMachineId)] == 0`, instead of defaulting to `address(this)`. If same-address-everywhere is a deliberate design assumption for this deployment topology, it must be enforced by requiring an explicit self-registration entry in `_instances` for every peer chain (including "this chain") rather than an implicit fallback, so that an unregistered chain can never be treated as authenticated.

### Proof of Concept
Conceptual PoC (illustrates the code-level flaw; full weaponization requires an address collision on a chain Hyperbridge tracks but the gateway team has not registered):
1. Attacker identifies a legitimate order on the Tron `IntentGatewayV2` with commitment `C` and non-zero `_orders[C][token]`.
2. Attacker arranges for a genuine ISMP `PostRequest` to be delivered to this gateway with `source` = any state machine id `S` such that `_instances[keccak256(S)] == address(0)`, and `from` = `abi.encodePacked(address(thisGateway))` (achievable if the attacker controls/deploys a contract at that exact address on chain `S`, e.g. via CREATE2 on an as-yet-unclaimed chain, or if chain `S` is added to Hyperbridge consensus before the gateway registers a peer there).
3. Body = `bytes1(RequestKind.RedeemEscrow) || abi.encode(WithdrawalRequest({commitment: C, tokens: <victim's escrowed tokens>, beneficiary: <attacker address>}))`.
4. `onAccept` → `authenticate(request)` calls `instance(S)`, which returns `address(this)` (fail-open default) — equal to `module` — so authentication passes.
5. `withdraw()` executes, transferring the victim order's escrowed tokens to the attacker's `beneficiary`, confirmed by `_orders[C][token] -= amount` succeeding and tokens leaving the contract. [1](#0-0) [2](#0-1) [4](#0-3)
