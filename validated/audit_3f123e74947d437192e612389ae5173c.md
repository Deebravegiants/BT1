Based on my investigation, I've confirmed the root cause. Here's my analysis:

### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-verifying the raw request body, then hands the handler a `shop` value taken from the unauthenticated `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header. Because that header is never part of the signed material, any party who can obtain one valid `(body, hmac)` pair — for example a merchant who has installed the app on their own shop and thus legitimately receives real webhooks — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header value. The handler will treat the payload as having originated from the spoofed shop, breaking the tenant-attribution identity binding.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Yet the same class exposes `shop`, `topic`, `api_version`, and `webhook_id` derived purely from headers, with no cryptographic tie to the body: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` uses this validator as the sole authentication gate, then constructs `WebhookMetadata` using `request.shop` — the unauthenticated header value — and dispatches it to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop attributed to this webhook == shop whose secret produced the HMAC`. Instead, the library only enforces `bytes verified (body) == bytes parsed (body)`, while the `shop` field that the handler acts on is taken from a header entirely outside the signed scope. This is the “field acted on but not covered by the HMAC” bug class.

### Impact Explanation
Any user who has installed the app for at least one shop (a normal, unprivileged onboarding action, not requiring the app's `client_secret` or another tenant's access token) can capture a legitimately-signed `(raw_body, hmac)` pair from their own webhook deliveries and resend it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a different, victim shop. `Registry.process` will accept it as authentic (HMAC matches) and invoke the app's handler with `data.shop` set to the victim shop. If the host application (as documented, see `docs/usage/webhooks.md`) uses `WebhookMetadata#shop` to look up/update per-tenant records, this allows cross-tenant data manipulation or information disclosure — writing or triggering tenant-scoped side effects (e.g. `orders/create`, `app/uninstalled`, GDPR topics) attributed to a shop the attacker does not own. This matches the Critical “cross-tenant access” impact category.

### Likelihood Explanation
Likelihood is high for any app that exposes an HTTP webhook endpoint per the documented `ShopifyAPI::Webhooks::Registry.process` flow. Obtaining a valid signed `(body, hmac)` pair only requires the attacker to install the app on any shop they control (a trivial, low-privilege action) and observe one webhook delivery; replaying it with a different `shop-domain` header requires no cryptographic capability, only a basic HTTP client. The bug is entirely within this gem's `process`/`HmacValidator`/`Request` code path, not a host-application misuse.

### Recommendation
Bind the shop identity to the signed payload, or otherwise verify it independently before trusting it:
- Include `shop-domain` (and ideally `topic`, `webhook-id`) in the HMAC-signed material, e.g., by having `to_signable_string` combine header values with the body in a canonical, delimited form, and require callers to compute HMAC over that same string; or
- After authenticating the raw body, independently validate that `request.shop` corresponds to a shop with an active, known session/installation before invoking the handler, rather than trusting the header outright; or
- At minimum, document loudly (and enforce in `Registry.process`) that `shop` must be cross-checked by the caller against their own tenant store before being used for any tenant-scoped action.

### Proof of Concept
```ruby
require "shopify_api"
require "openssl"
require "base64"

ShopifyAPI::Context.setup(
  api_key: "key", api_secret_key: "secret", host: "https://example.com",
  scope: "read_products", is_embedded: true, api_version: "2024-01",
)

# Attacker installs the app on their own shop "attacker.myshopify.com" and
# captures ONE legitimate webhook delivery it receives, e.g. for orders/create:
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# The attacker now replays the exact same body + hmac to the app's webhook
# endpoint, but swaps the shop-domain header to a victim shop they don't own:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- unauthenticated, attacker-controlled
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation succeeds because it only checks raw_body, not shop-domain:
ShopifyAPI::Webhooks::Registry.process(request)
# => the registered handler for "orders/create" is invoked with
#    data.shop == "victim-shop.myshopify.com", even though the HMAC
#    was produced using the attacker's own shop's legitimate webhook delivery.
```
