Confirmed root cause. The webhook HMAC only signs the raw request body via `to_signable_string` returning `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC and then dispatches the handler using the unverified `request.shop` and `request.topic` values [3](#0-2) .

### Title
Webhook HMAC does not bind `shop-domain`/`topic` headers, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop`, `topic`, `api_version`, and `webhook_id` values that the handler consumes are taken straight from HTTP headers that are never included in the signed material, so any party who can obtain one validly-signed `(raw_body, hmac)` pair for the app can replay it with arbitrary `shop-domain`/`topic` headers and have the library treat it as an authentic webhook for a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, signable_string)` and compares it to the `hmac` field [4](#0-3) . Because `api_secret_key` is the app's single shared secret (not per-shop), it is identical for every shop that has the app installed. `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read from headers that are entirely outside this signed string:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [5](#0-4) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then immediately uses `request.shop` and `request.topic` to route and construct `WebhookMetadata` passed to the handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [3](#0-2) 

The identity binding this breaks is: `hmac(request) valid` should imply `request.shop == shop that produced raw_body` **and** `request.topic == topic that produced raw_body`. Instead, `hmac(request) valid` only proves `raw_body` was signed by *some* installation of the app — the shop/topic headers are attacker-controlled and unauthenticated. This is the same class of bug as the referenced report: a downstream action (`handler.handle` / webhook routing) is performed using fields (`shop`, `topic`) that are not covered by the integrity check that gated the action (the HMAC check), exactly analogous to `swapTo` performing NFT transfers without the `allValidNFTs`/`afterRedeemHook` checks that bind eligibility.

### Impact Explanation
Any merchant (or trial-store operator) who installs the app — a low-privilege, unauthenticated-relative-to-other-tenants actor — legitimately receives webhooks signed with the app's shared secret for their own store. They can capture any such `(raw_body, hmac)` pair and POST it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a victim shop and/or a forged `x-shopify-topic` header. The library will report the HMAC as valid and hand the handler a `WebhookMetadata` claiming to originate from the victim shop/topic. If the host application trusts `data.shop`/`data.topic` (as the gem's own documentation and test suite assume it will) to look up sessions, update per-shop state, or process compliance topics such as `customers/redact`/`shop/redact`, this enables cross-tenant data manipulation or spoofed mandatory-compliance webhooks — a cross-tenant access impact.

### Likelihood Explanation
Requires only that the attacker be able to install the target application on their own (or any) Shopify store to receive genuinely-signed webhook traffic — no access to `api_secret_key`, access tokens, or privileged accounts is needed. Capturing one's own inbound webhook body/HMAC and replaying it with modified headers to the app's public webhook endpoint is straightforward and repeatable.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signed material (or otherwise independently verify them, e.g. via Shopify's webhook signing conventions), so that a valid HMAC binds the raw body to the specific shop/topic it was issued for, mirroring how `AuthQuery#to_signable_string` binds `shop`/`state`/etc. into the OAuth HMAC computation [6](#0-5) .

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends the app a legitimate webhook, e.g. body `{"id":1}` with headers `x-shopify-hmac-sha256: <valid_for_attacker_shop>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but substitutes `x-shopify-shop-domain: victim.myshopify.com` and/or `x-shopify-topic: customers/redact`.
4. `HmacValidator.validate` recomputes the HMAC over `raw_body` only, which still matches, so `Registry.process` proceeds and invokes the handler with `shop: "victim.myshopify.com"`, `topic: "customers/redact"` — data the app will treat as authentic for the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
