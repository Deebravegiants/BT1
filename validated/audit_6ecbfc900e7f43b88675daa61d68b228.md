This confirms the vulnerability: the webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are all read directly from HTTP headers via `shopify_header` in `lib/shopify_api/webhooks/request.rb:20-33`, while the HMAC signature (verified in `lib/shopify_api/utils/hmac_validator.rb:13-31`) only covers `to_signable_string`, which returns just `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`). ### Title
Webhook shop/topic identity spoofing via unsigned headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
Shopify webhook authenticity is verified by HMAC-signing only the raw request body [1](#0-0) , computed and compared in `HmacValidator.validate`/`validate_signature` [2](#0-1) . However, the tenant-identifying fields `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers, which are never included in the signed payload [3](#0-2) .

### Finding Description
`Registry.process` only checks `Utils::HmacValidator.validate(request)` before trusting `request.shop`, `request.topic`, and `request.webhook_id` to construct `WebhookMetadata` and invoke the registered handler [4](#0-3) . Since the HMAC only binds the raw body bytes, an identity binding is broken: `shop header claimed by request` ≠ `shop bytes actually covered by HMAC`. Any party capable of sending a POST to the app's webhook endpoint with a **previously-observed valid `(raw_body, hmac)` pair** (e.g., a legitimate webhook the attacker's own shop received/triggered, since all shops share the same app-level `client_secret`/HMAC key) can freely rewrite the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers while keeping the same body+HMAC, and the signature will still validate. The handler then processes the payload attributing it to an attacker-chosen `shop` and `topic`, even though those values were never authenticated.

### Impact Explanation
Because the Shopify webhook HMAC secret (`api_secret_key`) is shared across every shop that installs the app, a merchant/attacker who legitimately triggers one webhook for their own shop obtains a valid `(body, hmac)` pair. They can replay that request to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop, causing the app's handler logic (tenant lookup, data storage keyed by `shop`, `customers/data_request`/`shop/redact` mandatory topics, etc.) to act as if the event came from a different, arbitrary tenant. This can lead to cross-tenant data corruption, spoofed mandatory compliance webhooks, or triggering handler logic under an impersonated shop identity — matching a cross-tenant access impact.

### Likelihood Explanation
Moderate: it requires the attacker to control or observe at least one legitimate `(raw_body, hmac)` pair from a webhook delivered to the app (achievable by any merchant who installs the app on their own store and triggers any webhook event), plus the ability to replay/forge the HTTP request to the app's public webhook endpoint with modified headers — no possession of `api_secret_key` is needed.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the signed payload verification — e.g., include them in `to_signable_string`, or independently verify that the `shop` header matches an expected/allow-listed value for the session/tenant context being processed — instead of trusting them purely from unauthenticated headers alongside a body-only HMAC.

### Proof of Concept
1. App owner installs their test/attacker shop `attacker-shop.myshopify.com` and triggers any webhook topic (e.g., `orders/create`); Shopify POSTs to the app with body `B` and header `x-shopify-hmac-sha256: H` (valid since `H = HMAC(secret, B)`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this raw request.
3. Attacker replays the exact same body `B` and `hmac` header `H` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares it to `H` — validation succeeds because the body was not altered [5](#0-4) .
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to process/store the event under the victim shop's tenant identity [6](#0-5) .
