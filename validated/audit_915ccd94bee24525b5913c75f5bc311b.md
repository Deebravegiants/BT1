## Title
Unbounded computation in `pallet_ismp::handle_unsigned` charged a fixed static weight, enabling a weight-underestimation DoS - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet_ismp::Pallet::handle_unsigned` is a free, permissionless, unsigned extrinsic that accepts an arbitrary-length `Vec<Message>` and iterates over every message to verify proofs and dispatch to router callbacks, yet its declared `#[pallet::weight]` is a fixed constant (`300_000_000`) that does not scale with the number or complexity of messages submitted. This mirrors the reported "unbounded gas consumption from nested loops" bug class: a function whose real cost grows with an attacker/relayer-controlled input size but whose accounted cost is static.

### Finding Description
`handle_unsigned` is declared with a fixed weight function that ignores the actual size of the input: [1](#0-0) 

```
#[pallet::weight(weight())]
#[pallet::call_index(0)]
#[frame_support::transactional]
pub fn handle_unsigned(origin: OriginFor<T>, messages: Vec<Message>) -> DispatchResultWithPostInfo {
    ensure_none(origin)?;
    Self::execute(messages.clone())?;
    Ok(().into())
}
```

and the weight function itself: [2](#0-1) 

`weight()` returns a hard-coded `Weight::from_parts(300_000_000, 0)` regardless of `messages.len()`, the number of `PostRequest`/`GetResponse` leaves inside each `RequestMessage`/`ResponseMessage`, the number of storage keys per `GetRequest`, or the MMR/trie proof sizes carried in each message.

`Self::execute` then iterates over the entire `messages` vector, calling `handle_incoming_message` (proof verification + router dispatch) for every entry: [3](#0-2) 

Each `handle_incoming_message` call in turn loops through nested collections — e.g. `RequestMessage::requests`, `ResponseMessage::requests` (with each `GetRequest` itself carrying an unbounded `keys: Vec<Vec<u8>>`), or `PostRequestTimeoutMessage::timeouts` — performing MMR/trie membership or non-membership proof verification plus a router callback per element: [4](#0-3) [5](#0-4) 

Because `handle_unsigned` is dispatched with `ensure_none(origin)` (unsigned, free of transaction fees) and comment in the pallet explicitly says "This allows users execute ISMP datagrams for free. Use with caution": [6](#0-5) 

the same `Self::execute(messages.clone())` full-batch work is additionally re-run once per node during `validate_unsigned` — before the extrinsic even enters a block — meaning the unbounded cost is paid twice per validating node (mempool gossip validation and block execution) for the same submission, without the FRAME weight/fee system ever knowing the batch is large. `T::FeeHandler::on_executed` only computes a post-hoc weight-derived fee (used for optional treasury transfer accounting), it does not gate acceptance or bound the pre-execution/validation cost: [7](#0-6) 

### Impact Explanation
Substrate's block-authoring and weight-accounting model assumes a call's declared weight approximates its real execution cost so the runtime can bound how many extrinsics fit in a block and avoid exceeding the block's time/PoV budget. Because `handle_unsigned`'s declared weight is a fixed constant unrelated to `messages.len()` or nested array sizes, a single valid submission carrying a very large batch of messages (many `PostRequest`s, `GetResponse`s with many keys, or many timeout leaves, each requiring real proof verification against MMR/trie roots) can consume execution time far beyond the 300M-weight budget the runtime accounted for when including it. This can push actual block execution time past the block's real time limit, threatening block production liveness and the reliability of the message-delivery route (a route becoming unable to deliver messages predictably is one of the accepted impact classes), and it is exploitable by any unprivileged party since the call is permissionless, unsigned, and fee-free.

### Likelihood Explanation
The extrinsic is reachable from a single unsigned transaction submitted by anyone; the only gate is that messages carry valid proofs, which is checked by `validate_unsigned`, itself performed by fully re-executing the same unbounded batch (`Self::execute(messages.clone())`) at mempool-validation time — so the cost is unavoidable for any validating node the transaction reaches, valid or not, up until failure. An attacker who controls a small number of already-finalized/valid PostRequest or GetResponse batches from a real (even low-value) source chain can replay/aggregate many of them, or dispatch many trivial GET requests each with a large `keys` array (bounded only by extrinsic/block length limits, not by weight), to build one oversized-but-valid batch.

### Recommendation
Compute `handle_unsigned`'s weight dynamically from the input, e.g., a base cost plus a per-message and per-nested-element multiplier (number of `PostRequest`/`GetResponse` entries, number of keys per `GetRequest`, proof size), similar to how `WeightFeeHandler` already computes weight-based fees post-execution — but apply the estimate *before* dispatch via `#[pallet::weight(fn(messages))]` so oversized batches are rejected by `CheckWeight`/block-fullness logic rather than executed at a flat, underestimated cost. Additionally consider capping the maximum number of messages and the maximum keys-per-`GetRequest` accepted per `handle_unsigned` call, and avoid doing the full unbounded `Self::execute` inside `validate_unsigned` (e.g., cheaper structural/format checks only) to prevent double-paying the unbounded cost during pool validation.

### Proof of Concept
1. An attacker (no special privileges) crafts (or gathers already-valid) `Message::Response(ResponseMessage { requests, .. })` where `requests` contains many `GetRequest`s, each with a large `keys: Vec<Vec<u8>>` array, along with a legitimate state proof large enough to satisfy `verify_state_proof` for all of them.
2. The attacker submits `pallet_ismp::Call::handle_unsigned { messages: vec![huge_response_message, ... repeated many times ...] }` as an unsigned extrinsic.
3. Every validating node executes `validate_unsigned`, which calls `Self::execute(messages.clone())` — this loops over every request/key performing full state-proof verification, taking execution time proportional to the batch size, not to the flat `300_000_000` weight the call is registered with.
4. If it validates, the same unbounded `Self::execute` runs again during block execution, again charged only the flat weight — allowing a maliciously (or just carelessly) large but valid batch to blow past the weight budget the block-authoring logic assumed when deciding how many extrinsics to include, risking excess block execution time and degraded delivery reliability for the state machine.
