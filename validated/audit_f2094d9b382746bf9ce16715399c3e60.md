**Analysis:**

The custody-relevant object address derivation paths (`create_object_address`, `create_user_derived_object_address`, `create_guid_object_address`, and the AUID-based `create_object`) all funnel into `create_object_internal`, which explicitly guards against address collisions:

```
fun create_object_internal(...) {
    assert!(!exists<ObjectCore>(object), error::already_exists(EOBJECT_EXISTS));
    ...
}
``` [1](#0-0) 

This means any attempt to create a new object at an address that already holds an `ObjectCore` (e.g. an existing multisig- or resource-account-owned object) will abort with `EOBJECT_EXISTS`, exactly matching the outcome the question's own proof idea expects ("attempt to create an object at an already-occupied address and assert abort"). The invariant is already enforced by design, not broken by it.

Additionally, each derivation scheme uses a distinct domain-separation tag appended before hashing — `OBJECT_FROM_SEED_ADDRESS_SCHEME = 0xFE`, `OBJECT_DERIVED_SCHEME = 0xFC`, `OBJECT_FROM_GUID_ADDRESS_SCHEME = 0xFD`, `DERIVE_AUID_ADDRESS_SCHEME = 0xFB` — specifically to prevent cross-scheme collisions between object addresses, resource-account addresses, and authentication keys. [2](#0-1) 

For an attacker to actually collide two *within-scheme* addresses (same creator/seed derivation producing the same address as another existing custodied object), they would need to find a SHA3-256 preimage collision — computationally infeasible and not something reachable via any unprivileged transaction input. The native implementation (`create_user_derived_object_address_impl`) is a deterministic, memoized function of `(source, derive_from)` with no attacker-controlled entropy that bypasses the hash. [3](#0-2) [4](#0-3) 

The framework's own spec (`object.spec.move`) formally encodes this same abort condition (`aborts_if exists<ObjectCore>(obj_addr)`) for every creation path, confirming the collision-guard is a verified invariant, not an oversight. [5](#0-4) 

Since the abort check already closes the path described (per the Review Path step 4: "Reject if authority checks or ownership refs already close the path"), and no unprivileged input can force a real SHA3-256 collision, there is no exploitable custody-boundary crossing here.
