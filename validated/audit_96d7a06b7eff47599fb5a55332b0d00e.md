**Why this doesn't qualify:**

1. **No unprivileged entrypoint.** `WriteSetDb::prune` at [1](#0-0)  is only invoked by `WriteSetPruner::prune`, which is a `DBSubPruner` driven by the node's internal `LedgerPruner` background thread, itself gated by `prune_window` configuration (`PrunerManager::get_prune_window`) — not by any transaction, package, view, authenticator, API, bytecode, or proof input from an unprivileged user. The review bounds require the path to originate from such an entrypoint.

2. **No race between deletion and progress tracking on the actual call path.** `WriteSetPruner::prune` builds `begin`/`end` strictly from its own tracked `current_progress` and `target_version`, and writes the `WriteSetSchema` deletions and the `DbMetadataKey::WriteSetPrunerProgress` update into the *same* `SchemaBatch`, committed atomically via a single `write_schemas` call: [2](#0-1) . There is no code path where an external caller can pass an arbitrary `begin`/`end` into `WriteSetDb::prune` independent of the tracked progress; `begin` is always the pruner's own last-recorded progress.

3. **No custody impact even if the write set were prematurely pruned.** Write sets stored via `WriteSetSchema` are historical execution output records used for auditing/replay/API queries (`get_write_set`, `get_write_sets`), not the live custody state. Actual balances and ownership live in the state/resource tree, which is governed by a separate pruner (state-merkle/state-kv) with its own progress tracking. Deleting a stale write-set record does not change any current holder's balance, ownership, freeze/mint/burn authority, or ability to move funds — it only affects historical auditability, which the review bounds explicitly exclude ("event-level mismatch", non-custody, non-controller-changing impacts).

Since there is no unprivileged-triggerable path and no resulting change to who can own, move, mint, burn, freeze, upgrade, or recover value, this does not meet the Custody Impact Gate.
