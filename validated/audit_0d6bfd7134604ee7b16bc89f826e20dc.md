### Title
Attacker hijacks victim's two-step (cooldown) withdrawal from a shared external protocol position because Emporium's stateless ops attribute all state to a single shared caller identity - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction()` executes "stateless" operations (`op.invokeWallet == false`) as direct calls from the Emporium contract itself, so any external protocol receiving them (e.g. a staking contract) sees `msg.sender == address(Emporium)` regardless of which end-user's proof triggered the call. Any state the external protocol keys off that caller (e.g. `pendingWithdrawals[msg.sender]` set by `requestWithdraw()`) is therefore shared across every Hinkal user, letting an unrelated attacker later trigger `withdraw()` themselves and sweep the unlocked principal into a UTXO under their own stealth address via `handleOut`.

### Finding Description
Broken equality: `principal_released_to == account that originally called requestWithdraw() (victim)`; actual: `principal_released_to == whichever unprivileged account's runAction call next invokes withdraw() on the same external contract, because both calls share the same on-chain caller identity (Emporium)`.

In `runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`), stateless ops are executed as:
```
(success, err) = op.endpoint.call{value: op.value}(op.callData);
``` [1](#0-0) 
This call originates from `address(this)` (the single, protocol-wide `EmporiumUpgradeable` proxy), not from any per-user identity. `onlyAllowedRecipient` only checks that the caller is the `Hinkal` contract [2](#0-1) ; it does nothing to bind a two-step external protocol interaction (request → cooldown → withdraw) to the same underlying UTXO-proof owner.

Exploit flow:
1. Victim submits a `transact()` with an Emporium external action whose `EmporiumStack.ops` contains a stateless op calling `stakingContract.requestWithdraw()`. Inside the staking contract this records state against `msg.sender == Emporium`.
2. Cooldown elapses.
3. Attacker (any unprivileged account, using their own valid proof/UTXOs) submits their own `transact()` with an Emporium external action whose stack includes a stateless op calling `stakingContract.withdraw()`, and whose `circomData.erc20TokenAddresses` includes the now-released token.
4. Because the staking contract's pending-withdraw state is keyed to `address(Emporium)` (shared identity), `withdraw()` succeeds and sends the victim's principal to `address(this)` (Emporium), increasing its ERC20 balance.
5. Back in `runAction`, `balanceChange = balancesAfter[i] - balancesBefore[i]` captures this increase [3](#0-2) . The attacker sets `deltaAmountChanges[i] == 0` for that token (no real deposit), so the full amount flows through unmodified.
6. `handleOut` transfers `balanceChange` back to `msg.sender` (the `Hinkal` contract) and mints a `UTXO` keyed to the attacker's own `circomData.stealthAddressStructure` [4](#0-3) .
7. `Hinkal.transact()`'s balance-diff/slippage checks compare `balanceDif` against `circomData.amountChanges[i] + utxoAmount` using only the attacker's own proof-controlled values [5](#0-4) ; nothing here validates whose funds actually produced the balance increase, so the attacker's own proof self-consistently "explains" the stolen amount as their own new private UTXO.

None of the existing guards (`onlyAllowedRecipient`, `verifyWallet`'s EIP-712 signature check for `invokeWallet` ops, `performHinkalChecks`, nullifier/root checks, `BalanceChangeShouldBePositive`) bind stateless-op side effects to the specific account whose proof originated the first leg of a multi-step interaction — they only ensure proof/UTXO integrity for the caller's own transaction, not cross-transaction identity continuity on the external protocol.

### Impact Explanation
The attacker permanently steals the victim's unlocked staking principal by capturing it into their own private Hinkal balance. This is direct theft of a victim's shielded/locked funds — Critical severity. It is repeatable against any external staking/lock protocol integrated through Emporium's stateless-call path that uses `msg.sender`-keyed multi-step withdrawal state.

### Likelihood Explanation
Preconditions: an external protocol integrated via Emporium must implement a caller-address-keyed, multi-transaction lock/cooldown pattern (common for staking/vesting/vault withdrawals). The attacker needs no special role — just the ability to submit their own valid Hinkal proof and craft `EmporiumStack.ops` targeting the same endpoint/function. Cost is a single transaction after cooldown elapses; the race is trivial to win since anyone (including the attacker) can watch for the cooldown expiry and front-run the victim's own follow-up call.

### Recommendation
Do not treat `address(Emporium)` (or any singleton) as a valid caller identity for multi-step, stateful external protocol interactions in "stateless" mode. Either: (a) require all multi-step/cooldown-based external interactions to go through the stateful `IHinkalWallet` per-user proxy path (`invokeWallet == true`) so each user has a distinct on-chain identity, and disallow stateless ops for any endpoint known to hold per-caller withdrawal state; or (b) require the released funds' recipient/beneficiary to be explicitly bound and checked against the original requester in a way enforced on-chain (e.g., require withdraw calls to specify and verify a beneficiary matching the request), which is protocol-specific and cannot be generically enforced by Emporium — hence integrations with lock/cooldown protocols should mandate per-user `HinkalWallet` deployment for the entire request→withdraw lifecycle rather than direct stateless calls.

### Proof of Concept
Foundry fork test plan:
1. Deploy `MockLockedStaking` with `deposit()`, `requestWithdraw()` (records `pendingAmount[msg.sender]`, `unlockTime[msg.sender] = block.timestamp + COOLDOWN`), and `withdraw()` (requires `block.timestamp >= unlockTime[msg.sender]`, transfers `pendingAmount[msg.sender]` to `msg.sender`, clears state).
2. Deploy `Hinkal`, `EmporiumUpgradeable` (as `_allowedRecipients` in `runAction`), register Emporium as external action.
3. Victim deposits token X into Hinkal, then calls `transact()` with an Emporium `EmporiumStack` containing a stateless op: `{endpoint: staking, invokeWallet:false, callData: abi.encodeCall(staking.requestWithdraw, (amount))}`, moving `amount` of X from Emporium's UTXO balance into the staking position (via `deltaAmountChanges[i] < 0` pre-transfer in `_externalTransact`).
4. Assert `staking.pendingAmount(address(Emporium)) == amount` and `staking.unlockTime(address(Emporium)) > block.timestamp`.
5. `vm.warp(block.timestamp + COOLDOWN + 1)`.
6. Attacker (different EOA, own fresh UTXOs, own proof/circomData with `erc20TokenAddresses = [X]`, `amountChanges = [0]`) calls `transact()` with Emporium stack containing stateless op `{endpoint: staking, invokeWallet:false, callData: abi.encodeCall(staking.withdraw, ())}`.
7. Assert equality violated: capture `EmporiumUpgradeable` X-balance before/after attacker's tx equals `amount` (the victim's principal), and assert a new UTXO/commitment event is emitted for the attacker's `stealthAddressStructure` with `amount == victim's amount`, while `staking.pendingAmount(address(Emporium))` is now zero — proving the victim can never redeem it and the attacker captured it in one transaction.
