### Title
Webhook HMAC verifies only the raw body while `shop`, `topic`, `webhook_id`, and `api_version` are taken from unauthenticated headers, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/utils/hmac_validator.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts a `Request` as authentic once `Utils::HmacValidator.validate` succeeds, but the HMAC only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that are subsequently used to authorize dispatch and identify the tenant are read straight from HTTP headers that are never included in the signed bytes, so any bit of that metadata can be swapped by an attacker without invalidating the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
`HmacValidator.validate_signature` computes the signature over that same signable string and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` then trusts `request.topic` and `request.shop` — both parsed from unauthenticated headers — to pick the handler and to build the `WebhookMetadata` that is handed to application code: [3](#0-2) 
and those accessors are simple header reads with no cryptographic binding to the body: [4](#0-3) 

Because the HMAC is computed with the app's single, shared `client_secret` over the body alone, any (body, hmac) pair that Shopify legitimately produced for **any** shop and **any** topic on the app (including one the attacker legitimately installed the app on) will still validate after the attacker swaps `x-shopify-shop-domain` and/or `x-shopify-topic` to arbitrary values. `Utils::HmacValidator.validate` returns `true` unconditionally in that case because it never inspects `shop` or `topic`: [5](#0-4) 

This is the same class of break as the external report: a value that drives execution/routing (`processLidoOracleReport`'s callback identity there; here, `shop`/`topic`) is not covered by the check that is supposed to authenticate the whole message (`processCallback` existence check there; `Utils::HmacValidator.validate` here). The equality that should hold — HMAC-authenticated-shop == shop-used-for-tenant-routing — is broken because the shop is never part of the signed material.

### Impact Explanation
An attacker who has installed the target app on their own Shopify store (a normal, unprivileged action) can capture a genuine `(raw_body, hmac)` pair Shopify sent for their own shop/topic, then replay it directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop and/or the `x-shopify-topic` header changed to any topic registered by the app (e.g. `app/uninstall`, `orders/create`, `customers/data_request`). `Registry.process` will accept it as authentic and invoke the handler with attacker-chosen `shop`/`topic`/`body`, causing the host application to act on a victim tenant using attacker-supplied data — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Any developer/attacker can register the app on a shop they control at no cost, obtain a validly signed webhook, and replay it with modified headers to the app's public webhook receiver endpoint. No credentials, access tokens, or `client_secret` knowledge are required — only the ability to receive one legitimate webhook from Shopify for their own installation.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the signed material verified by `HmacValidator`, or otherwise cryptographically tie the header values to the specific delivery (e.g., verify the `shop` against a value looked up via `webhook_id` from Shopify's API, or reject any header set inconsistent with values Shopify itself would send for a legitimately-registered subscription). At minimum, document that `shop`/`topic` in `WebhookMetadata` are unauthenticated and must not be used for tenant-authorization decisions without an additional integrity check.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic to receive `raw_body` and `x-shopify-hmac-sha256` genuinely signed by the app's `client_secret`.
2. POST that exact `raw_body` to the app's webhook endpoint, replacing headers:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic: app/uninstall` (or any other registered topic)
   - keep `x-shopify-hmac-sha256` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which passes because it only checks `raw_body` against the shared secret: [6](#0-5) 
4. The registered handler for `app/uninstall` (or the chosen topic) executes with `shop: "victim.myshopify.com"`, letting the attacker trigger tenant-scoped side effects for a shop they do not control.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
