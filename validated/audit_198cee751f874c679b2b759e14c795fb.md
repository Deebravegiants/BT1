### Title
Webhook `shop-domain` header is unauthenticated and not covered by HMAC verification, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs (and `HmacValidator` verifies) only the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values are parsed straight from HTTP headers and are never part of the HMAC-covered data, yet `Registry.process` immediately treats `request.shop` as the authenticated tenant identity when dispatching to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controllable HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`HmacValidator.validate` only ever hashes `verifiable_query.to_signable_string` (i.e., the raw body) against the configured secret: [3](#0-2) 

`Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` and, on success, unconditionally trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` passed to the app-supplied handler: [4](#0-3) 

This breaks the identity binding that should hold:
`shop_authenticated_by_HMAC == shop_the_handler_acts_on`

In reality, only `raw_body_authenticated_by_HMAC == raw_body`. The `shop` (tenant key) is completely decoupled from what the HMAC actually covers. This matches the bug class in the reference report: a value/field that is *acted upon* (here, the tenant/shop the handler processes data for) is not included in the integrity-checked bytes (the HMAC signable string), so validating the HMAC gives no guarantee about that field's authenticity.

### Impact Explanation
Because the `x-shopify-shop-domain` (and topic/webhook-id) headers are outside the HMAC's scope, any party capable of capturing one legitimately-signed webhook body+HMAC pair for their *own* shop (trivial — any developer can install the app on their own free/dev store and generate events with attacker-influenced body content, e.g. product/customer field values) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shop-domain` header for an arbitrary victim shop. `Registry.process` will validate successfully (the body/secret pair is legitimate) and dispatch a `WebhookMetadata` claiming to be from the victim shop, with attacker-influenced body content, to the app's registered handler. For mandatory compliance topics (`shop/redact`, `customers/redact`, `customers/data_request`) or state-changing topics (e.g., `app/uninstalled`), this allows one shop to inject webhook events attributed to a completely different shop — a cross-tenant identity/data confusion. This satisfies the "cross-tenant access" criterion for a Critical finding.

### Likelihood Explanation
Requires only: (1) installing the target app on any shop the attacker controls (unprivileged, self-service), and (2) the ability to send an arbitrary HTTP POST with attacker-chosen headers to the app's public webhook endpoint (which is by design internet-reachable). No access token, `client_secret`, or privileged account is needed — the attacker never needs to know the shared secret, only to replay a body/HMAC pair they legitimately received for their own tenant while forging the header that identifies which tenant it belongs to.

### Recommendation
Bind the tenant/topic identity into the HMAC-covered signable string, or otherwise cryptographically verify that the `shop-domain` header matches the shop embedded in the webhook body/metadata registered with Shopify for that specific delivery (Shopify's webhook payloads generally include shop identifying fields that can be cross-checked against the header before trusting it). At minimum, `Registry.process` should not treat `request.shop`/`request.topic` as authenticated merely because the raw body's HMAC validated; the library should document/enforce that consumers must not rely on the header-derived `shop` for authorization decisions without additional verification against the signed body content.

### Proof of Concept
1. Attacker installs the target Shopify app on shop `attacker-shop.myshopify.com` (self-service, no special privilege).
2. Attacker triggers a webhook event on their own shop whose JSON body content they control (e.g., renaming a product/customer field to embed a desired payload), causing Shopify to POST to the app's webhook endpoint with a valid `x-shopify-hmac-sha256` computed over that exact `raw_body` using the app's shared secret (attacker never sees the secret, only observes the resulting request).
3. Attacker captures this `(raw_body, hmac)` pair and re-sends it to the same app endpoint, changing only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com` (and optionally the topic header, since it's also unsigned).
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — this matches, so validation succeeds: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, even though nothing about this request was ever validated against `victim-shop`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
