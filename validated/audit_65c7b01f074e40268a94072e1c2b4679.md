Audit Report

## Title
Nil pointer dereference (node crash / DoS) on `MethodPublicKeyGet` gateway messages missing `params` - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` dispatches `vaulttypes.MethodPublicKeyGet` requests directly to `handlePublicKeyGet` without validating that `req.Params` is non-nil, unlike the other vault methods which are routed through `GatewayVaultRequestProcessor.ProcessRequest` and its per-method validators that explicitly guard against nil `Params`. `handlePublicKeyGet` unconditionally dereferences `*req.Params`, causing a nil-pointer-dereference panic when a JSON-RPC request for this method omits the `params` field.

## Finding Description
`HandleGatewayMessage` [1](#0-0)  routes `MethodSecretsCreate`/`MethodSecretsUpdate`/`MethodSecretsDelete`/`MethodSecretsList` through `h.requestProcessor.ProcessRequest`, whose internal validators (`processCreateSecretsRequest`, `processDeleteSecretsRequest`, `processListSecretIdentifiersRequest`) all check `if req.Params == nil` before any unmarshalling, confirming that `req.Params` is a nilable pointer type (`*json.RawMessage`) [2](#0-1) [3](#0-2) [4](#0-3) . In contrast, the `MethodPublicKeyGet` branch calls `h.handlePublicKeyGet(ctx, gatewayID, req)` directly with no equivalent guard [5](#0-4) , and `handlePublicKeyGet` unconditionally dereferences the pointer at `json.Unmarshal(*req.Params, r)` [6](#0-5) . If `req.Params` is nil (i.e., the JSON-RPC request omits the `params` field), this dereference panics.

This panic path is reachable through the connector's `readLoop`, which parses the incoming message and calls `handler.HandleGatewayMessage` for any recognized method name with no panic recovery wrapping the call [7](#0-6) . Because there is no `recover()` in this call chain, a panic here is not caught locally and will propagate up the goroutine stack; in Go, an unrecovered panic terminates the entire process unless some ancestor frame in that goroutine's call stack has a deferred recover, which is not present in `readLoop`, `HandleGatewayMessage`, or `handlePublicKeyGet`.

## Impact Explanation
This is an availability/DoS issue: an unrecovered panic on the goroutine processing Gateway messages will crash the node process, disrupting the Vault capability (and potentially the whole node) for any DON member that processes the malformed message. This maps to a legitimate in-scope Chainlink impact category (node availability / DoS via crafted gateway request).

## Likelihood Explanation
Likelihood is high. Triggering this requires only sending a JSON-RPC 2.0 request with `method` set to `vaulttypes.MethodPublicKeyGet`'s value and the `params` field entirely omitted, targeted at a Vault-enabled DON through the Gateway. No authentication, valid vault owner, JWT, or privileged role is needed, because the `MethodPublicKeyGet` branch bypasses the `ProcessRequest` pipeline (and the authorization/validation logic within it) entirely.

## Recommendation
Add a nil check for `req.Params` in `handlePublicKeyGet` before dereferencing, mirroring the pattern already used in `processCreateSecretsRequest`/`processDeleteSecretsRequest`/`processListSecretIdentifiersRequest`, e.g., return a `UserMessageParseError`/`InvalidParamsError` response if `req.Params == nil`. More broadly, consider adding panic recovery in `readLoop`/`HandleGatewayMessage` as defense-in-depth so a single malformed message cannot crash the whole node.

## Proof of Concept
1. Send a JSON-RPC request to a Vault-enabled DON's Gateway: `{"jsonrpc":"2.0","id":"1","method":"vault.publicKeyGet"}` with no `params` key.
2. The Gateway forwards this to the node's `GatewayConnector.readLoop`, which unmarshals it into `jsonrpc.Request[json.RawMessage]`, leaving `Params` as a nil pointer, and dispatches it to `GatewayHandler.HandleGatewayMessage`.
3. `HandleGatewayMessage` matches `case vaulttypes.MethodPublicKeyGet` and calls `handlePublicKeyGet` directly.
4. `json.Unmarshal(*req.Params, r)` dereferences the nil pointer, panicking with "invalid memory address or nil pointer dereference," which is unrecovered and crashes the node process.

A Go unit test calling `GatewayHandler.HandleGatewayMessage` with a `&jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` would directly reproduce the panic.

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
