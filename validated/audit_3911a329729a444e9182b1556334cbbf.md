## Title
GetResponse delivery pays relayer fee without clearing `_requestCommitments`, permitting the same request to later be paid again via `dispatchTimeOut` — (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(GetResponse)` follows checks-effects-interactions for the response receipt (it stores `_responseReceipts[commitment]` and calls the destination module before any fee transfer), which closes the direct reentrancy path analogous to the SFPM bug. However, unlike `dispatchTimeOut`, it never deletes `_requestCommitments[commitment]` after paying the relayer fee [1](#0-0) . `dispatchTimeOut(GetRequestTimeout, ...)` independently trusts `_requestCommitments` as its sole "known request" check before refunding the same fee amount to `meta.sender` and only then deletes it [2](#0-1) .

### Finding Description
This is a stale-state/double-payment class bug, structurally analogous to the reported issue in that a state variable (`removedLiquidity` there, `_requestCommitments` here) is trusted for downstream accounting but is not correctly invalidated after the first state-changing consumption of it, and the money-relevant path is reached through low-level `.call` to untrusted app code (`IApp.onGetResponse`), similar to the `onERC1155Received` callback used in the original PoC.

Concretely:
1. `dispatch(DispatchGet...)`/outgoing request path stores `_requestCommitments[commitment] = FeeMetadata({sender, fee})`.
2. When the response is delivered via `HandlerV2.handleGetResponses` → `EvmHost.dispatchIncoming(GetResponse, relayer)`, the host stores the `_responseReceipts[commitment]` receipt, invokes `IApp.onGetResponse` on the destination app (an arbitrary, potentially malicious contract), and on success pays `fee = _requestCommitments[commitment].fee` to the relayer [3](#0-2) . Crucially, `_requestCommitments[commitment]` is **not deleted**.
3. Because `_requestCommitments[commitment]` still holds a non-zero `sender`, the same commitment is still considered a "known request" by `HandlerV2.handleGetRequestTimeouts`, whose only proof obligation is a state-trie **non-membership** proof for the response receipt key on Hyperbridge's own state, not on the EvmHost [4](#0-3) . If Hyperbridge's own bookkeeping for this Get request diverges from EvmHost's local `_responseReceipts` state (e.g., through relayer-controlled ordering/timing of proof submission across two different verification systems — a state root here on the destination host vs. a separate non-membership proof from the coprocessor chain), an already-answered request can still pass the timeout's non-membership check and reach `EvmHost.dispatchTimeOut(GetRequestTimeout, meta, commitment)`.
4. `dispatchTimeOut` for `GetRequestTimeout` deletes `_requestCommitments[commitment]` and, on a successful `onGetTimeout` callback, refunds `meta.fee` to `meta.sender` [5](#0-4) . Because `meta` was never cleared or nulled by step 2, this fee has now been paid out twice for the same underlying request: once to the relayer on response delivery, once to the original sender on timeout.

### Impact Explanation
Duplicate fee disbursement for a single Get request drains the fee-token balance held by `EvmHost` beyond what protocol economics intend, i.e., an unbacked payout / permanent loss of protocol-held funds. This is a Medium-severity accounting error in the exact spirit of the referenced report: state left in an inconsistent condition (not underflowed here, but not cleared) is later consumed by a second code path that assumes it is authoritative, producing an incorrect (here, double) transfer of value gated by `IERC20.safeTransfer`.

### Likelihood Explanation
Exploiting this requires a race/mismatch between when EvmHost records a `_responseReceipts` entry and when Hyperbridge's coprocessor state (used for the non-membership proof in `handleGetRequestTimeouts`) reflects that same response — a scenario dependent on the two verification systems (local state vs. cross-chain proof) staying in lockstep, an assumption this design implicitly relies on. Given that `_requestCommitments` is not defensively cleared on the response path, any relayer or app-level bug that lets a stale non-membership proof be constructed for an already-answered request converts directly into a double payout. This is a plausible operational condition rather than a purely theoretical one, warranting Medium severity per the same "hypothetical attack path with external requirement" standard applied to the referenced finding.

### Recommendation
Delete `_requestCommitments[commitment]` in `dispatchIncoming(GetResponse)` immediately after (or as part of) storing the response receipt, before or alongside the relayer fee payment, mirroring the CEI pattern already used for `_requestReceipts` in `dispatchIncoming(PostRequest)` and for `_requestCommitments` in `dispatchTimeOut`. This ensures a response and a timeout can never both consume the same fee metadata for one request.

### Proof of Concept
Conceptual sequence (cannot be fully constructed without the coprocessor-side non-membership proof generation, which lives outside the EVM contracts under review):
1. App dispatches a `GetRequest`; `EvmHost` records `_requestCommitments[c] = {sender: payer, fee: F}`.
2. Relayer delivers the corresponding `GetResponse` through `HandlerV2.handleGetResponses` → `EvmHost.dispatchIncoming(GetResponse)`; `_responseReceipts[c]` is set, `onGetResponse` succeeds, and fee `F` is paid to the relayer. `_requestCommitments[c]` remains unchanged.
3. Separately, a `GetRequestTimeout` for the same request `c` is submitted with a state-trie non-membership proof (against some earlier/inconsistent Hyperbridge height) that satisfies `handleGetRequestTimeouts`'s check [6](#0-5) .
4. `EvmHost.dispatchTimeOut(GetRequestTimeout, meta, c)` executes, deletes `_requestCommitments[c]`, and refunds fee `F` again to `payer`.

Because I cannot fully replay Hyperbridge's coprocessor-side commitment lifecycle for `_responseReceipts`/non-membership state from the code indexed here, I could not confirm whether the coprocessor enforces an invariant that would make step 3 impossible after step 2; this should be verified against `modules/ismp/core/src/handlers/timeout.rs` and the corresponding response-receipt storage-write path on the pallet side before treating this as fully proven.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
