### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) attribution is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only. The `shop-domain`, `topic`, `api-version`, and `webhook-id` values that `ShopifyAPI::Webhooks::Registry.process` hands to the application's webhook handler are read from unauthenticated HTTP headers that are never covered by the HMAC signature check. This breaks the intended binding of "the tenant (`shop`) that the signed payload originated from" == "the tenant the handler is told the payload belongs to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled straight from headers, with no cryptographic tie to the body or to each other: [2](#0-1) 

`Registry.process` verifies the HMAC over the `Request` object (i.e., over the body only) and then constructs `WebhookMetadata` using `request.shop` and `request.topic`, both of which come from the header, not from anything the HMAC covers: [3](#0-2) 

`Utils::HmacValidator.validate` confirms that `verifiable_query.to_signable_string` (the raw body) matches `verifiable_query.hmac`, and never inspects `shop`, `topic`, or any other header: [4](#0-3) 

Because the body and HMAC pair is valid for *any* header combination, an unprivileged internet user who legitimately controls one shop (e.g. installs the target app on their own development/test store) can capture a real, validly-signed webhook delivery (body + `x-shopify-hmac-sha256`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`) with a victim shop's domain. `HmacValidator.validate` will still pass because it only checks the (unchanged) body against the (unchanged) signature computed with the app's shared secret. The application's webhook handler will then process the payload as though it came from the victim's tenant.

This is the "field acted on but not covered by the HMAC" pattern: `shop` is the value the handler uses to attribute/scope the webhook to a tenant, but it is not part of the signed content, so `shop (used by handler)` != `shop (implicitly authenticated by the HMAC)`.

### Impact Explanation
This allows cross-tenant data confusion: an attacker-controlled shop's webhook payload (e.g., an `orders/create` or `app/uninstalled` body they fully control by acting on their own store) can be attributed to an arbitrary victim `shop` domain of the attacker's choosing. Depending on how the host application uses `WebhookMetadata#shop` (e.g., looking up/creating tenant records, writing data keyed by shop, revoking access, mutating billing state), this can let an attacker inject or corrupt data into another merchant's tenant scope, or trigger tenant-scoped side effects (such as uninstall/deauthorization handling) against a shop they do not own. This falls into the "cross-tenant access" Critical impact category, since it crosses the tenant boundary using only capabilities of an ordinary shop owner (or any HTTP client capable of replaying a captured webhook).

### Likelihood Explanation
Exploitation requires: (1) obtaining one genuine, validly-signed webhook body from Shopify — trivial for anyone who installs the app on a shop they control, or who intercepts/records a delivery, and (2) the ability to POST arbitrary headers to the app's public webhook endpoint, which is inherent to any HTTP client. No access token, `client_secret`, or privileged access is required, only the app's public webhook URL and a legitimately obtained payload/signature pair. This is a realistic, low-effort exploitation path for an unprivileged internet user.

### Recommendation
- Bind `shop`, `topic`, `api-version`, and `webhook-id` cryptographically into the signed content that `HmacValidator` verifies (e.g., include the relevant headers as part of the canonical string that is HMAC'd, or require the consuming application to independently corroborate the header-derived `shop` against a value that is otherwise authenticated, such as a shop the app has an active session/webhook subscription for).
- At minimum, document and enforce that host applications must independently verify that the `shop` in `WebhookMetadata` corresponds to a shop with an active, expected installation/subscription before trusting it, since the gem itself does not bind `shop` to the HMAC.
- Add regression tests asserting that a captured valid `(body, hmac)` pair fails or is rejected when replayed with a different `shop-domain`/`topic` header, to make this binding explicit and testable going forward (mirroring the API3 report's recommendation to cover pre/postconditions with explicit unit tests).

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own store "attacker.myshopify.com"
#    and receives a genuine webhook delivery from Shopify:
raw_body = '{"id": 123, "note": "attacker-controlled payload"}'
valid_hmac_from_shopify = "<base64 HMAC-SHA256 computed by Shopify using the app's real client_secret>"

# 2. Attacker replays the exact same body + hmac, but swaps the shop-domain header
#    to a victim shop the attacker does not control:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_from_shopify,   # unchanged, still matches raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. Registry.process only checks the HMAC over raw_body, which still validates:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create",
#      shop: "victim-shop.myshopify.com", body: ..., ...))
# The application's handler now believes this payload legitimately belongs to
# "victim-shop.myshopify.com", even though it was never signed as such.
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
