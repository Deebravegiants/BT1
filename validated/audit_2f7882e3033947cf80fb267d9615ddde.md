### Title
Tron `IntentGatewayV2.onAccept` omits the relayer-authorization gate that the EVM `ExtrinsicIntents.onAccept` enforces on the same message-processing path - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The EVM intents gateway (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`) enforces a relayer-restriction gate, `_checkRelayer`, as the very first action inside `onAccept` before any incoming cross-chain message is decoded or acted upon. The Tron variant of the same gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements an `onAccept` that is functionally identical in every other respect (same `RequestKind` enum, same `RedeemEscrow`/`RefundEscrow`/`NewDeployment`/`UpdateParams`/`SweepDust` dispatch), but never calls an equivalent check — there is no `_relayer` state, no `setRelayer`, and no gate at all in this file. This is the same bug class as CVE-2023-45140: an access-control mechanism (there, group-based JIT MFA; here, the per-relayer authorization gate) is enforced on one code path but silently skipped on a functionally-equivalent sibling path that handles the same class of privileged action.

### Finding Description
`ExtrinsicIntents.onAccept` gates every incoming post request behind `_checkRelayer(incoming.relayer)`: [1](#0-0) 

`_checkRelayer` is documented as the defense that keeps a forged/compromised handler from injecting arbitrary relayer addresses into gateway deliveries: [2](#0-1) 

The design intent is spelled out in the repository's own decision log: the app-level relayer gate exists specifically because `EvmHost.dispatchIncoming` trusts whatever relayer address the configured `handler` reports, and that handler is itself a governance-replaceable parameter; if a consensus forgery ever swaps in a malicious handler, the app-level relayer gate is the last line of defense that keeps deliveries restricted to the designated relayer:


The Tron deployment of the same gateway (`IntentGatewayV2.sol` under `evm/tron/contracts/apps/`) reuses the identical `RequestKind` dispatch structure, but `onAccept` goes straight from `onlyHost` into decoding `RequestKind` and calling `authenticate`/`withdraw`, with no relayer check anywhere in the contract: [3](#0-2) 

A repo-wide search confirms `_relayer`/`setRelayer`/`relayer()` exist only in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` (and unrelated contracts `BridgeToken.sol`, `SimplexPaymaster.sol`) — the mechanism is entirely absent from the Tron gateway file, not merely unused.

### Impact Explanation
On the EVM gateway, `_checkRelayer` is the layer that keeps `RedeemEscrow`/`RefundEscrow` withdrawal deliveries (and every other `RequestKind`) restricted to the designated relayer once governance arms the gate, closing the specific attack described in the decision log: a forged consensus proof that swaps `_hostParams.handler` for a malicious contract reporting an arbitrary relayer, letting that address impersonate the trusted relayer to app-level gates. On Tron, this last line of defense does not exist at all, so the same forged-handler scenario reaches `withdraw()` (escrow redemption/refund of user funds) with no relayer-identity check whatsoever — only `authenticate()` (source-instance check) stands in the way, which the original gate was added specifically because it is not sufficient on its own once the handler itself is compromised. This is a concrete path to unauthorized escrow withdrawal / fund loss on the Tron deployment under conditions the mainline EVM deployment is explicitly hardened against.

### Likelihood Explanation
This requires the same triggering precondition as the defense it is missing was built for — a compromised or governance-forged `handler`/consensus state that lets an attacker control the relayer address the host reports on delivery. That is a high-severity but non-trivial precondition; however, it is exactly the scenario the corresponding EVM gate exists to defend against, and Tron's `IntentGatewayV2` has zero mitigation for it, whereas the mainline EVM path does. Given the report explicitly limits scope to Medium/High/Critical analogs and this is an unconditional, code-verifiable omission of a documented security control on a fund-custody path, it is assessed at Medium.

### Recommendation
Port the `_relayer` / `setRelayer` / `_checkRelayer` mechanism from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`, and call `_checkRelayer(incoming.relayer)` at the top of `onAccept`, mirroring the EVM gateway exactly, so both deployments enforce identical relayer-authorization semantics on identical message classes.

### Proof of Concept
1. Compare `onAccept` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` (line 330-337) against `onAccept` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (line 629-635): both decode the same `RequestKind` and call the same `authenticate`/`withdraw` logic for `RedeemEscrow`/`RefundEscrow`, but only the former is preceded by `_checkRelayer(incoming.relayer)`.
2. Under the forged-handler scenario documented in `sdk/packages/core/docs/ai/decisions/2026-09-03-hostmanager-deliveries-are-gated-too-and-that-does-not-touch.md` (a `SetHostParam` swap of `_hostParams.handler` accepted via a forged consensus proof), any relayer address can be reported by the malicious handler to `EvmHost.dispatchIncoming`.
3. On the EVM gateway, `_checkRelayer` would revert this delivery with `Unauthorized` once a relayer is set (see `testForgedHandlerSwapIsRefused` in `evm/tests/foundry/HostManagerTest.sol`, lines 225-241).
4. On the Tron gateway, the identical delivery proceeds directly to `authenticate()`/`withdraw()` with no relayer check, so the forged handler's ability to report an arbitrary relayer is never intercepted at the app layer.

     * @dev Once a relayer is set, rejects deliveries from anyone else before the body is read. The

     * every delivery passes: a proxy from before the gate stays open until `migrate` arms it.
     * @param relayer The account that submitted the message to the handler.
     */
    function _checkRelayer(address relayer) internal view {
        address authorised = _relayer;
        if (authorised != address(0) && relayer != authorised) revert Unauthorized();
    }

    /**
     * @notice Executes an incoming post request.
     * @dev This function is called when an incoming post request is accepted.
     * It is only accessible by the host.
     * @param incoming The incoming post request data.
     */
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return withdraw(body, kind == RequestKind.RefundEscrow);
        }

        // only hyperbridge is permitted to perfom these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            NewDeployment memory body = abi.decode(incoming.request.body[1:], (NewDeployment));
            _instances[keccak256(body.stateMachineId)] = body.gateway;

            emit NewDeploymentAdded({stateMachineId: body.stateMachineId, gateway: body.gateway});
        } else if (kind == RequestKind.UpdateParams) {
            // Decode the body which includes optional destination-specific protocol fee updates
            ParamsUpdate memory update = abi.decode(incoming.request.body[1:], (ParamsUpdate));
            emit ParamsUpdated({previous: _params, current: update.params});
            _params = update.params;

            // Update destination-specific protocol fees if provided
            for (uint256 i; i < update.destinationFees.length;) {
                bytes32 stateMachineId = update.destinationFees[i].stateMachineId;
                uint256 feeBps = update.destinationFees[i].destinationFeeBps;
                _destinationProtocolFees[stateMachineId] = feeBps;

                unchecked {
                    ++i;
                }
                emit DestinationProtocolFeeUpdated(stateMachineId, feeBps);
            }
        } else if (kind == RequestKind.SweepDust) {
            SweepDust memory req = abi.decode(incoming.request.body[1:], (SweepDust));

            uint256 outputsLen = req.outputs.length;
            for (uint256 i; i < outputsLen;) {
                TokenInfo memory info = req.outputs[i];
                address token = address(uint160(uint256(info.token)));
                uint256 amount = info.amount;

                if (token == address(0)) {
                    (bool sent,) = req.beneficiary.call{value: amount}("");
                    if (!sent) revert InsufficientNativeToken();
                } else {
                    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
                    if (!success) revert TransferFailed();
                }
                unchecked {
                    ++i;
                }
                emit DustSwept(token, amount, req.beneficiary);
            }
        }
    }
