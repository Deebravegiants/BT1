### Title
Non-USD same-token spread treated as fee-token (USD) value without price conversion, poisoning the profitability gate - (File: sdk/packages/simplex/src/strategies/fx.ts)

### Summary
`FXFiller.calculateProfitability` mixes a real USD figure (`feeProfit`) with `realizedSpreadProfit`, a raw token-unit amount that is only decimal-rescaled — never priced — whenever the fill is a same-token, non-USD pair (e.g. cNGN→cNGN cross-chain). The comment in the code even documents the flaw but under-estimates its blast radius.

### Finding Description
For same-token legs, the code computes the spread in the asset's own units and rescales its decimal precision to the fee token's decimals with `adjustDecimalsFloor`, then accumulates it into `realizedSpreadProfit`: [2](#0-1) 

The code's own comment acknowledges this is a decimal rescale, not a price conversion, and that the magnitude is wrong for non-USD assets: [3](#0-2) 

Later, for a full (non-partial) fill, this token-unit-as-USD figure is added directly to `feeProfit` — a genuine fee-token/USD-denominated value (`order.fees - executionCost`) — to produce `totalProfit`: [4](#0-3) 

This is the exact analog of the reported GMX bug: a token amount (`spread`, in the same-token asset's own decimals) is summed into a USD-denominated running total (`feeProfit`) with an implicit assumption that 1 unit of the asset = 1 USD, without multiplying by the asset's actual USD price/anchor factor (`usdFactorBySymbol`, which the same function already computes and correctly applies elsewhere, e.g. `sameTokenEdgeUsd`, `curveSurplusUsd`, `fxMarginUsd`).

Per the documentation, same-token markets are explicitly supported for non-USD-stable assets (e.g. cNGN/cNGN cross-chain transfer markets), so this path is reachable in production configurations, not just a theoretical edge case: [5](#0-4) 

### Impact Explanation
`totalProfit` (built from `feeProfit + realizedSpreadProfit`) is the actual number `evaluateOrder` uses to gate execution: only strategies scoring `profitability > 0` are eligible, and the highest-scoring one is picked and its `executeOrder` invoked, which submits an on-chain fill and commits the filler's real funds: [6](#0-5) [7](#0-6) 

For a non-USD same-token asset whose actual USD value per unit is far from 1 (e.g. cNGN, which per the docs prices at ~1550-1580 units per USD), the raw-unit spread added into `totalProfit` massively overstates or understates the dollar profit:
- If the asset is worth much less than $1 (cNGN case), a tiny real spread reads as a huge nominal "profit," causing the filler to accept fills whose real dollar edge does not cover its true cost/risk (loss of funds over time / fee/gas cost not actually covered despite passing Gate 1's `order.fees < executionCost` check being independent — the accounting for ranking and reporting is corrupted, and any downstream consumer or profit accounting relying on `profitUsd` from the `orderFilled` event is fed a false number).
- Conversely if the asset is worth much more than $1, correctly profitable fills could be mis-ranked or under-valued relative to other strategies, causing the filler to skip or de-prioritize genuinely better fills, or misreport `profitUsd` telemetry.

This directly corrupts the profitability decision and fund-accounting for any same-token, non-USD-stable market — a configuration the protocol's own documentation presents as a supported use case.

### Likelihood Explanation
Any operator configuring a same-token, non-$1 asset market (explicitly documented and supported, e.g. `cNGN/cNGN` cross-chain) hits this path on every full-fill same-token order. No attacker action beyond placing/filling an ordinary order in that market is required; likelihood is high wherever such a pair is configured.

### Recommendation
Multiply `spread` (in the same-token asset's own units) by the asset's `usdFactorBySymbol` value before folding it into any USD-denominated total, exactly as is already done for `sameTokenEdgeUsd`, `curveSurplusUsd`, and `fxMarginUsd`. `totalProfit` for full fills should use `feeProfit.plus(sameTokenEdgeUsd)` (already correctly converted) instead of `feeProfit + realizedSpreadProfit`, or `realizedSpreadProfit` itself should be built by multiplying the raw spread by the USD anchor factor rather than merely rescaling decimals. Add regression tests for a same-token, non-$1-anchored asset pair (e.g. cNGN/cNGN) verifying `calculateProfitability`'s returned value matches real USD profit, not raw token-unit magnitude.

### Proof of Concept
1. Configure a same-token cross-chain pair `cNGN/cNGN` with `askPricePolicy` slightly below par (e.g. `0.9995`), and a curve-priced `USDC/cNGN` anchor pair (`referenceOnly = true`) so cNGN's USD factor is ~1/1575.
2. Place a cross-chain order transferring, say, 1,000,000 cNGN cNGN→cNGN (input 1,000,000 cNGN, output 999,500 cNGN at the 0.9995 ask).
3. In `calculateProfitability`, `spread = 500` cNGN (raw units, rescaled to fee-token decimals via `adjustDecimalsFloor`), i.e. `realizedSpreadProfit ≈ 500` in fee-token (assumed USDC, 6-decimals) units — but 500 cNGN is worth roughly `500/1575 ≈ $0.32`, not $500.
4. `totalProfit = feeProfit + realizedSpreadProfit` therefore overstates the fill's dollar profit by roughly 1575x (`$0.32` real edge reported as `~$500`), causing the filler to systematically over-rank/execute this strategy over genuinely more profitable ones and to report a wildly incorrect `profitUsd` via the `orderFilled` monitor event used for accounting.

## Same-token markets

A pair may quote the **same symbol on both sides** — the same-asset cross-chain market (USDC on one chain in, USDC on another out). Same-token pairs are **ask-only** (both directions are one market) and their ask prices sit **strictly below par**: the price is the fraction of the input paid back out, so `0.9995` keeps 5 bps of every fill. Prices at or above 1 are rejected at startup — par is a zero spread that can never fill, and above par pays out more than received.

Same-token markets are **cross-chain only** — a same-chain order (source == destination) would be a pay-more-get-less self-swap and is rejected. Any registry asset works, USD-stable or not (e.g. a cNGN/cNGN transfer market across chains): the profit gate checks that each same-token leg comes out ahead **in its own asset** (a unit-independent sign check on input − output), and `order.fees` separately covers execution in the source fee token. The USD-anchor startup rule still applies, and a same-token pair contributes no FX edge of its own — a non-USD same-token market therefore needs a curve-priced USD pair for the asset alongside it (e.g. USDC/cNGN next to cNGN/cNGN) so confirmation depth can be sized in USD. Unlike cross-asset fills, the same-token spread is **realized in-kind on the fill itself**. It is not credited toward the fee gate, though: `order.fees` must cover execution on their own, and an order whose fees fall short is skipped no matter how wide the spread is. The realized spread only ranks orders that already passed both gates. Pre-position the asset on each destination chain (optionally backed by the [`[vault]` treasury](/developers/evm/simplex/treasury#vault-treasury-erc-4626)).
