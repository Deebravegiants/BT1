### Title
Webhook HMAC only signs the request body, letting an attacker forge the `shop`/`topic`/`webhook_id` claims trusted by the handler - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw HTTP body, while the `shop`, `topic`, and `webhook_id` values that the handler receives (and that host apps use to identify the tenant, per the gem's own documented contract) come straight from HTTP headers that are never part of the signed content. This breaks the intended binding `hmac == HMAC(body, shop, topic, webhook_id)`; in reality `hmac == HMAC(body)` only.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [2](#0-1) 
`to_signable_string` returns only `@raw_body`. The `shop`, `topic`, and `webhook_id` accessors read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) with no cryptographic tie to the body or to each other: [3](#0-2) 

`Registry.process` validates only the HMAC-over-body, then trusts these header-derived fields to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares against the header-supplied signature — again, only the body is covered: [5](#0-4) 

The gem's own documentation establishes that `data.shop` is meant to identify "The shop domain of the webhook" — the tenant-binding field the host app is expected to rely on: [1](#0-0) 

Because the shop/topic/webhook_id headers are not covered by the HMAC, any party who can obtain one genuine `(body, hmac)` pair signed with the app's `client_secret` — trivially available to any unprivileged merchant who installs the app on their own store and receives a real webhook — can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. The HMAC still validates because it only ever covered the body, so `Registry.process` invokes the host app's handler believing the event came from a different, victim shop.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an attacker-controlled body is delivered to the handler tagged with an arbitrary victim `shop` value, with a signature that appears valid. Any host application that uses `data.shop` from `WebhookMetadata` to look up the tenant's stored session/access token, update per-shop state, or make attributions (e.g., "shop X's order was created/updated", "shop X redacted its data") can be tricked into acting on forged cross-tenant data, since the gem provides no guarantee that `shop`/`topic` correspond to the entity that actually produced the signed body.

### Likelihood Explanation
Any unprivileged party can install the target app on their own free development store, receive one legitimate webhook (with a valid HMAC computed using the app's shared `client_secret`), and replay it with a modified `shop-domain` header — no access token, `client_secret`, or privileged account is required.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed material verified by `HmacValidator`, or otherwise cryptographically tie the header values to the body's signature before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document that host apps must independently verify `shop` against their own stored session/tenant record before trusting webhook-derived data, since this gem does not bind it.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify sends a legitimate webhook request to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and a JSON body.
3. Attacker captures this exact `(raw_body, hmac_header)` pair.
4. Attacker crafts a new HTTP POST to the same endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only, which matches, so `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though `victim-shop` never sent this webhook.
