### Title
Underpriced synchronous contract instrumentation on `DeployContract` lets a crafted control-flow-heavy contract spend outsized CPU time in chunk application relative to the linear per-byte gas charged - (`runtime/runtime/src/actions.rs`, `runtime/runtime/src/cache_warming.rs`, `runtime/near-vm-runner/src/prepare/prepare_v3.rs`)

### Summary
`action_deploy_contract` synchronously calls `precompile_contract_with_warming`, which runs `prepare_contract` (full `finite_wasm_6::Analysis::analyze` + `InstrumentContext::run`) on the chunk-application thread before any `max_instrumented_code_size` check can reject the contract. The `DeployContract` action's gas fee (`deploy_contract_base` + `deploy_contract_byte * code.len()`) is linear in the *original* code size and was calibrated using a non-adversarial "dummy" contract, so a control-flow/block-dense contract crafted just under `max_function_body_size`/`max_blocks_per_function`/`max_functions_number_per_contract` can make the synchronous analysis+instrumentation pass disproportionately expensive relative to gas charged, even in the case the deploy is ultimately accepted or rejected with `InstrumentedCodeTooLarge`.

### Finding Description
`Runtime::apply_action` dispatches `Action::DeployContract` to `action_deploy_contract` [1](#0-0) , which calls `precompile_contract_with_warming(&code, config, next_config, cache)` synchronously as part of the action's execution [2](#0-1) .

`precompile_contract_with_warming` runs `precompile_contract(code, current_config, cache)` inline (not on the background pool) - only the *next-epoch* config warm-up is fire-and-forget; the current-config compile is synchronous and blocks the apply: `let _ = precompile_contract(code, Arc::clone(&current_config), cache);` [3](#0-2) . This ultimately reaches `WasmtimeVM::compile_uncached`, which calls `prepare::prepare_contract` before running the wasmtime compiler [4](#0-3) .

`prepare_v3::prepare_contract` performs the full `finite_wasm_6::Analysis::analyze` and `InstrumentContext::run` passes over the entire module *before* the `max_instrumented_code_size` check runs, and any error from the precompile call is silently dropped by the caller (`let _ = precompile_contract(...)`) [5](#0-4) . As the code's own comment acknowledges, gas-metering instrumentation inserts metering code at every basic-block boundary, so instrumented output size (and the work to produce it) scales with block/function count, not simply with `code.len()` [6](#0-5) , and the project's own test explicitly exercises a contract built to make instrumented size blow up relative to source size [7](#0-6) .

Meanwhile, the `DeployContract` action's gas cost is `deploy_contract_base` + `deploy_contract_byte * code.len()` computed from the *original* code length only [8](#0-7) , and the estimator explicitly notes the per-byte estimate uses a "dummy contract" that is "clearly not the worst-case scenario for gas costs" [9](#0-8) .

Note: this work is not literally unbounded — it is capped by protocol-level structural limits (`max_function_body_size`, `max_blocks_per_function`, `max_blocks_per_contract`, `max_functions_number_per_contract`, `max_contract_size`) that are enforced incrementally inside the analysis/instrumentation pass itself. So the achievable worst case is a fixed, config-bounded amount of work at the maximum contract size — but that worst case is reachable synchronously per single `DeployContract` action, and the gas actually charged for that action is a simple linear function of `code.len()` that the estimator itself flags as not calibrated against the adversarial (block/control-flow-dense) case.

### Impact Explanation
This is a metering-completeness / underpriced-execution issue rather than an unbounded-DoS issue: repeated `DeployContract` transactions using near-limit, control-flow-dense contracts can force validators to repeatedly perform the most expensive analysis+instrumentation work the limits allow, synchronously in the chunk-apply path, while paying a `deploy_contract_byte` fee calibrated on non-adversarial contracts. This matches the "gas metering bypass / underpriced execution leading to chunk-application slowdown" bounty class, but the magnitude is bounded by the existing structural limits (not literally unbounded chain stall), and error paths (including `InstrumentedCodeTooLarge`) still charge the same fixed deploy_contract fee regardless of the CPU actually consumed.

### Likelihood Explanation
Any unprivileged account can submit `DeployContract` transactions with attacker-chosen bytecode up to `max_contract_size`; no special privilege is required. Feasibility is high in the sense that the call path (`action_deploy_contract` → synchronous `precompile_contract` → `prepare_contract`) is confirmed and unconditional for every deploy. However, quantifying "significant" disproportion requires benchmarking against the current calibrated `deploy_contract_byte`/`deploy_contract_base` values and current `LimitConfig` values, which were not available in this review — I could not confirm from the indexed code whether the estimator's current calibration (`get_runtime_config()` / worst-case near_test_contracts used for deploy estimation) already accounts for this scenario, since that special-casing is only referenced in a comment ("contract compilation costs are already accounted in deploy cost using special logic in estimator") without the actual estimator logic being located in this pass.

### Recommendation
- Charge (or bound) the deploy-time compilation cost using a metric that reflects instrumentation complexity (e.g., block/function count derived cheaply before running full instrumentation), not just `code.len()`.
- Consider deferring/parallelizing the synchronous current-config compile in `precompile_contract_with_warming` off the chunk-apply critical path, mirroring the existing fire-and-forget warming path used for `next_config`.
- Re-run/verify the runtime-params-estimator's `deploy_contract_byte`/`deploy_contract_base` calibration specifically against maximally block-dense contracts at `max_function_body_size`/`max_blocks_per_function`/`max_functions_number_per_contract`, and adjust fee parameters (or add a dedicated cap on total blocks/functions relative to gas charged) if the measured worst-case wall time exceeds the 1ms-per-Tgas budget.

### Proof of Concept
Benchmark/integration test plan:
1. Reuse `contract_with_many_blocks(num_functions)` from `runtime/near-vm-runner/src/prepare.rs` (or an equivalent generator) to build several near-limit contracts: vary `num_functions`/blocks up to `max_blocks_per_contract` while staying within `max_function_body_size` and `max_contract_size`.
2. For each contract, submit a `DeployContract` transaction through `Runtime::apply` (as in `runtime/runtime/src/tests/apply.rs` deploy tests) and measure:
   - Wall-clock time of `action_deploy_contract` (specifically the `precompile_contract_with_warming` call).
   - The `deploy_contract_base` + `deploy_contract_byte * code.len()` gas actually burnt for the action, converted to an expected time budget at the 1ms = 1Tgas rule.
3. Assert that wall-clock time stays within a small constant multiple of the time budget implied by charged gas, for contracts that succeed and for contracts that fail with `PrepareError::InstrumentedCodeTooLarge`.
4. Repeat with `config.limit_config.max_instrumented_code_size` set just below the instrumented size (as in the existing `instrumented_code_too_large` test) to specifically measure the wasted synchronous work in the rejection path, where `Runtime::apply` currently drops the precompile error and still only charges the linear byte fee.

pub(crate) fn precompile_contract_with_warming(
    code: &ContractCode,
    current_config: Arc<Config>,
    next_config: Option<Arc<Config>>,
    cache: Option<&dyn ContractRuntimeCache>,
) {
    if let (Some(next_config), Some(cache)) = (next_config, cache) {
        if cache_keys_differ(Arc::clone(&current_config), Arc::clone(&next_config)) {
            spawn_cache_warming(code.clone(), next_config, cache.handle());
        }
    }
    let _ = precompile_contract(code, Arc::clone(&current_config), cache);
}

```rust
pub(crate) fn prepare_contract(
    original_code: &[u8],
    features: crate::features::WasmFeatures,
    config: &Config,
    kind: VMKind,
) -> Result<Vec<u8>, PrepareError> {
    let lightly_steamed = PrepareContext::new(original_code, features, config).run()?;

    let analysis = finite_wasm_6::Analysis::new()
        .with_stack(SimpleMaxStackCfg)
        .with_gas(SimpleGasCostCfg {
            regular: u64::from(config.regular_op_cost),
            linear_base: config.linear_op_base_cost,
            linear_unit: config.linear_op_unit_cost,
        })
        .analyze(&lightly_steamed)
        .map_err(|err| {
            tracing::error!(target: "vm", ?err, ?kind, "analysis failed");
            PrepareError::Deserialization
        })?;
    // Make sure contracts can’t call the instrumentation functions via `env`.
    let res = InstrumentContext::new(
        &lightly_steamed,
        "internal",
        &analysis,
        config.regular_op_cost,
        config.limit_config.max_stack_height,
        config.limit_config.max_blocks_per_function.unwrap_or(u64::MAX),
        config.limit_config.max_blocks_per_contract.unwrap_or(u64::MAX),
        config.limit_config.max_params_per_function.unwrap_or(u64::MAX),
        config.limit_config.max_params_per_contract.unwrap_or(u64::MAX),
        config.limit_config.max_operand_stack_bytes_per_function.unwrap_or(u64::MAX),
    )
    .run()
    .map_err(|err| {
        use super::instrument_v3::Error;
        match err {
            Error::TooManyBlocksPerFunction => PrepareError::TooManyBlocksPerFunction,
            Error::TooManyBlocksPerContract => PrepareError::TooManyBlocksPerContract,
            Error::TooManyParamsPerFunction => PrepareError::TooManyParamsPerFunction,
            Error::TooManyParamsPerContract => PrepareError::TooManyParamsPerContract,
            Error::OperandStackTooLarge => PrepareError::OperandStackTooLarge,
            err => {
                tracing::error!(target: "vm", ?err, ?kind, "instrumentation failed");
                PrepareError::Serialization
            }
        }
    })?;
    // Guard against overflowing Cranelift’s 24-bit SSA value counter. Each wasm
    // byte produces at least one SSA value, so capping the instrumented size is a
    // conservative proxy.
    // TODO: if we ever need to relax this limit, count actual wasm instructions
    // during the instrumentation pass instead of using byte size as a proxy.
    if let Some(max_size) = config.limit_config.max_instrumented_code_size {
        if res.len() as u64 > max_size {
            tracing::debug!(target: "vm", size=res.len(), ?kind, "instrumented code too large");
            return Err(PrepareError::InstrumentedCodeTooLarge);
        }
    }
    Ok(res)
```

    #[test]
    fn instrumented_code_too_large() {
        with_vm_variants(|kind| {
            let mut config = test_vm_config(Some(kind));
            // Raise the function body size limit so it doesn't interfere.
            config.limit_config.max_function_body_size = None;

            // First, figure out the instrumented size without a limit so we can
            // set a meaningful threshold.
            config.limit_config.max_instrumented_code_size = None;
            let wasm = contract_with_many_blocks(200);
            let instrumented = prepare_contract(&wasm, &config, kind).unwrap();
            let threshold = instrumented.len() as u64;

            // With a limit just below the instrumented size, preparation should
            // fail.
            config.limit_config.max_instrumented_code_size = Some(threshold - 1);
            let r = prepare_contract(&wasm, &config, kind);
            assert_matches!(r, Err(PrepareError::InstrumentedCodeTooLarge));

            // With a limit at exactly the instrumented size, it should pass.
            config.limit_config.max_instrumented_code_size = Some(threshold);
            let r = prepare_contract(&wasm, &config, kind);
            assert_matches!(r, Ok(_));
        });
    }
