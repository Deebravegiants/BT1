### Title
Webhook shop-tenant identity not covered by HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop`, `topic`, `api_version`, and `webhook_id` values — which are taken from HTTP headers — are never part of the signed material, yet `shop` is subsequently trusted as the tenant identity passed to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` reads `shop`, `topic`, `api_version`, and `webhook_id` straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.), while `hmac` and `to_signable_string` are computed only from `@raw_body`: [1](#0-0) [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which computes `HMAC-SHA256(secret, to_signable_string)` (i.e. HMAC of the body only) and compares it to the `hmac` header: [3](#0-2) [4](#0-3) 

After this check passes, `request.shop` (an unauthenticated header value) is placed directly into `WebhookMetadata` and handed to the app's handler as the tenant identity: [5](#0-4) [6](#0-5) 

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality the code implicitly assumes is `shop_header == shop_that_produced(hmac)`, but the HMAC only binds `raw_body == HMAC(secret, raw_body)` — it says nothing about which shop the body came from. Since the app's `client_secret` (and hence the signing key) is identical for every shop that installs the app, any two webhook deliveries with the same body produce the identical, valid HMAC regardless of which shop they were sent for. Many webhook topics carry an empty or shop-independent body (the test fixtures even show `raw_body: "{}"` for topic webhooks), so a genuinely-Shopify-signed webhook body captured from one shop's delivery is a byte-for-byte valid, HMAC-valid payload for every other shop as well.

### Impact Explanation
An attacker who legitimately installs the app on their own store receives real webhook deliveries with a body and a valid HMAC generated using the app's actual `client_secret` — no leaked credential or privileged access is required, this is normal merchant behavior. Because the shop identity is never part of the signed content, the attacker can resend the exact same body/HMAC pair directly to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) headers to claim it originated from an arbitrary victim shop. `Registry.process` will accept it as authentic (the HMAC check passes) and invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain. Any handler logic that uses `data.shop` to select/mutate per-tenant state (e.g. deactivating a shop record on `app/uninstalled`, processing `shop/redact`, GDPR webhooks, or billing-related topics whose bodies are shop-independent) can be triggered against a shop the attacker does not control — a cross-tenant action performed with no credential belonging to the victim, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Moderate-to-high: the prerequisite (become an installer of the target app on any shop, including the attacker's own store) is an unprivileged, unauthenticated-relative-to-other-tenants action available to any internet user for public apps. Capturing one's own webhook delivery and replaying it with modified headers requires no special tooling beyond a basic HTTP client, and many mandatory/common webhook topics (`app/uninstalled`, `shop/redact`, `customers/redact`, etc.) have bodies that are empty or shop-agnostic, making the "identical body, identical HMAC" precondition easy to satisfy in practice.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the material that is authenticated, not just the raw body. At minimum, `Registry.process` should verify that the shop domain reported in the webhook is consistent with an expected/allow-listed shop for the given delivery context (e.g., cross-check against a per-shop webhook secret or a registered shop list), or extend `VerifiableQuery`/`Request#to_signable_string` so the HMAC covers the header-derived `shop` and `topic` values rather than the body alone, matching how Shopify's own webhook verification recommends validating the full set of relevant headers, not just the payload.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and enable a webhook topic whose payload is shop-independent (e.g. `app/uninstalled`, body `{}`).
2. Capture the genuine webhook POST Shopify delivers to the app's endpoint, noting `X-Shopify-Hmac-Sha256: <valid-hmac-of-{}>` and body `{}`.
3. Replay this exact body and HMAC directly to the same app endpoint, but replace `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` using `to_signable_string` (`"{}"`), which matches the captured HMAC (same secret, same body) — validation succeeds.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)`, causing the app to perform victim-shop-scoped actions (e.g., deactivate/delete the victim's stored session or data) without ever having a token or credential for `victim.myshopify.com`.         def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
