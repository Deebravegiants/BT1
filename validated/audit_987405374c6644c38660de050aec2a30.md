### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted by `Registry.process` without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain`, `topic`, and `webhook-id` **headers** to the app's handler as trusted identity data. Those headers are never part of the signed material, so the equality the library implicitly claims — "HMAC-verified request" == "HMAC-verified `shop`" — does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors, however, are read straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` verifies only `Utils::HmacValidator.validate(request)` — i.e., only the body — and then constructs `WebhookMetadata` directly from the unverified headers, passing it to the app's registered handler as authenticated data: [3](#0-2) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, which for a webhook `Request` is the raw body only, never the headers: [4](#0-3) 

Because a single `api_secret_key` is shared across every shop that has installed a given app, any merchant who has installed the app can legitimately trigger Shopify to send a validly HMAC-signed webhook containing attacker-chosen body content (e.g., by crafting order/product data on their own store). That attacker can capture the resulting `(raw_body, hmac)` pair from traffic to their own endpoint and replay it to the app's public webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because only the body is checked, and `Registry.process` forwards the forged `shop` value to the handler as if it were verified. The documented usage pattern confirms handlers are expected to treat `data.shop` as trustworthy for tenant attribution (e.g., `shop_domain: data.shop` used to route background jobs): [5](#0-4) 

This breaks the identity binding: `shop header trusted by handler` ≠ `shop bound to the HMAC-signed bytes`.

### Impact Explanation
This allows a low-privilege actor (any merchant who can install the multi-tenant app) to make the app attribute attacker-controlled webhook payloads to an arbitrary victim shop domain, since the shop identity used for tenant-scoped processing is never covered by the signature that gate-keeps the request. Depending on how the host app uses `data.shop` (e.g., as a lookup/session key to fetch the victim's access token or to write into the victim's tenant data store), this can lead to cross-tenant data corruption or misattribution — meeting the Critical "cross-tenant access" bar defined in scope.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be an installed user of the target multi-tenant app (no special privilege), (2) the ability to craft body content that reaches their own webhook delivery and capture the resulting signature, and (3) the ability to POST to the app's public webhook endpoint with a modified header — no `api_secret_key`, access token, or TLS interception is needed since the signature the library relies on never covered the header in the first place.

### Recommendation
Bind the shop (and ideally topic/webhook-id) identity to the verified data: e.g., require the app to independently confirm `shop-domain` against a known/authorized shop for the topic, or have `HmacValidator`/`Registry.process` fail closed unless the shop domain is cross-checked against a session or registration record before dispatch, rather than passing header-derived values straight into `WebhookMetadata` as verified.

### Proof of Concept
```ruby
# Attacker is a legitimate merchant of the app, "attacker-shop.myshopify.com".
# Shopify genuinely signs the body Shopify sends for attacker's own webhook.
raw_body = '{"id": 1, "note": "malicious payload"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_api_secret_key, raw_body)
# (Attacker legitimately obtains this pair from a real webhook delivered to their own server.)

# Attacker replays it to the app's public webhook endpoint, but swaps the shop header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds (body+secret match),
# handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker payload)
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
