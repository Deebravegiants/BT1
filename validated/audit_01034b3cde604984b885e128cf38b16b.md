### Title
Duplicate commitment via timestamp-collision in `prooflessDeposit` causes permanent freeze of one of two identical UTXOs - ([File: contracts/Hinkal.sol], [File: contracts/HinkalBase.sol])

### Summary
`HinkalBase.createOnchainCommitment` derives a UTXO's commitment purely from `(amount, erc20Address, stealthAddress, timeStamp)` with `timeStamp = block.timestamp`, and no leaf-index or per-call salt is mixed in. Because the spend-side nullifier is a deterministic function of the commitment and the recipient's private key (not of the tree index), two leaves that happen to carry an identical `(amount, token, stealthAddress, timeStamp)` tuple collide to the same commitment and, on redemption, to the same nullifier — permanently freezing whichever of the two leaves is not spent first.

### Finding Description
Broken equality: two distinct tree leaves at different `insertMany` indices resolve to the same `commitment` value, and therefore to the same `nullifier` value, even though they represent economically distinct deposits (funded by two different depositors).

Code path:
- `_createProoflessDepositCommitments` builds a `UTXO{amount, erc20Address, stealthAddressStructure, timeStamp: block.timestamp}` per deposit entry and calls `createOnchainCommitment`: [1](#0-0) 
- `createOnchainCommitment` computes `commitment = hash4(amount, erc20Address, stealthAddress, timeStamp)`: [2](#0-1) 
- `insertCommitments` inserts the resulting leaf value via `insertMany`, which happily accepts a duplicate leaf value at a new tree index: [3](#0-2) 
- At spend time, the circuit computes `signature = Poseidon(nullifyingPrivateKey, commitment)` and `nullifier = Poseidon(commitment, signature) * (commitment != 0)` — a function of only `(commitment, nullifyingPrivateKey)`, with no dependence on the Merkle path/leaf index: [4](#0-3) [5](#0-4) 
- The main circuit only checks `inNullifiers[i][j] === calcNullifier[i][j].out` and separately proves *some* valid Merkle path (via `ForceEqualIfEnabled` against `rootHashHinkal`) for that commitment — either duplicate leaf's path satisfies this constraint: [6](#0-5) 

Attacker action: attacker observes a victim's pending `prooflessDeposit(erc20Addresses, amounts, stealthAddressStructures, onChainEncryptedOutputs, ...)` transaction in the mempool — these arguments are plaintext calldata. Attacker submits their own `prooflessDeposit` call with the identical `erc20Addresses[i]`, `amounts[i]`, and `stealthAddressStructures[i]` (i.e., depositing their own funds to the same public stealth address the victim targeted), timed to land in the same block (same `block.timestamp`). Both transactions succeed independently: `performProoflessDepositChecks` only validates lengths, non-zero amount, and non-empty encrypted output — it never checks for commitment uniqueness. [7](#0-6) 

Result: two leaves at different `insertMany` indices carry the byte-identical `commitment`. When the legitimate owner of that stealth address later spends either UTXO, `nullifiers[nullifier]` is set true (via `insertNullifiers` in `HinkalBase.sol`, gated on `nullifiers[n] == false`). Because the nullifier is fully determined by `(commitment, nullifyingPrivateKey)` and both leaves share the same commitment, the second, distinct leaf becomes permanently unspendable — any proof attempting to redeem it will produce the exact same nullifier, which is already marked spent, and the transaction reverts forever.

None of the existing guards prevent this: `performHinkalChecks`/`dimensionsCheck` validate array shapes, not commitment uniqueness; `rootHashExists` only checks the Merkle root is known, and either duplicate leaf provides a valid inclusion path against that root; the circuit's balance equation (`inTotal + amountChanges === outTotal`) and `OverflowPreventer` operate on amounts, not leaf identity; there is no `ForceEqualIfEnabled` or index-binding constraint that ties the nullifier to the specific leaf index rather than the commitment value alone.

### Impact Explanation
The funds backing whichever of the two identical leaves is not spent first become permanently frozen — unspendable by anyone, including the legitimate stealth-address owner, since the required nullifier is already recorded as used. This is a direct "permanent freezing of user funds" event, matching the Critical severity bucket. It is fully repeatable by any unprivileged attacker against any observed `prooflessDeposit` call, at the cost of only the attacker's own deposited amount (which itself also risks being the frozen one, but the attacker can target freezing the victim's leaf specifically since the victim, unaware of the collision, is likely to redeem first via normal wallet flow).

### Likelihood Explanation
Preconditions are cheap and fully attacker-controlled: mempool visibility of a pending `prooflessDeposit` transaction (calldata is plaintext, non-hidden), and the ability to submit a copy-cat transaction that lands with the same `block.timestamp` (trivial on most EVM chains since many transactions share a timestamp within one block, and an attacker can also target sequencer/L2 environments with predictable block timing). No special role, oracle, or victim cooperation is required. This is realistically and repeatably exploitable whenever `prooflessDeposit` is used with a publicly known/reused stealth address, which is a normal use case for this proofless-deposit "pay to a known address" feature.

### Recommendation
Bind commitment (and hence nullifier) uniqueness to something that cannot collide across independent deposits — e.g., incorporate the tree leaf index (or a monotonically increasing deposit nonce/counter) into the `hash4` commitment preimage in `createOnchainCommitment`, and mirror this in `OriginalCommitmentCalculator`/`MainEVMCircuit` so that the nullifier calculation is bound to the specific leaf rather than solely to `(amount, token, stealthAddress, timeStamp)`. Alternatively, ensure `timeStamp` (or an added nonce field) is guaranteed unique per leaf (e.g., derived from `insertMany`'s assigned index) rather than relying on `block.timestamp`, which is coarse-grained and attacker-predictable/collidable.

### Proof of Concept
Hardhat test plan:
1. Deploy `Hinkal`/`HinkalHelper`/`Merkle` stack with a test ERC20.
2. Construct a fixed `stealthAddressStructure` (as if belonging to a victim recipient) and fixed `amount`/`erc20Address`.
3. Use `evm_setNextBlockTimestamp` to fix `block.timestamp` for both transactions, then have `victim` call `prooflessDeposit([erc20], [amount], [stealthAddressStructure], [encOutput1], false, "orderA")`.
4. Immediately after (same fixed timestamp, next tx in same block via `evm_setAutomine(false)` + manual mining, or same block via same `evm_setNextBlockTimestamp`), have `attacker` call `prooflessDeposit` with identical `erc20Addresses[0]`, `amounts[0]`, `stealthAddressStructures[0]` but their own funds and `encOutput2`.
5. Read both emitted `NewCommitment` events; assert `commitment_victim == commitment_attacker` (equality claimed broken) while `insertedIndex_victim != insertedIndex_attacker`.
6. Off-chain, generate a valid spend proof for the stealth address's private key redeeming the leaf at `insertedIndex_victim` (or `insertedIndex_attacker`) via `transact`; assert it succeeds and `nullifiers[n] == true` afterward for the derived nullifier `n`.
7. Generate a second valid spend proof for the *other* leaf (different Merkle path/index, but same commitment/private key) and assert its computed nullifier equals `n` from step 6, and that submitting it reverts with a "nullifier already used"-style require, proving the second leaf's value is permanently unspendable.
