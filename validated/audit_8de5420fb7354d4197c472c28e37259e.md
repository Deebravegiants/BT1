### Title
Webhook `shop` field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's webhook handler with the shop identity attached. In reality, the HMAC only covers the raw request body, not the `shop-domain` header. Any party who can obtain one valid `(body, hmac)` pair signed with the app's shared `api_secret_key` — for example, the owner of any shop that has this app installed, from their own legitimately-delivered webhook — can replay that same body/HMAC pair while substituting an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header naming a different, victim shop. The signature check still passes, and the handler receives `WebhookMetadata` attributing the (attacker-chosen) body to the victim shop.

### Finding Description
`Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)`, and `Request#hmac`/`#to_signable_string` show the HMAC is computed only over `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop` accessor is read directly from the (unsigned) header and is never included in `to_signable_string`: [3](#0-2) 

`Registry.process` then passes this unauthenticated `shop` value straight into the `WebhookMetadata` handed to the app's handler, alongside the topic and body: [4](#0-3) 

This is the same identity-binding gap as the reference bug class: a field that is *acted on* (here, the `shop` tenant identifier used to route/attribute webhook data) is not covered by the cryptographic check that is supposed to authenticate the whole message (here, the HMAC). The gem's own documentation reinforces the false assumption that `process` fully "verifies the request did indeed come from Shopify" for all fields used by the handler: [5](#0-4) 

Because `api_secret_key` is shared across all shops that install the same app, any shop owner (an "unprivileged" party relative to other tenants of the same app) legitimately receives real webhooks from Shopify for their own store, each with a valid `(raw_body, hmac)` pair signed with that shared secret. That attacker can replay the exact same body and HMAC to the app's webhook endpoint while swapping only the `shop-domain` header to name a victim shop. `HmacValidator.validate` recomputes the HMAC only over `to_signable_string` (the raw body) and compares it with `OpenSSL.secure_compare`, so the forged request passes validation: [6](#0-5) 

The handler then processes attacker-controlled data (body content the attacker chose is bounded to whatever their own store's webhook produced, but the topic and shop attribution can be freely mismatched) as if Shopify sent it *for the victim shop*, breaking the equality `shop authenticated by HMAC == shop used to key application state`.

### Impact Explanation
This crosses a tenant boundary: a webhook payload can be attributed to a shop other than the one that actually produced it, without possessing that shop's or the app's `client_secret`/access token beyond the shared, already-issued app secret material embedded in any of the app's own legitimate webhook deliveries. Any application logic that trusts `WebhookMetadata#shop` to identify which merchant's data changed (e.g., updating per-shop records, triggering per-shop side effects, invalidating per-shop caches) can be manipulated cross-tenant by any other installer of the same app. This matches the High-impact category of cross-tenant access via a credential/identity-binding bypass.

### Likelihood Explanation
Requires only: (1) being an installer of the target app on some shop (to receive real, validly-signed webhooks), and (2) the ability to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-controlled headers — both readily available to any unprivileged party who can install the app on their own store. No access to the app's `client_secret`, admin API access token, or any victim credential is needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signable string, or otherwise cryptographically bind the header-derived shop domain to the signed body before it's exposed via `WebhookMetadata`. At minimum, document prominently that `shop` is not covered by the HMAC and that callers must independently verify the shop is one they have an active session/install for before trusting it, rather than stating unqualified that `process` "will verify the request did indeed come from Shopify."

### Proof of Concept
1. App is installed by both the attacker's shop (`attacker.myshopify.com`) and a victim shop (`victim.myshopify.com`), sharing the same `api_secret_key`.
2. Shopify delivers a real webhook to the attacker's store, e.g. `orders/create` with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B`).
3. Attacker captures `(B, H)` and replays a POST to the app's webhook endpoint with the same body `B` and hmac header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, returns `true`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to act on victim-shop data that never originated from Shopify for that shop. [4](#0-3)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
