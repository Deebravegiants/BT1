## Confirmed analog vulnerability

### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are trusted from unauthenticated HTTP headers, not covered by the HMAC — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the tenant-identifying `shop` field (and `topic`, `webhook_id`, `api_version`) are read directly from HTTP headers that are never included in the signed data. `Registry.process` validates the HMAC and then dispatches to the app's handler using the header-derived, unauthenticated `shop` value.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers via `shopify_header`, with no relation to the signed body: [2](#0-1)  and [3](#0-2) .

`HmacValidator.validate` (used by `Registry.process`) only verifies `verifiable_query.hmac` against `to_signable_string`, i.e. the raw body bytes — it never checks that the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers were part of what was signed: [4](#0-3) .

`Registry.process` validates the HMAC of the body, then immediately trusts `request.shop` (and `request.topic`) — taken from headers — to build the `WebhookMetadata` passed to the app's handler: [5](#0-4) .

This breaks the identity binding: **bytes verified (raw body) ≠ bytes/headers acted on (shop-domain header)**. Because `shop-domain` is attacker-controllable header data that isn't bound by the HMAC over the body, a request with a body legitimately signed by Shopify for shop A, replayed or crafted with a different `X-Shopify-Shop-Domain` header value, would still pass HMAC validation, yet the handler would receive a `WebhookMetadata` claiming to be from an attacker-chosen shop.

### Impact Explanation
Impact is scoped by what host applications do with `WebhookMetadata.shop`. Since apps commonly use this field to select the tenant's stored session/access token for follow-up work, an unprivileged network attacker who can get any validly-HMAC'd webhook body (e.g., relaying a webhook that Shopify sent for a different, low-value/attacker-owned shop) could manipulate the `shop-domain` header to make the host app process the payload under a different tenant's identity — a cross-tenant confusion at the trust boundary this gem is responsible for verifying. This matches the category of "shop authenticated versus shop stored/acted upon" identity-binding breaks explicitly called out in scope.

However, note this requires the attacker to supply a body/HMAC pair (i.e., a real, Shopify-signed webhook payload from some shop) and then tamper with the un-signed headers of that request when relaying it to the app's endpoint — this is a request-forgery/header-tampering scenario at the HTTP layer, not a pure signature forgery. This is a real design gap in this gem's `Webhooks::Request`/`Registry` code (as opposed to a host-application misuse), since the gem itself defines the un-authenticated-header-trust pattern and hands the shop value to handlers post-"validation."

### Likelihood Explanation
Medium-low. Exploitation requires the attacker to control or replay the raw HTTP request to the app's webhook endpoint with modified headers alongside a validly-signed body they possess (e.g., from a webhook sent to their own store, or via request-smuggling/proxy header injection in the app's deployment). It does not require the `client_secret` or an access token, matching the exception carve-outs in the rules (no credential is required — only the ability to send an HTTP request with attacker-controlled headers and a legitimately-signed body).

### Recommendation
Include the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values in the HMAC-signable string (or otherwise cryptographically bind them to the payload) so header tampering is detected by `HmacValidator.validate`, rather than trusting these fields purely from unauthenticated headers after only the body's HMAC is checked.

### Proof of Concept
1. Attacker triggers a genuine Shopify webhook delivery to their own low-privilege/attacker-owned shop (`attacker-shop.myshopify.com`), obtaining a raw body + valid `X-Shopify-Hmac-Sha256` value signed with the app's shared secret.
2. Attacker replays this exact body/HMAC pair to the victim app's webhook endpoint, but rewrites the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com` (and, if desired, the `X-Shopify-Topic` header to a different registered topic).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the raw body HMAC — validation succeeds because the body signature is untouched: [6](#0-5) .
4. `WebhookMetadata` is built with `shop: request.shop` = `victim-shop.myshopify.com` (attacker-controlled), and the app's handler processes the attacker's body content as if it originated from `victim-shop.myshopify.com`: [7](#0-6) .
