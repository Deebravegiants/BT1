This confirms the exact analog: a GetRequest names a specific height on the destination chain (`GetRequest::height`), and both the EVM `handleGetResponses` [1](#0-0)  and the Substrate `state_coprocessor::handle_get_requests` [2](#0-1)  require that this exact `state_machine_commitment` at that height still exist, with the requirement that `get.height == proof.height.height` enforced strictly [3](#0-2) . Unlike POST-request MMR overlay roots (append-only, superseded by later heights), a GET response's `state_root` is a snapshot of chain state at one specific height — it cannot be regenerated at a later height once removed, exactly like Optimism's per-block L2 output root.

The `veto_state_commitment` extrinsic in `pallet-fishermen` deletes any `StateCommitment` — with no check that the challenge period has elapsed or that the height has already been relied upon for delivering a GetRequest/response [4](#0-3) . The underlying `delete_state_commitment` host call unconditionally removes the commitment and its update-time record [5](#0-4) . The equivalent EVM path, `deleteStateMachineCommitment`/`deleteStateMachineCommitmentInternal`, is likewise unconditional and callable by the handler (fraud-proof flow) at any time [6](#0-5) . The project's own docs acknowledge the veto has no time restriction ("ideally still in its challenge period") and claim it only "delays processing" because commitments are accumulators [7](#0-6)  — but this claim is false for GET requests, since the specific height's `state_root` is a one-time snapshot, not an append-only accumulator.

### Title
Fisherman/Challenger can veto a state commitment after its challenge period has elapsed, permanently bricking pinned-height GetRequests - (File: modules/pallets/fishermen/src/lib.rs, evm/src/core/EvmHost.sol)

### Summary
`pallet_fishermen::veto_state_commitment` (and the EVM equivalent `EvmHost::deleteStateMachineCommitment`) allow any single collator/fisherman to delete a `StateCommitment` for an arbitrary `StateMachineHeight` with no check that the challenge period has elapsed or that the commitment is still "live" (i.e. within its dispute window). This mirrors Sherlock M-10: the Optimism `Challenger` could call `deleteL2Outputs` on an output that was already past its 7-day finalization period, breaking already-confirmed withdrawals. Here, a fisherman can delete a `StateCommitment` after its `challenge_period` has elapsed and after relayers/users have already begun relying on it (e.g., dispatching or preparing to prove a `GetRequest` pinned to that exact height), permanently orphaning that request.

### Finding Description
A `GetRequest` is dispatched with a fixed `height` field specifying the exact destination-chain height whose storage must be proven [3](#0-2) . Both the substrate response handler and the EVM `handleGetResponses`/state-coprocessor `handle_get_requests` require `state_machine_commitment(height)` (or `response.height`) to exist and match exactly [2](#0-1) [8](#0-7) . This state root is a one-time snapshot of chain state at that specific block — unlike POST-request overlay (MMR) roots, which are cumulative and can be re-derived/re-proven at any later height, a `state_root` for height H cannot be regenerated once superseded by height H+1 (the chain's underlying state has already moved on).

`pallet_fishermen::veto_state_commitment` lets any single active collator delete this commitment via `ismp_host.delete_state_commitment(height)` with zero timing restriction [4](#0-3) . The pallet-ismp implementation of `delete_state_commitment` unconditionally removes both the state commitment and its `update_time` entry from storage [5](#0-4) , with no assertion that the height is still within its `challenge_period`, nor any check for pending `GetRequest`s anchored to that height. The docstring even concedes the commitment is "ideally still in its challenge period" but the code does not enforce this [9](#0-8) .

The equivalent EVM path (`EvmHost::deleteStateMachineCommitment`, invoked by the fraud-proof handler) is likewise unconditional [6](#0-5) .

Once the specific height's commitment is deleted, any `GetRequest` pinned to that height (already dispatched, with fee already paid, potentially already relayed with a proof in-flight) can never be answered: no future height's storage snapshot represents the state at the deleted height, and `handle_get_requests`/`handleGetResponses` will reject the proof with `StateCommitmentNotFound` because the exact `height == get.height` check cannot be satisfied by any other commitment [3](#0-2) .

### Impact Explanation
This causes permanent freezing/loss for the requester: the fee paid to dispatch the `GetRequest` is spent, but the request can never be fulfilled since its pinned height's state commitment is gone forever (state at that height is not recoverable from any future commitment). This is functionally identical to the Optimism M-10 outcome ("If a separate output root cannot be proven, then the user's withdrawal will be permanently stuck") — except here it is a `GetRequest` sender whose funds/request are permanently stuck rather than a withdrawing user. Any application built on Hyperbridge's `Get` primitive (e.g., cross-chain balance reads for token bridging, intents, bandwidth accounting) that relies on exact-height reads is exposed. This is reachable from a single unprivileged `dispatch_request` / `GetRequest` submission plus a fisherman veto that requires no cryptographic proof, no quorum, and no timing check — a misbehaving or compromised single collator (of potentially many) can trigger it.

### Likelihood Explanation
Likelihood is Medium: it requires a fisherman/collator (a permissioned but numerous role — every active collator is automatically a fisherman) to call `veto_state_commitment` on a height after the challenge period has elapsed and after a `GetRequest` has been pinned to it, either through a bad-faith veto or an automated fisherman task racing a slow RPC quorum disagreement after the window closed. The project's own documentation shows this is not considered dangerous today because they only reasoned about the POST/overlay-root case, not the exact-height `GetRequest` case, making an inadvertent trigger plausible in normal operation (e.g., the fisherman task in `parachain/simtests/src/pallet_fishermen.rs` reacts to `StateMachineUpdated` events without any challenge-period gate before vetoing).

### Recommendation
Enforce a time-based restriction in `veto_state_commitment` (and `EvmHost::deleteStateMachineCommitment`) so that a commitment can only be vetoed while still within its `challenge_period` (i.e. `current_timestamp - update_time <= challenge_period`), mirroring the `verify_delay_passed` check already used to gate message delivery [10](#0-9) . Additionally, before deleting a `StateCommitment`, check for any live `GetRequest`s pinned to that exact height and either block the veto or provide a compensating timeout/refund path for orphaned requests.

### Proof of Concept
1. A `GetRequest` is dispatched targeting `StateMachine::Evm(X)` at `height = H`, with the requester paying the dispatch fee [11](#0-10) .
2. Hyperbridge's consensus client commits `StateCommitment` for `height = H` on `StateMachine::Evm(X)`; the `challenge_period` for it elapses normally (e.g., days later), and the relayer begins constructing the storage proof for the pinned height `H`.
3. A single active collator calls `pallet_fishermen::veto_state_commitment(height = H)` — no proof, no quorum, no check that `H` is outside its challenge period or already relied upon [12](#0-11) .
4. `delete_state_commitment` removes the commitment for `height = H` unconditionally [5](#0-4) .
5. The relayer submits the `ResponseMessage`/`GetRequestsWithProof` for the pinned `height = H`; `handle`/`handle_get_requests` calls `host.state_machine_commitment(height)` which now returns `StateCommitmentNotFound`, and the enforced `get.height == proof.height.height` check means no future commitment can substitute [13](#0-12) .
6. The `GetRequest` is permanently unanswerable; the requester's paid fee and the underlying cross-chain read are lost forever, with no way to reconstruct state at height `H` from any later commitment.

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}
