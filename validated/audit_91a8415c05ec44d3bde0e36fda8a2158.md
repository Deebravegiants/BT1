Confirmed: `AddressRegistrar::register` has no excess-deposit refund path in the success (`Entry::Vacant`) branch, and there is no `withdraw`/`sweep` method anywhere in the contract. This is the direct nearcore analog of the reported ETH-stuck-on-overpayment bug.

### Title
Overpaid `attached_deposit` in `AddressRegistrar::register` is never refunded and becomes permanently locked - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
`AddressRegistrar::register` is a `#[payable]` method callable by any unprivileged account. It requires `attached_deposit >= required_deposit` (storage cost for the new address→account mapping), but only refunds the *full* deposit in the collision branch (`Entry::Occupied`). In the success branch (`Entry::Vacant`) any amount attached above `required_deposit` is silently kept by the contract with no code path to ever return or withdraw it, exactly mirroring the `forgeWithListed` `msg.value >= forgingFee` pattern from the referenced report.

### Finding Description
`register()` computes `required_deposit` from the byte cost of storing the 20-byte address key and the `account_id` value, then checks: [1](#0-0) 

using `given_deposit < required_deposit` — a strict-inequality guard that permits arbitrary overpayment, just like the Solidity `>=` check in the original report. When the address is new (`Entry::Vacant`), the full `given_deposit` (including any excess) is accepted and only the mapping is stored; no refund transfer is issued: [2](#0-1) 

Contrast this with the `Entry::Occupied` branch, which explicitly refunds the *entire* `given_deposit` back to `predecessor_account_id` because no storage was written: [3](#0-2) 

The contract exposes no `withdraw`, admin sweep, or any other method that can move NEAR out of the contract balance, confirmed by a full-file review — `lookup` and `get_address` are pure view methods: [4](#0-3) 

The existing test suite even documents that overpaying is expected behavior without refund of the excess, only asserting the contract balance increased by *at least* the deposit amount: [5](#0-4) 

This confirms `register` is reachable directly by any external, unprivileged NEAR account (not only internally by `WalletContract`), since the test calls it directly via `worker.root_account()?.call(address_registrar.id(), method).deposit(deposit_amount)`.

### Impact Explanation
Any account overpaying the storage deposit when registering a new address (e.g. due to naive client-side estimation, rounding up "to be safe", or a client using a stale/overestimated `storage_byte_cost`) permanently loses the difference between the attached deposit and the actual required storage cost. Because there is no refund and no withdrawal mechanism, the excess yoctoNEAR is locked in the `AddressRegistrar` contract forever — a genuine, unrecoverable value leak for the calling account, analogous in root cause and consequence to the reported Medium-severity `EntityForging` finding.

### Likelihood Explanation
The bug triggers on the ordinary, expected call path (no delay/race condition needed, unlike the original PoC which required a fee change mid-flight): any caller that attaches more than the exact `required_deposit` on a successful (non-colliding) registration loses the excess immediately and deterministically. Because `required_deposit` depends on `env::storage_byte_cost()` and `account_id.len()`, and clients commonly round up attached deposits for safety margins or because they cannot easily predict `account_id` length/byte cost precisely, overpayment is a realistic and easily reproducible scenario.

### Recommendation
In the `Entry::Vacant` branch, compute the excess (`given_deposit - required_deposit`) and issue a `promise_batch_action_transfer` refunding it to `predecessor_account_id`, mirroring the refund logic already implemented in the `Entry::Occupied` branch. Alternatively, require an exact-match deposit (reject if `given_deposit != required_deposit`) as one of the two mitigations suggested in the original report.

### Proof of Concept
1. Deploy `AddressRegistrar` and call `.new()`.
2. From any account, call `register({"account_id": "alice.near"})` attaching a deposit `D` strictly greater than `required_deposit` computed as `storage_byte_cost * (20 + len("alice.near"))`.
3. Observe the call succeeds, returns `Some(address)`, and the contract's balance increases by the full `D` (as shown by the existing `test_register_without_deposit` assertion pattern using `>=` rather than `==`) — [6](#0-5) .
4. There is no method on `AddressRegistrar` to retrieve `D - required_deposit`; it is permanently stuck in the contract.

    /// Attempt to look up the account ID associated with the given address.
    /// If an entry for that address is found then the associated account id
    /// is returned, otherwise `None` is returned. Use the `register` method
    /// to add entries to the map.
    /// This function will panic if the given address is not the hex-encoding
    /// of a 20-byte array. The `0x` prefix is optional.
    pub fn lookup(&self, address: String) -> Option<AccountId> {
        let address = {
            let mut buf = [0u8; 20];
            hex::decode_to_slice(address.strip_prefix("0x").unwrap_or(&address), &mut buf)
                .unwrap_or_else(|_| env::panic_str("Invalid hex encoding"));
            buf
        };
        self.addresses.get(&address).cloned()
    }

    /// Computes the address associated with the given `account_id` and
    /// returns it as a hex-encoded string with `0x` prefix. This function
    /// does not update the mapping stored in this contract. If you want
    /// to register an account ID use the `register` method.
    pub fn get_address(&self, account_id: AccountId) -> String {
        let address = account_id_to_address(&account_id);
        format!("0x{}", hex::encode(address))
    }
}
