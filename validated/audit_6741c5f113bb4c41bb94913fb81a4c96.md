### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `HmacValidator.validate` verifies solely against that body. The shop identity used to route the webhook to the app's handler is taken from the `X-Shopify-Shop-Domain` header, a value that is never included in the HMAC-signed material. An attacker who can obtain any validly-signed webhook payload (e.g., for a shop they themselves control) can replay it to a victim app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, and the HMAC check still passes.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns `@raw_body` exclusively — the `shop`, `topic`, `webhook_id`, and `api_version` values (all read from headers via `shopify_header`) are excluded from the signed bytes: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only computes/compares the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body) against the secret: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (header-derived) to construct `WebhookMetadata` passed to the app's handler: [5](#0-4) 

The documented usage pattern shows apps using `data.shop` directly to key tenant-scoped work (e.g., enqueuing jobs keyed by shop domain): [6](#0-5) 

This breaks the intended identity binding: `shop authenticated by HMAC == shop used as the tenant key by the handler`. In reality, the HMAC only authenticates the body bytes; the shop field is parsed independently and unauthenticated. Any bytes that satisfy `HMAC(secret, body) == header_hmac` will pass validation regardless of which shop header accompanies them.

### Impact Explanation
Because `data.shop` is unauthenticated relative to the HMAC, an attacker can:
1. Trigger (or capture) a legitimately signed webhook for a shop they control (e.g., install the target app type on their own dev/trial store and receive any webhook, such as `app/uninstalled` or a data topic).
2. Replay the identical raw body + HMAC header to the same app's webhook endpoint, but substitute `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) with a victim shop's domain.
3. The gem's `Registry.process` will accept the request as valid (HMAC still matches the unmodified body) and dispatch it to the app's handler with `shop` set to the victim's domain.

Depending on how the host app keys its tenant logic off `data.shop` (as the docs recommend), this can cause cross-tenant data corruption, forced processing of attacker-controlled webhook bodies under a victim shop's identity (e.g., forged `app/uninstalled`, `shop/update`, or GDPR/redact-style events causing deletion or mutation of victim tenant data), or state confusion between tenants — a cross-tenant integrity violation rooted entirely in this gem's webhook verification logic.

### Likelihood Explanation
Exploitation requires no access to `api_secret_key`, no leaked credentials, and no privileged account — only a single legitimately delivered webhook to any shop the attacker controls (trivially obtainable by installing the target app on a free development store) plus the ability to send an arbitrary HTTP request to the target app's public webhook endpoint with a modified header. Both are unprivileged-internet-user capabilities, making this readily reachable.

### Recommendation
Bind the shop identity (and other trust-relevant fields like `topic`/`webhook_id`) into the authenticated material, or independently verify that the shop the app processes the webhook for matches an expected/known shop before trusting `data.shop` for tenant-scoped actions. At minimum, `Request#to_signable_string` should not be the sole basis for trusting `Request#shop`; the registry/handler contract should document that `shop` is unauthenticated and require host apps to cross-check it against a known/registered shop list, or the gem should reconstruct/verify shop binding out-of-band (e.g., via a registered webhook ID to shop mapping) before dispatch.

### Proof of Concept
```ruby
require "openssl"
require "shopify_api"

secret = ShopifyAPI::Context.api_secret_key
body = '{"id":123}'  # any legitimately-received webhook body for attacker's own shop
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)

# Attacker replays the SAME signed body but swaps the shop-domain header to a victim shop
spoofed_headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled value
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: spoofed_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC check passes (body unmodified); handler receives data.shop == "victim-shop.myshopify.com"
```
