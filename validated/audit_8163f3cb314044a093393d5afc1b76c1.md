## Analysis Result

### Title
Unauthorized `transferFrom` via unauthenticated `circomData.originalSender` in `DepositOnChainUtxosExternalAction` - (File: `contracts/external-actions/DepositOnChainUtxosExternalAction.sol`)

### Summary
`DepositOnChainUtxosExternalAction.runAction` pulls ERC20 tokens from `circomData.originalSender` via `transferERC20TokenFrom`, but `originalSender` is never bound into the proof's public inputs, the `signedMessageHash`, or the `calldataHash`. Any prover can therefore submit a self-consistent, validly-proved transaction (spending only their own nullifiers/UTXOs, `deltaAmounts[i] == 0`) while setting `originalSender` to an arbitrary victim address, causing the victim's tokens to be pulled if the victim has ever granted an ERC20 allowance to this external action / Hinkal, and crediting the resulting on-chain UTXO to the attacker's own stealth address.

### Finding Description
The circuit and `CircomDataBuilder` only bind the following fields into the values that are cryptographically checked (signature over `signedMessageHash`, and the SNARK's public-input vector): `rootHashHinkal`, `erc20TokenAddresses`, `amountChanges`, `timeStamp`, `inputNullifiers`, `outCommitments`, `calldataHash`, and the `stealthAddressStructure` fields [1](#0-0) . The public-input assembly in `formInputNormal` likewise only encodes `H1x/H1y/stealthAddress`, `rootHashHinkal`, the signed message hash, token addresses, `amountChanges`, `inputNullifiers`, `timeStamp`, `outCommitments`, `calldataHash`, `H0x/H0y` [2](#0-1) . `circomData.originalSender` is absent from both.

Despite this, `DepositOnChainUtxosExternalAction.runAction` reads `circomData.originalSender` directly from calldata and uses it as the `from` address in `transferERC20TokenFrom`, requiring only that it be non-zero: [3](#0-2) [4](#0-3) 

Because `originalSender` never appears in `calldataHash`/`signedMessageHash`/the public-input vector, the circuit's signature check (`sigVerifier` over `spendingPublicKey`/`eddsaSignature`/`signedMessageHash`) and Merkle/nullifier checks in `MainEVMCircuit.circom` [5](#0-4)  do not constrain who `originalSender` is. An attacker can generate a fully valid proof for their own note-spend (nullifying only their own UTXOs, with `deltaAmounts[i] == 0` so the balance equation in `Hinkal._externalTransact`/`_internalTransact` is untouched by this parameter) [6](#0-5) , then independently set `circomData.originalSender` to any address, and `stealthAddressStructure` to their own key, so the resulting UTXO (crediting `userAddress`'s pulled tokens) is spendable only by the attacker.

The equality broken is the implicit assumption that "the address whose tokens fund a newly minted commitment is the address that authorized (signed/proved) the transaction." That link is never enforced, unlike every other value-moving field (`amountChanges`, `erc20TokenAddresses`, `stealthAddressStructure`) which are cryptographically bound.

### Impact Explanation
If the victim address has an outstanding ERC20 allowance to the `DepositOnChainUtxosExternalAction` contract (a realistic condition — this action's whole design point is repeated deposits, so allowances of `max uint256` or leftover unspent allowance from a prior legitimate call are the expected steady state), an attacker can drain up to that allowance by calling `Hinkal.transact` with a self-proved transaction and `circomData.originalSender = victim`. The pulled tokens are transferred to `msg.sender` (the caller of `runAction`, i.e., the `Hinkal` contract acting as `msg.sender` in the transfer target line 79, actually credited into the created UTXO owned by the attacker's stealth address) and a shielded UTXO is minted under the attacker's control — direct theft of user funds via a `transferFrom` never authorized by the prover or signer, satisfying the Critical impact bar ("executing calls or moving assets a wallet owner or prover never authorised" / direct theft).

### Likelihood Explanation
Requires only: (1) a non-zero, unspent ERC20 allowance from a victim to the `DepositOnChainUtxosExternalAction` contract (a byproduct of normal use of this feature, since users are expected to call it repeatedly and typical UX sets high/unlimited allowances), and (2) the attacker submitting their own, entirely self-funded valid proof with `deltaAmounts == 0`. No relayer, admin, or victim key is needed — the attacker only needs their own valid signature over their own note. This is a realistic, unprivileged-EOA analog directly matching the report's pattern (a value-bearing field manipulated outside the checked equality).

### Recommendation
Bind `circomData.originalSender` into the same hash/public-input set that is checked by the on-chain signature verification and/or the circuit (e.g., include it in `getSignedMessageHash`'s `hash1`/`hash2` preimage in `CircomDataBuilder.sol`), or require `circomData.originalSender == circomData.externalActionData.externalAddress`/`msg.sender`-derived signer rather than an arbitrary calldata address. Alternatively, restrict `DepositOnChainUtxosExternalAction` to only ever pull from `msg.sender` of the original `Hinkal.transact` call (already tracked elsewhere in the codebase as the transaction originator) instead of trusting an unauthenticated struct field.

### Proof of Concept
1. Victim previously calls the `DepositOnChainUtxosExternalAction` flow once, leaving a non-zero ERC20 allowance to the external action contract (or approves `type(uint256).max` per common UX patterns).
2. Attacker builds `circomData` for `Hinkal.transact` where: `externalActionData.externalActionId` maps to `DepositOnChainUtxosExternalAction`; `inputNullifiers`/root/signature all correspond to the attacker's own (possibly zero-value) note so the SNARK proof verifies; `amountChanges[i] == 0` for all tokens (satisfying `require(deltaAmounts[i] == 0, ...)` at `contracts/external-actions/DepositOnChainUtxosExternalAction.sol:50-53`); `externalActionMetadata` encodes `utxoAmounts` equal to the amount to steal from the victim; and `originalSender = victim`, `stealthAddressStructure` = attacker's own keys.
3. Call `Hinkal.transact(...)`. Proof verification and the `Hinkal.sol` balance-equation checks pass because they never reference `originalSender` and `amountChanges == 0`.
4. Inside `runAction`, `transferERC20TokenFrom(tokenAddress, victim, msg.sender, tokenTotal)` executes, pulling the victim's tokens, and a new on-chain UTXO for `tokenTotal` is created under the attacker's `stealthAddressStructure`, redeemable later by the attacker alone. [7](#0-6)

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) external override onlyAllowedRecipient returns (UTXO[] memory utxoSet) {
        uint256 tokenCount = circomData.erc20TokenAddresses.length;
        require(
            tokenCount > 0 && deltaAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: token count mismatch"
        );

        address userAddress = circomData.originalSender;
        require(
            userAddress != address(0),
            "DepositOnChainUtxosExternalAction: Invalid originalSender"
        );

        uint256[][] memory utxoAmounts = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (uint256[][])
        );
        require(
            utxoAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: metadata length mismatch"
        );

        utxoSet = new UTXO[](countUtxos(utxoAmounts));

        uint256 utxoIndex = 0;
        for (uint256 i = 0; i < tokenCount; i++) {
            require(
                deltaAmounts[i] == 0,
                "DepositOnChainUtxosExternalAction: Delta amount must be zero"
            );

            address tokenAddress = circomData.erc20TokenAddresses[i];
            uint256 tokenTotal = 0;

            for (uint256 j = 0; j < utxoAmounts[i].length; j++) {
                uint256 amount = utxoAmounts[i][j];
                require(
                    amount > 0,
                    "DepositOnChainUtxosExternalAction: UTXO amount must be positive"
                );
                tokenTotal += amount;

                utxoSet[utxoIndex] = UTXO({
                    amount: amount,
                    erc20Address: tokenAddress,
                    stealthAddressStructure: circomData.stealthAddressStructure,
                    timeStamp: circomData.timeStamp + utxoIndex
                });
                utxoIndex++;
            }

            if (tokenAddress != address(0) && tokenTotal > 0) {
                transferERC20TokenFrom(
                    tokenAddress,
                    userAddress,
                    msg.sender,
                    tokenTotal
                );
            }
        }

        emit BlockedUtxosCreated();
    }
