### Title
Malicious or reverting token bundled into an order's inputs can permanently freeze all escrowed funds via `IntentsBase._withdraw` - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` (and its equivalent in the Tron fork, `IntentGatewayV2.sol::withdraw`) iterates over an order's list of escrowed input tokens and transfers each one to the beneficiary in a single loop. Because an order's `inputs` array is fully attacker/user-controlled at `placeOrder` time and can contain any ERC-20 address, a single non-conforming or intentionally malicious token embedded among otherwise legitimate tokens will cause the entire loop — and thus the entire withdrawal/refund/redemption transaction — to permanently revert, freezing every token in that order, including the legitimate ones.

### Finding Description
`_withdraw` releases escrowed tokens for a `WithdrawalRequest` by looping over `body.tokens` and calling `safeTransfer` for each: [1](#0-0) 

This function is invoked from three unprivileged/relayer-reachable paths:

1. **Cross-chain settlement (`onAccept`)** — when a `RedeemEscrow` or `RefundEscrow` message is delivered by any relayer, `ExtrinsicIntents.onAccept` decodes the `WithdrawalRequest` (whose `tokens` array is copied verbatim from the original `order.inputs` chosen by the order's creator) and calls `_withdraw(..., true)`: [2](#0-1) 

2. **Same-chain cancellation (`_cancelSameChain`)** — the order owner (an unprivileged user) cancels their own order and all remaining escrowed `order.inputs` tokens are refunded in one `_withdraw` call: [3](#0-2) 

3. **Same-chain fill** — after a solver fills an order, escrowed inputs are released to the solver via the same `_withdraw`: [4](#0-3) 

The Tron variant of the contract has the identical pattern, using low-level calls that explicitly `revert TransferFailed()` on any single token failure inside the loop: [5](#0-4) 

Since `order.inputs` (the list of escrowed tokens) is chosen entirely by whoever places the order — an unprivileged, permissionless action — nothing prevents an order from bundling one legitimate, valuable token (e.g. USDC) together with a token that is guaranteed to make `transfer`/`safeTransfer` revert to the beneficiary (a blacklist-style token such as USDT/USDC where the beneficiary or the gateway itself gets blacklisted, a token with a `transfer` function that unconditionally reverts, a fee-on-transfer token whose accounting the escrow doesn't account for causing an underflow inside `safeTransfer`, or simply a token contract deployed by the attacker that always reverts).

Once such an order exists, every code path that must move that order's escrow (`onAccept` redemption/refund from a cross-chain fill, `_cancelSameChain`, or same-chain fill settlement) executes the loop in `_withdraw` and will deterministically revert on the malicious token entry. Because Solidity loops give no way to skip a single failing iteration and there is no retry-per-token mechanism, the *entire* transaction — and therefore release of the legitimate token(s) bundled in the same order — can never succeed. There is no code path elsewhere in `IntentsBase`, `IntrinsicIntents`, or `ExtrinsicIntents` that allows redeeming/cancelling a subset of an order's tokens; withdrawal is strictly all-or-nothing per commitment.

This exactly mirrors the reported bug class ("as long as one token withdraw fails, the entire collateral may fail to withdraw"): a single bad ERC-20 dependency embedded in a batch operation is sufficient to make the whole batch permanently unwithdrawable.

### Impact Explanation
Funds are permanently frozen with no recovery path:
- A user who places a cross-chain order with a mix of a valuable token and a hostile token can never have that order refunded/redeemed once the hostile token is guaranteed to revert on transfer — the legitimate collateral is locked forever in the gateway's escrow.
- Because the withdrawal call is also invoked by `onAccept` in response to a relayed cross-chain message (an operation the protocol itself needs to complete settlement, not something the frozen party controls), even honest users who unknowingly interact with, or third parties who maliciously craft, such orders can end up with escrow that cannot be released by any relayer or by the user themselves.
- This constitutes a permanent loss/freezing of funds for a legitimate portion of escrowed assets, meeting the High severity bar for the equivalent Teller Protocol finding.

### Likelihood Explanation
Likelihood is high: placing an order (`placeOrder`) is a fully permissionless action with no allowlist or validation on `order.inputs` token addresses, and creating a token that reverts unconditionally (or one that blacklists the gateway/beneficiary, as USDT/USDC-style tokens already support) requires no special privileges. Any user, or a malicious actor targeting another user by tricking them into escrowing an attacker-supplied token alongside legitimate ones, can trigger this.

### Recommendation
Change `_withdraw` (and the Tron equivalent `withdraw`) to not let a single token transfer failure block the release of the other tokens in the same request:
- Wrap each token transfer in a try/catch (or use low-level `call` and record failures) so a reverting/blacklisting token does not halt the loop.
- For tokens whose transfer fails, retain their escrowed balance under a separate "stuck balance" mapping keyed by `(commitment, token)` that the beneficiary can later retry withdrawing individually (e.g. once unblacklisted, or via an alternate recipient), rather than coupling its fate to the rest of the order's tokens.
- Ensure `_filled`/finalize state is only set after successful processing, or make the retry idempotent so partial retries don't corrupt order state.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer`/`transferFrom` always reverts (or reverts when the recipient equals a specific frozen address).
2. Attacker (or an unsuspecting user under attacker's influence) calls `placeOrder` with `order.inputs = [ {token: USDC, amount: 10_000e6}, {token: EvilToken, amount: 1} ]`, escrowing both tokens into the gateway.
3. Time passes / order needs to be cancelled or filled:
   - Same-chain: owner calls `cancelOrder` → `_cancelSameChain` builds `remainingTokens` from both USDC and EvilToken and calls `_withdraw(body, true, true)` (`IntrinsicIntents.sol:159-180`).
   - Cross-chain: a solver fills on the destination chain and Hyperbridge relays a `RedeemEscrow` message back to source; `onAccept` calls `_withdraw(body, false, true)` (`ExtrinsicIntents.sol:330-337`).
4. Inside `_withdraw`'s loop (`IntentsBase.sol:456-470`), the iteration for `USDC` succeeds, but the iteration for `EvilToken` calls `IERC20(EvilToken).safeTransfer(...)`, which reverts.
5. The entire transaction reverts. Because `EvilToken.transfer` is deterministic (always reverts), every future retry of cancellation/redemption for this commitment also reverts.
6. Result: the 10,000 USDC escrowed for this order is permanently locked in the `IntentGatewayV2` contract, with no way for the user or any relayer to recover it, since there's no per-token retry path.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
