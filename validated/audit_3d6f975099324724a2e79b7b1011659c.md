Found a legitimate issue in the POA bridge withdrawal-status matching logic that fits the "status misreport" bug class from the report (equality broken: the withdrawal status/hash reported for a given batch index is not guaranteed to correspond to that index's actual on-chain withdrawal).

### Title
POA bridge `describeWithdrawal` matches withdrawal status by `assetId` only, causing wrong status/txHash to be reported for batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the completion status of a specific withdrawal in a batch by matching only on `assetId`, not on the actual withdrawal's index/identity. When a caller submits a batch of withdrawals (`processWithdrawal`/`waitForWithdrawalCompletion` with `WithdrawalParams[]`) that includes two or more withdrawals of the same token, each per-index poll can match the *same* entry from the POA bridge's `withdrawals` response, so the returned `status`/`txHash` for one withdrawal index may actually belong to a different withdrawal in the batch.

### Finding Description
`findMatchingWithdrawal` is explicitly documented as only matching by `assetId`: [1](#0-0) 

`describeWithdrawal` calls this matcher using only `args.withdrawalParams.assetId`, ignoring `args.index`: [2](#0-1) 

The SDK's batch orchestration (`waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises`) independently polls `describeWithdrawal` per withdrawal index in the batch, each carrying the same `intentTx` hash: [3](#0-2) [4](#0-3) 

If a caller batches two withdrawals of the same asset (e.g., two USDC withdrawals to different destination addresses in one `signAndSendWithdrawalIntent`/`processWithdrawal` call), both indices query the POA bridge with the same `tx.hash` and the same `assetId`. `Array.prototype.find` in `findMatchingWithdrawal` returns the *first* array element matching that `assetId` for both queries — so both batch entries can resolve to the identical `withdrawal` record (same `status`, same `data.transfer_tx_hash`) regardless of which of the two actual on-chain withdrawals it corresponds to.

### Impact Explanation
This breaks the equality between "status/hash reported for withdrawal index N" and "the actual on-chain outcome of withdrawal index N." A consumer of `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` (e.g., an integrator crediting users based on destination tx completion) could:
- Report both batch entries as `completed` with the *same* `transfer_tx_hash`, even though only one of the two withdrawals actually landed — leading to double-crediting the recipient tied to the erroneously matched entry, or crediting the wrong destination address/amount pairing.
- Report a `failed`/`pending` status for one entry based on another entry's real (different) outcome.

This matches the "status or hash misreport making an integrator credit or refund twice" High-impact category, since it can cause an off-chain accounting system to treat one destination-chain payment as proof of settlement for two logically distinct withdrawals.

### Likelihood Explanation
Requires no malicious actor — it's triggered by ordinary usage: any caller batching ≥2 withdrawals of the same token via `processWithdrawal`/`signAndSendWithdrawalIntent`/`waitForWithdrawalCompletion` with an array of `WithdrawalParams`. The code comment itself acknowledges "multiple withdrawals of the same token in a single transaction are not supported," but nothing in the SDK prevents callers from constructing such a batch, and no error/guard is raised when this ambiguous case occurs — it silently returns a (potentially wrong) result instead.

### Recommendation
- Either reject/validate batches containing duplicate `assetId` entries at the SDK layer (`signAndSendWithdrawalIntent`/`createWithdrawalIntents`) until the POA bridge API supports disambiguation, or
- Implement the ordering-based matching suggested in the existing code comment (sort both the API results and the withdrawal params by amount, since relayer fees are equal for same-token withdrawals, preserving relative order) so each batch index maps deterministically to the correct withdrawal record, or
- At minimum, throw an explicit error from `describeWithdrawal`/`findMatchingWithdrawal` when more than one candidate withdrawal matches the same `assetId` for a given `tx.hash`, rather than silently returning the first match.

### Proof of Concept
1. Build a batch withdrawal: `withdrawalParams = [{ assetId: "nep141:usdc.token.near", destinationAddress: A, amount: 100 }, { assetId: "nep141:usdc.token.near", destinationAddress: B, amount: 200 }]`.
2. Call `sdk.processWithdrawal({ withdrawalParams })` (or step-by-step `signAndSendWithdrawalIntent` → `waitForWithdrawalCompletion`). Both `ft_withdraw` intents settle in the same NEAR `intentTx`.
3. `createWithdrawalCompletionPromises` creates two independent promises (index 0 for A, index 1 for B), each calling `PoaBridge.describeWithdrawal` with the same `tx.hash` and `assetId: "nep141:usdc.token.near"`.
4. The POA bridge's `getWithdrawalStatus` response contains two `withdrawals` records — one for the payment to A, one for B — both with `near_token_id: "usdc.token.near"`.
5. `findMatchingWithdrawal` for index 0's call returns `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)`, i.e., the first matching element (say, A's record). Index 1's call performs the exact same lookup and also returns the first matching element (A's record), even though it should resolve to B's.
6. Result: `waitForWithdrawalCompletion` resolves index 1's promise with A's `transfer_tx_hash`/status instead of B's, misreporting the outcome of B's withdrawal to any caller relying on this result for crediting/reconciliation.

		args: WithdrawalIdentifier & { logger?: ILogger },

		// Response list is unsorted, so we match by assetId instead of index

			return { status: "pending" };

				txHash: withdrawal.data.transfer_tx_hash,

		}

		return {

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
