### Title
Webhook `shop` identity is trusted from an HTTP header that is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook payload solely by validating an HMAC computed over the raw request body, then dispatches the event to the app's handler using a `shop` value taken from a separate, unsigned HTTP header. The equality the library implicitly relies on — "the shop whose secret produced this HMAC" == "the shop named in the `shop-domain` header" — is never checked, so the two can be made to diverge.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `hmac`/`shop`/`topic` are all read independently from HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e. the body) and compares it to the `hmac` header: [3](#0-2) 

`Webhooks::Registry.process` then dispatches to the app handler using `request.shop`, `request.topic`, and `request.webhook_id`, none of which were part of the signed material: [4](#0-3) 

Because every shop that installs a given app shares the same `api_secret_key` (`Context.api_secret_key`), any merchant who has legitimately installed the app receives real, validly-signed webhooks for their own store's events. Such a merchant possesses a genuine `(raw_body, hmac)` pair. They can then send a crafted HTTP request directly to the app's public webhook endpoint, replaying that same valid body/HMAC pair, but substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header with a different, victim shop's domain. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` builds `WebhookMetadata` with `shop: request.shop` set to the attacker-chosen victim domain, causing the app to process/act on the event as if it originated from the victim tenant.

This is the direct analog of the reported bug class: a field that is acted upon (`shop`, used as the tenant identity key for dispatch) is not covered by the authenticity check (`hmac`), which is computed over a different field (`raw_body`) — mirroring `_item.withdrawalToken` (acted upon) not being checked against `request.token` (the validated identity).

### Impact Explanation
This breaks the binding "authenticated origin == tenant acted upon," letting one unprivileged installer of the app impersonate another tenant's webhook events toward the app backend, i.e. cross-tenant confusion/spoofing without ever needing the victim's credentials, access token, or the app's `client_secret`. Any host application logic that trusts `WebhookMetadata#shop` to select or mutate per-shop state can be manipulated into acting on the wrong tenant's behalf.

### Likelihood Explanation
Any merchant who can install the app (no special privilege) automatically receives at least one legitimately-signed webhook, which is all that's needed to construct the forged request; no secret material needs to be obtained or brute-forced. The forging steps are a plain HTTP replay with a modified header.

### Recommendation
Bind the shop (and preferably topic/webhook-id) into the material that is HMAC-validated, or otherwise cryptographically/contextually verify that the `shop-domain` header matches the shop the payload was actually generated for (e.g., include it in the signable string, or require callers to supply/verify the expected shop out-of-band) before dispatching to handlers in `Webhooks::Registry.process`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic to receive a real request with body `B` and header `x-shopify-hmac-sha256: H` (valid for the shared `api_secret_key`).
2. Send a raw HTTP POST to the app's public webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds (body/HMAC pair unchanged); `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim.myshopify.com"`, causing the app to process the event as belonging to the victim tenant.
