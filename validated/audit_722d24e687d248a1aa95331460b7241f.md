### Title
Permanent freezing of escrowed/bridged funds when the fixed beneficiary/refundee address is blacklisted by the underlying ERC-20 token - ([File: evm/src/apps/intentsv2/IntentsBase.sol], [File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
Several ISMP-app `onAccept`/`onPostRequestTimeout` handlers push tokens to a **beneficiary/refundee address that is fixed at order-creation or send-time** (`order.user`, or the token-transfer message's `to`/`from` fields), with no mechanism to substitute a different recipient. If that address is later blacklisted by the underlying token (e.g., USDC), the `safeTransfer` call reverts, which — because message dispatch is not wrapped in try/catch — reverts the whole batched `handlePostRequests`/`handlePostRequestTimeouts` transaction, permanently freezing the escrowed/bridged funds with no recovery path.

### Finding Description
In `IntentsBase._withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`), the beneficiary is decoded from the `WithdrawalRequest.beneficiary` field, which for a `RefundEscrow` path is set to the immutable `order.user` at order placement (see `ExtrinsicIntents.sol:297-307`, `_cancelFromDest`). The user has no way to change this address after order creation. If `order.user`'s address is later blacklisted by the input token (e.g., a USDC address gets sanctioned/frozen), `IERC20(token).safeTransfer(beneficiary, amount)` at `IntentsBase.sol:468` reverts unconditionally.

Similarly, `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout` (`sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:306-364`) transfer the underlying token to a `beneficiary`/`refundee` address extracted from the message body (`message.to`/`message.from`), again fixed at send-time with no recipient override.

Crucially, this app-level revert is not isolated: `EvmHost.dispatchIncoming` → module `onAccept` is called synchronously inside `HandlerV2.handlePostRequests` (`evm/src/core/HandlerV2.sol:204-209`) and `handlePostRequestTimeouts` (`evm/src/core/HandlerV2.sol:267-284`), with no try/catch around the call. A revert in one leaf's `onAccept` reverts the entire batch transaction, so a relayer cannot simply skip the blacklisted-recipient leaf — the message (and any others batched with it) can never be successfully delivered as long as that recipient stays blacklisted.

### Impact Explanation
Funds legitimately owed to a user/beneficiary (escrowed order inputs on cancellation/refund, or bridged tokens on a wrapped-token transfer/timeout-refund) become **permanently unrecoverable** if the fixed recipient address is blacklisted by the token contract, since there is no `recipient` override and no retry-with-different-address mechanism. This is a genuine freezing-of-funds condition reachable by any ordinary intent user or token-bridge user without any privileged action — satisfying the Medium bug class from the original report (user blocked by token cannot withdraw).

### Likelihood Explanation
Requires the token issuer to blacklist the specific `order.user`/refundee address after order placement/token send but before settlement — a real-world scenario for centralized stablecoins like USDC/USDT which have blacklist functionality and have exercised it. Given intents and token-bridge flows are open to any user with any ERC-20 configured as input/fee/output token, this is plausible, not merely theoretical.

### Recommendation
Add an explicit recipient/beneficiary override path reachable by the affected user (or the order's designated authority) analogous to the original report's recommendation — e.g., allow the order creator to specify an alternate withdrawal address at cancellation time, or wrap per-leaf module dispatch in `try/catch` so a single failing recipient cannot block the whole batch, and expose a permissionless "sweep to alternate address" fallback for stuck escrow/refund balances.

### Proof of Concept
1. User places a cross-chain intent order with `order.user = A` on the source chain via `ExtrinsicIntents`, escrowing USDC as input.
2. USDC issuer blacklists address `A`.
3. Order expires; anyone calls `cancelOrder` from destination chain, which dispatches `RefundEscrow` back to source (`ExtrinsicIntents.sol:297-307`).
4. Relayer submits the resulting `PostRequest` via `HandlerV2.handlePostRequests`, which calls `EvmHost.dispatchIncoming` → `ExtrinsicIntents.onAccept` → `IntentsBase._withdraw` (`IntentsBase.sol:451-470`), attempting `IERC20(usdc).safeTransfer(A, amount)`.
5. The transfer reverts because `A` is blacklisted; since there is no try/catch in `HandlerV2.handlePostRequests` (`evm/src/core/HandlerV2.sol:181-209`), the whole transaction reverts.
6. The escrowed USDC is now permanently stuck: the refund message can never be delivered successfully, and no code path exists to redirect the beneficiary. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
