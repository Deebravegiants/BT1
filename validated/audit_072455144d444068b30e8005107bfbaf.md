### Title
POA Bridge `describeWithdrawal` misreports status/txHash across multiple withdrawals of the same asset in one intent - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the status/txHash of a withdrawal by matching only on `assetId` instead of the specific withdrawal instance, so when a single intent contains multiple withdrawals of the same asset (e.g., same token sent to two different destination addresses), both `WithdrawalIdentifier`s resolve to the same underlying withdrawal record — reporting one withdrawal's completion status/txHash for the other, unrelated withdrawal.

### Finding Description
`createWithdrawalIdentifiers` (in `packages/intents-sdk/src/core/withdrawal-watcher.ts`) builds one `WithdrawalIdentifier` per withdrawal in a batch, each carrying a distinct `index` and the shared `intentTx` (same `tx.hash` for all withdrawals originating from one intent): [1](#0-0) 

`PoaBridge.createWithdrawalIdentifier` stores this `index` on the identifier, but `describeWithdrawal` never uses it when resolving the withdrawal's on-chain status. It fetches the POA bridge's list of withdrawals for `args.tx.hash` and calls `findMatchingWithdrawal`, which does `.find()` by `assetId` only: [2](#0-1) [3](#0-2) 

The code comment explicitly acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported") but the SDK still allows building/watching such batches (`WithdrawalIdentifier[]`, `watchWithdrawal` per identifier) without rejecting or de-duplicating them, and silently returns the *same* first-matched record for every identifier that shares the `assetId`.

This breaks the equality that a reported `WithdrawalStatus` (and its `txHash`) corresponds to the specific withdrawal being watched. Because `findMatchingWithdrawal` always returns the first array entry matching `assetId` regardless of `index`, two independent withdrawals (different destination addresses, potentially different amounts) collapse into one reported status.

### Impact Explanation
If a caller creates an intent with two withdrawals of the same POA-bridged asset (e.g., paying two different recipients in the same token), `watchWithdrawal` for *both* `WithdrawalIdentifier`s will report identical `{status:"completed", txHash}` once the first of the two underlying withdrawals completes — even though the second withdrawal (to a different address) may still be pending or may fail. An integrator relying on `sdk.waitForWithdrawalCompletion` / `processWithdrawal` to gate crediting/settlement logic would treat the second (unrelated, potentially unfinished or failed) withdrawal as completed with a txHash that does not belong to it. This matches the "status/hash misreport causing an integrator to credit or refund twice" High-impact category: the integrator could release funds or mark the withdrawal fulfilled based on a txHash and completion status that describe a different, unrelated transfer.

### Likelihood Explanation
This does not require any malicious action — it triggers whenever a normal user or integrator batches two or more withdrawals of the same asset within a single intent to different destinations, which is an explicitly supported SDK pattern (`WithdrawalParams[]`, multi-withdrawal batching described in the README, `createWithdrawalIdentifiers` looping over `withdrawalParams`). The bug is deterministic given that input shape, not probabilistic.

### Recommendation
`findMatchingWithdrawal` must disambiguate between withdrawals sharing the same `assetId` within one `tx.hash` — e.g., by using `withdrawal.data.amount`/destination address correlated with `args.withdrawalParams.amount`/`destinationAddress`, or by tracking per-asset ordinal position (`index`) consistently with the order returned by the POA API, and by rejecting/flagging batches where such correlation cannot be made unambiguous instead of silently returning the first match for every identifier.

### Proof of Concept
1. Build an intent with two `WithdrawalParams` entries for the same `assetId` (e.g., `nep141:usdc.omft.near`) but different `destinationAddress` values.
2. Call `createWithdrawalIdentifiers` — this produces two `WithdrawalIdentifier`s with `index: 0` and `index: 1`, same `tx.hash`.
3. Call `watchWithdrawal` for both identifiers concurrently.
4. In `PoaBridge.describeWithdrawal`, `getWithdrawalStatusWithRetry` returns the POA API's withdrawal list for that `tx.hash` (containing 2 entries, one per real withdrawal). `findMatchingWithdrawal` runs `.find(w => nep141:${w.data.near_token_id} === assetId)` for each call — since both entries share the same `assetId`, `.find()` returns the identical first entry for both identifier's calls.
5. Once the first underlying withdrawal transitions to `COMPLETED`, both watchers resolve to `{status:"completed", txHash: withdrawal.data.transfer_tx_hash}` using the *same* record — the second, distinct withdrawal is reported completed with the wrong txHash even if it is still pending or has failed.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
