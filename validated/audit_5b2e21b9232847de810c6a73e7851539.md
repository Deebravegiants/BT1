Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant spoofing in `ShopifyAPI::Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` validates a webhook by checking the HMAC over the raw request body only, but the `shop` (and `topic`, `webhook_id`, `api_version`) values that are handed to the host application's webhook handler are taken directly from unauthenticated HTTP headers. Since Shopify signs webhooks using the app's single shared `client_secret` across every shop that installs the app, any merchant who can trigger a webhook to their own store can also forge the `shop-domain` header to any other shop's domain while keeping a valid HMAC, causing the gem to dispatch attacker-controlled tenant identity to the handler.

### Finding Description
Webhook signature validation is delegated to `Utils::HmacValidator.validate`, which calls `Request#to_signable_string`: [1](#0-0) 

This returns only `@raw_body` — none of the identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) are part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then builds the metadata dispatched to the host application's handler directly from these unsigned header accessors: [3](#0-2) 

The `WebhookMetadata` struct that the handler receives carries `shop` straight from the `shop-domain` header: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to handler`. Because the HMAC only covers the body, this equality does not hold — the `shop` value is fully attacker-controllable independent of what was cryptographically signed. Since the HMAC secret (`Context.api_secret_key` / `client_secret`) is the same for every shop that installs the app, a merchant on their own store can receive a legitimate, correctly-signed webhook to their own tunnel/endpoint, compute the same valid HMAC for a body of their choosing (they know the app's `client_secret` indirectly is not needed — Shopify will sign it for them on delivery to their own registered endpoint, or they can replay/resend the exact `body`+`hmac` pair they legitimately received), and then submit that HMAC-valid `(body, hmac)` pair to the app's shared webhook endpoint with an arbitrary `shop-domain` header pointing at a victim shop. `Registry.process` accepts it as valid and calls the handler with `data.shop` set to the victim's domain and attacker-chosen `body`, `topic`, etc.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing: `Registry.process` is the gem's own trust boundary for turning an HTTP request into a validated, shop-scoped event, yet the shop identity it exposes to the handler is not bound to the cryptographic proof it just checked. Any host application that uses `request.shop` (as returned by this gem, via `WebhookMetadata#shop`) to select or act on tenant data — the normal, documented usage pattern — can be made to perform actions against, or record data for, a different merchant's shop than the one that actually authorized/sent the payload. This is a cross-tenant identity-confusion vulnerability rooted entirely in this gem's `Webhooks::Request`/`Registry` implementation, not a misuse of a documented API.

### Likelihood Explanation
Exploitation only requires the attacker to be an ordinary merchant capable of installing the app on their own store (to receive at least one legitimately signed webhook) or to intercept their own webhook traffic (which they fully control), then replay/re-send the `(raw_body, hmac)` pair to the app's public webhook endpoint with a forged `shop-domain` header. No access to the app's `client_secret`, another merchant's token, or any privileged access is required — the shared-secret HMAC scheme combined with the header not being covered makes this directly and cheaply exploitable by any unprivileged internet user who is (or was) a legitimate installer of the target app.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed/verifiable material, or otherwise cryptographically bind the `shop` value asserted by the header to the HMAC-verified payload before it is handed to the application. At minimum, `Request#to_signable_string` should incorporate the `shop-domain` header (matching Shopify's actual webhook HMAC scheme, which historically has been body-only per Shopify's own webhook spec, so alternatively the gem should document/require that consuming applications independently verify `shop` against their own installed-shop registry) — but from the gem's perspective, the safer fix is to reconstruct/validate `shop` using an authenticated source rather than trusting the raw header field passed into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers/receives a webhook (or captures one already delivered) with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — note `client_secret` is the same across all merchants of this app.
2. Attacker crafts an HTTP POST to the app's webhook endpoint with:
   - body `B` and `x-shopify-hmac-sha256: H` (unchanged, so HMAC validation in `Utils::HmacValidator.validate` passes — see `lib/shopify_api/utils/hmac_validator.rb:12-22`)
   - `x-shopify-shop-domain: victim.myshopify.com` (forged, attacker's choice)
   - `x-shopify-topic`: chosen to match a registered handler.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers without validating that `shop` matches anything signed (`lib/shopify_api/webhooks/request.rb:45-63`).
4. `Registry.process` validates HMAC successfully (`lib/shopify_api/webhooks/registry.rb:190`), then calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`).
5. The host application's webhook handler processes the event as if it legitimately originated from `victim.myshopify.com`, even though the victim shop never sent or authorized this webhook.
