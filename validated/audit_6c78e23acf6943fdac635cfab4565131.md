### Title
Webhook Shop-Domain Impersonation via HMAC Scope Gap - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking `Utils::HmacValidator.validate(request)`, which validates the raw request body against the shared `client_secret`. However, `Webhooks::Request#to_signable_string` returns only `@raw_body`, so the `shop`, `topic`, `webhook_id`, and `api_version` values — all taken from unauthenticated HTTP headers — are never part of the signed content, yet they are trusted and forwarded to the app's handler as the tenant identity.

### Finding Description
`HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhooks, `to_signable_string` is defined to return only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from HTTP headers that are never mixed into the signed bytes: [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof of the whole request's authenticity and then dispatches to the handler using the unauthenticated `request.shop`: [3](#0-2) 

This breaks the intended identity binding `hmac_valid(body) == authentic(shop, topic, body)`. In reality `hmac_valid(body)` only proves `authentic(body)`; `shop` is asserted, not verified, by the same signature. Since the API secret (`client_secret`) is shared across every shop that installs the app, any unprivileged user can install the app on their own (e.g. free development) store, receive a legitimately signed webhook for that store, and then replay the identical raw body with a forged `X-Shopify-Shop-Domain` header naming a different, victim shop. The signature is unchanged (it never covered the header), so `HmacValidator.validate` still returns `true`, and `WebhookMetadata.new(shop: request.shop, ...)` is built with the attacker-chosen shop, which is exactly the value host applications use to look up the tenant/session record to act on.

### Impact Explanation
This is a cross-tenant identity binding violation: the gem allows an authenticated-looking webhook to be attributed to an arbitrary shop domain that never sent it. Host applications built following this gem's documented pattern of trusting `WebhookMetadata#shop` for tenant dispatch (as shown in `docs/usage/webhooks.md`) can be tricked into applying webhook side effects (data updates, `shop/redact` GDPR flows, mandatory compliance topics, etc.) against a shop the attacker does not own, meeting the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Exploitation only requires the attacker to install the same public app on a shop they control (a free action for any Shopify Partner/dev store) and capture one legitimate webhook delivery, since the shared `client_secret` HMAC only signs the body and never binds it to the sender's shop. No access to the app's `client_secret`, access tokens, or victim credentials is needed.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signed content (or independently verify the `shop` header against a known/allow-listed shop for the topic/subscription) before trusting `request.shop` in `Registry.process`, rather than relying on body-only verification via `Webhooks::Request#to_signable_string`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) and capture the raw POST body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed over `B` using the shared `client_secret`).
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only and matches `H`, so `Registry.process` succeeds and invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host app to process/act on data as if it came from `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
