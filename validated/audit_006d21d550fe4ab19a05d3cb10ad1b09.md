### Title
Webhook `shop`/`topic`/`webhook-id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from only the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` fields used by `Registry.process` to route and attribute the webhook are read from unsigned HTTP headers.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` and compares its HMAC against the `hmac` value, but for `Webhooks::Request` `to_signable_string` returns only `@raw_body` [1](#0-0) . The `hmac` itself is decoded from the `hmac-sha256` header [4](#0-3) , and `shop`, `topic`, `api_version`, `webhook_id` are all likewise read straight from headers, none of which are part of the signed payload [2](#0-1) .

`Registry.process` trusts these unsigned header-derived fields to select the registered handler (`@registry[request.topic]`) and to construct the `WebhookMetadata` (including `shop:`) delivered to the app's business logic [3](#0-2) .

This breaks the intended binding: `HMAC(secret, raw_body) == received_hmac` should imply `(shop, topic, body)` as a whole is authentic and unmodified, but the equality actually only proves the body bytes are authentic — the shop/topic attribution is not bound to that signature at all.

### Impact Explanation
An unprivileged attacker who can obtain any single valid `(raw_body, hmac)` pair signed with the app's real secret — for example by installing the app on their own development/test shop and receiving one legitimate webhook delivery for that shop — can replay that exact body+HMAC while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) to name a victim merchant's shop domain. `Registry.process` will accept it (HMAC still validates, since only the body is checked) and dispatch the attacker-controlled body to the app's handler labeled as coming from the victim shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up the merchant's session/store record and writing incoming data), this results in cross-tenant data contamination or being tricked into acting on behalf of another merchant — a cross-tenant access issue.

### Likelihood Explanation
Requires the attacker to already have a legitimately signed webhook body from *some* shop instance of the app (trivial to obtain by installing on any dev store) and requires the host app to trust `WebhookMetadata#shop`/`#topic` for tenant-sensitive logic, which is the documented intended use of this field.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` header values in the signable string used for HMAC verification (mirroring how Shopify's OAuth `AuthQuery#to_signable_string` binds `shop`, `host`, `state`, etc. into the signature [5](#0-4) ), or otherwise cryptographically bind these header fields to the signed body so that HMAC validity implies attribution validity, not just body integrity.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture one legitimate webhook delivery, `raw_body` and its `X-Shopify-Hmac-Sha256` value — these are validly signed with the app's real `api_secret_key`.
2. Replay the exact same HTTP request to the app's webhook endpoint, but change the `X-Shopify-Shop-Domain` header to `victim.myshopify.com` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only and succeeds because the body is unchanged [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` where `shop` is `victim.myshopify.com` even though the payload actually originated from and was signed for `attacker.myshopify.com` [7](#0-6) .
