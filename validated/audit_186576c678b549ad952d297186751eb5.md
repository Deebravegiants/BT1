### Title
Webhook shop-domain attribution is not bound to the HMAC signature, allowing cross-tenant event spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC verified by `Utils::HmacValidator.validate` binds nothing but the byte content of the payload. The `shop` value that the registry hands to application webhook handlers is read from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is completely outside the signed material. Since Shopify signs webhooks with a per-app secret shared across every shop that installs the app, a valid HMAC only proves "this body was signed with our app secret at some point by Shopify (for some shop)" — it does not prove "this body belongs to the shop named in this request's header."

### Finding Description
`Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) calls `verifiable_query.to_signable_string` and HMAC-SHA256-compares it against the `hmac` value: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from headers, not from the signed string: [3](#0-2) 

`Registry.process` validates only the HMAC of the body and then forwards `request.shop` (the unauthenticated header) directly to the application's webhook handler as the tenant identifier: [4](#0-3) 

The identity binding broken here is: **HMAC-verified bytes (body only) ≠ bytes acted on for tenant attribution (body + shop header)**. Because Shopify's webhook secret is the single app-level `api_secret_key` shared by *all* installed shops (the same key validated in `hmac_validator_test.rb` and used throughout OAuth), any shop that has installed the app can capture one of its own legitimately-signed webhook deliveries (same secret, same signature scheme for every tenant) and resend it to the app's webhook endpoint with the `shop-domain` header swapped to a different, victim shop. `HmacValidator.validate` will still pass, because the signature only covers the body — which the attacker did not need to change. `Registry.process` will then invoke the app's handler with `WebhookMetadata.new(shop: <victim-shop>, body: ..., topic: ..., ...)`, causing the host application to process/store data as if it belonged to the victim tenant.

### Impact Explanation
This crosses a tenant boundary: an unprivileged party who merely holds a developer/staff account on shop A (a customer of the app, i.e., "unprivileged" relative to other tenants of the multi-tenant app) can produce network traffic that the library's own trust primitive (`Utils::HmacValidator`) validates as authentic, yet which is attributable to an arbitrary shop B of the attacker's choosing. Any host application that trusts `WebhookMetadata#shop` (exactly as documented/demonstrated in `test/webhooks/registry_test.rb`) for tenant-scoped side effects (writing to shop B's data store, revoking shop B's resources, mandatory GDPR redact processing, etc.) is exposed to cross-tenant data corruption/exfiltration triggered purely by an unprivileged actor replaying their own genuinely-signed webhook body under a spoofed shop header — without needing the `client_secret`, an access token, or any credential belonging to the victim shop.

### Likelihood Explanation
Exploitation only requires: (1) the attacker's own shop being a legitimate installer of the target app (any merchant can install most public apps), (2) capturing one webhook delivery Shopify sends to their own shop (visible in their own server logs / ngrok tunnel), and (3) replaying that HTTP request to the app's public webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header value changed. No cryptographic material needs to be forged since the body (the only signed component) is reused verbatim. This is a low-effort, protocol-level manipulation entirely reachable through the gem's own `Webhooks::Registry.process`/`Webhooks::Request` API as documented and tested.

### Recommendation
Bind the shop (and ideally topic/api_version/webhook_id) into the value that is cryptographically verified, or otherwise cross-check the header-derived `shop` against an independently trusted source (e.g., require callers to pass the expected shop for the registered handler, or validate that `request.shop` matches a shop known to have an active session/install record) before invoking the handler. At minimum, `Utils::HmacValidator` should be extended so that webhook signature validation is not satisfied by a byte-for-body match alone when the consuming code also trusts unauthenticated headers for tenant attribution.

### Proof of Concept
1. Shop A installs the target app; the app registers a webhook handler via `ShopifyAPI::Webhooks::Registry.add_registration`.
2. Shopify delivers a legitimate webhook to the app for shop A:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw body, computed with the app's api_secret_key>
   x-shopify-shop-domain: shop-a.myshopify.com
   x-shopify-webhook-id: ...
   Body: {"id": 123, ...}
   ```
   The attacker (who controls shop A) captures this raw request.
3. The attacker resends the identical body and HMAC header, but changes only:
   ```
   x-shopify-shop-domain: shop-b.myshopify.com
   ```
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks the (unmodified) raw body against the (unmodified) HMAC: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: {"id": 123, ...}, ...)` and the host application performs shop-B-scoped processing driven entirely by attacker-supplied, unauthenticated header data.
