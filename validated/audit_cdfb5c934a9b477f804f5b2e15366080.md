## Title
Webhook `shop` and `topic` fields are excluded from HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC computed by `Utils::HmacValidator` binds nothing but the body bytes. The `x-shopify-shop-domain` and `x-shopify-topic` headers — which are trusted downstream to route and attribute the webhook — are never covered by the signature. This is the exact bug class in the reported Timelock issue: a value that is *acted upon* (here, the tenant/shop identity and topic used for routing) is not part of the data that is cryptographically bound by the signature check.

## Finding Description
`Webhooks::Request` reads `shop`, `topic`, and `hmac` from separate HTTP headers, but only `@raw_body` is fed into the HMAC computation: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header value: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` and `request.topic` to dispatch to the registered handler and to build `WebhookMetadata`: [3](#0-2) 

The identity binding that should hold is:
`hmac == HMAC(secret, shop ∥ topic ∥ body)` and therefore `request.shop == <shop that Shopify actually generated this HMAC for>`.

In this implementation the binding actually enforced is only:
`hmac == HMAC(secret, body)`,
so `request.shop` (and `request.topic`) can be anything the caller of `Registry.process` supplies in the headers, independent of what value the signature was actually computed over. For comparison, the correctly-bound field in the OAuth flow (`AuthQuery#to_signable_string`) *does* include `shop`/`host` in the signed payload: [4](#0-3) , showing the gem is capable of, but fails to apply, this binding for webhooks.

## Impact Explanation
An unprivileged internet user who can obtain any single genuine, HMAC-valid webhook delivery for the app (e.g., by installing the target app on their own free/dev store and letting Shopify deliver a real webhook to their own endpoint, or by intercepting any webhook body/HMAC pair they are legitimately entitled to receive) can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value (a victim's shop) and/or an arbitrary `x-shopify-topic` header. Because `Registry.process` never re-derives or checks these fields against the signature, the forged request passes `HmacValidator.validate` and is routed to the handler as `WebhookMetadata` attributed to the attacker-chosen shop and topic. This crosses the tenant boundary: data/processing intended to be scoped to one merchant's webhook can be attributed to another merchant, enabling cross-tenant data corruption or triggering of shop-specific business logic (e.g., `app/uninstalled`, `shop/redact`, order/customer processing) under an impersonated shop identity.

## Likelihood Explanation
Likelihood is high for any attacker who can obtain a single legitimate webhook (trivial for any app that grants webhooks upon install, since the attacker can install the app on their own shop). No access to `api_secret_key`, access tokens, or privileged accounts is required — only a replay of an already-authenticated payload with modified, unauthenticated headers.

## Recommendation
Include the `shop`, `topic`, and `webhook_id`/`api_version` values in the string that is HMAC-verified (or otherwise cryptographically bind them, e.g., via a signed envelope), so `Utils::HmacValidator.validate` fails whenever these header values do not match what Shopify actually signed. At minimum, `Request#to_signable_string` should incorporate the shop and topic headers rather than only the raw body.

## Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; Shopify delivers a legitimate webhook with a valid `x-shopify-hmac-sha256` for some body `B`.
2. Attacker replays the same `POST` to the app's webhook endpoint, keeping `body = B` and `x-shopify-hmac-sha256` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `Webhooks::Request.new` parses these headers without validating them against the signed content: [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B)`: [3](#0-2) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, even though the payload was never actually generated for that shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
