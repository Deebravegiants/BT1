### Title
D3Oracle-style vulnerability: `SimplexPaymaster._getOraclePrice` trusts a Chainlink answer stuck at its `minAnswer`/`maxAnswer` circuit-breaker bound instead of validating it against price bounds - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` fetches `latestRoundData()` from a Chainlink `AggregatorV3Interface` and only validates that the answer is positive and not stale. It never checks the answer against the feed's configured `minAnswer`/`maxAnswer` circuit-breaker bounds, mirroring the exact class of bug reported against DODO's `D3Oracle.getPriceFromFeed`. [1](#0-0) 

### Finding Description
`_getOraclePrice` is used by `_tokenPrice`, which is called from `_fetchDetails` — a `PaymasterERC20` hook invoked during `_validatePaymasterUserOp` for every submitted `PackedUserOperation` — and also from the treasury-gated `swapAndDeposit`. [2](#0-1) [3](#0-2) 

When either the native/USD feed or a registered token/USD feed experiences an extreme market move (e.g. a de-peg/crash like LUNA), Chainlink aggregators clamp the reported `answer` to the feed's `minAnswer` (or `maxAnswer`) rather than reverting or reporting the true price. `_getOraclePrice` treats that clamped value as legitimate as long as it is `> 0` and fresh, computing `tokenPrice` from it via `_tokenPrice`: [4](#0-3) 

This is functionally identical to the reported `D3Oracle.getPriceFromFeed` issue: no `require(price < maxPrice)` / `require(price > minPrice)` checks exist anywhere in `_getOraclePrice`.

### Impact Explanation
Any address can submit a `PackedUserOperation` through the EntryPoint that uses this paymaster (mode `0x00` permit or mode `0x02` Permit2) — this is an unprivileged, single-transaction-reachable path. If the tokenOracle (or nativeOracle) answer is pinned at its circuit-breaker bound while the true market price has moved far past it, `_tokenPrice` returns a stale/incorrect exchange rate between the gas token and native currency. A user operation could then pay a drastically undervalued amount of the ERC-20 token for gas (theft of paymaster funds/native deposit), or conversely be forced to overpay, depending on the direction of the mispricing and which side of the ratio is affected. Since `_prefund`/`_erc20Cost` compute the exact token amount to pull from the user based on this price, an attacker can drain the paymaster's stablecoin float relative to its native EntryPoint deposit by transacting while a feed is clamped.

### Likelihood Explanation
This requires the underlying Chainlink feed to actually be in a clamped state (feeding minAnswer/maxAnswer), which happens during genuine extreme volatility/de-peg events — not attacker-controlled, but a known, recurring real-world occurrence (as cited in the original report, e.g., LUNA/Venus). Given `SimplexPaymaster` is designed to hold stablecoins with governance-configured Chainlink feeds, and paths reaching the flawed pricing are open to any UserOp sender, exploitation likelihood is realistic whenever a configured feed is stressed.

### Recommendation
Extend `_getOraclePrice` (and the `swapAndDeposit` pricing path) to fetch and enforce the aggregator's `minAnswer`/`maxAnswer` bounds — either by querying `aggregator.minAnswer()/maxAnswer()` (via the `AggregatorV2V3Interface`/proxy's underlying aggregator) or by configuring per-feed min/max bounds in `TokenConfig`/`Params` at registration time, and reverting if `answer` is at or beyond those bounds, consistent with the report's suggested `require(price < _maxPrice)` / `require(price > _minPrice)` checks.

### Proof of Concept
1. Governance registers `usdc` with a Chainlink `AggregatorV3Interface` whose configured circuit-breaker `minAnswer` is, say, `0.10 USD` (in 8 decimals: `1e7`).
2. USDC de-pegs catastrophically to `$0.01`; the aggregator, per Chainlink's design, keeps returning `answer = 1e7` (the clamped `minAnswer`) instead of the true `$0.01`, and `updatedAt` stays fresh.
3. A user submits a `PackedUserOperation` with mode `0x00` targeting `usdc` as the gas token. `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` accepts the clamped `1e7` answer (passes `answer > 0` and freshness checks) and computes `tokenPrice` as if USDC were worth 10x its real market value.
4. `_erc20Cost` charges the user roughly 10x less USDC than the paymaster's real-value payout for the same gas, letting an attacker drain the token/native ratio the paymaster relies on for solvency, using ordinary UserOps with no special privilege.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
