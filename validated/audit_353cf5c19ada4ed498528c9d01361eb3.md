Confirmed: `VerifiableQuery#to_signable_string` is the only thing HMAC-verified, and for webhooks (`lib/shopify_api/webhooks/request.rb`) that method returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers.

### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and is validated by `Utils::HmacValidator.validate` inside `Registry.process`. The HMAC is computed only over `to_signable_string`, which is the raw JSON body. The `shop` attribute — the value used by the host application to identify *which tenant* the webhook belongs to — comes from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header and is never included in the signed bytes.

### Finding Description
`Registry.process` performs exactly one authenticity check before dispatching to the app's handler: [1](#0-0) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` to compute the expected signature: [2](#0-1) 

For webhooks, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding to the HMAC: [4](#0-3) 

After the HMAC check passes, `request.shop` (header-derived, unverified) is handed to the app's handler as the tenant identifier: [5](#0-4) 

The equality the gem is supposed to guarantee is:
`shop covered by valid HMAC == shop used to route/attribute the webhook payload`

In this implementation that equality does not hold: `shop (header, unauthenticated) ≠ shop (bytes covered by HMAC, which is empty for this field)`. Any request whose **body** carries a valid HMAC for the configured `api_secret_key` — a signature obtainable by an attacker who legitimately installs the app on a shop they control and receives real webhook deliveries for that shop — remains valid HMAC-wise even after the attacker swaps the `x-shopify-shop-domain` header to a different (victim) shop's domain and replays it to the app's public webhook endpoint. `Registry.process` will accept it and call the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`, attributing attacker-controlled/replayed data to a shop the attacker does not own.

### Impact Explanation
Applications built on this gem commonly use the `shop` field from `WebhookMetadata` to look up the tenant record and apply the webhook body to that tenant's data (e.g., updating order/customer state, revoking access on `app/uninstalled`, or reacting to `shop/redact`). Because `shop` is not authenticated by the HMAC, an attacker who can obtain any validly-signed webhook body (e.g., by installing the app on their own store to receive a legitimate signed webhook of a chosen topic) can relabel it to a victim shop domain and have the host application process it as if it originated from that victim tenant — a cross-tenant confusion/access issue rooted directly in this gem's verification logic.

### Likelihood Explanation
Requires network reach to the app's public webhook endpoint (inherent to how webhooks work) and the ability to obtain one validly-signed webhook body for the same app (trivial for anyone who can install the app on any store, including a free/trial store, since app installation itself is unprivileged from the platform's perspective). No `api_secret_key`, access token, or credential theft is required — the attacker only replays a header value alongside a body+HMAC pair that Shopify itself produced for a different, attacker-controlled shop.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the signed/verified material, or otherwise cryptographically bind them to the HMAC-covered payload, e.g. by having `to_signable_string` incorporate the shop-domain header, or by requiring host applications to double-check `shop` against an independently known active installation before trusting it. At minimum, document prominently that `request.shop` is unauthenticated and must not be used as the sole tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a store the attacker controls) and configures a webhook subscription for a topic of interest (e.g., `orders/create`).
2. Shopify delivers a webhook to the app with body `B`, and header `x-shopify-hmac-sha256 = HMAC(api_secret_key, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays this exact `B` and HMAC value to the app's public webhook endpoint, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes the HMAC over `B` only, which still matches, so `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, even though Shopify never issued this webhook for `victim-shop.myshopify.com`. # typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
