### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are parsed from unauthenticated headers while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`), `topic`, `api_version`, and `webhook_id` directly from HTTP headers, but `Utils::HmacValidator.validate` only verifies the HMAC over `to_signable_string`, which returns solely `@raw_body`. The `shop` field used downstream to dispatch webhook data to the app's handler is never covered by the HMAC signature.

### Finding Description
`Webhooks::Registry.process` gates handling on `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the JSON body bytes — never the headers: [3](#0-2) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers via `shopify_header`, with no cryptographic binding to the signed body: [4](#0-3) [5](#0-4) 

After HMAC validation passes, `Registry.process` builds `WebhookMetadata` directly from `request.shop` (the unauthenticated header) and hands it to the app's handler as the tenant identity for that event: [1](#0-0) [6](#0-5) 

The broken identity binding is:
`HMAC(secret, raw_body) == received_hmac` is treated as equivalent to `shop-domain header == authenticated tenant`, when in fact only `raw_body` is bound by the signature — `shop`, `topic`, `webhook_id`, and `api_version` are bytes *parsed* but never bytes *verified*.

### Impact Explanation
Because the app's `client_secret`-derived HMAC key is shared across every shop that installs the app, any unprivileged user who operates (or has installed) a shop with the app can obtain a genuine `(raw_body, hmac)` pair for a webhook topic they control (e.g. by triggering `orders/create` or any topic in their own store, or by using Shopify's webhook-resend/log tooling to capture a valid delivery). They can then replay that exact `raw_body`/`hmac` pair directly to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with a victim shop's domain or an arbitrary value. `HmacValidator.validate` will still succeed because it only checks `raw_body` against the shared secret, and `Registry.process` will dispatch the (attacker-controlled) body to the handler tagged with the spoofed `shop`. Any host application that uses `WebhookMetadata#shop` as a tenant key (looking up sessions, writing shop-scoped records, gating access) can be tricked into attributing attacker-supplied event data to a shop the attacker doesn't own — a cross-tenant data/trust confusion condition.

### Likelihood Explanation
High. Exploitation requires no privileged credentials, no access token, and no interaction with `api_secret_key` beyond what any app-installing merchant already has via legitimate use of the app (triggering their own webhook events). It is a straightforward header substitution on a normal HTTP POST to the public webhook endpoint, fully reachable through this gem's own `Webhooks::Request`/`Registry.process` code path with no reliance on the host app ignoring documented behavior — the gem itself never validates `shop` against the signed payload.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, e.g. by having the host confirm `request.shop` against a per-tenant secret/session before trusting it), so `HmacValidator.validate` authenticates the full identity tuple, not just the JSON body bytes.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook event (e.g. `orders/create`), capturing the genuine `raw_body` and the `shopify-hmac-sha256` header Shopify sent — both are valid for the app's shared `client_secret`.
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and `shopify-hmac-sha256`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com` from the header. [7](#0-6) 
4. `Utils::HmacValidator.validate(request)` computes HMAC over `raw_body` only and it matches, so validation succeeds. [2](#0-1) 
5. `Registry.process` dispatches `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker's data, ...)` to the app's handler, which processes attacker-controlled data under the victim's tenant identity. [1](#0-0)
