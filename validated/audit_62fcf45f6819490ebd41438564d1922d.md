### Title
Residual balances left in the CallDispatcher after executing an order's output calldata are permanently misappropriated as protocol dust instead of being returned to the order's beneficiary - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._execute()` sweeps every token/native balance left in the `CallDispatcher` after running the user-supplied `order.output.call` and unconditionally credits it to the protocol as `DustCollected` dust. Any value the call legitimately produces for the beneficiary (positive slippage, leftover swap proceeds, refunds from a DeFi action, etc.) is captured by the protocol rather than returned to the order's beneficiary, mirroring the Aura "extra rewards get swept to the wrong party" bug class.

### Finding Description
`_execute()` is invoked from both `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol`) and `_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`) after the solver has already paid the beneficiary the required output amounts directly. `order.output.call` is arbitrary calldata chosen by the user at order-placement time (part of the signed `Order` struct) and is executed through the `CallDispatcher` to enable composable post-fill actions (e.g. swapping the delivered output token, depositing into a vault, etc.): [1](#0-0) 

The function measures whatever balance is left on `dispatcher` after the call and treats 100% of it as `DustCollected` protocol dust, sweeping it back to `address(this)` (the gateway, i.e. protocol-owned funds later withdrawn via governance `SweepDust`): [2](#0-1) 

There is no attempt to distinguish "true leftover that belongs to nobody" from value that the executed call legitimately generated for the beneficiary (e.g., a DEX swap embedded in `order.output.call` that returns more tokens than consumed, or a refund from a lending/vault action). Because the beneficiary has no other path to reclaim funds that pass through the `CallDispatcher` during `_execute`, any positive by-product of the user's own calldata is unconditionally diverted to the protocol.

This is structurally the same root cause as the Aura `wstETH`/`OHM` extra-rewards bug: a fixed accounting assumption ("balance in dispatcher after action == protocol dust") misclassifies value that actually belongs to the party who initiated the action (the beneficiary/user), and permanently redirects it to a different party (the protocol treasury).

### Impact Explanation
Any user who sets `order.output.call` to perform a composable post-fill action that can yield residual value in the `CallDispatcher` (positive slippage on an embedded swap, a partial refund from a deposit/withdraw sequence, rounding remainders, etc.) permanently loses that value to the protocol. This is a direct, reachable loss of funds for an unprivileged order placer — no special privileges are required, only crafting `order.output.call` such that it can legitimately produce excess value. Given `IntentGatewayV2`/`IntentsBase` is a core, unprivileged, user-facing dispatch path (any user can place an order with output calldata), this qualifies as a Medium-severity fund-loss issue.

### Likelihood Explanation
Composable output calldata is an explicitly supported and advertised feature (`docs/content/developers/evm/intent-gateway/overview.mdx` "Calldata" section, `_execute`'s own doc comment). Any real-world usage of this feature that involves a swap, redemption, or other action with even slight positive slippage will trigger the misdirection on every such fill, making this a routine occurrence rather than an edge case.

### Recommendation
Do not attribute 100% of the post-call residual balance in the `CallDispatcher` to the protocol. Instead:
- Track balances before and after strictly around the action(s) that are actually meant to consume the required output amount, and forward any genuine residual (from the call the beneficiary itself configured) back to `beneficiary` rather than to the gateway/protocol.
- If a "dust to protocol" policy is still desired for truly unattributable leftovers, it should only apply to amounts that cannot be traced to the beneficiary's own calldata execution, and this should be documented/audited explicitly, consistent with how `surplusShareBps` splits solver overpayment between beneficiary and protocol elsewhere in the same file (`_splitSurplus`).

### Proof of Concept
1. User places an order with `order.output.call` set to a `CallDispatcher` sequence that: (a) receives the delivered output token, (b) swaps it via a DEX for a second token, where the swap intentionally/naturally returns slightly more of the second token than consumed (positive slippage), and (c) does not withdraw that surplus explicitly.
2. Solver fills the order; `_fillCrossChain`/`_fillSameChain` pays the beneficiary the required output amount, then calls `_execute(order, outputsLen)`.
3. `_execute` dispatches `order.output.call`, observes the leftover second-token balance on `dispatcher`, emits `DustCollected(token, balance)`, and sweeps it to `address(this)` (the `IntentGatewayV2` contract) — see `evm/src/apps/intentsv2/IntentsBase.sol` lines 507-528.
4. The beneficiary never receives this surplus; it sits in the gateway as "protocol dust" until swept to treasury via governance `SweepDust` (`evm/src/apps/IntentGatewayV2.sol` `SweepDust` handling), permanently diverting funds that were produced by the beneficiary's own configured action.

    /**
     * @dev Executes arbitrary calldata attached to an order's output via the CallDispatcher.
     * After dispatching the calls, any residual token balances left on the dispatcher
     * are swept back to this contract and accounted for as protocol dust.
     *
     * This enables composable order fulfillment — solvers can route through DEXes,
     * lending protocols, or other DeFi primitives as part of filling an order.
     *
     * @param order The order containing the output calldata to execute.
     * @param outputsLen The number of output assets to sweep after execution.
     */
    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }
