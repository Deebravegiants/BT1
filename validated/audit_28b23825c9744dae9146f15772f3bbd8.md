### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies the webhook HMAC before dispatching to the app's handler, but the HMAC signature only covers the raw request body. The `shop` attribute — taken from the `x-shopify-shop-domain`/`shopify-shop-domain` header and passed straight into the handler as the tenant identity — is never included in the signed bytes. Any bytes that produce a valid signature for one shop will also validate for any other value of that header, breaking the binding `signed_bytes == acted_upon_bytes` that the HMAC check is supposed to enforce.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read from an HTTP header that is completely independent of the signed body: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (i.e. only the body) against the request's `hmac`, and then — once that check passes — forwards `request.shop` directly to the app's webhook handler as the authoritative tenant identifier, without any further check that this shop matches the body or any known/expected value: [3](#0-2) 

`Utils::HmacValidator.validate` computes and compares the HMAC purely over `verifiable_query.to_signable_string`: [4](#0-3) 

Because the same `api_secret_key` is shared by the app across all installed shops (it is a per-app secret, not per-shop), any entity that can obtain one validly-signed webhook body/HMAC pair for their own shop (e.g., by installing the public app on a shop they control and receiving real webhook deliveries) can replay that exact `raw_body` + `hmac` to the app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header. The HMAC check in `HmacValidator.validate` will still pass — it never looks at the shop header — and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain.

The binding that should hold is:
```
HMAC(api_secret_key, bytes_verified) == HMAC(api_secret_key, bytes_the_app_acts_on)
```
Here, `bytes_verified = raw_body` while `bytes_the_app_acts_on` implicitly includes the `shop` header consumed by the handler — these are not the same bytes, so the equality is broken.

### Impact Explanation
Host applications built on this gem's `Webhooks::Registry.process`/`WebhookHandler` interface are expected to trust `WebhookMetadata#shop` as the identity of the shop the event pertains to (it is explicitly surfaced as the tenant identifier in the metadata struct alongside `topic` and `body`). Since it is not covered by HMAC verification, a data-owning attacker (any entity permitted to install the app, i.e. an unprivileged internet user relative to other merchants) can forge webhook deliveries that appear to originate from a victim shop, causing cross-tenant data confusion/corruption in the host application (e.g., triggering redaction, resource updates, or business logic keyed on `shop` for a shop the attacker does not control). This matches the "Critical – cross-tenant access" category, since the trust boundary between tenants (shops) is broken by a credential (the shared `api_secret_key`) that any installer legitimately possesses for their own tenant.

### Likelihood Explanation
Likelihood is high: obtaining a valid signed body+HMAC pair only requires installing the app on any shop (including one the attacker controls) and triggering any webhook topic the app subscribes to — no special access or secret leakage is needed. Replaying that payload with a modified `shop-domain` header against the app's public webhook endpoint requires no further authentication.

### Recommendation
Include the shop domain (and any other header claimed as the event's tenant identity) in the HMAC-signed material, or independently verify that `request.shop` corresponds to a shop with a known/expected session/access token in the host application's session store before treating it as trusted, rather than passing the raw header value straight through as tenant identity in `WebhookMetadata`.

### Proof of Concept
1. Install the app (as any user) on `attacker-shop.myshopify.com`; capture a real webhook delivery — raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (both signed with the shared `api_secret_key`).
2. Send a POST to the app's webhook endpoint with the identical body `B` and header `H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) verifies `H` against `to_signable_string` = `B` only, and passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host app to process the event as if it came from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
