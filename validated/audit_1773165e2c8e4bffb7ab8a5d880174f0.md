## Title
CORS Origin Allowlist Bypass via Unanchored Suffix Match on Wildcard Domains - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` in `core/services/gateway/network/httpserver.go` matches wildcard CORS entries (e.g. `https://*.example.com`) by stripping the `*.` prefix and calling `strings.HasSuffix(originHost, allowedHost)`, without verifying that a `.` label boundary (or exact equality) precedes the matched suffix. This lets an attacker who registers an unrelated domain that merely ends in the same character sequence (e.g. `attacker-example.com` against allowed `*.example.com`) be treated as a legitimate subdomain, causing the server to reflect `Access-Control-Allow-Origin: <attacker origin>` and grant that page cross-origin credentialed access.

## Finding Description
`isAllowedOrigin` parses the request's `Origin` header and each configured `CORSAllowedOrigins` entry into scheme/host/port [1](#0-0) . For wildcard-prefixed allowed hosts, it strips `*.` and checks `strings.HasSuffix(originHost, allowedHost)` with no dot-boundary check: [2](#0-1) . This conflates "string ends with configured suffix" with "is a genuine subdomain of the configured domain." A domain like `attacker-example.com` textually ends with `example.com` but is not a subdomain of it and can be freely registered by anyone. The result is fed directly into `Access-Control-Allow-Origin` in `handleRequest`: [3](#0-2) , so the browser will treat the attacker's page as authorized for cross-origin credentialed requests to the Gateway's `ProcessRequest` handler.

The existing test suite (`httpserver_test.go`) exercises the "correct subdomain" case and the "doesn't end with suffix" case but does not test the exact boundary-bypass scenario (e.g., `attacker-example.com` vs. allowed `*.example.com`), confirming this specific gap is present and unguarded by any other check (scheme/port matching, exact-match branch) upstream in the function.

## Impact Explanation
This maps to an in-scope "allowlist bypass" / cross-user response corruption category. If an operator configures a wildcard `CORSAllowedOrigins` entry, an unauthenticated attacker who controls a domain ending in the same suffix can have their web page treated as a trusted origin, enabling credentialed cross-origin reads of Gateway responses (e.g., job run results or DON responses returned by `ProcessRequest`) via a victim's browser session. This is a genuine logic flaw in code that ships and executes as part of default wildcard CORS handling, not a misconfiguration by itself — the bug undermines the security guarantee that a wildcard entry is supposed to provide.

## Likelihood Explanation
Exploitability requires: (1) the operator has configured a wildcard CORS entry (`*.domain.tld`), which is a supported, documented feature (present in sample configs and tests), and (2) the attacker registers/controls a domain that happens to end in the same literal suffix, and (3) a victim's browser with a credentialed session visits the attacker's page and it issues a cross-origin request. Domain registration is fully attacker-controlled and requires no privilege on the Gateway or node. Likelihood is realistic but conditioned on the specific wildcard domain in use and requires the attacker to acquire a domain with the exact matching suffix, which is a modest but real precondition.

## Recommendation
Require a `.` boundary immediately before the matched suffix (or exact equality) in the wildcard branch:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
This ensures `originHost` is either exactly `allowedHost` or a genuine subdomain of it, eliminating the unanchored-suffix bypass while preserving intended wildcard subdomain matching.

## Proof of Concept
1. Configure Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.example.com"]`.
2. Send an HTTP request to the Gateway's request path with header `Origin: https://attacker-example.com`.
3. Observe `isAllowedOrigin` computes `allowedHost = "example.com"`, `originHost = "attacker-example.com"`, and `strings.HasSuffix("attacker-example.com", "example.com")` returns `true`.
4. Observe the response includes `Access-Control-Allow-Origin: https://attacker-example.com`, confirming the bypass (this can be verified as a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, asserting the header is set for origin `https://attacker-example.com` against allowed `https://*.example.com`).
