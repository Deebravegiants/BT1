### Title
Vault `receive-underlying` ignores SIP-010 `transfer` boolean result, allowing share minting without backing assets - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar` and sibling vaults)

### Summary
`try!` in Clarity only aborts execution on an `(err ...)` response; it does not validate that an `(ok ...)` response actually carries `true`. Every vault's `receive-underlying` helper wraps the underlying SIP-010 `transfer` call in `try!` and then hard-codes `(ok true)` as its own return value, discarding the actual boolean payload of the transfer response.

### Finding Description
In `deposit`, the vault calls `(try! (receive-underlying amount account))` and then unconditionally mints zTokens and increases the `assets` variable: [2](#0-1) 

`receive-underlying` is implemented as:
```
(define-private (receive-underlying (amount uint) (account principal))
  (begin
    (try! (contract-call? 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token transfer amount account current-contract none))
    (ok true)))
``` [1](#0-0) 

If the underlying token's `transfer` function returns `(ok false)` instead of aborting with an `err` on failure (a behavior explicitly allowed for SIP-010 depending on implementation, and the exact bug class flagged in the referenced Visor Finance report — "unchecked return value of transferFrom/transfer"), `try!` unwraps the outer `ok` successfully, the inner `false` is thrown away, and `receive-underlying` still returns `(ok true)`. The `deposit` function then proceeds as if real underlying tokens were received: it mints `inkind` zTokens to the recipient via `ft-mint? zft inkind recipient` and increments the internal `assets` accounting variable by `amount`, even though the vault's real underlying balance never increased. [3](#0-2) 

This breaks the core vault invariant: `total zToken shares minted` must be backed 1:1 (via `convert-to-shares`) by `total-assets` actually custodied by the vault. If a transfer silently fails, shares are minted from nothing, diluting the claims of legitimate depositors on redemption. The same pattern is repeated identically across all vault variants (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) and their `local-testing` counterparts, and the `send-underlying` withdrawal path has the same unchecked pattern (impacting the vault the opposite way — burning shares while possibly not sending funds, but not creating value from nothing).

### Impact Explanation
If any of the six underlying tokens Zest wraps (sBTC, USDC, USDH, ststx, ststxbtc, wSTX) ever returns `(ok false)` for a failed transfer (e.g., insufficient balance handled non-idiomatically, a proxy/upgradable token bug, or a future token migration that doesn't strictly abort on failure), an attacker can call `deposit` and receive zTokens without the vault's underlying balance increasing. This is equivalent to minting shares from nothing, directly diluting/insolvent-izing the pool for all other depositors — a protocol insolvency / theft-of-principal class impact.

### Likelihood Explanation
Likelihood depends entirely on whether any of the six underlying SIP-010 tokens can return `(ok false)` instead of aborting on a failed transfer. Since wSTX's own `transfer` implementation uses `try!` on `stx-transfer?` (which does abort on failure) [4](#0-3) , that specific instance is currently safe. However, this repository does not contain the source of the mainnet third-party tokens (`sbtc-token`, `usdc`, `usdh-token-v1`, `ststx-token`, `ststxbtc-token-v2`) referenced by hardcoded principal, so their transfer-failure behavior cannot be verified from this codebase. The root-cause defect — Zest's own code not validating the inner boolean of the `transfer` response — is present and verifiable directly in Zest's vault contracts regardless of current third-party token behavior, matching the exact bug class of the reference finding (unchecked `transferFrom`/`transfer` return value).

### Recommendation
In every vault's `receive-underlying` (and `send-underlying`) helper, explicitly check the unwrapped boolean result of the token `transfer` call rather than discarding it, e.g.:
```clarity
(define-private (receive-underlying (amount uint) (account principal))
  (let ((success (try! (contract-call? .sbtc transfer amount account current-contract none))))
    (asserts! success ERR-TRANSFER-FAILED)
    (ok true)))
```
Apply the same fix consistently across `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` equivalents.

### Proof of Concept
1. Assume/require a scenario where the underlying SIP-010 token's `transfer` returns `(ok false)` on a failed transfer (e.g., an edge case not covered by strict abort semantics).
2. Attacker calls `deposit` on, e.g., `v0-vault-sbtc.clar` with an `amount` that triggers the underlying token to return `(ok false)`.
3. `receive-underlying` executes `(try! (contract-call? ... transfer ...))`, which succeeds at the `try!` level because the outer response is `ok`, and then unconditionally returns `(ok true)`. [1](#0-0) 
4. `deposit` proceeds to `ft-mint? zft inkind recipient` and `var-set assets (+ current-assets amount)`, crediting the attacker with zTokens backed by no real underlying assets. [2](#0-1) 
5. Attacker calls `redeem` to withdraw real underlying assets against the fraudulently minted shares, extracting value contributed by other depositors.
