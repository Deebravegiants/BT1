### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant misattribution - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the shop identity used to route/attribute the webhook (`x-shopify-shop-domain`) is taken from an unsigned header. `Registry.process` verifies only the body HMAC and then trusts the header-derived `shop` value to build `WebhookMetadata`, breaking the intended binding: *the shop that authenticates the webhook must equal the shop the handler acts on*.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed content: [2](#0-1) 

`Registry.process` validates only that the body/HMAC pair is authentic, then immediately trusts `request.shop` (the unsigned header) to build the metadata handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` and `validate_signature` confirm the signature only proves the body was produced with `Context.api_secret_key`; it says nothing about which shop the body belongs to: [4](#0-3) 

The `api_secret_key` is a single per-app secret shared across every shop that has installed a public app — it is not shop-specific. Any shop that has legitimately installed the app can therefore obtain a `(raw_body, hmac)` pair that is valid under the app's shared secret (e.g. by triggering an event in their own store and capturing the webhook delivery their own server receives, or by running their own instance of the app). That valid pair can then be replayed to the app's shared webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim shop's domain. Because the header is outside the signed content, `Registry.process` will accept the request as authentic and dispatch it to the app's handler tagged with the attacker-chosen `shop`, i.e.:

`hmac_valid(raw_body) == true` while `shop_claimed != shop_that_produced(raw_body)`.

This is the intended binding equality — `shop authenticated == shop stored/acted upon` — that the code fails to enforce, analogous to the reported bug class where a value is acted upon that is not covered by the authenticating check.

### Impact Explanation
An attacker who controls (or has installed) the app on their own shop can forge webhook deliveries attributed to another tenant's shop domain. Depending on how the host application implements its webhook handlers (the documented, expected pattern per `docs/usage/webhooks.md`/`registry.rb`), this can lead to cross-tenant data corruption or unauthorized actions being taken against a victim merchant's session/records (e.g., inventory, order, or app-uninstalled events being applied to the wrong shop). This falls under "cross-tenant access," a High/Critical-class impact per the given impact list.

### Likelihood Explanation
Requires only that the attacker operate their own installation of the target app (a normal, unprivileged capability for any merchant who installs a public app) and be able to send an HTTP POST to the app's public webhook endpoint with a header they fully control. No access token, `api_secret_key`, or TLS interception is required — the attacker only needs to observe (or produce) one legitimately-signed `(body, hmac)` pair for their own shop and replay it with a different `shop-domain` header.

### Recommendation
Include the shop domain in the signable content, or otherwise cryptographically bind the shop identity to the HMAC verification (e.g., verify the HMAC per registered shop/session rather than trusting the header independently). At minimum, `Registry.process` should cross-check `request.shop` against an expected/registered shop context before dispatching, rather than trusting it purely from an unauthenticated header.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` and triggers an event (e.g., creates a product) causing Shopify to deliver a webhook to the attacker's own server with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`).
2. Attacker replays the exact same `(B, H)` pair directly to the app's shared webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only (`Request#to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`) and succeeds, since `B`/`H` are a genuinely valid pair for the shared secret.
4. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-controlled webhook content as if it originated from the victim tenant.
