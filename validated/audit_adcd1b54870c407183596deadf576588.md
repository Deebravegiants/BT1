### Title
Third-party `supply` restamps a foreign account's liquidation risk parameters, bypassing the `update_account_threshold` health-factor floor - (File: contracts/controller/src/positions/supply.rs)

### Summary
The CVE class is an authenticated-but-unprivileged parameter (`newPassword`) reaching a privileged sink. The analog in XOXNO Lending is the permissionless third-party top-up path in `supply`: a stranger's caller-controlled `assets` list is permitted into a foreign account and, as a side effect, forces a `RiskRefreshScope::FullTuple` restamp of that account's cached per-position risk parameters. Unlike `update_account_threshold(has_risks=true)`, this path applies the new thresholds with no post-refresh solvency floor, so after governance tightens a listing's LTV/liquidation threshold, anyone can retroactively apply it to a victim's stale position and push it under `HF < 1` for liquidation.

### Finding Description
`process_supply` admits third parties when every supplied `hub_asset` already exists in the victim's `supply_positions` [1](#0-0) . Each leg then runs `merge_supply_leg`, which unconditionally calls `refresh_supply_risk_params(..., RiskRefreshScope::FullTuple)` on the victim's position [2](#0-1) . `FullTuple` is the scope that rewrites the cached liquidation-parameter tuple (the same scope `sync_account_thresholds` uses for `has_risks=true`) [3](#0-2) . The dedicated keeper entrypoint `update_account_threshold` enforces a final `HF >= 1.05` when refreshing that tuple [4](#0-3) , but the third-party supply path applies the identical refresh and only runs `finalize_position_flow` with `PositionSides::Supply`, i.e., no solvency check on the victim [5](#0-4) . Since `account_id` is supplied by the attacker and `is_owner_or_delegate` is only used to widen allowed markets — not to block the restamp — the attacker's input reaches a privileged write on another user's risk state [6](#0-5) .

### Impact Explanation
A victim holding a collateralized borrow whose position snapshot carries older, looser LTV/liquidation-threshold values (the hub/spoke design caches per-position risk parameters) can be force-liquidated the moment governance tightens those parameters, purely by a dust top-up into a market the victim already supplies. The attacker then calls `liquidate` and collects the HF-based bonus, extracting value from the victim's collateral. This is theft of user funds reachable by a single unprivileged address.

### Likelihood Explanation
Triggering requires two conditions: (1) governance has tightened an asset's risk parameters since the victim's position was last restamped, and (2) the victim's cached health factor is above 1 but below 1 under the new parameters. Both are routine in a live market — risk-parameter changes are the normal motivation for restamping at all — and the attack costs only a dust supply into an existing market. The attacker can liquidate in the same or an immediately following transaction.

### Recommendation
Restrict the `FullTuple` refresh inside `merge_supply_leg` (and any merge path reachable by a non-owner) to owner/delegate callers, or degrade third-party legs to `RiskRefreshScope::LtvOnly` — mirroring the permissionless `update_account_threshold` semantics — so a stranger can only restamp parameters that do not alter liquidation eligibility. Alternatively, apply the same `HF >= 1.05` post-refresh assertion on the target account that `update_account_threshold(has_risks=true)` enforces.

### Proof of Concept
1. Governance tightens `liquidation_threshold` for asset A in the victim's spoke via timelock.
2. Victim's account still caches the old tuple: `HF_old >= 1`, `HF_new < 1`. `update_account_threshold(has_risks=true, [victim])` would revert on the 1.05 floor, so keepers cannot restamp it.
3. Attacker calls `controller.supply(caller=attacker, account_id=victim, spoke_id=victim_spoke, assets=[(A, dust)])`. `require_third_party_existing_supply` passes because A is already in `victim.supply_positions`; `merge_supply_leg` restamps the position to the new threshold with no HF check.
4. Attacker calls `controller.liquidate(liquidator=attacker, account_id=victim, ...)`, which now sees `HF < 1` under the restamped tuple and seizes collateral at a bonus.

*Caveat: I could not fully read `risk/params.rs`/`totals.rs` within tool limits, so the exact field set restamped by `FullTuple` and the liquidation admission read path should be confirmed against `refresh_supply_risk_params` and `calculate_account_risk_totals` before finalizing severity.*

pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}
