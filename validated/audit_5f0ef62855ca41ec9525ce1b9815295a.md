### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing/replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs (and validates) only the raw request body via HMAC, while the `shop` (tenant) identity is taken from an unauthenticated HTTP header. Any party capable of obtaining one genuine, HMAC-signed webhook body for their own shop can replay that exact body to the app's webhook endpoint while forging the `shop-domain` header to claim it belongs to a different merchant. The HMAC check still passes because the header is never part of the signed material, breaking the binding between "the shop the signature was issued for" and "the shop the application acts on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

The `shop` accessor, however, is read straight from the (attacker-controlled) `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header with no cryptographic binding to the payload:

```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely over `verifiable_query.to_signable_string` (i.e., the raw body), using the app's shared `api_secret_key`:

```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

`Webhooks::Registry.process` then trusts `request.shop` directly and forwards it, unverified against the signed content, to the host application's handler:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The `api_secret_key` (`client_secret`) is shared by the app across **all** installing shops, not per-tenant. Any merchant who installs the app on their own store legitimately receives genuine, correctly-signed webhooks from Shopify for their own shop. Because the signature covers only the body and never the shop-domain header, that merchant can capture one such `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a *different* merchant's shop. `Utils::HmacValidator.validate` will still return `true` (the body and HMAC are unchanged and genuinely signed), and `Registry.process` will hand the body off as if it belonged to the victim shop.

This is precisely the class of bug described in the target rule: a field that is acted upon (`shop`) but not included in the value covered by the HMAC (`raw_body` only) — breaking the binding `shop_authenticated_by_signature == shop_acted_on_by_handler`.

### Impact Explanation
If the host application keys any tenant-scoped action (order updates, inventory changes, notification dispatch, data storage) off `WebhookMetadata#shop`/`request.shop` — which is the intended and documented use per `Webhooks::Registry` — an attacker-controlled shop identity lets one merchant's genuine webhook data be attributed to and processed against another merchant's tenant. This is a cross-tenant integrity/confidentiality violation reachable by any unprivileged internet user who has installed the app on their own store (no access token, admin credential, or privileged account required from the victim's side).

### Likelihood Explanation
Exploitation requires no special access beyond installing the app once (a normal, unprivileged onboarding step) and capturing one legitimately delivered webhook for the attacker's own store. Replaying that payload with a different `shop-domain` header is trivial (a single HTTP POST). The signature check by design cannot detect the tampering since it never covers the header. This makes the issue reliably and cheaply reproducible.

### Recommendation
Include the shop identity in the signed/verified material, or otherwise cryptographically bind the `shop-domain` header to the request before trusting it:
- Prefer validating `request.shop` against a known/registered shop for the webhook subscription id (`webhook-id`) rather than trusting the header value directly, or
- Additionally verify the header value is consistent with metadata retrievable via an authenticated API call (e.g., fetch the webhook subscription by `webhook_id` and compare shop), or
- At minimum, document prominently that `request.shop` is NOT covered by the HMAC and must not be used as the sole identity source for tenant-scoped actions; require host apps to cross-check it against a stored webhook-id-to-shop mapping created at registration time.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `raw_body` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, raw_body)`.
2. Attacker resends the identical `raw_body` and `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, raw_body)` (unchanged) and compares to `H` — validation passes per `lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. `Webhooks::Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's order body per `lib/shopify_api/webhooks/registry.rb:188-200`, causing the host application to process attacker-controlled data under the victim shop's tenant context.
