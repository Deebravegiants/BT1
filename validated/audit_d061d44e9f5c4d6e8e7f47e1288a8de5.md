Audit Report

## Title
Unbounded growth of the Gateway HTTP-capability `responseCache` — no maximum-size enforcement, unlike sibling `requestCache` - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
`responseCache.Fetch` and `responseCache.Set` insert entries into `rc.cache` keyed by `req.Hash()` with no bound on the number of entries, unlike the sibling `common.requestCache` type which enforces `maxCacheSize` and rejects new entries once full. [1](#0-0) [2](#0-1) [3](#0-2) 

## Finding Description
Both cache-insertion paths in `responseCache` (the `Fetch` slow path and `Set`) write to `rc.cache` unconditionally on size, with removal only occurring via the time-based `DeleteExpired` sweep run on a `CleanUpPeriodMs` ticker (default 10 minutes). [4](#0-3) [5](#0-4)  Cache keys are derived from `req.Hash()`, which is computed from the `gateway_common.OutboundHTTPRequest` unmarshaled from a `jsonrpc.Response` in `makeOutgoingRequest(ctx, resp *jsonrpc.Response[json.RawMessage], nodeAddr string)`. [6](#0-5) 

Importantly, `makeOutgoingRequest` receives its input as a message purportedly originating from a `nodeAddr` — i.e., a DON node, not a directly unprivileged/anonymous internet client. I was unable to locate and fully trace the exact `HandleNodeMessage` dispatcher (the calling function of `makeOutgoingRequest`) within the available tool budget to confirm what authentication/authorization (e.g., mTLS, signature verification, node allowlist) gates this call before it reaches `makeOutgoingRequest`. Based on the surrounding code and naming conventions (`nodeAddr` parameter, `sendResponseToNode`), this path appears reachable only from already-authenticated DON node connections, meaning the workflow owner cannot directly hit the gateway's response cache — their influence is indirect (via the DON executing their workflow and then relaying an outbound HTTP action result to the gateway).

The comparison to `common.requestCache.NewRequest`'s explicit `len(c.cache) >= int(c.maxCacheSize)` bound is accurate as a code-level architectural inconsistency. [7](#0-6) 

## Impact Explanation
If reachable, unbounded map growth in `rc.cache` would be a resource-exhaustion/DoS concern on the gateway process shared across DONs, matching a memory-growth bug class. However, the severity and reachability depend entirely on whether the DON-node-authenticated boundary (which I could not fully verify due to tool-call limits) meaningfully restricts this from being triggerable by unprivileged actors directly, or whether it constitutes an indirect path through a trusted DON relay — which per the validation rules, exploit paths requiring an intermediary node/DON to relay attacker-influenced data are typically treated with more scrutiny (bordering on the "malicious node" exclusion boundary), since the report explicitly relies on the DON already executing and relaying the workflow's HTTP action result back through its trusted, presumably authenticated node channel.

## Likelihood Explanation
Medium-to-low confidence: while the workflow owner can influence the *content* of requests (URL, headers, body) that eventually get cached, the direct actor triggering `makeOutgoingRequest`/`responseCache.Set`/`Fetch` is the DON node relaying results over what is very likely an authenticated node-to-gateway channel, not a raw unprivileged HTTP/gateway API call. I was unable to confirm the exact authentication middleware/dispatcher in the time available, which is required per the validation checklist ("Existing auth middleware, role wrappers, signature checks... reviewed and shown insufficient").

## Recommendation
If accepted as in-scope, add an explicit maximum-size guard to `responseCache` (mirroring `common.requestCache.NewRequest`'s `len(c.cache) >= int(c.maxCacheSize)` check) in both `Fetch`'s slow path and `Set`, exposed as a configurable limit in `ServiceConfig`, and reject or evict-oldest once the limit is reached.

## Proof of Concept
Not independently verified end-to-end. Confirming exploitability requires tracing the full node-message authentication path (likely in a `HandleNodeMessage` dispatcher or gateway node-connection manager) that ultimately calls `makeOutgoingRequest`, to determine whether an unprivileged workflow owner can, without possessing/compromising a DON node credential, cause an effectively unbounded number of unique cache keys to be inserted. This verification could not be completed within the available tool-call budget; a Devin session with full repository access would be needed to trace this call chain precisely (e.g., `grep` for `HandleNodeMessage` implementations in `core/services/gateway/connmgr` or handler registration code, and check for mTLS/node-ID verification prior to invoking `makeOutgoingRequest`).

func (rc *responseCache) DeleteExpired(ctx context.Context) int {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	now := time.Now()
	var expiredCount int
	for key, cachedResp := range rc.cache {
		if now.After(cachedResp.storedAt.Add(rc.ttl)) {
			delete(rc.cache, key)
			expiredCount++
		}
	}
	rc.lggr.Debugw("Removed expired cached HTTP responses", "count", expiredCount, "remaining", len(rc.cache))
	rc.metrics.IncrementCacheCleanUpCount(ctx, int64(expiredCount), rc.lggr)
	rc.metrics.RecordCacheSize(ctx, int64(len(rc.cache)), rc.lggr)
	return expiredCount
}

		URL:              req.URL,

		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,

			if req.CacheSettings.Store {
