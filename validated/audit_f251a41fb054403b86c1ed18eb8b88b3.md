Webhook HMAC only signs the raw body, letting the `shop`, `topic`, and `webhook-id` fields be forged for cross-tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating an HMAC that covers only the raw HTTP body, while the `shop`, `topic`, `api_version`, and `webhook_id` values that are handed to the app's `WebhookHandler` are read directly from unauthenticated HTTP headers. Because these identity fields sit outside the signed payload, any party who can obtain one validly-signed webhook body (e.g. a merchant who has legitimately installed the app and thus receives their own Shopify webhooks) can replay that same body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header, causing the app to process the payload as if it originated from a different, victim tenant.

### Finding Description
The identity binding that should hold is:

`shop (and topic) authenticated by the HMAC` == `shop (and topic) delivered to the handler`

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors, by contrast, are pulled straight from request headers with no cryptographic tie to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then immediately forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` to the registered handler: [3](#0-2) 

`Utils::HmacValidator.validate` simply recomputes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the supplied `hmac`: [4](#0-3) 

Since the app's `api_secret_key` is shared across all shops that install the app, any tenant of the app legitimately receives correctly-signed webhook bodies for its own store. Because the shop/topic headers are not part of the signed material, that tenant (an unprivileged, non-admin party from the perspective of any *other* tenant) can capture one such body+HMAC pair and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to any other merchant's `myshopify.com` domain. `Utils::HmacValidator.validate` still succeeds (the body and HMAC are unchanged and valid), so `handler.handle` runs with `WebhookMetadata.shop` set to the victim's domain, breaking the tenant boundary the app relies on to route/authorize webhook side effects.

### Impact Explanation
This is a cross-tenant access vulnerability: an attacker who is any legitimate but low-privilege user of a multi-tenant app (or anyone who otherwise observes a validly-signed webhook body, since the shop field isn't bound to it) can make the host application believe an event happened for a shop it did not happen for. Depending on how the host app's `WebhookHandler` implementations use `WebhookMetadata.shop` (e.g. to look up records, trigger mandatory `shop/redact`/`customers/data_request` compliance flows, or update per-shop state), this can corrupt or exfiltrate data belonging to another merchant — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The gem itself supplies no protection against this once a single valid signed body is obtainable, and multi-tenant apps built on this gem are the primary use case, so the precondition (attacker legitimately receiving their own store's webhooks) is trivially satisfied for any app with more than one installed merchant. No secret, admin access, or credential theft is required — only a normal app installation the attacker already controls.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the signed payload (e.g., append them to the string signed, similar to how `Oauth::AuthQuery#to_signable_string` includes `shop`, `host`, `state`, etc.), so a replayed body cannot be reattributed to a different shop.

### Proof of Concept
```ruby
# Attacker has legitimately installed the app on their own store "attacker.myshopify.com"
# and receives a real, validly-signed webhook for it:
body = '{"id":123,"note":"legit payload for attacker store"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

# Attacker replays the exact body+hmac but swaps the shop-domain header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "customers/data_request",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# HMAC check passes because only `body` is signed, not the shop-domain header:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle is invoked with WebhookMetadata.shop == "victim-shop.myshopify.com"
```
