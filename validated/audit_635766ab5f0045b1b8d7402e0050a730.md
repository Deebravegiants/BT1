### Title
Silent ERC20 transfer failures cause permanent loss of escrowed funds in Tron IntentGatewayV2 `withdraw` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` (and the `SweepDust` handler in `onAccept`) on the Tron deployment release escrowed ERC20 tokens using a raw low-level `.call` to the token's `transfer` selector, checking only whether the *call itself* reverted and discarding the returned `bool` payload. Any ERC20 implementation that signals transfer failure by returning `false` (instead of reverting) — the exact "inconsistent ERC20" behavior class flagged in the referenced report — will be treated as a successful transfer, permanently corrupting escrow accounting and losing user/solver funds.

### Finding Description
In `withdraw()`, escrowed input tokens and the transaction fee token are released like this: [1](#0-0) 

and the fee transfer: [2](#0-1) 

The same pattern is used for the `SweepDust` request kind: [3](#0-2) 

In each case, the code does `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only reverts `if (!success)`. `success` here reflects whether the low-level call reverted — it does **not** decode or validate the returned `bool` from `transfer`. Per EIP-20, a compliant token is permitted to return `false` on failure instead of reverting; such a call would return `success == true` with return data encoding `false`, which this code ignores entirely.

This is the mirror image of the audit report's root cause (`Erc20CheckedTransfer.checkedTransferFrom`/`checkedTransfer`, which reverts unconditionally for tokens that don't return a bool at all): both stem from not correctly interpreting/handling the diversity of ERC20 return-value conventions. Here the consequence is worse than a DoS — it silently accepts a *failed* transfer as successful.

Immediately after the unchecked call, the function decrements internal escrow accounting and marks the order filled regardless of whether tokens actually moved: [4](#0-3) 

By contrast, the EVM-mainline `IntentGatewayV2`/`IntentsBase` and other apps in this repo (`HyperFungibleToken`, `WrappedHyperFungibleTokenUpgradeable`, deposit paths in the same Tron file) consistently use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, e.g.: [5](#0-4) 
which correctly validates both call success and (if present) the returned boolean. Only the payout/withdraw/sweep paths in the Tron variant use the unchecked raw `.call` pattern.

### Impact Explanation
Any ERC20 (or Tron TRC20 equivalent) token that returns `false` rather than reverting on a failed `transfer` — a legitimate and common implementation choice — will cause `withdraw()` to:
- mark the order as filled/refunded (`_filled[body.commitment] = beneficiary`),
- decrement `_orders[commitment][token]` as if funds were paid out,
- emit `EscrowReleased`/`EscrowRefunded`,

while the beneficiary receives nothing. The tokens remain permanently stuck in the `IntentGatewayV2` contract with no accounting entry pointing to them (the escrow record was already decremented), and the order can never be retried because it's already marked filled. This is a direct, permanent loss of user/solver funds reachable through the normal intent settlement flow (fill → redeem escrow, cancel → refund escrow, or governance dust-sweep), which matches the in-scope "intents escrow and bids" surface.

### Likelihood Explanation
Likelihood depends on whether any token registered/used with the Tron `IntentGatewayV2` returns `false` on failure (e.g., insufficient balance/allowance edge cases, blacklist/pausable tokens, or bridged/wrapped tokens with non-standard implementations common on TRON). Given intent gateways are designed to be token-agnostic (arbitrary `order.inputs[i].token`), and Tron's token ecosystem includes many non-standard TRC20 contracts, this is a realistically triggerable condition, not a purely theoretical one.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (as already done for `safeTransferFrom` in the deposit path of this same file). `SafeERC20` correctly handles all three ERC20 return conventions (no return value, `true`/`false` return, or revert) and reverts on any real failure, ensuring escrow accounting is only mutated after a confirmed transfer.

### Proof of Concept
1. Register/permit a TRC20/ERC20 token whose `transfer` implementation returns `false` on failure instead of reverting (e.g., due to an internal pause, blacklist check, or insufficient balance edge case that the contract chooses to signal via return value).
2. A user places an order with this token as input; solver fills it; the fill/cancel flow eventually calls `withdraw()` (via `onAccept` `RedeemEscrow`/`RefundEscrow` or `onGetResponse`).
3. Arrange for the token's internal `transfer` to return `false` (e.g., beneficiary temporarily blacklisted at call time, later un-blacklisted).
4. `token.call(...)` succeeds (does not revert) with return data `abi.encode(false)`; `success` is `true`, so `if (!success) revert TransferFailed()` does not trigger.
5. `_orders[body.commitment][token] -= amount` executes, `_filled[commitment]` is set, `EscrowReleased` is emitted — but the beneficiary's token balance never increased.
6. The escrowed tokens are now permanently unrecoverable: the order is marked filled and the escrow ledger already shows zero for that token/commitment.
