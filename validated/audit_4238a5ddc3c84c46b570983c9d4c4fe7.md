## Finding is plausible but only partially verified — presenting with caveats

I confirmed the core code asymmetry directly, but ran out of tool budget before fully re-verifying the cycle-construction path (`transfer`/`transfer_raw`/`verify_ungated_and_descendant`). I'm flagging that limitation explicitly below.

### Title
Missing nesting-depth guard in `root_owner` allows unbounded loop on attacker-constructed cyclic ownership — (`aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`root_owner` walks up an object's ownership chain with no bound on iteration count, unlike the sibling function `owns`, which explicitly caps traversal at `MAXIMUM_OBJECT_NESTING` and asserts if exceeded.

### Finding Description
`owns` guards against unbounded/cyclic traversal: [1](#0-0) 

`root_owner` performs the same style of upward traversal but has no such guard: [2](#0-1) 

The relevant precondition is whether an unprivileged account can ever cause `owner(A) == B` and `owner(B) == A` to both hold simultaneously for two `ObjectCore`s it controls. If the object-transfer path (`transfer`/`transfer_raw`/`verify_ungated_and_descendant`) only validates that the *caller* is currently authorized to move the object being transferred (walking up from the object's own existing chain) and does **not** check whether the *destination* address is itself a descendant of the object being moved, then a user who legitimately owns both `A` and `B` could:
1. Transfer `A` so `owner(A) = B` (valid, since the caller currently owns `A` directly).
2. Transfer `B` so `owner(B) = A` (valid, since the caller currently owns `B` directly, and this check does not look at `A`'s ownership chain).

This produces a two-node cycle. I was not able to re-confirm the full body of `transfer_raw`/`verify_ungated_and_descendant` in this pass to definitively prove the destination is never checked for descendant-of-source, so this specific construction path needs direct confirmation against the current source before treating it as fully proven.

### Impact Explanation
If the cycle is constructible, calling `root_owner` on either object never terminates within the loop; in Move there is no way to "return a stale/incorrect owner" from a true infinite loop — execution simply keeps looping until it is stopped by the gas metering of the calling context. In a transaction/entry-function context this manifests as a deterministic out-of-gas abort, exactly as the proof idea anticipates, not a silently wrong answer. The custody-relevant risk is a denial-of-service against any code (on-chain or off-chain, including dapps/indexers/other Move modules) that calls `root_owner` to make an ownership/custody decision on attacker-influenced objects — the call cannot resolve, only abort or hang, which can be used to grief transactions or view-function servers that don't impose a shorter timeout than the loop needs to exhaust available gas/resources.

### Likelihood Explanation
Likelihood depends entirely on whether the transfer path lets an owner independently set `owner(A) = B` and `owner(B) = A` without any cross-check — this is the one fact I could not fully re-verify before running out of tool iterations. If confirmed, the attack requires only two ordinary `transfer` calls with objects the attacker already controls, no special privilege.

### Recommendation
- Add the same `MAXIMUM_OBJECT_NESTING` bound (with an `assert!`) used in `owns` to `root_owner`'s while loop, regardless of whether cycle creation is otherwise possible, since defense-in-depth against any future or already-possible cyclic state is cheap and consistent with the rest of the module.
- Separately, verify (by reading `transfer`, `transfer_raw`, and `verify_ungated_and_descendant` in full) whether destination-side cycle checks exist; if not, add a check when transferring `A` to destination `D` that `D` is not already a descendant of `A` in the ownership chain (mirroring `owns`'s traversal but checked at transfer time), which is the only way to prevent cyclic `ObjectCore.owner` graphs from being created at all.

### Proof of Concept
Conceptual outline (pending confirmation of transfer-path checks):
```
1. attacker creates ObjectCore A and B, both initially owned by attacker.
2. attacker calls object::transfer(attacker_signer, A, B_address)   // sets owner(A) = B
3. attacker calls object::transfer(attacker_signer, B, A_address)   // sets owner(B) = A
4. any caller invokes object::root_owner(A) (or B)
   -> while (is_object(obj_owner)) loops forever between A and B
   -> transaction/view execution aborts on out-of-gas (or hangs, depending on caller's gas/timeout policy)
```

**This needs verification**: re-check the current implementation of `transfer`, `transfer_raw`, and `verify_ungated_and_descendant` in `object.move` to confirm no destination-side descendant check blocks step 2/3, since that is the load-bearing fact for whether this finding is exploitable versus already mitigated.
