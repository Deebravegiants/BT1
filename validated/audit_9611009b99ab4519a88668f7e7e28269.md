## Finding: Webhook `shop` identity is not covered by the HMAC signature

### Title
Webhook shop-domain spoofing via HMAC/identity binding mismatch in `ShopifyAPI::Webhooks::Request` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the `shop` value taken from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header — a field that is never part of the signed bytes. The identity used by the host application (`data.shop` in `WebhookMetadata`) is therefore not bound to the cryptographic proof that "the request came from Shopify."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from an attacker-controllable HTTP header with no cryptographic tie to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC (i.e., the body bytes) and then immediately hands the unauthenticated `request.shop` to the app's handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`, i.e. the body only: [4](#0-3) 

The equality this mechanism should guarantee is: `bytes_covered_by_HMAC == identity_field_used_by_handler`. In reality: `bytes_covered_by_HMAC = raw_body` while `identity_field_used_by_handler = header["shop-domain"]` — two disjoint values. The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," which overstates what is actually checked (only body integrity, not shop attribution): [5](#0-4) 

Because the HMAC secret (`api_secret_key`) is shared across all shops that install the app, any merchant who has installed the app can legitimately trigger a webhook for their *own* shop and thus obtain one valid `(raw_body, hmac)` pair signed with the app's secret. That merchant can then replay the exact same body and HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (the body bytes are unchanged), and `Registry.process` dispatches to the handler with `shop` set to the victim's domain, since the shop field was never covered by the signature.

### Impact Explanation
Host applications built on this gem key their tenant data and business logic off `WebhookMetadata#shop` (as shown in the gem's own documentation example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`). An attacker who legitimately controls one shop that has the app installed can forge webhook deliveries that are attributed to a different, victim shop, causing cross-tenant data confusion/injection in the host application (e.g., processing forged `orders/create`, `app/uninstalled`, or GDPR-relevant payloads as if they belonged to another merchant). This satisfies the Critical "cross-tenant access" impact category, since the binding between the cryptographic proof of authenticity and the tenant identity used downstream is broken.

### Likelihood Explanation
High. Any merchant that installs the app under attack can obtain a valid `(body, hmac)` pair for free by simply triggering any subscribed webhook topic on their own store (e.g., updating a product). The webhook HTTP endpoint is public by design (Shopify must be able to reach it unauthenticated at the transport layer, relying only on the HMAC), so replaying the captured request with a modified `shop-domain` header requires no special access, credentials, or privileged account beyond running an ordinary Shopify store.

### Recommendation
Do not treat `request.shop` as authenticated by the HMAC. Either:
1. Include the shop-domain header (and ideally `topic`/`api-version`/`webhook-id`) in the signable string used for HMAC computation so the identity is cryptographically bound, matching what Shopify actually sends per-shop, or
2. Require host applications to cross-check `request.shop` against an independently known/authorized shop (e.g., a shop for which a valid, previously-stored offline session/access token exists) before trusting the payload, and clarify in `Registry.process`'s documentation and behavior that shop attribution is not verified by the HMAC alone.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal install, no special privileges).
2. Attacker triggers any registered webhook topic (e.g. update a product) and captures the raw HTTP request Shopify sends to the app's webhook endpoint, including `raw_body` and the `X-Shopify-Hmac-Sha256` header.
3. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the same webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — validation succeeds.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and the host app processes attacker-supplied data as if it originated from the victim shop.
