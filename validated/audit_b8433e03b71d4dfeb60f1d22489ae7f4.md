## Title
Escrow credited before sweep transfer is verified, allowing under-collateralized order commitments in `placeOrder()` — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` credits an order's escrow ledger with the full expected input amount *before* the token sweep that is supposed to actually deliver those tokens from the `CallDispatcher` back into the gateway is executed and *without* ever verifying that the gateway's balance increased by the credited amount afterwards. This is the same "check/record-then-act, no after-check" ordering flaw described in the external report: state is finalized based on a pre-transfer snapshot instead of a verified post-transfer balance.

### Finding Description
In `placeOrder()`'s predispatch branch, for each input token the code:
1. Reads `balance = IERC20(token).balanceOf(dispatcher)` (the dispatcher's balance *after* the arbitrary `order.predispatch.call` has run, but *before* the actual sweep).
2. Only checks `balance >= requiredAmount` and builds a `transferCalls[i]` sweep call.
3. Immediately credits the escrow ledger: `_orders[commitment][token] += reducedInputs[i].amount;` — using the originally requested (fee-reduced) amount, not the observed `balance`, and not any post-transfer measurement.
4. Only afterwards executes the actual sweep: `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls));`. [1](#0-0) 

There is no balance-diff check after the sweep dispatch confirms the gateway actually received `reducedInputs[i].amount` (or even `balance`) worth of tokens. Compare this to the corresponding EVM-mainline `IntentGatewayV2.sol`, which snapshots `balancesBefore[i]` immediately before the sweep dispatch and computes `received = balanceAfter - balancesBefore[i]` after the sweep, crediting/using only the actually-verified received amount: [2](#0-1) 

Because the Tron contract omits this after-the-fact reconciliation, any token whose actual transferred amount can diverge from its `balanceOf` snapshot at sweep time (fee-on-transfer tokens, tokens with transfer hooks/blacklists, or any effect triggered by the sweep's own `dispatch` call) will cause the escrow accounting (`_orders[commitment][token]`) to overstate what the gateway actually holds for that commitment. Since `_orders` is a shared per-token ledger across all commitments and is later drawn down by `_withdraw`/fill/refund/cancel paths using `safeTransfer`, an inflated ledger entry for one order allows that order's cancellation/refund/fill payout to be satisfied using tokens that were actually escrowed for a *different* order, producing insolvency of the gateway's token accounting.

### Impact Explanation
Under-verified escrow accounting means the protocol's internal ledger can promise more tokens than the contract actually holds. This is a fund-freezing/fund-theft class issue: whichever order attempts withdrawal/refund/fill-completion first drains real tokens that another legitimately-escrowed order is relying on, leaving that later order's owner unable to redeem or be refunded (frozen/stolen funds), directly matching the "tokens can be stolen" / "tokens get stuck" impact called out in the source report.

### Likelihood Explanation
This path is reachable by any unprivileged user calling `placeOrder()` with `predispatch.call` and `predispatch.assets` populated — no special privileges are required, and predispatch calldata routes through the `CallDispatcher` to arbitrary external contracts (e.g., swaps), which is a documented, user-controlled feature of the intent gateway. Any input token with fee-on-transfer/rebasing/hook semantics (or a predispatch call whose side effects alter the dispatcher's actual outgoing transfer) triggers the mismatch deterministically once such a token is accepted as an input.

### Recommendation
Mirror the EVM-mainline fix: snapshot the gateway's own balance immediately before dispatching the sweep `transferCalls`, execute the sweep, then compute the escrow credit strictly from the measured `balanceAfter - balanceBefore` (capped/adjusted for fee-on-transfer as done in `IntentGatewayV2.sol`), rather than crediting `reducedInputs[i].amount` speculatively based on a pre-sweep `balanceOf` read. Revert or emit dust for any discrepancy instead of silently trusting the requested amount.

### Proof of Concept
1. Configure an input token that is fee-on-transfer (or whose `transfer()` triggers a hook reducing the amount actually received) and set it as `order.inputs[0].token` with a non-empty `predispatch.call`/`predispatch.assets`.
2. Call `placeOrder()`. The dispatcher's `balanceOf` check at step (1)/(2) passes using the pre-sweep balance, and `_orders[commitment][token]` is credited with the full `reducedInputs[i].amount`.
3. Execute the sweep in step (4); due to the fee-on-transfer/hook, the gateway receives less than `reducedInputs[i].amount`.
4. The commitment's escrow ledger now overstates the gateway's actual token holdings for that token; a later `fillOrder`/cancel/withdraw flow for this or another commitment sharing the same token can pay out more than the gateway actually has reserved for it, draining tokens escrowed by other users' orders.
