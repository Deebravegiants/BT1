### Title
Webhook `shop` (and other identity headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the raw request body against the `X-Shopify-Hmac-Sha256`/`shopify-hmac-sha256` header, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers and hands them straight to the app's handler. The identity binding "HMAC verifies bytes X" vs. "handler acts on shop Y" is broken: `Y` is never part of `X`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers, completely outside the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC of the request and then immediately dispatches to the handler using `request.shop` (and the other header-derived fields) as trusted identity data: [3](#0-2) 

Because the shared `api_secret_key` is identical for every shop that has the app installed, any merchant who installs the app can trigger a legitimate webhook to their own shop and thereby obtain a body + valid HMAC pair signed with the app's secret. Nothing in the gem's verification logic binds that signature to the `shop-domain` header. An attacker (an unprivileged internet user relative to *other* tenants of the multi-tenant app, i.e. any merchant who installs the app) can replay that captured `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `Utils::HmacValidator.validate` will report success (it only recomputes the HMAC over `raw_body`), and `Registry.process` will pass the forged `shop` value to `WebhookMetadata`, which the host application will treat as authenticated: [4](#0-3) 

This is exactly the class of bug in the report — an identity field ("shop", the tenant identity) is acted on by the recipient (`Registry.process` → handler) without being covered by the same cryptographic check ("HMAC") that is used to authenticate the request. The equality that should hold and is broken is: `shop_bound_by_hmac == shop_delivered_to_handler`; here the left side doesn't exist (HMAC covers only body bytes) while the right side is attacker-controlled header content.

### Impact Explanation
This is a cross-tenant boundary violation: it allows an attacker who is a legitimate (but malicious) merchant of a multi-tenant app to make the app process arbitrary webhook bodies "as if" they came from a different, victim shop, since `data.shop` passed to `WebhookHandler#handle` is fully attacker-controlled while still passing HMAC validation. Depending on what the app's handler does with `shop` (e.g., look up/attribute records, update shop-scoped state), this can lead to cross-tenant data corruption/exfiltration, which maps to the report's "Critical – cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to control at least one shop where the app is installed (an unprivileged, ordinary merchant relationship — no special credentials, tokens, or `api_secret_key` needed) and requires triggering one webhook whose body is generic/predictable/reusable for the topic being targeted (many webhook topics, e.g. `app/uninstalled`, have body content that is not shop-specific or can be crafted by the attacker's own store activity). No TLS interception, credential leakage, or privileged access is needed — only normal use of the app as a merchant plus a replayed HTTP POST to the app's public webhook endpoint.

### Recommendation
Bind the shop (and ideally the other webhook metadata) into the value that is HMAC-verified, or otherwise cryptographically authenticate the `shop-domain` header, rather than trusting it solely from an unauthenticated header. At minimum, `VerifiableQuery#to_signable_string` for webhook requests should incorporate the `shop-domain` (and `topic`) header value, and/or the library should document/require host apps to cross-check `request.shop` against a shop that is expected to have registered that specific webhook/topic before acting on it.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (ordinary merchant action, no special privilege).
2. Attacker triggers a webhook (e.g., `app/uninstalled`) and captures the raw POST body plus the `x-shopify-hmac-sha256` value sent by Shopify — both are valid because they're signed with the shared `api_secret_key`.
3. Attacker replays the exact same body + HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`) — validation succeeds.
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the request never actually originated from that shop.
