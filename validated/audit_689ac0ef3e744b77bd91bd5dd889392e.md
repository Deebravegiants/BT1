### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` values taken directly from HTTP headers — none of which are covered by that HMAC. This breaks the identity binding `shop that generated the HMAC == shop attributed to the payload`, allowing a previously captured, validly-signed webhook body to be replayed with an attacker-chosen `shop-domain` header and still pass verification.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from the (attacker-controllable, since they're transport-level headers on the request the app receives) headers, independent of the signed body: [2](#0-1) 

`Registry.process` validates only the body's HMAC, then immediately trusts `request.topic` for handler dispatch and `request.shop` as the tenant identity forwarded to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body) and the shared `api_secret_key`, with no shop/topic binding: [4](#0-3) 

Because the same `api_secret_key` is used for every shop installed on the app, and the HMAC is computed only over the JSON body, any valid `(body, hmac)` pair captured from one legitimately delivered webhook remains cryptographically valid when replayed with the `shop-domain` header changed to a different shop, or the `topic` header changed to a different topic. The identity equality the gem should enforce — `shop bound by the HMAC == shop attributed to the webhook payload` — does not hold, since `shop` is never part of the signed material.

### Impact Explanation
This is a cross-tenant identity-binding break: an app that relies on `WebhookMetadata#shop` (as forwarded unmodified by `Registry.process`) to determine which merchant a payload belongs to can be made to process data under a spoofed shop identity, since the gem provides no verification that the `shop-domain` header actually corresponds to the shop that produced the HMAC. Any application logic that persists webhook payloads keyed by `data.shop` (order data, product data, GDPR payloads, etc.) is exposed to injecting data attributed to a victim tenant using only a previously-observed webhook body/HMAC pair, without ever knowing the app's `api_secret_key`.

### Likelihood Explanation
Exploitation requires the attacker to have obtained at least one legitimately signed webhook body+HMAC pair (e.g. one delivered to their own installed shop, or a webhook receiver they control), which is realistic for any multi-tenant app since installing the app and receiving your own webhooks is not privileged. From there, replaying the same body to the app's public webhook endpoint with a modified `shop-domain` (and/or `topic`) header requires no secret material and no further authentication, since `Registry.process` performs no cross-check between the signed body and the header-derived identity.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` values in the signed/verified material (or otherwise cryptographically bind them, e.g. by requiring the host application to independently confirm that `request.shop` corresponds to a shop with an active installation/session before trusting `WebhookMetadata#shop`). At minimum, document and enforce that `Registry.process` callers must verify `request.shop` against their own store of installed shops rather than treating the header as authenticated by the HMAC.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `{"id":1}` and header `x-shopify-hmac-sha256: <valid HMAC over the body>` (the attacker is the merchant who installed the app on `shop-a`, so this is fully observable to them).
2. Attacker POSTs the exact same raw body and the exact same HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-victim.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the (unchanged) body against the (unchanged) HMAC.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches to the topic handler with `WebhookMetadata.new(..., shop: "shop-victim.myshopify.com", body: {"id"=>1}, ...)`, causing the host application to process/store data as if it originated from `shop-victim`.
