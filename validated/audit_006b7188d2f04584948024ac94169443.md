### Title
Withdraw slippage protection can be entirely bypassed when `min_coin_amount`/`min_pc_amount` are omitted, enabling sandwich attacks on LP withdrawals - (File: `program/src/processor.rs`, `program/src/instruction.rs`)

### Summary
The `Withdraw` instruction accepts `min_coin_amount` and `min_pc_amount` as `Option<u64>`, and the processor only enforces the slippage check when **both** are `Some`. If a withdrawer submits the legacy/short instruction encoding (without appending these two `u64` fields), the check is skipped entirely, meaning the LP receives whatever `coin_amount`/`pc_amount` the pool computes at execution time with no floor — this is the same "no slippage bound enforced" bug class as the reported Perp report, just realized through an optional field instead of a hardcoded 0.

### Finding Description
`WithdrawInstruction` defines `min_coin_amount` and `min_pc_amount` as optional fields, populated only if the instruction data is long enough: [1](#0-0) 

In the withdraw processor, after computing `coin_amount`/`pc_amount` from the current pool reserves via `InvariantPool::exchange_pool_to_token`, the slippage floor is applied **only if both options are present**: [2](#0-1) 

If a caller sends a withdraw transaction using the short (8-byte, `amount`-only) instruction payload — which `unpack` explicitly supports as a legitimate legacy format — `min_coin_amount` and `min_pc_amount` are `None`, and the branch at lines 1780-1786 is skipped completely. The withdrawal then proceeds using whatever `coin_amount`/`pc_amount` were calculated from the vault balances at execution time, with zero protection against reserve-ratio manipulation immediately before the withdraw executes.

Because `coin_amount`/`pc_amount` are derived directly from `amm_coin_vault.amount`/`amm_pc_vault.amount` at the time of processing (via `calc_total_without_take_pnl_no_orderbook` and `InvariantPool`), an attacker can, in the same or adjacent transaction ordering, swap into the pool to skew the coin/pc ratio right before the victim's unprotected withdraw executes, then swap back afterward — capturing the value the victim would otherwise have received. This directly mirrors the reported issue's root cause: a slippage-bound parameter exists in the interface but is not actually enforced under a reachable code path.

### Impact Explanation
A withdrawing LP using the legacy instruction encoding (with no min amounts) can have their proportional share of `coin`/`pc` reserves siphoned via sandwich attack, resulting in direct fund loss proportional to the reserve manipulation an attacker can achieve within their capital and the pool's fee/slippage curve. This is a concrete theft-of-user-funds vector reachable from a single attacker-controlled transaction sequence targeting a pending, unprotected withdraw.

### Likelihood Explanation
Likelihood depends on whether any withdraw caller (user-facing tooling, other integrating protocols, or a user manually crafting the instruction) submits the short-form `Withdraw` payload without the optional min-amount suffix — the on-chain program itself explicitly accepts and processes this format as valid, so the vulnerable path is fully reachable by any unprivileged signer choosing to (or being caused to, by client tooling) omit the fields. Any public mempool visibility of the pending withdraw transaction is sufficient for a searcher to sandwich it.

### Recommendation
Make slippage protection mandatory rather than optional for `Withdraw`: either always require `min_coin_amount`/`min_pc_amount` in the instruction encoding (reject short payloads), or independently validate each bound individually rather than only checking when both are simultaneously `Some` (currently, even supplying only one of the two silently disables protection on both amounts).

### Proof of Concept
1. Attacker observes a pending `Withdraw` transaction (tag `4`) whose instruction data is exactly 9 bytes (`tag + amount`), i.e. `min_coin_amount`/`min_pc_amount` unset, per `AmmInstruction::unpack` tag `4` handling. [1](#0-0) 
2. Attacker front-runs with a large swap (`SwapBaseIn`/`SwapBaseOut`) that skews `amm_coin_vault`/`amm_pc_vault` balances.
3. Victim's withdraw executes: `coin_amount`/`pc_amount` are computed from the now-skewed reserves, and since `withdraw.min_coin_amount`/`min_pc_amount` are `None`, the check block is bypassed entirely. [3](#0-2) 
4. Attacker back-runs with an opposite swap to restore the ratio, capturing the value taken from the victim's mispriced withdrawal.
