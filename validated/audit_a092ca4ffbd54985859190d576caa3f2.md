The report describes a class of bug where an authenticated field can be swapped for another, unauthenticated one after the identity check passes. The closest analog reachable in this gem's own code (not the host app, not privileged credentials) is in the webhook signature verification path.

### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only. The `shop` (tenant identifier) is read from the `X-Shopify-Shop-Domain` header, which is never included in the signed payload. `Registry.process` trusts this unauthenticated `shop` value and forwards it straight into the handler as the tenant identifier, exactly as the gem's own documentation instructs apps to do.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery`'s `hmac` against `to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body, while `shop` is pulled straight from a header without ever being included in the signed string: [2](#0-1) 

`Registry.process` verifies the HMAC and then hands the caller-controlled, unauthenticated `request.shop` value to the handler as if it were an authenticated tenant identifier: [3](#0-2) 

The documented integration pattern explicitly instructs apps to key off `data.shop` as the trusted tenant identifier for the webhook body: [4](#0-3) 

The binding that should hold is: `shop authenticated by HMAC == shop the body is processed for`. In reality the HMAC only proves `body authenticated == body processed`; the `shop` header is not bound to anything cryptographic. Any party that controls a genuine, validly-signed webhook body (any merchant with the app installed receives such requests) can resend that exact body to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` value. `HmacValidator.validate` will still pass (it never looks at the header), and `Registry.process` will call the handler with the attacker-chosen `shop`.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-processed binding, meeting the "cross-tenant access" criterion. The app's `api_secret_key` is shared across every installed shop, so the HMAC alone cannot distinguish which tenant a payload legitimately belongs to; that job is left entirely to the unauthenticated header. Any downstream logic that persists/attributes webhook data by `data.shop` (as the gem's own docs instruct) can have another tenant's records overwritten, tampered with, or confused, or can be triggered to run for a shop the attacker doesn't control.

### Likelihood Explanation
Any installed merchant/tenant of the host app is capable of generating a legitimately signed webhook body for their own shop (e.g., simply by taking an action that triggers a real webhook, since the shared secret only covers the body). Forging the header on replay requires no secret material and no elevated access — only the ability to send an HTTP request to the app's already-public webhook endpoint.

### Recommendation
Do not treat `request.shop` (or `WebhookMetadata#shop`) as authenticated. At minimum:
- Include `shop` (and other identity-bearing headers) in the HMAC-signed payload construction, or
- Require the caller to independently verify that `request.shop` matches an expected/registered shop for that webhook subscription before dispatching to the handler, and document this requirement prominently instead of encouraging direct trust of `data.shop`.

### Proof of Concept
1. Shop A (attacker, a legitimate installed merchant) triggers a real event (e.g. `orders/create`) and captures the resulting webhook POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the shared `api_secret_key`).
2. Attacker replays the exact same request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` from `shop-a.myshopify.com` to `shop-b.myshopify.com` (a victim tenant).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...， "x-shopify-shop-domain" => "shop-b.myshopify.com"})` is constructed; `hmac` still equals `H`, and `to_signable_string` still equals `B`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because verification only checks `B` against `H`. [3](#0-2) 
5. The registered handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and `body` from shop A's event, and — following the documented pattern of keying persistence off `data.shop` — processes/stores/attributes shop A's data under shop B's tenant.
