Based on my analysis, I found a concrete, in-scope vulnerability class matching the hint list exactly: **a field acted on but not covered by the HMAC**.

### Title
Webhook shop-domain identity spoofing via HMAC that only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The webhook `HmacValidator` proves only that the raw JSON body was signed with the app's `client_secret`; it never binds the `shop-domain`, `topic`, or `webhook-id` headers into the signature. Any of these headers can be swapped by an attacker between the time Shopify signs a webhook and the time it reaches the app's public webhook endpoint, without invalidating the HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: ` [1](#0-0) `. The `shop`, `topic`, and `webhook_id` accessors are all read straight from HTTP headers that are never part of the signed material: ` [2](#0-1) `.

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e. body-vs-secret) and then dispatches the handler using `request.shop`, `request.topic`, and `request.webhook_id` taken verbatim from the unauthenticated headers: ` [3](#0-2) `.

`HmacValidator.validate` only checks the signable string (body) against the secret with `OpenSSL.secure_compare`: ` [4](#0-3) `.

Because the body-only HMAC is identical for any request carrying the same bytes regardless of which shop it is claimed to be from, an attacker who is simply a merchant that has legitimately installed the app on their own store (no special credential, no `api_secret_key`, no access token) can capture one of their own real, validly-signed webhook deliveries (topic, body, and its valid `X-Shopify-Hmac-Sha256` value) and replay that exact `(body, hmac)` pair directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a victim shop. The HMAC check still passes because it never inspected those headers, and `WebhookMetadata.shop` will report the victim's domain to the host application's handler: ` [5](#0-4) `.

This breaks the identity binding: `shop authenticated == shop the HMAC is bound to` is false; the shop the handler trusts is not the shop the HMAC actually authenticates. Any host application that looks up the victim's stored session/access token keyed by `request.shop` (the gem's own documented `WebhookMetadata#shop` API, populated directly by this library) will then act on attacker-supplied body data under the victim tenant's identity — a cross-tenant confusion entirely rooted in this gem's own `Request`/`Registry` implementation, not host misuse.

### Impact Explanation
This is a cross-tenant identity-spoofing primitive: an unprivileged attacker (any merchant able to install the app once) can make the app process attacker-chosen webhook payloads under an arbitrary victim shop's identity, because the shop identity claim is not cryptographically bound to the signature the library relies on to authenticate the request. Depending on the topic and how the host app keys its business logic off `WebhookMetadata#shop` (e.g. `shop/redact`, `app/uninstalled`, order/customer topics), this can trigger cross-tenant data mutation, GDPR-redaction abuse, or state corruption scoped to a shop the attacker does not control.

### Likelihood Explanation
Likelihood is high for any app that exposes a webhook endpoint built on this gem: capturing one's own legitimately-signed webhook requires nothing more than installing the app (a normal, unprivileged flow), and replaying it with a modified header requires only basic HTTP tooling. No secrets, tokens, or elevated access are needed.

### Recommendation
Bind the tenant/topic identity into the value that is HMAC-verified, or independently re-derive/verify the shop from data that is itself signed (e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or reject/cross-check the header-derived `shop` against a shop identifier embedded in the verified body where the topic's payload provides one). At minimum, document and enforce that the `shop`/`topic`/`webhook_id` headers are only trustworthy in combination with the HMAC covering them, since currently `HmacValidator` in `lib/shopify_api/utils/hmac_validator.rb` provides no such guarantee for `Webhooks::Request`.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and registers a webhook (e.g. `shop/redact`).
2. Shopify delivers a legitimate webhook to the app: body `B`, headers include `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `client_secret`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `body=B`, `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` directly to the app's public webhook URL.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `body` vs `H` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app's business logic to run attacker-controlled content against the victim tenant.
