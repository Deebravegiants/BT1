## Analysis

The reported bug class — a function accepting `msg.value >= requiredAmount` but sending the entire `msg.value` onward (or otherwise failing to return unspent value to the caller) instead of refunding the excess to the user — has a direct analog in `EvmHost`'s native-token payment path for dispatching ISMP messages.

### Root cause

`EvmHost::dispatch(DispatchPost)`, `EvmHost::dispatch(DispatchGet)`, and `EvmHost::fundRequest()` all accept `payable` calls and, when `msg.value > 0`, forward the **entire** `msg.value` into a UniswapV2 `swapETHForExactTokens` call to buy an exact amount of `feeToken`: [1](#0-0) 

The Uniswap V2 router's `swapETHForExactTokens` refunds any unused ETH (`msg.value - amounts[0]`) to its **direct caller** via `msg.sender`. Since `EvmHost` itself calls the router, that refund lands back on `EvmHost`, not on the original transaction sender/application that supplied the `msg.value`. This is confirmed by the contract's own comment on its `receive()` function: [2](#0-1) 

The same pattern repeats in `dispatch(DispatchGet)` and `fundRequest()`: [3](#0-2) [4](#0-3) 

Documentation explicitly instructs integrators to size `msg.value` generously ("User must send enough native tokens to cover fees") without providing any exact-amount guarantee or refund mechanism back to the caller: [5](#0-4) 

Any surplus ETH is retained permanently by `EvmHost` as undifferentiated balance, recoverable only by cross-chain governance via `withdraw()` — never by the paying user: [6](#0-5) 

Notably, the newer `IntentGatewayV2`/`IntentsBase` applications already recognize and fix exactly this failure mode by explicitly refunding unspent `msgValue` back to `msg.sender` after any native-to-feeToken swap: [7](#0-6) [8](#0-7) 

This confirms the correct pattern is known and used elsewhere in the codebase, but `EvmHost`'s core `dispatch`/`fundRequest` functions — which every `IApp` and end user integrates with directly for cross-chain messaging — do not implement it.

### Title
Excess native ETH sent to `EvmHost::dispatch()`/`fundRequest()` is not refunded to the caller, permanently absorbed as host balance - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost::dispatch(DispatchPost)`, `EvmHost::dispatch(DispatchGet)`, and `EvmHost::fundRequest()` forward the caller's full `msg.value` into `swapETHForExactTokens`, which only spends the exact ETH amount needed for the fee and refunds the rest — but that refund goes to `EvmHost` itself (the direct router caller), not the original user/app that supplied `msg.value`. The excess is retained as host balance, withdrawable only by cross-chain governance.

### Finding Description
Applications and users pay Hyperbridge dispatch fees either in the fee token or in native token via `msg.value`, per the documented flow: `IDispatcher(host()).dispatch{value: msg.value}(post)`. When paying in native token, `EvmHost.dispatch()` calls `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. Because Uniswap V2's `swapETHForExactTokens` only requires enough ETH to cover the quoted `amounts[0]`, and refunds any excess (`msg.value - amounts[0]`) to its immediate caller, the refund is paid to `EvmHost` (the contract that invoked the router), not to the end-user/application whose funds were spent. `EvmHost`'s `receive()` function is explicitly documented as collecting this dust. The same defect exists in `dispatch(DispatchGet)` and `fundRequest()`.

### Impact Explanation
Any unprivileged caller who slightly overestimates the native-ETH amount required to cover the fee-token swap (which is expected practice to protect against price movement between fee quoting off-chain and on-chain execution) permanently loses the difference — it becomes indistinguishable host balance, recoverable only through a cross-chain governance `withdraw()` call, never returned to the payer. This is a real, reachable loss-of-funds path for the exact class of "unrefunded overpayment" bug described in the report, triggered by a single unprivileged dispatch/fundRequest call — not a privileged or admin-only path.

### Likelihood Explanation
High reachability: every `IApp`/user integrating native-token fee payment per the documented pattern is exposed, and slippage/price-movement buffers are a normal, encouraged practice (the docs tell integrators to "send enough native tokens"), making overpayment routine rather than an edge case.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, compute the actual ETH spent (`amounts[0]` returned by the swap) and refund `msg.value - amounts[0]` back to `_msgSender()` (or the intended payer), mirroring the pattern already implemented in `IntentGatewayV2Placement`/`IntentsBase._sendValue` refund logic.

### Proof of Concept
1. Caller estimates the fee-token cost of `post.fee` off-chain and, to buffer against slippage, sends `msg.value = quoted * 1.5`.
2. `EvmHost.dispatch(post)` forwards the full `msg.value` to `swapETHForExactTokens{value: msg.value}(post.fee, ...)`.
3. The router spends only `amounts[0]` (≈ `quoted`) and refunds `msg.value - amounts[0]` (the ~50% buffer) to `msg.sender`, which is `EvmHost`.
4. `EvmHost` never forwards this refund to the caller; it silently increases `address(this).balance`, capturable only via governance `withdraw()` — the caller has permanently lost the buffer amount.
