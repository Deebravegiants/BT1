### Title
CASE 2 "stateless" Emporium ops execute with `msg.sender == Emporium` for every external protocol, letting any user hijack another user's on-chain position and drain it into their own shielded UTXO - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
In `EmporiumUpgradeable.runAction`, CASE 2 ("Stateless Interaction") performs `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract, so `msg.sender` in the external protocol is always `address(Emporium)`, never a per-user address. Any stateful external protocol that records ownership keyed by `msg.sender` (vault shares, staking positions, NFTs, order books) will therefore attribute state opened via CASE 2 to the single shared `Emporium` contract, not to the individual user. Because `getBalancesForArray`/`handleOut` in the same function credit any Emporium-token-balance increase to whoever is currently calling `transact`, a second, unrelated, unprivileged attacker can submit their own valid Hinkal transaction with a CASE-2 op that withdraws/claims the victim's externally-tracked position (owned by "Emporium") and have the proceeds minted as their own shielded UTXO.

### Finding Description
Broken equality: the protocol's intended invariant is
`positionOwner(after user's op) == user's own scoped identity` (true for CASE 1 via `HinkalWallet.callHinkalWallet`, `contracts/external-actions/emporium/HinkalWallet.sol:28-34`, guarded by `onlyEmporium`).

For CASE 2 the actual value is:
`positionOwner(after user's op) == address(Emporium)`
for any external protocol whose ownership bookkeeping is `msg.sender`-based, since the call is a plain low-level `.call` from the Emporium contract itself: [1](#0-0) 

There is no code path in `runAction` (or anywhere else reachable from CASE 2) that resolves the call context to anything other than `address(this)`; `op.endpoint` is fully attacker/user-controlled and unwhitelisted — it comes straight out of `circomData.externalActionData.externalActionMetadata`, decoded into `EmporiumStack`/`EmporiumOperation` with no allowlist check: [2](#0-1) 

`EmporiumOperation.endpoint`/`callData` are hashed into the EIP-712 signature only when `stack.signerAddress != address(0)` (`verifyWallet`), which governs relay-fee accounting and CASE-1 wallet routing, not who owns state at `op.endpoint` — the ownership hijack described here applies regardless of whether a signer is set, because CASE 2 is exactly the branch taken whenever `invokeWallet` is false or `signerAddress == address(0)`.

After the loop of ops, the function measures `balanceChange` purely as the delta of `Emporium`'s own token balances (`getBalancesForArray`, `contracts/Transferer.sol:169-176`, backed by `balanceOf(address(this))`/`address(this).balance`), and unconditionally mints a UTXO for any positive delta to whoever is the current `msg.sender` of `runAction` (the Hinkal contract, acting for the current caller/prover): [3](#0-2) 

Exploit flow:
1. Victim submits a Hinkal `transact()` with `externalActionId = Emporium` and a CASE-2 op (`invokeWallet=false` or `signerAddress=address(0)`) that opens a position on some external protocol `P` (e.g. `P.stake(amount)`, `P.deposit(amount, receiver=msg.sender)`). Since the call originates from Emporium, `P` records the position under `msg.sender == address(Emporium)`.
2. Attacker (any unprivileged EOA with their own UTXOs/proofs) submits their own `transact()` with `externalActionId = Emporium` and a CASE-2 op calling `P.withdraw()`/`P.claim()`/`P.redeem()` etc. Because `P` also sees `msg.sender == address(Emporium)` for this call, and Emporium is the recorded owner of the victim's position, the withdrawal succeeds and sends the underlying tokens back to Emporium's own balance.
3. Emporium's `runAction` observes the resulting balance increase in `circomData.erc20TokenAddresses` (attacker-chosen token list) and calls `handleOut`, transferring the withdrawn tokens out and creating a UTXO for the attacker's `circomData.stealthAddressStructure` — i.e., the attacker mints a shielded note for value that belonged to the victim.

None of the existing guards prevent this: `onlyAllowedRecipient` only checks the caller is the Hinkal contract, `verifyWallet`/EIP-712 signature checks are only exercised for CASE-1/relay-fee bookkeeping and do not restrict `op.endpoint`/`callData` semantics for CASE 2, and the circuit-side checks (`inTotal + amountChanges === outTotal`, nullifier/root checks) only constrain the attacker's own shielded balance accounting — they say nothing about who legitimately owns externally-tracked, non-Hinkal state at `op.endpoint`.

### Impact Explanation
Any unprivileged attacker can steal externally-held funds/positions that another Hinkal user opened via a CASE-2 ("stateless") Emporium op on any stateful external protocol (vaults, staking, lending, NFT mints, order books) that tracks ownership by `msg.sender`. This is direct theft of user funds routed through Hinkal's own shielded-output minting path (`handleOut`), satisfying the Critical bar ("direct theft of shielded or in-flight user funds ... executing calls or moving assets a wallet owner or prover never authorised"). It is repeatable against every future protocol integration reachable via CASE 2, and against any victim who used CASE 2 for a stateful interaction instead of CASE 1's wallet-scoped path.

### Likelihood Explanation
Preconditions: a victim (or the protocol's own tooling/UI) must use CASE 2 to interact with an external protocol whose ownership is `msg.sender`-keyed and persists across calls (as opposed to a pure swap that settles balance in the same call). This is plausible/likely because CASE 2 is documented as the generic "any endpoint, any calldata" path and nothing in the code base restricts it to stateless protocols — `op.endpoint` is arbitrary and unwhitelisted. Once such a position exists, exploitation costs the attacker only a normal Hinkal `transact()` (their own valid proof/UTXOs, no privileged role needed) plus knowledge of the external protocol's withdraw/claim interface and the position size — both discoverable on-chain. Fully repeatable for every victim/position that follows this pattern.

### Recommendation
- Route every CASE-2 op through a per-user (or per-transaction) disposable proxy/wallet contract (analogous to `HinkalWallet`) instead of calling `op.endpoint` directly from the shared `Emporium` contract, so that `msg.sender` seen by external protocols is never a value shared across users.
- Alternatively, restrict CASE 2 to an allowlist of endpoints verified to be stateless (e.g., swap routers that fully settle within one call and never persist ownership keyed by `msg.sender`), and reject `op.endpoint` calls to unverified/unlisted external protocols.
- Document/enforce (at the interface or registration level) that any external protocol integrated via CASE 2 must not persist `msg.sender`-keyed ownership across transactions.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, `Hinkal`, and a mock stateful protocol `MockVault` with `deposit(uint256) -> credits msg.sender`, `withdraw(uint256) -> requires balance[msg.sender] >= amount, sends underlying ERC20 to msg.sender`.
2. Fund victim's shielded balance; victim calls `Hinkal.transact` with `externalActionId = Emporium`, a CASE-2 `EmporiumOperation{endpoint: MockVault, invokeWallet: false, callData: abi.encodeCall(MockVault.deposit, (amount))}`. Assert `MockVault.balanceOf(address(Emporium)) == amount` and `MockVault.balanceOf(victimAddress) == 0`.
3. Attacker (separate identity, own deposited UTXO, unrelated to victim) calls `Hinkal.transact` with `externalActionId = Emporium`, `erc20TokenAddresses = [underlyingToken]`, a CASE-2 op `{endpoint: MockVault, invokeWallet:false, callData: abi.encodeCall(MockVault.withdraw, (amount))}`.
4. Assert: (a) call succeeds without reverting despite attacker never having deposited into `MockVault`; (b) `MockVault.balanceOf(address(Emporium))` drops to 0; (c) attacker receives a new shielded UTXO of `amount` in `underlyingToken` (verify via emitted commitment/leaf and attacker's ability to later spend it), while the victim's on-chain claim to those funds has vanished.
5. This demonstrates `positionOwner(after CASE-2 op) == address(Emporium)` and that the shared identity lets an unrelated attacker redeem it, breaking the intended per-user ownership invariant and resulting in direct fund theft.
