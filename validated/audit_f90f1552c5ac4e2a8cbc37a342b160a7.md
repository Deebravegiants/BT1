## Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook forgery - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate(request)` succeeds, and then hands the handler a `shop` value taken directly from the `x-shopify-shop-domain` header. However, the HMAC signature only covers the raw request body — never the `shop-domain` header. Any attacker who can obtain one validly-signed webhook body (trivial: install the target app on their own shop and trigger any webhook event) can replay that exact body with the `shop-domain` header rewritten to a different tenant's domain, and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` decodes the signature from the `hmac-sha256` header, and `#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop` accessor reads a separate, unauthenticated header: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., only the body) and compares it to the supplied `hmac`: [4](#0-3) 

`Registry.process` uses this validation as the sole authenticity gate, then forwards the unauthenticated `request.shop` value straight to the app's handler: [5](#0-4) 

The identity binding that should hold is:
`HMAC-verified bytes == bytes the handler trusts as the tenant identity`

Here that equality is broken: the HMAC only proves "this exact `raw_body` was signed with our `api_secret_key` at some point," while `data.shop` (the tenant identity the handler acts on) comes from a header that is never part of the signed content. Because Shopify signs webhooks with the app-wide `api_secret_key` (shared across every shop that installs the app, not a per-shop secret), any shop that installs the app can produce a validly-signed body and then relabel it as belonging to any other shop.

### Impact Explanation
This is a cross-tenant identity confusion: a merchant/attacker with no elevated privileges (simply installing the public app on their own store, or capturing a webhook delivery) can forge webhook events that the app attributes to an arbitrary victim shop. Any handler logic keyed on `data.shop` (e.g., updating billing state, marking an order paid, disabling protections, writing to that shop's tenant record) can be triggered against a shop the attacker doesn't control, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High feasibility for anyone who can install the target Shopify app (a normal, unprivileged flow for any public app) or who can capture one webhook HTTP request (e.g., via a logging proxy, a misconfigured webhook forwarder, or their own installed instance). No knowledge of `api_secret_key` is required — the attacker reuses a legitimately-signed body they already possess and only tampers with the unauthenticated header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed content checked by `HmacValidator`, or independently verify that the `shop-domain` header matches an expected/registered shop for the given webhook subscription before invoking the handler. At minimum, `Request#to_signable_string` should not be the only thing verified when `Registry.process` implicitly trusts `request.shop`; the header must be authenticated the same way it's consumed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any event (e.g., updates an order) so Shopify sends a real webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` for that `raw_body`.
2. Attacker captures this request (own endpoint logs, proxy, etc.).
3. Attacker resends the identical `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks the (unchanged) `raw_body` against the (unchanged) `hmac`.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act on the victim shop's identity using attacker-controlled body content.
