### Title
Fee-swap deadline hard-coded to `block.timestamp` provides no expiration/slippage protection - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` swap any native ETH sent by the caller into fee tokens via Uniswap V2's `swapETHForExactTokens`, but pass `block.timestamp` (evaluated at execution time) as the `deadline` argument, exactly mirroring the reported bug class of a swap with no meaningful expiration/deadline protection.

### Finding Description
Both dispatch entry points build a swap path and call:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
``` [1](#0-0) 
and the analogous logic for `DispatchGet`: [2](#0-1) 

The Uniswap router's deadline check is `require(deadline >= block.timestamp)`. Because the value supplied here is `block.timestamp` itself, taken at the moment the swap actually executes (not at the moment the caller signed/submitted the transaction), the check is a tautology — it is `block.timestamp >= block.timestamp`, which is always true regardless of how long the transaction sat pending in the mempool. This is functionally identical to the reported issue where the deadline parameter is omitted entirely: the swap can be included and executed at any time, including long after the caller intended, with no bound on how stale the market conditions are relative to when the caller committed to the transaction.

This code path is reachable by any unprivileged caller: `dispatch(DispatchPost)`/`dispatch(DispatchGet)` are the core, permissionless entry points used by any application contract dispatching a cross-chain ISMP message and paying the relayer fee in native ETH.

### Impact Explanation
Because the deadline offers no real protection, a dispatcher's fee-swap transaction can be delayed and/or sandwiched by MEV actors: `swapETHForExactTokens` fixes the desired fee-token output (`post.fee`/`get.fee`) and bounds the ETH input only by `msg.value`. An attacker can manipulate the WETH/feeToken pool immediately before the swap executes (front-running) to push the effective price up toward the `msg.value` ceiling, extracting the difference between fair value and the amount the dispatcher is forced to spend, then restore the pool afterward (back-running) — a classic sandwich attack that a correctly-set, caller-chosen deadline (bounding the acceptable staleness window) does not by itself prevent, but at minimum a real deadline limits the exposure window; here the "deadline" provides zero limitation since it is recomputed to always equal the execution time. This results in dispatchers systematically overpaying ETH for relayer fees, i.e., loss of funds for any application/user that funds POST/GET dispatch with native ETH.

### Likelihood Explanation
Every `dispatch(DispatchPost)`/`dispatch(DispatchGet)` call funded with native ETH goes through this code path unconditionally — it requires no special configuration or malicious insider, only a public mempool and an economically motivated searcher/relayer, which is realistic on any EVM chain with public mempools or complicit block builders.

### Recommendation
Accept a caller-supplied, meaningful `deadline` (or a bounded relative expiry) as part of `DispatchPost`/`DispatchGet`, or at minimum derive the deadline from a value fixed at request-construction time, and pass that through to `swapETHForExactTokens` instead of `block.timestamp`. Additionally consider adding a slippage/quote check before swapping to bound the acceptable ETH cost.

### Proof of Concept
1. Application contract calls `EvmHost.dispatch(DispatchPost)` (or `DispatchGet`) with `msg.value > 0` to pay the relayer fee in native ETH.
2. The transaction is broadcast and sits in the public mempool.
3. A searcher observes the pending transaction and, immediately before it is mined, manipulates the WETH/feeToken Uniswap V2 pool to increase the ETH price needed to buy `post.fee` fee tokens, up to just under `msg.value`.
4. `EvmHost.dispatch` executes; because `deadline == block.timestamp` at execution time, the router's deadline check trivially passes regardless of the delay or manipulation.
5. The searcher back-runs to restore the pool, pocketing the difference between the fair-value ETH cost and the amount actually spent by the dispatcher, at the dispatcher's expense.
