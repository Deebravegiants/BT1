### Title
Front-running `Initialize2` permanently blocks legitimate pool creation for a market - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives all of the AMM's core accounts (`target_orders`, `lp_mint`, `coin_vault`, `pc_vault`, `amm_info`) deterministically from the OpenBook `market` pubkey via `generate_amm_associated_account` / `generate_amm_associated_spl_mint` / `generate_amm_associated_spl_token`, which all use `get_associated_address_and_bump_seed(program_id, market_account.key, associated_seed, program_id)`. Because these addresses depend only on the immutable `market` key, any unprivileged party can be the first to submit a valid `Initialize2` transaction for that market, permanently consuming the only address at which a legitimate pool for that market can ever be created. This is directly analogous to the reported `pontis-bridge-v1.sol` bug class: a shared, address/slot-bound resource (there, the `PegOutKeyUtxo` queue; here, the market-derived AMM PDA set) can be consumed cheaply by an attacker before the legitimate user acts, denying the core function (bridging out / pool creation) to that legitimate user — except here the denial is not "temporary" but permanent, since there is no re-initialization or account-closing path once the associated accounts are assigned.

### Finding Description
`process_initialize2` calls `generate_amm_associated_account` and `generate_amm_associated_spl_mint`/`generate_amm_associated_spl_token`, each of which checks:
```
if associated_token_account.owner == system_program_account.key {
    // allocate/assign/initialize the account
} else {
    return Err(AmmError::RepeatCreateAmm.into());
}
``` [1](#0-0) [2](#0-1) 

The associated addresses are derived solely from `market_info.key` and fixed seeds (`TARGET_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED`, `AMM_ASSOCIATED_SEED`): [3](#0-2) 

Anyone holding an OpenBook market not yet associated with an AMM pool, plus a small nonzero amount of the market's `coin_mint`/`pc_mint` tokens, can call `Initialize2` themselves. The only real cost gates are the `create_pool_fee` transfer (a config-controlled fee, potentially small or zero) and the requirement that computed `liquidity` exceed `10^lp_decimals` (`InitLpAmountTooLess`): [4](#0-3) 

Once any account is allocated/assigned by an attacker's `Initialize2` call, every subsequent `Initialize2` attempt for that same `market` — including one from the legitimate project/market-maker — hits `RepeatCreateAmm` in `generate_amm_associated_account`/`generate_amm_associated_spl_mint` and fails permanently. There is no instruction in the program to close or reset these associated accounts once created (no matching `close_account`/reset path found), so the market is permanently unable to have its intended pool created by this program.

### Impact Explanation
This maps to "insufficient restriction leading to DOS of core functions," but with strictly higher severity than the original report: the original bug produces a *temporary* DOS of bridging (recoverable once the off-chain system tops up `PegOutKeyUtxo`), whereas here the DOS is *permanent* for that market — there is no off-chain or on-chain remediation path once the deterministic PDAs are consumed. Beyond pure DOS, the attacker also fully controls the initial coin/pc ratio and mints themselves the resulting LP tokens, meaning they can additionally poison/claim the pool's initial state (skewed price, minimal liquidity) before anyone else can interact with it, which can facilitate downstream price-manipulation/griefing against later depositors or the legitimate project.

### Likelihood Explanation
Any unprivileged actor who can observe a not-yet-initialized OpenBook market (e.g., watching for market creation, or a project's own market prior to their planned `Initialize2` call) can race to submit `Initialize2` first. The cost is a config-controlled `create_pool_fee` plus a token amount just above the `InitLpAmountTooLess` bound — no minimum notional value is otherwise enforced. This is a single, unprivileged, attacker-chosen-accounts transaction, requiring no special access, matching the reachable-path constraints of this scan.

### Recommendation
Add an on-chain mechanism decoupling "who may create the canonical pool for a market" from "who first submits a valid transaction to the deterministic address," e.g.: allow only a designated/whitelisted creator (or the market's original creator) to initialize a pool for a given market, or provide an authorized recovery/close path so a griefed market's associated accounts can be reclaimed and a fresh initialization attempted by the legitimate party. At minimum, raise the effective economic cost of grief-initializing (deterministic minimum notional liquidity check, not just `> 10^decimals`) so front-running is not the cheapest execution path for an attacker.

### Proof of Concept
1. Attacker monitors on-chain OpenBook market creations for a market they know a legitimate project intends to use for `Initialize2`.
2. Attacker acquires a tiny nonzero amount of `coin_mint` and `pc_mint` tokens for that market (just enough to satisfy `amm_coin_vault.amount == 0` / `amm_pc_vault.amount == 0` checks and clear `InitLpAmountTooLess`). [5](#0-4) 
3. Attacker submits `Initialize2` for that `market` before the legitimate project does, paying only the `create_pool_fee` (config value, can be small) plus rent for the associated PDAs. [6](#0-5) 
4. `generate_amm_associated_account`/`generate_amm_associated_spl_mint`/`generate_amm_associated_spl_token` succeed for the attacker (system-owned → allocated/assigned), and the AMM is initialized with the attacker's chosen skewed ratio and their own LP tokens minted. [7](#0-6) 
5. When the legitimate project later calls `Initialize2` for the same `market`, every associated-account helper now finds `associated_token_account.owner != system_program_account.key` and returns `AmmError::RepeatCreateAmm`, permanently blocking creation of the intended pool for that market.
