### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let a single `msg.value` back multiple independent ETH deposit claims, minting shielded ETH without matching backing - ([File: contracts/Hinkal.sol])

### Summary
`Hinkal.transact` never enforces that token addresses in `circomData.erc20TokenAddresses` are unique, and the ETH deposit path (`transferERC20TokenFromOrCheckETH` with `_to == address(this)`) only *asserts* `msg.value == _value` without ever consuming or tracking it. Combined with the per-index `balanceDif` formula that adds `int256(msg.value)` independently at every index where the token is `address(0)`, an attacker can list `address(0)` at N indices with `amountChanges[i] == msg.value` for each, pass the balance-equality check at all N indices, and mint N times the shielded value with a single real ETH transfer.

### Finding Description
The claimed equality (real ETH received) `==` (shielded ETH value created) is broken.

Trace:
- `transact` captures `oldBalances`/`newBalances` via `getBalancesForArray` [1](#0-0) , both taken *after* `msg.value` has already been credited to `address(this).balance` by the EVM (the function is `payable`), so a pure ETH deposit produces zero delta between old/new balance during the body.
- For every index where `erc20TokenAddresses[i] == address(0)`, the code manually re-adds `msg.value` to compensate for that: `balanceDif = int256(newBalances[i]) + int256(msg.value) - int256(oldBalances[i])` [2](#0-1) . This addition is unconditional per loop iteration - it does not track or subtract how much of `msg.value` has already been "claimed" by a previous index.
- In `_internalTransact`, a positive `deltaAmountChange` (deposit) for `address(0)` calls `transferERC20TokenFromOrCheckETH`, which for `_to == address(this)` only does `require(msg.value == _value, ...)` and performs **no actual transfer** [3](#0-2) . Since `msg.value` is a transaction-level constant, this check can be satisfied repeatedly at every index that claims `amountChanges[i] == msg.value`.
- `dimensionsCheck` and `checkOnchainCreation` in `HinkalHelper.sol` validate array lengths and onChainCreation-specific fields, but never check that `erc20TokenAddresses` entries are distinct [4](#0-3) [5](#0-4) .
- The circuit (`MainEVMCircuit.circom`) enforces `inTotal[i] + amountChanges[i] === outTotal[i]` per index independently; it has no global constraint tying together multiple indices that happen to reference the same token address, so the attacker (proving for their own UTXOs) can freely construct N independent per-index balance equations each claiming a deposit of `X = msg.value`.

Attacker's exact call: submit `transact` with `erc20TokenAddresses = [address(0), address(0), ..., address(0)]` (N times), `onChainCreation = [false, ...]`, `amountChanges = [X, X, ..., X]`, `msg.value = X`, and a valid self-generated proof where each index's local UTXO output total equals `X` with zero real input UTXO. Each loop iteration in `transact`'s post-processing computes `balanceDif_i = 0 + X = X`, matching `amountChanges[i] + utxoAmount(=0) = X`, so all N indices pass, and N sets of new commitments worth `X` each are inserted, while only one `X` of real ETH was ever sent.

Existing guards fail to prevent this: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` don't check token-address uniqueness; `verifyProof` only checks the attacker's self-consistent circuit logic, which has no cross-index uniqueness constraint either; the balance/slippage `require`s are satisfied individually per index because the compensating `+msg.value` term is added independently and the deposit "transfer" itself never actually moves or decrements ETH.

### Impact Explanation
The attacker mints shielded ETH commitments (via `amountChanges`) worth up to `N * msg.value` while only having deposited `msg.value` once - i.e., minting shielded value with no backing, a direct Critical-severity finding (unbacked minting of shielded value). This is fully repeatable per transaction and scales with the number of duplicate `address(0)` entries the attacker chooses (bounded only by `dimensions.tokenNumber` / gas limits), each time draining the protocol's real ETH reserves relative to the shielded liabilities it must eventually honor.

### Likelihood Explanation
No special preconditions beyond being an ordinary user: the attacker deposits their own funds, builds their own `CircomData`/`Dimensions`, and generates a proof for their own UTXOs, exactly matching the allowed attacker capability in scope. The array-length and per-index circuit constraints are all locally satisfiable by the attacker with dummy/self UTXOs. Attacker cost is one real ETH deposit of `X`; gain is `(N-1) * X` unbacked shielded value per call, fully repeatable.

### Recommendation
Track how much of `msg.value` has already been consumed across the loop (e.g., accumulate a running total of ETH deltas across all `address(0)` indices and require the sum to equal `msg.value` exactly once, not add `msg.value` per-index), and/or enforce uniqueness of `erc20TokenAddresses` entries in `dimensionsCheck`, and make `transferERC20TokenFromOrCheckETH`'s `_to == address(this)` branch consume/decrement a shared "remaining msg.value" counter rather than re-checking the raw `msg.value` at every call site.

### Proof of Concept
Foundry fork test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and a minimal verifier stub (mocked to always return true, since real proof generation is out of scope for a plan but the finding's arithmetic is proof-independent given the verifier only checks the public input vector matches circuit outputs, which the attacker fully controls as a valid self-consistent witness).
2. Build `CircomData` with `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [1 ether, 1 ether]`, `onChainCreation = [false, false]`, `slippageValues = [1 ether, 1 ether]`, valid `inputNullifiers`/`outCommitments` dimensions matching a 2-token layout with zero real input UTXOs and outputs of `1 ether` each.
3. Call `transact{value: 1 ether}(...)`.
4. Assert both `require` checks in the `for` loop at `contracts/Hinkal.sol:100-146` pass (no revert), i.e., assert `balanceDif == 1 ether` computed at both index 0 and index 1 despite `address(this).balance` only increasing by `1 ether` total.
5. Assert two output commitments each worth `1 ether` are inserted via `insertCommitments`, and assert `address(this).balance - balanceBefore == 1 ether` while total shielded value inserted `== 2 ether`, proving the equality (`real ETH received == shielded value minted`) is broken.
