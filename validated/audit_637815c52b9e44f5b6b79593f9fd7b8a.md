Confirmed: no on-chain state or check anywhere references a "blocked" leaf/UTXO — `markUtxosAsBlocked()` only emits an event, and `nullifiers`, `insertNullifiers`, `dimensionsCheck`, and `performHinkalChecks` have no notion of "blocked" leaves at all.

### Title
`createBlockedUtxos` in `prooflessDeposit` is a pure event with no on-chain enforcement, allowing the depositor to immediately spend "blocked" leaves via `transact` - ([File: contracts/Hinkal.sol])

### Summary
`Hinkal.prooflessDeposit` optionally calls `markUtxosAsBlocked()` when `createBlockedUtxos=true`, but that function only emits `BlockedUtxosCreated()` with no leaf identifiers and creates no on-chain hold state. The freshly inserted leaves are ordinary Merkle leaves indistinguishable from any other UTXO, so the same depositor can immediately spend them with a normal `transact` call using a self-generated proof, defeating any off-chain reservation semantics implied by the flag.

### Finding Description
The claimed equality — "leaf marked via `createBlockedUtxos` is reserved/immovable until the off-chain flow (e.g., `DepositOnChainUtxosExternalAction`/LI.FI order matching) completes" == "leaf is actually non-spendable on-chain" — does not hold.

Tracing the code:
- `Hinkal.prooflessDeposit` inserts commitments via `_createProoflessDepositCommitments` → `insertCommitments` → `insertMany`, which is the same leaf-insertion path used for any ordinary deposit. [1](#0-0) 
- If `createBlockedUtxos` is true, the only additional effect is `markUtxosAsBlocked()`, which emits `BlockedUtxosCreated()` — no leaf index, no commitment hash, and no write to any mapping/state. [2](#0-1) 
- Nothing in `Merkle`/`HinkalBase` records which leaves came from a "blocked" deposit; the `nullifiers` mapping only tracks whether a nullifier hash has been spent, with zero relation to the blocked-event. [3](#0-2) [4](#0-3) 
- `Hinkal.transact` calls `performHinkalChecks` (which runs `dimensionsCheck`/`checkOnchainCreation`), verifies the Groth16 proof, and checks `rootHashExists`, none of which reference blocked status. [5](#0-4) [6](#0-5) 
- Since the leaf inserted by `prooflessDeposit` is a normal commitment in the Merkle tree, once the tree root is available, the depositor can generate a valid spend proof for that exact leaf (owning the `nullifyingPrivateKey`) and call `transact`, which will pass `insertNullifiers` and complete the spend. [4](#0-3) 

The `DepositOnChainUtxosExternalAction` contract independently emits its own identically named `BlockedUtxosCreated()` event as well, confirming the "blocking" signal exists purely for off-chain consumers (relayers/order-matchers), with zero on-chain effect anywhere in this codebase. [7](#0-6) 

### Impact Explanation
An attacker who deposits via `prooflessDeposit(..., createBlockedUtxos=true, orderId)` to signal (to an off-chain relay/counterparty/LI.FI flow) that specific leaves are reserved for a matched order can, before that off-chain party executes its leg, spend the identical leaves via `transact` for a private withdrawal. This does not break Hinkal's internal solvency (nullifier single-spend still holds, so Hinkal itself does not lose funds), but it lets the attacker double-use committed value against a counterparty/relay who relied on the block signal — theft of counterparty/relay funds in a two-leg off-chain/on-chain flow. This matches the "High" category: theft of protocol/relay funds or an action executed that a counterparty never authorized, since the block event is a bypassed authorization signal.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: any EOA can call `prooflessDeposit` with `createBlockedUtxos=true` for their own funds, then independently craft a valid Groth16 proof and `CircomData.inputNullifiers` for the very UTXO(s) they just created (they hold the `nullifyingPrivateKey`). No relay, admin, or privileged role is required for the `transact` call if `circomData.relay == address(0)` (self-relayed). The attack is trivially repeatable per deposit and only bounded by the speed at which the off-chain listener reacts to the `BlockedUtxosCreated()` event versus the attacker's own `transact` submission (e.g., same-block or next-block).

### Recommendation
Introduce actual on-chain enforcement for blocked UTXOs: record the specific leaf/commitment (or nullifier-precursor) as blocked in contract storage when `createBlockedUtxos=true`, and have `insertNullifiers`/`transact` check that mapping and reject (or require an authorized unblocking call, e.g. by the relay/order-matcher) before allowing a spend of a still-blocked leaf. Alternatively, remove the misleading `createBlockedUtxos` flag/event if the protocol intends for order-matching to rely purely on off-chain timing assumptions, and clearly document that no on-chain lock exists.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `HinkalHelperManager`, verifier, and a test ERC20; fund attacker EOA.
2. Attacker calls `Hinkal.prooflessDeposit([token], [amount], [stealthAddressStructure], [encryptedOutput], true, "orderXYZ")`.
   - Assert `BlockedUtxosCreated()` was emitted and a `NewCommitment` event with the new leaf/commitment was emitted.
3. Off-chain, compute the corresponding nullifier hash for that leaf using the attacker's own `nullifyingPrivateKey` and the known leaf's Merkle path/root (from `rootHashHinkal`/`rootHashHinkalIndex`).
4. Generate a valid Groth16 witness/proof (`a,b,c`) spending that leaf as `inputNullifiers[0][0]`, with `dimensions` matching the constructed `circomData`, in the same test transaction block (no off-chain listener action simulated).
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` immediately after step 2, in the same test (or same block).
6. Assert: `verifyProof` returns true, `rootHashExists` passes, `nullifiers[nullifierHash]` becomes `true`, and the withdrawal/transfer succeeds — i.e., the "blocked" leaf was fully spent despite `BlockedUtxosCreated()` having fired with no corresponding on-chain hold, proving the equality break between the signaled reservation and actual spendability.

    function insertNullifiers(
        uint256[][] calldata inputNullifiers,
        bool[] calldata onChainCreation
    ) internal {
        for (uint256 i = 0; i < inputNullifiers.length; i++) {
            for (uint256 j = 0; j < inputNullifiers[i].length; j++) {
                if (onChainCreation[i] == true) break;
                if (inputNullifiers[i][j] != 0) {
                    require(
                        !nullifiers[inputNullifiers[i][j]],
                        "Nullifier cannot be reused"
                    );
                    nullifiers[inputNullifiers[i][j]] = true;
                    emit Nullified(inputNullifiers[i][j]);
                }
            }
        }
    }

            CircomDataBuilder.getHashedCalldata(circomData) ==
                circomData.calldataHash,

        );
        relayerIsValid(circomData.relay);
        dimensionsCheck(circomData, dimensions);
        checkOnchainCreation(circomData);

        return
            CircomDataBuilder.formInputForCircom(
                block.chainid,
                hinkalAddress,
                circomData

contract DepositOnChainUtxosExternalAction is Transferer, ExternalActionBaseV2 {
    event BlockedUtxosCreated();

    constructor(
        address[] memory _allowedRecipients
    ) ExternalActionBaseV2(_allowedRecipients) {}

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) external override onlyAllowedRecipient returns (UTXO[] memory utxoSet) {
        uint256 tokenCount = circomData.erc20TokenAddresses.length;
        require(
            tokenCount > 0 && deltaAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: token count mismatch"
        );

        address userAddress = circomData.originalSender;
        require(
            userAddress != address(0),
            "DepositOnChainUtxosExternalAction: Invalid originalSender"
        );

        uint256[][] memory utxoAmounts = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (uint256[][])
        );
        require(
            utxoAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: metadata length mismatch"
        );

        utxoSet = new UTXO[](countUtxos(utxoAmounts));

        uint256 utxoIndex = 0;
        for (uint256 i = 0; i < tokenCount; i++) {
            require(
                deltaAmounts[i] == 0,
                "DepositOnChainUtxosExternalAction: Delta amount must be zero"
            );

            address tokenAddress = circomData.erc20TokenAddresses[i];
            uint256 tokenTotal = 0;

            for (uint256 j = 0; j < utxoAmounts[i].length; j++) {
                uint256 amount = utxoAmounts[i][j];
                require(
                    amount > 0,
                    "DepositOnChainUtxosExternalAction: UTXO amount must be positive"
                );
                tokenTotal += amount;

                utxoSet[utxoIndex] = UTXO({
                    amount: amount,
                    erc20Address: tokenAddress,
                    stealthAddressStructure: circomData.stealthAddressStructure,
                    timeStamp: circomData.timeStamp + utxoIndex
                });
                utxoIndex++;
            }

            if (tokenAddress != address(0) && tokenTotal > 0) {
                transferERC20TokenFrom(
                    tokenAddress,
                    userAddress,
                    msg.sender,
                    tokenTotal
                );
            }
        }

        emit BlockedUtxosCreated();
    }
