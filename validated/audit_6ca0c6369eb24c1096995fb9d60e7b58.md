### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing via webhook replay - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , so the HMAC that `Registry.process` validates covers the body alone [2](#0-1) . The `shop` identity that is handed to the app's webhook handler, however, comes straight from the unauthenticated `shopify-shop-domain` HTTP header [3](#0-2) . The equality the gem implicitly assumes — "the shop whose secret produced this HMAC" == "the shop reported in the `shop-domain` header" — does not actually hold, because the header is outside the signed payload.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are the two methods `Utils::VerifiableQuery`/`Utils::HmacValidator.validate` use to authenticate an inbound webhook [4](#0-3) . `to_signable_string` is defined as just `@raw_body` [1](#0-0) , meaning `HmacValidator.validate_signature` recomputes `HMAC-SHA256(secret, raw_body)` and compares it to the `shopify-hmac-sha256` header [5](#0-4) . None of `topic`, `shop-domain`, `api-version`, or `webhook-id` participate in the signed string; they are read straight from HTTP headers with no cryptographic binding [6](#0-5) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (the header value) as the tenant identity forwarded to the app's business logic: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [2](#0-1) . Because `shop-domain` is not part of the signed material, an HMAC that is valid for a given `raw_body` remains valid no matter what value the `shop-domain` header carries.

The binding that breaks, as an equality:
- Expected: `shop_that_produced_valid_hmac(raw_body) == shop_delivered_to_handler(request.shop)`
- Actual: `shop_delivered_to_handler(request.shop)` is attacker-controlled and independent of the HMAC computation.

### Impact Explanation
This is a cross-tenant identity confusion inside the gem's own webhook-verification primitive: the merchant/tenant identity handed to the app after "successful" verification is not actually authenticated by the same signature that gates the request. An app built on top of `Webhooks::Registry.process`/`Request` — following the gem's documented contract that a validated `WebhookMetadata#shop` can be trusted for tenant-scoped processing — can be made to attribute one shop's webhook payload to a different shop, i.e., cross-tenant data leakage/mixing at the application layer that consumes this gem's output.

### Likelihood Explanation
No `api_secret_key` or other Shopify credential is required. Any developer/merchant who installs the app on their own store legitimately receives real webhook deliveries — valid `(raw_body, hmac)` pairs signed with the app's real secret for their own shop. Because the header carrying `shop-domain` is not covered by that signature, the same `raw_body`/`hmac` pair remains valid if replayed with a different `shopify-shop-domain` header value. The attacker only needs network access to the app's webhook endpoint and one previously captured legitimate delivery — no secret extraction, TLS interception, or privileged access is needed.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the material that is HMAC-verified, or otherwise cryptographically bind the shop identity to the signed body before it is surfaced to `WebhookHandler#handle` via `WebhookMetadata`. At minimum, document and enforce that `WebhookMetadata#shop` must never be trusted as tenant-authenticated unless the header is bound to the signature.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; capture a legitimate webhook delivery — headers `shopify-hmac-sha256: H`, `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`, and body `B`. `H` is valid because `HMAC(secret, B) == H` [5](#0-4) .
2. Replay the exact same request to the app's webhook endpoint, changing only the `shopify-shop-domain` header to `victim.myshopify.com`, keeping body `B` and `hmac` `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)`, which still equals `H`, so validation passes [7](#0-6) .
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `request.shop == "victim.myshopify.com"` [8](#0-7) , even though the payload `B` and secret both belong to `attacker.myshopify.com`. The host application now processes attacker-supplied data under the victim shop's tenant identity.
