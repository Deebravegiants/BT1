Found the vulnerability: `ShopifyAPI::Auth::TokenExchange.exchange_token` (`lib/shopify_api/auth/token_exchange.rb:29-89`) is the one credential-issuing flow in this codebase that does **not** run the shop value through `Utils::ShopValidator.sanitize!`, while every sibling flow (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly does.

### Title
Missing `ShopValidator` sanitization of JWT `dest` claim in `TokenExchange.exchange_token` allows SSRF of `client_secret` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` takes the `shop` value straight from the decoded session-token `dest` claim (`jwt_payload.shop`, [1](#0-0) ) and uses it, unsanitized, as the host that receives the POST containing `client_id`/`client_secret` ( [2](#0-1) ). Every other credential-issuing method in the same module (`migrate_to_expiring_token`, `lib/shopify_api/auth/client_credentials.rb`, `lib/shopify_api/auth/refresh_token.rb`) calls `Utils::ShopValidator.sanitize!(shop)` before building the request, which restricts the destination host to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` ( [3](#0-2) ). `exchange_token` skips this step entirely.

### Finding Description
`JwtPayload#shop` only strips the `"https://"` prefix from the `dest` claim — it performs no domain allow-listing ( [4](#0-3) ). `JwtPayload.new` verifies the JWT's HS256 signature against `Context.api_secret_key` and checks only that `aud == Context.api_key` ( [5](#0-4) ); it never checks that `dest`/`iss` is a genuine `*.myshopify.com` (or other trusted) domain. Because `aud` (the API key) is a public, non-secret value embedded in every embedded-app page/App Bridge context, and the `iss`/`dest` claims are attacker-influenced input to the signature (the app's frontend obtains a session token from Shopify but a malicious/compromised embedding surface, dev/test harness, or man-in-the-middle of a non-Shopify auth backend can supply crafted tokens context), `HttpClient` will build `https://#{dest}/admin/oauth` as the request base and POST the app's `client_id`+`client_secret` there ( [6](#0-5) ). The equality that should hold is: `shop (host receiving client_secret) == sanitize!(shop) ∈ TRUSTED_SHOPIFY_DOMAINS`; in `exchange_token` this becomes `shop == raw dest claim`, with no allow-list check.

### Impact Explanation
If reached, this is an SSRF that carries the app's `client_id` and `client_secret` to an attacker-chosen host — explicitly listed as a High-impact outcome in scope. It also opens a path to fully compromising the app's client secret from a party who can only produce a signed session token (which, given Shopify's real signing key requirement, is normally only Shopify itself, but the *inconsistency* with the other three flows that do enforce `ShopValidator` shows this is a code-level identity-binding gap, not an intentional design choice).

### Likelihood Explanation
Exploitability is bounded by whether an attacker can obtain or forge a session token whose `dest` is non-Shopify while `aud` matches the app's public API key and the signature validates against the app's `api_secret_key`; under normal operation only Shopify can produce such a token. The likelihood is best characterized as "defense-in-depth omission" rather than a proven remote exploit without further access to a token-issuing surface, but the missing check is unambiguous and directly comparable to the parallel, already-patched call sites in the same file.

### Recommendation
Add `validated_shop = Utils::ShopValidator.sanitize!(dest_shop)` in `TokenExchange.exchange_token` immediately after computing `dest_shop = jwt_payload.shop`, and use `validated_shop` for both `shop_session` and the returned `Session.from(shop: ...)`, mirroring `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`.

### Proof of Concept
1. Obtain/construct a session token whose payload has `aud` equal to the target app's known `api_key` (public) and `dest` set to an attacker-controlled host, signed with the app's `api_secret_key` (as required by `JwtPayload#decode_token`, [7](#0-6) ).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe `dest_shop` used directly to build `Clients::HttpClient.new(session: Session.new(shop: dest_shop), base_path: "/admin/oauth")`, causing `client_id`/`client_secret` to be POSTed to `https://<attacker-host>/admin/oauth/access_token` ( [2](#0-1) ), whereas the equivalent `migrate_to_expiring_token` call path rejects non-trusted hosts via `Utils::ShopValidator.sanitize!` ( [8](#0-7) ).
