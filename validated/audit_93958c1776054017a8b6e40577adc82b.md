## Title
Fee-on-transfer/rebasing token escrow accounting in Tron IntentGatewayV2 credits the requested amount instead of the amount actually received, permanently freezing escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the internal escrow ledger `_orders[commitment][token]` using the user-requested input amount (minus protocol fee), not the amount of tokens the contract actually received after the ERC20 transfer. For fee-on-transfer, deflationary, or rebasing-down tokens, this causes the recorded escrow balance to exceed the contract's actual token balance, so a later `withdraw()` call reverts on insufficient balance and the funds become permanently stuck — the same root cause described in the referenced Teller `CollateralManager` report (constant recorded amount vs. actual balance available for withdrawal).

### Finding Description
In `placeOrder` (non-predispatch path), the contract does: [1](#0-0) 

```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
// Store reduced amount (after protocol fees) in escrow
_orders[commitment][token] += reducedInputs[i].amount;
```

`reducedInputs[i].amount` is derived purely from the originally requested `order.inputs[i].amount` minus the protocol fee (computed earlier in `placeOrder`): [2](#0-1) 

No balance-before/after measurement of the ERC20 transfer occurs anywhere in this function. If `token` charges a transfer fee (fee-on-transfer), rebases downward, or is otherwise deflationary, `IERC20(token).safeTransferFrom` delivers less than `order.inputs[i].amount` to the contract, but the escrow ledger is still incremented by the full (fee-reduced-only-for-protocol-fee) amount. The predispatch branch has the same flaw and is worse: it forwards tokens through an intermediate `dispatcher` with two hops (`safeTransferFrom` to dispatcher, then `token.transfer` from dispatcher back to the gateway), each of which can incur an additional transfer fee, yet escrow is still credited with `reducedInputs[i].amount` based on the original requested amount rather than the actual balance the gateway received: [3](#0-2) 

Later, `withdraw()` blindly transfers `body.tokens[i].amount` out and decrements the (already-inflated) escrow entry without any balance check: [4](#0-3) 

Because the contract's actual token balance is smaller than the sum of all `_orders[...][token]` entries for that token, the low-level `token.call(transfer...)` either reverts (standard ERC20 revert-on-insufficient-balance implementations) or returns `false`, which is caught and reverted with `TransferFailed`. Either way, `withdraw()` — reachable from `onAccept` (fill), `onGetResponse` (timeout refund), and the `RedeemEscrow`/`RefundEscrow` unsigned-request handler — permanently fails for the shortfall amount, and since the escrow decrement never happens, the deficit is never resolved.

This is a direct regression relative to the mainline EVM contract, which explicitly measures actual balance received and mutates `order.inputs[i].amount` before it is used for the commitment and escrow: [5](#0-4) 

The mainline contract's own test suite documents this exact class of bug and its intended fix (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_Predispatch`), confirming the maintainers are aware of and defend against this issue in the primary EVM path but the Tron variant does not implement the same defense.

### Impact Explanation
Any order placed on the Tron gateway using a fee-on-transfer/deflationary/rebasing ERC20 as an input token results in an escrow record that overstates the contract's actual holdings. When the order is filled, refunded, or cancelled, `withdraw()` will attempt to pay out more than the contract actually holds for that token, causing the transaction to revert. Since escrow accounting is per-token across all commitments in the same contract, this deficit is not isolated: it can also cause unrelated withdrawals for other orders denominated in the same token to fail once the shared token balance is exhausted below the sum of recorded entries. Funds become permanently stuck in the gateway — a concrete freezing-of-funds impact, matching the Medium severity of the original report.

### Likelihood Explanation
Any user or integrator placing an order with a non-standard ERC20 (fee-on-transfer, deflationary, or rebasing-down token) as input triggers the bug — no privileged role is required, and it is reachable directly from `placeOrder`, a fully permissionless entrypoint. The predispatch path doubles the exposure since two transfer hops each can apply a fee.

### Recommendation
Mirror the fix already present in the mainline `evm/src/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` (or the dispatcher, for predispatch) before and after each transfer, and use the actual delta — not the requested `order.inputs[i].amount` — both for computing `reducedInputs` and for crediting `_orders[commitment][token]`. Apply the same balance-delta pattern to the dispatcher-to-gateway sweep in the predispatch branch.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) and use it as `order.inputs[0].token` with `amount = 1000e18` in a call to the Tron `IntentGatewayV2.placeOrder`.
2. `safeTransferFrom` delivers only `990e18` tokens to the gateway (actual `balanceOf(gateway)` increases by 990e18), but `_orders[commitment][token]` is credited with `reducedInputs[0].amount` ≈ `1000e18` (minus only the protocol fee, not the transfer fee).
3. When the order is filled/refunded and `withdraw()` is invoked with `body.tokens[0].amount` set to the escrowed (inflated) value, the `token.call(transfer(...))` reverts or returns `false` because the gateway's actual balance for that token is short — reproducing the "fee on transfer token stuck in escrow" scenario, analogous to `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`, which the Tron contract lacks equivalent protection against.
