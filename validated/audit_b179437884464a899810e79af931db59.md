### Title
Webhook `shop` (tenant identity) field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `shop` (the tenant identifier passed to the app's webhook handler) is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the HMAC-signed material. `Registry.process` validates the HMAC and then trusts `request.shop` as the tenant for dispatch, breaking the binding `shop_verified == shop_acted_on`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` using `OpenSSL.secure_compare`: [1](#0-0) . For webhook requests, `to_signable_string` returns only `@raw_body`: [2](#0-1) . The `shop` accessor, however, is derived purely from an HTTP header that is not part of that signed string: [3](#0-2) .

`Registry.process` validates the HMAC and, if it matches, immediately dispatches to the registered handler using `request.shop` as the authoritative tenant identity, without any additional binding check between the signed body and the shop header: [4](#0-3) . The resulting `WebhookMetadata.shop` is the field host applications use to scope all subsequent tenant-specific logic (e.g. looking up sessions/access tokens, updating per-shop records): [5](#0-4) .

Because the HMAC only proves "this body was produced by Shopify for *some* shop that generated this exact payload," and not "this body belongs to shop X," an unprivileged actor who has legitimate access to a valid `(body, hmac)` pair for their own store (trivial — install the app on any shop they control and capture the webhook Shopify sends them) can replay that exact HTTP request to the target app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still succeed because the header is never part of the signed content, so `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop as the source of that (attacker-controlled) payload.

This is an equality that should hold but doesn't: `shop_that_signed(payload) == shop_reported_to_handler`. The gem verifies the bytes of the body but acts on a header that was never verified.

### Impact Explanation
This crosses the tenant boundary: an attacker can make a host application believe that a message it fully trusts (HMAC-verified) originated from a different merchant's shop, feeding attacker-controlled webhook bodies (topic/body they generated on their own store) into another tenant's data-processing path. Depending on how the host app uses `WebhookMetadata.shop` (e.g., to load that shop's session, write into its records, or trigger downstream automation), this enables cross-tenant data injection/confusion — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High. No secret, access token, or privileged access is required — only the ability to install/operate any shop that receives webhooks from the target app (something any unprivileged internet user/merchant can do by installing a public app), replay the captured HTTP request, and override one header field.

### Recommendation
Include the tenant-identifying fields (at minimum `shop-domain`, ideally also `topic` and `webhook-id`) in the signed material used for verification, or otherwise cryptographically bind the shop domain to the payload before trusting it in `Registry.process`/`WebhookMetadata`. Shopify's HMAC for webhooks is computed over the raw body by design, so the fix should be at the consuming application/gem layer: treat `shop` as unauthenticated header data unless independently corroborated (e.g., confirm the shop already has a known, registered session/webhook subscription for that exact `webhook_id`/topic pair) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers/receives a webhook (e.g. `orders/create`) — Shopify sends a valid request with headers `x-shopify-hmac-sha256`, `x-shopify-topic`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and a JSON body.
2. Attacker captures this raw request (`raw_body`, `hmac`, `topic`) unmodified.
3. Attacker replays the exact same `raw_body` and `hmac` to the app's webhook endpoint, but changes the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only covers `raw_body`, which is unchanged and still matches the original valid `hmac`: [2](#0-1) .
5. `Registry.process` dispatches to the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop: [4](#0-3) .
