## Title
Unvalidated JWT `dest` claim used to build the OAuth token-exchange host, bypassing the `ShopValidator` trust check applied to every sibling grant method - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the request host for the `access_token` call — which carries the app's `client_id`/`client_secret` — directly from the session token's `dest` claim via `JwtPayload#shop`, with **no** domain-trust validation. Every other grant method in the same module/family (`RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`) passes the `shop` value through `Utils::ShopValidator.sanitize!` before it is used to build the request host, guaranteeing the host is one of `TRUSTED_SHOPIFY_DOMAINS`. `exchange_token` breaks that binding.

### Finding Description
`JwtPayload#shop` only strips the scheme prefix from the `dest` claim, it performs no trusted-domain check: [1](#0-0) 

`TokenExchange.exchange_token` takes this unvalidated value and uses it to build the `Session`/`HttpClient` that will receive `client_id` and `client_secret` in the `access_token` request body: [2](#0-1) 

Compare this to the sibling methods in the same file and module family, which all call `Utils::ShopValidator.sanitize!(shop)` — restricting the resulting host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before constructing the session/host that will carry the `client_secret`: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

The `HttpClient` builds its request host directly from `session.shop` with plain string interpolation, with no additional validation at the HTTP layer: [7](#0-6) 

The equality this breaks is: **host validated (trusted-domain checked via `ShopValidator`) vs. host that actually receives `client_id`/`client_secret`**. For `refresh_access_token`, `client_credentials`, and `migrate_to_expiring_token`, these are the same by construction. For `exchange_token`, the host receiving the client secret is whatever string the `dest` claim contains after stripping `"https://"`, with no membership check against `TRUSTED_SHOPIFY_DOMAINS`.

### Impact Explanation
If the `dest` value in a token presented to `exchange_token` is not itself constrained to a legitimate Shopify-owned domain (e.g., malformed, or an unexpected shape from a non-admin token type such as a checkout UI extension token, since `JwtPayload` accepts and returns `shop` for any signed token regardless of `iss`), the resulting host string is used verbatim to build the request URL that carries the app's `client_id`/`client_secret`. This is exactly the SSRF-with-credentials class called out in scope (High: "SSRF with the app's credentials"), and it is inconsistent with the defense-in-depth the library otherwise applies uniformly via `ShopValidator.sanitize!` on every other code path that turns a `shop`-like value into a credential-carrying request host.

### Likelihood Explanation
Exploitation requires a validly-signed session token (HS256, verified against `Context.api_secret_key`/`old_api_secret_key`), so a fully external attacker without any token cannot trigger this directly. However, unlike the sibling methods, `exchange_token` provides no additional trust check on the claim value itself — it relies entirely on the correctness/format guarantees of whatever issued the token, which is a materially weaker guarantee than the explicit domain allow-list every other grant path enforces. This is a genuine asymmetry in the codebase's own defense model, not merely a theoretical one — the recently deprecated `shop:` parameter and the corresponding CHANGELOG entry confirm this code path was intentionally changed to trust the `dest` claim in place of validated input.

### Recommendation
Route `dest_shop` through `Utils::ShopValidator.sanitize!` (as is already done in `migrate_to_expiring_token`, `refresh_access_token`, and `client_credentials`) before constructing `shop_session`/`HttpClient` in `TokenExchange.exchange_token`, so the host that receives the `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, matching the guarantee provided everywhere else in the module.

### Proof of Concept
1. Obtain (or forge, if a signing-key compromise or non-admin token misuse scenario applies) a session token whose `dest` claim is not a plain trusted Shopify host string.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload#shop` returns the claim value with only the `"https://"` prefix stripped: `lib/shopify_api/auth/jwt_payload.rb:47-51`.
4. `exchange_token` builds `shop_session = Session.new(shop: dest_shop)` and `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, whose `@base_uri` becomes `"https://#{dest_shop}"` (`lib/shopify_api/clients/http_client.rb:18`), then POSTs `{client_id, client_secret, ...}` to `#{@base_uri}/admin/oauth/access_token` — with no `ShopValidator` check ever applied to `dest_shop`, unlike every sibling method in `lib/shopify_api/auth/{refresh_token,client_credentials,token_exchange}.rb`.
