### Title
Native-token refunds from the LI.FI router are not captured by the swap balance equation and are permanently stuck in `LifiExternalAction` - (File: `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`LifiExternalAction.callRouter` forwards the *entire* input amount to the LI.FI router as `msg.value` when swapping from native ETH, but only measures the balance change of the **output** token to compute `swappedAmount`. Any native-token refund the router sends back for unused value lands in the `LifiExternalAction`/`ExternalActionSwap` contract but is never included in the balance equation that determines what gets forwarded back to the caller, so it is permanently trapped — the same root cause pattern as the reported LayerZero refund-address bug (value returned by a downstream external call is absorbed by an intermediate contract instead of being routed back to the user).

### Finding Description
`ExternalActionSwap.swap` computes the amount to return to the caller purely from the change in the **output** token's balance: [1](#0-0) 

`callRouter` in `LifiExternalAction` sends the whole `inputAmount` as `msg.value` to the router and derives `swappedAmount` solely from the output-token balance delta, ignoring the input token entirely: [2](#0-1) 

If the LI.FI router (or any bridge/aggregator route it forwards to, several of which are LayerZero-based and quote a variable messaging fee) does not consume the full `msg.value` and refunds the difference natively, that refund is sent back to `msg.sender`, which is the `LifiExternalAction` contract itself (since it is the caller of `router.call{value: inputAmount}(...)`). This excess ETH increases the contract's native balance, but:
- It is never measured, because `callRouter` only diffs the **output** token balance, not the input (ETH) balance.
- `ExternalActionSwap.swap` only forwards `amountToSendToHinkal` (derived from `swappedAmount`, the output-token delta) back to `msg.sender` (the `Hinkal` contract); the leftover ETH is not part of this transfer.
- No rescue/withdraw function exists in `ExternalActionSwap`, `ExternalActionBaseV2`, or `LifiExternalAction` to later recover stray ETH sitting in the contract: [3](#0-2) 

This breaks the accounting equality enforced elsewhere in the protocol (e.g., the balance-diff checks in `Hinkal.transact`, which only work because every value-bearing token movement is captured in `circomData.erc20TokenAddresses`/`amountChanges`): value that physically returns to the contract from the external router is silently excluded from the equation used to determine what is owed back to the user.

### Impact Explanation
Any refunded native ETH from the LI.FI router (e.g., due to overestimated `msg.value`, or an underlying bridge leg quoting a smaller fee than supplied) is permanently frozen inside the `LifiExternalAction` contract with no path to recovery for the user or the protocol. Per the rubric this is a permanent freezing of user funds, which is a Critical-severity impact.

### Likelihood Explanation
This requires: (1) the user/relayer to build a swap with `inputToken == address(0)` routed through LI.FI, and (2) the LI.FI-routed call to refund unused native value (a realistic occurrence for bridge-aggregated routes with variable quoted fees, mirroring exactly the class of refund the external report describes for LayerZero). It does not require any privileged role, malicious relayer, or admin key — it can happen in the course of ordinary usage whenever the supplied `inputAmount` exceeds what the downstream call actually consumes.

### Recommendation
- Measure the native-token (input) balance before and after the `router.call`, and treat any positive delta as a refund owed back to `msg.sender` (mirroring how `swappedAmount` is computed for the output token), forwarding it to `Hinkal`/the caller as part of the returned `UTXO` set or `amountToSendToHinkal` logic.
- Alternatively, ensure `msg.value`/`inputAmount` passed to the router exactly matches what will be consumed, eliminating the possibility of a refund, or add an explicit sweep of leftover native balance back into the accounted swap output at the end of `swap()`.

### Proof of Concept
1. User submits a Hinkal `transact` with `externalActionId` pointing to `LifiExternalAction`, `erc20TokenAddresses = [address(0), outputToken]`, and `externalActionMetadata` built for a LI.FI route whose downstream leg (e.g., a LayerZero-based bridge) is quoted with a variable fee.
2. `Hinkal._externalTransact` transfers the full ETH `inputAmount` to `LifiExternalAction` before calling `runAction`: [4](#0-3) 
3. `LifiExternalAction.callRouter` forwards all of it via `router.call{value: inputAmount}(...)`. The router consumes less than `inputAmount` and refunds the remainder natively to `LifiExternalAction` (the caller).
4. `swappedAmount` is computed only from the output-token balance delta, so the leftover ETH is invisible to the accounting; `amountToSendToHinkal` of the output token is sent back, but the refunded ETH remains in `LifiExternalAction`'s balance indefinitely, with no function available to retrieve it.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }

        _;

        for (uint i = 0; i < _allowedRecipients.length; i++) {
            isAllowedRecipient[_allowedRecipients[i]] = true;
        }

    function setAllowedRecipients(

        for (uint i = 0; i < recipients.length; i++) {

            isAllowedRecipient[recipients[i]] = true;
