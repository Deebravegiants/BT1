This confirms the vulnerability: `WebhookMetadata.shop` (passed to every app's `WebhookHandler#handle`) is populated directly from `request.shop`, which reads the unauthenticated `X-Shopify-Shop-Domain` header, while `HmacValidator.validate` only verifies the HMAC over `to_signable_string`, which returns `@raw_body` — the header is never included in the signed material.

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` binds the identity of the merchant shop that a webhook is attributed to (`shop`) solely to the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. Since a single app-level `client_secret` (`Context.api_secret_key`) is shared across every merchant installation of the app, any unprivileged user who has installed the app on their own shop can capture a legitimate webhook (valid body + valid HMAC for their own tenant) and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain, causing the app to process attacker-controlled data under the victim's tenant identity.

### Finding Description
The identity binding that should hold is:
`shop-domain header used for tenant attribution == shop-domain bytes covered by the verified HMAC`

In `lib/shopify_api/webhooks/request.rb`:
- `shop` is read directly from an unauthenticated header: [1](#0-0) 
- `to_signable_string`, the value that is actually HMAC-verified, is only the raw body: [2](#0-1) 

In `lib/shopify_api/webhooks/registry.rb`, `Registry.process` validates the HMAC and, if it passes, immediately trusts `request.shop` to construct the `WebhookMetadata` handed to the app's handler, with no cross-check that the shop header actually matches the tenant the body/HMAC pair originated from: [3](#0-2) 

`WebhookMetadata.shop` is then delivered as trusted tenant context to every registered `WebhookHandler#handle` implementation: [4](#0-3) 

Because `client_secret` is per-app (not per-shop), the HMAC that Shopify computes for shop A's webhook is verifiable with the exact same secret as shop B's webhook. An attacker who owns shop A (an "unprivileged internet user" relative to the app's other tenants — shop B) can:
1. Install the target app on their own shop A and receive a legitimate webhook (raw body + `hmac-sha256` header) which is entirely valid per `Utils::HmacValidator.validate`.
2. Replay that exact body and HMAC header to the app's webhook endpoint, only changing the `X-Shopify-Shop-Domain` header to `shop-b.myshopify.com`.
3. `HmacValidator.validate` recomputes the signature over `@raw_body` only — unaffected by the header change — and passes.
4. `Registry.process` then builds `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and dispatches it to the handler, which will treat the attacker's payload as authentic data belonging to shop B.

### Impact Explanation
This breaks the tenant boundary the app relies on to attribute webhook events to the correct merchant. Any handler logic keyed off `WebhookMetadata#shop` (e.g., looking up per-shop settings, triggering data deletion/GDPR flows, updating per-shop records, or feeding shop-scoped caches) can be poisoned with attacker-chosen body content while being credited to a victim shop — a cross-tenant integrity issue matching the Critical "cross-tenant access" category, since the gem provides no binding between the authenticated bytes and the field used for tenant attribution.

### Likelihood Explanation
Any user able to install the app on their own store (a normal, unprivileged flow for any public or custom Shopify app) can obtain one valid (body, hmac) pair from their own tenant and replay it with a modified shop header — no access token, secret key, or elevated privilege is required. The only prerequisite is the ability to install the app once, which is the baseline capability of any Shopify merchant targeting a multi-tenant app.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed/verified material, or otherwise cryptographically bind the header used for tenant attribution to the verified payload before constructing `WebhookMetadata`. At minimum, cross-check `request.shop` against the tenant that actually installed the app (e.g., an offline session lookup keyed by shop) before invoking the handler, rather than trusting the header outright once only the body HMAC has been checked.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw POST body plus the `X-Shopify-Hmac-Sha256` header Shopify sends (both valid, since Shopify signed them with the app's shared `client_secret`).
2. Resend the identical body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and adjust `X-Shopify-Topic`/`X-Shopify-Webhook-Id` if desired, since these are also unauthenticated per `shopify_header`).
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `request.to_signable_string` (`@raw_body`) against the header HMAC: [5](#0-4) 
4. `ShopifyAPI::Webhooks::Registry.process` proceeds and dispatches the attacker's body to the app's handler tagged with `shop: "victim-shop.myshopify.com"`: [3](#0-2)
