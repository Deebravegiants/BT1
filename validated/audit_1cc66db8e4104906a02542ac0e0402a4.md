### Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload (`to_signable_string`) from the raw request body only, while the tenant identifier (`shop`) is read from an unsigned HTTP header. `Webhooks::Registry.process` validates the HMAC over the body and then forwards the header-derived `shop` value to the app's handler as trusted tenant identity, without any binding between the two.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed bytes: [2](#0-1) 

`Registry.process` verifies only the HMAC over the body via `Utils::HmacValidator.validate(request)`, then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop`, and dispatches it to the host app's handler as the trusted tenant identity: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` confirm that `computed_signature` (over `to_signable_string`, i.e. the body only) matches the received signature — it never touches `shop`: [4](#0-3) 

The identity binding the gem should enforce is: `signed_bytes == (body, shop)`; what is actually enforced is `signed_bytes == body`, while `shop` is taken from an unauthenticated header and passed straight to the handler. Because Shopify signs webhook bodies with a secret shared across every shop that installs the app, any shop owner can install the app on a store they control, trigger an event, and legitimately receive one HMAC-valid `(body, hmac)` pair for their own tenant. The header carrying `shop` is not part of what is verified, so that same valid `(body, hmac)` pair can be replayed with an arbitrary `X-Shopify-Shop-Domain`/`shopify-shop-domain` header value, and `Registry.process` will accept it and hand the handler a `WebhookMetadata` claiming the event belongs to a different shop.

### Impact Explanation
Any host application that uses `data.shop` from the dispatched `WebhookMetadata` to select the tenant record/session to update (a common and encouraged pattern, since the gem exposes `shop` specifically for that purpose) can be made to apply attacker-controlled webhook data under a victim shop's identity — a cross-tenant confusion caused entirely by this gem's own verification not covering the identity field it hands to the app.

### Likelihood Explanation
The attacker only needs the ability to install the target app on a shop they control (a normal, low-privilege action for any Shopify merchant) and the ability to send a crafted HTTP request to the app's webhook endpoint with the captured, still-HMAC-valid body but a different shop-domain header. No access token, `client_secret`, or other privileged credential is required.

### Recommendation
Include the shop domain (and topic/webhook-id, if used for routing) in the signed payload verification, or otherwise cryptographically bind `request.shop` to the verified body (e.g., re-derive/verify shop identity from data embedded in the signed body, or require the host app to independently confirm the shop is one it has an active session/installation for) before constructing `WebhookMetadata` and dispatching to handlers.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook event and capture the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (valid because `H = HMAC(secret, B)` and the secret is shared across all installs).
2. Replay a POST to the app's webhook endpoint using the exact same body `B` and hmac header `H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses `shop` from the spoofed header; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes because `B` and `H` are unchanged.
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., attacker-controlled webhook content is delivered under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
