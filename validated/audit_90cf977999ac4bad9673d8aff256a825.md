### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`, which computes the HMAC over the raw request body only. The `shop` (and `topic`, `webhook_id`) values are read directly from unauthenticated HTTP headers and passed straight into the handler as the tenant identifier, with no cryptographic binding between the signature and the shop domain.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no verification: [2](#0-1) 

`Registry.process` verifies only this body-based HMAC before invoking the app's handler with `request.shop` as the tenant key: [3](#0-2) 

`HmacValidator.validate` signs/verifies exactly `verifiable_query.to_signable_string`, i.e. the raw body — the shop header is never part of the signed material: [4](#0-3) 

The HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that has installed the app — it is not shop-specific. Consequently, any `(body, hmac)` pair that is valid for one installed shop remains a valid HMAC for that same body no matter which `x-shopify-shop-domain` header accompanies it. The equality the gem implicitly promises but does not enforce is:
`shop authenticated by the HMAC == shop delivered to the handler as request.shop`
In reality, `shop` is delivered to the handler entirely outside the signed payload, so this equality can be broken by an attacker who controls the header value while reusing (or engineering) a body that produces a valid signature.

The `docs/usage/webhooks.md` documentation states that calling `Registry.process` "will verify the request did indeed come from Shopify," which overstates what the code actually checks — it verifies only that the *body* bytes are unmodified, not that the *shop* attribution is authentic: [5](#0-4) 

### Impact Explanation
An attacker who operates their own installation of the target app (an unprivileged, legitimate merchant account — no special credentials needed) receives genuinely-signed webhooks for their own shop. Because `shop` is excluded from the signed material and the secret is shared across all shops, the attacker can replay a body they legitimately received (or any body whose HMAC they can produce/observe) while substituting the `x-shopify-shop-domain`/`shopify-shop-domain` header for a victim shop's domain. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming to originate from the victim shop. Any host application that uses `data.shop` from the handler to key its per-tenant session/data lookups (exactly as the gem's own documentation example does — `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be tricked into writing or reading data under the wrong tenant, i.e. cross-tenant access.

### Likelihood Explanation
Requires only an unprivileged attacker who can install the app on their own shop (or otherwise obtain a body/HMAC pair from the app's webhook delivery) and can freely choose the shop-domain header — no leaked secrets or privileged access are needed. The library's own documented usage pattern (keying data by `data.shop`) directly relies on the field the gem fails to authenticate, making the exploit path realistic in real integrations following the docs.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed payload, or independently verify that `request.shop` is a shop for which the app currently holds an active session/installation before dispatching to the handler. At minimum, update `to_signable_string` (or add a secondary check in `Registry.process`) so the signature is bound to the shop identity, not just the body bytes, and correct the documentation to avoid implying the shop domain is authenticated.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw body `B` and its valid `x-shopify-hmac-sha256` header `H` — `H = HMAC-SHA256(api_secret_key, B)`.
2. Send a forged HTTP request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid because the signed material is the body only)
   - Header `x-shopify-shop-domain`: `victim.myshopify.com` (attacker-chosen)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares it to `H` — validation succeeds since `shop` is not part of `to_signable_string`.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` and, if it uses `data.shop` to select which tenant's records to update (as the gem's documented example encourages), performs the action against `victim.myshopify.com` instead of the attacker's own shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
