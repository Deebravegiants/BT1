## Analog Found

### Title
Fee-on-transfer / deflationary underlying tokens break WrappedHyperFungibleToken's lock accounting, enabling unbacked minting cross-chain - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` assumes that transferring `params.amount` of the underlying ERC20 into the contract always results in the contract's balance increasing by exactly `params.amount`. For fee-on-transfer / deflationary ERC20s this assumption is false, yet the full requested `params.amount` (not the amount actually received) is embedded in the cross-chain `Message` and used to authorize minting/unlocking on the destination chain.

### Finding Description
In `send()`, the contract locks the underlying token via a plain `safeTransferFrom` without measuring the actual balance delta: [1](#0-0) 

The dispatched `Message.amount` is `params.amount` — the requested amount, not the amount that actually landed in the contract: [2](#0-1) 

If `_underlying` is a fee-on-transfer token, `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` at line 272 leaves the contract holding strictly less than `params.amount`, but the ISMP `PostRequest` body still claims `params.amount` was locked. On the destination chain, `HyperFungibleToken.onAccept()` mints the peer's ERC6160 representation using this unverified `message.amount` directly (mint is unconditional on the claimed amount, not on any proof of actual custody). The result is that more wrapped tokens are minted on remote chains than the underlying reserve actually locked in `WrappedHyperFungibleToken`.

This is the same root cause as the reported "FEE-ON-TRANSFER tokens are not accounted for" issue: crediting a cross-chain accounting system with the pre-transfer amount instead of the post-transfer, actually-received amount. Notably, the sibling `IntentGatewayV2.placeOrder()` in this same codebase explicitly guards against exactly this class of bug by measuring `balanceOf` before/after every `safeTransferFrom` and adjusting escrowed amounts to the actual received balance (see `evm/src/apps/IntentGatewayV2.sol` lines 312-329, and dedicated `FeeOnTransferToken` regression tests in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`), demonstrating the team is aware of and has fixed this bug class elsewhere — but `WrappedHyperFungibleToken.sol` was not updated with the same protection.

The symmetric refund path (`onPostRequestTimeout`) also assumes the contract holds `message.amount` of `_underlying` to refund, which can revert/DoS a legitimate timeout refund once the locked balance has been drained below the sum of outstanding claims: [3](#0-2) 

### Impact Explanation
- Unbacked minting: `HyperFungibleToken` instances on peer chains mint ERC6160 tokens 1:1 against the amount claimed in the cross-chain message, not against verified reserve backing. Repeated `send()` calls with a fee-on-transfer underlying inflate outstanding minted supply relative to the actual locked reserve in `WrappedHyperFungibleToken`.
- This reserve shortfall is systemic: any user attempting to redeem/unlock the underlying on the home chain (via a reverse cross-chain transfer that calls `onAccept`) can fail once the contract's real balance is insufficient to cover the sum of amounts claimed as locked, since `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` will revert on insufficient balance — freezing funds for whichever transfer runs out the reserve.
- Because the shortfall accrues per-transfer and compounds, this is a fund-accounting break of the bridge's core invariant (locked reserve ≥ minted supply), not a one-off rounding issue.

### Likelihood Explanation
Reachable with a single unprivileged transaction: any user calling `send()` where `configure()`'s `_underlying` has been set to a token with an active transfer fee (fee-on-transfer tokens are common, some can toggle fees on/off, e.g., USDT-style tokens) triggers the shortfall immediately — no privileged action, malicious admin, or off-chain component is required. The contract owner only configures which token is wrapped once at deployment; the vulnerability manifests purely from standard ERC20 transfer semantics differing from the contract's naive assumption.

### Recommendation
Mirror the fix already applied in `IntentGatewayV2.placeOrder()`: measure the actual balance received before crediting/dispatching.

```solidity
uint256 balBefore = IERC20(_underlying).balanceOf(address(this));
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
uint256 received = IERC20(_underlying).balanceOf(address(this)) - balBefore;
// use `received` (not params.amount) when building the DispatchPost / Message
```
Apply the same balance-diff pattern to the WETH-wrap branch if `_isWeth` deposit/withdraw can also incur fees, and use the same actually-locked amount consistently in `onPostRequestTimeout` refund accounting.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` and `configure()` it with `_underlying` set to a fee-on-transfer ERC20 (e.g., 1% fee token, as used in `FeeOnTransferToken` from `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`).
2. User calls `send(params)` with `params.amount = 1000e18`. `safeTransferFrom` moves 1000e18 out of the user's wallet, but only 990e18 actually lands in `WrappedHyperFungibleToken` due to the transfer fee.
3. The dispatched `Message.amount` is still `1000e18`.
4. On the destination chain, `HyperFungibleToken.onAccept()` mints `1000e18` of the wrapped ERC6160 token to the beneficiary — 10e18 more than what is actually backed by the locked reserve.
5. Repeating this drains the backing ratio; eventually a legitimate `onAccept()` unlock call on the home chain (from an inbound bridge-back message) reverts because `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` exceeds the contract's actual balance, freezing that user's funds.

            data: params.data

            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender

        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);

        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);

            commitment = dispatchWithFeeToken(request);
        }

            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
