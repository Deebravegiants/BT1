### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` field — used by `ShopifyAPI::Webhooks::Registry.process` to attribute the incoming webhook to a tenant — is read from an unauthenticated HTTP header. Because a single app `client_secret` signs webhooks for every shop that installs the app, any holder of one valid `(raw_body, hmac)` pair (obtainable legitimately from their own low-privilege shop install) can replay it with a forged `shop-domain` header naming a different, victim shop, and the signature check will still pass.

### Finding Description
The binding that should hold is:

`hmac == HMAC(secret, raw_body ‖ shop)` for the shop the webhook actually claims to be from.

Instead, the gem only enforces:

`hmac == HMAC(secret, raw_body)`

`to_signable_string` returns just `@raw_body`, deliberately excluding the shop identity: [1](#0-0) 

The `shop` accessor, by contrast, is taken straight from an attacker-controllable header with no cryptographic binding to the signed bytes: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then unconditionally trusts `request.shop` to build the `WebhookMetadata` that is handed to the app-defined handler for tenant-specific processing (e.g. looking up that shop's stored session/access token, or acting on `customers/data_request` / `customers/redact` payloads): [3](#0-2) 

Because Shopify signs webhooks for *every* shop that has installed a given app with that app's single `client_secret`, the secret is not shop-specific. An attacker who controls their own (even free/dev) shop installation of the target app will receive genuine webhooks with a valid `(raw_body, hmac)` pair for events they themselves trigger in their own store. Since the `shop-domain` header is excluded from the signed bytes, the attacker can resend that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a different, victim shop that also has the app installed. `HmacValidator.validate` will still return `true` because it only recomputes the HMAC over `raw_body`: [4](#0-3) 

The app's handler then processes attacker-chosen body content (e.g., fabricated `orders/create`, `customers/data_request`, or `customers/redact` payloads) as if it genuinely originated from the victim shop, since `WebhookMetadata.shop` is taken from the unauthenticated header.

### Impact Explanation
This breaks the tenant-isolation guarantee the HMAC is supposed to provide for the multi-tenant `Registry.process` webhook pipeline. An attacker with only a legitimate, unprivileged installation of the target app (no leaked secrets, no TLS interception, no host-application misuse) can make the app process attacker-controlled webhook bodies attributed to an arbitrary victim shop. Depending on the host app's handler logic (which the docs explicitly instruct to key off `data.shop` for session lookups and mandatory `customers/redact`/`customers/data_request` compliance flows), this enables cross-tenant data confusion, forged compliance/GDPR events against a victim shop, or injection of fabricated order/customer data into another merchant's processing pipeline — qualifying as cross-tenant access under a High-severity scope-check-style bypass.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own valid, low-privilege installation of the target app on any shop (freely obtainable for public apps), and (2) the ability to POST an HTTP request to the app's already-public webhook endpoint with a modified header — no secret, token, or TLS interception needed. This is realistically achievable by any unprivileged internet user who installs the app once.

### Recommendation
Include the shop identity (and ideally topic/webhook-id) in the HMAC-covered signable string, or otherwise cryptographically bind the `shop-domain` header value to the signature before trusting it in `Registry.process`. At minimum, `Webhooks::Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` alongside `raw_body` so a replayed body cannot be re-attributed to a different shop.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and triggers a real webhook event (e.g., `orders/create`), capturing the genuine request: `raw_body = B`, headers include `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs a new request to the app's webhook endpoint with the *same* `raw_body = B` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (a real shop that also has the app installed).
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `to_signable_string` is still `B` and whose `shop` is `"victim.myshopify.com"`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds.
5. The handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed(B), ...)` and processes attacker-controlled data as if it came from the victim shop.
