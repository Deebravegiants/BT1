## Analysis

The TOFT bug's root cause: caller-supplied parameters embedded in an internal payload (`sendFromData.adapterParams` / `callParams.refundAddress`) are trusted without validation, letting the caller redirect a privileged value-transfer operation (which key/address funds are sent to) away from the intended recipient. The closest structural analog in `hydra--006` is in the transaction-signing pipeline, where a caller-controlled field embedded in the transaction payload (`unsignedTx.txMeta.keyId`) can override which cryptographic key is used to sign, instead of the key strictly derived from the validated `walletAccount`.

### Title
Caller-controlled `txMeta.keyId` allows signing with an arbitrary key instead of the account-derived key - (File: `features/tx-signer/src/module/seed-signer.ts`)

### Summary
`SeedBasedTransactionSigner.signTransaction` derives the default signing key from the validated `walletAccount`, but if the caller-supplied `unsignedTx.txMeta.keyId` is present, it is used verbatim (only shape-validated, not scope-validated) to select an entirely different signer via `#getSignerForKeyId`, bypassing the walletAccount-to-key binding.

### Finding Description
`signTransaction` extracts `keyId` directly from caller-supplied `unsignedTx.txMeta` [1](#0-0) . If present, it's only checked for structural validity via `KeyIdentifier.validate(keyId)` — not checked against the `walletAccount` that was authorized/requested for this signing operation [2](#0-1) . It is then used to build a signer with `#getSignerForKeyId({ seedId: walletAccount.seedId, keyId })`, which constructs a `KeyIdentifier` purely from the caller value and signs with it [3](#0-2) . This is analogous to the TOFT bug: a "should-be-internal" routing parameter (which key to use / where funds go) is smuggled inside a payload nominally meant to carry transaction data, and consumed by a privileged code path without validating that the caller is authorized to select that particular parameter value. The `keyId` mechanism was explicitly designed for legitimate cross-key cases (e.g., signing an EOS tx with the Ethereum key) per the code comment [4](#0-3) , but nothing restricts it to the small set of asset-internal cross-key mappings — it accepts any well-formed `KeyIdentifier`, including derivation paths belonging to other accounts, other assets, or the account's `authKey`/other purposes within the same seed.

The public entry point is reachable through `TransactionSignerApi.signTransaction` → `TransactionSigner.signTransaction` → `SeedBasedTransactionSigner.signTransaction`, which only validates that `unsignedTx`/`txMeta` are objects, not their contents [5](#0-4) [6](#0-5) . The client-side asset interface similarly forwards `unsignedTx` unmodified [7](#0-6) .

### Impact Explanation
If any caller of the transaction-signer API (including a UI-layer request assembled from data influenced by an untrusted source, e.g., a connected dApp/website's transaction payload) can set `txMeta.keyId`, it would sign arbitrary attacker-chosen data (`unsignedTx.txData`) with a key belonging to a different account/address than the one the user believes they are authorizing, potentially producing a valid signed transaction that moves funds from an unintended account/address within the user's seed. This matches the "unauthorized signing" impact bar (concrete unauthorized use of a wallet key). Whether this is reachable end-to-end from an untrusted dApp/website input (vs. only from trusted first-party UI code) could not be confirmed from the indexed files — I could not locate the code that constructs `unsignedTx.txMeta` from web3-provider (`eth_sendTransaction`, etc.) requests, so it's unclear whether `keyId` is ever populated from dApp-supplied data or is exclusively set by internal wallet logic for the documented legitimate cross-asset-key cases.

### Likelihood Explanation
Likelihood is uncertain without confirming the origin of `txMeta.keyId` values in production call sites. If it is only ever set by trusted, hardcoded internal logic (as the code comment suggests — EOS-with-Ethereum-key, Ripple), likelihood is low. If any UI/API-exposed parameter passthrough allows a caller to set `txMeta.keyId` arbitrarily, likelihood is high, since the only server-side check is structural (`KeyIdentifier.validate`), not authorization-based.

### Recommendation
- Do not trust `txMeta.keyId` as an unconstrained caller input for selecting the signing key. Restrict it to signing/asset-metadata-derived server-side, or explicitly cross-check the derived `keyId` against a fixed set of `(baseAssetName, walletAccount)`-authorized alternate keys.
- If `keyId` must remain caller-provided, enforce that the resulting key belongs to the same `walletAccount`/`seedId` scope requested (e.g., verify `accountIndex` in the key derivation path matches `walletAccount.index`, and that `assetName` is in an allow-listed set of legitimate cross-signing pairs), rather than accepting any structurally-valid `KeyIdentifier`.

### Proof of Concept
Conceptual PoC based on `features/tx-signer/src/module/seed-signer.ts` [8](#0-7) :
1. Call `transactionSigner.signTransaction({ baseAssetName: 'ethereum', walletAccount: <account A>, unsignedTx: { txData: {...attacker tx...}, txMeta: { keyId: new KeyIdentifier({ derivationPath: "m/44'/60'/0'/0/5", derivationAlgorithm: 'BIP32', keyType: 'secp256k1' }) } } })`.
2. `keyId` is present, passes `KeyIdentifier.validate`, and is used unchanged for signing regardless of whether address index `5` (or a different account) was ever authorized in this signing request.
3. The result is a valid signature over attacker-controlled `txData` produced with a key that does not correspond to the `walletAccount` originally authorized by the user/UI for this operation.

Note: I was not able to verify from the indexed files whether an untrusted/website-facing surface (e.g. an injected web3 provider) can actually set `txMeta.keyId`, since the code that builds `unsignedTx` for provider RPC methods (`eth_sendTransaction`, etc.) is not present in the indexed context. Given the index size limits, some file contents (particularly the dApp-request-to-`unsignedTx` construction code) may not be available — a Devin session with full repo access would be needed to trace all call sites that populate `txMeta.keyId` to confirm end-to-end exploitability from an unprivileged/website origin.

    const { baseAssetName, unsignedTx, walletAccount } = opts

    if (!('compatibilityMode' in unsignedTx.txMeta)) {
      unsignedTx.txMeta.compatibilityMode = walletAccount.compatibilityMode
    }

    if (!('accountIndex' in unsignedTx.txMeta)) {
      unsignedTx.txMeta.accountIndex = walletAccount.index
    }

    assert(
      Number.isInteger(unsignedTx.txMeta?.accountIndex),
      `txMeta.accountIndex was not a valid integer`
    )

    assert(baseAsset.api.features.signWithSigner, `asset ${baseAssetName} does not support signing`)

    const keyId = unsignedTx.txMeta?.keyId
    const signTx = baseAsset.api.signTx!

    if (!keyId) {
      const signer = await this.#getSignerForWalletAccount({ walletAccount, baseAsset })
      return signTx({ unsignedTx, signer })
    }
