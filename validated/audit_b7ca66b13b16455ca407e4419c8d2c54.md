## Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant shop impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, while the `shop` identity that is handed to the app's webhook handler is read from an HTTP header that is never part of the signed payload. Any actor who can produce one genuinely-signed webhook body for the app (e.g. a merchant who has installed the app and receives real webhooks for their own shop) can replay that same signed body against the webhook endpoint with a forged `shopify-shop-domain` / `x-shopify-shop-domain` header, and the HMAC check will still pass, causing the app to attribute the payload to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates authenticity like this: [1](#0-0) 

The validation call delegates to `Utils::HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For a `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body — never the headers: [3](#0-2) 

Yet the `shop` value that is subsequently handed to the app's handler (as tenant/shop identity) is read directly from an unauthenticated header, with no cryptographic binding to the signed body: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`hmac(raw_body, api_secret_key) valid` ⇒ `(raw_body, shop)` is authentic

but the actual guarantee provided by the code is only:
`hmac(raw_body, api_secret_key) valid` ⇒ `raw_body` is authentic

`shop` is completely outside of that guarantee, exactly mirroring the Oracle bug class: a field that is acted upon (`shop`, used to select/attribute tenant data) is not covered by the authenticity check (the HMAC), analogous to the external oracle address not being locked to the battle it settles.

### Impact Explanation
Because a single app-wide `api_secret_key` is shared across every shop that installs the app, any merchant who legitimately installs the app receives genuinely HMAC-signed webhook bodies for their own shop. That merchant can capture such a signed body/HMAC pair and replay it to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. The HMAC check still succeeds (it only covers the body), and `Registry.process` passes `request.shop` (the forged value) straight to the app's handler as the shop of record: [6](#0-5) 

Any host application that keys tenant-scoped side effects (order/data mutation, uninstall/GDPR handling, billing, session/token lookups) off `WebhookMetadata#shop` can be tricked into applying another shop's webhook data to the wrong tenant — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Exploitation only requires being a legitimate (even free/trial) merchant of the target app to obtain one validly-signed webhook body, then replaying it with a different `shop-domain` header value to the app's shared webhook endpoint. No possession of `api_secret_key`, access tokens, or privileged access is required, satisfying the "unprivileged internet user" bar.

### Recommendation
Bind the shop identity into the authenticated payload before trusting it: include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the signable string that is HMAC-verified, or otherwise cryptographically bind the header value to the body signature, so that `Utils::HmacValidator.validate` fails if the shop header has been altered relative to what Shopify originally signed for that body.

### Proof of Concept
1. App `MyApp` is installed by both `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing one `api_secret_key`.
2. Shopify sends a legitimate `orders/create` webhook to `MyApp` for `attacker-shop.myshopify.com`:
   ```
   x-shopify-topic: orders/create
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-hmac-sha256: <valid HMAC of raw body>
   body: { ...order payload... }
   ```
3. The attacker (who owns `attacker-shop.myshopify.com` and can observe their own webhook traffic) captures this exact body + HMAC.
4. The attacker replays the identical body and HMAC to `MyApp`'s webhook endpoint but changes the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the signature over the (unchanged) raw body and it matches, so `Registry.process` in `lib/shopify_api/webhooks/registry.rb` proceeds and calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually belongs to `attacker-shop.myshopify.com`.
6. Any handler logic keyed on `data.shop` now operates on the wrong tenant.
