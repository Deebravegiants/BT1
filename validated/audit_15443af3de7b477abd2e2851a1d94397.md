### Title
Simplex Uniswap V4 venue pricing uses manipulable spot price with no execution-cost/TWAP protection - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
Simplex's FX filler strategy prices "exotic" (non-curve) intent legs from the live Uniswap V4 pool spot price (`sqrtPriceX96`-derived `token0Price`/`token1Price`) instead of a manipulation-resistant TWAP, and the only defense (`checkPriceGuard`) is a static deviation bound with no execution-cost/slippage term. This mirrors the APC exploit pattern (flash-loan/atomic manipulation of a spot price used directly for accounting/settlement), except the counterparty being drained is the solver's own on-chain inventory rather than a shared pool.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` (called from `FXFiller.getVenueUsdPrice` in `sdk/packages/simplex/src/strategies/fx.ts`) reads a pool's *current* `sdkPool.token0Price`/`token1Price` — the instantaneous spot price computed from the pool's live `sqrtPriceX96` — and uses it directly as the USD price for pricing an intent-order leg: [1](#0-0) 

This price feeds `resolveLegRates` in the FX strategy, which computes `rate = 1 / venueUsd` and then linearly extends that mid-price across the whole order size (`computeLegPolicyOutput`) with only a static `checkPriceGuard` deviation check against an operator-configured `referencePrice`/`maxDeviationBps` — both optional, and explicitly documented as leaving the chain "unguarded" if omitted: [2](#0-1) 

The venue-pricing flow doc confirms there is no size/impact term and that `computeDirectPoolPriceUsd` "returns the raw pool mid derived from `sqrtPriceX96`", with `checkPriceGuard` as "the only defense on this path," checking deviation from a static reference, not execution cost: [3](#0-2) 

An attacker who can move the pool's spot price within a single transaction (e.g., via a flash-loaned swap against the underlying Uniswap V4 pool, or any sequence of swaps that shifts `sqrtPriceX96` before the intent-fill transaction reads it) can push the read price to any value inside — or even outside if `referencePrice`/`maxDeviationBps` is unset — the guard's accepted band. Because the intent order itself is a single unprivileged, attacker-submitted transaction/order (the "intent solver" reachable surface named in scope), the attacker controls both the price-moving trade and the order that gets filled against the resulting mismatched price, exactly as in the APC PoC where a flash loan pumped/dumped the AMM price around a mispriced swap.

### Impact Explanation
If the manipulated spot price is fed into `resolveLegRates`/`computeLegPolicyOutput`, the filler either:
- Delivers more output tokens than the true market rate justifies (solver takes a loss, attacker profits), or
- Charges the user less than fair value cross-chain, causing under-collateralized escrow release relative to the true value delivered.

Either outcome is a direct theft of solver funds mediated by the intent-fill contract path (`fillOrder`/`IntentGatewayV2`), reachable by any unprivileged intent submitter who can also manipulate the referenced Uniswap V4 pool. Given Simplex may hold a market-maker's LP-backed inventory funding fills, a single manipulated fill can drain funds analogous to the original APC flash-loan drain.

### Likelihood Explanation
Likelihood is Medium: exploitation requires (1) an operator to configure a V4-funded pair with either no `referencePrice`/`maxDeviationBps` guard, or a guard band wide enough to admit a flash-loan-manipulated tick, and (2) sufficient capital/flash-loan access on the destination pool to move price within one block before the fill/quote reads it. The guard existing at all reduces likelihood versus the original APC case, but the documentation explicitly states both fields are optional and the pool is otherwise fully trusted, so misconfigured or thin-liquidity pairs remain exposed.

### Recommendation
- Require `referencePrice`/`maxDeviationBps` (or an equivalent guard) to be mandatory whenever `[vault.uniswapV4]` pool-based pricing is used, rather than optional.
- Replace or supplement the raw spot-price read (`sdkPool.token0Price`/`token1Price` from live `sqrtPriceX96`) with a TWAP oracle or multi-block sampling resistant to same-transaction manipulation.
- Add an execution-cost/size-impact term to `computeDirectPoolPriceUsd`/`computeLegPolicyOutput` so large fills are not priced at the undiluted mid, and reconcile the guard check against realistic flash-loan price ranges rather than only a static deviation band.

### Proof of Concept
Conceptual, mirroring the APC PoC structure (flash-loan pump/dump around a mispriced trade):
1. Attacker flash-loans capital and swaps against the configured Uniswap V4 pool backing a `[vault.uniswapV4]` position for an exotic token (e.g., cNGN/USDC), moving `sqrtPriceX96` and thus `sdkPool.token1Price`/`token0Price` far from the true market rate, while staying within (or exploiting the absence of) `maxDeviationBps`.
2. In the same transaction bundle, attacker (or an accomplice acting as intent placer) submits an intent order whose leg is priced via this pair.
3. Simplex's `FXFiller.calculateProfitability` → `resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` reads the manipulated spot price (`sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts:206-240`), and the resulting output amount is computed and filled at the wrong rate.
4. Attacker reverses the pool-price manipulation (swap back / unwind flash loan) in the same block, pocketing the difference between the fill's fair value and the manipulated value it was priced/settled at.

Note: I could not fully verify the exact numeric bounds/order in which `checkPriceGuard` executes relative to the pool-price read within `resolveLegRates` (only partial code for `fx.ts` was retrieved), so the precise call ordering and whether the guard runs before every use of the venue price should be confirmed directly in `sdk/packages/simplex/src/strategies/fx.ts`.

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
