### Title
Webhook `shop-domain` header is trusted for tenant identity but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC of the raw request body, then hands the caller a `shop` value taken from an unauthenticated HTTP header. Because a single `api_secret_key` is shared across every shop that installs the app, an attacker who controls one legitimately-installed shop can capture one of their own validly-signed webhook deliveries and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain, causing the app to process attacker-controlled webhook data under a different tenant's identity.

### Finding Description
`Registry.process` verifies authenticity solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

The HMAC check calls `request.to_signable_string`, which for `Webhooks::Request` returns only the raw HTTP body: [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` values used later are all pulled straight from HTTP headers, none of which participate in the signable string: [3](#0-2) 

After HMAC validation succeeds, `Registry.process` builds `WebhookMetadata` directly from `request.shop` (the unauthenticated header) and passes it to the app's handler as the tenant identity: [4](#0-3) 

The identity binding that should hold is: `shop bound by HMAC == shop used as the tenant/session key`. In this code, the HMAC only binds the *body bytes* to the app's `api_secret_key` (which is identical for every shop that has the app installed), while the *shop* value that the handler uses to route/attribute the webhook is taken from an entirely separate, unauthenticated header. Because the same secret signs webhooks for every tenant, a valid signature from tenant A's webhook says nothing about which shop actually sent it — the equality `HMAC-covered content == asserted shop` never holds.

### Impact Explanation
An unprivileged internet user can install the target app on their own (attacker-controlled) shop — a normal, unprivileged action available to anyone who can create a Shopify store — and receive real, validly HMAC-signed webhook deliveries for that shop. Because the signature covers only the body, the attacker can replay that exact body to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (body unchanged, same shared secret), and `Registry.process` forwards `shop: <victim-domain>` to the handler. Any app logic that uses `WebhookMetadata#shop` to select which merchant's data store to write into will attribute attacker-controlled webhook content to the victim's tenant — a cross-tenant data injection/confusion condition, meeting the "cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is high for any app built on this gem that trusts `request.shop`/`WebhookMetadata#shop` as the tenant key (the normal, documented usage pattern shown in the gem's webhook tests and docs). The only prerequisite is installing the app on one's own store, which requires no privileged credentials, access tokens, or the app's `client_secret`.

### Recommendation
Bind the `shop` (and other routing-relevant fields such as `topic`/`webhook_id`) into the HMAC-verified material, or independently cross-check the header-derived `shop` against a shop known to be associated with a previously-established session/installation record before trusting it as a tenant key, rather than passing the raw header value straight into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`; the app's webhook endpoint receives a real webhook with body `B`, headers including `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the identical body `B` and identical `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (see `lib/shopify_api/utils/hmac_validator.rb`) recomputes the HMAC over `B` only and it matches, so validation passes.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` and invokes the app's handler, which now processes attacker-controlled content as if it belongs to `victim.myshopify.com`. [1](#0-0) [5](#0-4)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
