### Title
Personal Custody Package (biometric data) is unconditionally uploaded to the backend before enrollment success is determined, disclosing biometric data even when the signup ultimately fails - ([File: src/plans/mod.rs])

### Summary
In `MasterPlan::do_signup`, the Personal Custody Package (PCP) — which contains the user's encrypted iris/face images and commitments — is built and uploaded to the backend unconditionally, before the actual enrollment/verification result (success, duplicate, fraud, software-version block, etc.) is known. This mirrors the reported pattern where an action that "spends"/discloses an asset is executed before the corresponding benefit (a successful, verified transaction) is confirmed, so the counterparty (here, the user) can end up having disclosed sensitive data with no benefit if the subsequent step fails.

### Finding Description
`do_signup` computes `signup_reason` (Normal/Failure/Fraud) from the capture/pipeline result, builds the PCP via `self.build_pcp(...)`, and immediately uploads tier-0 via `self.upload_pcp_tier_0(...)` and queues tier-1/tier-2 uploads, all *before* the eventual success/failure of the signup is determined by `self.enroll_user(...)` (which calls the backend `signup_post`/`signup_poll` endpoints): [1](#0-0) [2](#0-1) 

Only after this unconditional upload does the code proceed to `enroll_user`, whose outcome (`Success`, `SignupVerificationNotSuccessful`, `ServerError`, etc.) can still cause the signup to fail for reasons including "Backend duplicates", "Backend legacy signup requests", "Backend inflight matches", "Backend detected fraud", or "Orb agent, internal, capture or pipeline failures": [3](#0-2) 

Notably, in this build all local (on-orb) fraud checks have been stripped out (`detect_fraud` always returns `Ok(false)` unless the pipeline itself failed), so `signup_reason` is essentially always `Normal` locally, and the only real fraud/duplicate detection happens server-side, after the PCP (containing raw/encrypted biometric material) has already left the device: [4](#0-3) 

The `build_pcp` function packages the iris/normalized-iris/face images, encrypts them with backend keys, and returns tiers that are then transmitted via `upload_personal_custody_package::request`: [5](#0-4) [6](#0-5) 

### Impact Explanation
This ordering means biometric data disclosure to the backend (an action with real privacy consequences that cannot be "undone") occurs unconditionally and irrespective of whether the signup is ultimately accepted. If the backend subsequently rejects the signup (duplicate detection, fraud, server error, software version issues), the user has already had their encrypted iris/face package transmitted and stored server-side without receiving the corresponding benefit — a verified, successful signup/credential. This matches the reported bug class ("counterparty's asset/data is consumed/disclosed with no compensating benefit on partial or failed completion of the operation") mapped onto the biometric-upload domain.

### Likelihood Explanation
This occurs on every ordinary signup attempt that reaches the PCP-build stage and where the eventual backend enrollment check (duplicate/fraud/server error) later rejects the signup — it does not require any attacker action; it is a deterministic ordering issue in the normal control flow of `do_signup`.

### Recommendation
Defer irreversible PCP upload until after the backend has confirmed the signup will be accepted (or make PCP upload conditional/rollback-able), or clearly document/enforce that a failed enrollment after PCP upload triggers backend-side deletion of the already-uploaded biometric package, ensuring users are not left with disclosed biometric data and no corresponding signup benefit.

### Proof of Concept
1. Complete a biometric capture and pipeline successfully so `signup_reason == SignupReason::Normal`.
2. Observe that `build_pcp` + `upload_pcp_tier_0` (and tier1/tier2 queuing) execute and complete at lines 580–636 of `src/plans/mod.rs`, before `enroll_user` is invoked at line 647.
3. Let the subsequent `enroll_user` call return `Status::SignupVerificationNotSuccessful` (e.g., because the backend detects the user as a duplicate, per the comment list in `enroll_user.rs` lines 162-167) — the PCP containing the user's biometric data has already been fully uploaded to `DATA_BACKEND_URL`, while the user receives no successful signup outcome.
