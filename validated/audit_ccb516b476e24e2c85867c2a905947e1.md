### Title
Userinfo/port confusion in `hostnameFromString` lets attacker-controlled URLs match a scoped hostname (e.g. `exodus.io`), leaking `x-api-key`/scoped headers to an attacker host - ([File: adapters/fetch-factory/src/hostname.js])

### Summary
`hostnameFromString` naively treats the first `:` after `://` as a port separator without checking whether a subsequent `@` makes that segment actually userinfo. This lets a URL like `https://exodus.io:x@attacker.com/path` be parsed by `FetchFactory` as hostname `exodus.io`, while the real WHATWG `URL`/`fetch()` implementation dials `attacker.com`. Any header scoped via `setHeaders(headers, [EXODUS_HOST])` (e.g. `x-api-key`) is then attached and sent to the attacker-controlled endpoint.

### Finding Description
`hostnameFromString` (`adapters/fetch-factory/src/hostname.js:11-37`) extracts the authority substring after `://` and picks the earliest of `:`, `/`, or `?` to delimit the "hostname," then validates the delimited slice with `isValidHostname` (`adapters/fetch-factory/src/hostname.js:5-7`). For a `:`-delimited match it returns immediately (`adapters/fetch-factory/src/hostname.js:19-23`) without checking for a following `@`, i.e. it cannot distinguish `host:port` from `user:password@host`.

For `url = 'https://exodus.io:x@attacker.com/path'`:
- `hostnameFromString` slices the authority to `exodus.io` (everything before the first `:`), which passes `isValidHostname` and is returned as the resolved hostname.
- The real `new URL(url).hostname` (and thus the actual `fetch()`/`fetchFn` dial target) is `attacker.com`, because `exodus.io:x` is userinfo (username:password) preceding `@attacker.com`.

This function is reached from `FetchFactory#create()` → `#buildHeaders(url)` → `getUrlHostname(url)` → `hostnameFromString(url)` (`adapters/fetch-factory/src/fetch-factory.js:100-111`, `122-152`). If the caller previously scoped a secret via `setHeaders({'x-api-key': secret}, [EXODUS_HOST])` (`EXODUS_HOST = 'exodus.io'`, `adapters/fetch-factory/src/constants.js:3`), `#buildHeaders` matches `hostname === 'exodus.io'` against `this.headerConfigs['exodus.io']` and attaches `x-api-key` to the outgoing request headers, then `this.fetchFn(url, options)` is invoked with the crafted URL — sending the secret to `attacker.com`, not `exodus.io`.

### Impact Explanation
An attacker who controls or influences the URL string passed to a `FetchFactory` instance configured with an `EXODUS_HOST`-scoped secret (e.g. via a manipulated address-provider/public-key API base URL, remote config, or redirect target) can exfiltrate that scoped credential (`x-api-key`) to an attacker-controlled server. This breaks the per-origin secret isolation the `setHeaders(headers, [hostname])` API is designed to enforce, enabling downstream impersonation of the wallet against Exodus backend services (address-provider/account impersonation), matching a secret-disclosure / origin-isolation-bypass bounty category.

### Likelihood Explanation
Exploitability requires: (1) a scoped header configured for a specific hostname via `setHeaders`, and (2) attacker influence over the literal URL string later passed to the `fetch`-like function created by `FetchFactory#create()`. The crafted string `https://<scoped-host>:<anything>@<attacker-host>/...` is simple, deterministic, and requires no privileged state — any code path that builds request URLs from untrusted input (remote config, redirects, deep-linked URLs) and passes them through `create()` is affected. The bug is purely in string parsing logic, so it reproduces reliably.

### Recommendation
Replace the manual string-splitting logic in `hostnameFromString` with the WHATWG `URL` parser (`new URL(url).hostname`) wrapped in try/catch, or explicitly detect and strip userinfo (`user[:password]@`) before searching for the port `:` delimiter, ensuring the extracted hostname always matches what the real `fetch()` implementation will dial.

### Proof of Concept
```js
import { getUrlHostname } from '../src/hostname.js'

test('hostnameFromString must not diverge from real URL parsing for userinfo authority', () => {
  const url = 'https://exodus.io:x@attacker.com/path'
  const real = new URL(url).hostname // 'attacker.com'
  const extracted = getUrlHostname(url) // currently 'exodus.io' -- BUG

  expect(extracted).toBe(real) // fails on current implementation
})
```
Fuzz plan: generate authority strings combining `userinfo@`, embedded `://`, `\\` path separators, and `:port` across a corpus, comparing `new URL(url).hostname` to `getUrlHostname(url)` for every case where a scoped header (`EXODUS_HOST`) would otherwise be attached in `FetchFactory#create()`; assert no divergence, and add an integration test asserting `x-api-key` is never present in headers produced by `#buildHeaders('https://exodus.io:x@attacker.com/path')`.
