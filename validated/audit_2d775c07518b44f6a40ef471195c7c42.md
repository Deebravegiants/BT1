## Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook only by verifying the HMAC over the raw request body. The `shop` identifier that downstream handlers use to know *which merchant* the webhook is about is read straight from the `x-shopify-shop-domain` HTTP header, which is never included in the HMAC-signed data. An attacker who can obtain any single valid `(body, hmac)` pair for a topic they control (trivially achievable by installing the app on their own free/dev shop and receiving one legitimate webhook) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `shop-domain` header, and the library will report that webhook as authentic and belonging to the victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and `Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` to build the metadata handed to the app's handler, with no binding between the verified body and the shop value: [3](#0-2) 

The identity binding that should hold is: **shop the HMAC was computed for == shop passed to the handler**. Because the HMAC covers only `@raw_body` and the shop domain is carried in a separate, unsigned header, this equality is never enforced. Any party that can generate one legitimately-signed webhook body (e.g., by installing the app on a shop they control, which requires no privilege beyond being an "unprivileged internet user" with a free Shopify dev/partner shop) can pair that same `(body, hmac)` with a different `shop-domain` header value and the check in `HmacValidator.validate` — which never inspects headers — will still pass.

### Impact Explanation
This breaks the tenant boundary the webhook system is supposed to enforce. Applications built on this gem are expected to use `WebhookMetadata#shop` to decide which merchant's data/session/access token to act on. Since that value is not authenticated, an attacker can:
- Cause the app to process a webhook body under a victim shop's identity (`data.shop`), potentially triggering actions, data writes, or lookups scoped to the victim tenant using attacker-controlled body content.
- Combine this with a mismatched `topic` header (also unauthenticated) to invoke a handler for a topic different from what was actually signed, further widening the confusion between body content and the identity/semantics the app believes it has.

This is a cross-tenant identity confusion vulnerability reachable by any actor able to install the app on a shop they control and capture one legitimate webhook delivery — no access token, `client_secret`, or privileged account is required.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that relies on `WebhookMetadata.shop`/`topic` from `Registry.process` without independently re-validating the shop against session storage or other server-side state. Getting one legitimately HMAC-signed webhook body only requires installing the app on any shop (including a free development store), which is available to any unprivileged internet user.

### Recommendation
Include the shop domain (and topic) as part of the data that is cryptographically bound to the request, or otherwise cross-check the header-derived `shop` against an independent, trusted source (e.g., verify that the shop reported in the header is only ever used after confirming a corresponding valid, previously-provisioned session exists for that shop, and reject the header value if it doesn't match the tenant context established via other authenticated means such as the app's own session store lookups keyed by a value that was authenticated). At minimum, document clearly that `request.shop`/`request.topic` are unauthenticated and must not be trusted for authorization decisions without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they fully control) and receives one legitimate webhook delivery, e.g. for `orders/create`, with body `B` and a valid header `x-shopify-hmac-sha256: H` (computed by Shopify using the app's real secret over `B`).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == H` — the shop header is never part of that computation: [4](#0-3) 
4. `Registry.process` then invokes the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"victim-shop.myshopify.com"`, even though that shop never sent this webhook and its data never signed this body: [5](#0-4)
