Confirmed: `placeOrder` in `IntentGatewayV2.sol` only checks `order.inputs.length == 0` and rejects duplicate output tokens — there is no upper bound on `order.inputs.length` or `order.output.assets.length`. Every downstream consumer of these arrays (`fillOrder` → `_fillSameChain`/`_fillCrossChain`, `_execute`, `_withdraw`, `_cancelSameChain`, `_cancelFromSource`) loops over `outputsLen`/`inputsLen` with no cap, matching the reported bug class of an unbounded, attacker-grown array that a *different, unprivileged* party must later iterate over at their own expense, causing a gas-based DoS that permanently freezes funds.

### Title
Unbounded `order.inputs`/`order.output.assets` length lets an order placer permanently freeze escrowed funds by forcing solver fills and self-cancellation to exceed the block gas limit - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntentGatewayV2.placeOrder` escrows tokens for an `Order` whose `inputs` and `output.assets` arrays have no maximum length check [1](#0-0) . Every function that must later act on the order — `fillOrder`, `_fillSameChain`, `_fillCrossChain`, `_execute`, `_withdraw`, `_cancelSameChain`, `_cancelFromSource` — loops over these arrays with `for` loops sized by `inputsLen`/`outputsLen` [2](#0-1) [3](#0-2) [4](#0-3) . An order placer (the unprivileged party analogous to the "malicious seller" in the source report) can craft an order with an arbitrarily large number of distinct input/output tokens, escrow it, and make every subsequent action on that commitment (fill by a solver, or the placer's own cancel path) revert from gas exhaustion.

### Finding Description
`placeOrder` validates only `order.inputs.length == 0` (rejecting empty input) and duplicate output tokens via transient storage, but places no cap on how many entries `inputs` or `output.assets` may contain [5](#0-4) . Each additional element requires: an ERC-20 `transferFrom` for escrow at placement time [6](#0-5) , and — critically — a per-element loop at fill or cancel time performed by a *different account* than the order placer:

- `fillOrder` requires `options.outputs.length == outputsLen` and `order.inputs.length == outputsLen`, then routes to `_fillSameChain`/`_fillCrossChain`, both of which loop over every output asset doing a token transfer per iteration [7](#0-6) [8](#0-7) [4](#0-3) . This loop is paid for by the **solver**, not the order placer.
- `_withdraw`, called from `onAccept` for `RedeemEscrow`/`RefundEscrow` and from same-chain fill/cancel, loops over `body.tokens` doing a `safeTransfer` per input token [9](#0-8) . When invoked via `onAccept` this is executed as part of Hyperbridge's cross-chain message delivery, i.e. it is the **relayer's** transaction that must carry the gas for the full, attacker-sized token list.
- `_execute` (called on full fill) additionally loops over `outputsLen` twice (once to sweep dispatcher balances, once to rebuild the compacted call array) [10](#0-9) .
- `_cancelFromSource`, reachable to the order's own creator but also gating the GET-response driven refund flow relayed by Hyperbridge, loops over `inputsLen` before dispatching a GET request whose response handling later replays the same-sized `_withdraw` loop [11](#0-10) .

Because `keccak256(abi.encode(order))` is the commitment and the order struct (including its array contents) must match exactly at fill/cancel time, the order placer fully controls the size of every loop that a solver, relayer, or the destination-chain HyperApp callback must execute to move the escrowed funds. If the placer sizes `inputs`/`output.assets` large enough that any of these loops exceeds the destination chain's block gas limit, the order becomes fillable by no one and, for cross-chain orders, unrefundable via the normal `_cancelFromSource`/`onGetResponse` path either, since that path replays the same oversized `_withdraw` loop delivered through `onAccept`, which the relayer cannot execute within a block.

### Impact Explanation
This permanently freezes the escrowed input tokens: a solver cannot profitably (or at all) call `fillOrder` if `_fillSameChain`/`_fillCrossChain` plus `_execute` exceeds the gas limit, and the source-chain refund path for cross-chain orders (`_cancelFromSource` → GET request → `onGetResponse` → `_withdraw`) requires the relayer to deliver a proof/response whose handling replays the same oversized loop, which likewise cannot fit in a block. Escrowed tokens (any ERC-20/native amount the placer chose to lock, potentially attacker-controlled/self-funded to make the attack cheap) become permanently stuck, and legitimate solvers who might otherwise commit capital or gas to fill are denied service. This is a concrete freezing-of-funds / message-non-delivery condition against an unprivileged, single-transaction entry point (`placeOrder`), consistent with High severity.

### Likelihood Explanation
`placeOrder` is fully permissionless and payable by any account; the only cost to the attacker is the ERC-20 transfer cost for however many distinct tokens they choose to escrow (which can be minimal-value, freshly deployed ERC-20s or dust amounts of an existing token used repeatedly across index positions where duplicates are allowed for inputs — only output tokens reject duplicates). No governance or privileged role is required. The attack is a single crafted transaction with a large `Order.inputs`/`Order.output.assets` array; the number of elements needed to exceed a typical L2/L1 gas limit is well within calldata-size and gas-cost bounds for constructing the order.

### Recommendation
Enforce an explicit maximum length on `order.inputs.length` and `order.output.assets.length` inside `placeOrder` (mirroring the `MAX_PHANTOM_TOKEN_PAIRS` pattern already used elsewhere in the codebase, e.g. `modules/pallets/intents-coprocessor/src/types.rs` [12](#0-11) ), sized so that the worst-case `_fillSameChain`/`_fillCrossChain` + `_execute` and `_withdraw` loops comfortably fit within the destination chain's block gas limit, including the cross-chain message-delivery gas budget the relayer/host allocates for `onAccept`.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs` containing N (e.g., several hundred) distinct low-value ERC-20 tokens and/or `order.output.assets` containing N distinct output tokens, escrowing minimal but non-zero amounts of each; this passes the only checks present (`inputs.length != 0`, no duplicate *output* tokens) [1](#0-0) .
2. Any solver attempting `fillOrder` must supply `options.outputs` matching all N entries and pay for N token transfers plus N escrow-release iterations in `_fillSameChain`/`_fillCrossChain` and `_execute`; once N is large enough this exceeds the block gas limit and the call always reverts [8](#0-7) .
3. For a cross-chain order, the attacker's own `_cancelFromSource`/`onGetResponse` refund path replays the same N-sized `_withdraw` loop when delivered by the relayer via `onAccept`, so even self-cancellation cannot complete once N is large enough [2](#0-1) .
4. The escrowed tokens from step 1 remain locked in the contract indefinitely, with no code path capable of moving them.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }

    function _fillSameChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        bool isFullyFilled = true;

        TokenInfo[] memory escrowedInputs = new TokenInfo[](outputsLen);
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            uint256 alreadyFilled = _partialFills[commitment][outputToken];
            uint256 remaining = totalRequired - alreadyFilled;
            if (remaining == 0 || solverAmount == 0) {
                if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
                continue;
            }
            uint256 fillAmount;

            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;
            if (alreadyFilled == 0 && solverAmount > totalRequired) {
                fillAmount = totalRequired;
                (protocolShare, beneficiaryShare) =
                    _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);
            } else {
                fillAmount = solverAmount > remaining ? remaining : solverAmount;
            }

            uint256 amountFilled = alreadyFilled + fillAmount;
            _partialFills[commitment][outputToken] = amountFilled;
            uint256 beneficiaryTotal = fillAmount + beneficiaryShare;

            if (token == address(0)) {
                if (msgValue < beneficiaryTotal + protocolShare) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
                // Inline, not `_sendValue`: this loop is at the via-ir stack limit.
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }

            if (totalRequired > amountFilled) isFullyFilled = false;
            if (protocolShare > 0) emit DustCollected(token, protocolShare);

            uint256 escrowedAmount;
            if (amountFilled == totalRequired) {
                escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
            } else {
                escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
            }
            escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
            outputFills[i] = TokenInfo({token: outputToken, amount: fillAmount});
