### Title
Single reverting token in a multi-token order permanently freezes the entire escrow in `IntentsBase._withdraw` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` releases every escrowed input token for an order in one loop. A single failing token transfer (blacklisted address, paused/pausable token, or any other reverting ERC20) aborts the entire call, which is invoked from the ISMP `onAccept` delivery path — meaning the underlying cross-chain settlement message can never be delivered, and none of the order's escrowed tokens (including perfectly healthy ones) can ever be released. This is the same bug class as the referenced BakerFi `MultiStrategyVault` finding: a single unhealthy leg of a batched operation blocks withdrawal of everything else in the batch.

### Finding Description
`_withdraw` iterates over `body.tokens` and transfers each escrowed token to the beneficiary in a single loop with no isolation between tokens: [1](#0-0) 

If any single token in `body.tokens` reverts on `safeTransfer` (e.g., a USDC-style blacklist hitting the beneficiary, a third-party token that becomes `Pausable` and paused, or any token with transfer restrictions), the entire `_withdraw` call reverts — none of the other, healthy tokens in the same order are released, and the accumulated relayer/protocol fees are not released either.

This function is reached from the ISMP delivery path: when the destination-chain fill triggers a cross-chain `RedeemEscrow`/`RefundEscrow` settlement message back to the source chain, `EvmHost.dispatchIncoming` calls the app's `onAccept`, which (via `IntentGatewayV2`) eventually calls `_withdraw`. Per `EvmHost.dispatchIncoming`, when the low-level call to `onAccept` fails, the host merely deletes the request receipt "so it can be retried" and returns without reverting the batch: [2](#0-1) 

This "retry" is not a real remedy here: because `_withdraw` always replays the *same* `body.tokens` array, a token that permanently reverts (permanently blacklisted beneficiary, or a token contract that is permanently paused/deprecated) makes the message permanently undeliverable. There is no way to exclude the bad token and still release the rest of the escrow — exactly the missing capability the referenced BakerFi report calls out ("We need a way to exclude third parties... without making a withdrawal request").

Unlike the `EscrowRefunded`-via-`onGetResponse`/cancel path — which is bounded by an off-chain relayer proof and is triggered only after expiry — the fill/redeem path here has the same structural flaw as `MultiStrategy.sol`: a batched, per-item operation with no per-item fault isolation, executed as an atomic unit whose failure blocks every other item in the batch.

The same defect exists identically in the Tron variant of the app: [3](#0-2) 

### Impact Explanation
An order can escrow multiple distinct input tokens (`order.inputs`). If any single one of those tokens becomes non-transferable to the settlement beneficiary (blacklisting, pausing, token contract self-destructs its transfer path, etc.) at the time the `RedeemEscrow`/`RefundEscrow` message is delivered, the entire order's escrow — across all input tokens plus accumulated transaction fees — becomes permanently locked in the `IntentGatewayV2`/`IntrinsicIntents` contract. This is a direct, permanent freezing-of-funds condition affecting the solver (who already delivered outputs and is owed the escrow) or the user (in the refund case), for the full value of the order, not just the value of the problematic token.

### Likelihood Explanation
This requires only a single ordinary user action: placing a multi-input-token order where one of the tokens is (or later becomes) subject to a blacklist/pause. Common stablecoins such as USDC/USDT implement address blacklisting, and any third-party ERC20 used as an intent input can implement `Pausable` or similar transfer restrictions. No privileged role or malicious actor is required — a legitimate beneficiary being blacklisted by a token issuer, or a token being paused for unrelated reasons, is sufficient to trigger the permanent freeze. This mirrors the acknowledged-as-valid BakerFi finding's likelihood profile (external third-party pausability is explicitly a realistic, in-scope condition).

### Recommendation
Make `_withdraw` resilient to a single failing token transfer instead of aborting the whole batch:
- Use low-level `call` with a `try/catch`-equivalent success check per token (as already done in the Tron variant's raw `.call`) and skip/queue the failed token's balance rather than reverting the entire function, or
- Split settlement into a per-token claim mechanism so a beneficiary/user can withdraw the healthy tokens now and retry the specific stuck token later, or
- Track failed transfers in escrow state (do not decrement `_orders[...]`) so a permissionless "retry withdraw" for just the stuck token can be called later without blocking release of the other tokens and fees.

### Proof of Concept
1. User places a same-chain or cross-chain order with two input tokens: `USDC` and `DAI`.
2. Solver fills the order (cross-chain case: destination chain sends `RedeemEscrow` back to source).
3. Before/at delivery, the intended beneficiary (solver) is added to USDC's blacklist (or a third-party input token is paused).
4. `EvmHost.dispatchIncoming` calls `onAccept` → `IntentGatewayV2`/`IntrinsicIntents` → `IntentsBase._withdraw`.
5. In the `for` loop over `body.tokens`, `IERC20(USDC).safeTransfer(beneficiary, amount)` reverts.
6. The entire `_withdraw` call reverts; `EvmHost.dispatchIncoming` catches the failure, deletes the request receipt, and returns without emitting `PostRequestHandled` — the message is "retryable" but every retry replays the identical `body.tokens` array and reverts identically.
7. Result: the DAI escrow (healthy token) and the accumulated `TRANSACTION_FEES` are also permanently unreachable, even though only the USDC leg is impaired — permanent freezing of the full order value.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
