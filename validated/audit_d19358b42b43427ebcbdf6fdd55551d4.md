### Title
Unchecked ERC20 return value in `IntentGatewayV2.withdraw`/`onAccept` (Tron) causes escrowed funds to be marked released while transfer silently fails - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` on the Tron variant of the Intents contracts move ERC20 tokens using a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the *call itself* did not revert (`success`). They never decode or validate the returned `bool` payload, unlike the rest of the codebase which uses OpenZeppelin's `SafeERC20.safeTransfer` (e.g. `IntentsBase._withdraw` at `evm/src/apps/intentsv2/IntentsBase.sol:468`). For any ERC20 token that returns `false` on failure instead of reverting, this pattern will treat a failed transfer as a success.

### Finding Description
`withdraw()` is invoked from `onAccept()` when a relayed `RedeemEscrow`/`RefundEscrow` POST request is authenticated, and from `onGetResponse()` for GET-response driven refunds: [1](#0-0) [2](#0-1) 

Inside `withdraw()`, escrowed ERC20 tokens are moved via a raw call whose only validated condition is that the external call did not revert: [3](#0-2) 

The same unchecked pattern is used for transaction-fee redemption and for the `SweepDust` administrative flow: [4](#0-3) [5](#0-4) 

`success` here reflects only whether the target contract's code executed without reverting — it says nothing about the function's own logical outcome. A token that implements `transfer` by returning `false` on failure (rather than reverting) will make this call return `success = true` with `abi.decode`-able return data of `false`, which is never inspected. As a result, `withdraw()` proceeds to decrement `_orders[body.commitment][token]` and mark `_filled[body.commitment] = beneficiary`, emitting `EscrowReleased`/`EscrowRefunded`, even though the beneficiary never actually received the tokens.

This directly mirrors the referenced report's root cause class (ERC20 methods with non-standard return-value semantics being mishandled by the caller), except inverted: instead of reverting on tokens with no return data, this code fails to validate tokens that *do* return a `false` boolean, silently accepting the failure as success.

### Impact Explanation
Because `_filled[body.commitment]` is set and escrow accounting is decremented unconditionally once the low-level call doesn't revert, a solver or user redeeming/refunding escrow with such a token would have their order marked filled/refunded and their escrow balance zeroed out without receiving any tokens. The funds become permanently unrecoverable through the intended withdrawal path (order already marked filled, escrow already decremented), meeting the "permanent freezing/loss of funds" bar. This is reachable directly by any relayer delivering an authenticated `RedeemEscrow`/`RefundEscrow` message or GET response — no privileged role required — fulfilling the "unprivileged... intents escrow" reachability requirement.

### Likelihood Explanation
Requires escrowing/withdrawing a token whose `transfer` can return `false` on failure without reverting (a known, non-trivial subset of ERC20 tokens, distinct from the OpenZeppelin standard but still deployed on-chain, particularly plausible for tokens bridged/used on Tron-adjacent chains where this contract is deployed). Given the Intents system is explicitly designed to be generic across arbitrary ERC20 tokens (per `TokenInfo.token` being attacker/user-supplied in orders), this is a realistic, protocol-level gap rather than a contrived edge case.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the non-Tron `IntentsBase._withdraw` implementation, so that both call failures and logical `false` returns cause a revert instead of silently succeeding.

### Proof of Concept
1. Deploy a mock ERC20 whose `transfer` function returns `false` (without reverting) when, e.g., the caller's balance check fails internally (simulating a non-standard token behavior).
2. Place and escrow an order in `IntentGatewayV2` (Tron variant) using this token.
3. Trigger a `RedeemEscrow` (or `RefundEscrow`) delivery via `onAccept`, or a GET response via `onGetResponse`, pointing at the escrowed commitment.
4. Observe: `withdraw()` calls `token.call(...transfer...)`; `success` is `true` (call didn't revert) even though `transfer` returned `false` and no tokens moved to `beneficiary`.
5. Observe: `_orders[body.commitment][token]` is decremented, `_filled[body.commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — the beneficiary's tokens are now unrecoverable via the contract despite never being received.
