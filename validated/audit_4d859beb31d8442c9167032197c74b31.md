### Title
Stale debt position used after unguarded external swap allows mid-flight liquidation to corrupt repayment accounting - ([File: contracts/controller/src/strategies/repay_debt_with_collateral.rs](contracts/controller/src/strategies/repay_debt_with_collateral.rs))

### Summary
`process_repay_debt_with_collateral` snapshots the account's `DebtPosition` **before** executing an unallowlisted swap route, then repays the pool using that stale snapshot. The swap leg (`swap_tokens_or_passthrough`) executes arbitrary venue contracts **outside** `storage::with_flash_guard`, so a hostile venue (or token hook) can reenter the controller via permissionless `liquidate`/`update_indexes` and mutate the very debt position the in-flight request still references — the Soroban analog of `ffs_ep0_queue_wait` dereferencing `ep0req` after `functionfs_unbind` freed it.

### Finding Description
In `repay_via_collateral_swap` (contracts/controller/src/strategies/repay_debt_with_collateral.rs:96-132):

```rust
let debt_pos = get_debt_position_or_panic(env, account, debt);   // line 106: snapshot

let debt_available = withdraw_and_swap_from_supply(              // lines 108-118: external calls
    env, account, cache, caller, collateral, collateral_amount,
    &debt.asset, swap, events::PositionAction::RpColWd,
);

repay_debt_from_controller(                                      // lines 120-131: uses stale debt_pos
    env, account, cache, caller,
    StrategyRepay { debt, debt_available, debt_pos: &debt_pos, ... },
);
```

`withdraw_and_swap_from_supply` (contracts/controller/src/strategies/legs.rs:233-259) only wraps `execute_withdrawal` in `with_flash_guard` (legs.rs:93-106); the subsequent `swap_tokens_or_passthrough` call at legs.rs:258 runs **after** the guard is released. That swaps the withdrawn collateral through user-supplied, unallowlisted route venues.

`repay_debt_from_controller` (legs.rs:40-81) then forwards `debt_available` to the pool and calls `repay_prefunded_position` with `position: req.debt_pos` — the `ScaledPositionRaw` captured at line 106, reflecting the pre-swap `scaled_amount`.

The protocol itself acknowledges this exact threat shape: `process_flash_position` comments "token hooks can reenter first" and wraps both forwarding and the receiver callback in `with_flash_guard` (contracts/controller/src/strategies/flash_position.rs:119-143). The repay-with-collateral swap path receives no equivalent serialization — mirroring the kernel bug where `ffs_ep0_queue_wait` took only `ev.waitq.lock` while `functionfs_unbind` was unbounded.

### Impact Explanation
During the unguarded swap, the malicious venue contract can call any permissionless controller entrypoint. Because the withdrawal leg already removed collateral from the account (it is sitting in the controller/venue, not yet repaid), the account's health factor is temporarily depressed. If it crosses below the liquidation threshold, the venue (acting as liquidator) invokes `liquidate` on this account, restructuring `borrow_positions` — repaying or seizing part of the `debt` position and mutating its `scaled_amount` — or a permissionless `update_indexes` re-stamps the market index. Either way the `debt_pos` handed to `repay_prefunded_position` no longer describes the live position. Depending on how the pool consumes the supplied `ScaledPositionRaw`, this lets the attacker settle a larger scaled-debt credit than the tokens delivered justify, or write down debt that a liquidation already moved — corrupting per-position debt accounting, enabling debt erasure for less than full repayment (protocol insolvency / theft of pool funds), or permanently desyncing controller and pool position records (frozen funds).

### Likelihood Explanation
Fully attacker-driven: the caller supplies the swap route, so every reentry venue is attacker-controlled, and the attacker owns the account being mutated. The exploit window is inherent to the call ordering — collateral out, external callback, then debt repayment against a stale snapshot — and requires no privileged role. The main precondition is arranging HF near the liquidation boundary so a mid-flight `liquidate` succeeds; `update_indexes` needs no precondition at all but yields a weaker effect.

### Recommendation
Re-fetch the debt position after `withdraw_and_swap_from_supply` returns (call `get_debt_position_or_panic` again on the mutated `account` rather than reusing `debt_pos`), and extend `storage::with_flash_guard` to cover the swap leg the same way `process_flash_position` guards the receiver callback — i.e., serialize the external venue calls against controller state mutation, the direct analog of the fix's `mutex_lock(ffs->mutex)` around `ffs_ep0_queue_wait` and `functionfs_unbind`.

### Proof of Concept
1. Attacker owns account A with collateral C (asset X) and debt D (asset Y), HF slightly above liquidation threshold.
2. Calls `repay_debt_with_collateral(account_id=A, collateral=X, collateral_amount=..., debt=Y, swap=<route through attacker venue V>)`.
3. `repay_via_collateral_swap` stores `debt_pos` (A's scaled debt for Y) at line 106, withdraws X to the controller, guard released, then calls venue V.
4. V reenters `controller.liquidate` on account A — HF is now below threshold because X left the supply positions — repaying/seizing debt Y and mutating `scaled_amount` (or calls `update_indexes` to restamp Y's market index).
5. V returns swapped Y tokens; `repay_debt_from_controller` calls `repay_prefunded_position` with the stale `ScaledPositionRaw`, settling scaled debt per pre-swap state rather than the position's current reality.

Caveat: I could not inspect `repay_prefunded_position`/pool-side validation of the supplied `ScaledPositionRaw` in the available iterations; whether the pool bounds the submitted scaled amount against live state determines whether this is full debt-erasure insolvency or a lesser desync. The unguarded-swap ordering and stale snapshot are confirmed in the cited code.
