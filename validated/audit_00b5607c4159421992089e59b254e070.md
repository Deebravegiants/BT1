### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body against the HMAC, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the app relies on to route and attribute the webhook are all read from unauthenticated HTTP headers. This is the exact bug class from the report — a value that the code *acts on* (here, the shop the payload is attributed to) is not bound by the value that is *cryptographically verified* (here, only the request body).

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

and `Registry.process` validates the HMAC exclusively over that returned string via `Utils::HmacValidator.validate(request)`: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers that are never part of the signed material: [3](#0-2) 

`Registry.process` then dispatches to the app's handler using `request.topic` (unauthenticated) to select the handler, and builds `WebhookMetadata` using `request.shop`, `request.api_version`, `request.webhook_id` — all unauthenticated — while only the JSON body content is guaranteed to have been generated with knowledge of `Context.api_secret_key`: [4](#0-3) 

The invariant that should hold is: `shop attributed to the webhook == shop the HMAC secret was used to authenticate`. Because `to_signable_string` only commits to the body bytes, this equality is not enforced — the header-derived `shop` can differ from whatever shop the signature actually corresponds to, exactly as `totalDuration` in the report drifted from the invariant `endTime - startTime` because the code tracked/updated a quantity not equal to what was originally committed.

### Impact Explanation
Because the app's `api_secret_key` is shared across every shop that installs the app (it's an app-level secret, not per-shop), any merchant who has the app installed on their own store — an unprivileged actor with respect to other tenants — can capture a legitimately-signed `(raw_body, hmac)` pair delivered to their own endpoint (by controlling their own webhook receiver) and then replay that exact body/HMAC to the app's webhook endpoint while altering only the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) headers to name a victim shop. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the payload to the handler tagged with the attacker-chosen `shop`. This is a cross-tenant data/identity confusion: business logic keyed on `WebhookMetadata#shop` (e.g., processing `customers/data_request`, `customers/redact`, `shop/redact`, or order/inventory updates) can be made to run against a different tenant's data than the one that actually produced the signed payload.

### Likelihood Explanation
Requires only that the attacker be a legitimate merchant/user of the target app on their own store (no leaked credentials, no TLS interception, no privileged access) — they already possess a channel to obtain validly-signed webhook bodies for their own shop and can replay them with modified headers to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop`) in the material verified by the HMAC, or otherwise cryptographically bind the header-derived identity to the signed payload (e.g., have `to_signable_string` incorporate the shop domain header, matching how Shopify's actual webhook signing scheme ties the signature to the specific delivery). Do not trust header values for tenant attribution when only the body is what's authenticated.

### Proof of Concept
1. App merchant installs the app on `attacker-shop.myshopify.com` and configures a webhook receiver they control (e.g., via a proxy) to capture inbound Shopify webhook deliveries, obtaining a `(raw_body, shopify-hmac-sha256)` pair that is valid under the app's shared `api_secret_key`.
2. Attacker sends this exact `raw_body` and `hmac` value to the app's real webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally an arbitrary `shopify-topic`/`shopify-webhook-id` for a topic registered by the app).
3. `Utils::HmacValidator.validate(request)` succeeds because it recomputes the HMAC only over `@raw_body`: [1](#0-0) 
4. `Registry.process` looks up the handler by the attacker-controlled `request.topic` and invokes it with `shop: request.shop` set to `victim-shop.myshopify.com`, even though the payload content actually belongs to `attacker-shop.myshopify.com`: [5](#0-4) 
5. The app's webhook handler processes attacker-supplied data under the victim shop's tenant context.
