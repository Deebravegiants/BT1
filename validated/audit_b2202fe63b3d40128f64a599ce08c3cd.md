### Title
Unchecked ERC20 return value in escrow withdrawal allows silent fund loss - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2` on Tron pulls tokens into escrow with `safeTransferFrom` (which correctly checks return data), but pays escrowed tokens back out via a raw low-level `.call` that only checks the call's `success` bool, never decoding/validating the ERC20 `transfer` function's returned boolean. A non-standard ERC20 token that returns `false` on failure instead of reverting will make the withdrawal appear successful even though no tokens moved.

### Finding Description
In `withdraw()`, escrowed tokens and transaction fees are released using: [1](#0-0) 

Both branches check `success` only — the boolean returned by the `IERC20.transfer` low-level call is completely ignored. This is the same bug class as the reported "no return value check for transfer/transferFrom" issue: with a token that returns `false` (rather than reverting) when a transfer cannot be completed, `success` is still `true` because the *call itself* did not revert, so the code proceeds as if the transfer succeeded.

Meanwhile, the escrow accounting is unconditionally updated: [2](#0-1) 

and the order is marked `_filled[body.commitment] = beneficiary` before/independent of whether the transfer actually delivered funds. `SweepDust` has the identical pattern: [3](#0-2) 

The token used for escrow is fully attacker-controlled: `placeOrder` accepts any `order.inputs[i].token` address chosen by the order creator, using `safeTransferFrom` to pull it in: [4](#0-3) 

This is notable because the same repository's canonical EVM implementation (`IntentsBase.sol`) already uses `SafeERC20.safeTransfer` consistently for outbound payouts: [5](#0-4) 

confirming the Tron variant is an inconsistent, weaker re-implementation of the same withdrawal logic, even though `SafeERC20`/`IERC20` are already imported and used elsewhere (`using SafeERC20 for IERC20;`) in the same file.

### Impact Explanation
A user places an order (`placeOrder`) whose input token is a custom/non-standard ERC20 that accepts `transferFrom` on deposit but returns `false` (without reverting) when the gateway later attempts to pay it out via `transfer` in `withdraw()`. When the order is filled/refunded and the cross-chain (or GET-response) settlement request is delivered, `withdraw()` decrements the escrow bookkeeping and marks the order filled/refunded, but the solver or the refund beneficiary receives nothing — the tokens remain stuck in the contract with no accounting entry pointing to them (`_orders[...]` already zeroed and `_filled[...]` set), i.e., permanently frozen/lost funds for the legitimate recipient. This is a fund-loss/freezing bug reachable purely through the normal order-fill/settlement flow, not requiring any privileged or malicious admin action.

### Likelihood Explanation
Likelihood is limited to orders that escrow non-standard ERC20 tokens (tokens that signal failure by returning `false` rather than reverting), which is a known, common pattern among real-world tokens (deflationary/pausable/blacklist tokens, some Tron TRC20 tokens). Any user can freely choose an arbitrary token address as `order.inputs[i].token` when calling `placeOrder`, so the attack surface (or accidental trigger by a legitimate but non-conforming token) is fully reachable without special privileges.

### Recommendation
Replace the manual low-level `.call` + `success`-only check in `withdraw()` and `handlePostRequest`'s `SweepDust` branch with `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;` elsewhere in the file), matching the pattern already used in `IntentsBase.sol`'s `_withdraw`/`_execute`. This ensures both call failures and false-return failures cause a revert instead of being silently accepted as success.

### Proof of Concept
1. Deploy a malicious ERC20 `EvilToken` whose `transferFrom` succeeds normally (allowing escrow deposit) but whose `transfer` function returns `false` without reverting once a specific internal condition is met (e.g., a toggle the attacker controls, or simply always returns `false` for calls from the gateway).
2. Attacker calls `placeOrder` on `IntentGatewayV2` (Tron) with `order.inputs[0].token = EvilToken`, escrowing tokens successfully via `safeTransferFrom`.
3. A solver fills the order cross-chain; the destination chain dispatches a `RedeemEscrow` request back to the source chain.
4. `handlePostRequest` authenticates the request and calls `withdraw(body, false)`.
5. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, abi.encode(false))` — `success` is `true`, so the check `if (!success) revert TransferFailed();` passes even though the transfer failed.
6. `_orders[body.commitment][token] -= amount;` executes and `_filled[body.commitment] = beneficiary;` is set, permanently marking the order as settled — the solver's `EvilToken` balance never increases, and the escrowed tokens are unrecoverable through the contract's accounting.
