### Title
`operator_qr_expiration_time` default (23h) is too long, allowing stale operator location data to authorize user signups - ([File: src/config.rs])

### Summary
The `Config::default()` implementation sets `operator_qr_expiration_time` to `Duration::from_secs(60 * 60 * 23)` (23 hours). This value determines how long a previously-scanned operator's `OperatorData` (including GPS `session_coordinates`) is trusted and reused to authorize subsequent user signups without re-scanning/re-validating the operator QR code. Because signup authorization by default relies solely on this cached, increasingly stale location (`user_qr_validation_use_only_operator_location: true`), an operator's location captured up to 23 hours earlier can still be used to validate new signups, exactly mirroring the "stale value trusted for too long" class of bug described in the external report (where a `FETCH_TIME` that is too large causes stale data to be relied upon).

### Finding Description
`OperatorData` is captured once when the operator QR code is scanned and validated, storing `location_data` (operator GPS coordinates) alongside an `Instant` timestamp: [1](#0-0) 

This cached data is considered valid and reused as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, both when initially scanning QR codes in self-serve mode and when resolving the remaining QR codes for a signup: [2](#0-1) 

The default expiration is set far larger than a single signup session should reasonably require: [3](#0-2) 

This stale `OperatorData.location_data.session_coordinates` is then sent directly to the backend to authorize the *user* QR code/signup, and by default this is the only signal used for that authorization since `user_qr_validation_use_only_operator_location` defaults to `true`: [4](#0-3) [5](#0-4) 

Because the operator's coordinates are captured once and can be reused for up to 23 hours across many separate signups, the location used to authorize a signup can be significantly out of date relative to the operator's actual, current location — an operator that has moved to a different city/country within that 23-hour window will still have signups authorized against their old, stale coordinates.

### Impact Explanation
Signups can be authorized/attributed to a location (`session_coordinates`) that no longer reflects where the operator (and by extension the physical Orb device and the user being enrolled) actually is. Since location is used as a fraud/authorization signal for the signup session (`api/v2/session/{user_id}/status?lat=...&lon=...`), a stale value undermines the integrity of this location-based authorization check, potentially permitting signups that should have been rejected or flagged based on current location context. This is a legitimate impact in the "signup authorization" category since the check itself is designed to bind the signup to a current, trustworthy location.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the operator/orb to remain "logged in" under the same scanned operator QR code for an extended period (up to 23 hours, per the default config) while performing multiple signups, during which the operator's real-world location changes. This is a plausible operational scenario (e.g., an Orb transported between deployment locations without operator QR re-scan) rather than requiring active exploitation.

### Recommendation
Reduce `operator_qr_expiration_time`'s default value in `src/config.rs` to a much shorter duration (e.g., on the order of tens of minutes to a couple hours) so that operator location data used to authorize signups more closely tracks the operator's actual current location, consistent with the intended purpose of the expiration mechanism.

### Proof of Concept
1. Operator scans operator QR code at Location A; `OperatorData.location_data.session_coordinates` and `timestamp` are cached (`src/plans/mod.rs` `scan_initial_qr_codes`/`scan_remaining_qr_codes`).
2. Orb (with cached operator session) is moved to Location B, or operator moves, before 23 hours elapse.
3. A new user signup begins; because `operator_data.timestamp.elapsed() < operator_qr_expiration_time` still holds, the stale Location A coordinates are reused without a fresh operator QR scan.
4. `backend::user_status::request` sends the stale Location A `lat`/`lon` to authorize the signup (`src/backend/user_status.rs` `do_request`), causing the signup to be authorized under location data that no longer matches reality.

        &mut self,
        orb: &mut Orb,
        qr_codes: &mut QrCodes,
        self_serve: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<()> {
        if self_serve
            && qr_codes
                .operator_timestamp()
                .map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)
        {
            loop {
                let qr_capture_start = Instant::now();
                let operator_qr_code =
                    self.scan_operator_qr_code(orb, None).await?.expect("to never timeout");
                let Some(operator_qr_code) =
                    self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                else {
                    continue;
                };
                let Some((_, operator_location_data)) =
                    self.verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start).await?
                else {
                    continue;
                };
                *qr_codes = QrCodes::Operator {
                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }
