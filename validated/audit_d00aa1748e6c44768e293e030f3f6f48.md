### Title
Webhook `shop` and `topic` are not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating that the HMAC in the `X-Shopify-Hmac-Sha256` header matches a signature computed over the **raw body only**. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — all of which are subsequently trusted to route and attribute the webhook — are never part of the signed data. This breaks the identity binding `signed_bytes == acted_on_bytes`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` and compares it to the `hmac` value: [2](#0-1) 

`Webhooks::Registry.process` uses this validator as the sole authentication gate, then immediately trusts `request.topic` for handler dispatch and `request.shop` for tenant attribution — both derived from headers that were never part of the signed bytes: [3](#0-2) 

Because `shop` and `topic` come from headers (`shopify_header("shop-domain")`, `shopify_header("topic")`) rather than from `@raw_body`, they are parsed but unverified: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, bytes-that-determine-shop-and-topic)`. Instead the gem enforces only `hmac == HMAC(secret, raw_body)`, while `shop` and `topic` — the two values the host application uses to decide *which tenant* and *which handler* processes the payload — are taken from unauthenticated header bytes disjoint from the signed bytes.

### Impact Explanation
An app's `api_secret_key` is shared across every shop that installs the app — it is not shop-specific. Any unprivileged internet user can install the app on a shop they control (e.g. a free development store) and trigger a legitimate webhook delivery with attacker-chosen body content (e.g. `customers/update`, `orders/create` payloads with attacker-controlled fields). Shopify signs that body with the app's real `api_secret_key`, producing a valid `(raw_body, hmac)` pair that the attacker fully observes. Because `shop` and `topic` are excluded from the signed bytes, the attacker can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) with any victim shop domain / topic of their choosing. `HmacValidator.validate` still returns `true`, and `Registry.process` dispatches the attacker-crafted body to the handler registered for the spoofed topic, tagged with the victim's shop id via `WebhookMetadata`. Any host application that uses `request.shop` to look up per-tenant state (as the gem's own docs recommend) will apply attacker-controlled data to the wrong tenant — a cross-tenant data injection/corruption primitive reachable with no credentials beyond the ability to install the app once on an attacker-owned store.

### Likelihood Explanation
Moderate-to-high: the webhook endpoint is a public HTTP endpoint by design, `api_secret_key` is shared per-app (not per-shop), and getting one authentic `(body, hmac)` pair only requires installing the app on any shop the attacker controls and performing an ordinary write action. No TLS interception, leaked credentials, or privileged access is required — only crafting/replaying an HTTP POST with modified headers, squarely inside the "unprivileged internet user" threat model.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed payload used for HMAC verification (or otherwise cryptographically bind them to the body before trusting them for routing/attribution), e.g. by validating them out-of-band via a separate signed token, or by rejecting/reconciling any webhook whose header-derived `shop` does not match a shop the session/storage layer already associates with that specific `webhook_id`/subscription.

### Proof of Concept
1. Attacker installs the app on their own dev shop `attacker.myshopify.com` and triggers a webhook (e.g., updates a customer to fire `customers/update`) with attacker-controlled body fields.
2. Attacker captures the resulting POST: raw JSON body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — valid per `HmacValidator.validate_signature`.
3. Attacker sends a new POST to the same webhook endpoint with identical body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `Webhooks::Request.new` parses the spoofed headers; `HmacValidator.validate(request)` returns `true` because it only checks `B` against `H`.
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, causing the host app to process attacker-controlled data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
