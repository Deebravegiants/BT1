## Finding

### Title
Storage-deposit cache key collision lets one NEAR account's "sufficient balance" status be granted to another, causing withdrawal fee/storage-deposit checks to be bypassed - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU cache key by naively concatenating `contractId` and `accountId` with no separator: [1](#0-0) 

```
const key = `${contractId}${accountId}`;
```

Because NEAR account identifiers freely allow dots, dashes and digits, two different `(contractId, accountId)` pairs can produce the identical concatenated string (e.g. `"a.nearb" + "c.near"` and `"a.near" + "bc.near"` both yield `"a.nearbc.near"`). Since the cache is a single instance-level `LRUCache` shared across every withdrawal processed by that `DirectBridge`/SDK instance (i.e., shared across all users, analogous to the Symfony bug where one firewall's authenticated token became visible to all firewalls), a colliding key means the "storage deposit sufficient" result computed for account A's withdrawal of token X can be silently reused as the answer for account B's withdrawal of token Y.

### Finding Description
`getCachedStorageDepositValue` is used by `estimateWithdrawalFee` to decide whether a NEAR storage-deposit fee must be charged before an NEP-141 `ft_transfer` withdrawal: [2](#0-1) 

The cache is only populated when the account already has sufficient storage balance for that specific token (`result[1] >= result[0]`), and future callers that hit the same *string* key skip the RPC round trip and reuse `[minStorageBalance, userStorageBalance]` verbatim: [3](#0-2) 

If an attacker crafts a `destinationAddress` (fully attacker-controlled, since it's the withdrawal destination) whose concatenation with a target token's `contractId` collides with a previously-cached `(contractId', accountId')` key that was marked "sufficient," `estimateWithdrawalFee` will wrongly report `feeAmount = 0` / `amount = 0n` for a destination account that does **not** actually have sufficient storage balance on that token. The equality broken here is: *"storage balance validated for account/token pair (A, X)" == "storage balance validated for account/token pair (B, Y)"* — which should never hold for differing pairs, but the ambiguous key construction lets it hold.

Contrast this with the sibling `OmniBridge` class, which correctly delimits its analogous cache key (`` `${omniChainKind}:${contractId}` ``): [4](#0-3) 

confirming the `DirectBridge` concatenation is a real bug in this codebase rather than an accepted pattern.

### Impact Explanation
When the collision fires, the SDK proceeds to build a withdrawal intent with the storage-deposit fee omitted, based on `createWithdrawIntentPrimitive`: [5](#0-4) 

Since the destination account in fact lacks the NEP-141 storage deposit, the on-chain `ft_transfer` to that account will fail (NEAR's storage-staking model requires the receiver to be registered with the token contract). This leaves the withdrawal stuck/failed after the intent has already been signed and settled off-chain as "processed," requiring manual intervention to recover or refund — matching the High-severity class "a withdrawal stuck until manual intervention" / "a fee overcharge or a solver overpaid" analog (here, a fee undercharge that later externalizes as a stuck transfer).

### Likelihood Explanation
Exploitability requires:
1. Full control of `destinationAddress` (trivially true — it's a normal SDK/user input).
2. The `DirectBridge` cache being a shared, long-lived instance serving many users/withdrawals (true — it is created once per SDK instance and reused for all `estimateWithdrawalFee`/`createWithdrawalIntents` calls).
3. Finding or waiting for a `(contractId, accountId)` string collision with an already-cached "sufficient" entry, which is a NEAR-account-ID string-crafting problem, not something requiring the relayer, RPC, or any admin to behave maliciously — it is entirely under the calling user's control given enough attempts against a long-running relayer/service process using this SDK. This keeps it within the "unprivileged" analog class demanded by the prompt.

### Recommendation
Use an unambiguous, delimited cache key (e.g. `` `${contractId}:${accountId}` `` with escaping, or a two-level `Map`/array key), mirroring the pattern already used by `OmniBridge.getCachedDestinationTokenAddress`.

### Proof of Concept
1. Attacker A withdraws token `contractId = "a.near"` to `destinationAddress = "bc.near"` where `"bc.near"` genuinely satisfies the storage deposit. This populates the cache entry keyed `"a.nearbc.near"` with `[min, sufficientBalance]`.
2. Attacker B (or the same attacker with a second account) requests a withdrawal of token `contractId = "a.nearb"` (a distinct, valid NEP-141 token account under the `.near` accounts hierarchy) to `destinationAddress = "c.near"`, which does **not** actually have sufficient storage deposit on that token.
3. `getCachedStorageDepositValue("a.nearb", "c.near")` computes the same key `"a.nearbc.near"`, hits the cache populated in step 1, and returns the stale "sufficient" result.
4. `estimateWithdrawalFee` returns `amount: 0n` (no storage-deposit fee charged), and `createWithdrawalIntents` builds a withdrawal intent without a storage-deposit top-up.
5. On execution, the NEP-141 `ft_transfer` to `"c.near"` for `"a.nearb"` fails on-chain due to missing storage registration, leaving the withdrawal stuck after the intent was already signed/settled.
