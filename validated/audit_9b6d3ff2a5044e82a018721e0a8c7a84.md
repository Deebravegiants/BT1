The `Webhooks::Request` object's `to_signable_string` only returns `@raw_body` [1](#0-0) , meaning the HMAC that `Registry.process` validates only authenticates the request body, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers [2](#0-1) . Yet `request.shop` (read straight from the unauthenticated `shopify-shop-domain` header) is forwarded as the tenant identity in `WebhookMetadata` to the host app's handler [3](#0-2) .

### Title
Webhook tenant identity (`shop-domain` header) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — all read from HTTP headers — are never included in the signed payload. Because the merchant identity (`shop`) delivered to the host application's webhook handler is taken from an unauthenticated header, an attacker who can influence or replay the request headers (e.g. via a misconfigured proxy, header-injection point, or a captured legitimate payload from Shop A) can cause the handler to process the webhook body as if it belonged to Shop B.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. only the body bytes, and compares against the `hmac-sha256` header value [4](#0-3) .

`Registry.process` gates entirely on this body-only HMAC check, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all sourced from headers that were never part of the signed bytes — and passes them into `WebhookMetadata` for the handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [2](#0-1) 

The identity equality the gem should guarantee is: `shop_the_HMAC_was_computed_for == shop_delivered_to_the_handler`. Because `shop` is parsed from `shopify-shop-domain`/`x-shopify-shop-domain` headers and never enters `to_signable_string`, this equality does not hold — the gem verifies "these bytes (body) came from someone holding `api_secret_key`" but acts on "this shop-domain header value" as the tenant identity, which is a different, unauthenticated input.

### Impact Explanation
Host applications built on this gem (e.g. via the documented `Webhooks::Registry.process`/`WebhookHandler` interface) rely on `WebhookMetadata#shop` to know which merchant/tenant the webhook body belongs to, typically to look up that shop's session/access token and perform actions or store data under that shop. If the `shop` header can be manipulated independently of the signed body (for example, a webhook body that is legitimate/replayable, or an environment where headers are set from an untrusted proxy hop before signature verification), the host app will process order/customer/shop data believed to belong to Shop B under Shop A's identity or vice versa — a cross-tenant data confusion crossing the shop boundary that this gem is supposed to enforce via HMAC validation.

### Likelihood Explanation
Exploitation still requires some ability to influence the `shop-domain` header on an otherwise-valid signed request (e.g., a captured/replayed webhook body combined with header rewriting at an intermediary, or a host environment that does not strictly bind headers to the TLS-terminated request from Shopify). This is a real but narrower path than an outright HMAC bypass, since a valid `(body, hmac)` pair is still required. It is a design gap in the gem: nothing in `Webhooks::Request`/`Registry` binds the header-derived identity to the signature, so any environment where headers and body can be decoupled becomes exploitable.

### Recommendation
Include the shop-identifying header (and ideally topic/webhook-id) in the signable string, or otherwise cryptographically bind them to the verified payload before trusting `request.shop` in `WebhookMetadata`. At minimum, document and/or enforce that `shop-domain` must be independently corroborated (e.g., against a known/registered shop from session storage) before being used as a trust boundary, rather than passing the raw header value straight through to handlers as verified tenant identity.

### Proof of Concept
1. Attacker captures a legitimate Shopify webhook HTTP request for `shop-a.myshopify.com` (valid `x-shopify-hmac-sha256` over the JSON body).
2. Attacker replays the identical body and HMAC header, but rewrites `x-shopify-shop-domain` to `shop-b.myshopify.com` (possible whenever headers are set/forwarded by an intermediary that is not part of Shopify's TLS-terminated path, or whenever the request pipeline reconstructs headers separately from the body before invoking this gem).
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `@raw_body` only and it matches — validation passes.
4. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` using the attacker-controlled `shop-domain` header value, and the host app's handler processes the body as belonging to `shop-b.myshopify.com`.
