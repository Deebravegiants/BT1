### Title
LiFi swap: attacker-set `relay == address(0)` makes `sendToRelay` silently no-op, permanently stranding `relayFee`/`hinkalFee` in `ExternalActionSwap` - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
In `ExternalActionSwap.swap`, `sendToRelay` is a conditional no-op when `relay == address(0)`, meaning the relay/protocol fee is silently never transferred out of the action contract, while `amountToSendToHinkal` is still computed as `swappedAmount - totalFee` and is what is actually transferred to Hinkal and credited as the UTXO. This causes the fee amount to be permanently stranded in the `ExternalActionSwap`/`LifiExternalAction` contract balance rather than reaching the relay, but it does **not** cause Hinkal to over-credit a UTXO relative to what is actually delivered.

### Finding Description
The claimed equality to check is `amountToSendToHinkal == swappedAmount - totalFee` and whether the credited UTXO equals the value actually delivered to Hinkal.

`sendToRelay` in `contracts/Transferer.sol` is defined as: [1](#0-0) 
which only performs a transfer `if (relay != address(0) && actualAmount > 0)`. If an attacker sets `circomData.relay = address(0)`, both `sendToRelay` calls in `ExternalActionSwap.swap` become no-ops: [2](#0-1) 

However, `totalFee` and `amountToSendToHinkal` are computed independently of whether `sendToRelay` actually moved tokens: [3](#0-2) 

`amountToSendToHinkal = swappedAmount - totalFee` is unconditionally transferred to `msg.sender` (Hinkal) via `transferERC20TokenOrETH`, and the UTXO credited to the user carries exactly this `amountToSendToHinkal` value. Since this value is fixed by construction and is what is literally transferred, the UTXO credited always equals the value delivered to Hinkal in this call — there is no divergence and no over-crediting. The `swappedAmount` itself is computed as an actual balance delta in `callRouter` (`getERC20OrETHBalance` before/after), not from a router return value, so return-value-based token behavior ("silently returns false") does not desynchronize `swappedAmount` from real balances either: [4](#0-3) 

What does happen: the `relayFee + hinkalFee` tokens that should have gone to the relay are subtracted from the user's own credited amount (i.e., the user pays the fee) but are never transferred anywhere — they remain sitting in the `ExternalActionSwap`/`LifiExternalAction` contract's token/ETH balance. No sweep/rescue function was found in `ExternalActionSwap.sol` (only `setHinkalHelper` is `onlyOwner`); whether `ExternalActionBaseV2` provides a recovery mechanism was not confirmed from the files examined.

### Impact Explanation
This does not enable theft of user funds or over-crediting of shielded UTXOs — the credited UTXO amount always matches what is actually transferred to Hinkal in the same call, since `amountToSendToHinkal` and the UTXO amount are the same fixed value computed before any transfer occurs. The actual impact is that the relay/protocol fee (`relayFee + hinkalFee`) for that swap becomes stuck in the action contract instead of reaching the relay, i.e., permanent freezing/loss of protocol or relay fee revenue for that transaction. This maps to the "High: theft or permanent freezing of protocol/relay fees" category, not Critical.

### Likelihood Explanation
Any unprivileged user executing a LiFi swap action can trivially set `circomData.relay = address(0)` since `relay` is attacker-supplied metadata with no visible on-chain check forcing it to be non-zero in the reviewed files (`ExternalActionSwap.sol`, `Transferer.sol`, `LifiExternalAction.sol`). It costs the attacker nothing extra — they already forfeit that fee amount from their own credited UTXO regardless of whether the relay receives it — so there is no direct financial upside for the attacker, but it is repeatable per transaction and directly harms relay/protocol fee revenue. Whether `Hinkal.sol`/`HinkalHelper.sol` enforce `relay != address(0)` elsewhere was not fully confirmed within the available context.

### Recommendation
In `sendToRelay` (or in `ExternalActionSwap.swap`), require `relay != address(0)` before proceeding, or route the fee to a fixed protocol treasury address whenever `relay == address(0)` instead of silently skipping the transfer, so the fee amount deducted from the user is never stranded in the action contract.

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction` with a mock router that returns a fixed `swappedAmount` of output token to the action contract.
2. Craft `CircomData` with `relay = address(0)`, non-zero `feeStructure.flatFee` and `variableRate`.
3. Call `swap`/`runAction` and assert:
   - `amountToSendToHinkal == swappedAmount - totalFee` (holds).
   - The UTXO credited amount equals the actual token balance transferred to Hinkal (holds — no over-credit).
   - The `relayFee + hinkalFee` amount remains in `LifiExternalAction`'s balance after the call (confirms fee stranding/permanent freezing, since no sweep function exists in `ExternalActionSwap.sol`).
