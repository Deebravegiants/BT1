### Title
Rejected gateway node handshake leaves a leaked WebSocket connection and connection-attempt record - ([File: core/services/gateway/network/wsserver.go])

### Summary
`webSocketServer.handleRequest` upgrades an inbound node connection to a WebSocket before all validation is complete. On the specific error path where `s.config.MaxRequestBytesLimiter.Limit(r.Context())` returns an error, the function returns immediately without closing the just-upgraded `conn` and without calling `s.acceptor.AbortHandshake(attemptID)`. [1](#0-0) 

### Finding Description
The handshake flow is: `StartHandshake` records an in-memory attempt in `connectionManager.connAttempts` [2](#0-1)  → the socket is upgraded via `s.upgrader.Upgrade` → a request-size limit is fetched → the handshake response is read → `FinalizeHandshake` is called, which deletes the attempt from `connAttempts` on success, or the caller calls `AbortHandshake` to delete it on failure.

Every other failure branch in `handleRequest` (Upgrade failure, `ReadMessage` failure, `FinalizeHandshake` failure) correctly closes `conn` and calls `s.acceptor.AbortHandshake(attemptID)` to clean up the attempt state: [3](#0-2) 

However, the `MaxRequestBytesLimiter.Limit` error branch is missing both cleanup calls:
```go
maxRequestBytes, err := s.config.MaxRequestBytesLimiter.Limit(r.Context())
if err != nil {
    s.lggr.Errorw("failed to get request size limit", "err", err)
    w.WriteHeader(http.StatusInternalServerError)
    return
}
``` [4](#0-3) 

At this point the TCP connection has already been hijacked/upgraded to a WebSocket by `s.upgrader.Upgrade` (line 134), so `w.WriteHeader` is a no-op on the hijacked connection and the socket is never closed — it leaks as an open, unmanaged file descriptor/goroutine-less socket. Simultaneously, the corresponding entry created by `StartHandshake` in `connectionManager.connAttempts` is never removed (`AbortHandshake` is never invoked), so the map entry (holding a `connAttempt` struct with `nodeState`, `challenge`, etc.) persists indefinitely. This mirrors CVE-2017-16672's root cause: a session/attempt object created for a request that is rejected before being fully established is never destroyed, allowing unbounded accumulation over time.

This is unlike a pure DoS via connection flooding — the leak is a distinct code defect (missing cleanup in one specific branch), reachable by any actor able to reach the gateway's node-server endpoint with a header that passes `StartHandshake`'s auth-header parsing but hits this branch.

### Impact Explanation
Repeated triggering of this branch leaks WebSocket connections (open sockets) and `connAttempts` map entries. Over time and repeated attempts this results in memory/file-descriptor exhaustion in the Gateway process, potentially crashing or degrading gateway availability for legitimate DON node connections — directly analogous to the "Asterisk can run out of memory and crash" impact in CVE-2017-16672. This does not by itself grant authentication bypass or secret disclosure; the impact is limited to availability (DoS) of the gateway's node-connection subsystem.

### Likelihood Explanation
Reaching this branch requires `MaxRequestBytesLimiter.Limit(ctx)` to return a non-nil error. `ensureLimiters` builds this from `limits.MakeUpperBoundLimiter` [5](#0-4) , which is a settings-based rate/limit component; I could not fully verify from the available index whether an external, unprivileged caller can deterministically force this specific limiter call to error (e.g., via settings-store failures, concurrent misconfiguration, or resource exhaustion elsewhere in the process). Given the index size limits, the full implementation of `limits.MakeUpperBoundLimiter` / `BoundLimiter.Limit` was not available to inspect for externally-triggerable error conditions — this should be verified in a full checkout. Absent that trigger being externally controllable at will, likelihood is moderate at best; if the limiter can error under contention/backpressure (a state an attacker can help induce by connecting many nodes concurrently), likelihood increases correspondingly.

### Recommendation
In `handleRequest`, close `conn` and call `s.acceptor.AbortHandshake(attemptID)` in the `MaxRequestBytesLimiter.Limit` error branch, matching the cleanup pattern used in the surrounding branches:
```go
maxRequestBytes, err := s.config.MaxRequestBytesLimiter.Limit(r.Context())
if err != nil {
    s.lggr.Errorw("failed to get request size limit", "err", err)
    conn.Close()
    s.acceptor.AbortHandshake(attemptID)
    return
}
```
More generally, consider deferring `conn.Close()` and `s.acceptor.AbortHandshake(attemptID)` immediately after a successful `Upgrade`, using a "success" flag to skip cleanup only once `FinalizeHandshake` succeeds, so future added branches can't reintroduce this class of leak.

### Proof of Concept
1. An unprivileged client sends a request to the gateway's node WebSocket endpoint with a syntactically valid, correctly-signed auth header (so `StartHandshake` succeeds and an attempt is recorded in `connAttempts`).
2. The request is upgraded to a WebSocket connection by `s.upgrader.Upgrade`.
3. If/when `s.config.MaxRequestBytesLimiter.Limit(r.Context())` returns an error (e.g., under limiter contention or an internal error condition), `handleRequest` returns without closing `conn` or calling `AbortHandshake`.
4. Repeating steps 1–3 accumulates leaked WebSocket connections and stale `connAttempt` entries in `connectionManager.connAttempts`, growing gateway memory/FD usage unboundedly over time.

Note: I was unable to fully confirm, from the indexed code alone, the exact external conditions under which `MaxRequestBytesLimiter.Limit` errors in production; this should be validated against the full `chainlink-common/pkg/settings/limits` implementation in a complete checkout to establish precise reproduction steps.

func (m *connectionManager) newAttempt(nodeSt *nodeState, nodeAddress string, timestamp uint32) (string, []byte, error) {
	challengeBytes := make([]byte, m.config.AuthChallengeLen)
	_, err := rand.Read(challengeBytes)
	if err != nil {
		return "", nil, err
	}
	challenge := network.ChallengeElems{Timestamp: timestamp, GatewayID: m.config.AuthGatewayID, ChallengeBytes: challengeBytes}
	m.connAttemptsMu.Lock()
	defer m.connAttemptsMu.Unlock()
	m.connAttemptCounter++
	newID := fmt.Sprintf("%s_%d", nodeAddress, m.connAttemptCounter)
	m.connAttempts[newID] = &connAttempt{nodeState: nodeSt, nodeAddress: nodeAddress, challenge: challenge, timestamp: timestamp}
	return newID, network.PackChallenge(&challenge), nil
}
```

func (c *HTTPServerConfig) ensureLimiters(lf limits.Factory) (err error) {
