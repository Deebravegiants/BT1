### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing via payload replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop` field that identifies which tenant the event belongs to is taken from an unauthenticated header and is never bound into the signed content. This is the same class of bug the external report describes: a field that is acted upon (the tenant identity) is not covered by the cryptographic check (the accept/reject constraint), creating a gap between "what was verified" and "what was trusted."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it with the `hmac-sha256` header: [2](#0-1) 

`Registry.process` uses this check as the sole authentication gate, and then unconditionally trusts `request.shop` (from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed bytes) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

The identity-binding equality that should hold is:
`bytes_verified_by_hmac == bytes_that_determine_the_tenant (shop)`

In this implementation that equality does not hold — `bytes_verified_by_hmac = raw_body` while `tenant_identity = header["shop-domain"]`, which is disjoint from the signed bytes. Consequently, a valid HMAC only proves the body was produced with the app's secret; it proves nothing about which shop the header claims the body belongs to.

### Impact Explanation
An unprivileged internet user can install the target app on their own free/development store (a normal, unprivileged action requiring no special access) and thereby legitimately receive real webhooks — valid `raw_body` + valid `hmac-sha256` + `shop-domain: attacker-shop.myshopify.com`. Because the signature covers only the body, the attacker can replay that exact `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint while substituting `shop-domain` with a victim merchant's domain. `HmacValidator.validate` still succeeds (it only checks the body against the secret), so `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`. Any app that follows the gem's own documented usage — using `data.shop` to select the tenant/session/database row to act on, exactly as shown in `docs/usage/webhooks.md` (`shop_domain: data.shop`) — will process attacker-supplied data under the victim's tenant identity. This is a cross-tenant identity confusion rooted entirely in this gem's verification method, not a misuse of an undocumented API.

### Likelihood Explanation
Likelihood is moderate-to-high: the only prerequisite is the ability to install the target app on any shop (including a free/dev store the attacker controls) to obtain one genuine, signed webhook body, and the ability to send an HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header — both trivially available to an unprivileged internet user with no access to `api_secret_key` or any merchant's access token.

### Recommendation
Bind the tenant identity into the authenticated material: include the `shop-domain` (and ideally `topic`/`webhook-id`) in the signable string used for HMAC verification, or otherwise cryptographically bind the header value to the signature before trusting `request.shop` in `WebhookMetadata`. At minimum, document and enforce that `data.shop` must be cross-checked against a known, previously-provisioned shop/session before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Attacker triggers an event (e.g., `orders/create`) on their own store, capturing the genuine webhook POST: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the app's secret), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the request to the app's public webhook endpoint, keeping body `B` and header `H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (checking only `B` against `H`) returns `true`; `Registry.process` invokes the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`.
5. The app performs tenant-scoped actions (per the gem's documented handler pattern) using attacker-controlled body content attributed to the victim shop — a cross-tenant confusion originating from `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/utils/hmac_validator.rb`.
