Audit Report

## Title
LDAP Bind DN Injection via Insufficiently Escaped User-Supplied Email in Authentication Flow - (File: core/sessions/ldapauth/ldap.go)

## Summary
`CreateSession` and `TestPassword` in `core/sessions/ldapauth/ldap.go` build the LDAP bind DN by applying `ldap.EscapeFilter` (a search-filter escaper) to the user-supplied email before embedding it directly into a DN string with `fmt.Sprintf("%s=%s,%s,%s", ...)`. Since `EscapeFilter` only escapes filter metacharacters (`*`, `(`, `)`, `\`, NUL) and not DN-reserved characters (`,`, `+`, `"`, `<`, `>`, `;`, leading `#`/space), an unauthenticated caller of `POST /sessions` can inject additional RDN components into the DN string sent to `conn.Bind`.

## Finding Description
The public, unauthenticated endpoint handled by `sessions_controller.go` parses `{Email, Password}` and forwards it to `AuthenticationProvider().CreateSession` [1](#0-0) . In the LDAP authenticator, `CreateSession` builds the bind DN via `escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))` followed by `searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())`, which is passed straight into `conn.Bind(searchBaseDN, sr.Password)` [2](#0-1) . `TestPassword` repeats the identical unsafe pattern [3](#0-2) . By contrast, the same `escapedEmail` produced by `EscapeFilter` is correctly used in filter-context queries in `FindUser`, e.g. `filterQuery := fmt.Sprintf("(&(uniquemember=%s=%s,%s,%s))", ...)` [4](#0-3) , confirming the escaping mechanism was designed for filter syntax, not DN syntax. No DN-specific escaping, format validation, or email-shape validation exists anywhere in this path before the DN is constructed and used in `conn.Bind`.

## Impact Explanation
This is a real, verified misuse-of-escaping-function bug: DN metacharacters (comma, plus, semicolon, quotes) supplied in the `email` field of an anonymous `POST /sessions` request pass through unescaped into the LDAP bind DN, altering its intended RDN structure. This is a legitimate defense-in-depth/injection-class flaw in an unauthenticated-reachable, authentication-critical code path, and constitutes a broken security assumption (that the email is safely embedded in the DN). However, converting this into a concrete authentication bypass is not fully demonstrated: because `conn.Bind` is a credential check (not a search), successfully authenticating still requires the attacker to supply a password that matches whatever entry the manipulated DN happens to resolve to on the upstream server — which depends on the target LDAP server's schema/parsing behavior and directory layout, factors outside the attacker's control and not proven in the PoC. The report itself acknowledges this uncertainty ("depending on the upstream LDAP server's schema and how permissively it parses malformed/injected DNs").

## Likelihood Explanation
Triggering the malformed-DN construction requires no privileges — only a crafted `email` field in an anonymous login POST — and is present unconditionally whenever `WebServer.AuthenticationMethod = 'ldap'` is configured. This is a low bar for the injection primitive itself. Achieving concrete unauthorized session/role grant on top of it is speculative and server-dependent, which lowers overall exploit likelihood but does not eliminate the underlying code defect.

## Recommendation
Replace `ldap.EscapeFilter` with a proper RFC 4514 DN-escaping routine (escaping `,+"\<>;` and leading `#`/space) for the `escapedEmail`/username value used in `conn.Bind(searchBaseDN, ...)` in both `CreateSession` and `TestPassword`. Reserve `ldap.EscapeFilter` exclusively for values embedded in LDAP search filters (as already done correctly in `FindUser`/`validateUsersActive`). Additionally, validate/normalize the email format before using it in any LDAP protocol string, and reject values containing DN-reserved characters outright.

## Proof of Concept
1. Configure a node with `WebServer.AuthenticationMethod = 'ldap'` and valid `WebServer.LDAP` settings.
2. Send `POST /sessions` with `{"email": "user,ou=Admins,dc=example,dc=com", "password": "<value>"}`.
3. Observe that `core/sessions/ldapauth/ldap.go:407` produces `searchBaseDN = "uid=user,ou=Admins,dc=example,dc=com,ou=users,dc=custom,dc=example,dc=com"`, confirming the comma is not escaped and the DN structure is altered — demonstrating the injection primitive at the code level. A full bind-bypass PoC against a real/test LDAP server (e.g., OpenLDAP test fixture) would be needed to confirm whether any given directory layout allows this to resolve to an authenticatable alternate entry.
