### Title
Untrusted swap routes can inject caller-authorized token transfers - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept opaque route bytes and execute them through the configured router while the caller’s root authorization is active. [1](#0-0)  A malicious route can name a venue contract that additionally calls `token.transfer(victim, attacker, amount)`; Soroban records that request under the victim’s controller authorization tree, and it executes if the victim signs the simulated tree. [2](#0-1) 

### Finding Description
`process_swap_collateral` authenticates `caller` and verifies account ownership before withdrawing collateral. [3](#0-2)  The withdrawn amount is passed together with the caller-controlled `swap` bytes into `swap_tokens_or_passthrough`. [4](#0-3) 

`swap_tokens` treats those bytes as opaque router input: it checks only that the bytes are nonempty, snapshots input and output balances, authorizes one exact controller-to-router input transfer, and invokes `router.execute_strategy`. [5](#0-4)  The controller’s explicit invoker authorization is narrow, but it does not prevent route-selected downstream code from making an unrelated call that requires the original caller’s authorization. [6](#0-5) 

After the router returns, the controller only bounds the controller’s input spend and requires positive output; neither check detects an unrelated transfer from the caller’s wallet that was authorized elsewhere in the caller’s signed invocation tree. [7](#0-6)  The resulting output is redeposited and the account can pass all final risk checks, so the malicious transfer does not need to revert the lending operation. [8](#0-7) 

### Impact Explanation
A victim who signs a transaction containing a malicious route can lose unrelated wallet tokens not involved in the lending strategy. The attacker can make the route still spend the intended controller input and return enough output for the strategy to satisfy measured-output and solvency checks, while the injected nested `transfer` moves the victim’s separate token balance to the attacker. [9](#0-8)  This is theft of user funds and can cover the victim’s full balance of any token whose transfer is included in the signed authorization tree. [2](#0-1) 

### Likelihood Explanation
The attack requires the victim to submit a malicious route and sign the resulting authorization tree. That is realistic when route bytes are produced by an untrusted quote source, frontend, or strategy service: the route is opaque at the controller boundary, and the extra child authorization may not be obvious to a signer. [1](#0-0)  No protocol privilege, leaked key, account delegation, or control of the victim’s lending account is required; the attacker only needs the victim to execute the supplied strategy route. [3](#0-2) 

### Recommendation
Do not allow route-selected downstream contracts to run under the caller’s open-ended root authorization. Restrict executable venue/pool addresses to a governance-approved allowlist, or otherwise decode and validate the complete route before execution so every contract that can request caller authorization is known and trusted. [10](#0-9)  Clients should additionally reject any simulated authorization tree containing child calls beyond the expected token pull, but relying on wallet inspection leaves the protocol acceptance path unchanged. [11](#0-10) 

### Proof of Concept
1. The victim owns a lending account with collateral `current` and holds an unrelated wallet token `W`.
2. The attacker supplies route bytes for `swap_collateral(victim, account_id, current, amount, new, swap)` whose first hop names an attacker-controlled contract implementing the expected venue call. [12](#0-11) 
3. The victim authorizes `caller.require_auth()` for `swap_collateral`. The malicious venue accepts/spends the router input in the expected ABI shape, returns enough `new` tokens for a positive output, and additionally invokes `W.transfer(victim, attacker, victim_balance)`. [13](#0-12) 
4. Transaction simulation attaches the wallet-token transfer as a child of the victim’s `swap_collateral` authorization rather than the controller’s narrow router grant. If the victim signs that tree, the transfer executes. [2](#0-1) 
5. The controller redeposits the swap output and finishes successfully because its post-router checks only measure controller input/output and account risk; they do not enumerate or reject unrelated caller-authorized transfers. [7](#0-6)

pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
