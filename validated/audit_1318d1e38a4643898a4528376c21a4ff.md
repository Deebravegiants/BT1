### Title
`Webhooks::Request#topic`/`#shop` read unsigned headers while `to_signable_string` only covers the raw body, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` authenticates nothing but the JSON body. `Request#topic` and `Request#shop` are populated from `shopify-topic`/`x-shopify-topic` and `shopify-shop-domain`/`x-shopify-shop-domain` headers that are never included in the signed material, and `Registry.process` hands `request.shop`/`request.topic` straight to the app's webhook handler once the body-only HMAC passes. Additionally, the header-normalisation step `k.to_s.downcase.sub("http_", "").gsub("_", "-")` performs only a single, first-occurrence substitution, so a client-supplied header literally named `Http_Shopify-Topic` normalises to the same key (`shopify-topic`) as a genuine `Shopify-Topic` header, letting whichever header appears last in the hash silently overwrite the other with no bearing on the HMAC at all.

### Finding Description
The claimed binding is:
`OpenSSL.secure_compare(computed_signature, received_signature)` being true `⇒` `request.shop == <the shop that actually produced this body>` and `request.topic == <the topic that actually produced this body>`.

Tracing the code:
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and only compares against `verifiable_query.hmac` [1](#0-0) .
- `Request#to_signable_string` returns `@raw_body` exclusively — no header is folded into the signable string [2](#0-1) .
- `Request#topic` and `Request#shop` are read straight from `@headers` via `shopify_header`, which is populated in `initialize` from the raw, attacker-influenced headers hash with a lossy normalisation: `headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }` [3](#0-2) [4](#0-3) [5](#0-4) .
- `Registry.process` gates only on `HmacValidator.validate(request)`, then immediately trusts `request.topic` to select a handler and passes `request.shop` unmodified into `WebhookMetadata` for the handler to act on [6](#0-5) .

Because Shopify's webhook `api_secret_key`/`client_secret` is shared across every shop that installs a given app (it is not per-shop), an attacker who installs the app on their own development shop legitimately receives a `(raw_body, X-Shopify-Hmac-Sha256)` pair that is valid under that shared secret. Nothing in this gem binds `shop-domain` or `topic` to that pair. The attacker can replay the exact same body and HMAC to the victim app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value naming a different, victim merchant, and/or an arbitrary topic header. `HmacValidator.validate` still returns `true` because it only re-hashes `@raw_body`, so `Registry.process` accepts the forged attribution and dispatches the handler with `shop: <attacker-chosen value>` — a value never covered by "SIGNATURE COVERAGE." No other guard intervenes: `ShopValidator.sanitize!`, `state` comparisons, and JWT `aud`/`iss` checks are part of the OAuth/session-token path, not the webhook path, and are not invoked by `Registry.process`.

Separately, the `sub("http_", "")` normalisation only strips the first occurrence of the literal substring `http_`, so a header literally named `http_shopify-topic` (or `Http_Shopify-Topic`) normalises to the same hash key, `shopify-topic`, as the real `Shopify-Topic` header. Since `headers.to_h` on a plain Ruby hash keeps only the last-inserted value for a duplicate key, whichever variant is later in the input hash's iteration order silently wins for `Request#topic` — with zero effect on the HMAC either way, because (as above) headers are never part of `to_signable_string`. Whether an attacker can literally control key ordering into this collision depends on how the host framework builds the `headers:` hash before calling `Request.new` (e.g., whether it is Rack `env`-prefixed or a raw header map); this part of the exploit is framework-dependent and not solely determined by this gem's code. The `shop`/`topic` unsigned-metadata problem, by contrast, is unconditionally true and fully reproducible from this gem alone.

### Impact Explanation
Any party that can obtain one valid `(body, hmac)` pair — trivially available to any attacker who installs the app on their own shop, per the threat model — can replay it against the victim app's webhook endpoint with a forged `shop-domain` header, causing the receiving app to execute its webhook handler believing the payload originated from an arbitrary victim shop. This is a cross-tenant confusion / authentication-bypass primitive at the metadata level: the *body's* authenticity is genuinely Shopify's, but *which shop and which topic it is attributed to* is entirely attacker-controlled. The severity depends on how much the downstream app trusts `WebhookMetadata#shop`/`#topic` (e.g., for data deletion routing, entitlement changes, or triggering shop-specific side effects) — for apps that key any state mutation off `request.shop` without independently re-verifying shop identity, this is repeatable against arbitrary victim shop domains, matching the Critical "authentication bypass / cross-tenant access" class.

### Likelihood Explanation
Preconditions: the attacker must control (or install the app on) at least one real shop to legitimately receive one valid signed webhook — explicitly permitted by the threat model. No `api_secret_key`, access token, or credential leak is required. The attacker needs network access to POST to the victim app's public webhook endpoint, which is inherently internet-reachable. Cost is a single legitimate webhook capture plus a scripted replay with a modified header; this is fully repeatable against any shop domain string.

### Recommendation
Do not treat `shop-domain`/`topic` header values as authenticated. At minimum, cross-check `request.shop` against the shop recorded for the session/access-token that installed the app (i.e., validate that the shop asserted in the header actually corresponds to a shop with an active, previously-established installation/session), and consider including the shop domain and topic as part of the signed material or validating them out-of-band (e.g., via a signed query parameter delivered at registration time) rather than trusting the plain header. Additionally, fix the header normalisation in `Request#initialize` to strip only a legitimate `HTTP_`-prefix pattern anchored at the start (e.g., `sub(/\Ahttp[_-]/, "")`) and reject/collapse duplicate normalised keys defensively (raise instead of silently letting the last one win).

### Proof of Concept
```ruby
# test/webhooks/request_shop_forgery_test.rb
require "test_helper"

class RequestShopForgeryTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", api_version: "2023-01",
      is_private: false, is_embedded: false, host_name: "app.com",
      scope: [], user_agent_prefix: nil
    )
    @raw_body = '{"id":1}'
    digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", @raw_body)
    @hmac_b64 = Base64.strict_encode64(digest)
  end

  def build_request(shop_domain)
    ShopifyAPI::Webhooks::Request.new(
      raw_body: @raw_body,
      headers: {
        "X-Shopify-Topic" => "orders/create",
        "X-Shopify-Hmac-Sha256" => @hmac_b64,
        "X-Shopify-Shop-Domain" => shop_domain,
      }
    )
  end

  def test_same_signature_validates_for_two_different_shops
    req_a = build_request("victim-a.myshopify.com")
    req_b = build_request("victim-b.myshopify.com")

    assert ShopifyAPI::Utils::HmacValidator.validate(req_a)
    assert ShopifyAPI::Utils::HmacValidator.validate(req_b)

    # SIGNATURE COVERAGE violated: same hmac/body validates for two distinct shop claims
    refute_equal req_a.shop, req_b.shop
  end
end
```
Assertion under test: both `req_a` and `req_b` share identical `raw_body` and `hmac`, both pass `HmacValidator.validate`, yet `req_a.shop != req_b.shop` — proving `shop` (and equivalently `topic`) is not bound by `to_signable_string`/the HMAC check that `Registry.process` relies on.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
