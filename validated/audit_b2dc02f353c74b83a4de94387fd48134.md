### Title
Missing length validation on `message.from` before slice/copy panics in `hyper-fungible-token::on_accept` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The ImageMagick CVE is a heap overflow caused by trusting an attacker-controlled length/size field without validating it against the actual buffer before writing/reading. The same bug class — an attacker-influenced length feeding directly into a fixed-size buffer operation without a bounds check — exists in the `hyper-fungible-token` pallet's ISMP module callback, where `message.from` (a variable-length field decoded from the cross-chain message body) is sliced and copied into fixed-size buffers without checking its length first.

### Finding Description
`Pallet::on_accept` decodes the incoming `PostRequest.body` into a `Message` via ABI decoding, then — only in the optional-calldata / no-signature branch — derives the dispatch origin from `message.from` without any length check, unlike the parallel `to_bytes` handling a few lines above which explicitly validates for 32 or 20 bytes: [1](#0-0) 

```rust
let mut beneficiary_bytes = [0u8; 32];
let to_bytes = message.to.as_ref();
if to_bytes.len() == 32 {
    beneficiary_bytes.copy_from_slice(to_bytes);
} else if to_bytes.len() == 20 {
    beneficiary_bytes[12..].copy_from_slice(to_bytes);
} else {
    Err(HftError::InvalidRecipientLength(to_bytes.len()))?;
}
```

But later, in the signature-less origin-derivation branch: [2](#0-1) 

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

Neither arm validates `from_bytes.len()` before use:
- If `source.is_evm()` and `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows `usize`, which either panics directly (overflow-checked arithmetic) or produces a huge slice-range that panics on the out-of-bounds `&from_bytes[..]` index.
- In the non-EVM arm, `account.copy_from_slice(from_bytes)` panics unless `from_bytes.len()` is exactly 32 — `copy_from_slice` traps on any length mismatch (this is exactly the same class of bug the codebase's own regression tests call out elsewhere, e.g. the `as_utf8_string` fix and the `consensus_state_id` fix, both of which explicitly document that "the string/bytes must be exactly N bytes... this runs on untrusted input, so it must never panic").

This is executed only when the request carries non-empty `message.data` and no `substrate_data.signature`, i.e. it is on the reachable path for any cross-chain HFT transfer message that also carries calldata to run on the destination chain.

### Impact Explanation
A malformed/short `message.from` field triggers a Rust panic inside `on_accept`, which runs as part of `pallet_ismp`'s message-dispatch execution during block processing (reached via `handle_unsigned`/`handle` when delivering a `PostRequest` to this module). An unhandled panic inside a pallet's `on_accept` during on-chain execution traps block execution rather than gracefully failing the extrinsic, which can halt processing of the block/route for this module — a denial-of-service against message delivery for the `hyper-fungible-token` bridge, matching the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Exploitability depends on whether the length of `message.from` in the ABI-encoded `Message` body can be influenced to be `< 20` bytes (EVM path) or `!= 32` bytes (non-EVM path) by whoever can cause the trusted source-chain bridge contract to emit/construct such a message with attacher-influenced calldata present and no signature — this requires the EVM-side dispatcher contract (out of the Rust-only repo I can inspect) to allow a user-controlled `from` encoding of non-canonical length. I could not verify this contract-side constraint within the available context, so likelihood is uncertain pending confirmation of the corresponding Solidity dispatcher's encoding rules for `from`. If the source contract permits arbitrary `from` bytes-length (or if it is user-suppliable at all in the send-message path), likelihood is High; if `from` is always hard-set to a fixed 20-byte `msg.sender` on the EVM side, exploitability is null. This uncertainty should be resolved by inspecting the EVM contract's `Message`-construction / dispatch function before treating this as confirmed exploitable.

### Recommendation
Mirror the `to_bytes` validation pattern already present a few lines above: explicitly check `from_bytes.len()` against the expected 20 (EVM) or 32 (Substrate) before slicing or copying, and return a typed `HftError` (e.g. `InvalidSenderLength`) instead of allowing `copy_from_slice`/slice-indexing to panic.

### Proof of Concept
Not independently verified as exploitable end-to-end in this pass because the upstream constraint (whether the EVM dispatcher contract can be made to emit a `message.from` of non-canonical length) lives outside the Rust modules I was able to inspect in this session. The concrete, demonstrable defect is the missing length check itself:
1. Construct a cross-chain `PostRequest` whose ABI-decoded `body` yields a `Message` with `data` non-empty, no `signature`, and `from` shorter than 20 bytes (if `source.is_evm()`) or not exactly 32 bytes (otherwise).
2. Deliver it through the normal ISMP request-handling path to `hyper-fungible-token::on_accept`.
3. Execution panics at `from_bytes[from_bytes.len() - 20..]` (underflow/out-of-range slice) or at `account.copy_from_slice(from_bytes)` (length mismatch), instead of returning a typed error.
