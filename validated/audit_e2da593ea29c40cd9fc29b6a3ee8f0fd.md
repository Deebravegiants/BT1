## Title
SSRF Leaking `client_secret` via Unvalidated `shop` in OAuth Token Exchange - ([File: lib/shopify_api/auth/token_exchange.rb])

## Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the access-token POST request (which carries the app's `client_secret`) from the `dest` claim of a session token, without validating that this value is a legitimate `*.myshopify.com`/Shopify Plus/Shopify-domain host — unlike the sibling `ClientCredentials.client_credentials` flow, which explicitly sanitizes the `shop` value before use.

## Finding Description
In `lib/shopify_api/auth/client_credentials.rb`, the `shop` value supplied to build the request host is passed through `Utils::ShopValidator.sanitize!(shop)` before being used to construct the `Session` and, subsequently, the request host in `Clients::HttpClient` [1](#0-0) .

In contrast, `lib/shopify_api/auth/token_exchange.rb`'s `exchange_token` takes the shop directly from the JWT `dest` claim (`jwt_payload.shop`) with no equivalent sanitization/validation step, and uses it to build a `Session` that is fed straight into `Clients::HttpClient`: [2](#0-1) 

`Clients::HttpClient#initialize` builds the outbound request host directly from `session.shop` (`@base_uri = "https://#{api_host || session.shop}"`), and this exact host receives a POST request whose body includes `client_secret: ShopifyAPI::Context.api_secret_key` [3](#0-2) [4](#0-3) .

`JwtPayload` only verifies the JWT's HMAC signature (against `Context.api_secret_key`) and checks `aud == Context.api_key` and expiry/nbf; it performs no validation that `dest` (used to derive `shop`) is a well-formed Shopify shop domain [5](#0-4) .

The binding this breaks: **the host that receives the app's `client_secret`** should equal **a genuine, validated Shopify shop domain**, but the code instead trusts **whatever string is present in the token's `dest` claim, unsanitized**, as long as the signature verifies. Since the `dest`/`iss` claims are attacker-influenced content within a token that is otherwise validly signed by Shopify's session-token issuance for the app (the token is generated by Shopify's Admin/App Bridge context, but the gem does not independently constrain the domain format), any deviation between what the gem accepts as `dest` and what `ShopValidator.sanitize!` would accept for `client_credentials` represents an inconsistent trust boundary within the same codebase for the same class of request (both POST to `/admin/oauth/access_token` with `client_secret` in the body).

## Impact Explanation
If `dest` is not constrained to a `myshopify.com`-style domain, and any code path allows an untrusted or malformed value into that claim to reach `TokenExchange.exchange_token`, the gem will make a same-body POST request containing the app's `client_secret` to an arbitrary host derived from that value — Critical, per the report's classification of SSRF that carries the app's credentials.

## Likelihood Explanation
Exploitability depends entirely on whether the `dest` claim's format is enforced anywhere upstream (e.g., by Shopify's own token issuance, which is outside this gem). Within the scope of this gem alone, `JwtPayload` does not perform this validation, and this is inconsistent with `ClientCredentials`, which explicitly sanitizes `shop` before doing the identical `client_secret`-bearing request. I could not fully confirm from the available files whether Shopify-issued session tokens can ever contain a non-myshopify `dest` value in practice, or whether the deployment environment (App Bridge / iframe context) inherently constrains this. This uncertainty means the finding is a plausible internal inconsistency/defense-in-depth gap rather than a demonstrated end-to-end exploit purely from unauthenticated internet input.

## Recommendation
Apply `Utils::ShopValidator.sanitize!` (or equivalent host-format validation) to `jwt_payload.shop` / `dest_shop` in `TokenExchange.exchange_token` before constructing the `Session` and issuing the `client_secret`-bearing request, mirroring the validation already performed in `ClientCredentials.client_credentials`.

## Proof of Concept
Not independently reproducible from the code alone without confirming whether a caller can supply a `dest` claim value that bypasses Shopify's own domain constraints; the structural gap (`ClientCredentials` sanitizes, `TokenExchange` does not, both send `client_secret` to a `shop`-derived host) is shown by the cited code paths above.
