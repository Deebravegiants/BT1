### Title
Webhook `shop-domain` (and `topic`) headers are trusted by the handler dispatch but are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` and `topic` are read directly from HTTP headers that are never part of the signed data. `Registry.process` validates the HMAC over the body only, then trusts the unauthenticated `shop` and `topic` header values to build the `WebhookMetadata` passed to the host application's handler. This breaks the identity binding `shop authenticated == shop the handler acts on`.

### Finding Description
`Utils::HmacValidator.validate` verifies the HMAC by comparing it against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just `@raw_body`, while `shop` and `topic` come from `shopify_header(...)`, which reads directly from caller-supplied HTTP headers, entirely outside the signed payload: [2](#0-1) 

`Registry.process` performs HMAC validation, then immediately builds `WebhookMetadata` using `request.shop` and `request.topic` — both unauthenticated — and dispatches it to the registered handler: [3](#0-2) 

`WebhookMetadata#shop` is a plain `String` field with no further verification, and the interface contract (`WebhookHandler#handle`) gives no indication to implementers that `shop`/`topic` are unauthenticated, so host apps built against this gem's documented API will treat them as trustworthy: [4](#0-3) 

Because the HMAC only binds the raw body, any party who possesses one valid `(raw_body, hmac)` pair signed with the app's real secret (e.g. from a legitimate webhook delivered to a shop that installed the app, including a free/dev store the attacker controls) can resubmit that exact body to the app's webhook endpoint while substituting arbitrary `x-shopify-shop-domain` and `x-shopify-topic` header values. `Registry.process` will accept it as valid (the HMAC check only verifies the body was signed by Shopify with the app's secret, not which shop or topic it belongs to) and will invoke the handler believing the event originated from the victim shop/topic.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce for multi-tenant Shopify apps: an attacker who is a legitimate, unprivileged user of the app on their own store can make the host application believe an event (including mandatory compliance webhooks such as `customers/redact`, `customers/data_request`, `shop/redact`) came from a different merchant's shop. Any handler logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop records, triggering data deletion/export, revoking access) can be triggered against a shop the attacker does not control, which is a cross-tenant access/impact issue matching the report's core pattern of an identity-binding value ("field acted on") not being covered by the authenticity check.

### Likelihood Explanation
Requires only that the attacker be a legitimate merchant/installer of the target app (unprivileged internet user relative to other tenants) capable of triggering at least one webhook delivery to themselves, then replaying that exact body to the app's public webhook endpoint with forged headers. No access to the app's `client_secret`, other merchants' tokens, or TLS interception is needed — only observation of one's own genuinely-delivered webhook.

### Recommendation
Include `shop` (and ideally `topic`, `api_version`, `webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind the shop domain to the payload before dispatch, so `Registry.process` cannot be fooled into associating a validly-signed body with an unauthenticated shop identifier.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets it send any real webhook (e.g. `orders/create`), capturing the raw body `B` and the corresponding `x-shopify-hmac-sha256` header value `H` (a valid signature computed by Shopify using the app's `client_secret`).
2. Attacker POSTs to the app's public webhook endpoint with:
   - body = `B`
   - `x-shopify-hmac-sha256` = `H`
   - `x-shopify-shop-domain` = `victim-shop.myshopify.com`
   - `x-shopify-topic` = `customers/redact` (or any topic the attacker wants dispatched)
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers since only their presence is checked, not their authenticity: [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (= `B`) and finds it matches `H`, so validation passes: [6](#0-5)  even though `shop`/`topic` were forged.
5. `Registry.process` dispatches `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", ...)` to the app's registered handler, which will act as though `victim-shop.myshopify.com` issued the request.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
