### Title
Missing bounds check on the LP-rebalance ratio math permanently bricks `finalizeGraduation` when an attacker pre-seeds the HyperSwap V2 pair - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._noFeeSwapInput` (called from `_pairRebalance` → `_seedRebalancing` → `_seedUniswapV2Direct` → `finalizeGraduation`) computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` with no upper-bound check on the inputs before the division. `reserveIn`/`reserveOut` are the live HyperSwap V2 pair reserves, which an unprivileged actor fully controls by pre-creating and pre-seeding (`pair.mint`) the TOKEN/LT pair before the token graduates. `targetD` is `tokensForLP` (or `ltFromPair`), a value the bonding curve can legitimately drive arbitrarily close to zero on a full-sellout graduation. Combining attacker-chosen large reserves with a naturally tiny `targetD` pushes the `mulDiv` result past `type(uint256).max`, which reverts. Because `finalizeGraduation` has no fallback for that revert, phase 2 can never complete for that token, and the curve-raised LT plus the reserved 250M tokens stay permanently parked in `Bonding`.

### Finding Description
`_noFeeSwapInput` is documented as relying on an un-enforced invariant: [1](#0-0) 

The natspec explicitly acknowledges the failure mode but treats it as acceptable ("Constructed adversarial inputs that violate this would revert rather than silently truncate, which is the correct failure mode") — this is the same class of bug as CVE-2018-18309: a computation is performed without first bounding/validating its inputs, and the missing check surfaces as an unhandled crash on the very inputs an external actor controls.

`reserveIn`/`reserveOut` come straight from the HyperSwap V2 pair's live reserves in `_seedRebalancing`: [2](#0-1) 

Any unprivileged address can create and seed this pair ahead of graduation — the scope explicitly allows "pre-creating or pre-seeding the HyperSwap V2 TOKEN/LT pair before graduation." An attacker who accumulates curve-sold tokens (via ordinary buys) and pairs them with self-supplied LT via `pair.mint` sets `reserveToken`/`reserveLT` to whatever they can fund. Meanwhile `targetD` (`tokensForLP`) is derived purely from curve state in `_prepareGraduationLiquidity`: [3](#0-2) 

`tokensForLP = ltFromPair * tokenReserve / assetReserve`, a parabola in `sold` that tends to `0` as the curve approaches full sellout (`sold → S`). A token that graduates via the supply trigger (`tokenBalance() == 0`) near full sellout therefore produces a genuinely tiny, non-attacker-controlled `tokensForLP`. Combining attacker-chosen large `reserveIn * reserveOut` with this naturally-tiny `targetD` pushes `Math.mulDiv`'s result above `type(uint256).max`, which reverts with `MathOverflowedMulDiv` — an unhandled revert that propagates all the way up through `_pairRebalance` → `_seedRebalancing` → `_seedUniswapV2Direct` → `finalizeGraduation`.

`finalizeGraduation` has no try/catch or alternate path around this call: [4](#0-3) 

so the token is stuck at `Lifecycle.Graduating` forever. `_prepareGraduationLiquidity` had already burned the unsold token balance and transferred the curve-raised LT out of the `Pair` into `Bonding` via `Router.graduate` at phase-1 time: [5](#0-4) 

so all of that real LT plus the 250M reserved tokens are permanently parked in `Bonding` with no code path capable of moving them — `LPLock.recordLock` (the "one-shot" call `finalizeGraduation` cannot skip) is unreachable, and every other state transition requires reaching that same revert-prone call.

### Impact Explanation
This is a permanent freeze of funds: once a token enters `Lifecycle.Graduating` and hits this revert, `finalizeGraduation` can never succeed for that token (the pair reserves, curve state, and `tokensForLP`/`ltFromPair` are all frozen inputs recomputed identically on every retry), and no admin or rescue function exists to unstick it. All LT raised by the curve for that token and the 250M-token LP reserve are trapped in `Bonding` indefinitely — this satisfies the "permanent freezing of trader, creator, or LP funds" bar.

### Likelihood Explanation
Reachability requires an unprivileged attacker to (a) accumulate a meaningful share of a token's curve supply and (b) self-fund an LT-side deposit to mint a HyperSwap V2 pair with reserves large enough that `reserveIn * reserveOut * targetN` overflows uint256 once `targetD` (`tokensForLP`) is driven near zero by a full-sellout graduation. Both actions are attacker-affordable relative to the size of the token's own curve (buying up to 75% of a freshly launched token's supply and pairing it with self-supplied LT), and the near-zero `tokensForLP` condition is not adversarial at all — it is the ordinary shape of the bonding curve's parabola near full sellout. This makes the attack economically bounded by the target token's market cap rather than requiring astronomical capital, and it can be set up entirely from public entry points before graduation fires. I could not fully pin down the exact minimum capital threshold without simulating BounceTech's LT total supply and uint112 pair-reserve limits, so the precise cost/likelihood boundary is uncertain, but the code path and root cause are concretely established.

### Recommendation
Bound the rebalance inputs defensively before the `mulDiv` call in `_noFeeSwapInput` — e.g., cap `reserveIn`/`reserveOut` (or the whole rebalance) at a sane multiple of `tokensForLP`/`ltFromPair` rather than trusting live, attacker-influenceable V2 reserves directly, and/or wrap the `_pairRebalance` call in `_seedRebalancing` with a fallback (mirroring the existing `expectedOut == 0` fallback) that falls back to `_seedDirectMint` whenever the ratio math would revert, so `finalizeGraduation` can never permanently brick regardless of how the attacker shapes the pre-seeded pair.

### Proof of Concept
1. Launch a token via `Zap.createToken`.
2. As an unprivileged attacker, buy a large share of the curve-sellable supply via `Zap.buy` (accumulating `TOKEN`).
3. Create the HyperSwap V2 `TOKEN/LT` pair (permissionless) and call `pair.mint(...)` after transferring a large, self-funded amount of `TOKEN` and `LT` into it, setting `reserveToken`/`reserveLT` to attacker-chosen large values.
4. Continue buying on the curve until the token sells out (`Pair.tokenBalance() == 0`), triggering `canGraduate` via the supply leg; this drives `tokensForLP` (the parabola `sold*(S-sold)/S`) toward a very small value while `ltFromPair` stays large.
5. `_enterGraduating` fires, caching the tiny `tokensForLP` in `pendingGraduation`.
6. Anyone calls `Bonding.finalizeGraduation(token)`. `_seedRebalancing` computes `reserveToken * ltFromPair` vs `reserveLT * tokensForLP` and enters `_pairRebalance`, which calls `_noFeeSwapInput(reserveIn, reserveOut, targetN, targetD, maxSwap)` with the attacker-set large `reserveIn*reserveOut` and the curve's tiny `targetD`; `Math.mulDiv` overflows `type(uint256).max` and reverts.
7. `finalizeGraduation` reverts on every subsequent call (all inputs are frozen), permanently trapping the curve-raised LT and the 250M-token LP reserve in `Bonding`.

    ///      `Math.mulDiv` keeps the intermediate product
    ///      `reserveIn * reserveOut * targetN` inside its 512-bit working
    ///      space, but the final result `... / targetD` must still fit in
    ///      uint256. Call sites must keep that invariant — in practice
    ///      both the V2 uint112 reserve cap and the bound that
    ///      `tokensForLP` ≤ `LP_RESERVE` and `ltFromPair` ≤ raised LT
    ///      are well inside the safe envelope. Constructed adversarial
    ///      inputs that violate this would `revert` rather than silently
    ///      truncate, which is the correct failure mode.
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
