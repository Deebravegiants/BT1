### Title
Minimal-Emporium proof path (`formInputEmporiumMin`) omits chain/contract-binding `signedMessageHash`, enabling cross-instance replay of `transact` calls - ([File: contracts/CircomDataBuilder.sol])

### Summary
`CircomDataBuilder.getHashedCalldata` never mixes in `chainId`/`verifyingContract`, and for the `HINKAL_EMPORIUM_ACTION_ID` + zero-token path, `formInputForCircom` dispatches to `formInputEmporiumMin`, whose public-input vector is only `[emporiumMessage, timeStamp, calldataHash]` — it never calls `getSignedMessageHash` at all, unlike `formInputNormal`/`formBasicInput`. This means the SNARK proof and every field it covers (`relay`, `externalActionData`, `hookData`, `feeStructure`, etc., all folded into `calldataHash`) carry zero binding to a specific chain or Hinkal/Emporium deployment for this code path, so the identical `(a,b,c,dimensions,circomData)` tuple can be replayed on another Hinkal instance B that shares the same `externalActionId → EmporiumUpgradeable` mapping.

### Finding Description
Broken equality: the question posits `getHashedCalldata(circomData)` (instance-agnostic) should not be treated as sufficient integrity proof without an accompanying chain/contract-bound value; only `getSignedMessageHash(chainId, verifyingContract, ...)` supplies that binding, and it is proven absent for the minimal-Emporium path.

Code path:
- `HinkalHelper.performHinkalChecks` (contracts/HinkalHelper.sol) recomputes `CircomDataBuilder.getHashedCalldata(circomData) == circomData.calldataHash` [1](#0-0) . `getHashedCalldata`/`getHashedCalldata1`/`getHashedCalldata2` hash only `circomData` fields — no `chainId`, no `hinkalAddress` [2](#0-1) . This check is therefore identical on instance A and instance B for the same `circomData`.
- `formInputForCircom` branches: if `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, it calls `formInputEmporiumMin`, which builds only `[emporiumMessage, timeStamp, calldataHash]` and never calls `getSignedMessageHash` [3](#0-2) . By contrast `formInputNormal`/`formBasicInput` explicitly injects `getSignedMessageHash(chainId, verifyingContract, circomData, emporiumMessage)` into the public inputs [4](#0-3) .
- The corresponding circuit `MainEVMCircuitMin` only constrains `message === Poseidon(messageSeed)` against public inputs `outTimeStamp` and `calldataHash` [5](#0-4)  — there is no signal anywhere in this circuit that encodes chain identity or the verifying contract.
- Inside `EmporiumUpgradeable.verifyWallet`, when `stack.signerAddress == address(0)` (the stateless "CASE 2" path used together with zero-token proofs), the function only checks/sets the per-contract `usedMessages[circomData.emporiumMessage]` mapping and returns — it performs **no** EIP-712 `_hashTypedDataV4` chain/contract-bound signature check in that branch [6](#0-5) . The EIP-712 domain separator (which is chain/contract bound) is only exercised in the `signerAddress != address(0)` branch [7](#0-6) .
- `usedMessages` is per-deployment storage, so a fresh Emporium deployment on instance B has never seen this `emporiumMessage` and will accept it again, re-executing `stack.ops` (arbitrary `op.endpoint.call{value: op.value}(op.callData)`) and `payRelayFees` [8](#0-7) .

Root cause: for the min-Emporium code path, neither the on-chain calldata-integrity hash, nor the circuit's public inputs, nor the Emporium's stateless-signer branch of `verifyWallet` bind the action to a specific chain/contract instance, whereas the normal path relies on `getSignedMessageHash`'s explicit `chainId`/`verifyingContract` mixing for that purpose. This confirms the question's core claim: `getHashedCalldata` equality alone is chain-agnostic, and `formInputEmporiumMin` is a real code path that omits `signedMessageHash` from the public input vector entirely.

Guards that do NOT stop this: `performHinkalChecks`'s hash check (chain-agnostic by design), `relayerIsValid`, `dimensionsCheck`, `checkOnchainCreation` (all pass since zero-token dimensions are self-consistent), and `insertNullifiers`/`rootHashExists` are vacuous for this path because `erc20TokenAddresses.length == 0` implies an empty `inputNullifiers` matrix (nothing to spend or double-spend) — the exploit does not need to reuse a UTXO nullifier at all, only to replay the Emporium action itself.

### Impact Explanation
On instance B, a replayed minimal-Emporium proof causes `EmporiumUpgradeable.runAction` to execute `stack.ops` (stateless calls to `op.endpoint` with `op.value`, drawn from that Emporium instance's own held funds) and `payRelayFees`, without the wallet/attacker having independently authorized that action on instance B. This is an action "a wallet owner or prover never authorised" being executed on a second deployment/chain via mere replay of unmodified proof+calldata, and it can also be used to re-trigger relay fee payment logic repeatedly across every instance sharing the `externalActionId` mapping. This matches at least **High** severity (unauthorized execution of calls/movement of protocol-held Emporium funds, repeatable per additional instance); depending on what `stack.ops` were crafted to do against instance B's held balances, this can escalate to **Critical** (theft of funds held by Emporium on instance B) since the ops are attacker-chosen calldata with no re-validation tied to instance B.

### Likelihood Explanation
Preconditions match realistic multi-chain deployment practice: Hinkal deploys the same `HinkalHelper`/`Hinkal`/`EmporiumUpgradeable` bytecode and registers the same `externalActionId` for `EmporiumUpgradeable` across chains (a documented deployment pattern for this protocol). The attacker only needs to be an unprivileged EOA capable of generating a proof for the min-Emporium circuit (`MainEVMCircuitMin`, only requiring knowledge of `messageSeed`), and crafting `stack.ops`/`circomData` with `stack.signerAddress == address(0)` to hit the branch of `verifyWallet` with no signature check. Cost is one proof generation; the same proof/calldata is then submitted verbatim to instance B's `Hinkal.transact`. Repeatability is bounded only by the number of Hinkal deployments sharing the `externalActionId` and by `usedMessages` being unset on each new target instance.

### Recommendation
Mix `chainId` and `verifyingContract` (i.e., `hinkalAddress`) into every code path that produces public inputs consumed by `verifyProof`, including `formInputEmporiumMin`. Concretely, always compute and include `getSignedMessageHash(chainId, verifyingContract, circomData, emporiumMessage)` as one of the public inputs regardless of the `HINKAL_EMPORIUM_ACTION_ID`/zero-token special case, and update `MainEVMCircuitMin` to add a `signedMessageHash` public input signal that is asserted equal to a circuit-internal recomputation (or otherwise constrained), mirroring `MainEVMCircuit`. Additionally, make `EmporiumUpgradeable.verifyWallet`'s `signerAddress == address(0)` branch also bind to chain/contract identity (e.g., require the caller to be `msg.sender == address(this)`'s own chain-scoped context, not merely check `usedMessages`), or remove that branch's ability to run arbitrary `stack.ops` without a chain-bound signature.

### Proof of Concept
Foundry test plan:
1. Call `CircomDataBuilder.formInputEmporiumMin` and `formInputNormal` (via a test harness exposing the internal functions) with an identical `CircomData` struct; assert `formInputEmporiumMin`'s returned array length/contents (`[emporiumMessage, timeStamp, calldataHash]`) contain no element equal to `getSignedMessageHash(chainId, verifyingContract, circomData, emporiumMessage)`, while `formInputNormal`'s array does contain it at its known index — confirming the "slot absence."
2. Deploy two independent Hinkal/HinkalHelper/EmporiumUpgradeable instance sets (A and B) on two separate `vm.chainId(...)` contexts, both registering `EmporiumUpgradeable` at the same `HINKAL_EMPORIUM_ACTION_ID`.
3. Generate one real snarkjs proof for `MainEVMCircuitMin` (`messageSeed`, `emporiumMessage=Poseidon(messageSeed)`, arbitrary `timeStamp`, `calldataHash` computed from a `circomData` with `erc20TokenAddresses.length == 0`, `stack.signerAddress == address(0)`, and `ops` pointing at a benign test target contract holding funds on both A and B).
4. Submit `(a,b,c,dimensions,circomData)` to instance A's `Hinkal.transact` — expect success and `stack.ops` executed, `usedMessages[emporiumMessage] == true` on A's Emporium.
5. Submit the identical unmodified tuple to instance B's `Hinkal.transact` — assert `verifyProof` succeeds again (since public inputs are unchanged) and `EmporiumUpgradeable.runAction` on B executes `stack.ops` a second time, proving cross-instance replay of an unauthorized action.

Note: I was unable to fully verify within tool budget whether `rootHashExists`/initial Merkle root values are identical by default across fresh Hinkal deployments (this affects only whether the same `rootHashHinkal`/index also passes on instance B) — this should be confirmed alongside the PoC, since for the zero-token min-Emporium path `inputNullifiers` is empty regardless, so root reuse does not require any real spend.

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
