### Title
Missing L2 sequencer-uptime check in `SimplexPaymaster` Chainlink oracle pricing - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments for ERC-4337 user operations using Chainlink `AggregatorV3Interface.latestRoundData()` feeds for both the native asset and each registered token, with only a staleness (`maxOracleAge`) and positivity check on the answer — there is no check that the underlying L2's sequencer is up, unlike the Chainlink-recommended L2 pattern (sequencer uptime feed + grace period).

### Finding Description
`_getOraclePrice` reads `latestRoundData()` and enforces only `answer > 0` and `block.timestamp - updatedAt <= maxOracleAge`: [1](#0-0) 

This price feeds directly into `_tokenPrice`, which is used both for validating/charging user operations (`_erc20Cost`/prefund path) and for the public `getTokenPrice`/`estimateTokenCost` views: [2](#0-1) 

Unlike Chainlink's L2 example, there is no `AggregatorV2V3Interface`-based sequencer uptime feed, no `answeredInRound`/`startedAt` check, and no grace-period gate anywhere in the contract or its config types — a repo-wide search for sequencer-uptime patterns (`SequencerUptimeFeed`, `isSequencerUp`, `GRACE_PERIOD`) returned no results. The `maxOracleAge` staleness check alone does not detect the scenario the original report describes: when an L2 sequencer goes down, `updatedAt` can remain "fresh" relative to `block.timestamp` (L2 block timestamps can lag or L1-anchored oracle updates can still appear within the staleness window) while the market price has actually moved, letting stale/pre-outage rates be treated as valid.

### Impact Explanation
`SimplexPaymaster` is intended for the same EVM chains Hyperbridge operates on, including L2s such as Arbitrum, Base, Optimism (per the mainnet chain list used elsewhere in this repo, e.g. the collator config listing Arbitrum/Base/Optimism/Unichain/Soneium). If deployed on an Arbitrum-class L2 and the sequencer goes down, any address submitting a UserOperation through the paymaster (an unprivileged action — no admin/governance role required) can have their ERC-20 gas cost computed from a stale/mispriced rate. Because `_tokenPrice` sets the exchange rate charged for gas in `getTokenPrice`/`estimateTokenCost` and the prefund/postOp accounting, a malicious actor could exploit favorable stale pricing during an outage to pay under-market token amounts for native-gas-equivalent value, draining value from the paymaster's treasury/markup economics. This is a fund-drain vector reachable from an ordinary user operation, not requiring any privileged role.

### Likelihood Explanation
Requires an actual L2 sequencer outage window, which is an infrequent but real, publicly observable event (as acknowledged by Sherlock's rule exception for restricted admin/sequencer network issues explicitly named in scope). During such a window, exploitation only requires submitting UserOperations through the paymaster while stale rates remain within `maxOracleAge` — no special privileges needed. Likelihood is Low-to-Medium (bounded by outage frequency) but Impact is direct fund loss, consistent with the Sherlock precedent that graded the analogous Notional issue as Medium.

### Recommendation
Follow the Chainlink L2 example: integrate a chain-specific sequencer uptime feed (e.g. `0xFdB631F5EE196F0ed6FAa767959853A9F217697D` on Arbitrum mainnet) and revert in `_getOraclePrice`/`_tokenPrice` if the sequencer is down or still within the recommended grace period after it comes back up, in addition to the existing staleness and positivity checks.

### Proof of Concept
1. Deploy `SimplexPaymaster` on Arbitrum with a registered token and its Chainlink `tokenOracle`.
2. Arbitrum sequencer goes offline; Chainlink price feeds on L1-anchored/L2 oracle stop updating in real time but their last `updatedAt` remains inside `maxOracleAge`.
3. Market price of the native asset or token moves materially off-chain during the outage.
4. Once transactions can again reach the mempool (or via an L1-Arbitrum retryable path during the outage), an actor submits a `PackedUserOperation` through the paymaster; `_tokenPrice` → `_getOraclePrice` returns the stale pre-outage rate because no sequencer check exists, undercharging (or overcrediting) the actor relative to the true market rate at execution time, as `SimplexPaymaster` has no code path (`SequencerUptimeFeed`/`GRACE_PERIOD`) to reject this.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
