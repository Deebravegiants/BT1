### Title
Missing MEV/slippage protection on `EvmHost` native-token swaps causes excess ETH to be permanently trapped instead of refunded to the caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept `msg.value` and route it through `IUniswapV2Router02.swapETHForExactTokens`, exactly the class of "no transaction-order/slippage protection around a token swap" flagged in the external report. Unlike the reported contract, however, the concrete exploitable defect here is not front-running of a reward claim but that the router's ETH-in refund path sends unused native token back to `address(this)` (the `EvmHost` contract) rather than to the original caller, and `EvmHost` exposes no function to reclaim stray native balance.

### Finding Description
In all three payable dispatch paths: [1](#0-0) [2](#0-1) 

the call is `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. `swapETHForExactTokens` computes the exact ETH input needed (`amounts[0]`) to buy `post.fee`/`amount` units of `feeToken`, and if `msg.value > amounts[0]`, the Uniswap V2 router refunds the difference to `msg.sender` of the swap call — which is `EvmHost` itself, not the original transaction sender (`_msgSender()`). There is no code in `EvmHost` that later forwards that refunded dust back to the user, and no `withdraw`/`sweep` function for native ETH was found anywhere in the file (only fee-token accounting via `_requestCommitments`/governance withdraw of `feeToken`). Any ETH left over from these three functions is thus stranded in the contract permanently.

This ties directly to the report's bug class ("missing transaction order protections … enable arbitrage exploitation"): because the swap has no caller-supplied minimum-output/maximum-input bound and no MEV-aware pricing, an attacker who front-runs the pool (sandwiching the swap in the same or an adjacent block) can widen the gap between `msg.value` and the actual `amounts[0]` needed, increasing the amount of ETH that gets silently absorbed by the router's refund-to-contract behavior instead of returned to the user — and even without any attacker, ordinary users who overestimate `msg.value` lose the difference unconditionally, since it can never be reclaimed.

### Impact Explanation
Native ETH sent by any unprivileged caller of `dispatch()`/`fundRequest()` in excess of the exact swap cost is permanently locked inside `EvmHost` with no governance or user-facing mechanism to retrieve it. This is a concrete, protocol-level permanent freezing of user funds reachable by ordinary end users dispatching ISMP messages with native-token payment — one of the accepted impact categories (permanent freezing of funds). The severity scales with sandwich/MEV activity against the local Uniswap V2 pool, which increases the size of the stranded remainder per transaction, but the loss occurs deterministically on every overpayment even absent an attacker.

### Likelihood Explanation
High: `dispatch{value: ...}` with native-token payment is a documented, encouraged usage pattern (see `docs/content/developers/evm/messaging/post-requests.mdx`), and any caller who does not send the exact wei amount for `amounts[0]` (which requires an off-chain quote that can go stale by the time the transaction is mined, i.e., is inherently subject to the exact "missing transaction-order protection" class the external report describes) will trigger the stuck-refund path. No privileged role or malicious governance/admin action is required — any single dispatching transaction is sufficient.

### Recommendation
- Change the swap recipient in all three `swapETHForExactTokens` calls from `address(this)` to `_msgSender()` (or the designated `payer`), so unused ETH refunds go back to the original caller instead of the host contract.
- Alternatively/additionally, add a permissionless or admin `sweepNative()`/`refundExcess()` function that forwards any stray `address(this).balance` to the correct payer, and consider requiring callers to supply an `amountInMax`/deadline consistent with their intended slippage tolerance rather than relying on `block.timestamp` (which offers no MEV protection).

### Proof of Concept
1. User calls `EvmHost.dispatch{value: X}(post)` where `X` is intentionally or unintentionally larger than the exact ETH needed to buy `post.fee` units of `feeToken` at the current pool price (e.g., due to price movement from a sandwich attack, or simple slippage estimation error).
2. `swapETHForExactTokens` executes: it uses only `amounts[0] < X` ETH from the router's perspective and refunds `X - amounts[0]` to `msg.sender`, which is `EvmHost`, per the standard Uniswap V2 router implementation.
3. `EvmHost` receives this ETH into its own balance; no downstream logic references or forwards it.
4. Grep of `evm/src/core/EvmHost.sol` for any native-ETH withdrawal function confirms none exists (fee-token withdrawal for governance is present but does not act on native ETH balance), so the difference is unrecoverable by the user or by governance.
