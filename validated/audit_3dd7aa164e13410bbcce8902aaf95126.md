### Title
Webhook `shop-domain` and `topic` headers are not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC signature only to the raw request body, while `shop` (from `shop-domain` header) and `topic` are read independently from headers that are never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic` to attribute the webhook to a tenant and select a handler, breaking the intended binding `hmac == HMAC(body ++ shop ++ topic)` down to `hmac == HMAC(body)` only.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field using a constant-time compare [5](#0-4) . For webhook requests, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` and `topic` accessors, however, are pulled directly from the `x-shopify-shop-domain` / `x-shopify-topic` HTTP headers with no cryptographic binding to the HMAC at all [2](#0-1) .

`Registry.process` first calls `Utils::HmacValidator.validate(request)` — which only re-validates the body — and once that passes, it uses `request.topic` to look up a handler and `request.shop` to build the `WebhookMetadata` passed to the app's handler [4](#0-3) . Because the header values are never part of the signed content, any HTTP client that possesses one previously-observed valid `(raw_body, hmac)` pair for the app's `api_secret_key` (for example, from a webhook the attacker's own installed/test shop legitimately received) can replay that exact body/hmac pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header (a victim shop) and/or `topic` header matching a registered handler. `HmacValidator.validate` still succeeds because it only checks the body, and the app's handler executes believing the data originated from the victim shop.

### Impact Explanation
This breaks the identity binding between the cryptographically verified content and the tenant/topic the app attributes the data to, i.e. `verified(body) == attributed(shop, topic)` is false — the shop and topic are attacker-controlled despite being used as trust anchors. Depending on what the app's `WebhookHandler#handle` implementation does with `data.shop` (per the documented contract, apps key persistence/business logic off this field [6](#0-5) ), an attacker can inject forged webhook events tagged as belonging to a different, victim merchant, causing cross-tenant data corruption/injection in the host application. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to have obtained at least one legitimate `(raw_body, hmac)` pair signed with the target app's `api_secret_key` — realistically achievable by installing the app on their own store (or a free/dev store) and capturing a real webhook delivery for a topic the app handles. No access to the `api_secret_key` itself, an access token, or the victim's credentials is required; the attacker only needs to send an HTTP POST to the app's public webhook endpoint with modified headers. This is a moderate-likelihood, low-cost attack path since a malicious actor with any legitimate app installation can attempt it.

### Recommendation
Include `shop` and `topic` (and any other header-derived fields used for tenant attribution) in the HMAC-signable content for webhook requests, or otherwise cryptographically bind them (e.g., re-verify against Shopify's webhook registration/subscription metadata rather than trusting client-supplied headers). At minimum, `Request#to_signable_string` should not be the sole basis for trusting `shop`/`topic`.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop `attacker.myshopify.com` and lets a registered webhook topic (e.g. `orders/create`) fire; they capture the raw POST body `B` and the valid `x-shopify-hmac-sha256` header value `H` that Shopify computed over `B` with the app's `api_secret_key`.
2. Attacker sends a POST directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid since only `B` is signed)
   - Header `x-shopify-shop-domain`: `victim.myshopify.com` (forged)
   - Header `x-shopify-topic`: `orders/create` (unchanged or any registered topic)
3. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds [7](#0-6) .
4. The registered handler for `orders/create` is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed_body, ...)` [8](#0-7) , causing the host application to process attacker-supplied data as if it came from the victim shop.
