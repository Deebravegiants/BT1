### Title
`ShopifyAPI::Webhooks::Request` binds webhook processing to an unauthenticated `shop-domain` header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the *raw request body*, then trusts the `X-Shopify-Shop-Domain` (and `topic`/`webhook-id`/`api-version`) HTTP headers verbatim to build the `WebhookMetadata` handed to the application's handler. Because these headers are never included in the signed content, any actor who can produce one valid `(raw_body, hmac)` pair for the app's shared `api_secret_key` — e.g. a legitimate merchant receiving their own signed webhook — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the app to process the payload under a different tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the body only) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` gates entirely on that body-only HMAC check, then forwards the untrusted `request.shop`/`request.topic`/`request.webhook_id` straight into the handler's `WebhookMetadata`: [4](#0-3) 

The identity binding that should hold is: `shop header == shop cryptographically bound by the signature`. Instead the equality that actually holds is only `hmac(body, api_secret_key) == received_hmac`; `shop` is parsed but never verified. Since `api_secret_key` is a single per-app secret shared across every installed shop (not per-tenant), any merchant who has installed the app can capture a legitimately-signed webhook delivered to their own store (valid `raw_body` + valid `hmac` for that body), and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` because the HMAC only ever covered the body, and `Registry.process` dispatches the handler with `shop: request.shop` set to the attacker-chosen victim domain.

Before the attack: `handler` invocation binding is `{ shop: signer's own shop, body: signer's own body }`.
After the attack: `handler` invocation binding becomes `{ shop: victim shop (attacker-chosen, unauthenticated), body: signer's own body }` — the two halves of the tuple that a handler assumes are cryptographically tied together are not.

### Impact Explanation
Any application built on this gem that uses the `shop` field from `WebhookMetadata` to select which tenant's data to mutate (the officially documented usage pattern, e.g. `data.shop` in `ShopifyAPI::Webhooks::Registry.process` examples) can be made to write, delete, or redact data under the wrong shop's tenant context. This is a cross-tenant access primitive: a single malicious merchant with install access to the app can forge webhook events that appear to originate from a different tenant's shop, without needing that tenant's access token or credentials — satisfying the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (unprivileged, relative to other tenants) merchant of the multi-tenant app, capable of receiving at least one real webhook for their own shop (trivial — webhooks are delivered automatically after install/OAuth). No secret leakage, TLS interception, or privileged account is required; the entire signature the endpoint checks is reusable across shops by design because the identity field is excluded from the signed payload.

### Recommendation
Bind the shop identity (and ideally topic/webhook id) into the value being HMAC-verified, or otherwise verify `request.shop` against the shop context expected for the given signature/session before dispatching to the handler. Since Shopify's real webhook HMAC only signs the body, the gem should document/enforce that consuming apps must additionally verify that the `shop-domain` header corresponds to a shop actually known/installed for this app (e.g. cross-check against stored session/shop records) before trusting `WebhookMetadata#shop`, and the library's `Registry.process` should not present `shop` as if it were part of the verified data without that caveat being made unavoidable in the API surface.

### Proof of Concept
```ruby
# Attacker is a legitimate merchant "attacker-shop.myshopify.com" of a multi-tenant app.
# They receive a real webhook (e.g. orders/create) with a valid HMAC computed
# with the app's single shared api_secret_key over the raw body.
captured_raw_body = '{"id":1,"note":"hello"}'
captured_hmac_b64 = "..." # valid signature Shopify sent them for their own shop

# Replay the exact same body+hmac to the app's webhook endpoint,
# but spoof the shop-domain header to target a different tenant:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac_b64,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: forged_headers)

# HmacValidator.validate(request) returns true, because it only checks the raw body,
# which is unchanged from the legitimate capture.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app's handler now processes attacker-controlled data under the victim's tenant.
