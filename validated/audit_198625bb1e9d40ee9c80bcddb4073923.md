## Title
Webhook Shop and Topic Identity Not Bound by HMAC, Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain`, `topic`, and `webhook-id` HTTP headers — none of which are covered by that HMAC — to route the payload and identify the tenant for the handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are read directly from HTTP headers and are never mixed into the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)`, then immediately uses the unauthenticated `request.topic` for handler dispatch and the unauthenticated `request.shop` for tenant identification, passing it straight into the data the handler acts on: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body) and compares it against the `hmac` header: [4](#0-3) 

This breaks the identity binding: `shop authenticated by HMAC == shop delivered to handler`. In reality, `shop (HMAC-covered)` is empty/undefined — only the raw body is covered — while `shop (used by handler)` is taken from an attacker-controllable header. Any party who can obtain one legitimate `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own free development store and capturing a webhook delivery, or via any registered webhook topic) can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` and `shopify-topic` headers to impersonate a different (victim) shop and/or a different webhook topic. Since the HMAC only covers the body, the forged headers pass `HmacValidator.validate` unmodified, and `Registry.process` will invoke the handler for the victim shop/topic with data that was never actually sent by Shopify for that tenant.

### Impact Explanation
This is a cross-tenant integrity/authentication issue: the gem lets a request whose HMAC was computed under the app's real `api_secret_key` for one shop/topic be replayed and re-attributed to an arbitrary shop and/or topic simply by forging headers. Host applications that key off `WebhookMetadata#shop` (as documented) to select the tenant's data store, credentials, or business logic will process the forged payload as belonging to a shop that never sent it — a cross-tenant access primitive per the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Reachable by any unprivileged internet user: they only need one legitimate webhook delivery from any shop that has installed the app (including their own free/dev store) for any registered topic, since anyone can trigger webhook events on their own store. No `api_secret_key`, access token, or privileged account is required — only the ability to send an HTTP POST to the app's public webhook endpoint with forged headers, which is exactly the kind of unauthenticated boundary this scan targets.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, and `api-version`) in the signed/verified material, or otherwise cryptographically bind them to the body before trusting them, e.g., verify a canonical string like `"#{shop}|#{topic}|#{webhook_id}|#{raw_body}"` against the HMAC, or require the host app to additionally confirm `shop` against session/tenant state that it independently trusts before dispatching to a handler. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must not be used as the sole tenant-selection key.

### Proof of Concept
1. Attacker installs the target app on their own (free) development store `attacker.myshopify.com` and registers for topic `orders/create`.
2. Shopify delivers a legitimate webhook to the app's endpoint with a valid `shopify-hmac-sha256` computed over the JSON body using the app's real `api_secret_key`.
3. Attacker captures this exact `(raw_body, hmac)` pair.
4. Attacker POSTs the same `raw_body` and `hmac` to the same endpoint but replaces the headers:
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-topic: customers/create` (or any other registered topic)
   - `shopify-webhook-id: <arbitrary>`
5. `ShopifyAPI::Webhooks::Request.new` parses these forged headers; `Utils::HmacValidator.validate` still succeeds because only `raw_body` is checked.
6. `Registry.process` dispatches to the handler registered for `customers/create` with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though Shopify never sent this data for that shop/topic.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
