### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` header, but the HMAC signature validated by `HmacValidator` only covers the raw request body, never the shop-domain header. `Registry.process` trusts `request.shop` as the authenticated tenant identity for dispatch without any additional binding check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from a header that is completely independent of that signed string: [2](#0-1) 

`Registry.process` validates the HMAC over `to_signable_string` (body only) via `HmacValidator.validate`, and — once that check passes — immediately trusts `request.shop` to build the dispatched metadata, with no comparison against any other authenticated value: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC purely from `verifiable_query.to_signable_string` (the body) and the app's `api_secret_key`: [4](#0-3) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`shop_used_for_dispatch (X-Shopify-Shop-Domain header)` == `shop_authenticated_by_hmac (none — HMAC only covers body bytes)`.

Because the signature never binds the shop-domain header to the payload, any request whose body byte-for-byte matches a previously-observed, validly-signed webhook (the same `api_secret_key` signs all webhooks for all shops that installed the app, so any shop that received/can produce a legitimately-signed body for a given topic holds a valid `(body, hmac)` pair) can be replayed to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to an arbitrary victim shop. `Utils::HmacValidator.validate` and `Registry.process` will accept it, and the handler receives `WebhookMetadata` claiming the event originated from the victim shop: [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary the gem's webhook API is supposed to guarantee to consuming applications: a caller with no credentials for shop B can cause the app's registered webhook handler to execute as if it received an authentic event from shop B (cross-tenant confusion). Depending on how the host application keys its data/session lookups off `WebhookMetadata#shop` (which is the gem's documented, "verified" output), this can lead to cross-tenant data manipulation (e.g. an `app/uninstalled` or `shop/redact` style handler acting on the wrong tenant, or mixing shop A's payload into shop B's record). This satisfies the Critical "cross-tenant access" criterion since the vulnerability lives entirely in the gem's own verification logic, not in host-app misuse.

### Likelihood Explanation
Webhook endpoints exposed by apps using this gem are public HTTP endpoints reachable by any internet user. To exploit the flaw an attacker needs at least one legitimately HMAC-signed `(body, hmac)` pair for the target app (obtainable in any topic where the body content does not itself contain shop-identifying data reliably relied upon by the handler, or where the attacker's own shop can generate an identical body to what would be sent for the victim, e.g. topics with generic/empty payloads or attacker-controlled payload content). No possession of `api_secret_key`, access tokens, or victim credentials is required — only a captured/legitimately-received webhook and the ability to replay HTTP requests with a modified header, which is standard unprivileged-internet-user capability.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the signable string used for HMAC verification, or otherwise cryptographically bind the shop-domain header to the verified payload before it is used as `WebhookMetadata#shop`. At minimum, `Registry.process` should not treat `request.shop` as authenticated identity unless it has been proven to correspond to the body that produced a valid HMAC.

### Proof of Concept
1. App installs webhook handler via `ShopifyAPI::Webhooks::Registry`.
2. Attacker owns/controls Shop A and receives a legitimately-signed webhook for topic `T` with body `B` and `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
3. Attacker POSTs to the app's public webhook endpoint with the same body `B`, same header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (victim).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [6](#0-5) 
5. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "shop-b.myshopify.com", body: parsed(B), ...)`, causing the host application to process an event as if authentically originating from Shop B.
