### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers that are never part of the signed material. `HmacValidator.validate` only proves that the *body bytes* were produced with the app's `api_secret_key`; it says nothing about which shop the request claims to be from. `Registry.process` nonetheless treats the header-derived `request.shop` as trustworthy tenant context and hands it to the webhook handler.

### Finding Description
- The HMAC is validated against `to_signable_string`, which is just `@raw_body`: [1](#0-0) 
- `shop` is parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely outside the signed bytes: [2](#0-1) 
- `HmacValidator.validate` computes and compares the signature only over `verifiable_query.to_signable_string`, i.e. the body — it never incorporates the shop header: [3](#0-2) 
- `Registry.process` gates on this same HMAC check and then forwards the unauthenticated `request.shop` straight into the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding broken is: `shop used to authenticate/tenant-scope the webhook` ≠ `shop actually covered by the HMAC`. All shops installing the same app share the same `api_secret_key` used to compute/verify webhook HMACs, so a valid `(raw_body, hmac)` pair generated for one shop remains valid for any other shop — only the header, which carries no cryptographic weight, changes.

### Impact Explanation
Any merchant who installs the target app (an unprivileged actor with respect to other tenants of the same app) can trigger a legitimate webhook on their own store, capture the resulting `(raw_body, hmac)` pair, and replay it to the app's webhook endpoint while substituting a victim shop's domain in the `shopify-shop-domain` header. `HmacValidator.validate` still succeeds because it only checks the body bytes against the shared `api_secret_key`. The host application then processes the (attacker-controlled) body under the victim shop's identity, since that identity comes solely from `request.shop`. This is a direct cross-tenant confusion primitive at the gem boundary — the exact class of "field acted upon but not bound by the authentication tag" flagged in the source report.

### Likelihood Explanation
Any app installed on more than one shop is exposed, since `api_secret_key` is shared across all installations of the app. Triggering a webhook on one's own store (e.g., creating an order) is trivial and requires no special privilege or secret knowledge — only the ability to install the app, which is normal unprivileged merchant behavior.

### Recommendation
Bind the shop identity into the material that is actually verified: e.g., require the HMAC to cover a canonical string that includes the `shop-domain` header value alongside the body, or independently verify that the value of the `shop-domain` header matches a shop that is legitimately associated with the webhook payload (Shopify's own webhook payloads typically embed `myshopify_domain`/`shop_id` fields that could be cross-checked against the header, in addition to fixing the signable-string construction to include the header).

### Proof of Concept
1. App is installed on both `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both webhooks signed with the same `Context.api_secret_key`.
2. Attacker triggers a webhook (e.g. `orders/create`) on `attacker-shop`, capturing `raw_body` and the `x-shopify-hmac-sha256` value sent by Shopify.
3. Attacker POSTs the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `Registry.process` passes because it only hashes `raw_body`: [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and `body` fully attacker-controlled, and performs tenant-scoped side effects (e.g., order/customer writes) against the victim shop's data.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
