### Title
Webhook `shop`, `topic`, `webhook-id` and `api-version` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `webhook-id`, and `api-version` values used downstream by webhook handlers are taken directly from unauthenticated HTTP headers. This breaks the binding: *shop authenticated (implicitly, via the HMAC check) ≠ shop acted on by the handler*.

### Finding Description
`Registry.process` only checks `Utils::HmacValidator.validate(request)` before invoking the handler: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Request`, `to_signable_string` returns **only** `@raw_body`: [3](#0-2) 

But `shop`, `topic`, `webhook_id`, and `api_version` — the very fields passed to the handler as tenant/routing context — are read straight from HTTP headers that are never included in the signed content: [4](#0-3) [5](#0-4) 

Because a single app has one `api_secret_key` shared across every merchant/tenant that installs it, any merchant (including a low-privilege attacker who installs the app on their own store) legitimately receives real webhooks from Shopify with a valid HMAC computed over their own webhook body. That attacker can capture the `(raw_body, hmac header)` pair from their own genuine webhook delivery and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the (unmodified) body against the shared secret; `Registry.process` then calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` set to the attacker-chosen victim shop, even though the payload itself is attacker-controlled data from their own store.

### Impact Explanation
If a host application's webhook handler trusts `data.shop` (as documented, it is the canonical tenant key returned to handlers) to determine which merchant's records to update/create, this allows an attacker to inject or overwrite data attributed to a different tenant purely by replaying their own legitimately-signed webhook with a forged shop header — a cross-tenant access/write vulnerability. No `api_secret_key`, access token, or victim credential is required; the attacker only needs their own (unprivileged) shop installation of the app.

### Likelihood Explanation
Any user who can install the target app on a store they control can trivially capture a valid `(body, hmac)` pair from a real webhook delivery and replay it with different `shop`/`topic` headers via a normal HTTP client — no cryptographic material needs to be broken, only headers not covered by the signature need to be altered.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed content used for HMAC validation (or otherwise cryptographically bind them to the request), and reject webhooks whose header set does not match Shopify's actual delivery context.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and receives a real webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid, since Shopify signed `B` with the app's shared `api_secret_key`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the same `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers; `HmacValidator.validate` calls `to_signable_string` → `B`, computes HMAC(`B`, secret) == `H` → validation passes. [1](#0-0) 
4. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, even though that body never came from Shopify for that shop.
