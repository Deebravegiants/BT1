I found a directly analogous vulnerability. The root cause pattern from the Mover bug — a shared contract that (1) accumulates un-swept token balances and (2) allows an attacker to trigger an arbitrary external call from that contract's own balance — exists in Hyperbridge's `CallDispatcher`.

### Title
Unauthenticated `CallDispatcher.dispatch()` lets anyone drain any token/native balance stranded in the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single shared, non-upgradeable utility contract used by `IntentGatewayV2` (for `predispatch`/`postdispatch` calldata execution) and by `HyperFungibleTokenUpgradeable` (for cross-chain calldata execution after mint/unlock). Its `dispatch(bytes)` function is `external` with **no access control whatsoever** [1](#0-0) , and it executes any `Call{to, value, data}` array supplied by the caller against whatever balance the dispatcher currently holds. Because the gateways only sweep back the specific tokens they expect (`order.inputs` on predispatch, `order.output.assets` on postdispatch), any token that ends up on the dispatcher outside those explicit lists is permanently stranded there — and, because `dispatch()` is callable by anyone, it can be swept out by any attacker in a completely separate, unprivileged transaction.

### Finding Description
`IntentGatewayV2.placeOrder` sends `order.predispatch.assets` to the shared `dispatcher`, invokes attacker/order-creator-controlled `order.predispatch.call` via `ICallDispatcher(dispatcher).dispatch(...)`, and then sweeps back only the tokens named in `order.inputs`, based on a balance snapshot [2](#0-1) . Any token produced by the predispatch call that is not one of `order.inputs` (e.g., an intermediate swap hop, leftover approval residue, or a route that yields multiple output assets) is left sitting in the dispatcher's balance with no cleanup.

The same pattern repeats on the fill side: `_execute()` dispatches `order.output.call` and then only sweeps `order.output.assets[i]` tokens back to the gateway, emitting `DustCollected` for what it does sweep [3](#0-2) . Any other token or native balance the postdispatch calls leave behind on the dispatcher is not accounted for or retrieved.

`HyperFungibleTokenUpgradeable.onAccept` also forwards attacker-supplied cross-chain calldata straight to the same kind of dispatcher with **no sweep step at all** after execution [4](#0-3) .

Because `CallDispatcher.dispatch()` performs no `msg.sender` check — unlike the gateway's own entry points which are gated by `nonReentrant`, `onlyHost`, or solver-selection checks — any address, including one with no relationship to the order/order-creator, can call the dispatcher directly and issue a `Call{to: strandedToken, data: transfer(attacker, dispatcher.balanceOf(...))}`. This is architecturally identical to the Mover finding: a shared, whitelisted intermediary contract accumulates value that is "left in the contract's balance" and is drainable via a subsequent externally-triggered arbitrary call, because the intermediary imposes no restriction on who can invoke it or what it may call.

### Impact Explanation
Any token dust or native ETH that a predispatch/postdispatch call (or HFT calldata execution) leaves on the shared `CallDispatcher` — which can include real user/solver funds mid-swap, not just protocol fees — is permanently and trivially stealable by an unrelated third party. Since the dispatcher is reused across every order and every HFT calldata bridge on a chain, stranded value compounds over time from unrelated users' transactions into one commonly drainable pot. This is concrete, permanent loss of funds for users/solvers whose orders route surplus tokens through the dispatcher.

### Likelihood Explanation
Reaching a state where the dispatcher holds an un-swept balance only requires one ordinary (even benign) order whose predispatch/postdispatch swap path yields any token amount outside the exact set the gateway sweeps (very common with multi-hop swaps, slippage, or partial execution). Once such a balance exists, draining it needs a single unprivileged transaction calling `CallDispatcher.dispatch()` directly — no special permissions, timing, or governance/collator/admin trust is required.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to only be callable by an authorized caller (e.g., an `onlyAuthorizedCaller` modifier checking `msg.sender` against the calling gateway/HFT contract, or make the dispatcher single-use/ephemeral per order via `CREATE2`/minimal-proxy so no balance can ever be stranded across transactions).
- After any arbitrary calldata execution, sweep the dispatcher's *entire* balance of every touched token (not just the tokens explicitly named in `order.inputs`/`order.output.assets`) back to the gateway, or require the calldata array to end with an assertion that the dispatcher balance for arbitrary tokens is zero.
- Add the same explicit end-of-flow sweep to `HyperFungibleTokenUpgradeable`'s calldata execution path, which currently performs no cleanup at all.

### Proof of Concept
1. A user places an order via `IntentGatewayV2.placeOrder` with `predispatch.call` encoding a multi-hop router swap (e.g., ETH → USDC → DAI) where the router path incidentally leaves a small residual balance of an intermediate token (e.g., USDC) on the `dispatcher` because only DAI is listed in `order.inputs`.
2. `placeOrder` sweeps back only DAI per the loop at [5](#0-4) ; the residual USDC remains on `_params.dispatcher`.
3. An unrelated attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, USDC.balanceOf(dispatcher))})]))` directly — this succeeds because `dispatch()` in [1](#0-0)  has no caller restriction, transferring the stranded USDC to the attacker.
