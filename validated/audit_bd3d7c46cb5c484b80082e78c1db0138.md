### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the merchant identity (`shop`) from the `x-shopify-shop-domain`/`shopify-shop-domain` header, but the HMAC signature validated by `Utils::HmacValidator.validate` only covers the raw request body (`to_signable_string` returns `@raw_body`). The shop identity that `Registry.process` hands to the app's webhook handler is therefore not bound to the signature that authenticates the request.

### Finding Description
`Registry.process` validates a webhook purely with: [1](#0-0) 

and `Utils::HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is just the raw body, while `shop`, `topic`, `api_version`, and `webhook_id` come from unauthenticated HTTP headers: [3](#0-2) 

After the HMAC check passes, `request.shop` (an unauthenticated header value) is passed straight into `WebhookMetadata`, which the host app's handler uses to determine which merchant's data the webhook payload belongs to: [4](#0-3) 

The equality the gem should enforce is: `shop-that-triggered-the-signed-payload == shop-attribute-delivered-to-the-handler`. Because the HMAC only signs `@raw_body`, this equality is never checked — any header value can be substituted after the fact without invalidating the signature.

Exploitation path (no privileged credentials needed): a merchant who installs the app on their own store (an ordinary, unprivileged action) will receive real Shopify-delivered webhooks whose HMAC is computed with the app's shared `client_secret` — the same secret used for every shop that installs the app. The attacker captures one such legitimate `(raw_body, hmac)` pair, then replays the raw HTTP POST to the app's own webhook endpoint (which is under the app developer's own infrastructure and calls `Registry.process`), substituting the `x-shopify-shop-domain` header for a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will deliver the payload to the handler tagged with the victim's shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the identity used to route/attribute webhook data (`shop`) is decoupled from the value actually authenticated by HMAC (the body only). Depending on how the host app uses `WebhookMetadata#shop` (e.g., to select which merchant's record to update, to trigger `shop/redact` or `customers/data_request` compliance flows, or to gate multi-tenant data writes), an attacker-installed shop can inject attacker-controlled body content that the app will process as belonging to a different, victim shop — a cross-tenant data integrity/exfiltration primitive that matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Any actor able to install the app on a shop they control (a normal, unprivileged flow) can obtain valid `(body, hmac)` pairs signed with the app's shared secret and then freely re-target the `shop-domain` header when relaying the request to the app's webhook endpoint, since the gem itself never checks that the header-derived shop is bound to the signed payload.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable content validated by `HmacValidator`, or otherwise require the host application to independently verify that `request.shop` corresponds to a session/shop that is expected to receive that specific webhook (e.g., cross-check against the shop that owns the registered webhook subscription) before dispatching to handlers.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (no special privilege required).
2. Trigger any subscribed webhook topic on `attacker-shop.myshopify.com`; Shopify delivers a POST to the app's webhook endpoint with a body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Capture `(B, H)`.
4. Send a new POST to the same app endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` (via `Webhooks::Request#to_signable_string` / `#hmac`) succeeds because it only checks `B` against `H`; `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to attribute attacker-controlled body content to the victim shop.
