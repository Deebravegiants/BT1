### Title
POA Bridge withdrawal status matched only by `assetId`, causing status/hash misreport in batch withdrawals of the same token - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain completion status of a withdrawal by looking up the POA relayer's withdrawal list and matching purely on `assetId` (via `near_token_id`), with no consideration of `destinationAddress`, `amount`, or `index`. When a batch withdrawal contains two or more withdrawals of the *same* token (e.g., sending the same asset to two different destination addresses in one intent), the lookup function returns the first record that matches the assetId for every index, so the SDK can report the wrong destination's completion (status + `txHash`) for a given withdrawal slot.

### Finding Description
`findMatchingWithdrawal()` in `poa-bridge.ts` is used by `describeWithdrawal()`: [1](#0-0) 

It explicitly documents the limitation:
```
NOTE: Currently only matches by assetId. This means multiple withdrawals
of the same token in a single transaction are not supported.
```
and:
```
return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
```

`describeWithdrawal()` then returns whatever `findMatchingWithdrawal` yields as the authoritative status for that (index, withdrawalParams) pair, without ever using `index` to disambiguate multiple withdrawals of the same asset: [2](#0-1) 

The SDK's public batch-withdrawal API (`sdk.processWithdrawal` / `sdk.signAndSendWithdrawalIntent` in batch mode, and `sdk.createWithdrawalCompletionPromises`) accepts an array of `WithdrawalParams` without any validation preventing two entries sharing the same `assetId` but different `destinationAddress`/`amount` in a single intent: [3](#0-2) 

Each withdrawal in the batch gets its own `WithdrawalIdentifier` (with a distinct `index`) via `createWithdrawalIdentifier`, and `watchWithdrawal` calls `bridge.describeWithdrawal` per identifier independently: [4](#0-3) 

Because `PoaBridge.describeWithdrawal` ignores `index` when matching (it only filters by `assetId`), two withdrawals of the same token in the same batch will both resolve to the *same* matched relayer record — meaning both will be reported with the same `status`/`txHash` even though they are two distinct on-chain transfers to two different destination addresses. The identical bug exists in the sibling helper `waitForWithdrawalCompletion` in `internal-utils`, which uses the same assetId-only `findMatchingWithdrawal`: [5](#0-4) 

The equality that breaks: *the destination transaction hash reported for withdrawal index N* should equal *the on-chain transfer that actually settled withdrawal params[N]* (its own amount/destinationAddress). Instead, the reported hash/status is decoupled from the specific withdrawal instance and is aliased across duplicate-asset entries in a batch.

### Impact Explanation
If an integrator batches two withdrawals of the same token (e.g., paying two different users/addresses `nep141:usdt.tether-token.near`) in one intent, `waitForWithdrawalCompletion`/`describeWithdrawal` will hand back the *same* `txHash` (and completion signal) for both. A caller using `destinationTx[i]` (as documented: "Index correspondence: `promises[i]` corresponds to `withdrawalParams[i]`") to reconcile off-chain records could:
- Mark both withdrawals "completed" using one destination's actual transfer hash, causing the second withdrawal's real destination transaction to go unverified/unlinked while the integrator believes it's confirmed — a status misreport that can lead to double-crediting or premature release of funds/goods tied to the unconfirmed withdrawal.
- If the misreported first-match record is the one for a different destination, an integrator relying on "the withdrawal to address B is confirmed" could actually be looking at the transfer to address A.

This matches the "status or hash misreport making an integrator credit or refund twice" High-impact class.

### Likelihood Explanation
This does not require a malicious relayer, bridge, or RPC — it's a pure client-side aliasing bug: the caller only needs to submit a legitimate batch withdrawal containing two entries for the same POA-bridged asset (a supported, unprivileged usage pattern of the public `processWithdrawal`/`signAndSendWithdrawalIntent` batch API). There is no size/uniqueness validation rejecting or warning about this case at intent-creation time (`createWithdrawalIntents` in `sdk.ts` loops over `withdrawalParamsArray` with no duplicate-asset check), so it is straightforward for any integrator batching same-asset withdrawals to hit this silently. The code comment shows the authors were aware of the limitation but did not add any guardrails (e.g., throwing when duplicate assetIds occur in a batch), so it is reachable in production usage.

### Recommendation
- In `PoaBridge.createWithdrawalIntents`/`sdk.createWithdrawalIntents` (and the batch entry points in `sdk.ts`), detect and reject (or explicitly document/guard) batches containing multiple withdrawals of the same `assetId`, since POA's status API cannot disambiguate them.
- Alternatively, until the POA relayer API supports disambiguation, match relayer records using ordering derived from a stable, deterministic tiebreaker (e.g., sort by `amount` on both sides as the code comment suggests) and only mark distinct indices completed once each relayer record has been consumed, rather than always returning `find()`'s first match for every index.
- Apply the same fix to `waitForWithdrawalCompletion` in `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`.

### Proof of Concept
1. Call `sdk.processWithdrawal` (or `signAndSendWithdrawalIntent` in batch mode) with:
   ```ts
   withdrawalParams: [
     { assetId: "nep141:usdt.tether-token.near", amount: 100n, destinationAddress: "0xAAA...", feeInclusive: false },
     { assetId: "nep141:usdt.tether-token.near", amount: 200n, destinationAddress: "0xBBB...", feeInclusive: false },
   ]
   ```
2. Both withdrawals settle on-chain to different destinations, producing two distinct relayer records with different `transfer_tx_hash` values but the same `near_token_id`.
3. Call `describeWithdrawal` (or await the corresponding entries in `createWithdrawalCompletionPromises`) for index 0 and index 1.
4. `findMatchingWithdrawal(withdrawals, "nep141:usdt.tether-token.near")` returns the same first-matching record for both calls — both indices report identical `status`/`txHash`, incorrectly correlating index 1's completion with index 0's on-chain transfer (or vice versa), as shown by the existing unit test `matches withdrawal by assetId, not by index` (`poa-bridge.test.ts:1054`), which only verifies single-item resolution and does not cover the duplicate-asset multi-withdrawal batch scenario.

		args: WithdrawalIdentifier & { logger?: ILogger },

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(

			args.withdrawalParams.assetId,

			return { status: "pending" };

			return { status: "pending" };

				txHash: withdrawal.data.transfer_tx_hash,

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
