### Title
Webhook `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are trusted for tenant routing but excluded from the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and passed unmodified into `WebhookMetadata`, which host applications use to identify the tenant (`shop`) that owns the webhook payload.

### Finding Description
`Utils::VerifiableQuery` defines an abstract contract requiring `hmac` and `to_signable_string`, and `Utils::HmacValidator.validate` verifies the received HMAC only against whatever `to_signable_string` returns: [1](#0-0) 

For OAuth callbacks, `Auth::Oauth::AuthQuery#to_signable_string` correctly includes `shop` as part of the signed content, binding the shop identity to the signature: [2](#0-1) 

By contrast, `Webhooks::Request#to_signable_string` returns only `@raw_body`, and the `shop`, `topic`, `webhook_id`, and `api_version` fields are pulled straight from HTTP headers without being covered by the HMAC: [3](#0-2) 

`Webhooks::Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., the raw body signature) and then dispatches `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` directly into `WebhookMetadata`, which is the struct the host application's handler consumes to identify the shop associated with the payload: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `hmac_signed_content == (raw_body, shop, topic, webhook_id)`, i.e., the shop asserted in the header should be cryptographically bound to the payload that was HMAC-signed with the app's `client_secret`. Instead the actual binding is `hmac_signed_content == raw_body` only, while `shop` (and `topic`/`webhook_id`) are trusted unconditionally from headers.

Because Shopify signs the webhook body with the *app's* shared `client_secret` (the same secret across all shops/tenants of that app, not a per-shop key), any legitimate webhook delivery to any shop installed on the app yields a body+HMAC pair that remains valid for that exact body regardless of which shop header accompanies it. This is exactly the "field acted on but not covered by the HMAC" boundary-break pattern.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-used-by-handler identity binding, which can enable cross-tenant confusion in host applications: a handler that keys behavior (e.g. loading the merchant's session/access token, updating per-shop records, or acknowledging install/uninstall state) off `WebhookMetadata#shop` can be made to act on behalf of an attacker-chosen shop domain while presenting body content that was only ever validated against the shared HMAC key, not against that specific shop. Combined with a `topic` header that is likewise unauthenticated, an attacker could also relabel a legitimately-signed payload as a different topic (e.g., turning a benign webhook body into what the handler interprets as an `app/uninstalled` or `customers/redact` event) as long as the handler's logic does not independently validate the body shape against the topic.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one authentic (body, HMAC) pair — which is easy for an attacker who has their own shop installed the same app (a normal, unprivileged action), since Shopify signs with the shared app secret rather than per-shop secrets. No access token, `client_secret`, or privileged account is required. Whether an app is actually vulnerable end-to-end depends on how the host application's `WebhookHandler#handle` implementation uses `data.shop`/`data.topic`, but the gem itself offers no protection and forwards unauthenticated header values into the trusted `WebhookMetadata` struct after validating only the body.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable content (or otherwise cryptographically bind them to the signed body), mirroring the approach used in `Auth::Oauth::AuthQuery#to_signable_string`. At minimum, document clearly that `WebhookMetadata#shop`/`#topic` are unauthenticated header values so host applications do not assume they are covered by the HMAC check, and recommend applications independently validate that `shop` corresponds to a shop with an active installation/session before trusting it for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target app on their own controlled shop `attacker-shop.myshopify.com`, and triggers a webhook delivery (e.g., an `orders/create` event) to obtain a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared `client_secret`.
2. Attacker replays the exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `request.hmac` against `Digest.hexencode(...)` of `@raw_body` — see `lib/shopify_api/webhooks/request.rb:10-38` and `lib/shopify_api/utils/hmac_validator.rb:12-22`.
4. The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, body: <attacker's own webhook body>, ...)` and, if it uses `data.shop` to look up or mutate the merchant's data, the boundary between "shop cryptographically bound to signed payload" and "shop asserted by the caller" has been violated.
