### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are trusted from unauthenticated headers while the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the shop identity (`x-shopify-shop-domain`), topic, and webhook id are read from HTTP headers that are never included in the signed material. This breaks the equality "bytes verified == bytes trusted for tenant identity," letting an attacker who can obtain one genuinely-signed webhook body (e.g. from their own shop, which anyone can install a public app on) replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over `to_signable_string`, i.e. the raw body, and compares it to the `hmac` header: [2](#0-1) 

But `Request#shop`, `#topic`, and `#webhook_id` are all parsed straight from headers that are excluded from that signed string: [3](#0-2) 

`Registry.process` validates only the HMAC, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` handed to the app's handler with no cross-check that these header values are bound to the signed body: [4](#0-3) 

The gem's own documentation instructs app developers to trust `data.shop` directly (e.g. to key a job by `shop_domain: data.shop`) without saying it needs independent verification: [5](#0-4) 

This mirrors the report's bug class: a check (`canCall`/HMAC) that passes on one narrow condition (function selector / body bytes) is then treated as clearance for everything downstream (arbitrary transformer calls / arbitrary header-derived shop identity), when the thing actually validated does not cover the field being acted upon.

### Impact Explanation
Any user who can install the vulnerable app on their own (attacker-controlled) Shopify store — an unprivileged action requiring no special access — will receive genuine webhook deliveries with valid HMACs computed by Shopify using the app's real `client_secret`. Because the HMAC covers only the JSON body and not the `x-shopify-shop-domain` header, the attacker can replay that exact `(raw_body, hmac)` pair to the shared webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (body unchanged), and `Registry.process` passes `WebhookMetadata` with the attacker-chosen `shop` value to the handler as if it were an authenticated event for the victim tenant. Any handler logic that keys tenant data, session lookups, deduplication, or state transitions off `data.shop` can be tricked into cross-tenant writes/reads — this satisfies the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is meaningfully constrained: the attacker needs (a) at least one legitimate webhook delivery from Shopify to a shop they control that shares the same app/`client_secret`, and (b) knowledge of a webhook topic/body shape the app processes. Both are achievable by any developer who installs a public/unlisted app on a free development store, making this reachable by an unprivileged internet user without any leaked secret, TLS interception, or social engineering — matching the exploit primitive discussed in the analog report where a validated narrow check gives blanket downstream trust.

### Recommendation
Bind the identity fields into the authenticated material instead of trusting bare headers:
- Require the webhook handler/registry to cross-check the delivered `shop` against the shop for which the webhook topic was actually registered (the registry already tracks registrations per topic), rejecting deliveries whose header shop does not match an app-tracked, previously-authenticated shop/session.
- At minimum, document prominently (and ideally enforce in `Registry.process`) that `data.shop` must be re-validated by the host app against its own session store before being used for any tenant-scoped operation, since it is not covered by the HMAC.
- Consider including the shop domain in the signable string used for verification if/when this becomes possible on Shopify's platform, to make the identity binding cryptographic rather than advisory.

### Proof of Concept
1. Attacker signs up as a merchant and installs `TargetApp` on `attacker-shop.myshopify.com`; `TargetApp` uses `shopify_api` and registers an `orders/create` webhook.
2. Shopify delivers a legitimate webhook to `TargetApp`'s callback URL with headers including `x-shopify-hmac-sha256: <valid HMAC over raw_body computed with the app's real client_secret>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures the exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker re-sends an HTTP POST to the same webhook endpoint with the identical `raw_body`/`hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the secret (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
6. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though nothing about the request was signed with anything related to `victim-shop`, letting the attacker inject a spoofed event attributed to the victim tenant.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
