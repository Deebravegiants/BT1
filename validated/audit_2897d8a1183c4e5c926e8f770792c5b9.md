### Title
Untrusted swap routes can attach unrelated caller-signed token transfers and sweep wallet assets - (File: contracts/controller/src/strategies/swap.rs)

### Summary

Controller strategy entrypoints accept opaque swap routes and execute them while the caller’s original authorization remains active. The controller deliberately authorizes only the exact controller-to-router input transfer, but it does not constrain which contracts the route invokes beneath that authorization. A route-selected pool can therefore request an unrelated `token.transfer(victim, attacker, amount)` and have it attached as a child of the victim’s signed authorization tree.

This is the on-chain analogue of the password-manager sweep: the victim believes they are authorizing one bounded action, while code reached through that action obtains an additional credential-authorized transfer for a selected asset.

### Finding Description

`swap_collateral` authenticates `caller`, verifies that the caller owns or delegates the account, withdraws the requested collateral, and forwards the opaque `swap` bytes into `withdraw_and_swap_from_supply` [1](#0-0) .

The shared swap boundary grants the configured router only an exact transfer of `amount_in` from the controller [2](#0-1) . Afterward, the controller validates only that its input spend did not exceed `amount_in` and that its output balance increased [3](#0-2) .

The router decodes pool addresses from the route’s unrestricted address registry rather than from an allowlist [4](#0-3) . Each swap instruction resolves a caller-supplied `pool`, `token_in`, and `token_out`, then dispatches the selected venue adapter [5](#0-4) . Those adapters invoke the route-selected pool address [6](#0-5) .

Because the malicious pool executes below the victim-authorized controller call, a token transfer from the victim can join the victim’s authorization tree even though it is unrelated to the swap input. The regression test demonstrates a pool executing `token.transfer(victim, attacker, amount)` [7](#0-6) , simulation attaching that transfer beneath the victim’s `swap_collateral` authorization [8](#0-7) , and enforcement accepting the theft when the recorded child authorization is signed [9](#0-8) .

### Impact Explanation

An attacker can steal arbitrary token balances held by the swap caller, including tokens that were never supplied to the lending protocol and were not part of the declared swap. The stolen amount is not bounded by `amount_in`, route `min_out`, collateral value, or post-strategy health checks; the controller measures only controller-side input and output balances [3](#0-2) .

The same authorization-tree exposure applies to any controller strategy that passes route bytes to the router, including `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral`, because the extra transfer is performed by untrusted route code nested below the caller-authorized strategy invocation [10](#0-9) .

### Likelihood Explanation

An unprivileged attacker can deploy a malicious pool contract, encode its address in a syntactically valid route, and present the resulting strategy transaction through a malicious interface. The victim still must authorize the transaction, but the dangerous authorization is structurally attached to an otherwise valid swap and can be hidden behind normal transaction-simulation output.

No privileged role, leaked key, compromised oracle, protocol parameter change, or protocol-owned liquidity is required. The malicious pool can also return a fair output amount itself, allowing the lending strategy’s measured-output and solvency checks to pass while the unrelated wallet transfer succeeds [11](#0-10) .

### Recommendation

Do not invoke route-selected, unallowlisted contracts beneath a user-authorized controller strategy call.

Possible mitigations include:

- Enforce an on-chain allowlist of trusted pool addresses for every venue hop.
- Separate route execution from the user-authorized controller invocation so arbitrary venue code cannot inherit the user’s authorization scope.
- Add protocol-level route manifests that cryptographically bind every external contract that may run below the strategy call.
- Reject routes containing venue or pool addresses outside governance-approved registries.
- Require wallets and transaction builders to display and separately confirm every child token transfer, especially transfers whose source differs from the controller or router.

An allowlist is the strongest contract-side mitigation because client-side auth-tree inspection cannot protect users of nonconforming wallets or integrations.

### Proof of Concept

1. Deploy `RoguePool` with stored `(victim, victim_wallet_token, attacker, victim_balance)`.
2. Fund `RoguePool` with enough `ETH` to return the advertised fair swap output.
3. Build a `StrategyPayload` for `USDC -> ETH` containing:
   - `assets = [USDC, ETH, rogue_pool]`;
   - one Soroswap swap instruction whose `pool` index selects `rogue_pool`;
   - `min_out` equal to a fair `ETH` amount.
4. Have the victim call:

```rust
controller.swap_collateral(
    victim,
    victim_account_id,
    HubAssetKey { hub_id, asset: usdc },
    swap_amount,
    HubAssetKey { hub_id, asset: eth },
    malicious_swap_xdr,
);
```

5. The controller authenticates the victim and validates account ownership before executing the strategy [12](#0-11) .
6. `swap_tokens` authorizes only `controller -> router` for `swap_amount`, then invokes `execute_strategy` with the malicious route [2](#0-1) .
7. During the selected hop, `RoguePool` calls:

```rust
token::Client::new(&env, &victim_wallet_token).transfer(
    &victim,
    &attacker,
    &victim_balance,
);
```

8. Soroban records this as a child authorization under the victim’s `swap_collateral` entry [13](#0-12) .
9. If the victim signs the recorded tree, `RoguePool` receives `swap_amount`, returns `min_out` of `ETH`, and transfers the victim’s unrelated `victim_wallet_token` balance to the attacker [14](#0-13) .
10. The controller still sees a bounded input spend and positive `ETH` receipt, so the account finalization proceeds normally [3](#0-2) .
