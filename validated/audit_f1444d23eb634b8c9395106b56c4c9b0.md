### Title
Single-step `transferCreator` on `Bonding` allows creator-fee funds to be locked forever at an uncontrolled address - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.transferCreator` reassigns a token's creator (and therefore all future `FeeVault` fee attribution) in a single call, with only a zero-address and self-transfer check. Unlike the protocol's admin roles, which deliberately use `Ownable2StepUpgradeable` on `Bonding`, `Zap`, and `FeeVault` specifically to avoid this exact bug class (see the comment in `FeeVault.sol` explicitly citing "a bad `transferOwnership`... fat-fingered or contract-incompatible address"), the creator role has no equivalent two-step safeguard.

### Finding Description
`transferCreator` is: [1](#0-0) 

It only checks `newCreator != address(0)` and `newCreator != info.creator`, then immediately overwrites `info.creator` — a one-shot write, exactly the anti-pattern the external report describes. There is no pending-creator staging and no `acceptCreator()` step for the new address to confirm control.

By contrast, the codebase's own admin-ownership paths were explicitly hardened against this class of bug using `Ownable2StepUpgradeable`, as documented in `FeeVault.sol`: [2](#0-1) 

and exercised in tests such as `test_bonding_acceptCompletesTransfer` / `_assertOnlyPendingOwnerCanAccept`: [3](#0-2) 

The creator role is exactly as consequential as ownership for the affected token: it is the sole key used for future fee attribution. `FeeVault.accrue` credits `creatorBalance[creator]` using whatever `Bonding.tokenInfo(token).creator` currently is, and `claim()` pays out strictly to `msg.sender`'s balance: [4](#0-3) 

If a creator calls `transferCreator(tokenAddress, newCreator)` with a mistyped, unowned, or non-interactive contract address, all subsequent 0.25% creator-fee accruals for every future buy/sell on that token are routed to `creatorBalance[newCreator]` in `FeeVault`, and since only `newCreator` itself can call `claim()`, those funds become permanently unclaimable if `newCreator` cannot originate a transaction (e.g. a burn address, a contract with no fallback logic to call `claim`, or simply an address nobody controls).

### Impact Explanation
This is a permanent freezing of creator funds: every trade thereafter accrues real USDC fees into `FeeVault.creatorBalance[newCreator]`, and that balance is unrecoverable by the original creator or the protocol (there is no admin sweep for `creatorBalance`, only `sweepDonations()` for balance above the `totalAccruedCreator + protocolBalance` backing). This meets the "permanent freezing of ... creator ... funds" bar from the validation criteria.

### Likelihood Explanation
Reachable by any token creator (permissionless — anyone can `Bonding.launch()` a token and become its creator) via a single, ordinary call to `transferCreator`. No special privilege beyond being the token's own creator is required, and a simple typo, copy-paste error, or use of an unsupported contract address as the intended new payout target is a realistic and common user error, especially since there is no simulated confirmation step.

### Recommendation
Convert `transferCreator` into a two-step process mirroring `Ownable2StepUpgradeable`: store a `pendingCreator` on `initiateCreatorTransfer`, and only finalize the switch when the new address calls `acceptCreatorTransfer()`, consistent with the pattern already used for `owner()` across `Bonding`, `Zap`, and `FeeVault`.

### Proof of Concept
1. Creator `C` launches a token via `Bonding.launch`, becoming `tokenInfo[tokenAddress].creator`.
2. Trading proceeds through `Zap.buy/sell`, and `FeeVault.accrue` credits `creatorBalance[C]` with 0.25% fees each trade.
3. `C` calls `bonding.transferCreator(tokenAddress, newCreator)` where `newCreator` is a mistyped address or a contract that never calls `claim()`.
4. `info.creator` is now `newCreator`; per `test_transferCreator`, the change is immediate and irreversible: [5](#0-4) 
5. All future trades on that token accrue fees to `creatorBalance[newCreator]` in `FeeVault`, which nobody can ever claim, permanently locking those funds.

    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }

    // ─── Claims ──────────────────────────────────────────────────────────

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
