### Title
Unvalidated presigned URL in personal custody package upload enables biometric data exfiltration - (File: src/backend/upload_personal_custody_package.rs)

### Summary
`backend::upload_personal_custody_package::request` takes the `url` field from the backend's `presigned_url::request_tiered_package`/`request_package` response and uses it directly as the destination of a multipart POST containing the user's tier1/tier2 personal custody package (iris/face biometric data), without validating the URL's scheme or host against an allowlist. A malicious/compromised backend response during the attacker's own signup session can redirect the upload of biometric data to an attacker-controlled endpoint.

### Finding Description
The call chain is `plans::build_pcp` / `upload_pcp_tier_0` → `backend::upload_personal_custody_package::request` → `presigned_url::request_tiered_package`, and the resulting `presigned_url::Response.url` is passed straight into `reqwest` without any check: [1](#0-0) 

Specifically, `presigned_url` is only logged, then handed to `.post(presigned_url).multipart(form)`: [2](#0-1) 

The `presigned_url::Response` is deserialized straight from the JSON body returned by the backend endpoint `{backend_url}/api/v3/signups/{signup_id}/tiered/package`: [3](#0-2) 

The only network hardening present is at the client-builder level (`orb_security_utils::reqwest::http_client_builder()`, an external crate not part of this repo, providing TLS settings), not a destination-host allowlist: [4](#0-3) 

There is no code anywhere in `upload_personal_custody_package::request` or `presigned_url::request_tiered_package` that validates the returned `url` is `https://` and belongs to a Worldcoin-controlled domain (e.g., an S3 bucket under `worldcoin`'s control) before the biometric package (built in `plans::mod::build_pcp`, containing iris codes/images and face embeddings) is uploaded via multipart POST.

### Impact Explanation
If the backend response for the presigned-URL request is attacker-influenced during the attacker's own signup session, the Orb will multipart-upload the tier1/tier2 personal custody package — which contains iris-code shares, normalized iris images, and face embeddings/thumbnails — to whatever URL is provided, including an attacker-controlled HTTPS (or even non-HTTPS, if permitted by the client stack) endpoint. This is a biometric data disclosure impact matching "Sensitive data exposure/exfiltration" under the Worldcoin/Orb bounty scope, since the invariant that biometric secrets are sent only to backend-authorized destinations is violated.

### Likelihood Explanation
This requires the precondition stated in the question: the attacker can control/influence backend responses reachable during their own signup session (e.g., a rogue or MITM'd backend/proxy in that session). Given that precondition, the exploit is fully deterministic and repeatable — every tier1/tier2 upload for that signup follows the same unvalidated path.

### Recommendation
Before issuing the multipart upload, validate the `url` returned by `presigned_url::request_package`/`request_tiered_package`: enforce `https` scheme and restrict the host to an explicit allowlist (e.g., known Worldcoin S3/CDN domains or a suffix match against `DATA_BACKEND_URL`'s trusted domain set). Reject and error out (treat as an upload failure, not silently proceed) if validation fails.

### Proof of Concept
Integration test plan for `upload_personal_custody_package::request`:
1. Stand up a mock HTTP server implementing `/api/v3/signups/{signup_id}/tiered/package` that returns a `presigned_url::Response` with `url: "https://attacker.example.com/exfil"` and arbitrary `fields`.
2. Point `DATA_BACKEND_URL` at the mock server.
3. Call `backend::upload_personal_custody_package::request(signup_id, session_id, checksum, data, Some(tier), &config)`.
4. Assert that the request currently succeeds and multiparts `data` to `attacker.example.com` (demonstrating the bug), then after the fix, assert the function returns an `Err` before any POST to a non-allowlisted host is attempted (verified via the mock server never receiving the multipart body).
