### Title
Webhook shop/topic identity spoofing via headers not covered by HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop`, `topic`, and `webhook_id` values from HTTP headers, but the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the intended binding `hmac_verified_bytes == bytes_the_handler_trusts_as_tenant_identity`, allowing an attacker who possesses any one valid `(body, hmac)` pair to relabel that body as originating from an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, and `webhook_id` are all read directly from HTTP headers, which are never part of the signed content: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC strictly over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac-sha256` header: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` (all unauthenticated headers) as the tenant identity handed to the app's handler: [1](#0-0) 

Because Shopify signs webhooks with the single `api_secret_key` shared across all shops that installed the app (there is no per-shop key material), any entity that can obtain one legitimate `(raw_body, hmac)` pair — for example by installing the app on their own store and receiving real webhooks for it — can replay that exact body with a forged `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header pointed at a different, victim shop. `HmacValidator.validate` will still return `true` because it only checks body integrity, not header integrity, so `Registry.process` will invoke the handler believing the event came from the victim shop.

### Impact Explanation
This breaks the equality the code implicitly assumes: `hmac_verified(raw_body) == identity_of(shop_header)`. In reality, the `shop` header is decoupled from the signed payload, so an unprivileged app-installer (an "internet user" relative to other tenants of the same app) can impersonate another tenant's webhook stream. Depending on how the app's `WebhookHandler` implementations use `WebhookMetadata#shop` (e.g., `shop/redact`, `customers/redact`, `app/uninstalled` handling, which frequently key merchant-record deletion or de-provisioning directly off this field), this enables cross-tenant actions being attributed to, or triggered against, a shop the attacker does not control — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Any party can install the target app on their own development/trial store (a standard, unprivileged action) and thereby legitimately receive Shopify-signed webhooks, obtaining valid `(body, hmac)` pairs signed with the app's shared secret. Forging headers on a replayed HTTP POST requires no cryptographic secret. Likelihood is High for apps whose handlers key sensitive logic off `WebhookMetadata#shop`/`#topic` without independently re-verifying that the identified shop actually installed/owns the webhook.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed content verified by the HMAC (or verify them by an independent authenticated channel, e.g., cross-checking against a known-installed-shops table plus topic-specific expectations) rather than trusting raw headers. At minimum, `Utils::HmacValidator` should be extended so `VerifiableQuery#to_signable_string` for webhooks incorporates the header values that are later used as trust anchors, not just the body bytes.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development shop `attacker.myshopify.com`; this triggers a real webhook, e.g. `app/uninstalled`, with body `B` and header `shopify-hmac-sha256: H` (valid signature of `B` under the app's `api_secret_key`).
2. Capture the raw POST: headers include `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: app/uninstalled`, `shopify-hmac-sha256: H`, body `B`.
3. Replay the exact same body `B` and `hmac-sha256: H` to the app's webhook endpoint, but replace `shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, returns `true` — [5](#0-4) .
5. `Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)` — [6](#0-5) , causing the app to process an uninstall/redact-style event for a shop the attacker never controlled.
