### Title
Vault `GatewayHandler` permanently caches the master public key with no invalidation, causing silent misbehavior after key rotation - ([File: core/capabilities/vault/gw_handler.go])

### Summary
`GatewayHandler.getMasterPublicKey` fetches the Vault TDH2 master public key from `secretsService` only once and stores it forever in `h.cachedMasterPublicKey`. Every subsequent `CreateSecrets`/`UpdateSecrets` request reaching the node from the gateway is validated/processed against this permanently cached key, with no mechanism to refresh or invalidate it if the underlying master key is rotated. This mirrors the reported bug class: an admin-controlled reference (the redeemable token / here, the master public key) is cached once by a dependent component and never re-synced, so the system silently misbehaves once the upstream reference changes.

### Finding Description
`GatewayHandler` holds a `cachedMasterPublicKey *tdh2easy.PublicKey` guarded by `sync.RWMutex`: [1](#0-0) 

`getMasterPublicKey` implements a classic "cache on first use, never expire" pattern: [2](#0-1) 

Once any request populates `h.cachedMasterPublicKey`, the value is never refetched from `secretsService` for the remaining lifetime of the process. This value is used to validate/process every `MethodSecretsCreate` and `MethodSecretsUpdate` request handled by the gateway handler: [3](#0-2) 

Meanwhile, `handlePublicKeyGet` (the endpoint clients call to learn the current key before encrypting a secret) always queries `secretsService.GetPublicKey` fresh, with no caching: [4](#0-3) 

This asymmetry means: if the Vault master key is ever rotated/re-keyed on the `secretsService` side (e.g., due to threshold re-key or key-compromise remediation), clients calling `GetPublicKeyGet` immediately observe the new key and encrypt future secrets under it, but any node process that already served one `CreateSecrets`/`UpdateSecrets` request before the rotation will keep validating/processing all future requests against the stale key indefinitely — until the process restarts. This is functionally identical to the reported issue where `RageDnDepository` caches `redeemable` once at `initialize()` and never reacts to `UXDController.setRedeemable()` changing the canonical reference, causing mismatches across the system.

The existing test `TestGatewayHandler_CreateUpdateReusesCachedPublicKey` explicitly documents and locks in this caching behavior: [5](#0-4) 

### Impact Explanation
Because the cache is process-lifetime and per-node (each Vault DON node caches independently the first time it happens to serve a create/update request), a key rotation intended to revoke trust in an old key does not actually take effect on any node that already cached the old key. Practically this causes either:
- Silent, node-inconsistent failures/mismatches across the DON for `CreateSecrets`/`UpdateSecrets` once some nodes have rotated their in-memory view and others have not, breaking BFT/threshold consistency of the vault capability; or
- Continued trust in a public key whose rotation was performed specifically because the corresponding key material was believed compromised, undermining the security purpose of rotation.

This is reachable purely through unprivileged workflow-triggered gateway traffic (any `CreateSecrets`/`UpdateSecrets` call causes the cache to populate), and the resulting behavior deviates from the system's intended security invariant that all vault nodes validate against the current master key.

### Likelihood Explanation
Likelihood depends on operational key-rotation happening while nodes are already warmed up (i.e., have served at least one create/update request) — this is the expected steady-state condition for a running node, so any real-world key rotation event will trigger this staleness. No attacker action is required to trigger the caching; only a legitimate `CreateSecrets`/`UpdateSecrets` request (which any workflow owner unprivileged actor can send) is needed to populate the cache before rotation occurs.

### Recommendation
Do not cache the master public key for the lifetime of the process. Either fetch it fresh on every request (mirroring `handlePublicKeyGet`), or implement explicit, bounded-TTL cache invalidation and/or an active invalidation hook triggered when the underlying key material changes on `secretsService`, ensuring `getMasterPublicKey` cannot serve callers a permanently stale key.

### Proof of Concept
1. Vault DON node starts; `GatewayHandler.cachedMasterPublicKey` is nil.
2. A workflow owner sends a `CreateSecrets` request through the gateway; `getMasterPublicKey` fetches the current master public key (`K1`) from `secretsService` and caches it permanently (`core/capabilities/vault/gw_handler.go:238-261`).
3. Operator rotates the Vault master key on `secretsService` to `K2` (e.g., threshold re-key).
4. A client calls `MethodPublicKeyGet`; `handlePublicKeyGet` returns the fresh key `K2` (`core/capabilities/vault/gw_handler.go:364-386`), so the client encrypts a new secret under `K2`.
5. The client sends `CreateSecrets`/`UpdateSecrets` with the `K2`-encrypted payload; `HandleGatewayMessage` calls `getMasterPublicKey`, which returns the stale cached `K1` (`core/capabilities/vault/gw_handler.go:187-199, 238-261`) — the request is processed/validated against the wrong key, producing incorrect behavior/failures that persist until node restart, exactly matching the "change of redeemable will break the system" bug class.

func (h *GatewayHandler) getMasterPublicKey(ctx context.Context) (*tdh2easy.PublicKey, error) {
	h.mu.RLock()
	if h.cachedMasterPublicKey != nil {
		cachedCopy := *h.cachedMasterPublicKey
		h.mu.RUnlock()
		return &cachedCopy, nil
	}
	h.mu.RUnlock()

	publicKey, err := MasterPublicKeyFromSecretsService(ctx, h.secretsService)
	if err != nil {
		return nil, err
	}

	h.mu.Lock()
	defer h.mu.Unlock()
	if h.cachedMasterPublicKey != nil {
		cachedCopy := *h.cachedMasterPublicKey
		return &cachedCopy, nil
	}
	h.cachedMasterPublicKey = publicKey
	cachedCopy := *publicKey
	return &cachedCopy, nil
}

func (h *GatewayHandler) handlePublicKeyGet(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.GetPublicKeyRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	resp, err := h.secretsService.GetPublicKey(ctx, r)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.HandlerError, fmt.Errorf("failed to get public key: %w", err))
	}

	b, err := json.Marshal(resp)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}

	return &jsonrpc.Response[json.RawMessage]{
		Version: jsonrpc.JsonRpcVersion,
		ID:      req.ID,
		Method:  req.Method,
		Result:  (*json.RawMessage)(&b),
	}
}
