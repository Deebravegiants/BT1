This confirms the finding: the documented flow (`docs/usage/webhooks.md` lines 125-136) explicitly tells developers `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify," and the resulting `WebhookMetadata#shop` field [1](#0-0)  is what app developers are told to trust for tenant identification (as shown by the doc example `shop_domain: data.shop`) [2](#0-1) .

### Title
Webhook `shop` domain is not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate`, which verifies the HMAC over `request.to_signable_string`. For `Webhooks::Request`, that signable string is defined as the raw request body only, not the headers [3](#0-2) . The `shop` value passed downstream to the app's handler is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the HMAC's coverage [4](#0-3) .

### Finding Description
`Registry.process` does exactly one authenticity check before invoking the app-supplied handler:

```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [5](#0-4) 

`HmacValidator.validate_signature` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the received HMAC [6](#0-5) . For webhook requests, `to_signable_string` returns only `@raw_body` [3](#0-2) , so the HMAC cryptographically binds only the JSON body — never the `shop`, `topic`, `webhook_id`, or `api_version` headers.

The identity binding that should hold is:
`HMAC-authenticated(shop)` == `shop passed to handler.handle`

In this implementation, the equality breaks: the HMAC only authenticates "this body was produced by someone holding the app's shared secret" — it says nothing about which shop the body belongs to. The `shop` field is bytes-parsed from an attacker-controllable header but never bytes-verified.

Because the API secret is shared across every shop that has the app installed (it is not per-tenant), any merchant who installs the app is a legitimate holder of a validly-HMAC'd webhook body (their own genuine webhook delivery from Shopify). That merchant can replay/craft an HTTP request to the app's webhook endpoint using the *same, still-valid* body/HMAC pair while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still passes because it never inspects the header, and `Registry.process` forwards the attacker-chosen `shop` string straight into `WebhookMetadata`, which the documentation explicitly instructs developers to use as the tenant key (`shop_domain: data.shop`) [2](#0-1) .

### Impact Explanation
This lets an unprivileged merchant (privileged only over their own shop) inject webhook events that the host application will attribute to an arbitrary other tenant — a cross-tenant integrity/confidentiality break at the very point the gem promises verification ("This will verify the request did indeed come from Shopify") [7](#0-6) . Depending on how the host app keys its per-shop side effects off `data.shop` (job dispatch, cache invalidation, data sync, `app/uninstalled` cleanup, etc.), this can lead to cross-tenant data corruption or state changes attributed to a shop that never sent the event — meeting the "cross-tenant access" bar.

### Likelihood Explanation
Requires only: (1) installing the app on one's own shop (an unprivileged, self-service action every real customer can do), and (2) capturing one legitimate webhook delivery to reuse its body/HMAC pair with a modified `shop` header. No knowledge of `api_secret_key`, no TLS interception, and no privileged account is required — only the gem's own signature computation, which excludes the shop-identifying header from what it signs.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signable material verified against the HMAC, or independently cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription before dispatching to the handler, rather than trusting the raw header value once the body-only HMAC succeeds.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, which is a legitimate, unprivileged action.
2. Shopify sends a legitimate webhook (e.g. `orders/create`) to the app's endpoint for `attacker-shop.myshopify.com`, with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`.
3. Attacker replays this exact HTTP request to the same webhook endpoint, only changing the `x-shopify-shop-domain` header to `victim-shop.myshopify.com` (raw body and HMAC header untouched).
4. `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only [3](#0-2)  — it still matches, since the body wasn't modified.
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [8](#0-7)  and invokes the app's handler, which processes attacker-controlled order data as if it belonged to `victim-shop`.
