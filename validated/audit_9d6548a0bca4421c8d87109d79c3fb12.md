### Title
Webhook `shop` domain is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the `X-Shopify-Shop-Domain` header as the tenant identity forwarded to the app's handler. Because the shop domain is never included in the signed content, the binding "HMAC-authenticated request" == "claimed shop" does not hold, allowing a malicious merchant of a multi-tenant app to relabel their own validly-signed webhook payload as belonging to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

The HMAC is validated over this body-only string using the app's single, global `Context.api_secret_key` (shared across every shop that has installed the app), via `HmacValidator.validate`: [3](#0-2) 

`Registry.process` then forwards `request.shop` — read directly from the unauthenticated `X-Shopify-Shop-Domain` header — as the tenant identity to the app's webhook handler: [4](#0-3) 

The gem's own documentation instructs app developers to treat `data.shop` as the trustworthy "shop domain of the webhook" for dispatching per-tenant work: [5](#0-4) 

The identity equality that should hold is: **shop authenticated by the signed request == shop used as the tenant key for the handler.** Because the shop header is not part of `to_signable_string`, and the same `api_secret_key` is used for every shop under the app, any user who has installed the app onto their own (attacker-controlled) shop can:
1. Trigger a webhook of any registered topic to their own shop and capture the exact `raw_body` + valid `X-Shopify-Hmac-Sha256` value Shopify computed with the app's shared secret.
2. Replay that identical body and HMAC header to the app's webhook endpoint, but substitute `X-Shopify-Shop-Domain` with a victim shop's domain.
3. `HmacValidator.validate` succeeds (it only checks the body signature), and `Registry.process` calls the handler with `data.shop` equal to the victim's domain, even though Shopify never sent anything about the victim shop in this request.

### Impact Explanation
This breaks the cross-tenant isolation the HMAC check is meant to provide. Any app relying on `data.shop` to determine which merchant record/session/queue to act on (exactly as the gem's docs recommend) can be made to process attacker-supplied, attacker-timed webhook content under a victim shop's identity — e.g., triggering redaction/compliance webhooks, forged order/product change notifications, or any topic-specific business logic keyed off `data.shop`, for a shop the attacker does not control. This is a cross-tenant access vulnerability satisfying the "Critical - cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is high for any developer who installs the app on their own store (a normal, unprivileged action available to any internet user who can install a public/multi-tenant Shopify app) and simply forwards headers as documented (`request.headers.to_h`) without independently re-validating the shop domain against a per-merchant secret or a known-installed-shops list. No access token, `api_secret_key`, or privileged credential is required — only ordinary participation as one tenant of the app.

### Recommendation
Bind the shop domain into the signed content, or otherwise re-authenticate it before trusting `request.shop`:
- Have `VerifiableQuery`/`Request#to_signable_string` include the shop domain (or otherwise verify server-side that the header shop is one of the app's currently-installed, known shops with an active session) before dispatching to the handler, and document that host apps must not trust `data.shop` merely because HMAC validation passed.
- Alternatively, cross-check `request.shop` against the shop-specific access token/session already stored by the app for that topic/webhook_id before invoking the handler.

### Proof of Concept
1. Install the target multi-tenant app on attacker-owned shop `attacker.myshopify.com`; register for topic `orders/create`.
2. Trigger an `orders/create` event on `attacker.myshopify.com`. Capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256: H` header Shopify sends (computed with the app's shared `api_secret_key` over `B`).
3. Send a forged HTTP request to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...with victim domain...})` is constructed; `HmacValidator.validate` succeeds because it only checks `B` against `H`.
5. `Registry.process` invokes the registered handler with `WebhookMetadata`'s `shop` field set to `victim.myshopify.com`, even though Shopify never issued this webhook for that shop. [6](#0-5)
