Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches the handler using a `shop` value that is taken from an HTTP header which is never included in the signed bytes. Any party who can obtain one validly-signed webhook body (e.g., by installing the app on their own store) can replay that exact body with a forged `shop` header pointing at a victim shop, and the gem will treat it as an authentic webhook for the victim tenant.

### Finding Description
`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [1](#0-0) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, and `webhook_id` are parsed independently from HTTP headers with no cryptographic binding to the signature [3](#0-2) .

This is the exact bug class described in the report: a field (`quitPeriod`/here, `shop`) is acted upon by privileged logic but is not covered by the authenticity check (`onlyOwner`/here, HMAC). Contrast this with `Auth::Oauth::AuthQuery`, where `shop` is explicitly folded into the signed string via `to_signable_string`, correctly binding the shop identity to the HMAC [4](#0-3) . The webhook path lacks this equivalent binding.

`Registry.process` then uses this unauthenticated `shop` value directly to build the data passed to the app's handler: [5](#0-4) 

The binding that should hold is:
`hmac_valid(raw_body, secret) == true` should imply `shop == the tenant the body actually originated from`.
In this gem, `hmac_valid` only certifies `raw_body`; `shop` is asserted independently from an attacker-controlled header, so the equality does not hold — `shop` can be any value the caller supplies while `hmac_valid` still returns `true` for a body signed for a *different* shop.

### Impact Explanation
Because Shopify signs webhook payloads using the app's single `client_secret` (shared across all shops that installed the app, not per-shop), an attacker who legitimately installs the app on their own shop can capture one of their own valid webhook deliveries (valid body + valid HMAC). They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` (it only checks `raw_body`), and `Registry.process` will invoke the app's handler with `shop: <victim-shop>` [6](#0-5) . Any app logic that uses this `shop` value to look up per-tenant sessions, update tenant-scoped records, or act on behalf of "the shop that sent this webhook" is now operating on the wrong tenant using attacker-supplied body content — a cross-tenant data integrity/access violation.

### Likelihood Explanation
Requires only an attacker who can install the app on a shop they control (a normal, unprivileged action available to any Shopify merchant/developer for public or even development apps) and the ability to send an HTTP request to the app's public webhook endpoint with a captured body and forged header — no access token, `client_secret`, or privileged account needed. This satisfies the "unprivileged-internet-user" and "no privileged access" constraints.

### Recommendation
Bind the shop identity to the HMAC by including `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the bytes that are verified — either by mirroring Shopify's Admin webhook signing scheme if it covers headers, or by making `Webhooks::Request#to_signable_string` incorporate a canonicalized representation of these header values so a mismatch between the signed shop and the presented shop is rejected. At minimum, document that consuming code must independently authenticate the `shop` value (e.g., cross-check against a known set of installed shops) before trusting the webhook's shop attribution.

### Proof of Concept
1. App installs valid webhook handler via `Registry.add_registration` for topic `orders/create`.
2. Attacker's own shop `attacker.myshopify.com` triggers `orders/create`; Shopify delivers a webhook with body `B` and header `x-shopify-hmac-sha256` = HMAC(`client_secret`, `B`) and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this request, then POSTs to the app's webhook endpoint again with the same body `B` and same HMAC header, but with `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` computes `compute_signature(B, secret)` — unchanged since raw_body is identical — and returns `true` [1](#0-0) .
5. `Registry.process` calls the app's handler with `shop: "victim.myshopify.com"` and the attacker-controlled body `B`, even though this data never originated from `victim.myshopify.com` [6](#0-5) .
