### Title
Webhook shop-domain tenant attribution not covered by HMAC, enabling cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator.validate`, which HMACs `to_signable_string`. For webhook requests, `to_signable_string` returns only the raw request body [1](#0-0)  while the `shop` (tenant identity) is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, a field that is never included in the HMAC-signed payload [2](#0-1) .

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against `verifiable_query.hmac` using `OpenSSL.secure_compare` [3](#0-2) . `Registry.process` gates all webhook processing solely on this check: `raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)`, and then builds `WebhookMetadata` directly from `request.shop`, `request.topic`, and `request.parsed_body`, passing it straight to the app's handler [4](#0-3) .

The intended equality this mechanism should enforce is:
`shop_used_by_handler == shop_that_Shopify_actually_sent_the_signed_body_for`

But because `Request#to_signable_string` only returns `@raw_body` (never `@headers`) [1](#0-0) , the HMAC only binds the body bytes to the shared secret — it says nothing about which shop the body belongs to, nor which topic. `shop` and `topic` are both parsed straight from attacker-controllable HTTP headers [5](#0-4) .

Any internet user who runs the app on their own store (a legitimate, unprivileged install) receives real webhook deliveries from Shopify: a body + a valid `x-shopify-hmac-sha256` value + `x-shopify-shop-domain: their-shop.myshopify.com`. Because the signature never covered the shop header, that same `(raw_body, hmac)` pair remains valid when replayed to the app's webhook endpoint with the header rewritten to `x-shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still succeeds (it only re-hashes `raw_body`), and `Registry.process` hands the handler `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, body: <attacker's own body>)` [6](#0-5) . The documented handler contract explicitly trusts `data.shop` as the tenant identity for downstream persistence/enqueue calls (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [7](#0-6) , so this directly injects attacker-controlled data (including mandatory-compliance topics like `customers/redact`, `shop/redact`, `customers/data_request`) under an arbitrary victim shop's identity [8](#0-7) .

This is the exact "field acted on but not covered by the HMAC" analog of the report's binding failure: the report showed a plot identity check that answers permissively for an out-of-range/zero value; here the shop-identity binding is entirely absent from the signed material, so it answers permissively for any header value the attacker chooses.

### Impact Explanation
This crosses a tenant boundary using only an unprivileged app install the attacker already legitimately controls (no `api_secret_key`, no access token, and no privileged account needed) — it lets one merchant's real, validly-signed webhook traffic be replayed and reattributed to any other shop domain, corrupting that victim shop's data/state in the host application (cross-tenant access/data injection). Because the gem itself performs the trust decision (`HmacValidator.validate` → `Registry.process` → `WebhookMetadata`), this is a defect in the gem's own authentication logic, not merely a documentation gap that a diligent host could fix by revalidating on their own — the gem presents `shop` as an already-authenticated field.

### Likelihood Explanation
Likelihood is high for any app owner (attacker) who has installed the target app on a shop they control: they need only capture one legitimate webhook delivery (body + `hmac-sha256` header) and replay it to the same public webhook endpoint with a modified `shop-domain` (and optionally `topic`) header. No cryptographic secret, brute force, or privileged access is required.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signed material for webhook `Request` objects, e.g. compute the signature over a canonical string combining the raw body with the shop/topic headers rather than the raw body alone, or otherwise cryptographically bind those headers before trusting them in `to_signable_string`. At minimum, document/enforce that `shop`/`topic` must not be trusted until independently reconciled against the app's own webhook registration/subscription records for that shop.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook (e.g. `customers/data_request`) to the app's registered callback URL. Attacker captures the full raw body `B` and the `x-shopify-hmac-sha256` header value `H` from that legitimate request.
2. Attacker sends a new POST to the same webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (changed)
   - Header `x-shopify-topic`: unchanged or attacker's choice among registered topics
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `hmac` returns the decoded `H`; `to_signable_string` returns `B` [9](#0-8) .
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` with the app's `api_secret_key` and compares to `H` via `OpenSSL.secure_compare` — this passes because `B` and `H` are the same values Shopify actually signed [10](#0-9) .
5. `Registry.process` proceeds and invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <parsed B>, ...)` [6](#0-5) , causing the host app to process attacker-controlled data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
