Audit Report

## Title
Sensitive fields (e.g. GraphQL `password` inputs) nested under top-level JSON keys bypass log redaction, causing cleartext credential disclosure in debug logs - (File: core/web/router.go)

## Summary
Chainlink's HTTP request-logging middleware `loggerFunc` sanitizes request bodies before logging them at Debug level, but the sanitization function `readSanitizedJSON` only inspects top-level JSON keys against a `password`-substring blacklist. GraphQL mutations such as `createAPIToken`/`deleteAPIToken` carry the `password` field nested inside `variables.input`, so it is never redacted and is written verbatim to the Debug log.

## Finding Description
`readSanitizedJSON` unmarshals the request body into a flat `map[string]any` and only checks `isBlacklisted` against the first-level keys, copying any nested object or array value unmodified into the cleaned map before marshaling it back for logging: [1](#0-0) . This function is invoked via `readBody`, which is called from `loggerFunc`, a middleware registered globally on the gin engine and thus applied to every route, including `POST /query`: [2](#0-1)  and [3](#0-2) . The actual Debug log write, including the sanitized body, happens in [4](#0-3) .

The GraphQL schema defines `CreateAPITokenInput.password` and `DeleteAPITokenInput.password` as nested input fields, confirmed present in `core/web/schema/type/api_token.graphql`. A GraphQL POST body for these mutations has the shape `{"query": "...", "variables": {"input": {"password": "..."}}}`, so the `password` key is nested under `variables`, not top-level, and the flat blacklist check in `isBlacklisted` ( [5](#0-4) ) never examines it. This confirms the flat-only redaction check does not cover nested GraphQL payloads, unlike flat REST bodies (e.g. `/v2/user/password`) whose sensitive keys are top-level and correctly redacted by the same mechanism.

## Impact Explanation
This is a genuine, code-level confidentiality flaw (CWE-532, cleartext logging of sensitive information) reachable by any authenticated API user who calls `createAPIToken`/`deleteAPIToken` while the node runs with Debug-level logging enabled. Password disclosure in logs — which are frequently shipped to centralized aggregators or broader operational teams than credential stores — is a legitimate, concrete impact class involving credential/secret exfiltration through the node's own logging code, not through operator misconfiguration of an unrelated system.

## Likelihood Explanation
The vulnerability requires two preconditions: Debug-level logging enabled (a supported, documented configuration, not a privileged/host-only mode) and a valid authenticated session capable of calling the GraphQL mutation, which is the same minimal credential level required for the equivalent REST password-change endpoint. Given those preconditions, every invocation of the affected mutations deterministically leaks the password in cleartext with no additional attacker effort, making the flaw fully reproducible and systemic rather than speculative.

## Recommendation
Modify `readSanitizedJSON` (and its blacklist check) to recursively traverse nested JSON objects and arrays, redacting any key matching the `password` substring rule at any nesting depth, so fields like `variables.input.password` in GraphQL requests are redacted the same way flat REST body fields are. As a defense-in-depth alternative, apply GraphQL-schema-aware redaction to strip known sensitive input types before logging.

## Proof of Concept
1. Start a Chainlink node with `logging` level set to `debug`.
2. Authenticate as any node user to obtain a valid session cookie.
3. Send:
   ```
   POST /query
   Content-Type: application/json
   Cookie: clsession=<valid session>

   {"query":"mutation($input: CreateAPITokenInput!){ createAPIToken(input: $input){ ... on CreateAPITokenSuccess { token { accessKey secret } } } }",
    "variables":{"input":{"password":"MyS3cretPassw0rd!"}}}
   ```
4. Inspect the node's Debug log output produced by `loggerFunc`'s `"body"` field for this request; it will contain `"variables":{"input":{"password":"MyS3cretPassw0rd!"}}` in cleartext, whereas the equivalent field in a `/v2/user/password` REST request body would be shown as `*REDACTED*`.

```go
func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}
```

```go
// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
```
