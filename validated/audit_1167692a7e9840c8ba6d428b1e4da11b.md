### Title
Emporium Min-path (`externalActionId == HINKAL_EMPORIUM_ACTION_ID` with `erc20TokenAddresses.length == 0`) allows unauthenticated, repeatable draining of any funds sitting on the Emporium contract - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `formInputForCircom` routes to `formInputEmporiumMin` (i.e. `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`), the circuit used is `MainEVMCircuitMin`, which only proves knowledge of a Poseidon preimage (`messageSeed`) bound to an attacker-chosen `emporiumMessage`/`calldataHash`. Because `erc20TokenAddresses` is empty, every balance-accounting loop in `EmporiumUpgradeable.runAction` and in `Hinkal.transact` iterates zero times, so the arbitrary `stack.ops` calls executed by `EmporiumUpgradeable` are never checked against any balance-conservation equality, letting anyone drain whatever ERC20/ETH balance currently sits on the Emporium contract, repeatably, with a fresh `emporiumMessage` each time.

### Finding Description
The intended equality (enforced for the "normal" path) is: for every declared token `i`,
`balanceAfter[i] - balanceBefore[i] (+/- deltaAmountChanges[i]) == 0`, checked in `EmporiumUpgradeable.runAction`: [1](#0-0) 

This loop is bounded by `circomData.erc20TokenAddresses.length`. The attacker controls this array as part of `CircomData` and chooses length `0` in order to route to the Min circuit path: [2](#0-1) 

`MainEVMCircuitMin` does not constrain `tokenCount`, `erc20TokenAddresses`, `amountChanges`, nullifiers or output commitments at all - it only proves `message == Poseidon(messageSeed)` bound to `outTimeStamp`/`calldataHash`: [3](#0-2) 

`dimensionsCheck` in `HinkalHelper` permits `dimensions.tokenNumber == 0` (all the length-equality requires are vacuously satisfied by empty arrays), and `checkOnchainCreation` similarly loops zero times: [4](#0-3) 

In `EmporiumUpgradeable.runAction`, `verifyWallet` is the only gate before executing `stack.ops`. If the attacker sets `stack.signerAddress == address(0)`, `verifyWallet` marks `usedMessages[circomData.emporiumMessage] = true` and returns immediately - no EIP-712 signature is checked at all: [5](#0-4) 

With `signerAddress == address(0)`, every op goes through "CASE 2: Stateless Interaction", executing `op.endpoint.call{value: op.value}(op.callData)` directly, with only a check against re-entering the wallet-specific selectors: [6](#0-5) 

Because `circomData.erc20TokenAddresses.length == 0`, `balancesBefore`/`balancesAfter` are empty arrays and the post-loop balance-conservation check (lines 132-151) never runs, so any token the attacker's op transfers out of the Emporium's own balance (e.g. calling the ERC20 token contract's `transfer(attacker, balance)` as `endpoint`, with `msg.sender` being the Emporium contract) is completely unconstrained by both the circuit and the Solidity accounting. `Hinkal.transact`'s own balance/slippage checks are likewise indexed only over `circomData.erc20TokenAddresses`, so they add no protection for a token not listed there: [7](#0-6) 

Since `emporiumMessage` is entirely attacker-chosen (and `messageSeed` is the attacker's own private witness, trivially satisfying `message <== Poseidon(1)([messageSeed])` for any target value they pick), the `usedMessages` replay guard never blocks a new attack: the attacker simply picks a new `emporiumMessage`/`messageSeed` pair for every call. No leaf, nullifier, or signature is consumed or checked at all in this path.

**The broken equality:** intended invariant `Σ_i (balanceAfter[i]-balanceBefore[i])` accounted against `deltaAmountChanges[i]` for all tokens actually moved by `stack.ops` == `0`. In practice this is only checked for `i ∈ [0, erc20TokenAddresses.length)`, and the attacker sets `erc20TokenAddresses.length = 0`, making the check vacuous while real token movement (out of Emporium's own held balance) is nonzero.

### Impact Explanation
Any ERC20/ETH balance that accumulates at the Emporium contract's address (from prior legitimate stateless interactions, leftover dust, or funds sent there by any means) can be swept to an attacker-controlled address via a crafted `stack.ops` call, with zero authentication (no signature, no nullifier, no UTXO spend) and zero balance-conservation enforcement. This is repeatable indefinitely - each call only requires a fresh, self-chosen `emporiumMessage`/`messageSeed` pair and a proof for the (presumably registered) zero-dimension Min verifier. This is direct theft of funds held at a Hinkal-controlled contract address, matching the Critical category (direct theft of shielded/in-flight funds via a verification bypass, since no nullifier/leaf is ever checked for this path).

### Likelihood Explanation
Preconditions: (1) the zero-dimension (`tokenNumber=0`, `nullifierAmount=0`, `outputAmount=0`) verifier for `HINKAL_EMPORIUM_ACTION_ID` must be registered on-chain (this is the verifier the Min circuit exists to serve, so it is expected to be part of normal deployment for the Emporium's stateless flow), and (2) the Emporium contract must currently hold a nonzero balance of some token (which happens naturally whenever previous stateless CASE-2 ops route funds through it, or any accidental/intermediate transfer). Attacker cost is a single locally-generated Groth16 proof for a trivial circuit (Poseidon preimage of a self-chosen value) plus gas - no special role, key, or knowledge of any victim's UTXOs is required. Repeatable without bound.

### Recommendation
Reject the Min-path entirely for `runAction`, or explicitly forbid `stack.ops` from touching balances not accounted for: require `circomData.erc20TokenAddresses.length > 0` whenever `stack.ops` contains any external call capable of moving value, and/or have `EmporiumUpgradeable.runAction` snapshot and re-verify the Emporium's own balance for every ERC20/ETH token referenced by `op.endpoint`/`op.callData`, not merely those listed in the caller-supplied `erc20TokenAddresses` array. Additionally, remove the unauthenticated "return early" branch in `verifyWallet` for `signerAddress == address(0)` unless there's a hard guarantee that no `op` executed in that mode can access funds already resident at the Emporium's address.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as `HINKAL_EMPORIUM_ACTION_ID` external action) and register a verifier for `buildVerifierId(dimensions{tokenNumber:0,nullifierAmount:0,outputAmount:0}, HINKAL_EMPORIUM_ACTION_ID)` pointing at a real `MainEVMCircuitMin`-derived Groth16 verifier.
2. Fund the Emporium contract with `X` tokens (e.g. via any transfer or a legitimate prior stateless op leaving dust).
3. Attacker (unprivileged EOA) builds `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one op: `endpoint = tokenAddress`, `callData = transfer(attacker, X)`.
4. Generate `messageSeed`, compute `emporiumMessage = Poseidon(messageSeed)` locally, generate a valid proof for the Min circuit.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` - assert it succeeds and `token.balanceOf(Emporium) == 0`, `token.balanceOf(attacker) == X`.
6. Repeat steps 2-5 with a new `messageSeed2`/`emporiumMessage2` against freshly-arrived funds at the Emporium - assert it succeeds again (draining twice), proving `usedMessages` never blocks the attack and the balance-conservation loop (`EmporiumUpgradeable.sol:132-151`) never executes (assert both sides of the "intended" balance equality: `balanceBefore == balanceAfter` computed over the *actual* token used in the op, not over the empty declared array, diverge by `X` each time with no revert).
