### Title
`SessionUtils.current_session_id` trusts an unsigned, format-predictable cookie value as a session identity, allowing cross-tenant session hijacking on non-embedded apps - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps, `SessionUtils.current_session_id` resolves the active session purely by reading `cookies[SESSION_COOKIE_NAME]` via `cookie_session_id` and returning it verbatim, with no signature, no ACL, and no binding check to the requester. Because `Auth::Oauth.validate_auth_callback` sets that cookie's *value* to `session.id`, which is itself a fully deterministic, non-secret string (`"offline_#{shop}"` for offline sessions, or `"#{shop}_#{user_id}"` for online sessions), any attacker who can guess or observe another shop's domain can construct that exact cookie value and use it to have the host app resolve and use shop B's stored `OfflineSession`/access token.

which is a pure hash lookup with no owner/ACL/signature verification, called from `current_session_id`'s non-embedded branch: [2](#0-1) 

The cookie's *value* is not a random opaque token — it is set to the real session id at OAuth completion time: [3](#0-2) 

and the session id itself is generated deterministically from public information (the shop's `myshopify.com` domain) with no secret material: [4](#0-3) 

`SessionCookie` itself is a plain `T::Struct` with `name`/`value`/`expires` — no HMAC, no encryption, no nonce tied to a specific browser/session: [5](#0-4) 

Exploit flow: an attacker who has learned shop B's `myshopify.com` domain (from a support ticket, log line, or simply because it's a legitimate installed shop and domains aren't secret) computes `offline_#{shop_b_domain}` themselves — no `api_secret_key` or leaked token needed, since the format string is public in the gem's own source/docs. They then send an HTTP request to the target app's non-embedded endpoint with `Cookie: shopify_app_session=offline_shop-b.myshopify.com`. If that endpoint calls `SessionUtils.current_session_id(nil, cookies, false)`, the method returns `"offline_shop-b.myshopify.com"` verbatim — indistinguishable from a value legitimately set for a browser that actually completed shop B's OAuth flow. The host app then looks this id up in its session storage and, if shop B has installed the app, retrieves shop B's real `OfflineSession` (with its access token) and serves the attacker's request using it.

None of the gem's existing guards intervene here: `HmacValidator.validate`, `ShopValidator.sanitize!`, and the OAuth `state` comparison only apply to the `/oauth/callback` path, not to this cookie-lookup path; `JwtPayload`'s `aud` check only applies to the embedded/JWT branch; `Context.setup?`/`private?`/`embedded?` only gate feature availability, not per-request identity; Sorbet signatures only enforce types (`String`, `Hash`), not authorization.

### Impact Explanation
An attacker gains the ability to make the host app act as shop B (using shop B's stored offline access token) purely by knowing/guessing shop B's shop domain string — no secret, no token, no prior relationship with shop B is required. This is repeatable against any installed shop whose domain the attacker can learn, and the blast radius is cross-tenant: shop A's user reaches shop B's data/actions. This matches the **Critical — cross-tenant access** category.

### Likelihood Explanation
Preconditions: (1) the host app must be non-embedded and rely on this gem's documented `current_session_id(nil, cookies, ...)` cookie path, and (2) the host app must relay the raw cookie to the gem without adding its own independent tamper-protection (e.g., a signed/encrypted session mechanism around the cookie value) — which is exactly the flow documented in `docs/getting_started.md`. Shop domains (`*.myshopify.com`) are not secret; they are often visible in URLs, admin links, support tickets, or guessable from a merchant's storefront/custom domain. Attacker cost is a single crafted HTTP header — trivially cheap and fully repeatable against any shop whose domain is known.

### Recommendation
Do not use the deterministic session id as the cookie's literal value. Instead, generate a random, unguessable, per-browser opaque token at cookie-set time, store a server-side mapping from that opaque token to the real session id (or sign/encrypt the cookie value with a secret so it cannot be forged or predicted), and validate that mapping/signature inside `cookie_session_id` before trusting it as a session identifier. At minimum, document prominently that hosts MUST use a cryptographically signed/encrypted cookie jar (never a raw Rack cookie) for `SESSION_COOKIE_NAME`, since this gem's own `cookie_session_id` performs no integrity or ownership check whatsoever.

```ruby
# test/utils/session_utils_test.rb (additional test)
def test_cookie_session_id_accepts_forged_predictable_offline_id_with_no_ownership_check
  ShopifyAPI::Context.stubs(:embedded?).returns(false)

  victim_shop = "victim-shop.myshopify.com"
  forged_session_id = "offline_#{victim_shop}" # fully derivable from public shop domain,
                                                # matches SessionUtils.offline_session_id format exactly

  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_session_id }

  # No HMAC, no owner check, no api_secret_key involved anywhere in this call:
  resolved = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  assert_equal(forged_session_id, resolved)
  # Demonstrates: cookie_session_id/current_session_id perform a bare hash lookup;
  # any caller who can predict/guess a target shop's offline session id string
  # (a pure function of the public shop domain) obtains a session id indistinguishable
  # from one legitimately issued to that shop's own authenticated browser.
end
```
