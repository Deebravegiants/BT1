### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` value handed to the webhook handler is read from the unauthenticated `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` only proves that the *body* was signed by Shopify with the app's `api_secret_key`; it says nothing about which shop the header claims the body belongs to. Any party able to obtain one validly-signed webhook (e.g. by installing the app on their own store and triggering a webhook) can replay that exact body/HMAC pair while substituting an arbitrary victim shop domain in the header, and the app-supplied handler will process the data as if it belongs to the victim tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the (unsigned) `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` verifies only the HMAC of the request, then forwards `request.shop` (the header value) straight to the app's handler as the tenant identifier, with no cross-check that this shop is bound to the signed body: [3](#0-2) 

`HmacValidator.validate` only confirms `computed_signature(verifiable_query.to_signable_string, secret) == received_signature`, i.e. it authenticates the body bytes, not the shop attribution: [4](#0-3) 

The broken identity binding is:
`shop authenticated by HMAC` (nothing — shop is outside the signed content) ≠ `shop attributed to the webhook data` (`request.shop`, taken from an attacker-controllable header).

Because any user can install the app on their own development/test store, they can legitimately receive a validly-signed webhook body+HMAC pair for data they control. Since the header carrying the shop domain is excluded from the signed payload, that same body/HMAC pair remains valid when the header is rewritten to name a different (victim) shop. The app's webhook handler — which typically uses `shop` to select which tenant's records to update — will then act on the victim shop using data that actually originated from the attacker's own store.

### Impact Explanation
This breaks the multi-tenant isolation guarantee that `Registry.process`'s API promises: successful HMAC validation should mean "this webhook genuinely originates for the named shop." An attacker can inject or overwrite arbitrary application state under another merchant's identity (cross-tenant access) without needing that merchant's access token, `client_secret`, or any credential belonging to the victim — only their own, legitimately-installed instance of the app. This satisfies the "cross-tenant access" Critical-impact criterion.

### Likelihood Explanation
Medium/High: exploitation requires only that the attacker be able to install/uninstall the target app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer) and be able to send a crafted HTTP request with a legitimate HMAC/body pair but a rewritten shop header to the app's public webhook endpoint. No secrets, tokens, or privileged access to the victim's account are required.

### Recommendation
Bind the shop identity into the verified content, not just the payload bytes:
- Include the `X-Shopify-Shop-Domain` (and ideally `X-Shopify-Webhook-Id`/`X-Shopify-Topic`) header value in the string that is HMAC-verified, or
- Require the caller (or `Registry.process`) to independently confirm that `request.shop` matches the shop associated with the session/store that is expected to receive this specific webhook subscription (e.g., cross-reference against the shop for which the webhook was registered) before invoking the handler.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook subscription (e.g. `products/update`).
2. Shopify sends the app a webhook: `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>`, with `raw_body` containing attacker-crafted content.
3. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
4. Attacker sends a new HTTP request directly to the app's webhook endpoint, keeping `raw_body` and the HMAC header identical, but replacing `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unchanged) raw body against the (unchanged) HMAC.
6. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled data>, ...)` and processes/persists it as if it came from the victim's store.
