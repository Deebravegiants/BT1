### Title
Webhook HMAC only signs the request body, letting the `shop`, `topic`, `webhook-id`, and `api-version` headers be forged for cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate` verifies nothing but the JSON payload bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which `Registry.process` trusts unconditionally and hands to the host app's `WebhookHandler` as the tenant/identity for the event — are never covered by the signature. This is the same class of bug as the reported "missing approval path": a security-relevant action (attributing an event to a shop) is bound to a check (HMAC) that doesn't actually cover the field being acted on (the shop header).

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `hmac`/`shop`/`topic`/`webhook_id`/`api_version` are all read straight from HTTP headers with no cryptographic tie to the body: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string`, i.e. `@raw_body`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to trust every other field of the request, including `request.shop`, and forwards them into `WebhookMetadata`, which is exactly what host apps use to determine which tenant/store the event belongs to: [4](#0-3) [5](#0-4) 

Because the HMAC is only computed over the body, `shop == HMAC-bound shop` does not hold: a caller who possesses one genuine `(body, hmac)` pair for shop A (e.g. an attacker who installed the app on their own shop and legitimately receives a real webhook, or captured one via any other legitimate channel) can replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting `shopify-shop-domain: victim-shop.myshopify.com` (and freely choosing `topic`/`webhook-id`/`api-version`). `HmacValidator.validate` still returns `true` because the signature only checks `@raw_body`, which is unchanged. The webhook handler then receives `data.shop == "victim-shop.myshopify.com"` with a payload the attacker fully controls (their own shop's data), causing the host app to process/store attacker-controlled data under a victim tenant's identity — a direct violation of the shop-tenant boundary that the HMAC is presumed to guarantee.

### Impact Explanation
This breaks the identity binding "shop authenticated == shop the event is attributed to." Any app relying on `ShopifyAPI::Webhooks::WebhookHandler#handle`'s `data.shop` to scope database writes, cache invalidation, billing, or other side effects per tenant (as documented and demonstrated in `docs/usage/webhooks.md`) can be made to apply attacker-supplied webhook bodies to an arbitrary victim shop's records, i.e. cross-tenant data injection/corruption — meeting the "cross-tenant access" critical-impact bar.

### Likelihood Explanation
Exploitation only requires the attacker to obtain one legitimate `(body, hmac)` pair for the shared `api_secret_key` — trivially available to any merchant who installs the app on their own store, since every webhook it/she receives is a valid signed body. No access to the app's `api_secret_key`, access tokens, or the victim's credentials is needed; the webhook endpoint is a public, unauthenticated HTTP endpoint by design.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string (or otherwise bind them cryptographically to the payload/session), matching how Shopify actually computes its signature, so `to_signable_string` can't be satisfied while these fields are swapped independently of the body.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and lets a real webhook fire; they capture the raw body `B` and the valid `hmac-sha256` header `H` Shopify sent for it.
2. Attacker POSTs to the app's webhook endpoint with body `B`, header `hmac-sha256: H` (unchanged, still valid for `B`), but `shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31) succeeds because it only hashes `B`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) calls the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, and the host app processes attacker data as if it belonged to `victim.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
