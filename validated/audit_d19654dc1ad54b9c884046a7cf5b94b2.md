### Title
Webhook shop identity (`shop-domain` header) is not covered by the HMAC signature, allowing cross-tenant spoofing when body content is shared/predictable - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Registry.process` authenticates only the raw JSON body via `Utils::HmacValidator.validate(request)`, whose signable content is `Request#to_signable_string`, i.e. `@raw_body` alone. The shop identity (`request.shop`, taken from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is never part of the signed bytes, yet it is passed straight to the app's `WebhookHandler` as the authoritative tenant identifier.

### Finding Description
The binding that should hold is:
`HMAC-verified bytes == bytes the app trusts for the tenant (shop) identity`

In `lib/shopify_api/webhooks/request.rb`: [1](#0-0) 
`shop` is read from a header, while: [2](#0-1) 
`to_signable_string` — the only thing verified by HMAC — is just `@raw_body`.

In `lib/shopify_api/webhooks/registry.rb`: [3](#0-2) 
`process` validates the HMAC over the body only, then immediately forwards `request.shop` (the unauthenticated header value) to the handler as the trusted `shop` for that webhook event.

Because the webhook HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every merchant that installs the app, an attacker who controls their own shop installation can capture a legitimate, validly-signed webhook body (same `client_secret` HMAC over that body content is reproducible/predictable for events they control, e.g. `shop/redact`, `orders/create` with attacker-controlled content) and resend the request with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header changed to a victim shop's domain. Since `shop` is not part of `to_signable_string`, the HMAC still validates, and `Registry.process` dispatches the forged event to the host app's handler labeled as coming from the victim shop.

### Impact Explanation
This breaks the tenant-isolation equality the library is expected to enforce for its own webhook-processing API: "HMAC-authenticated payload" should equal "payload attributed to the shop the app acts on". A cross-tenant identity confusion here lets a malicious merchant impersonate another shop's webhook stream, causing the host app to execute tenant-scoped business logic (e.g., data deletion for `shop/redact`, order processing, GDPR handlers) against the wrong tenant's data — a cross-tenant access vulnerability per the in-scope impact list.

### Likelihood Explanation
Requires only what any unprivileged internet user with an app installation can obtain: their own shop's valid webhook deliveries (no leaked secrets, no access token, no privileged account) and the ability to POST directly to the app's public webhook endpoint with modified headers. This is fully reachable without TLS interception or social engineering, satisfying the "unprivileged-internet-user" analog requirement.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the HMAC-signable string, or otherwise cryptographically bind the header-derived `shop` value to the signed payload before it's handed to `WebhookHandler#handle`. At minimum, document/require host applications to cross-check `request.shop` against their own installation record before trusting it, since the gem currently provides no such binding.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`, receives a legitimate webhook POST with header `shopify-shop-domain: attacker.myshopify.com`, body `B`, and valid `shopify-hmac-sha256` computed as `HMAC(client_secret, B)`.
2. Attacker replays the exact same request to the app's webhook endpoint but rewrites the `shopify-shop-domain` header to `victim.myshopify.com`, leaving body `B` and the HMAC header untouched.
3. `Request#hmac` and `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:11-38`) only look at `@raw_body`; `Utils::HmacValidator.validate` succeeds because the body/HMAC pair is unchanged.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190-199`) accepts the request and calls `handler.handle` with `shop: request.shop` = `"victim.myshopify.com"`, even though the payload was never actually associated with that shop by Shopify.
