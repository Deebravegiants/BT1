### Title
Permanently frozen escrow when the settlement beneficiary is a blacklisted ERC20 address — ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` (and its Tron/legacy analog `IntentGatewayV2.withdraw`) unconditionally pushes escrowed ERC20 tokens to a `beneficiary` address derived from a cross-chain settlement message. If that token has a blacklist/freeze mechanism (e.g., USDC), and the beneficiary address is or becomes blacklisted, the transfer reverts every time the message is delivered, permanently freezing the escrowed funds with no admin bypass or alternate-beneficiary recovery path — the same root cause as Notional's M-5 (`TokenHandler.withdrawPrimeCash` rejecting settlement when the account is blacklisted).

### Finding Description
When a cross-chain order is redeemed or refunded, the source-chain `IntentGatewayV2`/`ExtrinsicIntents` contract receives a `RedeemEscrow` or `RefundEscrow` `PostRequest` through `onAccept`, which calls `_withdraw`: [1](#0-0) 

The beneficiary comes directly from the message body — the filler's address for `RedeemEscrow`, or the original order creator for `RefundEscrow`: [2](#0-1) [3](#0-2) 

`_withdraw` uses `IERC20(token).safeTransfer(beneficiary, amount)` with no fallback, no try/catch, and no way to redirect to a different address. The legacy/Tron variant is even more explicit about the failure mode — a bare low-level `.call` to `transfer` that reverts the whole `withdraw()` on failure: [4](#0-3) 

This `onAccept` call is invoked by `EvmHost.dispatchIncoming`, which wraps the module call in a low-level `.call` and, on failure, deletes the request receipt so the message stays "undelivered" and can be retried indefinitely — it does **not** revert the whole batch, and it never gives up on the delivery: [5](#0-4) 

Because the beneficiary address is fixed by the original message (the filler's `msg.sender` at fill time for redemption, or `order.user` for refund) and cannot be substituted, if that address is ever blacklisted by the escrowed ERC20's issuer (e.g. USDC), every retry of `handlePostRequests`/`dispatchIncoming` for that commitment will revert inside `safeTransfer`, and the escrow can never be released. There is no governance/admin path in `IntentsBase`/`IntentGatewayV2` to force-settle a stuck order to an alternate beneficiary or to skip the transfer — `SweepDust` only moves protocol-fee dust, not user escrow tied to a `_orders[commitment][token]` entry.

### Impact Explanation
This causes concrete, permanent freezing of user/solver funds:
- A solver who legitimately filled a cross-chain order and is owed escrowed input tokens on the source chain can never claim them if their own address is later blacklisted on that token (a real-world event for USDC addresses flagged by Circle/OFAC).
- A user whose cancelled/expired order is being refunded loses access to their own escrowed tokens if their address becomes blacklisted on the input token before the refund lands, with no recovery mechanism.
- The message is retried forever but will always fail identically, so the funds are locked indefinitely (matches the "permanent freezing of funds" acceptance criterion).

### Likelihood Explanation
Requires no attacker action beyond normal usage of a blacklistable ERC20 (e.g., USDC) as an order input — a common configuration for the Intent Gateway. The trigger condition (the beneficiary address getting blacklisted between order placement/fill and settlement) is realistic given increasing use of address-freezing stablecoins, and the design offers zero mitigation once it occurs.

### Recommendation
Add a fallback path analogous to what Notional was advised: allow an authorized recovery mechanism (e.g., governance-only `Execute` action or a dedicated rescue function) to redirect a stuck withdrawal to a new beneficiary address, or wrap the token transfer in a try/catch that, on failure, credits the amount to an internal claimable balance the affected party can later withdraw to a different address — mirroring the pattern already used in `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`, which fall back to re-wrapping and an alternate transfer path when a native-ETH push fails, rather than reverting unconditionally.

### Proof of Concept
1. Deploy `IntentGatewayV2` with USDC as an order input token.
2. User places a cross-chain order with USDC as input; solver fills it on the destination chain, dispatching `RedeemEscrow` with `beneficiary = solver`.
3. Before the settlement message is delivered/retried on the source chain, USDC's issuer blacklists the solver's address (or the solver's address was already blacklisted).
4. Any relayer calls `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `IntentGatewayV2.onAccept` → `_withdraw`, which calls `IERC20(usdc).safeTransfer(solver, amount)`; this reverts because the recipient is blacklisted.
5. `EvmHost.dispatchIncoming` catches the failure, deletes the request receipt, and returns — the message remains "undelivered" and can be resubmitted, but step 4 will always fail identically, permanently freezing the escrowed USDC with no recovery path in the contract.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {

            uint256 amount = body.tokens[i].amount;

            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
