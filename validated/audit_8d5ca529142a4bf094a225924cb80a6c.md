### Title
Direct token-donation into the curve `Pair` breaks the `_computeBuy` overflow-cap invariant, causing buys to permanently revert (arithmetic-underflow panic / `OverflowCapDegenerate`) and bricking curve exhaustion / graduation - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` caps `tokensOut` at the pair's real ERC20 balance (`pair.tokenBalance()`) whenever the virtual curve math would ask for more tokens than physically exist, and back-derives `amountInUsed` from `cappedReserveToken = reserveToken - tokensOut` [2](#0-1) . This logic implicitly assumes `reserveToken - realBalance` is always the constant, positive `LP_RESERVE` gap that the honest curve mechanics preserve. Any unprivileged holder can violate that assumption with a plain `IERC20.transfer` of the launched `Token` directly into the `Pair`, inflating `tokenBalance()` (`realBalance`) without touching the pair's stored `_pool.tokenReserve`. Once enough tokens are donated to close or invert the gap, any future buy whose uncapped `tokensOut` exceeds `realBalance` hits `cappedReserveToken = reserveToken - tokensOut`, which either equals `0` (explicit `OverflowCapDegenerate` revert) or, if `realBalance > reserveToken`, underflows and reverts with an unchecked arithmetic panic — a crash class directly analogous to CVE-2023-51391's invalid-pointer dereference during "header" (input) processing: an unvalidated internal invariant is dereferenced/subtracted against attacker-influenced state and blows up instead of failing gracefully.

### Finding Description
The bonding curve keeps two parallel counters per token: the virtual `tokenReserve` stored in `Pair._pool` (only mutated by `Pair.swap`, which never observes real ERC20 balances) [3](#0-2) , and the real ERC20 balance of the launched `Token` sitting in the `Pair` contract, read via `tokenBalance()` [4](#0-3) . Under honest curve trading these two values are locked together by the invariant `reserveToken − realBalance == LP_RESERVE` (250M tokens, `25%` of supply) because every buy decrements both by the same `tokensOut`.

`Router._computeBuy` relies on this invariant staying positive to safely compute `cappedReserveToken = reserveToken - tokensOut` when the naive curve formula would exceed the real balance: [5](#0-4) 

Elsewhere in the same codebase, `Bonding.previewLtUntilGraduation` explicitly defends against a donation-inflated `realBalance` with `if (realBalance >= reserveToken) return ltUntilThreshold;` [6](#0-5) , proving the team is aware that `tokenBalance()` can be inflated by a direct donation — but this guard was not replicated inside `Router._computeBuy`.

An attacker (any wallet that has bought — or is the creator of — the launched token) can:
1. Acquire launched `Token` balance via ordinary curve buys (`Zap.buy`).
2. `transfer` (a plain ERC20 call, no protocol function needed) a sufficient amount of that `Token` directly to the token's `Pair` address, inflating `tokenBalance()` without changing `_pool.tokenReserve`.
3. Once cumulative donations close the `LP_RESERVE` gap (bring `reserveToken − realBalance` to `≤ 0`), any subsequent buy through `Zap.buy` → `Bonding.buy` → `Router.buy` → `_computeBuy` whose uncapped `tokensOut` exceeds the (now inflated) `realBalance` will revert — either via the explicit `OverflowCapDegenerate()` check (`cappedReserveToken == 0`) or, if the donation over-shoots (`realBalance > reserveToken`), via an **unchecked Solidity 0.8 arithmetic-underflow panic** on `reserveToken - tokensOut`, since `tokensOut` was just set to `realBalance`.

### Impact Explanation
Because the `LP_RESERVE` gap is a fixed constant baked in at launch and never restored (there is no sync/skim on the curve `Pair`, unlike the post-graduation HyperSwap pair which has `skim`), the corrupted invariant is permanent for that token's remaining life on the curve. This:
- Permanently reverts any buy attempt that would otherwise partial-fill the curve near exhaustion, blocking the supply-side graduation trigger (`IPair(pair).tokenBalance() == 0`) in `Bonding.canGraduate` [7](#0-6)  forever for that token, since the curve can never be fully drained through the reverting buy path.
- Leaves the creator's raised LT, the curve's tokens, and any trader capital already committed to that token permanently stuck on `Bonding`/`Pair` if the USD threshold leg (which is independent and may not be reachable either, depending on price) also isn't crossed — a permanent freeze of creator/trader/LP funds matching the required impact bar.
- Produces an unhandled Solidity panic (raw revert reason `0x11`) in the over-shoot case, i.e., an un-graceful crash directly analogous to the reported CVE's "invalid pointer dereference … permitting a device crash / DoS" class: an unvalidated internal assumption is dereferenced against attacker-influenced external state.

### Likelihood Explanation
The only capital required is enough launched-token balance to donate ~`LP_RESERVE` (250M of the 1B fixed supply) directly to the `Pair`; tokens can be accumulated cheaply early in the curve (lowest bonding-curve price band) and the `transfer` itself is a single unprivileged ERC20 call with no protocol gating (`Token` has no transfer hooks/allowlist). No collusion, no privileged role, and no race condition is needed — it is a straightforward, repeatable, permissionless action available to any trader or the token's own creator.

### Recommendation
Harden `Router._computeBuy` (and any other reserve-derived arithmetic that reads `pair.tokenBalance()`) to defensively clamp/guard against `realBalance >= reserveToken`, mirroring the guard already present in `Bonding.previewLtUntilGraduation`, and use a `Math`-style saturating subtraction instead of a raw `-` so a donation-corrupted balance degrades gracefully (e.g., treat the gap as `0` / fail with a clear custom error) rather than panicking or permanently blocking the exhaustion path. Consider also adding a `skim`-style sweep on the curve `Pair` (burn or route excess donated `Token` balance to the pair's true accounting) so `tokenBalance()` cannot silently exceed `tokenReserve`.

### Proof of Concept
1. Launch a token via `Zap.createToken`; note `LP_RESERVE = 250_000_000e18` and the pair's initial `tokenReserve = TOTAL_SUPPLY (1_000_000_000e18)`, `realBalance = curveSupply (750_000_000e18)` — an honest gap of exactly `LP_RESERVE`.
2. Attacker buys a meaningful amount of the launched token via `Zap.buy` (curve buys are cheapest early), accumulating a `Token` balance.
3. Attacker calls `IERC20(token).transfer(pairAddress, donationAmount)` directly (no protocol function), repeating/aggregating across wallets/buys until cumulative donations plus natural curve drain make `reserveToken (stored) − tokenBalance() (real) ≤ 0`.
4. Any subsequent `Zap.buy` call sized so that `Router._computeBuy`'s uncapped `tokensOut` exceeds the now-inflated `pair.tokenBalance()` triggers the cap branch; `cappedReserveToken = reserveToken - tokensOut` either reverts with `OverflowCapDegenerate()` or panics with underflow (`0x11`) if `realBalance > reserveToken`, permanently reverting that and all subsequent similarly-sized buys, blocking the `tokenBalance() == 0` graduation trigger for that token.

```text
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
```
