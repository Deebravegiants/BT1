### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-verifying the raw request body, then passes the `shop` value taken from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header straight to the app's webhook handler. Because the shop identity is never part of the signed material, an attacker who owns a legitimate, installed shop can obtain a validly-HMAC'd webhook body from Shopify for their own shop and replay it to the app's webhook endpoint with a forged `shop-domain` header naming a victim tenant, producing a request that passes signature verification while asserting a false tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers and are never included in the signed payload: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` verifies exactly this signable string (the raw body) against `Context.api_secret_key`: [4](#0-3) 

`Registry.process` uses this validation as its sole authenticity check, then constructs `WebhookMetadata` directly from the request's unauthenticated `shop` header and hands it to the app's handler: [5](#0-4) 

The documented handler contract explicitly tells integrators to trust `data.shop` as "The shop domain of the webhook" and to use it to key application state (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [6](#0-5) 

The identity binding broken here is an equality that the gem never checks:
`shop_that_authorized_the_bytes == shop_the_handler_is_told_the_bytes_belong_to`

Before the attack: a webhook for shop A arrives with body B and `hmac = HMAC(secret, B)` and header `shop-domain = A`. HMAC validation succeeds and `data.shop == A`, which is correct.

After the attacker's request: the attacker submits the same `(B, hmac)` pair (both legitimately obtained from their own shop A's webhook deliveries) but changes only the `shop-domain` header to `V` (victim shop). `HmacValidator.validate` still succeeds because it only checks `B` and `hmac` against the shared `api_secret_key` — the same secret is used for every shop, since this gem is single-secret, multi-tenant. `Registry.process` then invokes the handler with `data.shop == "V"` and `data.body` equal to attacker-controlled shop A's data, i.e. `data.shop` no longer equals the shop that actually produced/authorized `data.body`.

This is exactly the class of bug the report highlights generically ("a field acted on but not covered by the HMAC"): the fix is to include the tenant-identifying field inside the signed payload (or otherwise cryptographically bind it), analogous to fixing `totalAssets()` by excluding/binding the unaccounted value rather than silently trusting it.

### Impact Explanation
This crosses a tenant boundary: any app that follows the gem's documented pattern of trusting `WebhookMetadata#shop` to select which merchant's records to update (exactly as the shipped documentation instructs) can be made to write attacker-supplied webhook data into a different, victim merchant's tenant, purely by an internet-facing replay with a modified header — no access token, secret, or privileged account is required, only a webhook that the attacker's own (unprivileged, installed) app received. This matches the "Critical – cross-tenant access" bucket, since it lets one merchant's traffic corrupt/impersonate another merchant's webhook stream at the boundary this gem itself is supposed to authenticate.

### Likelihood Explanation
Likelihood is realistic for any app built on this gem's documented integration pattern: an attacker only needs to install the target app on their own (attacker-controlled) shop to receive genuinely-signed webhook deliveries, then can replay the exact same body/HMAC pair to the app's public webhook endpoint with an altered `shop-domain` header. No knowledge of `api_secret_key` or any credential is required — only observation of one's own legitimate webhook traffic, which is trivially available to any developer/merchant installing the app.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is HMAC-verified, not just the raw body. Concretely, `Utils::VerifiableQuery#to_signable_string` for webhook requests should incorporate the `shopify-shop-domain` header (and other Shopify-owned webhook headers) into the signed material that `HmacValidator` checks, so that a request whose header claims a different shop than the one the body/HMAC combination was actually issued for fails validation. Until such a fix ships, document prominently that `WebhookMetadata#shop` is not authenticated by `Registry.process` and must be cross-checked against another trusted source (e.g. a previously stored session/shop record) before being used to select tenant data.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets Shopify deliver a real webhook, capturing the raw body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (computed by Shopify over `B` with the app's `api_secret_key`, which is identical for every tenant of the app).
2. Attacker sends a forged HTTP POST to the app's webhook endpoint with:
   - body: `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged)
   - header `x-shopify-shop-domain: victim.myshopify.com` (forged)
   - header `x-shopify-topic`: same or attacker-chosen registered topic
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed and passed to `Registry.process`.
4. `Utils::HmacValidator.validate` computes `HMAC(secret, B)` and compares it to `H` — this succeeds because `B` and `H` are the genuine, unmodified pair from step 1: [7](#0-6) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker's shop A data>, ...)`: [8](#0-7) 
6. Any handler written per the gem's own documented example (using `data.shop` to select which tenant's records to update) now processes attacker-controlled data under the victim's tenant identity.
