### Title
Webhook HMAC does not cover the `shop-domain` header, allowing shop-spoofed webhook delivery to be accepted as authentic - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC-SHA256 signature that `Utils::HmacValidator.validate` checks in `Registry.process` binds solely to the request body bytes. The `shop` (and `topic`, `webhook_id`, `api_version`) values used to identify the tenant and route the event are read straight from HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`) that are never part of the signed material.

### Finding Description
The intended identity binding is: `hmac == HMAC(secret, shop ++ topic ++ body)` (or equivalent), so that a valid signature proves both the body content and the claimed shop/topic came from Shopify for that specific webhook delivery. In this gem, the binding actually enforced is only `hmac == HMAC(secret, body)`: [2](#0-1) 

`shop` is read directly from an attacker-controllable header with no cryptographic tie to the HMAC: [1](#0-0) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, without any secondary check that the header-derived shop is consistent with anything cryptographically verified: [3](#0-2) 

Because the app's `client_secret`/`api_secret_key` is shared across all shops that install the app (it is an app-level, not a shop-level, secret), any merchant who has installed the app can legitimately receive Shopify-signed webhook bodies (e.g., topics with an empty `{}` body, or any topic where the merchant can predict/observe the JSON payload). That attacker-observed `(body, hmac)` pair remains valid for **any** `shop-domain` header value, because the header is outside the signed bytes. Replaying that body+HMAC to the app's webhook endpoint with a different, victim shop's domain in the header causes `Utils::HmacValidator.validate` to pass and the handler to run with `data.shop` set to the victim shop — a cross-tenant identity confusion at the point where the gem hands control to host application logic.

### Impact Explanation
This breaks the binding `shop authenticated == shop acted upon`, letting an unprivileged, already-installed merchant forge webhook events that the host application will process as though they originated from a different merchant's shop. Depending on how the host app's webhook handlers use `data.shop` (e.g., to select which shop's data/session to mutate), this enables cross-tenant data manipulation — data belonging to shop B being altered/triggered by a payload actually authored/replayed by shop A. This matches the in-scope "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is constrained by needing (a) the attacker to be an app-installed merchant able to observe or predict a valid `(body, hmac)` pair signed with the shared `api_secret_key`, and (b) a host application whose webhook handlers key sensitive actions off `data.shop` without any additional shop-consistency check. Topics with static/predictable bodies (e.g., mandatory compliance topics or empty-body events) make step (a) trivial. This is a low-to-moderate likelihood but plausible path since it requires no leaked credential — only ordinary app installation, which any Shopify merchant can perform.

### Recommendation
Bind the identifying headers into the signed material used for verification, e.g., extend `to_signable_string` to include `shop`, `topic`, and `webhook_id` alongside `@raw_body`, and update `Utils::HmacValidator`/documentation so verification fails if the shop/topic used by the handler doesn't match what was actually signed by Shopify for that specific delivery. At minimum, document prominently that `request.shop` is unauthenticated and must be cross-checked by the host app against a known/expected shop before use in any tenant-scoped action.

### Proof of Concept
1. App is installed on Shop A (attacker-controlled) and Shop B (victim), both signed with the same `ShopifyAPI::Context.api_secret_key`.
2. Attacker's app receives (or predicts) a legitimate Shopify webhook delivery to Shop A with body `{}` and header `x-shopify-hmac-sha256: <valid hmac for "{}">` (e.g., a `shop/redact` or other empty-payload topic).
3. Attacker replays the same raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `shop` returns `"shop-b.myshopify.com"`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `to_signable_string` (`@raw_body`, i.e., `"{}"`) — it passes because the body/HMAC pair is genuinely valid.
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: {}, ...)`, even though Shopify never actually sent this webhook for Shop B.
