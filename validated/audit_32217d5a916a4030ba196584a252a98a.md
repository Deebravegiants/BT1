Audit Report

## Title
Bridge OutgoingToken Secret Exposed to Any Authenticated (View-Role) User via Missing Role Check - (File: core/web/router.go, core/web/presenters/bridges.go)

## Summary
`GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` are registered with only base authentication (`auth.Authenticate`), no `RequiresEditRole`/`RequiresAdminRole` wrapper, and the `BridgeResource` presenter unconditionally serializes `OutgoingToken` in the JSON response. This is confirmed by direct code inspection of `core/web/router.go` (L269-271), `core/web/presenters/bridges.go` (L18, L37), and the RBAC test map in `core/web/auth/auth_test.go` (L227-229), which explicitly marks these routes `viewOnlyAllowed=true`.

## Finding Description
`core/bridges/bridge_type.go`'s `NewBridgeType` (L72-102) generates two secrets when a bridge is created: `incomingToken` (hashed and stored as `IncomingTokenHash`, used by `AuthenticateBridgeType`/`incomingTokenHash` at L104-121 to verify inbound requests from the external adapter into the node) and `outgoingToken` (stored in plaintext as `BridgeType.OutgoingToken` at L63, L98). Every subsequent `FindBridge`/`BridgeTypes` ORM read returns this plaintext `OutgoingToken`, and `NewBridgeResource` (`core/web/presenters/bridges.go` L30-41) copies it unconditionally into the response struct's `OutgoingToken` field (L18), which has no `omitempty`/redaction, unlike `IncomingToken` which is explicitly commented "only provided when creating a Bridge" (L16-17) and is only populated in `BridgeTypesController.Create` (`core/web/bridge_types_controller.go` L98-99) — never in `Index`/`Show`.

`v2Routes` in `core/web/router.go` (L268-273) wires `bt.Index` and `bt.Show` with no privileged-role wrapper, while `Create`/`Update`/`Destroy` are wrapped in `auth.RequiresEditRole`. The RBAC route table in `core/web/auth/auth_test.go` (L227, L229) confirms these two GET routes are `viewOnlyAllowed=true`, and `TestRBAC_Routemap_ViewOnly` (L484-532) asserts that a `sessions.UserRoleView` user gets neither 401 nor 403 on them — i.e., the lowest-privilege authenticated role can call `bt.Show`/`bt.Index` and receive the bridge's `OutgoingToken` in the JSON:API payload.

## Impact Explanation
This is a real inconsistency in secret redaction: the codebase clearly treats `IncomingToken` as sensitive (redacted after creation) but does not apply the same treatment to `OutgoingToken`, which remains in plaintext and is returned to any authenticated caller including `View`-role. However, when weighing severity, it should be noted that the vast majority of other `GET` routes in the RBAC table (e.g. `/v2/keys/*`, `/v2/jobs`, `/v2/chains/*`) are also `viewOnlyAllowed=true` by design — the `View` role is intentionally meant to allow read access across node resources. So the exposure of `OutgoingToken` to `View`-role users may be more a data-modeling gap (this field should arguably be treated like `IncomingToken`) than a broken role-gate that violates the app's intended security boundary as a whole. Still, since `OutgoingToken` is a credential used by the node to authenticate itself outward to the external bridge adapter, its exposure to any authenticated user (not just admins/editors) constitutes a legitimate secret-disclosure issue that maps to an in-scope "key/secret exfiltration" impact category.

## Likelihood Explanation
High likelihood/trivial exploitation: any account provisioned with `sessions.UserRoleView` (a normal, supported non-privileged role) can call `GET /v2/bridge_types` or `GET /v2/bridge_types/:BridgeName` with valid session/API-token credentials and receive `outgoingToken` in the response body — no race conditions, no additional exploitation steps, and directly demonstrated by the existing test suite's route map.

## Recommendation
Redact `OutgoingToken` from `BridgeResource` for read/list responses (e.g., only populate it via a separate, edit/admin-gated field or mark it `omitempty` and never populate on `Index`/`Show`), mirroring the pattern already used for `IncomingToken`. Alternatively, if `OutgoingToken` is intended to be readable by any authenticated node operator (as most other resource fields are), explicitly document that decision rather than treating it as equivalent to `IncomingToken`'s creation-only exposure model.

## Proof of Concept
1. Provision an API user with role `sessions.UserRoleView` (see `core/web/auth/auth_test.go` `TestRBAC_Routemap_ViewOnly`, L484-495).
2. Authenticate and issue `GET /v2/bridge_types/<BridgeName>`.
3. Observe the JSON:API response includes `"outgoingToken": "<plaintext secret>"`, per unconditional serialization in `presenters.NewBridgeResource` (`core/web/presenters/bridges.go` L30-41) and unrestricted route registration (`core/web/router.go` L269, L271).
4. Confirmed reproducible via the existing `TestRBAC_Routemap_ViewOnly` test, which asserts no 401/403 for `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` under a View-role client.
