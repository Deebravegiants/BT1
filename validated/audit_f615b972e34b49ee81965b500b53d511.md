## Analysis

The blacklisting bug class does map onto alt.fun, but not via `collectRedemption` (there is no analog to Ubiquity's redemption queue). The real analog is `FeeVault.claim()`. [1](#0-0) 

`claim()` always pays out to `msg.sender` with no caller-supplied `to`/recipient parameter, exactly like the reported `collectRedemption`'s hardcoded `msg.sender` transfer. [2](#0-1)  Fees accrue to a `creator` address recorded in `creatorBalance` automatically on every buy/sell via `Zap._accrueFee` → `FeeVault.accrue`, with no consent step from the creator. [3](#0-2) 

`Bonding.transferCreator` only updates `info.creator` for *future* fee attribution — it does not migrate the existing `creatorBalance[oldCreator]` mapping in `FeeVault`. [4](#0-3) 

`FeeVault`'s admin surface (`addDepositor`, `removeDepositor`, `setFeeTo`) has no mechanism to rescue or redirect a stuck `creatorBalance`. [5](#0-4) 

### Title
Creator fee balances are permanently frozen in `FeeVault.claim()` if the creator address is blacklisted by USDC - (File: packages/contracts/src/FeeVault.sol)

### Summary
`FeeVault.claim()` pays a token creator's pooled USDC balance to `msg.sender` with no alternate recipient parameter. USDC (the protocol's only fee currency) has a centralized blacklist feature; if a creator address is ever blacklisted, USDC's `_beforeTokenTransfer`-style check blocks any transfer to that address, so `claim()` will always revert for that creator, and the accrued balance is permanently unreachable.

### Finding Description
Every buy/sell fee is charged in USDC by `Zap` and routed into `FeeVault` via `_accrueFee`/`accrue`, which credits `creatorBalance[creator]` automatically — the creator never opts in to when or how funds land in the vault: [3](#0-2) 

The only way to withdraw that balance is `claim()`, which hardcodes the recipient to `msg.sender`: [1](#0-0) 

`Bonding.transferCreator` lets a creator reassign *future* fee attribution to a new address, but it never touches the existing `creatorBalance` entry already sitting in `FeeVault` for the old address: [4](#0-3) 

So a creator who calls `transferCreator` after being blacklisted still cannot recover the balance already accrued under the old (blacklisted) address — the new address only receives fees accrued from that point forward. `FeeVault`'s admin functions (`addDepositor`, `removeDepositor`, `setFeeTo`) provide no override or rescue path for a stuck `creatorBalance`: [5](#0-4) 

### Impact Explanation
This is a permanent freezing of creator funds. Because fee accrual is automatic and permissionless (anyone trading a creator's launched token accrues fees to that creator's address), a griefer cannot even be avoided by the creator declining deposits — funds keep piling into `creatorBalance[blacklistedCreator]` with no way for the creator (or anyone) to ever extract them via the vault. This matches the Medium-severity impact accepted in the referenced report: legitimate funds owed to a user become permanently unclaimable due to a third-party stablecoin blacklist, with no recovery path in the contract.

### Likelihood Explanation
Likelihood depends on an external event (USDC issuer blacklisting the specific creator address), which is outside the protocol's control but is a realistic, previously-exploited real-world occurrence for USDC/USDT-denominated protocols. No privileged action or complex setup is required on-chain — the freeze manifests the moment `claim()` is called by/for a blacklisted address, since `IERC20.safeTransfer` to that address will revert.

### Recommendation
Add a caller-specified recipient parameter to `claim()` (e.g., `claim(address to)`), restricted so only `msg.sender`'s own accrued balance can be redirected, mirroring the sherlock report's suggested fix for `collectRedemption`. Alternatively/additionally, expose an owner-gated `rescueCreatorBalance(address creator, address to)` that only the vault owner can invoke, to unblock funds for a creator address later proven to be blacklisted, without granting the owner unilateral access to unaffected creators' balances.

### Proof of Concept
1. `creatorA` launches a token via `Zap.createToken`; trades occur through `Zap.buy`/`Zap.sell`, each calling `_accrueFee` → `FeeVault.accrue(token, creatorA, creatorShare, protocolShare, isBuy)`, growing `creatorBalance[creatorA]`.
2. USDC's issuer blacklists `creatorA` (e.g., due to an unrelated sanctions/compliance event).
3. `creatorA` (or anyone) calls `FeeVault.claim()` from `creatorA`; the internal `$.usdc.safeTransfer(msg.sender, amount)` reverts because USDC disallows transfers to a blacklisted address.
4. `creatorA` calls `Bonding.transferCreator(token, creatorB)` to redirect future fees — this only changes `info.creator`; `creatorBalance[creatorA]` in `FeeVault` is untouched and still unclaimable.
5. `creatorA`'s already-accrued USDC balance in `FeeVault` remains permanently locked with no contract-level recovery mechanism.

    /// @notice Record a fee accrual. Caller MUST have transferred
    ///         `creatorAmount + protocolAmount` USDC to this vault first.
    /// @dev Reverts `UnderfundedAccrual` if the vault's USDC balance no longer
    ///      covers all outstanding claims — catches a depositor that calls
    ///      `accrue` without (or under-) transferring before user funds are lost.
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }

    function _accrueFee(
        address token,
        address creator,
        uint256 feeAmount,
        bool isBuy
    ) internal {
        ZapStorage storage $ = _s();
        uint256 creatorShare = (feeAmount * $.creatorFeeBps) / BPS_DENOM;
        uint256 protocolShare = feeAmount - creatorShare;
        $.usdc.safeTransfer(address($.feeVault), feeAmount);
        $.feeVault.accrue(token, creator, creatorShare, protocolShare, isBuy);
