Found it: in `Webhooks::Request` (`lib/shopify_api/webhooks/request.rb`), the `shop` value delivered to the webhook handler (`shopify-shop-domain` header) is **not** part of the HMAC-signed payload. `to_signable_string` returns only `@raw_body` (line 36-38), and `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`, lines 26-31) computes the signature purely from that string. The `shop` accessor (line 21-23) reads straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is completely outside the HMAC coverage.

`Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb`, lines 188-200) validates only the HMAC of the body, then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and dispatches it to the handler — the `shop` field the app trusts for tenant attribution is never bound to the HMAC, so a byte-for-byte valid signature (of a body an attacker can also reuse/replay if they ever observe one webhook, since HMAC only covers the body and the secret is shared across all shops using this app) still lets the header `shop` value be attacker-controlled independent of what was actually signed.

However, verifying exploitability: the attacker needs a `(raw_body, valid_hmac)` pair for *some* delivery to reuse against a different `shop-domain` header, since the HMAC is only over the body, not shop-domain, and any app receives webhooks from many merchants; the app-level `client_secret` is shared, so a previously-observed legitimate webhook body/HMAC pair for shop A can be replayed with `shop-domain: B`, causing the host application to process/act on shop B's tenant context using shop A's payload — this is a cross-tenant data/identity confusion purely due to the gem's design of excluding `shop-domain` from the signable string.

This does require an attacker to have first observed at least one legitimate webhook delivery (its body+HMAC), which is plausible since webhook endpoints are typically public HTTP endpoints and delivered over plain visible request bodies (not secret) — no credentials of the app are needed to mount this, only a previously delivered webhook body which is not confidential.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop` (shop-domain) value from HMAC verification. `Webhooks::Registry.process` trusts `request.shop` for tenant attribution after validating only the body's HMAC, allowing an attacker who has observed any single legitimate webhook delivery to replay it with a forged `shop-domain` header and have the host application process it under a different shop's identity.

### Finding Description
`Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) is defined as:
```ruby
def to_signable_string
  @raw_body
end
```
`shop` is read independently from an HTTP header (`lib/shopify_api/webhooks/request.rb:20-23`):
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) — i.e., over the body only. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the HMAC, then constructs `WebhookMetadata` using `request.shop` unauthenticated by the signature, and hands it to the app's handler. The identity binding that should hold is: `hmac == HMAC(secret, body || shop)`, but the gem only enforces `hmac == HMAC(secret, body)`, so `shop` is a free variable an attacker can set to any value while keeping a previously-valid `(body, hmac)` pair.

### Impact Explanation
This breaks the tenant boundary the host application relies on: `WebhookMetadata#shop` is the field applications use to scope database writes/reads per merchant. An attacker replaying a captured `(body, hmac)` pair with an arbitrary `shop-domain` header can make the host app apply another shop's webhook payload against a victim shop's records — a cross-tenant data confusion/integrity issue.

### Likelihood Explanation
Requires the attacker to have observed one legitimate webhook delivery's raw body and HMAC (webhook endpoints are public, unauthenticated HTTP endpoints, and delivery bodies themselves are not treated as secret), then send a forged HTTP request to the app's webhook endpoint with the same body/HMAC but an arbitrary `shop-domain` header — no possession of `api_secret_key` or any access token is required.

### Recommendation
Include the shop-domain (and ideally topic/api-version) in the HMAC-signed content, or independently verify that `request.shop` matches a shop actually associated with the currently active/expected session/installation before dispatching to handlers. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must be cross-checked against known installed shops by the host app.

### Proof of Concept
1. Observe (or receive as the legitimate app) one webhook POST: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for shop `A`).
2. Send a new POST to the app's webhook endpoint with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. `HmacValidator.validate` recomputes HMAC over `B` only and succeeds (line 190 in `registry.rb`), because `to_signable_string` never includes shop.
4. `Registry.process` builds `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...)` and invokes the handler, which now processes shop A's payload as belonging to shop B. [1](#0-0) [2](#0-1) [3](#0-2)
