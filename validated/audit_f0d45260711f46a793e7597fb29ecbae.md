### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that the rest of the library trusts for webhook processing purely from an HTTP header, while `Utils::HmacValidator` only authenticates the raw request body. Because the app's `api_secret_key` is shared across every shop that has the app installed, any shop that has the app installed can capture a legitimate, validly-signed webhook and replay it against the app's webhook endpoint with a different `x-shopify-shop-domain` header, causing the app to process attacker-controlled data under a victim shop's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers that are never mixed into the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC check passes, then dispatches to the app's handler using the *unauthenticated* `request.shop` value as the tenant identity: [4](#0-3) 

The identity binding the library implicitly claims to provide is: `hmac_valid(raw_body) == true` implies `shop header is authentic`. In reality the equality that holds is only `hmac_valid(raw_body) == true` implies `raw_body was signed by some shop using this app's shared api_secret_key`; nothing binds the `shop` header to that signature. Since `api_secret_key` is identical for every shop-installation of a given app, an unprivileged user who runs the app on their own store (a routine, unprivileged action — installing an app on a store you own requires no special privilege relative to the app developer's trust boundary between tenants) can:

1. Receive a real webhook for their own shop (`attacker-shop.myshopify.com`), capturing `raw_body` and the valid `x-shopify-hmac-sha256` value.
2. Replay that exact `raw_body` + `hmac` to the app's webhook endpoint, but substitute `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` still succeeds because it never looks at the shop header.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...))`, and any host application that uses `data.shop` to key into its own session/store logic (this is the documented usage pattern for webhook handlers) will act as if the payload legitimately originated from the victim's shop.

### Impact Explanation
This breaks the tenant/shop identity binding the gem is supposed to guarantee once `HmacValidator.validate` returns `true`. Any host application that trusts `WebhookMetadata#shop` (a value this gem hands the handler as "verified") for tenant-scoped business logic can be tricked into cross-tenant data corruption or disclosure — e.g., attributing order/customer data mutations, cache invalidation, or state updates to a shop the attacker doesn't control. This falls under cross-tenant access, a Critical-severity impact per the rules, since the shop boundary — the core multi-tenant boundary of a Shopify app — is not actually enforced by the cryptographic check the library performs.

### Likelihood Explanation
Likelihood is high for any app that has more than one shop installed (the normal case for a public/multi-tenant app). The attacker only needs their own legitimate install to obtain a validly-signed webhook body/HMAC pair; no access to the victim's data, credentials, or the app's `client_secret` is required. Replaying with a modified header is trivial (a single HTTP request), and the vulnerable code path (`Registry.process` → `HmacValidator.validate` → `handler.handle`) is the exact code path documented as the standard way to consume webhooks.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed string checked by `HmacValidator`, or otherwise cryptographically bind them to the payload before trusting them (e.g., require host apps to cross-check `request.shop` against a shop the app has confirmed installed the app for that specific installation/session, not merely rely on this gem's HMAC pass/fail). At minimum, document prominently that `Request#shop` is *not* authenticated by `HmacValidator.validate` and must be independently verified against stored session/shop records before being used for tenant-scoped actions.

### Proof of Concept
1. App is installed on both `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing one `api_secret_key`.
2. Shopify sends a legitimate webhook to the app for `attacker-shop.myshopify.com`:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-raw-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id": 1, ...attacker-controlled order fields...}
   ```
3. Attacker captures this exact body and HMAC value, then sends:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same-valid-hmac-of-raw-body>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: <same body>
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only recomputes HMAC over the body and succeeds. `handler.handle` is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload was never produced by or for that shop.
