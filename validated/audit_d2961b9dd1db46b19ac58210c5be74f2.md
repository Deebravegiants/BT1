### Title
Webhook `shop` (and topic/api-version/webhook-id) headers are not covered by the HMAC, allowing tenant-header spoofing on an otherwise-valid signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a passing HMAC check as proof the *entire* webhook request "did indeed come from Shopify," but the HMAC signature actually only covers the raw JSON body. The `shop`, `topic`, `webhook_id` and `api_version` values are taken verbatim from HTTP headers that are never included in the signed material, so they can be modified without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which only re-computes the HMAC over `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

Immediately after that single check passes, `process` builds `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`, and hands it to the app's handler: [4](#0-3) 

The gem's own documentation instructs developers to key their business logic off `data.shop` directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that this field is expected to be trusted once `process` succeeds: [5](#0-4) 

This is the same bug class as the report: an identity-binding field (`shop`) is *acted on* by the library/host app but is *not covered* by the HMAC that supposedly authenticates the whole request. The equality the code implicitly assumes — `shop header used by handler == shop cryptographically bound to the signed payload` — does not hold, because the signed payload is only the body.

### Impact Explanation
`api_secret_key` (the HMAC key) is shared across every shop that has installed a given app; a shop merely needs to install the app to receive real webhooks signed with that same key. An attacker who controls one shop that has installed the target app can capture a legitimately-signed webhook (body + `hmac` header) sent to their own endpoint, then replay it to the same app's webhook endpoint while substituting the `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) header with a victim shop's domain. `Utils::HmacValidator.validate` still passes because it only checks the body, and the handler receives `WebhookMetadata` claiming the payload belongs to the victim shop. If the host app uses `data.shop` to select the tenant record/store to write to (the exact pattern the gem's docs recommend), this results in cross-tenant data injection/corruption — one merchant's webhook payload being applied to another merchant's data.

### Likelihood Explanation
Any shop that installs a multi-tenant app already possesses valid `(body, hmac)` pairs for topics it has subscribed to, and HTTP headers are trivially forgeable by the party sending the replayed request to the app's own public webhook endpoint. No access to `api_secret_key`, access tokens, or TLS interception is required — only the ability to install the target app as a normal merchant and to send an HTTP request with custom headers.

### Recommendation
Bind tenant-identifying metadata into the authenticated material, or independently verify `request.shop` against a known/expected shop for the given topic/registration (e.g., cross-check `shop` against an existing session/installation record) before trusting it in `Registry.process`. At minimum, document explicitly that only the body is authenticated and that consumers must not treat `data.shop`/`data.topic`/`data.webhook_id` as cryptographically bound.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a subscribed webhook (e.g. `orders/create`) and capture the raw request Shopify sends, including body `B` and header `shopify-hmac-sha256: H` (valid for `B` under the shared `api_secret_key`).
2. Replay the captured request to the app's webhook endpoint, changing only the `shopify-shop-domain` header to `victim.myshopify.com`, keeping body `B` and `shopify-hmac-sha256: H` unchanged:
```
POST /callback/orders/create
shopify-topic: orders/create
shopify-hmac-sha256: H
shopify-shop-domain: victim.myshopify.com

B
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` → validation succeeds.
4. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: B, ...)`, and any host-app logic keyed on `data.shop` (as shown in the gem's own docs example) now processes the attacker's data under the victim shop's tenant context.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
