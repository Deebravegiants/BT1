Confirmed: the webhook HMAC only signs the raw body, while `shop`, `topic`, and `webhook_id` are trusted straight from headers and passed unauthenticated into the handler.

### Title
Webhook shop/topic identity is trusted from unsigned HTTP headers while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, and `webhook_id` from HTTP headers that are never included in the HMAC signature computation. `Utils::HmacValidator.validate` only authenticates `to_signable_string`, which returns solely `@raw_body`. This breaks the intended identity binding: `hmac(secret, body) == valid` should imply `shop-domain header == the shop that actually generated this body`, but the gem never enforces that equality.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)` [1](#0-0) , which computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header value [2](#0-1) .

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [3](#0-2) . Meanwhile `shop`, `topic`, and `webhook_id` are read directly from the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers with no cryptographic tie to the body or the HMAC [4](#0-3) .

After validation succeeds, `process` builds `WebhookMetadata` directly from these unauthenticated header values and hands them to the app's handler: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id)` [5](#0-4) . `WebhookMetadata#shop` is a plain `String` field with no relation to what was HMAC-signed [6](#0-5) .

Because the app's `api_secret_key` is shared across every shop that installs the app, any unprivileged merchant who installs the app on their own store receives legitimate webhook deliveries with a valid HMAC computed over their own store's body. For topics whose body content is attacker-influenceable or identical/predictable across shops (e.g. topics with generic/empty bodies, or bodies the attacker fully controls by editing their own store's data), the attacker can capture one `(raw_body, hmac)` pair from their own store and replay it to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop. `HmacValidator.validate` will still pass, because it never checks that the signed body actually originated from the shop named in the header, and `Registry.process` will invoke the app's handler believing the (attacker-supplied) body legitimately belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: the gem lets an attacker who is a legitimate (but unprivileged) user of the app on their own shop inject webhook payloads that are misattributed to an arbitrary victim shop, without needing the app's `api_secret_key` or any privileged credential. Depending on the host application's webhook handler logic (e.g. handlers that update per-shop state, revoke sessions, mark shops uninstalled/redacted, etc. keyed off `data.shop`), this can lead to cross-tenant data corruption or spoofed lifecycle events for a shop the attacker does not own, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker control (or observe) a legitimate webhook delivery for their own shop with a body that is reusable/predictable, plus the ability to send an arbitrary HTTP request with attacker-chosen headers to the app's public webhook endpoint (which by design must be internet-reachable to receive Shopify's webhooks). No secret material or privileged Shopify credentials are needed, only normal use of the app as any merchant. The gem itself provides no protection against this because the signable string is hard-coded to the raw body only.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the HMAC signable string for webhook requests, mirroring how `Oauth::AuthQuery#to_signable_string` binds `code`, `host`, `shop`, `state`, and `timestamp` together [7](#0-6) . If Shopify's actual webhook HMAC algorithm only ever signs the raw body server-side (this is Shopify's real, documented behavior and can't be changed unilaterally by this gem), then this finding should instead be treated as a documentation/guidance gap: the gem must clearly warn integrators that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and that handlers must independently verify the claimed shop is one they have an active, legitimate session/installation for before trusting the payload.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook whose body is empty/generic or fully attacker-controlled (e.g. via `{}` as shown in the test fixtures) [8](#0-7) , and capture the resulting `x-shopify-hmac-sha256`, `x-shopify-topic`, and raw body from the legitimate Shopify-issued request.
3. Replay that exact raw body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (it only checks the body against the shared `api_secret_key`) [9](#0-8) , and `Registry.process` dispatches `WebhookMetadata` with `shop: "victim.myshopify.com"` to the app's handler [10](#0-9) , causing the handler to act on the victim shop using attacker-controlled data.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
