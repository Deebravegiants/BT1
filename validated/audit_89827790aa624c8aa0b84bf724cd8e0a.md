### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not bound to the HMAC, allowing cross-tenant webhook spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop-domain` header (and `topic`/`webhook-id`/`api-version` headers) that the library hands to the app's handler as the trusted tenant identifier are never included in the signed material, so they can be swapped freely on any request that carries a body/HMAC pair the attacker legitimately possesses.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately forwards the header-derived `shop` (and `topic`) to the application's handler as the authoritative tenant identity: [3](#0-2) 

`Utils::HmacValidator.validate` confirms this: it calls `verifiable_query.to_signable_string`, which for webhooks is body-only, and compares against the secret-derived signature: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`HMAC-authenticated(shop-domain header) == shop used by handler.handle` — in reality, `HMAC` only authenticates the body; `shop` (and `topic`/`webhook_id`) are trusted independently of the signature.

The library's own documentation instructs app authors to trust `data.shop` directly as the tenant/shop identifier coming out of `Registry.process` without additional verification: [5](#0-4) 

### Impact Explanation
An unprivileged internet user who can install the target app on their own store (a normal, unprivileged, publicly available action for public/embeddable Shopify apps) will receive genuine Shopify-signed webhooks for their own shop — i.e., a valid `(raw_body, hmac)` pair, signed with the target app's `api_secret_key` that they never see or possess. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header with an arbitrary victim shop's domain. `HmacValidator.validate` still succeeds because the signature only covers the body, and `Registry.process` forwards the attacker-chosen `shop` value to the handler as if it were confirmed by Shopify. Any app that uses `data.shop` to route/store/attribute mutations (as the shipped example and docs recommend) will process or persist the replayed payload under the wrong tenant, resulting in cross-tenant data injection/corruption — this satisfies the "cross-tenant access" Critical impact category, without requiring the app's `client_secret`, any access token, or any privileged account.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to be an installed (even free/self-serve) merchant of the app in order to obtain one legitimate `(body, hmac)` pair — this is not "unprivileged internet user with zero relationship to the app," but it also requires no leaked credentials, no access token, and no interaction with any other merchant's store. Any public/embeddable app that allows install by any storefront (the common case) satisfies this. The replay itself (spoofing HTTP headers to a webhook endpoint) is trivial and repeatable indefinitely since the body/HMAC pair remains valid.

### Recommendation
Bind the identity fields to the signature, or otherwise cryptographically/authoritatively verify `shop` before it is handed to the handler:
- Extend `VerifiableQuery`/`to_signable_string` for webhooks to include the `shop-domain` (and ideally `topic`, `webhook_id`) alongside the body when computing/verifying the signature, matching Shopify's actual HMAC computation semantics if it covers more than body (verify against Shopify's current webhook signing spec), or
- Require/document that consuming apps must independently verify that `data.shop` corresponds to an actual currently-installed shop session before trusting it for any tenant-scoped action, and update `docs/usage/webhooks.md` to state this explicitly rather than implying `data.shop` is already verified.
- Additionally consider using `webhook_id` for idempotency/duplicate-detection tied to a per-shop webhook registration lookup rather than trusting the raw header value blindly.

### Proof of Concept
1. Attacker installs the target (public) app on their own store `attacker-shop.myshopify.com`, triggers a webhook (e.g., `orders/create`), and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid, computed by Shopify using the app's real `api_secret_key`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays this exact request to the app's webhook endpoint (e.g., via `curl`), but changes only the header:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
   keeping body `B` and `x-shopify-hmac-sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes.
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...))`.
5. Any handler logic that uses `data.shop` to attribute/store/act on data (as shown in the library's own documented example, `perform_later(topic:, shop_domain: data.shop, webhook: data.body)`) now processes attacker-supplied content under the victim shop's identity — a cross-tenant data injection.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
