Audit Report

## Title
Cross-user response confusion via unauthenticated `MessageID` collision in gateway legacy callback map - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
The gateway's `HandleLegacyUserMessage` stores per-request response callbacks in `h.savedCallbacks`, keyed solely by the client-supplied `MessageID`, without checking for an existing entry or binding the key to caller identity. Any unprivileged client can submit a `web_api_trigger` request with a `MessageID` colliding with another in-flight request, silently overwriting that request's callback, so that the eventual DON node response is delivered to the attacker's callback instead of the legitimate caller's.

## Finding Description
`gateway.ProcessRequest` accepts a signed message from any caller, validates only format/signature-well-formedness via `Message.Validate()` (length, null-byte, signature parseability) — never `MessageID` uniqueness or sender-to-`MessageID` binding — and forwards legacy requests directly to `HandleLegacyUserMessage`: [4](#0-3)  and [3](#0-2) .

`HandleLegacyUserMessage` then unconditionally writes `h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}` under the mutex, with no check for an existing key: [1](#0-0) . This is in contrast to the analogous `responses.new` in the outgoing connector handler, which explicitly rejects duplicate IDs: [6](#0-5) .

When any DON node later responds with `MethodWebAPITrigger`, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageID` and delivers the node's response to whatever callback currently occupies that slot: [2](#0-1) . The only authentication performed on the node-side response is that the message sender matches the expected node address in `HandleNodeMessage` — there is no check tying the response back to the specific client that submitted the original request: [7](#0-6) .

The `// TODO: apply allowlist and rate-limiting here` comment in `HandleLegacyUserMessage` confirms no allowlist/session-scoping exists to prevent one caller's `MessageID` from colliding with another's: [5](#0-4) .

## Impact Explanation
An unprivileged client (needing only its own valid signing key, which anyone can generate) can cause a victim's trigger response to be delivered to the attacker instead, resulting in cross-user response disclosure, or can cause a victim's request to receive the wrong/no response (denial of that request). This maps to the in-scope "cross-user response corruption" impact category.

## Likelihood Explanation
Exploitation only requires two unprivileged callers to submit requests with the same `MessageID` to the same DON within the same short window (up to `defaultCallbackMaxAgeSec = 120` seconds and `defaultMaxSavedCallbacks = 20000` entries), which is entirely under attacker control since `MessageID` is client-chosen and unconstrained beyond length/null-byte checks. No node compromise, operator access, or special privilege is required — this is directly reachable via the public `ProcessRequest` entrypoint.

## Recommendation
- In `HandleLegacyUserMessage`, reject the request if `h.savedCallbacks[msg.Body.MessageID]` already exists, mirroring the check in `outgoing_connector_handler.go`'s `responses.new`.
- Scope the callback map key by both `MessageID` and the validated `Body.Sender` (signer address) so a collision cannot cross caller boundaries.
- Alternatively, derive the internal correlation key server-side rather than trusting the client-supplied `MessageID` directly.

## Proof of Concept
1. Caller A signs and sends a `web_api_trigger` request to `gateway.ProcessRequest` with `Body.MessageID = "X"`, `Body.DonID = <target>`. This inserts `savedCallbacks["X"] = callbackA` in `HandleLegacyUserMessage`.
2. Before any node responds, Caller B (a different, unrelated signer) sends its own signed request with `Body.MessageID = "X"` to the same DON, overwriting `savedCallbacks["X"]` with `callbackB` since no duplicate check exists at handler.go:411-414.
3. A DON node responds with `MethodWebAPITrigger` and `MessageID = "X"` (in reply to either A's or B's forwarded request).
4. `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, deletes the entry, and delivers the response to Caller B, potentially exposing data intended for Caller A. This can be reproduced as a Go unit test instantiating `handler` directly, calling `HandleLegacyUserMessage` twice with the same `MessageID` and different callbacks, then invoking `HandleNodeMessage`/`handleWebAPITriggerMessage` and asserting which callback received the response.

}
