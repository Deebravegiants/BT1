### Title
Webhook HMAC does not cover the `shop-domain` header, allowing cross-tenant webhook shop-spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` reads the shop identity for an inbound webhook from the `shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature computed by `Utils::HmacValidator` only authenticates the raw request body. Any holder of a genuine webhook (body + HMAC) for their own shop can replay it with a different `shop-domain` header, and `Registry.process` will still accept it and hand the forged shop value to the handler as if it were verified.

### Finding Description
`Registry.process` treats a webhook as authenticated purely based on the HMAC check: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the signature using `verifiable_query.to_signable_string`: [2](#0-1) 

For webhooks, `to_signable_string` returns only the raw body — none of the Shopify headers are included: [3](#0-2) 

Meanwhile `shop` (as well as `topic`, `api_version`, `webhook_id`) is parsed straight from attacker-controllable HTTP headers: [4](#0-3) 

This `shop` value is then passed to the app's handler as though it were an authenticated attribute of the verified request: [5](#0-4) 

The documented contract explicitly promises verification of "the request," and describes `data.shop` simply as "The shop domain of the webhook" with no caveat that it is unauthenticated, encouraging host apps to key tenant-scoped logic off it directly (as shown in the doc's own example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [6](#0-5) [7](#0-6) 

The broken identity binding, stated as an equality that should hold but doesn't:
`HMAC(client_secret, raw_body)` should authenticate `{shop, topic, webhook_id, api_version, raw_body}` as one unit ("this event happened for shop X"), but in this implementation it only authenticates `raw_body`. Since a single app's `client_secret` is shared across every shop that installs it, any merchant who installs the app can legitimately receive a webhook `(body=B, hmac=HMAC(secret,B))` for their own shop, then resend the identical body/HMAC pair to the app's callback URL with the `shop-domain` header changed to a victim shop. `HmacValidator.validate` still succeeds because it never inspects the header, so `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B)` — an event that never happened for that shop, spoofed by an unrelated tenant.

### Impact Explanation
This breaks the tenant boundary between shops that install the same app: an attacker who is merely a legitimate installer of the app on their own store (an "unprivileged" party with respect to any other merchant) can forge webhook events attributed to a different shop. Any host application that follows the documented pattern of keying persistence, job dispatch, or session/token lookups off `data.shop` will process attacker-supplied body content under another tenant's identity — a cross-tenant access/data-integrity violation, which falls within the "Critical – cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is significant for any app that has more than one installing shop (the normal case for a public/multi-tenant Shopify app), since the `client_secret` (and hence the HMAC) is identical across all shops of the app. Any existing merchant of the app can capture one of their own genuine webhook deliveries (trivial, since it is delivered to their own registered endpoint) and replay it with an altered `shop-domain` header against the same endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified payload, or otherwise cryptographically tie the header-derived shop to the verified body, e.g. by including the relevant headers in `to_signable_string`, or by cross-checking `request.shop` against a shop known/expected for that specific webhook subscription (e.g., matched against the webhook's registered id) before invoking the handler. At minimum, update the documentation to make clear that `data.shop` is not authenticated by the HMAC check and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (same `client_secret`).
2. Shopify delivers a genuine webhook to the app's endpoint for `shop-a`:
   - Headers: `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: H`, body `B`.
   - `H = Base64(HMAC-SHA256(client_secret, B))`.
3. Attacker who controls `shop-a` (or can otherwise observe this delivery) resends the exact same body `B` and `hmac` header `H` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "shop-b.myshopify.com", hmac-sha256: H})` is constructed; `hmac` returns the decoded `H`.
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and compares it to `H` — this succeeds because only `B` is signed.
6. The handler is invoked with `WebhookMetadata(shop: "shop-b.myshopify.com", body: B, ...)`, even though this event never occurred for `shop-b`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
