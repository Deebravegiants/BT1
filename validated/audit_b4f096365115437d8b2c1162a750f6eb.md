Audit Report

## Title
Missing allowlist and rate-limiting enforcement in `HandleLegacyUserMessage` allows unrestricted broadcast to entire DON - (File: `core/services/gateway/handlers/capabilities/handler.go`)

## Summary
`HandleLegacyUserMessage` explicitly skips its documented allowlist/rate-limiting step (marked by an unresolved `TODO`) before forwarding every incoming `web_api_trigger` message to all DON members via `don.SendToNode`. The `nodeRateLimiter` field on the handler is only applied on the outbound (node→external HTTP) path in `handleWebAPIOutgoingMessage`, not on this inbound path, confirming the gap is real and unmitigated at the gateway ingress tier.

## Finding Description
The code at `core/services/gateway/handlers/capabilities/handler.go` L384-396 performs payload decoding and staleness checks, but the comment `// TODO: apply allowlist and rate-limiting here` immediately precedes the method check, and no allowlist or rate-limit logic exists anywhere in the function body before the fan-out loop at L411-420: [1](#0-0) [2](#0-1) 

The `nodeRateLimiter` is only invoked in `handleWebAPIOutgoingMessage`, which handles the node→external-HTTP direction, not the inbound user-message direction: [3](#0-2) 

The only mitigating check downstream is the per-workflow `allowedSenders`/`rateLimiter` check inside `trigger.processTrigger`, which happens on the node side, after the message has already been dispatched to every DON member from the gateway. This confirms the claim's central assertion: message fan-out to the entire DON occurs before any allowlist/rate-limit gating at the gateway layer, and the pruning logic for `savedCallbacks` (bounded by `MaxSavedCallbacks`, evicting oldest half when exceeded) does not prevent the fan-out itself, only limits unbounded memory growth from the map. [4](#0-3) 

I was unable to fully verify within available tool calls whether an upstream signature-verification or authentication middleware (e.g., in `core/services/gateway/network/handshake.go` or the gateway's HTTP entrypoint) restricts *who* can reach `HandleLegacyUserMessage` in the first place — i.e., whether every legacy user message must already be signed by a registered/known client key before this function is invoked. If message senders must already be cryptographically identified/registered at the transport layer, then the "any unauthenticated network caller" framing in the Impact/Likelihood sections may overstate the actual reachable threat model. That said, even with a valid signature check, the specific TODO gap remains real: there's no allowlist or rate-limit check restricting which authenticated senders can trigger fan-out, nor how frequently. This matches the code as written.

## Impact Explanation
The finding is legitimate as a code-quality/DoS-adjacent gap: the gateway broadcasts every legacy `web_api_trigger` message to all DON members without volume control before any per-workflow rate-limiting is applied, consuming node processing, network I/O, and gateway-side callback map memory. This falls into the "allowlist or subscription bypass" / resource-exhaustion category referenced in the impact taxonomy, since a party able to submit these messages can exceed intended per-sender volume/allowlist constraints at the gateway tier. However, the severity depends on how privileged a "message sender" already is by the time this handler is reached — if senders are already required to be part of a permissioned key set validated during connection setup (per `handshake.go`), this reduces from "unauthenticated internet-wide" to "any registered legacy-connector client can flood the DON," which is a narrower but still valid gap given the code explicitly acknowledges (via the TODO) that this control was never implemented.

## Likelihood Explanation
Likelihood is Medium, contingent on how message senders are authenticated at the transport/handshake layer before reaching this handler — a detail not fully confirmed in this review. Regardless of that boundary, the specific control the finding calls out (allowlist + rate-limiting inside `HandleLegacyUserMessage`) is verifiably absent in the code, and the surrounding downstream check (`trigger.allowedSenders`) only gates individual workflow triggering, not the gateway's decision to broadcast to `donConfig.Members`.

## Recommendation
Implement the allowlist and rate-limiting check indicated by the `TODO` in `HandleLegacyUserMessage`, gating on sender identity and request volume before persisting to `h.savedCallbacks` and before the `don.SendToNode` fan-out loop — reusing the `ratelimit.RateLimiter` pattern already used for `nodeRateLimiter`, but keyed per-sender for the inbound path.

## Proof of Concept
1. Establish a connection to the gateway as a legacy user-message client (subject to whatever transport-level identification is required, e.g., a signed connector key).
2. Submit a validly-formed, non-stale `api.Message` with `Body.Method = MethodWebAPITrigger` repeatedly, at high frequency.
3. Observe (via logs/metrics or a Go unit test invoking `handler.HandleLegacyUserMessage` directly with a mock `don` and `donConfig.Members`) that every message is forwarded to all DON members with no rejection based on sender identity or request rate, and that the `TODO` comment at L384 is not associated with any actual enforcement code in the function body.

			delete(h.savedCallbacks, e.id)

		}
	}
