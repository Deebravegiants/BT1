### Title
Login endpoint bcrypt timing side-channel allows user enumeration - ([File: core/sessions/localauth/orm.go])

### Summary
The local authentication `CreateSession` login flow performs an expensive bcrypt comparison only when a matching user record is found, and returns immediately with no password-hashing work when the submitted email does not exist. This produces a measurable, unauthenticated timing oracle for username/email enumeration, structurally identical to the Parse Server bug described in the report (CVE-2026-39321 / GHSA-mmpq-5hcv-hf2v).

### Finding Description
The Chainlink node's session/login endpoint is implemented by `SessionsController.Create`, which is reachable by an unauthenticated client and forwards the submitted credentials to `AuthenticationProvider().CreateSession(ctx, sr)` [1](#0-0) .

For the default/local authentication provider, `CreateSession` first looks up the user by email via `FindUser`, and returns an error immediately if no matching row exists — no bcrypt work is performed on this path: [2](#0-1) 

Only when the user *is* found does the code proceed to a constant-time email comparison (cheap) followed by `utils.CheckPasswordHash`, which invokes `bcrypt.CompareHashAndPassword` — a deliberately slow, cost-factor-driven operation: [3](#0-2) [4](#0-3) 

This is exactly the pattern described in the advisory: "When a user is not found, the server responds immediately. When a user exists but the password is wrong, a bcrypt comparison runs first, adding significant latency." The same unauthenticated-fast-path / authenticated-slow-path pattern also appears in the LDAP and OIDC authenticators' local-fallback login paths (`localLoginFallback` in `core/sessions/ldapauth/ldap.go` and `core/sessions/oidcauth/oidc.go`), which query the `users` table and only run `utils.CheckPasswordHash` if a row is returned [5](#0-4) [6](#0-5) .

### Impact Explanation
An unauthenticated attacker sending login requests to the node's `/sessions` endpoint can distinguish "email does not exist" (fast, no bcrypt) from "email exists, password wrong" (slow, bcrypt cost factor 10, ~tens of milliseconds) purely from response latency. This enables enumeration of valid Chainlink node admin/API user accounts without any credentials, which can be used to target subsequent password-guessing, phishing, or brute-force attacks against confirmed accounts. Per the CVSS vector in the report (`C:L/I:N/A:N`), impact is limited to disclosure of user existence, not direct compromise — consistent with Medium severity.

### Likelihood Explanation
The login endpoint is exposed to any client that can reach the node's operator UI/API port; no authentication or prior access is required to trigger the timing difference, and the bcrypt cost factor (visible in fixture: `$2a$10$...`) produces a difference on the order of tens of milliseconds — well within measurable range over a handful of repeated requests, especially by an attacker capable of averaging out network jitter. Likelihood is comparable to the original Parse Server case since the code structure (early return on not-found vs. bcrypt on found) is the same root cause.

### Recommendation
Perform a dummy bcrypt comparison (against a fixed, non-secret hash) whenever `FindUser` fails to find a match in `CreateSession` (and the equivalent LDAP/OIDC `localLoginFallback` paths), so that response timing is equalized regardless of whether the email exists. Apply the same fix to `TestPassword` in `core/sessions/localauth/orm.go`, `core/sessions/ldapauth/ldap.go`, and `core/sessions/oidcauth/oidc.go`, which have the identical early-return-without-bcrypt pattern. As a mitigating control, consider rate limiting on the login endpoint, though this only slows enumeration and does not eliminate the underlying timing oracle.

### Proof of Concept
1. Send repeated POST requests to the node's `/sessions` endpoint with a known-nonexistent email and any password; measure average response time (fast path — `FindUser` fails at `core/sessions/localauth/orm.go:145-148` with no bcrypt call).
2. Send repeated POST requests with a real, existing admin email and an incorrect password; measure average response time (slow path — `utils.CheckPasswordHash` at `core/sessions/localauth/orm.go:159` runs a bcrypt comparison).
3. Compare average latencies over many samples (to average out jitter); the existing-email requests will show a consistent, measurable latency increase proportional to the bcrypt cost factor, confirming the account's existence without needing the correct password.

		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}

// CheckPasswordHash wraps around bcrypt.CompareHashAndPassword for a friendlier API.
func CheckPasswordHash(password, hash string) bool {
	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	return err == nil
}
