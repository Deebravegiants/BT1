### Title
`bootstrap_congestion_info` omits postponed and promise-yield receipts, allowing congestion accounting to under-report backlog after restart/state-sync bootstrap - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`bootstrap_congestion_info` recomputes `CongestionInfo` from scratch only by iterating the delayed-receipt queue and outgoing buffers, never the postponed-receipt or promise-yield-receipt trie state, even though the `receipt_bytes` field's own doc comment says it should cover "delayed, buffered, postponed, or yielded" receipts. This function only runs when `ApplyState.congestion_info` has no entry for the shard (`own_congestion_info` in `runtime/runtime/src/lib.rs:2895-2907`), i.e., on genesis or on any restart/state-sync path where prior `CongestionInfo` is unavailable for that shard.

### Finding Description
`bootstrap_congestion_info` (`runtime/runtime/src/congestion_control.rs:743-789`) builds `CongestionInfoV1` by summing gas/bytes only from `DelayedReceiptQueue::load` and `ShardsOutgoingReceiptBuffer::load`: [1](#0-0) 
There is no iteration over postponed receipts (action receipts parked in state awaiting `input_data_ids`, `runtime/runtime/src/lib.rs:1529-1581`) or promise-yield receipts (parked via `yield_create`, `receipt.rs` `PromiseYield`/`PromiseYieldV2`). The struct field `receipt_bytes` is documented to include exactly these categories: [2](#0-1) 
but the bootstrap routine never touches them, so any accumulated postponed/yield backlog is silently dropped from the reconstructed `CongestionInfo` and the shard bootstraps with `congestion_level == 0` (or artificially low) despite holding real unprocessed/locked resources.

This is reachable in normal operation because `own_congestion_info` calls `bootstrap_congestion_info` whenever no prior `CongestionInfo` exists for the shard — this occurs on genesis, and, per the codebase's own test coverage (`pytest/tests/sanity/congestion_control_genesis_bootstrap.py`), is specifically exercised via node restarts after garbage collection. An attacker (ordinary account) can grow the postponed/promise-yield backlog cheaply: submit action receipts with `input_data_ids` referencing data that is never delivered (unresolved callback dependencies) or call `yield_create` with a long timeout, both of which are ordinary, unprivileged contract operations. These receipts remain in state accumulating storage/size and (for postponed receipts) locked resources, but are invisible to `bootstrap_congestion_info`.

Once bootstrapped to congestion_level 0, `shard_accepts_transactions` (`core/primitives/src/congestion_info.rs:123-151`) admits transactions freely because `incoming_congestion`/`outgoing_congestion`/`memory_congestion` are all computed from the under-reported `CongestionInfo`, even though the shard is actually near its real resource limits from the hidden postponed/yield backlog. This lets an attacker follow up the restart/bootstrap event with a burst of new transactions that the congestion gate should have throttled, compounding the shard's overload.

### Impact Explanation
This is a congestion/receipt-accounting integrity failure: `CongestionInfo`, which gates cross-shard forwarding (`outgoing_gas_limit`) and local transaction admission (`shard_accepts_transactions`), can be desynchronized from the true resource backlog after any bootstrap event. This does not directly cause fund loss but enables admission-control bypass — a targeted resource-exhaustion vector against a shard, worsening chunk-processing load and potentially degrading liveness/throughput for that shard, matching the "gas or storage metering bypass" / "receipt or congestion accounting failures" impact classes.

### Likelihood Explanation
Requires (1) an attacker filling a shard's postponed/promise-yield receipt storage via ordinary transactions (unresolved `input_data_ids` or long-timeout `yield_create` — both normal, permissionless operations), and (2) a bootstrap event for that shard occurring while the backlog exists (node restart / state-sync / after GC, as directly exercised by the existing pytest test `congestion_control_genesis_bootstrap.py`). Bootstrap is not attacker-triggered directly, but restarts are a routine, expected part of node operation, so the precondition is realistic and repeatable rather than a rare edge case — the attacker only needs to build up the backlog before/during any node restart on the target shard.

### Recommendation
Extend `bootstrap_congestion_info` to also iterate the postponed-receipt trie state (per-account `PendingDataCount`/postponed receipt keys) and the promise-yield receipt state, adding their congestion gas/size into `delayed_receipts_gas`/`receipt_bytes` (postponed/yield congestion gas is currently defined as 0 per `compute_receipt_congestion_gas`, but `receipt_bytes` must still include their serialized size per the documented field semantics). Alternatively, persist `CongestionInfo` deltas for postponed/yield state transitions so that no full recompute is ever required to be complete.

### Proof of Concept
Unit test in `runtime/runtime/src/congestion_control.rs` (or an integration test using `TestTriesBuilder`):
1. Populate the postponed-receipt state with several action receipts carrying unmet `input_data_ids` (using the same trie keys/helpers `Runtime::process_action_receipt`/`set_postponed_receipt` uses), and populate the promise-yield receipt state with several parked yields with long timeouts.
2. Call `bootstrap_congestion_info(trie, config, shard_id)`.
3. Assert that the returned `CongestionInfo`'s `receipt_bytes` (and/or `delayed_receipts_gas`) reflects the size/gas of the postponed and yielded receipts, not just delayed/buffered ones — the current implementation will return `receipt_bytes == 0` (or only counting delayed/buffered) despite substantial postponed/yield data present, demonstrating the omission.
