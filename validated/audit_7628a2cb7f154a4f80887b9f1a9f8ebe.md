### Title
Token exchange sends the app's `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the HTTP request host that receives the app's `client_id`/`client_secret` directly from the session token's `dest` claim, without ever passing it through `Utils::ShopValidator.sanitize!`. The sibling method `migrate_to_expiring_token` in the very same module does perform this validation before using the shop to build a request. This asymmetry breaks the intended binding: "the host that is trusted/validated as a Shopify domain" vs "the host that actually receives the `client_secret`."

### Finding Description
`exchange_token` decodes the session token via `ShopifyAPI::Auth::JwtPayload.new(session_token)` and extracts `dest_shop = jwt_payload.shop`, i.e. the `dest` claim with `https://` stripped off [1](#0-0) . `JwtPayload` only validates the signature (HS256 with `Context.api_secret_key`) and the `aud` claim against `Context.api_key`; it never validates that `dest`/`shop` is a Shopify-trusted domain [2](#0-1) .

That unvalidated `dest_shop` is then used to build the session that determines the HTTP request host: [3](#0-2) 
The request body explicitly includes `client_id` and `client_secret`: [4](#0-3) 

Contrast this with `migrate_to_expiring_token`, in the same file, which explicitly sanitizes the shop against `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before using it to build the request host that will also receive the `client_secret`: [5](#0-4) [6](#0-5) 

`HttpClient` uses the session's `shop` verbatim to build the request URL host (no additional domain check is performed at the HTTP layer) [7](#0-6) .

The equality that should hold is: `host validated as trusted-Shopify-domain == host that receives client_secret`. For `exchange_token`, the left side of that equality is never checked — only `aud == api_key` and the HMAC signature are checked — while the right side (the actual request destination) is derived straight from the same unchecked `dest` claim.

### Impact Explanation
If a `dest` value is ever a host outside `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (any domain other than `shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`, or the configured `myshopify_domain`) while still carrying a validly-signed session token (e.g. tokens issued for shop/checkout contexts on custom or shop-managed domains, as demonstrated by the `spin.dev`/custom-domain cases handled elsewhere in this same class), `exchange_token` will POST the app's `client_id` and `client_secret` to that host. This is credential leakage of the app's `client_secret` to a server outside Shopify's infrastructure — an SSRF carrying the app's credentials, matching the "High - SSRF with the app's credentials" impact category.

### Likelihood Explanation
Medium: the JWT signature and `aud` checks prevent outright forgery without the app secret, so this is not an unauthenticated bypass. However, the actual bug is a missing defense-in-depth check that the sibling method in the same file already implements, meaning the omission is a genuine, demonstrable inconsistency in this gem's own code rather than a host-application misuse issue — the fix requires no cooperation from the host application.

### Recommendation
In `exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `migrate_to_expiring_token`) before constructing `shop_session` and issuing the HTTP request that carries `client_id`/`client_secret`.

### Proof of Concept
1. Obtain (or have Shopify issue) a session token whose `dest` claim is a host outside `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, correctly signed and with `aud` equal to the app's `client_id` (as already exercised for `spin.dev`/custom-domain cases in `test/auth/jwt_payload_test.rb`).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` issues `POST https://<dest_shop>/admin/oauth/access_token` with a body containing `client_id` and `client_secret`, i.e., the app's `client_secret` is sent to `<dest_shop>` with no check that this host is a trusted Shopify domain, unlike `migrate_to_expiring_token` which enforces `Utils::ShopValidator.sanitize!` first.
