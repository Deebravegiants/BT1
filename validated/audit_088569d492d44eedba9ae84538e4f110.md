## Finding [1](#0-0) 

### Title
Missing chain-ID domain separation in `SignerCapabilityOfferProofChallengeV2` allows cross-chain replay of signer-capability delegation, leading to full custody takeover — (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
`account::offer_signer_capability` authorizes delegation of an account's `SignerCapability` (the ability to mint a full `signer` for that account) by verifying a signature over a `SignerCapabilityOfferProofChallengeV2` struct. Unlike its sibling `RotationCapabilityOfferProofChallengeV2`, which the framework authors explicitly upgraded to add a `chain_id` field "to prevent replaying the challenge message," `SignerCapabilityOfferProofChallengeV2` was never given the same fix. The signed message therefore has no domain separation across chains — the exact bug class described in the external Forwarder report, reproduced natively in Aptos's own account-capability delegation flow.

### Finding Description
The two "V2" capability-offer challenge structs are defined side by side: [2](#0-1) 

```
/// This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message.
struct RotationCapabilityOfferProofChallengeV2 has drop {
    chain_id: u8,
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}

struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

`RotationCapabilityOfferProofChallengeV2` includes `chain_id`, and its verification path (`offer_rotation_capability`) is specified to require the on-chain `chain_id::ChainId` resource to exist, confirming the chain ID is bound into the signed message: [3](#0-2) .

`SignerCapabilityOfferProofChallengeV2`, however, only binds `sequence_number`, `source_address`, and `recipient_address` — no chain identifier. This struct is consumed directly by `offer_signer_capability`: [4](#0-3) 

```
public entry fun offer_signer_capability(
    account: &signer,
    signer_capability_sig_bytes: vector<u8>,
    account_scheme: u8,
    account_public_key_bytes: vector<u8>,
    recipient_address: address
) acquires Account {
    let source_address = signer::address_of(account);
    ...
    let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
        sequence_number: get_sequence_number(source_address),
        source_address,
        recipient_address,
    };
    verify_signed_message(
        source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

    let account_resource = &mut Account[source_address];
    account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
}
```

`verify_signed_message` only checks that the signature matches `source_address`'s current auth key over the raw BCS-serialized `proof_challenge` — it never mixes in `chain_id`: [5](#0-4) .

Once the offer is recorded, anyone at `recipient_address` can call `create_authorized_signer` to obtain a full `signer` for `source_address` — equivalent to complete custody of that account (its APT balance, coin/fungible-asset stores, resource-account authority, and code-object ownership tied to it), as demonstrated in the test harness: [6](#0-5) , and the general `create_signer_with_capability` primitive: [7](#0-6) .

Because `sequence_number` and `source_address`/`recipient_address` alone are used, the same signed offer message is valid on **any** deployment of the `0x1::account` module sharing that account's public key/address and sequence-number state — for example: Aptos mainnet vs. testnet/devnet, or any independent chain built from an aptos-core fork (which retains identical module addresses and BCS layouts). A signature a user creates to delegate signer capability on one network can be replayed verbatim on another network where the account exists with the same address and the same (often 0, for a freshly created account) sequence number.

### Impact Explanation
Successful replay grants the attacker-controlled `recipient_address` a `SignerCapability` offer for the victim's account on the second chain. From there, `create_authorized_signer` mints a fully authoritative `signer` for the victim account, enabling the attacker to: transfer/drain APT and fungible-asset stores, rotate the account's authentication key (permanent account takeover), and exercise any resource-account or code-object authority tied to that account. This satisfies the custody gate's "unauthorized takeover of ... resource-account control ... tied to live assets" and "theft ... of APT" criteria at High/Critical severity, since it results in complete, non-privileged loss of custody.

### Likelihood Explanation
The precondition — a user (or a wallet/dApp signing on their behalf) producing a `SignerCapabilityOfferProofChallengeV2` signature that gets exposed and is valid on more than one aptos-core-based chain sharing the account's address/key/sequence-number — is realistic: multiple Aptos-derived networks and testnet/devnet/mainnet triads intentionally share the same account-address derivation and `0x1::account` module layout, and it is common practice for the same keypair/address to be used across environments before mainnet migration. The missing `chain_id` field is a straightforward, auditable code gap (contrasted directly against the sibling struct that was already patched for exactly this reason), which increases confidence this is a genuine oversight rather than an intentional design choice.

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2` (mirroring `RotationCapabilityOfferProofChallengeV2`), populate it with the current chain's ID inside `offer_signer_capability`, and bump/guard the struct so old (chain-id-less) signatures are rejected. This binds the signed delegation to a single chain, eliminating cross-chain replay of signer-capability grants.

### Proof of Concept
1. On Chain A (e.g., testnet), Alice signs a `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: alice, recipient_address: attacker }` and submits it via `offer_signer_capability`, intending to delegate access only within Chain A's context.
2. The attacker captures the raw signature bytes and public key used (these are transaction call arguments, visible on-chain/in mempool).
3. On Chain B (e.g., mainnet, or any other aptos-core deployment) where Alice's account exists at the same address with the same public key and sequence number 0, the attacker (or anyone) replays the identical call `offer_signer_capability(alice_signer_placeholder_data, signature_bytes, scheme, pubkey_bytes, attacker_address)` — since nothing in the signed payload references Chain B specifically, `verify_signed_message` succeeds.
4. The attacker calls `create_authorized_signer(&attacker, alice_addr)` on Chain B, obtaining a full `signer` for Alice's account, and drains her funds / rotates her key — this mirrors the exact test pattern shown in [6](#0-5)  but executed on a different chain than intended.

**Caveat**: I was not able to directly execute or fully trace whether any additional out-of-band context (e.g., a network-specific signing domain enforced at the wallet/CLI layer, outside the Move module) mitigates this at the client level; the Move-level contract itself, however, provides no on-chain chain-ID check for this specific capability-offer path, which is the root-cause gap being reported.

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }

#[test]
/// Tests Alice offering Bob a signer for her account.
fn offer_signer_capability_v2() {
    let mut harness = MoveHarness::new();

    let account_alice = harness.new_account_with_key_pair();
    let account_bob = harness.new_account_at(AccountAddress::from_hex_literal("0x345").unwrap());

    // This struct fixes sequence number 0, which is what Alice's account is at in this e2e test
    let proof_struct = SignerCapabilityOfferProofChallengeV2 {
        account_address: CORE_CODE_ADDRESS,
        module_name: String::from("account"),
        struct_name: String::from("SignerCapabilityOfferProofChallengeV2"),
        sequence_number: 0,
        source_address: *account_alice.address(),
        recipient_address: *account_bob.address(),
    };

    let proof_struct_bytes = bcs::to_bytes(&proof_struct);
    let signature = account_alice
        .privkey
        .sign_arbitrary_message(&proof_struct_bytes.unwrap());

    assert_success!(harness.run_transaction_payload(
        &account_alice,
        aptos_stdlib::account_offer_signer_capability(
            signature.to_bytes().to_vec(),
            0,
            account_alice.pubkey.to_bytes(),
            *account_bob.address(),
        )
    ));
