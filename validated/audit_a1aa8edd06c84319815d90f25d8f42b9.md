### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header when constructing the `WebhookMetadata` passed to the app's handler. Because the HMAC signing key (`api_secret_key`) is shared by the app across every merchant/shop that has installed it, and the signature never binds the `shop`, `topic`, or `webhook-id` header values, a party who can obtain one genuine, validly-signed webhook body (e.g. for their own installed shop) can replay it with a modified `shop-domain` header and have the host application attribute that data to a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are read straight from HTTP headers with no cryptographic binding to the HMAC at all: [2](#0-1) 

`Registry.process` validates only the HMAC (which covers the body) and then constructs `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`, handing that identity straight to the app's registered handler: [3](#0-2) 

The documentation confirms `data.shop` is meant to be trusted as "The shop domain of the webhook" by consuming apps, without any additional binding requirement: [4](#0-3) 

The identity binding this breaks: `shop authenticated by the HMAC == shop attributed to the webhook data` does not hold — the HMAC authenticates only the body bytes, not the `shop-domain` (or `topic`/`webhook-id`) header, so `shop_in_signed_bytes ≠ shop_used_as_tenant_key`.

### Impact Explanation
Because `api_secret_key` is a single per-app secret shared across all merchants who install the app (not a per-shop secret), any entity that can obtain one legitimately-signed webhook (for example, an app developer testing with their own store, or anyone who can observe/replay a genuine webhook delivery to an app endpoint) can resend the same `raw_body` + valid `hmac-sha256` header while swapping the `shop-domain` header to a victim shop's domain. `Registry.process` will accept the HMAC (it only checks the body) and dispatch the payload to the handler tagged with the attacker-chosen `shop`. Downstream apps that key persistence, authorization, or business logic off `data.shop` (as the documentation explicitly recommends, e.g. `perform_later(shop_domain: data.shop, ...)`) can be made to process, store, or act on data under the wrong tenant — a cross-tenant data integrity/confusion issue.

### Likelihood Explanation
Requires the attacker to obtain at least one validly-HMAC'd webhook body — achievable by any developer with their own store/app installation (a legitimate, unprivileged actor relative to other tenants of the same app), since the same `api_secret_key` signs webhooks for every shop using the app. No access token, `client_secret`, or privileged credential of the target is required; only reuse of one's own legitimately received webhook payload is needed. This is a lower-effort variant of the reported class of bug ("shop authenticated versus the shop stored as a session key") applied to webhook processing rather than OAuth.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` in the HMAC-signable material (if Shopify's webhook signing scheme allowed it), or — more practically given Shopify's fixed webhook signing scheme — require host applications to cross-check the `shop-domain` header against a shop that is known to have installed the app (e.g. verify a stored session/installation record exists for that shop) before trusting `data.shop`, and document this requirement prominently in `docs/usage/webhooks.md`. At minimum, the gem should not present `data.shop` to handlers without a clear, explicit warning that this value is not covered by the HMAC and must be independently validated against known installed shops.

### Proof of Concept
1. App merchant A installs the app; Shopify sends a webhook to the app's endpoint with body `B`, headers including `x-shopify-hmac-sha256: H` (computed over `B` using the app's shared `api_secret_key`) and `x-shopify-shop-domain: shopA.myshopify.com`.
2. Attacker (who is merchant A, or anyone who intercepts/replays this request) resends the exact same body `B` and the same `hmac-sha256` header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: modified_headers)` builds successfully; `to_signable_string` still returns `B`.
```ruby
# lib/shopify_api/webhooks/registry.rb
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  # validation passes because HMAC only covers raw_body, unchanged
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
  # request.shop == "victim-shop.myshopify.com" even though the HMAC was never computed with that value
end
```
4. The registered handler receives `data.shop == "victim-shop.myshopify.com"` alongside merchant A's actual webhook body, and any app logic that keys state, notifications, or storage off `data.shop` attributes merchant A's data to the victim tenant.
