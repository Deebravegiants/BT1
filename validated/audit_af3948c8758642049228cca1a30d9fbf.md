### Title
SSRF / `client_secret` exfiltration via unvalidated JWT `dest` claim host in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the token-exchange POST request (which carries the app's `client_id` and `client_secret`) directly from the `dest` claim of an attacker-controlled session token (JWT), without validating that the host is a trusted Shopify domain. This breaks the identity binding that should hold: `host validated == host that receives client_secret`. The sibling method `migrate_to_expiring_token` in the same file does perform this validation via `Utils::ShopValidator.sanitize!`, showing the intended control that is missing here.

### Finding Description
`JwtPayload#shop` simply strips the literal substring `"https://"` from the raw `dest` claim with no host/domain whitelist check: [1](#0-0) 

`TokenExchange.exchange_token` takes this unvalidated `dest_shop` value and builds a `Session` whose `shop` becomes the host used to build the outbound HTTP request: [2](#0-1) 

`Clients::HttpClient#initialize` builds `@base_uri` as `"https://#{api_host || session.shop}"`, i.e., directly from the unvalidated shop string: [3](#0-2) 

The POST body sent to that host includes `client_id` and `client_secret`: [4](#0-3) 

By contrast, `migrate_to_expiring_token`, which also builds a request carrying `client_secret`, explicitly sanitizes the `shop` parameter against a domain allowlist before using it as the request host: [5](#0-4) [6](#0-5) 

The identity binding that should be enforced is: **host validated as a trusted Shopify domain == host that receives the app's `client_secret`**. In `exchange_token`, the host is taken straight from the JWT `dest` claim with no call to `ShopValidator.sanitize!`, so this equality does not hold — the code path validates the JWT signature/audience (via `JwtPayload.new`) but never validates that the *destination host* derived from the claim is a Shopify-controlled domain.

While the `JwtPayload` constructor does verify the token is signed with `Context.api_secret_key` (so a fully unauthenticated attacker cannot forge an arbitrary token from scratch), the `dest` claim is not cryptographically bound to a fixed value by Shopify's token issuance process from the app's point of view within this gem — the gem trusts whatever string is present in `dest` as long as the JWT signature checks out. Session tokens are also accepted from client-side sources (e.g., the `Authorization` header or `id_token` URL param supplied by App Bridge in the browser), which is a context where the token transport is less trusted than a server-to-server OAuth callback; the gem's own docs state "Its `dest` claim determines which shop receives the token exchange request," confirming the host is claim-driven with no additional check in this code path.

### Impact Explanation
If a `dest` value is accepted that does not resolve to a genuine `*.myshopify.com` (or otherwise allow-listed) host, `exchange_token` will send an HTTPS POST containing the app's `client_id` and `client_secret` to that host. This is High-severity credential leakage: SSRF carrying the app's credentials to an attacker-influenced host, since the app's `client_secret` is transmitted to a destination selected by claim data rather than a validated allowlist, unlike the parallel `migrate_to_expiring_token` path which explicitly guards this with `ShopValidator.sanitize!`.

### Likelihood Explanation
Medium: exploitation is bounded by the fact that `JwtPayload.new` requires a token that verifies against `Context.api_secret_key` (or `old_api_secret_key`), and the `aud` claim must match `Context.api_key`. However, the whole point of `exchange_token` is to accept session tokens obtained from the browser/App Bridge context, a boundary the host application does not fully control end-to-end, and the code path shows an inconsistency with `migrate_to_expiring_token`'s explicit sanitization — indicating the omission is a gap relative to the gem's own established pattern rather than an intentional design choice.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` via `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token`) before constructing the `Session`/`HttpClient`, raising `Errors::InvalidShopError` for any host that isn't a trusted Shopify domain.

### Proof of Concept
Conceptual (not fully verified against live Shopify signing infrastructure, since it depends on how `dest` claims are issued/signed in practice):
1. Obtain or construct a session token whose `dest` claim is set to a non-Shopify host (e.g., `https://attacker.example`), signed with the app's `api_secret_key` (as would occur if the leeway/verification of `dest` format is not enforced upstream, or if a lower-trust code path re-signs/passes through claims).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `lib/shopify_api/auth/jwt_payload.rb` line 47-50 (`shop`) returns `attacker.example`, and `lib/shopify_api/clients/http_client.rb` line 18 builds `@base_uri = "https://attacker.example"`.
4. The client issues a POST to `https://attacker.example/admin/oauth/access_token` with body containing `client_id` and `client_secret` in cleartext (over HTTPS to the attacker's host).

Note: Full weaponization requires demonstrating a concrete way to get a `dest` claim signed with the app's secret pointing to an arbitrary host through Shopify's actual token issuance flow, which could not be independently confirmed with the available code/index. The core root-cause defect — the missing `ShopValidator.sanitize!` call in `exchange_token`, present in the sibling method `migrate_to_expiring_token` — is confirmed directly by the code.

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end
