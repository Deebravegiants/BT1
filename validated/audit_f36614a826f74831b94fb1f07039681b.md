Crucially, `request.shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header), `request.topic`, `request.api_version`, and `request.webhook_id` are all read directly from HTTP headers that are **not part of `to_signable_string`** — only the raw request body is HMAC-signed. ### Title
Webhook shop/topic/version/id headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from raw HTTP headers, while `to_signable_string` (used for HMAC validation) only covers the raw request body. `Registry.process` trusts `request.shop` for tenant identification after validating only the body's HMAC, so the shop identity is never actually authenticated.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac` [5](#0-4) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [6](#0-5) , while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from headers with no cryptographic binding to that signature [3](#0-2) .

`Registry.process` calls `Utils::HmacValidator.validate(request)` and, if it passes, immediately dispatches the handler using `request.shop`, `request.topic`, `request.parsed_body`, and `request.webhook_id` as trusted tenant/event identity [7](#0-6) . Because `api_secret_key` is one shared value for the whole app across all installed shops (not a per-shop secret), any request bearing a valid `HMAC(body)` for *any* shop's genuine webhook delivery will pass validation regardless of which `shop-domain` header value accompanies it.

### Impact Explanation
A user of the app on shop A (unprivileged relative to any other tenant) can intercept a webhook delivery legitimately sent to their own endpoint, then replay it with the `shopify-shop-domain` header rewritten to a victim shop B. The forged request still satisfies `HmacValidator.validate` since only the body is signed. If the host application uses `request.shop` to select the tenant's session/store (a common pattern this gem's docs recommend, e.g. `WebhookMetadata.new(... shop: request.shop ...)`), the attacker achieves cross-tenant confusion — injecting events or triggering processing attributed to shop B while only having credentials/access tied to shop A. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any merchant who installs the app receives real webhook deliveries and can freely replay/modify them since HTTP headers are attacker-controlled once traffic reaches the app's own endpoint (no TLS interception or credential theft needed — the merchant is a legitimate recipient of their own webhooks). No `api_secret_key` or access token is required to construct the attack, only observation of one's own legitimate webhook traffic.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed payload (or otherwise cryptographically bind them, e.g., by having the host application independently confirm the shop domain against session state established via other authenticated means) before trusting them in `Registry.process`. At minimum, document that `request.shop` must not be treated as authenticated by the HMAC check alone.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; attacker (merchant of shop A) triggers any webhook event and captures the raw POST: headers `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: shop-a.myshopify.com`, body `B`.
2. Attacker resends the identical body `B` and HMAC header to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` using only `request.to_signable_string == B`; validation succeeds because the HMAC never covered the shop header [6](#0-5) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [4](#0-3) , and the host application processes the event as belonging to the victim tenant.
