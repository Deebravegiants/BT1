## Finding

The bug class from the report — a bridge computing a conversion amount from a token's `decimals()`, which is fetched live and is externally mutable rather than pinned at registration — has a direct analog in `pallet-hyper-fungible-token`.

### Title
Unbacked cross-chain mint via mutable asset `decimals()` in `pallet-hyper-fungible-token` — (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`register_token` pins the *remote* EVM precision (`erc_decimals`) permanently in the `Precisions` storage map, but never pins the *local* asset's decimals. Every subsequent `send`, `on_accept`, and `on_timeout` call instead re-reads the local decimals live via `fungibles::metadata::Inspect::decimals()`. Because local assets are created and administered through `pallet-assets` with a permissionless `CreateOrigin`, any account that owns an asset can change that asset's `decimals` metadata at will, at any time after the bridge registers it — exactly the "decimals fetched real-time" pattern the Sherlock report flags as exploitable.

### Finding Description
`register_token` computes `local_decimals` once (for a check only, not storage) and stores only the peer chain's `erc_decimals` in `Precisions`: [1](#0-0) 

`send` recomputes `decimals` from the live asset metadata on every call and combines it with the cached `erc_decimals` to build the cross-chain message amount: [2](#0-1) 

`on_accept` and `on_timeout` do the same live lookup when minting locally from an incoming/timed-out message: [3](#0-2) [4](#0-3) 

The conversion helpers scale by `10^(erc_decimals − local_decimals)` (saturating), so shrinking or growing `local_decimals` directly and predictably changes the scale factor: [5](#0-4) 

Local `decimals` metadata is not a bridge-controlled constant — it is `pallet-assets` metadata, and `pallet-assets::Config::CreateOrigin` for this runtime is fully permissionless (`AsEnsureOriginWithArg<frame_system::EnsureSigned<AccountId32>>`), meaning any signed account can create an asset and remains its metadata owner, free to call `set_metadata` to change `decimals` after the bridge has registered the asset with a fixed `erc_decimals`: [6](#0-5) 

### Impact Explanation
An attacker who owns the underlying `pallet-assets` asset registered with the bridge can, immediately before calling `send`, lower the asset's `decimals` metadata. `convert_to_erc20` then inflates `erc20_amount` by `10^(erc_decimals − new_decimals)` relative to the tiny amount actually escrowed/burned locally, causing the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract to mint far more tokens than were ever backed on the source chain — an unbacked mint that drains the bridge's real collateral/backing on the EVM side. Symmetrically, raising `decimals` right before an incoming message is processed by `on_accept` shrinks the divisor in `convert_to_balance` toward 1, minting an inflated local balance for a given ERC20 message amount. Either path lets an attacker mint funds without matching burn/escrow, satisfying "unbacked mint" / concrete theft criteria.

### Likelihood Explanation
The only precondition is that the bridged asset's `decimals` metadata is externally mutable by an account other than the bridge governance that fixed `erc_decimals` at registration — true by default here since asset creation (and thus control of `set_metadata`) is permissionless via `EnsureSigned`. No compromise of consensus, relayers, or privileged roles is required; the attacker only needs to submit an asset-metadata extrinsic followed by their own `send` call (or time it before a message they control is processed on `on_accept`/`on_timeout`), both ordinary user-reachable calls.

### Recommendation
Cache the local asset's `decimals` in the `Precisions`/registration storage at `register_token` time (as is already done for `erc_decimals`), and use that cached value in `send`, `on_accept`, and `on_timeout` instead of re-reading `fungibles::metadata::Inspect::decimals()` on every call. Alternatively, freeze the asset's metadata (`pallet-assets::freeze_metadata`) as a precondition of `register_token`, and reject registration/updates if metadata is not frozen.

### Proof of Concept
1. Attacker calls `pallet_assets::create` (permissionless `CreateOrigin`) to create `AssetX`, becoming its metadata owner; sets `decimals = 18` via `set_metadata`.
2. Bridge governance (or any process trusting the declared decimals) calls `register_token` for `AssetX` with EVM `erc_decimals = 18`; `Precisions[AssetX][EVM-chain] = 18` is now fixed.
3. Attacker calls `pallet_assets::set_metadata` again, changing `AssetX.decimals` to `0`.
4. Attacker calls `hyper_fungible_token::send` with `amount = 1` unit of `AssetX`. Only `1` unit (in 0-decimal terms) is burned/escrowed locally, but `convert_to_erc20(1, erc_decimals=18, decimals=0) = 1 * 10^18`, so the outgoing `Message.amount` encodes `1e18` raw units.
5. The destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract on the EVM chain mints `1e18` tokens (18-decimal precision) to the recipient upon `onAccept`, vastly exceeding the single unit actually locked/burned on the source chain, draining the bridge's backing.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
