### Title
Ambiguous withdrawal-status matching by `assetId` misattributes destination tx hash / status when a batch contains duplicate-token withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` and the internal-utils `waitForWithdrawalCompletion()` helper both resolve the on-chain withdrawal status for a specific batch item purely by looking up the POA bridge's returned list of withdrawals for a NEAR transaction and matching on `assetId` (`near_token_id`), ignoring the withdrawal's index/amount/destination. If a batch withdrawal (`sdk.processWithdrawal`/`signAndSendWithdrawalIntent` with an array of `withdrawalParams`) contains two or more entries for the same token, `findMatchingWithdrawal` will always return the *first* matching entry in the POA API response for every one of the duplicate-token withdrawal identifiers, regardless of which one actually corresponds to that index.

### Finding Description
`createWithdrawalIdentifiers()` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` builds one `WithdrawalIdentifier` per withdrawal in a batch, keeping an `index` per-bridge-route counter [1](#0-0) . When resolving completion, `PoaBridge.describeWithdrawal()` fetches all withdrawals belonging to the intent's NEAR tx hash and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which returns the first item in the (explicitly documented as "unsorted") list whose `near_token_id` matches the queried `assetId` [2](#0-1) [3](#0-2) . The same matching-by-`assetId`-only pattern (and the same acknowledging comment) exists in the internal-utils `waitForWithdrawalCompletion` path used elsewhere [4](#0-3) .

The code comments explicitly acknowledge the collision: "multiple withdrawals of the same token in a single transaction are not supported" [5](#0-4) . Nothing in `processWithdrawal`/`createWithdrawalIdentifiers`/`createWithdrawalCompletionPromises` prevents a caller from constructing a batch with two withdrawals of the same `assetId` but different `destinationAddress` or `amount` — the SDK's public API (`withdrawalParams: WithdrawalParams[]`) does not deduplicate or validate against this case [6](#0-5) . This mirrors the H02 bug class: distinct queued/expected actions collapse onto the same lookup key ("identifier"), so status/result meant for one action is reported for another.

### Impact Explanation
When a batch has duplicate-`assetId` withdrawals with different destination addresses/amounts, `describeWithdrawal()`/`waitForWithdrawalCompletion()` will return the *same* completed `destinationTxHash` (and completion status) for every duplicate-token entry in the batch, even though only one of them actually landed. An integrator relying on this SDK to determine "withdrawal #1 succeeded with tx X" and "withdrawal #2 succeeded with tx Y" could:
- Credit/confirm the wrong destination transaction hash against the wrong withdrawal record (misreported settlement),
- Report withdrawal #2 as "completed" while it is still pending/failed (since the matcher stops at the first match), and
- In `processWithdrawal`, the aggregate `destinationTx` array would contain a duplicated/wrong entry for one of the two withdrawals [7](#0-6) .

This falls under "a status or hash misreport making an integrator credit or refund twice" (High), since integrators typically release/credit funds off-chain based on the SDK-reported completion status and tx hash.

### Likelihood Explanation
Likelihood is limited by the fact that duplicate-`assetId` withdrawals within a single batch is an edge case that must be constructed intentionally by the caller (two entries with identical `assetId` but different `destinationAddress`/`amount` in the same `withdrawalParams` array) — this is not attacker-controlled input from an external, untrusted party but rather a caller/integrator usage pattern that the code's own comments admit is unsupported. There is no on-chain/user path to trigger it without the integrator itself constructing such a batch, and the underlying POA Bridge API is stated to not support disambiguating this case either, meaning the root cause is partly external. This significantly reduces exploitability by an unprivileged attacker.

### Recommendation
Disambiguate withdrawal matching by more than `assetId`: incorporate amount/destination address, or fall back to the documented approach in the code comments — sort both the POA API withdrawal list and the local `withdrawalParams` by amount and match by relative order, consuming matched entries so they cannot be reused for a subsequent duplicate-token lookup. Alternatively, until the POA Bridge API supports positional/index disambiguation, throw an explicit unsupported-batch error when duplicate `assetId`s are detected within a single batch's `withdrawalParams`, rather than silently misattributing status.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ {assetId: "nep141:usdc.omft.near", amount: 100n, destinationAddress: "A"}, {assetId: "nep141:usdc.omft.near", amount: 200n, destinationAddress: "B"} ] })`.
2. Both withdrawals settle in the intent tx; the POA Bridge indexer returns both withdrawal records for that NEAR tx hash (order not guaranteed) via `getWithdrawalStatus`.
3. `createWithdrawalIdentifiers` assigns index 0 and 1 (both routed through `PoaBridge`) [1](#0-0) .
4. When `describeWithdrawal` is invoked for each identifier, `findMatchingWithdrawal` filters by `assetId` only and returns the same (first) matching withdrawal record for both index-0 and index-1 queries [8](#0-7) .
5. Result: `destinationTx[0]` and `destinationTx[1]` in `processWithdrawal`'s response can report the identical `txHash`/status even though they correspond to two distinct on-chain transfers to different destination addresses — a status/hash misreport that could cause an integrator to credit the wrong withdrawal as completed or credit one destination twice.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

	async processWithdrawal(
		args: ProcessWithdrawalArgs<WithdrawalParams | WithdrawalParams[]>,
	): Promise<WithdrawalResult | BatchWithdrawalResult> {
		const withdrawalParams = Array.isArray(args.withdrawalParams)
			? args.withdrawalParams
			: [args.withdrawalParams];

		// Step 1: Estimate fee
		const feeEstimation = await (() => {
			if (args.feeEstimation != null) {
				return Array.isArray(args.feeEstimation)
					? args.feeEstimation
					: [args.feeEstimation];
			}

			return this.estimateWithdrawalFee({
				withdrawalParams,
				logger: args.logger,
			});
		})();

		// Step 2: Sign and send intent
		const { intentHash } = await this.signAndSendWithdrawalIntent({
			withdrawalParams,
			feeEstimation,
			referral: args.referral,
			intent: args.intent,
			logger: args.logger,
		});

		args.logger?.info("Intent published", { intentHash });

		// Step 3: Wait for intent settlement
		const intentTx = await this.waitForIntentSettlement({
			intentHash: intentHash,
			logger: args.logger,
		});

		args.logger?.info("Intent settled", { txHash: intentTx.hash });

		// Step 4: Wait for withdrawal completion
		const destinationTx = await this.waitForWithdrawalCompletion({
			withdrawalParams,
			intentTx,
			logger: args.logger,
		});

		if (!Array.isArray(args.withdrawalParams)) {
			return {
				// biome-ignore lint/style/noNonNullAssertion: single withdrawal returns single-element arrays
				feeEstimation: feeEstimation[0]!,
				intentHash,
				intentTx,
				// biome-ignore lint/style/noNonNullAssertion: single withdrawal returns single-element arrays
				destinationTx: destinationTx[0]!,
			};
		}

		return {
			feeEstimation,
			intentHash,
			intentTx,
			destinationTx,
		};
	}
}
