### Title
Webhook shop-domain identity is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) used for routing and handler dispatch entirely from an HTTP header, while the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body. This breaks the binding `shop authenticated == shop the handler acts on for`, allowing an attacker who possesses one valid `(body, hmac)` pair to relabel it as belonging to a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, excluding all headers from the signed content: [1](#0-0) 

`Request#shop` is read straight from the (attacker-controlled, in a replay scenario) `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header, confirming the header set (including `shop`) is never part of the signed payload: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field that becomes the sole tenant identifier passed to `WebhookHandler#handle`: [5](#0-4) 

Because the HMAC only binds the body bytes, and topic/shop/webhook-id/api-version headers ride along unauthenticated, any party that can obtain one legitimate `(raw_body, hmac)` pair for a given topic (e.g., by installing the app on their own store and receiving a real webhook with that body/HMAC) can resend the same body+HMAC to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `Registry.process` will pass HMAC validation (since only the body is checked) and dispatch to the handler with `shop` set to the victim's domain, effectively identity binding: `hmac verified over body` ≠ `shop trusted by handler`.

### Impact Explanation
If the host application uses `WebhookMetadata.shop` (as documented/intended by this field's purpose) to look up the correct tenant's session/store record without an independent authenticated shop check, an attacker can inject data attributed to, or trigger tenant-scoped side effects (order/customer updates, redact processing, etc.) against, a shop they do not own — a cross-tenant access condition. This matches the Critical impact bucket for cross-tenant access, since the gem's own webhook-processing primitive is the component asserting an unauthenticated identity as trustworthy.

### Likelihood Explanation
Exploitation requires obtaining one valid `(body, hmac)` pair for a topic whose body content is not shop-specific (e.g., mandatory compliance topics `shop/redact`, `customers/redact`, `customers/data_request` have structurally similar bodies across shops, differing mainly by IDs which the attacker also can supply from their own legitimate delivery). An attacker who has installed the app on their own store (a normal, unprivileged install) can trivially capture such a pair from their own webhook deliveries and replay it against the same public webhook endpoint with a modified `shop-domain` header, requiring no credentials beyond app installation.

### Recommendation
Include the relevant identity headers (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in the signed material verified by `Utils::HmacValidator`, or otherwise cryptographically bind them to the raw body before dispatch, so that spoofing the `shop` header without also forging a matching HMAC becomes infeasible. At minimum, document and enforce that `WebhookMetadata.shop` must never be treated as authenticated data by consuming applications, or independently re-derive/validate the shop domain from a source outside of the header (e.g., binding to the store URL configured for the registered webhook, cross-checked with Admin API metadata) before invoking the handler.

### Proof of Concept
1. Attacker installs the app on their own dev store `attacker.myshopify.com` and receives a legitimate webhook for topic `customers/data_request` with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-for-body>` and body `B`.
2. Attacker resends the exact same body `B` and `hmac` to the app's public webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` against the supplied `hmac` — this passes because `B` and `hmac` are unmodified from the legitimate delivery: [6](#0-5)  and [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"`, even though the request never originated from Shopify for that shop, demonstrating the broken binding between the HMAC-verified bytes and the trusted tenant identity.
