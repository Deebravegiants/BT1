### Title
Webhook shop-domain (and other identifying headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` values exclusively from HTTP headers, but the HMAC signature that `Registry.process` validates is computed over the raw body only. Because Shopify signs webhooks with a single API secret shared by the app across **all** installed shops (not a per-shop secret), any shop that has this app installed can capture a webhook it legitimately receives (with a valid HMAC over that body) and replay the same body to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a different, victim shop. The signature check still passes because the header is never part of the signed material, so the handler is invoked believing the payload belongs to the victim tenant.

### Finding Description
`Utils::HmacValidator.validate` verifies the request by calling `verifiable_query.to_signable_string`, and for webhooks that method is implemented as: [1](#0-0) 

which returns only `@raw_body`. Meanwhile, the identifying fields consumed by the rest of the pipeline are pulled straight from attacker-controllable headers: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to build the metadata passed to the app's handler, with no cross-check that these headers are consistent with anything inside the signed body: [3](#0-2) 

The `hmac_validator` itself confirms the check is purely `secret + raw_body -> digest`, with no header binding at all: [4](#0-3) 

The broken equality is: **`shop` used by the handler to select/act on tenant data == `shop` that Shopify actually generated the HMAC for**. Since the header is outside the signed material, an attacker only needs *any* valid `(body, hmac)` pair — trivially obtainable by installing the app on their own shop and receiving one real webhook — and can then relabel it as coming from an arbitrary victim `myshopify.com` domain.

### Impact Explanation
This breaks the tenant-isolation guarantee that "a webhook whose HMAC validates truly originated for shop X." A host application that (as documented in `docs/usage/webhooks.md`) uses `request.shop`/`WebhookMetadata#shop` to look up the corresponding merchant session, write to that merchant's stored data, or take shop-scoped actions can be tricked into cross-tenant data confusion or corruption using attacker-controlled (but validly-HMAC'd) payload content stamped with a victim shop's domain. This satisfies the High-impact bar of "cross-tenant access" via a scope/identity-binding check that answers permissively.

### Likelihood Explanation
Likelihood is significant for any multi-tenant app built on this library: obtaining one legitimate webhook (with valid HMAC) from a shop where the attacker controls the installation (e.g., a free development store) is trivial and requires no special privileges, secrets, or social engineering — only the ability to install a public/public-listed app, which is normal unprivileged internet-user behavior.

### Recommendation
Bind the identifying headers to the HMAC-verified material, e.g. by including `shop-domain`, `topic`, and `webhook-id` (or the full raw header block) in `to_signable_string`, or by requiring callers to independently confirm `request.shop` against a shop encoded in the verified body/session before dispatch. At minimum, `Registry.process` should refuse to trust `request.shop` unless it can be corroborated against data that was actually covered by the signature.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Attacker triggers the webhook and captures the full genuine request: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` (the same `api_secret_key` is shared by the app for every shop).
3. Attacker replays the exact same `(B, H)` pair to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` re-computes `HMAC-SHA256(api_secret_key, B)` and it matches `H`, so validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the forged `shop` header (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the app's handler as if this webhook genuinely belongs to `victim.myshopify.com`.
