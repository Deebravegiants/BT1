### No vulnerability found for this question.

**Why the claimed equality holds:**

For the `SOLANA`/`raw_ed25519` case, `prepareSwapSignedData` sets `payload: new TextDecoder().decode(signature.signedData.message)` — i.e., an exact decode of the very bytes the wallet already signed, and `signature: transformED25519Signature(signature.signatureData)` — the signature the wallet produced over those same bytes. [1](#0-0) 

Neither this function nor `sendSignedIntents` ever reconstruct, re-serialize or mutate that `payload` string; `IntentsSDK.sendSignedIntents` forwards `args.multiPayloads` verbatim to `intentRelayer.publishIntents`, only adding `quoteHashes`. [2](#0-1) 

`composeMultiPayloads` in the executer likewise only concatenates already-signed `MultiPayload` objects into an array (`before` / new / `after`) without touching their contents. [3](#0-2) 

The contract-side verification for `raw_ed25519` recomputes `sha256` over the `payload` field exactly as received: `computeRawEd25519Hash` = `sha256(TextEncoder().encode(payload))`, and any change to `deadline` (which lives inside that `payload` string) would change this hash, invalidating the ed25519 signature against the unchanged `public_key`. [4](#0-3) 

**Conclusion:** The equality `signed.deadline == the value the caller/signer constructed` cannot be broken by an unprivileged caller through `sendSignedIntents(multiPayloads)`, because:
1. The SDK never re-derives or mutates the `payload` string for a pre-signed `raw_ed25519` payload — it only forwards it as-is.
2. Any attacker-side mutation of the `payload` bytes (e.g. to change `deadline`, `token`, `receiver_id`, `token_ids`, `amounts`, `msg`, or `min_gas`) would desynchronize the payload from the ed25519 signature, which intents.near verifies over the exact payload bytes — the altered payload would fail signature verification and be rejected on-chain, not "accepted because the signature still verifies," as the question's premise assumes.

The scenario described (payload altered post-signing, but contract "accepts it because the signature still verifies over the altered payload") is not reachable: any alteration to a signed field invalidates the signature by construction. There is no code path in this repo where the SDK mutates a caller-supplied, already-signed `MultiPayload` before relaying it.

function composeMultiPayloads(
	newPayload: MultiPayload,
	signedIntents?: SignedIntentsComposition,
): MultiPayload[] {
	if (!signedIntents) {
		return [newPayload];
	}

	const result: MultiPayload[] = [];

	// Add "before" intents first
	if (signedIntents.before && signedIntents.before.length > 0) {
		result.push(...signedIntents.before);
	}

	// Add the new payload
	result.push(newPayload);

	// Add "after" intents last
	if (signedIntents.after && signedIntents.after.length > 0) {
		result.push(...signedIntents.after);
	}

	return result;
}

import { sha256 } from "@noble/hashes/sha2";
import type { MultiPayload } from "@defuse-protocol/contract-types";

/**
 * Compute the SHA-256 hash of a Raw Ed25519 payload
 * This simply hashes the UTF-8 encoded payload string
 *
 * @param payload - The message string to hash
 * @returns 32-byte hash as Uint8Array
 */
export function computeRawEd25519Hash(payload: string): Uint8Array {
	const data = new TextEncoder().encode(payload);
	return sha256(data);
}

/**
 * Compute hash from a signed Raw Ed25519 payload
 *
 * @param signedPayload - The signed Raw Ed25519 payload
 * @returns 32-byte hash as Uint8Array
 */
export function computeSignedRawEd25519Hash(
	signedPayload: Extract<MultiPayload, { standard: "raw_ed25519" }>,
): Uint8Array {
	return computeRawEd25519Hash(signedPayload.payload);
}
