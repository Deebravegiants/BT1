Based on my investigation, I found a genuine identity-binding gap that matches the described bug class exactly.

### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable representation from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read from unauthenticated HTTP headers. `Webhooks::Registry.process` still uses these unauthenticated header values to construct the `WebhookMetadata` passed to the app's handler, breaking the intended binding: `HMAC-verified content == identity attributed to that content`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all sourced straight from client-controlled request headers with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against the computed HMAC — i.e., only the body: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the metadata dispatched to the app's handler: [4](#0-3) 

Because a single app has one `api_secret_key` shared across every merchant shop that installs it, a valid `(raw_body, hmac)` pair obtained from **any** shop (including a shop the attacker controls/installs the app on themselves) remains a valid signature no matter which `shop-domain` header is attached to the replayed request. The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to handler as request.shop`
This equality does not hold, since `shop` is never part of the signed bytes.

### Impact Explanation
An attacker who can obtain one legitimately signed webhook body/HMAC pair for the target app (trivially possible by installing the app on their own store and receiving one webhook) can replay that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` will accept it (same secret, same body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-chosen) body originated from the victim shop. Any host application that uses `request.shop`/`WebhookMetadata#shop` as a tenant key (e.g., to look up the shop's session, update per-shop records, or trigger per-shop side effects) can be tricked into attributing attacker-controlled data to another tenant — a cross-tenant data-injection/confusion primitive.

### Likelihood Explanation
Requires only: (1) installing the target app on any shop the attacker controls (or otherwise triggering one webhook delivery), (2) capturing that raw body + `X-Shopify-Hmac-Sha256` value, and (3) POSTing it back to the app's public webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key`, tokens, or privileged accounts is needed, matching the "unprivileged internet user" threat model.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC validation (or otherwise cryptographically bind them, e.g., by validating them against Shopify's registered webhook subscription for that HMAC/delivery), so that the identity fields delivered to the handler cannot be altered independently of the signed payload.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; capture a delivered webhook's raw body `B` and its `X-Shopify-Hmac-Sha256` value `H` (valid because computed with the app's shared `api_secret_key`).
2. Send a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `B` against `H`.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, letting the attacker inject data attributed to `victim-shop`.
