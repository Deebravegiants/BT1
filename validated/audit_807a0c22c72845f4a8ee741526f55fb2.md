### Title
Webhook `shop-domain` header is trusted for tenant attribution but is excluded from the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` attribute used to attribute the webhook to a tenant is read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header. `Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed to the app's webhook handler, without that value ever being covered by the signature check.

### Finding Description
The identity binding the code implicitly assumes is:

`shop attributed to the webhook == shop that produced the signed bytes`

But the actual binding enforced is only:

`HMAC(raw_body, api_secret_key) == received_hmac`

`to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is pulled straight from a header that plays no part in that computation: [2](#0-1) 

`Registry.process` validates the HMAC over the body, then hands `request.shop` to the handler as the trusted tenant identifier, with no cross-check that the header matches anything inside the signed body: [3](#0-2) 

Since `api_secret_key` is a single app-wide secret shared by every shop that installs the app (not a per-shop secret), any party who has legitimately received one valid `(raw_body, hmac)` pair for their own shop — for instance a merchant who installed the app and received a webhook for their own store — can resend that exact same body and HMAC to the app's webhook endpoint while substituting a different value in the `shopify-shop-domain` header. `Utils::HmacValidator.validate` will pass because it only checks the body bytes against the shared secret: [4](#0-3) 

The handler then receives `WebhookMetadata` with the attacker-chosen `shop` value and the original (legitimately signed) body/topic, so the host application processes it as authentic data belonging to a different merchant/tenant.

### Impact Explanation
This breaks the shop-authentication vs. shop-attribution binding described in the rules ("a field acted on but not covered by the HMAC"). If the host application uses `WebhookMetadata#shop` to key persistence, authorization, or downstream API calls (a documented and expected usage pattern of this gem, since `Registry.process` explicitly surfaces `shop` as part of the trusted metadata), an attacker who legitimately controls one tenant can cause webhook data to be attributed to another tenant — a cross-tenant confusion condition.

### Likelihood Explanation
Likelihood is constrained: the attacker must first legitimately receive at least one valid signed webhook (e.g., by installing the app on their own store), and must be able to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-controlled headers, both of which are realistic for any merchant/app installer since they do not require the `api_secret_key`, an access token, or any privileged credential.

### Recommendation
Bind the header-derived `shop` to the signed payload before trusting it as a tenant identifier, e.g. include the shop domain (and topic/webhook-id) in `to_signable_string`, or require the caller to cross-validate the header-derived shop against a shop value embedded in the parsed body (`parsed_body["domain"]` where present) before dispatching to handlers.

### Proof of Concept
1. App has a single `api_secret_key`, shared by all installs.
2. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: `raw_body = '{"id":1,...}'`, `hmac = HMAC_SHA256(raw_body, api_secret_key)`, header `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same `raw_body` and `hmac` to the app's public webhook endpoint, but sets header `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a request whose `to_signable_string` is still just `raw_body`: [5](#0-4) 
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because only the body bytes are checked: [6](#0-5) 
6. The registered handler is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"` even though the signed payload never originated from that shop, so any downstream logic keyed on this `shop` value is now cross-tenant confused.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
