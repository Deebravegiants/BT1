### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC signature over the raw request body only, while the `shop` (tenant identity), `topic`, and `webhook_id` values are taken directly from unauthenticated HTTP headers and handed to the app's webhook handler as trusted. This breaks the intended identity binding `authenticated_bytes == acted_on_identity`.

### Finding Description
`Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC over that same body-only signable string, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct the data passed to the app's handler, with no check that these header values are consistent with, or bound to, the HMAC-verified payload: [3](#0-2) 

Because the same `api_secret_key` (the app's client secret) is used to sign webhooks for *every* shop that has the app installed, a party who controls one shop with the app installed (e.g., a free/dev store) can obtain a valid `(body, hmac)` pair from their own legitimately-delivered webhook. They can then replay that exact `body` + `hmac` to the app's public webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with an arbitrary victim shop domain, and/or substituting `shopify-topic`/`shopify-webhook-id`. `HmacValidator.validate` will still pass because it only re-computes the HMAC over the body: [4](#0-3) 

The equality that should hold — "the shop attributed to this event equals the shop that actually produced the HMAC-covered bytes" — is broken: the gem authenticates the body but acts on an unauthenticated `shop` value, which is exactly the "field acted on but not covered by the HMAC" identity-binding failure.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (built directly from `Registry.process`, see the `handler.handle` call) as the tenant key to look up sessions, apply data mutations, or trigger cross-shop side effects (a common integration pattern encouraged by this library, since `WebhookMetadata` is the only tenant-scoping information the gem exposes to handlers), an attacker who controls one tenant of a multi-tenant app can forge webhook events attributed to an arbitrary other shop. This is a cross-tenant confusion vector: the attacker doesn't need the victim's credentials, only a legitimate installation of the same app on any shop (including their own), to produce events that appear to originate from a different, victim shop.

### Likelihood Explanation
Exploitation requires only: (1) the app being a public/multi-tenant app where `api_secret_key` is shared across installations, and (2) the attacker having any shop with the app installed (trivially achievable via a free Shopify development store), which is a very low bar. No knowledge of the victim's access token or the app's `client_secret` is required, since the HMAC validation logic in this gem never binds the shop header to the signed content.

### Recommendation
Extend `Request#to_signable_string` (or add a secondary check in `Registry.process`) to bind the `shop-domain`, `topic`, and `webhook-id` headers into the value that is HMAC-verified, or otherwise require correlating the delivered `shop` against a set of shop domains the app has legitimately installed sessions for before dispatching to the handler.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture a legitimately delivered webhook: raw body `B` and its valid header `x-shopify-hmac-sha256: H` (computed by Shopify using the app's shared `api_secret_key`).
2. POST to the app's webhook endpoint with:
   - Body: `B` (unmodified)
   - Header `x-shopify-hmac-sha256: H` (unmodified, still valid since it only covers `B`)
   - Header `x-shopify-shop-domain: victim.myshopify.com` (attacker-modified)
   - Header `x-shopify-topic`/`x-shopify-webhook-id` optionally modified
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (per [4](#0-3) ) because only body `B` is checked.
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` (per [5](#0-4) ) and dispatches to the app's handler, which now believes the event originated from the victim shop.
