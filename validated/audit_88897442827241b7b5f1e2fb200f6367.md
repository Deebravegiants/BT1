### Title
Mirror-pod restriction ("a mirror pod may not reference service accounts") is not enforced on Pod UPDATE requests - ([File: plugin/pkg/admission/serviceaccount/admission.go])

### Summary
`(s *Plugin) Validate` only runs the mirror-pod restriction checks (no ServiceAccountName, no secret references, no ServiceAccountToken projections) when `a.GetOperation() == admission.Create`. Any `admission.Update` request short-circuits at the `a.GetOperation() != admission.Create` check and returns `nil` before ever reaching the mirror-pod block, so a pod that acquires the `api.MirrorPodAnnotationKey` annotation via an update is never checked against this invariant.

### Finding Description
`Admit` also only mutates/validates on Create — for `admission.Update` it returns `nil` immediately [1](#0-0) , and `Validate` mirrors this with its own early return for non-create operations before the mirror-pod checks at lines 197‑219 [2](#0-1) .

Exploit flow:
1. An authenticated user with namespace-scoped pod create/patch RBAC creates an ordinary Pod. On Create, `Admit` defaults `pod.Spec.ServiceAccountName` (e.g. to `default`) and may auto-mount a ServiceAccountToken volume, and `Validate`'s mirror-pod branch does not apply because the pod has no `MirrorPodAnnotationKey` yet.
2. The same user issues a metadata-only PATCH adding `pod.Annotations[api.MirrorPodAnnotationKey]`. This is an `admission.Update` operation. `Validate` is invoked, but line 191 (`a.GetOperation() != admission.Create`) returns `nil` immediately, so the block that forbids a mirror pod from referencing a ServiceAccountName, secrets, or ServiceAccountToken projections (lines 197‑219) is never executed.
3. The result is a Pod object persisted in etcd that simultaneously carries `MirrorPodAnnotationKey` and a non-empty `Spec.ServiceAccountName` (plus any already-mounted ServiceAccountToken volume) — a combination the admission plugin is explicitly designed to prevent (`"a mirror pod may not reference service accounts"`).

This is a real gap in "validation totality": the invariant is enforced only at object creation time, not for every mutating request that can produce the same forbidden state, resulting in a persisted object combination the system's own validation logic considers invalid.

### Impact Explanation
The concrete, provable impact is a persisted invalid/protected object state: a Pod tagged as a mirror pod while still referencing a real ServiceAccount/token, something the admission controller is supposed to categorically reject. This corresponds to the "persisted invalid/protected field" impact class. Note that this does not by itself grant the attacker any new ServiceAccount token or secret they didn't already have legitimate access to (the SA/token was attached while the pod was still an ordinary pod, under normal SA admission rules, and `Spec.ServiceAccountName` itself is immutable on update per pod-spec update validation), and the kubelet's own mirror-pod bookkeeping is driven by its local static-pod manager/UID matching rather than by trusting this annotation from arbitrary API writers — so no direct privilege escalation to kubelet-managed identity was found. The verifiable, in-scope consequence is limited to bypassing the plugin's own consistency invariant for update requests.

### Likelihood Explanation
Fully attacker-reachable with only namespace-scoped `pods` create + patch/update RBAC (no admin, node, or kubelet access required). The sequence (create pod, then PATCH annotations) is trivial and fully reproducible via the public kube-apiserver.

### Recommendation
Remove the blanket `if a.GetOperation() != admission.Create { return nil }` short-circuit in `Validate`, or explicitly re-check the mirror-pod invariant whenever an update adds/has `MirrorPodAnnotationKey`, so that any request (create or update) resulting in a pod with both the mirror-pod annotation and a ServiceAccountName/secret reference/ServiceAccountToken projection is rejected.

### Proof of Concept
Table/unit test in `plugin/pkg/admission/serviceaccount/admission_test.go`:
1. Build a `*api.Pod` with `Annotations: {api.MirrorPodAnnotationKey: ""}` and `Spec.ServiceAccountName: "default"`.
2. Call `s.Validate(ctx, admission.NewAttributesRecord(pod, oldPod, ..., admission.Update, ...), o)`.
3. Assert the current behavior: `err == nil` (bug — should return `admission.NewForbidden(... "a mirror pod may not reference service accounts")` as it does for `admission.Create`).
4. Contrast with an equivalent Create-operation call, which correctly returns a forbidden error, to demonstrate the operation-dependent inconsistency.

```go
	if a.GetOperation() != admission.Create {
		// we only validate pod specs during create requests
		return nil
	}

	// Mirror pods have restrictions on what they can reference
	if _, isMirrorPod := pod.Annotations[api.MirrorPodAnnotationKey]; isMirrorPod {
		if len(pod.Spec.ServiceAccountName) != 0 {
			return admission.NewForbidden(a, fmt.Errorf("a mirror pod may not reference service accounts"))
		}
		hasSecrets := false
		podutil.VisitPodSecretNames(pod, func(name string) bool {
			hasSecrets = true
			return false
		}, podutil.AllContainers)
		if hasSecrets {
			return admission.NewForbidden(a, fmt.Errorf("a mirror pod may not reference secrets"))
		}
		for _, v := range pod.Spec.Volumes {
			if proj := v.Projected; proj != nil {
				for _, projSource := range proj.Sources {
					if projSource.ServiceAccountToken != nil {
						return admission.NewForbidden(a, fmt.Errorf("a mirror pod may not use ServiceAccountToken volume projections"))
					}
				}
			}
		}
		return nil
	}
```
