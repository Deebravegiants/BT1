### Title
Order cancellation permanently freezes all escrowed inputs if a single input token becomes non-transferable - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
Intent Gateway orders can escrow multiple different input tokens (`order.inputs: TokenInfo[]`). Both same-chain cancellation and cross-chain refund paths collect the *entire* set of escrowed input tokens for an order into a single `WithdrawalRequest` and refund them in one atomic call to `_withdraw`. If even one of those input tokens becomes non-transferable at refund time (e.g. a blacklist-capable stablecoin freezes the gateway or the user, or the token is paused), the whole withdrawal reverts, and the user has no way to reclaim the other, unaffected tokens in the same order. This is the same bug class as the referenced Gearbox report: a single blocked asset prevents a user from unilaterally closing/exiting a position, and there is no "force" parameter to skip the blocked asset and rescue the rest.

### Finding Description
`_cancelSameChain` builds a `remainingTokens` array covering every input token of the order and refunds them together: [1](#0-0) 

The cross-chain destination-side cancel path does the same — it packages all `order.inputs` into one `RefundEscrow` message that is later applied atomically via `withdraw()` on the source chain: [2](#0-1) 

And the source-side cancel path likewise bundles all inputs into a single `WithdrawalRequest` context for the eventual `onGetResponse` → `withdraw()` call: [3](#0-2) 

In every route, the refund of all escrowed tokens for the order happens as one transaction/one call. `SafeERC20.safeTransfer`/`safeTransferFrom` reverts if the token blocks the transfer (denylist, pause, upgradeable-token bug, etc.), and there is no per-token isolation, try/catch, or "force" flag allowing the caller to skip the blocked token and still recover the rest of the escrow. This mirrors the Gearbox `CreditManager.repay` issue: once one asset is blocked, the *entire* account-closing/refund action becomes permanently un-executable by the user, and no permissionless recovery path bypasses the stuck asset.

### Impact Explanation
Any user who places a multi-token input order that includes a token later blocked/paused/blacklisted (a realistic scenario for centralized stablecoins like USDC/USDT, or any pausable ERC20) permanently loses access to **all** of their escrowed inputs for that order — not just the blocked one. There is no admin sweep, no force-cancel, and no partial-refund mechanism in the reachable, unprivileged cancellation flow. This is a permanent freezing-of-funds condition reachable by an ordinary user's own order placement and by external token-issuer action outside the protocol's control.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a multi-input order with a token subject to a blocklist/pause capability, and (b) that token being blocked between order placement and cancellation/refund. Given that blacklist-capable stablecoins are extremely common DeFi assets and orders explicitly support multiple heterogeneous input tokens (`TokenInfo[] inputs`), this is a realistic condition, not a contrived edge case.

### Recommendation
Add a per-token failure-tolerant withdrawal mode (mirroring the "force" flag recommended in the referenced report): attempt each token transfer independently (e.g., via low-level call/try-catch) so that a revert on one token does not block release of the others, and record any failed-to-transfer token in an internal claimable balance the user can withdraw later once the block is lifted (or that governance can sweep to the user). Apply this uniformly to `_cancelSameChain`, `_cancelFromSource`'s downstream `withdraw()`, and `_cancelFromDest`'s downstream `withdraw()`.

### Proof of Concept
1. User places a same-chain order with two input tokens: `USDC` (blacklist-capable) and `DAI`.
2. Before the user cancels, `USDC` issuer blacklists the Intent Gateway contract address (or the user's address) — an event outside protocol control.
3. User calls `cancelOrder` → `_cancelSameChain` → `_withdraw(body, true, true)` attempts to transfer both `USDC` and `DAI` back to the user in one call.
4. The `USDC.transfer` call reverts due to the blacklist, causing the entire `_withdraw` call — and therefore the entire `cancelOrder` transaction — to revert.
5. The user cannot recover the `DAI` portion of the escrow either, since there is no code path that refunds tokens individually or skips the blocked token. [1](#0-0)

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }
