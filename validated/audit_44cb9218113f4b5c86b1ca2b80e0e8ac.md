## Finding

### Title
EmporiumStack EIP-712 signature omits `circomData.relay` (and `feeStructure.feeToken`/`variableRate`), letting an unprivileged party redirect signed relay fees to a relay address the owner never authorized - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`verifyWallet` recovers the EIP-712 signer over `EMPORIUM_SIGNATURE_TYPEHASH`, which only commits to `emporiumMessage`, the hash of `stack.ops`, `stack.maxFee`, and `stack.deadline`. It never commits to `circomData.relay`, `circomData.feeStructure.feeToken`, or `circomData.feeStructure.variableRate`, even though `payRelayFees` sends the (correctly capped) fee to whatever address is placed in `circomData.relay` at execution time.

### Finding Description
The claimed invariant is: *(destination of the fee the owner authorized paying) == (relay address the owner signed)*. Tracing the code:

- `verifyWallet` builds the signed digest from only `circomData.emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, `stack.deadline`: [1](#0-0) 
- The only fee-amount guard tied to the signature is `feeStructure.flatFee <= stack.maxFee`: [2](#0-1) 
- Nothing in the signed payload constrains `circomData.relay`. Yet `payRelayFees`/`payRelay` unconditionally sends the (bounded) `flatFee` to whatever `circomData.relay` is supplied at call time, using `sendToRelayFromWallet` -> `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)`: [3](#0-2) 

Since `stack` (containing `v/r/s`, `ops`, `maxFee`, `deadline`) is itself just `abi.decode`d from `circomData.externalActionData.externalActionMetadata`, and `circomData` (including `relay` and `feeStructure`) is supplied fresh with every call to `Hinkal.transact`, any party who obtains a validly-signed `EmporiumStack` (e.g., by observing a pending/broadcast transaction, since ECDSA signatures are visible in calldata) can re-encode the identical `stack` bytes into a new `circomData` where only `circomData.relay` differs, and resubmit the call. `verifyWallet` will still recover the correct signer and pass, because the digest never depended on `relay`. The relayer's fee (up to the owner-authorized `maxFee`) is then routed to the attacker's address instead of the intended relay.

This is distinct from, and not prevented by, the ZK-proof layer: the top-level `Hinkal.transact` recomputes `getSignedMessageHash` from `circomData` as a public circuit input, but that hash also excludes `feeStructure` and `relay`: [4](#0-3) 
so even the EdDSA/ZK-proof layer offers no independent binding of fee destination for the general (non-Emporium) path either — but the specifically targeted Emporium ECDSA path is the concrete, directly reachable break, since `runAction`/`verifyWallet` is the exact code the question scopes.

`onlyAllowedRecipient` only restricts who Hinkal routes the external-action call to (the registered Emporium contract address), not who can supply the `circomData`/`stack` bytes for a given `emporiumMessage`; the replay guard `usedMessages[circomData.emporiumMessage]` prevents reuse of the *same* message twice, but does not stop the first submission from using an attacker-chosen `relay`, since nothing ties `relay` to the signature at all.

### Impact Explanation
An unprivileged attacker who observes any pending/broadcast Emporium transaction can resubmit it (front-run/replace) with `circomData.relay` set to their own address, stealing the relay fee (bounded by `stack.maxFee`, so this is a bounded amount per transaction, but fully controllable and repeatable across every Emporium transaction observed). This is theft of protocol/relay fees, matching the Immunefi High category ("theft or permanent freezing of protocol/relay fees"). It does not directly move the wallet owner's principal assets beyond the fee already authorized to be paid — but it moves that fee to a party never authorized to receive it, which is exactly the "destination the owner's signature never authorised" scenario described in the target.

### Likelihood Explanation
Preconditions: an Emporium action using a signed `EmporiumStack` (`signerAddress != address(0)`) must be in flight; the attacker only needs to observe the calldata (mempool or already-broadcast tx) and resubmit with a modified `circomData.relay` before/instead of the original submitter, paying their own gas. No special role, key, or proof is required — the attacker never needs to forge the ECDSA signature, only decode calldata bytes and re-encode with a different `relay` field. This is cheap and repeatable for every signed Emporium transaction that becomes visible before finalization.

### Recommendation
Include `circomData.relay` (and ideally `feeStructure.feeToken`/`flatFee`, since only `flatFee<=maxFee` is currently checked and the token/relay pairing is otherwise unconstrained) in the `EMPORIUM_SIGNATURE_TYPEHASH` digest that `verifyWallet` recovers against, so the owner's signature binds the exact relay address and fee token, not just the fee cap and operations.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock `IHinkalWallet`, and a mock fee token.
2. Have "owner" sign an `EmporiumStack{ops, maxFee=100, deadline, signerAddress=owner}` for `emporiumMessage=1` via `_hashTypedDataV4`.
3. Build `circomData` with `feeStructure.flatFee=100`, `feeStructure.feeToken=token`, `relay=relayA`; call `Hinkal.transact` (or directly `EmporiumUpgradeable.runAction`) — assert `relayA` receives 100 tokens.
4. Re-run the *same* flow with a fresh `emporiumMessage=2` (to bypass the replay guard) but keep the identical signed `stack` bytes, changing only `circomData.relay = relayB` (attacker). Assert `verifyWallet` does NOT revert (signature still verifies) and `relayB` receives the 100-token fee.
5. Assert `(relay address the owner signed over) == relayA` is never checked anywhere on-chain — i.e., the equality `(fee destination executed) == (fee destination in EIP-712 digest)` is broken because the digest has no `relay` field at all.
