Audit Report

## Title
Truncated division in `reward_per_token` causes permanent loss of staking rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s reward accrual formula in `reward_per_token` performs a single integer division scaled only by the fixed constant `PRECISION_SCALING_FACTOR = 4096`, with no fractional remainder carried forward into future updates. Any interval where `reward_rate_per_block * rewardable_blocks_elapsed * 4096 < total_tokens_staked` contributes exactly zero to `reward_per_token_stored`, permanently discarding that interval's rewards rather than deferring them, and this computation is triggered on every unprivileged `stake`/`unstake` call.

## Finding Description
`reward_per_token` computes the increment to `reward_per_token_stored` as `reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`, using truncating integer division: [1](#0-0) . `PRECISION_SCALING_FACTOR` is fixed at `4096` regardless of the decimals or magnitude of `T::Balance` for any given asset pair: [2](#0-1) . Because `update_pool_rewards` simply overwrites `reward_per_token_stored` with this value each time (no remainder is tracked or carried over), any interval whose result truncates to zero is permanently lost: [3](#0-2) .

This recalculation is triggered on every call to the permissionless `stake` extrinsic (callable by any signed account) [4](#0-3)  and `unstake` (callable by the staker themselves at any time, or by any account once the pool has expired) [5](#0-4) , both of which unconditionally call `update_pool_and_staker_rewards` → `reward_per_token` with no minimum-interval throttling. There is no code path that accumulates or carries forward a fractional remainder from a truncated division; each call to `reward_per_token` finalizes and stores the (possibly zero) increment for the elapsed interval via `update_pool_rewards`, so any staker/attacker who forces frequent small-interval updates (e.g., by staking and unstaking trivial amounts every block) increases the likelihood that individual intervals round down to zero, permanently reducing the total rewards distributable to the pool relative to what the admin's configured `reward_rate_per_block` implies over elapsed blocks.

## Impact Explanation
When triggered, the affected interval's reward is not merely delayed but permanently lost — `reward_per_token_stored` has already been finalized for that interval with a zero contribution, and there is no remainder-carry mechanism to recover it later. This results in legitimate stakers receiving less than the reward rate configured by the pool admin, with the shortfall becoming stranded reward-asset balance in the pool's account, recoverable only by the admin via `cleanup_pool`, which additionally requires the pool to have zero remaining stakers: [6](#0-5) . This is a concrete, unprivileged-reachable accounting/precision defect affecting reward distribution correctness.

## Likelihood Explanation
The condition `reward_rate_per_block * rewardable_blocks_elapsed * 4096 < total_tokens_staked` is most easily satisfied for popular pools with a large `total_tokens_staked` (e.g., high-decimal staked assets) paired with a modest `reward_rate_per_block` (e.g., low-decimal reward assets), forcing `rewardable_blocks_elapsed = 1` via repeated stake/unstake calls (any signed account, cost limited to transaction fees and dust amounts). Because `PRECISION_SCALING_FACTOR` is a small, fixed constant (4096) rather than scaled to `T::Balance`'s magnitude (unlike the 1e18-scale precision used in the Synthetix `StakingRewards.sol` reference implementation this pallet is explicitly modeled after, per the module-level doc comments), realistic asset/rate combinations can plausibly trigger this truncation without requiring any privileged access or protocol-breaking assumptions.

## Recommendation
- Increase `PRECISION_SCALING_FACTOR` substantially (e.g., proportional to `T::Balance`'s expected magnitude/decimals, akin to `1e18`-style fixed-point scaling) to shrink rounding error.
- Track and carry over the fractional remainder from each `reward_per_token` computation across updates so no reward is discarded, only deferred.
- Consider imposing a minimum interval between reward-affecting operations per staker, or decoupling reward accrual from `stake`/`unstake` call frequency.

## Proof of Concept
1. Admin creates a pool with `reward_rate_per_block = R`, and total staked reaches `total_tokens_staked = S` such that `R * 4096 < S`.
2. Any account repeatedly calls `stake(pool_id, 1)` then `unstake(pool_id, 1, None)` every block, forcing `rewardable_blocks_elapsed = 1` in `reward_per_token` on each call.
3. Each call computes `R * 1 * 4096 / S = 0` via integer division, so `reward_per_token_stored` does not increase across these blocks despite `R` tokens/block nominally being due to the pool.
4. Over many such blocks, cumulative rewards distributed to legitimate stakers via `harvest_rewards` fall measurably short of `R * total_blocks_elapsed`, with the shortfall left stranded in the pool's reward account as verified by comparing `T::Assets::reducible_balance` on the pool account against the theoretical undistributed amount.

		#[pallet::call_index(8)]
		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}
