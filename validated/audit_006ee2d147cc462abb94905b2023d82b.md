### Title
Webhook shop/topic identity not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop`, `topic`, and `webhook_id` values used to route and label the webhook are pulled from the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` HTTP headers, which are never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` treats a request as authentic for a given shop and topic once `Utils::HmacValidator.validate(request)` succeeds [3](#0-2) . `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` [4](#0-3) , and for `Webhooks::Request`, that method returns only `@raw_body` [5](#0-4) . The `shop`, `topic`, and `webhook_id` accessors, however, are derived from `shopify_header`, which just reads plain (unauthenticated) HTTP headers [6](#0-5) [7](#0-6) . These header-derived values are then trusted directly to build `WebhookMetadata` and dispatched to the app's handler [8](#0-7) .

This breaks the intended identity binding: `HMAC(secret, raw_body) == received_hmac` should imply "this exact payload came from Shopify for shop = X", but the equality actually only proves "this body was HMAC-signed with the secret at some point" — it says nothing about which shop or topic header accompanies it. Any entity capable of relaying a previously-valid `(raw_body, hmac)` pair (e.g., a malicious merchant who owns their own shop and legitimately receives real, validly-signed webhooks for their own store) can resubmit that exact body with `x-shopify-shop-domain` and `x-shopify-topic` headers rewritten to name a different shop/topic. The HMAC check still passes because it never inspected those headers, and the app's handler will process the replayed body under the attacker-chosen shop identity.

### Impact Explanation
This crosses a tenant boundary: a party in control of one legitimate webhook flow (their own shop) can cause the host application to process fabricated shop/topic/webhook_id metadata alongside real signed body bytes, resulting in cross-tenant data confusion in the app's webhook handler (e.g., writing order/customer data associated with shop A into shop B's records, or triggering `shop/redact`/`customers/redact`-style side effects against a shop that never sent that event). This matches the Critical "cross-tenant access" bucket, since the shop identity is exactly the tenant boundary this library is responsible for authenticating.

### Likelihood Explanation
Exploitation requires only network-level access to the app's public webhook endpoint plus the ability to observe one legitimate `(raw_body, hmac)` pair for any shop that installed the app (trivial for any merchant with the app installed, since they can trigger real webhook events for their own store and capture the request). No possession of `api_secret_key` or any credential is required — the header manipulation happens entirely on the unprivileged attacker's own outgoing HTTP request to the app.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values (not just the raw body) inside `to_signable_string` for `Webhooks::Request`, or otherwise bind them cryptographically to the HMAC, so the signature can no longer be replayed with substituted header values.

### Proof of Concept
1. Install the app on Shop A and observe a real webhook delivery to `/webhooks` with headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>` and body `B`.
2. Replay the identical body `B` and identical `x-shopify-hmac-sha256` value to the same endpoint, but set `x-shopify-shop-domain: shop-b.myshopify.com` (a victim tenant of the same app).
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC solely over `@raw_body` [5](#0-4) , which still matches, so `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", topic: "orders/create", body: B, ...)` [8](#0-7) , causing the host app to process Shop A's data as if it belonged to Shop B.
