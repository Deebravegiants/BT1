This confirms the vulnerability: the gem's documented API contract explicitly promises that `data.shop` (`WebhookMetadata#shop`) is the authenticated shop for the HMAC-validated webhook, but `Registry.process` only verifies the HMAC over the raw body while the `shop` field is read from an unauthenticated header.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant impersonation - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC over the raw request body, then trusts the `shop` field taken directly from the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header when building the `WebhookMetadata` object passed to the app's handler. Because the HMAC signature never covers this header, any party who can produce one validly-signed webhook body (e.g., a merchant receiving their own legitimate webhooks) can replay that body with a forged `shop-domain` header claiming to be a different tenant, and the app-level handler will process it as validated data for the impersonated shop.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop` and `hmac` are both read from HTTP headers that are entirely outside the signed content:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end

def to_signable_string
  @raw_body
end
``` [3](#0-2) 

The gem's own documentation states that `data.shop` is "The shop domain of the webhook" and is one of the trusted fields apps are expected to key their logic on (e.g., session/token lookups, tenant-scoped storage) [4](#0-3) , and `WebhookMetadata` is a typed struct built directly from `request.shop` with no further verification [5](#0-4) .

This breaks the intended binding: `hmac-validated-body == body produced by shop S` should imply `WebhookMetadata.shop == S`. In reality, only the body's authenticity is checked; `shop` is unauthenticated attacker-controlled header data. Any actor who owns one legitimate installation of the app (and therefore legitimately receives real, validly-HMAC'd webhook bodies from Shopify, since the HMAC secret — the app's `client_secret` — is shared across all shop installations of the app) can capture their own webhook request and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to another tenant's domain. The signature still validates because it never covered that header, and the handler will process/attribute the (possibly sensitive) payload data to the impersonated shop.

### Impact Explanation
This is a cross-tenant boundary break: an unprivileged holder of one shop's webhook traffic can cause the app to treat arbitrary body content as belonging to a different, victim shop. Depending on how the host app uses `data.shop` (e.g., to select tenant-scoped storage keys, trigger tenant-specific side effects, or route data into another merchant's records), this can lead to cross-tenant data corruption or disclosure — matching the "cross-tenant access" Critical-impact category, since the trust boundary the gem is expected to enforce (HMAC binds all fields the handler relies on) does not hold for the `shop` field.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own valid app installation to legitimately receive one real webhook (trivial for any merchant who installs a public app), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a modified header — no access to the `client_secret`, access tokens, or any other shop's credentials is required. This is a realistic, low-effort attack path for any unprivileged internet user who is also a legitimate app installer.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values into the HMAC-signed content, or otherwise cryptographically bind the shop domain to the verified body (e.g., by having `to_signable_string` include the normalized headers along with the raw body, and validating the resulting HMAC), so that `Utils::HmacValidator.validate` cannot succeed unless the claimed `shop` matches the shop that actually produced the signed payload.

### Proof of Concept
1. Attacker legitimately installs the app on `attacker-shop.myshopify.com` and receives a real webhook, e.g. topic `customers/create`, body `raw_body`, with header `X-Shopify-Hmac-Sha256: <valid_hmac>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged `raw_body`) and succeeds, because `shop` is never part of the signed content [6](#0-5) .
4. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from `attacker-shop.myshopify.com` [7](#0-6) .
