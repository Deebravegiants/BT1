Confirmed. `WebhookMetadata.shop` is populated directly from `request.shop` (the `shopify-shop-domain` header) and passed to app-provided `WebhookHandler#handle` implementations as the tenant identifier, while the HMAC signature only covers the raw body bytes.

### Title
Webhook `shop` field used for tenant attribution is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but its `to_signable_string` (used for HMAC verification) returns only the raw request body. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body/HMAC pair validates, then constructs a `WebhookMetadata` using the unauthenticated `shop` header and dispatches it to the app's handler as the shop the event belongs to.

### Finding Description
The HMAC binding this gem enforces is: `HMAC(api_secret_key, raw_body) == received_hmac`. The claim actually acted upon by the app is: `this body pertains to shop = request.shop`. These are not the same binding — the `shop-domain` header sits entirely outside the signed material.

- `Request#hmac` and `Request#to_signable_string` compute/validate the signature purely over `@raw_body`: [1](#0-0) 
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are read straight from headers with no cross-check against the signed body: [2](#0-1) 
- `HmacValidator.validate` only proves the body/secret pair is correct; it says nothing about which shop the caller is claiming to be: [3](#0-2) 
- `Registry.process` validates the HMAC, then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` and hand it to the app's handler: [4](#0-3) 
- `WebhookMetadata.shop` is exactly what handler implementations use to know which tenant an event is for: [5](#0-4) 

Since `api_secret_key` (the app's client secret) is the same value for every shop that installs the app, a body+HMAC pair is valid regardless of which shop header accompanies it. Anyone who can obtain one legitimate `(raw_body, hmac)` pair for a topic — trivially, by installing their own store/dev shop with the app and receiving one real webhook, since the HMAC secret is shared across all tenants — can resend that exact body with an attacker-chosen `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. `HmacValidator.validate` still returns `true` because it never looks at those headers, and the handler is invoked believing the event came from a different, victim shop.

### Impact Explanation
This breaks the tenant boundary the whole webhook system is meant to guarantee: `shop` claimed == `shop` the HMAC actually authenticates for. An app that uses `WebhookMetadata#shop` to route data into per-tenant storage, trigger per-tenant side effects (e.g., de-provisioning, redaction, order/inventory sync), or select which tenant's session/credentials to act with, can be made to process attacker-supplied body content under a victim shop's identity — i.e., cross-tenant data injection/corruption. This falls under the Critical "cross-tenant access" category, since a valid signature is being used to authenticate a request for a shop other than the one that produced it.

### Likelihood Explanation
Requires only: (1) the attacker's own working installation of the target app (any developer can install most public/dev Shopify apps), and (2) capturing one webhook body for a topic they want to forge (e.g. by triggering it themselves, or replaying/publicly observable event shapes for topics with predictable/empty bodies like `shop/redact` or ones with fixed JSON structure). No access to the victim's credentials or the app's `client_secret` is needed. This is fully reachable through documented library usage — `Registry.process` is the intended entry point apps call for every inbound webhook.

### Recommendation
Bind the tenant/topic identity into the value that is actually verified:
- Include `shop`, `topic`, and `webhook_id` in the signed material checked against the HMAC (Shopify's own signature only covers the body, so this instead means the gem/app must cryptographically bind the header claims to a value it independently trusts), or
- At minimum, require callers to supply/verify the expected `shop` (e.g., from an existing authenticated session or app-installation record) before trusting `request.shop`, rather than accepting whatever `shop-domain` header arrives alongside a validly-signed body.
- Document prominently in `docs/usage/webhooks.md` that `request.shop`/`WebhookMetadata.shop` is unauthenticated with respect to the HMAC and must not be trusted as a tenant boundary on its own.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives one legitimate webhook delivery for topic `orders/create` (or any topic they want to forge), capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (both signed with the app's single, shared `api_secret_key`).
2. Attacker crafts a new HTTP POST to the app's webhook endpoint containing:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since body is unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic`, `X-Shopify-Webhook-Id` as desired
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`: [4](#0-3) 
4. `Utils::HmacValidator.validate(request)` passes because it only recomputes the HMAC over `B`.
5. `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` is built and dispatched to the app's `WebhookHandler#handle`, which processes attacker-controlled content as if it were an authentic event from `victim-shop.myshopify.com`.
