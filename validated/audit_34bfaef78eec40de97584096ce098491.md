This confirms the vulnerability: the documentation itself states `data.shop` is "The shop domain of the webhook" and is expected to be used to key merchant records (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), while `ShopifyAPI::Webhooks::Registry.process` docs claim the HMAC check "will verify the request did indeed come from Shopify" — but the HMAC signature only covers the raw body, not the shop-domain header, so shop attribution is not authenticated.

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed with the app's `api_secret_key` [2](#0-1) . The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers and are never included in the signed payload [3](#0-2) . `Registry.process` trusts `request.shop` as-is once the HMAC check on the body passes and forwards it to the app's handler [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop header validated by HMAC == shop attributed to the webhook data passed to the handler`. In this gem that equality does not hold — the HMAC only binds the raw body bytes to the shared `api_secret_key`, never to the `shop` header. Because `api_secret_key` is the same for every shop that installs a given app, any unprivileged user can install the app on a store they control, capture a legitimately-signed `(raw_body, hmac)` pair from a real webhook delivery, and replay that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain. `HmacValidator.validate` will still return `true` because it only recomputes the HMAC over `@raw_body` [5](#0-4) , and `Registry.process` will dispatch to the handler with `shop: request.shop` set to the attacker-chosen value [6](#0-5) . The library's own documentation instructs host apps to key downstream work off `data.shop` directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) precisely because `Registry.process` is documented to "verify the request did indeed come from Shopify," which callers reasonably interpret as covering shop attribution too.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-acted-upon binding and enables cross-tenant confusion: an attacker who legitimately installs the target app on their own store can forge webhook events (with a body payload of their choosing/replaying) that are attributed to any other merchant shop that also uses the app. Depending on the topic (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, order/product update topics), this can trigger data deletion, deprovisioning, or state mutation scoped to a victim tenant that the attacker does not control or have any relationship with — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app builder who follows this gem's documented pattern of trusting `request.shop`/`data.shop` after `Registry.process` succeeds, since nothing in the gem itself binds the shop header to the HMAC. The only prerequisite is that the attacker be a legitimate (even free/dev) merchant of the target app, which is a low bar and does not require any secret, token, or privileged access to the victim's account.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signed payload used by `Request#to_signable_string`, or otherwise cryptographically bind the shop domain to the verified body (e.g., verify that `shop` matches a shop associated with a previously-stored, trusted webhook subscription/session before dispatching to handlers) rather than trusting the unauthenticated header value.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, completing OAuth normally.
2. Attacker triggers (or waits for) a webhook delivery for a topic whose body is attacker-controlled or predictable (e.g., an empty-body topic like `shop/redact`, or one where the body content doesn't leak the shop), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header value — both signed with the app's single, shared `api_secret_key`.
3. Attacker resends the identical raw body and HMAC header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the HMAC [8](#0-7) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [9](#0-8) , causing the host app to act on the victim tenant based on a request the attacker fully controls.
