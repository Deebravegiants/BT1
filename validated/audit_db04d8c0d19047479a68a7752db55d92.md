## Finding

### Title
Webhook shop/topic identity not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds the HMAC signature check to the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used for dispatch and tenant identification are read from unauthenticated HTTP headers. `Registry.process` trusts these header-derived fields when invoking the registered handler, so the "shop this webhook belongs to" is never covered by the same cryptographic check that authenticates the payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All other webhook attributes — `shop`, `topic`, `webhook_id`, `api_version` — are read straight from HTTP headers with no integrity binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e. the body alone) and compares it against the `hmac` field, again taken from a header: [3](#0-2) [4](#0-3) 

`Registry.process` performs the HMAC check and then unconditionally trusts `request.shop` (and `request.topic`) to route to a handler and populate `WebhookMetadata`: [5](#0-4) 

Because the same app-level `api_secret_key` is shared across every shop that installs the app, a valid `(raw_body, hmac)` pair produced for one shop's webhook remains cryptographically valid regardless of which `shopify-shop-domain` header accompanies it. The equality the gem should enforce — "shop bytes verified by HMAC" == "shop bytes used to identify the tenant" — does not hold, because the shop identity is never part of the signed bytes at all.

### Impact Explanation
An attacker who can obtain (or generate, e.g. via their own legitimately installed store, or from any exposed test/staging webhook) one valid `(body, hmac)` pair for the target app can replay that exact body/HMAC combination to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `Registry.process` will accept it as authentic (HMAC still validates, since only the body is checked) and dispatch attacker-controlled payload data to the handler tagged with the victim's shop identity via `WebhookMetadata#shop`. Any host application logic keyed off that `shop` field (e.g. updating per-tenant records, triggering per-tenant side effects) can be corrupted with attacker-chosen content attributed to a shop the attacker does not control — a cross-tenant data/identity confusion.

### Likelihood Explanation
Exploitation does not require the app's `api_secret_key`, a stolen access token, or any privileged credential — only the ability to send an HTTP request to the app's public webhook endpoint and possession of any one legitimately-signed `(body, hmac)` sample for that app (trivially obtainable by installing the app on an attacker-owned development store, which produces genuine webhooks signed with the same shared secret). This is a realistic, unprivileged-internet-user scenario.

### Recommendation
Bind the shop (and ideally topic) to the authenticated bytes, e.g. include `shopify-shop-domain` (and `shopify-topic`) in the HMAC-signable string, or require the host application to cross-check `request.shop` against a known/installed shop record before trusting it — and document this requirement prominently, since currently `Registry.process` implies the shop is verified once HMAC passes.

### Proof of Concept
1. Install the target app on an attacker-controlled store `attacker.myshopify.com`; trigger any webhook topic the app subscribes to, capturing the raw body `B` and the `X-Shopify-Hmac-SHA256` header `H` (valid because it's signed with the app's `api_secret_key`).
2. Send a forged HTTP request to the app's webhook endpoint:
   - `shopify-hmac-sha256: H`
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-topic: <same topic>`
   - body: `B` (optionally attacker can substitute any body content for topics whose schema they know, since `H` only needs to match whatever body is sent — an attacker fully controls `B` from their own store, so `B` can be crafted maliciously before capturing `H` for it).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == H`.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., attacker-controlled data falsely attributed to the victim shop.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
