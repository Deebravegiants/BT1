### Title
Confused-deputy authorization bypass allows attacker to drain a victim's ERC20 allowance to `DepositOnChainUtxosExternalAction` via `EmporiumUpgradeable.runAction`'s stateless sub-call - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`DepositOnChainUtxosExternalAction.runAction` trusts `circomData.originalSender` as the `from` address for `transferERC20TokenFrom` and relies solely on `onlyAllowedRecipient` (a `msg.sender` allowlist check) rather than verifying that the passed `CircomData` was ever authenticated by a Groth16 proof. Because `EmporiumUpgradeable.runAction`'s stateless branch performs a raw `op.endpoint.call(callData)`, an attacker can list `DepositOnChainUtxosExternalAction` as an op target with a second, entirely self-crafted `CircomData` (with `originalSender = VICTIM`) that never passes through `HinkalHelper.performHinkalChecks` or `verifyProof`. If `Emporium` is configured as an allowed recipient of `DepositOnChainUtxosExternalAction`, this drains the victim's standing ERC20 allowance into `Emporium`, which the attacker's top-level `circomData.stealthAddressStructure` then claims as a UTXO.

### Finding Description
The broken equality is: **AUTHORITY** — `from` of every `transferFrom` performed by an external action must equal the account that produced the Groth16 proof verified in `Hinkal.transact`. `HinkalHelper.performHinkalChecks` enforces `circomData.originalSender == sender` (msg.sender of `Hinkal.transact`) only for the **single, top-level** `CircomData` struct passed into `transact` [1](#0-0) , and `Hinkal.transact` verifies the SNARK proof against that same top-level struct [2](#0-1) .

`EmporiumUpgradeable.runAction`, in its stateless branch, executes arbitrary attacker-supplied `EmporiumOperation.callData` via a raw low-level call: `(success, err) = op.endpoint.call{value: op.value}(op.callData);` [3](#0-2) . This `callData` is opaque bytes chosen entirely by the attacker inside `externalActionMetadata` (part of the top-level `CircomData`), so it can encode a call to `DepositOnChainUtxosExternalAction.runAction(secondCircomData, deltaAmounts)` where `secondCircomData.originalSender = VICTIM`. This second `CircomData` is never checked by `performHinkalChecks` or `verifyProof` — only the top-level circomData that entered `Hinkal.transact` is proof-checked.

`DepositOnChainUtxosExternalAction.runAction` only gates on `onlyAllowedRecipient` (a `msg.sender` allowlist, not a proof check) [4](#0-3) , then directly uses `circomData.originalSender` as the `from` of the transfer: `address userAddress = circomData.originalSender;` ... `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal);` [5](#0-4) . If `Emporium`'s address is in `DepositOnChainUtxosExternalAction`'s `isAllowedRecipient` map (a stated precondition), the call succeeds with `msg.sender == Emporium`, and the victim's standing ERC20 allowance to `DepositOnChainUtxosExternalAction` is pulled into `Emporium`.

Back in `EmporiumUpgradeable.runAction`, the token balance delta produced by this drain is measured via `getBalancesForArray` before/after and credited via `handleOut` to `circomData.stealthAddressStructure` — i.e., the **attacker's own** stealth address from the top-level (legitimately-proved) `circomData` [6](#0-5) . The attacker only needed one valid proof for their own UTXOs/nullifiers; the victim's funds are pulled with zero matching debit anywhere in the proven `amountChanges`.

`Hinkal.transact`'s post-call balance/slippage equality check operates on `circomData.erc20TokenAddresses`/`amountChanges` of the **top-level** circomData and does not know about or constrain the internal victim-targeting sub-call [7](#0-6) ; it simply sees "balance increased, and it matches this UTXO amount" — which is true, but the funds source is unauthorized.

### Impact Explanation
Critical — direct theft of a third party's approved ERC20 balance, credited into the attacker's own shielded UTXO without the victim ever producing a proof, signature, or nullifier for the transaction. This is repeatable against any victim with a standing (unrevoked) approval to `DepositOnChainUtxosExternalAction`, for any amount up to that allowance, and requires only one attacker-controlled proof per exploitation (for the attacker's own dummy top-level circomData).

### Likelihood Explanation
Requires: (1) `Emporium` configured as an allowed recipient of `DepositOnChainUtxosExternalAction` (owner-controlled config, but explicitly stated precondition and plausible given Emporium's designed composability with other external actions via arbitrary `op.endpoint.call`), (2) a victim with a nonzero leftover approval to `DepositOnChainUtxosExternalAction` (common residual state after any prior legitimate deposit that doesn't reset allowance to zero), and (3) Emporium holding zero balance of the token beforehand (attacker can choose an arbitrary token to guarantee this, or target a token where this is already true). Attacker cost is a single normal Hinkal transaction with one legitimately generated proof for their own funds; no privileged role, victim key, or victim cooperation is needed.

### Recommendation
`DepositOnChainUtxosExternalAction` (and any external action calling `transferERC20TokenFrom`) must not trust `circomData.originalSender` as an implicit authorization; instead it should require `circomData.originalSender == tx-level authenticated signer` for the exact call context, or these actions should only be reachable as the top-level `externalActionData.externalAddress` invoked directly by `Hinkal._externalTransact` (never via nested/opaque calls from `Emporium` or other stateless op endpoints). Concretely: remove `DepositOnChainUtxosExternalAction` from `Emporium`'s permitted set of stateless-call targets, or add an explicit check in `DepositOnChainUtxosExternalAction.runAction` that `msg.sender == hinkalAddress` (i.e., it can only ever be called directly by `Hinkal.transact`, which is the only place proof verification against that exact `circomData` occurs).

### Proof of Concept
Foundry fork test:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, and `DepositOnChainUtxosExternalAction`; register `EMPORIUM_ID -> Emporium` in `Hinkal.externalActionMap`; add `Emporium` to `DepositOnChainUtxosExternalAction`'s allowed recipients.
2. Mint `TOKEN` to `VICTIM`; have `VICTIM` `approve(DepositOnChainUtxosExternalAction, X)` as part of an earlier legitimate deposit, then never revoke.
3. Attacker builds a top-level `CircomData` for their own UTXO (originalSender = attacker, matching `msg.sender`), with `externalActionData.externalActionId = EMPORIUM_ID` and `externalActionMetadata = abi.encode(EmporiumStack{signerAddress:0, ops:[{endpoint: DepositOnChainUtxosExternalAction, invokeWallet:false, value:0, callData: abi.encodeCall(runAction, (fakeCircomDataWithOriginalSender=VICTIM, zeroDeltaAmounts))}]})`.
4. Attacker generates a single valid snarkjs proof for their own top-level `CircomData` only.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)`.
6. Assert: `VICTIM`'s `TOKEN` balance decreased by `tokenTotal`; `Emporium`'s balance transiently increased then forwarded out via `handleOut`; attacker's minted shielded UTXO amount equals `tokenTotal`; and no entry in the proven `circomData.amountChanges`/nullifiers accounts for this debit from `VICTIM`.
