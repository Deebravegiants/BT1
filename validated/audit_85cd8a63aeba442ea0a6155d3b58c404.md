### Title
Webhook shop-domain identity not covered by HMAC allows cross-tenant webhook shop-spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value returned to webhook handlers directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that authenticates the webhook only covers the raw request body. Because the shop identity is never bound to the signature, a party who can obtain one valid `(body, hmac)` pair (trivially, by installing the app on a shop they themselves control) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the app to process the payload as if it originated from a different (victim) tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Yet the same `Request` object exposes `shop`, `topic`, `api_version`, and `webhook_id` from headers that are excluded from the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC over the body and then forwards `request.shop` (an unauthenticated field) straight into the handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and the app's `api_secret_key`: [4](#0-3) 

This is the equality that should hold but doesn't:
`shop_bound_by_hmac == shop_trusted_by_handler`
Here, `shop_bound_by_hmac = ∅` (the signable string contains no shop identity) while `shop_trusted_by_handler = request.shop` (taken from an unauthenticated header). Anyone who can produce or capture one legitimately signed body (e.g., by installing the public app on their own store and receiving a real webhook) can resend that identical `(body, hmac)` pair with a forged `shop-domain` header pointing at a victim shop. The endpoint will accept it as valid (HMAC check passes because it only checks the body) and the handler will process/store the data attributed to the victim shop — a cross-tenant identity confusion.

### Impact Explanation
This breaks the shop/tenant authentication boundary that `WebhookMetadata.shop` is relied upon by host applications to route or attribute incoming Shopify data. It enables an attacker to make the app believe legitimate (attacker-controlled) webhook content came from a different merchant/tenant, which can lead to cross-tenant data injection or corruption of the victim's records within the host app's own data model — matching the "cross-tenant access" critical-impact category.

### Likelihood Explanation
Exploitation requires only: (1) obtaining a single genuine `(body, hmac)` pair, achievable by any unprivileged user by installing a public app on their own Shopify development/test store and observing the webhook delivery, and (2) sending a crafted HTTP request to the app's public webhook endpoint with the same body/HMAC but a different `shop-domain` header. No access token, `api_secret_key`, or privileged account is required, and it does not depend on the host application deviating from the gem's documented API — the gem itself supplies the vulnerable `shop` accessor and HMAC scope.

### Recommendation
Bind the shop identity (and ideally topic/webhook_id) into the HMAC-verified data, or otherwise cryptographically or contextually validate that the `shop-domain` header corresponds to a shop for which the app has an active session/installation. At minimum, do not treat `request.shop` from `Webhooks::Request` as verified without independently confirming it matches an existing session/install record before using it as a tenant key.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify computed with the app's shared `client_secret`.
2. Attacker (or anyone controlling network access to the app's public webhook endpoint) replays the exact same body and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it validates only the raw body against the (unchanged) HMAC — see: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, and the host app processes/stores the attacker's payload as belonging to the victim shop.
