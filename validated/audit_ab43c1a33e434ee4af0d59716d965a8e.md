## Analog Identified

### Title
Pool initialization can be front-run because `Initialize2`'s PDA derivation for the AMM/vault/target-orders/lp-mint accounts depends only on the public OpenBook `market` key, letting an attacker permanently seize the canonical pool address before the legitimate creator - ([File: program/src/processor.rs])

### Summary
The Sherlock report describes a governance bug class: an operation's "uniqueness key" is derived only from information that is public and reproducible by anyone (the action tuple), with no binding to the legitimate actor (e.g. proposal ID). An attacker can front-run and permanently occupy that slot, blocking the honest actor. Raydium's `process_initialize2` has the same structural weakness: the deterministic addresses for the AMM account, target-orders account, LP mint, and coin/pc vaults are derived solely from the OpenBook `market` pubkey (which is public, chosen at market-creation time, and known before any pool creator submits `Initialize2`), with no dependence on the submitting wallet.

### Finding Description
`get_associated_address_and_bump_seed` derives every AMM-related PDA using only `program_id`, `market_account.key`, and a fixed constant seed (`AMM_ASSOCIATED_SEED`, `TARGET_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED`): [1](#0-0) 

Because these seeds contain nothing tied to the calling user, anyone who observes an OpenBook `market` can pre-compute the exact same AMM/vault/target-orders/lp-mint addresses that a legitimate pool creator intends to use in their own `Initialize2` transaction.

`process_initialize2` creates these accounts via `generate_amm_associated_account`, `generate_amm_associated_spl_mint`, and `generate_amm_associated_spl_token`, each of which only proceeds if the target account is still owned by the system program, otherwise it fails with `AmmError::RepeatCreateAmm`: [2](#0-1) [3](#0-2) 

The only economic requirement for successfully calling `Initialize2` is providing non-zero coin/pc vault balances and initializing the LP mint: [4](#0-3) [5](#0-4) 

An attacker can:
1. Watch the mempool/observe a target `market` pubkey that a legitimate market maker intends to initialize with meaningful liquidity.
2. Submit their own `Initialize2` for that same `market` first, using trivial (e.g. minimal, disproportionate) `init_coin_amount`/`init_pc_amount`, since the only checks are `amount == 0` and mint/owner/delegate/freeze-authority sanity checks.
3. Because the PDAs are bound only to `market`, the attacker's transaction claims the canonical AMM account, LP mint, and vaults for that market permanently; the legitimate creator's later `Initialize2` for the same `market` will always hit `AmmError::RepeatCreateAmm` / `AmmError::AlreadyInUse`.

This is the direct structural analog of the report's root cause: a collision key that is fully attacker-computable and not bound to the rightful submitter allows front-running to permanently deny/seize the resource (here, the pool address) rather than merely delaying it.

### Impact Explanation
Unlike the governance report (where front-running only *delays* a queue action), here the consequence is stronger: because the PDAs are permanently and deterministically tied to the `market` pubkey, front-running Initialize2 **permanently and irrevocably** prevents the legitimate market maker from ever creating the intended pool for that market with proper liquidity. The attacker becomes the first LP and controls the initial coin/pc ratio (`liquidity = sqrt(pc_amount * coin_amount)`), which sets the pool's initial price. Legitimate liquidity providers/depositors who later interact with this attacker-seeded pool inherit an attacker-chosen initial price/ratio, and the attacker (as sole/first depositor) receives the corresponding LP tokens: [6](#0-5) . This is a genuine loss/DoS vector for the legitimate pool creator's intended pool and a price-manipulation vector for subsequent depositors, not merely a "no impact" delay.

### Likelihood Explanation
`market` pubkeys are public information (created via OpenBook before any `Initialize2` call), and `Initialize2` is a permissionless instruction reachable by any signer with the correct account list and a minimal token balance, making this front-run trivially executable by any attacker monitoring for imminent pool-creation transactions or valuable markets.

### Recommendation
Do not derive the AMM/target-orders/lp-mint/vault PDAs from the `market` pubkey alone. Include the intended pool creator (or a per-creation nonce/salt supplied and committed by the legitimate creator in advance, e.g. via a dedicated "reserve market for AMM" step) in the seed derivation, or otherwise gate `Initialize2` so that only the party who registered intent to create the pool for a given `market` can successfully claim these deterministic addresses.

### Proof of Concept
1. Attacker observes a `market` pubkey about to be used in a legitimate `Initialize2` call (visible on-chain/in mempool since market pubkeys are public).
2. Attacker computes the same AMM/target-orders/lp-mint/vault PDAs using `get_associated_address_and_bump_seed(program_id, &market, seed, program_id)` [1](#0-0) .
3. Attacker submits `Initialize2` for that `market` with minimal `init_coin_amount`/`init_pc_amount` (only requirement: non-zero) before the legitimate creator's transaction lands.
4. The legitimate creator's `Initialize2` transaction for the same `market` now fails at the associated-account creation step with `AmmError::RepeatCreateAmm` [7](#0-6) , or at the status check with `AmmError::AlreadyInUse` [8](#0-7) , permanently denying them the intended pool for that market.
