### Title
`Bonding.transferCreator` allows a creator to redirect future fee attribution to a contract address that can never call `FeeVault.claim()`, permanently freezing creator fees - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding.transferCreator` mirrors the reported class exactly: a user-reachable function accepts an arbitrary destination address for future value transfers with no validation against addresses that structurally cannot receive/claim it, causing funds to become permanently stuck — the same "recipient == engine" freezing pattern as the original `PrimitiveEngine.withdraw` bug, just applied to alt.fun's creator-fee attribution instead of a direct token transfer.

### Finding Description
`transferCreator` only guards against the zero address and against re-setting the same creator: [1](#0-0) 

```solidity
function transferCreator(
    address tokenAddress,
    address newCreator
) external {
    if (newCreator == address(0)) revert ZeroAddress();
    TokenInfo storage info = _s().tokenInfo[tokenAddress];
    if (msg.sender != info.creator) revert NotCreator();
    if (newCreator == info.creator) revert InvalidInput();
    info.creator = newCreator;
    emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
}
```

`info.creator` is exactly the address that all future creator-fee accrual is keyed to: `Zap._buyInternal`/`_sellInternal` fetch `bonding_.creatorOf(tokenAddress)` and forward it into `_accrueFee`, which writes the creator's share into `FeeVault.creatorBalance[creator]` [2](#0-1) [3](#0-2) .

`FeeVault.claim()` is strictly keyed on `msg.sender`, with no admin override or rescue path for a creator address that is not an EOA capable of initiating that call: [4](#0-3) 

If a creator sets `newCreator` to any contract address that has no built-in mechanism to call `claim()` on its own behalf — e.g. `Bonding` itself, `Zap`, `Pair`, `Token`, the LT, or any other non-participating contract deployed on the chain — every future creator-share of the 0.75% Alt Fun fee for that token accrues into `creatorBalance[newCreator]` in `FeeVault` and is unclaimable forever, exactly as tokens sent to `address(engine)` in the original `PrimitiveEngine.withdraw` report become permanently stuck.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any token creator (an unprivileged, permissionless role obtained simply by calling `Zap.createToken`). Every subsequent buy/sell against that token accrues creator fees that can never be claimed, for the lifetime of the token. Given the fee stream compounds with trading volume, the frozen amount is unbounded and grows with usage — satisfying the "permanent freezing of creator funds" impact bar.

### Likelihood Explanation
Likelihood is Medium: the trigger requires the creator's own action (calling `transferCreator` with a bad `newCreator`), so it is primarily an "Alice fat-fingers the recipient" scenario rather than a third-party attack — precisely analogous to the original report's exploit scenario ("Alice... accidentally specifies the address of the recipient as the engine address"). It could also be triggered adversarially against a compromised/griefed creator key, or by a phishing/UI bug that defaults `newCreator` to a known contract address (e.g. copy-pasting the `Bonding` or `Zap` proxy address instead of a wallet).

### Recommendation
- **Short term:** In `transferCreator`, reject `newCreator` values equal to any of the protocol's own contracts that cannot call `claim()` — at minimum `address(this)` (`Bonding`), the registered `Zap`/router addresses, `info.pair`, `tokenAddress` itself, and the token's `ltAddress`. More robustly, require the new creator to prove reachability (e.g. via a two-step accept pattern where `newCreator` must call an `acceptCreator` function, mirroring `Ownable2StepUpgradeable`'s pattern already used elsewhere in the codebase, such as `FeeVault`'s `Ownable2StepUpgradeable` owner transfer).
- **Long term:** Add an Echidna/invariant test asserting that for every token, `Bonding.tokenInfo(token).creator` is always an address capable of calling `FeeVault.claim()` (i.e., never a known protocol contract), and that `FeeVault.creatorBalance[creator]` is eventually claimable for any creator set via `transferCreator`.

### Proof of Concept
1. Creator launches a token via `Zap.createToken(...)`, becoming `Bonding.tokenInfo(token).creator`.
2. Creator calls `bonding.transferCreator(token, address(bonding))` (or `address(zap)`, or the token's own `pair`/`ltAddress`) — this succeeds because the only checks are `newCreator != address(0)` and `newCreator != info.creator`.
3. Any subsequent trade through `Zap.buy`/`Zap.sell` accrues the creator-share of the 0.75% fee to `FeeVault.creatorBalance[address(bonding)]` via `_accrueFee` → `FeeVault.accrue`.
4. No caller can ever satisfy `msg.sender == address(bonding)` in `FeeVault.claim()`, since `Bonding` has no function that calls out to `FeeVault.claim()` on its own behalf, so the balance is permanently frozen in `FeeVault`.

    function _accrueFee(
        address token,
        address creator,
        uint256 feeAmount,
        bool isBuy
    ) internal {
        ZapStorage storage $ = _s();
        uint256 creatorShare = (feeAmount * $.creatorFeeBps) / BPS_DENOM;
        uint256 protocolShare = feeAmount - creatorShare;
        $.usdc.safeTransfer(address($.feeVault), feeAmount);
        $.feeVault.accrue(token, creator, creatorShare, protocolShare, isBuy);
    }

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
