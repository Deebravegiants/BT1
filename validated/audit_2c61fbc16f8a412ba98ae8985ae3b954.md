### Title
Webhook `topic`/`shop-domain` headers are not covered by the HMAC signature, allowing cross-tenant/cross-topic webhook forgery via header replay - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`Request#initialize` (lib/shopify_api/webhooks/request.rb:45-63) only checks that the `shopify-topic`, `shopify-hmac-sha256`, and `shopify-shop-domain` headers are *present*, never that their values are bound to the request. `Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:12-22) and `Request#to_signable_string` (lib/shopify_api/webhooks/request.rb:35-38) confirm the signable string is `@raw_body` only, so the HMAC never covers `topic` or `shop-domain`. Because `api_secret_key` is a single per-app secret shared across every installing shop, any attacker who installs the target app on their own (attacker-controlled) development shop can capture one legitimately-signed `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with arbitrary `shopify-topic`/`shopify-shop-domain` header values, and `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) will accept it as valid.

### Finding Description
The broken binding, stated as an equality that the code should enforce but doesn't:

`HMAC_valid(raw_body, hmac) == true` should imply `(topic, shop_domain) == (topic_that_Shopify_actually_sent, shop_that_actually_sent_it)`, but in this codebase `HMAC_valid` is computed purely as a function of `raw_body`:

```
computed_signature = HMAC-SHA256(api_secret_key, raw_body)   # lib/shopify_api/utils/hmac_validator.rb:29,34-40
valid = secure_compare(computed_signature, header["hmac-sha256"])
``` [1](#0-0) [2](#0-1) 

`Request#initialize` only performs a presence check on the three headers and stores whatever values are supplied verbatim; it never cross-checks them against `@raw_body` or against each other: [3](#0-2) 

`topic` and `shop` are read straight from those unauthenticated headers: [4](#0-3) 

`Registry.process` gates only on `HmacValidator.validate(request)` and then dispatches purely on `request.topic`, forwarding `request.shop` unchecked into `WebhookMetadata`, which is the value the host app's `WebhookHandler#handle` implementation is expected to trust as "which merchant this event is about": [5](#0-4) [6](#0-5) 

**Attacker path (no privileged credentials required):**
1. Per the threat model, the attacker creates their own development shop and installs the target app on it — a fully legitimate, unprivileged action.
2. Shopify sends the attacker a real webhook delivery for their own shop: `raw_body = B`, `X-Shopify-Hmac-Sha256 = H = HMAC(api_secret_key, B)`, `X-Shopify-Topic = T_own`, `X-Shopify-Shop-Domain = attacker-shop.myshopify.com`.
3. The attacker replays `(B, H)` to the same app webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or `X-Shopify-Topic: <different topic the app has a handler for>`.
4. `Request.new` accepts this because it only checks header presence (lib/shopify_api/webhooks/request.rb:50-59).
5. `HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` — since `api_secret_key` is the same across every shop that installs the app, this still equals `H`, so validation **succeeds** (lib/shopify_api/utils/hmac_validator.rb:12-22, 26-31).
6. `Registry.process` dispatches to the handler registered for the forged topic and passes `shop: "victim-shop.myshopify.com"` (attacker-chosen, never verified) plus `body: parsed_body` (from the attacker's own legitimately-obtained payload) into the app's business logic.

This defeats the intended guarantee entirely: the library's only integrity check (`HmacValidator`) protects body authenticity/integrity assuming the app author trusts `request.topic`/`request.shop` as authenticated metadata about that body — but nothing in this gem binds those header values to the signature or to the body's actual origin. Presence-of-header ≠ authenticity-of-header-content, exactly as the question states, and no other guard (`ShopValidator`, `Context.setup?`, Sorbet typing) intervenes here — Sorbet only checks that the header values are `String`, not that they are truthful.

### Impact Explanation
An unprivileged attacker who legitimately installs the app on their own shop can:
- Make the app believe an arbitrary attacker-chosen body belongs to `victim-shop.myshopify.com` (or any other shop string), causing cross-tenant data confusion in any app logic that keys per-tenant state, storage writes, or actions off `WebhookMetadata#shop`.
- Trigger any topic-handler pairing the app has registered (e.g. `customers/redact`, `shop/redact`, `app/uninstalled`) against a forged shop-domain string, using a body the attacker fully controls the shape of because they chose which webhook subscription to trigger on their own dev shop.
- Repeat this indefinitely and against arbitrary target shop-domain strings, since nothing about the exploit depends on the victim shop at all (the value is never validated against real installation records inside this gem).

This is a genuine cross-tenant/authentication-bypass class finding: an unauthenticated, attacker-supplied value (`shop-domain`/`topic` header) is trusted by the library as if it had been authenticated by Shopify's HMAC, matching the "Critical - cross-tenant access" category. The severity of the blast radius, however, depends on what the host app's `WebhookHandler#handle` implementation actually does with `data.shop` — this gem hands the value off but does not itself perform any privileged, tenant-scoped mutation, so the concrete exploitability is app-dependent even though the root defect is squarely in this gem.

### Likelihood Explanation
Preconditions are minimal and entirely within the stated attacker capabilities: the attacker only needs to install the target app on their own development shop (explicitly permitted) to obtain one valid `(raw_body, hmac)` pair signed with the app's single, shop-independent `api_secret_key`. No credential theft, no TLS interception, no social engineering is required — the attacker crafts and sends the forged HTTP request themselves, since headers are attacker-controlled per the rules. The attack is cheap, deterministic, and repeatable against any topic the app registers and any shop-domain string.

### Recommendation
- Do not rely solely on `HmacValidator.validate` for header-content authenticity. Either:
  - Change `Request#to_signable_string` to include the security-relevant headers (`topic`, `shop-domain`) in the signable string bound to the HMAC (this would require behavior Shopify's actual delivery HMAC computation must also produce, so this must match Shopify's real signing scheme — verify against Shopify's canonical webhook verification spec before changing the signable string), or
  - At minimum, document/enforce that `request.shop` must additionally be cross-checked by the host application against the shop's known installation record (e.g. an existing, previously-persisted session/access token for that shop) before being trusted for any tenant-scoped action, and add that check inside `Registry.process` if this gem intends to provide that guarantee itself.
- Add validation in `Request#initialize` or `Registry.process` that rejects shop-domain values that are not valid `*.myshopify.com` hostnames (defense in depth, does not by itself fix the core signing gap).

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_process_accepts_forged_shop_and_topic_with_valid_body_hmac
  ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)

  raw_body = '{"id":1}'
  real_hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", "secret", raw_body))

  handler = mock
  handler.expects(:handle).with(
    data: has_attributes(shop: "victim-shop.myshopify.com", topic: "customers/redact")
  )
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "customers/redact", delivery_method: :http, path: "/x", handler: handler
  )

  forged_headers = {
    "shopify-hmac-sha256" => real_hmac,          # captured from attacker's own shop delivery
    "shopify-topic" => "customers/redact",        # forged: was not the topic Shopify actually sent for this body
    "shopify-shop-domain" => "victim-shop.myshopify.com", # forged: attacker's shop was actually attacker-shop.myshopify.com
  }
  request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

  # Binding under test:
  # LHS: HmacValidator.validate(request)   -> should be false when topic/shop are forged
  # RHS: false
  assert(ShopifyAPI::Utils::HmacValidator.validate(request)) # currently true -- demonstrates the gap
  ShopifyAPI::Webhooks::Registry.process(request) # succeeds and dispatches to victim-shop handler
end
```
This demonstrates that `Request.new` constructs successfully and `HmacValidator.validate`/`Registry.process` accept a body/HMAC pair paired with attacker-chosen `topic`/`shop-domain` values that were never actually sent together by Shopify.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
