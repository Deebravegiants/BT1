### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw JSON body, but the `shop` identity that gets handed to the application's webhook handler is read directly from the unauthenticated `shopify-shop-domain` HTTP header, which is never part of the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are all pulled from HTTP headers, which are outside of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC using only `to_signable_string` (the body) and then constructs `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id`, none of which were authenticated by the signature check: [3](#0-2) 

`HmacValidator.validate` computes the HMAC solely from `verifiable_query.to_signable_string`: [4](#0-3) 

The broken identity binding is:
`request.shop` (header, used to attribute the webhook to a tenant) ≠ `HMAC-covered bytes` (`@raw_body` only).

Because the signature only binds the body, an attacker who obtains one valid `(body, HMAC)` pair — for example by triggering a webhook to their own development/trial store, which any unprivileged user can create — can replay that exact body and HMAC to the target app's public webhook endpoint while substituting an arbitrary value in the `shopify-shop-domain` header (or `x-shopify-shop-domain`). `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will dispatch the handler believing the event came from the victim shop specified in the forged header.

This directly parallels the external report's root-cause pattern: a value that is acted upon by privileged logic (there: the collateral asset transferred/spent; here: the `shop` identity attributed to the webhook) is not actually covered by the binding mechanism that is supposed to guarantee its authenticity (there: the balance/transfer step; here: the HMAC signature).

### Impact Explanation
Any application built on this gem that uses `data.shop` from the webhook handler (as documented, e.g. to look up the store's session/access token, or to scope a database write) can be made to process a maliciously-labeled webhook as if it originated from an arbitrary victim shop. This is a cross-tenant confusion vector: an unprivileged attacker, using only their own store's legitimately signed webhook payload, can cause the host application to attribute webhook data/actions to a different, victim tenant, since the gem's HMAC check gives no cryptographic assurance over `shop`, `topic`, or `webhook_id`.

### Likelihood Explanation
Likelihood is high for any app that exposes an HTTP endpoint calling `ShopifyAPI::Webhooks::Registry.process`, as documented in this gem's webhook usage guide. The attacker only needs:
1. Their own Shopify (dev) store to trigger any real webhook and capture a valid `(raw_body, hmac)` pair — no privileged credentials of the target required.
2. Ability to send an HTTP POST to the target app's public webhook endpoint with a forged `shopify-shop-domain` header — trivial for an unprivileged internet user.

### Recommendation
Bind the identity headers into the signed content, or otherwise verify them out-of-band before trusting them:
- Include `shop`, `topic`, and `webhook_id` in the value passed to `HmacValidator`/`to_signable_string`, or
- Cross-check `request.shop` against a `shop_domain`/`shop_id` field embedded in the signed JSON body (when Shopify includes one) before dispatching to the handler, and reject the webhook if they disagree.

### Proof of Concept
1. Attacker creates a free/dev Shopify store and installs the target app, receiving a legitimately signed webhook for that store, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC over body B>
x-shopify-shop-domain: attacker-store.myshopify.com
x-shopify-webhook-id: <id>
Body: B
```
2. Attacker replays the exact same `Body: B` and `x-shopify-hmac-sha256` value to the target app's public webhook endpoint, but changes the header:
```
x-shopify-shop-domain: victim-store.myshopify.com
```
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `Body: B` only (per `Request#to_signable_string`) and it matches — validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using `shop = "victim-store.myshopify.com"` from the forged header, and invokes the registered handler as though the event came from the victim store. [5](#0-4) [3](#0-2)
