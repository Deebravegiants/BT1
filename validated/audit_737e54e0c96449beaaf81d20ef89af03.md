### Title
Webhook shop identity spoofing via unsigned `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by HMAC-validating the raw request body against the app's `client_secret`, then passes the shop identity extracted from an entirely unsigned HTTP header to the app's `WebhookHandler`. Because the `shop` value that downstream code uses to attribute the event to a tenant is not part of the signed material, an attacker who can produce a body/HMAC pair valid for the shared app secret can attach an arbitrary `shop-domain` header, causing the webhook to be processed as if it originated from a different merchant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is computed from the `hmac-sha256` header value: [4](#0-3)  and [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers with no cryptographic binding to the body: [5](#0-4) .

`Registry.process` validates only `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` (the raw body) against `Context.api_secret_key`: [6](#0-5) . After this single check passes, `Registry.process` builds `WebhookMetadata` directly from the unauthenticated `request.shop` header and forwards it to the app-defined handler as the tenant identity: [3](#0-2)  and [7](#0-6) . The gem's own documented usage pattern feeds `data.shop` straight into shop-scoped background work (e.g. `perform_later(shop_domain: data.shop, ...)`), so any host app following this gem's documented pattern trusts `data.shop` as the tenant identifier: [8](#0-7) .

This breaks the intended equality "the shop that authenticated the request (via a valid HMAC over the shared secret) == the shop the app processes data for." Any actor who can obtain one valid `(body, hmac)` pair signed with the app's single shared `api_secret_key` — most simply, by installing the app on their own shop and having it send that app a real webhook — can replay that same body/HMAC while substituting the `shopify-shop-domain` header for a victim shop, since the header is outside the signed scope.

### Impact Explanation
This is a cross-tenant identity confusion in a multi-tenant Shopify app: a request cryptographically proven only to originate from the app's secret (not from any specific shop) is attributed to an arbitrary shop chosen by the attacker. Depending on the handler's logic (as shown in the gem's own documented example), this can cause the app to process/store data, trigger shop-scoped jobs, or overwrite state under a victim shop's identity, i.e., cross-tenant access/data injection.

### Likelihood Explanation
Any developer/merchant who has installed the target app on a shop they control can trivially obtain a legitimately HMAC-signed webhook body/signature pair (since `api_secret_key` is shared across all tenants of the app, not shop-specific), and then re-POST it to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header set to any other shop. No secrets belonging to the victim shop are needed.

### Recommendation
Bind the shop identity into the authenticated material before dispatching to the handler: e.g., verify that the `shop-domain` header matches an active, previously-registered webhook subscription/session for that specific topic and webhook id (looked up server-side, not merely echoed from the header), or require the host application to independently confirm the shop exists in its own session store before trusting `WebhookMetadata#shop`. At minimum, document prominently that `data.shop` is unauthenticated and must not be used as a sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering a legitimate webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)` and `api_secret_key` is the same for every install of this app).
2. Attacker resends the same body `B` and header `shopify-hmac-sha256: H` to the app's webhook endpoint, but changes `shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B`/`H` against `api_secret_key`: [6](#0-5) .
4. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop = "victim.myshopify.com"` taken from the forged header, and passed to the app's handler as though Shopify sent this event for the victim shop: [9](#0-8) .
