The report describes a bug class where an accounting function fails to account for a field/data not properly tied to what's verified. The closest structural analog in this gem is in the webhook signature verification: the HMAC only signs the raw request body, but the `shop` (and `topic`/`webhook_id`) attribution used downstream by the application comes from unauthenticated HTTP headers that are never included in the signed payload.

### Title
Webhook shop-domain attribution is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are not part of the signed bytes [2](#0-1) . `Registry.process` verifies only this body-only HMAC and then trusts `request.shop` to build `WebhookMetadata` passed to the app's handler [3](#0-2) .

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` value [4](#0-3) . For webhooks, `to_signable_string` is defined as just `@raw_body` [1](#0-0) , so the HMAC binds only the JSON body — it says nothing about which shop the webhook headers claim to be from.

The equality that should hold is: `hmac == HMAC(shop_header ‖ body)`, but the actual implementation only enforces `hmac == HMAC(body)`. `request.shop`, taken from the `x-shopify-shop-domain`/`shopify-shop-domain` header, is used unchecked [5](#0-4) .

`Registry.process` documents that it "will verify the request did indeed come from Shopify" [6](#0-5) , then raises unless `HmacValidator.validate` passes, and forwards `request.shop` straight into the handler payload without any comparison against the signed body [3](#0-2) .

Because the shop attribution is decoupled from the signed bytes, any party who can obtain one genuine, validly-signed webhook body/HMAC pair (trivially done by installing the target app on their own free/dev store and triggering a webhook for a topic they control) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. The HMAC still validates (it only covers the body), but the app's handler now believes the payload belongs to a different shop.

### Impact Explanation
This breaks the tenant-attribution guarantee the gem's `Registry.process` claims to provide, letting an unprivileged actor who controls one shop's webhook stream inject data attributed to an arbitrary victim `shop` domain into the app's webhook handling logic — a cross-tenant confusion at the framework level, since nothing in the gem ties the header-derived `shop` to the cryptographically verified bytes.

### Likelihood Explanation
Any user can sign up for a free Shopify development store, install the target app, and trigger genuine webhook deliveries to capture valid `(raw_body, hmac)` pairs for topics under their control. They then only need to be able to POST directly to the app's webhook endpoint with a modified `shop`-domain header — no access token, `client_secret`, or privileged account is required.

### Recommendation
Bind the shop (and ideally topic) into the signed material, or require the caller to independently verify the shop header against an authenticated source (e.g., cross-check against the caller's own OAuth session store) before trusting `WebhookMetadata#shop`, rather than deriving tenant identity solely from an HMAC-unauthenticated header.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) to receive a real payload with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of body>`.
2. Attacker replays the exact same `raw_body`/`hmac` to the app's webhook controller, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks the body against the hmac [4](#0-3) .
4. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` and invokes the app handler as if the data came from `victim-shop.myshopify.com` [7](#0-6) .
