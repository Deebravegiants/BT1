### Title
Webhook shop-domain identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#to_signable_string` returns only the raw request body, so `HmacValidator.validate` cryptographically authenticates the body bytes but never the `shop`, `topic`, `webhook_id`, or `api_version` values. Those fields are read directly from HTTP headers (`shopify_header`) with no cryptographic binding to the signed body, yet `Registry.process` trusts `request.shop` as the verified tenant identity when constructing `WebhookMetadata` passed to the app's handler.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to the `hmac` field [5](#0-4) . For webhooks, `to_signable_string` is defined as simply `@raw_body` [2](#0-1) . The `shop` accessor, however, is pulled from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no involvement in the signature computation [1](#0-0) .

`Registry.process` raises `InvalidWebhookError` unless `Utils::HmacValidator.validate(request)` passes, then immediately builds `WebhookMetadata` from `request.shop`, `request.topic`, etc., and hands it to the registered handler as authenticated data [3](#0-2) . `WebhookMetadata.shop` is a plain `String` field with no further verification step exposed by the gem [4](#0-3) .

This breaks the intended binding: `shop reported by "verified" WebhookMetadata == shop that actually produced/authorized the signed body`. Because all Shopify apps share a single `client_secret` across every installed shop, the same secret produces the same HMAC for a given body regardless of which shop the body came from. An attacker who controls (or has access to) any one shop that has the app installed can capture a legitimate `(raw_body, hmac)` pair from their own webhook deliveries, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the gem lets a party who legitimately controls one tenant (any shop with the app installed) forge webhook events attributed to a different, victim tenant, because the "verified" `shop` field is not covered by the signature that the gem itself validates. Any app relying on `WebhookMetadata#shop` (the field this gem specifically hands to handlers after "validating" the webhook) to select which merchant's session/data/token to act on can be made to act on a victim shop's session/data using attacker-controlled webhook content, which the rules classify as cross-tenant access.

### Likelihood Explanation
Exploitation only requires the attacker to have (or obtain) their own store with the target app installed, which is realistic for any app usable on a free/dev store, plus the ability to send an arbitrary HTTP request to the app's public webhook endpoint with modified headers and a replayed body — no access to the `client_secret`, access tokens, or any privileged account is required, and the HMAC check itself will pass by design because it was never scoped to the shop identity.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind `request.shop` to the verified body (e.g., by having `to_signable_string` incorporate the shop header, or by cross-checking the header-derived shop against a shop identity embedded in the signed payload) so that `HmacValidator.validate` actually authenticates which shop a webhook body was generated for before `WebhookMetadata` is constructed.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and capture a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for the app's shared `client_secret`).
2. Replay to the app's webhook endpoint the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` (`B`) only and matches `H`, so validation passes [6](#0-5) .
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [7](#0-6) , causing the app to process attacker-controlled data under the victim shop's identity.
