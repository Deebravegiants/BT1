### Title
Tron IntentGatewayV2 uses raw `.call` with `IERC20.transfer.selector` and only checks call-success, not the returned boolean, silently accepting failed ERC-20 transfers on escrow release - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` (unlike the EVM `evm/src/apps/intentsv2/IntentsBase.sol`, which imports OpenZeppelin's `SafeERC20` and uses `safeTransfer`/`safeTransferFrom` throughout) still pays out escrowed order funds using a raw low-level `.call` with the manually-encoded `IERC20.transfer.selector`, checking only that the external call itself did not revert (`success`) rather than validating the returned boolean via `SafeERC20`.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the internal `withdraw()` function — invoked from both `onGetResponse` (cross-chain cancellation refund path) and the fill/redeem-escrow path — releases escrowed order tokens to a beneficiary like this: [1](#0-0) 

For every non-native token it does:
```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
This pattern only reverts if the low-level call itself reverts. Any ERC-20 implementation that is non-compliant and returns `false` (instead of reverting) on a failed transfer — e.g. a paused/blacklisted-recipient token, a token with hooks that fail gracefully, or one enforcing an allowance/limit check that returns `false` — will make `success == true` even though no tokens moved. The code proceeds to treat the transfer as successful: it has already decremented `_orders[commitment][token]` before the call (`_orders[body.commitment][token] -= amount` is done prior in the same loop iteration order shown), finalizes `_filled[commitment]`, and emits `EscrowReleased`/`EscrowRefunded`. The same unsafe pattern recurs for the transaction-fee payout and in the `SweepDust` handler: [2](#0-1) 

Additionally, the intermediate call-dispatcher sweep path builds `Call` structs with the same unchecked selector encoding: [3](#0-2) 

By contrast, the canonical EVM `IntentsBase.sol` already fixed this exact class by importing `SafeERC20` and using `safeTransfer` for all beneficiary payouts: [4](#0-3) 

The Tron contract imports `SafeERC20` and declares `using SafeERC20 for IERC20;` but does not actually apply it to the beneficiary-facing `withdraw()` payout path, leaving the raw, return-value-blind `.call` in place.

### Impact Explanation
This is the escrow-release path a solver or user reaches after a legitimate fill or a timed-out/cancelled order — a single unprivileged transaction (fill/select/cancel flow culminating in `withdraw`). If the output/input token is a non-standard ERC-20 that returns `false` rather than reverting on failure, the contract will mark the order `_filled`/refunded and decrement escrow accounting while the beneficiary receives nothing. The tokens remain trapped in the `IntentGatewayV2` contract with no accounting entry pointing to them (since escrow was already zeroed and the order marked finalized), and cannot be re-claimed by the intended beneficiary — a permanent freezing/loss of user or solver funds.

### Likelihood Explanation
Likelihood depends on the specific tokens supported on Tron deployments; many TRC-20/bridged tokens on Tron are non-standard or wrap conditional restrictions (blacklists, pausability) that return `false` instead of reverting, which is a well-documented category of "weird ERC-20" behavior. Since IntentGatewayV2 is designed to support arbitrary user/solver-specified tokens for cross-chain intents, this is a realistically reachable configuration rather than a purely theoretical one.

### Recommendation
Apply `SafeERC20.safeTransfer` (already imported and aliased via `using SafeERC20 for IERC20;`) consistently in `withdraw()`, the transaction-fee payout, and `_sweepDust`'s equivalent Tron handler, replacing the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern, mirroring the fix already applied in `evm/src/apps/intentsv2/IntentsBase.sol`. For the `ICallDispatcher`-routed sweep calls that must remain as raw low-level calls (since they execute via a separate dispatcher contract), ensure the dispatcher's `dispatch()` decodes and validates the ERC-20 boolean return value (not just call success) before treating the sweep as complete.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron) with an output/input token `T` that implements `transfer` to return `false` on failure without reverting (e.g., a blacklist-style token where the beneficiary address is later blacklisted, or any token that returns `false` under an internal cap/pause condition).
2. A user places an order escrowing `T`; a solver fills it, or the order expires and is cancelled.
3. When `withdraw()` executes and the beneficiary is in a state that makes `T.transfer` return `false` (but not revert), `success` from `token.call(...)` is still `true` because the call itself didn't revert. [5](#0-4) 
4. `_orders[body.commitment][token]` has already been decremented and `_filled[body.commitment]` set, and `EscrowReleased`/`EscrowRefunded` is emitted — the order is permanently finalized as fulfilled, yet the beneficiary never received the tokens, which remain stuck in the gateway contract.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
