### Title
`instance()` fallback to `address(this)` for unregistered state machines allows authentication bypass in Tron `IntentGatewayV2` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
This mirrors the Nayms "not all objects are existing objects" bug class: a lookup mapping (`_instances`) that is not populated for every valid key silently falls back to a value (`address(this)`) that collides with a legitimate identity, letting an unregistered/"non-existing" chain be treated as an authenticated one. The fixed EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol`) reverts on this exact case, while the Tron variant does not.

### Finding Description
`IntentGatewayV2.instance()` in the Tron contracts resolves the gateway address registered for a source state machine: [1](#0-0) 

```
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

`_instances` is only populated via governance/`NewDeployment` messages (`_addDeployment`). For any `stateMachineId` that has never had a deployment registered — i.e., a "non-existing" object in the mapping, exactly analogous to Nayms's `existingObjects` gap — `instance()` does not revert; it silently returns `address(this)`, the gateway's own address. `authenticate()` then accepts any incoming request whose `from` field equals `address(this)`.

Contrast with the corrected/"fixed" logic used elsewhere in the same codebase: [2](#0-1) 

```
function _instance(bytes calldata stateMachineId) internal view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
```

The EVM `IntentsBase._instance()` treats an unregistered chain as a hard error (`UnknownInstance`), never as an authenticated identity. The Tron contract keeps the vulnerable default-fallback pattern the Nayms report describes: a mapping's "empty"/default value (`address(0)` → remapped to `address(this)`) is treated as a valid, trusted identity instead of "does not exist."

This is reachable by `onAccept`, the entry point for all dispatched governance-style messages processed by the gateway (RedeemEscrow, NewDeployment, UpdateParams, SweepDust, RefundEscrow), which is gated solely by `authenticate(request)`.

### Impact Explanation
Any attacker who can get the ISMP `EvmHost`/handler on the Tron deployment to deliver a `PostRequest` whose `source` is a state machine the `IntentGatewayV2` instance has never registered (`_instances[keccak256(source)] == 0`), and whose `from` field is set to the gateway's own address, passes `authenticate()` and is treated as a legitimate peer gateway instance. This grants access to privileged `RequestKind` operations dispatched through `onAccept`, including:
- `NewDeployment` — attacker can register an attacker-controlled `gateway` address for any state machine, subsequently allowed to forge further authenticated cross-chain messages.
- `UpdateParams` — attacker can change `host`, `dispatcher`, fee parameters, etc.
- `RedeemEscrow` / `RefundEscrow` — attacker can redeem/withdraw escrowed order funds to an attacker-chosen beneficiary.
- `SweepDust` — attacker can sweep accumulated fees.

This satisfies the "unauthorized app action" / "theft of funds" bar: it is a full authentication bypass on a privileged, fund-custodying cross-chain application entry point.

### Likelihood Explanation
Exploitation requires the attacker to control a contract with address exactly equal to `address(this)` (the target `IntentGatewayV2` instance) on some *other* state machine that the Hyperbridge host still accepts state proofs from but for which the intents deployment has not registered an instance. Since cross-chain protocols like this are commonly deployed via deterministic CREATE2 factories with fixed bytecode/salt to get identical addresses across chains, an attacker can plausibly redeploy an arbitrary (even blank) contract at that identical address on any chain not yet configured with a `NewDeployment`, and dispatch a forged `PostRequest` from it. This is a realistic, not purely theoretical, attack path, though it depends on deployment practices (deterministic factory reuse) and requires the target chain to still be a supported consensus/state-machine client of the Hyperbridge host used by this gateway.

### Recommendation
Change `IntentGatewayV2.instance()` (Tron) to revert on an unregistered state machine (as `IntentsBase._instance()` already does), instead of falling back to `address(this)`:
```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
```
Audit all other places in the codebase using a similar "default value doubles as a trusted identity" pattern (any `mapping(... => address)` or `mapping(... => bytes32)` whose zero/default value is treated as `address(this)`, a system identifier, or otherwise privileged) and make unregistered/non-existing entries fail closed rather than fail open.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron) via a deterministic CREATE2 factory at address `G` on chain `A` (the real, governance-configured deployment).
2. Attacker deploys arbitrary bytecode at the same address `G` on chain `B` (a state machine still supported by the Hyperbridge host but never configured via `NewDeployment` in `A`'s `_instances` map, i.e. `_instances[keccak256(B)] == address(0)`), using the same CREATE2 factory/salt/init-code, or otherwise obtains a contract at address `G` on chain `B`.
3. From chain `B`, dispatch (as `msg.sender == G`) a `PostRequest` with `source = B`, `to = G` (on chain A), `from = abi.encodePacked(G)`, and `body` set to a `RequestKind.NewDeployment`/`UpdateParams`/`RedeemEscrow` payload of the attacker's choosing.
4. Relay this request (with a valid state/consensus proof of chain `B`, which the host already supports generically) to the `EvmHost`/`HandlerV2` on chain `A`, triggering `IntentGatewayV2.onAccept`.
5. `authenticate(request)` computes `instance(B)`, which returns `address(this) == G` (since `_instances[keccak256(B)] == 0`), matching `module = G` derived from `from`. Authentication passes.
6. The attacker-supplied `RequestKind` body executes with full privilege (e.g., registers a malicious deployment, changes params, or redeems escrow to an attacker beneficiary).
