### Title
Unbounded silent merge of `assetNames`/`walletAccount` into existing trusted origin records without re-approval - ([File: features/connected-origins/module/connections.js])

### Finding Description
`ConnectedOrigins#add` looks up an existing record purely by the `origin` string via `#getOrigin` [1](#0-0) , and when a record exists it unions the caller-supplied `assetNames` with the origin's previously approved `assetNames` and writes the merged set back via `#setAttributes`, without requiring `trusted` to be freshly re-confirmed: [2](#0-1) 

`#setAttributes` performs a blind spread-merge of whatever `attributes` object is passed, keyed only by matching `connection.origin === origin`: [3](#0-2) 

Because `trusted: trusted ?? value.trusted` preserves the existing trust flag when the caller does not explicitly pass `trusted`, a call to `add({ origin, assetNames: [...] })` (with no `trusted` argument at all) still succeeds in expanding `assetNames` for an already-trusted origin. This is directly demonstrated by the existing unit tests, which call `add()` a second time with only `assetNames` and observe the merge persisting and `connectedAccountsAtom` being recomputed with the newly added asset's addresses for every enabled wallet account: [4](#0-3) [5](#0-4) 

`#setData` then recomputes `connectedAccountsAtom` for the full asset superset via `#getConnectedAssets`/`#getAccounts`, so once merged, `getConnectedAccounts()` will expose addresses for the newly merged assets: [6](#0-5)  and [7](#0-6) .

At this module boundary there is no mechanism that distinguishes "the user just re-approved this exact scope in a popup" from "the caller (whatever invoked `add()`) merely re-invoked `add()` with a larger `assetNames` array." The only identity check is the origin string equality in `#getOrigin`/`#setAttributes`.

### Impact Explanation
If any code path that eventually calls `connectedOrigins.add()` can be reached with attacker/dapp-influenced `assetNames` (or `walletAccount`) for an origin the user already trusted for one narrow asset, the origin's asset/account exposure silently expands, and `getConnectedAccounts()` will return addresses for assets/accounts the user never explicitly consented to for that origin. This breaks address-provider isolation between the origins a user has scoped-approved and violates the principle that consent must be explicit and scoped per invariant stated in the question.

### Likelihood Explanation
Within the `ConnectedOrigins` module itself, this merge behavior is unconditional and trivially triggerable — the unit tests in `connections.test.js` (lines 129-158, 302-327) already confirm that calling `add()` twice, the second time supplying only extra `assetNames` and no `trusted` flag, is sufficient to expand the stored `assetNames` and recompute `connectedAccountsAtom`. However, I could not locate, within the indexed portion of this codebase, the RPC/background message handler that receives raw dapp/website `connect` requests and decides what `assetNames`/`trusted` values get passed into `connectedOrigins.add()`. The documented provider flows (`solana.connect()`, `BitcoinProvider.connect()`) state that a pop-up is shown for user approval on every `connect()` call, which suggests the actual attacker-reachable RPC boundary may gate this before calling `add()`. I was not able to confirm or rule out whether that gating passes through attacker-controlled `assetNames` unchanged, or whether it always re-derives `assetNames` from what the user approved in the popup for that call. This part of the trace is incomplete given the available index.

### Recommendation
Do not let `add()` merge `assetNames`/`walletAccount`/`trusted` for an existing record unless the call is explicitly marked as a fresh, user-confirmed approval (e.g., require an explicit `trusted: true` and a distinct "freshly approved assetNames" list from the approval UI, rather than merging arbitrary caller-supplied `assetNames` into the stored set by default). Consider splitting "read/derive existing merged connection" from "write new approved scope," so that expanding scope always requires the caller to have gone through the approval popup for exactly the new assets being requested, and audit/trace all call sites of `connectedOriginsApi.add` to confirm none pass dapp-controlled `assetNames` without a corresponding fresh consent action.

### Proof of Concept
Integration test against `ConnectedOrigins` (module level, using the existing test harness in `features/connected-origins/module/__tests__/connections.test.js`):
1. Call `connectedOrigins.add({ origin: 'exodus.com', name, icon, connectedAssetName: 'ethereum', assetNames: ['ethereum'], trusted: true })` — simulate the user's one-time approval for `ethereum` only.
2. Call `connectedOrigins.add({ origin: 'exodus.com', assetNames: ['ethereum', 'solana', 'bitcoin'] })` — no `trusted` flag, simulating a subsequent unprivileged/non-approval-gated call.
3. Assert that `connectedOriginsAtom.get()` for `exodus.com` still has `assetNames` equal to `['ethereum']` and `trusted` remains from the original approval only (expected to fail against current code, which merges to `['ethereum','solana','bitcoin']`).
4. Assert `connectedOrigins.getConnectedAccounts({ origin: 'exodus.com' })` addresses do not include `solana`/`bitcoin` addresses (expected to fail against current code, since `connectedAccountsAtom` is recomputed with the merged superset).

  add = async ({
    connectedAssetName,
    origin,
    name,
    icon,
    assetNames = [],
    trusted,
    favorite,
    walletAccount,
  }) => {
    const value = await this.#getOrigin({ origin })

    const allConnectedAssetNames = new Set([
      connectedAssetName,
      ...assetNames,
      ...(value?.assetNames ?? []),
    ])

    if (value) {
      await this.#setAttributes({
        origin,
        attributes: {
          icon: icon ?? value.icon,
          name: name ?? value.name,
          connectedAssetName: connectedAssetName ?? value.connectedAssetName,
          trusted: trusted ?? value.trusted,
          favorite: favorite ?? value.favorite,
          assetNames: [...allConnectedAssetNames],
          walletAccount: walletAccount ?? value.walletAccount,
        },
      })

      return
    }

    await this.#addNewItem({
      origin,
      icon,
      name,
      connectedAssetName,
      trusted,
      favorite,
      assetNames: [...allConnectedAssetNames],
      walletAccount,
    })
  }
