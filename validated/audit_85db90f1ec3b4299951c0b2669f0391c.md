### Title
Webhook shop-domain header is not cryptographically bound to the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by validating only the raw JSON body against the `x-shopify-hmac-sha256` signature. The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from unauthenticated HTTP headers and are never included in the signed content, so nothing binds the verified signature to the shop the data is subsequently attributed to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all parsed from headers that are excluded from the HMAC computation: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e. against the body alone: [3](#0-2) 

`Registry.process` trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build `WebhookMetadata` for the handler as soon as HMAC validation of the body succeeds: [4](#0-3) 

This breaks the identity binding `shop_authenticated == shop_acted_on`: the HMAC authenticates the *body bytes*, but the code acts on the *shop header value*, which is never covered by that signature. Anyone who can obtain one genuine `(body, hmac)` pair signed with the app's `api_secret_key` — trivially achievable by installing the app on their own store and capturing one of its own legitimate webhook deliveries — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a different (victim) shop. `HmacValidator.validate` will still pass because the signed bytes (the body) are unchanged, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This is a cross-tenant integrity issue for any consumer of this gem's `Webhooks::Registry`: a host application that keys its business logic (order/customer records, uninstall handling, GDPR-topic processing, billing state, etc.) off `WebhookMetadata#shop` can be made to attribute an attacker-controlled but genuinely-signed payload to a completely different merchant's tenant, since the gem provides no protection binding the shop identity to the signature. Per the rubric this maps to Critical - cross-tenant access, because data intended for/about one merchant can be injected into another merchant's tenant context purely by forging an unauthenticated header.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be able to install the target app on a shop they control (any Shopify Partner/developer store, freely available to any internet user) so a legitimately signed webhook can be captured, and (2) sending a crafted HTTP POST to the app's public webhook endpoint with the captured body/HMAC and a spoofed `x-shopify-shop-domain` header. No access token, `api_secret_key`, or privileged account for the *victim* shop is needed. This is a low-effort, realistically reachable attack path for any unprivileged internet user who can self-register a Shopify development store.

### Recommendation
Bind the shop (and ideally topic/webhook id) to the authenticated request. Options:
- Have `Request#to_signable_string` (or a Shopify-verified out-of-band mechanism) incorporate the shop domain, or
- After validating HMAC over the body, cross-check the delivered `shop` against a shop known to be legitimately associated with the topic/webhook subscription (e.g., verify the shop is one the app has an active session/registration for) before invoking the handler, or
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and instruct consuming applications to independently verify shop identity (e.g., against their own installed-shop registry) before trusting it for any tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and its `x-shopify-hmac-sha256` header — both validly signed with the app's shared `api_secret_key`.
2. Attacker sends a new POST to the app's webhook endpoint with:
   - Same raw body and same `x-shopify-hmac-sha256` value captured above.
   - `x-shopify-shop-domain` header changed to `victim-shop.myshopify.com`.
   - `x-shopify-topic` left as the original registered topic.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC — see `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to process attacker-supplied data as if it originated from the victim shop.
