### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant identity confusion - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The `Registry.process` method verifies a webhook request by validating the HMAC over the raw request body only. The `shop-domain` header, which the gem exposes to the application as the tenant identifier (`WebhookMetadata#shop`), is never included in the signed payload. This breaks the identity binding `HMAC-authenticated bytes == bytes used to determine the tenant (shop)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the signature strictly against that signable string [2](#0-1) . Meanwhile, `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body [3](#0-2) .

`Registry.process` validates only the HMAC before dispatching to the handler, then constructs `WebhookMetadata` using `request.shop` taken straight from that unauthenticated header: [4](#0-3) . The gem's own documentation instructs integrators to treat `data.shop` as the authoritative tenant identifier for routing/storing webhook data (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that this field is expected to be trust-worthy for tenant scoping [5](#0-4) .

This mirrors the report's bug class: a field acted upon (the `shop` value used for tenant identity) is not covered by the authentication mechanism (the HMAC signs only the body). An attacker who legitimately owns a Shopify store the app is installed on receives real, correctly-HMAC-signed webhook deliveries for their own shop. Since the signature depends only on body bytes and the shared `client_secret`/`api_secret_key` — not on the `shop-domain` header — the attacker can capture such a genuine webhook and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still return true (the body and secret are unchanged), and `Registry.process` will dispatch to the handler with `WebhookMetadata#shop` set to the victim's domain while `body` reflects the attacker's own data.

### Impact Explanation
If application code (following the gem's documented contract) uses `data.shop` to select which tenant's database row/webhook queue to update, an attacker can inject data that is written to another merchant's account — a cross-tenant integrity violation. This fits the "cross-tenant access" impact category, since the tenant-binding equality `authenticated-body-owner == shop-used-for-storage` is broken by the gem's own header-vs-signature design.

### Likelihood Explanation
Exploitation requires the attacker to control (or run) at least one shop where the target app is installed, so they can receive an authentically-HMAC-signed webhook, and then replay it with a modified header to the app's public webhook endpoint. This is realistic for any app with public/open installation (e.g. Shopify App Store apps), since installing the app on an attacker-owned dev/trial store is normally free and requires no special privilege. No `api_secret_key`, access token, or other credential theft is required — only a header rewrite of a message the attacker already legitimately possesses.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) into the signed material, or otherwise cross-check the header-derived `shop` against a shop known from another authenticated source (e.g. the webhook subscription that Shopify's API records for a given topic + shop) before dispatching to the handler. At minimum, update `Request#to_signable_string` to incorporate the `shop-domain` header so `HmacValidator` fails when it is altered independently of the body, and document explicitly that `data.shop` must not be treated as authenticated unless this is done.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, triggering a genuine `orders/create` webhook with a valid HMAC for `client_secret`.
2. Attacker intercepts this legitimate HTTP POST (body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, header `x-shopify-hmac-sha256: H` where `H = HMAC(secret, B)`).
3. Attacker resends the identical body `B` and identical `x-shopify-hmac-sha256: H` to the app's webhook endpoint but rewrites `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `HmacValidator.validate` recomputes the HMAC over `B` only and it matches `H`, so `Registry.process` proceeds [6](#0-5) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's order data>, ...)`, causing the application to associate attacker-controlled webhook content with the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
