### Title
Missing existence check on `DeleteAccountAction::beneficiary_id` causes permanent token burn on self-inflicted typo/non-existent beneficiary - (File: runtime/runtime/src/actions.rs)

### Summary
`action_delete_account` pays out a deleted account's remaining balance to an arbitrary, user-supplied `beneficiary_id` without verifying that account exists. If the beneficiary account does not exist, the resulting balance-refund receipt fails and, because such receipts are "system" receipts, the failed refund is unconditionally burnt instead of being returned to anyone. This is the nearcore analog of the reported Solidity bug class: a critical "destination"/"authority" parameter (`newGovernor` in the report, `beneficiary_id` here) is only checked for *syntactic* validity, not for being a usable/existing target, and an invalid value leads to irreversible loss.

### Finding Description
`validate_delete_action` only validates that `beneficiary_id` is a well-formed `AccountId` string: [1](#0-0) 

It never checks that the account actually exists on-chain. `action_delete_account` then unconditionally schedules the deleted account's full balance to be sent to that `beneficiary_id` via a system balance-refund receipt: [2](#0-1) 

`Receipt::new_balance_refund` produces this as a system-originated `Transfer` action (`predecessor_id == "system"`), per the refund model documented in the repo: [3](#0-2) 

If that receipt fails to execute — which happens whenever the `receiver_id` (the `beneficiary_id`) does not correspond to an existing account, exactly as demonstrated for ordinary transfers in `test_refund_on_send_money_to_non_existent_account` (`ActionErrorKind::AccountDoesNotExist`) — the runtime's rule for failed system-predecessor receipts kicks in: [4](#0-3) 

Unlike a normal failed transfer (where the deposit is refunded back to the *predecessor*, e.g. `test_refund_on_send_money_to_non_existent_account`), a failed **system** receipt has no predecessor to refund to, so the amount is added to `stats.balance.other_burnt_amount` and permanently removed from circulation — this matches the explicit rule "If the execution of a refund fails, the refund amount is burnt" in `docs/RuntimeSpec/Refunds.md`.

### Impact Explanation
Any account owner who submits a `DeleteAccount` action with a syntactically valid but non-existent (e.g., mistyped, or previously-deleted, or never-created) `beneficiary_id` will have their entire remaining account balance permanently burnt rather than delivered anywhere. This is a direct, protocol-level analog of the reported "missing zero address check" bug: the missing validation on a value-routing destination parameter converts what should be a safe/refundable operation into an irreversible token loss, exactly the "loss of ownership/loss of funds forever" impact class described in the original report. This causes concrete token deflation (permanently reduces total supply / burns user funds) triggered purely by an unprivileged account's own transaction, with no cross-account exploitation needed for a self-loss, though it equally means anyone drafting a `DeleteAccount` transaction (e.g., wallets, tooling, or relayed meta-transactions) must get `beneficiary_id` exactly right or funds vanish silently.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires a user (or a bug in wallet/tooling/relayer code building the `DeleteAccount` action) to specify a beneficiary account that doesn't exist. This is plausible for typos, sub-account naming mistakes, or beneficiary accounts that get deleted/never funded between transaction construction and execution (a race is not even required — simply typing a mistaken but valid-format account id is enough). There is no signal or dry-run check that would catch this before the account and its funds are irreversibly destroyed.

### Recommendation
Add an existence check for `delete_account.beneficiary_id` before allowing `DeleteAccount` to proceed (analogous to adding the zero-address check recommended in the original report), e.g.:
- Reject `DeleteAccount` actions (during validation or execution) when `beneficiary_id` does not resolve to an existing account, returning an `ActionError` instead of silently burning funds.
- Alternatively/additionally, treat a failed balance-refund-to-beneficiary receipt the same as normal deposit refunds by falling back to a known-safe recipient (e.g., the deleting account's own predecessor/signer) rather than unconditionally burning it.

### Proof of Concept
1. Create account `alice.near` with a non-zero balance and a full-access key.
2. Submit a `DeleteAccount` transaction from `alice.near` with `beneficiary_id = "doesnotexist.near"` (syntactically valid, never created).
3. `validate_delete_action` passes (format-only check): [1](#0-0) 
4. `action_delete_account` deletes `alice.near` and enqueues `Receipt::new_balance_refund(&"doesnotexist.near", alice_balance)`: [2](#0-1) 
5. This refund receipt (predecessor = `system`) is later processed against the non-existent `doesnotexist.near`, fails with `AccountDoesNotExist` (same mechanism verified for ordinary transfers in `test_refund_on_send_money_to_non_existent_account`), and per `lib.rs:993-1000` the amount is added to `other_burnt_amount`, permanently destroyed instead of returned to `alice.near` or anyone else.
