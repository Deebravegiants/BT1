### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` identity used to route and label the resulting `WebhookMetadata` comes from an HTTP header that is never part of the signed bytes. An attacker who can obtain any one genuine, validly-signed webhook body (e.g., by installing the app on their own store) can resend that exact body with a forged `shop-domain` header for a different (victim) shop, and the gem will report it to the host application as an authenticated webhook for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which — per `VerifiableQuery`/`HmacValidator` — computes the HMAC over `to_signable_string` (i.e., body only) and compares it to the `hmac` derived from the `hmac-sha256` header: [3](#0-2) [4](#0-3) 

Once the HMAC passes, `request.shop` (the unauthenticated header value) is trusted and forwarded verbatim to the app's handler as the tenant identifier: [5](#0-4) 

The identity binding broken is: `shop verified by HMAC` ≠ `shop delivered to the handler`. The gem only proves "this body byte-string was signed with the app's secret" — it does not prove "this body was signed *for this shop*." Because a single `api_secret_key`/`client_secret` is shared across every shop that installs the app, any tenant that can trigger a genuine webhook for itself (trivial for a public app — install it on your own store and cause any event) obtains a `(raw_body, hmac)` pair that is valid for that secret regardless of which shop header accompanies it. Replaying that pair with a different `shop-domain` header value causes `Registry.process` to treat it as an authenticated webhook belonging to an arbitrary victim shop.

### Impact Explanation
This crosses the Critical bar of "cross-tenant access": a host application built on this gem — which is documented to trust `data.shop` as returned by `Registry.process` (see `docs/usage/webhooks.md`, "Process a Webhook") — has no way, using only what the gem gives it, to detect that the `shop` value is unauthenticated. An attacker (any shop that has legitimately installed the app) can inject events attributed to a shop they do not control, e.g. to trigger the mandatory `shop/redact` / `customers/redact` / `customers/data_request` compliance flows or app-specific business logic (data sync, billing, provisioning) against a victim tenant's data namespace.

### Likelihood Explanation
Medium-High: exploitation requires only an ordinary, unprivileged app installation by the attacker (no leaked secret, no TLS interception, no social engineering) and knowledge of the target's `.myshopify.com` domain, which is public/discoverable. The attacker simply captures one of their own real webhook deliveries and replays it with a modified header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the material that is authenticated, or otherwise cross-check the header-derived `shop` against a trusted source before dispatching to handlers. Concretely:
- Include the `shop-domain` header (and other identity-bearing headers) in `to_signable_string`, or
- Require host applications to additionally verify that `request.shop` corresponds to a shop with a known, previously-established session/installation before trusting `data.shop`, and document this requirement prominently, or
- Have `Registry.process` accept an expected shop (from the caller's own session lookup) and raise if it doesn't match `request.shop`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and legitimately receives any webhook, e.g. `orders/create`, from Shopify. This is a genuine request with header `X-Shopify-Shop-Domain: attacker.myshopify.com`, a raw JSON body `B`, and a valid `X-Shopify-Hmac-Sha256: H` computed by Shopify over `B` using the app's `client_secret`.
2. Attacker resends the exact same `B` and `H` to the app's webhook endpoint, but replaces the header with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-hmac-sha256" => H, ...})` is constructed.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds: [6](#0-5) 
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...))` is invoked, and the host application processes/attributes the event to `victim-shop.myshopify.com` even though that shop never sent it. [5](#0-4)
