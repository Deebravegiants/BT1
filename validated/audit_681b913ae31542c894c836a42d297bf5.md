### Title
Reputation-per-byte minting in `pallet-messaging-incentives` lets an actor farm uncapped, unbacked collator-selection reputation via self-relayed, low-value messages - ([File: modules/pallets/messaging-incentives/src/lib.rs])

### Summary
`pallet-messaging-incentives` mints a soulbound "reputation" asset to the relayer of every executed ISMP request message, scaled purely by payload byte-length (`rate * bytes`), with no linkage to the relayer fee actually paid by the message (which can be, and legitimately often is, zero for self-relayed messages). This reputation is the sole ranking criterion `pallet-collator-manager` uses to select block-producing collators each session. An actor can therefore dispatch and self-relay large, economically worthless, self-crafted requests through Hyperbridge's free `handle_unsigned` extrinsic to accumulate reputation without bound, exactly analogous to the referenced report's pattern of cheaply, repeatedly performing an action to inflate an internal point balance that carries real downstream value.

### Finding Description
`Pallet::on_executed` in `pallet-messaging-incentives` mints `rate * message_bytes` reputation to whichever account's signature is recovered as the relayer for each executed `Message::Request`, with the per-request byte count floored at 32 bytes but otherwise unbounded: [1](#0-0) [2](#0-1) 

Nothing here checks the fee attached to the request, or caps the mint rate against any real value delivered — the relayer fee on a dispatched request is explicitly optional and can be set to zero for self-relay: [3](#0-2) 

Messages reach `on_executed` through `pallet-ismp`'s `handle_unsigned`, a free, permissionless unsigned extrinsic that "permits anyone execute ISMP messages for free, provided they have valid proofs": [4](#0-3) 

The relayer identity credited for the mint is simply whoever's signature is embedded in the message (`relayer_for`), which the actor submitting the batch fully controls — they sign the message themselves. So an actor can: (1) dispatch arbitrary, large-body POST requests from a source chain they control, paying only source-chain gas and zero relayer fee, and (2) submit the resulting state proof to Hyperbridge via `handle_unsigned`, self-attributed as relayer, to mint `rate * bytes` reputation. This can be repeated indefinitely with new nonces/commitments (duplicate detection only prevents re-processing the *same* commitment, not new ones), at a cost proportional only to source-chain calldata gas — decoupled from the reputation minted, whose rate is set independently by governance via `set_mint_per_byte`.

This reputation asset is not a cosmetic score: `pallet-collator-manager::new_session` ranks all eligible candidate controllers strictly by their reputation balance and selects the top `desired_collators` to become the new collator (block-producer) set each session: [5](#0-4) 

Reputation is burned only for accounts actually selected in a given session; unselected accounts keep whatever they've accumulated, and can keep growing it before the next selection round: [6](#0-5) 

Documentation confirms this design intent — reputation is "the primary input to collator selection" and mirrors `$BRIDGE` earnings 1:1 for messaging relayers: [7](#0-6) 

### Impact Explanation
Because reputation is minted per byte with no ceiling and no requirement that the relayed message carry genuine economic value or fee, a well-resourced actor can flood Hyperbridge with large, self-dispatched, self-relayed, zero-fee "junk" requests to accumulate reputation far faster than genuine relayers earning it through real fee-paying traffic. Since `pallet-collator-manager` selects collators purely by reputation ranking, this lets the actor dominate or monopolize the collator set — the entities that author Hyperbridge blocks, order transactions, and (per `pallet-fishermen`) participate in state-commitment attestation. This is a direct threat to consensus/liveness/censorship-resistance guarantees of the Hyperbridge chain itself, not merely an accounting nuisance, making it at least a High-severity issue: an unbacked internal "points" system directly gates access to block-production authority.

### Likelihood Explanation
The attack requires no privileged access — any account can dispatch requests from any connected chain and submit `handle_unsigned` batches to Hyperbridge for free. The only cost is source-chain gas proportional to payload size, which is far cheaper than the value of controlling collator seats on the network. The mechanism is reachable by any unprivileged relayer/message-dispatcher, matching the "relayer fee and reward accounting" attack surface explicitly in scope.

### Recommendation
Decouple reputation minting from raw byte count and tie it instead to genuinely paid relayer fees (mirroring `$BRIDGE` payouts as documented), or introduce a rate-limiting/decay mechanism (e.g., per-account per-session mint caps, or reputation decay over time) so that reputation cannot be inflated by volume of self-generated, fee-free traffic. Consider requiring a minimum non-zero fee (with real economic cost) before a request's delivery can mint reputation, and/or cap the total reputation an account can accrue between successive collator-selection sessions.

### Proof of Concept
1. Attacker deploys a lightweight application contract on any Hyperbridge-connected EVM chain.
2. Attacker repeatedly calls `dispatch()` with `DispatchPost{ fee: 0, body: <large filler bytes>, ... }`, paying only source-chain gas (no relayer fee escrowed, per `IsmpDispatcher::dispatch_request`, `modules/pallets/ismp/src/dispatcher.rs:96-106`).
3. For each dispatched request, attacker constructs a `RequestMessage` with a `signer` field they control, obtains the source-chain state proof, and submits it via `pallet_ismp::handle_unsigned` (free unsigned extrinsic, `modules/pallets/ismp/src/lib.rs:373-382`).
4. `pallet-messaging-incentives::on_executed` runs, computes `bytes = max(body.len(), 32)` per request, and mints `MintPerByte * bytes` reputation to the attacker's signer account (`modules/pallets/messaging-incentives/src/lib.rs:126-187`), with no relation to the (zero) fee paid.
5. Attacker repeats steps 2-4 across many nonces/commitments — each is a distinct, valid commitment so duplicate-detection does not block reuse — accumulating reputation far exceeding what any genuine, fee-driven relayer earns.
6. At the next session boundary, `pallet-collator-manager::new_session` ranks candidates purely by this inflated reputation balance (`modules/pallets/collator-manager/src/lib.rs:511-542`), letting the attacker's controller account(s) dominate the collator set.

	fn message_bytes(message: &Message) -> u32 {
		match message {
			Message::Request(req) => req
				.requests
				.iter()
				.map(|p| core::cmp::max(p.body.len() as u32, 32))
				.sum::<u32>(),
			_ => 0,
		}
	}

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
}

## Relayer Fees

The relayer fee is an optional incentive provided by applications initiating cross-chain transactions. It compensates Hyperbridge's decentralized relayers for delivering messages to the destination chain. Apps that prefer to self-relay can leave the fee at zero.

The fee is collected by `pallet-ismp`'s `IsmpDispatcher` from the configured `Currency` (typically a stablecoin). It's escrowed into the `RELAYER_FEE_ACCOUNT` and paid out to the relayer that delivers the message (or refunded to the payer on timeout).
