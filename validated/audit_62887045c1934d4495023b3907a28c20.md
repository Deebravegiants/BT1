This confirms `Registry.process` explicitly documents that it "will verify the request did indeed come from Shopify" (docs/usage/webhooks.md:125), but the HMAC only covers the raw body via `to_signable_string` returning `@raw_body` [1](#0-0) , while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers [2](#0-1)  and passed straight into `WebhookMetadata` without any binding to the verified bytes [3](#0-2) .

### Title
Webhook `shop` (and `topic`/`webhook_id`) headers are trusted without HMAC binding, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before dispatching to an app's handler [4](#0-3) . In reality, `Utils::HmacValidator.validate` only authenticates the raw request body, because `Request#to_signable_string` returns `@raw_body` alone [1](#0-0) . The `shop`, `topic`, and `webhook_id` fields consumed by the handler come from HTTP headers that are never covered by the HMAC computation [5](#0-4) .

### Finding Description
The binding the library implicitly claims to provide is:
`hmac_valid(raw_body) == true` implies `(topic, shop, body, webhook_id)` are all authentic and bound together as one Shopify-originated event.

In fact the equality only holds for `body`:
- Before: HMAC is computed over `verifiable_query.to_signable_string`, which for `Webhooks::Request` is exactly `@raw_body` [1](#0-0)  and validated via constant-time compare in `HmacValidator.validate_signature` [6](#0-5) .
- After: `Registry.process` raises only if the HMAC over the body fails [4](#0-3) , then unconditionally builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id`, all sourced from headers that were never part of the signed bytes [7](#0-6) [8](#0-7) .

Because the app's `client_secret`/`api_secret_key` used to sign webhooks is shared across every shop that has the app installed (it is not a per-shop secret) [9](#0-8) , any merchant who installs the app receives genuinely-signed `(raw_body, hmac)` pairs for their own shop. Since the `shop-domain` header is not part of the signed bytes, that attacker-controlled merchant can replay the exact same body and valid HMAC to the app's shared webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) for a victim shop. `HmacValidator.validate` still returns `true`, and `Registry.process` dispatches the forged event to the app's handler labeled as belonging to the victim tenant.

### Impact Explanation
This breaks the tenant boundary the library is expected to enforce for webhook processing (the doc's explicit promise to "verify the request did indeed come from Shopify" for that shop) [10](#0-9) . Any downstream logic in the host app that trusts `data.shop` for authorization, data storage keys, or state transitions (e.g., updating billing/order state, deleting/creating resources, revoking access) can be manipulated cross-tenant by an attacker who only needs to be a legitimate merchant/installer of the target app — no access token, `client_secret`, or victim credentials required. This matches the "cross-tenant access" critical-impact category since a request nominally scoped to attacker's own tenant is processed as belonging to a different tenant.

### Likelihood Explanation
Likelihood is high for any app that (a) uses a single shared webhook endpoint for all shops (the documented pattern in `docs/usage/webhooks.md`), and (b) trusts `WebhookMetadata#shop` to select/scope the affected tenant, which is the pattern the gem's own documentation recommends (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [11](#0-10) . The attacker only needs to install the target app on a shop they control to obtain valid `(body, hmac)` pairs, then send a crafted HTTP POST with substituted headers — no special access is required beyond normal app installation.

### Recommendation
Extend `Utils::VerifiableQuery`/`Webhooks::Request#to_signable_string` (or add a separate authenticated-header check in `Registry.process`) so that the `shop`, `topic`, and `webhook_id` values are cryptographically bound to the HMAC verification — e.g., by validating them against the corresponding fields embedded in the parsed webhook body where Shopify includes them, or by documenting/enforcing that host apps must independently confirm the `shop` header against an installed-session record before trusting `WebhookMetadata#shop` for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, receiving genuine webhooks (e.g. `orders/create`) at the app's shared HTTP webhook endpoint with headers `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and body `B`.
2. Attacker captures `(B, valid_hmac)` from their own legitimately received webhook.
3. Attacker POSTs to the same public webhook endpoint with body `B` and header `x-shopify-hmac-sha256: valid_hmac` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [12](#0-11) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-computes the HMAC over `B` [4](#0-3) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` [7](#0-6) , causing the app to process attacker-controlled data as if it originated from the victim tenant.
