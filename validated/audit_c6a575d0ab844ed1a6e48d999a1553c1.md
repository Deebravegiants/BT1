Based on my analysis, I've confirmed the vulnerability. The HMAC signature covers only the raw request body, while the `shop` field (and other headers like `topic`, `webhook_id`, `api_version`) are read from unauthenticated headers and passed downstream to the handler.### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract requires `hmac` and `to_signable_string`. For webhooks, `to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values, however, are read straight from unauthenticated HTTP headers, independent of the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, then immediately forwards `request.shop` (an unauthenticated field) into the handler-facing `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` computes/verifies the signature strictly against `verifiable_query.to_signable_string` (the body) and the app's `api_secret_key`; it never incorporates the `shop-domain` header into the signed material: [4](#0-3) 

The identity binding that should hold is: **`shop-domain` header == the tenant whose data the body actually belongs to**. Because the HMAC only binds body bytes to the secret, but not the `shop-domain` header, this equality is never enforced by the gem — `request.shop` is trusted purely from an attacker-controlled header, with only the body cryptographically authenticated.

Concretely: the `client_secret` (`api_secret_key`) used to compute HMACs is shared across *all* shops that install the app (it is an app-level secret, not a per-shop secret). A merchant who has legitimately installed the app on their own shop A can therefore capture a genuine webhook (valid body + valid HMAC for shop A), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain: shopB.myshopify.com` in the header. `HmacValidator.validate` still succeeds (it only checks the body against the shared secret), and `Registry.process` passes `shop: "shopB.myshopify.com"` to the app's handler, which will typically use it as a tenant/session key to look up or write per-shop data.

### Impact Explanation
This breaks the tenant-identity binding relied upon by any app that trusts `WebhookMetadata#shop` (or `Request#shop`) as an authenticated tenant identifier, enabling cross-tenant data confusion in the host application's webhook handler (e.g. writing/reading data under the wrong shop, or triggering shop-scoped side effects for a victim tenant using attacker-controlled body content). This matches the "cross-tenant access" class of Critical impact, since the gem asserts the shop identity has been verified once HMAC validation passes, when in fact only the body bytes were verified.

### Likelihood Explanation
Likelihood is High for any app that has at least one shop install (a very low bar — the attacker only needs to install the app on their own store, which is normal for a public/embedded app), capture one legitimate webhook delivery, and replay it with a modified header to the app's public webhook endpoint. No access token, session, or `client_secret` knowledge is required beyond what a normal merchant/tenant already has.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook_id`) header into the signable material used for HMAC verification, or otherwise cryptographically tie the claimed shop to the verified request (e.g., cross-check `request.shop` against a shop already known to be associated with the specific webhook subscription/id via a separate authenticated lookup) before passing it to `WebhookMetadata`.

### Proof of Concept
1. App installs on attacker's shop `attacker.myshopify.com`; Shopify delivers a webhook with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
2. Attacker replays the HTTP POST to the app's public webhook endpoint, keeping body `B` and the HMAC header unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally (no header content is bound to the signature) — see [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`B`) using the app's shared `api_secret_key` — this succeeds since `B` and the HMAC are untouched — see [6](#0-5) .
5. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop == "victim.myshopify.com"` even though the body content actually originated from `attacker.myshopify.com`'s webhook, letting the attacker inject attacker-controlled body content under the victim shop's identity in the host app's handler.
