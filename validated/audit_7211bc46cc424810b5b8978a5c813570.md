### Title
Webhook HMAC does not bind the `shop` (tenant) header, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` computes the HMAC only over the raw JSON body, never over the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` therefore proves that the *body bytes* were signed with the app's shared `api_secret_key`, but it proves nothing about which shop the request claims to be from. `Registry.process` accepts this weaker guarantee and hands the attacker-controlled `shop` value straight to the app's webhook handler.

### Finding Description
`Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding: [1](#0-0) 

The signable string used for HMAC verification is only the raw body: [2](#0-1) 

`HmacValidator.validate` computes/compares the HMAC solely against `to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient authorization and immediately dispatches `request.shop` (an unauthenticated header value) into `WebhookMetadata` for the app's handler: [4](#0-3) 

The broken identity binding is: **shop claimed in the unauthenticated header ≠ shop cryptographically bound by the HMAC**. `api_secret_key` is shared across every shop that installs the app (it is not per-tenant), so any shop that installs the app can generate a validly-HMAC'd `(raw_body, hmac)` pair for itself, then replay that exact pair to the app's webhook endpoint while substituting a different shop's domain in the `shop-domain` header. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` forwards the forged `shop` value to the handler unchecked.

This mirrors the report's "front-run" bug class: a system checks integrity of one thing (the price/liquidity state, here the body) while acting on another unchecked identity-binding field (the initial price/tenant, here the `shop` header) that a low-privilege actor fully controls.

### Impact Explanation
Applications built on this gem commonly use the webhook's `shop` field to select per-tenant state (stored access token, DB row, feature flags) and to attribute body content (e.g. `orders/create`, `customers/data_request`, `app/uninstalled`) to that tenant. Because `shop` is not authenticated, any entity that can install the app on a shop it controls (i.e., any unprivileged internet user, since app installation itself requires no special privilege) can forge webhook deliveries that the receiving app will process as if they came from an arbitrary victim shop domain — a cross-tenant confusion/injection primitive reachable purely through this gem's own webhook-verification code path.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-owned/controlled shop to receive a genuinely-signed webhook body+HMAC pair, and (2) replaying that pair to the app's public webhook endpoint with a substituted `shop-domain` header. No access token, `client_secret`, or privileged account is needed — this is entirely within reach of a normal, unprivileged Shopify merchant/attacker.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed material verified against Shopify's HMAC, or independently verify that `request.shop` matches a shop the app trusts/has stored a session for before dispatching to `WebhookMetadata`/handlers. At minimum, `Registry.process` should require the app to authenticate `request.shop` against its own tenant store rather than trusting the header outright once HMAC-on-body succeeds.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers/receives a webhook (e.g. `orders/create`), capturing the raw request body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with body `B` unchanged, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is built; `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which equals `H`, so `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) returns `true`.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...))`, causing the host application to process attacker-supplied body content under the victim shop's identity.
