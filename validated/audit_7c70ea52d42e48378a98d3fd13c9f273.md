### Title
Same-chain intent fills only release escrow indices covered by `order.output.assets`, permanently freezing excess `order.inputs` when the arrays' lengths diverge - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` mirrors the reported `_debtTokens`/`_tradeAssets` pattern: it assumes a strict 1:1 index correspondence between two independently-sized arrays (`order.inputs` and `order.output.assets`) without ever validating that the arrays have matching lengths, then drives all downstream escrow accounting off the shorter array's length.

### Finding Description
`_fillSameChain` computes `outputsLen = order.output.assets.length` and then, for each output index `i`, releases a *proportional* slice of the escrowed input at the *same index*: `order.inputs[i]`. [1](#0-0) 

The loop bound is `outputsLen`, not `order.inputs.length`: [2](#0-1) 

`_filled[commitment] = msg.sender` is set unconditionally at the very top of the function, before any correspondence between the two arrays is checked: [3](#0-2) 

`WithdrawalRequest.tokens` is built only from `escrowedInputs`, sized `outputsLen`, and passed to `_withdraw`, which releases exactly those entries: [4](#0-3) [5](#0-4) 

If `order.inputs.length > order.output.assets.length` (a placer can freely construct such an order — I found no length-parity check on `order.inputs` vs `order.output.assets` in the paths I inspected, e.g. `placeOrder`'s validation only rejects `order.inputs.length == 0` and duplicate output tokens), the excess input entries at indices `outputsLen .. inputsLen-1` are escrowed at `placeOrder` time but never appear in `escrowedInputs`/the `WithdrawalRequest`, so `_withdraw` never touches them. Meanwhile `_filled[commitment]` is already set to the solver, finalizing the order. This is the same root cause pattern as the reported bug: one array (`output.assets`) governs the amount/dispatch logic while a second, independently-sized array (`inputs`) supplies the actual token identities/amounts moved, with no assertion that the two are consistent.

### Impact Explanation
Any escrowed input token beyond `outputsLen` is left in the `_orders[commitment][token]` mapping with no reachable code path to release it: the order is already finalized (`_filled[commitment] != address(0)`), so the normal cancel-before-fill flow is foreclosed once `_fillSameChain` runs. This is a permanent freezing-of-funds bug reachable directly from an unprivileged order placer's own `placeOrder` call plus any solver's `fillOrder` call — no privileged role is required on either side.

### Likelihood Explanation
Reachability is high: `placeOrder` is a fully permissionless entry point and (based on the code reviewed) does not appear to enforce `order.inputs.length == order.output.assets.length`. Any user placing a same-chain order with more input legs than output legs, followed by a normal solver fill, triggers the freeze. I was not able to fully re-verify every validation branch of `IntentGatewayV2.sol`'s `placeOrder`/`fillOrder` wrappers within the remaining tool budget, so it is possible an un-reviewed check elsewhere enforces array-length parity — this should be confirmed by a deeper audit of `evm/src/apps/IntentGatewayV2.sol`'s `placeOrder` and `fillOrder` entry functions before treating this as fully confirmed.

### Recommendation
In `placeOrder` (or in `_fillSameChain` before proceeding), require `order.inputs.length == order.output.assets.length`, or otherwise change `_fillSameChain` to iterate and release *all* of `order.inputs` on full fill regardless of `outputsLen`, ensuring every escrowed token has a guaranteed release path when the order is finalized.

### Proof of Concept
1. Caller calls `placeOrder` with `order.inputs` containing 2 `TokenInfo` entries (e.g., USDC and DAI) but `order.output.assets` containing only 1 entry — no revert occurs since only `inputs.length == 0` and duplicate-output checks are known to apply.
2. Both input tokens are escrowed into `_orders[commitment][token]` under `placeOrder`'s Phase 3 crediting loop. [6](#0-5) 
3. A solver calls `fillOrder`, which routes into `_fillSameChain`. `outputsLen = 1`, so the loop only processes index 0, escrowing/releasing only the first input token; `_filled[commitment]` is set to the solver.
4. The second escrowed input token remains in `_orders[commitment][secondToken]` with no further code path to reach it, since the order is already `_filled` and same-chain cancellation is unreachable post-fill.

    function _fillSameChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        bool isFullyFilled = true;

        TokenInfo[] memory escrowedInputs = new TokenInfo[](outputsLen);
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            uint256 alreadyFilled = _partialFills[commitment][outputToken];
            uint256 remaining = totalRequired - alreadyFilled;
            if (remaining == 0 || solverAmount == 0) {
                if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
                continue;
            }
            uint256 fillAmount;

            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;
            if (alreadyFilled == 0 && solverAmount > totalRequired) {
                fillAmount = totalRequired;
                (protocolShare, beneficiaryShare) =
                    _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);
            } else {
                fillAmount = solverAmount > remaining ? remaining : solverAmount;
            }

            uint256 amountFilled = alreadyFilled + fillAmount;
            _partialFills[commitment][outputToken] = amountFilled;
            uint256 beneficiaryTotal = fillAmount + beneficiaryShare;

            if (token == address(0)) {
                if (msgValue < beneficiaryTotal + protocolShare) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
                // Inline, not `_sendValue`: this loop is at the via-ir stack limit.
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }

            if (totalRequired > amountFilled) isFullyFilled = false;
            if (protocolShare > 0) emit DustCollected(token, protocolShare);

            uint256 escrowedAmount;
            if (amountFilled == totalRequired) {
                escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
            } else {
                escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
            }
            escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
            outputFills[i] = TokenInfo({token: outputToken, amount: fillAmount});

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);

                IERC20(token).safeTransfer(beneficiary, amount);
