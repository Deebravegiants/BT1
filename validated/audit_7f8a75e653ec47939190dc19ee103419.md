### Title
Webhook shop/topic identity is unauthenticated — HMAC covers only the body, enabling cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies solely the byte-for-byte integrity of the JSON body. The `shop-domain` and `topic` headers that `Registry.process` uses to route the payload to a handler and to stamp `WebhookMetadata#shop` are read straight from HTTP headers and never enter the HMAC computation, so they carry no authenticity guarantee at all.

### Finding Description
`Request#hmac` decodes the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header [1](#0-0) , while `Request#shop` and `Request#topic` are pulled from separate, independent headers [2](#0-1) . Crucially, `to_signable_string` — the only thing `HmacValidator` ever signs/compares — is just `@raw_body` [3](#0-2) .

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` value using `OpenSSL.secure_compare` [4](#0-3) . This proves body integrity/authenticity — it proves *some* request with this exact body was signed by Shopify using the app's secret — but it says nothing about which shop or which topic that body was signed for.

`Registry.process` then uses the unauthenticated `topic` header to select the handler and the unauthenticated `shop` header as the tenant identity forwarded to the app's handler: [5](#0-4) 

This is the "field acted on but not covered by the HMAC" pattern: the binding the gem implicitly claims is `hmac_valid(body) ⇒ (shop, topic, body) are all authentic`, but the actual guarantee it proves is only `hmac_valid(body) ⇒ body is authentic for *some* (shop, topic) Shopify signed it for`. `shop` in the equality `authenticated_shop == tenant_used_for_dispatch` is never checked — the "authenticated" side is empty (no shop is authenticated at all), while the "tenant used for dispatch" side is fully attacker-controlled.

### Impact Explanation
Any unprivileged internet user who can obtain one genuine `(raw_body, hmac)` pair for a topic the target app subscribes to — for example by registering the app on their own trial/development shop and receiving a legitimate webhook — can replay that exact body and HMAC directly to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic` header) with an arbitrary victim shop domain (or a different registered topic). `Registry.process` will pass `HmacValidator.validate` (body/HMAC pair is genuine and untouched) and then invoke the victim's/target's handler with `WebhookMetadata.shop` set to the attacker-chosen value. Any application logic keyed on `data.shop` for tenant-scoped writes, cache keys, session lookups, or redaction/GDPR flows (`shop/redact`, `customers/redact`, `customers/data_request` are exactly the mandatory topics this registry special-cases) would then act under the wrong tenant identity — this is cross-tenant data corruption/confusion delivered entirely through the gem's own `process` dispatch path, not a host-application misuse.

### Likelihood Explanation
The attacker only needs the ability to send an HTTP POST to the app's public webhook endpoint (which by design accepts unauthenticated internet traffic prior to HMAC verification) plus one legitimate webhook body+HMAC pair, obtainable by installing the target app on any shop the attacker controls (including a free development store) and capturing a real delivery. No access token, `client_secret`, or privileged account is required.

### Recommendation
Bind the identity fields into the signed material, or independently verify them out-of-band with Shopify (e.g., via the Admin API) before trusting `shop`/`topic` for dispatch and tenant attribution. At minimum, `Registry.process` should not treat `request.shop` as a trusted tenant identifier for cross-topic mandatory compliance webhooks without confirming it against an authenticated source (e.g., correlate against a previously known session for that shop, or require the topic/shop pair to be embedded inside the HMAC-covered body rather than sourced from headers).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com` and capture a legitimate webhook delivery for a subscribed topic, e.g. `orders/create`, giving `raw_body` and a valid `x-shopify-hmac-sha256` value.
2. POST that exact `raw_body` to the app's webhook endpoint with headers:
   - `x-shopify-hmac-sha256: <captured value>` (unchanged)
   - `x-shopify-topic: orders/create` (unchanged, or swapped to another registered topic)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (attacker-substituted)
3. `Utils::HmacValidator.validate(request)` succeeds because it only re-derives HMAC over `raw_body` [3](#0-2) .
4. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the order payload captured from the attacker's own shop to be processed and persisted under the victim shop's tenant identity.
