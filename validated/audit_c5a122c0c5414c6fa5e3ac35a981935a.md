### Title
Caller-supplied swap route lets an attacker-named contract execute arbitrary calls under the victim's `require_auth` tree, draining the victim's wallet - (File: contracts/controller/src/strategies/swap.rs)

### Summary
This is the on-chain analogue of CVE-2022-4335's blind SSRF: like GitLab being forced to connect to an attacker-chosen host, the controller's swap entrypoints force the transaction to invoke attacker-chosen contracts (hop pools named inside the `StrategySwap` payload). Because those venue calls execute inside the caller's `require_auth` context, a rogue pool can issue `token.transfer(victim, attacker, X)` against *any* token in the victim's wallet, and Soroban simulation records that transfer as a child of the victim's own authorization entry — which the victim's signer then approves.

### Finding Description
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` all accept a user-provided `swap: StrategySwap` blob and forward it verbatim to the configured router in `swap_tokens` [1](#0-0) . The controller constrains only its own grant — one exact `authorize_transfer_as_current` input transfer with no sub-invocations [2](#0-1)  — and measures input/output deltas afterward [3](#0-2) . Neither the controller nor the router allowlists the pool/token addresses named inside the route payload, so arbitrary third-party code runs below the caller's `require_auth` on the entrypoint. The project's own threat model concedes "a route can put third-party code on the call stack below the caller's authorization" and that a transfer such code makes from the caller "executes if the caller signs that tree. The loss is then the caller's wallet" [4](#0-3) .

The harness test proves the mechanics end-to-end: `UnlistedPoolRouter` invokes the attacker-deployed `RogueHopPool` named in the route, and `RogueHopPool::swap` calls `token.transfer(alice, attacker, WALLET_BALANCE)` on an unrelated wallet token [5](#0-4) . In recording mode the stolen transfer is attached as a child of Alice's `swap_collateral` auth entry, and the wallet is drained [6](#0-5) ; in enforcing mode the same theft succeeds whenever the signed tree contains the rogue child [7](#0-6) .

### Impact Explanation
Theft of user funds. The loss is unbounded by the routed amount, the payload `min_out`, or the post-swap health gate: the rogue contract can transfer every token the victim holds, including assets the protocol never listed. The swap itself still returns a fair measured output, so all controller-side accounting checks pass and the transaction commits.

### Likelihood Explanation
Any unprivileged attacker can deploy a pool-shaped contract and distribute a malicious route (e.g., via a spoofed quote/UI). The victim's only defense is decoding the simulated auth tree and spotting a foreign `transfer` child — an unrealistic burden that the threat model itself pushes onto clients ("a client must decode the route it signs and refuse an authorization tree with any other child"). Standard wallets simulating the transaction will present the poisoned tree for signature.

### Recommendation
Do not place arbitrary route-named contracts inside the caller's auth boundary. Options: (1) have the controller delegate the swap to a trustee sub-account or hold the swap context outside `require_auth` so venue calls cannot attach children to the caller's entry; (2) enforce a governance-allowlisted venue/pool registry and reject routes naming unregistered contracts; (3) at minimum, document the auth-tree shape per entrypoint and have SDKs reject signatures whose simulated tree contains children beyond the single expected input transfer.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` — deploy `RogueHopPool` configured with `(victim=Alice, wallet_token, to=attacker, amount=WALLET_BALANCE)`, submit `swap_collateral(alice, account, USDC, 50_000_000_000, ETH, route)` where `route.hop_pool` names the rogue pool. `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows the stolen transfer attached to Alice's recorded auth entry and `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`; `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows the theft executes once the simulated (poisoned) tree is signed.

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
