### Title
Block-revenue delegator rewards calculated from vote account's `pending_delegator_rewards` are never settled against the source, enabling repeated/double distribution across epochs - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
The Popcorn bug class is: a "harvest" step that mutates the yield-bearing balance is invoked *after* shares/withdrawal amounts have already been computed from the stale balance, so depositors/withdrawers get mis-priced shares relative to freshly harvested yield. The closest reachable analog in Agave's bank commit path is the SIMD-0123 block-revenue-sharing reward calculation: `calculate_block_reward` reads a snapshot of the vote account's `pending_delegator_rewards` at epoch-boundary calculation time and distributes a proportional share of it to every staker, but no code path I could locate ever reduces that same `pending_delegator_rewards` field (or debits the vote account's lamports) to reflect that the pool has been paid out.

### Finding Description
`calculate_block_reward` in [1](#0-0)  reads `vote_state.pending_delegator_rewards()` from a cached vote-account snapshot and computes each stake account's proportional share, clamped only to `min(pending_delegator_rewards)` per staker — not against a running total across all stakers.

This value flows into `PartitionedStakeReward.block_reward` via `calculate_stake_rewards_and_commissions` [2](#0-1) , and is later credited directly to stake account lamports in `build_updated_stake_reward`: [3](#0-2) 

This credit happens purely via `account.checked_add_lamports(...)` on the *stake* account — there is no corresponding debit of the *vote* account's lamports, and no call anywhere in `distribution.rs` or `calculation.rs` that decrements `pending_delegator_rewards` on the vote account after the block reward has been paid out. Confirmed by grep across the runtime crate: the only occurrences of `pending_delegator_rewards = 0` in the whole repo are in vote-program *test* code that manually resets the field for test setup, not in any production reward-distribution code path.

Separately, `distribute_reward_commissions`'s accounting assertion only tracks inflation-derived `total_stake_rewards_lamports` (from `RewardAccumulation.stake_reward`, which is set to `inflation.stake_reward` only) — `block_reward` is excluded from this sum and from the capitalization return value in `begin_partitioned_rewards` [4](#0-3) . This is consistent with the intent that block rewards are meant to be funded from the vote account's own balance (deposited earlier via `deposit_delegator_rewards`'s CPI transfer, per SIMD-0123: [5](#0-4) ) rather than minted via capitalization — which makes the absence of a corresponding vote-account debit in the distribution path more significant, not less.

This mirrors the Popcorn harvest-ordering defect structurally: a value ("harvested" pending rewards) is used to compute a payout to multiple parties (analogous to depositors/withdrawers sharing yield), but the bookkeeping that should reflect the payout being drawn down against its source is missing, so the same pool can be treated as fully available again in a subsequent computation.

### Impact Explanation
If confirmed, every epoch that block-revenue-sharing is active and a vote account retains a positive `pending_delegator_rewards`, `calculate_block_reward` will recompute payouts from the *same* undiminished (or growing) pool each epoch, re-crediting stakers repeatedly for revenue that has already been distributed. This would be a case of value creation with no matching debit — lamports appear in stake accounts without draining the source vote account or being reflected in `self.capitalization`, which is exactly the class of "concrete value loss/creation" and "undeclared account mutation" this scan is meant to surface in bank-commit / reward-distribution paths.

### Likelihood Explanation
Likelihood is uncertain without full confirmation. Block revenue sharing (SIMD-0123) is gated behind the `block_revenue_sharing` feature flag and depends on validators actually calling `DepositDelegatorRewards`, so this only manifests once that feature is activated and vote accounts have non-zero `pending_delegator_rewards` across an epoch boundary. I was not able to inspect `distribute_epoch_rewards_in_partition`/`store_partitioned_stake_rewards` in full (index size limits), so I cannot rule out that vote-account debit/reset logic exists elsewhere and was simply not surfaced by search.

### Recommendation
Verify whether `distribute_partitioned_epoch_rewards` / `distribute_epoch_rewards_in_partition` (or any function that stores the vote account after reward distribution) debits the vote account's lamports and decrements `pending_delegator_rewards` by the total `block_reward` paid out across all stakers for that vote account. If no such settlement exists, add it — mirroring the recommended Popcorn fix of "settle the yield source before/atomically-with computing shares" — by reducing `pending_delegator_rewards` (and the vote account's lamport balance) by the exact aggregate `block_reward` amount distributed, before the next epoch's `calculate_block_reward` can read it again.

### Proof of Concept
Not independently reproducible from static analysis alone given the missing piece (I could not confirm the actual debit is absent in code I couldn't fully retrieve). A concrete PoC would require instantiating a bank with `block_revenue_sharing` enabled, calling `deposit_delegator_rewards` to set a vote account's `pending_delegator_rewards` to a known value, running two consecutive epoch-reward cycles, and checking whether: (1) the vote account's `pending_delegator_rewards` decreases by the total `block_reward` paid in epoch N, and (2) stakers do not receive a `block_reward` again in epoch N+1 without a fresh deposit.

Given the incomplete verification, I recommend a Devin session inspect `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` in full (particularly `distribute_epoch_rewards_in_partition` and whatever stores the updated stake/vote accounts) to confirm or refute whether this settlement step exists before treating this as a confirmed finding.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
