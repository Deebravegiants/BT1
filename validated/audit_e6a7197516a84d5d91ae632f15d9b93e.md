### Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` header — which is never covered by that HMAC — as the tenant identity handed to the app's handler. Any party who can obtain one valid `(body, hmac)` pair for the app (e.g. by installing the app on their own store) can replay that pair while swapping the `shop-domain` header to a victim shop, and the request will still pass validation.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`, and for webhooks that signable string is exclusively the raw body: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers that are not part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC and, on success, unconditionally forwards `request.shop` to the handler as the authenticated tenant identity, with no cross-check against the signature, a session store, or a list of shops that installed the app: [3](#0-2) 

The gem's own documentation reinforces this trust boundary violation: it states that `Registry.process` "will verify the request did indeed come from Shopify" and then instructs developers to use `data.shop` directly as the tenant key (e.g. `shop_domain: data.shop`) when enqueuing work — implying `shop` is authenticated when in fact only the body bytes are: [4](#0-3) [5](#0-4) 

This is structurally identical to the reported bug class: an operation is performed based on a field (here, the tenant/shop identity, analogous to `recipient`/`from` in `proposeMint`/`proposeBurn`) that is not covered by the authentication mechanism (HMAC/signature) guarding the operation. The binding that should hold — `hmac == HMAC(secret, body ++ shop)` — instead only enforces `hmac == HMAC(secret, body)`, leaving `shop` unauthenticated even though it is the value used to route/attribute the resulting side effects.

### Impact Explanation
Since the same `client_secret` (and thus the same HMAC key) is used for every shop that installs a given app, any unprivileged internet user who legitimately installs the target app on their own store obtains a valid `(raw_body, hmac)` pair for that app. By replaying that exact body/HMAC while substituting the `x-shopify-shop-domain` header with a victim shop's domain, they produce a request that passes `HmacValidator.validate` yet is dispatched to the handler as though it originated from the victim shop. Any host application following the gem's documented pattern (using `data.shop` to key persistence, job dispatch, or per-tenant business logic) will process attacker-supplied webhook bodies under a victim tenant's identity — a cross-tenant access/data-injection primitive achieved without ever needing the app's `client_secret`, an access token, or the victim's credentials.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a shop they control (the normal onboarding path for any public/unlisted Shopify app) and be able to reach the app's public webhook endpoint (routes are typically public HTTP callback URLs). No secrets, tokens, or victim interaction are required, and the request forgery (replaying a captured body/HMAC with a modified header) is trivial to script.

### Recommendation
Bind the shop identity to the authenticated payload instead of trusting an unsigned header:
- Include the `shop-domain` (and ideally `topic`/`webhook_id`) in the HMAC-signed material, or
- After HMAC validation, cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription (e.g., via a lookup of shops that have installed the app or registered that webhook), rejecting requests whose header shop does not match an expected/authorized value for that webhook subscription.
- Update `docs/usage/webhooks.md` to stop implying that `Registry.process` fully "verifies the request came from Shopify" with respect to the shop field, and explicitly instruct integrators to re-validate `data.shop` against known installed shops before trusting it.

### Proof of Concept
```ruby
# Attacker installs the target app on their own store "attacker.myshopify.com"
# and receives a legitimate webhook, capturing:
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)
valid_hmac_b64 = Base64.encode64(hmac)

# Attacker replays the SAME body+hmac but spoofs the shop header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,   # still valid, since HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
  "x-shopify-webhook-id" => "any-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/secret match)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# Host app, per gem docs, uses data.shop as the tenant key -> cross-tenant processing

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
