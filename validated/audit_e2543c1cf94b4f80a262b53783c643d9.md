### Title
Webhook HMAC does not bind the `shop-domain` header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature validated by `Utils::HmacValidator` never covers the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header. `Registry.process` trusts `request.shop` to attribute the webhook's data to a tenant after only checking that the body's HMAC is valid. This breaks the identity binding `shop authenticated == shop the payload is attributed to`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop` is read straight from an unauthenticated header: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the raw body only for webhooks) and compares it against the received signature: [3](#0-2) 

`Registry.process` only checks this body-only HMAC, then immediately trusts `request.shop` to build the metadata handed to the app's webhook handler: [4](#0-3) 

This is asymmetric with how `AuthQuery` (used for the OAuth callback) is signed — there, `shop` is explicitly included in the signable string, binding shop identity into the HMAC: [5](#0-4) 

Because a single `api_secret_key`/`old_api_secret_key` is shared by the app across every shop that installs it, any shop where the app is installed can receive a legitimately HMAC-signed webhook body from Shopify for its own store, and then replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still pass because the signature never covered the shop header, and `Registry.process` will dispatch the handler with `shop: request.shop` set to the attacker-chosen victim shop instead of the shop the data actually originated from.

### Impact Explanation
This breaks the equality `shop verified by HMAC == shop the app processes data for`, letting an unprivileged merchant who has the app installed on their own store inject data/events attributed to a different tenant (cross-tenant access/data confusion) in any host application that keys per-shop state off `WebhookMetadata#shop` without independently confirming that shop is the true origin. This matches the Critical "cross-tenant access" category, since the identity binding gap is in this gem's own webhook verification API (`Utils::HmacValidator`, `Webhooks::Request`, `Webhooks::Registry.process`), not a misuse of a documented contract by the host app.

### Likelihood Explanation
Requires only that an attacker controls (installs the app on) at least one Shopify store — no special privilege, credential leak, or TLS interception is needed. Capturing a legitimate webhook delivery for one's own shop and replaying it with a modified header is straightforward for anyone who can intercept their own store's HTTP traffic (e.g., via a proxy). Likelihood is Medium-High for apps whose webhook handlers key sensitive actions off `WebhookMetadata#shop`.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id/api-version) as part of the signed payload used for verification, or otherwise cryptographically bind the header claims to the body before dispatch — e.g., compute/verify the HMAC over a canonical string combining the raw body with the shop-domain header, or require the host app to separately confirm the delivered `shop` value against a per-shop webhook secret/session record rather than trusting the header outright. At minimum, document prominently that `request.shop` is not authenticated by the HMAC and must be independently cross-checked against known installed shops before being used to key any tenant-specific action.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker intercepts this request and re-sends it to the app's webhook endpoint, keeping body `B` and the same valid HMAC header, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `@raw_body` (`Request#to_signable_string`), never the shop header.
5. The handler executes with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: B ...)`, causing the host app to process attacker-controlled data as if it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
