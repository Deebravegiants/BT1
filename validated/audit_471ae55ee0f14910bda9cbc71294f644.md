### Title
Shopify webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler an unauthenticated `shop` value taken directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header. Because the app's `client_secret` (used to sign webhooks) is the same across every shop that installs the app, an attacker who controls one legitimate installation can capture a validly-signed webhook and replay it with a forged `shop-domain` header pointing at a victim shop, and the gem will report it as authentic for that victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC purely against `to_signable_string`, i.e. only the body: [2](#0-1) 

The `shop` accessor, however, is read directly and unauthenticated from a caller-supplied HTTP header: [3](#0-2) 

`Registry.process` validates the HMAC, then forwards `request.shop` — the header value, not anything cryptographically bound to the signature — straight to the app's handler as the tenant identity for the event: [4](#0-3) 

This is the exact identity-binding break called out in the rules: a field that is *acted on* (the `shop` used to route/attribute the webhook to a tenant) is not covered by the HMAC that is supposed to authenticate the request. Since Shopify webhooks for a given app are all signed with the same `client_secret`/`api_secret_key` regardless of which shop triggered them, any attacker who is a merchant with the app installed (or who otherwise obtains one genuine webhook body+HMAC pair) can:
1. Capture a legitimately-signed webhook delivered to their own store (valid `hmac` for that raw body, computed with the shared app secret).
2. Replay that exact body and HMAC to the app's webhook endpoint, but substitute the `shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` invokes the handler with `WebhookMetadata` claiming the event is from the victim shop.

Any host application that uses `request.shop` (as intended/documented by this gem) to look up the victim's session, scope data writes, or otherwise key business logic per-tenant will act on attacker-controlled data under the victim's identity — a cross-tenant confusion caused entirely by this gem's own `Request`/`Registry`/`HmacValidator` design, not by misuse of undocumented behavior.

### Impact Explanation
This breaks the tenant/shop identity binding that webhook processing is supposed to guarantee: `shop authenticated` (via HMAC) is not equal to `shop used for attribution` (from an unsigned header). Any app relying on `WebhookMetadata#shop` (populated with `request.shop`) to select which merchant's session/data the webhook body applies to can be tricked into cross-tenant actions (e.g. applying another shop's data mutation, order/customer data, or redact requests to the wrong tenant) using only a signature the attacker legitimately possesses for their own store. This matches the "cross-tenant access" Critical impact category since the attacker forces the app to process/attribute payloads under a shop identity they do not control.

### Likelihood Explanation
Requires the attacker to have at least one valid installation of the target app (to obtain one authentic signed webhook), which is a low bar for public apps (self-install) — comparable in spirit to the low-likelihood-but-severe scenario in the source report. No access token, `api_secret_key`, or privileged account is needed; only a normal merchant webhook delivery, which the attacker replays with a modified header.

### Recommendation
Bind the shop to the signature, not just the body. Options:
- Include the shop-domain (and ideally topic/webhook-id) in the signable string alongside the body, or
- Cross-check `request.shop` in `Registry.process` against a shop stored on the session/verified installation record before dispatching to the handler, rejecting mismatches, or
- Document/enforce that host apps must independently verify `shop` corresponds to an app installation they know about before trusting it, and provide an API to do so directly in this gem rather than leaving it fully to a documented-but-unenforced convention.

### Proof of Concept
```ruby
# Attacker owns a legitimate install on shop "attacker.myshopify.com"
# and receives a real webhook with a valid HMAC signed by the shared api_secret_key.

captured_body = '{"id":123,"note":"pwned"}'
captured_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, captured_body)
)

forged_headers = {
  "x-shopify-topic" => "orders/updated",
  "x-shopify-hmac-sha256" => captured_hmac,       # still valid: only body is signed
  "x-shopify-shop-domain" => "victim.myshopify.com" # forged: not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)

# Passes HMAC validation despite belonging to a different shop:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle receives WebhookMetadata(shop: "victim.myshopify.com", body: parsed_body, ...)
# even though the signature only ever proved the payload came from "attacker.myshopify.com"'s app secret usage.
