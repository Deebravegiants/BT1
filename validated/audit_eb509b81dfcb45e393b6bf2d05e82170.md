### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not bound to the HMAC signature, allowing cross-tenant replay of a genuine webhook - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body [1](#0-0) , while the `shop`, `topic`, and `webhook_id` values that `Registry.process` uses to dispatch and attribute the webhook are all read from unauthenticated HTTP headers [2](#0-1) . `Utils::HmacValidator.validate` only verifies that the body's signature matches `to_signable_string` (i.e. the body) [3](#0-2) , and `Registry.process` forwards the header-derived `shop` straight into `WebhookMetadata` for the handler to act on once the body HMAC passes [4](#0-3) . This breaks the intended binding `hmac_signed_content == (body, shop, topic, webhook_id)`; in reality it is only `hmac_signed_content == body`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` and nothing else [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from HTTP headers with no cryptographic tie to the signed body [2](#0-1) . `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and does a constant-time comparison against the received `hmac` [5](#0-4) , then `Registry.process` raises unless that check passes, and otherwise proceeds to look up the handler by the header-derived `topic` and hand the header-derived `shop` to the app's handler as trusted tenant identity [4](#0-3) .

Because none of `shop-domain`, `topic`, or `webhook-id` are part of the signed content, any body+HMAC pair that is valid for one webhook delivery (e.g. one the attacker legitimately received for their own store, since they can install the app on a shop they control and passively capture the webhook Shopify sends them) remains a **valid** signature no matter what `shop-domain`/`topic`/`webhook-id` header values are subsequently substituted when that exact body is replayed to the app's webhook endpoint. The equality the code should enforce — "the shop attributed to this event equals the shop whose secret produced this signature" — is never checked; only "the body matches some previously-seen signed body" is checked.

### Impact Explanation
An app built on this gem that trusts `request.shop` (or the `shop` field forwarded via `WebhookMetadata`) to select which merchant's data to update, without any independent verification, can be made to apply another merchant's genuine event payload as if it belongs to an attacker-chosen shop, or vice versa. This is a cross-tenant data-integrity violation: it lets one unprivileged install holder redirect/replay validly-HMAC'd webhook traffic and have it processed under a different tenant identity, satisfying the "cross-tenant access" impact criterion. It does not require the app's `client_secret`, an access token, or any privileged account beyond installing the app on a shop the attacker already controls (which is the normal unprivileged entry point for any Shopify merchant/developer).

### Likelihood Explanation
Likelihood is moderate: the attacker needs to (a) obtain at least one genuine signed webhook body (trivial — install the app on any shop and trigger an event), and (b) control the raw HTTP request delivered to the app's webhook endpoint headers (feasible for any actor who can send arbitrary HTTP requests to the app's public webhook URL, since Shopify webhook endpoints are plain public HTTPS endpoints and this gem performs no additional binding such as source-IP allow-listing or a shop/topic check against the signed content). The exploitability ultimately depends on how strongly a given host application trusts `request.shop`/`WebhookMetadata#shop`, but the gem itself provides no mechanism to prevent this substitution.

### Recommendation
Bind the tenant-identifying fields into the HMAC-verified content, or otherwise validate them independently of the header values before dispatch. Concretely: include `shop-domain`, `topic`, and `webhook-id` (or at minimum `shop`) in `Request#to_signable_string`, or have `Registry.process` re-verify the header-derived `shop` against a value obtained from a source that is itself covered by the signature (e.g. embed it in the payload and diff it against the header), and reject on mismatch. This mirrors the report's core recommendation to ensure every value acted upon carries the same authenticated binding as the value used for the security check, rather than trusting a subset of the data.

### Proof of Concept
1. Register a webhook handler on topic `orders/create` via `Registry.process`, which trusts `request.shop` from the header once `HmacValidator.validate(request)` passes [6](#0-5) .
2. Attacker installs the app on `attacker-shop.myshopify.com` and triggers an `orders/create` event, capturing the resulting POST request: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's real secret), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Webhook-Id: W1`.
3. Attacker resends the identical body `B` and identical `H` to the app's webhook endpoint, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com` substituted.
4. `Request#to_signable_string` still returns `B`; `HmacValidator.validate` recomputes the signature over `B` and it still matches `H`, since headers are excluded from the signable string [1](#0-0) .
5. `Registry.process` proceeds, and the handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload/signature actually originated from `attacker-shop.myshopify.com`'s webhook — a cross-tenant confusion of the signed data.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
