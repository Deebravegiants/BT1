### Title
Loss of batch atomicity in `pallet-call-decompressor::decompress_call` lets a failed extrinsic still commit partial ISMP message-batch state (request receipts, fees, events) — ([File: modules/pallets/call-decompressor/src/lib.rs])

### Summary
`pallet-call-decompressor::decompress_call` decompresses a relayer-submitted batch and calls `pallet_ismp::Pallet::execute(messages)` **directly**, bypassing the `handle_unsigned` dispatchable that pallet-ismp deliberately wraps in `#[frame_support::transactional]` for atomicity. Since `decompress_call` itself carries no `#[frame_support::transactional]` annotation, a batch in which an early message succeeds (writing request receipts / fee state / events) and a later message fails causes the extrinsic to return `Err(ErrorExecutingCall)` while the earlier message's storage mutations remain committed. This is the same root-cause bug class as CWE-444 (HTTP request smuggling): two different code paths interpret the same logical operation's atomicity boundary differently, letting content that should have been rejected as a whole get "smuggled" into committed state.

### Finding Description
`pallet-ismp`'s own entry point is explicit about batch atomicity: [1](#0-0) 

```
#[pallet::weight(weight())]
#[pallet::call_index(0)]
#[frame_support::transactional]
pub fn handle_unsigned(
    origin: OriginFor<T>,
    messages: Vec<Message>,
) -> DispatchResultWithPostInfo {
    ensure_none(origin)?;
    Self::execute(messages.clone())?;
    Ok(().into())
}
```

`#[frame_support::transactional]` is required here because `Pallet::<T>::execute` is not internally atomic: it iterates the batch with `.map(...).collect::<Result<Vec<_>,_>>()`, which runs `handle_incoming_message` — and its storage side effects — for every message up to and including the first failure, but does not undo the side effects of the messages that already succeeded: [2](#0-1) 

and, for POST requests specifically, each successfully-processed request in the batch stores a receipt, deposits an event, and invokes the destination module's `on_accept` *before* any later request in the same batch is even looked at: [3](#0-2) 

`#[frame_support::transactional]` on `handle_unsigned` is what discards these partial writes when `execute()` ultimately returns `Err`.

`pallet-call-decompressor` reimplements the same "decode a batch, hand it to `execute`" flow for the compressed-call fast path, but drops the transactional wrapper and calls `execute` directly instead of going through `handle_unsigned`: [4](#0-3) 

```
#[pallet::call_index(0)]
#[pallet::weight(T::WeightInfo::decompress_call())]
pub fn decompress_call(
    origin: OriginFor<T>,
    compressed: Vec<u8>,
    encoded_call_size: u32,
) -> DispatchResult {
    ensure_none(origin)?;
    ensure!(encoded_call_size < T::MaxCallSize::get() * ONE_MB, Error::<T>::CallSizeOutOfBound);
    let call_bytes = Self::decompress(compressed, encoded_call_size)?;
    Self::decode_and_execute(call_bytes)?;
    Ok(())
}
``` [5](#0-4)

    }

```

`decompress_call` has neither its own `#[frame_support::transactional]` attribute nor does it dispatch through `handle_unsigned` (which would supply one). It invokes `Pallet::<T>::execute` as a plain function call, so none of the storage-layer rollback machinery that `handle_unsigned`'s macro provides is applied to this path. The pallet's own `Call` enum documents that `decompress_call` should behave equivalently to `pallet_ismp::Call::handle`/`handle_unsigned` — but the atomicity guarantee that pallet-ismp's code and doc-comments treat as load-bearing ("This will short-circuit and revert if any of the provided messages are invalid") does not hold on this second, unprivileged, relayer-reachable entry point.

This is a differential-interpretation bug in the same family as request smuggling: the "front end" (transaction pool / block explorer / relayer / downstream indexers) sees `decompress_call` fail with `ErrorExecutingCall` and reasonably assumes no protocol state changed (mirroring the guarantee the equivalent uncompressed path provides), while the "back end" (pallet-ismp storage) has already committed request receipts, emitted delivery events, and possibly collected/adjusted relayer fee accounting for the messages that were processed before the batch-terminating failure.

### Impact Explanation
Any unprivileged relayer can submit `CallDecompressor::decompress_call` as an unsigned extrinsic (`ensure_none` origin, matching pallet-ismp's own unsigned-message model documented in `docs/content/developers/polkadot/pallet-ismp/overview.mdx`). By crafting a batch where the first N `PostRequest`/`GetResponse`/`Timeout` messages are valid and the last is deliberately invalid (e.g., a bad proof, duplicate receipt, or destination check failure), the attacker forces the outer extrinsic to fail while:
- request receipts for the successfully-processed messages remain stored (so those requests are considered "delivered"/"handled" going forward, `on_accept` was invoked on destination modules, and any state or funds movement it triggered is retained),
- `Event::PostRequestHandled`/other delivery events may already have been emitted for individually accepted messages in earlier passes,
- yet the on-chain extrinsic result is `Err`, which every consumer of transaction-result semantics (indexers, relayer bookkeeping, monitoring, downstream retries) will treat as "nothing happened."

This produces unsound state commitment / unauthorized app action: protocol state advances (module `on_accept` executes, receipts are written) without the atomic all-or-nothing guarantee the corresponding `handle_unsigned` entry point enforces, and without the extrinsic-level signal that would normally accompany it. Because relayer fee accounting, request-replay protection, and downstream apps all assume `execute()` is only reachable atomically (per `handle_unsigned`'s explicit `#[transactional]`), this asymmetry can be leveraged to desynchronize relayer/indexer bookkeeping from actual delivered-request state, and — depending on the destination module's `on_accept` semantics — to have application-level side effects execute that the caller can later "undo the record of" by ensuring the extrinsic as a whole reports failure.

### Likelihood Explanation
High. `decompress_call` is `ensure_none`-gated (any unprivileged relayer can submit it as an unsigned extrinsic, exactly like `handle_unsigned`), requires no special privilege, and is actively used by tesseract's substrate relayer as an alternative low-cost path for large ISMP batches: [6](#0-5) 

Constructing a batch with one deliberately-invalid trailing message is trivial for anyone who can already build valid ISMP messages (a base relayer capability), and the code path (`decode_and_execute` → `Pallet::<T>::execute`) is directly reachable without any consensus/proof forgery beyond what's already required to submit normal messages.

### Recommendation
Add `#[frame_support::transactional]` to `pallet_call_decompressor::decompress_call` (mirroring `pallet_ismp::handle_unsigned`), or change `decode_and_execute` to dispatch the decoded call through the pallet-ismp `Call::handle_unsigned` dispatchable (via `Dispatchable::dispatch`) instead of invoking `Pallet::<T>::execute` directly, so that the same transactional storage-layer guarantee is applied. Add a regression test analogous to `pallet_call_decompressor.rs`'s existing tests that submits a batch with a valid leading message and an invalid trailing message and asserts that request receipts/events from the valid message are rolled back when the overall call errors.

### Proof of Concept
1. Construct two `PostRequest`s, `A` (valid, well-formed, valid proof) and `B` (identical proof height but deliberately invalid — e.g. `dest` not matching host and host not configured as router, so `Error::InvalidRequestDestination` triggers) in a single `RequestMessage { requests: vec![A, B], proof, signer }`.
2. Encode `RuntimeCall::Ismp(pallet_ismp::Call::handle_unsigned { messages: vec![Message::Request(msg)] })`, compress with zstd (as the substrate relayer's `submit` does at `tesseract/messaging/substrate/src/provider.rs:858-876`).
3. Submit `CallDecompressor::decompress_call(compressed, encoded_call_size)` as an unsigned extrinsic.
4. Observe: the extrinsic fails with `Error::ErrorExecutingCall` (matching the existing test pattern in `modules/pallets/testsuite/src/tests/pallet_call_decompressor.rs:149-211`), but check storage — `RequestCommitments`/receipt storage for request `A` (the batch's valid leading message) is present, i.e., `A` was processed (its module's `on_accept` invoked, receipt stored) despite the extrinsic reporting failure. This differs from calling `Ismp::handle_unsigned` directly with the same batch, where `#[frame_support::transactional]` guarantees `A`'s effects are rolled back together with `B`'s failure.

Note: I could not execute this PoC in a live node from this environment (read-only code index); the analysis above is derived directly from the cited source and the pallet's own existing test suite pattern, which already demonstrates the `ErrorExecutingCall` failure mode for batches but does not check for the described state leakage — that gap is exactly what should be added as a regression test to confirm the described atomicity bypass.

			&mut &call_bytes[..],
		)
		.map_err(|_| Error::<T>::ErrorDecodingCall)?;

		// use call filter to filter out unwanted calls
		if !<T as frame_system::Config>::BaseCallFilter::contains(&runtime_call) {
			return Err(Error::<T>::CallNotSupported.into());
		}

		if let Some(call) = IsSubType::<pallet_ismp::Call<T>>::is_sub_type(&runtime_call).cloned() {

				pallet_ismp::Call::handle_unsigned { messages } =>
					<pallet_ismp::Pallet<T>>::execute(messages)
						.map_err(|_| Error::<T>::ErrorExecutingCall)?,
				_ => Err(Error::<T>::CallNotSupported)?,

					)?,

			};
		} else {
			return Err(Error::<T>::CallNotSupported)?;
		}
