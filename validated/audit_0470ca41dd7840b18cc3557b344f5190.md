### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are trusted from unauthenticated headers not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying the HMAC over the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values passed to the app's handler are read from HTTP headers that are never included in the signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
and `HmacValidator.validate` computes the HMAC exclusively over that signable string: [2](#0-1) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all derived from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-api-version`, `shopify-webhook-id`) that are not part of the signed bytes: [3](#0-2) 

`Registry.process` validates only the HMAC (over the body) and then trusts `request.topic` and `request.shop` to look up a handler and construct the `WebhookMetadata` delivered to the app: [4](#0-3) 

The resulting `WebhookMetadata` struct carries `shop`, `topic`, `webhook_id`, and `api_version` straight into the host application's handler: [5](#0-4) 

This is exactly the bug class in the report: a field (`shop`/`topic`/`webhook_id`) is *acted on* by the code (used as a tenant/topic identifier and handed to the app) but is *not covered by the HMAC* that is supposed to authenticate the request. The equality the code implicitly assumes is:
`hmac_verified_bytes == bytes_that_determine(shop, topic, webhook_id)`
but in reality:
`hmac_verified_bytes == raw_body` while `shop/topic/webhook_id` come from unauthenticated headers, so the equality does not hold.

Because `raw_body` alone is signed, an attacker who has ever observed (or can construct) any single valid `(raw_body, hmac)` pair from Shopify for their own shop can replay that exact body/hmac pair while freely swapping the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, and `X-Shopify-Api-Version` headers to any value, since none of those headers are checked against the signature. `Registry.process` will accept it as validly signed and dispatch it to the handler registered for the attacker-chosen topic, tagged with the attacker-chosen `shop`.

### Impact Explanation
This breaks the tenant/topic binding the HMAC is meant to enforce. A host application that uses `WebhookMetadata#shop` to determine which merchant's data to update, or that branches on `topic`/`webhook_id` for authorization decisions, can be tricked into attributing an HMAC-valid payload to the wrong shop or the wrong topic — a cross-tenant data integrity issue. Because this crosses a tenant boundary using a signature the gem itself validates and reports as "Invalid webhook HMAC." only for body mismatches, it satisfies the Critical "cross-tenant access" impact category listed in scope, contingent on how a host app consumes `WebhookMetadata`.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuine `(raw_body, hmac)` pair issued by Shopify (e.g., from a webhook sent to their own shop/app installation, or any raw_body/hmac pair for a topic the app subscribes to) and then replay it with modified headers to the app's webhook endpoint. This is a realistic capability for an unprivileged actor who has installed the app on their own store and received at least one webhook, then reuses that exact signed body against the same endpoint with forged shop/topic headers. Likelihood is moderate: it depends on the host app trusting `WebhookMetadata.shop`/`topic` for authorization without independent verification (e.g., checking the shop against an existing session/installation), but the gem provides no protection against this at the library level.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the body), so that any header tampering invalidates the signature. At minimum, document prominently that `WebhookMetadata#shop`/`topic`/`webhook_id` are unauthenticated and that host applications must independently verify `shop` against a known/installed shop before trusting webhook payload contents.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook for topic `orders/create`, capturing the raw body `B` and the valid header `X-Shopify-Hmac-Sha256: H` (where `H = HMAC(api_secret_key, B)`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since HMAC only covers body)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic: customers/redact` (forged, if handler exists for this topic)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed by the host app and passed to `Registry.process`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `B`, per [1](#0-0)  and [2](#0-1) .
5. `Registry.process` dispatches to the handler for `customers/redact` with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "customers/redact", ...)`, per [4](#0-3) , even though Shopify never issued this shop/topic combination with this signature.
