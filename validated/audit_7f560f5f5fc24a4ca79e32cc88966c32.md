### Title
Webhook shop identity spoofing via cross-tenant HMAC replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook purely by validating the HMAC of the raw request body, then hands the caller-supplied `shop-domain` header straight through to the handler as the trusted tenant identity, even though that header is never covered by the HMAC.

### Finding Description
The webhook signature check computes the HMAC over `to_signable_string`, which returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the untrusted `shopify-shop-domain` / `x-shopify-shop-domain` header and is never included in the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` as the tenant identity passed to the app's handler: [3](#0-2) 

This breaks the identity binding: `hmac_valid(body, api_secret_key) == true` is treated as equivalent to `shop_header == originating_shop`, but the two are independent. Because `api_secret_key` is a single app-wide secret shared across every shop that installs the app (not per-shop), any party who can obtain one valid `(raw_body, hmac)` pair signed with that secret (e.g. from their own shop's legitimate webhook deliveries, which they control as an app installer) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header for a victim shop. The HMAC still validates (it only checks the body), so `Registry.process` calls the handler with `WebhookMetadata` claiming the victim shop as the source: [4](#0-3) 

### Impact Explanation
This allows cross-tenant data confusion/injection: the receiving application, trusting `data.shop` from `WebhookMetadata`, will process attacker-supplied webhook content (order data, customer data, GDPR events, etc.) under a shop identity the attacker does not control and did not actually originate the event for. This is a cross-tenant boundary break directly caused by the gem's `Request`/`Registry` design decoupling the verified bytes (body) from the trusted identity field (shop) that host applications are documented to key their per-tenant logic on.

### Likelihood Explanation
Exploitation requires the attacker to be an app installer on at least one shop (an unprivileged internet user with respect to other tenants) in order to capture one legitimate `(body, hmac)` pair, and requires the app's webhook endpoint to be reachable directly over HTTP (which it is, by design, since Shopify delivers webhooks over plain HTTPS POST with no other transport-level authentication). No access to `api_secret_key`, access tokens, or the victim's credentials is needed.

### Recommendation
Bind the shop identity into the signed material, or otherwise verify it out-of-band: compute/verify the HMAC over a canonical string that includes the `shop-domain` header (not just the raw body), or require host applications to cross-check `request.shop` against an independently known/expected shop (e.g., the shop associated with the webhook subscription being processed) before trusting it, rather than passing the raw header value straight into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook delivery, capturing the raw body `B` and its valid `x-shopify-hmac-sha256` value `H` (both signed with the app's single `api_secret_key`).
2. Attacker POSTs to the victim app's webhook endpoint with headers `x-shopify-shop-domain: victim-shop.myshopify.com`, `x-shopify-hmac-sha256: H`, and body `B`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`: [5](#0-4) 
4. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body content, even though the request never originated from Shopify on behalf of that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
