### Title
Missing zero-address check on `Order.output.beneficiary` permanently burns solver funds in `IntentGatewayV2` / `IntrinsicIntents` / `ExtrinsicIntents` - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol], [File: evm/src/apps/intentsv2/ExtrinsicIntents.sol], [File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` never validates that `order.output.beneficiary` is non-zero. An unprivileged order placer fully controls this field (only `user`, `source`, and `nonce` are overwritten by the gateway), so an order can be placed with `beneficiary = bytes32(0)`. When any solver later fills that order, the fill logic in `IntrinsicIntents._fillSameChain` and `ExtrinsicIntents._fillCrossChain` decodes the beneficiary as `address(uint160(uint256(order.output.beneficiary)))` — i.e. `address(0)` — and sends the solver's output tokens (native or ERC-20) directly to that address, permanently burning them. This mirrors the reported RFP-committee bug class: a missing `address(0)` check on a value that is later used as a fund-recipient/accepted target, causing unrecoverable loss of value for whichever unprivileged party interacts next (there the pool manager who has to redeploy and re-pay fees; here the solver whose output tokens are burned).

### Finding Description
`placeOrder` performs multiple `InvalidInput` checks (empty inputs, zero input amounts, duplicate output tokens) but does not check `order.output.beneficiary`: [1](#0-0) 

The beneficiary is only decoded and used at fill time. In the same-chain fill path: [2](#0-1) 

and in the cross-chain fill path: [3](#0-2) 

Both paths transfer the solver-supplied output tokens (native via `_sendValue`/inline call, or ERC-20 via `safeTransferFrom`) straight to `beneficiary` with no zero-address guard. `_sendValue` itself has no zero-address check either: [4](#0-3) 

For native token payment, sending value to `address(0)` succeeds (the zero address has no code and accepts plain ETH transfers), so the call does not revert — the solver's ETH is silently burned. For ERC-20, `safeTransfer`/`safeTransferFrom` to `address(0)` also generally succeeds unless the specific token implements its own zero-address guard (most standard ERC-20s, including OpenZeppelin's, do not block transfers *to* an arbitrary externally-supplied recipient other than in `_mint`/`_burn` internals — a plain `transfer(address(0), amount)` succeeds on typical tokens). This means a malicious or careless order placer can construct an order whose output funds are unrecoverably destroyed the moment any solver fills it, with the solver having no way to detect this from on-chain state before submitting the fill transaction (nothing in `fillOrder` rejects a zero beneficiary either): [5](#0-4) 

### Impact Explanation
Any solver that fills such an order loses the entire output amount it was to deliver, with no recovery path — the tokens are sent to `address(0)`, permanently removed from circulation. This is a direct, unbounded fund-loss vector reachable by a single `placeOrder` call (fully unprivileged) followed by any third party's `fillOrder` call. Given the intent/solver ecosystem processes potentially large notional value per order, this satisfies "concrete theft or permanent freezing of funds."

### Likelihood Explanation
`placeOrder` is a fully permissionless, single-transaction call available to any user, and setting `beneficiary = bytes32(0)` requires no special privilege or unusual state — it is simply an unchecked struct field. The only precondition is that a solver actually fills the order, which is the expected, routine flow of the intents protocol (solvers scan and race to fill profitable orders); a solver evaluating apparent profitability from the input/output amounts has no obvious reason to inspect the beneficiary field before filling, especially under automated/bot filling.

### Recommendation
Add an explicit beneficiary validation in `placeOrder` (and any other order-construction entry point, e.g. the Tron variant of `IntentGatewayV2.sol`):
```solidity
if (order.output.beneficiary == bytes32(0)) revert InvalidInput();
```
Optionally also defensively guard `_sendValue`/`_withdraw` against `address(0)` recipients as a second layer of protection, consistent with the zero-address checks already applied elsewhere in the codebase (e.g. `_validateParams`, `HostManager`, `SimplexPaymaster`).

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder(order, graffiti)` with `order.output.beneficiary = bytes32(0)` and legitimate input tokens/amounts; the call succeeds since no field of `output` is validated (only `inputs` are checked): [6](#0-5) 
2. A solver observes the order (input amount looks profitable relative to requested output) and calls `fillOrder(order, options)` with matching `options.outputs`.
3. In `_fillSameChain` (or `_fillCrossChain` for cross-chain orders), `beneficiary` decodes to `address(0)`: [7](#0-6) 
4. The solver's output tokens are transferred to `address(0)` via `_sendValue` (native) or `safeTransferFrom` (ERC-20) — both succeed without reverting: [8](#0-7) 
5. The solver's funds are permanently lost; the user still receives the escrowed input release via the normal `RedeemEscrow`/`_withdraw` flow, so only the solver suffers loss.

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        uint256 blockNumber = _blockNumber();
        if (order.deadline < blockNumber) revert Expired();
        // The solver's own bound on how long its quoted price stands. Zero means unbounded,
        // which is the right default for a solver filling directly — it is only at risk from
        // its own staleness. It matters for a bid signed through the coprocessor, where the
        // order placer chooses the moment of execution and nothing else caps the wait.
        if (options.validUntil != 0 && blockNumber > options.validUntil) revert FillExpired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

        uint256 outputsLen = order.output.assets.length;
        if (options.outputs.length != outputsLen) revert InvalidInput();
