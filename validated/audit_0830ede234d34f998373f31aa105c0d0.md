### Title
Token address collision via unescaped `"::"` seed concatenation in `create_token_seed` - (File: `aptos-move/framework/aptos-token-objects/sources/token.move`)

### Summary
`aptos_token_objects::token::create_token_seed` derives a token's deterministic object address by naively concatenating `collection_name || "::" || token_name` with no length-prefixing or escaping of the `"::"` separator. [1](#0-0)  Because `collection` and `token` names are arbitrary, unrestricted `String` values (only bounded by length, `MAX_COLLECTION_NAME_LENGTH`/`MAX_TOKEN_NAME_LENGTH`), two semantically distinct `(collection, name)` pairs can produce byte-identical seeds and therefore the identical deterministic object address, e.g. `(collection="Foo::Bar", name="Baz")` and `(collection="Foo", name="Bar::Baz")` both yield the seed bytes `"Foo::Bar::Baz"`. [2](#0-1)  This is the direct Aptos-native analog of the Rolla `QToken` symbol-truncation bug: two different, legitimately-named assets can be made to resolve to a single on-chain identity, defeating identity assumptions relied on for custody/trading decisions.

### Finding Description
`create_named_token`/`create_named_token_object` compute the token's address as `object::create_object_address(&creator_address, create_token_seed(&collection_name, &name))`. [3](#0-2)  `create_token_seed` performs raw byte concatenation with a fixed `"::"` delimiter and does not reject names or collection names that themselves contain `"::"`:
```
public fun create_token_seed(collection: &String, name: &String): vector<u8> {
    assert!(name.length() <= MAX_TOKEN_NAME_LENGTH, error::out_of_range(ETOKEN_NAME_TOO_LONG));
    let seed = *collection.bytes();
    seed.append(b"::");
    seed.append(*name.bytes());
    seed
}
``` [4](#0-3) 
Since `collection.move`'s `Collection.name` field has no character restriction beyond a length cap [5](#0-4) , any account that calls `create_named_token`/`create_named_token_object`/`create_named_token_from_seed` for itself (its own `creator_address`) can choose a `(collection, name)` pair whose concatenation collides with another, unrelated, legitimately-shaped `(collection, name)` pair for that same creator address. `object::create_object_address` is a pure hash of `creator | seed | 0xFE` [6](#0-5) , so colliding seeds produce colliding addresses, and `create_object_internal` only guards against *re-creating* an object at an address that already has `ObjectCore` — it does nothing to prevent two different logical names from targeting the same address in the first place. [7](#0-6) 

This is directly exploitable in the common "shared minter" pattern used by many marketplaces/launchpads built on `aptos_token_objects`, where a single platform-controlled account (the `creator`) mints tokens on behalf of many different end users who supply arbitrary collection/token name strings (as seen in the example modules that build directly on `token::create_named_token`). [8](#0-7)  If such a platform does not explicitly reject `"::"` in user-supplied names, an attacker can pre-compute the seed for a target `(collectionA, nameA)` combination expected to be minted later (e.g. a rare/valuable drop) and instead mint their own `(collectionB, nameB)` whose seed happens to match, occupying that deterministic address first with attacker-controlled `Token`/`Collection`/royalty/URI data.

### Impact Explanation
Any downstream contract, escrow, or off-chain integration that computes an expected token address via `create_token_address(creator, collection, name)` and trusts address equality as a proof of identity (a standard, documented usage pattern for named objects) can be made to interact with an attacker-controlled token instead of the intended one. This enables:
- Front-running/squatting the address slot intended for a legitimate collection's item, redirecting buyer funds/expectations in any DEX/marketplace flow that resolves tokens by computed address rather than by manually re-verifying collection+name strings.
- Object/identity confusion equivalent to (and address-level, thus stronger than) the QToken symbol collision in the source report — trading platforms and smart contracts can be tricked into treating one asset as another.
Because this affects address-level identity of `Token` objects (which back real NFTs/fungible assets and their ownership records), this is a custody-relevant identity/ownership confusion, not merely a cosmetic display bug.

### Likelihood Explanation
Requires only that a single account act as `creator` for both the colliding names (native to shared-minter/platform-operated collection creators, a common Aptos NFT platform pattern) and that neither `collection.move` nor `token.move` reject `"::"` in names — confirmed absent in both modules. [9](#0-8) [10](#0-9)  No privileged access is needed; an ordinary caller of a public minting entry function that forwards arbitrary strings can trigger the collision.

### Recommendation
Encode `create_token_seed`/`create_token_name_with_seed` unambiguously, e.g. length-prefix each component (`len(collection) || collection || len(name) || name`) instead of relying on a bare `"::"` delimiter, and reject `"::"`/reserved separators inside collection and token names, or otherwise ensure no two distinct `(collection, name)` inputs can ever serialize to identical seed bytes.

### Proof of Concept
```move
// Same creator account for both collections/tokens.
collection::create_unlimited_collection(creator, desc, string::utf8(b"Foo::Bar"), option::none(), uri);
collection::create_unlimited_collection(creator, desc, string::utf8(b"Foo"), option::none(), uri);

// Token A: legitimate-looking token in collection "Foo::Bar"
let ctor_a = token::create_named_token(creator, string::utf8(b"Foo::Bar"), desc, string::utf8(b"Baz"), option::none(), uri);

// Token B: attacker-chosen collection "Foo" and name "Bar::Baz"
// create_token_seed("Foo", "Bar::Baz") == create_token_seed("Foo::Bar", "Baz") == b"Foo::Bar::Baz"
// => object::create_object_address(creator, seed) is identical for both,
//    so whichever is minted first occupies the address; the second call aborts with EOBJECT_EXISTS,
//    and any address computed via create_token_address(creator, "Foo::Bar", "Baz") actually
//    resolves to whichever token won the race, regardless of which (collection, name) the caller intended.
let addr_a = token::create_token_address(&creator_addr, &string::utf8(b"Foo::Bar"), &string::utf8(b"Baz"));
let addr_b = token::create_token_address(&creator_addr, &string::utf8(b"Foo"), &string::utf8(b"Bar::Baz"));
assert!(addr_a == addr_b, 0); // collision demonstrated
```

    public fun create_object_address(source: &address, seed: vector<u8>): address {
        let bytes = bcs::to_bytes(source);
        bytes.append(seed);
        bytes.push_back(OBJECT_FROM_SEED_ADDRESS_SCHEME);
        from_bcs::to_address(hash::sha3_256(bytes))
