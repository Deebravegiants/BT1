### Title
Native-token fee payments in `EvmHost.dispatch`/`fundRequest` and `IntentGatewayV2.placeOrder` are priced off a manipulable live Uniswap V2 spot rate, and any resulting overpayment is refunded to the wrong recipient - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)` and `fundRequest`, as well as `IntentGatewayV2.placeOrder`, convert user-supplied `msg.value` into the protocol's `feeToken` by calling `IUniswapV2Router02.swapETHForExactTokens` against the chain's live Uniswap V2 pool. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

Like the `SwapPair.getSwapFee` analog, the amount of native token actually required is a function of the AMM's spot reserves at execution time, not at signing time. Callers determine `msg.value` off-chain via `getAmountsIn`/`quoteNative`, which the docs explicitly flag as unsafe on-chain because it is "vulnerable to sandwich attacks." [5](#0-4) [6](#0-5)  Between transaction signing and inclusion, anyone can shift the pool's reserves (e.g. via a swap or LP donation) so that the actual `amountIn` required by `swapETHForExactTokens` differs from what the user funded.

### Finding Description
`swapETHForExactTokens` computes `amounts = getAmountsIn(amountOut, path)` at execution time and requires `amounts[0] <= msg.value`; any unused ETH (`msg.value - amounts[0]`) is refunded by the Uniswap V2 Router via `msg.sender` — but because the router is invoked *by* `EvmHost`/`IntentGatewayV2`, the router's `msg.sender` in that inner call is the host/gateway contract itself, not the original externally-owned account that funded the `dispatch`/`placeOrder` call. [1](#0-0) 

Consequently:
- If the pool's reserves are manipulated so the fee-token becomes *more expensive* in native terms between signing and inclusion, the swap reverts with `EXCESSIVE_INPUT_AMOUNT`, griefing/denying the dispatch (matching the original report's "reserves altered between signing and inclusion" root cause).
- If reserves move the other way (fee-token becomes *cheaper*, e.g. after someone dumps native/donates to the pair), `amounts[0] < msg.value`, and the router refunds the difference to `address(this)` — i.e., into the `EvmHost`/`IntentGatewayV2` contract balance rather than back to the caller. None of the visible dispatch/fundRequest/placeOrder code paths forward that native-token dust back to the original sender. [7](#0-6) [8](#0-7) 

This is the same class of bug as the `SwapPair.getSwapFee` finding: a value paid by an unprivileged caller is computed against a spot AMM state that a third party can alter between signing and inclusion, and the mismatch is not bounded by any explicit slippage/deviation check (no `amountInMax`, no fee/price deviation guard) at the dispatch call site.

### Impact Explanation
Any user or relayer dispatching a POST/GET request or an intent order with native-token fee funding can have their overpaid native token permanently stranded in the `EvmHost`/`IntentGatewayV2` contract if the AMM's spot price shifts favorably before inclusion — since there is no visible reconciliation or refund-to-sender mechanism in the reviewed code. This is a concrete loss of user funds reachable from a single unprivileged dispatched request or intent order (in-scope: "EvmHost and HandlerV2 dispatch and delivery"). Separately, an adversary can grief dispatches by moving the pool the opposite way, causing legitimate dispatch/order-placement transactions to revert.

### Likelihood Explanation
The `msg.value` sent by callers is necessarily computed off-chain (the docs explicitly instruct against on-chain `getAmountsIn`/`quote` calls due to sandwich-attack risk), so a gap between the quoted amount and the executed amount is expected in normal operation, not just under active attack — it can occur from ordinary pool trading activity between quote-time and inclusion, and can be amplified by a cheap donation/swap against a thin fee-token/WETH pair. Every native-funded `dispatch`, `fundRequest`, and `placeOrder` call is exposed.

### Recommendation
- Pass an explicit `amountInMax`/slippage bound (or the exact expected `amounts[0]`) into the swap calls, and require the caller-provided `msg.value` to reconcile the actual amount consumed vs. sent.
- After each `swapETHForExactTokens` call, explicitly forward any leftover native balance (`msg.value - amounts[0]`, or the router refund the contract receives) back to `_msgSender()`/`order.user`, rather than leaving it in `EvmHost`/`IntentGatewayV2`.
- Consider bounding acceptable price deviation between the quoted and executed spot price, similar to the mitigation recommended for `SwapPair.getSwapFee`.

### Proof of Concept
1. User calls `EvmHost.dispatch{value: v}(DispatchPost{...fee: F...})` where `v` was computed off-chain via `quoteNative`/`getAmountsIn` against the WETH/feeToken Uniswap V2 pair. [9](#0-8) 
2. Before the transaction is mined, an attacker (or ordinary market activity) trades against or donates to the WETH/feeToken pair, shifting reserves so that fewer WETH are now required to buy `F` feeTokens.
3. The user's `dispatch` transaction executes `swapETHForExactTokens{value: v}(F, [WETH, feeToken], address(this), block.timestamp)`; the router computes `amounts[0] < v` and refunds `v - amounts[0]` to `msg.sender`, which in this call context is `EvmHost` itself. [1](#0-0) 
4. The refunded native-token dust is now held by `EvmHost` with no code path shown that returns it to the original user, resulting in a permanent loss of that overpaid amount for the user.

    /**
     * @dev Dispatch a POST request to Hyperbridge
     *
     * @notice Payment for the request can be made with either the native token or the feeToken.
     * If native tokens are supplied, it will perform a swap under the hood using the local uniswap router.
     * Will revert if enough native tokens are not provided.
     *
     * If no native tokens are provided then it will try to collect payment from the calling contract in
     * the feeToken.
     *
     * @param post - post request
     * @return commitment - the request commitment
     */
    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

		const totalFee = (await this.quote(request)) + fee
		const feeToken = await this.getFeeTokenWithDecimals()
		// Quote against the router the host actually swaps through on dispatch,
		// which may price differently than the canonical Uniswap V2 router.
		const hostRouter = await this.publicClient.readContract({
			address: this.params.host,
			abi: EvmHost.ABI,
			functionName: "uniswapV2Router",
		})
		return this.getAmountsIn(totalFee, feeToken.address, request.source, hostRouter)
	}
