Cross-tenant webhook shop-spoofing due to `shop-domain` header not covered by HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute exclusively from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`). `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC and then hands `request.shop` straight to the app's `WebhookHandler` inside a `WebhookMetadata` object, so the shop identity used by the host app for the webhook is never bound to the cryptographic signature.

### Finding Description
The broken binding, expressed as an equality that should hold but doesn't:

`hmac_signed_bytes == bytes_used_to_attribute_the_request_to_a_shop`

In this gem:
- `Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it (via `OpenSSL.secure_compare`) to the `hmac` value taken from the request. [1](#0-0) 
- For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 
- `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed string at all: [3](#0-2) 
- `Registry.process` validates the HMAC, then immediately forwards `request.shop` (the unauthenticated header) into the handler as the tenant identifier, alongside the (correctly signed) body: [4](#0-3) 

Because the app's `api_secret_key` is shared across *all* shops that install a given public app, any merchant that installs the app receives legitimately-HMAC-signed webhook deliveries for their own shop. Nothing in this gem prevents an attacker who controls their own installed shop from capturing one of these legitimate `(raw_body, hmac)` pairs and replaying it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain. The HMAC still validates successfully (it only checks the body bytes), but `request.shop` — and therefore `WebhookMetadata#shop` delivered to the app's handler — now falsely claims the victim shop as the source.

This breaks the identity binding the gem is expected to enforce: "shop authenticated" (i.e., cryptographically tied to the payload) versus "shop stored/used as the tenant key" downstream, matching the documented analog class of an HMAC that doesn't cover a field that is nonetheless acted upon.

### Impact Explanation
Host applications rely on `WebhookMetadata#shop` (sourced from `Webhooks::Request#shop`) as the tenant key to decide which merchant's data/session the webhook body should be applied to — this is the gem's documented contract (see `docs/usage/webhooks.md` usage of `data.shop` in handlers). Because `shop` is unauthenticated, an attacker can forge which tenant a signed-but-attacker-controlled payload gets attributed to, enabling cross-tenant webhook injection: a payload legitimately signed for the attacker's own shop can be misattributed to and processed against a victim's shop, corrupting or exfiltrating cross-tenant data depending on what the handler does with `data.shop` (e.g., persisting data keyed by shop, revoking/deleting resources, triggering shop-scoped side effects). This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is realistic for any developer using an app that operates as a public/multi-tenant Shopify app (the normal use case for this gem): the attacker only needs to be a legitimate merchant who has installed the app (unprivileged relative to other tenants), capture one webhook HTTP request sent to their own endpoint, and replay it with a modified `shop-domain` header value. No access to the app's `api_secret_key` or any victim credentials is required — only the ability to observe/replay one's own inbound webhook traffic and issue an unauthenticated HTTP request to the app's public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`api-version`) to the HMAC-verified content, e.g., by:
- Including the shop domain (and other identity-bearing headers) in the string that is HMAC-verified, or
- Requiring the host application to independently confirm that the `shop-domain` header corresponds to a shop with an active, previously-established session/installation before trusting it, and documenting this requirement clearly, or
- At minimum, cross-checking `request.shop` against an out-of-band trusted source (e.g., looked-up session for the topic/webhook id) rather than trusting the raw header value implicitly in `Registry.process`.

### Proof of Concept
1. App `A` is installed on both the attacker's shop `attacker.myshopify.com` and the victim's shop `victim.myshopify.com`, sharing the same `api_secret_key`.
2. Shopify sends a legitimate webhook to `A`'s endpoint for `attacker.myshopify.com`:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body computed with api_secret_key>
   x-shopify-shop-domain: attacker.myshopify.com
   Body: {"id": 1, ...attacker-controlled order data...}
   ```
   The attacker captures this `(raw_body, hmac)` pair (it is delivered to their own server).
3. Attacker replays the exact same request to `A`'s endpoint but changes only the header:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
   keeping `raw_body` and `x-shopify-hmac-sha256` identical.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (= `raw_body`, unchanged) and it matches — validation passes. [5](#0-4) 
5. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` = `"victim.myshopify.com"` and dispatches it to the app's handler, which now performs shop-scoped work believing this signed order payload legitimately belongs to `victim.myshopify.com`. [6](#0-5)
