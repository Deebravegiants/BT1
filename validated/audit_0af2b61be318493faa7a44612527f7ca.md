### Title
Webhook `shop` (and topic/webhook-id) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) fields straight from unauthenticated HTTP headers, while `Utils::HmacValidator` only signs/verifies the raw request body. `Webhooks::Registry.process` accepts any request whose body+HMAC pair is valid and then trusts the header-derived `shop` value when building `WebhookMetadata` handed to the app's handler — breaking the binding `shop_authenticated == shop_acted_on`.

### Finding Description
`Request#shop` simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed payload: [1](#0-0) 

The HMAC that Shopify computes and that this gem verifies covers only the raw body, never the headers: [2](#0-1) 

`HmacValidator.validate` signs/compares against `verifiable_query.to_signable_string`, i.e. `@raw_body` only: [3](#0-2) 

`Registry.process` validates only this body HMAC, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` object delivered to the host application's handler: [4](#0-3) 

Because a single `api_secret_key` is shared by the app across every shop that installs it, any entity that legitimately possesses one valid `(raw_body, hmac)` pair for that key — e.g. a merchant who installed the app on their own store and can observe their own webhook deliveries — can replay that exact body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and `webhook-id`/`topic`) header for a different, victim shop. `HmacValidator.validate` will still pass because it never inspects those headers, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop: [5](#0-4) 

This is the "field acted on but not covered by the HMAC" binding break: the identity used for authorization/routing (`shop`) is disjoint from the identity actually authenticated (the raw body bytes).

### Impact Explanation
Any host application that uses `request.shop`/`data.shop` from `WebhookMetadata` to select which tenant's records to create, update, or delete (a documented, expected usage pattern of this gem) can be made to apply another shop's webhook body under an attacker-chosen shop identity, or vice versa. This is a cross-tenant integrity violation reachable purely through the gem's own webhook-processing API surface (`Registry.process`), satisfying the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Any Shopify merchant that installs the app is, by construction, able to legitimately trigger webhooks for their own shop and inspect the delivered `(body, hmac)` — no leaked secret or privileged account is required, only normal use of the app as an ordinary (low-trust) installer. Replaying that pair against the same public webhook endpoint with a forged `shop` header requires no `api_secret_key` knowledge, no TLS interception and no social engineering, so this is exploitable by an unprivileged internet-reachable actor who is merely one of the app's own tenants.

### Recommendation
Bind the identity fields to the signed payload instead of trusting bare headers: include `shop`, `topic`, and `webhook_id` in the signable string used by `HmacValidator`, or otherwise cryptographically bind them, so that `Registry.process` can prove the `shop` value delivered in `WebhookMetadata` was authenticated together with the body, not merely accompanying it.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a normal webhook event, capturing the delivered request: headers (including `x-shopify-shop-domain: attacker-shop.myshopify.com`) plus raw body `B` and its valid `x-shopify-hmac-sha256` value `H` (computed by Shopify using the app's shared `api_secret_key`).
2. Attacker resends the exact same `raw_body: B` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and optionally a different `x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) only — this still matches `H`, so validation passes (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `shop` value and invokes the app's `handler.handle(data:)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-supplied data under the victim shop's identity.
