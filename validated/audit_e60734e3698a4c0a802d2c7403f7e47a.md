### Title
Webhook shop-domain / topic identity is not covered by the HMAC signature, allowing tenant/topic spoofing on an otherwise valid webhook body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values that the registry hands to the app's handler are read directly and unauthenticated from HTTP headers. `Registry.process` validates the HMAC and then trusts these header-derived fields as the tenant/event identity, breaking the binding `authenticated(body) == identity(shop, topic)` that a multi-tenant app needs to safely route a webhook to the correct shop's data.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from request headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC using `HmacValidator.validate`, which internally calls `validate_signature`/`compute_signature` over `verifiable_query.to_signable_string` (i.e., only the raw body), and then immediately trusts `request.topic` and `request.shop` to dispatch the handler and construct `WebhookMetadata`: [3](#0-2) [4](#0-3) 

The equality the gem is implicitly promising is: `HMAC-verified-bytes == bytes the app treats as authenticated for this shop/topic`. In fact, only `raw_body` is HMAC-verified; `shop-domain`, `topic`, `webhook-id`, and `api-version` are parsed from headers that are never part of the signed string, so `HMAC-verified-bytes ⊊ identity-bytes-trusted-by-handler`. This is the same class of defect as the reported `SnapshotERC20Guild` bug: a value used to make an authorization/identity decision (there, `votingPower`; here, `shop`/`topic`) is not covered by the mechanism (there, the snapshot; here, the HMAC) that is supposed to make that value trustworthy.

### Impact Explanation
Because the `shop-domain` header is not part of the signed material, any request that reaches the app's webhook endpoint with a body+HMAC pair that validates (for example, a body an attacker can get validly signed for their own shop, or any body whose HMAC they can otherwise obtain) can be replayed with an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header value. A host application that follows this gem's documented pattern — trust `WebhookMetadata#shop` returned by `Registry.process` as the tenant key for looking up records or an access token — can be tricked into acting on data under a different shop's identity than the one that actually authenticated the payload, i.e. cross-tenant access. This satisfies the Critical impact bar ("cross-tenant access") because the boundary broken is exactly the shop-to-payload binding that this gem is responsible for enforcing before handing data to the app.

### Likelihood Explanation
Exploitability depends entirely on an attacker being able to produce (or capture) any raw body + valid HMAC pair signed with the app's `client_secret` (e.g., from webhooks fired to their own, attacker-controlled shop that has installed the app) and then re-POST it to the app's webhook endpoint with a different `shop-domain`/`topic` header. This is plausible for any public app that accepts install from arbitrary shops, since the webhook HMAC secret is shared per-app (not per-shop), and nothing in `Webhooks::Request` or `Registry.process` re-derives or cross-checks the header-supplied shop/topic against anything cryptographically tied to that specific shop.

### Recommendation
Bind the identity fields into the signed material, or otherwise verify them out-of-band: at minimum, verify that the `shop-domain` header corresponds to a shop that is expected to be sending exactly the topic/body received (e.g., cross-check against a shop-specific webhook secret, or validate the `shop` against `ShopValidator` and confirm the request originated from Shopify's known IP ranges/endpoint), and document clearly in `Registry.process`/`WebhookMetadata` that `shop`/`topic` are unauthenticated header values so host apps do not treat them as a trusted tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimately Shopify-signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`), `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker replays the exact same `raw_body` (`B`) and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` in [4](#0-3)  still succeeds because it only checks `B` against `H` — the shop header is never part of the signed string.
4. `Registry.process` in [3](#0-2)  passes `request.shop` (now `victim.myshopify.com`) straight into `WebhookMetadata`, so the host app processes attacker-controlled data as if it belongs to the victim shop.
