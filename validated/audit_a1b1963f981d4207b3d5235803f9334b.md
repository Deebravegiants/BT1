### Title
Attacker-supplied swap route executes arbitrary pool code under the caller's signed authorization tree, enabling wallet-token theft - (File: contracts/controller/src/strategies/swap.rs)

### Summary
CVE-2022-0517 is "trusting and loading attacker-controlled configuration/code from an unsecured location, yielding arbitrary code execution with the victim's privileges." The on-chain analog: the controller's strategy entrypoints (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, `flash_position`) accept a caller-supplied `StrategySwap` payload and forward it verbatim to the swap aggregator, which invokes whatever `pool`/`token` contract addresses the payload names, with no venue or pool allowlist. Code inside such a hop runs on the call stack below the caller's `require_auth`, so any `token.transfer(victim, attacker, x)` it makes is recorded as a child of the caller's authorization entry and executes if the caller signs the simulated tree — draining tokens the protocol never touched.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` validates only `amount_in > 0` and a non-empty payload, authorizes one exact input transfer to the configured router, and calls `router.execute_strategy(&controller, &amount_in, swap)` with the raw caller bytes (line 37). It never inspects which contracts the route will invoke. The router's `dispatch_hop` (`contracts/swap-aggregator/src/venues/mod.rs:23-59`) calls `env.invoke_contract(&ctx.hop.pool, "swap", ...)` (e.g. `phoenix.rs:23-25`) for whatever address the payload encodes — "The router calls the pool and token addresses its payload names and keeps no allowlist of them" (`docs/explanation/threat-model.md:154-156`).

The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the exploit end-to-end via `swap_collateral`: a `RogueHopPool.swap` that calls `token::Client::transfer(alice, attacker, WALLET_BALANCE)` (lines 62-71) executes, and `env.auths()` shows the stolen transfer recorded as a sub-invocation of Alice's `swap_collateral` root (lines 206-222), leaving Alice's balance 0 and the attacker's at `WALLET_BALANCE` (lines 224-225) — while the position still receives a fair swap output and passes all risk gates.

### Impact Explanation
Theft of user funds. Any token held by the victim's wallet — including assets never supplied to or listed by the protocol — can be transferred to the attacker inside the signed transaction. The loss is unbounded by `amount_in`, the payload `min_out`, or the controller's final health/collateral gates, because it is the caller's wallet authorization being abused, not routed funds. Neither the measured-output check (`verify_router_output`, swap.rs:75-84) nor the final account risk check bounds it (`threat-model.md:157-161`).

### Likelihood Explanation
High feasibility for a phishing-style attack: an unprivileged attacker crafts a `StrategySwap` payload whose hop `pool` is an attacker-deployed contract, gets the victim to sign the composed `swap_collateral`/`swap_debt`/`multiply` transaction (route bytes are opaque XDR that wallets do not decode for the user), and the recorded authorization tree is accepted because the rogue transfer attaches as a child of the entry the user intended to sign. The only mitigation is client-side route decoding, which the threat model itself documents as an external requirement (`threat-model.md:161-165`) — the contracts enforce nothing.

### Recommendation
Enforce an on-chain allowlist of permitted venue/pool addresses (or venue types with governance-vetted pools) inside `execute_strategy`/`dispatch_hop`, or have the controller refuse strategy payloads it cannot verify against such a list. At minimum, restrict hop invocations so payload-named contracts cannot be reached beneath a user's `require_auth` tree — e.g. require each hop pool address to come from governance-managed storage rather than caller bytes.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `Scene::route_through_pool_stealing` registers `RogueHopPool` with `(victim=alice, wallet_token, to=attacker, WALLET_BALANCE)` and embeds it as the hop pool in a `swap_collateral` route; the simulation test shows the `transfer(alice, attacker, WALLET_BALANCE)` recorded under Alice's `swap_collateral` auth entry and both balances moved as expected.
