Audit Report

## Title
Malicious ERC20-Backed Foreign Asset Can Block/Grief Multi-Asset XCM `DepositAsset`/`TransferAsset` Batches - (File: `polkadot/xcm/xcm-executor/src/lib.rs`, `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` makes an XCM asset transactor call into arbitrary, attacker-deployed `pallet_revive` contract code, and it is wired into asset-hub-westend's production `AssetTransactors` tuple with a fully permissionless matcher (`ERC20Matcher`/`IsLocalAccountKey20`) that recognizes any `(0, [AccountKey20 { .. }])` location as a valid ERC20 asset, with no registration or governance gate. Because `TransferAsset`/`InitiateTransfer` and, on the retry pass, `deposit_assets_with_retry` in `polkadot/xcm/xcm-executor/src/lib.rs` process multiple bundled assets under a single `TransactionalProcessor`/error-propagating loop, a single malicious ERC20 contract that reverts on demand can abort the whole instruction, causing legitimate co-bundled assets to fail delivery and the entire pre-instruction holding to be trapped.

## Finding Description
`ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` perform a `pallet_revive::Pallet::<T>::bare_call` into a contract address resolved from the XCM asset's `AccountKey20` junction, and treat `return_value.did_revert()` as `Err(XcmError::FailedToTransactAsset(...))` [1](#0-0) [2](#0-1) .

Critically, the matcher used by this transactor, `ERC20Matcher = MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, matches *any* location of the shape `(0, [AccountKey20 { .. }])` with no registry, whitelist, or governance check [3](#0-2) . `ERC20Transactor` is included in asset-hub-westend's production `AssetTransactors` tuple [4](#0-3) . This confirms the previously-open question in the original report: recognition of an arbitrary `pallet_revive` contract as an XCM-fungible asset is permissionless — any user can deploy an ERC20-like contract and reference it by its address in an `AccountKey20` junction without any registration step.

The XCM executor batches multiple assets in a single atomic instruction. `TransferAsset` iterates `assets.inner()` and calls `transfer_asset_with_surplus` per-asset inside one `TransactionalProcessor::process` closure, propagating the first error with `?` [5](#0-4) . `transfer_asset_with_surplus`'s default implementation falls back to `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` [6](#0-5) , which for the ERC20 asset invokes attacker-controlled contract code. Similarly, `deposit_assets_with_retry`'s retry pass short-circuits with `?` on the first failing deposit [7](#0-6) .

## Impact Explanation
When the malicious ERC20 asset's transfer/deposit call reverts, the entire `TransferAsset`/`DepositAsset`/`InitiateTransfer` instruction aborts via the propagated `XcmError`, and `post_process` traps the full pre-instruction holding (both the legitimate and malicious assets) rather than losing them, as demonstrated by the repo's own tests `deposit_assets_with_retry_aborts_on_failure_and_post_process_traps` and `partial_deposit_failure_aborts_instruction_and_traps_full_holding` [8](#0-7) [9](#0-8) . The trap-and-`ClaimAsset` recovery path means funds are not permanently lost, so the concrete impact is availability/griefing (blocked delivery, `Outcome::Incomplete`, requiring a manual `ClaimAsset` follow-up) rather than fund loss.

## Likelihood Explanation
The precondition — an attacker-controlled `pallet_revive` contract being recognized as a valid XCM fungible asset — is confirmed permissionless: `IsLocalAccountKey20` and `ERC20Matcher` accept any `AccountKey20` location with no registration or governance step. Any user can deploy such a contract on Asset Hub Westend and construct an XCM instruction referencing it. However, actually griefing a victim's batch requires that victim to voluntarily bundle the attacker's asset alongside their own legitimate assets in the same `DepositAsset`/`TransferAsset` instruction (e.g., by trusting an attacker-supplied multi-asset XCM program, or by a relayer/aggregator combining unrelated deposits into one instruction) — this is a realistic but non-trivial precondition, not automatically triggered against arbitrary unrelated victims' independent XCM messages.

## Recommendation
- Treat ERC20-backed foreign assets matched via `IsLocalAccountKey20`/`ERC20Matcher` as untrusted, attacker-controlled code paths at the UI/tooling level, since no registration gate exists.
- Consider isolating per-asset transactor calls in `TransferAsset`/`InitiateTransfer` (mirroring the first-pass isolation already present in `deposit_assets_with_retry`) so a single reverting/malicious asset does not force rollback of already-completed transfers for co-bundled legitimate assets.
- Document that bundling foreign/ERC20-backed assets with trusted assets in a single XCM instruction carries availability risk given the permissionless nature of ERC20 asset recognition.

## Proof of Concept
Static analysis confirms the mechanism: deploy a Solidity contract that always reverts on `transfer()`, reference its address via `Location { parents: 0, interior: X1(AccountKey20 { key, network: None }) }` in an XCM `DepositAsset`/`TransferAsset` instruction alongside a legitimate asset, and execute. Per the confirmed code path, the malicious contract's `did_revert()` propagates as `XcmError::FailedToTransactAsset`, aborting the whole instruction with `Outcome::Incomplete` and trapping the full pre-instruction holding (as already exercised by the analogous tests `deposit_assets_with_retry_aborts_on_failure_and_post_process_traps` and `partial_deposit_failure_aborts_instruction_and_traps_full_holding` for other `TransactAsset` implementations). A full PoC would additionally require an asset-hub-westend integration test wiring a reverting mock ERC20 via `pallet_revive` through `ERC20Transactor` in a bundled `DepositAsset`/`TransferAsset` instruction to directly confirm the outcome end-to-end.

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;

	fn convert(location: &Location) -> Option<H160> {

	fn deposit_assets_with_retry(
		to_deposit: AssetsInHolding,
		beneficiary: &Location,
		context: Option<&XcmContext>,
	) -> Result<Weight, XcmError> {
		let mut total_surplus = Weight::zero();
		let mut failed_deposits = AssetsInHolding::new();

		// First pass: try to deposit each asset; failures go to retry.
		for single in to_deposit.into_per_asset_holdings() {
			match Config::AssetTransactor::deposit_asset_with_surplus(single, beneficiary, context)
			{
				Ok(surplus) => total_surplus.saturating_accrue(surplus),
				Err((unspent, _)) => {
					// First-pass failure: keep for retry. A subsequent deposit in the same
					// pass may create the destination account (by satisfying ED), allowing
					// the retry pass to succeed for assets that fall here.
					failed_deposits.subsume_assets(unspent);
				},
			}
		}

		// Retry previously failed deposits, this time short-circuiting on any error.
		for single in failed_deposits.into_per_asset_holdings() {
			let surplus =
				Config::AssetTransactor::deposit_asset_with_surplus(single, beneficiary, context)
					.map_err(|(unspent, error)| {
					tracing::debug!(
						target: "xcm::deposit_assets_with_retry",
						?error,
						?unspent,
						"Retry-pass deposit failed"
					);
					error
				})?;
			total_surplus.saturating_accrue(surplus);
		}

		Ok(total_surplus)
	}

	fn transfer_asset_with_surplus(
		asset: &Asset,
		from: &Location,
		to: &Location,
		context: &XcmContext,
	) -> Result<(Asset, Weight), XcmError> {
		match Self::internal_transfer_asset_with_surplus(asset, from, to, context) {
			Err(XcmError::AssetNotFound | XcmError::Unimplemented) => {
				let (credit, withdraw_surplus) =
					Self::withdraw_asset_with_surplus(asset, from, Some(context))?;
				let deposit_surplus = Self::deposit_asset_with_surplus(credit, to, Some(context))
					.map_err(|(unspent, error)| {
					// best effort try to return the assets to original owner
					let _ = Self::deposit_asset(unspent, from, Some(context));
					error
				})?;
				let total_surplus = withdraw_surplus.saturating_add(deposit_surplus);
				Ok((asset.clone(), total_surplus))
			},
			result => result,
		}
	}

#[test]
fn deposit_assets_with_retry_aborts_on_failure_and_post_process_traps() {
	// fund sender
	add_asset(SENDER, (Here, 200u128));

	// sub-ED amount (< ED=2): this `DepositAsset` will fail and abort the program.
	let dust: Asset = (Here, 1u128).into();

	// ≥ED amount: would succeed on its own — but the program aborts at the first error,
	// so this instruction never runs.
	let legit: Asset = (Here, 100u128).into();

	let xcm = Xcm::<TestCall>(vec![
		WithdrawAsset((Here, 101u128).into()),
		DepositAsset { assets: Definite(Assets::from(vec![dust])), beneficiary: RECIPIENT.into() },
		DepositAsset { assets: Definite(Assets::from(vec![legit])), beneficiary: RECIPIENT.into() },
	]);

	let (mut vm, weight) = instantiate_executor(SENDER, xcm.clone());

	let err = vm
		.bench_process(xcm)
		.expect_err("a sub-ED `DepositAsset` must error out and abort the rest of the XCM");
	vm.set_error(Some((err.index, err.xcm_error)));

	let outcome = vm.bench_post_process(weight);
	assert!(
		matches!(outcome, Outcome::Incomplete { .. }),
		"Expected Incomplete, got {:?}",
		outcome
	);

	// Nothing reached the recipient: the failing `DepositAsset` rolled back its own take,
	// and the subsequent `DepositAsset(legit)` was never executed because the program is
	// already in error state.
	let here_assets = asset_list(RECIPIENT);
	assert!(here_assets.is_empty(), "no deposit should reach recipient when program aborts");

	// `post_process` trapped the leftover holding — the full 101 originally withdrawn.
	let trapped = asset_list(TRAPPED_ASSETS);
	assert_eq!(
		trapped,
		vec![(Here, 101u128).into()],
		"the entire pre-instruction holding must be trapped (claimable later), not silently lost"
	);
}

#[test]
fn partial_deposit_failure_aborts_instruction_and_traps_full_holding() {

	add_asset(SENDER, (Parent, 1u128)); // < ED — will fail on retry

			assets: AssetFilter::Wild(WildAsset::All),

		},
	]);
