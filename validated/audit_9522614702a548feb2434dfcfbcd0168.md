### Title
Excess native ETH sent to `EvmHost.dispatch`/`fundRequest` is refunded by Uniswap to the Host contract, not to the caller, permanently trapping the surplus - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` are `payable` functions that accept native ETH and forward the *entire* `msg.value` to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)` in order to buy an exact amount of `feeToken` (`post.fee`, `get.fee`, or `amount`). This mirrors the `AvailBridge.sendMessage` bug class: a user-supplied payable value that is greater than the amount actually required is not returned to the original caller.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

`swapETHForExactTokens` only consumes the ETH needed to obtain the exact `amountOut` (`post.fee`/`get.fee`/`amount`) and, per the standard UniswapV2Router02 implementation, refunds any unused ETH via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])`. Because `EvmHost` itself is the caller of the router (not the end user), the refund lands back in `EvmHost`, not in `_msgSender()` (the dispatcher/user who originally overpaid). There is no code path in `EvmHost.sol` that captures this router refund and forwards it to `_msgSender()`/`post.payer`/`get.payer`. Unlike `AvailBridge`, the surplus isn't even explicitly added to a `fees` accounting variable — it simply accumulates as ETH balance on the Host contract with no user-facing mechanism to reclaim it, and no documented admin sweep for native ETH (protocol revenue withdrawal is only handled in `feeToken`, e.g., via `hostManager`/`GetRequestTimeoutHandled`/fee refund paths, which operate exclusively on `IERC20(feeToken())`).

Any caller who overestimates the native ETH needed (e.g. due to slippage buffering, as explicitly done by `HyperbridgeLzEndpoint.quote` which applies "a generous 2x buffer" per its own comments) permanently loses the difference between `msg.value` and the ETH actually consumed by the swap: [4](#0-3) 

This is the same root cause class as the reported `AvailBridge.sendMessage` issue: a payable entrypoint accepts `msg.value` greater than what's required for the operation, with no refund logic for the excess.

### Impact Explanation
Every unprivileged caller of `IDispatcher.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest` on any EVM chain that pays with native token risks losing the ETH surplus above the exact swap cost. Given Uniswap V2 pricing is variable (slippage, price movement between quote and execution), users/integrators (e.g. `HyperFungibleToken.send`, `WrappedHyperFungibleToken.send`, `IntentGatewayV2`/`ExtrinsicIntents` fill/cancel flows, `HyperbridgeLzEndpoint`) that pass `msg.value` computed off-chain via `quote()` — which itself warns it is subject to sandwich-attack-level imprecision — will regularly overpay, and that overpayment is unrecoverable. This is a direct, permanent loss of user funds at protocol scale (every dispatch call using native payment), not a one-off mistake.

### Likelihood Explanation
High. Native-token dispatch is a first-class, documented payment method (`docs/content/developers/evm/messaging/post-requests.mdx`), and the SDK/docs explicitly recommend using `quote()` off-chain estimates (acknowledged to be imprecise and subject to sandwich attacks) to determine `msg.value`. Any deviation between the estimated fee and actual on-chain Uniswap price at execution time (which is common and expected) results in a nonzero, non-refunded surplus. This will happen routinely under normal operation, not merely in an adversarial/negligent edge case.

### Recommendation
After calling `swapETHForExactTokens`, capture the returned `amounts` array (or measure `address(this).balance` before/after the swap) and refund any leftover ETH balance to `_msgSender()` (or the designated `payer`) in all three functions: `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`. Use `swapETHForExactTokens`'s returned `amounts[0]` to compute `msg.value - amounts[0]` and transfer it back via a safe ETH transfer helper.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch{value: X}(DispatchPost{... fee: F ...})` where `X > F`'s ETH-equivalent cost at current Uniswap price.
2. Inside `dispatch`, `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: X}(F, path, address(this), block.timestamp)` executes, consuming only `Y < X` ETH to acquire exactly `F` feeToken units.
3. The router refunds `X - Y` ETH to `msg.sender` of the router call, which is `EvmHost` (`address(this)`), not the original transaction sender.
4. `EvmHost` has no logic to detect or forward this `X - Y` surplus to `_msgSender()`; it remains trapped in the Host contract's ETH balance indefinitely, unrecoverable by the user who paid it.
