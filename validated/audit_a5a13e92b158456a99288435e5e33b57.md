### Title
`Oauth.validate_auth_callback` sends the app's `client_secret` to an unvalidated `shop` host, unlike every other credential-issuing flow in the gem - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the OAuth access-token request URL directly from `auth_query.shop` via `auth_base_uri(shop)` without ever passing it through `Utils::ShopValidator.sanitize!`, even though every other credential-exchange path in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before using the shop value to construct the request host that receives `client_id`/`client_secret`.

### Finding Description
`validate_auth_callback` validates the HMAC of the callback query (`Utils::HmacValidator.validate(auth_query)`, `lib/shopify_api/auth/oauth.rb:64`) and the `state` cookie, then immediately uses `auth_query.shop` unsanitized to build the base URI for the token request: [1](#0-0) 

and [2](#0-1) 

`auth_base_uri` builds `"https://#{shop}/admin"` with no domain allow-listing, and the `Clients::HttpClient` sends the POST containing `client_id` and `client_secret` in the JSON body to that host.

By contrast, the sibling credential flows all enforce the invariant `sanitized_shop == Utils::ShopValidator.sanitize!(shop)` before the same client_secret-bearing POST is issued: [3](#0-2) [4](#0-3) [5](#0-4) 

`ShopValidator.sanitize!` raises `Errors::InvalidShopError` unless the host resolves to one of the `TRUSTED_SHOPIFY_DOMAINS` (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`): [6](#0-5) [7](#0-6) 

This inconsistency breaks the equality the gem otherwise enforces everywhere else: `host that receives client_secret == a domain validated by ShopValidator`. In `oauth.rb` the equality checked is only `HMAC(query) == valid`, which binds `shop` to the *signed query string*, but never constrains `shop` to actually be a Shopify-owned host before that value is turned into a network destination for the client secret.

### Impact Explanation
Whether this is exploitable depends entirely on where `auth_query.shop` originates before it reaches this method, which is outside this gem's control (the host application constructs `AuthQuery` from its own request parameters, as shown in the gem's own docs example). If a host application does not itself sanitize the `shop` query parameter — and the gem provides no built-in enforcement here despite doing so in the other three sibling flows — an attacker-supplied `shop` value in the callback URL query string is used verbatim to build the destination for the token exchange request, causing the app's `client_id`/`client_secret` to be POSTed to an attacker-influenced host (SSRF carrying the app's credentials) if the surrounding query happens to carry a validly-computed HMAC (e.g., replay/forwarding scenarios, or non-standard `shop` values Shopify itself might redirect with, such as unified-admin/dev hosts that `ShopValidator` explicitly normalizes but `oauth.rb` does not).

This matches the escalation pattern in the reported analog class: a value participates in one binding (HMAC over the query) but is not bound to the separate, security-relevant use it is later put to (as the destination host for a secret-bearing request) — mirroring the report's "field acted on but not covered by the intended check" pattern, here applied to the host-vs-validated-host binding rather than a leftover-balance transfer.

### Likelihood Explanation
Moderate-to-low confidence without visibility into how a specific host application constructs `AuthQuery`. The gem's own inconsistency — sanitizing `shop` in three of four credential-issuing code paths and omitting it in `validate_auth_callback` — is the strongest signal that this omission is a defect rather than an intentional design choice, but I could not fully verify from the available files whether Shopify's own OAuth redirect ever supplies `shop` values that require the same normalization `ShopValidator` performs (e.g., `.spin.dev`/unified-admin hosts), which would make the missing check practically reachable even for a fully-compliant host app.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, sanitize `auth_query.shop` with `Utils::ShopValidator.sanitize!` immediately after HMAC/state validation, and use the sanitized value both to construct `null_session` and to build `auth_base_uri`, mirroring `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb#migrate_to_expiring_token`.

### Proof of Concept
Not independently reproducible from the gem alone: the exact trigger depends on how a specific host application populates `AuthQuery#shop` from the callback request and whether an HMAC-valid query with a non-`myshopify` `shop` value can occur in practice (e.g., relayed/forwarded callback, or Shopify-issued dev/spin domains). The code-level gap — missing `ShopValidator.sanitize!` call before `auth_base_uri(shop)` is used to send `client_secret` — is directly verifiable by comparing `lib/shopify_api/auth/oauth.rb:60-113` against the sanitize-then-use pattern in `lib/shopify_api/auth/client_credentials.rb:19-33`, `lib/shopify_api/auth/refresh_token.rb:18-33`, and `lib/shopify_api/auth/token_exchange.rb:97-115`.

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
