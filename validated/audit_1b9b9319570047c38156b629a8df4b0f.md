### Title
Non-embedded session lookup trusts raw, unsigned cookie value as the session id, enabling cross-tenant session hijack - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
For non-embedded apps, `ShopifyAPI::Utils::SessionUtils.current_session_id` returns the session id by reading it verbatim out of the `shopify_app_session` cookie, with no signature or MAC check that the value actually originated from this gem's OAuth flow.

### Finding Description
`SessionUtils.cookie_session_id` simply does `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` and returns it as the session id, unconditionally, for both the embedded-fallback and non-embedded paths [1](#0-0) [2](#0-1) .

The cookie value that legitimate OAuth completion sets is fully deterministic and computed from public data: `Session.from` builds the id as `"#{shop}_#{associated_user.id}"` for online sessions or `"offline_#{shop}"` for offline sessions [3](#0-2) . `Oauth.validate_auth_callback` writes this same id straight into the `SessionCookie` value with no additional signature: `SessionCookie.new(value: session.id, expires: ...)` [4](#0-3) . The `SessionCookie` struct itself carries only `name`, `value`, `expires` — no `hmac` or `signature` field to bind the value to the issuing transaction [5](#0-4) .

The binding that should hold is: **cookie value == the session id that this gem's own OAuth flow generated for the requesting browser's shop/user**. Instead, the gem's `cookie_session_id` accepts **any bytes present in the cookie** as the session id, i.e. the check degenerates to **cookie value == cookie value**, with no verification that those bytes were ever produced by `Session.from`/`validate_auth_callback` for the current shop. Since shop domains are public and shop/user id formats are documented and predictable (`shop_userid` / `offline_shop`), any unprivileged internet user who can set an arbitrary cookie value on their own browser session (trivial — cookies are always attacker-writable client-side, or via any host-app endpoint that reflects/sets cookie content from user input) can supply another merchant's `offline_<shop>` or `<shop>_<user_id>` string as their session id.

If the host application stores sessions keyed by this id (which is exactly the documented pattern this gem promotes — "pass the cookies into `current_session_id`" to retrieve a session for making authenticated Admin API calls), the returned id is then used to look up a `Session` containing another shop's real `access_token`. This breaks the identity binding "session id must have been issued by this gem's own OAuth completion for this browser" and effectively allows a cross-tenant session/access-token substitution purely from attacker-supplied cookie bytes — no `api_secret_key`, no token, and no privileged access is required by the attacker.

### Impact Explanation
This satisfies "Critical - cross-tenant access": an unauthenticated/unprivileged actor can, purely by setting a cookie, cause an app instance to resolve and use a *different* merchant's session/access token, because the gem never verifies that the session id in the cookie was legitimately produced for the requesting tenant. The only mitigating factor is that the host application must actually use session ids returned by `current_session_id`/`cookie_session_id` to fetch a `Session` from storage — but that is precisely the documented and intended usage of this API (see `docs/getting_started.md`'s "Cookie" section instructing developers to pass cookies into `current_session_id`).

### Likelihood Explanation
High for any app following the gem's documented non-embedded cookie flow verbatim: the session id format is public and deterministic (`offline_<shop>` or `<shop>_<user-id>`), shop domains are enumerable/public, and cookies are always writable by the client. No cryptographic secret, token, or privileged access is needed to exploit — only knowledge of another tenant's shop domain (and, for online sessions, a user id, which may also be enumerable).

### Recommendation
Bind the session cookie value to the OAuth transaction cryptographically (e.g., HMAC-sign the cookie value with `Context.api_secret_key`, or store only an opaque, server-generated random token in the cookie that maps to the session server-side) so `cookie_session_id` can verify integrity/origin before trusting the value, rather than returning raw, attacker-controllable cookie bytes as an authoritative session id.

### Proof of Concept
1. Merchant A installs the app; OAuth completes and the gem sets cookie `shopify_app_session = "offline_shop-a.myshopify.com"` (deterministic, per `Session.from`/`validate_auth_callback`).
2. Attacker, running the same non-embedded app in their own browser, manually sets their `shopify_app_session` cookie to `"offline_shop-a.myshopify.com"` (a value they can construct with zero secrets, since the id format is documented and `shop-a.myshopify.com` is a public domain).
3. Attacker calls any host-app route that does `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` — the gem returns `"offline_shop-a.myshopify.com"` verbatim [6](#0-5) .
4. The host app looks up the `Session` for that id from its store and uses its `access_token` on behalf of the attacker's request — the attacker is now operating with Merchant A's access token, a cross-tenant compromise.
