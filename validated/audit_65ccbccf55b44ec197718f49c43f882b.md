The gem's own documentation explicitly instructs developers to use `data.shop` as the tenant identifier (`shop_domain: data.shop`) after `ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" [1](#0-0) [2](#0-1) , yet the HMAC only signs the raw body, not the shop-domain header.

### Title
Webhook shop-domain identity spoofing via HMAC that only covers the body, not the `shop` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as the mechanism that "verify[ies] the request did indeed come from Shopify" before dispatching to a merchant's webhook handler with a `WebhookMetadata` struct that carries `shop` as the tenant identifier. However the HMAC signature computed and verified by the gem only covers the raw request body, never the `shop`, `topic`, `webhook_id`, or `api_version` headers. An attacker who can obtain one genuinely-signed webhook body/HMAC pair (e.g., by installing the app on their own shop and receiving a real Shopify webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. The signature check still passes because the header is not part of the signed payload, so the handler receives forged data attributed to a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it with the `hmac-sha256` header value: [4](#0-3) 

`Registry.process` treats a passing `HmacValidator.validate` result as proof the request came from Shopify, and then constructs `WebhookMetadata` using `request.shop`, which is read directly and unauthenticated from the `shop-domain` header: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `shop header value == shop the HMAC was computed for`. Because the HMAC only signs `@raw_body`, this equality is never checked — the `shop` field is a field acted on (used to route/attribute webhook data to a tenant) but not covered by the HMAC, matching exactly the class of flaw called out in scope. Since the same `api_secret_key` is shared across all shops installing a given app, any shop that has legitimately installed the app can capture one valid `(raw_body, hmac)` pair from Shopify and reuse it against the app's webhook endpoint with a forged `shop-domain` header naming a different, victim shop.

### Impact Explanation
This breaks cross-tenant isolation: a malicious merchant (or anyone who can capture a legitimately-signed webhook payload, since headers are visible on the wire/in server logs and the same webhook body format applies across order/product/etc. topics regardless of shop) can cause the app to process attacker-controlled webhook data while believing it originates from an arbitrary victim shop domain. Depending on how the host application uses `data.shop` (e.g., looking up the victim's stored session/access token to act on their behalf, or writing data into the victim's tenant record), this can lead to cross-tenant data corruption or being tricked into performing privileged actions against the wrong store — squarely a cross-tenant access issue.

### Likelihood Explanation
Likelihood is realistic for any developer who has installed the target app themselves (a common step for competitors or malicious actors when the app is public on the Shopify App Store): they receive a real webhook with a valid HMAC for their own shop, then only need to change one HTTP header and replay the request to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is required — only the ability to install the app once and control the header of a subsequently forged request.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signed payload used for HMAC verification, matching Shopify's actual webhook signing scheme's intent — or, more practically, since Shopify does not sign these headers itself, the app must be documented to independently verify that `data.shop` corresponds to a shop that is expected to be sending this specific webhook (e.g., cross-check against a known/installed shop list) rather than treating `HmacValidator.validate` as authenticating the `shop` field at all. At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not covered by HMAC verification and must not be trusted as an authenticated tenant identifier without additional application-level checks.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, obtaining a genuine webhook delivery, e.g. for `orders/create`, with a body `raw_body` and header `x-shopify-hmac-sha256: <valid_hmac>` computed by Shopify over `raw_body` using the app's `api_secret_key`.
2. Attacker sends a new POST request to the app's webhook endpoint with the same `raw_body` and the same `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and finds it matches — validation passes despite the forged `shop-domain` header [8](#0-7) .
5. The registered handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the host application to attribute the attacker's forged/replayed webhook data to the victim shop [9](#0-8) .
