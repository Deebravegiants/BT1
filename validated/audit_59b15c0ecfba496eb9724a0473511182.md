### Title
Missing storage gap in `IntentsBase`/`IntentGatewayV2` upgradeable contract permits storage collision on upgrade - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2` is a UUPS-style upgradeable proxy contract (deployed behind an `ERC1967Proxy`, upgraded via `upgradeToAndCall` reachable through the `Execute` request kind delivered by the Hyperbridge coprocessor) whose storage-holding base, `IntentsBase`, declares no storage gap (`__gap`) at the end of its state-variable layout, unlike the project's own `SimplexPaymaster.sol`, which does reserve `uint256[48] private __gap;` for exactly this purpose.

### Finding Description
`IntentsBase` declares a fixed sequence of storage variables — `_filled`, `_nonce`, `_params` (`Params` struct), `_orders`, `_instances`, `_partialFills`, `_destinationProtocolFees`, `_paused`, `_relayer` — with no trailing `__gap` reservation. [1](#0-0) 

The project's own decision log confirms the team is fully aware that inserting a field anywhere in this layout (e.g. into the `Params` struct) shifts every mapping declared after it and corrupts already-escrowed order state on the live proxy — which is precisely the storage-collision risk a `__gap` is meant to prevent, and precisely why they instead appended `_relayer` "after `_paused`" as a workaround rather than editing `Params`: [2](#0-1) 

`IntentGatewayV2` composes `IntentsBase` via `IntrinsicIntents`/`ExtrinsicIntents` and is deployed and upgraded as a UUPS proxy (`ERC1967Proxy`, `initialize`/`reinitializer`, `_disableInitializers()` in the constructor): [3](#0-2) 

Upgrades are triggered by a cross-chain governance/relayer message: `onAccept` decodes an `Execute` request body and delegatecalls it, which reaches `ExtrinsicIntents.upgradeToAndCall`, changing the ERC-1967 implementation slot while preserving all existing storage slots of the proxy: [4](#0-3) 

Because there is no `__gap` reserved at the end of `IntentsBase`'s storage layout, any future implementation that needs to insert a new state variable into `IntentsBase` (or any contract in its inheritance chain) — rather than strictly appending after `_relayer` — will shift the storage slots of every mapping declared below the insertion point. The project's own tests hard-code slot numbers (`_filled` at slot 2, `_orders`/commitment slot combined with hard-coded base slot `9`) that a future implementation must exactly preserve, illustrated by: [5](#0-4) 
and [6](#0-5) 

This is a real production risk surface because upgrades on this contract are delivered by a Hyperbridge-relayed message reachable by the authorized relayer/governance path, and any deviation from strict slot-append discipline in a future implementation — e.g. adding a field into the middle of `Params`, or a new base contract with its own storage between `IntentsBase` and `IntentGatewayV2` — silently corrupts `_filled`, `_orders`, `_partialFills`, `_destinationProtocolFees` and `_relayer`, exactly the escrow-critical state the upgrade path is tested to preserve.

By contrast, `SimplexPaymaster.sol` — another upgradeable contract in the same repo — already applies the OpenZeppelin storage-gap convention, showing the team is aware of the pattern but has not applied it consistently to the intents stack: [7](#0-6) 

### Impact Explanation
If a future `IntentGatewayV2`/`IntentsBase` implementation is upgraded without perfectly append-only storage discipline (a mistake that a storage gap exists specifically to make structurally impossible/obvious via OpenZeppelin's upgrade-safety tooling), the escrow mappings (`_orders`, `_filled`, `_partialFills`) and the `_relayer`/`_params` gating variables can be silently overwritten or misread. This can lead to: loss/misattribution of escrowed user funds (`_orders` slot collision), forged "filled" status enabling double payout or unauthorized redemption (`_filled` slot collision), or the `_relayer` gate binding to garbage/attacker-influenced data, permitting unauthorized delivery of governance/relayer-only actions (`onAccept`, `Execute`, `upgradeToAndCall`, `setRelayer`). All of these directly cause theft or freezing of escrowed funds and forged authorization of privileged cross-chain actions.

### Likelihood Explanation
The likelihood of triggering this specific bug class today is low (no upgrade currently violates the slot layout), but the structural precondition — no compiler/tooling-enforced storage gap — makes it a landmine for any future upgrade. Given that `IntentGatewayV2` is under active, frequent development (multiple recent changelog entries about `initialize`/`migrate`/`VERSION` and relayer placement show the storage layout is already being carefully hand-managed slot-by-slot to avoid exactly this collision), the absence of a `__gap` significantly raises the probability that a future PR introduces a collision that automated tools (e.g. OpenZeppelin Upgrades plugin) would otherwise catch pre-merge.

### Recommendation
Add an explicit storage gap at the end of `IntentsBase`'s storage-variable declarations (after `_relayer`), e.g. `uint256[45] private __gap;`, sized to leave headroom for future variables. Additionally, since `Params` is stored inline (not as a mapping), consider gapping the struct itself or documenting immutably that no field may ever be inserted into `Params`. Integrate the OpenZeppelin Foundry/Hardhat storage-layout diff checks (`forge inspect storage-layout` diffing, or `@openzeppelin/upgrades-core`'s `validate` command) into CI so any accidental slot-shifting change is caught automatically rather than relying purely on manual slot-number tests.

### Proof of Concept
1. Deploy `IntentGatewayV2` behind `ERC1967Proxy`, `initialize` it, and escrow an order (`_orders[commitment][token] = amount`) and mark another as `_filled`.
2. Ship `IntentGatewayV2V2`, a hypothetical future implementation that adds a new `bool internal _pendingUpgrade;` variable inside `IntentsBase` immediately before `_orders` (a plausible mistake absent a storage-gap/layout-diff safeguard), instead of strictly appending after `_relayer`.
3. Deliver the upgrade via the same relayer/governance path already tested in `testOnAcceptUpgradeContractRejectsNonHyperbridgeSource`/adjacent upgrade tests (`onAccept` → `Execute` → `upgradeToAndCall`), as shown in: [8](#0-7) 
4. After the upgrade, `_orders[commitment][token]` and `_filled[commitment]` now read from shifted slots, since every mapping declared after the insertion point moved down by one slot — the escrowed amount either reads as zero (fund freeze) or picks up unrelated data from the neighboring slot (fund misattribution/theft), exactly as the team's own slot-preservation assertions (`testFilledMappingStaysAtSlotTwo`, hard-coded slot `9` in `testProtocolFeeWith10Percent`'s neighbor test) would fail to hold under such a change.

# 2026-09-03 — The relayer is a separate storage variable, not a `Params` field

Chosen: `address _relayer` appended after `_paused` in `IntentsBase`, set through its own
`setRelayer` call.

`Params` occupies slots 4 to 8 and `_orders` starts at slot 9. Adding a field to the struct would

contract IntentGatewayV2 is IntrinsicIntents, ExtrinsicIntents, ReentrancyGuardTransient, Initializable {
    using SafeERC20 for IERC20;

    /// @dev Privileged admin for future upgrade-gated actions (e.g. pausing). Immutable, so it must
    /// be identical across chains or the deterministic proxy address diverges. Does not gate
    /// `initialize`; atomic CREATE2 deployment already binds the init data to the canonical address.
    address public immutable _owner;

    /// @dev Sets the EIP-712 domain ("IntentGateway", "2"), records the admin, and locks this raw
    /// implementation against direct initialization.
    /// @param owner The privileged admin address.
    constructor(address owner) EIP712("IntentGateway", "2") {
        if (owner == address(0)) revert InvalidInput();
        _owner = owner;
        _disableInitializers();
    }
