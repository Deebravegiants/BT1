### Title
Unhandled panic (division-by-zero / subtraction underflow) in `swap_token_amount_base_out` causes AMM swap instruction to abort - (File: program/src/math.rs, program/src/processor.rs)

### Summary
The external report describes a DoS caused by an unhandled exception on an edge-case input (an empty collection) that crashes the process. The analogous bug class in this program is a reachable Rust panic (`unwrap()` on `None`) triggered by attacker-controlled instruction data in the `SwapBaseOut` / `SwapBaseOut2` instructions, before any of the safety checks that would normally reject the request.

### Finding Description
`process_swap_base_out` and `process_swap_base_out_v2` compute the reserves and then immediately call `Calculator::swap_token_amount_base_out` with the user-supplied `swap.amount_out`, *before* validating that `amount_out` is less than the pool reserve: [1](#0-0) 

Inside `swap_token_amount_base_out`, the denominator is computed with `checked_sub(amount_out).unwrap()` and is then used as a division denominator via `checked_ceil_div(denominator).unwrap()`: [2](#0-1) 

If an attacker submits `swap.amount_out == total_pc_without_take_pnl` (Coin2PC direction) or `== total_coin_without_take_pnl` (PC2Coin direction), `checked_sub` succeeds and yields `0` (no underflow), but the subsequent `checked_div`/`checked_ceil_div` by that zero denominator returns `None`, and the chained `.unwrap()` panics the program.

Only *after* this computation does the code check whether `amount_out >= total_pc_without_take_pnl` (or the coin equivalent) and return `AmmError::InsufficientFunds`: [3](#0-2) 

Because the panic occurs before that guard is reached, the guard never has a chance to reject the malformed request gracefully — the transaction instead aborts with a runtime panic instead of a controlled program error. The same ordering issue exists in `process_swap_base_out_v2`: [4](#0-3) 

This is directly analogous to the mongo-express bug class: an "edge case" input (an amount that exactly exhausts one side of the pool, akin to an "empty" available balance) hits an unhandled code path (`unwrap()` on `None`) and crashes execution instead of returning a controlled error.

### Impact Explanation
A panic inside a Solana on-chain program instruction aborts the containing transaction. This does not corrupt state or steal funds (there is no unbacked minting or permanent freeze of already-deposited funds), but it does allow an unprivileged, arbitrary caller to reliably trigger a program panic via a single `SwapBaseOut`/`SwapBaseOut2` transaction using attacker-chosen `amount_out`. Because reserves are visible on-chain, an attacker can precisely craft `amount_out` to equal the current reserve, deterministically causing the panic on every attempt while conditions hold, degrading availability of the swap-out instruction path for that pool/slot.

### Likelihood Explanation
The trigger condition depends on `amm_pc_vault.amount` / `amm_coin_vault.amount` at the time of the swap, values that are readable from on-chain accounts and can be raced/timed by an attacker, or exploited immediately after a large withdraw/swap leaves one side of the pool at a specific residual value. Reaching the vulnerable line requires no special privilege — any user can submit a `SwapBaseOut` instruction with attacker-chosen `amount_out`, `user_source`, and `user_destination` accounts, only needing to pass the earlier basic account/mint checks.

### Recommendation
Reorder the logic in `process_swap_base_out` / `process_swap_base_out_v2` so that the `swap.amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl` bound check happens *before* calling `Calculator::swap_token_amount_base_out`, and additionally make `swap_token_amount_base_out` (and `swap_token_amount_base_in`) return a `Result` using `checked_sub`/`checked_div`/`checked_ceil_div` with `.ok_or(AmmError::...)?` instead of `.unwrap()`, so any zero-denominator or underflow condition surfaces as a normal `ProgramError` instead of a panic.

### Proof of Concept
1. Attacker observes an AMM pool's current `total_pc_without_take_pnl` (or `total_coin_without_take_pnl`) reserve value via `amm_pc_vault`/`amm_coin_vault` account data.
2. Attacker submits a `SwapBaseOut` (or `SwapBaseOut2`) instruction with `swap.amount_out` set exactly equal to that reserve value, using their own token accounts as `user_source_info`/`user_destination_info` (with the appropriate mint matching so `swap_direction` resolves).
3. Execution reaches `Calculator::swap_token_amount_base_out` at [5](#0-4)  before the `amount_out >= total_pc_without_take_pnl` check.
4. Inside `swap_token_amount_base_out`, `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` evaluates to `0` (no panic there), but the following `.checked_ceil_div(denominator).unwrap()` call divides by zero, returns `None`, and `.unwrap()` panics, aborting the transaction with a runtime panic rather than a clean `ProgramError`.

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
