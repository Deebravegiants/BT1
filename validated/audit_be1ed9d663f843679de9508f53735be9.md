### Title
Withdraw permanently reverts and locks a user's LP position when either the coin- or pc-side redemption rounds down to zero - (File: `program/src/processor.rs`)

### Summary
`process_withdraw` computes the coin and pc amounts a user receives for burning LP tokens using floor-division (`InvariantPool::exchange_pool_to_token` with `RoundDirection::Floor`), then unconditionally reverts the entire instruction if *either* resulting amount is zero. Because a Solana transaction is atomic, this leaves no path to recover: any LP balance whose corresponding coin or pc share rounds down to zero can never be withdrawn, exactly mirroring the "redeem returns zero" DoS pattern described in the referenced report, and the current implementation has no per-user mitigation equivalent to `previewRedeem()`.

### Finding Description
In `process_withdraw`, the payout for a `withdraw.amount` of LP tokens is derived via: [1](#0-0) 

Both `coin_amount` and `pc_amount` are computed independently with floor rounding from the *same* `withdraw.amount` numerator but against two different denominators (`total_coin_without_take_pnl` and `total_pc_without_take_pnl`, whose ratio to `amm.lp_amount` differs because coin/pc decimals and market prices differ). Immediately after, the code enforces: [2](#0-1) 

If a user's remaining LP balance is small enough that the floor-divided share of *either* token (not necessarily both) truncates to zero, the whole withdrawal fails with `AmmError::InvalidInput`, even though the user may still be entitled to a non-trivial amount of the other token. There is no fallback such as computing a `preview`-style check to only fail when the actual entitlement is negligible on both sides, nor any way to redeem only the non-zero side. The earlier guard at: [3](#0-2) 

only prevents withdrawing more than the user's balance or leaving `amm.lp_amount` at zero — it does nothing to prevent a user's own remaining LP dust from becoming permanently stuck once it crosses this rounding threshold. Because deposits/withdrawals over time and use of `calc_take_pnl` continuously reshuffle `total_pc_without_take_pnl`/`total_coin_without_take_pnl` relative to `amm.lp_amount`, a user's LP balance can end up in a state that always trips this zero-check for one side, exactly the class of bug the referenced report calls out as *not mitigated* by only handling one triggering scenario.

### Impact Explanation
Once a user's LP holdings fall into this zero-rounding band for one of the two tokens, `unstake`/withdraw calls will always revert, permanently freezing that portion of the user's funds in the pool with no recovery path (no partial-token withdrawal, no rescue instruction). This is a permanent freezing of user LP funds, which is a Medium/High severity DoS on withdrawal rather than a purely cosmetic issue, since the user cannot ever redeem their remaining LP position through the normal instruction.

### Likelihood Explanation
This can be triggered unintentionally by any combination of legitimate deposit/withdraw activity that leaves a user with a small residual LP balance relative to `amm.lp_amount`, especially in pools where `coin_decimals`/`pc_decimals` or price ratios are skewed (common for many SPL token pairs on Raydium). No privileged access is required — an ordinary swapper/LP can reach this purely by calling `Withdraw` with attacker-chosen (or naturally arising) small `withdraw.amount` values, and it can also arise from normal wear from other users' pool activity.

### Recommendation
Do not hard-fail the whole instruction when only one of `coin_amount`/`pc_amount` rounds to zero. Options:
1. Allow a zero-amount transfer to be skipped instead of reverting the whole withdrawal — only revert if the total value being withdrawn is negligible on both sides.
2. Alternatively, provide a "final full withdraw" path that lets a user redeem their entire remaining LP balance (bypassing the strict per-token floor-zero check) once their balance falls under the dust threshold, analogous to using `previewRedeem()` to distinguish "no value at all" from "value on one side only."

### Proof of Concept
Given a pool where `total_pc_without_take_pnl` is small relative to `amm.lp_amount` (or `pc_decimals` is low), pick a user LP balance `L` such that:
```
coin_amount = floor(L * total_coin_without_take_pnl / amm.lp_amount) > 0
pc_amount   = floor(L * total_pc_without_take_pnl   / amm.lp_amount) == 0
```
Calling `Withdraw` with `withdraw.amount = L` (satisfying `L < amm.lp_amount` and `L <= user_source_lp.amount`) reaches the checks at `processor.rs:1713-1718`, computes the above `coin_amount`/`pc_amount` pair at `processor.rs:1751-1761`, and then unconditionally reverts at `processor.rs:1775-1777` with `AmmError::InvalidInput`, regardless of `coin_amount` being meaningfully large — permanently blocking that user from ever withdrawing this LP balance through `process_withdraw`.
