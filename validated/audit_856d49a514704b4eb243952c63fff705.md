### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields are read directly from unauthenticated HTTP headers and never included in the signed content. `Registry.process` validates only the body's HMAC and then trusts the header-derived `shop` value to attribute the webhook to a tenant. Because the app's webhook signing secret (`api_secret_key`) is shared across every shop that installs the app, any user who installs the app on their own store can capture a legitimately-signed `(body, hmac)` pair and replay it to the app's webhook endpoint with a forged `shop-domain` header pointing at a victim shop, producing a cross-tenant identity mismatch.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are parsed straight from headers with no cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, and then immediately trusts the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, identical for webhooks originating from any shop that has installed the app — it is not shop-specific. This means the equality the code implicitly relies on:

`hmac_valid(raw_body, shop_A) == hmac_valid(raw_body, shop_B)` for the *same* `raw_body` and app secret, regardless of which shop actually triggered the event, since `shop` is never part of the signed material.

Consequently, an attacker who installs the app on their own store (a fully unprivileged, self-service action) can obtain a valid `(raw_body, x-shopify-hmac-sha256)` pair from any real webhook delivered to their own endpoint, then send that exact body/HMAC to the target app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` will accept the request because it only checks the body bytes, and the handler will process attacker-controlled data as if it were an authentic event from the victim tenant.

This directly matches the report's bug class: "a field acted on but not covered by the HMAC" — here the `shop` field is acted upon (used to route/attribute data cross-tenant) but is excluded from the HMAC-covered `to_signable_string`.

### Impact Explanation
This breaks tenant isolation: the receiving application will invoke its webhook handler believing the event/data originated from `victim-shop.myshopify.com` when it was actually forged using a secret shared across all installs. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up/update per-shop records, trigger fulfillment, sync data, or write to a shop-scoped database row), this enables cross-tenant data injection/corruption without any credentials belonging to the victim — satisfying the "Critical - cross-tenant access" bar, since the gem's only authenticity guarantee (the HMAC) does not bind the identity field the application relies on.

### Likelihood Explanation
Any internet user can register as a Shopify Partner and install the target app on their own development/trial store for free, which is enough to receive real, validly-HMAC-signed webhook bodies from Shopify signed with the target app's `client_secret`. Replaying that body against the app's public webhook endpoint with a modified shop header requires no additional secret — only knowledge of the (documented, predictable) header names the gem parses. This makes the attack straightforward once the fundamental design gap is understood.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body (e.g., signing a canonical concatenation of headers + body) instead of relying solely on `@raw_body`. At minimum, document and enforce that consumers must independently corroborate `shop` (e.g., against a known/registered shop list) before trusting it, since today `HmacValidator.validate` gives no guarantee about header integrity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (self-service, no special privileges needed).
2. Shopify sends a real webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, body `B`, and `x-shopify-hmac-sha256: HMAC(client_secret, B)`.
3. Attacker captures `B` and the HMAC value.
4. Attacker crafts a new HTTP POST to the same webhook endpoint with the identical body `B` and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `@raw_body` against the HMAC — it never inspects the shop header.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the application to process attacker-controlled data under the victim tenant's identity.
