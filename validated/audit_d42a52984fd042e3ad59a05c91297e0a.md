## Title
Griefing via unprivileged `TransferToGasKey` deposits blocks gas-key/account deletion (`GasKeyBalanceTooHigh` DoS) - ([File: runtime/runtime/src/access_keys.rs](), [File: runtime/runtime/src/actions.rs]())

### Summary
The reported bug class is a strict/threshold balance check that an attacker can push over its allowed bound by sending an unwanted deposit to a victim-controlled account/vault, causing a legitimate follow-up action to fail (DoS). Nearcore has a directly analogous pattern: `TransferToGasKey` actions can be sent by *any* predecessor to fund *any* account's gas key, and gas-key/account deletion enforces a strict upper bound (`GasKeyInfo::MAX_BALANCE_TO_BURN`) on the balance that may be burned. An attacker can grief a victim by topping up their gas key(s) above this threshold, permanently blocking `DeleteKey`/`DeleteAccount` on that key/account.

### Finding Description
`action_transfer_to_gas_key` funds an existing gas key by adding `action.deposit` to `GasKeyInfo::balance`, keyed only by `account_id` and `public_key` taken from the action itself, with no check that the predecessor of the receipt equals the account being funded: [1](#0-0) 

Unlike `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, and `DeleteAccount`, which the protocol documentation explicitly requires `predecessor_id == receiver_id` for, `TransferToGasKey` (like plain `Transfer`) is not in that restricted list, meaning any account can include this action in a receipt directed at any other account's `receiver_id`: [2](#0-1) 

Gas-key deletion enforces a strict maximum balance that can be "burned" during deletion — `GasKeyInfo::MAX_BALANCE_TO_BURN = 1 NEAR`. If the balance exceeds this, the whole `DeleteKey` action fails with `GasKeyBalanceTooHigh` and the key is left untouched: [3](#0-2) [4](#0-3) 

The same threshold check is applied when deleting the whole account, summing all gas-key balances on the account: [5](#0-4) 

Because `TransferToGasKey` has no ownership/actor restriction, an attacker can repeatedly send small `TransferToGasKey` deposits (in receipts whose `predecessor_id` is the attacker, `receiver_id` is the victim account) to push the target gas key(s)' cumulative balance above `MAX_BALANCE_TO_BURN`. Once above the threshold, the victim's own `DeleteKey` (for that gas key) or `DeleteAccount` (if it's the only/aggregate blocking factor) will always fail with `GasKeyBalanceTooHigh`, exactly mirroring the reported pattern of an attacker depositing to a target's vault to break a downstream strict balance check.

### Impact Explanation
This blocks a victim from deleting a specific gas key or their entire account, a persistent denial-of-service on account/key lifecycle management. It does not directly cause fund loss (funds remain until the balance is brought back under the threshold, e.g., via `WithdrawFromGasKey`, which appears to be self-executable via `action_withdraw_from_gas_key`), but it can indefinitely block account deletion/key cleanup flows that other logic (e.g., migrations, key rotation, contract self-destruct patterns) may depend on, at negligible attacker cost (as little as slightly over 1 NEAR total, split across multiple griefing transactions, or smaller top-ups if the balance is already close to the cap).

### Likelihood Explanation
Likelihood is high for any victim account with a discoverable gas key public key (public keys are visible on-chain via `AddKey`/RPC), since the funding action requires no special permission on the sender's side — it is reachable directly from a submitted transaction/receipt by any account. The cost to the attacker is low (near the 1 NEAR threshold) and the operation is a single, standard `TransferToGasKey` action.

### Recommendation
Restrict `TransferToGasKey` (and re-evaluate `WithdrawFromGasKey`) to require `predecessor_id == receiver_id`, consistent with other actions that mutate access-key state (`AddKey`, `DeleteKey`), so that only the account itself (or something acting with delegated authority for it) can fund its own gas keys. Alternatively, decouple the deletion-burn cap from being a hard failure — e.g., allow deletion to proceed while capping/truncating the burned amount, or refund/burn any excess above the cap instead of blocking the action outright.

### Proof of Concept
1. Victim account `alice.near` has a gas key with public key `PK` and balance `0`.
2. Attacker `mallory.near` sends a transaction/receipt containing `Action::TransferToGasKey { public_key: PK, deposit: 1 NEAR + 1 yocto }` with `receiver_id = alice.near` (no special permission on `alice.near` is required, per `action_transfer_to_gas_key` in [1](#0-0) , and per the actor-restriction table in [6](#0-5)  which does not include `TransferToGasKey`).
3. `alice.near`'s gas key `PK` now has balance `1 NEAR + 1 yocto`, exceeding `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR).
4. `alice.near` submits `Action::DeleteKey { public_key: PK }`. This fails with `ActionErrorKind::GasKeyBalanceTooHigh`, as demonstrated by the existing unit test `test_delete_gas_key_balance_too_high`: [7](#0-6) 
5. The attacker repeats step 2 for every gas key/account the attacker wishes to block from deletion, at minimal ongoing cost.

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}

Each transaction consists a list of actions to be performed on the `receiver_id` side. Since transactions are first
converted to receipts when they are processed, we will mostly concern ourselves with actions in the context of receipt
processing.
 
For the following actions, `predecessor_id` and `receiver_id` are required to be equal:

- `DeployContract`
- `Stake`
- `AddKey`
- `DeleteKey`
- `DeleteAccount`

NOTE: if the first action in the action list is `CreateAccount`, `predecessor_id` becomes `receiver_id`
for the rest of the actions until `DeleteAccount`. This gives permission by another account to act on the newly created account.
