Confirmed: this is exploitable in both the outbound `send` path (native asset escrow) and the `on_timeout` refund path, since both use the same truncating `convert_to_balance`. I have enough to finalize.

### Title
Cross-chain decimal-scaling division truncates dust that is fully burned/escrowed on the source chain but never credited or refundable on the destination — ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s `on_accept` (and its `on_timeout` refund path) convert an incoming EVM ERC20 `U256` amount to the local Substrate balance via `convert_to_balance`, which performs an integer **floor division** by `10^(erc_decimals - local_decimals)`. Since `register_token`/`update_token` enforce `erc_decimals >= local_decimals` (a scale-down conversion is always required for HyperFungibleToken cross-chain transfers such as BRIDGE, 18 decimals on EVM vs 12 on nexus), any ERC20 amount that is not an exact multiple of the scale factor loses its fractional remainder. On the EVM side, the corresponding `HyperFungibleToken.send()` unconditionally `_burn`s the **full** `params.amount` before dispatching — there is no check that the amount is a multiple of the destination's precision factor, and the message forwards the untruncated amount as-is.

### Finding Description
The outbound flow:
1. A user calls `HyperFungibleToken.send()` on the EVM side with an arbitrary `uint256 amount` [1](#0-0) . The full amount is burned from the caller with no divisibility check, and the same raw amount is placed in the dispatched `Message.amount`.
2. On the Substrate destination, `on_accept` computes the local balance to release/mint by calling `convert_to_balance`, which does `value / 10^(erc_decimals - local_decimals)` [2](#0-1) . This is called from `on_accept` [3](#0-2)  and used to either transfer from the pallet's escrow account (native-asset/BRIDGE model) or mint (non-native model) [4](#0-3) .
3. Because the EVM contract already destroyed the entire (untruncated) amount, and the destination only releases/mints `floor(amount / scale)`, the remainder (up to `scale - 1` ERC20-precision units, e.g. up to 999,999 wei of BRIDGE's 18-decimal representation for the 1e6 BRIDGE scale factor) is permanently unaccounted for. For the native/escrow model (e.g. `BridgeToken`, documented as "the two ends run the escrow model ... the supply of this token is always backed by the pallet's escrow account" [5](#0-4) ), this dust remains stuck in `pallet_account()`'s escrowed balance forever with no code path to reclaim or credit it.
4. The exact same truncating conversion, with the identical missing-remainder problem, is repeated in the `on_timeout` refund path [6](#0-5) , so even a refund after a failed delivery does not return the full originally-burned/escrowed amount.

There is no compensating mechanism anywhere in the pallet (no dust ledger, no "credit remainder to next transfer," no minimum-transfer-amount enforcement rounding to a multiple of the scale factor) to prevent or recover this loss.

### Impact Explanation
Every single-transaction cross-chain transfer via `HyperFungibleToken.send()` (or the corresponding Substrate `send()` in the reverse direction using `convert_to_erc20`, which is safe because it only scales up) from an EVM chain to a Substrate chain where `erc_decimals > local_decimals` (a configuration required by `register_token`'s `ErcDecimalsBelowLocal` check) permanently locks the fractional remainder below the destination's precision. For the native/escrow-backed token (BRIDGE), this is a direct, permanent loss of user funds with no recovery path — the tokens are burned on the EVM side but never released from escrow on the destination. This is a High-severity freezing-of-funds bug reachable by any unprivileged user via a single `send` transaction, matching the token-bridge mint/burn class explicitly in scope.

### Likelihood Explanation
Any user who sends an amount that is not an exact multiple of `10^(erc_decimals - local_decimals)` (e.g., 1e6 for BRIDGE) triggers this truncation — this requires no special conditions, admin action, or race and will happen routinely to ordinary users specifying convenient amounts (e.g., "1.0000005 BRIDGE") since the EVM side accepts any `uint256` with no divisibility validation.

### Recommendation
Either (a) reject `send()`/dispatch amounts on the EVM contract that are not exact multiples of the destination chain's known scale factor (requiring the contract or an off-chain SDK helper to know/enforce `erc_decimals - local_decimals`), or (b) have the Substrate side round the amount to be escrowed/burned on the reverse leg and refunded on timeout consistently, and instead of losing the remainder, either return a "dust" amount to the sender in a follow-up event/refund, or use `Precision::Exact`-style ceiling checks that reject non-exact amounts rather than silently truncating in `convert_to_balance`.

### Proof of Concept
1. Register BRIDGE with `erc_decimals = 18`, `local_decimals = 12` (scale factor `1e6`) as done in `BridgeToken` [7](#0-6) .
2. A nexus user first bridges `1000` BRIDGE (nexus units, 12 decimals) to EVM; the pallet escrows `1000 * 10^12` in `pallet_account()` and the EVM contract mints `1000 * 10^18` BRIDGE.
3. The EVM holder calls `send()` back to nexus with `amount = 1000 * 10^18 + 500000` (i.e., `1000.0000005` BRIDGE) — `HyperFungibleToken.send()` burns the entire amount with no validation.
4. `on_accept` on nexus computes `convert_to_balance(1000*10^18 + 500000, 18, 12) = floor((1000*10^18+500000)/10^6) = 1000*10^12` — exactly `500000` wei (1e-18 BRIDGE precision) short of what was burned. The pallet transfers only `1000 * 10^12` from escrow to the beneficiary; the remaining `500000` wei-equivalent of value that was burned on EVM is never released from `pallet_account()`'s escrow and has no recovery mechanism, permanently reducing the beneficiary's expected balance versus what they destroyed on the source chain.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
