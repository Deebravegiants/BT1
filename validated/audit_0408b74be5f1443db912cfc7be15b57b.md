### Title
Webhook `shop-domain`/`topic`/`webhook-id` headers are trusted for tenant/handler dispatch but excluded from the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely via `Utils::HmacValidator.validate(request)`, but the HMAC only covers the raw request body. The `shop-domain` header, which is passed downstream as the trusted tenant identifier, is never part of the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` decodes the `hmac-sha256` header value [1](#0-0) [2](#0-1) . `Utils::HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., body only) and compares it to the received signature [3](#0-2) . Meanwhile `Request#shop`, `#topic`, and `#webhook_id` are read straight from unauthenticated HTTP headers [4](#0-3) .

`Registry.process` then dispatches the *authenticated-body* payload together with the *unauthenticated* `shop` header directly to the merchant's registered handler as the tenant identifier: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [5](#0-4) .

The identity binding that should hold is: `shop header verified by HMAC == shop trusted by handler for tenant-scoped action`. Here, the left side is never checked — only `hmac(body)` is verified — while the right side (`request.shop`) is taken from a header outside the HMAC's protected scope. This is the same "field acted on but not covered by the HMAC" bug class as the analog report: an attacker can hold body bytes and signature constant while substituting the field that governs the security-relevant decision (there, the aggregator field driving `refresh()`; here, the `shop-domain` header driving tenant dispatch).

### Impact Explanation
Any party who has legitimately received one authentic webhook delivery (e.g., a developer on their own test/dev store, which routinely receives real signed webhooks from Shopify for that same app) possesses a valid `(raw_body, hmac)` pair. Because `shop-domain`, `topic`, and `webhook-id` are excluded from the signable string, that same body+HMAC can be replayed to the app's webhook endpoint with an arbitrary attacker-chosen `shop-domain` header. `HmacValidator.validate` will still return `true` (it only checks body integrity), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to originate from an arbitrary victim shop. Any host application that uses `data.shop` from `WebhookMetadata` to select the session/tenant record to act on (the intended and documented use of this field) can be made to perform an action attributed to, or scoped to, a shop the attacker does not control — a cross-tenant identity-binding break.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint plus possession of a single genuine `(body, hmac)` pair, which is trivially obtainable by any merchant/developer who installs the app on their own store (no leaked secret, no privileged account, no TLS interception needed). This is a realistic, low-effort attack path for an "unprivileged internet user" as scoped by the rules.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, at minimum) in the HMAC-signable material, or independently bind/validate `request.shop` against a value derived from an authenticated channel (e.g., cross-check against the shop associated with the webhook subscription that Shopify's delivery infrastructure maps for that HMAC secret) before passing it to `handler.handle`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be used as a sole tenant-scoping key without additional verification.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; capture one legitimate webhook POST, noting `raw_body` and the `x-shopify-hmac-sha256` value (a valid signature for that exact body under the app's `client_secret`).
2. Replay that exact `raw_body` to the app's webhook endpoint, keeping the `hmac-sha256` header identical, but set `shop-domain` (and optionally `topic`/`webhook-id`) to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `hmac(raw_body)` [6](#0-5) .
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, despite the HMAC never having covered that shop value [7](#0-6) .
