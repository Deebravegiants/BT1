This confirms the vulnerability: the webhook `shop` (`x-shopify-shop-domain`) header is validated as a required header for presence, but is never bound into the HMAC signature. `Utils::HmacValidator.validate` verifies only `to_signable_string`, which returns `@raw_body` — the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are entirely excluded from the signed payload.

### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` from the `x-shopify-shop-domain` HTTP header, but `to_signable_string` only returns the raw body. `Utils::HmacValidator.validate` therefore authenticates the body bytes only, never the shop, topic, webhook-id, or api-version headers.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively [1](#0-0) , while `Request#shop` is read straight from the unauthenticated header `shopify-shop-domain`/`x-shopify-shop-domain` [2](#0-1) . `Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which calls `validate_signature`, comparing the HMAC against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., against the body only [3](#0-2) . Once that check passes, `Registry.process` forwards `request.shop` unmodified to the app's handler as the tenant identifier [4](#0-3) . This breaks the equality `shop authenticated by HMAC == shop delivered to the handler`: the shop field acted upon (tenant attribution) is not covered by the same HMAC that is verified.

### Impact Explanation
A merchant who has installed the app (an "unprivileged" party relative to other tenants of the same app) receives genuine, correctly-HMAC-signed webhooks for their own shop. Because the HMAC only signs the body, that merchant can capture their own valid `(body, hmac)` pair and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a different, victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the shop header, and the app's webhook handler will process/store the payload as if it originated from the victim shop — a cross-tenant data injection/spoofing primitive. Depending on the topic (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`), this can trigger incorrect data deletion, wrong tenant state changes, or false GDPR redaction actions against a shop that never sent that webhook.

### Likelihood Explanation
Likelihood is realistic: any app-installing merchant can capture their own legitimately-signed webhook traffic (it is delivered to their configured endpoint or can be triggered via normal shop actions) and replay it with a modified `shop-domain` header, since HTTP headers are attacker-controlled at the point they hit the app's endpoint and this gem does not bind them into the signature check.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise independently authenticate the `x-shopify-shop-domain` header against a known/expected value bound to the recipient's own credentials before trusting it, rather than deriving the tenant identity solely from an unauthenticated header while validating the HMAC against body bytes alone.

### Proof of Concept
1. App receives a legitimate webhook for `attacker-shop.myshopify.com` with body `B` and valid header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker resends `POST /webhooks` with the same body `B` and same HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` builds successfully; `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` and it matches, since the shop header is never part of the signed string [1](#0-0) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, attributing the event to `victim-shop.myshopify.com` [5](#0-4) .
