### Title
Webhook tenant identity (`shop`) and dispatch key (`topic`) are not bound to the HMAC-verified payload, enabling cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable string as just the raw request body, never mixing in the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` trusts `Utils::HmacValidator.validate(request)` as proof that "this webhook is authentic," but the fields it then acts on (`request.shop`, `request.topic`) are unauthenticated attacker-controlled headers.

### Finding Description
The binding that should hold is: `hmac_valid(request) == true` implies `request.shop` and `request.topic` are the shop/topic that the app's secret actually authenticated. In reality:

- `to_signable_string` only returns `@raw_body` [1](#0-0) .
- `shop`, `topic`, `webhook_id`, `api_version` come straight from HTTP headers with no cryptographic tie to the body [2](#0-1) .
- `HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares against the `hmac-sha256` header [4](#0-3) .
- `Registry.process` accepts the request once that body-only HMAC checks out, then looks up the handler purely by the unauthenticated `topic`, and passes the unauthenticated `shop` header to the handler as the tenant identifier [3](#0-2) .

An unprivileged actor who can obtain one genuine, validly-HMAC'd webhook body (e.g. a merchant receiving webhooks for their own shop, or any observer of a webhook delivery for any topic) can replay that exact body to the app's webhook endpoint while substituting the `shopify-shop-domain` and/or `shopify-topic` headers. Because the HMAC never covered those headers, the signature still verifies, and the app's registered handler will process attacker-chosen `shop`/`topic` values paired with someone else's payload — a violation of the intended per-shop/per-topic authenticity guarantee that `Registry.process`'s single HMAC check is supposed to provide.

### Impact Explanation
This breaks the tenant/topic identity binding without needing `api_secret_key`, an access token, or any privileged credential — only a previously observed, validly-signed webhook body (which any shop owner using the app already receives). Consequences depend on the host app's webhook handlers, but generically:
- Cross-tenant confusion: an app that keys per-shop state off `WebhookMetadata#shop` can be made to apply Shop A's payload to Shop B's tenant record, since `shop` is not authenticated.
- Handler confusion: the `topic` header selects which handler processes the body, so a payload validly signed for one topic can be redelivered under a different registered topic string, causing the wrong handler to parse/act on a payload it never expected.

This matches the report's core lesson: a value that participates in a security-relevant decision (tenant/topic identity) is not covered by the cryptographic check that's meant to guarantee its authenticity, exactly like the `I` ratio being computed from an unprotected rounding path.

### Likelihood Explanation
Any user of the app who legitimately receives webhooks (i.e., any merchant with the app installed) can capture a real `raw_body` + valid `hmac-sha256` for a topic. They don't need Shopify credentials to hit the app's public webhook endpoint with modified `shop-domain`/`topic` headers and the untouched body/HMAC. This is a low-effort replay, not requiring MITM, TLS interception, or secret compromise.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signable string (or otherwise cryptographically bind them to the body before validation) in `lib/shopify_api/webhooks/request.rb`'s `to_signable_string`, so that `HmacValidator.validate` fails if any of these header values are altered relative to what was actually signed by Shopify.

### Proof of Concept
1. App has a real webhook handler registered for `orders/create`, and shop `victim.myshopify.com` has the app installed.
2. Attacker installs the same app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: raw body `B`, headers `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`, `shopify-hmac-sha256: H` (valid HMAC over `B`).
3. Attacker resends the exact same body `B` and HMAC `H` to the app's webhook endpoint but sets `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim.myshopify.com", ...})` is built; `to_signable_string` still returns `B` [1](#0-0) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `H` against `B` [5](#0-4) .
6. The registered `orders/create` handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed(B), ...)` [6](#0-5) , even though this payload was never signed for `victim.myshopify.com`.
