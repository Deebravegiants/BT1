### Title
Unverified pool endpoints in caller-supplied swap routes let route code drain the signer's wallet via the caller's own authorization tree - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The Cryptomator advisory is a tampered-configuration bug: the client trusted endpoints (auth/API URLs) taken from an attacker-modifiable vault config, mixing a legitimate endpoint with a malicious one to exfiltrate tokens. The structural analog in XOXNO Lending is the router hop endpoint: a swap route is caller-supplied "configuration" (the `swap`/`swap_xdr` bytes in `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and direct `execute_strategy`), and the pool addresses embedded in it are invoked with no authenticity check or venue allowlist. A route mixing a legitimate token flow with a malicious pool lets that pool execute `token.transfer(victim, attacker, x)` on *any* token in the signer's wallet; Soroban simulation records the transfer as a child of the signer's `swap_collateral` authorization entry, and if the signer signs the simulated tree, the theft executes on-chain.

### Finding Description
The controller's strategy verbs forward the caller's `StrategySwap` bytes verbatim to the configured router inside `swap_tokens` (contracts/controller/src/strategies/swap.rs:34-38). The router decodes the payload's `assets` registry, where each 5-byte hop instruction names an arbitrary pool address by index (contracts/swap-aggregator/src/program.rs), and `dispatch_hop` calls whatever contract that address points to (contracts/swap-aggregator/src/venues/mod.rs:34-40). There is no allowlist or authenticity check on hop pool addresses anywhere — the router only measures its own `token_in`/`token_out` balance deltas around the call (venues/mod.rs:30-56), which bounds *routed* funds but not code execution under the caller's auth context.

Because `execute_strategy` runs under `sender.require_auth()`, a hop pool invoked below it can call `token::Client::transfer(victim, attacker, amount)` on an unrelated wallet token. In simulation (recording mode) that unauthorized-looking transfer is attached as a `sub_invocation` of the signer's `swap_collateral`/`execute_strategy` auth entry. An attacker who serves a poisoned route (compromised quote path, phishing UI, or tampered `routeXdr` — the exact analog of the tampered `vault.cryptomator`) gets the victim to sign the tree containing the rogue transfer; the host then enforces it.

The harness pins this end to end: `UnlistedPoolRouter` invokes the payload-named pool, `RogueHopPool::swap` transfers the victim's unrelated wallet token to the attacker, and `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows the stolen transfer recorded under Alice's `swap_collateral` entry with `alice → attacker` moving `WALLET_BALANCE` while the swap itself still delivers a fair output (tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:39-71, 195-227). `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` confirms the signed poisoned tree executes the theft (lines 259-268). The threat model documents the same exposure: the router "keeps no allowlist" of the pool/token addresses its payload names, and the loss "is the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (docs/explanation/threat-model.md:154-165).

### Impact Explanation
Theft of user funds beyond the routed amount: any token the victim holds (including assets the protocol never listed) can be transferred to the attacker inside a single signed `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or standalone `execute_strategy` transaction. The swap itself completes "successfully" — measured output is produced, `NoSwapOutput`/`RouterOverspend` pass, position risk gates pass — so there is no on-chain signal of the theft. Loss is bounded only by the victim's wallet balances, matching the High-severity theft-of-funds class.

### Likelihood Explanation
Requires user interaction (victim signs a transaction containing a poisoned auth tree), mirroring the CVE's `UI:R` vector where the attacker tampers the vault config the victim later loads. Preconditions are weak: the attacker deploys one pool contract and gets a malicious `routeXdr` in front of a victim via any channel that supplies routes (the protocol intentionally treats route bytes as untrusted caller input). All entrypoints used are unprivileged — `swap_collateral(caller, account_id, collateral, amount_in, swapped_asset, swap)` needs only the caller's own account. The residual mitigation is entirely client-side (decoding the auth tree before signing), which the codebase itself acknowledges most honest flows never produce a child entry for, so a careful client can detect it — but nothing in-protocol prevents it.

### Recommendation
Enforce pool authenticity on-chain rather than relying on clients to audit auth trees:
- Keep an owner-managed allowlist of venue pool/share addresses in the swap-aggregator and reject any hop whose `pool` index resolves to an unlisted address (`InvalidRouteXdr` or a new `UnknownVenue` error). Alternatively, since the quote server fixes the route shape, require the pool address for each venue to come from on-chain registry config rather than the payload.
- Where an allowlist is impractical, have `dispatch_hop` wrap venue invocations so that hop code cannot perform `require_auth`-gated calls attributable to the `sender` (e.g., verify after each hop that no authorization consumption beyond the router's own invoker auth occurred — the practical form is the allowlist).
- Document for integrators that an honest composed lending swap produces exactly the controller's single `authorize_as_current_contract` input transfer and no signer-level children on token contracts other than `token_in`.

### Proof of Concept
Executed scenario (mirrors `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`):

1. Attacker deploys `RogueHopPool` with plan `(victim = ALICE, wallet_token, to = attacker, amount = ALICE's full balance)` — a contract whose `swap()` does `token::Client::new(&wallet_token).transfer(&alice, &attacker, &amount)` (lines 56-71).
2. Attacker constructs route bytes naming that pool as the hop pool, with `token_in = USDC`, `token_out = ETH`, `min_out` set to a fair quote so the swap appears legitimate (lines 111-125).
3. Victim calls `controller.swap_collateral(alice, account_id, usdc_hub_key, 50_000_000_000, eth_hub_key, route)`. The controller authorizes the exact input transfer and calls `router.execute_strategy(controller, amount_in, swap)` under Alice's `require_auth` root (contracts/controller/src/strategies/swap.rs:34-37).
4. The router dispatches to the rogue pool; `RogueHopPool::swap` calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`. In simulation this is recorded as a `sub_invocation` of Alice's `swap_collateral` auth entry (test lines 206-222).
5. Alice signs the simulated tree (the poisoned child is invisible to a client that doesn't decode it). Enforced mode executes the transfer: `alice` wallet balance → 0, `attacker` → `WALLET_BALANCE`, while the account still receives the fair `ETH` output and passes all risk gates (test lines 224-226, 259-268).

Uncertain/excluded considerations: the codebase documents this exposure in `docs/explanation/threat-model.md` and prescribes client-side auth-tree verification, so a reviewer could treat it as an accepted documented risk rather than a defect; however, no in-scope contract enforces pool authenticity, the test suite proves wallet-scale theft is reachable from an unprivileged caller signature, and the residual loss is unbounded by any protocol gate — so it stands as a valid analog on XOXNO Lending's own code.
