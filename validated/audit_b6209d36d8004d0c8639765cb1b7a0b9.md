### Title
Webhook shop/topic identity spoofing via HMAC bypass on unsigned headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` and `topic` values used for dispatch and tenant identification are read from HTTP headers that are excluded from the signed bytes. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC but then trusts these unsigned headers to route the webhook and to populate `WebhookMetadata`, breaking the binding between "bytes that were HMAC-verified" and "the shop/topic the app acts on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `topic`, `shop`, `webhook_id`, and `api_version` are all read straight from HTTP headers, none of which are part of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` (which signs/verifies only `to_signable_string`, i.e. the raw body), then immediately dispatches on `request.topic` and forwards `request.shop` into `WebhookMetadata` without any check that these header values are consistent with, or bound to, the HMAC-authenticated body: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string`: [4](#0-3) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`HMAC-authenticated bytes (raw_body)` should determine `shop` and `topic` used for dispatch, but instead `shop`/`topic` come from independent, unauthenticated headers (`shopify-shop-domain`, `shopify-topic`). An attacker who possesses any single genuine `(raw_body, hmac)` pair — for example a webhook delivered to their own, unprivileged development/trial shop — can replay that exact body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` and/or `shopify-topic` headers. `Utils::HmacValidator.validate` still returns `true` (the body/HMAC pair is legitimately signed with the app's real webhook secret for *some* delivery), and `Registry.process` will then invoke the handler registered for the attacker-chosen `topic` with the attacker-chosen `shop` in `WebhookMetadata`, impersonating a different tenant or a different event type than what was actually authenticated.

### Impact Explanation
This allows cross-tenant webhook spoofing: an attacker who legitimately receives at least one signed webhook (e.g., for their own low-privilege store) can forge webhook deliveries that the host app believes originate from an arbitrary other shop domain or from an arbitrary registered topic, without ever needing the app's `client_secret`, an access token, or any other credential beyond the ability to receive one genuine webhook. Depending on how the host app's registered `WebhookHandler` implementations use `shop`/`topic` (e.g., `shop/redact`, `customers/data_request`, or app-specific business logic keyed by shop), this can lead to cross-tenant data manipulation or triggering of mandatory-compliance handlers for a shop that never sent the event — a cross-tenant access issue.

### Likelihood Explanation
Exploitation requires the attacker to have received (or otherwise obtained) one genuine `(raw_body, hmac)` webhook pair, which is achievable by any developer who installs the app on their own store and observes a webhook delivery — no privileged credential is required. From there, forging the header values and replaying the body/HMAC to the app's public webhook endpoint is trivial. This makes the likelihood moderate: it's gated by needing one legitimate delivery sample, but that sample is obtainable by any unprivileged user of the app.

### Recommendation
Bind `shop` and `topic` (and any other routing-critical field) into the HMAC-signed payload, or otherwise cryptographically tie the header values to the verified body — for example, by including the `shopify-shop-domain` and `shopify-topic` header values in `to_signable_string`, or by having the host application independently verify that the shop/topic in the headers match a shop/subscription the app expects, rather than trusting them purely because the body's HMAC validated.

### Proof of Concept
1. Install the app on an attacker-controlled Shopify development store and subscribe to any webhook topic (e.g. `orders/create`); capture one legitimate webhook delivery's raw body and its `X-Shopify-Hmac-Sha256` header.
2. Replay a POST to the app's webhook endpoint using the identical raw body and HMAC header, but replace `X-Shopify-Shop-Domain` with a victim shop's domain and/or `X-Shopify-Topic` with a different registered topic (e.g. `shop/redact`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the raw body against the HMAC — both unchanged from the legitimate delivery.
4. The handler registered for the forged topic is invoked with `WebhookMetadata.new(topic: <forged>, shop: <forged>, ...)`, causing the app to act as if the victim shop sent that webhook event.
