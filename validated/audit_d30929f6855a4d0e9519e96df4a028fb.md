### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator` verifies binds nothing but the JSON payload bytes. The `shop`, `topic`, `webhook_id` and `api_version` values are read directly from HTTP headers and are never included in the signed material, yet `Webhooks::Registry.process` forwards them unchecked to the host application's handler as trusted identity metadata.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
which returns `@raw_body` only. `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the HMAC exclusively over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to trust every other field of the request, including `request.shop`, and hands them to the app's webhook handler as `WebhookMetadata`: [4](#0-3) [5](#0-4) 

Because Shopify's real signature only covers the body, any entity that legitimately receives one authentic, HMAC-signed webhook (e.g., an attacker who owns their own installed shop and receives its own webhooks) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers for a different, victim shop. `HmacValidator.validate` will still return `true` since the signed bytes (the body) are unchanged, but `Registry.process` will dispatch `WebhookMetadata` carrying the attacker-chosen `shop` value. Any host application that (as documented/intended) uses `data.shop` to select the tenant session, look up the merchant record, or scope a database write, will act on attacker-supplied content under the wrong tenant's identity — this breaks the intended binding `hmac == HMAC(secret, body ‖ shop ‖ topic ‖ webhook_id)` down to `hmac == HMAC(secret, body)` only.

### Impact Explanation
This allows cross-tenant access: an attacker with only their own valid webhook (no access token, no `client_secret`, no privileged account) can forge the shop identity attached to arbitrary attacker-controlled body content and have it processed by the app as if it originated from a different, targeted merchant. This maps to the "Critical – cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is moderate to high: obtaining one legitimately signed webhook is trivial for anyone who installs the app on any shop (including a free/test shop), since apps commonly subscribe to broad topics (e.g., `app/uninstalled`, `orders/create`) that fire automatically. Replaying the captured body with a different `shop-domain` header requires no cryptographic secret and is fully reachable through this gem's own public `Registry.process` / `Request` API surface, not a misuse of undocumented behavior.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` header values in the signable string used for HMAC verification (or otherwise cryptographically bind them to the signed payload), so that `HmacValidator.validate` fails if any of these fields are altered relative to what Shopify actually signed.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; Shopify delivers a legitimately HMAC-signed webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
2. Attacker replays the same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`), keeping body `B` and `x-shopify-hmac-sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only presence is checked): [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-hashes `B`: [7](#0-6) 
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and processes attacker-controlled body content under the victim shop's identity.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
