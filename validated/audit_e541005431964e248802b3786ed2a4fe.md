### Title
Storage-deposit accounting corruption via contract address reuse (terminate + re-instantiate at same address) causes silent loss of deferred storage-deposit charges - (File: substrate/frame/revive/src/metering/storage.rs)

### Summary
`RawMeter::execute_postponed_deposits` coalesces per-transaction storage-deposit `Charge` entries keyed only by `T::AccountId`, with no notion of contract "generation." When a contract at address `A` is terminated and a *new* contract is instantiated at the same address `A` (achievable via a deterministic `salt` in `instantiate_with_code`) within the same call stack, the new contract's legitimate deferred `Alive` deposit charges get merged into the old contract's already-`Terminated` bucket. The coalesced entry stays `ContractState::Terminated`, which is skipped by both settlement loops that actually invoke `E::charge` (the only place real currency moves), so the new contract's storage-deposit obligation is silently dropped from `total_deposit` and never collected from the origin.

### Finding Description
`self.charges` is a flat `Vec<Charge<T>>` where each entry only carries a `T::AccountId` and a `ContractState` (`Alive{amount}` or `Terminated`), with no identifier distinguishing "incarnations" of a contract at the same address. [1](#0-0) 

In `execute_postponed_deposits`, charges are sorted by contract address with a stable sort, so same-address entries retain their original temporal push order, then adjacent entries for the same address are merged: [2](#0-1) 

For the sequence `Alive(c1)` (X's write) → `Terminated` (X's termination, pushed by `RawMeter::terminate`) → `Alive(c2)` (Y's base-deposit charge after re-instantiating at the same address) → possibly more `Alive`/`Refund` entries from Y's later writes, the merge proceeds as:
- `Alive(c1) + Terminated` → `total_deposit -= c1`, state becomes `Terminated` (correct: X's deferred charge is subsumed by the direct on-chain refund performed in `do_terminate`/`terminate()` at line 450-452, which separately does `total_deposit += Refund(info.total_deposit())`).
- `Terminated + Alive(c2)` → matches the same `(Terminated, Alive{amount})` branch → `total_deposit -= c2`, state **stays** `Terminated`.

This second merge is the bug: `c2` belongs to the *new*, still-alive contract Y, not to the terminated X, yet it is treated identically to "undo a stale charge belonging to the terminated account." Because the merged state remains `Terminated`, the two settlement loops that perform the real balance movement only match `ContractState::Alive { .. }`: [3](#0-2) 
so `E::charge` is never invoked for Y's charges at address `A` — they are neither charged nor refunded to the origin; they simply vanish from settlement while also decrementing the bookkeeping `total_deposit`.

Note: this does **not** manifest as a spurious `Deposit::Refund` transfer to the attacker (as the question's proof idea assumes) — the settlement loops require `ContractState::Alive` to fire `E::charge` at all, so a `Terminated`-tagged merge result triggers no on-chain transfer in either direction. The actual observable effect is that the origin's real balance is never debited for Y's deferred base/storage deposit, and the reported `total_deposit` undercounts the true consumed deposit. `charge_instantiate`'s immediate ED transfer via `T::Currency::transfer` still occurs and is unaffected. [4](#0-3) 

The `debug_assert!(false, "We never emit two terminates for the same contract.")` on the `(Terminated, Terminated)` branch shows the coalescing logic was designed under the assumption that a given address is terminated at most once per transaction and never reused afterward — an assumption that address-reuse via deterministic salts breaks. [5](#0-4) 

### Impact Explanation
The origin's actual on-chain balance is never debited for the re-instantiated contract's legitimate deferred storage-deposit charges (base deposit and any subsequent net storage growth) once its address is coalesced under a prior termination in the same transaction. This is a genuine storage-deposit accounting-conservation violation: `total_deposit` no longer equals the real net cost, and the corresponding `E::charge` call that should debit the origin is skipped entirely. The net effect is that the attacker retains balance corresponding to storage that is left unbacked by deposit — a violation of the "assets must remain fully backed" invariant — rather than a literal spurious-refund payout as hypothesized in the question.

### Likelihood Explanation
Fully reachable by an unprivileged caller: `instantiate_with_code` accepts an attacker-chosen `salt`, deterministically fixing the contract address; terminate-then-reinstantiate-at-the-same-address within one call stack is a normal, permission-less contract-authoring pattern (e.g., a "factory" contract or a single transaction driving both operations via `call`/`instantiate` sub-calls). No signature/origin/proxy checks intervene since this is pure intra-transaction contract execution logic.

### Recommendation
Key the coalescing/matching logic by contract "incarnation" rather than raw `AccountId` alone (e.g., tag `Charge` entries with a generation counter incremented on each instantiate at a given address, or flush/finalize all pending charges for an address at the moment of termination instead of deferring them into the same coalescing bucket that a later re-instantiation can still write into). At minimum, before merging an `Alive` charge into a `Terminated` bucket, verify the charge was recorded *before* the corresponding `Terminated` entry for that exact incarnation, not merely sharing the same address later in the same vector.

### Proof of Concept
Rust integration test in `substrate/frame/revive/src/exec/tests.rs` (or `metering/storage/tests.rs`) style:
1. Instantiate contract X with `salt = S` at deterministic address `A`; have X write storage (charge `c1`).
2. Terminate X (refund `info.total_deposit()`, including `c1`).
3. Within the same call stack, instantiate a new contract Y with the same `salt = S` (or crafted code_hash/salt combo yielding the same address `A`); have Y write storage (charge `c2`).
4. Call `meter.execute_postponed_deposits(&origin, &exec_config)` and assert:
   - `T::Currency::free_balance(origin)` change equals the true net cost (ED for X + ED for Y + `c2`), i.e. **not** silently missing `c2`.
   - Compare against current (buggy) behavior where the balance change is short by `c2`, proving Y's deposit was never collected despite Y being alive with real persisted storage.
