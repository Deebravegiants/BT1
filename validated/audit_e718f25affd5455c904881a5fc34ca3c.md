### Title
Webhook `shop-domain` header is trusted by `Registry.process` without being covered by the request's HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `HmacValidator.validate` authenticates the byte content of the body but never binds the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers to that signature. `Registry.process` nonetheless trusts `request.shop` (taken verbatim from the `x-shopify-shop-domain`/`shopify-shop-domain` header) and hands it straight to the app's handler as the tenant identity for the event, breaking the equality "HMAC-authenticated bytes == bytes acted on as the tenant identifier."

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string` and HMAC-compares it against the `hmac` field: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers, none of which participate in `to_signable_string`: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then forwards `request.shop` to the registered handler as authoritative tenant data, with no secondary binding between the verified body and the claimed shop: [4](#0-3) 

The binding that should hold is: `shop header value == shop that produced the HMAC-signed body`. Because the signature covers only `@raw_body`, this equality is never checked — an attacker who has ever obtained one valid `(raw_body, hmac)` pair for the app's secret (e.g., a webhook payload sent to a publicly reachable endpoint and observed/replayed, or captured via any means not requiring the `api_secret_key` itself) can resend that exact body+hmac while substituting an arbitrary value in `x-shopify-shop-domain`. `Registry.process` will validate the HMAC (it only checks the body) and pass the attacker-chosen `shop` to the handler as if the event originated from that shop.

### Impact Explanation
This lets an unprivileged party who possesses a single legitimate `(body, hmac)` pair impersonate a different shop/tenant when the app processes webhooks, causing the host application to act on data under an attacker-chosen shop identity (cross-tenant confusion) — the HMAC validation gives false assurance that the `shop` field is trustworthy when it never was checked. This matches the Critical "cross-tenant access" category since the tenant-selection field is unauthenticated relative to the credential-derived signature.

### Likelihood Explanation
Exploitation requires the attacker to have captured (not derived) at least one genuine `(body, hmac)` pair without needing the `api_secret_key`, which can happen because webhook receiving endpoints are internet-reachable and the same body could plausibly be replayed with a modified shop header (e.g., a merchant-agnostic payload, or a body an attacker can trigger themselves for their own shop and then replay against another shop's identity in the app). This is a design gap in the library rather than a trivial one-shot forgery, so likelihood is moderate rather than high, but it directly stems from `to_signable_string` not covering the identifying headers.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable string used by `Webhooks::Request#to_signable_string`, or otherwise require the HMAC validation to cross-check that the shop the body was originally signed for matches `request.shop` before invoking the handler. At minimum, document/require callers to compare `request.shop` against an independently trusted app/session store shop before trusting it, and consider incorporating the header content into the signature verification path used by `HmacValidator`.

### Proof of Concept
1. Attacker registers/owns "attacker-shop.myshopify.com" or otherwise triggers the app to receive one legitimate webhook for that shop; captures the raw JSON body and the corresponding `X-Shopify-Hmac-Sha256` value (both are visible to the receiving endpoint operator or can be observed if the transport is not fully controlled by the attacker but the payload is replayable).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the exact same raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`; validation succeeds because it only re-hashes `@raw_body`, per `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`) with `shop == "victim-shop.myshopify.com"`, even though the signed body was never associated with that shop.
