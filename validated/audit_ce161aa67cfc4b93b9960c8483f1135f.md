### Title
Webhook shop-domain header is not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that host applications are expected to trust for tenant identification, but that value is read from the unsigned `shopify-shop-domain` HTTP header. The HMAC signature that this gem verifies (via `Utils::HmacValidator.validate`) only covers the raw request body, not any header, so the `shop` identity used by the calling app to route webhook processing is never bound to the bytes that were actually verified.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

The `hmac` method reads the signature from the `shopify-hmac-sha256` header, while `shop` reads the tenant identity from the separate `shopify-shop-domain` header. Crucially, `to_signable_string`, which is the data that `Utils::HmacValidator.validate` actually authenticates, returns only the raw body: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it via `OpenSSL.secure_compare` against the received signature: [3](#0-2) 

Because `to_signable_string` for `Webhooks::Request` is `@raw_body` only, the signature check proves the *body* bytes are authentic (i.e., produced by an app that shares `api_secret_key` with Shopify — which includes the app itself, and thus any legitimate merchant/shop that installed the app), but it says nothing about the `shopify-shop-domain`, `shopify-topic`, `shopify-api-version`, or `shopify-webhook-id` headers. This is the exact bug-class pattern described in the reference report: an identifier ("shop" identity) is acted upon by the consumer (`request.shop`) without being covered by the cryptographic check that is meant to authenticate the request — an equality of the form `verified_bytes (body) ≠ identity_bytes (shop header)` that the host application implicitly assumes are bound together.

**Binding broken:** `shop_header_value == tenant_that_actually_generated(verified_body)` — this equality is never checked by the gem; only `hmac(verified_body) == received_hmac` is checked.

### Impact Explanation
Any unprivileged internet user who can install the same app on their own (attacker-controlled) shop can legitimately trigger a webhook and thus obtain a validly-signed `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` for their own shop. Because the `shop` field consumed by the host application is not part of the signed bytes, the attacker can replay that same body+HMAC pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Webhooks::Request#shop` will return the attacker-chosen victim domain even though the signature only proves the *body* came from a legitimately-configured installation (the attacker's own). A host app that (as intended by this gem's API) uses `request.shop` to select the tenant/session to act on (e.g., to look up a stored session, mark data as deleted for GDPR webhooks, disconnect a shop, or update per-shop settings) can be made to apply attacker-controlled webhook data to another tenant's record — i.e., cross-tenant access, without needing the victim's access token or the app's `client_secret`.

### Likelihood Explanation
Requires no privileged access: the attacker only needs their own (attacker-owned) shop to install the target app once to capture a genuine signed webhook body/HMAC pair, and network access to POST to the app's public webhook endpoint with a modified header — both are unprivileged-internet-user capabilities. The webhook endpoint is, by design, unauthenticated apart from the HMAC check this gem performs, so this is directly reachable.

### Recommendation
Bind the tenant identity to the verified bytes. Either:
- Include the shop-domain (and ideally topic/api-version) header values in the HMAC-signable string used by `Webhooks::Request`, forcing signature verification to fail if the header is tampered with, or
- Document/enforce that `request.shop` must never be trusted independently of body content, and instead require the shop identity to be re-derived/cross-checked against a value embedded in the (HMAC-covered) body, or against the session that the webhook is dispatched to, rather than the raw header.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic (e.g., `app/uninstalled` or a GDPR webhook) to capture a real request with:
   - Header `X-Shopify-Hmac-Sha256: <valid_hmac>`
   - Header `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - Body `<raw_body>`
2. Confirm locally that `ShopifyAPI::Utils::HmacValidator.validate(ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers))` returns `true` (per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`, only `raw_body` is checked).
3. Replay the identical `raw_body` and `X-Shopify-Hmac-Sha256` header to the same app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` still returns `true` (body/HMAC unchanged), and `request.shop` now returns `"victim.myshopify.com"` — the host app processes the attacker's payload as though it originated from the victim's tenant.
