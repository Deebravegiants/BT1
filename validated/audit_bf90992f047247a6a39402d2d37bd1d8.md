Audit Report

## Title
JWT/Bearer auth token logged in plaintext when the Vault gateway handler receives a JSON-RPC message - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` logs the entire inbound `*jsonrpc.Request[json.RawMessage]` struct — including its `Auth` field, which carries the caller's raw JWT/bearer token — via `reqLggr.Debugw("received message from gateway", "req", req)` before any authorization check runs.

## Finding Description
The handler is the entry point for every JSON-RPC vault message relayed from the gateway: [1](#0-0) . This `Debugw` call passes the entire `req` struct value as a structured field, and `req.Auth` is the same field used to carry the bearer token elsewhere in the codebase — it is read directly during authentication in `jwtBasedAuth.AuthorizeRequest`: [2](#0-1) , and it is explicitly stripped before re-marshalling requests in system-test helpers via `outboundRequestWithoutAuth`: [3](#0-2) .

Other call sites in this same package consistently avoid logging the raw token, logging only a `hasAuth` boolean instead, e.g. in `authorizer.AuthorizeRequest`: [4](#0-3)  and in `GatewayVaultRequestProcessor.authorizeAndStamp`: [5](#0-4) . This confirms the codebase treats `req.Auth` as sensitive and normally redacts it, but the `Debugw("received message from gateway", "req", req)` call bypasses that discipline by logging the whole struct. No `MarshalLogObject`/redaction wrapper was found for `jsonrpc.Request` in this repo (the type is defined in the external `chainlink-common` module and not vendored/indexed here), so absent such a wrapper, a structured logger serializing the struct would include `Auth` in cleartext.

This call executes unconditionally on every message reaching `HandleGatewayMessage`, prior to `AuthorizeRequest`/JWT validation via `h.requestProcessor.ProcessRequest` further down in the same function: [6](#0-5) .

## Impact Explanation
If Debug-level logging is enabled — a supported node operational configuration — every caller's JWT/bearer token used to authenticate Vault secret operations (`SecretsCreate`, `SecretsUpdate`, `SecretsDelete`, `SecretsList`) would be written to node logs in cleartext. Anyone with log read access could extract and replay a valid token to impersonate the token owner for Vault secret operations within the token's validity window. This maps to a credential/secret exfiltration impact class.

## Likelihood Explanation
The vulnerable log line is unconditionally reached on the hot path for every gateway-forwarded vault message, with no additional preconditions besides Debug-level logging being enabled. It is triggered by any client request reaching the handler, before authorization succeeds or fails.

## Recommendation
Remove or redact the `Auth` field before logging in `HandleGatewayMessage` — log only `req.Method`, `req.ID`, and a `hasAuth` boolean, consistent with the pattern already used in `authorizer.go` and `gateway_vault_request_processor.go`.

## Proof of Concept
1. Run a Chainlink node with the Vault gateway handler configured with Debug-level logging.
2. Send a JSON-RPC vault request (e.g., `secrets_list`) through the gateway with a `Bearer <JWT>` populated in the request's `Auth` field.
3. `GatewayHandler.HandleGatewayMessage` executes `reqLggr.Debugw("received message from gateway", "req", req)` at core/capabilities/vault/gw_handler.go:182, before `AuthorizeRequest` runs.
4. Inspect node logs: the `req` field in the "received message from gateway" entry contains the full request struct, including the raw JWT in `Auth`, regardless of whether the token is later accepted or rejected.
