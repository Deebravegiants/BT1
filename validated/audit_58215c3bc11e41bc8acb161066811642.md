Found a concrete, unmitigated analog in `BandwidthManager.sol`: the fee token used to price a bandwidth purchase is read live from the host (`IDispatcher(_host).feeToken()`) at purchase time, but tier prices and treasury withdrawals are addressed only by explicit `Withdraw{token, beneficiary, amount}` governance messages that name a token. If the host's `feeToken` is swapped by `EvmHost.updateHostParams` while `BandwidthManager` still holds a balance of the *old* fee token (collected from purchases denominated in that token), there is no automatic sweep/drain step tied to the fee-token change — governance must remember to issue a separate `Withdraw` for the old token before/after the swap, exactly the "old calculator's fees get stranded unless someone remembers to claim them first" pattern from the report. Unlike `EvmHost.updateHostParamsInternal`, which explicitly reverts with `CannotChangeFeeToken` if the host's own old-token balance is nonzero, `BandwidthManager` has no such interlock, since it is a downstream consumer of `feeToken()` that never registers with the host params-change validation.

### Title
Stranded old fee-token balance in `BandwidthManager` on host fee-token rotation - (File: evm/src/apps/BandwidthManager.sol)

### Summary
`BandwidthManager.purchase()` reads the fee token from the host at call time (`IDispatcher(_host).feeToken()`) and pulls payment in whatever token is currently configured. Governance can independently rotate the host's `feeToken` via `EvmHost.updateHostParams`. Unlike `EvmHost` itself — which explicitly reverts (`CannotChangeFeeToken`) if it still holds a nonzero balance of the old fee token — `BandwidthManager` has no linkage to that host-params-change validation and is never consulted before the swap. Any balance of the pre-rotation fee token still sitting in `BandwidthManager` (collected from purchases) is not automatically swept, and unlike the report's proposed vault fix, there is no built-in "claim on the old calculator/token before switching" step.

### Finding Description
`purchase()` transfers `amount` of `feeToken = IDispatcher(_host).feeToken()` from the buyer into the `BandwidthManager` contract: [1](#0-0) 

Governance withdraws accumulated revenue only through an explicit, token-addressed `Withdraw` message decoded in `onAccept`, using the `Withdrawal{token, beneficiary, amount}` struct — note the comment acknowledging the exact hazard: "`token` is named explicitly so stale fee-token balances after a host-side swap can still be drained": [2](#0-1) 

Compare this to `EvmHost.updateHostParamsInternal`, which hard-blocks a fee-token rotation while the host itself still holds old-token balance: [3](#0-2) 

`BandwidthManager` is never part of that check — the host only inspects its own balance, not any downstream app contracts (like `BandwidthManager`) that also collect fees in `feeToken()`. If governance rotates `feeToken` on the host (satisfying the host's own zero-balance requirement) without separately issuing a `Withdraw` to drain `BandwidthManager`'s old-token balance, that balance becomes orphaned: new purchases will be priced and paid in the new token, and the only recovery path is governance remembering to dispatch a `Withdraw{oldToken, beneficiary, amount}` — the same "must proactively claim from the old calculator/token before/around the swap" pattern flagged in the source report, but with no automated safeguard and no on-chain protection against skipping it.

### Impact Explanation
This is a permanent/indefinite freezing-of-funds risk for the protocol's own accumulated bandwidth revenue (funds are still technically recoverable via a follow-up governance `Withdraw`, but nothing enforces or reminds this, and a rotation performed without draining first strands the funds until someone notices and manually issues the correct `Withdraw{oldToken,...}` action). Given `BandwidthManager` is deployed per-chain and revenue accrues continuously from purchases, a routine fee-token migration (e.g., swapping stablecoins) is a realistic, low-effort operational trigger for stranding real protocol funds.

### Likelihood Explanation
Medium: fee-token rotations are an expected governance operation (the code comment itself anticipates "stale fee-token balances after a host-side swap"), and nothing in `EvmHost`, `BandwidthManager`, or the governance dispatch pipeline forces a drain of `BandwidthManager` before or as part of the rotation. It only requires an operational oversight, not an attacker, though any actor observing the rotation could also front-run/predict it and simply wait for it, since exploitation here is really about the omission rather than active adversarial action.

### Recommendation
Adopt one of the report's mitigations adapted to this contract: (1) have the governance flow that rotates `feeToken` on the host automatically emit/require a paired `Withdraw` sweep of `BandwidthManager`'s (and other fee-token-consuming app contracts') balance in the old token before the rotation is considered complete, or (2) add an explicit balance check analogous to `EvmHost.CannotChangeFeeToken` that governance tooling consults across all registered fee-collecting app contracts before permitting a `feeToken` rotation, or (3) at minimum, document and enforce via tooling/CLI that a `Withdraw{oldToken,...}` is dispatched to every `BandwidthManager` instance immediately prior to any `feeToken` change on the corresponding host.

### Proof of Concept
1. Deploy `BandwidthManager` bound to `EvmHost` with `feeToken = TokenA`.
2. Multiple buyers call `purchase()`, accumulating `TokenA` balance in `BandwidthManager` (per `evm/src/apps/BandwidthManager.sol:170`).
3. Governance rotates the host's fee token via `EvmHost.updateHostParams` to `TokenB` — this succeeds as long as `EvmHost` itself holds zero `TokenA` (per `evm/src/core/EvmHost.sol:617-621`); it does not check `BandwidthManager`'s balance.
4. `BandwidthManager` still holds the `TokenA` balance from step 2. Future `purchase()` calls now pull `TokenB` (`evm/src/apps/BandwidthManager.sol:164`), and nothing forces a `Withdraw{TokenA,...}` sweep.
5. If governance's runbook/tooling for a fee-token rotation does not separately account for `BandwidthManager` (or any other fee-token consuming app deployed against the host), the `TokenA` balance remains stranded until manually rediscovered and withdrawn.
