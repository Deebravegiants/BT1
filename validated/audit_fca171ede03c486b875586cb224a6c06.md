### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant identity) is read straight from an unauthenticated HTTP header. `Webhooks::Registry.process` verifies only the body's HMAC and then hands the unauthenticated `shop` value to the host application's handler as the tenant identifier, breaking the binding `shop_authenticated == shop_used_for_tenant_routing`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic protection: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.to_signable_string` against `verifiable_query.hmac`, i.e. only the raw body: [3](#0-2) 

`Registry.process` calls this HMAC check and then forwards `request.shop` (the unauthenticated header value) into `WebhookMetadata`, which becomes the tenant/shop identity the host application acts on: [4](#0-3) 

Because Shopify's HMAC only covers the body, and this gem does nothing additional to bind the `shop` header to that HMAC, an unprivileged party who can obtain any one valid `(raw_body, hmac)` pair — for example by installing the target app on their own development/trial store and capturing a genuine webhook delivery for that store — can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g. a victim merchant's domain). `HmacValidator.validate` will succeed because it only checks the body bytes, and `Registry.process` will pass the attacker-chosen `shop` value straight to the handler as if the event genuinely originated from that shop.

This is a direct instance of the reported bug class applied to this gem: a field (`shop`) that is acted upon (used as the tenant-identity for the webhook payload) is not covered by the same authentication mechanism (`HMAC`) that verifies the payload it's paired with.

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` (as `Registry.process` explicitly documents/passes it) to select the tenant record, session, or shop-scoped data to write/update can be tricked into attributing attacker-controlled webhook data to a different, victim shop — a cross-tenant write/data-confusion primitive. This matches the Critical impact category of cross-tenant access, since one merchant's authenticated webhook traffic can be relabeled as belonging to a different merchant purely by forging an HTTP header.

### Likelihood Explanation
Exploitation only requires: (1) ability to install the target app on any Shopify store the attacker controls (trivial for public apps, or via a free development store), (2) capturing one legitimate raw webhook body + HMAC pair for any subscribed topic, and (3) replaying that exact byte-for-byte body to the app's public webhook endpoint with a spoofed `x-shopify-shop-domain` header. No access to `api_secret_key`, tokens, or the victim's credentials is needed, making this reachable by any unprivileged internet user who can register their own shop with the app.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook-id`) header values as part of the signed/verified material — or, more practically, require the host application to independently look up the expected shop for a given webhook out of a channel it controls, and reject webhooks whose header-provided shop does not correspond to that binding. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop domain so `HmacValidator.validate` protects the shop attribution, not merely the body bytes. Alternatively, `Registry.process` should treat `request.shop` as untrusted and document/enforce that host apps must cross-check the source domain against a durable session/shop mapping before acting on the payload.

### Proof of Concept
1. Register a public/dev instance of the target app on an attacker-controlled store `attacker-shop.myshopify.com` and subscribe to a webhook topic (e.g. `orders/create`).
2. Trigger the event on the attacker's own store; Shopify delivers a POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — a value the attacker can legitimately obtain without knowing `api_secret_key`.
3. Replay the exact same request to the app's webhook endpoint, but change the header:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H          # unchanged, still valid for body B
   x-shopify-shop-domain: victim-shop.myshopify.com   # forged
   body: B                            # unchanged
   ```
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `HmacValidator.validate` returns `true` because it only checks `B` against `H`
   ( [5](#0-4) ).
5. `Registry.process` invokes the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`
   ( [6](#0-5) ), even though the payload actually originated from the attacker's own store.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
