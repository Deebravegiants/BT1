### Title
LT-rich HyperSwap pair pre-seed forces graduation LP to open materially off the curve-close price ([File: packages/contracts/src/Bonding.sol])

### Summary
CVE-2015-8688 lets an unauthenticated remote attacker push a crafted stanza that the victim client accepts as authoritative, silently corrupting state (the roster) it should have validated against the true source. The alt.fun analog is `finalizeGraduation`'s HyperSwap V2 LP-seeding path: an unprivileged attacker can pre-seed the permissionlessly-creatable TOKEN/LT pair with a sufficiently lopsided ratio that `Bonding`'s rebalance-and-deposit logic cannot fully correct it within its swap budget, so the protocol's own `finalizeGraduation` call — which trusts the pair's reserves as a legitimate price signal to rebalance against — mints the locked LP at a price materially different from the curve's closing price.

### Finding Description
Graduation seeds a HyperSwap V2 TOKEN/LT pair via `Bonding._seedUniswapV2Direct` / `_seedRebalancing` / `_pairRebalance`, which is documented in detail in `packages/contracts/AGENTS.md` and implemented starting at [1](#0-0) . Because `factory.createPair` and `pair.mint` are permissionless, an attacker can front-run phase 1→phase 2 of graduation by creating the pair and minting dust LP to themselves at an arbitrary reserve ratio ("Regime 3 — mint pre-seed", per the AGENTS.md walkthrough).

The defense computes a no-fee-model swap size to rebalance the pool back toward the curve-close ratio (`_noFeeSwapInput` / `_pairRebalance`), but caps that swap at a fixed per-side budget (~99% of `tokensForLP` per the test). When the pre-seed ratio is extreme enough (e.g. LT reserve ≫ token reserve), the optimal corrective swap exceeds this budget, and the capped swap cannot fully rebalance the pool before `router.addLiquidity` deposits the remaining inventory. This is proven directly by the project's own regression test `test_hostilePreSeed_budgetCappedSwap_isNotProfitable`, which sets `reserveToken = tokensForLP/100` and `reserveLt = ltFromPair*200`, asserts the optimal rebalance swap exceeds the 99% budget, and then asserts the resulting pool price is materially (>1.2x) off the curve-close price: [2](#0-1) 

Because `finalizeGraduation` is permissionless (callable by "anyone" per its own natspec) and does not gate on a freshness/ratio check before seeding — it treats the pair's crafted reserves as the correction target for its bounded rebalance — the attacker's forged pool state is partially trusted by the protocol's finalize path in the same way Gajim's roster-push handler trusted an unauthenticated stanza as an authoritative state update.

### Impact Explanation
The validation criteria explicitly accept "an LP seeded away from the curve close price" as concrete impact. `test_hostilePreSeed_budgetCappedSwap_isNotProfitable` demonstrates exactly this: the protocol's own test asserts the LP opens at more than 1.2x the intended curve-close price after a sufficiently extreme LT-rich pre-seed. Every trader who buys into or provides liquidity against the newly-graduated pool inherits a mispriced venue immediately post-graduation — arbitrageurs extract the gap at the expense of the protocol-held LP (locked in `LPLock` with no withdraw path in v1) and any users who trade before the market corrects it, which is a direct value-transfer out of the locked LP position.

### Likelihood Explanation
The attack requires only unprivileged, permissionless actions reachable by any address: calling HyperSwap's `factory.createPair(token, lt)`, transferring TOKEN and LT to the pair, and calling `pair.mint(attacker)` before `finalizeGraduation` executes — exactly the "mint pre-seed" scenario the project's own AGENTS.md documents as "the actual exploit." The only cost is funding the extreme reserve ratio (in the reproducing test, LT reserve = 200× `ltFromPair`), which is capital the attacker recovers minus fees since the LT side above the swap budget is later swept to the protocol owner rather than lost outright — the residual risk being borne by the mispriced LP itself, not solely the attacker.

### Recommendation
Either remove the fixed swap-budget cap in favor of a cap that scales with how far the pre-seed sits from the curve-close ratio (so the corrective swap can always reach the target, subject only to K-invariant limits), or add a maximum-deviation check after the rebalance step that reverts/redirects to a safer disposal path (e.g., extending the direct-mint/skim fallback) when the post-rebalance price would still land outside an acceptable bps band of the cached curve-close ratio, rather than accepting the open-at-any-price outcome the current budget cap produces.

### Proof of Concept
Reference the project's own reproducer, which is a live, passing regression test demonstrating the issue end-to-end: [2](#0-1) 

1. Launch and drive a token into `Lifecycle.Graduating` via `_enterGraduating` (reachable by any trader crossing the curve threshold).
2. Front-run: call `hsFactory.createPair(tokenAddr, address(lt))`, transfer `reserveToken = tokensForLP/100` TOKEN and `reserveLt = ltFromPair*200` LT to the pair, then call `pair.mint(griefer)`.
3. Call the permissionless `bonding.finalizeGraduation(tokenAddr)`.
4. Observe (per the test's assertions) that finalize succeeds but `_poolPriceLtPerToken(hyperPair, tokenAddr)` exceeds `1.2 × (ltFromPair/tokensForLP)` — the LP is locked in `LPLock` at a price materially off the curve's closing price.

    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );
