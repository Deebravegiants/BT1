### Title
Emporium stateless-op forwarding lets attacker spoof `CircomData.originalSender` and steal victim ERC20 allowance via `DepositOnChainUtxosExternalAction.runAction` - (`File: contracts/external-actions/DepositOnChainUtxosExternalAction.sol`)

### Summary
`DepositOnChainUtxosExternalAction.runAction` trusts `circomData.originalSender` as the ERC20 `from` address for `transferERC20TokenFrom`, gated only by `onlyAllowedRecipient` (a `msg.sender` allowlist check), with no binding to the SNARK-verified outer `CircomData`. When `EmporiumUpgradeable` is a registered allowed recipient, its stateless-op path (`op.endpoint.call(op.callData)`) forwards attacker-chosen calldata verbatim to any allowed endpoint without validating its semantic content, letting an attacker embed a completely fabricated `CircomData` naming a victim as `originalSender` and drain the victim's ERC20 allowance.

### Finding Description
The broken equality: `transferERC20TokenFrom`'s `_from` parameter should only ever equal an address that produced/authorized the exact `CircomData` that was checked by `performHinkalChecks` (`circomData.originalSender == sender`, [1](#0-0) ) and proven via `verifyProof`. In this attack, `_from == victim`, but victim never produced, signed, or was a party to `fabricatedCircomData`, and `fabricatedCircomData` was never passed to `performHinkalChecks` or `verifyProof` — only the *outer* `circomData` was.

Path traced:
1. Attacker submits a genuine proof for their own outer `CircomData` to `Hinkal.transact`, which calls `performHinkalChecks`/`verifyProof` only on that outer struct [2](#0-1) .
2. `_externalTransact` dispatches to the registered external action (Emporium) with the outer `circomData` [3](#0-2) .
3. `EmporiumUpgradeable.runAction` decodes `externalActionMetadata` into an `EmporiumStack` and, for CASE 2 "Stateless Interaction" (`stack.signerAddress == address(0)`), calls `op.endpoint.call(op.callData)` with **no signature check at all** (verified in `verifyWallet`, which returns immediately if `signerAddress == address(0)`) and no semantic validation of `op.callData` beyond blocking two specific selectors [4](#0-3) [5](#0-4) .
4. `op.callData` is `abi.encodeCall(DepositOnChainUtxosExternalAction.runAction, (fabricatedCircomData, [0]))`. This reaches `DepositOnChainUtxosExternalAction.runAction`, gated only by `onlyAllowedRecipient`, i.e. `isAllowedRecipient[msg.sender]` where `msg.sender == Emporium` [6](#0-5) .
5. Inside, `userAddress = circomData.originalSender` (attacker-set to victim) is used directly as the `_from` in `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal)`, pulling `A` of token `T` from victim's allowance to `DepositOnChainUtxosExternalAction` into `msg.sender` (Emporium) [7](#0-6) .
6. Back in Emporium, the resulting balance increase on token `T` is credited to `handleOut`, which forwards the tokens to `msg.sender` (Hinkal) and returns a `UTXO` keyed to the *outer* circomData's `stealthAddressStructure` (attacker's) [8](#0-7) .
7. `Hinkal.transact`'s balance/UTXO-amount equality holds because it only checks consistency of Hinkal's own balance delta against the returned `utxoSet`, which is fully satisfied — Hinkal has no visibility into where the sub-call's tokens actually came from.

Root cause: `onlyAllowedRecipient` only authenticates *who* is calling (`msg.sender`), not *whether the `CircomData` argument is the one that was actually proven*. `performHinkalChecks`' `originalSender == sender` rule is enforced solely against the top-level `circomData` passed into `Hinkal.transact`; it has no mechanism to constrain the content of arbitrary calldata Emporium forwards to sub-endpoints in stateless mode. This turns any external action that trusts `circomData.originalSender` as an authorization signal (like `DepositOnChainUtxosExternalAction`) into an allowance-draining primitive once Emporium (or any calldata-forwarding allowed recipient) is registered as its caller.

### Impact Explanation
Critical — direct theft of a victim's ERC20 allowance-backed funds, minted as a shielded UTXO under the attacker's control with no corresponding nullifier spend or authorization from the victim. This is effectively a proof/authorization bypass: the SNARK proof and `originalSender` check are made meaningless for any composed sub-call routed through a stateless Emporium operation. The attack is repeatable for every victim who has approved `DepositOnChainUtxosExternalAction` for any nonzero allowance, up to the full allowance amount, each time consuming one attacker-owned nullifier for the outer transaction (which the attacker can generate arbitrarily many of, e.g. from their own dust deposits).

### Likelihood Explanation
Requires: (1) `DepositOnChainUtxosExternalAction.isAllowedRecipient[Emporium] == true` and (2) Emporium registered in `Hinkal.externalActionMap`, both plausible production composability configurations set by the owner/admin (not attacker-privileged), and (3) any victim having approved `DepositOnChainUtxosExternalAction` for a nonzero allowance (a normal, expected user action for that contract's own intended deposit flow). Attacker cost is a single genuine transact proof for their own funds/nullifier — no special privileges, no victim cooperation, and no reliance on relayer/RPC compromise. Given these preconditions, the exploit is fully feasible and repeatable.

### Recommendation
Do not let `DepositOnChainUtxosExternalAction` (or any external action that trusts `circomData.originalSender` to authorize a `transferFrom`) be reachable via forwarded/arbitrary calldata. Concretely:
- Bind `originalSender`-trusting pulls to the outer, proof-verified `CircomData` only — e.g., have `Hinkal` pass a hash/commitment of the verified `circomData` down through `_externalTransact` and require any nested `runAction` call to match it, or forbid such actions from being callable as Emporium sub-ops entirely.
- In `EmporiumUpgradeable`, for stateless ops, disallow calling any endpoint whose function selector matches `IExternalActionV2.runAction` (or any allowlisted "trusted circomData" pattern) unless the forwarded `CircomData` is provably identical to the one already verified for the current `Hinkal.transact` call.
- Alternatively, remove `originalSender`-based allowance pulls from `DepositOnChainUtxosExternalAction` and require pre-funding (push, not pull) the action contract, consistent with `ExternalActionSwap`'s pattern of only ever moving funds that Hinkal already transferred to it via `_externalTransact`.

### Proof of Concept
Hardhat fork test:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (proxy), `DepositOnChainUtxosExternalAction`, register Emporium in `Hinkal.externalActionMap` and set `isAllowedRecipient[Emporium] = true` in `DepositOnChainUtxosExternalAction`.
2. Victim: `T.approve(DepositOnChainUtxosExternalAction, A)`.
3. Attacker: deposit/derive one genuine UTXO+nullifier of their own in the Hinkal tree; build outer `CircomData` with `externalActionData = {externalAddress: Emporium, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: DepositOnChainUtxosExternalAction, invokeWallet: false, value: 0, callData: abi.encodeCall(runAction, (fabricatedCircomData, [0]))}], ...}}`, with `fabricatedCircomData.originalSender = victim`, `erc20TokenAddresses = [T]`, `externalActionMetadata = abi.encode([[A]])`, `stealthAddressStructure = attacker's`.
4. Generate one real snarkjs proof for the outer `circomData` only (never for `fabricatedCircomData`).
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)`.
6. Assert: victim's `T.balanceOf` decreases by `A`; Hinkal's `T` balance increases by `A`; a UTXO(A, T, attacker's stealth address) commitment is inserted (verify by subsequently spending it in a follow-up `transact` call); confirm this occurs with zero proof input ever referencing `fabricatedCircomData`'s fields.
