### Title
Emporium-Min proof path lets an attacker execute unsigned, unaccounted arbitrary calls from Emporium's identity - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, whose circuit only constrains `message`, `timeStamp`, and `calldataHash` [1](#0-0) . This path never constrains `erc20TokenAddresses`, `amountChanges`, or nullifier ownership, yet `EmporiumUpgradeable.runAction` still executes `stack.ops` with no accounting when the array is empty, and completely skips signature verification when `stack.signerAddress == address(0)` [2](#0-1) . This lets any unprivileged caller force Emporium to make an arbitrary, unsigned, unaccounted external call from Emporium's own address.

### Finding Description
The broken equality: "assets Emporium can move in a tx" must equal "assets accounted in `balancesBefore`/`balancesAfter`", and "an op executed by Emporium" must equal "an op that was actually cryptographically authorized (by proof-bound token/amount data, or by a valid EIP-712 signature)". Both sides diverge here.

Path:
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks` → `CircomDataBuilder.formInputForCircom`, which detects `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` and returns `formInputEmporiumMin`'s 3-element input (`emporiumMessage`, `timeStamp`, `calldataHash`) instead of the full input vector used by `formInputNormal`/`formBasicInput` [1](#0-0) . No `amountChanges`, `erc20TokenAddresses`, nullifiers, or root are bound into this proof's public signals.
2. Because `erc20TokenAddresses.length == 0`, the balance-tracking loop in `Hinkal.transact` (lines 97-147) never executes, so no slippage or balance-diff check applies to whatever Emporium does [3](#0-2) .
3. `Hinkal._externalTransact` calls `EmporiumUpgradeable.runAction`, which computes `balancesBefore`/`balancesAfter` over the same empty `erc20TokenAddresses` array — an empty loop that accounts for nothing [4](#0-3) .
4. `runAction` decodes `EmporiumStack` fully from attacker-controlled `circomData.externalActionData.externalActionMetadata` [5](#0-4) . `verifyWallet` marks `emporiumMessage` used and, when `stack.signerAddress == address(0)`, returns immediately with **no signature check at all** [6](#0-5) . Since `emporiumMessage` is entirely attacker-chosen (and only needs to satisfy `Poseidon(messageSeed) == emporiumMessage`, which the attacker can pick a fresh `messageSeed` for), there is no meaningful gate here.
5. The op loop then executes: with `signerAddress == 0`, every op takes the "Stateless Interaction" branch and does a raw `op.endpoint.call{value: op.value}(op.callData)` directly from Emporium's address, for any attacker-chosen `endpoint`/`callData`/`value` [7](#0-6) . Success is only checked as a raw call success — it doesn't decode ERC20 boolean return values, so a token that "returns false" on failure is still treated as `success == true`.
6. Because `circomData.erc20TokenAddresses` is empty, the post-loop accounting (`balanceChange`, `BalanceChangeShouldBePositive` check, UTXO creation) never inspects the token(s) actually moved by the call in step 5 [8](#0-7) .

Net effect: the attacker gets Emporium (a contract other trusted flows may hold balances in/route funds through, or that could itself be `onlyAllowedRecipient`-listed on other actions) to execute an arbitrary call with none of the normal proof-bound guarantees, none of the signature guarantees, and none of the balance-accounting guarantees that protect the normal (non-Min) path.

Existing guards fail because: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` don't constrain `externalActionMetadata` contents; `verifyProof` only checks the 3 Min public signals, none of which bind `stack.ops`, `stack.signerAddress`, or the token/amount fields; and `verifyWallet`'s `signerAddress == address(0)` branch was designed for the normal path where amount/token/nullifier data is proof-bound — that assumption silently breaks under the Min circuit.

### Impact Explanation
An attacker can make the `EmporiumUpgradeable` contract execute an arbitrary, unauthenticated call (e.g., `ERC20.transfer(attacker, EmporiumBalance)` on any token Emporium happens to hold — from prior partial ops, dust, in-flight bridging/swap funds, or fee remnants) with zero accounting and zero signature check. This is direct theft of protocol/in-flight funds held by Emporium, matching the Critical category ("direct theft of shielded or in-flight user funds") — or at minimum executes calls/moves assets that neither a wallet owner nor a prover ever authorized (High). It's repeatable per unique `emporiumMessage` value, of which there is an unbounded supply.

### Likelihood Explanation
No privileged role is required. The attacker only needs to submit a valid Hinkal `transact` call with a self-generated Min proof (trivial: pick any `messageSeed`, compute `Poseidon(messageSeed)`, and constrain `timeStamp`/`calldataHash` accordingly) and craft `externalActionMetadata` as an ABI-encoded `EmporiumStack` with `signerAddress == address(0)` and `ops` pointing at any endpoint/token. The only precondition for actual fund theft is that Emporium holds some balance at call time (deposits, dust, or funds in transit through multi-step external actions), which is a realistic operating condition for a contract designed to route/hold assets across ops.

### Recommendation
Reject the Emporium-Min proof path whenever `stack.signerAddress == address(0)`, or equivalently disallow unsigned (`signerAddress == 0`) Emporium ops unless the transaction went through `formInputNormal` where `erc20TokenAddresses`/`amountChanges` are proof-bound. At minimum, require `circomData.erc20TokenAddresses.length > 0` (or otherwise proof-constrained token/amount data) whenever `stack.signerAddress == address(0)`, and reject empty-array Min-path invocations of `runAction` for actions whose semantics allow arbitrary calls.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (registered as `HINKAL_EMPORIUM_ACTION_ID`), and a test ERC20 token; fund Emporium directly with `token.transfer(emporiumAddress, 1000e18)` to simulate in-flight/held balance.
2. As an unprivileged attacker EOA, build `circomData` with `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, and `externalActionData.externalActionMetadata` ABI-encoding `EmporiumStack{signerAddress: address(0), ops: [{endpoint: token, invokeWallet: false, value: 0, callData: abi.encodeCall(token.transfer, (attacker, 1000e18))}], maxFee: 0, deadline: 0}`.
3. Generate a valid Min-circuit proof locally for `emporiumMessage = Poseidon(messageSeed)` with attacker-chosen `messageSeed`, matching `timeStamp`/`calldataHash`.
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)` as the attacker.
5. Assert: (a) `token.balanceOf(attacker)` increases by `1000e18`; (b) `token.balanceOf(emporium)` decreases by `1000e18`; (c) no revert occurred despite `erc20TokenAddresses.length == 0` and `stack.signerAddress == address(0)` — i.e., `balancesBefore == balancesAfter == []` (empty) while real token balances moved, proving the accounting equality "assets moved == assets accounted" is broken.

    function formInputEmporiumMin(

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
