### Title
`IntentGatewayV2.placeOrder()` Predispatch Sweep Uses Shared `dispatcher` Contract Balance Instead Of Per-Order Delta, Allowing Theft Of Residual Funds Between Orders - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
In the `predispatch` branch of `placeOrder`, the amount swept from the shared `CallDispatcher` contract is derived from that contract's *total token balance* rather than a value that is cryptographically or programmatically tied to the specific order being processed. Any unprivileged caller can invoke `placeOrder` with a no-op (or minimal) `predispatch.call` and have the sweep logic pull in whatever balance is sitting on the shared `dispatcher`, including residual/dust tokens left behind by a different, unrelated order. This mirrors the C4 `ConvexStakingWrapper._calcRewardIntegral()` bug class: an unguarded, publicly reachable code path (here, `placeOrder`) computes "amount received" from a shared contract's balance rather than a value scoped to the caller, letting one user's action silently absorb value belonging to another.

### Finding Description
`placeOrder` supports an optional `predispatch` phase used to perform arbitrary pre-processing (e.g. unwrapping LP tokens) via the shared, stateless `CallDispatcher` contract (`_params.dispatcher`) before escrowing input tokens: [1](#0-0) 

For each input token, the code reads the *entire current balance* of the shared `dispatcher` contract and sweeps it wholesale into the gateway: [2](#0-1) 

```solidity
uint256 balance = IERC20(token).balanceOf(dispatcher);
if (balance < requiredAmount) revert InvalidInput();
transferCalls[i] = Call({
    to: token,
    value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
});
balancesBefore[i] = IERC20(token).balanceOf(address(this));
```

The only check performed is `balance >= requiredAmount` — there is no verification that the balance sitting on `dispatcher` was actually produced by *this order's* `predispatch.call`. `CallDispatcher.dispatch()` itself is a stateless, permissionless pass-through executor with no accounting of which caller/order "owns" any token sitting on it: [3](#0-2) 

Consequently, if the shared `dispatcher` contract accumulates any residual token balance — e.g., a previous order's `predispatch.call` (a Uniswap swap, LP unwrap, etc.) delivers slightly more output than that order required, or a fee-on-transfer/rounding quirk leaves dust, or a transaction is front-run/interleaved at the mempool level with another `predispatch` order using the same token — a subsequent, unrelated `placeOrder` call can supply a `predispatch.call` that does nothing at all (or something irrelevant) and still pass the `balance >= requiredAmount` check purely off that leftover balance. The full balance is then transferred into escrow for the attacker's own order at line 279, and the "actual received" measurement at lines 292–306 only ever *reduces* the credited amount when it is below the required amount — it never rejects or attributes ownership of the swept balance back to the party that actually produced it: [4](#0-3) 

This is architecturally identical to the reported bug: `_calcRewardIntegral()` computed `d_reward = bal - reward.remaining` off a **shared contract's balance**, letting anyone who could call the unguarded `getReward` on any pool credit themselves with rewards that belonged to other pools. Here, `placeOrder`'s predispatch sweep computes the sweep amount off the **shared `CallDispatcher`'s balance**, letting anyone who calls `placeOrder` with predispatch credit their own order with tokens that were produced by, or intended for, a different order.

### Impact Explanation
An attacker can steal input tokens that were legitimately produced for another user's order (e.g., excess swap output, rounding dust, or funds left mid-flight by a griefed/front-run predispatch order) by submitting their own `placeOrder` call with a trivial or empty `predispatch.call` targeting the same input token, as long as the shared `dispatcher`'s balance happens to cover `requiredAmount`. The stolen value is escrowed as the attacker's own order input and can subsequently be redeemed by a colluding/self-controlled solver via `fillOrder`, resulting in direct theft of funds intended for another party — a concrete loss-of-funds condition matching the High-severity classification of the original finding.

### Likelihood Explanation
Exploitation requires the shared `dispatcher` to hold a non-zero balance of the targeted token at the moment the attacker's `placeOrder` call executes its sweep. This condition can arise naturally (rounding/dust from swaps executed by other orders' `predispatch.call`), or be engineered by an attacker who monitors the mempool for predispatch orders and races/sandwiches them, or who deliberately crafts their own preceding order's `predispatch.call` to leave dust and then completes the theft with a second order in the same or a following transaction. Because `placeOrder` is a fully public, unprivileged entry point and `dispatcher` is a single shared, stateless contract instance for the entire gateway deployment, the precondition (shared balance, no per-order attribution) is a structural property of the design rather than an edge case, making exploitation realistic rather than merely theoretical.

### Recommendation
Do not use the shared `dispatcher`'s absolute balance as the sweep amount. Track the *delta* produced specifically by this order's `predispatch.call` (e.g., snapshot `dispatcher`'s balance immediately before dispatching `order.predispatch.call` and immediately after, and only sweep that delta — never the dispatcher's pre-existing balance), or deploy a fresh, single-use `CallDispatcher` instance (e.g. via `CREATE2`/minimal proxy) per order so no cross-order balance can ever accumulate. Additionally, revert (rather than silently treat as "dust") whenever the swept amount exceeds what this order's own predispatch flow is expected to produce, so unexplained balances cannot be absorbed into any order's escrow.

### Proof of Concept
1. User A submits `placeOrder` with a `predispatch.call` that swaps some asset via the shared `dispatcher`, producing slightly more of token `X` than `order.inputs[i].amount` requires (e.g. due to slippage/rounding), or a similarly-shaped transaction is front-run such that token `X` ends up sitting on `dispatcher` before A's own sweep executes.
2. Attacker B observes (or engineers) that `dispatcher` now holds a balance of token `X` ≥ B's `requiredAmount` for a new order that also uses `predispatch`.
3. B submits `placeOrder` with `predispatch.assets`/`predispatch.call` that does nothing meaningful for token `X` (a no-op or unrelated call) — line 274's check `balance = IERC20(token).balanceOf(dispatcher); if (balance < requiredAmount) revert InvalidInput();` passes purely because of the pre-existing balance.
4. The full `balance` (including the residual belonging to A's flow) is swept into the gateway and credited toward B's escrowed order inputs (lines 279–306).
5. B's order is filled via `fillOrder` (or cancelled and refunded), letting B extract value that was never contributed by B, at the expense of whichever flow originally produced the residual balance on `dispatcher`.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
