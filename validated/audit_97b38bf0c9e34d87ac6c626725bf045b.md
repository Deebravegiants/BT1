## Finding

### Title
Webhook HMAC only authenticates the request body, not the `shop-domain`/`topic`/`webhook-id`/`api-version` headers, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/utils/hmac_validator.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `to_signable_string` to return only the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` are read from unauthenticated HTTP headers that are never covered by the HMAC signature check.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as just the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC solely over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` accepts the request as valid as soon as the body HMAC checks out, then dispatches the handler using the *unauthenticated* `shop`, `topic`, and `webhook_id` values: [4](#0-3) 

Crucially, the HMAC is computed with the app's single `api_secret_key`/`client_secret`, which is shared across every shop/tenant that installs the app — it is not shop-specific. That means the equality the code needs to hold is:

`hmac == HMAC(secret, body)` **and** `shop header == shop that produced that HMAC`

but only the first half is checked. The `shop` (and `topic`/`webhook_id`) half of that binding is never verified. Any party that can obtain one legitimately-signed `(body, hmac)` pair for the app (e.g. a merchant/tenant who installed the app themselves and can observe the raw webhook delivered to their own endpoint, or via Shopify's "send test notification" feature) can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header naming a *different* tenant. `Registry.process` will treat it as a valid, authentic webhook for the victim shop.

### Impact Explanation
This breaks the tenant-identity binding: `Registry.process` hands off `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the app's handler believing `shop` has been authenticated by Shopify, when in fact only the body bytes were authenticated. A tenant of the app (unprivileged relative to other tenants) can spoof webhook events "from" another shop, causing the app to create/update/process data attributed to a shop the attacker does not control — a cross-tenant access/injection primitive, which the rules classify as Critical impact.

### Likelihood Explanation
Any merchant who installs the app receives real, validly-signed webhook deliveries to their own endpoint and can trivially capture the raw body and `hmac-sha256` header (their own webhook traffic). Crafting and sending a second HTTP POST to the app's webhook URL with the captured body/hmac but a forged `shopify-shop-domain` header requires no secret and no elevated privilege — only network access to the app's public webhook endpoint.

### Recommendation
Include the shop domain, topic, webhook id and API version in the HMAC-signable content (or otherwise cryptographically bind them to the verified body/signature) so that `HmacValidator.validate` fails if any of these header-derived fields are altered, rather than checking only the raw body.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop `attacker.myshopify.com` and configures/observes a webhook delivery to their endpoint, capturing the raw JSON body `B` and the `X-Shopify-Hmac-Sha256` header value `H` Shopify computed with the app's shared secret.
2. Attacker sends a POST request directly to the app's webhook processing endpoint with:
   - Body: `B` (unmodified)
   - Header `X-Shopify-Hmac-Sha256: H` (unmodified)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic`: any topic registered by the app (forged/unchanged)
3. `Utils::HmacValidator.validate` in `lib/shopify_api/webhooks/registry.rb` line 190 recomputes HMAC over `B` only, matches `H`, and passes.
4. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"`, `body: JSON.parse(B)`, causing the app to act on forged data attributed to the victim tenant.
