### Title
Attacker-controlled swap route can dereference caller authorization to steal unrelated wallet tokens - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
`swap_collateral` accepts an attacker-supplied route and invokes arbitrary route-selected pool code beneath the caller’s authorization. A malicious pool can request an unrelated token transfer from the caller, causing simulation to add that transfer as a child authorization; if the caller signs the resulting tree, the pool steals wallet assets unrelated to the lending position.

### Finding Description
`swap_collateral` authenticates only the account owner or delegate and forwards the user-controlled `swap` bytes into the configured router. [1](#0-0)  The controller authorizes only the controller’s exact input-token transfer to the router, but it does not constrain which pool contracts the route reaches. [2](#0-1)  The router treats payload addresses as venue pools and dispatches them directly. [3](#0-2)  For a Soroswap-shaped hop, the selected pool is invoked twice and its `swap` implementation runs arbitrary contract code. [4](#0-3) 

This is the on-chain analogue of following a symlink outside the build context: the route payload acts as the indirection, and the protocol dereferences it into attacker-controlled code outside the trusted controller/router boundary. During that call, the pool can invoke `token.transfer(victim, attacker, amount)` on any token held by the victim. Soroban records that authorization requirement as a child of the victim’s `swap_collateral` authorization; enforcing mode executes it if the victim signs the expanded tree. The repository’s regression test demonstrates the resulting unrelated-wallet-token theft. [5](#0-4) 

### Impact Explanation
The attacker can steal unrelated wallet tokens from a user who executes a maliciously constructed route. The stolen funds need not be supplied collateral, borrowed assets, or tokens otherwise intended for the strategy. A successful call can simultaneously pass the router’s measured-output checks and complete a valid collateral swap while silently including an extra victim-signed transfer to the attacker.

This is theft of user funds and can exceed the routed collateral amount because the malicious child call may target any token balance the victim can authorize.

### Likelihood Explanation
Exploitation requires the victim to use an attacker-supplied or tampered route and sign the authorization tree returned by simulation. That is a meaningful phishing/frontend-compromise path because users commonly submit opaque XDR route payloads produced by an off-chain quote service. The attack does not require privileged protocol access, leaked keys, invalid signatures, or a compromised controller.

Likelihood is limited by the need for the victim to sign an authorization tree containing the unexpected token transfer. Wallets or clients that clearly display and reject unexpected child invocations prevent the theft, but nothing in the controller path itself prevents the route from introducing that child invocation.

### Recommendation
Do not allow route payloads to name arbitrary pool contracts. Bind each venue adapter to governance-approved pool deployments or verify pool addresses against the relevant DEX’s authoritative factory/registry before invocation. At minimum, routes reaching `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` should reject unallowlisted pool addresses.

Clients should additionally enforce an authorization-tree policy for these calls: refuse any signed tree containing child invocations beyond the expected controller-authorized input transfer and known venue mechanics.

### Proof of Concept
1. Victim owns a lending account with USDC collateral and also holds an unrelated wallet token `LOOT`.
2. Attacker deploys a fake pool implementing:
   - `get_reserves() -> (i128, i128)`, returning reserves sufficient to produce a positive Soroswap output;
   - `swap(amount_0_out, amount_1_out, to)`, which:
     - calls `LOOT.transfer(victim, attacker, victim_balance)`;
     - transfers enough of the expected output asset to the router to satisfy the router’s measured-output check.
3. Attacker constructs a `StrategyPayload` whose asset registry contains the fake pool, USDC, and the legitimate output token, and whose single instruction is a Soroswap swap using that fake pool.
4. Victim calls:

```text
Controller::swap_collateral(
    caller = victim,
    account_id = victim_account,
    current = USDC hub asset,
    amount = collateral_to_swap,
    new = ETH hub asset,
    swap = malicious_StrategyPayload_XDR,
)
```

5. `swap_collateral` reaches `swap_tokens`, which invokes the configured router with the attacker-controlled payload. [6](#0-5) 
6. The router resolves the payload’s pool address and invokes the fake Soroswap pool. [7](#0-6) 
7. Simulation records a child `LOOT.transfer(victim, attacker, victim_balance)` under the victim’s `swap_collateral` authorization.
8. If the victim signs that tree, enforcing mode executes the child transfer, drains `LOOT`, returns the expected swap output, and leaves the final lending-account checks successful. The test fixture confirms both the recorded child authorization and the wallet-token transfer. [8](#0-7)

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
