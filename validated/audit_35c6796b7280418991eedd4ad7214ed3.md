### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header trusted for tenant routing without HMAC coverage - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers and handed to the app's handler as trusted tenant-identifying metadata.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Registry.process` accepts the request as authentic once `Utils::HmacValidator.validate(request)` succeeds against that raw body [2](#0-1) . However, the `shop` attribute used to build the `WebhookMetadata` passed to the app handler is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the signed body [3](#0-2) . The intended equality is `HMAC(secret, signed_bytes) == HMAC(secret, received_bytes)` where `signed_bytes` should cover every field the handler treats as authoritative (including `shop`); instead the gem enforces `HMAC(secret, raw_body) == received_hmac` while `shop` (and `topic`, `webhook_id`, `api_version`) are parsed independently of that check.

### Impact Explanation
This breaks the identity binding "bytes verified versus bytes parsed": an attacker who can produce (or replay) any single validly-HMAC'd webhook body for topic X from their own shop can swap the `shop-domain` header value to a victim shop before delivery to the app's registered callback endpoint. Because `Registry.process` never re-validates that the `shop` header corresponds to the signed payload, host applications that use `WebhookMetadata#shop` to route the payload to a particular tenant's data store (a documented, expected usage pattern of this gem) can be made to write or process the same webhook body under an arbitrary tenant identity, i.e., cross-tenant data confusion sourced entirely from this gem's un-bound header parsing.

### Likelihood Explanation
Exploitability depends on whether the calling application forwards raw headers to `Request.new` verbatim and trusts `request.shop`/`WebhookMetadata#shop` for tenant routing — which is exactly the documented usage of this class. An attacker needs a delivery endpoint reachable over the internet and a validly-signed webhook body for any shop (trivial for an attacker who runs their own Shopify development store and receives real webhooks their own shop is entitled to) to reuse against another tenant identity, without needing the app's `api_secret_key` or any merchant's access token.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, e.g. mirror them from the signed body/subscription metadata) so `Utils::HmacValidator.validate` fails if any of these header-derived values are altered independently of the signed body.

### Proof of Concept
1. Attacker owns/operates Shop A and receives a legitimately-signed webhook (valid `shopify-hmac-sha256` for the JSON body) from Shopify for topic `orders/create`.
2. Attacker resends this exact HTTP request to the app's public webhook endpoint but rewrites the `shopify-shop-domain` header to Shop B's domain, leaving body and HMAC header untouched.
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC [4](#0-3) .
4. `Registry.process` invokes the handler with `shop: request.shop` set to Shop B [5](#0-4) , causing the host app to process Shop A's order payload under Shop B's tenant context.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
