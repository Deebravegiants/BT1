### Title
Excess native-token payment in `EvmHost.dispatch()` is not refunded to the caller and is trapped in the Host contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `fundRequest()` accept `msg.value` and forward it to the local `UniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)` to buy an exact amount of fee tokens. Uniswap's `swapETHForExactTokens` only spends what is needed and refunds the unused ETH — but it refunds it to `msg.sender` of that call, which is `EvmHost` itself, not the externally-owned account or application that originally called `dispatch()`. Any ETH sent above what the swap actually consumes is silently absorbed into the Host contract's balance instead of being returned to the depositor.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

When `msg.value > 0`, the Host calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. This is the exact analog of the Numoen bug: the caller sends ETH to cover an amount that is only known precisely at execution time (a market-priced swap), and any surplus (`msg.value - amountSpent`) is not routed back to the original transaction sender. Standard `UniswapV2Router02.swapETHForExactTokens` implementations refund unspent ETH via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])` — but here `msg.sender` (from the router's perspective) is `EvmHost`, not the dApp/user that called `dispatch()`. The refunded ETH therefore lands in `EvmHost`'s own balance.

Unlike the Numoen `LendgineRouter`, which at least exposes a public, permissionless `refundETH()` that anyone (including the depositor) can call to sweep the router's ETH balance, `EvmHost` has no such permissionless recovery path for native ETH. The only path that manipulates funds held by the host is the privileged `IHostManager.withdraw(WithdrawParams)` (invoked only via the `hostManager` module from governance messages), which is scoped to sweeping "bridge revenue" — not user-owned refund dust. This means the excess ETH sent by ordinary users of `dispatch()`/`fundRequest()` is neither refunded automatically nor recoverable by them, and can end up permanently commingled with — and eventually withdrawn as — protocol revenue by governance, which never actually earned it.

### Impact Explanation
Every `dispatch()` or `fundRequest()` call that pays in native token can leave residual ETH stuck in `EvmHost`, because slippage/price movement on the local Uniswap V2 pool means the amount of ETH required to buy exactly `fee` amount of feeToken is unknown until execution. Since callers of `dispatch()` are typically other smart contracts (e.g. `HyperApp`-based apps, `IntentGatewayV2`, `HyperbridgeLzEndpoint`) forwarding `msg.value` from end users, this can affect any application built on top of Hyperbridge that lets users pay dispatch fees in native token. Funds are not stolen in a single atomic transaction, but they are permanently lost to the original depositor (no refund mechanism reachable by them) and effectively transferred to protocol-controlled balance, satisfying "permanent freezing/loss of user funds."

### Likelihood Explanation
High likelihood of occurrence: every native-token dispatch is exposed to normal price fluctuation on the configured Uniswap V2 pool between the moment the client estimates `msg.value` off-chain (via `quote()`, explicitly documented as unsafe for on-chain use and sandwich-attack prone) and the moment the swap executes on-chain. The documentation itself instructs users to "send enough native tokens to cover fees," inherently encouraging overpayment/buffering, which guarantees dust ETH accumulates in the Host on virtually every native-token dispatch.

### Recommendation
After the `swapETHForExactTokens` call in both `dispatch(DispatchPost)` and `dispatch(DispatchGet)` (and in `fundRequest`), compute the residual `msg.value - amountsSpent` and refund it directly to `_msgSender()` (or `post.payer`/`get.payer`) within the same transaction, mirroring the wrapper contracts already in this repo (`UniV3UniswapV2Wrapper.swapETHForExactTokens`, `UniV4UniswapV2Wrapper.swapETHForExactTokens`) which correctly refund unused ETH to the original caller. Alternatively, expose a permissionless `refundETH()`-style sweep function on `EvmHost` scoped to non-revenue dust, and document that native-token dispatch requires atomic follow-up handling of leftover value.

### Proof of Concept
1. Attacker/user contract calls `host.dispatch{value: X}(DispatchPost{...fee: F...})` where `X` is a generous ETH buffer to cover fee `F`.
2. `EvmHost.dispatch` executes `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: X}(F, [WETH, feeToken], address(this), block.timestamp)`. [3](#0-2) 
3. The router spends `amountsIn < X` ETH and refunds `X - amountsIn` to `msg.sender`, i.e., to `EvmHost`'s own address (because `EvmHost` is the caller of the router).
4. `EvmHost`'s ETH balance increases by `X - amountsIn` with no code path to return it to the original dispatcher/user; it is not tracked, and only `IHostManager.withdraw` (governance-only) can move funds out of `EvmHost`. [4](#0-3) 
5. Repeated across normal usage, user-supplied ETH buffers accumulate as unrecoverable dust inside the protocol contract.
