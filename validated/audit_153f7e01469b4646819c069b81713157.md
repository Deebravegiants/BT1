I have enough evidence to confirm this finding. The `ShopifyAPI::Webhooks::Request` and `Registry.process` flow signs only the raw body via HMAC while treating the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers as trusted, unauthenticated identity fields that get handed to the app's handler.

### Title
Webhook shop/topic identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verified by `Utils::HmacValidator.validate` binds solely to the JSON body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers with no cryptographic binding, yet `Registry.process` forwards `request.shop`/`request.topic` unchanged to the app's `handler.handle(data: WebhookMetadata.new(...))` as the trusted tenant identity.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header [1](#0-0) . For webhook requests, `to_signable_string` is defined as just the raw body [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that participate in no signature at all [3](#0-2) .

`Registry.process` only checks the HMAC before dispatching, then passes the unauthenticated `request.shop` and `request.topic` straight into the handler payload: `raise ... unless Utils::HmacValidator.validate(request)` followed by `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [4](#0-3) . The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to handler`. Because the signature covers only the body bytes, this equality never actually holds — any `(body, hmac)` pair valid for one shop/topic remains valid after swapping the `shop-domain` or `topic` header to a different value, since `compute_signature` is recomputed over the same `@raw_body` regardless of headers.

### Impact Explanation
Any unprivileged internet user who can obtain one legitimate `(raw_body, hmac)` pair for the app — e.g., by installing the app on a shop they control and capturing their own webhook delivery — can replay that exact body+HMAC to the app's webhook endpoint while substituting the `shop-domain` header (and/or `topic`/`webhook-id`) for a different tenant of the same app. `HmacValidator.validate` still passes because it never inspects the headers, and `WebhookMetadata.shop`/`topic` handed to the app-defined handler will reflect the attacker's forged header rather than the shop that actually produced the signed body. Per the documented usage pattern, `data.shop` is exactly what apps use to route work to a specific merchant's queue/session (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [5](#0-4) , so this allows cross-tenant event injection — an app processes attacker-supplied data as if it originated from a victim shop, or vice versa, without any credential belonging to the victim.

### Likelihood Explanation
Reachable by any internet user with no privileged credentials: they only need one self-obtained, legitimately-signed webhook payload (from their own installed instance of the target app) and the ability to send arbitrary HTTP headers to the app's public webhook endpoint. No `api_secret_key`, access token, or TLS interception is required — only header manipulation, since the gem never validates that the `shop-domain`/`topic` headers correspond to what was actually signed.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed content used by `to_signable_string` (e.g., by concatenating a canonical representation of the header set with the raw body before computing/verifying the HMAC), or otherwise cryptographically bind these header-derived identity fields to the signature so a captured `(body, hmac)` pair cannot be replayed under a different shop/topic.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header value Shopify sent.
2. Attacker sends a forged HTTP POST directly to the app's webhook route with the exact same `raw_body` and `hmac` header, but with `X-Shopify-Shop-Domain` changed to `victim.myshopify.com` (a real merchant using the same app) and/or a different `X-Shopify-Topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) — this matches, since the body is unchanged [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `"victim.myshopify.com"` taken from the forged header [7](#0-6) , causing the app to process attacker-controlled data under the victim's tenant identity.
