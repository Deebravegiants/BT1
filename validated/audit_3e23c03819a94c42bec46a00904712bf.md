### Title
Webhook shop/topic identity spoofing via HMAC that only signs the raw body, not the `shop`-domain header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively over that signable string. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers and are never part of the signed material, yet they are forwarded as authoritative tenant/event identity to the app's webhook handler.

### Finding Description
`Registry.process` treats a request as verified purely based on the body HMAC: [1](#0-0) 

The `Request` object derives `shop`, `topic`, `webhook_id`, and `api_version` directly from HTTP headers with no cryptographic binding: [2](#0-1) 

And the signature check only covers `@raw_body`: [3](#0-2) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [4](#0-3) 

The library's own documentation asserts that `Registry.process` "will verify the request did indeed come from Shopify," and demonstrates handlers trusting `data.shop` as the tenant identity for downstream dispatch (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) [6](#0-5) 

The binding that should hold is:
`shop header used by handler == shop cryptographically bound to the signed payload`

but the actual equality enforced is only:
`hexdigest(HMAC(api_secret_key, raw_body)) == received_hmac`

The `shop` header is completely outside this equality. Because `api_secret_key` is a single static secret shared across every shop that has installed the app (not per-tenant), any store owner can legitimately install the app on their own shop and thereby obtain a genuinely Shopify-signed `(raw_body, hmac)` pair. That pair remains valid under `HmacValidator.validate` no matter what `x-shopify-shop-domain` (or `x-shopify-topic`/`x-shopify-webhook-id`) header value accompanies it, since those headers are never part of `to_signable_string`.

### Impact Explanation
An attacker who has (or can trivially obtain, e.g. via a free/dev installation of the target app on their own store) one valid signed webhook body can replay it to the app's public webhook endpoint while substituting the `shop` header with any other shop domain known to be using the app. `Registry.process` will accept it as authentic and dispatch it to the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. Any host application that follows the documented pattern (using `data.shop` to route/attribute data, e.g. `shop_domain: data.shop`) will process attacker-controlled data under a victim tenant's identity — a cross-tenant data confusion/injection primitive delivered through a channel the gem asserts is "verified" to have come from Shopify.

### Likelihood Explanation
Moderate-to-high: no access token, `client_secret`, or `api_secret_key` is required. The attacker only needs one legitimately signed webhook body (trivially obtainable by installing the target app on a shop they control, a normal unprivileged action) and the ability to POST to the app's public webhook endpoint with a modified header, which is standard HTTP tooling — no interception of another party's traffic required.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signed material, or otherwise cryptographically bind them (e.g., derive `shop` only from a value cross-checked against a session/registration record rather than trusting the header). At minimum, update `to_signable_string` in `lib/shopify_api/webhooks/request.rb` and clearly document that `data.shop`/`data.topic` are unauthenticated and must be independently validated by the host app (e.g., matched against a shop with a known, previously stored session) before being used for tenant attribution.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`; capture a real webhook Shopify sends, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid_hmac_for_body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the exact same body and `x-shopify-hmac-sha256` value to the same app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (and optionally change `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only hashes `raw_body`, which is unchanged.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: {...}, ...)`, causing the host app (following the documented pattern) to process/attribute the payload to `victim.myshopify.com` even though it never sent this data.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
