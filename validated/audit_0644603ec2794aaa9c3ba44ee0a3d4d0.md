### Title
Webhook shop-domain header not covered by HMAC signature allows cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw webhook body for HMAC verification, but exposes `shop`, `topic`, `api_version`, and `webhook_id` from unauthenticated HTTP headers. `Registry.process` trusts `request.shop` after validating only the body's HMAC, so the shop identity delivered to the app's webhook handler is not bound to the signature that authenticated the request.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhooks that method returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled directly from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC over the request (i.e., over `@raw_body`) and then immediately trusts `request.shop` to build the metadata passed to the app's webhook handler: [3](#0-2) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop the handler acts on`

But because `to_signable_string` only returns `@raw_body`, the equality actually enforced is:
`HMAC(raw_body, api_secret_key) == HMAC(raw_body, api_secret_key)`

with `shop` (and `topic`/`api_version`/`webhook_id`) completely excluded from the signed material. Since `api_secret_key` is identical for every shop that installs the app, any tenant who legitimately installs the app receives genuine, validly-HMAC-signed webhook deliveries for their own shop. That tenant can replay the exact same raw body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. The HMAC check still passes because it never inspected the header, and `Registry.process` will hand the (forged) victim shop identity plus the attacker-supplied body to the host app's registered handler.

### Impact Explanation
This breaks the tenant isolation the HMAC check is supposed to provide. Any shop that installs the app (an unprivileged action requiring no special credential) can forge webhook events attributed to any other merchant shop using the app, feeding attacker-controlled body content into the handler under a victim's shop identity. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to update per-shop records, trigger per-shop side effects, or gate access), this is a cross-tenant access primitive.

### Likelihood Explanation
Exploitation only requires operating one's own shop installation of the target app (no leaked secrets, no privileged account, no TLS interception) — a realistic and low-effort action for an "unprivileged internet user" relative to other tenants of the same app.

### Recommendation
Bind `shop` (and ideally `topic`/`api_version`/`webhook_id`) into the signed material verified by `HmacValidator`, or otherwise cryptographically tie the header-derived shop domain to the signature (e.g., include the header value in `to_signable_string`, or require the host application to cross-check `request.shop` against the shop of the currently active session/install before trusting it).

### Proof of Concept
1. Attacker installs the target Shopify app on their own development store `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` computed over the raw JSON body, and header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this request (raw body + valid HMAC header) and replays it directly to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks the raw body's HMAC — this still passes (`lib/shopify_api/webhooks/registry.rb:190`).
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now returns `"victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198`, `lib/shopify_api/webhooks/request.rb:21-23`), causing the host app to process attacker-controlled webhook data as if it originated from the victim shop.
