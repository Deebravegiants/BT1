### Title
Webhook shop/topic identity not bound to HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, using the app's single, shop-agnostic `api_secret_key`. The `shop`, `topic`, and `webhook_id` values that are handed to the app's webhook handler as the tenant identity are read directly from HTTP headers and are **not** included in the HMAC-signed content. Because the same `api_secret_key` is used to validate webhooks for every shop that has installed the app, a party who legitimately receives (or triggers) one valid `(body, hmac)` pair for their own shop can replay that exact body/HMAC to the app's webhook endpoint while substituting a different `shopify-shop-domain` header, and the request will still pass HMAC validation — but will be attributed to a victim shop.

### Finding Description
The HMAC binding equality the gem is supposed to enforce is:
`HMAC(secret, signable_content) == received_hmac` where `signable_content` should uniquely bind the request to `(shop, body)`.

In `lib/shopify_api/webhooks/request.rb`: [1](#0-0) 
`to_signable_string` (the content actually signed and checked) returns only `@raw_body`: [2](#0-1) 
while `shop`, `topic`, and `webhook_id` are pulled straight from attacker-controllable HTTP headers without being part of the signed content: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC using the app-wide `Context.api_secret_key` — the same secret is shared by every shop that has the app installed, not scoped per shop: [4](#0-3) 

`Registry.process` trusts `request.shop` (and `request.topic`) for tenant identity once the HMAC check passes, without any additional binding check between the shop header and the signed body: [5](#0-4) 

Because the signature check only proves "this body was produced with our client secret" and not "this body belongs to this shop," any actor who can obtain one valid `(body, hmac)` pair — e.g., by installing the same public app on their own store and capturing a webhook Shopify sends them — can resend that identical body+HMAC to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header naming a different, victim shop. The HMAC validation in `HmacValidator.validate` succeeds because it never inspects the header values, and `Registry.process` will dispatch the handler with `shop: <victim-shop>`.

### Impact Explanation
This breaks the tenant-identity binding: `shop asserted to the handler == shop that actually produced the signed payload` no longer holds. Any app that uses `data.shop` from `WebhookMetadata` to select which merchant's record to create/update/delete (a very common integration pattern) can be made to apply another shop's webhook event to a victim tenant's data, i.e., cross-tenant data injection/corruption without possessing that victim's credentials. This matches the Critical "cross-tenant access" impact category, since the boundary crossed is between mutually untrusted tenants of the same app, using only capabilities available to any user who can install the app on their own store.

### Likelihood Explanation
Likelihood is high for any app that has webhook handlers keyed off `WebhookMetadata#shop`/`#topic` without independently validating that header against a known/expected shop for that install (which the gem does not require or enforce). Obtaining a valid `(body, hmac)` pair requires nothing more than installing a public app on an attacker-owned development store and observing one webhook delivery — an unprivileged, self-service action.

### Recommendation
Bind the shop (and topic/webhook id, if used for routing/authorization) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop domain to the secret used for verification (e.g., verify against a per-shop secret, or include the shop domain in `to_signable_string`, or require the caller to compare `request.shop` against the shop associated with the session/webhook subscription the app itself registered, not just header content). At minimum, document clearly that `request.shop`/`request.topic` are unauthenticated header values and must not be trusted for tenant scoping without an independent binding check.

### Proof of Concept
1. Attacker registers the target app on their own store `attacker.myshopify.com` and lets it send a real webhook (e.g., `orders/create`). Shopify delivers:
   - Headers: `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: `{"id": 1, ...}`
2. Attacker captures this exact `(body, hmac)` pair.
3. Attacker replays the same body and HMAC value to the app's webhook endpoint, but changes the header:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, raw_body)` — identical to before, so validation passes: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the host app to process attacker-supplied order data as if it belonged to `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
