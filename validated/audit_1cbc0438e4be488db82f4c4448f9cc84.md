### Title
Unbounded dust account creation permanently grows per-user persistent storage and starves keeper TTL coverage - (File: contracts/controller/src/account.rs)

### Summary
The OpenFGA report is a resource-exhaustion DoS: repeated calls allocate resources that are never released, so cumulative state grows until the service degrades. The XOXNO Lending analog is `supply(caller, account_id = 0, ...)`: every call with `account_id == 0` mints a new position-NFT and persists a fresh `AccountMeta`, `SupplyPositions`, NFT `Owner(id)`, and delegates entry set, with no dust floor on the deposit amount and no global account cap. A single unprivileged address can mint arbitrarily many permanent accounts at a cost of 1 stroop each, and there is no unprivileged path to delete a non-empty account, so the per-user persistent keyspace grows monotonically forever — an unreleased resource per call, exactly matching the bug class. A PoC already exists in the repo test suite confirming the mechanic.

### Finding Description
`process_supply` in `contracts/controller/src/positions/supply.rs:40-74` calls `account::load_or_create_account`, which creates a new account whenever `account_id == 0` (`contracts/controller/src/account.rs:95-97`). `create_account` mints a position NFT (`nft_mint_call`) and writes `AccountMeta` to persistent storage (`account.rs:62-71`). The only amount validation is `aggregate_positive_payments` plus `transfer_amount_measured` requiring `AmountMustBePositive` — i.e., `amount > 0`; there is no minimum deposit. `require_third_party_existing_supply` (`supply.rs:78-97`) exempts new accounts entirely because the caller becomes the owner.

Deletion only happens via `cleanup_account_if_empty` (`account.rs:166-170`), which requires both position maps empty; an account holding a 1-unit supply position can never be cleaned up by anyone, and even the owner cannot remove it without withdrawing — and withdrawal of a 1-unit leg leaves the account burned only if fully emptied, which the attacker simply never does.

The harness test `poc_single_actor_spams_unbounded_dust_accounts` (`tests/test-harness/tests/controller/supply.rs:313-344`) demonstrates a single actor minting N distinct persistent accounts with 1-unit deposits, asserting each persists.

The resource that is leaked is persistent ledger footprint and the keeper's renewal coverage. Per `services/keeper/README.md:36-44`, the keeper renews per-user keys (`AccountMeta`, `SupplyPositions`, `BorrowPositions`, `Delegates`, NFT `Owner`) by scanning at most `max_accounts_scan` ids (default 50,000) per TTL tick, wrapping around, so a full cycle takes `ceil(max_account_id / max_accounts_scan)` ticks. Each spammed account permanently enlarges that cycle. The threat model's own STRIDE row `DoS.6` acknowledges that archived storage blocks access until restoration (`docs/explanation/threat-model.md:369`), and `renew_account` (`account.rs:217-226`) is owner-authorized, so renewal is not permissionless at the contract level — the keeper (or each user) must front it.

### Impact Explanation
Temporary freezing of funds / degraded protocol liveness. Once the attacker's cheap accounts inflate `max_account_id` well beyond what the keeper window can cover within the per-user entry TTL, legitimate users' `AccountMeta`/`SupplyPositions`/NFT-owner entries archive before the keeper's rotating window reaches them. Every controller entrypoint that loads an account (`withdraw`, `borrow`, `repay`, `liquidate`, `update_account_threshold`) then fails on the missing entries until someone restores them, freezing those users' collateral and debt positions and blocking their liquidations. The attacker retains the ability to keep inflating the id space faster than the keeper can cover it, at ~1 unit of any listed token per account plus tx fees, and can repeat indefinitely since nothing rate-limits or prices account creation.

### Likelihood Explanation
Medium. The attack is permissionless and mechanically proven by an in-repo test; the only cost is transaction fees plus one token unit per account. The freeze is not instant — it requires the spammed id space to exceed keeper scan coverage for a TTL period — so impact materializes as a slow-burn liveness degradation rather than an immediate halt, and honest keepers/operators can mitigate by raising `max_accounts_scan` or running `prepay_rent`, at growing cost. That places it below Critical/High but above a no-impact griefing note: there is a real, attacker-controlled path to archived user entries and frozen funds.

### Recommendation
Impose a minimum supply amount per account-creation leg (a dust floor denominated per asset, enforced in `process_supply`/`validate_position_entry_gates` when `account_id == 0`), and/or a governance-set global `max_accounts` cap checked in `create_account`. Additionally, allow a permissionless "abandon" path that burns an account whose total scaled value is below the dust threshold (forgiving the residual to the pool), so spammed accounts can be garbage-collected rather than persisted forever.

### Proof of Concept
Conceptual PoC, mirroring `tests/test-harness/tests/controller/supply.rs:313-344`:

```rust
// Attacker loop — each call mints NFT + AccountMeta + SupplyPositions entries
for _ in 0..N {
    let dust = vec![&env, (hub_asset(usdc.clone()), 1i128)]; // 1 unit, accepted
    let id = ctrl.supply(&attacker, &0u64, &1u32, &dust);     // account_id=0 => create
    assert!(id > last_id);                                    // unbounded id growth
}
// NFT counter / max_account_id now = N; entries are never reclaimable because
// cleanup_account_if_empty requires both position maps empty.
// With N >> keeper max_accounts_scan (default 50_000), the keeper's rotating
// window (services/keeper README, lines 38-44) cannot renew every per-user
// entry within one TTL period; victim entries archive, and victim
// withdraw/repay/liquidate calls fail until restore.
```
