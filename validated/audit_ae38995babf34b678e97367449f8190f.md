## Title
Webhook shop/topic identity is not covered by the HMAC signature, enabling cross‑tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — which `ShopifyAPI::Webhooks::Registry.process` uses to route data to the app's handler as the authoritative tenant identity — are taken straight from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. only the body, using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` gates on that body-only HMAC check and then trusts the header-derived `request.shop`/`request.topic` to build the `WebhookMetadata` passed to the app's handler, without any check that this `shop` actually corresponds to the shop the payload was generated for: [4](#0-3) 

The broken identity binding is: `shop authenticated by HMAC (∅, not covered)` ≠ `shop trusted for tenant routing (request.shop header)`. Any unprivileged actor who can obtain one validly-signed webhook body/HMAC pair (trivially available to them if they install the app on their own store and capture their own webhook deliveries — the HMAC is computed with the real `api_secret_key` by Shopify for their own shop) can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop. `HmacValidator.validate` still succeeds because it never inspects the headers, and `Registry.process` hands the attacker-chosen `shop`/`topic` to the app's handler as if it were authentic data from the victim tenant.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: an attacker can inject payloads that the host application's handler will process as belonging to another merchant's shop (e.g., writing "victim shop" records with attacker-controlled body content, or triggering shop-scoped side effects for a shop the attacker does not control). This is a cross-tenant integrity/authenticity issue rooted entirely in this gem's `Webhooks::Request`/`Registry` verification logic, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs at least one legitimately-signed body/HMAC pair, which is trivial to obtain by installing the app on the attacker's own store (a standard, unprivileged action for any Shopify Partner/developer) and capturing the resulting webhook delivery. The webhook endpoint itself is, by design, a public HTTP(S) endpoint reachable from the internet (that is the whole point of webhook delivery), so no additional access is required to replay the captured request with a modified `shop-domain` header.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value verified by HMAC, or otherwise cryptographically/independently confirm that the header-asserted `shop` matches the shop associated with the currently-installed webhook subscription (e.g., cross-check `webhook_id`/`shop` against records created during `Registry.register`) before dispatching to handlers. At minimum, document/require that the `shop` header must not be treated as authenticated data by handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, triggering Shopify to deliver a real webhook: body `B`, headers include `x-shopify-hmac-sha256: H` (computed over `B` with the app's real `api_secret_key`), `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker captures `(B, H)` from their own delivery.
3. Attacker sends a forged HTTP POST directly to the app's public webhook endpoint with body `B`, `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) succeeds because it only checks `B` against `H`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the app's handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body `B`, even though this payload was never issued for that shop.
