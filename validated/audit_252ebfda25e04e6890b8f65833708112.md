### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then trusts these header-derived values, breaking the intended binding `hmac_signed_bytes == bytes_trusted_by_handler`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value, exactly as documented: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` values, and hands them to the app's registered handler: [3](#0-2) 

This is the exact analog of the RToken bug class: the code that performs the authorization check (`Utils::HmacValidator.validate`, which only covers `@raw_body`) uses a different "source of truth" than the code that acts on the result (`Registry.process`, which trusts the header-derived `shop`/`topic`/`webhook_id`). The intended invariant `signed_bytes == bytes_the_handler_relies_on` does not hold — the `shop` field acted upon is not covered by the HMAC at all.

Because Shopify signs webhooks with the app's single `client_secret` shared across every shop that has installed the app, this is not merely a body-tampering issue: an attacker who controls any one shop that has the app installed can capture one of their own genuine, validly-signed webhook deliveries (same body, same secret, so same valid HMAC) and resend it with the `shopify-shop-domain` (and/or `shopify-topic`/`shopify-webhook-id`) header rewritten to name a different, victim shop that also has the app installed. `HmacValidator.validate` still returns `true` because it never inspects those headers, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop, `webhook_id`, and/or `topic`. Any app logic that uses `data.shop` to select the merchant record/tenant to update (a very common and expected usage per this gem's own webhook docs) will act on the wrong tenant, achieving cross-tenant data confusion/write using data attributed to a shop the attacker never owns.

### Impact Explanation
This crosses the tenant boundary: an unprivileged holder of one shop's installation can inject webhook events labeled with another merchant's shop domain into the host app's webhook handler, without possessing that merchant's credentials. This maps to "Critical - cross-tenant access" per the rules, since the gem's own signature verification (`HmacValidator.validate`) is the mechanism apps rely on to trust `WebhookMetadata#shop`, yet that trust is misplaced by design of `to_signable_string`.

### Likelihood Explanation
Requires only that the attacker's own store has the app installed (an ordinary, low-privilege install available to any merchant/attacker who can install the app), the ability to capture/replay one legitimate outbound webhook to their own endpoint, and the ability to resend it with modified headers to the app's webhook endpoint — no access token, `client_secret`, or victim credentials needed.

### Recommendation
Include `shop-domain`, `topic`, `webhook_id`, and `api_version` in the bytes covered by the HMAC (e.g., concatenate/canonicalize the relevant headers with the body before computing the signature in `to_signable_string`), or otherwise cryptographically bind those header values to the signed payload, so `Registry.process`/`WebhookMetadata` cannot be handed shop/topic values that diverge from what was actually signed.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a genuine webhook (e.g., `orders/create`) to the app's endpoint. The request has `x-shopify-hmac-sha256` valid for the raw body, and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the identical body (and therefore identical valid HMAC) to the app's webhook endpoint, but rewrites `x-shopify-shop-domain` to `victim.myshopify.com` (a real merchant that also installed the app).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the raw body) against the HMAC — this still passes.
4. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` with `shop == "victim.myshopify.com"` and dispatches it to the handler, even though `victim.myshopify.com` never sent or authorized this event.
