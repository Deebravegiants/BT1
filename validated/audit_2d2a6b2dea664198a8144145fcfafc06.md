### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` as if they were verified/trusted attributes, but its `to_signable_string` — the value that `HmacValidator.validate` actually authenticates — only covers the raw request body. The identity binding "shop the HMAC authenticates" == "shop the host application acts on" is broken: any attacker who can obtain one validly-signed webhook body (e.g., by installing the app on their own store) can replay that body with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop, and `HmacValidator.validate` will still report success.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` are the two members required by the `Utils::VerifiableQuery` interface used by `HmacValidator.validate`: [1](#0-0) 

Note that `to_signable_string` returns only `@raw_body` — it does not incorporate `topic`, `shop`, `api_version`, or `webhook_id`, all of which are read directly from HTTP headers: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac`: [4](#0-3) 

So `HmacValidator.validate(request)` returning `true` proves only that the *body bytes* were signed by Shopify with the app's `client_secret`. It proves nothing about which shop sent the request, which topic it represents, or which webhook subscription it belongs to — those come from unauthenticated headers that a host application (following this gem's own object model) would naturally treat as verified once `validate` succeeds, since the gem bundles them together into one "verified" `Request` object.

This exactly matches the reported bug class: a field acted on (the shop identity used to route/store data per-tenant) is not covered by the cryptographic binding (HMAC over body only), letting the "authenticated" identity diverge from the "stored/routed" identity.

### Impact Explanation
Any unprivileged internet user can install the target app on their own free/development store (no special privilege required) and receive a legitimately HMAC-signed webhook for that store. They can then replay the identical raw body and HMAC while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header value for a victim shop. Because `HmacValidator.validate` never inspects those headers, the request still validates as authentic. A host application built directly on this gem's documented `Request`/`HmacValidator` API would process the payload as if it genuinely originated from, and pertains to, the victim shop — resulting in cross-tenant data confusion/injection (e.g., writing attacker-controlled order/product/customer data into the victim shop's records, or triggering shop-scoped side effects under the victim's identity). This meets the Critical bar of cross-tenant access.

### Likelihood Explanation
Likelihood is high: obtaining one valid signed webhook only requires installing the app (a normal, unprivileged flow that any developer/merchant can perform), and forging headers on a replayed HTTP request requires no cryptographic material. The vulnerability is a structural gap in the gem's own verification primitive rather than a misuse by the host app.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the authenticated data used for verification, e.g., have `to_signable_string` incorporate `shop`/`topic` alongside the body, or have `HmacValidator`/`Webhooks::Request` cross-check the `shop` header against the shop the caller expects (e.g., require callers to pass an expected shop and assert equality) before exposing `shop` as trusted. At minimum, update documentation to explicitly warn that `shop`/`topic`/`api_version`/`webhook_id` are unauthenticated header values and must not be used as a tenant-identity boundary without an independent check (e.g., comparing against a shop already known to be installed via a stored offline session).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) to their endpoint, capturing the raw body and the `X-Shopify-Hmac-Sha256` header — both are legitimately signed by Shopify using the app's real `client_secret`.
2. Attacker sends a new HTTP request to the app's webhook endpoint with the *same* raw body and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. The host app builds `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and calls `HmacValidator.validate(request)` (or equivalent), per [4](#0-3) ; validation succeeds because it only checks the raw body's HMAC.
4. `request.shop` now returns `"victim-shop.myshopify.com"`, per [5](#0-4) , even though the payload originated from the attacker's own store — the host application processes attacker-controlled data as belonging to the victim tenant.
