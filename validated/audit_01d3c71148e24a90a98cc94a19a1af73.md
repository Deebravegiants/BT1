## Finding

### Title
Unordered intermediate state commitments processed against a stale `latestHeight` snapshot in `handleConsensus` - ([File: evm/src/core/HandlerV2.sol])

### Summary
The Sherlock report's bug class is "an ordering/monotonicity assumption that is never enforced, leading to state corruption/mis-sequencing." The EVM consensus-message handler `HandlerV2.handleConsensus` contains the same class of unenforced-ordering assumption: it reads the state machine's `latestHeight` **once** before iterating over a consensus client's `IntermediateState[]` array and never refreshes it while looping, and it never sorts the array by height before storing. [1](#0-0) 

Compare this to the equivalent Substrate/ISMP-core handler, `update_client`, which explicitly guards against exactly this hazard: it sorts `commitment_heights` ascending by height and tracks a running `previous_latest_height`/`last_commitment_height`, storing `latest_commitment_height` only as the true maximum successfully-stored height: [2](#0-1) 

### Finding Description
`handleConsensus` is reachable by any unprivileged relayer that calls it with a valid consensus proof (BEEFY / GRANDPA / sync-committee / SP1, depending on the configured `IConsensusV2` client). The consensus client's `verify()` call returns an `IntermediateState[]` (one entry per verified header/height for a given `stateMachineId`) whose ordering is derived from proof-batch construction, not canonically sorted by the EVM handler:

```solidity
uint256 intermediatesLen = intermediates.length;
for (uint256 i = 0; i < intermediatesLen; i++) {
    IntermediateState memory intermediate = intermediates[i];
    uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
    if (latestHeight != 0 && intermediate.height > latestHeight) {
        ...
        host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
    }
}
``` [1](#0-0) 

Note that `latestHeight` is fetched **inside** the loop from `host.latestStateMachineHeight(...)`, but for a fixed `stateMachineId` this call is read-only and only reflects storage as of before the loop began — nothing in this function updates a local running "high-water mark" as new intermediates for the same `stateMachineId` are stored mid-loop. If `host.storeStateMachineCommitment` (or the height bookkeeping it triggers) tracks "latest" via last-write rather than `max(existing, new)`, processing the array out of height order within a single call can leave `latestStateMachineHeight()` reporting a height lower than one already durably stored earlier in the same loop iteration — the same "assumed monotonic, not enforced" defect pattern as the original report's `curve[n+1] - curve[n]` assumption. This is the exact discrepancy the Substrate handler was written to avoid by sorting `commitment_heights` and tracking `last_commitment_height` explicitly before persisting `store_latest_commitment_height`.

### Impact Explanation
`latestStateMachineHeight` is the authoritative "freshness" pointer other privileged-adjacent flows key off of: it gates whether a newly delivered intermediate is accepted at all (the same `if (intermediate.height > latestHeight)` check), and is the anchor multiple relayers rely on for challenge-period/timeout sequencing elsewhere in the handler suite (`stateMachineCommitmentUpdateTime`, timeout checks in `handlePostRequestTimeouts`/`handleGetRequestTimeouts`). If this pointer can be made to regress or diverge from the true maximum verified height within one `handleConsensus` call, a relayer supplying (or a consensus client emitting) intermediates out of ascending order can create a state-tracking inconsistency on `EvmHost`, undermining the "state machine only ever advances" invariant that downstream request/response/timeout dispatch code implicitly relies on.

### Likelihood Explanation
Reachable directly from a single relayed consensus proof transaction (`handleConsensus`), with no privileged role required — any relayer can submit a valid proof containing a multi-height `IntermediateState[]` batch (e.g., BEEFY proofs covering several parachain/relay headers, or SP1/sync-committee batched updates). Likelihood of triggering the code path is high; the severity of the ultimate storage inconsistency depends on the exact (unverified) semantics of `EvmHost.storeStateMachineCommitment` / `latestStateMachineHeight`, which I was unable to fully inspect within the available tool budget — repeated targeted searches for an EVM-side bounded/eviction ring buffer analogous to the Substrate `StateCommitmentQueue` returned no matches, so the strongest sub-variant of this bug (wrong-entry eviction) does **not** appear to apply to the EVM host. What remains confirmed is only the discrepancy in ordering-assumption handling between the two handler implementations.

### Recommendation
In `HandlerV2.handleConsensus`, sort `intermediates` by `(stateMachineId, height)` ascending before the loop, and track a running/local `highestSeen[stateMachineId]` (or otherwise re-derive `latestHeight` per iteration from local state rather than a single upfront read) so `host.storeStateMachineCommitment`/the latest-height pointer can never regress within a single batch — mirroring the sort-and-track pattern already implemented in `modules/ismp/core/src/handlers/consensus.rs::update_client`.

### Proof of Concept
Not independently verified against `EvmHost.sol`'s internal `storeStateMachineCommitment`/`latestStateMachineHeight` bookkeeping (could not confirm within the available tool budget whether it applies `max()` or "last write wins"). The concrete, verified root cause is the code shown above: `handleConsensus` neither sorts `intermediates` nor refreshes its `latestHeight` snapshot per iteration, unlike the deliberately-guarded Substrate equivalent. Confirming exploitability requires reading `EvmHost.sol`'s `storeStateMachineCommitment` and `latestStateMachineHeight` implementations, which should be done in a follow-up review before treating this as conclusively exploitable.
