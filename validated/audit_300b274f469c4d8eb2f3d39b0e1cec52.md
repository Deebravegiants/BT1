### Title
Webhook shop-domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
This is the identity-binding analog of the reported "no minimum-return / no bound-value check" bug class: a value that downstream code trusts (the webhook's `shop` tenant identifier) is never covered by the cryptographic check (`HmacValidator`) that is supposed to authenticate the request. `ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, while `#shop` is read straight from an unauthenticated HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` to the app's webhook handler as the tenant key, without ever confirming that header is bound to the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

Specifically:
- `hmac` is parsed from the `x-shopify-hmac-sha256` / `shopify-hmac-sha256` header.
- `shop` is parsed from the `x-shopify-shop-domain` / `shopify-shop-domain` header.
- `to_signable_string` returns only `@raw_body`. [2](#0-1) 

`HmacValidator.validate` (used by `Registry.process`) computes the signature over `verifiable_query.to_signable_string` — i.e. only over the raw body — and compares it against the supplied `hmac`: [3](#0-2) 

`Registry.process` then trusts `request.shop` (the unauthenticated header) as the tenant identifier passed to the app's handler: [4](#0-3) 

Because the shop-domain header is excluded from the signable string, the binding the gem is supposed to enforce — `HMAC-authenticated request == shop the payload is attributed to` — does not hold. Any party that legitimately receives one genuinely-signed webhook for **their own** shop (e.g., an attacker who installs the app on their own store and receives an `orders/create`, `app/uninstalled`, or GDPR webhook) can replay that exact `(raw_body, hmac)` pair to the merchant's public webhook endpoint while substituting an arbitrary victim's domain in `shop-domain`. `HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` dispatches the payload to the handler labeled as coming from the victim shop.

### Impact Explanation
This breaks the equality the whole webhook-authentication mechanism exists to guarantee:
`shop the app processes data for == shop that generated the HMAC-signed payload`.
Before the attack: shop == the domain that actually sent the signed body. After the attack: shop == attacker-chosen value, while the signed body still passes verification. Host applications built on this gem (per the documented handler contract) key their persisted/mutated state off `data.shop`, so this allows cross-tenant data injection/attribution — e.g. forging an `app/uninstalled` or `customers/data_request` event that causes the host app to act (delete records, revoke access, process a data/erasure request, log business events) against a shop the attacker does not own. This satisfies the "cross-tenant access" criterion.

### Likelihood Explanation
The prerequisite is only that the attacker be an unprivileged internet user with (a) their own install of the app (readily obtainable, e.g. via a free trial or dev store — no special privilege inside the target's tenant is required), and (b) network access to the target app's public webhook endpoint (which is inherently unauthenticated apart from this HMAC check). No access to `api_secret_key`, no TLS interception, and no privileged account for the victim shop are needed — this is exactly the gap the rules call out ("a shop authenticated versus the shop stored as a session/tenant key").

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the signable content that `HmacValidator` verifies, or otherwise cryptographically tie the header to the payload before trusting `request.shop` for tenant dispatch. At minimum, `Registry.process` should cross-check that the shop reported in the header matches an expected/known value (e.g. the body's own shop-identifying fields, or a value already associated with the webhook subscription) before handing it to application code as the trusted tenant key.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets it register webhooks normally (as any customer of the app can).
2. Shopify sends a legitimate webhook to the app's public callback URL with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON body.
3. Attacker captures this `(raw_body, hmac)` pair (it is delivered to an endpoint the attacker controls, since it's their own shop).
4. Attacker resends an HTTP POST to the same public webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` [5](#0-4)  — validation succeeds because the body/hmac pair is unchanged.
6. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` [6](#0-5) , causing the host application to process/attribute the webhook event to a shop the attacker never authorized against.

          received_signature = verifiable_query.hmac
