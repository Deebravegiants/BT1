### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) that is handed to the host app's `WebhookHandler` purely from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` checks covers only the raw request body. This breaks the identity binding `authenticated_shop == shop_the_body_was_signed_for`, allowing a party who possesses one valid `(body, hmac)` pair for the app (e.g., from their own legitimately installed shop) to relabel it as belonging to any other shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, none of which are covered by the signature: [2](#0-1) 

`Registry.process` validates only that `hmac` matches the body, then immediately dispatches to the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

`HmacValidator.validate` computes and compares only `verifiable_query.to_signable_string` (i.e., the body) against the secret-keyed HMAC — it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) 

The resulting `WebhookMetadata` (which carries the unauthenticated `shop` value) is exactly what is passed to the app-defined `WebhookHandler#handle`: [5](#0-4) 

Because the secret key (`Context.api_secret_key`) is shared across all shops that install the same app, and only the request body is bound to that secret, `shop` is a pure claim, not something the signature attests to. Equality that should hold — `hmac_signed_for(shop) == claimed(shop)` — never actually gets checked; the gem only checks `hmac_signed_for(body) == claimed(body)`.

### Impact Explanation
Any user who can get one legitimate webhook delivered to the app for their own shop (trivial: install the app on a store they control and trigger any webhook topic) captures a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared secret. They can then replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a victim shop. `Utils::HmacValidator.validate` still returns `true` because the body is unchanged, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any host application logic that trusts `data.shop` to select a session, tenant, or database record (the documented and expected usage pattern for this struct) will act on attacker-supplied `body` content under a victim tenant's identity — a cross-tenant data-integrity/authentication issue matching the "High" bar for scope/identity-check bypass in the target impact list.

### Likelihood Explanation
The prerequisite (owning/controlling one shop that installs the target app) is available to any unprivileged internet user with no access token, `client_secret`, or privileged account required — merely a webhook subscription on their own store, which is standard app-install behavior. Sending a crafted HTTP request with a spoofed `x-shopify-shop-domain` header to the app's own publicly reachable webhook endpoint requires no special access either.

### Recommendation
Bind the identity claims to the signature instead of trusting bare headers:
- Include `shop`, `topic`, and `webhook_id` in the signable payload used by `HmacValidator` (or otherwise cryptographically bind them, e.g., by having the host app independently confirm `shop` against a per-tenant webhook secret/session lookup before trusting `WebhookMetadata#shop`).
- At minimum, document and/or enforce that `WebhookMetadata#shop` must be independently corroborated (e.g., cross-checked against an existing session for that shop) before being used for any tenant-scoped operation, since the current HMAC check gives no such guarantee.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic, capturing the raw POST body `B` and header `x-shopify-hmac-sha256: H` sent by Shopify (both valid since they're genuinely signed with the app's `api_secret_key`).
2. Attacker sends a new POST request directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (spoofed)
   - Header `x-shopify-topic`/`x-shopify-webhook-id` optionally spoofed too
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only recomputes the HMAC over `B`. [6](#0-5) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and processes attacker-controlled data as if it originated from the victim's shop. [7](#0-6)
