This is the key finding: `TokenExchange.exchange_token()` derives the destination host for sending the app's `client_secret` from the JWT's `dest` claim, while only the `aud` claim is bound/verified. `iss` and `dest` are never cross-checked against each other.

### Title
Token Exchange sends `client_secret` to a host derived from an unverified JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`TokenExchange.exchange_token()` extracts the shop host to contact from `jwt_payload.shop` (the `dest` claim) and uses it, unsanitized by `Utils::ShopValidator`, to build the HTTP client that POSTs the app's `client_id`/`client_secret` for a token-exchange grant.

### Finding Description
`ShopifyAPI::Auth::JwtPayload#initialize` only asserts `@aud == Context.api_key` [1](#0-0) . The `dest`/`iss` claims are stored but never validated to be a legitimate `*.myshopify.com`/`*.myshopify.io` domain, nor cross-checked against `iss`. `shop` (used everywhere downstream) is derived purely from `dest`: `@dest.gsub("https://", "")` [2](#0-1) .

`TokenExchange.exchange_token` then does:
```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
body = { client_id: ..., client_secret: ShopifyAPI::Context.api_secret_key, ... }
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
``` [3](#0-2) 

Unlike its sibling flows `RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials`, which explicitly call `Utils::ShopValidator.sanitize!(shop)` before building the session used to route the request carrying the `client_secret` [4](#0-3) [5](#0-4) , `exchange_token` never runs `dest_shop` through `ShopValidator`. The `HttpClient` builds its request URL directly from `session.shop`, so whatever host string is in the JWT's `dest` claim becomes the destination that receives `client_secret` in the POST body.

The identity binding broken is: **host authenticated by JWT signature (bound only via `aud == api_key`) ≠ host that receives the `client_secret`, which is taken from the unbound `dest` claim.** Nothing in `JwtPayload` ties `dest` to `iss`, to the shop that actually established the session, or to any allow-list of Shopify domains.

### Impact Explanation
Since `client_secret` is included in the POST body sent to a base path built from attacker-influenced `dest`, this is an SSRF-style credential exfiltration path: if any component upstream of `exchange_token` accepts a session token whose `dest` claim can be influenced (e.g. a token relayed from a different, less trusted context, or a future code path that decodes a token before fully trusting its origin), the app's `client_secret` would be POSTed to a host chosen via that claim, rather than to Shopify's actual admin API host for the legitimately authenticated shop.

### Likelihood Explanation
Exploiting this specifically requires a validly-signed JWT (i.e., signed with the correct `api_secret_key`) whose `dest` is not the caller's real shop, which in the normal embedded-app / Shopify-issued-session-token flow is not achievable by an unprivileged attacker without already possessing the secret. The finding is best framed as a defense-in-depth / inconsistency issue: the gem validates the shop consistently everywhere else (`RefreshToken`, `ClientCredentials`, `TokenExchange.migrate_to_expiring_token`) except in `TokenExchange.exchange_token`, which is the single place where an externally-controlled claim value (`dest`) is trusted directly for constructing the outbound request carrying `client_secret`, without the same sanitize/allow-list step or an `iss`/`dest` consistency check that Shopify's own documentation recommends.

### Recommendation
In `JwtPayload`, additionally validate that `iss` and `dest` refer to the same shop domain, and pass `dest_shop` through `Utils::ShopValidator.sanitize!` in `TokenExchange.exchange_token` before using it to build `shop_session`, mirroring the sanitize step already used in `RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
Not concretely reproducible as a standalone unauthenticated exploit from the current index: it requires a validly HMAC-signed JWT with an attacker-chosen `dest`, which in turn requires possession of (or a signing oracle for) `api_secret_key`. This is flagged as an internal consistency/defense-in-depth gap based on direct comparison of code paths in `lib/shopify_api/auth/token_exchange.rb` [3](#0-2)  versus `lib/shopify_api/auth/refresh_token.rb` [6](#0-5)  and `lib/shopify_api/auth/client_credentials.rb` [7](#0-6) , rather than a fully demonstrated end-to-end attack chain — a Devin session with the full codebase and ability to run/trace the JWT verification path (`jwt` gem behavior, any callers passing externally-sourced tokens) would be needed to confirm whether an attacker-reachable path exists to supply a validly-signed token with a mismatched `dest`.
