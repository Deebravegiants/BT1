This confirms the vulnerability. The `WebhookMetadata` struct passed to every app's handler exposes `shop` (from the unauthenticated `X-Shopify-Shop-Domain` header) as the tenant identifier, while the HMAC signature verified by `Registry.process` only binds the request body (`to_signable_string` returns `@raw_body`), not the shop header.### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body, while the `shop` value that downstream apps use to attribute the webhook to a specific merchant/tenant comes from an HTTP header that is completely outside the signed data. This breaks the identity binding `hmac_signed_bytes == identity_used_by_app`, the same bug class flagged in the report (a value used to make a security-relevant decision — here, tenant attribution — is not covered by the mechanism used to authenticate the request).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never mixed into the signed string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which hashes `to_signable_string`, i.e. only the body) and then, once that check passes, forwards `request.shop` — the unauthenticated header — directly to the app's handler as the trusted tenant identifier: [3](#0-2) 

That value is wrapped in `WebhookMetadata`, whose `shop` field is the only tenant-scoping information the host app receives to decide which merchant's data the payload belongs to: [4](#0-3) 

`Utils::HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field using `OpenSSL.secure_compare`; it never inspects or binds any headers other than the HMAC value itself: [5](#0-4) 

Because the signature only proves "this body was produced by someone holding the app's `client_secret` (i.e., genuinely Shopify)" but says nothing about which shop the body is *for*, any raw_body+HMAC pair that is legitimately valid for one shop (e.g., a webhook the attacker legitimately received because they installed the app on their own store, or a `shop/redact`/`customers/data_request` mandatory webhook they can trigger themselves) can be replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a victim shop domain. `Registry.process` will still consider it "valid" and hand the app a `WebhookMetadata` claiming the payload is for the victim shop, even though the body and signature were computed for the attacker's own shop.

This is the equality that is broken:
`shop used for tenant attribution (Request#shop, from header)` ≠ `shop bound by the HMAC (Request#to_signable_string, body only)`

### Impact Explanation
This is a cross-tenant identity confusion: the gem authenticates the payload but not its tenant attribution, then hands the unauthenticated tenant claim to the app as if it were verified. Any app that keys per-shop state, deletion, or business logic off `WebhookMetadata#shop` (which is the only field the gem provides for this purpose) can be tricked into applying an attacker's own genuinely-signed webhook body under a victim shop's identity — e.g., causing customer/data-redaction actions, inventory/order state changes, or cached-data updates to be misattributed to a shop the attacker does not control. This matches the "cross-tenant access" Critical-impact category in scope, since the attack breaks the shop/tenant boundary that the HMAC is supposed to enforce.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker needs a legitimately signed `raw_body`/HMAC pair, which they can only obtain for webhooks addressed to a shop they control (e.g., their own store where they installed the app, or by triggering a mandatory webhook such as `customers/data_request`). No `api_secret_key`, access token, or privileged account is required — only ordinary merchant/app-install-level access to receive one authentic webhook and the ability to replay an HTTP request with a modified header to the app's public webhook endpoint. This is an unprivileged-internet-user attack once one authentic sample payload has been observed.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop domain to the signed body before it is exposed via `WebhookMetadata`. At minimum, `Registry.process`/`Request` should cross-check the header-derived `shop` against an independently-verified source (e.g., compare against the shop associated with the session/access token that registered the webhook, or include the shop domain in the canonical string that is HMAC'd) rather than trusting the raw header once the body signature passes.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers/receives a real webhook (or the mandatory `customers/data_request` webhook), obtaining a raw body `B` and a valid `X-Shopify-Hmac-Sha256: H` computed by Shopify over `B` with the app's real `client_secret`.
2. Attacker POSTs `B` with the same `H` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation succeeds because the shop header was never part of the signed data: [6](#0-5) 
4. The app's handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed_body_of_B, ...)` and performs shop-scoped logic under the wrong tenant's identity: [7](#0-6)
