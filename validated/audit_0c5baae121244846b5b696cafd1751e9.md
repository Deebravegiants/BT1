### Title
Permanent freezing of escrowed input tokens when a refund/redeem beneficiary is blocklisted by the underlying ERC-20 (e.g., USDC) - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2`'s escrow release path (`_withdraw`) transfers escrowed input tokens directly to a beneficiary address that is fixed at order-placement or cancellation time, with no ability for that beneficiary (or anyone) to redirect the payout to an alternate address. If the escrowed token is a blocklist-capable ERC-20 such as USDC and the beneficiary becomes blocklisted, `IERC20.safeTransfer` reverts every time the withdrawal is attempted, permanently freezing the escrowed funds — mirroring the exact root cause described in the referenced Cooler finding (a hardcoded, non-redirectable recipient for a token with a blocklist feature).

### Finding Description
`_withdraw` in `IntentsBase.sol` is the single code path used for both `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund on cancellation). It resolves the beneficiary from the incoming cross-chain message and unconditionally calls `safeTransfer(beneficiary, amount)`: [1](#0-0) 

The beneficiary is fixed and non-overridable:
- For `RefundEscrow` (both cancel-from-source and cancel-from-destination), the beneficiary is `order.user`, an address baked into the order at placement time and never adjustable by the user afterward: [2](#0-1) 
- The same `order.user` beneficiary is used on the cancel-from-source path that later triggers `_withdraw` via `onGetResponse`.

This is dispatched through `onAccept`, which routes `RedeemEscrow`/`RefundEscrow` straight into `_withdraw`: [3](#0-2) 

Unlike the referenced Cooler pattern where `repayLoan` at least allows an eventual, separately-callable `claimRepaid()` (which the audit finding says should also accept an arbitrary recipient), the IntentGateway does not even have a two-step "accrue, then claim to any address" design for refunds/redemptions — the transfer target is baked into the cross-chain message body and the transfer happens atomically inside `onAccept`/`onGetResponse`. If `IERC20(token).safeTransfer(beneficiary, amount)` reverts (as it does for a blocklisted address on tokens like USDC), the entire message processing reverts. Because there is no fallback recipient field, no admin/user override, and no alternate claim function, the escrowed tokens for that commitment can never be released: every future relayer submission of the same refund/redeem message will hit the same revert.

### Impact Explanation
This is a concrete, permanent freezing of user funds: once a user's (or occasionally a solver's) address for the escrowed input token is blocklisted post-placement (a realistic event for centrally-managed stablecoins like USDC), the specific order's escrowed `TokenInfo` amounts become permanently stuck in the `IntentGatewayV2` contract. There is no governance or user recovery mechanism (no `SweepDust`-style function applies to `_orders[commitment][token]` balances, only to protocol dust) to redirect these funds to a non-blocklisted address. This qualifies as a Medium-severity permanent freezing-of-funds issue, matching the criteria and the exact bug class of the referenced report.

### Likelihood Explanation
Likelihood is non-trivial but not high: it requires the specific order's `user` address (a legitimate on-chain actor, not an attacker) to become blocklisted by the token issuer (e.g., a sanctioned/compromised USDC address) between order placement and refund/cancellation. Given USDC and similar centrally-blocklistable stablecoins are explicitly supported input tokens in the IntentGateway's fee/swap flows, and cancellations can be triggered by the user or, after deadline, by any third party, this scenario is realistic in production for any long-lived or contentious order.

### Recommendation
Introduce an escrow/claims model analogous to the recommended Cooler fix: instead of transferring directly to the immutable `beneficiary` inside `_withdraw`, credit an internal "claimable" balance keyed by `(commitment/beneficiary, token)` when the direct transfer would fail (e.g., wrap the transfer in a try/catch or a pull-based claim function), and expose a separate `claim(token, recipient)` function that lets the rightful beneficiary designate an alternate recipient address to receive the funds. At minimum, allow the beneficiary to pass a `recipient` parameter to `cancelOrder`/`fillOrder`/`onAccept`-adjacent claim logic instead of hardcoding `order.user`/`msg.sender` as the final transfer target with no override.

### Proof of Concept
1. `orderSource`: a user places a cross-chain order on chain A with `order.user = U` and USDC as an input, escrowing funds via `placeOrder`.
2. Before the order is filled, `U`'s address is added to USDC's blocklist (e.g., due to sanctions/compromise, a well-documented event for USDC — see the referenced weird-erc20 list).
3. The order expires or is cancelled from the destination chain (`_cancelFromDest`), dispatching a `RefundEscrow` message back to chain A with `beneficiary = order.user = U`. [2](#0-1) 
4. On chain A, `onAccept` decodes the message and calls `_withdraw(body, isRefund=true, finalize=true)`, which calls `IERC20(USDC).safeTransfer(U, amount)`. [1](#0-0) 
5. Because `U` is blocklisted, USDC's `transfer` reverts, causing `onAccept` to revert. Any relayer resubmission of the same delivery proof hits the identical revert — the escrowed USDC for this commitment is permanently locked in `IntentGatewayV2` with no way for `U` to specify an alternate receiving address.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }
