### Title
Webhook shop/topic identity fields excluded from HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body alone, while the `shop`, `topic`, `api_version`, and `webhook_id` values that `Registry#process` acts on are read from unauthenticated HTTP headers, exactly mirroring the reported bug class: a field that downstream logic relies on for identity/accounting is not covered by the cryptographic check that is supposed to authenticate the message.

### Finding Description
`Utils::HmacValidator.validate` authenticates a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the `hmac` field with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, which are never included in the signed string: [3](#0-2) 

`Registry#process` validates only the body HMAC and then dispatches the handler using the unauthenticated `request.topic` and `request.shop` values: [4](#0-3) 

The identity binding that should hold is: `hmac_signature == HMAC(shop ‖ topic ‖ body, client_secret)`. Instead, the gem only enforces `hmac_signature == HMAC(body, client_secret)`, leaving `shop` and `topic` completely unauthenticated. Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every merchant that installs the app, any unprivileged internet user can self-serve a Shopify development store, install the target app, and receive a legitimately-HMAC-signed webhook body for their own shop. They can then replay that exact body to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers with a victim shop/topic of their choosing. `HmacValidator.validate` still succeeds (the body and secret are unchanged), and `Registry#process` hands the handler a `WebhookMetadata` claiming to be from the victim shop and/or a different topic: [5](#0-4) 

This directly matches the report's root cause pattern: `_getPendingRewards` trusted `lpBalance` (mutable state) while only `rewardsPerLPQ128`/`usrRwdIndexQ128` were update-gated; here the handler trusts header-derived `shop`/`topic` while only the raw body is protected by the HMAC "index".

### Impact Explanation
Any handler that keys off `request.shop` to update per-tenant records (as the gem's own `WebhookMetadata.shop` API is documented and intended to be used) can be tricked into applying a webhook payload to the wrong tenant, or into misclassifying the event's topic — a cross-tenant integrity break driven purely by unauthenticated header data flowing past a signature check that never covered it. This meets the Critical bar defined in scope ("cross-tenant access") because the tenant boundary (`shop`) is exactly the field an attacker can freely forge while the check that is supposed to authenticate the whole message silently passes.

### Likelihood Explanation
High: obtaining a genuine signed webhook body requires nothing more than installing the target public app on a free/self-service Shopify development store — no privileged account, leaked secret, or TLS interception is needed. Replaying the body with attacker-chosen headers to the app's public HTTP webhook endpoint is a standard, unauthenticated HTTP request.

### Recommendation
Include the identity-bearing fields (`shop`, `topic`, and ideally `webhook_id`) in the signable string that `HmacValidator` verifies for webhook requests, or otherwise cryptographically bind them to the body (e.g., verify them against a value embedded/signed inside the payload, or require they match a shop/topic the app expects for a previously-registered subscription) before `Registry#process` passes them to handlers.

### Proof of Concept
1. Attacker creates a free Shopify development store `attacker.myshopify.com` and installs the victim app (using its public install flow — no privileged credentials required).
2. Shopify sends a legitimate webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>`, and some `raw_body`.
3. Attacker captures this raw body + HMAC header pair.
4. Attacker POSTs the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
5. `ShopifyAPI::Webhooks::Request.new` accepts the headers (all three required headers present) and `Utils::HmacValidator.validate(request)` returns `true`, since it only recomputes the HMAC over `raw_body`: [6](#0-5) 
6. `Registry#process` invokes the registered handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled data as if it originated from the victim shop.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
