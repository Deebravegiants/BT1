### Title
Malicious swap-route venue can steal arbitrary tokens from the caller's wallet via a poisoned authorization tree - ([File: contracts/swap-aggregator/src/venues/mod.rs])

### Summary
This is the Soroban analog of the Trivy credential-leak class (CWE-522): code trusted only for a bounded task contacts an attacker-chosen endpoint, and ambient authority the user granted for that task is exercised by the malicious endpoint for its own purposes. The swap router dispatches hops to pool/token addresses named in the caller-supplied payload with no venue or address allowlist. Because `execute_strategy` runs under the sender's `require_auth`, a `transfer` that a rogue hop contract makes from the sender is recorded as a child of the sender's auth entry during simulation and executes at submission if the user signs the returned tree. The loss is the caller's entire wallet balance of any token, not just the routed input. [1](#0-0) [2](#0-1) 

### Finding Description
`execute_strategy(sender, total_in, swap_xdr)` authenticates the sender once and then executes a packed program whose `assets` registry can name any contract address. `dispatch_hop` invokes the venue/pool address taken directly from the payload — there is no allowlist or registry check on hop pools or hop tokens. The controller side mirrors this: `swap_tokens` grants exactly one input transfer to the router (`authorize_transfer_as_current`) but cannot constrain what addresses the route visits or what the route does under the sender's auth. [3](#0-2) 

Concretely, an attacker deploys a "pool" contract whose `swap` method calls `token::Client::transfer(victim, attacker, amount)` on an unrelated token the victim holds, then induces the victim to run a `swap_collateral`/`multiply`/`swap_debt`/`repay_debt_with_collateral` (or a direct `execute_strategy`) whose route includes that pool. Under `simulateTransaction` (recording mode), the rogue transfer is attached as a child invocation under the sender's auth root; if the client blindly signs the simulated auth tree, the host enforces the signed tree and the rogue transfer succeeds — draining the victim's unrelated wallet tokens in the same transaction that produces a perfectly fair-looking swap output. The repository's own test fixture demonstrates exactly this: `RogueHopPool::swap` transfers Alice's `WALLET_BALANCE` of an unlisted token to the attacker while returning `FAIR_OUT_ETH`. [4](#0-3) [5](#0-4) 

The in-protocol mitigations do not bound this loss: `dispatch_hop`'s measured `spent != amount_in → InvalidAmount` check only watches the hop's `token_in` balance, `SlippageExceeded` only guards `token_out`, and the controller's `RouterOverspend`/`NoSwapOutput` checks only measure the controller's own balances. None of them sees a transfer of a third token from the sender's wallet. [6](#0-5) 

### Impact Explanation
Theft of user funds. A single unprivileged attacker who can get a victim to submit one crafted route drains arbitrary tokens from the victim's wallet in amounts unrelated to the swap size — the threat model itself states "the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it." This applies to every `execute_strategy` caller and every controller strategy that embeds a route. [7](#0-6) 

### Likelihood Explanation
The attacker needs the victim to sign the poisoned authorization tree. This is not automatic, but it is realistic: standard wallet/dApp flows simulate a transaction and present the simulation-produced auth entries, and users are conditioned to sign what simulation returns — especially when the swap leg itself is honest (fair input, fair output, correct `min_out`). The rogue child invocation is indistinguishable in effect from a legitimate pre-transfer unless the client decodes the route and diffs the auth tree against the expected single `token_in.transfer` child. The threat model places the burden on clients ("a client must decode the route it signs and refuse an authorization tree with any other child"), which means any client that does not implement that check exposes its users. Medium likelihood, matching the Medium severity of the source advisory. [8](#0-7) 

### Recommendation
On-chain, add a venue/pool allowlist or governance-curated pool registry so `dispatch_hop` rejects hop addresses governance has not vetted, eliminating the ability of a route to put arbitrary attacker code on the call stack under the sender's auth. Short of that, enforce at the router level that the sender's auth tree grants only the exact `token_in.transfer(sender, router, total_in)` (e.g., by documenting and hard-checking in the controller/SDK that any additional child of the sender's root aborts the transaction), and ship a route-decoding verifier in the SDK that rejects any simulated auth tree containing children beyond the single expected input transfer. [9](#0-8) 

### Proof of Concept
The repository already contains a working PoC in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. `Scene::new` sets up Alice with 10,000 USDC supplied, an unrelated `wallet_token` balance of 77,770,000,000, and registers `UnlistedPoolRouter` as the controller's swap aggregator.
2. The attacker deploys `RogueHopPool`, whose `swap` calls `token::Client::transfer(alice, attacker, WALLET_BALANCE)` on the wallet token, and embeds its address as `hop_pool` in the route XDR.
3. `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows recording-mode simulation attaching the rogue `transfer(alice → attacker)` as a child of Alice's `swap_collateral` auth entry, with the swap paying fair ETH output.
4. `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows enforcing mode rejects the route under an honest root-only tree, but succeeds — moving the full `WALLET_BALANCE` to the attacker — once the client signs the simulation-returned poisoned tree.

Reachable entrypoints: `controller.swap_collateral` / `swap_debt` / `multiply` / `repay_debt_with_collateral` (any route-bearing strategy) and direct `router.execute_strategy`. [10](#0-9)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
