### Title
Webhook `shop` identity is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the JSON body of an incoming webhook via HMAC, but the `shop` (tenant) identity that the handler acts on is read from an HTTP header that is excluded from the signed bytes. Any party able to present a payload whose body-HMAC pair validates can attach an arbitrary `shop-domain` header, and the gem will hand that attacker-chosen shop identity to the app's webhook handler as if it were authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `#shop` is pulled straight out of the (attacker-controllable) request headers, with no relation to the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely over `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then forwards `request.shop` — the unauthenticated header value — into the metadata delivered to the app's handler: [4](#0-3) 

The equality the gem implicitly asserts is:
`shop used by handler (header "shopify-shop-domain") == shop that produced/owns the signed body`

but the code only proves:
`HMAC(secret, raw_body) == received_hmac`

These are not the same claim. The signature never binds the body to the `shop-domain` header, so the header can be swapped independently of the signed payload while the HMAC check still passes.

### Impact Explanation
An app that relies on `WebhookMetadata#shop` (as documented/intended — see `data.shop` used directly in handlers in `test/webhooks/registry_test.rb`) to attribute incoming webhook data to a tenant can be made to process a validly-signed payload under a different shop's identity. In a multi-tenant Rails app this leads to cross-tenant data confusion (e.g., an order/customer/inventory update for shop A being written into shop B's tenant scope), which falls under the "cross-tenant access" Critical-impact category defined for this scan.

### Likelihood Explanation
Exploitation requires the attacker to have obtained one legitimately-signed webhook body+HMAC pair (which Shopify sends over the public internet to the app's callback endpoint, and which is not secret-bound to the shop header). Once obtained — e.g., via a leaked log, a debugging proxy, replay from a compromised/rogue shop, or an app installed on an attacker-controlled shop that receives its own genuine signed webhooks — the same body/HMAC can be re-sent with a different `shopify-shop-domain` header to the same public endpoint, and the library will accept it as authentic for the new shop. No `api_secret_key`, access token, or privileged account is needed by the requester; they only need network access to the app's public webhook endpoint and a previously delivered payload (including one for a shop they themselves legitimately installed the app on).

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signed bytes that `to_signable_string` returns, or otherwise independently bind the header-derived `shop` to the payload before it is trusted, so that mutating the header invalidates the HMAC.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `{"id":1}` and header `x-shopify-hmac-sha256: <valid HMAC of body>`.
2. Attacker replays the exact same body and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds (HMAC only covers the body, which is unchanged).
4. `Registry.process` builds `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)` and invokes the app's handler, which now processes shop A's data under shop B's tenant identity — demonstrated directly by the header-controlled `shop` accessor in `lib/shopify_api/webhooks/request.rb` lines 20-23 and its unauthenticated use in `lib/shopify_api/webhooks/registry.rb` lines 188-200.
