### Title
Multisig/singlesig `WalletAccount` identity collapse in `known-addresses.js` cache-key derivation via non-canonical `toString()` - ([File: features/address-provider/module/known-addresses.js])

### Summary
`known-addresses.js` derives its cache key and tx-log lookup key via `walletAccount.toString()` (`getCacheKey`, `#getTxLog`), but `WalletAccount.toString()` deliberately omits the `isMultisig` (and `delegated`) fields that are otherwise treated as immutable, identity-defining properties elsewhere in the codebase. Two distinct `WalletAccount` instances that differ only by `isMultisig` (e.g. `exodus_0` singlesig vs `exodus_0` multisig) coerce to the identical string `"exodus_0"`, causing `getCacheKey`/`#getTxLog`/`blockchain-metadata`'s tx-log storage (also keyed by `${walletAccount}`) to collapse them into one bucket.

### Finding Description
`known-addresses.js` builds its per-account/per-asset cache key by string-interpolating the `walletAccount` object directly: `getCacheKey = ({ walletAccount, assetName }) => \`${walletAccount}|${assetName}\`` [1](#0-0) . This template-literal coercion calls `walletAccount.toString()`. The same coercion is used to key the tx log lookup on `#txLogsAtom`'s `value[walletAccount]` object [2](#0-1) , and explicitly again via `walletAccount.toString()` when calling `#getTxLog` in `get` [3](#0-2) .

`WalletAccount.toString()` is defined as:
```
toString() {
  return [
    this.source,
    this.index,
    ...(this.source === SEED_SRC ? [this.seedId, this.compatibilityMode] : [this.id]),
  ].filter((v) => v != null).join('_')
}
``` [4](#0-3) 

Notice that `isMultisig` and `delegated` are **not** part of this string, even though `WalletAccount` treats `id`, `source`, `index`, `isMultisig`, and `delegated` all as `IMMUTABLE_PROPERTIES` — i.e., fields that define a distinct wallet-account identity and cannot be changed via `.update()` [5](#0-4) . `equals()`, by contrast, correctly compares the full `toJSON()` (which does include `isMultisig`/`delegated`) and would treat them as different accounts [6](#0-5) .

Consequently, `new WalletAccount({ source: 'exodus', index: 0 })` (singlesig) and `new WalletAccount({ source: 'exodus', index: 0, isMultisig: true })` (multisig) both `toString()` to `"exodus_0"`. This is directly demonstrated in the repo's own test fixture, where `multisigWalletAccount = new WalletAccount({ ...WalletAccount.DEFAULT, isMultisig: true })` shares the same key as `walletAccount = WalletAccount.DEFAULT`, and blockchain-metadata's tx-log storage — itself keyed by `${walletAccount}` in `stringifyAssetSource` / `changesArrayToObject` (`features/blockchain-metadata/module/blockchain-metadata.js` lines 12–29) — writes both accounts' transactions into the same underlying bucket [7](#0-6) [8](#0-7) [9](#0-8) .

The result: `knownAddresses.get({ walletAccount: multisigWalletAccount, assetName })` returns the *singlesig* account's addresses (and vice versa), because `KnownAddresses.get`/`#cached`'s cache key and the underlying tx-log atom key both collapse to `"exodus_0|bitcoin"` regardless of `isMultisig` [10](#0-9) . This is a real string-coercion identity collapse: two distinct account authorization contexts (a regular Exodus HD account vs. a multisig account sharing the same `source`/`index`) merge into one permission bucket purely due to `toString()` omitting an immutable identity field.

### Impact Explanation
Any caller (including dapp/UI flows that resolve `receive-address`/`default-address` by constructing or receiving a `WalletAccount` with attacker-influenced or misconfigured `isMultisig`/`delegated` flags but matching `source`/`index`/`id`) can retrieve or poison the known-address list belonging to a *different* account context. Because known addresses feed directly into receive-address display and change-address reuse logic, an attacker able to trigger a lookup under a colliding `WalletAccount` shape can cause the wallet to present, cache, or reuse addresses derived from the wrong account/derivation namespace (singlesig vs multisig), which can lead to funds being sent to/received at addresses associated with an unintended key-derivation context — a form of address/account confusion that maps to Hydra's "Direct theft of user funds" category if downstream signing/verification also trusts the same collapsed string identifier without re-validating the full `WalletAccount` shape.

### Likelihood Explanation
This requires that some code path constructs or accepts a `WalletAccount` object (not just a plain string name) with the same `source`, `index`, and `id`/`seedId` but a different `isMultisig`/`delegated` flag, and that this object is passed into `knownAddresses.get`. Since `WalletAccount` instances are typically constructed internally from stored/wallet-accounts state rather than raw attacker-supplied strings, the most concrete demonstration is the repo's own test, which shows the collision occurs unconditionally by construction whenever a multisig and singlesig account share `source`+`index`. Whether an unprivileged external dapp can force such a `WalletAccount` object to be constructed and passed to `known-addresses.js` (as opposed to controlling only a raw string) is not established from the code inspected; this weakens confidence that the *full* attacker chain (external dapp request → `receive-address`/`default-address` handler → this collapsed key) is reachable without further tracing of the request handlers that resolve `assetSource`/`walletAccount` from external input.

### Recommendation
Fix `WalletAccount.toString()` (or add a dedicated canonical-key method used by all storage/cache layers, including `known-addresses.js`, `blockchain-metadata.js`, and `wallet-accounts.ts`) to include all `IMMUTABLE_PROPERTIES` (`id`, `source`, `index`, `isMultisig`, `delegated`), not just `source`/`index`/`id`/`seedId`. Additionally, `getCacheKey` in `known-addresses.js` should not rely on implicit string coercion of a rich object; it should explicitly serialize all identity-relevant fields (or use `walletAccount.toJSON()`/a hash of it) to guarantee that distinct `WalletAccount` identities never collapse to the same cache/storage key.

### Proof of Concept
Extend `features/address-provider/__tests__/module/known-addresses.test.js`:
1. Create `accountA = new WalletAccount({ source: 'exodus', index: 0, isMultisig: false })` and `accountB = new WalletAccount({ source: 'exodus', index: 0, isMultisig: true })`.
2. Call `blockchainMetadata.updateTxs({ assetName, walletAccount: accountA, txs: txsA })` and separately `updateTxs({ assetName, walletAccount: accountB, txs: txsB })` with distinct, non-overlapping transactions/addresses.
3. Call `knownAddresses.get({ walletAccount: accountB, assetName })`.
4. Assert failure of the invariant: the returned addresses equal (or are derived from) `txsA` instead of `txsB`, and that `getCacheKey({ walletAccount: accountA, assetName }) === getCacheKey({ walletAccount: accountB, assetName })` — i.e., `accountA.toString() === accountB.toString()` despite `accountA.equals(accountB) === false`. This confirms permission/address data bleeds across two distinct wallet-account identities through the shared string key.
