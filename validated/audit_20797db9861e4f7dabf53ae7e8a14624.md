### Title
Webhook shop identity is taken from an unauthenticated header not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable string from the raw body only, while the `shop` (and `topic`/`webhook_id`/`api_version`) values used to route and process the webhook are read from plain HTTP headers that are never included in the signature. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identifier after validating only the body's HMAC, breaking the intended binding `HMAC(secret, verified_bytes) == HMAC(secret, bytes_the_shop_field_is_derived_from)`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from HTTP headers that are not part of that signable string: [2](#0-1) 

`Registry.process` validates only the body's HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because a single app-wide `api_secret_key` is used to sign webhooks for every shop that installs the app, a valid `(raw_body, hmac)` pair generated for one tenant (Shop A) remains a **valid** HMAC pair regardless of which `shop-domain` header accompanies it — the signature makes no statement about the shop. The binding that should hold — "the shop this event is attributed to" == "the shop whose data produced these HMAC-verified bytes" — does not hold in this code.

### Impact Explanation
An unprivileged internet user who is simply a legitimate merchant/tenant of the app (Shop A, i.e. a low-privilege actor relative to any other tenant Shop B) can:
1. Trigger a legitimate webhook from their own store (Shop A) and capture the raw body + `x-shopify-hmac-sha256` value (e.g., by pointing their own webhook endpoint at a URL they control, entirely within their own store's permissions).
2. Replay that exact `(raw_body, hmac)` pair to the target app's webhook endpoint, but with the `x-shopify-shop-domain` header rewritten to Shop B.
3. `Utils::HmacValidator.validate` still succeeds because the signature only covers `raw_body`, and `Registry.process` hands the handler `WebhookMetadata` with `shop: "Shop B's domain"` and the attacker's chosen body content.

This lets an attacker who controls no more than their own installation cause the app to process attacker-controlled webhook data under a victim tenant's identity — a cross-tenant access/data-injection primitive that can corrupt another merchant's records, trigger unauthorized actions keyed off `shop`, or pollute per-shop caches/queues, without ever touching `api_secret_key` or an access token.

### Likelihood Explanation
Any app built on this gem that (a) uses the documented `Registry.process`/`WebhookHandler` flow, and (b) uses `data.shop` to select the tenant/session for further processing (the pattern explicitly documented in `docs/usage/webhooks.md`), is affected. The only capability required from the attacker is the ability to receive webhooks for their own shop (i.e., install the app once) and to send an arbitrary HTTP request to the app's public webhook endpoint — no secret material is needed.

### Recommendation
Include the shop domain (and topic/webhook id) in the HMAC-signable string, or otherwise cryptographically bind them to the verified body, and reject requests where the header-derived shop cannot be tied to the signed payload. At minimum, document/require that shop scoping never be trusted purely from `x-shopify-shop-domain`.

### Proof of Concept
```ruby
# Attacker installs the app normally on their own shop, shop-a.myshopify.com,
# and points a webhook at an endpoint they control to capture:
#   raw_body = '{"id":1,"note":"hi"}'
#   hmac     = Base64.encode64(OpenSSL::HMAC.digest("SHA256", app_secret, raw_body))
# (app_secret is unknown to the attacker; this is Shopify's real signature for
#  a legitimate event on the attacker's own shop)

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,       # valid, unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # swapped, unauthenticated
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

# POST captured raw_body + headers to the target app's public webhook route.
# ShopifyAPI::Webhooks::Registry.process passes HmacValidator.validate (body matches signature)
# and calls the handler with WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker's body)
