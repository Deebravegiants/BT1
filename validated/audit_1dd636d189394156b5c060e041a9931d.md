Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only this body-only HMAC and then trusts `request.shop`/`request.topic` to dispatch and populate `WebhookMetadata` passed to the app's handler [3](#0-2) . This is the same "field acted on but not covered by the HMAC" defect class as the ERC-777 report's "hook fires without being accounted for by the state check" — here the identity field (`shop`) is parsed from headers that sit entirely outside the signed byte range.

### Title
Webhook shop-domain/topic headers are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC that only signs the raw JSON body, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers, yet `ShopifyAPI::Webhooks::Registry.process` uses those unsigned headers to decide which handler to invoke and which shop's tenant context the payload belongs to.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header [4](#0-3) . Because `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers without being folded into `to_signable_string` [2](#0-1) , an attacker who can obtain one genuine `(raw_body, hmac)` pair — trivially done by triggering any real webhook event on their own store where the same app is installed, since `Context.api_secret_key` is a single app-wide secret shared across every shop's webhooks [5](#0-4)  — can then POST that exact body+hmac to the app's public webhook endpoint while freely rewriting the `shop-domain` and `topic` headers to point at any other merchant using the app. `Registry.process` accepts it because the HMAC check passes, and dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` straight to the app's handler [3](#0-2) . The handler has no way to detect this — the library documents `data.shop` as *the* shop-domain identity for the event [6](#0-5) .

The identity binding broken: `authenticated(body-bytes) == claimed(shop, topic)` should hold, but the gem only proves `authenticated(body-bytes)`; `shop` and `topic` are parsed, not verified.

### Impact Explanation
This crosses a tenant boundary within a single app deployment: any unprivileged internet user who can install the app on their own (free) development store can forge webhook deliveries that the app's own webhook registry will accept and label as belonging to an arbitrary victim shop that also uses the app, since the webhook endpoint is a public URL and the only gate is this body-only HMAC. Depending on how the host app trusts `data.shop` (e.g., to select which merchant's session/database row to update), this enables cross-tenant data confusion — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires no privileged credentials: an attacker only needs their own store with the same app installed (something any developer/merchant can freely obtain) to legitimately harvest a Shopify-signed `(body, hmac)` pair, then replay it directly to the app's public webhook URL with modified headers. The webhook endpoint is internet-reachable by design, and nothing besides `Utils::HmacValidator.validate` gates the request.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed material used for comparison (e.g., verify them against values embedded in the parsed/signed body, or require the host application to cross-check `request.shop` against the shop that owns the currently active session/subscription before trusting it), so that no header outside the HMAC's coverage can influence tenant attribution.

### Proof of Concept
1. Install the app under attacker's own `attacker.myshopify.com` store (same `client_secret` as every other install).
2. Trigger a real webhook event (e.g. `orders/create`) on the attacker's store; Shopify delivers `POST /webhook` with `raw_body`, `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Capture this exact request.
4. Replay the identical `raw_body` and `hmac` header to the same app endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different registered `x-shopify-topic`).
5. `HmacValidator.validate` in `Registry.process` succeeds because it only checks `raw_body` against the secret [7](#0-6) ; the handler receives `WebhookMetadata` claiming the event is for `victim.myshopify.com`.
