### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` treats the `X-Shopify-Shop-Domain` header as trusted tenant-identifying data, but the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body — never the shop header. Any party who can obtain one legitimately-signed webhook body/signature pair (for example by installing the app on their own store) can replay that exact body+signature while substituting an arbitrary `shop-domain` header, and `Webhooks::Registry.process` will accept it as authentic and hand the attacker-chosen shop to the app's webhook handler.

### Finding Description
`Request#hmac` and `Request#to_signable_string` show that the HMAC signable content is only the raw body: [1](#0-0) 

The `shop` value, however, is read straight from the (attacker-controlled, from the transport's perspective) HTTP header and is never included in that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it with the `hmac-sha256` header using `OpenSSL.secure_compare`: [3](#0-2) 

`Webhooks::Registry.process` performs exactly this HMAC check and then immediately forwards `request.shop` — the unauthenticated header value — into the handler's `WebhookMetadata`: [4](#0-3) 

The identity binding that should hold is:
```
shop_used_by_handler (header) == shop_that_the_signed_body_was_actually_generated_for
```
This equality is never checked anywhere in the gem. The HMAC only proves "this body was produced by someone holding `api_secret_key`" (i.e., genuinely came from Shopify, for *some* shop using that app's credentials) — it says nothing about *which* shop the body belongs to. Since `client_secret`/`api_secret_key` is shared across all shops that install the app, any shop that installs the app can trigger real, validly-signed webhook deliveries for itself. The webhook body content for many topics contains no verifiable indication of the shop identity (order/product IDs are shop-scoped, not globally unique in a way the receiver can distinguish). An attacker who legitimately installs the target app on their own store can capture a genuine `(body, hmac)` pair, then resend that exact body and signature to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still succeed because it only checks the body, and `Registry.process` will dispatch the payload to the handler tagged with the victim's shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to select which tenant's session/database row to act on (the documented and expected usage pattern, as shown in `test/webhooks/registry_test.rb` assertions on `data.shop`), an attacker can cause the application to apply another merchant's webhook business logic (state changes, cache invalidation, order/inventory updates, deletion flows, uninstall handling, etc.) under an incorrect shop context that the attacker fully controls the timing and body content of (their own shop's data), while the app attributes it to the victim shop. This is a cross-tenant data-integrity/access issue rooted directly in this gem's webhook verification primitive, matching the "Critical – cross-tenant access" impact bucket.

### Likelihood Explanation
Medium-High. It requires the attacker to be an app user (any shop can install a public app), which is an unprivileged-internet-user-equivalent position relative to other tenants of the same app. No access to `api_secret_key`, access tokens, or `client_secret` is required — only the ability to receive one's own legitimately-signed webhook and replay it with a modified header, which is trivial HTTP tooling.

### Recommendation
Bind the shop identity into the signed content that `HmacValidator` verifies (e.g., include the shop domain, or have the host application independently verify that the shop header corresponds to a shop that is actually installed/known, and treat `request.shop` as merely a routing hint, not an authenticated tenant identifier). At minimum, document prominently in `Webhooks::Request`/`WebhookMetadata` that the `shop` field is unauthenticated and must be cross-checked by the caller against its own list of installed shops before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook event (e.g. `orders/create`) and captures the resulting POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (a real, validly-computed signature since Shopify generated it using the shared `api_secret_key`).
3. Attacker resends the same body `B` and header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` accepts the headers, `HmacValidator.validate` succeeds because it only re-derives the HMAC over `B` (see `to_signable_string` returning `@raw_body`), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`.
5. The application processes the attacker's own order data under the victim shop's tenant context.
