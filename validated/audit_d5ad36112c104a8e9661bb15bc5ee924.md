Confirmed: the docs explicitly promise that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`) before invoking the handler with the tenant-identifying `shop` field, but the implementation's HMAC only covers the JSON body, not the `shop-domain` header.

### Title
Webhook `shop` identity is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the handler a `shop` value read from an unauthenticated HTTP header. Because the signed bytes and the trusted identity field are different, an attacker who can produce a genuinely-signed webhook (e.g. the owner of any shop that has this app installed, who legitimately receives such webhooks) can change the `shop-domain` header to any other shop string while keeping the same body/HMAC pair, and the gem will report it as authentic for a shop it never actually came from.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed payload: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string` (i.e. the body only) and compares it to the `hmac-sha256` header: [3](#0-2) [4](#0-3) 

If the HMAC check passes, the unauthenticated `shop` header value is forwarded, unmodified and unchecked, straight into `WebhookMetadata` and into the app's handler: [5](#0-4) [6](#0-5) 

This breaks the identity binding `shop_authenticated == shop_acted_on`: the bytes verified by the HMAC (`raw_body`) are not the bytes that identify the tenant (`shop-domain` header). The bug-class analog to the referral-mint report is direct: a field that downstream logic treats as trusted/attributable (`referrerTokenId` in the report, `shop` here) is never checked against the value actually covered by the authenticity proof (ownership check in the report, HMAC signature here).

The documentation for this gem explicitly tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" before dispatching to the handler: [7](#0-6) 
so host applications are encouraged to trust `data.shop` as an authenticated fact, which the gem does not actually guarantee.

### Impact Explanation
Any attacker who can obtain one genuinely Shopify-signed webhook body/HMAC pair for a topic with a fixed or attacker-controllable body (for example, `shop/redact`, `customers/redact`, or any topic whose JSON body content the attacker can predict/replicate for two different shops, or simply a topic with an effectively-empty/constant body across shops) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `Registry.process` will accept it as authentic and dispatch it to the handler as if it originated from the victim shop. Depending on how the host app implements its handler (as the gem's own docs suggest — keying off `data.shop` to route data/perform actions like uninstall cleanup, GDPR redaction, or updating shop-scoped records), this enables cross-tenant data corruption or action-spoofing against a shop the attacker doesn't control — a cross-tenant integrity/access violation.

### Likelihood Explanation
Exploitability depends on the attacker's ability to obtain a validly-signed body for a webhook topic whose payload is shop-independent or otherwise reproducible (e.g., mandatory compliance topics such as `shop/redact` have minimal/predictable bodies). Any store owner who installs the app receives real, signed webhooks and can freely modify unsigned headers before relaying them to the app's endpoint, so the attack requires no privileged access beyond running a Shopify store.

### Recommendation
Include the shop domain (and other identity-bearing headers such as topic/webhook id) inside the HMAC-signed payload verification — either by validating that the header contents match values encoded within the signed body, or by extending `to_signable_string`/`HmacValidator` to fold in the `shop-domain`, `topic`, and `webhook-id` headers so that a signature is only valid for the exact tuple of (body, shop, topic, webhook id) it was issued for.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` with the app installed and receives a legitimate `shop/redact` webhook with body `{}` (or any shop-independent JSON) plus a valid `x-shopify-hmac-sha256` computed over that body with the app's `client_secret`.
2. Attacker relays the same raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` reads `shop` from the attacker-supplied header (`lib/shopify_api/webhooks/request.rb:20-23`); `HmacValidator.validate` recomputes the HMAC over the body only and it matches (`lib/shopify_api/utils/hmac_validator.rb:26-31`), so `Registry.process` proceeds.
4. The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "shop/redact", body: {})` (`lib/shopify_api/webhooks/registry.rb:198-199`) and executes shop-scoped logic (e.g. data deletion/redaction) against the victim shop, despite the request never having come from Shopify on behalf of that shop.
