### Title
Borrow-index accrual overflows `i128` before the `MAX_BORROW_INDEX_RAY` cap engages, permanently freezing a high-utilization market - (File: common/src/rates/scaling.rs)

### Summary
The analog of CVE-2017-16644 (improper error handling → crash/DoS triggered through attacker-influenced state) is the pool's interest accrual path: every mutating verb accrues first, and accrual computes total borrowed value via `scaled_to_original`, i.e., `scaled.mul(index)` in RAY fixed point. At sustained high utilization on a steep rate curve the borrow index compounds to the point where `scaled * index` exceeds `i128::MAX` and panics with `MathOverflow` — before the intended `MAX_BORROW_INDEX_RAY` ceiling ever clamps the index. From that block onward, every entrypoint that touches the market (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `update_indexes`) aborts on the same overflow, so all supplier and borrower funds in the market are frozen.

### Finding Description
`scaled_to_original` multiplies the scaled share total by the index and panics on overflow rather than degrading (common/src/rates/scaling.rs:14-16). It is called by `Cache::calculate_utilization` and by the accrual/unscale helpers (`unscale_borrow`, `unscale_supply`) that run inside `interest::global_sync`/`ops::synced_market` before any position mutation (contracts/pool/src/cache/scale.rs:23-26, 71-95). The protocol has an explicit guard for this scenario — `MAX_BORROW_INDEX_RAY` clamps index growth (common/src/constants/pool.rs:19) — but the total-value computation overflows at a far lower index than the cap when the scaled debt base is large, so the clamp never engages. The repository's own harness test proves the freeze end-to-end: after enough years at ~98% utilization on the XLM curve, `update_indexes`, `withdraw`, and `repay` all fail with `MATH_OVERFLOW`, and the test notes the cap "did not engage before the value overflow" and that the documented bound in `docs/reference/formulas.md` is wrong (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361).

Attack path for a single unprivileged address: `supply` a very large amount into a high-decimals market, `borrow` to near-max utilization (caps are per-market configuration, and utilization near the steep curve segment is reachable by any borrower with sufficient collateral), then let millisecond-chunked accrual compound. No privileged call is needed; `update_indexes` is permissionless, so anyone — including the attacker or an innocent keeper — triggers the freezing panic.

### Impact Explanation
Permanent freezing of funds: once `scaled * index` overflows, all verbs accrue first and panic, so suppliers cannot `withdraw`, borrowers cannot `repay`, liquidators cannot `liquidate`, and `clean_bad_debt`/`recapitalize` cannot run for that market. Unlike a fail-closed validation reject on a single bad call, this is an irreversible state-level DoS of an entire market book — there is no admin verb that lowers `borrowed` or the index without first accruing. All user funds parked in that (hub, token) market are bricked, satisfying the "permanent freezing of funds" acceptance bar.

### Likelihood Explanation
Medium. Triggering requires whale-scale capital (test uses ~10^28 raw units of an 18-decimal asset, i.e., ~$10B-scale) and many years of compounding at high utilization, so it is not cheaply reachable tomorrow. However, it requires no privilege, no oracle manipulation, and no cooperation — only ordinary `supply`/`borrow` calls plus time, and Ledger time in Soroban advances regardless of governance attention. The codebase itself treats this as a live defect (the test asserts the documented safety bound is wrong), so it is a real reachable edge rather than a theoretical one.

### Recommendation
Guard the multiplication, not just the index: in `scaled_to_original` (common/src/rates/scaling.rs:14) and its callers, clamp or saturate the index (and/or the product) at the point where `scaled * index` would exceed `i128::MAX` — e.g., apply `MAX_BORROW_INDEX_RAY`/`MAX_SUPPLY_INDEX_RAY` to the effective index *before* unscaling, or compute utilization/accrual with a saturating `mul_div` variant analogous to `mul_div_floor_saturating` already used in `calculate_scaled_cap` (common/src/rates/scaling.rs:26-33). Additionally, ensure `clean_bad_debt`/`recapitalize` have an accrual-free recovery path so a frozen market can still be wound down.

### Proof of Concept
Existing in-repo reproduction: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361):

```rust
// BIG18: 18-decimal market on the XLM rate curve
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);          // unprivileged supply
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% utilization

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; } // panics
}
// => Error(Contract, MATH_OVERFLOW), borrow_index < MAX_BORROW_INDEX_RAY
// Market frozen: withdraw and repay both panic on the same overflow
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

The panic originates in `scaled_to_original` → `Ray::mul` overflow during accrual, which runs before every market mutation, bricking the market for all users.

Note on uncertainty: I verified the accrual-first ordering and the panic site from `scale.rs`, `scaling.rs`, the constants, and the harness test; I did not read `interest::global_sync` line-by-line in this pass, but the test demonstrably shows `update_indexes`, `withdraw`, and `repay` all abort with `MATH_OVERFLOW`, confirming the shared accrual path is the choke point.
