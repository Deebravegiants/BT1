### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates nothing but the JSON body bytes. The `shop` value that `Registry.process` passes into the host application (via `WebhookMetadata`) is read straight from the `x-shopify-shop-domain` header, which is never part of the HMAC input. This breaks the equality that should hold: `shop_used_for_tenant_dispatch == shop_that_the_HMAC_actually_authenticates`.

### Finding Description
`Request#hmac` decodes the `hmac-sha256` header, and `Request#to_signable_string` returns the raw body only: [1](#0-0) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac`: [2](#0-1) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build `WebhookMetadata`, which is handed to the app's business-logic handler: [3](#0-2) 

Because the signature only covers the body, and the `client_secret` used to compute it is a single, app-wide value shared across *every* shop that installs the app, any request whose body byte-for-byte matches a body Shopify has previously HMAC-signed for the app will pass verification — no matter what `shop`, `topic`, or `webhook-id` headers are attached. An attacker who controls (or merely observes traffic on) any one shop that has installed the app can capture one legitimate `(raw_body, hmac)` pair from Shopify, then resubmit that same body/hmac pair to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to an arbitrary victim shop domain. `Registry.process` will accept it as valid and dispatch it to the handler labeled with the attacker-chosen shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: the gem authenticates *body bytes* but the host application (per the gem's documented API in `docs/usage/webhooks.md`) is expected to trust `WebhookMetadata#shop` as the tenant identifier for looking up sessions/state and applying side effects (e.g., recording an order paid, redacting data, updating subscription/billing state) for that shop. An attacker can force the app to process an attacker-supplied body under a victim shop's identity, i.e. cross-tenant data injection/spoofing without ever possessing the victim's access token or the app's `client_secret`. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic for any unprivileged internet user who can install the target app on their own shop (or otherwise observe one legitimate webhook delivery): they receive a genuine `(body, hmac)` pair signed with the app-wide secret, and can replay it against the app's public webhook endpoint with a forged `shop-domain` header. No secrets, tokens, or privileged access are required — only the shared `client_secret` computation is reused, not disclosed.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or otherwise reject webhooks whose header-derived shop does not correspond to a shop that is actually expected to be sending that specific signed payload. At minimum, `Request#to_signable_string` should not be the sole channel of trust for `request.shop`; the gem should document/enforce that consumers cannot rely on `WebhookMetadata#shop` being cryptographically bound unless the header is included in the verified signable content, or the registry should independently confirm the delivering shop before dispatching.

### Proof of Concept
```ruby
# Attacker owns/installs the target app on their own shop "attacker.myshopify.com"
# and receives a real, Shopify-signed webhook delivery:
raw_body = '{"id":1,"note":"hi"}'
real_hmac_b64 = "<value from genuine x-shopify-hmac-sha256 header Shopify sent for attacker's own shop>"

# Attacker replays the identical body/hmac pair but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => real_hmac_b64,          # unchanged - still a valid HMAC of raw_body
  "x-shopify-shop-domain"  => "victim.myshopify.com", # forged - not covered by the HMAC at all
  "x-shopify-webhook-id"   => "forged-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (only raw_body is checked),
#    and the app's handler.handle is invoked with WebhookMetadata#shop == "victim.myshopify.com",
#    even though Shopify never sent this event for that shop.

          received_signature = verifiable_query.hmac
