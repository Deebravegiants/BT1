Confirmed root cause. Documented behavior: `data.shop` (the tenant identity) is officially documented as trusted output of the webhook handling process, but it is derived from the `shopify-shop-domain` header which is never covered by the HMAC signature.

### Title
Webhook Shop Domain Header Is Not Covered by HMAC Signature, Allowing Cross-Tenant Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , so `Utils::HmacValidator.validate` in `Registry.process` only authenticates the *body bytes*, never the `shopify-shop-domain` / `x-shopify-shop-domain` header [2](#0-1) . The `shop` value that is exposed to the host application's webhook handler as the tenant identity comes straight from that unauthenticated header [3](#0-2) .

### Finding Description
`HmacValidator.validate_signature` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header [4](#0-3) . For webhook requests, `to_signable_string` is defined as simply `@raw_body` [1](#0-0) . This matches Shopify's real webhook HMAC scheme (which only ever signs the body), but it means the equality the gem effectively verifies is:

`HMAC(secret, body) == received_hmac`

while the value used downstream as the authenticated tenant identifier is:

`request.shop == headers["x-shopify-shop-domain"]` (or `shopify-shop-domain`)

These two are never bound together. `Registry.process` validates only the body's HMAC and then immediately trusts `request.shop` to build `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle` as the shop that "owns" this webhook [2](#0-1) . The gem's own documentation instructs integrators to use `data.shop` directly as the tenant key (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [5](#0-4)  and the struct exposes it unqualified as `# The shop domain of the webhook` [6](#0-5) , with no note that it is unauthenticated.

Because a valid `(body, hmac)` pair is agnostic of which shop it was issued for, any party capable of resending or relaying a previously-seen valid webhook payload (which is delivered over plain HTTPS to a merchant-configured callback URL, and whose HMAC/body pair a receiving endpoint necessarily has in cleartext once received) can re-POST that same body/HMAC pair to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true`, because it never inspects the shop header, and `Registry.process` will invoke the handler claiming the payload originated from the attacker-chosen shop.

### Impact Explanation
This breaks the tenant-identity binding the gem is trusted to enforce: `shop authenticated via HMAC` vs `shop actually attributed to the webhook data`. In a multi-tenant SaaS app built on this gem, an attacker who can capture or replay one legitimate webhook body+HMAC pair (e.g. from their own shop's install, or an intercepted/logged request) can cause the host application to process/store that payload under a different, victim shop's identity, since the gem provides no cryptographic assurance binding shop-domain to the signed content. This constitutes cross-tenant data confusion/injection, which is a Critical-class impact (cross-tenant access) per the scope's criteria.

### Likelihood Explanation
Exploitation requires network reachability to the app's public webhook callback endpoint (which is internet-facing by design) and possession of any one valid `(raw_body, hmac)` pair — obtainable trivially from the attacker's own shop's webhook traffic to their own app instance, since `raw_body`/`hmac` are visible in plaintext to whoever receives the webhook. No access token, `client_secret`, or privileged credential is required, satisfying the "unprivileged internet user" bar. The only gem-level control (`HmacValidator.validate`) does not defend against this because it was never designed to bind shop identity — it defends against body tampering only.

### Recommendation
Since Shopify does not include shop-domain in the webhook HMAC signature, the gem cannot cryptographically verify shop-domain via HMAC. However, the current API/documentation implies `WebhookMetadata#shop` is trustworthy. At minimum, the gem should document in `webhook_handler.rb`/`docs/usage/webhooks.md` that `shop` is unauthenticated header data and must be cross-checked by the host application against a known/registered shop record before being used as a tenant key, and/or the `Request#shop` accessor should be renamed/annotated to make its untrusted nature explicit (e.g. `unverified_shop`).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, capturing the exact raw JSON body `B` and the `x-shopify-hmac-sha256` header value `H` Shopify computed for it (this HMAC only covers `B`, per `Request#to_signable_string` [1](#0-0) ).
2. Attacker sends an HTTP POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (changed)
   - Header `x-shopify-topic`: same registered topic
3. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and finds it equal to `H`, returning `true` [7](#0-6) .
4. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` and invokes the app's handler [8](#0-7) , which processes/stores attacker-controlled data under `victim-shop.myshopify.com`'s tenant record — a cross-tenant write/read confusion entirely undetected by the gem.
