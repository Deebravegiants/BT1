### Title
Permanent freezing of LT donated directly to a curve `Pair` before graduation - (`packages/contracts/src/Router.sol`, `packages/contracts/src/Pair.sol`)

### Summary
Any unrelated wallet can `transfer` LT (the reserve asset) directly to a bonding-curve `Pair` contract (e.g. mistakenly, or via any excess/dust) before the token graduates. There is no function anywhere in scope that lets the payer, the curve, or anyone else recover that excess LT — it is permanently and irreversibly locked once the token leaves `Lifecycle.Curve`.

### Finding Description
`Pair.transferAsset` (`packages/contracts/src/Pair.sol:81-86`) is the only function capable of moving the LT (`assetToken`) out of the pair, and it is gated `onlyRouter`. `Router.sol` exposes exactly two callers of `transferAsset`: `sell()` (line 167, `BONDING_ROLE`-gated, driven by a curve sell) and `graduate()` (lines 203-211, `BONDING_ROLE`-gated). `graduate()` is called exactly once, from `Bonding._prepareGraduationLiquidity` (`packages/contracts/src/Bonding.sol:1073-1096`), and it pulls out only the exact computed `ltFromPair = assetReserve - virtualLtReserve` amount — deliberately excluding any LT donated directly to the pair (donation-resistance by design, per the natspec at `Router.sol:184-202`). Once `graduate()` runs, the token's lifecycle flips past `Curve` and `Router.graduate` becomes permanently unreachable for that pair — `Bonding` never calls it again. `Router.sell` also can't reach the donated LT because `_computeSell` derives `assetOut` purely from the stored `(reserveToken, reserveAsset)` K-math, not the pair's live balance.

The codebase's own comment on `Router.graduate` (lines 193-202) states this explicitly: *"Locked" here is a trust-assumption claim ... the leftover is unreachable as long as BONDING_ROLE is not granted to any other address and future Bonding upgrades preserve the lifecycle gate.* There is no `rescueERC20`/sweep-style function on `Pair`, `Router`, or `Bonding` that can pull excess/donated LT out of a `Pair` — unlike `FeeVault.sweepDonations()` (`packages/contracts/src/FeeVault.sol:151-160`), which provides exactly this recovery mechanism for excess USDC in the fee vault, or `Bonding._sweepLTToOwner` (`packages/contracts/src/Bonding.sol:1042-1052`), which sweeps rebalance-residue LT held by `Bonding` itself to the owner during `finalizeGraduation`. The `Pair` contract has no analogous mechanism for its own donated LT.

### Impact Explanation
LT donated to a `Pair` (whether by mistake, dust, or an attacker/creator wallet) before graduation is permanently and irrecoverably frozen once the pair's token lifecycle passes `Curve`. This is a permanent loss of funds with no path to recovery for anyone — not the payer, not the protocol owner, not governance — matching the "unrecoverable funds sent in excess" bug class from the source report, but worse here because in the alt.fun case there is no privileged escape hatch at all (the report's target had `rescueERC20`, just an incomplete one; alt.fun's `Pair` has none).

### Likelihood Explanation
Likelihood is moderate: this requires a direct `IERC20(lt).transfer(pair, amount)` call bypassing `Zap`/`Bonding`, which is unusual but fully permissionless and reachable by any wallet holding the paired LT — no privilege required. Accidental transfers (e.g., a user mistaking the `Pair` address for the token contract, or wallets/scripts sending LT to a discovered pair address) are a realistic real-world occurrence given `Pair` addresses are publicly discoverable via `Factory`.

### Recommendation
Add a permissionless sweep function, analogous to `FeeVault.sweepDonations()`, that lets any caller sweep LT held by a `Pair` in excess of its stored `assetReserve` to a safe destination (e.g., the protocol owner or back to the curve as additional buy liquidity), gated appropriately by lifecycle state so it can't be used to bypass donation-resistance for the graduation trigger. This mirrors the report's suggested fix: comparing the contract's live balance against the stored/expected balance and only permitting recovery of the delta.

### Proof of Concept
1. Launch a token via `Zap.createToken`, obtaining `tokenAddr` and its curve `Pair` (discoverable via `Bonding.tokenInfo(tokenAddr).pair` / `Factory.getPair`).
2. From any unrelated wallet holding the paired LT, call `IERC20(lt).transfer(pairAddr, X)` directly (not through `Zap`/`Bonding`).
3. Continue normal trading until the token graduates via either trigger (`Bonding.canGraduate` / `_enterGraduating` / `finalizeGraduation`).
4. Observe (as asserted by `test/GraduationInvariants.t.sol`'s invariant 4, `packages/contracts/test/GraduationInvariants.t.sol:216-218`) that `IPair(pairAddr).assetBalance() != 0` post-graduation when a donation occurred — the donated `X` LT sits in the now-`Graduated` `Pair` contract with `Router.graduate` unreachable (lifecycle gate) and no other function capable of calling `Pair.transferAsset` for that amount. The `X` LT is permanently lost.

    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }
