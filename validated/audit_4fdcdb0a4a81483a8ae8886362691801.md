## Analog Found

### Title
Fee-on-transfer tokens cause `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` to commit and later disburse more tokens than were actually locked, insolvency-draining the bridge's token reserve - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` pulls the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` but never measures the actual amount received by the contract. It then builds the cross-chain `Message` using the caller-supplied `params.amount` unconditionally [1](#0-0) . If `_underlying` is a fee-on-transfer (FOT) token, the contract actually receives less than `params.amount`, yet the ISMP `PostRequest` commitment and the resulting `Message.amount` encode the full, un-deducted `params.amount` [2](#0-1) .

### Finding Description
The contract explicitly compares the identical code path in `IntentGatewayV2.placeOrder`, which was hardened against exactly this bug class: it snapshots `balanceOf` before and after `safeTransferFrom` and mutates `order.inputs[i].amount` to the actually-received amount before it is hashed into the commitment [3](#0-2) . `WrappedHyperFungibleToken.send()` and its upgradeable twin (`WrappedHyperFungibleTokenUpgradeable.sol`, same pattern) never perform this balance check, so with an FOT `_underlying` token the amount encoded in the dispatched, hash-committed cross-chain message is systematically larger than what the contract actually escrowed [4](#0-3) .

On `onAccept` (destination side of this same bidirectional lock/unlock contract), the peer instance pays out `message.amount` in full from its own locked reserve of the underlying token via `safeTransfer` [5](#0-4) , i.e. more than was actually escrowed on the source side. The same over-payment also occurs on the timeout/refund path, which likewise refunds the full, un-deducted `message.amount` from the sender's own contract balance [6](#0-5) .

Because both the destination-unlock and the timeout-refund amounts are derived from the ISMP-committed `message.amount` (not from actual receipts), each transfer of an FOT-underlying asset silently leaks value out of the paired custody contracts. Repeated `send()` calls accumulate a growing deficit between the tokens actually held and the tokens the protocol is contractually obligated to release, eventually leading to insufficient balance and reverted/failed unlocks or refunds for other users.

### Impact Explanation
This is an unbacked-disbursement / insolvency bug in a token-bridge lock-unlock mechanism, reachable from a single unprivileged `send()` transaction whenever the deployment's `_underlying` is configured to a fee-on-transfer ERC20. It causes permanent freezing/loss of funds for later users once the reserve is drained below what is owed, and lets early actors extract more value than they deposited (since the commitment — and thus the destination-side payout — is always based on the pre-fee amount).

### Likelihood Explanation
Likelihood depends on the owner configuring `_underlying` to an FOT token via `configure()` [7](#0-6) ; this is not enforced against in code, unlike `IntentGatewayV2`, which was specifically patched (with dedicated FOT unit tests) to survive such tokens [8](#0-7) . Any ERC20 that is FOT (or later upgraded to add a fee, or is a rebasing/tax token) configured here triggers the bug on ordinary use, with no special privilege required by the caller.

### Recommendation
In `send()`, snapshot `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom`, and use the actual delta as `message.amount` in `_buildDispatchPost` — mirroring the fix already applied in `IntentGatewayV2.placeOrder` [3](#0-2) . Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.sol`.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = an ERC20 charging a 1% transfer fee.
2. Alice calls `send({amount: 1000e18, ...})`; contract only receives 990e18 via `safeTransferFrom`, but `Message.amount` dispatched/committed is `1000e18` [1](#0-0) .
3. On the destination chain, `onAccept` transfers out `1000e18` of the underlying to the beneficiary from the destination contract's reserve [5](#0-4) , exceeding what was ever locked for this transfer by 10e18.
4. Repeating this drains the paired reserve pool over time, eventually causing failed unlocks/refunds (insolvency) for legitimate users.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)

                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
