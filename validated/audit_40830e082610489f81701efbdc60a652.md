### Title
Reflected status/hash misattribution across same-asset withdrawals in a batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` matches a withdrawal record returned by the POA bridge API solely by `assetId`, ignoring the `index` and `destinationAddress` of the specific withdrawal being queried [2](#0-1) . The matcher itself documents this gap: "multiple withdrawals of the same token in a single transaction are not supported" [3](#0-2) .

### Finding Description
The SDK explicitly supports batching multiple `WithdrawalParams` into one NEAR intent transaction via `processWithdrawal`/`signAndSendWithdrawalIntent`, and then polls each one's status independently by `index` using `createWithdrawalCompletionPromises` → `watchWithdrawal` → `bridge.describeWithdrawal` [4](#0-3) [5](#0-4) . Nothing in `createWithdrawalIntents`/`validateWithdrawal` (`packages/intents-sdk/src/sdk.ts` lines 334-372) prevents two entries in a batch from sharing the same `assetId` while differing in `destinationAddress` and `amount`.

When `describeWithdrawal` is later called per-index, `findMatchingWithdrawal` looks up the API's `withdrawals` array by `nep141:${near_token_id} === assetId` only, taking the first match with `Array.prototype.find` [6](#0-5) . If the batch contains two withdrawals of the same token to different destinations, the same withdrawal record (and therefore the same `transfer_tx_hash`/status) will be returned for both indices — regardless of which one actually completed. This breaks the equality "status/hash reported == on-chain outcome for *this* withdrawal": index B can be reported `completed` with `txHash` X even though X is the hash of the transfer that actually paid index A's destination address, while B's own transfer may still be pending or may go to a different address entirely.

### Impact Explanation
An integrator relying on `waitForWithdrawalCompletion`/`processWithdrawal` per-withdrawal results to credit/settle off-chain balances or release goods could credit or mark-as-settled a withdrawal to destination B based on a transaction hash that never paid B — this is the "status or hash misreport making an integrator credit or refund twice" class explicitly called out as accepted impact. Because the code path is reachable purely through the SDK's public batch withdrawal API without needing bridge-operator or admin misbehavior, this is High severity when an integrator batches same-asset withdrawals to multiple recipients (a supported, unprivileged usage pattern).

### Likelihood Explanation
Likelihood requires: (1) an integrator issuing a batch withdrawal with ≥2 entries sharing an `assetId` (fully supported by public API, no validation blocks it), and (2) the POA bridge indexer returning multiple withdrawal records for the same NEAR tx hash concurrently in different states. The code comment acknowledges the POA API can return multiple such records and that the SDK does not disambiguate them, meaning this is a known, reachable gap rather than a hypothetical one.

### Recommendation
Disambiguate `findMatchingWithdrawal` by an unambiguous key (e.g., destination address, per-token ordering/amount as the existing comment already proposes, or an explicit withdrawal index from the API) instead of `assetId` alone. Until the POA API exposes such an identifier, `PoaBridge` should refuse to multiplex same-asset withdrawals within a single batch (throw instead of silently returning a possibly-wrong txHash/status), or de-duplicate matching by sorting withdrawals and params by amount as the existing code comment suggests, applying that logic rather than leaving it as an unimplemented note.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ {assetId: "nep141:btc.omft.near", amount: 100000n, destinationAddress: A}, {assetId: "nep141:btc.omft.near", amount: 50000n, destinationAddress: B} ] })`.
2. Both withdrawals settle in the same NEAR intent tx; the POA bridge processes them as two independent withdrawal records with the same `near_token_id`.
3. When `describeWithdrawal` is invoked for index `1` (destination B), `findMatchingWithdrawal` returns the first record whose `near_token_id` matches — which may be the record for destination A's completed transfer.
4. `waitForWithdrawalCompletion` resolves index 1 with `{status:"completed", txHash: <A's tx hash>}`, even though B's own transfer may still be pending or point elsewhere, causing the integrator to treat B's withdrawal as settled based on A's transaction.

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
