### Title
Passphrase cache reuse after lock due to fire-and-forget `set()` racing with `clear()` - (File: features/application/src/modules/passphrase-cache.ts)

### Summary
`Application#unlock` caches the passphrase via a fire-and-forget (`void`) call to `PassphraseCache.set()`, while `Application#lock` awaits `PassphraseCache.clear()`. If a lock is triggered immediately after an unlock (e.g., rapid unlock→auto-lock or lock→unlock→lock sequences during normal app lifecycle), the un-awaited `set()` can resolve after the awaited `clear()`, leaving the plaintext passphrase persisted in the cache even though the wallet is supposed to be locked. On the next app start, `#autoUnlock()` will read this stale cached passphrase and silently unlock the wallet without any user authentication.

### Finding Description
`Application.unlock` in `features/application/src/modules/application.ts` does: [1](#0-0) 
Note `void this.#passphraseCache.set(opts.passphrase)` — the write is not awaited before `unlock()` returns.

`Application.lock` does: [2](#0-1) 
Here `await this.#wallet.lock()` and `await this.#passphraseCache.clear()` run and complete before `lock()` returns.

`PassphraseCache.set` and `PassphraseCache.clear` in the target file both independently perform async storage operations with no mutual exclusion or versioning/generation check: [3](#0-2) [4](#0-3) 

Exploit flow:
1. User (or an automated/attacker-influenced UI/port event stream) triggers `unlock({ passphrase })`. `unlock()` fires `Hook.Unlock`, returns to caller, and asynchronously (unawaited) begins writing the passphrase into `#storage` via `set()`.
2. Before that pending `set()` resolves, a `lock()` call is triggered (e.g., an auto-lock timer firing right after manual unlock, or attacker-controlled timing of lock/unlock port messages as described in the audit's threat framing). `lock()` awaits and completes `clear()` synchronously with respect to its own call, wiping the passphrase storage.
3. The earlier, still-pending `set()` promise from step 1 then resolves and writes `PASSPHRASE_KEY`, `ADDED_AT_KEY`, `TTL_KEY` back into storage — after the clear.
4. The wallet is now in the locked state (`lockedAtom === true`, `wallet.isLocked() === true`), but the passphrase cache holds a valid, non-expired passphrase.
5. On the next application restart, `Application#start` calls `#autoUnlock()`: [5](#0-4) 
Since `walletLocked` is true and `passphraseCache.get()` returns the leaked passphrase, the wallet silently auto-unlocks, bypassing the lock boundary that `lock()` was supposed to enforce.

The root cause is that `createPassphraseCache`/`PassphraseCache` provides no atomicity or ordering guarantee between concurrent `set()`/`clear()` calls, and `Application.unlock` deliberately does not await the cache write, allowing `lock()`'s `clear()` to be overtaken by a stale `set()`.

### Impact Explanation
A stale passphrase surviving an explicit `lock()` means the secret required to decrypt/derive private keys is available for automatic reuse without the account owner supplying credentials again. This directly violates the invariant that lock must fully reset secrets before reuse, and results in unauthorized wallet unlock (private key/passphrase leakage path) on restart — matching the "Private key or private key generation leakage leading to unauthorized access to user funds" impact category, in scenarios where the attacker can influence app restart/relock timing (e.g., shared/relocked device, forced backgrounding, or the attacker-controlled `port`/timing mentioned in the audit scope).

### Likelihood Explanation
This requires a specific but realistic race window: `lock()` occurring while a prior `unlock()`'s passphrase-cache write is still in flight. Auto-lock timers, rapid user actions, or externally-controlled port/message timing (as posited in the audit's threat model) can produce this ordering without any privileged access, and the bug is deterministically reproducible by controlling the relative resolution order of the two promises in a test harness.

### Recommendation
Make `Application.unlock` await `this.#passphraseCache.set(opts.passphrase)` before returning, and add a guard in `PassphraseCache` (e.g., a monotonically increasing operation/generation counter, or a mutex/queue over `#storage` writes) so that `clear()` always wins over any `set()` issued before it, and any `set()` racing a later `clear()` is rejected or no-op'd.

### Proof of Concept
Unit/integration test plan for `features/application/src/modules/passphrase-cache.ts` and `features/application/src/modules/application.ts`:
1. Instantiate `PassphraseCache` with an in-memory storage whose `batchSet`/`clear` implementations can be artificially delayed via controllable promises.
2. Call `set('secret')` but delay its underlying `storage.batchSet` resolution (simulate the `void` fire-and-forget from `Application.unlock`).
3. Concurrently call and await `clear()` (simulating `Application.lock`).
4. Resolve the delayed `batchSet` after `clear()` completes.
5. Assert: `await passphraseCache.get()` returns the leaked `'secret'` value even though `clear()` was the logically-last completed lock operation — expected/desired assertion should be `undefined`.
6. At the `Application` level, reproduce via: `application.unlock({ passphrase })` immediately followed (without awaiting the internal cache write) by `application.lock()`, then simulate `application.start()` again and assert `#autoUnlock()` does NOT unlock the wallet (i.e., `wallet.isLocked()` remains `true`) — currently it would incorrectly auto-unlock.
