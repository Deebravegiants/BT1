### Title
Webhook shop/topic/webhook-id identity is not bound to the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC over the raw body only, then trusts the unauthenticated `shop-domain`, `topic`, `webhook-id`, and `api-version` headers to build the `WebhookMetadata` handed to the host app's handler. Because these fields are not part of the signed content, an attacker who possesses one validly-signed webhook body (e.g. delivered for their own installed store) can replay that exact body with forged identity headers claiming any other shop, and the signature check still passes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., of `raw_body`), and then constructs the trusted `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

`HmacValidator.validate` confirms this: it signs/verifies only `verifiable_query.to_signable_string`, which for `Webhooks::Request` is the raw body, never the headers: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(raw_body) == true` implies `shop_header == originating_shop`.

In reality the equality only proves `hmac_valid(raw_body) == true` implies `raw_body` was produced with `Context.api_secret_key`; it says nothing about which shop, topic, or webhook id the header claims. An attacker who is a legitimate (even free/dev-store) merchant of the app receives real webhooks for their own shop with a valid HMAC over the body. Because `shop-domain`, `topic`, and `webhook-id` are excluded from the signed string, the attacker can resend that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `shop-domain` header (and/or `topic`/`webhook-id`) for a different, victim shop. `HmacValidator.validate` still succeeds because `raw_body` is unchanged, and `Registry.process` will invoke the app's handler with `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the gem hands the host application webhook data falsely attributed to a shop that never sent it. Any downstream logic that trusts `WebhookMetadata#shop` (e.g., updating per-shop settings, triggering data-deletion/GDPR handlers, canceling subscriptions, writing order/customer records under the victim's tenant key) can be manipulated by a single low-privilege merchant using their own genuine webhook traffic as a signature oracle. This matches the Critical bucket of "cross-tenant access" caused by an identity-binding field (`shop`) not being covered by the same authenticator that gates the request.

### Likelihood Explanation
Any developer/merchant account (unprivileged) can install the app on their own store to receive legitimately-signed webhooks, then replay the raw body with a forged `shop-domain` header to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is required. The only work needed is finding a webhook `topic`/body whose content is otherwise attacker-controllable or replayable (e.g. `app/uninstalled`, `customers/redact`, or any topic where the body content doesn't itself uniquely identify the shop) which is broadly true for most topics that key off the header rather than an in-body shop domain.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed content verified against the HMAC (or otherwise cryptographically bind them, e.g. by deriving an expected shop from a separately validated access token/session rather than trusting the header), and reject the request if the header-derived shop cannot be independently authenticated. At minimum, `Registry.process` should document, and the library should optionally enforce, that `request.shop` must be cross-checked by the host application against a session/store known independently of this header.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com`. Shopify delivers a legitimate webhook to the app's callback endpoint:
   - headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: customers/redact`, `x-shopify-hmac-sha256: <valid HMAC of BODY>`
   - body: `BODY` (JSON payload).
2. Attacker replays the exact same `(BODY, hmac)` pair to the same endpoint, but this time sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-webhook-id`).
3. The host app calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `OpenSSL.secure_compare(computed_signature, hmac)` against `request.to_signable_string == BODY`, which is unchanged: [1](#0-0) 
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop: [3](#0-2) 
6. The host app's handler performs shop-scoped side effects (e.g., data deletion, subscription state change) against the victim shop's tenant record, despite the victim never sending this webhook.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
