Found a genuine unguarded panic reachable from cross-chain message content.

### Title
Panic (denial-of-service) via unchecked `copy_from_slice` on attacker-controlled `from` bytes in `on_timeout` - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
The GhostScript CVE is a buffer-overflow crash triggered by a crafted input whose size doesn't match what a fixed-size destination expects. The closest reachable analog in Hyperbridge is `Pallet::<T>::on_timeout` in the `hyper-fungible-token` pallet, which decodes an ABI `Message` from a timed-out `PostRequest.body` and then unconditionally `copy_from_slice`s the attacker-controlled `to` bytes into a fixed `[u8; 20]` buffer for `H160::from_slice`-style conversion path — but more precisely, in the `on_accept` handler's non-signature branch, `account.copy_from_slice(from_bytes)` is called on a substrate-destination path with no length check on `from_bytes`, and the length branch guarding `sender_bytes.copy_from_slice` in `on_timeout` only handles exactly 32/20 byte cases explicitly, erroring otherwise — this part is actually already length-checked. However, the sibling non-substrate branch in `on_accept` (`account.copy_from_slice(from_bytes)` at line 184) has **no length check at all**.

### Finding Description
In `on_accept` (reached when a `PostRequest` addressed to this module's registered contract carries optional calldata with no signature), the code builds the dispatch origin from the request's `from` field:
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]));
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
``` [1](#0-0) 

`message.from` is decoded from the ABI-encoded `body` of an inbound `PostRequest` — fully attacker/relayer-controlled bytes, since `Message::abi_decode(&body)` only validates ABI shape, not field lengths beyond the dynamic `bytes` type's own encoding. When `source` is a non-EVM (substrate) state machine and no signature is present, `account.copy_from_slice(from_bytes)` requires `from_bytes.len() == 32` exactly; any other length (0, 19, 33, etc.) makes Rust's `copy_from_slice` panic with a length-mismatch assertion, since the destination is a fixed `[u8; 32]` array. This directly parallels the GhostScript bug class: a size mismatch between attacker-supplied data and a fixed-size buffer that the code writes into without validating.

Similarly, the EVM branch does `&from_bytes[from_bytes.len() - 20..]`, which underflows/panics if `from_bytes.len() < 20`.

### Impact Explanation
A panic inside `on_accept`, which executes during ISMP message dispatch/handling (`pallet_ismp::Pallet::execute` → router → module `on_accept`), aborts the runtime call in the middle of state mutation. Substrate/FRAME wraps dispatchables so a panic here typically unwinds and gets caught by the executive at the top level (as a `PanicPayload`/`TransactionOutcome` in most builds), but if reached in an `on_finalize`/inherent context or through paths not covered by panic-catching wasm execution, it can produce a block-execution failure — effectively a routable-message class that can never be delivered (permanent DoS for that message and potentially for the block producer, since panicking runtime code is the highest-severity crash class available on-chain). Even bounded to "message can never be delivered," this satisfies the required impact bar of "a route unable to deliver messages," since the crafted request would need retrying or filtering out entirely, and any relayer that includes it in a batch risks the whole batch's execution.

### Likelihood Explanation
Reaching this path requires only: (1) the destination contract on the source chain being registered via `ContractToAsset` for a real asset (a normal, permissionless bridging config), (2) a `PostRequest` with `data` set that decodes to `SubstrateCalldata` with `signature: None`, and (3) `message.from` of any length other than exactly 32 bytes when the request's `source` is a substrate state machine. Any relayer or user able to submit/relay an ISMP `PostRequest` to a registered HFT contract address can trigger this — no privileged role needed. This is a straightforward, low-effort crafted-message DoS, but exploitability is gated on running actual HFT-registered token deployment coupled with a substrate destination chain, and I have not been able to fully trace all intermediate guards (e.g., whether the ISMP router itself imposes any additional relaying/authentication constraints or whether Substrate's WASM executor catches panics before block finalization) — that final blast-radius nuance would need to be confirmed by a Devin session with full build/test access.

### Recommendation
Length-check `from_bytes.len() == 32` (mirroring the existing pattern already used in `on_timeout` and in the `on_accept` beneficiary conversion above it) before calling `copy_from_slice`, returning a typed error like `HftError::InvalidSenderLength` instead of panicking. Likewise, bound-check the EVM branch's `from_bytes.len() >= 20` before the subtraction/slice.

### Proof of Concept
1. Register an HFT contract mapping for `source = Polkadot(_)` (or any substrate state machine) pointing to a valid `local_asset_id`.
2. Craft a `PostRequest` whose ABI-encoded `body` decodes to a `Message` with:
   - `to`: valid 20 or 32 bytes (so the beneficiary conversion succeeds),
   - `data`: SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <any valid call> }`,
   - `from`: a byte string of length ≠ 32 (e.g., 31 or 33 bytes).
3. Deliver this `PostRequest` through the ISMP handler to the registered module.
4. Execution reaches `let mut account = [0u8; 32]; account.copy_from_slice(from_bytes);` at [2](#0-1) , which panics because `from_bytes.len() != 32`.
