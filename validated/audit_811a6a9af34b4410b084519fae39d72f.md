### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only and then trusts the header-derived `shop` value when invoking the app's webhook handler, breaking the intended equality "shop authenticated by HMAC == shop acted on by the handler."

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` from the `x-shopify-shop-domain`/`shopify-shop-domain` header: [1](#0-0) 

but the signable content used for HMAC verification is only the raw body: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which calls `to_signable_string`, i.e. body-only) and, once that passes, forwards `request.shop` straight into `WebhookMetadata` for the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever compares the HMAC against `verifiable_query.to_signable_string`, so any header not embedded in that string — including `shop` — is never covered by the signature: [4](#0-3) 

Because the HMAC secret (`api_secret_key`/`client_secret`) is per-app rather than per-shop, any store that has legitimately installed the app can generate an arbitrary body with a valid signature (by triggering any event on its own store, e.g. renaming a product to attacker-controlled JSON-safe content) and then replay that exact `body + hmac` pair to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Registry.process` will accept the request as valid (body HMAC matches) and hand the handler a `WebhookMetadata` claiming the event originated from the victim shop, even though nothing about the shop identity was cryptographically verified.

### Impact Explanation
This breaks the identity binding "verified sender == acted-upon tenant," letting one unprivileged app-installing merchant impersonate webhook traffic for a different, unrelated shop that also installed the same app. Any host application that uses `data.shop` from `WebhookMetadata` to select which tenant's data/session to act on (updating records, dispatching background jobs keyed by shop, etc., exactly as shown in this gem's own documentation example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be tricked into performing actions against the wrong tenant, i.e. cross-tenant access/injection of forged tenant-scoped events — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires no special credentials beyond being any legitimate (even free/trial) merchant who installs the target app on their own store — an "unprivileged internet user" relative to other tenants of the same app. They can trigger events on their own store to obtain valid `(body, hmac)` pairs, then simply resend the POST to the app's public webhook URL with a different `shop-domain` header. No access token, `api_secret_key`, or TLS interception is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) values into the signed content, or otherwise validate the `shop-domain` header against a value derived from data actually covered by the HMAC (e.g., require host apps to look up whether that shop actually has a matching webhook subscription id and treat mismatches as invalid) before trusting `WebhookMetadata#shop`. At minimum, document clearly that `shop` is unauthenticated and must be independently corroborated (e.g., against `webhook_id`-to-shop mappings recorded at registration time) before being used for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook-generating action (e.g., updates a product) so Shopify sends a legitimately signed webhook: `body = B`, header `x-shopify-hmac-sha256 = HMAC(client_secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same `body=B` and `x-shopify-hmac-sha256` header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate` over `to_signable_string` (`= B`), which matches, so validation passes; the handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, letting the attacker inject fabricated webhook data attributed to a shop they do not control.
