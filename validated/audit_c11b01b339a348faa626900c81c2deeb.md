### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read verbatim from HTTP headers without being part of the signed payload. `Registry.process` validates only the body's HMAC and then dispatches to handlers using the unauthenticated `shop` header value.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and exposes: [1](#0-0) 

specifically: [2](#0-1) 

Here `hmac` is derived from the `hmac-sha256` header, and `to_signable_string` returns `@raw_body` alone — it does not include `shop`, `topic`, `webhook_id`, or `api_version`. Compare this to the OAuth callback path, `AuthQuery#to_signable_string`, which explicitly includes `shop` (and `host`) in the signed string: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC over exactly `verifiable_query.to_signable_string` using `Context.api_secret_key`: [4](#0-3) 

`Registry.process` then checks only this body HMAC before dispatching the handler with the unauthenticated `shop`/`topic`/`webhook_id` values pulled straight from headers: [5](#0-4) 

The identity binding broken here is: `shop authenticated by HMAC == shop the handler is told to act on`. In this gem, `client_secret` (used to compute the HMAC) is shared across every shop that installs the app — it is not shop-specific. So a valid `(raw_body, hmac)` pair only proves "this body was signed by the app's secret," not "this body originated from shop X." Because `shop` is excluded from the signable string, any two shop headers can be paired with the same signed body and both will pass `HmacValidator.validate`. A party who can obtain one valid `(body, hmac)` pair for the app (e.g., via their own store's legitimately-delivered webhook, a replay, or an SSRF/queue misconfiguration on the delivery side) can present it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header and it will still validate, causing `WebhookMetadata.shop` to report an attacker-chosen shop while `Registry.process` never re-derives or checks the shop against anything the HMAC actually covers.

### Impact Explanation
This breaks the tenant isolation guarantee this gem is supposed to provide the host application for webhook processing. Because `data.shop` (built purely from an unauthenticated header) is the only shop identity signal `Registry.process` gives to the handler, host applications that trust it (as the gem's own docs/tests imply is the sanctioned identifier) can be made to write attacker-controlled webhook payloads into a victim shop's record, or process the payload with victim-shop scoped side effects — a cross-tenant data-integrity/isolation break rooted entirely in this gem's `Request`/`Registry` code, not application misuse.

### Likelihood Explanation
This requires the attacker to already have a route to obtain one validly-signed `(body, hmac)` pair (e.g. control of their own shop's webhook delivery, or a replay of a captured delivery), which is a real, low-barrier condition — merchants naturally receive genuinely signed webhooks for their own store's events. No secret material, TLS interception, or privileged account is needed; only a signed body that happens to also validate under a spoofed shop header.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signed string used for webhook HMAC verification, or independently re-validate `shop` against Shopify per delivery (Shopify's official verification only signs the body per their spec, so the fix should instead be to never let `Registry.process`/handlers treat the header-derived `shop` as authenticated — require host apps to cross-check `webhook_id`/topic against their own registered subscription record, or document/enforce that `shop` must be independently corroborated, e.g. by matching against a known/installed shop list) before any state mutation keyed on that `shop` occurs.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and configures a webhook topic (e.g. `orders/create`) whose body they can influence (fields like `note`, line item titles, etc.).
2. Shopify delivers the webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <hmac(body, secret)>`, and the attacker-influenced JSON body.
3. Attacker captures this exact `(raw_body, hmac)` pair (e.g. by pointing at an endpoint they control that echoes it back, or intercepting their own inbound traffic which they legitimately can).
4. Attacker replays the identical body and `hmac` header to the real app endpoint but swaps `x-shopify-shop-domain` to `victim.myshopify.com`.
5. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body against the secret; `Registry.process` in `lib/shopify_api/webhooks/registry.rb:189-199` dispatches to the handler with `shop: "victim.myshopify.com"`, and any handler logic keyed on `data.shop` now operates on the victim's tenant using attacker-supplied content.
