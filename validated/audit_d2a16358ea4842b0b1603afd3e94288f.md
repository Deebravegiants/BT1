### Title
Webhook `shop`, `topic`, `webhook-id`, and `api-version` fields are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. However, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, meaning the `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers are never part of the signed material. `Registry.process` nonetheless uses these unauthenticated header values to select the handler and to populate `WebhookMetadata` (including `shop`), which is passed directly to the application's handler logic.

### Finding Description
The identity binding that should hold is: `shop header used by handler == shop that the HMAC actually authenticates`. In this implementation that equality does not hold, because the HMAC is computed only over the body: [1](#0-0) [2](#0-1) [3](#0-2) 

`HmacValidator.validate` verifies `received_signature` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. only the body bytes: [4](#0-3) 

`Registry.process` then trusts `request.topic` for handler dispatch and forwards `request.shop`, `request.webhook_id`, and `request.api_version` — none of which are covered by the signature — straight into the handler: [5](#0-4) 

Because only the body is authenticated, an attacker who legitimately installs the app on their own (attacker-controlled) shop can capture one genuine, validly-signed webhook delivery (valid `body` + valid `x-shopify-hmac-sha256`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain (and/or an arbitrary `topic`/`webhook-id`). `HmacValidator.validate` still succeeds because the body bytes are unchanged, so `Registry.process` will dispatch the forged request to the registered handler with `WebhookMetadata#shop` claiming to be the victim tenant.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (or `#topic`/`#webhook_id`) to key merchant-specific business logic (e.g., updating a specific tenant's order/inventory records, revoking access, looking up sessions by shop) can be made to act on the wrong tenant using attacker-supplied, unauthenticated header data. This breaks the shop-identity binding the HMAC is meant to guarantee and constitutes cross-tenant access/data confusion — the field driving tenant-scoped handling (`shop`) is not the field the cryptographic check actually authenticates (`body`).

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on any shop the attacker controls to obtain one valid signed webhook (a normal, unprivileged action available to anyone who can create a Shopify dev/trial store), and (2) sending a raw HTTP POST with attacker-chosen headers to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is required, matching the in-scope "unprivileged internet user" threat model.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` header values in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g. by validating them against a value independently looked up via a prior API call keyed to a value that *is* authenticated), so that `Registry.process` cannot be made to attribute a webhook body to an arbitrary shop or topic.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (free/unprivileged action).
2. Shopify delivers a legitimate webhook to the app, e.g.:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   body: {"id": 1, ...attacker-controlled order payload...}
   ```
3. Attacker captures this raw body and its valid `x-shopify-hmac-sha256` value.
4. Attacker sends a new POST to the app's webhook endpoint reusing the identical body and HMAC header, but sets:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) succeeds because it only checks the body bytes.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from and describes `attacker-shop`.
