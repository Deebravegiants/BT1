## Finding

### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone drain tokens left stranded in the shared dispatcher by `IntentGatewayV2`/`HyperFungibleToken` swap flows - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is the exact "arbitrary-call" primitive the WatchPug report warns about: an `external` function that blindly forwards attacker-supplied `to`/`data`/`value` via `to.call{value: call.value}(call.data)`, with **no caller restriction whatsoever**. Unlike the Tally `Swap.sol` case (where the risk was stolen *user allowances*), here the risk is stolen *protocol-held dust*: `IntentGatewayV2` and the `HyperFungibleToken`/`WrappedHyperFungibleToken` apps route escrowed/minted tokens through this single shared `CallDispatcher` instance to execute swaps, but only sweep back the tokens explicitly listed as order outputs/inputs — any other token balance the swap produces (or ETH slippage remainder) is left sitting in the dispatcher indefinitely. Because `dispatch()` has no access control, any address can call it directly to move that stranded balance to itself.

### Finding Description
`CallDispatcher.dispatch` decodes an attacker-controlled `Call[]` and executes each call from the dispatcher's own context: [1](#0-0) 

There is no `onlyGateway`/`onlyHost`/allow-list check — any EOA or contract can call `dispatch(bytes)` directly on the deployed `CallDispatcher` singleton with arbitrary `Call[]` targeting arbitrary contracts.

`IntentGatewayV2` and the token bridge apps use this same shared, persistent `CallDispatcher` as an intermediate holder of user/protocol funds during predispatch/postdispatch composable execution:
- Predispatch: assets are transferred to the dispatcher, arbitrary swap calldata is executed, then only the tokens matching `order.inputs`/`order.output.assets` are swept back: [2](#0-1) 
- Postdispatch sweep in `_execute` only iterates over `outputsLen` (i.e., `order.output.assets.length`) — any token balance left on the dispatcher that isn't one of the declared output tokens is never swept and is not accounted for: [3](#0-2) 
- The `WrappedHyperFungibleToken` calldata-execution pattern explicitly documents unlocking/minting funds **to the `CallDispatcher` address itself** before running follow-up calls, meaning the dispatcher transiently (and, on partial/odd swap outcomes, potentially permanently) holds real user value: [4](#0-3) 

Because the sweep logic only returns the *declared* output/input tokens, any calldata path where the swap produces a different token than declared (rounding remainders, an unexpected multi-hop swap output, partial fill leftovers, or a malicious/misconfigured solver's `output.call` that intentionally swaps into an undeclared token) leaves a nonzero balance parked on the `CallDispatcher`. Since `dispatch()` is callable by anyone, an attacker simply calls `CallDispatcher.dispatch(abi.encode([Call({to: strandedToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` to sweep that balance to themselves — precisely the "arbitrary call, then `transferFrom`/`transfer` an asset the attacker doesn't own" pattern from the H-01 report, except here the asset is protocol/user-owned funds resting in a shared, address-stable contract rather than a per-order escrow.

### Impact Explanation
Any value left in the `CallDispatcher` — from failed sweeps, non-output swap byproducts, dust, or funds routed to the dispatcher address as an intermediate `to` in HFT/WHFT calldata execution — can be stolen by any unprivileged third party by directly invoking `dispatch()`. Because `CallDispatcher` is a single long-lived contract address referenced by multiple apps (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`) across many independent orders/transfers, stranded balances from unrelated users/orders accumulate at the same address, making this a shared attack surface rather than a one-off per-order risk. This is a concrete theft-of-funds vector (Medium/High depending on realistic dust magnitude and whether solvers can be induced to swap into undeclared tokens).

### Likelihood Explanation
`dispatch()` is public and requires no proof, signature, or state to invoke — likelihood of exploitation is bounded only by whether/how often non-output-token residue or ETH slippage remainder accumulates on the dispatcher (e.g., via `predispatch`/`output.call` swap paths that don't perfectly match declared assets, or `WrappedHyperFungibleToken` calldata flows unlocking to the dispatcher address). Any attacker can passively monitor the dispatcher's token/ETH balances and call `dispatch()` the moment a nonzero balance appears.

### Recommendation
- Restrict `CallDispatcher.dispatch` to be callable only by the trusted caller for the current call (e.g., pass the intended caller/gateway and check `msg.sender`, or make the dispatcher single-use/ephemeral per invocation via `create2`/clone-and-destroy rather than a persistent shared contract holding cross-order balances).
- Generalize the sweep logic in `IntentsBase._execute`/`IntentGatewayV2` predispatch handling to sweep the dispatcher's *entire* balance of any token touched by the executed calldata (not just the declared input/output tokens), or explicitly forbid dust from being anything other than the declared output/input token.
- Ensure the `CallDispatcher` never holds value across transaction boundaries; verify pre/post balances are zero for any token or ETH not explicitly expected to remain.

### Proof of Concept
1. A solver's `order.output.call` (executed via `ICallDispatcher(dispatcher).dispatch(order.output.call)` in `IntentsBase._execute`) performs a swap that, due to slippage/path choice, yields a small amount of an undeclared token `X` in addition to the declared `order.output.assets`.
2. `_execute`'s sweep loop only iterates `order.output.assets` (`outputsLen`), so the `X` balance is never swept off the `CallDispatcher` and is never reflected in any `DustCollected` accounting: [5](#0-4) 
3. Attacker (anyone, no privilege) calls `CallDispatcher.dispatch(abi.encode(calls))` directly where `calls = [Call({to: X, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(X).balanceOf(dispatcher))})]`, using the unrestricted entrypoint: [6](#0-5) 
4. The full balance of token `X` is transferred to the attacker, with no relation to any order the attacker placed or filled.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Calldata Execution

Pass a non-empty `data` field to execute arbitrary calls on the destination chain after tokens are unlocked. The `data` must be an ABI-encoded `Call[]` array (see [overview](/developers/evm/hyper-fungible-token/overview#calldata-execution) for the full `Call` struct and security details).

When `isWeth = true`, the WrappedHFT unwraps WETH to native ETH on receive. This example bridges WETH back to the home chain, where it's unwrapped to native ETH and swapped for an exact amount of USDC via UniswapV2. The `Call.value` field forwards the native ETH to the router — demonstrating that the `CallDispatcher` can hold and forward native tokens:

address[] memory path = new address[](2);
path[0] = WETH;
path[1] = USDC;

Call[] memory calls = new Call[](1);

// Swap native ETH → exact USDC via UniswapV2
