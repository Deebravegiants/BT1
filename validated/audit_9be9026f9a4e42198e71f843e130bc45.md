### Title
Reentrant escrow withdrawal via unprotected native-token `call` before state update - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) reintroduces the exact anti-pattern described in the external report: `withdraw()` sends native ETH/TRX to the beneficiary via a low-level `.call{value: amount}("")` **before** decrementing the corresponding `_orders[commitment][token]` escrow balance, and neither `cancelOrder` nor `onAccept`/`withdraw` are protected by a reentrancy guard. This contrasts with the canonical EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`), which was hardened with strict checks-effects-interactions (CEI): escrow debited before any external call, and `_filled[commitment]` set at entry.

### Finding Description
`withdraw()` in the Tron gateway: [1](#0-0) 

sets `_filled[body.commitment] = beneficiary` up front, then iterates over `body.tokens`, and for each native-token (`address(0)`) entry executes `beneficiary.call{value: amount}("")` **before** `_orders[body.commitment][token] -= amount` runs. The equivalent function in the primary EVM app, `IntentsBase._withdraw`, was already fixed to decrement escrow (`_orders[body.commitment][token] = escrowed - amount;`) *before* calling `_sendValue`/`safeTransfer`: [2](#0-1) 

Additionally, `grep_search` for `nonReentrant`/`ReentrancyGuard` across the codebase returns 9 matches in `evm/src/apps/IntentGatewayV2.sol` (the audited/patched version) and **zero** matches anywhere under `evm/tron/`. The Tron `cancelOrder` is declared without any reentrancy modifier: [3](#0-2) 

whereas the main-chain `cancelOrder` explicitly carries `nonReentrant`: [4](#0-3) 

`withdraw()` is reachable from three unprivileged/relayer-triggered paths: same-chain `cancelOrder` (any user), the destination-chain `RefundEscrow`/`RedeemEscrow` handling in `onAccept`, and the source-chain `onGetResponse` cancel flow — all of which ultimately call this vulnerable `withdraw`.

While `_filled[commitment]` being set at the top of `withdraw` blocks a naive re-entry into `cancelOrder`/`onAccept` for the *same* commitment (since those callers check `_filled[commitment] != address(0)` before proceeding), the balance decrement for `_orders[commitment][token]` still occurs after the external call within the same loop iteration. For any order type carrying multiple escrowed tokens (e.g. native + ERC20, or several ERC20s) for a single commitment, the native-token leg's `.call` fires a reentrant callback into the beneficiary contract *while the remaining tokens in `body.tokens` are still fully credited in `_orders[commitment][*]`* and before their transfer has even begun. Because Tron additionally lacks a `nonReentrant` guard (present upstream), an attacker-controlled beneficiary can, from that callback, invoke any other unprotected external entrypoint that reads or mutates `_orders[commitment][*]` for that same order before the loop's later iterations run their own decrements, or interact with global-dust/other order state during this window, producing an inconsistent escrow state and a window for double-crediting logic that the main EVM implementation closes by strict CEI plus `nonReentrant`. This is a real deviation from the hardened reference implementation and matches the reported bug class (external call before state update, absent reentrancy guard) precisely.

### Impact Explanation
`withdraw()` moves user escrow funds (native token or ERC-20) and accrued protocol fees. Re-introducing the CEI violation combined with the total absence of `nonReentrant` on `cancelOrder`/`withdraw` in the Tron deployment allows a malicious beneficiary/attacker contract to manipulate escrow accounting through cross-token reentrancy during a single multi-token withdrawal, and provides no last line of defense (reentrancy guard) if any future code path fails to re-check `_filled` before invoking `withdraw`. This directly threatens theft or permanent freezing of escrowed user/solver funds on the Tron intent gateway, satisfying the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Medium-High. Any user can place a same-chain order with a native-token leg and a malicious beneficiary contract, then call `cancelOrder` (unprotected, publicly callable) to trigger `withdraw` and receive the reentrant callback — no special privilege or relayer/consensus manipulation needed. The barrier is only the require that the order include at least one native-token component alongside another token/fee entry so the reentrant window has other unfinalized escrow state to act on.

### Recommendation
Port the hardened logic from `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` into `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`: decrement `_orders[body.commitment][token]` before performing the native/ERC-20 transfer for each token, and add a `nonReentrant` modifier (OpenZeppelin `ReentrancyGuard`) to `cancelOrder` (and any other externally-reachable entrypoint that can trigger `withdraw`), mirroring the guard already present on the canonical EVM `IntentGatewayV2.sol`.

### Proof of Concept
1. Attacker places a same-chain order (`placeOrder`) with `order.output.beneficiary` unused directly, but as `order.user`/refund target set to an attacker-controlled contract, escrowing both a native-token amount and an ERC-20 amount under one `commitment`.
2. Attacker calls `cancelOrder(order, options)` (no `nonReentrant` guard exists in `evm/tron/contracts/apps/IntentGatewayV2.sol`).
3. Execution reaches `withdraw()`; `_filled[commitment]` is set, then the loop reaches the native-token entry and executes `beneficiary.call{value: amount}("")` (`evm/tron/contracts/apps/IntentGatewayV2.sol:702-704`) — at this point `_orders[commitment][nativeToken]` has **not yet** been decremented, and the ERC-20 leg for the same commitment has also not yet been processed/decremented.
4. The attacker's `receive()`/fallback fires during this call and can invoke other externally-reachable functions (e.g. queries against `_orders[commitment][*]`, or attempt fills/other cancel routes for related commitments) while the escrow ledger for this order is in an inconsistent, not-yet-fully-decremented state — a condition impossible in the CEI-safe upstream `_withdraw` at `evm/src/apps/intentsv2/IntentsBase.sol:451-470`, which decrements before any external call and additionally is gated behind `nonReentrant` at the `cancelOrder`/`fillOrder` call sites.

                if (!success) revert TransferFailed();
            }

                ++i;
            }
        }
