### Title
Webhook `shop` (and other identity headers) not covered by HMAC signature allows cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers from the HMAC-verified data. `Utils::HmacValidator` and `Webhooks::Registry.process` treat a valid HMAC as proof that the *entire request*, including `request.shop`, came from Shopify, but the signature only binds the body bytes. This breaks the equality: `bytes verified == bytes parsed` — the verified bytes are `raw_body` only, while the parsed/acted-upon identity includes the unauthenticated `shop-domain` header.

and `shop` is read straight from an HTTP header with no relation to the signed bytes: [2](#0-1) 

`HmacValidator.validate` verifies the received HMAC against `to_signable_string` (i.e. the body only): [3](#0-2) 

`Registry.process` uses this HMAC check as its sole authentication gate, then immediately trusts `request.shop` (and `request.topic`) to build the metadata handed to the app's handler: [4](#0-3) 

The webhook signature is computed with the app's single `api_secret_key`, shared across *every* shop that installs the app — it is not shop-specific. Since `shop-domain` is excluded from the signed bytes, any `(raw_body, hmac)` pair that is valid for one shop is valid, byte-for-byte, for a request claiming to be from any other shop.

### Impact Explanation
An unprivileged internet user who controls their own Shopify store with the same app installed can legitimately trigger a webhook (e.g. `orders/create`) and capture the genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair Shopify sends. Because `shop-domain` isn't part of the signed content, they can replay that exact body+signature to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (the body/signature pair is genuinely valid), and `Registry.process` passes the attacker-controlled `shop` value into `WebhookMetadata` as the trusted tenant identity for the handler. This is a cross-tenant confusion: the app processes attacker-supplied data (or attacker-timed replay of their own data) as though it belongs to another merchant's shop, which can corrupt per-shop state, trigger shop-scoped side effects, or leak data attribution across tenants — matching the "cross-tenant access" critical-impact category.

### Likelihood Explanation
Exploitation only requires an attacker to install the target app on any shop they control (a normal, unprivileged action available to any merchant) and observe one legitimate webhook delivery — no leaked secrets, tokens, or elevated access are needed. The replay itself is a trivial HTTP POST with a modified header.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed content used by `to_signable_string`, or otherwise cryptographically bind the `shop` value to the signed payload before it is trusted downstream in `Registry.process`. At minimum, document that host applications must independently verify `request.shop` belongs to a shop with an active installation/session before acting on it, since this gem's HMAC check does not cover that field.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g., creates an order) and captures the raw request: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC(api_secret_key, B)`).
3. Attacker resends the identical `B`/`H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC(api_secret_key, B)`, which still equals `H` — validation passes.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and invokes the app's handler, which now processes attacker data under the victim shop's identity.
