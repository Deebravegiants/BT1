### Title
HOT Bridge falsely reports withdrawal as "completed" when the contract returns an unrecognized status value - (File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts)

### Summary
The Ajna report's underlying bug class is: a status/outcome reported by the system does not match what actually happened on-chain, causing incorrect downstream state (blocked or, in the credit-checking category, wrongly-confirmed actions). The closest reachable analog in this repo's scope is in `HotBridge.describeWithdrawal`, where a withdrawal is unconditionally reported as `"completed"` based on an unrecognized/garbage contract-status value, without any on-chain confirmation of a destination transfer.

### Finding Description
`HotBridge.describeWithdrawal` polls `hotSdk.getGaslessWithdrawStatus(nonce)` for the withdrawal's on-chain contract status [1](#0-0) . For non-EVM/non-Stellar/non-TON landing chains, it falls into this "fallback" branch:

```
if (status === HotWithdrawStatus.Completed) {
    return { status: "completed", txHash: null };
}
if (typeof status === "string") {
    // HOT returns hexified raw bytes without 0x prefix, any other value should be ignored.
    if (!isHex(status)) {
        args.logger?.warn("HOT Bridge incorrect destination tx hash detected", { value: status });
        return { status: "completed", txHash: null };
    }
    return { status: "completed", txHash: formatTxHash(status, args.landingChain) };
}
``` [2](#0-1) 

The comment explicitly states that a non-hex string value "should be ignored" — yet the code does the opposite: it logs a warning and still returns `{ status: "completed", txHash: null }`, i.e. it reports the withdrawal as finished. This breaks the equality that **the reported status must reflect the verified on-chain outcome**: an unparseable/invalid value from the bridge contract is not proof that the destination transfer executed, but it is treated identically to a genuinely completed withdrawal (the same code path used for `HotWithdrawStatus.Completed`).

This contrasts with the parallel EVM/Stellar/TON code path in the same function, which explicitly falls back to the bridge indexer/HOT API and returns `"pending"` when the response is invalid or unverifiable [3](#0-2) , and is exercised by tests such as `"ignores API response with invalid hash format"` which correctly asserts `{ status: "pending" }` for the analogous invalid-hash case in the EVM branch [4](#0-3) . No equivalent test exists for the non-EVM branch's invalid-status case; it is untested and inconsistent with the safer pattern used elsewhere in the same file.

`describeWithdrawal`'s result feeds directly into `watchWithdrawal`, which treats `"completed"` as terminal and stops polling [5](#0-4) , and into `sdk.createWithdrawalCompletionPromises` / `waitForWithdrawalCompletion`, which integrators use to decide when to credit or release funds tied to a withdrawal [6](#0-5) .

### Impact Explanation
An integrator relying on the SDK's withdrawal-completion signal (`describeWithdrawal` / `watchWithdrawal` / `waitForWithdrawalCompletion`) for a non-EVM/non-Stellar/non-TON HOT bridge withdrawal (e.g. Solana, NEAR-adjacent chains) can be told the withdrawal is `"completed"` purely because the on-chain contract returned an unrecognized status string, with no destination transaction hash to verify against. If the actual destination transfer did not happen (or happens later/differently), the integrator may prematurely credit the user or release dependent funds — this matches the High-impact category "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This path triggers whenever `getGaslessWithdrawStatus` returns any string that is neither the `Completed` sentinel nor valid hex, for a non-EVM/Stellar/TON landing chain — i.e., any unexpected/garbage/future-format value from the HOT bridge contract. This does not require attacker privilege; it can occur from bridge contract upgrades, unexpected value encodings, or transient anomalies, and the code comment itself acknowledges this value should be treated as untrustworthy, yet the implementation marks it as final success instead of `"pending"`.

### Recommendation
In the `typeof status === "string" && !isHex(status)` branch, return `{ status: "pending" }` (mirroring the EVM/Stellar/TON handling and the code's own comment that such values "should be ignored") instead of `{ status: "completed", txHash: null }`, and only report `"completed"` when a verifiable destination hash or the explicit `HotWithdrawStatus.Completed` sentinel is available.

### Proof of Concept
1. A withdrawal targets a HOT-bridge-supported chain that is not EVM, Stellar, or TON (falls into the `else` fallback branch) [7](#0-6) .
2. `hotSdk.getGaslessWithdrawStatus(nonce)` returns an arbitrary non-hex string (not `HotWithdrawStatus.Completed`, not valid hex) — e.g., due to a contract format change or malformed response.
3. `describeWithdrawal` hits the `!isHex(status)` branch and returns `{ status: "completed", txHash: null }` [8](#0-7) .
4. `watchWithdrawal` immediately resolves with `{ hash: null }` as a final, non-retryable success [5](#0-4) , and any integrator awaiting `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` treats the withdrawal as settled and credits accordingly — with no txHash to verify the claim against the destination chain.

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
