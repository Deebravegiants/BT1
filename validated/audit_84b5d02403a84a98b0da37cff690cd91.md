### Title
Missing validation of `amount`/`to` in `HyperFungibleToken.send()` and `WrappedHyperFungibleToken.send()` allows undeliverable/fund-losing cross-chain transfers - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.send()` and `WrappedHyperFungibleToken.send()` are unprivileged, user-callable entry points that burn/lock tokens and dispatch a cross-chain ISMP POST request. Neither function validates `params.amount > 0` nor `params.to != 0` before committing the source-side action (burn/lock) and dispatching the message, mirroring the Chakra `handler_erc20::cross_chain_erc20_settlement()` bug class where `to_token`, `to`, and `amount` were left unchecked.

### Finding Description
`send()` in `HyperFungibleToken.sol` immediately burns the caller's tokens and builds/dispatches the request without checking the recipient or amount: [1](#0-0) 

`_buildDispatchPost()` only validates that the destination chain is supported — it does not check `params.to` or `params.amount`: [2](#0-1) 

On the destination side, `onAccept()` decodes the message and mints to `beneficiary = _toAddr(message.to)`: [3](#0-2) 

If `params.to` is `bytes32(0)`, `beneficiary` resolves to `address(0)`; the downstream ERC20 `_mint(address(0), amount)` call reverts unconditionally (standard OZ `_mint` guards against the zero address). Because `onAccept` is invoked by the host's request-handling path and must succeed for the request to be marked handled, this makes the specific POST request permanently undeliverable on the destination chain — the tokens are already burned on the source chain in `send()` before the dispatch occurred, so the user's funds are stuck until a timeout is proven and refunded via `onPostRequestTimeout` (if that path exists and works), or lost if not reclaimed.

If `params.amount == 0`, the request is dispatched and must still be delivered/verified by relayers (wasting relayer/validator resources, exactly as flagged in the original Chakra report) for a message that transfers nothing.

The exact same pattern (lock instead of burn, but same missing checks) exists in `WrappedHyperFungibleToken.sol`: [4](#0-3) 

and in the upgradeable variant: [5](#0-4) 

### Impact Explanation
- **Zero `amount`**: wastes relayer resources signing/delivering a message that moves zero value; low-cost griefing but still a real invariant break for a "valid amount" precondition.
- **Zero `to` (recipient)**: burns/locks the caller's tokens on the source chain, then dispatches a request whose destination-side handling (`_mint`/`safeTransfer` to `address(0)`) reverts, making that specific cross-chain message permanently undeliverable through the normal accept path. This satisfies the "route unable to deliver messages" acceptance criterion — the message can only be recovered (if at all) through the timeout/refund path, which requires an additional relayed timeout proof and is not guaranteed to exist for every deployment, effectively freezing the user's funds for at least the full timeout window.
- This is reachable by any unprivileged caller of `send()` — no privileged role is required, matching the "single submitted transaction" criterion.

### Likelihood Explanation
Likelihood is moderate: it requires either a caller supplying `to = 0`/`amount = 0` by mistake (e.g., a buggy integrator or wallet), or a malicious caller deliberately griefing relayer resources with zero-amount transfers, or deliberately burning another griefing vector's funds. Since these are user-facing SDK entry points with no client-side enforcement guarantee on-chain, the invalid state is fully reachable from a single external call.

### Recommendation
Add explicit validation in `send()` (and equivalently in `_buildDispatchPost()`/`onAccept()` as defense in depth) in both `HyperFungibleToken.sol` and `WrappedHyperFungibleToken.sol` (and their upgradeable counterparts):
```solidity
require(params.amount > 0, "Amount must be greater than 0");
require(params.to != bytes32(0), "Invalid recipient");
```
placed before the burn/lock and dispatch calls, so that invalid transfers revert atomically instead of committing source-side state changes for a message that cannot be delivered.

### Proof of Concept
1. Caller invokes `HyperFungibleToken.send({dest: "EVM-X", to: bytes32(0), amount: 100, data: "0x", relayerFee: fee, timeout: t})`.
2. `send()` executes `_burn(msg.sender, 100)` unconditionally (line 265), then dispatches the POST request via `_buildDispatchPost()`, which performs no check on `to` (lines 237-256).
3. On the destination chain, `onAccept()` decodes `message.to = 0` and computes `beneficiary = address(0)` (lines 292-300); the subsequent mint to `address(0)` reverts.
4. The request handling fails on the destination chain — the message cannot be delivered through the normal path, while the caller's 100 tokens are already burned on the source chain, leaving them stuck pending a timeout-based refund (if configured) rather than immediately deliverable or immediately refundable.

    function _buildDispatchPost(SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

        _burn(msg.sender, params.amount);
