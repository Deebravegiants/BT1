### Title
Unvalidated swap route can inject caller-authorized token transfers and drain unrelated wallet funds - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller accepts opaque, caller-supplied `StrategySwap` bytes and forwards them to the configured aggregator without decoding or constraining the pool addresses they contain. The aggregator resolves pool and token addresses from that payload and calls the selected venue adapter. A malicious route can therefore place attacker-controlled contract code inside the victim's authorized controller invocation. Soroban records token calls requiring the victim's authorization as children of the signed `swap_collateral`/strategy authorization tree; simulation can consequently produce a poisoned tree that moves unrelated wallet tokens.

### Finding Description
`process_swap_collateral` accepts `swap` as caller-controlled data and passes it through `withdraw_and_swap_from_supply` after only checking caller authorization, market eligibility, and amount validity. The shared router helper rejects only an empty distinct-token route, authorizes exactly one controller-to-router input transfer, and invokes `router.execute_strategy(&controller, &amount_in, swap)` without inspecting the payload's embedded addresses. [1](#0-0) [2](#0-1) 

The aggregator derives `pool`, `token_in`, and `token_out` directly from the route's `assets` registry, then dispatches the selected venue against that pool address. [3](#0-2)  There is no venue or pool allowlist in the route execution path. [4](#0-3) 

A hostile pool contract invoked by an adapter can issue an unrelated `token.transfer(victim, attacker, amount)`. Soroban authorization makes that transfer execute only if it is present in the victim's signed authorization tree, but ordinary simulation records it there automatically. The repository's reproduction demonstrates this exact auth-tree poisoning: simulation records the rogue pool's wallet transfer beneath `swap_collateral`, and signing that generated tree lets the rogue transfer execute. [5](#0-4) [6](#0-5) 

### Impact Explanation
An unprivileged attacker can steal arbitrary unrelated tokens from a victim who submits a crafted strategy route and signs the authorization tree generated by simulation. The stolen assets need not be the strategy's input, output, collateral, debt, or any pool reserve. The attacker can preserve a valid measured swap output, so the controller's positive-output, overspend, and final-risk checks do not prevent the unrelated wallet transfer.

This is theft of user funds. The malicious behavior is not prevented by the controller's narrowly scoped contract authorization: that scope protects the controller's balance, while the vulnerability abuses the root caller's broader signed invocation tree.

### Likelihood Explanation
The attack requires the victim to submit an attacker-provided route and authorize the simulated transaction. Route payloads are opaque XDR supplied off-chain, and ordinary users rely on wallets or integrators to inspect the generated authorization tree. A route that produces an economically valid swap can conceal the extra token transfer among nested authorization entries.

No protocol role, delegate access, leaked key, compromised router, or protocol funds are required. The attacker supplies the route and deploys a malicious pool-compatible contract; the route itself directs the configured aggregator to call it.

### Recommendation
Do not let route bytes select arbitrary executable pool addresses. Decode the route at the controller or aggregator boundary and require every pool/venue pair to be present in a governance-managed allowlist. Token addresses must also be checked against the declared strategy input/output and validated pool metadata before invocation.

At minimum, aggregator dispatch should reject pool addresses absent from a pinned venue registry. The controller should reject opaque payload structures it cannot validate rather than forwarding them wholesale. Wallet UX mitigations that display nested authorization are useful but should not be the protocol boundary.

### Proof of Concept
1. The attacker deploys `RoguePool`, a contract implementing the invoked venue ABI. During the venue call it also executes:

```rust
token::Client::new(&env, &victim_wallet_token)
    .transfer(&victim, &attacker, &victim_balance);
```

2. The attacker gives the victim a `routeXdr` whose `assets` registry contains `RoguePool` and whose instruction selects that registry entry as the hop pool.
3. The victim calls:

```text
swap_collateral(
    caller = victim,
    account_id,
    current = legitimate_collateral,
    from_amount,
    new = legitimate_collateral,
    swap = routeXdr
)
```

4. The controller validates the account operation, authorizes only the exact controller input transfer, and forwards `routeXdr` to the configured aggregator.
5. The aggregator invokes `RoguePool`. The pool performs the unrelated wallet transfer and still returns/provides a valid measured swap output, so router and controller settlement checks pass.
6. Transaction simulation records the wallet transfer as a child of the victim's `swap_collateral` authorization. If the victim signs that generated tree, the rogue transfer executes and the unrelated wallet balance moves to the attacker.
7. The repository test confirms the two outcomes: an honest authorization tree rejects the rogue transfer, while the simulation-produced poisoned tree authorizes it and drains the wallet. [6](#0-5)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
