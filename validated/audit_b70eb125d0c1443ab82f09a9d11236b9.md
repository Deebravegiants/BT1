Webhook `shop` field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which validates the HMAC against `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only the raw body — the `shop` (and `topic`/`webhook_id`/`api_version`) values, which are taken straight from HTTP headers, are never included in the signed material. Yet the gem's own documented usage pattern treats `data.shop` as the trusted tenant identifier for dispatching post-webhook work.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`shop` is read directly, unauthenticated, from the `shop-domain` header: [2](#0-1) 

`Registry.process` verifies HMAC over that signable string and, if it passes, forwards `request.shop` verbatim into `WebhookMetadata` handed to the app's handler — with no separate binding check between the verified body and the `shop` header: [3](#0-2) 

Contrast this with `Auth::Oauth::AuthQuery`, which correctly includes `shop` inside `to_signable_string` so the HMAC binds `shop` to the rest of the signed OAuth callback parameters: [4](#0-3) 

Because the webhook path lacks the equivalent binding, `HMAC(api_secret_key, body) == HMAC(api_secret_key, body)` remains valid regardless of which `shop-domain` header value is attached to the request. The equality the app relies on — "the shop that produced this signed body" equals "the shop reported in `data.shop`" — is not enforced anywhere in the gem.

The gem's own documentation instructs developers to trust `data.shop` as the tenant key for further processing (e.g., enqueuing per-shop jobs), reinforcing that this is intended to be an authenticated field: [5](#0-4) 

### Impact Explanation
Any party that can obtain one validly-HMAC'd webhook body for the app (e.g., an attacker who has installed the app on their own shop and can intercept/replay the webhook delivered to their own registered endpoint) can resubmit that exact body to the app's shared webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to name a different, victim shop. `HmacValidator.validate` will still pass because the header is outside the signed payload, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop. Any host app that uses `data.shop` to select per-tenant state (session/access-token lookup, tenant-scoped data writes, job routing) as the docs suggest can be made to act on forged data attributed to a shop the attacker does not control — a cross-tenant confusion condition.

### Likelihood Explanation
Exploitation requires the attacker to control at least one shop where the app is installed (to receive a validly HMAC'd webhook for a body of their choosing) and the ability to replay that request to the shared webhook endpoint with a modified header. This is a realistic scenario for any public app with self-serve installs, since the `client_secret`/`api_secret_key` is shared across all shops of the app (not per-shop), so a genuinely-signed webhook obtained from one tenant is valid input to the endpoint for any other tenant claim.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed material for webhooks, mirroring what `Auth::Oauth::AuthQuery#to_signable_string` already does, or otherwise cross-check `request.shop` against an independently verified source (e.g., the webhook's registered callback/shop mapping) before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers a webhook.
2. Shopify delivers a legitimately HMAC-signed webhook to the attacker's endpoint with body `B` and header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical request (same body `B`, same `x-shopify-hmac-sha256`) to the app's shared webhook route, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes HMAC over `body` only and it matches, so `Registry.process` proceeds and calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, as shown in `lib/shopify_api/webhooks/registry.rb:198-199`.
