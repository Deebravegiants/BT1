### Title
Webhook `shop-domain` header is trusted for tenant dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity with `Utils::HmacValidator.validate`, but the signed payload (`to_signable_string`) is only the raw body. The `shop` (and `topic`/`webhook_id`/`api_version`) values that `Registry#process` uses to route the payload to per-tenant handler logic come from HTTP headers that are never included in the HMAC computation, breaking the binding between "bytes verified" and "identity acted on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `Request#shop` is read straight from an unauthenticated header: [2](#0-1) 

`Registry#process` validates the request purely via `HmacValidator.validate(request)` (which only checks the body/HMAC pair) and then immediately uses `request.shop` — the unverified header — to build the `WebhookMetadata` passed into the host app's handler: [3](#0-2) 

`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against `verifiable_query.hmac`, so it never touches `shop`, `topic`, or `webhook_id`: [4](#0-3) 

The equality that should hold is: `bytes_verified_by_hmac == bytes_that_determine_tenant_identity`. Here it does not — `bytes_verified_by_hmac = raw_body` while `tenant_identity = header["shopify-shop-domain"]`. Any request whose body+HMAC pair is valid for the shared `api_secret_key` (e.g., a genuine webhook delivery for the attacker's own shop, since the same API secret signs webhooks for every tenant of a given app) can have its `shop-domain` header rewritten to any other shop's domain without invalidating the signature, because that header sits entirely outside the signed content.

### Impact Explanation
Since the API secret key is shared across all shops installing the same app, an unprivileged holder of a legitimate webhook for their own shop (or anyone able to influence the HTTP headers reaching the app between Shopify and the app, e.g. via a proxy or gateway under their control) can produce a request with a valid HMAC over the body while asserting an arbitrary `shop-domain`. Handlers written against `WebhookMetadata#shop` (all mandatory GDPR handlers `shop/redact`, `customers/redact`, `customers/data_request`, and any custom handler) will process the payload under the wrong tenant's identity — this is a cross-tenant confusion/impersonation at the identity-binding layer that this gem is responsible for enforcing.

### Likelihood Explanation
High: no secret material beyond an app's own valid webhook delivery is required, only control over the header value that carries tenant identity, which is common when the app sits behind any reverse proxy/CDN/load balancer that does not itself pin these headers, or when the host framework merges headers from multiple sources.

### Recommendation
Include the tenant-identifying fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed payload used for HMAC verification, or, at minimum, verify equality between the header-derived shop and a trusted value (e.g., cross-check against the JSON body's own shop domain fields when present, or require an allowlist of source shops) before dispatching to handlers. At minimum, document that `to_signable_string` only covers the body and instruct implementers to independently authenticate the `shop-domain` header via a transport-level control (mutual TLS, static IP allowlist) rather than relying on `HmacValidator.validate` for tenant binding.

### Proof of Concept
```ruby
# Legitimate delivery for "attacker-shop.myshopify.com" produces body B and hmac H
# where H = HMAC-SHA256(api_secret_key, B). H depends only on B.

request = ShopifyAPI::Webhooks::Request.new(
  raw_body: B,
  headers: {
    "shopify-topic" => "customers/redact",
    "shopify-hmac-sha256" => H,          # unchanged, still valid for B
    "shopify-shop-domain" => "victim-shop.myshopify.com",  # swapped, not covered by H
    "shopify-webhook-id" => "any",
    "shopify-api-version" => "any",
  },
)

ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) passes because it only checks B against H.
# Handler receives WebhookMetadata with shop: "victim-shop.myshopify.com",
# even though the payload B and signature H were generated for a different shop.
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
