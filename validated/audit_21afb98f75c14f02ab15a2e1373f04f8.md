## Title
Hyper-fungible-token `on_accept` mints/transfers before optional calldata execution, and pallet-ismp deletes the request receipt on module failure — enabling unbounded double-minting via replay of a single valid request proof (analog of MultiversX CVE-2023-34458 "always increment" bug) - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`Pallet::on_accept` in `pallet-hyper-fungible-token` unconditionally mints/transfers the bridged amount to the beneficiary *before* attempting the optional calldata execution step, and returns an `Err` if that later step fails. [1](#0-0) [2](#0-1)  `pallet-ismp`'s request handler treats any `on_accept` error as "not delivered" and deletes the request receipt so the message "can be timed out" — i.e. so it can be retried. [3](#0-2)  Because the mint/transfer already ran and is not rolled back when the module call later returns `Err`, replaying the same still-valid state/membership proof for that request causes the token credit to repeat every time, as long as the embedded calldata is crafted to deterministically fail.

### Finding Description
The MultiversX advisory describes a case where a relayed operation's partial/failed effects (nonce increment) persisted despite the operation being considered "failed," enabling retried effects that shouldn't recur. The same defect class exists here, but with a stronger impact (asset duplication instead of nonce DoS):

1. `on_accept` first performs the fund transfer/mint to `beneficiary` unconditionally: [1](#0-0) 

2. It then optionally decodes and dispatches a `runtime_call` from `message.data`. If dispatch fails (bad call, filtered call, bad signature, etc.), the function returns an `Err` via `?`, well after step 1 has already run: [4](#0-3) 

3. `pallet-ismp`'s `handlers::request::handle` invokes `cb.on_accept(request.clone())`; on any `Err`, it deletes the previously-stored request receipt via `host.delete_request_receipt(&wrapped_req)?`, explicitly to allow the message to be retried/timed-out: [3](#0-2) 

4. Crucially, the per-request error is captured into a `Vec` of results rather than propagated as the overall handler failure: [5](#0-4) 

so the enclosing `#[frame_support::transactional] handle_unsigned` extrinsic still succeeds overall and does **not** roll back the earlier mint/transfer performed inside `on_accept`: [6](#0-5) 

Because the request receipt is deleted on the module-level failure, the exact same `PostRequest` (same commitment) is no longer marked delivered. The state-machine commitment used to verify membership remains valid for as long as the challenge/finalization window holds, so any relayer (or the attacker acting as a permissionless "relayer," since `handle_unsigned` is unsigned and callable by anyone with a valid proof) can resubmit the identical request with a fresh membership proof against the same finalized height. Each resubmission re-enters `on_accept`, re-runs the unconditional mint/transfer, and then re-fails the same deterministic calldata step, deleting the receipt again — an unbounded loop of "mint, then fail-and-reset."

An attacker only needs to craft the original cross-chain `Message.data` so `SubstrateCalldata` decodes but is guaranteed to fail deterministically at dispatch — e.g., encode a `runtime_call` that is rejected by `BaseCallFilter` (`HftError::CallFiltered`) or an invalid signature (`HftError::SignatureVerificationFailed`), both of which are deterministic and occur strictly after the mint/transfer step. [7](#0-6) 

### Impact Explanation
This is an unbacked/duplicate mint of bridged assets: the beneficiary (attacker-controlled) receives the bridged `amount` again on every retried delivery of the same request, without any additional legitimate dispatch occurring on the source chain and without consuming additional escrowed collateral there. This is a direct violation of the Hyperbridge escrow/mint invariant (1 source dispatch → 1 destination credit) and constitutes theft/unbacked minting of funds, which is High/Critical severity — analogous to, but more severe than, the referenced MultiversX advisory's "limited DoS," since here it is state-changing value duplication rather than a nonce griefing vector.

### Likelihood Explanation
The path is reachable by any unprivileged party able to submit `Ismp::handle_unsigned` (the whole point of the unsigned extrinsic is to let "anyone execute ISMP datagrams for free... provided they have valid proofs").<cite repo="Alyssadaypin/hyperbridge--007" path="modules/pallets/ismp/src/lib.rs" start="358| 371" end="382" /> An attacker who controls the source-chain sender (or who can get a message routed to a `hyper-fungible-token` contract they influence) fully controls `message.data`, so crafting a deterministically-failing `SubstrateCalldata` is straightforward and repeatable. No governance, consensus corruption, or privileged role is required — only a legitimately delivered, still-provable request plus repeated resubmission of the membership proof while the finalized state height remains valid.

### Recommendation
- Perform the fund transfer/mint atomically with the optional-calldata dispatch outcome: either move the transfer after a successful calldata dispatch, or wrap the whole `on_accept` body (mint + calldata dispatch) in a storage transaction (`frame_support::storage::with_transaction`) so a later failure rolls back the earlier mint.
- Alternatively/also, do not fail (and therefore do not delete the request receipt) when only the *optional* calldata execution fails; treat calldata failure as a non-fatal follow-up action (e.g., emit an error event) once the primary transfer has been committed, so the request is marked delivered exactly once regardless of calldata outcome.
- Ensure `pallet-ismp`'s receipt-deletion-on-error semantics are only relied upon by modules whose `on_accept` implementations are fully atomic (all side effects reverted together on error).

### Proof of Concept
1. Attacker (as source-chain sender) dispatches a cross-chain message to `hyper-fungible-token` with `message.data` containing valid `SubstrateCalldata` whose `runtime_call` is filtered by `BaseCallFilter` (or with a `signature` that fails verification), and `amount` set to the desired mint amount.
2. Relayer (can be the attacker) submits `Ismp::handle_unsigned` with the membership proof for this request. `on_accept` runs: step 1 mints/transfers `amount` to `beneficiary`, step 2's `runtime_call.dispatch` fails `BaseCallFilter::contains` check → `HftError::CallFiltered` → `on_accept` returns `Err`. [8](#0-7) 
3. `handlers::request::handle` sees `res.is_err()` and calls `host.delete_request_receipt(&wrapped_req)`, and the overall extrinsic still succeeds (no propagated error). [9](#0-8) 
4. Attacker resubmits the same request (same commitment) with a fresh membership proof against the same/any later finalized height via another `Ismp::handle_unsigned` call. Because the receipt was deleted, `host.request_receipt(&wrapped_req).is_some()` is false, so it dispatches again, minting `amount` a second time to `beneficiary`.
5. Repeat step 4 indefinitely to accumulate unbounded minted balance for `beneficiary`.

Note: I was not able to fully trace whether an additional replay-protection layer exists elsewhere (e.g. in the state-machine client's membership-proof verification or challenge-period bookkeeping) that might reject re-verifying the same commitment against the same height twice; this should be verified against `modules/ismp/core/src/handlers.rs` and the specific `StateMachineClient::verify_membership` implementation in use, which were not fully inspected in this pass.
