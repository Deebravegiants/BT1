### Title
Webhook signature wrapping — HMAC only signs the raw body, letting an attacker forge `shop-domain`/`topic`/`webhook-id` headers to inject a validly-signed payload as if it came from a different shop or topic - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw request body: `@raw_body`. The HMAC validation in `Utils::HmacValidator.validate` therefore proves nothing about the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, or `x-shopify-api-version` headers — it only authenticates the body bytes. `Registry.process` verifies the HMAC over the body, then trusts the unauthenticated headers to build `WebhookMetadata` (`shop`, `topic`, `webhook_id`, `api_version`) that gets handed directly to the app's `WebhookHandler#handle`.

### Finding Description
This is a direct analog of SAML signature wrapping: the signature covers one part of the message (the body), while the data actually acted upon (the shop identity and topic used to route/attribute the event) is taken from a separate, unsigned part of the message (the HTTP headers).

- `to_signable_string` for `Request` returns only `@raw_body`: [1](#0-0) 
- `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 
- `Registry.process` validates only the HMAC (over the body) and then constructs `WebhookMetadata` from these unauthenticated header fields, passing it to the registered handler: [3](#0-2) 
- `HmacValidator.validate`/`validate_signature` compute the HMAC purely over `verifiable_query.to_signable_string` (the body, in this case) and compare against the `hmac` header: [4](#0-3) 
- `WebhookMetadata.shop` and `.topic` are the fields the app's own handler uses to attribute/route the event to a tenant: [5](#0-4) 

The equality this design implicitly assumes but never enforces is:
`shop_that_produced(HMAC-valid body) == shop_named_in(x-shopify-shop-domain header)`

Because `api_secret_key` (the app's `client_secret`) is shared across *all* shops that install the app — it is not shop-specific — any shop that has installed the app (an ordinary, unprivileged action available to any internet user who can install a public/test app) will receive real Shopify-signed webhooks whose body+HMAC pair is valid under the app's single, global secret. An attacker who controls such a shop can capture a legitimately-signed `(raw_body, hmac)` pair from their own shop's webhook delivery, then replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain (and/or a different `x-shopify-topic`, since `topic` is likewise unsigned). The HMAC check in `Registry.process` still passes — it only re-verifies the body — but the handler now processes the payload believing it originates from the victim shop/topic.

### Impact Explanation
This breaks the tenant identity binding the whole webhook-verification mechanism is supposed to provide: the HMAC is meant to prove "this data really came from Shopify for this shop and this topic," but the shop and topic are never actually part of what's cryptographically authenticated. Any app handler logic that trusts `WebhookMetadata#shop` (e.g., to look up/mutate per-tenant state, deauthorize a shop on `app/uninstalled`, or process compliance webhooks like `shop/redact`) can be tricked into acting on behalf of, or against, an arbitrary victim shop using attacker-supplied header values combined with a validly-signed body the attacker legitimately received for their own shop. This is cross-tenant data confusion/cross-tenant action achieved without ever knowing the app's `api_secret_key` — qualifying as cross-tenant access under the stated impact criteria.

### Likelihood Explanation
Exploitation requires only unprivileged capabilities already granted to any internet user under the rules: installing the target app on an attacker-controlled/free development shop (a normal, unprivileged workflow, not a "privileged account" in the sense of accessing someone else's tenant) to receive at least one real, validly HMAC-signed webhook body, then replaying that request to the app's public webhook endpoint with forged `shop-domain`/`topic` headers. No TLS interception, leaked secrets, or social engineering is needed — the vulnerability is purely a scoping gap in what `to_signable_string` includes.

### Recommendation
Include the shop domain, topic, webhook id, and API version in the HMAC-signed material (or otherwise cryptographically bind them to the body) so that `Registry.process` cannot be satisfied by a signature that only covers the body while the headers used for routing/attribution are forged. At minimum, `Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` alongside the body before computing/verifying the HMAC.

### Proof of Concept
1. Install the vulnerable app on shop `attacker-shop.myshopify.com` (unprivileged, standard app installation).
2. Capture a real, Shopify-delivered webhook request to the app's endpoint, e.g. topic `orders/create`, with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: <valid HMAC over the raw body, computed with the app's shared api_secret_key>`
   - raw body: `{"id":1,...}`
3. Replay this exact raw body and HMAC header to the same app endpoint, but rewrite:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over the identical raw body and it still matches, per `lib/shopify_api/webhooks/request.rb` (`to_signable_string` returning only `@raw_body`).
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) proceeds to invoke the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: <attacker-controlled JSON>, ...)`, causing the app to process attacker-controlled data as if it were a genuine event for `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
