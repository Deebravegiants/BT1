Audit Report

## Title
Missing `return` after failed OIDC email-claim extraction allows session creation to proceed on error path - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `handleTokenExchange`, the type assertion `email, ok := claims["email"].(string)` writes a `500` error response when `ok` is `false` but does not `return`, unlike every other error branch in the same function. Execution falls through, inserting a session row with an empty `user_email`, auditing a false `AuthLoginSuccessNo2FA` login, and returning `Success: true` to the client. A second, identical missing `return` exists after the `INSERT INTO oidc_sessions` error branch a few lines later.

## Finding Description
`handleTokenExchange` at [1](#0-0)  handles the email-claim assertion failure by logging and writing `c.String(http.StatusInternalServerError, ...)`, but omits `return`, in contrast to the sibling checks for `id_token` presence, ID token verification, claims parsing, and role mapping, all of which correctly `return` at [2](#0-1)  and [3](#0-2) . As a result, execution proceeds to role mapping, session insertion with the empty `email` value, audit logging of a successful login, and a `200 Success: true` response at [4](#0-3) . The same fall-through pattern recurs after the `oidc_sessions` INSERT failure branch, which also lacks a `return` at [5](#0-4) , causing an audit log entry and session cookie to be issued even when no session row exists in the database. Downstream, `AuthorizedUserWithSession` trusts `user_email`/`user_role` read directly from `oidc_sessions` without further validation, as shown at [6](#0-5) .

## Impact Explanation
This is a genuine control-flow bug that falsifies the audit log (`AuthLoginSuccessNo2FA` recorded for an empty email) and creates a cookie-backed session with a real RBAC role but an empty user identity, while the client is told the login succeeded despite the server already emitting an internal error. This matches the "failure path not acted upon, treated as success" bug class. However, it is not a full authentication/role bypass of a specific victim account: the role is still derived from genuine, verified IdP group claims (not attacker-controlled), and reaching the email-claim-missing branch requires the trusted upstream IdP to omit or malform the `email` claim — a condition not directly controllable by an unprivileged network attacker interacting only with the Chainlink node's HTTP surface, but rather dependent on IdP behavior/configuration. The DB-insert-failure fall-through similarly produces an inconsistent-but-not-directly-exploitable state, since `AuthorizedUserWithSession` will reject a missing session row via `sql.ErrNoRows`.

## Likelihood Explanation
Reachability depends on an uncommon IdP condition (a verified, non-error ID token whose claims omit `email` or use a non-string type) rather than something a fully unprivileged external client can force by itself against a correctly configured IdP integration; likelihood is low-to-moderate and edge-case dependent.

## Recommendation
Add `return` immediately after both error-response blocks (lines 226-230 and 257-260) so the handler halts on failure, matching the pattern used by every other error branch in `handleTokenExchange`.

## Proof of Concept
1. Configure/point the OIDC provider such that the verified ID token's claims map omits `email` (or uses a non-string value) while still containing valid group claims mapping to a role via `IDClaimsToUserRole`.
2. Complete `/oidc-login` and POST the resulting `code`/`state` to `/exchangeToken`.
3. Observe the server writes `500 Failed to get email from claims`, yet still inserts a row into `oidc_sessions` with `user_email = ''`, audits `AuthLoginSuccessNo2FA`, sets the session cookie, and returns `HTTP 200 {Success: true}` — confirming the missing `return` at [1](#0-0) .
