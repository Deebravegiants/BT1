## Title
Webhook HMAC verification does not bind `shop`/`topic` headers, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `HmacValidator.validate` verifies the HMAC exclusively against that body. The `shop-domain` and `topic` headers — which `Registry.process` trusts to route the webhook and to identify the tenant — are never included in the signed material. Any actor able to obtain one genuinely-signed `(body, hmac)` pair from Shopify for the target app (e.g. by installing the app on their own store and triggering a webhook) can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header, and the signature check still succeeds.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only `@raw_body` is signed. `Request#shop` and `Request#topic` are read straight from attacker-controlled HTTP headers with no cryptographic tie to the body: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` compute and compare the HMAC only over `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` gates entirely on this HMAC check and then dispatches to the handler using the unauthenticated `request.shop` and `request.topic` values as the tenant/topic identity for the callback: [4](#0-3) 

The identity binding that should hold is: `shop asserted to the handler == shop cryptographically bound inside the verified payload`. Because the signature covers only the body bytes, this equality never holds — the `shop-domain` header is verified against nothing. An attacker who has legitimately installed the target app on their own store receives genuinely-signed webhook requests (using the app's single, shared `api_secret_key`, identical for every installing shop). They can capture one such `(raw_body, hmac)` pair and replay it against the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header changed to point at a different, victim shop. `HmacValidator.validate` still returns `true` because it never inspected those headers, and `Registry.process` calls the app's handler with `WebhookMetadata` claiming the victim shop as the source.

### Impact Explanation
This breaks the tenant boundary the whole webhook-processing feature is meant to enforce: host applications reasonably rely on `WebhookMetadata#shop` (sourced from `request.shop`) to decide which tenant's data to update as a result of an HMAC-"verified" webhook. An attacker with no privileges other than the ability to install the app on their own store (a completely unauthenticated action from the target's perspective) can forge webhook events attributed to any other shop of their choosing, leading to cross-tenant data confusion/injection in any host application that trusts `data.shop` after a successful `Registry.process` call — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is significant: the only prerequisite is the attacker's ability to install the target app on a store they control (any developer/merchant can do this for free), and then observe/capture one legitimately delivered webhook body+HMAC. No secrets, tokens, or privileged access are required, and the gem performs no additional binding (e.g., no shop-scoped secret, no inclusion of headers in the signed string, no origin/IP check) to prevent replay across shops.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the HMAC-signable string, or otherwise cryptographically bind them to the payload before verification, so that `HmacValidator.validate` fails if any of these header values are altered relative to what was originally signed by Shopify.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development store (no elevated privileges needed).
2. Attacker triggers any webhook topic (e.g. `orders/create`) on their store; the app's endpoint receives a request with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`.
3. Attacker replays the exact same raw body and HMAC to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`) — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to process attacker-supplied data as if it originated from the victim tenant.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
