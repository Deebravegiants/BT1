### Title
Tron `IntentGatewayV2` accepts arbitrary, non-whitelisted ERC-20 tokens in `placeOrder`/`fillOrder` with no reentrancy guard at all - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of `IntentGatewayV2` lets any caller escrow or fill an order with an arbitrary `IERC20` token address (no whitelist), exactly like the reported `addLiquidity` pattern, but — unlike the audited EVM `IntentGatewayV2` — it ships with **no reentrancy guard whatsoever**, not even the `ReentrancyGuardTransient` used in the sibling contract to close a previously-fixed reentrancy hole in the same `placeOrder`/`fillOrder` flow.

### Finding Description
`placeOrder` in the Tron contract takes `order.inputs`/`order.output` as raw `TokenInfo{token, amount}` values and immediately calls `IERC20(token).safeTransferFrom(...)` / `IUniswapV2Router02.swapETHForExactTokens` on whatever address the caller supplies, with no token registry or allowlist check: [1](#0-0) [2](#0-1) 

The dust-collection logic re-reads `IERC20(token).balanceOf(dispatcher)` after an arbitrary `ICallDispatcher.dispatch` call and derives escrow amounts from the balance delta: [3](#0-2) 

Critically, this entire file has **no `ReentrancyGuard`/`nonReentrant` import or modifier** anywhere (confirmed via full-file search — zero matches for `nonReentrant`/`ReentrancyGuard`). Compare this to the canonical EVM `IntentGatewayV2.sol`, which explicitly composes `ReentrancyGuardTransient` and guards `placeOrder` with `nonReentrant`: [4](#0-3) [5](#0-4) 

The project's own regression tests document that the EVM `fillOrder`/`_fillSameChain` path previously had a **real, exploitable reentrancy bug** ("Escrow theft", "Fee theft") that required moving `_filled[commitment] = msg.sender` to the top of the function (CEI) specifically because a malicious/attacker-controlled token or beneficiary could reenter mid-fill and steal escrowed funds: [6](#0-5) [7](#0-6) 

The Tron file contains the same `_filled`, `fillOrder`, `_fillSameChain`, `_fillCrossChain` surface, but I was unable to fully verify (search iterations were exhausted) whether the CEI ordering fix (`_filled[commitment] = msg.sender` set before external transfers) was ported into the Tron implementation, and — independent of that ordering — the contract has no `nonReentrant` backstop at all, so any gap in CEI ordering across `placeOrder` (predispatch dispatch, Uniswap swap) and `fillOrder`/`cancelOrder`/`redeemEscrow` (arbitrary-token transfers to `order.output.beneficiary`) is directly reachable by an unprivileged solver/user submitting a single `placeOrder`/`fillOrder` transaction with a malicious ERC-20 as input or output token.

### Impact Explanation
If a malicious token's `transferFrom`/`transfer` hook (or a beneficiary contract's fallback during native-token payout) can reenter `placeOrder`, `fillOrder`, or `cancelOrder` before escrow bookkeeping (`_orders[commitment][token] += …`, `_filled[commitment]`) is finalized, an attacker can double-credit escrow, self-fill and drain another user's escrowed tokens, or manipulate the `dust`/protocol-fee token swap logic to steal funds from the gateway — a direct theft-of-funds outcome, matching the report's exploit scenario of "steal funds from Alice who provides liquidity/escrow."

### Likelihood Explanation
Reachable by any user in a single transaction (`placeOrder` and `fillOrder` are both public/payable, permissionless, and take user-controlled arbitrary token addresses). The precedent in this exact codebase (documented, previously-exploitable reentrancy in the sibling EVM contract's identical fill flow) shows the vulnerability class is realistic and has already manifested once in this feature area; the Tron variant simply lacks the guard entirely.

### Recommendation
- Add `ReentrancyGuardTransient` (or standard `ReentrancyGuard`) and a `nonReentrant` modifier to `placeOrder`, `fillOrder`, `cancelOrder`, and any withdrawal/redeem entry points in `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirroring `evm/src/apps/IntentGatewayV2.sol`.
- Verify and, if missing, port the CEI fix (`_filled[commitment] = msg.sender` set before any external call) into the Tron `_fillSameChain`/`_fillCrossChain` implementations.
- Consider a token registry/allowlist for `order.inputs`/`order.output.assets` to reduce the malicious-token attack surface, consistent with the external report's core recommendation.

### Proof of Concept
Conceptual (Tron contract, unguarded):
1. Attacker deploys a malicious ERC-20 whose `transfer`/`transferFrom` callback re-enters `IntentGatewayV2`.
2. Attacker calls `placeOrder` with this token as an input/predispatch asset; during `ICallDispatcher.dispatch`/`safeTransferFrom`, the token reenters `placeOrder` (or `fillOrder` on a previously placed order) before `_orders[commitment][token] += reducedInputs[i].amount` (line 441/463) or `_filled[commitment]` bookkeeping completes.
3. Because no `nonReentrant` modifier exists anywhere in the file, the reentrant call executes fully, allowing double-crediting of escrow or a self-fill that drains another user's escrowed tokens — analogous to the previously fixed `testReentrancy_EscrowTheft_MultiOutput` scenario in the EVM sibling contract.

Note: full confirmation of whether the Tron `_fillSameChain`/`_fillCrossChain` internals already contain the CEI ordering fix could not be completed within the available tool budget; this should be verified directly against `evm/tron/contracts/apps/IntentGatewayV2.sol` in a follow-up review.
