### Title
Unfunded `recapitalize` books cash without custody, permanently freezing supplier withdrawals - (File: contracts/pool/tests/flows.rs)

### Summary
The MongoDB report describes a crash caused by an internal inconsistency between two representations of the same state. The XOXNO Lending analog is the pool's `recapitalize` path: it mutates the `cash` book and pays out tokens under the assumption an external transfer already funded the pool, but it never verifies that funding. A permissionless call through `controller::recapitalize(payer, hub, amount)` therefore desynchronizes the cash book from real token custody — the same class of "two views of one fact" divergence — and the discrepancy surfaces later as failed supplier withdrawals rather than at the call site.

### Finding Description
The pool tracks liquidity in two places that must agree: the `cash` ledger field (bookkeeping, checked by `guards::require_reserves` / `backing_shortfall`) and the actual SAC token balance of the pool contract. The pool README documents the invariant that guards read the book, and every normal mutation (`supply`, `withdraw`, `borrow`, `repay`) keeps book and custody in lockstep via measured settlement [1](#0-0) .

`recapitalize` is the exception. It credits the `cash` book and transfers `amount` tokens to `payer` on the trust assumption that the controller already collected matching funds — there is no measured-receipt check like the flash loan's balance reconciliation [2](#0-1) . The repository's own adversarial test demonstrates the result: calling `pool.recapitalize(hub, payer, custody)` on a funded market drains the entire token balance to `payer` while `state.cash` still reports the supplier's deposit as backed [3](#0-2) . Because `recapitalize` mints no shares and writes down nothing, every guard that consults the book keeps passing on a pool that is actually empty — `require_reserves` clears a withdrawal the SAC transfer cannot pay [4](#0-3) .

`recapitalize` is listed among the permissionless controller entrypoints (`scripts/permissionless_entrypoints.txt`), so a single unprivileged address reaches the pool path via `controller.recapitalize`. Even where the controller collects `amount` from the payer before invoking the pool, the pool's refund-style payout nets custody to zero while booking `+amount` of cash — the book diverges from custody by `amount` either way, and the payer is made whole.

### Impact Explanation
Permanent freezing of user funds plus protocol insolvency. Once book-custody divergence exists, every `withdraw`/`seize`/`flash_loan`/`repay_debt_with_collateral` leg that passes the pool's liquidity guards fails inside the SAC `transfer` with `BalanceError`, and Soroban rollback leaves the overstated book untouched, so the condition is unrecoverable through normal flows — suppliers' exits revert forever while their shares remain on the books [5](#0-4) . Where the payout went to the attacker's `payer` address, it is additionally outright theft of pool custody.

### Likelihood Explanation
`recapitalize` is a permissionless entrypoint taking attacker-controlled `payer` and `amount` arguments; the only requirement is a market with existing cash. The test fixture shows the full exploit sequence succeeds against a normally funded market with no privileged setup [6](#0-5) . Likelihood is bounded only by whether the controller wrapper requires the payer to pre-fund the exact `amount` — and even then the refund leg still produces a free, unbacked cash-book inflation at zero cost to the caller.

### Recommendation
Make `recapitalize` a measured-receipt operation like `flash_loan`: snapshot the pool's token balance before crediting, require `balance_after - balance_before >= amount` (or accept a direct-transfer deposit from `payer` and reconcile it), and never transfer tokens to `payer` beyond a verified surplus. Alternatively, restrict the entrypoint to the governance/admin path and have the controller collect and forward funds atomically in the same call, with the pool asserting custody increased by at least `amount` before updating `cash`.

### Proof of Concept
The repository already contains the executable witness at `contracts/pool/tests/flows.rs::test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (lines 3408–3483): mint a 10_000_000_000 deposit through `supply`, call `recapitalize(hub, payer, custody)` with an unfunded random `payer`, observe `token.balance(pool) == 0` while `state.cash >= deposit`, then observe the supplier's `withdraw` fail with SAC `BalanceError = 10` while neither `InsufficientLiquidity` nor `PoolInsolvent` fires — proving the book overstated custody and the exit is permanently blocked [7](#0-6) .

fn test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);
    let receiver = Address::generate(&t.env);

    // A legitimate supplier, with custody moved in as the controller would.
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t
        .client()
        .supply(&t.sup(0, deposit))
        .get_unchecked(0)
        .position
        .scaled_amount;
    assert_eq!(
        t.state_snapshot().cash,
        token.balance(&t.pool),
        "fixture guard: book and custody must still agree after the deposit"
    );

    // Drain every token via an unfunded refund.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0, "custody is gone");

    let book = t.state_snapshot().cash;
    assert!(
        book >= deposit,
        "the book still claims more than the supplier's deposit: {book}"
    );

    // The supplier's exit clears the pool's own liquidity guard -- the book
    // says the cash is there -- and then fails in the token transfer.
    let outcome = t
        .client()
        .try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
    assert!(
        outcome.is_err(),
        "the withdraw cannot be paid, so it must fail"
    );
    // The failure must come from custody, not from a pool guard. The SAC
    // reports insufficient balance as its own contract error `BalanceError = 10`.
    // The asserts check that exact code and that neither pool liquidity guard
    // fired: `require_reserves` read the book and let the exit through.
    const SAC_BALANCE_ERROR: u32 = 10;
    match outcome {
        Err(Ok(err)) => {
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::InsufficientLiquidity as u32),
                "the pool's own liquidity guard must NOT be what stopped this -- \
                 it reads the cash book, which still shows the funds"
            );
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::PoolInsolvent as u32),
                "the pool's solvency guard must NOT be what stopped this either"
            );
            assert_eq!(
                err,
                Error::from_contract_error(SAC_BALANCE_ERROR),
                "the exit must fail inside the SAC transfer for want of custody"
            );
        }
        Err(Err(host_abort)) => panic!("expected a SAC contract error, got {host_abort:?}"),
        Ok(_) => unreachable!("asserted is_err above"),
    }
    assert_eq!(token.balance(&receiver), 0, "the supplier received nothing");
    assert_eq!(
        t.state_snapshot().cash,
        book,
        "the failed exit rolled back, so the book still overstates custody"
    );
}
