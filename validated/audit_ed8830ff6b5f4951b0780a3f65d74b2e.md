### Title
Native stake deposited into the ERC-4337 EntryPoint via `SimplexPaymaster.addStake()` is permanently unrecoverable — no code path can ever unlock or withdraw it - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
This is a structural analog of the Gitcoin `QVBaseStrategy` bug: a value can be pushed into a particular state (`Status.Appealed` there; "staked with the EntryPoint" here) for which the contract's state machine has *no* corresponding transition back out. In `SimplexPaymaster`, `addStake()` is a permissionless entry point that locks native ETH/BNB with the ERC-4337 `EntryPoint`, but every recovery path (`unlockStake()`/`withdrawStake()`) is gated behind `_authorizeWithdraw()`, which unconditionally reverts, and the contract's governance message-dispatch enum (`RequestKind`) has no variant to reach or bypass that gate. The result is state with no legal transition forward, exactly the class of bug flagged in the original report.

### Finding Description
`SimplexPaymaster` is an ERC-4337 paymaster used by Hyperbridge's Simplex intent solver to sponsor gas for order fills [1](#0-0) . It exposes `addStake(uint32 unstakeDelaySec)` (payable, permissionless), `unlockStake()`, and `withdrawStake(address payable to)`, which proxy to OpenZeppelin's `BasePaymaster`/EntryPoint stake-management functions [2](#0-1) .

The repository's own fork test documents the root cause directly: "once native is staked with the EntryPoint, no caller and no governance action can ever recover it, because every unlock path routes through `_authorizeWithdraw()`, which reverts unconditionally, and the governance `RequestKind` enum has no stake variant." [3](#0-2) 

This is functionally identical to the `QVBaseStrategy` bug class: a status/state (`Appealed` there, "staked" here) can be *entered* through a normal, permissionless flow, but the code paths that are supposed to transition it forward (`reviewRecipients` there, `unlockStake`/`withdrawStake` here) are unconditionally blocked for that state, and there is no alternate path (governance message, admin call, or otherwise) to reach a resolved state. In the original report the recipient is "locked out of any functionality"; here the staked funds are locked out of any recovery functionality.

Compounding the lock, `addStake` itself is permissionless, so any unprivileged actor can call it to (a) lock additional native value into the paymaster, and (b) extend the EntryPoint's `unstakeDelaySec` arbitrarily (the test demonstrates pushing the delay beyond a century), which further cements the freeze even if a fix were later deployed and a legitimate unlock became possible in principle [4](#0-3) .

### Impact Explanation
This is a permanent freezing-of-funds bug reachable without any privileged role:
- All native currency ever staked with the EntryPoint through this paymaster (used to sponsor Simplex solver transactions) becomes permanently irrecoverable — not by the treasury, not by the host/governance, not by anyone.
- An unprivileged caller (`griefer`) can worsen the situation by calling `addStake` to push the unstake delay to an effectively infinite value, foreclosing any future governance-authorized fix path that might rely on eventually calling `withdrawStake` after the delay elapses.
- The test file explicitly confirms this against the **live deployed** paymasters on BSC and Ethereum mainnet (`0xeD02f9f0...`, `0xD4340d74...`), meaning real staked value is at risk in production, not just a theoretical/mock scenario.

### Likelihood Explanation
High likelihood / already demonstrated: the vulnerability requires no adversarial conditions beyond calling `addStake` (permissionless) and observing that every one of `unlockStake`, `withdrawStake` for every plausible privileged caller (treasury, host, EntryPoint, and an arbitrary EOA) reverts. The repository's own regression tests (`testLiveBscStakeIsPermanentlyLocked`, `testLiveEthereumStakeIsPermanentlyLocked`, `testAnyoneCanAddStakeAndExtendTheUnstakeDelay`) assert this behavior against the live deployed contracts, confirming the bug is already present on-chain rather than hypothetical.

### Recommendation
- Add a governance-authorized `RequestKind` (or equivalent privileged function) that allows `_authorizeWithdraw()` to succeed for a designated admin/treasury/timelock, mirroring how other cross-chain governance actions (`UpdateParams`, `SweepDust`) are already dispatched through Hyperbridge messages in the intents/gateway contracts.
- Alternatively, restrict `addStake`/`unlockStake`/`withdrawStake` calls to a governance-controlled account entirely, removing the permissionless griefing vector on `unstakeDelaySec`.
- Provide an emergency recovery path (e.g., time-locked multisig call) that can call `unlockStake`/`withdrawStake` on the EntryPoint directly, bypassing the paymaster's own broken `_authorizeWithdraw` gate, to recover any stake already locked in the currently deployed instances.

### Proof of Concept
The existing fork test in the repository is itself the proof of concept:
```solidity
function _assertStakeUnrecoverable() internal {
    (, bool staked, uint112 stake,,) = ENTRY_POINT.getDepositInfo(address(paymaster));
    assertTrue(staked);
    assertGt(stake, 0);

    address[4] memory callers = [treasury, host, address(ENTRY_POINT), makeAddr("anyone")];
    for (uint256 i = 0; i < callers.length; i++) {
        vm.prank(callers[i]);
        vm.expectRevert();
        paymaster.unlockStake();

        vm.prank(callers[i]);
        vm.expectRevert();
        paymaster.withdrawStake(payable(callers[i]));
    }
    // stake remains staked and unchanged for every possible caller
}
``` [5](#0-4) 

Additionally, permissionless griefing of the unstake delay:
```solidity
vm.prank(griefer);
paymaster.addStake{value: 1 wei}(type(uint32).max);
// unstake delay now pushed beyond 100 years
``` [6](#0-5)

    /// `addStake` is permissionless, so a griefer can both lock fresh value into the
    /// contract and stretch the unstake delay a future upgrade would have to wait out.
    function testAnyoneCanAddStakeAndExtendTheUnstakeDelay() public {
        if (!_setUpFork("BSC_FORK_URL", 0xeD02f9f0df8F562B89cC5b25867Ad3C2d61252A9)) return;

        (,,, uint32 delayBefore,) = ENTRY_POINT.getDepositInfo(address(paymaster));
        address griefer = makeAddr("griefer");
        vm.deal(griefer, 1 ether);

        vm.prank(griefer);
        paymaster.addStake{value: 1 wei}(type(uint32).max);

        (,, uint112 stakeAfter, uint32 delayAfter,) = ENTRY_POINT.getDepositInfo(address(paymaster));
        emit log_named_uint("unstake delay before (s)", delayBefore);
        emit log_named_uint("unstake delay after  (s)", delayAfter);
        assertGt(delayAfter, delayBefore, "an unprivileged caller extended the unstake delay");
        assertGt(uint256(delayAfter), 100 * 365 days, "delay pushed beyond a century");
        assertGt(stakeAfter, 0);
    }
