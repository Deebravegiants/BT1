**Rationale:**

The proof idea assumes an `EntryFunction` transaction can directly invoke a `public` (but non-`entry`) function published under a resource account. This is not possible in the Aptos VM's execution path: when an `EntryFunction` payload is processed, `validate_and_execute_entry_function` explicitly calls `function.is_entry_or_err()` before execution, which rejects any function that is not marked `entry`, regardless of its `public`/`public(friend)`/private visibility. [1](#0-0)  Native/user-defined native entry functions are also explicitly forbidden earlier in the same function. [2](#0-1)  So a "public non-entry-gated transfer function" simply cannot be reached via the `EntryFunction` dispatch path described — the VM's own gate closes it.

Separately, the framework's actual custody mechanism for resource accounts does not rely on function visibility for protection. `resource_account::retrieve_resource_account_cap` requires the caller to already hold the resource account's own `&signer`, and it immediately rotates that account's authentication key to `0x0`, making the account's raw signer permanently unobtainable via transaction signing thereafter. [3](#0-2)  After that point, the only way to obtain a `signer` for the resource account is through the `SignerCapability` object held in the deploying module's own storage (e.g., `ModuleData.signer_cap`), which is entirely controlled by that module's own function definitions and visibility choices. [4](#0-3) [5](#0-4) 

Whether an individual third-party module correctly gates access to its own transfer/mint/burn logic (e.g., via `public(friend)`, capability checks, or address assertions) is a property of that specific module's Move source code, not of `types/src/transaction/script.rs`'s `EntryFunction` struct or the core VM/framework custody logic. [6](#0-5)  The file cited in the question only defines the serializable `EntryFunction` data structure and carries no custody logic itself — it is not the "controller/holder/capability" boundary described in the review's custody pivots. No repo-root-caused defect in aptos-core's resource-account or entry-function dispatch mechanism was found; the scenario as stated is either blocked by the VM's `is_entry_or_err()` check, or depends entirely on hypothetical third-party module design errors outside review scope.

    /// When called by the resource account, it will retrieve the capability associated with that
    /// account and rotate the account's auth key to 0x0 making the account inaccessible without
    /// the SignerCapability.
    public fun retrieve_resource_account_cap(
        resource: &signer, source_addr: address
    ): account::SignerCapability acquires Container {
        assert!(
            exists<Container>(source_addr),
            error::not_found(ECONTAINER_NOT_PUBLISHED)
        );

        let resource_addr = signer::address_of(resource);
        let (resource_signer_cap, empty_container) = {
            let container = borrow_global_mut<Container>(source_addr);
            assert!(
                container.store.contains_key(&resource_addr),
                error::invalid_argument(EUNAUTHORIZED_NOT_OWNER)
            );
            let (_resource_addr, signer_cap) =
                container.store.remove(&resource_addr);
            (signer_cap, container.store.length() == 0)
        };

        if (empty_container) {
            let container = move_from<Container>(source_addr);
            let Container { store } = container;
            store.destroy_empty();
        };

        account::rotate_authentication_key_internal(resource, ZERO_AUTH_KEY);
        resource_signer_cap
    }
