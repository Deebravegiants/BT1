### Title
Same-token duplicate slot in `erc20TokenAddresses` lets `EmporiumUpgradeable.runAction` pay out a stranded/residual balance twice, minting an unbacked output UTXO - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` computes `balanceChange` for each *position* in `circomData.erc20TokenAddresses` from `balancesBefore`/`balancesAfter` snapshots taken once at the top/bottom of the function, then calls `handleOut` (a real ERC20 transfer) independently for every position. If the attacker lists the same token address twice, both positions compute the identical `balanceChange`, and `handleOut` physically pays it out **twice**, with the second payout drawn from whatever balance the Emporium contract already held before the call (residual/stranded funds). `Hinkal.sol`'s post-action reconciliation loop does not catch this because it re-sums the *entire* `utxoSet` for every matching index, so it self-consistently validates the duplicated payout instead of detecting it.

### Finding Description
The invariant that should hold is: for a given call, the physical value that leaves the Emporium action for a token equals `-deltaAmountChanges` sent to it plus whatever the ops genuinely produced — i.e. each unit of value paid out must be backed by a distinct genuine balance increase, not the same increase counted twice.

In `runAction`: [1](#0-0) 
the loop iterates over `circomData.erc20TokenAddresses` by index, not by unique token. `balancesBefore[i]`/`balancesAfter[i]` are simple array reads populated by `getBalancesForArray`, so if the same token appears at index `i0` and `i1`, `balanceChange[i0] == balanceChange[i1]`. `handleOut` then performs an actual `transferERC20TokenOrETH` for **each** index: [2](#0-1) 
The first call correctly pays out the genuine inflow that occurred during the `ops` execution. The second call for the duplicate index re-pays the *same* amount again; this succeeds physically as long as the Emporium contract held at least that much of the token *before* the call started (`balancesBefore >= balanceChange`), which the code's own comment acknowledges is a real scenario ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call", line 141). That pre-existing balance can be dust/rounding remainders from prior swaps, or funds an attacker (or anyone) simply donates to the Emporium contract address via a plain `ERC20.transfer` ahead of time — no privilege required.

Nothing dedupes `erc20TokenAddresses`. `dimensionsCheck` and `performHinkalChecks` only verify array lengths match `dimensions.tokenNumber`, never uniqueness: [3](#0-2) 

The downstream reconciliation in `Hinkal.transact` also fails to catch the double payout because it re-computes `utxoAmount` by scanning the **whole** `utxoSet` for matching address on every duplicated index, so the aggregate check passes twice with the same numbers instead of flagging the duplication: [4](#0-3) 
Since `balanceDif` (Hinkal's own measured balance swing) genuinely equals the sum of both UTXOs (Hinkal really did receive both transfers), the `require(balanceDif == amountChanges[i] + utxoAmount)` check is self-consistent and offers no protection — it only proves internal consistency of the exploit, not that the second UTXO is economically backed.

Exploit flow:
1. Attacker (unprivileged) ensures/creates a stranded balance `D` of token `X` sitting in the Emporium contract (either naturally occurring dust from prior swaps, or the attacker directly transfers `D` of their own `X` to the Emporium address ahead of time as a plain token transfer).
2. Attacker calls `Hinkal.transact` targeting Emporium, with `circomData.erc20TokenAddresses = [X, X]` (duplicate), `amountChanges/deltaAmountChanges = [0, 0]`, and one `EmporiumOperation` whose `callData` is `X.transferFrom(attacker, emporium, amount)` (attacker pre-approved Emporium to pull their own funds) with `amount <= D`.
3. During `runAction`, this op moves `amount` of `X` into Emporium, producing a real `balanceChange = amount` for both duplicate indices.
4. `handleOut` for index0 pays `amount` back to Hinkal (legitimate, self-funded loop). `handleOut` for index1 pays `amount` again, drawn from the pre-existing `D`.
5. Two on-chain output UTXOs of `amount` each are created; the second is entirely unbacked by any nullifier spend, deposit, or `amountChanges` entry — it is minted purely from residual balance that belonged to the protocol/other users.
6. `Hinkal.sol`'s balance-diff check passes because Hinkal's own balance genuinely grew by `2*amount`, matching the summed `utxoSet`.

### Impact Explanation
The attacker extracts up to `min(D, amount)` of another party's/protocol's value (any stranded balance sitting in the Emporium contract) per call, receiving it as their own genuine on-chain output UTXO/commitment, entirely uncorrelated to the funds they actually spent-through-the-loop. This is direct theft of shielded/in-flight or protocol-held funds via a duplicated token slot, matching the Critical severity category (theft of shielded/in-flight user funds). It is repeatable any time residual balance accumulates in the Emporium contract (which the code's own comments acknowledge is an expected occurrence), and the attacker can even seed the residual themselves in a prior transaction and later reclaim more than they put in if other legitimate users' dust has also accumulated there in the interim.

### Likelihood Explanation
Preconditions are trivial for an unprivileged attacker: they need their own funds to trigger the "genuine" leg of the double-processed token, self-approval of the Emporium contract to move their own tokens (fully within their control), and knowledge/creation of a nonzero pre-existing balance of that token in Emporium (which they can create themselves via a plain transfer, or wait for/scan for organically). No proof forgery, nullifier double-spend, or privileged role is required — only crafting `erc20TokenAddresses` with a duplicate entry and constructing an `EmporiumOperation` that performs a self-funded `transferFrom`. This is straightforward to construct and repeat.

### Recommendation
- In `EmporiumUpgradeable.runAction`, reject or collapse duplicate entries in `circomData.erc20TokenAddresses` (e.g., require strict ordering/uniqueness, or aggregate `balanceChange` per unique token before calling `handleOut` once per unique token, tracking already-paid amounts).
- Alternatively, track a running "already-withdrawn" total per token address within the loop and subtract it from further balance-change computations for the same address so a second occurrence cannot double-claim the same delta.
- In `Hinkal.sol`'s reconciliation loop, ensure token addresses are unique across `circomData.erc20TokenAddresses` (or validate that `utxoSet` entries are 1:1 with array index) rather than re-summing the whole `utxoSet` for every index, so duplicated slots can't self-validate.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, and a mock ERC20 `X`.
2. Seed residual: from an attacker EOA, `X.transfer(emporium, D)` directly (e.g., `D = 1000e18`), simulating either attacker-created or organically-stranded dust.
3. Attacker approves `Emporium` to spend `amount = 500e18` of their own `X`.
4. Construct `CircomData` with `erc20TokenAddresses = [X, X]`, `amountChanges = [0, 0]`, `deltaAmountChanges` derived as `[0, 0]`, and `externalActionMetadata` encoding an `EmporiumStack` with one stateless `EmporiumOperation{endpoint: X, callData: abi.encodeCall(IERC20.transferFrom, (attacker, emporium, amount))}`.
5. Generate a valid proof (or use test doubles/mocked verifier if available) satisfying `inTotal + amountChanges === outTotal` for both (zero) slots, and call `Hinkal.transact`.
6. Assert:
   - Before: Emporium `X` balance == `D`; attacker's Hinkal-side X UTXO total == 0 (aside from initial capital).
   - After: Emporium `X` balance == `D - amount`; two on-chain UTXO/commitments of `amount` each are created and attributable to attacker (i.e., attacker's net captured value == `2*amount`, while they only put in `amount` of their own capital) — violating `tokens leaving an action in a tx == -deltaAmountChanges Hinkal sent it that tx` (LHS `= 2*amount`, RHS `= 0`).
   - Confirm `Hinkal.sol`'s `balanceDif == amountChanges[i] + utxoAmount` check passes for both indices (proving the guard is bypassed, not merely absent).

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
