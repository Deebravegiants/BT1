## Finding

### Title
Webhook `shop` (and topic/webhook-id/api-version) header not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop` (tenant identity) that the SDK hands to the app's handler is taken from an HTTP header that is never included in the signed payload. This breaks the intended binding `authenticated_signature == request.shop`, allowing a party who can obtain one validly-signed webhook body (e.g. by installing the app on their own store) to relabel that same signed payload as originating from a different, victim shop.

### Finding Description
`Webhooks::Registry.process` validates the request with: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers (`shopify-shop-domain`, etc.) and are never part of the HMAC-signed content: [4](#0-3) 

After HMAC validation succeeds, `process` forwards `request.shop` — the unauthenticated header value — straight into the `WebhookMetadata` passed to the app's registered handler: [1](#0-0) 

The identity binding that should hold is: *the shop whose credentials produced the HMAC == the shop the handler is told the event came from*. Because the header is outside the signed content, this equality is not enforced by the gem — it holds only if the host application separately re-validates `shop` against its own store of installed/known shops, which the gem neither requires nor guides.

Crucially, `Context.api_secret_key` (the HMAC secret) is the app's `client_secret`, shared across *every* shop that installs the app — not a per-shop secret. Any actor who installs the app on their own store legitimately receives a validly-HMAC-signed webhook body from Shopify for that store. Since the header carrying `shop` is not part of the signed bytes, that same `(raw_body, hmac)` pair remains valid if replayed directly to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a different, victim shop's domain.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker who is a legitimate (if malicious) merchant of the app can produce webhook traffic that passes `HmacValidator.validate` while attributing the event to any other shop domain of their choosing. Any host application that relies on `WebhookMetadata#shop` (as returned by this gem) to decide which tenant's data/record to create, update, or trigger action for — the documented and expected usage pattern shown in the gem's own tests — will process attacker-controlled data under a victim shop's identity. This matches the Critical "cross-tenant access" category: the boundary between one merchant's data/identity and another's is crossed using only the shared app secret that the attacker legitimately possesses through their own installation, not the victim's credentials.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: obtaining a signed webhook body requires nothing more than installing the app on any store (a normal, permissionless action for anyone who can install a Shopify app), and replaying an HTTP POST with a modified header requires no special access. The main constraint is that the attacker can only control the shop label attached to *their own* webhook body content, not arbitrary body content for the victim — but many topics (e.g. `app/uninstalled`, `shop/update`, or handlers that only branch on `shop` + fixed/topic-controlled logic) do not require attacker-influenced body content to cause damage.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the authenticated material, or, short of changing Shopify's wire protocol, require/document that host applications must independently verify `request.shop` against a known/installed-shop store before trusting it — and have `Registry.process` enforce this via an injectable shop-validation hook rather than silently trusting the header. At minimum, the gem should surface a clear warning in `WebhookMetadata`/`Request` documentation that `shop` is unauthenticated by the HMAC check performed in `process`.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`, triggering Shopify to send a legitimately signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid because computed with the app's single shared `client_secret`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)` and replays it directly to the app's public webhook endpoint, but rewrites the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` — this still passes because `to_signable_string` never included the shop header.
4. `request.shop` now returns `"victim-shop.myshopify.com"`, and `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: B, ...)` and invokes the app's handler with it, causing the app to act as if `victim-shop` sent this webhook event. [1](#0-0) [5](#0-4)
