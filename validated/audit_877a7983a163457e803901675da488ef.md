## Title
Webhook HMAC only authenticates the raw body, not the `shop-domain`/`topic` identity used by handlers — cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic for whatever `shop`/`topic` values are on the *unauthenticated* HTTP headers, while the HMAC signature only ever covers the raw request body. Because the app's `client_secret` (used as the HMAC key) is a single shared secret across every merchant that installs the app, any attacker who can obtain one valid `(body, hmac)` pair for their own tenant can replay that exact pair against the same public webhook endpoint while forging the `shopify-shop-domain` and `shopify-topic` headers to point at a victim shop and a different topic — the signature will still validate, and the handler will execute believing it received an authentic event for the victim tenant.

### Finding Description
`Registry.process` authenticates a webhook solely via: [1](#0-0) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and the shared `Context.api_secret_key`: [2](#0-1) 

For webhook requests, `to_signable_string` returns only the raw body — `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from headers and are **not** part of the signed bytes: [3](#0-2) 

So the equality the code implicitly assumes — "bytes verified by the HMAC == identity fields (`shop`, `topic`) trusted by the handler" — does not hold. The verified quantity is `raw_body` only; the parsed/trusted quantities `request.shop` and `request.topic` come from attacker-controllable headers and are handed directly into `WebhookMetadata`, which the registered handler executes against: [1](#0-0) 

Because `api_secret_key` is one value shared across all shops that install the app (a multi-tenant OAuth app), a valid `(body, hmac)` pair legitimately produced for one tenant is cryptographically indistinguishable from a valid pair for any other tenant when the body content is the same — the signature carries no tenant binding at all.

### Impact Explanation
An attacker who installs the app on their own store (fully unprivileged relative to any other merchant) can capture a legitimate webhook delivery — many topics have small, predictable, or attacker-triggerable bodies (e.g. `"{}"`, or a body the attacker controls by triggering the event on their own shop). They then replay the exact same `raw_body` and `hmac` to the app's public webhook endpoint while spoofing `shopify-shop-domain` to a victim shop and/or `shopify-topic` to a different registered topic. `HmacValidator.validate` will accept it, and `handler.handle` will run believing the event genuinely originated from the victim shop for that topic. Depending on what handlers do (revoke access on `app/uninstalled`, purge data on `shop/redact` or `customers/redact`, mutate per-shop state keyed by `data.shop`), this is a cross-tenant integrity/availability break achieved without ever touching the victim's credentials — falling under the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only: (1) the attacker's own (unprivileged) installation of the app to obtain one valid signed webhook body, and (2) network access to POST to the app's public webhook endpoint with forged headers — no secret, token, or victim-shop access needed. This is fully reachable by any unprivileged internet user who can install the app once.

### Recommendation
Bind the identity fields into what is verified: include `shop`, `topic`, and `webhook_id` in the HMAC-computed signable content (or otherwise cryptographically bind them to the signed body), and/or require host applications to independently verify that `request.shop` corresponds to a shop with an active installation before trusting `WebhookMetadata#shop`. At minimum, document prominently that `shop`/`topic` on `ShopifyAPI::Webhooks::Request` are unauthenticated and must not be trusted for tenant-identification without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers (or otherwise obtains) a webhook delivery whose body is small/known, e.g. raw body `"{}"`. Capture the resulting `shopify-hmac-sha256` value — this is `HMAC-SHA256(api_secret_key, "{}")`, valid for that exact body regardless of shop.
2. Attacker crafts a raw HTTP POST to the app's webhook endpoint with:
   - `shopify-topic: app/uninstalled` (or any topic registered by the app)
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-hmac-sha256: <captured value>`
   - body: `"{}"`
3. `ShopifyAPI::Webhooks::Request.new` parses `shop = "victim-shop.myshopify.com"`, `topic = "app/uninstalled"` from headers, unrelated to the signed bytes.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, "{}")` and matches the attacker's captured signature — validation succeeds.
5. The registered handler for `app/uninstalled` executes with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", body: {})`, acting on the victim tenant's behalf without any credential belonging to that tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
