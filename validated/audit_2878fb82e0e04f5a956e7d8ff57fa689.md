### Title
Floor-rounding leak in `Router._computeBuy`/`_computeSell` lets repeated buy/sell cycles erode `Pair` reserves below the launch-time virtual floor, causing an unguarded subtraction underflow that permanently bricks the curve — ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` (and its preview twin `previewLtUntilGraduation`) compute `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with no check that `assetReserve` is still ≥ the recovered virtual floor [1](#0-0) . This is the same bug class as CVE‑2025‑39817: a subtraction is performed on the assumption that an invariant (`len ≥ EFI_VARIABLE_GUID_LEN` in the kernel case, `assetReserve ≥ virtualLtReserve` here) always holds, without validating it first. In `efivarfs_d_compare` a violated invariant leads to an OOB read; here, in checked Solidity 0.8.24 arithmetic, a violated invariant leads to a `Panic(0x11)` underflow revert, which is reachable by any unprivileged trader and permanently bricks every entry point that calls `canGraduate` for that token.

### Finding Description
`Router._computeBuy` and `Router._computeSell` derive swap outputs from `Pair.k()` using floor division, and both roundings are biased in the *trader's* favor:

- Buy: `tokensOut = reserveToken - (k / newReserveAsset)` — flooring `k / newReserveAsset` makes the subtrahend smaller, so `tokensOut` is rounded **up** (buyer gets slightly more tokens than the exact curve amount). [2](#0-1) 
- Sell: `assetOut = reserveAsset - (k / newReserveToken)` — same flooring bias makes `assetOut` rounded **up** (seller gets slightly more LT than the exact curve amount). [3](#0-2) 

`Pair.swap` only enforces `(newTokenReserve+1)*(newAssetReserve+1) < k()` — the `+1` slack — and never re-derives or updates the stored `k`, which is fixed once at `mint()` to `tokenReserve * assetReserve` [4](#0-3) . Because the check only bounds how far the *product* may fall below `k`, and every buy/sell leaks a small excess to the trader, an unprivileged trader can repeatedly `buy`/`sell` small amounts through `Zap.buy`/`Zap.sell` (which call `Router.buy`/`Router.sell` via `Bonding`) to accumulate rounding leakage that steadily depletes `assetReserve` toward (and eventually below) `_launchTimeVirtualLtReserve(token_, pair) = Pair.k() / Token.TOTAL_SUPPLY()` — the launch-time virtual LT floor recovered in [5](#0-4) .

Once `assetReserve < virtualLtReserve`, the unguarded subtraction in `canGraduate`:

```solidity
(, uint256 assetReserve) = IPair(pair).getReserves();
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
```

reverts with an arithmetic underflow panic. `canGraduate` is invoked unconditionally after every successful buy in `Bonding._executeBuy` [6](#0-5) , and is also invoked in `Zap.sell`'s pre-graduation check [7](#0-6)  and in the permissionless `triggerGraduation` [8](#0-7) . Since these are the only ways to buy, sell, or graduate a curve token, once the invariant is violated **every** trade and every graduation attempt on that token reverts — the token, its creator's raised funds, and every trader's remaining position are permanently stuck in `Lifecycle.Curve` with no admin recovery path (no setter mutates `assetReserve` or bypasses `canGraduate`).

### Impact Explanation
This is a permanent freeze of trader and creator funds: once `assetReserve` dips below the recovered virtual floor, `Zap.buy`/`Zap.sell`/`Bonding.triggerGraduation` all revert unconditionally for that token (they all route through `canGraduate`), locking in the pair the LT raised from all prior buyers and the creator's seed, with no path to graduate or exit via the curve. This satisfies the "permanent freezing of trader, creator or LP funds" bar in the validation rules, and the underlying rounding bias is itself a small continuous economic leak from the pool to any trader willing to round-trip, satisfying "unbacked token or LT payouts" as a secondary effect.

### Likelihood Explanation
The path only requires an unprivileged trader to repeatedly call `Zap.buy`/`Zap.sell` (or `buyWithPermit`/`sellWithPermit`) on a single curve token — no privileged role, no race condition beyond ordinary sequential transactions, and no interaction with BounceTech's LT internals is needed. The magnitude of leakage per trade is tiny (bounded by integer-division rounding, at most 1 wei-scale unit per swap on the losing side), so many round trips are needed, but there is no cap on the number of trades a single address can submit against its own curve token, and gas cost per call is the only friction. `MIN_TRANSACTION_SIZE`/`minUsdcAmount` floors limit how small each round trip can be, which affects the number of iterations required but not feasibility.

### Recommendation
- In `Bonding.canGraduate` and `previewLtUntilGraduation`, guard the subtraction: if `assetReserve <= _launchTimeVirtualLtReserve(token_, pair)`, treat `realLtRaised` as `0` instead of underflowing, mirroring the saturating-subtract pattern already used elsewhere in the same file (e.g. `_ltSwapInventory`, `_sweepLTToOwner`) [9](#0-8) .
- Separately, remove or shrink the systemic rounding bias in `Router._computeBuy`/`_computeSell` (e.g., round `tokensOut`/`assetOut` down instead of implicitly up via floor-then-subtract, or explicitly ceil the reserve side instead) so the pool no longer leaks value on every swap regardless of the underflow guard.

### Proof of Concept
1. Launch a token via `Zap.createToken`, establishing `assetReserve = virtualLtReserve` and `Pair.k() = totalSupply * virtualLtReserve` per `Bonding._deployAndSeed` [10](#0-9) .
2. As any unprivileged address, repeatedly call `Zap.buy(tokenAddress, minUsdcAmount(), 0, address(0))` followed immediately by `Zap.sell(tokenAddress, tokensOut, 0)` for the tokens just received, using the minimum permitted `usdcAmount` each round.
3. Each round-trip pair leaks a small amount of LT out of the `Pair` beyond what the exact (non-floored) curve math would allow, per the rounding bias in `Router._computeSell` [3](#0-2) , gradually pushing the stored `assetReserve` toward `_launchTimeVirtualLtReserve`.
4. Once `assetReserve` strictly drops below the recovered virtual floor, the next call to any of `Zap.buy`, `Zap.sell`, or `Bonding.triggerGraduation` for this token reverts with an arithmetic underflow panic inside `canGraduate` [1](#0-0) , permanently bricking all trading and graduation for the token.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
