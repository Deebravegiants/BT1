### Title
Unguarded relayer/sender fee transfer in `EvmHost.dispatchIncoming(GetResponse)` / `dispatchTimeOut` can revert an entire batched delivery, causing DoS of unrelated messages - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost` isolates failures of the application callback itself (`onGetResponse`, `onPostRequestTimeout`, `onGetTimeout`) by invoking them through a low-level `.call` and checking `success` before proceeding, explicitly to avoid "reverting the entire batch." However, the reward/refund transfer that runs *after* a successful callback — `IERC20(feeToken()).safeTransfer(relayer, fee)` in `dispatchIncoming(GetResponse,...)`, and `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` in both `dispatchTimeOut` overloads — is **not** wrapped in the same isolation pattern. If this transfer reverts (e.g. `feeToken()` is a blacklist-capable stablecoin such as USDC and the recipient address is blacklisted, or the recipient is a malicious ERC777-style hook contract), the whole external call reverts and propagates up through `HandlerV2.handleGetResponses` / `handlePostRequestTimeouts` / `handleGetRequestTimeouts`, which loop over multiple unrelated responses/timeouts in a single relayer transaction (and can additionally be wrapped in `IHandlerV2.batchCall`). This is the same bug class as the reported `UFarmPool.quexCallback()` issue: a single blacklisted/malicious address can force an entire otherwise-valid batch to fail.

### Finding Description
`HandlerV2.handleGetResponses` verifies a Merkle multiproof over a batch of GET responses and then, in a loop, calls `host.dispatchIncoming(leaf.response, _msgSender())` for every response in the batch: [1](#0-0) 

`EvmHost.dispatchIncoming(GetResponse, address)` correctly isolates the app callback failure with a low-level call/success check, but then performs the relayer fee payout unconditionally: [2](#0-1) 

The same unguarded pattern exists for timeout refunds, both dispatched in per-item loops from `HandlerV2.handlePostRequestTimeouts` / `handleGetRequestTimeouts`: [3](#0-2) [4](#0-3) [5](#0-4) 

In every case, `IERC20(feeToken()).safeTransfer(...)` is a plain (non-try/catch, non-low-level) external call. If it reverts — which is trivially possible if `feeToken()` is configured to a blacklist-enforcing token (USDC-style) and the payee (`relayer` in the GET-response case, or `meta.sender`/original requester in the timeout case) is a blacklisted address, or the payee is a contract with a reverting `receive`/hook — the revert bubbles all the way out of `dispatchIncoming`/`dispatchTimeOut`, out of the enclosing handler loop, and reverts the entire transaction. Because these handler functions process **batches** of unrelated responses/timeouts from potentially many different users/relayers in one transaction (and can be further composed via `IHandlerV2.batchCall`), a single attacker-controlled blacklisted/malicious recipient can block delivery of every other item in the same batch.

This mirrors exactly the root cause identified in the external report: lack of per-item isolation around a token transfer inside a loop that processes many independent operations atomically. `EvmHost` even documents the intended design goal ("instead of reverting the entire batch, early return here" in `dispatchIncoming(PostRequest,...)`), showing the fee-transfer paths are an inconsistent application of that same principle.

### Impact Explanation
This is a Medium-severity denial-of-service: an attacker who controls (or becomes) a relayer address that is blacklisted by the fee-token issuer, or who is the original `payer`/`sender` of a GET request/timeout and is blacklisted, can cause `handleGetResponses`, `handlePostRequestTimeouts`, or `handleGetRequestTimeouts` to permanently revert whenever their item is included in a batch with other legitimate messages. Relayers batch messages for gas efficiency (`HandlerV2.batchCall`, `submit_batch_messages` in the tesseract relayer), so this can stall delivery of many independent, valid cross-chain messages/timeouts and relayer fee payouts until relayers learn to exclude the poisoned item — requiring off-chain remediation rather than an on-chain retry, and blocking route liveness for affected batches. It does not directly cause fund loss, but it is a real availability/DoS vector against the messaging pipeline reachable from an ordinary relayed transaction.

### Likelihood Explanation
Reachable by any permissionless relayer submitting `handleGetResponses`/`handlePostRequestTimeouts`/`handleGetRequestTimeouts` (or `batchCall`) — no special privilege needed. The only precondition is that `feeToken()` supports a blacklist mechanism (e.g. USDC) or that the payee can be made to revert on receipt (malicious contract as `payer`/relayer). Given Hyperbridge deployments commonly use USDC-class fee tokens on EVM chains, and relayers naturally batch multiple items to save gas, the likelihood of a legitimate batch inadvertently containing one poisoned item — or an attacker deliberately engineering this — is realistic.

### Recommendation
Wrap the fee/refund transfers in `dispatchIncoming(GetResponse,...)`, `dispatchTimeOut(GetRequestTimeout,...)`, and `dispatchTimeOut(PostRequestTimeout,...)` in a try/catch (or low-level `call` with a success check, consistent with the pattern already used for the `onAccept`/`onGetResponse`/`onPostRequestTimeout` callbacks). On transfer failure, do not revert the whole dispatch: either skip the payout and leave it claimable via a separate pull-based withdrawal function, or emit a failure event and retain the entitlement for retry, mirroring the `_requestReceipts`/`_responseReceipts` rollback-and-retry design already used for callback failures.

### Proof of Concept
1. Configure/deploy `EvmHost` with `feeToken()` returning a USDC-like ERC-20 that reverts transfers to blacklisted addresses.
2. Have relayer address `R` (or GET-request `payer`/`sender` `S`) added to the token's blacklist by the issuer, out of the protocol's control.
3. A legitimate relayer builds a batch containing several unrelated GET responses/timeouts plus one response/timeout whose relayer/sender is `R`/`S`, and submits it via `HandlerV2.handleGetResponses` (or `handlePostRequestTimeouts`/`handleGetRequestTimeouts`, optionally through `batchCall`).
4. Inside the loop, `EvmHost.dispatchIncoming`/`dispatchTimeOut` executes `IERC20(feeToken()).safeTransfer(R_or_S, fee)` for the poisoned item; the token reverts.
5. The revert propagates out of the handler function, reverting the entire transaction — none of the other unrelated, valid responses/timeouts in the batch are delivered, even though only one item was problematic.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
