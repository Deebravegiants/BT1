## Title
Webhook `shop` (and topic/api_version/webhook_id) is trusted from unauthenticated headers and not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, while the `shop` (tenant identity), `topic`, `api_version`, and `webhook_id` values used to route and process the webhook are all read directly from HTTP headers that are never included in the signed payload.

### Finding Description
`Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string`: [1](#0-0) 

This method returns only `@raw_body` — none of the Shopify headers are part of the signable string. Yet immediately after this HMAC check succeeds, the library trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id`, all of which are read straight from attacker-controllable HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

and these unauthenticated values are then handed to the application-level handler as the tenant/routing context: [3](#0-2) 

The identity-binding equality that should hold is: `shop used to attribute/process the webhook == shop that was cryptographically verified by the HMAC`. Because `to_signable_string` only covers the body, this equality does not hold — the HMAC only proves "this body was signed by our app's shared `client_secret`" (the same secret is used for every shop installation of the app), it proves nothing about which shop the request is claiming to be from.

An attacker who installs the same app on their own (attacker-controlled) shop can trigger a legitimate webhook delivery from Shopify with a validly computed HMAC for a body they control (e.g. a webhook payload whose body content is influenced by fields the attacker sets on their own store, such as an order note, customer field, or product title). Since the HMAC signature only binds the body — not the `shop-domain` header — the attacker can then replay that same signed body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` will still return `true` because it only re-computes the HMAC over `@raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented/intended, see `Registry.process` at `lib/shopify_api/webhooks/registry.rb:198`) to select which tenant's session/data to act on, this allows a low-privilege attacker (merely another merchant/installer of the same app) to inject data attributed to a victim shop, or to have handlers execute cross-tenant actions using a payload the attacker fully controls the content of. This is a cross-tenant confusion / cross-tenant access primitive matching the report's abstract bug class ("a field acted on but not covered by the HMAC").

### Likelihood Explanation
Requires only that the attacker be able to install the app on any shop they control (an "unprivileged internet user" from the app's perspective) and be able to trigger an inbound webhook whose body content they can shape. No access to `api_secret_key`, access tokens, or TLS interception is required — the attacker uses their own legitimately-issued, validly-signed webhook and replays it with a forged shop header.

### Recommendation
Include `shop-domain` (and ideally `topic`, `api_version`, `webhook-id`) in the signable string validated against the HMAC, or otherwise cryptographically bind the shop identity to the signed payload before it is trusted for routing/processing in `Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook subscription (e.g. `orders/create`) whose body the attacker controls (order fields they set themselves).
2. Shopify delivers the webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`.
3. Attacker captures this request and resends it directly to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) — the body is unchanged, so validation passes.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and processes attacker-supplied data as if it originated from the victim shop.
