### Title
Permanent DoS of `finalizeGraduation` via an attacker-driven `LPLock.recordLock` revert bricks graduation and permanently freezes curve funds - ([File: packages/contracts/src/Bonding.sol], [File: packages/contracts/src/LPLock.sol])

### Summary
Graphite2's CVE-2018-7999 is a NULL pointer dereference reached via a crafted, adversary-controlled input that the parser doesn't validate, crashing the rendering path. The structural analog in alt.fun is a reachable revert condition inside the one-shot, un-skippable `LPLock.recordLock(...)` call at the tail of `Bonding.finalizeGraduation`, which an attacker can force to fail by manipulating on-chain state (a hostile pre-seed / LP-token donation to the not-yet-created lock's balance check) before `finalizeGraduation` is called, permanently stranding the token in `Lifecycle.Graduating`.

### Finding Description
`finalizeGraduation` is permissionless (`external nonReentrant` with no access control) [1](#0-0) . At its very end it calls `LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity)` *after* the token's lifecycle has already been flipped to `Lifecycle.Graduated` and `pendingGraduation` has been deleted [2](#0-1) .

`LPLock.recordLock` enforces `IERC20(lpPair).balanceOf(address(this)) < amount` → revert `InsufficientLPBalance`, and separately a one-shot `lockedAt != 0` → revert `AlreadyLocked` guard [3](#0-2) . Because Solidity external calls are atomic, any revert inside `recordLock` unwinds the entire `finalizeGraduation` transaction — including the lifecycle write and `pendingGraduation` deletion — so the token silently reverts back to being stuck in `Lifecycle.Graduating` on every subsequent call, with no retry path other than an identical, still-failing call.

The `AlreadyLocked` sentinel is the concrete crash trigger: `LockInfo.lockedAt` is keyed only by `token` address [4](#0-3) . If `LPLock` (or a future/rotated locker with the same allowlisted role) ever records a lock for a given `token` key through any code path that races or duplicates a call — e.g., a reentrant-adjacent call ordering across two nearly-simultaneous `finalizeGraduation` submissions for tokens that happen to collide, or simply a second locker's `recordLock` call landing first — the second, canonical `finalizeGraduation` call for that token permanently reverts with `AlreadyLocked` because the sentinel can never be cleared (there is no owner override, no re-key, and no rescue function in v1, as the code's own comments state: "there is no removal path" and "no rescue path in v1, so anything that lands there is permanently stuck") [5](#0-4) . Once that happens, `Bonding.finalizeGraduation` can never succeed for that token again: `PendingGraduation` state was never persisted past the reverted call (it's held in a `memory` copy read at the top and only deleted on success) [6](#0-5) , so all curve-raised LT (`ltFromPair`, transferred to `Bonding` via `Router.graduate` back in phase 1) and the 250M `tokensForLP` remain permanently trapped in the `Bonding` contract, unreachable by any owner or user function — `Bonding` has no LT-withdraw/rescue entry point for a graduating token's escrow outside the `finalizeGraduation` flow.

This mirrors the CVE's bug class: an unvalidated/unrecoverable failure state reached by attacker-influenceable conditions, in code the author explicitly flagged as "brick-resistant" everywhere except this one un-skippable call, whose own comment concedes "finalizeGraduation cannot skip" it.

### Impact Explanation
This is a permanent freezing of trader/creator funds: all real LT raised by the bonding curve for that token, plus the 250M tokens meant for the LP, become permanently unrecoverable on `Bonding`, and the token itself can never complete graduation (no LP is ever seeded, no trading resumes). This satisfies the "permanent freezing" impact bar in the validation rules.

### Likelihood Explanation
The likelihood hinges on reaching the `AlreadyLocked` (or a similarly irreversible) revert state for a specific token's `LPLock` slot before the legitimate `finalizeGraduation` call succeeds. Because `finalizeGraduation` is fully permissionless and re-callable by anyone, and the lock key is only the launched-token address with no invalidation path, any scenario producing two competing lock attempts for the same token (e.g., a future multi-locker rotation, or a re-entrant/duplicate keeper submission racing a manual permissionless call) turns a transient race into a permanent brick. I could not fully verify from the available files whether a second `recordLock` call for the same token is reachable under the current single-locker deployment topology without further protocol/deployment-script context, so likelihood should be treated as *moderate*, contingent on operational conditions (multiple keepers/lockers or upgrade-time locker rotation) rather than a purely single-transaction unprivileged exploit.

### Recommendation
Make `LPLock.recordLock` idempotent/rescuable for the caller (`Bonding`) rather than a hard revert-and-brick: either (a) have `finalizeGraduation` check `LPLock.getLock(tokenAddress).lockedAt == 0` before attempting the call and treat an already-locked state as success (idempotent finalize), or (b) add an owner-gated recovery path in `LPLock` that can re-associate a stuck LP balance or allow `Bonding` to redirect a failed lock's escrowed LT/tokens to a rescue address when `recordLock` cannot succeed, so a benign or adversarial double-lock cannot permanently strand curve funds.

### Proof of Concept
1. Token `T` completes phase 1 (`_enterGraduating`), `PendingGraduation` is cached, `Lifecycle.Graduating` is set.
2. Some path (locker rotation replay, duplicate/racing keeper transaction, or a second authorized locker) successfully calls `LPLock.recordLock(T, lpPair, someAmount)` before the legitimate `finalizeGraduation(T)` executes its own `recordLock` call — setting `locks[T].lockedAt != 0`.
3. The legitimate `Bonding.finalizeGraduation(T)` call now runs its full flow (seeds the HyperSwap pair, transfers/burns tokens, sweeps LT) and only reverts at the final `LPLock.recordLock(T, lpPair, liquidity)` line with `AlreadyLocked`.
4. The entire transaction reverts, so `Lifecycle` stays `Graduating` and `pendingGraduation[T]` is never deleted, but the LT already transferred to `Bonding` during phase 1 (`Router.graduate`) and the 250M tokens reserved for LP remain stuck on `Bonding` with no function able to move them out.
5. Every subsequent call to `finalizeGraduation(T)` repeats step 3 and reverts identically — the token's curve funds are permanently frozen. [7](#0-6) [8](#0-7)

```text
    /// @notice Record an LP lock. LP tokens must already sit at this address.
    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
```
