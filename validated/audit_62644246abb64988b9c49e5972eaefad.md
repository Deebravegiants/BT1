### Title
Webhook `shop`/`topic` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Registry.process` verifies authenticates *body bytes* only, not the shop or topic identity that the same request claims via headers. Any attacker capable of obtaining one valid `(body, hmac)` pair for this app (e.g., by installing the app on their own shop and triggering a webhook they control) can replay that identical body+hmac to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers to claim it originated from a different shop and/or topic. Since the HMAC check passes (it never inspects those headers), the handler processes attacker-controlled data as if it came from another tenant.

### Finding Description
The equality that should hold is: `shop/topic authenticated by HMAC == shop/topic acted upon by the handler`. In this gem it instead holds: `bytes verified by HMAC (raw body) != identity fields consumed by the handler (shop-domain, topic headers)`.

- `Request#hmac` reads `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header [4](#0-3) .
- `Request#to_signable_string` returns `@raw_body` only — no shop, topic, or webhook id is folded into what gets signed/verified [1](#0-0) .
- `Request#shop`, `#topic`, `#api_version`, `#webhook_id` are pulled straight from headers, entirely outside the HMAC's scope [2](#0-1) .
- `Registry.process` calls `Utils::HmacValidator.validate(request)` (which only checks the body-bound signature) and, if it passes, immediately trusts `request.topic` and `request.shop` to look up a handler and build `WebhookMetadata` that is handed to app code [3](#0-2) .

Because the HMAC secret (`Context.api_secret_key`) is shared by the app across all of its installed shops, any tenant that has installed the app can obtain a legitimately-signed `(body, hmac)` pair from Shopify for a webhook topic they can trigger (e.g. `products/update` on their own store, with attacker-chosen body content). Since the signature never covers `shop-domain`/`topic`, that exact `(body, hmac)` pair remains valid when replayed with different `shop-domain`/`topic` headers. The webhook handler receives `WebhookMetadata` claiming the victim's shop/topic while the body content is entirely attacker-controlled [5](#0-4) .

### Impact Explanation
This breaks the cross-tenant isolation boundary: a merchant/attacker who has valid access to the app on their own shop can cause the app to process attacker-controlled webhook data attributed to a different shop's tenant (cross-tenant access/data injection), which is a Critical-severity outcome per the given impact classes.

### Likelihood Explanation
Requires only that the attacker has installed the app themselves (a normal, low-privilege state — not requiring `api_secret_key` or any leaked credential) and can trigger at least one webhook delivery for a topic they control, then replay it with modified headers to the app's public webhook endpoint. No credential theft is needed since the HMAC is copied verbatim from a legitimately Shopify-issued webhook.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived identity fields to the signature before trusting them — e.g., fail closed by re-deriving/confirming `shop`/`topic` from a separately authenticated channel, or require the `to_signable_string` used for verification to incorporate the header values so a replay with altered headers invalidates the signature.

### Proof of Concept
1. App installs and receives a legitimate Shopify webhook for shop `attacker.myshopify.com`, topic `products/update`, with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: products/update`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and an attacker-crafted JSON body.
2. Attacker captures this exact `(raw_body, hmac)` pair.
3. Attacker (or anyone who can reach the app's public webhook endpoint) resends the identical raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC [6](#0-5) .
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker JSON>, ...)`, so the app processes attacker-controlled data under the victim shop's identity [7](#0-6) .
