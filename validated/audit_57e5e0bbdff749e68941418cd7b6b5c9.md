### Title
Vault `principal-scaled` diverges from `Σ market-vault.debt-scaled` because `system-repay` reduces principal via an aggregate ratio instead of the per-user index conversion - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, `mainnet/contracts/market/v0-market-vault.clar`, `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.repay` reduces a user's scaled debt with the exact inverse of the index formula used at borrow time (`mul-div-down(safe-amount, INDEX-PRECISION, borrow-index)`), but the vault's `system-repay` reduces the pool-wide `principal-scaled` with an unrelated ratio formula, `calc-principal-ratio-reduction = mul-div-down(capped-amount, scaled-principal, debt)`. When more than one borrower's scaled debt contributes to the pool's aggregate `scaled-principal`/`total-debt()`, these two formulas are mathematically independent and round differently, so `vault.principal-scaled` drifts away from `Σ market-vault.debt-scaled` even though every individual repay call is internally self-consistent.

### Finding Description
Invariant that must hold: `vault.principal-scaled * idx == Σ_users(market-vault.debt-scaled) * idx (== vault.total-debt())`.

Code path:
- `market.borrow` (`mainnet/contracts/market/v0-4-market.clar:1289-1296`) calls `vault-system-borrow` then `debt-add-scaled` with `scaled-debt-added = convert-to-scaled-debt(...)`. Both the vault's `system-borrow` (`v0-vault-*.clar:871-877`, `scaled-amount = mul-div-up(amount, INDEX-PRECISION, idx)`) and the market's scaled-debt use the same `mul-div-up` formula against the same cached index, so borrow never introduces divergence.
- `market.repay` (`v0-4-market.clar:1330-1361`) derives `repaid-scaled-debt` purely from the user's own `account-scaled-debt` and `borrow-index` via `mul-div-down(safe-amount, INDEX-PRECISION, borrow-index)`, capped by the user's own debt, and forwards `amount-to-repay = mul-div-up(repaid-scaled-debt, borrow-index, INDEX-PRECISION)` to `vault-system-repay`.
- `vault.system-repay` (`v0-vault-usdc.clar:900-916` and equivalents at lines 863-940 across all `v0-vault-*.clar`) recomputes the scaled-principal reduction independently from the **pool aggregate** state: `principal-reduction = calc-principal-ratio-reduction(capped-amount, scaled-principal, debt) = mul-div-down(capped-amount, scaled-principal, debt)`.

These two reductions are equal only in degenerate cases (e.g., a lone borrower fully repaying, where the division is exact). As soon as the pool has any other outstanding debt (`scaled-principal` and `debt` reflect the sum of all borrowers, not just the attacker's), the two formulas diverge. Concrete numeric trace (INDEX-PRECISION=1000, idx=1300): attacker's own scaled debt = 6, another borrower's scaled debt = 1 (pool total scaled-principal = 7, `total-debt()=ceil(7*1300/1000)=10`). Attacker fully repays their own 6 scaled-debt via `amount-to-repay = 8` (computed purely from their own 6/1300/1000 figures). `market-vault.debt-remove-scaled` correctly zeroes the attacker's 6 scaled debt (sum of users' scaled debt = 1, the other borrower). But `vault.system-repay` computes `principal-reduction = mul-div-down(8, 7, 10) = floor(5.6) = 5`, leaving `vault.principal-scaled = 7 - 5 = 2`, i.e. 1 scaled unit (≈1 token unit after re-scaling) higher than the true sum (1). `vault.total-debt()` now reports `ceil(2*1300/1000)=3` versus the real obligation of `ceil(1*1300/1000)=2` — a 1-unit overstatement created by a single ordinary repay call, no privileged access required.

Existing guards do not prevent this: `check-caller-auth`/`check-impl-auth` only gate who can call these functions, not the arithmetic consistency between the vault ledger and the market-vault ledger; there is no cross-check reconciling `principal-scaled` against `Σ debt-scaled`; pause states don't block ordinary repay; and the 1-unit-per-operation cap is enforced only within a single call, not across the whole system.

### Impact Explanation
Each repay call by any borrower, whenever other borrowers hold outstanding debt in the same vault, can shift `vault.principal-scaled` by up to a few scaled units relative to `Σ market-vault.debt-scaled`, independent of whether that specific call is "correct" from the caller's own-account perspective. This is repeatable: an attacker can loop `borrow(amount)`/`repay(amount)` on their own account, and because the rounding direction of `calc-principal-ratio-reduction` depends on the exact aggregate `scaled-principal`/`debt` at call time (which the attacker's own borrow/repay cycle also perturbs), the attacker can choose amounts each cycle to bias the ratio computation, accumulating a systematic (not merely random ±1) drift over K cycles. The resulting mispricing of `vault.total-debt()` corrupts `total-assets()`, the utilization/interest-rate curve, and consequently the LP share price — this is a protocol-insolvency-class bug (Critical), borne by LPs and other borrowers/lenders whose position values and interest accrual are derived from the corrupted aggregate state.

### Likelihood Explanation
No privileged access is required — only an unprivileged principal calling public `borrow`/`repay` on a vault/market pair that already has other outstanding debt, which is the normal state of any live lending pool. Capital cost is bounded to the amount borrowed/repaid per cycle (fully recovered each cycle since it's the attacker's own debt), so the attack is essentially free to repeat many times, and it can be combined with the attacker's own borrow to seed favorable aggregate ratios before repaying, making the divergence direction attacker-influenceable.

### Recommendation
Make `system-repay`'s scaled-principal reduction use the same index-based formula the market layer uses for the user (`mul-div-down(capped-amount, INDEX-PRECISION, idx)`) rather than ratioing against the pool aggregate `scaled-principal`/`debt`. If an aggregate ratio approach is kept for socialization purposes, it must be reserved exclusively for `socialize-debt` (bad-debt writedown), and ordinary `system-repay` should mirror the exact per-repayment scaled-amount computed by the caller (the market), e.g. by having `market.repay` pass `repaid-scaled-debt` directly into `system-repay` and having the vault derive its principal reduction from that same value instead of recomputing it via a different, aggregate-dependent formula.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Deploy market + vault with two borrowers, Alice and Bob (attacker = Alice).
2. Bob borrows an amount so that his `debt-scaled` in `market-vault` is a small fixed value (e.g., corresponds to scaled debt `1`), and leave it untouched for the rest of the test.
3. Alice borrows an amount producing scaled debt `6` at the same `idx`/`INDEX-PRECISION` (choose the underlying decimals/index so the raw integers match the worked example, i.e., `idx/INDEX-PRECISION = 1300/1000`).
4. Record `vault.principal-scaled`, `vault.total-debt()`, and `Σ` of `market-vault.get-account-scaled-debt` over both accounts.
5. Alice calls `market.repay` for an amount that fully covers her own debt (`amount-to-repay` computed the same way as `max-repay-tokens`).
6. After the call, assert:
   - `market-vault` sum of scaled debt over Alice+Bob == `1` (Bob's untouched debt).
   - `vault.principal-scaled` == `2` (not `1`), reproducing the divergence.
   - `vault.total-debt()` == `3` while the true obligation (`Σ debt-scaled` converted via idx) == `2`.
7. Repeat steps 3–6 in a loop (K cycles) with Alice re-borrowing and repaying, asserting the gap between `vault.total-debt()` and the off-chain-computed `Σ(debt-scaled)*idx/INDEX-PRECISION` grows beyond the bound of 1 wei per transaction (i.e., grows roughly linearly with K rather than staying capped at a single rounding unit), confirming systemic, repeatable ledger divergence.
