Audit Report

## Title
`submit_commitment` charges a hardcoded zero weight regardless of validator-set size, signature count, or MMR proof length - ([File: bridges/modules/beefy/src/lib.rs])

## Summary
`submit_commitment` in `bridges/modules/beefy/src/lib.rs` is annotated with a fixed `#[pallet::weight(0)]` while performing verification work (merkle-root recomputation over the full validator set, per-signature ECDSA/BLS checks, and MMR proof verification) that scales with attacker-supplied input sizes. This mismatch means the declared/charged weight does not reflect the true cost of the call, allowing an unprivileged signed account to make the runtime perform substantial computation for negligible fees.

## Finding Description
The `submit_commitment` extrinsic is declared with a static zero weight: [1](#0-0) . Notably, this stands in contrast to the other calls in the same pallet (`initialize`, `set_owner`, `set_operating_mode`), which are given non-zero, `DbWeight`-derived weights and are marked `DispatchClass::Operational` [2](#0-1) , showing that the pallet author explicitly chose to leave `submit_commitment`'s weight at literal `0` rather than relying on a benchmarked cost.

Internally, the call does real work proportional to attacker-controlled input sizes:
- `utils::verify_authority_set` recomputes a merkle root over the full `authority_set.validators()` list [3](#0-2) .
- `utils::verify_signatures` iterates and calls `authority.verify(sig, &msg)` — a full cryptographic signature check — for entries up to `authority_set.len()` [4](#0-3) .
- `utils::verify_beefy_mmr_leaf` calls `verify_mmr_leaves_proof`, whose cost scales with `mmr_proof.items.len()` [5](#0-4) .

The only pre-verification guards are `Self::ensure_not_halted()`, `ensure_signed(origin)`, and `RequestCount < MaxRequests` [6](#0-5) . `RequestCount` is only incremented on a *successful* import [7](#0-6) , so it does not throttle repeated calls with large-but-invalid signature sets or proofs that fail deep inside verification after the expensive work has already run. Also note the pallet is declared with `#[frame_support::pallet(dev_mode)]` [8](#0-7) , and the weight was still explicitly hardcoded to `0` rather than being derived from a `WeightInfo` trait — there is no `WeightInfo` type anywhere in this pallet's Config [9](#0-8) , confirming no benchmarking-based weight accounting exists for this pallet at all.

## Impact Explanation
Because weight is fixed at zero, transaction fees for `submit_commitment` do not scale with the actual computational cost of verifying a large validator set, many signatures, or a long MMR proof. Any signed account can invoke this extrinsic with maximally sized (though not necessarily successfully-imported) inputs, forcing the node to perform disproportionate CPU work (merkle-root recomputation + per-authority signature verification + MMR proof verification) relative to the fee charged. This undermines the weight-based accounting the runtime relies on to bound per-block execution time, which is a legitimate weight-accounting/DoS-amplification concern in the bridges pallet.

## Likelihood Explanation
The call is reachable by any signed, unprivileged account once the pallet is initialized and not halted — there is no special permission required. `MaxRequests`/`RequestCount` only bounds *successful* commitment imports per block window, not the number of calls with invalid signatures/proofs that still trigger the expensive verification path before failing. This makes the issue realistically and repeatably triggerable without governance or relayer privileges.

## Recommendation
Replace `#[pallet::weight(0)]` on `submit_commitment` with a benchmarked weight function (e.g., `WeightInfo::submit_commitment(validator_set.len(), mmr_proof.items.len())`) that scales with `validator_set.len()`, `commitment.signatures.len()`, and `mmr_proof.items.len()`, and/or enforce explicit upper bounds on these sizes via `ensure!` checks prior to performing verification work, consistent with a documented worst-case bound reflected in the declared weight.

## Proof of Concept
1. Initialize the pallet with a large validator set (e.g., via `run_test_with_initialize(1000, ...)` in the existing test harness).
2. Construct a `HeaderAndCommitment` with a full-size `commitment.signatures` vector (matching `authority_set.len()`, e.g. mostly invalid signatures) and a maximal `mmr_proof.items` vector.
3. Call `Pallet::<TestRuntime>::submit_commitment` directly with these inputs and measure the actual work performed inside `utils::verify_signatures` and `utils::verify_beefy_mmr_leaf` (e.g., via instrumented counters around `authority.verify` calls or wall-clock timing).
4. Confirm that the call's declared/charged weight is always `Weight::from_parts(0, 0)` (per `#[pallet::weight(0)]`) regardless of these input sizes, while the measured execution cost scales with `validator_set.len()` and `mmr_proof.items.len()`, demonstrating the accounting mismatch.

fn verify_authority_set<T: Config<I>, I: 'static>(
	authority_set_info: &BridgedBeefyAuthoritySetInfo<T, I>,
	authority_set: &BridgedBeefyAuthoritySet<T, I>,
) -> Result<(), Error<T, I>> {
	ensure!(authority_set.id() == authority_set_info.id, Error::<T, I>::InvalidValidatorSetId);
	ensure!(
		authority_set.len() == authority_set_info.len as usize,
		Error::<T, I>::InvalidValidatorSetLen
	);

	// Ensure that the authority set that signed the commitment is the expected one.
	let root = get_authorities_mmr_root::<T, I, _>(authority_set.validators().iter());
	ensure!(root == authority_set_info.keyset_commitment, Error::<T, I>::InvalidValidatorSetRoot);

	Ok(())
}

fn verify_signatures<T: Config<I>, I: 'static>(
	commitment: &BridgedBeefySignedCommitment<T, I>,
	authority_set: &BridgedBeefyAuthoritySet<T, I>,
) -> Result<(), Error<T, I>> {
	ensure!(
		commitment.signatures.len() == authority_set.len(),
		Error::<T, I>::InvalidCommitmentSignaturesLen
	);

	// Ensure that the commitment was signed by enough authorities.
	let msg = commitment.commitment.encode();
	let mut missing_signatures = signatures_required(authority_set.len());
	for (idx, (authority, maybe_sig)) in
		authority_set.validators().iter().zip(commitment.signatures.iter()).enumerate()
	{
		if let Some(sig) = maybe_sig {
			if authority.verify(sig, &msg) {
				missing_signatures = missing_signatures.saturating_sub(1);
				if missing_signatures == 0 {
					break;
				}
			} else {
				tracing::debug!(
					target: LOG_TARGET,
					%idx,
					?authority,
					?sig,
					"Signed commitment contains incorrect signature of validator"
				);
			}
		}
	}
	ensure!(missing_signatures == 0, Error::<T, I>::NotEnoughCorrectSignatures);

	Ok(())
}

pub(crate) fn verify_beefy_mmr_leaf<T: Config<I>, I: 'static>(
	mmr_leaf: &BridgedBeefyMmrLeaf<T, I>,
	mmr_proof: BridgedMmrProof<T, I>,
	mmr_root: BridgedMmrHash<T, I>,
) -> Result<(), Error<T, I>> {
	let mmr_proof_leaf_count = mmr_proof.leaf_count;
	let mmr_proof_length = mmr_proof.items.len();

	// Verify the mmr proof for the provided leaf.
	let mmr_leaf_hash = BridgedMmrHashing::<T, I>::hash(&mmr_leaf.encode());
	verify_mmr_leaves_proof(
		mmr_root,
		vec![BridgedMmrDataOrHash::<T, I>::Hash(mmr_leaf_hash)],
		mmr_proof,
	)
	.map_err(|e| {
		tracing::error!(
			target: LOG_TARGET,
			error=?e,
			?mmr_leaf_hash,
			root=?mmr_root,
			leaf_count=%mmr_proof_leaf_count,
			len=%mmr_proof_length,
			"MMR proof of leaf verification has failed"
		);

		Error::<T, I>::MmrProofVerificationFailed
	})
}
