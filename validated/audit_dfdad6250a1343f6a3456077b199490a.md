## Title
Missing shop-domain validation in `Oauth.begin_auth` enables OAuth `state` nonce leakage to attacker-controlled hosts, permitting forced OAuth completion / session fixation - (`lib/shopify_api/auth/oauth.rb`)

## Summary

### Finding Description
`ShopifyAPI::Auth::Oauth.begin_auth` builds the Shopify authorization redirect URL directly from the caller-supplied `shop:` argument, with no validation that it is a legitimate `*.myshopify.com` (or other trusted Shopify) domain: [1](#0-0) [2](#0-1) 

The authorization URL is constructed as `auth_base_uri(shop) + "/oauth/authorize?#{query_string}"`, where `auth_base_uri` simply returns `"https://#{shop}/admin"` for any string passed in as `shop`. The query string embeds the freshly generated CSRF `state` nonce, and a `SessionCookie` binding that same `state` to the victim's browser is set *before* the redirect occurs: [3](#0-2) 

This is exactly the class of bug the library itself guards against elsewhere: `ShopifyAPI::Utils::ShopValidator.sanitize!` exists specifically to constrain a caller-supplied `shop` string to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before it is used to build a request URL, and it is applied in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`: [4](#0-3) [5](#0-4) [6](#0-5) 

`begin_auth` is the one entry point in this family that skips this check entirely, even though its own docs describe `shop` as coming straight from the incoming, unauthenticated request (e.g. `shop = request.headers["Shop"]`) that a host app is expected to hand to the library unmodified: [7](#0-6) 

This breaks the intended binding: **host that receives the OAuth `authorize` request (and therefore learns the anti-CSRF `state` nonce) == a trusted Shopify domain**. Because `shop` is neither sanitized nor bound to the `state`/cookie by anything other than string interpolation, an unprivileged internet user can supply `shop=attacker.example` to the app's login route, causing the library to redirect the victim's browser to `https://attacker.example/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=<real-app-callback>&state=<nonce>` while simultaneously setting the real `state` value in a cookie on the victim's own browser for the legitimate app domain.

### Impact Explanation
The attacker's server receives the `state` nonce as a plain query parameter in the redirected request. Because `Oauth.validate_auth_callback` only checks that the callback's `state` matches the victim's session cookie and that the HMAC over `code/shop/state/timestamp/host` validates — it does **not** bind `state` to a specific `shop` at generation time — the attacker can now start their own legitimate OAuth authorization against Shopify for a shop they control, using a URL where they force `state=<leaked nonce>`. Shopify will produce a validly-HMAC-signed callback (`code`, `shop=attacker-shop`, `state=<the leaked nonce>`, `hmac`) for that flow. Delivering that valid Shopify-signed callback URL to the victim (e.g., via a link) causes the victim's browser — which still has the matching `state` cookie set by the original hijacked `begin_auth` redirect — to complete OAuth and install/authorize the app under the **attacker's** shop, while the victim believes they are interacting with their own installation flow. This is a forced OAuth completion / session-fixation primitive, explicitly listed as a High-impact scenario, because it lets an attacker fixate which shop's session gets bound to a victim's browser/session state without needing any secret.

### Likelihood Explanation
`shop` is documented and expected to be taken directly from an unauthenticated request parameter by any app integrating this gem's `begin_auth`, so exploitation requires only that an attacker get a victim to click a crafted login link containing an attacker-controlled `shop` value — no credentials, tokens, or privileged access are required.

### Recommendation
Apply `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (as already done in `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb#migrate_to_expiring_token`) inside `Oauth.begin_auth` before it is used to construct `auth_base_uri`, rejecting any `shop` value that does not resolve to a trusted Shopify domain.

### Proof of Concept
1. Victim visits the vulnerable app's login route with `?shop=attacker.example`.
2. App calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.example", redirect_path: "/auth/callback")`.
3. `begin_auth` sets the `state` cookie in the victim's browser and redirects the victim's browser to `https://attacker.example/admin/oauth/authorize?client_id=...&state=<nonce>&redirect_uri=https://real-app.example/auth/callback&...` — the attacker's server logs the `state`.
4. Attacker separately performs their own legitimate installation flow against a shop they control, injecting the leaked `state` value into the authorize request sent to the real Shopify servers, obtaining a validly Shopify-HMAC-signed callback URL `https://real-app.example/auth/callback?shop=attacker-shop.myshopify.com&code=...&state=<nonce>&hmac=...`.
5. Attacker lures the victim (whose browser still carries the matching `state` cookie from step 2) into visiting that crafted callback URL; `validate_auth_callback` accepts it because both the cookie/state match and the HMAC is valid, completing OAuth for the attacker's shop under the victim's session.

        def auth_base_uri(shop)

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission

    head 307
