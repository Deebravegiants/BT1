### Title
Unsafe `U256::low_u128()` truncation in relayer fee withdrawal silently loses accumulated fees - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet-ismp-relayer`'s `withdraw` function converts the accumulated `U256` fee balance to a `u128` using the unchecked, truncating `low_u128()` cast when the destination is a substrate chain, then unconditionally zeroes the full `U256` balance. This mirrors the report's core bug class: a down-cast (`int256`→`int128` in the audited protocol, here `U256`→`u128`) performed without verifying the value fits in the narrower type, silently truncating instead of reverting.

### Finding Description
In `Pallet::withdraw`: [1](#0-0) 

`available_amount` is read as `U256` from the `Fees` storage map, which is accumulated over many delivered/relayed requests via `pallet_ismp_relayer::accumulate`. When `withdrawal_data.dest_chain` is a substrate chain, the code builds the outbound `WithdrawalRequest` with:

```rust
amount: available_amount.low_u128(),
```

`low_u128()` (from `primitive_types::U256`) does not check whether `available_amount` fits in 128 bits — it simply truncates to the low 128 bits and discards the high bits, silently producing a smaller (effectively arbitrary, modulo 2^128) value whenever the true balance exceeds `u128::MAX`. Regardless of the truncation, the pallet then unconditionally zeroes the full `U256` entry:

```rust
Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());
```

and emits the event with the un-truncated `available_amount`, meaning the accounting event reports one figure while the actual dispatched settlement instructs disbursement of a different (truncated) amount. The dispatched request's `WithdrawalRequest.amount` field is `u128`, so the destination host mints/transfers based on the wrong value while the source-side ledger is fully cleared — the difference between the true `U256` balance and the truncated `u128` is permanently lost with no path to reclaim it, exactly the "safe typecast" gap the audit report calls out for `getNetBalance` and the invariant down-cast.

Note: I was not able to fully verify, within the available index, whether `modules/pallets/relayer/src/accumulate.rs` enforces any bound that prevents `Fees` from ever exceeding `u128::MAX` for a given `(dest_chain, address)` pair. If accumulation is unbounded (fees can be added indefinitely across many relayed messages before a withdrawal is claimed), this truncation is reachable purely by a relayer accumulating enough fee credit and then calling the permissionless `withdraw`/`accumulate_fees` flow — no privileged role is required. If such a bound does exist elsewhere in the pallet, the severity of this specific path is reduced to defense-in-depth, but the unsafe cast pattern itself remains present and inconsistent with the safe-typecast recommendation from the audit.

### Impact Explanation
If reachable, this results in a relayer's legitimately accumulated cross-chain fee balance being permanently and silently reduced/lost on withdrawal — the `Fees` ledger is zeroed unconditionally while only the truncated (`low_u128()`) amount is actually dispatched for settlement on the destination chain. This is a fund-loss/accounting-corruption bug affecting the relayer fee and reward accounting pathway explicitly in scope, with no revert or recovery mechanism.

### Likelihood Explanation
Likelihood depends on whether `Fees` values can realistically exceed `u128::MAX` (a threshold of ~3.4×10^38 base units of the fee token) before a withdrawal is claimed. This requires either (a) no bound on fee accumulation across many messages/relayers over time, or (b) a fee-token/decimal configuration that makes reaching this threshold practically achievable. This was not fully confirmed against `accumulate.rs`. Absent such a bound, the likelihood is low-to-moderate given today's realistic fee volumes, but the code path itself constitutes an unchecked type-cast defect regardless of current practical odds — consistent with the "Acknowledged" severity classification the original report gives to unsafe-casting findings that are not immediately exploitable but violate the safe-cast invariant.

### Recommendation
Replace `available_amount.low_u128()` with a checked conversion, e.g. `u128::try_from(available_amount)`, and reject (or split into successive withdrawals) any amount that does not fit in `u128`, rather than silently truncating. Additionally, do not zero the full `Fees` entry unless the entire balance was successfully included in the dispatched withdrawal amount — decrement `Fees` by exactly the amount actually withdrawn so any un-withdrawn remainder (in case of a deliberately staged multi-step withdrawal) stays claimable.

### Proof of Concept
Conceptual PoC (bounded by inability to confirm accumulation limits from the indexed code):
1. A relayer accumulates cross-chain delivery fees via the permissionless `accumulate_fees` flow across many requests/epochs targeting the same `(dest_chain, address)` key, driving `Fees::<T>::get(dest_chain, address)` above `u128::MAX`.
2. The relayer calls `withdraw` with a valid signature for that `(nonce, dest_chain)`.
3. `available_amount.low_u128()` truncates the value; `Fees` is reset to `U256::zero()` unconditionally.
4. The relayer receives only the truncated amount on the destination chain, permanently losing the remainder that was already zeroed from `Fees`. [2](#0-1) [3](#0-2)
