### Title
Unsigned cross-chain calldata lets the bridge dispatch arbitrary runtime calls under a self-declared origin - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
CVE-2016-4473 is a case of an incomplete fix: PHP kept instantiating and invoking attacker-influenced objects (`phar` metadata) from untrusted serialized input without properly authenticating that the object should be trusted before code paths acted on it. The closest reachable analog in this codebase is `pallet-hyper-fungible-token`'s `on_accept` handler, which decodes an attacker-supplied `call_data` blob carried inside a cross-chain token message and — when no signature is attached — directly dispatches it as a live `RuntimeCall` using an origin taken from a self-reported field of the same untrusted message, rather than from any cryptographically verified identity.

### Finding Description
When a `HyperFungibleToken`/`WrappedHyperFungibleToken` transfer arrives via ISMP, `on_accept` ABI-decodes the `Message` body and, if `message.data` is non-empty, decodes it into `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` [1](#0-0) .

If a `signature` is present, it is cryptographically verified against `beneficiary_bytes` and the call is dispatched under the beneficiary's identity [2](#0-1) .

But if `signature` is `None`, the dispatch origin is derived purely from `message.from` — a field inside the same attacker-authored ABI-encoded message body, with no signature check at all:

```rust
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(

    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);
        account.into()

};
``` [3](#0-2) 

The pallet then decodes `substrate_data.runtime_call` into a live `T::RuntimeCall`, checks only the runtime's generic `BaseCallFilter`, and dispatches it under `RawOrigin::Signed(origin)`:
```rust
let runtime_call = T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)
    .map_err(HftError::RuntimeCallDecodeError)?;
if !<T as frame_system::Config>::BaseCallFilter::contains(&runtime_call) {
    Err(HftError::CallFiltered)?
}
runtime_call
    .dispatch(RawOrigin::Signed(origin.clone()).into())
    .map_err(|e| HftError::CallDispatchError(e.error))?;
``` [4](#0-3) 

The `on_accept` authentication step only checks that `source`/`from` (the ISMP request sender contract address) maps to a configured asset via `ContractToAsset::<T>::get(source, &from)` [5](#0-4) ; it never validates that the `message.from` field embedded in the ABI-decoded body actually corresponds to the account that authorized the transfer. That inner `from` field is documented as attacker/user-supplied application data forwarded from the source-chain contract call, and the docs confirm that when no signature is supplied "the origin is derived from the sender address in the cross-chain message" [6](#0-5) . I was not able to fully confirm from the indexed Solidity source whether the source-chain contract cryptographically pins this `from` field to `msg.sender` before ABI-encoding the outbound message (the relevant `Message` struct usages in `HyperFungibleToken.sol`/`WrappedHyperFungibleToken.sol` were located but their bodies were not retrievable within the available tool budget), so this should be verified before treating the finding as fully proven.

This mirrors the CVE-2016-4473 bug class: untrusted encoded input is decoded into a structure that is then acted upon (invoked/dispatched) based on self-declared metadata inside that same untrusted input, with the authorization boundary resting on data the attacker controls rather than on an independently verified signature.

### Impact Explanation
If the `from` bytes inside the ABI-encoded `Message.data` are not strictly bound to the actual transaction signer on the source chain, an attacker can craft a cross-chain message that (a) transfers/mints tokens to any `beneficiary`, and (b) supplies `call_data` with no signature but an arbitrary `from` value, causing the destination pallet to dispatch any `RuntimeCall` permitted by `BaseCallFilter` under `RawOrigin::Signed(<attacker-chosen account>)`. This is a critical "unauthorized app action" primitive — capable of moving funds, adjusting allowances, or invoking any other unfiltered dispatchable as if it originated from a victim account, without ever presenting that victim's signature.

### Likelihood Explanation
Reachable from a single unprivileged cross-chain token transfer through the standard `HyperFungibleToken` message-relay path; no special privilege, governance, or malicious-collator assumption is needed — only that `message.from`/`call_data` are not properly bound to `msg.sender` on the emitting side. Because I could not confirm the source-chain contract logic in this pass, confidence is Medium-High pending that verification rather than fully Critical-confirmed.

### Recommendation
Enforce that the unsigned-call-origin path can never use `message.from` unless it is provably bound (on the destination chain, independent of the source contract) to the same identity that authorized the underlying transfer — e.g., always require the `signature` field for `call_data` execution, or derive the origin solely from a value the pallet itself controls, such as `beneficiary`, rather than an application-layer-supplied `from` byte string.

### Proof of Concept
1. Attacker calls the source-chain `HyperFungibleToken` contract's send function, supplying `call_data` = SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <any RuntimeCall permitted by BaseCallFilter> }`, and setting the `Message.from` field (if unconstrained by the source contract) to the 20/32-byte identifier of a victim account.
2. Relayer delivers the resulting `PostRequest` to the destination chain; `on_accept` runs, mints/transfers tokens to `beneficiary`, then decodes and dispatches `runtime_call` with `RawOrigin::Signed(T::EvmToSubstrate::convert(victim_address))` [7](#0-6) .
3. The victim's mapped substrate account executes the attacker-chosen call without ever signing anything on the destination chain.

## Calldata Execution

The `call_data` field in `SendParams` allows executing arbitrary runtime calls on the destination substrate chain after the tokens are transferred. The calldata is SCALE-encoded as:

```rust lineNumbers
pub struct SubstrateCalldata {
    /// Optional SCALE-encoded MultiSignature of (account_nonce, runtime_call)
    pub signature: Option<Vec<u8>>,
    /// SCALE-encoded runtime call to execute
    pub runtime_call: Vec<u8>,
}
```

If a signature is provided, it is verified against the beneficiary's account nonce and the runtime call before dispatch. Supported signature types: Ed25519, Sr25519, ECDSA. The account nonce is incremented after dispatch to prevent replay.

If no signature is provided, the origin is derived from the sender address in the cross-chain message.
```
