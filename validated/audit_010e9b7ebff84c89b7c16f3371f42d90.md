### Title
Oversized supply saturates the market's RAY value capacity; every subsequent sync panics and the market is bricked permanently — (File: contracts/pool/src/interest.rs)

### Summary
The logrus bug class is "a single input exceeding a fixed internal bound permanently breaks a shared resource" (`Entry.Writer()` dies forever after one >64KB token). The analog here is the pool's fixed `i128` RAY-value capacity: a single large `supply` — or borrow — that pushes `supplied × supply_index` past `i128::MAX` makes every future call to `global_sync` panic, and because `synced_market` wraps every market operation, the market becomes permanently unusable with all deposited funds frozen.

### Finding Description
Every mutating pool operation loads the market through `synced_market` / `renewed_market`, which unconditionally calls `interest::global_sync`. [1](#0-0) 

`global_sync` calls `accrue_chunk` → `accrue_step`, which multiplies the cached scaled totals (`borrowed`, `supplied`, each a RAY-domain `i128`) by the running indexes to value the book and mint revenue. [2](#0-1) 

The scaled domain multiplies token base units by `10^(27 - decimals)`, so the RAY value `supplied × supply_index` overflows `i128` well before any share count does. The codebase itself acknowledges this: "Finite RAY value capacity can be exhausted before the index ceiling. Synchronizing an overlarge book can then fail before an otherwise risk-reducing operation." [3](#0-2) 

The entry-side cap does not prevent this. `SpokeAssetConfig.supply_cap` is enforced in scaled-share terms by `enforce_spoke_cap`, and the admitted cap maximum is `i128::MAX / 10^(27−d)` — i.e., the cap deliberately permits scaled supply up to nearly the full `i128` range. [4](#0-3)  A single supply sized so that `supplied × supply_index ≥ i128::MAX` passes the cap check (cap is compared on shares against `cap_scaled`, not on post-accrual value), but on the next sync `accrue_step`'s value multiplication overflows and panics.

The panic is not contained per-leg like the liquidation planner's zero-seizure drops; it aborts the whole transaction inside `run_batch`'s leg evaluation, leaving `last_timestamp` unadvanced. Because the overflow is a function of stored state (`supplied`, `supply_index` ≥ 1 RAY and only grows), no subsequent operation on that market can ever succeed: `supply`, `withdraw`, `repay`, `borrow`, `seize`, `settle`, `claim_revenue`, and `recapitalize` all route through `synced_market`. Even `apply_bad_debt_to_supply_index` — which itself starts by computing `supplied × supply_index` — cannot run to shrink the book. [5](#0-4) 

This mirrors the logrus failure exactly: one oversized input trips a fixed capacity bound (`i128` ≈ the 64KB scanner token limit), and the resource (the market, like the dead `Writer`) is permanently unusable — not merely one failed call.

### Impact Explanation
Permanent freezing of funds and a contract unable to operate. Once `supplied × supply_index` crosses `i128::MAX`, every supplier's balance in that `(hub, token)` market is locked forever — `withdraw` panics in `global_sync` before touching balances. All queued interest, revenue, and liquidation flows for the market halt. Unlike a transient price outage (DoS.1), no oracle update or governance action can restore the market: `supply_index` never decreases through normal accrual, and `update_indexes`/cleanup paths also sync first. Because the pool holds one physical balance per market, this is protocol-wide, not per-account.

### Likelihood Explanation
Reachable by a single unprivileged address via `controller.supply` (or `borrow` against `borrowed × borrow_index`), provided the configured cap admits enough scaled supply. The defect is that the cap conversion `cap_scaled = cap × 10^(27−d) × RAY / index` saturates at `i128::MAX` and the admitted maximum (`i128::MAX / 10^(27−d)` tokens) already corresponds to scaled supply of order `i128::MAX` — at which point any `supply_index > RAY` overflows the value multiplication. For a low-priced, high-decimal-count token listed with a permissive cap, the token cost is cheap. Likelihood is therefore conditional on listing configuration but requires no privileged action, no oracle manipulation, and no third-party misbehavior — the trigger input is one ordinary `supply` call. Severity is High (permanent freeze of all market funds) rather than Critical, since a reasonably tight cap blocks it.

### Recommendation
Enforce a headroom invariant at share-minting entry points: after computing the post-operation scaled `supplied`/`borrowed`, require `supplied × supply_index` (and `borrowed × borrow_index`) to stay below a safety margin under `i128::MAX` — e.g., reject with a dedicated error when `supply_index > 0` and `supplied > i128::MAX / supply_index`. Equivalently, cap configured `supply_cap`/`borrow_cap` at a fraction of `i128::MAX / 10^(27−d)` divided by a bounded projected index, and apply the same check in `accrue_step` so runaway index growth degrades gracefully (e.g., clamp/skip accrual) instead of bricking the market.

### Proof of Concept
1. A market is listed for token T with `decimals = d` and `supply_cap` set near the admitted maximum `i128::MAX / 10^(27−d)` (or `borrow_cap` similarly; or a cap sized such that scaled supply approaches `i128::MAX / supply_index`).
2. Time accrues so `supply_index = S > RAY`.
3. Attacker calls `controller.supply` depositing `amount` T such that `scaled = amount × 10^(27−d)` satisfies `(existing_supplied + scaled) × S ≥ i128::MAX`. The cap check in `enforce_spoke_cap` compares `usage_scaled + scaled ≤ cap_scaled` (saturated at `i128::MAX`) and passes. [6](#0-5) 
4. On the very next call touching the market — including the same batch's next leg — `synced_market` → `global_sync` → `accrue_step` computes the book value `supplied × supply_index`, which overflows `i128` and panics. [7](#0-6) 
5. Every subsequent `supply`/`withdraw`/`repay`/`borrow`/`liquidate`-leg/`clean_bad_debt`/`recapitalize`/`claim_revenue` on that `(hub_id, asset)` reverts identically, forever: `supply_index` is monotone under accrual, and no path can reduce `supplied` without first syncing. All supplier and revenue balances in the market are permanently frozen.

Caveat: I could not exhaustively verify the exact overflow site inside `common::rates::accrue_step`/`Ray::mul` within the tool budget; the claim rests on the checked/saturating RAY arithmetic described in the docs ("checked" multiplications, `mul_ceil`/`mul_floor` panicking on overflow per `common::math::fp`) and the protocol's own documented admission that "synchronizing an overlarge book can fail" (`threat-model.md` numeric-limits section). If `accrue_step` saturates rather than panics on the value multiplication, the impact degrades to mispriced accrual rather than a permanent freeze.

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}
```

```rust
pub(crate) fn apply_bad_debt_to_supply_index(cache: &mut Cache, bad_debt: Ray) {
    let total_supplied_value = cache.supplied().mul(cache.env(), cache.supply_index());

    if total_supplied_value == Ray::ZERO {
        return;
    }

    let capped = bad_debt.min(total_supplied_value);
    let remaining = total_supplied_value.checked_sub(cache.env(), capped);

    let reduction_factor = remaining.div_floor(cache.env(), total_supplied_value);
    let new_supply_index = cache
        .supply_index()
        .mul_floor(cache.env(), reduction_factor);

    cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
```

cap_scaled     = floor_saturating(cap × 10^(27−d) × RAY / index)      // calculate_scaled_cap, supply or borrow index
usage_scaled   = SpokeUsageRaw.supplied_scaled_ray | borrowed_scaled_ray   // get_spoke_usage
usage + new_shares ≤ cap_scaled   else SpokeSupplyCapReached | SpokeBorrowCapReached
headroom_tokens = floor(floor((cap_scaled − usage) × index / RAY) / 10^(27−d))
