### Title
`getConnectedAccounts()` Exposes Addresses of All Enabled Wallet Accounts to a Trusted Origin, Not Just the Account(s) It Was Granted - ([File: features/connected-origins/module/connections.js])

### Summary
`ConnectedOrigins.getConnectedAccounts()` is meant to return only the account(s) an origin was granted access to, but it iterates over every entry in `connectedAccountsAtom` (which is derived from *all* enabled wallet accounts) and returns every account's addresses, filtered only by asset name — never by the per-origin `walletAccount` grant that is stored alongside the connection. This mirrors the report's root cause of "recover/return everything except what is currently entitled, ignoring what should be excluded/scoped" — instead of scoping the return set by entitlement, the code just filters by an unrelated dimension (asset name) and passes through all accounts.

### Finding Description
When an origin is added via `add()`, a `walletAccount` field can be stored on the connection record, apparently intended to scope which wallet account(s) the origin was authorized for: [1](#0-0) 

However, `getConnectedAccounts()` never reads or enforces this `walletAccount` field. It only checks `isTrusted`, computes the set of `assetNames` for the origin, and then loops over **every key** in the module-wide `connectedAccountsAtom` (which is populated by `#getAccounts()` from `enabledWalletAccountsAtom`, i.e., all wallet accounts currently enabled in the wallet), returning addresses for all of them: [2](#0-1) 

`#getAccounts()` confirms the account set is built from the whole wallet, not the specific origin: [3](#0-2) 

This is the same class of bug as the report: a "return/settlement" function calculates its result using the wrong scope (all funds/records minus an unrelated filter) instead of the actual entitlement (what was specifically granted/reserved to the requester), leaking data/assets that belong to a different party (here, other wallet accounts/other user identities) to the requesting party (here, a connected dApp origin).

### Impact Explanation
Any third-party site that becomes "trusted" for one wallet account (e.g., after a normal `connect()` approval flow for `exodus_0`) can, via `getConnectedAccounts()`, receive the receiving addresses of every other enabled wallet account in the same Exodus wallet instance (`exodus_1`, `exodus_2`, etc.), for every asset the origin has ever been connected to. This breaks account isolation — a core wallet security boundary — by disclosing addresses of accounts the user never approved for that origin, enabling cross-account address correlation/deanonymization by an unprivileged, malicious website.

### Likelihood Explanation
This is reachable by any web page that has completed one legitimate `connect`/`add` + `isTrusted` flow for a single account (the standard, low-privilege dApp connection flow exposed via the RPC/provider bridge), so no special privilege beyond a normal wallet-connection approval is required to trigger the over-broad disclosure.

### Recommendation
Scope `getConnectedAccounts()` to only the wallet account(s) actually stored on the origin's connection record (`value.walletAccount`, or an explicit per-origin accounts allow-list) rather than iterating over the entire `connectedAccountsAtom`. Concretely, replace the loop over `Object.keys(accounts)` with a lookup restricted to the origin's granted account(s), analogous to fixing the original report by computing the returned set from the actual entitlement rather than "everything minus an unrelated exclusion."

### Proof of Concept
1. User approves origin `dapp.example` and connects wallet account `exodus_0` (calls `connectedOrigins.add({ origin: 'dapp.example', connectedAssetName: 'ethereum', trusted: true, walletAccount: 'exodus_0' })`).
2. The wallet separately has `exodus_1` enabled (a different account the user never connected to `dapp.example`).
3. `dapp.example` calls the exposed API `exodus.connectedOrigins.getConnectedAccounts({ origin: 'dapp.example' })`: [4](#0-3) 
4. The returned array contains an entry for `exodus_1` with its Ethereum address, even though `exodus_1` was never part of the connection grant, because `getConnectedAccounts()` iterates all keys of `connectedAccountsAtom` rather than filtering by the origin's `walletAccount`: [5](#0-4)

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
