## Finding: `SignerCapabilityOfferProofChallengeV2` is missing `chain_id`, unlike its sibling `RotationCapabilityOfferProofChallengeV2` — enabling cross-network replay of signer-capability grants

### Title
Missing `chain_id` domain-separation field in `SignerCapabilityOfferProofChallengeV2` allows cross-chain replay of a signed authorization, leading to unauthorized `SignerCapability` (full account takeover) - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
The external report's root cause is a domain separator that omits a field (`version`) that the protocol relies on elsewhere for context-binding, so a signature validly produced for one context can be misapplied in another. The same class of bug appears in Aptos's `account` module: `RotationCapabilityOfferProofChallengeV2` was explicitly upgraded to add `chain_id` "to prevent replaying the challenge message" [1](#0-0) , but its sibling struct `SignerCapabilityOfferProofChallengeV2`, used to authorize delegation of a `SignerCapability` (which lets the recipient fully impersonate the source account), does not carry a `chain_id` field, as shown by the exact BCS-matching off-chain struct used in the e2e tests [2](#0-1) .

### Finding Description
Signature verification for these capability-offer challenges goes through `verify_signed_message`/`signature_verify_strict_t`, which wraps the message as `SignedMessage { type_info: type_info::type_of<T>(), inner: data }` before hashing [3](#0-2) . `type_info::type_of<T>()` only encodes the module address/name/struct name (e.g. `0x1::account::SignerCapabilityOfferProofChallengeV2`), which is identical across every Aptos-based network that runs the same framework bytecode at `0x1` (mainnet, testnet, devnet, or any fork/rehearsal network). It does **not** encode `chain_id`.

Compare the two challenge structs:
- `RotationCapabilityOfferProofChallengeV2` fields: `chain_id`, `sequence_number`, `source_address`, `recipient_address` — chain_id was deliberately added [1](#0-0) , and is consumed accordingly in `offer_rotation_capability` [4](#0-3) .
- `SignerCapabilityOfferProofChallengeV2` fields (per the exact BCS mirror used for signing in tests): `account_address`, `module_name`, `struct_name`, `sequence_number`, `source_address`, `recipient_address` — no `chain_id` [2](#0-1) .

Because `sequence_number`, `source_address`, and `recipient_address` can be identical across two different Aptos networks (e.g., a freshly created account at sequence number 0 on both mainnet and a testnet/fork sharing the same account-creation flow, or two independent chains derived from the same framework/genesis), a signature authorizing `offer_signer_capability` on one network is bit-for-bit valid on another network. `verify_signed_message` performs no chain-context check beyond what's embedded in the signed struct [5](#0-4) .

### Impact Explanation
`SignerCapability` is the highest-privilege custody primitive in Aptos: whoever holds it can call `create_signer_with_capability` and generate a `signer` for the victim account at will [6](#0-5) , which grants complete control — the ability to transfer/burn APT and any fungible-asset/object holdings, rotate keys, and take over any resource account built on top of that address. If a user (or protocol/backend) signs a `SignerCapabilityOfferProofChallengeV2` intending to authorize a specific delegate on one Aptos network, and the same address/sequence-number state exists on a different Aptos network using the same framework module (a realistic scenario for parallel testnet/mainnet deployments, migrations, or L1 forks of Aptos), that signature can be replayed to seize `SignerCapability` — and therefore full custody — on the other network without the owner's consent. This satisfies the custody-impact gate: unauthorized takeover of account/resource-account control tied to live assets.

### Likelihood Explanation
Exploitation requires a scenario where the same `(sequence_number, source_address, recipient_address)` triple is meaningful on two networks sharing the same framework code — most plausible for freshly bootstrapped accounts (sequence number 0, a common state for newly funded custodial or resource accounts) that are provisioned identically across a mainnet/testnet pair, or for any Aptos fork/L1 that reuses the reference framework without changing the struct. This is a narrower attack surface than a straightforward on-chain bug, but it is a genuine, code-provable absence of domain separation that the codebase itself demonstrates is necessary (via the `RotationCapabilityOfferProofChallengeV2` fix), making it Medium-High likelihood rather than purely theoretical.

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2` (mirroring `RotationCapabilityOfferProofChallengeV2`), update `offer_signer_capability` to populate it from `chain_id::get()`, and bump serialization/versioning so old signatures are rejected. Provide a migration/deprecation path analogous to the existing `SignerCapabilityOfferProofChallenge` → `V2` transition.

### Proof of Concept
Conceptual PoC (cannot be executed without two live networks sharing framework state):
1. On Network A, Alice's account exists at address `addr_A` with `sequence_number = 0`.
2. Alice signs `SignerCapabilityOfferProofChallengeV2 { account_address: 0x1, module_name: "account", struct_name: "SignerCapabilityOfferProofChallengeV2", sequence_number: 0, source_address: addr_A, recipient_address: attacker_addr }` intending to authorize a delegate on Network A only, per the flow in [7](#0-6) .
3. On Network B (same framework bytecode, e.g. testnet or fork), an account with the identical address `addr_A` also exists with `sequence_number = 0` (plausible for freshly derived accounts or parallel deployments).
4. The attacker submits the identical signature to `account::offer_signer_capability` on Network B; since no `chain_id` is part of the signed payload, verification in `verify_signed_message` succeeds [5](#0-4) , granting the attacker `SignerCapability` over `addr_A` on Network B and full custody of its assets.

**Caveat / uncertainty**: I confirmed the missing `chain_id` field via the Rust struct that must byte-for-byte match the Move struct for BCS-signature verification to succeed in the existing e2e test (`offer_signer_capability.rs`), but I was not able to directly view the exact Move struct definition of `SignerCapabilityOfferProofChallengeV2` in `account.move` within available tool calls (the source view was truncated before reaching it). I recommend confirming the exact field list directly in `aptos-move/framework/aptos-framework/sources/account/account.move` before treating this as a fully verified finding.
