### Title
Webhook `shop-domain`/`topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` trusts `request.shop` for tenant identification after validating only the body's HMAC, so any header value can be substituted without invalidating the signature — the same "field acted on but not covered by the signature" class of bug as the reported gnark advisory (there, extra commitment components were unbound by the proof of knowledge; here, the `shop`/`topic` headers are unbound by the webhook HMAC).

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is derived from the `x-shopify-hmac-sha256` header, and `to_signable_string` returns `@raw_body` only — `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the supplied `hmac`, which for a `Webhooks::Request` means it checks `HMAC(secret, raw_body)` — nothing about `shop`, `topic`, or `webhook_id` is included in the signed material: [3](#0-2) 

`Registry.process` validates only that HMAC and then dispatches the handler using the unauthenticated `request.shop` and `request.topic`: [4](#0-3) 

The equality the code implicitly assumes is: `shop_that_produced(hmac, body) == request.shop`. In fact `hmac` binds only to `body`; `shop` (and `topic`/`webhook_id`) can be freely rewritten by whoever controls the HTTP request to the app's public webhook endpoint, as long as they can supply *some* valid `(body, hmac)` pair signed with the app's secret.

### Impact Explanation
This breaks the tenant-identity binding that multi-tenant apps rely on to route webhook data to the correct shop's records. An unprivileged internet user who can install the app on their own store (a normal, permission-less action for any public app) receives legitimate webhooks for their own shop — i.e., a valid `(body, hmac)` pair signed by Shopify with the app's `client_secret`, without ever needing to know the secret itself. They can then replay that exact body/HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` invokes the registered handler with `shop: request.shop` set to the victim's domain and attacker-controlled body content. Any app that uses the webhook `shop` field to look up/write per-tenant data (order sync, GDPR/customer-redact processing, inventory updates, etc.) will process attacker-controlled data under the victim's tenant — a cross-tenant data-integrity/confusion vulnerability reachable without any credential leak, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app built on this gem that (a) is installable by external merchants/stores and (b) uses `request.shop` from `Webhooks::Request`/`WebhookMetadata` to key its per-tenant processing, which is the documented usage pattern (`WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`). No leaked secret, TLS interception, or privileged account is required — only the ability to install the app on an attacker-controlled shop, a standard install flow for public apps.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed material verified against the HMAC (or at minimum require the app/host to independently verify the `shop-domain` header against a known/installed shop registry before trusting it), rather than trusting these headers unconditionally once only the raw body's HMAC checks out. Shopify's webhook HMAC is computed over the body by design; the gem/host application should not use unauthenticated headers as the sole tenant-routing key without an additional authenticated check tying the delivery to the specific shop.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com` and trigger any subscribed webhook topic (e.g. `orders/create`) to receive a legitimate delivery: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's secret), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay an HTTP POST to the app's public webhook endpoint with the same `x-shopify-topic` and `x-shopify-hmac-sha256: H`, the same body `B`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` — matches `H` — and returns `true` because `shop` is not part of the signed payload. [5](#0-4) 
4. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and body content that actually originated from the attacker's own shop, causing the app to process/store attacker-controlled data under the victim tenant. [6](#0-5)
