### Title
Uniswap V4 venue pricing derives fill rates from the raw, un-impacted pool mid price with no size/impact term, letting a flash-loan price manipulation drain a Simplex solver through the Intent Gateway - (File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts)

### Summary
For cross-asset pairs without static bid/ask curves ("venue-priced" pairs), the Simplex filler prices fills directly off a Uniswap V4 pool's current tick/`sqrtPriceX96` instead of a slippage-aware quote. `UniswapV4FundingPlanner.computeDirectPoolPriceUsd` reads `sdkPool.token0Price`/`token1Price` — the pool's instantaneous mid — and `getExoticTokenPrice` returns it unmodified as the exotic token's USD price. [1](#0-0)  This mid price is consumed by `FXFiller.getVenueUsdPrice`/`venuePriceMemo`, which is used by `resolveLegRates` to compute the leg's fill rate. [2](#0-1)  This is the exact bug class rekt.news describes for Jimbo's Protocol: a rebalancing/pricing function that trusts a live, atomically-manipulable AMM price with no slippage/impact control, letting a flash-loan buyer temporarily distort the price and drain value through the mispriced operation.

### Finding Description
The flow, as documented in the repo's own analysis, is:

```
resolveLegRates(...)
  curveless pair && token0 is a USD stable
    -> venuePriceMemo() -> getVenueUsdPrice(chain, token1)
         -> UniswapV4FundingPlanner.getExoticTokenPrice
              picks the position with the largest pool liquidity
              -> computeDirectPoolPriceUsd -> sdkPool.token0Price / token1Price
    -> checkPriceGuard(...)   reject if outside maxDeviationBps of the static reference
    -> rate = 1 / venueUsd
``` [3](#0-2) 

`computeDirectPoolPriceUsd` returns the raw pool mid derived from `sqrtPriceX96` with no size or price-impact term — `computeLegPolicyOutput` then linearly extends that unimpacted mid across the whole priced quantity of the order. [4](#0-3)  The only defense is `checkPriceGuard`, which bounds deviation from a static, operator-configured `referencePrice`/`maxDeviationBps` — and this guard is explicitly optional ("omit both to leave the chain unguarded"). [5](#0-4)  Even when configured, the guard only checks deviation from a stale, operator-set reference value, not real execution cost or pool depth, so an attacker can still move price within the allowed band, or when unguarded, arbitrarily.

Because the fee tier of the position is stored but never applied to the price, and because there is no size/impact term, a solver relying on this pool as its price oracle is exposed exactly the way Jimbo's `JimboController.shift()` was: an attacker takes a flash loan, moves the referenced pool's price with a large swap, then submits (or has a colluding party submit) an Intent Gateway order that gets bid/priced against the now-distorted mid, extracting more output value than the true market rate justifies, before reversing the manipulation in the same or a following block. This is a live pricing dependency reachable from a single order submission through `IntentGateway`/`IntrinsicIntents.fillOrder`, no privileged role required.

### Impact Explanation
A manipulated venue price directly changes `rate = 1/venueUsd` used to size `finalOutputAmount` for a fill. An attacker who transiently distorts the referenced Uniswap V4 pool can force the solver to pay out output tokens (e.g., cNGN) valued at an inflated USD price relative to the true market, or accept input at a deflated price, extracting value from the solver's escrowed/backing inventory on each such fill — a concrete theft of funds from the liquidity backing the Intent Gateway pool, matching the "concrete theft... of funds" bar in the validation rules.

### Likelihood Explanation
Any unprivileged actor can submit an Intent Gateway order and, in the same transaction bundle or block, manipulate the specific Uniswap V4 pool a solver has configured for venue pricing (a flash loan requires no special privilege). Exploitability depends on: (1) the pair being curveless / venue-priced (a supported and documented configuration), and (2) whether the operator configured `referencePrice`/`maxDeviationBps`. Per the documentation this guard is optional and, when present, still allows manipulation up to the configured band and does not account for execution cost — so the attack surface exists in the documented default configuration and is only partially mitigated, not eliminated, even in the "guarded" configuration.

### Recommendation
- Replace the raw pool mid with a size-aware, manipulation-resistant price: use a TWAP/observation-based price from the pool (or a spot price averaged over multiple blocks) rather than the instantaneous `sqrtPriceX96`.
- Apply an actual swap-simulated (impact-aware) quote for the order's notional rather than linearly extending the unimpacted mid across the whole fill size.
- Make the `referencePrice`/`maxDeviationBps` guard mandatory for venue-priced pairs rather than optional, and tighten it to reflect realistic execution cost, not just a static deviation band.
- Apply the pool's fee tier to the priced quantity so the quoted rate reflects the true cost of sourcing inventory through that pool.

### Proof of Concept
1. Operator configures a venue-priced pair (no bid/ask curves) sourced from a Uniswap V4 position, per the documented example, and no `referencePrice`/`maxDeviationBps` guard (a supported, unguarded configuration). [6](#0-5) 
2. Attacker takes a flash loan and swaps a large amount through the exotic/USD pool referenced by that position, moving `sqrtPriceX96` far from the true market price.
3. Attacker (or an accomplice) submits an Intent Gateway order for that pair sized so the solver bids/fills it; `resolveLegRates` -> `getVenueUsdPrice` -> `UniswapV4FundingPlanner.getExoticTokenPrice` -> `computeDirectPoolPriceUsd` returns the manipulated mid, and `computeLegPolicyOutput` extends it linearly across the whole order notional with no impact discount. [4](#0-3) 
4. The solver's fill is priced/sized off the manipulated rate and released to the attacker via `IntentGateway.fillOrder`, over-delivering value relative to the true market price.
5. Attacker reverses the pool manipulation (repaying the flash loan) and nets the difference, exactly mirroring the Jimbo `shift()` slippage-control failure pattern from the external report.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	/**
	 * Queries funding venues for `token1Address`'s USD price on a chain.
	 * Uniswap V4 is preferred; falls back to other venues. Returns null when no
	 * venue can price the token there.
	 */
	private async getVenueUsdPrice(chain: string, token1Address: string): Promise<Decimal | null> {
		if (this.fundingVenues.length === 0) return null

		// Prefer V4, fall back to others
		const v4 = this.fundingVenues.filter((v) => v.name === "UniswapV4")
		const venues = v4.length > 0 ? v4 : this.fundingVenues

		for (const venue of venues) {
			const usdPrice = await venue.getExoticTokenPrice(chain, token1Address)
			if (usdPrice?.isPositive()) return usdPrice
		}
		return null
	}

	/** Per-evaluation memo over `getVenueUsdPrice`, keyed by (chain, token1). */
	private venuePriceMemo(): (chain: string, token1Address: string) => Promise<Decimal | null> {
		const cache = new Map<string, Decimal | null>()
		return async (chain: string, token1Address: string) => {
			const key = `${chain}:${token1Address}`
			const cached = cache.get(key)
			if (cached !== undefined) return cached
			const price = await this.getVenueUsdPrice(chain, token1Address)
			cache.set(key, price)
			return price
		}
	}

## Pool-Based Pricing

When **`[vault.uniswapV4]`** lists at least one position, cross-asset pairs without curves derive bid/ask prices from **Uniswap V4 pool state** (current tick). The pool acts as the price oracle instead of a static curve. Note this yields a **single** price used in both directions — a venue-priced pair has no bid/ask spread of its own, so its margin comes from `order.fees` alone.

With Uniswap V4 positions configured, you can **omit** `bidPriceCurve` and `askPriceCurve` on the pair. Pool pricing requires the pair's `token0` to be a USD stablecoin, and same-token pairs always need their curve. The optional **`spreadBps`** field (basis points) sets the slippage tolerance for on-chain LP redemptions; defaults to `50` (0.50%).

Uniswap V4 venue pricing uses pools that pair the exotic token with **USDC or USDT** (addresses from your chain config). When multiple positions exist for the same exotic token on a chain, the most-liquid qualifying pool's price is used.

```toml lineNumbers
[assets.CNGN]
"EVM-8453" = "0x46C85152bFe9f96829aA94755D9f915F9B10EF5F"

[[pairs]]
token0 = "USDC"
token1 = "CNGN"
maxOrderSize = "5000"       # no curves — priced from the pool

[vault.uniswapV4]
spreadBps = 50  # 0.5% slippage tolerance on LP redemptions
positions = [
    { chain = "EVM-8453", tokenId = "2087350" },
]
```

<Callout type="info">
Startup validation requires a pricing source per pair: **either** bid/ask price curves, **or** at least one `[vault.uniswapV4]` position. A pair with neither fails validation.
</Callout>
```

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
