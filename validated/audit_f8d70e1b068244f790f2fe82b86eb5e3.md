### Title
Interest accrual overflows before the index cap and permanently freezes a large market - (File: common/src/rates/simulate.rs)

### Summary
A sufficiently large market can reach an `i128` value-overflow during interest accrual before its configured borrow-index cap is reached. Once that happens, every pool operation that synchronizes the market panics with `MathOverflow`, permanently freezing withdrawals, repayments, liquidation settlement, and subsequent index updates absent a contract upgrade. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` first reconstructs `borrowed_original` and `supplied_original` with `scaled_to_original`, which is simply `scaled.mul(index)` in RAY precision. [3](#0-2) [4](#0-3)  `Ray::mul` delegates to `mul_div_half_up`, which panics with `GenericError::MathOverflow` when the exact result does not fit in `i128`. [5](#0-4) [6](#0-5) 

The borrow index is capped only after `old_index.mul(interest_factor)` successfully returns, so the cap cannot prevent either the index-product overflow or the earlier scaled-total overflow. [7](#0-6) [8](#0-7)  `global_sync` invokes this accrual step for every elapsed chunk before marking the market accrued, and `synced_market` performs that synchronization before ordinary pool mutations. [9](#0-8) [2](#0-1) 

The controller exposes the trigger through permissionless `update_indexes(caller, assets)`, while borrower repayments and supplier withdrawals route into the same synchronized pool paths. [10](#0-9) [11](#0-10) [12](#0-11) 

### Impact Explanation
After the market crosses the representable-value boundary, the failed accrual is repeated from the stale `last_timestamp` on every future attempt. Because the market can never synchronize again, suppliers cannot withdraw the affected asset and borrowers cannot repay it; liquidation and other market-mutating flows that touch the market are likewise blocked by their synchronized pool calls. [13](#0-12) [14](#0-13) 

The repository's regression test demonstrates this end state explicitly: after `update_indexes` returns `MathOverflow`, both a one-unit withdrawal and a repayment return the same error, while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [15](#0-14)  This constitutes permanent freezing of user funds and protocol liveness for the affected market unless an administrative upgrade changes the arithmetic. [16](#0-15) 

### Likelihood Explanation
The attack requires an unusually large market rather than privileged access: the demonstrated configuration supplies one billion 18-decimal tokens and borrows approximately 98% of it, then lets the high-utilization XLM curve compound until the index exceeds the representability boundary. [17](#0-16)  At that scale, an index above roughly 170 makes the one-billion-token RAY-scaled total exceed `i128::MAX`, while the configured index ceiling is far higher at `1e36` raw units. [18](#0-17) [8](#0-7) 

The final trigger can be sent by any caller through `update_indexes`; setting up the state requires whale-scale capital and an existing listed market whose caps and rate parameters permit the position, but no privileged runtime action. [11](#0-10) [10](#0-9)  The likelihood is therefore lower than an ordinary economic exploit, but the result is deterministic once the market reaches the boundary.

### Recommendation
Make accrual total-value calculations overflow-safe before deriving utilization or rewards. In particular, `accrue_step`, `update_borrow_index`, `calculate_supplier_rewards`, and related unscaling paths should use widening arithmetic or explicit saturation where an intermediate economic value exceeds `i128`, and the index cap must be enforced before any conversion that can panic. [19](#0-18) [7](#0-6) 

A stronger invariant is to enforce a market-specific index bound derived from maximum scaled supply/debt so that `scaled * index` always remains representable, rather than relying on the global `MAX_BORROW_INDEX_RAY`. [8](#0-7) [20](#0-19)  Add the existing whale-market scenario as a regression test requiring that `update_indexes`, `withdraw`, `repay`, and liquidation entry paths remain executable at the configured cap.

### Proof of Concept
The repository already contains a deterministic reproduction in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`. [21](#0-20) 

1. Create an 18-decimal market using the steep XLM rate curve and a collateral market. [22](#0-21) 
2. Supply `1_000_000_000 * 10^18` units of the debt asset, supply collateral from another account, and borrow 98% of the debt market. [23](#0-22) 
3. Advance ledger time and call the permissionless controller `update_indexes` path once per simulated year. [24](#0-23) 
4. The accrual eventually fails with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`, proving the value overflow occurs before the configured index cap. [25](#0-24) 
5. Subsequent `withdraw` and `repay` attempts also fail with `MathOverflow`, leaving supplier and borrower funds frozen. [26](#0-25)

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
