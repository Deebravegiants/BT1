## Title
`IsmpCallFilter` on Nexus/Gargantua checks `Message::Consensus` for BEEFY but not `Message::FraudProof`, allowing an unsigned `handle_unsigned` call to freeze the BEEFY consensus client without the same scrutiny applied to updates - (File: `parachain/runtimes/nexus/src/lib.rs`, `parachain/runtimes/gargantua/src/lib.rs`)

## Summary
This mirrors the nuclei bug class: a security gate is enforced for one path (workflow templates require a signature; here, BEEFY *consensus updates* are blocked from the unsigned/free `handle_unsigned` path so they must go through `pallet-beefy-consensus-proofs`'s SP1 zkVM verification), while a sibling path that reaches the *same privileged state transition* is left unchecked because the filter only pattern-matches on `Message::Consensus`, not `Message::FraudProof`.

## Finding Description
Both runtimes install an `IsmpCallFilter` as `BaseCallFilter` specifically to stop BEEFY-related state transitions from being pushed through the free, unsigned `handle_unsigned` extrinsic, since BEEFY updates on these chains are required to go through SP1 zkVM verification (`pallet-beefy-consensus-proofs`) instead of the raw BEEFY consensus client logic: [1](#0-0) [2](#0-1) 

The filter's `contains` implementation only inspects `Message::Consensus(consensus)` and compares `consensus.consensus_state_id` against the BEEFY client id; every other `Message` variant, including `Message::FraudProof`, is passed through:
```
Message::Consensus(consensus) => host.consensus_client_id(consensus.consensus_state_id) == Some(BEEFY_CONSENSUS_ID),
_ => false,
```
`Message::FraudProof(FraudProofMessage)` also carries a `consensus_state_id` field [3](#0-2)  and is routed by `handle_incoming_message` to `consensus::freeze_client(host, fraud_proof)` — a state transition against the very same consensus-client storage that the filter is trying to protect [4](#0-3) . Because the filter's match arm only recognizes `Message::Consensus`, a `Message::FraudProof` batch naming the BEEFY `consensus_state_id` is *not* rejected by `IsmpCallFilter`, and reaches `pallet_ismp::Pallet::handle_unsigned` → `Self::execute(messages)` unsigned and free of charge, exactly as `handle_unsigned` normally allows [5](#0-4)  and validated via `ValidateUnsigned::validate_unsigned` [6](#0-5) .

This is structurally identical to the nuclei bug: the intended guard ("only allow BEEFY consensus state transitions through a specially-verified path") is expressed as a filter matching one specific message *tag/shape* (`Message::Consensus`), while another message tag (`Message::FraudProof`) that reaches an equivalent privileged consensus-state mutation for the same `consensus_state_id` slips past unexamined — just like nuclei's `-w` workflow path failed to require the `-code` flag/signature that `-t` template execution enforced.

## Impact Explanation
I was unable to fully trace `consensus::freeze_client`/`verify_fraud_proof`'s exact effects in the final iteration (tool budget exhausted before reading `modules/ismp/core/src/handlers/consensus.rs` and the BEEFY client's fraud-proof verification), so I cannot conclusively state whether the fraud-proof path itself contains an exploitable bypass of BEEFY-specific cryptographic checks, or whether it independently and correctly verifies two conflicting BEEFY commitments before freezing the client. If `freeze_client`/`verify_fraud_proof` for the BEEFY consensus client validates proofs using the BEEFY client's own logic (not through the SP1 zkVM gate the comment says is mandatory), an attacker could submit a crafted `Message::FraudProof` naming the BEEFY `consensus_state_id` to freeze the BEEFY consensus client on Nexus/Gargantua without going through `pallet-beefy-consensus-proofs`, causing a denial of message delivery (route unable to deliver messages) for all Polkadot-relayed traffic — a protocol-halting impact matching the "unauthorized action bypassing signature/verification" bug class in the report.

## Likelihood Explanation
The `handle_unsigned` extrinsic is explicitly free and open to unsigned submission by design (that's the whole point of the pallet, so any external caller including an unprivileged relayer or unauthorized third party can submit it), and the filter gap is a straightforward pattern-match omission rather than requiring a race condition or privileged access. However, likelihood of *impact* is uncertain because it hinges on unverified downstream fraud-proof-verification code — this is the exact "unable to fully explore" caveat that I need to flag honestly.

## Recommendation
Extend `IsmpCallFilter::contains` in both `parachain/runtimes/nexus/src/lib.rs` and `parachain/runtimes/gargantua/src/lib.rs` to also match `Message::FraudProof(fraud_proof)` and reject it under the same BEEFY-client-id condition applied to `Message::Consensus`, so that any message batch (regardless of tag) targeting the BEEFY `consensus_state_id` is blocked from the unsigned `handle_unsigned` path, forcing all BEEFY-related state transitions through the intended SP1-verified route.

## Proof of Concept
Conceptual reproduction (pending confirmation of `freeze_client` internals):
1. Construct `Message::FraudProof(FraudProofMessage { proof_1, proof_2, consensus_state_id: <BEEFY id>, signer })`.
2. Submit via `pallet_ismp::Call::handle_unsigned { messages: vec![msg] }` as an unsigned extrinsic to Nexus/Gargantua.
3. `IsmpCallFilter::contains` returns `true` (not filtered) because it only special-cases `Message::Consensus`.
4. `validate_unsigned`/`execute` calls `handle_incoming_message` → `consensus::freeze_client(host, fraud_proof)` against the BEEFY consensus state, bypassing the SP1 zkVM-gated update path the runtime comment says is mandatory.

**Note on completeness:** Due to exhausting my tool-call budget, I could not read `modules/ismp/core/src/handlers/consensus.rs` (`freeze_client` implementation) or the BEEFY client's fraud-proof verification logic to confirm whether that code independently enforces sufficient safeguards, which would determine whether this filter gap is merely defense-in-depth or a concretely exploitable freeze/DoS. This should be verified before treating this as a confirmed High/Critical finding.
