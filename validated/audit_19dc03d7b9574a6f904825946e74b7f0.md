### Title
`transfer_from` in the USDK stablecoin example uses the account's live sequence number as a permit "nonce," allowing unlimited replay of a single signed transfer authorization - ([File: aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move])

### Summary
`stablecoin::usdk::transfer_from` implements a gasless, meta-transaction-style transfer (an off-chain-signed "permit") analogous to the ERC-7683 gasless order flow in the external report. Just as the external bug allowed an intent to be opened at any time because `openDeadline` was never checked, this Move analog allows a signed transfer approval to be *executed at any time, repeatedly*, because the message contains neither an expiration/deadline field nor a self-consumed, dedicated nonce.

### Finding Description
`transfer_from` builds the signed payload as: [1](#0-0) 

The `nonce` field is populated with `account::get_sequence_number(from)` — the *live* on-chain sequence number of the owner's account, read at verification time: [2](#0-1) 

This sequence number is not incremented, consumed, or otherwise invalidated by `transfer_from` itself — it only changes when the owner `from` submits an ordinary transaction from their own account (i.e., normal Aptos replay-protection via `check_for_replay_protection_regular_txn`, which requires `txn_sequence_number == account_sequence_number` in `transaction_validation.move`). Nothing in `usdk.move` mutates or reserves this counter as part of executing the approval.

Consequently, once `from` signs one `Approval` message off-chain and hands it to a `spender` (this is the entire purpose of `transfer_from` — a gasless permit), that exact same `proof` remains valid for `transfer_from` on every call, by any caller who possesses the signature, for as long as `from`'s account sequence number does not change on-chain. There is no deadline field to bound how long the authorization is valid, and no self-incrementing "used" nonce as EIP-2612/ERC-20 `permit()` typically implements. The spender (or anyone who intercepts the signature) can call `transfer_from` with the identical `proof` many times in a loop (or across many transactions) before the owner ever submits a transaction, draining far more than the single `amount` the owner intended to authorize.

This is the direct custody analog of the external bug: a signed authorization intended to be bounded/one-shot is instead unboundedly reusable, because the enforcement mechanism (a proper nonce/deadline check) that should gate execution is missing.

### Impact Explanation
**High**: A single signed `Approval` can be replayed an unbounded number of times against `transfer_from`, draining an owner's entire USDK balance in repeated calls rather than the single approved `amount`, without further owner action or consent. This is a direct theft-of-funds/custody-corruption path (unauthorized token movement) affecting real user balances held in the fungible asset's primary store.

### Likelihood Explanation
**Medium-High**: Any party who learns the `proof` bytes for an authorized `transfer_from` (the spender by design, or anyone who observes the call in mempool/on-chain, since the proof is submitted in plaintext) can immediately resubmit it repeatedly. It requires no additional signature and no privileged access — exploitation is trivial once one legitimate approval has been signed and observed.

### Recommendation
Add an explicit, single-use nonce and/or expiration (`deadline`) field to the `Approval` struct that is independent of the account's transaction-level sequence number, and persist/consume it on-chain in `transfer_from` (e.g., a per-owner `Table<u64,bool>` of used nonces, incremented/marked used atomically with the transfer, plus a `deadline: u64` checked against `timestamp::now_seconds()`), mirroring standard `permit()`-style replay protection rather than relying on the account's regular transaction sequence number.

### Proof of Concept
1. Owner `from` signs an `Approval { owner: from, to, nonce: account::get_sequence_number(from), chain_id, spender, amount }` and gives `proof` to `spender` for a single transfer of `amount`.
2. `spender` calls `usdk::transfer_from(spender, proof, from, scheme, pubkey, to, amount)` — succeeds, moving `amount`.
3. Because `from`'s sequence number is unchanged (transfer_from does not touch it), `spender` calls the exact same `transfer_from(spender, proof, from, scheme, pubkey, to, amount)` again — verification recomputes the identical `Approval` (same `nonce` value since sequence number hasn't changed) and succeeds again, moving another `amount`.
4. Repeat until `from`'s balance is exhausted or `from` happens to submit an unrelated on-chain transaction (which would only incidentally bump the sequence number and invalidate future replays, not something the protocol enforces intentionally). [3](#0-2)

    /// Allow a spender to transfer tokens from the owner's account given their signed approval.
    /// Caller needs to provide the from account's scheme and public key which can be gotten via the Aptos SDK.
    public fun transfer_from(
        spender: &signer,
        proof: vector<u8>,
        from: address,
        from_account_scheme: u8,
        from_public_key: vector<u8>,
        to: address,
        amount: u64,
    ) acquires Management, State {
        assert_not_paused();
        assert_not_denylisted(from);
        assert_not_denylisted(to);

        let expected_message = Approval {
            owner: from,
            to: to,
            nonce: account::get_sequence_number(from),
            chain_id: chain_id::get(),
            spender: signer::address_of(spender),
            amount,
        };
        account::verify_signed_message(from, from_account_scheme, from_public_key, proof, expected_message);

        let transfer_ref = &borrow_global<Management>(usdk_address()).transfer_ref;
        // Only use with_ref API for primary_fungible_store (PFS) transfers in this module.
        primary_fungible_store::transfer_with_ref(transfer_ref, from, to, amount);
    }
