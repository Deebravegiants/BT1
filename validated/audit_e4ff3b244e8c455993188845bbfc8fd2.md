Audit Report

## Title
`add_tip` bypasses the operating-mode halt check enforced on `register_token`, allowing bridge operations to continue while Ethereum export is halted - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
The `pallet-snowbridge-system-frontend` pallet gates outbound `register_token` calls with an `ExportOperatingMode` halt check, but the sibling extrinsic `add_tip`, which performs the same category of privileged action (swapping/burning an asset and dispatching an XCM `Transact` to BridgeHub's `EthereumSystem`), has no such check. Any signed account can therefore keep swapping/burning assets and pushing `Transact` messages toward BridgeHub even after governance sets the mode to `Halted`.

## Finding Description
`register_token` enforces the halt as its first statement: [1](#0-0) 

`add_tip` performs the analogous action — via `swap_fee_asset_and_burn` and `send_transact_call`/`build_add_tip_call` — with no equivalent `ensure!(!Self::export_operating_mode().is_halted(), ...)` guard: [2](#0-1) 

Both extrinsics converge on `send_transact_call`, which builds and dispatches the XCM `Transact` to `T::BridgeHubLocation` targeting `EthereumSystem`: [3](#0-2) 

`add_tip` requires only `ensure_signed(origin)` — no privilege beyond a normal signed account: [4](#0-3) 

The `ExportOperatingMode` storage item and its `is_halted()` accessor are shared by both paths, confirming this is a pallet-wide pause intended to cover all export operations, not just `register_token`: [5](#0-4) 

This confirms the claim's code-level assertions are accurate: the halt check exists on one extrinsic and is absent on the other, structurally identical, extrinsic.

## Impact Explanation
When the pallet mode is `Halted`, the intent is to stop non-governance Ethereum export activity. `add_tip` remains fully functional in that state: any signed account can still swap/burn assets and dispatch XCM `Transact` calls to BridgeHub's `EthereumSystem`. This undermines the completeness of the halt mechanism as an incident-response control, allowing continued outbound message generation and asset burns during an emergency the operator believed was fully quiesced. This is a real, concrete logic inconsistency in the pallet's own code — not a hypothetical construct — and matches a legitimate "missing modifier/guard" bug class.

However, note the caveat already flagged in the original report: the pallet's own unit tests and index do not show whether an independent runtime-level filter (e.g., `SafeMode`/`TxPause`, or the `EthereumSystem` pallet's own halt check on BridgeHub, which receives the `Transact` call) provides a compensating control. Since `send_transact_call` only dispatches a `Transact` XCM to a remote pallet (`EthereumSystem` on BridgeHub) rather than directly executing the halted operation locally, the actual on-chain effect of `add_tip` during a local halt depends on whether the remote `EthereumSystem::add_tip`/equivalent backend call independently checks its own halted state. This could not be verified from the indexed frontend pallet code alone.

## Likelihood Explanation
High for reachability at the frontend-pallet level: `add_tip` is callable by any signed account with no special permission, matching the unprivileged-user requirement. The pallet's own test suite exercises `add_tip` succeeding under `Normal` mode but has no test covering `add_tip` while `Halted`, unlike `register_token`, which has `test_switch_operating_mode` proving its guard works.

## Recommendation
Add the halt guard to `add_tip`, mirroring `register_token`:
```rust
pub fn add_tip(origin: OriginFor<T>, message_id: MessageId, asset: Asset) -> DispatchResult {
    ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted);
    let who = ensure_signed(origin)?;
    ...
}
```
Add a regression test analogous to `test_switch_operating_mode` asserting `add_tip` fails with `Error::<T>::Halted` while the mode is `Halted`.

## Proof of Concept
1. Root calls `set_operating_mode(Halted)`.
2. Confirm `register_token` is blocked with `Error::<T>::Halted` (already covered by existing test `test_switch_operating_mode`).
3. Call `add_tip` with a signed origin while the mode remains `Halted` (using the same setup as `add_tip_ether_asset_succeeds`) and observe it succeeds and emits `Event::MessageSent`, proving the local halt check is bypassed for this extrinsic. This scenario is not covered by any existing test in `tests.rs`.
