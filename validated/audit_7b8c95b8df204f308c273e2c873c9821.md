## Title
Unchecked division-by-zero panic in `InvariantToken` exchange functions reachable from `Deposit` — denial of service on liquidity provisioning - (`File: program/src/math.rs`)

### Summary
`InvariantToken::exchange_coin_to_pc` and `InvariantToken::exchange_pc_to_coin` internally call `.checked_div(...).unwrap()` (and `.checked_ceil_div(...).unwrap()`) on the pool's `token_coin`/`token_pc` totals, but always wrap the result in `Some(...)`, so the function signature returning `Option<u64>` never actually surfaces a `None` to callers — a zero divisor causes an immediate Rust panic instead of the graceful `AmmError::CalculationExRateFailure` the caller (`process_deposit`) expects via `.ok_or(...)?`. This mirrors the CVE-2019-12615 pattern of an unchecked value (there, an allocation result; here, a `checked_div` result) that can be null/`None` and is dereferenced/unwrapped without validation, crashing the program instead of failing safely.

### Finding Description
In `program/src/math.rs`: [1](#0-0) 
`exchange_coin_to_pc` divides by `self.token_coin` using `.checked_div(...).unwrap()` (Floor branch) or `.checked_ceil_div(...).unwrap()` (Ceiling branch). If `self.token_coin == 0`, `checked_div`/`checked_ceil_div` return `None`, and `.unwrap()` panics — the function can never actually return `None` to the caller as its `Option` return type implies; the whole function body is wrapped in `Some(...)`.

The same issue exists in `exchange_pc_to_coin`: [2](#0-1) 

This is invoked directly from `process_deposit` in `program/src/processor.rs`, an unprivileged, permissionless instruction reachable by any liquidity provider with attacker-chosen `max_coin_amount`/`max_pc_amount`/`base_side`: [3](#0-2) 
The only guard before this call is `amm.lp_amount == 0` (line 1180) — there is no check that `total_coin_without_take_pnl` or `total_pc_without_take_pnl` (the `token_coin`/`token_pc` fields feeding `InvariantToken`) are non-zero: [4](#0-3) [5](#0-4) 

`total_coin_without_take_pnl`/`total_pc_without_take_pnl` are derived from vault balances minus `need_take_pnl_coin`/`need_take_pnl_pc`: [6](#0-5) 
As `need_take_pnl_*` accumulates over the life of the pool (via `calc_take_pnl`, driven by price appreciation) and can approach/equal the corresponding vault amount, `total_coin_without_take_pnl` or `total_pc_without_take_pnl` can legitimately reach `0` while `amm.lp_amount` remains non-zero, since nothing in `process_deposit`, `process_withdraw`, or `calc_take_pnl` prevents this state.

### Impact Explanation
When the pool reaches a state where `total_coin_without_take_pnl == 0` (or `total_pc_without_take_pnl == 0`) with `lp_amount != 0`, any subsequent call to `process_deposit` with `base_side` selecting the zero-valued side as divisor will panic the program instead of returning a controlled `AmmError`. Because Solana aborts the entire transaction on panic, this makes the `Deposit` instruction permanently unusable for that AMM pool (a persistent denial-of-service against new liquidity provisioning), analogous to the unchecked-`kstrdup_const` NULL-dereference crash in the CVE: an unchecked "nullable" result (`None` from division) is unwrapped without validation, converting a recoverable error condition into a program crash.

### Likelihood Explanation
Reaching the zero-divisor state does not require a privileged signer — it results from normal pool lifecycle (price movement accumulating `need_take_pnl_*` toward vault balances) or can be engineered by an attacker who drains the relevant vault via `Swap`/`WithdrawPnl` operations to bring `total_coin_without_take_pnl`/`total_pc_without_take_pnl` toward zero, then submits a single `Deposit` transaction with `base_side` chosen to target the zero side, triggering the panic deterministically.

### Recommendation
Replace the internal `.unwrap()` calls in `InvariantToken::exchange_coin_to_pc`/`exchange_pc_to_coin` (and the analogous `InvariantPool` methods) with proper `checked_div`/`checked_ceil_div` propagation that returns `None` instead of panicking, so the existing `.ok_or(AmmError::CalculationExRateFailure)?` in `process_deposit` can actually catch the zero-divisor case and fail the transaction gracefully rather than panicking.

### Proof of Concept
1. Let a pool reach (through normal trading/PNL accrual, or attacker-driven swaps) a state where `total_coin_without_take_pnl == 0` while `amm.lp_amount > 0`.
2. Submit a `Deposit` instruction with `base_side = 0` (base coin) and any `max_coin_amount > 0`.
3. `process_deposit` builds `InvariantToken { token_coin: total_coin_without_take_pnl /* 0 */, token_pc: total_pc_without_take_pnl }` and calls `exchange_coin_to_pc(deposit.max_coin_amount, RoundDirection::Ceiling)`.
4. Inside `exchange_coin_to_pc`, `checked_ceil_div(self.token_coin.into())` divides by zero, returns `None`, and `.unwrap()` panics, aborting the transaction and bricking the `Deposit` path for the pool instead of returning `AmmError::CalculationExRateFailure`.

        token_coin: u64,

    ) -> Option<u64> {

            U128::from(token_coin)
                .checked_mul(self.token_pc.into())
                .unwrap()
                .checked_div(self.token_coin.into())

                .unwrap()

                .as_u64()
        })
    }
