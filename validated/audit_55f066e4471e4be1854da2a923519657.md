## Title
`EvmHost.dispatch()`, `dispatch(DispatchGet)`, and `fundRequest()` do not refund excess native token sent for fee swaps, permanently locking user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept `msg.value` and swap it via `IUniswapV2Router02.swapETHForExactTokens` for an exact amount of `feeToken` (`post.fee` / `get.fee` / `amount`). Any unused ETH from an over-supplied `msg.value` is refunded by the Uniswap V2 router — but the router refunds it to `msg.sender` of the swap call, which is `EvmHost` itself, not the original transaction caller. `EvmHost` never forwards this leftover ETH back to the caller, so it is permanently retained inside the host contract with no code path to recover it.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 
the function does `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` and discards the return value, capturing no refund logic afterward. The same pattern repeats verbatim in `dispatch(DispatchGet)`: [2](#0-1) 
and in `fundRequest`: [3](#0-2) 

Uniswap V2's `swapETHForExactTokens` sends any unspent ETH back to the address that invoked the router call — here that is `address(this)` (the `EvmHost` contract), because `EvmHost` is the direct caller of the router, not the original externally-owned account that sent the transaction. This is structurally identical to the reported bug class: a caller supplies more of an asset than is actually consumed by an exact-output swap (`amountInMax`/`msg.value` analog), and the unused portion is not routed back to the payer — it instead becomes stuck in the intermediary contract (`V3Proxy` in the original finding, `EvmHost` here).

Unlike `IntentGatewayV2.placeOrder` and `ExtrinsicIntents.fillOrder` in the same codebase, which explicitly track `msgValue -= amounts[0]` and call `_sendValue(msg.sender, msgValue)` to refund the unspent portion (see `evm/src/apps/IntentGatewayV2.sol:375-397` and `evm/src/apps/intentsv2/ExtrinsicIntents.sol:203-217`), `EvmHost.dispatch`/`fundRequest` have no equivalent refund step. There is no `receive()`/withdrawal mechanism visible in `EvmHost` that would let users reclaim this stranded ETH.

### Impact Explanation
Any unprivileged user or application dispatching a POST/GET request or funding a pending request with native token, who supplies `msg.value` greater than what the swap consumes (which is the normal case, since callers must estimate/guess the exact amount needed via off-chain quoting and typically over-provision to guarantee the swap succeeds against slippage), permanently loses the difference. Funds are not sent to any recoverable address, an attacker cannot even sweep them, and there is no governance/admin path shown to retrieve them from the contract — this is a direct, permanent freezing/loss of user funds reachable by any single `dispatch()` transaction, matching a "concrete... permanent freezing of funds" impact class.

### Likelihood Explanation
High likelihood in practice: `dispatch()` and `fundRequest()` are the primary entry points used by any app or user paying relayer fees in native currency across the entire Hyperbridge messaging surface (used by `IntentGatewayV2`'s fee-swap path, `HyperFungibleToken`, `HyperbridgeLzEndpoint`, and any custom `HyperApp`). Since exact swap output amounts can't be predicted precisely on-chain ahead of time (price moves between quote and execution), callers routinely send extra ETH as slippage buffer, guaranteeing this bug triggers on ordinary usage, not just adversarial inputs.

### Recommendation
Capture the array returned by `swapETHForExactTokens` (amounts[0] = ETH actually spent) in all three functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`), compute `refund = msg.value - amounts[0]`, and send it back to `_msgSender()` — mirroring the pattern already implemented in `IntentGatewayV2.placeOrder` (`msgValue -= amounts[0]; if (msgValue > 0) _sendValue(msg.sender, msgValue);`).

### Proof of Concept
1. Deploy/fork mainnet EVM host with a configured Uniswap V2 router and fee token.
2. Call `EvmHost.dispatch{value: X}(DispatchPost{... fee: F ...})` where `X > amountRequiredFor(F)` (e.g., send 5 ETH for a fee swap that only costs 0.1 ETH, mirroring the PoC pattern already present in this codebase's own tests at `evm/tests/foundry/IntentGatewayV2Test.sol:3714-3752` for the mitigated `IntentGatewayV2.placeOrder` path).
3. Observe `swapETHForExactTokens` refunds unspent ETH to `address(this)` (`EvmHost`), increasing the host's ETH balance.
4. Check the caller's ETH balance: it decreased by the full `X`, not by the actual amount spent on the swap — no refund was issued, and there is no subsequent call in `EvmHost` that returns this ETH to the caller, confirming the funds are stuck.

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(

            );

        }
