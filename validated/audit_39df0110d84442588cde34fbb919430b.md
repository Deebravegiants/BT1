### Title
Unbounded/cyclic ancestry walk in GRANDPA `AncestryChain::ancestry` allows a relayer-submitted consensus proof to spin the node in an infinite loop ("Loop with Unreachable Exit Condition") - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
The GRANDPA finality-proof verifier walks a caller-supplied `unknown_headers` list from `child_hash` back to a `base_hash` by repeatedly looking up `parent_hash` in a `BTreeMap` built directly from those untrusted headers, with no cycle detection and no bound on the number of hops. If the submitted header set contains a cycle that does not include the `base` hash, the `while current_hash != base` loop never terminates and never hits the `None` branch that would return `Error::NotDescendent`, because every hop successfully resolves to another attacker-controlled header in the cycle.

### Finding Description
`AncestryChain::ancestry` is implemented as: [1](#0-0) 

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

The `ancestry` map is built purely from the relayer-supplied `unknown_headers` (`AncestryChain::new`), with no validation that the headers form an acyclic chain ending at `base`, and no cap on how many distinct headers/hops it may traverse: [2](#0-1) 

This function is called from the entry point `verify_grandpa_finality_proof`, which is the top-level function invoked whenever a GRANDPA consensus proof is submitted (as a `ConsensusMessage`) to update on-chain (or light-client) consensus state: [3](#0-2) 

```rust
if base.number() < &consensus_state.latest_height {
    headers
        .ancestry(base.hash(), consensus_state.latest_hash)
        .map_err(|_| Error::InvalidAncestry)?;
}
let finalized = headers.ancestry(from, target.hash()).map_err(|_| Error::InvalidAncestry)?;
```

An attacker submitting a consensus update simply needs to supply `finality_proof.unknown_headers` containing a set of fabricated headers `H1, H2, H3, ...` whose `parent_hash` fields form a cycle disjoint from `base`/`from` (e.g. `H1.parent_hash = H2.hash()`, `H2.parent_hash = H3.hash()`, `H3.parent_hash = H1.hash()`), and set one of them as `finality_proof.block`/the justification's `target_hash` (matched against the earlier consistency checks in `verify_grandpa_finality_proof`, lines ~55-72). Because the map lookup for every hash in the cycle always succeeds (they are all present in `self.ancestry`), the loop never reaches the `None` branch and `current_hash` never equals `base`, so the function spins forever, consuming 100% CPU exactly as described for the pdfio `nGroups` bug — an "unreachable exit condition" caused by attacker-controlled loop state.

Note: `finality_grandpa::validate_commit` (called earlier in `GrandpaJustification::verify`) validates commit/precommit signatures, but the `unknown_headers` set used purely for the ancestry-route computation is not required to be signed or otherwise constrained to a straight-line chain terminating at `base`; the SCALE-decoded header list is attacker-supplied data forwarded straight into the map.

### Impact Explanation
This function sits directly on the path used to accept new GRANDPA consensus state and finalized parachain headers into Hyperbridge's ISMP consensus client (`modules/ismp/clients/grandpa/src/consensus.rs`), which is invoked whenever anyone relays a `ConsensusMessage` for a GRANDPA-based chain. A single malicious/malformed consensus-update submission can hang the executing thread/runtime in an infinite loop, denying availability of consensus updates for that state machine, and — if run inside block execution rather than pure off-chain worker context — can stall block production for the affected component. This is a denial-of-service against a core message-routing capability (consensus verification gates request/response delivery), matching the CVE's "Medium" DoS class (memory/CPU exhaustion via an unreachable loop exit), not a fund-theft or forgery bug.

### Likelihood Explanation
Likelihood is high for any deployment accepting permissionless GRANDPA consensus proofs (which is the design: any relayer can submit a proof). Constructing headers with the right hash-forming cycle only requires SCALE-encoding fabricated substrate-header-shaped structs with `parent_hash` fields set to each other's computed hashes — no cryptographic secret is needed, since these are just headers stored in an in-memory map used for path derivation, and the earlier `validate_commit`/signature checks apply to the finality commit/precommits, not to every element of `unknown_headers`.

### Recommendation
Bound `AncestryChain::ancestry` with an explicit step limit (e.g., cap iterations at `unknown_headers.len() + 1`) and/or track visited hashes in a `BTreeSet`, returning `Error::NotDescendent` (or a new cycle-detection error) once a hash is revisited or the step budget is exhausted, before ever reaching a cycle. Additionally consider validating on entry that `unknown_headers` forms a single, non-cyclic chain (e.g., by checking each header's number strictly decreases along the walk) before performing the ancestry walk.

### Proof of Concept
1. Craft three fake headers `H1`, `H2`, `H3` (arbitrary state/extrinsics roots, monotonically-decreasing block numbers are not enforced) such that:
   - `H1.parent_hash = hash(H2)`
   - `H2.parent_hash = hash(H3)`
   - `H3.parent_hash = hash(H1)`
2. Set `finality_proof.unknown_headers = [H1, H2, H3, target_header]` where `target_header.hash() == justification.commit.target_hash` (satisfying the checks at the top of `verify_grandpa_finality_proof`), and craft/borrow a valid justification for `target_header` so the early signature/commit checks pass.
3. Ensure `base` (the header with the lowest number among `unknown_headers`, or `consensus_state.latest_hash`) is not equal to any of `H1`, `H2`, `H3` and is unreachable from them (i.e., none of `H1..H3`'s `parent_hash` ever equals `base`).
4. Submit this `FinalityProof` as a `ConsensusMessage` to the ISMP GRANDPA consensus client's `verify` entrypoint.
5. Execution enters `headers.ancestry(from, target.hash())` (or the `base`-height check above it) and loops forever cycling through `H1 → H2 → H3 → H1 → ...`, never returning, hanging the calling context.
