### Title
CatFee API credentials (`api_key`, `api_secret`) logged in plaintext at INFO level - (File: `tesseract/messaging/tron/src/lib.rs`)

### Summary
`TronClient::new` logs the full `CatFeeConfig` struct — including the plaintext `api_key` and `api_secret` used to authenticate to the CatFee bandwidth-purchasing API — via `log::info!("CatFee integration enabled: {:#?}", catfee_config)`. Because `CatFeeConfig` derives `Debug` without redacting its secret fields, every field, including the raw HMAC signing secret, is written to whatever log sink is configured whenever the tesseract TRON relayer starts with CatFee credentials configured.

### Finding Description
`CatFeeConfig` is defined with `#[derive(Debug, Clone)]` and holds `api_key` and `api_secret` as plain `String` fields with no `Debug` redaction (e.g. no custom `impl Debug` masking the secret): [1](#0-0) 

`api_secret` is the HMAC-SHA256 signing key used to authenticate every CatFee order request (per the module doc, `Base64(HMAC-SHA256(secret, timestamp + method + requestPath))`): [2](#0-1) 

When `TronClient::new` builds this config from the operator-supplied API credentials, it logs the whole struct at `info` level using the `{:#?}` (pretty Debug) formatter before constructing the client: [3](#0-2) 

Since `Debug` is derived rather than manually redacted, this `log::info!` call serializes `api_key` and `api_secret` verbatim into the log line. Any relayer/operator log aggregation pipeline (stdout capture, log shipping to a SIEM, error-tracking integration, etc.) that runs at INFO or lower will receive the plaintext CatFee credentials — the exact bug class described in the Apache APISIX advisory (plaintext credentials logged at INFO/DEBUG and forwarded to log sinks).

### Impact Explanation
CatFee credentials authorize purchasing TRON bandwidth/energy on behalf of the relayer's TRON account and can be used to place financially-impactful orders against the operator's CatFee balance. Exposure through log files, log-shipping pipelines, or any third party with read access to the tesseract node's logs (common in shared infra, CI logs, or cloud logging services) allows an attacker to steal the credentials and abuse the CatFee account, or use the credential material to correlate/detect relayer infrastructure and target it further. This is a credential-exposure vulnerability directly reachable from normal relayer startup configuration, not from a privileged/administrative-only code path — the CatFee integration is optional operator configuration used by the TRON bandwidth-purchasing relayer component explicitly in scope.

### Likelihood Explanation
This triggers unconditionally and automatically on every startup of the TRON relayer client whenever `catfee_api_key` and `catfee_api_secret` are configured — there is no attacker action required beyond having read access to the operator's logs, which commonly occurs through misconfigured log verbosity, log aggregation services, or crash/monitoring integrations that capture INFO-level logs by default (this is precisely the scenario the upstream Apache APISIX CVE-2025-62232 also describes: an operator running at the default/INFO level unintentionally exposes secrets to whatever consumes those logs).

### Recommendation
Implement a manual `Debug` impl for `CatFeeConfig` that redacts `api_key` and `api_secret` (e.g., print `"***REDACTED***"` or only the last 4 characters), or avoid deriving `Debug` on the struct entirely and log only non-sensitive fields (e.g. `api_base`, `timeout`) explicitly instead of the whole struct with `{:#?}`.

### Proof of Concept
1. Configure a `TronConfig` with `catfee_api_key = Some("AKIA_REAL_KEY")` and `catfee_api_secret = Some("super-secret-hmac-key")`.
2. Call `TronClient::new(config)` (the standard construction path for the TRON messaging relayer).
3. Observe the process's INFO-level logs (or whatever sink log crate is configured to forward to, e.g. journald, a log file, or a log-shipping agent) contain the line:
   `CatFee integration enabled: CatFeeConfig { api_key: "AKIA_REAL_KEY", api_secret: "super-secret-hmac-key", api_base: "https://api.catfee.io", timeout: 30s }`
   confirming the plaintext secret is written to the log sink at INFO level.

	/// Generate HMAC signature for API request
	///
	/// Signature format: Base64(HMAC-SHA256(secret, timestamp + method + requestPath))
	/// where requestPath includes query parameters
	fn generate_signature(&self, timestamp: &str, method: &str, request_path: &str) -> String {
		let message = format!("{}{}{}", timestamp, method, request_path);

		let mut mac = HmacSha256::new_from_slice(self.config.api_secret.as_bytes())
			.expect("HMAC can take key of any size");
		mac.update(message.as_bytes());

		BASE64.encode(mac.finalize().into_bytes())
	}
