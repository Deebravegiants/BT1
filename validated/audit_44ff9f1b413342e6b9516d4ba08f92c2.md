## Title
Unbounded low-level `call` in `EvmHost.dispatchIncoming` enables a return-data gas bomb that can revert an entire relayed batch of POST requests/GET responses - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(PostRequest, address)` and its GET-response counterpart invoke the destination application with a raw, ungas-limited low-level `.call(...)`, exactly the pattern flagged in the external report. Because Solidity implicitly copies *all* returndata from a low-level call into memory before the `success` flag can be checked, a malicious destination contract can force that copy to be arbitrarily expensive. Since `HandlerV2.handlePostRequests`/`handleGetResponses` iterate over an entire batch of proven messages and call `host.dispatchIncoming` for each one in a single transaction with no per-message gas isolation or try/catch boundary, one attacker-controlled message in the batch can burn all remaining gas in the transaction and abort delivery of every other (legitimate) message batched alongside it. [1](#0-0) [2](#0-1) 

### Finding Description
`dispatchIncoming` resolves the destination address from `request.to` (fully attacker-controlled, since any user can call `IDispatcher.dispatch` with an arbitrary `to` on the destination chain) and executes:

```solidity
(bool success,) = address(destination)
    .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
``` [3](#0-2) 

The same unrestricted pattern is used for GET responses, POST timeouts, and GET timeouts: [4](#0-3) [5](#0-4) [6](#0-5) 

None of these calls bound the amount of gas forwarded, nor the size of returndata copied back into the caller's memory. As with the referenced Recall/`CrossMsgHelper` report, a callee can cheaply grow its own memory and `return`/`revert` a large payload; the EVM must then copy that same payload into the caller's memory when the call unwinds, at quadratic memory-expansion cost that is charged against the **caller's** remaining gas — not the callee's. This is a classic "return-data bomb."

Crucially, `dispatchIncoming` is invoked from a loop over an entire relayed batch:

```solidity
for (uint256 i = 0; i < requestsLen; ++i) {
    ...
    host.dispatchIncoming(leaf.request, _msgSender());
}
``` [7](#0-6) 

and identically for `handleGetResponses`: [8](#0-7) 

There is no try/catch, no gas stipend limiting, and no returndata truncation around any of these calls or the surrounding loop. An out-of-gas exception triggered by the returndata copy during one message's dispatch is not contained to that message — it propagates and reverts the entire `handlePostRequests`/`handleGetResponses` (and, if wrapped, the entire `batchCall`) transaction: [9](#0-8) 

### Impact Explanation
An attacker can:
1. Deploy a malicious contract on the destination chain implementing `onAccept`/`onGetResponse` that, on invocation, returns (or reverts with) a large data blob sized to make the caller's implicit returndata copy consume most of the remaining transaction gas.
2. Dispatch a legitimate, provable cross-chain message (`IDispatcher.dispatch`) from any source chain targeting this malicious contract as `to`, requiring no special privilege.
3. Once relayed and included by `HandlerV2.handlePostRequests`/`handleGetResponses` in the same batch as other, legitimate messages (which relayers batch together to amortize proof-verification costs), the malicious message's dispatch triggers the gas bomb, causing the whole batch transaction to run out of gas and revert.

Because these calls are not wrapped in per-message gas caps and the loop is transactional, all other requests/responses batched with the malicious one fail to be delivered, and relayers must resubmit smaller batches (raising relaying costs) or risk repeatedly hitting the same poisoned message if it is included again. This directly undermines the intended fault-isolation design documented in `dispatchIncoming`'s early-return-on-failure pattern (which assumes ordinary reverts, not OOG from returndata copying), producing a denial-of-service on legitimate message delivery — a route rendered unable to deliver messages, matching the accepted impact class for this report family.

### Likelihood Explanation
The precondition (deploying an arbitrary contract as message recipient and dispatching a message to it) requires no special privilege — any address can be the `to` of a dispatched request, and any account can call `dispatch`. Relayers routinely batch multiple proven messages into a single `handlePostRequests`/`handleGetResponses`/`batchCall` transaction to amortize gas, meaning legitimate traffic can be collaterally impacted by any single malicious inclusion. The attack is inexpensive relative to the disruption caused, since malicious return-data can be constructed to be cheap for the callee (its own memory expansion) while forcing an equivalent, cumulative cost onto the shared batch transaction's remaining gas budget.

### Recommendation
Wrap all low-level calls in `EvmHost.dispatchIncoming`/`dispatchTimeOut` with a bounded-returndata-safe call helper (e.g., `ExcessivelySafeCall`, or manual `call` + `returndatacopy` with a fixed max length), and/or forward only a capped amount of gas to the destination so a malicious recipient cannot induce unbounded memory-expansion costs on the caller.

### Proof of Concept
1. Attacker deploys `Bomb` on the destination chain:
```solidity
contract Bomb is IApp {
    function onAccept(IncomingPostRequest calldata) external onlyHost {
        assembly {
            return(0, 1000000) // large returndata, cheap for Bomb's own forwarded gas
        }
    }
}
```
2. Attacker (or anyone) calls `IDispatcher(host).dispatch(DispatchPost{ to: address(Bomb), ... })` from a source chain, producing a valid, provable `PostRequest`.
3. A relayer batches this request together with N legitimate `PostRequestLeaf`s into one `PostRequestMessage` and calls `HandlerV2.handlePostRequests`.
4. During the loop at [7](#0-6) , when `host.dispatchIncoming` reaches the `Bomb` request, the low-level `.call` in `EvmHost.dispatchIncoming` [3](#0-2)  triggers a costly returndata copy, exhausting the remaining gas of the outer transaction and reverting the entire batch, including the legitimate co-batched messages.

        address destination = _bytesToAddress(request.to);

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
