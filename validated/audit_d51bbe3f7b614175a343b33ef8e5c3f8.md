### Title
Webhook `shop` (and `topic`/`api-version`) identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — read straight from unauthenticated HTTP headers — are the values actually delivered to the host application's webhook handler as the tenant identity. Because `Utils::HmacValidator.validate` only proves that *the body* was signed with the app's `client_secret`, and never proves that the *shop-domain header* was, an attacker who can obtain any one valid `(body, hmac)` pair signed with the app's shared secret (e.g. by triggering a webhook on their own store, which every merchant using the app can legitimately do) can replay that exact body/HMAC pair while swapping the `X-Shopify-Shop-Domain` header to an arbitrary victim shop. `Registry.process` will accept it as valid and dispatch it to the handler tagged with the attacker-chosen shop, breaking the identity binding between the HMAC-covered bytes and the shop the application believes originated the event.

### Finding Description
- `HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`, using `OpenSSL.secure_compare`: [1](#0-0) 
- For webhooks, `to_signable_string` returns only `@raw_body`, and `hmac` is parsed from the `hmac-sha256` header: [2](#0-1) 
- Critically, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from client-supplied headers and are never part of the signed content: [3](#0-2) 
- `Registry.process` validates only the HMAC (i.e., the body), then immediately trusts `request.shop` (and `request.topic`) as the tenant identity for dispatch: [4](#0-3) 
- The `WebhookMetadata` built from these unauthenticated header values is exactly what host applications are documented to use for tenant attribution (`data.shop`, `data.topic`): [5](#0-4) 

The equality that should hold is:
`shop bound by HMAC == shop delivered to WebhookHandler.handle`

but in this implementation it is actually:
`shop bound by HMAC == "" (nothing) ; shop delivered to handler == header value chosen by whoever sends the HTTP request`

Since the HMAC secret (`Context.api_secret_key`) is the same for every shop installing a given app, any merchant/attacker who has installed the app on their own store can legitimately trigger a webhook (e.g. `orders/create`) and receive a correctly signed `(body, hmac)` pair for that body. That signature says nothing about which shop it came from. The attacker can then POST that same `raw_body` and `hmac-sha256` header to the app's public webhook endpoint, but with `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) rewritten to a victim shop's domain. `Registry.process` will pass HMAC validation (the body is unmodified and correctly signed) and hand the handler a `WebhookMetadata` claiming the event came from the victim shop.

### Impact Explanation
This breaks the tenant-identity binding the HMAC is supposed to provide. A host application that (as documented) uses `data.shop` to decide which tenant's records to create/update/delete based on webhook content will process attacker-controlled data under a victim shop's identity — this is a cross-tenant data-injection primitive achieved without possessing the victim's access token, session, or any credential beyond the ability to trigger webhooks on the attacker's own store using the same shared app secret.

### Likelihood Explanation
Likelihood is high for any app: any user who installs the app (a normal, unprivileged action) can generate a validly-signed webhook body for themselves. The webhook endpoint is a public, internet-facing HTTP route by design (per `docs/usage/webhooks.md`), and no additional secret or credential is required to send it a forged request — only the ability to intercept/observe one's own legitimately-delivered webhook `(body, hmac)` pair and replay it with modified headers.

### Recommendation
Bind the identity fields into the signed content, or otherwise cryptographically bind the `shop-domain` (and `topic`) header to the request before dispatch:
- Change `Webhooks::Request#to_signable_string` (or `HmacValidator`) so that `shop`, `topic`, and `webhook_id` are included in the material that is HMAC-verified, not just the raw body, or
- Independently verify shop ownership/authenticity of the `shop-domain` header (e.g., cross-check against a known/registered shop list obtained via an authenticated channel) before trusting it in `WebhookMetadata`, or
- At minimum, document prominently that `data.shop`/`data.topic` are NOT covered by the HMAC and must not be used for authorization/tenant-routing decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers `orders/create`. They capture the resulting HTTP request their own store's webhook delivers to the app: `raw_body = B`, header `X-Shopify-Hmac-Sha256: H` (valid since `H = HMAC-SHA256(client_secret, B)`), `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker resends the identical request to the app's public webhook endpoint, but replaces the header: `X-Shopify-Shop-Domain: victim.myshopify.com`. Body `B` and `X-Shopify-Hmac-Sha256: H` are left untouched.
3. Server-side: `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...with victim's shop-domain...})` is constructed and passed to `ShopifyAPI::Webhooks::Registry.process`.
4. `HmacValidator.validate(request)` calls `compute_signature(request.to_signable_string, secret)` which only re-hashes `B` — matches `H` — validation succeeds: [6](#0-5) 
5. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: JSON.parse(B), ...))`: [7](#0-6) 
6. The host application's handler now processes attacker-supplied order data believing it originated from `victim.myshopify.com`, even though the victim never sent this event.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
