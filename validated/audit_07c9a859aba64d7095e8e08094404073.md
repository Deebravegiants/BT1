### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers — none of which are included in the signed payload — when constructing the `WebhookMetadata` passed to the host app's handler.

### Finding Description
The identity binding that should hold is:
`hmac_signed_bytes == bytes_the_handler_acts_on`

In `ShopifyAPI::Webhooks::Request`, the value fed into the HMAC computation is only the raw body: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are all pulled straight from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates only the HMAC (which covers the body) and then hands the header-derived `shop`/`topic`/`webhook_id` straight to the app's handler as trusted tenant/routing metadata: [3](#0-2) 

`WebhookMetadata.shop` is a plain, unvalidated `String` field consumed by the host application's `WebhookHandler#handle`: [4](#0-3) 

The HMAC secret (`Context.api_secret_key`) is shared across every shop that has the app installed — it is not per-shop: [5](#0-4) 

Because of this, any merchant who has legitimately installed the app can capture a valid `(raw_body, x-shopify-hmac-sha256)` pair from a webhook delivered to their own endpoint, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header value naming a *different* tenant. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` will dispatch the handler with the attacker-chosen `shop` value as if Shopify itself vouched for it.

### Impact Explanation
This breaks the equality `shop_authenticated_by_hmac == shop_the_handler_believes_it_received_data_for`. Any host application that uses `WebhookMetadata#shop` to key data writes, cache invalidation, order/customer records, or authorization decisions (a documented and expected usage pattern per this gem's webhook docs) can be tricked into applying attacker-supplied body content under a victim shop's identity — i.e., cross-tenant data injection/access. This matches the Critical bucket ("cross-tenant access").

### Likelihood Explanation
Any unprivileged internet user who is (or becomes) a merchant installer of the target app satisfies the prerequisites: no `api_secret_key`, access token, or privileged account is required — only receipt of one legitimately signed webhook for their own shop, which the shared-secret HMAC scheme guarantees is byte-identical in validity regardless of which shop's header claims are attached. The attack is a header swap on a replayed request, requiring no cryptographic break.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them, e.g., by having `to_signable_string` incorporate the header values Shopify signs), so that any mismatch between headers and signed content is rejected by `Utils::HmacValidator.validate`. At minimum, document that `WebhookMetadata#shop`/`#topic` are unauthenticated and must be cross-checked by the host application against a known/expected shop before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers an HTTP webhook (e.g. `orders/create`) pointed at their own listener, or intercepts a delivery.
2. Attacker captures the raw POST body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker sends a new HTTP request to the target app's webhook endpoint with body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com` (a real installed shop) instead of their own domain.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares it to `H` — this succeeds because `B` is unmodified.
5. `Registry.process` then invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: JSON.parse(B), ...)`, causing the host application to process attacker-controlled data under the victim's tenant identity.
