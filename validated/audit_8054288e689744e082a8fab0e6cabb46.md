### Title
Missing `nonReentrant` guard on Tron `IntentGatewayV2.placeOrder()` allows reentrant escrow/state manipulation - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical EVM `IntentGatewayV2.placeOrder()` is guarded with `nonReentrant` [1](#0-0) , and the project's own `IntrinsicIntentsReentrancyTest.sol` shows the team already had to retrofit checks-effects-interactions into `fillOrder`'s same-chain/cross-chain fill paths after a reentrancy bug was found [2](#0-1) . The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the identical `placeOrder()` logic but declares it **without** `nonReentrant` and does not import/inherit any reentrancy guard at all [3](#0-2) . This is the same bug class as H-14: a state-mutating, externally reachable entrypoint that performs external calls mid-execution while state (`_nonce`, `_orders[commitment][token]`) is still being assembled, without reentrancy protection.

### Finding Description
`placeOrder()` in the Tron contract:
1. Increments the global nonce and computes the order commitment [4](#0-3) .
2. When a `predispatch` call is set, transfers assets to an attacker/caller-controlled `dispatcher` and then invokes `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` with **arbitrary caller-supplied calldata**, followed by a second dispatcher call to sweep funds back [5](#0-4) .
3. Only after these external calls does it credit escrow into `_orders[commitment][token]` [6](#0-5) , and separately handle fee escrow, which itself makes an external Uniswap swap or `safeTransferFrom` call before writing `_orders[commitment][TRANSACTION_FEES]` [7](#0-6) .

Because no `nonReentrant` modifier exists, the `dispatch()` callback (or the fee-swap external call) can re-enter `placeOrder()`, `cancelOrder()`, `onAccept()` (escrow redeem/refund `withdraw()`), or `onGetResponse()`/`withdraw()` on the same contract while the outer call's escrow bookkeeping is incomplete. This mirrors the mergeTranches pattern in the reference report: an externally triggered callback executing mid-transaction while `_loans`/`_orders` storage is only partially updated, letting the attacker fork the flow into two inconsistent, independently-redeemable states.

The main EVM contract explicitly closes this window with `nonReentrant` [1](#0-0) , confirming the team recognizes `placeOrder` as reentrancy-sensitive; the Tron variant is a regression of that fix.

### Impact Explanation
A caller controlling `order.predispatch.call` (executed via `ICallDispatcher.dispatch`) or a malicious/fee-on-transfer fee token can reenter the gateway mid-`placeOrder`. Depending on the reentrant path chosen (e.g., re-entering `cancelOrder` on a commitment computed with a nonce/order state not yet fully persisted, or re-entering `placeOrder` again to manipulate `_nonce`/commitment ordering before the outer call's escrow write lands), escrow accounting (`_orders[commitment][token]`) can be desynchronized from the tokens actually held by the contract — enabling theft of escrowed input tokens/fees or permanent freezing of legitimate orders' funds, the same class of loss described for `_loans[]` corruption in H-14.

### Likelihood Explanation
`placeOrder` is a permissionless, user-facing entrypoint reachable by any solver/user submitting an order with a `predispatch.call`/`predispatch.assets` payload routed through `ICallDispatcher`, or by using a fee token with transfer hooks — no privileged role is required. The reference report and the project's own reentrancy test suite demonstrate this exact function family (`fillOrder`) was previously exploitable this way on the main EVM contract, showing the attack pattern is realistic and already validated as reachable in this codebase; only the Tron port failed to receive the corresponding fix.

### Recommendation
Add a reentrancy guard (`ReentrancyGuard`/`nonReentrant`) to `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`, mirroring `evm/src/apps/IntentGatewayV2.sol`, and audit `cancelOrder`, `withdraw`, `onAccept`, and `onGetResponse` in the Tron contract for the same missing protection, applying checks-effects-interactions (write `_orders`/`_nonce`/`_filled` state before any external call) consistent with the CEI fix already applied to `fillOrder` in the main contract.

### Proof of Concept
1. Attacker crafts an `Order` with `predispatch.call` pointing at a malicious contract deployed as the `CallDispatcher` target (or a fee token with a transfer hook), and calls `IntentGatewayV2(tron).placeOrder(order, graffiti)`.
2. During `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` (line 414) or during the fee-token `safeTransferFrom`/swap (lines 474-485), the malicious contract re-enters `placeOrder` (or `cancelOrder`/`withdraw` via `onAccept`) before the outer call's `_orders[commitment][token] += reducedInputs[i].amount` has executed.
3. Because `placeOrder` has no `nonReentrant` guard, the reentrant call succeeds, allowing the attacker to manipulate `_nonce`/commitment state or trigger `withdraw` against escrow that has not yet been (or is only partially) credited, producing an accounting mismatch that lets the attacker redeem more than deposited or leaves legitimate escrow permanently stuck.
