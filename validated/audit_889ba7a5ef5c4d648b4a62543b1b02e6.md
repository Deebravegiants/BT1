### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity using only the raw request body as the HMAC-signed content, while the `shop` (tenant) identity is read from an unauthenticated HTTP header. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose HMAC matches the body, then forwards the caller-supplied `shop` header value to the app's handler as trusted tenant identity. This breaks the equality that should hold: `shop bound by HMAC == shop delivered to handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and does not include `shop`, `topic`, `api_version`, or `webhook_id`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC and, on success, unconditionally trusts `request.shop` as tenant identity when building `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the app's `client_secret` (and thus HMAC secret) is the same for every shop that installs the app, any body+HMAC pair that was legitimately generated by Shopify for one shop (e.g. an attacker's own development/test store that has the app installed) remains a *valid* signature for that exact body regardless of which `shop` header accompanies it. An unprivileged internet user who controls a shop with the app installed can capture a legitimate webhook delivery (raw body + valid `hmac-sha256` header) and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it only checks the untouched body bytes, and `Registry.process` passes the attacker-controlled `shop` value straight to the handler as the authenticated tenant.

This is the "bytes verified versus bytes parsed" / "shop authenticated versus the shop stored as identity" analog: the equality `signed_bytes == identity-bearing_shop` does not hold, since `shop` is parsed from headers that sit entirely outside the HMAC's protected scope.

### Impact Explanation
If the app's webhook handler uses `WebhookMetadata#shop` to select which tenant's records to read, write, or trigger side effects for (a common pattern, e.g. `shopify_app`'s webhook job dispatch keyed by shop), this allows a low-privilege user (anyone who can install the app on any shop, including a free/dev store) to inject attacker-controlled webhook bodies that are processed and attributed to a victim shop of their choosing. This is a cross-tenant data confusion vector: the attacker's payload (e.g. `orders/create`, `customers/data_request`, `app/uninstalled`, etc.) executes app-side logic as if it originated from the victim shop, potentially triggering unwanted actions, data corruption, or leaking victim-shop-scoped behavior — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires: (1) the attacker to have (or create) a shop with the app installed, so Shopify sends them a legitimately-HMAC-signed webhook body, and (2) the app's webhook endpoint to be reachable and to trust `WebhookMetadata#shop` for tenant-scoped actions without any additional binding (e.g. cross-checking against a session/shop registered for that specific webhook_id or an out-of-band verification). Both conditions are realistic for any public multi-tenant Shopify app, since installing an app on a store is generally free and self-serve, making this a Medium-to-High likelihood issue for apps that don't add their own compensating tenant checks.

### Recommendation
Include the delivery-identifying fields (`shop`, `webhook_id`, `topic`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind the shop-domain header to the verified payload before it is handed to `Registry.process`'s handler dispatch, e.g. by having `Request#to_signable_string` incorporate the header values Shopify actually signs over (mirroring how `AuthQuery#to_signable_string` binds `shop`, `host`, `state`, etc.), or by requiring the app to separately confirm the delivered `shop`/`webhook_id` pair against Shopify's Admin API before trusting it for tenant-scoped effects.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app: body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`), header `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the same request to the app's webhook endpoint, but changes `shopify-shop-domain` to `victim-shop.myshopify.com`, keeping body `B` and header `H` unchanged.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the (now attacker-modified) header: [2](#0-1) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H`, so validation passes: [5](#0-4) 
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: request.shop, ...)`, delivering `shop: "victim-shop.myshopify.com"` together with attacker-controlled body `B`, even though `B` and `H` were never issued for `victim-shop`: [6](#0-5)
