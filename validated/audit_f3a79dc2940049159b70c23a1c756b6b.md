### Title
`WrappedHyperFungibleTokenUpgradeable` (and its non-upgradeable twin) unconditionally calls `safeTransfer`/`safeTransferFrom` for zero-amount cross-chain messages, permanently bricking delivery for underlying tokens that revert on zero-value transfers - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol)

### Summary
`WrappedHyperFungibleTokenUpgradeable.onAccept`, `onPostRequestTimeout`, and `send` all move the underlying ERC20 with an amount taken directly from an untrusted/attacker-influenced message field, with no `amount != 0` guard, unlike the escrow-release path in `IntentsBase._withdraw`, which explicitly does `if (amount == 0) continue;` before transferring. If the wrapped `_underlying` token reverts on zero-value transfers (a documented real-world token behavior class), a legitimately-dispatched zero-amount cross-chain message becomes permanently undeliverable.

### Finding Description
`WrappedHyperFungibleTokenUpgradeable` is the home-chain "lock" side of the `HyperFungibleToken` bridge; the paired remote-chain contract is `HyperFungibleToken`, which is burn/mint-based: [1](#0-0) 

`HyperFungibleToken.send()` calls `_burn(msg.sender, params.amount)` with **no minimum-amount check**, so any account can dispatch a cross-chain transfer message with `amount == 0` — OpenZeppelin's `_burn(0)` does not revert.

That message is delivered to the home chain and handled by: [2](#0-1) 

For the non-WETH branch, `onAccept` unconditionally executes `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` regardless of whether `message.amount` is zero. If `_underlying` is a token that reverts on zero-value transfers, this call always reverts deterministically for that message.

The same missing guard exists in the timeout handler: [3](#0-2) 

and in `send()`'s `safeTransferFrom`: [4](#0-3) 

This is the exact bug class from the external report: a zero-value-reverting token combined with unconditional transfer of a possibly-zero amount. The codebase already recognizes this pattern needs a guard elsewhere — `IntentsBase._withdraw` explicitly skips zero amounts before transferring: [5](#0-4) 

but `WrappedHyperFungibleTokenUpgradeable` (and the identically-structured `WrappedHyperFungibleToken.sol`) lacks this protection.

Once a message reaches `onAccept` via `EvmHost`/`HandlerV2`, the host only marks the request as received if the module call succeeds: [6](#0-5) 

If `onAccept` reverts deterministically (because the amount is always 0 for that specific commitment and the token always reverts on zero-value transfer), a relayer can retry the delivery indefinitely and it will always fail — the request commitment can never be cleared/received, so that message can never be delivered to its destination through this route.

### Impact Explanation
This is a "route unable to deliver messages" condition: any zero-amount transfer routed from a remote `HyperFungibleToken` deployment to a `WrappedHyperFungibleTokenUpgradeable` instance wrapping a zero-transfer-reverting token becomes permanently stuck — it can never be accepted, and no relayer or retry can resolve it. The analogous timeout path (`onPostRequestTimeout`) has the same defect: a zero-amount outbound message that times out can never be refunded/settled, leaving the pending request state permanently unresolved on the source-side host as well (any collected relayer fee for that request also stays escrowed indefinitely since the module never finalizes the message).

### Likelihood Explanation
Likelihood is Medium: it requires (a) the wrapped `_underlying` token to revert on zero-value transfers — a known but uncommon token trait — and (b) a zero-amount `send()` call, which is trivially reachable by any unprivileged user calling `HyperFungibleToken.send()` on the remote chain with `amount = 0` (no minimum-amount validation exists there either). No special privileges, governance, or malicious relayer/consensus corruption are required — a single ordinary user transaction is sufficient to trigger the permanently-stuck message.

### Recommendation
Mirror the guard already used in `IntentsBase._withdraw`: skip the token transfer entirely when the message amount is zero (and consider also rejecting zero-amount sends in `HyperFungibleToken.send()`/`HyperFungibleTokenUpgradeable.send()` and the corresponding Wrapped variants):

```solidity
if (message.amount != 0) {
    IERC20(_underlying).safeTransfer(beneficiary, message.amount);
}
```

Apply the same fix to `onPostRequestTimeout`'s `safeTransfer` calls and to `send()`'s `safeTransferFrom`, in both `WrappedHyperFungibleTokenUpgradeable.sol` and `WrappedHyperFungibleToken.sol`.

### Proof of Concept
1. Deploy `HyperFungibleToken` on chain B (remote/burn-mint side) and `WrappedHyperFungibleTokenUpgradeable` on chain A (home/lock side), with chain A's `_underlying` set to a token that reverts on `transfer(to, 0)` (e.g., the `ZeroTransferERC20` pattern from the original report).
2. Register the chains as peers per `addChain`.
3. On chain B, any user calls `HyperFungibleToken.send({ dest: chainA, to: recipient, amount: 0, ... })`. `_burn(msg.sender, 0)` succeeds; the POST request is dispatched.
4. A relayer delivers the request to chain A's `EvmHost`, which calls `WrappedHyperFungibleTokenUpgradeable.onAccept`.
5. `IERC20(_underlying).safeTransfer(beneficiary, 0)` reverts inside `onAccept`; per `HandlerV2.handlePostRequests` → `host.dispatchIncoming`, the request is never marked as received, so any subsequent relayer resubmission hits the exact same deterministic revert — the message can never be delivered.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(request.body, (HyperFungibleTokenUpgradeable.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({from: message.from, to: beneficiary, source: string(request.source), amount: message.amount});
    }
