### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` identity that is later trusted by `Registry.process` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signed material. This breaks the binding: `shop authenticated == shop used to route/attribute the event`.

### Finding Description
`ShopifyAPI::Webhooks::Request` includes `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; the `topic`, `shop`, `api_version`, and `webhook_id` accessors read from unauthenticated headers: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the body only) and compares it against the received `hmac`: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` (from the header) to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

Because the signature only proves "this body byte-sequence was signed with the app's `client_secret` at some point by Shopify," and never binds *which shop* the payload belongs to, an attacker who can reach the app's webhook endpoint can take **any previously-observed, legitimately-signed webhook body+HMAC pair** (e.g., from their own shop, or one leaked/logged/replayed) and resend it with a different `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` (the body and HMAC are unmodified and match), but `Registry.process` will attribute the event to the attacker-chosen `shop`, invoking the app's handler as if the victim shop sent it — a direct violation of the equality `shop verified by HMAC == shop used for tenant routing`.

### Impact Explanation
This is a cross-tenant attack: an app's webhook handler typically uses `shop` to look up/create/update per-tenant records (e.g., orders, customer data, redact requests, entitlements). By spoofing the `shop-domain` header on a validly-signed body, an attacker can inject or corrupt data under another merchant's tenant context, or trigger mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) against a shop they don't control. This matches the "Critical - cross-tenant access" impact category, since the tenant boundary (`shop`) is not part of what's authenticated.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair signed by Shopify — which any merchant with a store on the target app already legitimately receives for their own webhooks (e.g., `orders/create` with attacker-controlled content) — and to be able to POST directly to the app's public webhook endpoint with a forged `shop-domain` header. Since the endpoint is typically internet-reachable (that's the point of webhooks) and headers are fully attacker-controlled on a raw HTTP request, likelihood is realistic for any app whose webhook handler trusts `shop` for tenant routing/authorization without independent verification.

### Recommendation
Do not treat the `shop-domain` header as trusted merely because the HMAC over the body validates. Either:
- Include the shop domain in the signed material used for verification (not possible unilaterally since Shopify controls the signature format), or
- Cross-check `request.shop` against an independent, already-authenticated source of truth (e.g., look up the specific webhook subscription/shop pair registered with Shopify for that `webhook_id`, or validate against the shop associated with the app's stored session/installation before trusting the payload for that tenant), and document this requirement prominently for consumers of `ShopifyAPI::Webhooks::Registry` and `Request`.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimately signed webhook, e.g. `orders/create` with headers:
   - `x-shopify-hmac-sha256: <valid-hmac-of-body>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
2. Attacker resends the exact same raw body and `x-shopify-hmac-sha256` value directly to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (`lib/shopify_api/webhooks/request.rb:45-63`), `HmacValidator.validate` succeeds because it only checks the (unmodified) body against the (unmodified) HMAC (`lib/shopify_api/utils/hmac_validator.rb:13-22`), and `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:190-199`), causing the app to process attacker-controlled data as if it originated from the victim's shop.

          received_signature = verifiable_query.hmac
