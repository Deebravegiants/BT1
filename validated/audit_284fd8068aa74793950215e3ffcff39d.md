### Title
CostModel::calculate_allocated_accounts_data_size only inspects top-level System Program instructions and misses CPI-invoked allocations - (File: cost-model/src/cost_model.rs)

### Summary
`CostModel::calculate_allocated_accounts_data_size` estimates a transaction's account-data allocation solely from `transaction.program_instructions_iter()`, i.e. the top-level (outer) instructions, and only recognizes allocation when `program_id == system_program::id()` directly at that top level. Any account-data growth performed by a CPI from a user-deployed BPF program into the System Program (`CreateAccount`, `CreateAccountWithSeed`, `Allocate`, `AllocateWithSeed`, `CreateAccountAllowPrefund`) is invisible to this estimator, so `allocated_accounts_data_size` returned to `CostTracker` can be `0` while real, measured account growth is non-zero.

### Finding Description
`CostModel::calculate_allocated_accounts_data_size` (`cost-model/src/cost_model.rs:265-301`) iterates `instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>`, which is always populated from the *outer* message instructions (`transaction.program_instructions_iter()` / `SVMStaticMessage::program_instructions_iter`, see e.g. `cost-model/src/cost_model.rs:36-51`). For each outer instruction, `calculate_account_data_size_on_instruction` (`cost-model/src/cost_model.rs:242-261`) only recognizes an allocation if `program_id == &system_program::id()` for that specific outer instruction and deserializes only that instruction's data via `calculate_account_data_size_on_deserialized_system_instruction` (`cost-model/src/cost_model.rs:203-240`). There is no traversal of the instruction trace / CPI stack (unlike `svm/src/transaction_processor.rs:1234+` which does walk `instruction_trace` including CPIs for other purposes such as inner-instruction reporting).

Consequently, if the attacker's top-level instruction targets a program other than the System Program (e.g., their own permissionlessly-deployed program) and that program performs a CPI to the System Program's `CreateAccount`/`Allocate`/etc., `calculate_account_data_size_on_instruction` returns `SystemProgramAccountAllocation::None` for that outer instruction (since `program_id != system_program::id()`), and the entire CPI-driven allocation contributes `0` to `allocated_accounts_data_size`.

This value feeds `TransactionCost.allocated_accounts_data_size` (`cost-model/src/transaction_cost.rs:15,35-37`), which `CostTracker::would_fit` (`cost-model/src/cost_tracker.rs:272-309`, esp. lines 288-293) uses to enforce `CostTrackerLimits::allocated_data_size` (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`, `cost-model/src/cost_tracker.rs:75-96`). Since the estimate is `0`, `would_fit` never rejects/limits such transactions on the account-data-size axis, and `add_transaction_cost`/`remove_transaction_cost` (`cost-model/src/cost_tracker.rs:313-336`) accumulate `0` into `self.allocated_accounts_data_size` regardless of the real bytes allocated.

Actual per-transaction runtime enforcement of resize growth is separate and real: `TransactionAccounts::can_data_be_resized` (`transaction-context/src/transaction_accounts.rs:309-326`) caps `resize_delta` at `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` regardless of whether the growth originates from a top-level instruction or a CPI, and the true chain-wide accounts-data-size delta used for consensus bookkeeping (`runtime/src/bank.rs:4419-4430`, `update_accounts_data_size_delta_on_chain`) is computed from the *actual* `accounts_resize_delta`/`accounts_uninitialized_size` returned by execution, not from the cost-model estimate. So the global on-chain accounting is accurate and this is not a consensus-divergence or double-settlement bug. The gap is isolated to the leader-side/scheduler-side `CostTracker`, which uses the pre-execution static estimate to decide whether transactions "fit" into a block/account budget.

### Impact Explanation
An unprivileged attacker can deploy a trivial permissionless BPF program that CPIs into the System Program to create/allocate accounts (up to `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` per transaction, enforced by the runtime), and wrap that call as the top-level instruction. `CostModel::calculate_allocated_accounts_data_size` will compute `allocated_accounts_data_size == 0` for such a transaction because it never inspects CPI-invoked System Program calls. Because `CostTracker::would_fit` uses this value to police `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`, the attacker can pack many such transactions into a block that each still individually pass the per-transaction runtime cap, yet collectively cause real account-data growth far above what the cost tracker's `allocated_accounts_data_size` bookkeeping reflects, exhausting the intended per-block account-data growth budget without ever being throttled by it. This matches the described bounty category: materially underpriced/undercounted resource accounting that lets an attacker exceed effective block capacity for account-data growth (cost-model/cost-accounting underpricing), scoped to `gossip/src/crds_entry.rs`'s referenced impact class ("compute-budget, cost-model, or fee accounting charge materially less than the real ... work performed"). It does not corrupt on-chain state or cause cross-node divergence, since the authoritative accounts-data-size accounting in `bank.rs` uses actual execution deltas.

### Likelihood Explanation
High feasibility and fully within the "unprivileged attacker" threat model: no special privileges, staking, or leader control are required — only the ability to deploy an ordinary BPF program (a normal, permissionless operation) and submit transactions to a public RPC/TPU that CPI into the System Program's allocating instructions. The bug is deterministic and reproducible for every transaction whose top-level instruction is not the System Program itself but performs system-program CPIs; it does not depend on race conditions, malformed instruction data, or fuzzing edge cases (though such variations were part of the question, the core gap is simply "not top-level" CPI usage, which is a completely normal, everyday transaction pattern, e.g. programs that create PDAs via `invoke_signed(system_instruction::create_account(...))`).

### Recommendation
Extend `CostModel::calculate_allocated_accounts_data_size` (or its estimation call sites in `CostModel::calculate_cost`/`estimate_cost`) to account for CPI-invoked System Program allocations, or otherwise ensure `CostTracker`'s pre-execution "would_fit" budget cannot be starved by CPI-hidden allocations. Concretely:
- Either replace/augment the pre-execution static estimate with a conservative worst-case bound per transaction (e.g., clamp every transaction's contribution to `MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION`/`MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` whenever it contains any invocation of a BPF program that is not verifiably free of system-program CPI potential — expensive/impractical statically), or
- After execution, reconcile the `CostTracker`'s `allocated_accounts_data_size` using the *actual* `accounts_resize_delta` from `AccountsDeltas` (already computed in `svm/src/transaction_processor.rs` and used in `runtime/src/bank.rs:4419-4430`) rather than (or in addition to) the pre-execution static estimate, similar to how `CostModel::calculate_cost_for_executed_transaction` already reconciles `loaded_accounts_data_size_cost` using actual execution data.
- Document/clarify that the current comment "eventually, potentially determine account data size of all writable accounts" reflects a known limitation, and prioritize closing it since CPI-based account creation is a common pattern (e.g., PDA creation via CPI), not a rare edge case.

    /// eventually, potentially determine account data size of all writable accounts
    /// at the moment, calculate account data size of account creation
    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
