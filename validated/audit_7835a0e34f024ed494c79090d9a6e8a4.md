## Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats the `shop` value it hands to application webhook handlers as trusted merchant identity, but that value is read straight from an unauthenticated HTTP header. The HMAC signature validated before dispatch only covers the raw request body, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers, so any caller who can reproduce (or replay) a validly-signed body can freely choose which shop the webhook is attributed to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all parsed from HTTP headers that are never part of the signed material: [2](#0-1) 

`HmacValidator.validate` computes the digest over exactly that `to_signable_string` value (the body) using the app's single, shop-independent `Context.api_secret_key`: [3](#0-2) 

`Registry.process` performs this body-only HMAC check and then immediately forwards the unauthenticated `request.shop` header value to the application's registered handler as the trusted tenant identifier: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop acted on by the handler`. Because the secret is shared across every shop that installs the app (it is the app's `client_secret`, not a per-shop secret) and the signature never covers the `shop-domain` header, this binding does not exist — the HMAC only proves "this body was produced with knowledge of the app secret," not "this body originated from shop X." An attacker who has installed the app on their own store receives real, validly-HMAC'd webhook deliveries for their own shop. They can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary victim `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` calls the handler with `shop: request.shop` set to the attacker-chosen victim domain, alongside a `body` fully controlled by the attacker.

### Impact Explanation
Any host application that keys per-tenant logic (access-token lookup, data writes, entitlement changes, mandatory-compliance topics like `customers/redact`/`shop/redact`/`customers/data_request`) off `WebhookMetadata#shop` as populated here is exposed to cross-tenant data injection/confusion: attacker-supplied content processed and attributed to a shop the attacker does not own or control. This crosses a tenant boundary using only the attacker's own legitimate webhook traffic and no leaked credentials, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any merchant that installs the app (an unprivileged actor from the app's perspective) can trivially capture one of their own real webhook deliveries and replay it with a modified `shop-domain` header to the app's public webhook endpoint. No secret material, TLS interception, or social engineering is required — only the ability to install the app once and send an HTTP request with attacker-chosen headers.

### Recommendation
Bind the shop identity into the verified signature material, or otherwise cross-check `request.shop` against an independently authenticated source (e.g., verify the delivery via Shopify's per-shop webhook subscription record, or require that `shop` match a session/access-token already on file that was itself obtained through a verified OAuth/token-exchange flow) before handing it to application handlers. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Install the app on `attacker.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw POST: body `B`, and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's shared secret).
2. Send a new POST to the app's webhook endpoint with the identical body `B` and `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against `H`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches to the registered handler with `shop: "victim.myshopify.com"` and attacker-controlled `body`, causing the host app to process attacker data under the victim tenant's identity.
