Audit Report

## Title
LDAP DN injection in `CreateSession`/`TestPassword` due to filter-escaping (not DN-escaping) of attacker-controlled email - (File: `core/sessions/ldapauth/ldap.go`)

## Summary
The public, unauthenticated `POST /sessions` login endpoint forwards the user-supplied `email` field into `ldapAuthenticator.CreateSession`, which sanitizes it with `ldap.EscapeFilter` before concatenating it into an LDAP Bind DN string. `EscapeFilter` implements RFC 4515 filter escaping (`*`, `(`, `)`, `\`, NUL) and does not escape RFC 4514 DN metacharacters such as `,`, so a crafted email containing a comma changes the RDN structure of the DN string passed to `conn.Bind()`. The same defect is present in `TestPassword`.

## Finding Description
`CreateSession` builds the bind DN as: [1](#0-0) 
using `ldap.EscapeFilter(strings.ToLower(sr.Email))`, which leaves `,` unescaped. Because `,` is the RDN separator in RFC 4514 distinguished names, an attacker-supplied email value such as `victim,ou=someOtherOU` alters the number and structure of RDN components in the final DN handed to `conn.Bind()`, rather than being safely contained within a single `uid=<email>` component. The identical pattern exists in `TestPassword` at [2](#0-1) . By contrast, `FindUser`'s filter construction correctly uses `EscapeFilter` because that value is placed inside a search filter, not a DN: [3](#0-2) . This confirms the escaping-context mismatch: the wrong sanitizer is applied where a DN is being constructed. The endpoint is reachable pre-auth via `sessionsController.CreateSession`, which passes the raw request body straight to `AuthenticationProvider().CreateSession(ctx, sr)`: [4](#0-3) . No authentication middleware or input validation intercepts or rejects DN metacharacters in the email field before this call.

## Impact Explanation
This breaks the security assumption that the Bind DN sent to the upstream LDAP server always resolves to the single, intended `uid=<email>,<usersDN>,<baseDN>` entry. An unauthenticated caller can alter the DN's RDN chain structure, which can be used to probe or redirect authentication targeting within the directory depending on the LDAP server's tree layout and alias/referral handling. This maps to the node API authentication/role-integrity impact category, analogous to the referenced Derby DN-injection advisory. Note that full account impersonation still requires the attacker to supply a password valid for whatever DN the crafted structure resolves to (LDAP bind enforces credential validity at the resolved DN), which bounds the practical severity to authentication-target manipulation/probing rather than an unconditional login bypass.

## Likelihood Explanation
The vector is trivially reachable: any unauthenticated client can POST to `/sessions` with an arbitrary `email` field, no prior session or credentials required. Exploiting it to achieve a concrete unauthorized login additionally depends on directory-specific DN layout and knowledge of a valid password for the resolved target, so likelihood is high for structural manipulation/probing and directory-dependent for full impersonation. This is the same reachable-precondition profile described in the original finding.

## Recommendation
Use a DN-specific escaping function (e.g., `ldap.EscapeDN` in newer `go-ldap` versions, or manual RFC 4514 escaping of `,`, `+`, `"`, `<`, `>`, `;`, `=`, and leading/trailing spaces) wherever attacker-controlled values are concatenated into a bind DN or search base DN — specifically in `CreateSession`, `TestPassword`, and equivalent DN-construction sites in `core/sessions/ldapauth/ldap.go`. Reserve `EscapeFilter` exclusively for values embedded in LDAP search filter expressions, as already correctly done in `FindUser`. As defense in depth, reject emails containing DN metacharacters before they are used in any DN context.

## Proof of Concept
1. Configure `WebServer.AuthenticationMethod = 'ldap'` with `BaseUserAttr = 'uid'`, `UsersDN = 'ou=users'`, `BaseDN = 'dc=example,dc=com'`.
2. Send an unauthenticated request: `POST /sessions` with body `{"email": "victim,ou=someOtherOU,dc=example,dc=com", "password": "guess"}`.
3. Observe that `CreateSession` (core/sessions/ldapauth/ldap.go:407) constructs `searchBaseDN = "uid=victim,ou=someOtherOU,dc=example,dc=com,ou=users,dc=example,dc=com"` instead of the intended single-RDN `uid=<email>,ou=users,dc=example,dc=com`, confirming the comma is not neutralized and the DN structure sent to `conn.Bind()` is attacker-controlled.
4. A Go unit test can mock `LDAPConn.Bind` to assert the exact DN string passed for a crafted email containing `,`, demonstrating the structural injection without needing a live LDAP server.
