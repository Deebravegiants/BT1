Audit Report

## Title
Bridge `OutgoingToken` Credential Exposed to Any Authenticated User via Bridge Read APIs - ([File: core/web/presenters/bridges.go])

## Summary
Chainlink bridges store an `OutgoingToken` used by the node to authenticate itself to external adapters [6](#0-5) . This token is returned in plaintext by the REST `GET /v2/bridge_types` / `GET /v2/bridge_types/:BridgeName` endpoints and the GraphQL `bridges`/`bridge`/`updateBridge` operations, and — unlike write operations on the same resource — these read routes carry no role restriction in `core/web/router.go`, so any authenticated node-API user (including the minimal "View" role) can retrieve it.

## Finding Description
`BridgeType.OutgoingToken` is stored server-side and passed straight through to `presenters.NewBridgeResource`, which always serializes `outgoingToken` with no omission logic [7](#0-6) . The `Index` and `Show` controller handlers call this presenter directly on ORM-fetched bridge records with no additional filtering [3](#0-2) . Critically, `core/web/router.go` registers `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` with only the base `authv2` authentication middleware, while the `POST`/`PATCH`/`DELETE` routes on the same resource are explicitly wrapped in `auth.RequiresEditRole` [1](#0-0) . This asymmetry confirms bridge reads are available to any authenticated principal regardless of role, whereas bridge management requires the Edit role — meaning a lower-privileged user with only read/View access can still retrieve the `OutgoingToken` credential. The GraphQL `Bridge` type mirrors this by hard-coding `outgoingToken: String!` as a non-nullable field returned by `bridges`, `bridge`, and `updateBridge` [5](#0-4) , and the resolver test only requires `authenticated: true` with no role-based restriction demonstrated [8](#0-7) . This contrasts with `IncomingToken`, which the codebase already treats as sensitive: it is populated on the response resource only inside `Create`, and never re-attached in `Index`/`Show`/`Update` [4](#0-3) , demonstrating the code owners already recognize the need to avoid re-exposing bridge secrets on read paths — but failed to apply the same treatment to `OutgoingToken`.

## Impact Explanation
Any authenticated node-API user who only has read-level (View) permissions can enumerate `OutgoingToken` values for every configured bridge via a normal `GET /v2/bridge_types` call or a `bridges { results { outgoingToken } }` GraphQL query. Since this token authenticates the Chainlink node to the external adapter, disclosure lets a low-privileged, non-bridge-managing user impersonate the node when calling that external adapter — a concrete secret-exfiltration / impersonation impact in line with CWE-522, mapping to the in-scope "key/secret exfiltration" impact category.

## Likelihood Explanation
The exploit requires only a normal authenticated session with default/View-level access — no elevated Edit/Admin role, no host or database access, and no special technique. It is trivially reachable via a single unauthenticated-role-gated GET request or GraphQL query, is fully repeatable, and requires no victim interaction.

## Recommendation
Remove `OutgoingToken` from the `Index`/`Show`/GraphQL read responses for bridges. Follow the existing pattern used for `IncomingToken`: only surface it once at creation (or on an explicit, Edit/Admin-role-gated reveal endpoint), and gate the bridge read routes (`GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, and the GraphQL `bridges`/`bridge` resolvers) so that credential fields are redacted for callers without the Edit/Admin role.

## Proof of Concept
1. Create a user with only the View role and authenticate as that user (session cookie or API token).
2. Issue `GET /v2/bridge_types/<name>` — no `auth.RequiresEditRole`/`RequiresAdminRole` wrapper exists on this route in `core/web/router.go` (compare lines 269/271 vs. 270/272/273), so the request succeeds.
3. Observe the JSON:API response includes `"outgoingToken":"<value>"` per the presenter's unconditional field [9](#0-8) .
4. Equivalently, run the GraphQL query `query { bridges { results { id name outgoingToken } } }` with any `authenticated: true` session, as validated by the resolver test fixture returning `outgoingToken` in plaintext [10](#0-9) .

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
