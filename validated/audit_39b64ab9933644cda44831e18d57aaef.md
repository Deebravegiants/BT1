### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw body via HMAC, but the `shop-domain` header — which `Registry.process` trusts as the tenant identity passed to the host app's webhook handler — is excluded from the signed payload.

### Finding Description
The gem's webhook signature verification binds `computed_hmac == request.hmac` to `to_signable_string`, which returns solely `@raw_body`: [1](#0-0) . The HMAC never covers the `shop`, `topic`, `api_version`, or `webhook_id` headers. `Utils::HmacValidator.validate` performs a secure comparison purely against that body string and the app's shared `api_secret_key`: [4](#0-3) .

`Registry.process` uses this validation as the sole authenticity gate, then constructs `WebhookMetadata` using `request.shop`, i.e., the unauthenticated header value, and passes it straight to the app-supplied handler: [3](#0-2) . `WebhookMetadata#shop` is a plain `String` field with no further validation: [5](#0-4) .

Because `api_secret_key` is the app's single client secret shared across every installing merchant, any low-privileged merchant who installs the app can trigger a legitimate webhook to their own endpoint, obtain a body + valid HMAC signature pair, then replay that exact body/HMAC pair to the app's shared webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop domain. The signature check still passes because the shop header was never part of the signed bytes — this breaks the equality `shop identity verified by HMAC == shop identity acted upon by the handler`.

### Impact Explanation
This enables cross-tenant confusion: an attacker-controlled webhook body (still valid JSON with a genuine app-level HMAC) is delivered to the handler tagged with an arbitrary victim `shop` domain. Any app logic that uses `data.shop` to look up sessions, update tenant-scoped state, or make authorized API calls on behalf of "that shop" can be manipulated into acting on the attacker's payload under the victim's identity — a cross-tenant access class issue, matching the report's underlying bug class of "extra/adjacent data not covered by the verified signature being trusted anyway."

### Likelihood Explanation
Any developer who installs the target app on their own store (a normal, unprivileged action) can capture a real signed webhook and immediately has everything needed to forge the shop-domain association, since no additional secret or privilege is required beyond running the app once.

### Recommendation
Include `shop-domain`, `topic`, and `webhook_id` in the signed material verified by `to_signable_string`/`HmacValidator`, or otherwise cryptographically bind the shop header to the signature (e.g., verify the header value returned by Shopify's official webhook signing rather than trusting a client-supplied header unconditionally).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers any subscribed webhook (e.g., `orders/create`) and captures the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent to the app endpoint — this HMAC is valid because it's signed with the app's shared `api_secret_key`, not a per-shop secret.
3. Attacker replays the exact same body + `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` returns `true` because it only checks the raw body against the HMAC [6](#0-5) ; `Registry.process` then invokes the handler with `WebhookMetadata(shop: "victim.myshopify.com", ...)` [7](#0-6) , causing the app to process attacker-controlled data as if it originated from the victim's shop.
