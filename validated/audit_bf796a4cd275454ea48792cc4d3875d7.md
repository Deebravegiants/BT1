### Title
Any unprivileged bandwidth purchaser can grief-evict a victim's paid `Subscription` from another app's FIFO queue, permanently destroying prepaid bandwidth credit - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth`'s `on_accept` credits every inbound `BandwidthPurchaseMsg` to a `(app_chain, app)` FIFO queue keyed entirely by fields chosen by the caller of `purchase()` on `BandwidthManager.sol` — a completely permissionless, unprivileged entry point (any "bandwidth purchaser"). Because the `chain`/`app` pair is attacker-controlled and the FIFO list is capped at `MAX_SUBSCRIPTIONS = 1024` with unconditional oldest-first eviction on overflow, an attacker can pay for the cheapest tier 1024+ times targeting a victim's `(app_chain, app)` bucket to evict the victim's real, still-live, still-funded `Subscription` — destroying bandwidth the victim already paid for, with no way to reverse it except a privileged `force_credit` bail-out from governance. This mirrors the reported analog: an unprivileged, "legitimate-looking" call against shared/queued accounting state desyncs it and corrupts a process that other parties depend on, requiring a privileged party to intervene to restore consistency.

### Finding Description
`purchase()` on `BandwidthManager.sol` is callable by anyone and lets the caller specify an arbitrary `chain` argument independent from the source chain and an arbitrary `app` recipient — this is by design ("Sponsorship"): [1](#0-0) 

On the pallet side, `on_accept` authenticates only that the message came from the registered manager for `request.source` — it performs no check that the caller/payer has any relationship to the `(msg.chain, msg.app)` pair being credited. It then calls `push_subscription`, which is keyed purely by attacker-supplied `app_chain`/`app`: [2](#0-1) 

`push_subscription` appends unconditionally, and once the `(app_chain, app)` list is at the 1024 cap, every further push unconditionally evicts index 0 — the *oldest* entry in FIFO/insertion order — regardless of that entry's remaining bytes, tier, or how much unexpired credit it still holds: [3](#0-2) 

The `MAX_SUBSCRIPTIONS` cap and eviction rule are documented as being sized for pathological repeat-buy behavior, but that framing assumes the app or its own operators are the ones producing the spam. Since `purchase()` is unprivileged and the `(chain, app)` target is entirely attacker-chosen, any third party can target *any other app's* bucket: [4](#0-3) 

The overview docs confirm the intended trust model is only that `request.from` is checked against the registered manager for the *source* chain — nothing gates who the credited `app`/`chain` is, since that's the explicit sponsorship feature: [5](#0-4) 

An attacker who buys 1024 cheap `TierOne` (1-month) subscriptions for the exact victim `(app_chain, app)` pair guarantees that, once the queue is full, the next attacker purchase evicts index 0. If the attacker floods the queue *after* the victim's purchase lands, the victim's subscription — however large or long-lived — becomes index 0 once the preceding entries (attacker's own) are consumed/expired or simply once enough attacker pushes have occurred to rotate it to the front; concretely, an attacker who pushes 1024 entries immediately after a victim's single purchase guarantees the victim's entry is evicted on the 1024th subsequent push (worst case; fewer are needed if any pre-existing entries expire or drain first). Each `TierOne` purchase costs only whatever `tierPrice[1]` governance set (a cheap SKU by design), so the attacker can destroy an arbitrarily large, arbitrarily expensive victim subscription for a bounded, attacker-controlled cost.

This is the same bug class as the referenced report: an unprivileged actor calls a "normal" function (`pushTotalUnderlyingToController` there / `purchase()` here) against a target it has no legitimate business interacting with (an inactive vault / another app's bucket), and the resulting state corruption (extra `underlyingReceived` / evicted `Subscription`) can only be fixed by a privileged party stepping in (`guardian` manually rewriting `underlyingReceived` / governance calling `force_credit` to refund the victim).

### Impact Explanation
The victim's paid-for bandwidth allowance is silently and permanently destroyed (only a `SubscriptionEvicted` event fires — no automatic refund, no protocol-side compensation), which is a direct, quantifiable loss of funds for the victim (they paid the fee token for bytes/duration they can never consume). It also functions as a denial-of-service: the victim's dispatches through `BandwidthGate::try_consume` will subsequently fail with `NoAllowance`/`Insufficient`, blocking their legitimate cross-chain messages until governance manually intervenes with `force_credit`. Given `force_credit` is `AdminOrigin`-gated, recovery is entirely dependent on a privileged actor noticing and acting — exactly the "until guardian steps in" failure mode described in the source report. This satisfies "concrete theft or permanent freezing of funds" at at least Medium severity.

### Likelihood Explanation
The attack requires no privilege whatsoever — only calling the public `purchase()` function repeatedly with the victim's `(app, chain)` pair and paying for the cheapest configured tier each time. The cost is bounded (attacker-controlled number of purchases × cheapest tier price), while the damage scales with however much bandwidth the victim purchased. Any well-resourced or motivated actor (a competitor, a griefer, or someone seeking to disrupt a rival app's cross-chain traffic) can execute this at will; it does not depend on network conditions, timing races, or any special access.

### Recommendation
Do not evict FIFO-blind by insertion order alone. Options:
- Require the evicted entry to be attributable to (or purchased/sponsored by) the same payer/manager as the new push, or otherwise segregate subscriptions by `paid_from` so unrelated payers cannot evict each other's credit.
- Instead of a hard cap with silent eviction, reject the purchase (`revert`/`Error::QueueFull`) when the list is full and expired-only, or scale the cap dynamically, so unrelated parties cannot destroy others' unexpired allowance.
- At minimum, refuse to evict entries that still have `remaining_bytes > 0` and `expires_at > now` unless the pusher is the same `paid_from`/authorized party, forcing griefers to only be able to evict their own stale purchases.

### Proof of Concept
1. Governance configures `TierOne` with a low price and registers `BandwidthManager` for some `source` chain: `set_manager`, `set_tier(TierOne, {bytes, duration_secs})`, `dispatch_set_tiers`.
2. Victim (owner of `app` on `app_chain = "EVM-8453"`) calls `BandwidthManager.purchase(app, TierExpensive, manyMonths, "EVM-8453")`, paying a large sum for a long-lived, large-byte subscription. This lands as `Allowance["EVM-8453"][app][0]`.
3. Attacker, from any chain with a registered manager, calls `purchase(app, TierOne, 1, "EVM-8453")` 1024 times in sequence (or fewer if some pre-existing entries expire/drain first), each time paying only the cheap `TierOne` price and targeting the *same* victim `app`/`chain`.
4. On the 1024th attacker purchase (queue now at `MAX_SUBSCRIPTIONS`), `push_subscription` evicts index 0 — the victim's subscription — emitting `SubscriptionEvicted { app_chain: "EVM-8453", app, tier: TierExpensive, lost_bytes: <victim's full unspent balance> }`.
5. Victim's subsequent dispatches through `BandwidthGate::try_consume` on `"EVM-8453"` for `app` fail with `NoAllowance`/`Insufficient` despite having paid for a large, still-unexpired subscription; the fee token spent by the victim is unrecoverable absent a governance `force_credit` bailout. 		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}

### Purchase messages skip the gate

The router uses `Pallet::is_purchase_message(request)` to identify a purchase from a registered manager (`request.source` is managed _and_ `request.from` matches the registered manager address). Purchase messages bypass the gate — otherwise a depleted app couldn't ever recharge.

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
