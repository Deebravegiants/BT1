Confirmed: `Context.api_secret_key` is a single global app secret shared across every merchant install, set once via `ShopifyAPI::Context.setup` [1](#0-0) , not a per-shop value.

### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body against the app's single, global `api_secret_key`. The `shop` (and `topic`/`webhook_id`) values used to dispatch the webhook to the host application's handler are read directly from HTTP headers that are **not** included in the signed material, so they are never cryptographically bound to the verified payload. Any actor who has legitimately installed the app on their own store (an unprivileged action available to any internet user for a public app) receives real webhooks whose body+HMAC pair is valid under the same global secret used for every other merchant. That valid `(body, hmac)` pair can be replayed against the app's webhook endpoint with the `shop-domain` header changed to an arbitrary victim shop, and it will still pass verification.

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)` and, if it returns true, immediately dispatches to the handler using `request.shop`, `request.topic`, and `request.parsed_body`: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC by calling `verifiable_query.to_signable_string`: [3](#0-2) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body — the `shop`, `topic`, `api_version`, and `webhook_id` values (all pulled from headers) are excluded from what is signed: [4](#0-3) 

Because `Context.api_secret_key` is one static value configured for the whole app (shared by all installed shops) rather than a per-shop secret [1](#0-0) , the equality the code implicitly relies on is:

`HMAC_valid(body, api_secret_key) == true` ⟹ `shop header == true tenant of body`

but the actual guarantee provided by `safeApprove`-style verification here is only:

`HMAC_valid(body, api_secret_key) == true` ⟹ `body was produced by some shop that installed this app`

The `shop` field — used by host applications as the tenant/session key to route webhook data — crosses this boundary unchecked, exactly analogous to the AMO report's pattern of a field (allowance value) being acted upon without the safety property (`safeApprove`'s zero-allowance precondition) actually being enforced for that specific value.

### Impact Explanation
This breaks a tenant-isolation boundary. A malicious but unprivileged actor can:
1. Install the target app on a store they control, becoming a legitimate recipient of real, correctly-signed webhooks for their own shop (this is unprivileged — anyone can install a public embedded Shopify app).
2. Capture a `(raw_body, x-shopify-hmac-sha256)` pair from one of these legitimate webhooks.
3. Replay that exact body and HMAC to the app's public webhook endpoint, substituting the `x-shopify-shop-domain` header with a victim shop's domain.
4. `HmacValidator.validate` still succeeds (it only checks the body against the shared secret), and `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: <victim shop>, body: <attacker-controlled JSON>, ...)`.

Any host application that trusts `request.shop` from `WebhookMetadata` as the tenant identifier (the documented, expected usage pattern) will process attacker-controlled webhook data as if it originated from the victim's store — enabling cross-tenant data injection/corruption (e.g., forged `orders/create`, `app/uninstalled`, or GDPR-relevant webhooks attributed to a shop the attacker doesn't control). This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app that has webhook topics subscribed to more than a trivial handler, since:
- Installing an app to obtain a valid signed webhook requires no privilege beyond having a development/test store.
- The webhook endpoint is, by design, a public unauthenticated HTTP endpoint reachable by any internet user.
- No component in this gem's webhook pipeline ties the header-derived `shop` to the HMAC-verified body, so the replay is trivial once a valid `(body, hmac)` sample is obtained.

### Recommendation
Include the tenant-identifying header (`shop-domain`, and ideally `topic`/`webhook_id`) in the HMAC-signed material, e.g., by having `to_signable_string` compose a canonical string of `shop-domain + topic + raw_body` instead of `raw_body` alone, and validating that composed string in `Registry.process`. Alternatively, cross-check `request.shop` against an independently authenticated session/store record before dispatching to handlers, rather than trusting the header value implicitly.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., updates a product to fire `products/update`). Shopify sends a POST with header `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body B>`, body `B`.
2. Attacker captures `B` and the HMAC value.
3. Attacker sends a new POST to the same webhook endpoint with identical body `B` and identical `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (see `lib/shopify_api/utils/hmac_validator.rb`) verifies successfully because it only checks `B` against `Context.api_secret_key`, which is identical for every shop.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker's body content, even though the victim shop never sent this webhook.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end
