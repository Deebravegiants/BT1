### Title
Missing `chain_id` domain separation in `SignerCapabilityOfferProofChallengeV2` allows cross-network replay of signer-capability delegation — full account takeover ([File: aptos-move/framework/aptos-framework/sources/account/account.move])

### Summary
`account.move` defines two "V2" off-chain challenge structs used to authorize delegation of account authority via a detached Ed25519/MultiEd25519 signature: `RotationCapabilityOfferProofChallengeV2` and `SignerCapabilityOfferProofChallengeV2`. The former was explicitly hardened to include a `chain_id` field "to prevent replaying the challenge message" across networks, but the latter — which grants a *strictly more powerful* capability (a full raw `signer` for the source account, not just key-rotation rights) — was never given the same fix. [1](#0-0) 

### Finding Description
`offer_rotation_capability` builds its challenge with `chain_id: chain_id::get()`: [2](#0-1) 

But `offer_signer_capability` builds `SignerCapabilityOfferProofChallengeV2` with only `sequence_number`, `source_address`, and `recipient_address` — no `chain_id`: [3](#0-2) 

The struct itself confirms the omission: [4](#0-3) 

Signature verification (`verify_signed_message`) only checks the current authentication key and the signature over this under-specified message; it never binds the signature to a network/chain: [5](#0-4) 

Because Aptos accounts derive their address purely from the public key (same key ⇒ same address on every Aptos-based network — mainnet, testnet, devnet, or any forked/rebooted network with equivalent genesis state), and because the only replay-inhibiting field left is `sequence_number` (which is frequently `0` for freshly created accounts), a `SignerCapabilityOfferProofChallengeV2` signature produced by a user on one network can be replayed verbatim by the same or a colluding recipient address on a different network where the source account exists with a matching sequence number. This mirrors the reported EIP-2612 bug exactly: a domain-separator field required to bind a permit-style signature to a specific chain context is missing from one of two structurally similar challenge types, while the sibling type explicitly acknowledges and fixes this exact class of risk.

Root cause: inconsistent domain separation between two structurally-parallel authorization challenges in the same module — one patched with `chain_id`, one not.

### Impact Explanation
`offer_signer_capability` → `create_authorized_signer` grants the recipient a genuine Move `signer` for the source account, i.e., unrestricted custody control equivalent to the private key itself (can move APT/fungible assets, publish/rotate code under the account, rotate keys, control any resource/object owned by that account). This is a strictly higher-privilege capability than the rotation capability that Aptos developers already recognized needed chain-binding. A replayed/leaked signer-capability-offer signature therefore enables full, unrecoverable takeover of account-held assets and control on a network the owner never intended to authorize — satisfying "unauthorized takeover of ... resource-account control ... tied to live assets" and "theft ... of APT, fungible assets, token objects."

### Likelihood Explanation
Exploitation requires: (1) the victim to have signed a `SignerCapabilityOfferProofChallengeV2` message off-chain at some point (a documented, supported CLI/SDK flow), and (2) the victim's account to exist with the same `sequence_number` on a second Aptos-compatible network sharing the same address (e.g., a devnet/testnet reset, a permissioned/appchain deployment forked from mainnet state, or genesis-cloned test networks) where the same or a colluding recipient address also exists. This is a realistic and previously-acknowledged threat model within this exact module (as shown by the `chain_id` fix applied to the sibling rotation-capability struct), making likelihood moderate-to-high in multi-network Aptos deployments rather than purely theoretical.

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2` (and correspondingly update `offer_signer_capability` to populate it via `chain_id::get()`), matching the mitigation already applied to `RotationCapabilityOfferProofChallengeV2`. Because this changes the signed message format, it requires a coordinated framework upgrade with a version bump/migration path (and off-chain SDK/CLI updates) rather than a silent in-place change.

### Proof of Concept
1. Alice creates account `A` on Network 1 (e.g. testnet) and Network 2 (e.g. a forked/rebooted network sharing the same genesis derivation), both at `sequence_number = 0`, using the same key pair (same address on both networks, as Aptos addresses are key-derived).
2. Alice signs a `SignerCapabilityOfferProofChallengeV2{ sequence_number: 0, source_address: A, recipient_address: Bob }` intending to delegate signer capability to Bob only on Network 1, via the documented flow in [6](#0-5) .
3. Bob (or an attacker who intercepts the signature) submits the identical `signature`, `account_scheme`, `account_public_key_bytes` to `offer_signer_capability` on Network 2, where `A` also exists at `sequence_number = 0`.
4. `verify_signed_message` succeeds because the message bytes (lacking `chain_id`) and Alice's public key are identical on both networks; `account_resource.signer_capability_offer.for` is set to Bob on Network 2 without Alice's consent for that network.
5. Bob calls `create_authorized_signer(&bob, A)` on Network 2 and obtains a full `signer` for Alice's account there, enabling unrestricted asset transfer/control — confirmed by the capability-consumption path shown in test usage at [7](#0-6) .

Note: I was not able to independently confirm within the index whether any two live Aptos networks actually share identical genesis/account state today (this depends on deployment/ops practices outside this repo, e.g. testnet resets or private forks), so real-world exploitability depends on that operational condition; the code-level absence of `chain_id` domain separation itself is confirmed directly from the source.

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
