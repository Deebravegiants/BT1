### Title
Unprivileged counterparty can permanently DoS `staking_contract::distribute`, freezing already-unlocked stake for the other party - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`distribute_internal` (invoked by the public entry function `distribute`, and internally by `request_commission`, `unlock_stake`, `switch_operator`, and `update_commission`) drains all withdrawable stake from a shared `distribution_pool` and pays out **every** shareholder (staker and operator/beneficiary) in a single, atomic loop. Because `aptos_account::deposit_coins` will abort if the target account has not registered a `CoinStore<AptosCoin>` and has opted out of direct coin transfers, either counterparty of a staking contract can make this shared payout loop abort forever — permanently freezing the other party's already-unlocked funds inside the staking-contract's resource-account-controlled stake pool. This is the same bug class as the external report: a shared/batch state-transition function that must never permanently fail is gated behind a per-entity precondition that an unprivileged party fully controls.

### Finding Description
`distribute_internal` withdraws all inactive/pending_inactive stake and pays every shareholder recorded in `staking_contract.distribution_pool` in one loop: [1](#0-0) 

Each iteration calls `aptos_account::deposit_coins(recipient, ...)` for `recipients[0]`, redeeming and removing that shareholder's entry only *after* a successful deposit. `deposit_coins` will abort with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient's `CoinStore<AptosCoin>` does not exist and `can_receive_direct_coin_transfers` is false for that address: [2](#0-1) 

A staking contract's `distribution_pool` only ever contains two possible recipients: the staker and the operator (or the operator's beneficiary, via `beneficiary_for_operator`). Since Move transactions are atomic, if `deposit_coins` aborts for either party while it is processed at `recipients[0]`, the **entire** `distribute()` call reverts — nothing is paid out, and the pool's shareholder state is unchanged. Because that same shareholder is deterministically re-selected as `recipients[0]` on every subsequent call, this failure repeats forever: neither party can ever again withdraw stake through `distribute()`, `request_commission()`, `unlock_stake()`, `switch_operator()`, or `update_commission()`, since all of them invoke `distribute_internal()` first (e.g. `unlock_stake` at line 691, `request_commission` at line 625).

The precondition that triggers the permanent abort (an un-registered `CoinStore<AptosCoin>` combined with `allow_arbitrary_coin_transfers = false`) is entirely unprivileged and self-inflicted: any account (the operator, or an operator-controlled beneficiary set via `set_beneficiary_for_operator`) can configure itself this way before ever having received a payout, then continue to earn commission normally while permanently blocking the staker's principal/reward withdrawals (and vice versa — a staker could do the same to block the operator's commission).

### Impact Explanation
This breaks the custody invariant that funds unlocked from a resource-account-controlled stake pool must remain recoverable by their rightful owner. Once poisoned, the staker's (or operator's) already-unlocked stake becomes permanently non-withdrawable through the module's only payout path — a **permanent lock of resource-account-held value** with no on-chain recovery mechanism (there is no per-shareholder distribute or admin override). This matches the report's custody-impact criterion for "permanent lock or non-recoverable loss of ... resource-account-held value," warranting a High severity rating, since real staker funds (potentially the bulk of the reward/principal amounts under management) can be frozen indefinitely by an adversarial counterparty.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires one counterparty to intentionally configure a plain, no-cost account state (never registering `CoinStore<AptosCoin>` and calling `set_allow_direct_coin_transfers(false)`, or pointing `beneficiary_for_operator` at such an account) before the staking relationship begins earning distributable balances. This requires deliberate action but no special privilege, no race condition, and no cost beyond ordinary transaction fees, making it fully within reach of a malicious operator or staker who wants to grief the other side (e.g., an operator refusing to let a staker exit, or vice versa).

### Recommendation
- In `distribute_internal`, isolate per-recipient payout failures so that one poisoned recipient cannot block the entire loop — e.g., wrap each `aptos_account::deposit_coins` call so a failure diverts that recipient's share to a separate, individually-claimable "pending withdrawal" resource rather than aborting the whole distribution.
- Alternatively, use a lower-level deposit path that force-creates/registers the recipient's `CoinStore` (bypassing the opt-out check) for `distribute`-style flows, since these are protocol-level unlocks rather than arbitrary/unsolicited transfers.
- Add a view/guard so that when a shareholder is known to be unable to receive funds, an admin or the shareholder itself can register/opt-in before more funds accumulate, and ensure `distribute()` cannot process other shareholders' funds contingent on that one recipient succeeding.

### Proof of Concept
1. Operator O creates (or points `beneficiary_for_operator` to) address B, which has never registered `CoinStore<AptosCoin>`, and calls `aptos_account::set_allow_direct_coin_transfers(B_signer, false)`.
2. Staker S creates a staking contract with operator O via `staking_contract::create_staking_contract`, deposits stake, and O joins the validator set.
3. Time passes; the stake pool earns rewards. S calls `unlock_stake` to unlock part of the stake; this internally calls `distribute_internal` then `request_commission_internal`, adding both S and (B via O's commission) as shareholders in `distribution_pool`.
4. After the stake pool's lockup expires (stake becomes inactive/pending_inactive and thus withdrawable), anyone calls `staking_contract::distribute(S, O)`.
5. `distribute_internal` reaches B (operator's beneficiary) in the shareholder loop and calls `aptos_account::deposit_coins(B, ...)`, which aborts because B has no `CoinStore<AptosCoin>` and disallows direct transfers.
6. The entire `distribute` transaction reverts. S's unlocked stake (and O's commission) remain trapped in the `distribution_pool`/stake pool forever, since every future call to `distribute`, `unlock_stake`, `request_commission`, `switch_operator`, or `update_commission` re-triggers the same abort at the same shareholder entry.
