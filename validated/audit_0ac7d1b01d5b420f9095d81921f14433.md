## Finding

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) fields are not covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` field that the library hands to application webhook handlers as the tenant identifier is taken from an unsigned HTTP header. Anyone holding one valid `(raw_body, hmac)` pair (e.g. a merchant who has the app installed on their own store and can observe the webhooks Shopify sends them) can replay that exact body/HMAC pair while substituting a different `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` still succeeds because it never looks at the shop header, so `Webhooks::Registry.process` invokes the handler with an attacker-chosen `shop`, breaking the binding between the authenticated bytes and the tenant identity that consuming apps rely on.

### Finding Description
`Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC purely against `to_signable_string` (i.e. the raw body): [3](#0-2) 

`Webhooks::Registry.process` trusts `request.shop` as the tenant identity and forwards it straight to the application handler after the HMAC check passes: [4](#0-3) 

The equality the library is supposed to enforce is:
`shop_bound_by_hmac == shop_delivered_to_handler`

but in reality it is:
`shop_bound_by_hmac == "" (not present in signable string)`, while `shop_delivered_to_handler == header_value` (fully attacker-controllable once a valid raw_body/hmac pair for *any* shop is known).

Because the header value is never part of the signed content, an unprivileged actor who has legitimately received (or otherwise obtained) one valid `raw_body` + `X-Shopify-Hmac-Sha256` pair — for example a merchant/developer that installed the app on their own store and can see the webhook Shopify sends them — can resend that identical body and HMAC to the app's webhook endpoint while changing only `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-Api-Version`) to point at a different shop. `HmacValidator.validate` still returns `true`, and `WebhookMetadata` is built with the forged `shop`, so any host application logic keyed off `request.shop`/`data.shop` (e.g. "look up the session/tenant for this shop and update its records") is deceived into acting on behalf of a shop the attacker doesn't own.

### Impact Explanation
This is a cross-tenant access vector: the gem hands application code a `shop` value it presents as authenticated (it passed HMAC verification) but which is not actually bound to the signed bytes. Any consuming app that uses `WebhookMetadata#shop` to select which merchant's data/session to act on can be manipulated into performing actions against the wrong tenant using a replayed, still-valid-looking webhook. This matches the "cross-tenant access" Critical impact category since it lets one merchant's webhook data be attributed to another shop.

### Likelihood Explanation
Exploitation requires only one legitimately-observed `(raw_body, hmac)` pair, which any developer/merchant who installs the app on their own store can obtain from Shopify's real webhook deliveries. No access to `api_secret_key`, access tokens, or any privileged account is needed — only the ability to send an HTTP request to the app's public webhook endpoint with a substituted header, which is available to any unprivileged internet user with network access to that endpoint.

### Recommendation
Include `shop` (and ideally `topic`/`api_version`/`webhook_id`) in the HMAC-signed content, or otherwise cryptographically bind the shop-domain header to the signature (e.g., verify shop domain against a value derived from a per-shop secret/session rather than a bare header), so `to_signable_string` cannot be satisfied by replaying a body signed for one shop under a different shop's identity.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and capture a real webhook delivery Shopify sends to the app's endpoint, e.g.:
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - body: `{"id":1,...}`
2. Replay the exact same body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `victim-shop.myshopify.com` as `shop`; `Utils::HmacValidator.validate` recomputes HMAC over the (unchanged) raw body and it matches, so `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process the attacker's forged webhook as if it came from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
