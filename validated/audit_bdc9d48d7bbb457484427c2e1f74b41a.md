### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface, whose contract requires `hmac` and `to_signable_string` to represent the data being authenticated. For OAuth callbacks (`ShopifyAPI::Auth::Oauth::AuthQuery`), `to_signable_string` binds every field that is later acted upon (`code`, `host`, `shop`, `state`, `timestamp`). For webhooks, however, `to_signable_string` returns only the raw request body, while the `shop` and `topic` values — read from HTTP headers — are used by `ShopifyAPI::Webhooks::Registry.process` to dispatch the payload to a handler as tenant-identifying data, without ever being included in the HMAC computation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

while `shop` and `topic` are simply read from headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` against the HMAC, i.e. only the body content is authenticated: [3](#0-2) 

`Registry.process` accepts the request once the (body-only) HMAC check passes, then forwards the **unauthenticated** `request.shop` and `request.topic` values straight to the handler as trusted tenant/event identity: [4](#0-3) 

This is exactly the class of bug described in the external report: an interface (`VerifiableQuery`) is implemented inconsistently across two contracts (`AuthQuery` binds all identity fields it depends on; `Webhooks::Request` does not), breaking the invariant `bytes verified == bytes acted upon`. Because Shopify apps share one `api_secret_key` across every installed shop, any merchant that has installed the app can:
1. Receive a legitimate webhook delivery for their own shop (a valid `hmac-sha256` header computed over the body they control/receive).
2. Replay that exact body + HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header to name a **different** shop.
3. `HmacValidator.validate` still succeeds (it only checks the body), so `Registry.process` calls the handler with `WebhookMetadata` claiming the forged shop/topic, even though that shop never sent this data.

An app that uses `data.shop` from `WebhookMetadata` to look up/create/update per-tenant records (the documented and expected usage pattern) can be tricked into associating attacker-supplied data with an unrelated victim shop — a cross-tenant integrity/access violation using only a legitimate low-privilege installation.

### Impact Explanation
This breaks the tenant isolation boundary the gem is supposed to enforce for webhook delivery. A single unprivileged app-installer (attacker with an ordinary Shopify store) can inject payloads that the host application will process on behalf of a shop it does not control, since the multi-tenant identity field (`shop`) has no cryptographic binding to the payload's signature. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any merchant that installs the app can register a webhook subscription in their own shop and observe body+HMAC pairs delivered to their own endpoint (or an endpoint they control), then replay them against the vulnerable app's public webhook URL with a modified shop header. No access to `api_secret_key`, tokens, or the target shop is required — only ordinary use of the app as an unprivileged internet user/merchant.

### Recommendation
Include the shop domain (and topic, if relied upon for dispatch) in the value that is HMAC-verified, or independently verify that the shop header corresponds to a shop for which this delivery is expected (e.g., cross-check against an active session/webhook registration id, and treat `shop`/`topic` headers as untrusted until bound to the signed payload). At minimum, document that `WebhookMetadata#shop`/`#topic` are not authenticated and must not be used as sole tenant identifiers without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`) pointed at an endpoint they control.
2. Shopify delivers a webhook to the attacker with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some JSON body.
3. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` value to the app's real webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, `Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) body, and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: <attacker-controlled>)`, causing the app to act on `victim-shop`'s tenant data using attacker-supplied content.
