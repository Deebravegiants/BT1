### Title
Webhook `shop` (and other) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from an HTTP header, while the HMAC signature that authenticates the request only covers the raw request body. Because the body and the shop-identifying header are verified independently — one cryptographically, one not at all — an attacker who possesses one legitimately-signed webhook payload (e.g., a webhook delivered by Shopify to their own installed shop) can replay that exact body/HMAC pair while substituting the `shop-domain` header for a victim shop, and the library will accept it as authentic and pass the victim's shop identity to the app's webhook handler together with attacker-controlled body content.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` is defined to return only the raw HTTP body: [2](#0-1) 

However, the `shop` (and `topic`, `api_version`, `webhook_id`) values used by the rest of the library — including the value handed to the app's webhook handler as the tenant identity — are read directly from HTTP headers, which are entirely outside the HMAC-protected content: [3](#0-2) [4](#0-3) 

`Webhooks::Registry.process` validates only the body's HMAC and then forwards `request.shop` — the unauthenticated header value — straight to the app-defined handler as the webhook's shop/tenant identity: [5](#0-4) 

The identity binding that should hold is: **the shop asserted to the handler == the shop the HMAC-authenticated body was actually generated for**. Because `shop` is never folded into `to_signable_string`, this equality is never checked. The gem authenticates *that the body bytes are unmodified and secret-derived*, but not *which shop the request claims to be from*. Any actor capable of obtaining one valid `(raw_body, hmac)` pair (trivial — every shop that installs the app receives real, validly-signed webhooks to its own endpoint) can resend that identical body/HMAC pair to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` will report success because it never inspected the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim's shop while carrying attacker-chosen body content.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook delivery: cross-tenant data can be injected into another merchant's webhook processing pipeline using only a webhook payload the attacker legitimately received for their own shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up the session/store record to update), this can lead to data corruption or spoofed events being attributed to a shop the attacker doesn't control — a cross-tenant confusion vulnerability, which the assessment scope classifies as Critical (cross-tenant access).

### Likelihood Explanation
Any developer/merchant who has installed the app receives genuine webhook deliveries containing a valid raw body and `X-Shopify-Hmac-Sha256` value for their own shop. Capturing and replaying that request with a modified `shop-domain` header requires no secret material, no privileged access, and no interaction with Shopify's servers beyond normal app usage — it is exploitable by any unprivileged internet user who can install the app (or intercept/log a delivered webhook to their own endpoint) and send an HTTP request to the app's public webhook endpoint.

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values in the data that is HMAC-verified, or otherwise cryptographically bind them to the body before trusting them. Since Shopify's webhook HMAC scheme signs only the raw body, the safest fix is for `ShopifyAPI::Webhooks::Request` to require the app to independently authenticate/authorize the asserted `shop` (e.g., cross-check against a shop that is expected to receive this specific webhook, or validate that the shop domain is one with an active session/registration before acting on the payload) rather than trusting the header as if it were signed.

### Proof of Concept
1. Install the app on attacker-controlled shop `evil.myshopify.com`; trigger any webhook (e.g., `orders/create`) so Shopify delivers a real request to the app's webhook endpoint with headers `X-Shopify-Shop-Domain: evil.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some JSON body `B`.
2. Capture the exact `raw_body = B` and `hmac` value from that request.
3. Resend an HTTP POST to the same webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body as usual; `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks `raw_body`, which is unchanged.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: B, ...)`, causing the app to process attacker-controlled body `B` as though it were a legitimate webhook from `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
