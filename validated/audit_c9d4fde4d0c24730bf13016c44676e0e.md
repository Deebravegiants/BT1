Found it: `Webhooks::Request#shop` is read from the `X-Shopify-Shop-Domain` header, but `to_signable_string` (the bytes actually verified by HMAC) is only the raw request body [1](#0-0) . The shop identity used by the host app to route/tenant-scope the webhook is never part of the signed bytes.

### Title
Webhook shop-domain identity spoofing via HMAC/parsed-field mismatch in `Webhooks::Request` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies an inbound webhook's authenticity using `hmac` (parsed from the `X-Shopify-Hmac-Sha256` header) validated against `to_signable_string`, which returns only `@raw_body` [2](#0-1) . The `shop` accessor, used by host applications to determine which merchant/tenant the webhook belongs to, is read directly from the unsigned `X-Shopify-Shop-Domain` header [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop header value == shop bound inside the HMAC-signed payload`. Instead the gem enforces only `HMAC(raw_body) == received_hmac`; the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are read via `shopify_header` and returned by dedicated accessors [4](#0-3) , but none of these headers are included in `to_signable_string`. The class's own `hmac` method reflects this: it derives the signature strictly from the `hmac-sha256` header and the body [5](#0-4) , meaning the value that `AbstractWebhookHandler`/host callers use to key `shop` is verified against a completely disjoint set of bytes than what carries the tenant identity.

Because Shopify computes the HMAC over the raw JSON body with the app's `client_secret`, a signature that is valid for a given body remains valid regardless of what `shop-domain` header accompanies it. Any party capable of relaying (not necessarily forging) a legitimately-signed webhook payload — e.g., a merchant replaying their own previously-received, validly-signed webhook to an app that services multiple shops, or a network intermediary — can attach an arbitrary `X-Shopify-Shop-Domain` header while keeping the original valid HMAC and body untouched. `Request` will report `hmac` as valid via `Utils::HmacValidator`-style verification (`OpenSSL.secure_compare` against `to_signable_string`, i.e. body-only) while `shop` returns the attacker-controlled header value.

### Impact Explanation
Host applications built on this gem are documented to key session/data lookups by `request.shop` after confirming HMAC validity, since the class provides no other way to bind webhook payload to tenant. If an attacker can present a validly-signed body under a different `shop-domain` header, the application will attribute that webhook's data (order, customer, inventory events, etc.) to the wrong merchant/tenant — a cross-tenant data-integrity issue. This matches the report's underlying bug class (front-running/binding failure: "a field acted on but not covered by the HMAC") mapped onto this gem's webhook verification surface. It does not itself leak a token or secret, but it breaks the tenant boundary that the gem is expected to enforce for webhook shop attribution, which is the closest reachable, in-scope analog to a cross-tenant access issue.

### Likelihood Explanation
Exploitability depends on an attacker's ability to relay/replay a validly-signed webhook body with a different `shop-domain` header to the app's webhook endpoint. This does not require the `client_secret` or any credential — only a previously observed, validly-signed webhook (which by design is delivered over plain HTTP to the app's public webhook URL and is not scoped to a single recipient by the signature). This is realistic in multi-tenant apps that share one webhook endpoint for all shops, which is the common integration pattern the gem's `Webhooks::Registry`/`Request` API is built for.

### Recommendation
Bind the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values into the signed payload verification, or otherwise cryptographically tie the shop identity to the signature — e.g., have `to_signable_string` incorporate the shop domain alongside the raw body, or require host apps to independently corroborate `shop` against a value obtained through an authenticated channel (such as the session/offline access token already on file for that shop) before trusting `request.shop` for tenant routing. At minimum, document that `shop` is unauthenticated and must not be used as the sole tenant key.

### Proof of Concept
1. Register a webhook and capture one legitimate, validly-signed delivery: headers include `X-Shopify-Hmac-Sha256: <valid-hmac>`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`, and body `B`.
2. Replay the exact same body `B` and the same `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but substitute `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. Construct `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: replayed_headers)`.
4. `Utils::HmacValidator.validate(request)` (or equivalent HMAC check using `request.hmac` / `request.to_signable_string`) returns `true`, because verification only checks `HMAC(secret, B) == received_hmac`, which is unchanged.
5. `request.shop` returns `"shop-b.myshopify.com"` [3](#0-2)  — the host app processes shop-a's data under shop-b's tenant context, despite HMAC validation succeeding.
