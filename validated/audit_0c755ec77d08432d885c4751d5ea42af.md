### Title
Decimal-scaling function silently mis-scales cross-chain transfer amounts when local asset decimals exceed the registered EVM decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `pallet-hyper-fungible-token` bridge converts amounts between an EVM contract's ERC20 decimals and the local Substrate asset's decimals using `convert_to_erc20` / `convert_to_balance` in [1](#0-0) . Like Futureswap's `DecimalPaddingToken`, this is a decimal-normalization boundary where fewer/more decimals must be scaled correctly in both directions; getting the direction wrong causes either dust loss or, more seriously, silent amount corruption.

### Finding Description
`convert_to_erc20` is documented to "multiply by `10^(erc_decimals - local_decimals)`" to scale a local balance up to ERC20 precision: [2](#0-1) 

It computes the exponent with `erc_decimals.saturating_sub(local_decimals)`. This only behaves correctly when `erc_decimals >= local_decimals` (the case documented and tested for `BridgeToken`, where nexus is 12 decimals and the EVM side is the ERC20-default 18 decimals — see [3](#0-2) ). When a registered pair instead has `local_decimals > erc_decimals` (a legitimate, non-malicious registration — e.g. a locally-issued asset configured with higher precision than the fixed 18-decimal `HyperFungibleToken` contract on the destination, or any local asset with >18 decimals as already exercised for other decimal-aware components in this codebase, cf. `VWAPOracleTest.sol`'s 24-decimal token tests), `saturating_sub` clamps to `0`, so the exponent becomes `10^0 = 1` and **no down-scaling occurs at all**. The function silently returns `value` unchanged even though the destination side expects units already normalized to the (smaller) `erc_decimals` precision.

This is invoked from `Pallet::send` in the ISMP dispatch path reachable by any signed extrinsic call: [4](#0-3) 

The counterpart, `convert_to_balance`, used on `on_accept`/`on_timeout` (also reachable via a relayed message delivery) has the analogous asymmetry in the opposite direction: it always divides, which is correct when `erc_decimals >= local_decimals` but truncates/loses precision silently — the counterpart of the reported Futureswap withdrawal bug — when receiving amounts that don't divide evenly, with no accounting for or return of the truncated remainder: [5](#0-4) 

Neither function validates that `erc_decimals >= local_decimals` (or vice versa) before choosing to multiply/divide; both simply assume one fixed ordering the entire pallet is built around, with no `checked_sub` or explicit revert/branch for the other case.

### Impact Explanation
If a token pair is configured (via `register_token`, an ordinary — not malicious — administrative action, or simply an asset that legitimately carries higher local decimal precision than the peer's fixed 18-decimal ERC20 contract) with `local_decimals > erc_decimals`, every `send()` silently emits a `Message.amount` that is orders of magnitude too large relative to what the destination expects (the code fails to divide down as it should). Depending on how the destination `HyperFungibleToken` mints tokens (verbatim from `message.amount`), this results in wildly over-minted, unbacked tokens on the destination chain, or otherwise an amount mismatch between the escrowed/burned local balance and what is credited remotely — a form of unbacked mint / fund mismatch. In the reverse direction (`convert_to_balance`), the systematic truncation of amounts below the local unit permanently drops the remainder with no refund path, i.e., a (dust-scale) permanent loss of value on every affected transfer.

### Likelihood Explanation
Triggering the severe (multiplication) direction requires a token registration where the local asset's decimals exceed the destination's registered `erc_decimals` — plausible for any non-native asset issued with higher-than-18 decimal precision, or any misconfigured-but-benign pairing, and is not gated by any additional check in `send()` beyond looking up `Precisions`. Once such a pair exists, any ordinary user calling `send()` triggers the bug on every transfer, requiring no special privilege beyond a normal signed extrinsic.

### Recommendation
Replace the one-directional `saturating_sub`-based scaling in `convert_to_erc20` and `convert_to_balance` with logic that explicitly branches on which side has more decimals (multiply when scaling up, divide when scaling down) — mirroring the correct pattern already implemented in `VWAPOracle::_normalizeAmount` ( [6](#0-5) ) — and add either a hard invariant check in `register_token`/`update_token` enforcing a supported decimal ordering, or full bidirectional scaling support with defined rounding/remainder handling (and remainder accounting, so no value is silently destroyed).

### Proof of Concept
1. Governance (non-maliciously) registers a non-native asset `X` with `local_decimals = 24` and configures `Precisions::<T>::get(X, dest) = 18` for a `HyperFungibleToken` destination (whose `decimals()` is the fixed ERC20 default of 18, per `BridgeToken.sol`'s own documented convention).
2. A user calls `send(params)` with `params.amount = 1_000_000` (1 unit at 24-decimal precision, `1e-18` of a whole token) and `asset_id = X`.
3. In `Pallet::send`, `decimals = 24`, `erc_decimals = 18`, so `convert_to_erc20(1_000_000, 18, 24)` computes `saturating_sub(18, 24) = 0`, multiplier `= 10^0 = 1`, and returns `erc20_amount = 1_000_000` unchanged — instead of the correct `1_000_000 / 10^6 = 1` (in 18-decimal terms).
4. The dispatched `Message.amount = 1_000_000` (interpreted by the destination `HyperFungibleToken` as `1_000_000 * 1e-18` tokens is actually fine numerically here, but the real corruption manifests whenever the true intended amount should have been divided down — e.g., sending `params.amount = 10^24` (1 whole token at 24 decimals) yields `erc20_amount = 10^24` verbatim instead of the correct `10^18` (1 whole token at 18 decimals) — a 10^6x amount inflation reaching the destination mint call.

**Note:** I was not able to independently confirm whether `HyperFungibleToken.sol`'s `decimals()` is strictly hardcoded to 18 with no override path, nor whether `register_token` enforces `erc_decimals >= local_decimals` elsewhere in validation logic not surfaced by search — verifying these would require reading the full `register_token` extrinsic and `HyperFungibleToken.sol` constructor, which were not fully retrieved in this session.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}

    function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
    }
