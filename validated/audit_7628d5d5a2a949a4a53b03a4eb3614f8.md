### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop spoofing / cross-tenant webhook impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts the `shop` value taken from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header as the tenant identity for a webhook, but `HmacValidator.validate` only verifies the raw request body against the HMAC — the shop header is never part of the signed material. An attacker who can obtain any single validly-signed webhook body/HMAC pair (e.g. from their own shop where the app is legitimately installed) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary victim shop domain in the header, and the signature check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` (and `topic`, `api_version`, `webhook_id`) are pulled straight from unauthenticated headers: [2](#0-1) 

`HmacValidator.validate_signature` computes the signature purely over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the received HMAC: [3](#0-2) 

`Registry.process` then does nothing more than check this body-only HMAC before handing `request.shop` straight to the caller's handler as the authoritative tenant identity: [4](#0-3) 

Because the `api_secret_key` used for HMAC computation is a single shared per-app secret (not per-shop), any body+HMAC pair that is valid for one shop's webhook is *also* valid for the same body posted with a different `shop-domain` header — the header is never part of what is authenticated. This breaks the intended identity binding: **shop header trusted by the handler == shop actually authenticated by the HMAC**, which does not hold, since the HMAC authenticates only the body.

### Impact Explanation
This is a cross-tenant identity confusion at the point where the gem exposes webhook data to the consuming application: `WebhookMetadata.shop` (built entirely from unauthenticated header input) is delivered to the app's handler as if it were a verified fact. Any consuming app that keys per-shop actions (token revocation on `app/uninstalled`, data deletion on `shop/redact`/`customers/redact`, order/customer processing, etc.) off `WebhookMetadata#shop` can be made to act against a victim shop's tenant record using a payload that was never actually sent by Shopify for that shop. This matches the "Critical – cross-tenant access" impact category, since it lets an attacker who legitimately controls one shop (or intercepts one valid webhook) impersonate webhook traffic for an arbitrary victim shop.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint plus one legitimately-obtained (body, HMAC) pair — trivially obtainable by any developer who installs the target app on their own store, since HMAC never binds to shop identity. No access token, `client_secret`, or privileged access is needed.

### Recommendation
Bind the shop identity into the authenticated material, e.g., include the `shop-domain` header (and ideally `topic`/`webhook-id`) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived shop to the payload before `Registry.process` exposes it to handlers as trusted `WebhookMetadata`.

### Proof of Concept
1. Install/receive a legitimate webhook for shop A: capture `raw_body` and the `x-shopify-hmac-sha256` header (both valid, produced by Shopify using the app's shared `api_secret_key`).
2. POST the identical `raw_body` and identical `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `raw_body` against the HMAC.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to act on shop A's payload as if it belonged to the victim shop.
