### Title
Supply-trigger graduation with near-zero real LT raised can permanently brick `finalizeGraduation` via UniswapV2 `MINIMUM_LIQUIDITY` revert - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._prepareGraduationLiquidity` and `_seedDirectMint` compute and deposit `(tokensForLP, ltFromPair)` into a freshly-created HyperSwap V2 pair via `pair.mint(lpLock)`. A real UniswapV2-style pair (mirrored faithfully by the project's own `MockHyperswapPair.mint`) requires `sqrt(amount0 * amount1) > MINIMUM_LIQUIDITY (1000)` on the first mint, else it reverts with `INSUFFICIENT_LIQUIDITY_MINTED`. Neither `_prepareGraduationLiquidity` nor `_seedDirectMint`/`_seedUniswapV2Direct` guards against `tokensForLP` or `ltFromPair` being small enough that this product falls at or below `MINIMUM_LIQUIDITY`. This is analogous to CVE-2019-12974's class of bug: an unguarded edge case (a "null"/degenerate value that a low-level dependency call chokes on) causes a deterministic, unrecoverable revert in a code path that is documented as needing to "never revert under any pre-seed shape."

### Finding Description
The dual graduation trigger fires on whichever condition is met first — either the USD threshold, or `IPair(pair).tokenBalance() == 0` (the supply trigger), documented at `Bonding.canGraduate` [1](#0-0) . The supply trigger is designed explicitly to handle "flat/bear markets where $9K is never reached," meaning it can fire while very little LT has actually been raised by the curve — bounded below only by the mandatory `$20` seed buy (`Zap.MIN_SEED_USDC`).

At phase 1, `_prepareGraduationLiquidity` computes:
```
ltFromPair = assetReserve - virtualLtReserve
tokensForLP = (ltFromPair * tokenReserve) / assetReserve   // capped at LP_RESERVE
``` [2](#0-1) 

Both values are derived from the real (small) amount of LT raised by the curve. If a token's curve trading stays extremely thin (near the `$20` minimum seed, no further buys) and reaches graduation purely via the supply trigger, `ltFromPair` and the correspondingly-scaled `tokensForLP` can be pushed low enough — depending on the LT's decimals/price and the token's price path — that `sqrt(tokensForLP * ltFromPair) <= 1000`.

At phase 2, `finalizeGraduation` calls `_seedUniswapV2Direct` → (Regime 1, `totalSupply() == 0`) → `_seedDirectMint`, which transfers `tokensForLP`/`ltFromPair` to the pair and calls `pair.mint(lpLock)` unconditionally, with no minimum-liquidity precheck:
```solidity
function _seedDirectMint(...) internal returns (uint256 liquidity) {
    IERC20(tokenAddress).safeTransfer(pair, tokensForLP);
    IERC20(lt).safeTransfer(pair, ltFromPair);
    liquidity = IUniswapV2Pair(pair).mint(_s().lpLock);
    ...
}
``` [3](#0-2) 

The project's own faithful mock of the real V2 pair enforces exactly this UniswapV2 semantics and demonstrates the revert path that would occur on the real HyperSwap V2 pair:
```solidity
if (totalSupply_ == 0) {
    liquidity = _sqrt(amount0 * amount1) - MINIMUM_LIQUIDITY;
    _mint(DEAD, MINIMUM_LIQUIDITY);
} ...
require(liquidity > 0, "MockPair: INSUFFICIENT_LIQUIDITY_MINTED");
``` [4](#0-3) 

Note `_sqrt(amount0*amount1) - MINIMUM_LIQUIDITY` even underflows/reverts with a panic if the sqrt result is below 1000, compounding the failure mode. This is distinct from the hostile-pre-seed defense (Regimes 2/3), which is explicitly documented and tested against attacker-controlled dust seeding — the failure here is triggered by the protocol's *own* honest-path numbers being too small, a case the "brick resistance" documentation and tests (`test_brick_resistance_frontRun_dust_seed`, etc.) do not appear to cover.

Once `pair.mint` reverts, the entire `finalizeGraduation` transaction reverts. Because `_enterGraduating` already flipped `lifecycle` to `Graduating` and froze trading in a prior, already-committed transaction (phase 1 is inline in the threshold-crossing buy or a separate `triggerGraduation` call), the token is permanently stuck: `finalizeGraduation` will deterministically revert on every retry since `(tokensForLP, ltFromPair)` are cached in `pendingGraduation[token]` and reused verbatim regardless of how many times or by whom the call is retried [5](#0-4) . There is no admin escape hatch to force-clear `pendingGraduation` or otherwise unstick the token.

### Impact Explanation
This permanently freezes:
- All curve-raised LT that was already drained into `Bonding` via `Router.graduate` during phase 1 (`ltFromPair`) — unreachable, since `_sweepLTToOwner`/further code never runs (the revert happens before it).
- The 250M `LP_RESERVE` tokens reserved for LP seeding, held in `Bonding`.
- Every trader's remaining token balance for that token, since trading is frozen at `Lifecycle.Graduating` and can never advance to `Graduated` or roll back to `Curve`.

This is a permanent freezing of trader/creator funds with no recovery path, matching the "Validate" criteria (concrete permanent freezing of funds).

### Likelihood Explanation
The trigger requires only that a token graduate via the supply trigger with an unusually small real LT raise — plausible for a token launched at the `$20` minimum seed with little-to-no further curve activity before all 750M curve tokens are sold (which the supply trigger is explicitly designed to accommodate for "flat/bear markets"). Reaching the exact numeric boundary where `sqrt(tokensForLP * ltFromPair) <= 1000` (in the LT's native decimal units) depends on the specific LT's price/decimals, so it is not guaranteed on every thin token, but it's a reachable, unprivileged, no-special-permission scenario — anyone can call `Bonding.triggerGraduation` on such a token (or simply let the natural buy flow reach the supply trigger) without needing any elevated role.

### Recommendation
Add an explicit precheck in `_prepareGraduationLiquidity` / `_seedDirectMint` (or a dedicated guard before minting) that detects `sqrt(tokensForLP * ltFromPair) <= MINIMUM_LIQUIDITY` and either (a) tops up the smaller side from the protocol's `LP_RESERVE`/floor logic to clear the minimum before minting, or (b) defines a documented minimum-raise floor on the supply trigger so degenerate near-zero raises cannot reach `finalizeGraduation` in the first place, and add regression tests exercising a graduation at the smallest possible curve raise (`Zap.MIN_SEED_USDC`) against realistic LT decimal/price combinations.

### Proof of Concept
1. Launch a token via `Zap.createToken` with the minimum seed (`Zap.MIN_SEED_USDC = $20`) against an LT whose price/decimals make the resulting LT amount raised by the curve very small in absolute wei terms.
2. Do not perform further buys; instead drive the curve toward the supply trigger by having the LT's `exchangeRate` depreciate sharply (bear-market leverage decay) combined with minimal additional buys, or by constructing a token/LT pairing where `750M` tokens can be sold for a small absolute LT amount.
3. Once `IPair(pair).tokenBalance() == 0`, call `Bonding.triggerGraduation(tokenAddress)` (permissionless) to run phase 1, caching `(tokensForLP, ltFromPair)` in `pendingGraduation`.
4. Call `Bonding.finalizeGraduation(tokenAddress)`. If `sqrt(tokensForLP * ltFromPair) <= 1000`, the underlying `pair.mint` call (matching `MockHyperswapPair.mint`'s asserted semantics) reverts with `INSUFFICIENT_LIQUIDITY_MINTED` (or an arithmetic underflow panic from `_sqrt(...) - MINIMUM_LIQUIDITY`), and every subsequent call to `finalizeGraduation` reverts identically forever, permanently freezing the token in `Lifecycle.Graduating` along with all curve-raised LT and the 250M LP-reserve tokens held by `Bonding`.

Note: I was not able to fully verify within the available exploration budget whether real-world LT decimal/price combinations and the protocol's minimum-seed floor make the `sqrt(tokensForLP*ltFromPair) <= 1000` condition actually reachable in practice (this depends on BounceTech LT decimal conventions not fully surfaced in the indexed code), so this should be validated numerically against the deployed LT configurations before treating it as confirmed-exploitable rather than a theoretical edge case.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }
```

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }
```
