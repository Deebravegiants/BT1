### Title
Cross-Tenant Webhook Spoofing via Unauthenticated `shop-domain` Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) exclusively from the `x-shopify-shop-domain` HTTP header, while the HMAC signature validated by `HmacValidator` only covers the raw request body. Because the webhook secret (`api_secret_key`) is shared across every shop that installs the app, any unprivileged attacker who installs the app on their own store can obtain a genuinely-signed webhook and then re-emit it with the `shop-domain` header changed to a victim shop, without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` and `topic` accessors are read straight from attacker-controllable HTTP headers, entirely outside the signed payload: [2](#0-1) 

`Registry.process` validates only this body-based HMAC before trusting the request's `shop` field and dispatching it to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the raw body only) and compares it against the `hmac` header value — it never incorporates `shop`, `topic`, or any other header: [4](#0-3) [5](#0-4) 

**Broken binding (equality that should hold but doesn't):**
`HMAC-authenticated sender == shop value trusted by the handler`

Before the attack: for a legitimate webhook, `hmac` is valid for body `B` and the `shop-domain` header correctly identifies the shop that produced `B`.
After the attack: an unprivileged user who has legitimately installed the app on their own store `attacker.myshopify.com` receives a real webhook `(B, HMAC(secret, B))`. Because `api_secret_key` is a per-app secret shared by all installed shops, this `HMAC` value remains valid for body `B` regardless of which `shop-domain` header accompanies it. The attacker resends the identical body/HMAC pair to the app's webhook endpoint with `x-shopify-shop-domain: victim.myshopify.com`. `HmacValidator.validate` still returns `true` (it only checks the body), and `Registry.process` forwards `request.shop == "victim.myshopify.com"` to the app's registered handler as trusted tenant identity via `WebhookMetadata.new(topic: ..., shop: request.shop, ...)`.

This is exactly the documented use of the gem: the `shop` field returned in `WebhookMetadata` is the mechanism host applications are expected to use to look up the corresponding merchant session/access token and act on their behalf — there is no other tenant-binding field provided by this gem's webhook API.

### Impact Explanation
Because host applications rely on `WebhookMetadata#shop` (sourced from this gem, per its documented contract) as the trusted tenant identifier to select which merchant's stored session/access token to use for follow-up Admin API actions, an attacker who is any unprivileged Shopify merchant that installs the target app can forge webhook deliveries that spoof another merchant's identity. This enables cross-tenant access: actions, data writes, or side effects intended to be scoped to the victim shop can be triggered by an attacker impersonating that shop through the webhook `shop` field, without ever obtaining the victim's credentials. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app author following the gem's documented API: any unprivileged internet user can register as a legitimate merchant of the target app (no special privilege needed), capture one of their own genuine webhook deliveries (trivial — just observe their own app's webhook traffic), and replay it with an altered `shop-domain` header. No secrets, tokens, or privileged access are required — only the ability to install the app as a normal merchant, which is the baseline "unprivileged internet user" threat model for this analysis.

### Recommendation
Bind the trusted `shop` value to something that is actually covered by the cryptographic signature, or otherwise cryptographically tie the header-derived shop to the request body/signature (e.g., include the shop domain in the signable string per-shop-secret scheme if supported by Shopify's webhook payload, or require host apps to cross-check the header-derived shop against the shop embedded within the JSON body/`WebhookId` mapping obtained via a prior, authenticated GraphQL lookup). At minimum, the gem should document explicitly, and ideally enforce, that `request.shop` must never be trusted as an authenticated tenant identifier on its own, since it is unauthenticated by the HMAC scheme used in `Utils::HmacValidator`.

### Proof of Concept
1. Install the target app as a normal merchant on `attacker.myshopify.com`.
2. Trigger any webhook topic the app subscribes to (e.g. `orders/create`) and capture the raw POST: body `B`, and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
3. Replay the exact same body `B` and header `H` to the app's webhook endpoint, but replace `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
4. In the gem: `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim.myshopify.com", "shopify-hmac-sha256" => H})` is constructed; `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks `B` against `H` [6](#0-5) [3](#0-2) 
5. The host application's webhook handler receives `WebhookMetadata` with `shop == "victim.myshopify.com"`, and performs whatever tenant-scoped action the app implements (e.g., looks up victim's stored access token/session and performs Admin API mutations, or trusts the payload as originating from the victim), even though the actual content `B` and triggering account belongs to the attacker.
