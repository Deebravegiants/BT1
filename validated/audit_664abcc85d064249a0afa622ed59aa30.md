### Title
Webhook shop/topic identity spoofing via unsigned headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` trusts and forwards to the app's handler are read from unauthenticated HTTP headers that the HMAC never covers. This breaks the identity binding `hmac-verified bytes == bytes used to identify the tenant/topic`, letting an attacker who has legitimately received one signed webhook replay it with a forged `shop-domain` (and/or `topic`) header and still pass HMAC validation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are read directly from headers, which are never part of the signed bytes: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header value using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` validates the HMAC and then, without any further check, trusts `request.topic` to select the handler and `request.shop` to populate `WebhookMetadata` passed to the app's business logic: [4](#0-3) 

Because `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are outside the signed payload, any party who has ever received one genuine webhook (body + valid `hmac-sha256` header) for their own shop can resend that exact HTTP body/HMAC pair to the app's public webhook endpoint while substituting a different `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` (the body and secret-derived signature match), and `Registry.process` will hand the forged shop identity straight to the handler, exactly mirroring the reported bug class: a field that is acted on (`shop`/`topic`) is not covered by the cryptographic binding (`hmac` over body only).

### Impact Explanation
This allows cross-tenant data confusion: a merchant who has installed the app (an unprivileged actor with respect to other tenants) can cause the app to process webhook data under another shop's identity, without ever needing the app's `client_secret`, an access token, or TLS interception. Depending on how the host app uses `data.shop` (e.g., session/token lookup, per-tenant data writes), this can lead to cross-tenant access or data corruption, which is a Critical-severity outcome per the defined impact categories.

### Likelihood Explanation
Likelihood is moderate: the attacker must have first legitimately received at least one signed webhook (trivial for any app installer/merchant) and must be able to POST a modified HTTP request (with a different `shop-domain` header but the same body/HMAC) to the app's public webhook endpoint, which is exposed to the internet by design. No secret material or privileged access is required beyond normal app installation.

### Recommendation
Bind the shop/topic identity to the HMAC-verified payload instead of trusting headers alone:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for HMAC computation, or
- Cross-check the header-derived `shop` against the shop encoded inside the JSON body (or an independently verified session/subscription record) before dispatching to the handler.

### Proof of Concept
1. Install the app on `shop-a.myshopify.com`; Shopify delivers a genuine webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid for secret `S` and body `B`), `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Capture this exact HTTP request (the app owner has full access to their own inbound requests).
3. Resend the same body `B` and same `hmac-sha256` header `H` to the app's webhook endpoint, but replace the header with `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `HmacValidator.validate` in `hmac_validator.rb` recomputes the HMAC over body `B` only, matches `H`, and returns `true`.
5. `Registry.process` (`registry.rb#L188-L200`) proceeds and calls the handler with `shop: "shop-b.myshopify.com"`, even though the payload was never issued for `shop-b`.

          received_signature = verifiable_query.hmac
