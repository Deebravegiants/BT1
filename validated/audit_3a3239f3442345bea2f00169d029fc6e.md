### Title
Unallowlisted route venues execute arbitrary contracts beneath the caller's `require_auth`, letting a crafted route graft a wallet-draining `token.transfer` onto the victim's signed authorization tree - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
CVE-2022-0097 is a "trusted-context escape": Chrome's DevTools let a malicious extension run with privileges the user never intended to grant, because a crafted payload was executed inside a privileged scope. The structural analog in XOXNO Lending is the swap router's venue dispatch: `dispatch_hop` invokes whatever `hop.pool` address the route payload names, and the lending controller forwards user-supplied `swap_xdr` verbatim. Because Soroban records every `require_auth` made by callee code as a sub-invocation of the signer's authorization tree, a malicious "pool" contract inside the route can call `token.transfer(victim, attacker, amount)` on any token, and that transfer executes if the victim signs the simulation-produced tree — exactly the "install this extension / sign this transaction" precondition the CVE relies on.

### Finding Description
`dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs:23-58` dispatches `hop.venue` to a venue adapter which calls the `hop.pool` address taken directly from the user-supplied route XDR. The router keeps no allowlist of pool or token contracts — the only whitelist in `contracts/swap-aggregator/src/storage.rs:27-39` (`DataKey::WhitelistedTokens`) is a *fee* whitelist, unrelated to execution targets. The threat model confirms this: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md:154-165`).

On the controller side, `swap_tokens` in `contracts/controller/src/strategies/swap.rs:34-38` authorizes only the controller's own exact input transfer and then runs `router.execute_strategy` inside a flash guard — but nothing constrains which contracts the route invokes, and the balance checks at `swap.rs:41-54` only bound the controller's `token_in`/`token_out` deltas. A malicious pool invoked mid-route runs arbitrary code in a call stack where the *user's* `require_auth` is still the enclosing authorization context. When that code calls `token.transfer(victim, attacker, amount)` on an unrelated wallet token, the host records it as a child of the victim's auth entry; the simulation the wallet signs therefore contains the theft as a sub-invocation.

This is demonstrated end-to-end in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `RogueHopPool::swap` calls `token::Client::transfer(victim → attacker)` (`:62-71`), and the test at `:229-269` shows that via the production `swap_collateral` entrypoint the host rejects the transfer under an honest tree but executes it — draining Alice's entire `WALLET_BALANCE` of an unlisted token — once the signed tree includes the rogue child. The same exposure applies to the direct `Router::execute_strategy` path for every swap user.

### Impact Explanation
Theft of user funds, unbounded by the routed amount: neither the payload `min_out`, the measured input/output deltas, nor the controller's final risk gate limits what route-invoked code requests from the signer's auth tree. A victim who signs the simulation-produced tree loses any token balance the rogue pool names (any token contract, any amount up to their full balance), not just the swap input. This matches the CVE's sandbox-escape impact — code the user "installed" (the route's pool contract) escapes its intended scope and acts with the victim's authority.

### Likelihood Explanation
User interaction is required (the victim must sign a tree containing the extra child), which mirrors the CVE's `UI:R` vector and tempers severity from Critical to High. However, the trap is realistic: the route XDR is opaque bytes produced by an off-chain quote server, the simulated auth tree legitimately contains nested entries for honest routes, and wallets render these trees poorly. An attacker only needs to get a crafted `routeXdr` in front of a user (phishing a quote, a malicious dapp, or a compromised quote response). The protocol provides no on-chain mitigation — no venue/pool registry, no WASM-hash pinning — so every `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and direct `execute_strategy` call carries this exposure.

### Recommendation
Constrain what a route can invoke on-chain rather than relying on clients to decode auth trees:

- Add an admin-governed pool/venue registry to the router (per `(venue, pool)` or per WASM hash) and reject hops targeting unregistered pools in `dispatch_hop` before any external call.
- Alternatively, pin venue adapters to verified interface contracts and refuse `hop.pool` addresses not present in a `PoolRegistry` storage key; governance-delay changes to the registry.
- Keep the controller-side documented requirement (clients must reject auth trees with unexpected children) as defense in depth, not as the sole mitigation.

### Proof of Concept
1. Attacker deploys `RogueHopPool` initialized with `(victim, victim_wallet_token, attacker, amount)` — the constructor stores the theft plan and `swap()` executes `token.transfer(victim, attacker, amount)` (see `rogue_hop_pool_transfer_joins_caller_auth_tree.rs:52-72`).
2. Attacker crafts a `swap_xdr` route that prices correctly (fair `min_out`, correct `token_in`/`token_out`) but routes a hop through `RogueHopPool`'s address as `hop.pool`. `dispatch_hop` invokes it because no allowlist exists (`venues/mod.rs:34-40`).
3. Victim submits `controller.swap_collateral(account, usdc, amount_in, eth, swap_xdr)` (or `router.execute_strategy` directly). Simulation records the rogue `token.transfer` as a child of the victim's auth entry and returns the poisoned tree.
4. Victim signs the returned tree; the host enforces it, the rogue transfer executes, and `WALLET_BALANCE` moves to the attacker while the swap itself settles normally and all controller risk gates pass. This is asserted verbatim in the test at `rogue_hop_pool_transfer_joins_caller_auth_tree.rs:259-269`.

Note on scope: this exposure is already described in `docs/explanation/threat-model.md:154-165` as a residual risk with a client-side mitigation ("a client must decode the route it signs"). It is reported here as a valid analog rather than an ADR-accepted design because it is an on-chain reachable theft of user funds with no contract-side bound; if the documented client-side check is considered an accepted trust assumption, this finding should be reclassified accordingly.
