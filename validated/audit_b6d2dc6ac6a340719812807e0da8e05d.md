**Rationale:** The reviewed code path is CLI/config-loading tooling for validator key management, not an on-chain custody surface reachable by unprivileged transactions, packages, or API/bytecode input. The `from_encoded_string`/`to_encoded_string` logic strips the AIP-80 prefix only if present via `strip_prefix` and always defers final validation to `TryFrom<&[u8]>`, which for BLS12-381 requires an exact-length, curve-valid byte string (48 bytes for `PublicKey` via `blst::min_pk::PublicKey::from_bytes`, 32 bytes for `PrivateKey`) [1](#0-0) [2](#0-1) . A mismatched prefix (e.g., using the `bls12381-priv-` prefix on public-key bytes or vice versa) does not cause cross-type confusion because `PublicKey::from_encoded_string` and `PrivateKey::from_encoded_string` are distinct associated functions tied to their own `AIP_80_PREFIX` constants and their own `TryFrom` deserializers [3](#0-2) [4](#0-3) ; a caller must already have chosen which concrete type to parse into, so a crafted string cannot make `PublicKey::from_encoded_string` silently return key material that Rust's type system treats as a `PrivateKey`, or vice versa.

Beyond this, the described scenario (operator/CLI accidentally registering wrong key material via `ValidatorConsensusKeyArgs::consensus_public_key`) requires local tooling misuse and does not originate from an unprivileged transaction, package, view function, authenticator, on-chain API, bytecode, or proof input as required by the review bounds. This falls squarely under "local tooling" which is explicitly excluded from review scope, and does not cross any on-chain custody boundary affecting APT, fungible assets, objects, or resource accounts.

    fn from_encoded_string(encoded_str: &str) -> std::result::Result<Self, CryptoMaterialError> {
        let mut str = encoded_str;
        // First strip the AIP-80 prefix
        str = str.strip_prefix(Self::AIP_80_PREFIX).unwrap_or(str);

        // Strip 0x at beginning if there is one
        str = str.strip_prefix("0x").unwrap_or(str);

        let bytes_out = ::hex::decode(str);
        // We defer to `try_from` to make sure we only produce valid crypto materials.
        bytes_out
            // We reinterpret a failure to serialize: key is mangled someway.
            .or(Err(CryptoMaterialError::DeserializationError))
            .and_then(|ref bytes| Self::try_from(bytes))
    }

impl TryFrom<&[u8]> for PublicKey {
    type Error = CryptoMaterialError;

    /// Deserializes a PublicKey from a sequence of bytes.
    ///
    /// WARNING: Does NOT subgroup-check the public key! Instead, the caller is responsible for
    /// verifying the public key's proof-of-possession (PoP) via `ProofOfPossession::verify`,
    /// which implicitly subgroup-checks the public key.
    ///
    /// NOTE: This function will only check that the PK is a point on the curve:
    ///  - `blst::min_pk::PublicKey::from_bytes(bytes)` calls `blst::min_pk::PublicKey::deserialize(bytes)`,
    ///    which calls `$pk_deser` in <https://github.com/supranational/blst/blob/711e1eec747772e8cae15d4a1885dd30a32048a4/bindings/rust/src/lib.rs#L734>,
    ///    which is mapped to `blst_p1_deserialize` in <https://github.com/supranational/blst/blob/711e1eec747772e8cae15d4a1885dd30a32048a4/bindings/rust/src/lib.rs#L1652>
    ///  - `blst_p1_deserialize` eventually calls `POINTonE1_Deserialize_BE`, which checks
    ///    the point is on the curve: <https://github.com/supranational/blst/blob/711e1eec747772e8cae15d4a1885dd30a32048a4/src/e1.c#L296>
    fn try_from(bytes: &[u8]) -> std::result::Result<Self, CryptoMaterialError> {
        Ok(Self {
            pubkey: blst::min_pk::PublicKey::from_bytes(bytes)
                .map_err(|_| CryptoMaterialError::DeserializationError)?,
        })
    }
}
