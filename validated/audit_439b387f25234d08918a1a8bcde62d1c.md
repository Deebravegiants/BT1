## Confirmed Vulnerability

### Title
Empty `erc20TokenAddresses` on the Emporium-Min circuit path skips all ETH balance-conservation checks in `runAction`, letting an attacker drain Emporium's pre-existing ETH balance via `op.value` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `circomData.erc20TokenAddresses.length == 0` (the Min-circuit Emporium path), `Hinkal.transact` performs no per-token balance check loop at all [1](#0-0) , and `Hinkal._externalTransact`'s `deltaAmountChanges` loop (which is the only mechanism that pulls funds from Hinkal to Emporium) also never executes because it iterates over the same empty array [2](#0-1) . Inside `EmporiumUpgradeable.runAction`, the balance-conservation loop that computes `balanceChange` and reverts with `BalanceChangeShouldBePositive` also iterates over `circomData.erc20TokenAddresses`, so with an empty array it never runs either [3](#0-2) . The only remaining check is `verifyWallet`, which for `stack.signerAddress == address(0)` returns immediately without any signature validation [4](#0-3) . This leaves `op.endpoint.call{value: op.value}(op.callData)` [5](#0-4)  as an unconstrained ETH transfer out of the Emporium contract's own balance.

### Finding Description
The claimed broken equality is: **net tokens entering Hinkal == sum(amountChanges) + on-chain UTXOs inserted**. With `erc20TokenAddresses = []`:
- `amountChanges = []` (enforced equal length by `dimensionsCheck`) [6](#0-5) .
- `Hinkal.transact`'s post-action reconciliation loop over `circomData.erc20TokenAddresses` (lines 97-147) — which normally enforces `balanceDif == amountChanges[i] + utxoAmount` and folds in `msg.value` for ETH (address(0)) — never executes.
- `_externalTransact`'s `deltaAmountChanges` computation and any negative-delta transfer from Hinkal to Emporium never executes.
- Inside `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter`/`balanceChange` are all computed over the same empty array, so the `BalanceChangeShouldBePositive` guard and `handleOut` UTXO creation never fire for ETH.

Given this, an attacker can call `Hinkal.transact` with `msg.value == 0`, `erc20TokenAddresses = []`, and `externalActionData.externalActionMetadata` ABI-encoding an `EmporiumStack` whose `ops` array contains an entry with `invokeWallet = false`, `signerAddress = address(0)` (skips EIP-712 verification), an arbitrary `endpoint`, and `value > 0`. Because `stack.signerAddress == address(0)` also satisfies `verifyWallet`'s early return, no signature is checked at all. The call reaches `op.endpoint.call{value: op.value}(op.callData)`, which draws `op.value` in ETH from `EmporiumUpgradeable`'s own contract balance (`address(this).balance`), since Solidity's low-level `.call{value:}` always spends from the calling contract's balance, not from any value transferred in the current transaction. This ETH was never accounted for by `amountChanges` (empty) nor validated by any balance-diff check, so it leaves Emporium unconditionally whenever Emporium holds any ETH.

The only friction is `require(GetHashedCalldata(circomData) == circomData.calldataHash)` in `performHinkalChecks`, and proof verification against the Min-circuit's public inputs (`emporiumMessage`, `timeStamp`, `calldataHash`) [7](#0-6) . These bind the calldata (including the malicious `EmporiumStack`) to a valid proof for the attacker's own UTXOs, but they do not constrain `op.value` against any deposited amount — the attacker fully controls `calldataHash` and the circuit inputs since they are proving over their own (possibly self-generated, zero-value) transaction data. `checkOnchainCreation` and `dimensionsCheck` only constrain array lengths, not ETH movement, and are satisfied trivially by empty arrays.

### Impact Explanation
Direct theft of ETH balance held by the Emporium contract (e.g., accumulated dust, fees, or previously routed but not-yet-forwarded funds) by any unprivileged attacker, to an arbitrary attacker-controlled `endpoint`, with no requirement to deposit any of their own funds. This is repeatable on every transaction as long as Emporium holds a nonzero ETH balance, and qualifies as Critical — direct theft of protocol-held funds via a path where the value-conservation invariant claimed in the codebase's own comments (`// this equation reads: total change of emporium balance = ...`) is silently bypassed by the empty-array Min-circuit branch.

### Likelihood Explanation
Preconditions: (1) Emporium contract must hold some ETH balance (plausible in normal operation from flat fees, leftover dust from prior stateless calls, or direct transfers); (2) attacker needs a valid Groth16 proof for the Min circuit over their own (possibly trivial/self-funded) UTXO set, which is fully attacker-generatable since they control all circuit inputs for their own transaction; (3) `HINKAL_EMPORIUM_ACTION_ID` must be registered in `externalActionMap` (a standard deployment configuration, not owner-gated at call time). Attacker cost is minimal (one transaction, no deposit required, `msg.value == 0`). Fully repeatable until Emporium's ETH balance is exhausted.

### Recommendation
In `EmporiumUpgradeable.runAction`, do not gate the balance-conservation loop solely on `circomData.erc20TokenAddresses.length`. Explicitly track and validate native ETH balance change (`address(this).balance` before/after) independent of the ERC20 token array, and require that any ETH spent via `op.value` across all ops is fully accounted for by a corresponding `amountChanges`/deposit entry, even when `erc20TokenAddresses` is empty. Alternatively, disallow `op.value > 0` entirely on the Min-circuit path (i.e., when `erc20TokenAddresses.length == 0`), since that path was designed to skip token bookkeeping and should not permit any native value transfer.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register `HINKAL_EMPORIUM_ACTION_ID` in `externalActionMap`.
2. Fund `EmporiumUpgradeable` with e.g. 5 ETH directly (simulating pre-existing balance from fees/dust).
3. Deploy a trivial `endpoint` contract that just accepts ETH (`receive() external payable {}`).
4. Construct `EmporiumStack` with one `EmporiumOperation{ endpoint: attackerEndpoint, invokeWallet: false, value: 5 ether, callData: "" }`, `signerAddress: address(0)`.
5. Build `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, etc., `externalActionData.externalActionMetadata = abi.encode(stack)`, and compute `calldataHash` via `getHashedCalldata`.
6. Generate a valid Min-circuit proof for these public inputs (attacker's own UTXO set, can be trivial/self-consistent).
7. Call `Hinkal.transact{value: 0}(a, b, c, dimensions, circomData)` from an attacker EOA with zero prior deposit.
8. Assert: `attackerEndpoint.balance == 5 ether` after the call, `EmporiumUpgradeable` balance reduced by 5 ETH, while `circomData.amountChanges.length == 0` and `msg.value == 0`, proving the outflow was never reflected in the value-conservation equation.
