### Title
Missing minimum-bound validation on `challengePeriod` allows governance to set a zero/near-zero dispute window - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.updateHostParamsInternal` validates several `HostParams` fields (host manager, handler, consensus client, hyperbridge id, state machine list, and `unStakingPeriod`) but performs **no minimum-bound check on `challengePeriod`**, even though this field is the security-critical fraud-proof/dispute window for state commitments delivered by the consensus client.

### Finding Description
`HostParams.challengePeriod` is documented as the "Minimum challenge period for state commitments in seconds" [1](#0-0) . It is set through `updateHostParamsInternal`, which is reachable via a single cross-chain governance message: a relayer delivers a `PostRequest` from the Hyperbridge parachain to `HostManager.onAccept`, which decodes a `SetHostParam` action and calls `IHostManager(_params.host).updateHostParams(hostParams)` [2](#0-1) , which in turn calls `updateHostParamsInternal` [3](#0-2) .

Inside `updateHostParamsInternal`, every other invariant is checked with a revert (`InvalidHostManager`, `InvalidHandler`, `InvalidConsensusClient`, `InvalidHyperbridgeId`, `InvalidStateMachinesLength`, and critically `InvalidUnstakingPeriod` which enforces `1 days` as a floor on `unStakingPeriod`): [4](#0-3) 

However `challengePeriod` is assigned directly with **no equivalent floor check**: [5](#0-4) 

This mirrors the reported bug class exactly: a security-relevant delay parameter (there, the multisig timelock; here, the state-commitment challenge/fraud-proof period) is fully configurable by a privileged-but-external actor without any range enforcement in code, while the rest of the protocol design and documentation treats it as a meaningful minimum delay that fishermen rely on to dispute fraudulent state commitments before they are consumed. This is confirmed by the test suite, which freely sets `challengePeriod` to arbitrary values (including small deltas) with no revert [6](#0-5) , and by the Rust test that sets it to an arbitrary `U256` value without any bound rejection [7](#0-6) .

Because `challengePeriod` gates whether a state commitment can be used to verify incoming messages (it is the window during which the Polkadot pallet-ismp / EvmHost apply `check_challenge_period` before trusting a state commitment) [8](#0-7) , setting it to `0` (or an unreasonably small value) via a single governance-relayed `SetHostParam` message removes the dispute window entirely. State commitments submitted by a compromised or malicious consensus client/relayer could then be relied upon for proof verification (message delivery, state membership proofs) immediately, before fishermen have any chance to challenge them.

### Impact Explanation
If `challengePeriod` can be set to zero without restriction, the fraud-proof / dispute window that protects the entire ISMP message-delivery and state-verification pipeline (`HandlerV2` proof verification against `EvmHost` state commitments) is nullified. This enables unsound state commitments to be accepted and acted upon before fishermen can intervene, which can lead to forged message delivery or unauthorized app actions relying on unverified/fraudulent state — a concrete "unsound state commitment" class of impact.

### Likelihood Explanation
The change is a single governance action (`SetHostParam` relayed through `HostManager`/`EvmHost`), requiring no on-chain bug beyond the missing validation itself. It only requires the entity currently authorized to send governance messages (the Hyperbridge relayer/admin acting through `HostManager`) to submit a param update — no additional exploit is needed once such a message is (mis)configured or compromised, since the code path performs zero enforcement of a minimum challenge period, unlike the analogous `unStakingPeriod` field which is explicitly protected.

### Recommendation
Add a minimum-bound check for `challengePeriod` in `updateHostParamsInternal`, analogous to the existing `InvalidUnstakingPeriod` check for `unStakingPeriod`:
```solidity
if (MIN_CHALLENGE_PERIOD > params.challengePeriod) revert InvalidChallengePeriod();
```
Define `MIN_CHALLENGE_PERIOD` to match the protocol's documented security assumptions, and mirror the same validation in `evm/rust/src/host_params.rs::EvmHostParam::update` so the Rust-side ABI encoder/validator used by tooling stays consistent with the Solidity contract.

### Proof of Concept
1. Governance (via `HostManager.onAccept`, called by an authorized relayer delivering a `SetHostParam` `PostRequest` from the Hyperbridge state machine) submits a `HostParams` payload identical to the current params except `challengePeriod = 0`.
2. `EvmHost.updateHostParams` → `updateHostParamsInternal` executes all listed checks; none of them reference `challengePeriod`, so the zero value is accepted and stored [9](#0-8) .
3. Any subsequently delivered state commitment for a whitelisted state machine can now be treated as immediately final/usable by `HandlerV2` and downstream proof verification, since the challenge-period gate is effectively disabled — as demonstrated by the existing test harness that arbitrarily overwrites `challengePeriod` and observes it applied without restriction [6](#0-5) .

    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }

        // otherwise cannot process new cross-chain governance requests
        if (keccak256(params.hyperbridge) == keccak256(bytes(""))) revert InvalidHyperbridgeId();

        // otherwise cannot process new datagrams
        uint256 stateMachinesLen = params.stateMachines.length;
        if (stateMachinesLen == 0) revert InvalidStateMachinesLength();

        // otherwise cannot process new datagrams
        if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();

        address oldFeeToken = feeToken();
        if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
            uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
            if (balance != 0) revert CannotChangeFeeToken();
        }

        // safe to emit here because invariants have already been checked
        // and don't want to store a temp variable for the old params
        emit HostParamsUpdated({oldParams: _hostParams, newParams: params});

        _hostParams.feeToken = params.feeToken;
        _hostParams.admin = params.admin;
        _hostParams.handler = params.handler;
        _hostParams.hostManager = params.hostManager;
        _hostParams.uniswapV2 = params.uniswapV2;
        _hostParams.unStakingPeriod = params.unStakingPeriod;
        _hostParams.challengePeriod = params.challengePeriod;
        _hostParams.consensusClient = params.consensusClient;
        _hostParams.stateMachines = params.stateMachines;
        _hostParams.hyperbridge = params.hyperbridge;

        HostParams memory params = host.hostParams();
        uint256 previousPeriod = params.challengePeriod;
        params.challengePeriod = previousPeriod + 1234;
        PostRequest memory request = _setHostParamRequest(params);

        vm.prank(address(host));
        vm.expectRevert(HostManager.UnauthorizedAction.selector);
        manager.onAccept(IncomingPostRequest(request, OUTSIDER));
        assertEq(host.hostParams().challengePeriod, previousPeriod, "params unchanged");

        // The relayer as reported by the host is never zero, and the admin is never zero either, so
        // zero matches nothing.
        vm.prank(address(host));
        vm.expectRevert(HostManager.UnauthorizedAction.selector);

        // The same message goes through from the authorised relayer.
