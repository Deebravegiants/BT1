### Title
Webhook shop identity spoofing via HMAC that binds only the raw body, not the `shopify-shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body alone, while the `shop` (tenant identity) is read from an HTTP header that is never included in the signed payload. `Registry.process` trusts that header as the tenant identifier when dispatching to app handler code.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed string: [2](#0-1) 

`Registry.process` validates the HMAC over the request via `Utils::HmacValidator.validate(request)` — which internally calls `request.to_signable_string` (body only) — and then, if valid, dispatches to the app-registered handler using `request.shop` as the tenant identity, with no additional check that the shop matches anything cryptographically bound to the signature: [3](#0-2) 

The HMAC validator itself simply recomputes HMAC over `to_signable_string` and compares: [4](#0-3) 

The equality this breaks: **the shop the HMAC authenticates ≠ the shop the handler acts on.** Shopify computes a valid `hmac-sha256` header using the app's shared `client_secret` over the JSON body for events from *any* shop that has the app installed — including a store the attacker legitimately owns/controls (e.g. a free development store). Because the shop-domain header is excluded from the signed bytes, an attacker who has a genuine, validly-HMAC-signed webhook from their own store can replay that exact body+HMAC to the victim app's webhook endpoint while substituting the `shopify-shop-domain` header value with an arbitrary/victim shop domain. `Utils::HmacValidator.validate` still returns `true` (the body and secret match), and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` reporting the attacker-chosen shop, allowing the attacker to have their forged/replayed data attributed to and processed under a different tenant's identity in the app's own business logic.

### Impact Explanation
This satisfies the "Critical — cross-tenant access" bar: an attacker with only a legitimate webhook subscription on their own (attacker-controlled) shop can make an app that consumes this gem's webhook processing believe an arbitrary event (with attacker-controlled JSON body content, since the body is only checked for authenticity, not attributed identity) originated from a victim/different shop. Any app logic keyed off `WebhookMetadata#shop` — updating merchant records, provisioning, billing, deactivation, order sync, etc. — can be poisoned for a shop the attacker does not control, without holding the victim's access token or any privileged credential.

### Likelihood Explanation
The prerequisite is low: obtaining a legitimate, validly HMAC-signed webhook payload only requires installing the app on any Shopify store (including a free development store), which is available to any unprivileged internet user with a Shopify Partner account. From there, replaying the captured request body/HMAC while swapping the shop-domain header is a straightforward HTTP request; there's no rate limiting or nonce/timestamp binding in `to_signable_string` that would prevent this replay path from an identity-spoofing perspective (nonce/replay/timing behavior is out of scope here — the root issue is the missing binding of `shop` into the signed bytes).

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signable string, or otherwise cryptographically bind the identity claimed in `Webhooks::Request#shop` to the same bytes verified by `Utils::HmacValidator`, so that no header outside the signed payload can be substituted post-signature without invalidating the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own Shopify development store (`attacker-shop.myshopify.com`) and triggers a real webhook event, capturing the exact raw body `B` and the valid `X-Shopify-Hmac-SHA256` header `H` that Shopify computed with the app's shared secret over `B`.
2. Attacker sends a POST to the victim app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because it only signs `B`)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (swapped)
   - Header `X-Shopify-Topic`: unchanged
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and finds it matches `H`, so validation succeeds: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `request.shop` is `"victim-shop.myshopify.com"` — a value never covered by the HMAC — causing the app to process attacker-supplied data under the victim shop's identity.
