### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC that covers only the raw request body, while the `shop` (and `topic`/`webhook_id`/`api_version`) values used by the app to identify the tenant are read directly from HTTP headers that are never part of the signed bytes. This breaks the identity binding `shop asserted == shop authenticated`, the same class of bug as the reported PRBProxy issue where a security-relevant field (there, plugin/permission mappings; here, the tenant shop identity) is not protected by the mechanism meant to guarantee its integrity.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a webhook by comparing the received HMAC against a digest computed over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body, and `hmac` is decoded straight from the `hmac-sha256` header — the `shop`, `topic`, `webhook_id`, and `api_version` values are read from separate, unsigned headers: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — none of which are covered by that validation — to build the tenant-identifying `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The equality the library implicitly claims to guarantee is:
`shop used by handler == shop that Shopify actually sent this payload for`

But the HMAC only proves:
`body bytes == body bytes Shopify signed with api_secret_key`

It says nothing about which shop those bytes belong to, since the shop identity travels in an unsigned header (`x-shopify-shop-domain` / `shopify-shop-domain`).

### Impact Explanation
An unprivileged internet user who is themselves a legitimate (e.g., free/dev-store) Shopify merchant can obtain a genuinely-signed webhook body+HMAC pair for their own shop (Shopify sends real webhooks to any store's registered endpoint, and the attacker controls that endpoint). They can then replay the identical body and HMAC to the target app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because the body is unchanged and the signature matches, and `Registry.process` forwards `request.shop` (the attacker-forged header) as the tenant identity to the app's `WebhookHandler`. Any app logic keyed off `WebhookMetadata#shop` (e.g., looking up the victim's stored session/access token to process the "event", or writing data attributed to the victim shop) is now cross-tenant confused — data or actions intended for the attacker's own shop are attributed to, or acted on behalf of, the victim shop. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Reachable by any actor able to register a Shopify store and receive webhooks to a controlled endpoint (no privileged credentials, access tokens, or `api_secret_key` needed) — only body/HMAC capture and header replay against the target's public webhook endpoint are required. The library provides no mechanism to bind the shop header to the signed body, so any app relying on `HmacValidator` + `Request#shop` for tenant identity (the documented, intended usage pattern) is exposed by design.

### Recommendation
Do not treat `Webhooks::Request#shop` (or `topic`/`webhook_id`) as authenticated merely because `HmacValidator.validate` returned true. Either:
- Include the shop domain (and topic/webhook id) in the signable string used for HMAC verification, matching them against the header-derived values before trusting them, or
- Cross-check the header-derived `shop` against a shop value independently known to the app (e.g., the session/shop the webhook was registered against) rather than trusting the header value directly, and document clearly that `HmacValidator` only certifies body integrity, not header authenticity.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-owned) Shopify store and registers/receives a legitimate webhook, capturing the raw body and the `x-shopify-hmac-sha256` header — both genuinely signed by Shopify with the app's `api_secret_key`.
2. Attacker sends an HTTP request to the app's public webhook endpoint reusing the exact captured body and HMAC header, but with `x-shopify-shop-domain` (or `shopify-shop-domain`) rewritten to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the HMAC: [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though Shopify never sent this event for that shop, causing the app to act on/attribute data to the wrong tenant.
