## Analysis: Front‑running of `create_pool_with_fee` in `pallet-asset-conversion`

### Title
Permissionless `create_pool` can front‑run `AdminOrigin`'s privileged `create_pool_with_fee`, locking a pool into the default fee tier - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion` exposes two ways to create a pool for an asset pair: the fully permissionless `create_pool` (any signed account, default global `LPFee`), and the privileged `create_pool_with_fee` (requires `T::AdminOrigin`, allows setting a custom per-pool fee). Both funnel into the same `do_create_pool` internal function, which derives a deterministic `pool_id` purely from the two asset kinds and rejects creation if a pool for that pair already exists.

### Finding Description
`create_pool` is callable by any signed account and creates a pool with `initial_fee = None` (falls back to the global `T::LPFee`): [1](#0-0) 

`create_pool_with_fee` is the privileged equivalent, gated by `T::AdminOrigin`, intended to set up a pool with a specific, possibly non-default, swap fee (e.g., a near-zero fee for a stable pair, or a deliberately higher fee): [2](#0-1) 

Both dispatch into `do_create_pool`, which computes the `pool_id` deterministically from `(asset1, asset2)` via `T::PoolLocator::pool_id` and enforces `Error::PoolExists` if that `pool_id` is already registered — irrespective of who created it or what fee was requested: [3](#0-2) 

Because the `pool_id` is fully determined by the asset pair (no salt tied to the caller or intended fee), any unprivileged account can pre-create the canonical pool for a pair the `AdminOrigin` intends to configure with a custom fee. Once created, `Pools::<T>::contains_key(&pool_id)` is `true`, so the subsequent privileged `create_pool_with_fee(origin, creator, asset1, asset2, fee)` call unconditionally fails with `Error::PoolExists`, exactly mirroring the `PAIR_EXISTS` lock described in the external report.

This is the same root-cause pattern as the reported Uniswap issue: a privileged initialization path (which sets special parameters — hooks/fee) can be preempted by a permissionless path that initializes the same deterministic identifier with default/void parameters, and the registry (`getPair` / `Pools` storage) then rejects re-initialization.

### Impact Explanation
Unlike the original report, this analog is **not permanent/unrecoverable**. `pallet-asset-conversion` provides `set_pool_fee`, gated by the same `T::AdminOrigin`, which can retroactively set the custom fee on an *already existing* pool without needing to recreate it: [4](#0-3) 

Also, unlike the Uniswap pair contract (where `launchpadFeeDistributor == 0` hard-gates fee accrual/distribution to zero forever), the asset-conversion swap fee logic falls back to the non-zero global `T::LPFee` when no per-pool override exists — fees are never fully suppressed, only potentially set to the wrong (default) value until an admin notices and corrects it via `set_pool_fee`. There is also a pallet test explicitly demonstrating that an attacker cannot permanently block a legitimate pool creator, `cannot_block_pool_creation`, though that test targets asset dust-spam griefing on the pool account, not the fee-tier front-run described here: [5](#0-4) 

So the realistic impact is: temporary use of the wrong (default) swap fee for a pool the admin intended to configure specially, correctable in a single subsequent `set_pool_fee` call — not the “permanent reward suppression” described in the original report.

### Likelihood Explanation
Likelihood of the front-run itself is high (any signed account, no special preconditions, deterministic `pool_id` is fully predictable from public asset identifiers, cheap `create_pool` extrinsic). However, the likelihood of *material* economic harm is low because the vulnerability is self-healing via `set_pool_fee`, which does not require pool recreation.

### Recommendation
Not required as a critical fix given the existing `set_pool_fee` remediation path, but for defense-in-depth: consider allowing `create_pool_with_fee` to overwrite/upgrade a pool that was created via plain `create_pool` with the default fee (instead of failing with `PoolExists`) when called by `T::AdminOrigin`, or emit a distinct event/warning when an admin's `create_pool_with_fee` collides with a pre-existing permissionless pool so operators know to immediately follow up with `set_pool_fee`.

### Proof of Concept
1. Admin/governance decides pool `(Native, WithId(2))` should use a custom fee via `create_pool_with_fee`.
2. Before the admin's extrinsic lands, any account calls `AssetConversion::create_pool(origin, Native, WithId(2))` — succeeds, creating the pool with the default global `LPFee`, per [1](#0-0) .
3. Admin's subsequent `create_pool_with_fee(origin, creator, Native, WithId(2), fee)` now fails with `Error::PoolExists`, mirroring the behavior verified by `create_same_pool_twice_should_fail`: [6](#0-5) .
4. Admin must instead call `set_pool_fee(origin, pool_id, fee)` on the existing pool to achieve the intended configuration — an extra step, but not a permanent loss of functionality.

---

Given the presence of `set_pool_fee` as a full remediation path and the fact that default (non-zero) fees still accrue during the window, this does not rise to the severity of the original "permanent suppression of rewards" finding. It is a valid but low-impact analog of the same *pattern* (deterministic-ID front-running of privileged initialization parameters), not an equivalent-severity vulnerability.

		pub fn set_pool_fee(
			origin: OriginFor<T>,
			pool_id: T::PoolId,
			fee: Permill,
		) -> DispatchResult {
			T::AdminOrigin::ensure_origin(origin)?;
			ensure!(fee <= T::MaxSwapFee::get(), Error::<T>::FeeTooHigh);
			ensure!(Pools::<T>::contains_key(&pool_id), Error::<T>::PoolNotFound);
			PoolFees::<T>::insert(&pool_id, fee);
			Self::deposit_event(Event::PoolFeeSet { pool_id, fee });
			Ok(())
		}

		pub(crate) fn do_create_pool(
			creator: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			initial_fee: Option<Permill>,
		) -> Result<T::PoolId, DispatchError> {
			ensure!(asset1 != asset2, Error::<T>::InvalidAssetPair);
			if let Some(fee) = initial_fee {
				ensure!(fee <= T::MaxSwapFee::get(), Error::<T>::FeeTooHigh);
			}

			// prepare pool_id
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;
			ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists);

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

#[test]
fn create_same_pool_twice_should_fail() {
	new_test_ext().execute_with(|| {
		let user = 1;
		let token_1 = NativeOrWithId::Native;
		let token_2 = NativeOrWithId::WithId(2);

		create_tokens(user, vec![token_2.clone()]);

		let lp_token = AssetConversion::get_next_pool_asset_id();
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(token_2.clone()),
			Box::new(token_1.clone())
		));
		let expected_free = lp_token + 1;
		assert_eq!(expected_free, AssetConversion::get_next_pool_asset_id());

		assert_noop!(
			AssetConversion::create_pool(
				RuntimeOrigin::signed(user),
				Box::new(token_2.clone()),
				Box::new(token_1.clone())
			),
			Error::<Test>::PoolExists
		);
		assert_eq!(expected_free, AssetConversion::get_next_pool_asset_id());

		// Try switching the same tokens around:
		assert_noop!(
			AssetConversion::create_pool(
				RuntimeOrigin::signed(user),
				Box::new(token_1.clone()),
				Box::new(token_2.clone())
			),
			Error::<Test>::PoolExists
		);
		assert_eq!(expected_free, AssetConversion::get_next_pool_asset_id());
	});
}

#[test]
fn cannot_block_pool_creation() {
	new_test_ext().execute_with(|| {
		// User 1 is the pool creator
		let user = 1;
		// User 2 is the attacker
		let attacker = 2;

		let ed = get_native_ed();
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), attacker, 10000 + ed));

		// The target pool the user wants to create is Native <=> WithId(2)
		let token_1 = NativeOrWithId::Native;
		let token_2 = NativeOrWithId::WithId(2);

		// Attacker computes the still non-existing pool account for the target pair
		let pool_account =
			<Test as Config>::PoolLocator::address(&(token_1.clone(), token_2.clone())).unwrap();
		// And transfers the ED to that pool account
		assert_ok!(Balances::transfer_allow_death(
			RuntimeOrigin::signed(attacker),
			pool_account,
			ed
		));
		// Then, the attacker creates 14 tokens and sends one of each to the pool account
		for i in 10..25 {
			create_tokens(attacker, vec![NativeOrWithId::WithId(i)]);
			assert_ok!(Assets::mint(RuntimeOrigin::signed(attacker), i, attacker, 1000));
			assert_ok!(Assets::transfer(RuntimeOrigin::signed(attacker), i, pool_account, 1));
		}

		// User can still create the pool
		create_tokens(user, vec![token_2.clone()]);
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone())
		));
