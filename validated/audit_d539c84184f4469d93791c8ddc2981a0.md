### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the signable string used for HMAC verification from the raw body only, while `shop`, `topic`, and `webhook-id` are read from unauthenticated HTTP headers. Any party capable of producing one validly-signed webhook body for the app (e.g. by triggering a webhook event on their own installed shop) can resend that request to the app's webhook endpoint with a forged `x-shopify-shop-domain` header, and the HMAC check will still pass because the header is never part of the signed payload.

### Finding Description
`Utils::HmacValidator.validate` verifies the HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body: [2](#0-1) 

But `shop`, `topic`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the body: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards the *unauthenticated* `request.shop` (and `request.topic`) directly to the app's handler as trusted identity data: [4](#0-3) 

The broken identity binding is:
`shop authenticated by HMAC` (nothing — HMAC only covers `raw_body`) **≠** `shop trusted by the handler` (`request.shop`, taken from the `x-shopify-shop-domain`/`shopify-shop-domain` header).

Since Shopify webhook HMACs are computed with the app-wide `api_secret_key` (not a per-shop secret), any shop that has the app installed can obtain a validly-signed webhook body for itself (Shopify sends it to the app's own callback URL), and then replay that exact body to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Registry.process` will accept it as authentic because the signature check only covers the body bytes, and will call the handler believing the event originates from the victim tenant.

### Impact Explanation
This breaks the shop/tenant identity boundary the HMAC is supposed to enforce: an attacker who is merely a legitimate (unprivileged) installed merchant of the app can impersonate the webhook shop of any other tenant. Any app logic keyed off `WebhookMetadata#shop` (e.g. updating shop-scoped records, triggering shop-scoped side effects, or feeding `shop` into subsequent authenticated actions) can be manipulated cross-tenant, i.e. cross-tenant access/data corruption using another shop's identity without ever obtaining that shop's credentials.

### Likelihood Explanation
Requires only that the attacker control one shop that has the app installed (or captures one legitimate webhook delivery for any shop) and can send arbitrary HTTP requests to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed. This is a realistic, unprivileged-internet-user attack path fully reachable through this gem's own webhook verification code.

### Recommendation
Include the shop domain (and topic/webhook-id, if they are relied upon for identity) in the HMAC-covered signable string, or otherwise cryptographically bind these header values to the payload before trusting them (e.g., verify `request.shop` against a shop the app is actually expecting for that specific installation/session, or require Shopify's newer authenticated webhook payload fields rather than trusting the header in isolation).

### Proof of Concept
1. App shop `attacker.myshopify.com` has the app installed; Shopify sends it a legitimate webhook (e.g. `orders/create`) to the app's callback URL with body `B`, a valid `x-shopify-hmac-sha256` computed over `B` using the app's `api_secret_key`, and header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this request and replays it to the same webhook endpoint, keeping body `B` and the original (still-valid) HMAC header unchanged, but rewriting `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` (`B`) only and it matches, so `Registry.process` accepts the request.
4. `Registry.process` invokes `handler.handle` with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled webhook content under the victim's shop identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
