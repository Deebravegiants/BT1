Based on my analysis, I have confirmed a valid analog vulnerability.

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing in webhook processing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body [1](#0-0) , then hands the handler a `WebhookMetadata` struct whose `shop` field is taken directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . The signable content used for HMAC verification is only `@raw_body` [3](#0-2) , so the `shop` header value is never bound to the signature at all.

### Finding Description
The identity binding that should hold is: `shop value cryptographically bound by HMAC == shop value the handler treats as the tenant key`. In this gem, that equality is broken. `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it against the received HMAC [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only the raw body bytes [3](#0-2) , while `shop` is read straight out of the header dictionary with no cryptographic tie to the HMAC [2](#0-1) .

Because a given app uses the same `api_secret_key` for every shop that installs it, any webhook payload/HMAC pair legitimately delivered by Shopify for Shop A (which the app owner/merchant of Shop A can observe, since they control that shop's webhook endpoint) remains a **valid** HMAC for the exact same raw body regardless of which `shop-domain` header accompanies it. An attacker who operates (or has installed) the app on Shop A can capture one legitimately-signed webhook body+HMAC and resubmit it to the app's webhook endpoint with the `shopify-shop-domain` header changed to Shop B. `Registry.process` will accept it because `Utils::HmacValidator.validate(request)` only checks body integrity, not shop binding [1](#0-0) , and it will invoke the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is the attacker-controlled header value [5](#0-4) .

Any host application that uses `data.shop` from `WebhookMetadata` to key its per-tenant session/data lookups (the documented, expected usage pattern for `WebhookHandler#handle`) [6](#0-5)  will process attacker-supplied body content under another merchant's identity — a cross-tenant data-confusion primitive rooted entirely in this gem's webhook verification logic, not merely host misuse.

### Impact Explanation
This breaks the tenant/shop authentication boundary: the shop value trusted by the handler is not the shop value actually bound by the HMAC. This enables cross-tenant confusion — an attacker in control of one shop's webhook traffic can cause the app to process (and potentially persist/act on) forged webhook content attributed to a victim shop, since the `shop` field is unauthenticated but is the field used to select per-tenant context.

### Likelihood Explanation
Exploitation requires only: (1) installing/operating the app on any one shop (unprivileged relative to other tenants), (2) capturing one legitimate webhook body and its HMAC for that shop, and (3) POSTing it to the app's public webhook endpoint with a modified shop-domain header. No access to `api_secret_key`, access tokens, or other shops' credentials is needed, since the same app secret signs webhooks for all installs.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified signable content, or independently verify that the `shop-domain` header corresponds to a shop with an active installation/session before trusting it as the tenant key in `WebhookMetadata`. At minimum, document and enforce that host apps must re-validate `data.shop` against a known/installed shop list rather than treating it as authenticated purely because HMAC validation passed.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker's own webhook endpoint receives a legitimate webhook, e.g. `orders/create` with raw body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical raw body `B` and identical HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` succeeds because it only checks `B` against the unchanged HMAC [7](#0-6) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [5](#0-4) , and the host app processes attacker-controlled body content as if it originated from `victim-shop.myshopify.com`.
