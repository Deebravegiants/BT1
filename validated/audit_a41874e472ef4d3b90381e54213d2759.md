### Title
GetResponses can be delivered against a state commitment before its challenge period elapses, bypassing the fraud-proof dispute window - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handleGetResponses` dispatches GET responses to destination modules using a state commitment as soon as it exists, without checking that the configured `challengePeriod` has elapsed for that `StateMachineHeight`. Every sibling handler in the same contract (`handlePostRequests`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) enforces this wait.

### Finding Description
The protocol's documented defense against forged/eclipsed state commitments is the challenge window: after a consensus update stores a new `StateCommitment`, relayers must wait `challengePeriod` before using it, giving fishermen time to submit a fraud proof and freeze the host [1](#0-0) . This is enforced consistently in the Substrate ISMP core via `validate_state_machine`, which checks both `is_consensus_client_frozen` and `verify_delay_passed` before request/response/post-timeout handling [2](#0-1) .

On the EVM side, `HandlerV2` mirrors this with an explicit `challengePeriod` check in `handlePostRequests`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts`: [3](#0-2) [4](#0-3) [5](#0-4) 

`handleGetResponses`, however, only applies the `notFrozen` modifier and skips the `challengePeriod`/delay check entirely before verifying the MMR proof and dispatching responses: [6](#0-5) 

This is the same class of bug as the referenced report: one operation (`handlePostRequests`, the "borrow"-equivalent action) is correctly gated on the dispute/manipulation window, while a functionally identical sibling operation (`handleGetResponses`, delivering externally-sourced data) is not, even though both consume the exact same untrusted resource — a freshly-stored `StateCommitment` that has not yet survived its fraud-proof window.

### Impact Explanation
If a byzantine/eclipsed validator set (per the protocol's own threat model of 51%/eclipse/long-range attacks documented in `consensus-proofs.mdx`) gets a forged `StateCommitment` accepted by `handleConsensus`, an attacker can immediately call `handleGetResponses` with a proof against that unvetted commitment — without waiting out the window fishermen need to submit a `FraudProofMessage` and freeze the host. This lets forged GET response data (arbitrary storage values from a forged/eclipsed chain) be delivered to and acted on by destination `IsmpModule`s before the network has any chance to freeze the client, defeating the entire purpose of the challenge period for this message type and enabling unauthorized app actions based on unsound state data.

### Likelihood Explanation
Exploitation requires the attacker to first get a malicious `StateCommitment` accepted (an eclipse/51%/long-range style attack against the consensus client), which is a pre-existing, non-trivial but in-scope threat that the protocol explicitly designs the challenge period to mitigate. Given that pre-condition, exploiting the missing check in `handleGetResponses` is trivial and permissionless — any relayer can call it the instant the commitment is stored, with no additional cost or race condition beyond winning the initial consensus attack.

### Recommendation
Add the same `challengePeriod` delay check used in `handlePostRequests`/`handlePostRequestTimeouts`/`handleGetRequestTimeouts` to `handleGetResponses` before it reads `host.stateMachineCommitment(message.proof.height)` and dispatches responses, e.g.:
```solidity
uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
uint256 challengePeriod = host.challengePeriod();
if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();
```

### Proof of Concept
1. Attacker/byzantine validator set gets a forged/eclipsed header finalized and submits it via `handleConsensus`, which stores a new (unvetted) `StateCommitment` for a counterparty height [7](#0-6) .
2. Within the same block (or shortly after), before `challengePeriod` elapses and before any fisherman can submit a `FraudProofMessage`, attacker calls `handleGetResponses` with a `GetResponseMessage` whose MMR proof verifies against the forged `overlayRoot`.
3. `handleGetResponses` only checks `notFrozen(host)` (line 217) — since the client isn't frozen yet (no time was given for fraud proofs), the call succeeds, and `host.dispatchIncoming(leaf.response, ...)` delivers forged data to the destination module [8](#0-7) .
4. Compare with `handlePostRequests` against the same forged commitment in the same block: it reverts with `ChallengePeriodNotElapsed()` since `delay` is ~0 [9](#0-8) , proving the asymmetry.

    function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 responsesLength = message.responses.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](responsesLength);

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // don't check for timeouts because it's checked on Hyperbridge

            // known request? also serves as source check
            FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
        }

        bytes32 root = host.stateMachineCommitment(message.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, message.proof.multiproof, leaves, message.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // duplicate response?
            if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.response, _msgSender());
        }
    }
