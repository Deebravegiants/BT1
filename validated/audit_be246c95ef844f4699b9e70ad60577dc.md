### Title
LP share-minting math in `process_deposit` uses live, donation-manipulable vault balances with floor rounding and no minimum-LP-output slippage check, enabling a CompoundV2/ERC4626-style share-inflation theft - (File: `program/src/processor.rs`)

### Summary
The external report describes a classic vault/cToken "inflation attack": an attacker manipulates the share-price of a pooled vault by donating underlying tokens directly to the vault (bypassing normal deposit accounting) while holding almost all outstanding shares, then a victim's subsequent deposit is minted a disproportionately small (often rounded-to-zero) number of shares relative to the value they contribute, letting the attacker redeem the inflated pool value. Raydium's constant-product pool exhibits the same structural weakness in `process_deposit`: LP-token minting is computed from the *live* SPL token balances of `amm_coin_vault`/`amm_pc_vault` (read via `unpack_token_account`), not from an internal, deposit-tracked total, and the resulting share calculation uses floor rounding with no caller-supplied minimum-LP-out protection.

### Finding Description
`process_deposit` computes the new LP amount to mint as: [1](#0-0) 

using `total_coin_without_take_pnl`/`total_pc_without_take_pnl`, which are derived directly from the **actual current SPL balances** of the coin/pc vaults: [2](#0-1) 

`Calculator::calc_total_without_take_pnl_no_orderbook` simply subtracts the internal `need_take_pnl_*` counters from the *live* vault amounts, with no comparison against any internally-tracked reserve total: [3](#0-2) 

Because the vaults are ordinary SPL Token accounts owned by the AMM authority PDA, **any account holder can transfer tokens directly into `amm_coin_vault`/`amm_pc_vault` using a plain `spl_token::transfer` instruction**, completely outside the `Deposit` instruction and without touching `amm.lp_amount`. This is the exact "donation" primitive used in the kTAF/CompoundV2 exploit to inflate the exchange rate.

The LP mint math then divides by `amm.lp_amount` (the internal share-total) using floor rounding: [4](#0-3) 

If an attacker first becomes (or remains) the dominant LP holder and drives `amm.lp_amount` down via `Withdraw` — which only enforces `withdraw.amount < amm.lp_amount` (never reaching zero, but able to reach the protocol's minimum floor) — [5](#0-4) 

and then donates tokens directly to the vaults to inflate `total_coin_without_take_pnl`/`total_pc_without_take_pnl` relative to `amm.lp_amount`, any subsequent depositor's `mint_lp_amount` computed by `exchange_token_to_pool` will be rounded down disproportionately — potentially to a negligible fraction of the depositor's fair share — while the depositor's own contributed tokens (`deduct_coin_amount`/`deduct_pc_amount`) are still pulled in full: [6](#0-5) 

Critically, `DepositInstruction` provides **no minimum-LP-output field** to protect the depositor — `other_amount_min` only bounds the *paired token* amount, not the minted LP quantity: [7](#0-6) 

The only backstop is the blanket `mint_lp_amount == 0` revert, which prevents *total* theft-via-zero-mint but does not prevent minting a share that is far smaller than the depositor's fair proportional contribution once the vault balances have been artificially inflated relative to `amm.lp_amount`.

### Impact Explanation
An attacker who holds (or acquires) the dominant share of a pool's outstanding LP supply can donate tokens directly to the vaults to inflate the coin/pc-to-LP ratio, then wait for (or induce) a normal user's `Deposit`. The victim's deposited tokens increase the vault balances but the victim receives an LP allocation rounded down against the inflated ratio, while the attacker's un-diluted LP holdings become redeemable for a share of the combined (donated + victim-deposited) pool value via `Withdraw`. This is a direct theft of user/LP funds — insolvent/unfair pool accounting where value flows from a depositing victim to the LP-share-holding attacker, matching the report's fund-loss class.

### Likelihood Explanation
Exploitation requires the attacker to (a) be able to bring `amm.lp_amount` to a very small value relative to attacker-affordable donation size (achievable by any pool where the attacker is the majority LP, e.g., pools they just created or a low-liquidity pool they can dominate), and (b) have a subsequent depositor interact with the manipulated pool. Both conditions are attacker/economically controllable and require only standard SPL transfers plus the four in-scope instructions (`Initialize2`/`Withdraw`/`Deposit`), with no privileged signer needed. Newly created or thin pools are the most practical targets, similar to how the original kTAF pool had low liquidity.

### Recommendation
- Add an explicit `min_lp_amount_out` parameter to `DepositInstruction` and enforce it in `process_deposit`, so depositors can bound their acceptable share dilution.
- Consider tracking pool reserves via internally maintained state rather than trusting live vault balances for share-math, or reconcile any balance surplus (donations) into the pool's accounted reserves/PNL rather than letting it silently inflate the per-share redemption value for existing LPs only.
- Enforce a stronger minimum-liquidity floor on `amm.lp_amount` relative to vault balances at `Withdraw` time to make ratio manipulation economically impractical (beyond the one-time floor subtracted in `Initialize2`).

### Proof of Concept
1. Attacker creates (or dominates) a pool via `Initialize2`, retaining ~100% of minted LP tokens (`amm.lp_amount` after subtracting the one-time `10^decimals` floor — `program/src/processor.rs:915-917`).
2. Attacker calls `Withdraw` with `amount = amm.lp_amount - 1`, reducing their real LP holdings to the minimum allowed by `withdraw.amount >= amm.lp_amount` check (`program/src/processor.rs:1716-1718`), while retaining the last unit of LP supply.
3. Attacker submits a plain SPL `transfer` instruction sending a large amount of coin/pc tokens directly into `amm_coin_vault`/`amm_pc_vault` (no Raydium instruction involved), inflating `total_coin_without_take_pnl`/`total_pc_without_take_pnl` relative to the now-tiny `amm.lp_amount`.
4. A victim calls `Deposit` with reasonable `max_coin_amount`/`max_pc_amount` for the current price; `deduct_coin_amount`/`deduct_pc_amount` are pulled in full, but `mint_lp_amount = amm.lp_amount * deduct_coin_amount / total_coin_without_take_pnl` (floor) yields a share far smaller than the victim's fair proportional contribution (or reverts if it floors to 0, in which case attacker retries with a smaller donation ratio tuned to leave the victim with 1 unit).
5. Attacker calls `Withdraw` with their retained LP unit(s), redeeming a share of the now-inflated vault (donation + victim deposit) far exceeding what they contributed, profiting at the victim's expense.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }

    pub fn exchange_token_to_pool(
        &self,
        pool_total_amount: u64,
        round_direction: RoundDirection,
    ) -> Option<u64> {
        Some(if round_direction == RoundDirection::Floor {
            U128::from(pool_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_div(self.token_total.into())
                .unwrap()
                .as_u64()

                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_ceil_div(self.token_total.into())
                .unwrap()
                .as_u64()
        })
    }
