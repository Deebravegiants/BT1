This confirms the vulnerability. `HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, which for `Webhooks::Request` returns `@raw_body` alone [1](#0-0) , and `validate_signature` compares that against `verifiable_query.hmac` [2](#0-1) . The `shop` value read from the `x-shopify-shop-domain`/`shopify-shop-domain` header is never included in the signable string and is never passed through `ShopValidator.sanitize!` before `Registry.process` uses it directly to build `WebhookMetadata` [3](#0-2) . Since the same `api_secret_key` is shared by the app across all merchant installs, an attacker who owns their own dev shop can obtain a validly-signed webhook body/HMAC pair and simply resubmit it with a different `X-Shopify-Shop-Domain` header claiming a victim shop — the signature check still passes because it only covers `raw_body`, and the forged `shop` value flows unchecked into the handler.

### Title
Webhook shop attribution is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates the body and topic but never authenticates the `shop` value derived from the `x-shopify-shop-domain`/`shopify-shop-domain` header. `Registry.process` passes `request.shop` straight into `WebhookMetadata` without calling `ShopValidator.sanitize!` or otherwise cross-checking it, so an attacker who owns a legitimate dev shop can replay one of their own validly-signed webhooks against the target app while spoofing the shop-domain header to any victim shop.

### Finding Description
The broken binding: `HMAC-signed bytes (raw_body)` == `bytes the app trusts as belonging to a shop (raw_body + shop header)` is assumed true by `Registry.process`, but is actually false.

Code path:
1. `Request#initialize` parses headers case-insensitively and stores `@raw_body` and `@headers`, requiring only that `topic`, `hmac-sha256`, and `shop-domain` headers be present — it does not validate their values [4](#0-3) .
2. `Request#shop` simply returns the raw header value cast to `String`, with no format/sanitization check [5](#0-4) .
3. `Request#to_signable_string` returns `@raw_body` only, excluding all headers, including `shop` [1](#0-0) .
4. `HmacValidator.validate` -> `validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac`, i.e., it authenticates `raw_body` and the app's `api_secret_key`/`old_api_secret_key`, nothing else [6](#0-5) .
5. `Registry.process` gates on `HmacValidator.validate(request)` and then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` directly from the unauthenticated header value, handing it to the app's handler [3](#0-2) .

Because a single app has one `api_secret_key` shared across every merchant installation, a validly-signed webhook obtained from the attacker's own dev shop is valid HMAC material for any shop under that app. The attacker's request: POST the captured raw body `B` and header `X-Shopify-Hmac-Sha256: H` (both legitimately produced by Shopify for the attacker's own shop) to the target's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`. `HmacValidator.validate` still returns `true` because it only checks `B`/`H` against the secret; `request.shop` returns `"victim-shop.myshopify.com"` unchecked, and the handler receives `WebhookMetadata` attributing forged data to the victim tenant.

No existing guard closes this gap: `ShopValidator.sanitize!` exists in the gem but is never invoked inside `Request` or `Registry.process`; there is no comparison between `request.shop` and any session/install record that the gem itself tracks at webhook-processing time.

### Impact Explanation
Any internet attacker with their own dev-shop install of a victim app can make the app's webhook handler execute with attacker-controlled `body`/`topic` while attributing the event to an arbitrary victim shop domain string, since `shop` is taken from an attacker-controlled header. This is a cross-tenant authentication bypass: the handler trusts `WebhookMetadata#shop` as if it were authenticated by the signature, but it is not. This is repeatable against arbitrary victim shop names (no need to know the victim actually exists as an install, though impact depends on how the host app uses `shop` — e.g., to look up records/tenant data to mutate). This matches "Critical – cross-tenant access" in the given severity taxonomy.

### Likelihood Explanation
Preconditions are minimal and fully within the described attacker capability: register any development shop, install the target app, trigger one real webhook to capture a valid `(raw_body, HMAC)` pair signed with the app's real secret, then replay that exact pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No credentials, no TLS interception, no secrets are required. This is a single crafted HTTP POST, fully repeatable and automatable against any victim shop string.

### Recommendation
Bind `shop` to the HMAC-verified payload rather than trusting the header: either include the shop domain from the header in the signable bytes if Shopify supports it, or — since Shopify's webhook system does not sign headers — cross-check `request.shop` against the calling app's own record of which shop the specific webhook subscription/callback path belongs to (e.g., verify shop against a per-shop callback path, session store, or subscription ID recorded at registration time) before invoking the handler. At minimum, call `ShopValidator.sanitize!` on `request.shop` in `Registry.process`, and document/require that host apps must independently confirm shop identity (e.g., via a shop-specific webhook path) since the HMAC alone does not authenticate the shop.
