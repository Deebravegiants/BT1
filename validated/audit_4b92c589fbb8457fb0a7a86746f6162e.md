### Title
Webhook `shop-domain` header is trusted without being covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers and passed straight through to the app's webhook handler as trusted identity data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that value [2](#0-1) . `HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, to_signable_string)`, i.e., against the body bytes alone [3](#0-2) . `Registry.process` then trusts `request.shop` and forwards it, unverified, into `WebhookMetadata` that is handed to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) . The `shop` field on `WebhookMetadata` is a plain `String` constant with no verification tie to the signature [5](#0-4) .

The binding that should hold is: `bytes_verified_by_hmac == bytes_the_app_treats_as_the_authenticated_tenant_identity`. Here, `bytes_verified_by_hmac = raw_body` while `bytes_the_app_treats_as_the_authenticated_tenant_identity = header["shop-domain"]`, which are disjoint. Any unprivileged internet user who can obtain one legitimate `(raw_body, hmac)` pair for their own shop (e.g., by triggering a webhook to their own app instance, or observing any publicly-reachable webhook payload with a valid signature for that body) can replay that exact body/HMAC pair to a target host application's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` still returns `true` because it only checks the body against the secret, and `Registry.process` will invoke the handler with the attacker-chosen `shop` value.

### Impact Explanation
Any host application whose webhook handler uses `WebhookMetadata#shop` to key data writes, lookups, or authorization decisions (a very common pattern, since `shop` is the documented tenant identifier for webhook processing) can be made to attribute another tenant's legitimately-signed webhook body to an attacker-chosen shop, or attribute an attacker's own webhook to a victim shop domain. This crosses the tenant boundary the gem is supposed to enforce for webhook authenticity, matching the "cross-tenant access" class of impact.

### Likelihood Explanation
Exploitation requires only network access to the target app's webhook endpoint and possession of one valid `(body, hmac)` pair signed with the app's own secret — obtainable by any developer who has installed the same app on their own shop (a normal, unprivileged action) and then captured one of their own genuine webhook deliveries. No access to `api_secret_key`, tokens, or the target's infrastructure is required, and the header can be freely set by any HTTP client. The `shop` header is not otherwise cross-checked by the gem against any known/expected value before being handed to the handler.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable material verified by `HmacValidator`, or at minimum have `Registry.process`/`WebhookMetadata` treat `shop` as untrusted unless independently corroborated (e.g., requiring the host app to supply and compare an expected shop, or documenting explicitly that `shop` must not be trusted without additional verification). Shopify's canonical guidance is that only the body is HMAC-signed for webhooks, so the safer fix is to require/encourage callers to validate `WebhookMetadata#shop` against their own known-shop registry rather than trusting it implicitly, and to make this a documented, enforced contract in `Registry.process` rather than leaving it silent.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker.myshopify.com` and captures a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's secret, and also correctly formatted per `Request#initialize` header checks) [6](#0-5) .
2. Attacker sends a new HTTP request to the same app's webhook endpoint with the identical body `B` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` and any desired `x-shopify-topic`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body` [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process/attribute the webhook data under the wrong tenant.

```ruby
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
