Audit Report

## Title
Cross-User Response Hijack via Global `MessageID` Key in Gateway `savedCallbacks` Map - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
The legacy capabilities gateway handler stores per-request callbacks in `h.savedCallbacks`, keyed solely by the client-supplied `msg.Body.MessageID`, with no binding to the sender's identity and no rejection of duplicate/colliding IDs. If two different clients submit legacy `web_api_trigger` requests using the same `MessageID` while both are in-flight, the second submission silently overwrites the first entry, causing the DON's response intended for the first client to be delivered to the second client instead.

## Finding Description
`HandleLegacyUserMessage` writes unconditionally to the shared map:
```go
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
``` [1](#0-0) 

When a DON node later responds, `handleWebAPITriggerMessage` looks up and deletes the entry purely by `MessageID` and forwards the response to whichever callback currently occupies that slot:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageID]
delete(h.savedCallbacks, msg.Body.MessageID)
...
return savedCb.SendResponse(...)
``` [2](#0-1) 

`MessageID` is entirely client-controlled: for legacy gateway requests it is taken directly from the JSON-RPC request `ID` field supplied by the caller [3](#0-2) , and `Message.Validate`/`Sign` compute `Body.Sender` from the signature but never use it to scope callback storage [4](#0-3) . The signature check in `HandleNodeMessage` only verifies that the DON node's address matches the message's stated sender for node→gateway messages; it does nothing to bind a `savedCallbacks` entry to the original requesting client [5](#0-4) . The code explicitly acknowledges the missing authorization layer with `// TODO: apply allowlist and rate-limiting here` [6](#0-5) .

This is a materially different and weaker design than the `globalID{sender, id}`-keyed cache in `handlers/common/requestcache.go`, which explicitly rejects duplicate in-flight requests [7](#0-6) , and than the newer v2 `httpTriggerHandler`, which explicitly detects and rejects colliding request IDs with an `ErrConflict`/"in-flight request" error [8](#0-7) . The legacy handler in `capabilities/handler.go` has no equivalent protection.

## Impact Explanation
An unprivileged client submitting legacy `web_api_trigger` requests through the gateway can cause cross-user response corruption: if it submits a request with the same `MessageID` as another user's in-flight request, it silently overwrites that user's callback entry and receives the DON's response meant for the victim's request instead. This falls under the gateway request impersonation / cross-user response confusion impact class.

## Likelihood Explanation
The attack is fully reachable by any client permitted to call the gateway's legacy `web_api_trigger` endpoint, requiring no special privileges. `MessageID` is client-chosen input, so the only precondition is that the attacker knows or predicts the victim's exact `MessageID` value while the victim's request is still in-flight (within the default 120-second callback max age). Likelihood is high in scenarios where IDs are non-random, predictable, or coordinated (e.g., colluding parties, or an attacker replaying/observing a victim's ID from another channel); likelihood is low for accidental collision if IDs are high-entropy random values, but the code provides no protection either way.

## Recommendation
Scope `savedCallbacks` (store, lookup, and delete) by both `MessageID` and an authenticated sender identity, mirroring the `globalID{sender, id}` pattern already used in `handlers/common/requestcache.go`. Reject or fail closed on `MessageID` collisions instead of silently overwriting an existing entry, consistent with the duplicate-ID rejection behavior already implemented in the v2 `httpTriggerHandler`.

## Proof of Concept
1. User A signs and submits a legacy `web_api_trigger` message with `MessageID = "X"`; the gateway calls `HandleLegacyUserMessage`, storing A's callback at `savedCallbacks["X"]` and fanning the request out to all DON members.
2. Before any DON node responds, Attacker B signs and submits a legacy `web_api_trigger` message also using `MessageID = "X"`; `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with B's callback.
3. A DON node responds for `MessageID = "X"` (originally A's request). `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's callback, deletes the entry, and delivers A's response payload to B via `SendResponse`.
4. This can be verified as a Go unit test extending `TestHandlerReceiveHTTPMessageFromClient` in `handler_test.go`: call `HandleLegacyUserMessage` twice with two distinct callbacks but the same `MessageID` (signed by two different keys), then call `HandleNodeMessage` with the DON's response and assert that the second callback (not the first) receives the response.

	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}

	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
