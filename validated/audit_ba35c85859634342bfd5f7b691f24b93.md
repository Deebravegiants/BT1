### Title
Unbounded BEEFY signature-vector length drives per-signature ECDSA recovery before membership is checked, enabling relayer-submitted CPU-amplification DoS - (File: modules/consensus/beefy/verifier/src/lib.rs)

### Summary
`verify_mmr_update_proof` in the BEEFY consensus verifier iterates over every entry in `mmr.signed_commitment.signatures` and performs a `secp256k1_recover` + two `keccak256` hashes per entry, *before* the merkle multi-proof that actually validates authority-set membership is checked. The only gate applied ahead of this loop, `check_participation_threshold(signatures_length, authority_set.len)`, is a lower-bound supermajority ratio check (`signatures_length` vs `authority_set.len`), not an upper bound on the absolute size of the vector. Structurally this is the same bug class as GHSA-3prj-6hqw-cm82: an attacker-controlled count taken from the message body is fed directly into a loop of expensive cryptographic work with no cap, and the eventual rejection (bad merkle proof / bad authority indices) happens only after the cost has already been paid.

### Finding Description [1](#0-0) 

The relevant flow:
1. `signatures_length = mmr.signed_commitment.signatures.len()` is read directly from the submitted `ConsensusMessage`/`MmrProof`.
2. `check_participation_threshold(signatures_length as u32, authority_set.len)` only verifies `signatures_length` is *at least* the 2/3+1 supermajority fraction of `authority_set.len` — it can never reject a vector for being too large, only for being too small.
3. Immediately after, the code loops over **every** signature in `mmr.signed_commitment.signatures` and calls `H::secp256k1_recover` (ECDSA public-key recovery) plus two `keccak256` hashes per entry, unconditionally, to build `authority_leaves`/`authority_indices`.
4. Only *after* this full loop completes does the code build/verify the `rs_merkle` multi-proof (`merkle_proof.verify(...)`) that actually determines whether the claimed signers are real, known authorities.

Because nothing bounds `signatures_length` independently of the ratio check, an attacker can submit a `signed_commitment.signatures` vector containing far more entries than the real authority set size (duplicate indices, bogus indices, or garbage signature bytes crafted to still satisfy the ratio check relative to `authority_set.len`, which is public knowledge). Each entry costs a full secp256k1 recovery, which is significantly more expensive than a hash comparison, and the loop runs to completion regardless of validity before the single merkle-proof check that would reject the whole thing fires.

This mirrors the reported bug class precisely: attacker-controlled iteration count → unbounded expensive-crypto loop → rejection happens only after the cost is paid, with no per-item nor absolute-count ceiling enforced before the loop.

### Impact Explanation
This code path is reached by any relayer submitting a BEEFY consensus update (`pallet-beefy-consensus-proofs::submit_proof` → `handle_incoming_message` → `verify_consensus` → `verify_mmr_update_proof`), which is exactly the "consensus verification (BEEFY...)" surface this analog scan is scoped to. A malicious relayer can craft an oversized `signatures` vector that:
- Passes the participation-ratio gate (since the ratio only compares against the known, public `authority_set.len`, an attacker can pad well past the minimum required count while remaining "sufficient").
- Forces the node to perform thousands of secp256k1 recoveries and keccak hashes before the merkle multi-proof check ultimately fails.

If the transaction weight/fee charged for `submit_proof` is benchmarked against a "typical" signature count rather than bound to the actual size of the submitted vector, the attacker pays a fixed/underestimated fee while the validating node burns disproportionate CPU — a CPU-amplification denial of service against block/message processing, degrading availability of BEEFY consensus updates (and therefore message delivery relying on it) for legitimate relayers.

### Likelihood Explanation
Likelihood is moderate: exploitation requires only crafting a `ConsensusMessage` with an inflated `signatures` Vec — no privileged role, no cryptographic breaks, and no cooperation from validators is needed. The only constraints are the outer extrinsic/message size limits and whatever weight is charged for the call, which bound but do not eliminate the amplification unless the weight formula scales precisely with `signatures.len()` and is enforced pre-dispatch.

### Recommendation
Add an explicit upper bound on `mmr.signed_commitment.signatures.len()` before entering the recovery loop — e.g., reject when it exceeds `authority_set.len` (a signature vector can never legitimately be larger than the authority set it draws from) or a fixed protocol maximum. Additionally, reorder verification so authority-index validity/duplication is checked (cheap) before the expensive `secp256k1_recover` is invoked per signature, and ensure the extrinsic's declared weight scales with the actual submitted vector length rather than a fixed/benchmarked average.

### Proof of Concept
Not independently reproduced against a running node in this session (no filesystem/terminal access in ask-only mode); the finding is based on static analysis of the cited functions. A concrete PoC would: build a `ConsensusMessage` whose `mmr.signed_commitment.signatures` contains N >> `authority_set.len` entries (duplicate `index` values or arbitrary signature bytes) such that `check_participation_threshold` still passes, submit it via `pallet-beefy-consensus-proofs::submit_proof`, and measure CPU time consumed in `verify_mmr_update_proof` prior to the merkle-proof rejection, comparing it against the weight/fee charged for the extrinsic.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}

	let mmr_root_data = commitment
		.payload
		.get_raw(&MMR_ROOT_PAYLOAD_ID)
		.ok_or(Error::MmrRootHashMissing)?;

	if mmr_root_data.len() != 32 {
		return Err(Error::InvalidMmrRootHashLength { len: mmr_root_data.len() });
	}
	let mmr_root = H256::from_slice(mmr_root_data);

	let commitment_hash = H::keccak256(&commitment.encode());
	let mut authority_leaves: Vec<[u8; 32]> = Vec::new();
	let mut authority_indices = Vec::new();

	for sig in mmr.signed_commitment.signatures.iter() {
		let uncompressed = H::secp256k1_recover(&commitment_hash.0, &sig.signature)
			.map_err(|_| Error::FailedToRecoverPublicKey)?;

		let hashed_uncompressed = H::keccak256(&uncompressed);

		let mut eth_address = [0u8; 20];
		eth_address.copy_from_slice(&hashed_uncompressed.as_ref()[12..]);

		let authority_address_hash = H::keccak256(&eth_address);

		authority_leaves.push(authority_address_hash.into());
		authority_indices.push(sig.index as usize);
	}

	let merkle_proof = MerkleProof::<MerkleHasher<H>>::new(mmr.authority_proof.clone());

	let valid = merkle_proof.verify(
		authority_set.keyset_commitment.into(),
		&authority_indices,
		&authority_leaves,
		authority_set.len as usize,
	);

	if !valid {
		Err(Error::InvalidAuthoritiesProof)?;
	}
