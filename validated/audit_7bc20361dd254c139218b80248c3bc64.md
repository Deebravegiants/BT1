### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator.validate` only covers the raw request body (`to_signable_string` returns `@raw_body`). The header used to attribute a webhook to a specific tenant is never part of the signed bytes, so a request whose body+HMAC pair is legitimate for one shop can be replayed with a forged `shop-domain` header and will still pass verification.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by calling: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is only the raw body, and `hmac` is decoded solely from the `hmac-sha256` header — the `shop` value is not part of the signed string at all: [3](#0-2) 

After successful HMAC validation, `process` passes `request.shop` — an unauthenticated field — straight into `WebhookMetadata` used by the host application's handler to attribute the webhook data to a tenant: [4](#0-3) 

This is the exact identity-binding break called out by the report's bug class: an accounted/acted-upon field (`shop`) is not covered by the HMAC that is supposed to authenticate the whole request. The equality that should hold — `bytes verified by HMAC == bytes the handler uses to identify the tenant` — does not hold, because `shop` is read from an unsigned header while only the body is signed.

### Impact Explanation
Because the same app `client_secret`/HMAC key is shared across every shop that installs the app, any attacker who is themselves a merchant/user of the app can trigger a legitimate webhook to their own shop, capture the valid `(raw_body, hmac)` pair from that delivery, and replay the identical body+HMAC to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` will still accept it since the shop header plays no role in the signature, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the payload belongs to the victim shop. Any host application that trusts `request.shop`/`WebhookMetadata#shop` (as the documented usage pattern instructs) to key its per-tenant data store will ingest/attribute attacker-controlled (replayed) data under another tenant's identity — a cross-tenant data-integrity/access break.

### Likelihood Explanation
Exploitation requires only that the attacker be an ordinary, unprivileged installer of the target app (a normal merchant), able to receive one legitimate webhook to their own store and replay it with a rewritten header value — no access to `api_secret_key`, tokens, or privileged accounts is needed, satisfying the "unprivileged internet user" constraint. The gem's documented usage pattern (`docs/usage/webhooks.md`) directly forwards `request.shop`/`WebhookMetadata#shop` to the host app without any additional binding, making the unsafe pattern the expected one.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signed string (`to_signable_string`), or otherwise cryptographically bind them to the body so verification fails if any of these headers are altered. At minimum, document prominently that `request.shop` is unauthenticated and must be cross-checked by the host application against its own registered-shop list before use.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`).
2. Attacker captures the exact raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent for that delivery.
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks the body, ignoring the forged shop header (`lib/shopify_api/webhooks/request.rb:10-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and the host app processes/stores the attacker's replayed data as if it came from the victim tenant.
