### Title
Webhook `shop` field is trusted from an unauthenticated header and not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. Any request whose body/HMAC pair is legitimately obtained (e.g. from a webhook delivered to the attacker's own shop) can be replayed with a different `shop-domain` header value, and the webhook will still pass HMAC validation while `Registry.process` dispatches the payload to the handler tagged with the attacker-chosen shop.

### Finding Description
The identity binding that should hold is:
`HMAC-authenticated shop == shop value used by the webhook handler`

In `lib/shopify_api/webhooks/request.rb`, `shop` is read directly from headers with no cryptographic binding: [1](#0-0) 

The value used for HMAC verification (`to_signable_string`) is only the raw JSON body, and does not include the `shop` (or `topic`, or `webhook-id`) header at all: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC purely against this signable string: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately forwards `request.shop` (the unauthenticated header value) to the app's handler as the tenant identifier, with no additional check that it matches the shop the body was actually signed for: [4](#0-3) 

By contrast, the OAuth callback path (`Auth::Oauth::AuthQuery`) does the identity binding correctly: `shop` is explicitly included in `to_signable_string`, so it cannot be swapped without invalidating the HMAC: [5](#0-4) 

This asymmetry shows the webhook path is the vulnerable analog: the HMAC only proves "this body was signed with the app's secret," not "this body belongs to shop X." Since all shops installing a given app share the same `api_secret_key`, a body+HMAC pair that is valid for shop A's webhook is equally valid (HMAC-wise) when replayed with shop B's domain in the header, because the header is never part of the signed content.

### Impact Explanation
An attacker who installs the target app on their own (attacker-controlled) shop can trigger and capture legitimately-signed webhook deliveries (body + valid `x-shopify-hmac-sha256`) from Shopify. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspected the shop header), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain instead of the attacker's own. Any host application that uses this `shop` field to look up tenant records, write data, or trigger tenant-scoped side effects (order processing, GDPR data actions, billing, etc.) can be made to associate attacker-supplied payload content with a different tenant — a cross-tenant data confusion/injection primitive reachable by any unprivileged internet user who can install the app once.

### Likelihood Explanation
Moderate-to-high: the only prerequisite is the ability to install the target app on an attacker-controlled development/test store (a normal, unprivileged action for any Shopify developer) to obtain one valid signed webhook body, plus the ability to POST directly to the app's public webhook endpoint (which is inherently internet-reachable, unauthenticated by design apart from the HMAC). No access to `api_secret_key`, tokens, or any privileged account is required.

### Recommendation
Bind the shop domain (and ideally topic/webhook-id) into the value that is HMAC-verified, or independently verify that the `shop` header corresponds to a shop that has legitimately installed/authorized the app (e.g., cross-check against stored sessions) before dispatching to the handler, mirroring the approach already used in `Auth::Oauth::AuthQuery#to_signable_string` where `shop` is part of the signed content.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw request: body `B`, header `x-shopify-hmac-sha256: H` (valid, since Shopify signed it with the app's `api_secret_key`).
2. POST the same body `B` and header `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com`; `Utils::HmacValidator.validate` succeeds because `to_signable_string` is only `B`, unaffected by the header change.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled data under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
