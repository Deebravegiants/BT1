## Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) headers are trusted without being covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, `webhook-id`, and `api-version` values taken from HTTP headers - none of which are covered by that signature - and forwards them to the app's handler as the identity of the originating shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers, independent of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately hands `request.shop` (and the other header-derived fields) to the registered handler without any further binding check: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the raw body only) and compares it to the `hmac` header value: [4](#0-3) 

This is exactly the bug class from the report generalized to an identity-binding break: "a field acted on (`shop`) but not covered by the HMAC." The equality that should hold is:
`hmac-authenticated shop == shop attributed to the event by the handler`
but the code only proves `hmac-authenticated raw_body == raw_body`, and separately trusts an unauthenticated `x-shopify-shop-domain` header as the shop identity.

### Impact Explanation
An unprivileged attacker who installs the app on their **own** shop receives genuine webhooks for that shop, each consisting of a raw body and a valid HMAC computed with the app's `client_secret` over that body only. Because the signature does not bind the body to the `shop` header, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain the attacker does not control. `HmacValidator.validate` still succeeds (it only checks the body/HMAC pair), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the spoofed victim domain. Any app logic that uses `data.shop` to look up a tenant record, update per-shop state, or make authorization decisions will act as though the event originated from the victim's shop - a cross-tenant data integrity/confidentiality break using only the attacker's own legitimately-issued webhook material.

### Likelihood Explanation
Any developer/merchant can install the target app on a shop they control at no cost, capture a legitimate webhook payload plus its HMAC, and replay it with a modified `shop` header via a simple HTTP request. No secrets, tokens, or privileged access are required beyond running a normal (attacker-owned) shop - this is reachable by any unprivileged internet user who can install the app once.

### Recommendation
Bind the shop (and other trust-sensitive fields such as topic/webhook-id) into the value that is actually authenticated: either include the `x-shopify-shop-domain` (and other Shopify-supplied identity headers) in the HMAC-signed material verified server-side, or cross-check the header-derived `shop` against a shop already known/authorized for the given `webhook_id`/topic combination (e.g. via a prior registration record) before invoking handlers. At minimum, document and enforce that `WebhookMetadata#shop` must not be trusted for authorization decisions unless independently verified.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app registers for (e.g. `orders/create`).
2. Capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent for that webhook.
3. Replay the identical body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate`, which passes because only the raw body is checked (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` and processes/attributes the attacker's own webhook data as if it came from `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
