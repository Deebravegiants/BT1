### Title
Pool `repay`/`recapitalize` refund is computed from the declared amount, not measured receipts, letting an unfunded call drain pool custody - (File: contracts/pool/src/ops/repay.rs)

### Summary
The Linux bug class is a resource leak on an error/handoff branch: memory is freed (released) on a path where ownership accounting doesn't match reality. The analog in XOXNO Lending is the pool's refund legs, which "release" tokens back to the payer based on a **declared** inbound `amount` inside `PoolAction`, not on balance actually received. Both `ops::repay::apply` (overpayment above debt) and `ops::recapitalize::apply` (excess above the backing shortfall) call `transfer_out(payer, refund)` without debiting `cash` or checking `require_reserves`, so a call that was never funded still pays real custody out. The pool's own test suite pins this behavior: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` documents that a repay on a market with zero debt makes the whole declared amount "overpayment" and refunds it out of real custody with the book untouched.

### Finding Description
In `contracts/pool/src/ops/repay.rs`, `accounting` resolves `action.amount` into `(burned, overpayment)` via `cache.resolve_repay`; when `current_debt_ceil` is zero the full amount becomes `overpayment`, `net_repay` is `0`, the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct, and `apply` executes `cache.transfer_out(payer, overpayment)`. Nothing in this leg verifies that `amount` tokens were actually transferred into the pool — the controller's normal flow pre-funds the pool (`The controller transfers the repay amount into the pool before this call`), but that invariant is enforced by convention, not by the pool. `ops/recapitalize.rs` has the same shape: `applied = amount.min(backing_shortfall)`, `refund = amount - applied`, then `transfer_out(payer, refund)`, again with no receipt measurement (`refund` is derived purely from the declared `amount`). The pool tests at `contracts/pool/tests/flows.rs:3578-3611` explicitly acknowledge the gap: "Neither refund debits `cash` or passes `require_reserves`," and demonstrate custody being drained by an unfunded `repay` call with a fabricated `PoolAction`.

### Impact Explanation
If the pool's `repay`/`recapitalize` entrypoints can be reached without the controller pre-funding (the pinned test invokes `client().repay(&payer, …)` directly with a fabricated action and custody is drained), an unprivileged address declares `amount = pool_balance` on a zero-debt market and receives `transfer_out(payer, pool_balance)` — direct theft of supplier funds / protocol insolvency, which satisfies the acceptance criteria. Even if only reachable through the controller, any controller path that issues a repay/recapitalize action whose declared amount exceeds the measured pool receipt (e.g., a fee-on-transfer or deflationary debt token where the pool receives less than `action.amount`) has the pool refund `amount - applied` out of custody while only `applied` was credited — silently leaking reserves. (Caveat: I could not confirm within available context whether the pool leg gates the caller to the controller address; the test harness calls it unauthenticated, which suggests it does not, but this should be verified against `contracts/pool/src/lib.rs` auth checks.)

### Likelihood Explanation
The vulnerable code path is deterministic and requires no price manipulation, oracle drift, or timing: an attacker only needs to submit a `repay` action with `amount > 0` against a market with no outstanding debt (or `recapitalize` with `amount > backing_shortfall`). Every refund branch is reached on the first call. Likelihood is bounded only by whether the leg is externally callable or reachable through an unfunded controller path — the refund computation itself contains no guard.

### Recommendation
Measure receipts instead of trusting the declared amount. In `ops::repay::apply` and `ops::recapitalize::apply`, snapshot the pool's token balance before accounting (or have the controller's settle call pass the measured delta, as `transfer_amount_measured` already does elsewhere) and cap `refund`/`overpayment` at `min(declared_refund, measured_inflow)`. Alternatively, treat the refund like every other outflow: debit `cash` by the refund or run `require_reserves` after the transfer, so an unfunded refund reverts instead of paying out of suppliers' custody.

### Proof of Concept
1. Deploy pool with a (hub, token) market holding supplier custody `C` and zero debt.
2. Attacker calls the pool `repay` leg directly with `payer = attacker` and a `PoolAction` carrying `amount = C` (no tokens transferred in).
3. `resolve_repay` takes the full-close branch: `overpayment = C`, `net_repay = 0`, `burned = 0`; the `net_repay == 0` disjunct lets `RepayRoundsToZeroShares` pass.
4. `apply` executes `transfer_out(attacker, C)` — pool custody is drained while `cash`, `borrowed`, and indexes are unchanged, leaving suppliers with book claims on an empty pool. This is exactly what `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (contracts/pool/tests/flows.rs:3590-3611) demonstrates end-to-end.

Key code references: `accounting`/`apply` in `contracts/pool/src/ops/repay.rs:25-67`, the declared-amount refund in `contracts/pool/src/ops/recapitalize.rs:44-67`, and the acknowledging test in `contracts/pool/tests/flows.rs:3578-3611`.
