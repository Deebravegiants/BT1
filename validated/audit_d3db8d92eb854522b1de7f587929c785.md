### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body for HMAC verification, while the `shop` domain used to identify the tenant is read from an HTTP header that is entirely excluded from that signature. Any request whose body+HMAC pair is valid for the app's `api_secret_key` (e.g., a genuine webhook the attacker's own shop legitimately receives) will pass `Utils::HmacValidator.validate`, and the attacker can freely set the `shop-domain` header to any other merchant's domain.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight out of the `shop-domain` header without any cross-check against the signed payload [2](#0-1) . `Registry.process` verifies only `HmacValidator.validate(request)` (which checks the body signature) and then forwards `request.shop` straight into `WebhookMetadata` handed to the app's handler, with no comparison to any value bound by the HMAC [3](#0-2) .

This reproduces the report's bug class exactly: a field that is *acted upon* (the tenant-identifying `shop`) is *not covered* by the authentication mechanism (the HMAC), so the equality the code implicitly assumes —
`shop_used_by_handler == shop_that_actually_sent_the_signed_body`
— does not hold. The HMAC only proves "this body was produced with the app's secret"; it proves nothing about which shop header should accompany that body.

Because `api_secret_key` is a single value shared by the app across every shop that installs it, an attacker who installs the same app on their own store receives their own genuine webhooks — valid `raw_body` + valid `X-Shopify-Hmac-Sha256` for the app's secret. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain.

The gem's own documentation instructs developers to trust `data.shop` directly as the tenant identifier (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) and states that `Registry.process` "will verify the request did indeed come from Shopify" [4](#0-3)  — implying the whole request, including the shop identity, is authenticated, when in fact only the body bytes are. This is a design flaw in the gem's own verification contract, not a misuse of it.

### Impact Explanation
This is a cross-tenant identity-binding break: an app following the gem's documented pattern will attribute attacker-controlled webhook data to an arbitrary victim shop of the attacker's choosing. Downstream, apps commonly use `data.shop` to look up the victim's stored session/access token to react to the "event" (e.g., enqueue background jobs, invalidate data, trigger sync tasks) — allowing attacker-controlled input to be processed under the victim tenant's identity, i.e., cross-tenant access, which is a Critical-impact category per the assessment rules.

### Likelihood Explanation
The forgery requires only a body+HMAC pair that is valid for the app's shared secret — trivially obtainable by any unprivileged internet user who installs the app on their own (attacker-controlled) shop and captures one of their own real webhook deliveries. No access token, `client_secret`, or privileged access is needed; only replaying an intercepted HTTP request with one header changed.

### Recommendation
Bind the `shop` domain (and ideally `topic`/`webhook-id`) into the HMAC-signed material, or otherwise independently authenticate the shop identity before dispatching to handlers — e.g., include the `shopify-shop-domain` header value in `to_signable_string`, or require callers to supply/verify the expected shop out-of-band (matching it against the shop tied to the registered webhook subscription) rather than trusting the raw header.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers/receives a real webhook (e.g. `orders/create`), capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC_SHA256(api_secret_key, B)`, and `api_secret_key` is the same for all shops using the app).
2. Attacker replays the request to the victim app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B) == H` [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and `body:` attacker-controlled JSON, and the app processes it as if Shopify legitimately reported this event for the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
