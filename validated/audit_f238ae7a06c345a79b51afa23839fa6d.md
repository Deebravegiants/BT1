### Title
Webhook shop attribution is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity using an HMAC computed only over the raw request body, but the `shop` value used to attribute the webhook to a specific merchant tenant is read from an HTTP header that is completely outside the scope of that HMAC. This breaks the identity binding `shop covered-by-HMAC == shop used-by-handler`, analogous to the reported bug class where a value used downstream doesn't match the value that was actually protected/verified.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the signature from `to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a request as fully authenticated once the HMAC check passes, then forwards `request.shop` — the unverified header — straight to the app's webhook handler as the tenant identifier: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is shared across every merchant that installs the app (it is not per-shop), any merchant who has legitimately installed the app can capture one of their own genuine, validly-signed webhook deliveries (valid `body` + valid `hmac` for that body, since the HMAC is computed with the app-wide secret, not a shop-specific one). That attacker-merchant can then replay the identical `body`/`hmac` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` will still succeed (it never looks at the shop header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop: [5](#0-4) 

Any app logic that uses `WebhookMetadata#shop` to select which tenant's records to read, write, or delete (a normal pattern, since mandatory webhooks like `shop/redact` and `customers/redact` exist specifically to act on a shop's data) will act on the wrong tenant, entirely under attacker control of the body content.

### Impact Explanation
This crosses a tenant boundary using only data the attacker already legitimately possesses (their own webhook payload/HMAC pair) plus a header they fully control. The result is cross-tenant data corruption/injection: attacker-chosen webhook body content gets attributed to and processed against a shop the attacker does not control. Per the report's severity classification, cross-tenant access qualifies as Critical impact.

### Likelihood Explanation
Exploitation requires only that the attacker be (or briefly become) a legitimate installer of the target app — a low bar for any public app — and the ability to send an HTTP POST with a chosen header to the app's known webhook endpoint. No secret material beyond what the attacker already legitimately has access to (their own signed webhook) is required.

### Recommendation
Bind the shop identity into the verified signature space rather than trusting the header alone:
- Include the shop domain (and ideally topic/webhook-id) in the signed payload used for HMAC verification, or
- Cross-check `request.shop` against an independently authenticated source (e.g., the shop associated with the session/access token that was used to register the webhook subscription, tracked server-side per webhook id) before invoking the handler, or
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must never be used alone to scope tenant-affecting operations without an additional authoritative check.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (a normal, legitimate installation).
2. Trigger any webhook topic the app subscribes to (e.g., `orders/create`) so Shopify delivers a webhook with:
   - Header `x-shopify-hmac-sha256: <valid HMAC of body B computed with the app's shared api_secret_key>`
   - Header `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body `B` (attacker-controlled content, since attacker owns the shop generating the event).
3. Capture `B` and the resulting `hmac` header value.
4. Replay an HTTP POST to the app's webhook endpoint with the same `B` and same `hmac`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) succeeds because it only checks `B` against the HMAC.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, so the app processes attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.
