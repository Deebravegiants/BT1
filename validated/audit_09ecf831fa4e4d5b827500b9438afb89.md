### Title
Router.sell/`_computeSell` can permanently freeze traders out of selling due to accumulated K-slack drift - (File: packages/contracts/src/Router.sol)

### Summary
`Router._computeSell` computes `assetOut = reserveAsset - (k / newReserveToken)` as an unchecked Solidity 0.8 subtraction. `k` is a constant set once at `Pair.mint` and never updated [1](#0-0) , while `Pair.swap` only enforces the *loosened* invariant `(newTokenReserve+1)*(newAssetReserve+1) >= k` rather than the exact product `>= k` [2](#0-1) . Every `sell` sets `newAssetReserve = floor(k / newReserveToken)`, which is `<= k / newReserveToken`, so the true reserve product `newReserveToken * newReserveAsset` can end up strictly less than `k` after each sell — this is exactly the "+1 K slack" flagged in the repo's own risk notes. Over repeated sells this rounding loss (drift) accumulates in the reserves. Once the accumulated drift exceeds the pair's `reserveAsset`, the very next `sell` call — by any trader — computes `k / newReserveToken > reserveAsset` and the subtraction `reserveAsset - (k / newReserveToken)` underflows and reverts, exactly analogous to the reported `Vault.sol#L195` issue (`amountToProtocol > currentBalance` reverting the same class of unchecked subtraction).

### Finding Description
- `Pair.mint` fixes `k = tokenReserve * assetReserve` once and it is never recalculated after that [1](#0-0) .
- `Router._computeSell` (called by every curve `sell`) computes:
```solidity
uint256 newReserveToken = reserveToken + amountIn;
assetOut = reserveAsset - (k / newReserveToken);
``` [3](#0-2) 
- After executing, `Pair.swap` updates reserves and only checks the loosened invariant `(newTokenReserve + 1) * (newAssetReserve + 1) >= k` [2](#0-1) , which tolerates the exact reserve product falling below `k` by up to `newTokenReserve + newAssetReserve` per call.
- Because `assetOut` is floor-divided, `newAssetReserve = floor(k/newReserveToken) <= k/newReserveToken`, so `newReserveToken * newAssetReserve <= k` — every sell can only shrink the true product relative to the fixed `k`, never grow it back (unlike buys, where `Router._computeBuy`'s floor-rounding of `tokensOut` biases the product upward instead) [4](#0-3) .
- The per-call rounding loss is `k mod newReserveToken`, which is bounded only by `newReserveToken - 1`. Given `tokenReserve` is a virtual reserve seeded at `TOTAL_SUPPLY` (1e27) [5](#0-4)  while `reserveAsset` (the real/virtual LT amount) is orders of magnitude smaller (curve opens at ~$3K market cap and graduates around $9K of raised LT) [6](#0-5) , a single (or a handful of) adversarially-sized `sell` calls can accumulate rounding drift that is large relative to `reserveAsset`.
- Once drift `D = k - (reserveToken * reserveAsset)` exceeds `reserveAsset * amountIn` for any subsequent sell amount, `k / newReserveToken > reserveAsset`, and `_computeSell`'s subtraction underflows, reverting every future `sell` (via `Bonding.sell` → `Zap.sell`) until enough curve buys (which are structurally biased to restore product headroom) push `reserveAsset` back up.

### Impact Explanation
This is a denial-of-service on the sell side of the bonding curve: legitimate traders (and the `Zap.sell` → `triggerGraduation` fallback path) cannot exit their position via `sell`/`Zap.sell` while the curve is in this state, effectively freezing trader funds on the curve until a large enough buy arrives to restore headroom — with no guarantee such a buy occurs before the token is meant to graduate. Reachable by any unprivileged trader simply calling `Zap.sell`/`Bonding.sell` in sequence with sizes they can compute from the pair's public `getReserves()`/`k()`, no privileged role required.

### Likelihood Explanation
Medium-High. The math only requires ordinary sell calls with the drift-maximizing size at each step (`amountIn` chosen so `newReserveToken` divides `k` unevenly with maximal remainder) — computable off-chain from `Pair.getReserves()` and `Pair.k()`, both public. No governance/oracle manipulation needed; the virtual-reserve design that makes `tokenReserve >> reserveAsset` makes the worst-case per-call rounding loss (`< newReserveToken`) large relative to `reserveAsset`, so a small number of transactions likely suffice.

### Recommendation
In `Router._computeSell` (and symmetrically consider `_computeBuy`), guard the subtraction: if `k / newReserveToken >= reserveAsset`, either cap `assetOut` at `reserveAsset` (mirroring the overflow-cap treatment already used on the buy side in `_computeBuy`) or clamp to zero instead of reverting, and align `Pair.swap`'s invariant check with the exact (non-`+1`-slack) product so reserves never actually drift below `k` in the first place.

### Proof of Concept
1. Launch a token; note `Pair.getReserves()` → `(tokenReserve, reserveAsset)` and `Pair.k()`.
2. Repeatedly call `Zap.sell`/`Bonding.sell` with `amountIn` values chosen (from the public reserves/k) to maximize `k mod (tokenReserve + amountIn)` each call, accumulating drift `D = k - tokenReserve*reserveAsset`.
3. Once `D` exceeds `reserveAsset`, submit any further `sell` with `amountIn ≥ 1`; `Router._computeSell` computes `k / newReserveToken > reserveAsset`, and `assetOut = reserveAsset - (k/newReserveToken)` reverts with a Solidity Panic (arithmetic underflow), bricking `sell` for all traders on that curve until an offsetting buy restores enough `reserveAsset`.

*Note: I could not execute this against the test suite (no tool access to run Foundry), so the magnitude of drift achievable in a small number of transactions is derived analytically from the reserve/`k` relationship rather than empirically confirmed — a Devin session with repo/test access should verify the exact number of transactions and gas cost needed to trigger the revert in practice.*

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
