## Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) values are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's webhook handler directly from HTTP headers, but `Utils::HmacValidator` only verifies the raw request **body** against the app's `client_secret`. None of these header-derived fields are bound to (i.e., included in) the signed bytes, so anyone who can send an HTTP request to the app's public webhook endpoint with a *previously observed valid `(raw_body, hmac)` pair* can freely rewrite the `shop-domain` header to impersonate a different, unrelated tenant.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the provided `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body — headers are excluded entirely from the signed material: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controlled HTTP headers with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` validates only the body HMAC, then dispatches to the handler using the unauthenticated `request.shop` header value as the tenant identifier: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:

`shop_authenticated_by_hmac(raw_body) == shop_used_for_tenant_dispatch(headers["shopify-shop-domain"])`

Because the HMAC is computed only over `@raw_body` and the app's `client_secret` is shared across *all* installed shops for that app, any attacker who can obtain one legitimate `(raw_body, hmac)` pair (e.g., from a webhook the app sent to their own shop after installing the app — an unprivileged, self-service action) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) header to name a *different* victim shop. `HmacValidator.validate` will still return `true` because it never inspects the headers, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop.

### Impact Explanation
This crosses a tenant boundary using only the app's own webhook endpoint and no access token, `client_secret`, or privileged account — it lets one shop's attacker-controlled webhook payload be attributed to and processed as if it came from a different (victim) shop. Depending on how the host application uses `WebhookMetadata.shop` (e.g., to look up per-shop state, trigger `shop/redact` style actions, or route data into per-tenant records), this enables cross-tenant data corruption/injection, which matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any unprivileged internet user who can install the target app (even as a personal/dev store) can capture one legitimate `(raw_body, hmac-sha256)` pair from a real webhook delivery to their own shop, since nothing about the HMAC depends on the shop identity. They can then replay that exact body+HMAC to the app's public webhook URL with a forged `X-Shopify-Shop-Domain` header naming any other shop. No secrets, TLS interception, or social engineering are required — only that the webhook endpoint is reachable, which it is by design.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed material verified by the HMAC (Shopify's actual webhook HMAC is computed over the raw body only by design, so this must be mitigated at the validation layer instead): require that the app independently confirms the `shop-domain` header corresponds to a shop for which a session/webhook was actually registered before trusting it, and/or reject webhook requests where the recomputed HMAC was already seen for a different shop/topic pair (replay detection keyed on webhook_id). At minimum, document prominently that `WebhookMetadata.shop`/`topic` are unauthenticated relative to the HMAC and must not be used as the sole tenant-routing key without additional verification (e.g., cross-checking against a shop that has an active, previously-established session).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering a legitimate webhook delivery, e.g. for `orders/create`. They capture the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header value from that request.
2. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with:
   - Same `raw_body` (unchanged)
   - Same `X-Shopify-Hmac-Sha256` value (unchanged — still valid, since HMAC only covers `raw_body`)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic` / `X-Shopify-Webhook-Id` set to whatever the attacker wants
3. `Utils::HmacValidator.validate(request)` returns `true` because `Request#to_signable_string` never includes the headers: [5](#0-4) 
4. `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, letting the attacker's own webhook body be processed as belonging to `victim-shop.myshopify.com`: [6](#0-5)

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
