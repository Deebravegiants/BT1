### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (and `topic`) values used to route/process a webhook are read from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only proves that the *body* was signed by Shopify with the app's `api_secret_key` — it proves nothing about which shop the header claims the webhook came from. This breaks the identity binding: `hmac_valid(body) == true` should imply `shop_header == shop_that_signed_the_body`, but the code lets `shop_header` be attacker-controlled independent of the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes: [1](#0-0) 

`hmac` is computed from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header, and `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header. But `to_signable_string`, which is what gets fed into HMAC verification, returns only `@raw_body` — it never includes `shop`, `topic`, or any other header.

`Utils::HmacValidator.validate` verifies exactly this signable string: [2](#0-1) 

and `Registry.process` trusts `request.shop` (taken straight from the unauthenticated header) once that check passes, forwarding it to the handler as the tenant identifier: [3](#0-2) 

Because Shopify signs `HMAC(body, secret)` and this value is deterministic for a given body/secret, and the secret is shared across all shops installing the same app, any webhook payload legitimately delivered to the app for **shop A** (which an attacker can obtain simply by owning/controlling shop A and observing traffic to their own configured endpoint, or from any webhook whose body content the attacker can otherwise predict/reuse) carries a valid HMAC that is completely independent of the `shop-domain` header. An attacker who operates their own Shopify store (an "unprivileged internet user" who is a merchant of the target app) can:
1. Install the app on their own shop A, capture a real webhook request (raw body + valid `X-Shopify-Hmac-Sha256`).
2. Replay that exact body/HMAC pair directly to the app's public webhook endpoint, but substitute `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` still returns `true` (it only checks the body), so `Registry.process` executes the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`.

The equality that should hold — `authenticated_signer(shop-domain-header) == shop_that_the_HMAC_actually_binds_to` — does not, because the shop-domain header is never part of the signed content.

### Impact Explanation
This is a cross-tenant identity-binding failure: a value trusted as the tenant identifier (`shop`) for dispatching webhook side effects (data updates, GDPR redaction, uninstall cleanup, order/customer processing, etc., depending on what the host app's webhook handlers do with `data.shop`) is not authenticated by the HMAC that is supposed to prove Shopify's origin. This lets one merchant (an unprivileged actor relative to other merchants) forge webhook events that the app attributes to a different, victim shop, which is a cross-tenant access primitive.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate merchant of the target app (to obtain one valid body/HMAC pair) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — both are within reach of an unprivileged internet user and require no leaked secrets, TLS interception, or privileged access.

### Recommendation
Include the `shop` (and ideally `topic`) values in the signable content used for HMAC verification, or otherwise cryptographically bind the shop-domain header to the payload before trusting it (e.g., verify the shop against a previously-established session/access-token record rather than trusting the header on its own). At minimum, document/enforce that `request.shop` must be cross-checked against a known, already-authorized shop for that webhook `topic`/subscription before being used to drive tenant-scoped side effects.

### Proof of Concept
1. App owner installs the shopify_api-based webhook handler that runs `ShopifyAPI::Webhooks::Registry.process(request)`.
2. Attacker registers/owns shop `attacker.myshopify.com`, triggers any webhook topic the app subscribes to, and captures the raw POST body `B` and its header `X-Shopify-Hmac-Sha256: H` (a legitimate signature since Shopify signed it for the attacker's own shop).
3. Attacker sends a new HTTP POST directly to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), `X-Shopify-Topic:` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds a request whose `to_signable_string` is `B`; `Utils::HmacValidator.validate` recomputes `HMAC(B, api_secret_key)` and compares it to `H` — this matches because `B` and `H` are unchanged.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, even though the actual signer/source shop was `attacker.myshopify.com`.
