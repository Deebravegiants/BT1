### Title
Unbounded length-prefixed allocation in `EventReader::poll_stream` allows remote DoS of the livestream agent - ([File: src/agents/livestream/upstream.rs])

### Summary
`EventReader::poll_stream` reads a 4-byte big-endian length prefix from the TCP stream on port 9201 and immediately allocates `self.buf = vec![0; u32::from_be_bytes(self.len) as usize]` with no upper-bound check before any `livestream_event::Event` deserialization or validation occurs. A remote attacker who can reach port 9201 can send `u32::MAX` (~4 GiB) as the length prefix, forcing a huge allocation on the `livestream` agent's dedicated thread.

### Finding Description
`Upstream::new` binds a `TcpListener` on `0.0.0.0:9201` [1](#0-0) . When a connection is accepted, `poll_stream` first reads 4 bytes into `self.len`, and as soon as `len_read == 4` it allocates `self.buf = vec![0; u32::from_be_bytes(self.len) as usize]` with no bound check [2](#0-1) . Only after the full buffer is filled does the code call `rkyv::from_bytes(&bytes)` to deserialize into `livestream_event::Event` values [3](#0-2) , so validation happens strictly after the allocation, not before it. This `Upstream` stream is driven inside the `livestream` agent's dedicated OS thread (`agentwire::agent::Thread::run`), which runs its own single-threaded tokio runtime and polls `upstream.poll_next_unpin` in a loop alongside `port.poll_next_unpin` for `Input` messages such as `Input::Clear`, `Input::Phase`, and camera frames [4](#0-3) .

### Impact Explanation
A crafted 4-byte length prefix of `u32::MAX` causes a ~4 GiB `Vec<u8>` allocation attempt on the livestream agent thread. Depending on available memory this can trigger an allocator abort/OOM kill of the orb-core process or a large stall while the allocation is serviced, blocking the agent's event loop that also processes `Input` messages (e.g., `Input::Clear`, `Input::Phase`) used to reset/update the livestream overlay between signup sessions. This matches a bounty-relevant availability/DoS impact against the livestream/observability agent, but it is confined to the `livestream` agent thread/process behavior — it does not directly grant unauthorized signup, wrong-identity binding, biometric disclosure, or attestation forgery.

### Likelihood Explanation
Precondition is simply reachability of TCP port 9201, which the code binds on `0.0.0.0` with no authentication of the connecting client before length-prefix parsing [5](#0-4) . The exploit requires only `connect` + send 4 bytes, making it trivially repeatable and low-effort for an attacker with network access to the port.

### Recommendation
Add an explicit upper bound check on the parsed length (e.g., a small constant max payload size for `livestream_event::Event` messages) immediately after reading the 4-byte prefix, and reject/close the connection with an error before allocating `self.buf` if the length exceeds that bound.

### Proof of Concept
Unit test plan for `EventReader::poll_stream` (or an integration test against `Upstream`): construct/drive an `EventReader` with `len = u32::MAX.to_be_bytes()` fed via a mock `AsyncRead`/`TcpStream` pair, and assert that `poll_stream` returns an `Err` (rejected due to exceeding a maximum payload bound) before any `vec![0; len]` allocation is performed, i.e., before `self.buf_read < ...` branch is reached. A fuzz target driving `poll_stream`'s state machine with adversarial 4-byte length values should similarly assert no allocation exceeding a fixed cap (e.g., 16 MiB) is ever made.
