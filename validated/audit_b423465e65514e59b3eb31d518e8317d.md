### Title
Webhook shop-tenant identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, but then trusts the `shop` (and `topic`/`webhook_id`) values taken from unsigned HTTP headers when dispatching the payload to the registered handler. This breaks the identity binding: **HMAC-verified bytes ≠ bytes the tenant-routing decision is based on**, the same bug class as the Solidity report where a value used for a security-relevant calculation (`withdrawTime`) was derived from state not properly bound to the field actually being validated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string: [2](#0-1) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from HTTP headers and are never part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (an unauthenticated header value) to the app's handler as the tenant identity for the webhook, with no cross-check that the signed body actually belongs to that shop: [4](#0-3) 

Because a single Shopify app uses one shared `api_secret_key` across all of its installations/tenants, any shop that has legitimately installed the app can receive a genuinely-signed webhook (valid body + valid HMAC) from Shopify for its own store. That attacker-controlled tenant can then resend the identical `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at those headers), and `Registry.process` will hand the victim's identity plus the attacker-supplied body to the host application's handler as if it came from the victim shop.

### Impact Explanation
This lets one tenant impersonate another tenant to the app's webhook handler — the same class of cross-tenant identity confusion flagged as Critical impact ("cross-tenant access"). Any host application that keys business logic, database writes, or session/store lookups off `WebhookMetadata#shop` (exactly the pattern the gem's own docs/tests promote, e.g. `data.shop`) is exposed to attacker-controlled cross-tenant data injection/corruption, entirely reachable by a normal, unprivileged merchant who has simply installed the app on their own store — no leaked credentials, access token, or `api_secret_key` are required.

### Likelihood Explanation
Any merchant can install a public Shopify app and thereby obtain real webhook deliveries validly signed with the app's shared `api_secret_key`. Capturing one's own webhook body+HMAC and replaying it with a modified `shop-domain` header requires no special access — only the ability to send an HTTP POST to the app's public webhook endpoint, which by design must be internet-reachable.

### Recommendation
Bind the tenant identity to the signed content: include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string (as Shopify's REST/OAuth query validation already does via `VerifiableQuery`), or otherwise require the host application to independently verify that `request.shop` corresponds to a shop with an active session before trusting it. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as the sole tenant key.

### Proof of Concept
1. App shares one `api_secret_key` for all installs. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the same `B`/`H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — succeeds. [5](#0-4) 
4. Handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed(B) ...)` and processes attacker-controlled data under the victim's tenant identity.
