### Title
Missing transaction deadline in `SimplexPaymaster.swapAndDeposit` enables sandwich attacks on fee-recycling swaps - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster.swapAndDeposit` sells accrued stablecoin fees for the native asset via `IUniswapV2Router02.swapExactTokensForETH`, but hardcodes the swap's `deadline` parameter to `block.timestamp` instead of a caller-supplied, time-bound value. This disables Uniswap's transaction-expiration protection, exactly mirroring the M-38 pattern where `Swap.swapTokensMulti` set `deadline` to `block.timestamp` when selling reward tokens.

### Finding Description
`swapAndDeposit` computes `amountOutMin` from Chainlink oracle prices captured at call time and a fixed `swapSlippageBps` tolerance, then calls the router with `deadline = block.timestamp`: [1](#0-0) 

Setting `deadline` to `block.timestamp` means the deadline check inside Uniswap's router (`require(deadline >= block.timestamp)`) is always satisfied whenever the transaction is eventually mined, regardless of how long it sat in the mempool. This nullifies the transaction-expiration protection that the `deadline` parameter is designed to provide — an outdated transaction can be executed at any point in the future as long as it clears the `amountOutMin` floor, and MEV searchers can sandwich it, pushing the execution price down to just above `amountOutMin`, capturing the difference. This is architecturally identical to the referenced M-38 report: `Vault.rebalance`/`claimTokens` selling COMP rewards via `Swap.swapTokensMulti` with `deadline = block.timestamp` on `exactInput`.

The comment in the code at lines 447-453 argues that "the minimum output is derived onchain from the Chainlink oracles… so the caller cannot influence the execution price," but this only bounds the *floor* of acceptable output — it does nothing to prevent the *actual* execution price from being pushed down to that floor by a sandwich, nor does it protect against a stale transaction being executed long after being broadcast (e.g., during gas-price spikes), by which time the oracle price band captured at submission time may no longer reflect market conditions.

### Impact Explanation
Each `swapAndDeposit` call moves the paymaster's entire accrued token balance through a single-hop Uniswap V2 swap with an execution-price ceiling equal to `swapSlippageBps` below the oracle price at submission time, but with no time-bound floor on the swap's execution. A searcher who detects the pending transaction in the mempool can sandwich it: front-run to depress the pool price, let the paymaster's swap fill at (or just above) `amountOutMin`, and back-run to restore the price, extracting the difference as MEV. This directly reduces the native-asset amount deposited into the EntryPoint on every fee-recycling cycle (`FeesRecycled` event under-reports realized value), degrading the paymaster's gas-sponsorship reserve funding over time — a recurring value leak rather than a one-off loss, and the loss is unbounded up to the full slippage tolerance on every call.

### Likelihood Explanation
`swapAndDeposit` is intended to be called regularly (fee recycling is core to keeping the paymaster funded), and Uniswap V2 pools are permissionlessly front-runnable by any searcher watching the mempool — no privileged or malicious behavior from the treasury caller is required. The likelihood is high given routine invocation and the trivial cost of running a generic Uniswap sandwich bot against a `deadline`-less swap.

### Recommendation
Add a `deadline` parameter to `swapAndDeposit` (or derive it as `block.timestamp + MAX_SWAP_DELAY`, e.g. a few minutes) and pass that bounded value to `swapExactTokensForETH` instead of `block.timestamp`, so the router enforces genuine transaction expiration. Consider also validating `amountOutMin` against a live on-chain quote (e.g., `getAmountsOut`) in addition to the oracle-based floor, to tighten the acceptable execution-price band further.

### Proof of Concept
1. Governance/treasury calls `swapAndDeposit(token, amountIn)`; `amountOutMin` is computed from the current oracle price minus `swapSlippageBps`. [2](#0-1) 
2. The transaction is broadcast but sits in the mempool (e.g., due to low gas price or network congestion).
3. A searcher observes it and prepares a sandwich: buy the native asset in the same Uniswap V2 pool before the paymaster's swap executes (depressing `token`→native price), let the paymaster's `swapExactTokensForETH` fill near `amountOutMin` since `deadline = block.timestamp` never rejects a stale transaction, then sell back afterward, capturing the spread. [3](#0-2) 
4. `deposited`/`FeesRecycled` reflects a value materially lower than the true market rate for `amountIn` tokens at execution time, permanently reducing the funds available for EntryPoint gas sponsorship. [4](#0-3)
