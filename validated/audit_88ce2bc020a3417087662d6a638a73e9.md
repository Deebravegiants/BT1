### Title
Legacy (`define_ltds_fee_only_semantics=false`) fee-only semantics let an attacker zero out `loaded_accounts_data_size` cost while real account-load I/O still occurs - ([File: svm/src/account_loader.rs])

### Summary
When a transaction fails during `load_transaction_accounts` with `MaxLoadedAccountsDataSizeExceeded` (or any other load error) and `define_ltds_fee_only_semantics` is inactive, `load_transaction` reports `loaded_accounts_data_size` as `tx_details.rollback_accounts.data_size()` — the byte size of only the fee-payer (and nonce, if any) account — instead of the actual bytes read up to the point of failure. Since a normal fee payer typically has zero-length data, this resolves to `0`, and `CostModel::calculate_loaded_accounts_data_size_cost` charges zero CU cost for the loaded-accounts-data-size component, even though the account loader actually read the fee payer, program, and every other referenced account from the accounts store before hitting the limit.

### Finding Description
The bug is in the `Err` branch of `load_transaction`: [1](#0-0) 

Under legacy semantics, `loaded_accounts_data_size` for a `FeesOnlyTransaction` is set from `RollbackAccounts::data_size()`, which only sums the fee payer's (and nonce's) account data length: [2](#0-1) 

Meanwhile, the real work performed before the failure is substantial: `load_transaction_accounts` incrementally loads each account (including large ones and program/programdata accounts) from the account loader and only fails once the running total exceeds `requested_loaded_accounts_data_size_limit`: [3](#0-2) [4](#0-3) 

This means every account up to (and typically including) the one that trips the limit is actually fetched from accounts-db/cache — real I/O/CPU work — yet the eventual `loaded_accounts_data_size` reported for costing purposes collapses to whatever the fee payer's data length happens to be (frequently `0`).

This value flows unmodified into commit results and then into the cost model used to update the cost tracker / block cost accounting: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

`calculate_loaded_accounts_data_size_cost` is a pure function of the reported byte count — `0` bytes yields exactly `0` cost pages, hence `0` CU cost — regardless of how much genuine account data was actually read.

The exact legacy-vs-SIMD-0186 behavioral split, including the "0 under legacy semantics" degenerate case, is already codified in the integration test: [10](#0-9) 

No existing guard (signature check, nonce check, status cache, rent check, lock check) prevents this, because the transaction is syntactically and semantically valid up to the point of the data-size limit; the only "protection" removed under legacy semantics is that the reported cost basis is decoupled from the real work.

### Impact Explanation
An unprivileged user can submit ordinary transactions (any instruction mix, with a `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit` set intentionally low and account lists that reference many/large accounts) that deterministically trigger `MaxLoadedAccountsDataSizeExceeded` during `load_transaction_accounts`. Under legacy (`define_ltds_fee_only_semantics=false`) semantics — the default on any cluster/environment where the SIMD-0186 amendment feature has not yet been activated — each such transaction causes the validator to perform real account-load I/O/CPU work (reading potentially many large accounts) while being charged effectively `0` for the loaded-accounts-data-size component of its cost. This under-prices real resource consumption relative to the cost-tracker's block-cost accounting, allowing repeated intentional-overflow transactions to consume account-load resources for a price that does not reflect the work performed (materially underpriced execution / CU-accounting gap).

### Likelihood Explanation
This is trivially and repeatably reproducible by any transaction sender: it requires no special privileges, only (1) `define_ltds_fee_only_semantics` inactive on the target cluster, and (2) a normal fee payer account with little/no data (the common case), plus a transaction whose accounts sum exceeds an attacker-chosen `SetLoadedAccountsDataSizeLimit`. The exact scenario is already exercised (and asserted to produce `0`) by the in-repo test `fee_only_loaded_transaction_data_size` with `define_ltds_fee_only_semantics=false`.

### Recommendation
Do not gate the fix behind cluster-wide feature activation timing risk: either accelerate/ensure activation of `define_ltds_fee_only_semantics` on all clusters, or change the legacy fallback in `load_transaction`'s `Err` branch to report the actual `loaded_transaction_data_size` accumulated up to the point of failure (as the SIMD-0186 semantics already do) rather than `rollback_accounts.data_size()`, so that FeesOnly-path costing always reflects real work performed regardless of feature-gate state.

### Proof of Concept
Reuse and adapt the existing test `fee_only_loaded_transaction_data_size` in `svm/tests/integration_test.rs` (lines 3624-3770), running only the `false` (`old_fee_only`) case, and add an assertion computing the actual CU cost:

```rust

            error_metrics.max_loaded_accounts_data_size_exceeded += 1;
            Err(TransactionError::MaxLoadedAccountsDataSizeExceeded)

            Ok(())
        }
```

```rust
// Get actual transaction execution costs from transaction commit results
fn get_transaction_costs<'a, Tx: TransactionWithMeta>(
    bank: &Bank,
    commit_results: &[TransactionCommitResult],
    sanitized_transactions: &'a [Tx],
) -> Vec<Option<TransactionCost<'a, Tx>>> {
    assert_eq!(sanitized_transactions.len(), commit_results.len());

    commit_results
        .iter()
        .zip(sanitized_transactions)
        .map(|(commit_result, tx)| {
            if let Ok(committed_tx) = commit_result {
                Some(CostModel::calculate_cost_for_executed_transaction(
                    tx,
                    committed_tx.executed_units,
                    committed_tx.loaded_account_stats.loaded_accounts_data_size,
                    &bank.feature_set,
                ))
            } else {
                None
            }
        })
        .collect()
}
```
