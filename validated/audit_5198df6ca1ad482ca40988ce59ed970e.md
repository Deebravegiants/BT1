### Title
Single Poisoned Token in a Multi-Asset Order Permanently Blocks Escrow Release for All Tokens - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` releases every escrowed token of an order in one atomic loop using `safeTransfer`/`_sendValue`, both of which revert the entire call on any single transfer failure. Because `_withdraw` is invoked synchronously from `onAccept` (for `RedeemEscrow`/`RefundEscrow`) and from `onGetResponse` (for source-chain cancellation), a single misbehaving/blacklisting output or input token in a multi-asset order makes the whole settlement message permanently undeliverable — freezing every other, otherwise-transferable token in that same order, and stranding the solver's already-delivered destination-side outputs with no possible redemption. This mirrors the Arbitrum report's bug class: one failing leg of a bridging/settlement operation propagates its revert all the way up and blocks the entire canonical path, with no bypass mechanism.

### Finding Description
`_withdraw` iterates over `body.tokens` and unconditionally reverts the whole transaction if any single leg fails: [1](#0-0) 

This is called directly from `ExtrinsicIntents.onAccept` for both `RedeemEscrow` (solver claiming their filled order's input escrow) and `RefundEscrow` (user refund after cancellation): [2](#0-1) 

The call arrives through `EvmHost.dispatchIncoming`, which wraps the app call in a low-level `.call` and, on failure, deletes the receipt "so it can be retried" — it does not revert the outer transaction, but it also does not resolve the underlying problem: [3](#0-2) 

If the order's input/output token set includes a token whose transfer to the specific beneficiary deterministically reverts (e.g., a blacklist-style token like USDC/USDT refusing a sanctioned address, a paused token, or a token the order creator intentionally designed to fail for a particular solver address), then:
1. Every relayer delivery attempt of the `RedeemEscrow`/`RefundEscrow` message fails identically and forever (the failure is deterministic, not transient).
2. `dispatchIncoming` simply deletes the receipt each time, so the message is "retryable" in name only — it can never actually succeed.
3. All other tokens escrowed in the same order (which are perfectly transferable) become permanently locked in the gateway, because `_withdraw` has no per-token skip/try-catch or bypass, exactly the missing mechanism the external report calls out for `Arbitrum_Adapter`/`Arbitrum_SpokePool`.

The same all-or-nothing pattern also exists in the same-chain `_withdraw` usage and the `evm/tron/contracts/apps/IntentGatewayV2.sol` variant: [4](#0-3) 

### Impact Explanation
A solver who fills a cross-chain order (delivering real output assets to the beneficiary on the destination chain) can be permanently denied their input-token redemption on the source chain if the order's inputs include even one poisoned/blacklisting token, or if the solver's own address later becomes blacklisted on one of the input tokens before redemption completes. Likewise, a cancelling user can be permanently denied their refund of otherwise-healthy tokens because one co-escrowed token fails. This is a permanent freezing of legitimate funds with no protocol-level recourse (no admin bypass, no per-token skip, no try-catch), matching the "permanent freezing of funds" / "route unable to deliver messages" acceptance criteria.

### Likelihood Explanation
Reachable by any order creator (fully permissionless — anyone can call `placeOrder`/`fillOrder`/`cancelOrder`) who selects a multi-token input/output set that includes a token capable of deterministic transfer failure toward a particular address (blacklist tokens such as USDC/USDT are common in production; a malicious order creator could also deliberately combine such a token with healthy ones to grief a solver). No special privileges, consensus manipulation, or admin/governance compromise are required — this is triggerable by a single submitted order and its normal fill/cancel flow.

### Recommendation
Change `_withdraw` (and the tron `IntentGatewayV2.withdraw`) to isolate per-token transfer failures instead of reverting the whole batch, e.g.: (a) use a low-level call with a caught failure per token that skips the failed leg while still decrementing accounting once and emitting a distinct event/marking that token as "stuck" for later manual sweep, or (b) allow the withdrawal to be retried per-token/per-list rather than atomically for the entire order, or (c) allow governance/admin recovery for tokens whose transfer permanently fails, separate from the rest of the order's healthy tokens, so a single bad token cannot hold hostage the rest of the escrow or block message delivery indefinitely.

### Proof of Concept
1. User places a cross-chain order via `ExtrinsicIntents`/`IntentGatewayV2` with two input tokens: TOKEN_A (healthy ERC20) and TOKEN_B (a blacklist-style token, e.g. modeled on USDC) — see the input-escrow loop in `IntentGatewayV2.sol` lines 391–469.
2. A solver fills the order on the destination chain, delivering real output assets to the beneficiary, and the gateway dispatches a `RedeemEscrow` POST request back to the source chain (`_fillCrossChain`, `ExtrinsicIntents.sol` lines 164–210).
3. Before delivery, TOKEN_B's issuer blacklists the solver's address (a realistic, permissionless action available to token issuers, or simply have the order creator preselect a token that already blacklists common solver addresses).
4. A relayer submits proof and Hyperbridge attempts delivery; `onAccept` → `_withdraw` loop reaches TOKEN_B's `safeTransfer` to the solver, which reverts, reverting the entire `onAccept` call.
5. `EvmHost.dispatchIncoming` catches the failure, deletes the receipt, and returns — the message is nominally "retryable," but every subsequent relayer attempt fails identically since the blacklist condition doesn't change.
6. Result: TOKEN_A (fully transferable) remains stuck in escrow forever alongside TOKEN_B, and the solver — who already delivered real value on the destination chain — can never redeem the source-chain escrow.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
