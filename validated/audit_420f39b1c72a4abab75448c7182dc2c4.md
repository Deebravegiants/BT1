### Title
Webhook topic/shop headers are not covered by the HMAC signature, enabling cross-topic and cross-tenant data injection via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Request#to_signable_string` (used by `HmacValidator.validate`) only returns `@raw_body`, so the HMAC never covers `topic` or `shop-domain`. An attacker who owns their own shop installation of the same app receives genuinely Shopify-signed `(raw_body, hmac)` pairs and can replay that exact pair to the app's webhook endpoint with an arbitrary `topic` and/or `shop-domain` header, since neither is checked against the signature.

### Finding Description
The claimed binding is: `topic header value under which handler.handle() interprets parsed_body == topic under which raw_body was originally generated by Shopify`. This binding is FALSE.

`HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`, and for webhooks that method returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` re-computes `OpenSSL::HMAC.hexdigest` over that signable string with `Context.api_secret_key` and compares it via `OpenSSL.secure_compare` to the `hmac-sha256` header — `topic` and `shop-domain` never enter the computation: [2](#0-1) 

`Registry.process` then trusts `request.topic` unconditionally to select the handler and to label the parsed body passed to `handler.handle`: [3](#0-2) 

Exploit flow: the attacker registers their own webhook endpoint on their own development shop (permitted by the threat model) and receives a genuine Shopify-generated `(raw_body, hmac)` pair for some topic (e.g. `products/update`), signed with the app's shared `api_secret_key`/`client_secret` — the same secret used for every shop that installs the app. Because the HMAC only binds `raw_body`, the attacker can replay that identical `raw_body` + `hmac` to the app's real, public webhook endpoint while substituting the `shopify-topic` header (e.g. to `orders/create`) and/or the `shopify-shop-domain` header (to the victim merchant's shop domain). `HmacValidator.validate` still returns `true` because the signature check only re-derives the HMAC from `raw_body`; `Registry.process` then dispatches the handler for the forged topic with the replayed body, and/or attributes the payload to a victim tenant whose domain the attacker never controlled.

No other guard in the reachable path closes this gap: `ShopValidator.sanitize!`, `state` comparisons, and JWT `aud`/`iss` checks apply to OAuth/session-token flows, not to webhook `Request` processing, and `Context.setup?`/`private?`/`embedded?` and Sorbet runtime types do not constrain header contents at all.

### Impact Explanation
Any host application whose webhook handler branches on `data.topic` (from `WebhookMetadata`) to interpret the shape/semantics of `data.body`, or that trusts `data.shop` to select the tenant record to mutate, can be fed attacker-chosen but genuinely-signed JSON under a mislabeled topic or an arbitrary shop domain. Because the same `api_secret_key` is shared across all shops that install a given app, this is repeatable against arbitrary victim merchants of that app and constitutes cross-tenant data confusion — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Preconditions are met entirely within the stated attacker capabilities: create a development shop, install the target app, register a webhook endpoint, and receive at least one genuinely-signed webhook for a resource the attacker controls. No credentials, secrets, or privileged access are required — only capturing one legitimate `(raw_body, hmac)` pair and replaying it with forged headers to the app's real public webhook endpoint. This is low-cost and fully repeatable.

### Recommendation
Include `topic` and `shop-domain` (and ideally `webhook-id`) in the signable string used by `HmacValidator`, or otherwise bind them cryptographically to the payload before dispatch, so that a captured `(body, hmac)` pair cannot be replayed under a different topic or shop label.

### Proof of Concept
```ruby
# test/webhooks/request_topic_binding_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class TopicBindingTest < Minitest::Test
      def setup
        super
        @raw_body = '{"id":123,"note":"attacker-controlled"}'
        @hmac = Base64.encode64(
          OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, @raw_body)
        )
      end

      def test_hmac_ignores_topic_mismatch
        original = ShopifyAPI::Webhooks::Request.new(
          raw_body: @raw_body,
          headers: {
            "shopify-topic" => "products/update",
            "shopify-hmac-sha256" => @hmac,
            "shopify-shop-domain" => "attacker-shop.myshopify.com",
          },
        )
        replayed = ShopifyAPI::Webhooks::Request.new(
          raw_body: @raw_body,
          headers: {
            "shopify-topic" => "orders/create", # forged topic, same body+hmac
            "shopify-hmac-sha256" => @hmac,
            "shopify-shop-domain" => "victim-shop.myshopify.com", # forged tenant
          },
        )

        assert(ShopifyAPI::Utils::HmacValidator.validate(original))
        assert(ShopifyAPI::Utils::HmacValidator.validate(replayed))
        refute_equal(original.topic, replayed.topic)
        refute_equal(original.shop, replayed.shop)
        assert_equal(original.parsed_body, replayed.parsed_body)
      end
    end
  end
end
```
This demonstrates both sides of the claimed binding diverge (`original.topic != replayed.topic`, `original.shop != replayed.shop`) while `HmacValidator.validate` accepts both, proving `parsed_body`'s interpreted schema/topic is not cryptographically tied to the topic under which the body was actually generated.
