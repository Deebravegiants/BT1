### Title
Shop-tenant confusion in webhook processing — shop domain header is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook request solely via `Utils::HmacValidator.validate(request)`, which validates only the raw request body against `Context.api_secret_key`. The `shop` value used downstream to attribute the webhook to a tenant (`request.shop`, sourced from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header) is never included in the signed payload, so its authenticity is never checked.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw body, while `shop` is pulled from a plain, unsigned header:
```ruby
def to_signable_string
  @raw_body
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

Since a single app-level `client_secret` (`Context.api_secret_key`) is shared across every merchant shop that installs the app, an attacker who installs the app on their own store receives genuine, validly-HMAC-signed webhook deliveries for that store (with body content the attacker fully controls, e.g. `orders/create`). The attacker can then replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because the header is not part of the signed content, and `Registry.process` dispatches the handler with `shop: <victim-shop>` bound to attacker-controlled body data.

This breaks the intended binding: `shop authenticated by HMAC` should equal `shop the payload is attributed/acted upon`, but here `shop attributed` is taken from an unauthenticated header while only the body is authenticated.

### Impact Explanation
Any app built on this gem that keys per-tenant state, session lookup, or business logic off `WebhookMetadata#shop` (as the gem's own documented `Registry.process` API encourages) can have an attacker-controlled tenant inject fabricated webhook data attributed to a different, victim shop — i.e., cross-tenant data injection/confusion. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is Medium: exploitation requires only that the attacker (1) can install the target app on their own Shopify store (a normal, unprivileged action for any Shopify merchant/developer) and (2) can send arbitrary HTTP requests to the app's public webhook endpoint with a modified shop-domain header — no access token, `client_secret`, or privileged account is needed.

### Recommendation
Include the shop domain in the HMAC-signed material, or otherwise cryptographically bind the `shop` value used for tenant attribution (e.g., verify it against a shop known to have a stored, authenticated session/access token) before dispatching to handlers in `Registry.process`.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`; the app auto-registers a webhook (e.g. `orders/create`) using the app's shared `client_secret`.
2. Attacker triggers the webhook (e.g., creates an order) and captures the genuine POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`).
3. Attacker crafts arbitrary content inside body `B` (since it is their own store's order data) before triggering step 2.
4. Attacker replays the exact `(B, H)` pair to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [4](#0-3) ; the handler then runs with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content [5](#0-4) .

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
