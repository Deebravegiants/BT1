### Title
`Auth.setPin` accepts non-digit / adversarial string-like values, allowing persistence of a weak or malformed PIN - ([File: features/auth-mobile/module/auth.js])

### Summary
`Auth.setPin` only checks `value.trim().length !== 6` before persisting the value as the PIN secret via `keystore.setSecret`. It never verifies that `value` is a primitive string nor that its characters are ASCII digits, so any 6-character string (including Unicode confusables, whitespace-padded strings, or the return value of a custom `trim()`/`toString()` on an object) is accepted and stored as the user's PIN.

### Finding Description
`setPin` is implemented as: [1](#0-0) 

The only guard is `value.trim(); if (value.length !== 6) throw InvalidPasscodeLengthError()`. There is no `typeof value === 'string'` check, and no regex/character-class validation (e.g. `/^\d{6}$/`) enforcing that the stored PIN is composed of 6 ASCII digits. Because JavaScript is dynamically typed, `value.trim()` will happily execute on any object that exposes a `trim` method (or, since `String.prototype.trim` is looked up via the prototype chain / duck typing at the call site, any object explicitly providing `trim`), and the result of that call — not the original input — is what gets length-checked and persisted. This means:
- A value like `"６１２３４５"` (fullwidth Unicode digits) or other confusable Unicode characters of length 6 passes the length check and is stored verbatim as the "PIN", even though it is not a canonical 6-ASCII-digit secret.
- An input that is only length 6 *after* `trim()` (e.g. `"  1234  1234  "` trimmed unexpectedly, or a crafted object whose `trim()` returns an arbitrary 6-character string) is accepted.
- There is no validation that the stored secret satisfies a strict `^[0-9]{6}$` policy anywhere in this function or in `isCorrectPin`, which likewise does a plain `pin === input` comparison with no normalization.

This confirms the `AUTH_KEYSTORE_PIN_KEY` secret persisted via `this.#keystore.setSecret(...)` (features/auth-mobile/module/auth.js:122) is not guaranteed to be a canonical 6-digit numeric PIN, which is a real gap against the "persisted state is authentic" and strict-format invariant described in the question.

However, I could not find evidence in this repository that `Auth.setPin` (exposed via `authApi.auth.setPin` in [2](#0-1) ) is reachable from an untrusted/unprivileged RPC bridge such as a dApp-connector or external origin without any unlock/authentication gate. The `authApi` factory simply spreads the internal `auth` module's methods into an app-level API object consumed within the app's own DI system; there's no code in this repo showing this API surface bound to a dApp/browser RPC bridge, deeplink handler, or otherwise reachable by an "unprivileged attacker" as defined in the rules (ordinary dapp/origin requests, deeplinks, QR/import payloads, remote config/API responses, RPC calls). Without that reachability evidence, the "RPC bridge input with no unlock" precondition in the question is unverified in this codebase — it may be internal-only, invoked from trusted UI flows (e.g., PIN-setup screen) rather than an externally-reachable RPC surface.

### Impact Explanation
If `setPin` is ever reachable by input the app does not fully trust (e.g., programmatic RPC-style calls rather than a native PIN-entry UI that itself restricts input to digits), the weak validation lets a caller store a "PIN" that: (a) is not composed of digits, undermining any UX/UI code and other logic elsewhere that assumes numeric PIN entry; (b) may consist of Unicode confusable characters that a real user could never enter on a numeric keypad, effectively locking the legitimate user out or creating an unusable/inauthentic PIN state. This does not by itself constitute a signing-key leak, but it does weaken the auth control identified in `shouldAuthenticate = hasDeviceAuth || hasBioAuth || hasPin` and violates strict secret-format expectations.

### Likelihood Explanation
Exploitability strictly within this file is straightforward — no legitimate string-type or character-class validation exists. However, likelihood as an externally-triggerable "unprivileged RPC" attack is not established: I did not find code in this repo binding `setPin` to a dApp/RPC bridge or unauthenticated external caller. The precondition "attacker only has RPC call access, no unlock" is asserted by the question but not confirmed by repo evidence I could locate.

### Recommendation
Add explicit input validation in `setPin`:
```js
setPin = async (value) => {
  if (typeof value !== 'string') throw new InvalidPasscodeLengthError()
  const trimmed = value.trim()
  if (!/^[0-9]{6}$/.test(trimmed)) {
    throw new InvalidPasscodeLengthError()
  }
  await this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_PIN_KEY), trimmed)
  ...
}
```
This enforces the "6 ASCII digits" policy regardless of object trickery, Unicode confusables, or locale-normalized input.

### Proof of Concept
Unit test (extends `features/auth-mobile/module/__tests__/auth.test.js`):
```js
it('rejects non-digit / adversarial string-like values', async () => {
  const fakeString = { trim: () => '123４56' } // fullwidth '４' char, length 6 after trim
  await expect(auth.setPin(fakeString)).rejects.toThrow(InvalidPasscodeLengthError)

  const unicodeConfusable = '１23456' // fullwidth '１', trims to length 7 or 6 depending on chars
  await expect(auth.setPin(unicodeConfusable)).rejects.toThrow(InvalidPasscodeLengthError)

  // Assert keystore.setSecret was never called with a non-[0-9]{6} value
  expect(keystore.setSecret).not.toHaveBeenCalledWith(
    expect.stringContaining(AUTH_KEYSTORE_PIN_KEY),
    expect.not.stringMatching(/^[0-9]{6}$/)
  )
})
```
Fuzz plan: generate string-like objects (custom `trim()`/`toString()`), Unicode digit variants (fullwidth, Arabic-Indic, Devanagari), and confirm that for every case where `keystore.setSecret(AUTH_KEYSTORE_PIN_KEY, ...)` is called, the stored value strictly matches `/^[0-9]{6}$/`; currently this assertion fails for the crafted inputs above.
