### Title
Malicious `tokenIn` in `IntentGatewayV2` cross-chain orders permanently blocks `RedeemEscrow` settlement, letting an attacker steal a solver's real output tokens - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2.placeOrder` accepts an arbitrary `order.inputs[i].token` address with no whitelist check, exactly like the `tokenIn` in the referenced `OracleLess` report. An attacker can escrow a malicious ERC-20 as an order's input token whose `transfer`/`transferFrom` reverts when called from the gateway. When a solver fills the resulting cross-chain order on the destination chain, the solver immediately sends real output tokens to the attacker's beneficiary, then a `RedeemEscrow` message is dispatched back to the source chain to pay the solver the escrowed input tokens. That settlement call permanently reverts inside `_withdraw`'s `safeTransfer`, so the solver is never paid while the attacker has already received the solver's real assets.

### Finding Description
`placeOrder` (evm/src/apps/IntentGatewayV2.sol) transfers `order.inputs[i].token` via `IERC20(token).safeTransferFrom` for arbitrary attacker-supplied token addresses, with no allowlist: [1](#0-0) 

On a cross-chain fill, the solver unconditionally sends real output tokens to `order.output.beneficiary` before any cross-chain settlement occurs: [2](#0-1) 

The solver's compensation (the escrowed input tokens) is only released later, when the `RedeemEscrow` message is delivered on the source chain via `onAccept` → `_withdraw`: [3](#0-2) [4](#0-3) 

`_withdraw` calls `IERC20(token).safeTransfer(beneficiary, amount)` unconditionally for every escrowed input token; if the attacker's `token` reverts on transfer, this call — and thus the whole `onAccept` — reverts. `EvmHost.dispatchIncoming` treats any `onAccept` revert as "not yet delivered": it deletes the request receipt and returns without reverting the outer transaction, explicitly so the message "can be retried": [5](#0-4) 

Because the malicious token's revert behavior is deterministic, every retry of this specific `RedeemEscrow` message fails identically forever. The message can never be delivered, and the solver's promised payout (the escrowed input tokens matching the value the solver already sent out) can never be released. There is no per-token isolation, try/catch around individual token transfers, or fallback compensation path in `_withdraw`.

### Impact Explanation
A solver who fills such an order has already irrevocably transferred real, valuable output tokens to the attacker-controlled beneficiary on the destination chain (`_fillCrossChain`, executed before the `RedeemEscrow` dispatch). The matching settlement on the source chain — the solver's only compensation — is permanently undeliverable because of the malicious `tokenIn`. This is a concrete theft of solver funds: the attacker receives the solver's real assets and the solver receives nothing, with no recovery mechanism, satisfying the "permanent freezing of funds" / "route unable to deliver messages" bar. It also mirrors the source report's cancellation griefing: `_cancelSameChain`/`_cancelFromSource`/`_cancelFromDest` all funnel through the same `_withdraw`, so same-chain and cross-chain cancellations of such an order are likewise permanently blocked, freezing whatever real assets might be entangled in the order (e.g., partially filled escrow, fees) for as long as the order exists.

### Likelihood Explanation
The attack requires only deploying a standard malicious ERC-20 (revert-on-transfer-from-this-address) and calling the permissionless `placeOrder`/`fillOrder` flow — no privileged role, governance, or admin cooperation is needed. Any solver competing for orders in the open auction is a potential victim, since nothing in the fill path checks that `order.inputs` tokens are well-behaved before a solver commits real capital.

### Recommendation
Introduce a token allowlist/registry for `order.inputs` (and `order.output.assets`) that `placeOrder`/`fillOrder` enforce before escrowing or accepting fill commitments, or isolate each token transfer in `_withdraw` behind a try/catch so a single malformed token cannot block settlement of the entire withdrawal, with a documented fallback (e.g., skip-and-record for manual sweep) for tokens that fail to transfer.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer`/`transferFrom` always reverts when `msg.sender == IntentGatewayV2` (or unconditionally).
2. Attacker calls `placeOrder` on the source chain with `order.inputs = [{token: EvilToken, amount: X}]` and a real, attractive `order.output` (e.g., requesting valuable DAI/USDC on the destination chain), using their own address as `beneficiary`.
3. A solver, seeing an apparently fillable order, calls `fillOrder` on the destination chain, transferring the real requested output tokens to the attacker's beneficiary per `_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:186-199`), and dispatches the `RedeemEscrow` message.
4. When a relayer delivers the `RedeemEscrow` message on the source chain, `ExtrinsicIntents.onAccept` → `IntentsBase._withdraw` attempts `IERC20(EvilToken).safeTransfer(solver, X)`, which reverts.
5. `EvmHost.dispatchIncoming` catches the failure, deletes the receipt, and returns — the message is "retryable" but will revert identically on every future retry, so the solver's compensation is permanently unrecoverable while the attacker keeps the solver's real output tokens.
