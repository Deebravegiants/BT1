### Title
Unsafe `uint256` → `int256` cast on attacker-supplied order amounts in `VWAPOracle.recordSpread` - (File: evm/src/utils/VWAPOracle.sol)

### Summary
`VWAPOracle.recordSpread` casts solver/user-supplied `TokenInfo.amount` values (`uint256`) directly to `int256` without checking that they are below `type(int256).max`, mirroring the `TaxCollector` "[M06] Unsafe casting" bug class where an unbounded `uint` value is cast to a signed `int` and used in arithmetic.

### Finding Description
`recordSpread` is called by `IntentGatewayV2` (`restrict(_intentGateway)`) with `inputs`/`outputs` arrays of `TokenInfo{token, amount}` taken from an `Order` submitted by a user and filled by a permissionless solver [1](#0-0) . Both `inputs[i].amount` and `outputs[i].amount` are `uint256` values controlled by the order's creator/filler and are normalized to 18 decimals, then cast unchecked:

```solidity
int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
...
int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
``` [2](#0-1) 

Solidity 0.8's `int256(uint256)` cast reverts only if the value exceeds `type(int256).max` (2**255-1) — it does not clamp, and once a value close to that boundary is fed in, subsequent multiplications (`spreadBps * int256(inputAmountNormalized)`, or `amountDiff * int256(BPS_DENOMINATOR)`) can overflow `int256`'s signed range and cause reverts, or with values just under the boundary can flip sign semantics when multiplied against `BPS_DENOMINATOR` (10_000), corrupting `weightedSpreadSum`. `_normalizeAmount` further scales up amounts by `10**(18-decimals)` for low-decimal tokens, which increases the magnitude passed into the casts [3](#0-2) , making it easier to approach or exceed `int256` bounds/overflow thresholds than the raw order amount would suggest.

There is no `require(amount <= type(int256).max)` or use of a safe-casting helper anywhere in this path, matching the exact root cause described in the external report (unchecked `uint`→`int` cast before arithmetic).

### Impact Explanation
`_tokenSpreads[chainHash][token].weightedSpreadSum` is cumulative, persistent oracle state read by `spread()` and, per the `IIntentPriceOracle` interface, is meant to inform solver/pricing decisions for intents. A revert-inducing or sign-corrupting amount permanently disrupts the oracle's cumulative VWAP data for a token (griefing / persistent data corruption), and because `weightedSpreadSum` accumulates indefinitely, a single crafted large-but-valid order amount can poison downstream consumers of `spread()` that use this value to price fills. This is a Medium-severity data-integrity issue reachable from a single permissionless order fill (unprivileged solver/order-placer path), not merely a monitoring or low-severity concern.

### Likelihood Explanation
`recordSpread` is called automatically for every intent fill through `IntentGatewayV2`'s solver-fill flow (no `onlyOwner`/governance gate — only `restrict(_intentGateway)`), so any user placing an order or any solver filling it can supply arbitrarily large `TokenInfo.amount` values (bounded only by the token's max supply/ERC20 transfer amount, i.e., up to `type(uint256).max`) as `inputs`/`outputs`. High-decimal or amplified-by-normalization amounts approaching `2**255` are attacker-reachable, making the likelihood non-trivial for tokens with low decimals (normalization multiplies by up to 10**18).

### Recommendation
Bound-check all `uint256` amounts before casting to `int256` in `recordSpread` (e.g., `require(inputAmountNormalized <= uint256(type(int256).max) / BPS_DENOMINATOR)`), or adopt OpenZeppelin's `SafeCast.toInt256` plus explicit overflow checks on the subsequent multiplications, consistent with the fix pattern referenced in the external report.

### Proof of Concept
1. An order is placed with `inputs[0].amount` set to a low-decimal token (e.g., 6-decimal token) amount close to `type(uint256).max / 10**12` so that `_normalizeAmount` scaling by `10**12` pushes `inputAmountNormalized` near or above `type(int256).max`.
2. A solver fills the order (same-chain or cross-chain), triggering `IntentGatewayV2` to call `VWAPOracle.recordSpread(commitment, sourceChain, inputs, outputs)` [4](#0-3) .
3. `int256(inputAmountNormalized)` either reverts (DoS on that fill/oracle update) or succeeds near the boundary; the subsequent `spreadBps * int256(inputAmountNormalized)` multiplication overflows `int256`, reverting the fill transaction or (depending on the exact values chosen) wrapping/corrupting `weightedSpreadSum` in the `CumulativeSpreadData` storage that all future `spread()` calls read [5](#0-4) .

    function recordSpread(
        bytes32 commitment,
        bytes memory sourceChain,
        TokenInfo[] calldata inputs,
        TokenInfo[] calldata outputs
    ) external restrict(_intentGateway) {
        // Validate inputs and outputs have the same length
        if (inputs.length != outputs.length || inputs.length == 0) {
            return;
        }

        bytes32 sourceChainHash = keccak256(sourceChain);
        uint256 tokensLen = inputs.length;
        for (uint256 i = 0; i < tokensLen; i++) {
            address inputToken = address(uint160(uint256(inputs[i].token)));
            address outputToken = address(uint160(uint256(outputs[i].token)));

            // Get decimals for input token from storage (remote chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 inputDecimals = inputToken == address(0) ? 18 : _tokenDecimals[sourceChainHash][inputToken];
            if (inputDecimals == 0) continue; // Skip if decimals not configured

            // Get decimals for output token directly from contract (local chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 outputDecimals = outputToken == address(0) ? 18 : IERC20Metadata(outputToken).decimals();

            // Normalize both amounts to 18 decimals for comparison
            uint256 inputAmountNormalized = _normalizeAmount(inputs[i].amount, inputDecimals);
            uint256 outputAmountNormalized = _normalizeAmount(outputs[i].amount, outputDecimals);

    function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
    }
