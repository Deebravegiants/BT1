### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC verification exclusively to `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed unchecked into the webhook handler. This breaks the intended equality `shop bound by HMAC == shop delivered to handler`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook request purely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and compares it against the received `hmac`: [1](#0-0) 

`Request#to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controllable HTTP headers, with no cryptographic binding to the signed payload: [3](#0-2) 

After HMAC validation succeeds, `Registry.process` dispatches to the handler using these unauthenticated fields directly, including `shop: request.shop`: [4](#0-3) 

This differs from the OAuth flow's `AuthQuery`, which correctly folds `shop` (along with `code`, `host`, `state`, `timestamp`) into the signed string that is HMAC-verified: [5](#0-4) 

The consequence: the app's `client_secret`/`api_secret_key` (used in `HmacValidator.compute_signature`, see `lib/shopify_api/utils/hmac_validator.rb`) only authenticates the raw JSON body of a webhook, not which shop it is attributed to. Any entity capable of obtaining one valid `(raw_body, hmac)` pair from the app - e.g., an ordinary merchant who installs the app on their own store and receives a legitimately signed webhook - can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a different, victim shop. `HmacValidator.validate` will still pass because it only checks `@raw_body`, and `Registry.process` will invoke the handler believing the event originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the handler's per-shop attribution (`WebhookMetadata#shop`) can be forged by any shop that has legitimately received one webhook from the app, without needing the `api_secret_key` itself. Any host application that uses `shop` from `WebhookMetadata` to key persistence, trigger per-tenant side effects, or make trust decisions (which is the documented and expected usage pattern of this gem's webhook API) will attribute attacker-controlled webhook bodies to a shop the attacker does not control. This matches the "Critical - cross-tenant access" category, since it lets a merchant with no elevated privilege inject webhook events attributed to another tenant.

### Likelihood Explanation
Requires only: (1) becoming a shop that has the app installed (trivial via Shopify's free development store program), (2) receiving at least one webhook from the app for that shop, and (3) sending it to the app's public webhook endpoint with a forged `shop-domain` header. No knowledge of `api_secret_key` or any victim credential is required. This is fully reachable through the gem's documented, unprivileged flow (`Registry.process`).

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or otherwise cryptographically bind them, e.g. via a per-shop nonce/derivation), so that any mismatch between the signed payload and the header-derived shop/topic causes validation to fail — mirroring the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`, which folds `shop` into the signed string.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) Shopify development store, `attacker-shop.myshopify.com`.
2. App sends attacker a legitimate webhook: `raw_body = "{...attacker order data...}"`, `X-Shopify-Hmac-Sha256 = HMAC(raw_body, api_secret_key)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (== `raw_body`) against the HMAC — passes.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...))` is invoked; the host app now processes attacker-controlled webhook content as if it came from `victim-shop.myshopify.com`.
