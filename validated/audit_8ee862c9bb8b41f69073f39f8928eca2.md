Based on the code and documentation, this finding does not hold up.

The premise that "the error type does not distinguish 'unknown' from 'failed'" is factually incorrect. The SDK already has two distinct, separately-typed errors:

- `WithdrawalFailedError` — thrown only when `describeWithdrawal` returns `status.status === "failed"` (i.e., the bridge itself reports terminal failure) [1](#0-0) 
- `WithdrawalWatchError` — thrown only for polling timeout (`PollTimeoutError`) or `MAX_CONSECUTIVE_ERRORS` transient RPC errors, i.e. explicitly an "unknown/watch-failed" state, not a bridge-reported failure [2](#0-1) 

This distinction is also explicitly documented in the public API's JSDoc, which tells integrators exactly how to interpret each: `@throws {WithdrawalWatchError} When status polling fails (timeout or consecutive errors). Inspect error.cause to determine the reason.` versus `@throws {WithdrawalFailedError} When the withdrawal fails on the destination chain.` [3](#0-2) 

The equality the question wants broken is: "`WithdrawalWatchError` (timeout/unknown) == `WithdrawalFailedError` (terminal bridge failure)". These are two distinct classes at both the type and semantic level, and the SDK never collapses "unknown" into a "failed" signal — an integrator that correctly follows the documented contract (treating `WithdrawalWatchError` as "unknown, retry/reconcile" rather than "funds lost, refund now") would not double-pay. If an integrator chooses to treat a documented "unknown/timeout" error as a terminal failure despite the explicit JSDoc guidance to the contrary, that is integrator misuse of a documented API contract, not a defect in the SDK's equality/logic [4](#0-3) .

Additionally, the entire premise rests on the polling timeout being "too short" relative to actual bridge completion time — this is fundamentally a timeout/rate-limiting concern, which is explicitly listed as out of scope for this audit ("OUT OF SCOPE, reject on sight: ... denial of service, rate limiting, timeouts, unbounded loops...").

The `getWithdrawalStatsForChain` 3x-p99 multiplier and `MAX_CONSECUTIVE_ERRORS` are conservative, tunable constants, not a broken equality in signed/debited/routed state [5](#0-4) .

export function getWithdrawalStatsForChain(
	options: GetWithdrawalStatsOptions,
): CompletionStats {
	const p99Seconds = WITHDRAWAL_P99_BY_CHAIN[options.chain];

	if (p99Seconds == null) {
		const extraTimeout =
			options.bridgeRoute === RouteEnum.HotBridge ? HOT_EXTRA_TIMEOUT_MS : 0;
		return {
			...DEFAULT_WITHDRAWAL_STATS,
			p99: DEFAULT_WITHDRAWAL_STATS.p99 + extraTimeout,
		};
	}

	const p99 = p99Seconds * 1000;
	const timeout = p99 * 3;
	const extraTimeout =
		options.bridgeRoute === RouteEnum.HotBridge ? HOT_EXTRA_TIMEOUT_MS : 0;

	// Derive p50/p90 from p99 with minimum floors
	// p50: 15% of p99, minimum 5s - aggressive polling phase
	// p90: 50% of p99, minimum 30s - moderate polling phase
	const p50 = Math.max(5_000, p99 * 0.15);
	const p90 = Math.max(30_000, p99 * 0.5);

	return { p50, p90, p99: timeout + extraTimeout };
}
