Confirmed: the webhook HMAC signable string is only the raw body — the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are never part of the signed payload, yet `Registry.process` trusts `request.shop` (from the unauthenticated header) as the tenant identity passed to the handler.### Title
Webhook shop-tenant identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop-domain` (and `topic`/`webhook-id`/`api-version`) values are taken from unauthenticated HTTP headers and are never included in the signed material. `Registry.process` nonetheless treats `request.shop` as the authoritative tenant identifier and forwards it, unverified, to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shop-domain` header with no relation to the signed bytes: [2](#0-1) 

`HmacValidator.validate` only proves that the *body bytes* were signed with `api_secret_key`; it says nothing about which shop the header claims to be from: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant for the handler: [4](#0-3) 

The identity binding that should hold is:
`hmac == HMAC(api_secret_key, bytes-that-include-shop)` 

but the actual binding enforced is:
`hmac == HMAC(api_secret_key, raw_body)` while `shop = header["x-shopify-shop-domain"]` (unauthenticated, independent value).

Because every shop that installs the app shares the *same* `api_secret_key`, any shop that has legitimately received (or self-triggered) a webhook obtains a validly-signed `(raw_body, hmac)` pair. That signature is valid for the body under any shop label, since the shop is not part of the signed string. An attacker who is a legitimate installed merchant of the target app (an "unprivileged internet user" from the perspective of any other merchant's data) can capture one authentic `(body, hmac)` pair from their own shop's webhook deliveries and replay it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still return `true` (the body/signature pair is genuine), and `Registry.process` will dispatch to the handler with `WebhookMetadata.new(shop: request.shop, ...)` pointing at the victim shop.

Any app that uses the `shop` value from `WebhookMetadata` to select which merchant's data/session to act on (the documented, intended usage per `docs/usage/webhooks.md`) will attribute attacker-controlled webhook content to another tenant — a direct cross-tenant confusion caused entirely by this gem's own webhook-verification API, not by host-application misuse. This is exactly the "field acted on but not covered by the HMAC" analog: `shop` is acted on (used as the tenant key) but not bound to the signature the way `code`/`host`/`shop`/`state`/`timestamp` are bound together in the OAuth `AuthQuery#to_signable_string` (which correctly HMACs the shop value along with the other OAuth parameters): [5](#0-4) 

The contrast with `AuthQuery` shows the gem is capable of, and does elsewhere, bind the shop identity into the signed payload — but the webhook `Request` class does not do so for the tenant-identifying header.

### Impact Explanation
This breaks the tenant-isolation boundary the HMAC check is supposed to provide. An attacker who legitimately controls one installed shop can forge webhook deliveries that the app believes originated from a *different* shop, letting them inject fabricated webhook data (e.g. fake `orders/create`, `app/uninstalled`, `customers/data_request`) attributed to a victim tenant. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up and use that shop's stored access token, to trigger data deletion/redaction routines, or to write records under the victim's tenant), this can result in cross-tenant data corruption, unauthorized actions taken against a victim's store data, or triggering mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) against the wrong tenant. This matches the "cross-tenant access" Critical impact category — no access token, secret, or privileged account is required, only the ability to be an ordinary installed merchant (or to observe one delivered webhook) and to send a crafted HTTP POST to the app's public webhook route.

### Likelihood Explanation
High. Webhook endpoints are public HTTP routes by design (Shopify posts to them over the internet), the `api_secret_key` is shared across all shops using the app, and capturing one's own webhook's `(body, hmac)` pair requires nothing more than being an installed merchant or observing a single delivery. No cryptographic secret needs to be guessed or leaked — the attacker uses a signature that is genuinely valid, just for a body they are allowed to replay under a different claimed shop.

### Recommendation
Bind the shop (and ideally the topic/webhook id) into the HMAC-verified material, or otherwise cryptographically tie the `shop-domain` header to the signature, e.g., by including a per-shop secret/derivation, or requiring the caller to independently confirm the shop is one they have an active, verified session/webhook subscription for before trusting `request.shop`. At minimum, document prominently (and enforce in `Registry.process`) that `request.shop` must be cross-checked by the host application against its own registered/installed-shop list before being used as a tenant key, since the HMAC does not protect it. Consider extending `Request#to_signable_string` to canonically include the shop and topic headers alongside the raw body so `HmacValidator.validate` actually authenticates them.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook to the app's callback URL:
```
POST /callback/orders/create
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <valid-signature-of-raw-body>
X-Shopify-Shop-Domain: attacker-shop.myshopify.com
Body: {"id": 1, "note": "hello"}
```
2. Attacker captures the exact raw body and the `X-Shopify-Hmac-Sha256` value (both are visible to them since it's their own shop/webhook, or interceptable via a proxy on their own server).
3. Attacker crafts a new POST to the same app endpoint, keeping body and HMAC identical but replacing the shop header:
```
POST /callback/orders/create
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <same-valid-signature>
X-Shopify-Shop-Domain: victim-shop.myshopify.com
Body: {"id": 1, "note": "hello"}
```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the raw body against the shared `api_secret_key`: [6](#0-5) 
5. The handler is invoked with `shop: "victim-shop.myshopify.com"`, and the app processes/attributes the forged webhook data as belonging to `victim-shop.myshopify.com`, even though the content originated from and was signed for `attacker-shop.myshopify.com`.

*(Note: I was unable to find a `WebhookMetadata` file in the index — it may exist but not be captured by the index size limits; its definition was referenced only via `Registry.process`'s call site and `docs/usage/webhooks.md`, which was sufficient to confirm `shop` is passed through unverified.)*
