### Title
Webhook shop/topic identity spoofing via unsigned headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook `HMAC` validation in this gem only signs the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — which are used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook to a specific merchant/topic — are taken directly from unauthenticated HTTP headers and are never part of the signed payload. This breaks the identity binding: `HMAC-verified bytes == raw_body` while `shop/topic used-by-handler == unverified header value`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC of the body only, then uses the unauthenticated `request.topic` to look up a handler and forwards the unauthenticated `request.shop` straight into `WebhookMetadata`, which is handed to the app's business logic: [3](#0-2) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) against the secret — it has no knowledge of, and does not cover, the `shop`/`topic` headers: [4](#0-3) 

Because a single app `client_secret`/`api_secret_key` is shared across every merchant installation of the app, any unprivileged internet user who has legitimately installed the app on their own development/test store can capture a genuine, validly-signed webhook body+HMAC pair that Shopify sends to their store's endpoint. They can then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header with a victim shop's domain or a different topic. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will hand the (now falsely-attributed) payload to the handler as if it originated from the victim shop/topic: [5](#0-4) 

This is exactly the "field acted on but not covered by the HMAC" identity-binding break called out in the review rules — here the equality that should hold, `verified_bytes == attributed_shop`, does not hold, because `attributed_shop` is parsed from an unsigned header.

### Impact Explanation
Any handler logic that trusts `WebhookMetadata#shop` (e.g., to look up the correct merchant's stored session/access token, update per-tenant records, or gate per-shop business logic) can be tricked into processing attacker-supplied webhook content while believing it came from an arbitrary victim shop of the attacker's choosing. This is a cross-tenant identity-confusion vector: the attacker fully controls which `shop` value is presented to the app for a payload whose only "authenticity" guarantee (HMAC) never covered that field. Depending on how the host app uses `data.shop`/`data.topic` in `WebhookMetadata`, this can lead to cross-tenant data corruption or logic being applied against the wrong tenant.

### Likelihood Explanation
The `api_secret_key` is a single app-wide secret, not shop-specific, so any user who can install (or has installed) the app on any store — a purely unprivileged, ordinary merchant onboarding action — can obtain valid signed webhook traffic and then freely craft new HTTP requests to the app's public webhook endpoint with attacker-chosen `shop`/`topic` headers alongside the replayed, still-validly-signed body. No access token, leaked credential, or privileged role is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content (or otherwise cryptographically bind them, e.g., by having `to_signable_string` incorporate the header values, matching how Shopify signs OAuth callback parameters via `AuthQuery#to_signable_string`), so that `HmacValidator.validate` fails if any of these identity-bearing fields are altered relative to what was originally signed.

### Proof of Concept
1. Install the app (as any ordinary merchant) on `attacker-shop.myshopify.com`; trigger any registered webhook topic (e.g. `orders/create`) so Shopify sends a valid request: body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Capture `B` and `H` (attacker controls their own store/traffic).
3. Replay an HTTP POST to the same app webhook endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `Registry.process` succeeds because it only validates `B` against `H`: [6](#0-5) 
5. The registered handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
