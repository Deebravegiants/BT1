### Title
Webhook `shop` (and `topic`) identity is trusted from unauthenticated headers, not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string solely from the raw HTTP body, while the `shop`, `topic`, and `webhook_id` fields it exposes to the caller are read directly from unauthenticated HTTP headers. `Registry.process` verifies only the HMAC over the body and then hands the header-derived `shop` value to the app's webhook handler as authoritative tenant identity. An attacker who can obtain one validly-signed webhook body (e.g., by installing the app on their own store) can replay that exact body/HMAC pair while forging the `shop-domain` header to any other shop, and the gem will accept it as valid and route it to the handler as if it came from the victim shop.

### Finding Description
`Request#to_signable_string` binds the HMAC to `@raw_body` only: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are parsed straight out of the (attacker-controlled, over plain HTTP) headers, with no cryptographic tie to the body or to the HMAC: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC (which is a function of `to_signable_string`, i.e. the body) and then immediately trusts `request.shop` and `request.topic` as the tenant/event identity passed to the handler: [4](#0-3) 

`HmacValidator.validate` confirms this: it only ever hashes `verifiable_query.to_signable_string` (the body for webhooks) against the app's shared `api_secret_key`: [5](#0-4) 

Because `api_secret_key` is a single app-level secret shared across every shop that installs the app, and the HMAC never covers the `shop-domain` header, the equality the code implicitly assumes — "the shop whose domain the HMAC-verified request was authenticated for" == "the shop attributed to this webhook payload" — does not actually hold. Any request bearing a body+HMAC pair the attacker legitimately obtained for their own shop can be replayed with an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header, and `Registry.process` will still consider it "Valid" and forward it to the handler labeled with the forged shop.

### Impact Explanation
This breaks the tenant-isolation guarantee that host applications rely on `ShopifyAPI::Webhooks::Registry.process`/`WebhookMetadata#shop` for. Any application logic that keys off `WebhookMetadata#shop` (e.g., loading the session/access token for that shop, updating per-shop billing/plan state, triggering per-shop side effects such as data deletion for GDPR topics, or writing shop-scoped records) can be made to act on forged shop identity while consuming attacker-supplied payload content, i.e., a cross-tenant confusion/injection primitive rooted entirely in this gem's webhook verification logic. Because `MANDATORY_TOPICS` includes `shop/redact` and `customers/redact`/`customers/data_request`, this is not merely cosmetic — it enables attacker-triggered invocation of privacy/compliance webhook handlers attributed to an arbitrary victim shop domain.

### Likelihood Explanation
The attacker only needs a webhook subscription that fires under their own control (achievable via a normal, unprivileged install of the app on their own dev/test store, or simply capturing any webhook the app already sends them) plus the ability to POST directly to the app's public webhook endpoint (no session, access token, or `client_secret` required). This requires no interaction with Shopify's platform beyond owning one shop.

### Recommendation
Bind the shop/topic identity into the HMAC-verified payload rather than trusting sibling HTTP headers: either include the `shop-domain`/`topic` headers in the signable string used for HMAC computation, or independently verify the shop against a value that is itself authenticated (e.g., cross-check against an already-established, HMAC/OAuth-verified session for that shop) before dispatching to the handler.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture a legitimate webhook delivery — raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Replay the request to the app's webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com` from the header [6](#0-5) ; `Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over `B` [7](#0-6) .
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ...)` [8](#0-7) , causing the host app to act as though `victim.myshopify.com` sent this payload, despite no legitimate webhook for that shop ever occurring.

        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
