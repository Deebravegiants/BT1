### Title
Webhook `shop-domain` header is trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header, while the HMAC that `Registry.process` validates is computed only over the raw request body. The identity binding "shop authenticated == shop acted upon" is broken: the HMAC proves the body's integrity/authenticity but says nothing about which shop it belongs to, so a replayed body with a swapped shop header is accepted and dispatched under attacker-chosen tenant identity.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`to_signable_string` returns only `@raw_body`: [2](#0-1) 
`shop` is read straight from the `shop-domain` header, which is not part of the signed material: [3](#0-2) 

`Registry.process` validates only that HMAC-of-body is correct, then trusts `request.shop` to build the tenant-scoped `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` (body only) to compute/compare the signature — the shop header never enters the computation: [5](#0-4) 

The broken binding, stated as an equality that the code fails to enforce:
`shop_header (used for tenant routing in handler.handle)` == `shop_bound_by_hmac (none — HMAC covers only raw_body)`.

This is the same bug class as the VRF report: a value consumed to determine "whose data this is" (the pending-request identity in the VRF case; the tenant/shop in this case) is not validated against the cryptographically-verified channel (the `requestId`/`s_requestId` check in VRF; the HMAC signature here) before being acted upon.

### Impact Explanation
Any party capable of triggering, receiving, or otherwise observing one valid `(raw_body, hmac)` pair for the app's webhook endpoint (e.g. as a legitimate merchant that installs the app on their own store and captures Shopify's genuine webhook deliveries) can resend that exact body+HMAC to the same endpoint while substituting an arbitrary `shop-domain` header. Because `Registry.process` only checks `Utils::HmacValidator.validate(request)` (body integrity) and never checks that `request.shop` corresponds to the signed content, the forged request passes validation and is dispatched to the handler tagged with the attacker-chosen shop. Any host application that uses `WebhookMetadata#shop` to select the tenant's session/access token or apply tenant-scoped writes will process attacker-controlled data as if it originated from a different, victim tenant — a cross-tenant data-integrity/confusion issue reachable without the app's `client_secret`, access token, or TLS interception.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on one's own Shopify store to receive at least one genuine, correctly-HMAC'd webhook delivery (something any unprivileged merchant/attacker can do), and (2) the ability to POST to the app's public webhook endpoint with custom headers, which is inherent to how webhook endpoints are exposed. No secret material, TLS interception, or social engineering is needed, making this practically reachable by an unprivileged internet user who can install the app.

### Recommendation
- Include the shop domain (and ideally topic/api-version) inside the HMAC-signed material, or otherwise cryptographically bind the shop identity to the payload before trusting it for routing.
- Alternatively, since Shopify's real HMAC secret binds only the body, treat `request.shop` as untrusted input and require host applications to independently verify that the shop in the webhook matches an existing, previously-authorized installation/session before processing — but this gem should not present `request.shop` as a value implicitly protected by `Utils::HmacValidator.validate`. At minimum, document explicitly in `Webhooks::Request`/`Registry.process` that `shop`, `topic`, `api_version`, and `webhook_id` are NOT covered by the HMAC and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker-shop.myshopify.com`) and triggers a webhook event (e.g., `orders/create`), capturing the genuine POST Shopify sends, including body `B` and header `x-shopify-hmac-sha256: H` (valid because Shopify computed `H` using the app's `client_secret` over `B`).
2. Attacker resends the identical request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`B`) and finds it matches `H` — validation passes: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now returns `"victim-shop.myshopify.com"`: [7](#0-6) 
5. The host application's handler processes attacker-supplied body `B` as if it were genuine data from `victim-shop.myshopify.com`, confusing tenants.
