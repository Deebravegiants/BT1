### Title
Webhook HMAC validation only covers the raw body, not topic/shop/webhook-id headers, allowing signed-body replay under a forged topic or shop - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, while `Webhooks::Registry.process` dispatches on `request.topic` and passes `request.shop`/`request.webhook_id` to the handler — none of which are covered by the HMAC. An attacker who obtains one validly-signed webhook body (trivially, by installing the app on their own development shop and receiving a real webhook) can resend that exact body to the app's webhook endpoint with a modified `X-Shopify-Topic` and/or `X-Shopify-Shop-Domain` header, and `HmacValidator.validate` will still accept it because the signature check never inspects those headers.

### Finding Description
The binding the app relies on is: **every value `Webhooks::Registry.process` acts on is inside the string handed to `HmacValidator` via `to_signable_string`.**

Tracing the code:
- `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `Request#topic`, `#shop`, `#api_version`, `#webhook_id` are all read from HTTP headers, independent of the body: [2](#0-1) 
- `HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [3](#0-2) 
- `Registry.process` gates only on that HMAC check, then dispatches purely on `request.topic` (header) and forwards `request.shop`, `request.webhook_id`, `request.api_version` (all headers) to the handler untouched: [4](#0-3) 

So the equality `signed(topic, shop, webhook_id, api_version, body) == acted_on(topic, shop, webhook_id, api_version, body)` does **not** hold — the left side is really `signed(body)` only. Nothing else in the gem (`ShopValidator.sanitize!` is never invoked in this path) revalidates `request.shop` or `request.topic` against anything cryptographic.

Attacker flow:
1. Attacker creates their own development shop, installs the target app, and registers a webhook endpoint they control — receiving a genuinely, validly-signed webhook `(body B, hmac H)` for some topic (e.g. `orders/create`).
2. Attacker crafts a raw HTTP POST to the target app's public webhook route with the identical body `B` and `hmac` header `H`, but changes `X-Shopify-Topic` to a different registered topic (e.g. `customers/data_request` or any topic with a handler) and/or changes `X-Shopify-Shop-Domain` to an arbitrary shop domain string.
3. `HmacValidator.validate` recomputes HMAC over `B` with the app's secret and it matches `H` — validation passes, because the topic/shop headers were never part of the signed material.
4. `Registry.process` looks up the handler for the *attacker-chosen* topic and invokes `handler.handle` with a `WebhookMetadata` whose `shop`, `topic`, and `webhook_id` are attacker-controlled strings that the app's code treats as authenticated (they arrived past HMAC validation).

Existing guards do not stop this: `HmacValidator.validate` only checks body integrity, not header integrity; there is no `ShopValidator.sanitize!` call anywhere in `Registry.process`; there is no delivery-id or nonce tracking to detect this cross-context replay; Sorbet typing only enforces types, not provenance.

### Impact Explanation
This is a **Critical — authentication bypass** condition: a request whose topic/shop association was never actually signed by Shopify is accepted and processed by the app as if it were. Concretely:
- An app that branches handler logic or data access by `topic` can be made to run the wrong handler against attacker-chosen JSON, because the topic string is unauthenticated.
- An app that trusts `WebhookMetadata#shop` as the authenticated tenant identifier (a very common pattern for looking up per-shop sessions/data) can be made to process one shop's signed payload under a **different, attacker-chosen shop domain** — a cross-tenant confusion, since the only thing cryptographically tied to the app's secret is the body bytes, not the shop they are attributed to.
- This is trivially repeatable: any attacker with their own dev-shop installation can harvest arbitrarily many validly-signed bodies and replay them under any topic/shop header they like, against any merchant's install of the same app, since the secret is shared across all shops.

### Likelihood Explanation
- Preconditions: the app must be built on this gem's webhook route using `Registry.process` as documented (the standard integration pattern) and register at least one `:http` webhook handler.
- Attacker cost: one dev-shop signup, one webhook subscription, capture of one legitimate signed callback — all fully within the unprivileged attacker's stated capabilities (own shop, own endpoint, own server).
- No secrets, no privileged access, and no race condition are required. Feasibility is high and the exploit is deterministic/repeatable.

### Recommendation
Include all security-relevant, attacker-influenced fields (`topic`, `shop-domain`, `webhook-id`, `api-version`) in the value passed to `HmacValidator`, or otherwise cryptographically bind them to the body before dispatch — e.g. build `to_signable_string` from a canonical concatenation of these headers plus the raw body, and re-derive `request.topic`/`request.shop` only from that verified representation rather than from raw, unauthenticated headers.

### Proof of Concept
```ruby
# test/webhooks/registry_topic_confusion_test.rb
require "test_helper"

class RegistryTopicConfusionTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.clear
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/wh",
      handler: OrdersHandler.new,
    )
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "customers/data_request", delivery_method: :http, path: "/wh",
      handler: CustomersHandler.new,
    )
  end

  def test_signature_covers_body_only_not_topic
    body = '{"id":1}'
    hmac = compute_valid_hmac(body, "secret")

    request_orders = build_request(body: body, hmac: hmac, topic: "orders/create", shop: "attacker-dev-shop.myshopify.com")
    request_confused = build_request(body: body, hmac: hmac, topic: "customers/data_request", shop: "victim-shop.myshopify.com")

    # Both pass HMAC validation despite different topic/shop -> signature does not cover topic/shop
    assert ShopifyAPI::Utils::HmacValidator.validate(request_orders)
    assert ShopifyAPI::Utils::HmacValidator.validate(request_confused)

    # Dispatch follows the (unauthenticated) topic header, not anything tied to the signature
    CustomersHandler.any_instance.expects(:handle).with(has_entry(shop: "victim-shop.myshopify.com"))
    ShopifyAPI::Webhooks::Registry.process(request_confused)
  end
end
```
Assertions on both sides of the binding: `HmacValidator.validate` returns `true` for two requests with identical body/hmac but different `topic`/`shop` headers, proving the signed material (`to_signable_string` == raw body) does not equal the set of values `Registry.process` acts on (`topic`, `shop`, `webhook_id`).
