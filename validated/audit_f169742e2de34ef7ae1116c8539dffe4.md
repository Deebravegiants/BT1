### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` field from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) HTTP header, but `HmacValidator` only authenticates the raw request body. The tenant-identifying field is never bound to the cryptographic signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an unauthenticated header, independent of the signed payload: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute the HMAC purely over `verifiable_query.to_signable_string` (i.e., the body) and compare against the `hmac` header — the `shop` header plays no role in the equality check: [3](#0-2) 

`Registry.process` validates only the HMAC, then immediately trusts `request.shop` as the tenant identity forwarded to the host application's handler: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, raw_body)` AND `shop` is authenticated as part of that same signed material. In this code, `shop` is asserted (`request.shop` == "the tenant this webhook is for") but the equality is never actually checked against anything covered by the HMAC — the signature only proves "some request produced this exact `raw_body` under this app's secret", not "this body/topic is associated with this specific shop."

### Impact Explanation
Because the shop header sits outside the signed material, a request with an unmodified, validly-signed `raw_body` but a **substituted** `shop-domain` header still passes `Utils::HmacValidator.validate`. Since `Registry.process` passes `request.shop` straight into `WebhookMetadata.new(... shop: request.shop ...)` for the host handler, any host application that uses `data.shop` (the documented, intended way to identify which merchant a webhook belongs to, per `webhook_handler.rb`/`WebhookMetadata`) as a lookup key for that merchant's session/access token/data store will process the payload under the wrong tenant. This is a cross-tenant identity-binding break directly caused by this gem's own webhook-verification code, not by host misuse.

### Likelihood Explanation
Exploitation requires the attacker to possess one legitimately-signed webhook payload for a shop they control (any app-installing merchant can trivially obtain this by triggering an event on their own store) and replay it against the app's webhook endpoint with the `shop-domain` header swapped to a victim shop's domain. No access to `api_secret_key`, access tokens, or any privileged credential is required — this is exactly the "unprivileged internet user" analog: an app-installer replaying their own valid signature while relabeling the tenant field the gem exposes as trusted.

### Recommendation
Bind the shop identity into the material that is actually verified — e.g., include the `shop-domain` header (and/or `topic`) in `to_signable_string`, or have `HmacValidator`/`Registry.process` cross-check that the `shop` claimed in the header matches an expected value tied to the registered webhook/session before constructing `WebhookMetadata`, so that `shop` cannot be varied independently of the HMAC-protected body.

### Proof of Concept
1. Merchant A installs the app and legitimately triggers a webhook (e.g., `orders/create`). The app receives:
   - `raw_body = B`
   - `shopify-hmac-sha256 = HMAC(secret, B)` (valid)
   - `shopify-shop-domain = shop-a.myshopify.com`
2. Merchant A resends the exact same `raw_body`/`hmac` pair to the app's webhook endpoint but sets `shopify-shop-domain: shop-victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "shop-victim.myshopify.com"` (`lib/shopify_api/webhooks/request.rb:21-23`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B)` against the unchanged `hmac` header (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop = "shop-victim.myshopify.com"` and invokes the host handler (`lib/shopify_api/webhooks/registry.rb:198-199`), causing Merchant A's data/event to be processed as if it belongs to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
