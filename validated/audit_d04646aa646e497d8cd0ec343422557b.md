### Title
Unchecked ERC20 Transfer Return Value in `IntentGatewayV2.withdraw()` and `SweepDust` Handler on Tron - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` uses low-level `.call()` to perform ERC20 transfers in `withdraw()` (escrow release/refund path) and in the `SweepDust` handler, checking only whether the call reverted (`success`) but never decoding/validating the boolean value the token contract returns. Tokens that return `false` on failure instead of reverting will be treated as successful transfers, while escrow accounting is unconditionally decremented and the order is marked filled — permanently losing funds without delivering them to the beneficiary.

### Finding Description
In `withdraw()`, tokens are moved to the beneficiary with: [1](#0-0) 

and the fee-token payout uses the identical pattern: [2](#0-1) 

The same unchecked pattern also appears in the privileged `SweepDust` request handler: [3](#0-2) 

In all three cases, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` returns `(bool success, bytes memory data)`. `success` only reflects whether the external call reverted; it does not reflect the ABI-decoded boolean return value that a compliant ERC20 `transfer` function returns to signal application-level failure. Some TRC20/ERC20 tokens (including some deployed on Tron, and generally any non-standard, pausable, blocklist-gated, or partially-compliant token) return `false` on failure rather than reverting. Under this pattern, such a call would report `success == true` even though `data` decodes to `false` and no tokens moved.

Meanwhile, `_orders[body.commitment][token] -= amount;` (line 710) unconditionally decrements the escrow balance, and `_filled[body.commitment] = beneficiary;` (line 693) is set before the loop even runs, regardless of whether the underlying transfer actually succeeded. The beneficiary never receives funds, but the order is marked filled/redeemed and cannot be retried.

This is architecturally identical to the reported bug class (`MarginTrading._closetrade`'s unchecked `.transfer()`), but reachable here through the core escrow withdrawal path of Hyperbridge's `IntentGatewayV2` on Tron — triggered by any `RedeemEscrow`/`RefundEscrow` cross-chain message or a hyperbridge-authorized `SweepDust` message referencing a token that returns `false` instead of reverting.

Note the primary EVM `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol`) and `IntentsBase.sol` correctly use OpenZeppelin's `safeTransfer`/`safeTransferFrom` via `SafeERC20`, e.g.: [4](#0-3) 
The Tron fork diverges from this safe pattern by using raw `.call()` without decoding the return data.

### Impact Explanation
For any input/output token on Tron that implements `transfer` returning `false` on failure (a common non-reverting failure mode for tokens with pausability, blocklists, or fee-on-transfer edge cases), the `withdraw()` path will silently "succeed" while funds remain stuck in the `IntentGatewayV2` contract and the corresponding escrow record is permanently decremented/marked filled. This results in permanent loss of escrowed user/solver funds with no path to retry withdrawal, satisfying the "permanent freezing/theft of funds" bar.

### Likelihood Explanation
This is triggered automatically on ordinary escrow redemption or refund flows (`RedeemEscrow`/`RefundEscrow` messages processed via `onAccept`, and the hyperbridge-only `SweepDust` message) — no attacker privilege is required beyond using or configuring a token with this common non-reverting-failure behavior. Given TRC20 tokens on Tron routinely mirror legacy `transfer` implementations (some based on the original non-reverting Zeppelin ERC20 pattern), likelihood is realistic whenever such a token is supported by the gateway.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` invocations in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()` and the `SweepDust` handler) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. This decodes and validates the boolean return value (when present) and reverts on failure, preventing state updates (`_orders[...]` decrement, `_filled` marking) from being committed when the transfer did not actually occur.

### Proof of Concept
1. Register/escrow an input token `T` in an intent order whose `transfer` implementation returns `false` on failure instead of reverting (e.g., due to a blocklist check on the beneficiary, or insufficient contract-level balance edge case where the contract chooses to return `false`).
2. Deliver a valid `RedeemEscrow` (or `RefundEscrow`) message to `IntentGatewayV2` for that commitment via `onAccept`/`handle`, invoking `withdraw()`.
3. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes without reverting, so `success == true`, even though `T.transfer` internally returned `false` and moved no tokens.
4. `_orders[body.commitment][token] -= amount;` decrements escrow to zero and `_filled[body.commitment] = beneficiary;` marks the order redeemed; `EscrowReleased`/`EscrowRefunded` is emitted.
5. The beneficiary's token balance is unchanged — the escrowed tokens remain stuck in the `IntentGatewayV2` contract with no accounting entry left to claim them, permanently freezing the funds.
