Found it: the webhook HMAC in this gem is computed over the raw body bytes, but the field the library actually trusts for tenant identity — `request.shop` — comes from the `X-Shopify-Shop-Domain` header, which is **not** covered by the signature at all.

### Title
Webhook shop identity spoofing via unsigned `shop-domain` header - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only `@raw_body` [1](#0-0) , while the tenant identity used by handlers (`request.shop`) is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that HMAC [2](#0-1) . `Registry.process` validates the HMAC and then hands `request.shop` directly to the host app's handler as the tenant identifier for the payload, without ever checking that the header value matches an app-derived shop [3](#0-2) .

### Finding Description
`HmacValidator.validate` signs/verifies `verifiable_query.to_signable_string`, which for `Request` is defined as `@raw_body` only [1](#0-0) . The `shop` accessor used by `WebhookMetadata` (and thus the host app's tenant-scoping logic) is populated purely from an HTTP header value that an attacker fully controls when replaying a *different, legitimately-obtained* webhook body signed with the same `api_secret_key` for shop A, but with the `X-Shopify-Shop-Domain` header rewritten to shop B:

```
shop == header("shop-domain")   [never part of hmac-signed bytes]
vs.
hmac == HMAC(secret, raw_body)  [only covers body]
```

Because these two are not bound together, any request whose body+hmac pair is valid for *some* shop the attacker has visibility into (e.g., their own installed app instance receiving legitimate webhooks) can be replayed with an arbitrary `shop-domain` header value, and `Registry.process` will accept it and dispatch it to the handler tagged as coming from the attacker-chosen shop [4](#0-3) .

This mirrors the "donation/binding-break" bug class from the report: an attacker-controlled field (`shop-domain`) is acted upon by downstream logic (tenant attribution) but is excluded from the field set actually covered by the cryptographic proof (`raw_body`), letting the attacker forge the tenant binding while keeping the signature valid.

### Impact Explanation
If the host application trusts `WebhookMetadata#shop` to route the payload's `body` to per-tenant storage/processing (which is the documented and expected use per the `WebhookHandler#handle(data:)` contract), an attacker who can obtain one valid signed webhook (e.g., by installing the app on their own store and capturing its webhooks) can relabel it as belonging to a victim shop. This is a cross-tenant data/state confusion issue: the victim's tenant record ends up processed with attacker-supplied body content, or attacker-controlled webhook content gets attributed to the victim shop's session/data. This crosses a tenant boundary using this gem's own trust decision (`Registry.process` -> handler dispatch), satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is bounded by the difficulty of obtaining an app's `api_secret_key`-signed webhook body — but the attacker does not need the secret itself, only a genuinely-signed webhook delivered to any store where they control the app installation (trivial for public/dev apps, or any shop the attacker can install the target app on). No shop-scoped nonce, timestamp binding, or shop field inside the signed payload is required by the gem to prevent this replay-with-relabeled-shop attack.

### Recommendation
Include the `shop-domain` header value inside the HMAC-signed material (or otherwise cryptographically bind it, e.g., signing `shop-domain + raw_body`), and have `Registry.process` reject requests where the header shop doesn't match the shop encoded in the verified payload. At minimum, document that host apps must independently corroborate `request.shop` against a session lookup keyed by webhook_id before trusting it for tenant attribution, or use Shopify's newer webhook validation that binds shop domain into the signed payload.

### Proof of Concept
```ruby
# Attacker installs the target app on their own dev store, and captures one
# legitimately Shopify-signed webhook delivery:
raw_body = capture_raw_body_from_shopify_delivery_to_attacker_shop
valid_hmac_b64 = capture_hmac_header_from_same_delivery

# Attacker replays it to the app's webhook endpoint, changing only the
# shop-domain header (not covered by the signature):
headers = {
  "X-Shopify-Topic" => "orders/create",
  "X-Shopify-Hmac-Sha256" => valid_hmac_b64,       # unchanged, still valid for raw_body
  "X-Shopify-Shop-Domain" => "victim-shop.myshopify.com", # attacker-controlled
  "X-Shopify-Api-Version" => "2025-01",
  "X-Shopify-Webhook-Id" => "whatever",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) passes (only raw_body is checked),
#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
#    dispatches attacker's body under the victim's identity.
```
