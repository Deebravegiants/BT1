### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant shop spoofing in `Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)`, which only proves that the **body** was signed with the app's `client_secret`. The `shop` (and `topic`/`webhook_id`) values that the gem hands to the application's handler come from HTTP headers that are never included in the signed material, so a request that passes HMAC validation can carry an attacker-chosen shop identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are read straight from HTTP headers that are completely outside the signed data: [2](#0-1) 

`Registry.process` treats a passing `HmacValidator.validate(request)` check as proof the whole request is legitimate, then forwards `request.shop` (and `request.webhook_id`) directly into `WebhookMetadata` given to the app's handler: [3](#0-2) 

The identity binding that should hold is:
`shop-domain header used by the app == shop bound inside the HMAC-verified bytes`

Because the HMAC only covers `@raw_body`, this equality does not hold — `shop` can be swapped freely by the caller of `Registry.process` without invalidating the signature, since the signature only certifies the body, not the header claiming which shop it came from. This is exactly the identity-binding gap the source report describes: a value ("shop") that consumers rely on for tenant identification is sourced from a channel (headers) different from — and not overlapping with — the channel that is actually cryptographically verified (the body).

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` is explicitly folded into `to_signable_string` and therefore is bound by the HMAC: [4](#0-3) 

No equivalent binding exists for `Webhooks::Request`.

### Impact Explanation
An unprivileged internet user who can obtain any one valid `(raw_body, hmac)` pair signed with the app's secret (e.g., a legitimate webhook delivered to their own, self-owned store where they installed the app) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Registry.process` will pass HMAC validation (body untouched) and hand the handler a `WebhookMetadata` claiming the event originated from the victim shop, even though the actual signed payload is the attacker's own data. Any application logic that uses `data.shop` returned by this gem to scope tenant data (the documented, expected use of `Registry.process`/`WebhookMetadata`) can be tricked into attributing/merging attacker-controlled event data into another merchant's tenant context — a cross-tenant data-integrity break rooted entirely in this gem's validation contract.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint plus one legitimately-signed webhook body (obtainable by installing the app on the attacker's own store, which needs no special privilege). No access to `api_secret_key`, tokens, or the victim's credentials is needed.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cryptographically tie the header-derived `shop` value to the verified body (e.g., require the shop domain to be embedded in and validated against the JSON payload, or compute the HMAC over `shop-domain + raw_body`). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-scoping key by the host application.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B`), header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays this exact `B`/`H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes HMAC over `B` only and it matches `H`, so validation succeeds.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` line 190) proceeds and calls the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: parsed(B) ...)`, misattributing attacker-controlled body content to the victim shop.
