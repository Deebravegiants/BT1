### Title
Unauthorized cross-user secret deletion due to unused/unhandled authorized-owner value in `GatewayHandler.handleSecretsDelete` - ([File: core/capabilities/vault/gw_handler.go])

### Summary
The reported AAVE bug class is: a security-relevant "true" value returned by a trusted internal call (the actual withdrawn amount) is computed but never used, and the code instead keeps operating on an unvalidated, caller-supplied value, leading to an accounting/authorization mismatch. The chainlink analog is in the Vault gateway handler's dispatch path: for `MethodSecretsList` the authoritative `authResult.AuthorizedOwner()` value produced by the authorization pipeline is explicitly substituted into the request (`r.Owner = authResult.AuthorizedOwner()`), but for `MethodSecretsDelete` this substitution is missing, so the request continues to use the caller-supplied `Owner` field taken directly from the untrusted client request.

### Finding Description
`GatewayHandler.HandleGatewayMessage` runs `vaulttypes.MethodSecretsDelete` and `vaulttypes.MethodSecretsList` through the same authorization pipeline (`h.requestProcessor.ProcessRequest`), which produces an `authResult` containing the caller's authorized identity/owner: [1](#0-0) 

The two dispatch handlers then diverge in how they use that `authResult`:

- `handleSecretsList` explicitly discards the client-supplied `Owner` and replaces it with the authorized value before calling the service: [2](#0-1) 

- `handleSecretsDelete` unmarshals the client-supplied `DeleteSecretsRequest` (which itself carries per-secret `Owner` identifiers inside `Ids`) and passes it straight to `h.secretsService.DeleteSecrets` without ever consulting `authResult`, and `authResult` is not even passed into the function: [3](#0-2) 

This is structurally the same defect pattern as the reported bug: the authoritative value produced by a trusted step (`authResult.AuthorizedOwner()` — analogous to Aave's "final withdrawn amount" return value) is computed but not threaded through to the operation that actually performs the sensitive state change (delete), while the sibling operation (list) demonstrates that the codebase itself treats this substitution as necessary. Whether this is fully mitigated depends on whether earlier validation in the pipeline (`ValidateSecretOwners`/`validator.go`) independently enforces that every `Owner` in the `DeleteSecretsRequest.Ids` matches the authorized caller — I was not able to fully confirm this from the available index within my remaining search budget, so this should be verified directly in `core/capabilities/vault/validator.go` / `validate_secret_owners.go` before treating this as a confirmed bypass.

### Impact Explanation
If the pre-dispatch pipeline validation does not strictly bind every `Owner` referenced in a `DeleteSecretsRequest` to `authResult.AuthorizedOwner()` (the same way `handleSecretsList` defensively does), an unprivileged/allow-listed caller could submit a `Delete` request whose `Owner` field references a different tenant/workflow owner, causing the node to delete secrets belonging to another user — a cross-user, unauthorized state-mutating action reachable directly from the internet-facing gateway.

### Likelihood Explanation
Likelihood depends entirely on whether `ValidateSecretOwners`/the request validator enforces ownership equality for the `Delete` method before `ProcessRequest` returns success. The `List` handler's explicit `r.Owner = authResult.AuthorizedOwner()` override strongly suggests that owner correctness for outbound service calls is not universally guaranteed purely from the earlier pipeline step, and the omission of the same defensive step for `Delete` is inconsistent with that pattern — increasing the likelihood that this is a genuine, not-yet-hardened gap rather than an intentional simplification. This should be treated as **unconfirmed but plausible** given the asymmetry between the two handlers.

### Recommendation
- Mirror the `handleSecretsList` pattern in `handleSecretsDelete`: pass `authResult` into `handleSecretsDelete` and either overwrite/validate every `Owner` in `DeleteSecretsRequest.Ids` against `authResult.AuthorizedOwner()` before calling `h.secretsService.DeleteSecrets`.
- Audit `core/capabilities/vault/validator.go` and `validate_secret_owners.go` to confirm (and add a regression test for) strict owner-binding for the `Delete` method specifically, not just `Create`/`Update`.
- As a general rule, any authoritative value returned by an authorization/validation step (the "final" owner/amount/identity) should be the single source of truth used downstream — client-supplied copies of the same field should never be trusted directly, mirroring the Aave `withdraw()` return-value fix recommended in the source report.

### Proof of Concept
Not independently reproducible from the indexed code alone — reproducing this would require confirming (via a Devin session with full repo access) whether `ValidateSecretOwners`/the request validator invoked inside `ProcessRequest` for `MethodSecretsDelete` rejects requests where any `Ids[].Owner` differs from the authorized caller's identity. If it does not, a PoC would be: an allow-listed workflow/caller submits a `vaulttypes.MethodSecretsDelete` JSON-RPC request through the gateway with `Ids: [{Owner: "<victim-address>", ...}]`, and observe that `secretsService.DeleteSecrets` is invoked with the victim's owner rather than being rejected or rewritten to the caller's own authorized owner.

func (h *GatewayHandler) handleSecretsDelete(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.DeleteSecretsRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	h.lggr.Debugw("Processing authorized delete secrets request", "request", r.String())
	resp, err := h.secretsService.DeleteSecrets(ctx, r)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.HandlerError, fmt.Errorf("failed to delete secrets: %w", err))
	}

	resultBytes, err := resp.ToJSONRPCResult()
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}

	return &jsonrpc.Response[json.RawMessage]{
		Version: jsonrpc.JsonRpcVersion,
		ID:      req.ID,
		Method:  req.Method,
		Result:  (*json.RawMessage)(&resultBytes),
	}
}
