The codebase already implements excess-payment refunds in multiple places. Let me verify whether there's any reachable path where an overpayment is accepted but not refunded.### Title
Repay overpayment "refund" pays out declared excess from pool custody without verifying any inbound transfer - (File: contracts/pool/src/ops/repay.rs)

### Summary
The AvailBridge report concerns excess-payment handling: value above the required amount is accepted without being reconciled to the payer. The XOXNO Lending analog lives in the same code shape — the pool's repay leg computes an "overpayment" refund purely from the *declared* `action.amount`, then pays that refund out of the pool's real token custody without checking that any tokens were actually transferred in, and without debiting the cash book. On a market with no outstanding debt, the entire declared amount becomes "excess" and is paid to an arbitrary `payer` out of suppliers' funds.

### Finding Description
`ops::repay::accounting` resolves the declared amount into `(burned, overpayment)` via `cache.resolve_repay(amount, position)` and credits only `net_repay = amount - overpayment` to cash. `apply` then calls `outcome.cache.transfer_out(payer, outcome.overpayment)`, sending the refund from the pool's own balance. Neither step verifies that the pool received `amount` tokens — the pool trusts that the controller prefunded it (`debt.rs::settle_repay` does `transfer_amount_measured` into the pool first, but the pool itself does not check custody).

When a market carries no debt (`current_debt_ceil == 0`), `resolve_repay` treats the whole declared `amount` as overpayment: `net_repay == 0`, the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct, `cash` is untouched, and `transfer_out(payer, amount)` drains real custody. The same gap exists in `ops::recapitalize::apply`, where `refund = amount - applied` is paid out the same way. This is demonstrated by the pool's own test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (contracts/pool/tests/flows.rs:3590), which repays `custody_before` on a zero-debt market and asserts custody is drained while the book is unchanged.

If `Pool::repay` / `Pool::recapitalize` are callable by any address with a chosen `payer`/`refund_to` (as the direct client calls in the pool test suite indicate), an unprivileged attacker can repeatedly declare large repays on debt-free markets and receive the full pool balance as "refunds". If those entrypoints are controller-gated, the exposure narrows to whatever paths the controller exposes — but the pool-level refund still never reconciles declared vs. received amounts.

### Impact Explanation
The refund is drawn from pool custody, not from a verified inbound transfer, so each call transfers supplier-backed tokens to the attacker while `cash` on the book stays unchanged — bookkeeping and custody diverge, and suppliers' principal is stolen. Repeated calls on every zero-debt or low-debt (hub, token) book can drain the physical pool balance, producing direct theft of user funds and eventual insolvency of remaining books.

### Likelihood Explanation
The trigger requires only a market whose outstanding debt is below the declared amount — trivially satisfiable on any freshly listed or fully repaid market, or by declaring an amount just above existing debt. No privileged role, oracle manipulation, or timing is needed: a single transaction declaring `repay(amount)` with `payer = attacker` suffices wherever the pool entrypoint is reachable. The behavior is deterministic and already encoded as a passing test.

### Recommendation
Reconcile the refund against measured inbound funds, not the declared amount:
- Snapshot the pool's token balance before the repay batch and cap `overpayment` (and `recapitalize`'s `refund`) at the measured balance increase, or
- Have the controller pass the measured receipt (`amount_in` from `transfer_amount_measured`) as the action amount and require `overpayment <= measured_in`, and/or
- Gate `repay`/`recapitalize` to the controller contract so declared amounts always correspond to a just-executed prefund, and debit the refund against the prefunded receipt rather than custody.

### Proof of Concept
1. Deploy pool + a listed market with suppliers' cash `C` and zero debt.
2. Attacker calls `Pool::repay(payer = attacker, actions = [PoolAction { hub_asset, amount: C, position: 0 }])` transferring nothing.
3. `resolve_repay` returns `overpayment = C`, `net_repay = 0`; the `RepayRoundsToZeroShares` check passes via `net_repay == 0`.
4. `transfer_out(attacker, C)` moves the entire pool balance to the attacker; `cash` still reads `C`.
5. Existing test evidence: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (contracts/pool/tests/flows.rs:3590-3611) executes exactly this and asserts `credited == 0` with custody drained.

Note: I was unable to confirm the exact authorization checks on `Pool::repay`/`Pool::recapitalize` in `contracts/pool/src/lib.rs` (grep returned match counts without content). The direct, unauthenticated client calls in the pool's own test suite indicate no caller gate, but if the pool enforces controller-only invocation, the finding's reachability depends on whether any unprivileged controller path can drive an unfunded repay — the refund-vs-receipt mismatch in `repay.rs`/`recapitalize.rs` remains the root cause either way.
