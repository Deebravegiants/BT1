Found it: `pallet-bandwidth`'s `try_consume` gate walks the entire `Allowance` FIFO `BoundedVec` (up to 1024 subscriptions) on every single non-purchase POST request, and that same bounded vector can be driven toward its cap by an attacker who is not the app owner — anyone can call `BandwidthManager.purchase()` for a victim `(app_chain, app)` pair with `months = 1` at the cheapest tier, repeatedly, since `purchase()` has no access control tying the caller to the `app` being credited. This is directly analogous to the reported `nonces` unbounded-loop pattern: an attacker-growable array that a hot, permissionless path (`try_consume`, invoked by the ISMP router on every message from that source chain to that app) must linearly scan/mutate.

### Title
Unbounded per-message linear scan/eviction over an attacker-inflatable subscription FIFO in `BandwidthGate::try_consume` - (File: `modules/pallets/bandwidth/src/lib.rs`, `modules/pallets/bandwidth/src/types.rs`)

### Summary
`pallet-bandwidth`'s `BandwidthGate::try_consume` is invoked by the ISMP router on **every** non-purchase POST request from a bandwidth-managed source chain to a metered app [1](#0-0) . It sweeps expired entries and then drains from the head of the `(chain, app)` subscription `BoundedVec` (capped at 1024 entries) until the requested bytes are satisfied [2](#0-1) . `BandwidthManager.purchase()` on the EVM side is **fully permissionless** — any `msg.sender` can pay to append a subscription to an arbitrary `app`/`chain` pair, since the only checks are on `app.length`, `chain.length`, `months`, and a configured tier price [3](#0-2) . The pallet appends every purchase for that `(app_chain, app)` key regardless of who paid [4](#0-3) .

### Finding Description
Every legitimate message an app dispatches through Hyperbridge triggers `try_consume`, which must walk the subscription list from the head, summing/deducting `remaining_bytes` and popping exhausted entries in place [5](#0-4) . Because the FIFO cap is 1024 and eviction only occurs on overflow-push (which pops the *oldest* entry, not necessarily the attacker's), any address can repeatedly call `purchase()` with `months = 1` against a victim app's `(chain, app)` key — the cheapest tier still creates a full-weight `Subscription` entry that must be linearly walked on every gated message the victim tries to send. `Self::push_subscription` mutates the whole `BoundedVec` under a single storage key on every purchase and the same key is read/written entirely on every `try_consume` call [6](#0-5) . This mirrors the reported bug class in `SafeGuard.checkTransaction`: an attacker-controllable, unbounded (here, capped-but-fully-fillable-by-anyone) array that a permissionless, per-message hot path must scan on every call, driving up cost (weight/PoV in this case) proportional to array size rather than to the actual work needed.

### Impact Explanation
An attacker can grief a competing or targeted app by cheaply purchasing many small/short subscriptions against the app's `(chain, app)` key (bounded only by gas/fee cost of repeated `purchase()` calls, and the tier price floor set by governance), inflating the FIFO close to its 1024-entry cap. Every subsequent legitimate message from that source chain to that app then pays the cost of a maximal FIFO scan/eviction in `try_consume`, increasing the weight charged against `handle_unsigned` for otherwise ordinary, permissionless message delivery, and — depending on how conservatively the pallet's declared weight for message handling accounts for this — could push actual execution weight for a block of messages past what was budgeted, causing relayer-submitted deliveries to under-price their weight or fail. Because delivery is meant to be permissionless and cheap for anyone to relay, this degrades liveness of the routed app's cross-chain messaging (a route becoming effectively unable to deliver messages promptly is one of the accepted impact classes).

### Likelihood Explanation
Likelihood is high in that `purchase()` is deliberately open to any caller (sponsorship is a documented, intended feature) and costs only the tier price, which governance may set very low for the cheapest tier [7](#0-6) ; there is no minimum-months, per-caller, or per-app-owner restriction preventing a non-owner from padding a victim's subscription list. The severity of the resulting griefing depends on the actual byte cost of a max-length scan relative to the message-handling weight budget, which was not directly measured here.

### Recommendation
Bound how much churn a single non-owner purchaser can add to another app's queue (e.g., cap subscriptions-per-purchaser-per-window, or require app-owner authorization for `purchase()` sponsorship of a given `(chain, app)`), and/or change `try_consume`'s cost model so it does not scale linearly with the full FIFO length on every gated message (e.g., track a running `total_remaining_bytes` aggregate updated incrementally on push/consume rather than re-summing/walking the list, and defer expiry-sweeping to a bounded batch rather than doing it inline on the hot path).

### Proof of Concept
1. Governance registers a `BandwidthManager` for a source chain and configures at least one low-price tier via `set_tier`/`dispatch_set_tiers` [8](#0-7) .
2. An attacker, not affiliated with victim app `V`, calls `BandwidthManager.purchase(app=V, tier=cheapest, months=1, chain=V_chain)` repeatedly (e.g., 1000 times) — nothing in `purchase()` checks that the caller controls `V` [9](#0-8) .
3. Each purchase message is relayed and accepted by `pallet-bandwidth`'s `on_accept`, appending a `Subscription` to `Allowance[V_chain][V]` via `push_subscription`, growing the FIFO toward the 1024 cap [4](#0-3) .
4. `V`'s own legitimate cross-chain messages, or any relayer delivering them, now trigger `try_consume` against a maximally-long FIFO on every single message, incurring the cost of scanning/evicting up to 1024 entries per gated request [5](#0-4) , degrading throughput/latency for `V`'s messaging route without `V`'s consent or ability to prevent it.

A tier is a `(bytes, duration_secs)` SKU on the pallet, paired with an 18-decimal price on the manager. Purchases scale both axes linearly by `months`:

allowance.cost          = tier.price × months   (18-decimal, scaled to fee-token decimals)

```text
### Drain order

The gate drains from the **head** of the list. Once the head is fully consumed it pops and continues into the next. If the next entry is expired it's swept silently — what you paid for is yours only until it expires.

This matters when you queue multiple tiers: the cheapest/oldest entry is consumed first regardless of which tier it came from. Plan top-ups so a higher tier doesn't sit behind a soon-to-expire lower tier you'd rather burn last.

### Eviction

Pushing onto a full list (1024 entries) evicts the **oldest** entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain. In practice this only happens under pathological repeat-buy behavior — at the default of one purchase per cycle, 1024 buys is years of headroom.

### Expiry sweep

The gate retains expired entries in storage until the next consume call, at which point it filters them out in place. Reading `Pallet::remaining(chain, app)` or `Pallet::allowances(chain, app)` always returns the live-filtered view — expired entries never leak into the public-facing API.
```

```text
Every non-purchase POST request from a registered source chain runs through `BandwidthGate::try_consume(source, app, bytes)`:

1. If the app is on the **allowlist** for that source, return `Ok` without touching the ledger.
2. Sweep expired subscriptions in place.
3. If no live subscriptions remain → `GateError::NoAllowance`.
4. Sum `remaining_bytes` across live entries. If the sum is short → `GateError::Insufficient { remaining, required }`. **No mutation happens in this case** — the caller can retry after a top-up.
5. Otherwise drain from the head until the requested bytes are satisfied. Pop entries that hit zero. Emit `BandwidthConsumed` with the post-deduct remaining.

The "no mutation on insufficient" property is load-bearing: it means a top-up race is safe — if a message arrives between when an app notices it's short and when the top-up lands, the message stays rejectable rather than half-consuming the subscription.
```

    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || app.length > MAX_APP_LENGTH || chain.length == 0 || months == 0) {
            revert InvalidPurchase();
        }
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

        commitment = IDispatcher(_host).dispatch(
            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );

        emit BandwidthPurchased({
            payer: msg.sender,
            feeToken: feeToken,
            tier: tier,
            months: months,
            amountPaid: amount,
            app: app,
            chain: chain,
            commitment: commitment
        });
    }

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});
