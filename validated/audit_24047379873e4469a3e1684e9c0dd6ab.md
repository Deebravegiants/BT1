### Title
Webhook tenant identity (`shop`) is trusted from an HTTP header that is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` (tenant) value used by the host application to route/attribute the webhook is read from a separate, unsigned HTTP header.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Webhooks::Registry.process` validates the HMAC over the `Request` object with `Utils::HmacValidator.validate(request)` [2](#0-1) , which in turn calls `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., HMAC(secret, raw_body) — and compares it via `OpenSSL.secure_compare` [3](#0-2) . Meanwhile `request.shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header [4](#0-3) , and that unauthenticated value is passed straight into `WebhookMetadata` as the tenant identifier handed to the host app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [5](#0-4) .

The identity binding that should hold is: `HMAC-covered bytes == bytes used to identify the shop`. Instead, the equality that actually holds is: `HMAC(secret, raw_body) == received_hmac` while `shop == header value that is never included in the signable string`. Because Shopify's real webhook HMAC (in the actual platform) is computed only over the body too, this in itself is not new — but within this gem, nothing enforces that the `shop-domain` header the app trusts for tenant attribution was ever bound to the signed payload. Any header value can be substituted by a network intermediary or a component that constructs `headers` from lower-trust input, and the HMAC check will still pass as long as the body is unmodified and correctly signed by the real Shopify secret for *some* legitimately-topic'd payload — the `shop` header is not part of what is verified.

### Impact Explanation
If a host application relies solely on `WebhookMetadata#shop` (populated from this unauthenticated header) to determine which merchant's data/session to update, an attacker capable of influencing headers before this gem's `Request.new` (e.g., a shared/misconfigured proxy, header-injection point, or a component that merges attacker-controlled headers) could get a validly-signed webhook body attributed to a different shop of the attacker's choosing, causing cross-tenant data confusion. This matches the "field acted on but not covered by the HMAC" analog category. However, this requires an intermediary condition (control over headers reaching the gem) that is not guaranteed to be reachable purely over the internet against a correctly configured host app in the normal Shopify webhook delivery path, so exploitability depends heavily on how the host application sources `headers` for `Webhooks::Request.new`.

### Likelihood Explanation
Low-to-Moderate. In the standard Shopify-to-app webhook delivery, the `shop-domain` header is set by Shopify itself; an unprivileged internet attacker cannot directly craft a webhook accepted by `Utils::HmacValidator.validate`, because they don't possess `api_secret_key` to forge a valid HMAC over an arbitrary body of their choosing tied to a different shop. The realistic risk surface is narrower: if a host app front-end (e.g., a shared load balancer, or reused connection with header leakage) allows header spoofing while preserving a previously-valid signed body/HMAC pair (replay with header swap), the mismatch between what's verified (body) and what's trusted (shop header) becomes exploitable. This is a real gap in the binding but is conditioned on infrastructure/replay factors outside pure request forgery.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the material verified by the HMAC, or at minimum document/verify that these header-derived fields must be treated as authenticated only after successful HMAC validation and mandate that host apps never trust `shop-domain` from a source that could diverge from the actual signed delivery channel. Consider exposing an API that lets consumers assert the expected shop out-of-band (e.g., matching against the shop tied to the webhook subscription that was registered) rather than trusting the raw header value implicitly.

### Proof of Concept
Conceptual (cannot be fully executed without live Shopify HMAC secret/signed payloads):
1. Attacker/proxy intercepts a legitimately Shopify-signed webhook POST for `shop-a.myshopify.com` (valid `raw_body` + valid `x-shopify-hmac-sha256`).
2. Attacker replays the exact same `raw_body` and `hmac-sha256` header, but rewrites `x-shopify-shop-domain` to `shop-b.myshopify.com`.
3. `Webhooks::Request.new` accepts the mutated headers (only checks presence, not consistency) [6](#0-5) .
4. `Registry.process` validates HMAC successfully (body unchanged) and calls the handler with `shop: "shop-b.myshopify.com"` [7](#0-6) , causing the host app to process/attribute shop-a's webhook payload as belonging to shop-b.

Note: this PoC depends on an attacker being able to intercept/replay a delivery and alter headers before this gem parses them — I could not verify within this gem's code whether a realistic host integration path exposes this to a fully unauthenticated, non-interception-based internet attacker. Given the scope's exclusion of TLS interception and given normal Shopify delivery integrity, this finding should be treated as a design/documentation gap in the binding rather than a directly exploitable remote vulnerability under the stated constraints.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
