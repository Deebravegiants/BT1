### Title
Webhook HMAC does not bind the `shop` (or `topic`) identity to the signed payload, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , and `Utils::HmacValidator.validate` verifies the incoming `hmac` solely against that signable string using the app's shared `api_secret_key` [2](#0-1) . The `shop` value used to identify the tenant, however, is taken from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header [3](#0-2)  and is never included in the signed material. `Registry.process` validates the HMAC and then immediately trusts `request.shop` to dispatch the event to the handler [4](#0-3) .

### Finding Description
The binding that should hold is:
`HMAC-verified bytes == bytes used to identify the tenant (shop) that the event is attributed to`

In this gem, that equality is broken: the HMAC only covers `@raw_body` [1](#0-0) , while `shop` is read from a plain, unsigned header [3](#0-2) . Because the app's `api_secret_key` is shared across every shop that has installed the app, any merchant that installs the app can legitimately receive a validly-HMAC-signed webhook body for their own shop. That attacker-controlled merchant can then capture the `raw_body` + `hmac-sha256` pair from a webhook Shopify sent them, and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain (also an installed shop of the same app). `Utils::HmacValidator.validate` will still succeed because it never checks the shop header [5](#0-4) , and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is the victim's domain, not the domain that actually produced the payload [6](#0-5) .

### Impact Explanation
This is a cross-tenant data/event confusion: an app cannot distinguish "this body genuinely originated for shop X" from "this body originated for the attacker's own shop but is being replayed under shop X's identity." For any host application that uses `WebhookMetadata#shop` to key persistence, trigger per-tenant business logic, or handle mandatory compliance webhooks (`customers/redact`, `shop/redact`, `app/uninstalled`), this allows a low-privileged attacker (who only needs to install the same public/free app on their own store) to inject or forge events attributed to a different merchant. This matches the Critical category of cross-tenant access.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the attacker to (a) install the target app on a shop they control (to receive legitimately-signed webhook traffic under the shared `api_secret_key`), and (b) know or guess a victim shop's domain that also uses the same app, and (c) the host application must not perform any additional shop-authorization check (e.g. cross-referencing shop against a known-installed-shops list) before trusting `WebhookMetadata#shop`. The gem itself provides no such secondary check and documents `Registry.process` as the complete verification step [7](#0-6) , so any app that follows the documented usage pattern is exposed. This is a real weakening of the identity-binding guarantee (mirroring the report's "field acted on but not covered by the [safety mechanism]" bug class), rather than a purely theoretical concern, because it is Shopify's own documented HMAC scheme that only covers the body — but this gem provides no mitigation or warning about the shop-header trust gap.

### Recommendation
Bind the tenant identity into the value used for HMAC verification, or otherwise cryptographically corroborate `request.shop`. Options:
- Include `shop`, `topic`, and `webhook_id` in the signed material rather than relying on `@raw_body` alone (requires coordinating with Shopify's signature scheme, which is body-only, so this may instead require an application-level secondary check).
- At minimum, document/require that consuming applications verify `request.shop` against their own list of known-installed shop domains before trusting `WebhookMetadata#shop`, and add such a check as an opt-in verification step in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's shared `api_secret_key`.
2. Shopify sends a webhook to the app's endpoint with body `{"id":1,...}` and header `x-shopify-hmac-sha256: <valid HMAC of body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `raw_body` [1](#0-0)  and succeeds because the body is unmodified [2](#0-1) .
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker's payload>, ...)` [6](#0-5) , causing the host application to process attacker-controlled data as if it belonged to the victim shop.
