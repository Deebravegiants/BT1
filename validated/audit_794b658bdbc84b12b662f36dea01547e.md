### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a successful HMAC check as proof that an *entire webhook request* — including which shop and topic it belongs to — came from Shopify. In reality, `ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, so the `shop-domain` and `topic` HTTP headers are never covered by the signature. Anyone who can produce or capture one genuine `(body, hmac)` pair signed with the app's `api_secret_key` (trivially available to any developer who installs their own app on a free/dev store and receives a real webhook) can replay that pair to the victim app's public webhook endpoint with arbitrary `shop-domain`/`topic` headers, and the check will still pass.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; `shop` and `topic` are read straight from attacker-controllable HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`HmacValidator.validate` verifies exactly this unbound value: [3](#0-2) 

`Registry.process` uses the HMAC result as the sole authenticity gate, then dispatches on the (unverified) `topic` header and forwards the (unverified) `shop` header straight to the app's handler as trusted tenant identity: [4](#0-3) 

The equality the gem is supposed to guarantee is:
`shop/topic delivered-to-handler == shop/topic that produced this exact HMAC-signed body`

What is actually verified is only:
`HMAC(raw_body, api_secret_key) == received_hmac`

Because `shop-domain` and `topic` are not part of the signed material, the check passes for *any* combination of headers as long as the `(raw_body, hmac)` pair was legitimately produced by Shopify for **any** shop/topic using the same app credential. This is exactly the "field acted on but not covered by the HMAC" bug class: the identity used downstream (`data.shop`, `data.topic` in `WebhookMetadata`) is not the identity the cryptographic check actually authenticates.

The gem's own documentation reinforces that developers rely on `process` for full authenticity: "This will verify the request did indeed come from Shopify" — but it does not verify which shop/topic it came from. [5](#0-4) 

### Impact Explanation
The webhook HTTP endpoint is public (reachable by any internet user who knows/guesses the path) and, per the gem's design, has no authentication beyond this HMAC check. An attacker who has ever received one legitimate webhook for their own shop (e.g., by installing their own copy of the app on any store, or via the public app's own installation flow) obtains a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`. They can then POST that exact body/hmac to the target app's webhook endpoint while setting `x-shopify-shop-domain` to a victim shop and `x-shopify-topic` to any registered topic. `Registry.process` will accept it, route it to the corresponding handler, and hand the handler a `WebhookMetadata` claiming it is data for the victim shop. If the host application uses `data.shop` to key per-tenant storage or trigger tenant-scoped side effects (the exact pattern the docs example encourages — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this allows cross-tenant data injection/corruption attributed to a shop the attacker does not control — a cross-tenant integrity breach.

### Likelihood Explanation
Exploitation requires only: (1) one legitimately signed webhook body from any shop using the same app credential — obtainable by any developer/user who can install the target app on a shop they control, and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers, which is possible for any unprivileged internet user since the endpoint's only defense is this HMAC check. No access to `api_secret_key`, tokens, or privileged accounts is required.

### Recommendation
Bind `shop` and `topic` (and any other header-derived routing/identity data) into the HMAC-verified signable string, or otherwise cryptographically tie them to the specific delivery (e.g., verify against Shopify's per-delivery webhook id/shop registered for that topic via a lookup, not solely trusting headers). At minimum, document and encourage host apps to independently confirm that `data.shop` corresponds to a shop with an active, matching webhook registration/session before trusting it as tenant identity, since the HMAC alone does not authenticate that binding.

### Proof of Concept
1. Attacker creates a Shopify app using the same `client_secret` as the target production app (or is themselves an installer of the target public app on a store they own) and registers for topic `orders/create`. Shopify delivers a legitimate webhook to the attacker's own endpoint with headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and body `B`.
2. Attacker captures `(B, H)`.
3. Attacker sends `POST /callback/orders/create` to the victim's app deployment with body `B` unchanged, `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(B, api_secret_key)` and it matches `H` (since the secret and body are unchanged), per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb#to_signable_string`.
5. `Registry.process` invokes the app's `orders/create` handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, per `lib/shopify_api/webhooks/registry.rb#process`, causing the host app to process attacker-controlled data under the victim shop's identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
