Based on my investigation, I've confirmed a valid analog vulnerability in the webhook shop-domain/HMAC binding.

### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` (the tenant identifier the app acts on) is read from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header, which is never included in the HMAC-signed material.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` to compute the HMAC: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, but `shop` is extracted independently from the `shop-domain` header via `shopify_header("shop-domain")`, completely outside the signed content: [3](#0-2) [4](#0-3) 

The identity binding this breaks is: `HMAC-verified bytes == bytes the app trusts as the tenant identity`. In reality, `HMAC-verified bytes == raw_body only`, while `tenant identity used downstream == shop-domain header (unverified)`.

After validation succeeds, `Registry.process` passes `request.shop` straight into `WebhookMetadata`, which is delivered to the app's handler as the authoritative shop for that event: [1](#0-0) 

The documented usage pattern shows apps trusting `data.shop` directly to route/attribute the webhook to a tenant (e.g. enqueuing a job keyed by `shop_domain: data.shop`): [5](#0-4) 

### Impact Explanation
`api_secret_key` is shared by the app across **all** installed shops — it is not shop-specific. Since `shop-domain` isn't part of the signed payload, any unprivileged attacker who has installed the app on their **own** shop can capture a genuine webhook (valid HMAC for their own body) and replay it with the `X-Shopify-Shop-Domain` header changed to a victim tenant's domain. The HMAC still validates because it only checks `@raw_body`, and the app's handler will process/attribute the (attacker-controlled, for their own shop) body as if it originated from the victim shop. This is a cross-tenant identity confusion: the app acts on a shop identity it never actually verified, potentially triggering tenant-scoped side effects (writes, job enqueues, state changes) attributed to the wrong merchant.

### Likelihood Explanation
Exploitation only requires an unprivileged attacker with any shop that has the target app installed (a normal, low-barrier precondition for any public/multi-tenant Shopify app) — no access token, no `client_secret`, and no TLS interception is needed. The attacker can freely choose the header value since it's outside the HMAC scope.

### Recommendation
Include the shop domain (and ideally topic/api-version/webhook-id) in the signed material used for HMAC verification, or otherwise cryptographically bind the shop identity to the payload before trusting it (this mirrors Shopify's real webhook signing where verification is body-only — this gem should compensate by not treating the unauthenticated header as tenant-trusted, or by requiring the caller/host app to cross-check `shop` against a session look-up before acting).

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`, receives a legitimate webhook `orders/create` with header `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`.
2. Attacker replays the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` recomputes HMAC over `request.to_signable_string` (== `raw_body` only) and it matches, so validation passes.
4. `ShopifyAPI::Webhooks::Registry.process` builds `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)` and calls the app's handler, which trusts `data.shop` as the tenant for this event — despite the payload never actually being authenticated as coming from `victim.myshopify.com`.
