### Title
Webhook `X-Shopify-Shop-Domain` and `X-Shopify-Topic` Headers Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface used by `HmacValidator` to authenticate inbound webhook calls, but its `to_signable_string` method returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and passed straight to the application's webhook handler. This breaks the identity binding `bytes verified == bytes trusted for tenant identity`, since only the body is verified while the shop identity used for tenant dispatch is not.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from HTTP headers that are never part of the signed payload: [2](#0-1) 

`HmacValidator.validate` (and the underlying `validate_signature`) only recomputes and compares the HMAC of `to_signable_string`, i.e., the raw body — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` calls this same validation and then dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` values: [4](#0-3) 

Because the shop identity is never bound into the HMAC, the equality the app relies on — `shop authenticated by Shopify == shop dispatched to the handler` — does not hold. Any HTTP body that produces a valid HMAC under the app's own `api_secret_key` (which an attacker can freely obtain by triggering a real webhook delivery to a webhook endpoint they control, using their own Shopify development/test store — since the same `client_secret` is shared across all shops that installed the app) can be replayed to the victim application's webhook endpoint with the `X-Shopify-Shop-Domain` header (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) swapped to any other value. The HMAC check still passes because it never covered those headers.

### Impact Explanation
Multi-tenant Shopify apps route webhook processing and typically persist/act on data keyed by `WebhookMetadata#shop`, which comes straight from this forged header. An attacker who has installed the app on their own shop (a routine, unprivileged action) can generate arbitrary attacker-controlled, validly-signed webhook bodies (e.g., `orders/create`, `customers/create` payloads with attacker-chosen field content) and replay them against the same endpoint while claiming an arbitrary victim `shop` domain and/or topic. This is a cross-tenant data-integrity/confusion vulnerability: the receiving app cannot distinguish "a message legitimately about shop A" from "a message signed for shop A's payload but relabeled as shop B," which can pollute or corrupt victim tenants' data paths, trigger unauthorized actions keyed by `shop`, or be combined with topic confusion to route one webhook type's body into a different handler. This satisfies the Critical "cross-tenant access" impact class since tenant isolation depends solely on the unauthenticated `shop` header.

### Likelihood Explanation
Likelihood is high for any application built on this gem's default `Webhooks::Request`/`Registry.process` path: no special access beyond installing the app on one's own store (or intercepting/observing one legitimate webhook) is required, and the forgery only requires replaying an HTTP POST with modified headers — no cryptographic secret needs to be broken because the fields that matter for tenant dispatch were simply never part of the signed material.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, e.g., via a dedicated MAC that covers the full header+body tuple) so `HmacValidator.validate` fails whenever any of these dispatch-relevant fields are altered relative to what Shopify actually signed. At minimum, document and enforce that consumers must not treat `request.shop`/`request.topic` as authenticated unless they perform their own additional verification (e.g., checking the shop against a known list of installed, active offline sessions) before dispatch.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `customers/create`) with attacker-chosen JSON body content. Shopify computes and sends `X-Shopify-Hmac-Sha256` over that raw body using the app's shared `api_secret_key`.
2. Capture the raw body and the resulting valid `X-Shopify-Hmac-Sha256` value.
3. Re-POST the same raw body + valid HMAC header to the app's public webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL.secure_compare` against `to_signable_string` (the raw body) — the swapped `shop`/`topic` headers do not affect this check, so validation succeeds: [5](#0-4) 
5. The application's registered handler is invoked with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"` even though the payload actually originated from and was crafted by the attacker's own shop.
