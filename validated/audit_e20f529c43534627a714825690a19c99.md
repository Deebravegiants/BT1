Audit Report

## Title
Stale/Rotated Workflow Signer Keys Remain Valid For HTTP Trigger Authentication Due To Cross-Shard "First-Writer-Wins" Metadata Merge - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.syncMetadata` iterates `h.shards` sequentially and merges each shard's `Aggregate()` output into shared `authorizedKeys`/`workflowIDToRef` maps, but for a `workflowID` already registered from an earlier shard with a matching `workflowReference`, it only appends the shard to the fan-out list and never overwrites `authorizedKeys[workflowID]` with a newer key set from a later shard. [1](#0-0)  This means a stale (pre-rotation) `AuthorizedKeys` observation that reaches quorum first in one shard can persist in `h.authorizedKeys` and continue to be accepted by `Authorize()` even after another shard has already converged on the rotated key set for the same workflow. [2](#0-1) 

## Finding Description
`WorkflowMetadataAggregator.Collect` keys observations by the digest of the full `WorkflowMetadata` (including `AuthorizedKeys`), so a key rotation produces a new digest/observation while the old one remains until `cleanupInterval` elapses without renewed observations. [3](#0-2)  `Aggregate()` sorts all quorate observations newest-first by `sequence` within a single shard, explicitly so that "workflows that were registered most recently take precedence." [4](#0-3)  However, this newest-first ordering is only local to each shard's aggregator; `syncMetadata` does not do a global re-sort or re-merge across shards' outputs by sequence number before writing into `authorizedKeys`. [5](#0-4)  The unit test `TestMultiShardAssignment` confirms that the same `workflowID` is designed to be legitimately reported and merged from multiple shards (the sharding fan-out model), which is exactly the scenario in which this ordering gap becomes exploitable during propagation delays. [6](#0-5)  `Authorize()` is the sole authentication gate for HTTP-triggered JSON-RPC requests and relies entirely on the (potentially stale) `h.authorizedKeys[workflowID]` map populated by `syncMetadata`. [7](#0-6) 

## Impact Explanation
This is a genuine, code-confirmed authentication bypass window: an attacker holding a rotated-out private key can still have JWT-signed HTTP trigger requests accepted as long as any shard's aggregator retains the stale observation (up to the full `cleanupInterval`, default 10 minutes, or longer if propagation to the affected shard/its nodes' quorum is delayed). This maps to the in-scope "node API authentication or role bypass" / "gateway request impersonation" impact category, since it allows execution of a workflow trigger using a signer the workflow owner has explicitly revoked.

## Likelihood Explanation
No malicious node, peer, or elevated privilege is required — this is triggerable by an ordinary external caller who retains an old private key and issues a normal signed HTTP trigger request during the natural, expected propagation window created by asynchronous per-shard metadata pull/aggregation (`MetadataPullIntervalMs`, `MetadataAggregationIntervalMs`, `cleanupInterval`). This is a realistic and repeatable condition, particularly relevant to the exact scenario key rotation is meant to protect against (responding to key compromise).

## Recommendation
In `syncMetadata`, when merging observations for the same `workflowID`/`workflowReference` across shards, compare the `sequence` (or another recency indicator) of the winning per-shard observation and always retain the most recent `AuthorizedKeys` set globally instead of the first one encountered while iterating `h.shards`. Concretely: collect all per-shard aggregated observations for a given workflow reference first, then select the one with the highest global sequence number before writing to `authorizedKeys`, `workflowRefToID`, and `workflowIDToRef`. Additionally, consider shortening/aligning `cleanupInterval` with the metadata pull/aggregation cadence to reduce the propagation/staleness window after a rotation.

## Proof of Concept
1. Workflow `W` (fixed owner/name/tag) is registered with `AuthorizedKeys = [K_old]`, reaching quorum on shard A and shard B, producing observation digest `D_old` in both aggregators.
2. The workflow owner rotates keys to `[K_new]`; new metadata (`D_new`) begins propagating to nodes.
3. Due to normal propagation timing, shard A's aggregator still reports `D_old` (not yet reaped, within `cleanupInterval`) while shard B's aggregator has already converged on `D_new`.
4. `syncMetadata` runs: because `h.shards` is iterated in fixed order, if shard A is processed before shard B, `authorizedKeys[W]` is set to `{K_old}` via "Case 3"; shard B's later `D_new` observation for the same `workflowReference` hits "Case 1" and is merely appended to `workflowShards[W]` without updating `authorizedKeys[W]`.
5. An attacker holding `K_old`'s private key signs a JWT and sends an HTTP trigger request for workflow `W`; `Authorize()` looks up `h.authorizedKeys[W]`, finds `K_old` still present, and accepts the request.
6. A Go unit test extending `TestMultiShardAssignment` can directly demonstrate this: collect an old-key observation to quorum in shard 0, collect a new-key observation (different digest, higher sequence) to quorum in shard 1, call `syncMetadata`, then assert that `handler.authorizedKeys[workflowID]` still contains the old key and `Authorize()` succeeds with a JWT signed by the old (rotated-out) key.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

// Aggregate returns the aggregated workflow metadata for workflows that have reached the threshold.
// Results are sorted chronologically by sequence number (newest first, oldest last).
func (agg *WorkflowMetadataAggregator) Aggregate() []gateway_common.WorkflowMetadata {
	agg.mu.RLock()
	defer agg.mu.RUnlock()

	type aggregatedObs struct {
		metadata gateway_common.WorkflowMetadata
		sequence uint64
	}

	var toSort []aggregatedObs
	for _, nodeObs := range agg.observations {
		if len(nodeObs.nodes) >= agg.threshold {
			toSort = append(toSort, aggregatedObs{
				metadata: *nodeObs.observation,
				sequence: nodeObs.sequence,
			})
		}
	}

	// Sort chronologically (newest first) so that workflows that were registered most recently
	// takes precedence
	sort.Slice(toSort, func(i, j int) bool {
		return toSort[i].sequence > toSort[j].sequence
	})

	// Extract just the metadata
	aggregated := make([]gateway_common.WorkflowMetadata, len(toSort))
	for i, obs := range toSort {
		aggregated[i] = obs.metadata
	}

	return aggregated
}

func TestMultiShardAssignment(t *testing.T) {
	t.Parallel()

	handler, _, _ := createMultiShardMetadataHandler(t)
	ctx := t.Context()
	for _, shard := range handler.shards {
		require.NoError(t, handler.aggs[shard.donID].Start(ctx))
		t.Cleanup(func() { _ = handler.aggs[shard.donID].Close() })
	}

	obs := gateway_common.WorkflowMetadata{
		WorkflowSelector: gateway_common.WorkflowSelector{
			WorkflowID:    testWorkflowID1,
			WorkflowName:  testWorkflowNameHex1,
			WorkflowOwner: testWorkflowOwner1,
			WorkflowTag:   testWorkflowTag1,
		},
		AuthorizedKeys: []gateway_common.AuthorizedKey{{KeyType: gateway_common.KeyTypeECDSAEVM, PublicKey: testPublicKey1}},
	}

	// Initially unassigned.
	require.Empty(t, handler.WorkflowShards(testWorkflowID1))

	// Quorum (F+1=1) reached only in shard 1 (node3).
	require.NoError(t, handler.aggs[handler.shards[1].donID].Collect(&obs, "node3"))
	handler.syncMetadata(ctx)
	assigned := handler.WorkflowShards(testWorkflowID1)
	require.Len(t, assigned, 1)
	require.Equal(t, handler.shards[1].donID, assigned[0].donID)

	// Later quorum reached in shard 0 too (node1) => assigned to both shards.
	require.NoError(t, handler.aggs[handler.shards[0].donID].Collect(&obs, "node1"))
	handler.syncMetadata(ctx)
	assigned = handler.WorkflowShards(testWorkflowID1)
	require.Len(t, assigned, 2)

	// An observation from an unknown node is rejected.
	_, err := handler.aggForNode("unknown-node")
	require.Error(t, err)
}
