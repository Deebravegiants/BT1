### Title
Missing `+1` in BSC (Parlia) supermajority threshold check permits finalization below the required 2/3+1 quorum - (File: `modules/consensus/bsc/verifier/src/lib.rs`)

### Summary
The BSC/Parlia consensus verifier computes its supermajority participation check with a truncated integer division that omits the `+1` required for a true supermajority, unlike every other consensus verifier in the same codebase (BEEFY, sync-committee/GRANDPA-style, Pharos), all of which explicitly require `⌊2N/3⌋ + 1` participants. This is the same class of bug as the reported Vyper `sqrt` miscalculation: an arithmetic/rounding shortfall that silently accepts a boundary value it should reject.

### Finding Description
`verify_bsc_header` enforces the BFT participation threshold as: [1](#0-0) 

`participant_count < ((2 * current_validators.len()) / 3)` only rejects when strictly fewer than `⌊2N/3⌋` validators participated — meaning exactly `⌊2N/3⌋` participants is accepted as sufficient. Every other consensus client in the repository requires strictly more than 2/3, i.e. `⌊2N/3⌋ + 1`:

- BEEFY: `len >= ((2 * total) / 3) + 1` [2](#0-1) 
- Sync-committee: `sync_aggregate_participants < ((2 * committee_size as u64) / 3) + 1` [3](#0-2) 
- Pharos: `required = (total_stake * 2 / 3) + 1` [4](#0-3) 

The BSC verifier's own doc-comment acknowledges it is deliberately using `2/3` without the `+1`, citing upstream `parlia.go`, but this creates an internal inconsistency: for validator-set sizes where `N` is a multiple of 3 (e.g. `N=21`, BSC's real validator count), `⌊2N/3⌋ = 14`, so exactly `14` of `21` validators (precisely two-thirds, not "more than two-thirds") is accepted as sufficient to sign an aggregate BLS signature and finalize a header. A true BFT supermajority requires strictly more than 2/3 of the validator set to guarantee that no coalition of up to `⌊(N-1)/3⌋` Byzantine validators can produce two conflicting valid quorums. With exactly `N/3` Byzantine validators (7 of 21), an honest quorum of only `14` and a dishonest quorum of `14` (7 honest + 7 Byzantine, reusing the boundary case) could both satisfy the check, undermining the safety assumption the bridge relies on for BSC-relayed state commitments.

### Impact Explanation
This threshold governs `verify_bsc_header`, which produces the `VerificationResult` used to accept BSC state/consensus updates for state machine height commitments consumed via `pallet-ismp`/`ismp-bsc` in Hyperbridge. A relaxed threshold reduces the fault-tolerance margin of the BSC light client from the intended `f < N/3` to an effectively weaker boundary, increasing the risk that a coalition at or near one-third of validators can produce or accept conflicting/forged finalized headers, leading to unsound state commitments and potentially forged message delivery/proof verification for BSC-sourced ISMP requests.

### Likelihood Explanation
Exploitation requires control or collusion among BSC validators at the boundary case (exactly `⌊2N/3⌋` signers), which is a validator-set-level assumption rather than a single-transaction exploit, so likelihood is lower than a pure smart-contract bug, but the check is reachable purely through relayed consensus proofs — no privileged Hyperbridge role is needed to submit them — and the deviation from the codebase's own supermajority convention (used everywhere else) is a concrete arithmetic defect.

### Recommendation
Align the BSC verifier's participation check with the rest of the codebase's supermajority convention: require `participant_count < ((2 * current_validators.len()) / 3) + 1` (i.e., reject unless strictly more than 2/3 participated), matching BEEFY, sync-committee, and Pharos, unless it can be independently confirmed and documented that BSC/Parlia's actual finality rule genuinely uses `>= 2/3` rather than `> 2/3`, in which case the discrepancy with sibling verifiers should at minimum be clearly justified and tested at the exact boundary (`N` divisible by 3).

### Proof of Concept
For `current_validators.len() = 21` (BSC's live validator count):
- `(2 * 21) / 3 = 14` (integer division, exact).
- `participant_count = 14` passes the check (`14 < 14` is false), even though 14/21 = exactly 2/3, not a strict supermajority.
- Contrast with `check_participation_threshold` in the BEEFY verifier, which for the same `total = 21` requires `len >= 14 + 1 = 15` — one more signer than the BSC path demands. [2](#0-1) [5](#0-4)

fn verify_stake_threshold(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let participating_stake = validator_set.participating_stake(participants);
	let total_stake = validator_set.total_stake;
	let required = (total_stake * 2 / 3) + 1;

	if participating_stake >= required {
		Ok(())
	} else {
		Err(Error::InsufficientStake {
			participating: participating_stake,
			required,
			total: total_stake,
		})
	}
}
