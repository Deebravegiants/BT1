Audit Report

## Title
Missing per-task-run completion guard in `UpdateTaskRunResult` allows already-finished `pipeline_task_runs` rows to be overwritten - (File: core/services/pipeline/orm.go)

## Summary
The `/v2/resume/:runID` endpoint is intentionally unauthenticated by design; its security relies on the randomness of the per-task-run UUID acting as a bearer token, sent only to the external adapter that the bridge task itself invoked, embedded in the `responseURL` field of the outgoing bridge request [1](#0-0) . Separately, `UpdateTaskRunResult`'s `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1` has no `finished_at IS NULL` precondition, so a caller who resends a request bearing an already-consumed task UUID can overwrite a previously-recorded result while the parent run is still `running`/`suspended` [2](#0-1) .

## Finding Description
The router intentionally leaves `/v2/resume/:runID` unauthenticated [3](#0-2) , but this is a deliberate design choice: the task-run UUID embedded in the resume URL functions as an unguessable, single-purpose bearer secret, generated per pipeline task and communicated only to the specific external adapter/bridge the node itself called, via the `responseURL` field of the outbound bridge request [1](#0-0) , confirmed by both integration tests [4](#0-3)  and unit tests [5](#0-4) . This is analogous to common secret-URL webhook patterns and is not, by itself, an authentication bypass reachable by an "unprivileged" party with no relationship to the job — only the adapter the node called (or someone who compromises/intercepts that specific channel) holds the token.

The `UpdateTaskRunResult` SQL guard is coarse: it verifies `pipeline_runs.state in ('running', 'suspended')` but never checks that the individual `pipeline_task_runs.id` targeted by the `UPDATE` still has `finished_at IS NULL` [6](#0-5) . This means a resend/replay of a resume callback for a task UUID that was already resolved can silently overwrite `output`/`error`/`finished_at` as long as the parent run has not yet fully completed.

Regarding the claimed race between concurrent async tasks A and B: the `SELECT ... FOR UPDATE` in `UpdateTaskRunResult` joins `pipeline_runs`, `pipeline_task_runs`, `pipeline_specs`, and `job_pipeline_specs` [7](#0-6) . In Postgres, a `FOR UPDATE` without an `OF table_name` clause locks the matching rows of *all* tables that can be locked in the join, which for two resume calls belonging to the same `pipeline_run_id` means both transactions contend for the same `pipeline_runs` row lock. This tends to serialize concurrent resume calls for the same run rather than the fully racy "read-then-write" pattern the report assumes. I could not fully trace `runner.Run`'s internal task-scheduling logic (specifically whether the in-memory `run.PipelineTaskRuns` snapshot passed to the resumed goroutine can genuinely be stale relative to a task resolved by a serialized-but-later transaction) within the available exploration budget, so I cannot confirm the "duplicate execution of downstream ETHTx" claim as stated. That portion of the report is speculative and unverified.

What is verifiable and real: the missing `finished_at IS NULL` guard on the row-level `UPDATE` is a genuine gap — replaying a resume call with an already-used task UUID while the run is still in a non-terminal state will silently overwrite the previously stored result.

## Impact Explanation
The concrete, verified impact is data corruption of an already-finished `pipeline_task_runs` row via replay of a resume request, not an authentication bypass in the traditional sense (the "credential" here is the per-task random UUID, functioning as intended by the bridge protocol design). The severity of this is bounded by exposure of the UUID: it is not disclosed to unrelated unprivileged parties, only to the specific external adapter the bridge task calls. The claimed "duplicate ETHTx invocation" / fund-movement outcome from a race between two concurrent async tasks in the same run is not substantiated by the code reviewed — the `FOR UPDATE` lock scope contradicts the described race window, and I was unable to confirm the in-memory snapshot staleness claim within the runner's scheduling logic.

## Likelihood Explanation
Exploiting the verified gap (missing `finished_at IS NULL`) requires possession of a task UUID that was already consumed — i.e., control over, or compromise of, the specific external adapter endpoint that received the resume URL for that task. This is not exploitable by a generic unprivileged actor with no relationship to the job/bridge; it requires the same level of access already assumed safe by the existing async-bridge callback design (an adapter that was legitimately invoked, or an attacker who has separately obtained/intercepted that adapter's copy of the URL). The report does not establish a plausible path for an unprivileged, unrelated attacker to obtain a valid task UUID for a run they don't already have adapter-level involvement in.

## Recommendation
Add a `finished_at IS NULL` condition to the `UPDATE pipeline_task_runs` statement in `UpdateTaskRunResult` (`core/services/pipeline/orm.go`) so a task run can be resolved at most once, and treat a no-op update (zero rows affected) as a no-start condition rather than assuming success.

## Proof of Concept
Not provided — the multi-task race scenario described in the original submission (steps 1–4) could not be confirmed against the actual locking/scheduling behavior of `UpdateTaskRunResult`/`runner.Run` within the scope of this review. A minimal reproducible unit test would call `orm.UpdateTaskRunResult` twice in sequence for the same `taskID` with a still-`running` parent run state and assert that the second call is rejected (currently it is not, but the exploitability of this beyond "replay by whoever already holds a used token" is limited).
