### Title
Unvalidated swap routes execute attacker-controlled contracts that can drain caller wallet tokens - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
The controller forwards caller-supplied swap bytes to the configured aggregator without validating which contracts the route invokes. A malicious route can therefore place attacker-controlled code below the caller’s authorized controller invocation and add arbitrary `token.transfer(caller, attacker, amount)` requests to the signed authorization tree.

### Finding Description
`swap_collateral` accepts caller-controlled `swap` bytes and forwards them into the shared strategy path after authenticating the caller and checking account ownership. [1](#0-0) [2](#0-1) 

`swap_tokens` restricts only the controller’s own input-token transfer to the configured router; it does not constrain downstream contracts named by the opaque route. [3](#0-2) 

The project’s threat model states that the router calls pool and token addresses named by the payload without an allowlist, and that a transfer from the caller made by that third-party code is recorded as a child of the caller’s authorization and executes if that tree is signed. [4](#0-3) 

A harness model demonstrates the primitive: a route-selected contract invokes `token.transfer(victim, attacker, amount)`, simulation records that transfer under the caller’s `swap_collateral` authorization, and signing the resulting tree drains an unrelated wallet token. [5](#0-4) [6](#0-5) 

### Impact Explanation
This is theft of user funds beyond the swap input. The malicious venue can request transfers of any token held by the caller, including tokens unrelated to the lending position, while still returning enough swap output to satisfy the controller’s measured-output and risk checks. [7](#0-6) [8](#0-7) 

The same opaque route reaches the router through `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`, so all strategy callers are exposed when they sign route-generated authorization trees. [9](#0-8) 

### Likelihood Explanation
Likelihood is medium because execution requires the account owner or delegate to sign the poisoned authorization tree. [10](#0-9) [11](#0-10) 

The route is supplied as opaque bytes and can come from an attacker-influenced quote or UI, while ordinary users may sign the prepared transaction without recognizing an extra child authorization. [12](#0-11) [13](#0-12) 

### Recommendation
Do not allow route payloads to name arbitrary executable venues. Enforce a governance-managed venue/pool registry inside the swap router, resolve routes only to registered venue identifiers, and reject payload-supplied contract addresses that are not registered. Add transaction-level validation that rejects unexpected child authorization requests, and add regression tests proving a rogue hop cannot attach a token transfer beneath `multiply`, `swap_debt`, `swap_collateral`, or `repay_debt_with_collateral`.

### Proof of Concept
1. Alice owns a funded account and holds an unrelated token `T`.
2. An attacker deploys contract `R` whose swap method calls `T.transfer(Alice, attacker, Alice_balance)`.
3. The attacker supplies a `swap_collateral` route whose hop venue is `R`, with otherwise valid USDC-to-ETH input and output parameters.
4. Alice submits `swap_collateral(caller=Alice, account_id, current=USDC, amount, new=ETH, swap=route)`, causing the controller to invoke `execute_strategy(controller, amount, route)`. [3](#0-2) 
5. The router invokes attacker-controlled `R`; its token transfer is simulated as a child of Alice’s controller authorization and, once signed, transfers the unrelated `T` balance to the attacker. [5](#0-4) [6](#0-5)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
