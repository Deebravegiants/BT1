### Title
`Wallet.updateSeed` missing unlock guard allows seed-metadata write while locked and without seed ownership check - ([File: features/wallet/module/wallet.js])

### Summary
`Wallet.updateSeed` mutates `#seedMetadataAtom` for an arbitrary `seedId` without ever calling `#assertWalletIsUnlocked`, unlike its sibling mutators `addSeed` and `removeManySeeds`, and it is directly exposed on the public wallet API surface. This allows metadata (label) for any `seedId`, including ones not owned by the unlocked wallet, to be written or overwritten while the wallet is locked.

### Finding Description
`addSeed` and `removeManySeeds` both begin with `await this.#assertWalletIsUnlocked()` before touching wallet state [1](#0-0) [2](#0-1) . `updateSeed`, however, only validates that `seedId` and `label` are truthy and directly calls `#seedMetadataAtom.set` to write the entry, with no unlock check and no verification that `seedId` corresponds to the primary seed or one of the wallet's extra seeds: [3](#0-2) 

`updateSeed` is exposed unchanged on the public `walletApi` object alongside `isLocked`, `addSeed`, `removeSeed`, etc., making it reachable the same way as any other wallet RPC method: [4](#0-3) 

Because there is no `#assertWalletIsUnlocked()` call and no membership check against `getPrimarySeedId()`/`getExtraSeedIds()`, a caller can invoke `updateSeed({ seedId, label })` with any `seedId` string — including one that belongs to another account/seed not currently unlocked — and the `#seedMetadataAtom` will be updated regardless of lock state.

### Impact Explanation
This breaks the "locked means locked" invariant: while `isLocked()` returns `true`, an attacker-controlled call can still mutate protected wallet state (`#seedMetadataAtom`), writing a spoofed `label`/`dateUpdated` for any `seedId`. Because there's also no check that `seedId` is one of the wallet's own seeds, metadata can be forged for accounts unrelated to the current wallet's known seeds. This is a metadata/label spoofing and unauthorized-state-mutation issue across accounts while locked, matching a wrong-account state-tampering impact class.

### Likelihood Explanation
The precondition is simply that the RPC/API surface exposes `wallet.updateSeed` to a caller (dapp/origin request or any code that can reach the module's public API), with no separate unlock gate imposed at the API layer. Given `updateSeed` is wired 1:1 from `walletApi.updateSeed = wallet.updateSeed` with no wrapper, and the module method itself has no guard, this is directly and repeatably reachable — no privileged state or key leakage is needed, just an ordinary call.

### Recommendation
Add `await this.#assertWalletIsUnlocked()` at the start of `updateSeed`, matching `addSeed`/`removeManySeeds`. Additionally, validate that `seedId` belongs to the currently known set of seeds (primary seed id or one of `getExtraSeedIds()`) before writing to `#seedMetadataAtom`, rejecting unknown/foreign `seedId` values.

### Proof of Concept
Unit test (extending `features/wallet/module/__tests__/index.test.js` pattern):
```js
it('updateSeed does not mutate metadata while wallet is locked', async () => {
  // wallet created but not unlocked -> isLocked() === true
  expect(await wallet.isLocked()).toBe(true)

  const foreignSeedId = 'some-other-account-seed-id'
  await expect(wallet.updateSeed({ seedId: foreignSeedId, label: 'pwned' }))
    .rejects.toThrow(/locked/i)

  const metadata = await wallet.getSeedMetadata()
  expect(metadata[foreignSeedId]).toBeUndefined()
})
```
Expected current behavior (bug): the call succeeds and `metadata[foreignSeedId]` is set to `{ label: 'pwned', dateUpdated: ... }` even though the wallet is locked and `foreignSeedId` is not owned by this wallet. Expected fixed behavior: the call throws (`'wallet is locked'` from `#assertWalletIsUnlocked`) and/or throws for unknown seed ids, leaving `#seedMetadataAtom` unchanged.
