### Title
Webhook `shop`/`topic` identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify," but the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — which are read straight from HTTP headers and handed to the app's handler as trusted identity data — are never bound to that signature. Any request bearing a previously-seen valid `(body, hmac)` pair can be replayed with arbitrary `shop`/`topic` headers and will still pass verification.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then trusts `request.topic` and `request.shop` unconditionally to select a handler and build the metadata passed to app code: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that `to_signable_string` (i.e. the body) was signed with the shared `api_secret_key`; it says nothing about which shop or topic the signature was intended for: [4](#0-3) 

Because `api_secret_key` is a single shared secret used for every shop that installs the app (not per-tenant), any tenant that receives a genuine webhook already possesses a valid `(body, hmac)` pair. Nothing in this gem prevents that pair from being replayed to the same endpoint with different `shop-domain`/`topic` headers substituted, since those headers are outside the signed material. This breaks the identity binding that the API's own documentation assumes:

`shop declared in x-shopify-shop-domain header (trusted by handler.handle)` ≠ `shop actually bound to the HMAC-verified bytes (none — HMAC only covers body)`

The gem's own usage docs instruct apps to forward `data.shop` as the authoritative tenant identifier without any additional verification step: [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker who is merely a legitimate (unprivileged) installer of the app on their own shop — no access to `api_secret_key`, no stolen tokens — can capture a genuine webhook delivery for their own store (valid body + valid HMAC), then replay that exact body/HMAC pair to the app's webhook endpoint while swapping the `x-shopify-shop-domain` and/or `x-shopify-topic` headers to point at a victim shop/topic. `Registry.process` will accept it as authentic and dispatch it to the app's handler tagged as belonging to the victim tenant. This is a cross-tenant data injection into the app's per-shop processing pipeline (e.g., queued jobs, DB writes keyed by `shop_domain`), i.e., cross-tenant access/contamination without any credentials belonging to the victim.

### Likelihood Explanation
Any app built with this gem that follows the documented `Registry.process` flow is affected. Exploitation requires only: (1) becoming an app user on any shop (trivial, self-service), (2) capturing one legitimate webhook delivery for that shop, (3) resending it with edited headers to the public webhook endpoint. No secret material, no privileged access, and no interaction with the victim is required, making this readily reachable by any external actor who installs the app.

### Recommendation
Bind the tenant/topic identity into the signed material rather than trusting unauthenticated headers:
- Cross-check `request.shop` against the shop associated with the webhook registration/session the app expects, rather than trusting the header value implicitly.
- Where possible, include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, e.g. verify against Shopify's webhook delivery metadata/API) so a captured `(body, hmac)` pair cannot be replayed under a different shop or topic.
- At minimum, document prominently that `Registry.process`'s HMAC check authenticates body integrity only, not the `shop`/`topic` headers, and require apps to independently confirm `data.shop` matches an existing, expected session before acting on webhook data.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (normal merchant self-service, no special privilege).
2. Attacker triggers an event (e.g., creates an order) causing Shopify to send a legitimate webhook to the app's endpoint with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: <valid HMAC over body>`
   Attacker intercepts/records this `(raw_body, hmac)` pair (e.g., via a proxy they control in front of their own install, or a webhook debugging tool they configure for their own shop).
3. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook endpoint, but changes:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` computes:
   ```ruby
   Utils::HmacValidator.validate(request) # true, since HMAC only covers raw_body, unchanged
   ```
   per `lib/shopify_api/webhooks/registry.rb:190` and `lib/shopify_api/utils/hmac_validator.rb:13-22`, and proceeds to call:
   ```ruby
   handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
   ```
   with `shop == "victim-shop.myshopify.com"` even though the payload originated from and was signed for the attacker's own shop event.
5. The app's handler (per the documented pattern) processes/queues this attacker-controlled body under the victim shop's identity, achieving cross-tenant data injection.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
