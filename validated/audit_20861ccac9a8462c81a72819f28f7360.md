I have sufficient evidence to confirm the analog vulnerability. The `WebhookMetadata.shop` field, which is passed to the host application's handler as the tenant identifier, comes from the `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header, but the HMAC signature only covers the raw request body — not this header.

### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` value used to identify which merchant a webhook belongs to directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, while `Utils::HmacValidator` only validates the raw JSON body against the HMAC signature. Because the shop identity is never covered by the cryptographic signature, an attacker who can produce (or replay) a validly-signed body for one shop can rebind that signed payload to an arbitrary target shop by changing only the header.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read from a separate, unsigned header: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` computes and compares the signature purely over `to_signable_string` (the body), never incorporating `shop`, `topic`, or any other header: [4](#0-3) 

`Webhooks::Registry.process` calls this validator and, once it passes, trusts `request.shop` to construct the `WebhookMetadata` handed to the host application's handler as the merchant identity for that event: [5](#0-4) 

Because the app's `client_secret`/`api_secret_key` used for webhook HMAC signing is shared across every shop that installs the app (it is not per-tenant), a validly-signed body-plus-HMAC pair is not bound to any particular shop. This is structurally identical to the reported bug class: a field the code *acts on* (here, the `shop` used as the tenant/session key) is not covered by the authentication check (the HMAC), so the equality "shop authenticated == shop the identity is derived from" is broken — `request.shop` (header-derived) is trusted independently of what was actually verified (`request.hmac` over `raw_body` only).

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as returned by this gem) to look up per-tenant session/state without any additional binding, an attacker who controls a shop capable of installing the app (e.g., a free development store) can capture one of their own genuinely-signed webhook deliveries — valid body + valid HMAC — and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `Registry.process` will accept it because HMAC validation only checks the body, and the handler will receive a `WebhookMetadata` claiming it originates from the victim shop. This is a cross-tenant identity confusion at the gem's trust boundary, matching the Critical "cross-tenant access" impact category, since the gem itself asserts this shop value is authenticated when it is not covered by the signature it validates.

### Likelihood Explanation
Exploitability requires only that an attacker be able to install the target app on any shop they control (an unprivileged action for public apps) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — both are things any internet user can do. No access token, `client_secret`, or privileged account is required; the attacker never needs to know the app's secret because they reuse a legitimately-issued signature for their own tenant and simply relabel the tenant.

### Recommendation
Bind the shop identity into the material that is HMAC-verified, or otherwise cryptographically tie the `shop` header value to the signed body, e.g., by including `shop` (and `topic`) in `to_signable_string`, or by cross-checking `request.shop` against a shop value embedded in the verified body/topic before constructing `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop` is not covered by the HMAC and must not be treated as authenticated tenant identity without further verification (e.g., resolving it through a known, previously-stored session for that shop).

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, a shop they control, and triggers a real webhook (e.g., `orders/create`) with body `B`. Shopify sends a request with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: HMAC(secret, B)`, and body `B`.
2. Attacker captures this request and resends it to the app's webhook endpoint, replacing only the `x-shopify-shop-domain` header with `victim.myshopify.com`, keeping body `B` and the same `x-shopify-hmac-sha256` value unchanged.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — using `request.to_signable_string` (the unchanged body) — and it matches, since `shop` is never part of the signed material: [1](#0-0) [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ...)`, causing the host app to process attacker-controlled data as if it belongs to the victim shop: [7](#0-6)
