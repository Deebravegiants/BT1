## Title
Webhook shop-domain header is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The BLS `aggregateVerify` bug allowed a check that "verified" cryptographic material without actually binding all the semantically important inputs to what was cryptographically verified. The same class of bug exists in `ShopifyAPI::Webhooks::Request`/`Registry`: the webhook HMAC only covers the raw request body, while the `shop` identity that the handler acts on (`x-shopify-shop-domain` header) is never part of the signed material, so `bytes verified != bytes/fields acted on`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over that signable string (the body) and compares it to the `hmac-sha256` header: [2](#0-1) 

Meanwhile, `Request#shop` is read straight from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never part of the HMAC input: [3](#0-2) 

`Registry.process` validates only the HMAC-over-body, then forwards the unauthenticated `request.shop` straight to the app's handler as the tenant identifier: [4](#0-3) 

Because `Context.api_secret_key` is a single shared secret used to validate webhooks for *every* shop that installs the app (it is not a per-shop secret), an attacker who installs the app on their own (attacker-controlled) shop legitimately receives Shopify-signed webhooks whose HMAC is computed with that same shared secret. The attacker can capture a valid `(raw_body, hmac)` pair from their own shop's webhook traffic, then replay that exact body+HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain. `HmacValidator.validate` will still succeed (it never looks at the shop header), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field is the attacker-chosen victim domain: `shop: request.shop`.

This breaks the identity binding: `shop authenticated by HMAC` ≠ `shop the handler is told acted`.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (the documented, intended way to know which merchant a webhook is for) to scope state, session lookups, or side effects will process attacker-supplied data under a victim shop's identity — a cross-tenant confusion/spoofing vector purely due to this gem's webhook verification only covering the body and not the tenant-identifying header, despite exposing `shop` as a verified field on the callback data.

### Likelihood Explanation
Exploitation only requires the attacker to be an ordinary merchant who installs the target app on their own store — no special privileges, leaked secrets, or access tokens are needed. Capturing their own valid webhook body+HMAC and replaying it with a modified header is trivial for anyone who can install the app and receive its webhooks.

### Recommendation
Bind the shop domain (and other trust-relevant headers such as `api-version`/`webhook-id`) into the signable material used for HMAC verification, or otherwise cryptographically tie the `shop` value to the verified payload before exposing it in `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be trusted for tenant scoping without an independent cross-check (e.g., verifying the webhook id against a previously registered subscription for that shop).

### Proof of Concept
1. App developer configures a single `Context.api_secret_key` shared by all installing shops (as required by this gem).
2. Attacker installs the app on `attacker.myshopify.com` and lets Shopify send a legitimate webhook; attacker records the raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the shared secret).
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` — this passes.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, i.e., attacker-controlled data attributed to the victim shop.
