### Title
Meta-transaction (`DelegateAction`) signatures lack any chain/genesis identifier, enabling cross-chain replay of relayed actions - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
NEAR's NEP-366 meta-transaction scheme signs a `DelegateAction`/`DelegateActionV2` with a domain-separated hash (`get_nep461_hash`) that binds only to a message-type discriminant plus `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`. Unlike the outer `SignedTransaction` (which is bound to a specific chain implicitly through a recent `block_hash`), the inner delegate signature contains nothing that ties it to a particular chain/genesis instance. This mirrors the reported EIP-712 class of bug ("Trust"/`ERC1155BaseToken` message hashing lacking `chainid`), where the fix was to add a chain identifier to the signed payload.

### Finding Description
The signable payload for meta-transactions is constructed in `SignableMessage::new`/`sign` [1](#0-0)  and consumed by `DelegateAction::get_nep461_hash` / `VersionedDelegateActionPayload::get_nep461_hash` [2](#0-1) [3](#0-2) . The fields hashed are exactly `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key` (plus the NEP discriminant) [4](#0-3) . None of these fields identify the target chain (no `genesis_id`, no `chain_id`, no recent block hash of the destination chain). Verification on the receiving side (`apply_delegate_action`) only checks the signature, `max_block_height` against local block height, and that `sender_id` matches the tx receiver — again nothing chain-specific [5](#0-4) .

Nearcore itself ships `tools/fork-network`, which produces a new chain (with its own `chain_id`) that clones the full source-chain account/access-key state, including AccessKey nonces, from a mainnet/testnet snapshot [6](#0-5) . Because the nonce (`AccessKey.nonce` tracked per access key, matching `DelegateAction.nonce`) and account state are preserved verbatim across the fork, a `DelegateAction`/`SignedDelegateAction` signed by a user for the original chain remains fully valid — same nonce state, same public key, same `max_block_height` window — and can be replayed as-is on the forked chain, executing the same delegated action there without the sender's intent or consent for that particular chain.

### Impact Explanation
An attacker or an operator running a forked/cloned NEAR-based network (via `fork-network`, state-sync-based mirrors, or any other tool that imports genuine account state including access-key nonces) can capture a previously broadcast `SignedDelegateAction`/`VersionedSignedDelegateAction` (visible in a relayer's mempool, RPC logs, or on-chain history) and resubmit it — wrapped in a fresh outer `SignedTransaction` produced by any relayer — against the forked chain. Because the delegate signature has no chain-binding, it verifies successfully, causing the delegated actions (e.g., `Transfer`, `FunctionCall`, `AddKey`) to execute on the sender's behalf on a network the sender never intended, resulting in unauthorized state/balance changes for that account. This is a genuine "unauthorized action execution" analog to the Sequence report.

### Likelihood Explanation
Exploitation requires a second nearcore-based chain that has cloned the exact account/access-key state of the source chain (e.g., via the in-repo `fork-network` tool or similar state-import tooling) and requires the attacker to have observed a previously signed delegate action still within its `max_block_height` validity window. This is a realistic but not trivially "always available" precondition — it depends on state-cloning infrastructure existing and a valid, unexpired signed delegate message being obtainable, so likelihood is moderate rather than high.

### Recommendation
Include a chain-identifying value (e.g., `genesis_id`/`chain_id` from `ChainGenesis`) inside the `SignableMessage`/`DelegateAction` payload that is hashed and signed, analogous to adding `chainid` to the EIP-712 message. Reject delegate actions during `apply_delegate_action` whose embedded chain identifier does not match the local chain's genesis/chain id, so signatures produced for one nearcore-based network cannot be replayed on another cloned or forked network.

### Proof of Concept
1. On chain A, user Alice signs a `DelegateAction` (`sender_id: alice.near`, `nonce: N`, `max_block_height: H`) via `SignedDelegateAction::sign`, authorizing a `Transfer`/`FunctionCall`, and hands it to Relayer R for inclusion (as in `meta_tx` helper) [7](#0-6) .
2. An operator runs `fork-network` against chain A's state snapshot, producing chain B with a distinct `chain_id` but the same account `alice.near`, same access key, and the same nonce `N` still stored under that key [8](#0-7) .
3. Before block height `H` is reached on chain B, an attacker (or R itself) wraps the captured `SignedDelegateAction` in a new `SignedTransaction` addressed at chain B and submits it via RPC.
4. `apply_delegate_action` on chain B validates the signature (`signed_delegate_action.verify()`), checks `max_block_height` against chain B's local height, and finds the nonce/state acceptable, then executes the delegated action on `alice.near`'s behalf on chain B, even though Alice never authorized any action on chain B [9](#0-8) .

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
