### Title
Webhook `shop-domain` header is trusted as tenant identity without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` computes the HMAC over the raw body only [1](#0-0) , while `shop` is read directly and unauthenticated from the `x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates the HMAC over the body/secret pair only, then forwards `request.shop` straight into `WebhookMetadata`, which is handed to the app's webhook handler as the trusted tenant identifier [3](#0-2) .

### Finding Description
This is the same class of bug as the report's core theme — an identity-relevant field acted upon by the library is not covered by the cryptographic check that is supposed to authenticate the whole request. Here the binding that should hold is:

`shop used to authorize/attribute the webhook == shop cryptographically bound by the HMAC`

But the HMAC's signable string is only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` only checks that this raw body matches the signature computed with the app's secret [4](#0-3) . The `shop`, `topic`, `api-version`, and `webhook-id` values are all taken verbatim from HTTP headers with no cryptographic linkage to the signed body [5](#0-4) .

Consequently, if an attacker who has captured one legitimately-signed webhook payload (e.g., from their own shop, or via a request that transits an intermediary/logging proxy) can cause `Registry.process` to be invoked with the original raw body/HMAC pair but a substituted `x-shopify-shop-domain` header, the `shop` value used to build `WebhookMetadata` — and therefore the tenant context handed to the app's handler — is unverified.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to select which merchant's data record to update/read (a common integration pattern), an attacker able to replay a validly-signed body with a forged shop-domain header can cause the handler to attribute or apply mutations under a different tenant's identity — i.e., cross-tenant confusion, sourced entirely from an HMAC-uncovered header field the gem treats as authoritative.

### Likelihood Explanation
Exploitability depends on the host application exposing a single shared webhook endpoint (not per-shop paths) and forwarding raw headers/body untouched, and on an attacker being able to obtain one valid signed payload (own-shop webhook) to splice with a forged domain header. This requires network-level request manipulation between Shopify and the app (or a replay through a component that preserves the raw body/HMAC but allows header rewriting), which is a nontrivial precondition, but the library itself performs no defense against it — the gem never binds `shop` into the HMAC-checked material.

### Recommendation
Bind the `shop` (and ideally `topic`) header values into the HMAC-covered signable string, or independently verify `x-shopify-shop-domain` against the session/shop context associated with the receiving endpoint before constructing `WebhookMetadata`. At minimum, document that `request.shop` is not authenticated by `HmacValidator.validate` so integrators do not treat it as a trusted tenant identifier.

### Proof of Concept
1. Capture a legitimate webhook delivery (raw body `B` and `x-shopify-hmac-sha256` header `H`) for `shop-a.myshopify.com`.
2. Replay a request to the app's webhook endpoint with the same body `B` and header `H`, but with `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H` [1](#0-0) .
4. `Registry.process` calls the handler with `shop: request.shop` == `"shop-b.myshopify.com"` [6](#0-5) , even though the payload actually originated from `shop-a`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)

        end
