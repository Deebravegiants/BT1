### Title
Webhook shop-tenant identity spoofing due to HMAC covering only the raw body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then passes the *unauthenticated* `shop-domain` header value straight through to the app's webhook handler as the tenant identifier. Because the signed bytes (body) and the trusted tenant-binding field (`shop`) are not cryptographically bound together, a webhook that is legitimately and validly signed for one shop can be replayed with a different `shop-domain` header, causing the host application to attribute the (attacker-controlled) payload to an arbitrary victim shop.

### Finding Description
`Registry.process` performs authentication like this: [1](#0-0) 

The only authentication check is `Utils::HmacValidator.validate(request)`, which computes the signature exclusively over `request.to_signable_string`: [2](#0-1) 

`to_signable_string` returns `@raw_body` only — no header, including `shop-domain`, is part of the signed content: [3](#0-2) 

Meanwhile `request.shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cross-check against the signed body: [4](#0-3) 

After the HMAC check passes, this unauthenticated `shop` value is handed to the app's handler as the tenant identity for the webhook: [5](#0-4) 

The identity binding that should hold is:

```
shop_that_signed_this_body == shop_the_handler_is_told_it_is_for
```

but the gem only proves `hmac_valid(body)`; it never proves `hmac_valid(body, shop)` or otherwise ties `shop` to the signed bytes.

### Impact Explanation
Since a Shopify app's `api_secret_key` is shared across every shop that installs the app (it is not per-shop), any unprivileged internet user can install the target app on their own free/dev store and receive genuinely, validly-signed webhooks for their own store's events (e.g. `orders/create`, `app/uninstalled`, `shop/redact`). Because the signature covers only the body and not the `shop-domain` header, that attacker can capture a validly-signed body+HMAC pair and resend it to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim merchant's domain. `Registry.process` will accept it (the HMAC still matches the unchanged body) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any host application that uses `WebhookMetadata#shop` to select which merchant's session/record to update (a documented, intended use of this field) will apply attacker-controlled webhook data under the victim tenant's identity — this is a cross-tenant data-integrity/confusion vector, and in the case of mandatory topics like `shop/redact` or `app/uninstalled`, it lets an attacker trigger destructive/administrative actions attributed to a shop they do not own.

### Likelihood Explanation
Likelihood is high for any app that exposes a webhook receiving endpoint (which is the intended, documented use of `Registry.process`) and relies on `WebhookMetadata#shop` for tenant routing without independently re-verifying it — the attack requires only a normal (free) Shopify store installation and the ability to POST to the app's public webhook URL, no leaked secrets or privileged access.

### Recommendation
Bind the shop identity to the signed content, e.g. include `shop-domain` (and ideally `webhook-id`/`topic`) in the HMAC-signed material, or independently verify that the `shop-domain` header matches a shop-specific value derived from data already authenticated for that request (such as validating against the session/shop the webhook was registered for). At minimum, `Registry.process` should reject/flag requests where the tenant-identifying header cannot be cryptographically tied to the authenticated payload, rather than passing it through unauthenticated to handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify legitimately delivers a webhook to the app's endpoint, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: shop/redact
   x-shopify-hmac-sha256: <valid HMAC of body>
   x-shopify-shop-domain: attacker.myshopify.com
   Body: {"shop_id":..., "shop_domain":"attacker.myshopify.com", ...}
   ```
3. Attacker captures this exact request (body + `x-shopify-hmac-sha256` unchanged) and re-sends it to the same public endpoint, only replacing the header:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `Utils::HmacValidator.validate(request)` re-computes the HMAC over `@raw_body`, which is unchanged, so validation succeeds.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host app to process a `shop/redact` (or other) event as if it originated from `victim.myshopify.com`.
