### Title
Non-embedded session cookie value equals the predictable session ID (`offline_#{shop}`), allowing session fixation/cross-tenant impersonation - (File: `lib/shopify_api/utils/session_utils.rb`, `lib/shopify_api/auth/oauth.rb`)

### Summary
For non-embedded (and embedded-without-JWT) requests, this gem resolves "the current session" by trusting the raw, unsigned `shopify_app_session` cookie value as the session-store lookup key. That cookie value is set by the gem itself, during OAuth completion, to the deterministic `Session#id` (`"offline_#{shop}"` for offline sessions, or `"#{shop}_#{associated_user_id}"` for online sessions) — a value derivable from public information, not from anything cryptographically bound to a completed OAuth handshake.

### Finding Description
During `ShopifyAPI::Auth::Oauth.validate_auth_callback`, after the HMAC/state check on the OAuth callback succeeds, the non-embedded cookie is built directly from the new session's id: [1](#0-0) 

`Session.id` for an offline session is simply `"offline_#{shop}"`: [2](#0-1) 

Later, when the app wants to identify "who is calling", `SessionUtils.current_session_id` is used. For non-embedded apps (and for embedded apps when no JWT is supplied), it returns the raw cookie value verbatim, with no signature or integrity check of any kind: [3](#0-2) [4](#0-3) 

The binding that should hold is:
`session_id supplied by the browser == session_id that can only be produced by a party who has completed a real OAuth exchange for that specific shop`

Instead, the gem breaks this binding into an equality of two unauthenticated strings:
`session_id supplied by the browser == "offline_" + shop_domain (a value with no secret entropy)`

Any actor who merely knows a target shop's `*.myshopify.com` domain (public info — visible on storefronts, sitemaps, app listings, etc.) can compute the exact string `"offline_target-shop.myshopify.com"` and set it as their own `shopify_app_session` cookie value. The gem's own documented usage pattern stores this cookie as a **plain, non-signed** cookie (`cookies[name] = { value:, expires:, secure:, http_only: }`, not `cookies.signed[...]`): [5](#0-4) 

And the BREAKING_CHANGES doc's reference session-storage implementation looks sessions up purely `by id`: [6](#0-5) 

Combining the gem's own `SessionUtils.current_session_id` (which returns the forged cookie value as-is) with this documented `retrieve(id)` pattern, an attacker's forged cookie resolves to the id of a legitimate, already-installed shop's session, and the host app will retrieve and use that shop's stored `access_token` on the attacker's behalf — a cross-tenant session-fixation/impersonation, without ever needing the shop's real access token or the app's `client_secret`.

### Impact Explanation
This is a session id derived from unauthenticated, guessable bytes (the shop domain), used directly as an authentication/session lookup key by `ShopifyAPI::Utils::SessionUtils.current_session_id`. Per the given impact taxonomy this is High: it enables session fixation / forced session adoption and, when combined with the gem's own documented session-storage pattern, cross-tenant access to another merchant's session/access token — all reachable by an unprivileged internet user who only needs to know (or guess/enumerate) a target's `myshopify.com` domain.

### Likelihood Explanation
Likelihood is high in the non-embedded (or JWT-less embedded fallback) code path: `myshopify.com` domains are not secrets — they're often visible in the merchant's public storefront URL, in app-review listings, or trivially guessable from a business name. No credentials, tokens, or privileged access are required to construct the forged cookie value; the attacker only needs to send a single crafted HTTP request with that cookie to any endpoint of the target app that calls `SessionUtils.current_session_id`.

### Recommendation
Do not use a deterministic, guessable string (`"offline_#{shop}"` / `"#{shop}_#{user_id}"`) as a bearer-style session cookie value. Instead:
- Store a high-entropy, unguessable, randomly generated token as the cookie value (decoupled from the `Session#id` used for storage lookups), and map that opaque token to the session server-side.
- Cryptographically sign/HMAC the cookie value (or use `cookies.signed`/`cookies.encrypted` in Rails) so its authenticity can be verified before it is used as a lookup key.
- Update `SessionUtils.cookie_session_id`/`current_session_id` and the documentation examples in `docs/usage/oauth.md` to reflect that the cookie must not be treated as self-authenticating.

### Proof of Concept
1. Victim installs the app; the gem completes `Oauth.validate_auth_callback` and sets `shopify_app_session = "offline_victim-shop.myshopify.com"` in the victim's browser as a plain cookie (per documented example).
2. Attacker learns `victim-shop.myshopify.com` (public storefront domain).
3. Attacker sends a request to any app endpoint with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`.
4. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` verbatim (`lib/shopify_api/utils/session_utils.rb:19-37,68-71`) with zero verification.
5. Following the gem's own documented session-storage retrieval pattern (`BREAKING_CHANGES_FOR_V16.md:66-75`), the host app looks up and returns the victim's real, previously stored `Session` (with its live `access_token`), and the attacker's subsequent API calls are executed using the victim shop's session.
