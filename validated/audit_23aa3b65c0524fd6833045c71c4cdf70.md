Audit Report

## Title
Quadratic-cost GRANDPA ancestry traversal in `verify_justification` is not captured by the linear `submit_finality_proof` weight formula - (File: bridges/primitives/header-chain/src/justification/verification/mod.rs, bridges/modules/grandpa/src/lib.rs)

## Summary
`submit_finality_proof_ex` prices its dispatch weight strictly as independent linear terms in `precommits.len()` and `votes_ancestries.len()`, while `JustificationVerifier::verify_justification` calls `AncestryChain::ancestry()` once per precommit, and each call walks the `parents` map from the precommit's target back toward `base` until it hits an already-visited node. With an adversarially branched `votes_ancestries` structure, per-precommit traversal cost can approach the full remaining branch length instead of being amortized via the "visited" short-circuit, so total verification cost can approach `O(p*v)` while the charged weight remains purely linear in `p` and `v`.

## Finding Description
`submit_finality_proof_ex`'s weight annotation is derived only from `justification.commit.precommits.len()` and `justification.votes_ancestries.len()`: [1](#0-0) 

The verification loop in `JustificationVerifier::verify_justification` iterates once over all precommits and, for each one not previously resolved, calls `chain.ancestry(...)`, which walks backward via `parent_hash_of` through the `parents: BTreeMap<Hash, Hash>` built from `votes_ancestries`, stopping only at `base` or at a node marked visited by a prior call: [2](#0-1) [3](#0-2) 

The "already visited" short-circuit (`self.unvisited.get(&current_hash).is_none()`) only helps when routes share a common suffix that has already been traversed and marked visited via `mark_route_as_visited`. If `votes_ancestries` is structured as several disjoint branches off different points, and precommits are distributed across those branches (rather than reusing one already-visited chain), each `ancestry()` call must walk close to its full branch length before hitting `base` or a shared visited node, since `mark_route_as_visited` only removes hashes belonging to already-resolved routes — it does not shortcut unrelated branches.

The weight formula (`Weight::from_parts(...).saturating_mul(p.into())` plus a separate `v`-scaled term, with no `p*v` cross term) is structurally incapable of expressing this super-linear cost: [4](#0-3) 

The only existing mitigation, `submit_finality_proof_limits_extras`, flags `is_weight_limit_exceeded` purely based on `votes_ancestries_len > REASONABLE_HEADERS_IN_JUSTIFICATION_ANCESTRY` and — if triggered — charges the entire (still linearly-computed) call weight as "extra" via `submit_finality_proof_info_from_args`: [5](#0-4) [6](#0-5) 

This mechanism does not reject the call outright, does not scale with a `p*v` term, and — critically — is only enforced through an *optional* transaction-validity extension (`check_obsolete_from_extension` / `fits_limits`) that a runtime may or may not register; even where present, it only affects fee refund/free-execution eligibility, not the actual weight charged for dispatch, nor does the in-pallet call itself hard-reject an oversized/adversarially-branched `votes_ancestries`. The call itself (`submit_finality_proof_ex`) has no in-pallet cap on `votes_ancestries.len()` before invoking `verify_justification`.

## Impact Explanation
If the quadratic blow-up is real and reachable at scale, a relayer could submit a `submit_finality_proof_ex`/`submit_finality_proof` call whose actual CPU cost during on-chain execution significantly exceeds the weight charged, since the weight formula only bounds `O(p+v)`-style cost, not `O(p*v)`. In the worst theoretical case this could push execution time beyond expectations for the declared weight. However, this is bounded in practice by hard ceilings: `p` (`precommits.len()`) is bounded by `MAX_AUTHORITIES_COUNT`, and `v` (`votes_ancestries.len()`) is implicitly bounded by the extrinsic/block size limits (each ancestor header must be fully encoded in the justification) as well as `REASONABLE_HEADERS_IN_JUSTIFICATION_ANCESTRY`-based economic disincentives. The report does not provide (nor could it be verified from static review) concrete numbers showing that realistic bounded values of `p` and `v` (constrained by existing `MAX_AUTHORITIES_COUNT`, block/extrinsic length limits, and PoV weight limits already charged per byte) produce an actual execution time that exceeds the block's time budget. The claim also does not demonstrate that GRANDPA justifications with such deliberately branched, non-chain-shaped `votes_ancestries` can be constructed as *valid* finality proofs that pass the surrounding checks (`DuplicateVotesAncestries`, `RedundantVotesAncestries`, cumulative-weight threshold) rather than being rejected early with only partial traversal cost.

## Likelihood Explanation
The call path is reachable by any signed account, and `votes_ancestries`/`precommits` content is attacker-supplied, so the mechanical code-path claim (repeated `ancestry()` calls with a per-precommit traversal, and a purely linear weight formula) is accurate as a code-review finding. However, no PoC, benchmark, or fork/integration test is provided showing the asymptotic gap is exploitable within the actual bounded parameter ranges enforced by the runtime (`MAX_AUTHORITIES_COUNT`, block length limits, `REASONABLE_HEADERS_IN_JUSTIFICATION_ANCESTRY`-based extension where wired in). Without concrete numbers or a reproducible benchmark demonstrating that worst-case `p`/`v` within these bounds cause execution time to meaningfully exceed the charged weight (let alone exceed the block time budget), the finding remains a theoretical asymptotic-complexity observation rather than a demonstrated DoS.

## Recommendation
- Add a hard, in-pallet cap on `votes_ancestries.len()` enforced before verification (reject outright, not merely economically discourage via an optional extension).
- Change the ancestry traversal to a provably bounded-cost algorithm (e.g., single-pass depth memoization) so total cost is `O(p+v)` regardless of branch topology.
- If super-linear cost cannot be eliminated, update `submit_finality_proof`/benchmarking in `bridges/modules/grandpa/src/weights.rs` to include a cross term reflecting worst-case traversal cost, and produce a benchmark demonstrating the actual worst-case cost under existing `MAX_AUTHORITIES_COUNT`/size-limit constraints.

## Proof of Concept
No PoC was supplied that demonstrates exploitability under the runtime's actual enforced bounds (`MAX_AUTHORITIES_COUNT`, extrinsic/block size limits). A conclusive PoC would need to: (1) construct a valid `GrandpaJustification` with maximal `p` (bounded by `MAX_AUTHORITIES_COUNT`) and maximal `v` (bounded by realistic block/extrinsic size limits) arranged in disjoint branches; (2) measure actual `verify_justification` execution time versus the weight returned by `WeightInfo::submit_finality_proof(p, v)`; (3) show the measured time exceeds the charged weight's time budget by a margin significant enough to matter for block production, not just an asymptotic difference between two justification shapes of hypothetical unbounded size.

	pub fn ancestry(
		&self,
		precommit_target_hash: &Header::Hash,
		precommit_target_number: &Header::Number,
	) -> Option<Vec<Header::Hash>> {
		if precommit_target_number < &self.base.number() {
			return None;
		}

		let mut route = vec![];
		let mut current_hash = *precommit_target_hash;
		loop {
			if current_hash == self.base.hash() {
				break;
			}

			current_hash = match self.parent_hash_of(&current_hash) {
				Some(parent_hash) => {
					let is_visited_before = self.unvisited.get(&current_hash).is_none();
					if is_visited_before {
						// If the current header has been visited in a previous call, it is a
						// descendent of `base` (we assume that the previous call was successful).
						return Some(route);
					}
					route.push(current_hash);

					*parent_hash
				},
				None => return None,
			};
		}

		Some(route)
	}

pub fn submit_finality_proof_limits_extras<C: ChainWithGrandpa>(
	header: &C::Header,
	proof: &justification::GrandpaJustification<C::Header>,
) -> SubmitFinalityProofCallExtras {
	// the `submit_finality_proof` call will reject justifications with invalid, duplicate,
	// unknown and extra signatures. It'll also reject justifications with less than necessary
	// signatures. So we do not care about extra weight because of additional signatures here.
	let precommits_len = proof.commit.precommits.len().saturated_into();
	let required_precommits = precommits_len;

	// the weight check is simple - we assume that there are no more than the `limit`
	// headers in the ancestry proof
	let votes_ancestries_len: u32 = proof.votes_ancestries.len().saturated_into();
	let is_weight_limit_exceeded =
		votes_ancestries_len > C::REASONABLE_HEADERS_IN_JUSTIFICATION_ANCESTRY;

	// check if the `finality_target` is a mandatory header. If so, we are ready to refund larger
	// size
	let is_mandatory_finality_target =
		GrandpaConsensusLogReader::<BlockNumberOf<C>>::find_scheduled_change(header.digest())
			.is_some();

	// we can estimate extra call size easily, without any additional significant overhead
	let actual_call_size: u32 =
		header.encoded_size().saturating_add(proof.encoded_size()).saturated_into();
	let max_expected_call_size = max_expected_submit_finality_proof_arguments_size::<C>(
		is_mandatory_finality_target,
		required_precommits,
	);
	let extra_size = actual_call_size.saturating_sub(max_expected_call_size);

	SubmitFinalityProofCallExtras {
		is_weight_limit_exceeded,
		extra_size,
		is_mandatory_finality_target,
	}
}
