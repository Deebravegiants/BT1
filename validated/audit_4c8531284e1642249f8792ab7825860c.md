### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing in webhook processing - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the handler a `WebhookMetadata` object whose `shop` field is taken verbatim from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header. The header is never included in the signed bytes, so the shop identity delivered to the app is not bound to the HMAC that "authenticates" the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is read directly from an HTTP header with no cryptographic tie to the signature: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string (body only) and then forwards `request.shop` straight into `WebhookMetadata`, which is passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` only ever compares the HMAC against `verifiable_query.to_signable_string`, i.e. the body — the `shop` header plays no role in the cryptographic check: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by the HMAC == shop delivered to the app's webhook handler`

Because the HMAC covers only the JSON body, this equality does not hold. Any party who can obtain one genuine, correctly-signed webhook body for their own shop (e.g., a merchant who installs the app and receives real webhook deliveries, since the signing secret is the app's shared `client_secret`, not something scoped per merchant) can replay that exact body to the app's webhook endpoint while substituting a different value in the `shop-domain` header. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` then invokes the handler with `WebhookMetadata.new(shop: <attacker-chosen shop>, body: <replayed body>, ...)`. Documentation states that `Registry.process` "will verify the request did indeed come from Shopify", which does not hold for the shop-identity claim specifically: [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce: an app that persists or acts on `data.shop` from `WebhookMetadata` (the officially documented usage pattern) can be made to associate one shop's real webhook payload (orders, customer data, GDPR requests, etc.) with a different, attacker-chosen shop domain string, since the HMAC provides no binding between the body and the shop header. This is a cross-tenant data-integrity/access issue — the impact category matches "cross-tenant access."

### Likelihood Explanation
Exploitation requires only the ability to send an arbitrary HTTP request to the app's public webhook endpoint plus one legitimately-signed webhook body (obtainable by installing the app on any shop, a normal unprivileged action) — no access token, secret, or privileged account is needed. The `shop-domain` header is a plain HTTP header with no additional integrity mechanism, making the swap trivial once one valid signed body is captured.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the signed payload used for `to_signable_string`, or require the host application to independently correlate `request.shop` against the shop associated with the session/subscription that requested the given webhook `topic`/`webhook_id`, rejecting mismatches before invoking the handler. At minimum, document prominently that `Registry.process` does not authenticate the `shop` header, and that callers must not trust `WebhookMetadata#shop` as tenant-authoritative without additional verification.

### Proof of Concept
1. App installs webhook handling per the documented pattern in `docs/usage/webhooks.md`, trusting `data.shop` in the handler.
2. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real event (e.g. `orders/create`), capturing the genuine POST request Shopify sends, including its valid `x-shopify-hmac-sha256` value computed over the JSON body.
3. Attacker replays that exact body and HMAC header to the same webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:26-31) succeeds because it only checks the body against the HMAC.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)`, causing the app to process attacker-controlled data under the victim shop's identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
