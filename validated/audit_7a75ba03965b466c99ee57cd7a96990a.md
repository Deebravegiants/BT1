### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `#shop` is read from the unauthenticated `X-Shopify-Shop-Domain` header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the body only and then dispatches the handler with the header-derived `shop` value, so the tenant identity attached to a webhook event is never bound to the cryptographic signature that authenticates the request.

### Finding Description
`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field of the request: [1](#0-0) 

For webhook requests, `to_signable_string` is defined as just the raw body, and `shop` is pulled from a separate, unsigned header: [2](#0-1) 

`Registry.process` uses `Utils::HmacValidator.validate(request)` to authenticate the request, then immediately trusts `request.shop` (the header value) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because the HMAC only certifies the *body*, not the `(shop, body)` pair, the binding the gem should enforce — "the shop this event is attributed to" == "the shop for which Shopify actually signed this body" — is broken. Any party who can obtain one genuinely-signed webhook body/HMAC pair from Shopify (trivially done by installing the target app on their own store and triggering any webhook, including the mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header value naming a different, victim shop. `HmacValidator.validate` still succeeds because it only re-hashes the unchanged body, and the handler receives `WebhookMetadata` with `shop` set to the attacker-chosen victim domain.

### Impact Explanation
This lets an unprivileged attacker who merely has a developer/trial store make the host application process webhook events as if they originated from a shop the attacker does not control. Because host applications key their per-tenant business logic and data records off `WebhookMetadata#shop`, this enables cross-tenant confusion/access: attacker-controlled webhook payloads get attributed to, and processed against, an arbitrary victim tenant's records without ever compromising that tenant's credentials. This satisfies the Critical "cross-tenant access" impact category, since the shop identity binding that the HMAC is supposed to guarantee is not actually enforced by the gem.

### Likelihood Explanation
Likelihood is realistic: obtaining one legitimately-signed webhook body (e.g., by installing the app for free/trial on an attacker-owned store and letting any topic fire) requires no privileged access to the victim, and the header the gem trusts for tenant attribution (`shop-domain`) is fully attacker-controllable on the replayed request, since only the raw body is authenticated.

### Recommendation
Bind the `shop` (and ideally topic/api-version) values into the signed material, or otherwise cryptographically verify that the claimed `shop` header matches the shop Shopify actually signed for that body/delivery. Concretely, `Webhooks::Request#to_signable_string` should not be the sole authentication input relied upon for tenant attribution — the library should either document/verify webhook shop association against a known/installed-shop set before dispatch, or reject requests where the `shop` cannot be independently corroborated (e.g., cross-checked against the delivery's `webhook-id`/topic via the Admin API, or simply making clear to consumers that `shop` is unauthenticated and must be validated against their own session store before use).

### Proof of Concept
1. Attacker installs the target Shopify app on their own development store `attacker.myshopify.com`, triggering a webhook (e.g. `shop/redact`) with body `B`. Shopify sends `X-Shopify-Hmac-Sha256: H` where `H = HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays the exact same `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` (per `Request#to_signable_string` returning only `@raw_body`) and matches `H` — validation passes.
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, so the app processes the event as belonging to `victim.myshopify.com` even though Shopify never signed anything for that shop. [4](#0-3) [5](#0-4) [6](#0-5)
