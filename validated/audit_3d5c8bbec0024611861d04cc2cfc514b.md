## Finding

Direct LT donations to a curve `Pair` become **permanently unrecoverable** — there is no function anywhere in the protocol that can pull that surplus LT back out, even after the token graduates.

### Title
Permanent freezing of LT donated directly to a curve `Pair` — no withdrawal path exists post-graduation - (File: `packages/contracts/src/Router.sol`, `packages/contracts/src/Pair.sol`)

### Summary
The reported bug class is "multiple tokens can accumulate in a vault-like contract, but the withdraw function can only recover one specific token, permanently stranding the rest." In alt.fun's shape, the analogous asset-holding contract is the curve `Pair`, and the analogous "excess balance that can't be withdrawn" is LT donated directly to the pair via a plain ERC20 `transfer`.

### Finding Description
Any address (attacker, well-meaning donor, or the creator themselves) can call `IERC20(lt).transfer(pairAddress, X)` at any time while the token is on the bonding curve. `Pair.assetBalance()` reads live `balanceOf`, so this donation inflates the pair's real LT balance above its stored `assetReserve` [1](#0-0) .

By design, the protocol's graduation and USD-trigger logic deliberately ignore this excess — `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve` from the pair's *stored* reserves, not its live balance, so the donation is excluded from the USD threshold and from LP seeding [2](#0-1) .

`Router.graduate` transfers only that exact `amount` out of the pair via `Pair.transferAsset`, explicitly leaving any donated LT behind: [3](#0-2) 

The natspec on `Router.graduate` itself admits this is only a "trust-assumption," not an on-chain guarantee, and spells out that the leftover LT is unreachable once the token's lifecycle passes `Curve`, because `Router.graduate`/`Pair.transferAsset` are gated behind `BONDING_ROLE` and `Bonding` never calls `graduate` again after `_prepareGraduationLiquidity` [4](#0-3) . `Pair.transferAsset` itself has no cap or accounting check — it is a raw `onlyRouter`-gated transfer, and the only caller path into it is `Router.sell` (bounded by `_computeSell`) and `Router.graduate` (bounded by the caller-supplied `amount`) [5](#0-4) . Neither `Bonding.sol` nor `Router.sol` exposes any owner/admin rescue function that can move LT out of a `Pair` — the only sweep mechanisms that exist target LT held by `Bonding` itself (`_sweepLTToOwner`, used only for `finalizeGraduation`'s own escrow accounting), not LT sitting inside a `Pair` [6](#0-5) .

This mirrors the original report precisely: multiple "deposits" (curve-raised LT + donated LT) can sit in the same contract, but the withdraw path (`Router.graduate`) only ever extracts the one accounted-for amount tied to the pool's own bookkeeping (`storedAssetReserve - virtualLtReserve`), and anything outside that accounting is permanently stuck with no alternate withdrawal function — exactly as `DonationVotingMerkleDistributionVaultStrategy.withdraw` could only rescue the single pool-registered token while other allowed tokens were lost forever.

### Impact Explanation
Any LT donated directly to a `Pair` (accidentally, via griefing, or via a misconfigured integration) is permanently and irrecoverably locked in that `Pair` contract for the lifetime of the protocol. This is a genuine permanent freezing of funds: no owner function, no `Bonding` code path, and no `Router` function can ever move that balance out, by the contract's own design and its own natspec admission. This is worse than an accidental design gap — it is an acknowledged, permanent, un-mitigatable loss condition reachable by any unprivileged wallet with an ERC20 `transfer`.

### Likelihood Explanation
Trivial to trigger: any wallet holding the paired LT can call a single ERC20 `transfer` to the `Pair` address (which is public/discoverable via `Bonding.tokenInfo(token).pair` or `Factory.getPair`) at any point pre- or post-graduation. No special timing, no race condition, and no privileged role is required.

### Recommendation
Add an owner-gated (or otherwise access-controlled) rescue path — e.g. a `Router.rescueDonatedAsset(token, recipient)` restricted to `BONDING_ROLE`/owner that transfers `Pair.assetBalance() - storedAssetReserve` (the excess over what the pool accounts for) to a designated recipient, callable regardless of the token's lifecycle state (including post-`Graduated`). This mirrors the Sherlock recommendation of parameterizing the withdraw target instead of hard-coding it to a single accounted asset.

### Proof of Concept
1. Launch a token via `Bonding.launch`/`Zap.createToken`, obtaining `tokenAddress` and its `pairAddress` (`Bonding.tokenInfo(tokenAddress).pair`).
2. From any unprivileged EOA, call `IERC20(ltAddress).transfer(pairAddress, 1000e18)` — a direct donation, no approval to `Bonding`/`Router` needed.
3. `Pair.assetBalance()` now exceeds stored `assetReserve` by `1000e18`, but `_prepareGraduationLiquidity`'s `ltFromPair` calc still uses the stored reserve, so this amount is never drained by `Router.graduate` during `_enterGraduating`/`finalizeGraduation`.
4. After the token graduates (`Lifecycle.Graduated`), attempt to recover the donated LT: there is no `Bonding`, `Router`, or `Pair` function reachable by anyone (owner included) that can move LT out of `pairAddress` — `Pair.transferAsset` requires `onlyRouter`, and `Router`'s only two callers of it (`sell`, gated by curve-state `BONDING_ROLE` calls from `Bonding.sell`, and `graduate`, unreachable post-`Curve`) never target this leftover balance.
5. The `1000e18` LT is permanently stuck in `pairAddress` with no recovery mechanism, confirmed by the contract's own natspec stating the balance is "unreachable."

```text
    /// @notice Transfer exactly `amount` of LT out of the pair to the caller.
    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }
```
