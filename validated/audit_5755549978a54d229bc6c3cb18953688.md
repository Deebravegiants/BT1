### Title
`EvmHost.dispatch()`/`fundRequest()` do not refund or bound excess `msg.value` swapped via Uniswap, causing overpaid native token to be lost - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept `msg.value` and forward the **entire** value to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, ...)`, requesting an exact output of `post.fee` in the fee token, but the code never validates that `msg.value` corresponds to (or is bounded relative to) the amount actually required for that exact-output swap, nor does it forward any unspent native token back to the original caller (`_msgSender()`). This mirrors the reported RouterV2 issue: no check that the value sent equals the amount intended to be spent, so overpayment can be silently absorbed rather than returned to the sender.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 
the function does:
```solidity
if (msg.value > 0) {
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
```
The entire `msg.value` is sent to the router as `msg.value`, with `post.fee` as the exact output amount. Standard `UniswapV2Router02.swapETHForExactTokens` refunds unused ETH to `msg.sender` of the router call — which is `EvmHost` itself, not the EOA/contract that originally called `dispatch()`. As a result, any ETH sent beyond what is required to purchase `post.fee` worth of the fee token is refunded into `EvmHost`'s own balance, not the original caller's account, and `EvmHost` has no user-facing mechanism to reclaim or account for that dust — `_msgSender()` who overpaid permanently loses the difference.

The same pattern occurs in `fundRequest()`: [2](#0-1) 

and in `dispatch(DispatchGet)`: [3](#0-2) 

This is directly analogous to the reported RouterV2 issue: no check/reconciliation between `msg.value` sent and the amount actually needed for the swap, and no refund path to the original payer.

By contrast, `IntentGatewayV2.placeOrder()`/`fillOrder()` explicitly implement overpayment protection and refund excess native token to the sender (confirmed by tests `testPlaceOrder_RefundsExcessNativeToken` and `testFillOrder_RefundsSolverExcessNativeToken`): [4](#0-3) 
This shows the codebase is aware of the overpayment-refund pattern elsewhere but `EvmHost`'s `dispatch`/`fundRequest` do not implement it, confirming the gap is a genuine, in-scope inconsistency rather than an intentional design choice.

I was unable to fully verify, from the indexed snippets alone, the exact behavior of the specific `uniswapV2` router address configured in `_hostParams.uniswapV2` (it could be the canonical `UniswapV2Router02` or one of the repo's own wrapper contracts such as `GnosisUniswapV2Wrapper`, `UniV3UniswapV2Wrapper`, or `UniV4UniswapV2Wrapper`). The custom wrappers (`UniV3UniswapV2Wrapper`, `UniV4UniswapV2Wrapper`) do refund unused ETH, but critically **refund it to `msg.sender` of the wrapper call, which is `EvmHost`, not the end user who called `dispatch()`** — so the loss to the original caller persists regardless of which router implementation is deployed. `GnosisUniswapV2Wrapper.swapETHForExactTokens` doesn't refund at all and wraps the entire `msg.value`, compounding the issue further on that chain.

### Impact Explanation
Any user or dApp calling `dispatch()`, `dispatch(DispatchGet)`, or `fundRequest()` on `EvmHost` with native token payment and sending more than exactly required for the fee-token swap will have the excess silently retained by `EvmHost` (or, in the wrapper case, forwarded to `EvmHost`'s own balance instead of refunded to the caller). Since `quote()`-based off-chain estimation is explicitly documented as approximate/subject to slippage (per the docs: "Fee Calculation: Approximate (subject to slippage)"), users following recommended workflows are likely to send slightly more `msg.value` than strictly needed, guaranteeing recurring fund loss across the protocol. This is a direct, concrete loss of user funds with no recovery path exposed to end users.

### Likelihood Explanation
Likelihood is elevated relative to the original RouterV2 report because native-token dispatch is a documented, first-class payment path (see `docs/content/developers/evm/messaging/post-requests.mdx`), and the docs explicitly warn that fee quoting via Uniswap is "approximate (subject to slippage)" — meaning users following the docs' guidance to estimate and send `nativeCost` will routinely overpay due to slippage between quote-time and execution-time, triggering the loss on essentially every native-token dispatch, not merely due to user error.

### Recommendation
- After the `swapETHForExactTokens` call, compute the unspent ETH (`msg.value - amounts[0]`, where `amounts[0]` is the actual ETH spent as returned by the swap) and refund it to `_msgSender()` (or `post.payer`), analogous to how `IntentGatewayV2` refunds overpayment.
- Alternatively, require `msg.value` to exactly match the ETH needed (quoted just-in-time) and revert otherwise, or expose a dedicated sweep function so unintended dust does not become permanently unrecoverable.
- Apply the same fix consistently to `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: X}(post)` with `post.fee = F` (a small fee) where `X` significantly exceeds the ETH needed to buy `F` fee-token via the configured Uniswap router (e.g., due to quote() slippage documented in `docs/content/developers/evm/messaging/post-requests.mdx` lines 236-238, or simply overestimating gas price ahead of time).
2. `EvmHost.dispatch()` forwards the full `X` as `msg.value` to `swapETHForExactTokens{value: X}(F, path, address(this), ...)`.
3. The router buys exactly `F` fee-token using only the portion of `X` required (`spent < X`) and refunds `X - spent` ETH — but to `msg.sender` of the swap call, i.e., `EvmHost`, not to the original caller.
4. `EvmHost`'s ETH balance increases by `X - spent`; the original caller has no function to reclaim this amount. Repeating this across many dispatches accumulates stuck/lost user ETH inside `EvmHost` with no user-facing withdrawal mechanism — confirmed absent from the `EvmHost.sol` sections reviewed (`admin`-restricted functions only manage `feeToken`/consensus state, not native ETH refunds).
