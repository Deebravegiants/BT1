### Title
Shopify webhook `shop` attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw request body only, while the `shop` value used to attribute the webhook to a tenant is read from an unsigned HTTP header. Any party who can obtain one legitimately-signed webhook (e.g., by installing the app on their own shop) can replay that exact body+HMAC pair to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop, and the library will accept it as authentic and hand the forged shop identity to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

`shop` is read straight from an HTTP header with no cryptographic binding to the payload: [2](#0-1) 

`Registry.process` validates only the body HMAC via `Utils::HmacValidator.validate`, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, with no additional check that the header-derived shop matches anything cryptographically verified: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body) and the app's shared `api_secret_key`: [4](#0-3) 

Because Shopify signs webhooks with the app's single `client_secret` shared across every shop that installs the app (not a per-shop secret), and that secret only covers the body, a valid HMAC does not bind the request to any particular shop. This is the same class of bug as the report's "array keyed by unchecked/unbound index": the code trusts a value (`shop`) that is used to make identity/tenant decisions, but that value sits outside the region actually covered by the verification check (the HMAC), so two different "identities" (`victim-shop.myshopify.com` vs `attacker-shop.myshopify.com`) can be substituted at will without invalidating the check — exactly the "field acted on but not covered by the HMAC" pattern.

### Impact Explanation
An attacker who installs the target app on their own shop can receive a legitimately-signed webhook from Shopify for security/compliance-sensitive topics (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, or any topic the app subscribes to). The attacker can replay the identical body and `X-Shopify-Hmac-Sha256` value while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `Registry.process` will validate the HMAC successfully (it never inspected the shop header) and invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain. If the host application uses this `shop` value to look up/act on session records keyed by shop (the documented pattern, e.g. deleting the victim's stored access token on a forged `app/uninstalled`, or purging the victim's data on a forged `shop/redact`), this results in unauthorized cross-tenant actions taken against a shop the attacker never authenticated as. This satisfies the Critical "cross-tenant access" bar.

### Likelihood Explanation
Any internet user can install the target app on a shop they control (installation of apps is not privileged in the sense required by the exclusion rules — no `api_secret_key`, access token, or leaked credential of the victim/app is needed) and thereby obtain a validly-signed webhook. Replaying an HTTP POST with a modified header is trivial. The only prerequisite is that the app subscribes to webhook topics whose handler trusts `WebhookMetadata#shop` for tenant-scoped actions, which is the standard, documented usage pattern of this gem's webhook API.

### Recommendation
Do not treat header-derived `shop` as authenticated. Either:
- Extend `to_signable_string`/the HMAC computation to include the shop domain (would require coordinating with Shopify's signing scheme, which is not fully under this gem's control), or, more practically,
- Require/encourage callers to cross-check `request.shop` against the shop associated with the session/webhook subscription that was registered (e.g., verify the shop is one the app currently has an active session/install for) before acting on `WebhookMetadata`, and document clearly in `Registry`/`Request` that `shop` is not HMAC-verified so handler authors don't assume it is trustworthy on its own.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a legitimate `app/uninstalled` (or `shop/redact`) webhook signed by Shopify using the app's `client_secret`. Attacker captures the raw body `B` and the `X-Shopify-Hmac-Sha256` header `H`.
2. Attacker sends a POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic: app/uninstalled` (unchanged)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only — this still matches `H`, so validation succeeds: [3](#0-2) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and performs the app's `app/uninstalled` cleanup logic (e.g., deleting the stored session/access token) for the victim shop, even though the victim never uninstalled the app and the request never touched the victim's tenant.
