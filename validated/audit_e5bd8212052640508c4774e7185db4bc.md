No vulnerability found for this question.

**Reasoning:**

`TransactionAccumulatorDb::prune(begin, end, ...)` is a `pub(crate)` internal storage function; its `begin`/`end` parameters are not attacker-influenced. They come exclusively from `current_progress`/`target_version` passed by `TransactionAccumulatorPruner::prune`, which in turn are set by the ledger pruner's internal progress tracking and `target_version`, driven by the node's own committed `latest_version` and a locally configured `prune_window`/`user_pruning_window_offset` — not by any transaction, API request, or bytecode input. [1](#0-0) [2](#0-1) [3](#0-2) 

There is no "pruning-window request" surface reachable by an unprivileged caller — pruning windows are local node configuration, not a network/API-exposed parameter, and no external actor supplies `begin`/`end` to this function.

Additionally, the deletion algorithm itself is the standard Merkle accumulator one-sided pruning technique documented at aptos-labs/aptos-core#1288: it walks to the first ancestor that is a left child (via `find_first_ancestor_that_is_a_left_child`, using `trailing_ones()`), which by construction is never deleted, and only descends to delete strictly non-useful subtree nodes along the way. This is verified by existing tests such as `verify_transaction_accumulator_pruned`, which checks that all postorder positions below the least-readable-position boundary are deleted and nothing above it is touched. [4](#0-3) [5](#0-4) 

Even under a hypothetical where an attacker could somehow shift the pruning boundary, the worst-case outcome would be loss of historical proof availability for pruned versions — a data-retention/liveness concern, not a custody-control issue. It does not change any asset owner, holder, freeze authority, dispatchable-hook registration, or mint/burn/transfer capability; fungible-asset dispatch hooks are a Move-level registration stored in on-chain resources, entirely unrelated to this Rust-level accumulator pruning code path. This fails both the required unprivileged-entrypoint requirement and the custody-impact gate (no owner/balance/authority is altered), so it is rejected per the decision standard.

    fn prune(&self, max_versions: usize) -> Result<Version> {
        let mut progress = self.progress();
        let target_version = self.target_version();

        while progress < target_version {
            let current_batch_target_version =
                min(progress + max_versions as Version, target_version);

            info!(
                progress = progress,
                target_version = current_batch_target_version,
                "Pruning ledger data."
            );
            self.ledger_metadata_pruner
                .prune(progress, current_batch_target_version)?;

            THREAD_MANAGER.get_background_pool().install(|| {
                self.sub_pruners.par_iter().try_for_each(|sub_pruner| {
                    sub_pruner
                        .prune(progress, current_batch_target_version)
                        .map_err(|err| anyhow!("{} failed to prune: {err}", sub_pruner.name()))
                })
            })?;

            progress = current_batch_target_version;
            self.record_progress(progress);
            info!(progress = progress, "Pruning ledger data is done.");
        }

        Ok(target_version)
    }

fn verify_transaction_accumulator_pruned(ledger_store: &LedgerStore, least_readable_version: u64) {
    let least_readable_position = if least_readable_version > 0 {
        Position::root_from_leaf_index(least_readable_version).left_child()
    } else {
        Position::root_from_leaf_index(least_readable_version)
    };
    let least_readable_position_postorder = least_readable_position.to_postorder_index();
    for i in 0..least_readable_position_postorder {
        assert!(ledger_store
            .get(Position::from_postorder_index(i).unwrap())
            .is_err())
    }
}
