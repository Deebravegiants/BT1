### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, but the `shop` field returned to the application (and passed into the handler as the identity of the merchant the payload belongs to) comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the HMAC-signed content. This breaks the identity binding `hmac-verified bytes == data attributed to shop`, letting a holder of any single valid (body, hmac) pair reattribute that payload to an arbitrary victim shop domain.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived independently from an HTTP header that is not part of the signable string: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because the same app `client_secret` is used to sign webhooks for *every* shop that has installed the app (this is inherent to Shopify's webhook HMAC design and is exactly the identity boundary this gem is supposed to help enforce), any unprivileged internet user who owns a shop and installs the app can:
1. Receive a genuine webhook for their own shop, complete with a valid `hmac-sha256` header computed over the raw body using the app's shared secret.
2. Replay that exact body and HMAC to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `Utils::HmacValidator.validate` still succeeds, since it only checks the (unchanged) body bytes against the (unchanged) HMAC: [4](#0-3) 
4. `Registry.process` then calls the handler with `WebhookMetadata` claiming the payload is `shop: <victim>`, even though the signed bytes actually originated from the attacker's own shop.

The gem's documented contract explicitly tells integrators that `process` "will verify the request did indeed come from Shopify" (see `docs/usage/webhooks.md` lines 125), and that `data.shop` is "The shop domain of the webhook" — i.e., a trusted, verified field. In reality, `shop` is not covered by the verification at all, so the guarantee the gem advertises does not hold for that field.

### Impact Explanation
This is a cross-tenant identity binding failure: an attacker who is merely an unprivileged, legitimate installer of the app (no special privilege, no access token theft) can make forged/attacker-controlled webhook payloads be attributed to a different, victim tenant (shop) inside the host application. Since integrators are told (and reasonably expect) that `data.shop` is authenticated, downstream logic that keys off `data.shop` to select the victim's session/access token, update the victim's local records, or trigger further authenticated Admin API calls on the victim's behalf will process attacker-supplied body content as if it came from the victim shop — a cross-tenant access/data-integrity violation rooted directly in this gem's verification logic.

### Likelihood Explanation
High likelihood of exploitability: obtaining a single valid (body, HMAC) pair requires nothing more than installing the app on any attacker-controlled shop, which is achievable by any unprivileged internet user for public/freemium Shopify apps. No access token, `client_secret`, or privileged account is needed — only header manipulation on an HTTP request to the app's own webhook endpoint.

### Recommendation
Bind the `shop` field into the value that is actually verified. Concretely, either:
- Include the shop domain in the signed material checked against the HMAC digest (not possible without protocol changes on Shopify's side), or, more practically for this gem:
- After validating the body HMAC, cross-check the header-supplied `shop` against a shop actually known to be registered for the specific `webhook_id`/topic (e.g., verify the shop has an active session/registration matching that webhook before dispatching), or
- Clearly document that `data.shop` in `WebhookMetadata` is **not** cryptographically bound by `Registry.process`'s HMAC check, and require integrators to independently verify shop ownership (e.g., against their own session store) before trusting `data.shop`, or reject the analog if this is intended/documented behavior of Shopify's actual webhook protocol (Shopify's own HMAC also famously excludes headers — but the gem should not represent `process` as verifying "the request did indeed come from Shopify" for the `shop` value it hands off).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining valid webhooks for actions on their own store (e.g., `orders/create`).
2. Attacker triggers an event on their own shop, capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker replays the request to the app's webhook endpoint with the same `B` and `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `H`: [5](#0-4) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)`: [6](#0-5) 
6. Any application logic that trusts `data.shop` (as the docs instruct) now processes attacker-controlled data under the victim shop's identity.
