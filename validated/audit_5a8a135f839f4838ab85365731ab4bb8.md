### Title
Escrow crediting decoupled from actual transferred amount in `placeOrder` (Tron IntentGateway) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of the intents `IntentGatewayV2.placeOrder` credits the internal `_orders` escrow ledger using the user-declared `order.inputs[i].amount` (minus protocol fee) instead of the amount actually received by the contract via `safeTransferFrom`. This is the same class of accounting bug as the Beanstalk `FieldFacet` report: the amount recorded in internal accounting is not tied to the amount actually pulled into the contract, allowing escrow records to exceed real token balances for any input token whose transfer can deliver less than the requested `amount` (fee-on-transfer / deflationary / rebasing ERC20s).

### Finding Description
In the non-Tron `evm/src/apps/IntentGatewayV2.sol`, `placeOrder` explicitly measures actual received balances before crediting escrow — see the "Phase 1" comment and code that snapshots `balBefore`/`balancesAfter` and mutates `order.inputs[i].amount` to the delta actually received: [1](#0-0) 

The Tron contracts fork of the same function (`evm/tron/contracts/apps/IntentGatewayV2.sol`) removed this safety measurement. It computes `reducedInputs[i].amount` directly from the user-supplied `order.inputs[i].amount` (only reduced by protocol fee bps), commits it into `commitment`, then performs `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, with no check that the contract's balance actually increased by that amount: [2](#0-1) [3](#0-2) 

This exactly mirrors the Beanstalk `FieldFacet._sow()` flaw: pods (here, escrow ledger entries) are computed and credited from the *declared* amount, while the actual value taken from the user (here, actual ERC20 balance delivered, analogous to Beans actually burned) can be smaller for fee-on-transfer or deflationary tokens. The predispatch branch of the same function has an identical issue — it credits `reducedInputs[i].amount` to escrow while only checking `balance < requiredAmount` from the dispatcher, not the actual delta received by the gateway itself: [4](#0-3) 

Escrowed balances are later paid out via `safeTransfer` to solvers/refund beneficiaries (the withdrawal/redeem/refund logic that reads `_orders[commitment][token]`), which will attempt to transfer out the recorded (inflated) escrow amount regardless of the contract's true token balance.

### Impact Explanation
If a fee-on-transfer or deflationary ERC20 is used as an order input, `_orders[commitment][token]` is credited with more tokens than the gateway actually holds for that order. When solvers fill the order and the escrow is released (or the user cancels and is refunded), the payout for this order — and consequently for any other unrelated orders sharing the same token's pooled balance in the contract — can fail (revert due to insufficient balance) or drain balance meant for other users' orders. This causes permanent freezing of funds for the affected orders/users and can corrupt shared-token accounting across the whole intents gateway, since `_orders` is a per-token mapping backed by one shared ERC20 balance in the contract. This is reachable by any unprivileged user who simply calls `placeOrder` with a fee-on-transfer token as input — no privileged role or governance required.

### Likelihood Explanation
Medium-to-High. Any ERC20 token configured as a supported input (fee-on-transfer, deflationary, or tokens with transfer hooks that can reduce the delivered amount) triggers this immediately and deterministically on a single `placeOrder` call — no timing race or unusual market condition is needed, unlike the original Beanstalk peg-dependent scenario. The severity depends on whether the deployment allows arbitrary/permissionless input tokens; if input tokens are allow-listed to only standard, non-fee ERC20s, exploitability is reduced, but the code contains no check enforcing that invariant, and the sibling non-Tron implementation already treats "for fee-on-transfer tokens, the gateway receives less than the requested amount" as an explicit, expected condition to guard against (per its own inline comment), confirming this is a recognized real-world risk class for this contract family.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure the actual token balance delta before and after each `safeTransferFrom` (and after sweeping from the predispatch dispatcher), mutate `order.inputs[i].amount` to the actually-received amount, and derive `reducedInputs`/escrow credits and the commitment hash from that verified actual amount rather than the caller-declared `amount`. Apply the same actual-balance-delta measurement in the predispatch sweep path.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and register a 1% fee-on-transfer ERC20 as a valid input token (or use a token that already exists as a supported input in the deployment).
2. A user calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes, but the FOT token only delivers `990e18` to the gateway (1% fee burned/redirected by the token itself).
4. `reducedInputs[0].amount` is computed from the declared `1000e18` (minus protocol fee, if any) — not from the `990e18` actually received — and `_orders[commitment][FOT] += reducedInputs[0].amount` credits the escrow with an amount exceeding the gateway's real token balance for this order.
5. When a solver fills the order and the escrow-release/`safeTransfer(beneficiary, escrowedAmount)` path executes, the transfer either reverts due to insufficient balance (freezing this and possibly other users' orders sharing the same token pool) or succeeds by draining tokens belonging to other orders' escrow, breaking the accounting invariant that `sum(_orders[*][token]) <= actual token balance held by the gateway`.
