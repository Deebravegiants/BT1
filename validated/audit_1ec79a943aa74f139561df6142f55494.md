### Title
Webhook `shop`, `topic`, and `webhook-id` Headers Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop`, `topic`, and `webhook_id` fields directly from unauthenticated HTTP headers, while the HMAC signature verified by `Registry.process` only covers the raw request body. This is the same overshadowing/binding class as the reported `Staking.withDrawFunds` bug: a field that is *acted on* (here, the shop the webhook data is attributed to) is not actually *covered* by the cryptographic check that is supposed to authenticate the whole request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are read straight from attacker-controllable HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body and then trusts `request.shop` / `request.topic` / `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string`, so it never touches the headers: [4](#0-3) 

The identity binding that should hold is:
`HMAC-authenticated bytes == bytes that determine the tenant (shop) the data is attributed to`

but in this implementation:
`HMAC-authenticated bytes = raw_body` while `tenant attribution = x-shopify-shop-domain header (unauthenticated)`

Because a real Shopify webhook body's HMAC is computed with the app's `api_secret_key` regardless of which of the app's installed shops sent it, an unprivileged attacker who legitimately installs the app on their own (e.g. free/dev) store can capture a genuine `(raw_body, hmac)` pair from their own webhook delivery, then resend that exact body+hmac to the app's webhook endpoint while overwriting `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) to point at a different, victim merchant's shop domain. `Registry.process` will still pass HMAC validation (since it only checks the body) and will invoke the topic handler with `shop: <victim-domain>`, causing the host application to process/store data under the wrong tenant.

### Impact Explanation
This breaks tenant isolation for webhook processing: the library-provided `ShopifyAPI::Webhooks::Request`/`Registry.process` API — which app developers rely on specifically because "this will verify the request did indeed come from Shopify" (per the gem's own docs) — does not actually authenticate which shop a webhook body belongs to. Any app that keys per-tenant side effects (order/customer record updates, GDPR data requests, uninstall handling, billing state, etc.) off `WebhookMetadata#shop` inherits a cross-tenant data-confusion vulnerability purely from using the gem as documented, satisfying the "cross-tenant access" impact bar.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a shop they control (any developer/free-trial store) to obtain one legitimately-HMAC-signed webhook body/signature pair, and the ability to send an arbitrary HTTP request to the target app's public webhook endpoint with custom headers — both are unprivileged-internet-user actions with no access token, `api_secret_key`, or elevated privilege required.

### Recommendation
Bind the tenant-identifying fields into the HMAC-covered signable content (e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`, mirroring what OAuth's `AuthQuery#to_signable_string` already does for `shop`/`host`), or otherwise cryptographically/contractually bind the `shop-domain` header to the payload before it is trusted for dispatch in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) with an empty/minimal body, capturing the resulting raw body and the `x-shopify-hmac-sha256` value the app's server received.
2. Attacker sends a forged POST to the app's webhook route with the same raw body and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes the HMAC over the (unchanged) body via `Utils::HmacValidator.validate`, which succeeds, per `lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, per `lib/shopify_api/webhooks/registry.rb:198-199`, even though the HMAC never authenticated that shop value.
