### Title
Unchecked ERC20 return value in `withdraw()` and `SweepDust` handling permanently locks escrowed collateral - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` uses low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` for releasing escrowed order tokens (`withdraw()`) and for sweeping protocol dust (`SweepDust` handling in `onAccept`), checking only that the external call did not revert (`success`) but never inspecting the ABI-decoded boolean return value. For ERC20 tokens that signal failure by returning `false` instead of reverting (e.g. tokens with blocklists such as STASIS EURO, or legacy non-reverting tokens), the call reports `success == true` even though no tokens were actually moved, while the contract still permanently updates escrow accounting and finalizes order state.

### Finding Description
In `withdraw()`, escrowed input tokens are released to the beneficiary/solver via: [1](#0-0) 

and transaction fees are released the same way: [2](#0-1) 

`withdraw()` unconditionally marks the order as finalized before/around the transfer attempts (`_filled[body.commitment] = beneficiary;`) and decrements the escrow balance (`_orders[body.commitment][token] -= amount;`) regardless of whether the underlying token transfer actually moved funds: [3](#0-2) 

The same unchecked pattern exists in the `SweepDust` branch of `onAccept`, used by governance-authorized protocol dust sweeps: [4](#0-3) 

Because `token.call(...)` only reverts if the callee itself reverts or the call target has no code, tokens that return `false` on failure (rather than reverting) will make `success` true. The code checks `if (!success) revert TransferFailed();` — this only guards against the call reverting, not against the token semantically failing the transfer via a `false` return value. This is the exact bug class reported in the external report for Cooler.sol's `rescind`: an unchecked/insufficiently-checked ERC20 transfer whose failure mode is a `false` return rather than a revert.

This contrasts with the rest of the same file and the parallel EVM implementation (`evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/IntentsBase.sol`), which correctly use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (which decode and check the boolean return value) for all user-facing transfers: [5](#0-4) 

The Tron `IntentGatewayV2` even imports and uses `SafeERC20` elsewhere in the same file for `placeOrder`'s `safeTransferFrom` calls, but not for `withdraw()`/`SweepDust`: [6](#0-5) 

### Impact Explanation
If a user escrows a token that has blocklisting or non-reverting failure semantics (e.g., regulated stablecoins, or tokens that later become non-standard due to upgrades/proxy changes), and the beneficiary/solver becomes blocked or the transfer otherwise semantically fails without reverting at settlement time:
- `withdraw()` will still mark the order as filled/refunded (`_filled[body.commitment] = beneficiary`) and decrement `_orders[commitment][token]`, permanently finalizing order state.
- The tokens are never actually delivered to the beneficiary/solver, yet the internal escrow accounting no longer reflects any recoverable balance for that commitment (since the order is finalized and the escrow slot has been zeroed/decremented).
- This results in permanent loss of the escrowed collateral for the affected token — funds are stuck in the contract with no path to recovery for that order, since `withdraw()` is the terminal state-transition function for both `RedeemEscrow` and `RefundEscrow` code paths (cross-chain fill settlement and cancellation refunds) as well as the GET-response cancellation path (`onGetResponse`).

### Likelihood Explanation
Likelihood is contingent on the specific ERC20 collateral token used for a given order. Not "all" ERC20 tokens exhibit this behavior, but this is a well-known class of non-standard tokens (blocklisting stablecoins, some legacy tokens) that are realistically usable as intent-gateway input assets since `IntentGatewayV2` accepts arbitrary ERC20 addresses as `order.inputs[i].token` without an allow-list restricting to strictly-reverting-on-failure tokens. Any user or relayer settling an order denominated in such a token can trigger this silently.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` and the `SweepDust` branch of `onAccept` with OpenZeppelin's `SafeERC20.safeTransfer` (already imported and used elsewhere in this same file for `safeTransferFrom`), which decodes and validates the boolean return value and reverts on `false`:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```
Apply the same fix to the fee transfer and dust-sweep transfer sites.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a mock ERC20 `BlockableToken` whose `transfer()` returns `false` (without reverting) when the recipient is in a blocklist, mimicking STASIS EURO/blocklist-style tokens.
2. A user calls `placeOrder` with `BlockableToken` as an input, escrowing tokens; `_orders[commitment][token]` is credited via `safeTransferFrom` (which succeeds normally).
3. Add the eventual beneficiary (e.g., the solver address, or user address for a refund) to the token's blocklist before settlement.
4. Trigger settlement: either a solver calls `fillOrder` on the destination and the source-chain `onAccept` processes `RedeemEscrow`, or a `cancelOrder` flow leads to `RefundEscrow`/`onGetResponse` on the source chain, invoking `withdraw()`.
5. Observe: `token.call(...)` returns `success = true` (call itself doesn't revert) but the internal `false` return of `transfer()` is ignored; `_filled[commitment]` is set and `_orders[commitment][token]` is decremented, yet `BlockableToken.balanceOf(beneficiary)` shows no tokens received — the tokens remain stuck in the `IntentGatewayV2` contract with no further code path to reclaim them for that commitment.
