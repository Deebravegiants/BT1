### Title
POA Bridge withdrawal status is matched by `assetId` only, causing misreported completion status/tx hash for same-token batch withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
The `KelpCooldownHolder` report describes a class of bug where a claim/finalization function picks an entry from an array of pending requests using a naive, unauthenticated selector (hardcoded index) instead of verifying that the entry actually corresponds to the request being finalized — letting an unrelated entry get matched/consumed in place of the real one. The analogous pattern exists in this repo's POA bridge withdrawal-status matching: `findMatchingWithdrawal` selects the *first* withdrawal in the API response whose `near_token_id` maps to the requested `assetId`, without checking amount, destination address, or withdrawal index. When a batch intent contains more than one withdrawal leg of the same underlying token (POA bridge doesn't disambiguate this case, as the code itself documents), `describeWithdrawal` for every leg of that token resolves to the *same* entry, misreporting completion status/transaction hash for legs that are not actually the one it claims to be.

### Finding Description
`PoaBridge.describeWithdrawal` fetches all withdrawals associated with a NEAR transaction hash and picks a match purely by `assetId`: [1](#0-0) [2](#0-1) 

The `args.index` field carried on the `WithdrawalIdentifier` (used everywhere else in the SDK to disambiguate legs of a batch withdrawal, e.g. in `HotBridge.describeWithdrawal` via `nonces[args.index]` and in `OmniBridge.describeWithdrawal` via `getTransfer(...)[args.index]`) is **not used at all** by `findMatchingWithdrawal`. The exact same matching-by-asset-only logic (and the exact same documented limitation) is duplicated in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`: [3](#0-2) 

Both implementations carry the same self-documented caveat:
> "NOTE: Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported."

This is precisely the equality the Kelp report describes as broken: the routine is supposed to report the status of *the specific withdrawal request the caller is asking about*, but instead it reports whatever it finds first that shares only a coarse attribute (asset), silently ignoring the other identifying fields (index, amount, destination) that would make the match unambiguous — the same class of bug as Kelp's hardcoded "claim the 0-th request" instead of the caller's actual request.

### Impact Explanation
The SDK explicitly supports batch withdrawals where `sdk.createWithdrawalCompletionPromises` returns one promise per leg and documents "Index correspondence: `promises[i]` corresponds to `withdrawalParams[i]`" as a contract integrators rely on: [4](#0-3) 

If a batch contains two or more withdrawal legs that route through the POA bridge for the *same* NEP-141 asset (e.g., two USDC withdrawals to two different destination addresses/amounts in one NEAR intent transaction), each leg's `describeWithdrawal` call returns the identical first-matched entry. The consequence is a status/tx-hash misreport: an integrator polling `promises[0]` and `promises[1]` (or using `waitForWithdrawalCompletion`) can be told both legs completed with the *same* destination transaction hash, even though only one of the two on-chain transfers actually happened for that hash. This matches the "High" impact bucket defined by the rules: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This does not require an external malicious actor to inject data into someone else's request (unlike the Lido scenario, where a third party can freely call `requestWithdrawals`), because the POA API keyed by `withdrawal_hash` only returns withdrawals belonging to the same NEAR intent transaction. However, it is entirely reachable by any integrator/service that batches multiple recipients' same-token withdrawal legs into one intent transaction (a supported, documented SDK feature), without any privileged or malicious action — simply exercising ordinary batch-withdrawal functionality with two legs of the same asset. Given the code's own comment acknowledges this exact scenario ("multiple withdrawals of the same token in a single transaction are not supported"), it is a real, currently-unhandled gap rather than a theoretical one, though it is a known/documented limitation rather than a hidden defect.

### Recommendation
Extend `findMatchingWithdrawal` (in both `poa-bridge.ts` and `waitForWithdrawalCompletion.ts`) to disambiguate among multiple candidates sharing the same `assetId` by additionally matching on amount and/or destination address, or by sorting candidates and the caller's withdrawal params consistently (as the code comment suggests) and selecting by relative order/index rather than returning the first `Array.prototype.find` match. Until fixed, the SDK should explicitly reject or warn when a batch contains multiple same-asset POA-bridge legs, since the current matching cannot disambiguate them.

### Proof of Concept
Conceptual reproduction (cannot be executed here, but derivable from the code paths cited above):
1. Build a batch withdrawal intent with two `withdrawalParams` entries, both `assetId: "nep141:usdc.token.near"` routed via `PoaBridge`, but with different `destinationAddress`/`amount` (e.g., leg A → address X for 100 USDC, leg B → address Y for 200 USDC).
2. Submit via `sdk.signAndSendWithdrawalIntent` and settle the intent, obtaining a single `intentTx.hash`.
3. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams: [legA, legB], intentTx })`.
4. Once the POA bridge indexes and completes both transfers, `poaBridge.httpClient.getWithdrawalStatus({ withdrawal_hash: intentTx.hash })` returns an array with two `COMPLETED` entries (one per leg), both having `near_token_id: "usdc.token.near"`.
5. `findMatchingWithdrawal(withdrawals, "nep141:usdc.token.near")` is called independently for `promises[0]` and `promises[1]`; both invocations run `.find(w => nep141:${w.data.near_token_id} === assetId)` and return the **same first entry** in the array — e.g., leg B's transfer data — regardless of which index was requested.
6. Both `promises[0]` and `promises[1]` resolve to the same `{ status: "completed", txHash }`, so an integrator relying on "Index correspondence: `promises[i]` corresponds to `withdrawalParams[i]`" would incorrectly report leg A as completed using leg B's transaction hash/amount, and vice versa — a status/hash misreport that could lead to crediting the wrong destination or crediting twice.

Note: This is based on static code review of the matching logic and its documented limitation; I was not able to execute a live test against the POA bridge API to confirm the exact response shape/ordering in production, so this should be validated against the live indexer behavior before treating it as confirmed exploitable in a specific integrator's flow.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).

function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
