### Title
`delegated` wallet-account asset restriction is enforced only in a UI selector, not in the transaction/message signing path - ([File: features/tx-signer/src/module/seed-signer.ts])

### Summary
`SettV3.transferFrom`'s bug class is: a security-critical check (`_blockLocked`) is bound to the wrong context (`msg.sender`) and can be bypassed by reaching privileged state mutation through an alternate call path (`transferFrom`) that never re-validates the constraint that mattered (the token owner). In hydra, the same pattern occurs with `WalletAccount.delegated`: the restriction "delegated accounts may only use `solana`/`usdcoin_solana`" is implemented once, in a display/selector atom, but is never re-checked at the actual authorization boundary where signing happens.

### Finding Description
`WalletAccount` has a `delegated` boolean flag [1](#0-0) , which is documented/tested to restrict a delegated account to a limited allow-list of assets (`delegatedAllowedAssetNames`, defaulting to `['solana', 'usdcoin_solana']`) [2](#0-1) .

That restriction is implemented purely as a `createSelector` filter used to compute `availableAssetNamesByWalletAccount`, i.e. it only decides which assets are *displayed/offered* for a delegated account: [3](#0-2) 

However, the actual signing modules that perform the privileged action — `SeedBasedTransactionSigner.signTransaction` and `SeedBasedMessageSigner.signMessage` — never read or check `walletAccount.delegated` anywhere. `signTransaction` only uses `walletAccount.index`, `compatibilityMode`, and an optional caller-supplied `txMeta.keyId`, deriving a signer for whatever `baseAssetName` is passed in: [4](#0-3) 

Similarly `SeedBasedMessageSigner.signMessage` derives the key purely from `baseAssetName`/`walletAccount` with no `delegated` check: [5](#0-4) 

The public `TransactionSignerApi`/`TransactionSigner` and `MessageSigner` entry points accept an arbitrary `baseAssetName` string directly from the caller and simply resolve the `WalletAccount` object, then forward to the seed-based signer — there is no gate anywhere in this call chain re-validating that `baseAssetName` is a member of `delegatedAllowedAssetNames` for a `delegated` account: [6](#0-5) [7](#0-6) 

This is directly analogous to `SettV3`: the guard (`_blockLocked` / `delegatedAllowedAssetNames` filter) exists, but is bound to the wrong "actor" — it's attached to a UI-facing selection atom (the equivalent of checking `msg.sender` instead of `from`) instead of the actual state-mutating call (signing), so any code path that calls `transactionSigner.signTransaction` / `messageSigner.signMessage` directly with a delegated `WalletAccount` and a non-allow-listed `baseAssetName` bypasses the restriction entirely, just as `transferFrom` bypassed `_blockLocked` by routing around the guarded `msg.sender` check.

### Impact Explanation
If `delegated` wallet accounts are meant to represent a reduced-trust/compliance-restricted account type (e.g., an institutional or custody-delegated account that is only supposed to be able to transact in `solana`/`usdcoin_solana`), any caller with access to the `transactionSignerApi.signTransaction` or `messageSigner.signMessage` module APIs (e.g. an SDK consumer, headless integration, or any internal/plugin code that doesn't go through the asset-selection UI) can sign transactions/messages for that delegated account using an asset outside the allowed set. Since signing is the ultimate privileged action that produces a valid, broadcastable transaction, this defeats the entire purpose of the `delegated` restriction and allows unauthorized fund movement/signing outside the intended asset scope for that account — a direct wallet-authorization-bypass impact, mirroring the "block lock is ineffective" impact of the original finding.

### Likelihood Explanation
Reachable by any code that has access to `walletAccountsAtom`/`transactionSigner`/`messageSigner` module APIs and knows (or can guess) the account is `delegated` (its `toJSON()`/`toRedactedJSON()` exposes `delegated: true`) [8](#0-7) . No UI interaction, private-key access, or externally-privileged capability is needed beyond the same level of access already required to legitimately sign for that account through the intended (filtered) UI flow — likelihood is high for any consumer that calls the signer APIs directly rather than going exclusively through the asset-selection atom.

### Recommendation
Move (or duplicate) the `delegated` → `delegatedAllowedAssetNames` enforcement from the display-only selector into the actual signing authorization boundary: `SeedBasedTransactionSigner.signTransaction` and `SeedBasedMessageSigner.signMessage` (and/or their public `transactionSignerApi`/`messageSigner` API wrappers) should assert that `walletAccount.delegated` implies `baseAssetName` (and any equivalent asset for message signing) is a member of the configured `delegatedAllowedAssetNames` set, throwing/rejecting otherwise. The check must live at the point where the private key is actually used, not only where the asset list is computed for UI display.

### Proof of Concept
1. Construct a `WalletAccount` with `delegated: true`, e.g. `new WalletAccount({ source: 'exodus', index: 0, delegated: true })`.
2. Call `transactionSigner.signTransaction({ baseAssetName: 'ethereum', unsignedTx, walletAccount })` (or the equivalent `transactionSignerApi.signTransaction`) directly, bypassing the `availableAssetNamesByWalletAccountAtom` selector that would normally have excluded `ethereum` for a delegated account.
3. Observe that `SeedBasedTransactionSigner.signTransaction` proceeds to derive a signer via `#getSignerForWalletAccount` for `ethereum` and returns a validly signed Ethereum transaction for the delegated account [4](#0-3) , with no rejection based on the `delegated`/`delegatedAllowedAssetNames` restriction — confirming the guard is bypassable via the direct signer API path, exactly as `transferFrom` bypassed `_blockLocked`.

    const { baseAssetName, unsignedTx, walletAccount } = opts

    if (!('compatibilityMode' in unsignedTx.txMeta)) {
      unsignedTx.txMeta.compatibilityMode = walletAccount.compatibilityMode

    if (!('accountIndex' in unsignedTx.txMeta)) {
      unsignedTx.txMeta.accountIndex = walletAccount.index
    }

    assert(
      Number.isInteger(unsignedTx.txMeta?.accountIndex),
      `txMeta.accountIndex was not a valid integer`
    )

    assert(baseAsset.api.features.signWithSigner, `asset ${baseAssetName} does not support signing`)

    const keyId = unsignedTx.txMeta?.keyId
    const signTx = baseAsset.api.signTx!

    if (!keyId) {
      const signer = await this.#getSignerForWalletAccount({ walletAccount, baseAsset })
      return signTx({ unsignedTx, signer })
    }

const createTransactionSignerApi = ({
  transactionSigner,
  walletAccountsAtom,
}: Dependencies): TransactionSignerApi => {
  const getWalletAccount = async (name: string): Promise<WalletAccount> => {
    const walletAccounts = await walletAccountsAtom.get()
    const walletAccount = walletAccounts[name]
    assert(walletAccount, `Unknown wallet account: ${name}`)
    return walletAccount
  }

  return {
    transactionSigner: {
      signTransaction: async (params: SignTransactionApiParams) => {
        const walletAccount =
          typeof params.walletAccount === 'string'
            ? await getWalletAccount(params.walletAccount)
            : params.walletAccount

        return transactionSigner.signTransaction({ ...params, walletAccount })
      },
    },
  }
}
