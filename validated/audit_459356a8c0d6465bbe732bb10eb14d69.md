Audit Report

## Title
DMP inbound message path never enforces `check_enough_messages_included_advanced`, allowing a malicious collator to censor downward XCM/DMP messages while satisfying all on-chain checks - ([File: cumulus/pallets/parachain-system/src/lib.rs])

## Summary
`enqueue_inbound_horizontal_messages` enforces both the weak `check_enough_messages_included_basic` and the size-based `check_enough_messages_included_advanced` invariant before accepting a collator-provided HRMP message collection, but `enqueue_inbound_downward_messages` only calls `check_enough_messages_included_basic`. [1](#0-0) [2](#0-1)  This asymmetry means a collator can satisfy the DMQ MQC-head consensus check while including only a minimal filler full message and hashing away larger legitimate downward messages (DMP-delivered XCM, UMP responses, etc.), effectively censoring specific messages without violating any enforced invariant.

## Finding Description
`AbridgedInboundMessagesCollection::check_enough_messages_included_basic` only asserts `full_messages.len() >= 1` whenever `hashed_messages` is non-empty — it performs no size accounting at all. [3](#0-2)  The complementary `check_enough_messages_included_advanced` asserts that the sum of included full-message sizes plus the worst-case size of the first hashed message must exceed the size budget (`max_full_messages_size`), which is the actual mechanism that prevents a collator from artificially truncating the full-message set while claiming there wasn't room for more. [4](#0-3)  The doc-comment explicitly states the basic check alone is insufficient and that a malicious collator omitting the advanced check leads to censorship. [5](#0-4) 

`enqueue_inbound_horizontal_messages` calls the advanced check, using the ingress channel's `max_message_size` as `first_hashed_msg_max_size` and `Self::messages_collection_size_limit()` as `max_full_messages_size`. [2](#0-1)  `enqueue_inbound_downward_messages` calls only the basic check and never calls the advanced check anywhere in its body. [6](#0-5)  This is confirmed directly by reading the full function body — there is no call to `check_enough_messages_included_advanced` for DMP anywhere in `lib.rs`; only two total call sites of that method exist in the codebase, both inside `enqueue_inbound_horizontal_messages`.

The abridged inbound message collections (both DMP and HRMP) are constructed by `Pallet::do_create_inherent` from collator-supplied `ParachainInherentData`/`InboundMessagesData`, using `into_abridged` to split full vs. hashed messages according to a size limit computed by the collator's client code — but the runtime only re-verifies this split via the two check functions described above, since the actual message data (not size limit) originates from the relay chain state proof. Since the advanced check is skipped for DMP, a collator can submit a `set_validation_data` inherent whose `downward_messages.full_messages` contains just one trivial (e.g. 1-byte) message and whose `hashed_messages` contains the hash of a larger legitimate message, satisfying `check_enough_messages_included_basic` (full_messages.len() >= 1) without ever needing to prove that no more full messages could fit.

## Impact Explanation
This allows a malicious or colluding collator to selectively censor specific downward (relay-chain-to-parachain) XCM/DMP messages — e.g., incoming token transfers, governance-relayed calls, or other cross-chain instructions targeted at unprivileged accounts — by consistently hashing them away while including only a minimal filler full message, as long as that collator continues to produce blocks for the parachain. This is a legitimate asymmetry in the codebase: the HRMP path has an explicit defense against this exact censorship vector (as documented in the code's own comments) that the DMP path lacks entirely. The impact matches an in-scope "selective message censorship" class since it is caused directly by an SDK code omission (missing invariant enforcement) rather than by external/mocked components.

## Likelihood Explanation
The attack requires only that the attacker control block production for the parachain (an operational collator role), which is an explicitly anticipated adversarial model per the pallet's own documentation. No governance, root, or leaked-key access is needed, and the attack is repeatable every block for as long as the attacker retains collator privileges. This is a realistic and directly reachable condition, not a purely theoretical one.

## Recommendation
Add a call to `check_enough_messages_included_advanced` in `enqueue_inbound_downward_messages`, mirroring the HRMP path: use `AbridgedInboundMessagesSizeInfo` with `max_full_messages_size` set to the DMP portion of `Self::messages_collection_size_limit()` and `first_hashed_msg_max_size` set to the relay chain's configured `max_downward_message_size` (obtainable from the relay-chain host configuration in the state proof, analogous to how the HRMP path reads `channel.max_message_size` from `ingress_channels`).

## Proof of Concept
1. Construct an `AbridgedInboundDownwardMessages` with `full_messages = [1-byte message]` and `hashed_messages = [hash of a much larger legitimate message]`, matching the pattern of the existing `check_enough_messages_included_advanced_works` unit test in `parachain_inherent.rs`. [7](#0-6) 
2. Compute the correct MQC head for this collection (over full + hashed messages) so the `assert_eq!(dmq_head.head(), expected_dmq_mqc_head, ...)` structural check in `enqueue_inbound_downward_messages` passes. [8](#0-7) 
3. Call `Pallet::<T>::enqueue_inbound_downward_messages(expected_head, downward_messages)` and observe that it completes without panicking, even though separately calling `check_enough_messages_included_advanced` on the same collection with realistic size parameters (`max_full_messages_size` from `messages_collection_size_limit()`, `first_hashed_msg_max_size` from the relay's `max_downward_message_size`) would panic — demonstrating that the advanced invariant is silently unenforced on the DMP path while it is enforced on the equivalent HRMP path. 	fn enqueue_inbound_downward_messages(
		expected_dmq_mqc_head: relay_chain::Hash,
		downward_messages: AbridgedInboundDownwardMessages,
	) -> Weight {
		downward_messages.check_enough_messages_included_basic("DMQ");

		let mut dmq_head = <LastDmqMqcHead<T>>::get();

		let (messages, hashed_messages) = downward_messages.messages();
		let message_count = messages.len() as u32;
		let weight_used = T::WeightInfo::enqueue_inbound_downward_messages(message_count);
		if let Some(last_msg) = messages.last() {
			Self::deposit_event(Event::DownwardMessagesReceived { count: message_count });

			// Eagerly update the MQC head hash:
			for msg in messages {
				dmq_head.extend_downward(msg);
			}
			<LastDmqMqcHead<T>>::put(&dmq_head);
			Self::deposit_event(Event::DownwardMessagesProcessed {
				weight_used,
				dmq_head: dmq_head.head(),
			});

			let mut last_processed_msg =
				InboundMessageId { sent_at: last_msg.sent_at, reverse_idx: 0 };
			for msg in hashed_messages {
				dmq_head.extend_with_hashed_msg(msg);

				if msg.sent_at == last_processed_msg.sent_at {
					last_processed_msg.reverse_idx += 1;
				}
			}
			LastProcessedDownwardMessage::<T>::put(last_processed_msg);

			T::DmpQueue::handle_messages(downward_messages.bounded_msgs_iter());
		}

		// After hashing each message in the message queue chain submitted by the collator, we
		// should arrive to the MQC head provided by the relay chain.
		//
		// A mismatch means that at least some of the submitted messages were altered, omitted or
		// added improperly.
		assert_eq!(dmq_head.head(), expected_dmq_mqc_head, "DMQ head mismatch");

		ProcessedDownwardMessages::<T>::put(message_count);

		weight_used
	}

	/// Check that the current collection contains at least 1 full message if needed.
	pub fn check_enough_messages_included_basic(&self, collection_name: &str) {
		if self.hashed_messages.is_empty() {
			return;
		}

		// Here we just check that there is at least 1 full message.
		assert!(
			self.full_messages.len() >= 1,
			"[{}] Advancement rule violation: full messages missing",
			collection_name,
		);
	}

	/// Check that the current collection contains as many full messages as possible, taking into
	/// consideration the collection constraints.
	///
	/// The `AbridgedInboundMessagesCollection` is provided to the runtime by a collator.
	/// A malicious collator can provide a collection that contains no full messages or fewer
	/// full messages than possible, leading to censorship.
	pub fn check_enough_messages_included_advanced(
		&self,
		collection_name: &str,
		size_info: AbridgedInboundMessagesSizeInfo,
	) {
		// We should check that the collection contains as many full messages as possible
		// without exceeding the max expected size.
		let AbridgedInboundMessagesSizeInfo { max_full_messages_size, first_hashed_msg_max_size } =
			size_info;

		let mut full_messages_size = 0usize;
		for msg in &self.full_messages {
			full_messages_size = full_messages_size.saturating_add(msg.data().len());
		}

		// The worst case scenario is that were the first message that had to be hashed
		// is a max size message.
		assert!(
			full_messages_size.saturating_add(first_hashed_msg_max_size) > max_full_messages_size,
			"[{}] Advancement rule violation: full messages size smaller than expected. \
			full msgs size: {}, first hashed msg max size: {}, max full msgs size: {}",
			collection_name,
			full_messages_size,
			first_hashed_msg_max_size,
			max_full_messages_size
		);
	}
