### Title
Webhook shop/topic/webhook-id attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the shop identity (`shop-domain` header) that the gem hands to the merchant's webhook handler is taken from an unauthenticated header. Any party who can obtain one valid `(body, hmac)` pair for the app (e.g. by installing the app on their own store) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop, and `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic and dispatch it as if it came from the victim.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface used by `HmacValidator`: [1](#0-0) [2](#0-1) 

`to_signable_string` returns `@raw_body` only — none of `shop`, `topic`, `webhook_id`, or `api_version` (all read from HTTP headers, see `shopify_header`) are part of the signed material: [3](#0-2) [4](#0-3) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the HMAC: [5](#0-4) 

`Registry.process` gates on this HMAC check and then unconditionally forwards `request.shop` — the unauthenticated header value — to the app's webhook handler: [6](#0-5) 

The gem's own documentation instructs integrators to trust exactly this behavior: it states that `Registry.process` "will verify the request did indeed come from Shopify" and that the resulting `data.shop` is "The shop domain of the webhook," to be used directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [7](#0-6) [8](#0-7) 

The broken identity binding is: `shop_that_the_HMAC_actually_authenticates` (nothing — HMAC only authenticates the body) is treated as equal to `shop_the_handler_acts_on` (`request.shop`, an arbitrary attacker-supplied header). Since a webhook app's `client_secret`/HMAC key is shared across all shops that install the app (it is not per-shop), any legitimate, unprivileged merchant who installs the app can:
1. Receive one genuine webhook for their own shop (body `B`, valid HMAC `H` computed by Shopify with the app's shared secret).
2. Replay `B`/`H` directly to the app's webhook endpoint, but with the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) headers changed to a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks `B` against `H`. `Registry.process` then calls the handler with `shop: "victim-shop.myshopify.com"`.

### Impact Explanation
This breaks the tenant isolation the gem is documented to provide: an unprivileged, single-store merchant of a multi-tenant app can make the app process fabricated webhook events (e.g. `app/uninstalled`, `customers/redact`, `shop/redact`, `orders/create/update`) attributed to a different merchant's shop, without ever obtaining that merchant's access token or the app's `client_secret`. Depending on how the host app's handler acts on `data.shop` (as the docs recommend), this can cause cross-tenant data corruption, spurious uninstall/redaction actions against a victim shop, or injection of forged order/customer data into a victim's records — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's documented pattern of trusting `data.shop`/`data.topic` directly from `Registry.process`. The only prerequisite is that the attacker is themselves a legitimate (even single) installer of the target app — no special privilege, access token, or leaked secret is required, since the HMAC key is shared per-app across all installing shops and the shop attribution is carried in an unsigned header.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or a canonical concatenation with the body) in the HMAC-signed material, or otherwise cryptographically bind the header-derived shop identity to the HMAC. At minimum, update `Utils::VerifiableQuery`/`Request#to_signable_string` so the signable string incorporates the same header values that are later handed to the handler, and document that hosts must not treat `data.shop` as authenticated unless this binding exists.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers (or receives) a normal webhook, e.g. `orders/create`, capturing the raw body `B` and the valid `x-shopify-hmac-sha256` value `H` computed by Shopify using the app's shared `client_secret`.
3. Attacker sends a POST request directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
   - `x-shopify-topic`/`x-shopify-webhook-id` optionally changed
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` and succeeds.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the host app to act as if `victim-shop.myshopify.com` sent this webhook, per [6](#0-5) .

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
