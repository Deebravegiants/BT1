### Title
Webhook HMAC Does Not Cover the Shop/Topic Headers, Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs webhook authenticity using `Utils::HmacValidator.validate`, but the HMAC is computed only over the raw request body [1](#0-0) . The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from unauthenticated HTTP headers and are never included in the signed content [2](#0-1) . `Registry.process` trusts these header-derived fields to route the webhook to a handler and attribute it to a shop [3](#0-2) .

### Finding Description
The equality this code is supposed to enforce is: `hmac_over(body) == hmac_over(body, shop, topic)`. In reality the code only checks `hmac_over(body)`, so `shop` and `topic` are unauthenticated relative to the signature.

Because a Shopify app's webhook signing secret (`api_secret_key`) is a single, app-wide secret shared across every merchant shop that installs the app (it is not per-shop), any legitimate webhook payload signed for one installed shop is a valid HMAC for the *identical body* regardless of which shop or topic header accompanies it. An attacker who controls one installation of the app (a normal, unprivileged merchant who installed the app on their own store) can:
1. Receive a genuine webhook from Shopify for their own shop with a valid `x-shopify-hmac-sha256` value for some JSON body.
2. Replay that exact HTTP body with the same, still-valid HMAC to the app's webhook endpoint, but with the `x-shopify-shop-domain` header changed to a victim shop's domain (and/or the `x-shopify-topic` header changed to a different registered topic).
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks the body [4](#0-3) , and `Registry.process` dispatches the forged `shop` and `body` to the registered handler as if it came from the victim [5](#0-4) .

This is the same bug class as the report: an instruction (here, `Registry.process`) trusts a field (`shop`, `topic`) that is acted upon but not bound by the same cryptographic check that gates trust (the HMAC).

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce: `WebhookMetadata.shop` [6](#0-5)  can be forged to any shop domain string while still passing HMAC validation, letting one merchant's installation inject fabricated webhook events (e.g., orders/customers/app-uninstalled data) attributed to a different, victim shop. Depending on how the host application's handler uses `WebhookMetadata.shop` (e.g., to look up/update per-shop records), this enables cross-tenant data corruption or spoofed lifecycle events (such as a forged `app/uninstalled` for another shop), which falls under "cross-tenant access."

### Likelihood Explanation
Requires only an unprivileged attacker who can install the app on their own store (no special access) and can send arbitrary HTTP POSTs to the app's public webhook endpoint. No secrets need to be stolen — the attacker simply keeps a genuine signed body/HMAC pair from their own store's webhook traffic and replays it with different headers.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the signed content checked by `to_signable_string`, or otherwise cryptographically bind them (e.g., verify `shop` against a shop known to have installed the app for that specific webhook subscription rather than trusting the header verbatim).

### Proof of Concept
1. App is installed on `attacker.myshopify.com` and receives a real webhook, e.g. topic `products/update`, with body `{"id":1}` and a valid `x-shopify-hmac-sha256` header computed by Shopify using the app's shared secret.
2. Attacker resends the exact same body and HMAC to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com` and/or `x-shopify-topic: app/uninstalled`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [7](#0-6) ; `HmacValidator.validate` succeeds because only the body is checked [8](#0-7) .
4. `Registry.process` invokes the registered handler with `shop: "victim.myshopify.com"` and the forged topic, even though this request never originated from Shopify for that shop [9](#0-8) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
