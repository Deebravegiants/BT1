### Title
Excess input-token balance left in `ExternalActionSwap`/`LifiExternalAction` after a swap is permanently unrecoverable - (File: contracts/external-actions/swaps/ExternalActionSwap.sol, contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`ExternalActionSwap.swap()` pulls the full `inputAmount` from `Hinkal` and hands control to `callRouter()`, which lets the LI.FI router pull whatever amount is encoded in `externalActionMetadata` via `approveUnlimited` + a raw `router.call`. The function only measures and refunds the **output**-token balance delta; it never measures or refunds any **input**-token balance left over in the contract after the call. Any residual input token therefore stays trapped in the external-action contract forever, with no code path anywhere in the repo to withdraw it back into a UTXO.

### Finding Description
`swap()` computes `inputAmount` from `deltaAmounts[0]` (the exact amount debited from the user's shielded balance and transferred from `Hinkal` to the swap contract) [1](#0-0) , then calls `callRouter(inputToken, inputAmount, outputToken, externalActionMetadata)` [2](#0-1) .

`LifiExternalAction.callRouter()` only tracks the **output** token balance before/after the router call; for the ERC20 branch it grants the router unlimited allowance and performs a raw low-level call using externally supplied `externalActionMetadata`, without ever checking how much of `inputToken` the router actually consumed: [3](#0-2) 

Back in `swap()`, the only UTXO created is for `outputToken`, sized as `swappedAmount - totalFee`: [4](#0-3) . There is no `balanceBefore`/`balanceAfter` check on `inputToken`, so if the router (per the caller-supplied `externalActionMetadata`) pulls less than the full `inputAmount` that was transferred in — which is entirely plausible for a generic aggregator route where the encoded call and the assumed `inputAmount` diverge, or where dust/rounding is left over — that residual balance simply remains on the `ExternalActionSwap`/`LifiExternalAction` contract.

Because `Hinkal.transact()`'s balance equation only checks the balance change of the `Hinkal` contract itself against `circomData.amountChanges[i] + utxoAmount` [5](#0-4) , this equation is satisfied the moment `Hinkal` sends the full `inputAmount` out — it has no visibility into what happens to that money afterward inside the external action. The leftover input token is a value that was "moved by Hinkal … but not counted in the balance equation" on the way back: it is neither swept into the output UTXO, nor refunded as an input-token UTXO, nor recoverable by any subsequent Hinkal transaction, since `ExternalActionBaseUpgradeable`/`ExternalActionBaseV2` expose no sweep, rescue, or generic withdraw function that could reclaim stray token balances and re-mint them as a shielded UTXO.

This is the direct analog of the BakerFi finding: post-swap leftovers get parked in a place from which the protocol's own logic has no path to pull them back out.

### Impact Explanation
Any input-token dust or partial-consumption leftover from a swap becomes permanently stuck in the `ExternalActionSwap`/`LifiExternalAction` contract. This is a permanent freezing of user funds (the depositor already had that exact amount debited from their shielded balance via `circomData.amountChanges`/`inputNullifiers`, yet receives no corresponding value back), matching the High/Critical impact category "permanent freezing of user funds."

### Likelihood Explanation
Likelihood depends on how `externalActionMetadata` is constructed by the relayer/off-chain LI.FI integration relative to the `inputAmount` actually transferred to the contract; whenever they diverge (dust, rounding, partial fill route, or a route that intentionally consumes less than the full allowance), funds are stranded. The contract code itself provides no safety net regardless of cause, since the input-token balance is never checked or refunded.

### Recommendation
Track `inputToken` balance before/after the router call (the same way `outputToken` is tracked), refund any un-consumed `inputToken` back to the user (or add it to a UTXO for that token), or alternatively use an exact-amount, allowance-scoped call pattern (i.e., after the swap, revoke or check remaining allowance and reconcile against the actual balance decrease) so that `amountToSendToHinkal`-style handling exists for the input token exactly as it does for the output token.

### Proof of Concept
1. A user submits a shielded swap transaction of `inputAmount = 1000` of `tokenA` for `tokenB` via `Hinkal.transact()` → `_externalTransact()` → `LifiExternalAction.runAction()` → `swap()`.
2. `Hinkal` transfers the full `1000 tokenA` to `LifiExternalAction` [6](#0-5) .
3. `callRouter()` grants unlimited allowance and invokes the LI.FI router with `externalActionMetadata` that, per the encoded route, only pulls `950 tokenA` (e.g., due to a route that was quoted for a slightly smaller amount, or partial-fill route data) [7](#0-6) .
4. `swappedAmount` (measured only on `tokenB`) is computed and sent out as a single output UTXO; the `50 tokenA` remaining on `LifiExternalAction`'s balance is never measured, never refunded, and never re-minted as a UTXO [4](#0-3) .
5. `Hinkal.transact()`'s balance-equation check passes because it only checks `Hinkal`'s own balance delta against `amountChanges`/`utxoAmount`, which is unaffected by what `LifiExternalAction` does with the funds it received [5](#0-4) .
6. The `50 tokenA` remains locked in `LifiExternalAction` indefinitely — there is no function in `ExternalActionBaseUpgradeable`/`ExternalActionBaseV2`/`ExternalActionSwap` to reclaim it.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
