This confirms the vulnerability path: the documented app pattern (`docs/usage/webhooks.md:24-27`) explicitly uses `data.shop` to route work (`shop_domain: data.shop`), trusting it as the tenant identifier, while the HMAC computed by `Utils::HmacValidator.validate` only signs `request.to_signable_string`, which returns `@raw_body` alone.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is read separately and passed unauthenticated into the webhook handler.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` to compute the HMAC-signed message: [1](#0-0) [2](#0-1) 

`to_signable_string` returns `@raw_body` exclusively — the `shop` field (`shopify-shop-domain` header) is never included in the signed bytes: [3](#0-2) 

The binding that should hold is: `shop_header == shop_bound_by_hmac`. In this implementation, `shop_header` is read straight from an attacker-controllable HTTP header while the HMAC only authenticates `@raw_body`, so `shop_bound_by_hmac` is undefined for the `shop` field — the equality never gets checked at all.

Because a single app-level `api_secret_key` is shared across every installed shop (it is not shop-specific), any tenant that has legitimately received one authentic webhook (valid body + valid HMAC) can replay that exact body/HMAC pair while substituting the `shopify-shop-domain` header for a different, victim shop domain. `HmacValidator.validate` will still pass because it only recomputes the signature over the untouched raw body.

### Impact Explanation
`Registry.process` passes the unauthenticated `request.shop` straight into `WebhookMetadata.new(... shop: request.shop ...)`, which is delivered to the app's handler as `data.shop`: [1](#0-0) 

The gem's own documented integration pattern uses `data.shop` as the tenant key to dispatch/attribute work (e.g., `shop_domain: data.shop`): [4](#0-3) 

Since `shop` is not bound by the HMAC, an attacker who obtains one legitimate webhook delivery to their own shop can relabel it as belonging to any victim `myshopify.com` domain and have it pass signature validation, causing the host application to process attacker-supplied data under a victim tenant's identity — a cross-tenant confusion/integrity issue that meets the Critical bar (cross-tenant access) defined in scope.

### Likelihood Explanation
Requires only: (1) the attacker's own legitimate, installed shop able to receive at least one real webhook from Shopify (trivial — trigger any subscribed event on their own store), and (2) the ability to replay an HTTP POST with a modified header value, which is standard unprivileged internet-facing capability. No access token, `client_secret`, or privileged account is needed — only interception/replay of the attacker's own already-received webhook body+signature pair.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header value in the HMAC-signed payload verification, or otherwise cryptographically bind the shop domain claimed in the request to the signed body (e.g., verify against a shop-specific secret, or require the shop domain to be echoed inside the signed body/metadata rather than trusted from an unsigned header).

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` is installed and receives a genuine webhook: body `B`, header `shopify-hmac-sha256: HMAC(secret, B)`, `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the same request to the app's webhook endpoint but changes only `shopify-shop-domain` to `victim.myshopify.com`, keeping `B` and the HMAC header unchanged.
3. `ShopifyAPI::Webhooks::Request.new` parses the modified headers; `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` from `to_signable_string` (`@raw_body`, unchanged) and it matches, so validation passes.
4. `Registry.process` invokes the app handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the host app (per the documented pattern) enqueues/attributes work to `victim.myshopify.com` using attacker-controlled body content.
