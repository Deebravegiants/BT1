This is a solid finding. I traced the object ownership model in `aptos_framework::object` and found that the core transfer primitives never validate that an object cannot be transferred to itself, which permanently bricks the ownership chain and any value the object holds.

### Title
Self-referential object transfer (`to == object`) permanently bricks object custody with no recovery path - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::transfer`, `object::transfer_call`, `object::transfer_raw`, and `object::transfer_to_object` all route through `transfer_raw_inner`, which sets `ObjectCore.owner = to` with no check that `to` differs from the object's own address. If an object is ever transferred to itself, the object's ownership pointer becomes a self-loop, and the ungated-transfer authorization check (`verify_ungated_and_descendant`) can never resolve again — every future transfer attempt aborts. Any fungible asset, token, or resource held by that object is then permanently locked with no recovery mechanism (short of a `TransferRef`/`LinearTransferRef` obtained *before* the self-loop was created).

### Finding Description
`ObjectCore.owner` is the sole source of truth for who controls an object [1](#0-0) .

Transfers are performed by `transfer_raw`, which authorizes the caller via `verify_ungated_and_descendant` and then unconditionally writes the new owner in `transfer_raw_inner`, with no equality check between `object` and `to`: [2](#0-1) 

This is reachable through the public entry points `transfer`, `transfer_call`, and `transfer_to_object` [3](#0-2) . In particular, `transfer_to_object<O, T>(owner, object, to)` simply forwards to `transfer(owner, object, to.inner)` — if a caller supplies the same object for both `object` and `to`, `to.inner == object.inner`, producing a direct self-transfer.

The authorization check for any future transfer is `verify_ungated_and_descendant`, which walks the ownership chain starting at the object being moved, until it reaches the calling `owner`: [4](#0-3) 

Once `ObjectCore.owner == object_address` (self-owned), `current_address` is reassigned to itself on every loop iteration (`current_address = object.owner`, where `object.owner` is the object's own address). Since `owner != current_address` for any normal signer address, the `while` loop never terminates naturally — it iterates until `count == MAXIMUM_OBJECT_NESTING` (8) and then aborts with `EMAXIMUM_NESTING`. This means **every subsequent call** to `transfer`, `transfer_call`, `transfer_raw`, or `transfer_to_object` on that object will abort, permanently, for every possible caller.

The only bypass is `transfer_with_ref`, which uses a previously-generated `LinearTransferRef` and checks against the owner captured *at ref-generation time* rather than walking the chain [5](#0-4) . If no such `TransferRef` was generated and externally retained before the self-transfer, there is no recovery path (unlike `burn`/`unburn`, which explicitly preserves `original_owner` in a `TombStone` for reclaiming — self-ownership has no analogous recovery struct).

### Impact Explanation
Any object — including one wrapping a `FungibleStore` (holding APT or other fungible assets), a digital asset/token, or arbitrary application resources — can be irrecoverably locked by a single transfer transaction that sets its own address as the destination. This satisfies the custody-impact gate's "Permanent lock or non-recoverable loss of object-held ... value": once locked, the object's owner field can never be corrected back through the standard transfer API, and neither the true owner nor the protocol can move, sell, or reclaim the underlying value. This is especially dangerous for any downstream contract (marketplaces, vaults, lending positions, NFT escrows) that forwards a caller-/counterparty-supplied `to` address into `object::transfer`/`transfer_to_object` without validating it isn't the object's own address — a very common integration pattern — turning this into a griefing vector against value that belongs to a third party (e.g., an escrowed buyer/seller position), not just the caller's own assets.

### Likelihood Explanation
The root cause requires no privilege beyond being the current (rightful) owner of an object — no admin, governance, or key compromise is needed. Triggering it is a single, simple transaction (`object::transfer_to_object(owner, obj, obj)` or `object::transfer(owner, obj, object::object_address(&obj))`). The bug can be hit accidentally by any integrator that plumbs a user-controlled recipient address into the object transfer primitives without an explicit `to != object_address` guard, making it plausible as unintentional self-DoS as well as intentional griefing.

### Recommendation
Add an explicit check in `transfer_raw` (and thus covering `transfer`, `transfer_call`, `transfer_to_object`) that aborts if `to == object`, e.g.:
```move
assert!(to != object, error::invalid_argument(ESELF_TRANSFER_NOT_ALLOWED));
```
This should be enforced at the lowest-level primitive (`transfer_raw`) so all higher-level entry points inherit the protection, consistent with how `verify_ungated_and_descendant` already guards against deeper cyclic nesting via `MAXIMUM_OBJECT_NESTING`.

### Proof of Concept
```move
#[test(creator = @0x123)]
fun test_self_transfer_bricks_object(creator: &signer) {
    use aptos_framework::object;

    let constructor_ref = object::create_object(signer::address_of(creator));
    let obj = object::object_from_constructor_ref<object::ObjectCore>(&constructor_ref);
    let obj_addr = object::object_address(&obj);

    // Owner "transfers" the object to itself — no check prevents this.
    object::transfer(creator, obj, obj_addr);

    // ObjectCore.owner is now obj_addr itself.
    assert!(object::owner(obj) == obj_addr, 0);

    // Any future transfer by the true owner now aborts permanently:
    // verify_ungated_and_descendant loops on the self-referential owner
    // until MAXIMUM_OBJECT_NESTING is hit, then aborts EMAXIMUM_NESTING.
    // The object (and any FungibleStore/token resources moved into it)
    // can never be transferred out again via the standard API.
}
```

```text
        let object_core = borrow_global_mut<ObjectCore>(object);
        if (object_core.owner != to) {
            event::emit(
                Transfer {
                    object,
                    from: object_core.owner,
                    to,
                },
            );
            object_core.owner = to;
        };
    }
```

```text
    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }
```
