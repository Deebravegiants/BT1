## Finding

### Title
Unbounded `object::root_owner()` traversal permanently locks code-object upgrade and lazy self-init once an ownership cycle exists - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
The external report's custody invariant is: *a control-authority getter must correctly reflect current ownership state, or protected functionality silently becomes inaccessible*. In Aptos's object model, the equivalent authority getter is `object::root_owner()`, which the new lazy-module-initialization feature (`init.move` / `code::publish_package`) relies on to gate self-initialization and to attribute code-object ownership on every (re)publish. Unlike every other ownership-traversal function in the same module, `root_owner()` has no cycle/depth bound, so an ownership cycle among objects turns it into an unbounded loop that always exhausts gas, permanently bricking `code::publish_package` and `init::internal_maybe_initialize` for any code object caught in (or downstream of) the cycle.

### Finding Description
`object::owns()` and `object::verify_ungated_and_descendant()` both walk the ownership chain but explicitly bound the walk to `MAXIMUM_OBJECT_NESTING` (8) and abort with `EMAXIMUM_NESTING` if exceeded: [1](#0-0) [2](#0-1) 

`root_owner()`, however, has no such bound: [3](#0-2) 

Nothing in the `transfer`/`transfer_raw`/`transfer_with_ref` path prevents an object's `owner` field from being set to one of its own descendants. `transfer_raw_inner` unconditionally overwrites `object_core.owner = to` with no cycle check: [4](#0-3) 

`verify_ungated_and_descendant`, which gates `transfer_raw`, only validates that the *calling signer* is an ancestor of the object *currently* being moved — it says nothing about whether the new destination address is a descendant of that same object. Concretely: a user who owns object `A` can create object `B` with `owner = A` (a legitimate child), and then transfer `A` to `B` (a legitimate operation, since the user is `A`'s current owner). This produces `A → owner → B → owner → A`, a two-node ownership cycle.

`root_owner()` is now load-bearing for asset/code custody via the new `LAZY_MODULE_INITIALIZATION` feature: `code::publish_package` calls `object::address_to_object<ObjectCore>(addr).root_owner()` to record the deploy owner for every module in an object-hosted package, and `init::assert_may_self_initialize` calls the same `root_owner()` to verify the object hasn't changed hands before letting a module mint its own signer: [5](#0-4) [6](#0-5) 

If the code-object address `addr` itself ever becomes part of an ownership cycle (its `owner` chain eventually points back to `addr`), both of these `root_owner()` calls loop forever (`is_object(obj_owner)` is always true) and the enclosing transaction can only end by running out of gas — it never returns a wrong answer, it simply can never complete.

### Impact Explanation
Once a code object's ownership chain contains a cycle:
- `code::publish_package` (and therefore `object_code_deployment::upgrade`) for that object can never succeed again while `LAZY_MODULE_INITIALIZATION` is enabled and `object::is_object(addr)` is true, because the `root_owner()` call inside `publish_package` never returns. This permanently locks the upgrade authority of that code object.
- `init::internal_maybe_initialize`, used by lazily-initializing modules to mint their own signer for `move_to` operations (e.g., binding refs such as `MintRef`/`BurnRef`/`TransferRef` to storage on first call), permanently aborts for that address, since `assert_may_self_initialize` cannot terminate.

Any value or capability whose custody depends on that code object completing an upgrade or a first-time lazy self-init (e.g., a managed-fungible-asset pattern that defers storing `ManagingRefs` until lazy init runs) is non-recoverably stuck, satisfying the "permanent lock or non-recoverable loss of object-held ... value" custody-impact category. It is a liveness/lock bug rather than a theft primitive, and only manifests once the `LAZY_MODULE_INITIALIZATION` feature is enabled and the affected address is object-hosted.

### Likelihood Explanation
Constructing the cycle requires only ordinary, permission-respecting object operations (create a child object, then transfer the parent into it) — no privilege escalation is needed, and `object::create_object`/`transfer` place no restriction against it. The trigger condition (the *specific* code-object address participating in a cycle) requires either a deliberate attack against a target project's object-hosted deployment, or a project inadvertently nesting its deployment object under an object it also assigns as owner elsewhere. Given `LAZY_MODULE_INITIALIZATION` and object-hosted code deployment (`aptos move deploy-object`) are both explicit, documented, increasingly common patterns, the likelihood of this being reachable in a real deployment is non-trivial but requires specific composition; I could not verify from the index whether `root_owner()` is invoked anywhere else in framework code outside `code.move`/`init.move` that would broaden the blast radius, since some file contents may be excluded from the index — a full-repo grep from a Devin session would confirm this.

### Recommendation
Bound `root_owner()`'s traversal the same way `owns()` and `verify_ungated_and_descendant()` are bounded (abort with `EMAXIMUM_NESTING` past `MAXIMUM_OBJECT_NESTING` hops), and/or prevent `transfer`/`transfer_raw_inner` from setting an object's `owner` to one of its own descendants (i.e., reject a transfer destination that is provably an ancestor-of-self in the existing chain, within the same nesting bound already enforced elsewhere).

### Proof of Concept
Cycle construction (pseudocode, using existing public APIs; no privileged signer required):
```move
// user U owns object A
let ref_a = object::create_object(@U);
let a = object::address_from_constructor_ref(&ref_a);

// U creates object B with A as its owner (legitimate: create_object lets you pass any owner)
let ref_b = object::create_object(a);
let b = object::address_from_constructor_ref(&ref_b);

// U (who currently owns A) transfers A to B -- passes verify_ungated_and_descendant
// because U is A's current owner; nothing checks that B is a descendant of A.
object::transfer(&signer_for(@U), object::object_from_constructor_ref<ObjectCore>(&ref_a), b);

// Now: A.owner == B, B.owner == A  -> cycle.
// Any call to object::address_to_object<ObjectCore>(a).root_owner() (or on b)
// loops forever via is_object(obj_owner), consuming gas until the VM aborts.
```
If `a` (or `b`) is later used as a `LAZY_MODULE_INITIALIZATION`-enabled code-object address, `code::publish_package`'s `root_owner()` call at [7](#0-6)  and `init::assert_may_self_initialize`'s call at [8](#0-7)  will never complete, permanently blocking upgrade/self-init for that address. I was not able to execute this against a live harness in this environment; the referenced e2e test file `init_module_api.rs` would be the natural place to add a regression test for this cycle case.

    public fun root_owner<T: key>(self: Object<T>): address {
        let obj_owner = self.owner();
