Audit Report

## Title
Outbound HTTP response cache in the CRE gateway is keyed by `workflowOwner` (not `workflowID`), causing cross-workflow response confusion despite documented workflow-scoped isolation - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The gateway's `responseCache` caches outbound HTTP Action responses using `OutboundHTTPRequest.Hash()`, and both the struct comment and the test suite confirm this hash covers method, URL, headers, body, and `WorkflowOwner` while explicitly excluding `WorkflowID`. The package README claims the opposite ("Cache Key: Generated from workflow ID and request hash", "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage"), so two distinct workflows belonging to the same owner that issue identical outbound HTTP requests with `CacheSettings.Store=true` will share a cache entry.

## Finding Description
`responseCache.Fetch` and `responseCache.Set` key the cache map exclusively by `req.Hash()`: [1](#0-0) [2](#0-1) 

The struct's own comment states the hash covers "method, URL, headers, body, workflowOwner" — no `WorkflowID`: [3](#0-2) 

The test suite explicitly locks in that behavior, asserting `Hash()` is identical regardless of `WorkflowID` but differs by `WorkflowOwner`: [4](#0-3) [5](#0-4) 

The README documents a stronger, contradicting guarantee for the same component: [6](#0-5) 

This is a genuine discrepancy between documentation and implementation. However, `OutboundHTTPRequest` and its `Hash()` method live in the external `github.com/smartcontractkit/chainlink-common/pkg/types/gateway` package, not in this repository, so the actual hash implementation is outside the scope of this repo and cannot be modified here. I was unable to fully trace within this repo how `CacheSettings.Store` and `MaxAgeMs` are populated on the workflow-node side, nor confirm whether workflow authors have any practical way to construct genuinely identical outbound requests across sibling workflows (same owner) that also opt into caching, since that logic largely lives in the workflow SDK/DON node code that produces the `OutboundHTTPRequest`, not in this handler.

## Impact Explanation
If triggered, this would cause one workflow to receive a cached HTTP response that was fetched on behalf of a different workflow under the same owner, contradicting the documented workflow isolation guarantee — this maps to the "cross-user response confusion" impact category. The severity is bounded: it requires (a) the requests to be byte-identical in method/URL/headers/body, (b) `CacheSettings.Store=true` and non-zero `MaxAgeMs`, and (c) both workflows to share the same `WorkflowOwner`. It does not bypass any authentication, allowlist, or fund-movement control, and it does not span across owners (the owner boundary itself is enforced).

## Likelihood Explanation
Likelihood is plausible but not high-confidence without further evidence: it depends entirely on ordinary (non-adversarial) usage patterns where a customer runs multiple workflows hitting the same external endpoint with caching enabled, and requires no privileged access to trigger — an unprivileged workflow author under a legitimate owner account could produce this simply by writing two workflows that call the same URL with `Store: true`. The test suite in this repo directly documents and asserts this behavior as-is (`response_cache_test.go`), confirming it is current, deterministic, shipped behavior rather than speculative.

## Recommendation
Modify `OutboundHTTPRequest.Hash()` (in the `chainlink-common` package that defines it) to include `WorkflowID` in the hash input so cache entries cannot be shared across distinct workflows, aligning the implementation with the documented "Workflow Isolation" contract. If per-owner sharing is an intentional design tradeoff (e.g., to reduce duplicate calls to a shared upstream endpoint across an owner's own workflows), then the README claim "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" should be corrected to reflect owner-level (not workflow-level) sharing, and workflow authors should be warned that `Store=true` responses can be shared with sibling workflows of the same owner.

## Proof of Concept
1. Workflow A (`WorkflowID = wf-A`, `WorkflowOwner = 0xOwner1`) issues `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings: {Store: true, MaxAgeMs: 600000}}`; the gateway calls `responseCache.Fetch`, misses, fetches externally, and stores under `req.Hash()` (independent of `wf-A`).
2. Workflow B (`WorkflowID = wf-B`, same `WorkflowOwner = 0xOwner1`) issues an identical request shortly after with `Store: true`/non-zero `MaxAgeMs`.
3. Per `TestRequestHash`'s "having different workflowID results in same Hash" assertion (`response_cache_test.go:139-149`), `hash1 == hash2`, so `responseCache.Fetch` returns Workflow A's cached response to Workflow B without a new external call.

A Go unit test extending `response_cache_test.go` that calls `Fetch` twice with two `OutboundHTTPRequest` values differing only in `WorkflowID` (same owner), with a `fetchFn` that returns different responses/increments a call counter on each invocation, would demonstrate that the second call returns the first workflow's cached response and the `fetchFn` is invoked only once — directly proving the cross-workflow cache-sharing behavior asserted in this report.

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
```

```go
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```
