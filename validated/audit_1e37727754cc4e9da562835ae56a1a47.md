### Title
Webhook shop-domain attribution is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` directly from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw JSON body (`to_signable_string` returns `@raw_body`). The header is never part of the signed bytes, so the binding "shop attributed to event" == "shop authenticated by HMAC" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop` is read straight from an unauthenticated header with no cross-check against the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (covering only the body) and then passes `request.shop` — the unauthenticated header value — straight into `WebhookMetadata` for the handler to trust as the event's tenant: [3](#0-2) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the supplied `hmac`; since `to_signable_string` never includes `shop`, `topic`, or `webhook_id`, none of those header-derived fields are protected by the signature: [4](#0-3) 

The gem's own documentation confirms `data.shop` is the trusted "shop domain of the webhook" that handler code is expected to key business logic on (e.g. session lookups, `perform_later(shop_domain: data.shop, ...)`): [5](#0-4) 

This matches the report's bug class analog: "a shop authenticated versus the shop stored/used as a tenant key" and "bytes verified versus bytes parsed" — the bytes cryptographically verified (`@raw_body`) are not the same bytes used to determine which merchant/tenant the event belongs to (the `shop-domain` header).

### Impact Explanation
An attacker who can install the app on their own store (an unprivileged action, no `api_secret_key` or credentials required) will receive genuine, validly-HMAC-signed webhook deliveries for their own shop. Because the `shop-domain` header is outside the signed content, the attacker can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` header. `Registry.process` will still consider the HMAC valid (it never checked the header) and will invoke the handler with `WebhookMetadata#shop` equal to the attacker-chosen victim domain. Any host application that follows the gem's documented pattern of trusting `data.shop` to key session lookup, data deletion (e.g. `shop/redact`, `app/uninstalled`), or other per-tenant side effects would then perform that side effect against the victim merchant instead of the attacker's own store — a cross-tenant access/action.

### Likelihood Explanation
Moderate/High. Exploitation only requires becoming a legitimate (even trial/free) installer of a public app to obtain a valid raw-body/HMAC pair, then crafting an HTTP POST with a forged shop header — no secrets, tokens, or privileged access are needed. The only prerequisite is that the host application follows this gem's documented, expected usage of `data.shop` to determine the affected tenant.

### Recommendation
Include the shop/topic/webhook_id identifying values in the signed payload used for verification, or otherwise cryptographically bind the `shop-domain` header to the signature check (e.g., verify the header value against the shop encoded in a signed claim rather than trusting it as a bare header). Alternatively, document explicitly that the `shop` header is unauthenticated and that consumers must independently verify shop ownership (e.g., against an existing session for that shop) before using `data.shop` for tenant-scoped actions.

### Proof of Concept
1. Attacker installs app on `attacker.myshopify.com`; Shopify sends a legitimate webhook `POST` with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the identical body `B` and identical `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches — validation passes [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing any per-tenant logic keyed on `data.shop` to run against the victim's tenant using attacker-supplied data.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
