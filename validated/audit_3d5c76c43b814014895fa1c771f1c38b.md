### Title
Flash-loanable balance weighting in phantom-bid price aggregation lets an attacker manipulate `LiquidityPool.buyRate`/`sellRate`, which prices real intents - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
`aggregatePhantomBids` weights every phantom bid's quoted price by the bidder's **instantaneous on-chain balance** of the leg's output token, read once per aggregation. Phantom orders are guaranteed non-executable (expired, zero-amount, same-chain) probes, so a "bid" on one carries zero execution risk. Because the weight is a point-in-time balance rather than escrowed or continuously-held capital, an attacker can transiently acquire a large balance (e.g. via a flash loan, treasury shuffle, or CEX withdrawal timed to the read) of the relevant token, submit an extreme-price bid signed by any EIP-7702-delegated `SolverAccount`, get counted as a heavily-weighted quote by `weightedMedian`, and immediately move the balance away — repeating every phantom cycle at effectively no cost. This is structurally the same bug class as the referenced report: a signal that passes the system's formal verification (solver signature + delegation check) but is not economically backed in practice, used to move a published price that real users and downstream logic rely on.

### Finding Description
`isVerifiedSolverBid` only checks that (1) the bid's solver signature recovers over the `userOpHash`, and (2) the sender is EIP-7702-delegated to a configured `SolverAccount`. [1](#0-0) 

Since "anyone can submit a bid to the coprocessor" and phantom orders can never actually be filled (by construction they are expired / zero-output / same-source-dest probes), the only thing standing between a bid and influencing the published price is whether the bidder holds the quoted output token's balance at the moment the aggregation runs: [2](#0-1) 

`weightedMedian` is a **selection**, not a blend — the solver holding over half a leg's weight sets the published price verbatim: [3](#0-2) 

There is no staking, escrow, lock-up, or minimum holding duration tied to that balance — it is a live `getBalance` read at aggregation time, per the flow documentation and the "block-tagged balance reads" change: [4](#0-3) 

The resulting per-leg median is persisted as `PhantomOrderPriceSnapshotV2.medianPrice` and merged by `mergeChainRowsIntoPool`/`weightedRate` into the pool's single `sellRate`/`buyRate`: [5](#0-4) 

Those pool rates are the **default** price source `IntentGateway.quoteIntent` (and its default `indexed_rates` strategy) uses to price real, executable intents: [4](#0-3) 

This mirrors the original report's root cause exactly: a component (`checkIsValidSellOrder` there, `isVerifiedSolverBid`/`weightedMedian` here) is treated as sufficient proof that a quote is genuine liquidity, when in fact the underlying economic backing (approved allowance there, a *held* balance here) can be manufactured cheaply and briefly, purely to move a price index that other parties trust.

### Impact Explanation
Manipulating `LiquidityPool.buyRate`/`sellRate` directly corrupts the price that `quoteIntent` uses to construct real orders, and the pool's `sellDepth`/`buyDepth`/`bidCount` figures exposed via `queryAvailableLiquidity`/`queryBuyAndSellRates` that front-ends and third-party integrators trust for routing and pricing decisions. An attacker can:
1. Push the published rate favorably before real solvers/users act on it, extracting value from counterparties who trade against the skewed price (analogous to the original report's "buy underpriced contracts" attack), or
2. Depress confidence/route liquidity away from a legitimate corridor by publishing a false depth/price, degrading service for genuine users.
Because the weight comes from an unlocked balance snapshot rather than escrowed capital, the attacker never risks the "sunk cost" the original report's author noted was the only deterrent for its own attack — flash-loaned balance has zero holding cost.

### Likelihood Explanation
Phantom orders are generated periodically and deterministically by the runtime, so an attacker can predict exactly which block/window a `PhantomBidWindowExhausted` snapshot will read balances at, and time a flash loan or temporary balance acquisition to land precisely there. Submitting a bid requires only a `SolverAccount`-delegated EOA (obtainable by anyone via EIP-7702) and a signed `PackedUserOperation` — no special privilege, whitelisting, or governance action is needed, matching the "unprivileged... bandwidth purchaser/intent solver" reachability bar.

### Recommendation
- Weight bids by capital that is actually locked/escrowed for the bid's lifetime (e.g., require the quoted balance to be bonded/staked for a minimum window spanning the bid window plus a buffer), not by an instantaneous balance read.
- Require a minimum holding duration (e.g., balance held over N prior blocks) before counting a solver's inventory toward a leg's weight, to defeat single-block flash-loan/temporary-funding manipulation.
- Consider capping any single solver's influence on `weightedMedian` (a "no solver may exceed X% of total weight") independent of raw balance, and/or requiring multiple independent solvers to corroborate a leg before it is priced.
- Add anomaly detection (already partially present via `warnOnDivergentSample`) that flags/pauses `sellRate`/`buyRate` updates when a snapshot's dominant bidder's weight materializes and disappears within one aggregation cycle.

### Proof of Concept
1. Attacker deploys/uses an EOA delegated (EIP-7702) to the chain's `SolverAccount`.
2. Attacker predicts the block at which the next `PhantomBidWindowExhausted` snapshot will be taken for a target chain/leg (deterministic per the pallet's phantom generation interval).
3. Immediately before that block, attacker flash-loans (or otherwise transiently acquires) a large balance of the leg's output token.
4. Attacker signs and submits a `PackedUserOperation` bid quoting an extreme price for the phantom order (no capital ever changes hands since the order is non-executable), satisfying `isVerifiedSolverBid`.
5. `aggregatePhantomBids`'s `getBalance` read at the snapshot block sees the large transient balance, `weightedMedian` selects the attacker's extreme price as `medianPrice`.
6. Attacker repays/moves the flash-loaned balance immediately after.
7. `updateLiquidityPools` folds the manipulated snapshot into `LiquidityPool.sellRate`/`buyRate`.
8. `IntentGateway.quoteIntent`'s default `indexed_rates` strategy now prices real user intents off the manipulated rate until enough honest samples/age out the poisoned one.

Note: I was unable to fully verify within available context whether any minimum sample count, outlier rejection, or staleness window (beyond `MAX_SAMPLE_AGE_BLOCKS`) exists that might partially dampen a single manipulated snapshot's effect on the merged pool rate; the merge logic (`mergeChainRowsIntoPool`) does include a divergence warning (`warnOnDivergentSample`) but explicitly still merges divergent samples rather than rejecting them, per the code cited above.

// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

function mergeChainRowsIntoPool(pool: LiquidityPool, rows: PoolChainLiquidity[], referenceBlock: bigint): void {
	for (const direction of [SELL, BUY]) {
		const directionRows = rows.filter((row) => row.direction === direction)
		if (directionRows.length === 0) continue

		// Blocks are processed in order, so the difference is non-negative in practice; a row
		// from a "future" block would simply count as fresh, which is the right reading anyway.
		const fresh = directionRows.filter((row) => referenceBlock - row.lastUpdatedBlock <= MAX_SAMPLE_AGE_BLOCKS)
		const merged = fresh.length > 0 ? fresh : directionRows

		warnOnDivergentSample(pool.id, direction, merged)

		const depth = merged.reduce((acc, row) => acc + row.depth, 0n)
		const rate = weightedRate(merged)
		const bidCount = merged.reduce((acc, row) => acc + row.bidCount, 0)

		if (direction === SELL) {
			pool.sellRate = rate
			pool.sellDepth = depth
			pool.sellBidCount = bidCount
		} else {
			pool.buyRate = rate
			pool.buyDepth = depth
			pool.buyBidCount = bidCount
		}
	}
}
