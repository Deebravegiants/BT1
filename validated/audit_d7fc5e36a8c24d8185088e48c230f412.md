### Title
`validateBchAddress` legacy branch skips base58Check checksum verification, accepting corrupted BCH addresses that `Chains.Bitcoin` would reject - (File: packages/intents-sdk/src/lib/validateAddress.ts)

### Summary
`validateBchAddress` matches legacy `1...`/`3...` addresses with a pure regex and never runs the double-SHA256 checksum check that `validateBtcBase58Address` performs for the same string shape when the chain is `Chains.Bitcoin`. This creates a real divergence: an identical checksum-broken legacy address string returns `false` for `Chains.Bitcoin` but `true` for `Chains.BitcoinCash`.

### Finding Description
The broken equality: `validateAddress(addr, Chains.Bitcoin) === validateAddress(addr, Chains.BitcoinCash)` for any string matching the base58 legacy P2PKH/P2SH shape is claimed/assumed to hold (both should require valid base58Check), but it does not.

`validateBtcBase58Address` [1](#0-0)  decodes with `base58.decode`, checks length, version byte, and verifies the 4-byte checksum against `sha256(sha256(payload))`.

`validateBchAddress`'s legacy branch, by contrast, only runs a regex against the character shape and returns `true` immediately with no base58 decode and no checksum verification at all: [2](#0-1) .

Root cause: the regex `/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/` (and the `3...` variant) only constrains the base58 alphabet and rough length, it says nothing about whether the last 4 bytes of the decoded payload are a valid checksum over the preceding 21 bytes. A single mutated character in an otherwise well-formed legacy address will still satisfy the regex (base58 alphabet is large and length range is loose) while breaking the checksum, exactly as `validateBtcBase58Address` is designed to catch.

Exploit flow: the attacker (an ordinary withdrawing user) supplies `destinationAddress = <BCH legacy address with one mutated character>` for a `BitcoinCash` asset withdrawal. `PoaBridge.validateWithdrawal` calls `validateAddress(args.destinationAddress, assetInfo.blockchain)` [3](#0-2) , which resolves to `validateBchAddress` and returns `true` despite the checksum being invalid. Nothing downstream in `validateWithdrawal` re-checks the checksum (the subsequent checks only look at min amount, XRPL-specific flags, and address-equals-token-address). `createWithdrawalIntents` then calls `createWithdrawIntentPrimitive` with the unchanged `destinationAddress` [4](#0-3) , which — per the question's description of `createWithdrawIntentPrimitive` (not fully re-verified here beyond confirming the address flows through unmodified) — encodes it verbatim into the withdrawal memo/intent that gets signed.

Why existing guards don't help: `validateWithdrawal`'s only address-format guard is the single `validateAddress` call; there is no separate checksum-specific check for BCH legacy addresses, and `compareAddresses` is only used to compare against the token's own origin address, not to validate checksum correctness.

### Impact Explanation
A withdrawal intent gets signed and submitted by the PoA bridge with a `destinationAddress` that fails base58Check and therefore does not decode to any valid hash160 on the Bitcoin Cash network. Since BCH nodes/wallets require checksum-valid legacy addresses, funds sent to such a string are not deliverable to any real destination and are lost with no recovery path — this matches the Critical category ("funds delivered to a wrong address/chain/contract with no recovery"). This is repeatable for any BCH withdrawal where the caller passes a legacy-format address; each call independently produces a stuck/misrouted withdrawal.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: BitcoinCash asset withdrawal, `destinationAddress` in legacy `1...`/`3...` form with one mutated character (a typo, not a deliberately crafted attack against someone else — this affects the caller's own funds, since PoA Bridge withdrawals send to the address the signer specifies). No special RPC/relayer/contract state is needed; the flaw is purely inside `validateAddress`. This is a self-harm/data-integrity bug for the withdrawing user (or an integrator who forwards a bad address on the user's behalf) rather than something one user could exploit against another; it's highly likely to occur via ordinary user error since there's no checksum enforcement at all to catch it.

### Recommendation
In `validateBchAddress`, for the legacy branch, decode with `base58.decode`, verify length is 25 bytes, verify the version byte is `0x00` (P2PKH) or `0x05` (P2SH), and verify the double-SHA256 checksum over the first 21 bytes — mirroring `validateBtcBase58Address` exactly (or simply delegate legacy validation to that same function) — instead of relying on a shape-only regex.

    expect(validateAddress(corrupted, Chains.Bitcoin)).toBe(false); // checksum enforced

  });

function validateBtcBase58Address(address: string): boolean {
	const decoded: Uint8Array = base58.decode(address);

	// version (1) + hash160 (20) + checksum (4) = 25 bytes
	if (decoded.length !== 25) return false;

	const version = decoded[0];
	// 0x00 = P2PKH mainnet, 0x05 = P2SH mainnet
	if (version !== 0x00 && version !== 0x05) return false;

	const payload = decoded.subarray(0, 21);
	const checksum = decoded.subarray(21, 25);
	const expectedChecksum = sha256(sha256(payload)).subarray(0, 4);

	for (let i = 0; i < 4; i++) {
		if (checksum[i] !== expectedChecksum[i]) return false;
	}
	return true;
}

export function validateBchAddress(address: string): boolean {
	// Legacy address format (same as Bitcoin)
	if (
		/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(address) ||
		/^3[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(address)
	) {
		return true;
	}

	// CashAddr format
	return validateBchCashAddr(address);
}
