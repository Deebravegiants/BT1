## Analog Found

### Title
Pre-seeded HyperSwap V2 pair lets an attacker set the graduation LP price away from the curve close price - ([File: packages/contracts/src/Bonding.sol])

### Summary
The Sherlock report's root cause is that a critical price-dependent decision (mint/redeem threshold checks) is made from an unprotected, single-snapshot "price" rather than a value that resists last-block manipulation. alt.fun has a structurally identical weak point in its graduation LP-seeding step: `_prepareGraduationLiquidity` computes an exact `tokensForLP`/`ltFromPair` ratio meant to match the closing curve price 1:1, but the actual on-chain price that ends up live in the HyperSwap V2 pool depends on whatever reserve ratio already exists in that pair at the moment `addLiquidity` executes — and pair creation on a Uniswap-V2-style factory is permissionless.

### Finding Description
`Bonding._prepareGraduationLiquidity` reads the pair's stored reserves, drains the real LT raised (`ltFromPair`), and derives `tokensForLP = (ltFromPair * tokenReserve) / assetReserve` so that the new HyperSwap V2 pool is supposed to open at **exactly** the curve's last marginal price: [1](#0-0) 

This is documented as the "zero price gap" design intent — the whole point of the exact ratio computation is to prevent arbitrage bots from immediately extracting value from a mis-priced LP: [2](#0-1) 

The flaw is that this ratio is only meaningful if the HyperSwap V2 TOKEN/LT pair the LP tokens are added into is empty at that moment. Because pair creation on a Uniswap-V2-style DEX factory is permissionless, any unrelated wallet can pre-create the TOKEN/LT pair and directly ERC20-transfer ("donate") a skewed amount of TOKEN and/or LT into it before `Bonding`'s permissionless two-phase graduation (`triggerGraduation` / `finalizeGraduation`) calls `addLiquidity(tokensForLP, ltFromPair, ...)`. Standard Uniswap-V2 router semantics take the *minimum* of the two possible ratios implied by the existing reserves versus the desired amounts — so if the pre-seeded reserves are skewed, the LP opens at the pre-seeder's ratio, not at `ltFromPair / tokensForLP` (the curve's true close price), even though `tokensForLP`/`ltFromPair` were computed correctly by `Bonding`.

This directly parallels the TWAP report's core class: a value that is trusted to represent "the fair price at this moment" (there, a 1-block-old cumulative price; here, an attacker-seedable pool ratio) is used for an economically important, effectively irreversible action (there, mint/redeem threshold gating; here, the one-time LP seed that is locked forever via `LPLock`) without any check that the value hasn't been set up adversarially just before use.

### Impact Explanation
A skewed LP-open price means the graduated pool does not actually open at the curve's close price, breaking Invariant #1 ("Zero price gap") that the protocol explicitly relies on: [3](#0-2) 
Whoever pre-seeded the skewed reserves (or a bot watching for the graduation) can immediately arbitrage the mispriced pool against the true curve-close price, extracting value that should have accrued to the LP (locked permanently in `LPLock`, "no withdraw in v1") and to post-graduation traders. Since the LP tokens are permanently locked and the mis-seeding happens atomically with the one-shot `addLiquidity`/`recordLock` call, the loss is effectively permanent — value is transferred out of the protocol's LP into the pre-seeder's/arbitrageur's pocket the moment the pool goes live.

### Likelihood Explanation
Reachable by any unrelated wallet with no privileges: create the TOKEN/LT pair on the HyperSwap V2 factory ahead of time (a token's paired LT address and eventual token address are knowable/predictable once `Zap.createToken` is called, since `Bonding.launch` deploys the `Token` clone and `Pair` deterministically before the curve trades open), then transfer a small, skewing amount of TOKEN/LT directly into that pre-created pair. Graduation itself is either triggered inline by any ordinary buyer crossing the USD/supply threshold, or permissionlessly via `Bonding.triggerGraduation`/`finalizeGraduation`, so the attacker does not need to control graduation timing precisely — the mis-seeded pair simply sits waiting for the LP seed. This requires no flash loans, no privileged role, and no interaction with BounceTech's LT internals.

### Recommendation
Before calling `addLiquidity`, verify (and if necessary, revert or self-heal) that the target HyperSwap V2 TOKEN/LT pair has zero reserves, or compute `tokensForLP`/`ltFromPair` against the *actual* pre-existing reserves rather than assuming an empty pool; alternatively, have `Bonding`/`Router` create the pair itself atomically inside the graduation transaction (removing the permissionless pre-creation window), and reject donations by sweeping/burning any tokens sitting in the pair before seeding liquidity.

### Proof of Concept
1. Attacker calls the HyperSwap V2 factory's `createPair(token, lt)` for a not-yet-graduated `tokenAddress`/`ltAddress` pair (predictable once `Zap.createToken` deploys the `Token` clone).
2. Attacker transfers a small, deliberately skewed amount of `lt` (or `token`, once mintable/transferable) directly into that pair via plain ERC20 `transfer`.
3. Any ordinary buyer's `Zap.buy` pushes the curve past the graduation threshold; `Bonding`'s dual-trigger logic and the permissionless `triggerGraduation`/`finalizeGraduation` flow proceed, calling `_prepareGraduationLiquidity` (`Bonding.sol:1073-1096`) to compute the "correct" `tokensForLP`/`ltFromPair`, then `addLiquidity(tokensForLP, ltFromPair, ...)` on the pre-seeded, skewed pair.
4. The router honors the existing skewed reserve ratio (standard Uniswap-V2 `addLiquidity` behavior), so the LP opens away from the curve's true close price.
5. Attacker (or any bot) immediately swaps against the newly opened, mispriced pool to extract the difference, at the expense of the locked LP position in `LPLock` and subsequent traders.

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

### Dynamic LP Seeding (zero price gap)

The problem: the reserve asset (LT) has a varying USD price, so the exact number of LP tokens needed to make the DEX pool open at the last curve price is not known ahead of time. Naively seeding the LP with the full 250M reserve would create a large price gap that arbitrage bots would immediately close, transferring value out of the protocol.

Our approach: compute the exact `tokensForLP` at graduation time so the LP opens at **precisely** the last curve price. Burn whatever is left of the 250M reserve.

`_graduate()` performs, in order:

1. Read `(reserve0, reserve1)` from the Pair **before** any state mutation.
2. Burn any unsold real curve tokens from the pair (`unsoldBurned`). This also burns any tokens donated to the pair via direct ERC20 transfer.
3. Recover `virtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()` and compute `ltFromPair = reserve1 - virtualLtReserve` — the real LT raised by the curve, excluding the launch-time virtual seed AND any LT donated to the pair. Drain exactly that amount via `Router.graduate(token, ltFromPair)`. Donated LT remains in the curve pair, reachable only via `Pair.transferAsset` which is gated by `Router`'s `BONDING_ROLE`.
4. Compute `tokensForLP = (ltFromPair × reserve0) / reserve1` — the unique amount that sets the LP price `ltFromPair / tokensForLP` equal to the last curve price `reserve1 / reserve0`. Capped at `lpReserveTotal` as a defensive guard (parabola math proves `tokensForLP ≤ lpReserveTotal` by construction).
5. Burn `lpReserveTotal − tokensForLP` from `Bonding`'s held reserve (`lpBurned`).
6. `addLiquidity(tokensForLP, ltFromPair)` on HyperSwap V2 → LP tokens go to `LPLock`.
