### Title
Missing para lifecycle validation in `on_demand::do_place_order` allows on-demand orders for non-onboarded (`Onboarding`) paras, letting them seize scheduler core-assignment slots - ([File: polkadot/runtime/parachains/src/on_demand/mod.rs])

### Summary
`Pallet::<T>::do_place_order` (and therefore `place_order_allow_death`, `place_order_keep_alive`, `place_order_with_credits`) never checks the target `para_id`'s `ParaLifecycle` state before accepting payment and enqueuing the order. `pop_assignment_for_cores` and the coretime assigner's `pop_assignment_for_ondemand_cores` likewise perform no lifecycle/validity filtering, so an order for a para still in `Onboarding` (or even an unregistered `para_id`) can be popped and handed a pool core-assignment slot that no collator can ever fill with a valid backed candidate.

### Finding Description
`do_place_order` in [1](#0-0)  only validates `spot_price <= max_amount` and that the queue is not full - `ensure!(spot_price.le(&max_amount), ...)` and `ensure!(order_status.queue.len() < ..., Error::<T>::QueueFull)`. There is no `Paras::is_valid_para(para_id)`, `Paras::is_parathread(para_id)`, or `ParaLifecycle` check of any kind, contrary to the documented error list (`InsufficientBalance`, `QueueFull`, `SpotPriceHigherThanMaxAmount` only) at [2](#0-1) . The order is unconditionally pushed via `order_status.queue.try_push(now, para_id)` at [3](#0-2) .

Downstream, `OrderQueue::pop_assignment_for_cores` only checks timing readiness (`ready_at <= now`) and de-duplicates per-call via a `BTreeSet`, with no lifecycle filter: [4](#0-3) . The scheduler's coretime assigner calls this directly through `pop_assignment_for_ondemand_cores` in `AccessMode::pop_assignment_for_ondemand_cores` at [5](#0-4) , which is invoked from `advance_assignments_single_impl` for every `Pool`-typed core at [6](#0-5) . No para-registration/lifecycle validity check exists anywhere in this call chain (`grep` for `is_parathread`/`is_valid_para`/`ParaLifecycle` in `scheduler/assigner_coretime/**` returns nothing).

Because a para in `ParaLifecycle::Onboarding` has no live collator/validator infrastructure and, per the onboarding flow (`schedule_para_initialize`, `apply_actions_queue`), its `Heads`/`CurrentCode` are not yet materialized until the next session boundary (see [7](#0-6)  and [8](#0-7) ), no valid backed candidate can ever be produced for that core-round. The core is nonetheless popped from the pool queue and occupies that assignment slot for the round, ahead of any legitimate parathread orders queued behind it.

### Impact Explanation
An unprivileged signed account can reserve+register a `para_id` (permissionless reservation is a normal registrar flow) and immediately call `place_order_allow_death`/`place_order_with_credits` for it while it is still `Onboarding`. The order is accepted, queued, and later popped by `pop_assignment_for_cores`/`advance_assignments`, consuming one pool core-assignment slot that could otherwise serve a real parathread's order. Because the para cannot produce a valid candidate, that slot's block-space capacity is effectively wasted for that round, and the attacker can repeat this every block/order cycle to keep siphoning slots from the shared on-demand queue - a resource-seizure DoS against the on-demand core assignment mechanism, scoped exactly to what the question describes.

### Likelihood Explanation
Feasible with only normal, permissionless extrinsics: reserve a `para_id`, register it (genesis args with non-empty validation code, which is the only check `schedule_para_initialize` performs — [9](#0-8) ), and call `place_order_allow_death`/`place_order_with_credits` before the next session rotation completes onboarding. This is repeatable every block/order cycle as long as the attacker can pay the current spot price (which floats with traffic and can be low), giving high repeatability at modest cost.

### Recommendation
Add a lifecycle validity check in `do_place_order` before accepting payment/enqueuing, e.g. `ensure!(<paras::Pallet<T>>::is_valid_para(para_id) || is_parathread/is_parachain as appropriate, Error::<T>::InvalidParaId)`, mirroring the check already used in `paras_registrar`'s `make_parachain`/`make_parathread` (`paras::Pallet::<T>::lifecycle(id) == Some(ParaLifecycle::Parathread)` at [10](#0-9) ). As defense in depth, also filter non-stable-lifecycle paras out in `pop_assignment_for_cores`/`advance_assignments` so that stale onboarding paras that somehow got queued (e.g., due to timing races) are dropped rather than scheduled.

### Proof of Concept
Rust unit test in `polkadot/runtime/parachains/src/on_demand/tests.rs`:
1. Register a para via `Paras::schedule_para_initialize` (or the registrar) but do **not** advance to the session where `apply_actions_queue` promotes it — assert `Paras::lifecycle(para_id) == Some(ParaLifecycle::Onboarding)`.
2. Give `alice` sufficient balance/credits and call `OnDemand::place_order_allow_death(RuntimeOrigin::signed(alice), amt, para_id)`.
3. Assert the call currently returns `Ok(())` (proving the missing check) instead of an expected `Error::<Test>::InvalidParaId`/`NotRegistered`.
4. Advance blocks for async-backing readiness and call `OnDemand::pop_assignment_for_cores(block_num, 1)`; assert it currently yields `Some(para_id)` even though the para is still `Onboarding`, demonstrating that a non-live para consumes a pool core-assignment slot.

impl<N> OrderQueue<N> {
	/// Pop `num_cores` from the queue, assuming `now` as the current block number.
	pub fn pop_assignment_for_cores<T: Config>(
		&mut self,
		now: N,
		mut num_cores: u32,
	) -> impl Iterator<Item = ParaId>
	where
		N: Saturating + Ord + One + Copy,
	{
		let mut popped = BTreeSet::new();
		let mut remaining_orders = Vec::with_capacity(self.queue.len());
		for order in mem::take(&mut self.queue) {
			// Order is ready 2 blocks later (asynchronous backing):
			let ready_at = order.ordered_at.saturating_plus_one().saturating_plus_one();
			let is_ready = ready_at <= now;

			if num_cores > 0 && is_ready && popped.insert(order.para_id) {
				num_cores -= 1;
			} else {
				remaining_orders.push(order);
			}
		}
		self.queue = BoundedVec::truncate_from(remaining_orders);
		popped.into_iter()
	}

/// Pop assignments for `now`.
fn advance_assignments_single_impl<T: Config>(
	now: BlockNumberFor<T>,
	core_states: &mut BTreeMap<CoreIndex, CoreDescriptor<BlockNumberFor<T>>>,
	mut mode: AccessMode<T>,
) -> AdvancedAssignments {
	let mut bulk_assignments = Vec::with_capacity(num_coretime_cores::<T>() as _);
	let mut pool_cores = Vec::with_capacity(num_coretime_cores::<T>() as _);
	for (core_idx, core_state) in core_states.iter_mut() {
		ensure_workload::<T>(now, *core_idx, core_state, &mode);

		let Some(work_state) = core_state.current_work.as_mut() else { continue };

		// Wrap around:
		work_state.pos = work_state.pos % work_state.assignments.len() as u16;
		let (a_type, a_state) = &mut work_state
			.assignments
			.get_mut(work_state.pos as usize)
			.expect("We limited pos to the size of the vec one line above. qed");

		// advance for next pop:
		a_state.remaining = a_state.remaining.saturating_sub(work_state.step);
		if a_state.remaining < work_state.step {
			// Assignment exhausted, need to move to the next and credit remaining for
			// next round.
			work_state.pos += 1;
			// Reset to ratio + still remaining "credits":
			a_state.remaining = a_state.remaining.saturating_add(a_state.ratio);
		}
		match *a_type {
			CoreAssignment::Pool => pool_cores.push(*core_idx),
			CoreAssignment::Task(para_id) => bulk_assignments.push((*core_idx, para_id.into())),
			CoreAssignment::Idle => {},
		}
	}

	let pool_assignments = mode.pop_assignment_for_ondemand_cores(now, pool_cores.len() as _);
	let pool_assignments = pool_cores.into_iter().zip(pool_assignments).collect();

	AdvancedAssignments { bulk_assignments, pool_assignments }

	pub(crate) fn schedule_para_initialize(
		id: ParaId,
		mut genesis_data: ParaGenesisArgs,
	) -> DispatchResult {
		// Make sure parachain isn't already in our system and that the onboarding parameters are
		// valid.
		ensure!(Self::can_schedule_para_initialize(&id), Error::<T>::CannotOnboard);
		ensure!(!genesis_data.validation_code.0.is_empty(), Error::<T>::CannotOnboard);
		ParaLifecycles::<T>::insert(&id, ParaLifecycle::Onboarding);

		// HACK: here we are doing something nasty.
		//
		// In order to fix the [soaking issue] we insert the code eagerly here. When the onboarding
		// is finally enacted, we do not need to insert the code anymore. Therefore, there is no
		// reason for the validation code to be copied into the `ParaGenesisArgs`. We also do not
		// want to risk it by copying the validation code needlessly to not risk adding more
		// memory pressure.
		//
		// That said, we also want to preserve `ParaGenesisArgs` as it is, for now. There are two
		// reasons:
		//
		// - Doing it within the context of the PR that introduces this change is undesirable, since
		//   it is already a big change, and that change would require a migration. Moreover, if we
		//   run the new version of the runtime, there will be less things to worry about during the
		//   eventual proper migration.
		//
		// - This data type already is used for generating genesis, and changing it will probably
		//   introduce some unnecessary burden.
		//
		// So instead of going through it right now, we will do something sneaky. Specifically:
		//
		// - Insert the `CurrentCodeHash` now, instead during the onboarding. That would allow to
		//   get rid of hashing of the validation code when onboarding.
		//
		// - Replace `validation_code` with a sentinel value: an empty vector. This should be fine
		//   as long we do not allow registering parachains with empty code. At the moment of
		//   writing this should already be the case.
		//
		// - Empty value is treated as the current code is already inserted during the onboarding.
		//
		// This is only an intermediate solution and should be fixed in foreseeable future.
		//
		// [soaking issue]: https://github.com/paritytech/polkadot/issues/3918
		let validation_code =
			mem::replace(&mut genesis_data.validation_code, ValidationCode(Vec::new()));
		UpcomingParasGenesis::<T>::insert(&id, genesis_data);
		let validation_code_hash = validation_code.hash();
		CurrentCodeHash::<T>::insert(&id, validation_code_hash);

		let cfg = configuration::ActiveConfig::<T>::get();
		Self::kick_off_pvf_check(
			PvfCheckCause::Onboarding(id),
			validation_code_hash,
			validation_code,
			&cfg,
		);

		Ok(())
