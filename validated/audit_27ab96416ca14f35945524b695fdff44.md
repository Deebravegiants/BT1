### Title
Dangling controller account after position-NFT ownership becomes unreadable strands bad debt permanently — debt cleanup and liquidation fail on the owner lookup, leaving leaked spoke usage and unsocializable loss - (File: contracts/controller/src/storage/account.rs)

### Summary
The kernel bug leaks a dentry on an error path: one half of a paired resource (temporary dentry vs. superblock) is dropped while the other half survives, so teardown of the survivor can never complete. XOXNO Lending has the same shape across the position-NFT ↔ controller-account pairing: the controller's `clean_bad_debt`, `force_socialize_bad_debt`, and liquidation paths resolve account ownership by calling `owner_of` on the position NFT, and treat a failed owner lookup as `AccountNotFound`. When the NFT's `Owner(token_id)` entry becomes unreadable (archived persistent TTL, or the documented case where the NFT was burned while controller entries survive) while `AccountMeta`, position maps, and spoke `usage` remain live, the debt position becomes a dangling resource: it cannot be liquidated, cannot be bad-debt-cleaned, and cannot be written down — permanently stranded in spoke usage.

### Finding Description
- `account_owner`/`try_account_owner` resolve ownership exclusively through `nft_try_owner_of_call`; any failure of that call returns `None`, which callers escalate to `GenericError::AccountNotFound` (`storage/account.rs:35-44`).
- Deletion is one-directional: `remove_account_entry` clears `AccountMeta`, `SupplyPositions`, `BorrowPositions`, `Delegates`, and `remove_account_and_burn_nft` burns the NFT, but nothing enforces the reverse — the NFT `Owner` entry can disappear while all controller entries persist (`storage/account.rs:250-256`, `account.rs:159-163`).
- The NFT's own `burn` comment acknowledges the asymmetric lifetime, and `renew`/`owner_of` panic with `NonExistentToken` for missing tokens — which `try_account_owner` maps to `None`, i.e. `AccountNotFound` (`position-nft/contract.rs:88-115`).
- The repo's own test `bad_debt_winddown_resolves_nft_ownership` proves the outcome: after the NFT is burned, `account_exists(id)` is still true (controller state live) yet `try_clean_bad_debt` and `try_force_socialize_bad_debt` both fail with `AccountNotFound` (`tests/test-harness/tests/controller/position_nft_ttl_and_ownership_reads.rs:311-335`). The certora spec separately notes cleanup removes the account entry so its usage stays "stranded" if the account cannot be processed (`certora/controller/spec/spoke_rules.rs:2409-2416`).
- Like the leaked dentry that blocks unmount, the leaked debt position blocks the spoke's teardown accounting: `usage.borrowed_scaled_ray` retains the stranded debt and the pool's supply index can never write it down via `recapitalize`/`clean_bad_debt`.

### Impact Explanation
An account holding debt whose NFT owner entry is unreadable becomes permanently unliquidatable and uncleanable: every keeper path (`liquidate`, `clean_bad_debt`, `force_socialize_bad_debt`) fails closed on `AccountNotFound`, while spoke usage and (until its own TTL lapses) the borrow position continue to count as outstanding debt. This yields permanent freezing of supplier funds via stuck utilization on the spoke and un-socializable bad debt — protocol insolvency rather than a transient DoS. Dentry-leak analog: the surviving half (controller account/usage) references a dropped half (NFT owner) and can never be torn down.

### Likelihood Explanation
Reachability is timing/lifecycle driven, not attacker-cost driven. The NFT `Owner` entry is a persistent key with a finite user TTL; `owner_of` extends it to a shorter window than controller account entries, and nothing on the borrower's side forces renewal (`position-nft/contract.rs:34-46, 97-115`). A borrower who opens a debt position and abandons it (or a compositing contract that renews only its own pointer, not the NFT owner key — the skill docs explicitly warn `account_exists` does not renew NFT state, `skills/xoxno-lending-contracts/positions.md:11-13`) eventually reaches a state where `owner_of` fails while debt and usage persist. A `restore` of the archived entry may rescue the state, but if the account's position maps or the NFT entry lapse asymmetrically the windows diverge; and where the burn-first ordering already occurred (per the test), the state is permanently unrecoverable by design. Unprivileged path: `borrow`/`multiply`/`flash_position` to open debt, then simply never renew — no privilege required.

### Recommendation
Decouple teardown authority from NFT liveness: for bad-debt/insolvency paths (`clean_bad_debt`, `force_socialize_bad_debt`, liquidation of an account whose owner lookup fails), verify `AccountMeta`/position existence instead of NFT ownership, or add a fallback that treats a missing `Owner` entry as terminal and proceeds to wind down debt and clear usage. Alternatively, pin the `Owner(token_id)` TTL to the same renewal performed for `BorrowPositions`/`AccountMeta` inside `renew_user_account` and every owner lookup, so the NFT half can never expire while the controller half lives.

### Proof of Concept
Reproduced by existing test `bad_debt_winddown_resolves_nft_ownership` in `tests/test-harness/tests/controller/position_nft_ttl_and_ownership_reads.rs:314-335`:

```rust
t.supply(ALICE, "USDC", 10_000.0);
t.borrow(ALICE, "ETH", 3.0);
let id = t.account_id(ALICE);
position_nft::PositionNftClient::new(&t.env, &t.position_nft).burn(&token_id);
assert!(t.account_exists(id));                 // controller state still live
// both keeper paths now fail permanently:
assert_contract_error(flatten(t.ctrl_client().try_clean_bad_debt(&keeper, &id)), errors::ACCOUNT_NOT_FOUND);
assert_contract_error(flatten(t.ctrl_client().try_force_socialize_bad_debt(&id)), errors::ACCOUNT_NOT_FOUND);
```

The same end-state is reachable without the privileged `burn` by letting the persistent `Owner(token_id)` TTL archive while debt positions and spoke usage remain: any subsequent `liquidate`/`clean_bad_debt` hits `account_owner → None → AccountNotFound` at `contracts/controller/src/storage/account.rs:41-44`.

Uncertainty note: I confirmed the asymmetric lifetime, the fail-closed owner resolution, and the existing test demonstrating permanently-failing cleanup. I could not verify in remaining iterations whether a permissionless `restore` reliably resurrects every divergence scenario (burn-ordering is unrecoverable regardless; TTL-ordering may be restorable, which would downgrade that variant to temporary freezing — still an accepted impact category).
