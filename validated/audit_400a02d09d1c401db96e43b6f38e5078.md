### Title
Two-Phase Graduation Permanently Freezes a Token When Cached `ltFromPair`/`tokensForLP` Round Below UniswapV2's `MINIMUM_LIQUIDITY` - ([File: packages/contracts/src/Bonding.sol])

### Summary
The FreeRDP bug class is: a piece of state (`h264->width`/`height`) is updated and *committed* on the assumption that a subsequent allocation step will succeed; when that later step actually fails, the already-committed state is inflated/inconsistent and cannot be walked back, corrupting later operations. `Bonding`'s two-phase graduation has the identical shape: Phase 1 (`_enterGraduating` → `_prepareGraduationLiquidity`) permanently commits `lifecycle = Graduating` and caches `pendingGraduation.{tokensForLP, ltFromPair}` on the assumption that Phase 2 (`finalizeGraduation` → `_seedUniswapV2Direct` → `_seedDirectMint`) will successfully mint LP against those exact cached numbers. If the cached numbers are small enough that UniswapV2's first-mint liquidity formula underflows/rounds to zero, `pair.mint()` deterministically reverts forever, and the already-committed Phase-1 state (frozen trading, drained curve LT, cached amounts) can never be un-done.

### Finding Description
`_enterGraduating` flips lifecycle and drains/caches unconditionally: [1](#0-0) 

`_prepareGraduationLiquidity` computes `ltFromPair` from `assetReserve - virtualLtReserve` and derives `tokensForLP` proportionally, then calls `router.graduate` to irreversibly move the raised LT out of the curve pair: [2](#0-1) 

These cached values are documented as immutable for the life of the `Graduating` state — no recompute, no re-pricing, no rollback path: [3](#0-2) 

Phase 2's empty-pair path (`_seedDirectMint`, described as "~99% of graduations") transfers exactly the cached amounts and calls `pair.mint(lpLock)` directly, with no guard for a zero/near-zero liquidity mint: [4](#0-3) 

Standard UniswapV2 `mint()` on the first deposit (`totalSupply()==0`) computes `liquidity = sqrt(amount0*amount1) - MINIMUM_LIQUIDITY` and reverts with `INSUFFICIENT_LIQUIDITY_MINTED` if that underflows/equals zero. The codebase's own brick-resistance design explicitly anticipates and handles the analogous "swap rounds to zero" failure mode inside `_pairRebalance`/`_noFeeSwapInput` by falling back to `_seedDirectMint`: [5](#0-4) 

but there is no equivalent fallback for the case where `_seedDirectMint` itself is the terminal path and its `pair.mint()` call is the one that reverts — the brick-resistance natspec asserts `_seedUniswapV2Direct` "MUST never revert," yet the guarantee is not actually enforced against a tiny cached `(tokensForLP, ltFromPair)` pair.

The trigger for a tiny cached pair is the dual-trigger USD condition, which multiplies the *raw* `ltFromPair` by the live, externally-controlled `exchangeRate()` of the rebasing LT to reach a fixed USD threshold (per `AGENTS.md`'s documented dual trigger). Because `exchangeRate()` is read live from an external rebasing asset, a spike in `exchangeRate()` shrinks the raw LT amount needed to cross the fixed USD threshold proportionally — the higher the rate, the smaller `ltFromPair` (in LT wei) needs to be for `ltFromPair * exchangeRate() >= graduationThresholdUsd` to hold, which is exactly the value that gets permanently frozen into `pendingGraduation` and fed into `pair.mint()`.

### Impact Explanation
Once `lifecycle` flips to `Graduating`, curve trading is frozen (buy/sell only proceed under `Lifecycle.Curve`) and the curve's real LT has already been moved out via `router.graduate` inside Phase 1 — this happens in the *same* transaction as the lifecycle flip, so it is irreversible for that token regardless of what happens in Phase 2. If the cached amounts are small enough to make `pair.mint()`'s first-deposit branch revert, every future call to the permissionless `finalizeGraduation(tokenAddress)` reverts identically (the cached values in `pendingGraduation` never change), so the token can never reach `Graduated`. This permanently freezes: the creator/LP-bound 250M `tokensForLP` allocation, the curve-raised LT that was already swept out of the pair, and all trader positions in the token (no further buys/sells, no LP ever created, no rescue path since `finalizeGraduation` is the only exit from `Graduating`). This is a permanent freezing-of-funds impact.

### Likelihood Explanation
Reachability requires only unprivileged transactions: any trader's `Zap.buy`/`Bonding.buy` that crosses the USD graduation threshold at a moment when the LT's live `exchangeRate()` is elevated enough that the resulting raw `ltFromPair` computed in `_prepareGraduationLiquidity` is small (on the order of UniswapV2's `MINIMUM_LIQUIDITY = 1000` or less in the `sqrt(tokensForLP*ltFromPair)` sense), or equivalently the permissionless `triggerGraduation` call once `canGraduate` is already true. No privileged role, upgrade, or off-chain component is needed — a trader simply needs to be the one whose buy crosses the USD trigger while the externally-priced LT's exchange rate is high relative to its own decimal/wei scale. Since exchange rate volatility of the LT is an explicit, acknowledged property of the design (documented as accepted drift risk elsewhere in `AGENTS.md`), this is a realistic, not purely theoretical, edge condition, though it is a narrower window than the already-covered "swap rounds to zero" and dust-pre-seed cases that the code does defend against.

### Recommendation
Add an explicit guard in `_seedDirectMint` (and generally before any first-time `pair.mint()` call in `_seedUniswapV2Direct`'s empty-pair/direct-mint branches) that checks `tokensForLP * ltFromPair` against UniswapV2's `MINIMUM_LIQUIDITY` threshold before attempting the mint, and if it would round to zero, fall back to a deterministic non-reverting path (e.g., mint with a synthetically bumped floor amount sourced from `Bonding`, or explicitly allow `finalizeGraduation` to complete with `liquidity == 0`/no-LP and instead sweep the tiny LT/token amounts to the owner, similavailable to `_sweepLTToOwner`) so `finalizeGraduation` truly can never revert regardless of how small the cached graduation amounts are.

### Proof of Concept
1. Launch a token whose LT has a live, externally-set `exchangeRate()` (per the mock/test harness's `setExchangeRate`, as used in `test/GraduationInvariants.t.sol`).
2. Drive `exchangeRate()` to a very large value (simulating LT rebasing/appreciation) such that `graduationThresholdUsd / exchangeRate()` (i.e., the raw LT needed to cross the USD trigger) rounds down to a value on the order of a few hundred wei once converted through `_prepareGraduationLiquidity`'s `ltFromPair = assetReserve - virtualLtReserve` and `tokensForLP = ltFromPair * tokenReserve / assetReserve`.
3. Submit a normal `Bonding.buy`/`Zap.buy` (or `Zap.buyPermit`) that pushes `canGraduate(tokenAddress)` true via the USD trigger; `_executeBuy` calls `_enterGraduating`, which flips `lifecycle = Graduating`, drains the curve's LT via `router.graduate`, and caches the tiny `(tokensForLP, ltFromPair)` into `pendingGraduation`.
4. Call the permissionless `finalizeGraduation(tokenAddress)`. `_seedUniswapV2Direct` → `_seedDirectMint` transfers the tiny cached amounts to the fresh pair and calls `pair.mint(lpLock)`; UniswapV2's first-mint `sqrt(amount0*amount1) - MINIMUM_LIQUIDITY` underflows/rounds to zero and the pair reverts with `INSUFFICIENT_LIQUIDITY_MINTED`, reverting the entire `finalizeGraduation` call.
5. Every subsequent call to `finalizeGraduation(tokenAddress)` by any caller reverts identically because `pendingGraduation` is never recomputed — the token is permanently stuck in `Lifecycle.Graduating` with trading frozen and its curve-raised LT/reserved 250M tokens unrecoverable.

```text
    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }
```

```text
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair
    ) internal returns (uint256 liquidity) {
        IERC20(tokenAddress).safeTransfer(pair, tokensForLP);
        IERC20(lt).safeTransfer(pair, ltFromPair);
        liquidity = IUniswapV2Pair(pair).mint(_s().lpLock);
        uint256 leftoverToken = IERC20(tokenAddress).balanceOf(address(this));
        if (leftoverToken > 0) {
            Token(tokenAddress).burn(address(this), leftoverToken);
        }
    }
```

```text
    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }
```
