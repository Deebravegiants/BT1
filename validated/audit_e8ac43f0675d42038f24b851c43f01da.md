### Title
Division-by-zero panic in `calc_take_pnl` permanently freezes LP funds after decimal-truncation of pool reserves - ([File: program/src/processor.rs])

### Summary
`Processor::calc_take_pnl` (called from `process_deposit`, `process_withdraw`/`process_withdraw2`, and `process_withdrawpnl`) computes `y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` where `x1`/`y1` are the *decimal-normalized* pool reserves produced by `Calculator::normalize_decimal_v2`. Because `normalize_decimal_v2` performs integer division (`val * sys_decimal_value / 10^native_decimal`), a nonzero raw reserve can normalize to exactly `0` when it is small relative to `10^native_decimal / sys_decimal_value`. When that happens and the "take pnl" branch is entered, the code divides by `x1 == 0`, `checked_div` returns `None`, and `.unwrap()` panics, aborting the transaction. [1](#0-0) [2](#0-1) 

### Finding Description
`calc_take_pnl` is entered whenever `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount` (i.e., the current invariant is at least the last recorded one, which is the normal state since trading fees continuously grow the invariant): [3](#0-2) 

Inside this branch it computes `x2_power` via `calc_x_power` and then `x2 = x2_power.integer_sqrt()`, followed by:
```
let y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap();
```
`x1` and `y1` are the normalized (decimal-adjusted) totals passed in by the caller (`process_deposit`, `process_withdraw2`, `process_withdrawpnl`), computed via `Calculator::normalize_decimal_v2(total_pc_without_take_pnl, amm.pc_decimals, amm.sys_decimal_value)`: [2](#0-1) [4](#0-3) 

`normalize_decimal_v2` truncates via integer division, so if `total_pc_without_take_pnl * sys_decimal_value < 10^pc_decimals`, `x1` becomes `0` even though the raw pc reserve is nonzero. Since `x1 == 0` forces `x2_power == 0` (because `calc_x_power` multiplies by `current_x = x1`), `x2` also becomes `0`, and the subsequent `checked_div(x1)` is a `0/0` divide, which panics.

An unprivileged trader can drive `total_pc_without_take_pnl` this low with an ordinary swap: `process_swap_base_in`/`process_swap_base_out` only enforce `amount_out < total_pc_without_take_pnl` (strictly), so the remaining reserve after a large swap can be reduced to an arbitrarily small nonzero raw amount (e.g., `1`): [5](#0-4) [6](#0-5) 

Once the reserve is this thin, any subsequent call to `process_deposit` or `process_withdraw2` (both of which invoke `calc_take_pnl`) panics deterministically: [7](#0-6) [8](#0-7) 

### Impact Explanation
Once the pool is put into this state, every deposit or withdrawal attempt aborts with a panic (division by zero), because the panic condition is a deterministic function of the on-chain reserves and does not require any privileged signer to trigger repeatedly. This means LP token holders can no longer withdraw their share of the pool (`process_withdraw2`), and no new liquidity can be added (`process_deposit`) — a durable freeze of LP funds until reserves happen to shift back out of the truncation range (which, for a drained/imbalanced side, may never happen without further outside intervention). This matches the CVE's "hang / crash / complete DoS" bug class, translated to Solana semantics as a permanent, unprivileged-reachable freeze of user/LP funds rather than a process-level crash.

### Likelihood Explanation
Reachable with a single unprivileged swap transaction (attacker-chosen `amount_in`/`amount_out`, standard swap accounts) followed by any ordinary deposit/withdraw transaction from any user. No special build flags, validator/leaked-key assumptions, or off-chain components are needed — only sufficient capital (or a sufficiently shallow pool) to push one side of the reserves under the `10^decimals / sys_decimal_value` truncation threshold while the invariant-growth condition (`pool_pc*pool_coin >= calc_pc*calc_coin`, generally true because fees only grow the invariant) still holds.

### Recommendation
In `Calculator::normalize_decimal_v2`/`calc_x_power`/`calc_take_pnl`, treat a normalized reserve of `0` as a guarded case: return an explicit `AmmError` (e.g., `CalcPnlError`) instead of unwrapping `checked_div`, and/or skip the pnl-taking branch entirely when `x1 == 0 || y1 == 0`. More robustly, replace the `.unwrap()` calls in `calc_take_pnl`'s division/multiplication chain with `.ok_or(AmmError::CalcPnlError)?` so any degenerate reserve state fails gracefully with a recoverable error rather than an unrecoverable panic, and add a minimum-reserve invariant check in swap processing so any single swap cannot leave `total_pc_without_take_pnl`/`total_coin_without_take_pnl` below the decimal-normalization safety margin.

### Proof of Concept
1. Create (or select) a pool where `pc_decimals` (or `coin_decimals`) combined with `amm.sys_decimal_value` allows truncation to zero for small raw reserves (e.g., `pc_decimals = 9`, `sys_decimal_value = 1_000_000` → any raw pc reserve `< 1000` normalizes to `0`).
2. Submit a `SwapBaseIn`/`SwapBaseOut` transaction with `amount_in`/`amount_out` chosen so that `total_pc_without_take_pnl` after the swap is reduced to a small nonzero value below the truncation threshold (still passes the `amount_out < total_pc_without_take_pnl` check in `process_swap_base_in`/`process_swap_base_out`). [5](#0-4) 
3. Submit a subsequent `Deposit` or `Withdraw` instruction on the same pool. `process_deposit`/`process_withdraw2` compute `x1 = normalize_decimal_v2(total_pc_without_take_pnl, ...) == 0` and call `calc_take_pnl`, which panics at `x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()`. [9](#0-8) 
4. Observe the transaction abort; repeat step 3 with any account — every deposit/withdraw against this pool continues to panic, permanently freezing existing LP funds and blocking new deposits.

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }
