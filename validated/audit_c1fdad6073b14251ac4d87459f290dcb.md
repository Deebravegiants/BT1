### Title
Emporium's signature-based withdrawal path skips the variable-rate relay fee, letting a user underpay protocol/relay fees - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.payRelayFees` computes the relay fee differently depending on whether an EIP-712 `signerAddress` (a `HinkalWallet`) is used for the Emporium operation. When `signerAddress == address(0)` the full fee (`flatFee` **plus** `feeStructure.variableRate`) is charged via `IHinkalHelper.calculateRelayFee`. When `signerAddress != address(0)` (the "stateful"/wallet-invoking path), only the `flatFee` is charged — the percentage-based `variableRate` component is never applied.

### Finding Description
In `payRelayFees`:
```solidity
contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:226-237
if (signerAddress == address(0)) {
    uint256 sumAbs = uint256(-deltaAmountChanges[i]);
    relayFee = $._hinkalHelper.calculateRelayFee(sumAbs, flatFee, feeStructure.variableRate);
} else {
    relayFee = flatFee;
}
``` [1](#0-0) 

`calculateRelayFee` (mirrored in `RelayStore.sol`) is the intended fee model: `relayFee = balance - ((10000 - variableRate) * (balance - flatFee)) / 10000`, i.e. flat fee + a percentage of the remainder. [2](#0-1) 

The internal (non-Emporium) withdrawal path in `Hinkal.sol` also always applies the full flat+variable fee model regardless of caller. [3](#0-2) 

However, for Emporium operations that use the `invokeWallet`/`signerAddress` (EIP-712 signature) path, `payRelayFees` intentionally bypasses `variableRate` and charges only `flatFee`, no matter how large the withdrawn `sumAbs` is:
```solidity
contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:235-237
} else {
    relayFee = flatFee;
}
``` [4](#0-3) 

`verifyWallet` only checks that `flatFee <= stack.maxFee`; it never validates or requires the variable-rate component:
```solidity
contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:346-348
if (circomData.feeStructure.flatFee > stack.maxFee) {
    revert FeeExceedsSignedMax();
}
``` [5](#0-4) 

`signerAddress` is supplied inside `circomData.externalActionData.externalActionMetadata` (decoded as `EmporiumStack`), which is any user/prover-controlled value bound into the `calldataHash` public signal — it is not forced to be zero. [6](#0-5) [7](#0-6) 

Consequently, any user who structures their Emporium withdrawal to go through their own `HinkalWallet` with a valid signature (something entirely within their control, since they own the stealth wallet and can sign it themselves) pays only the fixed `flatFee`, while a functionally identical withdrawal through the `signerAddress == 0` path would be charged `flatFee + variableRate%`. This breaks the fee-equality invariant the protocol otherwise enforces uniformly (`RelayStore.calculateRelayFee`, `Hinkal._internalTransact`), effectively letting the depositor/withdrawer choose the cheaper unauthorized fee path and short the relay/protocol of the variable-rate portion of the fee on every large withdrawal routed this way.

### Impact Explanation
This is an unauthorized reduction of protocol/relay fee revenue: relays and/or the protocol treasury are not paid the `variableRate` fee component they are entitled to on withdrawals that go through the wallet-signature Emporium path, even though the exact same `feeStructure.variableRate` value is present in `circomData` and enforced everywhere else. For any sizeable withdrawal, the loss (variableRate% of the withdrawn amount) is only bounded by the relay's/protocol's `variableRate` setting, and it accrues on every transaction using this path — this is a theft/permanent loss of protocol/relay fees (High impact per the given criteria).

### Likelihood Explanation
Likelihood is high in practice: any ordinary user with a `HinkalWallet` can trivially choose `invokeWallet=true` and provide a valid signature over their own operations (they hold the wallet's signing key by design), routing the withdrawal path so `signerAddress != address(0)`. No privileged role, relayer collusion, or protocol misconfiguration is required — it is purely a consequence of choosing which of the two legitimate `EmporiumOperation` paths to use.

### Recommendation
Make `payRelayFees` apply the same fee formula (`calculateRelayFee`, including `variableRate`) regardless of whether `signerAddress` is zero or not, e.g.:
```solidity
uint256 sumAbs = uint256(-deltaAmountChanges[i]);
relayFee = $._hinkalHelper.calculateRelayFee(sumAbs, flatFee, feeStructure.variableRate);
```
for both branches, and additionally validate in `verifyWallet` that the total fee (`flatFee` + variable component) implied by `feeStructure` does not exceed `stack.maxFee`, so signature-based approvals cannot be used to silently waive the percentage fee.

### Proof of Concept
1. Attacker deposits funds into the shielded pool normally and later wants to withdraw via Emporium.
2. Attacker constructs an `EmporiumStack` with `invokeWallet = true` and `signerAddress = <their own HinkalWallet>`, signs the `EmporiumSignature` typed-data payload themselves (they control the wallet key), and sets `stack.maxFee = feeStructure.flatFee` (the check in `verifyWallet` only compares against `flatFee`).
3. Attacker calls `Hinkal.transact` with a valid ZK proof for the withdrawal amount and this `circomData` (the `externalActionMetadata`/`signerAddress` value is only hashed into `calldataHash`, not otherwise constrained).
4. `EmporiumUpgradeable.runAction` → `payRelayFees` executes the `signerAddress != address(0)` branch, so `relayFee = flatFee` only; the `variableRate` percentage of the (possibly large) withdrawn amount is never deducted, and is instead paid out entirely to the attacker.
5. Repeating this for every withdrawal, the attacker (or any operator/relay) permanently under-collects the `variableRate` fee that the protocol's own `feeStructure` and `calculateRelayFee` model says should be charged.

    function calculateRelayFee(
        uint256 balance,
        uint256 flatFee,
        uint256 variableRate
    ) public pure returns (uint256 relayFee) {
        require(balance >= flatFee, "Relay Fee is over withdraw amount");
        uint256 recipientAmount = ((10000 - variableRate) *
            (balance - flatFee)) / 10000;
        relayFee = balance - recipientAmount;
    }
