### Title
OAuth callback leaks `client_secret` to an unvalidated `shop` host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` and `begin_auth` use the caller-supplied `shop` value to build the URL that receives the app's `client_id`/`client_secret` (via `auth_base_uri(shop)` and `Clients::HttpClient`'s `@base_uri = "https://#{api_host || session.shop}"`), but never runs `shop` through `Utils::ShopValidator.sanitize!`. Every other credential-sending flow in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host that will receive the secret. The OAuth callback path is the one exception.

### Finding Description
`Auth::Oauth.validate_auth_callback` does: [1](#0-0) 
It validates the HMAC over the query (`code, host, shop, state, timestamp`) with `Utils::HmacValidator.validate(auth_query)` [2](#0-1) , then immediately builds `null_session = Auth::Session.new(shop: auth_query.shop)` and passes it to `Clients::HttpClient`. `HttpClient#initialize` derives the request host purely from `session.shop`, with no domain allow-list check: `@base_uri = "https://#{api_host || session.shop}"` [3](#0-2) . That URI is where the POST body containing `client_id` and `Context.api_secret_key` is sent: `body = { client_id: ..., client_secret: Context.api_secret_key, code: ..., ... }` followed by `client.request(...)` [4](#0-3) .

By contrast, the other three flows that also POST `client_secret` to a shop-derived host all guard the shop string with `Utils::ShopValidator.sanitize!` first: [5](#0-4) [6](#0-5) [7](#0-6) 
`ShopValidator.sanitize!` restricts the host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [8](#0-7) . `validate_auth_callback` (and `begin_auth`, which likewise builds `auth_base_uri(shop)` with no validation [9](#0-8) ) never applies this check.

This breaks the intended equality: **host authenticated by the HMAC-bound `shop` value == host that is allowed to receive `client_secret`**. The `AuthQuery` HMAC only proves that whoever produced `code/host/shop/state/timestamp` knew `Context.api_secret_key`; it enforces integrity of that string, but the library itself performs no allow-list check that the resulting host is actually a `*.myshopify.com`/trusted Shopify domain before dispatching the secret there. Since the host application is the one that instantiates `AuthQuery` from the incoming request's raw query parameters, and this gem provides no built-in domain restriction on `shop` in this specific path (unlike the other three sibling flows), the library's own OAuth callback code path is inconsistent and lacks the same defense-in-depth check present everywhere else `client_secret` is transmitted.

### Impact Explanation
If the value ultimately supplied as `shop` for `AuthQuery` is not otherwise constrained to a `myshopify.com`/trusted domain by the host application, the completion of OAuth will POST the app's `client_id` and `client_secret` to an attacker-influenced host. This qualifies as Critical — "theft or exfiltration of ... the app's `client_secret`" — since the secret is sent in the POST body to whatever host `auth_base_uri(shop)` resolves.

### Likelihood Explanation
Medium: this depends on how permissively the host application is that wires unauthenticated query parameters into `AuthQuery.new(shop: ...)`. Since the gem itself provides no `ShopValidator.sanitize!` guard at this specific call site — while it does so at every other credential-sending call site — the library fails to provide the defense-in-depth its own sibling methods rely on, making this a real gap in the gem rather than solely an integration mistake.

### Recommendation
In `ShopifyAPI::Auth::Oauth.begin_auth` and `validate_auth_callback`, call `Utils::ShopValidator.sanitize!(shop)` (as is already done in `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`) before constructing `auth_base_uri(shop)` / `Auth::Session.new(shop:)`, so the same trusted-domain allow-list applies uniformly across every code path that transmits `client_id`/`client_secret`.

### Proof of Concept
1. Host application receives an OAuth-initiation or callback request and constructs `ShopifyAPI::Auth::Oauth::AuthQuery.new(shop: params[:shop], ...)` directly from request parameters (as shown in this gem's own test setup pattern) without separately validating `shop` against `ShopValidator`.
2. Attacker crafts a request where they can also produce/replay a query whose `shop` resolves to an attacker-controlled host reachable by the merchant/app server (e.g., during `begin_auth`, no HMAC is required at all — see `lib/shopify_api/auth/oauth.rb:22-52` — the `shop` parameter is used directly with no validation to build the OAuth authorize redirect target, and the same unchecked `shop` is later reused to build the token-exchange endpoint on `validate_auth_callback`).
3. `Auth::Oauth.validate_auth_callback` builds `Clients::HttpClient.new(session: Auth::Session.new(shop: auth_query.shop), base_path: "/admin/oauth")` and POSTs `{client_id, client_secret, code, expiring}` to `https://#{auth_query.shop}/admin/oauth/access_token`.
4. Because `lib/shopify_api/utils/shop_validator.rb`'s `TRUSTED_SHOPIFY_DOMAINS` allow-list is never consulted in this path, the request (and the `client_secret`) is sent to the attacker-controlled host instead of a real Shopify domain.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
```

```ruby
          shop_name = shop.split(".").first
```
