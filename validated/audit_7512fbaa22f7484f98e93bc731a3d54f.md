### Title
Webhook `shop-domain` is trusted by handlers but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` (merchant) attribution comes from the `x-shopify-shop-domain` header, which is never included in the signed data. `Registry.process` validates the HMAC and then hands `request.shop` straight to the app's handler as an authenticated fact, creating a binding mismatch: `HMAC(secret, raw_body) == valid` is treated as if it implies `shop-domain header == the shop that actually sent this payload`, but the header is not part of what was signed.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a header that is not included in the signable string at all: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header — it has no knowledge of, and does not cover, the shop header: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then unconditionally trusts `request.shop` and forwards it to the application's webhook handler as the shop the event pertains to: [4](#0-3) 

Because the same `api_secret_key` is shared across *all* shops that have installed the app, a valid `(raw_body, hmac)` pair produced for one installation (e.g. a webhook the attacker's own store legitimately receives, or any topic whose payload is attacker-predictable/replayable, such as `app/uninstalled`, `shop/redact`, or any webhook with an empty/static body) remains cryptographically valid regardless of which `shop-domain` header value accompanies it. An unprivileged attacker who controls a shop with the app installed (or who can otherwise capture one genuine `(body, hmac)` pair) can POST that same body+hmac to the app's webhook endpoint with an arbitrary victim `shop-domain` header. Since the gem's `Registry.process` never checks that `shop` is bound to the signed payload, the HMAC check passes and the handler executes believing the event belongs to the victim shop.

This mirrors the report's root cause: the value acted upon downstream (`shop`, used by the host application to look up/act on a tenant's session or data) is not the value covered by the cryptographic check (`raw_body` only) — exactly the "field acted on but not covered by the HMAC" pattern from the referenced analog.

### Impact Explanation
This breaks the tenant-identity binding relied upon by every consumer of this gem's webhook processing: `Registry.process` explicitly passes `request.shop` into `WebhookMetadata` as trusted, authenticated data after HMAC validation succeeds. An application built on this gem (as intended — see `docs/usage/webhooks.md` and `WebhookHandler` usage) will process/act on webhook payloads under a shop identity that was never actually verified, enabling cross-tenant confusion: e.g. triggering `shop/redact` or `app/uninstalled` handling logic for a victim shop, or having the handler write/derive data keyed by the forged `shop` value. This is a cross-tenant access issue as defined in scope (Critical impact category: "cross-tenant access").

### Likelihood Explanation
Medium-High. It requires no privileged credentials — only a valid `(body, hmac)` pair, which is trivial to obtain if the attacker's own shop has the app installed (any legitimate webhook delivery to the attacker's own store yields a valid pair signed with the shared `api_secret_key`), or if a webhook body is static/predictable across shops (many Shopify webhook bodies for a given topic/schema are deterministic or attacker-influenceable, e.g., empty-body test pings or `shop/redact`). The header can then be freely modified when replaying to the target app's public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) header values into the signed data checked by `HmacValidator`, or have `Webhooks::Request#to_signable_string` incorporate the shop-domain header so a mismatch invalidates the signature; alternatively, cross-check the header `shop` against a shop known to have installed the app (via stored session/webhook subscription state) before invoking the handler, rather than treating the header as authenticated purely because the body's HMAC matched.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, and receives a legitimate webhook delivery (e.g. `orders/create` with a body they can also reproduce, or a topic with an empty/fixed body such as a compliance webhook), capturing the genuine `x-shopify-hmac-sha256` header value for that `raw_body`.
2. Attacker POSTs to the app's webhook endpoint the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body`: [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload never originated from, nor was ever verified against, that shop, allowing the attacker to trigger shop-scoped webhook handling logic under the victim's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
