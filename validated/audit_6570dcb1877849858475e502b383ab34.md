### Title
Destination-side order cancellation permanently locks escrow when the `RefundEscrow` message is never delivered - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`_cancelFromDest` marks a cross-chain order as irrevocably settled on the destination chain (`_filled[commitment] = order.user`) *before* the corresponding `RefundEscrow` message has been delivered and processed on the source chain. Because the Intent Gateway dispatches this POST message and does not provide a working timeout-recovery path (its `onPostRequestTimeout` is not overridden and falls back to `HyperApp`'s default, which reverts with `UnexpectedCall`), a stalled or undelivered refund message leaves the order in a state that can neither be filled, nor re-cancelled from the source, nor have its escrow released — the deposited collateral is frozen indefinitely.

### Finding Description
`_cancelFromDest` in `ExtrinsicIntents.sol` (equivalently `IntentGatewayV2.sol` / `evm/tron/contracts/apps/IntentGatewayV2.sol`) performs the state mutation and the cross-chain dispatch in this order: [1](#0-0) 

`_filled[commitment]` is set to the order's user **immediately**, unconditionally of whether the `RefundEscrow` POST ever reaches and is accepted by the source chain. This mapping is the sole gate that:
- Prevents future fills of the order, and
- Is read directly by the source-side cancellation path (`_cancelFromSource`) via a Hyperbridge storage-proof GET query against this exact slot: [2](#0-1) [3](#0-2) 

Once `_filled[commitment]` is non-zero on the destination, `onGetResponse` on the source will see a non-empty storage value and revert with `Filled()`, permanently closing the only alternate recovery route.

The escrow itself is only released when the source chain's `onAccept` processes the incoming `RefundEscrow` request and calls `_withdraw`: [4](#0-3) 

If that message is never relayed/delivered (relayer censorship, relayer set removal, host issues, or the relayer simply never picks it up), the escrow on the source chain is never released, yet the destination has already burned the only paths to recovery.

Critically, the gateway's cross-chain dispatch offers no functioning timeout-based recovery: the project's own design notes confirm the Intent Gateway "does not gate its timeout callbacks because `HyperApp`'s defaults revert and it dispatches with no timeout": [5](#0-4) 

`HyperApp`'s default `onPostRequestTimeout` simply reverts: [6](#0-5) 

This is exactly the reported bug class ("Improper State Management in Canceling Orders" — state marked as settled/locked without an unwind path on cancellation), reachable via a single unprivileged `cancelOrder(order, options)` call on the destination chain by the order's own user (or by anyone after the deadline).

### Impact Explanation
If the `RefundEscrow` message dispatched by `_cancelFromDest` is never delivered (a realistic scenario for a permissionless relayer network — no relayer is obligated to deliver any specific message, and delivery is not enforceable or replayable by an alternate mechanism once `_filled` is set), the user's escrowed input tokens become permanently frozen:
- They cannot be filled (order marked settled).
- They cannot be refunded via the destination path a second time (idempotent state check would simply no-op or revert as already filled).
- They cannot be recovered via the source-side cancellation path, since the GET-based proof will always show the slot as non-empty and revert with `Filled()`.

This is a permanent freezing-of-funds condition for the exact escrowed principal amount of any order cancelled through the destination route whose refund message stalls, satisfying the "concrete... permanent freezing of funds" bar.

### Likelihood Explanation
Likelihood is moderate: it requires the relayer network to fail to deliver a specific POST message indefinitely (e.g., due to censorship, relayer downtime, fee insufficiency discouraging relaying, or targeted griefing by a relayer who can selectively decline to deliver a chosen commitment). Because `_cancelFromDest` is reachable by anyone after the order deadline (not just the order owner), and no on-chain incentive/enforcement guarantees timely delivery of this specific message type, an adversarial or negligent relayer set can trigger this condition deterministically for a targeted order.

### Recommendation
Do not mark `_filled[commitment]` as terminal on the destination until the refund has been confirmed released on the source, or provide a real timeout/retry mechanism:
- Attach a genuine `timeoutTimestamp` to the `RefundEscrow` dispatch instead of `0`/no-timeout, and implement `onPostRequestTimeout` in the gateway (rather than relying on `HyperApp`'s reverting default) to revert the local `_filled` marker so the order can be retried or cancelled through the source path.
- Alternatively, allow `_cancelFromDest` to be re-invoked (idempotently) to re-dispatch a fresh `RefundEscrow` request if the prior one is confirmed lost/expired, without requiring the GET-based source path (which is now permanently blocked by the non-empty `_filled` slot).
- Consider decoupling "blocked from future fills" from "escrow released," e.g. using a distinct status enum value for "cancellation pending" vs. "settled/refunded," so that a stalled cross-chain leg does not also poison the alternate recovery path.

### Proof of Concept
1. User places a cross-chain order via `placeOrder`, escrowing `inputAmount` of `usdc` on the source chain.
2. After (or before) `order.deadline`, an unprivileged caller invokes `cancelOrder(order, options, { from: "destination" })`, which internally calls `_cancelFromDest`: [1](#0-0) 
   - `_filled[commitment]` is now set to `order.user` on the destination chain.
   - A `RefundEscrow` POST request is dispatched via Hyperbridge.
3. Assume the relayer set never delivers this specific POST request to the source chain (a realistic censorship/liveness failure, not requiring any privileged/malicious-relayer assumption beyond ordinary non-delivery).
4. On the source chain, escrow for `commitment` remains locked in `_orders[commitment][token]`; `onAccept`/`_withdraw` is never invoked.
5. The user (or anyone) attempts the alternate `_cancelFromSource` recovery path once `options.height > order.deadline`: [2](#0-1) 
   - The dispatched GET request queries the destination's `_filled[commitment]` slot, which is now non-empty (set to `order.user` in step 2).
   - `onGetResponse` on the source reverts with `Filled()`: [7](#0-6) 
6. The escrowed `inputAmount` is now permanently unreachable: no fill, no destination refund (already "settled"), and no source-side recovery (blocked by the non-empty `_filled` slot) — a permanent freeze of user funds, with no timeout-driven unwind available given the gateway's zero-timeout, reverting `onPostRequestTimeout` design confirmed by the project's own documented decision.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }

    /**
     * @dev Handles the response to a Hyperbridge GET request dispatched during
     * `_cancelFromSource`. Verifies that the `_filled` storage slot on the destination
     * chain is empty (meaning the order was never filled), then refunds the escrowed
     * tokens to the original user. Reverts with `Filled` if the slot is non-empty.
     *
     * @param incoming The incoming GET response from Hyperbridge containing the storage proof.
     */
    function onGetResponse(IncomingGetResponse calldata incoming) external override onlyHost {
        _checkRelayer(incoming.relayer);
        if (incoming.response.values[0].value.length != 0) revert Filled();

        WithdrawalRequest memory body = abi.decode(incoming.response.request.context, (WithdrawalRequest));
        _withdraw(body, true, true);
    }
