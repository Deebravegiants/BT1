### Title
Bad-debt wipeout clamps supply index UP at `SUPPLY_INDEX_FLOOR_RAW`, resurrecting wiped supplier claims that drain fresh deposits — (File: contracts/pool/src/interest.rs)

### Summary
The pool's bad-debt socialization in `apply_bad_debt_to_supply_index` reduces `supply_index` to reflect a loss, but then clamps the result to a minimum of `RAY/1000` (`SUPPLY_INDEX_FLOOR_RAW`). When a bad-debt seizure wipes out the entire supplied value (the attacker-reachable `clean_bad_debt` / liquidation seize path via `pool::ops::seize::apply`), the index should approach zero but is instead forced back up to the floor. Every scaled supply share that should have become worthless retains a claim of `scaled × RAY/1000`. Once any new deposit brings cash into the market, those "freed" claims are redeemable again — a use-after-free analog where shares that were economically burned remain live handles that withdraw real tokens — and the fresh depositor's cash is stolen.

### Finding Description
`Cache::supply_index` is documented as non-monotone specifically because `apply_bad_debt_to_supply_index` lowers it to socialize losses (contracts/pool/README.md). The implementation computes `remaining = total_supplied_value − capped_bad_debt`, scales the index by `remaining / total`, then floors it:

```rust
// contracts/pool/src/interest.rs:84-88
let new_supply_index = cache
    .supply_index()
    .mul_floor(cache.env(), reduction_factor);
cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
```

When `bad_debt >= total_supplied_value`, `reduction_factor = 0` and the correct index is 0 — every supply share is wiped. Instead the index is set to `RAY/1000`, so every surviving scaled position keeps a positive claim (`unscale_supply_floor > 0`). Because the shares were never burned, `withdraw`/`seize`/controller exits still resolve them via `resolve_withdrawal`/`burn_position`, and `require_reserves` admits them as soon as cash exists.

The trigger path is unprivileged: a user creates an account that accrues bad debt (e.g., price move or dust-threshold debt), then anyone calls the controller's `clean_bad_debt`/`liquidate`, which routes through `execute_bad_debt_cleanup` → `pool_seize_positions_call` → `ops::seize::apply` → `AccountPositionType::Borrow` leg → `interest::apply_bad_debt_to_supply_index` (contracts/pool/src/ops/seize.rs:24-28). Other suppliers' shares in the same market keep the phantom claim. The project's own tests demonstrate the exploit end-to-end: `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` and `test_raw_cache_seizure_residual_would_drain_fresh_cash_without_supply_guard` (contracts/pool/tests/interest.rs:373-494) show the wiped position paying out `gross == fresh_deposit`, leaving `cash < fresh_claim`.

### Impact Explanation
Theft of user funds. After a full bad-debt wipeout, wiped suppliers (or the attacker who also holds supply shares in that market — nothing prevents the bad-debt account's own shares or a second account's shares from surviving) can withdraw tokens backed only by the floor-clamped index. Each fresh deposit into the market is immediately claimable by phantom shares; the fresh depositor's `unscale_supply_floor` claim exceeds remaining `cash`, so the pool is insolvent and the new supplier permanently loses funds. Repeated cycles (deposit → wipeout → deposit) re-arms the drain.

### Likelihood Explanation
High. `clean_bad_debt` and `liquidate` are permissionless entrypoints, and creating a bad-debt position requires only posting collateral and borrowing — normal user actions. A total wipeout occurs whenever bad debt meets or exceeds total supplied value, which is typical for a small/new market or when the bad-debt account's supply shares dominate the market. No privileged role, upgrade, or oracle misbehavior is required. The `require_reserves` check only masks the bug while cash is zero; the first honest deposit unmasks it.

### Recommendation
Remove the floor clamp on the post-write-down index, or handle the wipeout explicitly: when `remaining == 0`, either burn all outstanding supply shares (set `supplied`/`revenue` to zero alongside `supply_index = 0` and treat `unscale` of a zero index as zero), or set the index to a value proportional to `remaining` without flooring — i.e., delete `.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW))` and make the share→asset conversions and `require_reserves` tolerate a zero index. If a floor is needed to avoid division-by-zero for future `calculate_scaled_supply` calls, gate it so it only applies when `remaining > 0`, and add a `supplied == 0`-with-claims guard as defense in depth.

### Proof of Concept
From contracts/pool/tests/interest.rs:372-428 (simplified):

1. Market state: `supplied = 1000e27` scaled, `supply_index = RAY`, `cash = 0`.
2. `apply_bad_debt_to_supply_index(cache, 5000e27)` — bad debt exceeds total supplied value. `supply_index` is clamped UP to `RAY/1000` instead of 0.
3. `unscale_supply_floor(old_scaled)` returns a positive amount — a stranded claim on an empty market.
4. Bob deposits `fresh_cash = stranded`; pool `cash = fresh_cash`.
5. The wiped position calls `resolve_withdrawal(i128::MAX, old_scaled)` → `require_reserves` passes → `burn_supply`/`debit_cash(gross)` with `gross == fresh_cash`.
6. Bob's claim `unscale_supply_floor(bob_scaled) > cash` — the fresh depositor cannot be paid; the wiped supplier stole the deposit.

Same outcome via the `AccountPositionType::Borrow` seize leg during `clean_bad_debt` when remaining debt ≥ total supplied value (contracts/pool/src/ops/seize.rs:24-28, contracts/pool/src/interest.rs:73-89).
