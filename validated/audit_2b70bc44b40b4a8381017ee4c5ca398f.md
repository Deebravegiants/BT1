### Title
Webhook `shop` (and `topic`) fields are trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw request body, then dispatches the webhook handler using the `shop` value taken from an HTTP header that is never included in the signed payload. Since a Shopify app's `client_secret` (and therefore its webhook HMAC secret) is shared across every shop that has the app installed, HMAC validity proves only that the body was produced with that shared secret — it proves nothing about which shop the body belongs to. An attacker who controls (or has previously captured) one genuine `body + hmac` pair for the app is able to replay it to the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` header, and the request will still validate.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an unauthenticated header with no cross-check against the signed content: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC (which covers only the body), and then immediately hands the caller-supplied `shop` header value to the app's handler: [4](#0-3) 

`HmacValidator.validate` / `validate_signature` confirm only that `verifiable_query.to_signable_string` (the raw body, for webhooks) matches the HMAC against `Context.api_secret_key`: [5](#0-4) 

The broken identity binding is:
`shop header value used by the webhook handler` ≠ `shop bound inside the HMAC-covered bytes (the body)`

Because a single app has one `api_secret_key` shared by all shops that install it, any tenant of the app can obtain a valid `(raw_body, hmac)` pair from their own genuine webhook deliveries, then resend that exact pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` (or `shopify-shop-domain`) header value naming another tenant of the same app. `Utils::HmacValidator.validate` still returns `true`, because it only recomputes the HMAC over the body — the shop header plays no role in the signature. `Registry.process` then invokes the merchant's registered handler with `WebhookMetadata.shop` set to the attacker-chosen (victim) shop, while the actual JSON payload/content is whatever the attacker was able to produce (from their own store's data).

### Impact Explanation
This breaks the tenant isolation the HMAC check is supposed to provide: an app that trusts `WebhookMetadata#shop` (as returned by this gem) to route data or authorize an action per-tenant can be made to apply attacker-influenced payload content under another tenant's identity — a cross-tenant access/data-integrity violation, one of the explicitly allowed Critical/High impact categories in scope.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint plus one genuine `(body, hmac)` pair, which any shop that has legitimately installed the app can obtain from its own webhook deliveries (webhook endpoints are public HTTP(S) endpoints with no mutual TLS or IP allow-listing enforced by this gem). No possession of `client_secret`, access tokens, or other shop's credentials is required — only the shared HMAC secret's *effect*, which is inherently the same across all tenants of one app.

### Recommendation
Do not treat the `shop`/`shop-domain` header as trusted merely because the body HMAC validates. Either:
- Include the shop domain (and topic) inside the HMAC-signed material so the signature binds the claimed tenant to the payload, or
- Independently verify that the `shop` header corresponds to a shop with a currently valid, stored session/installation for this app before acting on the webhook, rather than passing the raw header value straight through to `WebhookMetadata`.

### Proof of Concept
1. App `A` shares one `client_secret` across shop `attacker.myshopify.com` and shop `victim.myshopify.com` (both have the app installed).
2. Shopify sends a genuine webhook to `A`'s endpoint for `attacker.myshopify.com`:
   headers: `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`, body: `B`.
   `H = HMAC-SHA256(client_secret, B)` — valid per `HmacValidator.validate_signature`.
3. Attacker resends the identical `B` and `H` to `A`'s webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and compares to `H` — matches, since `B` and `H` are unchanged (`request.rb` lines 35-38).
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` (`registry.rb` lines 198-199), even though the payload actually originated from the attacker's own shop.

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
