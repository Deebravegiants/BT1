The strongest analog to the reported bug class ("a field acted on but not covered by the HMAC") in this gem is in the webhook‑processing pipeline.

### Title
Webhook `shop` (and `topic`/`webhook_id`) headers are trusted for tenant dispatch despite being excluded from HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook using `Utils::HmacValidator.validate(request)`, but the HMAC only covers the raw request body. The `shop` (and `topic`/`webhook_id`) values, which are read straight from unauthenticated HTTP headers, are handed to the app's handler as the trusted tenant identifier without being part of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers (`x-shopify-shop-domain`, etc.) that are never mixed into the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string`, i.e., the body: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to trust `request.shop` (and other headers) as the identity of the webhook, and dispatches it directly to the app's handler: [4](#0-3) 

The binding that is broken is: `shop authenticated by HMAC` ≠ `shop used as the tenant/session key passed to the handler`. Since every shop installed on a given app shares the same `api_secret_key`, any merchant who has installed the app can capture a genuinely-signed webhook body (with a valid HMAC over that body, computed with the app's shared secret) from an event in their *own* store, then replay that exact raw body/HMAC pair while substituting the `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop as `data.shop` while carrying attacker-chosen body content.

### Impact Explanation
This breaks the tenant isolation boundary the HMAC is supposed to guarantee: the gem asserts "this webhook is authentic," but the authenticity only applies to the bytes of the body, not to which shop it's attributed to. Any downstream app logic that uses `data.shop` from `WebhookMetadata` to select a session, tenant record, or authorization scope (a standard and encouraged pattern per this gem's own webhook docs) can be tricked into processing attacker-supplied webhook content under a victim shop's identity — a cross-tenant data/integrity violation.

### Likelihood Explanation
Any user who can install the app on their own shop (an "unprivileged internet user" relative to other tenants) can trigger webhooks with real events, capture the raw body + signature, and replay them with a forged `shop-domain` header value. No access token, `client_secret`, or privileged access is required — only the ability to install the app on any shop and intercept/replay the webhook HTTP request, which is exactly the class of unauthenticated request this gem's `Registry.process` is meant to validate.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook_id`) in the signed payload used for HMAC verification, or otherwise cryptographically bind the `shop` value to the verified body (e.g., require the caller to supply an out-of-band, pre-registered shop-to-secret mapping and verify per-shop). At minimum, document that `data.shop` from `WebhookMetadata` must not be trusted as a tenant boundary unless additional verification (e.g., comparing against a known webhook subscription id previously registered for that shop) is performed by the host application.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook event (e.g., `orders/create`) with attacker-controlled body content.
2. Shopify delivers the webhook with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's shared `api_secret_key`, plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the identical raw body and `hmac-sha256` header to the app's webhook endpoint, but rewrites `x-shopify-shop-domain` (and optionally `x-shopify-topic`) to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) validates successfully because it only checks the body bytes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_body, ...)` to the app's handler, which processes attacker-controlled data under the victim shop's tenant identity.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
