### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` entirely from HTTP headers, but the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body [1](#0-0) . Since these headers are excluded from the signed data, an attacker who has legitimately received one valid `(body, hmac)` pair for their own shop can replay it to the app's webhook endpoint while altering the `x-shopify-shop-domain` header to name a different (victim) shop. The HMAC check will still pass because it only validates the body, not the header claiming which shop the event belongs to.

### Finding Description
`Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string`, itself equal to just `@raw_body` [2](#0-1) [3](#0-2) . The identity fields `topic`, `shop`, `webhook_id`, and `api_version` are read straight off request headers with no cryptographic binding to the body's HMAC [4](#0-3) . Because Shopify uses a single shared `api_secret_key` (or `old_api_secret_key`) to sign all webhooks for the app across every installed shop [5](#0-4) , any shop where the app is installed can capture a legitimately-signed webhook body it receives for its own store, then resend that same body with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`/`webhook-id`) header pointing at another tenant's shop. `Registry.process` passes `request.shop` straight into the handler's `WebhookMetadata` unauthenticated with respect to the signature [6](#0-5) , so the handler executes believing the event originated from the spoofed shop.

This breaks the intended binding: `shop-domain header == shop that produced/owns the HMAC-signed body`. The HMAC validates "this body was signed with our secret" but not "this body belongs to this shop."

### Impact Explanation
Any app handler logic keyed off `WebhookMetadata#shop` (e.g., looking up per-shop session/access token, updating shop-scoped records, or triggering shop-specific side effects) can be triggered under an attacker-chosen shop identity, since the shop label is fully unauthenticated. This is a cross-tenant confused-deputy condition: a shop with the app installed (an "unprivileged" but real installer) can forge webhook events attributed to a different merchant, without needing that merchant's credentials.

### Likelihood Explanation
Exploitation requires only that the attacker be a real merchant who has installed the app (so they receive at least one legitimate signed webhook for their own shop) and can POST to the app's public webhook endpoint with modified headers — no `api_secret_key`, access token, or privileged account for the *victim* shop is needed. The barrier is low: capture one webhook, replay it with a different `shop-domain` header.

### Recommendation
Bind the shop/topic identity into the signed material, or otherwise verify it out-of-band: e.g., include `shop`, `topic`, and `webhook_id` in the string that is HMAC-verified (mirroring how `AuthQuery#to_signable_string` includes `shop` [7](#0-6) ), or require the caller to cross-check `request.shop` against the session/shop the webhook subscription was registered for before trusting it in the handler.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker receives a legitimate webhook: body `{"id":1}` with header `x-shopify-hmac-sha256: <valid HMAC of body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `HmacValidator.validate(request)`, which only hashes `@raw_body` and succeeds [8](#0-7) .
4. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the payload/signature never authenticated that shop [9](#0-8) .
