This confirms the finding: the documentation explicitly states `Registry.process` "will verify the request did indeed come from Shopify" (docs/usage/webhooks.md:125), and hands the app a `WebhookMetadata` with `shop` presented as a verified field alongside `topic` and `body` (docs/usage/webhooks.md:12-17) — but only the raw body is actually covered by the HMAC.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` in `Registry.process` verifies the HMAC over the JSON body alone. The `shop` (and `topic`) values are read straight from HTTP headers that are never part of the signed material, yet `Registry.process` forwards `request.shop` into `WebhookMetadata` as if it were an authenticated identity, and the documentation states processing "will verify the request did indeed come from Shopify."

### Finding Description
`lib/shopify_api/utils/hmac_validator.rb` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it with `OpenSSL.secure_compare` against the `hmac` value. [1](#0-0) 
For `ShopifyAPI::Webhooks::Request`, `to_signable_string` is defined to return only the raw body: [2](#0-1) 
Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers, which are outside the signed data: [3](#0-2) 
`Registry.process` validates only this body-bound HMAC, then dispatches the handler using the unauthenticated `request.shop` value as the tenant identifier: [4](#0-3) 
This breaks the intended identity binding: `HMAC(body) == valid` should imply `shop-header == the shop that produced this body`, but the equality actually enforced is only `HMAC(body) == valid`; `shop` is fully attacker-controlled. Any party who can obtain one validly-signed webhook body (e.g., by installing the app on their own store and triggering an event, since HMAC-SHA256 is computed with the app's real `api_secret_key` over content the attacker can influence) can replay that exact body with an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header. `HmacValidator.validate` still returns `true`, and `WebhookMetadata.shop` will contain the attacker-chosen victim shop domain. [4](#0-3) 
The gem's own documentation reinforces the false trust: it states `Registry.process` "will verify the request did indeed come from Shopify" and describes `data.shop` simply as "The shop domain of the webhook," implying it is a verified value. [5](#0-4) [6](#0-5) 

### Impact Explanation
Apps that key tenant-scoped logic (data writes, uninstall/cleanup, billing state, multi-tenant record lookups) off `WebhookMetadata#shop` — exactly as the documented handler example does (`shop_domain: data.shop`) — can be made to act on behalf of, or against, a shop the attacker does not control, using only a webhook body legitimately signed for the attacker's own shop. This is a cross-tenant identity-binding failure reachable by an unprivileged internet user who merely needs to operate any store that installs the app (or otherwise obtain one signed body/HMAC pair) to then target arbitrary victim shop domains.

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP endpoint by design (Shopify calls it directly). The only barrier is possessing one valid `(body, hmac)` pair signed with the app's `api_secret_key` — trivially obtainable by installing the app on any shop (including a free/trial shop) and observing its own legitimate webhook deliveries. No access token, secret leakage, or privileged access is required.

### Recommendation
Bind the `shop` (and `topic`) header values into the signed material the gem verifies, or explicitly document/require that consumers cross-check `request.shop` against a known/registered shop list before trusting it, rather than presenting it as verified inside `WebhookMetadata`. At minimum, `HmacValidator`/`Request` should not imply header fields are authenticated when only the body is covered by the signature.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, and configures/triggers a webhook topic whose JSON body content they influence (or simply captures any legitimately delivered webhook, e.g. `app/uninstalled` with body `{}`).
2. Attacker captures the real request: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = Base64(HMAC-SHA256(api_secret_key, B))` — a value the attacker cannot forge but legitimately received.
3. Attacker sends a new POST to the app's webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only look at the body, so `Utils::HmacValidator.validate` returns `true`. [7](#0-6) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: {}, ...)`, and any app logic trusting `data.shop` as an authenticated tenant identifier now performs an action attributed to `victim-shop.myshopify.com` triggered entirely by the attacker.
