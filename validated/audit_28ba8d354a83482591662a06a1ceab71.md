## Finding: `Oauth.begin_auth` / `Oauth.validate_auth_callback` never validate the `shop` value against the Shopify domain format before it is used as the request host for the token exchange that carries `client_secret`

### Summary
The authorization-code-grant flow in `lib/shopify_api/auth/oauth.rb` never validates that the `shop` value is a legitimate Shopify domain before using it (a) to build the authorize redirect host in `begin_auth`, and (b) to construct the `HttpClient` that POSTs the app's `client_id`/`client_secret` to obtain an access token in `validate_auth_callback`. Meanwhile, the library ships a dedicated `ShopValidator` utility that other auth flows (`client_credentials`, `refresh_token`, `token_exchange`) reference before trusting a shop value, but the oldest OAuth flow (`begin_auth`/`validate_auth_callback`) omits this check entirely.

### Finding Description
`Oauth.begin_auth` builds the authorization redirect purely from the caller-supplied `shop` string: [1](#0-0) 

`Oauth.validate_auth_callback` then only checks the HMAC over the callback query and the state-cookie match; it never re-validates that `auth_query.shop` conforms to a `*.myshopify.com` domain before using it: [2](#0-1) 

The `shop` value is used to build a `null_session`, which `HttpClient` turns directly into the request host when no `api_host` override is configured, and the request body carries the app's `client_id`/`client_secret`: [3](#0-2) 

The HMAC in `AuthQuery` does cover `shop` (`to_signable_string` includes it), so this specific value can't be tampered with in-flight once Shopify has signed a callback: [4](#0-3) 

However, that HMAC only proves the callback parameters weren't altered after Shopify's redirect — it says nothing about what `shop`/host was fed into `begin_auth` in the first place. `begin_auth` accepts and blindly trusts the caller's `shop` parameter as a domain to redirect the browser to, with no validation, and the documentation itself only says the value "should" be in `{exampleshop}.myshopify.com` form — it is not enforced by the library: [5](#0-4) 

By contrast, other OAuth entry points in the same library (`client_credentials.rb`, `refresh_token.rb`, `token_exchange.rb`) reference a `ShopValidator` utility to gate the shop value before it is trusted as a request host, based on grep results across the repo, whereas `oauth.rb` contains no such reference. This is an inconsistency in the identity binding: "shop value accepted by `begin_auth`" is not equal to "shop value validated as a genuine Shopify domain" in this particular flow, even though the library elsewhere enforces that equality.

### Impact Explanation
If a host application passes an unvalidated, user-influenced `shop` value into `begin_auth` (which the library's own API surface permits, since it performs no validation itself), the resulting authorize URL host and the subsequent `validate_auth_callback` token-exchange request host are both derived from that same unvalidated string. Because `validate_auth_callback` builds its `HttpClient` from `auth_query.shop` with no independent domain check, a crafted/replayed flow that gets a validly-HMAC'd callback for an attacker-controlled "shop" string would cause the library to POST the app's `client_id` and `client_secret` to that attacker-controlled host — an SSRF that exfiltrates the app's `client_secret`.

### Likelihood Explanation
Exploitation requires the host application to relay an unsanitized `shop` parameter into `begin_auth`/`validate_auth_callback`, and it does not by itself let a fully unprivileged internet user forge a passing HMAC out of thin air. The severity therefore hinges on the fact that this library provides zero defense-in-depth here (no `ShopValidator` call), unlike every other OAuth entry point in the same codebase, which is a real gap but its exploitability is contingent on how permissively the calling app forwards `shop`.

### Recommendation
Call the existing `ShopValidator` (or equivalent domain-format check) on the `shop` value at the start of both `Oauth.begin_auth` and `Oauth.validate_auth_callback`, exactly as is already done in `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`, so that the identity binding "trusted shop host" == "validated `*.myshopify.com` domain" holds consistently across every OAuth flow the library exposes, and so `client_secret` can never be sent to a host that hasn't passed that check.

### Proof of Concept
Not independently reproducible from the index alone: confirming actual exploitability requires reading the exact `ShopValidator` regex/behavior (`lib/shopify_api/utils/shop_validator.rb`) and how a real host application wires an inbound `shop` request parameter into `begin_auth`, neither of which was fully retrievable in this session. I recommend a Devin session with full repo/file access to inspect `lib/shopify_api/utils/shop_validator.rb` in full and to build a concrete end-to-end repro (crafted `shop` → `begin_auth` → forged/legit HMAC callback → `validate_auth_callback` → outbound request host) before treating this as a confirmed, exploitable vulnerability rather than a design inconsistency.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI

            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
