### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts the `shop` value taken from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while the HMAC signature that is verified only covers the raw request body. Because the header is not part of the signed data, any shop that legitimately installs the app can capture one of its own genuinely-signed webhook deliveries and replay it with the `shop-domain` header changed to a different (victim) shop, producing a request that still passes HMAC validation but is attributed to the wrong tenant.

### Finding Description
The bug class from the report is a signature/identity-binding mismatch: data that is *acted on* (the destination/identity context) is not part of the data that is *cryptographically bound* by the signature. In the Opera-Bridge case, the chain/contract identity wasn't in the signed hash. Here, the analogous binding is:

`shop used to route/attribute webhook data == shop covered by the HMAC signature`

This equality does not hold:

- `Webhooks::Request#hmac` is read straight from the `hmac-sha256` header, and `#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

- The `shop` accessor pulls straight from the `shop-domain` header, which is never included in the signed string: [3](#0-2) 

- `HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it against `verifiable_query.hmac`: [4](#0-3) 

- `Registry.process` validates the HMAC, then immediately passes the unauthenticated `request.shop` value on to the app's webhook handler as the tenant identity, with no cross-check against any shop identifier inside the signed body: [5](#0-4) 

Because the signature covers only `@raw_body`, an unchanged body plus its original valid HMAC remains valid no matter what the `shop-domain` header says. An attacker who installs the app on their own shop (an ordinary, unprivileged action requiring no special credentials) receives real, correctly-signed webhook deliveries from Shopify for their own store. They can then resend that exact body/HMAC pair to the app's public webhook endpoint with the `shop-domain` header rewritten to any other merchant's domain. `HmacValidator.validate` still succeeds because it only checks the (untouched) body against the (untouched) signature; `Registry.process` then hands the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This crosses a tenant boundary using only actions available to any unprivileged Shopify merchant who installs the app: no leaked secret, access token, or `client_secret` is needed, and no TLS interception is required. Depending on how the host application's webhook handler uses `data.shop` (e.g., to key per-tenant records, trigger data deletion for mandatory `shop/redact` and `customers/redact` topics, or update per-tenant state), the attacker can inject data or trigger actions against a victim tenant's records — this is a cross-tenant access issue.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate (even free) installer of the target app on their own store, capture one webhook delivery (trivial — they control the receiving endpoint or can sniff their own traffic), and replay it with a modified header to the same publicly reachable webhook endpoint. No special privileges, secrets, or race conditions are needed, making this straightforward to reproduce for any app relying on this gem's `Registry.process`/`Webhooks::Request` for tenant attribution.

### Recommendation
Bind the shop identity into the value that is actually verified. Concretely:
- Include the `shop-domain` header value in the HMAC-signed material (e.g., have `to_signable_string` combine the raw body with the shop/topic/webhook-id headers), or
- Cross-check `request.shop` against a shop/domain identifier embedded inside the verified JSON body before dispatching to the handler, and reject the webhook if they disagree.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers/receives a webhook for a topic the app handles (e.g., `app/uninstalled` or `orders/create`).
2. Shopify sends a POST to the app's webhook endpoint with headers such as `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, and a JSON body.
3. Attacker replays the identical raw body and identical `x-shopify-hmac-sha256` value to the same endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only [4](#0-3) , finds it matches, and `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host app to attribute attacker-controlled webhook data/actions to the victim tenant.
