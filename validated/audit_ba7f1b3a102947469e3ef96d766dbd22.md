### Title
Excessive gas consumption via unbounded quadratic `bytes.concat` loop in `Codec.Encode(Commitment)` — (File: `evm/src/consensus/Codec.sol`)

### Summary
`EcdsaBeefy.verifyMmrUpdateProof` calls `Codec.Encode(commitment)` on a relayer-supplied `Commitment` before any signature is cryptographically validated. `Codec.Encode` rebuilds the `payload` byte string by repeated `bytes.concat` inside a `for` loop, exactly the anti-pattern behind the Go `net/mail` `ParseAddress` CVE (repeated string/byte concatenation causing O(n²) cost). Because `commitment.payload` length and the size of each `Payload.data` element are fully attacker-controlled ABI-decoded values with no bound, an unprivileged relayer can submit a `BeefyConsensusProof` whose commitment carries a large/malformed `payload` array to force quadratic-cost re-hashing before the cheap validity checks (participation threshold, merkle multi-proof) can reject it.

### Finding Description
`Codec.Encode` builds the SCALE-encoded commitment like this: [1](#0-0) 

Each iteration re-copies the entire accumulated `payload` buffer plus the new element, which is the same O(n²) concatenation-in-a-loop pattern flagged in the report (Go's `ParseAddress` building a domain-literal via repeated string concatenation).

This function is invoked directly on attacker-supplied data in the ECDSA BEEFY consensus path: [2](#0-1) 

The `commitment` here comes straight from `abi.decode(proof, (RelayChainProof, ParachainProof))` inside `verify()`, which is the `IConsensusV2` entrypoint any relayer calls via `HandlerV2` when submitting a consensus update: [3](#0-2) 

`Commitment.payload` is an unbounded `Payload[]` where each `Payload.data` is an unbounded `bytes` field: [4](#0-3) 

Order of operations in `verifyMmrUpdateProof`:
1. Cheap threshold check (`checkParticipationThreshold`) — only checks the *count* of votes supplied, not their validity.
2. A linear scan over `commitment.payload` to find the MMR-root payload id.
3. `keccak256(Codec.Encode(commitment))` — the quadratic-cost operation — computed **before** any signature is actually verified against the authority set.
4. Only afterwards does `ECDSA.recover` + `MerkleMultiProof.VerifyProof` reject bogus votes.

Because step 3 happens unconditionally regardless of whether the votes are genuine, an attacker only needs to supply `sigLen` bogus (but correctly counted) votes to pass step 1, then a `payload` array with many/large entries to blow up step 3's cost, before the transaction is rejected in step 4.

### Impact Explanation
This is a gas-griefing / denial-of-service vector on the on-chain BEEFY light client (`EcdsaBeefy`), the consensus verification path that gatekeeps state commitments used across Hyperbridge's message delivery, proof verification, and mint/burn flows. A relayer (unprivileged, no special permissions required to call `verify`/submit a consensus update transaction) can force the contract to spend disproportionate gas re-copying an attacker-grown payload buffer before rejecting the proof. At sufficient payload sizes this can push a legitimate consensus-update transaction toward, or past, the block gas limit, or make honest relayers' updates prohibitively expensive to include (since the cost scales quadratically with attacker-chosen `payload.length`/`data` sizes), stalling the "route unable to deliver messages" condition called out as in-scope — legitimate BEEFY consensus updates (and everything downstream depending on fresh consensus state: state proofs, message delivery, mint/burn) can be delayed or blocked while the contract or mempool absorbs griefing transactions.

Note: because the attacker pays gas for their own transaction, this is not free for the attacker, and the ultimate bound is Ethereum's own block gas limit — so severity is best characterized as a griefing/DoS vector rather than unbounded resource exhaustion (unlike the original off-chain Go CPU-exhaustion bug). Whether the achievable payload sizes here can actually push a legitimate follow-up transaction out of the block gas limit in practice was not confirmed with a concrete gas benchmark; this could not be fully verified without running Foundry gas-profiling, which is outside available tooling here.

### Likelihood Explanation
The path is reachable by any address that can call `EcdsaBeefy.verify` (via `HandlerV2`/`EvmHost` consensus-update dispatch) — no privileged role is needed. The `payload` array size and each `data` bytes length are entirely attacker-controlled via ABI-encoded calldata with no length checks before `Codec.Encode` runs, and the vote-count check that gates entry to this code path only requires the correct number of `Vote` entries, not correct signatures. Likelihood is thus non-trivial, bounded mainly by the attacker's willingness to spend gas.

### Recommendation
- Pre-allocate the output buffer once (e.g., compute total payload length first, then write into a single `bytes memory` buffer with `mstore`/`Bytes` helpers) instead of repeated `bytes.concat` in a loop, eliminating the quadratic behavior.
- Bound `commitment.payload.length` and each `Payload.data.length` to sane maxima (BEEFY commitments in practice carry a small, fixed number of payload items) and revert early if exceeded, before any encoding work is done.
- Reorder `verifyMmrUpdateProof` so signature/authority validity is confirmed as cheaply as possible before the expensive `Codec.Encode`/`keccak256` step is performed on attacker-supplied payload data (e.g., validate array-size bounds immediately after decoding, before any loop-based encoding).

### Proof of Concept
1. Call `EcdsaBeefy.verify(previousState, proof)` (reachable via the relayer path that submits consensus updates through `HandlerV2`) with `proof` ABI-encoding a `RelayChainProof` where:
   - `signedCommitment.commitment.payload` contains one entry with `id == MMR_ROOT_PAYLOAD_ID` and 32-byte `data` (to pass the `mmrRoot` check), followed by N additional `Payload` entries each carrying maximal-size `data` (e.g., tens of KB each), and
   - `signedCommitment.votes` contains `sigLen` garbage `Vote` entries sized to pass `checkParticipationThreshold` for the claimed `authoritySet.len`.
2. Observe gas consumption of `keccak256(Codec.Encode(commitment))` growing quadratically with N/`data` sizes, before the subsequent `ECDSA.recover`/`MerkleMultiProof.VerifyProof` steps reject the forged votes.
3. Compare gas cost against a baseline commitment with a single small payload entry to demonstrate the quadratic-vs-linear discrepancy directly attributable to the `bytes.concat` loop in `Codec.Encode`.

(This PoC could not be executed against the live Foundry test suite in this session; the analysis is based on static code review of `Codec.sol`, `EcdsaBeefy.sol`, and `Types.sol`.)

    function Encode(Commitment memory commitment) internal pure returns (bytes memory) {
        uint256 payloadLen = commitment.payload.length;
        bytes memory payload = bytes("");
        for (uint256 i = 0; i < payloadLen; i++) {
            payload = bytes.concat(
                payload,
                abi.encodePacked(commitment.payload[i].id),
                ScaleCodec.encodeBytes(commitment.payload[i].data)
            );
        }

        return bytes.concat(
            ScaleCodec.encodeUintCompact(payloadLen),
            payload,
            ScaleCodec.encode32(commitment.blockNumber),
            ScaleCodec.encode64(commitment.validatorSetId)
        );
    }
