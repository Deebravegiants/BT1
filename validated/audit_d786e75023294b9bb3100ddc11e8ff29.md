### Title
Webhook `shop` header not bound to HMAC signature enables cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` fields entirely from unauthenticated HTTP headers, while the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body. Any actor who can obtain one validly-signed webhook body (e.g., by installing the app on their own store and receiving a real Shopify webhook) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header, causing the receiving application to process the payload as if it belongs to a different tenant.

### Finding Description
The signable string used for HMAC verification is defined as only the raw body: [1](#0-0) 

Meanwhile, the `shop` accessor — the value the host application uses to identify *which tenant* the webhook belongs to — is read straight from a header with no cryptographic binding to the signature: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header — it never incorporates the `shop`, `topic`, or `webhook-id` headers into the signed material: [4](#0-3) 

`Webhooks::Registry.process` trusts `request.shop` for dispatch after only checking the body HMAC: [5](#0-4) 

This breaks the identity binding: `shop_that_HMAC_authenticates != shop_delivered_to_handler`. The equality that should hold — `shop header ∈ HMAC-covered bytes` — does not; the HMAC covers only `raw_body`, not the `shop` (or `topic`/`webhook-id`) headers used to route/attribute the event.

### Impact Explanation
Shopify webhook signatures are computed using the app's single `api_secret_key`, shared across every shop that has the app installed — it is not per-shop. Consequently, any unprivileged user who installs the app on their own (attacker-controlled) shop will receive genuinely Shopify-signed webhook deliveries for their own store. Because the signature never binds to the `shop` header, that attacker can capture one such (body, hmac) pair and replay it against the app's webhook controller with a forged `x-shopify-shop-domain`/`shopify-shop-domain` header naming a victim shop. `Registry.process` will pass HMAC validation (since the body/hmac pair is legitimate) and will hand the attacker-chosen `topic`/body content to the handler tagged with the victim's shop identity, as seen in `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`. This is a cross-tenant confusion: it lets an unprivileged user forge webhook events attributed to another merchant's shop, which can be leveraged depending on the host application's handler logic (e.g., triggering shop-scoped data mutations, cache invalidation, or fulfillment logic under a false shop identity).

### Likelihood Explanation
Any developer or user who can install the app on a shop they control (a completely unprivileged, self-service action for any app listed or dev-installed) can capture a legitimate signed webhook and replay it with a modified shop header — no access to `api_secret_key`, access tokens, or any privileged credential is required.

### Recommendation
Bind the routing identity fields to the HMAC-verified material. At minimum, include `shop`, `topic`, and `webhook_id` header values in the signable string alongside the raw body (or otherwise cryptographically bind them, e.g., by having `HmacValidator.validate_signature` verify a canonicalized string containing both headers and body), so that a valid signature for one shop/topic cannot be replayed as if it belonged to a different shop or topic.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a normal, unprivileged onboarding flow) and subscribes/receives any webhook topic, capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — both are validly signed with the app's shared `api_secret_key`.
2. Attacker resends this exact `(raw_body, hmac)` pair to the same app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) calls `Utils::HmacValidator.validate`, which succeeds because it only checks the body against the hmac — `lib/shopify_api/utils/hmac_validator.rb:27-31`.
4. The handler is invoked with `WebhookMetadata` carrying `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`, `shop` sourced per `lib/shopify_api/webhooks/request.rb:20-23`), despite the payload never having been issued for that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
