## Title
Webhook `shop`/`topic`/`webhook_id` identity headers are not covered by the HMAC signature, enabling cross‑tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the merchant identity (`shop`), `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are excluded from the signed content. Any actor who can obtain one validly-signed webhook body/HMAC pair (e.g. from their own store where the app is installed) can replay it while substituting the `x-shopify-shop-domain` header for a different, victim shop, and the gem will hand the handler data attributed to the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers and are never part of the signable/verified content: [2](#0-1) 

`Registry.process` verifies only the HMAC (over the body) and then forwards `request.shop` (an unauthenticated header value) to the handler as the tenant identifier, alongside the HMAC-verified body: [3](#0-2) 

`Utils::HmacValidator.validate` confirms this — it only ever calls `verifiable_query.to_signable_string`, which for webhooks is the raw body, never the headers: [4](#0-3) 

This breaks the identity binding: **shop authenticated (HMAC covers only `@raw_body`) ≠ shop acted upon (`request.shop`, read from an unauthenticated header)**. Any client (e.g. a developer running their own store with the same app installed, or any party who can capture one genuine webhook delivery) can take a legitimately Shopify-signed `(body, hmac)` pair and re-send it to the app's public webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header swapped to reference a different shop. Because the gem never cross-checks these header values against anything cryptographically bound to the payload, `WebhookMetadata` will report the victim's `shop` alongside attacker-controlled body content that passed HMAC validation for a *different*, legitimate delivery. Downstream handler logic that uses `shop` to key storage, trigger shop-scoped side effects, or attribute data will process it under the wrong tenant.

This is directly analogous to the reported Tomcat trailer-parsing bug: a boundary (there, "what belongs to which HTTP request"; here, "which body belongs to which shop") is enforced only partially — one side (body integrity) is checked, while an adjacent, security-relevant field (shop identity) is trusted without being included in that check.

### Impact Explanation
This is a cross-tenant integrity issue: it allows an unprivileged actor (anyone who can install the app on any store, including a free/dev store, or otherwise obtain a genuine webhook delivery) to make the host application ingest body content under an arbitrary victim `shop` value, since the gem provides no mechanism binding `shop`/`topic`/`webhook_id` to the HMAC-verified bytes. Depending on how the host app uses `WebhookMetadata#shop`, this can lead to cross-tenant data corruption or cross-tenant action execution — matching the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Moderate-to-high: exploitation requires only obtaining one legitimately-signed webhook (trivially available to anyone who installs the app on their own store) and the ability to send an HTTP request to the app's public webhook endpoint with modified headers — no access to `api_secret_key`, access tokens, or privileged accounts is required.

### Recommendation
Include the security-relevant header values (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content that `Utils::HmacValidator` verifies (e.g., sign `headers + body`, as Shopify's webhook signing already effectively covers only the body — so the gem should additionally validate `shop` against the shop the delivery was registered for/expected, or require the host app to supply the expected shop and compare it explicitly before dispatching to handlers).

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: body `B` plus header `x-shopify-hmac-sha256` (valid, computed by Shopify over `B` with the real app secret).
2. Replay this exact request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)` over `B` (unchanged) → passes.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` — attacker-supplied body now attributed to the victim shop. [5](#0-4)
