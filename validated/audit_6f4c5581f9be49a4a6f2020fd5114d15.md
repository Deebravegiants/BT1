### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, while the `shop` value that the app uses to attribute the webhook to a tenant is read from an unsigned HTTP header. This breaks the equality that should hold: `shop authenticated via HMAC == shop the handler acts on`. An attacker who can obtain one valid `(body, hmac)` pair (e.g., by triggering a webhook on their own installed shop) can replay that exact body/HMAC pair while substituting the `shop-domain` header for a victim shop, and the gem will accept it as authentic for the victim tenant.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing the received HMAC against a signature computed over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body — it does not include the shop domain, topic, or any other header: [2](#0-1) 

The `shop` value used by the rest of the library, however, comes straight from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`), with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC over the body only, then passes the header-derived, unauthenticated `shop` straight into the tenant-identifying `WebhookMetadata` handed to the app's handler: [4](#0-3) 

This is the same bug class described in the external report: a value used to determine "which account/tenant this data belongs to" is not covered by the integrity check that is supposed to authenticate the whole message (analogous to the vault's share price being computed from donated/unverified assets rather than the value actually backing the shares). Here, the equality that should hold is:

`shop bound by HMAC == shop the webhook handler treats as the event's origin`

but in fact:

`shop bound by HMAC == "" (never included in the signable string)`
`shop the webhook handler treats as the event's origin == unauthenticated header value`

### Impact Explanation
An app that has installed webhook handlers keyed by shop domain (e.g., updating per-shop billing state, syncing per-shop data, revoking access on `app/uninstalled`) can be made to apply a legitimately-HMAC'd payload to the wrong tenant. Because the `shop` header is never part of the signed content, any actor capable of producing (or capturing) a valid `(raw_body, hmac)` pair — trivially available to any merchant/app user by installing the app on their own store and triggering the event themselves — can resend that exact body/HMAC to the app's public webhook endpoint with the `shop-domain` header replaced by any victim shop domain. This crosses the tenant boundary named explicitly in the report's Critical bucket ("cross-tenant access"), since the attacker's own webhook content is now attributed to another merchant's account inside the app.

### Likelihood Explanation
Webhook endpoints are typically public HTTP(S) endpoints (that is the point of webhooks), and this gem does not perform any IP-allowlisting or additional binding beyond the documented HMAC-over-body check. Any actor who can install the app on a shop they control (a normal, unprivileged flow) can capture a valid signed payload for an event of their choosing and then replay it toward the same endpoint with a forged `shop-domain` header, requiring no access to `api_secret_key`, tokens, or TLS interception.

### Recommendation
Bind the shop identity to the HMAC-verified content rather than trusting a bare header:
- Look up the expected shop for the delivery via a value that is itself authenticated (e.g., correlate against the `webhook-id`/subscription registered for a known shop, or require the app to independently verify the `shop-domain` header against an actively-tracked, installed-shop allowlist before trusting it), and/or
- Treat the `shop-domain` header as untrusted metadata only, never as the sole tenant key for stateful side effects, unless combined with an application-level check that the shop is currently installed and the specific `webhook-id` was actually registered for that shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an event the app subscribes to (e.g., `orders/create`), capturing the delivered `raw_body` and the `x-shopify-hmac-sha256` header Shopify computed over that body.
2. Attacker sends a POST directly to the app's public webhook endpoint with:
   - the exact same `raw_body`
   - the exact same `x-shopify-hmac-sha256`
   - `x-shopify-topic: orders/create`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `raw_body` only and it matches, so validation passes.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the app's handler with `shop: "victim-shop.myshopify.com"`, even though the payload/HMAC never originated from or was signed with knowledge of that shop — the app now processes attacker-controlled data as belonging to the victim tenant.
