### Title
Relay is underpaid its variable-rate fee for Emporium stateful (wallet-signed) actions, letting the user keep the difference - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.payRelayFees` computes the relay fee differently depending on whether the Emporium operation is "stateless" (`signerAddress == address(0)`) or "stateful" (routed through a persistent `HinkalWallet`, `signerAddress != address(0)`). In the stateless branch it correctly calls `calculateRelayFee(sumAbs, flatFee, variableRate)`, which folds in both the flat fee and the `feeStructure.variableRate` cut. In the stateful branch it instead does `relayFee = flatFee;`, entirely dropping the variable-rate component that the same `circomData.feeStructure` specifies.

### Finding Description
`payRelayFees` in [1](#0-0)  branches on `signerAddress`:

```solidity
if (signerAddress == address(0)) {
    uint256 sumAbs = uint256(-deltaAmountChanges[i]);
    relayFee = $._hinkalHelper.calculateRelayFee(sumAbs, flatFee, feeStructure.variableRate);
} else {
    relayFee = flatFee;
}
```

`calculateRelayFee` ( [2](#0-1) ) is the canonical fee formula used everywhere else in the protocol: `Hinkal._internalTransact` ( [3](#0-2) ) and `ExternalActionSwap.swap` ( [4](#0-3) ) both apply `flatFee` **and** `variableRate` on every withdrawal/output path. Only the Emporium stateful (wallet) branch skips the variable-rate portion of the fee that `circomData.feeStructure.variableRate` specifies for the transaction.

Because the fee actually paid to `relay` is only the flat fee, the remainder of the token balance that should have gone to the relay as the variable-rate cut instead remains part of the Emporium/wallet's net balance change, and is swept into the user's own output UTXO by `handleOut` ( [5](#0-4) ). The proof/balance-equation checks in `Hinkal.sol` ( [6](#0-5)  and `Hinkal.sol` and the `Emporium` balance-change loop ( [7](#0-6) ) do not enforce any specific fee amount — they only verify that whatever was moved is fully accounted for in the resulting UTXOs, so an under-collected fee is silently absorbed into the user's shielded output rather than reverting.

This is structurally analogous to the `reduce_position` bug: a value that a specific state-transition formula is supposed to deduct/allocate to a party (there: margin owed back to the user; here: relay fee owed to the protocol/relay) is computed with an incomplete formula, so the intended recipient never receives the correct amount while the difference silently accrues to the wrong party.

### Impact Explanation
Every Emporium operation that goes through a `HinkalWallet` signer (`signerAddress != address(0)`) and has a nonzero `feeStructure.variableRate` results in the relay being underpaid: it collects only the flat fee, losing the variable-rate share entirely. This matches the "High - theft ... of protocol/relay fees" impact category: the relay/protocol systematically loses fee revenue on the wallet-based Emporium path, while the user who issued the wallet-signed operation keeps the withheld amount in their shielded output.

### Likelihood Explanation
This triggers on every stateful (wallet-signed) Emporium transaction with `feeStructure.variableRate > 0` — no special preconditions, malicious relayer, or privileged role is required; it is a deterministic formula defect reachable by any user who routes an Emporium action through their `HinkalWallet` with a signed `EmporiumStack`.

### Recommendation
Make the stateful branch use the same fee formula as the stateless branch, e.g.:
```solidity
uint256 sumAbs = uint256(-deltaAmountChanges[i]);
relayFee = $._hinkalHelper.calculateRelayFee(sumAbs, flatFee, feeStructure.variableRate);
```
so that `variableRate` is honored regardless of whether the operation is invoked statelessly or via a signed `HinkalWallet` call.

### Proof of Concept
1. User deposits/holds funds routed through their persistent `HinkalWallet` and issues a signed `EmporiumStack` operation with `feeStructure.variableRate = 500` (5%) and `flatFee = X`.
2. `EmporiumUpgradeable.runAction` executes the ops, then calls `payRelayFees` with `stack.signerAddress != address(0)`.
3. In `payRelayFees`, since `signerAddress != address(0)`, `relayFee` is set to `flatFee` only — the 5% variable cut is never computed or sent to `relay`.
4. `sendToRelayFromWallet`/`payRelay` transfers only `flatFee` to the relay ( [8](#0-7) ).
5. The remaining balance (including the un-collected variable fee) is picked up by `handleOut` and transferred to `msg.sender` (Hinkal) as part of the user's new UTXO, so the user's shielded balance keeps value that should have been paid to the relay/protocol.

```text
    function calculateRelayFee(
        uint256 balance,
        uint256 flatFee,
        uint256 variableRate
    ) public pure returns (uint256 relayFee) {
        require(balance >= flatFee, "Relay Fee is over withdraw amount");
        uint256 recipientAmount = ((10000 - variableRate) *
            (balance - flatFee)) / 10000;
        relayFee = balance - recipientAmount;
    }
```
