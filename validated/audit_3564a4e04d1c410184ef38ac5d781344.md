### Title
Panic-inducing fixed-size copy of an attacker-supplied BEEFY vote signature — ([File: evm/rust/src/conversions.rs])

### Summary
`From<Vote> for SignatureWithAuthorityIndex` in `evm/rust/src/conversions.rs` copies a variable-length `bytes` field (`value.signature`, taken from a Solidity `Vote` struct decoded from relayed BEEFY consensus-proof calldata) into a hardcoded `[0u8; 65]` array using `copy_from_slice` without first checking that the source length is exactly 65 bytes. [1](#0-0) 

### Finding Description
`copy_from_slice` in Rust panics if the source slice length does not match the destination length. Here the destination is a hardcoded `TSignature = [0u8; 65]`, but `sig_bytes` comes directly from `value.signature.to_vec()`, i.e., an ABI-decoded `bytes` field from the `Vote` struct that is part of `SignedCommitment`/`RelayChainProof`, which in turn is constructed from relayer-submitted BEEFY consensus proof data (`RelayChainProof` → `MmrProof` → `ConsensusMessage`, used in the BEEFY consensus update path). [2](#0-1) 

Unlike the sibling conversions in the same file, which validate lengths with `try_into()...expect(...)` on fixed-size fields already guaranteed by the Solidity ABI types (`bytes32`, etc.), the `Vote.signature` field is Solidity `bytes` (dynamic length), so nothing in the ABI type system constrains it to 65 bytes before this conversion runs. This is structurally analogous to CVE-2017-16844: a hardcoded buffer/size assumption (`realloc`'d/allocated to a fixed size) is used to receive attacker-controlled variable-length data without validating the length first, causing an out-of-bounds/panic condition instead of a controlled rejection.

By contrast, the codebase elsewhere is careful about exactly this class of bug — e.g. `modules/utils/serde/src/lib.rs`'s `as_utf8_string` deserializer was hardened specifically because `copy_from_slice` from untrusted length-varying input previously panicked and crashed a production RPC worker thread, and tests explicitly regression-guard this pattern. [3](#0-2) [4](#0-3) 

The `Vote → SignatureWithAuthorityIndex` conversion was not given the same treatment.

### Impact Explanation
If `value.signature` is not exactly 65 bytes, `copy_from_slice` panics. In a `no_std`/native Rust process (light-client prover/verifier, or any binding built from this `evm/rust` crate that processes relayed BEEFY proofs before/after the on-chain Solidity path), an uncaught panic here aborts the calling process or worker thread — a denial of service against BEEFY consensus verification/relaying triggered by a single malformed, attacker-supplied relay message. This blocks message delivery routes that depend on BEEFY consensus updates (a "route unable to deliver messages" condition), which matches the accepted impact classes.

### Likelihood Explanation
The trigger requires only that a relayer or any party able to submit/relay a BEEFY consensus proof supplies a `Vote.signature` whose byte length is not 65 (e.g., 0, 64, or 66 bytes) — trivial to construct and does not require any privileged role, valid signature, or successful cryptographic verification, since the panic occurs during struct conversion before verification logic runs.

### Recommendation
Validate `sig_bytes.len() == 65` and return a decode/conversion error (propagate via `TryFrom`/`Result`) instead of using `copy_from_slice` on a value whose length is not statically guaranteed. Mirror the pattern already used in `modules/utils/serde/src/lib.rs::as_utf8_string` and the `ByteVector<N>::decode` length check in `modules/utils/bls-utils/src/ssz/byte_vector.rs`, both of which reject mismatched lengths as ordinary errors rather than panicking. [5](#0-4) 

### Proof of Concept
1. Construct a `Vote` (as part of a `SignedCommitment`/`RelayChainProof`) where `signature` is any `bytes` value whose length is not 65 (e.g., empty bytes or 64 bytes).
2. Submit/relay this as part of a BEEFY consensus proof through the path that invokes `From<Vote> for SignatureWithAuthorityIndex` (via `From<RelayChainProof> for MmrProof`, `signedCommitment.votes.into_iter().map(Into::into)`).
3. `signature.copy_from_slice(&sig_bytes)` at `evm/rust/src/conversions.rs:360` panics because `sig_bytes.len() != 65`, aborting the process/thread handling the proof instead of returning a decode error. [1](#0-0) 

**Caveat / uncertainty**: I could not fully confirm from the index which binary/service links `evm/rust` (e.g., whether it's compiled into an on-chain-callable native verifier, a light-client prover binary, or a test/tooling-only crate) — the `Cargo.toml` and `lib.rs` module wiring were only partially inspected due to tool-call limits. This affects the precise blast radius (whether a panic here crashes an on-chain-reachable process vs. only an off-chain relayer/prover tool); confirming the exact deployment target of `evm/rust` would sharpen the severity assessment.

	/// Deserialize a string into utf8 bytes
	///
	/// The string must be exactly 4 bytes long (bytes, not chars — a 4-char string of
	/// multi-byte codepoints is rejected). Anything else is a deserialization error; this
	/// runs on untrusted RPC input, so it must never panic.
	pub fn deserialize<'de, D, T>(deserializer: D) -> Result<T, D::Error>
	where
		D: serde::Deserializer<'de>,
		T: From<[u8; 4]>,
	{
		let s = <String>::deserialize(deserializer)?;

		// `s.len()` is the utf-8 byte length, which is what the `[u8; 4]` needs to match.
		let bytes: [u8; 4] = s
			.as_bytes()
			.try_into()
			.map_err(|_| serde::de::Error::invalid_length(s.len(), &"a 4-byte utf-8 string"))?;
		Ok(bytes.into())
	}

impl<const N: usize> codec::Decode for ByteVector<N> {
	fn decode<I: codec::Input>(input: &mut I) -> Result<Self, codec::Error> {
		let bytes = Vec::<u8>::decode(input)?;
		if bytes.len() != N {
			return Err(codec::Error::from("ByteVector: decoded length does not equal N"));
		}
		ByteVector::<N>::try_from(bytes)
