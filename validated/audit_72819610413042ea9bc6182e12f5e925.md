### Title
Webhook `shop`, `topic`, and `webhook_id` identifiers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and attribute the webhook are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then trusts these header-derived values verbatim, breaking the intended binding of `shop == the tenant whose secret produced this signature`.

### Finding Description
`Utils::HmacValidator.validate` verifies a request by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it to the supplied signature: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to that body or signature: [3](#0-2) 

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)` — and then dispatches to the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

Because Shopify apps share a single `api_secret_key` across all installed shops, any merchant who has installed the app can legitimately trigger a webhook delivery to themselves and obtain a valid `(raw_body, hmac)` pair signed with that shared secret. Since the HMAC never covers `shop-domain`, `topic`, or `webhook-id`, that attacker can replay the exact same body/HMAC to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header (and/or a different topic in `X-Shopify-Topic`). `Registry.process` will accept it as authentic and hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop.

This is the same class of bug described in the report's identity-binding hint: a field that is *acted on* (`shop`, used exactly like a session key to attribute/authorize the webhook payload) is not *covered by the HMAC* that is supposed to authenticate the request. The documented guarantee in `docs/usage/webhooks.md` — that `Registry.process` "will verify the request did indeed come from Shopify" — is broken with respect to the `shop` identity, since only body integrity is verified, not shop attribution.

### Impact Explanation
This breaks the binding `shop (authenticated by HMAC) == shop (acted on by the handler)`, letting an attacker who is a legitimate but malicious installer of the app cross tenant boundaries: they can inject attacker-controlled webhook payloads that the host application will process as belonging to any other shop of their choosing (as long as they know or guess the victim's `myshopify.com` domain, which is often public/guessable). Depending on which topic-driven handler exists in the host app, consequences include:
- Forcing `app/uninstalled` or `shop/redact` handling for a victim shop, causing the app to delete/corrupt the victim's stored session/access token (denial of the victim's own use of the app).
- Injecting forged `orders/create`, `customers/*`, or other business-data webhooks attributed to a victim shop, corrupting that tenant's data.

This matches the "cross-tenant access" impact category since it lets one tenant force the app to treat their own data/actions as belonging to a different tenant.

### Likelihood Explanation
Any user able to install the target app in their own store (the normal, unprivileged path for any Shopify merchant/app installer) can obtain a valid signed webhook body/HMAC and immediately reuse it against the app's public webhook endpoint with forged headers — no `api_secret_key`, access token, or privileged access required. The only extra step is capturing one legitimately delivered webhook, which is trivial for the attacker's own shop.

### Recommendation
Include the identity fields that are acted upon (`shop-domain`, `topic`, `webhook-id`) in the signed material, or otherwise cryptographically bind them to the HMAC-verified body (e.g., concatenate them into `to_signable_string`, or independently verify `shop` against the shop that was registered for that specific `webhook_id`/topic before dispatching to the handler). At minimum, document clearly that `Registry.process` only authenticates the body and that host applications must independently verify `data.shop` against a known list of shops that installed the app before trusting it.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, subscribing to a topic (e.g. `orders/create`).
2. Shopify sends a webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid HMAC over raw body>`, and some `raw_body`.
3. Attacker records `raw_body` and the valid `X-Shopify-Hmac-Sha256` value (computed using the shared `api_secret_key`).
4. Attacker sends a new HTTP request directly to the app's public webhook route with the same `raw_body`/HMAC but `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`, e.g. `app/uninstalled`).
5. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, `Utils::HmacValidator.validate` succeeds (it only checks `raw_body`), and `Registry.process` invokes the handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim.myshopify.com", body: <attacker's data>, ...)`, causing the host app to act on victim.myshopify.com's behalf using attacker-supplied data.
