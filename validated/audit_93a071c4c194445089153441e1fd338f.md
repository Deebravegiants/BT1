### Title
Webhook `shop` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, never over the `shopify-shop-domain` (or `shopify-topic`/`shopify-webhook-id`) header. `ShopifyAPI::Webhooks::Registry.process` accepts the request as authentic once the body's HMAC matches, then dispatches the handler using `request.shop` taken directly from the unauthenticated header. This breaks the identity binding `shop verified-by-HMAC == shop delivered-to-handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, independent of the signed body: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` only ever verifies `verifiable_query.to_signable_string` (the body) against the HMAC secret — the shop header plays no part in the signature computation: [3](#0-2) 

`Registry.process` gates entirely on this body-only HMAC check, and then trusts `request.shop` (the unauthenticated header) when building the `WebhookMetadata` passed to the host application's handler: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop installed on that app (not per-tenant), any merchant who has installed the app can legitimately receive a validly-HMAC-signed webhook for their **own** shop. Since the signature never binds the `shop-domain` header, that same `(raw_body, hmac)` pair remains valid if replayed to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a different, victim shop. `Registry.process` will accept it (HMAC over body matches) and hand the handler a `WebhookMetadata` claiming the body originated from the victim shop — a cross-tenant identity spoof achieved without needing the victim's or the app's secret at all beyond what the attacker's own tenant access already grants.

### Impact Explanation
This allows cross-tenant confusion: a host application's webhook handler (e.g. one that updates per-shop billing state, order records, or redact/data-request flows keyed by `WebhookMetadata#shop`) can be made to process attacker-controlled payload data under another merchant's identity, since the gem-provided authenticity guarantee (`Utils::HmacValidator.validate`) does not actually authenticate the `shop` field the handler receives. This matches the Critical bucket "cross-tenant access" since the shop-scoped trust boundary the library is supposed to enforce is bypassed.

### Likelihood Explanation
Medium-to-High: the attacker only needs to be a legitimate, unprivileged merchant on the same app (installable by anyone) to obtain real, validly-signed webhook bodies for their own shop, then replay them with a modified `shop-domain` header to the app's public webhook endpoint. No secret key, access token, or privileged access is required beyond ordinary app installation.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable string that `Utils::HmacValidator` verifies, or otherwise cryptographically bind the shop identity to the signed payload before `Registry.process` trusts `request.shop` for dispatch, matching Shopify's documented practice of verifying the full webhook context rather than the body alone.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) so Shopify sends a validly HMAC-signed webhook, e.g. body `{"id":1}` with header `shopify-hmac-sha256: <valid signature over body>` and `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the same raw body and same HMAC header to the app's webhook endpoint, but replaces the header with `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `Utils::HmacValidator.validate` passes because the signature only covers `raw_body`, per [1](#0-0) .
4. `Registry.process` calls `handler.handle` with `WebhookMetadata.new(... shop: request.shop ...)`, i.e. `shop: "victim-shop.myshopify.com"`, per [4](#0-3) , causing the host app to process attacker data as if it came from the victim tenant.
