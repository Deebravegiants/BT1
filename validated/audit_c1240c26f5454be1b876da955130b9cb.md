### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Finding Description
Shopify webhook requests are validated by `ShopifyAPI::Webhooks::Registry.process`, which calls `Utils::HmacValidator.validate(request)` before dispatching the payload to the registered handler: [1](#0-0) 

The HMAC is computed over `Request#to_signable_string`, which returns **only the raw request body**: [2](#0-1) 

However, the `shop` value that is handed to the application's handler as the merchant/tenant identity is read straight from an HTTP header, which is **not** included in the signed bytes at all: [3](#0-2) 

and it is passed to the handler unauthenticated: [4](#0-3) 

The identity binding the gem implicitly claims to guarantee is:

```
shop used by handler (WebhookMetadata#shop) == shop that produced/authorized this signed body
```

But the actual check only proves:

```
HMAC-SHA256(raw_body, client_secret) == received_hmac
```

Since `client_secret` is shared across **every merchant** that installs the app, any attacker who has installed the app on their own (attacker-controlled) shop can:
1. Trigger a legitimate webhook delivery for their own shop, capturing a valid `(raw_body, hmac)` pair signed with the app's `client_secret`.
2. Replay that exact `raw_body`/`hmac` pair directly to the app's public webhook endpoint, but substitute the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain.
3. `HmacValidator.validate` still passes, because it only checks the raw body against the secret — it never checks that the `shop` header matches the shop that actually produced the signed payload.
4. `Registry.process` then invokes the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, while the body content is the attacker's own (fully attacker-controlled) data.

This breaks the tenant boundary this library is documented to enforce: the app never gets cryptographic assurance that the `shop` reported in `WebhookMetadata` is the shop that actually owns the signed payload contents.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged internet user (any developer able to install the app on a free/dev shop — no `api_secret_key`, access token, or credential leak required) can make the app process attacker-supplied webhook data under a victim shop's identity. Any host application that trusts `WebhookMetadata#shop` to route updates/deletes/state changes to per-shop storage (a normal and expected usage pattern for this gem, e.g. updating customer records, order state, or app-uninstalled handling for "shop") can be tricked into writing attacker-controlled data into another tenant's records, or forging administrative events (e.g., `app/uninstalled`) against a shop the attacker does not own. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic: no special credentials are needed beyond the ability to install the target app on any Shopify store (including a free development store the attacker fully controls), which is normal, unprivileged access. Capturing one's own webhook `(body, hmac)` pair and replaying it with a different `shop` header against the app's public webhook endpoint requires no cryptographic secret and no interaction with the victim.

### Recommendation
Do not treat the `shop` header as authenticated purely because the request's HMAC passes. Either:
- Include the `shop` (and ideally `topic`, `webhook-id`) in the signed material verified against the registered/expected shop for that delivery, or
- Cross-check the `shop` header against an independently-verified source (e.g., confirm the shop is the one for which this specific webhook subscription/session was registered) before trusting `WebhookMetadata#shop`, or
- At minimum, document prominently that `Request#shop` is unauthenticated and must not be used as a sole tenant-routing key without additional verification (e.g., verifying the shop exists in the app's own installed-shops table before acting).

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app there,
# so Shopify sends them a legitimately-signed webhook:
raw_body = '{"id":123,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)
captured_hmac_b64 = Base64.encode64(hmac)   # attacker now has a *valid* signature for raw_body

# Attacker replays the same body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => captured_hmac_b64,
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # <-- forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) returns true (it only checks raw_body against the secret).
# The handler is invoked with WebhookMetadata#shop == "victim-shop.myshopify.com",
# even though "victim-shop.myshopify.com" never sent or authorized this payload.
```
