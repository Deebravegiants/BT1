### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` value used to identify the tenant is read from the `x-shopify-shop-domain` header, which is never included in the HMAC-signed material.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and compares it against `request.hmac`: [1](#0-0) 

`Request#to_signable_string` returns `@raw_body` only: [2](#0-1) 

but `shop` is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, outside of the signed payload: [3](#0-2) 

After a successful HMAC check, `process` passes `request.shop` straight into the handler as the tenant identity for the webhook, with no additional binding to the signed body: [1](#0-0) 

Because the app uses a single, global `Context.api_secret_key` to sign/verify every webhook regardless of shop, any body+HMAC pair that is valid for one shop's webhook is *also* a valid body+HMAC pair when replayed with a different `shop-domain` header — the identity is never part of the equality the HMAC actually checks. This breaks the intended binding:

`hmac_valid(body, secret) == true` should imply `shop_claimed == shop_that_produced_this_body`, but the code only verifies `hmac_valid(body, secret) == true`, with `shop` supplied out-of-band and unauthenticated.

This is the same bug class as the Sherlock H-6 report: a value that participates in a security decision (there, `_collateralAmount`; here, `shop`) is not actually covered/bound by the verification mechanism that is supposed to protect it (there, the `STANDARD_EXPANSION_FACTOR` multiplication silently weakened the collateral check; here, the omission of `shop` from `to_signable_string` silently weakens the tenant-identity check).

### Impact Explanation
Any party capable of triggering (or capturing) one legitimate, correctly-HMAC'd webhook delivery for a given raw body (e.g. by installing the app on their own store, or via a `customers/data_request`/`shop/redact` mandatory webhook, or any webhook whose body content is attacker-influenced) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `Registry.process` will accept it as authentic and invoke the registered handler with `WebhookMetadata#shop` set to the attacker-chosen shop string, since nothing re-derives or cross-checks `shop` against the signed content. Any host application that keys per-tenant data lookups/writes off `data.shop` (the documented and expected usage pattern for this gem) can be made to attribute a webhook payload to the wrong merchant — a cross-tenant confusion that can lead to acting on/exposing another merchant's records depending on the handler logic.

### Likelihood Explanation
Exploitation requires the ability to send an HTTP POST directly to the app's webhook endpoint with attacker-controlled headers, and possession of at least one valid `(body, hmac)` pair — obtainable trivially by any developer/merchant who installs the app on their own store and observes their own legitimate webhook deliveries (unprivileged, no special secret needed). The `shop` header spoof itself needs no cryptographic material at all.

### Recommendation
Bind the `shop` identity into the verified material, e.g. include the `shop-domain` header (and/or `topic`, `webhook_id`) in `to_signable_string`, or independently verify that `request.shop` matches an expected/registered shop before trusting it — matching how `AuthQuery#to_signable_string` in `lib/shopify_api/auth/oauth/auth_query.rb` correctly folds `shop` into the signed parameters for OAuth callbacks. At minimum, the gem should document prominently that `WebhookMetadata#shop` is *not* cryptographically authenticated and must not be trusted for tenant identification without an independent check.

### Proof of Concept
1. App merchant A installs the app; Shopify delivers a webhook with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker captures `(B, HMAC)` (trivial since they are shop A's own merchant/admin, or the body is otherwise attacker-supplied, e.g. via a GDPR mandatory webhook whose content originates from a self-service request).
3. Attacker POSTs to the app's webhook endpoint with the same `B` and same `hmac-sha256` header, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (the victim shop).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` — it passes because `B` and the HMAC are unchanged. [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"shop-b.myshopify.com"`, despite the body never having been produced for/by shop B. [5](#0-4)
