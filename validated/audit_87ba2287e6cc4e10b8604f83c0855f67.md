### Title
Unauthorized `TransferToGasKey` donations from any account can permanently block key/account deletion via `GasKeyBalanceTooHigh`, griefing victims with repeated failed-deletion gas costs - ([File: runtime/runtime/src/actions.rs])

### Summary
`check_actor_permissions` places `Action::TransferToGasKey(_)` in the same "no actor restriction" bucket as `Action::Transfer(_)`, meaning **any account can send a receipt that funds another account's gas key**, exactly like anyone can send a plain NEAR transfer to any account. [1](#0-0)  This mirrors the reported pattern: a party outside the victim's control can push tokens into a balance that gates an important state-machine trigger, forcing the victim into a costly or blocked state.

### Finding Description
`action_transfer_to_gas_key` blindly adds `action.deposit` to the target gas key's `GasKeyInfo::balance` for the given `account_id`/`public_key`, with no check that the caller is the account owner: [2](#0-1) 

Deletion of a gas key (`delete_gas_key`) or of the whole account (`action_delete_account`) enforces a hard cap, `GasKeyInfo::MAX_BALANCE_TO_BURN = 1 NEAR`: if the gas key balance (or aggregate for account deletion) exceeds this cap, the delete action fails with `GasKeyBalanceTooHigh` instead of succeeding: [3](#0-2) [4](#0-3) [5](#0-4) 

Because `TransferToGasKey` requires no relationship between predecessor and receiver, an attacker who observes a victim's gas key balance sitting near the `MAX_BALANCE_TO_BURN` threshold (or who front-runs a `DeleteKey`/`DeleteAccount` transaction) can send a tiny `TransferToGasKey` deposit that tips the balance over the threshold. Any subsequent `DeleteKey`/`DeleteAccount` transaction from the victim then fails with `GasKeyBalanceTooHigh`, exactly as the DCA "swap trigger" in the report keeps firing/failing due to attacker-controlled dust donations that the victim did not ask for and cannot prevent.

### Impact Explanation
- The victim's transaction fails (`ActionErrorKind::GasKeyBalanceTooHigh`), but the victim still pays for the gas burnt executing/validating the failed `DeleteKey`/`DeleteAccount` action, just like the DCA bot repeatedly executing negligible swaps at the victim's gas expense.
- The victim cannot reach their intended "exit" state (deleting the key/account) without first issuing an additional `WithdrawFromGasKey` transaction (extra gas cost), and the attacker can repeat the donation to re-block deletion, turning this into a repeatable griefing loop — directly analogous to "the bot will not unsubscribe the user... attacker can ensure will never be true."
- This is an unprivileged, permissionless action reachable purely by submitting ordinary transactions/receipts (no validator or P2P access needed), fitting the in-scope "action execution / balance accounting / access-key authorization" surface.

### Likelihood Explanation
High: `TransferToGasKey` is a standard, always-available action once `GasKeys` (protocol feature, stable by v85) is enabled; it requires no special permission, no large deposit (an attacker only needs enough to push the balance a few yoctoNEAR over `MAX_BALANCE_TO_BURN`), and gas-key public keys are visible on-chain via account state queries, making targeting straightforward.

### Recommendation
Restrict `Action::TransferToGasKey` to require `actor_id == account_id` (i.e., only the account itself, via its own access key or through a delegate action it authorized, may top up its own gas keys), consistent with how `AddKey`/`DeleteKey` are actor-restricted. Alternatively, decouple the deletion threshold check from unsolicited third-party deposits, e.g., by refunding/rejecting excess deposits beyond `MAX_BALANCE_TO_BURN` at transfer time rather than only at deletion time, or by allowing deletion to withdraw-then-burn only up to the cap and refund the remainder to the beneficiary instead of failing outright.

### Proof of Concept
1. Victim creates a gas key on `alice.near` with `GasKeyInfo.balance = 0.9 NEAR` (below `MAX_BALANCE_TO_BURN = 1 NEAR`).
2. Attacker (`mallory.near`, unrelated account) submits a transaction to `alice.near` containing a single `TransferToGasKeyAction { public_key: <alice's gas key>, deposit: 0.2 NEAR }`. Because `check_actor_permissions` imposes no actor restriction on `TransferToGasKey` [1](#0-0) , this succeeds and the gas key balance becomes `1.1 NEAR`, as computed in `action_transfer_to_gas_key` [6](#0-5) .
3. Victim (`alice.near`) submits `DeleteKeyAction { public_key: <gas key> }`. `delete_gas_key` checks `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN` (1.1 NEAR > 1 NEAR) and returns `GasKeyBalanceTooHigh`, so the delete fails and the key remains, while the victim's transaction still burns gas. [7](#0-6) 
4. Attacker can repeat step 2 after the victim withdraws funds via `WithdrawFromGasKey`, indefinitely griefing the victim's ability to clean up/delete the key or account and wasting gas on every failed attempt — the on-chain analog of the report's "negligible ERC20 donation forces repeated wasted-gas execution and blocks the intended exit."

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
