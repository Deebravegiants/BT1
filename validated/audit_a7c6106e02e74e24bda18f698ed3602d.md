This confirms the vulnerability: the gem's own documentation explicitly tells developers to trust `data.shop` from the webhook handler as "The shop domain of the webhook" [1](#0-0) , and `Registry.process` passes `request.shop` straight into `WebhookMetadata` after only checking `Utils::HmacValidator.validate(request)` [2](#0-1) . But the HMAC only ever covers `@raw_body` [3](#0-2) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers [4](#0-3) .

### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw body only, but the `shop` (and `topic`/`webhook_id`/`api_version`) values that `Registry.process` hands to the app's handler come from HTTP headers that are not included in the signed content. Since a single app-level `client_secret` (`Context.api_secret_key`) is shared across every merchant/shop installed on the app, any attacker who is themselves a legitimate merchant (or otherwise able to submit an HTTP request to the app's public webhook endpoint with a validly-signed body) can present a genuine `hmac` for one payload while forging the `shop-domain` header to name a different, victim shop.

### Finding Description
The equality that should hold is:

`hmac_verified(content) == content acted upon by the handler`

In `Webhooks::Request`, `to_signable_string` only returns `@raw_body`: [3](#0-2) 

But `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from headers, independent of the signed body: [4](#0-3) 

`Registry.process` verifies only the HMAC of the body, then trusts `request.shop`/`request.topic`/etc. wholesale when building `WebhookMetadata` for the app's handler: [5](#0-4) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e., the body: [6](#0-5) 

Because the same `api_secret_key` is used to sign webhooks for every shop that has installed the app, a valid `(raw_body, hmac)` pair obtained from a webhook fired on the attacker's own shop remains valid HMAC-wise no matter what `shop-domain` header value accompanies it. An attacker can therefore trigger a legitimate webhook against their own store (obtaining a real signed body/HMAC pair), then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` header (and optionally `topic`/`webhook_id`) with a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` forwards the attacker-chosen `shop` value straight to the app's handler as though it were authentic.

This breaks the intended binding: `shop-domain header == shop that produced the signed body`. The gem provides no mechanism to prove that binding; it is left entirely to headers that carry no cryptographic linkage to the signed payload, unlike the OAuth callback flow in the same library, where `AuthQuery#to_signable_string` deliberately folds `shop` into the HMAC-covered string: [7](#0-6) 

### Impact Explanation
This is a cross-tenant integrity issue reachable by an unprivileged internet user who is (or becomes) a legitimate merchant on the app (installing a free/trial app is not a privileged credential in the sense excluded by the rules — it grants no access to the victim's tenant or the app's secrets). By spoofing the `shop-domain` header, they can cause the host application to process attacker-authored webhook data (order data, product data, GDPR/mandatory topics, etc.) as though it originated from a different, victim shop. Depending on how the host app keys its per-shop database records or triggers actions off `data.shop` (as the gem's own docs instruct at docs/usage/webhooks.md:24-27), this can lead to cross-tenant data corruption, false attribution of events to a victim shop, or spoofed mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) against a shop that never requested them.

### Likelihood Explanation
Likelihood is high for any app using the gem's documented webhook processing path as-is: the webhook endpoint is necessarily public (Shopify must be able to POST to it), the shared secret means the same HMAC key validates payloads for every installed shop, and nothing in `Request` or `Registry.process` binds the header-derived `shop` to the HMAC-covered body.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable content (or otherwise cryptographically bind them to the body), mirroring what `AuthQuery#to_signable_string` already does for the OAuth callback. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop-domain header so `HmacValidator.validate` cannot be satisfied by a body signed for one shop while a different shop is claimed in the header.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers a webhook subscribed by the app (e.g. `orders/create`), capturing the raw POST: headers (`shopify-hmac-sha256: <H>`, `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`, ...) and `raw_body: B`.
2. Attacker replays this exact request to the app's public webhook endpoint but rewrites the `shopify-shop-domain` header to `victim.myshopify.com`, keeping `raw_body: B` and `shopify-hmac-sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim.myshopify.com", ...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, causing the host application to process attacker-controlled data under the victim shop's identity.
