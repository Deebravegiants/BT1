This confirms the finding: `cookie_session_id` in `lib/shopify_api/utils/session_utils.rb` returns the raw, unauthenticated cookie value directly as the session lookup key, with no HMAC/signature binding it to a prior OAuth-issued value — this is exactly the "session id derived from unauthenticated bytes" pattern from the rules, analogous to the Wildcat H-03 access-control-binding gap.

### Title
Non-embedded session lookup trusts a raw, unsigned cookie value as the session identifier - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps, `ShopifyAPI::Utils::SessionUtils.current_session_id` resolves the active session purely from the `shopify_app_session` cookie's raw value, with no cryptographic binding between that value and the session it was originally issued for.

### Finding Description
When the OAuth callback completes for a non-embedded app, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the session cookie value to `session.id`, which is deterministically derived as `"offline_#{shop}"` or `"#{shop}_#{user_id}"` [1](#0-0) [2](#0-1) . This plaintext session id is the literal cookie value — the `SessionCookie` struct carries only `name`, `value`, and `expires`, with no signature or MAC field [3](#0-2) .

When retrieving the active session, `SessionUtils.current_session_id` (for non-embedded apps, and as the embedded fallback path) reads this cookie value directly via `cookie_session_id(cookies)` and returns it as-is to be used as the lookup key into the host application's session store [4](#0-3) [5](#0-4) . There is no verification step anywhere in this gem confirming that the value the client presents was actually the one this library generated during a legitimate OAuth callback (e.g., no HMAC-signed cookie, no `secure_compare` against a server-side nonce, no re-derivation from a still-valid, previously-verified state).

Because the offline id format `"offline_#{shop}"` is fully deterministic and depends only on the publicly-known shop domain (e.g. `offline_test-shop.myshopify.com`), and the online id format `"#{shop}_#{user_id}"` depends only on the shop domain plus a typically-small, often-guessable numeric user id, an attacker who can influence or set this cookie for the victim's browser (e.g. via a subdomain cookie-tampering vector, a shared/misconfigured cookie domain, or any injection point in the host app that reflects attacker-supplied cookie values) can supply a forged session id for a shop they do not control and have the host application's session store resolve it to that shop's real, persisted access token.

### Impact Explanation
If the host application's session storage (as documented, storage is the host app's responsibility, e.g., the `shopify_app` reference implementation keyed by `Session#id` [6](#0-5) ) trusts this gem's `current_session_id` return value as an authenticated identifier, an attacker who can set an arbitrary cookie value for the app's origin can cause the app to load and use another merchant's stored offline or online access token — a cross-tenant access / access-token exfiltration outcome, matching the Critical impact class in the rules (cross-tenant access, theft of a merchant access token).

### Likelihood Explanation
This requires the attacker to be able to set the `shopify_app_session` cookie value in the victim's browser for the app's domain (e.g. via a cookie-injection primitive elsewhere in the host stack, subdomain takeover, or any endpoint that lets an unauthenticated user set cookies), which is a narrower, but still unprivileged-only, precondition — no access token, `api_secret_key`, or privileged account is required, only knowledge of a target shop domain and, for online sessions, a guessable numeric user id.

### Recommendation
Bind the session cookie value to the session it was issued for cryptographically (e.g., HMAC-sign the cookie value with `Context.api_secret_key` and verify the signature in `cookie_session_id` before returning it), rather than trusting the raw cookie content as the authoritative session-lookup key.

### Proof of Concept
1. Legitimate merchant `victim-shop.myshopify.com` completes OAuth; the app sets cookie `shopify_app_session=offline_victim-shop.myshopify.com` per `validate_auth_callback` [1](#0-0) .
2. Attacker, via any cookie-setting primitive on the app's origin (not requiring credentials), sets their own browser's `shopify_app_session` cookie to the same deterministic value `offline_victim-shop.myshopify.com`.
3. Attacker requests an authenticated app page; the host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged, with no check that this value was ever legitimately issued to this browser [7](#0-6) .
4. The host app looks up and loads `victim-shop`'s stored session, including its access token, and uses it on the attacker's behalf.
