### Title
Webhook shop identity not covered by HMAC signature allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unsigned HTTP headers. `Registry.process` validates the HMAC over the body only, then passes the unauthenticated `shop` header value straight to the app's webhook handler as the tenant identifier. Since a single app-level `client_secret` HMAC-signs webhooks for every merchant that has installed the app, a valid `(body, hmac)` pair obtained from one tenant's webhook can be replayed with a different `shop-domain` header, and the gem will treat it as authentic for the spoofed tenant.

### Finding Description
`VerifiableQuery#to_signable_string` is the only material bound by `HmacValidator.validate`: [1](#0-0) 

But the identity fields that the rest of the pipeline treats as authenticated are pulled from headers that are never part of that signed string: [2](#0-1) 

`HmacValidator.validate` only recomputes and compares the signature over `to_signable_string` (the raw body) against the app's `client_secret`: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately forwards the unauthenticated `request.shop` (and `request.topic`) into the tenant-scoped `WebhookMetadata` object dispatched to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop value verified by HMAC == shop value acted upon by the handler`. Because the HMAC secret (`client_secret`) is shared across every merchant that has the app installed, a legitimate `(raw_body, hmac)` pair generated by Shopify for tenant A's webhook remains cryptographically valid no matter what `shop-domain` header is attached to the HTTP request. An attacker who controls (or has installed) the app on their own shop can:
1. Trigger a real webhook delivery to their own shop (e.g. `orders/create`) and capture the genuine `raw_body` and `X-Shopify-Hmac-Sha256` value.
2. Replay that exact body/HMAC pair to the app's webhook endpoint, substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) with a victim shop's domain.
3. `HmacValidator.validate` passes because it only checks the body bytes against the shared secret — it never binds `shop` to the signature.
4. `Registry.process` dispatches the handler with `WebhookMetadata.shop == victim-shop`, causing the app to record/act on attacker-supplied data under the victim tenant's identity.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: cross-tenant access/injection is possible because an authenticated-looking event can be attributed to any shop domain the attacker chooses, without needing that victim's credentials. This matches the "cross-tenant access" Critical impact category, since app-side data or actions keyed by `shop` (webhook bookkeeping, order/customer records, uninstall handling, etc.) can be manipulated for a shop the attacker does not control.

### Likelihood Explanation
Any actor who can install the target app on their own (attacker-controlled) shop — a normal, unprivileged action for a public Shopify app — can obtain a validly-signed body/HMAC pair and replay it with a forged `shop-domain` header, since nothing in this gem binds that header to the signature. No access token, `client_secret`, or privileged access is required beyond ordinary app installation.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) as part of the signed material verified against the HMAC, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it (e.g., validate that the shop domain is one for which a webhook was actually registered/expected, or require the host application to separately verify shop membership before using `request.shop`). At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted as verified tenant identity by consuming applications.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `client_secret`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and `H`.
3. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and header `H`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` — this succeeds because `B`/`H` are the untouched, genuine pair [5](#0-4) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [6](#0-5) , causing the app to process attacker-controlled data as belonging to the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
