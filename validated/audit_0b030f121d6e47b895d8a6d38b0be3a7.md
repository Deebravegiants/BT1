### Title
Webhook Shop/Topic Header Spoofing via HMAC that Only Covers the Raw Body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw JSON body, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from HTTP headers that are never included in the HMAC computation. `Registry.process` then trusts `request.shop` and `request.topic` — taken from these unverified headers — to route the webhook to a handler and to populate `WebhookMetadata`, which apps use as the authoritative tenant identifier for processing the payload. Any party capable of producing one genuine `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own shop and triggering a webhook) can replay that exact body/HMAC combination while substituting the `shop-domain` header for a different, victim shop, and the request will still pass `HmacValidator.validate`.

### Finding Description
The identity binding that should hold is:
`hmac_signed_bytes == bytes_the_app_acts_upon_for_tenant_identity`

Instead:
- `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all derived from HTTP headers, not from the signed body: [2](#0-1) 
- `HmacValidator.validate` verifies the HMAC over exactly that signable string (the body) and nothing else: [3](#0-2) 
- `Registry.process` validates the HMAC, then immediately uses the unverified `request.topic` to select a handler and the unverified `request.shop` as the tenant field passed to the handler: [4](#0-3) 

Because the app's `client_secret` (used as the HMAC key) is shared across every shop that has the app installed, an attacker who controls any shop with the app installed can legitimately trigger a webhook delivery to the app's endpoint and capture a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with that shared secret. The attacker then re-sends this exact body and HMAC to the same public endpoint, only changing the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim's domain while the body content is entirely attacker-chosen. This breaks the equality between "HMAC-verified sender" and "shop the payload is attributed to," letting one tenant's traffic be laundered as another tenant's webhook.

### Impact Explanation
This is a cross-tenant identity confusion: a request that only proves "signed by this app's secret" is treated by the handler as "authoritative data for shop X" where X is attacker-chosen and unverified. Any host application that uses `WebhookMetadata#shop` to select which merchant's record to update, store data for, or authorize actions on will process attacker-controlled body content under a victim shop's identity — cross-tenant data injection/corruption without ever compromising the victim's credentials.

### Likelihood Explanation
Exploitability only requires that the attacker be able to install the app on a shop they control (a normal, unprivileged action available to anyone using the Shopify platform) and be able to reach the app's public webhook endpoint, which is the whole point of the endpoint. No `api_secret_key`, access token, or victim credentials are needed — only capture-and-replay of one legitimate delivery with a substituted header.

### Recommendation
Include the security-relevant identifiers in the HMAC-covered material, or otherwise cryptographically bind `shop-domain`/`topic`/`webhook_id` to the verified body — e.g., have `to_signable_string` incorporate the headers, or have `Registry.process` cross-check that the shop named in the header actually corresponds to a session/shop the app has independently authorized for that specific webhook subscription (e.g., look up the webhook subscription by `webhook_id` from the signed body/topic mapping rather than trusting the header verbatim). At minimum, document clearly that `WebhookMetadata#shop`/`#topic` are unauthenticated and must not be used as the sole tenant-selection key without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they legitimately control) and triggers any subscribed webhook topic (e.g. `orders/create`) with a payload of their choosing.
2. Attacker's own endpoint (or a packet capture) records the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify sent — this HMAC is valid because it's computed with the app's shared `client_secret`.
3. Attacker POSTs that identical `raw_body` + `X-Shopify-Hmac-Sha256` to the app's public webhook endpoint again, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body`: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker-chosen body> ...)`, causing the app to process attacker-controlled data as if it originated from the victim shop.
