### Title
Stale/expired-in-place reuse of validated user QR-code data without independent re-verification deadline - ([File: src/plans/mod.rs])

### Summary
The reported "missing deadline" bug class describes authorization data (a signed transaction) being usable for an unbounded/unexpectedly long window because there is no independent expiry check tied to that specific authorization, relying only on a broader, unrelated protection mechanism (slippage). In orb-core, the closest analog is in the QR-code signup-authorization flow: the *user* QR-code's backend-validated authorization (`backend::user_status::UserData`, including identity commitment and self-custody keys) has no independent expiration/deadline of its own. It is only gated indirectly by the *operator* QR-code's `operator_qr_expiration_time` (default 23 hours), via `QrCodes::Both` caching in `scan_remaining_qr_codes`.

### Finding Description
`MasterPlan::scan_remaining_qr_codes` in `src/plans/mod.rs` re-uses a previously validated `user_qr_code`/`user_data` pair from the `QrCodes::Both` variant as long as the *operator's* timestamp has not exceeded `operator_qr_expiration_time`: [1](#0-0) 
There is no separate timestamp or deadline attached to the user QR-code validation itself — the `OperatorData` struct carries the only `timestamp` field used for expiry decisions: [2](#0-1) 
Meanwhile, `verify_user_qr_code` performs a one-time backend validation call and returns cached `UserData` (identity commitment, self-custody keys, backend encryption keys) with no deadline metadata of its own: [3](#0-2) 
The backend request/response for user status likewise carries no expiration/nonce/deadline field to bound how long the validated authorization can be treated as fresh: [4](#0-3) 
By contrast, the operator QR-code path explicitly re-verifies and time-stamps on every scan, and the system defines a dedicated `operator_qr_expiration_time` config knob (`Duration::from_secs(60 * 60 * 23)` by default): [5](#0-4) 
This is a direct structural analog to the swap "missing deadline" bug: a piece of authorization/state (validated user identity/keys) is allowed to be used at a time far removed from when it was actually verified, bounded only by an unrelated, coarser mechanism (the operator's own QR expiry) rather than a deadline tied to the user authorization itself.

### Impact Explanation
If the operator keeps re-scanning or otherwise avoids operator QR expiry, a previously fetched `user_data`/`UserData` (identity commitment, self-custody public key, backend encryption keys) can remain "valid" and reusable for up to the full `operator_qr_expiration_time` window without a fresh backend re-validation. Any change in the user's validity state on the backend (e.g., revocation, fraud flag, or re-issued keys) during that window would not be re-checked before the cached authorization is used to complete a signup — this mirrors the report's "unfavorable market conditions" analog, translated to "unfavorable authorization conditions" (revoked/changed identity state) not being re-checked before execution.

### Likelihood Explanation
Likelihood is low-to-moderate: `QrCodes::Both` reuse only occurs in specific flows where the master loop retains cached QR data across a failed/incomplete signup attempt and re-enters `scan_remaining_qr_codes` before the operator QR expires. It requires an operator-driven retry pattern within the up-to-23-hour operator expiry window rather than a single-shot signup, and is not exploitable by an anonymous external party — the operator (already a semi-trusted role) is the one navigating QR scans.

### Recommendation
Attach an independent expiration/deadline to the validated `user_data` result — e.g., add a `timestamp` field to the `QrCodes::Both`/`ResolvedQrCodes` state analogous to `OperatorData::timestamp`, and re-invoke `verify_user_qr_code` if that timestamp exceeds a short, dedicated deadline (independent from `operator_qr_expiration_time`), rather than relying solely on the operator's QR expiry as a proxy deadline for the user's authorization freshness.

### Proof of Concept
1. Configure a long `operator_qr_expiration_time` (or use the default 23h).
2. Scan operator QR code, then scan and successfully validate a user QR code, producing `QrCodes::Both { operator_data, user_qr_code, user_data, .. }` (see `scan_remaining_qr_codes`, `src/plans/mod.rs:796-805`).
3. Interrupt/fail the signup after this point (e.g., `is_orb_os_version_allowed` fails or biometric capture is aborted) so the `QrCodes::Both` state persists into the next loop iteration in `MasterPlan::run`.
4. Re-enter `do_signup` before `operator_data.timestamp.elapsed()` exceeds `operator_qr_expiration_time` — the cached `user_data` (from the earlier validation) is reused directly without calling `backend::user_status::request` again (`src/plans/mod.rs:796-805`), even though a meaningful amount of time (up to ~23h) may have elapsed since the user's authorization was actually checked against the backend.
