### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute from the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header, but `Utils::HmacValidator` only verifies the raw request body against the app's secret. The header identifying which tenant/shop the webhook belongs to is never included in the signed material, so it can be swapped without invalidating the HMAC check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an attacker-controllable header with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Webhooks::Registry.process` validates only this body HMAC, then forwards the unverified `request.shop` value straight into `WebhookMetadata`, which host applications use to attribute the event to a tenant/session: [4](#0-3) 

The identity-binding equality the gem should enforce is:
`shop header used to attribute/process the event == shop bound inside the HMAC-verified payload`

Instead, the code enforces only:
`HMAC(raw_body, secret) == received_hmac`, independent of `shop`.

### Impact Explanation
Because the `shop` header is entirely outside the signed content, an unprivileged attacker who can obtain any single genuine, validly-signed webhook byte stream from Shopify (e.g., by installing the app on their own store and triggering an event) can replay that exact `raw_body` + `hmac-sha256` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Any host application relying on this gem's documented API (`Registry.process` / `WebhookMetadata#shop`) to determine which merchant/session a webhook event belongs to will process attacker-controlled data under a victim shop's identity — a cross-tenant identity confusion that meets the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Likelihood is realistic: no access token, `client_secret`, or privileged account is required. The attacker only needs to be a legitimate (even free/dev-store) merchant of the target app to receive one authentic webhook, then reuse the untouched body+HMAC with a forged shop header against the app's public webhook URL, which is typically a fixed, discoverable route.

### Recommendation
Bind the shop identity to the signed payload before trusting it: either (a) include the shop domain/webhook id in the HMAC-signed material and verify it in `HmacValidator`/`Request`, or (b) require host applications to cross-check `request.shop` against an independently trusted source (e.g., an existing session record whose shop was established during OAuth/token exchange) before acting on webhook data, and document this requirement clearly since `Registry.process` currently implies the shop field is trustworthy once HMAC validation passes.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger an event (e.g., create an order) so Shopify sends a real webhook to the app's public endpoint, or capture one delivered to an attacker-controlled relay for their own shop.
2. Record the exact `raw_body` and `x-shopify-hmac-sha256` value from that genuine request — both remain valid since neither depends on the shop header.
3. Send a new POST to the same app webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and `x-shopify-topic`/`x-shopify-webhook-id` as desired).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only `raw_body` is checked (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The registered handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-supplied data under the victim's tenant identity.
