### Title
Non-consumed pending storage diff can be applied multiple times to `ContractInfo`, allowing storage deposit double-counting and over-refund - (File: substrate/frame/revive/src/metering/storage.rs, mod.rs)

### Summary
`RawMeter::apply_pending_changes_to_contract` (`substrate/frame/revive/src/metering/storage.rs:503-510`), exposed via `FrameMeter::apply_pending_storage_changes` (`substrate/frame/revive/src/metering/mod.rs:673-675`), mutates a live `ContractInfo` (`storage_bytes`, `storage_items`, `storage_byte_deposit`, `storage_item_deposit`) from the parent frame's still-pending `own_contribution` diff, but explicitly does **not** consume/reset that diff. If the same accumulated diff is later re-applied — either by a subsequent call to `apply_pending_storage_changes` before another nested call, or by the normal `finalize`/`finalize_own_contributions` path (`mod.rs:655-663`, `storage.rs:488-494`) — the same bytes/items/deposit get counted against `ContractInfo` more than once.

### Finding Description
`apply_pending_changes_to_contract` reads `Contribution::Alive(diff)` and calls `diff.update_contract::<T>(Some(info))`, which mutates the passed `ContractInfo` in place (`storage_bytes`, `storage_byte_deposit`, etc., see `Diff::update_contract`, `storage.rs:121-173`). Crucially, the method does not transition `own_contribution` to `Contribution::Checked(..)` nor reset it, as the doc comment states: *"Unlike `finalize_own_contributions`, this does not consume the pending diff, allowing the meter to continue tracking changes after the nested call returns"* (`storage.rs:496-502`).

By contrast, the codebase already contains a safe pattern for this exact situation: `bank_pending_changes` (`storage.rs:512-528`) applies the diff to `info` **and then resets** `own_contribution` to a fresh `Contribution::Alive(Default::default())` specifically to prevent `finalize` from applying it a second time (see the `debug_assert!` guarding re-entry). `apply_pending_changes_to_contract`/`apply_pending_storage_changes` has no equivalent safeguard.

Consequently, any code path in `exec.rs` that calls `apply_pending_storage_changes` for a parent frame that later either (a) makes another nested call from the same frame while the diff is still pending, or (b) proceeds to a normal `finalize()` without going through `bank_pending_storage_changes`, will invoke `diff.update_contract(Some(info))` a second time against the *same* diff. Because `Diff::update_contract` unconditionally accumulates onto `info.storage_bytes`/`storage_items`/`storage_byte_deposit`/`storage_item_deposit` (`storage.rs:151-170`), each redundant application inflates these persisted fields without any corresponding new balance actually being reserved from `origin`. `info.storage_byte_deposit`/`storage_item_deposit` subsequently drive refund pro-rata ratio calculations for later storage removals (`storage.rs:136-148`), so an inflated recorded deposit produces an inflated refund when storage is later shrunk or the contract terminated — a refund larger than what was ever actually placed on hold via `HoldReason::StorageDepositReserve`.

An unprivileged contract can trigger this simply by writing storage and then making two or more nested calls (e.g., `call`/`delegate_call` to unrelated sub-contracts) from the same execution frame before that frame finalizes, provided the code path invokes `apply_pending_storage_changes` per nested-call construction (this was added specifically to fix cross-frame refund visibility per the referenced issue `contract-issues#213`). I was not able to fully confirm from `exec.rs` the precise call frequency/ordering (i.e., whether `apply_pending_storage_changes` is invoked once per nested call construction or once per frame), so the exact reachable trigger count is not fully verified, but the underlying meter API itself has no protection against being called more than once against an unconsumed diff, which is a genuine accounting defect independent of exact call-site cadence.

### Impact Explanation
Double- (or N-times) counting of a pending storage diff into `ContractInfo`'s deposit-tracking fields inflates the recorded storage deposit for a contract beyond the balance actually held/reserved via `HoldReason::StorageDepositReserve`. When that contract's storage later shrinks (or the contract terminates), the refund is computed as a ratio against this inflated deposit figure, resulting in a refund larger than the real amount ever deposited — an over-refund of storage deposit balance to the calling account, i.e. balance being paid out that was never actually collected/reserved from any account.

### Likelihood Explanation
Preconditions require only: a contract with an existing pending (uncommitted) storage diff, and the ability to make two or more nested calls out of the same execution frame — both trivially achievable by any unprivileged contract deployer/caller through ordinary `call`/`delegate_call` sequencing. No special origin, proxy, or privileged access is needed. The bug is inherent to the meter's API contract (no reset on `apply_pending_changes_to_contract`) rather than a rare race condition, making it deterministically reproducible whenever the vulnerable call pattern occurs.

### Recommendation
Make `apply_pending_changes_to_contract`/`apply_pending_storage_changes` idempotent with respect to `ContractInfo`, e.g. by tracking a "last-applied diff" snapshot and only applying the delta since the previous call, or by having callers in `exec.rs` guarantee it is only ever invoked once per pending diff lifetime (mirroring the reset behavior already implemented in `bank_pending_changes`). Add a debug assertion (analogous to the one in `bank_pending_changes`) that fires if `apply_pending_changes_to_contract` is called on an already-visible/applied diff without an intervening reset, and add regression tests covering multiple nested calls originating from a single frame with pending storage changes.

### Proof of Concept
Rust unit test plan in `substrate/frame/revive/src/metering/storage/tests.rs`:
1. Construct a root `Meter` and a nested `RawMeter` with `charge(&Diff{bytes_added: 100, items_added: 1, ..})`.
2. Call `apply_pending_changes_to_contract(&mut info)` twice in succession (simulating two nested subcalls from the same frame) and then call `finalize_own_contributions(Some(&mut info))`.
3. Assert `info.storage_bytes`/`info.storage_byte_deposit`/`info.storage_item_deposit` equal the value expected from a **single** application of the diff (e.g., `100 * per_byte`), not `2x` or `3x`.
4. Extend to a fuzz/invariant test that randomizes the number of nested calls made from a frame with a pending diff and asserts `execute_postponed_deposits` result plus final `ContractInfo` deposit fields never exceed the real net bytes/items charged to `origin`.
