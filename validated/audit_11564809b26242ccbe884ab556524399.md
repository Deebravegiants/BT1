### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) header is trusted despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` authenticates the body bytes but never binds the `shop`, `topic`, `webhook-id`, or `api-version` values (all read from unauthenticated HTTP headers) to that signature. `Registry.process` accepts any request whose body HMAC matches, then forwards the header-derived `request.shop` straight to the handler as the tenant identifier.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop` is read from a plain header with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` only checks that `HMAC(api_secret_key, to_signable_string)` matches the supplied `hmac`, i.e. it verifies `raw_body` bytes only: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` (and `request.topic`/`webhook_id`/`api_version`) as the tenant/context identifier passed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop attributed to the webhook payload`. Because the HMAC only covers `raw_body`, this equality does not hold — `request.shop` can be set to any value independent of what the HMAC actually signs.

### Impact Explanation
Since the same `api_secret_key` is used to HMAC-sign webhook bodies across every shop that has installed the app, a request with a genuinely-valid HMAC (e.g., a webhook body the attacker legitimately received for their own, attacker-owned shop after installing the app) can be replayed to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim's shop. `Registry.process` will accept the request (HMAC matches the body) and hand the handler a `WebhookMetadata` claiming to be from the victim shop: [5](#0-4) 

Any host application logic keyed on `WebhookMetadata#shop` (e.g., updating merchant-scoped records, triggering per-shop side effects) can be manipulated cross-tenant, since the shop identity is never actually authenticated by the signature that this gem verifies.

### Likelihood Explanation
Exploitation requires the attacker to be able to install/uninstall the app on a shop they control (or otherwise legitimately receive an app webhook), then resend that request to the target's public webhook endpoint with a modified `shop-domain` header — all reachable by an unprivileged internet user with no leaked secrets, tokens, or credentials.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the HMAC-covered signable string, or otherwise cryptographically tie the shop domain to the signed body (e.g., include it as signed metadata verified against the destination the webhook is registered for) so `to_signable_string` cannot be satisfied while the shop attribution is forged.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook delivery, e.g. `orders/create`, with headers `x-shopify-hmac-sha256: <validHmac>`, `x-shopify-shop-domain: attacker.myshopify.com`, and body `B`.
2. Compute/keep the valid `hmac = HMAC_SHA256(api_secret_key, B)` (unchanged, still valid since body `B` didn't change).
3. Resend the exact same request to the target app's webhook endpoint but replace the header `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, B)` — this still matches, so validation passes: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled body>, ...)`, causing the host app to process attacker-supplied data attributed to the victim's tenant.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
