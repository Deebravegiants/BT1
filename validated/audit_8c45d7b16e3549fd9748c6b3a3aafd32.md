### Title
Webhook `shop-domain` header is not bound to the HMAC signature, enabling cross-tenant shop spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature (`to_signable_string`) over the raw request body only, while the `shop` value handed to the app's webhook handler is read from an unauthenticated HTTP header (`X-Shopify-Shop-Domain`). The HMAC secret (`api_secret_key`) is the app's single client secret, shared across every merchant/shop that has installed the app — it is not shop-specific. This breaks the intended binding `HMAC(body, api_secret_key) == valid ⇒ shop-domain header is trustworthy`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body` — the `shop` field (read via `shopify_header("shop-domain")`) is never included in the bytes that are HMAC-verified. `Utils::HmacValidator.validate` simply recomputes `HMAC(to_signable_string, api_secret_key)` and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (from the unauthenticated header) to build `WebhookMetadata`, which is handed directly to the app's handler as the tenant identifier: [4](#0-3) 

Because `api_secret_key` is the app's single client secret (identical for all shops that installed the app — see `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb`), any body+HMAC pair that is valid for the attacker's own shop (e.g., obtained by installing the app on a free/attacker-controlled development store and capturing a real webhook Shopify sends them) remains valid for the exact same body when replayed with a different `X-Shopify-Shop-Domain` header — the signature says nothing about which shop it originated from. Documentation confirms `Registry.process` is expected to "verify the request did indeed come from Shopify" before invoking the handler, i.e., the shop identity is implicitly assumed to be authenticated by this check, which it is not: [5](#0-4) 

This is precisely the anchor pattern called out in the rules: "a field acted on but not covered by the HMAC."

### Impact Explanation
Downstream apps (per the documented handler contract) key their tenant-scoped logic off `WebhookMetadata#shop`: [6](#0-5) 

Since this value is not authenticated by the HMAC, an attacker who can obtain any single validly-signed webhook body from Shopify for a shop they control can replay that body with a forged `shop-domain` header naming a victim shop. Because `Registry.process` reports the request as HMAC-valid, the host application will process attacker-supplied webhook data under the identity of the victim tenant — a cross-tenant data-integrity/confusion issue (e.g., poisoning cached victim-shop data, triggering victim-scoped side effects, or corrupting per-shop state keyed by the spoofed `shop` value), without ever compromising `api_secret_key` itself.

### Likelihood Explanation
Any actor with an unprivileged internet-accessible entry point (installing the app on a free Shopify development store, which they fully control) can obtain a fully valid `(body, hmac)` pair signed with the app's real secret. Forging the `shop-domain` header on the replayed HTTP request requires no cryptographic material — it's an ordinary HTTP header the attacker fully controls when posting to the app's public webhook endpoint. The library provides no cross-check between the authenticated body/signature and the `shop` used downstream, so exploitation is straightforward and reachable through the gem's documented `Registry.process` API exactly as intended to be used.

### Recommendation
Bind the shop identity to the signed material: either (a) include the shop domain in `to_signable_string` (not possible without Shopify changing its signature format, since Shopify controls this), or, more practically, (b) require callers of `Registry.process`/`WebhookHandler` to cross-validate `request.shop` against an expected/known shop (e.g., a shop for which the app currently holds a session) before trusting `WebhookMetadata#shop`, and document this requirement prominently since the gem cannot enforce it itself given Shopify's real signature format only covers the body.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) Shopify development store `attacker-shop.myshopify.com` and receives a real webhook, e.g., for `orders/create`, with a genuine `X-Shopify-Hmac-Sha256` header computed over the JSON body using the app's real `api_secret_key`.
2. Attacker replays the exact same raw body and HMAC header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this into a `Request` whose `hmac` matches `HMAC(raw_body, api_secret_key)` (unchanged, since `to_signable_string` == `raw_body` only).
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which returns `true` (see `lib/shopify_api/utils/hmac_validator.rb` lines 12-31 and `lib/shopify_api/webhooks/registry.rb` line 190).
5. `Registry.process` builds `WebhookMetadata.new(topic:, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` (line 198-199) and invokes the app's handler, which — per the documented contract — trusts `data.shop` as the tenant identity, processing attacker-controlled data under the victim's identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
