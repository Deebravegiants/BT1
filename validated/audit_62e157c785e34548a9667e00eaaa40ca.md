### Title
Excess native ETH sent to `placeOrder` is permanently stuck because the Tron `IntentGatewayV2` never refunds unspent `msgValue` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` only performs `>=`/insufficiency checks on `msg.value` against the required native input and fee amounts, but — unlike the canonical EVM implementation — never refunds or otherwise accounts for any leftover `msgValue` at the end of the function. Any unprivileged caller who overpays `msg.value` (accidentally or otherwise) has the excess ETH permanently locked in the contract with no self-service recovery path.

### Finding Description
In `placeOrder`, native-token inputs are validated with a loose sufficiency check rather than an exact-match check: [1](#0-0) 

If `order.fees > 0` and the caller pays with native ETH, the remaining `msgValue` is spent via a `swapETHForExactTokens` call which itself may leave a further remainder (since `amountOut` is fixed but `msg.value` can exceed the required input): [2](#0-1) 

After this, the function goes straight to emitting `OrderPlaced` and returns — there is no step that inspects or forwards any remaining `msgValue` back to `msg.sender`: [3](#0-2) 

This is a direct regression relative to the canonical (non-Tron) `IntentGatewayV2.sol`, which explicitly refunds any unspent native token at the end of `placeOrder`: [4](#0-3) 

There is also no protocol-level accounting/event for this leftover value (unlike the `DustCollected` events emitted for protocol-fee dust and predispatch overpay dust), so the stuck balance is not even tracked on-chain. The only theoretical recovery path is the governance-driven `RequestKind.SweepDust` handler, which requires a cross-chain governance message specifying the exact token/amount/beneficiary — this is not something the affected user can trigger themselves, and depends on off-chain discovery of the exact stuck amount: [5](#0-4) 

The Tron `IntentGatewayV2.sol` also does not implement `fillOrder`, so this over-collection defect is confined to `placeOrder`'s native-ETH escrow/fee-swap paths, but that path alone is directly reachable by any unprivileged user.

### Impact Explanation
Any user submitting a `placeOrder` transaction with native ETH inputs and/or fees who supplies `msg.value` greater than strictly required (e.g., due to fee-estimation slippage margin, wallet UX rounding up, or a swap consuming less than the full `msgValue`) has the excess permanently locked in the contract, with no user-callable withdrawal function. This is a concrete freezing-of-funds bug reachable from a single unprivileged transaction, matching the reported bug class (loose `msg.value` checks causing ETH to become stuck).

### Likelihood Explanation
Likelihood is high in practice: callers routinely pad `msg.value` above the exact required amount to be safe against fee/slippage fluctuations (as demonstrated by the corresponding test suite for the canonical EVM contract explicitly testing overpayment refunds), and the fee-swap path (`swapETHForExactTokens`) inherently tends to leave unspent native ETH whenever the swap consumes less than the full `msgValue` supplied.

### Recommendation
Mirror the canonical EVM `IntentGatewayV2.sol` behavior: after all native-token legs (inputs and fee swap) have been settled, refund any remaining `msgValue` to `msg.sender` (e.g., via a low-level `call` with a revert-on-failure check), consistent with the pattern already implemented at `evm/src/apps/IntentGatewayV2.sol:394-397`.

### Proof of Concept
1. On the Tron chain, call `IntentGatewayV2.placeOrder{value: order.inputs[0].amount + order.fees + overpayment}(order, graffiti)` where `order.inputs[0].token == address(0)` (native ETH) and `order.fees == 0` (or `> 0` with `overpayment` exceeding what the fee swap consumes).
2. `msgValue` sufficiency checks at lines 456-457 pass since `msgValue >= order.inputs[i].amount`; the excess `overpayment` is never spent or refunded.
3. The function completes and emits `OrderPlaced` without moving the leftover `msgValue` anywhere.
4. `address(intentGateway).balance` now permanently includes `overpayment` with no on-chain record and no function callable by the depositor to reclaim it.
