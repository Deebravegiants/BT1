### Title
Webhook `shop` identity not bound to the HMAC, allowing cross-tenant webhook spoofing via HMAC-valid replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` (used by `Registry.process`) verifies the integrity of the JSON body alone. The `shop` value that is handed to the app's handler (and used to attribute the webhook to a tenant) comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a field that is never included in the HMAC-signed material.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`shop` is read straight from a header with no cryptographic tie to the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` to construct `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the raw body: [5](#0-4) 

The identity binding broken is: `HMAC(secret, raw_body) == received_hmac` is treated as proof that `(shop, raw_body)` jointly came from Shopify, when in fact only `raw_body` is authenticated. `shop_claimed_in_header != shop_bound_by_hmac` can diverge without failing validation, because the HMAC check only asserts `raw_body_received == raw_body_signed`, never `shop_header_received == shop_bound_by_signature`.

As the docs confirm, apps are expected to use `data.shop` directly as the tenant identifier for downstream processing (e.g. `perform_later(shop_domain: data.shop, webhook: data.body)`): [6](#0-5) [7](#0-6) 

### Impact Explanation
An unprivileged party who can obtain any single legitimate `(body, HMAC)` pair for a webhook topic (e.g. by triggering an `orders/create` event on their own store and capturing the POST their app receives — no `api_secret_key` needed) can replay that exact body and HMAC to the target app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. Since `to_signable_string` never includes `shop`, `HmacValidator.validate` still returns `true`, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen (victim) shop and the attacker's own body content. Any downstream code that trusts `data.shop` as the tenant to attribute/act on that body (as the gem's own documented usage pattern encourages) will process attacker-controlled data under another merchant's identity — a cross-tenant data-integrity/confusion issue reachable without holding any secret.

### Likelihood Explanation
Moderate-to-high: exploitation requires only (1) capturing one's own valid webhook body+HMAC (trivially available to any merchant/developer who installs the app on their own store) and (2) sending an HTTP POST to the app's public webhook endpoint with a modified shop header — both actions available to an unprivileged internet user/merchant, no `api_secret_key`, access token, or privileged account required.

### Recommendation
Bind the claimed `shop` (and other headers relied upon for identity, e.g. `topic`, `webhook_id`) into the HMAC-signable material, or otherwise cryptographically verify that the shop attributed to the webhook is consistent with the signed payload/topic subscription, rather than trusting an unauthenticated header value once body-only HMAC validation succeeds.

### Proof of Concept
1. Register the app's webhook handler for `orders/create` as shown in `docs/usage/webhooks.md`.
2. As a legitimate merchant "shop-A.myshopify.com" using the app, trigger an `orders/create` event; capture the resulting POST to the app's webhook endpoint, noting the raw JSON body and the `x-shopify-hmac-sha256` value.
3. Send a new POST to the same endpoint with the identical raw body and `x-shopify-hmac-sha256` value, but replace `x-shopify-shop-domain` with `"shop-B.myshopify.com"` (the victim).
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses successfully; `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the HMAC.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "shop-B.myshopify.com", body: <shop-A's order data>, ...)`, demonstrating that data from shop-A is delivered under shop-B's identity.

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
