### Title
Duplicate `address(0)` entries in `circomData.erc20TokenAddresses` let a single ETH UTXO be double-counted, minting shielded value without matching `msg.value` - ([File: contracts/Hinkal.sol])

### Summary
The specific variant proposed for the single-`address(0)` index (relying only on `msg.value=0`) is correctly blocked, because `require(balanceDif == ...)` on line 137-146 fails as computed. However, the alternate variant the question raises - listing `address(0)` **twice** in `circomData.erc20TokenAddresses` - is exploitable: `Hinkal.transact`'s per-index balance/UTXO-matching loop (lines 97-147) re-evaluates the identical `msg.value`-based `balanceDif` and re-scans the same `utxoSet` entries for every index sharing the same token address, so a single ETH UTXO backed by one `msg.value` payment produces two identical `onChainCommitments`.

### Finding Description
Equality that should hold once per unique token, but instead holds independently per array index:
`balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]`, where for `address(0)` entries `balanceDif[i] = newBalances[i] + msg.value - oldBalances[i]` [1](#0-0) .

`getBalancesForArray` simply queries `address(this).balance` for every `address(0)` entry regardless of index, so `oldBalances[i]` and `newBalances[i]` are identical across all indices holding `address(0)` [2](#0-1) . Consequently `balanceDif` computed for index `0` and index `1` (both `address(0)`) is the exact same value, `msg.value` (since `runAction` does not move ETH itself for `tokenAddress == address(0)` at line 75 of `DepositOnChainUtxosExternalAction.sol`).

The inner UTXO-matching loop (lines 116-132) also matches purely by `erc20Address`, with no marking/exclusion of already-consumed `utxoSet` entries: [3](#0-2) 
So for index `1` (the second `address(0)` entry) the loop re-scans the *same* `utxoSet[0]` (5 ether ETH UTXO) and re-sums it into `utxoAmount`, and calls `createOnchainCommitment` a second time on the identical `UTXO` struct, producing an identical commitment hash (`hash4(amount, erc20Address, stealthAddress, timeStamp)` [4](#0-3) ), since the `UTXO` object (including `timeStamp`) is unchanged between the two matches.

Exact attacker call:
- `erc20TokenAddresses = [address(0), address(0)]`
- `externalActionData.externalActionId` -> `DepositOnChainUtxosExternalAction`
- `externalActionMetadata` decodes to `utxoAmounts = [[5 ether], []]` -> `runAction` builds exactly **one** UTXO (5 ether, `address(0)`) [5](#0-4) 
- `onChainCreation = [true, true]`, `amountChanges = [0, 0]`
- `msg.value = 5 ether`

Trace:
- `i=0`: `balanceDif = 0 + 5 ether - 0 = 5 ether`. `utxoAmount` = 5 ether (matches `utxoSet[0]`). `require(5 ether == 0 + 5 ether)` passes. `onChainCommitments[0]` created from `utxoSet[0]`.
- `i=1`: same token address(0), same `oldBalances[1]`/`newBalances[1]` (identical actual ETH balance), same `msg.value` -> `balanceDif = 5 ether` again. Inner loop again matches `utxoSet[0]` (still the only ETH-addressed UTXO) -> `utxoAmount = 5 ether` again. `require(5 ether == 0 + 5 ether)` passes AGAIN. `onChainCommitments[1]` created from the SAME `utxoSet[0]`, producing an identical commitment.

Both `onChainCommitments[0]` and `[1]` are inserted as tree leaves via `insertCommitments`/`insertMany` [6](#0-5) , with no uniqueness check on `erc20TokenAddresses` performed anywhere in `dimensionsCheck` or `checkOnchainCreation` [7](#0-6) [8](#0-7) . Since both leaves encode identical private data (same `amount`, `erc20Address`, `stealthAddress`, `timeStamp`), the attacker who knows the single secret backing the UTXO can later generate a valid membership/spend proof against **either** leaf independently, effectively enabling two spends of value that was only paid for once.

### Impact Explanation
Critical - a single `msg.value` payment (5 ether) mints two identical on-chain shielded commitments (10 ether of claimable value), and because the two leaves share identical underlying secrets, the attacker can subsequently redeem both via independent withdraw/transact proofs, directly minting shielded value without backing / enabling a double-spend of protocol-held ETH. This is repeatable for any number of duplicated `address(0)` (or any single ERC20 address) entries in `erc20TokenAddresses`, each additional duplicate index re-matching the same UTXO(s) and multiplying the minted shielded value relative to actual funds received.

### Likelihood Explanation
The attacker is a fully unprivileged EOA who only needs to: craft `circomData` with duplicated token addresses (nothing prevents this in `dimensionsCheck`/`checkOnchainCreation`), generate a valid proof for their own chosen public inputs (attacker fully controls their own UTXO secrets), and call `transact` with `externalActionId` pointing at `DepositOnChainUtxosExternalAction`. No special preconditions on tree state, no privileged role required, and the cost is exactly the `msg.value` for one deposit to mint double that value in shielded commitments. This is straightforward and repeatable.

### Recommendation
- In `Hinkal.transact`, deduplicate/validate `erc20TokenAddresses` (reject duplicate token addresses within a single `circomData`), or restructure the balance/UTXO-accounting loop to operate over a set of unique tokens rather than iterating per raw array index.
- Alternatively, mark `utxoSet` entries as "consumed" once matched in the inner loop (line 116-132) so the same physical UTXO can never be counted toward more than one index's `utxoAmount`/commitment creation.
- Include the array index or a per-UTXO nonce in the commitment hash to prevent identical `UTXO` structs from producing identical commitments even if accidentally processed twice.

### Proof of Concept
Foundry test outline:
1. Deploy `Hinkal`, `HinkalHelper`, and `DepositOnChainUtxosExternalAction`; whitelist the external action.
2. Build `CircomData` with `erc20TokenAddresses = [address(0), address(0)]`, `onChainCreation = [true, true]`, `amountChanges = [0,0]`, `slippageValues = [0,0]`, `externalActionMetadata = abi.encode([[5 ether],[]])`.
3. Generate a valid proof/`inputForCircom` consistent with these public inputs (locally, using attacker's own secret UTXO data) satisfying `performHinkalChecks` and `verifyProof`.
4. Call `hinkal.transact{value: 5 ether}(a,b,c,dimensions,circomData)`.
5. Assert: transaction succeeds (`require` at line 137-146 passes for BOTH `i=0` and `i=1`), `onChainCommitmentCounter == 2`, and both `onChainCommitments[0].commitment == onChainCommitments[1].commitment` (identical hash from `hash4`), confirming 10 ether of shielded commitments were created from a single 5 ether `msg.value` payment - i.e., `sum(committed UTXO values) (10 ether) != msg.value (5 ether)`.
