## Analysis

I found a valid analog: the Tron fork of the intent gateway performs the token/native transfer **before** decrementing escrow accounting, unlike the corresponding mainnet EVM contract, which was already hardened against this exact class of bug.

### Title
Reentrancy via pre-decrement external transfer in `IntentGatewayV2.withdraw` (Tron) inflates/duplicates escrow release - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` in the Tron `IntentGatewayV2` sends tokens/native value to an attacker-influenced `beneficiary`/`token` **before** updating the `_orders[commitment][token]` escrow accounting, reproducing exactly the root cause described in the external report (external call before state update, allowing a reentrant call to observe stale accounting and double-spend/duplicate protocol actions).

### Finding Description
`withdraw()` is invoked from `onAccept` (for `RedeemEscrow`/`RefundEscrow` messages) and from `cancelOrder` (same-chain path). It performs the external transfer first, then decrements the escrow map: [1](#0-0) 
```
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```
This is the *interactions-before-effects* pattern that the report flags: `holdings`/`_orders` is only updated after the external call returns, so any callback triggered during that call (a malicious `beneficiary` receiving native value, or a malicious `token` contract with a transfer hook) executes while `_orders[commitment][token]` still reflects the pre-withdrawal (undecremented) balance.

Both `beneficiary` and `token` in the `WithdrawalRequest` originate from attacker-controlled order fields: `order.user`/`order.output.beneficiary` (set by the caller in `placeOrder`) and `order.inputs[i].token` (also caller-chosen) [2](#0-1) , so an attacker fully controls the values in scope of the reentrant callback.

Critically, this contrasts with the mainline EVM `IntentsBase._withdraw`, which was hardened to decrement escrow **before** the external transfer (checks-effects-interactions): [3](#0-2) 
```
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```
and a dedicated regression test suite (`IntrinsicIntentsReentrancyTest.sol`) confirms the mainline contracts were previously vulnerable to the same class of bug and were fixed with a "set state before external call" (CEI) pattern [4](#0-3) . The Tron fork of `IntentGatewayV2` was not updated to match this fix and still contains the vulnerable ordering.

Reachability: `withdraw()` is reached from `onAccept` for a `RedeemEscrow`/`RefundEscrow` request, gated only by `authenticate()` verifying the *source chain identity* of the relayed ISMP message, not the *contents* of the body [5](#0-4) . It is also reachable directly and permissionlessly from same-chain `cancelOrder` [6](#0-5) , which any order owner can trigger with attacker-chosen `beneficiary`/`token` inputs and no reentrancy guard.

### Impact Explanation
A reentrant call during the `.call{value:}` (native) or `token.call(transfer)` leg can re-enter the gateway (e.g. `cancelOrder`, or via a token callback) while `_orders[commitment][token]` still shows the pre-withdrawal balance. Depending on which entry point is re-entered, this permits stale-state–gated checks (e.g. `if (_orders[body.commitment][token] == 0) revert UnknownOrder();`) to pass a second time, enabling duplicate dispatch of refund/redeem requests or duplicate transfers drawing on escrow the protocol has already logically released — the same "inflating internal accounting through reentrancy" impact described in the report, leading to loss of escrowed funds/protocol insolvency for orders processed on the Tron deployment.

### Likelihood Explanation
Medium-to-High: exploitation requires supplying a malicious `token` contract (as an order input) or a malicious `beneficiary` contract for native-token outputs — both fully attacker-controlled at `placeOrder` time — and a relayed message or same-chain `cancelOrder` call to trigger `withdraw()`. No privileged role is needed; this is reachable by any ordinary user placing/cancelling an intent order.

### Recommendation
Apply the same checks-effects-interactions ordering already used in the mainline `IntentsBase._withdraw`: decrement `_orders[body.commitment][token]` **before** performing the native/ERC-20 transfer in the Tron `withdraw()` function, and consider adding an explicit reentrancy guard (`nonReentrant`) around functions that both read and later mutate `_orders`/`_filled`.

### Proof of Concept
1. Attacker calls `placeOrder` with an input token set to a malicious ERC-20-like contract whose `transfer()` callback re-enters the gateway (or with a native-token output routed to a malicious `beneficiary` contract with a `receive()` hook).
2. Attacker triggers `withdraw()` — either via same-chain `cancelOrder` (permissionless once expired/owned) or via a legitimately relayed `RedeemEscrow`/`RefundEscrow` message that decodes attacker-supplied `beneficiary`/`token` values.
3. During the `beneficiary.call{value: amount}("")` or `token.call(...transfer...)` in `withdraw()` (`evm/tron/contracts/apps/IntentGatewayV2.sol:702-708`), before `_orders[body.commitment][token] -= amount;` executes, the malicious contract re-enters `cancelOrder`/another reachable path that reads `_orders[commitment][token]`, observing the stale (undecremented) balance and triggering an additional refund/redeem dispatch or transfer against the same escrow.
4. Net effect: escrow accounting and outgoing transfers desynchronize, allowing more value to be dispatched/transferred than was actually escrowed for the order.

Note: I was unable to fully trace the downstream cross-chain settlement (whether a duplicate `RefundEscrow` dispatch during reentrancy is later rejected on the source chain) within this session's tool budget; a Devin session should be used to build a Foundry-style PoC against the Tron contract analogous to `IntrinsicIntentsReentrancyTest.sol` to confirm the exact drainable amount end-to-end.

```text
    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);
```
