### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing a valid webhook body to be replayed under a spoofed shop domain - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which verifies the HMAC over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , while the `shop` (tenant) value that is subsequently trusted and handed to the app's handler is read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . The HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that has installed the app — it is not a per-shop secret. This is structurally the same bug class as the `WithdrawalEscrow` off-by-one: a value acted upon (here, the tenant-identifying `shop` field passed into `WebhookMetadata`) is not actually bound by the verification the code relies on for trust (the HMAC).

### Finding Description
`Registry.process` performs exactly one authentication check before dispatching to the merchant's webhook handler: [3](#0-2) 

That check calls `HmacValidator.validate`, which computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it against the `hmac` header using a constant-time comparison [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is defined as just the raw body bytes: [1](#0-0) 

None of the other headers — `topic`, `shop`, `api_version`, `webhook_id` — participate in the signed content; they are parsed straight out of caller-supplied headers [5](#0-4) . Yet `request.shop` is exactly the value forwarded into the handler as the tenant identifier for the event: `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [6](#0-5) .

Because `api_secret_key` is the app-wide `client_secret` (identical for every merchant/shop using the app), an HMAC that is valid for a given body is valid for *that body* regardless of which shop it is claimed to originate from. Formally, the binding the code implicitly relies on is:
`valid_hmac(body, header_shop) == valid_hmac(body, header_shop')` for any `header_shop'`, i.e. the HMAC check answers "is this body genuinely signed by our app secret?" but the code then treats that as if it also answered "did shop `S` send this?" — the two are not equivalent because `S` is never part of the signed material.

An unprivileged actor who can obtain one legitimately-signed webhook payload for *their own* shop (a merchant who installs the app on a shop they control will legitimately receive Shopify-originated webhooks addressed to their own shop, with a valid HMAC computed by Shopify using the app's `client_secret`) can replay the exact same `(raw_body, hmac header)` pair to the app's webhook endpoint while substituting a different value in the `shopify-shop-domain` header. `Webhooks::Request.new` only requires the header to be present, not that it matches any expected value [7](#0-6) , and `HmacValidator.validate` never looks at the shop header at all. The forged request passes `Registry.process`'s only check and is dispatched to the handler tagged with a shop the attacker does not control.

### Impact Explanation
This crosses the tenant boundary the gem is trusted to establish: the merchant application typically uses `WebhookMetadata#shop` to decide which tenant's database record to update/create/delete in response to the webhook (e.g., processing an `orders/create`, `app/uninstalled`, or a data-request GDPR webhook for shop B while it was actually only genuinely signed for shop A). Since the gem provides `shop` as an authenticated-looking field (it comes out of the same object whose `hmac` was "validated"), downstream integrators reasonably treat it as trustworthy without re-validating tenant identity — this is exactly the class of "field acted on but not covered by the HMAC" identity-binding break called out as in-scope. This enables cross-tenant event injection/spoofing without any credential beyond having been a legitimate installer of the app on some shop (an unprivileged, low-barrier position).

### Likelihood Explanation
Likelihood is moderate-to-high: any merchant who installs the app on their own store can capture a genuine webhook (topic/body/hmac) sent by Shopify and replay it with a modified shop header; no cryptographic material or secret needs to be broken since the header simply is not part of the signed content. The main precondition is that the app's webhook consumer trusts `WebhookMetadata#shop` for tenant scoping without independently confirming it against, e.g., a known list of installed shops or additional GraphQL confirmation — which is the natural/expected usage pattern this gem's API encourages by bundling `shop` into the same `WebhookMetadata` struct that carries the "validated" data.

### Recommendation
Bind the tenant identity into the material that is authenticated, or otherwise make it explicit that `shop` is unauthenticated header data:
- At minimum, document prominently that `WebhookMetadata#shop` is **not** covered by the HMAC and must be cross-checked by the integrator against their own list of installed/authorized shops before being used for tenant-scoped operations.
- Where feasible, extend `Webhooks::Request#to_signable_string` (or add a parallel validation) to incorporate the `shop`, `topic`, and `webhook_id` headers so that tampering with any of them invalidates the signature, matching the same fix pattern as the referenced report (extend the checked/verified surface to cover the full set of fields that are subsequently acted upon).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Shopify sends a genuine webhook to the app's endpoint: body `B`, header `shopify-shop-domain: attacker-shop.myshopify.com`, and `shopify-hmac-sha256: HMAC(client_secret, B)`.
3. Attacker replays the same `B` and same `hmac` header to the endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` accepts the request (all required headers present) [7](#0-6) ; `HmacValidator.validate` recomputes `HMAC(client_secret, B)` — unaffected by the shop header — and matches [8](#0-7) .
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [6](#0-5) , causing the app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
