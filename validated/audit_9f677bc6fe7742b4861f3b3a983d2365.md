### Title
Webhook `shop` field is not covered by HMAC verification, allowing shop-identity spoofing on otherwise-valid webhook deliveries - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload solely from the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` accessor used by consuming applications to identify the tenant is taken directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed bytes.

### Finding Description
`Utils::HmacValidator.validate` recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value using `OpenSSL.secure_compare`: [3](#0-2) 

For webhooks, `to_signable_string` is defined as just the raw body bytes: [2](#0-1) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)` — verifying that the *body* bytes are authentic — and then immediately hands the handler `request.shop`, which was parsed straight from an attacker-controllable header, never bound into the signature: [4](#0-3) [1](#0-0) 

This is precisely the "bytes verified versus bytes parsed" / "field acted on but not covered by the HMAC" pattern from the report: the gem cryptographically proves the *body* came from Shopify, but the *shop* value the host app relies on for tenant binding (session lookup, data scoping, `WebhookMetadata.shop`) is unauthenticated. Since a legitimate webhook's HMAC is computed only from the body and the same body can be replayed with a different `shop-domain` header value, an attacker who can obtain (or replay) one valid, previously-delivered webhook body/HMAC pair for topic X (e.g., a webhook their own installed app receives, since Shopify sends the same generic body content for many merchants on common topics, or a body that's identical/predictable across shops) can submit it to the host application's webhook endpoint with a *different* `x-shopify-shop-domain` header, and the signature will still validate because the header is not part of the signed content. The application then processes that payload as if it belongs to the spoofed shop — a cross-tenant data-binding break: `shop_claimed_in_header == shop_that_produced_hmac` is not enforced.

### Impact Explanation
This maps to Critical – cross-tenant access: an attacker can cause a host application to process webhook data attributed to a merchant/shop it doesn't control, potentially triggering shop-scoped side effects (data updates, orders, uninstall handling, etc.) against a victim tenant, purely by controlling the HTTP header on a request they send to the app's public webhook endpoint. No `api_secret_key`, access token, or privileged account is required — only knowledge/observation of one valid raw-body + HMAC pair (bodies for many topics are low-entropy or observable by the attacker's own store), which is an unprivileged-internet-user capability.

### Likelihood Explanation
Moderate-to-high. The attacker needs a valid `(raw_body, hmac)` pair, which is trivial to obtain by installing the app on their own shop and capturing a real webhook delivery (or by triggering webhooks whose body content is attacker-influenced/generic, e.g., app/uninstalled, or bodies with few merchant-specific fields). No cryptographic material besides the intercepted (or self-generated) valid webhook is needed, and the endpoint is by definition internet-reachable.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed/verified material, or independently verify that the header `shop` matches an expected, out-of-band-authenticated value (e.g., cross-check against the shop associated with the app installation) before trusting `request.shop`/`WebhookMetadata.shop`. At minimum, document and enforce that `shop` must never be trusted unless it is corroborated by data authenticated elsewhere (e.g., only accept webhooks for shops with an active session/installation, rather than trusting the header value alone).

### Proof of Concept
1. Attacker installs the target app on their own shop (`attacker.myshopify.com`) and captures a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`, verified per `hmac_validator.rb`).
2. Attacker sends a POST to the host app's webhook endpoint with the same body `B` and the same valid `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H, ...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` (see `to_signable_string` returning `@raw_body`).
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, so the application processes attacker-supplied body content as authentic data for `victim-shop`, despite the shop binding never having been cryptographically verified.
