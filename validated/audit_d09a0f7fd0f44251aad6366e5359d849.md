### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant-identity spoofing via HMAC replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the trusted tenant identifier (`shop`) that gets handed to app-level webhook handlers from an unauthenticated HTTP header, while the HMAC that Shopify supplies only signs the raw JSON body. Because the same `client_secret` is shared across every shop that installs the app, any merchant who installs the app (an "unprivileged internet user" relative to other tenants) can obtain a validly-signed body for their own shop, then replay that exact body against the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `Utils::HmacValidator.validate` will still report the request as valid, and the handler will process the (correctly signed) body under the attacker-chosen shop identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from attacker-controllable HTTP headers, independent of the signature: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., body only) and compares it to the `hmac` field, so it never checks whether `shop`, `topic`, or `webhook_id` were tampered with: [3](#0-2) 

`Registry.process` gates entirely on this body-only HMAC and then constructs `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`, handing it to the app's registered handler as trusted metadata: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(request) == true` should imply `request.shop == the shop Shopify actually generated this exact webhook for`. In this gem, that equality does not hold — `hmac_valid` only proves `raw_body` is authentic for *some* shop using the shared secret, not that `request.shop` is the shop that produced it.

Because `client_secret` (and hence the HMAC secret) is shared across every merchant who installs the app, a malicious merchant can:
1. Install the app on their own store (`attacker-shop.myshopify.com`) and trigger a real webhook event, capturing the resulting `raw_body` and its valid `x-shopify-hmac-sha256` value.
2. Replay a POST to the app's public webhook endpoint with the same `raw_body`/HMAC pair, but with `x-shopify-shop-domain` changed to `victim-shop.myshopify.com` (and optionally a different `topic`/`webhook_id`).
3. `HmacValidator.validate` passes (it never inspected the shop header), `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, and the host application's handler executes attacker-controlled body content under the victim's tenant identity.

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` (as the gem's own API and tests imply it should be trusted, e.g. to look up/act on a specific merchant's session or data) can be made to process attacker-supplied webhook content as if it originated from a different, victim tenant — i.e., cross-tenant data injection/confusion driven entirely through this gem's own webhook-verification API, without needing the victim's or the app's private credentials.

### Likelihood Explanation
Likelihood is Low/Medium in practice: it requires the attacker to be an existing installer of the target app (to obtain one valid signed body/HMAC pair using the shared secret) and requires the host application to trust `WebhookMetadata#shop` for tenant-scoped actions without independently re-validating shop ownership (e.g., matching against a stored, previously-issued session for that shop/webhook_id combination). No access token, refresh token, or `client_secret` theft is needed — only normal app installation and the ability to POST an HTTP request to the app's public webhook endpoint.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` fields into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop identity to the signed body (e.g., include a canonicalized `shop|topic|webhook_id|body` string in `to_signable_string`, matching what `HmacValidator` computes). At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated header data and must not be used as a trusted tenant key by host applications without independent verification (e.g., checking that the shop has an active, previously-established session/webhook subscription for the given `webhook_id`).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing:
   - `raw_body` (JSON payload)
   - `x-shopify-hmac-sha256` (valid HMAC of `raw_body` using the shared `client_secret`)
2. Attacker sends a POST to the app's public webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic`, `x-shopify-webhook-id` set as desired
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — validation succeeds. [5](#0-4) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and processes attacker-controlled body data attributed to the victim tenant.
