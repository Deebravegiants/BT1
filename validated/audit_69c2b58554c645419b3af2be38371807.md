### Title
`describeWithdrawal` matches PoA withdrawals purely by `assetId`, causing txHash/status misreport for duplicate-token withdrawals in one tx - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the withdrawal status via `findMatchingWithdrawal`, which matches solely on `nep141:${w.data.near_token_id} === assetId` and never consults `WithdrawalIdentifier.index`. When a single NEAR transaction contains two `ft_withdraw`/`mt_withdraw` intents for the same `assetId` (e.g. two `btc.omft.near` withdrawals to different destinations), both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` calls select the first array element in the unsorted `response.withdrawals` list, so both watchers can report the same `(status, txHash)` pair for two logically distinct withdrawals.

### Finding Description
The equality that must hold is: for `WithdrawalIdentifier.index = i`, `describeWithdrawal(i)` must resolve `(status, txHash)` corresponding to the outcome of the i-th `ft_withdraw`/`mt_withdraw` intent submitted in that NEAR transaction.

Code path:
- `watchWithdrawal` in [1](#0-0)  calls `bridge.describeWithdrawal({...args.wid, ...})`, passing through `wid.index` unchanged for each withdrawal created by `createWithdrawalIdentifiers`, which assigns per-bridge sequential `index` values to each `WithdrawalParams` entry [2](#0-1) .
- `PoaBridge.describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which never reads `args.index` [3](#0-2) .
- `findMatchingWithdrawal` itself is documented in its own comment as returning the first array element found by `assetId`, explicitly noting: "multiple withdrawals of the same token in a single transaction are not supported" [4](#0-3) .

Root cause: the POA bridge status API returns an unsorted list of withdrawals for a given NEAR tx hash, keyed loosely by token id, and the SDK has no mechanism to disambiguate multiple withdrawals of the same asset within one tx — the code comment itself acknowledges this as a known gap, with a proposed but unimplemented fix (sort by amount).

Attacker input: an ordinary user (or an integrator forwarding user-supplied `withdrawalParams`) submits a single NEAR transaction containing two withdrawal intents with the same `assetId` (e.g., `nep141:btc.omft.near`) but different amounts/destinations. No privileged access or malicious relayer/API is needed — this is a completely ordinary "batch withdraw the same token to two addresses" use case, which the public `WithdrawalParams[]` API allows (nothing in `createWithdrawalIdentifiers` or `supports()`/`validateWithdrawal()` rejects duplicate assetIds in the same batch).

Exploit/failure flow: once both intents land in one NEAR tx and the POA bridge indexes two withdrawal records for that tx hash with the same `near_token_id`, calling `describeWithdrawal` for `index:0` and `index:1` both invoke `Array.prototype.find` over the same unsorted list and get the identical first match — so `watchWithdrawal` for index 0 and index 1 can report the same `(status, txHash)`, or index 0 can report index 1's actual completion data (or vice versa), depending on API ordering.

None of the existing guards prevent this: `validateAddress`, `compareAddresses`, and `validateWithdrawal` only check the per-item destination/amount at request-build time and do nothing to disambiguate two same-asset withdrawals at status-check time; `supports()` ordering is unrelated; there is no sanity `assert` comparing `index` against amount/destination in `describeWithdrawal`.

### Impact Explanation
An integrator relying on `waitForWithdrawalCompletion`/`watchWithdrawal` per-index results to gate off-chain crediting can attribute withdrawal-1's real `txHash` (and completion) to withdrawal-0, or the reverse. This can cause the integrator to believe the wrong withdrawal completed, potentially double-crediting a destination or crediting an operation that has not actually completed — matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. It affects any party consuming per-index `describeWithdrawal`/`watchWithdrawal` results for multi-item same-asset withdrawal batches, and is repeatable on every batch containing duplicate-assetId POA withdrawals.

### Likelihood Explanation
Preconditions: the user (or integrator forwarding user withdrawal params) must submit ≥2 withdrawal intents for the *same* POA `assetId` within a single NEAR transaction — an ordinary, unrestricted operation requiring no special privileges, cost, or timing beyond normal transaction construction. The bug triggers deterministically whenever the POA bridge's status API returns ≥2 records for that tx hash with matching `near_token_id`, which is the expected/normal outcome of such a batch. This is fully repeatable and low-cost for an attacker (or occurs incidentally for a legitimate integrator batching withdrawals of the same token to multiple recipients).

### Recommendation
Disambiguate withdrawals of the same `assetId` within `findMatchingWithdrawal`/`describeWithdrawal`, e.g., by sorting both the requested withdrawal amounts (per `index`) and the API's returned withdrawals by amount (since relayer fees are identical for the same token, relative amount ordering is preserved) and matching by `index` position rather than solely by `assetId`. Alternatively, reject/warn when `createWithdrawalIdentifiers` detects duplicate `assetId` values routed to the PoA bridge within one tx, until the POA API/SDK can uniquely disambiguate withdrawals by index.

import { describe, it, expect, vi } from "vitest";
import { poaBridge } from "@defuse-protocol/internal-utils";
import { PoaBridge } from "./poa-bridge";

describe("findMatchingWithdrawal index collision", () => {
  it("reports the same txHash for both index 0 and index 1 with duplicate assetId", async () => {
    vi.spyOn(poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({
      withdrawals: [
        {
          status: "COMPLETED",
          data: { near_token_id: "btc.omft.near", transfer_tx_hash: "TX_WITHDRAWAL_1", amount: "500" },
        },
        {
          status: "COMPLETED",
          data: { near_token_id: "btc.omft.near", transfer_tx_hash: "TX_WITHDRAWAL_0", amount: "1000" },
        },
      ],
    });

    const bridge = new PoaBridge({ envConfig: /* ... */, xrplRpcUrls: [] });

    const baseParams = {
      assetId: "nep141:btc.omft.near",
      amount: 0n,
      destinationAddress: "addr",
    };
    const tx = { hash: "sometx", accountId: "acc" };

    const statusIndex0 = await bridge.describeWithdrawal({
      landingChain: "somechain",
      index: 0,
      withdrawalParams: baseParams,
      tx,
    } as any);

    const statusIndex1 = await bridge.describeWithdrawal({
      landingChain: "somechain",
      index: 1,
      withdrawalParams: baseParams,
      tx,
    } as any);

    // BROKEN EQUALITY: both indexes resolve to the identical first-found record,
    // i.e. status/txHash for index 0 and index 1 collapse to the same value,
    // even though the correct expectation is txHash(0) === "TX_WITHDRAWAL_0"
    // and txHash(1) === "TX_WITHDRAWAL_1".
    expect(statusIndex0.status).toBe("completed");
    expect(statusIndex1.status).toBe("completed");
    expect((statusIndex0 as any).txHash).toBe((statusIndex1 as any).txHash); // demonstrates the collision
  });
});

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
