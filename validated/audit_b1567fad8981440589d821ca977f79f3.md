### Title
Stale calculation-phase stake delegation used in partitioned epoch reward distribution can desync from live `StakesCache` state, triggering an `assert_eq!` panic - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
`Bank::build_updated_stake_reward` combines a stake reward amount computed at the epoch-boundary "calculation" phase with the stake account's *live* delegation read from `StakesCache` at distribution time (which can be up to `num_partitions` blocks later). When the rent-adjustment relaxation path is not taken (`adjust_delegations_for_rent == false`), the code asserts that `live_delegation + reward == calculation_time_delegation_with_reward`. Because an unprivileged staker can mutate their own stake account's delegation (via `split`/`merge`/`deactivate`/`redelegate`) in any of the blocks between the calculation slot and the specific distribution-partition slot for their account, this invariant is not guaranteed and the assert can fail, panicking the validator process during bank-freeze/commit.

### Finding Description
This is the on-chain analog of the reported bug class: a balance/state snapshot is taken at "request" time (epoch-boundary reward calculation) and is later relied upon as still valid at "settlement" time (distribution, several blocks later), without re-validating it against the account's current state.

`store_stake_accounts_in_partition` reads the **current** stake state for each pubkey from `stakes_cache_accounts` (the live `StakesCache`) at distribution time: [1](#0-0) 

It then calls `build_updated_stake_reward`, which looks up the same live account and destructures its **current** `StakeStateV2::Stake(meta, stake, flags)`: [2](#0-1) 

`new_stake` comes from `partitioned_stake_reward.inflation.stake`, which was computed during the earlier calculation phase (a separate slot, potentially several blocks prior), i.e. it is a **stale snapshot**: [3](#0-2) 

When `adjust_delegations_for_rent` is false, the code does not reconcile stale vs. live delegation values — it instead hard-asserts they must match: [4](#0-3) 

The comment on `delegation_may_need_adjustment` confirms the underlying design problem: lamports/delegation can legitimately change between calculation and distribution, and only the rent-adjustment code path (gated by `adjust_delegations_for_rent`, i.e., the `relax_post_exec_min_balance_check` feature) accounts for this: [5](#0-4) 

The existing test suite even demonstrates awareness of "lamports transferred in before distribution time" as a scenario, but only exercises the path where `adjust_delegations_for_rent` is true (so the delegation-adjustment logic silently handles it) — the `else` branch's `assert_eq!` is never exercised against a genuinely diverged live delegation: [6](#0-5) 

### Impact Explanation
If triggered, `assert_eq!` panics the bank-processing thread while committing a block that falls inside the active partitioned-rewards distribution window. Because reward distribution is part of consensus-critical bank state (capitalization, stake state, and the `EpochRewards` sysvar), a panic here would be hit deterministically by every validator processing that slot, producing a network-wide halt rather than a fork — a high-impact liveness failure reachable without any validator/operator privilege, purely from a staker's ordinary stake-management transactions (`split`, `merge`, `deactivate`, `redelegate`, `withdraw`) executed in the wrong slot window.

### Likelihood Explanation
Reachability depends on the `adjust_delegations_for_rent` feature flag (tied to `relax_post_exec_min_balance_check` / SIMD-392) being inactive; if that feature is permanently active on the current mainnet feature set, the vulnerable `else` branch is dead code in practice, which would make this a low/no likelihood legacy-path issue rather than a live one. I was not able to conclusively determine from the available index whether `relax_post_exec_min_balance_check` is unconditionally active by default in this codebase version (feature-gate activation state lives in `feature-set/src/lib.rs`, and I could not fully inspect its activation slot/epoch or whether it's already baked-in as always-true). If the feature is still gateable/not yet activated on any live cluster using this code, likelihood is Medium (requires only ordinary stake instructions timed within the multi-block distribution window, no special access).

### Recommendation
- Remove the hard `assert_eq!` in the `adjust_delegations_for_rent == false` branch of `build_updated_stake_reward`, or gracefully error/skip the account (recording it under `stake_reward_lamports_burned`, as already done for `Err` results in `store_stake_accounts_in_partition`) instead of panicking.
- Alternatively, apply the same delegation-reconciliation logic used in the `adjust_delegations_for_rent == true` branch universally, so distribution always computes the final delegation from the account's live state at distribution time rather than assuming the calculation-time snapshot is still valid.
- If `relax_post_exec_min_balance_check` is already unconditionally active for all supported clusters, confirm this and remove the dead legacy branch entirely to eliminate the unreachable-but-latent panic path.

### Proof of Concept
Conceptual PoC (could not be executed, index is read-only):
1. At an epoch boundary, `distribute_partitioned_epoch_rewards` computes and partitions stake rewards across N blocks, recording each account's calculation-time `partitioned_stake_reward.inflation.stake` (derived from the pre-distribution delegation).
2. Before the specific partition/block that will process a given staker's account is reached, the staker submits an ordinary `Split`, `Merge`, or `Deactivate` stake instruction that changes `StakeStateV2::Stake(..).delegation.stake` for that account in the live `StakesCache`.
3. When `distribute_epoch_rewards_in_partition` reaches that account's partition, `build_updated_stake_reward` reads the now-different live `stake.delegation.stake` and compares `expected_delegation = live_stake + reward` against the stale `new_stake.delegation.stake` computed at calculation time — these differ, and `assert_eq!` panics the bank-processing code path for every validator committing that slot.
