### Title
Webhook shop/topic identity spoofing via HMAC binding gap - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by verifying only the raw request body against the `X-Shopify-Hmac-Sha256` header, but the `shop`, `topic`, `webhook_id`, and `api_version` values that the handler acts on are taken from separate, unauthenticated HTTP headers that are never part of the signed payload. This breaks the identity binding: `hmac(raw_body) == valid` is treated as proof that `(shop, topic)` are also authentic, when in fact `shop` and `topic` are attacker-controlled inputs independent of the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from request headers, none of which are covered by the signable string: [2](#0-1) 

`Registry.process` validates only the body's HMAC and then dispatches the handler using the unauthenticated `shop`/`topic` header values as if they were verified: [3](#0-2) 

This is the same bug class as the referenced report: a field that downstream logic acts on (`shop`, the identity that a fee/route/handler decision hinges on) is not covered by the cryptographic check (the HMAC / referrer routing), so the authenticated value and the acted-upon value can diverge. Concretely: `hmac_valid(raw_body) == true` is treated as equivalent to `request.shop == genuine_source_shop`, but the equality never actually holds because `shop` is read from a header outside the signed scope.

Exploit path: An attacker who operates their own shop with the app installed legitimately receives real, validly-signed webhooks from Shopify for topics whose bodies carry no shop-specific data (e.g., topics with an effectively empty or shop-agnostic JSON body). Capturing one such `(raw_body, hmac)` pair, the attacker can replay the exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it only checks `raw_body` against the secret-derived signature, and `Registry.process` forwards the attacker-chosen `shop`/`topic` to the handler unchanged.

### Impact Explanation
This allows cross-tenant identity spoofing: business logic that is keyed off `WebhookMetadata#shop` (e.g., session/data cleanup on `app/uninstalled`, state changes gated on a specific shop) can be triggered for a shop the attacker does not own, using a signature that was never generated for that shop. This matches the "Critical - cross-tenant access" impact bucket, since a value trusted as tenant identity is not actually bound by the authentication mechanism protecting the request.

### Likelihood Explanation
Requires only that the attacker control one shop with the app installed (an ordinary, unprivileged merchant tenant) and that at least one subscribed webhook topic have a body that doesn't uniquely encode the originating shop (many lightweight/system topics qualify). No access token, `client_secret`, or elevated privilege is needed — only observation of one legitimate webhook delivery to their own store.

### Recommendation
Include `shop`, `topic`, and any other header-derived fields the application relies on in the value that is HMAC-verified (or otherwise cryptographically bind them, e.g. by validating them out-of-band against the recipient's known/installed shop list), rather than trusting header values that sit outside the signed scope. At minimum, `Registry.process` should cross-check `request.shop` against the shop associated with the currently active/expected session before invoking the handler.

### Proof of Concept
1. App subscribes to a webhook topic whose payload body has no shop-identifying content (e.g., `{}`).
2. Attacker's own shop (attacker is a legitimate, unprivileged tenant of the multi-tenant app) receives this real webhook from Shopify with header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`.
3. Attacker resends the identical raw body and HMAC header to the app's webhook endpoint, replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` at `lib/shopify_api/webhooks/registry.rb:190` succeeds because it only checks the body signature.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` runs with `shop == "victim-shop.myshopify.com"`, even though Shopify never sent this webhook for that shop.
