### Title
Webhook `shop`, `topic`, and `webhook_id` are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking the HMAC of the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's webhook handler are read from unauthenticated HTTP headers that are never included in the signed content. An attacker who is able to obtain one legitimate `(raw_body, hmac)` pair addressed to their own shop can replay that exact body/HMAC pair while substituting a different shop's domain in the header, and the library will accept it as an authentic webhook "from" that other tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all derived from HTTP headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the body only) and compares it to the received `hmac` header: [3](#0-2) 

`Registry.process` validates only that HMAC before constructing `WebhookMetadata` from the unauthenticated headers and dispatching it to the app's handler: [4](#0-3) 

The identity binding this breaks is: `shop` (and `topic`/`webhook_id`) claimed in the request headers == `shop` that produced/is bound to the HMAC-covered body. In truth, the HMAC only proves "this body was signed with the app's secret at some point for some webhook delivery" — it proves nothing about which shop, topic, or webhook the body belongs to. Any two fields (body, headers) can be freely recombined by anyone who has seen one legitimate delivery, because the header values are never mixed into the signed material.

This is a direct analog to the report's core bug class: a field (`shop`) that is acted upon (used to select/scope tenant data in the app built on this library) is not covered by the cryptographic check (HMAC) that is supposed to authenticate the request.

### Impact Explanation
This enables cross-tenant confusion: an attacker who legitimately installs the target app on their own shop can capture a real webhook delivery (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`, or any topic delivering attacker-influenced body content) and replay the exact same body + HMAC to the app's public webhook endpoint while spoofing `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) to name a victim shop. Because `Registry.process` and `HmacValidator.validate` only check the body's HMAC, the forged request passes verification, and the host application's webhook handler receives a `WebhookMetadata` claiming the (attacker-chosen) victim shop, topic and webhook id, causing the app to perform per-tenant actions (e.g., mark another shop as uninstalled, trigger GDPR redaction/data-request flows, or otherwise mutate state) against a tenant the attacker does not control. This is a cross-tenant access impact.

### Likelihood Explanation
Any internet user can create a Shopify development/free store, install a public app built with this gem, and thereby receive real webhook deliveries with valid HMACs for content they at least partly influence (e.g., triggering `app/uninstalled` by uninstalling their own app, or shop-level topics). No access to the app's `api_secret_key` or any privileged credential is needed — only the ability to observe headers/body of a webhook delivered to infrastructure they control. Combined with the trivial replay (just changing the shop header), this is straightforward for a motivated unprivileged attacker.

### Recommendation
Bind the values used to route/process the webhook to the material that is HMAC-verified. At minimum, include `shop`, `topic`, and `webhook_id` in `to_signable_string` (matching what Shopify's own delivery guarantees expect), or independently re-validate that the webhook (by its `webhook_id`) is genuinely registered for the `shop` claimed in the header (e.g., cross-check against the shop's registered webhook subscriptions via the Admin API) before dispatching to the handler. Additionally, since HMAC alone doesn't prevent replay, consider tracking/deduplicating `webhook_id` values per shop to reject reprocessed deliveries.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook, e.g. `app/uninstalled`, capturing the raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because it's genuinely signed by Shopify with the app's secret for this delivery).
2. Attacker sends a new HTTP POST to the app's public webhook route with:
   - body = `B` (byte-for-byte identical)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
   - `X-Shopify-Topic: app/uninstalled` (unchanged or attacker-chosen)
3. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: spoofed_headers))`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, passes. [4](#0-3) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)` and the host app performs uninstall/cleanup logic against `victim-shop`, even though `victim-shop` never sent or authorized this event.
