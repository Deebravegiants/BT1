### Title
Unvalidated swap routes can invoke attacker-controlled contracts that steal unrelated caller funds - (File: contracts/controller/src/strategies/swap.rs) [1](#0-0) 

### Summary

`swap_collateral` accepts a caller-supplied opaque `swap` payload and forwards it to the configured router without constraining which pool contracts the route may invoke. [2](#0-1) [1](#0-0) 

A malicious venue or pool reached by that route can request a token transfer from the swap caller while executing below the caller’s top-level authorization, causing the unauthorized transfer to appear as a child authorization that the caller may sign. [3](#0-2) [4](#0-3) 

### Finding Description

The public `swap_collateral(caller, account_id, current, amount, new, swap)` entrypoint accepts `swap` as arbitrary bytes supplied by the caller. [2](#0-1) 

After owner-or-delegate authorization, `process_swap_collateral` withdraws `amount` of `current`, invokes `withdraw_and_swap_from_supply`, redeposits the measured proceeds into `new`, and performs the final strategy risk check. [5](#0-4) 

The swap helper grants the router one exact input-token transfer and invokes `router.execute_strategy(controller, amount_in, swap)`, but it performs no validation of the route’s venue or pool addresses before execution. [6](#0-5) 

The documented router behavior permits payload-selected pool and token addresses without an allowlist, allowing third-party contract code to execute beneath the caller’s authorization tree. [7](#0-6) 

That contract can request a token transfer from the caller for a token unrelated to the swap input, and Soroban records the transfer as a child of the caller’s `swap_collateral` authorization. [8](#0-7) [4](#0-3) 

### Impact Explanation

An attacker can steal arbitrary spendable token balances from a user who signs a malicious swap authorization tree, while still returning enough swap output for the controller’s positive-output and solvency checks to pass. [9](#0-8) 

The loss is not limited to the collateral being routed because the malicious subcall can name a different wallet token, transfer amount, and recipient. [10](#0-9) [11](#0-10) 

The same route-submission surface is reachable through the other strategy entrypoints that accept a swap payload, including `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [12](#0-11) [13](#0-12) [14](#0-13) 

### Likelihood Explanation

Any unprivileged user can deploy a malicious venue contract and construct a route naming that contract; no privileged role, leaked key, oracle manipulation, or protocol-owned funds are required. [10](#0-9) 

Successful exploitation requires the victim to sign the poisoned authorization tree, but the malicious transfer is nested under the otherwise legitimate `swap_collateral` invocation rather than requiring separate wallet approval. [15](#0-14) [4](#0-3) 

The protocol’s own threat model places the mitigation on clients decoding the route and rejecting unexpected authorization children, which means a wallet or frontend that trusts a quoted route exposes its users to this behavior. [16](#0-15) 

### Recommendation

Constrain route-selected venue and pool addresses to a protocol-approved registry or cryptographically derivable venue deployment before executing the swap. [1](#0-0) [17](#0-16) 

The route format should bind each hop to validated pool and token pairs, and execution should reject any venue capable of requesting authorization from the original caller or transferring unrelated caller assets. [18](#0-17) [19](#0-18) 

Client-side authorization-tree inspection should remain a defense-in-depth measure rather than the protocol’s primary protection against attacker-controlled route contracts. [16](#0-15) 

### Proof of Concept

1. Alice owns a funded lending account and also holds an unrelated token in her wallet. [20](#0-19) 

2. The attacker deploys a pool contract whose `swap` function loads a stored plan and calls `token.transfer(victim, attacker, amount)`. [21](#0-20) 

3. The attacker encodes the malicious pool address into the swap payload while keeping a fair output amount so the surrounding strategy still settles successfully. [10](#0-9) 

4. Alice invokes `swap_collateral(alice, account_id, current=USDC, amount, new=ETH, swap=malicious_route)`; the controller verifies Alice is authorized and forwards the route into the swap flow. [2](#0-1) [22](#0-21) 

5. The router invokes the payload-selected pool, which requests the unrelated wallet-token transfer from Alice to the attacker. [23](#0-22) [19](#0-18) 

6. Simulation records that stolen transfer as a child authorization beneath Alice’s `swap_collateral` invocation, and signing that tree empties Alice’s unrelated wallet-token balance while crediting the expected swap output. [24](#0-23)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
