### Title
Webhook shop-domain (and topic/webhook-id) header is trusted by `ShopifyAPI::Webhooks::Registry.process` without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the **raw body**, then hands the handler a `shop` value taken from the `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header, which is never included in the signed material. Any party who can obtain one genuine, validly-signed webhook body/HMAC pair (e.g., by owning a shop that installs the app) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` header value. The gem will report the HMAC as valid and pass the attacker-chosen `shop`/`topic`/`webhook_id` to the app's handler as if it were authenticated.

### Finding Description
The identity binding that should hold is:

`shop reported to the handler == shop that Shopify actually signed the payload for`

Instead the code implements:

`hmac_valid(raw_body) AND shop_used_by_handler = header["shopify-shop-domain"]` (header not part of signed input)

Evidence:

- `Request#hmac` reads the signature strictly from a header: [1](#0-0) 

- `Request#to_signable_string` — the only bytes that are ever HMAC-verified — is just the raw body, with no header data mixed in: [2](#0-1) 

- `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controlled headers and are never part of `to_signable_string`: [3](#0-2) 

- `Registry.process` validates only the HMAC (over the body) and then constructs the metadata handed to the app's handler directly from those unauthenticated header-derived fields (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`): [4](#0-3) 

- `HmacValidator.validate_signature` confirms the comparison is exactly `HMAC(secret, to_signable_string)` vs. the header HMAC — again, body-only, no headers: [5](#0-4) 

Because `shop` is not bound to the signature, "HMAC valid" does not imply "this body belongs to this shop." An unprivileged actor who legitimately receives real webhook deliveries for their own shop (any developer/merchant can install the app and receive genuine webhooks) can capture a `(raw_body, hmac)` pair and resend it to the app's public webhook endpoint with a different `shopify-shop-domain` header. `Registry.process` will accept it, and the handler will process the payload under the attacker-chosen shop identity, since the equality "authenticated shop == handler shop" never actually holds.

### Impact Explanation
This is a cross-tenant identity-binding break carried into every webhook handler the host application registers (order/customer/app-uninstalled data, etc.), because the gem hands the handler a `shop` value that was never authenticated. Depending on how the host application keys its per-shop data/session lookups off `WebhookMetadata#shop` (a pattern explicitly documented/expected by this gem, e.g., `data.shop` in the test suite), this can let one tenant's genuine webhook body be attributed to another tenant, corrupting per-shop state, or - most severely - trigger the mandatory `app/uninstalled` handling logic against a shop the attacker does not own, causing cross-tenant data loss or state corruption purely by manipulating an unauthenticated header value. This matches the "cross-tenant access" / "field acted on but not covered by the HMAC" bug class called out in scope.

### Likelihood Explanation
Reachability is high: the webhook endpoint is intentionally public and unauthenticated apart from the HMAC. Obtaining a genuine `(body, hmac)` pair requires nothing more than installing the app on a shop the attacker controls and observing one real webhook delivery — no access token, no `api_secret_key`, and no privileged account are needed, satisfying the "unprivileged internet user" constraint. The only friction is that the replayed payload's *content* still belongs to the attacker's own shop (the body itself is unmodified, since altering it would invalidate the HMAC) — but the header-derived `shop`, `topic`, `webhook_id` fields handed to the handler are fully attacker-controlled at replay time.

### Recommendation
Bind the identity fields the handler relies on into the HMAC input, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the signed payload (e.g., verify against Shopify by making a follow-up authenticated API call scoped to `request.shop` before trusting it, or document/require that host apps independently re-validate `shop` against their own installed-shop registry before trusting webhook metadata). At minimum, update `Request#to_signable_string` guidance/docs to make clear that `shop`, `topic`, and `webhook_id` are NOT authenticated by the HMAC check, so host applications do not treat `WebhookMetadata#shop` as a trusted tenant identifier without independent verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and receives a genuine webhook delivery, capturing:
   - raw body `B`
   - header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`)
2. Attacker POSTs to the app's webhook endpoint with:
   - body: `B` (unchanged, so `H` still validates)
   - headers: `x-shopify-hmac-sha256: H`, `x-shopify-topic: <same or different topic>`, `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and finds it matches `H` — validation passes: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, i.e., a validly-"authenticated" webhook falsely attributed to `victim-shop.myshopify.com`: [7](#0-6) 

Any host-application logic keyed on `data.shop` (session lookup, per-tenant storage, uninstall cleanup, etc.) now operates on attacker-chosen tenant identity despite passing HMAC verification.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
