### Title
Tron `IntentGatewayV2.onAccept` applies `UpdateParams` without validating fields, unlike the EVM/host-chain implementation - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2` writes governance-supplied `Params` directly to storage on `RequestKind.UpdateParams` with no bounds or sanity checks, whereas the canonical EVM implementation of the same gateway (`ExtrinsicIntents.sol`/`IntentsBase.sol`) routes the identical update through `_validateParams` before writing. This is the same bug class as CVE-2016-0753: a writer path exists that bypasses the validation the "real" setter enforces.

### Finding Description
On the EVM host chain, `UpdateParams` is handled by `_updateParams`, which calls `_validateParams(update.params)` before committing the new `Params` struct: [1](#0-0) 

`_validateParams` rejects a zero/non-contract `host`, a zero/non-contract `dispatcher`, `surplusShareBps > 10_000`, `protocolFeeBps >= 10_000`, and a non-contract `priceOracle`.

The Tron variant of the same gateway decodes the identical `ParamsUpdate` struct from the identical `RequestKind.UpdateParams` discriminator, but writes `_params = update.params` unconditionally, with no call to any validation routine: [2](#0-1) 

Both paths are reached the same way: `onAccept` first checks `RequestKind`, then gates non-withdrawal actions to messages sourced from Hyperbridge itself: [3](#0-2) 

Because this is a "governance" instance-level writer that skips the shared invariant enforced everywhere else in the codebase, any malformed, buggy, or unexpectedly-encoded `UpdateParams` payload relayed through this path (a relayer submitting a proof of a Hyperbridge-originated request) lands unchecked: `host`/`dispatcher` can be set to `address(0)` or a non-contract address, `protocolFeeBps`/`surplusShareBps` can exceed 10,000 (100%), and `priceOracle` can point at an EOA or dead address.

### Impact Explanation
- Setting `dispatcher` to zero or a non-contract address breaks every subsequent `placeOrder`/withdrawal flow that reads `_params.dispatcher`, permanently freezing escrowed order funds already recorded in `_orders`, since `withdraw` needs a working dispatch path for cross-chain post-fill/refund flows and predispatch calls depend on `_params.dispatcher`.
- Setting `host` to zero/non-contract breaks `host()`/`IDispatcher(host()).hyperbridge()` checks used throughout `onAccept`, `authenticate`, and dispatch logic, potentially bricking the contract's ability to process any further incoming or outgoing governance/user messages — a permanent freeze of funds already escrowed.
- `protocolFeeBps >= 10_000` or `surplusShareBps > 10_000` breaks fee-percentage arithmetic used at order placement/fill time (fee = amount * bps / 10_000 patterns elsewhere in the codebase), which can cause reverts that make legitimate order flows permanently unusable, or (depending on the exact arithmetic used downstream) fee/surplus miscalculation that misallocates escrowed value.

This matches the required bar: "concrete theft or permanent freezing of funds ... unauthorized app action" reachable via a relayed message on the intent-escrow path.

### Likelihood Explanation
Reaching this path requires a relayer to deliver a Hyperbridge-sourced `UpdateParams` message with a verified proof — this is the same trust boundary already exercised on the EVM chain, where the identical message kind is exhaustively validated. The vulnerability is not that governance is malicious, but that on Tron the validation invariant the rest of the protocol relies on (and tests against, e.g. `testOnAcceptUpdateParams*` in `evm/tests/foundry/IntentGatewayV2Test.sol`) silently does not exist for this deployment target — any bug in the Hyperbridge-side encoder (`ParamsUpdate` construction), a stale/incorrect off-chain params computation, or a relayer replaying an older/malformed proof that still passes consensus verification, applies unchecked fields with no on-chain backstop. Given the codebase's own EVM implementation demonstrates this exact class of input needs validation, and Tron is a maintained, deployed chain target within the same monorepo, this is a real, reachable regression rather than a hypothetical.

### Recommendation
Add the same `_validateParams`-equivalent check (host/dispatcher non-zero and code-bearing, `surplusShareBps <= 10_000`, `protocolFeeBps < 10_000`, `priceOracle` zero-or-contract) to the Tron `IntentGatewayV2.onAccept`'s `UpdateParams` branch before writing `_params = update.params`, mirroring `IntentsBase._validateParams` used by the canonical EVM gateway, and add a regression test (parallel to `IntentGatewayV2Test.sol`'s `testOnAcceptUpdateParams*`) asserting that out-of-range `protocolFeeBps`/`surplusShareBps` or zero `host`/`dispatcher` are rejected on Tron.

### Proof of Concept
1. Hyperbridge (or a bug in the params encoder / stale off-chain state) dispatches a `PostRequest` to the Tron `IntentGatewayV2` with body `[RequestKind.UpdateParams] ++ abi.encode(ParamsUpdate{params: Params{host: address(0), dispatcher: address(0), surplusShareBps: 20000, protocolFeeBps: 10000, ...}, destinationFees: []})`.
2. The authorized relayer submits the proof through the handler; `onAccept` verifies `request.source == hyperbridge` and decodes the body.
3. Unlike the EVM contract (which would revert with `InvalidInput` in `_validateParams`), the Tron contract executes `_params = update.params;` unconditionally at [4](#0-3) .
4. Subsequent calls relying on `_params.dispatcher`/`_params.host` (order placement, escrow release/refund, fee computation) fail or misbehave, freezing any tokens already escrowed in `_orders` for outstanding intents on that chain.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return withdraw(body, kind == RequestKind.RefundEscrow);
        }

        // only hyperbridge is permitted to perfom these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            NewDeployment memory body = abi.decode(incoming.request.body[1:], (NewDeployment));
            _instances[keccak256(body.stateMachineId)] = body.gateway;

            emit NewDeploymentAdded({stateMachineId: body.stateMachineId, gateway: body.gateway});

            // Decode the body which includes optional destination-specific protocol fee updates
