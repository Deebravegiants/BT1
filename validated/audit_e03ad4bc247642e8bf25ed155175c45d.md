### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identifier passed to the app's handler after only validating the body's HMAC. This breaks the intended binding `HMAC-verified bytes == data acted upon`; in reality `HMAC-verified bytes == raw_body only`, while `shop` (the tenant key) is taken from a header that is never part of the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the received `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then immediately constructs `WebhookMetadata` using `request.shop` (and `request.topic`, `request.webhook_id`) as trusted tenant-identifying values passed to the app-supplied handler: [4](#0-3) 

This is documented as verifying provenance: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook," and the handler is told it can trust `data.shop` as "The shop domain of the webhook": [5](#0-4) [6](#0-5) 

The root cause mirrors the report's bug class: code that verifies one thing (the raw body bytes via HMAC) is unsoundly assumed to authenticate a broader structure (the full webhook context, including which shop it came from). Because the `shop-domain` header sits entirely outside the signed material, an attacker who can obtain any single genuine `(raw_body, hmac)` pair — trivially available to any developer who installs the (often public) app on their own store and receives real webhook deliveries at the app's single shared webhook endpoint — can replay that exact body/HMAC pair to the same endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain. The signature still validates because it never depended on that header, and `Registry.process` will invoke the handler believing the payload originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an unprivileged actor (any merchant/developer who can install the app, which is the normal, unprivileged way to interact with a Shopify app) can forge webhook events attributed to a different shop by replaying their own genuine webhook body under a spoofed shop identity. Any app logic that uses `data.shop` from `WebhookMetadata` to scope writes, cache invalidation, order/customer record updates, or trigger downstream actions per-tenant can be tricked into acting on/for the wrong tenant, i.e., cross-tenant data corruption or cross-tenant action injection — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for apps that key any state or side effects off `data.shop`/`data.topic`/`data.webhook_id` (the gem's documented usage pattern, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)` shown in the docs) since:
- The webhook endpoint is a single shared URL for all shops using the app.
- Any legitimate installer of the app (self-service, unprivileged) can capture a real, validly-signed `(body, hmac)` pair from their own webhook traffic.
- No additional secret or privilege is required to alter the `shop-domain` header and replay the request.

### Recommendation
Bind the tenant-identifying fields into the signed material, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the HMAC check:
- Reject/flag replay by tracking `webhook_id` uniqueness per verified request (mitigates replay but does not itself bind `shop`).
- More directly, have `HmacValidator`/`VerifiableQuery` incorporate `shop`, `topic`, and `webhook_id` into the signable string comparison logic, or validate that the `shop` header is consistent with out-of-band knowledge (e.g., cross-check against the registered webhook subscription's known shop before invoking the handler), rather than trusting the header value verbatim once only the body HMAC has passed.
- At minimum, update the documentation to make clear that only the raw body is authenticated by the HMAC check, so integrators are not misled into trusting `data.shop`/`data.topic`/`data.webhook_id` as verified.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop `attacker.myshopify.com` — a normal, unprivileged installation flow.
2. Shopify delivers a genuine webhook to the app's shared webhook endpoint, e.g.:
   ```
   POST /webhooks
   shopify-topic: orders/create
   shopify-hmac-sha256: <valid-hmac-of-body>
   shopify-shop-domain: attacker.myshopify.com
   shopify-webhook-id: <id>

   {"id": 123, "note": "attacker-controlled order payload"}
   ```
3. Attacker captures this exact `(raw_body, hmac)` pair (they receive it themselves, no interception needed) and replays it to the same endpoint, changing only the shop header:
   ```
   POST /webhooks
   shopify-topic: orders/create
   shopify-hmac-sha256: <same-valid-hmac-of-body>
   shopify-shop-domain: victim-shop.myshopify.com
   shopify-webhook-id: <same-or-new-id>

   {"id": 123, "note": "attacker-controlled order payload"}
   ```
4. `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) raw body and it matches, per `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
5. `Registry.process` proceeds and invokes the registered handler with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, per `lib/shopify_api/webhooks/registry.rb` lines 188-200 — even though the payload never actually originated from that shop.
