Audit Report

## Title
Response cache keyed by `WorkflowOwner` instead of `WorkflowID` causes cross-workflow HTTP response leakage - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
The Gateway's HTTP-action `responseCache` deduplicates and serves cached responses using `OutboundHTTPRequest.Hash()`, which the repo's own test suite proves excludes `WorkflowID` while including `WorkflowOwner`. As a result, two distinct workflows owned by the same address that issue outbound HTTP actions with identical method/URL/headers/body collide on the same cache key, causing one workflow to receive an HTTP response that was actually fetched and cached on behalf of a different, sibling workflow.

## Finding Description
`responseCache` stores and retrieves entries keyed by `req.Hash()` in `isExpiredOrNotCached`, `Fetch`, and `Set`: [1](#0-0) , [2](#0-1) , [3](#0-2) .

The repo's own test suite explicitly documents and asserts that `Hash()` is invariant to `WorkflowID` while varying with `WorkflowOwner`: [4](#0-3) , and confirms that same-owner requests hash identically while different-owner requests hash differently: [5](#0-4) .

This directly contradicts the component's documented design intent, which states cache entries should be scoped by workflow ID specifically "to prevent cross-workflow data leakage." The cache is consumed on every outbound HTTP action from `makeOutgoingRequest`, gated only by `req.CacheSettings.MaxAgeMs`/`Store`, with no workflow-identity check between fetch and hit: [6](#0-5) . Because `Hash()` (defined upstream in `chainlink-common`) omits `WorkflowID`, any two workflows under the same owner issuing the same outbound HTTP request pattern will transparently share cache entries, with no existing check compensating for this gap.

## Impact Explanation
This maps to cross-user/cross-workflow response corruption: a workflow can silently receive an HTTP response payload that was fetched and cached on behalf of a different workflow belonging to the same owner. If the external endpoint's response is sensitive or context-dependent, this constitutes data leakage between logically distinct workflows and can propagate incorrect data into downstream on-chain decision logic. Severity is Medium given it is confined to workflows sharing the same owner and depends on identical request shape.

## Likelihood Explanation
This requires no privileged or malicious-node access — it is triggerable purely by a normal, unprivileged workflow owner running two or more workflows that issue outbound HTTP actions with the same method/URL/headers/body and non-zero `CacheSettings.MaxAgeMs`/`Store`, a realistic scenario for common third-party API integrations (e.g., multiple workflows polling the same public endpoint). This makes the bug practically reachable and repeatable.

## Recommendation
Include `WorkflowID` in the value hashed by `OutboundHTTPRequest.Hash()` (in `chainlink-common`) so requests from different workflows never collide on cache keys, matching the documented design intent. Update/replace the test at `response_cache_test.go` lines 139-149 to assert that different `WorkflowID` values produce different hashes.

## Proof of Concept
1. Workflow A (`WorkflowOwner = 0xabc`, `WorkflowID = "wf-A"`) issues `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings:{Store:true, MaxAgeMs:600000}}`; gateway fetches and caches the response under `req.Hash()`.
2. Workflow B (`WorkflowOwner = 0xabc`, `WorkflowID = "wf-B"`) issues an outbound HTTP action with identical method/URL/headers/body and `CacheSettings.MaxAgeMs > 0`.
3. As demonstrated by the existing unit test `TestRequestHash/having different workflowID results in same Hash` [4](#0-3) , `req.Hash()` is identical for both workflows.
4. `responseCache.Fetch`, invoked from `makeOutgoingRequest` [7](#0-6) , returns Workflow A's cached response to Workflow B without making a fresh request, confirming cross-workflow response leakage.

func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
