### Title
Webhook shop domain is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop` (parsed from the `x-shopify-shop-domain` header) as the tenant identifier that `Registry.process` hands to the app's webhook handler, but the HMAC signature computed by `Utils::HmacValidator` only ever covers the raw request body, never the shop header. Because the signing secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that installs the app, any unprivileged user who installs the app on their own store can capture a legitimately-signed webhook and replay it with a forged `x-shopify-shop-domain` header pointing at a different (victim) shop. The signature still validates, and the handler processes the payload as if it originated from the victim tenant — a cross-tenant identity-binding break of the same class as the referenced report (an acted-upon field that is not covered by the integrity check).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an attacker-controllable header, entirely independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` verifies exactly that signable string (the body) against the HMAC using the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` trusts `request.shop` as the tenant for the handler call once the body HMAC passes, with no separate binding between `shop` and the signature: [4](#0-3) 

The identity binding that is broken is: `shop authenticated (by HMAC) == shop acted upon (WebhookMetadata#shop passed to the handler)`. Before the attack, both sides are equal for a genuine webhook. After the attack, the attacker satisfies the HMAC check (body+signature pair captured from their own store's install of the app, since `api_secret_key` is shared per-app, not per-shop) while substituting an arbitrary `shop` value, so the two sides diverge: the verified bytes (body) say nothing about tenant, but the acted-upon field (`shop`) determines which tenant's data the host application updates.

### Impact Explanation
This is a cross-tenant access vector: an app that keys any state, side effects, or session lookups off `WebhookMetadata#shop` (the intended and documented usage of this field) can be made to apply another merchant's webhook payload/side effects under an attacker-chosen shop identity, without needing the app's `client_secret`, an access token, or any privileged credential — only a legitimate, low-privilege install of the target app on any store. This matches the Critical impact bucket (cross-tenant access) defined for this scan.

### Likelihood Explanation
High. The prerequisite is simply installing the target app on any store (a normal, unprivileged action for any Shopify merchant/developer) and triggering any subscribed webhook topic on that store to capture a valid `(body, hmac)` pair, since `api_secret_key` is shared across all shops using the app. No secret material, TLS interception, or social engineering is required — only sending a normal HTTP POST to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header and the captured `body`/`hmac`.

### Recommendation
Bind the shop identity into the verified material, e.g. include the `x-shopify-shop-domain` (and ideally `x-shopify-webhook-id`) value in the string that is HMAC-verified, or require host applications to cross-check `request.shop` against an independently known, previously-registered shop for that webhook/session before trusting it in `Registry.process`. At minimum, document that `Request#shop` is unauthenticated and must be independently verified by the host application before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (normal, unprivileged flow).
2. Attacker triggers any subscribed webhook topic (e.g. `products/update`) on their store, capturing the raw POST body and its `x-shopify-hmac-sha256` header — both valid under the app's shared `api_secret_key`.
3. Attacker sends the same body/HMAC pair to the app's public webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (body signature unchanged), `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the app's handler executes tenant-scoped logic against the victim shop using attacker-supplied data.
