Audit Report

## Title
Gateway `responseCache` cache key omits `WorkflowID`, allowing cross-workflow disclosure of cached HTTP response headers (including `Set-Cookie`) among workflows sharing the same `WorkflowOwner` - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
The `responseCache.Set`/`Fetch` functions in `core/services/gateway/handlers/capabilities/v2/response_cache.go` cache the full `OutboundHTTPResponse` (all headers, including `Set-Cookie`) keyed by `req.Hash()`. `TestRequestHash` in `response_cache_test.go` demonstrates that this hash is invariant to `WorkflowID` while depending on `WorkflowOwner`, directly contradicting the component's own README, which states the cache key is "generated from workflow ID and request hash" and that entries are "scoped by workflow ID to prevent cross-workflow data leakage."

## Finding Description
`responseCache.Set` stores `rc.cache[req.Hash()] = &cachedResponse{response, storedAt}` [1](#0-0) , and `Fetch` retrieves and replays the same cached value based purely on `req.Hash()` [2](#0-1) . The test suite proves the hash explicitly ignores `WorkflowID` ("Hash should be the same regardless of WorkflowID") while distinguishing on `WorkflowOwner` [3](#0-2) . Meanwhile the README explicitly documents the opposite design: "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [4](#0-3) . The lookup/store call sites in `makeOutgoingRequest`/the HTTP action handler pass caller-controlled `CacheSettings.Store`/`MaxAgeMs` without any additional workflow-scoping logic before invoking `Fetch`/`Set` [5](#0-4) . Since two distinct workflows registered under the same on-chain owner address (a common pattern for platforms/integrators deploying multiple customer-facing workflows under one owner key) that issue byte-identical outbound requests (method/URL/headers/body) will collide on the same cache key, a response containing session-specific `Set-Cookie`/auth headers from one workflow's external call can be replayed verbatim into a completely different workflow's execution.

## Impact Explanation
This is a cross-workflow response/secret disclosure (CWE-285-class) that breaks a documented isolation guarantee: a response destined for one workflow execution (potentially containing a session cookie, CSRF token, or other per-invocation secret from an external endpoint) can be silently delivered to a different, unrelated workflow sharing the same owner address — a realistic setup for platforms/integrators running multiple customer workflows under a single deployer key. This maps to the "cross-user response corruption" impact category since the actual downstream consumers of the two workflows' outputs can be different parties even though the on-chain `WorkflowOwner` is shared.

## Likelihood Explanation
Exploitation requires no elevated privilege: any workflow author can set `CacheSettings.Store=true` and `MaxAgeMs>0` on their own outbound HTTP action, which is a caller-controlled field. The only additional precondition is that two workflows under the same owner issue an outbound request identical in method/URL/headers/body within the cache TTL window (10 minutes by default) — plausible for shared upstream integrations (common login/webhook/API endpoints reused across workflows). This is fully reachable through the normal gateway HTTP action flow with no operator/admin access needed.

## Recommendation
Include `WorkflowID` (and consider `WorkflowExecutionID` for one-shot session-bearing responses) in the `OutboundHTTPRequest.Hash()` computation used as the cache key, so cache entries cannot cross workflow boundaries, matching the README's documented guarantee. Additionally, consider stripping or refusing to cache well-known private headers (`Set-Cookie`, `Authorization`) by default unless explicitly opted into by the workflow.

## Proof of Concept
1. Workflow A (`WorkflowOwner=O`, `WorkflowID=W1`) issues `OutboundHTTPRequest{Method:GET, URL:https://svc/login, CacheSettings:{Store:true, MaxAgeMs:600000}}`; the endpoint replies `200` with `Set-Cookie: session=abc123`.
2. `responseCache.Set` stores this response under `req.Hash()`, which per `TestRequestHash` does not vary with `WorkflowID`.
3. Workflow B (`WorkflowOwner=O`, `WorkflowID=W2`, functionally unrelated to A) issues an outbound request identical in method/URL/headers/body within the TTL window.
4. `responseCache.Fetch` returns Workflow A's cached response — including `Set-Cookie: session=abc123` — to Workflow B's execution via `sendResponseToNode`, confirmable by extending `TestRequestHash`/`response_cache_test.go` to assert two requests differing only in `WorkflowID` produce the same `Hash()` and thus the same cache entry (already demonstrated by the existing "having different workflowID results in same Hash" subtest at lines 139-149).

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
```

```go
// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```
