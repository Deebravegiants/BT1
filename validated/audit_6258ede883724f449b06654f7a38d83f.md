## Title
Hardcoded 18-decimal default withdrawal threshold compared against relayer fees denominated in the destination chain's actual fee-token decimals - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`pallet-relayer`'s `withdraw` function gates a relayer's fee withdrawal on `available_amount >= min_withdrawal_amount`, but the default minimum (`MinWithdrawal`) is a constant hardcoded assuming an 18-decimal fee token, while `available_amount` (the `Fees` map) accumulates raw fee amounts read directly from each source chain's on-chain fee metadata — in that chain's actual fee-token decimals, which are not universally 18. This is the same class of bug as the Ion Protocol report: a threshold denominated in one unit is compared against a value denominated in a different unit, with no conversion.

### Finding Description
`MinWithdrawal` is defined as a flat constant: [1](#0-0) 

This is only used as a **fallback** when no per-chain value has been explicitly configured via `set_minimum_withdrawal`, whose own doc comment acknowledges that decimals differ across chains ("Sets the minimum withdrawal amount using the correct decimals"): [2](#0-1) 

The value being compared against this threshold, `available_amount`, is read straight from `Fees::<T>`, which is populated in `accumulate()` from the **raw** on-chain fee value decoded from `RequestMetadata`/`FeeMetadata` on the source chain — i.e. in whatever decimal precision that specific chain's configured fee token actually uses, with no normalization step to 18 decimals: [3](#0-2) [4](#0-3) 

The gating check itself performs no decimal normalization between the two: [5](#0-4) 

That fee-token decimals genuinely vary per destination chain (and are not assumed to be 18) is confirmed by the tesseract relayer client, which queries `fee_token_decimals()` dynamically per chain rather than assuming 18: [6](#0-5) 

So for any `state_machine` whose fee token has fewer than 18 decimals (e.g. a 6-decimal USDC-style fee token) and for which governance has not (yet, or ever) called `set_minimum_withdrawal` to set a correctly-scaled per-chain value, `min_withdrawal_amount` falls back to `10 * 10^18` raw units — a threshold that is `10^12`× too large relative to the token's real decimals. `available_amount` (accumulated in 6-decimal units) can then never reach that threshold, and `withdraw_fees` unconditionally reverts with `NotEnoughBalance`.

### Impact Explanation
This directly matches the accepted impact class "relayer fee and reward accounting" / "permanent freezing of funds." Relayer fees that have already been legitimately earned and proven via `accumulate_fees` become permanently unwithdrawable for any chain whose fee token decimals differ from 18 until a privileged governance call configures the per-chain override — a route that is unable to deliver value to the relayer despite the funds existing on-chain. Because outbound message delivery (and the resulting settlement/rewards) is economically incentivized specifically by this fee-withdrawal mechanism, an unconfigured chain effectively removes the economic incentive for relaying to/through it, degrading message delivery reliability for that route.

### Likelihood Explanation
This triggers automatically and deterministically for any newly onboarded state machine using a non-18-decimal fee token, the moment relayers try to withdraw before (or if) governance sets `set_minimum_withdrawal` for it — no attacker action is required, and the affected caller is the unprivileged relayer submitting the unsigned `withdraw_fees` extrinsic that any relayer address can call.

### Recommendation
Store or resolve the destination chain's fee-token decimals when comparing against `MinWithdrawal`, or require `MinimumWithdrawalAmount` to be mandatorily configured (with the correct decimals) before permitting any withdrawal for a newly-registered state machine, rather than silently falling back to an 18-decimal-denominated constant.

### Proof of Concept
1. Configure a new EVM state machine whose `HostParam::EvmHostParam.fee_token` is a 6-decimal token (e.g. USDC), without calling `set_minimum_withdrawal` for that `StateMachine`.
2. A relayer delivers messages and calls `accumulate_fees` with a valid `WithdrawalProof`; `Fees::<T>` for that chain/relayer accumulates real 6-decimal fee-token units (e.g. `50_000_000` = $50 of USDC).
3. Relayer calls `withdraw_fees`; `min_withdrawal_amount` is unset, so it falls back to `MinWithdrawal::get()` = `10_000_000_000_000_000_000` (10 * 1e18).
4. `available_amount (50_000_000) < min_withdrawal_amount (10_000_000_000_000_000_000)` is always true, so `withdraw` reverts with `Error::<T>::NotEnoughBalance`, regardless of how much fee actually accrues, permanently blocking withdrawal until governance intervenes.
