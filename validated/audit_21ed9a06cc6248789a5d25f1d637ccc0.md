This confirms the flow: `Bank::process_and_record_transactions_with_pre_results` calls `bank.prepare_sanitized_batch_with_results` **before** `check_transactions`/`check_status_cache` are ever invoked, and this call performs actual account locking via `try_lock_accounts_with_results` → `rc.accounts.lock_accounts` (`runtime/src/bank.rs:3733-3744`, `core/src/banking_stage/consumer.rs:199-216`). Two identical transactions necessarily reference the same writable accounts (fee payer at minimum), so the second copy attempting to lock those same accounts while the first batch's lock is still held will receive `TransactionError::AccountInUse` from `AccountLocks::can_lock_accounts` (`accounts-db/src/account_locks.rs:56-71`), and the lock is held for the full duration of execution+commit — it is only released when the `TransactionBatch` is dropped after `commit_transactions` completes (`runtime/src/transaction_batch.rs:100-110`, `core/src/banking_stage/consumer.rs:216`). This means the two threads can never simultaneously reach `check_status_cache` while both hold locks on the same accounts: one gets `AccountInUse` and is filtered out before `check_transactions`/`load_and_execute_transactions` even run (`core/src/banking_stage/consumer.rs:244-266`). This is exactly demonstrated by the existing test `test_bank_process_and_record_transactions_account_in_use` with `use_duplicate_transaction=true` (`core/src/banking_stage/consumer.rs:1565-1639`), which asserts only one of two identical transactions is processed and the duplicate is filtered with no retry.

Additionally, within a single batch (same PoH slot, same call), `try_lock_accounts_with_results` explicitly deduplicates by `message_hash()` before even attempting the account lock (`runtime/src/bank.rs:3702-3716`), independently rejecting the second identical message with `TransactionError::AlreadyProcessed`.

The `update_transaction_statuses` / status-cache insert at `runtime/src/bank.rs:3515-3543` is a secondary/cross-slot dedup layer (added for SIMD-83 message-hash dedup, exercised by `test_process_entry_duplicate_transaction` at `ledger/src/blockstore_processor.rs:3728-3781` and `test_update_transaction_statuses_fail` at `ledger/src/blockstore_processor.rs:4096-4138`). It is not the sole mechanism preventing double execution — the account-lock mechanism already serializes any concurrent attempt to process transactions touching the same accounts, closing the race window the question describes before `check_status_cache` is ever reached concurrently by two threads on the same accounts.

Given this, the described race (two banking threads both passing `check_status_cache` concurrently for the identical transaction before either inserts) is not reachable, because account locking already serializes access to the shared accounts across all banking threads for the full duration of execute+commit, and the in-batch message-hash dedup independently blocks same-batch duplicates.
