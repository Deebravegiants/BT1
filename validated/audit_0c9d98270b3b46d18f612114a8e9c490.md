### Title
Webhook `shop` (tenant identity) field is not covered by the HMAC signature that authenticates the webhook - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value it hands to the app's handler is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the HMAC-signed material. An attacker who can produce any request whose *body* matches a signature computable from a known/leaked event payload for topic `T` (or, more directly, any man-in-the-middle/relay that can replay a legitimately-signed body while rewriting headers) can make the app process the webhook as coming from an arbitrary shop, breaking the binding between "shop authenticated by the HMAC" and "shop the app acts on."

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is to expose `hmac` and `to_signable_string` so `HmacValidator` can verify the whole request is authentic: [1](#0-0) 

For webhooks, `to_signable_string` returns **only** the raw body — none of the Shopify-specific headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are part of the signed string: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then immediately trusts the header-derived `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler, with no re-check that these headers are consistent with anything cryptographically verified: [3](#0-2) 

`WebhookMetadata.shop` is a plain, unauthenticated string field that the handler (the app's business logic) is expected to trust as the tenant identifier: [4](#0-3) 

The equality this breaks is:
`shop authenticated by HMAC(secret, raw_body)` ≠ `shop the handler is told the event belongs to (X-Shopify-Shop-Domain header)`

Because the header is outside the signed byte range, the gem's `HmacValidator.validate` call in `process` (`lib/shopify_api/webhooks/registry.rb:190`) can return `true` while `request.shop` (`lib/shopify_api/webhooks/request.rb:20-23`) has been altered — the two values are never checked against each other or against a value protected by the signature.

### Impact Explanation
Confirming this as a genuine cross-tenant issue requires knowing exactly how Shopify's Webhooks delivery infrastructure treats these headers in transit (e.g., whether the delivery channel/TLS termination between Shopify and the app is trusted so headers can't be tampered with independently of the signed body) — that is outside this gem's code and cannot be verified from `lib/shopify_api/**` alone. If the header can be manipulated independently of the signed body (e.g., by an intermediary proxy/load balancer misconfiguration, or by any code path that constructs a `Webhooks::Request` from attacker-influenced headers alongside a genuinely-signed body, such as a test/dev harness or a custom `Rack` app that merges headers from multiple sources), the app would process the webhook payload as belonging to the wrong `shop`, resulting in cross-tenant data being attributed to another merchant's session/handler logic. This maps to the report's underlying bug class ("a field acted on but not covered by the HMAC") and to the Critical "cross-tenant access" impact bucket, but the exploitability is conditioned on how the host application/network path passes headers through — the gem itself, by design, only signs the body.

### Likelihood Explanation
Low-to-moderate on its own within Shopify's standard HTTPS webhook delivery (where headers and body arrive as a single TLS-protected unit from Shopify, making header tampering hard for a pure "unprivileged internet user" without also being able to forge the signature). However, the design gap is real and concrete in the gem: nothing in `lib/shopify_api/webhooks/**` cryptographically binds `shop-domain`, `topic`, or `webhook-id` to the signed payload, so any deployment pattern that reconstructs `headers` from a different trust boundary than `raw_body` (e.g., an intermediary that terminates/forwards webhooks, or a queue-based fan-out where body and headers are stored/relayed separately) reintroduces the vulnerability entirely within this gem's verification logic.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook-id`) in the HMAC-signed material, or independently verify `request.shop` against a value derived from the signed payload (e.g., a shop identifier embedded in the JSON body) before constructing `WebhookMetadata`. At minimum, document that `Registry.process` callers must not construct `Webhooks::Request` from headers sourced separately from the raw body that produced `hmac-sha256`.

### Proof of Concept
Not executable — this finding is a structural analog derived by tracing `Registry.process` → `HmacValidator.validate` → `Webhooks::Request#to_signable_string`/`#shop`, showing the shop identity used by handlers is header-derived and outside the HMAC's signed scope: [5](#0-4) [6](#0-5) 
Actual exploitation depends on a deployment/transport scenario (outside `lib/shopify_api/**`) that lets an attacker present a genuinely-signed body alongside an attacker-chosen `shop-domain` header — this could not be confirmed as exploitable purely from the in-scope library code.
