### Title
Webhook HMAC Does Not Bind the `shop-domain` Header, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw request body only, while the shop identity used to route and label the webhook to a specific tenant is read from an unsigned HTTP header. Since Shopify signs webhooks with the app's single shared `api_secret_key` (the same secret for every shop that installs the app), an attacker who controls their own installation of the app can obtain a validly-signed webhook body, then replay it with a different `shop-domain` header value, causing `Webhooks::Registry.process` to accept the request and hand the handler data labeled with an arbitrary target shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` (and `topic`, `api_version`, `webhook_id`) are read from HTTP headers that are never part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `to_signable_string` against the received HMAC — it has no knowledge of, and does not bind, the `shop` field: [3](#0-2) 

`Webhooks::Registry.process` trusts `request.shop` (and other headers) as soon as the body HMAC validates, and forwards it to the application handler as the tenant identity for the event: [4](#0-3) 

The identity binding that should hold is:
`bytes verified by HMAC == bytes used to identify the tenant (shop)`

In this implementation that equality breaks down to:
`bytes verified by HMAC (raw_body only) != bytes used to identify the tenant (shop-domain header, unverified)`

Because Shopify computes the webhook HMAC using the app's single `api_secret_key` shared across all shops that have the app installed (not a per-shop secret), any body+HMAC pair obtained from a webhook sent to the attacker's own shop is a validly-signed pair for that *body*, but says nothing about *which shop* it came from. Swapping the `shopify-shop-domain` / `x-shopify-shop-domain` header therefore does not invalidate the signature.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an attacker who has installed the app on a shop they control can craft a webhook body of their choosing (e.g., by triggering an event on their own store, such as `orders/create`/`app/uninstalled` with attacker-controlled content), capture the resulting valid `(body, hmac)` pair, and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop that also has the app installed. `Registry.process` will pass HMAC validation and invoke the registered handler with `WebhookMetadata.shop` set to the victim shop, causing the host application to process attacker-controlled data under another tenant's identity. Depending on what the host app's webhook handlers do with this data (e.g. updating per-shop state, deleting resources, revoking access, syncing orders), this can lead to data corruption or unauthorized actions scoped to another merchant — a cross-tenant boundary violation.

### Likelihood Explanation
Exploitability only requires the attacker to be able to install the app on their own store (a routine, unprivileged action for any public/dev Shopify app) and to control an HTTP client capable of setting arbitrary headers when forwarding a webhook — no access to `api_secret_key`, access tokens, or any other credential is required. The only non-trivial step is obtaining a delivery to intercept/replay, which any merchant with the app installed can trigger on demand for events they control (e.g. creating their own order/product).

### Recommendation
Include the identity/routing fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable content that is verified against the HMAC, or otherwise cryptographically bind them (e.g., derive/verify the shop domain from a per-shop secret or from an authenticated registration record rather than trusting the header), so that `to_signable_string` covers everything the handler acts on, not just the raw body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook (e.g., `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker crafts a POST request to the app's webhook endpoint with:
   - Body: `B` (unchanged, keeping `H` valid)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (changed from the real value)
   - Header `x-shopify-topic`, `x-shopify-webhook-id` optionally altered as desired
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only checks presence, not authenticity, of `shop-domain`) — see [5](#0-4) .
4. `Utils::HmacValidator.validate` succeeds because it only recomputes HMAC over `@raw_body`, matching `H`.
5. `Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body(B), ...)`, causing the host application to treat attacker-controlled data as originating from `victim-shop.myshopify.com`.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
