Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `topic`, `shop`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC and then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` verbatim when building `WebhookMetadata` passed to the app's handler [3](#0-2) . This is a genuine "field acted on but not covered by the HMAC" identity-binding break.

### Title
Webhook shop/topic/webhook_id identity spoofing via HMAC that only covers the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the Shopify webhook HMAC over the raw body only, but exposes `shop`, `topic`, `webhook_id`, and `api_version` as separate values sourced from HTTP headers that are never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body/HMAC pair is valid and then forwards the header-derived `shop` value to the app's webhook handler as if it were an authenticated identity binding.

### Finding Description
The gem's documented HMAC validation contract is: `Utils::HmacValidator.validate(request)` computes `HMAC-SHA256(secret, request.to_signable_string)` and compares it to `request.hmac` using a constant-time compare [4](#0-3) . For webhook requests, `to_signable_string` is defined as simply `@raw_body` [1](#0-0) , i.e. the HMAC only binds the JSON body bytes to the app's shared secret. It does **not** bind the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` headers, which are read independently via `shopify_header` [2](#0-1) .

`Registry.process` treats a valid HMAC as authenticating the entire request, then constructs `WebhookMetadata` directly from these unauthenticated header fields and dispatches it to the app-supplied handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))` [5](#0-4) . `WebhookMetadata.shop` is documented as "The shop domain of the webhook" [6](#0-5)  and the gem's own docs tell integrators to key business logic off `data.shop` directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [7](#0-6) , i.e. the library's public contract treats `shop` as an authenticated tenant identifier once HMAC validation passes.

Because the app's `api_secret_key` is a single shared secret used for **every** shop/merchant using the app (not scoped per-shop), any merchant who installs the app on their own store legitimately receives real webhooks with a valid HMAC computed from that same shared secret. Such a merchant (an unprivileged internet user with respect to any *other* tenant) can capture a genuine `(raw_body, hmac)` pair from their own webhook deliveries and replay it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` will still succeed because the shop header is not part of `to_signable_string`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event originated from the victim shop.

The identity binding broken, stated as an equality that should hold but doesn't:
`HMAC(secret, signable_string)` should authenticate `(shop, topic, body)` as a unit, but only authenticates `body`. Thus `shop_claimed_by_header != shop_actually_authenticated_by_hmac`.

### Impact Explanation
This crosses the "cross-tenant access" boundary described in scope: an attacker who is a legitimate (but unprivileged w.r.t. other tenants) merchant using the shared app can forge webhook events attributed to any other shop using the same app instance. Depending on how the host application uses `data.shop` and `data.topic` (which the gem's own docs recommend using directly, e.g. to look up the shop's stored session/access token and act on their behalf, or to trigger mandatory compliance topics like `customers/redact`/`shop/redact`), this can lead to cross-tenant data corruption, spoofed compliance/GDPR events, or triggering shop-scoped business logic for a victim tenant without their knowledge — satisfying the "cross-tenant access" Critical-impact category defined in scope.

### Likelihood Explanation
Exploitation only requires: (1) the attacker to be a merchant who has installed the target app on their own store (a low bar — many apps are public/free to install), (2) capturing one legitimate webhook body+HMAC pair delivered to their own store, and (3) resending that payload to the app's public webhook endpoint with a modified `shopify-shop-domain` header. No access token, `client_secret`, or privileged credential is required — this fits the "unprivileged internet user" threat model in scope, since the attacker only ever needs data addressed to their own tenant.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) in the HMAC-signed material, or otherwise cryptographically bind `request.shop` to the verified body — e.g. by validating the `shop` header against the shop that was independently used to look up/authorize the specific webhook subscription (via `webhook_id`), rather than trusting it as an unauthenticated header once any valid-body HMAC is present. At minimum, update `Utils::HmacValidator`/`Webhooks::Request#to_signable_string` so it authenticates a canonicalized string that includes `shop-domain` and `topic`, matching Shopify's actual webhook delivery guarantees, and document that host apps must not treat `WebhookMetadata#shop` as authenticated unless this binding exists.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app.
# They receive a legitimate webhook for their own shop:
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Legitimate headers captured from Shopify's real delivery to attacker's shop:
# "shopify-hmac-sha256" => Base64.encode64(hmac)
# "shopify-shop-domain" => "attacker-shop.myshopify.com"
# "shopify-topic"       => "orders/create"

# Attacker replays the SAME body+hmac but swaps the shop-domain header:
forged_headers = {
  "shopify-topic"        => "orders/create",
  "shopify-hmac-sha256"  => Base64.encode64(hmac),   # unchanged, still valid because HMAC ignores shop
  "shopify-shop-domain"  => "victim-shop.myshopify.com", # attacker-controlled
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) succeeds (HMAC only covers raw_body)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app processes this as an authentic event for "victim-shop.myshopify.com".
```
