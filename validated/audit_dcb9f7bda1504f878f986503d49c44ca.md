## Finding

### Title
Webhook HMAC only covers the raw body, letting shop/topic/webhook-id headers be forged to spoof a different tenant — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw HTTP body. The `shop`, `topic`, and `webhook_id` values that `Webhooks::Registry.process` later trusts and hands to the app's handler are read straight from unauthenticated HTTP headers, breaking the identity binding: `shop_authenticated == shop_acted_upon` does not hold.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled directly from headers, with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `hmac == HMAC(api_secret_key, raw_body)`: [3](#0-2) 

`Webhooks::Registry.process` calls this validator and then unconditionally trusts `request.shop`/`request.topic`/`request.webhook_id` to build the metadata dispatched to the app's handler: [4](#0-3) 

Because `api_secret_key` is a single, app-wide secret shared by every merchant that installs the app (not a per-shop secret), any merchant who has installed the app can capture a legitimate webhook they themselves received (valid `raw_body` + valid `hmac`, both computed with the shared app secret) and replay it to the app's public webhook endpoint while rewriting only the unsigned `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers. `HmacValidator.validate` still passes because it never inspects those headers, and `Registry.process` will dispatch the handler believing the event originated from an arbitrary victim shop/topic/webhook id of the attacker's choosing (as long as the body content is acceptable to that handler, e.g. an empty `{}` body for topics that don't require specific fields, such as `app/uninstalled`).

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: an unprivileged internet user who is merely a legitimate installer of the same app (no `api_secret_key`, no access token, no privileged account beyond a normal shop install) can make the host application process a forged webhook attributed to a different shop. Depending on how the host app implements handlers (e.g., deleting shop data on `app/uninstalled`, updating shop-scoped records keyed by `request.shop`), this enables cross-tenant data manipulation — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own legitimate app installation (to obtain one valid `(raw_body, hmac)` pair), and (2) the ability to POST to the app's public webhook endpoint with custom headers — both trivially available to any merchant/tester using the target app. No secret material or privileged credentials are required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable payload used for HMAC verification (or otherwise cryptographically bind them, e.g., by validating the shop against a previously stored/authorized session before dispatching), so `Registry.process` cannot be fed spoofed identity headers alongside a replayed-but-otherwise-valid body/HMAC pair.

### Proof of Concept
1. Install the target Shopify app on shop `attacker-shop.myshopify.com`; trigger any webhook event (e.g., `app/uninstalled`), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header — both valid under the shared `api_secret_key`.
2. Replay this exact `(body, hmac)` pair to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or `X-Shopify-Topic` to another registered topic if the body content applies, e.g. `{}`).
3. `Utils::HmacValidator.validate` (which only checks the body) succeeds; `Webhooks::Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., ...)`, causing the host app to execute shop-scoped logic against `victim-shop.myshopify.com` on the attacker's behalf.
