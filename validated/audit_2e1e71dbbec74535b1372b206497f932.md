### Title
Bad-debt wipeout clamps `supply_index` to `SUPPLY_INDEX_FLOOR_RAW` instead of zeroing claims, leaving wiped suppliers a phantom balance that drains the next depositor's cash - (File: contracts/pool/src/interest.rs)

### Summary
The analog of the CVE class (a bounded write that corrupts adjacent state — heap buffer overflow in `vim_strncpy`) is a bounded state write in bad-debt socialization: `apply_bad_debt_to_supply_index` writes a clamped index rather than the true (zero) value, corrupting the accounting of every supply share in that market. When socialized bad debt meets or exceeds the market's total supplied value, the function floors the new supply index at `SUPPLY_INDEX_FLOOR_RAW` (RAY/1000) instead of zeroing supply shares, so wiped suppliers keep a positive claim backed by nothing. That phantom claim is later paid out of fresh deposits via `withdraw`, transferring a new supplier's real tokens to the holder of wiped shares.

### Finding Description
In `contracts/pool/src/interest.rs`, `apply_bad_debt_to_supply_index` computes `remaining = total_supplied_value - capped_bad_debt` and scales the index by `remaining / total_supplied_value`, then applies `new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW))` (lines 73-89). On a full wipeout (`capped == total_supplied_value`) `remaining` is 0 and `reduction_factor` is 0, so the mathematically correct index is 0 — but the clamp rewrites it to `RAY/1000`. Every pre-existing scaled supply position thereby retains `scaled × RAY/1000` of claim value while the market holds zero cash for them.

The bug is reachable permissionlessly: `clean_bad_debt` on the controller (and the post-`liquidate` bad-debt path) drives `pool::seize` → `ops/seize.rs::apply`, which calls `unscale_borrow_ceil_ray` and then `apply_bad_debt_to_supply_index` for `AccountPositionType::Borrow` entries (`contracts/pool/src/ops/seize.rs:24-28`). An attacker can manufacture full-wipeout bad debt: supply the market, open a borrow collateralized in another asset on their own account, move the collateral price down (`set_price`-equivalent via the real oracle feed), then `liquidate`/`clean_bad_debt` so the unpaid debt leg socializes an amount ≥ total supplied value. Nothing requires privilege.

The in-repo unit test `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` (`contracts/pool/tests/interest.rs:372-427`) demonstrates the exact corruption: after the clamp, `unscale_supply_floor(old_scaled) > 0` ("floor clamp leaves S_old a phantom claim"), a fresh deposit of the same amount is minted, and `resolve_withdrawal(i128::MAX, old_scaled)` followed by `require_reserves`/`debit_cash` pays `gross == fresh_cash` — the wiped position "drains exactly the fresh deposit," leaving `cash < fresh_claim` ("funds lost").

### Impact Explanation
Theft of user funds. A holder of wiped shares can withdraw tokens that no longer belong to them; the withdrawal is funded by whatever cash later enters the market (new `supply` deposits, repayments, or liquidation proceeds). The victim is the next supplier, whose claim becomes unbacked — equivalent to a direct transfer of their deposit to the wiped-share holder. The attacker can hold the wiped shares themselves (they were a supplier before triggering the wipeout), making this a self-contained exploit by one unprivileged address: create wipeout bad debt → hold stranded shares → wait for (or sandwich) a fresh deposit → `withdraw` to extract the victim's tokens.

### Likelihood Explanation
Full wipeout requires bad debt ≥ total supplied value of that market, which normally needs the borrowed amount to approach or exceed the supply-side value (e.g., a thin market where one borrow is nearly all utilization and the collateral collapses in price, or accrued interest pushing `unscale_borrow_ceil_ray` above `supplied × supply_index`). The 200 bps liquidation buffer caps a single borrow draw at ~98% of supplied value, but bad debt is measured after accrual and collateral failure, so exceeding it is realistic in small/spoke-isolated markets — and the attacker controls both the supply size and the borrow size. Once wiped, any subsequent deposit triggers the loss, so the attack needs only one later depositor; the attacker can even supply "fresh" cash through a second account and immediately re-extract via the phantom share, though profit requires a third-party depositor for net gain.

### Recommendation
In `apply_bad_debt_to_supply_index`, when `capped == total_supplied_value` (or `remaining == Ray::ZERO`), do not resurrect the index via the floor clamp; instead set the index to a state that zeroes all claims — e.g., reset `supplied` to zero alongside the index, or skip the clamp when the reduction factor is zero so the index lands at its true wiped value and a guard prevents resurrection. Alternatively, keep the floor but simultaneously clear `cache.supplied` (burn all shares' backing) and treat the market as reset, since retaining `RAY/1000` of claim is precisely what creates the phantom balance. The clamp exists to avoid a zero index breaking later `div` operations, so the fix should pair the index write with a supply-share reset rather than leaving mismatched state.

### Proof of Concept
1. Attacker account A supplies `s` units into market M (attacker holds scaled supply `S_old`).
2. Account A (or a second attacker account) supplies collateral in another market and borrows nearly all of M's cash; or any organic borrower's position collapses.
3. Collateral price drops so the borrower's position is insolvent with residual collateral ≤ $5. Attacker calls `liquidate` then `clean_bad_debt` (both permissionless). `seize` socializes bad debt ≥ M's total supplied value → `apply_bad_debt_to_supply_index` clamps `supply_index` to `SUPPLY_INDEX_FLOOR_RAW` instead of 0.
4. Victim V supplies `x` tokens into M (fresh cash, minted `calculate_scaled_supply(x)` at the clamped index).
5. Attacker calls `withdraw(account_A, M, 0)` (withdraw-all sentinel): `resolve_withdrawal` pays `unscale_supply_floor(S_old) > 0`, `require_reserves` passes because V's cash is present, and A receives tokens backed by V's deposit.
6. Result: V's claim (`unscale_supply_floor(fresh_scaled) == x`) is no longer covered by pool cash — V's funds were transferred to A.

This mirrors the repository's own demonstration in `contracts/pool/tests/interest.rs:372-427`, which asserts `gross == fresh_cash` ("S_old drains exactly the fresh deposit") and `cache.cash() < fresh_claim` ("funds lost").
