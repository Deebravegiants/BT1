### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable signable string as the raw request body only, while `topic`, `shop`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then forwards the header-derived `shop` value to the app's handler as trusted tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding to the signed content: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the raw body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` gates only on this body-HMAC check, then builds `WebhookMetadata` using the unauthenticated `request.shop` header and dispatches it to the app's handler as the identified tenant: [4](#0-3) [5](#0-4) 

This breaks the intended identity binding: **the shop that the app's secret key authenticates the payload for** should equal **the shop the handler acts on (`data.shop`)**. Here, `HMAC(api_secret_key, raw_body) == received_hmac` is verified, but `data.shop` (from the `shopify-shop-domain` header) is never included in that signed content, so `shop_verified_by_hmac == shop_acted_on` does not hold.

Because a single app's `api_secret_key` is shared across every merchant that installs the app, any merchant who installs the app (an unprivileged, non-victim tenant) receives real webhook deliveries for their own shop with a valid HMAC over the body. That attacker can capture one such legitimate `(raw_body, hmac)` pair from their own store, then replay the exact same raw body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain, causing the app to process/act on data as if it came from a different, unauthorized tenant.

### Impact Explanation
This is a cross-tenant data/action injection: an app built directly on the documented API (`Registry.process` + `WebhookMetadata.shop`) will trust `data.shop` as the authenticated identity of the merchant whose event just fired. A malicious merchant can forge webhook deliveries "for" another shop, potentially causing the host application to perform tenant-scoped writes, cache updates, uninstall/reinstall logic, or billing/reconciliation actions attributed to the wrong shop — a cross-tenant boundary violation, which maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that installs the library as documented: no access token, `client_secret`, or privileged access is required by the attacker — only that they operate their own (attacker-controlled) shop with the target app installed, which is achievable by anyone. Capturing a real webhook body+HMAC from their own store is straightforward (they control the endpoint or can log requests), and header spoofing on the replayed HTTP request requires no special access.

### Recommendation
Bind the header-derived identity fields into the signed material, or verify them independently:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in `to_signable_string` (matching how Shopify actually signs the payload, if it does), or
- If Shopify's real signature only covers the body (as it does in production), the header values must instead be cross-checked against server-side/application state (e.g., confirm `shop` corresponds to a shop that has an active, registered webhook subscription with a matching `webhook_id`) before trusting `data.shop`, rather than passing it through unvalidated in `WebhookMetadata`.
- At minimum, document prominently that `data.shop` in `WebhookMetadata` is not cryptographically authenticated and must not be trusted as tenant identity by consuming applications without additional verification.

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
