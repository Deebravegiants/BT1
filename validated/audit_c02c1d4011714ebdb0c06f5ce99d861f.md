### Title
Webhook `shop` and `topic` fields are trusted from unauthenticated headers while only the raw body is HMAC-covered - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by exposing `to_signable_string`, which returns only the raw HTTP body: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely over that signable string (the raw body): [2](#0-1) 

However, `Registry.process` derives the tenant identity (`shop`) and event semantics (`topic`) for the dispatched handler directly from the request's un-covered headers, not from anything bound by the HMAC: [3](#0-2) 

And `Request#shop` / `Request#topic` simply read the corresponding `shopify-shop-domain` / `shopify-topic` headers with no cryptographic binding to the body that was actually verified: [4](#0-3) 

This creates exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality the code implicitly assumes is
`shop_header == shop_that_produced(body, hmac)`,
but nothing in `HmacValidator` or `Request` enforces that equality — the HMAC only proves "this body was produced with the app's secret for *some* registered shop's delivery," not "this body belongs to the shop named in this header."

### Impact Explanation
An attacker who controls (or has previously received) any single legitimate webhook delivery for their own shop — a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header value naming a victim shop. `Utils::HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data came from the victim shop/topic. Any host application that uses `WebhookMetadata#shop` to look up a session/access token, gate per-tenant logic, or attribute security-sensitive events (e.g., `app/uninstalled`, `customers/redact`, `shop/redact`) is thus exposed to cross-tenant event forgery, satisfying the "cross-tenant access" impact bar — the attacker never needs the victim's or the app's actual secret, only a single genuine webhook of their own.

### Likelihood Explanation
Any merchant who installs the app receives real webhook deliveries with valid HMACs for their own shop, so obtaining a valid `(body, hmac)` pair requires no special access — just installing the app once. Forging headers on a replayed HTTP request to the app's own public webhook endpoint requires no credentials, TLS interception, or social engineering, making this reachable by any unprivileged internet user who can install/uninstall the app or trigger a webhook for themselves.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is actually HMAC-verified, e.g., include `shop-domain`/`topic`/`webhook-id` headers in `to_signable_string` (matching Shopify's documented HMAC computation, which is body-only, but requiring host apps to be explicitly warned) or, at minimum, have `Registry.process`/`Request` cross-check the `shop` header against an independently known/registered shop identity before dispatching to handlers rather than passing it through unauthenticated.

### Proof of Concept
1. Install the app on `attacker.myshopify.com`; capture any inbound webhook request, e.g. `orders/create`, noting `raw_body` and the `x-shopify-hmac-sha256` header (this HMAC validates because it's genuinely signed with the app's `api_secret_key` for that exact body).
2. Replay the identical raw body and HMAC header to the same endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and optionally `x-shopify-topic` with a different registered topic).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `"victim-shop.myshopify.com"` — a value entirely attacker-controlled and never covered by the HMAC — even though the underlying signed payload actually belongs to the attacker's own shop.
