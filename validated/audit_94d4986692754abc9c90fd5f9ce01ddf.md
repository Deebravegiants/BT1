Based on my investigation, I've confirmed the vulnerability: the `shop` field used to route webhook processing to tenant-specific handlers comes from an HTTP header that is never part of the HMAC-signed payload.

### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop` (tenant identity) used by the registry to dispatch the webhook to the merchant's handler is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#shop` reads `shopify_header("shop-domain")`, a value taken straight from request headers with no cryptographic binding to the signature at all: [1](#0-0) 

`Registry.process` validates only that the HMAC over the raw body is correct, then immediately uses `request.shop` — the unauthenticated header value — to build the `WebhookMetadata` handed to the tenant handler: [2](#0-1) 

`HmacValidator.validate` only proves that `HMAC(raw_body, api_secret_key)` matches; it says nothing about which shop the body belongs to: [3](#0-2) 

This is the same class of bug as the reported analog: a value that is *acted on* (the tenant/wallet identity used to route funds or webhook data) is not the value that is *covered by the integrity check* (HMAC / constructor assignment). Here, the app's authorization decision "this payload belongs to shop X" is made from a header the signature never touches, while the signature only proves body integrity. An unprivileged actor who can obtain one valid `(raw_body, hmac)` pair for their own shop (e.g., a merchant installing the app receives their own webhook deliveries and can inspect/replay them) can resend that exact body and hmac to the app's webhook endpoint while substituting `shopify-shop-domain` for a victim shop, and the signature will still validate — the app has no way to detect the substitution, because the header is not signed.

### Impact Explanation
This breaks the tenant-authentication binding `shop_authenticated == shop_used_for_dispatch`, exactly the pattern flagged as in-scope ("a shop authenticated versus the shop stored/used as a session key"). If the handler uses `data.shop` to look up or mutate per-shop records (as the library's own webhook docs demonstrate), an attacker can cause the host app to process an HMAC-"verified" webhook under a shop identity of the attacker's choosing, leading to cross-tenant data confusion — writes, deletes, or GDPR-redaction actions (`shop/redact`, `customers/redact`, `customers/data_request`) being applied to the wrong merchant's data.

### Likelihood Explanation
Requires the attacker to possess at least one legitimately signed `(raw_body, hmac)` pair, which is trivially available to any merchant who has installed the app (they receive real webhooks for their own shop) or to anyone who can observe one webhook delivery. No `api_secret_key` or access token is required — only replay of already-authenticated bytes with a substituted, unauthenticated header. This keeps the finding within the "no privileged credentials required" scope.

### Recommendation
Bind the tenant identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the HMAC. Concretely:
- Include `shop`/`topic`/`webhook-id` in `to_signable_string` (or require the host app to independently verify `shop` against a known/expected value, e.g. the shop tied to the session/subscription that registered the webhook) before trusting `request.shop` downstream, and
- Document/enforce single-use `webhook-id` tracking to reject replays, since replay is the mechanism that makes the unsigned header exploitable.

### Proof of Concept
1. App merchant for `shop-a.myshopify.com` installs the app and receives (or intercepts) one legitimate webhook delivery: raw body `B` with header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's secret) and `shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker crafts a new POST to the app's webhook endpoint reusing the exact same body `B` and `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: shop-b.myshopify.com` (a victim shop).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B, secret) == H`: [2](#0-1) 
4. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` even though the payload was never actually generated or signed for `shop-b`, and the host app processes the action against the wrong tenant.
