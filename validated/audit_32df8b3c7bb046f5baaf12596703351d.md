### Title
Webhook shop identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (shop-domain), `topic`, `api_version` and `webhook_id` values are read from unauthenticated HTTP headers that are never part of the signed bytes. `Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to route the webhook payload to a handler, so any caller who possesses one valid `(body, hmac)` pair for the app can replay it while claiming a different shop, and the gem will accept it as authentic for that shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `api_version`, `webhook_id`) are pulled directly from headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC exclusively against `to_signable_string`, i.e. the body: [3](#0-2) 

`Webhooks::Registry.process` accepts the request purely based on that body-only HMAC check, then forwards `request.shop` straight to the app's handler with no further verification: [4](#0-3) 

The broken binding, expressed as an equality that the gem fails to enforce:
`hmac == HMAC(secret, raw_body)` is checked, but the code implicitly relies on `hmac == HMAC(secret, raw_body + shop)`. Because `shop` is excluded from the signed bytes, `shop` can be swapped freely on any request that carries a validly-signed body, exactly as in the reported bug class where transferring the identity-bearing token (`receiptID`/NFT owner) never updates the bound-but-separate `managerAddress` field that downstream logic still trusts.

### Impact Explanation
Any consumer of this gem that keys tenant lookups off `WebhookMetadata#shop` (the documented, intended use of `Registry.process`) can be made to process a webhook body under the wrong shop's identity. An attacker who has legitimately received one valid webhook delivery for their own store (which is trivial — install the app on any store and observe/capture one webhook POST) can resend that exact body+HMAC to the app's webhook endpoint with the `shop-domain` header changed to a victim shop. The signature still validates because `shop` was never covered by it, letting the attacker's data cross into another tenant's processing path — a cross-tenant access primitive per the impact categories.

### Likelihood Explanation
Exploitation needs only a single previously-observed valid `(body, hmac)` pair, obtainable by installing the app on an attacker-controlled store — no `api_secret_key`, access token, or privileged account is required. The gem's own webhook handling API (`Registry.process`) is the code path exercised, not a misuse of an undocumented feature, so this is directly reachable through the library's supported flow.

### Recommendation
Bind the shop (and ideally topic/api_version/webhook_id) identity into the signed material that `HmacValidator` checks, e.g. include `shop-domain` in `to_signable_string`, or require the host application to independently authenticate the shop before trusting `WebhookMetadata#shop` (document this loudly if the header truly cannot be covered by Shopify's HMAC scheme).

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the raw JSON body and the `X-Shopify-Hmac-Sha256` header value Shopify sent.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the identical body and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only hashes `@raw_body`, which is unchanged. [5](#0-4) 
4. `Registry.process` calls the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from and describes the attacker's own store.
