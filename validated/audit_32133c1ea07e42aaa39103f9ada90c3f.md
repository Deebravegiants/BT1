### Title
Public key cache is keyed only by `walletAccountName` string, which is not seed-bound, allowing stale-seed public keys/xpubs to leak into a re-created wallet account with a different `seedId` - ([File: features/public-key-provider/module/store/formats/storage/legacy.ts])

### Summary
`StorageFormatLegacyBuilder.#findPublicKeyEntry`/`.get` resolve cached public keys purely by `walletAccountName` (a string) and `derivationPath`, with no `seedId` component in the lookup key. Because `WalletAccount.toString()` for the `exodus` source deliberately excludes `seedId` (`exodus_0` regardless of which seed backs it), a wallet account that is deleted/reset and re-created under a new seed but with the same name will still resolve cached entries written for the old seed, unless every entry for that path has since been overwritten.

### Finding Description
`PublicKeyStore.get()` resolves the live `WalletAccount` object from `walletAccountsAtom` by `walletAccountName`, and then calls `StorageFormatLegacyBuilder.get({ walletAccountName, keyIdentifier })`, which performs `this.#data[walletAccountName]?.[keyIdentifier.derivationPath]` with no seedId check whatsoever: [1](#0-0) 

The cache write path (`addMany`) is likewise keyed only by `walletAccountName` and `derivationPath`: [2](#0-1) 

Critically, `WalletAccount.toString()` deliberately omits `seedId` for `exodus`-source accounts — only `source` and `index` are used, so the string identity `exodus_0` is stable across a seed reset/re-import: [3](#0-2) [4](#0-3) 

`PublicKeyProvider.#exportPublic` writes to this cache after deriving from the keychain for whichever `walletAccount` object it currently holds (bound to whatever `seedId` is live at write time), using `walletAccountName` as the only account-scoping key: [5](#0-4) 

If a device goes through a wipe/re-import flow where the exodus default account (`exodus_0`) ends up bound to a new `primarySeedId` (this is possible per the multi-seed migration/lifecycle code that sets `seedId: primarySeedId` on `exodus`-source accounts), any derivation paths not yet re-derived and re-added for the new seed will still return the old seed's `publicKey`/`xpub` from the persisted legacy-format blob (`hardwareWalletPublicKeysAtom`/`softwareWalletPublicKeysAtom`), because nothing purges entries keyed by `exodus_0` on seed replacement — the cache is simply merged/overwritten path-by-path as new keys get added, not wiped wholesale for that account name.

There is a `clearSoftwareWalletAccountKeys()` method that empties the entire software key cache: [6](#0-5) 
However, whether this is reliably invoked on every seed-reset/re-import path (as opposed to only on explicit wallet wipe) could not be confirmed from the code reachable in this investigation; if any reset/re-import path does not call it (or if `addMany` writes for the new seed only cover a subset of previously-cached derivation paths), stale entries for unfetched paths remain and will be returned by `get()`.

### Impact Explanation
`get()` returning a public key/xpub derived from the old seed while the caller (address derivation, watch-address generation, or any consumer trusting the `walletAccountName → key` binding) believes it belongs to the new seed leads to addresses/watch-keys being generated against the wrong seed material. Depending on downstream usage (e.g., balance/address display, ordinal derivation index continuity, or any flow that trusts the cached xpub as authoritative for signing key derivation validation), this can cause funds to be shown/tracked against, or transactions constructed against, the wrong seed's key hierarchy — a wrong-account key binding violation with wallet-compromise-adjacent impact (mixing of two independent seeds' key material under one account identity).

### Likelihood Explanation
This requires a legitimate device-level event: a wallet reset/re-import that causes the `exodus`/default wallet account to be rebound to a new `seedId` while retaining the same `walletAccountName` (this is architecturally supported and even tested for `primarySeedId` reassignment in the wallet-accounts module). It does not require any privileged access or malicious peer — an ordinary user performing "restore from different seed" or a stale/replayed `addMany` RPC call for the old seed reaching the store after the seed swap would suffice. Exploitability depends on whether the cache-clearing call is consistently wired into every reset/re-import path, which could not be confirmed with certainty from the available code.

### Recommendation
Bind the public-key cache lookup/write key to `(walletAccountName, seedId)` rather than `walletAccountName` alone (or embed `seedId` in the storage key even for `exodus`-source accounts), and/or unconditionally invalidate (`clearSoftwareWalletAccountKeys`/per-account purge) all cached entries for an account whenever its `seedId` changes, before any new `get()` call can observe stale data.

### Proof of Concept
Integration test (extending `features/public-key-provider/module/store/__tests__/public-key-store.test.ts`):
1. Create `walletAccount = new WalletAccount({ ...WalletAccount.DEFAULT, seedId: 'seedA' })`, `walletAccountName = 'exodus_0'`.
2. Call `publicKeyStore.add({ walletAccount, keyIdentifier, xpub: xpubForSeedA })`; assert `get({ walletAccountName, keyIdentifier })` returns `xpubForSeedA`.
3. Simulate a seed reset/re-import: replace the account in `walletAccountsAtom` with `new WalletAccount({ ...WalletAccount.DEFAULT, seedId: 'seedB' })` under the same name `'exodus_0'` (do not call `clearSoftwareWalletAccountKeys`, do not re-add a key for this derivation path).
4. Call `publicKeyStore.get({ walletAccountName: 'exodus_0', keyIdentifier })`.
5. Expected (secure) behavior: returns `null` or throws, since no key has been derived/added for `seedB` at this path. Actual (vulnerable) behavior: returns `xpubForSeedA`, proving the stale seedA-bound key leaks under the new seed's account name.

    assert(typeof walletAccountName === 'string', 'walletAccountName must be string')

        ...(key.publicKey ? { publicKey: key.publicKey } : {}),
        ...(key.xpub ? { xpub: key.xpub } : {}),
        chain: [0, 0, 0],
      }
    })

  }

  #findPublicKeyEntry = ({ walletAccountName, keyIdentifier }: GetParams) => {
    return this.#data[walletAccountName]?.[keyIdentifier.derivationPath] || null
  }

  get = ({ walletAccountName, keyIdentifier }: GetParams): GetReturn => {
    assert(typeof walletAccountName === 'string', 'walletAccountName must be string')
    const found = this.#findPublicKeyEntry({ walletAccountName, keyIdentifier })
    if (found) {
      if (!found.xpub && !found.publicKey) {
        throw new Error('publicKey entry has neither publicKey nor xpub')
      }

      return found
    }

    return null
  }
