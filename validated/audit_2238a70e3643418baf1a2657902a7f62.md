### Title
Unsafe low-level `IERC20.transfer` call in `IntentGatewayV2.withdraw` (Tron) checks call-success but not return value, causing silent fund loss on escrow redemption/refund - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` imports and uses `SafeERC20` for input transfers (`safeTransferFrom`), but its escrow payout path (`withdraw`) and dust-sweep handler (`onPostRequest`, `SweepDust` branch) instead use a raw low-level `.call` with the `IERC20.transfer` selector, checking only that the call itself did not revert (`success`) and never decoding the returned `bool`. Tokens that signal failure by returning `false` instead of reverting will pass this check even though no tokens were actually moved, while the contract still decrements its internal escrow accounting and emits a "released"/"refunded" event as if the payout succeeded.

### Finding Description
`withdraw()` releases escrowed order inputs and transaction fees to a beneficiary on `RedeemEscrow`/`RefundEscrow` delivery: [1](#0-0) 

For non-native tokens it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
...
_orders[body.commitment][token] -= amount;
```
and the same pattern for the transaction-fee payout:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
delete _orders[body.commitment][TRANSACTION_FEES];
```

`success` here only reflects whether the external call reverted, not the ABI-encoded return value of `transfer`. Per EIP-20, a compliant token may legally return `false` on failure instead of reverting (e.g. paused token, blacklist, insufficient balance edge cases, non-standard TRC20 tokens). In that case `success == true` (the call executed without reverting) even though the actual value transfer did not happen. The contract proceeds to decrement `_orders[...]`/delete the fee escrow and emits `EscrowReleased`/`EscrowRefunded` as if the beneficiary was paid.

The same unsafe pattern is used in the `SweepDust` handler: [2](#0-1) 

This is notably inconsistent with the rest of the same contract, which correctly uses `SafeERC20.safeTransferFrom` for pulling in order inputs/fees: [3](#0-2) 

and with the sibling non-Tron `IntentsBase.sol`/`IntentGatewayV2.sol` contracts, which use `safeTransfer`/`safeTransferFrom` throughout their escrow logic (e.g. `WrappedHyperFungibleToken.sol` consistently uses `IERC20(...).safeTransfer`): [4](#0-3) 

The `withdraw` function is reached from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests (authenticated as being from the correct source module) and from `onGetResponse`, both of which are invoked by relaying ISMP responses/requests that ultimately originate from an order's fill/cancel flow — a path reachable by any solver/relayer completing the normal intents lifecycle, not a privileged admin action.

### Impact Explanation
When a beneficiary token is a non-reverting ERC20/TRC20 that returns `false` on failure, `withdraw()` will:
1. Not actually transfer the escrowed input tokens or transaction fee to the beneficiary.
2. Still decrement/delete the internal `_orders[commitment][token]` accounting as though the payout succeeded.
3. Emit `EscrowReleased`/`EscrowRefunded`, signalling completion.

Because the escrow accounting is destroyed once `withdraw` "succeeds," there is no way to retry or reclaim the funds — they remain locked in the `IntentGatewayV2` contract with no accounting entry pointing to the rightful owner. This is a permanent freezing/loss of user or solver escrowed funds, matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
This does not require a malicious relayer or admin — any TRC20 token that follows the non-reverting failure convention (a real possibility on Tron, where TRC20 semantics/tooling are less standardized than Ethereum ERC20) used as an order's input/output/fee token will trigger this on any transient failure condition (e.g., temporary pause, blacklist checks, edge-case balance/allowance interactions on the destination token). Given IntentGatewayV2 is designed to be generic across arbitrary user-supplied tokens for intents/orders, encountering such a token is a realistic and likely event over the contract's operational lifetime, not a contrived edge case.

### Recommendation
Replace the raw `.call(...)` + `success`-only checks in `withdraw()` and in the `SweepDust` branch of `onPostRequest` with `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`IntentsBase.sol`, `WrappedHyperFungibleToken.sol`), so that both call failure and a returned `false` result in a revert, preventing escrow accounting from being cleared without funds actually moving.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an ERC20/TRC20 token `T` that returns `false` on transfer failure instead of reverting (e.g., a paused/blacklist-style token, or one that returns `false` when the recipient is blacklisted).
2. A solver fills an order and escrows `T` for the beneficiary via the normal order flow (`_orders[commitment][T] = amount`).
3. Trigger delivery of a `RedeemEscrow` (or `RefundEscrow`) request whose `withdraw()` invocation attempts `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` against `T`, at a moment where `T.transfer` internally returns `false` for the beneficiary (e.g., beneficiary got blacklisted, or the token entered a paused state) rather than reverting.
4. `success` is `true` (the low-level call did not revert), so `withdraw()` proceeds: `_orders[body.commitment][token] -= amount` is executed and `EscrowReleased`/`EscrowRefunded` is emitted.
5. The beneficiary's on-chain `T` balance is unchanged (transfer silently failed), yet the escrow slot is now decremented to zero — the beneficiary has no accounting path left to reclaim the tokens, and the tokens remain stuck in the `IntentGatewayV2` contract permanently.
