### Title
Same-chain intent fills only release escrow for as many input tokens as there are outputs, permanently freezing excess escrowed input tokens - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` builds the list of escrowed input tokens to release to the solver by sizing the array to `order.output.assets.length` and indexing directly into `order.inputs[i]`, instead of iterating over `order.inputs.length`. Users are allowed to escrow any number of input tokens via `placeOrder` with no constraint that `inputs.length == output.assets.length`. When an order has more input tokens than output tokens, the extra input tokens are escrowed at placement but never appear in the `WithdrawalRequest.tokens` array passed to `_withdraw` on a full fill, so they are never transferred out and remain permanently stuck in the gateway contract, exactly analogous to the referenced OpenQ report where a bounty issuer funds more than one ERC20 token but only one gets paid out.

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol` only validates `order.inputs.length == 0` [1](#0-0)  and separately rejects duplicate *output* tokens [2](#0-1) . There is no check anywhere in `placeOrder` that the number of input tokens equals the number of output tokens; every distinct input token is escrowed independently and credited in `_orders[commitment][token]` [3](#0-2) .

For same-chain fills, `IntrinsicIntents._fillSameChain` allocates the escrow-release array using `outputsLen` (the number of *output* assets) and then indexes into `order.inputs[i]` using that same loop counter: [4](#0-3) [5](#0-4) 

This implicitly assumes `order.inputs.length == order.output.assets.length` (a 1:1 pairing between input index `i` and output index `i`), but that invariant is never enforced. If `order.inputs.length > order.output.assets.length`, only the first `outputsLen` input tokens are ever placed into `escrowedInputs`, and only those are passed to `_withdraw`: [6](#0-5) 

`_withdraw` only decrements/transfers the tokens present in `body.tokens` [7](#0-6) , so `order.inputs[outputsLen..inputsLen-1]` are never released to the solver, yet `finalize=true` still marks the order filled: `_filled[body.commitment] = beneficiary` [8](#0-7) .

Because the order is now finalized, the only reclaim path — `_cancelSameChain`, which requires the order not already filled — can no longer be used to recover the excess tokens, and no other function iterates `_orders[commitment][token]` for arbitrary tokens to sweep them out. The excess escrow is permanently locked in the `IntentGatewayV2` contract.

This closely mirrors the referenced OpenQ pattern: a user (order placer) funds/escrows more ERC20 tokens than the payout logic is designed to release, and the excess is stuck with no recovery mechanism, because the release path only knows about a fixed subset of the funded tokens (there, the single "current payout token"; here, the first `outputsLen` inputs).

### Impact Explanation
Any order placer who supplies more distinct input tokens than output tokens (a valid, unrestricted configuration under `placeOrder`) will have the surplus input tokens permanently locked in the `IntentGatewayV2` contract once any solver fully fills the order. This is a direct, permanent loss of user funds with no recovery path (cancellation is blocked once `_filled` is set), satisfying the "permanent freezing of funds" criterion. Any unprivileged user submitting a single `placeOrder` transaction with `inputs.length > output.assets.length` can trigger this, and any solver simply calling the normal `fillOrder` flow completes the freeze — no privileged or malicious actor is required.

### Likelihood Explanation
Likelihood is moderate-to-high: nothing in the public interface, SDK docs, or contract prevents a user from placing an order with more input tokens than output tokens (e.g., a user escrowing two different stable-coins to be swapped for a single output token, or wanting to attach extra collateral/tokens to an order for use by output calldata). The `Order` struct and `placeOrder` never enforce a length match between `inputs` and `output.assets`, so this is reachable through completely standard usage of `placeOrder` plus a normal `fillOrder` call by any solver — no special conditions, front-running, or governance/admin action are required.

### Recommendation
In `_fillSameChain`, iterate escrow release over `order.inputs.length` rather than `order.output.assets.length`, or explicitly enforce (and validate at `placeOrder` time) that `order.inputs.length == order.output.assets.length` for same-chain orders that rely on this positional pairing. Alternatively, decouple escrow release entirely from output-token indexing: on a full fill, always call `_withdraw` with the complete set of remaining `_orders[commitment][token]` balances for every token in `order.inputs`, not just the first `outputsLen` entries, so no escrowed input token can be left unaccounted-for once the order is finalized.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [TokenA: 100, TokenB: 100]` (two input tokens) and `order.output.assets = [TokenC: 100]` (a single output token) — this is accepted since only `inputs.length == 0` is checked, and no cross-check against `output.assets.length` exists.
2. Both `TokenA` and `TokenB` are escrowed: `_orders[commitment][TokenA] = 100` and `_orders[commitment][TokenB] = 100`.
3. A solver calls `fillOrder` providing exactly `100 TokenC` to the beneficiary. In `_fillSameChain`, `outputsLen = 1`, so `escrowedInputs` has length 1 and is populated only with `order.inputs[0]` (`TokenA`), since the loop `for (uint256 i; i < outputsLen; i++)` never reaches index 1 (`TokenB`).
4. `_withdraw` is called with `tokens = [TokenA: 100]`; `_orders[commitment][TokenA]` is zeroed and 100 `TokenA` is sent to the solver. `_orders[commitment][TokenB]` still holds 100 `TokenB`, but `finalize = true` sets `_filled[commitment] = solver`.
5. The order is now finalized (`_filled[commitment] != address(0)`), so `_cancelSameChain`'s early-cancellation window is closed and any attempt to cancel/fill again reverts as already filled. The 100 `TokenB` remains locked in the `IntentGatewayV2` contract with no function able to move it out (it is not part of the `TRANSACTION_FEES` sentinel and is never referenced by any subsequent withdrawal or sweep call for this commitment).

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
