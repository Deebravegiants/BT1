### Title
Emporium's runAction only accounts for ERC20 balance deltas, letting any attacker sweep an ERC1155 position minted/held on Emporium via a self-executed CASE 2 `safeTransferFrom` - (File: `contracts/Transferer.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`Transferer.onERC1155Received`/`onERC1155BatchReceived` unconditionally accept any ERC1155 transfer with no bookkeeping of which stealth address or tx the tokens belong to. `EmporiumUpgradeable.runAction` (which inherits `Transferer`) only diffs `circomData.erc20TokenAddresses` balances before/after a CASE 2 op to mint UTXOs; it has no concept of ERC1155/ERC721 accounting at all. Because CASE 2 ops are executed as `op.endpoint.call(op.callData)` from within the Emporium contract itself, `msg.sender == emporium == from` for any ERC1155 `safeTransferFrom` call an attacker crafts, so the standard `msg.sender==from` authorization trivially passes for anyone.

### Finding Description
The broken equality: `position_owner_after_victim_tx (should be victim's stealth address / UTXO) == actual_holder (Emporium contract, an unowned shared pot)`. Once true, `next_caller_transferFrom_authorised` becomes `true` for **any** subsequent caller, not just the depositor.

Trace:
- `EmporiumUpgradeable.runAction` ( [1](#0-0) ) executes attacker/victim-supplied `EmporiumOperation[] ops` decoded straight from `circomData.externalActionData.externalActionMetadata`. For CASE 2 (`op.invokeWallet==false` or no signer), it does `(success, err) = op.endpoint.call{value: op.value}(op.callData);` — the caller as seen by `op.endpoint` is `address(this)` i.e. the Emporium contract.
- Any ERC1155 mint or transfer performed inside that call that credits `address(this)` (Emporium) leaves the position sitting on the Emporium contract, which accepts it unconditionally via `Transferer.onERC1155Received`/`onERC1155BatchReceived` ( [2](#0-1) ), which unconditionally return the receiver selectors with no state recorded about which run/stealth address the tokens belong to.
- After the ops loop, `runAction` only reconciles `circomData.erc20TokenAddresses` balances via `getBalancesForArray`/`handleOut` ( [3](#0-2) ) to mint an outgoing UTXO. There is no equivalent logic for ERC1155/ERC721 ids — the position is simply left owned by Emporium with zero linkage to the depositor's nullifier/UTXO.
- `verifyWallet` ( [4](#0-3)  ) only checks `usedMessages[circomData.emporiumMessage]` and, if `stack.signerAddress != address(0)`, an EIP-712 signature. For CASE 2, `signerAddress` can be `address(0)`, so no signature/authorization is required at all beyond the replay-guard on `emporiumMessage`.
- The attacker's own subsequent call: any unprivileged EOA runs their own `transact`/proof for their own UTXOs, sets `circomData.externalActionData` pointing to Emporium, and crafts an `EmporiumOperation` with `endpoint = ERC1155TokenAddress`, `callData = abi.encodeWithSelector(IERC1155.safeTransferFrom.selector, emporium, attacker, id, amount, "")`. Since the call originates as `op.endpoint.call(...)` from inside `EmporiumUpgradeable`, `msg.sender` at the token contract equals `emporium == from`, so the ERC1155 standard's `require(from == msg.sender || isApprovedForAll(from, msg.sender))` passes trivially. No nullifier or UTXO of the attacker references the victim's deposit; the attacker's own (unrelated) proof for their own UTXOs is all that's needed to invoke `runAction`.
- None of the existing guards (`onlyAllowedRecipient`, `verifyWallet`'s message replay-guard, `verifyProof`, `insertNullifiers`, `rootHashExists`) constrain which assets a CASE 2 op may move, because CASE 2 ops are arbitrary attacker-chosen calls scoped only by ERC20 balance-delta bookkeeping — ERC1155/ERC721 assets are entirely outside that accounting model.

### Impact Explanation
Any ERC1155-represented position (e.g., a Uniswap-V3-style LP NFT minted as ERC1155, or any other ERC1155 asset) that ends up credited to the Emporium contract as a side effect of a victim's CASE 2 op becomes shared, unauthenticated protocol-level treasure that any subsequent unprivileged caller can drain with a single `safeTransferFrom` op, because Emporium's own address is both `from` and the acting `msg.sender`. This is direct theft of a victim's shielded/in-flight position with no cryptographic linkage or nullifier check protecting it — matching the "Critical: direct theft of shielded or in-flight user funds" category. It is repeatable for every ERC1155 asset that transiently lands on Emporium.

### Likelihood Explanation
Preconditions: some CASE 2 op flow must result in an ERC1155 token being minted/transferred to the Emporium contract (plausible for any integrated protocol that returns an ERC1155 position rather than an ERC20, e.g., concentrated-liquidity LP receipts). Attacker cost is minimal — a single `transact` call with their own valid proof and a crafted `EmporiumOperation`; no special role, signature, or victim key material is required. This is trivially and cheaply repeatable by any observer who monitors on-chain Emporium ERC1155 balances.

### Recommendation
Add ERC1155/ERC721 accounting symmetric to the ERC20 path in `EmporiumUpgradeable.runAction`: track and diff balances (or `ownerOf`) for any ERC1155/ERC721 ids that the op is expected to touch, mint a corresponding UTXO tied to the depositor's `stealthAddressStructure`, and require CASE 2 ops that move ERC1155/ERC721 assets out of Emporium to be constrained to `msg.sender`'s own accounted position (e.g., only allow withdrawing token ids that the current proof/circomData attests were deposited by the same caller, mirroring the ERC20 `deltaAmountChanges` mechanism). Alternatively, disallow CASE 2 ops whose calldata selector matches known NFT/ERC1155 transfer/mint patterns unless routed through a per-user custody contract instead of the shared Emporium address.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC1155 contract with a `mintTo(address to, uint256 id, uint256 amount)` function.
2. Victim calls `transact`/`runAction` with a CASE 2 `EmporiumOperation{endpoint: mockERC1155, callData: mintTo(emporium, id, amount)}`; assert `mockERC1155.balanceOf(emporium, id) == amount` afterward and that no ERC1155-related UTXO was minted for the victim (confirms the position is "orphaned" on Emporium).
3. Attacker (unrelated depositor, own valid proof/UTXO) calls `transact`/`runAction` with a CASE 2 `EmporiumOperation{endpoint: mockERC1155, callData: safeTransferFrom(emporium, attacker, id, amount, "")}`.
4. Assert `mockERC1155.balanceOf(attacker, id) == amount` and `mockERC1155.balanceOf(emporium, id) == 0`, while confirming the attacker's nullifiers/UTXOs used in step 3 are unrelated to the victim's deposit in step 2 (equality broken: intended owner == victim vs. actual owner == attacker).

            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);

                    revert UnauthorizedWalletCall();
                }

            }

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
