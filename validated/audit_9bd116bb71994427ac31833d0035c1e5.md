## Finding

### Title
Unauthenticated legacy QR fallback (`QR_CODE_V2`) allows signup identity claims without cryptographic consent binding - ([File: src/plans/qr_scan/user.rs])

### Summary
The primary user-QR format is cryptographically bound to backend-issued consent data via a `user_data_hash` produced by `decode_qr`, and this hash is later verified against the backend's `authenticated_app_data` before any biometric-key material or data-policy is trusted [1](#0-0) . However, `Data::try_parse` also accepts a legacy, unsigned `QR_CODE_V2` text format (`userid:<uuid>:<digit>`) that produces `user_data_hash: None` and silently discards the QR-embedded `data_policy` digit entirely [2](#0-1) . This is structurally the same "two equivalent entry points, one gated by consent verification and one not" pattern described in the MetaMask report: the strict, hash-verified path enforces that the exposed identity/data truly corresponds to what the user's app consented to, while the fallback low-level text format bypasses that binding entirely.

### Finding Description
`Data::try_parse` tries three parsers in order: the cryptographically bound `decode_qr` format, the unsigned `QR_CODE_V2` regex format, and (feature-gated) the signup-extension format [3](#0-2) . Only the first format populates `user_data_hash`; the `QR_CODE_V2`-derived `Data` always has `user_data_hash: None` [2](#0-1) .

Downstream, `backend::user_status::request` uses this hash as the sole binding mechanism between the backend's `authenticated_app_data` (which carries the real consent-derived fields: `data_policy`, `pcp_version`, `user_centric_signup`, custody keys) and the physical QR the person is holding at the Orb [4](#0-3) . When the backend has no `authenticated_app_data`/`backend_keys` for that `user_id` (the "old QR-code format" branch), the code does not require any hash at all and unconditionally defaults the data policy to `DataPolicy::FullDataOptIn`, ignoring whatever digit was actually encoded in the QR text [5](#0-4) .

The consequence is that an attacker who can print/display any string matching the `QR_CODE_V2` regex — including someone else's known UUID or a completely fabricated one — obtains an accepted, "valid" signup identity/session without ever going through the app-issued, hash-verified consent artifact that the strict path enforces (`decode_qr` + `user_data.verify(user_data_hash)`) [6](#0-5) [7](#0-6) . This mirrors the report's core defect: a low-level/legacy interface that skips the security check ("consent"/verification binding) enforced by the primary interface, enabling the same effective read/claim of identity/data with a weaker gate.

### Impact Explanation
If reachable in production (i.e., the backend still accepts `/api/v1/user/{user_id}/status` for a bare UUID without further binding to a signed artifact), this allows a misattributed or unauthorized signup: a user_id belonging to one person can be claimed/signed-up-against via a fabricated QR, and the Orb will proceed with a default `FullDataOptIn` policy rather than the policy the real user actually consented to in their app. This is a cross-identity attribution/consent-bypass issue, matching the accepted "unauthorized or misattributed signup" impact class.

### Likelihood Explanation
Exploitability depends entirely on backend-side acceptance of the legacy `/api/v1/user/{id}/status` path for arbitrary UUIDs without requiring a corresponding signed consent artifact — code on the Orb side unconditionally trusts this fallback whenever the backend reports no `authenticated_app_data`. Since the legacy format is still actively parsed (`QR_CODE_V2` is not feature-gated, unlike `QR_CODE_SIGNUP_EXTENSION`), the client-side gate for this bypass is always compiled in.

### Recommendation
Remove or feature-gate the unauthenticated `QR_CODE_V2` fallback for production builds, or require the same `user_data_hash`-based verification for any accepted user QR format before trusting `data_policy`/consent fields; never default silently to `FullDataOptIn` for an unverified identity path.

### Proof of Concept
1. Construct a text string `userid:<uuid>:<digit>` matching `QR_CODE_V2`, using either a fabricated UUID or one belonging to another user.
2. Present it as the "user QR code" at the Orb; `Data::try_parse` accepts it via the `QR_CODE_V2` branch with `user_data_hash: None`.
3. If the backend user-status endpoint returns `valid: true` with no `authenticated_app_data` for that id, `backend::user_status::request` proceeds to the "old QR-code format" branch and returns a `UserData` with `data_policy: DataPolicy::FullDataOptIn` and `id_commitment: None`, regardless of what digit was embedded in the QR text and without any cryptographic binding to a genuine app-issued consent artifact.

        if let Ok((user_id, user_data_hash)) = decode_qr(code) {
            return Some(Self {
                user_id: user_id.hyphenated().to_string(),
                signup_extension: false,
                signup_extension_config: None,
                user_data_hash: Some(user_data_hash),
            });
        }
        if let Some(captures) = QR_CODE_V2.captures(code) {
            return Some(Data::from_v2(&captures));
        }
        #[cfg(feature = "internal-data-acquisition")]
        if let Some(captures) = QR_CODE_SIGNUP_EXTENSION.captures(code) {
            return Some(Data::from_signup_extension(&captures));
        }
        None
    }
