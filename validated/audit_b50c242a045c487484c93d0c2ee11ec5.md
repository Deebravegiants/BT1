### Title
Missing reentrancy guard on Tron `IntentGatewayV2.placeOrder()` allows CEI-violation reentrancy across escrow/order state - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The EVM `IntentGatewayV2.placeOrder` at [1](#0-0)  is protected with `nonReentrant`, but the Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, defines `placeOrder` without any reentrancy guard: [2](#0-1) . This mirrors the `createHat()` bug class: state is read, external calls are made to untrusted/attacker-influenced contracts, and only afterward is critical state (escrow accounting, nonce, commitment) finalized — with no reentrancy protection or check-effects-interaction ordering to prevent an attacker from re-entering mid-execution.

### Finding Description
`placeOrder` in the Tron contract computes `order.nonce = _nonce++` and the order `commitment`, then — when `predispatch.call` is set — performs a sequence of external calls before finalizing escrow bookkeeping:
1. `dispatcher.call{value: amount}("")` / `IERC20.safeTransferFrom` to move predispatch assets to the `CallDispatcher` [3](#0-2) 
2. `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` — an arbitrary, attacker-supplied call sequence executed via `CallDispatcher` [4](#0-3) 
3. Only after these external calls does the function credit `_orders[commitment][token]` for escrow and update `_orders[commitment][TRANSACTION_FEES]` [5](#0-4) .

Because `placeOrder` lacks `nonReentrant` (unlike its sibling in `evm/src/apps/IntentGatewayV2.sol`, which uses `nonReentrant` at line 194 and also uses transient-storage duplicate-output guards), an attacker-controlled predispatch target reached through `CallDispatcher.dispatch` can re-enter `placeOrder` (or other unprotected state-mutating functions in the same contract, e.g. `cancelOrder`, which is also not `nonReentrant` at [6](#0-5) ) while the outer call's `_nonce`, commitment, or escrow state is still mid-update. This is structurally identical to the `createHat()` root cause: a state pre-read (`getNextId`/`_nonce++`), a reentrant-reachable external call (`_checkAdmin`/`CallDispatcher.dispatch`), and deferred finalization of critical accounting (`_hats[_admin].lastHatId++`/`_orders[commitment][token] +=`).

### Impact Explanation
A malicious predispatch target can re-enter `placeOrder` during the `ICallDispatcher.dispatch` callback to place additional orders that consume the same `_nonce` sequence inconsistently, or interleave escrow writes so that `_orders[commitment][token]` accounting diverges from actual token custody in the gateway. Given `withdraw()` later trusts `_orders[commitment][token]` to release exactly what was escrowed [7](#0-6) , a reentrancy-induced mismatch between recorded escrow and actual balances can lead to over-crediting escrow relative to tokens actually held, i.e. draining of gateway funds when a solver/relayer later redeems via `withdraw`. This satisfies "concrete theft ... of funds" via an unprivileged, single-transaction path (any user calling `placeOrder` with a malicious predispatch `CallDispatcher` target).

### Likelihood Explanation
Likelihood is High: `placeOrder` is a fully permissionless, unprivileged entry point reachable by any user submitting a transaction with attacker-controlled `predispatch.call` and `predispatch.assets` (routed through `CallDispatcher`, which the docs confirm "executes each call sequentially" [8](#0-7) ). No governance, admin, or privileged relayer role is required — an ordinary user can supply predispatch calldata that targets a contract they control, which re-enters `placeOrder` from within the `dispatch` call.

### Recommendation
Add a reentrancy guard (`nonReentrant`, matching `evm/src/apps/IntentGatewayV2.sol`) to `placeOrder`, `cancelOrder`, and any other state-mutating external entry points in `evm/tron/contracts/apps/IntentGatewayV2.sol`. Additionally, apply check-effects-interactions: increment `_nonce`, compute the commitment, and write escrow/state entries strictly before invoking `ICallDispatcher.dispatch` or any other external call reachable from user-supplied predispatch data.

### Proof of Concept
1. Attacker deploys `MaliciousCallDispatcherTarget`, a contract that, when invoked as part of `order.predispatch.call` via `CallDispatcher`, calls back into `IntentGatewayV2.placeOrder()` with a second order.
2. Attacker calls `placeOrder(order1, graffiti)` on `evm/tron/contracts/apps/IntentGatewayV2.sol`, where `order1.predispatch.call` triggers a call into `MaliciousCallDispatcherTarget`.
3. During `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` (line 414), before `order1`'s escrow (`_orders[commitment1][token]`) is credited, the malicious target re-enters `placeOrder(order2, graffiti)`.
4. Because there is no `nonReentrant` guard, `order2` executes fully (including its own nonce increment and escrow credit) nested inside `order1`'s execution.
5. Depending on shared token balances and `CallDispatcher` sweep timing, the interleaved balance snapshots (`balancesBefore` / actual transferred amounts) used to compute escrowed amounts for `order1` can be manipulated by state changes `order2` made during the reentrant call, producing an `_orders` ledger that credits more escrow than tokens actually received by the gateway — enabling later over-withdrawal via `withdraw()`.

Note: I was not able to fully trace whether every downstream balance-diffing step in the non-`predispatch` branch is similarly reentrancy-safe, since this analysis is based on the indexed contents of `evm/tron/contracts/apps/IntentGatewayV2.sol`; a full symbolic/fuzz test against the compiled Tron contract would be needed to confirm the exact profitable exploitation path and quantify drainable value.

Orders support arbitrary calldata execution at two points in the lifecycle — before escrow (predispatch) and after fill (postdispatch). Both are executed through the `CallDispatcher` contract, which takes an ABI-encoded `Call[]` array:

```solidity
struct Call {
    address to;      // Target contract (must have code, reverts with NotContract otherwise)
    uint256 value;   // ETH to send with call
    bytes data;      // Calldata to execute
}
```

The `CallDispatcher` executes each call sequentially and reverts the entire batch if any call fails.
