### Title
Webhook shop-domain header is not covered by the HMAC, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `#shop` is read directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header. `Utils::HmacValidator` validates the HMAC only over that signable string (the body), so the shop identity delivered to the app's webhook handler is never bound to the cryptographic signature. This is the same class of bug as the reported EIP-777 issue: an identity/field that is acted upon (`shop`) is not covered by the binding mechanism (the HMAC) that is supposed to authenticate the whole message.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it against `verifiable_query.hmac`: [1](#0-0) 

For webhook requests, `to_signable_string` returns `@raw_body` exclusively — the `shop` value (populated from the `shop-domain` header) is excluded entirely from the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app-defined handler, with no additional verification that the shop header matches the tenant the body actually belongs to: [3](#0-2) 

`WebhookMetadata.shop` is the only shop-identifying field the gem hands to the handler, and the documented handler pattern uses it directly to key merchant data/dispatch business logic (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [4](#0-3) [5](#0-4) 

Because a Shopify app's `api_secret_key` is shared across all shops that install the app (it is the app's client secret, not a per-shop secret), any merchant/tenant who has installed the app can trigger a legitimate webhook to their own store, capture the resulting `(raw_body, hmac-sha256)` pair — both are visible to the merchant, since the merchant's own store generated the event — and then replay that exact `raw_body` + `hmac-sha256` to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a different (victim) shop's domain that also has the app installed. Because the HMAC never covers the shop header, `HmacValidator.validate` still succeeds, and `Registry.process` calls the handler with `shop` equal to the attacker-chosen victim domain while `body` is the attacker's own (but validly-signed) payload.

### Impact Explanation
This breaks the equality that should hold between "the shop whose secret produced this HMAC" and "the shop the app processes the payload as." An unprivileged tenant of a multi-tenant app can cause the app to process attacker-controlled webhook content under another tenant's identity — the classic cross-tenant confusion primitive. Depending on what the host application's `WebhookHandler#handle` does with `data.shop` and `data.body` (e.g., write to a merchant record, revoke/replace stored data, trigger merchant-authenticated API calls using a session looked up by `data.shop`), this can lead to cross-tenant data corruption or a foothold for further cross-tenant actions performed with the victim shop's stored access token. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be an ordinary merchant/tenant of the app (able to trigger a webhook-eligible event in their own shop) and be able to send an arbitrary HTTP POST to the app's public webhook endpoint with modified headers — no access to `api_secret_key`, access tokens, or any other credential is needed. This is directly reachable through the gem's documented `Registry.process` / `Webhooks::Request` API exactly as shown in `docs/usage/webhooks.md`, not a misuse of undocumented behavior.

### Recommendation
Bind the shop domain to the HMAC-signed payload before trusting it, e.g., by including `shopify_header("shop-domain")` in `to_signable_string`'s canonical form (or by validating it out-of-band against Shopify per-shop context if `shopify_id_token`/OAuth session data is available), so a valid HMAC for shop A's body cannot be replayed with shop B's header and pass verification. At minimum, document prominently that `request.shop` is not authenticated by `Registry.process` and must be independently reconciled against a known/expected shop before being trusted by the handler.

### Proof of Concept
1. App has two independent tenants: `attacker-shop.myshopify.com` (attacker's own trial/dev store) and `victim-shop.myshopify.com`, both with the same app installed (same `api_secret_key`).
2. Attacker triggers a real webhook-eligible event in their own store (e.g., updates an order), causing Shopify to POST to the app's webhook endpoint with headers including:
   - `x-shopify-hmac-sha256: <valid HMAC over raw_body using api_secret_key>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - body: attacker-controlled order JSON.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (they own the request/response, e.g. via a logging proxy in their own infra, or by controlling the webhook payload's crafted content ahead of time).
4. Attacker sends a forged POST directly to the app's public webhook route with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC — it never inspects the shop header: [6](#0-5) 
6. The app's `WebhookHandler#handle` is invoked with `data.shop == "victim-shop.myshopify.com"` and `data.body` equal to the attacker's own crafted content, causing the app to act on victim-shop's tenant context using attacker-supplied data.
