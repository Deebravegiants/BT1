Based on my investigation, I found a concrete analog of the reported bug class in the Omni Bridge withdrawal status-reporting path.

### Title
Omni Bridge `describeWithdrawal` reports the transfer status/hash of the wrong withdrawal in a multi-withdrawal transaction by trusting array position instead of matching the actual withdrawal identity - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`OmniBridge.describeWithdrawal()` fetches all transfers associated with a NEAR transaction hash and then blindly indexes into that array with `args.index`, assuming that position `N` in the indexer's response always corresponds to withdrawal `N` as tracked by the SDK's local per-bridge counter. There is no validation that the transfer actually returned at that position belongs to the withdrawal being queried (e.g. by comparing `recipient`/`token_id`/`destinationAddress`/`assetId`). This is the same class of bug that was already identified and fixed for the PoA Bridge in this exact repository.

### Finding Description
`describeWithdrawal` in the Omni Bridge does: [1](#0-0) 

```ts

        await this.omniBridgeAPI.getTransfer({
            transactionHash: args.tx.hash,

    if (transfer == null || transfer.recipient == null) {
        return { status: "pending" };
    }
    ...
```

The `index` used here comes from `createWithdrawalIdentifiers()`, which maintains a purely local, per-bridge-route counter incremented in the order the SDK iterates `withdrawalParams`: [2](#0-1) 

There is no cross-check between the transfer object actually returned at position `args.index` by `omniBridgeAPI.getTransfer(...)` and the withdrawal that `args.index` is supposed to represent (e.g. no comparison of `transfer.recipient` against `args.withdrawalParams.destinationAddress`, and no comparison of `transfer.token_id`/`transfer.amount` against the expected asset/amount). The dedicated test `"returns correct transfer by index"` at [3](#0-2)  only proves that indexing works when the indexer's array order matches the SDK's assumed order — it does not, and cannot, prove that the third-party Omni Bridge indexer's ordering is guaranteed to match that assumption for every transaction containing multiple transfers, especially since the indexer is described as the authoritative source of truth for other paths in this SDK (compare the HOT Bridge's similar reliance on the bridge indexer as "source of truth", [4](#0-3) ).

Critically, this codebase has already recognized and fixed exactly this equality-break pattern once before, for the PoA Bridge: [5](#0-4)

And the current PoA implementation explicitly matches by `assetId` rather than raw array position: [6](#0-5) 

```ts
async describeWithdrawal(
    args: WithdrawalIdentifier & { logger?: ILogger },
): Promise<WithdrawalStatus> {
    const response = await this.getWithdrawalStatusWithRetry(args);

    // Response list is unsorted, so we match by assetId instead of index
    const withdrawal = findMatchingWithdrawal(
        response.withdrawals,
        args.withdrawalParams.assetId,
    );
```

The Omni Bridge implementation was never updated to apply the same fix — it still uses the raw `args.index` into an externally-controlled/ordered array, breaking the equality "the status/hash returned corresponds to the withdrawal that was actually queried."

### Impact Explanation
If a single NEAR transaction contains multiple withdrawal intents routed through the Omni Bridge (e.g. a batched request with several assets/destinations), and the Omni Bridge indexer returns transfers for that transaction hash in an order that does not strictly match the SDK's locally-assumed submission order, `describeWithdrawal` will report the completion status and destination transaction hash of a *different* withdrawal than the one being polled. This falls under the "status or hash misreport making an integrator credit or refund twice" impact class: an integrator using `waitForWithdrawalCompletion`/`describeWithdrawal` could mark withdrawal A as completed using withdrawal B's destination `txHash`, potentially crediting/reconciling the wrong withdrawal, or leaving the true withdrawal A permanently unresolved (stuck) while a mismatched result is propagated for it.

### Likelihood Explanation
This requires no privileged access — it only requires more than one Omni Bridge withdrawal to occur within the same NEAR transaction, which is a legitimate SDK-supported flow (the batched-withdrawals API explicitly increments the per-bridge index for such cases). The risk is entirely dependent on whether the external indexer's returned order can diverge from submission order, which is an assumption this codebase has already proven wrong once (PoA Bridge fix). No test in the repository verifies indexer ordering under concurrent/batched transfers for the Omni Bridge, so the code path currently has no defense against this drift.

### Recommendation
Match the transfer to the withdrawal by content (e.g. `recipient` derived from `destinationAddress`/`token_id` derived from `assetId`/`amount`) rather than raw array position, mirroring the fix already applied to the PoA Bridge in `poa-bridge.ts`. At minimum, assert that `transfer.recipient` and `transfer.token_id` are consistent with `args.withdrawalParams` before returning a `completed` status/hash, and treat mismatches as `pending` (or a distinct error) rather than silently returning another withdrawal's outcome.

### Proof of Concept
1. Submit a single NEAR transaction with two Omni Bridge withdrawals in one call: withdrawal #0 sends asset X to address A, withdrawal #1 sends asset Y to address B.
2. The SDK assigns local indices 0 and 1 respectively via `createWithdrawalIdentifiers`.
3. Assume (as demonstrated possible via the existing PoA Bridge unordered-response comment, `"Response list is unsorted"`) that the Omni Bridge indexer's `getTransfer(txHash)` returns the transfer for withdrawal #1 first and withdrawal #0 second.
4. When the SDK calls `describeWithdrawal({ index: 0, ... })` for withdrawal #0, it receives `transfer[0]`, which is actually withdrawal #1's transfer (recipient B, asset Y).
5. `describeWithdrawal` returns `{ status: "completed", txHash: <B's tx hash> }` for what the caller believes is withdrawal #0 (asset X, address A) — an integrator now credits/reconciles withdrawal #0 using address B's transaction, misreporting the on-chain outcome.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
