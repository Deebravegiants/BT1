### Title
Unbounded ancestry walk over attacker-supplied, unverified GRANDPA headers permits an infinite loop / permanent DoS - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
The libarchive CVE describes a crafted-but-checksum-valid input that drives a decompression state machine into a condition where forward progress is never made, causing an unbounded CPU-consuming loop. The closest reachable analog in this codebase is `AncestryChain::ancestry` in the GRANDPA consensus primitives: it walks `parent_hash` pointers over a set of headers supplied verbatim inside an untrusted consensus proof, with no cycle detection and no bound on the number of iterations. Because this walk is invoked on `finality_proof.unknown_headers` *before* any GRANDPA signature/justification check, an attacker can submit a proof whose header set contains two (or more) headers whose `parent_hash` fields point at each other, forming a cycle that never reaches the loop's `base` hash. The `while` loop then never terminates.

### Finding Description
`AncestryChain::ancestry` is implemented as: [1](#0-0) 

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

The loop terminates only when `current_hash == base`, or errors out only if a hash is *missing* from the map. It never checks whether `current_hash` has already been visited. `self.ancestry` is a `BTreeMap<H::Hash, H>` built directly from `finality_proof.unknown_headers` — an attacker-controlled `Vec<H>` of arbitrary SCALE-decoded headers, each with an arbitrary `parent_hash` field (the header hash is derived from its own contents, but `parent_hash` is just a field an attacker fully controls independent of the actual chain).

Critically, this call happens **before** the GRANDPA justification/signature is checked: [2](#0-1) 

```rust
pub fn verify_grandpa_finality_proof<H>(...) -> Result<(...), Error> {
    let headers = AncestryChain::<H>::new(&finality_proof.unknown_headers);
    let target = finality_proof.unknown_headers.iter().max_by_key(|h| *h.number())...;
    if target.hash() != finality_proof.block { Err(Error::LatestBlockMismatch)?; }
    let justification = GrandpaJustification::<H>::decode_all(...)?;
    if justification.commit.target_hash != finality_proof.block { Err(...)?; }
    let from = consensus_state.latest_hash;
    let base = finality_proof.unknown_headers.iter().min_by_key(|h| *h.number())...;
    if base.number() < &consensus_state.latest_height {
        headers.ancestry(base.hash(), consensus_state.latest_hash).map_err(...)?;   // <-- unbounded walk, no sig check yet
    }
    let finalized = headers.ancestry(from, target.hash()).map_err(...)?;             // <-- unbounded walk, no sig check yet
    justification.verify(consensus_state.current_set_id, &consensus_state.current_authorities)...?; // signature check happens AFTER
    ...
}
```

If `finalized_hash` chosen for `base`/`from` never actually connects (because the crafted set contains a cycle disjoint from `base`), the two `headers.ancestry(...)` calls above hang forever, well before any cryptographic signature is verified. No proof-of-authority, no valid GRANDPA commit, and no correct chain data are required to trigger the hang — only a self-consistent SCALE-encoded `Vec<H>` of headers with a `parent_hash` cycle.

This code path is directly reachable through `pallet-ismp`'s unsigned message handler: [3](#0-2) [4](#0-3) 

`handle_unsigned` is an unsigned extrinsic that "permits anyone execute ISMP messages for free," and its `validate_unsigned` implementation calls `Self::execute(messages.clone())` directly during **transaction-pool validation** (i.e., every full node that receives this transaction over the network will attempt to validate it, well before block inclusion). `Message::Consensus` messages route into `GrandpaConsensusClient::verify_consensus`: [5](#0-4) 

which calls `verify_grandpa_finality_proof` / `verify_parachain_headers_with_grandpa_finality_proof` for both `StandaloneChain` and `Relaychain` consensus messages — both feed attacker-controlled `unknown_headers` straight into the unbounded `ancestry` walk.

### Impact Explanation
Because `validate_unsigned` runs on every node that receives the unsigned extrinsic in gossip (not only on the block author), a single crafted "consensus proof" message can hang the transaction-pool validation thread of every node running the GRANDPA ISMP consensus client on the network — a persistent, self-propagating denial-of-service. Even if the extrinsic never gets included in a block, the mere act of broadcasting/validating it consumes unbounded CPU, matching the CVE's "checksum passes, but processing does not detect the issue before hanging" pattern. This satisfies the "route unable to deliver messages" / DoS bar required for a High-severity analog, since it can stall consensus-client updates and message delivery across the network.

### Likelihood Explanation
Likelihood is high: the attacker needs only to submit a single unsigned extrinsic (`Ismp::handle_unsigned`) containing a `Message::Consensus` whose `finality_proof.unknown_headers` include two attacker-crafted headers with mutually-referential `parent_hash` fields (any node fields can be zero/arbitrary since headers only need to SCALE-decode and their `.hash()` derives from their own encoded bytes, which the attacker fully controls). No signatures, no real chain state, and no privileged role are required to reach the vulnerable code, since the ancestry walk executes before the justification signature check.

### Recommendation
- Add cycle detection to `AncestryChain::ancestry` (e.g., track visited hashes in a `BTreeSet` and return an error if a hash is revisited) or bound the walk by the number of entries in `self.ancestry` (a walk can never legitimately need more than `unknown_headers.len()` steps).
- Alternatively, cap `unknown_headers.len()` at ingestion and additionally bound loop iterations to that length, erroring out (`NotDescendent`) once the bound is exceeded.
- Consider verifying the justification/signature threshold before doing any ancestry walk over unauthenticated header data, so unauthenticated input cannot reach expensive graph-walking logic at all.

### Proof of Concept
1. Construct two headers `H_a`, `H_b` (arbitrary state/extrinsics roots, any digest) such that `H_a.parent_hash = H_b.hash()` and `H_b.parent_hash = H_a.hash()` (mutual self-reference achievable by iterating candidate field values until the hashes match, or more simply by pointing both parent_hash fields at pre-computed hashes of each other — feasible since header hash is a deterministic function of its SCALE encoding and the attacker fully controls all fields including `parent_hash`).
2. Set `unknown_headers = [H_a, H_b, ...]` such that `min_by_key(number)` = some `base` header B and `max_by_key(number)` = target T, chosen so that neither `H_a` nor `H_b` is on a real path to `consensus_state.latest_hash` — i.e., `base`/`from` never actually connects to the cycle nodes when traversing from `target`/`from`.
3. Set `finality_proof.block = T.hash()`, and supply a syntactically well-formed (but not necessarily validly-signed) `GrandpaJustification` whose `commit.target_hash == T.hash()` so decoding and the pre-signature-check equality checks pass.
4. Wrap this in `ConsensusMessage::StandaloneChain` (or `Relaychain`), place it in `Message::Consensus`, and submit as `Ismp::handle_unsigned([message])`.
5. On any node processing this extrinsic (via `validate_unsigned` in gossip, or execution), `verify_grandpa_finality_proof` calls `headers.ancestry(from, target.hash())`, which enters the `H_a <-> H_b` cycle and never reaches `base`/`from`, looping forever and consuming 100% CPU on that thread indefinitely.

Note: exact field values needed to make `H_a.parent_hash == H_b.hash()` (and vice versa) depend on the concrete `Header` hashing scheme (Blake2b via `sp_runtime`); this is a standard hash-of-encoded-bytes computation with no cryptographic obstacle, but I was unable to fully hand-construct concrete byte values in this analysis — a background engineer with test-harness access should confirm the exact PoC bytes by writing a unit test analogous to the existing `test_ancestry_route` test in the same file, replacing the honest ancestor chain with a synthetic two-node cycle and asserting the call hangs (or, defensively, that it now returns an error once the fix lands).

pub fn verify_grandpa_finality_proof<H>(
	mut consensus_state: ConsensusState,
	finality_proof: FinalityProof<H>,
) -> Result<(ConsensusState, H, Vec<H256>, AncestryChain<H>), Error>
where
	H: Header<Hash = H256, Number = u32>,
	H::Number: finality_grandpa::BlockNumberOps + Into<u32>,
{
	// First validate unknown headers.
	let headers = AncestryChain::<H>::new(&finality_proof.unknown_headers);

	let target = finality_proof
		.unknown_headers
		.iter()
		.max_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	// this is illegal
	if target.hash() != finality_proof.block {
		Err(Error::LatestBlockMismatch)?;
	}

	let justification =
		GrandpaJustification::<H>::decode_all(&mut &finality_proof.justification[..])
			.map_err(|e| Error::DecodeJustification(alloc::format!("{e:?}")))?;

	if justification.commit.target_hash != finality_proof.block {
		Err(Error::JustificationTargetMismatch)?;
	}

	let from = consensus_state.latest_hash;

	let base = finality_proof
		.unknown_headers
		.iter()
		.min_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	if base.number() < &consensus_state.latest_height {
		headers
			.ancestry(base.hash(), consensus_state.latest_hash)
			.map_err(|_| Error::InvalidAncestry)?;
	}

	let finalized = headers.ancestry(from, target.hash()).map_err(|_| Error::InvalidAncestry)?;

	// 2. verify justification.
	justification
		.verify(consensus_state.current_set_id, &consensus_state.current_authorities)
		.map_err(|e| Error::JustificationVerify(e.to_string()))?;
