This confirms the vulnerability. The `Registry.process` method dispatches `WebhookMetadata` (including `shop`) to the host app's handler after validating only the HMAC, and the HMAC's signable string is the raw body alone, never binding the `shop-domain` header.### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing of delivered webhooks - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but the `shop` value it later hands to the app's `WebhookHandler` is read from an unauthenticated HTTP header. The gem's documented processing flow (`docs/usage/webhooks.md`) instructs apps to trust `data.shop` from the dispatched `WebhookMetadata` as the tenant identifier, but that field is never part of the value that is HMAC-verified.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and secure-compares it against `verifiable_query.hmac`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from independent, unsigned HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`): [3](#0-2) 

The identity binding that should hold is:
`shop asserted to the handler (request.shop, from the shop-domain header) == shop whose secret produced the verified HMAC (implicitly bound by Shopify's real delivery, but not enforced by this gem)`

Because the HMAC is computed only over the body, this equality is never checked by the gem. Any bytes that happen to produce a body whose HMAC validates for the app's `api_secret_key` (e.g. a legitimately-received webhook for Shop A, replayed by an unprivileged actor who intercepts/forwards it, or any request satisfying the body+HMAC pair) can be re-delivered to the app's webhook endpoint with an attacker-chosen `shopify-shop-domain` header for Shop B. The gem will pass HMAC validation (since the header is not part of the signed content) and dispatch `WebhookMetadata` claiming the event belongs to Shop B, even though the signed payload was never associated with Shop B.

This mirrors the analog pattern requested: "a field acted on but not covered by the HMAC" — here the acted-upon field is `shop`, used by host apps (per the gem's own documented example in `docs/usage/webhooks.md`, lines 24-26, which does `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) to route data/session lookups per tenant, while the HMAC covers only the raw body.

### Impact Explanation
This enables cross-tenant data association: a webhook payload legitimately signed for one merchant can be attributed to a different merchant's shop domain in the app's processing pipeline, since the gem provides no binding between the verified bytes and the shop identifier it hands to the handler. Per the app's documented usage pattern, this directly leads to cross-tenant processing of webhook data (e.g., writing shop A's order data under shop B's identity, or triggering actions scoped to the wrong tenant) — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires an unprivileged actor to be able to submit a request to the app's webhook endpoint with a body+HMAC pair that validates for the app's secret and an arbitrary `shop-domain` header — e.g., replaying/forwarding a previously observed valid webhook delivery (which is not encrypted or bound to a specific recipient shop by the gem) with a modified header. Since HTTP headers are trivially attacker-controlled and the endpoint is internet-reachable (that's the whole point of webhook delivery), likelihood is high once any valid (body, hmac) pair for the given secret is obtainable through legitimate observation of one delivered webhook.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) header values inside the HMAC's signable content, or otherwise cryptographically bind the header-derived identity to the verified payload before constructing `WebhookMetadata`, so that `to_signable_string` (or an equivalent check in `HmacValidator`/`Registry.process`) covers all fields that downstream handlers use as trust/tenant boundaries — not just the raw body.

### Proof of Concept
1. App has topic `orders/create` registered with a handler that does `perform_later(shop_domain: data.shop, ...)`, matching the documented example in `docs/usage/webhooks.md`.
2. An unprivileged actor obtains one legitimately delivered webhook body + its `shopify-hmac-sha256` value for Shop A (e.g., by observing/replaying a request to the webhook endpoint before it's consumed, or through any means giving access to a valid (body, hmac) pair for the app's secret).
3. The actor re-submits the same `raw_body` and `hmac` to the app's webhook route, but sets `shopify-shop-domain: shop-b.myshopify.com` instead of Shop A's domain.
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC [4](#0-3) .
5. `Registry.process` dispatches `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <Shop A's data>, ...)` to the app's handler [5](#0-4) , causing Shop A's webhook payload to be processed under Shop B's tenant identity.
