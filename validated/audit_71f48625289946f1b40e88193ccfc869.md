Found it: `ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the OAuth token-exchange request using `auth_query.shop` directly as the target host, without ever routing it through `Utils::ShopValidator.sanitize!` — unlike every sibling flow (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange` via `Session.new`) which all call `ShopValidator.sanitize!` before using `shop` to build a session/host. This breaks the equality "the shop that gets HMAC-verified == the shop that is actually treated as a validated Shopify tenant host," because the HMAC check only proves the query bytes came from someone possessing the app secret's signing key over `{code, host, shop, state, timestamp}` — it does not constrain `shop` to be a syntactically valid `*.myshopify.com`/trusted domain the way `ShopValidator` does (rejecting values like `evil.com/.myshopify.com`, embedded userinfo `@`, multi-label suffix tricks, etc., per `test/utils/shop_validator_test.rb`).

### Title
Missing `ShopValidator` sanitization of `auth_query.shop` in OAuth callback allows `client_secret` (and authorization code) to be sent to an unvalidated host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` ( [1](#0-0) ) takes `auth_query.shop` and uses it, unsanitized, to build `Auth::Session.new(shop: auth_query.shop)` which `Clients::HttpClient` turns directly into the request host: `@base_uri = "https://#{api_host || session.shop}"` ( [2](#0-1) ). The POST body sent to that host includes `client_id`, `client_secret`, and the OAuth authorization `code` ( [3](#0-2) ).

By contrast, every other flow that turns a caller-supplied `shop` string into a request host explicitly calls `Utils::ShopValidator.sanitize!` first: `ClientCredentials.client_credentials` ( [4](#0-3) ) and `RefreshToken.refresh_access_token` ( [5](#0-4) ). `ShopValidator.sanitize!` exists specifically to reject non-Shopify hosts and domain-confusion payloads such as `attacker.com/.myshopify.com`, `myshopify.com.evil.com`, embedded userinfo (`shop.myshopify.com@evil.com`), and lookalike TLDs ( [6](#0-5) , confirmed by `test/utils/shop_validator_test.rb` cases such as `test_rejects_path_that_suffix_matches_myshopify_host` and `test_rejects_userinfo_before_at_sign`).

### Finding Description
`validate_auth_callback` only checks:
1. `Utils::HmacValidator.validate(auth_query)` — an HMAC over `{code, host, shop, state, timestamp}` ( [7](#0-6) , [8](#0-7) ).
2. That the `state` cookie value matches `auth_query.state`.

Neither of these constrains the *format* of `shop` to be a real Shopify domain — the HMAC only proves the bytes were signed with the app secret, it says nothing about whether `shop` parses to a safe host. If a caller's callback route ever ends up handling an `auth_query.shop` value that is not a clean `*.myshopify.com` hostname (e.g. a value containing a path/userinfo trick that Ruby's/HTTParty's URI construction resolves to a different authority than intended, such as `"legit-shop.myshopify.com@attacker.com"` or `"attacker.com/.myshopify.com"`), the resulting request built from `"https://#{session.shop}"` in `HttpClient#initialize` ( [2](#0-1) ) can resolve to `attacker.com`, and the POST to `/admin/oauth/access_token` — carrying `client_secret` and the authorization `code` — is sent there instead of to Shopify. This is exactly the class of "host validated vs. host that receives the client_secret" binding break called out in the scan rules, and it is inconsistent with the rest of the codebase which treats `ShopValidator.sanitize!` as the required gate before using any shop-derived string as a request host.

### Impact Explanation
If exploitable, this results in exfiltration of the app's `client_secret` and the OAuth authorization `code` to an attacker-controlled host, which can be used to complete the OAuth exchange as the attacker and obtain the merchant's access token — a Critical-impact credential theft / cross-tenant access scenario per the given impact taxonomy.

### Likelihood Explanation
Likelihood is **uncertain/low-to-moderate** and I cannot fully confirm exploitability from the gem's code alone:
- `URI(request_url(request))` in `HttpClient#request` ( [9](#0-8) ) is built from `@base_uri_and_path`, which is `"https://#{session.shop}#{base_path}/#{request.path}"`. Whether a crafted `shop` string (e.g. containing `@`, `/`, or other URI-authority-confusing characters) actually causes `URI()`/HTTParty to route to a different host than intended depends on Ruby's `URI` parsing behavior, which I could not execute/verify in this read-only review.
- The HMAC does bind `shop` to a value chosen by whoever initiated the OAuth redirect (normally Shopify, redirecting with a real shop domain). For an attacker to supply a malicious `shop` value with a valid HMAC, they would need the app's `redirect_uri` to be invoked directly by them with a self-forged query string and a valid HMAC — which requires knowing `api_secret_key`, OR relying on the host application forwarding a shop value from some other unauthenticated source into `AuthQuery` before HMAC validation is even meaningful (host-application-dependent, and the HMAC check happens first and would normally reject a request whose `shop` wasn't part of what Shopify actually signed).
- Given the rules exclude findings that "depend on the host application ignoring this gem's documented API" and findings "requiring `api_secret_key`", this analog sits close to the boundary. The concrete gap that *is* independently verifiable and gem-internal is the **inconsistency**: `oauth.rb` omits the `ShopValidator.sanitize!` call that `client_credentials.rb` and `refresh_token.rb` both perform for the same purpose (host safety before sending `client_secret`), which is a real defense-in-depth omission in this gem's own code, not merely a host-app misuse issue.

### Recommendation
In `ShopifyAPI::Auth::Oauth.validate_auth_callback`, sanitize `auth_query.shop` via `Utils::ShopValidator.sanitize!` before constructing `null_session`/`Session.from`, mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`:
```ruby
validated_shop = Utils::ShopValidator.sanitize!(auth_query.shop)
null_session = Auth::Session.new(shop: validated_shop)
...
session = Session.from(shop: validated_shop, access_token_response: ...)
```
This ensures the host that ultimately receives `client_secret` is provably a trusted Shopify domain, independent of any HMAC-format assumptions.

### Proof of Concept
Not independently reproducible from static review alone — reproducing this would require constructing an `AuthQuery` with a `shop` value containing URI-authority-confusion characters (e.g. `"real-shop.myshopify.com@attacker.example"`), a matching HMAC computed with the app's secret over that exact string, and observing whether `URI("https://#{shop}/admin/oauth/access_token")` in `HttpClient` resolves the connection to `attacker.example` rather than `real-shop.myshopify.com`. I was not able to execute code to confirm this URI-parsing behavior, so I cannot assert with certainty that this is exploitable end-to-end; I am flagging the missing `ShopValidator.sanitize!` call as a concrete, verifiable inconsistency in this gem's own code relative to its sibling OAuth flows.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

    module ShopValidator
      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end
