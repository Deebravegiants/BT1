# Title
Donation-inflated token balance permanently bricks the curve's overflow-cap buy path via `OverflowCapDegenerate` / arithmetic underflow — (File: `packages/contracts/src/Router.sol`)

### Summary
The referenced CVE (CWE-20, improper input validation) describes a crafted payload driving an outdated library into an unhandled degenerate state that causes a DoS. alt.fun's `Router._computeBuy` has its own unvalidated invariant: it assumes `Pair.tokenBalance()` (a live, attacker-influenceable ERC20 balance) always stays below the stored virtual `reserveToken` by at least the `LP_RESERVE` gap. Any unprivileged wallet can violate that assumption with a plain ERC20 donation of the launched `Token` directly to its `Pair`, driving the overflow-cap branch into a hard revert (either the explicit `OverflowCapDegenerate()` error or a raw arithmetic-underflow panic) for every subsequent buy that is large enough to hit the real-balance cap — including the curve's own exhaustion-triggered graduation path.

### Finding Description
`Router._computeBuy` caps `tokensOut` at the pair's *live* balance and back-derives `amountInUsed` from a "capped" reserve: [1](#0-0) 

`cappedReserveToken = reserveToken - tokensOut` is only safe as long as `reserveToken > realBalance` — i.e. the design invariant that the stored virtual `reserveToken` always exceeds the live ERC20 `tokenBalance()` of the `Pair` by the `LP_RESERVE` buffer (25% of `Token.TOTAL_SUPPLY`, carved out at launch specifically so the gap never closes under normal trading): [2](#0-1) 

Under a normal buy or sell, `Pair.swap` mutates the stored `tokenReserve` and the real ERC20 balance by the *same* amount, so the gap stays fixed at `LP_RESERVE`: [3](#0-2) 

But `Pair.tokenBalance()` is a live `IERC20.balanceOf`, not something `swap`/`mint` protects from outside transfers: [4](#0-3) 

Any wallet can buy tokens off the curve (`Zap.buy` → `Bonding.buy` → `Router.buy`) and then plainly `transfer()` those same tokens directly to the `Pair` address — an explicitly in-scope action per the rules. That donation increases the live `tokenBalance()` without moving the stored `tokenReserve` (only `Router.buy`/`sell` mutate the stored reserve), which **shrinks** `reserveToken − realBalance` below `LP_RESERVE`. Repeating the buy→donate cycle for roughly `LP_RESERVE` (250M) tokens' worth drives the gap to zero or negative.

Once `realBalance ≥ reserveToken`, the next buy whose uncapped `tokensOut` exceeds `realBalance` (the exact condition the cap exists to catch) hits:
```
tokensOut = realBalance;
cappedReserveToken = reserveToken - tokensOut;  // == 0 or underflows
if (cappedReserveToken == 0) revert OverflowCapDegenerate();
```
producing either the explicit revert or an unguarded arithmetic-underflow panic — permanently, since nothing in `Pair`/`Router` ever reconciles the donated balance back out (there is no sweep of `tokenBalance()` dust; `Router.graduate` only moves the LT/asset side, and `Router.buy`/`sell` only ever move exactly the computed amount).

### Impact Explanation
This bricks every buy sized to land in the overflow-cap band for that token, which specifically includes the curve-exhaustion buy that is one of the two `canGraduate` triggers: [5](#0-4) 

Buyers who would otherwise complete the curve or trigger supply-based graduation are permanently denied service on that size of trade, and any USDC/LT they've committed to a `Zap.buy` that lands on the cap boundary reverts. Because the donated balance can never be un-donated, this is a permanent freeze of the affected trade sizes on that token's curve, not a transient griefing cost.

### Likelihood Explanation
The attack requires only funds to buy roughly `LP_RESERVE`-worth of the token (which the attacker gets back in tokens, not spent LT/USDC beyond fees/slippage) and two plain, permissionless calls: a curve buy through `Zap`/`Bonding`/`Router`, and a raw `IERC20.transfer` to the `Pair` address. No privileged role, oracle manipulation, or upgrade is needed — any unrelated wallet can execute it against any actively-trading token.

### Recommendation
Do not use the live `IERC20.balanceOf`-derived `Pair.tokenBalance()` as the authoritative cap input in `Router._computeBuy`/`previewLtUntilGraduation`/`canGraduate`'s supply leg. Track the real, donation-immune sellable balance in `Pair`'s own accounting (mirroring how `assetReserve` already excludes donations via the stored `k`/virtual-reserve recovery), or explicitly floor `cappedReserveToken` and treat `realBalance >= reserveToken` as "already capped to zero output" instead of reverting, so a donation can only ever reduce achievable buy size, never permanently brick the pair.

### Proof of Concept
1. Token launches on `Bonding`/`Router`/`Pair` with `LP_RESERVE = 250_000_000e18` gap between virtual `tokenReserve` and real `tokenBalance()`.
2. Attacker (any wallet) calls `Zap.buy` repeatedly (or once, sized large) to buy ~250,000,000 tokens off the curve, receiving them to their own address.
3. Attacker calls `Token.transfer(pairAddress, amountJustBought)` directly — a plain ERC20 donation, bypassing `sell()`/`Router`.
4. Repeat 2–3 until `Pair.tokenBalance() >= storedTokenReserve` (verifiable via `Router.getAmountOut`/`previewBuy`/`Pair.getReserves`).
5. Any subsequent buy whose uncapped `tokensOut` (from `_computeBuy`) exceeds `tokenBalance()` now reverts with `OverflowCapDegenerate()` (or an underflow panic), permanently blocking that buy size — including the curve-exhaustion buy needed for supply-triggered graduation — for the lifetime of the pair.

        address token_
