### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` builds the value used to validate a webhook's authenticity (`to_signable_string`) from only the raw HTTP body, while the `shop` (and `topic`/`webhook_id`/`api_version`) values are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` treats a valid HMAC as proof of authenticity for the *entire* request, including `request.shop`, and hands that unauthenticated `shop` value straight to the app's webhook handler.

### Finding Description
`Webhooks::Registry.process` validates a webhook using `Utils::HmacValidator.validate(request)` and, if it passes, immediately trusts `request.shop` when constructing `WebhookMetadata` for the handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the expected signature over `verifiable_query.to_signable_string` using the app's shared `api_secret_key`: [2](#0-1) 

But `Webhooks::Request#to_signable_string` returns only the raw body — it does not include `shop`, `topic`, `webhook_id`, or `api_version`, all of which are read straight from attacker-controllable HTTP headers: [4](#0-3) 

Because `api_secret_key` is a single value shared by the app across **all** shops that install it (not a per-shop secret), any actor who can install the app on a shop they control (an ordinary, otherwise unprivileged action available to any merchant/internet user who installs the public app) receives genuine webhooks whose bodies are HMAC-signed with that same shared secret. That actor can then replay a captured, validly-signed body while rewriting only the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to name a *different* shop. `HmacValidator.validate` will still report success because the signature check never inspects the header. `Registry.process` then calls the handler with `WebhookMetadata#shop` set to the attacker-chosen shop, breaking the equality the host application relies on: `shop authenticated by HMAC == shop attributed to the payload`. In reality only `HMAC-verified == body bytes`, while `shop` is parsed, not verified.

### Impact Explanation
This crosses a tenant boundary within data this gem itself asserts as authenticated: a request that only proves knowledge-of-secret-for-some-body is relabeled as belonging to an arbitrary target shop. Any host application that keys per-shop state, access tokens, or business logic off `WebhookMetadata#shop` (as the gem's own API and tests, e.g. `test/webhooks/registry_test.rb`, encourage) can be made to apply shop-A's webhook payload as if it originated from shop B, i.e. cross-tenant data confusion, satisfying the Critical "cross-tenant access" impact class.

### Likelihood Explanation
The `api_secret_key`/`api_key` pair is shared by every store that installs a given app; any user able to install the app on their own store (a routine, non-privileged action for public apps) can generate arbitrarily many validly-HMAC'd webhook bodies at will and then relabel the shop header before delivering it to the app's endpoint, since the gem never binds the header to the signature.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`/`api_version`) in the value that gets HMAC-verified, e.g. by having `Webhooks::Request#to_signable_string` incorporate the shop-domain header (and other identity-bearing headers) alongside the raw body, so that a signature only validates for the exact shop/topic combination it was generated for, mirroring Velodrome's fix pattern of always binding all state that participates in authorization to the value that's checked.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, receiving genuine webhook deliveries HMAC-signed with the app's shared `api_secret_key`.
2. Attacker captures one such delivery: body `B`, and its valid `x-shopify-hmac-sha256` header `H = HMAC(api_secret_key, B)`.
3. Attacker resends the same body `B` and the same header `H` to the app's webhook endpoint, but rewrites `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers and `to_signable_string` still returns `B`; `HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and it matches `H`, so validation succeeds.
5. `Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, even though the payload never originated from that shop — demonstrating the shop-identity binding is not enforced by the signature.
