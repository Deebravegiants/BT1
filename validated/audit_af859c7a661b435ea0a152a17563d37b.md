### Title
Webhook `shop` field trusted by handlers is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, whose signature check only covers `request.to_signable_string`, i.e. the raw HTTP body. The `shop` value delivered to the host application's handler is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header and is never included in the signed bytes, so it can be modified after a valid signature has been produced without invalidating that signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is derived independently from a header that is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC and then forwards `request.shop` unchecked to the handler: [3](#0-2) 

`WebhookMetadata.shop` is the value the host application is expected to use as the tenant/shop identifier for the webhook: [4](#0-3) 

The binding this gem is expected to guarantee is: `hmac_valid(request) == true` implies `request.shop == the shop Shopify actually sent this exact payload for`. Because `to_signable_string` binds only the body bytes and not the shop-domain header, this equality does not hold. An unprivileged attacker who is a legitimate merchant/app-user of the same app receives genuine webhook deliveries for their own shop (with a valid `hmac-sha256` header computed over the body using the app's secret, which the attacker never needs to know — Shopify computes it). Because the signature is body-only, the attacker can replay that same request to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop domain. `Utils::HmacValidator.validate` still returns `true` (body unchanged), yet `WebhookMetadata#shop` now reports the victim's shop, causing the host application's handler to process attacker-controlled data under the wrong tenant identity.

### Impact Explanation
This is a cross-tenant identity-binding break inside the gem's own webhook-verification primitive: successful HMAC validation is documented/relied upon as proof that the whole webhook request (including which shop it belongs to) is authentic, but the `shop` field the gem hands to handlers is unauthenticated. Any application that uses `WebhookMetadata#shop` (as the library's own generated struct encourages) to select the tenant/session/database record to update is exposed to cross-tenant data confusion or spoofed webhook events attributed to an arbitrary shop, meeting the "cross-tenant access" bar.

### Likelihood Explanation
An attacker only needs to be an ordinary merchant/user who can trigger any webhook-eligible event on their own installed shop (e.g. create an order) to obtain one genuine, validly-signed request, then replay it to the app's public webhook endpoint with a modified shop-domain header. No secret, token, or privileged access is required — this is achievable by any unprivileged internet user who is a customer of the app.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable payload used by `HmacValidator`, e.g. bind `shopify-shop-domain` header content into `to_signable_string`, or independently verify that the shop reported by the request corresponds to a shop the merchant has an active session/installation for before trusting it, rather than relying on HMAC-over-body-only as proof of the full request's authenticity.

### Proof of Concept
1. App exposes a webhook endpoint using `ShopifyAPI::Webhooks::Registry.process`.
2. Attacker (merchant of shop `attacker.myshopify.com`, with the app installed) triggers a genuine event; Shopify sends a POST with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker intercepts/re-sends this exact request to the app's webhook endpoint but rewrites `x-shopify-shop-domain` to `victim.myshopify.com`, leaving body `B` and the HMAC header untouched.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only [5](#0-4)  — it matches, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.shop == "victim.myshopify.com"` [3](#0-2) , even though the payload actually originated from the attacker's shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
