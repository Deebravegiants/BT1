### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop` (tenant identity) is read from an HTTP header that is never included in the signed bytes. `Registry.process` trusts that header value once the body-only HMAC passes and hands it straight to the app's webhook handler as the authoritative tenant identifier. Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that has installed the app, a merchant who has installed the app on their own store can capture one of their own legitimately-signed webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain — the signature still validates.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing the received `hmac` against `OpenSSL::HMAC.hexdigest(..., secret, verifiable_query.to_signable_string)`. [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from unauthenticated HTTP headers, entirely outside the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identity passed to the app's handler: [4](#0-3) 

The binding that should hold is:
`shop used to authorize/attribute the webhook payload == shop cryptographically bound by the HMAC`

but in reality:
`shop trusted by Registry.process (request.shop, from an unsigned header) != shop covered by HmacValidator.validate (only @raw_body is signed)`

Since the HMAC secret is the single app-wide `client_secret` (not a per-shop secret), *any* shop that has installed the app can produce a request with a valid signature for arbitrary raw body bytes it received from Shopify, and then present that same signed body while swapping the `x-shopify-shop-domain`/`shopify-shop-domain` header to name a different, victim shop. The signature check has no way to detect the substitution because the header was never part of the signed content.

### Impact Explanation
This breaks the tenant boundary the webhook processing pipeline is supposed to enforce (Critical - cross-tenant access). An attacker who is merely an unprivileged internet user with respect to other merchants — but a legitimate installer of the app on their own shop — can cause the app to process/attribute webhook data under an arbitrary victim shop's identity, since `WebhookMetadata#shop` (built directly from `request.shop`) is the only tenant signal the host application receives and it is not authenticated. Depending on how the host app's `WebhookHandler` uses `shop` (e.g., to look up/attribute records, redact data, or as a trust anchor for mandatory compliance webhooks like `customers/redact`, `customers/data_request`, `shop/redact`), this can lead to cross-tenant data corruption, spoofed compliance actions, or confused-deputy behavior against other merchants' data.

### Likelihood Explanation
Moderate-to-high likelihood: the attacker only needs to be able to install the app on a shop they control (a normal, low-privilege action) and observe/capture one webhook delivery via any HTTP intermediary they control (their own server, proxy, or logs), then resend it to the app's webhook endpoint with the header modified. No access to the app's `client_secret`, an access token, or any other merchant's credentials is required.

### Recommendation
Bind the shop identity (and other trust-relevant metadata such as topic/api_version/webhook_id) into the HMAC-signable content, or independently verify that `shop` matches an installation the app actually manages before trusting it. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop-domain` header (and ideally topic/webhook-id) so that tampering with those headers invalidates the signature, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` already includes `shop` in its signed parameters. [5](#0-4) 

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, receives a real webhook delivery from Shopify, e.g. body `{"id":1,...}` with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of body computed with the app's client_secret>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: customers/data_request`
2. Attacker resends the exact same raw body and HMAC header to the app's webhook endpoint, but changes only:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this into a `Request` object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `request.to_signable_string` (`@raw_body`) against the HMAC — the `shop-domain` header is irrelevant to that check. [6](#0-5) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` is `"victim.myshopify.com"` — an identity the attacker fully controls, despite never possessing any credential belonging to `victim.myshopify.com`. [7](#0-6)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
