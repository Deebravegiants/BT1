### Title
Webhook Shop Identity Not Bound by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then trusts the `shop` value taken from an unauthenticated header when dispatching to the app's handler. Because the `x-shopify-shop-domain` (or `shopify-shop-domain`) header is never included in the signed material, any party capable of obtaining one genuine, validly-signed webhook (e.g., by installing the app on their own store) can replay that same body+HMAC pair while substituting an arbitrary `shop` header value, causing the host application to process attacker-supplied webhook data attributed to a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from an HTTP header with no cryptographic binding to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` computes/verifies the signature using exactly `verifiable_query.to_signable_string` (the raw body), which for `Request` never includes `shop`: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately forwards `request.shop` to the app's handler as the identity of the tenant the webhook is "for": [4](#0-3) 

The equality this breaks: the gem implicitly promises `shop header == shop that produced/authorized this signed body`, but the HMAC only proves `body == body signed by this app's api_secret_key` — it says nothing about which shop the body belongs to. Since a single app's `api_secret_key` is shared across every shop that installs the app, an unprivileged user can install the target app on their own shop, capture one genuine webhook request (raw body + valid `x-shopify-hmac-sha256`), and replay it against the app's webhook endpoint with the `x-shopify-shop-domain` header changed to any other shop's domain. `HmacValidator.validate` will still pass because it never inspected the header, and `Registry.process` will invoke the registered `WebhookHandler` with `shop:` set to the attacker-chosen (victim) domain.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to key its shop-scoped data model (which is the documented, expected use of this field) can be tricked into writing, updating, or acting on data under a victim shop's tenant using attacker-controlled webhook content. This is a cross-tenant identity-binding failure directly caused by the gem's webhook verification design, not a documented limitation an app could reasonably work around, since the library provides no mechanism to authenticate the `shop` field.

### Likelihood Explanation
Exploitation requires only: (1) an app installed on the attacker's own (or any) Shopify shop — trivial for public/free apps and even for many paid apps via a free trial, and (2) the ability to observe one legitimate webhook delivery to capture body+HMAC, and (3) sending a crafted HTTP POST to the app's public webhook endpoint with a modified `shop` header. No access token, `client_secret`, or privileged account is required — this is achievable by any unprivileged internet user who can install the app once.

### Recommendation
Bind the shop identity into the verified material: include the `shop` (and ideally `topic`/`webhook_id`) header values in the string that `Utils::HmacValidator` verifies, or independently verify that the `x-shopify-shop-domain` matches an expected/whitelisted shop for the given secret before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted as an identity boundary without additional verification (e.g., cross-checking against the app's known installed shops).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a genuine webhook, e.g. `orders/create`, with:
   - `x-shopify-hmac-sha256: <valid HMAC over raw body B>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - raw body `B` (attacker fully controls its content, e.g., by creating an order on their own store)
2. Attacker POSTs the exact same raw body `B` and the exact same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4)  which succeeds because it only hashes `raw_body` (unchanged).
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker-controlled body B>, ...)` [6](#0-5) , causing the host app to process attacker-controlled data as if it originated from the victim shop.
