### Title
Webhook shop-domain and topic headers are trusted for tenant routing but excluded from the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature exclusively over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — all delivered as unauthenticated HTTP headers — are handed to the application's webhook handler as if they were verified. This breaks the intended binding "the shop that receives/produces this webhook body == the shop the handler is told this data belongs to," letting an attacker who can produce one genuine `(body, HMAC)` pair for their own tenant relabel it as belonging to a different shop.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery`'s `hmac` against `to_signable_string` [1](#0-0) . For webhooks, `to_signable_string` returns only the raw JSON body [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are parsed directly from HTTP headers with no cryptographic binding to the body or to each other [3](#0-2) .

`Registry.process` validates only the HMAC over the body, then dispatches the handler using the unauthenticated `request.shop` and `request.topic` values taken straight from headers: [4](#0-3) 

The equality the design implicitly assumes is:
`shop authenticated by HMAC == shop delivered to the handler as WebhookMetadata#shop`

In reality the HMAC only authenticates `raw_body`; it says nothing about the `shopify-shop-domain` (or `x-shopify-shop-domain`) header value that is forwarded to the handler. Any entity capable of causing the app to receive one legitimately-signed webhook body for their **own** shop (trivial — install the app on any store you control, take any action that fires a webhook with attacker-influenced body content, e.g., updating a product title) can capture that valid `(raw_body, hmac)` pair and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` will call the handler with `WebhookMetadata.new(shop: <victim shop>, body: <attacker-controlled body>, ...)` — the handler cannot distinguish this from a genuine webhook about the victim.

### Impact Explanation
This is a cross-tenant impact: the vulnerable field (`shop`) is exactly the value applications are expected to use to select which tenant's records to read/write in response to a webhook (this is the documented purpose of `WebhookMetadata#shop`). An attacker who only needs to control one shop can inject attacker-chosen webhook body content and shop attribution for **any other merchant**, which meets the "cross-tenant access" bar for Critical severity in the rules.

### Likelihood Explanation
Medium-High. No access to another merchant's credentials, no `client_secret`, no TLS interception, and no privileged account are required — only ordinary installation of the app on a shop the attacker controls (or, more directly, use of Shopify's own webhook-trigger tooling, which delivers a genuinely HMAC-signed payload to a URL of the attacker's choosing) plus a standard HTTP replay with a modified header. The header rewrite step is entirely within reach of an unprivileged internet-facing client since the header is not cryptographically protected.

### Recommendation
Include the tenant-identifying and routing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable payload used for HMAC verification, or otherwise bind them (e.g., by validating `shop` against the session/shop that owns the specific `webhook_id`, and rejecting mismatches) before handing them to `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated and must be independently reconciled by the host app against known installed shops before being trusted for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and performs an action producing a webhook whose body they can influence (e.g., renames a product to arbitrary attacker-controlled text), causing Shopify to POST a validly HMAC-signed webhook to the app's endpoint:
   ```
   POST /webhooks
   X-Shopify-Topic: products/update
   X-Shopify-Hmac-Sha256: <valid HMAC over raw body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   { "id": ..., "title": "ATTACKER PAYLOAD" }
   ```
2. Attacker captures this exact `(raw_body, X-Shopify-Hmac-Sha256)` pair (their own webhook, so no interception needed — e.g. via their own reverse proxy logs, or Shopify's webhook trigger/testing tools).
3. Attacker resends the identical body and HMAC header, only changing:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) succeeds because it only checks the body against the HMAC.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, and the host app acts on victim-shop's data using attacker-supplied content.
