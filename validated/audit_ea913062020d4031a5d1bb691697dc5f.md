### Title
Mixed-route batches can bind `describeWithdrawal` to the wrong on-chain nonce, letting withdrawal `j`'s cancellation be reported as withdrawal `i`'s failure - ([File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts])

### Summary
`describeWithdrawal` selects the on-chain nonce for a withdrawal purely by `nonces[args.index]`, where `args.index` is a per-bridge-route ordinal counter assigned in `createWithdrawalIdentifiers` from the order of `withdrawalParams` passed by the caller. Nothing cross-checks that the nonce fetched at that position actually corresponds to withdrawal `i`'s destination/chain/amount, so if the ordinal position diverges from the true on-chain order of gasless-withdraw intents (e.g. in a mixed-route batch where some entries are routed to other bridges), a `Canceled` status belonging to a different withdrawal can be reported for withdrawal `i`.

### Finding Description
The broken equality this depends on is:

`index-th element of withdrawalParams filtered by bridge.route (assigned in createWithdrawalIdentifiers)` == `index-th element of nonces[] returned by hotSdk.near.parseWithdrawalNonces(tx.hash, tx.accountId)`

`createWithdrawalIdentifiers` computes `args.index` as a simple counter keyed only by `bridge.route`, incremented every time a withdrawalParam is routed to that bridge [1](#0-0) . This value is later passed straight into `HotBridge.describeWithdrawal` as `args.index`, which uses it to index directly into the array of nonces parsed from the NEAR transaction: `const nonce = nonces[args.index]` [2](#0-1) . There is no check anywhere in `describeWithdrawal` that the selected `nonce` actually corresponds to `args.withdrawalParams` (its `destinationAddress`, `assetId`/chain, or `amount`) — the code trusts positional alignment only.

Once `nonce` is selected, `getGaslessWithdrawStatus(nonce.toString())` is queried and, if the result is `HotWithdrawStatus.Canceled`, the function unconditionally reports `{status: "failed", reason: "Withdrawal was cancelled"}` for whatever `WithdrawalIdentifier` was passed in [3](#0-2) . `watchWithdrawal` then turns any `"failed"` status into a thrown `WithdrawalFailedError` [4](#0-3) , which callers (e.g. `sdk.waitForWithdrawalCompletion`) treat as definitive proof withdrawal `i` failed and is refundable off-chain.

If the ordinal position assigned to withdrawal `i` by `createWithdrawalIdentifiers` does not match `i`'s true position among the on-chain gasless-withdraw intents (e.g., because the batch is mixed-route and the counter is per-route rather than tracking the true global intent order, or because a `supports()` call throws/skips unexpectedly for one entry, shifting all subsequent counts), `nonces[args.index]` resolves to a nonce belonging to a different withdrawal `j`. If `j` was legitimately cancelled while `i` is still pending/completing on-chain, the integrator is told `i` failed, even though `i`'s real funds later land.

None of the existing guards catch this: `validateAddress`/`compareAddresses` only validate the destination string format, not that it matches the withdrawal actually reported on; `assert` sanity checks in `createWithdrawalIntents` only validate amounts at intent-build time, not at status-read time; and `describeWithdrawal` performs no assertion tying the fetched nonce/status back to `args.withdrawalParams`.

### Impact Explanation
The misreported `status: "failed"` for withdrawal `i` is surfaced to the integrator as a hard `WithdrawalFailedError`, causing the integrator to treat `i` as failed/refundable while `i`'s real on-chain transfer may still complete — a status misreport that can lead to a double payout (refund off-chain + real transfer on-chain). This matches the "status or hash misreport making an integrator credit or refund twice" High-severity category. The bug is repeatable for any mixed-route batch withdrawal call where the ordinal/index bookkeeping in `createWithdrawalIdentifiers` diverges from the true on-chain nonce ordering.

### Likelihood Explanation
This requires: (1) a batch of withdrawal params spanning multiple routes/bridges submitted together, and (2) the per-route index counter in `createWithdrawalIdentifiers` diverging from the actual on-chain ordering of gasless-withdraw nonces for the HotBridge-routed subset. The attacker (an unprivileged party whose withdrawal request is one entry in a batch) does not need special privileges beyond normal SDK usage to trigger a divergent ordering in a mixed-route batch; whether such divergence is actually reachable depends on invariants in the intent-building code (i.e., whether `withdrawalParams` order is always guaranteed to match on-chain intent order for the filtered subset) that were not independently re-verified in this pass — this analysis relies on the premise (stated in the question) that such index-mismatch scenarios are already established elsewhere.

### Recommendation
In `HotBridge.describeWithdrawal`, do not rely solely on positional array indexing to bind a `WithdrawalIdentifier` to a nonce. Cross-validate the selected nonce/withdrawal record against `args.withdrawalParams` (destination address, chain, token, amount) before treating any status — especially `Canceled` — as authoritative for that specific `WithdrawalIdentifier`. Alternatively, make `createWithdrawalIdentifiers` compute `index` from the same on-chain source of truth (`parseWithdrawalNonces`) rather than a client-side per-route counter derived from caller-supplied `withdrawalParams` ordering.

### Proof of Concept
```ts
// vitest, mocks only HTTP/SDK calls
it("misattributes Canceled status from nonce j to withdrawal i when index is miscomputed", async () => {
  const nonces = [10n, 20n]; // on-chain order: index 0 -> nonce 10n (withdrawal i), index 1 -> nonce 20n (withdrawal j, cancelled)

  vi.spyOn(hotSdk.near, "parseWithdrawalNonces").mockResolvedValue(nonces);
  vi.spyOn(hotSdk, "getGaslessWithdrawStatus").mockImplementation(async (nonce) => {
    return nonce === "20" ? HotWithdrawStatus.Canceled : HotWithdrawStatus.Pending;
  });

  // Simulate a miscomputed index (e.g. from a mixed-route batch) that points
  // withdrawal i's identifier at index 1 (nonce 20n) instead of the correct index 0 (nonce 10n)
  const widForI = { ...baseWid, index: 1 }; // should have been index: 0

  const status = await hotBridge.describeWithdrawal(widForI);

  // Assert the equality is broken: status returned for "withdrawal i" reflects nonce 20n's (withdrawal j's) cancellation
  expect(status).toEqual({ status: "failed", reason: "Withdrawal was cancelled" });

  await expect(
    watchWithdrawal({ bridge: hotBridge, wid: widForI })
  ).rejects.toThrow(WithdrawalFailedError); // thrown for withdrawal i based on withdrawal j's cancellation
});
```
