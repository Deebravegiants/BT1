### Title
Stale cached QR-code eligibility state bypasses re-validation across signup attempts - (File: src/plans/mod.rs)

### Summary
`MasterPlan::scan_remaining_qr_codes` caches previously scanned/validated operator and user QR-code state (`QrCodes::Both`) and reuses it for a subsequent signup attempt as long as an elapsed-time check passes, without re-invoking `check_signup_conditions` or re-verifying the user's eligibility. This mirrors the `AirdropBroker` root cause: a per-attempt eligibility artifact (`phase4Users[msg.sender]`) that is not cleared/re-validated at the boundary of a new "epoch" (here, a new signup attempt) is carried forward and consumed again.

### Finding Description
`QrCodes` is a cache of `{operator_data, user_qr_code, user_data, user_qr_code_string}` populated once via `scan_operator_qr_code` → `verify_operator_qr_code` and `scan_user_qr_code` → `handle_user_qr_code` → `verify_user_qr_code`. It is threaded across the outer signup loop in `MasterPlan::run` [1](#0-0) .

In `scan_remaining_qr_codes`, when `QrCodes::Both { .. }` already holds a previously validated operator/user pair and the operator timestamp has not exceeded `operator_qr_expiration_time`, the function immediately returns the cached `ResolvedQrCodes` without calling `check_signup_conditions`, without re-running `verify_operator_qr_code`, and without re-running `verify_user_qr_code`: [2](#0-1) 

Contrast this with the fully fresh path (the `_ =>` branch), which explicitly calls `check_signup_conditions(orb)` before proceeding and performs full operator+user verification each time: [3](#0-2) 

The eligibility artifact (`user_data`/`user_qr_code` obtained from a single backend validation call in `backend::user_status::request`) is the analog of `phase4Users[msg.sender]`: it is set once and is expected to gate exactly one signup, but the branch-selection logic based purely on a timestamp comparison (`operator_data.timestamp.elapsed() < operator_qr_expiration_time`) allows this already-consumed validation result to be reused to satisfy the "eligibility gate" of a later signup pass through `do_signup`, exactly as `phase4Users` was reused across epoch 4/5 in the reported bug, because nothing clears or re-checks the cached state at the new "epoch" (signup attempt) boundary.

### Impact Explanation
If `do_signup` returns early (e.g., version check, relay failure, capture failure) with the `QrCodes::Both` value never being invalidated, and the caller loop re-enters with that stale `QrCodes` value, `scan_remaining_qr_codes` will skip: (a) `check_signup_conditions` (which gates on network health) and (b) any re-verification of the user's current eligibility/session status with the backend for a value that is otherwise treated as fresh authorization for a new biometric-capture/enrollment attempt. This risks a stale/one-time-use identity authorization being consumed to authorize a second capture-and-enrollment pass without a fresh backend eligibility check, a cross-signup state bleed of an authorization artifact analogous to the confirmed Medium-severity finding in `AirdropBroker`.

### Likelihood Explanation
Reachable only through the internal state machine (not attacker-controlled input directly), and requires a specific sequence: cached `QrCodes::Both` surviving into a re-entry of `scan_remaining_qr_codes` within the expiration window. This is an unprivileged/no-elevated-access code path (ordinary signup flow), so it does not require malicious node/peer/operator access — it is purely a logic-timing condition in the signup state machine, matching the "unprivileged-user analog" and "signup authorization" categories in scope.

### Recommendation
On every new signup attempt (each `do_signup` invocation, or before returning from `scan_remaining_qr_codes`'s cached branches), explicitly invalidate/re-derive `QrCodes::Both` unless it can be proven the previous attempt never consumed it, and always call `check_signup_conditions` before using a cached user/operator eligibility result. Prefer per-attempt eligibility values that are consumed exactly once (analogous to deleting `phase4Users[msg.sender]` after use) rather than relying solely on a timestamp/expiration comparison to decide whether a previously granted authorization is still valid for a fresh attempt.

### Proof of Concept
1. Complete `scan_remaining_qr_codes` once via the `_ =>` branch, producing `QrCodes::Both { operator_data, user_qr_code, user_data, .. }` with `operator_data.timestamp = now`.
2. `do_signup` fails after `scan_remaining_qr_codes` succeeds but before completing enrollment (e.g., `is_orb_os_version_allowed` fails-open in `stage`, or `orb_relay_announce_orb_id` fails), returning `result` while the original `QrCodes::Both` reference is still in scope for a subsequent call path that reuses it.
3. On next invocation of `scan_remaining_qr_codes` with the same `QrCodes::Both` and `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, the branch at [4](#0-3)  is taken, bypassing `check_signup_conditions` and both `verify_operator_qr_code`/`verify_user_qr_code`, reusing the already-consumed eligibility/user_data for a new signup pass.

Note: I could not fully trace whether `QrCodes::Both` is guaranteed to be reset to `QrCodes::None`/`Operator` by the caller between every `do_signup` call in all failure paths of `MasterPlan::run`; this would need to be confirmed by tracing all callers/return paths of `do_signup` and `after_signup` to determine whether the analog is exploitable in practice or only under specific error branches.
