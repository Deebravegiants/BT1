### Title
`system-repay` rounds `principal-repaid` and `principal-reduction` independently, letting `total-borrowed` desync from `principal-scaled`/`total-debt` - (File: `local-testing/contracts/vault/vault-stx.clar`, also `vault-sbtc.clar`, `vault-ststx.clar`, `vault-ststxbtc.clar`, `vault-usdc.clar`, `vault-usdh.clar` and their `mainnet/contracts/vault/v0-vault-*.clar` counterparts)

### Summary
`system-repay` computes two structurally-identical but independently-rounded pro-rata reductions from the same `capped-amount`: `principal-reduction = mul-div-down(capped-amount, scaled-principal, debt)` (applied to the global `principal-scaled`) and `principal-repaid = mul-div-down(capped-amount, total-borrowed-amount, debt)` (applied to the global `total-borrowed`). Because `scaled-principal/debt` and `total-borrowed/debt` are generally different ratios (the former is fixed by `INDEX-PRECISION/index` while the latter depends on the historical mix of borrow-time indices across the whole pool), a small enough `capped-amount` can floor `principal-repaid` to `u0` while `principal-reduction` stays non-zero, decoupling `total-borrowed` from the debt actually represented by `principal-scaled`.

### Finding Description
The intended debt-agreement identity is:
```
total-debt = principal-scaled * index / INDEX-PRECISION
total-borrowed should shrink in lockstep with principal-scaled on every repay
``` [1](#0-0) 

In `system-repay`, both reductions are derived from the *same* `capped-amount` but scaled by two different bases and independently floor-rounded: [2](#0-1) 

```
principal-reduction = mul-div-down(capped-amount, scaled-principal, debt)   -- reduces principal-scaled
principal-repaid    = mul-div-down(capped-amount, total-borrowed-amount, debt) -- reduces total-borrowed
``` [3](#0-2) 

`calc-principal-ratio-reduction` and the inline `mul-div-down` used for `principal-repaid` are the same primitive applied to different quantities: [4](#0-3) 

Because `debt = scaled-principal * index / INDEX-PRECISION` exactly (by construction, `calc-cumulative-debt`), the ratio `scaled-principal/debt ≈ INDEX-PRECISION/index` is essentially fixed by the vault's *current* index, whereas `total-borrowed/debt` reflects the *nominal, non-index-adjusted* sum of historical borrows (`total-borrowed` is simply accumulated via `(var-set total-borrowed (+ (var-get total-borrowed) amount))` in `system-borrow`, with no index correction) [5](#0-4) . These two ratios have no enforced relationship, so for a pool whose outstanding debt is dominated by long-aged, heavily-interest-accrued borrowing, `capped-amount * total-borrowed / debt` can floor to `u0` while `capped-amount * scaled-principal / debt` (and thus `capped-reduction`) remains positive.

When this happens: `total-borrowed-new = total-borrowed-amount` (unchanged, since `principal-repaid = u0`), `interest-paid = capped-amount` (the *entire* repaid amount is credited to `assets` as "interest"), and `principal-scaled` is still reduced by `capped-reduction` — so `total-debt` (`principal-scaled * index / INDEX-PRECISION`) shrinks while `total-borrowed` does not. Repeating this on many dust-sized partial repayments (each individually satisfying `capped-amount * total-borrowed < debt`) can drive `principal-scaled`/`total-debt` all the way to `u0` while `total-borrowed` never decreases — the only case where the mismatch is guaranteed to self-correct is a single repayment where `capped-amount == debt` exactly (then `mul-div-down(debt, total-borrowed, debt) = total-borrowed` exactly, with no rounding loss).

The call path is reachable by an ordinary unprivileged liquidator through the market's liquidation flow: `process-debt-asset` / `calc-final-liquidation-amounts` / `calc-liq-debt-repay-real` compute a `debt-final`, which `scale-debt-for-liquidation` converts to `debt-to-repay` (the `amount` forwarded to `system-repay`) [6](#0-5) . A liquidator that partially liquidates a small, collateral-capped chunk of an old, interest-heavy position (via `calc-liq-debt-repay-real`, triggered when seized collateral is capped below expectation) controls the size of `debt-to-repay`/`amount`, and thus can choose values small enough to trigger the described rounding split.

No existing guard prevents this: `check-caller-auth` only restricts the caller to the authorized market contract (not the size of `amount`), `capped-amount = min(amount, debt)` only bounds the top end, and there is no invariant check tying `total-borrowed` to `principal-scaled`/`index` after a repay.

### Impact Explanation
Each qualifying dust liquidation leaves `total-borrowed` stale by `principal-repaid`'s rounding error (up to a few base units per call, since `mul-div-down` floors), while the underlying tokens for `capped-amount` are still fully received (`receive-underlying`) and fully credited to `assets` via `interest-paid = capped-amount`. No tokens vanish or are stolen — the divergence is a bookkeeping/state-consistency bug between `total-borrowed` and `principal-scaled`/`total-debt`. Its consequence is that `total-assets = assets + max(0, debt - total-borrowed)` and `get-available-assets` (used to gate `system-borrow`/withdrawals) can misstate the interest-vs-principal split once `total-borrowed` no longer tracks real outstanding principal, understating available liquidity relative to what `assets` actually holds. This is repeatable per dust liquidation on any position/pool state where `total-borrowed/debt` is smaller than `scaled-principal/debt`, and it is self-healing whenever debt is repaid in one exact full-amount shot; it only accumulates permanently if a position/pool's debt is walked all the way to `u0` exclusively through partial dust repayments that individually floor `principal-repaid` to zero.

### Likelihood Explanation
Exploiting this at meaningful scale requires: (1) a pool/position whose outstanding debt is dominated by very old, heavily interest-accrued borrows relative to the vault's current `index` (an economically unusual state, since normal liquidation thresholds should force full liquidation well before this magnitude of divergence accumulates), (2) many repeated attacker-funded liquidation transactions each carefully sized to keep `capped-amount * total-borrowed < debt`, and (3) the targeted debt eventually reaching exactly `u0` without any single repayment satisfying `capped-amount == debt`. The capital cost per call is small (dust-sized liquidations), but the number of transactions needed and the narrow precondition on the vault's aggregate index/borrow-age distribution make this a low-to-moderate likelihood, position-specific/aggregate-state-dependent issue rather than a trivially repeatable drain.

### Recommendation
Derive `total-borrowed`'s reduction from the *same* rounding-consistent path as `principal-scaled`, e.g., compute `total-borrowed-new` directly from `updated-scaled-principal` and the borrow-index history, or reconcile `total-borrowed` to `min(total-borrowed-amount, total-borrowed-amount * updated-scaled-principal / scaled-principal)` so both quantities scale by the identical fraction with a single rounding, and additionally force `total-borrowed-new = u0` whenever `updated-scaled-principal` reaches `u0` (full pool closure) to prevent any residual phantom principal from surviving debt reaching zero.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Deploy `vault-stx` (or any vault) and the market; set an interest-rate curve with nonzero rate.
2. Borrow a moderate amount at time `t0` (records `principal-scaled0`, `total-borrowed0`, `index0 = INDEX-PRECISION`).
3. Advance many blocks / accrue interest until `index` has grown substantially relative to `INDEX-PRECISION` (so `total-debt >> total-borrowed`).
4. Trigger repeated small partial liquidations (or direct authorized-contract calls to `system-repay` with small `amount` values in a test harness) sized so that `amount * (var-get total-borrowed) / (total-debt)` floors to `0` each time, while `amount * (var-get principal-scaled) / (total-debt)` stays `>= 1`.
5. After each call assert: `(var-get total-borrowed)` is unchanged while `(var-get principal-scaled)` has strictly decreased.
6. Repeat until `(var-get principal-scaled)` reaches `u0` (equivalently `total-debt` reaches `u0`), and assert `(var-get total-borrowed) > u0` at that point — i.e., `total-borrowed` did not reach `u0` in lockstep with `principal-scaled`, breaking the debt-agreement identity `principal-scaled * index == total-debt` vs. `total-borrowed` tracking.
7. Contrast with a control test where the position is closed via one `system-repay` call with `amount >= debt`: assert both `principal-scaled` and `total-borrowed` reach `u0` simultaneously (no divergence), demonstrating the bug is specific to the partial/dust-repayment path.

(define-public (system-repay (amount uint))
  (let (
        (states (var-get pause-states))
        (u (try! (accrue)))
        (scaled-principal (var-get principal-scaled))
        (idx (var-get index))
        (debt (total-debt))
        (total-borrowed-amount (var-get total-borrowed))
        (capped-amount (if (> amount debt) debt amount))
        (principal-reduction (calc-principal-ratio-reduction capped-amount scaled-principal debt))
        (capped-reduction (if (> principal-reduction scaled-principal) scaled-principal principal-reduction))
        (updated-scaled-principal (- scaled-principal capped-reduction))
        (principal-repaid (mul-div-down capped-amount total-borrowed-amount debt))
        (interest-paid (- capped-amount principal-repaid))
        (total-borrowed-new (if (> total-borrowed-amount principal-repaid) (- total-borrowed-amount principal-repaid) u0)))

;; Scale debt for storage and calculate final execution amounts
;; Converts to scaled units, caps at current debt, calculates final collateral
;; Returns: { scaled-to-remove: uint, debt-to-repay: uint, coll-final: uint }
(define-private (scale-debt-for-liquidation
  (debt-final uint)
  (coll-actual uint)
  (curr-scaled uint)
  (asset-id uint))
  (let (;; convert debt amount to scaled units for storage
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        (scaled-debt (mul-div-down debt-final INDEX-PRECISION borrow-index))
        ;; cap at current debt (prevent over-repayment)
        (scaled-to-remove (if (> scaled-debt curr-scaled) curr-scaled scaled-debt))
        (debt-to-repay (mul-div-up scaled-to-remove borrow-index INDEX-PRECISION))
        ;; If debt was capped, scale collateral proportionally
        (coll-final (if (< scaled-to-remove scaled-debt)
                        (mul-div-down coll-actual scaled-to-remove scaled-debt)
                        coll-actual)))
    {
      scaled-to-remove: scaled-to-remove,
      debt-to-repay: debt-to-repay,
      coll-final: coll-final
    }))
