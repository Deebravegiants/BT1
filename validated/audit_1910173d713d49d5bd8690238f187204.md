### Title
Whale-sized high-utilization debt overflows index accounting and permanently freezes a market - ([File: common/src/rates/index.rs])

### Summary
An unprivileged borrower can leave a market in a state where the next interest accrual overflows `i128` while converting scaled debt to its indexed value. Because every subsequent accrual follows the same path, `update_indexes`, `withdraw`, `repay`, and liquidation operations fail with `MathOverflow`, leaving suppliers and borrowers unable to exit that market. [1](#0-0) 

### Finding Description
`Controller::borrow` is an unprivileged owner-authorized path that ultimately calls `Cache::calculate_utilization`, which computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`. [2](#0-1)  The debt-side index update similarly materializes `borrowed.mul(old_borrow_index)` and `borrowed.mul(new_borrow_index)` without constraining the RAY-scaled product to `i128::MAX`. [3](#0-2)  Although `update_borrow_index` caps the index itself after multiplication, that cap does not bound `borrowed * index`; therefore a sufficiently large scaled-debt total can overflow before the configured `MAX_BORROW_INDEX_RAY` is reached. [4](#0-3) 

`interest::global_sync` repeatedly applies `accrue_chunk`, and every chunk calls `accrue_step` with the market's scaled supply, scaled debt, and indexes. [5](#0-4) [6](#0-5)  Once one chunk reaches the overflowing product, the transaction reverts before `mark_accrued` or a commit can shorten the accrued interval, so the same oversized interval and state are retried forever. [7](#0-6) 

The repository's own long-horizon test demonstrates the reachable cliff: with a one-billion-token 18-decimal market and 98% utilization, `update_indexes` eventually raises `MathOverflow` while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`, and subsequent `withdraw` and `repay` calls raise the same error. [8](#0-7) 

### Impact Explanation
This permanently freezes all funds in the affected market because borrowers cannot repay and suppliers cannot withdraw once the next accrual reaches the overflowing product. [9](#0-8)  The failure also blocks liquidation and ordinary index refresh, so collateral backing the affected debt cannot be recovered through the normal protocol paths. [10](#0-9)  This can therefore cause user funds to remain locked indefinitely and can leave protocol debt unrecoverable. [11](#0-10) 

### Likelihood Explanation
A single unprivileged account can establish the prerequisite position through `supply` followed by `borrow`; the pool-side borrow leg only requires a positive draw, sufficient reserves, liquidation-buffer room, a nonzero scaled mint, and the configured utilization cap. [12](#0-11)  The attack requires whale-scale liquidity and a market whose caps and risk configuration permit sustained high utilization, making it materially conditional rather than universally exploitable. [13](#0-12)  Once that state exists, any caller can trigger the terminal condition through permissionless `update_indexes`, after which normal remediation paths share the same failing accrual. [14](#0-13) [15](#0-14) 

### Recommendation
Bound scaled debt and scaled supply at market creation and borrow time so the maximum possible product `scaled * MAX_*_INDEX_RAY` remains representable for the asset's decimal domain. [4](#0-3)  Accrual should additionally saturate or cap the index before materializing old/new debt values, with an explicit capped-interest accounting path, rather than allowing a fixed-point multiplication to panic. [16](#0-15)  Add a production invariant and regression test asserting that every market operation remains executable when `borrow_index` approaches `MAX_BORROW_INDEX_RAY`. [9](#0-8) 

### Proof of Concept
1. Create a large 18-decimal market, supply `1_000_000_000 * 10^18` base units, provide sufficient separate collateral, and borrow 98% of that market through `Controller::borrow`; this is the state constructed by the existing regression test. [13](#0-12) 
2. Advance ledger time until another permissionless `Controller::update_indexes(caller, vec![hub_asset])` call reaches the overflowing indexed-debt product. [14](#0-13) [17](#0-16) 
3. Observe `MathOverflow` while the stored `borrow_index` is still below `MAX_BORROW_INDEX_RAY`, proving that the configured index cap did not prevent the product overflow. [18](#0-17) 
4. Attempt `withdraw` and `repay`; both revert with `MathOverflow` because they must first accrue the same market. [11](#0-10)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
