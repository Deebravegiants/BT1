### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` binds the tenant identity of an inbound webhook to the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` validates is computed only over the raw request body. This breaks the equality that should hold: `shop_used_by_handler == shop_authenticated_by_hmac`. Any recipient of a legitimately signed webhook (any app-installing merchant) can replay the same body/HMAC pair while substituting a different shop-domain header, and the library will report that payload to the host application's handler as belonging to the attacker-chosen shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#shop` returns the unauthenticated header value: [6](#0-5) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string`, i.e. the body, never the `shop` header: [5](#0-4) 

`Registry.process` accepts the request once this body-only HMAC passes, then forwards `request.shop` verbatim as the tenant identity in `WebhookMetadata` to the app-supplied `WebhookHandler#handle`: [3](#0-2) [4](#0-3) 

Because the HMAC key (`Context.api_secret_key`) is the single shared secret for the whole app (identical across every shop that installs it), any shop that has the app installed will, over the normal course of business, legitimately receive body/HMAC pairs signed with that same key. Nothing in the signable string binds those bytes to the specific shop they were addressed to. An attacker who is an ordinary, unprivileged merchant using the app can capture one such valid `(raw_body, hmac)` pair from their own webhook traffic and resend it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop. `Registry.process` will still validate the HMAC (it never inspected the header) and will invoke the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, i.e., cross-tenant impersonation, entirely through this gem's own verification logic, with no access to `api_secret_key` or the app's OAuth credentials.

### Impact Explanation
This is a Critical-tier cross-tenant access: the library exposes an unauthenticated field as if it were authenticated, letting one tenant's traffic be attributed to another tenant inside the host application's webhook handling. Any host logic that trusts `WebhookMetadata#shop` for lookups, writes, or authorization decisions (which is the documented/intended usage of this field) can be made to act on the wrong shop's data.

### Likelihood Explanation
High. It requires no leaked secret, no privileged account, and no TLS interception — only that the attacker be a normal app installer (an "unprivileged internet user" in the sense that they never need the app's credentials), capable of receiving their own legitimate webhook deliveries and replaying the body with a modified header to the app's already-public webhook URL.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker.myshopify.com`) and receives a legitimately signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (H = HMAC-SHA256(`api_secret_key`, B)), header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only from `to_signable_string` (`B`) and matches `H` — validation succeeds. [7](#0-6) 
5. `handler.handle` is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed_body, ...)`, so the host application processes attacker-controlled data as though it originated from `victim.myshopify.com`.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the signed material, or otherwise cryptographically bind the shop identity to the signature — e.g., require the host app to validate that the delivered `shop` matches an expected/registered shop for the corresponding webhook subscription, or have `HmacValidator`/`Request#to_signable_string` incorporate the shop-domain header so a mismatch between signed shop and header shop is rejected before the handler is invoked.
