### Title
Webhook tenant identity (`shop-domain` header) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) used to route and process a webhook from an HTTP header, while the HMAC signature that authenticates the webhook only covers the raw request body. This breaks the binding `shop-that-was-HMAC-authenticated == shop-that-the-handler-acts-on`, letting a request with a validly-signed body be attributed to an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is completely disjoint from what gets signed: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop` (an unauthenticated header) as the tenant identifier passed to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is the field host apps use to scope all subsequent per-tenant logic (looking up the merchant, updating tenant records, etc.): [4](#0-3) 

The `VerifiableQuery` interface only requires `hmac` and `to_signable_string`, so the library's own contract has no place for `shop` to be authenticated as part of the signature for webhooks (contrast this with `Auth::Oauth::AuthQuery`, where `shop` **is** included in `to_signable_string` and thus is HMAC-bound): [5](#0-4) [6](#0-5) 

**The broken identity binding, stated as an equality that should hold but doesn't:**
`shop` used by `HmacValidator.validate(request)` to authenticate the request `==` `shop` used by `Registry.process` / `WebhookHandler#handle` to attribute and act on the event.

Because the HMAC only signs `@raw_body`, any actor who can produce (or capture) one validly-HMAC'd webhook body/signature pair for their **own** shop can resend that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for a victim's `myshopify.com` domain. `HmacValidator.validate` will still pass (it never looks at the header), and the app's handler will process/attribute the payload as belonging to the victim tenant.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged party with a legitimate installation of the app on their own shop can forge webhook events that the app attributes to a different merchant's shop, without needing the app's `client_secret` or any privileged credential — they only need a body/HMAC pair they legitimately received for their own tenant. Depending on what the host app's webhook handler does with `WebhookMetadata#shop` (e.g., writing order/customer data keyed by shop, triggering per-tenant side effects, or looking up and mutating another merchant's stored session/access token), this can lead to cross-tenant data corruption or unauthorized actions performed against a victim shop's record — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The prerequisite — obtaining one legitimate `(raw_body, hmac)` pair — is trivial for any developer who installs the app on a shop they control (a normal, unprivileged action), since Shopify sends real webhooks to every installed shop. Replaying that captured request while swapping only the `shop-domain` header requires no cryptographic secret and no code changes to bypass validation, because the signature check in `HmacValidator`/`Registry.process` never consults the header at all. The main variable affecting exploitability is how consequential the host app's webhook handler logic is when keyed by an attacker-chosen `shop` value — this gem provides the primitive (`WebhookMetadata#shop` sourced from an HMAC-unbound header) but the concrete exploit depth depends on the integrating app.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signed material for webhooks, or otherwise cryptographically bind the header-derived `shop` to the signature (e.g., verify against a per-shop registered domain looked up independently, or require the shop domain to be embedded in the signed payload as Shopify does for OAuth's `AuthQuery`). At minimum, document prominently that `WebhookMetadata#shop` is NOT authenticated by the HMAC check and must not be trusted as a tenant identifier without independent verification (e.g., cross-checking against the session/shop the app already has on file for the topic in question).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets Shopify deliver one real webhook (e.g. `orders/create`) with a valid `shopify-hmac-sha256` header computed over the raw body using the app's `client_secret`.
2. Attacker captures the raw request: `raw_body`, `shopify-hmac-sha256: <valid-hmac>`, `shopify-topic: orders/create`.
3. Attacker replays this exact request to the app's public webhook endpoint, but changes only the `shopify-shop-domain` header to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= raw_body`, unchanged) and succeeds: [7](#0-6) 
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and processes/attributes the (attacker-supplied) body's data as belonging to the victim shop, despite the HMAC never having authenticated that shop value.
