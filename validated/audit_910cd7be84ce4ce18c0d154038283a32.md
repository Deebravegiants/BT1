### Title
Webhook `shop` (and `topic`/`api-version`) identity fields are trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read from unauthenticated HTTP headers and passed straight through to the application's webhook handler as the tenant identifier. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` to the handler without any check that this shop is the one Shopify actually signed the payload for.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then dispatches to the handler using `request.shop` as the tenant key, with no cross-check that this shop matches anything cryptographically tied to the signed payload: [3](#0-2) 

This is exactly the "field acted on but not covered by the HMAC" pattern: the equality that should hold is `shop-domain header == shop the HMAC was computed for`, but nothing in this gem enforces that equality — the HMAC only proves "this body was produced with the app's secret", not "this body/header combination came from shop X". An attacker who owns a legitimate installed instance of the app on their own shop receives genuinely Shopify-signed webhook deliveries (valid HMAC over the body) for their own shop. Because the `x-shopify-shop-domain` header is not part of the signed material, the attacker can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim `x-shopify-shop-domain` value. `ShopifyAPI::Webhooks::Registry.process` will accept it (HMAC check passes because only the body is checked) and invoke the app's handler with `data.shop` set to the victim shop and attacker-controlled `data.body`, which most host applications use as the tenant lookup key (e.g., to update per-shop records) — see the gem's own documented handler pattern using `data.shop` as the tenant key: [4](#0-3) 

### Impact Explanation
This breaks the tenant/shop identity binding that webhook processing is supposed to guarantee ("this event genuinely originates from shop X"). Any application that trusts `data.shop` from the handler (as the library's own documentation instructs) for tenant-scoped writes/lookups can be tricked into applying an attacker-controlled, but HMAC-"valid", payload under a victim shop's identity — a cross-tenant data-integrity/access issue. This satisfies the High-severity class of "scope or expiry check bypass" style identity-binding failures, since the shop's binding check is effectively absent from the gem's verification path.

### Likelihood Explanation
Any developer/merchant who can install the app on their own store (a completely unprivileged action for any Shopify user, no special credentials of the app required) can capture legitimate signed webhook deliveries for their own shop and replay them with a modified `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or other privileged material is required — only knowledge of the HMAC of a webhook they legitimately received.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material verified by `ShopifyAPI::Utils::HmacValidator`, or otherwise require callers to independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting it as the tenant key. At minimum, document prominently that `Registry.process`'s HMAC check does not authenticate the `shop`/`topic`/`webhook_id` headers, since the current doc/API implies "this will verify the request did indeed come from Shopify" without that caveat.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed with the app's secret.
2. Send a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid because it only signs `B`), but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com`; `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate` which succeeds (body/HMAC pair unchanged), then invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: parsed_body ...)`, causing the host application to process attacker-supplied data under the victim's tenant identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
