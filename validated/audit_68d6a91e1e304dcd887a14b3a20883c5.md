## Title
Webhook shop identity spoofing via unauthenticated `X-Shopify-Shop-Domain` header not covered by HMAC — cross-tenant webhook forgery (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` treats the `shop` value as an authenticated attribute of an inbound webhook, but the HMAC signature that the library verifies covers only the raw request body — never the `shop-domain` header (or any other header). Any party who can obtain one genuine, validly-signed webhook body/HMAC pair (trivially available to any developer/attacker who installs the app on their own store, since Shopify sends them real signed webhooks) can replay that exact body+HMAC to the app's webhook endpoint while substituting a different shop domain in the header, and the library will report the webhook as authentic for the victim shop.

### Finding Description
The identity binding that should hold is:

`shop_attributed_to_this_webhook == shop_that_the_HMAC_cryptographically_proves`

In `lib/shopify_api/webhooks/request.rb`, the `shop` accessor simply reads the `shopify-shop-domain` / `x-shopify-shop-domain` header verbatim: [1](#0-0) 

The HMAC that `HmacValidator.validate` checks is only computed over `to_signable_string`, which for `Request` is defined as the raw body — nothing else: [2](#0-1) 

`HmacValidator.validate_signature` confirms this: it signs/compares `verifiable_query.to_signable_string` against the `hmac` field, and for `Request` that string is `@raw_body` only: [3](#0-2) 

`Registry.process` gates on this HMAC check and then forwards the *unauthenticated* `request.shop` straight to the app's handler as the tenant identity for the event: [4](#0-3) 

So the equality that should hold (`shop header == shop bound by HMAC`) never actually holds — the HMAC binds only the body bytes, and the shop header is parsed and trusted independently of that proof. Because Shopify's real webhook HMAC is computed the same way (body-only, via HMAC-SHA256 with the app's client secret) for every shop that installs the app, a person who installs the app on their own store receives a completely genuine `(raw_body, hmac)` pair from Shopify. They can capture that pair and re-POST it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header (e.g., a victim's shop). `HmacValidator.validate` will succeed (the body/HMAC pair is genuinely valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the whole webhook system is meant to enforce: any application logic that uses `WebhookMetadata#shop` (e.g., to look up per-shop settings/session, to make Admin API calls attributed to that shop, or to trigger shop-scoped data mutation/deletion — including the mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics) can be triggered for an arbitrary victim shop by any user who can install the app once on a shop they control. This is cross-tenant access/data corruption without needing the victim's access token, the app's `client_secret`, or any privileged access — matching the High/Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: the only precondition is installing the app on a self-controlled development/trial store (a routine, unprivileged action for any Shopify Partner/developer), capturing one legitimate webhook delivery, and replaying it with a modified header to the target app's public webhook endpoint. No secret material or elevated privileges from the victim are required.

### Recommendation
Bind the shop identity cryptographically into the verified signable content instead of trusting the header value independently — e.g., include the `shop-domain` (and `topic`/`webhook-id`) in the string that is HMAC-verified, or require the consuming application to cross-check `request.shop` against a shop it already has an active, previously-established session/webhook registration for before acting on the payload. At minimum, document prominently that `Webhooks::Request#shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier by itself.

### Proof of Concept
1. Install the target app on an attacker-controlled store `attacker.myshopify.com`; trigger any subscribed webhook topic so Shopify delivers a real webhook: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with the app's `client_secret`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the exact same request to the app's webhook endpoint, but change only the `X-Shopify-Shop-Domain` header to `victim.myshopify.com` (leave `B` and `H` untouched).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed; `HmacValidator.validate` succeeds because it only checks `B` against `H`: [5](#0-4) 
4. The registered handler receives `WebhookMetadata` with `shop == "victim.myshopify.com"`, and the app processes/acts on it as if Shopify itself confirmed this event originated from the victim's store.
