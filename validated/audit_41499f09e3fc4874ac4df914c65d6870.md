### Title
Webhook shop-domain header is unauthenticated / not covered by HMAC, enabling cross-tenant forgery of `app/uninstalled` (and any topic) via header substitution - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`Registry.process` validates the webhook HMAC over the raw body only, then trusts the `shop-domain` header verbatim when constructing `WebhookMetadata` passed to the handler. Because the signature never covers the shop-domain header, an attacker who legitimately triggers and captures their own signed `app/uninstalled` webhook can resend the exact same signed body to the shared endpoint with the `shop-domain` header rewritten to a victim shop, causing the host app to act as if the victim uninstalled the app.

### Finding Description
The broken binding: `shop for which @raw_body was actually generated/signed by Shopify` == `request.shop` (the value the handler receives and acts upon). This does not hold.

- `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13`) calls `validate_signature`, which computes the HMAC over `verifiable_query.to_signable_string`.
- `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:36`) returns only `@raw_body` - it does not include any headers.
- `Webhooks::Request#shop` (`lib/shopify_api/webhooks/request.rb:21`) reads the `shop-domain` header directly, which is completely outside the HMAC-signed surface.
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) validates the HMAC (body-only) and then builds `WebhookMetadata.new(shop: request.shop, ...)` from the unsigned header and hands it to `handler.handle`.

Exploit flow: the attacker installs the app on their own shop (a normal, permitted action) and triggers `app/uninstalled` by uninstalling it, causing Shopify to deliver a validly signed webhook to the attacker's own registered endpoint - the attacker fully controls this endpoint and can capture the raw bytes (`@raw_body`, `x-shopify-hmac-sha256`, etc.). The attacker then re-POSTs the identical body and HMAC header to the target endpoint, but with `x-shopify-shop-domain` rewritten to `victim.myshopify.com`. Since `to_signable_string` is body-only, `HmacValidator.validate` still succeeds (the body and secret are unchanged), and `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", ...))`. If the host app's handler deletes stored sessions/tokens keyed by `data.shop` (the documented/expected pattern for `app/uninstalled`), it purges the victim's still-valid session even though the victim never uninstalled anything.

No other guard intervenes: `ShopValidator.sanitize!` is not invoked in this path, there is no cross-check between the shop-domain header and any shop identifier inside the JSON body, and Sorbet typing only enforces that `shop` is a `String`, not that it matches the signer.

### Impact Explanation
This is a cross-tenant forgery: an unprivileged attacker (using only their own shop) can force a host app to treat an arbitrary victim shop as though it sent an `app/uninstalled` (or any other topic) webhook. For handlers that key session/token deletion off `data.shop`, this causes forced logout / credential purge of a legitimate, currently-installed victim tenant, without ever compromising `api_secret_key` or the victim's credentials. The attack is repeatable against any victim shop domain (a value the attacker can enumerate or guess, e.g. `victim.myshopify.com`) at will, since the attacker retains the captured signed body/HMAC pair and can replay it indefinitely.

### Likelihood Explanation
Preconditions are minimal and fully within attacker capability: create a development/trial shop, install the target app, uninstall it to get one validly-signed `app/uninstalled` webhook delivered to an endpoint the attacker controls, capture the raw body + `x-shopify-hmac-sha256` header, then replay to the shared production webhook endpoint with a forged `shop-domain` header. It requires the host app to actually implement the documented mandatory-webhook behavior (deleting/invalidating stored session state by shop on `app/uninstalled`), which is the standard, expected implementation per Shopify's own compliance requirements for this gem's mandatory topics.

### Recommendation
Do not trust `request.shop` (header) as authenticated tenant identity derived purely from HMAC validation. At minimum:
- Cross-check the shop-domain header against a shop identifier embedded in the verified JSON payload body (most Shopify webhook payloads include the shop's id/domain in the body) before constructing `WebhookMetadata`, rejecting mismatches.
- Alternatively/additionally, validate that `request.shop` corresponds to a shop with an active session/registration known to the app before dispatching, rather than blindly trusting the header.
- Document/enforce that HMAC validation only proves body integrity/origin, not header authenticity, and require callers of `Registry.process` to independently authenticate the shop.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (proof-of-concept addition)
def test_process_trusts_forged_shop_domain_header_when_hmac_only_covers_body
  fake_store = {}
  handler = Class.new do
    define_method(:handle) do |data:|
      fake_store.delete(data.shop) # mimic host app deleting session on app/uninstalled
    end
  end.new

  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "app/uninstalled", delivery_method: :http, path: "webhooks", handler: handler,
  )

  fake_store["victim.myshopify.com"] = "victim_access_token"

  # Attacker captures a validly-signed webhook from THEIR OWN shop
  attacker_body = '{"id":1,"domain":"attacker.myshopify.com"}'
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, attacker_body)

  forged_headers = {
    "x-shopify-topic" => "app/uninstalled",
    "x-shopify-hmac-sha256" => Base64.encode64(hmac),
    "x-shopify-shop-domain" => "victim.myshopify.com", # forged, never signed
    "x-shopify-webhook-id" => "forged-id",
    "x-shopify-api-version" => "2024-01",
  }

  forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: attacker_body, headers: forged_headers)

  # HMAC validation succeeds because it only covers the body, not the shop-domain header
  ShopifyAPI::Webhooks::Registry.process(forged_request)

  # Victim's session is deleted despite never uninstalling
  assert_nil(fake_store["victim.myshopify.com"])
end
