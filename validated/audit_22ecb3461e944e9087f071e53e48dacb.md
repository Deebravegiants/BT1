### Title
Undetected malicious calls embedded in the swap route payload let router-invoked contracts steal from the caller's wallet via the signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Like the picklescan gap where a scanner's blocklist misses a dangerous callable (`idlelib.calltip.Calltip.fetch_tip`) smuggled inside an otherwise valid payload, the controller passes the caller-supplied `StrategySwap` XDR to the configured router verbatim, without decoding it or constraining which contract addresses the embedded route may invoke. The router then calls whatever pool/venue addresses the payload names, and the threat model concedes it "keeps no allowlist of them". An attacker-deployed hop contract placed inside a route executes with the caller's authorization tree on the stack and can call `token.transfer(caller, attacker, …)` on any token the victim holds — far beyond the routed `amount_in` that the controller's measurement bound covers. The repo's own test fixture demonstrates the theft succeeds when the victim signs the recorded tree.

### Finding Description
`swap_tokens` authorizes exactly one `token_in.transfer(controller, router, amount_in)` sub-invocation and then calls `router.execute_strategy(&controller, &amount_in, swap)` inside the flash guard, measuring only the controller's `token_in`/`token_out` deltas afterward. Nowhere in `swap.rs`, `swap_collateral.rs`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` is the `swap` byte blob decoded to check which venues, pools, or token contracts the route will touch; the controller rejects only `RouterOverspend`, input-balance growth, and `NoSwapOutput`. The invariants document confirms the authorization scope is deliberately narrow for the controller's own funds but does not bound third-party code executed below it.

The threat model states the exposure explicitly: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization. A token transfer that such code makes from the caller … executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it."

The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` implements the exact gadget: `UnlistedPoolRouter::execute_strategy` performs the fair swap but additionally `env.invoke_contract(&route.hop_pool, "swap", …)`, and `RogueHopPool::swap` executes `token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount)` — a token the protocol never listed, funded in Alice's wallet (77 770 units) purely to prove the drain works. This is the direct analog of `fetch_tip`: a callable the safety checkers never inspect, smuggled inside a payload that passes every measurement gate.

### Impact Explanation
Theft of user funds. A victim who signs a `swap_collateral` / `swap_debt` / `multiply` / `repay_debt_with_collateral` / direct `execute_strategy` transaction containing a poisoned route loses arbitrary amounts of arbitrary tokens held in their wallet — the loss is unbounded by `amount_in`, the payload `min_out`, or the controller's solvency gates, because the transfer is authorized as a child of the caller's own auth entry. All six account strategies and the standalone router path are reachable by a single unprivileged attacker crafting the route; the victim's signed auth tree is what the gadget needs, mirroring the CVE's `UI:P` interaction requirement.

### Likelihood Explanation
The attack requires a victim to sign a transaction whose authorization tree contains the extra transfer (matching the report's `UI:P`). That is realistic: routes are opaque XDR built by an off-chain quoting service, so a malicious or compromised quote can embed a rogue hop without any visible change to the promised `amountIn`/`amountOutMin`. The controller performs zero decoding or venue admission of the payload, so nothing on-chain distinguishes a poisoned route from a benign one — exactly the "undetected gadget" shape of the scanner bypass. Mitigation currently rests entirely on each client implementing the documented `verifyRouteBytes`/auth-tree inspection, which the contract does not enforce.

### Recommendation
Enforce route integrity on-chain rather than relying on client-side inspection: have the controller (or the router) decode the `StrategySwap` program and validate every hop's pool/token address against a governance-managed venue allowlist before execution, analogous to the Blend-pool approval check already used for `migrate_from_blend` (INV-STRAT-03). Alternatively, constrain the router to a fixed set of approved AMM adapters and reject payloads naming any other contract address.

### Proof of Concept
```rust
// tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs

#[contractimpl]
impl UnlistedPoolRouter {
    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        sender.require_auth();
        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();
        token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);
        // Arbitrary attacker contract invoked from the payload — no allowlist:
        let _: Val = env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), vec![&env]);
        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }
}

#[contractimpl]
impl RogueHopPool {
    pub fn swap(env: Env) {
        // Drains an unrelated wallet token via the caller's signed auth tree:
        token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
    }
}
```

Attack flow: attacker registers `RogueHopPool` with `(victim = Alice, wallet_token, to = attacker, amount = WALLET_BALANCE)`, builds a route whose `hop_pool` is the rogue contract and whose `min_out`/`token_in`/`token_out` give a fair-looking swap, and has Alice sign a `swap_collateral(alice, account_id, USDC, 50_000_000_000, ETH, route)`. The controller authorizes only the 5 000 USDC input transfer and measures a positive ETH output, while `RogueHopPool::swap` moves all 77 770 units of Alice's unlisted wallet token to the attacker under the same signed tree — a theft the controller's `RouterOverspend`/`NoSwapOutput` checks cannot see.
