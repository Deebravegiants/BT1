### Title
Unbounded recursion in `MemTrieUpdate::post_order_traverse_updated_nodes` can be driven by attacker-controlled writes to cause stack-overflow-induced chunk application failure - (File: core/store/src/trie/mem/memtrie_update.rs)

### Summary
`post_order_traverse_updated_nodes` recurses once per `Branch`/`Extension` node on the path from the trie root to each newly-created leaf, with no explicit depth limit or iterative fallback. [1](#0-0) 
The recursion depth is only indirectly bounded by gas costs on `storage_write`, not by any hard-coded trie-depth guard, so an attacker who submits enough distinct storage writes with carefully diverging key prefixes in a single chunk can force the creation of a long chain of branch/extension nodes, and this same recursive function is invoked from the consensus-critical `to_trie_changes` path used during chunk application. [2](#0-1) 

### Finding Description
`to_trie_changes` (called during `to_memtrie_changes_internal`) performs a post-order DFS over `updated_nodes` starting at the root, recursively descending into every `Branch` child and every `Extension` child before it can emit a node into `ordered_nodes`. [3](#0-2) 
Because Patricia tries compress runs of single-child nodes into a single `Extension` node, the recursion depth is governed by the number of *branching points* on the path to the deepest new key, not the raw key length. An attacker can create a large number of branching points by writing many distinct keys via `storage_write` host calls, sharing long common prefixes that diverge from each other only near the tail, e.g. `prefix + i` for `i` in a large range, and repeating this across many receipts/transactions packed into one chunk.

The only protocol control limiting depth is the per-write gas cost (`wasm_storage_write_base` ≈ 6.4×10^10 gas plus per-byte fees) and per-chunk gas limits, not an explicit trie-depth bound. [4](#0-3) 
There is no equivalent to `max_stack_height` (used for wasm execution) enforced for native Rust recursion in this trie-construction code path, so the number of branch points reachable is set only by how much gas a chunk can absorb across all its receipts, which can be in the tens of thousands of individual writes given typical chunk gas budgets. This produces recursion depths that are large and whose actual overflow behavior depends on the compiled stack-frame size and the runtime thread's stack size — both of which can legitimately differ between validator builds/OS defaults, meaning some nodes could stack-overflow while others complete successfully.

### Impact Explanation
If different validators/chunk producers use different native stack sizes (default OS thread stack, or different build optimization levels affecting frame size), a chunk containing enough divergent-prefix writes could cause a subset of nodes to crash with a native stack overflow inside `to_trie_changes` while others successfully apply the chunk. This is a determinism/liveness class issue (node panic and potential chain stall) rather than a fund-loss or metering-bypass issue, matching NEAR's "node panic / chain split from non-deterministic native code behavior" bounty category.

### Likelihood Explanation
Exploitation requires an unprivileged attacker to submit a large volume of ordinary storage-writing transactions/contract calls in a single chunk with keys engineered to create deep chains of branch nodes rather than a bushy tree. This is feasible without any special privileges (regular account, ordinary `FunctionCall` actions calling `storage_write`), but the depth achievable in a single chunk is gas-limited, and the exact stack-frame size of the compiled recursive function determines whether a given depth actually triggers an overflow — this is speculative without a measured PoC on the actual attack the compiler-emitted frame size and target stack size. This makes the finding architecturally real but its concrete exploitability threshold uncertain without direct measurement.

### Recommendation
Convert `post_order_traverse_updated_nodes` (and any other unbounded recursive traversal over `updated_nodes`, e.g. `compute_hashes_and_serialized_nodes` uses an explicit `ordered_nodes` list already, but the traversal itself is recursive) to an explicit iterative traversal using a heap-allocated stack, removing dependence on native call-stack depth entirely. This eliminates any environment-dependent (stack size/build) divergence in whether chunk application succeeds.

### Proof of Concept
1. Using `TestTries`/`insert_changes_to_memtrie` helpers already present in the memtrie test module, construct a change set of many keys sharing prefixes but diverging progressively near the tail (e.g. `prefix + i.to_be_bytes()` for `i` in `0..N` with large `N`), sized to emulate what a chunk's aggregate gas budget could pay for.
2. Run `MemTrieUpdate::to_trie_changes()` under a thread spawned with a deliberately constrained stack size (e.g. `std::thread::Builder::new().stack_size(...)`) to simulate a validator with a smaller default stack.
3. Assert the call completes without a stack overflow/panic for the maximum key/branch-point count derivable from the current gas parameters (`max_gas_burnt`, `wasm_storage_write_base`, per-chunk gas limit), and separately measure native stack usage growth per recursion level to compute the theoretical overflow threshold.
4. If overflow is reproduced within gas-derivable limits under a reduced (but still realistic) stack size, this confirms the liveness/determinism impact described.

    fn post_order_traverse_updated_nodes(
        node_id: UpdatedNodeId,
        updated_nodes: &Vec<Option<UpdatedMemTrieNodeWithSize>>,
        ordered_nodes: &mut Vec<UpdatedNodeId>,
    ) {
        let node = updated_nodes[node_id].as_ref().unwrap();
        match &node.node {
            UpdatedMemTrieNode::Empty => {
                assert_eq!(node_id, 0); // only root can be empty
                return;
            }
            UpdatedMemTrieNode::Branch { children, .. } => {
                for child in children.iter() {
                    if let Some(OldOrUpdatedNodeId::Updated(child_node_id)) = child {
                        Self::post_order_traverse_updated_nodes(
                            *child_node_id,
                            updated_nodes,
                            ordered_nodes,
                        );
                    }
                }
            }
            UpdatedMemTrieNode::Extension { child, .. } => {
                if let OldOrUpdatedNodeId::Updated(child_node_id) = child {
                    Self::post_order_traverse_updated_nodes(
                        *child_node_id,
                        updated_nodes,
                        ordered_nodes,
                    );
                }
            }
            _ => {}
        }
        ordered_nodes.push(node_id);
    }

    fn to_memtrie_changes_internal(self) -> (MemTrieChanges, Vec<(CryptoHash, Vec<u8>)>) {
        MEMTRIE_NUM_NODES_CREATED_FROM_UPDATES
            .with_label_values(&[&self.shard_uid])
            .inc_by(self.updated_nodes.len() as u64);
        let mut ordered_nodes = Vec::new();
        Self::post_order_traverse_updated_nodes(0, &self.updated_nodes, &mut ordered_nodes);

        let hashes_and_serialized_nodes =
            self.compute_hashes_and_serialized_nodes(&ordered_nodes, &self.updated_nodes);

        let node_ids_with_hashes = hashes_and_serialized_nodes
            .iter()
            .map(|(node_id, hash, _)| (*node_id, *hash))
            .collect();
        (
            MemTrieChanges { node_ids_with_hashes, updated_nodes: self.updated_nodes },
            hashes_and_serialized_nodes
                .into_iter()
                .map(|(_, hash, serialized)| (hash, serialized))
                .collect(),
        )
    }

    /// Converts the updates to memtrie changes only.
    pub fn to_memtrie_changes_only(self) -> MemTrieChanges {
        let (memtrie_changes, _) = self.to_memtrie_changes_internal();
        memtrie_changes
    }

    /// Converts the updates to trie changes as well as memtrie changes.
    pub(crate) fn to_trie_changes(mut self) -> TrieChanges {
        let old_root =
            self.root.map(|root| root.as_ptr(self.memory).view().node_hash()).unwrap_or_default();
        let mut refcount_changes = self
            .nodes_tracker
            .take()
            .expect("Cannot to_trie_changes for memtrie changes only")
            .finalize();
        let (memtrie_changes, hashes_and_serialized) = self.to_memtrie_changes_internal();

        // We've accounted for the dereferenced nodes, as well as value addition/subtractions.
        // The only thing left is to increment refcount for all new nodes.
        for (node_hash, node_serialized) in hashes_and_serialized {
            refcount_changes.add(node_hash, node_serialized, 1);
        }
        let (insertions, deletions) = refcount_changes.into_changes();

        TrieChanges {
            old_root,
            new_root: memtrie_changes
                .node_ids_with_hashes
                .last()
                .map(|(_, hash)| *hash)
                .unwrap_or_default(),
            insertions,
            deletions,
            memtrie_changes: Some(memtrie_changes),
            children_memtrie_changes: Default::default(),
        }
    }
