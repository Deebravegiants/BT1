## Analysis Result

The vulnerability class described in the report (trusting a token transfer call's success without verifying the actual balance delta, which breaks accounting for fee-on-transfer / non-standard tokens) has a direct analog in this repository's `ERC20Transactor`, used as an XCM `TransactAsset` implementation on Asset Hub Westend to bridge ERC20 tokens deployed via `pallet-revive` into the XCM asset model.

### Title
ERC20Transactor credits/moves a fixed requested amount instead of the actual ERC20 balance delta, breaking XCM asset accounting for non-standard ERC20 tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` move ERC20 tokens by calling the Solidity `transfer()` function via `pallet_revive::Pallet::bare_call` and only check the boolean return value / revert status of the call. Neither function verifies that the `TransfersCheckingAccount`'s or beneficiary's actual token balance changed by the requested `amount`. This mirrors exactly the reported `_pullTokenInputAndPayProtocolFee()` flaw: trusting a `transfer`/`transferFrom`-style call's outcome instead of checking pre/post balances.

### Finding Description
`withdraw_asset_with_surplus` builds an `IERC20::transferCall` moving `amount` from the user to the checking account, and if the call doesn't revert and decodes to `true`, it unconditionally credits `AssetsInHolding` with the full requested `amount`: [1](#0-0) 

Symmetrically, `deposit_asset_with_surplus` moves `amount` out of the checking account to a beneficiary using the same pattern, without checking whether the beneficiary's balance actually increased by `amount`: [2](#0-1) 

Crucially, the asset id that selects which ERC20 contract to call is not restricted to any allow-listed/registered set of tokens. `ERC20Matcher` matches **any** location of the form `(0, [AccountKey20 { key, .. }])`: [3](#0-2) 

and this transactor is wired directly into the runtime's `AssetTransactors` tuple used by the XCM executor: [4](#0-3) 

This means any unprivileged account can reference an arbitrary, attacker-deployed `pallet-revive` contract address as an "ERC20 asset" in an XCM program (e.g. via `pallet_xcm::execute`, which lets a signed origin execute an XCM program against its own local assets) without any registration step. If that contract implements a fee-on-transfer, rebasing, or otherwise non-standard `transfer()` (deducting a fee, minting extra, or simply returning `true` while moving a different amount than requested), the `AssetsInHolding` credit created by `withdraw_asset_with_surplus` will not reflect the token amount actually held by the `TransfersCheckingAccount`. The XCM holding register (accounting layer) and the real ERC20 ledger (state layer) diverge, exactly the accounting-vs-reality gap flagged in the source report.

### Impact Explanation
Because the same shared `TransfersCheckingAccount` custodies ERC20 balances for all users of the transactor, an accounting mismatch introduced by one withdrawal (crediting more/less XCM-holding value than what was actually deposited into the checking account) desynchronizes the pool of tokens the checking account actually holds from what the protocol believes it holds. Concretely:
- Subsequent `DepositAsset`/reserve-transfer instructions relying on the inflated accounted amount will attempt to move more tokens out of the checking account than it actually possesses, causing ERC20 `transfer()` reverts and XCM assets being trapped (`AssetsTrapped`), a availability/fund-lock impact for the affected user's own funds and for any protocol composition (e.g. cross-chain transfer paths) that assumes the withdrawn amount equals the deposited amount.
- More broadly, any downstream logic that treats the `AssetsInHolding` amount as ground truth (fee accounting, further XCM hops, reserve transfers to other chains) is silently working off of a value that does not correspond to the actual token movement, which is the same class of bug (fee-on-transfer/rebasing token breaks internal accounting) called out as Medium risk in the source report.

### Likelihood Explanation
The entry path is reachable by any unprivileged account: `ERC20Matcher`/`IsLocalAccountKey20` accepts any `AccountKey20` location without requiring the token to be registered as a `ForeignAsset` or otherwise vetted, and XCM execution of asset withdraw/deposit instructions against one's own account is a standard, permissionless XCM capability (`pallet_xcm::execute`). No privileged role or trusted party needs to be compromised — a user only needs to deploy (or reference) a non-standard ERC20 contract via `pallet-revive` and issue an XCM program against it.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, query the ERC20 contract's `balanceOf` for the relevant account (checking account / beneficiary) before and after the `transfer()` call, and use the observed balance delta — not the requested `amount` — when constructing the `AssetsInHolding` credit or when reporting success. Alternatively, restrict `ERC20Matcher` to an explicitly allow-listed set of vetted ERC20 contracts known to implement standard, non-fee-on-transfer semantics, similar to how `ForeignAssetsConvertedConcreteId` requires explicit registration.

### Proof of Concept
1. Deploy a `pallet-revive` contract implementing `IERC20` whose `transfer()` deducts a 5% fee on every transfer but still returns `true`.
2. Submit an XCM program via `pallet_xcm::execute` with `WithdrawAsset` for `Asset { id: Location(0, [AccountKey20{ key: <contract address> }]), fun: Fungible(100) }` from the signed origin's own account.
3. `ERC20Transactor::withdraw_asset_with_surplus` (`erc20_transactor.rs:150-216`) calls `transfer(checking_account, 100)`; the contract moves only 95 to the checking account but returns `true`. The function nonetheless returns `AssetsInHolding` credited with `Erc20Credit(100)`.
4. Chain a `DepositAsset` instruction in the same/following XCM program attempting to move the full "100" out of the checking account; `deposit_asset_with_surplus` (`erc20_transactor.rs:225-306`) issues `transfer(beneficiary, 100)` from the checking account, which only holds 95 real tokens and reverts, causing the XCM instruction to fail and the "100" units to be trapped (`AssetsTrapped`) — demonstrating the accounting/reality mismatch caused by the unmet balance check, analogous to the reported `_pullTokenInputAndPayProtocolFee()` flaw.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}
