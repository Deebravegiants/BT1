### Title
Withdraw path in the Tron IntentGatewayV2 releases escrowed tokens and fees via low-level `.call` before updating escrow state, enabling reentrant double-withdrawal - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Curves report's root cause is a Checks-Effects-Interactions (CEI) violation: using `call` (which forwards all remaining gas to the recipient) to pay out funds *before* the corresponding accounting state is updated, letting the untrusted recipient re-enter and claim value against stale state. The Tron variant of Hyperbridge's Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) contains the identical pattern in its `withdraw()` function, which releases escrowed order inputs and accumulated transaction fees to an attacker-influenced `beneficiary` address.

### Finding Description
`withdraw()` in the Tron `IntentGatewayV2` is the function that actually pays out escrowed intent funds on settlement (`RedeemEscrow`) or refund (`RefundEscrow`): [1](#0-0) 

For each escrowed token it checks `_orders[body.commitment][token] == 0`, then makes an external `.call` — either a native ETH transfer (`beneficiary.call{value: amount}("")`) or an ERC-20 `transfer` via low-level `.call` — and only *afterwards* decrements `_orders[body.commitment][token] -= amount`. The same pattern repeats for the transaction-fee payout immediately below: [2](#0-1) 

`fees` are read, transferred via `.call`, and only then deleted from `_orders[...][TRANSACTION_FEES]`. Since `beneficiary` is derived directly from `body.beneficiary` — the order's `output.beneficiary` (solver-fill case) or `order.user` (refund case), both attacker-choosable addresses — a malicious beneficiary contract that receives native ETH here executes arbitrary code in its `receive()`/fallback before the escrow bookkeeping (`_orders[...]`) or fee bookkeeping (`TRANSACTION_FEES`) is updated. This is structurally identical to the Curves `_transferFees` bug: pay first via `call`, update the ledger second.

`withdraw()` is `internal` and reachable only through `onAccept`, which is `restrict`ed to the configured host address: [3](#0-2) 

This means a genuine reentrancy exploit requires the host's message-delivery path (the Tron ISMP host / handler equivalent to `EvmHost`/`HandlerV2` on mainline EVM) to itself be reenterable during `onAccept`'s execution — i.e., the host must allow a second `handleRequests`/`dispatchIncoming` call to land on the same commitment while the first is still executing. I was not able to confirm from the indexed code whether the Tron host implementation carries the same `ReentrancyGuard` protection that `evm/src/core/EvmHost.sol` appears to use (two references found there), because the Tron host source was not available in the indexed context. Given the size limits on the codebase index, I could not verify the Tron host's `handlePostRequests`/dispatch entrypoint for a reentrancy guard equivalent to the mainline EVM host — a Devin session with full repository access would be needed to confirm this definitively.

### Impact Explanation
If the Tron host lacks (or has a gap in) reentrancy protection around request/response delivery, a malicious `beneficiary` (attacker-controlled fill destination or order owner) can re-enter during the native-ETH payout leg of `withdraw()` and drain escrowed input tokens and/or accumulated transaction fees beyond what is legitimately owed to them, before `_orders[commitment][token]` or `_orders[commitment][TRANSACTION_FEES]` is decremented — a direct theft of escrowed user/protocol funds, matching the "concrete theft of funds" acceptance bar. This mirrors exactly the Curves finding's mechanism (pay via `call`, update ledger after).

### Likelihood Explanation
Likelihood is contingent on the Tron host's dispatch/handler layer permitting reentrant delivery of a second request/response while the first `onAccept` call is on the stack. I could not confirm this from the available index. If the Tron host mirrors the mainline `EvmHost`'s apparent `ReentrancyGuard` usage, this path is not exploitable and the CEI violation is latent-only defense-in-depth issue rather than an active vulnerability. Given this open question, this should be treated as a candidate finding requiring verification of the Tron host's reentrancy posture before confirming exploitability.

### Recommendation
Regardless of whether the host currently blocks reentrancy, harden `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to follow Checks-Effects-Interactions: decrement `_orders[body.commitment][token]` (and delete `_orders[body.commitment][TRANSACTION_FEES]`) *before* performing the external `.call` transfers, matching the pattern already used in the newer `IntentsBase._withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol`), which decrements escrow before calling `_sendValue`/`safeTransfer`: [4](#0-3) 

Additionally, confirm (or add) a `nonReentrant`/reentrancy-guard on the Tron host's inbound message handler, or on `onAccept` itself, so the fix is defense-in-depth rather than relying solely on ordering.

### Proof of Concept
Conceptual PoC (mirrors the Curves gist structure), contingent on the host allowing reentrant `onAccept` delivery:
1. Attacker places/fills an intent order with `output.beneficiary` set to an attacker-controlled contract.
2. When settlement/refund triggers `onAccept` → `withdraw()`, the native-token branch calls `beneficiary.call{value: amount}("")` before `_orders[commitment][token]` is decremented.
3. The attacker's `receive()` re-enters the host's delivery entrypoint with a duplicate (or related) message targeting the same `commitment`/token, hitting `withdraw()` again while `_orders[commitment][token]` still reflects the pre-payout balance, and passes the `_orders[body.commitment][token] == 0` check a second time.
4. The token/fee ledger is drained beyond the legitimately escrowed amount before either invocation's state update completes.

This PoC could not be executed against the codebase in this session; it is derived analogically from the confirmed CEI-violation code pattern and requires validating the Tron host's reentrancy protections to fully confirm exploitability.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
