### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing tenant spoofing via header replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` (parsed from the `x-shopify-shop-domain` / `shopify-shop-domain` header) is never part of the signed bytes. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler. The binding "HMAC-authenticated bytes == shop identity acted upon" does not hold, letting an attacker who possesses one validly-signed webhook payload replay it while claiming a different tenant's shop domain.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are the two members required by `Utils::VerifiableQuery`: [1](#0-0) [2](#0-1) 

`to_signable_string` returns `@raw_body` exclusively — the `shop` field (read from the `shop-domain` header at line 21-23) is not included in the signable string at all: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to the received `hmac`: [4](#0-3) 

`Registry.process` uses this validation result to gate whether the request is trusted, then builds `WebhookMetadata` directly from `request.shop`, which is the unauthenticated header value: [5](#0-4) 

So the equality that should hold — `shop_bound_by_hmac == shop_delivered_to_handler` — does not: the HMAC only proves "this body byte-string was signed with the app's `api_secret_key` at some point", it proves nothing about which shop the signer intended. `shop` is a field "acted on but not covered by the HMAC", exactly the binding-break class in scope.

### Impact Explanation
Because the app-level `api_secret_key` is shared across all shops that installed the app (it is not per-tenant), any merchant/unprivileged user who can trigger a webhook delivery to themselves (e.g., an app installed on their own shop, or any endpoint where they can observe one legitimately-signed webhook body+HMAC pair) obtains a `(body, hmac)` pair that will still validate under `HmacValidator.validate` no matter what `shop-domain` header accompanies it. Replaying that exact body/HMAC pair with the `x-shopify-shop-domain` header rewritten to a victim shop causes `Registry.process` to pass HMAC validation and hand the host application a `WebhookMetadata` claiming `shop: <victim-shop>` with attacker-controlled `body`. Any host application that uses `data.shop` (as documented via `WebhookMetadata`) to scope per-tenant writes/side effects will act on the victim tenant using attacker-supplied data — a cross-tenant access/injection primitive that fits the "Critical: cross-tenant access" impact bucket in scope.

### Likelihood Explanation
Moderate-to-high for an attacker who has any access to a shop that runs the target app (installing an app themselves and observing its own webhook deliveries is fully unprivileged and requires no secrets). No `api_secret_key`, access token, or TLS interception is needed — only the ability to capture one legitimately delivered webhook (attacker's own shop) and resend it to the same public webhook endpoint with a different `shop-domain` header value.

### Recommendation
Include `shop` (and ideally `topic`) as part of the signed material, or otherwise bind the verified `shop` value to the body cryptographically before constructing `WebhookMetadata`. At minimum, `Registry.process` should not treat `request.shop` as trustworthy tenant identity unless it is itself covered by the HMAC computation in `to_signable_string`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, which is fully unprivileged/self-service.
2. Attacker triggers any event that produces a webhook delivery from Shopify to the app's webhook endpoint, capturing the raw POST body and the `x-shopify-hmac-sha256` header value (this HMAC is valid because `Utils::HmacValidator.validate` only signs `@raw_body`, per `lib/shopify_api/webhooks/request.rb:35-38`).
3. Attacker resends the exact same body + HMAC header to the same public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:12-22` succeeds (body/HMAC pair unchanged).
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's body>, ...)` and passes it to the host app's handler, which now believes attacker-controlled data originated from the victim's shop.

          received_signature = verifiable_query.hmac
