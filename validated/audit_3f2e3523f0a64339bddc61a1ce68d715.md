### Title
Unbounded-time zstd decompression of attacker-controlled bytes in `validate_unsigned` enables mempool CPU-exhaustion DoS - (File: modules/pallets/call-decompressor/src/lib.rs)

### Summary
`pallet-call-decompressor`'s `decompress` function feeds attacker-supplied bytes into `ruzstd::StreamingDecoder` and loops calling `decoder.read()` until the stream is exhausted or the claimed size is exceeded. This function is invoked directly from `ValidateUnsigned::validate_unsigned` [1](#0-0)  — a path that every node in the network runs on every gossiped unsigned extrinsic during mempool validation, before any fee, weight metering, or execution authorization applies.

### Finding Description

The existing size guard (`ensure!(encoded_call_size < T::MaxCallSize::get() * ONE_MB, ...)`) only bounds the *claimed output size*; it does nothing to bound the CPU time the `ruzstd` streaming decoder spends processing a crafted, malformed compressed byte stream before it emits output or errors out. This mirrors the pypdf `/FlateDecode` advisory's root cause exactly: a decompression routine that, given adversarial malformed compressed input, can be driven into a pathologically slow processing path (e.g., inefficient entropy/Huffman/FSE table handling on corrupt input) that is decoupled from the eventual output size and thus unbounded by the `MaxCallSize` output-size check.

Because `validate_unsigned` runs this decompression on **every** unsigned `decompress_call` transaction that reaches a node's transaction pool (`TransactionSource::External` included), an attacker does not need to pay fees, hold any privilege, or get a transaction included on-chain — they only need network connectivity to gossip transactions. The fixed weight `Weight::from_parts(500_000_000, 0)` assigned to `decompress_call()` further confirms the design assumes bounded, predictable decompression cost [3](#0-2) , an assumption that a malformed zstd stream (rather than a legitimate one) can violate, since decode work is not charged or capped by wall-clock/CPU time, only by claimed output size.

### Impact Explanation
A remote, unauthenticated peer can submit a small, cheaply-crafted "malformed zstd" payload (well under `MaxCallSize`) that causes `ruzstd::StreamingDecoder` to burn disproportionate CPU time per node during `validate_unsigned`. Because this runs pre-fee and pre-inclusion on every full node/collator that receives the gossiped transaction, a modest stream of such transactions can degrade transaction-pool validation throughput network-wide, delaying legitimate extrinsics (including relayed ISMP messages and fee-accumulation calls that this same pallet routes to) — a route-availability degradation (CWE-770), matching the "route unable to deliver messages" impact class for Hyperbridge.

### Likelihood Explanation
Likelihood is high for a determined attacker: the entry point is unsigned, feeless, and reachable via the standard transaction-gossip network path — no special permission or on-chain state is required, only crafting a malformed zstd frame that triggers atypically slow decode behavior in `ruzstd`, analogous to publicly known FlateDecode-class decompression DoS constructions.

### Recommendation
Bound the CPU/time cost of the decompression loop independent of the claimed output size, e.g., by capping the number of decoder iterations/input bytes consumed per unit of output, adding a strict deadline/step-count limit to the `loop` in `decompress`, or switching to a decompression bomb-resistant implementation with guaranteed linear/bounded time complexity on malformed input, and enforcing this same bound in `validate_unsigned` before it is ever reached by unauthenticated gossip.
