### Title
Cross-deployment replay of relayer reward-claim signatures due to missing source-chain identifier in the signed payload - (File: `modules/pallets/relayer/src/outbound_consensus.rs`, `modules/pallets/relayer/src/outbound_request.rs`)

### Summary
`OutboundConsensusDeliveryClaim` and `OutboundRequestDeliveryClaim` both authorize a reward payout with a relayer signature over a hash that omits any identifier of the Hyperbridge chain paying the reward. The signed payloads are: [1](#0-0) [2](#0-1) 

Both hash only `(set_id/commitment, dest_chain, payee)` — never the identity of the source Hyperbridge instance (genesis hash, para/chain id, etc.) that is doing the paying. This is structurally the same class of bug as the referenced report: a signed authorization that should be scoped to one chain but omits the chain identifier, so it can be replayed on another chain/deployment.

### Finding Description
Both claim-processing functions rely entirely on an on-chain per-chain idempotency map to prevent replay:
- `OutboundConsensusRotationsClaimed::<T>::contains_key(destination, set_id)` [3](#0-2) 
- `OutboundRequestsClaimed::<T>::contains_key(commitment)` [4](#0-3) 

These maps live in *this* runtime's storage only. The signature itself carries no binding to which Hyperbridge runtime/deployment is authorized to pay it — it is a plain `keccak256` over `(set_id, dest_chain, payee)` or `(commitment, dest_chain, payee)`: [5](#0-4) [6](#0-5) 

Both flows explicitly document that replay protection is *only* this local idempotency tag, not a nonce, and not a chain-scoping value: [7](#0-6) [8](#0-7) 

Whenever more than one Hyperbridge/pallet-ismp-relayer deployment exists that (a) shares the same reward-eligible EVM/substrate destination and (b) shares the same on-chain attribution slot state (e.g. the same `EvmHost._epochs[set_id]` address, or coincidentally the same commitment encoding), a single off-chain signature produced by the relayer for one deployment is also a valid signature for the other deployment, because the message the relayer signed never named which chain's treasury is supposed to pay it. Each deployment tracks its own idempotency flag, so the same signature clears the replay check independently on each chain and each one pays out its own configured `OutboundConsensusDeliveryReward` / `OutboundRequestDeliveryReward` from its own treasury for what is, from the relayer's perspective, a single act of signing.

This mirrors exactly the referenced Sherlock finding: `_checkOrder()`'s EIP-712 signature omitted `chainId`, so the same signature validated on any fork/chain sharing the same verifying contract layout. Here, the analogous "chain scope" (which Hyperbridge treasury/runtime is authorizing the payout) is missing from the hashed payload the relayer signs.

### Impact Explanation
A relayer (or anyone who captures a broadcast/pending `OutboundConsensusDeliveryClaim`/`OutboundRequestDeliveryClaim` extrinsic, since these are dispatched as `validate_unsigned` transactions and are visible before/at inclusion) can resubmit the identical `signature` field to a second Hyperbridge deployment configured with a nonzero reward for the same destination/module, draining that deployment's treasury for work that was never done against it. This is a treasury drain / unbacked reward payout — squarely "concrete theft ... of funds" from the relayer reward-accounting surface explicitly listed as in-scope.

### Likelihood Explanation
Requires that two (or more) Hyperbridge deployments configure rewards for overlapping destinations/modules and that the attribution proof used to authorize a claim (the destination `EvmHost._epochs[set_id]` address, or the request receipt relayer bytes) coincides across those deployments — a realistic scenario for testnet/mainnet twins, multiple parachain deployments of the same runtime, or forked deployments sharing consensus infrastructure, which the project explicitly builds for (Gargantua, Nexus, etc. runtimes appear in the repo). Exploitation needs no privileged access — only observing or being the relayer who legitimately earns the reward once, then replaying the same signature against every other deployment paying for the same destination/module.

### Recommendation
Include a source-chain identifier in the signed payload for both `outbound_consensus_delivery_message` and `outbound_request_delivery_message` — e.g. `IsmpHost::host_state_machine()` of the paying Hyperbridge instance (or its genesis hash / a configured domain constant) — analogous to including `chainId` in an EIP-712 domain separator, so a signature produced for one deployment's treasury cannot validate against another's.

### Proof of Concept
1. Deploy two Hyperbridge instances/runtimes ("Chain A" and "Chain B") both configured with `OutboundConsensusDeliveryReward(dest) > 0` for the same EVM destination chain, and both tracking `EvmHost._epochs[set_id]` state for that destination (a legitimate multi-deployment/testnet-mainnet setup).
2. Relayer delivers the mandatory consensus rotation for `set_id` to the EVM destination once; `EvmHost.recordEpoch(set_id, relayerAddress)` is set on the destination.
3. Relayer signs `outbound_consensus_delivery_message(set_id, destination, payee)` = `keccak256((set_id, destination, payee).encode())` once and submits `OutboundConsensusDeliveryClaim` to Chain A → `process_outbound_consensus_delivery_claim` verifies the state proof, recovers the same EVM address, and pays out from Chain A's treasury, then sets `OutboundConsensusRotationsClaimed[destination, set_id]` on Chain A only.
4. The identical `signature`, `set_id`, `payee`, and a state proof valid against Chain B's own stored commitment for the same destination height are submitted as a claim to Chain B. Because `OutboundConsensusRotationsClaimed` is per-runtime storage and the signed message never referenced which chain is paying, Chain B's `process_outbound_consensus_delivery_claim` passes every check (`!contains_key`, state proof, signature recovery) and pays out a second time from Chain B's treasury for a single relayer action.
5. Same mechanics apply to `OutboundRequestDeliveryClaim` via `outbound_request_delivery_message(commitment, destination, payee)`.

/// comes from the on-chain `(destination, set_id)` idempotency tag in
