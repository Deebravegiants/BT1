### Title
Fee-on-transfer/deflationary underlying tokens create unbacked cross-chain mints in `WrappedHyperFungibleToken.send()` - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` locks the configured `_underlying` ERC20 token via `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain message that always encodes the full nominal `params.amount` as the amount to be minted/unlocked on the destination chain. It never measures the actual balance change on the wrapper, so if `_underlying` is a fee-on-transfer/deflationary token, the wrapper receives less than `params.amount` while the remote `HyperFungibleToken` mints the full nominal amount, creating an unbacked cross-chain supply.

### Finding Description
In `send()`, the ERC20 lock path is: [1](#0-0) 

`params.amount` is transferred in via `safeTransferFrom` with no before/after balance check, and the same `params.amount` is embedded verbatim in the dispatched `Message` (via `_buildDispatchPost`): [2](#0-1) 

On the destination chain, `HyperFungibleToken.onAccept` trusts `message.amount` completely and mints it 1:1 to the beneficiary: [3](#0-2) 

If `_underlying` charges a transfer fee (or is otherwise deflationary), the wrapper actually locks `params.amount * (1 - fee)`, but the destination chain mints `params.amount` of the wrapped representation — the exact fee-on-transfer accounting gap that the referenced VaultHelper report describes, except here it manifests as unbacked mint supply across the bridge rather than a reverted deposit. The same pattern exists in the upgradeable variant: [4](#0-3) 

By contrast, the newer `IntentGatewayV2.placeOrder` path in the same repo was explicitly hardened against this exact issue by measuring `balanceOf` before/after the transfer and using the actual received amount: [5](#0-4) 

`WrappedHyperFungibleToken.send()` was not given the same treatment.

### Impact Explanation
Each `send()` call with a deflationary/fee-on-transfer underlying token causes the wrapper's actual locked balance to fall short of the cumulative nominal amount it has promised to mint/unlock across all destination chains. Over repeated sends, the escrow backing the wrapped token becomes permanently under-collateralized: some legitimate holders of the minted/wrapped representation will be unable to redeem the full underlying amount when bridging back, because `onAccept`'s `safeTransfer(beneficiary, message.amount)` will eventually fail or drain the pool disproportionately for earlier redeemers, resulting in unbacked mint / permanent loss of funds for later users. This is a protocol-level bridge insolvency, not merely a reverted single transaction as in the original VaultHelper report.

### Likelihood Explanation
Reachable by any unprivileged user in a single `send()` transaction as long as the token deployer/owner configures a fee-on-transfer, rebasing, or otherwise non-standard ERC20 as `_underlying` via `configure()`. Since `configure()` is owner-gated but token selection is a normal deployment/business decision (not malicious governance), and many real-world tokens (e.g. certain stablecoins with fee switches, RFI-style tokens) exhibit this behavior, the precondition is realistic rather than adversarial-admin-only.

### Recommendation
Mirror the fix already used in `IntentGatewayV2.placeOrder`: measure `IERC20(_underlying).balanceOf(address(this))` before and after the `safeTransferFrom` call in `send()`, and use the actual received delta (not `params.amount`) when constructing the dispatched `Message`, in both `WrappedHyperFungibleToken.sol` and `WrappedHyperFungibleTokenUpgradeable.sol`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken`, configure `_underlying` to a fee-on-transfer ERC20 (e.g., 1% fee) via `configure()`.
2. User approves and calls `send({ amount: 1000e18, ... })`. `safeTransferFrom` pulls 1000e18 nominally but the wrapper only receives 990e18 due to the transfer fee.
3. The dispatched `Message.amount` is still `1000e18`.
4. On the destination chain, `HyperFungibleToken.onAccept` mints `1000e18` to the beneficiary — 10e18 more than what is actually locked in the source wrapper.
5. Repeating this widens the backing gap; eventually a `send()` back to the home chain (`onAccept` on `WrappedHyperFungibleToken`, unlocking `message.amount`) will fail for the last redeemers or drain the pool for earlier ones, leaving some holders permanently unable to redeem.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
        }

        DispatchPost memory request = _buildDispatchPost(params);
        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }
