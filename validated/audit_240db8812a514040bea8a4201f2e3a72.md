### Title
Webhook cross-tenant forgery — `shop` field is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the `shop` value taken from an unauthenticated header to identify the tenant the payload belongs to. Because the shop identity is never part of the signed material, any user who can obtain one validly-signed webhook (e.g. by triggering an event on their own, legitimately-installed store) can replay that exact signed body while swapping the shop header to a different shop domain, and the library will accept it as an authentic webhook for that other shop.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` verifies authenticity only through `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` and compares it to the received HMAC: [2](#0-1) 

For webhooks, `to_signable_string` is defined as just the raw request body — it does not include the shop, topic, webhook id, or api version: [3](#0-2) 

Meanwhile `shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers with no cryptographic binding to the body or to the HMAC at all: [4](#0-3) 

After the HMAC check passes, `process` forwards this unauthenticated `request.shop` value directly into `WebhookMetadata` and into the registered handler as ground truth for which tenant the event belongs to: [1](#0-0) 

The broken identity binding, stated as an equality that the code fails to enforce, is:
`HMAC(raw_body, api_secret_key) == received_hmac` should imply `shop_header == shop_that_produced(raw_body)`, but the code only checks the left side and blindly trusts `shop_header` for tenant attribution.

Because `api_secret_key` is a single, app-wide secret shared across every shop that has installed the app (it is not shop-specific), any merchant who installs the app is able to receive a genuinely Shopify-signed webhook body for their own store. Since the shop identity is carried out-of-band in a header that isn't covered by the signature, that same signed body/HMAC pair remains valid if replayed with a different `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header pointing at another (victim) shop — a value that is often guessable or publicly known.

### Impact Explanation
This breaks the tenant boundary the webhook mechanism is supposed to enforce: an unprivileged actor (any merchant who can install the app on their own store) can make the app process forged data as if it originated from an arbitrary other shop, i.e. cross-tenant access/data injection. If the host application uses `data.shop` from `WebhookMetadata` to look up that shop's session/access token or to trigger tenant-scoped side effects, an attacker can drive those effects under a victim shop's identity without ever compromising that victim or the app's secret.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs to legitimately install the target app on a store they control (a normal, unprivileged onboarding action) to capture one validly HMAC-signed webhook body/header pair, then modify only the shop header before replaying it to the app's public webhook endpoint. No knowledge of `api_secret_key`, no access token, and no privileged account is required.

### Recommendation
Bind the tenant identity into the signed material, or otherwise cross-verify it out of band:
- Include `shop` (and `topic`, `webhook_id`) in the value covered by the HMAC (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signed payload), or
- Require the host application to independently confirm `request.shop` corresponds to a shop that actually has an active session/installation before trusting `WebhookMetadata#shop`, and document this requirement explicitly since the gem currently does not enforce it.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled store `attacker-shop.myshopify.com`.
2. Trigger a webhook event (e.g. `orders/create`) on that store; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify — both are valid under the app's `api_secret_key`.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body's HMAC.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb`) invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop.
