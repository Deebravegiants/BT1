### Title
Missing shop-binding in `validate_auth_callback` enables OAuth state/session fixation - (`lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` only checks `state == auth_query.state` (cookie vs. callback) and a valid HMAC; it never records or checks which shop `begin_auth` actually redirected to. Chained with the (separately-flagged) unsanitized `shop` input to `auth_base_uri`, an attacker can leak the victim's `state` nonce and later replay a real, validly-signed OAuth completion for their *own* shop against the victim's browser, fixing the victim's app session onto the attacker's tenant.

### Finding Description
The claimed binding, expressed as an equality, is:

`shop_begin_auth_redirected_to == auth_query.shop` (as seen by `validate_auth_callback`)

Tracing `begin_auth` [1](#0-0) , the only artifact persisted for the browser is a random nonce (`state`) placed in `SessionCookie`; no shop value is stored anywhere client- or server-side to later compare. `auth_base_uri(shop)` builds the redirect target directly from the caller-supplied `shop` with no call to `Utils::ShopValidator.sanitize!` [2](#0-1) .

In `validate_auth_callback`, the checks performed are: HMAC validity via `Utils::HmacValidator.validate(auth_query)`, then `state == auth_query.state`, then `Session.new(shop: auth_query.shop)` / `Session.from(shop: auth_query.shop, ...)` — at no point is `auth_query.shop` compared to anything recorded from the corresponding `begin_auth` call [3](#0-2) . This confirms the equality is never checked, before or after the callback is processed.

Exploit chain (given the prior unsanitized-`shop` redirect issue is present so `auth_base_uri` can point off Shopify):
1. Attacker lures the victim to the app's login route with a malicious `shop` value, causing `begin_auth` to set a legitimate `SessionCookie` (real nonce `X`) on the victim's browser and redirect the browser to an attacker-controlled origin, with `X` appearing in plaintext as the `state` query parameter of that redirect URL.
2. Attacker's server, receiving that redirected request, reads `X` out of the URL (the cookie itself is inaccessible cross-origin, but the leaked query param is not).
3. Attacker separately drives a real Shopify `/oauth/authorize` flow on their own registered development shop, supplying `state=X` themselves, and lets Shopify redirect to the app's genuine callback URL with a validly-signed `hmac`, `code`, and `shop=<attacker-shop>`.
4. Attacker sends that completed callback URL to the victim (link/redirect). The victim's browser still carries the `SessionCookie` with value `X` from step 1, so `state == auth_query.state` passes, `HmacValidator.validate` passes (it's a genuine Shopify-signed callback), and `validate_auth_callback` issues a `Session` keyed to the attacker's shop — under the victim's browser/session context.

None of the existing guards catch this: `HmacValidator.validate` only proves the callback was genuinely issued by Shopify for *some* shop, not that it's the shop the victim intended; the `state` check only proves browser continuity, not shop continuity; there is no `ShopValidator.sanitize!` call in `begin_auth` at all.

### Impact Explanation
This does not hand the attacker the victim's own store's access token or data — the resulting `Session` is bound to the attacker's own shop, using the attacker's own legitimately-obtained access token. The real impact is that the victim's browser/app session becomes fixed to a tenant the attacker chose, i.e. a **session fixation / forced OAuth completion**, which the rules place in the **High** category rather than the "Critical - cross-tenant access" framing in the question (cross-tenant *data* exposure of the victim's real store to the attacker does not occur here). The attack is repeatable against any victim who can be induced to click two crafted links, and its blast radius is limited to confusing/fixating individual victim sessions onto attacker-chosen shops, not extracting victim secrets.

### Likelihood Explanation
Exploitability is entirely contingent on the separate, already-noted precondition that the host app passes an unsanitized `shop` value into `begin_auth` (no `ShopValidator.sanitize!` call exists in this gem's `begin_auth`), so `auth_base_uri` can be redirected off-Shopify to leak the `state` nonce. Absent that chain, the missing shop-binding by itself is inert, since Shopify itself is the sole entity minting valid, HMAC-signed callbacks with a given `state`, and legitimate flows never let an attacker learn or set an arbitrary `state` value in a victim's cookie. The attack additionally requires two social-engineering steps (getting the victim to click two links) and yields a lower-value payoff (session fixation) than the "Critical" cross-tenant label implies.

### Recommendation
Have `begin_auth` persist an authenticated binding of the expected shop (e.g., HMAC-sign `shop` together with `state` into the cookie, or store `shop` server-side keyed by the nonce) and have `validate_auth_callback` verify `auth_query.shop` against that stored/signed value before proceeding, in addition to enforcing `ShopValidator.sanitize!` on any caller-supplied `shop` before it is ever used to build `auth_base_uri`.

### Proof of Concept
minitest (WebMock, no live shop) in `test/auth/oauth_test.rb`:
1. Call `ShopifyAPI::Auth::Oauth.begin_auth(shop: "test-shop.myshopify.com", redirect_path: "/callback")`, capture `cookie.value` as `state_x` and the `auth_route`.
2. Simulate the "attacker leaks state_x and replays a Shopify-signed callback for their own shop": build an `AuthQuery` with `shop: "attacker-shop.myshopify.com"`, `state: state_x`, and a correctly computed HMAC (using `ShopifyAPI::Context.api_secret_key`, matching real production signing) over `{code, host, shop: "attacker-shop.myshopify.com", state: state_x, timestamp}`.
3. Call `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies: { SessionCookie::SESSION_COOKIE_NAME => state_x }, auth_query: attacker_auth_query)`.
4. Stub `POST https://attacker-shop.myshopify.com/admin/oauth/access_token` with WebMock to return a valid token response.
5. Assert the call succeeds (no `InvalidOauthError`) and returns `session.shop == "attacker-shop.myshopify.com"`, proving `auth_query.shop` was never checked against the shop (`test-shop.myshopify.com`) that `begin_auth` was originally invoked for — i.e., assert `expected_shop_from_begin_auth != session.shop` while validation still passes.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
