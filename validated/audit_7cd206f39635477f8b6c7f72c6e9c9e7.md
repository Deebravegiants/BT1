### Title
`compareAddresses` case-sensitive raw comparison for Bitcoin lets an uppercase bech32 destination bypass `DestinationAddressMatchesTokenAddressError`, and the value is later lower-cased to the token's own custody address - (File: `packages/intents-sdk/src/lib/compareAddresses.ts`, `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`, `packages/intents-sdk/src/bridges/omni-bridge/omni-withdraw-params.ts`)

### Summary
`OmniBridge.validateWithdrawal` calls `compareAddresses(destTokenAddress, args.destinationAddress, Chains.Bitcoin)` to block withdrawals to the token's own custodian address, but the Bitcoin branch of `compareAddresses` does a raw `a === b` string comparison with no case normalization. Because `validateAddress`/`validateBtcAddress` accepts bech32 in either all-lowercase or all-uppercase form (BIP-173), an attacker can submit an uppercase bech32 `destinationAddress` that decodes to the exact same witness program bytes as the token's (lowercase) custody address; the equality check treats them as different and lets the withdrawal through.

### Finding Description
The broken equality: `destTokenAddress` (lowercase bech32, e.g. `bc1qxyz...`) is claimed to be "not equal" to `args.destinationAddress` (uppercase bech32 of the identical witness-program bytes, e.g. `BC1QXYZ...`) by `compareAddresses`, when semantically for Bitcoin they are the same address.

Code path:
1. `validateWithdrawal` (`packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts:358-365`) calls `validateAddress(args.destinationAddress, Chains.Bitcoin)`, which routes to `validateBtcBech32Address` (`packages/intents-sdk/src/lib/validateAddress.ts:160-202`). `bech32.decode`/`bech32m.decode` from `@scure/base` accept either all-lowercase or all-uppercase input per BIP-173 — an all-uppercase address passes validation.
2. `validateWithdrawal` then fetches `destTokenOmniAddress` and derives `destTokenAddress = getAddress(destTokenOmniAddress)` (`omni-bridge.ts:373-384`), which per the code comment in `omni-withdraw-params.ts:118-119` ("Omni contract only accepts lowercase bech32 addresses") is the canonical **lowercase** custody address for that token.
3. The self-transfer guard: `compareAddresses(destTokenAddress, args.destinationAddress, assetInfo.blockchain)` (`omni-bridge.ts:386-391`) falls into the Bitcoin branch of `compareAddresses` (`compareAddresses.ts:48-60`), which does `return a === b;` — a raw string comparison with no case folding, unlike the Ethereum (`getAddress`), hex (`normalizeHexAddress`), TON, Tron, and Stellar (`toUpperCase`) branches, which all normalize case/format.
4. If the attacker supplies `args.destinationAddress` as the uppercase form of `destTokenAddress`'s bytes, `a === b` is `false`, so `DestinationAddressMatchesTokenAddressError` is NOT thrown, and `validateWithdrawal` proceeds (independent of `skipMinAmountValidation`, which only guards the minimum-amount check further down at `omni-bridge.ts:405-426`).
5. Later, when the withdrawal is actually built, `deriveOmniWithdrawIntentParams` (`omni-withdraw-params.ts:118-124`) lower-cases the destination address for BTC before constructing the `recipient` `OmniAddress` used for the on-chain transfer: `params.destinationAddress.toLowerCase()`. This converts the attacker's uppercase input back into the exact lowercase custody address that the guard was supposed to reject, so the actual on-chain recipient becomes the token's own bridge-custodied address.

Existing guards fail because: `validateAddress` doesn't reject case variants (by design, per BIP-173 spec compliance), and `compareAddresses`'s Bitcoin branch is the only one among the case/format-insensitive chains (EVM, Aptos/Sui/Starknet, TON, Tron, Stellar) that does not normalize before comparing.

### Impact Explanation
A user calling `IntentsSDK`/`OmniBridge.validateWithdrawal` (and the subsequent withdrawal build/sign flow) with an uppercase-bech32 `destinationAddress` bypasses the self-custody-address guard, and the funds get built into an intent whose recipient is the token's own bridge custodian address on Bitcoin. This is a Critical impact: BTC withdrawal proceeds to the bridge's own custody address (funds unrecoverable by the withdrawing user), matching "funds delivered to a wrong address... with no recovery." It is repeatable per withdrawal attempt for any UTXO-chain (specifically Bitcoin) asset routed through `OmniBridge`.

### Likelihood Explanation
Preconditions: the attacker only needs to know the token's public custody bech32 address on Bitcoin (obtainable via `getCachedDestinationTokenAddress`/public bridge data) and re-case it to uppercase — a trivial, zero-cost, entirely client-side transformation requiring no privileged access, no relayer/RPC manipulation, and no admin cooperation. `skipMinAmountValidation: true` is not required for this specific bypass (the case-sensitivity flaw exists in the `compareAddresses` self-match check regardless), though a caller could combine both. This is highly feasible and fully repeatable.

### Recommendation
Normalize Bitcoin (and other UTXO chain) bech32 addresses to lowercase (or decode to raw witness-program bytes) before comparing in `compareAddresses`'s Bitcoin/BitcoinCash/Litecoin/Dogecoin/Dash branch, mirroring how EVM/hex/TON/Tron/Stellar branches already normalize. E.g., for bech32-style addresses, decode via `bech32`/`bech32m` and compare `(prefix, words)` tuples instead of raw strings, falling back to case-insensitive comparison for base58 legacy forms only if bytes decode equal.
