### Title
Webhook HMAC does not bind the `shop-domain` header, enabling cross-tenant webhook spoofing via body replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` checks the HMAC signature against that body alone. The `shop` (from the `x-shopify-shop-domain` header), `topic`, `api-version`, and `webhook-id` values are never included in the signed payload. `Registry.process` accepts any request whose HMAC matches the body, then trusts the *unauthenticated* `shop` header value as the tenant identity handed to the application's webhook handler.

### Finding Description
The identity binding the code implicitly assumes is: `shop authenticated by HMAC == shop used as the tenant/session key delivered to the handler`. In reality:
- HMAC-verified: `@raw_body` only — see `hmac` and `to_signable_string` in [2](#0-1) .
- Tenant-key used downstream: `request.shop`, parsed straight from the `shop-domain` header with no cryptographic binding — see `shop` accessor at [3](#0-2)  and its use in `Registry.process` at [1](#0-0) .

Because `shop-domain` is outside the signed bytes, an attacker who can capture one legitimate webhook delivery from Shop A (e.g. a public/observable webhook payload, a shared reverse proxy log, a debugging tool, or their own dev-store subscription for a topic with body content identical/predictable across shops, such as `app/uninstalled` or `shop/redact` with minimal or fixed body) can resend the exact same `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value (e.g. Shop B's domain). `HmacValidator.validate` still succeeds because it only recomputes the HMAC over `raw_body`, which is unchanged. The forged request is then dispatched to the app's handler tagged with the attacker-chosen `shop`, i.e. cross-tenant confusion: `shop (HMAC-authenticated) != shop (used as session/tenant key)`.

### Impact Explanation
This breaks the tenant identity boundary the whole webhook subsystem relies on. Depending on the handler's logic (which typically trusts `WebhookMetadata#shop` to look up/mutate per-shop state, e.g., de-provisioning, GDPR redaction, or billing state), an attacker can trigger actions attributed to a shop they do not own, or cause state confusion between tenants — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires the attacker to first observe one valid `(raw_body, hmac)` pair, which is feasible for topics with static/predictable/empty bodies (mandatory topics like `shop/redact`, `customers/redact`, `app/uninstalled` often carry minimal, non-secret bodies), and does not require knowledge of `api_secret_key`. This keeps it in the unprivileged-internet-user threat model, though it is somewhat constrained by needing a captured sample per topic.

### Recommendation
Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the verified body before it is handed to `WebhookHandler#handle`. At minimum, document that host applications must not trust `WebhookMetadata#shop` without additional verification (e.g., cross-checking against a known/expected shop), or Shopify's HMAC scheme should be extended to cover headers.

### Proof of Concept
1. Capture a legitimate webhook delivery for shop `victim-a.myshopify.com`, topic `app/uninstalled`, with headers `x-shopify-hmac-sha256: <H>` and body `raw_body` (e.g. `{}` or minimal JSON) and note that `H = HMAC-SHA256(api_secret_key, raw_body)`.
2. Replay this exact `raw_body` and `x-shopify-hmac-sha256: <H>` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body (`lib/shopify_api/webhooks/request.rb:45-63`), `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against `H` (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop = "victim-b.myshopify.com"` even though the HMAC only ever proved the body's authenticity, not the shop identity — demonstrating the cross-tenant identity-binding break.
