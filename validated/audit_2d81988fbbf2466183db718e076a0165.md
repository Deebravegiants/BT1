### Title
`placeOrder` uses `block.timestamp` as the Uniswap V2 swap deadline, giving no MEV/sandwich protection on the fee-token swap - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
When a user calls `placeOrder` and pays the solver fee in native token, `IntentGatewayV2` converts the sent ETH into `feeToken` via `swapETHForExactTokens` on Uniswap V2, passing `block.timestamp` as the swap `deadline`. Because `block.timestamp` is evaluated at execution time, it is not a real time bound — a validator/searcher can hold, reorder, or delay inclusion of the transaction indefinitely and the "deadline" check will always pass, exactly the bug class described in the referenced Notional report.

### Finding Description
In `placeOrder`, when `order.fees > 0` and the user paid with native currency (`msgValue > 0`), the contract performs an on-chain swap to acquire the exact fee token amount: [1](#0-0) 

The `deadline` argument passed to `IUniswapV2Router02.swapETHForExactTokens` is `block.timestamp`, i.e., the timestamp of whatever block the transaction ends up mined in. This provides zero protection against delayed execution: unlike a user-supplied deadline that bounds staleness relative to signing time, `block.timestamp` always satisfies `deadline >= block.timestamp` trivially at execution, so the swap will never revert due to staleness regardless of how long the transaction sat in the mempool or was delayed by a block builder/validator. This is the exact anti-pattern flagged in the referenced report (`StrategyUtils.sol`), reproduced here in `IntentGatewayV2.placeOrder`.

The swap uses `swapETHForExactTokens` (exact-output), where `amountInMaximum` is implicitly `msgValue` (the ETH forwarded with the call), and `amounts[0]` (actual ETH spent) is later refunded via `msgValue -= amounts[0]` and returned to the user: [2](#0-1) 

Because the deadline offers no real time bound, a block builder/validator (or a searcher paying for priority) can arbitrarily delay inclusion of the `placeOrder` transaction to a more favorable block for themselves, then sandwich the swap: front-run with a trade that pushes the WETH/feeToken pool price up, let the victim's exact-output swap consume more ETH than intended (up to the full `msgValue` ceiling), and back-run to restore price and capture the difference. The victim's refund (`amounts[0]` vs `msgValue`) shrinks accordingly, i.e., value is extracted from the user's own ETH deposit that would otherwise have been refunded.

### Impact Explanation
This is directly reachable by any unprivileged user submitting a `placeOrder` transaction with `order.fees > 0` paid in native token — no privileged role is required. The manipulable deadline removes the intended protection against delayed/sandwiched execution, allowing MEV extraction of value from the user's escrowed ETH during order placement. While the loss is bounded by the ETH the user forwarded (`msgValue`), it still represents value siphoned away from users on every fee-paid order placement through a mechanism that should have been preventable with a real, short deadline window. This qualifies as a Medium-severity fund-loss issue analogous to the reported class.

### Likelihood Explanation
Likelihood is high: `placeOrder` is a core, frequently invoked entry point of the Intent Gateway, and any order with a nonzero `fees` field paid in native token triggers this code path. No special conditions or races beyond normal MEV infrastructure (which is ubiquitous on EVM chains) are needed to exploit it.

### Recommendation
Replace `block.timestamp` with a caller-supplied `deadline` parameter (e.g., add a `feeSwapDeadline` field to the `Order`/`placeOrder` call, or derive it from a short, explicit offset agreed with the user off-chain) so the Uniswap deadline check meaningfully bounds how long the transaction can be delayed before the swap becomes invalid.

### Proof of Concept
1. User calls `placeOrder` with `order.fees > 0` and sends native ETH (`msgValue > 0`) intended to cover the fee-token purchase plus slack for refund.
2. A validator/searcher observing the pending transaction delays its inclusion and/or sandwiches it: front-run buy on the WETH/feeToken pair to raise price, include the victim's `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` call (which cannot revert on staleness since `deadline == block.timestamp` at execution), then back-run sell to restore price.
3. `amounts[0]` (ETH actually spent) is higher than it would have been absent manipulation, shrinking the refund computed at [3](#0-2) , extracting value from the user with no on-chain recourse.
