## Title
Webhook Shop-Domain Header Is Not Covered by HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, excluding the `shop-domain` header from the HMAC-protected content. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then trusts `request.shop` (read straight from the unauthenticated header) as the tenant identity passed to the app's handler. This breaks the equality that should hold between "bytes verified by HMAC" and "shop identity acted on," allowing a party who has observed one validly-signed webhook body (e.g., from their own shop's installation) to replay that body with a different `shop-domain` header value and have it accepted as belonging to another tenant.

### Finding Description
For OAuth callbacks, the library correctly binds the shop to the signature: `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in the signed parameter set [1](#0-0) .

For incoming webhooks, however, `Request#to_signable_string` returns only `@raw_body`, and `Request#shop` reads the `shop-domain` header independently of anything covered by the signature: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which internally calls `validate_signature` using `verifiable_query.to_signable_string` (i.e., the body only) [3](#0-2) . After that check passes, `process` immediately forwards the unauthenticated `request.shop` into the handler's metadata as the tenant context: [4](#0-3) 

The broken identity equality is:
`hmac_valid(raw_body) == true` does **not** imply `shop_header == shop_that_actually_generated(raw_body, hmac)`

Because the app's `api_secret_key` is shared across every shop that installs the app, any party can obtain at least one genuine `(raw_body, hmac)` pair for their own shop (by installing the app and letting Shopify deliver a webhook to their own endpoint/logs), then submit a request to the app's public webhook endpoint with that same body/HMAC but an arbitrary `shop-domain` header. Since `shop` is not part of the signed content, `HmacValidator.validate` still returns `true`, and `Registry.process` dispatches the payload to the handler tagged with the attacker-chosen `shop`, crossing tenant boundaries. This mirrors the report's underlying bug class: a field that is *acted upon* (here, the tenant-identifying `shop`) is not covered by the same authentication mechanism (HMAC) that is presumed to authenticate the whole request, just as `delegatorAssets`/`delegatorMap` in the report were acted upon without being kept in sync with the actually-verified state.

### Impact Explanation
This qualifies as Critical/cross-tenant access: any app relying on `WebhookMetadata#shop` (populated straight from the request, as most host apps do to route data to the correct tenant record) can be made to process/store attacker-supplied webhook payloads under a victim shop's identity, without ever needing that victim's credentials. This can lead to data corruption, unauthorized state changes, or injection of fabricated events into another merchant's tenant data, entirely from an unprivileged attacker who merely installed the app on their own shop.

### Likelihood Explanation
The attacker needs no privileged credentials, TLS interception, or leaked secrets — only the ability to install the app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint, which by design must be internet-reachable. This makes the likelihood realistic for any host application that trusts `WebhookMetadata#shop`/`request.shop` for tenant routing, as documented and expected in this gem's own webhook usage flow.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-verified scope for webhooks, analogous to how `AuthQuery#to_signable_string` already includes `shop` for OAuth. Since Shopify's webhook HMAC spec only signs the raw body, the safer fix within this gem is to require host apps to cross-check `request.shop` against a shop that is independently known/authorized (e.g., an existing session/webhook registration for that shop and topic) before trusting it, and to document this gap prominently. Alternatively/additionally, provide a helper that validates the `webhook_id` against a shop-scoped registration record so that the tenant binding is verified by something other than the unauthenticated header.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and lets it register for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a legitimately signed webhook to the app's endpoint: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the shared `api_secret_key`), `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and re-sends a POST to the same public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid since `to_signable_string` only covers `B`), but `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` returns `true` (body/HMAC match, per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`), and `Registry.process` dispatches `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ...)` to the handler [4](#0-3) , causing the host app to process attacker-controlled data under the victim's tenant identity.
