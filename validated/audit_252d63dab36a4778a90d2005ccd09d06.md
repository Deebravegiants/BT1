## Title
Escrow accounting credited from requested amount instead of actual tokens received, exceeding real balance for fee-on-transfer inputs - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` on the Tron deployment credits per-order escrow (`_orders[commitment][token]`) using the pre-computed `reducedInputs[i].amount` (protocol-fee-reduced *requested* amount) rather than the amount the contract actually received via `safeTransferFrom`/dispatcher sweep. This is structurally the same class of bug as CVE-2023-53270: an accounting field (`i_disksize` / here, `_orders[commitment][token]`) is advanced to an optimistic value derived from the intended transfer size, without first confirming that the actual transfer delivered that amount. When the underlying token takes a fee on transfer, the escrow ledger permanently overstates the tokens actually custodied by the contract for that commitment.

### Finding Description
In the audited/fixed EVM `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol:230-329`), Phase 1 explicitly measures the *actual* balance delta after each transfer/sweep and mutates `order.inputs[i].amount` to that measured value before computing the commitment and crediting escrow — this exists specifically to make escrow "consistent with what the gateway holds" for fee-on-transfer tokens, and is exercised by tests such as `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2441-2494`).

The Tron variant at `evm/tron/contracts/apps/IntentGatewayV2.sol` does not perform this measurement: [1](#0-0) 

For the non-predispatch path, `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` is called, and immediately after, `_orders[commitment][token] += reducedInputs[i].amount;` credits escrow using the requested (fee-reduced) amount — never the delta actually received by the contract. The predispatch path has the same defect: it computes `dust = balance - requiredAmount` against the dispatcher's balance (used only for a dust event), but still credits escrow with `reducedInputs[i].amount`, the intended amount, not what the gateway itself ends up holding after the sweep transfer (`evm/tron/contracts/apps/IntentGatewayV2.sol:416-446`).

If the input token charges a transfer fee (deflationary/fee-on-transfer ERC20, or any token with non-1:1 transfer semantics — common on Tron's TRC20 ecosystem), the contract will hold strictly less of that token than `_orders[commitment][token]` records. Since `_orders` is a mapping shared across the token's global balance in the contract (not a segregated per-order vault), this creates escrow entries backed by phantom balance.

### Impact Explanation
This is a concrete state/accounting-integrity bug reachable from a single unprivileged `placeOrder` call — no special permissions required, and it does not depend on a "malicious admin" or off-chain component. The consequences:
- **Insolvent escrow / fund freezing**: once enough orders using fee-on-transfer tokens are placed, the sum of all `_orders[commitment][token]` entries can exceed the gateway's actual token balance. A later solver's legitimate `withdraw()`/fill settlement for an *unrelated* order sharing that token can then fail (revert) because the contract lacks the tokens to pay out, freezing funds for the order whose withdrawal happens to be starved.
- **Theft/misallocation across orders**: because the escrow ledger is a mapping rather than a real per-order token custody, an earlier order's inflated credited balance is effectively drawn down from tokens that truly belong (in reality) to a *different* order's actual deposit, letting one order's solver/fill drain balance that another user is relying on.

This matches the "concrete theft or permanent freezing of funds" acceptance criterion and is reachable purely through the standard intent-placement flow used by any unprivileged token bridger/intent submitter.

### Likelihood Explanation
Likelihood is Medium-to-High wherever the deployment can accept arbitrary/permissionless input tokens (which is the general design of `IntentGatewayV2`, supporting any ERC20/TRC20 as `order.inputs[i].token`). Fee-on-transfer and rebasing tokens are common in the wild (and especially prevalent among Tron TRC20 tokens), so a user placing an order with such a token — or an attacker deliberately choosing one to create insolvency — triggers this without any privileged action, matching the requirement of a single submitted transaction from an intent creator.

### Recommendation
Mirror the fix already applied to the canonical EVM `IntentGatewayV2.sol`: measure the actual token balance delta (`balanceOf(address(this))` before/after `safeTransferFrom`, and the dispatcher-sweep balance delta for the predispatch path) and use that measured value — not the nominal/requested `reducedInputs[i].amount` — both when computing the commitment hash and when crediting `_orders[commitment][token]`. Apply the same fee-on-transfer regression tests that exist for the EVM contract (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`, `testPlaceOrder_FeeOnTransferToken_Predispatch`) to the Tron contract test suite.

### Proof of Concept
1. Deploy a fee-on-transfer TRC20 token (e.g. 1% fee on `transfer`/`transferFrom`, as modeled by the `FeeOnTransferToken` test helper at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2690-2730`) and mint balance to `user`.
2. `user` approves `IntentGatewayV2` (Tron) for `inputAmount = 1000e18` of this token and calls `placeOrder` with this token as `order.inputs[0]`, no predispatch.
3. `safeTransferFrom(user, address(this), 1000e18)` moves only `990e18` into the gateway (1% fee burned/retained by token), so the gateway's actual balance increases by `990e18`.
4. `_orders[commitment][token] += reducedInputs[0].amount` credits based on `1000e18` (minus protocol fee if configured) — i.e., escrow now claims more tokens than the `990e18` actually held.
5. Repeat with more orders on the same token; the sum of `_orders[...]` entries for that token now exceeds `IERC20(token).balanceOf(address(intentGateway))`. Any subsequent `withdraw()`/settlement path that tries to pay out the full credited amount for one of these commitments will either revert (freezing that order) or, if it succeeds by consuming balance intended for a different order's escrow, effectively steals from that other order.
