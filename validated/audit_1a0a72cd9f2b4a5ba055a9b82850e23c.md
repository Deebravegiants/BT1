### Title
Webhook `shop` identity is taken from an HMAC-unsigned header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, but exposes a `shop` attribute that is read from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header. `Registry.process` validates the HMAC and then forwards `request.shop` unauthenticated to the app's webhook handler. Because the header is not part of the signed bytes, any party who can produce (or replay) a validly-signed body for one shop can attach an arbitrary `shop` value, causing the handler to process the webhook under the wrong tenant's identity.

### Finding Description
The HMAC binding for webhooks is defined in `lib/shopify_api/webhooks/request.rb`: [1](#0-0) 

`hmac` is derived from the `hmac-sha256` header, and the `shop` accessor reads the `shop-domain` header directly: [2](#0-1) 

But `to_signable_string`, which is what actually gets HMAC-verified, is only the raw JSON body: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` and compares it to the supplied `hmac`: [4](#0-3) 

`Registry.process` calls this validator, then trusts `request.shop` (from the header) to build the `WebhookMetadata` passed to the app's handler: [5](#0-4) 

The equality that should hold is: *the shop bound into the HMAC signature == the shop the handler acts on*. Instead, the gem verifies `HMAC(body)` but acts on `shop = header["shop-domain"]`, a value entirely outside the signed material. Any request with a body whose HMAC happens to validate (e.g., a genuine webhook delivery for Shop A, replayed/relayed with the `shop-domain` header changed to Shop B) will pass `HmacValidator.validate` and be dispatched to the handler claiming to originate from Shop B.

### Impact Explanation
This breaks the tenant-identity binding for webhook processing: a webhook payload cryptographically proven only to have originated from *some* authentic Shopify webhook (correct body + secret) can be relabeled to appear as if it came from a different, arbitrary shop, since the `shop-domain` header itself carries no cryptographic proof. Applications that key their handler logic (e.g., which merchant's data record to update, delete, or redact) off `WebhookMetadata#shop` as trusted input — exactly as the gem's own API surface documents and encourages via `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` — can be induced into cross-tenant data operations. This matches the Critical "cross-tenant access" category, since the attack surface is the identity binding this gem is responsible for enforcing before invoking application code.

### Likelihood Explanation
Exploitability depends on an attacker's ability to get a body+HMAC pair accepted while controlling the `shop-domain` header value delivered to the app's endpoint (e.g., a network intermediary, misconfigured proxy, or a scenario where webhook bodies for shared/generic topics like `shop/redact` are replayable across shops). It requires no possession of the `api_secret_key` or an access token — only the ability to influence the unsigned header alongside a validly-signed body, which is a lower bar than full HMAC forgery.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values in the material that is HMAC-verified, or otherwise cryptographically bind them to the request, so that `to_signable_string` covers every field the handler subsequently trusts. At minimum, `Request#to_signable_string` should not be limited to `@raw_body` while `shop` (and other headers) are treated as authenticated identity by downstream code.

### Proof of Concept
1. Attacker (or a relaying intermediary) captures a legitimately-signed webhook body+HMAC pair for `shop-a.myshopify.com`.
2. Attacker resends the same body and HMAC signature to the app's webhook endpoint, but sets the `shopify-shop-domain` (or `x-shopify-shop-domain`) header to `shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `request.to_signable_string` (`@raw_body`) against the HMAC — the tampered `shop-domain` header is never part of that check: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` even though the signed payload was never proven to originate from `shop-b`, allowing the app to act on shop-b's data for a payload that was never authenticated as belonging to shop-b.
