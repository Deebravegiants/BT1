Webhook `shop`/`topic`/`webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` authenticates nothing but the raw JSON body against the shared `api_secret_key` [2](#0-1) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, which are never fed into the HMAC computation [3](#0-2) .

### Finding Description
This is the exact bug class flagged by the external report: "a field acted on but not covered by the HMAC." `Registry.process` only checks `Utils::HmacValidator.validate(request)` (HMAC of the body) before trusting `request.shop`, `request.topic`, and `request.webhook_id`, and hands them straight to the host app's handler via `WebhookMetadata` [4](#0-3) . The identity binding the gem implicitly claims to enforce is:

`HMAC-verified(shop header) == shop header used by handler`

but the actual binding enforced is only:

`HMAC-verified(raw_body) == raw_body`, while `shop header` is passed through unauthenticated.

Because the `X-Shopify-Hmac-Sha256` value from Shopify is computed purely over the body with the shared secret, and is completely independent of the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers, an unprivileged internet user who controls (or has a store on) any shop that has this app installed can capture one genuine webhook delivery (body + valid HMAC) sent to the app's endpoint, and then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting a **different** value in the `shop-domain` header (e.g., a victim's `victim.myshopify.com`) — or a different `topic`/`webhook_id`. `HmacValidator.validate` will still pass because it validates only the body bytes, not the header bytes [5](#0-4) . The forged request will be dispatched to the registered handler tagged as coming from the victim shop [6](#0-5) .

Host apps are documented to build tenant-scoped side effects directly from `data.shop` (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [7](#0-6) , so this attack lets a low-privilege attacker inject events attributed to a shop they do not control (cross-tenant data confusion), or spoof mandatory-compliance topics like `shop/redact`/`customers/redact` for a shop they don't own.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: the `shop` value that host applications use to route/attribute webhook data is not bound to the HMAC that proves Shopify authorship. This matches the "Critical - cross-tenant access" bar in the rules, since the merchant identity conveyed to the app is forgeable by anyone who can capture a single valid webhook delivery for any shop (including their own trial/dev store) and replay it against the endpoint with a modified `shop-domain` header.

### Likelihood Explanation
Likelihood is moderate-to-high for any developer using this gem as documented: the attacker only needs one legitimately-signed webhook body from any store using the app (trivially obtainable by installing the app on their own free/dev store) and network access to POST to the app's public webhook endpoint with modified headers — no leaked secrets or privileged accounts are required.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable material verified by the HMAC, or otherwise cryptographically bind them to the body (e.g., compute the signature over a canonical string that concatenates these header values with the raw body, mirroring how `AuthQuery#to_signable_string` includes all OAuth-relevant fields [8](#0-7) ). At minimum, document prominently that `request.shop`/`topic`/`webhook_id` are unauthenticated and must be cross-checked by the host app against known/expected values before use.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g., `orders/create`, capturing the exact `raw_body` and `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint reusing the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this into a `Request` whose `shop` returns `"victim.myshopify.com"` [9](#0-8) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) and compares it to the unmodified, still-valid signature — validation succeeds [10](#0-9) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host app to process/attribute the webhook as belonging to the victim shop [11](#0-10) .
