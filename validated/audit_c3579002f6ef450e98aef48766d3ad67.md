### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the **raw body**, while the `shop` (and `topic`/`webhook_id`) identity that the handler acts on is read from an **unauthenticated header** that is never part of the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate, unsigned header: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the HMAC header — it never binds the `shop-domain`, `topic`, or `webhook-id` headers into the signature check: [3](#0-2) 

`Registry.process` uses this same unauthenticated `request.shop` to build the `WebhookMetadata` object handed to the app's handler, after only checking the HMAC: [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is shared across *all* shops that install the same app, any shop that has legitimately installed the app receives real webhooks addressed to it with a valid `X-Shopify-Hmac-SHA256` header computed only from the JSON body. That signature is not shop-specific, and since the `shop-domain` header is excluded from the signed content, a malicious (but otherwise unprivileged/merchant-level) actor can replay a `(body, hmac)` pair they legitimately received for their own shop while substituting the `X-Shopify-Shop-Domain` header to name a victim shop. `HmacValidator.validate` still passes because the body and signature match, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload is for the victim shop.

This is precisely the bug class in the analog report: a field that is *acted upon* (here, the shop identity used to route/attribute the webhook) is not covered by the authentication check (the HMAC), breaking the equality `shop authenticated by HMAC == shop the handler acts on`.

### Impact Explanation
Any handler that uses `data.shop` from `WebhookMetadata` to key state, trigger tenant-scoped side effects (e.g., GDPR `shop/redact`, `app/uninstalled` cleanup, order/customer sync) can be made to perform those actions against a shop the attacker does not control, purely by controlling the header of a request they send to the app's own webhook endpoint. This is a cross-tenant action-forgery: the "authentication" (HMAC) of the message content is disconnected from the "tenant attribution" (`shop`) that drives the action, matching the report's "authenticated one thing, acted on another" flaw. This is a Critical-class cross-tenant impact per the scope rules, and it does not require the `api_secret_key`, an access token, or any privileged credentials — only that the attacker's own shop has legitimately installed the app and can receive/replay one of its own real webhook deliveries.

### Likelihood Explanation
Any Shopify merchant can install a free/public app to receive genuine webhook deliveries for their own store; capturing a `(raw_body, X-Shopify-Hmac-SHA256)` pair requires only intercepting their own inbound HTTP traffic (e.g., logging their own webhook endpoint), which is trivial and needs no elevated access. Replaying that pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header is a simple HTTP request. Likelihood is High for any app whose webhook handlers key security- or tenant-relevant logic on `data.shop`.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is HMAC-verified, or independently verify that the `shop-domain` header corresponds to a shop with an active session/installation matching the webhook subscription that produced this delivery (e.g., cross-check against the shop's registered webhook ID via Shopify's API, or include shop in the signable string if Shopify's webhook signing supported it). At minimum, document prominently that `data.shop` is not authenticated by `Registry.process`/`HmacValidator`, so host apps do not trust it for tenant-scoping decisions, and provide a supported way for the gem to cryptographically bind shop identity to the payload.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering Shopify to send a real webhook (e.g., `orders/create`) to the app's registered endpoint with a valid `X-Shopify-Hmac-SHA256: H` computed over raw body `B` using the app's shared `api_secret_key`.
2. Attacker intercepts/logs this legitimate request from their own webhook stream (no special access needed — it's their own store's traffic).
3. Attacker resends `POST /callback/orders/create` to the app with the same body `B` and the same `X-Shopify-Hmac-SHA256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` recomputes the HMAC of `B` and matches `H` (see `lib/shopify_api/utils/hmac_validator.rb#L26-31`), so validation succeeds.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb#L198-199`), causing the app to process attacker-controlled webhook content as if it originated from the victim's shop.
