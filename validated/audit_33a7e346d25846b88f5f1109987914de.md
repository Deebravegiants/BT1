## Title
Webhook shop/topic header spoofing — HMAC covers only the raw body, not the tenant-identifying headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` treats the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, and `x-shopify-api-version` HTTP headers as trusted, authoritative identifiers, yet the HMAC signature that `Registry.process` verifies only covers the raw request body. Any actor who can obtain one genuinely-signed webhook body/HMAC pair (which any merchant can do simply by installing the app on their own, unprivileged development store and triggering a webhook) can replay that exact body with a forged `shop-domain`/`topic` header to the app's shared webhook endpoint. The signature still validates (it only checks the body), but the handler is invoked believing the event originated from a different shop or topic — a cross-tenant identity-binding break.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers, with no cryptographic tie to the body: [2](#0-1) 

`Registry.process` validates only the HMAC (i.e., only the body) via `HmacValidator.validate`, then dispatches the handler using `request.shop` and `request.topic` as if they were verified: [3](#0-2) 

`HmacValidator.validate` itself only ever checks `verifiable_query.to_signable_string` (the body) against the secret — it has no way to authenticate anything outside that string: [4](#0-3) 

The equality that should hold is: `shop authenticated by HMAC == shop the handler trusts as the event's tenant`. Because the HMAC only signs the body, this equality is not enforced — the header-derived `shop`/`topic` can diverge from what Shopify actually signed for, while remaining "valid" per `Registry.process`.

### Impact Explanation
Any app built on this gem that keys business logic, database writes, entitlement checks, or webhook-driven side effects (e.g., `shop/redact`, `customers/redact`, subscription/billing state changes, uninstall handling) off `WebhookMetadata#shop`/`#topic` is exposed to cross-tenant data corruption or spoofed lifecycle events: an attacker with a legitimate install on Shop A can cause the app to process a fabricated event "from" Shop B (or fabricate a different topic than what was actually delivered for that body), since neither field is bound to the HMAC. This is a cross-tenant boundary violation, satisfying the Critical impact bar in the rules ("cross-tenant access").

### Likelihood Explanation
Exploitation requires no `api_secret_key`, no access token, and no privileged account — only the ability to install the target app on any store (including the attacker's own free/dev store) to legitimately capture one valid `(raw_body, hmac)` pair, then POST it to the app's public webhook endpoint with attacker-chosen `x-shopify-shop-domain`/`x-shopify-topic` headers. This is squarely within the "unprivileged internet user" threat model this scan targets.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically verify it: at minimum, cross-check `request.shop` against a shop already known/authorized for this app (e.g., an existing session) before acting on webhook data, and treat header-only fields as untrusted metadata rather than as authenticated identifiers. Longer term, consider incorporating the relevant headers into the value verified against the HMAC where the delivery protocol allows it, matching Shopify's actual signing guarantees.

### Proof of Concept
1. Attacker installs the target app on an unprivileged, attacker-owned development store (`attacker-shop.myshopify.com`) and triggers any webhook (e.g., updates a product), causing Shopify to POST a body `B` with header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(secret, B)`.
2. Attacker replays the exact same `B`/`H` to the app's shared webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <any topic the app has a handler for>`
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` and the app's `Context.api_secret_key` — this succeeds because `B`/`H` are a genuinely matching pair. [5](#0-4) 
4. The registered handler for that topic is invoked with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, even though Shopify never sent this event for that shop — any handler logic keyed on `shop` now operates on the wrong tenant.
