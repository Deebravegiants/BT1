### Title
Native-ETH escrow refund/release in IntentGatewayV2 permanently reverts and locks funds when the beneficiary is a contract that rejects plain ETH transfers - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`_withdraw` (used for both cross-chain `RedeemEscrow`/`RefundEscrow` handling and same-chain fills/cancellations) sends native-token escrow to `beneficiary` via a low-level `.call{value: amount}("")` that reverts the whole transaction if the transfer fails. Because `beneficiary` is user-controlled (the order's `user` address for refunds, or `msg.sender`/solver for fills) and there is no fallback/pull-payment path, an order whose native-token beneficiary cannot accept plain ETH (e.g. a contract with no `receive`/`fallback`, or one that reverts/out-of-gases on receipt) makes the escrow permanently unwithdrawable through both the fill path and the refund/cancel path.

### Finding Description
`IntentsBase._sendValue` reverts on failed native transfer: [1](#0-0) 

It is used inside `_withdraw`, the single function responsible for releasing/refunding escrowed native tokens to a beneficiary derived from cross-chain messages or local order data: [2](#0-1) 

`_withdraw` is reached from:
- `onAccept` handling `RedeemEscrow`/`RefundEscrow` cross-chain messages (source-chain settlement after a solver fills on the destination chain, or after cross-chain cancellation) — the `beneficiary` here is either `order.user` (refund case) or the filling solver's address encoded in the settlement message.
- `_cancelSameChain` in `IntrinsicIntents.sol`, refunding to `order.user`.
- `_fillSameChain`'s partial/full-fill escrow release to the solver.

None of these paths validate that `beneficiary` can actually receive native ETH before crediting/decrementing escrow accounting is finalized through a reverting external call. Similarly, `_fillCrossChain` and `_fillSameChain` send native output funds directly to `order.output.beneficiary` via `_sendValue`/inline `.call`, which also reverts on failure: [3](#0-2) [4](#0-3) 

Since a user places the order (and sets `order.user`/`order.output.beneficiary`) themselves, and the same beneficiary is used for both fill delivery and refund/cancellation, if that address is (or later becomes, e.g. via `SELFDESTRUCT`-based redeploys or proxy upgrades that remove a `receive` function) unable to accept a plain ETH transfer, then:
1. The cross-chain `RedeemEscrow`/`RefundEscrow` message delivered via `onAccept` will revert every time it is processed by the ISMP host's message dispatch, since `_withdraw`'s internal call fails and there is no try/catch — this is functionally identical to the report's core defect ("if the recipient address is a contract that cannot handle the pool tokens, the funds are lost") except here it manifests as a hard revert that blocks settlement rather than a silent loss.
2. Because ISMP `onAccept` calls that revert are typically retried by relayers, this creates a permanently un-deliverable message — the escrowed native ETH can never be released, and it can also never be refunded through `_cancelFromSource`/`_cancelSameChain` since those funnel through the same `_withdraw`/`_sendValue` logic.
3. There's no alternate governance/keeper recovery path in `IntentsBase.sol`/`ExtrinsicIntents.sol`/`IntrinsicIntents.sol` to sweep native ETH stuck in this state to the rightful owner in an ERC20-wrapped/pull-based manner.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any unprivileged user simply by placing (or filling) an order whose native-token beneficiary is a contract that cannot receive plain ETH. The escrowed principal (the user's or protocol's native ETH) becomes permanently locked in the `IntentGatewayV2` contract with no way to fill, cancel, or refund it — satisfying the "permanent freezing of funds" bar. This is a stronger and more concretely exploitable instance of the analog bug class than the referenced report (which describes silent token loss on success) because here it also creates a route that becomes unable to deliver/settle the cross-chain message.

### Likelihood Explanation
Likelihood is high on any chain/order combination that allows `token == address(0)` (native ETH) inputs/outputs, which is explicitly supported (`order.inputs`/`order.output.assets` allow `bytes32(0)` for native token, as seen throughout `IntentGatewayV2Test.sol`/`IntentGatewayV2SameChainTest.sol`). Any user (attacker or accidentally) can set `order.user`/`order.output.beneficiary` to a contract without a payable `receive`/`fallback` (or one that intentionally reverts), triggering the freeze on the very first `RedeemEscrow`/`RefundEscrow`/cancel attempt. No special privileges or race conditions are required — a single `placeOrder` transaction combined with the natural fill/cancel/settlement lifecycle is sufficient.

### Recommendation
Do not let a failed native transfer to `beneficiary` permanently block escrow accounting/settlement. Options:
1. Use a pull-payment pattern for native ETH: on failure of `.call{value: amount}("")`, credit an internal `pendingWithdrawals[beneficiary] += amount` mapping instead of reverting, and expose a separate `withdrawPending()` function beneficiaries (or anyone on their behalf) can call, possibly wrapping to WETH.
2. Alternatively, wrap failed native sends into WETH and transfer the ERC20 equivalent, which virtually all contracts can hold even without a `receive` function.
3. Ensure this fallback applies uniformly to `_withdraw` (in `IntentsBase.sol`), `_fillCrossChain` (`ExtrinsicIntents.sol`), and `_fillSameChain`/`_cancelSameChain` (`IntrinsicIntents.sol`), so that cross-chain settlement messages via `onAccept` cannot be perpetually stuck/un-retryable due to an unreceivable beneficiary.

### Proof of Concept
1. User calls `placeOrder` with a native-ETH input (`token = bytes32(0)`) and sets `order.user` to be recovered as `msg.sender` — but for the output/beneficiary side, or in a scenario where the order is later cancelled and refunded, the relevant beneficiary address is a contract `Bad` with no `receive()`/`fallback()` (or one that always reverts).
2. Order expires; `cancelOrder` → `_cancelSameChain` (same-chain) or the cross-chain GET-response path → `onGetResponse` → `withdraw`/`_withdraw` is invoked with `beneficiary = Bad`.
3. `_withdraw`/`withdraw` executes `(bool sent,) = beneficiary.call{value: amount}(""); if (!sent) revert InsufficientNativeToken();` — see: [5](#0-4) [6](#0-5) 
4. Since `Bad` cannot accept ETH, the call fails and the entire transaction (including the ISMP `onAccept`/`onGetResponse` delivery or the `cancelOrder` call) reverts. There is no alternative code path to release these escrowed native funds — every future attempt to withdraw, refund, or settle this order's escrow will revert identically, permanently freezing the ETH in the `IntentGatewayV2` contract.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
