### Title
Missing empty-body check before `body[0]` index causes an unguarded array-index revert in `IntentGatewayV2.onAccept` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.onAccept` reads `incoming.request.body[0]` to determine the `RequestKind` before validating that `body` is non-empty and before checking the message source. An attacker who can get any PostRequest routed to this contract's address (as `to`) with a zero-length `body` — dispatched from any source state machine, since the source check happens only after this line for privileged kinds — causes a Solidity array-index-out-of-bounds panic, reverting the entire `onAccept` call.

### Finding Description
This is the closest reachable analog to CVE-2018-18828's pattern: a decoder indexes into attacker-controlled buffer data without first validating the buffer's length, causing an out-of-bounds access when the crafted input is a degenerate/short case. Here:

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    ...
``` [1](#0-0) 

No `incoming.request.body.length == 0` guard exists before the index access, unlike other decode paths in the codebase that carefully guard against empty/short inputs (e.g. the RLP node decoder's regression fix for `empty HP-encoded partial key`, [2](#0-1) , or the Pharos SPV proof's `nibble_at_depth` bounds guard, [3](#0-2) ).

`onAccept` is invoked by the host (`onlyHost`) whenever a PostRequest whose `to` field targets this contract is delivered via `HandlerV2.handlePostRequests`. The source-authorization check (`keccak256(incoming.request.source) != keccak256(...hyperbridge())`) only happens *after* the `RequestKind` decode and only gates the privileged branches (`NewDeployment`, `UpdateParams`, `SweepDust`); it does not protect the initial `body[0]` read. Any state machine can dispatch a PostRequest with `to = IntentGatewayV2` and an empty `body`, and any relayer submitting the resulting message-delivery proof triggers the revert.

### Impact Explanation
Solidity's array-index-out-of-bounds access on `bytes calldata` produces a panic that reverts the entire transaction. Since message delivery (`HandlerV2.handlePostRequests`/`batchCall`) commonly processes multiple PostRequests together for gas efficiency, a single attacker-crafted zero-length-body request targeting `IntentGatewayV2` can revert the whole batch, denying delivery of every other legitimate message bundled in that transaction. This matches the "route unable to deliver messages" acceptance criterion — an attacker can grief relayers and block intent fills/refunds for other users by forcing repeated batch reverts unless relayers learn to isolate and skip the poisoned message.

### Likelihood Explanation
High: dispatching an empty-body PostRequest costs the attacker only the source-chain dispatch fee, is fully permissionless (a "single submitted transaction, extrinsic, dispatched request" per the validation criteria), and requires no special privilege or state proof forgery — the malicious request is genuinely delivered and provable.

### Recommendation
Add an explicit length check at the top of `onAccept` (e.g., `if (incoming.request.body.length == 0) revert InvalidRequestBody();`) before indexing `body[0]`, mirroring the length checks already present elsewhere in this codebase's decode paths (RLP node codec, Pharos SPV proof depth checks). Additionally, move the `source == hyperbridge` authorization check ahead of any decode step that is only valid for privileged callers, and consider validating `body.length` for each `RequestKind`'s expected minimum size before calling `abi.decode` on `body[1:]`.

### Proof of Concept
1. On any source state machine, dispatch a `PostRequest` with `to = <IntentGatewayV2 address>`, `body = ""` (zero length), and any `source`.
2. Relay this request together with other legitimate PostRequests in a single `HandlerV2.handlePostRequests`/`batchCall` transaction (or standalone).
3. `onAccept` executes `uint8(incoming.request.body[0])` on the empty `bytes calldata`, which reverts with an out-of-bounds panic.
4. The entire transaction (including any other batched, legitimate messages) reverts, so no messages in that batch are delivered.

Note: I was not able to execute this against a live/test deployment to confirm no upstream guard (e.g. in `HandlerV2` or `EvmHost`) rejects zero-length bodies before dispatch to `onAccept`; based on the code reviewed, no such guard exists on this path, but a background Devin session with full repo/build access would be needed to run the Foundry test suite and confirm this end-to-end.
