Based on my review of the webhook signature-verification path in `lib/shopify_api/webhooks/`, I found a concrete analog to the report's bug class: a field ("shop") that the application logic trusts and acts on, while not being covered by the HMAC that is supposed to authenticate the request.

### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is trusted but not covered by HMAC verification, enabling cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating an HMAC computed only over the raw request body [1](#0-0) , then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all pulled from unauthenticated HTTP headers — to build the `WebhookMetadata` handed to the app's handler [2](#0-1) . `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, `api_version` are read straight from headers without being part of the signed content [3](#0-2) . The equality that should hold — "shop bound in HMAC" == "shop acted upon by the handler" — is broken: the HMAC binds only the body bytes, not the shop identity.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header using `OpenSSL.secure_compare` [4](#0-3) . For webhooks, `to_signable_string` is defined as the raw body only [5](#0-4) , whereas `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from `shopify-*`/`x-shopify-*` headers [6](#0-5) . `Registry.process` only checks that the body's HMAC is valid, then dispatches to the handler using the unauthenticated header values to identify the topic and shop for the event [2](#0-1) .

Because the body content and the `hmac-sha256` value are the only two things bound together, any request with a **valid (body, hmac) pair for one shop** can be replayed against the app's public webhook endpoint with an arbitrary `shopify-shop-domain` header value substituted, and the signature will still validate — since `shop` never enters the signature computation. Any Shopify merchant can install the app on their own store, capture one authentic webhook `(body, hmac)` pair sent to the app (this is entirely self-service and requires no privileged access), and then resend that exact payload to the app's public webhook endpoint while swapping the `shopify-shop-domain` header to a victim shop's domain (and/or the `shopify-topic`/`shopify-webhook-id` headers). `Utils::HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will invoke the handler with `WebhookMetadata.new(topic: <attacker-chosen>, shop: <victim-shop>, body: <attacker's own signed body>, ...)`.

### Impact Explanation
Apps commonly key their tenant data, session lookups, or side effects (e.g., "mark shop X uninstalled", "update shop X's order/inventory cache") off `WebhookMetadata#shop`. Since `shop` is not bound by the HMAC, an attacker can forge webhook events that the app attributes to any victim shop, using only a legitimately signed body they obtained from their own (attacker-controlled) shop's webhook traffic. This is a cross-tenant data-integrity/confusion vulnerability: it lets an unprivileged user (any merchant who installs the app) inject fabricated data associated with a different tenant's identity, which the app will treat as authentic because HMAC validation passed. Depending on how the host app uses the topic/shop (e.g., `app/uninstalled` triggering token revocation, or order/customer data being written against a shop-keyed store), this can enable cross-tenant state corruption.

### Likelihood Explanation
High — no secret material is needed. An attacker needs only: (1) the ability to install the app on a shop they control (trivial, self-service, unprivileged) and observe one webhook `(body, hmac)` pair sent to the app's public endpoint, and (2) network access to POST to that same public endpoint with a modified `shop`/`topic` header. No credential, admin API access, or knowledge of `api_secret_key` is required.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed content used by `HmacValidator`, or otherwise cryptographically bind them to the payload (e.g., verify HMAC over a canonical string of `body + shop + topic`, not body alone), so header values cannot be swapped independently of the signed body. At minimum, `Webhooks::Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate `shop` and `topic` into the signed string, matching what Shopify's HMAC actually protects.

### Proof of Concept
1. Install the target app on an attacker-controlled dev/trial shop (`attacker-shop.myshopify.com`) and trigger any webhook (e.g., `orders/create`) to be delivered to the app's public webhook endpoint.
2. Capture the raw POST request Shopify sends, including the `shopify-hmac-sha256` header and raw body — this HMAC is valid because the app's `Utils::HmacValidator.validate` will accept it (computed only over body bytes, per `lib/shopify_api/utils/hmac_validator.rb`).
3. Replay this exact `(body, hmac)` pair to the app's webhook endpoint again, but change the `shopify-shop-domain` header to `victim-shop.myshopify.com` (and optionally `shopify-topic` to another registered topic).
4. Observe that `ShopifyAPI::Webhooks::Registry.process` still passes HMAC validation (per `lib/shopify_api/webhooks/registry.rb` line 190) and invokes the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the signed body actually belongs to the attacker's own shop — demonstrating the shop binding is not enforced by the cryptographic signature.
