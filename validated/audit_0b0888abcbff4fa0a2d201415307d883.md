### Title
Webhook `shop-domain` header (and `topic`/`webhook-id`/`api-version`) is not covered by HMAC verification, allowing cross-tenant shop-attribution spoofing via webhook replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`, `webhook_id`, `api_version`) values it hands to the app's handler are taken from unauthenticated HTTP headers that are never included in the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header — it never touches `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`Registry.process` then trusts `request.shop` (and the other unauthenticated headers) directly when constructing the data handed to the app's webhook handler: [4](#0-3) 

The resulting `WebhookMetadata.shop` field — which apps use to determine which merchant/tenant the payload belongs to — is not bound to the HMAC-verified bytes at all: [5](#0-4) 

Because a single `api_secret_key` is shared across *every* shop that installs the app, any unprivileged internet user can install the app on their own store, capture a legitimate webhook delivery for their own shop (valid body + valid HMAC signed with the app's shared secret), and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, so `Registry.process` will dispatch the attacker-controlled body to the app's handler labeled as belonging to the victim shop. This breaks the equality the app relies on: `shop authenticated via HMAC == shop attributed to the payload`.

### Impact Explanation
This is a cross-tenant confusion primitive: an attacker-controlled payload (their own shop's real webhook data) can be delivered to an app's webhook handler while impersonating a different, victim shop. Any app that uses `WebhookMetadata#shop` to select which tenant's database row/session to update (a documented and expected usage pattern) can be tricked into writing or acting on attacker data under another merchant's identity — a cross-tenant access/data-integrity violation using only the gem's own webhook processing pipeline, no leaked credentials, TLS interception, or privileged access required.

### Likelihood Explanation
Exploitation requires only the ability to (1) install the target app on an attacker-owned store (a normal, unprivileged action for any app listed on a public storefront/App Store, or a custom app the attacker controls) to obtain one legitimately HMAC-signed webhook body, and (2) send an HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header — both are within reach of an ordinary internet-facing attacker with no special access.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified signable content, or otherwise cryptographically tie the claimed shop to the verified payload (e.g., require the shop domain to be embedded/signed inside the request body/JWT and reject mismatches), instead of trusting the standalone `X-Shopify-Shop-Domain` header.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture a legitimate webhook POST, e.g. body `{"id":1,...}` with header `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the identical body and HMAC header to the same app endpoint, changing only:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` passes because it only checks `raw_body` against `hmac` (both unchanged and still valid).
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...))`, causing the app to process attacker data under the victim shop's identity.
