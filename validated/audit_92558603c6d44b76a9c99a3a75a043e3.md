Webhook tenant identity (`shop`, `topic`, `webhook_id`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, but the merchant identity (`shop`), `topic`, and `webhook_id` fields that the gem hands to the app's handler are parsed straight from HTTP headers that are never part of the signed material. Any party who can obtain one genuine `(raw_body, hmac)` pair from Shopify (trivially available to any developer who installs their own app on their own store) can replay that exact body/HMAC to the victim app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the gem will accept it as authentic and dispatch it to the handler tagged with the attacker-chosen shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is read from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body` — no shop domain, topic, or webhook id is included in the signed material. `shop`, `topic`, and `webhook_id` are all read from separate, unauthenticated headers via `shopify_header`: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `HMAC(secret, to_signable_string) == received hmac`: [3](#0-2) 

`Registry.process` gates purely on this HMAC check, then builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` — none of which were part of the verified bytes — and dispatches it to the app's handler: [4](#0-3) 

The documented usage pattern explicitly instructs apps to trust `data.shop` as the tenant identity for downstream processing (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`shop_that_produced_the_HMAC-verified_bytes == shop_the_gem_reports_to_the_handler`

Since `shop` (and `topic`/`webhook_id`) is not covered by the signature, these two values can diverge under attacker control.

### Impact Explanation
This breaks the cross-tenant boundary the gem is supposed to enforce for its consuming app: an attacker who runs their own Shopify store (an "unprivileged internet user" relative to the victim app/merchant) can trigger a real webhook from Shopify for their own shop, capture the `(raw_body, X-Shopify-Hmac-Sha256)` pair (both are delivered over the wire to the attacker's own endpoint or observable via the attacker's own app logs), then replay that exact body and HMAC to the victim app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming the victim shop. The HMAC validation passes (same body, same valid signature), and the gem hands the app a `WebhookMetadata` claiming the data belongs to the victim shop. Any app that keys per-tenant storage, authorization, or business logic off `WebhookMetadata#shop` (exactly as the gem's own docs recommend) will process attacker-controlled body content under the victim's tenant context — a cross-tenant data injection/confusion primitive.

### Likelihood Explanation
Moderately likely to be exploitable in real deployments: the prerequisite (having a genuine app installation on some shop, even the attacker's own free/dev store, to harvest one valid signed webhook body) is cheap and requires no privileged access to the victim. The webhook endpoint is by design internet-reachable and unauthenticated apart from this HMAC check. The main constraint is that the attacker's forged body must still be a well-formed payload the handler expects for the topic being spoofed, but since the attacker fully controls the content of their own shop's webhook events (product/order data etc.), this is easy to satisfy.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically tie the `shop-domain`/`topic`/`webhook-id` headers to the verified payload before exposing them to the handler — e.g., include the headers in `to_signable_string`, or independently verify that `request.shop` corresponds to a shop with an active app installation/session known to the app before dispatching. At minimum, update `lib/shopify_api/webhooks/request.rb`/`registry.rb` so `WebhookMetadata#shop` cannot be sourced from a header that lies outside the domain covered by `Utils::HmacValidator.validate`, and document to consuming apps that `data.shop` must not be treated as authenticated for tenant-scoping decisions unless this binding exists.

### Proof of Concept
1. Attacker installs their own test app (or uses `shopify_api` on their own dev store) and registers a webhook, e.g. `orders/create`.
2. Attacker triggers an order event on their own store; Shopify delivers a webhook POST to the attacker's endpoint with a valid `X-Shopify-Hmac-Sha256` header computed over the raw JSON body using the shared `client_secret`.
3. Attacker crafts the raw body content in their own store to contain whatever payload fields they want (they fully control content of their own store's resources).
4. Attacker replays the exact same raw body and `X-Shopify-Hmac-Sha256` value to the victim app's webhook controller endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. Inside the victim app, `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the (correctly signed, replayed) HMAC — [6](#0-5) .
6. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: attacker_controlled_json, ...)` to the app's handler, which (per the gem's documented pattern) trusts `data.shop` as the tenant to act on.
