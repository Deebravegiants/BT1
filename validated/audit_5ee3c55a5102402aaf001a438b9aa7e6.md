### Title
Mixed-subject biometric capture set assembled without identity-continuity check - (src/plans/biometric_capture/mod.rs)

### Summary
`run_check`/`run` in `src/plans/biometric_capture/mod.rs` assembles a `Capture` from independently-populated per-side slots (`left_ir`, `left_rgb`, `right_ir`, `right_rgb`, `self_custody_candidate_rgb`) with no cross-check binding all slots to a single, continuously-tracked subject. An unprivileged attacker can have two different people alternate in front of the sensor between objectives (left-eye vs right-eye) to produce a `Capture` blending frames from two identities. The one nominal downstream safeguard, the fraud-detection pipeline that consumes `face_identifier_fraud_checks`, is a stub in this build (`detect_fraud` always returns `Ok(false)`; `N_FRAUD_CHECKS = 0`), so nothing rejects the mixed-identity capture before signup/enrollment.

### Finding Description
`Plan::run` drives objectives sequentially (`set_next_objective`, `objectives: VecDeque<Objective>`), alternating `target_left_eye` per `Objective` (`src/plans/biometric_capture/mod.rs:602-615`). Each objective independently fills `self.left_ir`/`self.left_rgb` or `self.right_ir`/`self.right_rgb` via `handle_ir_net`/`handle_rgb_net` (lines 217-287) purely based on per-frame image-quality thresholds (`IRIS_SCORE_MIN`, brightness range, `perceived_side` match) — there is no check that the left-eye frames and right-eye frames (or the self-custody face frame from `handle_face_identifier`, lines 289-323) originate from the same physical person across time. `run_check` (lines 485-501) only tracks whether all `Objective`s in the queue have been satisfied and advances to the next objective — it contains zero identity/subject-continuity logic. The only inter-objective gate is `valid_capture_after = Instant::now() + delay_between_eye_captures` (200 ms, `DEFAULT_DELAY_BETWEEN_EYE_CAPTURES`), which per its doc comment exists only "to defend against inaccuracies in IR-Net, which lead to accepting the same eye as the second capture" — a debounce, not an identity check.

`into_capture` (lines 557-600) then unconditionally merges `left_ir`, `left_rgb`, `right_ir`, `right_rgb`, and `self_custody_candidate_rgb` into one `Capture`, regardless of which physical subject produced each slot.

Downstream, `biometric_pipeline::Plan` does send `frame_left`, `frame_right`, and `frame_self_custody_candidate` together to the `face_identifier::Input::Estimate` Python model (`src/plans/biometric_pipeline/mod.rs:517-536`), which could in principle detect a mismatch via `FraudChecks`. However, the consumer of that output, `detect_fraud` in `src/plans/mod.rs:1392-1406`, explicitly discards all fraud signal:
```
// FOSS: WE HAVE DELETED ALL FRAUD CHECKS
Ok(false)
```
and `fraud_check.rs` backs this with `N_FRAUD_CHECKS: usize = 0`, `fraud_checks() -> []`. So even if the Python model flagged cross-identity inconsistency internally, that signal is never wired into `fraud_detected`/`SignupReason::Fraud` in this build.

### Impact Explanation
A `Capture` (and subsequently a `Pipeline` and enrolled `PersonalCustodyPackages`) can be assembled from iris/face frames belonging to two different individuals: e.g., left iris + left face from person A, right iris + right face + self-custody face from person B. This corrupts the uniqueness/biometric-record guarantee central to Worldcoin/Orb's identity model — the resulting enrollment binds two people's biometric material to one signup record, undermining "one iris code = one person" invariants. This matches an Immunefi-class "biometric record blending two identities" impact.

### Likelihood Explanation
Feasibility requires only physical presence at the Orb during a normal signup session (unprivileged attacker per the rules), timed to swap between the left-eye and right-eye capture objectives (which are seconds apart and separated only by a 200 ms debounce). No token/key leakage, operator access, or hardware tampering is needed. It is repeatable across signup attempts since `run_check`'s logic is deterministic and stateless with respect to subject identity.

### Recommendation
Add explicit identity-continuity enforcement in `biometric_capture::Plan`:
- Track a per-objective face/eye embedding or landmark-consistency signature (e.g., via the RGB-Net face bbox/embedding already available) and reject/reset a slot if `handle_ir_net`/`handle_rgb_net`/`handle_face_identifier` observe a discontinuity relative to previously captured slots for the same signup.
- Alternatively/additionally, restore and wire the `face_identifier_fraud_checks` (left/right/self-custody consistency) result into `detect_fraud` so a real fraud signal blocks `SignupReason::Fraud` before `enroll_user`/PCP upload, instead of the current unconditional `Ok(false)`.
