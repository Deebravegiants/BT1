### Title
Silent zero-share stake donation on `add_stake` permanently forfeits an existing delegator's deposit - (File: `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary
`delegation_pool::add_stake` transfers a delegator's coins into the underlying stake pool and only afterwards attempts to mint proportional `pool_u64` shares via `buy_in_active_shares`. When the share-rounding math yields `0` new shares, the code silently discards the mint instead of reverting, exactly mirroring the `AdapterBase` bug class (deposit succeeds, `0` shares minted, assets lost).

### Finding Description
`add_stake` performs the transfer and underlying stake increase unconditionally, then computes shares: [1](#0-0) 

`buy_in_active_shares` computes `new_shares = pool.active_shares.amount_to_shares(coins_amount)` and, if it rounds down to `0`, returns early without minting anything and without reverting: [2](#0-1) 

The rounding-down conversion is implemented in `pool_u64::amount_to_shares_with_total_coins`, which floors `coins_amount * total_shares / total_coins`: [3](#0-2) 

After the buy-in call, `add_stake` only asserts `assert_min_active_balance(pool, delegator_address)`, which checks the delegator's *total* current balance, not that new shares were actually minted for this specific deposit: [4](#0-3) 

For a delegator who already holds shares worth more than `MIN_COINS_ON_SHARES_POOL` (from an earlier deposit), this assertion is satisfied by their pre-existing balance regardless of whether the new deposit minted any shares. Once the stake pool has accrued rewards, `total_coins > total_shares` in the `active_shares` pool (each existing share is worth more than 1 coin), so any sufficiently small `add_stake` amount (down to the coin's smallest indivisible unit, octas) rounds to `0` new shares. The coins have already been irreversibly transferred to the pool address and staked via `stake::add_stake` before the rounding-to-zero is discovered, and since there is no re-check that `new_shares > 0` for the *specific* deposit, the transaction completes successfully: the depositor's coins increase `total_coins` (and are thus split among all other existing shareholders' shares) while the depositor's own share balance is unchanged.

This directly matches the report's custody invariant: "a deposit must not silently consume assets while minting zero shares of value back to the depositor." Here that invariant is broken for the `add_stake` custody flow of Aptos' native delegation-pool staking.

### Impact Explanation
An existing delegator with a balance above the minimum threshold who submits (or is tricked/automated into submitting, e.g. via dApp rounding, dust re-staking of rewards, or "top-up" flows) a sufficiently small `add_stake` amount will have that amount permanently and non-recoverably transferred out of their control into the shared stake pool, with zero shares credited back to represent it — a direct, unrecoverable loss of custody over APT that is silently redistributed to the pool's other shareholders. This is a custody-accounting corruption (value moves to the wrong holders — the rest of the pool — instead of the depositor) affecting a live, mainnet-relevant asset-management path (delegated staking of APT).

### Likelihood Explanation
Likelihood depends on the deposit size relative to `total_coins/total_shares` share price of the specific pool at call time. Because APT precision is 8 decimals (octas) and staking pools accrue rewards continuously (making the share price strictly increase over time, i.e., `total_coins > total_shares` once any reward epoch has passed), there is always some small positive `coins_amount` window that rounds to `0` shares once the pool has existed and earned rewards for enough epochs. Practical likelihood is higher for older, high-TVL delegation pools where the coins/shares ratio has drifted furthest from `1`, and for automated wallets/dApps that batch-stake reward dust or perform frequent very small top-ups.

### Recommendation
In `buy_in_active_shares` (and the analogous `buy_in_pending_inactive_shares`), fail the operation instead of silently discarding the deposit when `new_shares == 0` and `coins_amount > 0`, or refund/reject the transfer in `add_stake` before it is committed to the stake pool. At minimum, `add_stake` should assert that `new_shares > 0` whenever `coins_amount - add_stake_fee > 0`, ensuring the transaction reverts atomically rather than silently donating the depositor's stake to other shareholders.

### Proof of Concept
1. A validator's delegation pool has been active long enough to have earned rewards, so `active_shares.total_coins > active_shares.total_shares` (share price > 1 octa/share).
2. Delegator Alice already holds shares worth `> MIN_COINS_ON_SHARES_POOL` from an earlier `add_stake` call, satisfying `assert_min_active_balance` independent of any new deposit.
3. Alice calls `add_stake(delegator, pool_address, amount)` with a small `amount` such that `(amount - add_stake_fee) * total_shares / total_coins` floors to `0` (achievable at the octa level whenever the price ratio is unfavorable enough), see the flooring math in `pool_u64::amount_to_shares_with_total_coins` [5](#0-4) .
4. `aptos_account::transfer` and `stake::add_stake` execute, moving Alice's coins into the pool and increasing `total_coins` in the underlying stake pool [6](#0-5) .
5. `buy_in_active_shares` returns `0` without minting shares and without aborting [7](#0-6) .
6. `assert_min_active_balance` passes because Alice's pre-existing balance already exceeds the minimum, so the transaction succeeds.
7. Alice's `amount` of APT is now part of the pool's `total_coins`, proportionally benefiting all other shareholders' share value, while Alice's own share count — and thus her redeemable balance — is unchanged. Alice has permanently lost `amount` of APT with nothing credited back.

**Uncertainty note:** I was unable to locate the exact numeric value of `MIN_COINS_ON_SHARES_POOL` or the precise `get_add_stake_fee` formula in the indexed content (searches for these constants returned no direct matches in `delegation_pool.move`), which are needed to pin an exact minimal reproducing `amount` on a live pool. A Devin session with full file access would be needed to compute a concrete numeric PoC value and confirm no additional un-indexed guard exists between the transfer and the rounding check.

    /// Buy shares into the active pool on behalf of delegator `shareholder` who
    /// deposited `coins_amount`. This function doesn't make any coin transfer.
    fun buy_in_active_shares(
        pool: &mut DelegationPool,
        shareholder: address,
        coins_amount: u64,
    ): u128 acquires GovernanceRecords {
        let new_shares = pool.active_shares.amount_to_shares(coins_amount);
        // No need to buy 0 shares.
        if (new_shares == 0) { return 0 };

        // Always update governance records before any change to the shares pool.
        let pool_address = get_pool_address(pool);
        if (partial_governance_voting_enabled(pool_address)) {
            update_governance_records_for_buy_in_active_shares(pool, pool_address, new_shares, shareholder);
        };

        pool.active_shares.buy_in(shareholder, coins_amount);
        new_shares
    }

    /// Return the number of new shares `coins_amount` can buy in `self` with a custom total coins number.
    /// `amount` needs to big enough to avoid rounding number.
    public fun amount_to_shares_with_total_coins(self: &Pool, coins_amount: u64, total_coins: u64): u64 {
        // No shares yet so amount is worth the same number of shares.
        if (self.total_coins == 0 || self.total_shares == 0) {
            // Multiply by scaling factor to minimize rounding errors during internal calculations for buy ins/redeems.
            // This can overflow but scaling factor is expected to be chosen carefully so this would not overflow.
            coins_amount * self.scaling_factor
        } else {
            // Shares price = total_coins / total existing shares.
            // New number of shares = new_amount / shares_price = new_amount * existing_shares / total_amount.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(coins_amount, self.total_shares, total_coins)
        }
    }
