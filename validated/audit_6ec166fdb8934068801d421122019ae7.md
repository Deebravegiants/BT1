### Title
Direct ERC20 donations (USDC, LT, or launched Token) to `Zap` are permanently unrecoverable — no sweep/rescue mechanism exists - ([File: packages/contracts/src/Zap.sol])

### Summary
`Zap` holds USDC, LT, and launched-Token balances transiently during `buy`/`sell`/`createToken` flows, but any asset sent to it outside those flows (a stray/accidental `transfer`) has no recovery path. Unlike `FeeVault` (`sweepDonations`) and `Bonding` (`_sweepLTToOwner`/`LTRescued`), `Zap` defines no admin or permissionless sweep function for any token it can hold.

### Finding Description
`Zap` is a UUPS-upgradeable, `Ownable2StepUpgradeable` contract whose only owner-gated function is `setFees` [1](#0-0) . There is no `sweep`, `rescue`, or `recoverERC20` function anywhere in the contract — confirmed by inspecting the full public/external surface (`createToken`, `createTokenWithPermit`, `buy`, `buyWithPermit`, `sell`, `sellWithPermit`, `setFees`, and view functions) [2](#0-1) .

Within the normal flows, every USDC/LT/Token balance the contract briefly holds is fully accounted for and forwarded out (unused USDC refund, fee refund, LT-excess refund, token payout) [3](#0-2) . But nothing prevents an unprivileged wallet from directly calling `IERC20(usdc).transfer(zapAddress, amount)`, `IERC20(lt).transfer(zapAddress, amount)`, or `IERC20(launchedToken).transfer(zapAddress, amount)` outside of any Zap function call. Such a donation sits on `Zap`'s balance permanently: no owner-only sweep, no `sweepDonations`-style permissionless surplus-sweep (as `FeeVault` has, gated by an accrual-tally check) [4](#0-3) , and no `_sweepLTToOwner`-style rescue (as `Bonding` has for stray/rebalance LT during graduation, emitting `LTRescued`) [5](#0-4) .

This is the direct alt.fun analog of the external report's bug class: `Comet`/`Bulker` can receive ETH but have no way to sweep it back out; here, `Zap` can receive ERC20 assets (USDC, LT, launched Token) via ordinary `transfer` calls but has no equivalent recovery mechanism, even though the sibling contracts `FeeVault` and `Bonding` were explicitly hardened against exactly this class of stuck-fund scenario.

### Impact Explanation
Any USDC, LT, or launched-Token balance accidentally or mistakenly sent directly to `Zap`'s address (e.g., a bot or frontend integration error, a user sending funds to the wrong contract, or dust left behind by a future code path that doesn't fully drain its own balance) is permanently frozen with no path to recovery, even by the protocol owner. This is a permanent loss of trader/creator funds, matching the "permanent freezing of trader, creator or LP funds" acceptance criterion. Severity is bounded by the fact that this requires an out-of-band transfer rather than a flaw reachable purely through `buy`/`sell`/`createToken` arguments, but the resulting loss is total and irreversible for whatever is sent.

### Likelihood Explanation
Moderate: `Zap` is the advertised user-facing entry point and its address is widely referenced (frontend, bots, integrators). Given three donatable asset types (USDC, any LT, any launched Token) and no restriction on who can call `IERC20.transfer(zap, amount)`, accidental transfers are a realistic and recurring occurrence in a live system — exactly the scenario the team already anticipated and mitigated for `FeeVault` and `Bonding`, but not for `Zap`.

### Recommendation
Add an owner-only (or permissionless-but-owner-directed, mirroring `FeeVault.sweepDonations`) rescue function to `Zap` that can sweep any ERC20 balance not currently earmarked for an in-flight user refund. Since `Zap`'s functions are `nonReentrant` and fully settle balances by the end of each call, a simple `sweep(address token, uint256 amount)` restricted to `onlyOwner`, transferring to a fixed treasury/owner address, would close this gap without introducing a way to steal in-flight user funds (there is never a legitimate non-zero balance persisted across transactions in the current design).

### Proof of Concept
1. An external wallet (not the Zap contract) calls `usdc.transfer(address(zap), 1_000e6)` directly, bypassing `Zap.buy`/`sell`/`createToken`.
2. `Zap.usdc().balanceOf(address(zap))` now includes this 1,000 USDC on top of any transient in-flight balance.
3. No function on `Zap` (owner or public) can move this balance out: `setFees` only mutates fee parameters [1](#0-0) ; every other external function is scoped to a specific trader's `buy`/`sell`/`createToken` accounting and reads/writes only the amounts computed within that call, never a stray pre-existing balance.
4. The 1,000 USDC (or an equivalent donation of LT or a launched Token) remains stuck in `Zap` indefinitely — contrast with the equivalent donation to `FeeVault`, which can be recovered via `sweepDonations()` [6](#0-5) , or to `Bonding`, where stray/rebalance LT is recovered via `_sweepLTToOwner` during `finalizeGraduation` [5](#0-4) .

    /// @notice Sweep unbacked USDC (donations) to `feeTo`. Required because
    ///         direct USDC transfers would otherwise inflate `balanceOf` above
    ///         the accrual tally and silently mask the `accrue` underfund
    ///         check. Permissionless — funds always go to the admin-set `feeTo`.
    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit DonationsSwept(feeTo_, amount);
    }

    /// @dev Send LT held by this contract above `keep` to the owner,
    ///      emitting `LTRescued`. Called at the end of
    ///      `finalizeGraduation` with `keep = protectedLT` (any escrow
    ///      that doesn't belong to this graduation), so only THIS
    ///      graduation's rebalance residue lands on the owner. No-op on
    ///      the empty-pair fast path (nothing to sweep).
    function _sweepLTToOwner(
        address lt,
        uint256 keep
    ) internal {
        uint256 bal = IERC20(lt).balanceOf(address(this));
        if (bal <= keep) return;
        uint256 amount = bal - keep;
        address recipient = owner();
        IERC20(lt).safeTransfer(recipient, amount);
        emit LTRescued(lt, recipient, amount);
    }
