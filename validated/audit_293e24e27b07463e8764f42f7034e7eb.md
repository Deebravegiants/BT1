### Title
Unvalidated user identifier format in signup-extension QR-code path bypasses backend verification - (File: `src/plans/qr_scan/user.rs`, `src/plans/mod.rs`)

### Summary
The external report describes a Gravity faucet bug where a destination address string is accepted without validating it conforms to the required bech32 format, allowing malformed identifiers into a critical flow. The closest analog in `orb-core` is in the user/operator QR-code parsing for the "signup extension" (data-acquisition) flow: the regex used to extract `user_id` (`QR_CODE_SIGNUP_EXTENSION`) accepts an arbitrary string (`[a-z0-9_-]+`) instead of enforcing the UUID format that the field is documented and normally expected to have, and this unvalidated identifier is accepted directly into the signup flow without any backend verification call.

### Finding Description
The normal, non-extension QR parsing path (`QR_CODE_V2`) strictly enforces a UUID-like structure for `user_id`: [1](#0-0) 

However, the signup-extension regex used for the "internal-data-acquisition" feature relaxes this constraint to an arbitrary alphanumeric/underscore/hyphen string with no length or UUID-shape enforcement: [2](#0-1) 

The struct's own doc comment states the field must be "in format of 128-bit UUIDv4", but nothing enforces this for the signup-extension path: [3](#0-2) 

A test in the same file explicitly demonstrates that a non-UUID string (`"data_acquisition_mode_focus_sweep"`) is accepted as a valid `user_id` through this code path: [4](#0-3) 

Critically, when both the operator and user QR codes are in "signup extension" mode, `handle_user_qr_code` skips the normal backend verification (`verify_user_qr_code`, which calls the backend to validate the QR code and fetch real user cryptographic keys) and instead returns a default, unauthenticated `UserData` directly built from the unvalidated `user_id`: [5](#0-4) 

Compare this to the standard flow, where `verify_user_qr_code` is always invoked to authenticate the QR code and identity against the backend: [6](#0-5) 

This unvalidated `user_id` string is later used as material for the enrollment signature (hashed alongside biometric data and signed by the secure element) and forwarded to the backend as the signup identifier: [7](#0-6) 

### Impact Explanation
Because the signup-extension path bypasses the backend identity/authorization check (`verify_user_qr_code`) entirely and accepts any string matching `[a-z0-9_-]+` as `user_id`, biometric capture and signature/enrollment data can be bound to an arbitrary, non-authenticated, non-UUID identifier chosen by whoever generates the QR code. This is directly analogous to the unvalidated bech32 destination address issue: a critical identifier field is not format-validated and is trusted downstream without corroborating checks, risking cross-signup/state confusion (data or biometric signatures associated with a bogus or attacker-chosen identity string) rather than a clean failure. This differs from the vanilla QR path, which both enforces UUID format and always performs backend verification of the identity before any biometric linkage occurs.

### Likelihood Explanation
This code path is gated behind the `internal-data-acquisition` Cargo feature and requires both operator and user QR codes to opt into "signup extension" mode, so it is not exercised in the default production configuration. Within builds where this feature is enabled (used for controlled data-acquisition sessions), any operator/tester capable of generating a QR code that matches the loose regex can trigger this path without further authentication, since the feature intentionally short-circuits the standard backend verification call.

### Recommendation
Enforce the same UUID-format validation on `user_id` in `QR_CODE_SIGNUP_EXTENSION` as is used in `QR_CODE_V2`, and require `verify_user_qr_code`/backend authorization even when `signup_extension` mode is active, rather than substituting a `UserData::default()` derived purely from unauthenticated client-supplied input.

### Proof of Concept
Using the existing unit test as a demonstrable PoC: parsing the QR-code string `"userid:data_acquisition_mode_focus_sweep:1::2:7::"` through `Data::try_parse`/`Data::from_signup_extension` succeeds and yields `user_id == "data_acquisition_mode_focus_sweep"` — a value that is not a UUID and would fail the strict `QR_CODE_V2` regex — yet this value flows unmodified into `handle_user_qr_code`'s signup-extension branch, bypassing `verify_user_qr_code`, and ultimately into `make_signature`'s SHA-256 hash used for the secure-element signature in `enroll_user.rs`. [4](#0-3)

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
