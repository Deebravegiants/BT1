### Title
Unauthenticated TCP livestream listener discloses another user's raw biometric camera frames to attacker-chosen IP - ([File: src/agents/livestream/upstream.rs])

### Summary
The `livestream` agent binds an unauthenticated `TcpListener` on `0.0.0.0:9201` [1](#0-0) . Any TCP client that connects is treated as `Event::Connected(addr)`, and the broker immediately creates `Downstream::new(addr.ip())`, which configures a GStreamer `udpsink` to stream all subsequent camera frames (IR eye/face, RGB, thermal, depth) to that IP over UDP with no authentication or allowlist check [2](#0-1) [3](#0-2) .

### Finding Description
`Upstream::poll_next` accepts any incoming TCP connection unconditionally via `self.listener.poll_accept(cx)` and emits `Event::Connected(addr)` with the peer's raw socket address, without checking credentials, tokens, or any operator/user QR-code binding [4](#0-3) . In `Agent::run`, on receiving `Event::Connected(addr)` the broker logs the connection and unconditionally does `downstream = Some(Arc::new(Downstream::new(addr.ip())?))`, replacing/overwriting any previous session [5](#0-4) . From that point, every camera frame processed by the loop (`gpu.render(events, move |buffer| downstream.push(&buffer))`) is streamed over UDP to `addr.ip()` at port 9200 [6](#0-5) [7](#0-6) . There is no allowlist, token, TLS, or pairing check anywhere in this path — `Downstream::new` only uses the peer IP to configure `udpsink`'s `host` property.

However, this capability is gated entirely behind compile-time and CLI opt-in mechanisms that are not attacker-controlled:
- The entire `livestream` module only compiles when the `livestream` Cargo feature is enabled: `livestream = ["dep:egui", "dep:egui-wgpu", "dep:egui-phosphor"]`, and the broker's `livestream` field itself only exists `#[cfg(feature = "livestream")]` [8](#0-7) [9](#0-8) .
- Even with the feature compiled in, the agent is only started when the operator explicitly passes the `-l`/`--livestream` CLI flag, which then calls `orb.enable_livestream()` [10](#0-9) [11](#0-10) .
- This feature is documented in `Cargo.toml` as "used for internal development ONLY... not used for normal orbs" and explicitly described as "Enable livestream agent to debug cameras" [12](#0-11) .

So while the code path itself genuinely lacks any authentication (confirming the technical claim), reaching it requires the orb operator to explicitly opt in via a debug/R&D CLI flag on a build with the `livestream` feature compiled — this is not a state reachable by an "unprivileged network client" alone under normal production orb operation. Production orbs are not expected to run with `-l`.

### Impact Explanation
If this debug listener were active on a production orb with the flag enabled, an unprivileged attacker on the same network segment could indeed intercept another user's IR-eye/IR-face/RGB/thermal/depth biometric imagery mid-signup by simply opening a TCP connection to port 9201 and having frames redirected to their own IP over UDP on port 9200. This matches a biometric-data-disclosure impact category if it occurred on a production/fielded orb.

### Likelihood Explanation
Likelihood on a real deployed orb is low-to-none because the vulnerable code path is dead unless: (1) the binary is compiled with the internal `livestream` Cargo feature, and (2) the orb operator explicitly passes the `--livestream` CLI flag intended only for internal camera-debugging sessions. There is no evidence in the repo of this flag being enabled in production signup flows; it's explicitly called out as an internal-development-only feature. Absent operator/build-level enablement, no unprivileged network client can reach `Event::Connected` at all in a real production signup.

### Recommendation
If this feature must remain available for debugging, add mutual authentication (e.g., pre-shared token or TLS client cert) checked in `Upstream::poll_next`/`Event::Connected` handling before creating `Downstream`, and bind the listener to localhost or a debug-only interface rather than `0.0.0.0`. Regardless, ensure production/release builds never compile the `livestream` feature and never pass `--livestream`, and consider adding a build-time or runtime assertion preventing this feature from being enabled on production-signed images.

### Proof of Concept
Not applicable as a production security finding: reproducing the disclosure requires building with `--features livestream` and running the binary with `--livestream`, which is an internal debug configuration, not something reachable by an unprivileged remote attacker against a stock production orb. A test confirming the *lack of authentication* within that debug path could spin up `Agent::run`, connect a bare `TcpStream` to port 9201, and assert `Downstream::new` is called with the attacker's IP with no token exchanged — but this only demonstrates the debug tool has no auth, not an exploitable production vulnerability given the required opt-in flag.

impl Downstream {
    #[allow(clippy::cast_possible_truncation)]
    pub fn new(addr: IpAddr) -> Result<Self> {
        let video_info =
            VideoInfo::builder(VideoFormat::Bgrx, LIVESTREAM_FRAME_WIDTH, LIVESTREAM_FRAME_HEIGHT)
                .build()?;
        let pipeline = Pipeline::with_name("livestream");
        let appsrc = AppSrc::builder().caps(&video_info.to_caps()?).build();
        let nvvidconv = ElementFactory::make("nvvidconv").build()?;
        let nvv4l2h264enc = ElementFactory::make("nvv4l2h264enc").build()?;
        let rtph264pay = ElementFactory::make("rtph264pay").build()?;
        let udpsink = ElementFactory::make("udpsink").build()?;
        pipeline.add_many([
            appsrc.upcast_ref(),
            &nvvidconv,
            &nvv4l2h264enc,
            &rtph264pay,
            &udpsink,
        ])?;
        nvv4l2h264enc.set_property_from_str("insert-sps-pps", "1");
        nvv4l2h264enc.set_property_from_str("insert-vui", "1");
        udpsink.set_property_from_str("host", &addr.to_string());
        udpsink.set_property_from_str("port", &PORT.to_string());
        appsrc.link(&nvvidconv)?;
        nvvidconv.link(&nvv4l2h264enc)?;
        nvv4l2h264enc.link(&rtph264pay)?;
        rtph264pay.link(&udpsink)?;
        pipeline.set_state(gstreamer::State::Playing)?;
        appsrc.set_block(true);
        Ok(Self { pipeline, appsrc, video_info })
    }
