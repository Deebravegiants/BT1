### Title
Cross-chain replay of `SubstrateCalldata` signatures in `pallet-hyper-fungible-token` due to missing chain/domain binding - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler authenticates an attached `runtime_call` by verifying a `MultiSignature` over `(account_nonce, runtime_call)` only. No chain-identifying data (genesis hash, `StateMachine` id, spec name/version, or any other domain separator) is included in the signed payload, so the exact same signed authorization is valid on every chain that runs this pallet with the same `EvmToSubstrate` conversion — a direct analog of the reported `Factory.sol` bug where `signedOnly` hashed `msg.sender/templateName/initdata` without `block.chainid`.

### Finding Description
`on_accept` decodes an optional `SubstrateCalldata { signature, runtime_call }` from the incoming cross-chain `Message.data` and, when a signature is present, verifies it like this: [1](#0-0) 

For every signature scheme (Ed25519, Sr25519, ECDSA) the signed message is constructed purely as:
```rust
let payload = (nonce, substrate_data.runtime_call.clone()).encode();
``` [2](#0-1) 

`nonce` is `frame_system::Pallet::<T>::account_nonce(beneficiary)` — the destination account's local system nonce, which is a per-account, per-chain counter, not a global or chain-specific value: [3](#0-2) 

There is nothing in the payload binding it to a specific chain — no genesis hash, no `StateMachine`/parachain id, no contract/source binding, unlike standard Substrate extrinsics which use `CheckGenesis`/`CheckSpecVersion`/`CheckMortality` to prevent exactly this kind of replay. The pallet's own docs confirm it is designed to be deployed identically "on any chain": [4](#0-3) 

`SubstrateCalldata` is defined with no chain-scoping field either: [5](#0-4) 

`call_data` is a free-form, attacker-controlled field of `SendParams` supplied by whoever calls `send()` — it is not tied to the specific sender who produced the signature: [6](#0-5) 

Because the signed payload is only `(nonce, runtime_call)`, the same signed blob a user creates to authorize a call on one deployment of this pallet (e.g. parachain A) remains a valid authorization on any other deployment (parachain B, or the same chain after a runtime migration/fork) for as long as the beneficiary account's nonce on the second chain matches the nonce that was signed — which is trivially true for any account that has not yet transacted on that chain (nonce 0 is the common case for freshly-bridged recipients).

### Impact Explanation
Any party that observes a `SubstrateCalldata` blob (they are embedded in a public `PostRequest.body`, dispatched and relayed over Hyperbridge, hence visible on-chain and to relayers) can replay it by calling `send()` (or by having a relayer deliver an equivalent `PostRequest`) to a different chain/instance of the pallet that recognizes the same source contract for `ContractToAsset`, causing the victim's originally-signed `runtime_call` to be dispatched as `RawOrigin::Signed(beneficiary)` on that unintended chain: [7](#0-6) 

This is an unauthorized app action: a user who signed a call intending it for use only on one specific chain can have the identical privileged dispatchable (e.g. governance vote, staking bond/unbond, `proxy::add_proxy`, asset transfer, etc., subject only to `BaseCallFilter`) executed as themselves on a different chain without their consent, wherever the beneficiary account's nonce happens to line up (nonce 0 for a first-time recipient being the trivial case).

### Likelihood Explanation
Likelihood is high in the intended deployment topology: the pallet is explicitly designed to run identically "on any chain" bridging to the same EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contracts, so multiple live instances sharing account-derivation logic (`EvmToSubstrate`) are the expected, documented setup rather than an edge case. No special privilege is required — any user that submits a `send()` with attached calldata is exposed, and any third party who can read the resulting request body (which travels over the public Hyperbridge relay network) can attempt the replay on a sibling chain.

### Recommendation
Include a chain-domain separator in the signed payload, mirroring what `CheckGenesis`/`CheckSpecVersion` provide for ordinary extrinsics — e.g. bind the signature to `(genesis_hash_or_state_machine_id, nonce, runtime_call)`:
```rust
let payload = (
    T::StateMachineId::get(), // or frame_system::Pallet::<T>::block_hash(0)
    nonce,
    substrate_data.runtime_call.clone(),
).encode();
```
This ensures a signature produced for one chain deployment of `pallet-hyper-fungible-token` cannot be replayed to authorize the same call on any other chain.

### Proof of Concept
1. Two parachains, A and B, both run `pallet-hyper-fungible-token` configured identically (same `EvmToSubstrate`, same registered `ContractToAsset` mapping to the same EVM `HyperFungibleToken` contract), per the documented integration pattern.
2. Victim bridges tokens from EVM to parachain A specifying `beneficiary` = `V` (a never-before-used account, `nonce = 0`) and attaches `SubstrateCalldata { signature: sig_over(0, call), runtime_call: call }`, intending `call` (e.g. `pallet_balances::transfer_keep_alive(to: trusted_party, amount)`) to run only on chain A.
3. Attacker observes the `PostRequest.body` (public via Hyperbridge relaying/indexing) and extracts the exact `data` bytes.
4. Attacker calls `send()` to parachain B with the same `beneficiary` address `V` and reuses the identical `call_data` bytes. On parachain B, `V`'s account also has `nonce = 0` (fresh bridging recipient), so:
   `sp_io::crypto::{ed25519,sr25519,secp256k1_ecdsa}_verify(sig, keccak256((0, call).encode()), V)` succeeds exactly as it did on chain A.
5. `runtime_call.dispatch(RawOrigin::Signed(V))` executes on parachain B — the victim's authorization, scoped in their mind to chain A only, is replayed to trigger an identical dispatchable as `V` on chain B, which the victim never approved for that chain.
