### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (tenant identity) is read from an unauthenticated header. `Registry.process` validates the HMAC over the body and then trusts `request.shop` — sourced from that unauthenticated header — to build the `WebhookMetadata` passed to the host application's handler. This breaks the intended binding: `HMAC(secret, raw_body) == valid` should imply `(raw_body, shop) is authentic`, but in fact the shop value is never part of what is verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, with no relation to the HMAC: [2](#0-1) 

`Registry.process` validates the request via `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., the raw body) and compares against the computed HMAC — never touching `shop`: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `request.shop` (the unauthenticated header value) is placed directly into `WebhookMetadata`, which is the tenant-identifying value the host application's `WebhookHandler#handle` receives and is expected to trust for per-shop dispatch: [5](#0-4) 

The broken binding, as an equality that should hold but does not:
`HMAC_valid(raw_body) == true` should imply `shop_header == shop_that_produced(raw_body)`; instead `shop` is orthogonal to the HMAC check.

### Impact Explanation
An unprivileged internet user who can obtain one genuine `(raw_body, hmac)` pair for *any* shop (e.g., their own free/development store installing the vulnerable app) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. Because `Registry.process` only checks the HMAC of the body and then trusts `request.shop` for dispatch, the host application will process/attribute that webhook payload as if it came from a different, victim shop — a cross-tenant identity confusion. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up which merchant's data to update/redact), this can lead to cross-tenant data corruption or incorrect redaction/processing under another shop's identity.

### Likelihood Explanation
Medium. The webhook endpoint is a public, unauthenticated HTTP endpoint (this is standard/expected for Shopify webhooks — the HMAC is normally the entire protection). Exploitation requires the attacker to source one legitimate `(body, hmac)` pair, which any attacker with a webhook-capable shop can generate themselves at will (e.g., mandatory `customers/redact` or their own app-uninstall webhook), then replay it toward the target app with a forged shop header. No access token, `api_secret_key`, or privileged account is required — only a network request with a modified header.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or verify it independently after HMAC validation:
- Include the `shop-domain` header (and ideally `webhook_id`/`topic`) in `to_signable_string`, or
- After HMAC validation, cross-check `request.shop` against an authoritative source (e.g., look up the session/shop associated with the specific `webhook_id`, since Shopify's real webhook subscriptions are shop-scoped) before constructing `WebhookMetadata`, rejecting any mismatch.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a genuine webhook POST with a valid `X-Shopify-Hmac-Sha256` header computed over the raw body by Shopify using the app's shared secret.
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the raw body only) — this still matches since the body is unchanged. [6](#0-5) [1](#0-0) 
4. `WebhookMetadata` is built with `shop: request.shop` = `"victim.myshopify.com"` (attacker-controlled header) and dispatched to the host app's handler as if it were an authentic webhook from the victim shop. [7](#0-6)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
