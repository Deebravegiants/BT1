### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) fields are trusted from unauthenticated headers while HMAC only covers the raw body, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process` verify the webhook's authenticity using an HMAC that is computed only over the raw request body, but the `shop` attribution used to route/process the webhook is read from an HTTP header that is never included in that signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC and then immediately hands the un-covered `shop` header straight to the app's handler as trusted tenant identity: [2](#0-1) 

The `shop` value itself comes straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding to the body or to the HMAC: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `hmac-verified bytes == bytes the app attributes to a shop`. In this implementation the equality is broken: `hmac == HMAC(secret, raw_body)` but `shop == header["x-shopify-shop-domain"]`, an independent, unauthenticated field. Because a single app's webhook signing secret (`Context.api_secret_key`) is shared across every shop that has the app installed, any merchant who legitimately installs the app receives real webhooks with valid HMACs for their own shop's payload. That merchant (an unprivileged actor with respect to any other tenant) can capture one of their own genuine webhook deliveries — HMAC and body intact — and replay it to the app's webhook endpoint after only changing the `x-shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body: [5](#0-4)  and the forged `shop` value is passed through unchanged to `WebhookMetadata`, so the host application processes attacker-supplied body content believing it originates from the victim shop.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): a webhook payload genuinely produced for shop A can be replayed and attributed to shop B purely by tampering with an unauthenticated header, since neither `shop`, `topic`, `api_version`, nor `webhook_id` are covered by the signature. Depending on how the host application keys its state off `WebhookMetadata#shop` (e.g. updating billing status, uninstall handling, order/customer records, GDPR data-request routing), this allows one tenant to poison or corrupt another tenant's data/processing using only its own legitimately-issued webhook traffic — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Any merchant who installs the app (a normal, unprivileged action) can obtain a validly-HMACed webhook body/signature pair for their own shop and replay it with a modified `shop` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged access is required — only a header modification on a captured legitimate request, which is straightforward for anyone able to install the app.

### Recommendation
Include `shop` (and ideally `topic`/`api_version`/`webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind the shop identity to the verified payload (e.g., by using Shopify's per-request payload verification that ties the shop to the signed content) rather than trusting a separate, unauthenticated header for tenant attribution.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, so the app registers webhooks and shares the app's `api_secret_key` for HMAC signing across all installs.
2. Shopify sends the attacker's app instance a genuine webhook, e.g. `orders/create`, with headers:
   - `x-shopify-hmac-sha256: <valid HMAC over raw body>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
3. Attacker intercepts/replays this exact request to the app's public webhook endpoint, changing only:
   - `x-shopify-shop-domain: victim.myshopify.com`
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds (see [6](#0-5) ).
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker-controlled data>, ...)` and processes it as if it were victim's legitimate webhook data.

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
