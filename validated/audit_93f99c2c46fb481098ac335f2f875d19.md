## Title
Webhook shop/topic identity spoofing via unsigned headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields come from HTTP headers that are never covered by the HMAC. `Webhooks::Registry.process` accepts any request whose body/HMAC pair validates and then dispatches to the handler using the unauthenticated `shop` and `topic` header values, breaking the binding between "HMAC-authenticated bytes" and "tenant identity acted upon."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the raw body) against the secret-derived signature: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then hands the *header-derived, unsigned* `shop` and `topic` straight to the app's handler: [4](#0-3) 

Because every shop that installs the same app shares the single app-level `api_secret_key`, any merchant who installs the app (an "unprivileged internet user" from the perspective of other tenants of the app) legitimately receives real, correctly-signed webhook deliveries for their own shop. Since the HMAC signs only the body bytes, that same attacker can capture one of their own genuine `(raw_body, hmac)` pairs and replay it to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain or a more sensitive topic. `HmacValidator.validate` still returns `true` because the raw body it checks is unchanged and correctly signed by the shared secret. `Registry.process` then invokes the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop and/or `topic` set to a value not represented by the actual body — an identity/tenant binding break: the shop value acted upon by the handler is not the shop whose data actually produced the HMAC-verified bytes.

This is the exact bug class described in the report's family (a check validates one thing — HMAC over bytes — while the security-relevant field consumed downstream — shop/topic — is a separate, unauthenticated input), applied here to `Webhooks::Registry`/`Webhooks::Request` rather than fork choice.

### Impact Explanation
Any application built on this gem that uses the `shop` (or `topic`) exposed on `WebhookMetadata` to select which tenant's session/access token to load, or to gate tenant-scoped side effects (e.g., `app/uninstalled` cleanup, `customers/data_request`/`shop/redact` GDPR handling, inventory or order mutation triggers keyed off the webhook shop), can be made to perform those actions against a shop the attacker does not own. This is a cross-tenant confusion vulnerability: the security decision (which tenant's data/session to touch) is made using bytes that were never authenticated as belonging to that tenant.

### Likelihood Explanation
Any merchant who installs the app can trivially obtain a genuinely-HMAC-signed webhook delivery for their own store (this happens automatically via normal use), then craft an HTTP request to the app's public webhook endpoint with the same body/HMAC but a different `shop-domain`/`topic` header. No access token, `client_secret`, or privileged access is required — only the ability to install the target app on a shop the attacker controls and send an HTTP request, which is unprivileged-internet-user level access.

### Recommendation
Bind the `shop` (and ideally `topic`) to the signature verification, e.g., by requiring the host application to independently confirm that the `shop` in the webhook belongs to a shop with a known, previously-stored session before trusting it, and/or by having `Utils::VerifiableQuery`/`HmacValidator` include the `shop` and `topic` header values in the signable string used for HMAC comparison so any header tampering invalidates the signature. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are not covered by the HMAC and must be cross-checked against a durable, previously-established shop/session record before being trusted for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify delivers a genuine webhook, e.g. body `{"id":1}` with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of body with app's api_secret_key>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
2. Attacker replays the identical raw body and HMAC header to the app's public webhook endpoint but rewrites:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` constructs a `Webhooks::Request`, and `HmacValidator.validate` succeeds because it only compares the (unchanged) body against the (unchanged, valid) HMAC: [4](#0-3) 
4. The registered handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload and signature originated from `attacker-shop.myshopify.com` — demonstrating the broken identity binding.
