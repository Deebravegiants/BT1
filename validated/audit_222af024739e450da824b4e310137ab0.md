### Title
Unchecked ERC20 `transfer` return value in Tron `IntentGatewayV2.withdraw()` lets escrow release silently fail while accounting marks the order filled/refunded - permanent loss of filler/user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` on the Tron variant of the intents contract redeems escrowed input tokens to the filler (on `RedeemEscrow`) or refunds the user (on `RefundEscrow`/cancel-via-GET) using a raw low-level `.call()` to the ERC20 `transfer` selector, checking only that the call did not revert (`success`), never decoding/asserting the returned boolean. Any ERC20 that returns `false` on failure instead of reverting will silently fail the transfer while the contract's accounting proceeds as if payment succeeded: `_filled[commitment]` is set, the escrow ledger `_orders[commitment][token]` is decremented, and `EscrowReleased`/`EscrowRefunded` is emitted. The intended recipient (filler or user) never receives the tokens and has no way to reclaim them, since the order is now marked filled and the escrow entry is already zeroed.

### Finding Description
`withdraw()` is invoked from `onAccept` (`evm/tron/contracts/apps/IntentGatewayV2.sol:629-635`) for `RedeemEscrow`/`RefundEscrow` requests delivered by any relayer with a valid ISMP proof, and from `onGetResponse()` (line 738-743) for cross-chain cancellations. In the withdraw body:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();

_orders[body.commitment][token] -= amount;
``` [1](#0-0) 

`success` here reflects only whether the external call reverted, not the ERC20 `transfer` return value. This differs materially from the sibling EVM implementation, which uses `SafeERC20.safeTransfer` throughout `_withdraw` in `IntentsBase.sol`:

```solidity
_orders[body.commitment][token] = escrowed - amount;
...
IERC20(token).safeTransfer(beneficiary, amount);
``` [2](#0-1) 

`SafeERC20.safeTransfer` reverts on both a low-level call failure and on a `transfer` call that returns `false`, guaranteeing the accounting update and the transfer are atomic. The Tron `withdraw()` path drops that guarantee: for any ERC20 token deployed on Tron's EVM-compatible chain that returns `false` rather than reverting on failure (a common non-standard-but-legal ERC20 behavior, e.g., when the sender/contract balance is insufficient or the recipient is blacklisted), the low-level `.call()` still returns `success = true` (the call executed without reverting), so `TransferFailed()` is never raised. The function then decrements the escrow ledger and, for a fill, permanently marks `_filled[commitment] = beneficiary` — finalizing the order — even though the beneficiary received nothing.

This is the same root-cause shape as the referenced Ajna finding: an accounting/state update ("payment complete") is committed without confirming that the actual value transfer occurred, so the intended recipient's reward/escrow is irrecoverably lost. Here it is reachable from a single relayed ISMP `PostRequest` (permissionless relaying is Hyperbridge's design — any relayer can submit a proof for `RedeemEscrow`/`RefundEscrow`) or a routine cross-chain cancellation `GetResponse`, i.e. by an ordinary unprivileged user/filler flow with no admin or malicious-party involvement required — the trigger is simply a token whose `transfer` implementation returns `false` on failure.

The `DustSwept` / `SweepDust` path (lines 661-682) has the identical unchecked-success pattern, compounding the exposure for any token used with this contract.

### Impact Explanation
- A filler who redeems escrow after fulfilling an order (`RedeemEscrow`) can be permanently denied their input-token payout: the order is marked filled and `_orders[...] -= amount` is committed, but no tokens move if the token's `transfer` returns `false`.
- A user whose order is cancelled/refunded (`RefundEscrow`, or a cross-chain cancel through `onGetResponse`) can lose their entire escrowed principal the same way — the refund is marked complete but the funds stay stuck in the contract, inaccessible to anyone since the escrow accounting has already been zeroed and the order finalized.
- This is a concrete freezing/loss of user and filler funds with no path to retry, since post-`withdraw` state (`_filled`, decremented `_orders`) makes the commitment appear settled.

### Likelihood Explanation
Occurs whenever the escrowed/paid-out token's `transfer()` can return `false` instead of reverting on failure (a legal ERC20 pattern, not limited to malicious tokens) combined with any condition that causes the internal transfer to fail — e.g., a temporary balance mismatch from prior dust handling, a blacklisted beneficiary address, or a token that pauses transfers. No admin, governance, or malicious relayer action is required; the vulnerable code path executes on ordinary `fillOrder`→escrow-redeem and `cancelOrder` flows, triggered by permissionless relayers delivering standard Hyperbridge messages.

### Recommendation
Replace the raw `.call()` + `success`-only check in `withdraw()` (and in the `SweepDust` handler) with `SafeERC20.safeTransfer`/`safeTransferFrom`, mirroring the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures a `transfer` that returns `false` reverts the whole `onAccept`/`onGetResponse` call, which — per the ISMP delivery model documented in `docs/content/protocol/ismp/requests.mdx:113-115` and enforced by `EvmHost.dispatchIncoming` (`evm/src/core/EvmHost.sol:794-818`) — leaves no request receipt and keeps the message retryable, instead of silently finalizing a failed payout.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an escrow token whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., an intentionally non-standard ERC20, or any token contract paused/blacklisting the beneficiary at the time of withdrawal).
2. A user places a cross-chain order with that token escrowed via `placeOrder`.
3. A filler fills the order on the destination chain; the source-chain `IntentGatewayV2` receives a `RedeemEscrow` `PostRequest` through `onAccept` → `withdraw(body, false)` (`evm/tron/contracts/apps/IntentGatewayV2.sol:629-635, 691-714`).
4. Arrange for the token's `transfer(beneficiary, amount)` call to return `false` (not revert) — e.g., blacklist the filler's address in the token contract, or drain the contract's balance via a reentrant dust-sweep in the same block.
5. Observe: `success` is `true` (external call did not revert), so `TransferFailed()` is never thrown; `_orders[commitment][token] -= amount` executes; `_filled[commitment] = beneficiary`; `EscrowReleased` is emitted — yet `token.balanceOf(beneficiary)` is unchanged and the escrowed amount is now unrecoverable, since the commitment is marked filled and its escrow reduced to zero elsewhere.
