## Finding

### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body, but the `shop` tenant identifier that is subsequently trusted and dispatched to the app's handler is read from an HTTP header that is **not** included in the HMAC-signed data. This breaks the binding `hmac-authenticated bytes == identity used downstream`, allowing a party who can obtain one validly-signed webhook delivery to relabel it as coming from a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop` is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never mixed into the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the app's `WebhookHandler`: [3](#0-2) 

`HmacValidator.validate` computes the signature using `Context.api_secret_key`, which is the app's single `client_secret` shared across **every** shop that has installed the app — it is not a per-shop secret: [4](#0-3) 

Because (a) the signing secret is shared across all tenants of the app and (b) the `shop` header is excluded from the signed payload, a valid `(raw_body, hmac)` pair obtained from one shop's webhook delivery remains cryptographically valid when replayed with a different `shop-domain` header. `Registry.process` will pass this forged shop identity straight into `WebhookMetadata` and the registered handler, with no code path anywhere in `lib/shopify_api/webhooks/**` cross-checking `request.shop` against the HMAC-covered body.

This is the same class of defect as the report's core issue: a value that participates in downstream trust decisions (there, the `NDS` bound used to gate loop execution; here, the `shop` identity used to gate per-tenant handling) is not properly validated/bound, so the safety property the mechanism is supposed to enforce silently fails.

### Impact Explanation
This is a cross-tenant integrity break: an attacker who controls a shop that has installed the vulnerable app (i.e., can trigger a legitimate, validly-HMAC-signed webhook for their own shop) can capture that `(raw_body, hmac)` pair and re-POST it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop. Since the header is not covered by the signature, `Utils::HmacValidator.validate(request)` still returns `true`, and the app processes attacker-controlled webhook data (topic, body) under the victim shop's identity. Depending on the handler's logic, this can lead to data being written to, or actions being taken against, a different tenant's account — a cross-tenant access/data-integrity violation, which the rules classify as Critical.

### Likelihood Explanation
Any app author using this gem must implement a `WebhookHandler` and typically uses `WebhookMetadata#shop` to route data/records to the correct tenant record — this is the intended and documented usage. Because the gem provides `request.shop` as an already-"validated" value once `HmacValidator.validate(request)` passes, downstream code has no reason to independently re-verify tenant binding, making the exploit straightforward for anyone who is a legitimate merchant/tenant of the target app (an "unprivileged internet user" with respect to *other* tenants' data).

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signable material, or otherwise cryptographically bind the header-derived `shop` value to the signed body before trusting it in `Registry.process`. At minimum, document and enforce that consumers must not treat `request.shop` as authenticated on its own, and consider deriving/validating the shop domain from a value that is included in the signed payload wherever the webhook topic supports it (e.g. compliance topics that include shop info in-body).

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and on `victim-shop.myshopify.com`, both sharing the same `api_secret_key`.
2. Attacker triggers any webhook for their own shop (e.g., `products/update`) and captures the raw POST: headers (`X-Shopify-Topic`, `X-Shopify-Hmac-Sha256: <hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`) and body.
3. Attacker resends the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` builds `to_signable_string` from `@raw_body` only [1](#0-0) ; `HmacValidator.validate` succeeds because body and secret are unchanged [5](#0-4) .
5. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the app to process attacker-supplied data under the victim tenant's identity.
