## Finding: Webhook `shop-domain` and `topic` are not covered by the HMAC signature, enabling cross-tenant webhook forgery/replay

This is the strongest analog to the reported bug class ("a field acted on but not covered by the HMAC"): the gem's webhook layer validates the HMAC only against the raw request body, while the `shop` and `topic` values that the host application actually acts on are taken from unauthenticated HTTP headers.

### Title
Webhook shop/topic identity not bound to HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `HmacValidator` covers the body bytes exclusively. However, `shop`, `topic`, `webhook_id`, and `api_version`, which are the identity/routing fields dispatched to the host app's handler via `WebhookMetadata`, are read directly from HTTP headers that carry no cryptographic binding to that signature.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers with no cross-check against the signed payload: [3](#0-2) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the received `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) 

`Registry.process` then trusts the header-derived `topic` and `shop` unconditionally once the body HMAC passes, and dispatches them straight to the app's handler: [5](#0-4) 

The identity binding that should hold is:
`HMAC_valid(body) == true` should imply `shop_header == shop_that_produced(body)` and `topic_header == topic_that_produced(body)`.

Because the app's `client_secret` (used as the HMAC key) is a single shared secret across **all shops** that install the app — not a per-shop secret — a valid `(body, hmac)` pair legitimately received for one tenant (e.g., a webhook delivered to the attacker's own installed shop) remains cryptographically valid when replayed with different `shop-domain`/`topic` headers. `HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will hand the forged `shop`/`topic` combination to the handler as if it were authentic.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce. Any actor who has legitimately received one authentic webhook body+HMAC pair from Shopify for the app (e.g., because they run their own store that has the app installed) can replay that exact body to the app's public webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop and/or the `x-shopify-topic` header to a different topic. The signature check still passes, and the host application's webhook handler processes attacker-chosen `(shop, topic, body)` combinations as authentic Shopify traffic for a shop the attacker does not control — a cross-tenant data/authorization confusion (e.g. injecting an `orders/create` or `app/uninstalled` event attributed to a victim's tenant record).

### Likelihood Explanation
Exploitation requires only: (1) being an unprivileged merchant/user who can install the target app on their own store to legitimately receive one signed webhook, and (2) sending a raw HTTP POST with modified headers to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is required. This is fully reachable by an unprivileged internet actor.

### Recommendation
Bind the routing/identity headers into the signed material, or otherwise verify them independently of the raw-body HMAC:
- Include `shop`, `topic`, and `webhook_id` in the string that `to_signable_string` returns (Shopify already sends them; the app just needs to fold them into what's verified) rather than trusting them from unauthenticated headers, or
- Cross-check the header-derived `shop` against a shop that is known to have installed the app (e.g., an existing stored session) before invoking the handler, rejecting the request if there's no matching install, or
- At minimum, document/require that webhook handler implementations independently verify `data.shop` against their own session/tenant store before acting on webhook content, since `Registry.process` currently offers no such guarantee.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker sends a raw HTTP POST directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid since only `B` is signed)
   - Header `x-shopify-shop-domain: victim.myshopify.com` (forged)
   - Header `x-shopify-topic: orders/create` (unchanged or forged to another topic string)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `H` against `B`.
4. The app's registered handler is invoked with `WebhookMetadata` claiming `shop: "victim.myshopify.com"`, even though the payload never originated from that shop, letting the attacker inject cross-tenant webhook events into the host application.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
