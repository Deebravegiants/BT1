### Title
Webhook shop-domain and topic headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw HTTP body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values used to route and attribute the webhook to a specific merchant are read straight from unauthenticated HTTP headers. `Registry.process` trusts these header-derived values once the body HMAC checks out, allowing an attacker who owns a *single* legitimately-signed `(body, hmac)` pair to relabel it as belonging to any other shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled from headers that are never part of the signed content: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., the raw body), and nothing else: [3](#0-2) 

`Registry.process` performs this single HMAC check and then unconditionally forwards the header-derived `shop`, `topic`, `webhook_id`, and `api_version` to the app's handler as `WebhookMetadata`: [4](#0-3) 

The identity binding that should hold is: `shop` used to attribute/act on the webhook == `shop` cryptographically bound to the signed bytes. Instead, only `raw_body` is bound to the HMAC; `shop` (and `topic`) are unauthenticated header values that can be freely rewritten by anyone who can reach the app's public webhook endpoint, as long as they supply *any* previously valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` for a body they legitimately received (e.g., from their own store's webhook delivery, which any merchant installing the app can trigger).

### Impact Explanation
An unprivileged internet user who has installed the target app on their own store (a normal, non-privileged action) can capture one genuine `(raw_body, hmac)` pair delivered by Shopify. They can then POST that exact `raw_body` and `hmac` header to the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name an arbitrary victim shop. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` will hand the attacker-controlled body to the handler tagged as belonging to the victim shop/topic. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up the merchant's session/access token or to write data scoped to that shop), this breaks the shop-to-signed-content binding and can result in cross-tenant data injection/attribution — data intended for one merchant being processed and stored under another merchant's identity.

### Likelihood Explanation
Reaching the webhook endpoint requires no privileges beyond normal internet access, and obtaining one valid `(body, hmac)` pair only requires installing the app on any store the attacker controls (a standard, unprivileged action for public apps). No secrets, tokens, or elevated access are required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the signed content, or otherwise verify these header values against Shopify's known good values (e.g., cross-check `shop` against a shop already known to the app for that specific delivery, or include the header values in the signable string per Shopify's documented webhook verification guidance) before trusting them for routing or data attribution in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` that Shopify sent to the app's webhook endpoint.
2. Attacker sends a new POST request directly to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks `B` against `H` — validation passes.
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches it to the app's handler, which processes `B`'s content as if it authentically originated from the victim shop.
