### Title
Unbounded octal wavelength parameter from QR code causes panic in overcapture extension parsing - (File: src/plans/biometric_capture/overcapture.rs)

### Summary
The `overcapture` biometric-capture extension derives its configuration from a `wavelength` parameter that is embedded in a user-scanned QR code and passed through unbounded/unvalidated integer parsing before being used in an `assert_eq!` that can panic, mirroring the reported bug class of "unbounded and invalidly bounded system parameters may cause undefined behavior."

### Finding Description
When a QR code encodes a signup-extension configuration, `qr_scan::user::Data::from_signup_extension` extracts a free-form `parameters` string directly from the regex capture group of the scanned code, with no bounds validation on its contents [1](#0-0) .

This `parameters` string is later consumed by the `overcapture::Plan` constructor, which splits it on `:` and feeds the first component into `parse_u8_octal`, defaulting to `1` on parse failure but otherwise accepting **any** valid octal `u8` value (0–255) with no bound check against the expected 3-bit range: [2](#0-1) [3](#0-2) 

The resulting `wavelength_parameter: u8` is then passed to `Configuration::new` / `parse_wavelength_configuration`, which formats it as a zero-padded binary string and asserts that it is exactly 3 characters long: [4](#0-3) 

`format!("{configuration_value:0>3b}")` only pads to a *minimum* width of 3; for any `configuration_value` greater than 7 (i.e., requiring more than 3 bits, up to 255 for a `u8`), the resulting binary string will be longer than 3 characters, causing `assert_eq!(binary_repr.chars().count(), 3, ...)` to fail and **panic**. Because the octal parser (`u8::from_str_radix(src, 8)`) happily accepts multi-digit octal strings like `"377"` (=255 decimal) or even `"10"` (=8 decimal, which already produces a 4-character binary string `"1000"`), a QR code containing a signup-extension parameter such as `mode:overcapture,parameters:10:5000` (or any wavelength value ≥ 8) will reach this `assert_eq!` and crash the process, since this code path is only reachable via feature `internal-data-acquisition`, which is compiled into non-FOSS/internal builds per `Cargo.toml` feature flags referenced throughout `src/plans/mod.rs`, `src/plans/idle.rs`, and `src/plans/qr_scan/user.rs`.

### Impact Explanation
This is an unprivileged-user-reachable input: any person presenting a QR code to the orb during the signup/idle QR-scan flow controls the raw string that eventually becomes `wavelength_parameter`, and no boundary is enforced between the QR-code-derived octal string and the 3-bit domain the `parse_wavelength_configuration` function assumes. A crafted QR code can panic the orb-core process during signup, denying service to the legitimate operator/user session (a fraud/liveness-enforcement disruption analog: it interrupts the biometric capture flow that includes fraud/liveness checks), consistent with the report's concern that unbounded parameters "increase the risk of undefined system behavior" and unexpected reverts/crashes.

### Likelihood Explanation
Likelihood is Low-Medium: it requires the `internal-data-acquisition` feature to be compiled in, and requires an attacker (or malfunctioning tool) to craft a QR code with a signup-extension mode set to `Overcapture` and a wavelength value ≥ 8. Given the code is gated by a feature flag intended for internal/data-acquisition builds (not necessarily all production fleets), exploitability depends on deployment configuration, which could not be fully confirmed from the indexed code alone.

### Recommendation
Bound-check the parsed octal wavelength value against the valid 3-bit range (0–7) in `parse_u8_octal`/`Configuration::new` and return a safe default or reject the signup extension gracefully instead of using `assert_eq!` (which panics) when the derived binary representation is not exactly 3 bits. More generally, validate all QR-code-derived numeric/enum parameters against their defined domain immediately upon parsing, consistent with the report's recommendation to bound and validate all externally influenced parameters at the point of ingestion.

### Proof of Concept
1. Enable the `internal-data-acquisition` feature build.
2. Present a QR code matching `QR_CODE_SIGNUP_EXTENSION` with `mode` set to the value corresponding to `SignupMode::Overcapture` (`5`) and `parameters` set to `"10:1000"` (wavelength octal digits `10` = decimal 8).
3. `Data::from_signup_extension` parses this into `signup_extension_config.parameters = Some("10:1000")` [1](#0-0) .
4. On entering the overcapture plan, `parse_u8_octal("10", 1)` returns `8u8` (octal `10` = 8) [3](#0-2) .
5. `Configuration::new(8, ...)` calls `parse_wavelength_configuration(8)`, producing `format!("{8:0>3b}")` = `"1000"` (4 characters), causing `assert_eq!(4, 3, ...)` to panic and crash the orb-core process mid-signup [5](#0-4) .
