### Title
Webhook shop/topic identity spoofing via unsigned headers — HMAC only covers the request body ([File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that the handler receives and trusts as the tenant/context identifiers are read directly from unauthenticated HTTP headers and are never part of the signed content [2](#0-1) . Because `api_secret_key` is shared by every shop that has installed the same app, any shop owner (an unprivileged internet user with respect to other tenants) can legitimately obtain a validly-signed `(body, hmac)` pair for their own store and then replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, producing a signature that still validates.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, signable_content)` where `signable_content` includes everything the caller relies on for tenant attribution. Instead the gem computes:

- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the caller-supplied `hmac` [3](#0-2) .
- For webhooks, `to_signable_string` returns only `@raw_body` [4](#0-3) .
- `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding to the signature [5](#0-4) .
- `Registry.process` trusts these header-derived values wholesale when it builds `WebhookMetadata` and dispatches to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [6](#0-5) .

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" [7](#0-6)  and shows the handler using `data.shop` as the authoritative tenant identifier for downstream work such as `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [8](#0-7)  — i.e., the documented, intended usage treats `data.shop` as authenticated, when in fact it is not covered by the signature.

Because `Context.api_secret_key` is the app's single client secret shared across all shop installations (not per-shop), an attacker who has installed the same public app on their own store receives genuinely signed webhooks for that store. They can capture a `(raw_body, hmac)` pair and replay a POST to the target app's webhook endpoint, substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop/topic they want to spoof. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` calls the registered handler believing the webhook body genuinely belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: the equality `hmac == HMAC(secret, signable_content)` should imply `shop`/`topic` are also authentic, but `signable_content` excludes those fields. Any application that uses `data.shop` (as documented) to route, attribute, or persist webhook data per-tenant can be made to associate attacker-supplied body content with an arbitrary victim shop — a cross-tenant data injection/spoofing primitive reachable by any user able to install the app on their own store, which qualifies as Critical (cross-tenant access) per the scope's impact classes.

### Likelihood Explanation
Likelihood is meaningful but bounded: exploitation requires the attacker to have their own install of the same third-party app (readily achievable for any public app), knowledge of the target's webhook endpoint (a static, discoverable route), and a registered topic/handler that consumes `data.shop` for tenant-sensitive logic. No access token, session, or secret leakage is required — only the ability to install the target app on an attacker-controlled store and observe the resulting HTTP request Shopify sends.

### Recommendation
Bind the tenant-identifying headers into the signed content check, or at minimum require the host application to independently verify `request.shop` against its own list of installed/authorized shops before trusting the webhook payload. Concretely: document (and, where feasible, enforce in `Registry.process`) that `shop` must be cross-checked against a known-installed-shop list before use, since the current HMAC only proves the raw body was produced with `api_secret_key`, not that the accompanying headers are authentic.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers/receives a webhook for a topic the app also handles for other merchants (e.g. `orders/create`).
2. Shopify sends the attacker a legitimately signed webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays a POST to the app's webhook endpoint with the same body `B` and the same valid `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` only checks `B` against the secret and returns `true`; `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and invokes the app's handler, which (per the documented usage pattern) persists/acts on the body as if it belongs to `victim-shop.myshopify.com`.
