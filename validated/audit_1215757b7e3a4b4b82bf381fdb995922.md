### Title
Webhook shop domain is not covered by HMAC verification, enabling cross-tenant webhook payload injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from an unauthenticated HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` relies on to trust the request only covers the raw body. This breaks the intended binding `verified_shop == trusted_shop`, letting an attacker reuse a genuine, self-obtained (body, HMAC) pair while substituting an arbitrary victim shop domain.

### Finding Description
`Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` verifies exactly `verifiable_query.to_signable_string`, i.e., only the body, using the app's shared `client_secret`: [4](#0-3) 

`Webhooks::Registry.process` accepts the request once the body-only HMAC passes, then forwards the unauthenticated `request.shop` value to the app's handler as the trusted tenant key: [5](#0-4) [6](#0-5) 

This is exactly the bug class described in the analog: a field ("shop", used downstream as the session/tenant key) is acted upon but not covered by the HMAC that establishes trust in the request. For comparison, `Auth::Oauth::AuthQuery` (used in the OAuth callback flow) explicitly includes `shop` inside its `to_signable_string`, so it is properly bound to the signature: [7](#0-6) 

The webhook `Request` class has no equivalent binding for `shop`.

### Impact Explanation
Because the app's HMAC secret (`client_secret`) is shared across all shops that install the app, any unprivileged user can install the target app on their own store (a store they fully control) and receive genuine Shopify-signed webhooks for it. Each such webhook is a valid `(raw_body, hmac)` pair signed with the app's `client_secret`. The attacker can capture that pair and replay it to the app's webhook endpoint while changing only the `X-Shopify-Shop-Domain` header to name a different, victim shop that also installed the same app. `HmacValidator.validate` still passes because it never inspects the shop header, and `Registry.process` hands the handler a `WebhookMetadata` whose `shop` field is the attacker-chosen value. Any app that uses `data.shop` (the documented, intended usage per `docs/usage/webhooks.md`) to select which tenant's records to update, create, or delete will act on attacker-controlled data under a different tenant's identity — a cross-tenant integrity violation achieved without ever touching the victim's credentials.

### Likelihood Explanation
Likelihood is High for any developer/attacker who can install the target app on a shop they control (a normal, unprivileged action available to any Shopify Partner/developer store owner) and can send arbitrary HTTP requests to the app's public webhook endpoint (a required, internet-reachable endpoint). No secrets belonging to the victim or the app owner are needed.

### Recommendation
Bind the `shop` header value into the HMAC-verified material, e.g. by including the shop domain (and ideally webhook id/topic) in `to_signable_string`, or by independently validating that the shop asserted in the header corresponds to a shop session/installation record the app already trusts before dispatching to the handler. At minimum, document clearly that `WebhookMetadata#shop` is not cryptographically authenticated and must be cross-checked by the host application against its own installation records before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g., `orders/create`) and captures the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H`, both computed by Shopify using the app's `client_secret` over `B` only.
3. Attacker crafts a new HTTP request to the app's webhook endpoint:
   - Body: `B` (unchanged, so HMAC stays valid)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (arbitrary victim who also installed the app)
   - Header `X-Shopify-Topic`, `X-Shopify-Webhook-Id` set as desired.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — validation succeeds.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and, if it trusts `data.shop` as the tenant key (the documented usage), applies the attacker's payload `B` to the victim shop's records.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
