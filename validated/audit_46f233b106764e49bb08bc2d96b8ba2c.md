### Title
Webhook shop-tenant identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by defining `to_signable_string` to return only the raw HTTP body: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. only the raw body bytes: [2](#0-1) 

Meanwhile, the tenant identifier `shop` that the registry acts on is read from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signed payload: [3](#0-2) [4](#0-3) 

`Registry.process` validates only the HMAC over the body, then hands `request.shop` (the unauthenticated header value) straight to the application's webhook handler as the tenant-scoping field: [5](#0-4) 

This is precisely the identity-binding break called out by the rules: a field (`shop`) that is acted on (used to scope/attribute the webhook to a specific merchant) but is not covered by the HMAC signature. The signature proves only "these body bytes were signed with the app's `api_secret_key` at some point"; it proves nothing about which shop the payload is "for". Since `api_secret_key` is shared across every shop that installs the app (it is not per-shop), any merchant who installs the app on their own store legitimately receives validly-signed `(body, hmac)` pairs. That merchant can replay one of those bodies to the app's webhook endpoint while swapping only the `x-shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` calls the handler with `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This breaks the equality the gem is implicitly supposed to guarantee: `shop-that-signed-the-payload == shop-attributed-to-the-payload`. An attacker who is merely an unprivileged installer of the target app on their own shop (no access token, no `api_secret_key`, no privileged account needed) can produce webhook deliveries that are cryptographically "valid" per this gem but are falsely attributed to a different tenant. Any host application that trusts `WebhookMetadata#shop` (or `Request#shop`) to look up per-shop data, credentials, or state — which is the documented and expected usage pattern — can be tricked into performing actions against/using the wrong shop's records, i.e., cross-tenant access, which the rules classify as Critical impact.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs to be a legitimate (even free/trial) installer of the target app, which is normal, unprivileged access. They can trigger their own webhooks (e.g., by editing a product) to obtain a fresh, validly-HMAC'd `(body, hmac)` pair, then replay it to the app's public webhook endpoint with a forged `shop-domain` header. No secret material, TLS interception, or social engineering is required — only network access to the app's already-public webhook URL.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cryptographically tie the header-derived tenant identity to the signature before it is handed to handlers — e.g., verify the `shop-domain` header against a per-shop secret/session record known from installation, rather than trusting it merely because the *body* HMAC validated. At minimum, document prominently that `Request#shop`/`WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application against its own shop/session store before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (normal unprivileged onboarding).
2. Attacker triggers a webhook (e.g. updates a product), capturing the raw POST body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed using the app's `api_secret_key`.
3. Attacker replays a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid since it only covers `B`), but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because `to_signable_string` only returns `@raw_body`, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, per `lib/shopify_api/webhooks/registry.rb:188-200`, causing the host application to process attacker-controlled data as if it originated from the victim shop.
