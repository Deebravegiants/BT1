### Title
Unchecked ERC20 `transfer` Return Value in `IntentGatewayV2.withdraw()`/`SweepDust` Silently Fails While Escrow Is Debited - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed tokens to solvers/users via a raw low-level `.call` to `IERC20.transfer`, checking only that the *call itself* didn't revert, not the ABI-decoded boolean return value. Many TRC20/ERC20-like tokens (mirroring the STASIS EURO example in the referenced report) return `false` on failure instead of reverting. When this happens, the escrow accounting is still decremented and the order is marked filled/refunded as if the payout succeeded, permanently freezing the underlying tokens in the contract.

### Finding Description
In `withdraw()`:
```solidity
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
``` [1](#0-0) 

`success` here only reflects whether the external call reverted, not whether the token's internal logic returned `true`. Tokens that return `false` on a failed transfer (blocklists, pausable transfers, insufficient internal balance edge cases, etc.) will make this branch appear to succeed. The same unchecked pattern also appears for fee redemption in the same function:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [2](#0-1) 

and in the `SweepDust` handler inside `onAccept()`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [3](#0-2) 

This is exactly the bug class from the referenced report: an unchecked (or improperly checked) ERC20 transfer return value lets state that assumes a successful payment diverge from what actually happened on the token contract. Notably, the contract otherwise imports and uses OpenZeppelin's `SafeERC20` (`using SafeERC20 for IERC20;`) for inbound `safeTransferFrom` calls during `placeOrder`/`fillOrder`, but the outbound payout path in `withdraw()` and `SweepDust` bypasses `SafeERC20` entirely in favor of a manually checked raw `.call`, reintroducing the exact class of bug `SafeERC20` exists to prevent. [4](#0-3) 

`withdraw()` is reached from `onAccept()` when a relayer delivers a `RedeemEscrow` or `RefundEscrow` cross-chain settlement message (a relayed proof/dispatched request delivery, one of the explicitly in-scope reachable paths):
```solidity
if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
    authenticate(incoming.request);
    WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
    return withdraw(body, kind == RequestKind.RefundEscrow);
}
``` [5](#0-4) 

Because `_filled[body.commitment] = beneficiary` is set unconditionally at the top of `withdraw()` and `_orders[body.commitment][token] -= amount` executes regardless of whether the token actually moved, once the message is delivered the order is permanently marked settled — there is no retry path for the beneficiary to reclaim the escrowed tokens if the `transfer` call returned `false`. [6](#0-5) 

### Impact Explanation
If the escrowed input token (or protocol fee token) is one that returns `false` rather than reverting on transfer failure — a well-known behavior for several TRC20/ERC20 tokens, including on Tron where non-reverting failure semantics are common — the solver or refunded user permanently loses their entitled tokens: the contract's internal accounting is finalized (order marked filled/refunded, escrow decremented) while the tokens remain stuck in the `IntentGatewayV2` contract with no accounting path left to claim them. This is a permanent freezing/loss of funds for legitimate solvers and users, satisfying the High severity bar for the same reason as the original report (silent `transferFrom`/`transfer` failure decoupled from state updates).

### Likelihood Explanation
This does not require any malicious actor at all — it triggers whenever the input/fee token used in an order is a non-standard ERC20/TRC20 that returns `false` instead of reverting (e.g., due to a blocklist, pause, or internal balance check), which is a realistic and known category of tokens deployed on Tron and EVM chains generally. Any settlement (`RedeemEscrow`/`RefundEscrow`) or `SweepDust` message for such a token will hit this path via the normal relayer flow.

### Recommendation
Replace the raw `.call` + `success`-only check with OpenZeppelin's `SafeERC20.safeTransfer` (already imported and used elsewhere in this same contract) in `withdraw()` (both the token loop and the fee redemption) and in the `SweepDust` branch of `onAccept()`, so that both call failure and a `false` boolean return revert the transaction instead of silently finalizing escrow state.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron) with an input token `T` whose `transfer()` implementation returns `false` (without reverting) once a per-account blocklist flag is set (mirroring STASIS EURO-style tokens).
2. A user places an order with `T` as input; the escrow correctly records the deposited amount via `safeTransferFrom`.
3. A solver fills the order on the destination chain; a `RedeemEscrow` message is dispatched back to the source chain naming the solver as beneficiary.
4. Before the message is relayed, the token issuer blocklists the solver's address (or any condition causing `T.transfer` to return `false`).
5. The relayer delivers the `RedeemEscrow` proof; `onAccept()` invokes `withdraw()`. `token.call(...)` succeeds (no revert) but returns `abi.encode(false)`; `success` is `true` so the check passes, `_orders[...][T] -= amount` executes, and `_filled[commitment] = beneficiary` is set.
6. The solver never receives token `T`, and there is no remaining code path or escrow record to reclaim the now-stuck balance — the funds are permanently frozen in the contract.
