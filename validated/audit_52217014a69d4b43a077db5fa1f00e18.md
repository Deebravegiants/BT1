### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body, while the `shop`, `topic`, `api_version`, and `webhook_id` values that a host application uses to route/attribute the webhook are taken from unauthenticated headers.

### Finding Description
`Registry.process` gates handling on `Utils::HmacValidator.validate(request)` [1](#0-0) , and `HmacValidator.validate_signature` computes the digest over `verifiable_query.to_signable_string` [2](#0-1) . For `Webhooks::Request`, `to_signable_string` returns **only** `@raw_body`: [3](#0-2) . Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to the body: [4](#0-3) , and those unauthenticated values are handed to the host application's handler unchanged via `WebhookMetadata` [5](#0-4) [6](#0-5) .

This is the same bug class as the CBOR report: a field that is *acted upon* (`shop`) is not covered by the integrity check (`hmac` over `raw_body` only) — i.e., "bytes verified" (body) ≠ "bytes/fields parsed and trusted" (headers). Because the HMAC secret (`api_secret_key`) is never disclosed to an attacker, they cannot forge a body+HMAC pair from nothing, but that is not required: any actor who can obtain one valid `(raw_body, hmac)` pair for *any* shop — e.g., by installing the target app on their own (even free/dev) store and capturing an outbound webhook to a server they control — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `Topic`/`Webhook-Id`) headers for a different, victim shop. `HmacValidator.validate` will still pass because it never inspects those headers, and the handler will process attacker-supplied data under the identity of an arbitrary `shop` value the host application never independently verified.

For comparison, the OAuth callback flow in this same gem does bind `shop` into the signed material — `AuthQuery#to_signable_string` explicitly folds `shop`, `code`, `host`, `state`, and `timestamp` into the HMAC input [7](#0-6)  — showing that the library is capable of, but does not apply, this binding for webhooks.

### Impact Explanation
This breaks the identity binding `shop (as authenticated by HMAC) == shop (attributed to the processed data)`. A host application that uses `WebhookMetadata#shop` to select which merchant's records to update (a very common pattern, e.g. mapping `orders/paid` webhook data to a shop's local database row) can be made to apply attacker-controlled body content to a different, victim tenant's records purely by header substitution, despite the HMAC check passing. This is a cross-tenant data-integrity issue reachable by any actor able to install the target app on a shop they control (no leaked credentials, no access token, no privileged account beyond a free store signup are required to exploit it against the target app's endpoint).

### Likelihood Explanation
Moderate. It requires the attacker to first legitimately receive one valid signed webhook (achievable by installing the app on any shop, including a free development store) and then send a crafted HTTP POST directly to the target app's public webhook endpoint with a spoofed `shop-domain` header — both trivially achievable for an unprivileged internet actor, without needing the app's `client_secret` or any merchant's access token.

### Recommendation
Bind the routing-relevant fields into the signed material verified by `HmacValidator`, or have `Registry.process` independently corroborate `request.shop`/`request.topic` (e.g., verify against a known/allow-listed installation record) before dispatching to the handler, rather than trusting header values that fall outside the HMAC's coverage.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled store (`attacker-shop.myshopify.com`) and register/trigger any webhook subscription (e.g. `orders/create`) pointing to a server the attacker controls.
2. Capture the delivered POST request, including `raw_body`, `X-Shopify-Hmac-Sha256`, and other headers.
3. Replay the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the target app's real webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only re-computes the HMAC over `raw_body`, which is unchanged [3](#0-2) ; `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` [8](#0-7) , causing the host application to process attacker-supplied webhook content as though it originated from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
