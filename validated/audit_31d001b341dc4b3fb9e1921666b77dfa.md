## Title
Single authorized-relayer gate on IntentGatewayV2 allows censorship of escrow settlement messages with no permissionless fallback - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The rest of Hyperbridge's ISMP delivery pipeline is explicitly permissionless — `HandlerV2.handlePostRequests`, `handleGetResponses`, and `handlePostRequestTimeouts` can be submitted by anyone, mirroring pre-bedrock Optimism's censorship-resistant model. [1](#0-0)  However, `IntentGatewayV2`'s `ExtrinsicIntents` module layers an additional application-level relayer allowlist on top of this permissionless handler: `onAccept` and `onGetResponse` call `_checkRelayer(incoming.relayer)` before decoding any message body, and reject delivery from anyone other than the single address stored in `_relayer`. [2](#0-1)  This turns the app-level delivery of a validly-proven message back into a bedrock-style single-sequencer chokepoint, with no way for a user or solver to force-include their message via an alternative path.

### Finding Description
`_checkRelayer` reverts with `Unauthorized()` when `_relayer` is non-zero and the delivering account differs from it. [3](#0-2)  This check runs at the very top of `onAccept`, before `RequestKind` is even read, so it gates every message type handled by the gateway: `RedeemEscrow`, `RefundEscrow`, `NewDeployment`, `UpdateParams`, `SweepDust`, and `Execute` (governance/upgrades). [4](#0-3) 

Crucially, a rejected delivery from an unauthorized relayer reverts and leaves **no receipt** on the host (`EvmHost.dispatchIncoming` deletes the receipt on failure so the message "stays deliverable"), meaning the message is only actually settled once the specific authorized relayer chooses to submit it. [5](#0-4)  This is confirmed by `testOnAcceptRejectsUnlistedRelayer`, which shows escrow stays untouched when a non-authorized party (even the filler/solver who is owed the funds) submits the proven `RedeemEscrow` message, and only proceeds once the specific `relayer` address submits the identical message. [6](#0-5) 

The relayer is rotated only through governance (`setRelayer`, `onlyHost`, reachable solely via a Hyperbridge `Execute` action), so users and solvers have no code path to appoint an alternate relayer or force a stuck settlement through, regardless of how many honest, permissionless relayers are watching the chain and are willing to submit the message for free/for the fee. [7](#0-6) 

This is the same bug class as the reported bedrock issue: before bedrock, if the sequencer refused a transaction, users could submit it directly to `CanonicalTransactionChain` on L1 as a fallback. Here, ISMP's `HandlerV2` is the "direct L1 submission" analog and is fully permissionless — but `ExtrinsicIntents` reintroduces a single point of censorship on top of it that has no equivalent fallback.

### Impact Explanation
If the sole authorized relayer refuses (or is unable, e.g. compromised/offline/regulatorily coerced) to submit a specific `RefundEscrow` or `RedeemEscrow` message, the user's escrowed input tokens (`placeOrder`) or the solver's earned withdrawal remain permanently locked in the gateway contract — even though a valid Hyperbridge-attested proof of the settlement exists and any other party is willing and able to deliver it via the normal, permissionless `HandlerV2`/`EvmHost` path. This is a permanent freezing-of-funds condition scoped to whichever escrow entries the withheld message covers, satisfying the "route unable to deliver messages" / "permanent freezing of funds" criteria.

### Likelihood Explanation
The gate is unconditionally enforced whenever `_relayer != address(0)`, which is the intended steady-state configuration for a deployed, governance-armed gateway (the docs describe the open-gate state as a transient pre-governance-arming window only). [8](#0-7)  Any operational failure, key compromise, or selective withholding by that single relayer directly and deterministically blocks settlement of the targeted order(s); no additional attacker action or race condition is required beyond the relayer simply not submitting (or the host/relayer operator colluding to censor) a specific message.

### Recommendation
Do not gate settlement-critical message kinds (`RedeemEscrow`, `RefundEscrow`) behind a single-relayer allowlist at the application layer, since it defeats the censorship-resistance guarantee of the permissionless ISMP handler underneath it. If a relayer allowlist is required for other reasons (e.g., MEV/ordering control), scope it to non-fund-critical actions only, or add a timelocked fallback that allows any address to deliver an already-proven-but-stuck settlement message after a bounded grace period once the authorized relayer has failed to act, similar to how `handlePostRequestTimeouts` is kept permissionless.

### Proof of Concept
1. Governance arms the gateway with a single relayer via `setRelayer(relayer)` (host-only, delivered through an `Execute` governance action). [9](#0-8) 
2. A user places a cross-chain order and escrows input tokens; a solver fills it on the destination chain, and Hyperbridge produces a valid state proof for the resulting `RedeemEscrow` message back to the source chain.
3. Any relayer other than `relayer` calls `HandlerV2.handlePostRequests` with the valid proof; `EvmHost.dispatchIncoming` calls `onAccept`, but `_checkRelayer` reverts `Unauthorized()` — the receipt is deleted and no escrow release occurs, as shown in `testOnAcceptRejectsUnlistedRelayer`. [10](#0-9) 
4. If the authorized `relayer` never submits this specific message (offline, compromised, or deliberately censoring), the escrowed tokens remain locked indefinitely; no other party, however willing, can complete delivery through the otherwise-permissionless protocol.

```text
    function _authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        if (_instance(request.source) != module) revert Unauthorized();
    }

    /**
     * @dev Once a relayer is set, rejects deliveries from anyone else before the body is read. The
     * host records the revert as undelivered, so the authorised relayer can resubmit. While unset,
     * every delivery passes: a proxy from before the gate stays open until `migrate` arms it.
     * @param relayer The account that submitted the message to the handler.
     */
    function _checkRelayer(address relayer) internal view {
        address authorised = _relayer;
        if (authorised != address(0) && relayer != authorised) revert Unauthorized();
    }
```

```text
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        _checkRelayer(incoming.relayer);
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.Execute) {
            Address.functionDelegateCall(ERC1967Utils.getImplementation(), incoming.request.body[1:]);
        }
    }
```

```markdown
1. A relayer calls `HandlerV2.handlePostRequests` (or `handleGetResponses`). After proof
   verification the handler calls `host.dispatchIncoming(request, _msgSender())`. `_msgSender()` is
   plain `msg.sender`; the handler has no trusted forwarder.
2. `EvmHost.dispatchIncoming` (restricted to the handler) writes a receipt for the request
   commitment, then low-level calls the module with `IApp.onAccept(IncomingPostRequest(request,
   relayer))`. If that call fails the host deletes the receipt and returns without reverting, so the
   rest of the batch proceeds and the message stays deliverable.
3. `ExtrinsicIntents.onAccept` runs `onlyHost`, then `_checkRelayer(incoming.relayer)`, which reverts
   with `Unauthorized` when a relayer is set and the delivery is from anyone else. Only then is the
   first body byte read as a `RequestKind`. `onGetResponse` has the same two steps before touching
   the response.

So a delivery from anyone but the authorised relayer never decodes the body, never runs
`_authenticate`, and leaves no receipt. The authorised relayer submitting the same message later
takes the normal path. A gateway whose `_relayer` is zero accepts every relayer: that is the state
a fresh proxy is in until governance arms it, below.
```

```markdown
# 2026-09-05 — Gateway `setRelayer` is host-only and the only writer; unset means open

Chosen: `setRelayer` lives in `ExtrinsicIntents` behind `onlyHost`, `initialize` does not touch the
relayer, and `_checkRelayer` passes every delivery while `_relayer` is zero. This supersedes the
2026-09-03 decision below that zero fails closed.

The owner branch existed so a fresh proxy could be armed locally; it also let the owner key
redirect every cross-chain delivery without a governance message. Removing it leaves the host as
the only caller, reachable solely from `UpgradeContract` migration calldata. Carrying the relayer
in the init data was tried and rejected: the relayer is operational state that governance owns,
not part of what fixes a proxy's address. With no local or init-time arming left, the message that
arms a fresh proxy is a governance delivery, so the unarmed proxy has to accept it; an unset
relayer therefore gates nothing, and `setRelayer(address(0))` reopens the gate. The window is the
one between deployment and the `upgrade_gateway` that arms it, and closing it is governance's
first act on a new chain.
```
