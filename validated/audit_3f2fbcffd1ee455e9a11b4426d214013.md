### Title
Emporium `EmporiumSignature` EIP-712 typehash does not bind the output `stealthAddressStructure`, letting anyone replay a harvested signed op-stack to steal the resulting wallet UTXO - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EMPORIUM_SIGNATURE_TYPEHASH` and `_hashEmporiumOps` commit only to `message`, `ops` (endpoint/invokeWallet/value/callData), `maxFee`, and `deadline`, never to `circomData.stealthAddressStructure`. Since `handleOut` builds the resulting shielded UTXO directly from the caller-supplied `circomData.stealthAddressStructure`, any party who observes/harvests a valid, not-yet-used signed `EmporiumStack` can submit it with their own `circomData` (including their own `stealthAddressStructure` and a self-generated ZK proof) and redirect the wallet's on-chain output to themselves.

### Finding Description
The claimed equality is: `outUtxo.stealthAddressStructure` (constructed in `handleOut`) `== stealthAddressStructure the wallet owner's EIP-712 EmporiumSignature commits to`. This is never true because the typehash simply excludes it: [1](#0-0) 

`verifyWallet` only recovers the signer over `(emporiumMessage, _hashEmporiumOps(stack.ops), stack.maxFee, stack.deadline)`: [2](#0-1) 

After the signed `ops` execute and move funds through/for the wallet, `handleOut` mints the resulting UTXO to whatever `circomData.stealthAddressStructure` the *transaction submitter* (not the signer) supplied: [3](#0-2) 

`circomData` (including `stealthAddressStructure`) is supplied by `msg.sender` of `Hinkal.transact`, independent of `stack.signerAddress`: [4](#0-3) 

The only other place `stealthAddressStructure` is referenced is as a **public input to the attacker's own ZK proof** (`formBasicInput` / `getSignedMessageHash`), which is signed with an EdDSA key the prover freely chooses; when the transaction spends zero shielded input notes (`inAmounts == 0`), `MainEVMCircuit`'s root-hash equality constraint is disabled (`enabled <== inAmounts[i][j]`), so this "proof" carries no real third-party authorization — it merely proves self-consistency of attacker-chosen values: [5](#0-4) [6](#0-5) 

`performHinkalChecks` (`dimensionsCheck`, `checkOnchainCreation`, `getHashedCalldata` consistency) validates internal structural consistency of a single `circomData`, but nowhere ties `stack.signerAddress`/`stack.ops` to a specific `stealthAddressStructure`: [7](#0-6) 

**Exploit flow:**
1. A legitimate wallet owner signs an `EmporiumStack` (`v,r,s,signerAddress,ops,maxFee,deadline`) intending it to be submitted with `circomData.stealthAddressStructure` = their own address, and `emporiumMessage` unused so far.
2. The attacker obtains this signed stack (e.g., it is visible before being mined, via a relay/mempool/public order flow — no privileged role required, only public visibility of a not-yet-confirmed message).
3. The attacker crafts their own `CircomData` with `externalActionData.externalActionMetadata = abi.encode(stack)` (same `ops`/`v,r,s`), the same `emporiumMessage`, but `stealthAddressStructure` = attacker's own address, and generates a fresh, self-consistent ZK proof (0 input UTXOs, so no other party's signature is required).
4. Attacker calls `Hinkal.transact` before the legitimate transaction lands. `performHinkalChecks` passes (all fields internally consistent), `verifyProof` passes (self-generated proof), `verifyWallet` passes (`_hashEmporiumOps(stack.ops)` matches the original signature; `usedMessages[emporiumMessage]` is still false).
5. `EmporiumUpgradeable.runAction` executes `stack.ops`, which move/spend the wallet's own funds/approvals via `IHinkalWallet(stack.signerAddress).callHinkalWallet(...)`, producing a balance increase attributable to `handleOut`.
6. `handleOut` mints the resulting UTXO to the attacker's `circomData.stealthAddressStructure`, not the wallet owner's.
7. `usedMessages[emporiumMessage]` is now `true`, so the legitimate transaction (with the owner's correct `stealthAddressStructure`) permanently reverts with `UsedMessage`.

None of the existing guards (`performHinkalChecks`, `verifyProof`, `rootHashExists`, slippage/balance requires, `insertNullifiers`) check that the destination `stealthAddressStructure` is authorized by `stack.signerAddress`; they only check internal consistency of the attacker's own submitted `circomData`.

### Impact Explanation
This is direct theft of the wallet-owner-authorized value produced by their own signed on-chain calls (e.g., a swap/withdrawal executed via `IHinkalWallet.callHinkalWallet`), diverted entirely into a shielded UTXO the attacker controls. This is repeatable for every signed `EmporiumStack` that becomes observable prior to being consumed (`usedMessages` write), and additionally griefs/permanently blocks the legitimate transaction (message gets marked used). This matches the Critical category: "direct theft of shielded or in-flight user funds."

### Likelihood Explanation
Preconditions: an `EmporiumStack` signed by a wallet owner with `signerAddress != address(0)` and non-trivial `ops` that pull real value through the wallet, and the corresponding `emporiumMessage` not yet consumed on-chain when the attacker acts. The attacker needs no special role — only the ability to observe a not-yet-mined signed payload and to submit their own transaction with a locally generated proof (all attacker capabilities within the stated threat model). Cost is limited to gas plus generating a standard proof with zero input UTXOs. Feasibility depends on how the signed stack is transmitted to the chain (e.g., via a public relay/mempool) — if signed stacks are only ever transmitted through a private, already-included path, exposure window may be small, but the protocol's own EIP-712 typehash design provides no cryptographic binding regardless of transport, so the vulnerability is structural, not merely a race-condition curiosity.

### Recommendation
Include `circomData.stealthAddressStructure` (and ideally `msg.sender`/`circomData.relay`) inside `EMPORIUM_SIGNATURE_TYPEHASH` so the wallet owner's signature explicitly authorizes both the operations to run and the exact destination stealth address for the resulting UTXO. Recompute the typed-data hash to include these fields, e.g.:
```
keccak256("EmporiumSignature(uint256 message,EmporiumOperation[] ops,uint256 maxFee,uint256 deadline,uint256 H0x,uint256 H0y)EmporiumOperation(...)")
```
and pass `circomData.stealthAddressStructure.H0x/H0y` (or the full struct hash) into `verifyWallet`'s `abi.encode(...)` call before hashing.

### Proof of Concept
Foundry fork test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, a `HinkalWallet` for a victim EOA, and a test ERC20/endpoint.
2. Victim signs an `EmporiumStack` (`emporiumMessage=M`, `ops=[op that moves victim wallet's approved tokens through endpoint]`, `maxFee`, `deadline`) intended for `circomData_A.stealthAddressStructure = victimStealth`.
3. Simulate "harvesting": construct `circomData_B` with the same `externalActionMetadata` (same signed stack bytes) and `emporiumMessage=M`, but `stealthAddressStructure = attackerStealth`, `erc20TokenAddresses`/`amountChanges` set for zero input UTXOs, and locally generate a valid Groth16 proof for `circomData_B`.
4. Call `Hinkal.transact(...)` with `circomData_B` from the attacker address — assert it succeeds, `EmporiumStorageVars.usedMessages[M] == true`, and the resulting on-chain commitment corresponds to `attackerStealth` (assert `outUtxo.stealthAddressStructure.stealthAddress == attackerStealth.stealthAddress`, not `victimStealth.stealthAddress`).
5. Attempt to submit the victim's originally intended `circomData_A` transaction — assert it reverts with `UsedMessage`, proving the legitimate output was preempted and diverted.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
