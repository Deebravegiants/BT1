## Analog Vulnerability Found

Root cause class: **missing re-initialization guard on a privileged constructor**, structurally analogous to the `MintSaleBase.setVibeFees` issue — a state-mutating, privilege-defining entry point (`new`) that is reachable by *any* caller because the code fails to verify that the contract has not already reached a "committed/owned" state, exactly mirroring how the reported bug allows `setVibeFees` to run whenever there's no established master/owner association.

### Title
Missing re-initialization guard on `MultiSigContract::new` allows unprivileged takeover of an already-deployed multisig - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::new` in `multisig2/src/lib.rs` is marked `#[init]` but, unlike every sibling contract in this same repository, never checks `env::state_exists()` before writing the contract's state. [1](#0-0) 

### Finding Description
NEAR's `#[init]` macro does not automatically forbid re-invocation of an initializer once state exists — each contract author must explicitly guard against it. Every other production contract in this repo does so:
- `multisig/src/lib.rs`: `assert!(!env::state_exists(), "Already initialized");` [2](#0-1) 
- `staking-pool/src/lib.rs`: `assert!(!env::state_exists(), "Already initialized");` [3](#0-2) 
- `staking-pool-factory/src/lib.rs`, `lockup-factory/src/lib.rs`, `whitelist/src/lib.rs` all contain the identical `assert!(!env::state_exists(), ...)` check. [4](#0-3) [5](#0-4) [6](#0-5) 

`multisig2/src/lib.rs::new`, however, has no such check and unconditionally rebuilds `members`, `num_confirmations`, `requests`, `confirmations`, and `num_requests_pk` from caller-supplied arguments: [1](#0-0) 

Because `new` has no `#[private]`/owner check (it can't, since it's the constructor) and no state guard, **any unprivileged account** can call `new` again on an already-initialized, already-funded multisig account and overwrite its member list with attacker-controlled public keys/account IDs and set `num_confirmations` to a value the attacker fully controls (e.g., `1`).

### Impact Explanation
This maps to two allowed Critical/High impact categories:
- **Critical** — Unauthorized transfer/withdrawal of multisig-controlled NEAR: once the attacker resets `members` to include only their own key and `num_confirmations` to `1`, they can call `add_request_and_confirm` with a `Transfer` action to drain the account's entire balance via `execute_request`. [7](#0-6) 
- **High** — State-transition/confirmation bypass in the multisig flow, letting an unprivileged user perform actions (member/ownership control) beyond intended authority.

### Likelihood Explanation
Likelihood is high once discovered, because:
1. Calling `new` requires no special permission — it's a normal `pub fn` reachable via a standard function call, same public entry every legitimate deployer uses.
2. There is no atomicity requirement to exploit it after initial deployment — the attacker does not need to race the deployer's initial `new` call (that race exists too, but is the more commonly discussed "front-run the constructor" risk shared by all these contracts' manual deployment flows). This flaw is worse: it allows re-initialization of an **already fully configured, already funded** multisig at any point in its lifetime, since nothing ever flips a "state exists" flag.
3. Exploiting it only requires observing which accounts run the `multisig2` contract and issuing one `new` call to it.

### Recommendation
Add the same guard used by every other contract in the repo, and ideally combine it with `PanicOnDefault`'s intended pattern:
```rust
#[init]
pub fn new(members: Vec<MultisigMember>, num_confirmations: u32) -> Self {
    assert!(!env::state_exists(), "Already initialized");
    ...
}
```

### Proof of Concept
1. Attacker observes a `multisig2` contract account (e.g., `multisig.illia`) that has already been initialized with legitimate members and holds NEAR funds.
2. Attacker calls:
   ```
   near call multisig.illia new '{"members": [{"public_key": "<attacker_pubkey>"}], "num_confirmations": 1}' --accountId attacker.testnet
   ```
   This succeeds because `new` never checks `env::state_exists()`. [8](#0-7) 
3. The multisig's `members`/`num_confirmations` are now fully attacker-controlled.
4. Attacker calls `add_request_and_confirm` with a `Transfer` action for the full balance of `multisig.illia`, which passes `assert_valid_request`/`current_member` checks against the attacker's own key, and `confirm` triggers `execute_request`, transferring the funds out. [9](#0-8) [10](#0-9) 

### Note on uncertainty
I could not fully verify at what exact near-sdk version (`4.0.0-pre.4`, per `multisig2/Cargo.toml`) the `#[init]` macro behavior stands, since the near-sdk source itself is an external dependency not present in this repo's index. My conclusion relies on: (a) the documented/typical near-sdk contract convention observed across every other sibling contract in this same repository explicitly re-implementing the `state_exists()` guard, and (b) the absence of any equivalent check, `#[init(ignore_state)]` override, or other protective mechanism in `multisig2/src/lib.rs`. If near-sdk 4.0.0-pre.4's macro expansion for `#[init]` silently added this check by default (differing from the explicit pattern used everywhere else in the codebase), the finding would not hold — I recommend a Devin session with full build/test access to `multisig2` to confirm this empirically (e.g., write a test that calls `new` twice and observes whether the second call panics or succeeds).
