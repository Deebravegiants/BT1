### Title
Unauthenticated container fields (scrypt cost params, cipher, IV/authTag/key) are processed and expensive KDF work is performed before header authenticity (`checkMagic`) is validated - (`libraries/secure-container/src/index.js`, `libraries/secure-container/src/file.js`)

### Summary
`file.checkContents()` / the checksum check in `decrypt()` only proves the submitted blob is *self-consistent* (checksum is a plain unkeyed `sha256` over attacker-controlled `metadata`+`blob`, so an attacker can always make it match). The real `decrypt()` flow in `libraries/secure-container/src/index.js` decodes `metadata` and calls `metadata.decryptBlobKey()` (which runs scrypt with attacker-supplied `n`/`r`/`p` and attempts AES-GCM decryption) *before* it ever calls `header.decode()`, which is the only place `checkMagic()` runs. This lets an attacker-forged backup/import blob force expensive, attacker-parameterized KDF work and a crypto decrypt attempt to execute prior to any structural/type authenticity check.

### Finding Description
- `file.checkContents()` in `libraries/secure-container/src/file.js:30-33` only recomputes `sha256(metadata || len(blob) || blob)` and compares to the stored `checksum`. Since this hash is unkeyed, any attacker who controls `metadata` and `blob` can trivially compute a matching `checksum` themselves [1](#0-0) .
- Critically, `header` in the `file.js` `struct` is decoded as an opaque `Buf(HEADER_LEN_BYTES)` - `checkMagic()` is never invoked as part of `file.decode()`/`checkContents()`; it only runs inside `header.decode()`, a separate call [2](#0-1) [3](#0-2) .
- The actual `decrypt()` entrypoint used by the library performs, in order: decode file → verify checksum → `metadata.decode()` → `metadata.decryptBlobKey()` (scrypt + AES-GCM) → `header.decode()` (where `checkMagic` throws) → `blob.decrypt()`. The header/magic check happens *after* the KDF and decrypt attempt [4](#0-3) .
- `metadata.decode()` places no bounds on the attacker-controlled `scrypt.n`, `scrypt.r`, `scrypt.p` fields [5](#0-4) , and `boxDecrypt`/`stretchPassphrase` pass these straight into the `scrypt` KDF with the real, secret passphrase [6](#0-5) [7](#0-6) . I could not find any bounds check on `n`/`r`/`p` anywhere in this repo (the `@exodus/crypto/scrypt` implementation itself is outside the indexed code, so whether it enforces internal limits is unverified).
- Net effect: a container whose `header.magic` is invalid (i.e., not a real SECO container) is still accepted through the checksum stage and has its metadata parsed and its blobKey-decryption attempted (real passphrase run through attacker-chosen scrypt cost and AES-GCM parameters) before the code ever discovers, via `header.decode()`, that the structure isn't a valid container.

### Impact Explanation
This is a resource-exhaustion / Denial-of-Service vector, not a key-disclosure or signing-bypass one: the AES-GCM authentication tag check in `aesDecrypt`/`decryptGCM` will fail for attacker-forged ciphertext (since the attacker does not know the real passphrase-derived key), so no secret material is disclosed. The exploitable impact is that an attacker-supplied backup/import/QR payload can force the wallet's decrypt/import path to perform an expensive, attacker-parameterized scrypt derivation (and a GCM decrypt attempt) using the real user passphrase before the code validates that the payload is even a legitimate SECO container. If `n`/`r`/`p` are unbounded, this can be used to cause excessive CPU/memory consumption (hang or crash) on the device processing the import, reachable purely from an attacker-crafted import/backup blob with no privileged access required.

### Likelihood Explanation
Feasible and repeatable: an attacker only needs to construct a buffer matching the `file.js` struct (`header` bytes of any content, `checksum = sha256(metadata||len(blob)||blob)`, arbitrary `metadata` with huge `n`, arbitrary `blob`) and get it accepted into any application flow that decrypts/imports secure-container blobs (e.g., via `seco-file`/`seco-rw` read paths or a direct `decrypt()` call in `libraries/secure-container/src/index.js`). No cryptographic secrets or authentication bypass are required to reach this code path - checksum validity is self-computable by the attacker.

### Recommendation
- Validate `header.magic`/structural authenticity (`header.decode()` / `checkMagic`) before doing any checksum verification or metadata/blobKey processing, so malformed/non-SECO containers are rejected immediately.
- Bound `scrypt.n`, `scrypt.r`, `scrypt.p` to sane maximums when decoding untrusted `metadata` (reject decode or KDF attempts for out-of-range cost parameters) in `libraries/secure-container/src/metadata.js` / `libraries/secure-container/src/crypto.js`.
- Consider making the checksum a keyed MAC (e.g., HMAC keyed by a value derived after passphrase verification, or simply reordering: authenticate structure/magic and enforce sane metadata bounds first, then verify checksum, then perform KDF/decrypt).

### Proof of Concept
Unit test plan (extends existing `libraries/secure-container/src/__tests__/usage.test.js` patterns):
1. Build a `metadata` object via `metadata.create()` but override `metadata.scrypt.n` to a very large value (e.g., `2**30`) and set `metadata.cipher`, `blobKey.iv/authTag/key` to arbitrary attacker bytes.
2. Set `blob` to arbitrary bytes.
3. Compute `checksum = await file.computeChecksum(metadataBuf, blob)` (attacker can do this because it's unkeyed sha256).
4. Set `header` to a buffer that does **not** start with the `SECO` magic (or otherwise fails `header.decode()`).
5. `fileBuf = file.encode({ header, checksum, metadata: metadataBuf, blob })`.
6. Assert `await file.checkContents(fileBuf)` returns `true` (checksum "valid").
7. Call `decrypt(fileBuf, realPassphrase)` (or replicate the internal sequence: `metadata.decode()` then `metadata.decryptBlobKey()`) and assert/measure that the scrypt-based KDF actually executes (e.g., via timing or a spy on `@exodus/crypto/scrypt`) **before** the eventual `header.decode()` throws a `RangeError('Invalid secure container magic.')`.
8. Expected (current, vulnerable) behavior: KDF/decrypt attempt executes prior to the magic-check failure. Expected (fixed) behavior: `header.decode()`/`checkMagic()` throws immediately, with no scrypt invocation and no `metadata.decryptBlobKey()` call occurring beforehand.

```javascript
export async function computeChecksum(metadata, blob) {
  return scCrypto.sha256(Buffer.concat([metadata, fromUInt32BE(blob.byteLength), blob]))

export async function checkContents(fileContents) {
  const fileObj = decode(fileContents)
  return fileObj.checksum.equals(await computeChecksum(fileObj.metadata, fileObj.blob))
}
```

```javascript
export async function decrypt(encryptedData, passphrase) {
  const fileObj = conFile.decode(encryptedData)

  const checksum = await conFile.computeChecksum(fileObj.metadata, fileObj.blob)
  if (!fileObj.checksum.equals(checksum))
    throw new Error('seco checksum does not match; data may be corrupted')

  const metadata = conMetadata.decode(fileObj.metadata)
  const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)
  const header = conHeader.decode(fileObj.header)
  const data = await conBlob.decrypt(fileObj.blob, metadata, blobKey)

  return { data, blobKey, metadata, header }
}
```
