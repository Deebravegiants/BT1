### Title
Webhook `shop-domain` header trusted for tenant identification while excluded from the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body`), but exposes `shop`, `topic`, `api_version`, and `webhook_id` as trusted accessors that are read directly from unauthenticated HTTP headers. `shop` is the field host applications use to identify which tenant/merchant a webhook belongs to, yet it carries zero cryptographic binding to the signed payload.

### Finding Description
`Utils::VerifiableQuery`-based validation (used identically for OAuth `AuthQuery`, see `lib/shopify_api/auth/oauth/auth_query.rb`) signs every field that participates in identity decisions — `code`, `host`, `shop`, `state`, `timestamp` are all included in `to_signable_string`. In contrast, `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns only `@raw_body`, and the `hmac` getter (`lib/shopify_api/webhooks/request.rb:10-13`) is computed from a separate header (`shopify-hmac-sha256`) independent from `shop` (`lib/shopify_api/webhooks/request.rb:20-23`), which is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header via `shopify_header` (`lib/shopify_api/webhooks/request.rb:67-70`).

Equality that should hold but doesn't:
`HMAC-verified(bytes)` should equal `bytes-that-determine-tenant(shop)`. Here, `HMAC` only covers `raw_body`; `shop` is an independent, unauthenticated header value. An attacker who can influence or replay a request to the app's webhook endpoint (e.g., a party that has captured/replayed a legitimately signed body payload — such as another merchant's own webhook delivery, or any request whose body signature the attacker can reuse) can pair a *valid* `hmac`/`raw_body` pair with an *arbitrary* `shop-domain` header, since nothing ties the two together cryptographically.

Because this gem's own `Webhooks::Registry` (`lib/shopify_api/webhooks/registry.rb`) dispatches to handlers keyed by `topic` and passes the `Request#shop` value through to handler code untouched, any host app that uses `request.shop` to look up per-tenant state (session/access token) after only checking `Utils::HmacValidator`/signature validity is trusting an unauthenticated value as the tenant identifier.

### Impact Explanation
If an attacker can obtain any one validly-signed `(raw_body, hmac)` pair reaching the app's webhook endpoint — for example, by triggering a webhook on their own trial/store (which they fully control) and then replaying that exact body+hmac while substituting the `shop-domain` header of a victim shop — the app's webhook handler will process it believing it originated from the victim tenant. Depending on what the host application does with `Request#shop` (commonly: loading that shop's stored access token/session to make follow-up Admin API calls, or writing/deleting tenant data keyed by `shop`), this enables cross-tenant data confusion/access using only the attacker's own legitimately-signed webhook traffic — no possession of `api_secret_key` or any victim credential is required.

### Likelihood Explanation
Likelihood is High for any app that follows the common pattern of "verify HMAC, then trust `shop` from the request/headers to select the tenant." Because the gem itself provides `shop` as a first-class, seemingly-verified attribute of a `Request` object whose overall validity is anchored on `hmac`, an integrator has no visible signal that `shop` sits outside the signed envelope — the API surface (`hmac`, `shop`, `topic`, `to_signable_string`) implies verification covers the whole record, when it does not. An attacker only needs one self-controlled shop to generate valid `(body, hmac)` material and then a way to trigger request processing with a substituted header (e.g., via any HTTP-request-shaping surface between edge/proxy and the app, or a Rack test harness/replay tool the app or its infra exposes).

### Recommendation
- Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string bound to the HMAC verification for `Webhooks::Request`, or otherwise cryptographically bind the tenant identity to the payload (Shopify's actual HMAC only covers the body by design, so this is a structural gap in trusting `shop` as verified).
- At minimum, document prominently that `Request#shop`/`topic`/`webhook_id` are **not** covered by the HMAC and must be independently corroborated (e.g., cross-checked against `parsed_body["shop_domain"]`/`admin_graphql_api_id` inside the *signed* JSON body) before being used for tenant selection.
- Provide a helper that returns the shop identity strictly from the signed `raw_body`/`parsed_body`, and steer consumers away from `shopify_header("shop-domain")` for authorization-relevant decisions.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers any webhook subscription (e.g., `orders/create`), causing Shopify to POST a validly HMAC-signed payload to the app's webhook endpoint with headers:
   - `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
2. Attacker captures this exact `raw_body` and `hmac` header value (both fully valid, since `to_signable_string` only depends on `raw_body`, which is unchanged).
3. Attacker replays the identical `raw_body` + `X-Shopify-Hmac-Sha256` header to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (via `Utils::VerifiableQuery`/`to_signable_string`) succeeds, because it only checks `raw_body` against `hmac` — it never inspects `shop`.
5. `ShopifyAPI::Webhooks::Request#shop` now returns `"victim-shop.myshopify.com"` for a request whose signature validation passed, and any host code that does `session = SessionRepository.load_session_by_shop(request.shop)` will operate against the victim tenant using attacker-controlled, unauthenticated header content.       sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
