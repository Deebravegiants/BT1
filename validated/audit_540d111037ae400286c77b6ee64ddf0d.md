This confirms the documented, intended usage pattern: for non-embedded apps, the caller passes the raw HTTP `Cookie` header value straight into `current_session_id`, which the app then uses as the session-storage lookup key to fetch a `Session` (containing the real access token) via `ShopifyApp`/host session storage [1](#0-0) .

### Title
Predictable, unverified session-cookie value allows cross-tenant session hijack - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
`current_session_id`'s cookie branches (used for every non-embedded app, and as the embedded fallback when no token is supplied) return the raw cookie value with zero cryptographic verification, while the deterministic session IDs it computes elsewhere (`offline_#{shop}`, `#{shop}_#{user_id}`) are fully guessable from public information. An attacker who simply knows a target shop's `myshopify.com` domain can craft the `shopify_app_session` cookie themselves and have it accepted as that shop's real, storage-backed session.

### Finding Description
The broken binding: `bytes_verified_under(Context.api_secret_key) == bytes used to build session_id` holds for the JWT branch (via `Auth::JwtPayload`, which HMAC-verifies the token against `Context.api_secret_key`) but is false for both cookie branches, where `cookie_session_id` just does `cookies[SESSION_COOKIE_NAME]` with no signature check at all [2](#0-1) [3](#0-2) .

Root cause: after OAuth completes, the gem sets the long-lived, non-embedded session cookie's value directly to `session.id`, which is computed deterministically as `"offline_#{shop}"` or `"#{shop}_#{user_id}"` [4](#0-3) [5](#0-4) . Unlike the short-lived OAuth `state` nonce cookie used during `begin_auth`/`validate_auth_callback` (which is a random 15-char string compared against the HMAC-validated `auth_query.state`) [6](#0-5) [7](#0-6) , the post-auth session cookie carries no secret entropy and no signature — it is just a public, computable string.

Attacker's exact request: knowing (or guessing) a shop's `.myshopify.com` domain that has installed the target app, the attacker sends any request to a non-embedded app route with header `Cookie: shopify_app_session=offline_<victim-shop>.myshopify.com`. The host app (per documented usage) calls `SessionUtils.current_session_id(nil, cookies, false)`, gets back the attacker-supplied string unmodified, uses it as a session-storage lookup key, and loads the real `Session` object (with the victim's real access token) that was persisted there during the victim's legitimate OAuth flow [8](#0-7) .

Existing guards do not stop this: `HmacValidator.validate` and the `state` check only protect the OAuth callback itself, not this later session-lookup path [9](#0-8) ; `JwtPayload`'s `aud`/signature checks are simply never reached in the cookie branches; and `Context.setup?`/`private?`/`embedded?` gate configuration, not per-request authenticity. Nothing in `cookie_session_id` or `current_session_id` ties the presented cookie value back to a secret the attacker cannot compute.

### Impact Explanation
Any unprivileged internet user who knows a shop's storefront domain (public information) can obtain that shop's persisted session — including its real offline access token — for every non-embedded deployment (and every embedded deployment that ever falls into the "no token" cookie branch). This is a full authentication bypass and cross-tenant access: one attacker's request is treated as another (victim) tenant's authenticated session, repeatable against any installed shop by substituting the shop domain, with no rate limiting or secret required. This matches the Critical bucket ("authentication bypass ... cross-tenant access").

### Likelihood Explanation
Preconditions: default `Context.setup` with `is_embedded: false` (or an embedded app whose front-end calls `current_session_id` with `shopify_id_token: nil`, e.g. before App Bridge injects a token), and the host app following the gem's documented pattern of loading a session by the ID returned from `current_session_id`. Attacker cost is trivial — no credentials, no XSS, no MITM — just constructing an HTTP request with a computed cookie value. Feasibility is high wherever offline sessions are used (the common case for background/webhook-triggered API work), since `offline_#{shop}` requires zero secret knowledge.

### Recommendation
Do not use a deterministic, publicly-computable string as the bearer identifier stored in the session cookie. Instead, generate a high-entropy random session-cookie value at OAuth-callback time, store the mapping `{random_value => real_session_id}` server-side (or HMAC-sign the cookie value with `Context.api_secret_key`/`old_api_secret_key` and verify the signature in `cookie_session_id` before trusting it), mirroring the verification the JWT branch already performs via `JwtPayload`.
