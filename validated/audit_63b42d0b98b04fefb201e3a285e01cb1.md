## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body, while the `shop` attribute — which callers use to identify which merchant/tenant the webhook belongs to — is read from an HTTP header that is never included in the signed content. Anyone who possesses a single genuine `(raw_body, hmac)` pair for their own shop can replay it against the app's webhook endpoint while swapping the `shopify-shop-domain` / `x-shopify-shop-domain` header value, and the signature check still passes, causing the app to process the payload as if it belonged to a different shop.

### Finding Description
`Webhooks::Registry.process` accepts an incoming `Request` and validates authenticity purely via HMAC: [1](#0-0) 

The HMAC check delegates to `Utils::HmacValidator.validate`, which computes the expected signature from `to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the `shop`, `topic`, `api_version`, and `webhook_id` fields are all sourced from headers that are entirely outside the signed material: [3](#0-2) 

After the HMAC check succeeds, `process` hands `request.shop` (the unauthenticated header value) straight to the app's handler as the tenant identifier for the event: [4](#0-3) 

The identity binding that should hold is:
```
shop_that_produced(hmac, raw_body) == shop_the_handler_is_told_about (request.shop)
```
Because `shop` is excluded from `to_signable_string`, this equality is never enforced — the gem verifies "this body was HMAC'd with our secret" but not "this body belongs to the shop named in this header." Any body/hmac pair that was legitimately generated for shop A remains fully valid when submitted with a header claiming shop B, since `OpenSSL.secure_compare` only checks the body-derived digest.

### Impact Explanation
This breaks the tenant-identity binding: an unprivileged party who has observed (or controls, as an app-installing merchant) one legitimate webhook delivery — body + valid HMAC — for their own shop can resend that exact HTTP request to the app's public webhook endpoint with the `shop-domain` header changed to an arbitrary other shop domain known to have installed the app. The signature check still passes (`Utils::HmacValidator.validate` only checks the body), and `Registry.process` dispatches the event to the app's handler labeled as belonging to the victim shop. Downstream host applications rely on `WebhookMetadata#shop` to select which merchant's stored record/session to act on (e.g., mark uninstalled, update billing state, delete data) — since the routing/tenant selection key itself is forgeable, this is a cross-tenant access primitive rooted entirely in this gem's verification logic, meeting the Critical bar (cross-tenant access) defined in scope.

### Likelihood Explanation
The webhook endpoint is internet-facing by design (Shopify posts webhooks to a public URL), and any user with a functioning app installation on their own shop can capture a real `(raw_body, hmac)` pair from their own webhook traffic through normal legitimate use — no secret key, access token, or privileged access is required. Swapping one header value and replaying the HTTP POST is trivial.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the verified body before it is exposed to handlers — e.g., have `to_signable_string` incorporate the shop header, or require the host app to independently verify that `request.shop` corresponds to a shop for which a session/install actually exists before trusting it as the event's tenant.

### Proof of Concept
1. App has legitimately received a valid webhook for `shop-a.myshopify.com`:
   ```
   POST /webhook
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <valid HMAC of raw_body computed with app's secret>
   x-shopify-shop-domain: shop-a.myshopify.com
   body: {"id": 1}
   ```
2. Attacker (the merchant who owns `shop-a`, or anyone who intercepted this delivery) resends the identical body and HMAC, but changes only the shop header:
   ```
   POST /webhook
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <same HMAC as above>
   x-shopify-shop-domain: shop-victim.myshopify.com
   body: {"id": 1}
   ```
3. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only (per `to_signable_string`) and it matches, so `Registry.process` accepts the request and invokes the handler with `shop: "shop-victim.myshopify.com"` [5](#0-4) , causing the app to act (e.g., process an uninstall) against `shop-victim` even though the signed payload was never produced for that shop.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
