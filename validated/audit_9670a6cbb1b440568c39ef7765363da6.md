### Title
Wallet Contract pays the relayer fee before confirming the underlying eth-emulated transaction executes - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` (the eth-implicit account's contract, reachable from any submitted `FunctionCall` transaction/receipt to an eth-implicit account) fires an unconditional, unchained fee-transfer promise to the relayer as soon as a transaction is classified as an `EOABaseTokenTransfer`/`ERC20Transfer` with a non-zero fee, *before* the actual user action has been validated or executed.

### Finding Description
In `inner_rlp_execute` [1](#0-0) , once `parse_rlp_tx_to_action` classifies the transaction as `EOABaseTokenTransfer`/`ERC20Transfer` with a non-zero `fee`, the code immediately issues a standalone `env::promise_batch_create` + `promise_batch_action_transfer` sending `fee` to the predecessor (the relayer). This promise is *not* chained (`.then(...)`) to the promise that will actually carry out the user's requested action; it is a separate, independent receipt.

The real action is only constructed afterward, in the `match transaction_kind` block [2](#0-1) . For the `EOABaseTokenTransfer { address_check: Some(address), .. }` branch, the address registrar is queried first, and only in `address_check_callback` [3](#0-2)  is it discovered whether the target is actually valid. If the registrar shows the address already corresponds to a registered named account, the callback returns `ExecuteResponse { success: false, error: Some("Invalid target: ...") }` directly (lines 168-172) **without ever building or sending the underlying transfer/call promise**, and without any refund of the fee (the only refund path, for `caller_deposit`, is inside `rlp_execute_callback`'s `PromiseResult::Failed` arm at lines 296-312, which is never reached in this early-return case).

Because the fee-transfer receipt was already dispatched independently before this validation outcome is known, the relayer is paid even though the user's intended action never executes. This is structurally the same bug class as the reported `redeem()` issue: a value-transferring side effect is performed without gating it on confirmation that the paired operation it is compensating for actually succeeded, producing a discrepancy between perceived and actual execution.

### Impact Explanation
An external relayer (or any caller invoking `rlp_execute` with a fee-bearing eth-emulated transaction whose target ends up being an already-registered account) causes the wallet contract to pay out the fee amount from the eth-implicit account's own balance with no corresponding value delivered — the "paid-for" action silently fails. This is an unauthorized balance change / fund loss for the wallet-contract account: NEAR is transferred out of the account balance based on a code path that never validates that the compensated action occurred. Any account/relayer combination hitting this address-collision or generally the multi-step (registrar-check / storage-deposit) branches before the main promise resolves can trigger it, since the fee promise is dispatched at parse time, decoupled from the actual execution outcome.

### Likelihood Explanation
Reachable purely via a normal signed transaction (`FunctionCall` to `rlp_execute` on an eth-implicit account) with attacker-controlled RLP-encoded Ethereum transaction bytes; no validator/node privilege is required. Triggering the specific race requires only that the target's derived address collides with a subsequently-registered named account in the address registrar, which is a realistic scenario given named accounts can be created after an eth-implicit address is referenced. The fee is computed directly from attacker-supplied `max_fee_per_gas` / `gas_limit` fields [4](#0-3) , so the amount at risk is attacker/relayer-influenced.

### Recommendation
Chain the fee-transfer promise onto the same promise sequence as the main action (e.g., attach it via `.then()`/batch it together with the action promise, or move the fee payment into `rlp_execute_callback` and only pay it out conditioned on `PromiseResult::Successful`), so the relayer is compensated only if the corresponding action actually executes. Alternatively, refund the fee in the `address_check_callback`'s early-return branches (lines 161-173) the same way `rlp_execute_callback` refunds `caller_deposit` on failure.

### Proof of Concept
1. A relayer submits `rlp_execute(target, tx_bytes_b64)` where `tx_bytes_b64` decodes to an RLP Ethereum transaction whose payload is unparsable/looks like a base token transfer, `tx.to` corresponds to `target`'s eth-implicit address, and `max_fee_per_gas * gas_limit` yields a non-zero fee.
2. `parse_rlp_tx_to_action` classifies this as `EthEmulationKind::EOABaseTokenTransfer { address_check: Some(address), fee }` (target is `TargetKind::EthImplicit`) [5](#0-4) .
3. `inner_rlp_execute` immediately fires `env::promise_batch_action_transfer(refund_promise, fee)` to the predecessor (relayer) [6](#0-5) .
4. Separately, it queries the address registrar and schedules `address_check_callback`.
5. Suppose, by the time the registrar call resolves, `target`'s address is registered to an existing named account (`maybe_account_id.is_some()`), and the caller is not the signer — `address_check_callback` returns `ExecuteResponse{success:false, error: Some("Invalid target: ...")}` [7](#0-6)  without ever creating/executing the transfer.
6. Net effect: the wallet contract's NEAR balance was already debited by `fee` and sent to the relayer in step 3, but the user's requested transfer never happened — a balance discrepancy identical in class to the reported `redeem()` silent-failure bug.

    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

            };
            let address = format!("0x{}", hex::encode(address));
            address_registrar.lookup(address).then(ext.address_check_callback(
                target,
                action,
                caller_deposit,
            ))

        TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { receiver_id, .. }) => {
            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;
            let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }

            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.

            ext.rlp_execute_callback(caller_deposit)
