### Title
Webhook shop-domain header is trusted for tenant identification but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` validates the request's HMAC against that body alone before handing `request.shop` — taken verbatim from the unsigned `X-Shopify-Shop-Domain` header — to the app's webhook handler as the trusted tenant identifier.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC strictly over `verifiable_query.to_signable_string`. For `Webhooks::Request`, that method is defined as: [1](#0-0) 
which returns only `@raw_body`. The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards this unauthenticated `shop` value to the app's registered handler as the tenant context for the webhook: [3](#0-2) 

The library's own documentation instructs apps to trust `data.shop` for tenant-scoped work dispatch (e.g. `shop_domain: data.shop`), reinforcing that this field is treated as authenticated: [4](#0-3) 

This is the binding the fix should guarantee but does not:
`HMAC-verified(raw_body) == (raw_body, shop)` used by the handler.
In reality only `raw_body` is bound; `shop` is an independent, attacker-controlled header value. Because the webhook secret (`client_secret`) is shared across all shops that install the same app, any merchant who installs the app can legitimately receive a validly-signed webhook `(raw_body, HMAC)` for their **own** shop, then replay that exact `(raw_body, HMAC)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. The HMAC check still passes (it never inspected the header), and the handler processes attacker-controlled body content under the victim shop's identity.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: `request.shop`, used by host apps to scope database writes, background jobs, or state changes, is not authenticated. An unprivileged internet user who is themselves a merchant with the app installed (no special privileges, no access to the victim's credentials or the app's `client_secret`) can inject attacker-controlled webhook payloads that appear to originate from any other shop using the app. Depending on how the host application uses `data.shop` (as shown in the gem's own docs, to key job/queue dispatch), this enables cross-tenant data injection or corruption — a Critical-severity cross-tenant access issue.

### Likelihood Explanation
Likelihood is high: no secret material, no access token, and no privileged account is required — only a normal app installation (available to any Shopify Partner/developer store) to obtain one legitimate `(body, HMAC)` pair, followed by a simple HTTP replay with a modified header value. Standard `curl`/HTTP tooling suffices.

### Recommendation
Bind the shop identity into the signed material used for verification (e.g. verify the `shop-domain` header explicitly against the value returned by Shopify for that specific `webhook-id`/topic pairing via a signed channel), or, at minimum, do not treat `Request#shop` as authenticated tenant context without an out-of-band, per-shop verification step (e.g. only accept webhooks for shops that have an existing installed/offline session, and reconcile any mismatch as an error) before invoking the handler.

### Proof of Concept
1. Merchant A installs the app and receives a legitimate webhook `POST /callback/orders/create` with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker (Merchant A) captures `(B, H)`.
3. Attacker crafts a new HTTP request to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(client_secret, B) == H`, ignoring the shop header: [5](#0-4) 
5. `Registry.process` calls the app's handler with `shop: "victim-shop.myshopify.com"` and Merchant A's attacker-controlled body `B`, spoofing a webhook as if it came from the victim shop.
