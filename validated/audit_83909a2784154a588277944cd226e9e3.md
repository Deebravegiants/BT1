### Title
Webhook `shop`/`topic` headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC signature over the raw request body only, but the `shop`, `topic`, `webhook_id`, and `api_version` values used by the app's handler dispatch logic come from HTTP headers that are excluded from that signature.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) . `HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., only the body) and compares it to the `hmac` accessor, which is likewise derived only from the `hmac-sha256` header [4](#0-3) [5](#0-4) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read from `@headers` via `shopify_header`, none of which participate in the signature [2](#0-1) .

`Registry.process` trusts these unauthenticated header values directly for authorization and dispatch: it validates the HMAC, then looks up the handler by `request.topic` and constructs `WebhookMetadata` with `shop: request.shop` before invoking the app's handler [3](#0-2) .

This breaks the intended identity binding: `HMAC-verified(body)` ≠ `HMAC-verified(shop, topic, webhook_id, api_version)`. The signature proves the request body was signed by the app's `client_secret`/`api_secret_key`, but it proves nothing about which shop or topic the payload is attributed to.

Because a single app uses one shared `api_secret_key` across every merchant installation, an attacker who installs the app on their own store (Shop A) will receive genuinely-signed webhook deliveries. They can capture a `(raw_body, hmac)` pair from their own store and replay it to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name a victim merchant (Shop B) that also uses the app. Since HMAC validation only checks the body, the forged request passes `Utils::HmacValidator.validate` and the handler is invoked with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop.

### Impact Explanation
This is a cross-tenant integrity violation: the app-level webhook handler is invoked believing data originated from and applies to a different merchant's tenant than it actually did. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up/update records, provision resources, or trigger data-redaction/GDPR flows for `shop/redact`, `customers/redact`, `customers/data_request`), an attacker can inject or corrupt another merchant's tenant data, or trigger redaction/deletion actions against a victim shop's records, using only their own legitimately-issued webhook traffic.

### Likelihood Explanation
Requires the attacker to be a legitimate (even free/trial) installer of the target app on their own store — no privileged access, leaked secrets, or social engineering is needed. Capturing their own webhook deliveries and replaying them with a modified `shop-domain`/`topic` header against the app's public webhook endpoint is trivial once installed.

### Recommendation
Bind the security-relevant identity fields into the signed payload verification, not just the body: e.g. build the signable string (or a secondary check) that incorporates the `shop`, `topic`, and/or `webhook_id` headers, or independently verify that the `shop` header corresponds to a shop for which the app has an active, previously-established installation before dispatching. At minimum, document/require host applications to cross-check `request.shop` against their own installation records before trusting it, since the gem's own verification does not bind it.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook (e.g. `orders/create`) to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` header computed over the JSON body using the app's shared `api_secret_key`.
3. Attacker records `(raw_body, hmac_header)`.
4. Attacker crafts a new HTTP request to the same webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` identical, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`, e.g. `customers/redact`).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body/hmac pair [6](#0-5) .
6. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host application to act on the victim's tenant using attacker-supplied data.
