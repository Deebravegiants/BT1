### Title
Webhook `shop-domain` header (and `topic`/`webhook-id`/`api-version`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Utils::HmacValidator.validate` checks binds solely to `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` fields are read directly from HTTP headers and are never included in the signed bytes, yet `Registry.process` trusts them unconditionally and hands them to the host application's handler as the tenant identity.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract requires `to_signable_string` to represent what the HMAC actually attests to: [1](#0-0) 

For `Request`, that signable string is defined as just the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from attacker-controllable HTTP headers, entirely outside the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC against the body only, then immediately trusts `request.shop` (and the other header-derived fields) to build the `WebhookMetadata` passed into the app's handler: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:

`bytes_verified_by_HMAC == bytes_the_handler_acts_on`

Here, `bytes_verified_by_HMAC = raw_body` while `bytes_the_handler_acts_on = raw_body + shop-domain header + topic header + webhook-id header + api-version header`. The equality is broken: the header set is a superset of what's actually signed, so the `shop` field that host applications use to select the tenant/session is not cryptographically bound to the signature at all.

### Impact Explanation
This is a cross-tenant identity break at the boundary the gem is responsible for validating. An unprivileged internet user who legitimately owns *any* shop with the app installed can receive a genuinely Shopify-signed webhook for their own shop (a valid `raw_body` + HMAC pair, computed by Shopify using the app's `client_secret`), then replay that exact HTTP request to the app's public webhook endpoint while only changing the `X-Shopify-Shop-Domain` header to a victim shop's domain (and optionally `topic`/`webhook-id`). `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data came from the victim shop. Any host application that (as this gem's own documentation and `WebhookMetadata` design encourage) uses `data.shop` to look up the merchant/session for processing the payload will act on attacker-supplied data under a victim's tenant identity — a cross-tenant access/data-injection primitive, achieved without ever knowing the app's `client_secret`.

### Likelihood Explanation
Likelihood is realistic for a bug bounty scenario: the attacker only needs their own legitimate (even free/dev) shop installation to capture one valid signed webhook body/HMAC pair, then can freely forge the shop-domain, topic, and webhook-id headers on replay since none of them are covered by the signature. No secret material, TLS interception, or privileged account is required — only a normal internet-facing webhook endpoint exposed by a host app built on this gem, consistent with the gem's own documented usage pattern (`Registry.process(request)` → `handler.handle(data:)`).

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind those header values to the body before trusting them in `WebhookMetadata`. At minimum, document and/or enforce that host applications must independently verify `shop` against a known/registered tenant list rather than trusting the unauthenticated header value that this gem currently forwards verbatim.

### Proof of Concept
1. Attacker installs the target app on their own shop, `attacker.myshopify.com`, and triggers a webhook (e.g. `orders/create`) — Shopify computes `hmac_shopify = HMAC-SHA256(client_secret, raw_body)` and sends:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <hmac_shopify>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: <raw_body>
   ```
2. Attacker captures this request and replays it to the same endpoint, changing only the header:
   ```
   X-Shopify-Shop-Domain: victim.myshopify.com
   ```
   keeping `Body` and `X-Shopify-Hmac-Sha256` identical.
3. In `ShopifyAPI::Webhooks::Registry.process`, `Utils::HmacValidator.validate(request)` recomputes HMAC over `request.to_signable_string` (the unchanged raw body) and it matches — validation passes. [6](#0-5) 
4. `WebhookMetadata.new(..., shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"`, even though the payload never originated from Shopify for that shop. [7](#0-6) 
5. The host application's `WebhookHandler#handle` receives `data.shop == "victim.myshopify.com"` and processes attacker-controlled `data.body` under the victim's tenant context.
