### Title
Webhook Shop Identity Not Bound to HMAC Signature Allows Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` (and `topic`/`webhook-id`) HTTP header to populate `WebhookMetadata.shop`, which the host application's handler uses to attribute the event to a tenant. Because the HMAC signature never covers these headers, any unprivileged party who can obtain one valid `(raw_body, hmac)` pair — trivially available to any merchant who installs the app and receives their own legitimate webhooks — can resend that exact body/HMAC pair with an arbitrary `shop-domain` header and have the app process it as an event belonging to a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is `hmac` and `to_signable_string`. The class defines: [1](#0-0) 
`to_signable_string` returns only `@raw_body`: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string`, i.e. over the raw body: [3](#0-2) 

`Registry.process` gates on this HMAC check and then constructs the `WebhookMetadata` handed to the app's handler using `request.shop`, `request.topic`, and `request.webhook_id` — all of which are read straight from unauthenticated headers, never covered by the HMAC: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `hmac_verified(bytes)` == `bytes that determine the tenant (shop) the event is attributed to`. In this implementation that equality is broken — the HMAC only proves the body wasn't tampered with; it proves nothing about which shop the body came from. `request.shop` (from `shopify-shop-domain`/`x-shopify-shop-domain`) is fully attacker-controlled bytes with no cryptographic binding to the signed payload.

### Impact Explanation
This is a cross-tenant identity confusion at the shop level: an unprivileged actor (any merchant who installs the app, i.e., a low-privilege tenant of the multi-tenant app) can cause the host application to process a webhook body as if it originated from a different, victim shop. Depending on how the host app's `WebhookHandler#handle` implementation keys off `data.shop` (e.g., to look up sessions, credit/debit records, trigger side effects, or write data under a shop record), this can lead to cross-tenant data corruption or unauthorized actions attributed to another merchant's store — satisfying the "cross-tenant access" criterion, since the binding between the authenticated bytes and the shop identity used for authorization/attribution is broken.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker needs at least one legitimately-received `(raw_body, hmac)` pair, which they can trivially obtain by installing the app on their own store and letting Shopify deliver them a real webhook (no `api_secret_key` or victim credentials required — they only reuse a webhook they legitimately received). They then replay that exact body+HMAC to the app's webhook endpoint with a forged `shop-domain` header naming the victim shop. Because `Registry.process` never re-derives or cross-checks the shop against anything cryptographically bound to the payload, the forged request passes validation.

### Recommendation
Bind the shop identity to the verified payload instead of trusting the raw header value:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the string that is HMAC-verified (i.e., extend `to_signable_string` to incorporate these header values, mirroring how Shopify's own webhook signing should be validated end-to-end), or
- At minimum, require host applications to independently verify that `request.shop` matches a shop they have an active, previously-established session for before processing the event, rather than trusting it as ground truth solely because the body HMAC validated.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook event Shopify delivers, capturing the raw POST body and the `x-shopify-hmac-sha256` header value — both valid and verifiable with the app's `api_secret_key` (attacker never sees the secret).
2. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but change the `x-shopify-shop-domain` header to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body`: [6](#0-5) 
4. `Registry.process` then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `shop` value and dispatches it to the app's handler: [7](#0-6) 
5. The host application's handler processes the event believing it originated from `victim.myshopify.com`, even though the body and HMAC were generated for `attacker.myshopify.com`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
