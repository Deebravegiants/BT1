## Title
EvmHost does not refund excess native ETH sent to `dispatch()` / `fundRequest()`, causing overpaid funds to be permanently stuck - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native ETH via `msg.value` and swap it for an exact amount of the fee token using Uniswap V2's `swapETHForExactTokens`. When the caller sends more ETH than needed to cover the exact fee-token output, the router refunds the unused ETH — but it refunds it to `address(this)` (EvmHost), the direct caller of the router, not to the original transaction sender. This causes any ETH overpayment to become permanently trapped in the `EvmHost` contract rather than being returned to the user.

### Finding Description
In all three payment paths, the pattern is identical: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    }
    ...
```

`swapETHForExactTokens` is an "exact output" swap: the caller sends `msg.value` in ETH, the router computes the exact ETH input required to yield `post.fee` (or `get.fee`, or `amount`) units of the fee token, and — per standard Uniswap V2 router behavior — refunds any leftover ETH to `msg.sender` of that call. Because `EvmHost` itself calls the router (`IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)`), the refund lands back in `EvmHost`'s own balance, not the original caller (`_msgSender()`), who is the one who actually overpaid.

The identical pattern repeats in:
- `dispatch(DispatchGet)`: [2](#0-1) 
- `fundRequest(bytes32,uint256)`: [3](#0-2) 

None of these three functions checks for or refunds any leftover `msg.value` (or leftover ETH balance in `EvmHost` after the swap) back to `_msgSender()`.

This is directly analogous to the reported `FootiumAcademy` bug class: a user pays native currency to cover a fee, and any surplus beyond what's actually required is silently retained by the contract instead of refunded.

By contrast, other parts of this same codebase correctly implement surplus refunds for native-token overpayment, showing the expected pattern was known but not applied to `EvmHost`: [4](#0-3) 

### Impact Explanation
Any application (an `IApp`) or end user integrating `EvmHost.dispatch()` or `EvmHost.fundRequest()` who overestimates the ETH required (a common practice to safely cover volatile swap slippage, as also acknowledged in the SDK/docs: "Excess native is refunded by the uniswap router" — an assumption that is incorrect here since the refund goes to EvmHost, not the caller) will have the excess ETH become permanently stuck in `EvmHost`. Given `dispatch()` is the primary entrypoint for **every** cross-chain POST/GET message on Hyperbridge, this affects a very broad, unprivileged surface — any relayer, app, or user dispatching a message with native-token payment. There is no discovered rescue mechanism in `EvmHost.sol` for stray native ETH (the `withdraw`-named functions found are in unrelated contracts — `HostManager.sol`, `IntrinsicIntents.sol`, `ExtrinsicIntents.sol`, and Uniswap wrapper utils — not `EvmHost` itself), so the funds are plausibly frozen forever, constituting a fund-loss/freezing issue of at least Medium severity.

### Likelihood Explanation
This is highly likely to occur in practice: because the exact ETH cost of a Uniswap V2 swap is unknown ahead of time (subject to price movement/slippage between quote and execution), callers must send an ETH buffer above the expected `getAmountsIn` estimate to avoid reverts. The SDK's own `quoteNative` helper doc-comments explicitly reference this behavior and even the LayerZero endpoint adapter deliberately applies "a generous 2x buffer to absorb ... Excess native is refunded by the uniswap router" — reflecting the developers' expectation that overpaid ETH would come back to them, when in fact it is retained by `EvmHost`. [5](#0-4) 

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the router's return value (`amounts[0]`, the actual ETH spent) or check `address(this).balance` delta, and refund any leftover `msg.value` back to `_msgSender()` via a low-level call, mirroring the refund pattern already used in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`.

### Proof of Concept
1. Alice calls `EvmHost.dispatch{value: 2 ether}(post)` with `post.fee = 100e18` (fee token units), intending to cover slippage since she doesn't know the exact ETH price at execution time.
2. `EvmHost` calls `swapETHForExactTokens{value: 2 ether}(100e18, [WETH, feeToken], address(this), deadline)`.
3. Suppose only 1 ETH was actually required to produce `100e18` fee tokens. The Uniswap V2 router refunds the remaining `1 ether` to `msg.sender` of the swap call — which is `EvmHost`, not Alice.
4. `EvmHost`'s ETH balance increases by 1 ether that belongs to Alice; `dispatch()` returns normally with no refund logic executed.
5. Alice has permanently lost 1 ETH with no function in `EvmHost.sol` to reclaim it.
