### Title
`pallet-hyper-fungible-token` calldata signature omits chain/message binding, enabling cross-context replay of a captured signature to force-dispatch an arbitrary runtime call as the victim - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The `on_accept` handler in `pallet-hyper-fungible-token` verifies the `SubstrateCalldata.signature` over a payload of just `(nonce, runtime_call)` — the beneficiary's account nonce and the call bytes — with no domain separation for the destination `StateMachine`, the source chain/contract, the asset/amount transferred, or any per-message commitment. This mirrors exactly the `changeRecipientAddress` bug class: a signature over a "very generic" payload that stays valid for any context sharing the same `(nonce, runtime_call)` pair.

### Finding Description
`on_accept` builds the verified message as:
```rust
let nonce = frame_system::Pallet::<T>::account_nonce(beneficiary.clone());
let payload = (nonce, substrate_data.runtime_call.clone()).encode();
``` [3](#0-2) 

This is then checked with `ed25519_verify`/`sr25519_verify`/`secp256k1_ecdsa_recover` against `beneficiary`, and on success the `runtime_call` is dispatched `RawOrigin::Signed(beneficiary)` [4](#0-3) .

Crucially, the `beneficiary` (i.e., whose signature is checked and on whose behalf the call is dispatched) is taken from `message.to`, which is fully attacker-controlled: any signed account can call the public `send` extrinsic, which lets the caller set `recipient` (→ `message.to`), `call_data` (→ `message.data`, decoded as `SubstrateCalldata`), `destination`, `asset_id` and `amount` arbitrarily [5](#0-4) .

Since `pallet-hyper-fungible-token` and its ABI-compatible message format are meant to be deployed identically "on any chain" [6](#0-5) , an attacker who observes any previously valid `(signature, runtime_call)` pair for a victim (these are public, embedded in on-chain `PostRequest`/`send` calldata and relayer-visible) can embed that exact `SubstrateCalldata` blob into their own `send()` call — naming the victim as `recipient`, on any `destination` chain/asset combination the attacker chooses — and as long as the victim's `frame_system` nonce on that destination still equals the value baked into the captured signature, the check passes and the call is dispatched as the victim. Nothing in the verified payload ties the signature to: the specific `PostRequest`/message it was intended for, the destination `StateMachine`, the source contract, or the asset/amount actually being delivered alongside it.

### Impact Explanation
A successful replay lets an unrelated attacker force an arbitrary previously-signed `RuntimeCall` to execute under `RawOrigin::Signed(victim)` on a chain/context the victim never intended, subject only to the `BaseCallFilter` [7](#0-6) . Because the account nonce is otherwise a shared, chain-local counter that also advances via unrelated victim activity (any extrinsic the victim signs on that chain), and because the same substrate `AccountId32` keys are reused across many parachains, this is a realistic "unauthorized app action" primitive: an attacker can wait for/target a moment when the victim's nonce matches a previously observed signed call and trigger dispatch of that call (e.g., a `Balances::transfer_allow_death`, as demonstrated in the pallet's own test) via their own unrelated `send()` transaction, at their chosen time and destination, out of the victim's control. This satisfies the "unauthorized app action" impact bar.

### Likelihood Explanation
Medium. The precondition — the victim's current `frame_system` account nonce on the target chain exactly matching the nonce baked into a previously captured signature — narrows the window, but is realistic: a freshly-created/rarely-used account (nonce 0, common right after an incoming cross-chain mint with attached calldata as shown in the pallet's own test) is squarely in scope, and the exploit requires no special privilege — merely calling the public, `Signed`-origin `send` extrinsic with a captured signature blob.

### Recommendation
Bind the signed payload to the full message context, mirroring how `pallet-ismp-relayer` protects its signed payloads by folding in `state_machine`/nonce (`modules/pallets/relayer/src/withdrawal.rs`, `accumulate.rs`). At minimum include: the destination `StateMachine`, the source contract/chain identifier, the request commitment (or `asset_id`+`amount`), in addition to the account nonce, e.g. `(nonce, dest_state_machine, source, asset_id, amount, runtime_call).encode()`. This ensures a signature is valid only for the exact cross-chain message it was produced for and cannot be replayed into a different `send()` call chosen by a third party.

### Proof of Concept
1. Victim signs a `SubstrateCalldata{signature, runtime_call}` intended to run alongside a legitimate incoming HFT transfer to their own account (nonce = 0), e.g. as in `modules/pallets/testsuite/src/tests/pallet_hyper_fungible_token.rs:255-322` — `payload = (0u64, runtime_call).encode()`, signed with the victim's key.
2. This `SubstrateCalldata` bytes (public — embedded in the relayed `PostRequest.body`) is observed by an attacker before/while the victim's account nonce is still 0 on the target chain.
3. Attacker calls `HyperFungibleToken::send` themselves, setting `recipient = victim`, `destination` and `asset_id`/`amount` of their choosing, and `call_data = captured_substrate_calldata_bytes`.
4. On delivery, `on_accept` recomputes `nonce = account_nonce(victim) == 0`, recovers/verifies the signature against `(0, runtime_call)`, which matches, and dispatches `runtime_call` as `RawOrigin::Signed(victim)` — even though this `send()` was never authorized nor initiated by the victim for this new message. ## Cross-Chain Message Format

The pallet encodes messages using the same ABI format as the Solidity contracts:

```solidity
struct Message {
    bytes from;    // original sender (for timeout refunds)
    bytes to;      // recipient on destination chain
    uint256 amount;
    bytes data;    // optional calldata
}
```

This ensures full compatibility between `pallet-hyper-fungible-token`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` on any chain.
