### Title
Non-embedded OAuth session cookie value is a predictable identifier (`shop_userID` / `offline_shop`), not a random secret, enabling session fixation/hijacking - (File: `lib/shopify_api/auth/session.rb`, `lib/shopify_api/auth/oauth.rb`)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser session cookie's value directly to `session.id`, and `session.id` is not a random token — it is deterministically derived from public/guessable data: `"#{shop}_#{associated_user.id}"` for online sessions or `"offline_#{shop}"` for offline sessions.

### Finding Description
In the OAuth callback flow, after the HMAC-verified `AuthQuery` and the access-token exchange, the resulting `Session` object's `id` is computed in `Session.from` as: [1](#0-0) 

This `id` is then used verbatim as the value of the browser-facing session cookie in the non-embedded flow: [2](#0-1) 

Later, `ShopifyAPI::Utils::SessionUtils.cookie_session_id` simply reads this cookie value back out with no additional verification/signature check, treating it as the sole session lookup key that a host app should use to fetch a stored `Session`: [3](#0-2) 

The binding this breaks, expressed as an equality that no longer holds: `bytes presented in the session cookie == a value only derivable by a party who completed HMAC-verified OAuth`. Because the cookie value is `shop + "_" + numeric_user_id` (or `"offline_" + shop`) rather than a `SecureRandom` opaque token (compare `Session.new`'s default `id: id || SecureRandom.uuid`, which is bypassed by `Session.from`), any party who knows or enumerates a target shop's domain and a merchant staff user's numeric ID (exposed via many public/semi-public channels: Admin API user IDs, other app installs, GraphQL `staff` responses, etc.) can construct the exact cookie value without ever completing OAuth or possessing the app's `client_secret`.

### Impact Explanation
This falls under "session fixation or forced OAuth completion" (explicitly listed High-impact category). An attacker who can set/guess this cookie value in a victim's browser (session fixation) or who submits it directly to a vulnerable host app's endpoint (session hijacking via ID prediction) can be treated by the host app as the corresponding merchant session, since `cookie_session_id` performs no cryptographic verification of the value — it is used as a raw lookup key. Because the gem is the one generating this predictable value and documenting `cookie_session_id`/`current_session_id` as the mechanism for retrieving "the" session, the un-randomized session identifier is an authentication-boundary weakness contained entirely within this library's OAuth/session code, not merely a host-app misuse of a documented API.

### Likelihood Explanation
The `offline_#{shop}` case requires only knowledge of the shop's `myshopify.com` domain, which is essentially public. The online `#{shop}_#{user.id}` case requires the numeric associated-user ID, which is often sequential/enumerable and frequently leaked through other Shopify Admin API responses or other installed apps sharing the same merchant staff. No secret material (`api_secret_key`, access token) is needed to construct the value, making exploitation practical for any host app that relies on this cookie value as a bearer/session credential per the gem's documented flow.

### Recommendation
Do not use the deterministic `Session#id` as the browser-facing session cookie value. Generate a separate, cryptographically random, unguessable session cookie value (e.g., `SecureRandom.uuid`/`SecureRandom.hex`) that is mapped server-side to the actual `Session` record, decoupling the externally-visible cookie token from the internally meaningful, predictable session key.

### Proof of Concept
1. App is configured as non-embedded; a merchant completes OAuth for `shop-a.myshopify.com`, online access, user ID `123`. The gem sets the browser cookie `shopify_app_session=shop-a.myshopify.com_123`.
2. Attacker who knows the shop domain and merchant user ID `123` (e.g., discovered via another installed app or public info) sets `shopify_app_session=shop-a.myshopify.com_123` in their own browser without ever performing OAuth.
3. Host app calls `SessionUtils.current_session_id` → `cookie_session_id(cookies)`, which returns `"shop-a.myshopify.com_123"` verbatim: [4](#0-3) 
4. The host app looks up its session store using this ID and returns the merchant's stored `Session` (with real `access_token`) to the attacker, granting cross-tenant access to that merchant's data without ever proving possession of a legitimate session.
