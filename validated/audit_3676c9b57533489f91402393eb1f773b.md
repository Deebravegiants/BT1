### Title
seedMetadataAtom.set() is callable directly by any consumer, bypassing wallet's lock-state and seedId validation - ([File: features/wallet/atoms/seed-metadata.js])

### Summary
`seedMetadataAtom` is a `public: true` storage atom with `isSoleWriter: true`, but `isSoleWriter` is purely documentation-level: the `storage.ts` factory does not even destructure or use `isSoleWriter` anywhere in `createStorageAtom`, and `enforceObservableRules` performs no writer-identity, origin, or lock-state check on `.set()`. Any module in the DI graph that lists `seedMetadataAtom` as a dependency receives the exact same singleton instance and can call `.set()` directly, completely bypassing `Wallet#assertWalletIsUnlocked` and the seedId-consistency logic in `wallet.js`.

### Finding Description
`seed-metadata.js` creates the atom via `createStorageAtomFactory({ storage })({ key: 'seedMetadata', isSoleWriter: true })` and registers it as a public dependency-injection node (`id: 'seedMetadataAtom', public: true`) [1](#0-0) .

Looking at `createStorageAtomFactory`/`createStorageAtom` in `libraries/atoms/src/factories/storage.ts`, the function signature destructures only `{ key, defaultValue }` from `Params<D>` — `isSoleWriter` is declared in the `Params` type but never read or enforced anywhere in the closure body [2](#0-1) . The resulting `get`/`set`/`observe` are wrapped by `enforceObservableRules`, which only adds concurrency serialization, setter-function support, and freezing of returned values — it performs no writer-identity check, no origin/lock-state gating, and no `isSoleWriter` enforcement of any kind [3](#0-2) .

Wallet's own business logic (`wallet.js`) does gate seed metadata writes behind `#assertWalletIsUnlocked()` and seedId validation in `addSeed`, `removeManySeeds`, and `updateSeed` [4](#0-3) [5](#0-4) . However, these checks live entirely in the `Wallet` class methods, not in the atom itself.

Because `@exodus/dependency-injection`'s `Container` instantiates each node exactly once and hands out the same reference to every declared consumer ("Only one instance of every node is ever created") [6](#0-5) , and `seedMetadataAtom` is marked `public: true` (making it resolvable by id from any module that lists it in `dependencies`) [7](#0-6) , a module elsewhere in the dependency graph that adds `seedMetadataAtom` to its `dependencies` array receives the live, writable atom object and can call `.set(...)` directly — with no lock check, no seedId shape validation, and no origin binding — same as `Wallet` itself does internally.

### Impact Explanation
A module that gains a reference to `seedMetadataAtom` (via inclusion in a plugin/module definition's `dependencies` list) can overwrite or inject arbitrary seed metadata regardless of wallet lock state, since neither the atom factory nor `enforceObservableRules` enforce lock/auth or writer-identity restrictions — `isSoleWriter` is not runtime-enforced at all in this atom implementation. This corrupts wallet-managed state (labels, `dateCreated`/`dateUpdated`, extra-seed bookkeeping) read via `wallet.getSeedMetadata()`, independent of `Wallet#isLocked()`.

### Likelihood Explanation
Requires a module in the dependency graph to declare `seedMetadataAtom` as a dependency — the audit's stated precondition is that an attacker-controlled/malicious plugin definition achieves this via the plugin/module registration list, which is explicitly excluded from scope ("test only the runtime enforcement, not the injection vector"). Given that precondition, the exploit is fully deterministic and reproducible: any reference-holder can call `.set()` at any time with no additional preconditions (no lock bypass needed, no timing window) because the atom performs zero authorization checks.

### Recommendation
Enforce `isSoleWriter` at the atom-factory level (e.g., reject `.set()` calls from callers other than the designated owner, or don't expose a `.set()` method on the public atom reference at all — expose a read-only projection via `readOnly()`/an enhancer to non-wallet consumers, keeping the writable instance private to the `wallet` module). Additionally, move/duplicate the lock-state and seedId validation into the atom's `set` path (or wrap it with a guard) so that authorization is enforced regardless of which module calls `.set()`, rather than relying solely on `Wallet`'s business-logic methods as the only enforcement point.

### Proof of Concept
```js
// libraries/atoms style unit test
import createInMemoryStorage from '@exodus/storage-memory'
import createStorageAtomFactory from '@exodus/atoms/src/factories/storage.js'

const storage = createInMemoryStorage()
const createAtom = createStorageAtomFactory({ storage })
const seedMetadataAtom = createAtom({ key: 'seedMetadata', isSoleWriter: true })

// Simulate a second "consumer" module receiving the same DI-resolved reference
const maliciousConsumerReference = seedMetadataAtom

// Attacker-influenced module calls .set() directly, bypassing Wallet entirely
await maliciousConsumerReference.set({ fake: { label: 'x' } })

const value = await seedMetadataAtom.get()
expect(value).toEqual({ fake: { label: 'x' } }) // succeeds: no error thrown, no lock/seedId check enforced

// Expected (secure) behavior: this call should throw, e.g.
// "seedMetadataAtom: unauthorized writer" or "wallet is locked"
// Actual: silently succeeds regardless of wallet lock state, proving isSoleWriter
// is a documentation convention only, not a runtime restriction.
```
