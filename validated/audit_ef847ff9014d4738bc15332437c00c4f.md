## Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which are taken from HTTP headers and handed to the app's webhook handler as trusted, tenant-identifying data — are never included in the signed content. Anyone who can produce (or replay) one valid `(raw_body, hmac)` pair for the app's secret can attach an arbitrary `shop-domain` header and have the library treat the request as an authenticated webhook for a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors read directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC via `Utils::HmacValidator.validate(request)`, and then immediately constructs `WebhookMetadata` from the unauthenticated header fields (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`) and dispatches it to the registered handler: [3](#0-2) 

`HmacValidator.validate` in turn only ever hashes `verifiable_query.to_signable_string`, i.e. the raw body: [4](#0-3) 

The broken identity-binding equality is:

`shop_bound_by_HMAC (none — HMAC only covers raw_body)` ≠ `shop_trusted_by_handler (== request.shop, an unauthenticated header)`

Because the header value is never part of the signed content, a valid `(body, hmac)` pair computed for one shop's webhook remains valid when the `x-shopify-shop-domain` (or `shopify-shop-domain`) header is swapped for a different shop. The same applies to `topic` and `webhook_id`, letting an attacker also relabel the event type or ID delivered to the handler while reusing a genuine signature.

### Impact Explanation
Webhook handlers built on top of this gem key their multi-tenant business logic on `WebhookMetadata#shop` (e.g., looking up the merchant record, applying the payload to that tenant's data). Since `shop` isn't bound to the HMAC, an attacker capable of obtaining a single genuine `(body, hmac)` pair for the app's secret (e.g., from a webhook delivered for their own shop) can relabel it to a victim shop's domain and have the app process attacker-controlled data under another tenant's identity — a cross-tenant integrity/authentication violation for any consumer of this API.

### Likelihood Explanation
Exploitation requires the attacker to possess a legitimately-signed `(raw_body, hmac)` pair, which they can obtain for their own tenant simply by installing the app and letting Shopify deliver a real webhook (or by using Shopify's own "send test webhook" functionality), without ever needing the app's `client_secret`. They then only need to alter the `shop-domain` (and optionally `topic`/`webhook-id`) header before it reaches the app's HTTP endpoint that calls `Registry.process`. No compromise of the app's credentials or infrastructure is required — only control of a single header value that this library fails to authenticate.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signable content (or otherwise cryptographically bind them to the signature), so that `Registry.process` cannot be tricked into attributing a validly-signed body to a different shop/topic/webhook than the one Shopify actually authenticated.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger (or wait for) any real webhook delivery, capturing the raw body `B` and its `x-shopify-hmac-sha256` header `H` (valid for the app's secret).
2. Replay the captured request to the app's webhook endpoint, but change the `x-shopify-shop-domain` header to `victim.myshopify.com` (and optionally change `x-shopify-topic`/`x-shopify-webhook-id`), keeping body `B` and hmac `H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)` over `B` only — validation succeeds — and dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: JSON.parse(B), ...)` to the handler, which now processes attacker-supplied content believing it originated from `victim.myshopify.com`.
