### Title
Tron `IntentGatewayV2.onAccept` omits the relayer allowlist gate present in the canonical EVM `ExtrinsicIntents.onAccept`, weakening delivery authorization parity across deployments - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The ENS bug pattern is: a security-critical state update (fuse/permission enforcement) is implemented correctly in one canonical path (`NameWrapper`) but a parallel caller (`ETHRegistrarController`) bypasses it, silently degrading the permission model. The same class of bug is reachable in Hyperbridge's intents stack: the mainline upgradeable `ExtrinsicIntents.onAccept` (used by `IntentGatewayV2` on standard EVM chains) enforces a relayer allowlist via `_checkRelayer(incoming.relayer)` before processing any delivery, while the parallel Tron deployment of the same logical contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements `onAccept` without ever calling an equivalent check.

### Finding Description
`ExtrinsicIntents.onAccept` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` calls `_checkRelayer(incoming.relayer)` immediately after the `onlyHost` modifier, before decoding the request kind or acting on it: [1](#0-0) 

This gate is deliberately part of the delivery-authorization design: per the repo's own architecture notes, the relayer allowlist is meant to be the last line of defense against a forged or unauthorized delivery, especially if the trusted handler/consensus path is ever compromised — "the HostManager therefore runs the same relayer check before decoding any governance action" and the gate "belongs to the token that needs it." [2](#0-1) [3](#0-2) 

The Tron deployment's `IntentGatewayV2.onAccept`, however, processes `RedeemEscrow`/`RefundEscrow`/`NewDeployment`/`UpdateParams`/`SweepDust` with no such call anywhere in the contract: [4](#0-3) 

Exactly as in the ENS finding — where `ETHRegistrarController.renew` calls `base.renew` directly instead of routing through `NameWrapper.renew`, silently skipping the `_setData` fuse update that the wrapper contract is relied upon to perform — the Tron `IntentGatewayV2` implements the withdrawal/governance dispatch logic directly instead of routing delivery authorization through the same relayer-allowlist step that the canonical implementation treats as part of its permission model.

### Impact Explanation
On the EVM mainline, if the trusted `handler` (settable via `HostManager`/`SetHostParam`) or the underlying consensus client is ever compromised or misconfigured, the relayer allowlist is the additional authorization boundary that limits which account can push `onAccept` deliveries through to escrow release/governance execution. The Tron deployment has no equivalent second boundary: any account that gets a message accepted by the Tron host's handler can trigger `withdraw()` (releasing escrowed funds) or governance-only actions (`NewDeployment`, `UpdateParams`, `SweepDust`) as soon as the (weaker) source/authenticate checks pass, with no allowlisted-relayer requirement ever configurable. This removes a documented, intentional defense-in-depth layer from one deployment of otherwise-identical production code, creating an inconsistent, weaker permission model on Tron relative to the canonical implementation — directly mirroring the ENS root cause of "critical permission-enforcing logic exists in one place but is bypassed by a parallel caller of the same operation."

### Likelihood Explanation
The Tron `IntentGatewayV2` is production code deployed to handle real escrowed value (`withdraw`, `SweepDust`, governance instance registration), reachable by any relayer submitting a valid proof to the Tron host/handler — no privileged role is required to trigger the missing-gate condition; it is simply the default, permanent behavior of this contract, not a transient misconfiguration.

### Recommendation
Add the equivalent `_relayer`/`_checkRelayer` mechanism (and its host-only setter) to `evm/tron/contracts/apps/IntentGatewayV2.sol` so its `onAccept`/`onGetResponse` enforce the same relayer-allowlist gate as `ExtrinsicIntents.onAccept`, restoring authorization parity between the two deployments of the same gateway logic.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` on Tron and register a remote gateway instance via `NewDeployment` as intended.
2. A user places a cross-chain order and escrow is locked in the Tron gateway (`_orders[commitment][token]`).
3. Any relayer (not a governance-designated/allowlisted one) delivers a `RedeemEscrow`/`RefundEscrow` `PostRequest` through the Tron host's `dispatchIncoming` → `onAccept`, per `evm/tron/contracts/apps/IntentGatewayV2.sol:629-635`.
4. Because no `_checkRelayer`-equivalent call exists, `authenticate(incoming.request)` and the module-source check are the only guards; the mainline's extra relayer-allowlist boundary described in `sdk/packages/core/docs/ai/flows/how-a-cross-chain-delivery-reaches-the-gateway-and-where-the.md:14-21` is entirely absent, so any delivery that passes the handler/consensus layer executes `withdraw()` or governance updates without the second permission check the canonical contract requires.
