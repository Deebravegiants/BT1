## Title
Improper privilege management in the Tron `IntentGatewayV2.onAccept` — missing relayer allow-list gate on escrow-release delivery - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

## Summary
The Tron variant of `IntentGatewayV2.onAccept` authorizes escrow-release/refund delivery only via `onlyHost` (caller must be the local ISMP host) plus `authenticate(incoming.request)` (source must be a known IntentGateway instance). It never checks `incoming.relayer` against an allow-listed relayer, unlike the mainline EVM implementation.

## Finding Description
`onAccept` in `evm/tron/contracts/apps/IntentGatewayV2.sol` handles `RedeemEscrow`/`RefundEscrow` requests by calling `authenticate(incoming.request)` and then `withdraw(body, ...)`: [1](#0-0) 

`authenticate` only checks that `request.from` matches the registered peer instance for `request.source` — it never inspects `incoming.relayer`: [2](#0-1) 

Compare this to the mainline EVM implementation (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`), which gates every `onAccept`/`onGetResponse` delivery behind `_checkRelayer(incoming.relayer)` before decoding the body, and which the project's own design docs describe as the authorization boundary for delivery: [3](#0-2) [4](#0-3) 

`EvmHost.dispatchIncoming` passes through `_msgSender()` as `relayer` for *any* caller who submitted a valid message-delivery proof to `HandlerV2` — it is not itself an authorization gate, it is informational plumbing that downstream apps are expected to check: [5](#0-4) 

Because the Tron `IntentGatewayV2` never performs this check, any account that can produce a valid state/consensus proof for a genuine `RedeemEscrow`/`RefundEscrow` request that was legitimately dispatched by a peer instance can be the one to deliver it through `HandlerV2`, becoming the `relayer` argument with no restriction. This mirrors the structure of the reported bug class (CWE-269: a REST/interface actor without the intended privilege can act on a resource — here, delivery — merely by knowing/possessing the object, here the proof of a known request/commitment), since delivery authorization intended to be relayer-gated is not enforced.

## Impact Explanation
Impact is bounded: `withdraw()` sends escrowed tokens strictly to `body.beneficiary`, which is fixed by the original order (`order.user` for refunds, the filling solver for redemption) — an unauthorized deliverer cannot redirect funds to themselves. The primary consequence of the missing gate is loss of the relayer allow-list control that the rest of the protocol relies on to prevent griefing/racing and to enforce operational policy (e.g., pausing delivery, coordinated upgrades via the gated relayer). It also creates an inconsistency with the documented/tested security invariant ("a delivery from anyone but the authorised relayer never decodes the body... leaves no receipt") that the mainline contract enforces and that downstream tooling (indexers, bots) may assume holds uniformly across all `IntentGatewayV2` deployments, including Tron.

## Likelihood Explanation
Likelihood is high for triggering the code path (any relayer submitting a valid proof reaches it) but the exploitable value is limited since fund destination is fixed by the order. The severity of the deviation itself — an authorization check present in the reference implementation but absent in a shipped variant — is what drives this above "low."

## Recommendation
Add the same relayer allow-list gate (`_checkRelayer(incoming.relayer)` equivalent) at the top of `onAccept` (and `onGetResponse`) in `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirroring `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, so delivery authorization is consistent across all `IntentGatewayV2` deployments.

## Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a relayer configured (if such a mechanism is later added) or observe that none exists today — as shipped, `onAccept` has no relayer-state variable at all (`grep` for `_relayer`/`_checkRelayer` in this file returns no matches).
2. A user places a cross-chain order on the source chain; a solver fills it on the destination, which dispatches a `RedeemEscrow` `PostRequest` back to source.
3. Any third-party account (not a designated relayer) submits the consensus/state proof for this request to `HandlerV2`, which calls `EvmHost.dispatchIncoming(request, thirdParty)`.
4. `IntentGatewayV2.onAccept` executes `authenticate` (passes, since `request.from`/`source` match the registered peer) and processes the withdrawal — with no check on `incoming.relayer` at all, confirming the gate the mainline contract has is absent here. [1](#0-0)
