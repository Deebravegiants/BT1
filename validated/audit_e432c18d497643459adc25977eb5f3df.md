### Title
Non-embedded session cookie value is trusted as an unauthenticated session identifier, enabling cross-tenant session hijacking - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` returns the raw, unsigned value of the `shopify_app_session` cookie as the lookup key a host application uses to retrieve a stored `Session` (and its `access_token`). Because the cookie carries no cryptographic binding (no HMAC/signature) to the OAuth grant that created it, and because the session id format is deterministic and guessable, an attacker who controls the value of their own request's cookie header can substitute another tenant's session id and cause the host app to serve their request using a different shop's stored `access_token`.

### Finding Description
This mirrors the analog vulnerability class: *"a session id derived from unauthenticated bytes."*

When a non-embedded OAuth flow completes, `ShopifyAPI::Auth::Oauth.validate_auth_callback` builds a cookie whose `value` is simply `session.id`: [1](#0-0) 

`session.id` is not random — it is deterministically derived from the shop domain (and user id for online tokens): [2](#0-1) 

The `SessionCookie` struct that carries this value has no signature or MAC field at all — it is just `name`, `value`, `expires`: [3](#0-2) 

Later, when the host app needs to identify "the current session" for a request, it calls `SessionUtils.current_session_id`, which — for non-embedded apps, or as a fallback for embedded apps without a bearer token — reads the cookie value verbatim and returns it as the session id, with no verification step: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`cookie_value == session_id_cryptographically_bound_to_this_browser's_completed_OAuth_grant`

but what is actually enforced is only:
`cookie_value == <opaque client-supplied bytes>`

Since the id format is public and predictable (`"#{shop}_#{associated_user.id}"` for online sessions, `"offline_#{shop}"` for offline sessions, per `Session.from` and `SessionUtils.offline_session_id`/`jwt_session_id`), any user of the multi-tenant app (a merchant of shop A, i.e. an "unprivileged" party with respect to shop B's data) can simply send a request with `Cookie: shopify_app_session=offline_shop-b.myshopify.com` (or `shop-b.myshopify.com_<known_user_id>`). Because `HttpOnly` only blocks JavaScript access, not the ability of a client to set arbitrary headers on requests it sends itself, this requires no XSS — only knowledge (or a guess/enumeration) of another shop's domain.

`current_session_id`'s return value is documented as the key host apps use to load a `Session` object from their own storage and subsequently make authenticated Admin API calls with its `access_token`: [6](#0-5) 

Thus the library hands the host application a tenant-selection key that is not authenticated in any way, contrary to what "session cookie" implies.

### Impact Explanation
This is a cross-tenant access primitive: an attacker who has completed installation for their own shop (or who simply knows/guesses another shop's `myshopify.com` domain) can cause the host app, built per this gem's documented pattern, to load and act with a different shop's stored offline or online access token. That access token can then be used to read/write the victim shop's Admin API data — a direct breach of the shop-to-session identity binding this gem is responsible for establishing and asserting on every request.

### Likelihood Explanation
High reachability: any client of a non-embedded app (or an embedded app falling back to the cookie path) can freely set the `Cookie` header on their own outbound HTTP requests. No secrets, XSS, or privileged access are required — only knowledge of the deterministic id format (published in this repo's own source/docs) and the target shop's domain, which is not secret (myshopify.com subdomains are commonly guessable/enumerable).

### Recommendation
Do not use the raw cookie value as a trusted session-lookup key. Either:
1. Sign/MAC the cookie value (e.g., HMAC it with `Context.api_secret_key`, verified in `current_session_id`/`cookie_session_id` before use), or
2. Bind the cookie to server-side state (e.g., store an opaque, randomly generated token server-side that maps to the session id, rather than embedding the derivable `shop`/`user_id` directly in a value trusted from the client), or
3. At minimum, require every session lookup driven by `current_session_id` to be re-validated against a subsequent authenticated signal (e.g., a valid session token / JWT) before the associated `access_token` is used for outbound requests.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, completing OAuth and receiving cookie `shopify_app_session=offline_attacker.myshopify.com` (or `attacker.myshopify.com_<uid>` for online mode).
2. Attacker sends a request to the host app's authenticated endpoint with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com` (guessed/known victim domain).
3. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged: [7](#0-6) 
4. Host app loads the `Session` stored under that id (victim shop's stored offline session/access token, per its own storage keyed by this id, as recommended in `BREAKING_CHANGES_FOR_V16.md`), and uses `session.access_token` to serve the attacker's request against the victim shop's data.

##### Example
Your app should call `validate_auth_callback` to construct the `Session` object and cookie that will be used later for authenticated API requests.

1. Call `validate_auth_callback` to construct `Session` and `SessionCookie`.
2. Update browser cookies with the new value for the session.
3. Store the `Session` object to be used later when [making authenticated API calls](#using-oauth-session-to-make-authenticated-api-calls).
   - See [Make a GraphQL API call](https://github.com/Shopify/shopify-api-ruby/blob/main/docs/usage/graphql.md), or
   [Make a REST API call](https://github.com/Shopify/shopify-api-ruby/blob/main/docs/usage/rest.md) for examples on how to use the result `Session` object.

An example is shown below in a Rails app but these steps could be applied in any framework:

```ruby
def callback
  begin
    # Create an AuthQuery object from the request parameters,
    # and pass the list of cookies to `validate_auth_callback`
    auth_result = ShopifyAPI::Auth::Oauth.validate_auth_callback(
      cookies: cookies.to_h,
      auth_query: ShopifyAPI::Auth::Oauth::AuthQuery.new(
        request.parameters.symbolize_keys.except(:controller, :action)
      )
    )

    # Update cookies with the authorized access token from result
    cookies[auth_result[:cookie].name] = {
      expires: auth_result[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_result[:cookie].value
    }

    # Store the Session object if your app has a DB/file storage for session persistence
    # This session object could be retrieved later to make authenticated API requests to Shopify
    MyApp::SessionRepository.store_session(auth_result[:session])
```
