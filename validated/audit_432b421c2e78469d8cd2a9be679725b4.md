### Title
Empty `erc20TokenAddresses` in Emporium actions disables all balance/UTXO accounting, letting an attacker drain any real ERC20 balance held by the Emporium contract via an unaccounted `EmporiumOperation` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` only computes `balancesBefore`/`balancesAfter` for tokens listed in `circomData.erc20TokenAddresses`, and `Hinkal.transact` performs its own conservation check over the very same array. Because `CircomDataBuilder.formInputForCircom` explicitly allows `circomData.erc20TokenAddresses.length == 0` for Emporium actions (`formInputEmporiumMin`), and `dimensionsCheck` accepts `tokenNumber == 0`, an attacker can submit a valid, ZK-proof-checked Emporium transaction whose token array is empty, so every conservation check (`balancesBefore`/`balancesAfter`, `balanceDif`, the circuit's `inTotal + amountChanges === outTotal`) is skipped entirely for the tokens actually touched by the arbitrary, attacker-crafted `EmporiumOperation[]` calls.

### Finding Description
The claimed-broken equality is: `Emporium ERC20 balance before ops == Emporium ERC20 balance after ops - accounted outflow (amountChanges/UTXO)`. This equality is enforced *only* over `circomData.erc20TokenAddresses`: [1](#0-0) [2](#0-1) 

When `circomData.erc20TokenAddresses` is the empty array, both `balancesBefore`/`balancesAfter` and the reconciliation loop are no-ops (zero iterations), and no `UTXO` is produced, no `BalanceChangeShouldBePositive` revert can ever fire. `Hinkal.transact`'s own top-level `oldBalances`/`newBalances`/`balanceDif` checks are driven by the exact same (attacker-supplied) `circomData.erc20TokenAddresses`, so they are equally empty: [3](#0-2) [4](#0-3) 

Crucially, an empty `erc20TokenAddresses` is a *sanctioned* code path for Emporium actions, not an oversight caught elsewhere: `CircomDataBuilder.formInputForCircom` explicitly branches to a minimal, non-token-aware public input set when `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [5](#0-4) 

and `dimensionsCheck`/`checkOnchainCreation` in `HinkalHelper.sol` place no lower bound on `dimensions.tokenNumber`, so `tokenNumber == 0` is a valid, separately-registered verifier (`buildVerifierId` hashes `tokenNumber` into the verifier lookup key) that skips the entire `MainEVMCircuit` per-token accounting (nullifiers, commitments, `inTotal + amountChanges === outTotal`) because that circuit is never invoked for this mode.

Inside `runAction`, once past `verifyWallet` (which only authenticates the EIP-712 signer of the stack, not the tokens touched), each `EmporiumOperation` is executed with fully attacker-controlled `endpoint`/`callData`/`value` in the "stateless" branch, with `Emporium` itself as `msg.sender`: [6](#0-5) 

The only restriction on the *stateless* call is that its selector isn't `callHinkalWallet`/`doSendToRelay`; there is no allowlist of `op.endpoint` targets and no requirement that `op.endpoint` be present in `circomData.erc20TokenAddresses`.

Exploit flow: the attacker builds a `CircomData` with `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, `dimensions.tokenNumber = 0`, and an `EmporiumStack` with two ops — op[0] targets a self-deployed "fake success" token (a no-op `transfer`/`transferFrom` that always returns `true`, purely cosmetic/decoy) and op[1] targets a real, legitimately funded ERC20 that currently has a non-zero balance sitting in the `Emporium` contract (e.g., dust/residue from a prior swap, or any token accidentally/temporarily held by Emporium), calling `RealToken.transfer(attacker, amount)` directly — this succeeds because `msg.sender` for that call is `Emporium`, which legitimately owns that balance; no allowance is even required. Because `erc20TokenAddresses == []`, neither `EmporiumUpgradeable.runAction`'s balance loop nor `Hinkal.transact`'s balance loop ever inspects `RealToken`, so the transfer is silently unaccounted: no `BalanceChangeShouldBePositive` revert, no UTXO minted/burned, no slippage or `balanceDif` check triggered, and no circuit constraint touches it (the circuit for `tokenNumber=0` never runs `MainEVMCircuit`'s token loop at all).

Existing guards fail specifically because: `verifyWallet` only checks the EIP-712 signature over the ops hash (authenticity of *who* requested the ops), not *what tokens* the ops move; `onlyAllowedRecipient` only restricts which contract can call `runAction` (i.e., `Hinkal`), not what `op.endpoint` may be called inside; `performHinkalChecks`/`dimensionsCheck` validate array-length consistency but impose no minimum on `tokenNumber`; and the whole point of `formInputEmporiumMin` is to *skip* the token-accounting circuit for this exact configuration.

### Impact Explanation
Any real ERC20 balance currently held by the `Emporium` contract can be transferred to the attacker's address with zero on-chain accounting, no UTXO creation, and no revert — a direct, silent theft of protocol/relay/user-adjacent assets held in `Emporium`, matching the Critical bar ("theft of shielded or in-flight user funds" / assets Emporium holds). It is repeatable every time `Emporium` accrues any non-zero ERC20 balance (dust, rounding remainders from prior swaps, mis-sent tokens, or fee residue), at zero marginal cost beyond one `transact()` call and the attacker's own signature.

### Likelihood Explanation
Preconditions: (1) `Emporium` must hold a non-zero balance of some ERC20 at the time of the attack — plausible via rounding/dust from prior legitimate swaps, protocol fee flows, or any token sent to `Emporium` outside the exact accounted flow; (2) attacker needs no privileged role — they self-sign the `EmporiumStack` as `stack.signerAddress` (or use `signerAddress = address(0)` to skip signature verification entirely) and self-construct `CircomData`/`Dimensions` with `tokenNumber = 0`, which is a supported, unauthenticated configuration. Cost is a single transaction; the finding is fully reproducible without needing any other user's key, and is repeatable indefinitely as long as exploitable balance accrues in `Emporium`.

### Recommendation
Do not allow `tokenNumber == 0` / empty `erc20TokenAddresses` to bypass balance accounting for actions that execute arbitrary `EmporiumOperation.endpoint.call`s. Either (a) always compute `balancesBefore`/`balancesAfter` over the full set of ERC20 addresses actually referenced by `stack.ops` (parsed/whitelisted at signing time and bound into the EIP-712 hash and `calldataHash`), independent of `circomData.erc20TokenAddresses`; or (b) require `Emporium` to enforce a strict "zero balance at rest" invariant (revert if any token balance is non-zero before/after any action) so no idle balance is ever available to `formInputEmporiumMin`-mode calls; or (c) restrict the "Min" input mode to only `invokeWallet=true`/signature-gated operations and disallow direct `op.endpoint.call` in stateless mode when `erc20TokenAddresses.length == 0`.

### Proof of Concept
Foundry test outline:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (with `HINKAL_EMPORIUM_ACTION_ID` registered), a `FakeSuccessToken` (transfer/transferFrom always return true, no state change), and a real `MockERC20` ("RealToken").
2. Fund `Emporium` directly with `RealToken.mint(address(emporium), 1000e18)` to simulate dust/residual balance.
3. Build `EmporiumStack` with `signerAddress = address(0)` (skips ECDSA check) and two ops: op[0] `endpoint = fakeToken`, `callData = transfer(attacker, 1e18)`; op[1] `endpoint = realToken`, `callData = transfer(attacker, 1000e18)`.
4. Build `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `dimensions.tokenNumber = 0`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata = abi.encode(stack)`, correct `calldataHash`.
5. Generate/register the corresponding minimal verifier for `verifierId = buildVerifierId(dimensions, actionId)` (or mock `IVerifier` to return true for the test, isolating the accounting bug from proof generation).
6. Call `hinkal.transact(a,b,c,dimensions,circomData)`.
7. Assert: `RealToken.balanceOf(attacker) == 1000e18` and `RealToken.balanceOf(address(emporium)) == 0`, while asserting `emit` logs show zero UTXOs created and no `BalanceChangeShouldBePositive`/slippage/`balanceDif` revert occurred — i.e., real value left the protocol with no matching entry on either side of the conservation equality.

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }
    }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
