### Title
Tron IntentGatewayV2.setParams accepts unvalidated host/dispatcher, permanently bricking message delivery and escrow release - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does not carry the same parameter-sanity checks as the canonical EVM implementation. Its `setParams` sets `_params` directly with no validation of `host` or `dispatcher`, unlike the EVM `IntentsBase._validateParams`, which explicitly rejects a zero or non-contract `host`/`dispatcher`.

### Finding Description
On the EVM production path, `IntentsBase._validateParams` (called from both `initialize`/`_updateParams`) enforces: [1](#0-0) 
This guarantees `host` and `dispatcher` are always non-zero contracts before being written to storage, because `host()` is what `HyperApp`'s `onlyHost` gate and every dispatch call rely on, and `dispatcher` is used to pull fees/execute predispatch calls.

The Tron fork of the same contract implements the equivalent write path with none of these guards: [2](#0-1) 
`setParams` is the only place `_params` (which holds `host` and `dispatcher`) is written on Tron, and it performs no zero-address or contract-code check before assigning `p` wholesale. `host()` simply reads back `_params.host`: [3](#0-2) 

If `host` is ever set to `address(0)` (or to an address that is not a real `IHost`), `host()` returns that value, `onlyHost`/`onAccept` checks against it break, `IDispatcher(host()).dispatch(...)` calls used to send cross-chain fill/refund/redeem messages revert, and the contract can no longer send or receive ISMP messages. If `dispatcher` is bricked, escrow-release/predispatch calls through `ICallDispatcher` fail as well. Because there is no subsequent path to correct `_params` other than another `setParams` call gated by `_admin` (which is zeroed the moment it's used per the pattern seen in the constructor/admin flow), a wrong assignment here is effectively permanent for that deployment, exactly mirroring the `StreamFactory` root cause: a critical implementation/target address accepted without a non-zero/contract check, disabling all future operations that depend on it.

### Impact Explanation
A misconfigured `host` or `dispatcher` on the Tron gateway permanently freezes:
- All order placement, filling, and escrow redemption/refund flows that depend on dispatching or receiving ISMP messages through `host()`.
- Any funds already escrowed in `_orders`/`_filled` for in-flight cross-chain orders, which can no longer be released or refunded because the gateway can't process incoming `RedeemEscrow`/`RefundEscrow` requests or dispatch outgoing ones.

This matches the Medium-severity bug class of the reference finding: a factory/config contract that can be pointed at an invalid target with no sanity check, permanently disabling its core function and wasting/freezing associated value.

### Likelihood Explanation
This requires the party controlling `setParams` (the deployment `_admin`, or governance via a cross-chain `UpdateParams` request reaching the equivalent update path) to submit a params struct with a zero or malformed `host`/`dispatcher`. Unlike the EVM implementation, there is no on-chain safeguard preventing this mistake, so any single incorrect parameter submission (accidental, not necessarily malicious) is sufficient — this is analogous to the original report's "wrongly assigned" scenario rather than requiring an adversarial actor.

### Recommendation
Add the same validation used in `evm/src/apps/intentsv2/IntentsBase.sol::_validateParams` to the Tron `IntentGatewayV2.setParams` (and any governance-driven params-update path in the Tron contract): reject `host == address(0)`, `host.code.length == 0`, `dispatcher == address(0)`, and `dispatcher.code.length == 0` before writing `_params`.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` with `admin = deployer`.
2. `deployer` (still authorized since `_admin` has not yet been reset) calls `setParams(Params({host: address(0), dispatcher: address(0), ...}))`. [4](#0-3) 
3. `_params.host` is now `address(0)`; `host()` returns `address(0)`.
4. Any subsequent call requiring `onlyHost` (via `HyperApp`) or `IDispatcher(host()).dispatch(...)` reverts, since `address(0)` has no code and does not implement `IHost`/`IDispatcher`.
5. There is no recovery path: `_admin` was consumed by this same call, so no further `setParams` call can correct the misconfiguration, permanently disabling the gateway's message dispatch/delivery and freezing any escrowed order funds.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
