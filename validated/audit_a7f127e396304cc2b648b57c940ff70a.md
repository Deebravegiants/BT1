### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` validates webhook authenticity by computing an HMAC over the raw request body only, while the `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` values used by the app are taken from unauthenticated HTTP headers. This breaks the binding between "bytes verified" and "bytes acted on": the signature proves the body came from Shopify using the app's shared secret, but it proves nothing about which shop the header claims the event belongs to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#hmac` decodes the `X-Shopify-Hmac-Sha256` header, and `HmacValidator.validate` compares `HMAC(api_secret_key, to_signable_string)` against it: [2](#0-1) 

However, `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers, none of which are included in `to_signable_string`: [3](#0-2) 

Because `api_secret_key` (the app's `client_secret`) is the same secret used for **every merchant** that has installed the app, any `(raw_body, hmac)` pair that is valid for one shop's webhook delivery is also a cryptographically valid pair in isolation from any specific shop. The identity binding that should hold is:

`shop_header_used_by_app == shop_that_the_HMAC-verified_bytes_originated_from`

but the gem only verifies `hmac == HMAC(secret, raw_body)`, never binding that check to the `shop-domain` header. This is the same class of defect as the report's "shared configuration parameter used across different asset types without a binding check": here, one shared secret authenticates the byte payload for all tenants, but the header that tells the app *which tenant* the payload is about is left outside the authenticated envelope.

### Impact Explanation
An attacker who controls (or can trigger events on) their own shop installation of the app receives legitimately-signed webhook deliveries (valid `raw_body` + valid `X-Shopify-Hmac-Sha256`). If that attacker can replay the same request to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `topic`/`webhook-id`) header to name a different, victim shop, `Utils::HmacValidator.validate` still returns `true`, since it only checks the raw body. Any handler in `Webhooks::Registry` that uses `request.shop` to select the tenant/session for downstream disaster (e.g., de-duplicate, look up offline session, update stored data) is fed spoofed tenant identity for a genuinely-signed payload — a cross-tenant confusion condition satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
The attacker only needs the ability to install the app on a shop they control (a normal, unprivileged action for a public app) and the ability to replay an HTTP request with modified headers to the app's own publicly reachable webhook endpoint — no access to `api_secret_key`, access tokens, or TLS interception is required. This is directly reachable through the gem's documented webhook-verification API (`Request` / `HmacValidator.validate`), not a host-application misuse.

### Recommendation
Bind the tenant-identifying headers into the signed payload verification, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the authenticated body, e.g.:
```ruby
def to_signable_string
  [shop, topic, webhook_id, @raw_body].join("\n")
end
```
and require Shopify webhook signers to include these fields in the digest (or, at minimum, document that `shop`, `topic`, and `webhook_id` are unauthenticated metadata and must never be trusted for tenant routing without an independent authenticated source, such as a stored subscription record keyed by `webhook_id`).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`).
2. Shopify delivers a POST to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`; headers also include `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures this request and resends it to the same endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and optionally `X-Shopify-Webhook-Id`), leaving `B` and the HMAC header untouched.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate(request)` calls `to_signable_string`, which returns `B` unchanged, so `OpenSSL.secure_compare` succeeds.
5. The app's webhook handler now processes body `B` under the identity `victim.myshopify.com` (from `request.shop`) even though `B` was never generated for that shop, demonstrating tenant-identity confusion accepted by the gem's own verification routine.
