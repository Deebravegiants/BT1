### Title
Webhook `shop` identity is taken from an unauthenticated HTTP header that is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity using an HMAC computed only over the raw request body [1](#0-0) , while the `shop` identity that the registry hands to the app's `WebhookHandler` is read directly from the `X-Shopify-Shop-Domain` HTTP header, which plays no part in the HMAC computation [2](#0-1) . This is the same bug class as the Sherlock report: a field that is acted upon (`shop`, analogous to `vouchers`) is not covered/bounded by the same check that protects the sibling field that is verified (`raw_body`/HMAC, analogous to `vouchees`/`maxVouchers`).

### Finding Description
`Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (`@raw_body`) and compares it against `request.hmac` (derived from the `X-Shopify-Hmac-Sha256` header) [3](#0-2) . After this check passes, the code builds `WebhookMetadata` using `request.shop`, which is simply `shopify_header("shop-domain")` [2](#0-1)  and hands it to the app-provided `handler.handle` [4](#0-3) .

The identity binding that should hold is: `shop header == shop cryptographically bound to this exact HMAC/body pair`. In reality the HMAC binds only `body`, and `shop` is unauthenticated header data. Because any merchant can install the app on their own shop and legitimately trigger a webhook, they can capture a valid `(body, hmac)` pair signed with the app's real `client_secret`. That pair remains valid for the exact same body content regardless of which `Shop-Domain` header value accompanies it, since the header is never part of the signable string. A user controlling the HTTP request (e.g., replaying the captured POST to the app's public webhook endpoint with the `Shop-Domain` header changed to a victim shop) causes `Utils::HmacValidator.validate` to still return `true`, and `WebhookMetadata.shop` will report the victim shop's domain even though the body is data the attacker fully controls (their own shop's data).

### Impact Explanation
Any webhook handler that trusts `WebhookMetadata#shop` to select which tenant's session/access token/database row to act on (a normal and expected usage pattern per this gem's own `docs/usage/webhooks.md` design, out of scope here but establishing intended use) will process attacker-supplied body content under the identity of a victim shop. This is a cross-tenant data confusion primitive: an attacker who owns one shop can inject fabricated webhook payloads (e.g., fake `orders/create`, `app/uninstalled`, `customers/data_request`) that the host application believes originated from a different, victim shop. Depending on how the host processes such data (e.g., syncing to victim's local storage keyed by the spoofed `shop`, or triggering the `app/uninstalled` cleanup flow for a victim's account), this can lead to cross-tenant data corruption or account/session disruption for shops the attacker doesn't control.

### Likelihood Explanation
The attacker needs a valid `(body, hmac)` pair, which they can obtain simply by installing the app on their own shop (or an existing merchant account) and generating any webhook event — no leaked secret, TLS interception, or privileged access is required. They then only need to be able to send an HTTP POST to the app's public webhook endpoint with a modified `Shop-Domain` header, something any unprivileged internet user with network access to that endpoint can do. This keeps the analog within the "unprivileged internet user breaks an identity binding" scope: shop authenticated (via header) vs. shop actually bound by the HMAC (none).

### Recommendation
Include the shop domain (and ideally topic, webhook id) in the HMAC-signed content check, or otherwise cryptographically bind `shop` to the verified body — e.g., require the host application to reconcile `request.shop` against a shop value embedded in `parsed_body` where available, or maintain a per-shop webhook secret/registration correlation so that a valid HMAC for shop A's body cannot be presented with shop B's domain header and still validate. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted as a tenant boundary without additional verification (e.g., cross-checking against an existing session record for that shop before acting).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook subscribed by the app (e.g. `orders/create`), capturing the full raw POST including `X-Shopify-Hmac-Sha256: <valid hmac>` and body `B`.
2. Attacker replays this exact POST to the app's public webhook endpoint, but replaces the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
3. `Request.new` accepts the request because required headers are present [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` (`B`, unchanged) using the app's real `client_secret` and matches the attacker-supplied HMAC — validation succeeds [6](#0-5) , [7](#0-6) .
5. `WebhookMetadata` is constructed with `shop: "victim-shop.myshopify.com"` and `body:` attacker-controlled content, then passed to the host app's handler as if it were a legitimate webhook for the victim shop [8](#0-7) .

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```

```ruby
        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```
