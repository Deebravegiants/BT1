### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs (and later verifies) only the raw HTTP body via HMAC, while the `shop` field that the registry hands to application webhook handlers as the tenant identity is read directly from an unauthenticated HTTP header. This breaks the intended binding `HMAC-verified bytes == bytes acted upon` and lets an attacker who can obtain any one validly-signed `(body, hmac)` pair from the app's own secret (e.g. by installing the app on their own store and capturing a real webhook delivery) replay that exact body/HMAC to the app's webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic tie to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` performs the HMAC check and then, without any further binding, forwards the unauthenticated `request.shop` value straight to the merchant-facing webhook handler as the tenant identity: [4](#0-3) 

The equality the gem's design implicitly claims is: `hmac_verify(secret, signed_bytes) == true` implies `shop == the shop the event is attributed to`. In reality the signed bytes are `raw_body` only, so `shop` (as well as `topic`, `api_version`, `webhook_id`) can be freely modified by anyone able to submit a POST to the app's webhook endpoint, as long as they can present *any* `(raw_body, hmac)` pair that is valid under the app's shared `api_secret_key`. Because the same `api_secret_key` is used to validate webhooks from *every* shop that installs the app, an unprivileged attacker can:
1. Install the app on their own (attacker-controlled) development/trial store.
2. Receive a genuine webhook (e.g. `customers/data_request`, `app/uninstalled`, or any subscribed topic) with a body and a correctly computed `x-shopify-hmac-sha256` value signed with the real `api_secret_key`.
3. Replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint, but with `x-shopify-shop-domain` rewritten to a victim's shop domain.
4. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"`.

### Impact Explanation
This is a cross-tenant identity spoofing vector: the host application's webhook handler is designed to trust `WebhookMetadata#shop` (sourced from `Request#shop`) as the authenticated tenant for the event, since the surrounding HMAC check is supposed to guarantee authenticity. An attacker can forge webhook events "from" any target shop for any topic the app is subscribed to (mandatory topics like `customers/redact`, `customers/data_request`, `shop/redact`, or any app-specific topic such as `app/uninstalled`), causing the application to perform tenant-specific side effects (e.g., wiping/exporting data, disabling the integration, revoking access) against a shop the attacker does not control. This falls under cross-tenant access.

### Likelihood Explanation
Any internet user can register a free/trial Shopify store, install a target app to receive one genuine webhook delivery, and then replay the intercepted body+HMAC with a different `shop` header value to the app's public webhook receiver endpoint. No access to `api_secret_key`, access tokens, or TLS interception is required — only a legitimately-signed sample the attacker obtains for their own tenant.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, and ideally `webhook_id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the verified body (e.g., verify HMAC over a canonical string that concatenates body + shop + topic, matching what Shopify actually authenticates for). At minimum, `Registry.process` should not pass an unauthenticated `shop` value to handlers without documenting clearly that it is unverified, and the gem should provide/require verification that ties the shop claim to the signed payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a subscribed webhook topic (e.g. `customers/data_request`) to receive a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid under the app's `api_secret_key`).
2. Attacker sends `POST <app_webhook_endpoint>` with the exact same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `request.to_signable_string` (== `B`). [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and executes tenant-scoped logic (e.g. data deletion for `customers/data_request`) against the victim's shop, even though the victim shop never sent this webhook.
