### Title
Missing re-entrancy re-check in the ISMP `Response` handler allows a timed-out `Get` request to still be delivered - ([File: modules/ismp/core/src/handlers/response.rs])

### Summary
CVE-2017-15951 is a Linux KEYS-subsystem TOCTOU bug: the kernel checked a key's "negative" (unusable) state and later updated/used it without holding the same lock, so a racing update could slip in between the check and the use. Hyperbridge's `pallet-ismp` message handlers implement the equivalent invariant — "a commitment/receipt must still be valid at the moment a module callback is invoked" — and the authors explicitly patched this class of bug in the `Request` and `Timeout` handlers by re-checking receipts/commitments immediately before dispatch, precisely because a module's `on_accept`/`on_timeout` callback can re-enter `pallet_ismp::Pallet::<T>::execute` mid-batch. The `Response` handler, however, was not given the same re-check for the request-commitment/timeout invariant.

### Finding Description
`request::handle` re-checks the receipt right before dispatch specifically to guard against a callback re-entering the handler mid-batch: [1](#0-0) 

`timeout::handle` (Get path) applies the same pattern, re-checking `request_commitment` immediately before deleting it and invoking `on_timeout`, with an explicit comment describing the exact reentrancy threat: [2](#0-1) 

`response::handle`, by contrast, performs its `request_commitment` existence check and its "already timed out"/response-receipt checks only in the up-front loop: [3](#0-2) 

but in the actual per-item dispatch loop it only re-checks `response_receipt` for duplication — it never re-verifies that `request_commitment` still exists before calling `store_response_receipt` and `cb.on_response`: [4](#0-3) 

Because `Pallet::<T>::execute` synchronously iterates every `Message` in the submitted batch and dispatches to whatever module the router resolves via `module_for_id`, a module callback invoked mid-batch can call back into `pallet_ismp::Pallet::<T>::execute` (a `pub fn`) before the outer batch iteration completes: [5](#0-4) [6](#0-5) 

If a relayer submits a single `handle_unsigned` batch containing (a) a `ResponseMessage` covering multiple `Get` requests and (b) a callback path that, upon processing an earlier response in that batch, re-enters `execute` with a `TimeoutMessage::Get` for a *different, later* Get request in the same batch, the timeout path will delete that request's commitment and invoke `on_timeout` for it. When the outer `response::handle` loop subsequently reaches that same Get request, it will not detect that the commitment is gone (it only re-checks `response_receipt`, not `request_commitment`), and will proceed to store a response receipt and invoke `on_response` for a request that has already been finalized via timeout — delivering both `on_timeout` and `on_response` for the same logical request.

### Impact Explanation
Double delivery of `on_timeout` followed by `on_response` (or the reverse ordering, depending on batch composition) for the same request breaks the "exactly-once" delivery guarantee that downstream `IsmpModule` implementations (token bridges, intents, bandwidth accounting) rely on. Depending on how a receiving module accounts for timeout vs. success (e.g., refunding on timeout then also crediting on response, or vice versa), this can lead to double-crediting/minting, inconsistent escrow release, or state corruption in modules that assume a request is processed at most once — i.e., unbacked mint / unsound state transition impact classes explicitly in scope.

### Likelihood Explanation
Exploitation requires a submitted batch to trigger genuine re-entrancy into `Pallet::<T>::execute` from within a module's `on_response`/`on_accept` callback during processing of an earlier message in the same batch — a scenario the codebase's own comments in `request.rs` and `timeout.rs` treat as a real, anticipated threat (hence the defensive re-checks added there). No currently-reviewed `IsmpModule` implementation in the shipped runtimes (`gargantua`/`nexus` `ProxyModule`) was observed calling back into `execute` synchronously, so this requires either an existing but unreviewed module path, or a future/pluggable module, capable of that recursive call. This lowers immediate likelihood but the root-cause gap in `response.rs` is concrete and asymmetric with the sibling handlers' hardening.

### Recommendation
Add the same "re-check right before dispatch" pattern used in `request.rs`/`timeout.rs` to `response::handle`: immediately before calling `store_response_receipt`/`cb.on_response`, re-verify `host.request_commitment(commitment)` is still `Ok` (i.e., the request has not been deleted/timed out by a re-entrant call earlier in the same batch), and fail with `Error::UnknownRequest`/`RequestTimeout` otherwise, mirroring the comment-documented rationale already present in the codebase.

### Proof of Concept
1. Attacker (any unprivileged relayer) crafts an unsigned `handle_unsigned` batch containing a `Message::Response(ResponseMessage)` covering two `Get` requests, `G1` and `G2`, both dispatched to a module whose `on_response` implementation is capable of synchronously calling `pallet_ismp::Pallet::<Runtime>::execute` (e.g. because the module forwards/relays ISMP messages internally).
2. During `response::handle`'s dispatch loop for `G1`, the module's `on_response` re-enters `execute` with a `TimeoutMessage::Get { requests: [G2] }`; since `G2`'s `request_commitment` still exists at that point, the nested timeout handler in `modules/ismp/core/src/handlers/timeout.rs` (lines 172-199) succeeds: it deletes `G2`'s commitment and invokes `on_timeout(G2)`.
3. Control returns to the outer `response::handle` loop, which proceeds to `G2`: it only checks `response_receipt` (not present) and does not re-check `request_commitment`, so it calls `store_response_receipt` and `cb.on_response(G2)`.
4. Result: both `on_timeout(G2)` and `on_response(G2)` execute for the same request within a single transaction, violating the intended exactly-once processing invariant.

pub fn handle_incoming_message<H>(
	host: &H,
	message: Message,
) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	match message {
		Message::Consensus(consensus_message) => consensus::update_client(host, consensus_message),
		Message::FraudProof(fraud_proof) => consensus::freeze_client(host, fraud_proof),
		Message::Request(req) => request::handle(host, req),
		Message::Response(resp) => response::handle(host, resp),
		Message::Timeout(timeout) => timeout::handle(host, timeout),
	}
}
