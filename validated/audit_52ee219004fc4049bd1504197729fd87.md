### Title
Webhook `shop-domain` and `topic` headers are not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `Registry.process` trusts these header-derived values to route the webhook to a handler and to attribute the event to a shop, without them ever being bound to the HMAC.

### Finding Description
`Utils::HmacValidator.validate` verifies a request by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it with `verifiable_query.hmac` [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are parsed directly from HTTP headers with no cryptographic binding to the signature [3](#0-2) .

`Registry.process` then uses these unauthenticated fields to select which handler runs and to construct the `WebhookMetadata` passed to it: `@registry[request.topic]&.handler` selects the handler by header-derived topic, and `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` attributes the payload to a header-derived shop [4](#0-3) .

The identity binding that should hold is: `shop verified by HMAC == shop the app acts on`. Here, the HMAC only proves "this body byte-string was produced with `api_secret_key`" — it proves nothing about which shop or topic the body belongs to, because the app's `api_secret_key`/`client_secret` is shared across every shop that installs the app, not per-shop. Any attacker who is (or has been) a legitimately installed merchant for the same app can capture one real, validly-signed `(raw_body, hmac)` pair from Shopify for their own store, then replay that exact `raw_body`/`hmac` to the app's webhook endpoint while substituting arbitrary `shopify-shop-domain` and `shopify-topic` header values. `HmacValidator.validate` still passes because it only checks the body, so `Registry.process` will dispatch to whatever handler the attacker names via the topic header and hand it `WebhookMetadata` claiming an arbitrary victim shop.

### Impact Explanation
This is a cross-tenant integrity break: a merchant who legitimately installed the app can forge webhook events "from" any other merchant's shop and for any registered topic (e.g. mandatory topics like `customers/redact`, `shop/redact`, or app-specific business-logic topics), since neither `shop` nor `topic` are authenticated. Depending on what the host app's handlers do with `WebhookMetadata#shop`/`#topic` (e.g., writing/deleting per-tenant data, triggering redaction, revoking access, updating billing state), this can lead to cross-tenant data corruption or spoofed lifecycle events attributed to a shop the attacker doesn't control — satisfying the "cross-tenant access" bar.

### Likelihood Explanation
Any app developer/tester who installs their own app has legitimate access to a real `(raw_body, hmac)` pair signed with the app's `api_secret_key` (this requires no leaked credentials — it's the normal webhook delivery any installed merchant receives). Replaying it with modified headers against the app's own public webhook endpoint requires no elevated privilege, matching the "unprivileged internet user" analog since the attacker only needs to be an ordinary app-installing merchant, not the app owner.

### Recommendation
Include `shop`, `topic`, and any other header fields the app relies on for routing/attribution in the HMAC-signed content (or otherwise cryptographically bind them, e.g., by having `to_signable_string` incorporate the verified headers, not just `@raw_body`), so `HmacValidator.validate` fails if any of these fields are altered relative to what Shopify originally signed.

### Proof of Concept
1. App legitimately installs on `attacker-shop.myshopify.com`. Shopify sends a real webhook: headers `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, plus `raw_body`.
2. Attacker captures this `(raw_body, hmac)` pair.
3. Attacker sends a new HTTP POST to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256` value, but headers changed to `x-shopify-topic: customers/redact` and `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` builds the request from these headers [5](#0-4) ; `HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC [6](#0-5) .
5. `Registry.process` looks up the `customers/redact` handler and invokes it with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"`, even though Shopify never sent this event for that shop.
