### Title
Withdrawal slippage check is skipped entirely unless *both* `min_coin_amount` and `min_pc_amount` are provided - (File: `program/src/processor.rs`)

### Summary
In `Processor::process_withdraw`, the slippage-protection check for LP withdrawals only executes when **both** `min_coin_amount` and `min_pc_amount` are `Some`. If a caller supplies only one of the two optional minimums (leaving the other `None`), the entire check is skipped, so neither the supplied minimum nor the vault balances are validated against slippage.

### Finding Description
The `WithdrawInstruction` struct defines `min_coin_amount` and `min_pc_amount` as independent `Option<u64>` slippage guards [1](#0-0) . In the withdraw processor, the guard is implemented as:

```rust
if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some() {
    if withdraw.min_coin_amount.unwrap() > coin_amount
        || withdraw.min_pc_amount.unwrap() > pc_amount
    {
        return Err(AmmError::ExceededSlippage.into());
    }
}
``` [2](#0-1) 

This uses `&&` (AND) to gate whether *any* slippage validation runs at all, rather than checking each minimum independently with its own `if let Some(...)`. As a result:
- If a caller sets `min_coin_amount = Some(x)` but leaves `min_pc_amount = None` (or vice versa), the `is_some() && is_some()` condition is `false`, and the entire slippage block is bypassed — even though the caller explicitly asked for protection on the coin (or pc) side.
- The withdrawal then proceeds unconditionally with whatever `coin_amount`/`pc_amount` were computed from `Calculator::calc_total_without_take_pnl_no_orderbook` and the pool's current LP-to-token exchange ratio [3](#0-2) , with no bound check at all.

This mirrors the reported bug class: a boolean condition that should independently gate/OR two checks instead uses AND, causing legitimate protective checks to be dropped whenever only one side of the condition is satisfied.

### Impact Explanation
An LP withdrawing liquidity via the `Withdraw` instruction who supplies only a single-sided minimum (a common pattern — e.g., only caring about the coin-side minimum) receives **no slippage protection whatsoever**. If the pool's price is manipulated (e.g., via a sandwich swap immediately before the withdrawal in the same slot/transaction bundle) the LP can receive significantly less value than expected on withdrawal, with the discrepancy captured by an attacker who moves the pool price and back. This is a direct value-loss vector for LP funds reachable by any unprivileged caller invoking `Withdraw`.

### Likelihood Explanation
Reachable in a single transaction: an attacker only needs to observe/target withdrawal transactions that set only one of the two `min_*_amount` fields (which the on-chain instruction encoding explicitly allows as independent `Option`s [1](#0-0) ), then execute a swap that moves the pool price before the withdrawal executes, extracting value with no on-chain check preventing it. No privileged signer or special build is required.

### Recommendation
Check each minimum independently instead of gating on both being present:
```rust
if let Some(min_coin_amount) = withdraw.min_coin_amount {
    if min_coin_amount > coin_amount {
        return Err(AmmError::ExceededSlippage.into());
    }
}
if let Some(min_pc_amount) = withdraw.min_pc_amount {
    if min_pc_amount > pc_amount {
        return Err(AmmError::ExceededSlippage.into());
    }
}
```
This ensures that supplying only one minimum still enforces that specific protection, matching the intended semantics of each field being an independent, optional guard.

### Proof of Concept
1. LP holds LP tokens and wants to withdraw, expecting at least `min_coin_amount = X` back in coin, but does not set `min_pc_amount` (passes `None`), matching the valid instruction encoding for `Withdraw` [1](#0-0) .
2. An attacker front-runs by swapping in the same block to shift the pool ratio unfavorably against the LP's coin side.
3. `process_withdraw` computes `coin_amount` below `X`, but because `min_pc_amount.is_some()` is `false`, the `&&` condition at [2](#0-1)  short-circuits and the entire slippage check block is skipped.
4. The withdrawal executes anyway via `Invokers::token_transfer_with_authority`, sending the LP fewer coin tokens than their intended minimum, with the attacker profiting from the price reversion afterward.
