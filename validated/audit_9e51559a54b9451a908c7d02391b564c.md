### Title
Division-by-zero panic in `SwapBaseOut`/`SwapBaseOutV2` swap math when `amount_out` equals the full pool reserve - ([File: program/src/math.rs])

### Summary
`Calculator::swap_token_amount_base_out` computes a swap's required input by dividing by `(reserve - amount_out)`. In `process_swap_base_out` and `process_swap_base_out_v2`, this division is executed **before** the code checks that `amount_out` is strictly less than the pool reserve. A user-controlled `amount_out` equal to the current pool reserve makes the denominator zero, triggering a division-by-zero panic instead of a controlled error return — the same root-cause bug class as the reported OpenJPEG CVE (division by zero in attacker/user-reachable code causing a crash/DoS).

### Finding Description
`Calculator::swap_token_amount_base_out` computes the constant-product input amount: [1](#0-0) 

For `SwapDirection::Coin2PC`, `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap()`. `checked_sub` only returns `None` (panicking) on underflow — when `amount_out == total_pc_without_take_pnl` the subtraction succeeds and yields `0`, which is then fed into `checked_ceil_div`, whose internal `checked_div` returns `None` for divide-by-zero and is immediately `.unwrap()`'d, causing a runtime panic.

In `process_swap_base_out`, the division happens here: [2](#0-1) 

and the guard that is supposed to prevent `amount_out` from reaching/exceeding the reserve is only checked afterward: [3](#0-2) 

The identical ordering issue exists in `process_swap_base_out_v2`: [4](#0-3) [5](#0-4) 

Because `Calculator::swap_token_amount_base_out` is invoked before the `swap.amount_out >= total_pc_without_take_pnl` (or `total_coin_without_take_pnl` for `PC2Coin`) sufficiency check, an attacker can pick `amount_out` exactly equal to the current pool balance (a value observable from any RPC node before submitting the transaction) and force the denominator to zero.

### Impact Explanation
Any unprivileged caller of the public `SwapBaseOut` (opcode 11) or `SwapBaseOutV2` instruction can submit `amount_out` equal to the pool's live PC or coin reserve (net of `need_take_pnl_*`). This causes an unhandled panic during execution instead of the intended `AmmError::InsufficientFunds` (or `ExceededSlippage`) error path. While a single panicking transaction is rolled back and does not directly move funds, it demonstrates that a basic bounds/sanity invariant (denominator > 0) that the code otherwise attempts to enforce is checked in the wrong order, allowing crafted, low-cost transactions to reliably abort mid-computation on attacker-chosen but easily-predictable state. This is directly analogous to the reported CVE class: a division performed on attacker-influenced values before the corresponding bounds check executes.

### Likelihood Explanation
High likelihood of triggering: pool reserves (`amm_pc_vault.amount`, `amm_coin_vault.amount`, and `need_take_pnl_*`) are all readable on-chain by anyone before constructing the swap instruction, so an attacker can deterministically compute the exact `amount_out` value that zeroes the denominator and submit it in a single transaction with no special privileges.

### Recommendation
Reorder the checks in `process_swap_base_out` and `process_swap_base_out_v2` so that `swap.amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl` is validated **before** calling `Calculator::swap_token_amount_base_out`, and/or make `swap_token_amount_base_out` return a `Result`/`Option` and explicitly reject a zero or non-positive denominator instead of relying on `.unwrap()`.

### Proof of Concept
1. Query the AMM's `amm_pc_vault`/`amm_coin_vault` balances and `need_take_pnl_pc`/`need_take_pnl_coin` to derive `total_pc_without_take_pnl` (per `Calculator::calc_total_without_take_pnl_no_orderbook`).
2. Submit a `SwapBaseOut` (or `SwapBaseOutV2`) instruction with `swap_direction = Coin2PC` and `amount_out` set exactly equal to `total_pc_without_take_pnl`.
3. Execution reaches `Calculator::swap_token_amount_base_out` at [2](#0-1)  before the `amount_out >= total_pc_without_take_pnl` guard at line 2214, computing `denominator = total_pc_without_take_pnl - amount_out = 0`.
4. `checked_ceil_div(0)` internally calls `checked_div(0)` which returns `None`, and the subsequent `.unwrap()` in [6](#0-5)  panics, aborting the transaction instead of returning `AmmError::InsufficientFunds`.

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)

                    .checked_mul(amount_out)
                    .unwrap()

                    .unwrap()
