## Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, and `webhook_id` from unauthenticated HTTP headers, while the HMAC that `Utils::HmacValidator` validates is computed **only** over the raw request body. [1](#0-0)  This breaks the intended binding `hmac == HMAC(secret, body + shop + topic)`; in reality it only enforces `hmac == HMAC(secret, body)`, leaving `shop` completely unauthenticated even though it is trusted downstream as the tenant identifier for the webhook handler.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for webhooks that method returns just `@raw_body`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic tie to the signed body:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

`Registry.process` validates only the body HMAC and then hands `request.shop` straight to the handler as the tenant identifier:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The identity binding that should hold is: **the `shop` value the handler trusts must equal the shop for which the signature was actually produced**. Because `shop-domain` is outside the signed payload, an attacker who legitimately controls their own shop can register a real webhook subscription, capture a genuine `body + hmac` pair (signed by Shopify with the app's real secret for the attacker's own shop), and replay that exact `body`/`hmac` to the app's public webhook endpoint while substituting a victim's domain in the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. `HmacValidator.validate` still passes because it only checks the (unmodified) body, and the handler now processes attacker-controlled body content under the victim's shop identity — a cross-tenant identity confusion analogous to the report's pattern of "a field acted on but not covered by the HMAC."

### Impact Explanation
This is a cross-tenant data-confusion vector: any host application that uses `request.shop`/`WebhookMetadata#shop` returned by this gem to select which merchant's records to update (the gem's own documented usage pattern) can be made to attribute attacker-supplied webhook payloads to an arbitrary victim shop, since the shop identity is never authenticated by the signature this gem validates.

### Likelihood Explanation
The attacker only needs to control one legitimate shop that has the app installed (unprivileged relative to any other tenant) — no access token, `api_secret_key`, or victim credentials are required. They obtain a valid `body`/`hmac` pair from their own genuine webhook delivery and freely rewrite the `shop-domain` header before submitting to the app's public webhook endpoint, since that header is outside the signed content.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable content, or otherwise cryptographically bind the header-derived `shop` value to the request before trusting it — e.g., verify `shop` against the session/store the webhook subscription was registered for, or require `to_signable_string` to incorporate the relevant headers so any header tampering invalidates the HMAC.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a genuine webhook (e.g., product update) with body `B`, obtaining the real `Shopify-Hmac-Sha256` header `H = HMAC(secret, B)` computed by Shopify.
2. Attacker sends a raw POST to the app's public webhook endpoint with:
   - Body: `B`
   - Header `Shopify-Hmac-Sha256: H`
   - Header `Shopify-Shop-Domain: victim-shop.myshopify.com` (replaced)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes because `B` and `H` are unmodified. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing attacker-controlled `B` to be processed as if it belonged to the victim's shop. [6](#0-5)
