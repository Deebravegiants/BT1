### Title
Governance withdrawals from EvmHost drain feeToken balance without reserving escrowed relayer fees for in-flight requests, risking undelivered fee payouts and timeout refunds - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.withdraw()` transfers an arbitrary, governance-supplied amount of the `feeToken` (or native token) out of the host's balance to a beneficiary, with no check against the fees the host has already promised to pay out for outstanding (undelivered/untimed-out) requests, tracked in `_requestCommitments`. This mirrors the Sherlock finding: rewards/fees are "accrued"/owed to a party but never reserved — the contract only realizes it can't pay when someone actually tries to redeem, at which point the party who withdrew earlier from the shared pool has already left insufficient balance for the remaining claimants.

### Finding Description
When a GET/POST request is dispatched with a relayer fee, the fee is transferred into the `EvmHost` contract and recorded per-commitment in `_requestCommitments[commitment].fee` (`FeeMetadata`). This balance is the pool used to:
- Pay the delivering relayer on successful delivery, e.g. `dispatchIncoming(GetResponse...)`: `IERC20(feeToken()).safeTransfer(relayer, fee);` [1](#0-0) 
- Refund the fee to the original sender on timeout, e.g. `dispatchTimeOut(GetRequestTimeout...)`: `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);` [2](#0-1) 

These obligations sit in the *same* `feeToken` balance that governance can withdraw as "host revenue" via:
```solidity
function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
    ...
    IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
    emit HostWithdrawal(...);
}
``` [3](#0-2) 

`withdraw` is reachable end-to-end from an unprivileged relayer delivering a governance-originated ISMP message: `HostManager.onAccept` decodes the `Withdraw` action and calls `IHostManager(_params.host).withdraw(withdrawParams)` once the message (dispatched from Hyperbridge, e.g. via `pallet-ismp-host-executive::withdraw`) is delivered and proven by any relayer. [4](#0-3) [5](#0-4) 

Crucially, there is no accounting in `EvmHost` that tracks "amount currently escrowed for outstanding requests" separately from "amount actually free to withdraw as protocol revenue." `withdraw()`'s only constraint is `SafeERC20.safeTransfer`'s underlying `ERC20.transfer` succeeding (i.e., sufficient total balance), confirmed by the test `test_host_manager_insufficient_balance`, which shows the *only* failure mode is a plain balance-insufficiency revert, not a reserved-funds check. [6](#0-5)  Likewise `test_host_manager_withdraw` demonstrates governance can withdraw any amount up to the full token balance with no notion of "committed" vs "free" funds. [7](#0-6) 

If governance withdraws feeToken revenue while relayer fees for still-pending (undelivered or not-yet-timed-out) requests are sitting in the same balance, subsequent legitimate `dispatchIncoming`/`dispatchTimeOut` calls will attempt `safeTransfer` calls that can revert (insufficient balance) or, worse, silently starve later claimants first — exactly the "players are not guaranteed to receive rewards" scenario: the fee accrual (`FeeMetadata.fee`) is a promise recorded in storage, but the underlying token backing that promise is not segregated/reserved from the pool governance can sweep.

### Impact Explanation
This is a fund-freezing / broken-payout bug reachable via ordinary relayer/governance message flow (no malicious governance assumption needed beyond the normal, in-scope `withdraw` governance action being delivered by any relayer). If the withdrawable amount is computed off-chain without subtracting outstanding escrowed relayer fees (there is no on-chain invariant preventing this), successful delivery of in-flight requests can leave relayers unable to collect fees they already earned, and timed-out requests can leave the original requester unable to recover their escrowed fee — i.e., permanent freezing/loss of funds owed to relayers or requesters. This satisfies the "permanent freezing of funds" / "route unable to deliver messages" (fee payment leg of delivery) bar for validity.

### Likelihood Explanation
Likelihood depends on governance/off-chain tooling correctly tracking "reserved" vs "free" feeToken balance when computing `WithdrawParams.amount`; the on-chain contract itself provides zero enforcement of this invariant, so any accounting drift, race between fee accrual and a withdrawal proposal being delivered, or intentional aggressive sweep of "revenue" will trigger the issue. Given the multi-step, cross-chain, asynchronous nature of Hyperbridge governance withdrawals (proposal encoded on Hyperbridge, later delivered by an arbitrary relayer at an unpredictable time), the balance available at delivery time can differ materially from the balance at proposal time, making this a realistic occurrence rather than a purely theoretical one.

### Recommendation
Track a running "reserved" total of outstanding `FeeMetadata.fee` amounts for undelivered/non-timed-out requests in `EvmHost` state, and enforce in `withdraw()` that `amount <= IERC20(token).balanceOf(address(this)) - reservedFees[token]` before transferring. Alternatively, escrow relayer fees in a dedicated contract/account (as is already done for Substrate's `RELAYER_FEE_ACCOUNT`) so that the "revenue withdrawable by governance" pool is provably disjoint from the "fees owed to relayers/requesters" pool.

### Proof of Concept
1. A user dispatches a `PostRequest`/`GetRequest` on `EvmHost` with a relayer fee `F` in `feeToken`; `F` is transferred into `EvmHost` and recorded in `_requestCommitments[commitment]`.
2. Before the request is delivered or times out, Hyperbridge governance issues a `Withdraw` action for `amount >= currentBalance - F` (e.g., withdrawing what it believes is all "accrued protocol revenue"), which is delivered by any relayer to `HostManager.onAccept`, calling `EvmHost.withdraw()` and draining the balance below `F`.
3. A relayer subsequently delivers the response/timeout; `dispatchIncoming`/`dispatchTimeOut` attempts `IERC20(feeToken()).safeTransfer(relayer/meta.sender, F)`, which reverts (insufficient balance) or, if multiple such requests exist, the first claimants drain what remains and the last claimants get nothing — reproducing the reported "not guaranteed to receive rewards" condition on Hyperbridge's EVM fee-accrual path.

				to: params.host_manager.0.to_vec(),
				timeout: 0,
				body: data,
			};

			// Account is not useful in this case
			dispatcher
				.dispatch_request(
					DispatchRequest::Post(post),
					FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
				)
				.map_err(|_| Error::<T>::DispatchFailed)?;

#[test]
fn test_host_manager_withdraw() {
	let mut env = TestEnv::new();
	let manager = host_manager_of(&mut env);

	// Mint 1000e18 fee tokens to the host
	let amount_to_mint = U256::from(1000u128) * U256::from(10u128.pow(18));
	env.call(env.fee_token, mintCall { to: env.host, amount: amount_to_mint }.abi_encode());
	assert_eq!(host_balance(&mut env), amount_to_mint);

	// Build a withdraw request (body = [0] + abi.encode(WithdrawParams)).
	// Withdraw the fee token (non-zero `token`) — the zero address would be
	// the native-ETH path which this test isn't exercising.
	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	// HostManager.onAccept is `restrict(_params.host)` — must call AS the host
	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);
	env.call_as(host_addr, manager, calldata);

	let withdraw_amount = U256::from(500u128) * U256::from(10u128.pow(18));
	assert_eq!(host_balance(&mut env), amount_to_mint - withdraw_amount);
}

#[test]
fn test_host_manager_insufficient_balance() {
	let mut env = TestEnv::new();
	let manager = host_manager_of(&mut env);

	// Host has no fee tokens; withdraw attempt should fail on SafeERC20 transfer
	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);
	let err = env
		.call_as_may_revert(host_addr, manager, calldata)
		.expect_err("expected revert");
	assert!(!err.is_empty(), "expected non-empty revert data");
}
