## Title
Vault gateway/DON handlers log the full incoming JSON-RPC request — including the caller's bearer JWT (`req.Auth`) — before authorization or redaction - ([File: core/services/gateway/handlers/vault/handler.go], [File: core/capabilities/vault/gw_handler.go])

## Summary
`HandleJSONRPCUserMessage` in the internet-facing gateway handler and `HandleGatewayMessage` in the DON-side gateway handler both log the entire `jsonrpc.Request[json.RawMessage]` object via structured logging (`"request", req` / `"req", req`) at Debug level, unconditionally, for every inbound vault request, prior to any authorization or field-level redaction. Since `jsonrpc.Request` carries an exported `Auth` field populated with the caller's JWT bearer token (confirmed by its use throughout `core/capabilities/vault/authorizer.go`, `jwt_based_auth_test.go`, and the system-test helpers that explicitly strip it via `outboundRequestWithoutAuth`/`req.Auth = ""` before making outbound calls), this results in the live JWT being written to logs verbatim whenever Debug-level logging is enabled.

## Finding Description
In `core/services/gateway/handlers/vault/handler.go:403`: [1](#0-0) 
this fires immediately on entry to `HandleJSONRPCUserMessage`, before `h.requestProcessor.ProcessRequest` performs any authorization, and before any redaction of the `Auth` field.

In `core/capabilities/vault/gw_handler.go`, the DON-side `HandleGatewayMessage` logs the same full request object at Debug level as its very first action: [2](#0-1) 
and unconditionally logs the full outgoing `response` object at Info level after every processed request: [3](#0-2) 

That `req.Auth` genuinely carries the caller's bearer JWT is confirmed by its use in the authorizer (`req.Auth != ""` gating JWT-based vs allowlist-based auth paths) and by test helpers explicitly stripping it before marshaling outbound requests to avoid re-serializing the secret: [4](#0-3) [5](#0-4) 

The codebase's own remediation of a related issue (`TestVaultHandler_InvalidParamsDoesNotLogRawParams`) only scrubs the later "invalid params" *error* log path and explicitly excludes the pre-existing whole-request Debug log from its assertions (it observes logs at Info level, deliberately filtering out the Debug-level "handling vault request" log), confirming this earlier log site was known and left unaddressed: [6](#0-5) 

No redaction, sanitization, or field-selection is applied at either log call site — both pass the raw struct directly to the structured logger, which will serialize all exported fields, including `Auth`.

## Impact Explanation
This is a credential/secret-disclosure issue: an operator or any process with read access to Debug-level gateway/DON logs (log aggregation, log files, support bundles) can recover live bearer JWTs used to authorize Vault secret operations (create/update/delete/list). Since the JWT's `authorization_details.request_digest` and owner/tenant claims are exactly what `Authorizer.AuthorizeRequest` uses to bind and permit a request, a captured token is directly replayable to construct new authorized requests for the same caller/workflow-owner until expiry — mapping to the "key/secret exfiltration" and "gateway request impersonation" impact classes.

## Likelihood Explanation
The log line at `handler.go:403` fires on every single inbound vault request, unconditionally, and the DON-side log at `gw_handler.go:182` and the Info-level response log at `gw_handler.go:231` fire on every gateway-forwarded message as well — no special or malformed input is needed. Triggering it requires nothing more than an unprivileged client sending a normal vault JSON-RPC request; the only precondition is that Debug-level logging be enabled on the gateway/DON, which is a common (if non-default) operational configuration for troubleshooting.

## Recommendation
Do not log the full `jsonrpc.Request`/`jsonrpc.Response` structs. At `core/services/gateway/handlers/vault/handler.go:403` and `core/capabilities/vault/gw_handler.go:182`, log only safe, non-sensitive fields (e.g., `method`, `requestID`, `hasAuth: req.Auth != ""`), following the same pattern already used elsewhere in the codebase (e.g., `authorizer.go`'s `"hasAuth", req.Auth != ""`). Similarly, avoid logging the full `response` object at `gw_handler.go:231`; log only status/method/requestID metadata.

## Proof of Concept
1. Run a Vault-enabled gateway/DON node with logger level set to `debug`.
2. As an unprivileged client, send a valid JSON-RPC vault request (e.g. `vault.secrets.list`) to the gateway HTTP endpoint with header `Authorization: Bearer <jwt>`.
3. Inspect gateway logs for the `"handling vault request"` entry (`handler.go:403`) and DON logs for `"received message from gateway"` (`gw_handler.go:182`) — the JWT supplied in `req.Auth` will appear in the serialized `request`/`req` field.
4. This can be encoded as a Go unit test analogous to `TestVaultHandler_InvalidParamsDoesNotLogRawParams` but observing at Debug level and asserting the JWT string does NOT appear anywhere in `logs.All()` after calling `HandleJSONRPCUserMessage`/`HandleGatewayMessage` with a request carrying `Auth: "test-jwt-marker"` — the test would fail against current code, demonstrating the leak.
