## Finding

### Title
Webhook Shop Domain Not Bound to HMAC Signature Enables Cross-Tenant Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC signature over the raw request body only, while the `shop` (tenant identity) is taken verbatim from an unauthenticated HTTP header. Because the header is never covered by the signature, an attacker who legitimately owns *any* shop that has installed the app can capture one of their own genuinely-signed webhooks and replay it against the app's webhook endpoint while forging the shop-domain header to point at a victim tenant, since the shared `api_secret_key` HMAC will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` with: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, so `shop` (sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is never included in the signed material. `HmacValidator.validate` verifies the HMAC purely against the body and the app's `api_secret_key`: [3](#0-2) 

`Registry.process` then trusts this unauthenticated `request.shop` value and forwards it directly to the app's handler as the tenant identity: [4](#0-3) 

Since the `api_secret_key` is shared across *all* shops that install the same app (it is not per-shop), any merchant/attacker who installs the app on their own store receives genuinely HMAC-valid webhooks for their own data. They can capture that body + `hmac-sha256` header and replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body/secret), so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain while the body content is attacker-controlled — an identity-binding break where the field acted on (`shop`) is not covered by the HMAC that authenticates the request.

### Impact Explanation
This breaks the equality that should hold: `shop authenticated by the signature == shop used to route/attribute the webhook payload`. If the consuming application uses `WebhookMetadata#shop` to select which tenant's session/data store the payload should be applied to (a standard and documented usage pattern shown in this gem's own webhook handling — `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, body: request.parsed_body, ...))`), an attacker can inject attacker-controlled webhook data attributed to an arbitrary victim shop, causing cross-tenant data confusion/injection. This matches the Critical-tier "cross-tenant access" impact category.

### Likelihood Explanation
Any unprivileged internet user can install a public app on their own store (no privileged credentials or leaked secrets required), which is sufficient to obtain one genuinely valid `(body, hmac)` pair since the `api_secret_key` HMAC is shared across all installs. Forging the shop-domain header on replay requires no cryptographic material and no access to `api_secret_key`, `access_token`, or any victim credentials — it is directly exploitable at the HTTP layer against the same shared endpoint.

### Recommendation
Do not treat `shopify-shop-domain` (or other unsigned headers such as topic/webhook-id) as trusted tenant identity on their own. At minimum, applications/documentation should be told to cross-check `request.shop` against a shop that is actually known to be installed with a stored session, and/or the gem should surface a warning that only the raw body is HMAC-covered so header values must not be used for tenant authorization without additional verification (e.g., confirming an active session exists for that shop before trusting the payload).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, permitted install for any Shopify merchant/dev store).
2. Attacker triggers a webhook event (e.g., creates an order), and captures the raw POST body plus the `X-Shopify-Hmac-Sha256` header sent to the app's webhook endpoint — this HMAC is valid because it is computed with the app's shared `api_secret_key` over the body only, per `to_signable_string` in `lib/shopify_api/webhooks/request.rb`.
3. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it never inspects the shop header.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`) invokes the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and attacker-supplied body content, causing the host application to process/store the forged data under the victim's tenant.
