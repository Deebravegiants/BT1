### Title
Crafted swap route can inject a wallet-draining transfer into the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs) [1](#0-0) 

### Summary
The lending controller forwards caller-controlled `swap` bytes to the configured router after authorizing only the expected input-token transfer. [1](#0-0)  Because route-selected pool and token contracts execute inside the caller’s authorization tree, a crafted route can make a malicious pool request an unrelated token transfer from the caller. [2](#0-1)  If simulation records that transfer and the caller signs the resulting tree, the attacker receives wallet funds unrelated to the routed input. [3](#0-2) 

### Finding Description
`swap_collateral` accepts a caller-supplied `swap: Bytes` argument and invokes `process_swap_collateral`. [4](#0-3)  The account check authorizes the caller, and the supplied bytes are passed unchanged into `withdraw_and_swap_from_supply`. [5](#0-4)  `swap_tokens` forwards the same opaque bytes to `router.execute_strategy`, while the controller’s own authorization covers only `token_in.transfer(controller, router, amount_in)`. [6](#0-5) 

The controller validates only its own input balance, output balance, and refund after the router returns. [7](#0-6)  It does not constrain which external pool or token addresses the route reaches, so malicious route code can issue a `token.transfer(caller, attacker, amount)` beneath the caller’s root authorization. [2](#0-1)  The same mechanism reaches routes through `swap_debt`, which borrows the new debt asset and passes the user’s `swap` bytes to the shared swap helper. [8](#0-7) 

### Impact Explanation
A malicious route can steal unrelated token balances held by the submitting account, not merely produce poor swap execution. [3](#0-2)  The tested sequence reduces Alice’s unrelated wallet token balance to zero and credits the attacker while the swap itself still deposits the expected collateral output. [9](#0-8)  Neither the route minimum, controller balance-delta check, nor final account-risk check bounds this separate wallet transfer. [2](#0-1) 

### Likelihood Explanation
Exploitation requires the victim to submit a crafted route and sign an authorization tree containing the malicious transfer, so it depends on route distribution and insufficient authorization-tree inspection. [10](#0-9)  The attack does not require privileged access, leaked keys, malformed account permissions, or a compromised configured router: the caller-controlled route selects the malicious contract. [1](#0-0)  A caller that signs a poisoned tree authorizes the transfer, making the loss deterministic once submitted. [11](#0-10) 

### Recommendation
Restrict executable routes to governance- or router-allowlisted venue contracts and token addresses rather than allowing arbitrary address registries to determine external calls. [12](#0-11)  Clients and wallets should reject any lending authorization tree containing children beyond the expected controller/account calls and the exact input transfer. [13](#0-12)  A stronger protocol-level fix is to make route venues transparent to the controller or have the router execute only from a fixed venue registry, so opaque bytes cannot introduce new contract addresses. [1](#0-0) 

### Proof of Concept
1. Deploy a malicious “pool” that calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` during its swap invocation. [14](#0-13) 
2. Encode that pool address in the route supplied to `swap_collateral`. [15](#0-14) 
3. Simulate Alice’s `swap_collateral` call; the host records the malicious wallet-token transfer as a child of Alice’s controller authorization. [16](#0-15) 
4. With the honest empty child list, enforcement rejects the rogue transfer and preserves Alice’s wallet balance. [17](#0-16) 
5. With the simulated poisoned tree signed, the call succeeds, Alice’s unrelated token balance becomes zero, and the attacker receives the full wallet balance. [11](#0-10)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
