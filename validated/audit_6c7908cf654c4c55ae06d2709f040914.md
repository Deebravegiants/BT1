## Finding

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values used to route and attribute the webhook are taken from unauthenticated HTTP headers that are never included in the signed data. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, breaking the binding between "bytes verified" and "shop acted upon."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop` (and `topic`/`api_version`/`webhook_id`) are read straight from headers that are not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the HMAC — i.e., only the body: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (from the unsigned header) to build the dispatched metadata and select/execute the handler: [4](#0-3) 

Because the app-wide `client_secret` (`Context.api_secret_key`) is shared across every shop that installs the app, any merchant who has legitimately installed the app can capture one of their own real webhook deliveries — a valid `(raw_body, X-Shopify-Hmac-SHA256)` pair. That merchant can then replay the identical body/HMAC to the app's webhook endpoint while swapping only the `X-Shopify-Shop-Domain` header to a victim shop's domain. `HmacValidator.validate` still returns `true` (the body is untouched and correctly signed), so `Registry.process` proceeds to call `handler.handle` with `shop:` set to the victim shop and `body:` set to the attacker's own webhook payload — a value the app's own signature check never authenticated for that shop.

### Impact Explanation
This breaks the tenant/identity binding "shop verified by HMAC == shop acted upon," letting an unprivileged (but app-installed) user impersonate another tenant to the app's own webhook-processing logic — a cross-tenant access issue. Depending on how the host app's handler uses `WebhookMetadata#shop`/`#body` (e.g., updating shop-scoped records, triggering mandatory GDPR flows like `customers/redact` or `shop/redact`), an attacker can inject attacker-controlled data or trigger data-affecting webhook actions attributed to a shop they do not own.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on a shop they control (a normal, low-privilege action) to obtain one legitimately-signed webhook body/HMAC pair, then issue a direct HTTP POST to the app's webhook endpoint with a modified shop header — no access to the app's `client_secret` or any victim credentials is needed.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` (or otherwise cryptographically bind the shop identity) in the signed payload used for HMAC validation, or require the caller to pass an out-of-band-verified shop identifier that is cross-checked against a trusted, pre-established relationship (e.g., an active session/installation for that shop) before dispatching to handlers, rather than trusting the unauthenticated header value directly.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and receives a real webhook delivery, e.g. an `orders/create` webhook, with raw body `B` and header `X-Shopify-Hmac-SHA256: H` (valid because `H = HMAC-SHA256(client_secret, B)`).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-SHA256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. The app constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` and calls `Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H` [5](#0-4) .
5. `Registry.process` dispatches to the registered handler with `shop: "victim.myshopify.com"` and the attacker's own body content, even though the shop value was never covered by the signature [6](#0-5) .

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
