## Title
Attacker-triggerable `unwrap()` panic in `calc_take_pnl` permanently freezes LP withdrawals and PNL distribution - (File: `program/src/processor.rs`)

### Summary
The reported CVE (`Node_ValidatePtr` in mkclean) is a classic "crafted/attacker-controlled input reaches an `assert`/`unwrap`-style invariant check, causing the process to abort (DoS)." The equivalent pattern exists in Raydium's `Processor::calc_take_pnl`, where two `checked_sub(...).unwrap()` calls assume an invariant (`x1 >= x2`, `y1 >= y2`) that is not actually enforced against the raw, attacker-influenceable vault balances that flow into this function on every `Deposit`, `Withdraw`, and `WithdrawPnl` instruction.

### Finding Description
`calc_take_pnl` computes `x1`/`y1` from the live vault token balances (`amm_pc_vault.amount`, `amm_coin_vault.amount`) via `calc_total_without_take_pnl_no_orderbook` and `normalize_decimal_v2`, both of which perform floor integer division: [1](#0-0) [2](#0-1) 

The pre-check that is meant to guarantee `x2 <= x1` compares raw/restored native amounts: [3](#0-2) 

but the actual `x2`/`y2` values used afterwards are computed in the *normalized* (`sys_decimal_value`) domain via `calc_x_power` and `integer_sqrt`: [4](#0-3) 

Because `normalize_decimal_v2`/`restore_decimal` round (floor) independently at different points (once when `target.calc_pnl_x/y` was stored during a prior deposit/withdraw, and again for the current `x1`/`y1`), the "native domain" guard does not perfectly correspond to the "normalized domain" quantities actually subtracted. Any unprivileged actor can shift the vault balances relative to the previously stored `target.calc_pnl_x`/`calc_pnl_y` by directly transferring SPL tokens into `amm_coin_vault`/`amm_pc_vault` (a normal, permissionless SPL Token `Transfer`, no program invocation required), nudging the balances by amounts smaller than the rounding granularity implied by `coin_decimals`/`pc_decimals` vs `sys_decimal_value`. This can push the true (post-floor) `x1`/`y1` just below the value implied by `target.calc_pnl_x`/`calc_pnl_y`, while the native-domain guard at line 190-192 still reports the state as valid, since that comparison is computed with different roundings. When this happens, `x2 = integer_sqrt(x2_power)` exceeds `x1` and: [5](#0-4) 
panics with an unwrap failure on `checked_sub`, aborting the transaction.

Since `calc_take_pnl` is invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`: [6](#0-5) [7](#0-6) [8](#0-7) 
once the vault state is nudged into the panicking condition, **every subsequent Deposit, Withdraw, and WithdrawPnl call on that pool will panic and revert**, because the vault balances and `target_orders.calc_pnl_x/y` persist on-chain and the attacker's donation is never reversed by the program.

### Impact Explanation
This is not a transient failure of a single caller's transaction — the underlying account state (`amm_coin_vault`/`amm_pc_vault` balances vs. `target_orders.calc_pnl_x/y`) is corrupted permanently on-chain. All future `Withdraw` calls by any LP, and all `WithdrawPnl` calls by the configured PNL owner, will hit the same panic path and fail, permanently freezing LP principal and accrued PNL in the pool (swap instructions do not call `calc_take_pnl` and may remain unaffected, but liquidity cannot be removed). This satisfies "permanent freezing of user or LP funds."

### Likelihood Explanation
The trigger requires only a standard SPL Token `Transfer` instruction sending a small, carefully chosen amount of coin or pc tokens directly to the pool's vault account — something any token holder can do without any special privilege, signature from the AMM authority, or malicious validator/build assumptions. The precise donation amount needed depends on the pool's specific decimals/`sys_decimal_value` and current `target_orders` state and would need to be computed/simulated per pool, which lowers likelihood somewhat relative to a trivial one-shot exploit, but it is fully computable off-chain by an attacker before submission.

### Recommendation
- Ensure the guard in `calc_take_pnl` (lines 188-192) is computed in the *same* domain (normalized, unrounded, or with explicit tolerance) as the values actually subtracted at lines 213-214, or use `checked_sub()` with graceful error handling (`ok_or(AmmError::CalcPnlError)`) instead of `unwrap()` so that an unfavorable rounding state returns a `ProgramError` rather than panicking.
- Replace all `unwrap()` calls in `calc_take_pnl` and its decimal-normalization helpers (`normalize_decimal_v2`, `restore_decimal`) with checked arithmetic that returns `AmmError` instead of panicking, so a bad/edge-case pool state degrades to a rejected instruction rather than a hard panic that can recur indefinitely.
- Consider tracking vault balances internally (or reconciling donations) rather than trusting live SPL token account balances directly for PNL/invariant math, to remove the donation-based manipulation vector entirely.

### Proof of Concept
1. Attacker identifies a Raydium pool and computes (via off-chain simulation using the public `normalize_decimal_v2`/`calc_x_power`/`integer_sqrt` logic) a small token amount `d` such that transferring `d` extra coin (or pc) tokens into `amm_coin_vault` (or `amm_pc_vault`) causes the floor-rounded `x1`/`y1` computed on the next `Deposit`/`Withdraw`/`WithdrawPnl` call to fall just short of `target_orders.calc_pnl_x`/`calc_pnl_y`'s implied value, while the native-domain check at `processor.rs:188-192` still passes.
2. Attacker sends a standard SPL `Transfer` instruction of `d` tokens directly to the pool's `amm_coin_vault` (or `amm_pc_vault`) — no interaction with the Raydium program required.
3. Any subsequent call to `Withdraw`, `Deposit`, or `WithdrawPnl` on that pool computes `x1`/`y1` from the now-perturbed vault balance, and `calc_take_pnl` panics at `x1.checked_sub(x2).unwrap()` (or the `y` equivalent), aborting the transaction.
4. Because the vault balance perturbation and `target_orders` state are persistent, all future LP withdrawal and PNL withdrawal attempts on the pool panic identically, permanently freezing LP and PNL funds.
