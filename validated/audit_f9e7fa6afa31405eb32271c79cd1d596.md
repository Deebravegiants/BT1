### Title
Same-chain `fillOrder` has no minimum partial-fill amount, allowing 1-wei dust fills that lock a user's order in a "filled" state — ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntrinsicIntents._fillSameChain` accepts any nonzero `solverAmount` per output leg as a valid partial fill, with no lower bound check analogous to the missing `fillThreshold` validation in the referenced report. Any filler can call `fillOrder` with `options.outputs[i].amount = 1` (1 wei) to register a `PartialFill` against the user's order, exactly mirroring the "trivial partial fill" bug class described in the external report.

### Finding Description
In `_fillSameChain`, for each output asset the code computes:
```
uint256 fillAmount = solverAmount > remaining ? remaining : solverAmount;
``` [1](#0-0) 
There is no check enforcing `fillAmount` (or `solverAmount`) to be above some meaningful fraction of `totalRequired`; only `solverAmount == 0` is special-cased to skip. A filler can therefore submit `solverAmount = 1` and have it accepted as a legitimate partial fill, updating `_partialFills[commitment][outputToken]`, transferring 1 wei to the beneficiary, and releasing a proportional (also near-zero) slice of escrowed input tokens back to the filler. [2](#0-1) 

This is architecturally the same root cause as the reported `fillThreshold` issue: the protocol's partial-fill feature (documented at `docs/content/developers/evm/intent-gateway/overview.mdx`) has no floor on how small an accepted fill can be. [3](#0-2) 

### Impact Explanation
A user placing a same-chain order can have it "touched" by a griefing filler with a dust amount (e.g., 1 wei of the output token), which:
- Emits `PartialFill` and updates on-chain partial-fill state for that order/token pair, giving off-chain monitoring tools/users a false signal that the order is progressing.
- Locks in the surplus-sharing rule change described in the code: once `alreadyFilled != 0` for a token pair, subsequent solvers filling the remainder can no longer receive any surplus (`_splitSurplus` only applies "when solver overpays on a fresh, unfilled order"), and (per `testPartialFill_SurplusOnlyWhenNotPartiallyFilled`) any surplus offered by later fillers gets capped/discarded rather than benefiting the protocol/beneficiary. This lets a griefer strip future surplus opportunities from an order with a trivial 1-wei front-run fill. [4](#0-3) 
- More generally, releases a proportional sliver of the user's escrowed input for essentially nothing in return, and can be repeated across many orders as a cheap griefing vector against the intent auction mechanism, undermining users' expectations about fill economics and surplus capture.

### Likelihood Explanation
High likelihood: `fillOrder` is a public, unauthenticated entry point (unless `solverSelection` is enabled) callable by any address holding a trivial amount of the output token, with no economic barrier beyond gas cost. The action costs the attacker as little as 1 wei of the output token plus gas.

### Recommendation
Add a minimum partial-fill validation in `_fillSameChain`, e.g. reject `fillAmount` below a configurable basis-points floor of `totalRequired` (mirroring the report's suggested fix of enforcing a nonzero/minimum `fillThreshold`), or require partial fills to clear at least 1% of the remaining amount unless they complete the order.

### Proof of Concept
1. User places a same-chain order via `placeOrder` requesting `1000e18` `tokenOut` for `1000e6` `tokenIn` escrowed.
2. A filler calls `fillOrder` with `options.outputs[0].amount = 1` (1 wei of `tokenOut`).
3. `_fillSameChain` accepts this as a valid partial fill: `remaining = 1000e18`, `solverAmount = 1`, so `fillAmount = 1`; `_partialFills[commitment][outputToken] = 1`; 1 wei is transferred to the beneficiary and a proportional (effectively 0, due to rounding) amount of escrowed `tokenIn` is released to the filler; `PartialFill` is emitted.
4. The order is now marked as partially filled, exactly as demonstrated by the analogous test pattern in `testSameChainFill_PartialAmount_IsValidPartialFill`, but with an amount reduced to the smallest possible unit instead of a meaningful fraction — no code path prevents this. [5](#0-4)

    function testPartialFill_SurplusOnlyWhenNotPartiallyFilled() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 outputAmount = 1000 * 1e18;
        Order memory order = _placeStandardOrder(inputAmount, outputAmount);

        // Solver fills 500 DAI (partial)
        vm.startPrank(solver);
        dai.approve(address(intentGateway), 500 * 1e18);
        TokenInfo[] memory outputs1 = new TokenInfo[](1);
        outputs1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 500 * 1e18});
        intentGateway.fillOrder(
            order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: outputs1})
        );
        vm.stopPrank();

        // Solver 2 fills remaining 500 with 600 offered — excess should be capped (no surplus on partially filled pair)
        address solver2 = makeCleanAddr("solver2");
        deal(address(dai), solver2, 100000 * 1e18);
        uint256 solver2DaiBefore = dai.balanceOf(solver2);
        uint256 userDaiBefore = dai.balanceOf(user);

        vm.startPrank(solver2);
        dai.approve(address(intentGateway), 600 * 1e18);
        TokenInfo[] memory outputs2 = new TokenInfo[](1);
        outputs2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 600 * 1e18});
        intentGateway.fillOrder(
            order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: outputs2})
        );
        vm.stopPrank();

        // Solver 2 should only spend 500 DAI (capped)
        assertEq(dai.balanceOf(solver2), solver2DaiBefore - 500 * 1e18, "Solver2 capped to remaining");
        // User should receive exactly 500 more DAI (no surplus)
        assertEq(dai.balanceOf(user), userDaiBefore + 500 * 1e18, "User gets exact remaining, no surplus");
        // No dust in gateway
        assertEq(dai.balanceOf(address(intentGateway)), 0, "No protocol surplus on partially filled pair");
    }
