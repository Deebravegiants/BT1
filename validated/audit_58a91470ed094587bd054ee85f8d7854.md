## Title
Webhook shop identity is trusted from an unauthenticated header while the HMAC signs only the raw body, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the `X-Shopify-Hmac-Sha256` signature against the raw request body. The `shop` value that is subsequently handed to the application's webhook handler is read directly from the `X-Shopify-Shop-Domain` header, which is never included in the signed payload. Any actor who can obtain one validly-signed webhook (trivially available to anyone who installs the app on their own store, since the HMAC secret is the app's single `client_secret` shared across every merchant install, not a per-tenant secret) can replay that request while substituting an arbitrary `shop-domain` header. The signature still validates, but the `shop` attribute delivered to the host application is now attacker-controlled and unauthenticated, breaking the equality "shop authenticated by the HMAC" == "shop the handler trusts as the tenant key."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from headers and is not part of the signed string at all: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and, on success, immediately forwards `request.shop` to the registered handler as the authoritative tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` (the raw body) using the app's shared `Context.api_secret_key`: [4](#0-3) 

Because the `client_secret`/`api_secret_key` is identical for every shop that installs the app (it is not shop-specific), any unprivileged user can install the app on their own store, capture a genuine webhook delivery (valid body + valid HMAC), and then re-send that exact body/HMAC pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header changed to a victim shop's domain. `HmacValidator.validate` only re-derives the signature from the body, so it still matches. `Registry.process` then constructs `WebhookMetadata` with `shop: request.shop`, i.e. the attacker-chosen value, and dispatches it to the host application's handler as if it were an authenticated event for the victim shop.

This breaks the identity binding the rules call out explicitly: a field (`shop`) that is acted upon by the handler but is not covered by the HMAC.

### Impact Explanation
Any host application handler that keys persistence, session lookup, or business logic off `WebhookMetadata#shop` (the documented/intended use of this field) can be made to process attacker-supplied data under a victim shop's tenant identity — e.g., writing spoofed order/customer/app-uninstalled events into another merchant's tenant records, or triggering shop-scoped side effects (data deletion via mandatory compliance topics, resource updates, etc.) attributed to a shop the attacker does not control. This is a cross-tenant integrity/confidentiality violation rooted entirely in this gem's webhook verification code, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires no privileged credentials, access tokens, or the app's `client_secret`: it only requires the ability to install the target app on an attacker-owned development/trial store (a normal, unprivileged action available to any internet user) to obtain one legitimately-signed webhook body/HMAC pair, and the ability to POST an HTTP request to the app's public webhook endpoint with a modified header. No cryptographic secret needs to be recovered because the signature check never depends on the header being forged.

### Recommendation
Bind the `shop` (and ideally `topic`/`api-version`) values into the material that is verified, not just trusted after the fact:
- Include the `shop-domain` header (and other identity-bearing headers) in `to_signable_string`, or
- After HMAC validation, cross-check `request.shop` against an independently-established value (e.g., the shop associated with the specific webhook subscription/session that the host app expects), rather than trusting the header verbatim.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant key by consuming applications, while updating `HmacValidator`/`Request` so `shop` participates in the signed payload by default.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (no special privilege needed).
2. Shopify delivers a legitimate webhook to the app's endpoint:
   - Body: `{"id": 1}`
   - Headers: `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`
3. Attacker captures this exact body + HMAC header pair (they legitimately received it) and replays it to the app's endpoint, only changing the domain header:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same-valid-hmac>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: {"id": 1}
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `{"id": 1}` only — it matches, since the header change didn't touch the signed content: [5](#0-4) 
5. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though this event never originated from that shop: [6](#0-5) 

The host application processes attacker-controlled data attributed to the victim's tenant.
