### Title
Webhook `shop` identity is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC that is verified against the raw request body only, while the `shop` (tenant) identity used by `Registry.process` to route the webhook to the app's handler comes from an unrelated, unsigned HTTP header. This breaks the binding: `hmac_verified(body) == true` does not imply `shop_header == shop_that_produced_this_body`.

### Finding Description
`Request#to_signable_string` returns only the raw body, and `Request#hmac` is derived from the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

`Request#shop` is read from the `shop-domain` header, which is completely disjoint from the signed material: [3](#0-2) 

`HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string` (the body); it never binds the `shop` header into the check: [4](#0-3) 

`Registry.process` uses this unauthenticated `request.shop` value directly as the tenant identity forwarded to the app's handler, with no cross-check against anything HMAC-covered: [5](#0-4) [6](#0-5) 

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` **is** part of the signed parameter set (`to_signable_string` includes `shop`), so the OAuth-callback shop cannot be swapped without invalidating the HMAC: [7](#0-6) 

This asymmetry is the same "identity binding not covered by HMAC" bug class flagged in the external report (a field acted on but not authenticated by the signature). Any party who can obtain one genuine, validly-signed webhook body+HMAC pair for the app (e.g. the operator of one shop that has the app installed, who can inspect their own store's outbound webhook deliveries) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value. `HmacValidator.validate` will still report the signature as valid (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field is the attacker-chosen value, not the shop that actually produced the payload.

### Impact Explanation
If the consuming application (as the gem's own `WebhookMetadata`/`WebhookHandler` interface encourages) uses `data.shop` to select which tenant's record to update/delete/create based on `data.body`, an attacker who legitimately controls one shop can forge webhook events attributed to a different, victim shop — a cross-tenant data-integrity/cross-tenant-access impact, achieved without knowledge of the app's `client_secret` (the attacker only needs a real signed sample produced for their own tenant, not the secret itself). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Moderate. The attacker must possess at least one genuine (body, HMAC) pair originally destined for the app (trivial if they run the app on their own store and can capture their own webhook deliveries), and must know the app's webhook endpoint URL (typically discoverable/static per app). No secret leakage or TLS interception is required to perform the replay itself — only substitution of an HTTP header on a POST the attacker sends directly to the app's endpoint.

### Recommendation
Bind the tenant identity into the verified material: either include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the HMAC-signed content the library validates, or require handlers to cross-check `request.shop` against another authenticated source (e.g. the shop stored against the currently active session/access token used to register that specific webhook) before trusting it for tenant routing. At minimum, document prominently that `Request#shop` is not authenticated by `HmacValidator.validate` and must not be used as a sole tenant-authorization signal by downstream `WebhookHandler` implementations.

### Proof of Concept
1. App installed on `shop-a.myshopify.com`; Shopify delivers a legitimate webhook to the app's endpoint with body `B` and headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`) and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (owner/operator of `shop-a`) captures this exact `(B, H)` pair from their own store's webhook logs/inspection tooling.
3. Attacker sends a new POST to the same app webhook endpoint with unchanged body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a victim tenant).
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `shop` returns `"shop-b.myshopify.com"` [3](#0-2) , while `hmac`/`to_signable_string` are unaffected by the header change [8](#0-7) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `H` against `HMAC(B)` [4](#0-3) , then invokes `handler.handle(data: WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...))` [9](#0-8) .
6. Any handler logic keyed on `data.shop` now processes `shop-a`'s payload as if it belongs to `shop-b`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
