### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only covers the request body, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw body, but the `shop` (and `topic`/`webhook_id`) that get handed to the app's handler are read straight from HTTP headers, which are not part of the signed material.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for a webhook `Request` that method returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are instead parsed directly out of caller-supplied headers with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` treats a request as authentic once `Utils::HmacValidator.validate(request)` passes, then immediately forwards the unauthenticated `request.shop` value into `WebhookMetadata` that is dispatched to the app's handler: [3](#0-2) 

This breaks the equality the app's handler code implicitly relies on: `shop-domain header == shop that produced/authorized this body`. Since the HMAC is `HMAC(secret, raw_body)` and does not include the shop domain, any two webhook deliveries whose bodies are byte-identical (which happens routinely for `shop/redact`, `customers/redact`, and other mandatory/compliance topics whose body content is often minimal or templated, and can also occur for ordinary topics when payloads coincide, e.g. duplicate/near-duplicate resource states) will produce the same valid HMAC regardless of which shop the request claims to be from via the header. A malicious or compromised merchant who has installed the app and thus legitimately receives real webhook deliveries (valid `raw_body` + valid `hmac-sha256` pairs for their own shop) can replay that exact body+hmac pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still pass (it only checks the body against the secret), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop, letting the attacker inject spoofed data attributed to another tenant.

### Impact Explanation
This crosses a tenant boundary: an app built on this gem's documented API (`docs/usage/webhooks.md`, which explicitly tells implementers to trust `data.shop` as "The shop domain of the webhook") will process attacker-controlled events labeled with an arbitrary victim shop domain, despite HMAC verification succeeding. Depending on what the host app does with `data.shop` (e.g., looking up per-shop sessions/records, triggering the mandatory `shop/redact`/`customers/redact` compliance flows for a shop the attacker doesn't own), this can enable cross-tenant data manipulation or spoofed compliance actions attributed to a shop the attacker does not control, without ever needing the app's `client_secret`.

### Likelihood Explanation
Exploitation only requires being an installed (even trial/free) merchant on the target app — an "unprivileged internet user" relative to other tenants — capturing one legitimate webhook delivery for their own shop, and replaying it with a modified `shop-domain` header. No secret material, token, or elevated access is needed; the vulnerable check is entirely internal to `HmacValidator`/`Registry.process`, which never binds the shop header into the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable string, or otherwise independently verify that the `shop-domain` header matches a shop actually associated with the raw body/session before trusting it in `WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated header data and must not be trusted for tenant-sensitive branching without additional verification against known shop sessions.

### Proof of Concept
1. App installs the handler exactly as documented in `docs/usage/webhooks.md`, trusting `data.shop`.
2. Attacker (a legitimate merchant `attacker.myshopify.com`) receives a real webhook delivery for topic `shop/redact` (or any topic with a predictable/minimal body) with `raw_body = B` and header `x-shopify-hmac-sha256 = HMAC(secret, B)` (valid, since Shopify signed it for their shop).
3. Attacker POSTs to the app's webhook endpoint with the same `raw_body = B` and the same valid `hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` passes because it only checks `B` against the secret.
5. `Registry.process` calls the handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: ..., body: B, ...)`, and the app performs shop-scoped actions (e.g., compliance redaction, cache invalidation, state changes) against `victim.myshopify.com` on the attacker's behalf.
