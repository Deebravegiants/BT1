### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by checking only the HMAC of the raw request body, but the `shop` value that identifies *which tenant* the webhook belongs to is read straight from an unauthenticated HTTP header and handed to the app's handler unchecked.

### Finding Description
`Webhooks::Registry.process` verifies authenticity with: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, and `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

The `shop` accessor, however, is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is *not* part of the signed bytes: [3](#0-2) 

After the HMAC on the body passes, `process` builds `WebhookMetadata` using this unauthenticated header value and forwards it to the app-registered handler as the trusted tenant identifier: [1](#0-0) 

Because `Context.api_secret_key` is a single, per-app secret shared across every installed shop (not a per-shop secret), any unprivileged user who has installed the app on their own store can legitimately receive one correctly-HMAC'd webhook for their own shop, then replay the identical body/HMAC pair while substituting the `x-shopify-shop-domain` header for a victim shop's domain. The binding the code should enforce is:
`shop asserted by request.shop == shop actually producing the signed bytes`
but the implementation only proves `hmac(raw_body) == valid`, leaving `request.shop` completely uncorrelated with the signature. This is the same class of bug as the reported `AutoCompound` issue: one field (`vaults[owner]`/here, the HMAC) is validated, while a different, unbound field (`owner` used for authorization/here, `shop` used for tenant routing) drives the security-relevant decision.

### Impact Explanation
Host applications are documented to use `WebhookMetadata#shop` to route webhook payloads to the correct tenant's data store (this is literally the value's purpose per `docs/usage/webhooks.md`). An attacker controlling their own legitimately-installed shop can forge webhook deliveries that the gem will report as authentic and attribute to an arbitrary victim shop domain, letting them inject attacker-chosen data/events into another tenant's processing pipeline — a cross-tenant integrity/confidentiality violation reachable by any unprivileged app-installing user, without needing the app's `client_secret` or any victim credentials.

### Likelihood Explanation
Any user who can install the app (an ordinary, unprivileged action) can obtain one valid `(raw_body, hmac)` pair for their own shop by triggering any subscribed webhook topic, then replay it with a modified `shop`-domain header value. No secret material, TLS interception, or victim cooperation is required, so likelihood is high for any app that trusts `WebhookMetadata#shop` for tenant identification (the documented usage pattern).

### Recommendation
Bind the `shop` value into the signed material that `HmacValidator` verifies (e.g., include the shop domain/header set in `to_signable_string`), or independently verify that the shop asserted in the header matches a shop the app has an active session/webhook registration for before dispatching to the handler, rather than trusting the unauthenticated header value as-is.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) so Shopify sends a POST with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Capture `B` and the valid HMAC header.
3. Replay the same `B` and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against the HMAC (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31; `lib/shopify_api/webhooks/request.rb` lines 35-38).
5. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `victim-shop.myshopify.com` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), causing the app to process attacker-controlled data under the victim tenant's identity.
