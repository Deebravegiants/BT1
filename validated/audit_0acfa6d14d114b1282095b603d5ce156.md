### Title
Panic-inducing out-of-bounds `copy_from_slice` when converting a relayer-supplied BEEFY `Vote` signature into a fixed 65-byte buffer - ([File: evm/rust/src/conversions.rs])

### Summary
`evm/rust/src/conversions.rs` implements `From<Vote> for SignatureWithAuthorityIndex`, which copies an ABI-decoded, variable-length `Bytes` signature field directly into a fixed-size `[u8; 65]` array using `copy_from_slice` without first checking that the supplied bytes are exactly 65 bytes long.

### Finding Description
```rust
// evm/rust/src/conversions.rs:356-366
impl From<Vote> for SignatureWithAuthorityIndex {
	fn from(value: Vote) -> Self {
		let sig_bytes = value.signature.to_vec();
		let mut signature: TSignature = [0u8; 65];
		signature.copy_from_slice(&sig_bytes);
		SignatureWithAuthorityIndex {
			signature,
			index: value.authorityIndex.try_into().expect("authority index out of bounds"),
		}
	}
}
```
`Vote.signature` is declared as Solidity `bytes` (an arbitrary-length dynamic type) in `evm/src/consensus/EcdsaBeefy.sol` / `Types.sol`, and `Vote` objects arrive inside a `RelayChainProof`/`BeefyConsensusProof`, which is exactly the untrusted, attacker/relayer-controlled consensus proof payload submitted to verify a new BEEFY commitment (`verify_mmr_update_proof` in `modules/consensus/beefy/verifier/src/lib.rs`, invoked from the ISMP consensus-client dispatch path in `modules/ismp/clients/beefy/src/consensus.rs`). Nothing upstream enforces that each vote's `signature` field is exactly 65 bytes before this conversion runs.

`Rust`'s `<[u8]>::copy_from_slice` requires the source and destination slices to have identical lengths; if `sig_bytes.len() != 65` (shorter or longer), it panics immediately (`slice::copy_from_slice: source slice length ... does not match destination slice length ...`). This is directly analogous to the OpenResty CVE: a fixed-size buffer is populated from attacker-influenced, variable-length data without validating the length first, producing an out-of-bounds condition (a Rust panic being the safe-language equivalent of the OOB write in C) that aborts/crashes the executing worker.

### Impact Explanation
Any relayer can submit a BEEFY consensus update message (`Message::Consensus` via `pallet_ismp::Call::handle_unsigned` or the equivalent EVM/host entrypoint) containing a `Vote` with a `signature` field that is not exactly 65 bytes. When the Rust host module for the EVM light client processes/converts this proof (e.g., during SP1/zk-proof related conversions or any code path invoking `From<Vote> for SignatureWithAuthorityIndex`), the process panics. Depending on panic-handling configuration this can abort the current transaction/task or crash the worker/node process handling that message, denying consensus updates and blocking message delivery on the affected route — a "route unable to deliver messages" outcome reachable from a single relayed proof, consistent with the accepted-impact criteria.

### Likelihood Explanation
High. Constructing an invalid-length `Vote.signature` is trivial — it merely requires ABI-encoding a `bytes` field of the wrong length, and this proof format is processed by any inbound consensus/relayer message. No privileged role is required; a single malicious relayer or a malformed input triggers the panic.

### Recommendation
Validate `sig_bytes.len() == 65` before calling `copy_from_slice`, returning a proper `TryFrom` error (propagated through the message pipeline) instead of using `From` with an implicit panic — mirroring the length checks already used elsewhere in this same file (e.g., `try_into().expect(...)` patterns should be replaced by fallible conversions that surface as `Err` in the consensus verification pipeline rather than panicking).

### Proof of Concept
1. Craft a BEEFY consensus proof (`BeefyConsensusProof`/`RelayChainProof`) where one `Vote.signature` is ABI-encoded as `bytes` with a length other than 65 (e.g., 64 or 66 bytes), leaving all other fields well-formed.
2. Submit this proof as a consensus update message through the normal relayer path (e.g., `handle_unsigned` with `Message::Consensus`, or the EVM `HandlerV2`/`EvmHost` consensus update flow that triggers the `From<Vote>` conversion in `evm/rust/src/conversions.rs`).
3. When the host converts the ABI `Vote` into `SignatureWithAuthorityIndex`, `signature.copy_from_slice(&sig_bytes)` panics because `sig_bytes.len() != 65`, crashing the worker/node processing that consensus update and halting delivery of further messages on that route. /// headers
pub fn verify_consensus<H: Keccak256 + EcdsaRecover + Send + Sync>(
	trusted_state: ConsensusState,
	proof: ConsensusMessage,
) -> Result<(Vec<u8>, Vec<ParachainHeader>), Error> {
	let (state, heads_root) = verify_mmr_update_proof::<H>(trusted_state, proof.mmr)?;
	let verified_headers = verify_parachain_headers::<H>(heads_root, proof.parachain)?;
	Ok((state.encode(), verified_headers))
}

/// Verifies a new Mmr root update, the relay chain accumulates it's blocks into a merkle mountain
/// range tree which light clients can use as a source for log_2(n) ancestry proofs. This new mmr
/// root hash is signed by the relay chain authority set and we can verify the membership of the
/// authorities that signed this new root using a merkle multi proof and a merkle commitment to the
/// total authorities
pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}

	let mmr_root_data = commitment
		.payload
		.get_raw(&MMR_ROOT_PAYLOAD_ID)
		.ok_or(Error::MmrRootHashMissing)?;

	if mmr_root_data.len() != 32 {
		return Err(Error::InvalidMmrRootHashLength { len: mmr_root_data.len() });
	}
	let mmr_root = H256::from_slice(mmr_root_data);

	let commitment_hash = H::keccak256(&commitment.encode());
	let mut authority_leaves: Vec<[u8; 32]> = Vec::new();
	let mut authority_indices = Vec::new();

	for sig in mmr.signed_commitment.signatures.iter() {
		let uncompressed = H::secp256k1_recover(&commitment_hash.0, &sig.signature)
			.map_err(|_| Error::FailedToRecoverPublicKey)?;

		let hashed_uncompressed = H::keccak256(&uncompressed);

		let mut eth_address = [0u8; 20];
		eth_address.copy_from_slice(&hashed_uncompressed.as_ref()[12..]);

		let authority_address_hash = H::keccak256(&eth_address);

		authority_leaves.push(authority_address_hash.into());
		authority_indices.push(sig.index as usize);
	}

	let merkle_proof = MerkleProof::<MerkleHasher<H>>::new(mmr.authority_proof.clone());

	let valid = merkle_proof.verify(
		authority_set.keyset_commitment.into(),
		&authority_indices,
		&authority_leaves,
		authority_set.len as usize,
	);

	if !valid {
		Err(Error::InvalidAuthoritiesProof)?;
	}

	verify_mmr_leaf::<H>(&mmr, mmr_root)?;

	if mmr.latest_mmr_leaf.beefy_next_authority_set.id > trusted_state.next_authorities.id {
		trusted_state.current_authorities = trusted_state.next_authorities.clone();
		trusted_state.next_authorities = mmr.latest_mmr_leaf.beefy_next_authority_set.clone();
	}

	trusted_state.latest_beefy_height = latest_height;

	Ok((trusted_state, mmr.latest_mmr_leaf.leaf_extra))
}
