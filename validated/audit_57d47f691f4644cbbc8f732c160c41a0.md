### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook attribution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the tenant identifier (`shop`) that the registry later trusts to attribute the webhook's data comes from an HTTP header that is never part of that signed content. This breaks the intended identity binding `hmac_valid(secret, payload) == true` ⇒ `shop == originating_shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, none of which are included in the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e. the body) against the received HMAC — it never checks or binds any header value: [3](#0-2) 

`Registry.process` trusts the HMAC check and then hands `request.shop` (the unauthenticated header) directly to the app's webhook handler as the tenant identity for the delivered body: [4](#0-3) 

Because the app's single `api_secret_key` is shared across every shop that installs the app, any shop can obtain a validly-HMAC'd `(body, hmac)` pair for events it legitimately triggers (e.g. by installing the app on an attacker-controlled test store and generating an order/customer event). Since the header carrying `shop` is outside the signed content, that same valid `(body, hmac)` pair can be replayed to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop. `HmacValidator.validate` still succeeds (only the body is checked), and `Registry.process` will dispatch the body to the handler tagged with the victim's `shop`, so the application-level handler processes/stores attacker-supplied data under the victim tenant's identity — the exact class of bug described in the report: a value (`shop`) that the gem acts on but that is not bound by the same authentication mechanism (HMAC) which is otherwise being relied on for trust.

### Impact Explanation
This is a cross-tenant identity confusion: the gem's own webhook-processing primitive (`Registry.process`) can be made to deliver a cryptographically-"valid" webhook under an arbitrary victim shop's identity. Any downstream handler that uses `WebhookMetadata#shop` to decide which tenant's records to create/update (the documented and intended usage of this API) can be poisoned with attacker-controlled data attributed to a shop the attacker does not own.

### Likelihood Explanation
Medium. It requires the attacker to (a) obtain at least one legitimately-signed `(body, hmac)` pair — achievable by installing the app on their own store and triggering a real event/webhook — and (b) be able to deliver a modified request (with a different `shop-domain` header but the same body/hmac) to the app's public webhook endpoint. No secret key, session, or privileged credential is required; only the ability to interact with the app as an ordinary merchant and reach its public webhook URL.

### Recommendation
Include the trusted shop/tenant identity in the HMAC-signed content (or otherwise cryptographically bind the `shop-domain`, `topic`, and `webhook-id` headers to the signature), e.g. by having `to_signable_string` incorporate the relevant headers, or by validating that the `shop` header matches a shop-specific secret/session rather than relying solely on a body-only signature under a single shared `api_secret_key`.

### Proof of Concept
1. Attacker installs the app on their own development store `attacker-shop.myshopify.com` and triggers a webhook-worthy event (e.g. creates an order), causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: H` (computed as `HMAC-SHA256(api_secret_key, B)`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` to the app's webhook endpoint.
2. Attacker captures `(B, H)` (e.g. via their own network tooling in front of the endpoint, or a webhook proxy/log they control).
3. Attacker re-sends a POST to the same public webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` calls `to_signable_string`, which only inspects `@raw_body` (`B`), so the signature check passes.
5. `ShopifyAPI::Webhooks::Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` using the spoofed header value `victim-shop.myshopify.com`, and the app's handler processes attacker-supplied data as if it belonged to `victim-shop`.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
