### Title
Permissionless canceller-set reset lets any address seize the `CANCELLER_ROLE` and censor all governance operations - (File: contracts/governance/src/timelock/recovery.rs)

### Summary
`Governance::propose_canceller_reset` schedules a reset of the timelock's canceller set with no authorization of any kind: no `require_auth`, no role check, no owner check. The resulting operation is flagged as a *recovery* op, which makes it permanently uncancellable, and `execute_canceller_reset` may be driven by anyone (`executor: None`). Any unprivileged address can therefore schedule a reset to an attacker-controlled canceller list, wait out the `Recovery`-tier delay, and execute it — acquiring the `CANCELLER_ROLE` and the ability to cancel every subsequent non-recovery governance operation. This is the direct analog of CVE-2017-4973's groups-endpoint privilege escalation: an endpoint that lets an ordinary user elevate their privileges.

### Finding Description
`propose_canceller_reset` builds a self-targeting `reset_cancellers` operation and calls `schedule_operation` directly, with no `begin_immediate`/role/owner gate anywhere in the function [1](#0-0) . It then marks the operation id as a recovery op via `storage::mark_recovery_op`, and `cancel` explicitly refuses to cancel recovery ops [2](#0-1) [3](#0-2) . Once the `Recovery`-tier delay elapses, `execute_canceller_reset` runs `apply_canceller_reset`, and `prepare_execute` authorizes nothing when `executor` is `None` — anyone may execute [4](#0-3) [5](#0-4) . `apply_canceller_reset` revokes `CANCELLER_ROLE` from every current holder except the owner and grants it to each address in `new_cancellers` — a list fully chosen by the attacker [6](#0-5) . Contrast with `propose`, which gates on `PROPOSER_ROLE` and further restricts sensitive ops to the owner [7](#0-6) .

### Impact Explanation
The attacker obtains `CANCELLER_ROLE` — a governance privilege — with no prior authorization, and simultaneously strips it from every legitimate canceller except the owner. From there the attacker can call `cancel` on any pending or future non-recovery operation [8](#0-7) : `Unpause` proposals, oracle reconfigurations, spoke edits, role revocations, and any other standard/sensitive op can be perpetually cancelled. If the controller is ever paused (e.g., by a guardian responding to an incident), the attacker can keep it paused indefinitely by cancelling every `Unpause` — a long-lived freezing of user funds. The malicious reset itself cannot be cancelled by anyone, so the only remediation is racing to schedule another recovery reset or an upgrade, both subject to the same long delays.

### Likelihood Explanation
A single unprivileged transaction (`propose_canceller_reset` with an attacker-chosen `new_cancellers` vector and arbitrary `salt`) initiates the attack; execution is also permissionless. No capital, no collusion, and no privileged access are required. The only mitigations are the `Recovery`-tier delay (`TIMELOCK_RECOVERY_MIN_DELAY_LEDGERS`, ~30 days) and off-chain monitoring — but even a detected attack cannot be cancelled on-chain, only pre-empted by scheduling a competing reset. The window where governance is censored is realistically long.

### Recommendation
Gate `propose_canceller_reset` at the entry point — e.g., `begin_immediate(env, &caller, PROPOSER_ROLE)` or `#[only_owner]` — matching how every other state-changing governance entrypoint is authorized. If a permissionless recovery path is an intentional design choice (to recover from a compromised/loss-of-key canceller set), the threat tradeoff should be documented in an ADR and the entrypoint declared in `scripts/permissionless_entrypoints.txt`; as written it grants a stranger the ability to silently replace a governance role set.

### Proof of Concept
```rust
// Attacker: any fresh address. Governance contract = gov.
let attacker = Address::generate(&env);
let salt = BytesN::<32>::from_array(&env, &[1u8; 32]);
let new_cancellers = vec![&env, attacker.clone()];

// 1. Schedule — no auth, no role required.
let op_id = gov.propose_canceller_reset(&new_cancellers, &salt);
assert_eq!(gov.get_operation_state(&op_id), OperationState::Waiting);

// 2. Owner/cancellers attempt to cancel — reverts: recovery op is uncancellable.
// gov.cancel(&legit_canceller, &op_id) -> Error(Contract, OperationNotCancellable)

// 3. After TIMELOCK_RECOVERY_MIN_DELAY_LEDGERS, anyone executes.
env.ledger().with_mut(|l| l.sequence_number += TIMELOCK_RECOVERY_MIN_DELAY_LEDGERS);
gov.execute_canceller_reset(&None, &new_cancellers, &salt);
assert!(gov.has_role(&attacker, &Symbol::new(&env, "CANCELLER")).is_some());

// 4. Attacker cancels the next legitimate proposal (e.g. Unpause).
gov.cancel(&attacker, &unpause_op_id); // succeeds
```

Note: verification that the API-level `propose_canceller_reset` wrapper adds no `#[only_owner]` or role guard could not be completed within available iterations; the underlying implementation in `recovery.rs` contains no authorization, and the codebase's own static gate (`scripts/check_access_control.py`) requires any guard to be reachable from the entrypoint — if the wrapper does add a guard, this finding reduces to a defense-in-depth gap rather than an exploitable path.

pub(crate) fn apply_canceller_reset(env: &Env, new_cancellers: &Vec<Address>) {
    renew_instance(env);
    let owner = owner_or_panic(env);
    let role = Symbol::new(env, CANCELLER_ROLE);
    let mut count = access_control::get_role_member_count(env, &role);
    while count > 0 {
        count -= 1;
        let holder = access_control::get_role_member(env, &role, count);
        if holder != owner {
            access_control::revoke_role_no_auth(env, &holder, &role, &owner);
        }
    }
    for account in new_cancellers.iter() {
        if account != owner && access_control::has_role(env, &account, &role).is_none() {
            require_executor_canceller_separation(env, &owner, &account, &role);
            access_control::grant_role_no_auth(env, &account, &role, &owner);
        }
    }
}
