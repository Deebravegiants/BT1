### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the event to the app's handler using the `shop` value taken from the `x-shopify-shop-domain` HTTP header — a value that is never included in the HMAC digest. This breaks the identity binding `authenticated_bytes == tenant_identifier`: the signature only proves the body's integrity/authenticity, not which shop it came from.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string`, and for webhooks `to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` used by `Registry.process` are all read directly from HTTP headers, none of which are part of the signed material: [3](#0-2) 

`Registry.process` checks only the HMAC (over the body) and then trusts `request.shop` and `request.topic` (from headers) to route and tag the event for the handler: [4](#0-3) 

Because Shopify apps share a single `api_secret_key` across every shop that has installed the app, any legitimately-received, correctly-signed webhook (for shop A, which an attacker controls/has installed the app on) has a body+HMAC pair that remains valid for that exact body regardless of which shop-domain header accompanies it. An attacker who has legitimate access to one installed shop can capture a real webhook delivery (body + valid HMAC) and replay the identical body/HMAC pair directly against the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` (and potentially `x-shopify-topic`) header value. `HmacValidator.validate` still succeeds because it only recomputes over `@raw_body`, and `Registry.process` will dispatch the (attacker-supplied) body to the app's handler tagged with the forged, victim shop's domain in `WebhookMetadata#shop`: [5](#0-4) 

This is the same bug class as the report: an identifier used to route/attribute privileged action (`permissionID` in the report, `shop` here) is not bound into the signed digest, and no separate check reconciles it against data that *is* authenticated.

### Impact Explanation
This allows a malicious or compromised app-installer (an "unprivileged internet user" relative to other tenants — they only have the privileges of their own shop's install) to make the app process events under another shop's identity. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., `shop/redact`, `app/uninstalled`, `customers/data_request`, or order/inventory sync handlers that look up or mutate per-shop records keyed by `shop`), this can lead to cross-tenant data corruption, spurious data deletion/redaction for a victim shop, or state confusion between tenants — a cross-tenant boundary violation.

### Likelihood Explanation
The prerequisite is that the attacker has legitimate access to at least one shop where the target app is installed (a low bar — installing a public/free app is unprivileged) and network access to the app's public webhook receiving endpoint (which by design must accept unauthenticated-at-transport-level POSTs, since the gem's own model of authentication is HMAC-over-body only). No access to the app's `client_secret`/`api_secret_key`, no TLS interception, and no privileged account is required — the attacker only replays a body/HMAC pair they legitimately received for their own tenant with a substituted header.

### Recommendation
Bind the tenant identity into the verified material instead of trusting an unauthenticated header:
- Prefer deriving `shop` from data that is itself protected by the HMAC (e.g., a shop identifier embedded in the JSON body, matched by the gem/host app against the header) rather than the header alone.
- At minimum, document/require that host applications reconcile `request.shop` against an out-of-band source of truth (e.g., the installed-shop registry) before trusting it, and consider extending `VerifiableQuery`/`to_signable_string` (or adding a companion check) so that the `shop-domain` and `topic` headers are validated to be consistent with the shop that a stored/expected webhook subscription belongs to.
- Reject webhooks whose `shop-domain` header does not correspond to a shop for which the app currently holds a session/install record.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g., `orders/create`) to the app's endpoint; attacker captures the raw POST: headers (`x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`) and the raw body `B`.
2. Attacker resends an HTTP POST to the same webhook endpoint with the identical body `B` and identical `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` (`B`) only and finds it matches `H` — validation succeeds: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed_body_of_B, ...)`, causing the app to process attacker-controlled data as though it originated from `victim-shop`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
