### Title
Webhook `shop` Attribution Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity used by webhook handlers (`shop`) from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that authenticates the request only covers the raw request body. This breaks the identity binding `hmac_verified_bytes == shop_attributed_to_handler`, allowing a party who legitimately receives one authentic webhook (i.e., any merchant who installs the app) to replay it to the app's public webhook endpoint with a different `shop` header while the HMAC check still passes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from an unauthenticated header, entirely independent of the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Webhooks::Registry.process` validates only this body HMAC, then immediately forwards the header-derived, unsigned `request.shop` to the merchant/tenant-scoped handler as the identity to act on: [4](#0-3) 

Because the `shop` header is never part of the signed payload, `HmacValidator.validate` returning `true` only proves "this body was produced by someone holding the app's `client_secret`" — it proves nothing about which shop the body belongs to. This is a direct instance of "a field acted on but not covered by the HMAC" breaking the equality `verified_bytes == attributed_tenant`. Note that in a single Shopify app, `Context.api_secret_key` is shared across all installs/tenants, so any merchant that installs the app can legitimately trigger genuine webhook deliveries (with a valid HMAC over their own body) and then replay that exact body+HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop.

### Impact Explanation
Any host application that follows the documented pattern of using `WebhookMetadata#shop` (populated straight from `request.shop`) to look up which tenant's session/access token to act on, or to write to tenant-scoped storage, can be tricked into processing attacker-supplied webhook content under a victim shop's identity — a cross-tenant confusion/write primitive. This matches the Critical/High "cross-tenant access" impact category, since the boundary broken is between two independent merchant tenants of the same app, using only a request that is fully producible by an unprivileged installer of the app (no access token, no `client_secret`, no privileged account required).

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP endpoint by design (Shopify calls it over the internet), and the attacker only needs to be a legitimate installer of the target app on their own store to obtain one genuine `(body, hmac)` pair, then replay it with a modified `shop-domain` header. No secrets, tokens, or elevated privileges are needed beyond normal app installation — a very low bar.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header value in the signed material verified by the HMAC check, or independently validate that the `shop` header corresponds to an existing, previously-registered session/install before dispatching to handlers. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically bound to the HMAC and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against a known session store keyed by shop).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a real webhook event (e.g., `products/update`) on their own store; Shopify delivers a POST to the app's webhook endpoint with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's shared `client_secret`, and header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same raw body and `x-shopify-hmac-sha256` value to the same endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` still returns `true` because it only checks the (unchanged) raw body against the (unchanged) HMAC.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the handler with `shop: "victim-shop.myshopify.com"` and the attacker-originated body, causing the host application to process attacker-controlled content under the victim shop's tenant context.
