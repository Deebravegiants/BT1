### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (tenant identity) is read from the `X-Shopify-Shop-Domain` header and is never included in the HMAC-signed material. Since the same app-level `client_secret` signs every merchant's webhooks for a given app, an attacker who controls one shop's install can replay a validly-HMAC'd webhook body while forging the `shop-domain` header to point at a different, victim tenant, and `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic for that victim shop.

### Finding Description
`Registry.process` verifies authenticity purely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes/compares the signature over `verifiable_query.to_signable_string` only: [2](#0-1) 

For webhook requests, `to_signable_string` is defined as just the raw body — it does not include the `shop`, `topic`, or `webhook_id` header values: [3](#0-2) 

Yet `request.shop` (parsed unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is passed straight into the webhook handler as the tenant identifier: [4](#0-3) 

The equality the gem is supposed to guarantee is: `hmac_valid(body, client_secret) == shop_is_authentic(request.shop)`. In reality the HMAC only proves "this body was signed by an app that shares this `client_secret`" — it says nothing about which of the app's installed shops sent it. Because the identical `client_secret` is used for every merchant that installs the app, any two webhook deliveries with the same body content produce the same HMAC regardless of shop. An attacker who operates (or has installed the app on) one shop can capture a genuine webhook delivery, then re-POST the same `raw_body` + `hmac-sha256` header to the app's webhook endpoint, substituting `X-Shopify-Shop-Domain` with a victim's shop domain. `HmacValidator.validate` still returns `true` (it never looked at the shop header), and the handler executes with `data.shop` set to the victim's domain — a full break of the shop/tenant identity binding.

This is most exploitable for the mandatory compliance topics (`shop/redact`, `customers/redact`, `customers/data_request`), whose payload schema is fixed/predictable, and for any webhook topic where the JSON body content is attacker-influenced or replayable (e.g., an app that includes attacker-controlled order/product data the attacker created on their own store, then replays with a spoofed shop header).

### Impact Explanation
This allows cross-tenant confusion in the app's webhook handling: a merchant/attacker can make the host application process data under an arbitrary victim shop identity that the app never actually sent a webhook for, while still passing this gem's authenticity check. Depending on what the app does with `data.shop` (e.g., using it to look up/modify the victim's stored session or trigger tenant-scoped actions), this can lead to cross-tenant access or data corruption — meeting the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Exploitation requires the attacker to control at least one legitimate install of the target app (any merchant can install a public app) and either observe/replay a webhook with a body identical/predictable enough to also be valid for the victim, most easily via the mandatory privacy webhooks whose bodies are structurally predictable per shop but not tied to shop by the signature. This requires no access to `client_secret`, no TLS interception, and no social engineering — it is a pure protocol-level identity binding gap in this gem's `Request`/`HmacValidator`/`Registry` code.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the HMAC-verified signable string for webhooks, or otherwise cryptographically bind the shop identity to the payload before trusting `request.shop` in `Registry.process`. At minimum, document and/or enforce that host apps must independently verify `request.shop` against a known/installed shop list before acting on webhook data, since the current design only proves body authenticity, not tenant authenticity.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a mandatory webhook, e.g. `shop/redact`, with some fixed-shape JSON body `B` and header `X-Shopify-Hmac-Sha256: H` (computed as `HMAC-SHA256(client_secret, B)`).
2. Attacker captures `B` and `H` (they own the shop, so they can freely trigger/observe this delivery, e.g. by requesting their own data export/redact).
3. Attacker POSTs to the app's webhook endpoint with the same `raw_body = B`, same `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(client_secret, B) == H`, and passes. [4](#0-3) 
5. The handler executes with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"`, even though Shopify never sent this webhook for that shop — the app has been tricked into acting on the victim shop's identity using attacker-supplied timing/content.
