### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the shop-domain and topic used to route and attribute the webhook are taken from unauthenticated HTTP headers. An attacker who can obtain any one valid `(body, hmac)` pair from Shopify (e.g. by installing the target app on their own free/dev store) can replay that exact body+hmac to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, causing the payload to be validated as authentic and attributed to a victim shop of the attacker's choosing.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are read straight from HTTP headers that are not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` (the body) against the HMAC secret — it never binds the shop/topic headers to the signature: [3](#0-2) 

`Registry.process` trusts `request.shop` and `request.topic` directly after this HMAC check succeeds, and hands them to the app's handler as the authoritative tenant identity: [4](#0-3) 

The gem's own documentation instructs developers to treat `data.shop` as "The shop domain of the webhook" and states that `Registry.process` "will verify the request did indeed come from Shopify," implying the entire payload — including the shop attribution — is authenticated: [5](#0-4) [6](#0-5) 

The broken identity binding is:
`shop authenticated by HMAC` (∅, not covered) ≠ `shop delivered to handler as tenant key` (`request.shop`, from header)

Since the HMAC only binds the JSON body to the secret, any `(body, hmac)` pair obtained from a legitimate delivery (even one triggered by the attacker installing the app on their own shop) remains valid when replayed with a different `shop-domain` header value, letting the attacker forge which tenant a given webhook body is attributed to.

### Impact Explanation
This breaks the tenant/shop identity boundary the gem is supposed to enforce for webhook processing, matching the Critical "cross-tenant access" category in scope: an attacker can make the host application process attacker-controlled data (or trigger side effects) under a victim shop's identity, since `data.shop` is what most integrating apps use to scope database writes, cache keys, or triggered jobs (as shown directly in the gem's own doc example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`).

### Likelihood Explanation
Exploitation requires no `api_secret_key`, access token, or privileged access — only the ability to (1) install the target app on any shop (including a free developer store) to capture one legitimate `(body, hmac)` webhook delivery, and (2) POST that same body/HMAC pair to the app's publicly reachable webhook endpoint with a forged `shop-domain` (and optionally `topic`) header. Both steps are available to any unprivileged internet user/app developer.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise independently authenticate the shop header against a value bound to the signature (e.g. requiring registries to be indexed by a signed shop claim) before dispatching to handlers. At minimum, document prominently that `data.shop`/`data.topic` are unauthenticated and must not be trusted for tenant scoping without additional verification (e.g. cross-checking against a known/registered shop for that webhook subscription).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering a real webhook delivery to the app's endpoint; attacker's own server logs the raw POST body `B` and the `X-Shopify-Hmac-Sha256: H` header Shopify sent.
2. Attacker sends a new POST to the app's public webhook URL with:
   - Body: exactly `B`
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid since it only signs `B`)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic` unchanged or forged similarly
3. `HmacValidator.validate` recomputes HMAC over `B` and matches `H`, so `Registry.process` accepts the request and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)` — an app following the documented handler pattern now processes attacker-controlled data as though it belongs to `victim-shop.myshopify.com`.
