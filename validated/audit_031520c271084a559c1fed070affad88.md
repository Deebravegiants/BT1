### Title
Orb-relay client responds to `RequestState` messages without verifying the sender's identity, bypassing the source-authorization check - (File: `orb-relay-client/src/client.rs`)

### Summary
In `PollerAgent::main_loop`, every payload received over the relay stream is normally validated against the expected communication partner (`src.id != self.config.dst_id`) before being handled. The one exception is `self_serve::app::v1::RequestState`, which is answered unconditionally with the client's cached `last_message`, skipping the same source-identity check that protects every other message type.

### Finding Description
The main receive loop enforces a peer-authorization invariant for all payloads: a message is only accepted into the buffer if its `src.id` matches the `dst_id` that was configured for this specific Orb/App relay session [1](#0-0) . This is the equivalent of `isApprovedOrOwner` in the original report — it is the sole binding between the payload and the party that is supposed to be allowed to trigger orb behavior for a given signup session.

However, the `RequestState` branch is evaluated *before* that ownership check, and it responds by echoing `self.last_message.clone()` back to the sender with no verification of `src.id` at all:

```rust
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx
        .send(self.last_message.clone())
        .await
        .wrap_err("Failed to send outgoing message")?;
} else if src.id != self.config.dst_id {
    tracing::error!(...);
} else {
    self.handle_message(...).await?;
}
``` [2](#0-1) 

`last_message` is whatever was most recently sent/received on this relay connection — it starts as a `NoState` default and is overwritten with every outgoing message the Orb/App sends, including self-serve signup control messages such as `CaptureStarted`, `CaptureTriggerTimeout`, or `AnnounceOrbId` [3](#0-2) . Because the `RequestState` handler never confirms that the requester is the same entity the connection was set up for, it discloses the session's last state to any entity able to send a `RequestState` payload on that stream, mirroring the report's root cause: a state-carrying action executed without validating the caller's ownership/authorization over the resource being acted upon.

### Impact Explanation
This allows disclosure/replay of the current self-serve signup session's last relayed control message to a party that was never authenticated as the legitimate counterpart for that session, breaking the same one-sided trust boundary that `carryVoteForward()` broke (acting/reading state tied to another identity's session without its owner's authorization). In the self-serve signup flow this state directly reflects biometric-capture session progression (e.g., whether capture has started), so unauthorized access constitutes cross-signup state bleed.

### Likelihood Explanation
Medium: exploitation requires being able to establish or otherwise place a payload on the same relay bidirectional stream identified by `orb_id`/`session_id`, and the surrounding gRPC relay auth model (token/ZKP) is only partially visible from this repository — the server-side of `orb-relay` (routing/session-isolation enforcement) is outside `orb-core--015` and was not available to inspect. That authentication may or may not fully prevent an unrelated but connected client from reaching this code path, so I cannot confirm end-to-end exploitability from the client-only code alone.

### Recommendation
Move the `RequestState` handling below (or make it subject to) the same `src.id == self.config.dst_id` check applied to all other payloads, so state is only replayed to the verified counterpart of the session, exactly as the original recommendation added an ownership check before permitting `carryVoteForward()` to act.

### Proof of Concept
Not independently verified end-to-end because the relay server-side authorization/session-routing implementation is not part of this repository; the client-side logic shown above is the exact, concrete code path that omits the identity check for the `RequestState` message type [4](#0-3) .
