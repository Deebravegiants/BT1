Based on the code cited in the report, the claim accurately reflects the pallet's design and represents a genuine logic flaw.

Audit Report

## Title
PSM permanently DoS's mint/redeem for an external asset if its live decimals metadata changes after registration - (File: `substrate/frame/psm/src/lib.rs`)

## Summary
`pallet-psm` snapshots an external asset's `decimals` at approval time in `ExternalAssetInfo::decimals` (and the internal asset's decimals in `PsmInfo::internal_decimals`), then enforces strict equality between that snapshot and the live decimals reported by `T::Fungibles::decimals(...)` on every mint/redeem call via `ensure_decimals_match`. Since asset decimals metadata in `pallet-assets` is controlled by that asset's own `Owner`/`Issuer` (or `Root`) via `set_metadata`/`force_set_metadata` — an authority entirely independent of the PSM instance's `full_admin`/`emergency_admin` — a metadata change performed outside the PSM's control permanently blocks all mint/redeem operations for that asset pair with `Error::DecimalsMismatch`.

## Finding Description
`add_external_asset` snapshots the external asset's decimals into `ExternalAssetInfo::decimals` at registration time, and `PsmInfo::internal_decimals` is snapshotted similarly at PSM creation. Every mint/redeem path calls `ensure_decimals_match`, which compares the live decimals from `T::Fungibles::decimals(...)` against these stored snapshots and returns `Error::DecimalsMismatch` on any divergence: [1](#0-0) 

`decimals` is asset metadata in `pallet-assets`, mutable after creation by that asset's team (`Owner`/`Issuer`) via `set_metadata`, or by `Root` via `force_set_metadata` — a completely separate authority from the PSM's own admin roles (`ensure_psm_admin`): [2](#0-1) 

There is no cross-pallet hook, resync mechanism, or fallback that reconciles the cached snapshot with a live metadata change — the strict equality check simply reverts every subsequent call touching the affected pair. This matches the described root cause: a cached, per-instance snapshot (`ExternalAssetInfo.decimals`/`PsmInfo.internal_decimals`) is permanently invalidated by an unsynchronized change from an independent authority (`pallet-assets` metadata owner), with no reconciliation path.

## Impact Explanation
Once the live decimals diverge from the stored snapshot, all `mint`/`redeem` calls for that `(internal_asset, external_asset)` pair on the affected PSM instance permanently fail with `DecimalsMismatch`. Per the pallet's documented remediation path, unblocking requires `remove_external_asset` (which requires debt to reach zero) followed by re-adding the asset — but debt reduction typically requires redemptions, which are themselves blocked by the same check, potentially leaving the pair in a state where neither minting, redeeming, nor removal (while debt is nonzero) is possible. This is a genuine denial-of-service of core PSM economic functionality for the affected asset pair, triggered by an action outside the PSM's own trust boundary.

## Likelihood Explanation
This requires the external (or internal) asset's own metadata-setting authority (Owner/Issuer of that specific `pallet-assets` asset, or Root) to change `decimals` after the PSM has already onboarded the asset. This is a plausible operational event — metadata corrections, migrations, or re-decimalization are realistic scenarios for real-world stablecoins — and crucially requires no compromise of the PSM's own admin roles, making this a legitimate cross-authority trust-boundary issue rather than a self-inflicted admin mistake.

## Recommendation
- Avoid hard-reverting on live/snapshot decimals mismatch. Preferable options:
  - Use live decimals for conversion math instead of pinning to a stale snapshot, or
  - Add a permissionless/PSM-admin extrinsic to refresh the stored decimals snapshot upon detecting a mismatch, or
  - Track debt/reserves in a decimals-agnostic unit.
- At minimum, allow `remove_external_asset` (or an emergency-only variant) to bypass `ensure_decimals_match`, ensuring operators are never stuck with a pair that can neither be traded nor removed.

## Proof of Concept
1. Asset team creates external asset `USDC` (id `X`) in `pallet-assets` with `decimals = 6`.
2. PSM admin calls `add_external_asset(internal_asset, X)`; `ExternalAssetInfo { decimals: 6, .. }` is stored.
3. Users mint/redeem normally, as `ensure_decimals_match` passes (live == snapshot == 6).
4. `X`'s asset `Owner`/`Issuer` (or `Root`) calls `pallet_assets::set_metadata`/`force_set_metadata`, changing decimals to 8.
5. Any subsequent `mint`/`redeem` call for `(internal_asset, X)` now fails `ensure_decimals_match` with `Error::DecimalsMismatch`, permanently, until removal/re-addition succeeds (blocked while `PsmDebt` is nonzero).

		/// Verify the live decimals for an external still match the snapshot taken at
		/// registration on this PSM, and that the internal asset's live decimals still
		/// match the snapshot stored in [`PsmInfo`].
		pub(crate) fn ensure_decimals_match(
			info: &PsmInfo<T>,
			internal_asset: &T::AssetId,
			external_asset: &T::AssetId,
			external: &ExternalAssetInfo,
		) -> Result<(u8, u8), DispatchError> {
			ensure!(
				T::Fungibles::decimals(external_asset.clone()) == external.decimals,
				Error::<T>::DecimalsMismatch
			);
			ensure!(
				T::Fungibles::decimals(internal_asset.clone()) == info.internal_decimals,
				Error::<T>::DecimalsMismatch
			);
			Ok((external.decimals, info.internal_decimals))
		}

		pub(crate) fn ensure_psm_admin(
			origin: OriginFor<T>,
			internal_asset: &T::AssetId,
			required: impl Fn(PsmManagerLevel) -> bool,
		) -> DispatchResult {
			let admin = PsmAdmin::<T>::get(internal_asset).ok_or(Error::<T>::PsmNotFound)?;
			let caller = <T as Config>::RuntimeOrigin::from(origin).into_caller();
			let level = if caller == admin.full_admin {
				PsmManagerLevel::Full
			} else if caller == admin.emergency_admin {
				PsmManagerLevel::Emergency
			} else {
				return Err(DispatchError::BadOrigin);
			};
			ensure!(required(level), Error::<T>::InsufficientPrivilege);
			Ok(())
		}
