### Title
Webhook `shop` identity is trusted from an unauthenticated header, not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to webhook handlers from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` checks only covers the raw request body. Because the shared `api_secret_key` used to compute the HMAC is the same across every shop that has the app installed, any merchant who has installed the app can obtain a body+HMAC pair that is valid for the app's secret, and then replay it to the app's webhook endpoint while substituting a different shop's domain in the (unsigned) header. The app will process attacker-supplied webhook data attributed to a victim shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the raw body — none of the Shopify headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included in the signed material: [2](#0-1) 

Yet `Registry.process` takes the `shop` used to build `WebhookMetadata` (the tenant identity delivered to the host application's handler) straight from that unsigned header: [3](#0-2) [4](#0-3) 

The binding that should hold is:
`shop asserted in header == shop that is cryptographically bound to the signed payload`

but the gem only enforces:
`HMAC(body, api_secret_key) == received_hmac`

The `shop` value is never part of the equality that the HMAC proves. Since `api_secret_key` is a single value shared by the app across *all* installed shops (it is not shop-specific — see `Context.setup`/`Context.api_secret_key` usage in `HmacValidator.validate`), any shop with the app installed can generate a legitimately-signed `(body, hmac)` pair from its own webhook traffic and then replay that exact pair to the same endpoint with the `shop-domain` header swapped to a victim shop. `HmacValidator.validate` will report success because it never checks the header, and `Registry.process` will hand the attacker-controlled body to the handler tagged with the victim's shop identity.

### Impact Explanation
This is a cross-tenant integrity failure: a low-privileged actor who merely has the target app installed on their own store (no admin secrets, tokens, or credentials needed) can cause the application's webhook handler to believe arbitrary attacker-chosen JSON payloads originated from a different merchant's shop. Depending on how the host app uses `WebhookMetadata.shop` (e.g., to key data updates, trigger redactions, or route sensitive processing), this enables injection of forged events into another tenant's data space — a cross-tenant access issue.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs the ability to install the app on any store (ordinary merchant capability, not a privileged account) and to capture one legitimate `(raw_body, hmac)` pair emitted for their own shop (e.g. via a debug proxy or by controlling a webhook receiver during app development/testing). No knowledge of `api_secret_key` itself is required — only reuse of a value the app itself produced.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material that `HmacValidator` checks, or otherwise cryptographically tie the header-derived shop to the payload before constructing `WebhookMetadata`. At minimum, `Request#to_signable_string` should incorporate the shop-domain header (mirroring how Shopify's own webhook signing includes the full raw body plus verifying the header out-of-band via TLS-terminated, per-shop delivery), and `Registry.process` should reject requests where the header-derived shop cannot be corroborated against a value bound by the signature.

### Proof of Concept
1. App has a single shared `api_secret_key` (`Context.api_secret_key`) for all installed shops.
2. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) captured with a debug endpoint, obtaining `raw_body` and its valid `X-Shopify-Hmac-Sha256` value.
3. Attacker POSTs the same `raw_body` and `hmac` header to the app's production webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(raw_body, api_secret_key) == received_hmac` per `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_controlled_json, ...)` per `lib/shopify_api/webhooks/registry.rb:198-199`, causing the host application to process attacker data under the victim's tenant identity.
