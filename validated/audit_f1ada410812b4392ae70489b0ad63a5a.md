### Title
Permanent market freeze from `i128` RAY-value overflow during index accrual - ([File: common/src/rates/simulate.rs])

### Summary
High severity. An unprivileged caller can permanently freeze an overgrown lending market by calling `Controller::update_indexes(caller, assets)` after accrued indexes push either `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY` beyond `i128::MAX`. [1](#0-0) [2](#0-1) 

### Finding Description
`update_indexes` is permissionless apart from caller authorization and forwards the requested `HubAssetKey` list to the pool. [3](#0-2)  The pool's `update_indexes` loads each market and calls `interest::global_sync`. [4](#0-3) 

`global_sync` applies `accrue_step` for each elapsed compounding chunk. [5](#0-4) [6](#0-5)  Before calculating the new borrow index, `accrue_step` converts total scaled debt and supply to their current RAY-denominated values through `scaled_to_original`. [7](#0-6) [8](#0-7)  `scaled_to_original` uses `Ray::mul`, which delegates to `mul_div_half_up` and panics with `GenericError::MathOverflow` when the resulting value cannot fit in `i128`. [9](#0-8) [10](#0-9) 

The global index ceiling is `1e36` raw RAY units, equivalent to a `1e9x` index multiplier. [11](#0-10)  That ceiling does not prevent the earlier market-value overflow: for a market with scaled principal `S`, accrual fails once `S * index / RAY > i128::MAX`, which can occur far below the global index cap. [12](#0-11) [10](#0-9) 

Every pool leg loads the market through `synced_market`, which runs `global_sync` before the operation's accounting. [13](#0-12)  Consequently, repayment calculates accrued debt only after synchronization and withdrawal resolves supply only after synchronization. [14](#0-13) [15](#0-14) 

### Impact Explanation
Once the boundary is crossed, the market cannot perform the accrual needed to update its indexes or reduce the offending scaled balances. [13](#0-12) [16](#0-15)  Repayment, withdrawal, borrowing, supplying, liquidation settlement, and subsequent explicit index updates all revert at the same arithmetic step, permanently freezing supplier collateral and borrower repayment paths for that market absent a code or accounting-model change. [17](#0-16) [18](#0-17) [4](#0-3) 

### Likelihood Explanation
The trigger call itself is permissionless: any address can authorize as `caller` and submit `update_indexes(caller, vec![hub_asset])`. [1](#0-0)  Exploitation requires an already-large scaled market and enough elapsed accrual for its index to cross `i128::MAX * RAY / scaled_total`; it does not require malformed parameters, leaked keys, oracle manipulation, or privileged execution. [19](#0-18) [11](#0-10)  For example, an 18-decimal market with `1e36` scaled units reaches the value boundary near a `170.14x` index, while the configured index ceiling permits growth to `1e9x`. [20](#0-19) [11](#0-10) 

### Recommendation
Make the market's index ceiling depend on its scaled totals instead of using only the global `1e9x` cap. [12](#0-11) [11](#0-10)  Before applying an accrual step, compute a safe upper bound such as `floor(i128::MAX * RAY / scaled_total)` using `I256` intermediate arithmetic and clamp the borrow and supply indexes to the tighter of that bound and the existing cap. [8](#0-7) [21](#0-20)  Alternatively, represent market-total value calculations in `I256` throughout accrual, while separately enforcing the native-token transfer bound before any asset-unit conversion. [16](#0-15) [22](#0-21) 

### Proof of Concept
An attacker can prepare or identify a market whose scaled debt/supply is close enough to the representable boundary, then invoke the permissionless index-update path:

```rust
let market = HubAssetKey { hub_id, asset };

// Optional setup on an underutilized market:
// supply collateral in another asset, supply a large amount of `asset`,
// then borrow a large fraction of it.
controller.supply(attacker, supply_account_id, spoke_id, vec![(market, supply_amount)]);
controller.borrow(attacker, borrow_account_id, vec![(market, borrow_amount)], None);

// After accrued indexes push scaled_total * index / RAY past i128::MAX:
controller.update_indexes(attacker, vec![market]);
```

The final call reaches `Controller::update_indexes`, `markets::update_indexes`, `LiquidityPool::update_indexes`, `global_sync`, and `accrue_step`, where `scaled_to_original` panics on `MathOverflow`. [1](#0-0) [3](#0-2) [4](#0-3) [19](#0-18)  Subsequent calls such as `controller.repay(caller, account_id, vec![(market, 1)])` and `controller.withdraw(caller, account_id, vec![(market, 1)], None)` still enter pool legs that synchronize the market before reducing debt or supply, so they cannot recover the frozen market. [23](#0-22) [14](#0-13) [15](#0-14)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
```
