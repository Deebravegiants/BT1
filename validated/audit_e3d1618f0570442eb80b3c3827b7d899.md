### Title
`TokenExchange.exchange_token` sends the app's `client_id`/`client_secret` to an unvalidated `dest`-derived host - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the shop it will contact directly from the session token's `dest` claim, without ever validating that claim against the gem's own trusted-domain allowlist. The sibling method `migrate_to_expiring_token`, in the very same file, does perform this validation before making a structurally identical request. This inconsistency means the request that carries the app's `client_id` and `client_secret` in its POST body is built from a host string that was never bound to `Utils::ShopValidator`'s trusted-domain check.

### Finding Description
In `exchange_token`: [1](#0-0) 
the shop used to build the outgoing request is taken as `dest_shop = jwt_payload.shop` and passed straight into `ShopifyAPI::Auth::Session.new(shop: dest_shop)` with **no call to `Utils::ShopValidator.sanitize!`**.

`JwtPayload#shop` simply strips `"https://"` from the raw `dest` claim with no domain-suffix check: [2](#0-1) 
and the JWT decode/verification logic only checks the HS256 signature, `exp`/`nbf` (with 10s leeway) and that `aud == Context.api_key` — it never constrains `iss`/`dest` to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`: [3](#0-2) 

That unvalidated `dest_shop` is used to construct the `Session` that `Clients::HttpClient` turns into the outbound request host: [4](#0-3) 
and the request body sent to that host contains the app's `client_id` and `client_secret` in plaintext: [5](#0-4) 

By contrast, `migrate_to_expiring_token` in the same module performs the exact same "build session → POST client_secret to `/admin/oauth/access_token`" operation, but first runs the shop value through `Utils::ShopValidator.sanitize!`, which enforces membership in `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [6](#0-5) [7](#0-6) 

The broken identity binding is: **host-that-receives-`client_secret` == host-validated-as-a-trusted-Shopify-domain**. `migrate_to_expiring_token` enforces this equality; `exchange_token` does not, relying solely on JWT signature/audience checks to implicitly vouch for `dest` being a legitimate Shopify host.

### Impact Explanation
If any value ever reaches `exchange_token` as a `dest` claim that is not itself constrained to a Shopify-owned domain (whether through JWT/secret handling edge cases, custom/dev-domain configurations, or host-application misuse of the token-exchange entry point without additional checks), the gem will unconditionally POST the app's `client_id` and `client_secret` to that host — an SSRF that exfiltrates the app's OAuth client credentials, matching the "SSRF with the app's credentials" High-impact category.

### Likelihood Explanation
Likelihood is limited by the fact that `dest` is inside an HS256-signed session token verified against `Context.api_secret_key` (or `old_api_secret_key`), which in the correct/documented flow is only known to Shopify and the app — so under strict, correct usage Shopify itself controls `dest`. However, the gem provides no defense-in-depth here, unlike its own sibling function, so any weakening of that external guarantee (secret rotation windows, alternate token issuance paths, or host-app misuse) has no secondary check to fall back on.

### Recommendation
In `exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` before constructing the `Session`/`HttpClient`, mirroring the check already present in `migrate_to_expiring_token`, so the host that receives the app's `client_secret` is always provably bound to a trusted Shopify domain.

### Proof of Concept
Not applicable as a standalone external PoC — forging a valid `dest` claim requires the app's `api_secret_key`, which is out of scope per the rules. The finding is the structural/code-level gap itself: `exchange_token` omits the `ShopValidator.sanitize!` call that its sibling `migrate_to_expiring_token` performs before sending the same credential-bearing request, as shown in the cited lines above.
