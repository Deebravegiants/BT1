### Title
Fee-on-transfer tokens break escrow accounting in the Tron `IntentGatewayV2.placeOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the `_orders` escrow map with the nominal (fee-reduced-for-protocol-fee-only) order amount instead of the amount the contract actually receives from `safeTransferFrom`. For fee-on-transfer ERC20 tokens, this permanently overstates escrow balances relative to the contract's real token holdings.

### Finding Description
In the no-predispatch branch of `placeOrder`, tokens are pulled with a plain `safeTransferFrom` call and the escrow ledger is incremented using `reducedInputs[i].amount`, which is derived purely from the user-specified `order.inputs[i].amount` minus the protocol fee — it never reflects what the contract's balance actually increased by: [1](#0-0) 

This is the fee-on-transfer bug class described in the report: the code assumes `transferFrom(amount)` delivers exactly `amount`, but deflationary/fee-on-transfer tokens deliver less, and nothing measures the actual delta.

The sibling, non-Tron contract explicitly guards against this by snapshotting `balanceOf` before and after the transfer and mutating `order.inputs[i].amount` to the real delta before it is used to compute the commitment/escrow: [2](#0-1) 

and this exact behavior is unit-tested for the main EVM contract: [3](#0-2) 

The Tron contract's predispatch branch also has a partial guard (it snapshots the dispatcher's balance and reverts if less than required), but the plain no-predispatch path — the common path most users take — has no such check: [4](#0-3) 

### Impact Explanation
`_orders[commitment][token]` is the sole source of truth used later by `withdraw()` (invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow`, and from `cancelOrder`) to pay out solvers or refund users: [5](#0-4) 

If a fee-on-transfer token is used as an order input, the gateway's actual token balance will be smaller than the sum of the credited escrow entries across all orders. Whichever redemption is processed later will find the contract under-collateralized for that token, causing:
- Reverting withdrawals for a later solver/user (permanent freezing of funds for that order), or
- If `withdraw()` performs a plain transfer without checking contract balance, an earlier claimant can drain the pool such that later legitimate claimants cannot be paid out at all.

This is a direct violation of the escrow's solvency invariant and matches "concrete... permanent freezing of funds" impact criteria.

### Likelihood Explanation
Likelihood is bounded by adoption of fee-on-transfer tokens as intent inputs on the Tron deployment, but the contract does not restrict or reject such tokens — any user can call `placeOrder` with any ERC20 as `order.inputs[i].token`. Since the vulnerable code path (no-predispatch) is the default/simplest usage, exploitation only requires selecting a deflationary token as input and placing an order; no special privileges are needed.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` immediately before and after each `safeTransferFrom` call in the no-predispatch branch, use the actual received delta to compute `reducedInputs[i].amount` (after subtracting protocol fee proportionally on the real amount), and use that adjusted amount both for the `commitment` hash and for the `_orders` escrow credit, exactly as done for the main EVM contract and validated by `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`.

### Proof of Concept
1. Deploy a 1% fee-on-transfer ERC20 (e.g., the `FeeOnTransferToken` test helper already in the repo) and mint balance to `user`.
2. `user` approves the Tron `IntentGatewayV2` for `inputAmount = 1000e18` and calls `placeOrder` with that token as the sole input, no `predispatch`.
3. Contract executes `IERC20(token).safeTransferFrom(msg.sender, address(this), 1000e18)` — actual balance increase is only `990e18` due to the 1% fee — but `_orders[commitment][token]` is credited with `reducedInputs[i].amount` computed from the full `1000e18` (minus only protocol fee, if any), e.g. `990e18`+ worth of nominal accounting that does not correspond to the true `990e18` balance once multiple such orders accumulate discrepancies from repeated fee deductions on withdrawal/refund paths, or simply exceeds the contract's actual token balance under `RefundEscrow`/`RedeemEscrow` given further transfer fees are also incurred paying out via `safeTransfer` in `withdraw()`.
4. When `withdraw()` is later invoked (via `onAccept` for `RedeemEscrow` or `cancelOrder`/`RefundEscrow`) for this and other concurrent orders on the same fee-on-transfer token, the sum of credited escrow entries exceeds the gateway's real token balance, causing a revert (frozen funds) for at least one legitimate claimant.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
