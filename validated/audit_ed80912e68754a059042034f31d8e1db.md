## Finding

The Tron variant of `IntentGatewayV2`'s escrow-release routine drops a zero-amount guard that the mainline EVM implementation has, making it vulnerable to a permanent freeze of escrowed funds when a leg's amount rounds down to zero and the token reverts on zero-value transfers — the exact same bug class as the referenced `FeeSplitter.distributeFees` report (a batch of transfers where one zero-value leg is not skipped, so a token reverting on `transfer(x, 0)` blocks the whole batch).

### Title
Zero-amount escrow leg can permanently freeze all withdrawal funds in `IntentGatewayV2.withdraw` (Tron) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw` (Tron variant) iterates over `body.tokens` and unconditionally calls `token.call(...transfer(beneficiary, amount)...)` for every entry, without skipping zero-amount entries. The sibling mainline implementation, `IntentsBase._withdraw`, explicitly guards this with `if (amount == 0) continue;`. Some ERC-20 tokens revert on a zero-value `transfer` call; because the Tron loop reverts the whole function on any single leg's failure, a single zero-amount leg permanently blocks release of every other (non-zero) token amount and the transaction fee bundled in the same withdrawal request.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()`: [1](#0-0) 
loops `body.tokens` and calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` for every token, including when `amount == 0`.

Compare to the mainline `IntentsBase._withdraw`, which explicitly skips zero-amount legs: [2](#0-1) 

A zero amount is reachable in normal operation: same-chain partial fills compute the escrow release amount proportionally with integer division: [3](#0-2) 
`escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;` — for a small `order.inputs[i].amount` relative to `totalRequired`, a small partial fill (any solver can choose `fillAmount`) truncates this to exactly `0`, while other legs in the same order can have nonzero amounts. This zero-amount `TokenInfo` is then included as one of the `tokens` in the `WithdrawalRequest` body dispatched cross-chain as `RedeemEscrow`/`RefundEscrow`, and delivered to `onAccept`, which calls `withdraw(body, ...)`: [4](#0-3) 

If the zero-amount leg's token reverts on a zero-value transfer (a known real-world token behavior, cited in the original report), the `token.call(...)` still "succeeds" at the low level for a `revert`-style ERC20 unless it actually reverts — in this case the low-level `.call` would return `success = false`, tripping `revert TransferFailed()` and aborting the entire `withdraw()` execution, including the release of every other nonzero-amount token and any escrowed transaction fee in the same request.

### Impact Explanation
Because the loop has no per-item isolation and the whole function reverts on the first failing transfer, this is not merely a griefing DoS: it results in **permanent freezing of all escrowed funds attached to that order/withdrawal request** — not just the zero-amount leg but every other token amount and the transaction fee bundled with it. There is no retry path that changes the outcome, since the zero-amount condition and the token's revert-on-zero behavior are both deterministic and immutable once the order was placed and partially filled. This satisfies the "permanent freezing of funds" bar.

### Likelihood Explanation
Reachable by any permissionless solver simply by choosing a small `fillAmount` for a same-chain partial fill relative to `totalRequired` for a small-denomination input token — no privileged role is required. The only external precondition is that one of the order's input tokens has zero-value-transfer-revert semantics (a real, documented ERC-20 behavior class, not a contrived assumption), making this a realistic Medium-severity issue analogous to the original `FeeSplitter` report.

### Recommendation
Mirror the mainline guard in the Tron `withdraw()` function: skip transferring (and correspondingly skip/zero out escrow bookkeeping for) any `body.tokens[i]` entry whose `amount == 0`, e.g.:
```solidity
if (amount == 0) { unchecked { ++i; } continue; }
```
before attempting the `token.call(...)` transfer, exactly as done in `evm/src/apps/intentsv2/IntentsBase.sol`.

### Proof of Concept
1. Place a same-chain order with two input legs: leg A with a very small amount (e.g. `1` unit of a token that reverts on zero-value transfers) and leg B with a large, unrelated amount of a normal token, both required to be fully filled to release escrow.
2. A solver performs a partial fill with a tiny `fillAmount` for the corresponding output such that `escrowedAmount = (legA.amount * fillAmount) / totalRequired` truncates to `0` for leg A, while any other output/legs remain nonzero.
3. The resulting `escrowedInputs` (including the zero-amount leg A) is bundled into a `WithdrawalRequest` and dispatched as `RedeemEscrow`/`RefundEscrow`.
4. On delivery, `IntentGatewayV2.onAccept` → `withdraw()` iterates the tokens; the zero-value `transfer` call to leg A's token fails (reverts), causing `withdraw()` to revert entirely via `TransferFailed()`.
5. All escrow release (including leg B's nonzero amount and any transaction fee) for this commitment is now permanently blocked, since the underlying zero-amount condition cannot be changed by retrying.
