### Title
Webhook shop-domain identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The `ShopifyAPI::Webhooks::Request` class computes its HMAC-signable string from the raw request body alone, while the `shop` (and `topic`) values delivered to app webhook handlers are taken from HTTP headers that are never included in the signed material. Any actor who can obtain one validly HMAC-signed webhook body (e.g., by installing the app on their own store and capturing the webhooks Shopify sends to the app's public endpoint) can replay that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header for a different, victim shop. Because `Utils::HmacValidator.validate` only checks the raw body against the secret [4](#0-3) , this forged request passes verification, and the handler receives `WebhookMetadata` claiming the payload originated from the victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read directly from headers with no cryptographic binding to the HMAC:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [5](#0-4) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` and compares it to the `hmac-sha256` header [6](#0-5) . It performs no check that the `shop-domain` header is consistent with anything cryptographically tied to that specific shop. After this single check, the handler is invoked directly with the untrusted header value:
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [7](#0-6) 

The identity binding broken here is: `shop header used by handler == shop the body was actually signed/sent for`. Since every webhook for an app (across all installed shops) is signed with the same `Context.api_secret_key`, an attacker who is a legitimate merchant of the app on their own shop can capture a body+HMAC pair that is valid under the app's secret, then resend that exact body to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. The HMAC still validates because it never covered the shop/topic headers, so the app processes attacker-controlled data as if it came from the victim shop.

### Impact Explanation
This breaks the tenant isolation the HMAC check is meant to provide: because `shop` is not part of the signed payload, an app relying on `WebhookMetadata#shop` to route data updates, or to determine which merchant's data record to modify or delete (e.g., `shop/redact`, `customers/redact`, `app_uninstalled`), can be made to attribute attacker-controlled data or events to an arbitrary victim shop. This is a cross-tenant access primitive: data intended for/about one shop is processed under a different shop's identity purely because of an unauthenticated header value, meeting the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Any user able to install the app on a shop they control (a normal, unprivileged flow, not requiring `api_secret_key`, an access token, or any privileged account) can capture at least one genuinely signed webhook body/HMAC pair for that install, since the app's webhook secret is shared across all installations. They can then freely replay that body against the app's public webhook receiver with a forged `shop-domain`/`topic` header, since the receiving endpoint is internet-reachable and the gem performs no additional binding check.

### Recommendation
Include the shop domain (and ideally topic, api version) in the value that is HMAC-verified, or otherwise cryptographically bind them—for example, look up the shop independently from a trusted, already-authenticated source (e.g., match against the shop tied to the `Auth::Session` used to register the webhook) rather than trusting the raw header value for any authorization-sensitive decision. At minimum, document that `WebhookMetadata#shop` is not itself HMAC-authenticated and must not be used for tenant-sensitive decisions without independent verification.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST body plus its `X-Shopify-Hmac-Sha256` header value — this HMAC is valid because it's signed with the app's single shared `api_secret_key`.
2. Replay the exact same body to the app's public webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and desired `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the secret [4](#0-3) .
4. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker's payload>, ...)` [7](#0-6) , causing the app to process attacker-supplied data under the victim shop's identity.
