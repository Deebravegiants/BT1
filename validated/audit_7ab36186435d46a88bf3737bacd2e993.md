### Title
Webhook `shop` field is unauthenticated relative to HMAC-signed body, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`Utils::HmacValidator.validate` only authenticates the raw webhook body via `Request#to_signable_string`, which returns `@raw_body` alone; the `x-shopify-shop-domain` header used to populate `WebhookMetadata#shop` is never included in the signed content. Because a single app-level `api_secret_key` is shared across every shop that installs the app, an attacker who receives their own validly-signed webhook can replay the identical `body` + `hmac-sha256` header to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop, and `Registry.process` will accept it and hand the attacker's body to the host app tagged as the victim's data.

### Finding Description
The broken binding, stated explicitly:

`WebhookMetadata#shop` (written to storage as tenant key) == the shop whose secret/body actually produced the accepted HMAC.

Trace:
- `Request#shop` reads directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cross-check against the body: [1](#0-0) 
- `Request#to_signable_string` (used as the HMAC signable content) returns only `@raw_body`, excluding every header including the shop domain: [2](#0-1) 
- `HmacValidator.validate_signature` computes the signature purely over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the received `hmac-sha256` header: [3](#0-2) 
- `Registry.process` validates HMAC, then constructs `WebhookMetadata` straight from `request.shop` (header) and `request.parsed_body` (body) with no additional consistency check between the two, and hands it to the host handler: [4](#0-3) 
- `WebhookMetadata` is a plain `T::Struct` carrying `shop` and `body` as independent fields with no derived relationship enforced by Sorbet typing: [5](#0-4) 

Root cause: the gem's webhook HMAC scheme authenticates "this body was produced by someone holding this app's `api_secret_key`" but does not authenticate "this body belongs to shop X." Since `api_secret_key`/`old_api_secret_key` are per-app, not per-shop, every merchant that installs the app holds the ability to produce a validly-signed `(body, hmac)` pair. An attacker who installs their own development shop receives genuine Shopify-signed webhook deliveries to their own endpoint. They can capture one such `(body, hmac-sha256)` pair, then send an unauthenticated POST directly to the target app's public webhook receiver endpoint, keeping `body` and `hmac-sha256` unchanged but substituting `x-shopify-shop-domain: other-shop.myshopify.com`. `HmacValidator.validate` still passes (it never looks at the shop header), and `Registry.process` produces `WebhookMetadata.new(shop: "other-shop.myshopify.com", body: {"id"=>1}, ...)`, which the host handler (per documented usage) uses as the tenant key to write into `other-shop`'s row.

No existing guard prevents this: `ShopValidator.sanitize!` is used only in OAuth/token-exchange flows (`lib/shopify_api/auth/token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`), never in the webhook path; there is no `JwtPayload`/`aud` check for webhooks; `Context.setup?`/`private?`/`embedded?` are unrelated to webhook shop binding; Sorbet only enforces field *types* (String), not field *provenance*.

### Impact Explanation
Any shop that has installed the app (an attacker's own unprivileged development/trial shop is sufficient) can forge webhook deliveries carrying arbitrary attacker-chosen JSON bodies while impersonating any other tenant shop domain, because the shared app secret makes the HMAC shop-agnostic. Host apps that follow the gem's documented pattern of using `WebhookMetadata#shop` as the tenant key will write attacker-controlled data into another merchant's records — this is cross-tenant data injection, repeatable against arbitrary victim shop domains (the domain is just a header value, no proof of shop identity is required), and it can be repeated for every mandatory or subscribed topic the app registers. This matches the "Critical - cross-tenant access" category.

### Likelihood Explanation
Preconditions are modest and within the defined attacker capability: the attacker only needs to install the target app on their own shop (a standard, unprivileged action) to obtain at least one genuine `(body, hmac)` pair signed with the app's shared secret, and to know/guess the app's public webhook endpoint URL (typically documented or discoverable, as it is a webhook registration `path`). No `api_secret_key`, access token, or session is required. The attack is a single crafted HTTP POST, fully repeatable and scriptable against any known victim shop domain.

### Recommendation
Bind the trusted shop identity to something cryptographically tied to the webhook signature rather than trusting the `x-shopify-shop-domain` header outright: e.g., have `Request#to_signable_string`/`HmacValidator` incorporate the shop domain header into the signed content check (not possible without protocol change from Shopify), or — more practically within this gem — document/require host apps to cross-verify `WebhookMetadata#shop` against a shop that is known to have actually subscribed to that specific `webhook_id`/topic (e.g., look up the registered webhook subscription for that `shop` + `topic` + `webhook_id` before trusting the payload), and add a check in `Registry.process` that rejects processing if the claimed `shop` does not match an expected/registered shop for that webhook registration.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require "test_helper"

class RegistrySpoofTest < Test::Unit::TestCase
  class FakeWebhookHandler
    include ShopifyAPI::Webhooks::WebhookHandler
    attr_reader :captured

    def handle(data:)
      @captured = data
    end
  end

  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.clear
    @handler = FakeWebhookHandler.new
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/webhooks", handler: @handler,
    )
  end

  def test_shop_header_is_unauthenticated_relative_to_body
    victim_shop = "victim-shop.myshopify.com"
    attacker_shop = "attacker-shop.myshopify.com"
    body = '{"id":1}'
    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest("sha256", ShopifyAPI::Context.api_secret_key, body),
    )

    # Attacker replays their own validly-signed body/hmac but forges the shop header
    request = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "x-shopify-topic" => "orders/create",
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => victim_shop, # forged
        "x-shopify-api-version" => "2024-01",
        "x-shopify-webhook-id" => "1",
      },
    )

    ShopifyAPI::Webhooks::Registry.process(request)

    # Binding check: body was only ever authenticated for the app secret,
    # never bound to attacker_shop or victim_shop specifically.
    assert_equal victim_shop, @handler.captured.shop        # unauthenticated header value flows through
    assert_equal({ "id" => 1 }, @handler.captured.body)      # body attacker fully controls
    # Both values reach the handler despite no cryptographic link between them,
    # demonstrating shop != authenticated owner of body.
  end
end
```
This demonstrates that `HmacValidator.validate` accepts the request and `Registry.process` yields `WebhookMetadata#shop == victim_shop` with attacker-controlled `body`, confirming the binding "`shop` written to storage == shop that signed the body" is broken.
