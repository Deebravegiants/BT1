### Title
Cumulative floor-rounding loss in `Router._computeBuy`/`_computeSell` can underflow `Bonding.canGraduate`'s `assetReserve - virtualLtReserve`, permanently bricking `sell()` on the curve - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.sell` unconditionally calls `canGraduate(tokenAddress)` before allowing a sell to proceed [1](#0-0) . `canGraduate` computes `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with plain (checked) Solidity subtraction [2](#0-1) . `_launchTimeVirtualLtReserve` is a constant derived once at launch from `Pair.k() / TOTAL_SUPPLY`, and `assetReserve` is expected to only stay at-or-above that floor because `tokenReserve * assetReserve` is supposed to never drop under `k`. However, both `Router._computeBuy` and `Router._computeSell` intentionally floor-divide when solving for the new reserve (`tokensOut = reserveToken - (k / newReserveAsset)` and `assetOut = reserveAsset - (k / newReserveToken)`) [3](#0-2) [4](#0-3) , and `Pair.swap`'s invariant check is deliberately loosened by `+1` on each side: `(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` reverts, rather than requiring the exact product `>= k` [5](#0-4) . This `+1` slack, combined with floor rounding on both the buy and sell legs, lets the *real* product `tokenReserve * assetReserve` drift strictly below `k` over repeated buy/sell round-trips by the same unprivileged trader, each cycle shaving off up to a few wei. Enough round trips can push `assetReserve` below the fixed `virtualLtReserve` floor, causing `canGraduate`'s subtraction to underflow and revert (Solidity 0.8.24 panics on unchecked arithmetic underflow rather than wrapping).

### Finding Description
The invariant that `assetReserve >= virtualLtReserve` (equivalently `realLtRaised = assetReserve - virtualLtReserve >= 0`) is assumed by every reader of `canGraduate`/`previewLtUntilGraduation`, but it is not enforced as an on-chain floor — it is only an emergent property of "the curve product never drops below `k`." That emergent property is broken by design: `Pair.swap`'s K-check uses `(newTokenReserve+1)*(newAssetReserve+1) >= k` instead of `newTokenReserve*newAssetReserve >= k`, and `Router._computeBuy`/`_computeSell` compute the counterpart reserve via **floor** division against `k`, so each buy leaves `tokenReserve*assetReserve <= k` (by up to `newReserveAsset - 1` short) and each sell leaves it `<= k` again (by up to `newReserveToken - 1` short). A trader who repeatedly buys and sells the same token on a curve with small reserves accumulates a downward drift in the true product across trades, permitted at every single step by the loosened `+1` K-check.

Because `assetReserve` starts exactly at `virtualLtReserve` on a fresh curve (`Pair.mint` sets `assetReserve = virtualLtReserve` at launch) [6](#0-5) , and only a sell can *decrease* `assetReserve` back toward that floor, a sequence of buy→sell round trips that nets back close to the starting `tokenReserve` can, via accumulated floor-rounding loss, leave `assetReserve` strictly below `virtualLtReserve`. The next call to `canGraduate` (invoked synchronously by every `Bonding.sell`) then executes `assetReserve - virtualLtReserve` with `assetReserve < virtualLtReserve`, triggering a Solidity panic revert (arithmetic underflow) rather than the graceful `false` the function is supposed to return.

### Impact Explanation
`Bonding.sell` calls `canGraduate(tokenAddress)` unconditionally before every sell to guard against selling through a graduatable threshold [7](#0-6) . If `canGraduate` reverts due to the underflow described above, **every subsequent `sell()` call on that token's curve reverts permanently** — there is no reset path since `virtualLtReserve` is immutable and `assetReserve` cannot be pushed back up except by buying (which increases `assetReserve` further away from, not toward, the underflow condition, but does nothing to fix the already-broken invariant for a fresh sell call). Traders and the token creator are permanently unable to sell/exit their position on the curve (`Zap.sell`/`Bonding.sell`), a freezing-of-funds condition. `previewLtUntilGraduation` (a public view relied on by keepers/front ends) would similarly revert. This qualifies as "permanent freezing of trader ... funds," matching the accept criteria.

### Likelihood Explanation
This requires no privileged role — any unprivileged trader can execute a sequence of buy/sell transactions against a low-liquidity/newly-launched curve (which starts with `assetReserve` exactly equal to `virtualLtReserve`, i.e., zero headroom) to accumulate the rounding drift. The exact number of round trips needed depends on per-trade rounding magnitude relative to reserve sizes, which was not empirically measured in this review (would need a PoC/fuzz test in Foundry to determine the minimum number of round trips against realistic reserve sizes and 18-decimal LT amounts). Given the headroom is initially zero (fresh curve) and grows only through buys, the most practical attack path is against a freshly launched, thinly-traded curve, which is realistic since many tokens are launched continuously and not all attract heavy volume before the attacker's first small buy.

### Recommendation
- Enforce `newTokenReserve * newAssetReserve >= _pool.k` exactly in `Pair.swap` (remove the `+1` slack, or bound the slack explicitly and prove it cannot compound across trades).
- Make `Router._computeBuy`/`_computeSell` round in the protocol's favor (ceiling instead of floor where appropriate) so `tokenReserve * assetReserve` never drops below `k`.
- Add a defensive floor-clamp in `Bonding.canGraduate`/`previewLtUntilGraduation`: `uint256 realLtRaised = assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0;` instead of raw subtraction, so a rounding-drift edge case degrades gracefully to "not graduatable" rather than reverting and bricking `sell()`.

### Proof of Concept
Conceptual (not executed — would need to be validated with a Foundry fuzz/invariant test against `packages/contracts/test/GraduationInvariants.t.sol` or a new test):
1. Launch a fresh token via `Bonding.launch`/`Zap.createToken` so `assetReserve == virtualLtReserve` (zero headroom, per `_deployAndSeed`).
2. As the same trader, repeatedly call `Zap.buy` followed by `Zap.sell` for the same small amount of tokens, many times, so that `tokenReserve` returns close to its starting value each cycle while `Router._computeBuy`'s and `Router._computeSell`'s floor divisions each shave a small amount off the true `tokenReserve * assetReserve` product, permitted by `Pair.swap`'s `(x+1)(y+1) >= k` check.
3. After enough cycles, call `Bonding.sell` (or the public `canGraduate`/`previewLtUntilGraduation` views) and observe a revert with the Solidity arithmetic-underflow panic (`0x11`) at `Bonding.sol:692`/`722`, rather than a normal `false`/valid-preview result — demonstrating the curve's `sell` path is now permanently bricked for that token.

Note: The exact number of round trips required to accumulate enough rounding loss to breach the zero-headroom floor was not verified numerically in this review; a concrete Foundry PoC is needed to confirm feasibility within reasonable gas/trade-count bounds before treating this as fully proven rather than a strong structural hypothesis grounded in the code's own floor-rounding + `+1`-slack design.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }
