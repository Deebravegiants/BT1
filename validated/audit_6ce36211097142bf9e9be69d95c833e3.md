Confirmed root cause. The webhook HMAC signature only binds the raw request body — `Request#to_signable_string` returns `@raw_body` alone, while `topic` and `shop` are read directly from HTTP headers and are never included in the signed material.### Title
Webhook `shop` and `topic` fields are trusted from unauthenticated headers while the HMAC only binds the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable material from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never covered by the signature. Any party capable of producing one valid `(body, hmac)` pair — including an attacker who legitimately installs the app on their own Shopify development store and receives real webhooks for it — can replay that exact body/HMAC pair to the app's public webhook endpoint while forging the `shop`/`topic` headers to any value they choose. `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic and hand the forged `shop`/`topic` to the host application's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are parsed straight out of the headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which only checks `verifiable_query.to_signable_string` (i.e. the raw body) against the secret — it never inspects `shop` or `topic` — and then forwards the attacker-controlled `request.shop` and `request.topic` straight into the handler's `WebhookMetadata`: [3](#0-2) [4](#0-3) 

The binding that should hold is: `hmac_valid(body) ⇒ shop_header == shop_that_actually_triggered(body)`. In reality, `hmac_valid(body)` only proves the body bytes were produced by Shopify for *some* shop under this app's `client_secret` — it says nothing about which shop the header claims, because `to_signable_string` never includes `shop` or `topic`.

### Impact Explanation
An attacker who installs the app on their own (free) development store receives genuine Shopify webhooks — valid `(raw_body, hmac)` pairs signed with the app's shared `client_secret`. Because the same `client_secret` signs webhooks for *every* shop that installs the app, and the signature never binds `shop`/`topic`, the attacker can POST that exact body to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop, and/or a forged `X-Shopify-Topic`. `Registry.process` will pass HMAC validation and invoke the handler with `WebhookMetadata(shop: <victim>, topic: <attacker-chosen>, body: <attacker's own genuine payload>)`. Any host application that uses `shop` as the tenant key to persist data, invalidate caches, trigger mandatory-compliance actions (`shop/redact`, `customers/redact`, `customers/data_request`), or otherwise scope side effects per shop will act on the victim tenant using attacker-supplied data — a cross-tenant integrity/confidentiality violation reachable by any unprivileged user who can self-install the app.

### Likelihood Explanation
Reaching this requires only: (1) the ability to install the target app on any Shopify store (including a free development store, which anyone can create), (2) capturing one legitimate webhook body+HMAC for a registered topic, and (3) sending a forged HTTP request directly to the app's public webhook endpoint with modified `shop`/`topic` headers — no access token, secret, or privileged account is needed. This is a plausible, low-effort exploit path entirely within the gem's own webhook-processing logic.

### Recommendation
Include `shop` and `topic` (and ideally `webhook_id`) in the HMAC-signable string, or otherwise cryptographically bind them to the verified body, so that forging the headers invalidates the signature. At minimum, document that host applications must not trust `WebhookMetadata#shop`/`#topic` as tenant-authoritative unless they independently cross-check it (e.g., against the shop embedded in the JSON body where Shopify includes one).

### Proof of Concept
1. Attacker creates a free Shopify development store `attacker.myshopify.com` and installs the target app, registering an HTTP webhook (e.g. `orders/create`).
2. Shopify sends a genuine webhook to the app: body `B`, headers `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`.
3. Attacker resends the identical body `B` and HMAC `H` to the app's public webhook route, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different registered `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` via `OpenSSL.secure_compare` — it never checks the `shop`/`topic` headers.
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's data>, ...)` and, if it persists or acts on this data keyed by `shop`, performs the action against the victim tenant using attacker-controlled data.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
