## Title
Webhook Shop-Domain Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The gem's webhook-processing pipeline verifies request authenticity by computing an HMAC over the raw request **body** only, but it treats the `shop-domain` request **header** as an authenticated tenant identifier when dispatching the webhook to the host application's handler. Because the header is never covered by the signature, an attacker who legitimately receives one genuine, signed webhook (e.g., to their own development store, which anyone can create for free) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. The handler will process the (still cryptographically "valid") payload as if it belongs to the victim shop named in the forged header, breaking the binding between "shop authenticated by the HMAC" and "shop the handler acts on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor simply reads the unauthenticated `shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the signature: [2](#0-1) 

`Registry.process` validates the HMAC purely against the body, and then immediately forwards `request.shop` — the unauthenticated header — to the application handler as the trusted tenant identifier in `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever operate on `verifiable_query.to_signable_string` (i.e. the body), confirming the header is outside the signed material: [4](#0-3) 

The identity binding that should hold is:

`shop_authenticated_by_HMAC == shop_the_handler_acts_on`

What actually holds is:

`shop_authenticated_by_HMAC == "" (nothing, only body is signed)` while `shop_the_handler_acts_on == request.shop (raw header, attacker-controlled)`

Because any developer can install the target app on their own store (or any store they control) and legitimately receive a correctly HMAC-signed webhook body from Shopify for that store, they possess a genuine `(raw_body, hmac)` pair. Nothing in `HmacValidator.validate` or `Registry.process` prevents them from re-sending that same body/HMAC pair with the `shop-domain` header rewritten to a different, victim shop that also has the app installed. `Registry.process` will accept it (the HMAC check passes because the body/HMAC pair is genuinely valid) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This crosses a tenant boundary: an attacker with no access to the victim's credentials, access token, or `client_secret` can cause the host application to process attacker-supplied webhook content (topic/body chosen by picking which real webhook they replay, timed at will) under the identity of another shop. Depending on how the host app's webhook handlers key their side effects (order/customer/product updates, GDPR mandatory webhooks, billing state, etc.) off `WebhookMetadata#shop`, this can lead to cross-tenant data corruption or disclosure — the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the capability any unprivileged internet user has: creating/using a Shopify development or trial store on which the target app is installed, capturing one legitimate webhook delivery, and replaying it with a modified header to the app's public webhook endpoint. No secret key, token, or privileged account for the victim is needed.

### Recommendation
Include the shop domain (and other identity-relevant headers such as `webhook-id`/`api-version` if they influence handler behaviour) in the signed material, or otherwise cryptographically bind the header to the verified body — e.g., by having `Registry.process` re-derive/verify the shop from data inside the signed body/topic-specific webhook registration, or by requiring host applications to cross-check `request.shop` against a shop that is independently known to have subscribed to that specific `webhook_id`/topic before trusting it. At minimum, the library documentation and `WebhookMetadata` should explicitly flag that `shop` is unauthenticated so host apps do not treat it as a trusted tenant key.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (any developer can do this for free).
2. Trigger any webhook topic the app subscribes to (e.g. `orders/create`) on `attacker-shop`; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this is a legitimately signed `(body, hmac)` pair.
3. Replay this exact body and `X-Shopify-Hmac-Sha256` header to the same app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a real shop with the app installed).
4. `HmacValidator.validate` succeeds (it only checks body vs. secret, both unchanged and valid), `Registry.process` dispatches to the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from and describes `attacker-shop`'s data. module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig

      def hmac

      end

      end

      sig { returns(String) }

        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id

        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end
