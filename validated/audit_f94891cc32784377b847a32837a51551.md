# Webhook shop/topic/webhook‑id are not covered by the HMAC signature, allowing cross‑tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read from unauthenticated headers. `Registry.process` accepts any request whose body HMAC validates against the secret, then hands the header-derived `shop` (and topic) straight to the app's handler as if they were verified. This mirrors the reported bug class: a field that is acted upon (`accounts[account].owners[owner].added`, here `request.shop`) is not the field actually protected by the security check (`removedAtBlockNumber`, here the raw-body HMAC).

### Finding Description
The webhook signature contract is: `to_signable_string == @raw_body`, and only that string is HMAC-verified:

<cite repo="AYontt/shopify-api-ruby--024" path="lib/shopify_api/webhooks/request.rb" start="35="38" /> [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers, none of which are part of the signed content: [2](#0-1) 

`Registry.process` validates only the body HMAC and then trusts `request.shop`/`request.topic` to build the metadata passed to the app's handler: [3](#0-2) 

The `HmacValidator` itself is generic and correctly checks whatever `to_signable_string` returns against the secret — the flaw is that the webhook `Request`'s signable string never binds the shop/topic/webhook-id, unlike `AuthQuery#to_signable_string` in the OAuth flow, which does include `shop` and `host` in the signed payload: [4](#0-3) [5](#0-4) 

Equality that should hold but doesn't: `hmac_verifies(raw_body) == hmac_verifies(shop, topic, webhook_id, raw_body)`. In this gem, only the left side is true; the right side (the actual security-relevant binding between body and the tenant it's asserted to belong to) is never checked.

### Impact Explanation
Any unprivileged internet user who can obtain **one legitimately HMAC-signed webhook body** for a given topic (e.g., because they install the target app on their own free/test Shopify shop and receive a real webhook for that topic) can replay that exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because the shop header isn't part of the signed content, and `Registry.process` will invoke the app's handler with `WebhookMetadata` claiming the payload came from the victim shop. This is a cross-tenant confusion vulnerability: an attacker-controlled payload is delivered to the app attributed to a shop they don't control, breaking the tenant isolation the gem is expected to provide via signature verification.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own valid webhook body+HMAC pair for a topic the target app registers (trivially obtainable by installing the app or triggering the relevant Shopify event on the attacker's own store), and (2) the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint — no access token, `client_secret`, or privileged account required. This is realistically exploitable by any external actor with a Shopify Partner/dev account.

### Recommendation
Bind the identity fields into the signed content, mirroring how `AuthQuery` includes `shop`/`host`. At minimum, `Webhooks::Request#to_signable_string` (or the validation step in `Registry.process`) should incorporate `shop`, `topic`, and `webhook_id` — or, more robustly, since Shopify's own webhook signature is computed over the raw body only, the gem should not treat header-derived `shop`/`topic` as unauthenticated. Alternatively, `Registry.process` should require that if the app has a way to independently know the topic/shop association it registered for (e.g., verify `topic` matches the handler that's about to run and treat `shop` as provisional/unauthenticated data that must be re-validated before being trusted for tenant-scoped operations), or document this loudly since HMAC covers body only. The safest concrete fix within this gem's control is documentation plus refusing to expose `request.shop`/`request.topic` as "verified" unless they're incorporated into the HMAC check.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, causing the app to register webhooks (e.g., `orders/create`).
2. Shopify sends a legitimately signed webhook to the app: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this request, then replays it directly to the app's webhook endpoint, keeping body `B` and header `H` unchanged but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation passes: [6](#0-5) 
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches it to the app's handler, which processes attacker-controlled data as if it originated from the victim shop.
