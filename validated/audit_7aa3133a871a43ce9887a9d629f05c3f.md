### Title
Unchecked Subtraction in `Bonding._prepareGraduationLiquidity` Underflows and Bricks Graduation - (File: packages/contracts/src/Bonding.sol)

### Summary
`_prepareGraduationLiquidity` computes `ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr)` with no guard that `assetReserve >= virtualLtReserve` [1](#0-0) . This is the exact bug class from the external report: a subtraction between two runtime-computed values that is assumed, but never enforced, to be non-negative. If `Pair`'s stored `assetReserve` is ever driven below the recovered launch-time virtual reserve, this line reverts with a Solidity `Panic(0x11)` underflow, and every caller of this internal function reverts with it.

### Finding Description
`virtualLtReserve` is recovered on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()`, relying on the invariant `k = tokenReserve_init * assetReserve_init` being fixed at mint time [2](#0-1) . The only guard against reserves violating this identity is `Pair.swap`'s K-floor check, which uses a `+1` slack on both reserves: `(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` reverts [3](#0-2) .

This `+1` slack means each `Bonding.sell` (an unprivileged, permissionless path any trader can call directly or via `Zap.sell`) can round in the seller's favor by a small integer amount when withdrawing `assetReserve` (LT) in exchange for tokens sold back into the curve. Because `tokenReserve` is bounded by `TOTAL_SUPPLY` (the virtual-reserve design keeps `tokenReserve ∈ [0.25·S, S]`), the worst-case single-swap slack pushes `assetReserve` toward `virtualLtReserve - 1` at the boundary where `tokenReserve → S` (i.e., when a large fraction of previously-bought tokens are sold back). Repeated chained sells that each shave a small amount off `assetReserve` via this rounding slack can accumulate the erosion below `virtualLtReserve` by more than the single-swap bound, since each swap's K-floor check is evaluated independently against the fixed `k`, not against a running "no erosion" invariant.

Once `assetReserve < virtualLtReserve`, `_prepareGraduationLiquidity` underflows and reverts. This function is invoked from `_enterGraduating`, which fires:
1. Inline at the end of every threshold-crossing `Bonding.buy` (via `_executeBuy`'s `canGraduate` check, per the documented dual-trigger flow) [4](#0-3) .
2. The permissionless `Bonding.triggerGraduation(tokenAddress)` entry point [5](#0-4) .

### Impact Explanation
If the underflow condition is reached, every buy that would cross the graduation threshold reverts, and the standalone `triggerGraduation` call also reverts — the token can never leave `Lifecycle.Curve` via the USD trigger. Depending on whether the same unchecked subtraction pattern also underlies the USD-value computation inside `canGraduate` (the view is documented to compute `(storedAssetReserve - virtualLtReserve) × exchangeRate`, per `docs/contracts-scope.md` lines 68-71), a revert there would additionally brick every subsequent buy on the token (since `canGraduate` is checked at the end of every buy inside `_executeBuy`), freezing the token's curve permanently and locking any USDC/LT value trapped in the pair — a permanent freezing-of-funds outcome consistent with Medium severity.

### Likelihood Explanation
Reaching this state requires an unprivileged trader to submit a sequence of `Bonding.sell` / `Zap.sell` calls (or a buy/sell round-trip pattern) that repeatedly exploits the `+1` K-floor rounding slack in `Pair.swap` to erode `assetReserve` below the recovered `virtualLtReserve` by more than the single-swap bound. This needs multiple transactions and careful sizing rather than a single call, so likelihood is Low-to-Medium, but it is fully reachable by a single unprivileged wallet with no special permissions, matching the report's precondition of "user has fewer [reserve] than the amount intended."

### Recommendation
Add an explicit floor check before the subtraction, mirroring the suggested fix in the external report:
```solidity
uint256 virtualLtReserve = _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
ltFromPair = assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0;
```
Apply the same guard to any equivalent subtraction inside `canGraduate`'s USD-trigger computation, and tighten `Pair.swap`'s K-floor check (or track cumulative rounding drift) so `assetReserve` can never legitimately fall below the recovered virtual reserve.

### Proof of Concept
Conceptual PoC (exact reproduction requires local Foundry testing against `Bonding.t.sol` / `Pair.t.sol` harnesses):
1. Launch a token via `Bonding.launch` and perform an initial `Zap.buy` to move the curve away from its virtual starting point.
2. Have an unprivileged trader alternate small `Zap.buy` / `Zap.sell` calls that each land at the K-floor boundary (`(tokenReserve+1)*(assetReserve+1) == k` exactly after rounding), each time reclaiming 1 extra wei of LT on the sell leg relative to the buy leg.
3. After enough iterations, `Pair.getReserves()` shows `assetReserve < Pair.k() / Token.TOTAL_SUPPLY()`.
4. Call `Bonding.triggerGraduation(tokenAddress)` (or perform a buy that would otherwise cross the USD threshold) and observe the transaction revert with a Solidity Panic(0x11) inside `_prepareGraduationLiquidity`, confirming graduation is permanently blocked for the token.

    /// @dev Recovers the launch-time virtual LT reserve from immutable
    ///      identities: `Pair._pool.k = tokenReserve_init * assetReserve_init
    ///      = TOTAL_SUPPLY * virtualLtReserve_init` is set ONCE in
    ///      `Pair.mint` and never modified by `Pair.swap` (swap only
    ///      mutates `tokenReserve` / `assetReserve` and asserts K-floor).
    ///      So `Pair.k() / Token.TOTAL_SUPPLY()` returns the exact
    ///      `virtualLtReserve` that was passed to `addInitialLiquidity` at
    ///      launch — for any pair, in any phase, with no storage of our own.
    ///
    ///      Going through this derivation rather than a stored mirror
    ///      eliminates an admin-writable economic-state slot and makes the
    ///      donation-immunity property a pure consequence of the pair's
    ///      already-immutable accounting. The `TOTAL_SUPPLY`-equality check
    ///      in `setTokenImplementation` keeps the divisor consistent across
    ///      impl rotations, so tokens launched under different
    ///      `tokenImplementation` versions still derive the same way.
    function _launchTimeVirtualLtReserve(
        address token_,
        address pair_
    ) internal view returns (uint256) {
        return IPair(pair_).k() / Token(token_).TOTAL_SUPPLY();
    }

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }
