### Title
Webhook `shop` field is not covered by the HMAC signature, allowing shop-domain spoofing in `WebhookMetadata` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies webhook authenticity using only the raw request body as the HMAC payload, while `shop` (`shopify-shop-domain` header) is read unauthenticated and forwarded verbatim into `WebhookMetadata` for handlers to consume as the tenant identifier. The identity binding `HMAC-authenticated bytes == data used by handler for tenant identification` is broken: the shop domain is acted upon by application code but is never part of what the HMAC actually protects.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` only — i.e. it authenticates the body bytes, not the headers: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (along with `request.topic`, `request.webhook_id`, etc., which are also headers outside the signed payload) to build the `WebhookMetadata` object passed to the app's handler: [4](#0-3) 

Because Shopify's genuine HMAC-SHA256 signature for a webhook delivery is computed over the JSON body using the app's `client_secret`/`api_secret_key`, and this library reproduces that same check, a valid `(body, hmac)` pair for one shop remains valid for *any* `shop-domain` header value an attacker supplies alongside it. The equality the code implicitly assumes — "the shop this HMAC authenticates" == "the shop in the `shopify-shop-domain` header" — does not actually hold, because the header is never part of `to_signable_string`.

### Impact Explanation
Any party who can obtain one genuine `(raw_body, hmac)` webhook pair for a shop (e.g., their own installed test store, or a captured/replayed delivery) can re-submit it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header. `ShopifyAPI::Webhooks::Registry.process` will pass HMAC validation (since it only checks the body) and hand the handler a `WebhookMetadata` whose `shop` field is attacker-controlled. If the host application uses `data.shop` (as this gem's own webhook workflow documentation implies apps should, to look up the corresponding merchant session/access token or to attribute the event) without independently re-verifying the shop against some other trusted binding, this enables cross-tenant data confusion: an app could act on, log, or apply state changes for the wrong shop, or fetch/act on another merchant's data using a session resolved from the spoofed `shop` value. This falls into the "cross-tenant access" impact category.

### Likelihood Explanation
Medium-to-High. No secret is required by the attacker other than possession of one legitimately-signed webhook body/HMAC pair, which is trivially obtainable for any shop the attacker controls (including a free trial/dev store on the same app), or by intercepting/replaying a delivery. The library provides no warning or built-in binding between the authenticated bytes and the shop metadata field it hands out, so any host application following the documented `WebhookMetadata` pattern is exposed unless it happens to add its own extra shop-binding check.

### Recommendation
Include the shop domain (and ideally topic and webhook-id) as part of the HMAC-signed payload, or independently bind the `shop` header to the shop the app expects for the given `hmac`. Practically, the library should either: (1) fail closed if `request.shop` doesn't match a shop the caller expects to receive events from before constructing `WebhookMetadata`, or (2) refuse to expose `shop`/`topic` as trusted values without documenting clearly that they are not covered by `to_signable_string`/HMAC verification, and encourage/require host apps to cross-check `data.shop` against the shop tied to the resolved session before using it.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, capturing `raw_body` and the `x-shopify-hmac-sha256` header value.
2. Attacker POSTs to the app's webhook endpoint with the exact same `raw_body` and `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only checks presence, not correctness) — `lib/shopify_api/webhooks/request.rb` lines 45-63.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` — `lib/shopify_api/utils/hmac_validator.rb` lines 12-31, `lib/shopify_api/webhooks/request.rb` lines 35-38.
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` and invokes the app's handler — `lib/shopify_api/webhooks/registry.rb` lines 188-200.
6. Any handler logic keyed on `data.shop` now operates under an attacker-chosen tenant identity despite a "valid" HMAC.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
