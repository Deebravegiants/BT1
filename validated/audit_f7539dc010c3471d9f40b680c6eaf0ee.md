### Title
Unfunded repay overpayment is refunded from pool custody — declared `amount` is treated as cash already received, letting anyone drain pool reserves - (File: contracts/pool/src/ops/repay.rs)

### Summary
The pool's `repay` leg computes the "overpayment" refund purely from the caller-declared `PoolAction.amount` compared against the position's ceiling-rounded debt (`resolve_repay`). It never verifies that tokens were actually transferred into the pool before the call. Any `amount` above the position's debt — or any positive `amount` on a market with no debt — is classified as "excess" and transferred out of the pool's real custody to `payer`, while `credit_cash` only books `net_repay` (which can be zero). This is the analog of the REXML round-trip bug: the same logical repayment value is reinterpreted across a trust boundary — the pool treats a *declared* amount as a *settled* receipt — so reparsing/re-entering the flow produces a different, attacker-favorable state.

### Finding Description
`contracts/pool/src/ops/repay.rs` documents "The controller transfers the repay amount into the pool before this call" and `accounting` then runs `cache.resolve_repay(amount, position)` on the declared `action.amount` (`common/src/rates/scaling.rs:171-192`). The excess branch returns `amount - current_debt_ceil` as `overpayment`, and `apply` calls `outcome.cache.transfer_out(payer, outcome.overpayment)` — a real token transfer out of pool custody — with no balance-delta check against actual receipts and no `cash`/`require_reserves` debit on the refunded amount (`contracts/pool/tests/flows.rs:3578-3610` explicitly pins this: "Neither refund debits `cash` or passes `require_reserves`... the whole amount is refunded out of real custody with the book untouched"). The controller path is safe because `settle_repay` uses `transfer_amount_measured` (`contracts/controller/src/positions/debt.rs:144-152`), but the pool entrypoint itself is invoked directly in tests (`t.client().repay(&payer, &t.ract(0, custody_before))`) with an arbitrary `payer` and no inbound funding, indicating it is callable by an unprivileged address that never transferred anything.

### Impact Explanation
Theft of user funds / contract unable to operate from lack of token funds. An attacker calls `pool.repay` with `action.amount` equal to the market's token balance and a zero (or dust) debt position; `resolve_repay` takes the full-close branch, `net_repay = 0`, the `RepayRoundsToZeroShares` assert passes via its `net_repay == 0` disjunct, and `transfer_out` pays the entire declared "overpayment" out of supplier custody — while `cash` bookkeeping stays untouched, desyncing book vs. custody and breaking `require_reserves`-backed withdrawals for honest users.

### Likelihood Explanation
A single unprivileged address submits one `repay` call with a fabricated `PoolAction`. No price movement, oracle manipulation, or prior position is required; the repayment leg on a debt-free market suffices, and it repeats across every listed market until custody is drained.

### Recommendation
In `ops::repay::apply`, measure the pool's actual balance delta for the leg's asset (snapshot before/after the inbound transfer, as the controller does with `transfer_amount_measured`) and clamp both `net_repay` and `overpayment` to the measured receipt; or restrict `repay` to the controller address / require that `cash` be debited for any outbound refund so refunds can never exceed funds actually received.

### Proof of Concept
```rust
// From contracts/pool/tests/flows.rs::test_unfunded_repay_overpayment_refund_also_pays_out_of_custody
let custody_before = token.balance(&t.pool);          // e.g. all supplier funds
// No token transfer into the pool, and the market has zero debt.
let credited = t
    .client()
    .repay(&payer, &t.ract(0, custody_before))        // amount = full custody, scaled = 0
    .get_unchecked(0)
    .actual_amount;
assert_eq!(credited, 0);                              // no debt retired
assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
// payer received `custody_before` tokens; cash book unchanged.
```
`resolve_repay` (`common/src/rates/scaling.rs:178-185`) sees `current_debt_ceil = 0`, so `overpayment = amount`; `accounting` credits `net_repay = 0` to cash and `apply` executes `transfer_out(payer, overpayment)` — draining real custody for funds that were never deposited.
