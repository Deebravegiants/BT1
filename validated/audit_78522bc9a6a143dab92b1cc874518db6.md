## Analysis

The Solidity bug involves a value (`numItemsToFill`) being computed from `start` after `start` was already mutated — an ordering flaw that breaks the intended relationship between two values that should have been evaluated together. The closest analog in this Ruby gem's in-scope code is a case where a value that is *used* to make a security decision is never *covered* by the cryptographic check meant to bind it — the webhook shop/topic identity is trusted while never being part of what the HMAC actually verifies. ### Title
Webhook shop/topic/webhook_id identity fields are not covered by the HMAC signature, allowing cross-tenant webhook forgery via signed-payload replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` validates only that the body matches the HMAC, then dispatches `WebhookMetadata` built from these unverified header fields to the application's handler.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes/verifies the signature strictly over `verifiable_query.to_signable_string`: [3](#0-2) 

For webhook requests, `to_signable_string` returns only `@raw_body`: [4](#0-3) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC signature: [5](#0-4) 

`Registry.process` validates the HMAC over the body only, then forwards the unverified `shop`/`topic`/`webhook_id` values straight to the app's handler: [2](#0-1) 

The identity binding that should hold is: `hmac_verified_bytes == bytes_the_app_trusts_for_tenant_attribution`. In reality: `hmac_verified_bytes = raw_body` while `bytes_the_app_trusts_for_tenant_attribution = headers[shop-domain]`. Because these are disjoint, any unprivileged internet user who can obtain one genuinely Shopify-signed `(raw_body, hmac)` pair — trivially available to them as the merchant of their own dev/test store, since Shopify signs all webhooks for an app with the same shared `api_secret_key` regardless of which shop triggered the event — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. `HmacValidator.validate` will report success (the body signature matches), and the gem will hand the app a `WebhookMetadata` claiming the event belongs to a victim shop the attacker does not control.

### Impact Explanation
This breaks tenant isolation in any multi-tenant app relying on this gem's `Registry.process`/`WebhookMetadata.shop` for attributing webhook data to the correct merchant. An attacker who legitimately installs the app on their own store can generate genuinely-signed webhook payloads (e.g. `customers/create`, `orders/create` with attacker-chosen field values) and then relabel them as belonging to any other shop domain, causing the host application to process/store attacker-controlled data under another tenant's identity, or trigger tenant-specific side effects (data deletion via GDPR-style topics, order processing, etc.) attributed to the wrong shop. This satisfies the "cross-tenant access" Critical-impact category since no access token, `api_secret_key`, or privileged account is required — only participation as an ordinary merchant/app installer.

### Likelihood Explanation
High. Obtaining a valid signed webhook is as simple as installing the app to one's own store and triggering an event; no secret material needs to be recovered, since the signature check never binds the `shop`/`topic` headers in the first place. This is a design gap reachable purely through the gem's public `Webhooks::Registry.process` / `Webhooks::Request` API as documented, not a host-app misuse.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the signed material the HMAC verifies (or otherwise cryptographically bind them, e.g. by having `to_signable_string` incorporate the normalized headers Shopify intends to be authoritative), so that `HmacValidator.validate` fails if any of these identity fields are altered relative to what Shopify actually sent.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures/triggers a webhook subscription (e.g. `customers/create`) — Shopify sends a POST with a body and a valid `X-Shopify-Hmac-Sha256` header computed over that body using the app's shared `api_secret_key`.
2. Attacker intercepts/records this exact `(raw_body, hmac_header)` pair.
3. Attacker replays the identical body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the HMAC — the forged `shop` header is never checked.
5. The app's webhook handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: ...)` and processes attacker-controlled data as if it originated from the victim shop.
