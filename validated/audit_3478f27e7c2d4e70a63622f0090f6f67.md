### Title
Missing Chainlink circuit-breaker price bounds in `SimplexPaymaster._getOraclePrice` lets stale/clamped oracle answers mis-price gas fees paid by bandwidth purchasers - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice()` only checks that the Chainlink `answer` is positive and not stale by timestamp; it never checks the returned answer against the underlying aggregator's `minAnswer`/`maxAnswer` circuit-breaker bounds. Any unprivileged user submitting an ERC-4337 `UserOperation` that pays gas through this paymaster (a "bandwidth purchaser" of gas) triggers this pricing path via `_fetchDetails` → `_tokenPrice` → `_getOraclePrice`. [1](#0-0) 

### Finding Description
`_getOraclePrice` fetches `latestRoundData()` and only guards against a non-positive answer and staleness by `updatedAt`: [2](#0-1) 

This function underpins `_tokenPrice`, which is invoked from `_fetchDetails` on every `UserOperation` that pays gas with a registered ERC-20 token, and from `swapAndDeposit`: [3](#0-2) [4](#0-3) 

`_fetchDetails` is called with no permission gating beyond the token being registered and active — any address can submit a `UserOperation` referencing this paymaster and a registered token: [5](#0-4) 

If the underlying Chainlink aggregator (either `nativeOracle` or a token's `tokenOracle`) hits its built-in circuit breaker (e.g., a severe de-peg or crash such as the LUNA/UST scenario referenced in the report), `latestRoundData()` keeps returning the clamped `minAnswer`/`maxAnswer` instead of the true market price, while still satisfying both of `_getOraclePrice`'s checks (`answer > 0` and freshly updated). Because there is no check of `answer` against the aggregator's min/max bounds, the paymaster will silently use this clamped, incorrect price to compute `tokenPrice` for gas charging.

### Impact Explanation
`_tokenPrice` computes `(nativeUsd * 10^tokenDecimals * (10000+markupBps)) / (tokenUsd * 10000)`, which directly determines how much ERC-20 token is pulled from a user's balance (via permit/Permit2 `_prefund`) to cover gas costs. A clamped/incorrect `nativeUsd` or `tokenUsd` value:
- Can cause users to be overcharged, resulting in fund loss for the bandwidth purchaser (unfair prefund transferFrom of an inflated token amount for the same gas cost), or
- Can cause the paymaster/treasury to undercharge, letting an attacker drain gas sponsorship at a fraction of true cost, draining the paymaster's EntryPoint deposit funded by the treasury.

Either direction is a concrete fund-loss scenario reachable by any unprivileged UserOperation submitter, matching the Medium-severity class described in the source report (missing Chainlink circuit-breaker checks leading to mispriced financial operations).

### Likelihood Explanation
Likelihood depends on the underlying Chainlink feed for either the native asset or a registered token actually hitting its circuit-breaker bounds (e.g. extreme volatility or a stablecoin de-peg below `minAnswer`). This is a known, previously realized failure mode for Chainlink feeds (as cited in the original report's Venus/LUNA precedent) and requires no special privilege from the exploiting party — only that they submit an ordinary `UserOperation` while the feed is clamped.

### Recommendation
Cache each aggregator's `minAnswer`/`maxAnswer` (or fetch them via the aggregator's `aggregator()` accessor) when registering `nativeOracle`/`tokenOracle` in `_setParams`/`_registerToken`, and add a bounds check in `_getOraclePrice`:
```solidity
if (answer <= minAnswer || answer >= maxAnswer) revert InvalidOraclePrice(address(oracle), answer);
```
so that a clamped circuit-breaker answer reverts pricing (and thus paymaster gas-sponsorship for that token) instead of being trusted as the true price.

### Proof of Concept
1. Governance registers a `tokenOracle` (or `nativeOracle`) for a Chainlink feed with a known `minAnswer`/`maxAnswer`.
2. The underlying asset price crashes far below the feed's `minAnswer` (or spikes above `maxAnswer`); Chainlink's aggregator keeps reporting the clamped bound value with a fresh `updatedAt` timestamp.
3. Any unprivileged actor submits a `UserOperation` with `paymasterData` mode `0x00`/`0x02` referencing the affected token; the bundler/EntryPoint calls `validatePaymasterUserOp` → `_fetchDetails` → `_tokenPrice` → `_getOraclePrice`, which passes both existing checks (`answer > 0`, not stale) despite the answer being the clamped, incorrect value.
4. `_prefund`/`_erc20Cost` compute the token amount to charge using this incorrect `tokenPrice`, producing a mis-priced gas charge (over- or under-charging) — see the pricing math and prefund flow at [6](#0-5)  and [7](#0-6) .

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
