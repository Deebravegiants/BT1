### Title
Webhook `shop` Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC computed over the raw request body only, then trusts the `shop` identity from an HTTP header that is not covered by that signature. An attacker who can obtain one genuinely-signed webhook body (e.g. by triggering an event on their own installed shop) can replay it with a forged `X-Shopify-Shop-Domain` header, causing the app to process attacker-controlled webhook data under a victim shop's identity.

### Finding Description
`Webhooks::Registry.process` verifies authenticity solely via: [1](#0-0) 

```
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only the raw body: [2](#0-1) 

But `request.shop`, which is passed downstream as the authoritative tenant identity in `WebhookMetadata`, is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of the signed content: [3](#0-2) 

This breaks the intended binding: `shop authenticated by HMAC == shop used as the tenant/session key`. The HMAC only proves "this body was produced with the app's `client_secret`" — it proves nothing about which shop the body belongs to. Because a single app's `client_secret` is shared across every shop that installs it, any unprivileged merchant who installs the app on their own store can capture one of their own legitimately-signed webhook deliveries (valid body + valid HMAC) and replay it to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Utils::HmacValidator.validate` still returns `true` (it only checks the body/secret pair), and `Registry.process` hands the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity spoofing primitive: any app built on this gem that uses `WebhookMetadata#shop` to key session lookups, database writes, or business logic (the documented intended use, see `docs/usage/webhooks.md`) can be made to attribute attacker-supplied data to a different merchant's tenant, without the attacker ever possessing that merchant's credentials, access token, or the app's `client_secret`. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires that the attacker be a legitimate (even free/trial) installer of the app — an unprivileged internet user relative to the target tenant. They need one real webhook delivery for their own shop (trivially triggered, e.g. updating a product) and the ability to replay an HTTP POST with a modified header, both of which are within reach of any external attacker with no special access.

### Recommendation
Do not treat the header-derived `shop` as authenticated purely because the body's HMAC validated. Options:
- Bind the shop domain into the signed content used for verification (not currently possible since Shopify signs only the body), or
- Require the app to independently corroborate `request.shop` against a shop it has a stored, previously-established session/webhook registration for, and document this requirement prominently, or
- At minimum, clearly document in `WebhookMetadata`/`Webhooks::Request` that `shop` is unauthenticated header data and must not be trusted as a tenant identity without additional verification (e.g., cross-checking against the shop associated with the registered webhook subscription id).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a real webhook, e.g. for `products/update`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `client_secret`).
2. Attacker replays the identical `B`/`H` pair to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request#shop` returns `"victim.myshopify.com"` from the header. `Utils::HmacValidator.validate(request)` still succeeds because it only re-derives HMAC from `B` using the shared `client_secret`, matching `H`.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to act on attacker-controlled data as if it came from the victim shop.
