### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. However, `Webhooks::Request#to_signable_string` returns only `@raw_body`, excluding the `shop-domain` (and `topic`) headers from the signed content. The `shop` value later handed to the app's handler (`WebhookMetadata.new(..., shop: request.shop, ...)`) is read directly from an unauthenticated header, breaking the identity binding: `shop covered by HMAC == shop delivered to the handler`.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it (constant-time) to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `Webhooks::Request` implements `VerifiableQuery` but defines the signable content as the raw body only, while `shop` and `topic` are pulled from separate, unsigned HTTP headers: [2](#0-1) 

`Registry.process` validates only this body-based HMAC and then trusts `request.shop`/`request.topic` verbatim to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because Shopify computes the webhook HMAC from `client_secret + raw body` only (not headers), and the `client_secret` is shared across *all* shops/tenants that installed a given app, any two merchants (tenants) of the same app receive webhooks signed with the *same* secret. An unprivileged merchant who has installed the app can capture a legitimately-delivered webhook (raw body + `X-Shopify-Hmac-Sha256` header) for their own shop, and replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain (and/or a different `X-Shopify-Topic`). `HmacValidator.validate` will still pass because it only checks the raw body, and `Registry.process` will hand the forged `shop` (and/or `topic`) straight to the registered handler as authenticated data.

This is the identity-binding analog of the reported bug class: a field (`shop`) that is *acted on* (used to attribute/route the webhook payload to a tenant) is not covered by the authentication mechanism (HMAC), so `shop authenticated ≠ shop delivered to the handler`.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to determine which tenant's data/session the webhook payload belongs to (the documented, expected usage pattern per `docs/usage/webhooks.md`), an attacker-controlled `shop` value combined with a genuinely-signed body enables cross-tenant data confusion/injection: a valid payload originating from the attacker's own shop can be misattributed to an arbitrary victim shop known to the app. This matches the "High - cross-tenant access" impact category, since it lets an unprivileged, otherwise-legitimate app user manipulate which tenant a signed webhook event is attributed to.

### Likelihood Explanation
Likelihood is moderate-to-high: any merchant who installs the app is inherently capable of receiving real webhooks for their own shop (no special privilege required), capturing the raw body + HMAC header pair, and replaying it to the app's public webhook endpoint with a different `shop-domain`/`topic` header. No knowledge of `client_secret` or access tokens is needed — only the ability to intercept/replay one's own legitimately-received webhook request, which is an unprivileged-internet-user-reachable action against the app's public webhook endpoint.

### Recommendation
Include the authenticated identity fields (`shop-domain`, `topic`, and ideally `webhook-id`) in the HMAC-covered signable content, or otherwise cryptographically bind them to the raw body (e.g., derive `to_signable_string` from a canonical concatenation of these headers plus the raw body) instead of computing the HMAC over the raw body alone. At minimum, document that `request.shop`/`request.topic` are not integrity-protected and must not be trusted for tenant attribution without an independent binding (e.g., verifying `shop` against the actual session/tenant that the webhook route is scoped to).

### Proof of Concept
1. App merchant A installs the app; Shopify delivers a legitimate webhook to the app's endpoint with headers:
   `X-Shopify-Hmac-Sha256: <valid-hmac-of-raw-body>`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Topic: orders/create`, and raw JSON body `B`.
2. Merchant A (attacker) captures this exact HTTP request (body `B` and the `X-Shopify-Hmac-Sha256` value are unchanged).
3. Attacker resends the request to the same webhook endpoint, only changing `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or `X-Shopify-Topic` to another registered topic), keeping body `B` and the original HMAC header identical.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC from `request.to_signable_string` (== raw body `B` only) and succeeds, since the body was not altered: [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: ..., ...)` where `shop` is now `victim-shop.myshopify.com` despite the payload actually originating from merchant A's shop, achieving cross-tenant attribution of a validly-signed payload.
