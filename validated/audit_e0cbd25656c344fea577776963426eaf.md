### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before dispatching it to the app's handler [1](#0-0) . In reality, the HMAC signature only authenticates the raw request body; the `shop`, `topic`, and `webhook_id` values used by the handler for tenant routing are taken from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` reads the signature from the `hmac-sha256`/`x-shopify-hmac-sha256` header [2](#0-1) [3](#0-2) . `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (i.e., the body only) and compares it to the received signature [4](#0-3) .

However, `shop`, `topic`, and `webhook_id` are all parsed straight from HTTP headers that are never included in the signed material [5](#0-4) . `Registry.process` validates only the HMAC and then forwards these unauthenticated header values directly into `WebhookMetadata`, which is handed to the app's handler as trusted data:

```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [6](#0-5) 

The identity binding that should hold is: `shop header == shop that the HMAC-signed body actually belongs to`. Because the signature covers only the body, that equality is never checked — the `shop` field is a field acted upon (used by the handler for tenant scoping, per the gem's own documented usage `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) but not covered by the HMAC [7](#0-6) .

An attacker who operates their own (e.g., free development) Shopify store can trigger a real webhook delivery to their own endpoint, capturing a genuinely Shopify-signed `(raw_body, hmac)` pair. Because the signature never binds `shop-domain`, `topic`, or `webhook-id`, the attacker can replay the identical body/HMAC to the victim app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain or a different topic. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will happily dispatch the forged `shop`/`topic` to the handler, which per the gem's documented pattern uses these fields as the tenant/topic key without any independent verification.

### Impact Explanation
This breaks the tenant-identity binding between the cryptographically-verified payload and the `shop` value the host application relies on to route/attribute the webhook, since the library only claims to verify "the request did indeed come from Shopify" while actually verifying only the body. Depending on how the host app persists or acts on `data.shop`/`data.topic` (as this gem's own docs instruct: enqueuing background jobs keyed by `shop_domain: data.shop`), this can lead to cross-tenant data being attributed to, or actioned against, the wrong merchant/shop, satisfying the "cross-tenant access" impact category.

### Likelihood Explanation
Requires an attacker to control a Shopify store capable of receiving genuine webhook deliveries (e.g., a free/dev store) — trivially available to any unprivileged internet user — plus knowledge of the victim app's webhook endpoint URL, which is generally either fixed/predictable or discoverable. No access to `api_secret_key`, tokens, or the victim's credentials is needed.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` header values into the HMAC-signed material (or otherwise cryptographically authenticate them), for example by including them in `to_signable_string`, or by having `Registry.process`/host apps independently verify that `request.shop` corresponds to a shop actually installed/known to the app before trusting it for tenant routing. At minimum, the documentation should be corrected to state that only the request body is authenticated, not the shop/topic/webhook-id headers.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) Shopify store `attacker.myshopify.com` and triggers a webhook delivery for a subscribed topic, capturing the real request: `raw_body`, and header `x-shopify-hmac-sha256`.
2. Attacker sends a POST to the victim app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC [9](#0-8) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from `attacker.myshopify.com`, demonstrating the broken binding [10](#0-9) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
