This is a legitimate, reachable finding. The path is confirmed end-to-end: an external HTTP/JSON-RPC user submits a `web_api_trigger` message via `handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go`, which forwards the raw payload unmodified to every DON node [1](#0-0) . Notably, the comment `// TODO: apply allowlist and rate-limiting here` confirms the gateway-side ingress applies no allowlist/size checks on the payload before broadcasting to all nodes [2](#0-1) . Each node's `triggerConnectorHandler.HandleGatewayMessage` then unmarshals `payload.Topics` and calls `processTrigger` with no upper bound on the number of topics, only rejecting empty topics [3](#0-2) , and executes `O(len(triggers) × len(topics))` iterations under `h.mu` [4](#0-3) .

The only bound on message size is `MaxAllowedMessageAgeSec`-independent, byte-oriented limits (`MaxRequestBytesLimiter`, `conn.SetReadLimit`) enforced at the websocket/HTTP layer, which cap total bytes but not element counts [5](#0-4) . Since JSON string topics can be very short (e.g., `"a"`), tens of thousands of unique topic strings easily fit within typical byte limits, so this doesn't meaningfully bound the topic count. The comparison to the vault handler's `MaxRequestBatchSizeLimiter` [6](#0-5)  is accurate — the webapi trigger path has no analogous check-count limiter.

One nuance for impact calibration: for topics that don't match `trigger.allowedTopics`, the per-iteration cost is a cheap map lookup [7](#0-6) , so the amplification is real but each unit of work is inexpensive (map lookup), not full per-item business logic — the more expensive work (rate limiter, telemetry, execution-ID generation) only runs for topics that both match `allowedTopics` and pass the sender check. Still, `O(registeredTriggers × topics)` map lookups under a shared mutex-guarded slice is a legitimate, unbounded resource consumption path triggerable by any caller permitted to submit `web_api_trigger` messages (which per the code appears to be any external user hitting the gateway's legacy endpoint, since the TODO shows no allowlist is applied at this stage). This matches an in-scope "excessive resource usage / DoS" impact class.

Audit Report

## Title
Unbounded `Topics` array in WebAPI trigger payload allows O(triggers×topics) amplification per gateway message - (File: core/capabilities/webapi/trigger/trigger.go)

## Summary
`triggerConnectorHandler.HandleGatewayMessage` decodes a `webapicap.TriggerRequestPayload` from a gateway-forwarded, user-originated message and passes it to `processTrigger` without any bound on the number of entries in `payload.Topics`. The gateway ingress path (`handler.HandleLegacyUserMessage`) explicitly has no allowlist/size validation yet (marked by a `TODO`), broadcasting the payload as-is to every DON node.

## Finding Description
`handler.HandleLegacyUserMessage` accepts a legacy user message, validates only that `Timestamp` is non-zero and non-stale, then forwards the raw payload to every member node with no topic-count or allowlist check, as the code's own comment acknowledges [8](#0-7) . On the node side, `triggerConnectorHandler.HandleGatewayMessage` unmarshals the payload and calls `processTrigger` for `MethodWebAPITrigger` [9](#0-8) . `processTrigger` only checks `len(topics) == 0`, with no upper bound, then iterates every registered trigger against every topic in the payload under `h.mu` [10](#0-9) . This is comparable to the vault handler's `MaxRequestBatchSizeLimiter`, which validates batch sizes before per-item work [6](#0-5) , and to wsserver's byte-based `MaxRequestBytesLimiter`, which does not bound array element counts [5](#0-4) . No equivalent count-based limiter exists for `Topics`.

## Impact Explanation
A caller able to submit legacy `web_api_trigger` user messages to the gateway can send a payload with a very large `Topics` array (bounded only by total byte limits, not element counts, since topic strings can be very short). This forces every subscribed node to perform `O(registeredTriggers × topics)` work under the shared `h.mu`-protected trigger list per message, and the gateway itself fans this single message out to all DON members, multiplying the effect across the whole DON. This is a resource-exhaustion / denial-of-service risk on the trigger-processing path, an in-scope "excessive resource usage" impact category. Note per-iteration cost for non-matching topics is a cheap map lookup, so severity is moderate rather than critical; expensive work (rate limiting, telemetry, execution ID generation) is only reached for topics matching a workflow's `allowedTopics`.

## Likelihood Explanation
Reaching this path only requires the ability to submit a `web_api_trigger` message to the gateway's legacy user-message endpoint; per the current code, this endpoint currently performs no allowlist or size-count validation (marked `// TODO: apply allowlist and rate-limiting here`), making the entry point reachable to an unprivileged external client. Exploitation is straightforward and repeatable since there is no existing per-message topic-count check to bypass.

## Recommendation
Add an explicit upper bound on `len(payload.Topics)` in `processTrigger` (and/or `HandleGatewayMessage`), rejecting oversized topic lists before the nested-loop dispatch, following the same pattern as `MaxRequestBatchSizeLimiter` in `core/capabilities/vault/validator.go`. Additionally, implement the still-outstanding `TODO: apply allowlist and rate-limiting` in `handler.HandleLegacyUserMessage` to reject unauthorized/oversized requests before fan-out to DON nodes.

## Proof of Concept
1. Submit a legacy JSON-RPC/HTTP user message with method `web_api_trigger` to the gateway, with a `webapicap.TriggerRequestPayload` whose `Topics` field contains tens of thousands of short unique strings, keeping total payload size under `MaxRequestBytesLimiter`.
2. The gateway's `handler.HandleLegacyUserMessage` forwards this unmodified to all DON member nodes (`core/services/gateway/handlers/capabilities/handler.go` lines 416-419).
3. Each node's `triggerConnectorHandler.HandleGatewayMessage` → `processTrigger` executes `len(registeredWorkflows) × len(Topics)` map-lookup iterations under `h.mu` per invocation.
4. Repeat the request to observe CPU/lock-contention amplification on the trigger-processing path across the DON, degrading legitimate trigger processing.
