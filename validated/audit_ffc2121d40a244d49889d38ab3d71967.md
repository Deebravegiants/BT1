## Custody-Analog Finding: Replay of `usdk::transfer_from` Approval Message via Stale Sequence-Number Nonce

### Title
Off-chain `transfer_from` approvals in the USDK example module are replayable because the "nonce" is the target account's transaction sequence number, which is never consumed by this call — (File: `aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move`)

### Summary
The external bug's core custody invariant is: *a function that moves value on behalf of another party must not let an unprivileged caller re-use or manipulate the authorization outside the bounds the original owner intended.* In the Bold Zapper, arbitrary `_zapper` input let anyone repeatedly "create volume" against a victim's approved balance. The Aptos analog is `usdk::transfer_from`, which lets any caller (`spender`) submit an off-chain signed `Approval` on behalf of `from` and move funds via `primary_fungible_store::transfer_with_ref`. The approval's replay protection is `account::get_sequence_number(from)`, but this call never increments that sequence number, so the same signed approval remains valid and can be submitted repeatedly.

### Finding Description
`transfer_from` builds an `Approval` struct and validates it with `account::verify_signed_message`: [1](#0-0) 

The `nonce` field is set to `account::get_sequence_number(from)` [2](#0-1) . `verify_signed_message` only checks that the signature over the exact `Approval` bytes matches the account's current auth key — it performs no bookkeeping of consumed nonces itself: [3](#0-2) .

Critically, `account::get_sequence_number(from)` only changes when `from` submits its own on-chain transaction (incremented in the VM prologue/epilogue via `check_for_replay_protection_regular_txn`, which asserts `txn_sequence_number == account_sequence_number` and is only bumped by actual transaction execution) [4](#0-3) . `transfer_from` is called by `spender` (not `from`), so it does **not** trigger `from`'s prologue/epilogue and does **not** advance `from`'s sequence number. Consequently, once a user signs an `Approval` for amount `X`, that exact same signed blob remains valid for the *same* `nonce` value indefinitely until `from` happens to submit an unrelated transaction of its own. Any spender who has a valid, unexpired approval can call `transfer_from` for the same `from`/`to`/`amount` repeatedly, and each call succeeds because `nonce` in `expected_message` recomputes to the same unchanged sequence number every time.

This breaks the custody invariant that "supply or custody accounting corruption [must not] move value to the wrong holder": a single owner authorization is turned into an unbounded, repeatable transfer authorization, effectively draining `from`'s balance in `amount`-sized increments until it's empty, contradicting the presumed one-time approval semantics implied by using a "nonce."

Design note: this module is example code under `move-examples/`, which is often excluded from custody-grade in-scope findings for pure documentation/demo purposes — however, `move-examples/fungible_asset/stablecoin` is explicitly presented as a reference implementation for production stablecoin deployments, so its custody logic is directly relevant to real, deployable USDK-style asset issuers.

### Impact Explanation
If deployed as-is, `transfer_from` allows unauthorized repeated draining of a user's fungible-asset balance from a single signed approval, moving asset custody to unintended holders beyond what the owner authorized (a single `amount`). This is a direct custody/supply-accounting corruption: value moves to the wrong holder repeatedly instead of once, and there is no recovery path since the underlying `TransferRef`-backed transfer is irreversible once executed. This matches the "Supply or custody accounting corruption that moves value to the wrong holder" and "theft ... of fungible assets" custody-impact classes.

### Likelihood Explanation
Likelihood is high for any real deployment that keeps a signed approval around (e.g., a dApp caching a user's gasless-transfer signature to be submitted later, or a relayer). As long as the `from` account does not submit any of its own transactions between calls (very plausible for delegated/gasless flows, which is the entire premise of `transfer_from`), an attacker (or a malicious/compromised relayer with a captured approval) can resubmit the exact call multiple times.

### Recommendation
Do not derive `nonce` from `account::get_sequence_number`, since that field is only advanced by the account's own submitted transactions, not by `transfer_from` invocations. Instead:
- Maintain an explicit, monotonically-incrementing nonce/allowance counter per `(from, spender)` (or globally per `from`) inside the `usdk` module's own storage, and increment it every time `transfer_from` succeeds.
- Alternatively, adopt an explicit one-time-use nonce set (similar to `nonce_validation::check_and_insert_nonce` used for orderless transactions) keyed by `(from, nonce)`, marking each nonce consumed after use so replay is impossible regardless of `from`'s activity.

### Proof of Concept
1. `from` signs an `Approval{owner: from, to, nonce: account::get_sequence_number(from), chain_id, spender, amount}` intending to authorize a single transfer of `amount` to `to`.
2. `spender` submits `usdk::transfer_from(spender, proof, from, scheme, pk, to, amount)`. It succeeds; `amount` moves from `from` to `to`.
3. Because `from` did not submit this transaction (it was submitted by `spender`), `from`'s on-chain sequence number is unchanged; `account::get_sequence_number(from)` is identical to before the call — confirmable by checking `check_for_replay_protection_regular_txn`, which only advances via `from`'s own submitted transactions, not this module call. [4](#0-3) 
4. `spender` resubmits the identical `transfer_from` call with the same `proof`. `expected_message` is recomputed identically (same unchanged `nonce`), so `verify_signed_message` again succeeds, and another `amount` is withdrawn from `from`.
5. Repeat until `from`'s balance is exhausted or the store is drained beyond the originally intended single authorization.

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
