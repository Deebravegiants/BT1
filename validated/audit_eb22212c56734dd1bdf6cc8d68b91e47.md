### Title
Webhook shop-domain header is trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking that the HMAC signature matches the raw request body. The `shop` value that is subsequently handed to the app's handler is read from an HTTP header that is **not part of the signed data**, so any caller who can produce one genuinely-signed body (which they legitimately receive for their own store, since every shop that installs the app shares the same `api_secret_key`) can attach that valid body+HMAC pair to a forged `shopify-shop-domain` header and have the app process it as if it came from a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signed content as only the raw body: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of the HMAC: [2](#0-1) 

`HmacValidator.validate` only compares the computed HMAC of `to_signable_string` (the raw body) against the received `hmac`; it never checks that the `shop` header is consistent with anything cryptographically bound to it: [3](#0-2) 

`Registry.process` performs exactly this HMAC-only check and then forwards the unauthenticated `request.shop` value straight into `WebhookMetadata`, which is delivered to the app's handler as the authoritative tenant identifier: [4](#0-3) [5](#0-4) 

The gem's own documentation confirms `shop` is meant to be trusted by the app to attribute the webhook to a specific tenant (`shop_domain: data.shop`): [6](#0-5) 

**Equality that should hold but doesn't:** `shop_used_for_tenant_attribution == shop_cryptographically_bound_by_HMAC`. In this gem, the left side comes from an unauthenticated header while the right side does not exist at all — the HMAC binds only the body bytes, never the shop identity.

### Impact Explanation
`api_secret_key` is a single per-app secret shared across every merchant that installs the app; it is not shop-specific. Any merchant with a legitimate install receives real, correctly-signed webhook deliveries for their own store from Shopify. Because the signature covers only the body, that same (body, hmac) pair remains valid no matter which `shop-domain` header accompanies it when it is sent to the app's public webhook endpoint. An attacker can therefore replay a legitimate signed payload from their own shop while substituting a victim shop's domain in the header, causing the app to process attacker-controlled webhook content attributed to another tenant (`data.shop`), i.e. cross-tenant data injection/corruption through the app's webhook processing pipeline. This does not require the app's `client_secret`, an access token, or any privileged credential — only a normal, unprivileged merchant install of the app plus the ability to send an HTTP request to the app's public webhook URL.

### Likelihood Explanation
Medium. It requires the attacker to install the target app on their own store (a normal, unprivileged action any merchant can take) and to know/guess the app's public webhook endpoint (documented convention, and often discoverable). No secret leakage, TLS interception, or social engineering is needed — only header manipulation on an HTTP POST, which is trivial for anyone with a legitimate account.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified against the HMAC rather than trusting it purely from an unauthenticated header, or at minimum require the consuming application to cross-check `request.shop` against a shop the app has an active session/install for before acting on webhook data. Document this requirement prominently, since `Registry.process` currently gives the impression that HMAC validation alone authenticates the `shop` field of `WebhookMetadata`.

### Proof of Concept
1. App `A` shares one `api_secret_key` across all installs.
2. Attacker installs `A` on `attacker-shop.myshopify.com` and receives a real Shopify webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker POSTs to the app's public webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request; `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` and it matches `H`, so validation passes (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), and the app processes attacker-supplied order/webhook data as if it belonged to `victim-shop.myshopify.com`.
