## Title
Bid-selection USD pricing derives from single-block on-chain DEX spot quotes with no manipulation resistance, allowing a solver to win an IntentGatewayV2 auction with a manipulated price - (File: sdk/packages/sdk/src/protocols/intents/BidManager.ts)

### Summary
`BidManager.sortMixedOutputs` ranks competing solver bids for an `IntentGatewayV2` order by calling `computeOutputsUsdValue`, which prices any non-stable output token via live, single-block Uniswap V2/V3/V4 quotes (`quoteTokenToUsdc` → `Swap.findBestProtocolWithAmountIn`, backed by `getAmountsOut`/`quoteExactInputSingle` reads of pool reserves/`sqrtPriceX96`). [1](#0-0) [2](#0-1)  These reads are the same class of price source the LULA report describes (spot AMM reserves), with no TWAP, no reserve-manipulation guard, and no deviation check against a reference price, unlike the analogous Uniswap V4 venue-pricing path in Simplex which explicitly warns about this exact risk and adds an optional `checkPriceGuard`. [3](#0-2) 

### Finding Description
When an order's outputs are a mix of stable and non-stable tokens, `sortBids` delegates to `sortMixedOutputs`, which computes the USD value of both the order's required outputs and every competing bid's outputs by calling `computeOutputsUsdValue` → `quoteTokenToUsdc` → `Swap.findBestProtocolWithAmountIn`/`getV2QuoteWithAmountIn`/`getV3QuoteWithAmountIn`/`getV4QuoteWithAmountIn`. [4](#0-3) [5](#0-4)  These quotes call `getAmountsOut` on Uniswap V2 and `quoteExactInputSingle`/`quoteExactOutputSingle` on V3/V4 quoters, all of which read the pool's *current* reserves/`sqrtPriceX96` — a value manipulable within a single transaction via a flash loan, exactly as in the LULA incident (attacker used a ~$237M flash loan to skew PancakeSwap V2 reserves that a privileged contract function trusted for pricing). [6](#0-5) [7](#0-6) 

The bids are ranked purely by this derived USD value: `validBids.sort((a, b) => b.usdValue.comparedTo(a.usdValue))`, and the winner is executed via `selectAndExecuteBest`/`Bid.execute()`, which signs and submits the on-chain `select` + `fillOrder` call against the `IntentGatewayV2` escrow. [8](#0-7)  There is no on-chain enforcement re-checking the DEX-quoted USD value at execution time — the pricing is purely an off-chain client-side ranking heuristic feeding directly into which solver receives the escrowed input funds.

This mirrors the acknowledged risk documented for Simplex's own Uniswap V4 venue pricing: "Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote," which is why that path was given an optional `referencePrice`/`maxDeviationBps` guard. [9](#0-8)  `BidManager.computeOutputsUsdValue`, by contrast, has no equivalent guard at all — no reference price, no deviation bound, and no TWAP fallback.

### Impact Explanation
A malicious/colluding solver can submit a low-value bid (fewer tokens, or tokens the attacker controls) and, immediately before the client's `sortBids` call, use a flash loan to temporarily inflate the spot price of that bid's output token on the relevant Uniswap pool. `computeOutputsUsdValue` will price this bid as higher-value than a genuinely superior competing bid, causing the client (a user's or integrator's IntentGatewayV2 executor) to select and execute the manipulated bid, unlocking the user's escrowed input for less real value than a fair market rate would provide — a direct value-extraction/theft vector against the intent-order flow, structurally identical to LULA's flash-loan-driven reserve manipulation used to trick a privileged pricing/recycling function.

### Likelihood Explanation
The attack requires no privileged access: any solver competing for `IntentGatewayV2` bids can construct a manipulated-output-token pool and a flash loan atomically with (or immediately before) their bid being evaluated by `sortBids`. The client-side nature of `BidManager` means this affects every consumer relying on the SDK's default bid-sorting logic for mixed-output orders rather than doing independent, manipulation-resistant valuation. The mitigating factor is that this path is only used for "mixed output tokens (at least one non-stable)" orders (`sortMixedOutputs`) — single-output and all-stable orders use different, less-manipulable comparators (`sortSingleOutput`, `sortAllStables`). [10](#0-9) 

### Recommendation
- Do not use single-block spot AMM quotes (`getAmountsOut`, `quoteExactInputSingle`/`quoteExactOutputSingle`) as the sole basis for ranking bids that gate release of escrowed funds.
- Add a TWAP-based price source or cross-check against the indexer's depth-weighted aggregate pool rates (already used elsewhere in the SDK, e.g. `IntentGateway.quoteIntent`'s `indexed_rates` strategy) as a sanity bound. [11](#0-10) 
- Introduce a `referencePrice`/`maxDeviationBps`-style guard (mirroring the Simplex Uniswap V4 venue-pricing guard) in `computeOutputsUsdValue`, rejecting or down-ranking bids whose DEX-quoted value deviates implausibly from a trusted reference.
- Consider re-verifying the selected bid's value on-chain (or via a second, delayed off-chain read) immediately before `Bid.execute()` submits the `select`/`fillOrder` transaction, to reduce the window for atomic flash-loan manipulation.

### Proof of Concept
1. Attacker deploys/targets a thin Uniswap V2/V3/V4 pool for `tokenX`, a non-stable output token they control, and submits a bid to an `IntentGatewayV2` order offering `tokenX` in place of a higher-value expected output.
2. In the same block the user's SDK client calls `gateway.sortBids(order, bids)` → `sortMixedOutputs` → `computeOutputsUsdValue(bid.outputs, chainId)`, the attacker takes a flash loan and swaps against `tokenX`'s pool to inflate `getAmountsOut`/`quoteExactInputSingle` results. [12](#0-11) [6](#0-5) 
3. `quoteTokenToUsdc` returns an inflated USDC-equivalent value for the attacker's bid, `validBids.sort(...)` ranks it first, and the client calls `selectAndExecuteBest`, which signs `SelectSolver` and submits the `select`+`fillOrder` UserOperation against the manipulated bid. [13](#0-12) [14](#0-13) 
4. The attacker repays the flash loan and unwinds the pool manipulation after the escrow is released, having supplied less real value than the true best bid would have.

Note: I could not directly execute or fully trace `Swap.findBestProtocolWithAmountIn` (truncated in the file read) to confirm every fallback path, so the exact selection order across V2/V3/V4 quoters in `quoteTokenToUsdc` is inferred from the surrounding code and comments rather than fully verified line-by-line.

```typescript
	async getV3QuoteWithAmountIn(
		client: PublicClient,
		tokenIn: HexString,
		tokenOut: HexString,
		amountIn: bigint,
		evmChainID: string,

		let bestAmountOut = BigInt(0)

		const v3Quoter = this.chainConfigService.getUniswapV3QuoterAddress(evmChainID)
```

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
