### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `ShopifyAPI::Webhooks::Registry.process` validates authenticates *only the body bytes*, never the `shop-domain`, `topic`, or `webhook-id` headers that the gem subsequently trusts and hands to the app's webhook handler. Any party who can obtain one genuinely-signed `(raw_body, hmac)` pair for the shared `api_secret_key` (e.g., by triggering a webhook on their own, freely-installable development store) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the app to process attacker-controlled data as if it originated from a different, victim shop.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable content as the raw HTTP body only: [1](#0-0) [2](#0-1) 

The `shop`, `topic`, and `webhook_id` values are all read directly from unauthenticated HTTP headers: [3](#0-2) 

`Registry.process` verifies the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `request.to_signable_string` (the body only) and compares it against `request.hmac`: [4](#0-3) 

After the HMAC check passes, `Registry.process` dispatches on the unauthenticated `request.topic` header and forwards the unauthenticated `request.shop` header straight into the data given to the app's handler: [5](#0-4) 

The binding that should hold is: `HMAC(raw_body, api_secret_key) == request.hmac` **and** `shop header == shop that the body actually belongs to`. Only the first half is enforced. Since the `shop-domain` header sits entirely outside the signed content, an attacker who possesses one authentic `(raw_body, hmac)` pair — trivially obtainable by installing the app on their own store and triggering any webhook whose body they can influence (e.g., `orders/create`, `products/update`) — can resend that identical body/HMAC combination to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a different, victim shop. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the victim's domain while the `body` is attacker-controlled.

### Impact Explanation
This breaks the shop-identity binding a webhook consumer is entitled to rely on: the library asserts the webhook is authentic (`Errors::InvalidWebhookError` is only raised when the body's HMAC fails), but the shop attribution used by host applications (session/tenant lookup, database writes, GDPR/compliance webhook triggers, uninstall handling, etc.) is not authenticated at all. This enables cross-tenant data injection/confusion — an attacker can make the app record or act on attacker-chosen data under a victim merchant's identity, satisfying the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Exploitability requires only: (1) the app's webhook endpoint be internet-reachable (a documented requirement for the feature to function at all), and (2) the attacker be able to obtain one authentic `(body, hmac)` pair, which any user can do by installing the target app on their own (free) development store and triggering a webhook with a body they can shape. No access token, `api_secret_key`, or privileged account is required — only ordinary use of the app as any external merchant. The main constraint is that the attacker cannot fully control the body's schema (it must be a shape the target handler will accept), which lowers likelihood somewhat but does not eliminate the class of attack, especially for webhook topics with attacker-influenceable bodies (e.g., order or product topics where the attacker is the shop owner creating the record).

### Recommendation
Bind the shop (and ideally topic) into the authenticated content, e.g., by having `Registry.process` re-derive/validate the shop identity from data already proven authentic (such as looking up the registered webhook by an authenticated shop-specific secret, or requiring the consuming application to cross-check `shop` against the body's own `myshopify_domain`/`admin_graphql_api_id` fields where present) rather than trusting the `shop-domain` header verbatim. At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be used as the sole tenant-identification key without an independent authenticated check.

### Proof of Concept
1. Attacker creates a free Shopify development store and installs the target app, becoming shop `attacker.myshopify.com`.
2. Attacker triggers a webhook with attacker-chosen content, e.g. `products/update`, capturing the raw request body `B` and its valid `X-Shopify-Hmac-Sha256: H` header (computed by Shopify using the app's real `api_secret_key`).
3. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid)
   - Header `X-Shopify-Shop-Domain: victim.myshopify.com` (forged)
   - Header `X-Shopify-Topic: products/update` (unchanged or forged, also unauthenticated)
4. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)` over `B` only — it succeeds.
5. The handler is invoked with `WebhookMetadata.new(topic: "products/update", shop: "victim.myshopify.com", body: <attacker's parsed body>, ...)`, i.e., attacker data is processed under the victim shop's identity. [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
