## Finding [1](#0-0) 

`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, but `to_signable_string` returns **only the raw body** — the `shop`, `topic`, `webhook_id`, and `api_version` values (all read directly from HTTP headers) are never mixed into the signed payload: [2](#0-1) 

`Registry.process` validates only that the HMAC matches, then immediately trusts `request.shop`/`request.topic` (unauthenticated header values) to route and label the payload passed to the merchant's handler: [3](#0-2) 

### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC signature to the raw body only, while `ShopifyAPI::Webhooks::Registry.process` uses the unsigned `shop-domain` header to identify which tenant a webhook belongs to when invoking the app's handler. The bytes verified (body) are not the bytes used for tenant identification (headers), breaking the equality `authenticated_shop == processed_shop`.

### Finding Description
`HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field with `OpenSSL.secure_compare` [4](#0-3) . For webhooks, `to_signable_string` returns `@raw_body` exclusively [5](#0-4) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors read straight from HTTP headers with no cryptographic binding to the signature [6](#0-5) .

`Registry.process` raises only if the HMAC check fails, then constructs the `WebhookMetadata` passed to the app's handler directly from `request.shop`/`request.topic`, i.e., from the unauthenticated headers [3](#0-2) .

Critically, the HMAC secret used to sign webhooks is the app-level `api_secret_key`/`old_api_secret_key`, shared across **every shop** that installs the app — it is not shop-specific [7](#0-6) . This means any merchant who legitimately installs the app can obtain a validly-signed webhook body for their own store (correct HMAC over their own body), then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. Because `to_signable_string` never includes the shop header, `HmacValidator.validate` still succeeds, and `Registry.process` will hand the (attacker-controlled) body to the app's handler labeled as if it came from the victim shop.

### Impact Explanation
This crosses the tenant boundary the HMAC is meant to protect: it allows a low-privileged actor (a merchant with their own legitimate install) to inject content that is processed by the host application as belonging to a **different shop**. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., to select the DB row/session/tenant to update), this can lead to cross-tenant data corruption or disclosure — matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate (even free) installer of the target app — no access to another merchant's access token, session, or the app's `client_secret` is needed, and no host-application misconfiguration is required; the gap exists purely in `Webhooks::Request`/`Registry` as shipped by this library.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) in the signable payload, or otherwise cryptographically bind the header identity to the HMAC before it is trusted for routing/handler dispatch, e.g., have `to_signable_string` combine `@raw_body` with the shop header, or require the host app to independently verify that `request.shop` matches an expected/registered shop before invoking handler logic.

### Proof of Concept
1. Attacker installs the target Shopify app for `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`); Shopify signs it with the app's shared secret over the JSON body, sending headers `X-Shopify-Hmac-Sha256: H` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` and body `B`.
2. Attacker captures `(B, H)` and replays a POST to the same webhook endpoint with the same body `B` and hmac `H`, but with header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` recomputes HMAC over `B` only [5](#0-4)  and it matches `H`, so validation passes.
4. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` [8](#0-7) , causing the attacker-controlled body to be processed under the victim tenant's identity.
