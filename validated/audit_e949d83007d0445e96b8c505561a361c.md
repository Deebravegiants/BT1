### Title
`TokenExchange.exchange_token` accepts non-admin session tokens (e.g. checkout/POS extension tokens) as if they were admin session tokens - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the OAuth token-exchange request using the `dest` claim of any JWT that decodes successfully via `JwtPayload`, without checking that the token is actually an *admin* session token (`iss` ending in `/admin`). `JwtPayload` already distinguishes admin tokens from other Shopify-issued session tokens (e.g. Checkout UI extension tokens) internally, but that distinction is never enforced before the token is used to request a real merchant access token.

### Finding Description
`JwtPayload#initialize` only validates the `aud` claim against `Context.api_key` and decodes/verifies the signature; it does not check `iss`: [1](#0-0) 

The class privately exposes `admin_session_token?` (checks `iss.end_with?("/admin")`), but this predicate is only used to gate `shopify_user_id`, never to gate the `shop`/`dest` usage itself: [2](#0-1) [3](#0-2) 

Tests confirm the gem happily decodes and accepts session tokens whose `iss` is `.../checkouts` (i.e., Checkout UI extension tokens), producing a valid `JwtPayload` with a usable `shop`/`dest`: [4](#0-3) [5](#0-4) 

`TokenExchange.exchange_token` takes this same `JwtPayload` and uses its `dest` claim (`jwt_payload.shop`) directly as the shop for which it requests an offline or online **Admin API** access token, sending the app's `client_secret` to that shop's `/admin/oauth/access_token` endpoint: [6](#0-5) 

There is no check anywhere in this method that the `session_token` came from an admin surface rather than a non-admin surface (Checkout UI extension, POS UI extension, customer account extension, etc.) that Shopify also issues signed session tokens for under the same `aud` (app API key). The binding that should hold is:

`token used to request a merchant Admin API access token == token issued for the Admin surface (iss ends with "/admin")`

but the gem instead enforces only:

`token's aud == app's api_key`

This is the "JWT claim trusted without being bound" class: the `iss`/token-type claim is decoded and available (`admin_session_token?`) but never bound to the privileged operation (`exchange_token`) that consumes the `dest` claim.

### Impact Explanation
Any Shopify-issued session token for the app - including one obtainable by an ordinary, unauthenticated storefront customer via a Checkout UI extension (`shopify.idToken()`/App Bridge in checkout, which requires no merchant privilege) - can be forwarded to `TokenExchange.exchange_token` by a host app built on this gem's documented API, and the gem will exchange it for a genuine offline/online Admin API access token for that shop. This crosses a privilege boundary (unauthenticated customer-facing checkout context → merchant Admin API credential) and matches the High/Critical impact bar of "scope check bypass" leading toward theft of a merchant access token, since the access token returned from Shopify is real and usable for Admin API calls once the exchange completes.

### Likelihood Explanation
Any app that uses both this gem's `TokenExchange` for admin embedded auth and also has a Checkout UI extension, POS UI extension, or other non-admin extension surface using the same client ID is exposed if the app's server-side endpoint that calls `exchange_token` does not itself independently verify the token's `iss`. Because the gem's own `JwtPayload`/`TokenExchange` provide no such enforcement, this is a latent gap in the library's stated security boundary (the gem exposes `admin_session_token?` precisely to distinguish these token types, but doesn't apply it here), making it a defect in the gem itself rather than solely host-app misuse.

### Recommendation
In `TokenExchange.exchange_token`, validate that `jwt_payload` is an admin session token (i.e., use the existing `admin_session_token?`-style check, exposed publicly) before using its `dest` claim to request an access token; raise `InvalidJwtTokenError` otherwise. This binds the claim used for the privileged operation to the token's intended issuer/audience type.

### Proof of Concept
1. App is embedded and also ships a Checkout UI extension under the same Shopify app (same `client_id`/`aud`).
2. A customer visits checkout; the Checkout UI extension obtains a valid, Shopify-signed session token via App Bridge (`iss: "https://{shop}/checkouts"`, `aud: <app api_key>`, `dest: "https://{shop}"`) - this requires no merchant credentials, just visiting the store.
3. If this token is submitted to the app's backend endpoint that calls:
   ```ruby
   ShopifyAPI::Auth::TokenExchange.exchange_token(
     session_token: token,
     requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN
   )
   ```
   the gem decodes it successfully (`JwtPayload.new` only checks `aud`), extracts `dest_shop`, and performs the token-exchange POST with the app's `client_secret` to `https://{shop}/admin/oauth/access_token`, per [6](#0-5) .
4. On success, Shopify returns a genuine Admin API access token for the shop, which the caller now possesses despite never having gone through an admin-authenticated flow.

        payload_hash = begin
          decode_token(token, Context.api_secret_key)
        rescue ShopifyAPI::Errors::InvalidJwtTokenError

          decode_token(token, T.must(Context.old_api_secret_key))
        end

        @dest = T.let(payload_hash["dest"], String)
