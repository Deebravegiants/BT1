## Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator.validate` binds nothing but the JSON payload. The `shop` (and `topic`/`webhook_id`/`api_version`) values that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler are taken straight from unauthenticated HTTP headers, so any request whose body reproduces a previously-issued valid signature will be accepted regardless of which shop header is attached to it.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

`shop` is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic tie to the body: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` relies solely on this HMAC check before dispatching to the handler with the shop taken from the header: [4](#0-3) 

The gem's own documentation instructs host apps to use `data.shop` directly as the tenant key (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), and describes `Registry.process` as verifying "the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

The identity binding broken is: `shop attributed to the webhook (unauthenticated header) ≠ shop bound by the HMAC (none — only the body is signed)`. Because the same app `client_secret` is shared across every shop that installs the app, any merchant who installs the app (an unprivileged internet user with respect to other tenants) can legitimately trigger webhooks whose body/HMAC pair is valid for the app's secret. That merchant can then replay the exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header of a different, victim shop that also has the app installed. `HmacValidator.validate` still passes because it never inspects the shop header, and `Registry.process` forwards the attacker-controlled body to the handler tagged with the victim shop's identity.

### Impact Explanation
This breaks the tenant boundary the host application relies on `shopify_api` to enforce: an attacker who is an unprivileged merchant of the app (not privileged with respect to any other tenant) can cause webhook events to be attributed to a different shop, i.e., cross-tenant access/injection of attacker-influenced data into another tenant's processing pipeline (e.g., `orders/create`, `products/update` payloads the attacker partially controls on their own store, replayed under a victim `shop_domain`). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic: no secrets, tokens, or privileged access are required — only (a) installing the public app once as any shop to obtain a legitimately signed body+HMAC pair, and (b) sending an HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header. Both are available to any unprivileged internet user who can install the target app.

### Recommendation
Bind the shop (and ideally topic/webhook_id/api_version) into the signed material verified by `HmacValidator`, or have `Registry.process` independently authenticate/authorize the `shop` header against the session/shop that was expected to receive the webhook before dispatching to the handler, rather than trusting it purely from the unauthenticated header.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, obtaining valid `x-shopify-hmac-sha256` signatures for webhooks Shopify sends for that store (e.g., `orders/create` with attacker-controlled order note/fields).
2. Attacker captures such a webhook request: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (a real shop that also has the app installed).
4. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "victim.myshopify.com"`, `to_signable_string = B`.
5. `HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)`, which equals `H`, so validation succeeds.
6. `Registry.process` dispatches to the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-influenced data under the victim shop's identity.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
