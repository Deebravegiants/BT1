The GraphQL `/query` endpoint accepts mutations like `createAPIToken(input: {password: "..."})` and `deleteAPIToken(input: {password: "..."})`, where the request body is a JSON envelope of the form `{"query": "...", "variables": {"input": {"password": "..."}}}` [1](#0-0) , and this endpoint is registered under the same global logging middleware as every other route [2](#0-1) .

### Title
Sensitive fields (e.g. GraphQL `password` inputs) nested under top-level JSON keys bypass log redaction, causing cleartext credential disclosure in debug logs - (File: core/web/router.go)

### Summary
Chainlink's HTTP request-logging middleware (`loggerFunc`) sanitizes request bodies before logging them at `Debug` level by parsing the body as JSON and redacting any top-level key whose name contains `"password"` [3](#0-2) [4](#0-3) . This mirrors the reported bug class (CVE-2023-31417): a URI/entry point exists that carries sensitive data through a request shape the redaction logic does not fully anticipate, so credentials end up in cleartext logs.

### Finding Description
`readSanitizedJSON` unmarshals the raw request body into a flat `map[string]any` and only inspects the **first level** of keys against the `blacklist`/`isBlacklisted` check [3](#0-2) . Any value that is itself an object or array is copied into the "cleaned" map unmodified — nested keys are never walked or checked. This same `loggerFunc` middleware is applied globally via `engine.Use(...)` in `NewRouter`, i.e., to every route registered on the engine, including the GraphQL endpoint at `POST /query` [5](#0-4) [2](#0-1) .

The GraphQL schema exposes mutations that take a `password` field nested inside an `input` object, e.g. `CreateAPITokenInput.password` and `DeleteAPITokenInput.password` [1](#0-0) . A GraphQL POST body for these mutations has the shape `{"query": "...", "variables": {"input": {"password": "<secret>"}}}`. Because `password` is nested under the top-level `variables` key (not itself a top-level key), `readSanitizedJSON`'s single-level `isBlacklisted` check never sees it, and the plaintext password is written verbatim into the application's Debug-level access log via `readBody` inside `loggerFunc` [6](#0-5) .

By contrast, the equivalent REST endpoint `/v2/user/password` uses a flat JSON body (`{"oldPassword":..., "newPassword":...}`) where the sensitive keys are top-level, so they are correctly redacted by the same substring check [7](#0-6) . The redaction logic was clearly designed with only flat REST payloads in mind and never updated for the nested GraphQL request envelope, exactly analogous to how Elasticsearch's audit-log filtering covered its modern APIs but not the older, differently-shaped deprecated URIs.

### Impact Explanation
When the node operator enables Debug-level logging (a supported, documented log level, not a niche developer-only mode), any unprivileged client that calls the `createAPIToken` or `deleteAPIToken` GraphQL mutations — which require only an authenticated session, not admin privileges beyond a normal API user — will have their session password written in cleartext into the node's log files. Since these logs are often shipped to centralized log aggregators, backed up, or accessible to a broader set of operators/support staff than the credential store itself, this is a genuine confidentiality violation of user passwords (CWE-532), matching the impact class of the reported advisory.

### Likelihood Explanation
Likelihood is limited by two factors: (1) Debug-level logging must be enabled (not the default in production, similar to audit logging being disabled by default in the Elasticsearch advisory), and (2) the caller must already possess valid, authenticated session credentials to invoke the `createAPIToken`/`deleteAPIToken` mutations (the GraphQL endpoint is gated behind `auth.AuthenticateGQL` [2](#0-1) ). However, exposure is systemic — every invocation of these mutations while Debug logging is on leaks the password, with no opt-out from the caller side, and requires no special crafting beyond using the documented GraphQL API.

### Recommendation
Make `readSanitizedJSON` (and the corresponding `blacklist`/`isBlacklisted` logic) recursively walk nested JSON objects and arrays rather than checking only the top level, so nested fields such as GraphQL `variables.input.password` are redacted the same way flat REST fields are. Alternatively (or additionally), exclude the `/query` GraphQL endpoint's request body from full-body debug logging, or apply GraphQL-aware redaction that strips known sensitive input types (`CreateAPITokenInput`, `DeleteAPITokenInput`, etc.) before logging.

### Proof of Concept
1. Start a Chainlink node with logging level set to `debug`.
2. Authenticate as any node user (any role able to call these mutations) to obtain a session cookie.
3. Send:
   ```
   POST /query
   Content-Type: application/json
   Cookie: clsession=<valid session>

   {"query":"mutation($input: CreateAPITokenInput!){ createAPIToken(input: $input){ ... on CreateAPITokenSuccess { token { accessKey secret } } } }",
    "variables":{"input":{"password":"MyS3cretPassw0rd!"}}}
   ```
4. Inspect the node's log output produced by `loggerFunc`'s `"body"` field for this request — it will contain `"variables":{"input":{"password":"MyS3cretPassw0rd!"}}` in cleartext, unlike an equivalent request to `/v2/user/password` where `oldPassword`/`newPassword` would be shown as `*REDACTED*`.

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}
