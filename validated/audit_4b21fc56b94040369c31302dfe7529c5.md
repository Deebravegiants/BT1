### Title
Webhook shop identity spoofing via HMAC that only signs body, not `x-shopify-shop-domain` — cross-tenant webhook injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate(request)` proves the body was signed with the app's `client_secret`, but never binds that signature to the `shop` value taken from the `X-Shopify-Shop-Domain` header. `Registry.process` then hands `request.shop` straight to the app's handler as the tenant identifier, so the field used to route/attribute webhook data (`shop`) is never covered by the HMAC that gates the request.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes: [1](#0-0) 
and defines the HMAC-signable content as: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string` (the raw body) against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` gates on this HMAC and then forwards `request.shop` — read from the unauthenticated `X-Shopify-Shop-Domain`/`shopify-shop-domain` header — to the app's handler as the tenant key: [4](#0-3) 

The equality that should hold is: `shop bound by HMAC == shop used to key tenant data`. Here, the HMAC binds nothing about `shop`; it only proves "this body was produced with our client_secret." Since the same `client_secret` is shared across all shops (any shop's webhook body is signed with the same secret), an attacker who can obtain one valid `(body, hmac)` pair for any shop (including their own store, or a topic whose body content is empty/predictable, e.g. `{}` for certain topics) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary victim `shop` value in the header. `HmacValidator.validate` still returns true because it never inspects the header, and the handler receives `WebhookMetadata` attributing that (possibly attacker-influenced) body to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing: an unprivileged holder of one valid signed webhook body can cause an app to process/attribute webhook data under an arbitrary shop's identity. Depending on how the host app keys logic off `data.shop` (e.g., app/uninstalled processing, GDPR shop/redact, subscription/billing state changes, or session invalidation), this enables cross-tenant interference — a High-severity outcome per the rubric ("cross-tenant access").

### Likelihood Explanation
Exploitability requires the attacker to first obtain one legitimately-signed `(raw_body, hmac)` pair — trivially available to any developer/merchant who installs the same app on their own store and receives their own webhooks, since Shopify uses the app's single shared `client_secret` for all shops' webhook HMACs. No access token, session, or `api_secret_key` leakage is required beyond what a normal store owner already legitimately observes from their own webhook deliveries. This is a realistic, unprivileged-internet-facing scenario for any multi-tenant app built on this gem.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value verified against the HMAC, or independently authenticate the shop before trusting it as the tenant key — e.g., verify the `shop` header against a known/installed-shop list (existing session storage) before invoking the handler, rather than trusting the header value solely because the body's HMAC validated. At minimum, document prominently that `data.shop` from `Registry.process` is not itself HMAC-authenticated and must be cross-checked by the host app against known installed shops before being used to key any tenant-sensitive action.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com` and receives a real webhook, e.g. `shop/redact` (or any topic whose body content is attacker-controllable/predictable), obtaining a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's shared `client_secret`.
2. Attacker sends a forged HTTP request to the target app's webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC (`lib/shopify_api/utils/hmac_validator.rb#L27-31`, `lib/shopify_api/webhooks/request.rb#L35-38`).
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb#L198-199`), causing the app to act on victim-shop data/state despite the request never being authenticated for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
