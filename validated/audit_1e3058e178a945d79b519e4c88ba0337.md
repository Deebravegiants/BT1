### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by `Registry.process` to identify the tenant and dispatch the handler are read directly from unauthenticated HTTP headers. This breaks the intended identity binding `HMAC(payload) == HMAC(what is trusted)`, allowing an attacker who possesses one valid `(body, hmac)` pair signed by the app's shared `api_secret_key` to replay it with a forged `shop-domain` header and have it accepted as originating from a different shop.

### Finding Description
The webhook HMAC is only computed over the raw body: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, which are never included in the signed content: [2](#0-1) 

`HmacValidator.validate` only checks `to_signable_string` (i.e. the body) against the received HMAC using the app's `api_secret_key`, which is shared by the app across every installed shop: [3](#0-2) 

`Registry.process` validates only that HMAC and then unconditionally trusts `request.topic` and `request.shop` to dispatch to the handler, constructing `WebhookMetadata` from these unauthenticated values: [4](#0-3) 

The equality that should hold is: `shop authenticated by HMAC == shop the handler acts on`. In reality the HMAC only authenticates `raw_body` genuineness (i.e., "this body was produced by someone possessing the app's secret"), not the shop-domain binding, so the equality is broken: `HMAC covers {raw_body}` while the handler acts on `{shop, topic, webhook_id, api_version} ∪ {raw_body}`.

Because `api_secret_key` is one shared secret for the whole app (not per-shop), any merchant who installs the app on their own store legitimately receives real Shopify webhooks whose bodies are signed with that same shared secret. Such a merchant can capture one legitimate `(topic, raw_body, hmac)` triple delivered to their own shop, then resend that exact triple to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and, for pub/sub or event-bridge deliveries, whatever channel carries the shop identity to the app) with a victim shop's domain. `HmacValidator.validate` will still pass because it revalidates only the untouched body, and `Registry.process` will hand the forged victim shop identity straight to the app's registered handler.

### Impact Explanation
This crosses the "cross-tenant access" boundary called out as Critical/High impact: an unprivileged party (any merchant with the app installed) can make the host application process attacker-controlled webhook data under a different tenant's (`shop`) identity, without ever needing the app's `client_secret`, an access token, or any privileged credential of the victim. Any host application logic that uses `WebhookMetadata#shop` to select which tenant's data/session to update is exposed to cross-tenant data corruption or disclosure.

### Likelihood Explanation
Likelihood is realistic for any multi-tenant app built on this gem, because: (1) obtaining a valid `(body, hmac)` pair only requires installing the app on any shop, which is normal, unprivileged app usage; (2) replaying an HTTP request with one modified header is trivial; (3) the gem's own `Registry.process` does the trusting of `request.shop` on the library's behalf, so the flaw is intrinsic to this gem's API rather than dependent on the host app ignoring documentation.

### Recommendation
Include the shop-identifying header(s) (and ideally `topic`/`webhook_id`) in the HMAC-signable content, or otherwise cryptographically bind the shop domain to the signed body (e.g., verify the request's `shop-domain` against a shop already known to be authorized/subscribed for that specific `webhook_id`/subscription before dispatch). At minimum, document that `request.shop` is unauthenticated and must be independently corroborated (e.g., against stored webhook subscription records) before being trusted for tenant selection.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; Shopify sends a legitimate webhook: 
   `headers = { "x-shopify-topic" => "orders/create", "x-shopify-hmac-sha256" => "<valid-hmac-of-body>", "x-shopify-shop-domain" => "attacker.myshopify.com" }`, with some `raw_body`.
2. Attacker captures `raw_body` and the valid `x-shopify-hmac-sha256` value.
3. Attacker resends the same `raw_body` and same `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `to_signable_string` is unchanged (`raw_body`), so:
   `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `ShopifyAPI::Webhooks::Registry.process(request)` passes HMAC validation and calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: request.parsed_body, ...))` (per `lib/shopify_api/webhooks/registry.rb:189-199`), causing the app to process attacker-supplied order data as if it belonged to `victim.myshopify.com`.

          received_signature = verifiable_query.hmac
