Found `LPLock.recordLock` requires `amount != 0` — this is the reachable-revert path worth flagging: `finalizeGraduation` calls `LPLock.recordLock(tokenAddress, lpPair, liquidity)` unconditionally, and `liquidity` is the return value of `_seedUniswapV2Direct`, which under the extreme-hostile-pre-seed rebalance branch can legitimately be computed as `0` even though the codebase's own `_swapBudget` (1%-reserve) comment explicitly describes this as a known failure mode it tries to prevent — but only for the swap-consumes-100%-of-one-side case, not for every zero-liquidity path.

### Title
`finalizeGraduation` permanently bricks a token in `Lifecycle.Graduating` when `_seedUniswapV2Direct` returns `liquidity == 0` - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` calls `LPLock.recordLock(tokenAddress, lpPair, liquidity)` unconditionally with whatever `liquidity` `_seedUniswapV2Direct` returns [1](#0-0) . `LPLock.recordLock` explicitly reverts with `ZeroAmount` when `amount == 0` [2](#0-1) . The protocol's own natspec acknowledges that an attacker who drives the hostile-mint-pre-seed rebalance swap to consume 100% of one side leaves `_routerDepositAndDispose`'s `addLiquidity` skipped (`remToken == 0` or `remLT == 0`), which makes `finalizeGraduation` return `liquidity = 0` and would make `LPLock.recordLock(...)` "record a zero-sized lock" [3](#0-2) . The `_swapBudget` 1%-reservation mitigates the *specific* "swap consumes exactly 100% of the swap-side budget" scenario, but does not guarantee `remToken > 0 && remLT > 0` after the swap in `_routerDepositAndDispose`, nor does it cover the "pool already at target ratio" no-swap branch or any rounding edge where the post-swap balanced deposit legitimately computes to a near-zero/zero `liquidity` from the router's `quote()`-based optimal split.

### Finding Description
Because `finalizeGraduation` is permissionless and one-shot — it flips `Lifecycle.Graduating → Graduated`, deletes `pendingGraduation`, and calls `LPLock.recordLock` at the very end, with no lifecycle rollback on revert — any revert inside this final call leaves the token lifecycle-locked in `Graduating` [4](#0-3) . In `Lifecycle.Graduating`, `Bonding.buy`/`sell` are frozen (curve trading reverts with `TokenIsGraduating`), and `LPLock.recordLock`'s one-shot `lockedAt` sentinel means the *same* `finalizeGraduation` call can never be re-attempted to fix the zero-liquidity outcome — every retry recomputes the exact same cached `(tokensForLP, ltFromPair)` from `pendingGraduation` and the exact same pre-seed-driven `liquidity == 0` result, since `_prepareGraduationLiquidity`'s cached values are frozen at phase 1 and never recomputed. The `AGENTS.md` author is aware this is theoretically possible ("the attacker's pre-existing LP becomes 100% of the pool") but frames the `_swapBudget` fix as sufficient; it does not enforce a floor on `liquidity` itself before calling `recordLock`, and it does not cover the branch where `reserveToken * ltFromPair == reserveLT * tokensForLP` (skip-swap, deposit-directly) landing on a degenerate router quote.

### Impact Explanation
If `liquidity` resolves to `0` (via an attacker engineering the hostile-mint pre-seed to exhaust the rebalance budget on one side, or to sit near the router's `quote()` rounding boundary), `LPLock.recordLock` reverts and `finalizeGraduation` reverts atomically — meaning the state changes preceding it (lifecycle flip to `Graduated`, `pendingGraduation` deletion) are rolled back too, so the token is stuck at `Lifecycle.Graduating` forever with no owner or permissionless recovery path. All curve-raised LT and the 250M reserved tokens that were already drained into `Bonding` at phase 1 are permanently frozen: creators and traders can neither trade the curve (frozen by lifecycle) nor exit via the (never-created) HyperSwap pool. This is a permanent freezing of trader/creator funds, satisfying the validation bar.

### Likelihood Explanation
Reaching the zero-liquidity state requires an attacker to front-run `finalizeGraduation` with a `pair.mint` pre-seed sized precisely enough to drive `_pairRebalance`'s swap to consume the entire capped budget on one side (bypassing the `_swapBudget` 99% cap only by chance/precision) or to land the router's `quote()` split at a zero/near-zero amount. This is a narrow, attacker-craftable-but-non-trivial condition — cheaper than the original "$1 dust" attack but requiring accurate on-chain simulation of `_noFeeSwapInput` and the live V2 fee to hit exactly the degenerate boundary. Medium likelihood: attacker-reachable with no privilege, but requires precise sizing rather than a trivial dust transfer.

### Recommendation
Before calling `LPLock.recordLock` in `finalizeGraduation`, explicitly guard against `liquidity == 0`: if zero, fall back to a `_seedDirectMint`-style deposit (or otherwise guarantee a strictly-positive lock) rather than calling into `recordLock` with a value that is guaranteed to revert. Alternatively, make `_seedUniswapV2Direct`'s regime-3 path provably return `liquidity > 0` in all reachable pre-seed shapes (extend the invariant tests in `test/TwoPhaseGraduation.t.sol` to fuzz the swap-consumes-full-budget and skip-swap branches specifically for `liquidity == 0`).

### Proof of Concept
1. Launch a token and drive it to the LT-appreciation or supply-sellout graduation trigger so phase 1 (`_enterGraduating`) fires and caches `(tokensForLP, ltFromPair)` in `pendingGraduation`.
2. Before phase 2, front-run: `factory.createPair(token, lt)`, transfer TOKEN and LT to the pair at a ratio and magnitude engineered so that `_noFeeSwapInput`'s uncapped `s` for the required side exceeds `_swapBudget(balance)` by a razor margin, and the resulting `_routerDepositAndDispose` deposit either has `remToken == 0` or `remLT == 0`, or the router's `quote()`-derived `liquidity` rounds to `0`.
3. Call `bonding.finalizeGraduation(tokenAddress)`. `_seedUniswapV2Direct` returns `liquidity == 0`; `LPLock($.lpLock).recordLock(tokenAddress, lpPair, 0)` reverts with `ZeroAmount`.
4. The whole `finalizeGraduation` transaction reverts; `pendingGraduation[tokenAddress]` is still set, lifecycle is still `Graduating`. Retry with identical inputs (cached values are frozen) reproduces the same revert indefinitely — the token, its drained LT, and its 250M reserved tokens are permanently stuck.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
