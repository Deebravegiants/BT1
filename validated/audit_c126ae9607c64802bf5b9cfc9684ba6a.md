Based on the confirmed code paths, the vulnerability is clear: `Utils::HmacValidator.validate` computes the signature over `to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body` — none of the identity-carrying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included in the signed bytes, yet `Registry.process` passes those unverified header values straight into the app-facing `WebhookMetadata` that host apps use to key sessions/tenant data.

### Title
Webhook `shop`, `topic`, and `webhook_id` fields are unauthenticated header values not covered by the HMAC, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw HTTP body. The HMAC that `Registry.process` validates therefore authenticates the request body bytes only, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` nonetheless forwards those unverified header values, including `shop`, directly into `WebhookMetadata` that is handed to the host application's `WebhookHandler`.

### Finding Description
`Registry.process` gates on `Utils::HmacValidator.validate(request)` before invoking the handler: [1](#0-0) 

`HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is defined to return only the raw body, while `shop`, `topic`, and `webhook_id` are parsed straight from HTTP headers with no cryptographic binding to the HMAC: [3](#0-2) [4](#0-3) 

The equality the gem's own validation implicitly claims to guarantee is:
`HMAC-valid(request) == HMAC-valid(request.raw_body) AND authentic(request.shop, request.topic, request.webhook_id)`

but the real guarantee is only:
`HMAC-valid(request) == HMAC-valid(request.raw_body)`

`request.shop`/`request.topic`/`request.webhook_id` are unauthenticated bytes parsed from headers that anyone controlling the HTTP request can set, independent of whether the body's HMAC is valid.

`Registry.process` treats the unverified `shop` header as trustworthy and forwards it to the handler: [5](#0-4) [6](#0-5) 

An unprivileged internet user who controls any single merchant/shop (which is trivial — anyone can install a free development store and receive real, validly-signed webhooks for it) can capture one of their own shop's legitimately-signed webhook deliveries (valid `hmac-sha256` header computed over the JSON body by Shopify using the app's real `client_secret`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain. Because `to_signable_string` never included the `shop-domain` header, the HMAC check still passes, and the host application — which typically uses `WebhookMetadata#shop` to look up the correct shop's offline `Session`/access token or to key per-tenant records — will process attacker-controlled webhook body content under the identity of a shop the attacker does not control.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: cross-tenant access/data confusion, matching the "Critical - cross-tenant access" impact category. Any host application that keys session lookup, data writes, or business logic off `WebhookMetadata#shop` (as the gem's own webhook docs instruct developers to do) is exposed, because the gem's HMAC validation does not bind the `shop` identity claim to the signed bytes.

### Likelihood Explanation
Likelihood is moderate-to-high: the attacker only needs control of one legitimate shop (freely obtainable as a Shopify development store) that has the target app installed with webhooks enabled, plus the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers — no access to `client_secret`, access tokens, or the victim shop is required.

### Recommendation
Include the identity-carrying headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signed material `to_signable_string` returns for `Webhooks::Request`, or otherwise cryptographically bind them to the HMAC (e.g., by having `HmacValidator`/`Registry.process` verify that the `shop` header matches metadata independently authenticated elsewhere, such as by requiring the app to reconcile it against a known session before trusting it). At minimum, update `docs/usage/webhooks.md` and `WebhookMetadata` consumers to explicitly warn that `shop`/`topic`/`webhook_id` are **not** covered by the HMAC and must not be used as the sole tenant-identity source without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers a real event (e.g., `orders/create`) so Shopify delivers a validly-signed webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this POST request.
3. Attacker resends the identical body `B` and identical `x-shopify-hmac-sha256` header to the app's webhook endpoint, but rewrites `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally the topic).
4. `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (`= B`) only, matches the header, and passes: [7](#0-6) 
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop = "victim-shop.myshopify.com"`, even though the HMAC never authenticated that value: [8](#0-7) 
6. Any host-app logic keyed on `data.shop` (e.g., "look up victim shop's session and update its records with body `B`'s attacker-controlled content") now executes cross-tenant.
