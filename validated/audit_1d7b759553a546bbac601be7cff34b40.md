Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  and the `shop`, `topic`, `api_version`, and `webhook_id` fields are read straight from unauthenticated HTTP headers [2](#0-1) . `HmacValidator.validate` only checks the HMAC against this signable string (the body), never against the `shop` header [3](#0-2) . `Registry.process` then trusts `request.shop` directly as the tenant identity passed to the app's handler [4](#0-3) .

### Title
Webhook `shop-domain` header is not bound by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate` [5](#0-4) . The `shop` value handed to the app's webhook handler, however, is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header and is never included in the signed payload [6](#0-5) [1](#0-0) . The binding that should hold is `shop_bound_by_hmac == shop_trusted_by_handler`, but here the HMAC only binds `body`, so `shop_trusted_by_handler` is fully attacker-controlled independent of the signature.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` is the abstract contract used by `HmacValidator` to compute/verify the signature [7](#0-6) . For `Webhooks::Request`, this method returns only `@raw_body`, deliberately excluding topic, shop, webhook id, and api version [1](#0-0) . Since every shop installation of a given app shares the same `api_secret_key` (`Context.api_secret_key`), a valid `(body, hmac)` pair generated by Shopify for *any* shop running the app is cryptographically valid for *every* shop running that same app — the HMAC never encodes which shop the payload belongs to.

`Registry.process` takes this unauthenticated `shop` value and forwards it verbatim into `WebhookMetadata` for the app's handler to act on [4](#0-3) , so any handler logic that keys off `data.shop` (e.g., looking up that shop's session/access token, updating that shop's settings, billing records, etc.) can be redirected to a different tenant than the one that actually produced the payload.

### Impact Explanation
This breaks the tenant-isolation guarantee the HMAC is meant to provide: a party who can obtain one genuine `(body, hmac)` pair — for example, a malicious merchant who has installed the same app on their own store and captures/replays their own legitimate webhook delivery — can relabel the `shop-domain` header to point at a victim shop and have the app process it as if it originated from that victim tenant. This is a cross-tenant confusion vulnerability (impact category: cross-tenant access) reachable without any credential beyond having installed the app on one's own shop.

### Likelihood Explanation
Medium-to-high: the attacker needs only to control (or observe) one legitimate webhook delivery to their own store — a very low bar for anyone who installs the app — and the ability to POST directly to the app's public webhook endpoint with a modified header, bypassing Shopify's delivery entirely. No secret key, access token, or privileged access is required.

### Recommendation
Include the shop domain (and/or webhook id/topic) inside the HMAC-signed material, or otherwise cryptographically bind `request.shop` to the signature (e.g., verify the shop against the session/webhook record identified by `webhook_id`), instead of trusting the unauthenticated `x-shopify-shop-domain` header.

### Proof of Concept
1. App merchant A installs the app on `shop-a.myshopify.com`. Shopify sends the app a legitimate webhook: body `{"...":"..."}`, header `x-shopify-shop-domain: shop-a.myshopify.com`, header `x-shopify-hmac-sha256: <valid HMAC of body using the app's shared api_secret_key>`.
2. Merchant A captures this request (they control their own store/traffic) and re-sends it directly to the app's webhook endpoint, but changes only the header to `x-shopify-shop-domain: shop-b.myshopify.com` (a victim tenant also using the app), leaving the body and HMAC untouched.
3. `Webhooks::Request.new` parses this as a valid request and `Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC over `@raw_body` only and succeeds, since the body/HMAC pair is unchanged and still matches the shared secret [8](#0-7) .
4. The app's registered handler is invoked with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)`, causing shop A's data/event to be processed under shop B's identity [9](#0-8) .

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
