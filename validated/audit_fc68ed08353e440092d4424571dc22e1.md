### Title
Attacker-supplied route venue executes arbitrary contract code under the caller's signed auth tree, draining tokens beyond the routed amount - (File: contracts/swap-aggregator/src/venues/dispatch via `dispatch_hop` and `contracts/controller/src/strategies/swap.rs`)

### Summary
The swap-aggregator decodes a fully user-supplied `swap_xdr` payload whose hop records name arbitrary `pool` contract addresses. `dispatch_hop` (`contracts/swap-aggregator/src/venues/mod.rs:23-59`) invokes whatever contract the payload names — there is no venue or pool allowlist — so an attacker can put arbitrary third-party code on the call stack inside a controller strategy call (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`) or a direct `execute_strategy` call. Because Soroban records every `require_auth` sub-invocation under the caller's auth entry during simulation, a rogue pool can request `token.transfer(victim, attacker, victim_balance)` for any token the victim holds; if the victim signs the simulated tree, the transfer executes. This is the Soroban analog of CVE-2024-46540: attacker-controlled remote code/artifact loaded into a privileged execution context, yielding theft of the victim's wallet funds.

### Finding Description
- The controller passes the user's `StrategySwap` bytes verbatim to the router: `router.execute_strategy(&controller, &amount_in, swap)` in `contracts/controller/src/strategies/swap.rs:36-38`, reached from `process_swap_collateral` (`contracts/controller/src/strategies/swap_collateral.rs:55-65`) and the other strategy entrypoints.
- The router's hop instructions carry a `pool` address drawn from the caller-controlled `assets` registry (`skills/xoxno-swap-aggregator/payload.md:62-87`), and each venue adapter calls that address (e.g., `ctx.env.invoke_contract(&ctx.hop.pool, ...)` in `venues/comet.rs:30-34`; Aquarius `invoke_pool_swap` similarly). Nothing validates that `hop.pool` is a real DEX pool.
- The balance-delta checks in `dispatch_hop` (`venues/mod.rs:42-56`) only measure the router's own token balances; they do not constrain what the invoked contract does with the caller's authorization context.
- The threat model itself acknowledges the consequence: "a route can put third-party code on the call stack below the caller's authorization… The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (`docs/explanation/threat-model.md:154-165`).
- The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves it end-to-end: a `RogueHopPool` named in the route calls `token.transfer(alice, attacker, WALLET_BALANCE)`; simulation records it as a child of Alice's `swap_collateral` auth entry, and signing that tree moves her entire unrelated wallet token balance to the attacker while the swap settles fairly and the position passes risk checks.

### Impact Explanation
Theft of user funds. Any token in the victim's wallet — including assets the protocol never listed — can be transferred to the attacker, for amounts unbounded by `min_out`, slippage checks, or the controller's final health-factor gate. The rogue pool simply returns a fair swap so every on-chain guard (`RouterOverspend`, `NoSwapOutput`, `SlippageExceeded`, post-swap risk validation) passes while the side transfer executes under the victim's own signature.

### Likelihood Explanation
The attack requires the victim to sign a route built by an attacker-influenced quote (malicious/off-axis quote server, phishing front-end, or any flow where route XDR is supplied to the user). Signing requires the victim to approve an auth tree containing an extra child transfer — wallets that display only the root invocation, or users who don't decode `routeXdr`, will sign it. No privileged role, leaked key, or oracle manipulation is needed; the attacker only deploys a contract and supplies bytes. Impact is critical-scale (whole wallet), likelihood moderate → High/Medium.

### Recommendation
Validate hop venue addresses on-chain: maintain an allowlist (or registry keyed by governance) of recognized pool contracts per venue in the swap-aggregator, and reject routes naming unlisted pools. Alternatively/additionally, have the controller or router reject any authorization tree shape beyond the single input transfer, and harden client-side verification (`verifyRouteBytes`) so wallets refuse routes whose simulated auth tree contains unexpected children.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` (full working PoC):

1. Attacker deploys `RogueHopPool`, a contract whose `swap` function calls `token::Client::transfer(victim, attacker, amount)` on an arbitrary token the victim holds (`rogue_hop_pool_transfer_joins_caller_auth_tree.rs:51-72`).
2. Attacker constructs a route whose hop `pool` field is that contract; a router double (`UnlistedPoolRouter`, lines 34-48 — semantically identical dispatch to the real adapter path of invoking the payload-named pool) is wired in via `set_swap_aggregator`.
3. Victim calls `controller.swap_collateral(caller, account_id, usdc_key, amount_in, eth_key, route)`. Simulation records the rogue `transfer` as a child invocation of the victim's auth entry (lines 194-227).
4. Victim signs the simulated tree; the enforced call executes `transfer(alice → attacker, 77_770_000_000)` on the unrelated wallet token while the swap returns fair ETH output and the account passes `strategy_finalize` risk checks (lines 230-269). Alice's wallet balance: 0; attacker's: full amount.
