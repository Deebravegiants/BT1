### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the shop, topic, webhook id and API version are read from HTTP headers that are excluded from the signed bytes. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC matches, then dispatches the handler using the unverified `shop` and `topic` header values. This breaks the identity binding `bytes verified == bytes acted on`.

### Finding Description
`Request#to_signable_string` returns solely `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from request headers, which are never part of the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, and then dispatches the handler and builds `WebhookMetadata` using the unverified `request.shop` and `request.topic` values: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, which for `Request` is just the raw body: [4](#0-3) 

Because the app's `api_secret_key` used to compute the webhook HMAC is a single, app-wide secret shared across every shop that installs the app (it is the app's client secret, not a per-shop secret), any unprivileged user who installs the app on their own (attacker-controlled) shop can trigger real Shopify webhook deliveries and obtain a genuinely valid `(raw_body, hmac)` pair signed with that shared secret. Because `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are not part of the signed bytes, the attacker can then submit a request directly to the app's webhook endpoint with that same valid `(raw_body, hmac)` pair but arbitrary values for the `shop-domain` and `topic` headers. `Registry.process` will accept the HMAC as valid (it only checks the body) and will invoke the handler for the attacker-chosen topic while attributing the event to an attacker-chosen shop.

This is the same identity-binding class of flaw referenced by the external report (a value used to drive privileged behavior is not the value that was actually verified): the verified bytes (raw body only) do not equal the bytes actually acted upon by the handler (topic + shop + body).

### Impact Explanation
An unprivileged user with a normal, unprivileged Shopify store (any developer/free store can install a public embedded app) can obtain a legitimately HMAC-signed webhook payload from their own store and use it to impersonate any other shop, or repurpose the payload under a different topic than the one Shopify actually generated it for. Downstream app logic that trusts `WebhookMetadata#shop` for tenant-scoping (e.g., writing/deleting data keyed by shop, or triggering mandatory compliance topics like `customers/redact`/`shop/redact`) can be made to act against a victim shop's tenant data using attacker-supplied timing and content, i.e., cross-tenant access/confusion attributable to a boundary this gem is responsible for enforcing (HMAC-based webhook identity verification).

### Likelihood Explanation
The prerequisite (installing the app on one's own shop, if the app is publicly installable) is an ordinary, unprivileged action, and no secret material, TLS interception, or social engineering is required — only the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers and a previously-observed valid `(body, hmac)` pair.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`, `api-version`) in the HMAC-signable content for webhook requests, or otherwise cryptographically bind them to the signed body (e.g., compute the HMAC over `topic + shop + raw_body` and require the caller/consuming app to reconstruct that same canonical string). At minimum, document and enforce that `Registry.process` must not trust `request.shop`/`request.topic` unless they are cryptographically bound to the signature.

### Proof of Concept
1. Install the target public embedded app on an attacker-controlled Shopify development store (`attacker-shop.myshopify.com`).
2. Trigger a real event (e.g., create an order) so Shopify sends a legitimately signed webhook: headers `shopify-topic: orders/create`, `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid HMAC of raw body>`, plus a JSON `raw_body` fully controlled in content by the attacker (order fields, etc.).
3. Capture the `raw_body` and `shopify-hmac-sha256` value (e.g., by pointing a personal proxy/logging endpoint at the same body, or by having a webhook debugging tool relay it).
4. Send a direct HTTP POST to the app's public webhook endpoint with the same `raw_body` and `shopify-hmac-sha256`, but attacker-chosen `shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `shopify-topic` that the app also has a handler for).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unmodified) raw body against the HMAC; the handler then executes with `shop: "victim-shop.myshopify.com"`, attributing attacker-controlled data/events to the victim shop.
