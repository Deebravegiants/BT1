### Title
`_paused` state in `IntentGatewayV2`/`IntentsBase` is not enforced in `fillOrder`, `cancelOrder`, or `onAccept` - (File: evm/src/apps/intentsv2/IntentsBase.sol, evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`IntentsBase` declares a `_paused` storage flag intended to halt the IntentGateway in an emergency, but a search of the intent-gateway contracts shows no `whenNotPaused`/pause check inside the fund-moving entry points (`fillOrder`, `cancelOrder`, `onAccept`, `onGetResponse`). This mirrors the reported Cooler `Clearinghouse` bug: an emergency-stop flag is written but never read by the functions that move value.

### Finding Description
`IntentsBase.sol` defines an internal pause flag: [1](#0-0) 

but none of the token-moving/settlement functions reference it. Grepping the intents contracts for `whenNotPaused|Pausable|paused` combined with the fill/cancel/accept function names only matched the function *declarations* themselves in `ExtrinsicIntents.sol`, not a pause guard — i.e. `fillOrder`, `cancelOrder`, `onAccept`, and `onGetResponse` contain no reference to `_paused` at all. The internal helpers that actually move escrowed funds, `_withdraw` (releases/refunds escrow) and `_fillSameChain`/`_cancelSameChain` (same-chain fill/cancel paths), also contain no pause check: [2](#0-1) [3](#0-2) 

This is the same bug class as the `Clearinghouse.emergencyShutdown()` report: a boolean "shut down/paused" flag exists, and presumably a `pause()` setter flips it, but the functions that dispatch new orders, fill orders, cancel orders, and process cross-chain settlement (`onAccept`) never check it before moving escrowed user funds or protocol dust. If `_paused` is meant to stop new activity (e.g., during a discovered exploit or oracle/price-manipulation issue), an attacker or ordinary user can continue to place, fill, and settle orders — including draining escrow via `_withdraw` — while the protocol operators believe the gateway is halted.

### Impact Explanation
If the pause flag is intended as the protocol's emergency circuit breaker (analogous to `active`/`emergencyShutdown` in the reference report), its non-enforcement in `fillOrder`/`cancelOrder`/`onAccept` means governance/emergency responders cannot actually stop fund movement through the IntentGateway during an incident. This allows continued draining of escrowed inputs, continued mint/release of outputs, and continued cross-chain settlement dispatch after the operators believed the contract to be safely halted — a direct path to fund loss during exactly the window the pause is supposed to protect.

### Likelihood Explanation
Reachable by any unprivileged solver/user calling `fillOrder`/`cancelOrder`, and by any relayer delivering a `PostRequest` that triggers `onAccept`/`onGetResponse` — no privileged role is required to exploit the missing check, only that `_paused` has been set true by an admin trying to stop the contract.

### Recommendation
Add an explicit pause check (e.g., `if (_paused) revert Paused();` or a `whenNotPaused` modifier) to `placeOrder`, `fillOrder`, `cancelOrder`, `onAccept`, and `onGetResponse` in `ExtrinsicIntents.sol`/`IntrinsicIntents.sol`, mirroring the recommendation in the source report to gate `lendToCooler()`/`rollLoan()` on the `active` flag.

### Proof of Concept
Not independently reproduced with a Foundry test in this pass — this conclusion is based on static analysis of the declared `_paused` field versus the absence of any pause-check reference in the fill/cancel/accept code paths found via `grep_search`. **Caveat:** I was not able to locate or inspect the function that actually sets `_paused` (e.g. a `pause()`/`setPaused()` entry point) within the tool budget available, so I cannot confirm with full certainty (a) that `_paused` is wired up to any admin/governance action at all, or (b) that there isn't a check enforced elsewhere (e.g., at the `IntentGatewayV2` composition level) that my searches missed. If a Devin session with full file access confirms `_paused` is set by governance and truly unchecked in these entry points, this finding should be treated as valid and high severity; if `_paused` turns out to be dead/unused code with no setter, this would not constitute an exploitable vulnerability.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
