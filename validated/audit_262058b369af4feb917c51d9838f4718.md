Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` (the tenant identifier) is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is completely outside of the HMAC-signed content [2](#0-1) . `Registry.process` validates the HMAC over the request (body only) and then dispatches the handler using `request.shop` taken from that unauthenticated header [3](#0-2) . This exactly matches the allowed bug class: "a field acted on but not covered by the HMAC."

### Title
Webhook shop-domain header not covered by HMAC signature allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only [1](#0-0) , but the `shop` value used by handlers to identify which merchant the event belongs to comes from the `x-shopify-shop-domain` HTTP header [2](#0-1) , which is not part of the signed payload. `Registry.process` accepts any request whose HMAC matches the body, then passes the header-derived `shop` straight to the app's webhook handler [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop used by handler == shop authenticated by HMAC`. Because the HMAC only covers `@raw_body` and the `shop-domain` header is read independently via `shopify_header("shop-domain")` [4](#0-3) , an attacker who possesses one validly-signed webhook body/signature pair for their own store (e.g., a webhook with a fixed or predictable JSON body like `{}` or `{"id":1}`, which is common for topics such as `shop/redact` or app-uninstall notifications) can resend the identical `raw_body` + `x-shopify-hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `Utils::HmacValidator.validate` only recomputes the signature from `to_signable_string` (the body) and compares against the header signature [5](#0-4) ; it never checks that the signed content is bound to the claimed shop. `Registry.process` then invokes the handler with `shop: request.shop`, believing the header is authenticated because "the HMAC passed" [6](#0-5) .

### Impact Explanation
This breaks the tenant-identity binding at the point where host applications key their business logic (data deletion, redaction, uninstall handling, order sync, etc.) off `WebhookMetadata#shop`. An attacker can trigger the app to act as though an event happened for a victim shop, e.g. forging a `shop/redact` or `app/uninstalled` webhook for a shop domain of the attacker's choosing (as long as the body content is fixed/guessable/replayable), causing the app to erase or mutate data belonging to another merchant — a cross-tenant access impact.

### Likelihood Explanation
Exploitability requires the attacker to already have a validly-signed body/HMAC pair, which is achievable because many webhook topics have small or fixed bodies (e.g. GDPR/mandatory topics have deterministic shapes, or an attacker's own store can generate a webhook with a body that happens to match/target data of interest), and because the shop header is trivially replaced in a replayed HTTP request. No secret material is required beyond capturing one legitimate webhook delivery (which any shop owner installing the app can capture for their own store).

### Recommendation
Bind the shop identity into the signed content that is verified, or otherwise cryptographically corroborate the `shop-domain` header before trusting it — e.g., include the raw headers (or at least `shop-domain`) in `to_signable_string`, or cross-check the header's shop domain against a shop known to be associated with the delivered `webhook_id`/topic via a server-side lookup, before dispatching to handlers.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger a webhook topic whose payload body is fixed or attacker-controlled/predictable (e.g. `{}` for `shop/redact`), and capture the raw HTTP request, including `x-shopify-hmac-sha256` and `raw_body`.
2. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches, so `Registry.process` proceeds and calls the handler with `shop: "victim-shop.myshopify.com"` [7](#0-6) , causing the app to process a forged event as if it originated from the victim's shop.
