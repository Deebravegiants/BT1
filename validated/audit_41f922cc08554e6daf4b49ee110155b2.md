### Title
`Webhooks::Request#shop` returns unvalidated, HMAC-uncovered `shop-domain` header, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Webhooks::Request#initialize` only checks for the *presence* of the `shopify-shop-domain`/`x-shopify-shop-domain` header and `#shop` returns its raw value with no call to `Utils::ShopValidator.sanitize!` or any format check. Because `HmacValidator.validate` signs only `to_signable_string` (the raw body) with the app's `Context.api_secret_key`, the shop-domain header is completely outside the authenticated envelope, so any body+HMAC pair legitimately issued by Shopify for one shop can be replayed against the app's public webhook endpoint with an arbitrary `shop-domain` header value.

### Finding Description
Binding claimed to hold but actually broken: `request.shop (header value) == authenticated tenant identity trusted by Registry.process/host handler`.

- `Request#initialize` (lib/shopify_api/webhooks/request.rb:46-63) validates only that `shopify-topic`, `shopify-hmac-sha256`, and `shopify-shop-domain` headers *exist* — it never validates their contents.
- `#shop` (lines 20-23) does `T.cast(shopify_header("shop-domain"), String)` — a raw, unsanitized pass-through of attacker-controlled header data.
- `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) calls `Utils::HmacValidator.validate(request)`, then hands `request.shop` straight to the host's `WebhookHandler` via `WebhookMetadata.new(... shop: request.shop ...)` with zero re-validation.
- `HmacValidator.validate`/`validate_signature` (lib/shopify_api/utils/hmac_validator.rb:12-31) computes `OpenSSL::HMAC.hexdigest(sha256, Context.api_secret_key, verifiable_query.to_signable_string)`, and `to_signable_string` returns only `@raw_body` (request.rb:36-38). The shop header is never part of the signed material.
- Contrast with `Utils::ShopValidator.sanitize!` (lib/shopify_api/utils/shop_validator.rb:56-64), which the gem *does* invoke for OAuth-related shop parameters (e.g. `Auth::TokenExchange`, `Auth::ClientCredentials`, `Auth::RefreshToken`) — but is never called anywhere in the webhook `Request`/`Registry` code path.

Exploit flow: the attacker installs the target app on their own development shop (a legitimate, unprivileged action), triggers any webhook topic the app subscribes to, and captures the resulting `(raw_body, x-shopify-hmac-sha256)` pair that Shopify delivered — this pair is validly signed with the app's shared `Context.api_secret_key` (the same secret is used for every shop that installs the app, it is not shop-specific). The attacker then POSTs that identical body/HMAC pair directly to the app's public webhook endpoint, substituting an arbitrary `x-shopify-shop-domain` header (e.g. a victim shop's domain, or any attacker-chosen string). `HmacValidator.validate` still returns `true` (it never touches the shop header), so `Registry.process` proceeds and calls the host's handler with `shop: request.shop` set to the attacker's chosen string.

None of the existing guards intercept this: `HmacValidator.validate` checks the body signature only; `ShopValidator.sanitize!` is never invoked in this path; there is no `state` comparison or JWT `aud`/`dest` check involved in webhook processing (those apply to OAuth/session-token flows, not webhooks); `Context.setup?`/`private?`/`embedded?` are unrelated configuration flags that do not gate this code path; Sorbet's `T.cast` performs no runtime validation of content, only a type assertion.

### Impact Explanation
Any host application that uses `request.shop` (as returned by this gem) as a tenant/session key — which is the documented and expected usage per `docs/usage/webhooks.md` and `WebhookMetadata` — will attribute an attacker-forged webhook event to an arbitrary shop string. This is repeatable indefinitely by any attacker with a single dev-shop installation: they can replay captured legitimate payloads under any `shop-domain` value they choose, corrupting or spoofing per-tenant state for shops they do not control (cross-tenant impact), matching the Critical "cross-tenant access" category to the extent the host's tenant-keying logic trusts this value without independent verification.

### Likelihood Explanation
Preconditions are cheap and entirely within an unprivileged attacker's reach: create a free development shop, install the target app, trigger any subscribed webhook topic once to obtain a valid `(body, hmac)` pair, then send a raw POST to the app's (typically documented/discoverable) webhook URL with a forged `shop-domain` header. No secrets, tokens, or privileged access are required, and the attack is trivially repeatable against arbitrary chosen shop strings since the `api_secret_key` is shared across all installs of the app.

### Recommendation
In `lib/shopify_api/webhooks/request.rb`, validate the `shop-domain` header value through `Utils::ShopValidator.sanitize!` (mirroring how OAuth flows validate shop) inside `#initialize` or `#shop`, rejecting requests whose shop domain is not a well-formed `*.myshopify.com` (or configured trusted) domain. This alone does not fully close the replay gap (an attacker's own shop is itself a valid myshopify.com domain), so host apps should additionally be advised/enforced to correlate `request.shop` against a shop known to have registered that specific webhook subscription (e.g., checking against installed/active sessions) rather than trusting the header as an implicit identity assertion.

### Proof of Concept
```ruby
# test/webhooks/request_test.rb (new test)
def test_shop_is_not_validated_or_sanitized
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, "{}")
  headers = {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => Base64.encode64(hmac),
    "x-shopify-shop-domain" => "not-a-real-shop.attacker.com",
  }

  request = ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: headers)

  # HMAC validation passes because the shop header is not part of the signed payload
  assert(ShopifyAPI::Utils::HmacValidator.validate(request))
  # #shop returns the arbitrary, unsanitized attacker-controlled string
  assert_equal("not-a-real-shop.attacker.com", request.shop)
end
```
This demonstrates both sides of the claimed binding diverge: `request.shop` ("not-a-real-shop.attacker.com") is accepted as valid downstream input even though it is not a trusted/verified shop identity, and `HmacValidator.validate` — the only authentication gate in `Registry.process` — never inspects or constrains it.
