### Title
Missing input validation in `ConnectedOrigins.add()` allows unvalidated trust/permission state to be persisted - (File: features/connected-origins/module/connections.js)

### Summary
The `@exodus/connected-origins` module maintains the authorization state (trust, auto-approve, connected assets/accounts) that gates whether a website can access wallet addresses and request signing through the injected web3 providers. The `add()` method (and its siblings `#addNewItem`/`#setAttributes`) accepts and persists caller-supplied fields — including `origin`, `trusted`, `assetNames`, `connectedAssetName`, and `walletAccount` — with no type/shape validation whatsoever before writing them into the `connectedOriginsAtom`/`connectedAccountsAtom` storage that downstream RPC permission checks (`isTrusted`, `isAutoApprove`, `getConnectedAccounts`) rely on.

### Finding Description
`ConnectedOrigins.add` destructures its parameters directly and writes them into persisted state without any schema/type validation: [1](#0-0) 

Compare this to `#addNewItem`, which builds the stored record directly from unvalidated inputs (`origin`, `trusted`, `favorite`, `assetNames`, `walletAccount`): [2](#0-1) 

This mirrors the analog bug class from the external report: object fields (`origin`, `trusted`, `assetNames`, `walletAccount`, etc.) are consumed and persisted without validating their required presence, type, or format (e.g., `origin` is never checked to be a well-formed origin string, `trusted`/`favorite` are never checked to be booleans, `assetNames`/`walletAccount` are never checked against known asset/account identifiers).

Trust state gates security-relevant decisions downstream:
- `isTrusted` simply reads back the unvalidated `trusted` field: [3](#0-2) 
- `getConnectedAccounts` exposes wallet addresses for `assetNames` taken directly from the unvalidated stored record: [4](#0-3) 

This whole API (`add`, `untrust`, `isTrusted`, `setAutoApprove`, `connect`, `getConnectedAccounts`) is re-exported as-is on the public SDK surface with no additional validation wrapper: [5](#0-4) 

### Impact Explanation
Because none of the fields are validated, any caller of this internal API (reachable from the RPC/messaging bridge that connects the injected web3 provider content-script/background flow, per `libraries/browser-extension-rpc` and `libraries/browser-extension-channels`) could persist malformed or malicious values — e.g., a non-string/spoofable `origin`, a `trusted: true` flag combined with an attacker-chosen `assetNames`/`walletAccount`, or duplicate/prototype-polluting keys — directly into the wallet's authorization store. Since `isTrusted`/`isAutoApprove`/`getConnectedAccounts` trust this stored data unconditionally, an unvalidated write could bypass the intended "user must approve popup" trust boundary, leak wallet addresses for arbitrary `assetNames`, or corrupt the connected-origins state used to decide whether transaction/message signing prompts should auto-approve.

### Likelihood Explanation
I was unable to fully trace the concrete call path from the browser-extension content-script / popup UI into `connectedOrigins.add` (that UI/background wiring code was not found in the indexed portion of the repo), so I cannot conclusively prove that an untrusted webpage can invoke `add` directly without a prior user-approval gate elsewhere in the extension background process. The missing validation in `connections.js` itself is confirmed and directly analogous to the reported bug class, but likelihood depends on whether an unprivileged caller can reach `add`/`#setAttributes` without passing through a trusted popup-approval step that isn't part of this indexed codebase.

### Recommendation
Add explicit schema validation (e.g., using `@exodus/typeforce` or `@exodus/zod`, both already used elsewhere in the codebase such as `features/feature-flags/module/types.js` and `features/remote-config/report/index.ts`) for all fields accepted by `ConnectedOrigins.add`, `#setAttributes`, `setFavorite`, `setAutoApprove`, `connect`, and `disconnect` — validating `origin` as a well-formed origin string, `trusted`/`favorite`/`autoApprove` as booleans, `assetNames` as an array of known asset identifiers, and `walletAccount` against the enabled wallet accounts atom — before persisting to `connectedOriginsAtom`/`connectedAccountsAtom`.

### Proof of Concept
Not constructed — reaching this code from an actual untrusted origin requires tracing the browser-extension background wiring (content script → RPC bridge → background message handler → `connectedOrigins.add`) that was not available in the indexed codebase. The concrete gap demonstrated is that `connections.js` itself performs zero validation on its inputs: calling `connectedOrigins.add({ origin: <anything>, trusted: true, assetNames: [...], walletAccount: <anything> })` will persist exactly those values into storage unchanged, as shown by the test suite that feeds arbitrary shapes straight through with no rejection: [6](#0-5)

  add = async ({
    connectedAssetName,
    origin,
    name,
    icon,
    assetNames = [],
    trusted,
    favorite,
    walletAccount,
  }) => {
    const value = await this.#getOrigin({ origin })

    const allConnectedAssetNames = new Set([
      connectedAssetName,
      ...assetNames,
      ...(value?.assetNames ?? []),
    ])

    if (value) {
      await this.#setAttributes({
        origin,
        attributes: {
          icon: icon ?? value.icon,
          name: name ?? value.name,
          connectedAssetName: connectedAssetName ?? value.connectedAssetName,
          trusted: trusted ?? value.trusted,
          favorite: favorite ?? value.favorite,
          assetNames: [...allConnectedAssetNames],
          walletAccount: walletAccount ?? value.walletAccount,
        },
      })

      return
    }

    await this.#addNewItem({
      origin,
      icon,
      name,
      connectedAssetName,
      trusted,
      favorite,
      assetNames: [...allConnectedAssetNames],
      walletAccount,
    })
  }

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
