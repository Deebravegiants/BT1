The Tron `IntentGatewayV2.sol` port of the intent gateway lacks the refund-of-excess-native-token step that the EVM version added. This is a direct analog of the `BreederTimeLockPool.crossChainClaimReward()` bug (accepting more native tokens than needed for a swap/dispatch, with no refund path).

### Title
Excess native `msg.value` sent for fee-token swap or dispatch gets permanently stuck in the Tron `IntentGatewayV2` (`placeOrder`) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder()` on the Tron contract port swaps any supplied native token (`msgValue`) into the fee token via `IUniswapV2Router02.swapETHForExactTokens` to cover `order.fees`, but — unlike the canonical EVM `IntentGatewayV2.sol` — it never returns the leftover `msgValue` to the caller after the swap or after covering the native input legs.

### Finding Description
In the Tron contract, once native input legs are consumed and `order.fees` is paid via the Uniswap swap: [1](#0-0) 
there is no equivalent of the refund step performed by the EVM sibling contract, which explicitly ends `placeOrder` with: [2](#0-1) 
`swapETHForExactTokens` only spends exactly `order.fees` worth of ETH and refunds the unspent ETH back to the router caller (the contract itself, not the user) as part of a normal V2 swap. Because `IntentGatewayV2.sol` (Tron) never forwards that leftover balance (or any unused native input) back to `msg.sender`, both the swap-router "change" and any msgValue amount the user overestimated for native input/fee payment remain locked inside the contract with no path to reclaim them — the same root cause as `BreederTimeLockPool.crossChainClaimReward()` accepting excess native tokens for bridging without a refund mechanism.

### Impact Explanation
Any user (or automated SDK integration, since the SDK quoting logic can only approximate gas/Uniswap price movement between quote and execution — see `docs/content/developers/evm/intent-gateway/placing-orders.mdx` describing `nativeValue` as an estimate) who overestimates the native value needed for `order.fees` or native inputs permanently loses the difference. This is a direct, unrecoverable freezing of user funds reachable from a single `placeOrder` transaction — the same unprivileged, externally-triggerable path called out in scope (token bridger/intent-solver entry point).

### Likelihood Explanation
Likelihood is high: overpayment is the expected/normal client behavior for native-token fee payment (SDK docs explicitly instruct users to send a fee estimate, not an exact amount, and describe refunds as an assumed protocol behavior), and Uniswap V2 exact-output swaps routinely leave dust/change from slippage or price movement between quoting and execution.

### Recommendation
Port the same "refund any unspent native tokens to the user" pattern used in `evm/src/apps/IntentGatewayV2.sol` (and in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`) into `evm/tron/contracts/apps/IntentGatewayV2.sol`: track remaining `msgValue` after native input legs and the fee swap, and send it back to `msg.sender` via a low-level call (as done with `_sendValue`) before the function returns.

### Proof of Concept
1. User calls `placeOrder` on Tron `IntentGatewayV2` with an ERC-20/native input order that has `order.fees > 0`, sending `msg.value` intentionally higher than the exact ETH needed for `swapETHForExactTokens(order.fees, ...)`.
2. The swap executes, spending only the ETH necessary to acquire `order.fees` in fee tokens.
3. The unspent ETH (the swap's returned change) is never transferred back to `msg.sender`; the function returns without touching the remaining balance.
4. The excess native tokens remain locked in the `IntentGatewayV2` contract balance indefinitely, exactly mirroring `BreederTimeLockPool.crossChainClaimReward()`'s pre-fix behavior of accepting excess native tokens for bridging without a refund path — confirmed by contrast with the fixed EVM version's explicit refund block at `evm/src/apps/IntentGatewayV2.sol:394-397`.
