# Analysis Result

### Title
Unbounded BEEFY signature-recovery loop is charged zero dispatch weight, allowing computational DoS of the consensus update path - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
The reported OpenSSL issue is a class of bug where a "cheap-looking" validation function (`DH_check()`) performs work that scales with an attacker-controlled parameter (`q`) with no upfront bound, letting an untrusted caller trigger a slow computation. The analogous pattern in Hyperbridge is the BEEFY ECDSA consensus verifier: `verify_mmr_update_proof` iterates over an attacker-supplied, unbounded `signatures` vector and performs one `secp256k1_recover` per entry, and this entire cost is dispatched through `pallet-ismp`'s `handle_unsigned` extrinsic, whose `MessageResult::weight()` returns `Weight::zero()` for consensus messages regardless of how much recovery work was actually performed.

### Finding Description
`verify_mmr_update_proof` first checks `check_participation_threshold(signatures_length, authority_set.len)` — a length-only comparison — and then loops over every signature calling `H::secp256k1_recover` (expensive elliptic-curve point recovery) for each one: [1](#0-0) [2](#0-1) 

There is no upper bound on `mmr.signed_commitment.signatures.len()` distinct from the authority-set size, and the threshold check that gates entry into the loop can be satisfied trivially by mixing in enough valid-format-but-garbage signature bytes to exceed the 2/3+1 count, after which the loop still performs ECDSA recovery on every entry — valid or not — before any of them are checked for authority-set membership via the merkle multi-proof: [3](#0-2) 

This verification is reached through `pallet-ismp`'s unsigned `handle_unsigned` extrinsic, which carries a `Message::Consensus(ConsensusMessage)` with a completely unbounded `consensus_proof: Vec<u8>`: [4](#0-3) 

Crucially, the weight accounting for this dispatch path treats consensus messages as free: `MessageResult::weight()` returns `Weight::zero()` for the `ConsensusMessage` variant no matter how many signature recoveries were performed inside it: [5](#0-4) 

Additionally, `validate_unsigned` for `pallet-ismp` fully executes `Self::execute(messages.clone())` — including the entire BEEFY signature-recovery loop — during **transaction-pool validation**, which every gossiping node performs, entirely outside of block-weight metering: [6](#0-5) 

This is the same bug class as `DH_check()`/`EVP_PKEY_param_check()`: a function that performs untrusted-input-scaled expensive cryptographic work is invoked on attacker-supplied data with no proportional cost accounting, allowing a denial-of-service via crafted input rather than via raw traffic volume.

Note: some runtimes (`gargantua`, `nexus`) explicitly reject raw BEEFY consensus messages through `handle_unsigned`, forcing the SP1 zk-proof path instead: [7](#0-6) 
This mitigates the issue only on runtimes that adopt this specific filter; the underlying verifier function and the zero-weight accounting for consensus messages are shared library/pallet code and remain exploitable wherever the raw ECDSA BEEFY path is exposed through `handle_unsigned`.

### Impact Explanation
An attacker able to submit or gossip an unsigned `handle_unsigned` extrinsic carrying a crafted BEEFY `ConsensusMessage` with a padded/oversized `signatures` list can force full nodes to perform a large, unmetered number of ECDSA recoveries — both during mempool `validate_unsigned` gossip validation (unmetered entirely) and, on any chain lacking the gargantua/nexus-style filter, during actual dispatch (metered at zero weight). This can degrade block production and consensus-update processing for the affected state machine, which can render the corresponding bridge route unable to timely deliver messages — a route/messaging-availability impact.

### Likelihood Explanation
`handle_unsigned` is explicitly designed to permit anyone to submit ISMP messages for free ("This is an unsigned extrinsic that permits anyone execute ISMP messages for free"), and consensus messages are unsigned by design, so no privileged access is required. The only defense identified is the runtime-specific `IsmpCallFilter` present in `gargantua`/`nexus`; any deployment relying on the raw ECDSA BEEFY path through `handle_unsigned` (rather than the SP1-gated `pallet-beefy-consensus-proofs`) is directly exposed.

### Recommendation
- Bound `mmr.signed_commitment.signatures.len()` to a reasonable multiple of the known authority-set size before entering the recovery loop, rejecting oversized signature lists immediately (cheap length check), analogous to OpenSSL's fix of rejecting `q > p` before the expensive check.
- Make `MessageResult::weight()` for `ConsensusMessage` proportional to the actual verification cost (e.g., number of signatures/proof size) rather than `Weight::zero()`, so dispatch fees/weight limits reflect real work.
- Consider pre-validating structural bounds (max signature count, max proof size) in `validate_unsigned` before invoking full message execution, so mempool-level gossip validation cannot be used to force unmetered expensive verification.

### Proof of Concept
1. Construct a `ConsensusMessage` whose `consensus_proof` decodes to a `MmrProof` with a legitimate authority set of size `N` but `signatures` populated with `M >> N` entries (garbage 65-byte signatures interspersed with just enough valid ones to pass `check_participation_threshold`).
2. Submit via `Ismp::handle_unsigned([Message::Consensus(msg)])` as an unsigned extrinsic.
3. Observe that `validate_unsigned` (modules/pallets/ismp/src/lib.rs:614-625) invokes `Self::execute` which calls `verify_mmr_update_proof`, performing `M` `secp256k1_recover` calls before rejecting/accepting — with no weight charged for the consensus message result (modules/ismp/core/src/handlers.rs:80), and this same cost is paid by every gossiping node during mempool validation.
