### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking that the HMAC of the **raw body** matches, but the `shop` value handed to the app's handler is taken from an HTTP header that is never part of the signed data. Any party who can obtain one valid `(body, hmac)` pair for the app's shared `api_secret_key` (e.g., by installing the app on their own store and capturing a genuine webhook delivery) can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header. The signature still validates (it only covers the body), so the handler will be invoked with attacker-chosen `data.shop`, breaking the equality that should hold: `shop authenticated by HMAC == shop trusted by the handler`.

### Finding Description
`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`. For `Webhooks::Request`, this method is defined as: [1](#0-0) 

i.e., only `@raw_body` is signed. Meanwhile, `shop`, `topic`, `webhook_id` and `api_version` are all pulled straight from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because the `api_secret_key` used to compute the HMAC is a single, app-wide secret shared across **every shop** that installs the app (not a per-shop secret), a malicious merchant who installs the app on their own store legitimately receives real webhook deliveries with valid `(body, hmac)` pairs signed under that same shared secret. They can then send a forged HTTP request directly to the app's webhook endpoint, reusing the untouched `raw_body` and its valid `x-shopify-hmac-sha256` value, but replacing `x-shopify-shop-domain` with any other shop's domain (e.g., a victim shop known to have the app installed). `Registry.process` will accept this request as valid — the HMAC check only depends on the (unmodified) body — and will invoke the registered handler with `data.shop` set to the victim's domain instead of the attacker's own shop.

This breaks the identity binding: **the shop whose secret validated the request** should always equal **the shop attributed to the resulting data**, but here they can diverge because `shop` is never covered by the signature.

### Impact Explanation
Consuming applications are explicitly told by this gem's own documentation to treat `data.shop` as authoritative shop identity for a verified webhook (see `docs/usage/webhooks.md`, which describes `shop` as "The shop domain of the webhook" delivered by a `process` call that "will verify the request did indeed come from Shopify"). Typical handler implementations use `data.shop` to look up/derive the shop's session or access token, or to write/update tenant-scoped records keyed by shop domain. An attacker able to inject an arbitrary `data.shop` value into a "verified" webhook can:
- Attribute attacker-controlled webhook payloads (order data, product data, etc.) to a victim shop, corrupting or polluting that tenant's data.
- Trigger tenant-scoped side effects (e.g., background jobs enqueued with `shop_domain: data.shop`, as shown in the very doc example) under a victim's identity, potentially triggering cross-tenant data writes, notifications, or reprocessing using the victim's stored access token if the handler looks it up by `data.shop`.

This is a cross-tenant data integrity/isolation break stemming directly from a documented and library-enforced trust boundary (`Registry.process`) that does not actually bind the identity field it exposes.

### Likelihood Explanation
The prerequisite — a party being able to install the app on their own shop (or otherwise obtain one legitimate webhook body+HMAC for the shared secret) — is a low bar for public/listed apps, since installing an app on one's own development or test store is normal, unprivileged access, not requiring the platform's `client_secret`, an access token belonging to another tenant, or any privileged capability. Constructing the replayed HTTP request only requires basic HTTP tooling; the raw body is reused verbatim so the HMAC remains valid.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the signature verification, or otherwise require the application to independently corroborate `x-shopify-shop-domain` against a shop it recognizes as having actually registered *that* `webhook_id`/topic before trusting `data.shop`. At minimum, the gem should document prominently that `data.shop` is **not** cryptographically bound by the HMAC check and must not be trusted as tenant identity without additional verification (e.g., checking that the webhook_id corresponds to a subscription actually created for that shop).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving a legitimate webhook delivery with raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`).
2. Attacker sends a new POST request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`: unchanged (or whatever suits the target handler)
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`, which calls `Utils::HmacValidator.validate(request)` — this passes because only body `B` is checked against `H`.
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, as shown in [4](#0-3) , causing the app to process attacker-controlled data under the victim shop's identity.
