### Title
Predictable, Unauthenticated Session Identifier Enables Session Fixation Across Shops - (File: `lib/shopify_api/auth/session.rb`, `lib/shopify_api/auth/oauth.rb`, `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded OAuth flows, this gem issues a session-identifying cookie whose value is a fully deterministic, publicly-derivable string (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`), and later trusts that cookie's raw value as the session lookup key with no cryptographic binding to the browser that legitimately completed OAuth. This breaks the intended binding: `session_id used to fetch a stored access token == session_id genuinely issued to this specific browser after OAuth`. Because the ID is guessable from a public shop domain, an unprivileged user can set this cookie value themselves (classic session fixation) and cause the host application (following this gem's documented usage) to serve them another shop's stored session/access token.

### Finding Description
`Session.from` derives the session `id` purely from public data — the shop domain and (for online sessions) the associated user id — with no random or secret component: [1](#0-0) 

For non-embedded apps, `Oauth.validate_auth_callback` sets the browser cookie's value directly to this predictable `session.id`: [2](#0-1) 

Later, `SessionUtils.current_session_id` — the utility this gem exposes for retrieving "the" session on subsequent requests — for non-embedded apps takes the raw cookie value with zero verification and hands it back as the authoritative session id: [3](#0-2) [4](#0-3) 

`cookie_session_id` performs no signature, HMAC, or freshness check on the cookie bytes — it is literally `cookies[SessionCookie::SESSION_COOKIE_NAME]`. The equality that should hold is `session_id trusted by the app == session_id cryptographically bound to a completed OAuth handshake for this browser`; instead it holds `session_id trusted by the app == unauthenticated bytes supplied in a cookie header`, and those bytes are trivially predictable (`offline_{shop}.myshopify.com`) for any target shop domain, which is public information.

Contrast this with the embedded flow, which correctly derives the session id from a JWT (`Auth::JwtPayload`) signed with `Context.api_secret_key` — a value an attacker cannot forge. The non-embedded, cookie-based path has no equivalent protection.

### Impact Explanation
This is a session-fixation class issue explicitly in scope for this analysis: an attacker who knows (or guesses) a victim shop's `myshopify.com` domain can pre-set the `shopify_app_session` cookie in their own browser to `offline_{victim-shop}.myshopify.com` and query the app. If the host application follows this gem's documented pattern of loading the session by the id returned from `SessionUtils.current_session_id`, it will hand the attacker's request the victim shop's stored `Session` (including its access token), resulting in cross-tenant access without ever needing the victim's cookie, credentials, or the app's `client_secret`.

### Likelihood Explanation
Likelihood is high for any non-embedded integration built per this gem's documented API: the session identifier requires no secret to construct, only the target shop's domain, which app developers, partners, or public storefront visitors can typically observe.

### Recommendation
Do not use a deterministic, publicly-derivable value as the externally-facing session cookie/session id for non-embedded apps. Either:
- Generate a cryptographically random session identifier (e.g., `SecureRandom.uuid`) distinct from the internal shop-scoped storage key, and map that random id to the shop-scoped session server-side, or
- Sign/HMAC the cookie value (similar to the embedded JWT flow) so `cookie_session_id` can verify authenticity before trusting it, rather than returning raw cookie bytes unchecked in `lib/shopify_api/utils/session_utils.rb`.

### Proof of Concept
1. Attacker observes/guesses a target shop's domain, `victim-shop.myshopify.com` (public information, e.g. from the storefront URL).
2. Attacker sends a request to the app's protected endpoint with `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`.
3. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which — since `Context.embedded?` is false — calls `cookie_session_id(cookies)`, returning the attacker-supplied string unchanged:
   `lib/shopify_api/utils/session_utils.rb:31-37,68-71`.
4. Host app loads the stored `Session` for id `offline_victim-shop.myshopify.com` (created by the real victim during their own legitimate OAuth, whose id was deterministically produced by `Session.from` in `lib/shopify_api/auth/session.rb:107-117`) and uses its `access_token` to serve the attacker's request — granting the attacker access to the victim shop's data through the app.
