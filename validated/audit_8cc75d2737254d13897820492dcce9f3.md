### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are trusted from unsigned headers while only the body is HMAC-verified, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `HmacValidator.validate` verifies the HMAC solely against that body. The `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` forwards to the app's `WebhookHandler` are all parsed straight out of HTTP headers, which are never part of the signed material.

### Finding Description
This gem's webhook secret (`Context.api_secret_key`) is shared by the app across all of the merchants/shops that install it — it is not per-shop. `Request#hmac` decodes the `x-shopify-hmac-sha256` header and `HmacValidator.validate_signature` recomputes an HMAC over `verifiable_query.to_signable_string`, which is defined as just `@raw_body`:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read from headers with no cryptographic binding to the HMAC at all:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [5](#0-4) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop`, `request.topic`, etc., building the `WebhookMetadata` object that is delivered to the host app's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [1](#0-0) 

The identity binding that should hold is: `shop_the_HMAC_authenticates == shop_the_handler_acts_on`. Because the HMAC is computed only from the body and the app secret (which is not shop-specific), the equality actually enforced is only `body_is_untampered && signer_knows_app_secret`. The `shop` header is completely outside that equality. An unprivileged user who legitimately operates their own shop installed on the same app (a routine, unprivileged action — installing a free/public app) can trigger real webhook deliveries with attacker-controlled body content and a genuine, Shopify-issued HMAC for that body. They can then replay that exact HTTP request to the app's public webhook endpoint while rewriting only the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header to name a victim shop that also uses the app. `HmacValidator.validate` still passes, because the signature never covered those headers, and `Registry.process` will happily hand a `WebhookMetadata` claiming the victim's `shop` to the host app's handler, driving whatever tenant-scoped effects that handler performs (e.g., writing/deleting data keyed by shop, triggering `customers/redact`-style actions, updating billing/subscription state, or overwriting per-shop tokens/settings) against the victim tenant using attacker-supplied body content.

### Impact Explanation
This breaks the shop-authentication boundary at the core of a multi-tenant app: a value trusted by every downstream handler as "the shop this webhook is about" is not covered by the message authentication code that is supposed to prove the message's authenticity and origin, letting one tenant forge webhook events for another tenant. That is cross-tenant access/data corruption, matching the Critical impact bar (cross-tenant access) defined for this assessment.

### Likelihood Explanation
Any user can install the vulnerable app on their own shop (or use a free/dev store) without any special privilege, capture a genuinely-signed webhook for a topic/body they control, and replay it with a rewritten `shop-domain` header to the app's public webhook endpoint. No secret material, TLS interception, or social engineering is required — only the ability to receive one legitimate webhook and re-POST it with a modified header, which is straightforward for any HTTP client.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the material that is HMAC-verified, or otherwise cryptographically/independently corroborate the header-derived `shop` against data inside the signed body (Shopify's payloads generally include the shop's numeric/GID identifiers) before constructing `WebhookMetadata`. At minimum, `to_signable_string` in [2](#0-1)  should incorporate the shop-identifying headers, and `Registry.process` in [6](#0-5)  should not treat `request.shop` as trusted until it is validated against signed data.

### Proof of Concept
1. Attacker installs the target app on their own controlled shop `attacker.myshopify.com` and triggers a webhook whose body they can influence (e.g., a metafield or order note field reflected in the webhook payload for a topic the app subscribes to).
2. Shopify delivers the webhook to the app's endpoint with headers including `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and the attacker-influenced body.
3. Attacker captures this raw HTTP request (their own webhook, so this is legitimate access) and replays it verbatim to the same endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (and, if desired, `x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — unchanged — so validation succeeds.
5. The app's registered `WebhookHandler#handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: attacker_controlled_body, ...)`, causing the host app to process attacker-controlled data as if it originated from, and applies to, `victim.myshopify.com`.
