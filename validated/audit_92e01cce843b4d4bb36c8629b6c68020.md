Audit Report

## Title
Weak `check_enough_messages_included_basic` allows a malicious collator to permanently censor targeted DMP messages while advancing the processed watermark - ([File: cumulus/pallets/parachain-system/src/parachain_inherent.rs])

## Summary
`enqueue_inbound_downward_messages` gates DMP inherent processing with `check_enough_messages_included_basic`, which only asserts `full_messages.len() >= 1` whenever `hashed_messages` is non-empty, unlike HRMP which uses the strictly stronger, size-bound `check_enough_messages_included_advanced`. [1](#0-0) [2](#0-1)  This lets a collator hash out an arbitrary, attacker-chosen subset of pending downward messages (including one specific victim message) while including only a single trivial full message, satisfying the check.

## Finding Description
`AbridgedInboundMessagesCollection::check_enough_messages_included_basic` only checks that at least one full message is present if any messages are hashed, with no relation to the actual size budget or to which specific messages are hashed. [3](#0-2)  By contrast, `check_enough_messages_included_advanced` requires the full-messages byte size to be within `first_hashed_msg_max_size` of the size limit, i.e., it forces the collator to include as many full messages as fit the size budget before it is allowed to hash any — and its own doc comment states this exists specifically because "a malicious collator can provide a collection that contains no full messages or fewer full messages than possible, leading to censorship." [4](#0-3) 

Critically, `enqueue_inbound_downward_messages` calls the weak `basic` variant for DMP: [5](#0-4)  while `enqueue_inbound_horizontal_messages` calls the strong `advanced` variant, with `max_full_messages_size` derived from `messages_collection_size_limit()` and `first_hashed_msg_max_size` from the channel's `max_message_size`, for HRMP: [6](#0-5)  This confirms the previously unverified precondition in the submitted claim: DMP indeed uses the weaker check.

Because `hashed_messages` only stores `sent_at`/`msg_hash` and never the payload, and only `full_messages` are passed to `T::DmpQueue::handle_messages(downward_messages.bounded_msgs_iter())`, any message placed into `hashed_messages` never reaches the message handler — only its hash contributes to the recomputed `dmq_head`, which is what must match the relay chain's `expected_dmq_mqc_head`. [7](#0-6)  Since the collator computes the hash honestly from the real message, the MQC head equality check still passes even though the content is discarded. `ProcessedDownwardMessages` and `LastProcessedDownwardMessage` are then advanced, which drives relay-chain pruning of the corresponding queue entries (via `prune_dmq`/watermark logic on the relay side), making the message permanently unrecoverable. [8](#0-7) 

The only relay-side backstop, `check_processed_downward_messages`, merely requires `processed_downward_messages > 0` when the queue is non-empty at the relay parent — it does not require processing of any specific message, so it does not prevent this targeted censorship. [9](#0-8) 

The `AbridgedInboundMessagesCollection` (and its `AbridgedInboundDownwardMessages` alias) is supplied directly by the collator inside the parachain inherent; the natural "maximal full-message prefix" invariant is only produced by honest software via `into_abridged`, but a malicious collator constructing this data directly is free to choose any split. [10](#0-9) 

## Impact Explanation
A malicious/censoring collator can, in every block it produces, include a single decoy full message and hash out all other pending DMP messages — including a specifically targeted message such as an XCM `Transact` or reserve-transfer intended to credit a particular user. The watermark still advances and the relay chain prunes the acknowledged entries, so the targeted message's content is permanently and unrecoverably lost. This is a genuine, targeted, permanent freeze/loss of a downward-routed message, which is a valid in-scope impact for the parachain-system pallet's message-passing correctness guarantees.

## Likelihood Explanation
The precondition raised in the original submission is now confirmed: the DMP path uses `check_enough_messages_included_basic`, not the advanced/size-bound variant used for HRMP. The attack requires no cryptographic forgery — the hash is honestly derived from the real message so the MQC head validation still passes — and is repeatable every block by a single collator without any special privilege beyond being the block producer for that slot, which in most permissionless collator-set parachains is attainable by any bonded/registered collator, not just a chain-privileged actor.

## Recommendation
Change `enqueue_inbound_downward_messages` to call `check_enough_messages_included_advanced` with an `AbridgedInboundMessagesSizeInfo` derived from `messages_collection_size_limit()` and the max downward message size, mirroring the HRMP path, so that a collator cannot hash out messages until the full-message budget is genuinely exhausted. Consider removing `check_enough_messages_included_basic` for DMP entirely, or otherwise establishing an invariant that ties `full_messages` to the actual byte budget so that a single decoy message can never satisfy the check while other messages are arbitrarily hashed out.

## Proof of Concept
Extend the existing `check_enough_messages_included_basic_works` unit test in `cumulus/pallets/parachain-system/src/parachain_inherent.rs` (lines 513–535) with a DMP-alias variant: construct an `AbridgedInboundDownwardMessages` with `full_messages: vec![decoy_msg]` (small, e.g. 1 byte) and `hashed_messages` containing the honestly-computed `HashedMessage` for a larger "victim" message plus additional pending messages, well within the actual `messages_collection_size_limit()` budget that would allow all of them to be full messages. Call `check_enough_messages_included_basic("DMQ")` — it does not panic. Then, as a comparative check, call `check_enough_messages_included_advanced("DMQ", AbridgedInboundMessagesSizeInfo { max_full_messages_size: <realistic limit>, first_hashed_msg_max_size: <victim size> })` on the same collection to show it does panic, demonstrating the `basic` check is what permits the collator to hash out the victim message despite ample remaining size budget. A full integration-level PoC would additionally show `Pallet::enqueue_inbound_downward_messages` succeeding on such a crafted `AbridgedInboundDownwardMessages` value (matching a correctly-computed `expected_dmq_mqc_head`) and that `T::DmpQueue::handle_messages` never receives the victim message's payload.

	fn enqueue_inbound_downward_messages(
		expected_dmq_mqc_head: relay_chain::Hash,
		downward_messages: AbridgedInboundDownwardMessages,
	) -> Weight {
		downward_messages.check_enough_messages_included_basic("DMQ");

		let mut dmq_head = <LastDmqMqcHead<T>>::get();

		let (messages, hashed_messages) = downward_messages.messages();
		let message_count = messages.len() as u32;
		let weight_used = T::WeightInfo::enqueue_inbound_downward_messages(message_count);
		if let Some(last_msg) = messages.last() {
			Self::deposit_event(Event::DownwardMessagesReceived { count: message_count });

			// Eagerly update the MQC head hash:
			for msg in messages {
				dmq_head.extend_downward(msg);
			}
			<LastDmqMqcHead<T>>::put(&dmq_head);
			Self::deposit_event(Event::DownwardMessagesProcessed {
				weight_used,
				dmq_head: dmq_head.head(),
			});

			let mut last_processed_msg =
				InboundMessageId { sent_at: last_msg.sent_at, reverse_idx: 0 };
			for msg in hashed_messages {
				dmq_head.extend_with_hashed_msg(msg);

				if msg.sent_at == last_processed_msg.sent_at {
					last_processed_msg.reverse_idx += 1;
				}
			}
			LastProcessedDownwardMessage::<T>::put(last_processed_msg);

			T::DmpQueue::handle_messages(downward_messages.bounded_msgs_iter());
		}

		// After hashing each message in the message queue chain submitted by the collator, we
		// should arrive to the MQC head provided by the relay chain.
		//
		// A mismatch means that at least some of the submitted messages were altered, omitted or
		// added improperly.
		assert_eq!(dmq_head.head(), expected_dmq_mqc_head, "DMQ head mismatch");

		ProcessedDownwardMessages::<T>::put(message_count);

		weight_used
	}

	/// Converts `self` into an [`AbridgedInboundMessagesCollection`].
	///
	/// The first messages in `self` (up to the provided `size_limit`) are kept in their current
	/// form (they will contain the full message data).
	/// The messages that exceed that limit are hashed.
	pub fn into_abridged(
		self,
		size_limit: &mut usize,
	) -> AbridgedInboundMessagesCollection<Message> {
		let mut messages = self.messages;

		let mut split_off_pos = messages.len();
		for (idx, message) in messages.iter().enumerate() {
			if *size_limit < message.data().len() {
				break;
			}
			*size_limit -= message.data().len();

			split_off_pos = idx + 1;
		}

		let extra_messages = messages.split_off(split_off_pos);
		let hashed_messages = extra_messages.iter().map(|msg| msg.to_compressed()).collect();

		AbridgedInboundMessagesCollection { full_messages: messages, hashed_messages }
	}

	/// Check that the current collection contains as many full messages as possible, taking into
	/// consideration the collection constraints.
	///
	/// The `AbridgedInboundMessagesCollection` is provided to the runtime by a collator.
	/// A malicious collator can provide a collection that contains no full messages or fewer
	/// full messages than possible, leading to censorship.
	pub fn check_enough_messages_included_advanced(
		&self,
		collection_name: &str,
		size_info: AbridgedInboundMessagesSizeInfo,
	) {
		// We should check that the collection contains as many full messages as possible
		// without exceeding the max expected size.
		let AbridgedInboundMessagesSizeInfo { max_full_messages_size, first_hashed_msg_max_size } =
			size_info;

		let mut full_messages_size = 0usize;
		for msg in &self.full_messages {
			full_messages_size = full_messages_size.saturating_add(msg.data().len());
		}

		// The worst case scenario is that were the first message that had to be hashed
		// is a max size message.
		assert!(
			full_messages_size.saturating_add(first_hashed_msg_max_size) > max_full_messages_size,
			"[{}] Advancement rule violation: full messages size smaller than expected. \
			full msgs size: {}, first hashed msg max size: {}, max full msgs size: {}",
			collection_name,
			full_messages_size,
			first_hashed_msg_max_size,
			max_full_messages_size
		);
	}

	/// Checks if the number of processed downward messages is valid.
	pub(crate) fn check_processed_downward_messages(
		para: ParaId,
		relay_parent_number: BlockNumberFor<T>,
		processed_downward_messages: u32,
	) -> Result<(), ProcessedDownwardMessagesAcceptanceErr> {
		let dmq_length = Self::dmq_length(para);

		if dmq_length > 0 && processed_downward_messages == 0 {
			// The advancement rule is for at least one downwards message to be processed
			// if the queue is non-empty at the relay-parent. Downwards messages are annotated
			// with the block number, so we compare the earliest (first) against the relay parent.
			let first = InboundDownwardQueue::<T>::peek_front(para);

			// sanity: if dmq_length is >0 this should always be 'Some'.
			if first.map_or(false, |msg| msg.sent_at <= relay_parent_number) {
				return Err(ProcessedDownwardMessagesAcceptanceErr::AdvancementRule);
			}
		}

		// Note that we might be allowing a parachain to signal that it's processed
		// messages that hadn't been placed in the queue at the relay_parent.
		// only 'stupid' parachains would do it and we don't (and can't) force anyone
		// to act on messages, so the lenient approach is fine here.
		if dmq_length < processed_downward_messages {
			return Err(ProcessedDownwardMessagesAcceptanceErr::Underflow {
				processed_downward_messages,
				dmq_length,
			});
		}

		Ok(())
	}

	/// Prunes the specified number of messages from the downward message queue of the given para.
	pub(crate) fn prune_dmq(para: ParaId, processed_downward_messages: u32) {
		InboundDownwardQueue::<T>::drop_front_n(para, processed_downward_messages as u64);
		let q_len = InboundDownwardQueue::<T>::len(para).unwrap_or(0);

		let config = configuration::ActiveConfig::<T>::get();
		let threshold =
			Self::dmq_max_length(config.max_downward_message_size).saturating_div(THRESHOLD_FACTOR);
		if q_len <= threshold as u64 {
			Self::decrease_fee_factor(para);
		}
	}
