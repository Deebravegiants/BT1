### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature exclusively over the raw request body, while the `shop-domain` and `topic` headers—used by `ShopifyAPI::Webhooks::Registry.process` to route and tag the webhook to a tenant—are never included in the signed material. Any actor who possesses one valid `(body, hmac)` pair signed with the app's shared webhook secret (trivially obtained by installing the app on their own store and receiving a legitimate webhook) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The HMAC check still passes because it only ever validates the body, so the app processes attacker-controlled content as if it originated from a different, victim tenant.

### Finding Description
The HMAC binding breaks the equality: "shop/topic acted on by the handler" should equal "shop/topic cryptographically bound by the signature," but it does not.

- `to_signable_string` returns only `@raw_body`, so the HMAC signature Shopify computes and the gem verifies covers the body alone: [1](#0-0) 
- `shop` and `topic` are read straight from HTTP headers with no cryptographic tie to the signature: [2](#0-1) 
- `HmacValidator.validate` only ever inspects `verifiable_query.hmac` against `to_signable_string`, i.e. the body; it has no knowledge of `shop` or `topic`: [3](#0-2) 
- `Registry.process` validates the HMAC, then immediately trusts `request.shop` and `request.topic` (unsigned headers) to build `WebhookMetadata` and dispatch to the shop-specific handler: [4](#0-3) 
- `WebhookMetadata.shop` is the field the host application's handler uses to identify which tenant the webhook belongs to: [5](#0-4) 

Because the webhook secret (`Context.api_secret_key`) is shared across every shop that has the app installed, any merchant/user of the app can generate a self-signed `(body, hmac)` pair via their own store's webhooks, then relay that untouched body with a forged `shop-domain`/`topic` header pair to the app's public webhook endpoint. The signature check in `HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:13-22) passes unchanged, because it is blind to header content.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an unprivileged app user can make the host application execute webhook handling logic under a different shop's identity with attacker-chosen body content, satisfying the "cross-tenant access" criteria. Depending on how the host app's `WebhookHandler#handle` implementation uses `data.shop` (e.g., look up per-shop settings/sessions, write to per-shop records, or trigger emails/notifications), this can result in cross-tenant data corruption, spoofed mandatory-compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`), or misattributed actions against a victim shop.

### Likelihood Explanation
Likelihood is high for any attacker who is a legitimate installer of the app on their own store — no leaked secret, TLS interception, or privileged account is required. They only need to capture one legitimate webhook delivery and are then able to freely alter the unauthenticated `shop-domain`/`topic` headers on replay.

### Recommendation
Include `shop`, `topic`, and `webhook-id` in the signed material verified against the HMAC (or otherwise cryptographically bind them, e.g. by validating them against Shopify's known IP ranges plus mutually authenticating with a per-shop secret), so header values cannot be substituted independently of the signed body.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and lets Shopify deliver a normal webhook, capturing the raw body `B` and its `x-shopify-hmac-sha256` header `H` (both signed with the app's single shared `api_secret_key`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the exact same body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request#hmac` reads `H`; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches, so `Registry.process` proceeds: [4](#0-3) 
4. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, believing the request legitimately originated from the victim shop.
