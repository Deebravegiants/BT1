### Title
Webhook HMAC only covers the request body, allowing shop/topic identity spoofing via signature replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The gem's webhook signature verification computes the HMAC over the raw request body only. The `shop`, `topic`, `webhook-id`, and `api-version` values used downstream for tenant/handler dispatch are taken from unauthenticated HTTP headers that are never part of the signed material. An attacker who can obtain one valid `(body, hmac)` pair — e.g., from a webhook legitimately delivered to their own shop's endpoint — can replay that same body/HMAC with different `shop-domain`/`topic` headers, and the library will report it as valid and hand the attacker-chosen shop/topic to the host application's handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC strictly against `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.topic` (to select the handler) and `request.shop`/`request.webhook_id`/`request.api_version` (passed into the handler's `WebhookMetadata`) — none of which were covered by the signature just checked: [3](#0-2) 

The `shop`, `topic`, and `webhook_id` accessors simply read unauthenticated headers: [4](#0-3) 

This exactly matches the bug class described in the report — a field (`shop-domain`/`topic`) is acted on (used to select a handler and stamp the tenant identity delivered to the host app) but is not included in the value the HMAC actually authenticates. Since the shared `api_secret_key` is the same for every shop that installs a given app, a valid `(body, hmac)` pair generated for one shop's webhook remains a valid pair for any other `shop`/`topic` header combination — this is a direct binding break: `shop authenticated ≠ shop the signature was computed for`.

By contrast, the OAuth callback path in this same gem does bind `shop` into the signed material (`AuthQuery#to_signable_string` includes `shop`, `host`, `code`, `state`, `timestamp`), showing the library is capable of, and elsewhere does, bind identity fields into the HMAC: [5](#0-4) 

### Impact Explanation
An attacker who can obtain a single legitimate `(raw_body, hmac)` pair (trivially available if they install the target app on their own store, since the app owner's secret is shared across all installs) can forge a "verified" webhook request claiming to originate from an arbitrary other shop or topic. Any host application that uses `WebhookMetadata#shop`/`#topic` (as returned from `Registry.process`) as the tenant key for persisting or acting on webhook data — a pattern the gem's own API encourages — would attribute attacker-controlled body content to a victim shop, or dispatch the payload to the wrong topic handler. This is a cross-tenant data-integrity/confusion issue reachable purely by an unprivileged internet user with no access token, credential, or social engineering, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is High: the attacker only needs to run/install the app on a shop they control (or otherwise obtain one valid webhook delivery) to capture a valid `(body, hmac)` pair, since the same `api_secret_key` signs webhooks for every installation of an app. No secret material, elevated privileges, or complex conditions are required beyond that.

### Recommendation
- Short term: Include the `shop-domain`, `topic`, and `webhook-id` header values (or minimally the shop domain) in the HMAC-signed material verified by `Utils::HmacValidator`, or independently validate that `request.shop` corresponds to a shop actually associated with a known installation before trusting it, mirroring the approach already taken in `AuthQuery#to_signable_string`.
- Long term: Document explicitly that `Registry.process`'s `shop`/`topic`/`webhook_id` are unauthenticated header values, and require/encourage host apps to cross-check them against records tied to the raw body's `id`/resource identifiers rather than trusting the header alone for tenant attribution.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`; the app is configured with the developer's shared `api_secret_key`.
2. Shopify delivers a legitimate webhook to the attacker's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, body `B`, and `x-shopify-hmac-sha256: H` (valid HMAC of `B`).
3. Attacker replays the same body `B` and `H` to the victim host application's webhook endpoint, but substitutes `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
4. `Webhooks::Request#hmac` decodes `H`; `Utils::HmacValidator.validate` recomputes HMAC over `@raw_body` (`B`) only — per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31` — and it matches, so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) proceeds and invokes the host handler with `shop: "victim-shop.myshopify.com"` even though the payload/signature never involved that shop.
