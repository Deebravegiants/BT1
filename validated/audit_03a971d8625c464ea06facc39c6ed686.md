### No vulnerability found for this question.

**Trace summary supporting this conclusion:**

For `feeInclusive: false`, `IntentsSDK.createWithdrawalIntents` computes `actualAmount = args.withdrawalParams.amount` (unchanged — no fee subtraction occurs in this branch) [1](#0-0) . This same `actualAmount` is passed both to `bridge.validateWithdrawal` and, overriding `withdrawalParams.amount`, to `bridge.createWithdrawalIntents` [2](#0-1) . There is no divergence between the value checked for the minimum and the value that ends up in the intent for the `feeInclusive: false` case, because fee is never subtracted from the amount in this branch.

In `OmniBridge.validateWithdrawal`, the UTXO-chain minimum check explicitly adds `utxoMaxGasFee + utxoProtocolFee` to `args.amount` before comparing to the bridge's `min_amount` [3](#0-2) . This exactly matches how `deriveOmniWithdrawIntentParams` builds the actual `ft_withdraw` amount for UTXO chains — it also adds `utxoMaxGasFee + utxoProtocolFee` on top of `actualAmount` [4](#0-3) , and the code comment explicitly documents this design: for `feeInclusive=false`, `amount = 4000 -> intent = 4100 -> user receives 4000` [5](#0-4) . For non-UTXO chains, `nativeFee` is paid separately via a `token_diff` swap plus `storage_deposit`, not subtracted from the withdrawn token amount at all [6](#0-5) , so the non-UTXO minimum check against the fee-less `args.amount` [7](#0-6)  is consistent with the amount actually carried by `ft_withdraw`.

The question's premise — that a fee subtraction happens for `feeInclusive: false` that could push the amount below minimum only in one of the two checks — does not hold: no fee is subtracted from `actualAmount` in this branch, and the two places that read the "actual" amount (`validateWithdrawal`'s min check and `deriveOmniWithdrawIntentParams`'s intent-amount construction) use the same value and apply the same UTXO fee addition consistently.

A distinct, narrower issue does exist — `createWithdrawalIntents` (used by `signAndSendWithdrawalIntent` with caller-supplied `feeEstimation`) lacks the `FeeExceedsAmountError` guard that `_estimateWithdrawalFee` applies for `feeInclusive: true` [8](#0-7)  — but that concerns `feeInclusive: true`, not the `feeInclusive: false` scenario this question asks about, and would only harm the caller's own supplied funds/estimation, not divert funds to a third party. It is out of scope for this specific question.
