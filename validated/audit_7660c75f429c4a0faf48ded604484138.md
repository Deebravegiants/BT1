### Title
Direct token transfers to the pool contract are permanently locked — accounting cash never absorbs donations and no skim/recovery path exists - (contracts/pool/src/cache/cash.rs)

### Summary
The pool contract tracks its token reserves exclusively through an accounting `cash` field maintained in `Cache`. `cash` is only mutated by `credit_cash`/`debit_cash` on protocol paths (supply, repay, recapitalize, withdraw, borrow). The pool's actual token balance is never reconciled against `cash` on any outbound or inbound path, and the contract exposes no entrypoint to sweep surplus tokens. Any token amount transferred directly to the pool contract address — reachable by any unprivileged address via a plain SAC token `transfer` — is permanently unrecoverable, analogously to L1 ECO locked in the bridge when users burn their L2 tokens outside the withdrawal path.

### Finding Description
All liquidity accounting runs through `Cache::cash`. `debit_cash` caps every outbound flow at tracked cash, and `transfer_out` is the only function that moves tokens, always paired with a prior `debit_cash` (e.g., `withdraw.rs` calls `gate_and_debit` → `debit_cash` → `transfer_out`). `credit_cash` is only invoked inside protocol ops (`supply`, `repay`, `recapitalize`); none of them measure the pool's real token balance — they credit exactly the caller-declared amount. The docs confirm this is deliberate bookkeeping: "Tracked cash is a separate reserve balance that incidental token donations do not increase" (`docs/reference/formulas.md`).

Relevant code:

```rust
// contracts/pool/src/cache/cash.rs
pub(crate) fn debit_cash(&mut self, amount: i128) {
    require_nonneg_amount(&self.env, amount);
    self.require_reserves(amount);           // cash >= amount, ignores real balance
    self.cash = self.cash.checked_sub(amount)...
}

pub(crate) fn transfer_out(&self, recipient: &Address, amount: i128) {
    ...
    tok.transfer(&self.env.current_contract_address(), recipient, &amount);
}
```

Even `recapitalize` — the only path that injects cash without minting shares — credits `min(amount, backing_shortfall)` based purely on the tracked `cash` figure and refunds the excess to the payer; donated surplus cannot be retroactively credited and the shortfall computation never observes the real balance (`contracts/pool/src/ops/recapitalize.rs`, `guards::backing_shortfall` uses `floor(supply) - (cash + ceil(debt))`). A repo-wide search finds no `skim`/`rescue`/`sweep` entrypoint in the pool or controller in-scope surface; the only `balance(` reads in the pool are in `flash.rs` for measuring the flash callback repayment, which settles against accounting, not surplus.

### Impact Explanation
Tokens sent directly to the pool contract (by mistake, by an integrator pre-funding an account, or by any holder) are permanently frozen. No unprivileged or privileged flow — withdraw, borrow, claim_revenue, recapitalize, clean_bad_debt, flash_loan — can release them, because every outflow is gated on `self.cash`, which the donation never incremented. This is permanent freezing of funds, the same impact class as L1 ECO locked in `L1ECOBridge` after an off-bridge `L2ECO.burn`. Unlike the ECO case the freeze here is not a share-burn bypass; it is the absence of a balance-vs-accounting reconciliation or recovery path.

### Likelihood Explanation
The trigger is a plain token `transfer` to the pool address — a single unprivileged call, no auth, no racing, no market state required. On Stellar, SAC transfers to contract addresses are unrestricted, so accidental or griefed transfers (e.g., refunds sent to the pool, `repay_debt_with_collateral`-style flows misrouted, or third-party integrations pre-transferring funds) are realistic over the contract's lifetime. The donation does not benefit other users: it does not raise share value or `cash`, it simply sits unspendable forever — it can never even become claimable revenue.

### Recommendation
Add a permissionless `skim`/`sync` entrypoint that measures `token.balance(pool) - sum(cash across markets)` and either credits the surplus to protocol revenue (`accrue_revenue`/`absorb_supply_as_revenue` on a designated market) or allows governance to sweep it to the treasury. Alternatively, route donation recovery through `recapitalize` by computing `applied` against real balance surplus, or document and hard-reject plain transfers where the token standard permits a transfer hook.

### Proof of Concept
1. Market is initialized for asset `T` via `controller.supply`/`borrow`; pool's tracked `cash` = e.g. 1000, real balance = 1000.
2. Any address calls `T.transfer(user → pool, 500)`. Real balance = 1500, `cash` still 1000.
3. Supplier calls `controller.withdraw(0 /* all */)`: `gate_and_debit` enforces `cash >= net_transfer` and `debit_cash` caps at 1000 — the extra 500 cannot leave.
4. `recapitalize` cannot absorb it: `applied = min(amount, backing_shortfall)` computes shortfall from tracked `cash`, so surplus is invisible; excess is refunded to the payer.
5. `claim_revenue` pays out `min(cash, floor(revenue))` — again bounded by tracked cash.
6. Real balance remains 1500 forever with only 1000 ever spendable; the 500 is permanently locked.
