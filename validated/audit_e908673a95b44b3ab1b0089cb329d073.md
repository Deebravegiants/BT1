## Title
Webhook `shop` (and `topic`/`webhook_id`) fields are trusted despite not being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (tenant identity), `topic`, and `webhook_id` fields come from HTTP headers that are excluded from the signature. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` when dispatching to the app's handler. An attacker who can obtain one legitimately-signed webhook body/HMAC pair (e.g. from their own shop where the app is installed) can replay it with an arbitrary `X-Shopify-Shop-Domain` header, and the HMAC check will still pass — because that header was never part of what was signed.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from a header that is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` validates the HMAC first, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The binding this breaks, expressed as an equality that the library implicitly claims but does not enforce:
`shop_bound_by_hmac == shop_delivered_to_handler`

In reality: `shop_covered_by_hmac = ∅` (only the body bytes are signed), while `shop_delivered_to_handler = request.shop` (an attacker-controllable header). Because the header is never included in the signed material, any request body/HMAC pair that validates for shop A also validates for shop B if the attacker simply swaps the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value. The library's own test suite confirms the header, not the body, carries shop identity, and shows no header value is part of the HMAC computation: [5](#0-4) 

### Impact Explanation
This is a cross-tenant identity-binding failure: an unprivileged actor who has their own instance of the app installed (or otherwise obtains a valid signed webhook payload/HMAC, e.g. via a shared test/dev shop) can replay that same body with a forged `shop` header pointing at a victim merchant. Any host application that relies on `WebhookMetadata#shop` (populated straight from `Registry.process`) to determine which tenant's data to update, delete, or resync will act on the attacker's payload as if it originated from the victim shop — a cross-tenant access/data-integrity violation, since the tenant identity delivered to application code is not authenticated by the HMAC that this gem itself validates.

### Likelihood Explanation
Exploitation only requires: (1) the attacker's own valid HMAC/body pair from any shop with the app installed (trivial to obtain — install the app on any test store and capture one webhook delivery), and (2) the ability to POST to the app's public webhook endpoint with a modified header, which requires no secret knowledge, no access token, and no privileged role. This is a purely unprivileged-internet-user primitive, matching the "field acted on but not covered by the HMAC" analog class directly.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the signature (e.g., compute the signature over a canonical string containing both headers and body, matching how `AuthQuery#to_signable_string` binds `shop` into its own signature). At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant identification without an independent, out-of-band binding (e.g., cross-checking against the session/shop the client used to register the webhook).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw body and the `X-Shopify-Hmac-Sha256` header Shopify sends.
2. Replay the exact same body to the app's webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes the HMAC over the (unchanged) body via `Request#to_signable_string`, so `Utils::HmacValidator.validate` still returns `true`: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload was never signed by/for that shop, letting the attacker inject or trigger processing under the victim's tenant identity.
