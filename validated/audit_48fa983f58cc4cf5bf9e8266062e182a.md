## Title
Unbounded ancestry-walk loop in GRANDPA consensus verification allows unauthenticated denial of service - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
The GRANDPA consensus client's ancestry-chain walk (`AncestryChain::ancestry`) has no cycle detection or step bound. It is invoked on attacker-supplied, **unsigned** header data (`FinalityProof::unknown_headers`) before any cryptographic signature check occurs, as part of `pallet_ismp::handle_unsigned`, which "permits anyone [to] execute ISMP messages for free." A relayer can submit a crafted `ConsensusMessage` whose `unknown_headers` contain a `parent_hash` cycle, causing the walk to loop indefinitely (or until the node's memory/CPU is exhausted), exactly matching the "uncontrolled recursion"/unbounded-traversal bug class in the reference advisory, but here reachable pre-authentication via a permissionless dispatch call.

### Finding Description
`AncestryChain::ancestry` walks parent-hash pointers from a target hash back to a base hash using a `BTreeMap` built purely from the caller-supplied header list, with no visited-set / cycle guard and no maximum iteration bound: [1](#0-0) 

```
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

Because `Header::hash()` and `Header::parent_hash()` are independent, attacker-controlled fields of a SCALE-decoded header object, a relayer can submit two (or more) headers `A`, `B` where `hash(A)`'s content encodes `parent_hash = hash(B)` and `hash(B)`'s content encodes `parent_hash = hash(A)`. Once `current_hash` enters this cycle it never equals `base` and is always found in the map, so the `while` loop never terminates (or grows the `route` vector without bound before terminating), consuming unbounded CPU/memory.

Critically, this function is invoked **before signatures are checked**: [2](#0-1) 

`verify_grandpa_finality_proof` calls `headers.ancestry(from, target.hash())` at line 88 — using only the unauthenticated `finality_proof.unknown_headers` — and only afterwards calls `justification.verify(...)` which performs the ed25519 signature checks on the actual GRANDPA commit. The same unguarded pattern is also used inside justification verification itself for each precommit's route: [3](#0-2) 

The entry point is fully unprivileged: `pallet_ismp::Call::handle_unsigned` is documented to allow "anyone execute ISMP messages for free, provided they have valid proofs," and dispatches to `Self::execute(messages)`: [4](#0-3) 

The `ConsensusMessage` variant routes to `GrandpaConsensusClient::verify_consensus`, which decodes the attacker-supplied proof and calls `verify_grandpa_finality_proof` (for `StandaloneChain`) or `verify_parachain_headers_with_grandpa_finality_proof` (for `Polkadot`/`Relaychain`), both of which reach the vulnerable `ancestry()` call: [5](#0-4) [6](#0-5) 

This GRANDPA client is wired into production runtimes (`gargantua`, `nexus`) via `ismp_grandpa`, confirming reachability in-production.

### Impact Explanation
An unauthenticated relayer can submit a single `handle_unsigned` extrinsic carrying a fabricated GRANDPA consensus proof whose `unknown_headers` contain a parent-hash cycle. The node executing `validate_unsigned`/`execute` for this extrinsic will hang (or exhaust memory building an unbounded `route` vector) inside `AncestryChain::ancestry`, before any authority signature is validated. Because `validate_unsigned` runs during transaction-pool validation on every node that receives the transaction (propagated `unsigned` extrinsics are gossiped), this can degrade or halt block production / relayer nodes network-wide — a sustained denial of service against the message-delivery pipeline, consistent with "a route unable to deliver messages."

### Likelihood Explanation
Likelihood is high: constructing two headers with reciprocal `parent_hash` fields requires no cryptographic break — headers are plain SCALE-decoded structures and `parent_hash` is an arbitrary field independent of the header's own hash. No valid GRANDPA authority signature is required, since the vulnerable ancestry walk executes prior to `justification.verify(...)`. Submission is a single unsigned, feeless extrinsic (`decompress_call`/`handle_unsigned`), reachable by anyone able to submit a transaction to the network.

### Recommendation
Add a bounded traversal to `AncestryChain::ancestry`: track visited hashes (or cap iterations at `unknown_headers.len() + 1`) and return an error (e.g. `NotDescendent`) immediately upon revisiting a hash or exceeding the header-set size, rather than looping until an unbounded chain resolves. Apply the same fix to any other unauthenticated ancestry/graph walk driven by attacker-supplied header lists (e.g., the identical pattern inside `GrandpaJustification::verify_with_voter_set`).

### Proof of Concept
1. Craft header `A` with fields hashing to `H(A)`.
2. Craft header `B` whose `parent_hash = H(A)` and header `A` whose own `parent_hash = H(B)` (reciprocal cycle; both headers' content-derived hashes remain unaffected since `parent_hash` is just a payload field).
3. Build a `FinalityProof { block: H(A) (or H(B)), justification: <any minimally-decodable justification bytes>, unknown_headers: vec![A, B] }` and wrap in `ConsensusMessage::StandaloneChain(...)`.
4. Submit via `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(...)] }` (optionally through `pallet_call_decompressor::decompress_call`).
5. `verify_grandpa_finality_proof` calls `headers.ancestry(from, target.hash())` at `modules/consensus/grandpa/verifier/src/lib.rs:88`, which enters the `A ↔ B` cycle in `AncestryChain::ancestry` and never returns, hanging the validating/executing node before the (invalid) justification's signatures are ever checked.
