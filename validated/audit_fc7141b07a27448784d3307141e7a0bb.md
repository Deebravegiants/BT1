### Title
Webhook Shop-Domain Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verification performed in `ShopifyAPI::Utils::HmacValidator.validate` binds solely to the body bytes. The `shop` (tenant identity) that `ShopifyAPI::Webhooks::Registry.process` hands to application handlers is read straight from the unsigned `shopify-shop-domain`/`x-shopify-shop-domain` header, so the tenant field acted on by the app is not the field covered by the HMAC.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. The `shop` accessor is read independently from an HTTP header: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC only against `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` uses this validator as the sole authenticity gate, then forwards the unauthenticated `request.shop` value straight to the handler as the tenant identity: [4](#0-3) 

This breaks the identity binding `shop-used-by-handler == shop-covered-by-HMAC`. In reality, the equality that holds is `HMAC-verified-bytes == raw_body`, while `shop` attributed to that body is an independently attacker-controllable header value.

### Impact Explanation
An app that operates multiple merchant tenants (the normal multi-tenant embedded-app model this gem is built for) determines which tenant's data a webhook payload belongs to via `WebhookMetadata#shop`, which is populated straight from `request.shop`: [5](#0-4) 
Because that header is outside the signed material, an unprivileged attacker who controls one legitimate installed shop (attacker's own tenant, thus in possession of genuinely-HMAC'd webhook deliveries for their own body content) can replay that body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still succeeds because it never inspected the header, and the application-level handler processes attacker-supplied body content as if it originated from the victim tenant — a cross-tenant data-confusion/injection primitive.

### Likelihood Explanation
Exploitation requires only that the attacker operate one legitimate shop with the app installed (a normal, unprivileged, self-service action) and be able to submit an HTTP POST to the app's public webhook endpoint with custom headers — no access token, `client_secret`, or privileged account is required. The webhook body and HMAC are legitimately obtained by the attacker for their own tenant and are simply replayed with a modified header.

### Recommendation
Include the header-derived tenant identity (`shop`, `topic`, `api-version`) in the signable string, or independently verify that `request.shop` corresponds to a shop with an active, previously established session/installation before dispatching to handlers, rather than trusting the header value implicitly once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, triggering a genuine webhook delivery from Shopify with body `B` and header `shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker captures the raw POST (headers + body).
3. Attacker resends the identical body `B` and identical `shopify-hmac-sha256` value to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` matches (`to_signable_string` only depends on `B`), so `HmacValidator.validate` in `Registry.process` returns `true`. [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` and processes attacker-chosen body content under the victim's tenant identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
