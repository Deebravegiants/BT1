Audit Report

## Title
Bridge `outgoingToken` (external adapter credential) is stored in cleartext and disclosed to any authenticated low-privilege ("view" role) user via REST and GraphQL - ([File: core/bridges/bridge_type.go])

## Summary
Chainlink stores the `BridgeType.OutgoingToken` (the credential the node uses to authenticate to an external adapter) in plaintext in the `bridge_types.outgoing_token` column, and returns it in full via `GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, and the GraphQL `bridge`/`bridges` queries. None of these read paths enforce a role check beyond "authenticated," so a user provisioned with the lowest-privilege "view" role can retrieve the same secret that only "edit"/"admin" roles are meant to manage.

## Finding Description
`NewBridgeType` hashes `IncomingToken` but stores `OutgoingToken` as plaintext [1](#0-0) , and `CreateBridgeType` persists it directly into `outgoing_token` with no encryption [2](#0-1) , backed by a plaintext `outgoing_token` column [3](#0-2) .

On the REST side, `core/web/router.go` wraps `POST`/`PATCH`/`DELETE` bridge routes in `auth.RequiresEditRole`, but leaves `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` with no role wrapper at all beyond the base `Authenticate` middleware [4](#0-3) . Both `BridgeTypesController.Index` and `.Show` call `presenters.NewBridgeResource` unconditionally, and `BridgeResource` includes `OutgoingToken` in every response with no redaction based on caller role [5](#0-4) [6](#0-5) . The project's own RBAC test matrix confirms this is intentional/tested behavior: both GET bridge routes are marked `viewOnlyAllowed: true` [7](#0-6) , and `TestRBAC_Routemap_ViewOnly` asserts that a `UserRoleView` session gets a non-403/401 response for these routes [8](#0-7) . This is corroborated by `RequiresEditRole`, which exists and is used elsewhere to block `view`/`run` roles, but is simply not applied to the bridge GET routes [9](#0-8) .

On the GraphQL side, `Bridges`/`Bridge` queries call `authenticateUser`, which only checks session presence ("presence of user inherently provides 'view' access") and does not check role, unlike `authenticateUserCanEdit`/`authenticateUserCanRun` which are used elsewhere in the resolver package specifically to gate privileged actions [10](#0-9) [11](#0-10) . The `Bridge` GraphQL type declares `outgoingToken: String!` and `BridgeResolver.OutgoingToken()` returns the raw stored value with no redaction [12](#0-11) .

An analogous, unaddressed pattern exists for `ExternalInitiator.OutgoingSecret`/`OutgoingToken`, which are likewise stored and returned in plaintext to any session that can hit `GET /v2/external_initiators` (also `viewOnlyAllowed: true` in the same test table).

## Impact Explanation
This is a genuine node-level RBAC boundary violation: the "view" role is documented/tested as a restricted, read-only role, yet it can retrieve a credential (`outgoingToken`) intended to let only the Chainlink node itself authenticate to an external adapter. A view-role holder can reuse/exfiltrate this credential to impersonate the node against the external adapter, or use it outside its intended scope — this maps to CWE-522 (Insufficiently Protected Credentials) and a role-bypass information-disclosure impact category consistent with in-scope node API authorization findings.

## Likelihood Explanation
Exploitation requires only a "view"-role authenticated session (or API token) — the lowest-privilege role a node operator can intentionally provision for read-only dashboard access — and a single unmodified `GET` request or GraphQL query; no additional exploitation steps, timing, or race conditions are needed. This is fully reproducible against the current code paths shown above.

## Recommendation
- Strip/redact `OutgoingToken` (and `ExternalInitiator.OutgoingSecret`/`OutgoingToken`) from `BridgeResource`/`BridgeResolver` responses for sessions below "edit"/"admin" role, mirroring how `IncomingToken` is already only returned at creation time.
- Encrypt `outgoing_token` at rest and only decrypt it internally when the node performs the outbound bridge call.
- Add explicit role checks (`auth.RequiresEditRole` for REST, `authenticateUserCanEdit` for GraphQL) to the bridge/external-initiator read endpoints, or split responses into a public subset (name/url/confirmations) and a privileged subset (tokens) gated by role.

## Proof of Concept
1. As an admin, create a bridge (`POST /v2/bridge_types`) and note its `outgoingToken`.
2. As an admin, create a "view"-role user/API token (`sessions.UserRoleView`).
3. Authenticate as the view-role user and call `GET /v2/bridge_types` or `GET /v2/bridge_types/:BridgeName` — per `auth_test.go`'s `viewOnlyAllowed: true` marking, this returns HTTP 200 (not 401/403).
4. Observe the JSON response body contains `outgoingToken` with the plaintext secret, per `presenters.BridgeResource.OutgoingToken` (`core/web/presenters/bridges.go:18`).
5. Equivalently, run the GraphQL query `query { bridges(limit: 100) { results { name outgoingToken } } }` as the same view-role session and observe the same disclosure via `BridgeResolver.OutgoingToken()`.

}

		return RoleNotPermittedError{session.User.Role}

	}
