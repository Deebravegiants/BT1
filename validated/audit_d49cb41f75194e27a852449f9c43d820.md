### Title
Webhook shop-domain header not bound to HMAC signature allows cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhooks by computing an HMAC over the raw request body only. The `x-shopify-shop-domain` header — the value the library and any consuming app use to attribute the webhook to a specific merchant/tenant — is never included in the signed material. Because the HMAC secret (`Context.api_secret_key`) is a single, app-wide secret shared across every shop that installs the app (not a per-shop secret), any attacker who can obtain one valid `(body, hmac)` pair — e.g. by installing the app on their own store and triggering a webhook, or capturing any legitimately delivered webhook for any shop — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `shop-domain` header. `HmacValidator.validate` will still succeed because it only checks the body's HMAC, and `Registry.process` will dispatch the (attacker-controlled) payload to the handler tagged with the forged `shop`.

### Finding Description
The webhook verification flow is:

1. `Webhooks::Request#to_signable_string` returns only `@raw_body`, and never incorporates `shop`, `topic`, or `webhook_id`: [1](#0-0) 
2. `HmacValidator.validate_signature` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header — i.e., it authenticates only the body bytes, not the shop attribution: [2](#0-1) 
3. `Registry.process` validates the HMAC and then immediately trusts `request.shop` (derived purely from the unauthenticated `shop-domain`/`x-shopify-shop-domain` header) to build `WebhookMetadata` and dispatch to the app's handler: [3](#0-2) 
4. `shop` itself is read straight off the request header with no cross-check against the signed payload: [4](#0-3) 

The identity binding broken is: `hmac_valid(body, api_secret_key) == true` is treated as equivalent to `shop-domain header == authenticated tenant`, but the `shop-domain` field is never part of the signed payload. Since `api_secret_key` is one value per app (shared across every merchant that installs the app), any holder of one valid `(body, hmac)` pair for that app can relabel it to any other tenant.

### Impact Explanation
This breaks the shop/tenant identity binding that host applications rely on `WebhookMetadata#shop` to enforce data isolation between merchants. An attacker who installs the app on a shop they control (a normal, unprivileged action any Shopify merchant/developer can take) can harvest valid `(body, hmac)` pairs for webhook topics they can trigger, then replay them against the app's webhook endpoint with a forged `shop-domain`/`x-shopify-shop-domain` value pointing at a victim shop. Any handler logic keyed off `WebhookMetadata#shop` (e.g., updating that shop's stored data, revoking access, processing `shop/redact` or `customers/data_request`, adjusting billing/entitlements) executes as if it were a legitimate event from the victim tenant — a cross-tenant access/injection primitive.

### Likelihood Explanation
Likelihood is high for any app author who trusts `request.shop`/`WebhookMetadata#shop` as an authenticated tenant identifier, which is the natural and encouraged usage pattern of this library. No secrets or privileged access are required — only the ability to install the target app on an attacker-owned shop (or otherwise obtain one valid webhook body/HMAC pair) and issue a normal unauthenticated HTTP POST with a forged header.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or otherwise cryptographically tie the header-derived `shop` to the signature — e.g., verify the `shop-domain` header against a shop the merchant has actually completed OAuth for and have `HmacValidator`/`Webhooks::Request` refuse to trust `shop` unless it matches a session already on record, rather than deriving tenant identity purely from an unauthenticated header.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) to capture the exact `raw_body` and its valid `x-shopify-hmac-sha256` value — both are computed with the app's single, app-wide `api_secret_key`.
2. Attacker POSTs the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks `HMAC(api_secret_key, raw_body)`: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the app to process attacker-controlled data as if it belongs to `victim.myshopify.com`: [6](#0-5)
