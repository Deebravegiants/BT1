### Title
Webhook `shop` Identity Not Bound to HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity delivered to app webhook handlers exclusively from the unauthenticated `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, while the HMAC signature covers only the raw request body. Because a single app-level `api_secret_key` is shared across every merchant installation of the app, an attacker who installs the app on their own (attacker-controlled) shop can generate a validly-signed webhook, then replay the same body/HMAC pair while substituting an arbitrary victim shop domain in the header — producing a request that `ShopifyAPI::Webhooks::Registry.process` accepts as authentic and hands to the handler tagged with the victim's shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from a header that is not part of that signed string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC using `Context.api_secret_key` (the app's single shared secret across all shop installations), computed only from `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC checks out, and then trusts the unauthenticated header value as the tenant identity passed to the handler: [4](#0-3) 

The identity binding that should hold is:
`hmac == HMAC(secret, raw_body ∥ shop)` — i.e., the shop the handler trusts should be cryptographically bound to the same bytes that were verified.

Instead the gem enforces only `hmac == HMAC(secret, raw_body)`, and `shop` is taken from a header that travels outside the signed payload. Since `api_secret_key` is identical for every shop that installs the app (it is the app's own client secret, not a per-shop secret), any unprivileged user who installs the app on a shop they control can:
1. Trigger a real event on their own shop so Shopify sends them a legitimately-signed webhook (`raw_body`, `hmac`).
2. Replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint, replacing only the `X-Shopify-Shop-Domain` header with a victim merchant's domain.
3. `Utils::HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop` set to the victim's domain.

This lets the attacker inject arbitrary, attacker-chosen webhook payloads that the app's handler will process as if they came from the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an attacker with no privileges beyond installing the app on any shop (including a free/dev store) can forge events attributed to a different merchant's shop, causing cross-tenant data confusion (e.g., orders/customers/app-data reconciled against the wrong tenant, or malicious data injected into a tenant's records the attacker doesn't control). This matches the Critical "cross-tenant access" category, since the shop identity — the sole tenant discriminator the host application receives from this gem — is unauthenticated.

### Likelihood Explanation
Any internet user can install (or already control) a shop and get the app to send it a legitimately HMAC-signed webhook, since installation itself is unprivileged for public/dev apps. Capturing and replaying their own signed body against the public webhook callback URL (whose path is typically predictable/documented per the registered `path`) requires no secret material — the `api_secret_key` is never exposed to the attacker; they only need the fact that it is identical across tenants and that the header is unsigned.

### Recommendation
Bind the shop identity into the signed material, or independently verify it: e.g., require the host to confirm the shop referenced in `WebhookMetadata#shop` corresponds to a shop with a currently valid, previously-issued session/access token before trusting the payload, or include the shop domain in the value passed to `HmacValidator` so tampering with the header invalidates the signature. At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` is not authenticated by the HMAC and must not be used as a trust boundary without additional verification.

### Proof of Concept
```ruby
# Attacker owns "attacker.myshopify.com" and has installed the app there.
# Shopify sends a legitimately signed webhook for that shop:
raw_body = '{"id":1,"note":"pwned"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_api_secret_key, raw_body)

# Attacker replays the exact same body+hmac to the app's public webhook URL,
# but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled value
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation passes (it only checks raw_body),
#    handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: {...}))
#    is invoked with attacker-controlled data attributed to the victim shop.
