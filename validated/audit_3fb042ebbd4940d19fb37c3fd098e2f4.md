### Title
Accrual `scaled_to_original` overflow permanently freezes a high-TVL market before the borrow-index cap can engage — ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
The CVE-2024-21196 bug class is "low-privilege network attacker causes a hang or repeatable crash → complete denial of service." The analog in XOXNO Lending is the RAY-value ceiling in interest accrual: `accrue_step` computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`, and once `scaled × index / RAY` no longer fits `i128`, the call panics with `GenericError::MathOverflow`. The borrow-index cap (`MAX_BORROW_INDEX_RAY = 10^36`) only bounds the index itself; nothing bounds `supplied`/`borrowed × index`. Because every mutating pool verb runs `interest::global_sync` first (`Cache::load → global_sync → mutate → guards`), the market becomes permanently uncallable — no repay, withdraw, liquidation, `clean_bad_debt`, or `recapitalize` can execute — even though the index is still far below its cap, so the cap can never absorb the overflow. The codebase itself proves this is reachable and unrecoverable: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320` drives exactly this cliff and asserts `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all revert with `MathOverflow`.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs:60-61` unscales both totals through `scaled_to_original` (`common/src/rates/scaling.rs:14-16`), which is `scaled.mul(env, index)` — `mul_div_half_up` widens to `I256` but panics with `MathOverflow` when the result does not fit `i128` (`common/src/math/fp_core.rs:108-118`). `update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY` (`common/src/rates/index.rs:13-19`), but the cap applies to the index, not the value product: a market carrying ~1 billion whole units of an 18-decimal asset (`supplied ≈ 10^36` RAY) overflows once the index passes ≈170× RAY, well below the 10^36 cap. `docs/reference/invariants.md` INV-IDX-01 acknowledges "Debt-value overflow can still revert accrual before that ceiling is reached," i.e. the cliff is real and uncapped. Once crossed, every verb that accrues that market (supply, borrow, repay, withdraw, liquidate legs, `clean_bad_debt`, `recapitalize`, `update_indexes`) hits the same panic in `global_sync`, so the stored `last_timestamp` never advances and no time-based recovery exists.

### Impact Explanation
Permanent freezing of funds for the affected (hub, token) book: suppliers can never withdraw, borrowers can never repay, liquidators can never unwind unhealthy debt in that market, and governance `recapitalize`/`clean_bad_debt` also accrue first, so there is no recovery path short of a contract upgrade. This is not a fail-closed safety gate; it is an arithmetic trap in the shared accrual routine.

### Likelihood Explanation
Requires a whale-scale market and sustained high utilization so the borrow index compounds ~170× before the cap — the pinned test reaches it at 98% utilization on the steep stress curve over years, after governance-set caps were lifted to admit the position. Any unprivileged address can push utilization toward `max_utilization` via `borrow`, and once total value approaches the cliff no participant can stop it (even repaying accrues first). Capital- and time-intensive, hence Medium, matching the report's CVSS 6.5 availability-only profile.

### Recommendation
Bound the value product, not only the index: in `accrue_step`/`update_supply_index`, clamp or saturate `scaled × index` at the maximum representable RAY value (`MAX_RAY_VALUE`) rather than letting `mul_div_half_up` panic, or cap scaled `supplied`/`borrowed` at listing so `scaled × MAX_INDEX / RAY` always fits `i128`. Alternatively, make `global_sync` catch the overflow and still advance `last_timestamp` so exits remain possible.

### Proof of Concept
`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361` is a working PoC: supply 10^9 whole tokens of an 18-decimal asset, borrow 98%, advance time yearly until `update_indexes` reverts with `MathOverflow`, then observe `borrow_index < MAX_BORROW_INDEX_RAY` (cap never engaged) and that `withdraw`/`repay` both revert with the same error — a permanent market freeze.
