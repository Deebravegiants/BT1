### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable value from the raw body only, while the `shop` (and `topic`) values used by `Registry.process` to route and attribute the webhook are read from unauthenticated HTTP headers. Any attacker who can obtain one validly-signed webhook body/HMAC pair for an app (e.g., by installing the public app on their own store) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for any other shop that has the app installed, and the gem's HMAC check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it only authenticates the body bytes: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then forwards the unauthenticated `request.shop` (and `request.topic`) directly to the app's handler as the tenant identity for the payload: [4](#0-3) 

The identity binding that should hold is: `shop asserted in the signed request == shop the app acts on`. Because the HMAC only covers `@raw_body`, that equality is never enforced — `shop` can be swapped freely without invalidating `hmac`, as long as the attacker supplies a body/HMAC pair that was legitimately signed with the app's own `client_secret` for *some* shop.

### Impact Explanation
A public app is installed on many merchants' shops but shares one `api_secret_key`. An unprivileged user who installs the app on their own shop can trigger a real webhook (e.g., `orders/create`) with an attacker-controlled body and topic and thereby obtain a validly-signed `(raw_body, hmac)` pair signed with the app's shared secret. Because `shop` is excluded from the signed content, that same request can be replayed against the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop. `Registry.process` will accept it (HMAC still validates) and hand the handler a `WebhookMetadata` claiming the (attacker-chosen) body belongs to the victim shop, causing the host application to act on/store attacker-controlled data under another tenant's identity — a cross-tenant data integrity/confidentiality break rooted entirely in this gem's webhook verification contract.

### Likelihood Explanation
Exploitation requires only: (1) installing the target public app on an attacker-controlled shop (normal, unprivileged action), (2) capturing one legitimate webhook delivery, and (3) resending it with a modified shop-domain header to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or any privileged account is required, making this practically reachable by any external user of a public Shopify app built on this gem.

### Recommendation
Bind the shop domain (and topic) into the authenticated material used by `HmacValidator`, or have `Registry.process` cross-check `request.shop` against a shop that is actually known/expected for the given webhook subscription/session before invoking the handler, so that the `shop` value acted upon is provably the same one the signature was issued for.

### Proof of Concept
1. Install the target public app on attacker-owned shop `attacker.myshopify.com`; trigger `orders/create` to receive a webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Replay the exact same body `B` and `H` to the app's public webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header; `Utils::HmacValidator.validate` recomputes the HMAC over `B` only and it matches `H`, so `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's body `B`, even though `victim-shop` never sent this webhook.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
