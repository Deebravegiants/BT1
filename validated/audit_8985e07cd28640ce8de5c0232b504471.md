## Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then dispatches the handler using the `shop` value taken from an HTTP header that is never covered by that signature. Any party who can obtain one valid `(raw_body, hmac)` pair for a webhook sent to the app (e.g., the legitimate owner of any single shop that has the app installed, capturing the webhook Shopify sends to their own endpoint) can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` header for a different tenant's domain. The HMAC check still passes because only the body is signed, and the (forged) shop value is what gets handed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates authenticity like this: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For a webhook `Request`, `to_signable_string` returns only the raw HTTP body — none of the Shopify-supplied headers are included: [3](#0-2) 

The `shop` value that is subsequently trusted and forwarded to the app's handler is read straight from the (unsigned) `shopify-shop-domain` / `x-shopify-shop-domain` header: [4](#0-3) 

and is passed into `WebhookMetadata` given to the handler without any additional cross-check against the signed payload: [1](#0-0) 

The identity binding that should hold is:
`shop asserted to the handler == shop the HMAC-signed bytes actually originated from`

Because the HMAC only covers `@raw_body`, this equality is not enforced — the `shop` header can be swapped for any value while keeping the same, still-valid, `(body, hmac)` pair.

### Impact Explanation
An attacker who is nothing more than the legitimate operator of one shop that has the vulnerable app installed can capture a real webhook (with a valid HMAC computed by Shopify using the app's real secret) sent to the app's webhook endpoint, then resend that exact body and HMAC to the same endpoint while changing only the `X-Shopify-Shop-Domain` header to point at a victim shop. `Registry.process` will accept it as authentic (HMAC still validates) and invoke the app's webhook handler believing the event originated from the victim shop. Any app logic that trusts `WebhookMetadata#shop` to select which tenant's data to create, update, or delete is exposed to cross-tenant data injection/corruption — a cross-tenant access violation.

### Likelihood Explanation
Exploitation only requires being able to install the app on any single shop (an unprivileged, self-service action available to any merchant) and the ability to POST an HTTP request to the app's own webhook endpoint with attacker-chosen headers — no access to `api_secret_key`, tokens, or the target shop is needed. The webhook body content does not need to be attacker-controlled for many topics (e.g., `app/uninstalled`, `shop/update`) to already cause meaningful cross-tenant effects.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the asserted `shop` header to the signed body (e.g., verify the shop returned by a separate authenticated lookup, or require the `shop` to be validated against a registered/expected value for the specific webhook subscription) before passing it to the handler in `Registry.process`.

### Proof of Concept
1. Register the app on `attacker-shop.myshopify.com` and receive a genuine webhook, capturing the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` (both are otherwise unremarkable to obtain since the attacker is the legitimate recipient of their own shop's webhooks).
2. Replay the request to the same app webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only, which matches `H`, so `Registry.process` proceeds.
4. The handler receives `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's parsed body>)`, causing the app to act on victim-shop's tenant data using attacker-supplied content.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
