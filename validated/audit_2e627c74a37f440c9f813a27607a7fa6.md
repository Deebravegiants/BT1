### Title
Webhook shop identity is not bound to the HMAC signature, allowing a shop-domain spoofing / cross-tenant replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read from unauthenticated HTTP headers and passed downstream to application handlers as trusted identifiers. Because the app's `api_secret_key` is a single shared secret across every shop that installs the app, any merchant who installs the app can capture a legitimate `(raw_body, hmac)` pair from their own webhook deliveries and replay it with a forged `x-shopify-shop-domain` header identifying a different, victim shop. The HMAC still validates, so `ShopifyAPI::Webhooks::Registry.process` accepts the request and calls the host application's handler with attacker-controlled shop identity.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and checks the signature over `verifiable_query.to_signable_string`. For webhooks, this string is defined as: [1](#0-0) 

which is only `@raw_body`. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never part of the signable string: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC and, once it passes, forwards the unauthenticated `request.shop` value straight into the handler's data object with no further binding check: [4](#0-3) 

Contrast this with the OAuth callback path, where the equivalent identity field (`shop`) *is* included in the signable string (`AuthQuery#to_signable_string`) and is therefore cryptographically bound to the HMAC: [5](#0-4) 

For webhooks no such binding exists. The equality that should hold — `shop asserted in the signed payload == shop the handler acts on` — is broken: the signature proves only "this body was produced with the app's secret," not "this body belongs to shop X." Since `api_secret_key` is shared by the app across all its installations, any unprivileged merchant who installs the app on their own store can:
1. Receive a legitimate webhook delivery for their own shop, capturing a valid `(raw_body, x-shopify-hmac-sha256)` pair.
2. Replay that exact body/HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain.
3. `Utils::HmacValidator.validate` still returns `true` (it never inspects headers), so `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with the forged victim shop identity.

### Impact Explanation
Any application built on this gem that uses the webhook `shop` field to key session/tenant lookups (a documented, standard integration pattern — see `docs/usage/oauth.md` and the `shopify_app` reference storage) will process attacker-fabricated events attributed to an arbitrary victim shop. This crosses a tenant boundary: an unprivileged merchant of Shop A can inject data or trigger business logic (e.g., order/customer webhook handling, mandatory-topic handling such as `app/uninstalled` or GDPR topics) that the host app believes originates from Shop B, without ever needing Shop B's access token or session. This matches the "cross-tenant access" impact class via a broken shop-identity binding.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (unprivileged) merchant who has installed the target app on their own store — a normal, low-privilege action available to any internet user for public apps — and the ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or any victim-owned secret is required, and the replayed body/HMAC pair is obtained through entirely legitimate means (the attacker's own webhook deliveries).

### Recommendation
Bind the shop (and ideally topic/webhook id) identity to the cryptographic verification, not just the raw body:
- Include the shop domain (and other headers the application intends to trust) in the value that is HMAC-verified, or
- Require and document that consuming applications must additionally verify that the header-derived `shop` corresponds to a shop with an existing, previously-established session/installation record before trusting `WebhookMetadata#shop`, explicitly noting that the shop header is *not* covered by the HMAC in this gem.
- At minimum, update `Registry.process`/`Request` to make this trust boundary explicit and fail closed if callers rely on `shop` without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, receiving a legitimate webhook delivery:
   - `raw_body = '{"id":123,...}'`
   - `x-shopify-hmac-sha256 = Base64(HMAC-SHA256(api_secret_key, raw_body))`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and same `x-shopify-hmac-sha256`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create` (or any topic they choose)
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks `raw_body` (unchanged), and `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`.
4. Host application logic keyed on `data.shop` now processes attacker-controlled data as if it came from `victim-shop.myshopify.com`.
