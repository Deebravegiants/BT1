## Finding: POA bridge withdrawal status is matched only by `assetId`, ignoring per-withdrawal index/amount/destination

This is a real, in-scope issue that is structurally analogous to the reported Celo `revokeVotes` bug class: an equality that should hold (the reported on-chain outcome corresponds to the specific withdrawal instance being polled) does not hold once the caller provides more than one withdrawal of the same asset in a single call — and nothing in the SDK enforces or fails on that condition, it silently returns a mismatched result.

### Title
Withdrawal status/hash misreport when multiple same-asset withdrawals are batched - (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Finding Description
`PoaBridge.describeWithdrawal` retrieves the list of withdrawals for a NEAR tx hash and finds "the" matching one using `findMatchingWithdrawal`, which filters **only by `assetId`** and ignores the withdrawal's `index`, `amount`, and `destinationAddress`: [1](#0-0) [2](#0-1) 

The same pattern (documented as a known limitation) exists in the internal-utils helper used elsewhere: [3](#0-2) 

When a caller batches two or more withdrawals of the same `assetId` (e.g. two different destination addresses, or two different amounts) in a single `processWithdrawal`/`signAndSendWithdrawalIntent` call, `createWithdrawalIdentifiers` assigns each withdrawal an `index` per bridge route: [4](#0-3) 

But `describeWithdrawal`/`findMatchingWithdrawal` never uses that `index` — `Array.prototype.find` returns the *first* withdrawal entry whose `near_token_id` matches, regardless of which of the batched requests is actually being polled. `waitForWithdrawalCompletion`/`waitForWithdrawalCompletion.test.ts` then resolve each of the caller's promises independently but with data drawn from whichever entry `find` happens to hit: [5](#0-4) 

So the equality broken is: *"the completion status/txHash reported for withdrawal request N corresponds to the on-chain outcome of withdrawal request N"*. Once two requests share an `assetId`, both polling calls converge on the same underlying withdrawal record — the status/hash of withdrawal A can be reported as the status/hash of withdrawal B (a different amount and/or destination address).

### Impact Explanation
This falls under "a status or hash misreport making an integrator credit or refund twice" (High). Concretely:
- An integrator polling two same-asset withdrawals with different destination addresses could see both marked `completed` with the *same* `transfer_tx_hash`, even though only one transfer actually executed on-chain, leading it to credit/confirm delivery for a destination that never received funds.
- Conversely, a withdrawal that legitimately failed/is pending could be reported `completed` because `find` picked the other batched withdrawal's `COMPLETED` record first.

### Likelihood Explanation
Likelihood is moderate: it requires the caller (integrator, or an end-user-driven multi-withdrawal request) to submit ≥2 withdrawals of the same POA-bridge `assetId` within one `withdrawalParams` array/one NEAR tx — which is a supported public API shape (`processWithdrawal`/`signAndSendWithdrawalIntent` accept arrays), not a contrived edge case. The code authors were aware of the limitation (see the inline `NOTE:` comments) but the SDK does not reject or warn on this input; it silently returns wrong data.

### Recommendation
- Reject/validate batches containing multiple withdrawals with the same `assetId` for the POA bridge route (fail fast with a clear error), or
- Disambiguate matching using amount/destination in addition to `near_token_id` (as the code comment itself suggests — sort both sides by amount since fees are equal for the same token), ensuring `describeWithdrawal` only ever returns a status belonging to the specific withdrawal instance being queried.

### Proof of Concept
1. Call `sdk.processWithdrawal` with `withdrawalParams: [w1, w2]` where both use the same POA-bridge `assetId` (e.g. `nep141:btc.omft.near`) but different `destinationAddress`/`amount`.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` respectively but both share the bridge and `assetId`.
3. When the POA indexer returns the withdrawals array containing both underlying transfers, `PoaBridge.describeWithdrawal` for both `wid`s independently calls `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which returns the **same** first array element for both, regardless of `index`.
4. Both `createWithdrawalCompletionPromises` entries resolve using that one entry's `status`/`transfer_tx_hash`, even though the two requests correspond to different on-chain transfers. [1](#0-0)

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
