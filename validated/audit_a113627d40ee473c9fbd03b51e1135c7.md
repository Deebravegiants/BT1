### Title
Webhook HMAC only covers the request body, not the `shop-domain`/`topic`/`webhook-id` headers, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never included in the HMAC-signed material.

### Finding Description
`Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)`, which calls `verifiable_query.to_signable_string` — for `Webhooks::Request` this is just the raw body: [4](#0-3) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled straight from the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers with no cryptographic binding to those values: [5](#0-4) 

After HMAC validation succeeds, `Registry.process` forwards `request.shop` (and `request.topic`/`request.webhook_id`) unauthenticated into `WebhookMetadata`, which is handed to the host application's handler as the authoritative tenant identity for the event: [3](#0-2) 

The identity binding broken is: `shop header value` (used by the handler to attribute the event to a tenant) `≠ bytes actually covered by the HMAC` (only the JSON body). Because the same `api_secret_key`/`client_secret` is shared across every shop that installs a given app, a valid `(body, hmac)` pair computed for one merchant's webhook delivery remains valid HMAC-wise even if the `x-shopify-shop-domain` header is swapped to a different merchant's domain — the signature never covered that field in the first place.

### Impact Explanation
An attacker who controls one shop where the target app is installed can generate legitimate webhook deliveries with attacker-influenced body content (e.g., by creating orders/products with attacker-chosen data), capture the resulting `(raw_body, hmac)` pair, and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still passes because only the body is checked, and `Registry.process` dispatches the attacker-crafted body to the handler while asserting it belongs to the victim tenant. Any host application logic that trusts `WebhookMetadata#shop` as an authenticated tenant identifier (e.g., to look up the victim's session/access token and act on their store, or to write attacker data into the victim's tenant record) is exposed to cross-tenant data injection — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker operate their own store with the vulnerable app installed (a normal, low-privilege merchant relationship) — no access to `api_secret_key`, access tokens, or TLS interception is needed. The header rewrite is a trivial HTTP replay.

### Recommendation
Bind the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) into the signed material verified by `HmacValidator`, or otherwise have `Webhooks::Request#to_signable_string` incorporate these headers so any tampering invalidates the HMAC. At minimum, document and encourage host applications to cross-check `request.shop` against an independently known/expected shop before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`.
2. Attacker triggers a webhook (e.g., `orders/create`) with attacker-controlled JSON body `B`; Shopify delivers it with headers including `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays this exact body `B` and HMAC value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) recomputes the HMAC over `B` only, which still matches, so validation succeeds.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: attacker's parsed body ...)` to the app's handler, which believes attacker-controlled data originated from the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
