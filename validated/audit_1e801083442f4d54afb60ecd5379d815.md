### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while the `shop` accessor is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Utils::HmacValidator.validate` only checks that `hmac` matches an HMAC-SHA256 of `to_signable_string` computed with `Context.api_secret_key` [3](#0-2) . This is the exact bug class described in the report: a field (`shop`) that is acted upon by the application (via `Registry.process`, which passes `data.shop` to the registered handler, as seen in `test/webhooks/registry_test.rb` lines 271-278) is not bound into the value that is cryptographically verified (`to_signable_string` = raw body only).

### Finding Description
`api_secret_key` is a single, static per-app secret shared across every shop/tenant that installs the app — it is not shop-specific. Consequently, any authority (merchant/tenant A) that has legitimately installed the app can receive a real, validly-HMAC-signed webhook for their own shop. Because the HMAC only covers the raw body (`to_signable_string` returns `@raw_body`) and not the `shopify-shop-domain` header, that authority can replay the exact same body + HMAC to the app's webhook endpoint while substituting the `shop-domain` header with a different tenant's (victim B's) shop domain. The signature will still validate successfully because it was computed with the same shared `api_secret_key`, and `to_signable_string` never included the shop header in the signed payload.

This directly parallels the analog required by the rules: "a field acted on but not covered by the HMAC" — here, `shop` is read and forwarded to the application's handler (`Registry.process`) as trusted tenant-identifying data, but it is never part of the signed bytes.

### Impact Explanation
This breaks the identity binding `shop_header == shop_that_signed_the_body`. An app author who relies on the gem's parsed `shop` attribute to select per-tenant state, credentials, or data (a documented, expected usage pattern of `ShopifyAPI::Webhooks::Request`) can be tricked into writing/processing data intended for shop A under the identity of shop B, i.e. cross-tenant data corruption/injection. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
High. Any single merchant who installs the app (a normal, unprivileged action requiring no special access) automatically has a stream of legitimately-signed webhooks for their own shop and can trivially replay them with a modified header, no `client_secret` or leaked credential is required — only receipt of the app's own genuine webhook traffic for their tenant.

### Recommendation
Bind the tenant identity into the signed payload verification, e.g., include the `shop-domain` header value in `to_signable_string`, or require verification of the `shop` header against the shop that owns the session/state being mutated before trusting the `shop` value the handler receives. At minimum, document/enforce that `Registry.process` callers must not treat the header-derived `shop` as authenticated for tenant-scoping decisions unless it is cryptographically bound to the body.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the target app; the app registers webhook subscriptions.
2. Shopify sends a legitimate webhook to the app's endpoint with headers:
   `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body with api_secret_key>`, and some `raw_body`.
3. Attacker captures this request and replays it to the same endpoint, changing only the header:
   `x-shopify-shop-domain: victim.myshopify.com` (keeping the same `raw_body` and `x-shopify-hmac-sha256`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (== `raw_body` only) — validation succeeds since the body/HMAC pair is unchanged [4](#0-3) .
5. The registered handler is invoked with `data.shop == "victim.myshopify.com"` [2](#0-1) , causing the host application to process/store attacker-controlled webhook content under victim's tenant identity.
