### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, then dispatches to the app's handler using the `shop` and `topic` values taken from HTTP headers that are never included in the signed material. Any party who can obtain one genuine `(raw_body, hmac)` pair signed with the app's shared `client_secret` (e.g., by installing the app on their own store and receiving a real webhook) can replay that body with forged `shop`/`topic` headers, causing the app to process attacker-chosen webhook content while attributing it to an arbitrary victim shop or topic.

### Finding Description
`Registry.process` validates authenticity like this: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC using only `verifiable_query.to_signable_string`: [2](#0-1) 

For webhook `Request`, `to_signable_string` returns solely the raw HTTP body — none of the identifying headers are part of the signed content: [3](#0-2) 

Yet `topic` and `shop` (parsed straight from unauthenticated headers) are exactly the fields passed on to the handler as the trust anchor for tenant/topic identification: [4](#0-3) 

This breaks the equality the HMAC is supposed to guarantee: `hmac_verified(raw_body)` is treated as if it also implies `shop_header == originating_shop` and `topic_header == originating_topic`, but neither is true. Because Shopify webhook HMACs are computed with the single `client_secret` shared by the app across **all** shops that install it, any shop that installs the app can legitimately receive a valid `(raw_body, hmac)` pair for content it can influence, then resend that exact body/HMAC to the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` header. `HmacValidator.validate` will still return `true` because it never inspects those headers.

### Impact Explanation
This crosses a tenant boundary without any privileged credential: an unprivileged internet user who merely installs the app on their own (attacker-controlled) shop can cause the host application to process fabricated webhook events "as" a different, victim shop or under a different topic than actually occurred. Since host apps commonly key session/access-token lookups and business logic off `WebhookMetadata#shop`/`#topic`, this enables cross-tenant data confusion/spoofing (e.g., triggering shop-scoped logic, mandatory compliance topics, or reprocessing data under another merchant's identity) — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) install the app on an attacker-controlled shop to obtain one genuine webhook delivery (readily available to any developer/merchant who can install a public/development app), and (2) POST the captured raw body with the original HMAC header but forged `shop-domain`/`topic` headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required.

### Recommendation
Do not trust `shop`/`topic` (or any other header) as authenticated identity once only the body HMAC has been checked. Bind the claimed shop to a value verified independently — e.g., confirm `request.shop` corresponds to a session/shop the app actually has installed and expects webhooks for, and/or require handlers to cross-check the claimed topic against out-of-band webhook subscription records — before acting on `WebhookMetadata`.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw POST body plus its `X-Shopify-Hmac-Sha256` header (valid, since signed with the app's real `client_secret`).
2. Replay the exact same body and HMAC header to the app's public webhook endpoint, but replace `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com` and/or change `X-Shopify-Topic` to a different subscribed topic.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — succeeds, since only the (unmodified) body is checked — see [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's chosen `topic`, even though the request never originated from `victim.myshopify.com`.
