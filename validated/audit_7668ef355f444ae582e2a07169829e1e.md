### Title
Round-trip buy/sell rounding drift can underflow `assetReserve − virtualLtReserve` and permanently brick graduation - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate`, `Bonding.previewLtUntilGraduation`, and `Bonding._prepareGraduationLiquidity` all compute `realLtRaised` / `ltFromPair` as a plain Solidity subtraction `assetReserve - _launchTimeVirtualLtReserve(...)` with no bounds check that `assetReserve` is actually `>=` the derived virtual reserve [1](#0-0) , [2](#0-1) , [3](#0-2) . `Router._computeBuy`/`_computeSell` compute `tokensOut`/`assetOut` via floor-division against `Pair.k()` [4](#0-3) , [5](#0-4) , and `Pair.swap` only enforces the loosened `(newTokenReserve+1)*(newAssetReserve+1) >= k` check instead of the exact `newTokenReserve*newAssetReserve >= k` [6](#0-5) . This is exactly the "`+1` K slack" the project's own docs flag as a live bug-class location [7](#0-6) . Because every sell resolves in the trader's favor by up to the floor-rounding remainder each time, an unprivileged trader can repeatedly buy and sell back small amounts through `Zap.buy`/`Zap.sell` (which route straight into `Bonding.buy`/`Bonding.sell` → `Router.sell`/`Router.buy`) to erode the pair's stored `assetReserve` down to, and then below, the recovered `virtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()` [8](#0-7) .

### Finding Description
`virtualLtReserve` is a fixed, launch-time-derived floor value, and the protocol's entire donation-resistance design assumes `assetReserve >= virtualLtReserve` always holds so that `assetReserve - virtualLtReserve` safely yields the real LT raised [9](#0-8) . However, nothing in `Router.sell`/`Pair.swap` guarantees this invariant is preserved exactly — the K-invariant check in `Pair.swap` allows `newTokenReserve` and `newAssetReserve` computed by the Router's floor-division formulas to *shrink* effective K slightly on every trade, and this slack compounds across independent transactions because each trade's `_computeSell`/`_computeBuy` call is recomputed from the pair's *current* (already-drifted) stored reserves rather than from an ideal continuous curve.

An attacker/trader who repeatedly buys a small amount and immediately sells it back (a fully permissionless action reachable via `Zap.buy` + `Zap.sell`, both of which any wallet can call) accumulates a systematic 1-wei-scale advantage per round trip at the pool's expense. Given enough iterations (trivially batchable in a single transaction via a loop, or across many transactions by any bot), the stored `assetReserve` can be pushed strictly below `virtualLtReserve`. Once that happens:

- `Bonding.canGraduate` reverts with an arithmetic-underflow panic instead of returning `false` [10](#0-9) .
- `Bonding.previewLtUntilGraduation` likewise reverts [11](#0-10) .
- `_executeBuy`'s inline post-buy `canGraduate()` check (called at the end of every buy) now always reverts, so **every subsequent buy on that token permanently reverts**, and the USD trigger can never fire again.
- The token can only "graduate" via the supply trigger (`tokenBalance() == 0`), and if that never happens (e.g., liquidity remains, low-volume token), the token is permanently stuck in `Lifecycle.Curve`.

This is the direct Solidity analog of CVE-2016-4447: a subtraction/pointer-arithmetic operation performed on attacker-influenceable bounds without validating that the subtrahend cannot exceed the minuend, causing a crash (revert / permanent DoS) reachable purely through malformed/adversarial input shaped by a normal external actor — here, adversarially sequenced buy/sell calls instead of a crafted XML element declaration.

### Impact Explanation
Once `assetReserve` is driven below `virtualLtReserve` for a token, that token can become permanently un-graduatable via the USD trigger, and any buy that would otherwise cross the USD threshold instead causes the whole `Bonding.buy` transaction to revert (since `canGraduate` is called inline at the end of every buy). This permanently freezes:
- The token's `LP_RESERVE` (250M tokens) held in `Bonding`, which can only be released through `_prepareGraduationLiquidity`/`finalizeGraduation`.
- All curve-raised LT locked in the `Pair`, since `Router.graduate` (which drains it) is only reachable from a successful `_prepareGraduationLiquidity` call.
- Ongoing trading on that token if the supply trigger is not otherwise satisfied, since every buy attempts to re-check `canGraduate` and reverts.

This is a permanent freezing-of-funds condition, satisfying the "Validate" bar (permanent freezing of trader/creator/LP funds) at High severity.

### Likelihood Explanation
Reachable by any unprivileged wallet solely via `Zap.buy`/`Zap.sell` (or `Bonding.buy`/`Bonding.sell` through an allowlisted router), with no special privileges required. The exact number of round trips needed depends on the initial gap between `assetReserve` and `virtualLtReserve` (which is smallest immediately after launch, before large buys accumulate real LT raised, and can be re-approached after heavy selling), making very-early-post-launch tokens (right after the mandatory `$20` seed buy) the most exposed. Executing many round trips in a single transaction (a loop calling `Zap.buy`/`Zap.sell` repeatedly) is gas-bound but technically unrestricted.

### Recommendation
- Add an explicit invariant check in `Router.sell`/`Pair.swap` (or directly in `_computeSell`) that rejects any swap that would push `assetReserve` below the pair's recoverable `virtualLtReserve` (`k / launchedToken.TOTAL_SUPPLY()`), reverting the trade rather than allowing silent drift.
- Tighten `Pair.swap`'s K-invariant check from `(newTokenReserve+1)*(newAssetReserve+1) >= k` back to the exact `newTokenReserve*newAssetReserve >= k`, removing the slack that permits repeated favorable rounding.
- In `Bonding.canGraduate`/`previewLtUntilGraduation`/`_prepareGraduationLiquidity`, guard the subtraction with a `>=` check and treat an unexpected underflow condition (`assetReserve < virtualLtReserve`) as "not graduatable" rather than allowing a panic revert, so a single stuck token cannot brick itself out of ever being checked again.

### Proof of Concept
1. Launch a token via `Zap.createToken` with the minimum seed (`Zap.MIN_SEED_USDC`), so `assetReserve` starts only marginally above `virtualLtReserve`.
2. From any unprivileged wallet, repeatedly call `Zap.buy(token, smallUsdcAmount, 0, referrer)` immediately followed by `Zap.sell(token, tokensJustReceived, 0)` in a loop (single tx or many txs).
3. Each round trip nets the trader a small floor-rounding advantage from `Router._computeSell`'s `assetOut = reserveAsset - (k / newReserveToken)` combined with `Pair.swap`'s loosened K check, incrementally lowering the pair's stored `assetReserve` relative to the fixed `virtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()`.
4. After sufficient iterations, `assetReserve` drops below `virtualLtReserve`. The next call to `Bonding.canGraduate(token)` (or any buy, since it's invoked inline in `_executeBuy`) reverts with an arithmetic underflow panic instead of returning `false`, permanently freezing the token's curve state, its `LP_RESERVE`, and any curve-raised LT.

```text
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
```

```markdown
## Graduation — Two-Phase, Dynamic LP Seeding (Read This Before Touching Graduation Code)

This is the most bespoke piece of the protocol. Full rationale + invariants live in [`docs/contracts-scope.md`](../../docs/contracts-scope.md#graduation); the short version:

- **Two-phase split.** Graduation is split across two transactions to fit HyperEVM's small-block (~2M gas) ceiling.
  - **Phase 1: `_enterGraduating`**, fired inline by the threshold-crossing buy (~150-200k of additional gas on top of the buy). Drains the curve, computes the LP-bound amounts, caches them in `pendingGraduation[token]`, flips `lifecycle: Curve → Graduating`, freezes trading. Emits `TokenGraduating`.
  - **Phase 2: `finalizeGraduation`**, **permissionless** big-block tx (~2.5M gas). Creates the HyperSwap pair if needed, seeds liquidity across the empty, donation, and hostile mint-pre-seed regimes, locks LP, flips `lifecycle: Graduating → Graduated`. Emits `TokenGraduated`. A Cloudflare Worker keeper handles the happy path; anyone can call to rescue a stuck token.
- **Brick resistance.** Phase 2 must never revert under any pre-seed shape. Empty/donation pairs use direct pair calls; hostile mint pre-seeds use direct `pair.swap` for rebalance plus router `addLiquidity` for the canonical quote-based deposit. Tested by `test_brick_resistance_frontRun_dust_seed` in [`test/TwoPhaseGraduation.t.sol`](test/TwoPhaseGraduation.t.sol).
- **Virtual token reserve.** At launch, `Pair.reserve0 = totalSupply (1B)` while only `curveSupply = 75%` (750M) of real tokens are transferred to the pair. The other 250M (`LP_RESERVE`) sit in `Bonding` for graduation. This extends the curve beyond the sellable supply, which is what makes dynamic LP seeding work cleanly.
- **Dual trigger.** Phase 1 fires on whichever hits first: `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` (USD, for LT pumps) or `IPair.tokenBalance() == 0` (supply, for flat/bear markets). The USD trigger reads STORED reserves so direct LT donations to the pair don't count toward the threshold; the launch-time `virtualLtReserve` is recovered on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()` (K is set once at mint and never modified by `Pair.swap`). The supply trigger reads live `tokenBalance()`, which is donation-resistant in the opposite direction: token donations only INCREASE the balance and can never satisfy `== 0`, and any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`.
- **Zero-gap LP seeding.** `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve` (the real LT raised by the curve, donation-immune; `virtualLtReserve` is derived from `Pair.k() / Token.TOTAL_SUPPLY()`) and `tokensForLP = ltFromPair × storedTokenReserve / storedAssetReserve` at end-of-phase-1, caching the result. Phase 2 uses the cached value verbatim, so the curve→LP price match is invariant under the tx split. Donated LT stays in the curve pair under the trust assumption that `BONDING_ROLE` is only ever held by `Bonding` and `Bonding` won't call `Router.graduate` again post-graduation.
- **Parabola invariant.** With `V_t_init = totalSupply` and `curveSupply = 75%`, the function `tokensForLP(sold) = sold·(S−sold)/S` peaks at `S/4 = LP_RESERVE`. The cap in `_prepareGraduationLiquidity` is defensive — it can never bind in normal operation.
- **Overflow buy cap.** `Router.buy` caps `tokensOut` at the pair's real balance and back-calculates the LT consumed, so the last buy cannot exceed remaining supply. `Zap.buy` returns the unused LT (`ltMinted - amountInUsed`) directly as LT — not redeemed, to avoid re-incurring the LT redemption fee on dust — while unconverted USDC and the fee over-charge are refunded in USDC. `Bonding.buy` returns `(tokensOut, amountInUsed)` for this reason.

**If you change `_enterGraduating`, `finalizeGraduation`, `_prepareGraduationLiquidity`, `_seedUniswapV2Direct` (or any of its `_seedRebalancing` / `_pairRebalance` / `_routerDepositAndDispose` / `_noFeeSwapInput` helpers), `Router.buy`'s capping logic, or the seeding in `_deployAndSeed`:** you MUST re-run `test/GraduationInvariants.t.sol`, `test/TwoPhaseGraduation.t.sol`, and `test/NoFeeSwapInput.t.sol`. All 7 zero-gap invariants must still pass; the phase-1-fits-in-small-block budget assertion (1.8M) must still hold; the brick-resistance regression test must still pass. These invariants are the product — do not loosen their assertions to make a change go green.
```

```markdown
`_graduate()` performs, in order:

1. Read `(reserve0, reserve1)` from the Pair **before** any state mutation.
2. Burn any unsold real curve tokens from the pair (`unsoldBurned`). This also burns any tokens donated to the pair via direct ERC20 transfer.
3. Recover `virtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()` and compute `ltFromPair = reserve1 - virtualLtReserve` — the real LT raised by the curve, excluding the launch-time virtual seed AND any LT donated to the pair. Drain exactly that amount via `Router.graduate(token, ltFromPair)`. Donated LT remains in the curve pair, reachable only via `Pair.transferAsset` which is gated by `Router`'s `BONDING_ROLE`.
4. Compute `tokensForLP = (ltFromPair × reserve0) / reserve1` — the unique amount that sets the LP price `ltFromPair / tokensForLP` equal to the last curve price `reserve1 / reserve0`. Capped at `lpReserveTotal` as a defensive guard (parabola math proves `tokensForLP ≤ lpReserveTotal` by construction).
5. Burn `lpReserveTotal − tokensForLP` from `Bonding`'s held reserve (`lpBurned`).
6. `addLiquidity(tokensForLP, ltFromPair)` on HyperSwap V2 → LP tokens go to `LPLock`.
```
