### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` derives its HMAC-signable content solely from the raw HTTP body: [1](#0-0) 

but the `shop` (and `topic`, `webhook_id`, `api_version`) attributes that the rest of the library treats as authoritative are read straight from unauthenticated headers: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `hmac` matches `HMAC(secret, to_signable_string)`: [3](#0-2) 

and `Registry.process` accepts the request the moment that check passes, then forwards `request.shop` to the handler as the trusted tenant identifier with no further binding check: [4](#0-3) 

The identity binding that should hold is:
`shop that produced/authorized this HMAC == shop attributed to the processed webhook (request.shop)`

Because `to_signable_string` returns only `@raw_body`, that equality is never enforced: the HMAC proves the body wasn't tampered with under the app's secret, but it proves nothing about which shop the body belongs to. Anyone who can obtain one valid `(raw_body, hmac)` pair for their own shop (trivial — any merchant who installs the app receives valid signed webhooks for events on their own store, and can craft body content by performing actions in their own store, e.g. creating orders/customers with attacker-chosen field values) can replay that identical body+hmac while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` still succeeds because the header is not part of `to_signable_string`, and `Registry.process` will happily deliver `WebhookMetadata.new(topic: ..., shop: <attacker-chosen victim shop>, body: ...)` to the app's handler.

This is the same bug class as the report's core lesson — a value that downstream logic treats as bound/verified (there: `current_debt` implicitly assumed synchronized with `newDebt` computation; here: `shop` implicitly assumed synchronized with the HMAC-verified payload) is not actually covered by the check that is supposed to guarantee it, and the code proceeds anyway.

### Impact Explanation
This breaks the tenant boundary the gem's webhook API is supposed to provide: an unprivileged internet user who is (or can become) an ordinary merchant using the app can forge webhook deliveries that the host application will process as belonging to a different, victim merchant's shop, with a body the attacker fully controls in content shape (subject to real Shopify JSON schemas for that topic). Any app logic that keys per-tenant side effects off `WebhookMetadata#shop` (order fulfillment automation, GDPR data deletion routines for `customers/redact`/`shop/redact`, billing/webhook-driven state transitions, etc.) can be triggered against an arbitrary victim shop, i.e., cross-tenant access/manipulation — a Critical-class impact per the scope's own definition.

### Likelihood Explanation
Likelihood is high for anyone with an installed instance of the app (a standard, unprivileged merchant relationship, not requiring `api_secret_key`, an access token, or any credential leak): they can capture a legitimately signed `(raw_body, hmac)` pair for their own store's webhook traffic (e.g. by installing the app and observing/receiving one webhook, or via any request-capturing proxy on their own endpoint) and simply resend it with a different `shopify-shop-domain` / `x-shopify-shop-domain` header value to the target application's webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed content, or otherwise cryptographically tie the header-derived identity to the HMAC check, e.g.:
```ruby
def to_signable_string
  # include the header-derived shop domain in the signable material so that
  # tampering with the shop-domain header invalidates the HMAC
  "#{shop}\n#{@raw_body}"
end
```
This requires coordinating the exact canonical format Shopify signs on, or alternatively cross-checking the source IP/registered domain out of band; at minimum, `Registry.process` should not treat `request.shop` as authenticated purely because the body hash matched.

### Proof of Concept
1. Install/operate the target app as an ordinary merchant on `attacker-shop.myshopify.com`.
2. Trigger a real webhook event for a registered topic (e.g. `orders/create`) on your own shop; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header — this pair validates correctly since it's a real Shopify-signed webhook.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (`lib/shopify_api/webhooks/request.rb:45-63`), `Utils::HmacValidator.validate` returns `true` because it only recomputes the HMAC over `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`), and `Registry.process` dispatches the handler with `shop: request.shop` set to `victim-shop.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:188-200`) even though the payload never originated from that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
