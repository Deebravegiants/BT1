### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers. Those identity fields are never included in the signed payload, so the equality the code implicitly relies on — "the shop whose data this webhook describes" == "the `shop-domain` header value" — is never actually checked.

### Finding Description
`Utils::HmacValidator.validate` computes/compares the HMAC using `verifiable_query.to_signable_string`. For webhooks, `Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` are pulled straight from headers, none of which participate in the HMAC computation: [2](#0-1) 

`Registry.process` validates only the body HMAC, then immediately trusts the header-derived `topic`/`shop`/`webhook_id` to route and label the webhook payload for the handler: [3](#0-2) 

Because Shopify signs webhooks for every shop of an app using the same shared `client_secret` (`Context.api_secret_key`), an attacker who has (or creates) their own shop installation of the app receives real, validly-signed webhook deliveries whose body content they substantially control (e.g., by setting a product title, order note, customer field, etc. before triggering the webhook event). The attacker can capture such a delivery — valid `raw_body` + valid `hmac` — and replay it to the app's public webhook endpoint after rewriting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) headers to name a different, victim shop. `HmacValidator.validate` still succeeds because it only checks the (unchanged) body against the (unchanged) HMAC; `Registry.process` then calls the handler with `shop: request.shop` set to the attacker-chosen victim domain, and `topic`/`webhook_id` are equally forgeable.

This breaks the binding: **HMAC-verified bytes (`raw_body`) ≠ identity fields acted upon (`shop`, `topic`, `webhook_id`)**. Any host application that uses `WebhookMetadata#shop` from `Registry.process` to key persistence, authorization, or side effects (a normal and expected usage pattern per the library's own webhook API) can be made to attribute attacker-controlled data to a victim shop it does not control.

### Impact Explanation
This allows cross-tenant data injection/spoofing: an unprivileged actor who merely installs the app on their own shop can cause an arbitrary victim shop's webhook processing pipeline to run with a payload and topic of the attacker's choosing. This matches the "Critical - cross-tenant access" impact class, since it lets one tenant (installer) forge events attributed to another tenant without needing that tenant's credentials.

### Likelihood Explanation
Any developer/merchant can install a public or unlisted app on a shop they control and observe genuine webhook deliveries with valid HMACs; replaying them to the app's public webhook endpoint with modified headers requires no special access, only knowledge of the endpoint URL (typically documented/discoverable), making this exploitable by any unprivileged internet user who can install the target app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified by the HMAC, or have `Registry.process` cross-check the header-derived `shop` against an application-side registry of shops with pending/expected webhooks tied to the specific `client_secret`/session that installed the app, rather than trusting the header value outright. At minimum, document prominently that `request.shop`/`request.topic` are not authenticated by the HMAC and must be independently validated by the host application before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g., updates a product title to attacker-controlled JSON-like content) so Shopify sends a webhook with `raw_body` containing attacker-influenced data and a valid `x-shopify-hmac-sha256` computed with the app's shared secret.
3. Attacker replays this exact `raw_body`/`hmac` pair to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` (body+hmac unchanged); `Registry.process` in `lib/shopify_api/webhooks/registry.rb` line 198 calls the handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, even though `victim-shop` never sent this webhook.
