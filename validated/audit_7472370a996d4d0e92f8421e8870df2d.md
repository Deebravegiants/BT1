### Title
Instruction-data cost is rounded down (floor division), systematically underpricing transaction cost accounting in the cost model - (File: cost-model/src/cost_model.rs)

### Summary
`CostModel::get_instructions_data_cost` computes the compute-unit cost attributable to instruction data bytes using a plain integer (floor) division, `instruction_data_len / INSTRUCTION_DATA_BYTES_COST`, instead of rounding up. This is the cost-model analog of the reported `YTokenL2` bug class: a division that should round in favor of the protocol (the block/cost-limit accounting) instead rounds in favor of the party being measured (the transaction/user), silently discarding a fractional remainder every time.

### Finding Description
`INSTRUCTION_DATA_BYTES_COST` is itself defined via truncating integer division: `140 /*bytes per us*/ / COMPUTE_UNIT_TO_US_RATIO` = `140 / 30` = `4` [1](#0-0) .

The per-transaction data-bytes cost is then computed as:
```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    transaction.instruction_data_len() / (INSTRUCTION_DATA_BYTES_COST as u16)
}
``` [2](#0-1) 

This is a plain floor division: for any `instruction_data_len` that is not an exact multiple of 4, the remainder (0–3 bytes worth of cost) is discarded rather than rounded up. This value feeds directly into `TransactionCost::sum()`, which is the quantity compared against `MAX_BLOCK_UNITS`, `MAX_WRITABLE_ACCOUNT_UNITS`, and per-account cost limits in the cost tracker/banking stage [3](#0-2) .

This stands in direct contrast to the sibling function in the very same file, `calculate_pages_for_bytes`, which correctly rounds *up* (ceiling division) when converting loaded-accounts-data bytes into CU cost:
```rust
fn calculate_pages_for_bytes(bytes: u32) -> u64 {
    u64::from(bytes)
        .saturating_add(ACCOUNT_DATA_COST_PAGE_SIZE.saturating_sub(1))
        .saturating_div(ACCOUNT_DATA_COST_PAGE_SIZE)
}
``` [4](#0-3) 

That asymmetry is the crux of the bug: one byte-to-CU conversion in the same cost model rounds up (favoring the protocol/limit-enforcement), while the other rounds down (favoring the unprivileged transaction sender), exactly mirroring the `previewMint`/`previewWithdraw` inconsistency in the original report where some conversions rounded toward the vault and others toward the user.

### Impact Explanation
Every unprivileged user submitting a transaction whose total instruction data length is not a multiple of 4 bytes has up to 3 CU of real resource cost silently dropped from the accounted `data_bytes_cost` used in `CostModel::calculate_transaction_cost` / `calculate_cost_for_executed_transaction` [5](#0-4) . This under-accounting is applied consistently and unconditionally to essentially all transactions (since arbitrary instruction data length is user-controlled), meaning the cost-tracker's view of block/account occupancy used to enforce `MAX_BLOCK_UNITS`/`MAX_WRITABLE_ACCOUNT_UNITS` is systematically biased low relative to the true intended per-byte pricing. This is a form of materially underpriced execution resource accounting: users are never charged CU for the fractional remainder of their instruction data, letting slightly more real instruction-data volume into a block than the cost model's stated per-byte rate implies.

The per-transaction magnitude (≤3 CU) is small relative to `MAX_BLOCK_UNITS_SIMD_0256` (60,000,000), so this is a low-severity, high-frequency systemic bias rather than a large single-transaction fund-loss bug — it does not directly move lamports the way the original ERC-4626 report did, but it is a concrete, always-reachable rounding-direction defect in an in-scope area (cost model) that consistently favors the unprivileged caller over the accounted resource limit, which is the class of issue requested.

### Likelihood Explanation
This triggers on essentially every transaction with non-4-byte-aligned instruction data, requires no special privileges, and needs no crafted/malicious input beyond ordinary transaction construction — it is exercised continuously by normal cluster traffic.

### Recommendation
Round `get_instructions_data_cost` up (ceiling division) to match the rounding convention already used by `calculate_pages_for_bytes`, e.g.:
```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    let len = transaction.instruction_data_len();
    let denom = INSTRUCTION_DATA_BYTES_COST as u16;
    len.saturating_add(denom - 1) / denom
}
```
This would require a feature gate / SIMD given it changes cost accounting and thus consensus-relevant cost limits.

### Proof of Concept
Given `INSTRUCTION_DATA_BYTES_COST == 4` [1](#0-0) :
- A transaction with `instruction_data_len() == 3` yields `get_instructions_data_cost() == 0`, even though the true per-byte cost rate (140 bytes / 30 µs, i.e. ~4.67 bytes per CU) implies a non-zero fractional cost should be charged.
- The existing unit test `test_non_vote_transaction_cost` confirms the floor behavior is baked into expectations (`data_bytes_cost = 19` for a fixed instruction length, matching `len / 4` truncation) [6](#0-5) , demonstrating the rounding-down behavior is the current, verified production behavior rather than a hypothetical edge case.
