### Title
Consensus handler skips storing the first state commitment for any state machine whose `latestStateMachineHeight` is still zero, permanently blocking message delivery for that route - (File: evm/src/core/HandlerV2.sol)

### Summary
`HandlerV2.handleConsensus` stores an incoming intermediate state commitment only when **both** `latestHeight != 0` **and** `intermediate.height > latestHeight` hold [1](#0-0) . The equivalent Rust/pallet-ismp analog only skips a commitment height when it is **not greater** than the previously recorded height — it has no special-case requirement that the previous height be non-zero [2](#0-1) . The extra `latestHeight != 0` conjunct in the EVM handler is an undocumented, additional AND-condition that has no counterpart in the reference implementation or in any written spec for `IConsensusV2`/`storeStateMachineCommitment`.

### Finding Description
`EvmHost` initializes `_latestStateMachineHeight[id] = 1` only for the state machine IDs that are present in `params.stateMachines` at `initialize`/construction time [3](#0-2) . For any state machine ID whose height has not been explicitly seeded to a non-zero value (e.g., a chain added to the whitelist after deployment through whatever mechanism does not also seed the height, or any ID the relayer submits proofs for that the deploying whitelist loop never touched), `host.latestStateMachineHeight(id)` returns `0`.

When a relayer subsequently submits a valid consensus proof containing an `IntermediateState` for that state machine ID, `handleConsensus` computes `latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId)` and only calls `host.storeStateMachineCommitment(...)` when `latestHeight != 0 && intermediate.height > latestHeight` [4](#0-3) . Because `latestHeight == 0` fails the first conjunct, the commitment is silently dropped — the consensus proof itself is still accepted and the consensus state is still advanced (`host.storeConsensusState(verifiedState)` at line 153 runs unconditionally before the loop) [5](#0-4) , but the very state commitment relayers need to prove message inclusion for that chain is never persisted, and `_latestStateMachineHeight[id]` never becomes non-zero. Every subsequent proof for that state machine ID hits the exact same `latestHeight != 0` failure, so the route can never accept its first commitment.

`storeStateMachineCommitment` on the host itself has no such precondition — it unconditionally writes the commitment and sets `_latestStateMachineHeight[height.stateMachineId] = height.height` whenever the handler calls it [6](#0-5) , confirming the `!= 0` guard is purely a `HandlerV2` logic artifact, not an invariant enforced anywhere else in the storage layer.

### Impact Explanation
`handlePostRequests` and `handleGetResponses` both require `host.stateMachineCommitment(proof.height).overlayRoot != bytes32(0)`, reverting with `StateCommitmentNotFound()` otherwise [7](#0-6) . If a state machine's first commitment can never be stored because of the `latestHeight != 0` gate, no POST request or GET response destined for/sourced from that state machine can ever be delivered or proven — a permanent freeze of the messaging route for that chain, matching the "route unable to deliver messages" impact class. This is triggered by ordinary relayer proof submission (a single `handleConsensus` call), requires no malicious/privileged actor, and is unrecoverable through normal protocol operation since the guard reproduces itself on every future proof for that ID.

### Likelihood Explanation
The bug fires deterministically whenever a state machine ID's `latestStateMachineHeight` is `0` at the time its first consensus proof arrives — this is the default/uninitialized value for any mapping key in Solidity, so any state machine not present in the constructor's `params.stateMachines` array (e.g., one enabled after deployment, or one referenced by an intermediate state the consensus client verifies but the host was never told to whitelist with a seeded height) will hit it on the very first legitimate relayer submission. No adversarial behavior is required; a single honest relayer delivering a normal consensus update is sufficient to reproduce it once the precondition (zero height) holds.

### Recommendation
Remove the `latestHeight != 0` conjunct from `handleConsensus`'s commitment-storage condition so that it matches the pallet-ismp semantics of "store whenever the new height is strictly greater than the previously recorded height, treating an unset/zero height as no prior commitment" (i.e., `intermediate.height > latestHeight` alone, or explicitly special-case `latestHeight == 0` to always accept the first commitment) [8](#0-7) . Additionally, audit every code path that can introduce a new state machine ID after deployment to confirm `_latestStateMachineHeight` is always seeded to a non-zero placeholder (as the constructor loop does) [3](#0-2) , since that is the only thing currently preventing this condition from being reachable in practice.

### Proof of Concept
1. Deploy/operate an `EvmHost` where a given `stateMachineId` `X` is not part of the initial `params.stateMachines` whitelist (so `_latestStateMachineHeight[X] == 0`), or is otherwise enabled without the height being seeded.
2. A relayer calls `HandlerV2.handleConsensus(host, proof)` with a valid consensus proof whose verified `intermediates` array includes an `IntermediateState` for `stateMachineId == X` at some height `h > 0`.
3. Inside the loop, `latestHeight = host.latestStateMachineHeight(X) == 0`, so `latestHeight != 0 && intermediate.height > latestHeight` evaluates to `false` — `host.storeStateMachineCommitment` is never called for `X` [8](#0-7) .
4. `host.stateMachineCommitment(...)` for state machine `X` remains unset (`overlayRoot == bytes32(0)`) forever.
5. Any later call to `handlePostRequests` or `handleGetResponses` referencing `X` at any height reverts with `StateCommitmentNotFound()` [7](#0-6) , and step 3 repeats identically for every future proof, permanently blocking delivery for state machine `X`.

Note: I was not able to fully inspect the body of `EvmHost.addStateMachine` (only confirmed its existence via search) to determine definitively whether every post-deployment path to enable a new state machine also seeds `_latestStateMachineHeight` to a non-zero value; this should be verified directly in the repository, as it determines exactly how easily the zero-height precondition is reached in production versus only being a theoretical edge case for un-whitelisted IDs.
