### Title
Unprotected re-initializer in `LockupContract::new()` allows resetting lockup state and hijacking ownership - (File: `lockup/src/lib.rs`)

### Summary
The external report's root cause class is "unprotected initializer" — a function that mutates critical contract state as if it were a one-time constructor, but lacks a guard against being invoked more than once. `core-contracts--006` has its own reachable instance of exactly this bug class, distinct from (and more severe than) the Solidity analog: `LockupContract::new()` in [1](#0-0)  is annotated `#[init]` but never checks `env::state_exists()` before overwriting the contract's storage.

### Finding Description
Every other production initializer in scope explicitly guards against re-initialization:
- `LockupFactory::new` — `assert!(!env::state_exists(), "The contract is already initialized");` [2](#0-1) 
- `MultiSigContract::new` — `assert!(!env::state_exists(), "Already initialized");` [3](#0-2) 
- `StakingPoolFactory::new` — `assert!(!env::state_exists(), "The contract is already initialized");` [4](#0-3) 
- `StakingContract::new` — `assert!(!env::state_exists(), "Already initialized");` [5](#0-4) 
- `WhitelistContract::new` — `assert!(!env::state_exists(), "Already initialized");` [6](#0-5) 
- `VotingContract::new` — `assert!(!env::state_exists(), "The contract is already initialized");` [7](#0-6) 

`LockupContract::new()`, however, has no such check anywhere in its body [8](#0-7) . It unconditionally rebuilds and returns a fresh `LockupContract` struct — including `owner_account_id`, `lockup_information` (which recomputes `lockup_amount` from the *current* `env::account_balance()`), `vesting_information`, `staking_information` (reset to `None`), and `foundation_account_id` — from attacker-supplied constructor arguments.

Because NEAR contract methods (other than those explicitly gated by `assert_self` / owner checks) are callable by any account via a `FunctionCall` action, any unprivileged account can send a transaction calling `new` on an already-deployed lockup contract account with attacker-chosen arguments, resetting `owner_account_id` to itself and clearing `staking_information`/`vesting_information`.

### Impact Explanation
This maps to the in-scope Critical impacts:
- "Unauthorized transfer, withdrawal, spending, or release of locked... NEAR through public-call... reachable by an unprivileged user" — by resetting `owner_account_id` to an attacker-controlled account, the attacker gains all owner-only privileges over the lockup contract (e.g., `transfer`, `select_staking_pool`, `withdraw_from_staking_pool`, termination logic), effectively hijacking control over the locked NEAR balance held by that account.
- "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in lockup release... flows" — wiping `vesting_information` and `staking_information` corrupts the contract's accounting of vesting/staking state, which can permanently desynchronize the contract from any staking pool it was previously bound to (the old `staking_information` reference is lost with no way to recover already-staked funds' bookkeeping).

### Likelihood Explanation
High likelihood: no privileged role, signature, or special condition is required — the vulnerable function is a normal public contract method reachable by anyone who knows the lockup account ID (which is derivable/public, per `lockup-factory/src/lib.rs`'s deterministic account-naming scheme [9](#0-8) ). The only requirement is a small amount of gas to submit the `new` call; no economic cost is imposed to block repeated calls (unlike, e.g., `env::state_exists()`-guarded contracts).

### Recommendation
Add the same guard used by every other contract in scope:
```rust
assert!(!env::state_exists(), "The contract is already initialized");
```
at the top of `LockupContract::new()` in `lockup/src/lib.rs`, immediately after the `#[init]` attribute, before any state mutation occurs.

### Proof of Concept
1. Lockup contract `abc123....lockup-factory.near` is created and initialized once via `LockupFactory::create` with legitimate `owner_account_id = alice.near`.
2. Attacker `mallory.near` submits a transaction calling `new` directly on `abc123....lockup-factory.near` with `owner_account_id = mallory.near`, `vesting_schedule = None`, `foundation_account_id = None`, and arbitrary values for the remaining parameters.
3. Because `new()` performs no `env::state_exists()` check, the call succeeds, overwriting `LockupContract`'s persistent state: `owner_account_id` becomes `mallory.near`, and `staking_information`/`vesting_information` are reset.
4. `mallory.near` now controls the previously-locked funds via owner-only methods (e.g., can redirect any future `transfer` calls, or manipulate staking pool selection) exposed on `LockupContract`.

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),

        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
