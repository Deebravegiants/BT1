### Title
Webhook shop/topic/version identity is trusted from unauthenticated headers while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` verifies nothing but the body bytes. The `shop`, `topic`, `api_version`, and `webhook_id` values that `Registry.process` hands to the app's webhook handler come straight from HTTP headers that are never covered by that HMAC, breaking the binding `shop authenticated == shop delivered to handler`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers with no cryptographic binding at all: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the body bytes were signed by someone holding `api_secret_key`) and then immediately dispatches the *header-derived, unsigned* `shop`, `topic`, `webhook_id`, and `api_version` to the registered handler: [3](#0-2) 

The identity binding that should hold is: `hmac-verified bytes == bytes describing which shop/topic this event is for`. Instead, the gem verifies the body but trusts the shop/topic identity fields from headers that were never part of the signed material. `Utils::HmacValidator.validate_signature` confirms only the body is signed: [4](#0-3) 

### Impact Explanation
This is a "bytes verified versus bytes parsed"-style identity break (matching the bug-class hint of trusting an unauthenticated field). An attacker who can obtain any single legitimately-HMAC-signed webhook payload for their own tenant (e.g. by installing the app on their own store — which any unprivileged internet user can do) can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-Api-Version`) headers to point at a victim shop. `HmacValidator.validate` still returns `true` because it only checked the body, and `Registry.process` will invoke the app's handler believing the event originated from the victim shop, achieving cross-tenant data/event injection without possessing the victim's credentials or the app's `client_secret`.

### Likelihood Explanation
Likelihood is moderate-to-high in any host application that uses the `shop` field from `WebhookMetadata` to key session lookups, tenant-scoped writes, billing/plan updates, or GDPR-style compliance actions (the registry's own `MANDATORY_TOPICS` include `shop/redact`, `customers/redact`, `customers/data_request`), since this gem's own webhook endpoint is directly reachable by any unprivileged internet user who can send an HTTP POST with attacker-chosen headers, and it does not require access to `api_secret_key`, a token, or the victim's data ahead of time (only a body/HMAC pair the attacker can legitimately obtain for themselves).

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `api_version`, `webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified body before they are passed to `WebhookHandler#handle`. At minimum, document/require the host application to independently re-verify the delivered `shop` against a known, previously-registered shop/session before acting on data derived from webhook headers, and consider cross-checking `request.shop` against the shop associated with the specific `webhook_id` via the Admin API when the topic touches sensitive or tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own dev/test store `attacker.myshopify.com`, granting the app access as normal.
2. Attacker triggers a webhook (e.g., `customers/data_request`) from their own store, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify computed over that body.
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally spoofs `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4)  which succeeds because only the (unmodified) body is checked.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from, and reflects data belonging to, `attacker.myshopify.com`, achieving cross-tenant confusion in the host application's processing logic.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
