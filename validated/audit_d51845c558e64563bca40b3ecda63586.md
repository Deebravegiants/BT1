### Title
JWT Replay Cache Check-Then-Act Race Allows Token Reuse in `WorkflowMetadataHandler.Authorize` - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` performs the JWT replay check (`isReplay`) and the replay record write (`recordUsage`) as two separate, non-atomic operations against `jwtReplayCache`, each taking its own lock. This check-then-act gap mirrors the report's read-only-reentrancy root cause (state is validated/read before the authoritative state update is committed), letting two concurrent requests carrying the same JWT both pass the replay check before either records usage.

### Finding Description
`Authorize` validates a JWT (`utils.VerifyRequestJWT`), then calls `h.jwtCache.isReplay(claims.ID)` to reject reused tokens, and only records the token as used with `h.jwtCache.recordUsage(claims.ID)` after the signer/authorized-key checks succeed: [1](#0-0) 

The cache's read and write paths take separate locks with no shared critical section spanning both: [2](#0-1) 

Because `isReplay` (RLock) and `recordUsage` (Lock) are independent operations, two goroutines handling concurrent gateway messages carrying the identical JWT (`jti`) can both execute `isReplay` and get `exists == false` before either calls `recordUsage`. Both requests then proceed to be treated as authorized. This is structurally the same class of bug as the reported read-only reentrancy: a security-relevant read (the replay check) is performed against state that has not yet been updated to reflect an in-flight/concurrent operation, and the update happens too late to prevent the second reader from observing stale (pre-update) state.

### Impact Explanation
A valid JWT-authenticated HTTP trigger request (`gateway_common.MethodWorkflowExecute`, handled via `httpTriggerHandler.HandleUserTriggerRequest` → `WorkflowMetadataHandler.Authorize`) is intended to be single-use per `jti` to prevent replay/duplication of a signed request. Under this race, an attacker who can send two copies of the same signed request concurrently (e.g., replaying an intercepted request alongside the original, or double-submitting) can have both accepted as authorized, defeating the anti-replay guarantee documented for this exact mechanism (contrast with the vault package's `RequestReplayGuard.CheckAndRecord`, which correctly performs check-and-record atomically under a single lock — `core/capabilities/vault/request_replay_guard.go` lines 35-47). The impact is a request-impersonation/replay bypass in the internet-facing gateway's authentication path for workflow trigger execution.

### Likelihood Explanation
Exploitation requires an unprivileged/external client to send (or capture-and-resend) two copies of a validly signed JWT request such that they are processed concurrently by the same `WorkflowMetadataHandler` instance — no privileged access or special network position is required. The race window is small (two lock acquisitions apart) but is a genuine, reachable concurrency bug in a client-facing authentication path, not a mocked-only or operator-only condition.

### Recommendation
Merge `isReplay` and `recordUsage` into a single atomic check-and-record operation performed under one lock (as `vault.RequestReplayGuard.CheckAndRecord` already does), so that the replay-check and the state update happen indivisibly. Call this atomic operation before/at the point of accepting the JWT as valid, ensuring no window exists where two concurrent requests with the same `jti` can both pass the check.

### Proof of Concept
1. Client obtains a validly signed JWT trigger request (signature over `req`, with `jti` = `claims.ID`).
2. Client sends this exact request twice concurrently to the gateway (e.g., via two parallel HTTP/websocket sends hitting the same `WorkflowMetadataHandler.Authorize` call path from `httpTriggerHandler.HandleUserTriggerRequest`).
3. Both goroutines call `h.jwtCache.isReplay(claims.ID)` before either calls `h.jwtCache.recordUsage(claims.ID)`; both see `exists == false` and both pass.
4. Both requests are authorized and proceed to workflow execution, despite the anti-replay guarantee, i.e., the token is used twice.

(Note: I could not fully trace whether downstream processing — e.g., dedup at the trigger-request/callback layer — independently prevents duplicate execution side effects; this could not be verified within available tool calls. The core authentication-layer race in `jwtReplayCache` is confirmed by direct code inspection.)

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
