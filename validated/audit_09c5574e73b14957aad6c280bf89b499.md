### Title
Absent input validation on cross-chain request body causes undefined behavior via `String::from_utf8_unchecked` in `pallet-ismp-demo` - (File: modules/pallets/demo/src/lib.rs)

### Summary
`pallet-ismp-demo`'s `IsmpModuleCallback::on_accept` handler decodes the raw `body` bytes of an incoming ISMP `PostRequest` originating from an `Evm` source chain using `String::from_utf8_unchecked`, without any validation that the bytes are valid UTF-8. This mirrors the reported `BinaryHttpParser` flaw: attacker-controlled, length-prefixed bytes are cast directly into a higher-level type (`String`) with no validation, and the result is then used in further state changes/log emission.

### Finding Description
`IsmpModuleCallback::on_accept` is the `IsmpModule` callback invoked by pallet-ismp's request handler (`modules/ismp/core/src/handlers/request.rs`) once a `PostRequest` has been verified for consensus/proof correctness and routed to the destination module (`modules/pallets/demo/src/lib.rs`, `on_accept`, ~lines 369-399):

```rust
impl<T: Config> IsmpModule for IsmpModuleCallback<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		let source_chain = request.source;

		match source_chain {
			StateMachine::Evm(_) => Pallet::<T>::deposit_event(Event::Request {
				source: source_chain,
				data: unsafe { String::from_utf8_unchecked(request.body) },
			}),
			...

`request.body` is fully attacker-controlled: any account can dispatch a `PostRequest` from an EVM source chain to this module's `to` address, and its `body` bytes are never validated before this call. Pallet-ismp only verifies the state-machine/consensus proof of the message's inclusion — it performs no validation of the request payload's contents, which is the receiving module's responsibility (as noted by pallet-ismp's own documentation, `docs/content/developers/polkadot/receiving.mdx`, "Here you would perform validations on the post request data ... before making any state changes"). This is exactly the same class of bug as `BinaryHttpParser`: raw bytes from an untrusted, remote party are blindly reinterpreted as a validated type (`HttpMethod`/`String` respectively) using an unsafe/unchecked constructor, skipping the validation the type is supposed to guarantee.

`String::from_utf8_unchecked` is documented by Rust as producing **undefined behavior** if the input is not valid UTF-8 — this is strictly worse than the Netty case, which only produced protocol-level injection strings; here it is a language-level safety violation. Depending on optimizer assumptions and how the resulting `String` (emitted in the runtime `Event::Request` and stored/pruned into the on-chain event log, then re-serialized for RPC subscribers and block explorers) is subsequently used, this can lead to memory-safety violations, corrupted event data, or a validator/RPC-node panic/crash when re-encoding or displaying the string, since the compiler is permitted to assume the invariant holds.

This pallet is not test-only: it is wired into the live parachain runtime as `IsmpDemo` at `pallet_index(52)` in `parachain/runtimes/gargantua/src/lib.rs` and configured in `parachain/runtimes/gargantua/src/ismp.rs` (`impl pallet_ismp_demo::Config for Runtime`), meaning it is compiled into and reachable on the actual Gargantua network runtime, not merely referenced in documentation or test fixtures.

### Impact Explanation
Any account able to dispatch an ISMP `PostRequest` targeting this module's id from an EVM source chain (an unprivileged action reachable by any relayer delivering a proven cross-chain message, or by anyone who can get a message routed to this module) can supply an arbitrary, non-UTF-8 byte sequence as the request body. This triggers undefined behavior at the language level inside the runtime's on-chain execution path (`on_accept`), which executes during block processing on every validator/collator. Depending on how the miscompiled/invalid string subsequently propagates (RPC event serialization, indexer parsing, logging), consequences range from validator/collator/RPC node crashes (denial of the event pipeline) to corrupted on-chain event data — a real, network-facing consensus-adjacent safety violation, not merely a cosmetic bug, satisfying the "unsound state" / "unauthorized action" bar via a fully attacker-reachable path.

### Likelihood Explanation
High likelihood of triggering the technical fault: constructing a `PostRequest` with a non-UTF-8 body and getting it delivered to this module requires nothing more than a normal, valid cross-chain dispatch from an EVM chain with `to` set to the demo pallet's module id (`ismp-ast`) — no privileged role, governance, or malicious-node assumption is required, satisfying the report's "unprivileged message dispatcher/relayer" reachability bar.

### Recommendation
Replace `String::from_utf8_unchecked(request.body)` with `String::from_utf8(request.body)` and handle the `Err` case explicitly (e.g., reject the request or store raw bytes instead of a `String`), mirroring the fix direction taken in the Netty advisory: never construct a higher-level "validated" type (`String`, `HttpMethod`, etc.) from untrusted bytes without going through its safe/validating constructor. More broadly, any `IsmpModule::on_accept` implementation that is included in a live runtime should validate the `body` payload's structure/encoding before performing state changes or emitting events derived from it.

### Proof of Concept
1. On the EVM source chain, call `IDispatcher(host).dispatch(DispatchPost{ dest: <Polkadot chain>, to: PALLET_ID ("ismp-ast") bytes, body: <bytes containing invalid UTF-8, e.g. 0xFF 0xFE>, ... })`.
2. Have the message relayed and proven via the normal ISMP request-handling path (`modules/ismp/core/src/handlers/request.rs::handle`), which validates the state machine/consensus proof but not the body contents.
3. Once routed to `IsmpModuleCallback::on_accept` for the `Evm` source branch, `String::from_utf8_unchecked(request.body)` executes on the invalid bytes, producing an invalid `String` value and undefined behavior when that value is later used (event emission/serialization).
