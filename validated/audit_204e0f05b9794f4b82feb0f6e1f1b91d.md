Based on my research, the strongest custody-relevant analog to the "stale authentication token can be replayed/mismatched from the actual authorized action" bug class is in Aptos's **multisig account transaction validation**, where the payload that owners voted on can diverge from the payload that actually gets executed by the VM, unless a specific feature flag is turned on.

### Title
Multisig-approved payload can diverge from the payload actually executed, unless `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is enabled — (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account::validate_multisig_transaction` is the VM-invoked prologue check that authorizes execution of a queued multisig transaction. When a transaction was created via `create_transaction` (full payload stored on-chain, as opposed to `create_transaction_with_hash`, which stores only a hash), the check that the actual runtime `payload` argument matches the `stored_payload` that owners voted for is **conditionally gated** behind the feature flag `features::abort_if_multisig_payload_mismatch_enabled()`, rather than being unconditionally enforced like the hash-based path.

### Finding Description
`validate_multisig_transaction` has two distinct authenticity checks depending on how the transaction was proposed: [1](#0-0) 

1. If `transaction.payload_hash.is_some()` (i.e. proposed via `create_transaction_with_hash`), the check `sha3_256(payload) == *payload_hash` is **unconditional** — any mismatch aborts.
2. If instead the transaction was proposed via `create_transaction` (full payload stored directly as `transaction.payload`), the equivalent check — `payload == *stored_payload` — is only performed **if** `features::abort_if_multisig_payload_mismatch_enabled()` returns true. If that feature is not active, the runtime `payload` supplied by the executing owner is never compared to what owners actually approved and voted on.

This exactly mirrors the pattern in the external report: the quorum's approvals (the "authentication") are bound to `transaction.payload` (the analog of `TermAuth`/signed intent), but the VM entry-point that actually executes the multisig call takes a separate runtime `payload` parameter (the analog of `txMsgData`) that is not cryptographically/structurally forced to match the approved one unless a specific opt-in safeguard is active. The report's own resolution language calls out precisely this class of risk: "when calling `Authenticator.authenticate()` directly, nonce and expiration timestamp could be modified... to bypass necessary checks... this did not appear exploitable... due to the way it is invoked... care should be taken to ensure this approach is consistent."

Here, the two code paths (`payload_hash` vs. `payload`) are *not* consistent: one enforces integrity unconditionally, the other only when a feature flag happens to be turned on.

### Impact Explanation
If quorum is reached to approve a `MultisigTransaction` created via `create_transaction` (stored payload, not stored hash) while `abort_if_multisig_payload_mismatch_enabled` is inactive, any single owner able to submit the execution transaction can supply an arbitrary `payload` argument at the VM/transaction level that differs from what the other owners actually voted for, and it will still pass `validate_multisig_transaction`'s payload check (the mismatch branch is simply skipped). Since the multisig account's signer authority is used to execute whatever entry function corresponds to the submitted runtime payload, this breaks the core custody invariant that "multisig-owned assets... must not leak upgrade, freeze, or transfer authority to unprivileged callers" — an owner with quorum on a decoy/'safe-looking' proposal could execute a completely different, unapproved transaction (e.g., a fungible-asset transfer, object ownership transfer, or capability grant) using the multisig account's authority. That is theft/misappropriation of any asset the multisig custodies.

### Likelihood Explanation
Exploitability is entirely gated on the runtime/default state of the `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` feature flag on mainnet, which I was **not able to confirm** within the available tool budget — I located the flag's usages in `features.move`/`features.spec.move`/`aptos_features.rs`/`aptos_vm.rs`/`transaction_validation.rs`, but did not get to read the actual default-enablement table or genesis feature set before running out of iterations. If the flag is (or ever was, pre-activation on any network) disabled by default, this is a live, unprivileged-owner-exploitable custody bypass on any multisig account using `create_transaction` (as opposed to `create_transaction_with_hash`). If the flag is unconditionally enabled at genesis/mainnet already, then the current live risk is null, but the *existence* of an unenforced-by-default code path is itself a latent defect that a future feature-flag rollback, migration, or a chain still pending activation could re-expose.

### Recommendation
Make the `payload == stored_payload` check for `create_transaction`-created transactions unconditional (matching the hash-path's unconditional enforcement), rather than depending on a feature flag. If backward compatibility requires the flag during a migration window, the flag should default to "enabled" and there should be no path where the VM can execute a stored, fully-known payload for a multisig transaction without validating it against what was actually voted on.

### Proof of Concept
Not executed in this environment (I don't have write/execute tooling), but conceptually:
1. Owner A creates a multisig transaction via `create_transaction(owner_A, multisig_addr, payload_1)` where `payload_1` is an innocuous entry function call (e.g. a small internal transfer).
2. Owners B, C vote to approve based on the displayed `payload_1`, reaching quorum.
3. Assuming `abort_if_multisig_payload_mismatch_enabled()` is false, Owner A (or any executing owner) submits the actual on-chain multisig-execution transaction with a *different* runtime `payload_2` (e.g. `object::transfer` of a high-value asset object owned by the multisig, or a large fungible-asset withdrawal) as the VM-level payload argument.
4. `validate_multisig_transaction` checks `transaction.payload_hash` — none, since `create_transaction` was used — then checks the `payload == stored_payload` branch, which is skipped because the feature is off.
5. The VM executes `payload_2` with the multisig account's authority, transferring/burning/freezing assets never actually approved by quorum.

I was unable to conclusively verify the mainnet default state of the feature flag before running out of iterations — this is the primary remaining uncertainty and should be confirmed before treating this as a live, currently-exploitable issue versus a latent/historical one. [2](#0-1)

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }
