### Title
Webhook shop identity is not covered by the HMAC signature, allowing tenant relabeling of a validly-signed webhook - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying the HMAC over the raw request body, then hands the `shop` value taken from an unauthenticated HTTP header directly to the app's handler as the tenant identifier, without that header ever being part of the signed material.

### Finding Description
`Registry.process` validates the webhook using only `Utils::HmacValidator.validate(request)`, and `Request#to_signable_string` returns `@raw_body` only [1](#0-0) [2](#0-1) . The `shop` accessor is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header [3](#0-2) , and this unauthenticated value is passed as the `shop` field of `WebhookMetadata` given to the app's handler [1](#0-0) , which the documentation explicitly instructs apps to use as the tenant/session key for subsequent processing (e.g. `shop_domain: data.shop`) [4](#0-3) .

The binding that should hold is: `shop_bound_by_signature == shop_used_as_tenant_key`. In this gem that equality does not hold — the signature only binds `raw_body`, not `shop`. Because `Context.api_secret_key` is a single secret shared across *all* merchant shops of a given app (not per-tenant), any merchant who has legitimately installed the app receives real webhook deliveries with a valid `(raw_body, hmac)` pair signed under that same shared secret. That merchant can replay the identical `raw_body`/`hmac` pair while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` only recomputes and compares the HMAC of `raw_body` [5](#0-4) , so the forged request still passes verification, and the handler will process the (attacker-controlled but validly-signed) body content as if it belonged to the victim shop.

### Impact Explanation
This breaks a cross-tenant identity binding: the shop value trusted by the host application as the source-of-truth tenant key is not authenticated by the same signature that authenticates the payload. Any app that uses `data.shop` from `WebhookMetadata` to select which merchant's stored session/access token to update, invalidate, or act upon (the documented and expected usage pattern) can be made to associate an attacker-chosen `body` with a different tenant's `shop`, causing cross-tenant data confusion/corruption without needing the app's `client_secret`, an access token, or any credential beyond having installed the app as an ordinary (potentially free/trial) merchant. This matches the "Critical – cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high in impact but requires: (1) attacker installs the app on a real shop and receives at least one legitimate webhook (any topic, since only the body/HMAC pair matters, not topic-shop binding — though `topic` is also unauthenticated header data), and (2) the host application relies on `data.shop` as an unauthenticated trust anchor for tenant selection when processing the body, which is the pattern the gem's own documentation recommends. The gem itself provides no mechanism (e.g., binding `shop`/`topic` into the signed payload, or validating that the header-provided shop actually owns a registered webhook subscription matching the body) to prevent this relabeling.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`) in the HMAC-covered signable string, or independently verify that the `shopify-shop-domain` header corresponds to a shop with an active, matching webhook registration/subscription before dispatching to the handler, rather than trusting the header value as-is once body-HMAC passes.

### Proof of Concept
```ruby
# Attacker has legitimately installed the app on their own shop "attacker.myshopify.com"
# and captured a real webhook delivery for topic "customers/data_request":
raw_body = '{"customer":{"id":123,"email":"victim@example.com"}}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
# (This hmac is valid because ShopifyAPI::Context.api_secret_key is the same for every shop of this app.)

forged_headers = {
  "shopify-topic"       => "customers/data_request",
  "shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "shopify-shop-domain" => "victim.myshopify.com",  # relabeled to a different tenant
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked),
#    and the handler receives WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-controlled>)
```
Note: I could not fully verify how a specific downstream app (e.g. `shopify_app`) uses `WebhookMetadata#shop` at the storage layer, since that logic lives outside this gem; the documentation in this repo, however, explicitly recommends using `data.shop` as the tenant key for subsequent processing.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
