Docs at `docs/usage/webhooks.md:125` explicitly promise: *"This will verify the request did indeed come from Shopify and then call the specified handler for that webhook."* This is the exact contract broken by the implementation.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are trusted from unauthenticated headers while the HMAC signs only the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verified by `Utils::HmacValidator.validate` in `Registry.process` binds solely to the JSON body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) and are never included in the signed content, yet `Registry.process` passes them straight into the app's `WebhookHandler` as trusted `WebhookMetadata` after the HMAC check succeeds.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [1](#0-0) 

`request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are simple header readers:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

The HMAC validator only checks `computed_signature = compute_signature(verifiable_query.to_signable_string, secret)` against the received hmac header — i.e., it authenticates the body bytes with the app's shared `api_secret_key`, not the shop-domain, topic, or webhook-id headers: [3](#0-2) 

Because the `api_secret_key` is a single shared secret for the whole app (not per-shop), any merchant who has installed the app receives real, validly-signed webhooks for their own store. Since the identity binding equality that should hold is `hmac == HMAC(secret, body || shop || topic || webhook_id)` but the implementation only enforces `hmac == HMAC(secret, body)`, an attacker who legitimately received one authentic webhook (with a valid `hmac` value for some `raw_body`) can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain (and/or a different `topic`/`webhook_id`). The signature still validates because the signed content is unchanged, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain and arbitrary attacker-chosen `topic`/`webhook_id`, tricking the host app into attributing attacker-supplied data to another tenant.

### Impact Explanation
This breaks the tenant-identity binding the docs promise ("verify the request did indeed come from Shopify") and results in cross-tenant data injection: an unprivileged internet user (any merchant who installed the app and thus can obtain one valid webhook signature) can forge webhook events that host applications will process as belonging to a different shop, corrupting per-tenant state, queues, or database records keyed by `shop`. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Any app using this gem's webhook processing exposes `Registry.process` on a public HTTP endpoint as documented. Obtaining one authentic `(raw_body, hmac)` pair only requires installing the app on the attacker's own store (or observing one webhook they legitimately received), which is trivial for an unprivileged user. No knowledge of `api_secret_key` is required — only replay of previously observed valid signed bytes with modified headers.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content (or otherwise cryptographically bind them, e.g. by validating `shop` against a list of shops with active app installations tracked by the host app, and rejecting replays via `webhook_id` uniqueness checks) before trusting these header-derived values in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker.myshopify.com`, granting Shopify knowledge of a valid `api_secret_key`-derived HMAC for the app.
2. Shopify sends attacker a legitimate webhook, e.g. `orders/create` with body `{"id":1}"`, headers including `x-shopify-hmac-sha256: <validHMAC(body)>` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker POSTs the same `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook route, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the body bytes against the secret [4](#0-3) .
6. `Registry.process` calls `handler.handle` with `WebhookMetadata#shop == "victim.myshopify.com"` even though the request never originated from Shopify for that shop [5](#0-4) , causing the host application to process attacker data under the victim's tenant identity.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
