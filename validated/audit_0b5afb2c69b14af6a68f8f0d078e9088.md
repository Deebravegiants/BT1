### Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` authenticates nothing but the byte content of the body. The `shop`, `topic`, and `webhook_id` values that `Registry.process` uses to route and attribute the webhook are read straight from unauthenticated HTTP headers.

### Finding Description
`Registry.process` is the entry point the host app calls to handle an inbound webhook: [1](#0-0) 

It only checks `Utils::HmacValidator.validate(request)`, which computes/verifies the signature over `request.to_signable_string`: [2](#0-1) 

But `to_signable_string` for a webhook `Request` is defined as just the raw body: [3](#0-2) 

Meanwhile `shop`, `topic`, and `webhook_id` are parsed from HTTP headers that are never part of the signed content: [4](#0-3) 

and those exact unauthenticated values are what gets passed to the handler as the tenant/topic identity of the event: [5](#0-4) 

The binding that should hold is: `HMAC(secret, signed_bytes)` should authenticate the *tuple* `(shop, topic, body)` that the handler acts on. Instead it authenticates only `body`; `shop` and `topic` are asserted-but-unverified. Formally: `verify(hmac, body) == true` is treated as `authenticated(shop, topic, body) == true`, which is false whenever `shop`/`topic` can be supplied independently of the signed bytes.

This directly parallels the reported `c-kzg-4844` bug class: a verification function is called with parameters that make the resulting proof cover less data than what the caller subsequently trusts (there, commitments excluded from the Fiat–Shamir challenge; here, `shop`/`topic` excluded from the HMAC input) — in both cases a value that is *acted upon* downstream is not bound by the signature/challenge that is presented as having validated it.

### Impact Explanation
Because the app's single `api_secret_key` is shared across every merchant/shop that has installed the app, any actor able to trigger a genuine webhook delivery for their *own* store (i.e., a legitimate merchant, or anyone who can get Shopify to deliver one webhook with a validly computed HMAC over some body) obtains a `(body, hmac)` pair that remains valid for that body regardless of which `shop-domain`/`topic`/`webhook-id` header accompanies it. Replaying that exact body with a different `x-shopify-shop-domain` header (spoofing a victim tenant that also uses the app) passes `HmacValidator.validate` and is handed to the handler as `WebhookMetadata` claiming to originate from the victim shop. If the host application trusts `WebhookMetadata#shop` to select which tenant's data to update (a common pattern, since this is literally the value the gem hands back as the shop identity), this results in cross-tenant data being attributed to, or acted on behalf of, the wrong merchant — a cross-tenant boundary violation.

### Likelihood Explanation
Exploitation requires the attacker to control (or observe) at least one raw HTTP request whose body+HMAC pair is valid for the shared `api_secret_key` — achievable by any developer/merchant who has legitimately installed the app and can trigger events (e.g., creating an order in their own store generates a validly-HMAC'd webhook body they fully observe), then replaying that body to the app's webhook endpoint with forged `shop-domain`/`topic`/`webhook-id` headers. No access to `api_secret_key` itself, TLS interception, or privileged accounts is needed — only network reachability to the app's own webhook endpoint, which is inherently internet-facing. Likelihood is elevated further because `Request.new` performs no cross-check that the header-derived `shop` is one the app has an active session/installation for; the gem provides no such binding at all.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the bytes that are HMAC-verified, or otherwise bind them to the signed body (e.g., canonicalize `shop|topic|webhook_id|body` before computing/verifying the digest) so that `to_signable_string` for `Webhooks::Request` cannot be satisfied by mixing a validly-signed body with attacker-chosen header values. At minimum, document prominently that host applications must independently verify `WebhookMetadata#shop` against a known/installed shop before trusting it, since the gem itself performs no such binding.

### Proof of Concept
1. App has `Context.api_secret_key = S` shared by all installed shops `A` (attacker-controlled) and `B` (victim).
2. Attacker triggers any event in shop `A` (e.g. creates a test order), causing Shopify to deliver a webhook to the app with body `raw_body` and header `X-Shopify-Hmac-Sha256: HMAC(S, raw_body)`, `X-Shopify-Shop-Domain: A`, `X-Shopify-Topic: orders/create`.
3. Attacker captures `raw_body` and the valid `hmac` value (both fully visible to them since they own shop `A`).
4. Attacker crafts a new request to the app's webhook endpoint with the identical `raw_body`/`hmac`, but sets `X-Shopify-Shop-Domain: B` (or a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` accepts it; `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks `hmac` against `raw_body` — never against `shop`/`topic`: [5](#0-4) [6](#0-5) 
6. The app's registered handler receives `WebhookMetadata` with `shop: "B"` even though the event and body actually originated from shop `A`, demonstrating the binding break.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
