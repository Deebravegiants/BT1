### Title
Unvalidated swap routes can inject unauthorized token transfers into the caller's authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The controller accepts an opaque `StrategySwap` payload and forwards it to the configured router without restricting the venue contracts that the route may invoke. [1](#0-0)  A malicious venue can place an unrelated `token.transfer(victim, attacker, amount)` beneath the victim's authorized strategy call; if the victim signs the simulated authorization tree, the transfer executes and steals wallet funds unrelated to the strategy. [2](#0-1) 

### Finding Description
`swap_collateral` authenticates the caller and account owner, withdraws collateral, and passes the user-supplied `swap` into `withdraw_and_swap_from_supply`. [3](#0-2)  `swap_tokens` validates only that the payload is non-empty, grants the router one exact input transfer, invokes `execute_strategy`, and then validates only measured token input/output deltas. [4](#0-3) 

No controller-side check restricts the route to known Aquarius or Soroswap pools. The repository's harness demonstrates the resulting authorization-tree injection: a router double invokes the payload-selected hop contract, and that contract calls `token::Client::transfer(victim, attacker, amount)`. [5](#0-4) [2](#0-1)  Simulation records the malicious transfer as a child of the victim's `swap_collateral` authorization, and signing that tree drains the victim's wallet token. [6](#0-5) 

The measured-output and final-account checks do not bound this loss because the stolen token need not be the route's `token_in` or `token_out`, and the strategy can still return a fair swap output. [7](#0-6) 

### Impact Explanation
A crafted route can steal arbitrary token balances from the strategy caller's wallet when the caller signs the generated authorization tree. This is direct theft of user funds rather than merely poor execution: the malicious child transfer can name a token, recipient, and amount unrelated to the lending operation. [8](#0-7) 

### Likelihood Explanation
Any unprivileged account owner or delegate can reach the vulnerable parameter through `swap_collateral`; related strategy paths also pass attacker-controlled route bytes to the same settlement helper. [3](#0-2) [9](#0-8)  Exploitation requires the victim to submit and sign a malicious route whose simulation contains the extra child authorization, so it depends on route delivery or client validation rather than being a purely permissionless on-chain theft.

### Recommendation
Do not treat opaque route bytes as safe merely because token deltas are measured. Restrict routes to a governance-approved venue registry, or add router/controller enforcement that permits only known venue contracts and expected token transfers for the declared route. Clients should additionally reject any authorization tree containing children beyond the exact expected input transfer, but contract-side venue allowlisting is needed to make the protocol boundary safe.

### Proof of Concept
1. The attacker deploys a contract exposing the venue interface expected by the swap route.
2. The venue's swap function executes:
   `token::Client::new(&env, &victim_token).transfer(&victim, &attacker, &victim_balance)`.
3. The attacker constructs a `swap_collateral` transaction with:
   - a funded victim account;
   - valid `current` and `new` markets;
   - positive `from_amount`;
   - a `swap` payload routing through the malicious venue;
   - a positive fair `min_out`, so all controller output and account checks pass.
4. Transaction simulation records the malicious token transfer as a child of the victim's `swap_collateral` authorization. [10](#0-9) 
5. If the victim signs the generated tree, the malicious venue transfers `victim_balance` of an unrelated wallet token to the attacker while the lending strategy still completes normally. [11](#0-10)
