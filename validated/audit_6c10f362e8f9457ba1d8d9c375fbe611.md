### Title
Replayable calldata-execution signature across chains in `pallet-hyper-fungible-token` — ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
The signed payload that authorizes execution of an arbitrary runtime call attached to an incoming cross-chain token transfer omits any chain/genesis-binding value, hashing only `(account_nonce, runtime_call)`. If the same beneficiary account exists at the same nonce on more than one chain running `pallet-hyper-fungible-token`, a signature captured on one chain can be replayed to dispatch the same runtime call on another chain.

### Finding Description
In `Pallet::on_accept`'s calldata-execution branch, when an incoming `PostRequest` carries `SubstrateCalldata`, the module verifies an optional signature over the tuple `(nonce, runtime_call)`, where `nonce` is `frame_system::Pallet::<T>::account_nonce(beneficiary)`: [1](#0-0) 

For all three supported signature schemes (Ed25519, Sr25519, Ecdsa) the hashed message is built purely from the local account nonce and the call bytes: [2](#0-1) 

There is no state-machine identifier, genesis hash, or any other chain-scoping value folded into the signed digest — unlike other signature-consuming code paths in this codebase, e.g. `pallet-ismp-relayer`'s `message()`/`beneficiary_message()`, which explicitly fold in `dest_chain`/`state_machine` specifically to prevent this exact class of replay: [3](#0-2) [4](#0-3) 

Replay protection for the HFT calldata signature relies solely on `account_nonce` being incremented after dispatch: [5](#0-4) 

`account_nonce` is local, per-chain state. Since `pallet-hyper-fungible-token` (and its EVM twins `HyperFungibleToken`/`WrappedHyperFungibleToken`) is meant to be deployed identically on multiple chains using the same message/ABI format, and account identity (an sr25519/ed25519/ecdsa keypair, or the EVM-derived SS58 account) is portable across chains, a beneficiary account that has performed the same number of prior calldata-executions on two different HFT-enabled chains will have the identical `nonce` on both. A signature the user (or an attacker who captured the signed payload in transit) produced for chain A is therefore a valid signature for chain B too, since the digest carries no chain-distinguishing information.

### Impact Explanation
An attacker who observes/relays a `SubstrateCalldata` signature intended for execution on one destination chain can replay it on another destination chain that also runs `pallet-hyper-fungible-token`, causing the runtime call to be dispatched with `RawOrigin::Signed(beneficiary)` on a chain the signer did not intend. Because the `runtime_call` is arbitrary (subject only to `BaseCallFilter`), this can result in unauthorized transfers, unintended approvals, or other state-changing actions signed with the victim's authority being executed on a chain outside the scope the victim signed for — a form of unauthorized app action / potential fund movement analogous to the reported `changeRecipientAddress` cross-chain signature replay.

### Likelihood Explanation
Exploitability requires: (1) the calldata-execution feature being used with a signature (not the "no signature, derive origin from sender" path), (2) the same beneficiary account existing/being reachable on ≥2 chains running the pallet with the same nonce value, and (3) the attacker being able to observe a signed cross-chain message and resubmit its calldata payload as a fresh incoming request to another chain (the payload travels inside the ISMP `Message.data` field of a `PostRequest`, which a relayer — an unprivileged, permissionless role in Hyperbridge — can construct and dispatch). Given nonces frequently start at (or return to) 0 for freshly used accounts on a new chain, and that Hyperbridge is explicitly designed for multi-chain deployment of this same pallet/message format, the condition is realistically reachable by any relayer or intent solver interacting with the token bridge.

### Recommendation
Bind the signed digest to the destination chain by including `T::IsmpHost::host_state_machine()` (or an equivalent genesis-hash / state-machine identifier) in the hashed payload, mirroring the pattern already used in `pallet-ismp-relayer`'s `message()` and `beneficiary_message()` (which include `dest_chain`/`state_machine`). E.g. change the hashed payload to `(nonce, host_state_machine, runtime_call).encode()` for all three `MultiSignature` variants in `on_accept`.

### Proof of Concept
1. User signs `(nonce=0, runtime_call=X)` intending it to execute only after a token transfer lands on Chain A's `pallet-hyper-fungible-token`.
2. A relayer/attacker observes this signed `SubstrateCalldata` inside the ISMP `PostRequest.body` en route to Chain A.
3. The same beneficiary account also exists on Chain B (another HFT-enabled chain) and happens to have `account_nonce == 0` there (e.g., it has never executed calldata via this pallet on Chain B).
4. The attacker crafts (or relays through the normal ISMP delivery path) an equivalent incoming `PostRequest`/message destined for Chain B carrying the identical `SubstrateCalldata` (signature + `runtime_call` bytes unchanged).
5. `Pallet::on_accept` on Chain B independently computes `msg = keccak256((0u64, runtime_call).encode())` — identical to what was signed for Chain A — and the same signature verifies successfully, since chain identity is not part of the digest.
6. `runtime_call` X is dispatched with `RawOrigin::Signed(beneficiary)` on Chain B, even though the user never authorized action on Chain B. [6](#0-5)

/// Signed payload for [`WithdrawalInputData`]. Includes the per-relayer nonce so a captured
/// signature cannot be replayed.
pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
