## Title
Reentrant fund drain via checks-effects-interactions violation in `IntentGatewayV2.withdraw()` (Tron variant) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron build of the Intent Gateway contains its own, divergent copy of the escrow-release routine `withdraw()`. Unlike the canonical EVM implementation (`IntentsBase._withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol`), which decrements the escrow accounting *before* transferring funds out, the Tron copy transfers funds out *first* and only decrements `_orders[commitment][token]` afterward. This is the same root-cause pattern flagged in the external `HATArbitrator` report: a transfer is executed based on state that has not yet been effectively/atomically validated against the real remaining balance, and no reentrancy protection exists to prevent that state from being read twice before it is updated.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` [1](#0-0)  only validates that escrow is non-zero (`if (_orders[body.commitment][token] == 0) revert UnknownOrder();`), then performs the token/native transfer, and only *after* the external call decrements `_orders[body.commitment][token] -= amount`:

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    for (uint256 i; i < len;) {
        ...
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");   // external call FIRST
            ...
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            ...
        }
        _orders[body.commitment][token] -= amount;   // state updated AFTER
        ...
    }
```

Compare this to the canonical EVM logic in `IntentsBase._withdraw` [2](#0-1) , which correctly follows checks-effects-interactions: `_orders[commitment][token] = escrowed - amount;` is written *before* `_sendValue`/`safeTransfer` is invoked. The Tron copy of `withdraw()` inverts this order and is reachable from `onAccept()` (permissionless-triggered, but host/authentication-gated ISMP delivery) for `RedeemEscrow`/`RefundEscrow` messages [3](#0-2) , and from `onGetResponse()` for source-chain cancellation refunds [4](#0-3) .

Because the native-token branch uses a raw `.call{value: amount}("")` to an attacker-controlled `beneficiary` (the solver for `RedeemEscrow`, or the order's own `user` for `RefundEscrow`/cancellation), the beneficiary contract's `receive()`/`fallback()` executes *before* `_orders[commitment][token]` is decremented. From that callback, the beneficiary can re-enter the gateway (e.g. via same-chain `cancelOrder`/`fillOrder` paths that read the same `_orders[commitment][token]` slot) and trigger a second release of the same escrowed balance, since the mapping still reflects the pre-withdrawal amount. No reentrancy guard (`nonReentrant`) is present in this file.

### Impact Explanation
This allows an attacker who controls the order (as user/canceller) or is the filling solver to drain escrowed order funds by re-entering before the escrow ledger is updated — a direct "permanent freezing/theft of user funds" outcome analogous to the `HATArbitrator` finding, where a transfer was executed against state that hadn't been properly validated/updated first. This is High severity: it results in concrete theft of user-escrowed value on the Tron deployment of the Intent Gateway, reachable from an ordinary user's own order lifecycle (place → cancel/fill → onAccept/onGetResponse), i.e. from a single submitted transaction/relayed message, no privileged role required.

### Likelihood Explanation
Likelihood is limited by the requirement that the escrowed input token be the native asset (`token == address(0)`), since the ERC20 branch uses a low-level `.call` to a standard `transfer` selector without hooks (standard ERC20 tokens do not re-enter). Reentrancy via native transfer requires the beneficiary to be a contract with a `receive()`/`fallback()` that calls back into the gateway. This is fully attacker-controlled (an attacker can simply create their own order with a native-token input, act as beneficiary, and re-enter), making exploitation straightforward for any attacker willing to use the Tron intent-gateway with native-asset escrow.

### Recommendation
Apply the same checks-effects-interactions ordering already used in the canonical `IntentsBase._withdraw`: decrement `_orders[body.commitment][token]` (and check `amount <= escrowed`, not just `!= 0`) before making the external transfer/call. Additionally add a reentrancy guard (`nonReentrant`) to `withdraw()`, `onAccept()`, `onGetResponse()`, and any other externally reachable functions that read/write `_orders`, consistent with best practice already followed in the primary EVM contract.

### Proof of Concept
1. Attacker places a same-chain (or cross-chain) order on the Tron `IntentGatewayV2` with a native-token (`address(0)`) input of value `V`, setting themselves as `order.user`, using a smart-contract wallet as `beneficiary`/`user`.
2. Attacker triggers cancellation (`cancelOrder`) once the deadline is reached (or, for cross-chain, once the fill/cancel message routes back via ISMP to `onAccept`/`onGetResponse`), causing `withdraw()` to be invoked with `token == address(0)`, `amount == V`.
3. Inside `withdraw()`, before `_orders[commitment][address(0)]` is decremented, the `beneficiary.call{value: V}("")` invokes the attacker's contract `receive()`.
4. From `receive()`, the attacker's contract re-enters the gateway (e.g., calls the same-chain cancel/withdraw path again for the same `commitment`), which still sees `_orders[commitment][address(0)] == V` (not yet decremented) and passes the `!= 0` check, transferring `V` again.
5. Repeating step 3–4 (bounded by gas) drains multiples of `V` from the gateway's native-token balance for a single `V`-sized escrow, before the outer call's own decrement finally executes.

Note: this PoC targets the Tron-specific contract copy (`evm/tron/contracts/apps/IntentGatewayV2.sol`); the mainline EVM Solidity contracts (`IntentsBase.sol`, `IntrinsicIntents.sol`, `ExtrinsicIntents.sol`) already implement the safe (decrement-then-transfer) ordering and are not affected by this specific issue.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
