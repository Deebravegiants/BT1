### Title
Webhook shop-domain identity is trusted without being covered by the HMAC, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as "verified to come from Shopify" once `Utils::HmacValidator.validate` succeeds, and then hands the request's `shop` field to the app's handler as trustworthy tenant identity. However, the HMAC only signs the raw body, not the `shop-domain` header, so the shop attribution can be forged independently of the signature check.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` (`lib/shopify_api/utils/verifiable_query.rb`), whose contract is `hmac` + `to_signable_string`. For webhooks, `to_signable_string` returns **only** the raw body: [1](#0-0) 

The `shop` accessor, by contrast, is read directly from an attacker-controllable HTTP header with no cross-check against anything covered by the signature: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(client_secret, signable_string)` and compares it to the `hmac-sha256` header — again, only the body is included in `signable_string`: [3](#0-2) 

`Registry.process` uses exactly this validation to gate trust, then immediately passes the (unverified) `shop` field into the handler as authoritative tenant identity: [4](#0-3) 

The library's own documentation describes `process` as verifying "the request did indeed come from Shopify," implying the whole payload — including the shop — can be trusted by the handler: [5](#0-4) [6](#0-5) 

**The broken identity binding** (as an equality that fails):
`shop-domain header value` (used by the app to attribute the webhook body to a tenant) is expected to equal `shop that authorized/generated the signed body`, but the gem only guarantees `HMAC(client_secret, body)` is valid — it never binds `shop-domain` into that signature. So:

`shop_used_by_handler == shop_that_actually_produced(body)` is NOT enforced by `HmacValidator.validate`; only `HMAC(body) == received_hmac` is enforced.

Because the `client_secret` used to compute the HMAC is scoped to the **app**, not to an individual shop, any shop that has installed the app can legitimately obtain valid `(body, hmac)` pairs for events on its own store (e.g., by registering an HTTP webhook subscription — via `Registry.register`/the Admin API — with a callback URL the attacker controls, such as a personal server or webhook-capture endpoint). Since the app's shared secret produced that HMAC, and the signable string never included the shop domain, the attacker can:
1. Capture a legitimate `(raw_body, x-shopify-hmac-sha256)` pair generated by Shopify for a webhook fired by their own store.
2. Replay that exact `raw_body` + `hmac` to the real app's webhook endpoint, but with the `x-shopify-shop-domain` / `shopify-shop-domain` header rewritten to a victim shop's domain.
3. `HmacValidator.validate` still succeeds (body/hmac pair unchanged), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: <victim shop>, body: <attacker's own data>, ...)`.

### Impact Explanation
This is a cross-tenant identity/data-attribution bypass: the app is made to believe attacker-controlled data (and the associated event, e.g. an `orders/create` or `app/uninstalled` payload) originated from an arbitrary victim shop chosen by the attacker, without needing the app's `client_secret`, an access token, or any privileged access to the victim. Any downstream logic that keys off `WebhookMetadata#shop` (e.g., writing to the victim's tenant record, triggering victim-specific side effects, or resetting/altering victim state such as via `app/uninstalled`) can be manipulated by an unrelated merchant. This matches "cross-tenant access" under the Critical impact criteria.

### Likelihood Explanation
Reachable by an ordinary, unprivileged internet user who simply signs up for/installs the vulnerable app on any shop they control (no TLS interception, no leaked credentials, no access token needed) and then crafts a raw HTTP POST to the app's public webhook endpoint. The only "special" step is capturing one legitimate `(body, hmac)` pair for their own shop, which is achievable through the standard, documented `Registry.register`/webhook-subscription workflow this gem itself exposes. No brute force of the HMAC secret is required.

### Recommendation
Bind the shop identity into the value verified by `HmacValidator`. Concretely:
- Extend `Webhooks::Request#to_signable_string` (or a separate check in `Registry.process`) to require that the shop domain from the header matches a shop the app actually expects (e.g., cross-checked against a stored session/webhook registration for that topic+shop), not merely accepted as-is once the body-only HMAC passes.
- At minimum, document prominently that `shop` on `WebhookMetadata` is *not* cryptographically bound by `HmacValidator.validate` and must be independently corroborated (e.g., against an existing installed-shop record) before being trusted for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal, unprivileged onboarding).
2. Attacker registers an `orders/create` webhook pointing at a server they control (via `ShopifyAPI::Webhooks::Registry.register`/Admin API, a legitimate, self-service action for their own shop).
3. Attacker triggers an order creation in their own store; Shopify POSTs to the attacker's own endpoint with headers including `x-shopify-hmac-sha256: <H>` and body `B`, where `H = HMAC_SHA256(app_client_secret, B)`.
4. Attacker crafts a new POST to the real app's public webhook endpoint:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
5. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H`, per `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
6. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and processes attacker-controlled data as if it belongs to the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
