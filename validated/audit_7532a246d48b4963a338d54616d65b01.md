### Title
Malicious token in a multi-asset order permanently freezes escrow release for all other tokens in the same order via unguarded `safeTransfer` in `_withdraw` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` iterates over every escrowed token in an order and releases them to the beneficiary using `IERC20.safeTransfer`, with no isolation between tokens. Because a user fully controls which tokens go into `order.inputs` when placing an order (`placeOrder`), a single malicious/blocking ERC20 in a multi-asset order can revert the entire withdrawal call, permanently freezing the release of the other, legitimate tokens escrowed under the same commitment — mirroring the `closeCompetition()` bug class where one unsafe external token call blocks an entire claim.

### Finding Description
`_withdraw` is the shared internal function that releases escrowed assets for a commitment, called from both the cross-chain `onAccept` path (`RedeemEscrow`/`RefundEscrow`, `ExtrinsicIntents.sol`) and the same-chain fill/cancel path (`IntrinsicIntents.sol`): [1](#0-0) 

It loops over `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each token in sequence, with no try/catch or per-token failure isolation. If any one of the tokens is a malicious/misbehaving ERC20 (e.g., a token that reverts on transfer to a specific address, a blocklist token, or one that simply always reverts), the `safeTransfer` call reverts the entire `_withdraw` execution — blocking release of every *other*, legitimate token bundled in the same order/commitment.

An order can contain multiple `inputs`/`outputs` tokens (`TokenInfo[]`), and the order creator (a user placing an order via `placeOrder`) fully controls the token addresses included in `order.inputs`. For cross-chain orders, `_withdraw` is invoked from `onAccept`, which is dispatched by the Hyperbridge host via a low-level `.call()`: [2](#0-1) 

A revert there causes the receipt to be deleted "so that it can be retried" — but if the malicious token deterministically reverts every time (e.g., it always reverts unconditionally, or blocklists the escrow/beneficiary address), every retry fails identically, and the funds (including the co-escrowed legitimate tokens) are permanently stuck, exactly like the referenced `closeCompetition()` bug where an unsafe `balanceOf`/token call bricks the entire claims flow.

### Impact Explanation
This is a permanent freezing-of-funds bug: legitimate escrowed assets (input tokens paid by a user, or output tokens owed to a solver) become permanently unrecoverable because they are commingled in the same withdrawal transaction as a malicious/adversarial token supplied by the same order. This satisfies "permanent freezing of funds" impact criteria for the intents escrow path, a directly reachable component from a single `placeOrder`/`fillOrder` transaction with no privileged role required.

### Likelihood Explanation
Likelihood is high: any unprivileged user can place a multi-asset order including one legitimate token (e.g. USDC) alongside one adversarial ERC20 contract they deploy or select (e.g., a fee/blocklist/reverting token). Once escrow is established and a fill/redeem/refund is triggered, `_withdraw` will always attempt to transfer both tokens in the same call, and the malicious token's revert blocks the legitimate token permanently.

### Recommendation
Isolate per-token transfers in `_withdraw` so a failure in one asset does not block release of the others — e.g., wrap each `safeTransfer` in a try/catch (or use a low-level `.call` with success check) and, on failure, either skip and let the beneficiary reclaim later via a separate emergency-sweep path, or emit an event and keep the escrow accounted (not silently dropped) for that specific token only, rather than reverting the whole batch.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer()` always reverts (or reverts specifically when the recipient is the eventual beneficiary/solver address).
2. Attacker (or any user) calls `placeOrder` with `order.inputs = [{token: USDC, amount: 1000e6}, {token: EvilToken, amount: 1}]`, escrowing both tokens under one `commitment`.
3. A solver fills the order (same-chain or cross-chain); the fill path eventually calls `_withdraw(body, ..., finalize: true)` with `body.tokens` containing both `USDC` and `EvilToken`.
4. Inside the loop in `IntentsBase._withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`), `IERC20(EvilToken).safeTransfer(...)` reverts, unwinding the entire transaction — the `USDC` transfer that would otherwise have succeeded is rolled back too.
5. For the cross-chain path, this revert propagates back through the host's low-level `.call` in `dispatchIncoming`/equivalent handler, which deletes the receipt for retry — but every retry hits the same revert, permanently freezing the `USDC` escrow alongside the un-transferable `EvilToken`.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
