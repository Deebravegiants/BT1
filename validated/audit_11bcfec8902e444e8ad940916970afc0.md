### Title
Cross-Tenant Webhook Spoofing via `shop-domain` Header Not Covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the `shop` field — parsed from the unauthenticated `X-Shopify-Shop-Domain` header — for all downstream tenant-scoped handling. Because the `shop` field is never included in the HMAC-signed payload, an attacker holding one valid `(raw_body, hmac)` pair (e.g., from their own legitimately-installed shop) can replay it to the app's webhook endpoint with an arbitrary `shop-domain` header and have it accepted as authentic data for a different tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field [1](#0-0) . For webhooks, `to_signable_string` returns only the raw JSON body: [2](#0-1) . The `shop` accessor, however, is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of the signed material at all: [3](#0-2) .

`Registry.process` validates only the HMAC-over-body check, then immediately trusts `request.shop` and hands it to the host application's handler: [4](#0-3) . The resulting `WebhookMetadata` struct carries `shop` as an opaque, un-signed `String` that the handler is expected to use to attribute the event to a tenant: [5](#0-4) .

Critically, the HMAC secret (`Context.api_secret_key`) is a single, app-wide secret shared across every shop that installs the app — it is not shop-specific: [6](#0-5) . This means any `(body, hmac)` pair that validates for one shop validates identically for every other shop, since neither the shop identity nor any per-tenant binding is part of the signed content.

**Binding that is broken (as an equality):**
`shop_used_for_tenant_routing (from unsigned header) == shop_bound_by_hmac (none — HMAC covers body only)`

This is the same class of defect as the reference report: a downstream-critical field ("shop", analogous to "rewardToken index"/creator identity) is *acted upon* by privileged logic (`Registry.process` → tenant-scoped `handler.handle`) without being *covered by the authenticity check* (HMAC), exactly the "bytes verified versus bytes parsed" / "field acted on but not covered by the HMAC" analog called out in scope.

### Impact Explanation
An attacker who is a legitimate (even free-tier) merchant of the host app can capture a genuine webhook delivery for their own shop (valid `raw_body` + valid `hmac`, since the secret is shared across all installs). They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (only the body is checked), and `Registry.process` forwards `shop: <victim-domain>` to the host application's webhook handler as if it were authentic data originating from the victim's store. Any host app that uses this `shop` value to look up/update tenant-scoped records (e.g., "look up victim's session and store this order/webhook payload") is subject to cross-tenant data injection/confusion — data from one tenant's shop event is attributed and applied to another tenant, a Critical-class cross-tenant impact.

### Likelihood Explanation
This requires the attacker to be an "unprivileged internet user" relative to the app secret — they need only be a normal user of the app (installing it on a shop they control) to legitimately receive a valid `(body, hmac)` pair, and then send crafted HTTP requests directly to the app's public webhook endpoint with a modified header. No access to `api_secret_key`, access tokens, or privileged credentials is required, satisfying the analog scope. The main constraint is that the attacker needs to obtain at least one topic/body they want replayed under another shop's identity, which is straightforward for any webhook topic they can trigger on their own store (e.g., an `orders/create` or `app/uninstalled` payload with attacker-controlled content, replayed as if from the victim).

### Recommendation
Bind the shop identity into the authenticity check rather than trusting an unsigned header:
- Cross-check the `shop` header value against a value looked up via a trusted mechanism (e.g., only accept webhooks for shops that the host app has stored as installed, and require the app to independently validate that this is an expected event id/source), or
- Where feasible, prefer per-shop shared secrets or otherwise include the `shop` value as part of the signed content the host verifies before trusting it for tenant attribution, and document explicitly (in `docs/usage/webhooks.md` and in `WebhookMetadata`) that `shop` is NOT authenticated by `HmacValidator.validate` and must not be used alone for tenant-scoped writes without additional verification (e.g., confirming an active, stored session/webhook registration for that exact shop+topic+webhook_id).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the exact raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify sent (computed with the app's single, shared `api_secret_key`).
2. Attacker sends their own HTTP POST to the host app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic: orders/create` (unchanged)
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally: [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`B` only) and matches `H` — validation succeeds despite the forged shop header: [8](#0-7) .
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)` — the host app's tenant-scoped logic now processes attacker-controlled data attributed to the victim's shop: [9](#0-8) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
