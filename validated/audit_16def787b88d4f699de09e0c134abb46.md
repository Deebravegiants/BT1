### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw` allows silent escrow-release failure without token delivery - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order tokens using a raw low-level `.call` to the ERC20 `transfer` selector, checking only that the call itself did not revert, but never decoding/validating the returned boolean success value. This is exactly the bug class described in the external report (unsafe non-`safeTransfer` ERC20 interaction incompatible with non-standard tokens that return `false` instead of reverting on failure).

### Finding Description
In `withdraw()` (and the fee-redemption branch immediately after it), the escrow release path uses: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```
and for fee redemption:
```solidity
uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
if (fees > 0) {
    address feeToken = IDispatcher(host()).feeToken();
    (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
    if (!success) revert TransferFailed();
    delete _orders[body.commitment][TRANSACTION_FEES];
}
```

Both snippets only check the outer `success` boolean of the raw `.call`, which is `true` as long as the target contract does not revert. Non-standard ERC20 tokens (USDT-style tokens, or any token implementation that returns `false` on failure rather than reverting) will cause this check to pass even though no tokens were actually transferred to the beneficiary. Immediately after, `_orders[body.commitment][token] -= amount` (or `delete _orders[...][TRANSACTION_FEES]`) unconditionally decrements the escrow accounting as if the transfer succeeded.

Notably, elsewhere in the very same file the maintainers correctly use OpenZeppelin's `SafeERC20.safeTransferFrom`/`safeTransfer` (which validate return data) for escrowing inputs and fees: [2](#0-1) [3](#0-2) 

but the `withdraw` escrow-release path (reachable by any relayer/solver/beneficiary calling `onGetResponse` -> `withdraw(body, true)`, or the normal fill/redeem flow that also calls `withdraw`) bypasses `SafeERC20` and reverts to an unchecked raw `.call`.

### Impact Explanation
If the escrowed token is a non-standard ERC20 that signals failure by returning `false` instead of reverting, a call to redeem the escrow (via the GET-response callback path `onGetResponse` -> `withdraw(body, true)`, reachable by any relayer delivering a proof, or via the normal order-settlement withdrawal path) will:
- Decrement `_orders[commitment][token]` as if the beneficiary was paid.
- Leave the tokens permanently stuck in the `IntentGatewayV2` contract, since the escrow accounting entry that tracked them is destroyed.
- Result in a permanent loss of user/solver funds (the beneficiary never receives their tokens, and the escrow bookkeeping no longer reflects the trapped balance, so there is no path to retry or recover it).

This matches the "concrete theft or permanent freezing of funds" bar: the beneficiary permanently loses the escrowed asset while the contract's internal accounting is silently corrupted.

### Likelihood Explanation
Likelihood is token-dependent: it only manifests for ERC20 tokens whose `transfer` implementation returns `false` on failure rather than reverting (a known but less common non-standard behavior compared to USDT's "no return value" pattern, which OZ's `SafeERC20` handles gracefully via `success && (returndata.length == 0 || abi.decode(...))`). Any order using a supported input/output token with such semantics, or any solver-selected output token that a solver front-runs to make partially insufficient (e.g., zero balance or blacklist checks returning `false`), can trigger the loss during withdrawal. Given the intent gateway is designed to be permissionless with arbitrary user-specified `token` addresses in `TokenInfo`, and no token allow-list is evident in the reachable code, this is directly triggerable by any order participant choosing such a token.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (both the per-token escrow release loop and the transaction-fee redemption block) with `SafeERC20.safeTransfer`, consistent with the rest of the contract (and consistent with the non-Tron `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`, which already correctly uses `IERC20(token).safeTransfer(beneficiary, amount)` — see [4](#0-3) ). This ensures both non-returning tokens and false-returning tokens are handled safely, and that escrow accounting is never decremented unless the transfer is confirmed successful.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an ERC20 token `T` whose `transfer(address,uint256)` returns `false` (instead of reverting) when, e.g., the recipient is blacklisted or the contract is paused for transfers.
2. A user places an order with `T` as an output/fee token; solver fills it, escrow is credited in `_orders[commitment][T]`.
3. The redemption path is triggered (e.g., relayer delivers the GET response, invoking `onGetResponse` -> `withdraw(body, true)`), targeting a `beneficiary` for which `T.transfer` returns `false` (e.g., temporarily blacklisted, or insufficient contract-level state causing a graceful `false` return).
4. `token.call(...)` succeeds (`success == true`) because the low-level call itself didn't revert; the `false` return payload is never inspected.
5. `_orders[body.commitment][token] -= amount;` executes, permanently erasing the escrow record even though the beneficiary received nothing — the tokens remain stuck in the `IntentGatewayV2` contract with no accounting path to reclaim them.
