### Title
Missing allowlist/authorization check in `HandleLegacyUserMessage` allows any external caller to inject arbitrary trigger requests into the DON - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The `WebAPIHandler.HandleLegacyUserMessage` function is the entry point that the internet-facing gateway invokes for legacy (`web_api_trigger`) user messages. Unlike the sibling `vault` handler, which enforces an `Authorizer.AuthorizeRequest` check (allowlist-based digest authorization) before forwarding any request, this handler contains an explicit `// TODO: apply allowlist and rate-limiting here` comment and performs no sender authorization at all before forwarding the request to every member of the DON.

### Finding Description
`gateway.ProcessRequest` in `core/services/gateway/gateway.go` routes any decoded legacy request straight to `h.HandleLegacyUserMessage(ctx, msg, callback)` based solely on the `DonID` in the message body [1](#0-0) . Inside `HandleLegacyUserMessage`, the code validates payload decoding, a non-zero timestamp, and message staleness, but the only access-control-related step is a comment stating the check is not implemented:

```go
// TODO: apply allowlist and rate-limiting here
if msg.Body.Method != MethodWebAPITrigger {
``` [2](#0-1) 

After this, the message is transformed into a signed request and unconditionally fanned out to every DON member:

```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()

// Send original request to all nodes
for _, member := range h.donConfig.Members {
    err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
}
``` [3](#0-2) 

This is the same bug class as the reported "Missing Access Restrictions" — a function whose purpose is to relay privileged/authorized traffic lacks the modifier/check that would restrict who can invoke it. Compare this to the `vault` handler, which enforces authorization via `h.requestProcessor.ProcessRequest` before processing any secrets method [4](#0-3) , and to `allowListBasedAuth.AuthorizeRequest`, which explicitly checks a request digest against an on-chain allowlist before authorizing [5](#0-4) . The capabilities `WebAPIHandler` has no equivalent gate for legacy `web_api_trigger` requests. This is corroborated by the handler's own test suite, which contains the note: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated` [6](#0-5) .

### Impact Explanation
Any unprivileged client that can reach the gateway's HTTP endpoint can submit a `web_api_trigger` legacy message for a known `DonID`, and the gateway will forward the (attacker-controlled) trigger payload to every node in that DON without verifying the sender is an authorized workflow owner. This is impersonation of an authorized trigger source, letting an unauthorized user inject workflow trigger executions into DON nodes.

### Likelihood Explanation
Likelihood is high: the code path is reachable directly from `gateway.ProcessRequest`, which is the gateway's HTTP-facing request dispatcher [7](#0-6) , requires only a validly-formed legacy message with a fresh timestamp, and there is no cryptographic sender validation prerequisite blocking the call (unlike the `v2` JSON-RPC trigger path, which enforces sender/JWT authorization, e.g. in `http_trigger_handler_test.go`'s `HandleUserTriggerRequest_JWTAuthorization` tests [8](#0-7) ).

### Recommendation
Implement the sender allowlist and rate-limiting check referenced in the TODO comment at `core/services/gateway/handlers/capabilities/handler.go:384` before forwarding any message to DON members, mirroring the authorization pattern already used by the `vault` handler (`requestProcessor.ProcessRequest`) or the `AllowListBasedAuth.AuthorizeRequest` mechanism.

### Proof of Concept
1. An external, unauthorized actor sends an HTTP request to the gateway with a legacy-format JSON body containing a valid `DonID`, `MessageID`, `Method: "web_api_trigger"`, a fresh `Timestamp`, and an arbitrary `TriggerRequestPayload`.
2. `gateway.ProcessRequest` decodes it, finds the handler for the `DonID`, and calls `h.HandleLegacyUserMessage` [1](#0-0) .
3. `HandleLegacyUserMessage` validates only payload structure/timestamp freshness, then forwards the request to every DON member via `don.SendToNode` [9](#0-8)  — with no verification that the sender is an authorized workflow/trigger owner.

func (r *allowListBasedAuth) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	r.lggr.Debugw("AllowListBasedAuth authorizing request", "method", req.Method, "requestID", req.ID)
	requestDigest, err := req.Digest()
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to create digest", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	requestDigestBytes, err := hex.DecodeString(requestDigest)
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to decode digest", "method", req.Method, "requestID", req.ID, "requestDigest", requestDigest, "error", err)
		return nil, err
	}
	requestDigestBytes32 := [32]byte(requestDigestBytes)
	if r.workflowRegistrySyncer == nil {
		r.lggr.Errorw("AllowListBasedAuth workflowRegistrySyncer is nil", "method", req.Method, "requestID", req.ID)
		return nil, errors.New("internal error: workflowRegistrySyncer is nil")
	}
	allowlistedRequest, allowedRequestsStrs, err := r.findAllowlistedItemWithRetry(ctx, req, requestDigest, requestDigestBytes32)
	if err != nil {
		return nil, err
	}
	if allowlistedRequest == nil {
		r.lggr.Debugw("AllowListBasedAuth request digest not allowlisted",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"allowedRequestsStrs", allowedRequestsStrs)
		return nil, errors.New("request not allowlisted")
	}
