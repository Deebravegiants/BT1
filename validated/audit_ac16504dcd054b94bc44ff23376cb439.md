### Title
Webhook shop identity is not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but `to_signable_string`, which is the value verified by `Utils::HmacValidator`, contains only the raw request body. The identity of the tenant (`shop`) is therefore never bound to the HMAC that authenticates the request.

### Finding Description
`Webhooks::Registry.process` authenticates an inbound webhook solely via: [1](#0-0) [1](#0-0) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
```

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` only: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is defined to be just the raw body: [3](#0-2) 

But `shop` — the value that identifies which tenant the webhook belongs to, and which is passed on to the app's handler as trusted metadata — is pulled straight from the request header, completely outside the HMAC-covered bytes: [4](#0-3) 

The identity binding that should hold is:
`shop (verified by HMAC) == shop (acted on by the handler)`

but the actual binding is:
`raw_body (verified by HMAC) == raw_body (acted on by the handler)`, while `shop` is taken from an unauthenticated header — i.e., the equality is broken: the HMAC covers `raw_body` only, while the handler trusts `request.shop`, a field never included in the signable string.

Because Shopify apps share a single `api_secret_key` across all shop installations of the same app (it is per-app, not per-shop), any merchant who installs the app can obtain a genuinely Shopify-signed `(raw_body, hmac)` pair for their own store's webhook traffic. That attacker-observed pair remains a **valid** signature for the identical `raw_body` regardless of which `shop` header accompanies it, since the header is not part of the signed content. An attacker can then replay that captured `raw_body`/`hmac` pair to the app's single shared webhook endpoint while substituting `x-shopify-shop-domain` with a victim tenant's domain. `HmacValidator.validate` will pass (body+hmac still match), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), one of the explicitly in-scope Critical impacts. A host application built on this gem typically keys persisted data (sessions, customer records, order state, GDPR/webhook-driven business logic) by `WebhookMetadata#shop`. Since `shop` is unauthenticated, an attacker who is merely a legitimate but unprivileged user of the app (an ordinary merchant with their own store install) can inject data attributed to another merchant's tenant, corrupting or exfiltrating information cross-tenant purely through the gem's documented `Webhooks::Registry.process` / `Webhooks::Request` API — no access token, secret, or privileged account of the victim is required.

### Likelihood Explanation
The attacker only needs: (1) their own legitimate app installation to observe at least one valid `(raw_body, hmac)` webhook pair (trivial — install the app, trigger any webhook-eligible event), and (2) the ability to POST to the app's single shared webhook endpoint with a forged `shop` header, which is normal, unauthenticated HTTP access. No secrets, tokens, or elevated privileges are needed, making this readily reachable by any unprivileged internet user who can install/use the app.

### Recommendation
Bind `shop` (and ideally `topic`, `api_version`) into the HMAC-verified content, or otherwise cryptographically tie the header-derived `shop` value to the verified payload — e.g., include the shop domain in `to_signable_string`, or cross-check `request.shop` against a shop value embedded in the verified JSON body (Shopify includes shop-scoped identifiers in most webhook payloads) before trusting it in `WebhookMetadata`. At minimum, document and enforce that `Webhooks::Request#shop` must not be treated as authenticated unless additionally corroborated (e.g., against the caller's known session/shop registration) before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker.myshopify.com`), which shares the same `api_secret_key` as every other merchant's installation of this app.
2. Attacker triggers a webhook event on their own store, capturing the exact `raw_body` and the corresponding `x-shopify-hmac-sha256` value that Shopify computed and sent to the app's webhook endpoint.
3. Attacker replays an HTTP POST to the app's (shared, single) webhook URL using the captured `raw_body` and `hmac` header unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`raw_body` only) and finds it matches — validation succeeds.
5. `request.shop` returns `"victim-shop.myshopify.com"` from the forged header, and `WebhookMetadata.new(... shop: request.shop ...)` passes this trusted-looking but unauthenticated value to the app's handler, which processes/stores it as if it were an authentic webhook for the victim shop.
