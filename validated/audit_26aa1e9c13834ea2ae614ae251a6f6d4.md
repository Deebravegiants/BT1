### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from only the raw request body, while the `shop` (merchant identity) is read from an unauthenticated header. This breaks the equality that should hold: `shop bound by HMAC == shop acted upon by the handler`. An attacker who controls their own installed shop (an unprivileged internet user with respect to any *other* merchant) can obtain a genuinely-signed `(raw_body, hmac)` pair for their own webhook traffic, then re-submit it directly to the app's public webhook endpoint with a forged `shopify-shop-domain` / `x-shopify-shop-domain` header pointing at a victim shop. The HMAC check still passes because it never covered the shop field, so the forged shop is passed on to the app's registered handler as if authentic.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the supplied `hmac`: [1](#0-0) 

For OAuth callbacks, `Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop` into the signed string along with `code`, `host`, `state`, and `timestamp`, so the shop identity is cryptographically bound to the signature: [2](#0-1) 

By contrast, `Webhooks::Request#to_signable_string` returns only `@raw_body` — the `shop` (and `topic`, `webhook_id`, `api_version`) are read from headers that are never part of the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches to the handler using the unauthenticated `request.shop`: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that has installed the app, a valid `(body, hmac)` pair generated for shop A's webhook is also a valid `(body, hmac)` pair when replayed with shop B's domain header — the signature check has no way to detect the substitution since it never inspected the shop field. This is exactly the reported bug class: "a shop authenticated versus the shop stored/acted upon" mismatch — the shop that is cryptographically verified (none) diverges from the shop that is passed to the handler (`request.shop`).

### Impact Explanation
This qualifies as Critical — cross-tenant access. An attacker who has installed the target app on their own store (a fully unprivileged action available to any internet user for public/embedded Shopify apps) can trigger genuine webhook deliveries for their own shop, capture the `(raw_body, hmac)` pair, and replay it against the app's public webhook endpoint with the `shop` header rewritten to any other merchant using the same app. If the host application trusts `WebhookMetadata#shop` (as documented/intended, since HMAC validation is supposed to be the authenticity guarantee) to select per-tenant state, credentials, or database records, the attacker can inject or trigger tenant-scoped side effects (e.g., fake `orders/create`, `app/uninstalled`, `shop/redact`) attributed to a victim shop — a cross-tenant confused-deputy attack achieved entirely by driving this gem's own verification API as documented.

### Likelihood Explanation
Moderate-to-high. The only prerequisite is that the attacker be a legitimate (even free-tier) installer of the target app — no special privilege, leaked secret, or TLS interception is required. Capturing their own valid webhook body+HMAC and replaying it with a different `shop` header is a simple, repeatable HTTP-level operation.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the HMAC-signed material, or independently authenticate the shop out-of-band (e.g., require correlating the webhook's shop against a webhook subscription id/topic pairing known only to the legitimate shop, or require topic-specific single-use secrets/registration IDs). At minimum, `Webhooks::Request#to_signable_string` should not be the sole trust anchor for `shop`; the gem should document/enforce that `shop` cannot be trusted unless separately corroborated (e.g., against the `webhook_id` returned from Shopify's registration for that specific shop), consistent with the way `Auth::Oauth::AuthQuery` binds `shop` into its signable string.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; wait for a legitimate webhook delivery, capturing the raw body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Send `POST /webhooks` directly to the app's webhook endpoint with:
   - body = `B`
   - `shopify-hmac-sha256: H` (unchanged)
   - `shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `shopify-topic`, `shopify-webhook-id` set arbitrarily/copied.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`: [5](#0-4) 
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload never originated from Shopify for that shop, allowing the attacker to spoof events attributed to a shop they do not control.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
