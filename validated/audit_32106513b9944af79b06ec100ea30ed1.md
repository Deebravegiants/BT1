## Title
Webhook `shop` identity is trusted by the handler but is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the raw request body against the HMAC signature, then hands the caller a `WebhookMetadata` struct whose `shop` field is read from an unauthenticated HTTP header. The documented handler contract (`docs/usage/webhooks.md`) explicitly tells integrators to use `data.shop` to route/attribute the event to a shop, so the gem is itself establishing (and recommending as trustworthy) an identity binding that its own signature check does not cover.

### Finding Description
`Utils::HmacValidator.validate` is the sole authenticity check for a webhook, and it verifies the signature over `Request#to_signable_string`, which returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Request#shop`, by contrast, is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of the signed bytes at all: [3](#0-2) 

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)` — and then immediately constructs the `WebhookMetadata` using the unauthenticated `request.shop`: [4](#0-3) 

The binding the gem implicitly asserts to the host application is:
`hmac_valid(raw_body) == true` implies `shop header is authentic for that body`.

That equality does not hold: the app's `client_secret` (used to compute the HMAC) is shared across every shop that installs the app, and the signature never covers the `shop` header. Any party who can obtain one genuine, validly-signed webhook delivery for **their own** shop (trivial — they just install the app on a store they control and trigger an event) possesses a `(raw_body, valid_hmac)` pair. Because the HTTP headers are not part of the signed content, they can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g. a victim's `myshopify.com` domain). `Utils::HmacValidator.validate` will still return `true` since it only recomputes the HMAC over `@raw_body`, and `Registry.process` will happily dispatch to the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

This is not merely "the host app must know Shopify's spec" — the gem's own documentation instructs the handler to trust `data.shop` for shop attribution: [5](#0-4) [6](#0-5) 

so the gem itself is the component asserting the (false) authenticity of the `shop` field.

### Impact Explanation
Any typical webhook handler implementation looks up the shop's stored offline access token/session keyed by `data.shop` and performs privileged actions against Shopify's Admin API on that shop's behalf (e.g., writing metafields, cancelling orders, updating fulfillment, etc., depending on topic), or persists incoming webhook data attributed to that tenant in a multi-tenant datastore. Since `data.shop` can be forged by any attacker who has legitimately installed the app once on their own store, this allows:
- Cross-tenant data injection/corruption (writing attacker-controlled webhook payload data as though it belongs to a victim shop).
- If the handler uses `data.shop` to fetch a session/access token and perform Admin API writes, the attacker can trigger those privileged operations against an arbitrary victim tenant merely by knowing/guessing the victim's `*.myshopify.com` domain (which is often public knowledge).

This satisfies the "Critical - cross-tenant access" impact bar, since the tenant boundary (which shop the webhook data belongs to) is broken using only the attacker's own legitimate installation, no leaked secrets or privileged access required.

### Likelihood Explanation
Likelihood is high for any app built on this gem that follows its documented pattern of trusting `data.shop`:
- The attacker only needs to be able to install the app on any shop (including a free development/trial store) — no special privilege, no access to the target's credentials.
- Capturing one raw webhook body + its HMAC header requires nothing more than logging their own inbound HTTP request.
- Replaying it with a different `Shop-Domain` header is trivial (any HTTP client), and the gem performs no additional check tying the header to the signed body.

### Recommendation
`Registry.process` / `Request` should not treat the `shop` header as authenticated. At minimum:
- Cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription that was registered (i.e., validate that the shop is one for which this app actually has an active session/webhook subscription), or
- Include the shop domain in the value that is HMAC-verified (e.g., by requiring the app to independently confirm shop identity via a separate authenticated channel, such as looking up the webhook_id in Shopify's API scoped to the expected shop) before trusting `WebhookMetadata#shop`.
- At the very least, the documentation and `WebhookMetadata` should clearly warn that `shop` is not covered by the HMAC and must be independently corroborated (e.g., against known installed shops) before being used for any privileged or tenant-scoping decision.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` (a normal, unprivileged action) and triggers a webhook topic the app is subscribed to (e.g. `orders/create`).
2. The attacker's server receives:
   ```
   POST /callback/orders/create
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC over the raw body, computed with the app's shared client_secret>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   X-Shopify-Webhook-Id: ...
   Body: {"id": 1, ...attacker-controlled fields...}
   ```
3. Attacker replays this exact body and HMAC header to the same endpoint, only changing the header:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed by the host app from this forged request, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` — it matches (unchanged from step 2), so the request is accepted as authentic.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: <attacker-controlled>, ...)` and dispatches to the registered handler, which — following the gem's documented pattern — treats the data as legitimately belonging to `victim-shop.myshopify.com`.
