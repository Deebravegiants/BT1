### Title
Permissionless graduation can permanently brick when `tokensForLP` rounds to zero, freezing the token forever in `Lifecycle.Graduating` - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The CVE describes a refcount-style bug: a resource is "acquired" (`pm_runtime_get_sync`'s counter increment) without a guaranteed matching "release" on the failure path, leaking state permanently. alt.fun's two-phase graduation has the same shape: `_enterGraduating` (Phase 1) permissionlessly *acquires* the `Lifecycle.Graduating` state and pins `pendingGraduation` [1](#0-0) , and only `finalizeGraduation` (Phase 2) can *release* it back to `Lifecycle.Graduated` [2](#0-1) . If `finalizeGraduation` hits a deterministic revert, there is no rollback path — the token is stuck in `Graduating` (trading frozen) forever, exactly like a leaked refcount that can never be decremented.

### Finding Description
`_prepareGraduationLiquidity` computes the exact LP seed amount as `tokensForLP = (ltFromPair * tokenReserve) / assetReserve`, capped at `LP_RESERVE` [3](#0-2) . This is plain integer division: whenever the curve graduates with a very small `tokenReserve` relative to `assetReserve` (i.e., the curve is nearly fully sold out at graduation — the exact condition the supply-sellout trigger is designed to reach, and also reachable on the USD trigger for tokens with most of the curve supply already sold), `tokensForLP` can round down to exactly `0` while `ltFromPair` remains `> 0`.

That `(tokensForLP = 0, ltFromPair > 0)` pair is cached verbatim into `pendingGraduation` and consumed unchanged by `finalizeGraduation` [4](#0-3) . On the (~99% of graduations) empty-pair fast path, `_seedUniswapV2Direct` routes straight to `_seedDirectMint`, which transfers `tokensForLP` (= 0) TOKEN and `ltFromPair` (> 0) LT to the pair and calls `pair.mint(lpLock)` [5](#0-4) . UniswapV2's first-mint formula is `liquidity = sqrt(amount0 * amount1) - MINIMUM_LIQUIDITY`; with one side `0`, `sqrt(0) = 0`, so this underflows/reverts (`INSUFFICIENT_LIQUIDITY_MINTED` or a Panic), deterministically, on every call.

Because the inputs (`tokenAddress`, `lt`, `pair`, `p.tokensForLP`, `p.ltFromPair`) are pinned and immutable once Phase 1 fires, and the pair's reserves never change while `finalizeGraduation` keeps reverting, **every subsequent call reproduces the identical revert** — there is no way for the permissionless caller (or anyone else) to unstick it. Unlike the hostile-pre-seed brick-resistance the authors explicitly engineered for regimes 2/3 (`_seedRebalancing` / `_swapBudget` / `_pairRebalance`, all documented at [6](#0-5) ), the zero-`tokensForLP` empty-pair path (regime 1) has no such guard.

### Impact Explanation
Once this state is hit:
- `Lifecycle.Graduating` never clears, so `Bonding.buy` / `Bonding.sell` (and therefore `Zap.buy`/`Zap.sell`) permanently revert with `TokenIsGraduating`/`NotTrading`-class errors for that token — freezing every trader and the creator out of the market.
- The entire curve-raised LT (`ltFromPair`) that was drained from the curve pair via `Router.graduate` in Phase 1 sits permanently on `Bonding`, unreachable by any withdrawal path.
- The token can never reach `Lifecycle.Graduated`, so `LPLock.recordLock` is never called and no LP is ever created for that token.

This is a concrete permanent freezing of trader/creator funds (the drained LT) caused by a reachable, unprivileged code path — squarely in-scope per the validation rules (permanent freezing of trader/creator funds via `Bonding.triggerGraduation`/`finalizeGraduation`).

### Likelihood Explanation
`triggerGraduation` is explicitly permissionless (`external nonReentrant`, no role check) and designed to be called by "the auto-buy keeper" or "anyone" once `canGraduate` is true [7](#0-6) ; `finalizeGraduation` is likewise callable by anyone [8](#0-7) . The rounding-to-zero condition is a natural consequence of the curve math when the token graduates late in its life (curve `tokenReserve` small relative to `assetReserve`) — this is exactly the regime the supply-sellout trigger targets, and it can also be nudged by an attacker sizing the threshold-crossing buy to leave the smallest possible unsold `tokenReserve` at the moment of graduation. No special privilege or timing beyond ordinary curve trading is required.

### Recommendation
In `_prepareGraduationLiquidity`, treat `tokensForLP == 0` (or `ltFromPair == 0`) as a degenerate case and either floor it to `1` wei (guaranteeing a non-zero first-mint amount) or route that graduation through a fallback that doesn't depend on UniswapV2's `sqrt(amount0*amount1)` first-liquidity formula, so `finalizeGraduation` can never deterministically revert. This mirrors exactly the CVE's fix pattern — pair every state "acquisition" (`Lifecycle.Graduating`) with a code path that is guaranteed to eventually "release" it, instead of leaving a reachable branch with no matching completion path.

### Proof of Concept
1. Launch a token via `Bonding.launch`.
2. Drive buys via `Bonding.buy` (through `Zap` or directly, using an allow-listed router in tests) until the curve is graduated by the supply trigger (`IPair.tokenBalance() == 0`) or the USD trigger at a point where the stored `tokenReserve` (from `IPair.getReserves()`) is tiny relative to `assetReserve` — e.g., size the final buy so it consumes nearly all remaining curve supply in one transaction, crossing the graduation trigger with `tokenReserve` at its smallest reachable non-zero value, so `(ltFromPair * tokenReserve) / assetReserve` truncates to `0`.
3. Phase 1 fires automatically (`_enterGraduating`), caching `pendingGraduation.tokensForLP == 0`.
4. Call `bonding.finalizeGraduation(tokenAddress)` from any address — it reverts inside `IUniswapV2Pair(pair).mint(lpLock)` (`INSUFFICIENT_LIQUIDITY_MINTED` / arithmetic underflow) because `amount0 == 0`.
5. Repeat the call — it reverts identically every time, since no state changed. `bonding.isGraduating(tokenAddress)` stays `true` forever; `bonding.buy`/`bonding.sell` for this token permanently revert with `TokenIsGraduating`.

Note: I was unable to run the actual test suite (`test/TwoPhaseGraduation.t.sol`, `test/GraduationInvariants.t.sol`) to confirm the exact rounding threshold numerically reachable under `DeployHelper`'s configured `VIRTUAL_LIQUIDITY_USD`/threshold constants — that requires executing Foundry, which is outside the scope of static code review. A Devin session with repo access could add a fuzz/unit test in `TwoPhaseGraduation.t.sol` driving `tokenReserve` to a small value at the graduation boundary to confirm the revert empirically.

```text
    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }
```

```text
    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }
```
