### Title
`deposit` mints zero `zft` shares while accepting full underlying principal when `total-assets-preview` is zero but `total-supply` is non-zero - ([File: mainnet/contracts/vault/v0-vault-ststx.clar])

### Summary
`convert-to-shares-preview` returns `u0` whenever `total-assets-preview` is `u0` and `total-supply-preview` is non-zero, and `deposit` only checks `(>= inkind min-out)` — it has no `(> inkind u0)` guard, unlike `redeem` which explicitly enforces `ERR-OUTPUT-ZERO`. With `min-out = u0` an attacker's deposit call passes the slippage check trivially (`0 >= 0`), so `amount` of underlying is pulled from the depositor and added to `assets`, while `0` shares are minted to `recipient`.

### Finding Description
Broken identity: `convert-to-assets-preview(convert-to-shares-preview(amount)) == amount` is claimed to hold for any deposit. With `ta = total-assets-preview() = 0` and `ts = total-supply-preview() > 0`:

```
convert-to-shares-preview(amount) = u0   ;; ta==0 branch
``` [1](#0-0) 

and then `convert-to-assets-preview(u0) = u0 != amount`.

`deposit` computes `inkind` before any state mutation and only guards it with the slippage check, not a nonzero-output check:
```
(inkind (convert-to-shares-preview amount)))
...
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
...
(try! (receive-underlying amount account))
(try! (ft-mint? zft inkind recipient))
(var-set assets (+ current-assets amount))
``` [2](#0-1) 

Contrast this with `redeem`, which explicitly protects against a zero-value conversion result:
```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
``` [3](#0-2) 

The asymmetry (guard present on the "sell shares" path but absent on the "buy shares" path) means `deposit` never rejects the degenerate `inkind == u0` case. If an attacker calls `deposit(amount, u0, recipient)` while `total-assets-preview` is `u0` (e.g., driven there by a prior socialize-debt event that wrote off `assets`/`principal-scaled` to zero while `zft` total supply remains non-zero from the `MINIMUM-LIQUIDITY` mint to `NULL-ADDRESS` and/or other holders), the deposit:
1. Transfers `amount` of underlying from the attacker into the vault via `receive-underlying`.
2. Mints `u0` `zft` to `recipient`.
3. Increases `var-get assets` by `amount`.

The attacker's principal becomes real backing for the *existing* `zft` supply with no corresponding share issuance, permanently diluting the attacker's claim to zero while proportionally increasing the redeemable value of every pre-existing `zft` holder (including the frozen `NULL-ADDRESS` minimum-liquidity balance).

I was not able to fully trace the exact `socialize-debt`/`system-borrow` code path in `mainnet/contracts/market/v0-4-market.clar` within the available tool budget to confirm the precise mechanics by which `assets` is driven to exactly `u0` while `total-supply` stays non-zero (the search confirmed matching call sites for `socialize-debt` in both the market and vault contracts, consistent with the scenario, but I did not read the full function bodies). The core deposit-side vulnerability — missing zero-output guard combined with `convert-to-shares-preview`'s `ta==0` branch — is directly confirmed in the code.

### Impact Explanation
Each such deposit call is a full, permanent loss of the depositor's transferred `amount` with zero shares received in return — this is a direct theft of principal (Critical), matching Immunefi's "permanent freezing/theft of funds at rest." It is repeatable for every deposit made while the `ta==0, ts>0` condition holds (until someone re-primes `assets` above zero), and the loss is absorbed collectively by all existing `zft` holders whose claim proportionally increases, including the untouchable `NULL-ADDRESS` minimum-liquidity balance which cannot be redeemed to realize the gain, permanently locking part of the stolen value.

### Likelihood Explanation
Requires the vault to reach the `total-assets-preview() == u0` / `total-supply() > u0` state, which per the question's precondition is reachable via an unprivileged liquidation triggering `socialize-debt` on the paired market contract (a `check-caller-auth`-gated function called from an authorized market contract, itself triggerable by an ordinary liquidation call). No privileged access is needed by the attacker to perform the deposit itself; the deposit call requires only `min-out = u0`, which is attacker-controlled and default-friendly (no wallet UI would normally set `min-out` above `0` here since the transaction succeeds and looks like a normal deposit). This is feasible with attacker-controlled capital only (the deposited `amount`).

### Recommendation
Add an explicit `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` check in `deposit` (mirroring `redeem`) immediately after computing `inkind`, before `receive-underlying`/`ft-mint?`/`var-set assets`, across all vault contracts (`v0-vault-ststx.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` counterparts). Additionally, consider whether `total-assets-preview() == u0` while `total-supply() > u0` should itself pause deposits entirely (e.g. treat the vault as insolvent) rather than silently letting `convert-to-shares-preview` degrade to `u0`.

### Proof of Concept
Clarinet simnet test plan:
1. Deploy market + `v0-vault-ststx`, call `initialize`, confirming `MINIMUM-LIQUIDITY = u1000` `zft` minted to `NULL-ADDRESS` and initial deposit establishing non-zero `total-supply`.
2. Drive `(var-get assets)` and `total-debt` to `u0` via the market's borrow + unprivileged liquidation path that invokes `socialize-debt` on the vault (per repo's `authorization.test.ts` socialize-debt test patterns), while confirming `(ft-get-supply zft)` remains `> u0`.
3. Assert `total-assets-preview` returns `u0` (via a read-only wrapper or by observing `convert-to-shares-preview` behavior) while `total-supply-preview` (or `(ft-get-supply zft)`) is non-zero.
4. Attacker calls `(deposit X u0 attacker)` with `X > u0` ustx-equivalent of underlying.
5. Assert:
   - `(ft-get-balance zft attacker)` == `u0` (no shares minted).
   - `(var-get assets)` increased by exactly `X`.
   - Underlying token balance of the vault contract increased by `X`.
   - Transaction returned `(ok u0)` (not an error), proving no revert occurred and the attacker's principal is unrecoverable while other `zft` holders' claim on `total-assets` increased.
