### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the handler a `WebhookMetadata` object built from `request.shop`, which is read directly from the unauthenticated `shop-domain` HTTP header. Because the `shop` value is never included in the signed payload, an attacker who possesses any single valid `(body, hmac)` pair can freely relabel that event as belonging to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

while `shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or HMAC: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature exclusively against `to_signable_string` (i.e., the raw body): [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then forwards the attacker-controlled `shop` header straight to the app's handler as trusted metadata: [4](#0-3) 

The gem's own documentation instructs handlers to treat `data.shop` as the authoritative shop for the event and use it to scope subsequent work (e.g. enqueuing jobs keyed by `shop_domain: data.shop`): [5](#0-4) [6](#0-5) 

The identity binding the gem claims to guarantee is: `hmac_valid(body) ⇒ shop == the_shop_that_produced_that_body`. In reality the equality that actually holds is only `hmac_valid(body) ⇒ hmac == HMAC(secret, body)`; `shop` is entirely outside that binding. Any unauthenticated internet user who can get one legitimate `(body, hmac)` pair signed by the app's `client_secret` — for instance by installing the app on their own store and capturing/triggering a webhook delivered to their own registered endpoint — can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` dispatches the event as if it originated from the victim shop.

### Impact Explanation
This breaks the tenant-isolation guarantee that host applications are told (by this gem's own documentation) they can rely on: the `shop` field handed to every webhook handler is not authenticated. A host app that uses `data.shop` to pick or create tenant-scoped records (as the documented example does) can be made to attribute attacker-controlled webhook bodies to a victim shop, corrupting or confusing that victim's tenant-scoped state — a cross-tenant integrity violation reachable by any unauthenticated internet user who has captured one valid webhook for any shop (including their own).

### Likelihood Explanation
The webhook processing endpoint is, by design, a public unauthenticated HTTP endpoint (`docs/usage/webhooks.md`), and any app developer or trial merchant can trivially obtain a genuine `(body, hmac)` pair by installing the target app on a shop they control and observing/triggering a webhook delivery to their own registered callback. No secrets, tokens, or privileged access are required — only the ability to replay HTTP requests with a modified `shop-domain` header, which is well within reach of an unprivileged internet user.

### Recommendation
Bind `shop` (and ideally `topic`/`api_version`/`webhook_id`) into the HMAC-covered signable string, or otherwise incorporate the shop-domain header value into `to_signable_string` so that `HmacValidator.validate` fails whenever the header has been altered relative to the value Shopify actually signed for. At minimum, document loudly that `data.shop` is unauthenticated and must be cross-checked against an independently-verified source (e.g. an existing stored session for that shop) before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`) pointing at the app's public callback URL.
2. Attacker triggers the event and captures the resulting HTTP request, including the genuine `x-shopify-hmac-sha256` header and raw body — both correctly signed by Shopify using the app's real `client_secret`.
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (it only checks the body against the HMAC), and `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload was never produced for that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
