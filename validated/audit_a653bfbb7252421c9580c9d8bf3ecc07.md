### Title
Governance-mutable `surplusShareBps` retroactively applied to already-placed (pending/ACTIVE) Intent Gateway orders - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
The Intent Gateway's `surplusShareBps` parameter, which determines how solver overpayment ("surplus") is split between the protocol and the order's beneficiary at fill time, is read live from mutable global governance state (`_params`) rather than being locked into the order at placement time. This mirrors the reported bug class where a fee parameter changeable by a privileged actor is applied to already-created, unsettled positions (loans/orders) whose owners agreed to different terms when they were created.

### Finding Description
When a user calls `placeOrder`, the protocol fee (`protocolFeeBps`) is fetched from governance state and immediately baked into the order: it is deducted from the inputs, the reduced amounts are what get hashed into the order commitment, and the commitment is what's checked at fill/settlement time [1](#0-0) . This design intentionally fixes the protocol fee at order creation.

In contrast, `surplusShareBps` — the parameter controlling how much of a solver's overpayment goes to the protocol versus the order beneficiary — is documented and implemented to be evaluated **at fill time**, not at order placement: [2](#0-1) 

Governance can update `surplusShareBps` at any time via `_updateParams`, which overwrites the entire `_params` struct (including `surplusShareBps`) for all orders currently outstanding on the gateway: [3](#0-2) 

Because an `Order` can remain unfilled/pending for an extended period (bounded only by `order.deadline`), a user places an order under one surplus-split policy, but if governance changes `surplusShareBps` before a solver fills it, the fill executes against the *new* policy — a term the user never agreed to when escrowing their tokens and committing to the order. This is structurally identical to the reported "new fee applied to ACTIVE loans" pattern: a mutable, owner/governance-controlled percentage is applied at a later settlement step instead of being snapshotted into the position at creation, as is correctly done for `protocolFeeBps`.

### Impact Explanation
Users placing intent orders make an economic assumption about surplus distribution based on the `surplusShareBps` value visible at the time they escrow funds. A governance change to a higher protocol surplus share applied retroactively to pending orders reduces the beneficiary's expected upside without consent, and conversely a change to zero could unexpectedly redirect surplus fully to the beneficiary at the protocol's expense. Because this affects value transfer determined at settlement of already-escrowed funds, this qualifies as unauthorized/unagreed redistribution of funds for outstanding orders — a Medium severity issue, consistent with the analog class (a term-of-service change applied to an existing financial position rather than only new ones).

### Likelihood Explanation
This requires a governance-side `_updateParams` call (already a normal, expected operational action, not a compromise) to occur while orders are pending — a routine and likely scenario given orders can be outstanding for the full window up to `order.deadline`, and governance fee updates are a normal part of gateway operations as evidenced by extensive fee-update test coverage in the repo (`IntentGatewayV2Test.sol`, `IntentGatewayV2SameChainTest.sol`).

### Recommendation
Snapshot `surplusShareBps` (and any other fill-time-sensitive economic parameter) into the `Order` struct or its commitment at `placeOrder` time, the same way `protocolFeeBps` is already locked in via the fee-reduced inputs baked into the commitment hash. This ensures the surplus split used at `fillOrder`/settlement matches what the user agreed to when the order was created, rather than whatever value governance has set by the time a solver chooses to fill it.

### Proof of Concept
Conceptual sequence (not independently executed against the repo in this review):
1. Governance sets `_params.surplusShareBps = X` favorable to beneficiaries; user calls `placeOrder` and escrows tokens, expecting surplus split under `X`.
2. Before any solver fills the order, governance calls `_updateParams` with `surplusShareBps = Y` (less favorable to the beneficiary) via the documented `UpdateParams` cross-chain governance path [3](#0-2) .
3. A solver overpays and fills the still-pending order; the surplus split is computed using the now-current `surplusShareBps = Y`, not `X`, redistributing value the user did not agree to at order placement.

Note: I was unable to directly inspect the exact surplus-computation code inside `fillOrder` (in `evm/src/apps/IntentGatewayV2.sol`, `ExtrinsicIntents.sol`, or `IntrinsicIntents.sol`) within the indexed context to confirm the precise line-level mechanics; the conclusion is based on the explicit fee-timing table in the official documentation and the confirmed global/mutable nature of `_params.surplusShareBps` via `_updateParams`. A full Devin session with file access would be needed to pinpoint the exact `fillOrder` surplus-calculation lines for a complete PoC.

    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
