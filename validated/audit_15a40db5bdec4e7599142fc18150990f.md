### Title
Unfunded `recapitalize` credits pool cash that was never deposited, so supplier exits pass solvency checks and then panic inside the token transfer - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
Analogous to the nimiq report (an attacker-controlled input mutates state before the validating check runs, so a later assertion/panic fires on poisoned state), `recapitalize::accounting` commits a cash credit to the market book without ever verifying that tokens actually arrived. The pool's own guards (`require_reserves`, `require_backed_market`, `require_liquidation_buffer`) all read the cash *book*, not custody, so the market reports itself solvent and liquid while it cannot pay. Withdrawals then sail through every pool check and panic only inside the SAC `transfer` — the same shape as `add_to_history` running before the history-root comparison: the invariant is "checked" against data the caller poisoned, and the failure surfaces as a panic downstream instead of a rejection at entry.

### Finding Description
`recapitalize::accounting` computes `applied = amount.min(backing_shortfall)`, calls `cache.credit_cash(applied)`, and `cache.commit()` — committing the inflated cash ledger — before any token movement is even attempted [1](#0-0) . The only "transfer" is `transfer_out(&payer, refund)` of the unused portion; nothing measures the inbound deposit (unlike `transfer_amount_measured` used elsewhere, `contracts/controller/src/payments.rs:5`) [2](#0-1) . All downstream solvency checks consume the book: `require_liquidation_buffer` and `backing_shortfall` compare `cache.cash()` rather than `token::balance(pool)` [3](#0-2) [4](#0-3) . The in-repo test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` proves the exact sequence: an unfunded recapitalize drains custody, the book still claims the cash is there, and a legitimate `withdraw` is only stopped by a raw SAC `BalanceError = 10` panic — explicitly *not* by `InsufficientLiquidity` or `PoolInsolvent` [5](#0-4) .

### Impact Explanation
Temporary freezing of funds / pool unable to pay claims. Once the cash book exceeds real custody, every supplier withdrawal routed through the pool's guard set passes `require_reserves` (book says liquid) and then aborts in the token contract's `transfer` with an unrecoverable `BalanceError`. Suppliers cannot exit until someone genuinely recapitalizes the shortfall. This is precisely the accepted impact class "temporary freezing of funds" and "a contract unable to operate from lack of token funds," and it mirrors the nimiq bug's property that the panic (rather than a clean validation error) is the only thing standing between the caller and a corrupted invariant.

### Likelihood Explanation
`recapitalize` is a permissionless entrypoint (it is designed to let any payer inject cash to cure a shortfall). Any unprivileged address can invoke it with `amount` equal to the current `backing_shortfall` — or, more simply, front-run the controller's funding transfer or call the pool op in a context where the inbound transfer is skipped/zero — so the book is credited `applied > 0` while custody receives nothing. No privileged role, oracle manipulation, or leaked key is required; the vulnerability is that the credited amount is trusted from the argument rather than measured from the balance delta.

### Recommendation
Measure the recapitalization like every other cash inflow: snapshot `token::balance(pool)` before the call, credit at most `min(measured_delta, backing_shortfall)`, and keep the refund path. Concretely, have the controller move funds first and let `recapitalize::accounting` derive `applied` from `balance_delta_since` instead of the `amount` argument, or have the pool compute `applied` as `min(actual_balance_increase, shortfall)`. Add a guard assertion that `cache.cash() <= token::balance(pool)` post-commit so an overstated book panics at write time rather than at a supplier's withdrawal.

### Proof of Concept
Already encoded in the repo at `contracts/pool/tests/flows.rs:3407-3483`:

1. Supplier deposits 10_000_000_000 units; book `cash` equals pool token balance.
2. Attacker (as `payer`) calls `recapitalize(hub_asset, payer, custody_amount)` **without funding the pool**. `accounting` credits `applied` to the cash book and commits; the refund transfer simply sends the pool's own tokens back out, draining real custody to 0.
3. `state_snapshot().cash >= deposit` while `token::balance(pool) == 0` — book and custody diverge.
4. Supplier calls `withdraw(supplied_shares, i128::MAX)`. All pool guards pass on the inflated book; the call panics inside the SAC `transfer` with `BalanceError = 10`. Supplier funds are frozen until a *real* recapitalization occurs.

Note: this analysis assumes the controller's `recapitalize` wrapper does not itself enforce a measured funding transfer before delegating to the pool op — the test demonstrates the pool-level defect unconditionally, but I could not verify the controller-side funding step within the available search budget. If the controller measures the payer's transfer with `transfer_amount_measured`, the reachable trigger narrows to any path that commits the credit without matching custody.

pub(crate) fn backing_shortfall(cache: &Cache) -> i128 {
    let supplied_claim = cache.unscale_supply_floor(cache.supplied());
    let outstanding_debt = cache.unscale_borrow_ceil(cache.borrowed());
    let backing = cache.cash().saturating_add(outstanding_debt);
    supplied_claim.saturating_sub(backing).max(0)
}
