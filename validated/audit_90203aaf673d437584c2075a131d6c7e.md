This confirms the asymmetry: the OAuth `AuthQuery#to_signable_string` explicitly includes `shop` in the signed payload [1](#0-0) , whereas the webhook `Request#to_signable_string` returns only `@raw_body`, entirely excluding the `shop-domain`, `topic`, and `webhook-id` headers from the HMAC computation [2](#0-1) . `HmacValidator.validate` only checks that `to_signable_string` matches the shared `api_secret_key` [3](#0-2) , and `Registry.process` trusts `request.shop` (read straight from the unauthenticated header) once that check passes, dispatching it to the handler as the tenant identity [4](#0-3) .

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, never the `shop-domain` (or `topic`/`webhook-id`) header [2](#0-1) . `Utils::HmacValidator.validate` signs/verifies exactly that string against the app's `api_secret_key`, which is identical for every shop that has installed the app [5](#0-4) . Consequently the HMAC proves only "this body was produced with our app secret," not "this body belongs to shop X." `Registry.process` passes the unauthenticated `request.shop` straight to the webhook handler as the acting tenant once the (body-only) HMAC check passes [4](#0-3) .

### Finding Description
The broken identity binding is: `shop-domain (header, unauthenticated) == shop (tenant used by handler)`.

Any merchant who has installed the app on their own shop (an unprivileged holder of a legitimate webhook delivery, analogous to the "holder" in the referenced report) can capture one authentic `(raw_body, hmac)` pair that Shopify sent for their own shop. Because the HMAC never binds the shop, that same `(raw_body, hmac)` pair remains valid when replayed to the app's public webhook endpoint with the `shop-domain` header rewritten to any other installed shop. `HmacValidator.validate` recomputes the signature over `to_signable_string` (body only) and it matches, so `Errors::InvalidWebhookError` is never raised [6](#0-5) . The handler then receives `WebhookMetadata` with `shop: request.shop` set to the attacker-chosen victim shop, alongside the attacker's own (but validly-signed) body content [7](#0-6) .

This directly matches the analog class "a field acted on but not covered by the HMAC": the `shop` field that downstream handler logic uses to select/act on tenant state is not part of the signed payload, while the OAuth flow's `AuthQuery` demonstrates the correct pattern of including `shop` inside `to_signable_string` [1](#0-0) .

### Impact Explanation
This is a cross-tenant vulnerability: data/action attribution for shop B can be forged using material sourced from shop A, purely by an app-installing merchant crafting an HTTP POST directly to the app's public webhook endpoint. Any host application that uses `request.shop` (or the `shop` field of `WebhookMetadata`) to select which merchant's records to update, credit, or delete based on webhook payloads is exposed to cross-tenant data corruption or unauthorized state changes attributed to a victim shop, without needing the victim's credentials, access token, or `client_secret`.

### Likelihood Explanation
Likelihood is realistic but requires: (1) attacker controls at least one shop that has the app installed (trivial — any developer can install a public app or a custom app they build), (2) attacker can reach the app's webhook HTTP endpoint directly with arbitrary headers (true for any publicly deployed webhook receiver), and (3) the host app relies on `request.shop`/`data.shop` for tenant-scoped actions, which is the documented intended use of `WebhookMetadata`.

### Recommendation
Bind the shop identity into the signed payload, mirroring the OAuth `AuthQuery` pattern: include `shop-domain` (and ideally `topic`/`webhook-id`) inside `Request#to_signable_string`, or otherwise separately authenticate the `shop-domain` header against a value derived from verified data (e.g., cross-check against the session/shop the webhook was registered for) before trusting it in `Registry.process`.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`. Attacker triggers a real event (e.g., product update) causing Shopify to POST a legitimate webhook to the app: body `B`, header `x-shopify-hmac-sha256: H = HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and `H`, then sends a new POST directly to the same webhook endpoint with body `B`, `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Request.new(raw_body: B, headers: ...)` parses the forged shop header successfully [8](#0-7) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and finds it equals `H` — validation passes because `shop-domain` was never part of the signed string [9](#0-8) .
5. The handler executes with `data.shop == "victim-shop.myshopify.com"` and attacker-controlled body `B`, i.e., cross-tenant impersonation succeeds [7](#0-6) .
