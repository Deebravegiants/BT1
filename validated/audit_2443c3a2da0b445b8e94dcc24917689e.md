### Title
Webhook `shop-domain` Header Is Not Covered by HMAC, Enabling Cross-Tenant Shop Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body, and `HmacValidator` verifies the HMAC solely against that body [4](#0-3) . The `shop` value handed to the app's webhook handler is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header [5](#0-4) , which is never part of the signed content. This breaks the identity binding `hmac(raw_body) == valid for shop == shop-domain header value`: the header can be swapped independently of the body while the HMAC remains valid.

### Finding Description
`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching the webhook to the registered handler [6](#0-5) . That validation recomputes the HMAC over `verifiable_query.to_signable_string`, which for `Request` is exactly `@raw_body` [3](#0-2) . None of `topic`, `shop`, `api_version`, or `webhook_id` — all parsed from HTTP headers — are included in the signable string [7](#0-6) . Consequently, any request whose body+HMAC pair is valid for *some* shop will pass validation regardless of what `shop-domain` header accompanies it, and that attacker-chosen `shop` value is trusted and forwarded verbatim into `WebhookMetadata` for the handler to act on [1](#0-0) .

Because a merchant who installs the app on their own store legitimately receives Shopify-signed webhook deliveries (valid HMAC over their own body) at the app's public webhook endpoint, that merchant — an otherwise unprivileged actor with respect to any other tenant of the app — can capture one such delivery and replay it to the same endpoint with only the `x-shopify-shop-domain` header changed to a victim shop's domain. The signature check still succeeds because it never inspected the header, and the app-level handler receives `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: data that a handler believes to be scoped to shop B (`WebhookMetadata#shop`) is actually attacker-controlled content originating from shop A. Any host application that uses `WebhookMetadata#shop` to select which tenant's records to create, update, or delete (a documented and expected usage pattern of this field per `WebhookHandler#handle`) can be made to write or leak data across tenant boundaries, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Any merchant who can install the app (an unprivileged action available to any Shopify store owner, requiring no `api_secret_key`, token theft, or privileged access) automatically receives legitimately HMAC-signed webhook deliveries for their own shop and can replay them with a modified header value. No credential leakage or TLS interception is required — only observing/replaying one's own valid webhook traffic.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header value into the signable content that is HMAC-verified, or independently verify that the `shop-domain` header matches a shop value cryptographically derivable from the signed payload/registration context before constructing `WebhookMetadata`. At minimum, document and enforce that `request.shop` must not be trusted unless it is cross-checked against an out-of-band source of truth (e.g., the shop associated with the webhook subscription ID via the Admin API).

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; Shopify legitimately delivers a webhook `POST` to the app's registered endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(B, client_secret)` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Intercept/replay this exact request, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (`= B`) and it still matches, per [3](#0-2)  and [4](#0-3) .
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` [1](#0-0) , causing the host app to process attacker-supplied data under the victim shop's identity.
