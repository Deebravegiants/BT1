### Title
Asymmetric decimal-scaling in `convert_to_balance`/`convert_to_erc20` can silently mis-mint/mis-burn HFT cross-chain transfers - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `pallet-hyper-fungible-token` decimal-conversion helpers use `saturating_sub` to compute the scaling exponent between an ERC20 token's remote decimals and the local balance decimals. When `local_decimals > erc_decimals`, `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, causing the conversion to skip scaling entirely instead of scaling up, and can produce a value up to `10^n` times smaller or larger than intended depending on the direction of the transfer.

### Finding Description
`convert_to_balance` and `convert_to_erc20` in `modules/pallets/hyper-fungible-token/src/impls.rs` (lines 39-59) are the functions used to translate amounts between the ERC20 18-decimal (or other) representation used on EVM `HyperFungibleToken` sends and the local substrate balance representation on mint/burn: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions assume `erc_decimals >= local_decimals` in all cases (a strict "divide down" / "multiply up" model). If a chain configures a local asset with **more** decimals than the remote ERC20 representation (`local_decimals > erc_decimals`), `erc_decimals.saturating_sub(local_decimals)` clamps to `0` rather than going negative, so:
- `convert_to_balance` performs **no division** at all on an incoming mint — the raw ERC20 `U256` value (scaled at `erc_decimals`) is parsed directly as the local balance (scaled at `local_decimals`), producing a balance that is off by `10^(local_decimals - erc_decimals)`.
- `convert_to_erc20` performs **no multiplication** on an outgoing burn — the raw local balance is sent as-is as the ERC20 amount, again off by the same factor.

This is directly analogous to the reported Unitas bug: `SwapFunctions._convertByToPrice` incorrectly handles decimal difference between `fromToken`/`toToken` (18 vs 6 decimals) when computing `amountIn` from a desired `amountOut`, causing the wrong amount to be charged/minted. Here, the same class of bug (an amount-scaling function that doesn't correctly account for decimal mismatch in both directions) sits directly in the token-bridge mint/burn conversion path that an unprivileged token bridger triggers on every cross-chain `HyperFungibleToken` send/receive.

### Impact Explanation
Depending on which side of the mismatch is hit:
- **Under-minting on receipt** (if the affected chain has higher local decimals than the ERC20 side and the bug goes the "no-scale-up" direction on `convert_to_balance`) causes recipients to receive far less than intended — loss of funds for the user, matching the report's "user pays/receives incorrect amount" impact.
- **Over-minting or under-burning** in the other direction breaks the 1:1 backing invariant between the locked/burned supply on one side and the minted supply on the other, i.e., unbacked mint — a protocol-level fund-safety violation, not just a UX loss.

Given this sits in the core cross-chain balance-conversion logic used by every `HyperFungibleToken` teleport (a token bridge mint/burn path explicitly in scope), a misconfiguration or an asset pairing where local decimals exceed remote decimals turns a routine bridge transfer into either a stuck/incorrect balance or a supply-backing break.

### Likelihood Explanation
Likelihood depends on whether any deployed/considered asset configuration has `local_decimals > erc_decimals`. Substrate assets are frequently configured with fewer decimals than EVM's ubiquitous 18 (e.g., DOT at 10 decimals bridged from an 18-decimal ERC20 wrapper), which is the common case this code was clearly written for (scaling **down** an 18-decimal EVM value to a lower-decimals substrate balance). However, nothing in the visible code enforces `erc_decimals >= local_decimals` as an invariant at asset-registration time within these two helper functions — if such a check exists elsewhere (e.g., in `module.rs` or asset registration validation), this would not be reachable; that could not be fully confirmed within the available tool budget since `module.rs` and `lib.rs` could not be read in the final iteration. This is flagged as a Medium-likelihood finding pending confirmation of whether decimal-ordering is validated at registration.

### Recommendation
Make `convert_to_balance`/`convert_to_erc20` handle both directions explicitly (divide when `erc_decimals > local_decimals`, multiply when `local_decimals > erc_decimals`) rather than relying on `saturating_sub`, which silently collapses the negative case to zero. Alternatively, enforce and assert the invariant `erc_decimals >= local_decimals` at asset-registration time and reject/reconfigure any asset pair that violates it, with an explicit error rather than silent truncation.

### Proof of Concept
Not independently executed (read-only analysis). Reasoning trace:
1. Register a local asset with `local_decimals = 18` and remote ERC20 `erc_decimals = 6` (a plausible configuration if a high-precision local asset is bridged against a 6-decimal stablecoin-style ERC20).
2. On an incoming HFT transfer of `1_000_000` (i.e., `1.0` token at 6 decimals) is delivered, `convert_to_balance` computes `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(18u8) = 0`, so `dec_str = 1_000_000` is parsed directly as the local balance — instead of the correct `1_000_000 * 10^12` local units, the recipient receives `10^12` times less than intended.
3. Symmetrically, an outgoing `convert_to_erc20` from that local balance would send `10^12` times less than intended, or — if the intended fix multiplies instead — creates an unbacked mint depending on which side is later "corrected" without validating the other. [2](#0-1)
