### Title
Webhook shop domain, topic, and webhook ID are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body. `Registry.process` validates the HMAC and then blindly forwards the header-derived `shop` value into `WebhookMetadata`, which host applications use to route/attribute the webhook to a tenant. An attacker who legitimately receives a genuinely-signed webhook for their own shop can replay it with a forged `shop-domain` header, and the signature will still validate.

### Finding Description
The equality the gem is supposed to guarantee is: `shop that was cryptographically authenticated == shop the handler acts on`. This breaks because the HMAC only signs the body: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, never the headers. `HmacValidator.validate` computes/compares the signature strictly against that string: [3](#0-2) 

`Registry.process` checks this body-only HMAC, then constructs `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` — all values read straight from unauthenticated headers — and dispatches them to the app's handler as trusted, verified data: [4](#0-3) 

`WebhookMetadata.shop` is a plain struct field with no independent verification step inside the gem: [5](#0-4) 

Because a legitimate, unprivileged merchant fully controls the HTTP request Shopify sends to their own webhook endpoint (headers included), they can capture a genuinely-signed webhook (valid body + valid HMAC for their own shop), then resend it to the shared app endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspected the shop header, so `Registry.process` dispatches the handler believing the (attacker-supplied) body genuinely originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem asserts webhook authenticity via HMAC but does not bind the `shop` (or `topic`/`webhook_id`) header to that signature. Any host application that trusts `WebhookMetadata.shop` from a passed `Registry.process` call (which is the gem's own documented verification entry point) can be made to process attacker-chosen body content as if it came from a different, victim tenant — e.g., updating shop-scoped records, disabling features, or triggering shop-specific side effects keyed off `data.shop`. This matches the "cross-tenant access" critical-impact category.

### Likelihood Explanation
Exploitation requires only that the attacker operate their own legitimate Shopify store/app installation (unprivileged, no `api_secret_key` or victim credentials needed) and be able to send an HTTP POST to the app's public webhook endpoint with modified headers — both of which are trivial for any developer/merchant with API access to their own store's webhook deliveries.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) in the HMAC-signed payload, or independently verify that `request.shop` corresponds to a shop the app has installed/expects for that webhook subscription before constructing `WebhookMetadata`, rejecting the webhook if the header-derived shop cannot be tied to the signed request.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com`.
2. Shopify sends a genuine webhook to the app's endpoint with body `B`, `shopify-hmac-sha256: HMAC(secret, B)`, and `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this raw request and resends it to the same endpoint, changing only `shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over the unchanged body `B` and succeeds.
5. `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...)` is passed to the app's handler, which processes attacker-controlled body content under the victim's identity.
