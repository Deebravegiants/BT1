Audit Report

## Title
Unsynchronized concurrent map access in `WorkflowMetadataHandler.Authorize` allows data race on JWT authorization state - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` reads `h.authorizedKeys[workflowID]` without acquiring `h.mu`, while the periodically-ticked `syncMetadata` goroutine reassigns `h.authorizedKeys`, `h.workflowRefToID`, `h.workflowIDToRef`, and `h.workflowShards` under `h.mu.Lock()`. This is an unsynchronized concurrent map read/write, inconsistent with every other accessor of the same struct fields, which correctly take `h.mu.RLock()`.

## Finding Description
`Authorize` is the authorization gate for every incoming HTTP trigger request; it verifies the caller's JWT and then does `keys, exists := h.authorizedKeys[workflowID]` with no lock held [1](#0-0) . Meanwhile `syncMetadata` runs on a periodic ticker started in `Start` (`h.runTicker(time.Duration(h.config.MetadataAggregationIntervalMs)*time.Millisecond, h.syncMetadata)`) [2](#0-1)  and, under `h.mu.Lock()`, reassigns the same map fields wholesale [3](#0-2) . By contrast, `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference` all correctly acquire `h.mu.RLock()` before reading the same underlying maps [4](#0-3) [5](#0-4) , confirming `Authorize` is the outlier and the locking discipline elsewhere in the file demonstrates the intended (but here broken) invariant. This is a genuine data race: one goroutine (HTTP trigger request handling, invoking `Authorize` for any incoming request with a JWT) can read `h.authorizedKeys` concurrently with the ticker goroutine's unguarded write, which Go's race detector will flag and which the Go runtime can escalate to a fatal, unrecoverable process crash (`fatal error: concurrent map read and map write`) if it detects a genuinely concurrent map mutation during iteration/access.

## Impact Explanation
The primary concrete, provable impact is availability: an unprivileged caller sending ordinary JWT-signed HTTP trigger requests can, purely through normal use concurring with the handler's own periodic background sync, trigger Go's fatal runtime map-race detection and crash the gateway process — a denial-of-service against the HTTP trigger capability path. This maps to an in-scope Chainlink impact (gateway/node availability disruption on the request-handling path). The claim's secondary suggestion of an authorization-bypass consequence from reading a "mid-swap" map is speculative rather than demonstrated; Go's map reassignment `h.authorizedKeys = authorizedKeys` is an atomic field write, so a racing read observes either the old or new map reference, not an intermediate corrupted map — the report itself acknowledges this is not a guaranteed silent bypass. The concrete claim here rests on the crash/DoS scenario.

## Likelihood Explanation
`syncMetadata` runs on every `MetadataAggregationIntervalMs` tick (default 1 minute), and `Authorize` runs on every single incoming HTTP trigger request, requiring no elevated privilege — just a validly-formed JWT request against the trigger capability, satisfying the "unprivileged actor" requirement. Because both accesses are unsynchronized and occur on independent, concurrently-scheduled goroutines, under sufficient production request volume, this race window is realistically and repeatably triggerable.

## Recommendation
Acquire `h.mu.RLock()` before and `h.mu.RUnlock()` (via `defer`) after the `h.authorizedKeys[workflowID]` lookup in `Authorize`, mirroring the locking pattern already used in `GetWorkflowID`, `GetWorkflowReference`, and `WorkflowShards`. Audit `Authorize` for any other unguarded reads of handler state before merging the fix.

## Proof of Concept
1. Construct a `WorkflowMetadataHandler` with `MetadataAggregationIntervalMs` set very low (e.g., 10ms) so `syncMetadata` runs frequently.
2. In one goroutine, call `h.Start(ctx)` so the ticker repeatedly invokes `syncMetadata`, which reassigns `h.authorizedKeys` under `h.mu.Lock()`.
3. In a second goroutine, repeatedly call `h.Authorize(workflowID, token, req)` with a valid signed JWT in a tight loop.
4. Run the test binary with `go test -race`; the tool will report a data race between the unguarded read at `workflow_metadata_handler.go:92` and the locked write at `workflow_metadata_handler.go:178`, and under load this can surface as `fatal error: concurrent map read and map write`.
