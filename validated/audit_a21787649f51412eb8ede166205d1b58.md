### Title
Swap output slippage floor is committed but never enforced against the actual router output - ([File: contracts/external-actions/swaps/ExternalActionSwap.sol])

### Summary
`swap()` in `ExternalActionSwap.sol` requires that a slippage floor be *set* (`circomData.slippageValues[1] != 0`) but never actually *checks* that the amount received from the router (`swappedAmount`) meets or exceeds that floor. This mirrors the reported bug class: a value used to compute an economically consequential outcome (there, the liquidation reward tied to a manipulable AMM ratio; here, the shielded swap's proceeds tied to a manipulable router-call result) is allowed to diverge from its committed/expected bound without an on-chain check, while the fee (`hinkalHelper.calculateRelayFee`) is still taken as a percentage of whatever `swappedAmount` turns out to be.

### Finding Description
`slippageValues` is part of `CircomData` and is hashed into `calldataHash` via `getHashedCalldata1` [1](#0-0) , so a relay cannot alter it without invalidating the ZK proof. This strongly implies `slippageValues[1]` is meant to be a user-committed minimum acceptable output for the swap.

However, in `ExternalActionSwap.sol`, the only check performed is that the floor is non-zero, not that it is respected: [2](#0-1) 

After `callRouter` executes and returns `swappedAmount`, that value is used directly to compute the relay/Hinkal fee and the amount forwarded into the shielded pool — with no comparison against `circomData.slippageValues[1]` anywhere in this function or its callers (`LifiExternalAction.callRouter`): [3](#0-2) [4](#0-3) 

Because the swap is routed through an external, MEV-visible router call (`router.call(externalActionMetadata)`), the actual output amount can be pushed down by sandwiching the transaction (front-run to move the pool/route price against the user, let the swap execute at a bad rate, back-run to restore price) — exactly the "manipulate reserves around the value-computing call" pattern described in the source report about `liquidateUser`. The committed slippage floor exists in the data structure and is part of the signed/hashed payload, but the equality "swap proceeds ≥ user-committed floor" is never enforced by the contract, so the CircomData field is effectively acted upon (fee computed from it indirectly via `swappedAmount`) while being decoupled from the actual protection it is supposed to represent.

### Impact Explanation
This breaks the shielded balance equality: the UTXO created (`amountToSendToHinkal`) can be arbitrarily lower than what the user authorized/expected when signing the proof, since there is no floor enforcement tying the executed swap result to the user's committed minimum. This is a temporary/permanent freezing and effective theft of user funds during an in-flight shielded swap — funds that should have gone to the user's new shielded UTXO are instead captured by whoever manipulates the router execution (e.g., a sandwiching searcher, or a relay that can influence `externalActionMetadata`/execution ordering). This qualifies as High/Critical impact under "theft of shielded or in-flight user funds."

### Likelihood Explanation
Any external swap performed through `ExternalActionSwap`/`LifiExternalAction` is exposed; MEV searchers routinely watch mempools for router calls and sandwich unprotected swaps. Since the require statement only checks `slippageValues[1] != 0` and never compares it to `swappedAmount`, exploitation requires no privileged access — any observer of the pending transaction can extract value via a standard sandwich attack.

### Recommendation
Add an explicit check after `callRouter` returns:
```solidity
require(
    int256(swappedAmount) >= circomData.slippageValues[1],
    "swap output below slippage floor"
);
```
placed before fees are computed and funds are transferred, so the committed slippage bound in `CircomData` is actually enforced against the real execution outcome.

### Proof of Concept
1. Alice builds a shielded swap: input WETH, output USDC, with `circomData.slippageValues[1]` set to her true minimum acceptable USDC amount (this value is baked into `calldataHash` and thus the ZK proof).
2. She submits `runAction`/`transact` calling into `ExternalActionSwap.swap`, which invokes `LifiExternalAction.callRouter` → `router.call(externalActionMetadata)`.
3. A searcher observes the pending transaction, front-runs it by trading against the same pool/route referenced in `externalActionMetadata` to worsen the price, letting Alice's swap execute at a much lower `swappedAmount` than her intended floor, then back-runs to restore price and capture the difference.
4. `ExternalActionSwap.swap` only validated `circomData.slippageValues[1] != 0` [5](#0-4)  — it never compares this floor to the actual `swappedAmount` obtained at line 63-68, so the transaction proceeds despite Alice receiving far less than her committed minimum, and the shortfall accrues to the searcher.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
