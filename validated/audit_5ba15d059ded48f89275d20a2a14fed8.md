## Title
`EvmHost.dispatch()` swallows leftover ETH from `swapETHForExactTokens` — spot-price/sandwich exposure on the fee-payment path with no refund to the dispatcher - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` let any unprivileged caller pay Hyperbridge's relayer fee in native token. The Host performs an on-chain `swapETHForExactTokens` against a plain Uniswap V2 pool using the caller's `msg.value` as the max input, with no minimum/maximum bound tied to what the caller actually intended to pay, and any leftover ETH from that swap is refunded by the router to `msg.sender` of the swap call — which is `EvmHost` itself, not the original transaction sender. [1](#0-0) 

### Finding Description
Callers are expected to size `msg.value` off-chain using `HyperApp.quote()`, which itself calls `getAmountsIn` against the live Uniswap V2 pool spot price — the same unprotected, TWAP-less pattern flagged in the external report as sandwichable: [2](#0-1) 

The documentation for this exact function explicitly warns that it is only safe off-chain because of sandwich risk: [3](#0-2) 

When `dispatch()` executes on-chain, it calls `swapETHForExactTokens(post.fee, path, address(this), block.timestamp)` with the caller's entire `msg.value` as the implicit `amountInMax`: [1](#0-0) 

Uniswap V2's `swapETHForExactTokens` refunds any ETH beyond what was actually required for the exact-output swap to the caller of the router, which here is `EvmHost` (`address(this)` is only the *recipient of the feeToken*, not the refund target — the refund goes to `msg.sender` of the swap, i.e., the Host contract). Nothing in `dispatch()` forwards that refunded ETH back to the original `_msgSender()`/`post.payer`. The same pattern repeats in `dispatch(DispatchGet)` and `fundRequest()`. [4](#0-3) 

Because the amount of ETH actually consumed depends entirely on the pool's spot price at execution time (no TWAP, no explicit slippage parameter passed by the caller, no minimum-out check beyond the exact-output amount), an MEV actor watching the mempool can sandwich a pending `dispatch()`/`fundRequest()` call: buy the fee token first to move the WETH→feeToken price down (cheapening the swap so the transaction needs less ETH than the sender computed off-chain via `quote()`), let the victim's `dispatch()` execute (which now needs less ETH, leaving more surplus trapped in the Host), then sell back. The dispatcher who computed `msg.value` off-chain via `quote()` for a reasonable buffer permanently loses the unrefunded difference — those funds are stuck in `EvmHost` with no user-facing withdrawal path in the shown code.

### Impact Explanation
Any unprivileged party (a message dispatcher/relayer-fee payer calling `dispatch`, `IApp.quote()`-based apps such as `HyperFungibleToken.send{value: msg.value}`/`BridgeToken`, or `fundRequest`) permanently loses native-token value whenever the spot price moves between their off-chain quote and on-chain execution — a scenario an MEV searcher can force deterministically via sandwiching. This is a direct, protocol-level (not user-supplied-calldata) loss of funds pattern, matching the root cause of the referenced Asymmetry Finance H-08 finding: an on-chain contract computing amounts from a live AMM spot price with no TWAP and no path for the caller to recover unused input. Funds end up value-freezing/loss for legitimate dispatchers of ISMP messages — a core, widely-reached surface of Hyperbridge (every POST/GET dispatch that pays with native token).

### Likelihood Explanation
`dispatch()` is reachable from a single unprivileged transaction/extrinsic-equivalent (any external call with `msg.value`), by any relayer-fee payer building a HyperApp integration that follows the officially documented "Native Token Payment" pattern. The Uniswap V2 pools backing `feeToken()` on most Hyperbridge-configured chains are shallow relative to MEV capital (similar to the rETH pool in the original report), making sandwiching to shift the spot price economically straightforward. The documentation itself flags the underlying `quote()`/spot-price mechanism as sandwich-prone, indicating the team is aware of the pricing hazard but has not closed the refund gap in `dispatch()`.

### Recommendation
- After `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, refund any unspent `msg.value` (i.e., `address(this).balance` delta, or the router's return value) back to `_msgSender()`/`post.payer` rather than letting it accumulate in `EvmHost`.
- Require callers to pass an explicit `amountInMax`/slippage-bound parameter instead of implicitly using the entire `msg.value`, and/or price the swap off a TWAP oracle rather than the instantaneous Uniswap V2 spot price.
- Provide a governance or user-triggered sweep/withdrawal path for any native token that does accumulate in the Host from swap dust, with transparent accounting.

### Proof of Concept
1. A HyperApp integrator calls `HyperApp.quote(post)` off-chain to size `msg.value`, getting `X` ETH needed for `post.fee` feeToken at the current WETH/feeToken spot price.
2. The integrator submits `dispatch{value: X}(post)`.
3. An MEV searcher observes the pending transaction and front-runs it with a swap that buys feeToken (pushing the WETH/feeToken price down, i.e., cheaper feeToken per ETH) — mirroring the original report's TX1 sandwich leg.
4. `EvmHost.dispatch()` executes `swapETHForExactTokens(post.fee, path, address(this), block.timestamp)` with `value: X`; because the price moved, it only needs `X' < X` ETH to acquire `post.fee` feeToken. Uniswap V2's router refunds `X - X'` ETH to the caller of the swap, `EvmHost` — not the original transaction sender. [1](#0-0) 
5. The searcher back-runs to restore the pool price (TX3 leg), completing the extraction, while the integrator's `X - X'` ETH remains trapped in `EvmHost` with no code path shown to return it.
