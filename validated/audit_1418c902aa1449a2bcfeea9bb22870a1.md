### Title
Front-runnable, unauthenticated pool initialization allows attacker to seize a market's canonical AMM-pool PDA slot with attacker-chosen mints/ratio - ([File: program/src/processor.rs])

### Summary
`process_initialize2` derives every account belonging to a new pool (`AmmInfo`, LP mint, coin/pc vaults, `TargetOrders`) from a single seed: the `market_info` account key, combined with fixed static seed strings (`AMM_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED`, `TARGET_ASSOCIATED_SEED`). `market_info` itself is explicitly *not* validated as a real, program-owned OpenBook market and is not required to be a signer — the code comments say outright that it can be "any account." [1](#0-0) [2](#0-1)  Because the resulting pool address space is fully deterministic from a public value that any observer can read out of a pending transaction (or simply guess in advance for a specific market), any unprivileged actor can submit their own `Initialize2` transaction using the same `market_info` key with attacker-controlled `coin_mint`/`pc_mint`/`init_coin_amount`/`init_pc_amount`, and — if it lands first — permanently claim that market's canonical AMM PDA slot.

### Finding Description
`process_initialize2` builds the pool's PDAs via `generate_amm_associated_account` / `generate_amm_associated_spl_token` / `generate_amm_associated_spl_mint`, all seeded with `market_account.key`. [3](#0-2)  These helper functions check only that the *derived* address matches the supplied account and that it is currently system-owned (uninitialized); if it is already owned by anything else they fail with `RepeatCreateAmm`. [4](#0-3)  There is no check binding `coin_mint`/`pc_mint` to the actual base/quote mints registered in the `market_info` account, and no requirement that `market_info` be owned by the OpenBook/Serum program or be a signer — the instruction handler even reads it in as "Just a seed for AMM account. Can be any account." [2](#0-1) 

Because Solana instructions are visible in the mempool before confirmation, an attacker who observes a legitimate `Initialize2` transaction targeting a given `market_info` can construct and submit their own `Initialize2` for the same `market_info` key (with arbitrary `coin_mint`, `pc_mint`, and minimal `init_coin_amount`/`init_pc_amount` under their control) and have it land first. Since all associated accounts (`AmmInfo`, LP mint, vaults, target orders) are PDAs of `market_info`, the attacker's transaction consumes that exact deterministic address space. The legitimate creator's follow-up transaction then fails at `generate_amm_associated_account`/`generate_amm_associated_spl_*` with `AmmError::RepeatCreateAmm`, permanently denying the intended pool for that market seed (the PDA cannot be re-derived under a different market key without changing the market itself).

The attacker, as sole initializer, becomes the recipient of the newly minted LP supply (minus the burned `10^decimals` floor) at whatever coin/pc ratio they chose, and controls which SPL mints back the "coin"/"pc" sides of the pool despite them having no relationship to the mints the community associates with that market. [5](#0-4) 

This is structurally the same bug class as the CPIMP/proxy front-running report: a resource is identified by a deterministic, publicly-derivable seed, initialization is not atomic with/protected against front-running, and whoever wins the race to initialize first permanently controls the resulting privileged state (here, ownership of the pool's LP supply and the mint pairing bound to that market identity), while later legitimate participants are locked out.

### Impact Explanation
- Attacker can permanently squat a specific market's AMM PDA address space with a pool containing attacker-chosen (potentially worthless or mismatched) mints and a skewed initial price ratio, then either extract value from downstream swappers/aggregators who trust the market→pool mapping, or simply grief the protocol by preventing the legitimate pool for that market from ever being created (permanent denial of service on that market's intended liquidity).
- The initial LP minting math (`liquidity = sqrt(pc*coin) - 10^decimals`) is entirely attacker-controlled since the attacker supplies both vault amounts, letting them set an arbitrary, non-market price for the pool identity that later traders may unknowingly interact with. [6](#0-5) 
- This qualifies as concrete impact under the validation criteria: permanent freezing of the intended pool's existence for that market and/or unbacked/mispriced LP issuance under attacker control.

### Likelihood Explanation
The `market_info` account key is public and its `Initialize2` transaction is visible in the mempool prior to confirmation, so any pool-creation transaction is trivially front-runnable by an unprivileged actor with no special access, matching the "single submitted transaction, attacker-chosen accounts and data" bar. No signer requirement, no market-mint binding, and no atomicity protection exist to stop it.

### Recommendation
- Require `market_info` to be validated as an actual, program-owned OpenBook/Serum `MarketState` account, and cross-check that its registered base/quote mints match the supplied `coin_mint`/`pc_mint`.
- Consider binding the pool creation to a creator-supplied nonce/signer or requiring the pool-creation and first-deposit to be submitted with commit-reveal or an allow-list, so front-running the deterministic PDA seed doesn't let an arbitrary third party claim the pool identity for a market that isn't theirs.
- At minimum, document/enforce that `Initialize2` callers must race-protect their own market-to-pool association off-chain, and add a check that rejects `Initialize2` if `market_info` is not owned by the configured `openbook_program`.

### Proof of Concept
1. Legitimate creator broadcasts `Initialize2` for market `M` with real mints `X`/`Y` and fair initial ratio.
2. Attacker observes the pending transaction (or simply knows `M` in advance), and submits their own `Initialize2` referencing the same `market_info = M`, but with `coin_mint = attacker_mint`, `pc_mint = attacker_mint2`, and minimal `init_coin_amount`/`init_pc_amount` sufficient to pass `InitLpAmountTooLess`, with higher priority fee.
3. Attacker's transaction lands first: `generate_amm_associated_account`/`generate_amm_associated_spl_mint`/`generate_amm_associated_spl_token` (all PDAs of `M`) succeed and assign ownership to the program, and `amm.initialize(...)` completes, minting all LP supply (minus the floor) to the attacker. [7](#0-6) 
4. Legitimate creator's transaction now fails at the same PDA derivation with `AmmError::RepeatCreateAmm` because the accounts are already program-owned. [8](#0-7) 
5. Market `M` now permanently maps to the attacker's mispriced/mismatched pool; the intended pool can never be created at that PDA address again.
