### Title
Webhook HMAC validation covers only the raw body, not the `shop-domain`/`topic` headers, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` verifies the HMAC exclusively against that body [1](#0-0) . The `shop`, `topic`, and `webhook_id` values used to attribute the webhook to a tenant are read straight from unauthenticated HTTP headers and are never included in the signed material [2](#0-1) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` before handing `request.shop` (and other header-derived values) to the app's handler as trusted tenant identity [3](#0-2) .

### Finding Description
The identity binding that should hold is: `hmac_verified_bytes == bytes_that_determine_tenant_identity`. Instead:
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received signature [4](#0-3) .
- For webhooks, `to_signable_string` is `@raw_body` only [5](#0-4) .
- `shop`, `topic`, and `webhook_id` are parsed from HTTP headers that are not part of the signed string at all [6](#0-5) .

The `api_secret_key` used to validate the HMAC is the app's single client secret, shared across **every** shop that has installed the app — it is not a per-shop secret. Any shop that has installed the app is a valid, unprivileged source of a `(raw_body, hmac)` pair signed with that same secret (e.g., by triggering any webhook-eligible event on their own store, or via any endpoint that echoes a webhook payload). Because the headers are excluded from the signed content, that exact `(body, hmac)` pair remains valid when replayed with **arbitrary** `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` header values pointing at a different, victim shop.

`Registry.process` raises only if `Utils::HmacValidator.validate(request)` fails [7](#0-6) , then immediately constructs `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` from the (unverified) headers and passes it to the app-registered handler [8](#0-7) . Nothing in this gem checks that the shop claimed in the header actually generated the signed body.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook consumers: an attacker who controls (or has installed the app on) shop A can obtain a validly-signed webhook body and replay it against the app's webhook endpoint while claiming to be shop B. Any handler logic that trusts `WebhookMetadata#shop` to route data, update per-shop records, or attribute the payload will act on shop B's tenant context using attacker-supplied body content — a cross-tenant access primitive as defined in scope (Critical impact category).

### Likelihood Explanation
Exploitability only requires: (1) installing the app on one shop (or otherwise obtaining any legitimately-signed webhook body from Shopify for the app), and (2) sending an HTTP request to the app's webhook endpoint with attacker-chosen `x-shopify-shop-domain`/`x-shopify-topic` headers and the captured body+HMAC. No access to `api_secret_key`, access tokens, or privileged accounts is needed — this is exactly the class of unprivileged, internet-reachable identity-binding break called out in scope.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the signable content verified by `HmacValidator`, or independently bind the verified body to a specific shop (e.g., by requiring the app to look up the topic/shop from the verified payload content rather than headers). At minimum, `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the `shop`, `topic`, and `webhook_id` header values into the HMAC-signed string so that `HmacValidator.validate` fails on any tenant/header substitution.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker-shop.myshopify.com`; trigger any registered webhook topic (e.g., `orders/create`) to receive a legitimate `(raw_body="{...}", x-shopify-hmac-sha256=<valid HMAC>)` pair signed with the app's `api_secret_key`.
2. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <topic the app handles>`
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC [9](#0-8) .
4. `Registry.process` dispatches to the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` [10](#0-9) , even though the body actually originated from and was signed for `attacker-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
