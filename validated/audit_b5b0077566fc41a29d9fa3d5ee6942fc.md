### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` builds the `hmac` signature check over the raw request body only, while the `shop` (tenant identifier), `topic`, and `webhook_id` fields that the app uses to determine *which merchant* the webhook belongs to are pulled straight from unauthenticated HTTP headers. The identity binding "HMAC-verified request == shop the app acts on" does not hold, since `shop` never enters the signed material.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string` [1](#0-0) . For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `Request#shop`, `#topic`, and `#webhook_id` are read directly from the (attacker-controllable) HTTP headers `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, with no cryptographic tie to the body or the HMAC: [3](#0-2) 

`Registry.process` validates only the HMAC over the body and then forwards `request.shop` (and topic/webhook_id) unchanged into `WebhookMetadata`, which host applications use to decide the tenant/merchant the event belongs to: [4](#0-3) [5](#0-4) 

The identity equality this breaks: `authenticated_body == HMAC(body, client_secret)` is enforced, but `shop_used_by_app != shop_covered_by_HMAC` — the `shop` field the app relies on for tenant routing (`WebhookMetadata#shop`) is outside the cryptographic envelope. Because the HMAC secret (`client_secret`) is shared across all shops that install the same app, any merchant that has installed the app can capture one of their own legitimately-signed webhook deliveries (valid body + valid HMAC) and replay it to the app's webhook endpoint with a forged `shopify-shop-domain` header pointing at a victim shop. `Utils::HmacValidator.validate` will still pass (it never inspects the header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop while carrying attacker-chosen body content, header `topic`, and `webhook_id`.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged (but validly onboarded, e.g. free-tier) merchant can cause the app to process data under another shop's identity. If the app trusts `WebhookMetadata#shop` to select the tenant record to update (e.g., `app/uninstalled`, `orders/*`, `customers/*` topics), the attacker can inject or manipulate data belonging to a different shop's tenant record, or spoof events (e.g., a fake `app/uninstalled`) against a shop they do not own. This matches the "Critical - cross-tenant access" category since the gem's own header parsing/binding is the root cause, not host-application misuse of a documented, correctly-scoped API.

### Likelihood Explanation
Medium-to-High: the attacker only needs to be a legitimate (even free) installer of the app in order to obtain one validly-HMAC-signed body/header pair from their own shop, then modify the `shopify-shop-domain` header (and optionally `topic`/`webhook_id`) and POST it to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only observation of one's own webhook traffic, which any merchant can capture.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified material, or otherwise cryptographically bind them to the HMAC-covered payload (e.g., verify a per-shop expected `shop` derived from the session/webhook subscription rather than trusting the header verbatim). At minimum, cross-check `request.shop` against an app-side registry of shop domains for which webhooks were actually subscribed before dispatching to `WebhookHandler#handle`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g.:
   - Headers: `shopify-topic: orders/create`, `shopify-hmac-sha256: <valid HMAC of body>`, `shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{"id": 1, ...}`
2. Attacker crafts a new HTTP POST to the app's webhook endpoint reusing the same body and the same `shopify-hmac-sha256` value (HMAC only covers the body, so it remains valid), but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `body` against `hmac` [6](#0-5) .
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: request.topic, body: ..., ...)` [7](#0-6)  and invokes the host app's handler as if the event genuinely originated from `victim-shop.myshopify.com`, even though it did not.
