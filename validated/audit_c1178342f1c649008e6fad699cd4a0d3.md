### Title
Webhook Shop Domain Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values that are handed to the app's webhook handler are parsed from HTTP headers that are never included in the signed material. Any merchant who has legitimately installed the app can capture one of their own validly-signed webhook deliveries and replay it against the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a different (victim) shop, and the request will still pass HMAC validation while being attributed to the victim shop.

### Finding Description
The signable string used for HMAC verification is defined as only the raw body: [1](#0-0) 

The `shop` accessor used downstream is read directly, and unauthenticated, from a header: [2](#0-1) 

`Registry.process` validates the request using only `Utils::HmacValidator.validate(request)`, which in turn calls `to_signable_string` (body-only), and then forwards `request.shop` unauthenticated straight into `WebhookMetadata`, which is passed to the app's handler: [3](#0-2) [4](#0-3) 

Because `api_secret_key` is shared across every shop that installs a given public app, any merchant/tenant that installs the app is able to generate or capture a request with a *valid* HMAC for their own shop's webhook body. Since the HMAC never covers the `shop-domain` header, that attacker can freely change the `shop-domain` header value on the captured request/body pair before replaying it to the app's webhook endpoint, and `HmacValidator.validate` will still return `true` because the signature check only inspects the body bytes.

The identity binding that should hold is:
```
shop authenticated by HMAC == shop attributed to the webhook data (request.shop used by handler)
```
In reality:
```
HMAC covers raw_body only != shop used for tenant routing (parsed from unauthenticated header)
```
This is exactly the "bytes verified versus bytes parsed" / "shop authenticated versus the shop... used as session key" class of identity-binding break.

### Impact Explanation
The documented usage pattern explicitly uses `data.shop` from `WebhookMetadata` to key or route work per tenant (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`, per the gem's own documentation): [5](#0-4) 

An attacker-controlled merchant can therefore inject attacker-controlled webhook bodies that the host application will process as if they originated from an arbitrary victim shop, since the gem provides no cross-check between the HMAC-verified bytes and the shop identity claimed via headers. This is a cross-tenant data-integrity/data-injection issue rooted entirely in this gem's `Webhooks::Request`/`Webhooks::Registry` design — the host app cannot detect the spoof because the library asserts the request "did indeed come from Shopify" (per its own documentation) purely from the body HMAC, while silently trusting the header-derived shop.

### Likelihood Explanation
Any unprivileged internet user can install a public app on their own Shopify development/test store (no special privilege required), trigger any webhook topic they are subscribed to, capture the genuine `raw_body` + `X-Shopify-Hmac-Sha256` pair from Shopify's real delivery, and replay it to the app's public webhook callback URL with a modified `X-Shopify-Shop-Domain` header. No access token, `client_secret`, or credential leak is required — only knowledge of the app's public webhook URL and topic, both discoverable by installing the app.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the material verified against the HMAC signature, or otherwise cryptographically bind the header-derived shop to the signed payload before it is trusted for tenant routing. At minimum, `Webhooks::Registry.process` should reject the header-derived `shop` unless it can be independently corroborated (e.g., checked against a known/registered shop for the given webhook topic/session), and the library's documentation should be corrected to state that only the body — not the shop, topic, or webhook id — is authenticated by `HmacValidator`.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. for `orders/create`, at the app's registered callback URL, with headers:
```
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>
X-Shopify-Shop-Domain: attacker-shop.myshopify.com
```
2. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but changes the header:
```
X-Shopify-Shop-Domain: victim-shop.myshopify.com
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body`; it matches, so validation succeeds — see: [1](#0-0) 
4. `request.shop` returns `victim-shop.myshopify.com` (attacker-controlled header value), and `WebhookMetadata` is built with this spoofed shop, then dispatched to the app's handler: [6](#0-5) 
5. The host application's handler processes attacker-supplied webhook data under `victim-shop.myshopify.com`'s identity, exactly as shown in the gem's own documented handler pattern (`shop_domain: data.shop`).
