### Title
Unvalidated `txMeta.keyId` allows signing with an unauthorized key/derivation path in `SeedBasedTransactionSigner.signTransaction` - (File: features/tx-signer/src/module/seed-signer.ts)

### Summary
`SeedBasedTransactionSigner.signTransaction` accepts an attacker-suppliable `unsignedTx.txMeta.keyId` and, if present, signs with that exact `KeyIdentifier` under the approved `walletAccount.seedId`, without checking that the keyId's `accountIndex`/`purpose`/`derivationPath`/`compatibilityMode` actually correspond to the `walletAccount` that was approved for the calling origin. The only check performed is structural (`KeyIdentifier.validate(keyId)`), not a scoping/consent check.

### Finding Description
The call chain is: `transactionSignerApi.signTransaction` (features/tx-signer/src/api/index.ts, resolves `walletAccount` but passes `unsignedTx` through unmodified) [1](#0-0)  → `TransactionSigner.signTransaction` (only asserts `txMeta` is an object) [2](#0-1)  → `SeedBasedTransactionSigner.signTransaction`.

In the seed signer, when `unsignedTx.txMeta.keyId` is present, it is validated only for shape via `KeyIdentifier.validate(keyId)`, then used directly to construct a signer bound to `walletAccount.seedId`: [3](#0-2) 

`#getSignerForKeyId` builds the signer from the raw supplied `keyId` with no cross-check against `walletAccount.index`, `compatibilityMode`, or asset purpose: [4](#0-3) 

Downstream, `keychain.signBuffer`/`getPublicKey` only validate `seedId`/`keyId` structurally and that the seed is unlocked — they do not enforce that the derived key belongs to a specific account index that was consented to: [5](#0-4) [6](#0-5) 

Because `walletAccount.seedId` is fixed to the seed backing potentially many accounts/assets, an attacker who controls `unsignedTx.txMeta` (per the documented 1:1 dapp-facing `exodus.transactionSigner.signTransaction` API surface — features/tx-signer/README.md) can set `txMeta.keyId` to a `KeyIdentifier` for a different `accountIndex`, `assetName`, `derivationPath`, or `purpose` than the one belonging to the approved `walletAccount`/asset combination that the user consented to sign for. The code comment even acknowledges this is an intentional escape hatch for cross-asset signing (EOS/Ripple use cases) but provides no allow-list or scoping restricting it to those legitimate cases.

### Impact Explanation
If a dapp/origin is only authorized (by user approval/connection) to interact with a specific `walletAccount`/asset, but can still smuggle a `keyId` for a different account index or derivation path within the same seed, it can obtain valid signatures under keys that were never approved for that origin/session. This can be leveraged to sign transactions that move funds from a different account than the user believed they approved, or produce raw signatures/public keys for arbitrary indices within the seed — a wrong-account signing/authorization bypass that could enable fund misdirection without a distinct, correctly-scoped re-approval.

### Likelihood Explanation
The precondition is only that the wallet is unlocked and that any caller (dapp/RPC/SDK integration) can invoke `transactionSigner.signTransaction` with a controlled `unsignedTx.txMeta.keyId` — this is the documented, dapp-facing entry point (`exodus.transactionSigner.signTransaction`, 1:1 with the SDK, per features/tx-signer/README.md). No privileged state or leaked keys are required; the flaw is a pure logic/scoping gap in `seed-signer.ts`. It is directly reachable and repeatable via a single call.

Note: I could not fully verify within available context whether a separate UI-level consent/approval screen (in an app not indexed here) independently re-derives and displays the exact `keyId`/derivation path to the user before signing, which could mitigate silent exploitation in practice; this module-level code, however, performs no such enforcement itself.

### Recommendation
In `SeedBasedTransactionSigner.signTransaction`, when `txMeta.keyId` is supplied, validate that it is consistent with the approved `walletAccount` (e.g., assert `keyId.accountIndex === walletAccount.index`, that `keyId.compatibilityMode` matches `walletAccount.compatibilityMode`, and restrict `keyId.assetName`/`purpose` to an explicit allow-list of legitimate cross-asset signing exceptions, e.g. EOS-via-Ethereum, Ripple, rather than accepting any well-formed `KeyIdentifier`). Alternatively, remove the generic `txMeta.keyId` override entirely and replace it with an explicit, narrowly-scoped API (e.g., `alternateAssetName`) that internally derives the permitted alternate key rather than accepting a raw `KeyIdentifier` from the caller.

### Proof of Concept
Unit test extending `features/tx-signer/src/module/__tests__/seed-signer.test.ts`:
1. Set up `seedSigner` as in the existing test harness with `walletAccount = walletAccounts[WalletAccount.DEFAULT_NAME]` (e.g., `accountIndex = 0`).
2. Construct `unsignedTx = { txData: {}, txMeta: { keyId: new KeyIdentifier({ assetName: 'bitcoin', derivationAlgorithm: 'BIP32', derivationPath: "m/84'/0'/5'/0/0", keyType: 'secp256k1' }) } }` — i.e., `accountIndex = 5`, different from `walletAccount.index = 0`.
3. Call `seedSigner.signTransaction({ walletAccount, baseAssetName: 'bitcoin', unsignedTx })`.
4. Expected (fixed) behavior: the call should `reject` with an error indicating the `keyId` does not match the approved `walletAccount`'s derivation scope.
5. Current (vulnerable) behavior: the call resolves successfully, producing a valid signature under account index 5's key using `walletAccount`'s `seedId`, proving the wallet signed with an unapproved key for the given `walletAccount`/origin context.

  async signBuffer({ seedId, keyId, data, signatureType, enc, tweak, extraEntropy, ...rest }) {
    const noTweak = tweak === undefined
    const noEnc = enc === undefined
    const noOpts = noEnc && noTweak && extraEntropy === undefined
    const invalidOptions = Object.keys(rest).filter((key) => key !== 'ecOptions') // ignore legacy option `ecOptions`

    assert(invalidOptions.length === 0, `unsupported options supplied to signBuffer()`)
    assert(data instanceof Uint8Array, `expected "data" to be a Uint8Array, got: ${typeof data}`)
    assert(
      (['ecdsa', 'schnorr', 'schnorrZ'].includes(signatureType) && keyId.keyType === 'secp256k1') ||
        (signatureType === 'ed25519' && ['nacl', 'cardanoByron'].includes(keyId.keyType)),
      `"keyId.keyType" ${keyId.keyType} does not support "signatureType" ${signatureType}`
    )

    if (signatureType === 'ed25519') {
      assert(noOpts, 'unsupported options supplied for ed25519 signature')

      if (keyId.keyType === 'cardanoByron') {
        return this.cardanoEd25519.signBuffer({ seedId, keyId, data })
      }

      return this.ed25519.signBuffer({ seedId, keyId, data })
    }

    if (signatureType === 'schnorrZ') {
      assert(noOpts, 'unsupported options supplied for schnorrZ signature')
      return this.secp256k1.signSchnorrZ({ seedId, keyId, data })
    }

    // only accept 32 byte buffers for ecdsa
    assert(data.length === 32, `expected "data" to have 32 bytes, got: ${data.length}`)

    if (signatureType === 'schnorr') {
      assert(noEnc, 'unsupported options supplied for schnorr signature')
      return this.secp256k1.signSchnorr({ seedId, keyId, data, tweak, extraEntropy })
    }

    // signatureType === 'ecdsa'
    assert(noTweak, 'unsupported options supplied for ecdsa signature')
    return this.secp256k1.signBuffer({ seedId, keyId, data, enc, extraEntropy })
  }
