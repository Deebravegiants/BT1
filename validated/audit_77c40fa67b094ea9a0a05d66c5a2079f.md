This confirms the design: the library explicitly documents `ShopifyAPI::Webhooks::Registry.process` as verifying "the request did indeed come from Shopify" (line 125 of `docs/usage/webhooks.md`), and delivers `data.shop` to the handler as the trusted tenant identifier [1](#0-0) , yet the `shop` value is taken from an HTTP header that is never covered by the HMAC computation.

### Title
Webhook shop-domain header is not bound by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate` succeeds, and then dispatches the handler using `request.shop`, taken from the `x-shopify-shop-domain` header. The HMAC, however, is computed only over the raw body, never over the shop-domain header, so the two identity claims (“HMAC-authenticated bytes” and “tenant the action is attributed to”) are not bound together.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`shop` is read from a separate, unauthenticated header: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e., the body) against the HMAC: [4](#0-3) 

`Registry.process` raises only if the HMAC check fails, then immediately trusts `request.shop` for dispatch: [5](#0-4) 

The binding that should hold is:
`HMAC-verified bytes == bytes that determine the tenant (shop) the handler acts on`

In this code it does not: `HMAC-verified bytes = raw_body` while `tenant identifier = headers["x-shopify-shop-domain"]`, which is disjoint from what is signed. Because the same `api_secret_key` is shared across every shop that installs the app, and many webhook topics have small or fixed/predictable bodies (e.g. `{}` for topics like `app/uninstalled`, `shop/redact`, etc., as used throughout this repo's own test fixtures [6](#0-5) ), an attacker who installs the app on their own store can capture a genuinely-signed webhook delivery (valid `hmac-sha256` for a given body) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to any victim shop domain. The HMAC still validates because it never covered that header, and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` for the attacker-chosen victim shop.

### Impact Explanation
This breaks tenant isolation: the app's webhook handler is documented to trust `data.shop` as "The shop domain of the webhook" once `Registry.process` confirms the request "did indeed come from Shopify" [7](#0-6) . Any host application that keys per-tenant side effects off `data.shop` (uninstall cleanup, GDPR redaction, order/product sync, billing state, etc., as shown in the doc's own example forwarding `data.shop` to a job queue [8](#0-7) ) can be made to perform that action against a shop the attacker does not own — a cross-tenant access impact.

### Likelihood Explanation
An unprivileged attacker only needs to install the target app on a store they control (a normal, permitted action for any Shopify merchant/developer), trigger or wait for a webhook whose body is fixed/predictable across topics, and replay the captured request to the app's public webhook endpoint with a modified shop header. No access token, `client_secret`, or privileged account is required — only the ability to be a legitimate tenant of the app once, which any internet user can obtain.

### Recommendation
Do not trust the `x-shopify-shop-domain` (or `shopify-shop-domain`) header as the tenant identifier unless it is cryptographically bound to the verified payload. Either:
- Bind the shop domain into the HMAC-verified signable string (e.g., include shop/topic/webhook-id in `to_signable_string`), or
- Require the host application to independently verify that `request.shop` corresponds to a shop with an active, known session/installation for this app before acting on the webhook, and document this requirement clearly, or
- Derive the shop identity from a value that is part of the signed body rather than headers.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`, obtaining legitimate webhook delivery for topic `app/uninstalled` with body `{}` and headers including `x-shopify-hmac-sha256: <valid-hmac-of-"{}">` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same body/HMAC to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` succeeds because it only checks `raw_body` (`"{}"`) against the HMAC, which is unaffected by the header change (`lib/shopify_api/webhooks/request.rb:35-43`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", body: {})` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host app to perform uninstall/redaction logic for `victim.myshopify.com` even though the attacker has no relationship with that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
