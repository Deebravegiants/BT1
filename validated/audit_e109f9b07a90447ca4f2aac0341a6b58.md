Audit Report

## Title
Missing balance verification in `ERC20Transactor` allows accounting desync with fee-on-transfer/deflationary ERC20 tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` credits the XCM `AssetsInHolding` register with the full `amount` requested by the caller as soon as the ERC20 `transfer()` call to the checking account succeeds (does not revert and returns `true`), without ever reading the checking account's actual token balance before/after the call. `deposit_asset_with_surplus` has the symmetric gap on the outgoing side. For any ERC20 contract whose `transfer()` delivers less than `value` to the recipient while still returning `true` (fee-on-transfer/deflationary tokens), the credited XCM holding amount will exceed the real balance increase in the checking account.

## Finding Description
On withdraw, the code builds `IERC20::transferCall { to: checking_address, value: amount }`, invokes it via `pallet_revive::Pallet::<T>::bare_call`, and — provided the call doesn't revert and the ABI-decoded return value is `true` — unconditionally constructs `Erc20Credit(amount)` and wraps it in `AssetsInHolding::new_from_fungible_credit`: [1](#0-0) . No `balanceOf` call is made before or after the transfer to confirm the checking account actually received `amount`. The symmetric deposit path transfers `amount` from the checking account to the beneficiary and treats a `true` return as full success without checking the beneficiary's balance delta: [2](#0-1) .

The asset matcher that feeds `asset_id`/`amount` into this transactor accepts *any* local `AccountKey20` location without any allow-list, registration, or governance gate: [3](#0-2) . This is exactly the behavior documented in the PRDoc, which states any asset id of the form `{parents:0, interior: X1(AccountKey20{key,network})}` is matched and its `transfer` is invoked with no mention of any balance-delta check or safe-transfer wrapping: [4](#0-3) . `ERC20Transactor` is wired into `AssetTransactors` on Asset Hub Westend, confirming it is a live, reachable path: [5](#0-4) .

I confirmed by reading the full `erc20_transactor.rs` file that there is no balance check anywhere in either function — the only signals used are `did_revert()` and the boolean ABI-decoded return value. There is no `balanceOf` call in the file at all.

## Impact Explanation
This is a genuine logic gap: the credited/debited XCM holding amount is derived from the caller-supplied `amount`, not from an observed balance delta, so it can diverge from the real ERC20 balance held by the checking account whenever the token's `transfer()` semantics do not deliver the full nominal amount (fee-on-transfer, deflationary/rebasing tokens, or any non-standard `transfer()` implementation that still returns `true`).

However, the practical exploitability for this class of bug is weaker than claimed for the following reason: because `ERC20Matcher` accepts *any* `AccountKey20` address with no registration step, an attacker can only meaningfully exercise this bug against a contract they themselves deploy and control. For a fee-on-transfer contract fully controlled by the attacker (mint function, fee parameters, etc. all attacker-defined), the attacker does not need this accounting-desync bug to obtain value — they can simply mint themselves unlimited tokens directly in their own contract. The bug becomes economically meaningful only if a third-party-controlled, already-valuable deflationary token is later matched by this transactor and other, unrelated users deposit real value into the checking account for that same contract; in a system with no permissioned asset registration, this is a plausible but still narrower/less immediate scenario than "any user can drain the system," and the impact is explicitly isolated to a single contract's own checking-account ledger, not systemic.

## Likelihood Explanation
No privileged role is required to reach the code path: any user can deploy a `pallet-revive` contract implementing `IERC20` and reference its address as an `AccountKey20` asset id in an XCM program, which `ERC20Matcher`/`ERC20Transactor` will process without any gate. The root-cause code (trusting the boolean return value alone) is verified present exactly as described.

## Recommendation
In `withdraw_asset_with_surplus`, query the checking account's ERC20 balance before and after the `transfer` call and credit `AssetsInHolding` with the observed delta instead of the requested `amount`. Symmetrically, in `deposit_asset_with_surplus`, verify the beneficiary's balance delta matches `amount` (or handle/report the shortfall) rather than trusting the boolean return value alone.

## Proof of Concept
1. Deploy a `pallet-revive` ERC20-like contract whose `transfer(to, value)` deducts a fee (e.g., burns 5%) before crediting `to`, but still returns `true`.
2. Construct an XCM program with `WithdrawAsset(asset)` where `asset.id` is `{parents:0, interior: X1(AccountKey20{key: <contract_address>, network: None})}` and `fun: Fungible(amount)`.
3. Execute via `pallet_xcm` from a signed account holding `amount` tokens; the code at `erc20_transactor.rs:197-203` will produce `Erc20Credit(amount)` in the holding register even though the checking account's real balance only increased by `amount * 0.95`.
4. Repeat and compare cumulative credited amounts against `balanceOf(checking_account)` to demonstrate the divergence.

This should be validated in an integration/fork test using `pallet-revive`'s deployed test fixtures plus a custom fee-on-transfer `IERC20` mock, executing real XCM `WithdrawAsset`/`DepositAsset` instructions through `pallet_xcm`, and asserting `AssetsInHolding` credited amount vs. on-chain `balanceOf` delta.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
