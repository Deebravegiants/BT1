Confirmed. `Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), so the HMAC computed over that string never covers the `shopify-shop-domain` / `x-shopify-shop-domain` header. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks that the body's HMAC matches under `Context.api_secret_key` (`lib/shopify_api/webhooks/registry.rb:189-190`, `lib/shopify_api/utils/hmac_validator.rb:13-31`), then forwards `request.shop` straight into `WebhookMetadata` passed to the handler (`lib/shopify_api/webhooks/registry.rb:198-199`). Since a single `client_secret`/`api_secret_key` is shared by the app across every merchant, and the shop identity is carried in an unsigned header, this breaks the identity binding `shop_used_by_handler == shop_that_produced_the_signed_body`.

### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` header, while `Registry.process` trusts `request.shop` (parsed from that unsigned header) to determine which merchant a webhook belongs to.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
and `shop` is read from a header that is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` accepts any `Request` whose body HMAC checks out, then passes `request.shop` (the unsigned header) into the handler as the authoritative shop identity: [4](#0-3) 

Because `client_secret`/`api_secret_key` is the same value for every shop installed on a given app, any holder of one valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on an attacker-controlled development store and receiving a legitimate webhook — can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The HMAC still validates (it never covered the header), so `Registry.process` dispatches the (attacker's) event data to the handler under a victim shop's identity. This breaks the equality `shop_bound_by_signature == shop_delivered_to_handler`.

### Impact Explanation
This is a cross-tenant identity spoofing: the receiving application's webhook handler (built on top of this gem's documented `WebhookMetadata#shop`) will process attacker-supplied data believing it originated from a shop chosen by the attacker, without any credential belonging to that shop. Depending on what the host app does with `shop` (e.g., looking up/mutating per-shop records, triggering shop-scoped side effects), this can lead to cross-tenant data corruption or disclosure — a Critical-class impact under the given rubric (cross-tenant access).

### Likelihood Explanation
No secrets or privileged access are required beyond the ability to install the target app on any store (including the attacker's own free/dev store) to legitimately receive one signed webhook, and the ability to send arbitrary HTTP requests to the app's public webhook callback endpoint. Both are available to an unprivileged internet user.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed payload verification path, e.g. by binding `to_signable_string` to a canonicalized combination of the raw body and the relevant Shopify headers, or by requiring host applications to cross-check `request.shop` against an independently-verified source (e.g., the app-installation record keyed by the `X-Shopify-Webhook-Id`/registered callback) before trusting it. At minimum, document prominently that `Request#shop` is unauthenticated and must not be used as a tenant key without further verification.

### Proof of Concept
1. Install the target app on an attacker-controlled store `attacker.myshopify.com` (a normal, unprivileged install).
2. Trigger any subscribed webhook topic (e.g. `products/update`) and capture the raw POST body plus the `X-Shopify-Hmac-Sha256` header sent by Shopify to the app's callback endpoint.
3. Replay the identical body and HMAC header to the same endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks the raw body against the shared `api_secret_key` (`lib/shopify_api/utils/hmac_validator.rb:12-31`); the handler then receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` built from attacker-controlled body data (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload never actually came from `victim.myshopify.com`.
