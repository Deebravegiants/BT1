### Title
Webhook shop-domain field trusted for identity while not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature verified by `Utils::HmacValidator.validate` covers exclusively the request body. The `shop`, `topic`, `api_version`, and `webhook_id` values are all read from unauthenticated HTTP headers and are never included in the signed material, yet `Registry.process` passes `request.shop` straight into the handler as the authoritative tenant identity.

### Finding Description
`Request#hmac`/`#to_signable_string` bind the signature check to the raw body only: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from the `shopify-*`/`x-shopify-*` headers, which are not part of `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` only checks that the computed HMAC over `to_signable_string` matches the supplied `hmac`, i.e. it authenticates the body bytes, not the header-derived fields: [3](#0-2) 

`Registry.process` then trusts `request.shop` (and `request.topic`, `request.webhook_id`) as the tenant identity forwarded to the app's handler after only checking the HMAC: [4](#0-3) 

This is the exact analog of the M-8 pattern: an identity-relevant field (`shop`) is *acted on* (used to build `WebhookMetadata` and dispatched to the app's business logic keyed by tenant) but is *not covered* by the cryptographic check that is supposed to authenticate the request. `shop == HMAC-authenticated shop` does not hold; the equality that actually holds is only `raw_body == HMAC-authenticated bytes`.

### Impact Explanation
Any party that can obtain one valid `(raw_body, hmac)` pair for the app's client secret — for example by installing the app on their own shop and receiving one real webhook delivery — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and topic/webhook-id headers) with an arbitrary victim shop domain. Because the shop field is never part of the signed content, `HmacValidator.validate` still returns `true`, and `Registry.process` will hand the forged tenant identity to the app's webhook handler via `WebhookMetadata#shop`. If the host application uses this value to key data lookups, cache invalidation, or state changes (a common, foreseeable usage of `WebhookMetadata`), this enables cross-tenant data confusion/write using only knowledge of one legitimately-received webhook body, without the app's `client_secret`.

### Likelihood Explanation
This requires no privileged credential — merely one's own (attacker-controlled) shop installing the app to receive a single legitimate webhook, after which the header can be freely rewritten for replay against the app's public endpoint. However, this mirrors Shopify's actual, documented webhook signing scheme (Shopify itself only HMACs the raw body, not headers), so a defensively-written host application is expected to additionally validate the source (e.g., matching `shop` against a known/installed-shop list before trusting it) rather than relying solely on this gem's `HmacValidator`. Because this gem's public documentation and API surface do not present `HmacValidator.validate` as authenticating anything beyond the body, and the header-derived `shop`/`topic` fields are exposed only as plain accessors (not claimed to be authenticated), this weakness is best characterized as an inherited protocol limitation rather than a defect unique to this gem's binding logic. This tempers confidence that it clears the "gem's own code" bar independent of host application behavior.

### Recommendation
If feasible, extend `Request#to_signable_string`/`HmacValidator` semantics (or add a documented helper) that also authenticates the `shop`, `topic`, and `webhook-id` header values against a canonical, signed representation, or explicitly document that `Registry.process`/`WebhookMetadata#shop` is not a cryptographically-verified tenant identity and that host apps must cross-check it against known installed shops before acting on it.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers/receives one real webhook delivery, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header (valid because it was computed by Shopify with the app's real `client_secret`).
2. Attacker sends a new HTTP POST directly to the app's webhook endpoint with the same `raw_body` and `hmac` header, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `shop` is `"victim-shop.myshopify.com"`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC and returns `true`.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to act as if the event originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
