This confirms the vulnerability. The `Webhooks::Request` class computes its HMAC signature exclusively over the raw request body via `to_signable_string` returning `@raw_body` [1](#0-0) , while the `shop` value used downstream comes from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed payload [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (which validates `to_signable_string`, i.e., the raw body) and then trusts `request.shop` to build `WebhookMetadata` dispatched to the app's handler [3](#0-2) . `HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string`, never incorporating the shop domain [4](#0-3) .

### Title
Cross-Tenant Webhook Spoofing via Shop-Domain Header Not Covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is completely excluded from the HMAC-signed payload. The library's own webhook dispatch (`Registry.process`) uses this unauthenticated `shop` value to build `WebhookMetadata` passed to the app's registered handler, breaking the binding: `shop authenticated by HMAC` != `shop used by handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight from the `shopify-shop-domain` header without any cryptographic binding to that body [2](#0-1) . `HmacValidator.validate` / `validate_signature` re-derive the HMAC exclusively from `to_signable_string` and compare it to the `hmac-sha256` header using `OpenSSL.secure_compare` [5](#0-4) . Because the shop-domain header is never part of the signed string, any `(raw_body, hmac)` pair that is valid for shop A remains a byte-for-byte valid signature when replayed with a different `shopify-shop-domain` header value for shop B. `Registry.process` performs no additional binding check before dispatching: it validates the HMAC, looks up the handler by topic, and forwards `request.shop` (the untrusted header) directly into `WebhookMetadata` given to the app's handler [3](#0-2) .

Because all shops served by a multi-tenant app share the same `api_secret_key`/`client_secret`, a malicious merchant who installs the app and receives a genuine webhook (with a valid `hmac-sha256` for their own tenant's body) can capture that raw body + HMAC pair and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. The gem's `Registry.process` will accept the HMAC as valid (it only checks the body) and will invoke the app's handler believing the event originated from the victim shop, with `WebhookMetadata#shop` set to the victim's domain and `WebhookMetadata#body` containing the attacker-controlled payload from their own shop.

### Impact Explanation
This breaks tenant isolation: an unprivileged app-installer (any merchant who installs the multi-tenant app) can cause the host application's webhook handler to process attacker-supplied data under a victim shop's identity. Depending on how host applications trust `WebhookMetadata#shop` (which the library's own docs instruct apps to use to look up/scope the affected tenant's records), this enables cross-tenant data corruption/access — e.g., writing attacker data into or triggering shop-scoped actions (billing, redact/GDPR flows, inventory, order webhooks) against a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category since the identity binding (shop <-> signed payload) that the gem is expected to enforce is absent.

### Likelihood Explanation
Likelihood is high for any app built on this gem that dispatches per-shop logic based on `WebhookMetadata#shop` without independently re-verifying the shop (which the gem's documentation does not instruct developers to do, since HMAC validation is presented as the full trust mechanism). The only precondition is that the attacker has (or can install a trial/dev instance of) the target app on at least one shop they control, which is trivial for any public/multi-tenant app — no leaked credentials, access tokens, or privileged accounts are required, satisfying the "unauthorized internet user" threat model.

### Recommendation
Include the shop domain (and ideally other identifying headers such as `topic`/`webhook-id`) inside the HMAC-signed material, or otherwise cryptographically bind `shop` to the verified body before it is handed to `Registry.process`/the app handler — e.g., have `Request#to_signable_string` incorporate the shop header, or have `HmacValidator`/`Registry.process` require an out-of-band verification that the domain in the header matches the domain embedded in the (signed) body/topic context.

### Proof of Concept
```ruby
require "shopify_api"

# Attacker legitimately installs the multi-tenant app on their own shop,
# "attacker-shop.myshopify.com", and receives a real webhook.
raw_body = '{"id": 1, "note": "hello"}' # genuine payload for attacker's shop
real_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the same (raw_body, hmac) pair but swaps the shop-domain header
# to the victim shop. HMAC validation only checks raw_body, so it still passes.
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)

# Passes HMAC validation (only the body is checked) and dispatches with
# request.shop == "victim-shop.myshopify.com", even though the body/HMAC
# actually originated from attacker-shop.myshopify.com.
ShopifyAPI::Webhooks::Registry.process(request)
```
