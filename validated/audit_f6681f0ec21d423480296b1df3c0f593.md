This confirms the finding: the docs explicitly state `Registry.process` "will verify the request did indeed come from Shopify" based purely on HMAC validation, and the `shop` field returned by `data.shop` (documented at `docs/usage/webhooks.md:14`) is meant to identify "The shop domain of the webhook" — but that field is never part of the HMAC-signed content.

### Title
Webhook `shop` Field Is Not Covered by HMAC Signature, Allowing Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`/`webhook_id`/`api_version`) values are read from HTTP headers that are completely excluded from the signed content. `ShopifyAPI::Webhooks::Registry.process` treats a valid body HMAC as proof that "the request did indeed come from Shopify" for the shop named in the header, then hands that unauthenticated `shop` value straight to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 
`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e. the body) against the computed HMAC using `Context.api_secret_key`: [3](#0-2) 
`Registry.process` accepts the request once that body HMAC checks out, and then constructs `WebhookMetadata` directly from the unauthenticated `request.shop` header value, passing it to the app's handler as the shop of record: [4](#0-3) 

Because a single app's webhook HMAC secret (`Context.api_secret_key`, i.e. the app's client secret) is shared across every merchant shop that has installed the app, any unprivileged user who owns/controls a shop that has installed the app can trigger a legitimate webhook to be sent to the app's endpoint for their own shop, capturing a validly-signed `(raw_body, hmac)` pair. That pair remains fully valid under `HmacValidator.validate` regardless of which `shop-domain` header accompanies it, since the header is never part of the signed content. The attacker can then replay that same body+HMAC to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop. `Registry.process` will accept it as authentic and invoke the handler with `shop: <victim shop>`, `body: <attacker's own webhook data>`.

This breaks the identity binding "the shop authenticated by the signature" vs. "the shop the app treats as the tenant/session key" — the gem authenticates only the body, but the host application (as documented) is told to trust `data.shop` as the authenticated tenant identifier.

### Impact Explanation
This is a cross-tenant data injection: an attacker with access to only their own (possibly free/trial) shop installation of the app can cause the host application to process fabricated webhook payloads under a different, victim shop's identity. Depending on how the host app uses `data.shop` (e.g., looking up the victim's stored access token/session and applying attacker-controlled webhook body data to that shop's records, job queues, or database rows), this can lead to cross-tenant data corruption, or an attacker forging events (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`) against another merchant's data pipeline. This matches the "cross-tenant access" high-severity criteria, as the shop-identity binding used to route trusted webhook data is not authenticated.

### Likelihood Explanation
Exploitation requires only: (1) an attacker-controlled shop that has installed the target app (trivial via a free Shopify developer/trial store), (2) the ability to trigger at least one webhook delivery to the app (trivial — e.g., updating an order), and (3) the ability to POST an HTTP request to the app's public webhook endpoint with a modified header, which is inherent to how HTTP webhook delivery works and requires no secret knowledge. No credentials, TLS interception, or privileged access are needed.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the HMAC-signed content that `Utils::HmacValidator.validate` checks, e.g., by having `Webhooks::Request#to_signable_string` incorporate the shop domain header alongside the raw body (mirroring the approach `Auth::Oauth::AuthQuery#to_signable_string` already takes for OAuth, where `shop` is explicitly part of the signed string as seen in `lib/shopify_api/auth/oauth/auth_query.rb:34-43`). Alternatively, document explicitly and prominently that `data.shop` from `WebhookMetadata` is unauthenticated and must not be trusted as a tenant key without independent verification (e.g., cross-checking against the webhook's registered callback association) — though correcting the signature scope is the more robust fix.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (self-serve, no privileges needed).
2. Attacker triggers an action (e.g., creates an order) causing Shopify to send a legitimately HMAC-signed webhook to the app's `path` endpoint, with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of raw body>`, and body `B`.
3. Attacker intercepts/replays this exact `(B, valid_hmac)` pair to the same app endpoint, but replaces the header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com"})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against the HMAC — validation succeeds.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-supplied data as if it originated from `victim.myshopify.com`.
