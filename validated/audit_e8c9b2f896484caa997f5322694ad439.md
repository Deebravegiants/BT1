Audit Report

## Title
Username Enumeration via Distinguishable Login Error Responses in Local Session Authentication - (File: `core/sessions/localauth/orm.go`)

## Summary
The `/sessions` login endpoint (`SessionsController.Create`) returns different, distinguishable error messages depending on whether the submitted email exists in the `users` table. An unknown email causes the raw `sql.ErrNoRows`-derived error to propagate unmodified from `findUser`/`CreateSession`, while a known email with an incorrect password returns the fixed string `"Invalid password"`.

## Finding Description
`CreateSession` in `core/sessions/localauth/orm.go` (lines 144-148) calls `FindUser`, which calls `findUser` (lines 55-59) that performs `o.ds.GetContext(ctx, &user, sql, email)` without wrapping the "no rows" case. When the email doesn't exist, this raw DB error is returned unmodified up through `CreateSession` to `SessionsController.Create` (`core/web/sessions_controller.go:56-60`), which calls `jsonAPIError(c, http.StatusUnauthorized, err)`. That helper (`core/web/helpers.go:19-29`, duplicated in `core/web/auth/helpers.go`) serializes `err.Error()` verbatim into the JSON:API response `detail` field unless the error is already a `*models.JSONAPIErrors`. In contrast, when the email exists but the password is wrong, `CreateSession` (lines 159-162) explicitly returns `pkgerrors.New("Invalid password")`, a distinct, deterministic string. No middleware, redaction, or generic-error normalization intervenes between these two code paths and the HTTP response body.

## Impact Explanation
An unauthenticated network attacker can enumerate valid node user emails by observing whether `POST /sessions` returns a raw SQL-style error (unknown email) versus `"Invalid password"` (known email). This is an information-disclosure vulnerability (CWE-200/CWE-204) that materially aids follow-on credential-stuffing, targeted phishing, or brute-force attacks against a Chainlink node's Operator UI/API, which controls job management and fund-related operations.

## Likelihood Explanation
The endpoint is unauthenticated, requires no prior privilege, and is directly reachable on any node exposing its standard HTTP login API. The distinguishing signal is deterministic, repeatable, and trivially scriptable, making exploitation highly likely wherever this API is network-accessible.

## Recommendation
Normalize all `CreateSession` failure paths in `core/sessions/localauth/orm.go` to return one generic, identical error (e.g., `"invalid credentials"`) regardless of whether email lookup failed or password check failed, ensuring no raw database error (e.g., `sql.ErrNoRows`) is ever propagated into the HTTP response. Apply the same fix to any LDAP/OIDC fallback paths exhibiting the analogous "invalid email"/"invalid password" distinction.

## Proof of Concept
1. `POST /sessions` with `{"email": "definitely-not-a-real-user@example.com", "password": "wrongpass"}` → response `errors[0].detail` contains a raw SQL/no-rows-style error string.
2. `POST /sessions` with `{"email": "<valid-existing-admin-email>", "password": "wrongpass"}` → response `errors[0].detail` is exactly `"Invalid password"`.
3. The differing response bodies let an attacker script a loop over candidate emails to confirm which are registered node users, without any credentials or authentication.

	}

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
