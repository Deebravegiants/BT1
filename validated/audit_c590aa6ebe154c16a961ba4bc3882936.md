**Analysis**: The `TwoKeyRegistry` used by `StateKey::position` is a genuine two-level `HashMap<Key1, HashMap<Key2, Weak<Entry>>>` structure, not a hash-collision cache [1](#0-0) . The `position()` helper on `StateKeyRegistry` only uses a coarse hash of the last byte of `exchange`/`account`/`market` to pick which of the 8 `position_shards` array slots to route the request to [2](#0-1) ; it does not determine the actual cache key used for lookup/storage.

Inside the selected shard, `get_or_add` (and `read_lock_try_get`/`write_lock_get_or_add`) index by the real, owned key values `key1 = (exchange, account)` and `key2 = market`, using standard Rust `HashMap` equality semantics — a hash collision in the shard-selection function or in Rust's internal hash buckets cannot cause two distinct `(exchange, account, market)` tuples to be treated as the same entry, because `HashMap::get`/`insert` always confirm full key equality, not just hash equality [3](#0-2) .

Consequently, `StateKey::position(exchange, account, market)` always creates or fetches an `Entry` whose `deserialized` field (`StateKeyInner::TradingNative(TradingNativeKey::Position { exchange, account, market })`) is built directly from the exact inputs of that call [4](#0-3) . A different market address for the same `(exchange, account)` pair is a distinct `key2` in the nested map, so it gets its own independent `Entry`; there is no path by which one market's lookup can return another market's cached `Entry`.

This pattern mirrors the identical interning scheme already used for `resource`, `resource_group`, `module`, and `table_item` state keys in the same file, all of which rely on the same two-level exact-match `HashMap`, so there's no novel collision surface introduced by the `TradingNative`/`position` addition [5](#0-4) .

Because the premise (that keying "only on (exchange, account) plus a hash of market" could merge distinct markets into one cached entry) does not hold — the actual lookup structure enforces exact equality on all three fields — there is no custody-impacting collision, misrouted position data, or freeze/settlement risk from this code path.

        &self,
        key1: &Ref1,
        key2: &Ref2,
        inner_gen: Gen,
    ) -> Result<Arc<Entry>>
    where
        Key1: Borrow<Ref1>,
        Key2: Borrow<Ref2>,

        Ref2: Eq + Hash + ToOwned<Owned = Key2> + ?Sized,

        // n.b. construct Entry only when decided to insert to registry, to save on drop
        let deserialized = inner_gen()?;
        let encoded = deserialized.encode().expect("Failed to encode StateKey.");
        let hash_value = {
            let mut state = StateKeyInnerHasher::default();
            state.update(&encoded);
            state.finish()
        };

        let mut locked = self.inner.write();

        Ok(match locked.get_mut(key1) {
            None => {
                let mut map2 = locked.entry(key1.to_owned()).insert(HashMap::new());
                let entry = Entry::new(deserialized, encoded, hash_value);
                Self::insert_key2(map2.get_mut(), key2.to_owned(), entry)
            },

                    let entry = Entry::new(deserialized, encoded, hash_value);
                    Self::insert_key2(map2, key2.to_owned(), entry)
                },
                Some(weak) => match weak.upgrade() {
                    Some(entry) => {
                        // some other thread has added it
                        entry
                    },
                    None => {
                        // previous version of this key is being dropped.
                        let entry = Entry::new(deserialized, encoded, hash_value);
                        Self::insert_key2(map2, key2.to_owned(), entry)
