### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Registry.process` authenticates the body bytes only. The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from unauthenticated HTTP headers and handed to the app's handler as trusted tenant-identifying data.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhooks that method is defined to be just the raw body: [1](#0-0) 

The `shop` (and `topic`/`api_version`/`webhook_id`) accessors are pulled from headers that are never part of the signed bytes: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching, then forwards the unauthenticated `request.shop` straight to the app's `WebhookHandler` as the tenant identifier: [3](#0-2) 

This breaks the identity binding: `hmac_verified(body) == true` is treated as equivalent to `shop_header == tenant_that_produced(body)`, but the gem never establishes that equality — the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that has installed the app, and the signature says nothing about which shop the body belongs to.

### Impact Explanation
Because the signing key is shared across all tenants of the app, any merchant/user who can capture (or is legitimately sent) one valid `(body, hmac)` pair for their own shop can replay that exact body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header for a different shop. `Utils::HmacValidator.validate` still passes (body/HMAC pair is untouched), and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen shop domain. Any host application that uses `data.shop` to select a per-tenant session/store (the documented and expected usage pattern shown in `docs/usage/webhooks.md`) will apply Shop A's payload to Shop B's tenant context — a cross-tenant data-injection/confusion issue.

### Likelihood Explanation
Reachable by any unprivileged internet user who is a legitimate (even single-shop) installer of the target app: they only need one real webhook body+HMAC pair for their own shop (easily obtained since they control their own store's events) and the ability to POST to the app's public webhook endpoint with modified headers. No access token, `client_secret`, or privileged account is required.

### Recommendation
Include the tenant-identifying header(s) (`shop-domain`, and ideally `topic`/`webhook-id`) in the signed payload used for HMAC verification, or independently verify that the `shop` header corresponds to a shop with an active installation/session before trusting it in `WebhookMetadata`, rather than relying solely on a body-only HMAC that is shared across all tenants.

### Proof of Concept
1. As a legitimate merchant, install the target app on `shop-a.myshopify.com`; trigger any subscribed webhook topic and capture the raw POST body and its `x-shopify-hmac-sha256` header (both are visible to the shop owner).
2. Replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint, but change `x-shopify-shop-domain` to `shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` in `Registry.process` succeeds because it only checks the body against the HMAC: [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` while `body` actually belongs to `shop-a`, causing the app to process/persist Shop A's data under Shop B's tenant identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
