### Title
Challenge-response authentication in `auth-client-base` lacks mandatory domain separation, enabling cross-service signature replay - ([File: libraries/auth-client-base/client.js])

### Summary
`Client#_authenticate()` signs a server-issued auth challenge with the wallet's `keyPair` to obtain a bearer token. Binding the signature to the specific backend service is only done when a `serverId` config value is supplied, and that value is optional. This mirrors the reported bug class exactly: a signed artifact (here, a signature over a raw challenge) that is not bound to the specific context (`address(this)` in the report, `serverId`/target service here) can be captured in one context and replayed in another.

### Finding Description
`Client._authenticate()` fetches a `challenge` from `authChallengeUrl`, optionally prepends `serverId` to it, and signs the result with the client's `keyPair`: [1](#0-0) 

The `serverId` field is declared as `typeforce.maybe(typeforce.String)` in the constructor's config validation, meaning it is entirely optional: [2](#0-1) 

If a consumer of this library instantiates `Client` (or `createClient`) without a `serverId` — as shown in the library's own `example.js` and test fixtures, neither of which set `serverId` — the value signed by the keypair is just the raw `challenge` bytes with no indication of which backend (`authChallengeUrl`/`authTokenUrl` pair) it was intended for: [3](#0-2) [4](#0-3) 

This is structurally identical to the reported bug: a signed/committed value (`_number`/`_salt` hash in the report; a `signedChallenge` here) that proves possession of a secret but is not bound to a specific execution context (`address(this)` in the report; the specific backend service here) can be replayed wherever the same verification logic and same public key are trusted.

### Impact Explanation
Any backend/service acting as a man-in-the-middle relay (e.g., a compromised or malicious service that shares the client's public key registration with another legitimate Exodus backend) could present the client with a challenge it obtained from a second, legitimate service. The client, having no way to know which service the challenge belongs to, would sign it and return `signedChallenge`. That signature can then be replayed by the attacker to the second, legitimate service's `authTokenUrl` to mint a valid bearer token and authenticate as the victim — an authentication bypass/identity impersonation across services, without ever needing the private key itself. This matches the report's "guaranteed win"-style abuse pattern: the artifact is only safe as long as it stays within a single trust boundary, but the code makes that boundary optional rather than enforced.

### Likelihood Explanation
Exploitation requires a relay position between the client and two services trusting the same public key/`keyPair`, plus one of those integrations omitting `serverId` — a config the library treats as optional rather than required, and which is in fact omitted in the library's own example/tests. Likelihood is Low, matching the original report's Low likelihood rating for the same reason (needs a specific multi-context reuse setup), but the impact when it occurs is High (full auth bypass), consistent with the source report's High-impact/Low-likelihood classification.

### Recommendation
Make `serverId` (or an equivalent, unique-per-deployment identifier such as `authTokenUrl`/service host) a required field in the config `typeforce` schema, and always mix it into the signed payload (with proper length-prefixing/domain-separated encoding, not naive `Buffer.concat`) rather than making the binding conditional: [5](#0-4) 
This ensures a signed challenge captured from one service can never be replayed to authenticate against another, directly analogous to the report's recommendation to encode `address(this)` in `verifySalt()`.

### Proof of Concept
1. Configure two `Client` instances (Service A and Service B) with the same `keyPair` but without `serverId`, as done in `example.js`/`client.test.js`.
2. Attacker-controlled Service A forwards to the victim's client the `challenge` value that Service A itself received from Service B's `authChallengeUrl`.
3. The client computes `signedChallenge = keyPair.sign(challenge)` (no `serverId` prefix) and returns it to (attacker) Service A.
4. Attacker replays `{ publicKey, signedChallenge }` to Service B's real `authTokenUrl`.
5. Service B verifies the signature against `challenge` + `publicKey`, sees a valid signature (because nothing in the signed bytes ties it to Service A), and issues a legitimate bearer `token`, completing an authentication bypass on Service B without the attacker possessing the private key. [6](#0-5)

```javascript
  _authenticate() {
    const { keyPair, authChallengeUrl, authTokenUrl, serverId } = this._config
    this._authPromise = (async () => {
      if (!keyPair) {
        return
      }

      const { challenge } = await this._request('POST', authChallengeUrl, {
        auth: false,
        data: {
          publicKey: keyPair.publicKey.toString('hex'),
        },
      })

      let encodedChallenge = Buffer.from(challenge, 'base64')

      if (serverId) {
        encodedChallenge = Buffer.concat([Buffer.from(serverId), encodedChallenge])
      }

      const signedChallenge = await keyPair.sign(encodedChallenge)
      const { token } = await this._request('POST', authTokenUrl, {
        auth: false,
        data: {
          publicKey: keyPair.publicKey.toString('hex'),
          signedChallenge: signedChallenge.toString('base64'),
        },
      })

      this._token = token
    })()

    return this._authPromise
```
