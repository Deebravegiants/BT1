Confirmed root cause: `dispatch_request` in `modules/pallets/ismp/src/dispatcher.rs:92-151` takes `dispatch_post.from`/`dispatch_get.from` verbatim from the caller-supplied `DispatchPost`/`DispatchGet` struct and writes it straight into the resulting `PostRequest.from` field with no validation that the caller is actually the module it claims to be.

### Title
Unvalidated attacker-supplied `from` field lets any pallet/user forge the `module_id` used by the outbound-request-delivery reward allowlist - (File: modules/pallets/ismp/src/dispatcher.rs)

### Summary
`App::Ack`'s bug class is "attacker-controlled string data is trusted and forwarded unchanged into a context that treats it specially." In pallet-ismp's dispatcher, the analogous unsanitized field is `DispatchPost::from` / `DispatchGet::from`: it is copied verbatim into `PostRequest.from` at `modules/pallets/ismp/src/dispatcher.rs:108-146`, and that same value is later trusted as the caller's identity by `pallet_ismp_relayer::outbound_request::process_outbound_request_delivery_claim` (`modules/pallets/relayer/src/outbound_request.rs:143-149`) to look up `OutboundRequestDeliveryReward`.

### Finding Description
`IsmpDispatcher::dispatch_request` on `pallet_ismp::Pallet` (`modules/pallets/ismp/src/dispatcher.rs:92-151`) builds the on-chain `PostRequest`/`GetRequest` by copying `dispatch_post.from` / `dispatch_get.from` directly into the request's `from` field, with no check that this bytestring actually corresponds to the calling pallet's own `ModuleId`. Any pallet that exposes an extrinsic wrapping `dispatch_request` (e.g. `pallet-ismp-demo`'s `dispatch_to_evm`, `send_message`-style examples documented in `docs/content/developers/polkadot/dispatching.mdx:57-77`) can let a signed, unprivileged caller choose the `from` bytes of a `DispatchPost`/`DispatchGet` and thereby the `from` field of the resulting `Request::Post`.

`pallet_ismp_relayer`'s outbound-request incentivization treats `request.from` as an authoritative "module_id" identity: `docs/outbound-request-incentivization.md:17` states "the source module is the `from` field on the request, and the relayer never gets to claim under a different module identifier than the one the request was actually dispatched with" — but this assumes only *hyperbridge system pallets* dispatch with meaningful `from` values, not that arbitrary dispatch call-sites are restricted from setting `from` to an allowlisted module's id. `process_outbound_request_delivery_claim` (`modules/pallets/relayer/src/outbound_request.rs:143-149`) derives `module_id` straight from `request.from` and looks up `OutboundRequestDeliveryReward::<T>::get(&module_id)` (`modules/pallets/relayer/src/lib.rs:174-177`) — if any dispatch call-site that end users can invoke lets them set `from` to a governance-allowlisted, rewarded module id (e.g. `b"ismp-ast"`, the `pallet-ismp-demo` PALLET_ID used in the documented Layer-4 runbook, `docs/outbound-request-incentivization.md:321,340`), the request is treated as "hyperbridge-originated and reward-eligible" purely because `request.source == host.host_state_machine()` and it exists in `RequestCommitments`.

This mirrors the ack bug class exactly: a value that should be sanitized/validated against the actual identity of its origin (a filename with embedded escape codes vs. a `from` module identifier) is instead passed through unchanged into a context (`-l`/`-c`/`--show-types` output vs. the reward allowlist lookup) that trusts it at face value.

### Impact Explanation
If any unprivileged-reachable dispatch entrypoint permits the caller to choose `DispatchPost.from`/`DispatchGet.from` matching an allowlisted, reward-bearing `module_id`, an attacker can: (1) dispatch trivial/spam `PostRequest`s from hyperbridge with `from` forged to the rewarded id, (2) self-deliver them to any destination they control (or piggyback on real deliveries), and (3) repeatedly call `claim_outbound_request_delivery_reward` to drain the `TreasuryPalletId` account (`modules/pallets/relayer/src/outbound_request.rs:175-184`) at the configured per-module reward rate, since nothing in the claim pipeline verifies that the dispatching call-site is the legitimate owner of that `module_id`. This is unbacked extraction of treasury funds — a concrete theft-of-funds impact.

### Likelihood Explanation
Likelihood is **conditional and unverified**: the audited codebase snapshot only shows system pallets (host-executive, intents-coprocessor, token-governor, the relayer pallet itself, `pallet-ismp-demo`) setting `from` to their own fixed `PALLET_ID`/`MODULE_ID` constants before calling `dispatch_request` — I did not find a production (non-demo/non-doc-example) pallet in this snapshot that lets an arbitrary signed extrinsic parameterize `from` freely and is also wired into a runtime with a non-zero `OutboundRequestDeliveryReward` for that id. `pallet-ismp-demo`'s `dispatch_to_evm`/`get_request` do let a signed origin trigger a dispatch with the pallet's fixed `PALLET_ID`, not an attacker-chosen arbitrary `from`, so as shipped this specific instance is not directly exploitable. However, the trust boundary itself — `dispatch_request` never validates `from` against caller identity — is the root cause, and the reward-allowlist design in `docs/outbound-request-incentivization.md` explicitly relies on that unvalidated field being trustworthy. Any future or third-party pallet that forwards a user-suppliable `from` into `dispatch_request` (or reuses `DispatchPost`/`DispatchGet` generically) would immediately become exploitable without any change to pallet-ismp or pallet-ismp-relayer.

### Recommendation
Bind `from` at the dispatcher layer to the calling pallet's own identity rather than accepting caller-supplied bytes: either (a) have `IsmpDispatcher::dispatch_request` derive `from` from the concrete `T::ModuleId`/`PalletId` of the module invoking it instead of trusting the `DispatchPost`/`DispatchGet` struct field, or (b) at minimum, have `pallet_ismp_relayer::process_outbound_request_delivery_claim` cross-check that `request.from` corresponds to a module the runtime's `IsmpRouter`/call-filter actually recognizes as capable of dispatching with that identity, rather than trusting the raw bytes unconditionally.

### Proof of Concept
1. Deploy/imagine a pallet `P` with a signed extrinsic `send(from: Vec<u8>, dest, to, body)` that forwards `from` unchanged into `DispatchPost { from, ... }` and calls `T::IsmpDispatcher::dispatch_request`, mirroring the pattern in `docs/content/developers/polkadot/dispatching.mdx:57-77`.
2. Governance sets `OutboundRequestDeliveryReward[b"ismp-ast"] = REWARD` (as documented in `docs/outbound-request-incentivization.md:340`) for the legitimate `pallet-ismp-demo` module.
3. Attacker calls `P::send(from = b"ismp-ast", dest = <attacker-controlled EVM chain>, to = <attacker contract>, body = "")`, producing a `PostRequest{ source: hyperbridge, from: b"ismp-ast", ... }` recorded in `RequestCommitments` via `modules/pallets/ismp/src/dispatcher.rs:108-151`.
4. Attacker relays/delivers this request to the destination themselves, so `RequestReceipts[commitment]` on the destination records the attacker's own relayer address.
5. Attacker calls `Relayer::claim_outbound_request_delivery_reward` with a valid state proof of that receipt and a matching signature; `process_outbound_request_delivery_claim` (`modules/pallets/relayer/src/outbound_request.rs:119-197`) passes every check (`source == host_state_machine`, commitment known, not yet claimed, `module_id = b"ismp-ast"` has nonzero reward) and pays `REWARD` from the treasury to the attacker.
6. Repeat with new nonces indefinitely to drain the treasury — limited only by the treasury balance, not by any real delivery work performed for the `ismp-ast` module. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

```rust
	fn dispatch_request(
		&self,
		request: DispatchRequest,
		fee: FeeMetadata<T>,
	) -> Result<H256, anyhow::Error> {
		// collect payment for the request
		if fee.fee != Zero::zero() {
			T::Currency::transfer(
				&fee.payer,
				&RELAYER_FEE_ACCOUNT.into_account_truncating(),
				fee.fee,
				Preservation::Expendable,
			)
			.map_err(|err| IsmpError::Custom(format!("Error withdrawing request fees: {err:?}")))?;
		}

		let request = match request {
			DispatchRequest::Get(dispatch_get) => {
				let get = GetRequest {
					source: self.host_state_machine(),
					dest: dispatch_get.dest,
					nonce: self.next_nonce(),
					from: dispatch_get.from,
					keys: dispatch_get.keys,
					height: dispatch_get.height,
					context: dispatch_get.context,
					timeout_timestamp: if dispatch_get.timeout == 0 {
						0
					} else {
						<T::TimestampProvider as UnixTime>::now()
							.as_secs()
							.saturating_add(dispatch_get.timeout)
					},
				};
				Request::Get(get)
			},
			DispatchRequest::Post(dispatch_post) => {
				let post = PostRequest {
					source: self.host_state_machine(),
					dest: dispatch_post.dest,
					nonce: self.next_nonce(),
					from: dispatch_post.from,
					to: dispatch_post.to,
					timeout_timestamp: if dispatch_post.timeout == 0 {
						0
					} else {
						<T::TimestampProvider as UnixTime>::now()
							.as_secs()
							.saturating_add(dispatch_post.timeout)
					},
					body: dispatch_post.body,
				};
				Request::Post(post)
			},
		};

		let commitment = Pallet::<T>::dispatch_request(request, fee)?;

		Ok(commitment)
	}
```

```rust
	pub fn process_outbound_request_delivery_claim(
		claim: OutboundRequestDeliveryClaim,
	) -> DispatchResult {
		let OutboundRequestDeliveryClaim { request, state_proof, payee, signature } = claim;
		let destination = state_proof.height.id.state_id;

		let commitment = hash_request::<<T as Config>::IsmpHost>(&Request::Post(request.clone()));

		let host = <T as Config>::IsmpHost::default();
		ensure!(
			request.source == host.host_state_machine(),
			Error::<T>::OutboundRequestSourceNotHyperbridge,
		);

		ensure!(
			RequestCommitments::<T>::get(commitment).is_some(),
			Error::<T>::OutboundRequestNotKnown,
		);

		ensure!(
			!OutboundRequestsClaimed::<T>::contains_key(commitment),
			Error::<T>::OutboundRequestAlreadyClaimed,
		);

		let module_id: BoundedVec<u8, ModuleIdBound> = request
			.from
			.clone()
			.try_into()
			.map_err(|_| Error::<T>::OutboundRequestModuleIdTooLong)?;
		let reward = OutboundRequestDeliveryReward::<T>::get(&module_id);
		ensure!(reward > BalanceOf::<T>::default(), Error::<T>::OutboundRequestNoRewardConfigured);

		ensure!(destination == request.dest, Error::<T>::MismatchedStateMachine);

		let state_machine = ismp::handlers::validate_state_machine(&host, state_proof.height)
			.map_err(|_| Error::<T>::OutboundDestinationStateNotKnown)?;
		let receipt_key = state_machine
			.receipts_state_trie_key(vec![commitment])
			.into_iter()
			.next()
			.ok_or(Error::<T>::OutboundRequestUnsupportedDestination)?;
		let proof_results =
			Self::verify_withdrawal_proof(&*state_machine, &state_proof, vec![receipt_key.clone()])
				.map_err(|_| Error::<T>::OutboundDestinationStateNotKnown)?;
		let raw = proof_results
			.get(&receipt_key)
			.cloned()
			.flatten()
			.ok_or(Error::<T>::OutboundDeliveryNotProven)?;

		let delivered_by = Self::decode_receipt_relayer(destination, &raw)?;

		let msg = outbound_request_delivery_message(commitment, destination, payee);
		let recovered = signature.verify(&msg, None).map_err(|_| Error::<T>::InvalidSignature)?;
		ensure!(recovered == delivered_by, Error::<T>::OutboundRequestSignerMismatch);

		let treasury: T::AccountId =
			<T as Config>::TreasuryPalletId::get().into_account_truncating();
		let payee_account: T::AccountId = payee.into();
		<<T as pallet_ismp::Config>::Currency as Mutate<T::AccountId>>::transfer(
			&treasury,
			&payee_account,
			reward,
			Preservation::Preserve,
		)
		.map_err(|_| Error::<T>::OutboundRequestRewardTransferFailed)?;

		OutboundRequestsClaimed::<T>::insert(commitment, ());

		Self::deposit_event(Event::OutboundRequestDeliveryRewarded {
			commitment,
			state_machine: destination,
			module_id,
			relayer: payee_account,
			amount: reward,
		});

		Ok(())
	}
```

**File:** docs/outbound-request-incentivization.md (L15-21)
```markdown
The issue creator's preferred shape ([comment 4428807013](https://github.com/polytope-labs/hyperbridge/issues/532#issuecomment-4428807013)): use `pallet-relayer` to pay BRIDGE to whoever proves they delivered a hyperbridge-originated request. The messaging task in the tesseract relayer submits the claim.

Not every pallet on hyperbridge that dispatches a request is in scope. `pallet_ismp::child_trie::RequestCommitments` ends up holding commitments for every successful dispatch via `IsmpDispatcher`, which includes both the system messages we want to incentivize (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path, future modules like bandwidth) and any other pallet that ends up dispatching from hyperbridge. The reward storage is therefore keyed by `source_module_id` and only modules with a non-zero reward are eligible. The `module_id` is the `from` field on the `PostRequest`, which each pallet sets to its unique module identifier. A module with zero reward is treated as not on the allowlist and rejected before any state proof verification runs.

This is structurally identical to the existing `claim_outbound_consensus_delivery_reward` (see `modules/pallets/relayer/src/outbound_consensus.rs`) on the consensus side. The request claim lives in its own `modules/pallets/relayer/src/outbound_request.rs` module that mirrors it: swap "consensus rotation delivered" for "request delivered," key the reward storage by `module_id`, and have the relayer ship the full `PostRequest` in the claim so the pallet can hash it on chain.

No changes to pallet-hyperbridge or to any of the system-message dispatch sites. The reward is decoupled from the dispatch path and paid out at claim time against a destination state proof.
```
