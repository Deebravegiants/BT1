### Title
Webhook `shop` domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw HTTP body, while the `shop` (tenant) identifier is read from a separate, unsigned HTTP header. An attacker who can obtain one valid `(body, hmac)` pair for any shop they control can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a victim shop, and the signature check will still pass.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`hmac` is likewise derived solely from a header value alongside the body, and the class's `shop` accessor pulls straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` (used to authenticate the webhook via `VerifiableQuery#to_signable_string` and `#hmac`) therefore only proves that the *body bytes* were signed by Shopify with the app's `client_secret` — it proves nothing about which shop the header claims to be from: [3](#0-2) 

This breaks the identity binding: `shop-header == tenant-that-signed-the-body` is never checked. The HMAC only certifies "Shopify signed this JSON payload," not "for the shop whose domain is in this HTTP header." Any HTTP client can independently set the `X-Shopify-Shop-Domain` header on a request to the app's webhook receiver.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who installs the app on their own store (Shop A) will receive genuine, correctly-HMAC'd webhook deliveries for Shop A. If the attacker captures one such `(raw_body, hmac)` pair and replays it against the app's public webhook endpoint with the `shop-domain` header changed to Shop B (a victim shop), the app — trusting `Request#shop` to select which tenant's session/data the payload applies to — will process Shop A's data as if it belongs to Shop B, or vice versa. Depending on how the host app keys per-shop state off `Request#shop` (a documented, intended use of this accessor), this can lead to cross-tenant data being attributed to the wrong merchant, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on a shop they control (a normal, permission-free action in the Shopify app ecosystem) can harvest a valid signed webhook body/HMAC pair for that shop. The webhook receiving endpoint is by definition a public HTTP endpoint (Shopify itself must reach it unauthenticated apart from the HMAC), so replaying a captured request with a modified header requires no credentials, no TLS interception, and no access to `client_secret`.

### Recommendation
Bind the shop identity into the signed material, or verify it out-of-band: e.g., include the shop domain in `to_signable_string` so it is covered by the HMAC, or cross-check `Request#shop` against a shop that is independently known to be authorized for the given `webhook_id`/topic before trusting it for tenant-scoped processing. At minimum, document clearly that `Request#shop` is unauthenticated and must not be used to select a tenant/session without additional verification.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: headers (`X-Shopify-Hmac-Sha256: <hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`) and the exact raw JSON body.
2. Replay the identical raw body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. In `ShopifyAPI::Webhooks::Request.new`, `hmac_valid?`/`HmacValidator.validate` recomputes the HMAC over `@raw_body` only (per `to_signable_string`), which still matches the supplied `X-Shopify-Hmac-Sha256` — the check passes.
4. `Request#shop` now returns `victim.myshopify.com`, so any handler in the host application keyed on `request.shop` processes attacker-supplied data under the victim shop's identity.
