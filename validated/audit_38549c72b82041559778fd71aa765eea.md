## Finding

### Title
Webhook HMAC Does Not Bind the `shop-domain` Header, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw HTTP body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken from HTTP headers — are never included in the signed content, yet they are trusted and forwarded to the app's handler as the tenant-identifying `WebhookMetadata`. This breaks the intended binding: `hmac_signed_bytes == raw_body` while `attributed_tenant == request.shop` (an unauthenticated header), so `hmac_signed_bytes ⊉ attributed_tenant`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., only the body) and then hands `request.shop` (and the other unauthenticated header fields) straight to the registered handler as trusted tenant metadata: [3](#0-2) 

`HmacValidator.validate` in turn only verifies `verifiable_query.to_signable_string` (the raw body for webhooks) against `Context.api_secret_key`: [4](#0-3) 

Because the signature never covers the `shop-domain` (or `topic`/`webhook-id`) header, any party who has ever received one legitimate, validly-signed webhook body (e.g. by installing the app on their own store and capturing an `orders/create` webhook and its `X-Shopify-Hmac-Sha256` value) can resend the exact same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value naming a different, victim shop. `HmacValidator.validate` still returns `true` because the body/HMAC pair is untouched, and `Registry.process` forwards `WebhookMetadata.new(... shop: request.shop ...)` — now the victim's domain — to the app's handler.

The identity binding that is expected to hold is:
```
hmac_verified(raw_body) == true  ⇒  shop_in_header is authentic
```
but the actual binding implemented is:
```
hmac_verified(raw_body) == true  ⇏  shop_in_header is authentic
```
since `shop_in_header` is outside the HMAC-signed byte range entirely.

### Impact Explanation
Any app that relies on `WebhookMetadata#shop` (or `Request#shop`) from this gem to determine which merchant/tenant a webhook payload belongs to — the documented and expected use per `docs/usage/webhooks.md` — can be made to attribute a payload it authenticated as "real" (in the sense that the HMAC is genuinely valid) to the wrong shop. This is a cross-tenant confusion vulnerability: data intended for/about one merchant can be filed, stored, or acted upon under another merchant's identity purely by an attacker who controls the header value of an otherwise-legitimate request.

### Likelihood Explanation
The only prerequisite is possessing one genuinely valid `(raw_body, hmac)` pair for the app, which any merchant who installs the app on a store they control naturally receives via normal webhook delivery — no access to `api_secret_key` or `client_secret` is required. Replaying the captured request to the same public webhook endpoint with a modified `shop-domain` header is a purely network-level action available to any unprivileged internet user who has ever installed the app.

### Recommendation
Bind the tenant-identifying fields into the signed content, or otherwise cryptographically verify that the `shop-domain` (and `topic`) header matches the shop the HMAC was actually issued for — e.g., by having `to_signable_string` (or a dedicated verification step) incorporate the headers Shopify signs, or by cross-checking `request.shop` against a shop-scoped secret/session rather than trusting the header value implicitly.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and trigger any webhook (e.g. `orders/create`). Capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` — both fully legitimate, produced by Shopify with the app's real secret.
2. Send a new HTTP request to the app's webhook route with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Topic: orders/create` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `B`: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ..., ...)`, even though the payload actually originated from `attacker-shop.myshopify.com`: [6](#0-5)
