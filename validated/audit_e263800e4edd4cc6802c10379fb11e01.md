### Title
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorize redirect from an unsanitized `shop` value, allowing an attacker-controlled redirect target to receive the app's `client_id` and CSRF `state` - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`begin_auth` is documented as requiring "A Shopify domain name in the form `{exampleshop}.myshopify.com`" for its `shop:` parameter, but the method never validates or sanitizes that value against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before using it to build the redirect URL for the OAuth authorize step.

### Finding Description
`begin_auth` takes `shop` directly and passes it into `auth_base_uri(shop)`, which simply does `"https://#{shop}/admin"`, then appends the OAuth authorize query string containing `client_id`, `scope`, `redirect_uri`, and `state`: [1](#0-0) [2](#0-1) 

Nowhere in `begin_auth` is `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` invoked, unlike `ClientCredentials.client_credentials`, which does validate the shop before use: [3](#0-2) 

`ShopValidator` exists specifically to enforce that a shop value resolves to one of the trusted Shopify domains (`myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, `shopify.com`) before it is used to build any outbound request/redirect: [4](#0-3) 

Because `begin_auth` skips this check, if the host application passes through an unvalidated `shop` value (which is exactly the documented pattern — reading `shop` from a request header/param before calling `begin_auth`), the resulting `auth_route` can point at an attacker-controlled host instead of a real Shopify shop domain.

The identity binding broken here is: **the domain that receives the OAuth authorize redirect (and therefore the app's `client_id`, requested `scope`, and CSRF `state`) should equal a domain the gem has verified is a Shopify (`myshopify.com`/trusted) domain** — but the actual code allows `redirect target == arbitrary attacker-chosen string`. In `validate_auth_callback`, the same unsanitized `auth_query.shop` is later used to build the null session's `shop`, which becomes the target host (`https://#{session.shop}`) for the `POST /admin/oauth/access_token` request that carries `client_secret` in the body: [5](#0-4) [6](#0-5) 

While the callback path is gated by `HmacValidator.validate` (which requires a valid HMAC over `code, host, shop, state, timestamp` computed with `api_secret_key`) — so an attacker cannot forge a callback for an arbitrary `shop` they don't legitimately control — the `begin_auth` path has **no such gate at all**. It runs before any HMAC is available, and is the entry point most likely to receive attacker-influenced input directly from the request (e.g. a `shop` query/header parameter), per the gem's own documented usage example that pulls `shop` from `request.headers["Shop"]`.

### Impact Explanation
An attacker who can influence the `shop` value passed into `begin_auth` (a normal login-route parameter in the documented integration pattern) can cause the merchant's browser to be redirected to `https://<attacker-domain>/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=...&redirect_uri=<APP_CALLBACK_URL>&state=<CSRF_NONCE>`. This is a "forced OAuth completion" style issue: the attacker's server, masquerading as the OAuth authorize endpoint, can capture the app's `client_id`, the intended `redirect_uri`, and the anti-CSRF `state` nonce (which is also placed in the victim's session cookie), and can itself redirect the victim back to the legitimate `redirect_path` with an attacker-supplied `code`/`shop`/`hmac` combination to attempt to hijack or fixate the session. This matches the "session fixation or forced OAuth completion" High-impact category.

### Likelihood Explanation
Likelihood is moderate: it requires the calling application to pass an unsanitized `shop` value into `begin_auth`, which is explicitly what the gem's own documentation shows (`shop = request.headers["Shop"]`) without any intervening sanitization step, and no sanitization is performed by the library itself despite `ShopValidator` existing precisely for this purpose and being used elsewhere (`ClientCredentials`). Because the gem provides `ShopValidator` and uses it in one OAuth-adjacent flow but omits it in `begin_auth`, this is a genuine internal inconsistency/gap in the library rather than solely a host-app misuse issue.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `ShopifyAPI::Auth::Oauth.begin_auth`, raising `Errors::InvalidShopError` for any `shop` that does not resolve to a trusted Shopify domain, before it is used to construct `auth_base_uri`. This mirrors the existing protection in `ClientCredentials.client_credentials` and ensures the OAuth authorize redirect can never target a non-Shopify host.

### Proof of Concept
1. Host application implements the documented login route: `shop = request.headers["Shop"]; ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")`.
2. Attacker sends `Shop: evil.example.com` (or tricks victim into hitting the login route with that header/param, e.g. via CSRF against the login route).
3. `begin_auth` computes `auth_base_uri("evil.example.com")` → `"https://evil.example.com/admin"` and returns `auth_route = "https://evil.example.com/admin/oauth/authorize?client_id=<APP_KEY>&scope=...&redirect_uri=<CALLBACK_URL>&state=<NONCE>"`.
4. The victim's browser is redirected to the attacker's server, leaking `client_id`, `redirect_uri`, and `state`, and giving the attacker control over what happens next in the flow (e.g., redirecting the victim back to the legitimate callback with attacker-influenced parameters).

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
