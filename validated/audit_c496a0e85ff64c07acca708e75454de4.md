### Title
Malicious `swap_xdr` route executes arbitrary contract calls under the signer's authorization, draining wallet funds beyond the routed amount - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
The swap router executes a caller-supplied packed program whose instruction stream invokes arbitrary token and pool addresses listed in the payload's `assets` registry. The router keeps no allowlist of the addresses it invokes, so any contract the route names runs on the call stack *below the signer's authorization entry*. A malicious venue contract can then call `token.transfer(victim, attacker, amount)` on any token the victim holds; Soroban records that call as a child of the victim's `require_auth` tree, and an honest simulation surfaces it as a signed authorization the victim may approve. This is the on-chain analog of the Paperclip report: an unsanitized user-provided payload causes the server (here, the router under the user's auth) to execute attacker-chosen code that moves assets far beyond the declared input.

### Finding Description
`execute_strategy(env, sender, total_in, swap_xdr)` decodes `swap_xdr` into a `StrategyPayload` and runs `execute::run` (contracts/swap-aggregator/src/lib.rs:250-255). The packed program's 5-byte instruction records carry `idx_a`/`idx_b`/`idx_c` indexes into `assets: Vec<Address>`, and each hop calls the named pool and token contracts via `dispatch_hop`. `Program::decode` validates opcode ranges, registry bounds, and byte layout only — it never checks that the addresses in `assets` are real DEX pools or listed tokens (skills/xoxno-swap-aggregator/payload.md lines 53-66, 74-87; README line 156 in docs/explanation/threat-model.md: "The router calls the pool and token addresses its payload names and keeps no allowlist of them").

The sender's signature is the only authorization (`sender.require_auth()`, then a measured `transfer_amount_measured(token_in, sender → router, total_in)`). The router's own venue pulls use `authorize_as_current_contract` and do not appear in the sender's tree — but a *rogue* hop pool invoked by `dispatch_hop` can issue `token::transfer(victim, attacker, x)` for an unrelated token. In recording mode the host attaches that transfer as a child of the victim's auth entry for `execute_strategy` (or for `swap_collateral`/`multiply`/etc. when composed through the controller), and in enforcing mode it executes if the victim signs the poisoned tree that simulation returned.

The test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates exactly this: a `RogueHopPool` named by the route steals Alice's entire `WALLET_BALANCE` (77,770 units of an unlisted token) when she signs the simulated tree, while delivering the honest `min_out` so every protocol check passes (lines 195-227, 258-268).

### Impact Explanation
Theft of user funds. The stolen amount is the victim's whole wallet balance of arbitrary tokens, unbounded by `total_in`, `min_out`, or the controller's post-swap risk gates — threat-model.md:154-165 confirms "the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it." This applies both to direct `execute_strategy` calls and to every composed controller strategy (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`) that forwards `swap_xdr`.

### Likelihood Explanation
Requires a victim to sign a poisoned authorization tree — the same precondition class as the reference report (a user must load a malicious skill). An attacker publishes a malicious quote/route (the `routeXdr` is opaque packed bytes that wallets and most clients render only as bytes); any off-chain quote source or phishing route can carry it. Every primitive needed (route naming a contract, venue invocation below caller auth, simulation returning the enlarged tree) is exercised by the harness test. No privileged access is needed. Severity Medium-High: high impact, gated on victim signature of a simulation-produced tree they may not inspect — the documented mitigation is entirely client-side ("a client must decode the route it signs and refuse an authorization tree with any other child").

### Recommendation
Bind routes to a venue allowlist: maintain an owner/governance-managed allowlist of pool and token addresses (or venue→allowed-pool registry) and have `dispatch_hop`/`Program::decode` reject any `assets` entry not registered for its opcode's venue. Absent that, treat the auth tree as the security boundary and enforce in the SDK (`verifyRoutePayload`/`verifyRouteBytes` already decode `routeXdr`) a hard check that the simulated authorization tree contains exactly the expected single `token_in.transfer(sender, router, total_in)` child and nothing else, and surface decoded hops to the signer.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

```rust
// RogueHopPool::swap — attacker contract named as the route's hop pool
pub fn swap(env: Env) {
    let (victim, wallet_token, to, amount): (Address, Address, Address, i128) =
        env.storage().instance().get(&symbol_short!("PLAN")).unwrap();
    if amount > 0 {
        token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
    }
}
```

The test signs `swap_collateral(alice, account, usdc, amount, eth, route)` where `route.hop_pool` is the rogue contract; the simulated auth tree gains a `wallet_token.transfer(alice → attacker, WALLET_BALANCE)` child, signing it executes the theft, and `min_out` is still paid so `swap_collateral` succeeds (asserts at lines 224-226 and 265-268).
