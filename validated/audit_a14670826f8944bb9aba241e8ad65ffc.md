### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop-domain`, `topic`, `api-version`, and `webhook-id` HTTP headers are read directly from unauthenticated request headers and passed downstream to webhook handlers as trusted values. This breaks the identity binding `shop attributed to a webhook == shop that the HMAC actually authenticates`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` reads the `X-Shopify-Hmac-Sha256` header: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` verifies that the HMAC over `to_signable_string` (i.e. the body bytes) matches the signature computed with `Context.api_secret_key`: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` — sourced from the `shop-domain` header, which is never included in the signed bytes — to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

Because `shop`, `topic`, `api-version`, and `webhook-id` are plain headers outside the HMAC's scope, anyone who possesses one genuine `(raw_body, hmac)` pair — for example a merchant who has installed the app on their own store and received a real webhook for their own shop — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` still returns `true` because the body bytes are unchanged, yet the app processes the payload under the identity of a different, attacker-chosen tenant. This is a direct instance of "a field acted on but not covered by the HMAC."

### Impact Explanation
This crosses a tenant boundary: an app built on this gem that uses `WebhookMetadata#shop` to key persistence, cache invalidation, or any per-tenant business logic can be made to apply another merchant's genuine webhook payload to a shop of the attacker's choosing, without needing the `client_secret`, an access token, or any privileged account. This matches the "cross-tenant access" Critical-impact category, since the confidentiality/integrity boundary between separate shops is not enforced by the value the gem itself proves authentic.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to already have a legitimate `(body, hmac)` pair for their own shop (trivially obtainable by installing the app on any store), and requires the target app's webhook endpoint to be reachable directly from the internet (the normal deployment model, since Shopify itself posts to it as a public HTTPS URL). No secret material, MITM position, or admin privileges are needed.

### Recommendation
Bind the shop (and other routing metadata) to the signed content rather than trusting unauthenticated headers. Concretely, verify that the `shop-domain` (and ideally `webhook-id`) reported by the header matches the shop encoded in the (already-signed) webhook body, or require callers to independently confirm the `shop-domain` header against a known, previously-registered shop for the given `webhook_id`/`topic` before invoking `handler.handle`, rather than passing header-derived values straight through as authenticated identity.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; capture a real webhook delivery, e.g. `raw_body` = `{"id":123,...}` with header `X-Shopify-Hmac-Sha256: <valid-hmac>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Resend the identical `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the unchanged HMAC: [4](#0-3) 
4. `handler.handle` is invoked with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled webhook content as belonging to a shop the attacker never controls.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
