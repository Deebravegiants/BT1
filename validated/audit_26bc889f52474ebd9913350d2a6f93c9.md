### Title
Webhook `shop` identity is read from an HTTP header that is not covered by the HMAC signature, allowing shop-identity spoofing in verified webhook requests - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` field entirely from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) HTTP header, while the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` is computed solely over the raw request body. The `shop` value is therefore never part of what is cryptographically verified, yet it is passed downstream, unqualified, as the authenticated tenant identity in `WebhookMetadata`.

### Finding Description
`Utils::HmacValidator.validate` authenticates a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the supplied `hmac`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body — none of the request headers, including the shop domain header, are included in the signed content: [2](#0-1) 

Meanwhile, `shop` is read directly, unauthenticated, from the header: [3](#0-2) 

`Webhooks::Registry.process` validates only the HMAC of the body and then immediately forwards `request.shop` to the handler as the authenticated tenant identifier, with no cross-check that the header value is consistent with anything that was actually signed: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` const with no additional verification, and the gem's own documentation instructs host applications to trust `data.shop` as the shop identity for the webhook, e.g. to enqueue per-shop jobs: [5](#0-4) [6](#0-5) 

This breaks the identity binding: `HMAC-verified-bytes (body) ≠ shop identity relied upon by the caller (header)`. An attacker who controls a legitimate, installed instance of the target app on their own shop (Shop A) can trigger a real webhook delivery with a valid HMAC for Shop A's body, then replay/modify that request against the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim's shop domain (Shop B). Because the header is excluded from the signed content, `Utils::HmacValidator.validate` still returns `true`, and the gem hands the handler a `WebhookMetadata` claiming the body belongs to Shop B, even though only Shop A's HMAC secret usage was actually proven.

### Impact Explanation
This is a cross-tenant identity-confusion vector: the shop-scoping value the gem exposes as "authenticated" (`WebhookMetadata#shop`), and that the docs explicitly tell developers to key persistence/job-enqueueing off of, is not bound to the cryptographic proof of authenticity at all. Any host application that follows the gem's documented pattern (using `data.shop` to select which shop's records to update, as literally shown in the gem's own usage docs) is exposed to writing or exposing attacker-supplied webhook body content under an arbitrary victim shop's identity — a cross-tenant impact reachable by any unprivileged internet user who can install the target app on a shop they control (no leaked credentials, no `api_secret_key`, no privileged account needed).

### Likelihood Explanation
Likelihood is high given the setup cost is low: an attacker only needs a normal, uninstalled/installable merchant shop to receive their own legitimately-signed webhook deliveries, then intercept and replay the request to the app's callback endpoint with a modified shop-domain header. No secret material or elevated access is required — this is exactly the "unprivileged internet user" scenario the analog rules target, and it directly parallels the reported bug class (a value used for critical binding — `reward/start/stop` in the original report, `shop` here — is not actually validated/covered by the mechanism meant to protect it).

### Recommendation
- Bind the shop identity to the signed payload: require the webhook body's own `shop` reference (or otherwise verifiably signed shop identifier) to match the `X-Shopify-Shop-Domain` header before trusting it, or include the header value inside the HMAC-covered signable string.
- At minimum, cross-validate `request.shop` against the shop tied to the webhook subscription/registration record used to route the request, rather than trusting the header value verbatim.
- Add unit test coverage asserting that `Registry.process` rejects (or at least does not silently trust) a request whose `shop-domain` header diverges from any shop-bound content in the verified body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker-shop.myshopify.com` and triggers a real webhook delivery (e.g. `orders/create`) — Shopify signs the raw body with the app's `api_secret_key`, producing a valid `X-Shopify-Hmac-Sha256` header for that exact body.
2. Attacker intercepts this outbound webhook POST (e.g. via a proxy they control, since it is their own shop/webhook endpoint) and replays it to the app's public webhook route, keeping the body and HMAC header untouched but replacing `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. The host app calls:
```ruby
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
)
```
4. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only [2](#0-1)  and succeeds, since the body/HMAC pair is untouched.
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` using the forged header value `victim-shop.myshopify.com` [7](#0-6) , and the app's handler — following the gem's documented pattern of `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [8](#0-7)  — processes the attacker's webhook content as if it belonged to the victim's shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
