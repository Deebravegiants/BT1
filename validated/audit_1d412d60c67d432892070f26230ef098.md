### Title
Route-supplied pool/token addresses let attacker code run beneath the caller's `require_auth` tree and steal wallet tokens — ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
CVE-2021-23154 is command injection: attacker-controlled arguments are concatenated into commands executed under the victim's authority. The lending analog is route injection. Every account strategy that takes a `swap` payload (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `flash_position`) forwards caller-chosen bytes to the swap router. The router treats the payload's `assets` registry — including the `pool` address of every hop — as trusted and `invoke_contract`s it (e.g. `phoenix.rs:25`, `soroswap.rs`, `comet.rs`, `sushi.rs`, `aquarius/pool.rs`). There is no venue/pool allowlist. A pool named by the route can execute arbitrary contract calls, including `token.transfer(victim, attacker, amount)` on any token the victim holds. Under Soroban, that nested call joins the victim's signed authorization tree as a child of the controller entrypoint the victim believes they are signing for.

### Finding Description
- `swap_tokens` authorizes only the input transfer and then calls `router.execute_strategy(&controller, &amount_in, swap)` under the flash guard, checking only measured input/output deltas afterward — never the route's destination contracts [1](#0-0) .
- `dispatch_hop` invokes whichever venue adapter the opcode selects with the hop's payload-named `pool`/`token_in`/`token_out`; each adapter calls `env.invoke_contract(&ctx.hop.pool, "swap", …)` with no registry check that `hop.pool` is a real DEX pool [2](#0-1) .
- When the caller is an EOA using `execute_strategy` directly, `sender.require_auth()` places every nested call under the sender's auth entry; when the caller goes through the controller, the victim signs `swap_collateral(account_id, token_in, amount, token_out, route)` and a rogue pool's `token.transfer(victim, attacker, x)` is recorded as a child of that root.
- The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves both halves: simulation attaches the theft transfer under Alice's `swap_collateral` entry (lines 194-227), and in enforcing mode the signed "poisoned" tree executes the theft — Alice's wallet balance of an unlisted token goes to 0 and the attacker receives it (lines 258-268). The threat model itself states the router "keeps no allowlist" and that a route "can put third-party code on the call stack below the caller's authorization … the loss is then the caller's wallet" [3](#0-2) .

### Impact Explanation
Theft of user funds, bounded only by the victim's wallet, not by the routed amount or by `min_out`. The rogue pool can drain every token the victim holds (as the test demonstrates: `WALLET_BALANCE` of a token the protocol never listed is moved to the attacker) while still returning a fair swap output so all controller gates — positive measured output, `RouterOverspend`, final health — pass. Neither the payload minimum nor the final risk gate bounds the loss.

### Likelihood Explanation
Any unprivileged address can craft a route through `swap_collateral`/`swap_debt`/`multiply`/`repay_debt_with_collateral` or direct `execute_strategy`. Exploitation requires the victim to sign an authorization tree containing the extra child entry. That is a realistic precondition: wallets render the top-level invocation, clients that sign the simulator-returned tree verbatim (the documented integration path produces exactly that tree) authorize the theft. Severity is High: deterministic theft of arbitrary wallet balances with a normal-looking signature.

### Recommendation
On-chain defense: maintain a governance-managed allowlist of pool addresses per venue in the swap-aggregator (analogous to the existing Blend-pool approval list used by `migrate_from_blend`), and have `dispatch_hop`/`HopContext::new` reject any `hop.pool` not on it. Until then, the router's per-hop `token_in` measurement and the controller's measured-output check do nothing against pool code that spends the *caller's* tokens rather than the router's. Client-side, wallets/SDKs must decode the route and refuse any auth tree whose children differ from the single expected `token_in.transfer`.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is a working PoC: `RogueHopPool.swap` calls `token::Client::transfer(&victim, &to, &amount)` (lines 62-71); `UnlistedPoolRouter.execute_strategy` invokes `env.invoke_contract(&route.hop_pool, "swap", …)` exactly as the real adapters do (line 44). The enforced-mode test shows the honest root-only tree makes the host reject the transfer (`Unauthorized function call for address`), while signing the simulation-produced tree — which contains the theft as a child — executes it, leaving Alice at 0 and the attacker with `WALLET_BALANCE`.
