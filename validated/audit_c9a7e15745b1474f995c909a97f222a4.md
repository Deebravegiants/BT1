### Title
Native token overpayment for solver fees is permanently trapped in the Tron `IntentGatewayV2` because `placeOrder` never refunds unspent `msg.value` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron variant of `IntentGatewayV2`, `placeOrder` accepts native token (`msg.value`) both for order inputs and, if present, for solver/relayer fees (`order.fees`). When fees are paid in native token, the function swaps the entire remaining `msgValue` — not just the amount required — via Uniswap `swapETHForExactTokens`, and then, unlike the canonical EVM implementation, never captures the swap's refunded excess nor returns any leftover native balance to the caller. Any native overpayment supplied by the user is left stranded inside the contract, effectively over-charging the user, which is the same root-cause bug class as the reported `LMPVaultRouterBase` issue (user pays more native/ERC20 value than the operation actually consumes, with no path to recover the surplus).

### Finding Description
`placeOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol` computes `msgValue = msg.value` and consumes it for native-token order inputs and, if `order.fees > 0`, swaps native for the fee token: [1](#0-0) 

The swap call forwards the **entire remaining** `msgValue` to `swapETHForExactTokens{value: msgValue}(order.fees, ...)` instead of only the amount required. Uniswap V2's `swapETHForExactTokens` internally refunds any unused ETH to `msg.sender` of that call — which is the `IntentGatewayV2` contract itself, not the original user — so any surplus lands in the gateway's own balance rather than back with the user. The function then emits `OrderPlaced` and returns, with **no** subsequent step that computes leftover `msgValue` or sends it back to `msg.sender`.

This is inconsistent with the canonical (non-Tron) implementation in `evm/src/apps/IntentGatewayV2.sol`, which explicitly tracks the swap's actual spend (`amounts[0]`) to decrement `msgValue`, and then explicitly refunds any unspent native token to the user at the end of `placeOrder`: [2](#0-1) 

The Tron contract has no equivalent refund path anywhere in `placeOrder`, so once a user supplies more native token than is strictly required for their order inputs plus the exact fee-swap cost, that excess is permanently retained by the contract with no mechanism for the user to reclaim it.

### Impact Explanation
Any user placing a cross-chain or same-chain order on the Tron `IntentGatewayV2` who pays the solver fee in native token and supplies `msg.value` that is not the exact minimal amount (which is normal, since callers typically add slippage buffer or round up their native fee quote, similar to how the SDK's `nativeValue` quoting works) will have the surplus captured by the contract instead of refunded. This is a direct loss of user funds analogous to the reported double-charge: users end up paying more than the operation they intended to purchase, and cannot recover the difference through any user-facing function in this contract.

### Likelihood Explanation
This is triggered on the ordinary, unprivileged `placeOrder` call path used by any end user or the SDK to submit an intent order — no special privileges or attacker setup required. It will occur whenever `order.fees > 0` is paid in native token and the caller's `msg.value` exceeds the exact amount consumed by input escrow plus the exact fee-swap output — a very common scenario given fee quoting includes buffer/slippage and native inputs are supplied as round transaction values.

### Recommendation
Mirror the canonical `evm/src/apps/IntentGatewayV2.sol` logic in the Tron contract: capture the actual amount spent by `swapETHForExactTokens` (its return value) to decrement `msgValue` precisely, and add an explicit refund of any remaining `msgValue` to `msg.sender` at the end of `placeOrder`.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with one native-token input of `X` and `order.fees > 0`, paying fees in native token.
2. User sets `msg.value = X + feeBudget`, where `feeBudget` is a native-fee estimate that includes reasonable slippage buffer above the exact amount the Uniswap swap will consume.
3. Inside `placeOrder`, `msgValue` is reduced by `X` for the input leg, then the fee branch calls `swapETHForExactTokens{value: msgValue}(order.fees, ...)`, spending only what's needed to obtain `order.fees` fee tokens; the router refunds the unspent portion to `address(this)` (the gateway contract), not the user.
4. `placeOrder` returns without ever checking or refunding leftover `msgValue`; `address(this).balance` permanently retains the surplus, and there is no user-callable withdrawal function for this stranded native balance, matching `_orders`/escrow accounting which only tracks `X` and `order.fees`, not the surplus.
