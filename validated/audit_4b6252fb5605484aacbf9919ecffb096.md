### Title
Webhook `shop` identity is trusted from an unauthenticated header field not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then separately reads the tenant identity (`shop`) from an HTTP header that is never included in that signature computation. Because the same `api_secret_key` is shared across every shop that installs the app, any party who can obtain one validly-signed webhook body/HMAC pair (e.g., from their own store) can splice in an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header value and have the library treat the forged request as authentic for a victim shop.

### Finding Description
`Registry.process` performs exactly one authentication check before dispatching to the app's handler: [1](#0-0) 

That check is `Utils::HmacValidator.validate(request)`, which computes an HMAC over `request.to_signable_string` (the raw body only) and compares it to the value taken from the `hmac-sha256` header: [2](#0-1) 

`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `shop` is read straight from an untrusted header, entirely outside the signed material: [3](#0-2) [4](#0-3) 

After a successful HMAC check, `Registry.process` builds `WebhookMetadata` using this unauthenticated `request.shop` value and hands it directly to the app-defined handler as the tenant identifier: [5](#0-4) [6](#0-5) 

This is the same bug class as the reported pool exploit: an access-control/identity decision (`overrideLock` in the report; here, "which shop does this webhook belong to") is derived from a user-/attacker-influenced field (`owner_address` in the report; here, the `shop-domain` header) instead of from the value that was actually authenticated (the signed message contents). The binding the library implicitly promises but fails to enforce is:

`hmac_verified(raw_body) == true` should imply `shop_header is bound to raw_body`

but in fact `shop` and `hmac` are computed from disjoint parts of the request, so the equality does not hold — HMAC validity says nothing about which shop the header claims to be from.

### Impact Explanation
Because `Context.api_secret_key` is the single app-wide client secret (not a per-shop secret), any merchant who installs the app can trigger webhooks against their own shop, capture a valid `(raw_body, hmac)` pair, and replay it to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop's domain. The library will validate the HMAC successfully (it only checks the body) and will pass the attacker-controlled `shop` value through to the handler's `WebhookMetadata#shop`. Any app logic that uses this trusted-looking `shop` field to select the tenant record, session, or database row to update will operate on the wrong tenant — a cross-tenant data confusion/injection primitive, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires possession of an app installation on any shop (an unprivileged, standard capability for anyone who can install a public/dev Shopify app) and the ability to capture and replay one legitimate webhook's raw body with a modified header — no access to the `api_secret_key`, access tokens, or the target shop is required. This is a low-effort, deterministic bypass rather than a theoretical or best-practice issue.

### Recommendation
Bind the tenant identity to the authenticated payload instead of an independent header:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the HMAC-signed material (`to_signable_string`) so any tampering with `shop` invalidates the signature, or
- If Shopify's webhook HMAC scheme is fixed to body-only (as documented by Shopify), have `Registry.process` cross-check the `shop` header against an app-side registry of expected/currently-installed shop domains (or bind webhook secrets per-shop where supported) before constructing `WebhookMetadata`, rather than passing it through unchecked.
- At minimum, document explicitly that `WebhookMetadata#shop` is unauthenticated and must not be trusted for authorization decisions, and provide a supported mechanism for verifying shop identity against session storage before acting on it.

### Proof of Concept
1. Install the target app on an attacker-controlled shop, `attacker.myshopify.com`.
2. Trigger any webhook (e.g., `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header — this HMAC is valid because it is computed with the app-wide `api_secret_key` over the body only, per `HmacValidator.validate_signature`: [7](#0-6) 
3. Replay the captured body and HMAC to the app's webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes (body/HMAC untouched), then builds `WebhookMetadata.new(... shop: request.shop ...)` using the forged `victim.myshopify.com` value, and invokes the app's handler as if the data legitimately belongs to the victim shop.           raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
