### Title
Escrow funds can be permanently frozen when cross-chain order state is finalized before settlement delivery is guaranteed - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentGatewayV2`/`ExtrinsicIntents` finalizes an order's `_filled[commitment]` state on one chain *before* the corresponding cross-chain settlement message (`RedeemEscrow` / `RefundEscrow`) is confirmed delivered, and dispatches that message with `timeout: 0` (never expires) and no `onPostRequestTimeout` fallback. If the delivery route becomes permanently unable to deliver messages (e.g. the destination's consensus client is frozen via `freeze_client`, which per the ISMP consensus spec "cannot be unfrozen" and requires a brand-new client), the escrowed input tokens on the source chain become permanently unrecoverable — exactly the "irreversible state change before completion is guaranteed, funds locked" pattern described in the M-18 report for `Vault.blacklistProtocol()`.

### Finding Description
In `_fillCrossChain` (solver fill) and `_cancelFromDest` (user/relayer-initiated cancel), the contract commits to a terminal local state change and only afterward dispatches the cross-chain message that actually releases the escrowed funds: [1](#0-0) [2](#0-1) 

Both routes call `_post`, which dispatches with `timeout: 0`: [3](#0-2) 

`timeout: 0` means the ISMP message never expires, so there is no timeout-triggered refund path. A grep across the intents app code confirms there is no `onPostRequestTimeout`/`onGetTimeout` handler implemented anywhere in `ExtrinsicIntents.sol` or `IntentGatewayV2.sol` — the only occurrences of timeout-handling logic in `evm/src/apps/**` are in the unrelated `BridgeToken.sol`. This means once the state-changing side (`_filled[commitment] = ...`) has executed, the only way funds are ever released is via a successful delivery of `onAccept`/`onGetResponse` on the counterparty chain.

Delivery, however, depends on the consensus client for that route staying alive. The protocol documentation for `freeze_client` explicitly states that a frozen consensus client can never process new requests or responses again, and cannot be unfrozen — a brand new client must be initialized instead: [4](#0-3) 

The same permanent-freeze semantics are documented for the on-chain `IsmpHost`/consensus flow: [5](#0-4) 

Once such a freeze occurs on the route that a pending `RedeemEscrow`/`RefundEscrow`/cancel-GET message depends on, the message can never be delivered again. Because the local, terminal state change (`_filled[commitment]`) already occurred on one side, there is no re-entry point to retry via a different route, and no timeout ever fires to trigger an alternate refund — the escrowed tokens on the source chain (for a fill or destination-initiated cancel) or the query context (for a source-initiated cancel) are permanently stranded. This mirrors `Vault.blacklistProtocol()` finalizing `currentAllocations[_protocolNum] = 0` and withdrawing before guaranteeing the claim/settlement completed, freezing LP funds that were still owed.

### Impact Explanation
Escrowed user/solver funds in `IntentGatewayV2` can be permanently frozen with no recovery path:
- A solver who fills a cross-chain order (`_fillCrossChain`) is entitled to the escrowed input tokens via `RedeemEscrow`; if the source-chain route later becomes permanently undeliverable, the solver's owed input tokens are locked forever in the gateway.
- A user who cancels from the destination chain (`_cancelFromDest`) has `_filled[commitment]` marked immediately, blocking any future fill and any alternative cancellation route; if the `RefundEscrow` message can never be delivered, the user's escrowed input tokens are frozen forever.

This satisfies the "permanent freezing of funds" and "route unable to deliver messages" acceptance criteria, and is reachable purely through normal solver/user actions (`fillOrder`, `cancelOrder`) — no privileged or malicious actor is required to trigger the loss, only an underlying consensus-client freeze event (a legitimate, documented, permanent state) occurring while a settlement message is in flight.

### Likelihood Explanation
Medium likelihood: consensus-client freezing via `freeze_client` is a designed, permissionless "fisherman" response to a proven byzantine fault, and is explicitly documented as permanent/unrecoverable for that client. Any solver fill or destination-cancel whose settlement message is in-flight at the moment the relevant route's consensus client is frozen will have its funds permanently stuck, since `timeout: 0` and the absence of `onPostRequestTimeout`/`onGetTimeout` handling remove any fallback. The order-of-operations issue (finalizing local state before settlement is guaranteed) is unconditional and present on every cross-chain fill/cancel, so the only condition needed for impact is a route freeze coinciding with a pending message — a scenario the protocol's own consensus-fault-handling design anticipates as a real, expected event.

### Recommendation
- Do not finalize `_filled[commitment]` (or otherwise treat the order as settled) until the cross-chain settlement message is confirmed delivered, or provide a compensating on-chain escape hatch keyed off `IsmpHost` freeze/route-health state.
- Implement `onPostRequestTimeout`/`onGetTimeout` in `ExtrinsicIntents` and set a bounded, non-zero `timeout` for `RedeemEscrow`/`RefundEscrow`/cancel-GET dispatches so a stuck message can eventually trigger a refund of the escrow rather than remaining pending indefinitely.
- Consider an admin/governance-gated emergency withdrawal path for escrow entries whose corresponding settlement message's destination consensus client has been frozen for longer than a configurable grace period, analogous to the M-18 recommendation to perform claiming/settlement accounting before an irreversible state transition and to bound how much value can be left unresolved.

### Proof of Concept
1. User A places a cross-chain order from chain S to chain D; input tokens are escrowed on S.
2. Solver fills the order on D via `fillOrder` → `_fillCrossChain` executes, transferring output tokens to the beneficiary and immediately setting `_filled[commitment] = msg.sender`, then dispatches a `RedeemEscrow` POST with `timeout: 0` back to S (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:164-220`).
3. Before the `RedeemEscrow` message is relayed and delivered to S, a fisherman submits a valid `FraudProofMessage` for S's (or the routing consensus state's) consensus client, causing `freeze_client` to permanently freeze that client (`modules/ismp/core/src/handlers/consensus.rs:124-145`).
4. Per protocol design, the frozen client "can no longer process new consensus messages as well as new requests & responses" and "cannot be unfrozen" — a new client must be initialized from scratch, which does not retroactively unblock the specific pending `RedeemEscrow` commitment's proof path in a way the solver can trigger permissionlessly.
5. Since `timeout: 0` was used and no `onPostRequestTimeout` exists, the solver has no mechanism to reclaim the input tokens escrowed on S; they remain locked in the `IntentGatewayV2` contract indefinitely.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});

/// Freeze a consensus client by providing a valid fraud proof.
pub fn freeze_client<H>(host: &H, msg: FraudProofMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host
		.consensus_client_id(msg.consensus_state_id)
		.ok_or_else(|| Error::Custom("Unknown Consensus State Id".to_string()))?;

	host.is_consensus_client_frozen(msg.consensus_state_id)?;

	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;

	consensus_client.verify_fraud_proof(host, trusted_state, msg.proof_1, msg.proof_2)?;

	host.freeze_consensus_client(msg.consensus_state_id)?;

	host.store_consensus_update_time(msg.consensus_state_id, host.timestamp())?;

	Ok(MessageResult::FrozenClient(msg.consensus_state_id))
}

The `freeze_client` method is used to prove the existence of a consensus fault to an onchain consensus client. This message will be sent by offchain parties, colloquially known as _fishermen_ when they detect the existence of two conflicting views of the network backed by consensus proofs. This may arise from double signing or eclipse attacks. The consensus client after successfully verifying the validity of the conflicting views of the network will go into a frozen state. In this state it can no longer process new consensus messages as well as new requests & responses. Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead.
