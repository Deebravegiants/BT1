## Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC of the raw request body, but the tenant-identifying `shop` value that is handed to the app's webhook handler is read from an HTTP header that is never included in that signature. Because the HMAC secret (`Context.api_secret_key`) is the app's single client secret shared across every shop that installs the app, any merchant who installs the app on their own store can capture one legitimately signed webhook and replay it with a forged `shop-domain` header pointing at a different, victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw request body — it does not include any headers: [2](#0-1) 

The `shop` accessor used downstream, however, is parsed straight from the `shop-domain`/`x-shopify-shop-domain` header, which is completely outside the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC-over-body, then immediately trusts `request.shop` as the tenant identity dispatched to the app's handler: [4](#0-3) 

This breaks the intended identity binding `hmac == HMAC(secret, body ∥ shop)` down to `hmac == HMAC(secret, body)`, i.e. the equality that should hold — *the shop for which the event is authenticated equals the shop the handler acts on* — no longer holds, because `shop` is bytes-parsed from an unauthenticated header rather than bytes verified by the signature.

Since `Context.api_secret_key` is the single client secret for the whole app (identical for every merchant install, not a per-shop secret), a valid `(body, hmac)` pair produced for attacker-controlled Shop A is also a valid `(body, hmac)` pair for any other `shop-domain` header value the attacker chooses to send, including a victim Shop B's domain.

### Impact Explanation
This is a cross-tenant integrity/impersonation issue: an unprivileged internet user who is a legitimate (but malicious) merchant can install the target app on their own store, trigger any webhook topic the app subscribes to (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`), capture the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair, and replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `Registry.process` will accept it as authentic and dispatch it to the handler tagged with the victim's shop, causing the host application to act on another tenant's data/session using attacker-controlled webhook payloads — a cross-tenant access violation.

### Likelihood Explanation
High likelihood: creating an app install to obtain a signed webhook requires no privileges beyond being any Shopify merchant/developer (public dev stores are freely available), and forging an HTTP header on a replayed request is trivial. No access token, `api_secret_key`, or insider access is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the authenticated request (e.g., verify the shop domain against the session/shop associated with the specific webhook subscription id returned by Shopify, not merely trust the header). At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop domain so `HmacValidator.validate` fails if the header is tampered with independently of the body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining a valid webhook delivery, e.g. for `orders/create`:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: `{"id":123,...}`
2. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) body and it matches, so `Registry.process` proceeds: [5](#0-4) 
4. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes attacker-controlled data as if it originated from the victim tenant.
