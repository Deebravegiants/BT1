### Title
Webhook `shop` tenant identifier is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while the `shop` (tenant) identifier used by `Registry.process` to route data to the app's handler is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in the HMAC-verified bytes.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates the webhook using `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` to compute the expected signature [1](#0-0) . `Request#to_signable_string` is defined to return only `@raw_body` [2](#0-1) . The `shop` accessor, by contrast, is read directly from the unauthenticated `shop-domain` header via `shopify_header` [3](#0-2) [4](#0-3) .

After HMAC validation succeeds, `Registry.process` passes `request.shop` straight into `WebhookMetadata`, which is handed to the app's registered handler as the tenant identifier for that webhook payload [1](#0-0) .

This breaks the intended binding: `shop header value == HMAC-authenticated shop`. In reality the equality that holds is only `HMAC == f(raw_body)`; the `shop` field is bytes parsed from a header that were never verified. Any user who can obtain one genuine, validly-signed webhook delivery for their own store (trivial — install the app on any shop and trigger a webhook) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. The signature check still passes (it never inspected the header), yet the handler receives a `WebhookMetadata` claiming the payload belongs to a different, victim shop.

This is analogous to the referenced Panoptic finding's root cause: an identity-binding field (`shop`, akin to “refunder”/“account” identity) is trusted after a check (`delegate`/refund success, here HMAC success) even though the specific field asserting identity was never actually covered by that check.

### Impact Explanation
Any app that keys business logic, data storage, or authorization decisions off of `WebhookMetadata#shop` (as the gem's own documentation instructs apps to do — using `shop` to look up the shop's session/store data) can be made to process attacker-supplied webhook content under the identity of a different, victim shop. This is a cross-tenant data integrity issue: an attacker-controlled webhook body (for topics they control, e.g. `app/uninstalled`, `orders/create`, custom app webhook topics they can trigger on their own store) can be attributed to an arbitrary victim shop domain string, corrupting per-tenant records, triggering unauthorized per-tenant side effects (e.g., app uninstall bookkeeping, order records, GDPR-topic processing) for a shop the attacker does not control.

### Likelihood Explanation
Likelihood is high enough to be practically exploitable: the attacker only needs a legitimate, unprivileged Shopify store with the app installed (or subscription to any public app webhook they can trigger) to obtain a genuine `(raw_body, hmac)` pair, then replay it to the app's public webhook endpoint with a forged `shop-domain` header. No secrets, tokens, or elevated access are required — this crosses the tenant boundary using only unauthenticated header bytes.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind them to the verified payload, so that `Utils::HmacValidator.validate` fails if any of these fields are altered after Shopify's original signing. At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` is not authenticated by `Registry.process` and must be independently reconciled against a shop known to be associated with the webhook subscription (e.g., cross-checked against stored session data) before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) they control the content of.
2. Attacker captures the raw HTTP request Shopify sends to the app's webhook endpoint, including `raw_body`, and the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header value. This HMAC is valid because `HmacValidator.validate` recomputes it purely from `raw_body` [2](#0-1) [5](#0-4) .
3. Attacker replays the exact same `raw_body` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because it only checks `raw_body` against the HMAC [6](#0-5) .
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim.myshopify.com"` and invokes the app's handler, which now processes attacker-controlled content believing it originated from `victim.myshopify.com` [7](#0-6) .
