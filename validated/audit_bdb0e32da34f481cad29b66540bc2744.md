### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are trusted from unauthenticated headers while only the request body is HMAC-verified, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values used to dispatch and attribute the webhook are read directly from HTTP headers that are **not** part of the signed payload [2](#0-1) . This is precisely the M-2 bug class described in the report: a field ("shop") that is acted upon (used to attribute/dispatch the event) is not covered by the cryptographic check ("HMAC"), breaking the intended binding `verified_bytes == attributed_identity`.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns just `@raw_body` [3](#0-2) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the body or to the HMAC signature [4](#0-3) .

`Registry.process` verifies the HMAC and then immediately constructs `WebhookMetadata` using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` taken from those unauthenticated headers, and dispatches it to the topic handler: [1](#0-0) 

Because the HMAC only proves the body bytes were signed by someone possessing `api_secret_key` (i.e., Shopify) — it proves nothing about which shop, topic, or webhook the payload is supposedly for. A merchant who has installed the app on their own store (an unprivileged actor with respect to any *other* tenant) legitimately receives real Shopify-signed webhook deliveries for their own shop, complete with a valid `hmac-sha256` header for that exact body. Since headers are excluded from the signature, that attacker can replay the same body + valid HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`/`shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` still returns `true` (body signature still matches), and the app's handler receives `WebhookMetadata` attributing the (attacker-controlled) body content to the victim shop.

This exactly mirrors the referenced bug class: "a field acted on but not covered by the HMAC." Here the field is the webhook's tenant identity (`shop`), acted upon by every downstream handler that trusts `data.shop` to scope database writes, job dispatch, etc. (as the gem's own documentation example demonstrates: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [5](#0-4) .

### Impact Explanation
This breaks the identity binding `HMAC-verified body == the shop/topic the app attributes the event to`, which is exactly a cross-tenant boundary violation: an attacker who controls one tenant (their own shop, running the same third-party app) can inject arbitrary application-level events (`orders/create`, `products/update`, GDPR-style topics, etc.) into another merchant's tenant data path, since the gem hands the caller-supplied `shop` straight through to the handler without any cryptographic tie to the signed body. Any host application following the gem's own documented pattern (using `data.shop` to scope work) inherits this cross-tenant confusion. This matches the "Critical - cross-tenant access" impact bucket defined in scope.

### Likelihood Explanation
Likelihood is high for any real-world app: the attacker only needs to be a legitimate merchant of the app (no special access, no leaked secrets) to capture a real signed webhook for their own shop and then re-POST it to the app's public webhook endpoint with a modified `shopify-shop-domain` header. No knowledge of `api_secret_key` is required — the attacker reuses a valid signature that Shopify itself computed for their own store's event.

### Recommendation
Bind the tenant/topic identity to the cryptographically verified data instead of trusting the raw headers:
- Include the `shop`, `topic`, and `webhook_id` values in the HMAC-signed payload (or otherwise cryptographically bind them, e.g., by deriving the signable string from headers + body together, mirroring how `AuthQuery#to_signable_string` includes `shop`/`host`/etc. in the OAuth flow) [6](#0-5) .
- At minimum, document and/or enforce that the host application must independently verify that `data.shop` corresponds to a shop with an active, previously-established session/installation before trusting webhook content for that shop, rather than accepting it as authenticated purely because the body HMAC validated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers an event Shopify will webhook for (e.g., updates a product), and captures the legitimate webhook POST, including headers `x-shopify-hmac-sha256: <valid-hmac-for-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: products/update`, and the raw JSON body.
3. Attacker resends the exact same body and the exact same `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` object where `hmac` still matches the (unchanged) body [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the raw body against the secret [8](#0-7) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though the payload never touched or was authorized for that shop [9](#0-8) .

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
