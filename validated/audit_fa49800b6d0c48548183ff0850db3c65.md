## Title
Webhook `shop` (tenant identifier) is read from an unauthenticated header and is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. Because a single app-level `client_secret` (`Context.api_secret_key`) is used to sign webhooks for *every* shop that installs the app, any shop that has installed the app can capture one of its own legitimately-signed `(raw_body, hmac)` pairs and replay it to the app's webhook endpoint while swapping the `shop-domain` header to point at a different (victim) shop. The signature check still passes because the shop identity is never part of the signed payload, letting an attacker inject data attributed to another tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an HTTP header with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only this body-only HMAC, then forwards the unauthenticated `request.shop` value directly to the host app's handler as the tenant key: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm the check is purely `HMAC(secret, raw_body) == received_hmac`, with no shop, topic, or webhook-id bound into the signed string: [4](#0-3) 

The documented integration pattern instructs host apps to trust `data.shop` as the tenant/shop key for routing and persistence (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that this gem's own contract treats the header-derived `shop` as authoritative: [5](#0-4) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`shop_bound_by_signature == shop_used_as_tenant_key` is false — the signature binds only `raw_body`, while `request.shop` (used as the tenant key by `Registry.process`) comes from an attacker-controllable header.

Exploit path:
1. Attacker installs the target app on their own shop (unprivileged, ordinary merchant install — the app's `client_secret` is shared across all installs, this is normal Shopify OAuth design).
2. Attacker triggers (or otherwise obtains) a legitimate webhook delivery for a topic whose body content is attacker-influenced or predictable (e.g. an event they control the payload of, or one with static/generic body content shared across shops for the same topic).
3. Attacker captures the valid `(raw_body, X-Shopify-Hmac-Sha256)` pair Shopify sent them — this pair is valid because it was signed with the app's `client_secret`, which is identical for every shop using the app.
4. Attacker replays the exact `raw_body`/`hmac` to the app's webhook endpoint but substitutes `X-Shopify-Shop-Domain` with a victim shop's domain (also an installer of the same app).
5. `HmacValidator.validate` passes (body/hmac match), `Registry.process` calls the handler with `shop: request.shop` set to the victim's domain, causing the host app to process/persist attacker-controlled data under the victim's tenant.

### Impact Explanation
This is a cross-tenant integrity/access issue: the gem allows a request bearing an arbitrary, unauthenticated shop identifier to pass its only integrity check and be delivered to the handler as if it originated from that shop. Depending on how the host app uses `data.shop` (e.g., to select which tenant's records to create/update, as demonstrated in the gem's own documentation example), this enables cross-tenant data injection/corruption for any app relying on this library's webhook processing exactly as documented.

### Likelihood Explanation
Any entity able to install the target app (a routine, low-privilege action for public apps) can obtain valid `(raw_body, hmac)` pairs signed with the shared `client_secret`, then trivially forge the `shop-domain` header on a raw HTTP POST to the app's webhook route. No access token, `client_secret`, or privileged access is required — only normal app installation and control over one HTTP request's headers.

### Recommendation
Bind the shop identity (and ideally topic/webhook-id) into the value that is cryptographically verified — e.g., require the host app to also verify that `request.shop` corresponds to a session that legitimately installed the app, or extend `to_signable_string`/validation so header-derived tenant fields cannot be swapped independently of the signed body. At minimum, the documentation should explicitly warn that `data.shop` is not covered by the HMAC and must be independently authenticated against known installations before being used as a tenant key.

### Proof of Concept
```ruby
# Attacker owns "attacker.myshopify.com" and has installed the target app.
# They receive a legitimate webhook delivery, e.g. for "app/uninstalled" with a
# static/empty body "{}" (topic content attacker fully controls/predicts).

raw_body = "{}"
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), Context.api_secret_key, raw_body)

# Same (raw_body, hmac) pair is valid for ANY shop using this app, since the
# HMAC covers only raw_body and is signed with the single, app-wide client_secret.
forged_headers = {
  "shopify-topic" => "app/uninstalled",
  "shopify-hmac-sha256" => Base64.encode64(hmac),
  "shopify-shop-domain" => "victim.myshopify.com", # attacker-controlled, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (body/hmac match)
# => handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", ...))
# The host app processes this event as if it legitimately came from victim.myshopify.com.
```
