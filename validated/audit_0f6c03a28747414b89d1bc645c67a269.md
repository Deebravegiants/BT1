### Title
Stale `Account.owner` lets the previous NFT holder keep full spending authority after `position-nft::transfer` - (File: contracts/controller/src/account.rs)

### Summary
The Obot bug class is an authorization bypass: a second authorizer grants access to a resource based on stale/incorrect identity, so knowing the resource ID suffices to act on it. The lending analog lives in the account-ownership check: `create_account_with` stamps `Account.owner` once at mint (`account.rs:64-65`), and `require_owner_or_delegate`/`is_owner_or_delegate` compare the caller against that **stored** address (`account.rs:121`, `account.rs:136`) — not against the live NFT owner that `require_account_owner` reads via `storage::account_owner` (`account.rs:143-147`). After `position-nft::transfer` moves the account to a buyer, the stored owner is never rewritten, so the seller (and its delegates, stored under the stale owner key at `account.rs:126`) retain spending authority over the account they no longer own, while the buyer's owner/delegate calls are checked against the stale list.

### Finding Description
- `Account.owner` is written once at account creation and never resynced to the NFT owner (`contracts/controller/src/account.rs:64-65`).
- `is_owner_or_delegate` returns `true` when `caller == owner` where `owner` is the stale stored field (`account.rs:121`), and delegate lookup is keyed by that same stale `owner` (`account.rs:126`).
- Every value-moving entrypoint — `borrow`, `withdraw`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `multiply`, `flash_position`, `migrate_from_blend` — reaches `require_owner_or_delegate` on the loaded `Account`, per `account.rs:102,106` and the declared INV-AUTH-02 guard in `scripts/permissionless_entrypoints.txt:49-56`.
- Meanwhile `add_delegate`/`remove_delegate`/`renew_account` use `require_account_owner`, which reads the live NFT owner (`account.rs:143-147`) — confirming the codebase itself treats NFT ownership and `Account.owner` as two different authorities that can diverge.

### Impact Explanation
Theft of user funds. A seller lists/transfers an account NFT holding collateral (and optionally debt). Immediately after the sale, the seller calls `controller::borrow` or `controller::withdraw` with their own signature: `caller.require_auth()` passes (it's their address), `caller == account.owner` passes (stale stored owner), and post-pool solvency gates only bound the draw to the account's borrowable equity. The seller extracts the buyer's collateral value as new debt proceeds / withdrawn tokens, leaving the buyer holding an NFT over a drained or maximally levered account. The seller's pre-transfer delegates also remain valid, and the buyer cannot revoke them because `remove_delegate` authenticates the live NFT owner while the grants are keyed under the seller's address.

### Likelihood Explanation
Anyone can buy or receive an account NFT (`transfer`/`transfer_from` are stock permissionless ERC-721 paths) and immediately exploit it in the same ledger sequence as the sale settles. No privileged role, oracle manipulation, or timing edge is required — only knowledge of `account_id`, exactly as the original report required only the MCP server ID. The post-pool risk gates limit extraction to the account's solvency headroom, which is still the full equity a buyer paid for.

### Recommendation
Resolve spending authority against the live NFT owner: `require_owner_or_delegate` should call `storage::account_owner(env, account_id)` (the same source `require_account_owner` uses at `account.rs:145`) instead of trusting `Account.owner`, or `Account.owner` must be resynced on every NFT transfer via a controller-observed hook. Delegate keys should likewise be rebound or cleared on transfer so pre-sale grants cannot follow the stale owner.

### Proof of Concept
1. Alice creates account `A` via `supply` (account_id returned, NFT minted to Alice) and supplies USDC collateral.
2. Alice sells/transfers NFT `A` to Bob via `position-nft::transfer`. `Account.owner` still equals Alice (`account.rs:64-65` — no resync path exists).
3. Alice calls `controller::borrow(caller=alice, account_id=A, hub_asset=USDC, amount=<equity>)`. `alice.require_auth()` passes; `is_owner_or_delegate` hits `caller == owner` on the stale field and returns early (`account.rs:121,136`); solvency check passes against the collateral Bob just bought.
4. Borrowed tokens are disbursed under Alice's authority; Bob's NFT now points at an account whose equity Alice extracted. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

Caveat: I was unable to read `storage::account_owner`/`storage::get_account` definitions to confirm `get_account` does not refresh `Account.owner` from the NFT owner on load — if it does, this finding does not hold. The presence of `require_account_owner` performing a separate live-owner read strongly suggests the stored field can diverge, but a Devin session should verify `contracts/controller/src/storage/account.rs` before treating this as confirmed.

pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}

/// Requires the owner or a registered, active manager delegated by that owner.
pub(crate) fn require_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) {
    if is_owner_or_delegate(env, account_id, caller, owner) {
        return;
    }
    panic_with_error!(env, GenericError::NotAuthorized);
}
