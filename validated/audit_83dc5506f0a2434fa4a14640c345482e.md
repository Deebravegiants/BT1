### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from only the raw request body, while the `shop` value (from the `X-Shopify-Shop-Domain` / `Shopify-Shop-Domain` header) is read independently and is not part of the signed bytes. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop`, passing it to the app's webhook handler as an authenticated tenant identifier.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
The `shop` accessor reads a separate header and is not mixed into that signable string at all: [2](#0-1) 
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(..., verifiable_query.to_signable_string, secret)` and compares it against the `hmac-sha256` header — i.e. it authenticates the body bytes only: [3](#0-2) 
`Registry.process` treats a passing HMAC check as authorization for the entire request, including the header-derived `shop`, and forwards it to the handler: [4](#0-3) 

This breaks the implicit binding the gem's own documentation promises: that `WebhookMetadata#shop` is a value the handler can rely on as authenticated ("The shop domain of the webhook"), because the HMAC never actually covers that byte range. The equality that should hold — `hmac_signed_bytes ⊇ {body, shop}` — instead only holds for `{body}`. Anyone who can obtain one genuinely Shopify-signed webhook delivery (trivial: install the app on any free/dev shop and trigger the subscribed topic) captures a valid `(raw_body, hmac)` pair. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value (e.g., a victim shop's domain) — the HMAC still validates because the header is never part of the signed material.

### Impact Explanation
This crosses the "bytes verified versus bytes parsed" / "field acted on but not covered by the HMAC" boundary explicitly, and results in cross-tenant impact: a webhook payload can be attributed to any shop domain the attacker chooses while still passing this gem's cryptographic check. Downstream app code that uses `data.shop` from `WebhookMetadata` (as the gem's own docs at `docs/usage/webhooks.md` instruct: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) to key database writes, enqueue background jobs, or select per-tenant credentials, will act on forged tenant attribution despite `ShopifyAPI::Errors::InvalidWebhookError` never being raised.

### Likelihood Explanation
High likelihood for any app author who — following the gem's documented pattern — trusts `WebhookMetadata#shop` as authenticated once `Registry.process` doesn't raise. The attacker only needs one legitimately delivered webhook body/HMAC pair (obtainable via any test/dev shop under their own control, no privileged credentials needed) and the ability to send an HTTP request with a modified shop-domain header to the app's public webhook endpoint.

### Recommendation
Include the shop-domain (and ideally topic/api-version/webhook-id) header values in the signable/verified material for webhooks, or otherwise cryptographically bind `shop` to the HMAC before exposing it via `WebhookMetadata`. At minimum, document loudly that `WebhookMetadata#shop` is *not* authenticated by the HMAC check and must be cross-checked by the host application against its own record of installed/authorized shops before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a subscribed webhook topic (e.g. `orders/create`), capturing the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC(secret, B)` per `lib/shopify_api/utils/hmac_validator.rb`).
2. Attacker resends the exact same request to the app's webhook endpoint, keeping `body = B` and `X-Shopify-Hmac-Sha256 = H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb#190` succeeds because it only checks `B` against `H`.
4. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and calls the app's handler, which (per the gem's documented usage) treats `data.shop` as the authenticated tenant and performs a tenant-scoped action (e.g., a background job keyed on `victim-shop.myshopify.com`) using attacker-controlled body content `B`.
