Audit Report

## Title
Legacy Web API trigger handler lets any unauthenticated user hijack another user's pending callback via `MessageID` collision - (File: `core/services/gateway/handlers/capabilities/handler.go`)

## Summary
`HandleLegacyUserMessage` stores each pending callback in the shared `h.savedCallbacks` map keyed solely by the caller-supplied `msg.Body.MessageID`, without checking whether that key is already occupied by another in-flight request. Because `MessageID` is fully attacker-chosen (propagated verbatim from the JSON-RPC request `ID` via `ValidatedMessageFromReq`/`gateway.ProcessRequest`) and is never bound to the sender's identity, any caller able to sign their own gateway message can pick a `MessageID` that collides with a victim's still-pending request and silently overwrite the victim's callback reference.

## Finding Description
`core/services/gateway/gateway.go`'s `ProcessRequest` decodes the raw JSON-RPC request, validates the legacy `api.Message` (`msg.Validate()`, which only checks signature well-formedness and extracts `Body.Sender` from the signature — it does not check MessageID uniqueness or bind it to any prior session), and calls `h.HandleLegacyUserMessage(ctx, msg, callback)`. [1](#0-0) 

In `HandleLegacyUserMessage`, after building the outbound request, the handler unconditionally inserts into the shared map:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [2](#0-1) 

There is no `if _, exists := h.savedCallbacks[msg.Body.MessageID]; exists { return error }` guard, unlike the duplicate-ID protection pattern present elsewhere in the codebase (e.g. vault handler and `request.NewServerRequest`'s "Send duplicate message" rejection). [3](#0-2) 

`msg.Body.MessageID` is taken directly from the JSON-RPC request `ID` field with no server-side uniqueness enforcement:
```go
m.Body.Method = req.Method
m.Body.MessageID = req.ID
err = m.Validate()
``` [4](#0-3) 

`Validate()` only checks length/format of `MessageID` and extracts the signer from the signature — it does not tie `MessageID` to `Body.Sender` or check for collisions against other pending requests: [5](#0-4) 

On the response path, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `msg.Body.MessageID`, with no verification that the responding entry corresponds to the same sender that originally registered it:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageID]
delete(h.savedCallbacks, msg.Body.MessageID)
h.mu.Unlock()
``` [6](#0-5) 

The only sender-identity check in the whole flow is `msg.Body.Sender != nodeAddr` in `HandleNodeMessage`, which verifies the *node*'s identity, not the original *user* who registered the callback — it does nothing to prevent a second unrelated user request from overwriting the first user's map entry. [7](#0-6) 

Note that a legacy message must carry a valid signature to pass `Validate()`, but this signature can be generated by any arbitrary keypair the caller controls — it proves nothing about privilege/authorization, only that *some* self-chosen key signed the payload. This does not prevent the described collision, since nothing binds `MessageID` uniqueness to `Body.Sender`.

## Impact Explanation
An attacker who can predict or learn a victim's chosen `MessageID` (client-supplied, arbitrary string up to 200 chars per the length check in `gateway.go`) can overwrite the victim's `savedCallbacks` entry before the DON responds. When the DON later replies with that shared `MessageID`, the response is delivered to whichever callback currently occupies the slot, causing the victim's original HTTP call to hang until `RequestTimeoutError` and potentially delivering a response tied to the victim's triggered work to the attacker instead. This maps to the "cross-user response corruption" in-scope impact class for the gateway's request/response correlation layer.

## Likelihood Explanation
This requires the attacker to know or guess the exact `MessageID` string used by a concurrent victim request within the callback lifetime window (`defaultCallbackMaxAgeSec` = 120s). Exploitability is entirely dependent on client-side `MessageID` generation practices being predictable/low-entropy (e.g., sequential counters, timestamps, or observable/leaked IDs); if IDs are generated as sufficiently random/high-entropy values by clients, collision is effectively infeasible. The root cause — no server-side uniqueness/ownership enforcement on `savedCallbacks` — is a genuine, reachable gap in the code, independent of collision probability.

## Recommendation
Bind `savedCallbacks` entries to request ownership rather than solely to the client-chosen `MessageID`:
- Reject registration if `msg.Body.MessageID` already exists in `savedCallbacks` (return an error instead of silently overwriting), mirroring the duplicate-ID rejection pattern used elsewhere in the codebase (e.g., `request.NewServerRequest`).
- Alternatively, key `savedCallbacks` by a server-generated composite value (e.g., a value derived from `Body.Sender` + `MessageID`, or a gateway-generated correlation ID) so that two different senders can never collide on the same map key.

## Proof of Concept
1. Victim signs and sends a legacy `web_api_trigger` gateway request with `MessageID = "X"` (their own valid signature over their own message body); `HandleLegacyUserMessage` inserts `savedCallbacks["X"]` and forwards the request to DON members.
2. Before the DON responds, an attacker — using their own independently generated signing key — signs and sends a `web_api_trigger` request also using `MessageID = "X"`. `HandleLegacyUserMessage` executes `h.savedCallbacks["X"] = &savedCallback{...attacker's callback...}`, overwriting the victim's entry with no collision check.
3. When a DON node responds with `MessageID = "X"`, `handleWebAPITriggerMessage` retrieves and deletes `savedCallbacks["X"]`, now holding the attacker's callback, and delivers the response there — the victim's original HTTP call receives nothing and times out via `api.RequestTimeoutError` in `gateway.ProcessRequest`.
- A Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go` can drive this directly: call `HandleLegacyUserMessage` twice with distinct `Callback` instances but identical `msg.Body.MessageID`, then assert that `h.savedCallbacks[id]` references the second (attacker) callback, and that invoking `handleWebAPITriggerMessage` with that ID resolves to the second callback rather than erroring or preserving the first.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
