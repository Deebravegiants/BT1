### Title
Webhook Shop Attribution Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are taken from unauthenticated HTTP headers. `Registry.process` validates only the body's HMAC and then hands the header-derived `shop` straight to the app's handler, so the shop identity that ends up driving the app's tenant-scoped logic is never bound to the value that was actually signed.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from request headers without being part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC of the body via `Utils::HmacValidator.validate(request)` and then constructs `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

`HmacValidator.validate_signature` compares `verifiable_query.to_signable_string` (the raw body only) against the HMAC, so the header fields are structurally excluded from the integrity check: [4](#0-3) 

The documented handler pattern explicitly keys tenant-scoped work off this unauthenticated `data.shop` value: [5](#0-4) 

This is the same class of bug as the analog cited in the report: a field ("shop") that is acted upon (used to attribute/process the webhook for a specific tenant) is not covered by the HMAC that is meant to authenticate the request. The binding the code should enforce is `hmac_signed_shop == request.shop`, but the actual signed content is `hmac_signed_bytes == raw_body` only, with `request.shop` sourced independently from a header. Because the webhook secret (`api_secret_key`/`client_secret`) is shared across every shop that installs the same app, any unprivileged user who can install the app on their own (e.g. free/dev) store receives real, validly-signed webhooks for that store. They can capture one such `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and other) headers to name a different, victim shop. `Utils::HmacValidator.validate` will still pass because it only checks the body bytes, and the app will process the request as if it originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an attacker with a legitimate installation on their own store can forge webhook events attributed to another merchant's shop, since shop identity is not cryptographically bound to the signature. Depending on what the app's webhook handler does with `data.shop` (e.g., looking up per-shop state, triggering shop-scoped side effects, writing records keyed by shop, as shown in the gem's own documented handler pattern), this enables cross-tenant data confusion/injection — data or events falsely attributed to a shop that never sent them. This matches the "cross-tenant access" criterion for Critical severity.

### Likelihood Explanation
Exploitation requires only an app installation on an attacker-controlled shop (the shared secret is per-app, not per-shop) plus the ability to POST arbitrary headers to the app's public webhook endpoint — both are achievable by an unprivileged internet user with no special credentials, access tokens, or social engineering.

### Recommendation
Include the identifying header fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed content that `to_signable_string` returns (or otherwise cryptographically bind them, e.g. by validating them against a signed/authenticated channel), so a valid HMAC for one shop/topic/body combination cannot be replayed with a different shop or topic header. At minimum, `Registry.process` should not trust `request.shop`/`request.topic` for tenant attribution unless those values are part of what was verified by `HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some `raw_body`.
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only look at the body, so `Utils::HmacValidator.validate` returns `true` (see `lib/shopify_api/utils/hmac_validator.rb` lines 26-31 and `lib/shopify_api/webhooks/request.rb` lines 35-38).
5. `Registry.process` calls the app handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb` lines 188-200), causing the app to process attacker-controlled webhook content as though it belongs to `victim.myshopify.com`.
