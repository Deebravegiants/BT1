### Title
Token-donation invariant break causes unsigned-integer underflow revert in `Router._computeBuy`'s overflow-cap branch, permanently DoSing curve buys - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy`'s overflow-cap branch computes `cappedReserveToken = reserveToken - tokensOut` assuming the invariant `reserveToken > tokenBalance()` always holds. An unprivileged attacker can break that invariant with a plain ERC20 `transfer` of the launched `Token` directly into the `Pair`, inflating `tokenBalance()` past the virtual `reserveToken`. The next buy that is large enough to hit the cap branch then underflows this subtraction and reverts, permanently DoSing `Bonding.buy`/`Zap.buy` for that token — the curve can never be bought into (or graduated) again.

### Finding Description
`Router._computeBuy` caps `tokensOut` at the pair's real balance and back-calculates `amountInUsed`: [1](#0-0) 

This logic assumes `reserveToken` (the virtual reserve fixed at `Pair.mint`) always exceeds `pair.tokenBalance()` (the real, donatable ERC20 balance) — an invariant the test suite calls out explicitly and treats as load-bearing for this exact branch: [2](#0-1) 

But `Pair.tokenBalance()` is a live `IERC20.balanceOf` read with no access control on inbound transfers: [3](#0-2) 

Any holder of the launched `Token` (e.g. the anti-snipe seed buyer, or any trader who bought tokens off the curve) can `Token.transfer(pairAddr, donatedTokens)` directly, inflating `tokenBalance()` past `reserveToken`. The project's own regression tests demonstrate this exact break of the invariant and note it previously caused an underflow/DoS in the sibling function `Bonding.previewLtUntilGraduation`, which was patched with an explicit guard: [4](#0-3) [5](#0-4) 

`Bonding.previewLtUntilGraduation` now explicitly checks `if (realBalance >= reserveToken) return ltUntilThreshold;` before subtracting, guarding exactly this underflow path: [6](#0-5) 

`Router._computeBuy`, however, has **no equivalent guard**. Its only defensive check is `if (cappedReserveToken == 0) revert OverflowCapDegenerate();`, which only fires *after* the subtraction has already been evaluated: [7](#0-6) 

Under Solidity 0.8's checked arithmetic, `reserveToken - tokensOut` with `tokensOut > reserveToken` reverts the whole call rather than wrapping — the exact same underflow class as CVE-2016-10377's `miniflow_extract` (an attacker-controlled value drives a subtraction below zero), except here Solidity's checked math converts it into an unconditional revert instead of a silent OOB/bypass. The practical effect is a permanent inability to reach the code path.

### Impact Explanation
Once the donation has broken the `reserveToken > tokenBalance()` invariant, any buy sized large enough to trigger the cap branch (i.e. any buy that would otherwise fully or near-fully drain the curve) causes `Router.buy` → `Bonding.buy` → `Zap.buy` to revert unconditionally. Because `tokenBalance()` monotonically increases with more donations and cannot be reduced by anyone except through `Router.buy`'s own token-out transfers (which are now unreachable in the cap branch), the affected token's bonding curve is bricked for any cap-triggering buy size — freezing that token's remaining curve-side liquidity and blocking the supply-side graduation trigger (`tokenBalance() == 0` can never be satisfied once inflated by donation, and the USD-trigger-only path may not be reachable for tokens with low LT-pump potential). This is a permanent freezing-of-funds/trading condition reachable by any unprivileged token holder, satisfying the "permanent freezing of trader, creator or LP funds" impact bar.

### Likelihood Explanation
High. The only precondition is holding any nonzero amount of the launched `Token` (trivially obtained via the anti-snipe seed buy or any regular curve buy) and calling a plain `IERC20.transfer` to the `Pair` address — no privileged role, no price manipulation, no timing dependency. The project's own test helper `_stageDonationAttack` in `Zap.t.sol` shows this is a known, reproducible attack primitive already used to break the `realBalance > reserveToken` invariant; it was only patched in `previewLtUntilGraduation`, not in `Router._computeBuy`.

### Recommendation
Add the same defensive guard used in `Bonding.previewLtUntilGraduation` to `Router._computeBuy`: before computing `cappedReserveToken = reserveToken - tokensOut`, check whether `tokensOut >= reserveToken` (i.e., the donation-inflated real balance has exceeded the virtual reserve) and handle it gracefully — e.g., treat the curve as fully drained without back-calculating a capped price, or clamp `tokensOut` to `reserveToken - 1` — instead of allowing the unguarded subtraction to revert the entire buy.

### Proof of Concept
1. Attacker buys a modest amount of `Token` off the curve via `Zap.buy`/`Bonding.buy` (any unprivileged caller can do this).
2. Attacker calls `Token.transfer(pairAddr, largeAmount)` directly (as in `_stageDonationAttack`, sized so `tokensOut` computed from the constant-product curve for a plausible buy would exceed the now-inflated `tokenBalance()`), pushing `pair.tokenBalance() > reserveToken` — confirmed reachable per `test_donation_realBalanceExceedsReserveToken`: [8](#0-7) 
3. Any subsequent trader calls `Zap.buy`/`Bonding.buy` with an amount large enough that `_computeBuy`'s naive `tokensOut` exceeds `realBalance` (now inflated past `reserveToken`), entering the cap branch.
4. `cappedReserveToken = reserveToken - tokensOut` underflows (`tokensOut = realBalance > reserveToken`), and the entire `buy` transaction reverts — no error is caught or handled, freezing that token's curve permanently for any cap-triggering buy size.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function previewLtUntilGraduation(
        address token_
    ) external view returns (uint256) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return 0;
        if (info.lifecycle != Lifecycle.Curve) return 0;

        address pair = info.pair;
        uint256 realBalance = IPair(pair).tokenBalance();
        if (realBalance == 0) return 0;

        (uint256 reserveToken, uint256 reserveAsset) = IPair(pair).getReserves();

        uint256 ltUntilThreshold = type(uint256).max;
        uint256 exchangeRate = IBounceLeveragedToken(info.ltAddress).exchangeRate();
        if (exchangeRate > 0) {
            uint256 realLtRaised = reserveAsset - _launchTimeVirtualLtReserve(token_, pair);
            uint256 thresholdRealLt = ($.graduationThresholdUsd * 1e18 + exchangeRate - 1) / exchangeRate;
            if (realLtRaised >= thresholdRealLt) return 0;
            ltUntilThreshold = thresholdRealLt - realLtRaised;
        }

        // Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
        if (realBalance >= reserveToken) return ltUntilThreshold;

        uint256 cappedReserveToken = reserveToken - realBalance;
        uint256 cappedReserveAsset = (IPair(pair).k() + cappedReserveToken - 1) / cappedReserveToken;
        uint256 ltUntilSupply = cappedReserveAsset - reserveAsset;

        return ltUntilSupply < ltUntilThreshold ? ltUntilSupply : ltUntilThreshold;
    }
