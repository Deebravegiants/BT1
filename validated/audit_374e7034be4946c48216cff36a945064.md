### Title
Attacker-controlled `amount_out` in SwapBaseOut/SwapBaseOutV2 causes an unwrap panic (denial of service) in `Calculator::swap_token_amount_base_out` before the insufficient-funds check runs - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
`process_swap_base_out` and `process_swap_base_out_v2` call `Calculator::swap_token_amount_base_out` with the fully attacker-supplied `swap.amount_out` *before* validating that `amount_out` is smaller than the pool's available liquidity. Inside that function, the pool liquidity is subtracted by `amount_out` using `checked_sub(...).unwrap()`. If `amount_out` is greater than or equal to the pool's liquidity, this returns `None` and `.unwrap()` panics, crashing transaction processing instead of returning the intended `AmmError::InsufficientFunds`.

### Finding Description
In `program/src/math.rs`, `swap_token_amount_base_out` computes the required input amount for a requested output amount: [1](#0-0) 

Both branches compute `denominator` by subtracting `amount_out` from the pool's `total_pc_without_take_pnl` (or `total_coin_without_take_pnl`) and immediately call `.unwrap()`. If `amount_out >= total_pc_without_take_pnl` (Coin2PC) or `amount_out >= total_coin_without_take_pnl` (PC2Coin), `checked_sub` returns `None` and the process panics.

Both call sites invoke this function *before* performing the "amount_out exceeds pool reserves" check that is supposed to guard against exactly this condition: [2](#0-1) [3](#0-2) 

The safety check `if swap.amount_out >= total_pc_without_take_pnl { return Err(AmmError::InsufficientFunds.into()); }` only runs *after* the panicking call at line 2172. The identical ordering bug exists in `process_swap_base_out_v2`: [4](#0-3) [5](#0-4) 

`swap.amount_out` originates directly from the unpacked `SwapInstructionBaseOut` instruction data supplied by the caller with no upper bound relative to pool reserves enforced earlier in either function (only account/mint/status checks precede it). This is directly analogous to the Nimiq `VestingContract::can_change_balance` bug: an error path meant to return a graceful `InsufficientFunds` error instead panics because the underflowing subtraction used for the error/calculation runs before the guard that would have prevented it.

### Impact Explanation
Any unprivileged party can submit a single `SwapBaseOut` or `SwapBaseOutV2` transaction against any existing AMM pool, setting `amount_out` to a value greater than or equal to the current pool reserves of the output token (trivially discoverable by reading the vault balances, which are public accounts). This deterministically panics the program during transaction processing. Repeated or crafted transactions against a targeted pool can be used to reliably fail/crash processing for that instruction path, a denial-of-service against the pool's swap-out functionality processed by validators executing the transaction.

### Likelihood Explanation
High likelihood: the precondition (`amount_out >= reserves`) is entirely attacker-chosen and requires no special privileges, no race conditions, and no prior state manipulation — a single transaction with `amount_out` set larger than the pool's current reserve of the requested token is sufficient. Pool reserves are public on-chain data, making this trivial to trigger deterministically.

### Recommendation
Reorder the checks in `process_swap_base_out` and `process_swap_base_out_v2` so the reserve-sufficiency check (`swap.amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl`) is performed **before** calling `Calculator::swap_token_amount_base_out`. Additionally, harden `swap_token_amount_base_out` itself to use `checked_sub(...).ok_or(AmmError::InsufficientFunds)?` (or equivalent) instead of `.unwrap()`, so that even if called from another site with an unvalidated `amount_out`, the function returns a proper error instead of panicking.

### Proof of Concept
1. Identify any live AMM pool and read its `amm_coin_vault`/`amm_pc_vault` balances to determine `total_pc_without_take_pnl` (or `total_coin_without_take_pnl`).
2. Submit a `SwapBaseOut` (or `SwapBaseOutV2`) instruction with `amount_out` set to a value `>= total_pc_without_take_pnl` for the Coin2PC direction (or `>= total_coin_without_take_pnl` for PC2Coin).
3. Execution reaches `Calculator::swap_token_amount_base_out` at [2](#0-1)  before the reserve check at [3](#0-2) , causing `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` at [6](#0-5)  to panic instead of returning `AmmError::InsufficientFunds`.
