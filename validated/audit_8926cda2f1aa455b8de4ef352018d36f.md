### Title
Opaque swap routes can inject unauthorized token transfers into the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept opaque route bytes and forward them to the configured router without validating the venue addresses embedded in that route. [1](#0-0) [2](#0-1)  A malicious venue can invoke a token transfer from the caller to an attacker while execution is under the caller’s `swap_collateral` authorization; Soroban simulation records that transfer as a required child authorization, and signing the resulting tree makes it valid. [3](#0-2) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` authorizes `caller`, verifies account ownership or delegation, withdraws collateral, and passes the attacker-influenced `swap` bytes to `swap_tokens`. [4](#0-3)  `swap_tokens` authorizes only the exact input-token transfer from the controller to the router, then executes the opaque route and validates only controller-side input/output balance deltas. [5](#0-4)  These checks do not constrain other calls made by route-selected venue contracts. [6](#0-5) 

The regression test deploys a router that invokes a route-selected pool, and that pool calls `wallet_token.transfer(alice, attacker, amount)`. [7](#0-6) [8](#0-7)  Simulation nests the unauthorized wallet transfer under Alice’s root `swap_collateral` authorization, and enforcement accepts it when Alice signs the poisoned tree. [9](#0-8) [10](#0-9) 

### Impact Explanation
A malicious route can steal arbitrary tokens held by the caller, including tokens unrelated to the lending position, while still returning enough output for the controller’s measured-output and account-risk checks to pass. [11](#0-10) [12](#0-11)  The demonstrated loss is the victim’s full unrelated wallet balance rather than merely the routed collateral amount. [13](#0-12) [14](#0-13) 

### Likelihood Explanation
Exploitation requires the victim to execute a malicious route and sign an authorization tree containing the injected transfer. [15](#0-14)  However, the route is supplied as opaque bytes, venue addresses are not allowlisted, and neither the route minimum nor the controller’s final solvency checks bound transfers outside the expected swap legs. [16](#0-15) [6](#0-5)  Because execution and loss are demonstrated but depend on a poisoned signed authorization tree, the issue is Medium severity. [17](#0-16) 

### Recommendation
Restrict executable route venues to governance-approved contracts or require a decoded, signed execution manifest that enumerates every permitted nested call and token transfer. [6](#0-5)  Clients should decode route bytes before signing and reject any `swap_collateral` authorization tree containing child calls other than the expected strategy-specific token pulls. [18](#0-17) 

### Proof of Concept
The test builds Alice’s `swap_collateral` call with a route whose venue contract transfers her entire unrelated wallet token balance to the attacker. [19](#0-18) [20](#0-19)  Recording-mode simulation emits one root `swap_collateral` authorization with `transfer(alice, attacker, WALLET_BALANCE)` as a child, and execution leaves Alice’s wallet empty while crediting the expected ETH output to her position. [21](#0-20)  In enforcing mode, the same route fails with an honest root-only tree but succeeds once Alice signs the simulation-produced poisoned tree. [22](#0-21)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
