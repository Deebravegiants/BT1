### Title
Webhook shop-domain spoofing due to shop identity not covered by HMAC verification - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before dispatching webhook data (including the `shop` field) to the app's handler. In reality, the HMAC signature only covers the raw request body — the `shop` (and every other) HTTP header, including `x-shopify-shop-domain`, is completely unauthenticated.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes and compares the signature strictly against that signable string: [2](#0-1) 

`Request#shop` is read straight from the `shop-domain`/`x-shopify-shop-domain` header with no cross-check against the verified body or against any known/installed shop: [3](#0-2) 

`Registry.process` verifies only the HMAC, then immediately forwards `request.shop` to the app handler as trusted tenant identity: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop the handler acts on`

But the actual binding is:
`bytes verified by HMAC (raw body only) != shop field the handler acts on (unauthenticated header)`

The gem's own documentation reinforces the false assumption, describing `process` as verifying the webhook is from Shopify and describing `data.shop` as "The shop domain of the webhook" without qualification: [5](#0-4) [6](#0-5) 

Because `api_secret_key` is shared by every shop that has the app installed, any merchant who has legitimately installed the app can trigger a genuine, correctly-HMAC-signed webhook for their own store, capture the raw body + valid HMAC, then resend it directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to name an arbitrary victim shop. `Registry.process` will accept it (HMAC checks out against the untouched body) and the handler will receive `WebhookMetadata` claiming the (fabricated) event belongs to the victim shop — even though nothing in the verified bytes ties the payload to that shop.

### Impact Explanation
This breaks the tenant/shop identity boundary that apps rely on `ShopifyAPI::Webhooks::Registry.process` to enforce, per its own documentation. An app that (per the documented usage pattern) trusts `data.shop` to route/attribute webhook-driven side effects (e.g., updating shop-scoped records, queuing shop-scoped jobs as shown in the docs example `perform_later(topic:, shop_domain: data.shop, ...)`) can be made to apply attacker-controlled data under another tenant's identity — cross-tenant data injection/corruption using only a self-service app install, no leaked secrets or privileged access required.

### Likelihood Explanation
Any unprivileged internet user can install a public Shopify app on their own (free) development store, trigger events to receive a validly-signed webhook, and replay the captured body to the app's webhook endpoint with a modified `x-shopify-shop-domain` header. No access token, `api_secret_key`, or social engineering is needed — only the ability to install the target app once and send an HTTP request.

### Recommendation
Do not treat `Request#shop` as authenticated identity. Either fold the shop domain into the signed material verified by `HmacValidator` (not possible without a Shopify-side protocol change), or require/document that `Registry.process` callers must independently confirm `data.shop` corresponds to a shop with a currently valid, previously-established session/install record before acting on the payload, and state explicitly in `docs/usage/webhooks.md` that `shop` is unauthenticated header data.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (legitimate self-service install).
2. Attacker triggers a webhook (e.g. `orders/create`) on their own shop, capturing the raw POST body and the genuine `x-shopify-hmac-sha256` header Shopify sends (signed with the app's shared `api_secret_key`).
3. Attacker resends that exact body + HMAC header to the app's public webhook endpoint, replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate` over the untouched raw body only [1](#0-0)  — validation succeeds — and dispatches the handler with `shop: "victim-shop.myshopify.com"` [7](#0-6) , causing the app to process attacker-supplied content as belonging to a shop the attacker does not control.
