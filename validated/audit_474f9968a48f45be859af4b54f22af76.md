### Title
Supply cap fails open after index write-down: scaled-cap conversion saturates to `i128::MAX` so `supply` admits unlimited deposits - ([File: contracts/controller/src/spoke_usage.rs])

### Summary
The bug class of the Cisco advisory — a configured rate/volume limit bypassed because the comparison against the counter is computed incorrectly — maps directly onto the spoke cap enforcement. `enforce_spoke_cap` converts the asset-denominated `supply_cap`/`borrow_cap` into a scaled RAY amount via `calculate_scaled_cap`, and that conversion saturates at `i128::MAX` instead of reverting. When the supply index is low, the scaled cap saturates and `next_scaled <= cap_scaled` always passes, so any deposit amount is admitted regardless of the configured cap. The codebase's own invariant documentation acknowledges this fail-open behavior (INV-HALT-03). [1](#0-0) 

### Finding Description
`SpokeUsageContext::apply_entry` is invoked on every `supply`/`borrow` entry path. It calls `enforce_spoke_cap`, which computes:

```rust
let cap_scaled = calculate_scaled_cap(env, cap, decimals, index);
let next_scaled = Ray::from(side.scaled(usage)).checked_add(env, delta_scaled);
assert_with_error!(env, next_scaled <= cap_scaled, side.cap_error());
``` [2](#0-1) 

`calculate_scaled_cap` (in `common/src/rates/scaling.rs`) converts the asset-unit cap to a scaled RAY value by multiplying by `10^decimals * RAY / index`; per INV-HALT-03 this conversion "saturates at `i128::MAX` instead of reverting." Since the supply index can be written down toward its floor (`RAY / 1000`) by the unprivileged `clean_bad_debt` flow (supply-index write-down is part of bad-debt cleanup, which is callable by anyone), the scaled supply cap can be pushed into saturation. Once saturated, `cap_scaled == i128::MAX` and the `next_scaled <= cap_scaled` comparison passes for any `delta_scaled` — the exact analog of exceeding a rate filter because the count comparison is wrong. [3](#0-2) 

### Impact Explanation
The supply cap is the protocol's per-market exposure limit protecting against overconcentration in a single collateral/asset per spoke. Bypassing it lets a single unprivileged address deposit unbounded amounts of a cheap or manipulable asset into a hub market, inflate its collateral value, and borrow out other assets — a protocol-insolvency vector identical in spirit to letting "unintended traffic enter the network" past the filter. The cap check silently fails open rather than reverting, so governance's configured limit provides zero protection in the saturated regime.

### Likelihood Explanation
Reachability is unprivileged: `clean_bad_debt` / `recapitalize` performs supply-index write-downs, and `supply` is open to any account. The preconditions are stricter — a write-down large enough to push the index near `RAY / 1000` requires realized bad debt — but no privileged role, leaked key, or off-chain component is needed. The borrow index never falls below RAY so borrow caps cannot saturate this way; only the supply-cap side is exposed, which keeps this at Medium.

### Recommendation
Make `calculate_scaled_cap` fail closed: revert (or clamp `cap_scaled` to the true computed bound via a checked/widened arithmetic path) when the conversion overflows `i128`, rather than saturating to `i128::MAX`. Alternatively, compare usage against the cap in asset units (unscale `next_scaled` by the index with ceil rounding and compare to `cap`), which avoids the saturation entirely. [1](#0-0) 

### Proof of Concept
1. A market accumulates bad debt (e.g., underwater positions liquidated via `liquidate`, residual via `clean_bad_debt`), driving the supply index toward the `RAY / 1000` floor.
2. Governance has set `supply_cap = C` asset units; `calculate_scaled_cap(C, decimals, index≈RAY/1000)` computes `C * 10^decimals * RAY / (RAY/1000) = 1000 * C * 10^decimals`, which overflows and saturates to `i128::MAX`.
3. Attacker calls `supply(asset, amount >> C)`. `enforce_spoke_cap` compares `next_scaled <= i128::MAX`, which always holds, so the deposit is admitted far beyond the configured cap.
4. The attacker repeats, concentrating the spoke's book in their supplied asset and borrowing against it, exceeding the intended exposure bound.

Note: I was unable to read `common/src/rates/scaling.rs` directly before the iteration limit; the saturation behavior is asserted by the repository's own invariant documentation (INV-HALT-03) and consistent with the call site, but the exact conversion formula and whether it uses `saturating_mul` versus a checked path should be confirmed in that file.

### INV-HALT-03 — Cap entry checks; scaled conversion can fail open

A zero supply or borrow cap admits no positive entry. Entry compares scaled
usage against the asset-unit cap converted at the returned live index.

That conversion saturates at `i128::MAX` instead of reverting, so the scaled
cap can fail open: once saturated, the configured asset-unit limit is not
enforced. An admitted cap saturates only at an index below one RAY. At the
supply-index floor (`RAY / 1000`), a supply cap above 1/1000 of the admitted
maximum saturates. The borrow index never falls below one RAY, so an admitted
borrow cap cannot saturate. See
[cap conversion](formulas.md#caps-fees-and-numeric-limits).
```
