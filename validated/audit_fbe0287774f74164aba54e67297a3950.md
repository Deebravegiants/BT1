### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` accepts any request whose body HMAC validates and then dispatches the handler using the header-derived `shop` value, without that value ever being bound to the signature. This is the same class of bug as the Notional report: a field (`shop`) that is *acted on* by the caller is not covered by the value that is *cryptographically verified* (the HMAC), breaking the identity binding `verified_bytes == acted_on_identity`.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
which only signs `@raw_body`. The `shop`, `topic`, and `webhook_id` accessors read straight from HTTP headers with no cryptographic protection: [2](#0-1) 

`Registry.process` validates only the body HMAC via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the raw body) and the shared `client_secret`: [4](#0-3) 

Because the same `client_secret` is shared across every shop that installs the app, an attacker who installs the app on a shop they control (an ordinary, unprivileged action) receives legitimate webhooks with a valid `raw_body` + HMAC pair signed by Shopify with the app's secret. Since the `shop-domain` header is not part of the signed data, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (e.g. a victim shop). `HmacValidator.validate` still succeeds, because it only checks the body bytes — the identity that is verified (the body was HMAC'd by Shopify with this app's secret) is not the identity that is acted on (`request.shop`, used by `WebhookMetadata.shop` and by whatever session/tenant record the host app keys off of).

This exactly matches the report's bug class: "a field acted on but not covered by the HMAC" — here, `shop` (and `topic`/`webhook_id`) are consumed by the handler but excluded from `to_signable_string`.

### Impact Explanation
This allows cross-tenant confusion/spoofing: an attacker-controlled webhook payload (with attacker-chosen topic/body content, since they control their own shop's data) can be attributed to an arbitrary victim shop domain in the host application, because `Registry.process` and `WebhookHandler#handle` receive `shop: request.shop` as an authenticated fact when it is not. Depending on how the host app's `WebhookHandler` implementations key their storage off `data.shop` (which is the documented, expected pattern per `docs/usage/webhooks.md`), this can lead to cross-tenant data corruption or forced processing of sensitive topics (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`) against a shop the attacker does not control — satisfying the "cross-tenant access" Critical impact bucket without requiring the attacker to possess the app's `client_secret`, an access token, or any privileged credential.

### Likelihood Explanation
Requires only that the attacker install (or otherwise interact with) the app on a shop they legitimately control to obtain one valid `(raw_body, hmac)` pair, then replay it with a forged `shop-domain` header to the app's public webhook endpoint. No secret material, TLS interception, or social engineering is needed — this is achievable by any unprivileged internet user who can install the target app on their own store and hit the app's public webhook URL.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the verified payload before it is trusted downstream — e.g., include the `shopify-shop-domain` header in `to_signable_string`, or independently verify that the `shop` in the payload/header corresponds to a shop with a currently valid, previously-stored session/access token for this app before dispatching the webhook handler.

### Proof of Concept
1. Install the target Shopify app on `attacker-shop.myshopify.com` (a shop the attacker legitimately controls). Trigger any webhook topic the app is registered for; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid for the app's `client_secret` over that exact body.
2. Replay that exact captured `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and adjust `X-Shopify-Topic` if desired).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the raw body) against the HMAC — validation succeeds because the body/HMAC pair is genuinely valid. [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...)`, causing the host application to process attacker-supplied content as if it originated from the victim shop.
