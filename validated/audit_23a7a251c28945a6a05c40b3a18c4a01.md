### Title
Unsanitized `shop` parameter in `Oauth.begin_auth` enables forced OAuth completion via attacker-controlled authorize host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorization redirect URL directly from the caller-supplied `shop` value without ever validating it against `ShopifyAPI::Utils::ShopValidator`, even though that validator exists specifically to guard against untrusted shop domains elsewhere in the library.

### Finding Description
`begin_auth` takes an unauthenticated, caller-supplied `shop:` string and uses it verbatim to build the redirect target for the merchant's browser: [1](#0-0) 

The resulting `auth_route` embeds the app's own `client_id` and its callback `redirect_uri` (`"#{ShopifyAPI::Context.host}#{redirect_path}"`), and `auth_route` is `auth_base_uri(shop) + "/oauth/authorize?..."` — i.e., `shop` becomes the host that the merchant's browser is redirected to. Nowhere in `begin_auth` is `shop` passed through `ShopifyAPI::Utils::ShopValidator.sanitize!`, which is the library's documented mechanism for confirming a `shop` value is actually a trusted Shopify domain (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`): [2](#0-1) [3](#0-2) 

The identity binding that should hold is: *the `shop` value used to construct the OAuth-authorize redirect (which carries the app's `client_id` and `redirect_uri`) equals a value validated by `ShopValidator` as a genuine Shopify domain*. `begin_auth` breaks this binding — it accepts any string as `shop` and uses it directly as the host component of the redirect, with no call to `ShopValidator` anywhere in the method or in `auth_base_uri`.

The getting-started flow explicitly shows that `shop` typically originates from unauthenticated request input (e.g., a header/query param on the app's login route) before `begin_auth` is invoked, meaning this is reachable by any unauthenticated visitor to the app's login endpoint: [4](#0-3) 

By contrast, `validate_auth_callback` (the step which actually sends the app's `client_secret`) at least gates on `Utils::HmacValidator.validate(auth_query)`, which requires possession of `api_secret_key` to forge — so that path is not exploitable by an unprivileged party. The exposure is specifically in `begin_auth`, where no equivalent binding check exists on `shop` before it is used as a URL host.

### Impact Explanation
An unprivileged party who can reach the app's OAuth-start endpoint (e.g., `/login?shop=<value>`) can supply an attacker-controlled `shop` value. Because `begin_auth` never validates that value against `ShopValidator`, the library-produced `auth_route` will redirect the merchant's browser to `https://<attacker-controlled-host>/oauth/authorize?client_id=...&redirect_uri=<app_callback>&state=...`. This lets the attacker force/hijack the beginning of the OAuth flow toward infrastructure they control, carrying the app's real `client_id` and the exact `redirect_uri` the app expects the final authorization code to land on — enabling forced OAuth completion / phishing that can be chained to trick a merchant into completing authorization against a spoofed consent screen. This matches the "session fixation or forced OAuth completion" High-impact category, since it subverts the intended binding between the `shop` domain and a genuine, Shopify-controlled OAuth endpoint.

### Likelihood Explanation
High likelihood: `shop` is normally sourced from unauthenticated request parameters at the very first step of OAuth (the app's own login route calls `begin_auth(shop: ...)` before any Shopify-signed data exists), and the gem provides no built-in guard — the burden falls entirely on the host application to call `ShopValidator.sanitize!` itself, which is easy to omit given the gem's own `begin_auth` implementation does not do it and the docs' example does not show it being done either.

### Recommendation
Have `ShopifyAPI::Auth::Oauth.begin_auth` call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) before using `shop` to construct `auth_base_uri(shop)`, raising `Errors::InvalidShopError` for any value that isn't a trusted Shopify domain, mirroring the protection already implemented in `ShopValidator` and used elsewhere (e.g., `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`).

### Proof of Concept
1. App exposes `GET /login?shop=<value>` which calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")` (as shown in the gem's own documented usage pattern).
2. Attacker sends a victim merchant a link: `https://victim-app.example.com/login?shop=evil-phish.attacker.com`.
3. `begin_auth` computes `auth_route = auth_base_uri("evil-phish.attacker.com") + "/oauth/authorize?client_id=<real client id>&redirect_uri=https://victim-app.example.com/auth/callback&state=<nonce>"` — no exception is raised because `ShopValidator` is never invoked.
4. The merchant's browser is redirected to the attacker's server with the app's real `client_id` and callback `redirect_uri`, which the attacker can use to stage a forced/spoofed OAuth completion flow against the merchant.

**Note on scope:** I could not directly view `auth_base_uri`'s body or `client_credentials.rb`/`refresh_token.rb` contents in this session (tool calls for those files did not return content), so I cannot confirm whether `auth_base_uri` performs any independent sanitation beyond what's visible in `begin_auth`. Based on the visible code, no `ShopValidator` call appears in the `begin_auth` method itself, and `grep_search` for `ShopValidator`/`sanitize_shop_domain` usage shows it is referenced only in `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, and `graphql/storefront.rb` — not in `oauth.rb`.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
end
