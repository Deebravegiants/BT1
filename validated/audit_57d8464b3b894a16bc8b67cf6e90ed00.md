### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw request body only, but the `shop` value used downstream for tenant identification is read from an HTTP header that is never included in that signed string. This breaks the intended binding "the shop the HMAC vouches for" == "the shop the app acts on behalf of."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed material at all: [2](#0-1) 

`Registry.process` validates the HMAC against the request (i.e., against the body) and, once that passes, immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only proves that `to_signable_string` (the body) was signed with the app's `api_secret_key`; it says nothing about which header values accompanied that body: [4](#0-3) 

This is structurally the same defect class as `unwrapETH2LD`'s use of `transferFrom` instead of `safeTransferFrom`: the code verifies one thing (an ERC-721 owner/approval check that doesn't validate the receiving contract) but acts on a different, unguarded parameter (`newRegistrant`). Here, the code verifies one thing (HMAC over the body) but acts on a different, unguarded field (the `shop` header) for tenant identity. The equality that should hold — `shop_bound_by_hmac == shop_used_for_tenant_lookup` — does not, because the `api_secret_key` used to sign webhooks is the **same app-level secret for every shop that installs the app**, not a per-shop secret.

### Impact Explanation
Because the `api_secret_key` is shared across all shops that install a given public app, any unprivileged user who installs the app on their own shop receives genuine webhook deliveries with valid HMAC signatures over bodies that pertain to their own shop's data. Such a user can capture one of these deliveries and replay it to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header to a victim shop's domain. The HMAC still validates (it only checks the body), so `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain while `body` is the attacker's own data. Any app that uses `WebhookMetadata#shop` as the tenant key for persisting/merging webhook payloads (the intended and documented use of this field) can have attacker-controlled body content written under a different shop's tenant, i.e., cross-tenant data injection/corruption.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (any developer/merchant with a Shopify Partner or dev store can do this — no privileged credentials, tokens, or `api_secret_key` knowledge needed) and be able to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint. No cryptographic secret needs to be forged, only replayed body+HMAC pairs paired with a substituted header. Likelihood is High for any app that trusts `request.shop`/`WebhookMetadata#shop` for tenant routing, which is the standard usage pattern shown in the library and its docs.

### Recommendation
Include the shop-identifying header(s) in the value that is HMAC-verified, or otherwise bind `shop` to the verified body (e.g., require the body to carry/echo the shop and compare it against the header, or maintain a per-shop verification secret/webhook id lookup instead of trusting the header). At minimum, `Registry.process` should cross-check `request.shop` against an independently trusted source (such as a `webhook_id` previously registered for that shop) rather than accepting the unauthenticated header value outright.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` and lets it deliver a normal webhook (e.g., `orders/create`) to the app's endpoint, capturing the raw body `B` and the valid header `X-Shopify-Hmac-Sha256: H` (computed by Shopify over `B` using the app's shared `api_secret_key`).
2. Attacker resends the exact same `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` reads `H` from the header and `to_signable_string` returns `B`; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` using the shared secret — see [5](#0-4) .
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)` — see [6](#0-5) , causing the app to process attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
