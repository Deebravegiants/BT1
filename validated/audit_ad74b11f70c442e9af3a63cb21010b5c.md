Confirmed: the webhook processing docs explicitly state `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" based solely on `ShopifyAPI::Webhooks::Request`, and the `shop` field passed to the handler comes directly from an unauthenticated header, not from the HMAC-signed content.

### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` attribute that the library hands to app webhook handlers is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed content. `ShopifyAPI::Utils::HmacValidator.validate` only proves that the *body bytes* were signed with the app's secret; it proves nothing about which shop that signature was intended for. [1](#0-0) [2](#0-1) 

### Finding Description
This mirrors the reported bug class: a field that is *acted on* (`shop`, used as the tenant identifier passed to the app's handler) is not *covered* by the authenticity check (the HMAC, which only signs `@raw_body`). The equality that should hold — "shop authenticated == shop the data is attributed to" — is broken because the HMAC binds only to `raw_body`, not to `shop-domain`.

`ShopifyAPI::Webhooks::Registry.process` raises `InvalidWebhookError` if `Utils::HmacValidator.validate(request)` fails, then immediately trusts `request.shop` to build `WebhookMetadata`: [3](#0-2) 

Because all shops installing the same app share one `api_secret_key` (the app's client secret, not a per-shop key), any shop that has this app installed can trigger a webhook event on its own store and receive a validly-HMAC-signed `(raw_body, hmac)` pair for content of the attacker's choosing (e.g. by editing a product's title/note field prior to triggering `products/update`, or similar attacker-controlled body fields). An attacker can then replay that exact `raw_body` + `hmac` header to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still passes, because the signature check never inspects the shop header. `Registry.process` then invokes the app's handler with `WebhookMetadata.new(shop: <victim_shop>, body: <attacker-chosen body>, ...)`, exactly as if Shopify had sent that event for the victim shop. [3](#0-2) 

The gem's own documentation reinforces that developers are meant to rely on `Registry.process` to fully "verify the request did indeed come from Shopify," and to trust `data.shop` as the shop domain of the webhook — there is no additional guidance to independently re-verify the shop.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged attacker who merely controls a shop that has the target app installed (a normal, unprivileged tenant of the app, requiring no `api_secret_key`, access token, or victim credentials) can make the app process attacker-controlled webhook payloads under the identity of a different, victim shop. Any app logic that uses `WebhookMetadata#shop` to select which tenant's records to update (a use pattern the docs explicitly demonstrate: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into writing attacker-controlled data into a victim tenant's records, or into de-registering/mis-processing events for a shop the attacker does not own. This satisfies the "cross-tenant access" criterion.

### Likelihood Explanation
The only prerequisites are: (1) the app is installed on a shop the attacker controls (self-installable/public apps, or a free/dev-store install — no special privilege), and (2) the app's webhook endpoint is reachable on the public internet, which it must be for Shopify to deliver webhooks at all. No secrets, tokens, or victim cooperation are required — the attacker simply captures one legitimately-signed webhook from their own store and replays it with a different shop header.

### Recommendation
- Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed content, or otherwise cryptographically bind the header-derived `shop` value to the signature check, so that `HmacValidator.validate` fails if the shop identity is altered.
- At minimum, document that `data.shop` from `WebhookMetadata` is unauthenticated relative to the HMAC and that host apps must independently confirm the shop is one they have a valid session/install record for before trusting webhook content for that shop, and reconsider signing the header value directly as Shopify's own signature scheme allows.

### Proof of Concept
1. Attacker owns `attacker.myshopify.com`, which has the app installed (app secret `S` shared across all installs).
2. Attacker triggers a `products/update` webhook on their own store with an attacker-controlled body field (e.g. product `note`/`title` containing malicious content), receiving:
   - `raw_body = B`
   - `X-Shopify-Hmac-SHA256 = HMAC_SHA256(S, B)` (valid)
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
3. Attacker POSTs to the app's webhook endpoint with the *same* `raw_body` and `X-Shopify-Hmac-SHA256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => hmac})` is built; `to_signable_string` returns `B` only. [4](#0-3) 
5. `ShopifyAPI::Utils::HmacValidator.validate` recomputes `HMAC_SHA256(S, B)` and compares to the supplied hmac — it matches, since `B` and the secret are unchanged. [2](#0-1) 
6. `Registry.process` proceeds and calls the app's handler with `shop: "victim.myshopify.com"`, `body:` the attacker's payload — the app now believes attacker-controlled data is a legitimate event from `victim.myshopify.com`. [3](#0-2)
