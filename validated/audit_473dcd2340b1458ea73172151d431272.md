This is a real, exact-boundary-break analog: `client_credentials.rb` and `refresh_token.rb` both call `Utils::ShopValidator.sanitize!(shop)` before constructing the `Session` and sending the request that carries `client_secret`, but `Auth::Oauth.validate_auth_callback` does not — it builds `null_session = Auth::Session.new(shop: auth_query.shop)` directly from the unsanitized `auth_query.shop` field and uses it as the HTTP host that receives `client_id`/`client_secret`/`code`.

### Title
Missing shop-domain sanitization in OAuth callback lets an attacker route the app's `client_secret` to a non-Shopify host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token request host directly from `auth_query.shop` [1](#0-0) , without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other flow in this gem that talks to `/admin/oauth/access_token` with the app's `client_secret` in the body (`ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`) [2](#0-1) [3](#0-2) . `HttpClient#initialize` then uses `session.shop` verbatim as the request's base host: `@base_uri = "https://#{api_host || session.shop}"` [4](#0-3) .

### Finding Description
The equality this gem is supposed to enforce is: `host that receives client_secret == a validated *.myshopify.com (or trusted Shopify) domain`. `ClientCredentials` and `RefreshToken` enforce this by calling `Utils::ShopValidator.sanitize!(shop)`, which restricts the resulting host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`, plus any configured `myshopify_domain`) [5](#0-4) [6](#0-5) .

`validate_auth_callback` breaks this equality: it validates the *integrity* of the callback query via HMAC (`Utils::HmacValidator.validate(auth_query)` at line 64) but never validates that `auth_query.shop` is a *trusted domain*. The HMAC only proves the `code`/`host`/`shop`/`state`/`timestamp` values were signed with `Context.api_secret_key` [7](#0-6)  — it says nothing about whether `shop` is actually a `*.myshopify.com`-style domain the app is willing to send its `client_secret` to. The unsanitized value flows straight into `null_session`, then into `HttpClient.new(session: null_session, ...)`, which sets `@base_uri = "https://#{session.shop}"` and POSTs `{client_id, client_secret, code, expiring}` to `#{@base_uri}/admin/oauth/access_token` [8](#0-7) [9](#0-8) .

### Impact Explanation
If a caller constructs `AuthQuery` from any means other than a value already restricted to Shopify's own signing pathway (e.g. a host application that treats `shop`/`hmac` as independent inputs, or any code path where the HMAC secret used to sign the callback is not exclusively controlled by Shopify), the missing sanitize step is the only thing standing between this gem and SSRF/credential exfiltration: `client_secret` would be sent as a POST body to whatever host is present in `shop`. This matches the "SSRF with the app's credentials" / "credential leakage" High-severity class, and is the direct in-scope analog of the reported bug class (an action taken on a value — the destination host for `client_secret` — that isn't actually verified against the intended trust boundary the way the analogous flows in the same file/module verify it).

### Likelihood Explanation
Exploitability is bounded by the strength of the HMAC check: as long as `Context.api_secret_key` is kept secret and only Shopify signs legitimate callbacks with real `*.myshopify.com` shop values, this cannot be triggered by an unprivileged internet user through the normal OAuth redirect flow. However, this is a real inconsistency in the library's own defense-in-depth: two sibling flows in the same module hierarchy (`ClientCredentials`, `RefreshToken`) explicitly treat `shop` as untrusted input requiring `ShopValidator.sanitize!`, while `Oauth.validate_auth_callback` relies solely on HMAC integrity and omits the domain allow-list check entirely, despite `AuthQuery.shop` reaching the exact same `client_secret`-bearing `HttpClient` code path.

### Recommendation
Sanitize `auth_query.shop` through `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`, raising `Errors::InvalidShopError` on failure) in `Oauth.validate_auth_callback` before constructing `null_session`/`Session.from`, mirroring the pattern already used in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, so the host that receives `client_id`/`client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.
