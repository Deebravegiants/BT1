## Title
Webhook `shop` (and `topic`) identity fields are not covered by the HMAC signature, allowing tenant spoofing in webhook processing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw body only, while the tenant-identifying field `shop` (and `topic`) is read from HTTP headers that are never included in the HMAC computation. `Registry.process` validates only the body's HMAC and then hands the header-derived, unauthenticated `shop` value straight to the host app's webhook handler as the tenant identifier.

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled from HTTP headers, completely outside the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the body was signed by *some* holder of the app's `api_secret_key`) and then trusts `request.shop`/`request.topic` from headers to build `WebhookMetadata`, which is handed to the app-defined handler as the authoritative tenant identifier: [3](#0-2) [4](#0-3) 

The binding broken is: `shop authenticated by HMAC` ≠ `shop used by the handler to select the merchant/tenant`. Since the HMAC key (`Context.api_secret_key`) is the app's single client secret shared across *every* shop that installs the app, any unprivileged user who installs the target app on their own (attacker-controlled) shop can obtain a validly-signed webhook body/HMAC pair from Shopify for their own store, then replay that exact `raw_body` + `hmac` header with an altered `x-shopify-shop-domain`/`shopify-shop-domain` header value pointing at a victim shop. `Utils::HmacValidator.validate` still passes because it only checks the body against the secret, not the header: [5](#0-4) 

### Impact Explanation
This crosses a tenant boundary (High impact per the criteria: "scope or expiry check bypass" / cross-tenant class of issue). Any app built on this gem that uses `WebhookMetadata#shop` from `Registry.process` to look up per-merchant records, apply mutations, or attribute events will process attacker-controlled data under a victim shop's identity, since the `shop` value is not cryptographically bound to the signed body.

### Likelihood Explanation
Likelihood is high for any real-world app: obtaining a legitimately-signed webhook requires nothing more than installing the target app on a free development/trial store (something any internet user can do), triggering any webhook event, capturing the raw body and its `hmac` header, and replaying it to the app's webhook endpoint with a forged shop-domain header. No access token, `client_secret`, or privileged account is required — only normal use of the app as an ordinary merchant.

### Recommendation
Include the tenant-identifying fields (`shop`, and ideally `topic`) in the HMAC-signed content, or otherwise cryptographically bind them to the verified payload before constructing `WebhookMetadata`. At minimum, `Registry.process` (or `Request`) should reject/flag cases where header-derived identity fields cannot be tied back to the specific signed body, and documentation should explicitly warn implementers not to trust `WebhookMetadata#shop` as authenticated unless additional binding is added.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (free/dev store, no privileged credential needed).
2. Attacker triggers a webhook event (e.g., `customers/create`) on their own store; Shopify sends the app a request with a body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)`.
3. Attacker resends the exact same `B`/`H` pair to the app's webhook endpoint but replaces the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC_SHA256(api_secret_key, B)` and it matches `H`, so validation passes (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...)` and invokes the app's handler with that spoofed shop, even though the body content actually originated from the attacker's own store event (`lib/shopify_api/webhooks/registry.rb:188-200`).
