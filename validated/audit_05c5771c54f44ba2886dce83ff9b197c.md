### Title
Missing ownership binding on user QR-code identity allows misattributed/unauthorized signup - (File: src/plans/qr_scan/user.rs, src/backend/user_status.rs)

### Summary
The external report describes an ERC20 `burn(address account, uint256 amount)` function that lets any caller destroy tokens belonging to an arbitrary `account` because the function never checks that `account == msg.sender`. The reachable analog in `orb-core` is the "old-format" user QR-code path, where the identity (`user_id`) that gets bound to a signup's biometric data is taken verbatim from an unauthenticated, un-signed string presented to the orb, with no cryptographic proof that the presenter is the owner of that identity — mirroring the missing "caller == account" check in the original bug.

### Finding Description
`qr_scan::user::Data::try_parse` accepts two QR formats:
- The modern format, decoded via `orb_qr_link::decode_qr`, which returns a `user_data_hash` used later to cryptographically verify the backend-returned `authenticated_app_data` against the physically-scanned code: [1](#0-0) 
- The legacy `QR_CODE_V2` format (`"userid:<uuid>:<policy>"`), which is a plain, unsigned string matched by regex and produces a `Data` with `user_data_hash: None`: [2](#0-1) 

Downstream, `backend::user_status::request` only performs a cryptographic ownership check (`user_data.verify(user_data_hash)`) when a `user_data_hash` is present; for the legacy/no-hash path it falls straight into the "old QR-code format" branch and returns `UserData` with no binding at all: [3](#0-2) [4](#0-3) 

That `user_id` string — whatever the person standing in front of the orb chooses to present — is what gets attached to the entire signup: it is sent as `userId` in the signup-create request, hashed into the personal custody package's `operator_id`/`qr_code` fields, and included in the secure-element-signed iris signature: [5](#0-4) [6](#0-5) 

At no point does orb-core itself verify that the physical person presenting the QR code is the one who legitimately owns/generated that `user_id` when the legacy no-hash format is used — the identity value is trusted as-is, just as the vulnerable `burn(address account, uint256 amount)` trusted the caller-supplied `account` without checking `msg.sender`.

### Impact Explanation
If an attacker can present (e.g., print or display) a QR code encoding another user's `userid:<uuid>:<policy>` string, the orb will attempt to bind that victim's identity/session to whatever biometric data it captures from the attacker standing in front of the camera. Successful completion means the victim's account gets enrolled/signed-up using the attacker's biometrics (or vice versa) — a misattributed signup and identity-binding compromise, and if the backend's session for that ID is still valid/unclaimed, this can result in unauthorized signup completion under another person's identity, which is the direct analog of "burning someone else's tokens."

### Likelihood Explanation
Exploitation requires the attacker to know/guess a valid, not-yet-completed `user_id` for a legacy-format QR code and for the backend to still respond with `valid: true` for it via `backend::user_status::request` (i.e., the backend must have an open, unclaimed session tied to this UUID). This constrains likelihood somewhat since backend-side validity gating is the primary defense, but the orb-core client itself performs no additional binding/ownership check for the legacy path, so any weakness or race in that backend-side session-validity check translates directly into an unauthorized/misattributed signup with no additional orb-core safeguard.

### Recommendation
Require the cryptographic `user_data_hash`/signature binding (the mechanism already used for the modern QR format via `decode_qr`) for all user QR-codes, and reject or deprecate the legacy no-hash `QR_CODE_V2` format in production so that `user_id` can never be accepted without proof that the presenter generated/owns it, analogous to enforcing `account == msg.sender` in the `burn()` fix.

### Proof of Concept
1. An attacker obtains or guesses a UUID `X` corresponding to another user's active, unclaimed signup session (created by the victim's app but not yet completed at the orb).
2. Attacker encodes `userid:X:<policy>` as a plain QR code (legacy `QR_CODE_V2` format) — no signature or hash required, see `Data::from_v2`: [2](#0-1) .
3. Attacker presents this QR code to the orb; `handle_user_qr_code`/`verify_user_qr_code` calls `backend::user_status::request`, which — lacking a `user_data_hash` — skips the `user_data.verify()` check entirely: [7](#0-6) .
4. If the backend still reports the session as `valid`, the orb proceeds to capture the attacker's own biometrics and submits them under `user_id = X` via `signup_post::request`: [5](#0-4) , completing a signup that binds the attacker's biometric data to the victim's identity.

    }

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());

    Ok(BASE64.encode(&signed))
