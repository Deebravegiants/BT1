### Title
Withdraw instruction performs an atomic dual-token transfer with no single-sided fallback, allowing an external freeze/blacklist on either vault mint to permanently lock all LP holders' funds - (File: program/src/processor.rs)

### Summary
`Processor::process_withdraw` requires both the coin-side and pc-side SPL token transfers out of the AMM's vaults to succeed before it burns the user's LP tokens and decrements `amm.lp_amount`. If the mint of either vault (e.g. a freezable/blocklist-capable stablecoin such as USDC) has its freeze authority freeze the AMM's vault token account or a user's destination token account, the whole withdraw transaction reverts, and there is no alternate single-sided withdrawal path in the program. This mirrors the reported bug class where an external token issuer's blocklist action makes a "balance drain to zero" precondition permanently unreachable, except here it blocks the users' only exit instruction rather than an admin's strategy-removal call.

### Finding Description
In `process_withdraw`, after computing `coin_amount` and `pc_amount` from the invariant, the function performs two token transfers unconditionally before burning LP and updating pool state: [1](#0-0) 

Both `Invokers::token_transfer_with_authority` calls (coin vault → user, pc vault → user) must succeed in the same instruction for `Invokers::token_burn` and `amm.lp_amount = amm.lp_amount.checked_sub(...)` to execute: [1](#0-0) 

`Invokers::token_transfer_with_authority` is a thin wrapper around the standard SPL `Transfer` instruction, invoked via CPI with no additional freeze-state checks performed by the AMM program itself: [2](#0-1) 

SPL tokens such as USDC support a mint-level freeze authority that can freeze any individual token account (including a pool's vault or a user's destination ATA) at any time, independent of the AMM program. Since neither `amm_coin_vault_info` nor `amm_pc_vault_info` (nor the user destination accounts) are checked for a frozen state before the transfers are attempted, if either the coin vault, pc vault, or the corresponding user destination account for one side of the pool is frozen/blocklisted by the token's freeze authority, the SPL Token program CPI for that leg will fail, causing the entire `process_withdraw` instruction — including the otherwise-successful transfer of the non-frozen asset and the LP burn — to revert.

The program provides no alternative, single-asset withdrawal instruction; `process_withdraw` is the only path by which an LP holder can redeem `AmmInstruction::Withdraw`: [3](#0-2) 

Because the two transfers plus the LP burn are bundled atomically with no fallback, a freeze imposed on just one side of the pool (analogous to the reported USDC admin blocklisting a strategy's contract) permanently blocks every LP holder from withdrawing either asset, even the non-frozen one, for as long as the freeze persists — and since freezes are controlled entirely by the external mint's freeze authority, the AMM program and its users have no way to reverse or work around it.

### Impact Explanation
This causes permanent freezing of LP funds for every liquidity provider in the pool, not just a single depositor, since `process_withdraw` is the sole exit mechanism and it is all-or-nothing across both vault legs. This matches the accepted impact category of "permanent freezing of user or LP funds."

### Likelihood Explanation
Any SPL token that implements a freeze authority (a first-class SPL Token feature used by regulated stablecoins such as USDC) can trigger this condition simply by freezing the AMM's vault token account or a legitimate user's destination account for one side of the pool. This requires no cooperation, privileged access, or malicious action from the Raydium program itself — it is an externally reachable precondition exactly analogous to the original report's "admin of USDC blocks the relevant contract" scenario, just applied to the withdraw path used by ordinary swappers/LPs instead of a strategy-removal admin call.

### Recommendation
Add a single-sided/emergency withdrawal path (or make the two transfers independently attemptable) so that if one vault's mint or token account is frozen, LP holders can still redeem the non-frozen asset and/or have their LP burned proportionally, rather than having the whole withdrawal instruction depend on both transfers succeeding atomically.

### Proof of Concept
1. Pool is created with `coin_mint` = a normal SPL token and `pc_mint` = USDC (or any freezable SPL token) via `Initialize2`.
2. USDC's freeze authority freezes the AMM's `pc_vault` token account (or a specific user's `user_dest_pc` ATA) — an action entirely outside the Raydium program's control.
3. Any LP holder calls `Withdraw`; `process_withdraw` computes `coin_amount`/`pc_amount` and attempts both `token_transfer_with_authority` calls at [4](#0-3) .
4. The pc-side transfer CPI fails due to the frozen account, causing the SPL Token program to return an error, which propagates and reverts the entire instruction — the coin-side transfer and the LP burn never happen.
5. Every LP holder in the pool is now permanently unable to withdraw any asset from the pool for as long as the freeze exists, with no alternate instruction available to recover funds.

    pub fn token_transfer_with_authority<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        authority: AccountInfo<'a>,
        amm_seed: &[u8],
        nonce: u8,
        amount: u64,
    ) -> Result<(), ProgramError> {
        let authority_signature_seeds = [amm_seed, &[nonce]];
        let signers = &[&authority_signature_seeds[..]];
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            authority.key,
            &[],
            amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, authority, token_program],
            signers,
        )
    }
