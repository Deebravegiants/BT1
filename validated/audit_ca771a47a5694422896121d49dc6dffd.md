### Title
Webhook `shop-domain` header is not covered by HMAC verification, breaking the shop-identity binding trusted by handlers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates authenticity of an inbound webhook by checking `Utils::HmacValidator.validate(request)`, which signs/verifies `request.to_signable_string`. That method returns only the raw body bytes. The `shop` (and `topic`, `webhook_id`, `api_version`) values that handlers subsequently use to identify *which tenant* the webhook belongs to are pulled straight from HTTP headers, which are completely outside the HMAC's coverage.

### Finding Description
`Request#hmac` is computed by the caller from the `X-Shopify-Hmac-Sha256` header and compared against `HMAC-SHA256(client_secret, raw_body)` via `Utils::HmacValidator.validate` [3](#0-2) . The signable string is exclusively `@raw_body` [2](#0-1) . However, `Request#shop` — the value handlers use as the tenant/session key when processing the webhook — is read directly from the `shop-domain` header without any cryptographic binding to that header value [4](#0-3) .

This creates the equality-breaking pattern this scan targets: the bytes verified by HMAC (`raw_body`) ≠ the bytes/field trusted for shop identity (`shop-domain` header). Since Shopify's genuine webhook HMAC never signs headers (this matches Shopify's documented webhook verification scheme — only the body is signed), any component sitting in front of the app (e.g., a shared reverse proxy, a misconfigured load balancer that lets a client set/override headers before HMAC termination, or a multi-tenant webhook receiver endpoint that fans out to multiple `Registry.process` calls with attacker-influenced headers) can replay a *validly HMAC-signed* body from Shop A while relabeling the `shop-domain` header to Shop B. `Registry.process` performs no independent verification that the header-derived `shop` matches any property actually secured by the signature [5](#0-4) .

### Impact Explanation
If the hosting application uses `request.shop` from `ShopifyAPI::Webhooks::Request` to select which merchant's session/data to mutate (a documented and expected usage pattern for this gem), an attacker who can influence headers on the path to the app's webhook endpoint — without knowing `client_secret` — can cause a genuinely-signed webhook payload to be attributed to, and processed against, a different tenant than the one it was actually generated for. This is a cross-tenant identity-binding failure at the library layer: the gem gives the impression that `validate()` returning true means "the shop tuple in `Request` is authentic," but only the body is authenticated.

### Likelihood Explanation
Exploitability depends entirely on whether the deployment environment allows header injection/rewriting independent of the signed body (e.g., proxies, CDNs terminating HMAC checks elsewhere, or multi-tenant router logic feeding `Registry.process`). Within the gem's own contract this is a real gap since it explicitly declares `to_signable_string` as body-only while exposing `shop` as an unauthenticated accessor with no warning or secondary binding.

### Recommendation
Extend `Request` to defensively cross-check the header-derived `shop` (and `topic`) against a field embedded in the signed JSON body when available (e.g., Shopify webhook payloads generally do not include the shop domain in-body, so the safer fix is to document/require that hosting apps never trust `request.shop` for authorization decisions without an out-of-band shop allowlist, or have the gem accept the shop domain only from a value it can verify came from Shopify's registered endpoint per-shop). At minimum, add explicit documentation/warning that `shop`, `topic`, and `webhook_id` are unauthenticated header values not covered by `hmac`, so consuming apps do not conflate "`HmacValidator.validate` succeeded" with "the shop attribution is trustworthy."

### Proof of Concept
1. App registers webhooks for Shop A and Shop B, both routed through `ShopifyAPI::Webhooks::Registry.process`.
2. Shopify sends a legitimate webhook for Shop A: body `B`, `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: shopA.myshopify.com`.
3. A component upstream of the app's webhook handler (proxy/router under attacker influence, or a bug in header propagation across tenants sharing infrastructure) forwards the same untouched body `B` and HMAC header, but rewrites `X-Shopify-Shop-Domain` to `shopB.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` still returns `true` because it only checks `raw_body` against the HMAC header [6](#0-5) .
5. `Registry.process` proceeds to invoke the handler with `request.shop == "shopB.myshopify.com"` [4](#0-3) , causing Shop A's webhook data to be applied under Shop B's tenant context, despite `validate()` reporting success.
