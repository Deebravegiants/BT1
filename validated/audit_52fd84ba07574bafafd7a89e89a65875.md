### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant misattribution of webhook payloads - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates nothing but the body bytes. The `shop-domain` header, which `ShopifyAPI::Webhooks::Registry.process` trusts and forwards to the app's handler as the tenant identifier, is never part of the signed material.

### Finding Description
`Registry.process` authenticates a webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and compares an HMAC over it against the `hmac` header: [1](#0-0) 

`Request#to_signable_string` returns `@raw_body` exclusively — the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are excluded from the signable string entirely: [2](#0-1) 

Yet `Registry.process` passes `request.shop` (parsed straight from the unauthenticated `shop-domain` header) into `WebhookMetadata`, which is the value host applications use to identify which tenant/merchant the payload belongs to: [3](#0-2) 

This breaks the identity binding: `shop-domain header value` used by the handler ≠ `shop bound by the HMAC`. The equality that should hold — *the tenant the HMAC authenticates == the tenant the handler acts on* — does not, because the signature covers `body` only, never `body ‖ shop-domain`.

Crucially, the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared globally across every shop that installs the app — it is not shop-specific. A merchant who installs the app on their own store legitimately receives real webhooks from Shopify, each with a **valid** `(body, hmac)` pair signed with that same global secret. Because the header is excluded from the signable string, that attacker can capture their own legitimate webhook and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), so `Registry.process` dispatches the attacker-controlled body to the handler under the guise of the victim shop.

### Impact Explanation
This is a cross-tenant integrity violation: a merchant with a completely unprivileged relationship to a victim shop (no access token, no session, no admin credentials for the victim) can inject arbitrary webhook payloads that the host app will process as if they originated from the victim tenant. Depending on how the host app uses webhook data (e.g., updating order/inventory/customer records keyed by `shop`), this can corrupt or overwrite another merchant's data, satisfying the "cross-tenant access" criteria for Critical impact.

### Likelihood Explanation
Any merchant who installs the app can generate valid `(body, hmac)` pairs at will simply by triggering webhook-eligible events on their own store — no secret extraction or credential theft is required. Replaying the captured pair with a modified header requires only basic HTTP tooling. This is realistically and cheaply exploitable by any of the app's own unprivileged users.

### Recommendation
Bind the tenant identity into the authenticated material. At minimum, `Request#to_signable_string` (or a follow-up check in `Registry.process`) should verify that the `shop-domain` (and ideally `topic`/`webhook-id`, to prevent cross-shop and replay reuse) is cryptographically tied to the payload — e.g., by requiring the host application to independently confirm `request.shop` corresponds to a shop with an active, expected app installation/session before trusting `WebhookMetadata#shop`, or by including the shop domain in the signable string if Shopify's webhook signing scheme is changed to support it. Short of a protocol change, document explicitly that `request.shop` is unauthenticated and must never be trusted as a tenant boundary on its own.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook-eligible action (e.g., updates an order), causing Shopify to POST a legitimately-HMAC-signed webhook to the app's endpoint.
2. Attacker intercepts/logs this request, capturing `raw_body` and the valid `X-Shopify-Hmac-Sha256` value (both computed with the app's global `client_secret`).
3. Attacker resends the identical `raw_body`/`hmac` pair to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header successfully (`lib/shopify_api/webhooks/request.rb:20-23`), and `HmacValidator.validate` returns `true` because it only checks `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/webhooks/registry.rb:190`).
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), and the host app processes attacker-controlled data as belonging to the victim tenant.
