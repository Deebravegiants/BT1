Audit Report

## Title
CORS wildcard origin allowlist bypass via unanchored suffix match - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway HTTP server's `isAllowedOrigin` function validates wildcard CORS allowlist entries (e.g. `*.ethereum.org`) using `strings.HasSuffix(originHost, allowedHost)` without requiring a `.` label boundary before the match. This allows an attacker-registered domain like `evilethereum.org` to satisfy the suffix check for allowlist entry `*.ethereum.org`, causing the Gateway to reflect the attacker's origin into `Access-Control-Allow-Origin`.

## Finding Description
In `isAllowedOrigin`, the wildcard branch strips the `*.` prefix from the configured allowed origin to get `allowedHost` (e.g. `ethereum.org`), then checks only `strings.HasSuffix(originHost, allowedHost)`: [1](#0-0) . This check has no requirement that the matched suffix be preceded by a `.`, so any host string that merely ends with the same characters — not just true subdomains — passes (e.g., `evilethereum.org`, `notethereum.org`). The scheme and port checks performed earlier in the loop [3](#0-2)  do not mitigate this, since an attacker fully controls scheme and port of their own hosted origin. If `isAllowedOrigin` returns `true`, `handleRequest` reflects the raw `Origin` header value into the `Access-Control-Allow-Origin` response header: [2](#0-1) , granting the attacker's domain full CORS trust equivalent to a legitimately allowlisted subdomain.

## Impact Explanation
An operator configuring a wildcard CORS entry (e.g., `*.mycompany.com`) intends to trust only genuine subdomains of `mycompany.com`. Due to the missing boundary check, any attacker who registers a domain ending in the same string (e.g., `evilmycompany.com`) can have their origin accepted, and browsers will grant that malicious page permission to read cross-origin Gateway API responses from a victim who has credentials/session with the Gateway — a concrete CORS allowlist bypass and cross-origin response exposure issue, mapping to the in-scope "gateway request impersonation / allowlist bypass" category.

## Likelihood Explanation
Exploitation requires only that the Gateway operator has enabled CORS with at least one wildcard allowlist entry, a supported and documented configuration pattern (present in `core/scripts/gateway/sample_config.toml` and exercised by existing test suites). No authentication or privileged access is needed by the attacker — the exploit is a single crafted `Origin` header on an otherwise normal HTTP request, combined with registering a domain string and luring a browser with an active Gateway session to visit it.

## Recommendation
Anchor the wildcard suffix match to a label boundary or exact match:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```

## Proof of Concept
1. Configure Gateway with `CORSEnabled: true`, `CORSAllowedOrigins: ["*.ethereum.org"]`.
2. Send an HTTP request to the Gateway's configured `Path` with header `Origin: https://evilethereum.org`.
3. Observe `isAllowedOrigin` computes `allowedHost = "ethereum.org"` and `strings.HasSuffix("evilethereum.org", "ethereum.org")` evaluates `true`.
4. Observe response includes `Access-Control-Allow-Origin: https://evilethereum.org`.
5. This can be codified as a Go unit test in `core/services/gateway/network/httpserver_test.go`, following the pattern of `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`, asserting that origin `https://evilethereum.org` against allowlist `*.ethereum.org` incorrectly returns allowed.
