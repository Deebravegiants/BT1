### Title
Inadequate default permission in `instance()` lets an unregistered peer chain forge escrow redemptions — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.instance()` on the Tron variant of the Intent Gateway silently falls back to `address(this)` for any state machine that has never been explicitly registered via governance, instead of failing closed like the audited EVM implementation does. Since `authenticate()` (used to gate `RedeemEscrow`/`RefundEscrow`) trusts whatever `instance()` returns, any not-yet-configured chain is implicitly treated as a fully trusted peer sharing the gateway's deterministic CREATE2 address — an over-permissive default that lets a message "from" that address, dispatched from any never-registered state machine, pass authentication without ever going through the `NewDeployment` governance action.

### Finding Description
`_instance()` in the reference implementation fails closed: [1](#0-0) 

The Tron fork instead fails open: [2](#0-1) 

`authenticate()` only checks that `bytes20(request.from) == instance(request.source)`. When `request.source` is a state machine identifier that has never been the target of an explicit `NewDeployment` governance message (`_instances[keccak256(source)] == address(0)`), `instance()` returns `address(this)` — the gateway's own address — rather than reverting with `UnknownInstance`. This is precisely the class of bug the reference advisory describes: an actor who should have no standing (a chain the operator never onboarded) inherits access that was meant to be explicitly granted only through the `NewDeployment` code path documented here: [3](#0-2) 

Because Hyperbridge's Intent Gateway is deployed deterministically via CREATE2 so that the same contract address recurs across many EVM chains (explicitly called out in the codebase's own comments about preserving deterministic addresses), an attacker can permissionlessly redeploy an arbitrary contract at that same address on any chain that Hyperbridge has not yet whitelisted as a peer for this specific gateway instance, using any of the widely available deterministic deployment factories. They then dispatch a `PostRequest` from that chain with `source` = the unregistered state machine and `from` = the shared deterministic address. `authenticate()` passes because `instance(source)` defaults to `address(this)`, which equals `from`. Note that `RedeemEscrow`/`RefundEscrow` are gated only by `authenticate()`, not by the separate `keccak256(source) == hyperbridge` check that protects `NewDeployment`/`UpdateParams`/`SweepDust`: [4](#0-3) 

### Impact Explanation
An attacker satisfying the `authenticate()` check can submit a forged `RedeemEscrow`/`RefundEscrow` body, invoking `withdraw()` to release any tokens the gateway holds in escrow to an attacker-controlled beneficiary — concrete theft of user/solver funds held by the Tron `IntentGatewayV2`, reachable by a single crafted cross-chain message from an ordinary, permissionless deployment on an un-onboarded chain. This is a High severity, direct-fund-theft analog of the "inadequate permission settings" class in the reference advisory: access (here, "trusted peer" status) that should require an explicit governance grant is instead handed out by default.

### Likelihood Explanation
Likelihood is High for any deployment of this Tron contract that escrows real value: CREATE2 deterministic-address factories are permissionless and widely deployed across EVM-compatible chains, and Hyperbridge cannot pre-register every chain that might reuse the same salt/bytecode/address. Any chain the operator has not yet issued a `NewDeployment` for is exploitable the moment a relayer can get a proof of the forged message accepted by the local host (which only requires that the source chain state be verifiable, not that it be "approved" by governance for this gateway).

### Recommendation
Change `instance()` to fail closed exactly like `IntentsBase._instance()`: revert with `UnknownInstance()` (or equivalent) when `_instances[keccak256(stateMachineId)] == address(0)`, and require every peer — including same-address CREATE2 deployments — to be explicitly registered through `NewDeployment` before its messages are authenticated.

### Proof of Concept
1. Identify an EVM-compatible state machine identifier that Hyperbridge has not registered as a `NewDeployment` peer for the target Tron `IntentGatewayV2` instance.
2. Using a public CREATE2 deterministic deployer (e.g., the well-known `0x4e59b44847b379578588920cA78FbF26c0B4956` factory) with the same salt/bytecode used for the legitimate gateway, deploy an attacker-controlled contract on that unregistered chain at the same address as the Tron gateway (`address(this)`).
3. From that contract, dispatch a `PostRequest` through Hyperbridge with `source` = the unregistered chain, `from` = the shared deterministic address, `to` = the Tron gateway, and `body` = `RequestKind.RedeemEscrow` followed by an ABI-encoded `WithdrawalRequest` naming a commitment with escrowed tokens and an attacker beneficiary.
4. Once delivered and proven through the host, `onAccept` → `authenticate()` succeeds because `instance(source)` returns `address(this)` (fallback for the unregistered chain) which equals `from`; `_withdraw` releases the escrowed tokens to the attacker.

Note: I could not fully trace how `request.from` is populated on the non-EVM/Tron dispatch path in this indexed subset of the codebase (only the EVM-side `DispatchPost` struct was visible, without an explicit `from` field), so the exact mechanics of forging `from` on a given source chain should be verified directly against that chain's host/dispatcher implementation before treating this as fully confirmed.

    function authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        // IntentGateway only accepts incoming assets from itself or known instances
        if (instance(request.source) != module) revert Unauthorized();
    }
