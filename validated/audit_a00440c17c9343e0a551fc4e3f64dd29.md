### Title
POA Bridge withdrawal status matched by `assetId` only, causing wrong `txHash`/status to be reported for multi-withdrawal transactions of the same asset - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` looks up the on-chain withdrawal status by matching the POA Bridge API response solely on `assetId`, ignoring the withdrawal `index` that uniquely identifies which intent in a NEAR transaction the caller actually wants the status for.

### Finding Description
`describeWithdrawal` fetches the list of withdrawals for a NEAR tx hash and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, explicitly commenting that matching is done "by assetId instead of index" because the response list is unsorted. [1](#0-0) 

The equality this is supposed to preserve is: *the withdrawal entry returned for `WithdrawalIdentifier{index, assetId}` must be the specific intent at that `index` in the originating transaction.* Instead, the code only checks `assetId` equality and returns the first entry satisfying it, dropping `index` from the comparison entirely. `waitForWithdrawalCompletion.ts`'s own `findMatchingWithdrawal` documents the same known limitation: "Currently only matches by assetId (near_token_id). This means multiple withdrawals of the same token in a single transaction are not supported." [2](#0-1) 

If a NEAR transaction batches two POA-bridge withdrawal intents for the *same* `assetId` but to two *different* destination addresses/amounts (a legitimate case for multi-recipient batching, which `createWithdrawalIntents` does not prevent), then calling `describeWithdrawal` for `index: 1` can resolve to the API entry that actually belongs to `index: 0`'s withdrawal (or vice versa), because the underlying `withdrawals` array from the API is unsorted and the code performs no index/amount/destination cross-check.

### Impact Explanation
This breaks the "status reported that is not the on-chain outcome" invariant: a caller polling for withdrawal #1 can be told `{ status: "completed", txHash: <hash of withdrawal #0's on-chain transfer> }` while withdrawal #1 has not actually landed (or has landed with a different amount/destination). An integrator relying on this status to credit a user or mark a withdrawal as fulfilled could:
- incorrectly mark withdrawal #1 as completed using withdrawal #0's `transfer_tx_hash`, and
- potentially double-credit or credit the wrong destination.

### Likelihood Explanation
Requires the caller to submit multiple POA-bridge withdrawal intents for the identical `assetId` within one NEAR transaction, which is not explicitly disallowed by `createWithdrawalIntents`/`validateWithdrawal` in this file. No malicious relayer or admin behavior is needed — an ordinary user or integrator batching two withdrawals of the same token in one transaction (e.g., paying two recipients) triggers this by construction.

### Recommendation
Match by both `index` and `assetId` (or by amount + destinationAddress) rather than `assetId` alone, or reject/serialize batched same-asset withdrawals so each transaction contains at most one withdrawal per `assetId`.

### Proof of Concept
1. Submit a NEAR transaction with two POA-bridge `ft_withdraw` intents for `nep141:btc.omft.near`: intent index 0 to address A for amount X, intent index 1 to address B for amount Y.
2. Call `bridge.describeWithdrawal({ index: 1, withdrawalParams: { assetId: "nep141:btc.omft.near", destinationAddress: B, amount: Y, ... }, tx })`.
3. Because `findMatchingWithdrawal` only filters on `assetId` and the API's `withdrawals` array is unsorted, the function can return the entry for index 0 (address A, amount X) as "completed" with its `transfer_tx_hash`, even though the withdrawal to B has not completed. [3](#0-2)

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
