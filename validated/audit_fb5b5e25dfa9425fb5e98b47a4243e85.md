### Title
Orb-Relay client leaks the last signup/session state to any sender via unauthenticated `RequestState` messages - ([File: orb-relay-client/src/client.rs])

### Summary
The `PollerAgent::main_loop` function in `orb-relay-client` replays the last message it sent (`self.last_message`) to whoever requests it via a `RequestState` payload, but it does this *before* checking that the sender is the paired entity (`src.id == self.config.dst_id`). Any client able to address a `RequestState` message to an Orb's (or App's) relay queue can retrieve state data intended only for its legitimate, session-bound counterpart, mirroring the externally reported `Option.take()` bug class: a state-returning entry point that is reachable by anyone, without access control, before/regardless of the intended consumer using it.

### Finding Description
In `orb-relay-client/src/client.rs`, `PollerAgent::main_loop` processes incoming relay payloads like this: [1](#0-0) 

Note the ordering of the checks:
1. If the payload matches `self_serve::app::v1::RequestState`, the agent immediately replies with `self.last_message.clone()` — **no identity check is performed**.
2. Only in the `else if` branch is `src.id != self.config.dst_id` checked, and only for non-`RequestState` payloads.

`self.config.dst_id` is the identifier the client (whether acting as `Orb` or `App`) expects to be talking to — this is the "identity binding" mechanism between the paired Orb/App session: [2](#0-1) 

`last_message` holds the most recently sent protocol message — this can be things like `SignupEnded` (including `failure_feedback`, which reflects fraud/liveness outcomes), `CaptureStarted`/`CaptureEnded`, `AgeVerificationRequiredFromOperator`, or `AnnounceOrbId`: [3](#0-2) 

Because the `RequestState` branch is evaluated before the source-identity check, any entity that can deliver a `RequestState` payload to this client's relay stream — regardless of its `src.id` — receives a copy of the last outgoing state message. This is structurally identical to the reported `Option.take()` issue: a public/unauthenticated operation exposes internal state that should only be released to the legitimate, bound counterpart, and it can be invoked by anyone before (or instead of) the rightful consumer.

### Impact Explanation
An unauthenticated or unpaired actor able to reach the relay stream for a given Orb/App queue can extract the latest signup-related state (e.g., signup success/failure and fraud/liveness failure feedback, capture start/end events, orb/app pairing announcements) that was meant only for the specific paired counterpart of that session. This can lead to cross-signup/session state disclosure and misattribution — an attacker impersonating (or merely addressing traffic toward) another orb/app session can learn sensitive session-progress and fraud-outcome metadata without ever having been validated as that session's counterpart.

### Likelihood Explanation
The vulnerable branch is unconditionally reachable in the main relay message-processing loop for both `Orb`- and `App`-mode clients; it requires only sending a `RequestState`-typed payload targeted at the victim's relay queue, with no valid pairing/session credential enforced by this check. The barrier to exploitation depends only on relay-server-level routing permissions, not on any identity validation performed by this client code — the client-side defense that exists for every other message type is explicitly skipped here.

### Recommendation
Move the `src.id != self.config.dst_id` check ahead of the `RequestState` special-case (or apply it uniformly to all payload types, including `RequestState`), so that state is only replayed to the entity actually bound to this session. If `RequestState` needs to be honored before full pairing is established, explicitly document and scope why, and ensure `last_message` does not carry sensitive signup/fraud data until the requester's identity has been validated.

### Proof of Concept
1. Start an Orb-mode relay client with `dst_id = session_id_A` (paired to App session A) and let it send a `SignupEnded { success: false, failure_feedback: [...] }` message, which populates `last_message`.
2. From a different, unpaired client (`src.id != session_id_A`) connected to the same relay server, send a `self_serve::app::v1::RequestState {}` payload addressed to the Orb's queue.
3. Observe that `PollerAgent::main_loop` (orb-relay-client/src/client.rs, lines 436-440) replies with `self.last_message.clone()` to the unpaired sender, disclosing the `SignupEnded` failure feedback for session A, without ever checking that the requester's `src.id` matches `session_id_A`.
