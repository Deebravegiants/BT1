Audit Report

## Title
Missing sender/workflow allowlist check in gateway capabilities' legacy trigger dispatch permits unauthorized DON-wide fan-out - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`gateway.ProcessRequest` routes any request carrying a `DonID` to the legacy path via `HandleLegacyUserMessage`, which validates payload shape, timestamp presence, and staleness, but contains an explicit `// TODO: apply allowlist and rate-limiting here` comment and performs no sender/workflow authorization check before broadcasting the request to every node in the DON. This allows any client able to reach the gateway's user-facing HTTP port to trigger `web_api_trigger` messages against an entire DON without being verified against any allowlist.

## Finding Description
`HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` performs, in order: JSON payload decode, a check that `payload.Timestamp != 0`, and a staleness check comparing against `h.config.MaxAllowedMessageAgeSec`. Immediately after these checks, at line 384, the code contains `// TODO: apply allowlist and rate-limiting here`, and then proceeds directly to method validation (`msg.Body.Method != MethodWebAPITrigger`) and dispatch via `common.ValidatedRequestFromMessage` and `don.SendToNode`, iterating over every `member` in `h.donConfig.Members`. No sender identity, workflow-owner, or allowlist check exists anywhere in this function.

This handler is reached from `gateway.ProcessRequest` in `core/services/gateway/gateway.go`, which for legacy requests (those carrying a `DonID`) only calls `msg.Validate()` — a structural validation — before looking up the handler by `handlerKey = msg.Body.DonID` and invoking `h.HandleLegacyUserMessage(ctx, msg, callback)`. This entrypoint is bound to `gw_net.HTTPServer`, the internet/user-facing HTTP server, with no authentication or allowlist gate at the gateway layer either.

This contrasts with the newer `capabilities/v2` HTTP trigger flow (`http_trigger_handler.go`), which explicitly calls `h.authorizeRequest(ctx, workflowID, req, callback)` before dispatch, and with the vault capability's `allowListBasedAuth.AuthorizeRequest`, which fails closed (`errors.New("request not allowlisted")`) when a request digest isn't found in the allowlist. The legacy capabilities handler has no equivalent enforcement. The handler's own test suite in `handler_test.go` contains a corroborating `// TODO: Validate Senders and rate limit check` comment, confirming this is a known, unresolved gap rather than logic implemented elsewhere.

## Impact Explanation
Any unprivileged external client that can reach the gateway's user-facing HTTP port and knows/enumerates a valid `DonID` can submit a well-formed `web_api_trigger` legacy JSON-RPC message with a non-zero, non-stale timestamp. The handler broadcasts this to every node in `h.donConfig.Members` without verifying the sender is authorized for that DON, enabling unauthorized workflow-trigger execution across an entire DON. This maps to a missing/incorrect authorization (CWE-284/CWE-863) class issue, corresponding to the "gateway request impersonation" / "unauthorized job run" impact categories relevant to Chainlink's gateway trust model.

## Likelihood Explanation
The path is directly reachable from the exported, unauthenticated `gateway.ProcessRequest` entrypoint bound to the public user HTTP server. The only preconditions — a structurally valid message, a non-zero/non-stale timestamp, and a valid `DonID` — are all attacker-controlled or discoverable through configuration/trial requests, requiring no credentials, node access, or operator privileges. This is a low-barrier, repeatable exploit path.

## Recommendation
Add an explicit sender/workflow allowlist authorization check (and rate limiting) in `HandleLegacyUserMessage`, before calling `common.ValidatedRequestFromMessage`/`don.SendToNode`, following the fail-closed pattern used in `allowListBasedAuth.AuthorizeRequest` — reject requests whose sender/workflow owner is not found in a configured allowlist, treating missing/absent allowlist configuration as deny-by-default.

## Proof of Concept
1. Send an HTTP POST to the gateway's user-facing port with a JSON-RPC legacy request containing a known `DonID`, `Method: "web_api_trigger"`, a non-zero `Timestamp`, and an arbitrary `TriggerRequestPayload`.
2. `gateway.ProcessRequest` validates only `msg.Validate()` (structural) and routes to `handler.HandleLegacyUserMessage` based on `msg.Body.DonID`.
3. `HandleLegacyUserMessage` passes the timestamp/staleness checks, skips the (unimplemented) allowlist check at the `// TODO` marker, and forwards the request to every node in `h.donConfig.Members` via `don.SendToNode`, triggering workflow dispatch across the DON with no verification that the sender is permitted to do so.
