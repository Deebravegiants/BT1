Webhook shop identity spoofing via header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies covers only the raw request body — never the `shop`/`topic`/`webhook-id` headers. Any request whose body carries a validly-signed HMAC (e.g. a genuine webhook delivery for the attacker's own shop) can be replayed to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header, and the signature check will still pass, letting the attacker have their webhook data attributed to a different (victim) shop.

### Finding Description
`Request#hmac`/`#to_signable_string` binds the signature only to `@raw_body`: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from headers that are not part of the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate`/`validate_signature` only recomputes and compares the HMAC over `verifiable_query.to_signable_string` (the body), never over the headers: [3](#0-2) 

`Registry.process` checks that HMAC validation passes and then forwards `request.shop` verbatim into `WebhookMetadata` for the app's handler, with no additional binding check between the signed body and the claimed shop: [4](#0-3) [5](#0-4) 

This breaks the equality that should hold: `shop asserted by the HMAC-signed bytes == shop delivered to the handler`. In practice the equality is `shop(header) ⊄ signed(body)`, so the header can be changed freely by anyone who can produce (or replay) a validly-signed body, without invalidating the signature.

### Impact Explanation
A merchant who has installed the app is a normal, unprivileged recipient of genuine Shopify webhook deliveries signed with the app's shared secret for their *own* shop. That merchant can capture one of their own legitimately-signed webhook bodies and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header to claim it belongs to a different, victim shop. Because the header is outside the HMAC boundary, `Registry.process` still succeeds and calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain and the attacker-controlled body. Any app logic that trusts `data.shop` to select which merchant's records to create/update/delete (a very common pattern per the gem's own docs example) can then be tricked into cross-tenant data injection or corruption attributed to the victim shop — this is a cross-tenant access issue.

### Likelihood Explanation
Any embedded/public app merchant can trigger this without additional secrets: they only need one authentic webhook delivery for their own shop (which every installed app receives routinely) and the ability to POST to the app's public webhook callback URL with modified headers. No access token, `client_secret`, or privileged account is required — the shared HMAC secret validity comes from Shopify's own legitimate delivery to the attacker's shop, not from the attacker possessing the secret.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is verified, e.g. include the `shopify-shop-domain` header in the signable string, or independently verify that the shop claimed in the header matches shop-scoped data already known to the app (such as an existing session/installation record) before trusting `WebhookMetadata#shop`. At minimum, document and enforce that consumers must re-validate `data.shop` against their own installation records rather than treating it as authenticated by the HMAC check.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and receives a legitimate webhook, e.g. `orders/create`, with body `B` and a valid `x-shopify-hmac-sha256` computed over `B` using the app's shared secret.
2. Attacker resends the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` recomputes the HMAC solely over `B` and it matches (per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`), so `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`).
4. Any handler logic keyed off `data.shop` now operates as if the (attacker-controlled) body content came from the victim shop.
