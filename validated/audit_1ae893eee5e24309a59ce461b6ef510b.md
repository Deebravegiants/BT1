## No vulnerability found for this question.

**Reasoning:** The premise that a TON Connect wallet extension uses the raw string's bounceable/testnet flag bits to alter its own hash construction is incorrect for this codebase's scope, and the equality the question claims is broken does not actually diverge.

`computeTonConnectHash` in `packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts` deliberately hashes only `parsedAddress.workchainId` and `parsedAddress.address` (the 32-byte hash), explicitly excluding the tag byte that encodes bounceable/non-bounceable and mainnet/testnet flags: [1](#0-0) 

This matches the documented TON Connect `sign-data` hash specification in the same file's comment block, which defines the hash as `workchain_id (4 bytes) + address (32 bytes) + ...` with no tag/flag bits included: [2](#0-1) 

`tryParseTonAddress` in `packages/intents-sdk/src/lib/ton-address.ts` explicitly notes this design: the tag byte is exposed for validation purposes but the hash-relevant identity is only `(workchainId, address)`: [3](#0-2) 

This is not an SDK-side bug but a faithful implementation of the actual TON Connect `sign-data` protocol, which any compliant wallet extension also follows — meaning the wallet that produces the signature also normalizes the address to `(workchain, hash)` before hashing, and does not feed raw flag bits into its hash. This is confirmed by the repo's own cross-validation tests against the reference `@ton/core` library, which agree that all bounceable/non-bounceable/testnet/mainnet encodings of the same account produce the same `(workchainId, address)` pair and thus the same hash: [4](#0-3) [5](#0-4) 

Since the SDK's hash construction matches the real TON Connect wallet's hash construction (both use only workchain + 32-byte hash, never the tag/flag bits), there is no divergence between `computeTonConnectHash`'s output and what a TON Connect wallet actually signs. The claim that "the actual wallet extension used the raw string's flag bits to alter which bytes it fed into its own hash construction" is a speculative assumption about third-party wallet internals with no support in this repo, and per the rules, defects/trust assumptions about third-party SDKs with no path through this repo are out of scope. The equality `computeIntentHash(multiPayload) == intent_hash` holds for any valid address encoding of the same account, so `waitForIntentSettlement` matching is unaffected.
