### Title
Webhook HMAC signs only the raw body, letting a valid signature from one shop be replayed with a spoofed `shop-domain` header to achieve cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated request headers. `Registry.process` validates the HMAC over the body only and then trusts the header-derived `shop` value to build the `WebhookMetadata` handed to the app's handler. The binding "HMAC-verified bytes == the tenant the app acts on" does not hold: the signature verifies the body, but the code acts on a `shop` value that was never covered by that signature.

### Finding Description
`AuthQuery` and other `VerifiableQuery` implementations sign every semantically important field (`code`, `host`, `shop`, `state`, `timestamp`), as shown in `lib/shopify_api/auth/oauth/auth_query.rb#to_signable_string`: [1](#0-0) 

But `Webhooks::Request` implements the same `VerifiableQuery` interface with `to_signable_string` returning only `@raw_body`: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from headers that are excluded from the signable string: [3](#0-2) 

`HmacValidator.validate` computes and compares the HMAC only over `to_signable_string`, i.e. the body: [4](#0-3) 

`Registry.process` gates on this HMAC check and then immediately trusts `request.shop`/`request.topic` (unauthenticated header values) to construct the metadata delivered to the app's business logic: [5](#0-4) 

Because the header values are never part of the signed material, any `(raw_body, hmac)` pair that is valid for one shop remains a byte-for-byte valid signature no matter what `shop-domain`, `topic`, `webhook-id`, or `api-version` headers are sent alongside it. An attacker who controls any shop that has the target app installed can:
1. Install the app on their own (free) development store.
2. Trigger a webhook of their choosing (e.g. by editing an order) to obtain a genuine `raw_body` + `X-Shopify-Hmac-Sha256` pair signed with the app's real `client_secret` — obtainable from their own webhook delivery logs in the Partner Dashboard, without ever needing the `client_secret` itself.
3. Replay that exact body + HMAC directly to the app's public webhook endpoint, substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) with a victim shop's domain.

The HMAC check in `Registry.process` still passes (it only validates the body), and the handler receives `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This breaks the equality "bytes verified by HMAC == tenant identity acted upon." Any consumer relying on `WebhookMetadata#shop` to route webhook data (create/update local records, trigger side effects, or select a stored access token/session for the corresponding shop) can be made to process attacker-crafted payloads under a victim shop's identity — a cross-tenant integrity/confusion issue reachable by any unprivileged internet user who can install the app on a store they control.

### Likelihood Explanation
High. Any internet user can install a public Shopify app on a free development store, capture a legitimately-signed webhook body/HMAC pair from their own webhook logs, and resend it to the app's endpoint with a forged shop header — no access token, `client_secret`, or privileged account is required.

### Recommendation
Include the trusted identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before validation, so a signature computed for one shop/topic cannot be replayed with different header values.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and captures a legitimate webhook delivery: `raw_body = B`, header `X-Shopify-Hmac-Sha256 = H` (valid for secret `S`).
2. Attacker sends:
```
POST /webhooks HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: H
X-Shopify-Shop-Domain: victim-shop.myshopify.com

B
```
3. `HmacValidator.validate` recomputes HMAC over `B` only (per `to_signable_string`), matches `H`, and returns `true`.
4. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and dispatches it to the app's handler as if it were a genuine webhook from `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
