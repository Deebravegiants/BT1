### Title
Emporium stateless operations can grant unlimited ERC20 approvals from the shared contract, enabling theft of other users' in-flight funds - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
Any unprivileged user who submits a normal, self-funded Hinkal `transact()` call can route an `Emporium` external action whose `EmporiumStack` contains a stateless `EmporiumOperation` (`invokeWallet == false`, `signerAddress == address(0)`). In that mode `EmporiumUpgradeable.runAction` executes `op.endpoint.call{value: op.value}(op.callData)` directly from the `Emporium` contract itself, with no restriction on `op.endpoint` and no selector filter beyond blocking `callHinkalWallet`/`doSendToRelay`. An attacker can therefore make `Emporium` call `approve(attacker, type(uint256).max)` on any ERC20 token, minting itself a permanent, unlimited allowance over `Emporium`'s own balance of that token.

### Finding Description
`EmporiumUpgradeable.runAction` handles two execution modes for each `EmporiumOperation` in a signed/committed `EmporiumStack`: [1](#0-0) 

For "CASE 2: Stateless Interaction" (the default path whenever `invokeWallet` is false or `signerAddress == address(0)`), the contract performs an arbitrary low-level `call` to `op.endpoint` with attacker-chosen `callData`, executing with `msg.sender == address(Emporium)`. The only guard is a selector blacklist that blocks `callHinkalWallet`/`doSendToRelay` selectors, not arbitrary ERC20 admin functions such as `approve`.

When `stack.signerAddress == address(0)`, `verifyWallet` returns immediately without any EIP-712 signature check, since that check is only meant to protect `HinkalWallet`-routed (stateful) operations: [2](#0-1) 

Because the entire `EmporiumStack` (including `ops`) is embedded in `circomData.externalActionData.externalActionMetadata`, which is committed via `calldataHash`/`signedMessageHash` and checked by `performHinkalChecks`, the *attacker's own* transaction is "authorized" in the sense that they proved ownership of their own spent UTXOs. However, the *effect* of the op — an ERC20 `approve()` call issued in `Emporium`'s own name — is not scoped to the attacker's own funds. It permanently grants the attacker (or any address they choose) an allowance over whatever balance of that token the shared `Emporium` contract holds, now or in the future.

Critically, the contract's own code acknowledges that `Emporium` can legitimately hold residual/in-flight token balances across transactions — this is exactly the case the `balanceChange < 0` branch anticipates: [3](#0-2) 

Any tokens sitting in `Emporium` at that moment — dust from previous stateless ops, in-flight funds from a multi-op batch belonging to a different user, or funds temporarily parked mid-sequence — become claimable by the attacker's dangling approval via a plain `token.transferFrom(emporium, attacker, amount)` call, executed completely outside of `Hinkal.transact()`. This bypasses every balance-equation check the protocol performs (`slippageValues` check in `Hinkal.sol`, `BalanceChangeShouldBePositive` in `Emporium`), since those checks only run during the attacker's original transaction, not at the time of the later `transferFrom` drain.

### Impact Explanation
This is Critical: it enables **direct theft of shielded/in-flight user funds** that transiently reside on the shared `Emporium` contract, with no nullifier, no proof, and no signer authorization required for the actual drain step. The approval, once granted, is a standing backdoor that can be exercised at any future point whenever the shared contract accumulates any balance of the approved token — a value-moving capability entirely outside Hinkal's UTXO/nullifier/balance-diff accounting.

### Likelihood Explanation
Any unprivileged EOA can trigger this using only their own funds and a normal, valid ZK proof for a self-contained transaction — no admin, relayer, or victim cooperation is needed. The only requirement is that `Emporium` at some point later holds a non-zero balance of the targeted token (explicitly anticipated by the contract's own comments and `balanceChange < 0` handling), making this readily exploitable by simply front-running or waiting for such a state.

### Recommendation
- Restrict stateless (`invokeWallet == false`) `EmporiumOperation` endpoints/selectors to a safe allowlist (e.g., only permit calls that cannot leave a standing state change like `approve`, `permit`, `setApprovalForAll`, `transferOwnership`, etc.), or require `approve` calls to be reset to zero / scoped to a single-use spender within the same transaction.
- Alternatively, ensure `Emporium` never legitimately retains a balance across transactions (sweep 100% of balance to `msg.sender`/UTXO on every call, disallowing the `balanceChange < 0` carry-over case), and add a blacklist of dangerous function selectors (`approve`, `increaseAllowance`, `setApprovalForAll`, `permit`) for stateless ops in addition to the existing `callHinkalWallet`/`doSendToRelay` blacklist.

### Proof of Concept
1. Attacker deposits/owns some shielded UTXO in Hinkal (their own funds, arbitrary token).
2. Attacker crafts `circomData.externalActionData` targeting `Emporium`, with `externalActionMetadata` = ABI-encoded `EmporiumStack` containing one `EmporiumOperation`:
   - `endpoint = <victimToken>`
   - `invokeWallet = false`
   - `value = 0`
   - `callData = abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)`
   - `stack.signerAddress = address(0)` (skips EIP-712 signature entirely per `verifyWallet`).
3. Attacker generates a valid ZK proof for their own transaction (spending only their own UTXO) and calls `Hinkal.transact(...)`.
4. `Hinkal._externalTransact` calls `Emporium.runAction`, which executes CASE 2 and issues `victimToken.approve(attacker, type(uint256).max)` from `address(Emporium)`.
5. At any later time when `Emporium` holds any balance of `victimToken` (e.g., dust from another user's op, or a multi-op batch mid-flight), the attacker calls `victimToken.transferFrom(emporium, attacker, amount)` directly — no Hinkal proof, no nullifier, no signer check involved — draining those funds.
