Audit Report

## Title
Missing MessageID uniqueness check in `HandleLegacyUserMessage` allows callback-registration collision and cross-user response confusion in the legacy Web API trigger handler - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`handler.HandleLegacyUserMessage` stores a pending callback keyed only by the client-supplied `msg.Body.MessageID` without checking for an existing in-flight entry under that key, unlike every analogous registration path in the gateway (`httpTriggerHandler.setupCallback`, confidentialrelay's `newActiveRequest`, vault's `newActiveRequest`, and `requestcache`'s sender-scoped cache). Since `MessageID` is fully attacker-chosen (only length/format-validated, never checked for uniqueness before this call), two overlapping legacy requests using the same `MessageID` can collide, causing one requester's DON response to be delivered to a different requester's callback while the original caller's request silently hangs until pruned.

## Finding Description
`HandleLegacyUserMessage` unconditionally overwrites the map entry: [4](#0-3) 

The response path matches solely on `MessageID` and delivers to whichever callback currently occupies that key: [5](#0-4) 

`MessageID` is a body field set entirely by the caller/signer (e.g. via `Sign`/`SignKS`), and is validated only for length and null-byte suffix, not uniqueness: [1](#0-0) 

The HTTP entrypoint `gateway.ProcessRequest` calls `msg.Validate()` (length/signature checks only) and then dispatches straight into `h.HandleLegacyUserMessage` via `multiHandler.HandleLegacyUserMessage`, with no request-cache or dedup layer in between for this legacy path: [2](#0-1) [3](#0-2) 

This confirms the collision is reachable: any two unprivileged callers (or the same caller twice) choosing the same `MessageID` value will collide in `h.savedCallbacks`. Other equivalent code paths in the codebase (`http_trigger_handler.go` setupCallback, confidentialrelay and vault handlers' `newActiveRequest`, and `requestcache.go`) all explicitly reject the second registration attempt when an ID is already in-flight, showing this is a recognized invariant that this handler alone fails to enforce.

## Impact Explanation
This is a genuine cross-user response confusion bug on an unprivileged, network-reachable gateway entry point (the legacy Web API trigger HTTP endpoint). A malicious client can:
1. Force another in-flight requester's trigger response to be delivered to itself instead of to the rightful caller (response leakage/misdelivery across users).
2. Cause the rightful caller's request to hang until `pruneCallbacks` expires it (up to `CallbackMaxAgeSec`, default 120s) — a bounded but real per-request denial-of-service.

This maps to the in-scope "cross-user response corruption" impact category referenced in the rules. Severity is moderate: it requires the victim's request and the attacker's colliding request to be in-flight concurrently and the attacker to guess/choose the exact `MessageID` used by the victim (or convince/observe it), but the check itself is objectively absent compared to every sibling handler.

## Likelihood Explanation
Exploitability requires the attacker to know or predict a legitimate in-flight `MessageID`. Since `MessageID` is fully attacker/sender-chosen (up to 128 chars, only format-validated) and there is no per-sender scoping (unlike `requestcache.go`'s `globalID{sender, id}` key), an attacker controlling their own client can trivially self-collide by reusing IDs across two of their own concurrent requests, and can also collide with a victim if the victim's client uses a predictable/low-entropy ID scheme (e.g., timestamps, counters) or if the ID is otherwise observable. Practical impact against a specific victim depends on the victim's ID entropy, which is outside this handler's control, but the missing uniqueness guard is a concrete, code-level defect that any unprivileged caller can trigger without special credentials.

## Recommendation
In `HandleLegacyUserMessage`, before inserting into `h.savedCallbacks`, check for an existing entry under the key and reject with a conflict error if found, mirroring `httpTriggerHandler.setupCallback`'s pattern. Ideally scope the key by sender (e.g., `{sender, messageID}`) similar to `requestcache.go`'s `globalID`, since `msg.Body.Sender` is already populated by `Message.Validate()`'s `ExtractSigner` call.

## Proof of Concept
1. Client A submits a legacy `web_api_trigger` request with `MessageID = "X"`; `HandleLegacyUserMessage` stores `savedCallbacks["X"] = callbackA` and forwards to DON members.
2. Before any DON node responds, Client B (or the same client) submits another legacy request with `MessageID = "X"`; this overwrites `savedCallbacks["X"] = callbackB` since no existence check occurs at `handler.go:411-412`.
3. A DON node responds for `MessageID = "X"` (originally intended for A's request); `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, deletes the entry, and delivers A's response payload to B via `callbackB.SendResponse(...)`.
4. `callbackA`'s HTTP caller (Client A) never receives a response and hangs until `pruneCallbacks` evicts the stale entry after `CallbackMaxAgeSec` (default 120s).

A Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go` can construct two `api.Message`s with identical `Body.MessageID`, call `HandleLegacyUserMessage` twice with distinct callbacks, then invoke `HandleNodeMessage`/`handleWebAPITriggerMessage` and assert that the second callback (not the first) receives the response.
