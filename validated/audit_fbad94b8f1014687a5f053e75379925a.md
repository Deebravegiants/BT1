### Title
Webhook `shop`, `topic`, and `webhook_id` are not covered by the HMAC, enabling cross-tenant webhook spoofing via header substitution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the **raw body only**, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and process the webhook are taken directly from unauthenticated HTTP headers. An unprivileged internet user who can obtain one genuinely-signed `(raw_body, hmac)` pair (e.g. from a webhook delivered to their own shop/app installation, or leaked/logged webhook traffic) can replay it to the app's public webhook endpoint with the `shop-domain`/`topic`/`webhook-id` headers rewritten to any value they choose, and `Registry.process` will accept it as authentic for the spoofed shop/topic because those fields are never part of the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC solely against `verifiable_query.to_signable_string`, i.e. the raw body — never the `shop`, `topic`, or `webhook_id` headers: [2](#0-1) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from request headers with no cryptographic binding to the body or to the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC once, then trusts `request.topic`, `request.shop`, `request.webhook_id`, and `request.api_version` unconditionally to dispatch and construct `WebhookMetadata` for the handler: [4](#0-3) 

The equality the code implicitly assumes is:
`HMAC_secret(raw_body) == received_hmac` ⇒ `(shop, topic, webhook_id)` in the headers are authentic.

That equality does not hold: the HMAC only proves the raw body was produced by an entity that knows `api_secret_key` (Shopify) for *some* delivery; it proves nothing about which shop, topic, or webhook the headers claim. Any client capable of reaching the app's public webhook HTTP endpoint (which must be internet-reachable for Shopify to deliver to it) can pair a validly-signed body with attacker-chosen identity headers.

### Impact Explanation
This breaks the shop/topic identity binding at the heart of multi-tenant webhook processing. A host application (using this gem exactly as documented, via `Registry.process`) that keys any downstream action, cache entry, session lookup, or data write off `WebhookMetadata#shop` or `#topic` can be made to attribute attacker-supplied or replayed body content to a victim shop, since the library provides no protection against header substitution once a single valid `(raw_body, hmac)` pair is known for the app's shared secret. This constitutes cross-tenant confusion/access at the identity layer the gem is responsible for validating, matching the Critical "cross-tenant access" category — the vulnerability lives entirely in this gem's `Webhooks::Request`/`Registry` design, not in host-application misuse.

### Likelihood Explanation
Obtaining one legitimate `(raw_body, hmac)` pair is realistic: it requires only owning/operating any single shop with the target app installed (an unprivileged, ordinary developer/merchant action — not access to `api_secret_key` or any privileged credential), or observing a delivered webhook in transit/logs. The webhook endpoint is by necessity a public, unauthenticated HTTP endpoint. No `client_secret`, access token, or privileged account is required to perform the header-substitution replay itself.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable material that the HMAC is computed and verified over, or otherwise cryptographically bind them to the body (e.g., verify body-declared identifiers such as embedded `admin_graphql_api_shop_id`/expected shop against the header before dispatch). At minimum, document and enforce that `Registry.process` must reject topics/shops it did not itself register as expected for the delivering credentials, rather than trusting header values unconditionally after a body-only HMAC check.

### Proof of Concept
```ruby
# Attacker owns/operates Shop A with the app installed, and receives one real webhook:
raw_body = '{"id": 1}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
# (Attacker legitimately obtains this pair for shop-a.myshopify.com / orders/create)

# Attacker replays same body+hmac against the victim app endpoint,
# substituting shop-domain and topic headers -- HMAC still validates:
headers = {
  "x-shopify-topic" => "shop/redact",          # arbitrary topic, attacker's choice
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed shop
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) succeeds (HMAC only checks raw_body)
# => handler.handle is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "shop/redact", ...)
```
