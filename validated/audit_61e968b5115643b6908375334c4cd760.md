### Title
Missing allowlist and rate-limiting enforcement in `HandleLegacyUserMessage` allows unrestricted broadcast to entire DON - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
`handler.HandleLegacyUserMessage` in the gateway's capabilities handler is the entry point for unprivileged, internet-facing client requests targeting `web_api_trigger` workflows. The function performs payload decoding and staleness checks, but explicitly skips the allowlist and rate-limiting step it documents as required, then unconditionally fans the raw user request out to every member of the DON.

### Finding Description
The handler validates payload structure and message freshness, but the code contains an explicit, unaddressed gap:

```go
// TODO: apply allowlist and rate-limiting here
if msg.Body.Method != MethodWebAPITrigger {
``` [1](#0-0) 

Immediately after this unguarded check, the request is forwarded to every DON member with no gating on sender identity or request volume:

```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()

// Send original request to all nodes
for _, member := range h.donConfig.Members {
    err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
}
``` [2](#0-1) 

The handler's `nodeRateLimiter` field is only consulted on the outbound path (node→external HTTP), not for this inbound user-triggered path:

```go
func (h *handler) handleWebAPIOutgoingMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.lggr.Debugw("handling webAPI outgoing message", "messageId", msg.Body.MessageID, "nodeAddr", nodeAddr)
	if !h.nodeRateLimiter.Allow(nodeAddr) {
``` [3](#0-2) 

This is structurally analogous to the `OmoRouter.mint()` bug class: the function's documented/intended pre-forwarding step (allowlist + rate-limit check) is omitted, so the downstream fan-out ("mint on the vault" ≈ "broadcast to the DON") proceeds without the safeguard it depends on. Actual sender authorization for the triggered workflow only happens later, per-workflow, inside the node-side `triggerConnectorHandler.processTrigger`, which checks `trigger.allowedSenders[sender.String()]` and a per-workflow `rateLimiter` [4](#0-3) . That downstream check mitigates unauthorized workflow execution, but it does not prevent the gateway from indiscriminately broadcasting every incoming legacy user message to all DON members with no volume control, since the rate limiter invoked there is per-registered-workflow and only reached after the message has already been dispatched network-wide.

### Impact Explanation
Because the gateway-level allowlist/rate-limit gate is missing, any unauthenticated network caller reaching this legacy endpoint can flood every member of the DON with signed-but-unfiltered messages, consuming node processing/network resources and callback-tracking memory (`h.savedCallbacks`) before any per-workflow sender/rate check is applied. This is a quota-bypass condition at the gateway ingress tier that the code's own TODO acknowledges is unaddressed.

### Likelihood Explanation
Likelihood is Medium: reaching this code path only requires sending a validly-signed `web_api_trigger` legacy message to the gateway's public endpoint; no privileged access or additional bypass is needed since the allowlist/rate-limit step was never implemented at this layer.

### Recommendation
Implement the allowlist and rate-limiting check called out by the TODO in `HandleLegacyUserMessage` before the request is persisted in `savedCallbacks` and fanned out to `donConfig.Members`, mirroring the `nodeRateLimiter` pattern already used for the outgoing path.

### Proof of Concept
1. Craft a validly-signed legacy `api.Message` with `Method = MethodWebAPITrigger` and a fresh `Timestamp`.
2. Repeatedly submit it through the gateway's legacy user-message ingress.
3. Observe that `HandleLegacyUserMessage` performs no allowlist/rate-limit rejection and forwards each message to every DON member (`don.SendToNode` loop), regardless of sender or request rate, confirming the missing gating step described in the code comment.
