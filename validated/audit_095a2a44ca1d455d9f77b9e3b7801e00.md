### Title
Missing shop-domain validation in `TokenExchange.exchange_token` allows the app's `client_secret` to be sent to an attacker-influenced host - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the token-exchange target host directly from the JWT session token's `dest` claim and never runs it through `Utils::ShopValidator.sanitize!`, unlike every other credential-issuing method in the same module and its sibling files. This breaks the identity binding that the rest of the gem enforces between "the host that is proven to be a legitimate Shopify shop domain" and "the host that receives the app's `client_secret`."

### Finding Description
`JwtPayload#shop` returns the raw `dest` claim of the session token with only `https://` stripped, with no restriction to Shopify's trusted domain suffixes: [1](#0-0) 

`JwtPayload#initialize` only validates `aud` against `Context.api_key`; it performs no validation of `dest`/`iss` against a trusted-domain allowlist: [2](#0-1) 

`exchange_token` takes this unvalidated value (`dest_shop = jwt_payload.shop`) and uses it, unsanitized, both to build the `Session` whose `shop` becomes the HTTP host and to receive the response: [3](#0-2) [4](#0-3) 

That `Session#shop` is fed directly into `HttpClient`, which builds the outbound request host from it with no further validation: [5](#0-4) 

The request body posted to that host includes `Context.api_secret_key` (the app's `client_secret`): [6](#0-5) 

By contrast, every sibling credential-granting method in the same file, and in the adjacent auth modules, explicitly sanitizes the shop before it is allowed to become the request host: [7](#0-6) [8](#0-7) [9](#0-8) 

`ShopValidator.sanitize!` exists precisely to enforce that a shop string resolves to one of a small set of trusted Shopify domains (`myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, `shopify.com`) before it is trusted as a network destination: [10](#0-9) [11](#0-10) 

This is the same bug class as the external report: a value that determines which "version"/tenant-scoped resource is acted upon (there, the PDA/account tied to `root_state.version`; here, the network host tied to the shop's trust domain) is used without re-deriving/re-checking it against the value that is supposed to be authoritative for that binding. The equality that should hold and is not checked is:

`host_used_for_client_secret_request == ShopValidator.sanitize!(jwt_payload.dest)`

but the code instead uses `host_used_for_client_secret_request == jwt_payload.dest` unchecked.

### Impact Explanation
If the `dest` claim value can ever diverge from a genuine, Shopify-issued `*.myshopify.com` / `*.myshopify.io` / `*.spin.dev` / `*.shop.dev` host — for example if a host application forwards a session token that was not itself strictly validated upstream, or if the claim contains an unexpected value (malformed host, embedded credentials in the URI, or a value picked up from an untrusted source before being wrapped as a session token) — `exchange_token` will happily construct an HTTPS request to that literal host and place the app's `client_id`/`client_secret` in the POST body. This is a credential-leakage / SSRF-with-credentials primitive: the app's `client_secret` is sent to a host that was never confirmed to be a legitimate Shopify tenant domain, whereas the maintainers clearly intended (as shown by the parallel `sanitize!` calls in `client_credentials`, `refresh_token`, and `migrate_to_expiring_token`) for this check to gate every code path that turns a caller-influenced shop identifier into a network destination for the client secret.

### Likelihood Explanation
Moderate-to-low on its own because the JWT is HMAC-signed with `api_secret_key`, so a value in `dest` is normally only ever set by Shopify itself. However, likelihood is elevated by the fact that this is the *only* credential-issuing path in the module that skips the check that all its siblings perform — i.e., it's a straightforward oversight/regression relative to the rest of the file, not a deliberate design decision, making it a real gap in the defense-in-depth that this library otherwise consistently applies to every other shop-derived host.

### Recommendation
Sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` immediately after extracting it from the JWT payload in `exchange_token`, exactly as `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token` already do, before it is used to construct `shop_session` or included in the `Session.from` call:
```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```

### Proof of Concept
1. Configure the gem as an embedded app (`Context.embedded? == true`).
2. Obtain/construct a session token whose `dest` claim is not a trusted Shopify domain (e.g., `https://attacker.example.com`) — via any path where the token consumer does not itself pre-validate the `dest` claim before invoking this API (e.g., token forwarded from a component that trusts `dest` at face value).
3. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
4. Observe that `Clients::HttpClient` builds the request to `https://attacker.example.com/admin/oauth/access_token` and the POST body contains `client_id` and `client_secret: Context.api_secret_key`, per [6](#0-5)  and [5](#0-4) , with no `ShopValidator.sanitize!` check ever executed — unlike the identical flow in `client_credentials.rb` / `refresh_token.rb` where such a call is present and would raise `Errors::InvalidShopError` for the same input.
