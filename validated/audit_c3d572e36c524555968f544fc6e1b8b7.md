Confirmed: this is a real vulnerability. The HMAC signature in this gem only covers the raw request body — `Request#to_signable_string` returns `@raw_body` alone, with no header data mixed in — and `Registry.process` never validates or sanitizes `request.shop` against anything.Given the confirmed code paths, I have enough to render a verdict.

### Title
Webhook HMAC signs only the request body, letting an attacker's own validly-signed webhook be replayed with an arbitrary `X-Shopify-Shop-Domain` to impersonate any tenant - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` verifies the HMAC solely against that body string; the `shop-domain` header is never included in the signed payload nor separately validated. `Registry.process` then passes `request.shop` straight into `WebhookMetadata` with no sanitization, so any attacker who can produce one validly-signed webhook body (e.g. from their own installed test shop) can replay that exact body/HMAC pair to the host app's endpoint with the `X-Shopify-Shop-Domain` header rewritten to any string they choose, and the gem will accept it as authentic for that arbitrary tenant.

### Finding Description
The claimed binding is: `shop_authenticated == shop_acted_on(request.shop)`. Tracing the code shows this binding is broken by construction:

- `Request#hmac` reads the `hmac-sha256` header and `Request#to_signable_string` returns `@raw_body` only [1](#0-0) .
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC — i.e., it authenticates the body bytes only, never the headers [2](#0-1) .
- `Registry.process` calls `Utils::HmacValidator.validate(request)`, and on success immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and hands it to the handler, with no check that `request.shop` corresponds to the shop that actually produced the signed body [3](#0-2) .
- `Request#shop` is a raw, unvalidated read of the `shop-domain` header [4](#0-3) .

Exploit flow: the attacker creates their own development/test shop, installs the app, and lets Shopify deliver one legitimate webhook to the app's callback URL (a real, validly-signed body + HMAC for topic `T` with body `B`). The attacker then sends their own HTTP POST directly to the same webhook endpoint, with identical body `B` and identical `X-Shopify-Hmac-Sha256` header, but replaces `X-Shopify-Shop-Domain` with any arbitrary string, including a nonexistent or victim-looking domain such as `admin.myshopify.com`. Because the signature never covered the shop-domain header, `HmacValidator.validate` still returns `true`. `Registry.process` proceeds to call the handler with `WebhookMetadata#shop` equal to the attacker-chosen string, which the host app (per documented gem usage) trusts to select which tenant's data row to write/read.

None of the existing guards intervene: `HmacValidator.validate` only checks the body signature; there is no `ShopValidator.sanitize!` call anywhere in `Registry.process` or `Request`; `state`/OAuth CSRF checks and `JwtPayload`'s `aud`/`dest` checks are unrelated code paths for App Bridge session tokens, not webhooks; `Context.setup?`/`private?`/`embedded?` are configuration flags unrelated to webhook shop binding.

### Impact Explanation
This allows cross-tenant impersonation in a webhook-processing host app: any unprivileged attacker who can obtain one validly-signed webhook (trivially available by installing the app on their own free development shop) can replay it with a forged `shop` value to have the handler read/write data keyed to an arbitrary tenant identifier of the attacker's choosing — not limited to real merchants, and repeatable indefinitely against any string. This matches the Critical category "cross-tenant access."

### Likelihood Explanation
Preconditions are minimal and entirely within attacker capability as defined: the attacker needs no secrets, just the ability to install the app on a shop they control (which the threat model explicitly grants) to harvest one real signed body/HMAC pair, and the ability to send arbitrary HTTP requests to the app's public webhook endpoint (also explicitly granted). The cost per exploit attempt is a single HTTP POST with a modified header; it is fully repeatable and requires no ongoing access to the harvested shop.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed payload, or independently verify that the `shop-domain` header corresponds to a shop actually known/installed by the host app (e.g., look up an existing session/access token for that shop before trusting it), rather than trusting an unauthenticated header value. At minimum, document/require that `WebhookMetadata#shop` must never be trusted without an independent shop-record lookup, and consider binding the callback path itself (per-shop unique URL) or validating source IP ranges as defense in depth. This must be fixed in `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_process_trusts_forged_shop_domain_header_despite_valid_hmac
  body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

  forged_headers = {
    "x-shopify-topic" => @topic,
    "x-shopify-hmac-sha256" => Base64.encode64(hmac), # valid signature, unrelated to shop header
    "x-shopify-shop-domain" => "admin.myshopify.com",  # attacker-chosen, not a real installed shop
    "x-shopify-webhook-id" => "attacker-chosen-id",
    "x-shopify-api-version" => "2024-01",
  }

  forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

  # Binding LHS: shop_authenticated (none - HMAC never covers shop header)
  # Binding RHS: shop_acted_on = request.shop
  assert_equal("admin.myshopify.com", forged_request.shop)
  assert(ShopifyAPI::Utils::HmacValidator.validate(forged_request)) # HMAC still validates

  captured_shop = nil
  handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| captured_shop = data.shop })
  ShopifyAPI::Webhooks::Registry.add_registration(topic: @topic, path: "path", delivery_method: :http, handler: handler)

  ShopifyAPI::Webhooks::Registry.process(forged_request)

  # Handler received the attacker-forged, unauthenticated shop value with no sanitization
  assert_equal("admin.myshopify.com", captured_shop)
end
```
This demonstrates `WebhookMetadata#shop` equals the attacker-supplied header string exactly, with `HmacValidator.validate` returning `true` and no `ShopValidator.sanitize!` (or equivalent) call anywhere in the `process` path.
