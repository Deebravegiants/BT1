### Title
Webhook shop-domain identity is not covered by HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone, while the `shop` (tenant identity) is read from a separate, unsigned header. `Utils::HmacValidator` only verifies that content, so any request carrying a body/HMAC pair that Shopify has genuinely signed for one shop will pass validation regardless of which `shopify-shop-domain` value is attached to the request, breaking the binding `hmac == HMAC(secret, body ‖ shop)` down to `hmac == HMAC(secret, body)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independently of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the request purely via `verifiable_query.to_signable_string`, i.e. the body only — the shop header never enters the HMAC computation: [3](#0-2) 

`Registry.process` trusts `request.shop` as the tenant identity forwarded to the app's webhook handler once the (body-only) HMAC passes: [4](#0-3) 

Because the app's `api_secret_key` used to compute the webhook HMAC is shared across every shop that installs the app (it is not per-shop), the resulting signature depends solely on the raw body bytes. This means the pairing `(raw_body, hmac)` is valid for the app in general — not bound to a specific `shop`. An attacker who legitimately installs the target app on their own (attacker-controlled) shop will receive genuinely-signed webhook deliveries from Shopify for topics with predictable/static bodies (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, `customers/data_request`, or `{}` bodies as seen in the test fixtures). The attacker can capture such a `(raw_body, hmac)` pair and replay it directly to the app's public webhook endpoint while swapping only the `shopify-shop-domain` header to name a victim shop. `HmacValidator.validate` will accept it because it never checks the shop header, and `Registry.process` will dispatch it to the app's handler with `WebhookMetadata` claiming it originated `shop: <victim-domain>`.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem authenticates the payload but not the tenant claim that host applications rely on to scope side effects (e.g. deleting a stored session/access token on `app/uninstalled`, purging merchant data on `shop/redact`/`customers/redact`, or updating records keyed by `shop`). An attacker can cause the host application to perform tenant-scoped actions attributed to an arbitrary victim shop domain using only a self-service app install, without possessing that victim's credentials — satisfying the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Likelihood is constrained by needing at least one legitimately-signed `(body, hmac)` pair, which is straightforward to obtain by installing the app on a free/attacker-owned development store (an unprivileged action requiring no special access to Shopify or the target merchant), then replaying it with a forged `shop` header to the app's public webhook endpoint. No TLS interception, leaked secrets, or privileged account is required — only network access to the target app's webhook receiver, which is exposed to the public internet by design.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-signable string, or otherwise cryptographically bind the header-derived `shop` value to the signed body before it is trusted in `Registry.process`/`WebhookMetadata`. At minimum, document this limitation clearly so host applications know they must independently verify shop identity (e.g. by cross-checking against a known/installed shop list) before acting on `request.shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, receiving legitimate webhook deliveries.
2. For a topic with a static/predictable body (e.g. `app/uninstalled` with `{}` body, as used in the gem's own test fixtures): [5](#0-4) 
   the attacker records `raw_body = "{}"` and the corresponding `x-shopify-hmac-sha256` header Shopify sent them.
3. Attacker sends a new HTTP POST to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (via `Request#to_signable_string` / `#hmac`) accepts the request because only the body is checked: [6](#0-5) 
5. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the host app to act as though the event came from the victim tenant: [7](#0-6)
