### Title
Webhook `shop` (and other identity headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then extracts the `shop`, `topic`, `webhook_id`, and `api_version` values from unauthenticated HTTP headers and hands them directly to the merchant's registered handler as trusted tenant-identifying data. The bytes actually verified by the HMAC (the request body) are not the same bytes used to determine which shop/tenant the data belongs to (the `shopify-shop-domain` header), breaking the intended binding between "HMAC valid" and "shop attribution trustworthy" — directly analogous to the `isClosed()` bug class where a check exists but the value it is supposed to gate is never actually covered/consulted.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read from HTTP headers that are never included in the signable string and therefore never covered by the HMAC: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic` to route and label the payload for the handler, with no additional check that the header-derived shop matches anything cryptographically tied to the body: [4](#0-3) 

`HmacValidator.validate` only compares `verifiable_query.hmac` against a signature computed from `to_signable_string` (the body), confirming that headers play no role in the cryptographic check: [5](#0-4) 

The equality that should hold is:
`shop attributed to webhook data (request.shop, used for handler routing/tenant labeling) == shop cryptographically bound by the HMAC signature`

Before the attacker's request: for a legitimate Shopify-originated webhook, the header `shop` happens to match the body's originating shop, but this is only true by convention of Shopify's own infrastructure — the gem enforces no such binding itself.

After the attacker's request: an attacker who owns/controls a legitimate app installation on shop A can capture a valid `(raw_body, hmac)` pair Shopify sent them (which validates against `Context.api_secret_key` since the HMAC only signs the body), then replay that exact body+hmac to the app's public webhook endpoint while substituting the `shopify-shop-domain` header (and optionally `shopify-topic`) with victim shop B's domain. `HmacValidator.validate` still returns `true` (body/hmac pair unchanged), and `Registry.process` passes `shop: "shop-b.myshopify.com"` (attacker-controlled) into `WebhookMetadata` for the handler to consume as if it were an authentic message about shop B.

### Impact Explanation
This breaks the tenant-authentication boundary the HMAC is meant to provide: an app's webhook handler, which typically uses `data.shop` to look up per-tenant sessions, update per-tenant state, or perform per-tenant side effects, can be made to act on behalf of a different, arbitrary shop while still passing the library's own signature check. This is a cross-tenant confusion vulnerability reachable by any unprivileged internet user who has (or creates) their own store/app installation to obtain one valid signed webhook body, satisfying the "cross-tenant access" criterion for High/Critical impact.

### Likelihood Explanation
Likelihood is high for apps that rely on the gem's documented webhook flow (`Registry.process` + `Utils::HmacValidator.validate`) as their sole authentication mechanism, since the vulnerability is entirely within the gem's own code path (`Request#to_signable_string`, `HmacValidator.validate`, `Registry.process`) — no reliance on the host app ignoring documented behavior. An attacker needs only network access to the app's public webhook endpoint and one legitimately-signed body/hmac pair from any shop that installed the target app (including the attacker's own dev/trial store), which is inexpensive to obtain.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, and ideally `webhook_id`) in the HMAC signable string, or otherwise cryptographically bind them to the request (e.g., re-deriving the signable string from `headers + body` per Shopify's webhook verification spec) so that `Utils::HmacValidator.validate` fails if any of these headers are altered independently of the signed payload. At minimum, `Webhooks::Registry.process` should not trust `request.shop` for any authorization/tenant-scoping decision unless it is included in what `HmacValidator.validate` verifies.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets Shopify deliver one legitimate webhook, capturing the raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (valid against the app's `api_secret_key`, per `lib/shopify_api/utils/hmac_validator.rb`).
2. Attacker sends a POST to the app's webhook endpoint with:
   - body = `B`
   - `x-shopify-hmac-sha256` = `H`
   - `x-shopify-shop-domain` = `victim-shop.myshopify.com` (attacker-chosen, not the shop that actually produced `B`)
   - `x-shopify-topic` = original or attacker-chosen registered topic
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`), which succeeds because it only checks `body`/`hmac`, per `lib/shopify_api/utils/hmac_validator.rb:27-31` and `lib/shopify_api/webhooks/request.rb:36-38`.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-supplied data under the victim shop's identity.
