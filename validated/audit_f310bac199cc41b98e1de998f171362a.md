### Title
Unfunded declared-amount refunds drain pool custody via `recapitalize`/`repay` - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The bug class — value accounted from a declared aggregate rather than the balance actually received, so a leg that never delivered funds still moves value — maps onto the pool's refund paths. `ops::recapitalize::apply` and `ops::repay::apply` each compute a refund from the *declared* inbound `amount` (`amount - applied` / `amount - net_repay`), not from tokens measured into the pool. The doc comments themselves state the assumption: "The controller transfers `amount` into the pool before this call." When invoked without a preceding real transfer (direct pool call, or an under-delivering token), the "excess" refund is paid out of the pool's real custody while the cash book is untouched — funds leave the contract that were never deposited.

### Finding Description
In `contracts/pool/src/ops/recapitalize.rs:44-67`, `accounting` computes `applied = amount.min(backing_shortfall)` and `refund = amount - applied` purely from the caller-supplied `amount`; `apply` then executes `cache.transfer_out(&payer, outcome.refund)` (line 34) with no balance measurement and no `require_reserves`/cash debit on the refund. Identically, `contracts/pool/src/ops/repay.rs:40-66` resolves `overpayment = amount - net_repay` from the declared `action.amount`, and `apply` refunds it via `transfer_out` (line 32); the `RepayRoundsToZeroShares` assert passes trivially when `net_repay == 0`.

The in-repo test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (`contracts/pool/tests/flows.rs:3589-3611`) proves the mechanics: a `repay` against a market with zero debt declares `custody_before` as the amount, transfers nothing in, credits 0, and the entire amount is refunded out of real custody — `assert_unfunded_refund_drained_custody` confirms the book is untouched while custody drops. The same shape holds for `recapitalize`: declaring `amount` above the shortfall yields `refund = amount - shortfall` paid from custody.

This is the XOXNO analog of the zkSync report: the aggregation check is against a declared value (`amount`, analogous to `msg.value`) rather than the contract's actual received balance, so a deployment/leg whose funding never arrived still causes token movement — here, an outgoing transfer of other users' pooled liquidity.

### Impact Explanation
Theft of user funds / protocol insolvency. Each unit of "refund" for tokens never deposited is paid from supplier-backed pool cash. Repeating the call (or sizing `amount` to the full custody, as the test does) drains the market's liquid balance, leaving suppliers unable to withdraw — direct loss of deposited funds, High/Critical in kind.

### Likelihood Explanation
Reachability depends on the pool's caller-auth model: the doc comments assume the controller is the sole caller that pre-funds the pool. The pool test invokes `client().repay`/`try_recapitalize` directly with a fresh `payer`, and `recapitalize` is listed as a permissionless controller-reachable path; if the pool does not enforce controller-only callers (nothing in these functions does), any unprivileged address can trigger the drain with a single `recapitalize` call using `amount > backing_shortfall` and zero actual transfer. Even if gated, any controller path that forwards a declared amount without measuring receipt (e.g., a deflationary/fee-on-transfer token, or a failed inner transfer) exposes the same gap — matching the report's point that the failure need only happen once.

### Recommendation
Measure receipts instead of trusting the declared amount: snapshot the pool's token balance, require `balance_delta >= net_repay`/`applied` (or compute the refund as `received - applied`), and only refund the actually-received excess. Alternatively/additionally, enforce that `repay`/`recapitalize` are callable only by the controller and have the controller use `transfer_amount_measured` (as it does for liquidation pulls in `apply_liquidation_repayments`), and route the refund through `require_reserves`/`cash` accounting so it can never exceed what was deposited in the same call.

### Proof of Concept
1. Pool holds `C` units of token T in custody with `backing_shortfall == 0` (or `borrowed == 0` for the repay variant).
2. Attacker calls `pool.recapitalize(hub_asset(T), attacker, C)` — or `pool.repay(attacker, [PoolAction{amount: C, ...}])` on a debt-free market — without transferring any T.
3. `accounting` computes `applied = 0`, `refund = C`; `apply` executes `transfer_out(attacker, C)`.
4. Attacker receives `C` units of real custody; cash book unchanged, so every subsequent withdraw over-claims against a now-empty balance. This is exactly what `contracts/pool/tests/flows.rs:3589-3611` demonstrates end-to-end.

Caveat: I could not fully verify whether the pool contract gates `repay`/`recapitalize` to the controller address; the tests call them directly, which suggests it does not, but if a caller check exists elsewhere the attack reduces to the under-delivery variant via controller paths.
