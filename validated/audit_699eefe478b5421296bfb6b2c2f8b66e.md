Audit Report

## Title
Malicious collator can permanently drop DMP messages by over-hashing them past `LastProcessedDownwardMessage`, despite valid MQC accounting - (File: cumulus/pallets/parachain-system/src/lib.rs)

## Summary
`enqueue_inbound_downward_messages` only calls `check_enough_messages_included_basic` on the collator-supplied `AbridgedInboundDownwardMessages`, which merely requires "at least one full message present if any message is hashed." The parallel HRMP path enforces the stricter `check_enough_messages_included_advanced`, which verifies the full-message payload actually fills the size budget before hashing is permitted. This asymmetry allows a malicious collator to hash away real DMP messages that are never dispatched to `T::DmpQueue`, while `LastProcessedDownwardMessage` still advances past them and the DMQ MQC assertion still succeeds.

## Finding Description
`Pallet::do_create_inherent` [1](#0-0)  is only a client-side helper that produces the inherent; the actual `AbridgedInboundDownwardMessages` on-chain is whatever the collator includes, so the full/hashed split is attacker-controlled at execution time.

On-chain, `enqueue_inbound_downward_messages` validates the DMQ collection with only the weak "basic" rule [2](#0-1) , which is defined to require merely that at least one full message is present when any message is hashed [3](#0-2) .

By contrast, the HRMP path additionally enforces the advancement rule via `check_enough_messages_included_advanced`, which asserts that the full messages' total size plus the worst-case next message size exceeds the size budget — i.e., a collator cannot hash a message that should have fit as a full message [4](#0-3) [5](#0-4) . No equivalent call exists for DMP.

Because the MQC hash computation (`extend_with_hashed_msg`/`extend_downward`) is identical whether a message is included as literal data or as a `HashedMessage` [6](#0-5) , a collator can reconstruct the correct DMQ MQC head using only hashes of real messages without exposing their literal payload, and the final assertion still passes [7](#0-6) .

`LastProcessedDownwardMessage` is advanced via `reverse_idx`, incremented once per hashed message sharing `sent_at` with the last literal message [8](#0-7) , while `T::DmpQueue::handle_messages` is only invoked on the literal `full_messages` [9](#0-8) . If a collator submits 1 literal message with `sent_at = N` followed by many hashed messages also with `sent_at = N`, the pointer advances past all of them even though none of their payloads were dispatched.

On a subsequent block, `drop_processed_messages` walks back `reverse_idx` positions and drains everything up to that index from the fresh DMQ contents [10](#0-9) , permanently discarding the never-dispatched messages before they can ever be resubmitted as literal messages.

The code comment on `check_enough_messages_included_advanced` explicitly acknowledges this exact censorship risk for HRMP ("A malicious collator can provide a collection that contains no full messages or fewer full messages than possible, leading to censorship") [11](#0-10) , and the repository's own `prdoc` confirms this protection was deliberately added/tightened for HRMP (`prdoc/stable2603/pr_9086.prdoc`, "Make HRMP advancement rule more restrictive") without an equivalent DMP change, corroborating that DMP lacks the same protection.

## Impact Explanation
Any DMP message (including XCM messages carrying asset transfers/teleports) that a malicious collator chooses to hash alongside one genuine literal message sharing the same `sent_at` is never handed to `T::DmpQueue::handle_messages` and can never be resubmitted, since `LastProcessedDownwardMessage`/`drop_processed_messages` permanently prune it from the DMQ view — all while the relay chain's DMQ MQC head check on-chain still succeeds with no panic or observable inconsistency. This constitutes silent, permanent loss/freezing of legitimate DMP messages (including fund-bearing XCM), which is a concrete in-scope impact for the Cumulus parachain-system message-passing security model.

## Likelihood Explanation
The attack requires only that an entity be the block-producing collator (no root, no leaked keys, no governance) and at least two DMP messages sharing the same `sent_at` (relay block), which is trivial to arrange since many DMP messages routinely share the same relay parent. This is a standard threat-model actor for Cumulus parachains (malicious/faulty collator), and the exploit is deterministic and repeatable each time the condition (≥2 messages, same `sent_at`) recurs.

## Recommendation
Apply the same advancement-rule enforcement used for HRMP (`check_enough_messages_included_advanced`) to the DMP path in `enqueue_inbound_downward_messages`: verify that literal DMP messages fill `messages_collection_size_limit()` as much as possible (using the worst-case next message size, e.g. `MaxDmpMessageLenOf<T>`) before any hashing of a subsequent message is permitted, mirroring the HRMP check at `enqueue_inbound_horizontal_messages`.

## Proof of Concept
Extend `inherent_messages_are_compressed` (or an equivalent new test) in `cumulus/pallets/parachain-system/src/tests.rs`:
1. Construct two DMP messages with the same `sent_at` (e.g., `sent_at = 1`) whose combined size fits within `messages_collection_size_limit()`, so both could legitimately be included literally.
2. Manually craft the on-chain inherent's `AbridgedInboundDownwardMessages` (bypassing `do_create_inherent`'s natural size-based split) marking only the first message literal and the second as hashed (using its correct hash), so the DMQ MQC assertion still passes.
3. Execute the block and assert that only the first message's payload is dispatched to the mock `DmpQueue`, and `LastProcessedDownwardMessage::<Test>::get()` shows `reverse_idx = 1`, i.e., advanced past the second, non-dispatched message.
4. Build a following block reusing the original DMQ contents (both messages still "present" on the relay chain); assert `drop_processed_messages` drops the second message before it can ever be resubmitted as a literal message, and it never appears in the dispatched messages set in any later block.

	/// Drop all the messages up to `last_processed_msg`.
	pub fn drop_processed_messages(&mut self, last_processed_msg: &InboundMessageId) {
		let mut last_processed_msg_idx = None;
		let messages = &mut self.messages;
		for (idx, message) in messages.iter().enumerate().rev() {
			let sent_at = message.sent_at();
			if sent_at == last_processed_msg.sent_at {
				last_processed_msg_idx = idx.checked_sub(last_processed_msg.reverse_idx as usize);
				break;
			}
			// If we build on the same relay parent twice, we will receive the same messages again
			// while `last_processed_msg` may have been increased. We need this check to make sure
			// that the old messages are dropped.
			if sent_at < last_processed_msg.sent_at {
				last_processed_msg_idx = Some(idx);
				break;
			}
		}
		if let Some(last_processed_msg_idx) = last_processed_msg_idx {
			messages.drain(..=last_processed_msg_idx);
		}
	}

	pub fn check_enough_messages_included_advanced(
		&self,
		collection_name: &str,
		size_info: AbridgedInboundMessagesSizeInfo,
	) {
		// We should check that the collection contains as many full messages as possible
		// without exceeding the max expected size.
		let AbridgedInboundMessagesSizeInfo { max_full_messages_size, first_hashed_msg_max_size } =
			size_info;

		let mut full_messages_size = 0usize;
		for msg in &self.full_messages {
			full_messages_size = full_messages_size.saturating_add(msg.data().len());
		}

		// The worst case scenario is that were the first message that had to be hashed
		// is a max size message.
		assert!(
			full_messages_size.saturating_add(first_hashed_msg_max_size) > max_full_messages_size,
			"[{}] Advancement rule violation: full messages size smaller than expected. \
			full msgs size: {}, first hashed msg max size: {}, max full msgs size: {}",
			collection_name,
			full_messages_size,
			first_hashed_msg_max_size,
			max_full_messages_size
		);
	}
