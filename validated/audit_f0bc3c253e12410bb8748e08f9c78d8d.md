Confirmed: the webhook HMAC (`Utils::HmacValidator.validate`) only signs the raw JSON body via `Request#to_signable_string` returning `@raw_body`, while `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never part of the signed bytes. `Registry.process` validates the HMAC and then unconditionally forwards `request.shop` into `WebhookMetadata`, which host apps use as the tenant identifier for the event (per `docs/usage/webhooks.md` example `data.shop`).

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` binds solely to the body bytes. The `shop` value handed to the webhook handler comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the signed data.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Specifically: [2](#0-1) [3](#0-2) [4](#0-3) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, which for a webhook `Request` is exactly `@raw_body`, and nothing else: [5](#0-4) 

`Registry.process` validates that HMAC, then trusts `request.shop` (the header value) as the shop identity passed to the handler: [6](#0-5) 

The equality this breaks: the gem treats `shop == HMAC-authenticated-shop`, but in reality `shop` is merely `shop == unauthenticated shopify-shop-domain header value`. The HMAC only proves "this body byte-sequence was signed with `api_secret_key`" — it proves nothing about which shop that body belongs to, because the shop identity is carried out-of-band in a header that isn't part of `to_signable_string`.

### Impact Explanation
Any body+HMAC pair that is valid for one shop's webhook (which an attacker can obtain, e.g. by receiving one legitimate webhook delivery to their own store, since HMAC verification does not depend on the secret being unknown to a merchant who installed the app) remains a *valid HMAC* if replayed with an arbitrary `shopify-shop-domain` header value. Since `Registry.process` builds `WebhookMetadata` directly from the unauthenticated header and passes it to the app-provided handler (documented pattern: `data.shop` used to look up the tenant, e.g. `perform_later(shop_domain: data.shop, ...)`), this allows an attacker to make the host application process/attribute webhook data under an arbitrary victim shop domain, i.e., cross-tenant data confusion/injection using only their own shop's valid signed payload.

### Likelihood Explanation
Any merchant who has installed the app and can observe/replay a webhook delivery (a normal, unprivileged action, not requiring `api_secret_key`) can forge the `shop` field while keeping a valid signature, since the header is never part of the signed bytes.

### Recommendation
Bind the shop identity into the signed payload verification: either compute/verify the HMAC over a canonical string that includes the `shop` (and `topic`) header values in addition to the body, or require host applications to cross-check `request.shop` against the shop associated with the session/subscription that the webhook was registered for before trusting it, and document this requirement prominently. At minimum, the gem should not silently hand an unauthenticated header value to the handler as if it were verified.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` receives a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: H` (valid, `H = HMAC(secret, B)`), and header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the same body `B` and same HMAC `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` — the shop header is irrelevant to the signature.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` and processes/attributes data under the victim shop, even though `B` was never signed for the victim.
