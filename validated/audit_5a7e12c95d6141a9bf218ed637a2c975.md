### Title
Cached operator QR-code validity is reused for up to 23 hours without re-checking revocation with the backend - (File: src/plans/mod.rs)

### Summary
The `NestedFactory` bug class describes an authorization cache (`operatorCache`) that is not invalidated when the underlying source of truth changes (`removeOperator()`), so the stale cache continues to authorize actions until an explicit resync happens. `orb-core` has a structurally similar pattern: once an operator QR-code is validated against the backend, the resulting `OperatorData` (including its "valid" status) is cached in memory and reused for subsequent signups as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, without re-querying the backend for revocation.

### Finding Description
`MasterPlan::scan_initial_qr_codes` validates an operator QR-code once via `verify_operator_qr_code`, which calls the backend `operator_status::request` and, on success, stores the result as `OperatorData { qr_code, location_data, timestamp: Instant::now() }` inside the `QrCodes::Operator` cache. [1](#0-0) 

This cached operator validity is then reused by `scan_remaining_qr_codes` for any subsequent signup as long as the cached timestamp has not exceeded `operator_qr_expiration_time`, entirely skipping a fresh call to `verify_operator_qr_code`/`backend::operator_status::request`: [2](#0-1) 

The same stale-cache reuse also occurs in the self-serve idle-scanning path, where the remaining validity window is simply computed from the elapsed time of the original validation, again without re-checking the backend: [3](#0-2) 

The expiration window defaults to 23 hours: [4](#0-3) 

This mirrors the `NestedFactory`/`MixinOperatorResolver` bug class: `verify_operator_qr_code` is the "cache-populating" call (analogous to `rebuildCache()`), and once populated, the cache (`operator_data`) is trusted for a long window by `create()`-equivalent flows (`scan_remaining_qr_codes`, `idle_scan_user_qr_code`) that assume the cached validity is still in sync with the backend's authorization state. If the backend revokes/deactivates the operator ID mid-window (the equivalent of `removeOperator()`), `orb-core` has no mechanism to detect that and continues to treat the operator as valid until the local timestamp naturally expires — there is no analog of an immediate cache-invalidation push, and no re-validation on each subsequent signup within the window.

### Impact Explanation
For up to `operator_qr_expiration_time` (23 hours by default), a distributor/operator whose authorization has been revoked by the backend can continue to be treated as valid by the orb, allowing signups to proceed under a revoked operator identity. This is a genuine "misattributed signup" / authorization-cache desync impact matching the bug class: the actions gated on operator validity (proceeding to scan/validate user QR-codes and complete signups) rely on a cache that is not proven to be in sync with the backend's current state.

### Likelihood Explanation
This is reachable in the normal self-serve flow (`self_serve == true`) without any special privileges — an operator whose QR-code was validated once continues to unlock the orb's signup flow for the full cache window, and the orb never re-asks the backend whether that operator is still valid during that window. The likelihood depends on an operator being revoked while their code is still within the cached expiration window, which is an operationally plausible scenario (e.g., compromised/terminated distributor).

### Recommendation
Do not treat backend operator validation as valid for the entire `operator_qr_expiration_time` window without re-confirmation. Instead: (1) shorten the trust window and/or periodically re-validate the operator status with the backend during long-lived self-serve sessions, (2) invalidate the cached `OperatorData` immediately when a config/backend push indicates the operator has been revoked (similar to adding a "removed operator" tracking mechanism), and (3) ensure `scan_remaining_qr_codes` / `idle_scan_user_qr_code` re-call `backend::operator_status::request` rather than relying solely on the elapsed-time check before permitting signups to proceed.

### Proof of Concept
1. Operator scans their QR code; `verify_operator_qr_code` succeeds and `OperatorData` with `timestamp = now` is cached in `QrCodes::Operator`.
2. Backend administrator revokes/deactivates this operator ID (analogous to `NestedFactory.removeOperator()`).
3. Within `operator_qr_expiration_time` (up to 23 hours), a user scans a user QR-code; `scan_remaining_qr_codes` sees `operator_data.timestamp.elapsed() < operator_qr_expiration_time` is still true and proceeds directly to `scan_user_qr_code` without re-calling `backend::operator_status::request`.
4. The signup proceeds under a now-revoked operator, because the orb never re-synced with the backend's current authorization state for that operator.

    async fn scan_initial_qr_codes(
        &mut self,
        orb: &mut Orb,
        qr_codes: &mut QrCodes,
        self_serve: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<()> {
        if self_serve
            && qr_codes
                .operator_timestamp()
                .map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)
        {
            loop {
                let qr_capture_start = Instant::now();
                let operator_qr_code =
                    self.scan_operator_qr_code(orb, None).await?.expect("to never timeout");
                let Some(operator_qr_code) =
                    self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                else {
                    continue;
                };
                let Some((_, operator_location_data)) =
                    self.verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start).await?
                else {
                    continue;
                };
                *qr_codes = QrCodes::Operator {
                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }
