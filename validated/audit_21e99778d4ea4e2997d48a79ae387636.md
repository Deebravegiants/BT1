### Title
Pipeline run disclosure via unscoped `runID` lookup in job runs endpoint - (File: core/web/pipeline_runs_controller.go)

### Summary
`PipelineRunsController.Show`, which serves `GET /v2/jobs/:ID/runs/:runID`, ignores the `:ID` (job) path parameter entirely and fetches the pipeline run using only `:runID`, without verifying that the run belongs to the job named in the URL.

### Finding Description
The route is registered as job-scoped: `authv2.GET("/jobs/:ID/runs/:runID", prc.Show)` [1](#0-0) . However, the handler never reads or validates `c.Param("ID")` — it only parses `runID` and passes it straight to `PipelineORM().FindRun`: [2](#0-1) 

This mirrors the Gitea bug class exactly: the parent-resource identifier in the URL (`jobID` in Gitea's issue, here the job `:ID`) is not used to scope the lookup of the child resource (`timeID` in Gitea, here `runID`). Any authenticated user with access to this API endpoint can enumerate/guess `runID` values and retrieve pipeline run data for jobs other than the one indicated in the request path, since the ORM call `FindRun(ctx, pipelineRun.ID)` performs no job-ownership or job-ID filter.

### Impact Explanation
This is a cross-resource (cross-job) response confusion / IDOR: a caller who is only supposed to see runs for the job referenced in the URL can retrieve run data (inputs, outputs, task run details, error messages) belonging to a completely different job by simply substituting `runID`. While Chainlink nodes are typically single-tenant, in any multi-user or role-restricted deployment (or any future job-level access control), this bypasses the intended job-scoping and leaks task run inputs/outputs across job boundaries — analogous to the confidentiality/integrity concern in the CVE (though here it is a read rather than a delete).

### Likelihood Explanation
High: the vulnerable path requires no special conditions — the endpoint is only reachable by an authenticated user (any user with node API session or read-scoped API access), and exploitation is a single GET request with an arbitrary `runID`. Because run IDs are simple auto-incrementing integers, they are trivially enumerable.

### Recommendation
Update `PipelineRunsController.Show` to require and validate the `:ID` (job) parameter, and modify `FindRun` (or add a variant) to filter by both `runID` and `jobID`, returning `404 Not Found` if the run does not belong to the specified job — mirroring how `Index` already scopes lookups via `jobSpec.ID` [3](#0-2) .

### Proof of Concept
1. As an authenticated user, create/observe pipeline run A under job 1, note its `runID` (e.g., 100).
2. As the same or another authenticated user, issue `GET /v2/jobs/2/runs/100` (job 2 unrelated to run 100).
3. The handler ignores `:ID=2` and calls `FindRun(ctx, 100)` [4](#0-3) , returning run 100's data even though it belongs to job 1, not job 2 — demonstrating the missing job-scope check.

Note: I was unable to fully confirm the exact SQL/implementation of `FindRun` in `core/services/pipeline/orm.go` (only its signature was located, not its body) due to tool-call limits reached before reading it; based on the controller code, it accepts only a run ID with no job-ID argument, which is consistent with the described lack of scoping, but this could not be double-verified against the full ORM method body.

```go
// Show returns a specified pipeline run.
// Example:
// "GET <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	pipelineRun := pipeline.Run{}
	err := pipelineRun.SetID(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	pipelineRun, err = prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
	jsonAPIResponse(c, res, "pipelineRun")
}
```
