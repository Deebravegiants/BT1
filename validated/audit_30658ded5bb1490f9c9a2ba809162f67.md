### Title
RAY value overflow during interest accrual permanently freezes a market - (File: common/src/rates/scaling.rs)

### Summary
An unprivileged borrower can push a large, highly utilized market into a state where index accrual overflows the `i128` RAY value range. Because every supply, borrow, withdrawal, repayment, liquidation and index-update path accrues the market before mutating it, the first overflow makes that market permanently unusable.

### Finding Description
Pool indexes accrue through `Controller::update_indexes`, while `supply`, `borrow`, `withdraw`, `repay` and `liquidate` all route through position processing that performs market accrual before the requested action. [1](#0-0) [2](#0-1) 

The repository includes a direct witness for this failure mode: a market with approximately `1e9` units at 18 decimals and 98% utilization continues accruing until the conversion of the scaled value overflows in `scaled_to_original`. The resulting `MATH_OVERFLOW` occurs before the configured borrow-index cap can engage. [3](#0-2) 

Once the overflowed state exists, calls to `update_indexes`, `withdraw` and `repay` fail with `MATH_OVERFLOW`; consequently, liquidation and any other path that accrues the same market are also blocked. [4](#0-3) 

### Impact Explanation
This permanently freezes all user funds associated with the affected market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate distressed debt, and `update_indexes` cannot recover the market because every path reaches the overflowing accrual calculation first.

The impact is permanent freezing of funds and protocol inoperability for that market, rather than theft. A rescue would require a privileged contract upgrade or another out-of-band remediation because the public exit paths themselves revert.

### Likelihood Explanation
Likelihood is constrained by the scale and duration required: the witness uses a very large 18-decimal market, 98% utilization and sustained accrual over multiple years. No privileged action is needed once such a market exists, but reaching the condition demands substantial liquidity and long-duration high utilization. The severity is therefore Medium: high local impact, with demanding economic and temporal prerequisites.

### Recommendation
Bound accrual before converting scaled values back to asset units. In particular:

- Detect the impending `i128` RAY-value overflow inside the accrual/scaling path and clamp or fail before committing a state that later accruals cannot process.
- Enforce the existing maximum borrow-index ceiling before the value conversion that can overflow.
- Add explicit regression coverage asserting that `withdraw`, `repay`, `liquidate` and `update_indexes` remain callable as the index approaches `MAX_BORROW_INDEX_RAY`.
- Prefer widening only the intermediate accrual calculation over suppressing the error, while preserving the public `i128` accounting representation.

### Proof of Concept
The repository test demonstrates the complete path:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() {
        break;
    }
}
```

After the accrual error:

```rust
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), MATH_OVERFLOW);
```

The stored index remains below `MAX_BORROW_INDEX_RAY`, proving that the cap does not prevent the overflow and that subsequent market operations remain blocked. [5](#0-4)

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
