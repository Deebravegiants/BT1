### Title
Webhook shop/topic identity spoofing via HMAC scope mismatch - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once the HMAC check passes, then hands the handler a `WebhookMetadata` struct built from `shop`, `topic`, `webhook_id`, and `api_version`. All four of those fields are read straight from HTTP headers, but the HMAC signature covers only the raw request body. The identity fields an app relies on to know *which tenant* sent the webhook are never bound to the cryptographic proof of authenticity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#hmac` decodes the `hmac-sha256` header for comparison: [2](#0-1) 

`#shop`, `#topic`, `#webhook_id`, `#api_version` are all read from separate, unsigned headers: [3](#0-2) 

`Registry.process` validates only the body/HMAC pair, then immediately trusts those header-derived fields to build the metadata passed to the app's handler: [4](#0-3) 

The equality the library implicitly claims to guarantee is:
`hmac_valid(raw_body) == request_is_authentically_from(shop, topic, webhook_id)`

But the real guarantee is only `hmac_valid(raw_body) == body_was_signed_with_client_secret`. Because Shopify signs webhooks with the app's single `client_secret` for every installed shop (not a per-shop key), any body/HMAC pair produced by a genuine, legitimate installation (e.g., the attacker's own dev/test store, or any store where they can trigger a webhook) remains valid regardless of which shop the request claims to be from. An unprivileged user who has installed the app on their own store can capture one of their own valid `(raw_body, X-Shopify-Hmac-Sha256)` pairs and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header pointing at a victim shop. `Registry.process` will accept it as valid and hand the app a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as the library's own struct and docs encourage) to select which merchant's data/session to act on — e.g., to look up the merchant's session/access token and apply the webhook body's mutations — an attacker can cause the app to process attacker-supplied data under a victim shop's identity, achieving cross-tenant data confusion/injection without ever holding a credential for the victim shop. This matches the Critical "cross-tenant access" impact category: the tenant boundary (`shop`) is asserted by the library as validated when it is not covered by the authentication check.

### Likelihood Explanation
Likelihood is moderate-to-high in typical usage. The prerequisite is trivial for an unprivileged internet user: install the (public/free-tier) target app on any store they control, capture one legitimate webhook body+HMAC pair from Shopify, and replay it to the app's public webhook endpoint with a different `Shop-Domain` header. No secrets, tokens, or privileged accounts are required — only knowledge of the gem's documented `Registry.process`/`Request` API, which unconditionally trusts header-derived identity fields once the body HMAC passes.

### Recommendation
Bind the tenant/topic identity to the authenticated bytes rather than trusting separate headers: include `shop`, `topic`, and `webhook_id` in the signed payload comparison (e.g., verify against Shopify's per-request context, cross-check `shop` against the session/store the app expects for that webhook subscription), or at minimum require the consuming application to independently verify that the `shop` header corresponds to a shop with an active installation before acting on the payload, and document that `Request#shop`/`#topic`/`#webhook_id` are unauthenticated metadata.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a store they own — no special privilege required).
2. Attacker triggers any subscribed webhook topic (e.g., updates a product) and captures the raw POST body plus the genuine `X-Shopify-Hmac-Sha256` header Shopify sent to the app's webhook endpoint.
3. Attacker replays that exact body and HMAC header to the same app webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a store the attacker does not control).
4. `Webhooks::Request#hmac` matches (same client_secret, same body) so `HmacValidator.validate` in `Registry.process` succeeds.
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and calls `handler.handle`, causing the app to process attacker-controlled data as if it came from the victim shop. [4](#0-3)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
