### Title
Webhook `shop`/`topic` identity is trusted from unauthenticated HTTP headers while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers that are **not** included in that HMAC computation. This breaks the identity binding `shop authenticated == shop acted upon`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are read straight from request headers, none of which are part of the signed content: [2](#0-1) 

`HmacValidator.validate` only compares the HMAC of `to_signable_string` (the body) against the `hmac` field, and never touches `shop`/`topic`/headers at all: [3](#0-2) 

`Registry.process` then uses the *unauthenticated* `request.shop` and `request.topic` to look up the handler and construct `WebhookMetadata`, which is handed to the app's handler as if it were verified: [4](#0-3) 

Because the `api_secret_key` is a single shared secret for the whole app (not per-shop), any shop that has legitimately installed the app receives real webhook deliveries whose body+HMAC are valid under that same shared secret. Nothing in this gem's webhook-processing code binds that valid HMAC to the specific `shop` (or `topic`) it was originally delivered for. An adversary who controls a shop that has installed the app (an "unprivileged internet user" from the perspective of any other merchant using the same app) can:
1. Receive a legitimate webhook for their own shop (valid body + valid `x-shopify-hmac-sha256`).
2. Replay that exact body/HMAC to the app's public webhook endpoint, but with the `x-shopify-shop-domain` header rewritten to a victim shop's domain (and/or `x-shopify-topic` rewritten to a different topic, e.g. `app/uninstalled` or `shop/redact`).
3. `Utils::HmacValidator.validate(request)` returns `true` (it never checked the shop/topic), so `Registry.process` dispatches the forged `WebhookMetadata{shop: victim_shop, topic: forged_topic, body: attacker_body}` to the app's handler as if Shopify had sent it for the victim shop.

### Impact Explanation
This is a cross-tenant authentication bypass at the identity-binding level: the equality that should hold — `HMAC-verified sender == shop the handler acts on` — does not hold, because `shop`/`topic` are outside the signed payload. Any app built on this gem that keys data storage, GDPR redaction, uninstall cleanup, or entitlement changes off `WebhookMetadata#shop`/`#topic` can be made to act on behalf of, or against, a shop that never sent that webhook, purely by an attacker who is a legitimate (if malicious) installer of the same app on a different shop. This satisfies the "cross-tenant access" impact category.

### Likelihood Explanation
Any merchant/attacker who can install the target app (a normal, unprivileged action for third-party embedded apps) automatically receives real signed webhook traffic and can replay it against the public webhook endpoint with modified headers — no access to `api_secret_key`, access tokens, or any privileged credential is required. The only requirement is that the app actually be installed on at least one shop controlled by the attacker, which is the normal, expected usage pattern for a public app.

### Recommendation
Include `shop`, `topic`, and any other header-derived fields that downstream code treats as authenticated (e.g. `webhook_id`) in the signed content that is verified, or otherwise cryptographically bind them to the request (e.g., require the app to independently confirm `shop` corresponds to a session it registered a webhook subscription for/its own known installed shop list before dispatching), rather than passing header values straight into `WebhookMetadata` as if HMAC-verified.

### Proof of Concept
1. Shop A installs the app and receives a genuine webhook `POST /webhooks` with body `B` and header `x-shopify-hmac-sha256: H = HMAC_SHA256(secret, B)` and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (owner of Shop A) resends the same request to the same endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally `x-shopify-topic` to a sensitive topic such as `shop/redact`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (headers are only checked for presence, not authenticity) — [5](#0-4) .
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because `H` still matches `HMAC_SHA256(secret, B)` — [6](#0-5) .
5. The app's handler is invoked with `WebhookMetadata{shop: "victim-shop.myshopify.com", topic: forged_topic, body: B}`, causing it to act as though Shopify had legitimately delivered that webhook for the victim shop.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
