### Title
Permissionless `update_account_threshold` can silently tighten a victim's cached LTV and revert their borrows/withdraws - (File: contracts/controller/src/risk/params.rs)

### Summary
The Teller bug class is "a party other than the victim writes state that makes the victim's next transaction revert" (DoS by forcing the auth/forwarder check to fail). XOXNO Lending has the same shape in `update_account_threshold`: any authenticated address may restamp another account's stored `loan_to_value` to the currently listed value, with no health-factor gate in `LtvOnly` scope. If governance ever lowers a collateral's LTV, a single unprivileged caller can selectively apply the tighter LTV to a victim's supply positions while the victim (and the attacker's own accounts) would otherwise keep operating on the stale, more permissive snapshot. The victim's subsequent `borrow` or `withdraw` then reverts on the LTV-weighted collateral check — a targeted, attacker-timed freeze of account functionality.

### Finding Description
`update_account_threshold` is a permissionless entrypoint (`scripts/permissionless_entrypoints.txt` line 76, `contracts/controller/src/risk/params.rs:124`). With `has_risks = false` it runs `RiskRefreshScope::LtvOnly`, which calls `refresh_supply_risk_params` and unconditionally overwrites `position.loan_to_value = effective_config.loan_to_value` (`params.rs:35`), skipping the `favors_liquidator`/min-HF gating that only exists in `apply_gated_liquidation_params` for the liquidation tuple (`params.rs:68-93`). The `hf >= 1.05` assertion at `params.rs:221-234` is only reached under `FullTuple`; `LtvOnly` never loads debt and never checks health factor.

`require_post_pool_risk_gates` (`contracts/controller/src/risk/validation.rs:29`) enforces LTV-weighted collateral coverage after `borrow` and `withdraw`. An attacker therefore calls `update_account_threshold(caller = attacker, has_risks = false, account_ids = [victim])` — reachable by any address per the entrypoint table — to restamp a victim whose listed LTV dropped (e.g., risk-off parameter change the victim hasn't noticed), then the victim's in-flight or imminent `withdraw`/`borrow` reverts.

### Impact Explanation
Temporary freezing of funds and blocked actions on demand: the attacker chooses exactly when the stricter parameter is enforced on the victim. During volatility this can block a victim's `borrow`/`withdraw` at a critical moment (e.g., to free collateral to defend another position), while accounts the attacker does not touch keep the stale permissive LTV. Impact is bounded — the victim can `repay` or `supply` more collateral, and the listed LTV is governance's intended value — so this is Medium, mirroring the source report's severity.

### Likelihood Explanation
Requires only that a listed LTV is ever lowered while an account holds that collateral — a routine risk-management action — plus one unauthenticated-class call. Any address can invoke it; no ownership, delegation, or approval relationship to the victim is needed.

### Recommendation
Symmetric gating: in `refresh_supply_risk_params`, when the new LTV is lower than the stored snapshot and the account is not debt-free, require the post-change LTV-weighted coverage to still pass (analogous to `clears_min_hf` for the liquidation tuple), or restrict `update_account_threshold` callers to the account owner/delegate and keepers. Alternatively, only restamp LTV upward permissionlessly.

### Proof of Concept
1. Governance lowers `loan_to_value` for asset X in a spoke.
2. Victim holds X as collateral with debt sized to the old LTV.
3. Attacker calls `controller::update_account_threshold(attacker, false, [victim_id])`; `restamp` writes the lower LTV into the victim's supply position with no HF check.
4. Victim's `withdraw`/`borrow` now reverts in `require_post_pool_risk_gates` until they deleverage, while untouched accounts still operate on the stale LTV.

Confidence caveat: I verified the LtvOnly path is ungated and that post-pool risk gates read LTV, but did not trace every consumer of `position.loan_to_value` — if withdraw gating actually reads only `liquidation_threshold`, the DoS surface narrows to `borrow` alone, which still qualifies but weakens impact.
