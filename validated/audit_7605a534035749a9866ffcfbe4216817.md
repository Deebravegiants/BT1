## Title
Webhook HMAC only authenticates the request body, not the `shop`/`topic`/`webhook_id` headers used for handler dispatch, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` verifies nothing but body integrity. The `shop`, `topic`, `api_version`, and `webhook_id` values that `Registry.process` uses to dispatch to app handlers are read straight from HTTP headers that are never covered by the HMAC. Anyone who can obtain one valid `(body, hmac)` pair (e.g. by installing the app on their own store and capturing a delivered webhook) can replay that exact body/HMAC to the app's public webhook endpoint with an arbitrary `shop-domain` header, causing the app to process the payload as if it came from a different (victim) shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. `HmacValidator.validate_signature` computes the HMAC exclusively over that signable string: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers with no cryptographic binding to the body: [3](#0-2) 

`Registry.process` verifies only the HMAC (i.e. body integrity) and then dispatches to the app's handler using the unauthenticated `request.shop`, `request.topic`, etc.: [4](#0-3) 

The identity binding that should hold is: `shop value used by the handler == shop that Shopify actually attributes to this exact signed payload`. Because the HMAC only signs the body, this equality is not enforced — the `shop` header can be swapped freely without invalidating the signature, breaking the binding between the authenticated payload and the tenant identity the app acts on.

### Impact Explanation
An app's webhook endpoint is a public HTTP endpoint. Any unprivileged internet user who can get the app installed on a store they control (dev store, free-tier app, etc.) can capture one legitimate `(raw_body, x-shopify-hmac-sha256)` pair for a given topic (many topics, e.g. `app/uninstalled`, have a body that is generic/predictable or contains no shop-specific data). That user can then directly POST that exact body and HMAC to the app's webhook endpoint with the `x-shopify-shop-domain` header set to an arbitrary victim shop domain and any `topic`/`webhook-id` they like. `Registry.process` will accept it (HMAC of body matches) and invoke the registered handler with `WebhookMetadata` claiming it originated from the victim shop. If the app's handler trusts `data.shop` to act on that shop's stored session/data (common patterns: revoking access on `app/uninstalled`, updating shop settings on `shop/update`, deleting/creating resources scoped by shop), this results in cross-tenant action/impersonation — one shop's webhook traffic can be used to spoof effects against another shop.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple merchants and exposes its webhook endpoint publicly (the normal deployment model). The only prerequisite is that the attacker can get one valid signed webhook delivered to them (trivially achievable by installing the app on a store they control), and that the target topic's body doesn't need to differ per victim shop for the intended abuse to matter (many topics, e.g. `app/uninstalled`, `customers/redact`, `shop/update`, carry attacker-controllable or shop-agnostic bodies).

### Recommendation
Do not trust header-derived `shop`, `topic`, `webhook_id`, or `api_version` for authorization/dispatch decisions unless they are cryptographically bound to the verified payload. At minimum:
- Include the relevant headers (shop domain, topic) in the HMAC-signed material used for validation, or
- Cross-check `request.shop` from the header against the shop encoded in the JSON body when available, and reject on mismatch, or
- Document loudly (and enforce in `Registry.process`) that the `shop` value from `WebhookMetadata` must never be trusted for cross-tenant-sensitive actions without an independent verification (e.g. looking up an existing session keyed by an out-of-band-verified shop identifier) before performing destructive or tenant-scoped operations.

### Proof of Concept
1. Install the target app on an attacker-controlled dev store; trigger a webhook (e.g. `app/uninstalled`) and capture the raw POST body plus its `x-shopify-hmac-sha256` header.
2. Send a new HTTP POST directly to the app's public webhook endpoint using the exact same body and `x-shopify-hmac-sha256` value, but set `x-shopify-shop-domain` to `victim-shop.myshopify.com` and `x-shopify-topic` to the same or a different registered topic.
3. `HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC: [5](#0-4) 
4. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"`: [6](#0-5) 
5. Any handler logic keyed off `data.shop` now executes against the victim shop's identity despite the payload never having been signed by Shopify for that shop.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
