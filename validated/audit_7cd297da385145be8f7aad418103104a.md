### Title
Unchecked ERC20 `transfer()` return value in `IntentGatewayV2.withdraw()` allows escrow accounting to advance without delivering funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron build of `IntentGatewayV2` releases escrowed order inputs, protocol fees, and swept dust using a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks the outer call-success boolean, discarding the returned ABI data. For any ERC20/TRC20 token that signals failure by returning `false` instead of reverting, the outer call succeeds, the `!success` check passes, and the function proceeds to decrement escrow storage and emit success events as if the beneficiary was paid — while no tokens actually moved.

### Finding Description
`withdraw()` is the internal function that finalizes escrow release for both `RedeemEscrow` (solver payout after a cross-chain fill) and `RefundEscrow` (order cancellation refund) flows, and is reached from `onAccept()` (triggered by any relayer delivering a Hyperbridge-authenticated message) and from `onGetResponse()` (triggered by relaying a GET-response proof for cross-chain cancellation): [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
```

The second return value of `token.call(...)` (the ABI-encoded `bool` returned by a standards-compliant `transfer()`) is discarded (`(bool success,)`). `success` here is only the *call-level* success flag: it is `true` whenever the target contract has code and does not revert, regardless of what boolean value it returns. A token that implements `transfer()` to return `false` on insufficient balance/blacklist/etc. (rather than reverting) causes `withdraw()` to treat the transfer as successful. The same pattern repeats for the fee-token payout later in the same function and for the `SweepDust` dust-sweep handler in `onAccept`: [2](#0-1) [3](#0-2) 

Critically, the contract already imports `SafeERC20` and declares `using SafeERC20 for IERC20;`, and the sibling EVM contracts (`evm/src/apps/intentsv2/IntentsBase.sol`) correctly use `IERC20(token).safeTransfer(beneficiary, amount)` for the identical `_withdraw` logic: [4](#0-3) 

confirming the Tron variant's raw-call pattern is a real deviation/regression, not an intentional design choice, and that `safeTransfer` was available but not used in the affected paths.

After the unchecked call, escrow storage is unconditionally decremented (`_orders[body.commitment][token] -= amount;`) and, on `finalize`, `_filled[commitment]` is set — permanently marking the order as settled. There is no balance-delta check (unlike the EVM `IntentGatewayV2.sol` sweep logic elsewhere in the codebase, which snapshots balances before/after transfers). Once escrow accounting reaches zero/settled state with no tokens actually delivered, the funds are unrecoverable — no further code path can re-derive or re-release them.

### Impact Explanation
This is reachable by any relayer completing the ordinary intent-fill or intent-cancellation lifecycle — no privileged role is required. If the input/output token used in an order is a TRC20/ERC20 whose `transfer()` can return `false` without reverting (common among Tron-ecosystem tokens and several mainstream tokens like legacy BAT/ZRX-style implementations), a filler's or user's escrowed funds are permanently locked in the `IntentGatewayV2` contract: the on-chain accounting (`_orders`, `_filled`) reports the order as settled/refunded, but the beneficiary never receives the tokens, and no other function path allows the deposit to be reclaimed. This is a permanent freezing/loss-of-funds condition for users and solvers who deposited into escrow.

### Likelihood Explanation
Likelihood is contingent on token behavior (a `false`-returning ERC20/TRC20 must be used as an order's input/output/fee token), but no attacker action or privileged access is required beyond ordinary use of the intent-fill/cancel flow that every solver and user triggers, and the Tron ecosystem specifically has a documented history of TRC20 tokens with non-standard `transfer()` return semantics, making this more likely to be hit here than on a generic EVM chain.

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()` for both the token loop and the fee-token payout, and in the `SweepDust` handler inside `onAccept`) with `IERC20(token).safeTransfer(beneficiary, amount)`, consistent with the already-imported `SafeERC20` library and with the equivalent logic in `evm/src/apps/intentsv2/IntentsBase.sol`. This guarantees a `false` return reverts the whole transaction instead of silently advancing escrow state.

### Proof of Concept
1. Register/escrow an order whose input token is a TRC20 implementation that returns `false` on `transfer()` failure instead of reverting (e.g., insufficient contract-held balance edge case, or a blacklist-style token).
2. A solver fills the order on the destination chain and Hyperbridge relays the `RedeemEscrow` message; `onAccept()` → `withdraw()` executes on the source chain.
3. Force (or naturally trigger, e.g. via a paused/blacklisted beneficiary) the token's `transfer()` to return `false`. The low-level `.call` still succeeds (`success == true`) because the token contract executed without reverting.
4. `withdraw()` proceeds past `if (!success) revert TransferFailed();`, decrements `_orders[commitment][token]` to zero, and sets `_filled[commitment] = beneficiary`.
5. The beneficiary's on-chain token balance is unchanged — no tokens were delivered — yet the order is permanently marked filled/settled with zero escrow remaining, so the deposited tokens are stuck in the `IntentGatewayV2` contract with no remaining code path to recover them.
