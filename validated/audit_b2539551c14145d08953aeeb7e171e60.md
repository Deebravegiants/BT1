### Title
Webhook shop identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` header from the HMAC-signed material. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over that body-only payload and then unconditionally trusts the unauthenticated `shop-domain` header when constructing `WebhookMetadata` passed to the app's handler. The equality the gem should guarantee — `shop_covered_by_hmac == shop_trusted_by_handler` — does not hold: the shop identity delivered to the app is never covered by the signature that is supposed to authenticate the whole message.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns `@raw_body` only — the `shop-domain`, `topic`, and `webhook-id` headers are excluded from the signed bytes.

`HmacValidator.validate` then verifies the HMAC strictly against that signable string: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC checks out, then builds `WebhookMetadata` directly from the unauthenticated `request.shop` header and dispatches it to the app-registered handler: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is per-app, not per-shop, this same key is used to sign webhook bodies for every merchant/shop that has the app installed. Any shop with the app installed will receive genuine, validly-signed webhook deliveries from Shopify. An attacker who has the app installed on their own (unprivileged) shop can capture one of these legitimate `(raw_body, hmac)` pairs and replay it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop. `HmacValidator.validate` still succeeds (the body and signature are untouched and were produced with the correct secret), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This breaks the tenant/identity binding the HMAC is meant to provide: verified bytes ≠ bytes the handler acts on for identity purposes. Any app whose webhook handler uses `WebhookMetadata#shop` to select which merchant's data to update, credit, or process (the common and documented pattern) can be made to apply data intended for shop A onto shop B's tenant context — a cross-tenant data-integrity/exfiltration vector achieved without ever possessing the app's `client_secret`, an access token, or any privileged credential, only requiring installing the app on an attacker-controlled shop.

### Likelihood Explanation
Likelihood is moderate to high: the required capability (install the target app on your own shop and receive its own legitimate webhook deliveries) is available to any unprivileged merchant/internet user who can install a public app; capturing one's own webhook POST and replaying it with a modified header is trivial. No cryptographic secret needs to be recovered.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, e.g. include the `shop-domain` (and ideally `topic`/`webhook-id`) header bytes in `to_signable_string`, or have `Registry.process` independently confirm `request.shop` against a shop that is known to have installed the app for the given webhook secret/session, rather than trusting the header verbatim once the body-only signature passes.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`; Shopify sends a legitimate webhook: body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker POSTs the same body `B` and the same HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` — matches because `to_signable_string` never included the shop header — validation passes.
4. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` to the app's handler, which now processes attacker-controlled data `B` under the victim shop's identity.
