Confirmed: `Request#hmac` computes the signature only over `to_signable_string`, which is `@raw_body` [1](#0-0) . The `shop` accessor reads the `x-shopify-shop-domain`/`shopify-shop-domain` header directly with no cryptographic binding to that signature [2](#0-1) . `HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the body) [3](#0-2)  and `VerifiableQuery` only requires `hmac` and `to_signable_string`, so `shop` is structurally excluded from the signed material [4](#0-3) . `Registry.process` then trusts `request.shop` as the tenant identifier passed to the handler without any additional check [5](#0-4) , and `WebhookMetadata.shop` is the field host apps are expected to use for tenant scoping [6](#0-5) .

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing on replayed webhooks - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler with the webhook's shop identity. In reality, the HMAC only authenticates the raw body bytes; the `shop-domain` header that becomes `WebhookMetadata#shop` (the tenant identifier consumed by the app) is read straight from unauthenticated headers and never enters the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` decodes the `hmac-sha256` header [7](#0-6) [8](#0-7) . `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC [9](#0-8) . Neither the topic, the webhook id, nor — critically — the `shop` header is part of the signed string. `Request#shop` simply reads `shopify-shop-domain` (or `x-shopify-shop-domain`) from the header hash with no verification [2](#0-1) .

`Registry.process` raises `InvalidWebhookError` only if the body HMAC check fails, then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and calls the app's registered handler with it [5](#0-4) . Because a single `api_secret_key` is shared across every shop that installs the app, any valid `(raw_body, hmac)` pair legitimately produced for shop A remains a valid pair for the same body no matter which `shop-domain` header value accompanies it. An entity that controls one installed shop (an ordinary, unprivileged merchant of the app) can capture their own legitimately-signed webhook deliveries and resubmit them to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop's domain; `HmacValidator.validate` still returns `true` because it only checks the body, and the handler executes believing the data (`WebhookMetadata#shop`) belongs to the victim tenant.

Binding that should hold but doesn't: `hmac_is_valid(body, secret) == true` should imply `shop_header == shop_that_actually_sent_this_body`. Instead, `hmac_is_valid(body, secret)` is fully independent of `shop_header`, so an attacker can satisfy the former while forging the latter.

### Impact Explanation
This breaks the tenant boundary the webhook processing pipeline is supposed to enforce: `WebhookMetadata#shop` is the only tenant-scoping signal the gem hands to the host app's `WebhookHandler#handle`, and it is exactly the field described in the docs as coming from a request that's been verified to "come from Shopify" [6](#0-5) . A malicious merchant can cause the app to process attacker-controlled (but genuinely-Shopify-signed) webhook bodies under another shop's identity, leading to cross-tenant data corruption/injection in any app logic keyed off `data.shop` (e.g., order/customer records, redact handling, GDPR mandatory webhooks).

### Likelihood Explanation
Requires only an ordinary account with the app installed (a real, if attacker-controlled, shop), which is exactly the "unprivileged internet user" threat model in scope. No access token, `client_secret`, or leaked credential is needed — only capturing one's own legitimately delivered webhook and replaying it with a modified header, which any app installer can do trivially against a publicly reachable webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the material that is HMAC-verified, or independently authenticate the shop domain by cross-referencing it against a shop known to have installed the app with a matching webhook subscription before invoking the handler. At minimum, `Registry.process` should reject requests whose `shop` cannot be corroborated against server-side state (e.g., an active session/installation record) rather than trusting the header outright once the body HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) so Shopify sends a legitimately HMAC-signed POST with headers `x-shopify-hmac-sha256: <valid mac over raw_body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures the exact `raw_body` and `hmac` value from that delivery.
3. Attacker resends the same `raw_body`/`hmac` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the secret [10](#0-9) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the app to act on attacker-supplied content attributed to the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
