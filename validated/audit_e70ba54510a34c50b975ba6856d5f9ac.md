### Title
Webhook shop/topic/metadata headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`HmacValidator.validate` only proves that the HMAC matches `to_signable_string`, and for webhooks that string is the raw JSON body alone [1](#0-0) [4](#0-3) . The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are taken from unauthenticated headers [5](#0-4) , so the binding `hmac(raw_body) == valid` is treated as equivalent to `shop header == authentic shop that sent this body`, which is false — the two are independent.

### Finding Description
`Registry.process` treats a request as authentic strictly based on `Utils::HmacValidator.validate(request)` succeeding [6](#0-5) . That validator recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header using `OpenSSL.secure_compare` [7](#0-6) . For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body`, and `hmac` is read from the `hmac-sha256` header [8](#0-7) . Critically, the `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from other headers with no cryptographic coverage at all [2](#0-1) .

`Registry.process` then constructs `WebhookMetadata` from these unverified header values and passes it to the host application's webhook handler as the trusted tenant identity for the event [9](#0-8) ; per the gem's own documentation, apps are expected to use `data.shop` as the shop-domain key for routing/persisting webhook data [10](#0-9) .

Since `shop-domain` is not part of the signed material, any two webhook bodies with identical content produce identical HMACs regardless of which shop's header accompanies them. An attacker who controls a shop (e.g., subscribes their own test store to a webhook topic that produces attacker-influenceable body content, such as `products/update` with a crafted product title/note) receives a validly-signed `(body, hmac)` pair from Shopify. They can then replay that exact body+hmac pair to the app's public webhook endpoint while substituting the `shop-domain` (and/or `topic`/`webhook-id`) header to name a victim shop. `HmacValidator.validate` still succeeds because it never inspected the header, and the app's handler receives `WebhookMetadata` claiming the event is for the victim's shop, breaking the equality `shop header trusted by handler == shop that actually authored the body`.

### Impact Explanation
This is a cross-tenant identity-binding failure: the webhook pipeline lets an unprivileged user (any merchant who can install/operate the app on their own shop and receive a legitimately-signed webhook) inject attacker-controlled webhook payloads under a victim shop's identity into the host application, since the shop identity is unauthenticated relative to the HMAC. Depending on how the host app's `WebhookHandler#handle` implementation uses `data.shop` (e.g., to select which merchant's DB row to update, uninstall/cleanup state, or trigger data mutations), this can result in cross-tenant data corruption or state confusion attributed to another merchant, meeting the "cross-tenant access" bar for Critical/High impact called for by the scan rules.

### Likelihood Explanation
Exploitation requires only: (1) the attacker operates a shop that can install the target app and receive at least one webhook with attacker-influenceable or otherwise reusable body content, and (2) the attacker can send an arbitrary HTTP POST to the app's public webhook endpoint (which by definition is internet-reachable) with a modified `shop-domain`/`topic`/`webhook-id` header alongside the replayed legitimate body and `hmac` header. No access to `api_secret_key`, access tokens, or victim credentials is required, and no TLS interception or privileged access is needed — only control of the header values on a normal HTTP request, which any internet client can do.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signed material that `to_signable_string` returns for `Webhooks::Request`, or otherwise cryptographically bind them (e.g., verify the `shop-domain` header against a shop known to be subscribed to that specific `webhook_id`, or require handlers to independently verify tenant identity via a separate authenticated channel) before constructing and dispatching `WebhookMetadata` to the app's handler in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and registers/receives a legitimate webhook for a topic whose body they can influence (e.g., `products/update` with a crafted note field), obtaining a valid `(raw_body, x-shopify-hmac-sha256)` pair computed with the app's real `api_secret_key`.
2. Attacker sends `POST /callback/<topic>` to the target app's public webhook endpoint with:
   - `x-shopify-hmac-sha256`: unchanged from step 1 (still valid, since it only covers `raw_body`)
   - `x-shopify-shop-domain`: changed to `victim.myshopify.com`
   - `raw_body`: unchanged from step 1
3. `HmacValidator.validate` in `Utils::HmacValidator.validate` succeeds because it only checks the HMAC over `raw_body` [1](#0-0) .
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` from the spoofed header and invokes the app's `handle(data:)` with it [9](#0-8) , causing the host application to process attacker-controlled data as though it originated from the victim's shop.
