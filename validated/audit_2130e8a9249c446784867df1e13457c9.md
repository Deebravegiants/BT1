### Title
Tron `IntentGatewayV2.placeOrder` accepts duplicate input/output tokens, allowing double-credited escrow / over-release — unlike the hardened EVM `IntentGatewayV2` (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The `NounsDAOLogicV1Fork.quit` bug class — accepting a caller-supplied array with duplicate entries and paying out once per (duplicated) entry instead of once per unique entry — has a direct analog in Hyperbridge's Tron-specific `IntentGatewayV2.placeOrder`. The canonical EVM `IntentGatewayV2.sol` was hardened against exactly this bug (duplicate input/output tokens), as proven by dedicated regression tests, but the parallel Tron implementation still uses the unguarded, pre-fix pattern.

### Finding Description
In the main EVM `IntentGatewayV2.sol`, `placeOrder` explicitly rejects duplicate tokens in both `order.output.assets` (via transient-storage dedup check) and `order.inputs` (via `if (_orders[commitment][token] != 0) revert InvalidInput();`): [1](#0-0) [2](#0-1) 

These checks were added specifically to fix a prior bug, documented by the regression tests: [3](#0-2) [4](#0-3) 

The test comments state the root cause plainly: duplicate input tokens previously "merged into one escrow bucket" causing "same-chain partial fills [to] over-release repeated input escrow," and duplicate output tokens "shares one `_partialFills` bucket" causing "same-chain partial fills [to] prematurely finalize repeated output legs."

The Tron variant of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements `placeOrder` without any of these dedup guards:
- No duplicate check on `order.output.assets` (absent transient-storage loop equivalent to lines 196-221 of the EVM version).
- Input escrow is credited additively per input index rather than rejecting a repeated token: `_orders[commitment][token] += reducedInputs[i].amount;` [5](#0-4) 

This is exactly the pre-fix pattern the EVM regression tests were written to prevent — a user-submitted array of tokens/amounts (`order.inputs`, `order.output.assets`) is processed per-entry without a check for duplicate token addresses, letting duplicated entries collapse into shared per-token accounting buckets (`_orders[commitment][token]`, and presumably an analogous `_partialFills`-style bucket for outputs, if the Tron contract implements same-chain/partial fills).

### Impact Explanation
If the Tron `IntentGatewayV2` implements the same same-chain/partial-fill semantics as the EVM contract (which the shared imported types `FillOptions`, `SelectOptions`, `WithdrawalRequest` from the same base library suggest), a malicious order-placer can submit an order with duplicate input or output token entries. Because escrow/fill accounting is bucketed by `token` address rather than by array index, this allows:
- Escrow credited from a single deposit to be logically counted against multiple order legs, letting a solver release more tokens to the user than were actually escrowed (fund loss for solvers/protocol), or
- A single partial fill of one output leg to satisfy (finalize) multiple duplicated legs prematurely, releasing the user's full escrow for a fraction of the promised output (fund loss for the user, or an unbacked release of escrowed funds to solvers).

This is a direct token-theft / fund-freezing analog reachable by an ordinary user submitting `placeOrder` — no privileged or governance role required — matching the Nouns `quit()` bug class (attacker-supplied duplicate array entries defeating a balance/escrow accounting scheme keyed by identity rather than by array position).

### Likelihood Explanation
Likelihood is high given the fix was already necessary once (the EVM regression tests exist specifically because this bug was found and patched in the primary contract), and the Tron fork was evidently not updated to carry the same fix forward, indicating a straightforward "unpatched sibling implementation" issue. Any user can trigger the vulnerable code path with a single `placeOrder` call containing duplicated token entries; no special conditions or races are required.

### Recommendation
Port the duplicate-token rejection logic from `evm/src/apps/IntentGatewayV2.sol::placeOrder` (both the output-token transient-storage dedup loop and the `if (_orders[commitment][token] != 0) revert InvalidInput();` input-token guard) into `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, and add the equivalent Tron-side regression tests (`testRevert_PlaceOrder_DuplicateInputTokens`, `testRevert_PlaceOrder_DuplicateOutputTokens`) to prevent regressions.

### Proof of Concept
Not independently executable from static review alone — full confirmation requires exercising the Tron contract's fill/partial-fill path (function names for same-chain filling in this file could not be fully enumerated before the tool budget was exhausted) to demonstrate the double-credit/over-release. The structural evidence is: 
1. EVM `IntentGatewayV2.placeOrder` rejects duplicate input/output tokens with dedicated regression tests explaining the exploit this prevents.
2. Tron `IntentGatewayV2.placeOrder` lacks the equivalent checks and instead merges duplicate input tokens into a shared `_orders[commitment][token]` bucket via `+=`.

**Uncertainty**: I was unable to fully confirm (due to exhausted tool budget) whether the Tron `IntentGatewayV2` contract actually implements a same-chain/partial-fill mechanism analogous to `_partialFills` in the EVM version — this is the specific mechanism the EVM fix was protecting. If the Tron contract only supports full cross-chain fills settled once via `onAccept`/`withdraw` (as its `RequestKind` enum and lack of any `fillOrder`/`partialFill` matches in earlier greps suggested), the *output*-duplicate risk may be reduced, but the *input*-duplicate escrow-merging behavior remains a structural deviation from the hardened sibling contract and should still be verified/fixed.

        // Two input legs both using USDC — this previously merged into one escrow bucket

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});
