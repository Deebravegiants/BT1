## Vulnerability Analysis

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The external report describes a class of bug where a field that is *used* by downstream logic is not actually *covered* by the integrity mechanism meant to protect it. In `ShopifyAPI::Webhooks::Request`, the HMAC signature validated by `Utils::HmacValidator` is computed only over the raw HTTP body, while the `shop` value that the gem hands to the application's webhook handler is read directly from the unauthenticated `shop-domain`/`x-shopify-shop-domain` HTTP header.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/verifies the HMAC solely against that signable string [2](#0-1) . Meanwhile, `Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) are pulled straight from request headers with no cryptographic binding to the signed body [3](#0-2) .

`Registry.process` validates only the HMAC, then immediately trusts `request.shop` as the tenant identifier and forwards it to the app's handler as `WebhookMetadata`, without any check that this header value corresponds to the shop that actually produced the signed body: [4](#0-3) .

This breaks the intended binding `shop_verified_by_signature == shop_used_for_tenant_routing`. Contrast this with `Auth::Oauth::AuthQuery`, where `shop` (along with `code`, `host`, `state`, `timestamp`) is explicitly included in `to_signable_string` and thus IS covered by the HMAC [5](#0-4) . The webhook path lacks this equivalent protection for the tenant-identifying field.

### Impact Explanation
An unprivileged user who legitimately controls one Shopify store (Shop A) receives real webhook deliveries for that shop, each with a body and a valid HMAC computed by Shopify using the target app's shared `client_secret`. Because the header `shop-domain` is excluded from the signed content, that attacker can capture one such legitimate `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `shop-domain` header value with Shop B's domain. `HmacValidator.validate` still passes (it never inspects the header), and the app's registered handler receives `WebhookMetadata` claiming the event originated from Shop B [6](#0-5) . Any app logic that uses `data.shop` to select which tenant's data/session to mutate (a common pattern for webhook handlers, e.g., "delete this shop's data" or "update this shop's subscription record") would act on the wrong tenant — a cross-tenant data integrity/confidentiality break attributable to gem-provided identity information.

### Likelihood Explanation
The prerequisite is only that the attacker operates any single shop that has the target app installed (or can otherwise obtain one authentic webhook body+HMAC pair for that app, e.g. a low-privilege store employee), and can send a raw HTTP POST to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or the target shop's credentials is required, satisfying the "unprivileged internet user" bar. Reproducing a valid HMAC over a self-chosen body without server cooperation is not required — the same accepted, unmodified body/HMAC pair is replayed with only the header value changed.

### Recommendation
Bind the tenant-identifying and topic-identifying headers into the signed content that `HmacValidator` verifies (e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`, mirroring `AuthQuery`), or otherwise cryptographically bind the header values to the payload before trusting them for routing/tenant attribution in `Registry.process`.

### Proof of Concept
1. App developer registers a webhook handler that uses `data.shop` from `WebhookMetadata` to look up/act on tenant records.
2. Attacker installs the app on `attacker-shop.myshopify.com` and captures one delivered webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(client_secret, B)`.
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only and matches `H` — validation succeeds [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload actually originated from `attacker-shop.myshopify.com` [6](#0-5) .
