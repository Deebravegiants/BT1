### Title
Unchecked scaled-value multiplication in interest accrual freezes the market - (File: common/src/rates/simulate.rs)

### Summary
The accrual engine treats scaled balances and indexes as individually valid `i128` values, but unconditionally multiplies them together when deriving their underlying RAY values. [1](#0-0)  For a sufficiently large market, the borrow index can remain below `MAX_BORROW_INDEX_RAY` while `borrowed * borrow_index` or `supplied * supply_index` exceeds the `i128` range. [2](#0-1)  Once the market reaches that boundary, every operation that performs accrual panics before making progress, leaving deposits, debt repayment, liquidation, recapitalization, and revenue processing unavailable. [3](#0-2) 

### Finding Description
`accrue_step` calls `scaled_to_original` for total borrowed and supplied shares before selecting the interest rate. [1](#0-0)  `scaled_to_original` delegates directly to checked fixed-point multiplication, so a product that does not fit `i128` traps rather than saturating or reducing the scaled total. [4](#0-3) 

The borrow index is capped only after multiplying it by the interest factor, and that cap is `10^9 * RAY`, which is independent of the market's scaled-balance magnitude. [5](#0-4)  Consequently, a state can satisfy every explicit index bound while still being too large for the next value calculation. [2](#0-1) 

The same overflow can also occur when calculating supplier rewards, because `calculate_supplier_rewards` separately multiplies total debt by the old and new borrow indexes. [6](#0-5)  Supply growth has a similar multiplication through `supplied * old_index` in `update_supply_index`. [7](#0-6) 

Every pool mutation loads a synced market, and `synced_market` always calls `interest::global_sync` before the requested operation. [3](#0-2)  `global_sync` invokes `accrue_step` for each elapsed chunk, so a failed transaction does not advance `last_timestamp` and every later attempt repeats the same overflowing calculation. [8](#0-7) [9](#0-8) 

An unprivileged user reaches this path through ordinary `supply` and `borrow` calls to create the market state, and through permissionless `update_indexes` once the products no longer fit `i128`. [10](#0-9) [11](#0-10)  The controller forwards `update_indexes` directly to the pool. [12](#0-11)  The pool then loads each requested market and runs `global_sync`. [13](#0-12) 

### Impact Explanation
This is a market-wide denial of service affecting real funds rather than merely reverting one malformed request. [3](#0-2)  Suppliers cannot withdraw because withdrawal calls `load_leg`, which syncs the market before resolving or burning shares. [14](#0-13)  Borrowers cannot repay because repayment also calls `load_leg` before resolving debt. [15](#0-14) 

Liquidation cannot rescue the market because its debt-burn and collateral-seizure pool legs use the same accrual path. [16](#0-15)  Recapitalization likewise cannot bypass accrual because it calls `renewed_market` before calculating the backing shortfall. [17](#0-16)  Even a privileged parameter update accrues under the old model first, so it cannot lower the rate before hitting the panic. [18](#0-17) 

The repository's long-horizon regression test demonstrates the failure and explicitly verifies that withdrawal and repayment subsequently fail with `MathOverflow` while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [19](#0-18)  Therefore, absent a contract upgrade that changes the accrual path, user funds are frozen and the affected market cannot operate. [20](#0-19) 

### Likelihood Explanation
The exploit does not require malformed authorization, leaked keys, privileged calls, external services, or dishonest oracle input. [10](#0-9)  It does require a very large scaled balance and sustained interest growth such that a balance-index product approaches `i128::MAX` before the index reaches its configured ceiling. [21](#0-20) [5](#0-4) 

That precondition is capital-dependent and market-dependent, so it is less likely than an immediately triggerable arithmetic bug. [22](#0-21)  Nevertheless, the required state consists entirely of values the protocol accepts: positive supply, ordinary debt, indexes below the explicit cap, and elapsed time. [23](#0-22)  Once reached, the permissionless `update_indexes` call is sufficient to expose the frozen state, and no subsequent ordinary market verb can advance it. [13](#0-12) [24](#0-23) 

### Recommendation
Bound the product `scaled * index`, rather than only the index itself, before calculating utilization or accrued totals. [1](#0-0)  A safe design should detect that `borrowed > i128::MAX / borrow_index` or `supplied > i128::MAX / supply_index` before calling `Ray::mul`, then clamp accrual, mark the market accrual-safe, or split the state before performing the multiplication. [4](#0-3) 

A safer invariant is `borrowed <= i128::MAX / MAX_BORROW_INDEX_RAY` and `supplied <= i128::MAX / MAX_SUPPLY_INDEX_RAY`, enforced whenever debt or supply shares are minted. [25](#0-24) [2](#0-1)  Alternatively, add a recovery path that can advance `last_timestamp` without calculating the overflowing value, so parameter changes, debt repayment, liquidation, or emergency settlement are not all blocked by the same mandatory calculation. [3](#0-2) 

### Proof of Concept
The existing harness test constructs a market whose scaled balances are large enough for the balance-index product to hit the `i128` ceiling before the explicit borrow-index cap. [22](#0-21)  The transaction sequence is:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);

// Elapsed accrual is committed through the permissionless controller path.
t.advance_time(YEAR_SECS);
let result = t.try_update_indexes_for(&["BIG18"]);
```

The test then shows that `update_indexes` returns `MathOverflow`, while the committed borrow index remains below `MAX_BORROW_INDEX_RAY`. [26](#0-25)  Subsequent withdrawal and repayment attempts fail for the same reason because they must perform accrual first. [27](#0-26) [28](#0-27)

```rust
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)

        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };

    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"

    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
```
