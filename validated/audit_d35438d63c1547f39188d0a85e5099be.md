### Title
Refund path (`onPostRequestTimeout`) is blocked by `whenNotPaused`, permanently freezing user funds while the token is paused - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`HyperFungibleToken` and `WrappedHyperFungibleToken` (and their upgradeable counterparts) use a single `whenNotPaused` modifier to gate both the risky outbound action (`send`, which burns/locks funds and dispatches a cross-chain message) and the compensating exit/refund action (`onPostRequestTimeout`, which re-mints/unlocks funds to the original sender after a timeout). Pausing the contract — the intended safety mechanism during an incident — also blocks users from recovering funds for messages that have already timed out, exactly analogous to the reported "user cannot exit paused vaults" issue.

### Finding Description
`send()` burns (or locks) a user's tokens and dispatches an ISMP POST request. If that request times out without being delivered, the relayer submits a timeout proof and the host calls `onPostRequestTimeout`, which is supposed to refund the user by re-minting/unlocking the previously burned/locked amount: [1](#0-0) 

Both `send` and `onPostRequestTimeout` (and `onAccept`) share the same `whenNotPaused` modifier: [2](#0-1) [3](#0-2) 

The same pattern exists in the wrapped/locking variant, where `onPostRequestTimeout` unwraps/transfers the locked underlying ERC20/native tokens back to the refundee but is also gated by `whenNotPaused`: [4](#0-3) [5](#0-4) 

The same coupling is present in the upgradeable variants: [6](#0-5) [7](#0-6) 

Because pausing is an owner action typically triggered in response to a detected exploit, bug, or compromise (i.e., precisely when users are most likely to have pending, at-risk transfers), this design means that any user whose outbound transfer times out while the contract is paused cannot call/receive their refund until the owner unpauses. If the pause is prolonged (e.g., owner key compromised/unavailable, or the pause is intentionally extended while an incident is investigated), the burned/locked funds remain unrecoverable for the duration — the user cannot "exit."

### Impact Explanation
Users with in-flight cross-chain transfers that time out during a pause window have their principal permanently stuck (burned on the source side with no possibility of remint, or locked with no possibility of unlock) until the owner chooses to unpause. This is a freezing-of-funds condition directly caused by the contract's own safety mechanism, contradicting the expected security property that a pause should stop new risky actions while still allowing users to recover/exit existing positions. Severity is Medium: it requires a timeout to occur during a pause window (not attacker-controlled in isolation) but the impact — indefinite fund freezing for affected users — is significant and squarely within an in-scope reachable path (`send` → dispatch → timeout → `onPostRequestTimeout`).

### Likelihood Explanation
Pausing is intended to be used during genuine incidents (e.g., a discovered vulnerability, oracle/consensus issue, or compromise), which are exactly the situations where pauses may be held open longer and where users are more likely to have pending transfers approaching timeout. Any relayer-submitted timeout proof arriving while paused will revert, and the relayer has no way to force settlement, so the condition is reachable by ordinary protocol operation (owner pause + natural message timeout) without requiring any additional privileged or malicious actor.

### Recommendation
Split the pause gating so the exit/refund path is not blocked by the same switch as the risky forward path: remove `whenNotPaused` from `onPostRequestTimeout` (and consider doing the same for `onAccept`, which delivers already-committed messages rather than initiating new risk), or introduce a separate flag that pauses `send` only while leaving refund/timeout settlement and delivery of already-dispatched messages always available, consistent with the intended pause semantics of allowing exit during a pause.

### Proof of Concept
1. Owner calls `pause()` on `HyperFungibleToken` (or `WrappedHyperFungibleToken`), setting `_paused = true`.
2. A user had previously called `send()` before the pause with a `timeout` that has now elapsed without delivery.
3. A relayer submits the timeout proof to the ISMP host, which calls `onPostRequestTimeout` on the token contract.
4. The call reverts with `Pausable: paused` because of the `whenNotPaused` modifier on `onPostRequestTimeout` [3](#0-2) , so the user's burned/locked tokens are not refunded.
5. The user's funds remain frozen until the owner calls `unpause()`, which may not happen promptly (or at all) if the pause was triggered by an incident affecting the owner's ability/willingness to unpause quickly.

            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }
