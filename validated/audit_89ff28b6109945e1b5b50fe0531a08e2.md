### Title
Manipulated Uniswap V4 venue price drives unbounded solver overpayment in Simplex FXFiller (overfill clamp disabled) - (File: sdk/packages/simplex/src/strategies/fx.ts)

### Summary
The WePiggy incident stemmed from a manipulated oracle price flowing unchecked into a fund-moving decision (liquidation), because the affected code trusted a single, momentarily-wrong price without a bound. The analogous pattern exists in `hyperbridge--009`'s Simplex intent-solver: when a trading pair is priced from a Uniswap V4 pool (used "instead of a static curve," per `docs/content/developers/evm/simplex/pricing.mdx:42`), a manipulated/stale pool tick feeds directly into `FXFiller`'s fill-amount computation in `sdk/packages/simplex/src/strategies/fx.ts`, and the one safety mechanism that used to bound this risk (`maxOverfillBps`) has been explicitly disabled, leaving the computed payout uncapped.

### Finding Description
`FXFiller` prices venue-based pairs from live Uniswap V4 pool state (`computeDirectPoolPriceUsd` in `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts:246-275`, and the pool-based pricing path described in `docs/content/developers/evm/simplex/pricing.mdx:40-46`), treating "the pool... as the price oracle instead of a static curve."

In the core fill-sizing loop (`sdk/packages/simplex/src/strategies/fx.ts:601-701`), each leg's payable amount (`rawPolicyMaxOutput`) is computed from `resolveLegRates` (which for venue-priced pairs pulls the live pool price) via `computeLegPolicyOutput`. The code then computes an `overfillCeiling` bound (`output.amount * (10000n + maxOverfillBps) / 10000n`) but, per the inline comment at lines 678-701, does **not enforce it**:

```
// Overfill detection is warn-only: the clamp is DISABLED, so the filler
// fills the full computed amount even when it exceeds
// (1 + maxOverfillBps) × user-requested — including venue-priced legs
// (e.g. Uniswap V4). NOTE: this removes the per-leg loss bound that
// previously protected against a bug / stale cache / manipulated venue
// price. Output is no longer capped; we only emit a warning.
``` [1](#0-0) 

Instead of clamping, the branch only logs a warning and proceeds to pay `policyMaxOutput = rawPolicyMaxOutput` unmodified. This means the fill amount actually dispatched (and escrow released against, per `IntrinsicIntents.sol`'s pro-rata release noted in the surrounding comments) is bounded only by the venue price at the moment of pricing — a price an order placer can move via a swap immediately before submitting the order (classic pool-tick manipulation, the same bug class as WePiggy's momentarily-wrong CHE price feeding an unguarded liquidation calculation).

A separate, optional guard exists (`referencePrice`/`maxDeviationBps` in `docs/content/developers/evm/simplex/pricing.mdx:68-84`, tested in `sdk/packages/simplex/src/tests/strategies/fx.price-guard.test.ts:97-146`) but it is opt-in per position ("omit both to leave the chain unguarded") and is a separate mechanism from the overfill clamp described above — an operator who has not configured `referencePrice`/`maxDeviationBps` (the guard is explicitly optional) has no protection at all once the overfill clamp is disabled.

### Impact Explanation
An attacker who can move the Uniswap V4 pool tick backing a venue-priced pair (e.g., via a large swap or flash-loan-funded swap, since V4 pool state is read live at plan/fill time in `UniswapV4LiquidityState.refresh` and `computeDirectPoolPriceUsd`) can inflate the "exotic tokens per USD" price the filler believes it must pay. Because the overfill clamp is disabled, `FXFiller` will fill the order at the manipulated, inflated rate without any ceiling, directly transferring excess solver funds to the attacker's order. This is a direct, unbounded loss of solver-held funds triggered by a single crafted order plus a price manipulation transaction — the same class of harm as WePiggy's ~$400k loss from an unguarded, momentarily-wrong price feeding a fund-moving action.

### Likelihood Explanation
Medium-to-High: the attack requires the ability to move a Uniswap V4 pool's price (feasible for thinly-liquid "exotic" pairs, which are exactly the pairs this pool-based pricing mode targets per the docs) and to submit/win an intent order routed to the affected solver at that moment. No privileged access is required — an ordinary intent placer/order submitter (one of the explicitly in-scope unprivileged actors) can trigger this path. The mitigating `referencePrice`/`maxDeviationBps` guard is optional and off by default, and even where configured, it is a separate code path from the overfill clamp that was deliberately disabled.

### Recommendation
Re-enable enforcement of `maxOverfillBps` as a hard clamp (not warn-only) for venue-priced legs, or require `referencePrice`/`maxDeviationBps` to be mandatory (not optional) whenever a pair has no static curve and is priced solely from a Uniswap V4 pool. At minimum, cap `policyMaxOutput` to `overfillCeiling` before it is used to size wallet spend/funding-venue withdrawals in `fx.ts`.

### Proof of Concept
1. Operator configures a venue-priced pair (no `bidPriceCurve`/`askPriceCurve`) backed by a Uniswap V4 position, without setting `referencePrice`/`maxDeviationBps` (both optional per `docs/content/developers/evm/simplex/pricing.mdx:70-72`).
2. Attacker swaps a large amount in the underlying Uniswap V4 pool to push the tick so the exotic token appears far cheaper in USD than its true market price.
3. Attacker immediately submits (or wins the bid for) an intent order requesting the exotic token as output, sized against the manipulated pool price.
4. `resolveLegRates` reads the manipulated pool price; `computeLegPolicyOutput` computes an inflated `rawPolicyMaxOutput`.
5. The overfill check at `fx.ts:684-701` detects `rawPolicyMaxOutput > overfillCeiling` but only logs a warning (confirmed by inline comment stating the clamp is disabled); `policyMaxOutput` is not reduced.
6. The filler proceeds to fund and fill the order at the unclamped, manipulated amount, transferring excess solver funds to the attacker. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

## Pool-Based Pricing

When **`[vault.uniswapV4]`** lists at least one position, cross-asset pairs without curves derive bid/ask prices from **Uniswap V4 pool state** (current tick). The pool acts as the price oracle instead of a static curve. Note this yields a **single** price used in both directions — a venue-priced pair has no bid/ask spread of its own, so its margin comes from `order.fees` alone.

With Uniswap V4 positions configured, you can **omit** `bidPriceCurve` and `askPriceCurve` on the pair. Pool pricing requires the pair's `token0` to be a USD stablecoin, and same-token pairs always need their curve. The optional **`spreadBps`** field (basis points) sets the slippage tolerance for on-chain LP redemptions; defaults to `50` (0.50%).

Uniswap V4 venue pricing uses pools that pair the exotic token with **USDC or USDT** (addresses from your chain config). When multiple positions exist for the same exotic token on a chain, the most-liquid qualifying pool's price is used.

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}
