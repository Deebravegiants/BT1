### Title
Webhook HMAC signature does not bind the `shop` (tenant) identity, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop` (tenant identifier) and `topic` used to dispatch webhook handling are taken from unauthenticated HTTP headers that are never covered by the HMAC signature. Because the HMAC secret (`api_secret_key`, the app's `client_secret`) is the same across every shop that has installed the app, any party who can obtain one genuinely-signed `(body, hmac)` pair (e.g. by triggering a webhook on their own, legitimately-installed shop) can replay that exact body/hmac with a spoofed `x-shopify-shop-domain` header naming a victim shop, and `ShopifyAPI::Webhooks::Registry.process` will accept it and dispatch the handler as if the data belongs to the victim shop.

### Finding Description
`Utils::HmacValidator.validate` recomputes the signature purely over `verifiable_query.to_signable_string` and compares it to the `hmac` header: [1](#0-0) 

For webhook requests, `to_signable_string` is defined to be only the raw body: [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields, however, are read straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body) and then dispatches the handler using the unauthenticated `request.shop` and `request.topic`: [4](#0-3) 

This breaks the intended identity binding: **shop authenticated by the signature** should equal **shop the handler acts on**, but here `shop` is never part of what's signed. Because `api_secret_key` is the single app-level secret shared by every merchant/shop that installs the app (not a per-shop secret), a valid `(body, hmac)` pair produced for one shop remains cryptographically valid for a request that names any other shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: an unprivileged user who installs the target app on their own (attacker-controlled) shop can capture a legitimately-signed webhook body+hmac and replay it with a different `x-shopify-shop-domain` header, causing the host application's webhook handler to process attacker-supplied data under a victim shop's identity. Depending on the topic (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, `orders/create`, etc.) this can be used to trigger data deletion, state changes, or business logic attributed to a shop the attacker doesn't control — a cross-tenant access/integrity violation.

### Likelihood Explanation
Likelihood is moderate-to-high for any app relying solely on this gem's `Registry.process`/`HmacValidator.validate` for webhook authentication: no credential theft is required, only the ability to install the app on one's own store and capture one legitimately-issued webhook, then replay it with a modified header value against the app's public webhook endpoint.

### Recommendation
Include the `shop` (and ideally `topic`) in the signed/verified material, or otherwise cryptographically/contextually bind the header-derived `shop` to the specific installation before dispatching (e.g., verify the target shop has an active, matching session/installation prior to invoking handlers), rather than trusting `x-shopify-shop-domain` as an unauthenticated value once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (normal, unprivileged installation flow) and triggers any webhook topic the app subscribes to, capturing the raw body `B` and the corresponding `x-shopify-hmac-sha256` header value `H` sent by Shopify (valid because `H = HMAC_SHA256(client_secret, B)`, and `client_secret` is the same for all shops using this app).
2. Attacker sends a POST request to the app's public webhook endpoint with the same `raw_body = B` and `x-shopify-hmac-sha256 = H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and succeeds, since `to_signable_string` never included the shop header.
4. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, and the host application acts on attacker-controlled body content as if it were authoritative data for `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
