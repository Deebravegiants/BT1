## Finding [1](#0-0) 

The webhook `HMAC` only covers the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are taken from unauthenticated headers and handed to the application's handler as trusted identity.

### Title
Webhook shop identity is not covered by the HMAC, allowing cross-tenant webhook spoofing via header substitution — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header [3](#0-2) . `HmacValidator.validate` verifies the request using `verifiable_query.to_signable_string` (i.e. body only) against `Context.api_secret_key` — the same shared secret for every shop that has installed the app [4](#0-3) . `Registry.process` accepts the request once this body-only HMAC checks out and forwards `request.shop` verbatim to the app's handler as the authenticated tenant identity [5](#0-4) .

### Finding Description
The identity binding that should hold is:
`shop asserted in the signed payload == shop the handler treats as the source of truth`

Here it does not, because the `shop` header is outside the HMAC-signed material. Since a single `api_secret_key` is shared by the app across all merchant shops, any party that can obtain one legitimately-signed webhook body+HMAC pair for a shop under their own control (e.g., their own free/dev install of the app) possesses a `(body, hmac)` pair that will pass `HmacValidator.validate` for **any** value of the `shop-domain` header, because the header is never part of what is signed or verified.

An attacker who has installed the target app on their own store therefore can:
1. Trigger a webhook event on their own shop, capturing the genuine `x-shopify-hmac-sha256` value Shopify computed with the shared `api_secret_key`.
2. Replay that same raw body and HMAC to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain.
3. `Registry.process` validates the (unchanged) HMAC successfully and invokes the handler with `WebhookMetadata.new(topic:, shop: <victim-shop>, body:, ...)` [6](#0-5) , i.e. the application is told this payload authentically originates from the victim tenant, when it did not.

Any host application logic that keys off `WebhookMetadata#shop` to select which merchant's session/data to mutate (a standard pattern, e.g. re-syncing orders/products for "the shop the webhook says it's from") can be made to act on the wrong tenant's records using attacker-supplied body content signed against the attacker's own installation.

### Impact Explanation
This breaks the tenant isolation the HMAC is supposed to guarantee: the shop identity delivered to application code is not actually authenticated, only the payload bytes are. This enables cross-tenant confusion/injection into another merchant's webhook processing pipeline using only a legitimate installation of the app on an attacker-controlled shop — no access token, `client_secret`, or privileged access required. This matches the "Critical — cross-tenant access" impact category since the effective boundary between one merchant's authenticated event stream and another's is not enforced by the gem.

### Likelihood Explanation
Likelihood is realistic: an attacker only needs to install the target app on their own (free) development store to obtain valid `(body, hmac)` pairs signed with the app's shared secret, then send a forged HTTP request to the app's public webhook endpoint with a different `shop-domain` header — no secret material or elevated privileges are required.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`/`api_version`) values in the HMAC-signed material verified in `HmacValidator`, or otherwise cryptographically bind the shop domain to the payload (e.g. incorporate it into `to_signable_string`, or require handlers to cross-check `shop` against a resource identifier embedded in the signed body) so that `Registry.process` cannot be tricked into associating an attacker's signed payload with an arbitrary victim shop.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to.
2. Capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent for that event.
3. Re-POST the identical body and HMAC header to the app's webhook endpoint, replacing `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` (via `Utils::HmacValidator.validate`) accepts the request because only the body is verified [5](#0-4) , and the handler receives `WebhookMetadata` claiming the event is from `victim.myshopify.com`.

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
