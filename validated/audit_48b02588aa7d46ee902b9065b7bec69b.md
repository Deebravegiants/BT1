### Title
Webhook shop-domain header is trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then forwards the unauthenticated `shop-domain` header to the app's handler as the trusted tenant identifier. Since the header is not part of the signed payload, its value can be swapped for any shop domain while keeping a valid HMAC, breaking the binding "authenticated shop == shop attributed to the webhook".

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC (covering only the body) and then unconditionally trusts `request.shop` when constructing the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is documented as "The shop domain of the webhook" and is the field host applications are expected to use to attribute the event to a tenant (e.g., to enqueue tenant-scoped jobs or look up that shop's session/access token): [4](#0-3) [5](#0-4) 

This contrasts with `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` *is* included in `to_signable_string` and thus is HMAC-covered: [6](#0-5) 

The binding that should hold is:
`shop domain used by HMAC signer == shop domain delivered to app handler`

But because only the body is signed, an attacker who controls any legitimately-signed webhook body/HMAC pair for shop A (e.g., their own store, or a body they can predict/observe) can replay it with the `shopify-shop-domain` header rewritten to shop B. `Utils::HmacValidator.validate` recomputes the HMAC purely from `to_signable_string` (the body) and secret key, so it still validates: [7](#0-6) 

The result: the handler receives `data.shop == "shop-B"` for a payload that was never actually generated for shop B, even though the HMAC "passed."

### Impact Explanation
Applications that key tenant-scoped operations (job dispatch, per-shop access token lookups, per-shop database writes) directly off `WebhookMetadata#shop` — exactly as this gem's own documentation instructs (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) — can be made to attribute attacker-controlled or replayed webhook data to an arbitrary victim shop domain. This is a cross-tenant identity-binding failure: the field acted upon (`shop`) is not covered by the same authentication mechanism (HMAC) that is used to establish trust in the request.

### Likelihood Explanation
Exploitability depends on the attacker being able to obtain at least one validly HMAC-signed body/signature pair (trivially available to any merchant installing the app on their own store, since Shopify signs and delivers real webhooks to real merchants) and being able to redeliver a request to the app's webhook endpoint with a modified `shopify-shop-domain` header — something entirely under the control of an unprivileged internet user submitting HTTP requests, requiring no access token, `client_secret`, or privileged account.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) in the HMAC-covered signable string for webhooks, or otherwise cryptographically bind the `shop-domain` header to the signed body before trusting it as the tenant identifier — mirroring how `Auth::Oauth::AuthQuery#to_signable_string` already includes `shop` in its signed payload.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers/observes a real webhook delivery, capturing the raw body and its valid `X-Shopify-Hmac-SHA256` header (both generated by Shopify with the app's real secret).
2. Attacker resends that exact body/HMAC pair to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the signature over `to_signable_string` (the body only) — passes, since the body/HMAC pair is untouched: [8](#0-7) 
4. `Registry.process` builds `WebhookMetadata.new(..., shop: request.shop, ...)` using the forged header value `victim.myshopify.com`: [9](#0-8) 
5. The app's handler executes tenant-scoped logic against `victim.myshopify.com` using data that was never actually generated for that shop.
