Audit Report

## Title
Wildcard CORS origin allowlist bypass via unbounded suffix match - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's `isAllowedOrigin` function in `core/services/gateway/network/httpserver.go` matches wildcard CORS entries (`*.example.com`) using a bare `strings.HasSuffix(originHost, allowedHost)` check with no domain-label boundary, allowing any origin whose hostname string merely ends with the allowed suffix (e.g., `evilexample.com`) to pass as if it were a genuine subdomain of the allowed domain. This lets an attacker-controlled origin receive a reflected `Access-Control-Allow-Origin` header and interact cross-origin with the Gateway's `/user` endpoint. [1](#0-0) 

## Finding Description
`isAllowedOrigin` parses the request's `Origin` header and each configured `CORSAllowedOrigins` entry into scheme/host/port via `splitURL`. [2](#0-1)  After matching scheme and port, for wildcard entries it strips the `*.` prefix from `allowedHost` and checks only `strings.HasSuffix(originHost, allowedHost)`: [1](#0-0) 

This check has no requirement that a `.` character (domain-label boundary) precede the matched suffix in `originHost`. As a result, `originHost = "evilexample.com"` satisfies `strings.HasSuffix("evilexample.com", "example.com")` even though `evilexample.com` is an entirely distinct, attacker-registrable domain and not a subdomain of `example.com`.

This value is then used directly in `handleRequest` to set the CORS response headers, reflecting the attacker's own `Origin` value back: [3](#0-2)  No other validation (auth middleware, redaction, or additional origin checks) exists to catch this before the header is set.

## Impact Explanation
This is a real allowlist-bypass logic flaw in code that is exercised whenever `CORSEnabled=true` and a wildcard entry is configured in `CORSAllowedOrigins` — a supported, documented configuration pattern (not an insecure default). Under that condition, an attacker who registers a domain such as `evilexample.com` or `notexample.com` can have a hosted webpage issue cross-origin `fetch()`/XHR requests to the Gateway's `/user` endpoint and receive a reflected `Access-Control-Allow-Origin`, enabling the browser to expose the JSON-RPC response to that unrelated domain's script — a CORS allowlist bypass on an internet-facing Gateway component.

## Likelihood Explanation
No credentials, roles, or victim interaction beyond visiting the attacker's page are required; the attacker only needs to control a domain and set the `Origin` header, both fully within an unprivileged actor's control. The only precondition is the operator's use of a wildcard `CORSAllowedOrigins` entry, which is a normal, supported gateway configuration choice for scoping trust to a family of subdomains.

## Recommendation
Require an explicit domain-label boundary in the wildcard match, e.g., after stripping `*.`, check `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)` instead of a bare `strings.HasSuffix`. Consider using a vetted host/domain-suffix comparison utility rather than manual string splitting to avoid future boundary errors.

## Proof of Concept
1. Configure `HTTPServerConfig{CORSEnabled: true, CORSAllowedOrigins: []string{"https://*.example.com"}}`.
2. Send an HTTP request to the Gateway's `/user` endpoint with header `Origin: https://evilexample.com`.
3. Observe `isAllowedOrigin` returns `true` because `strings.HasSuffix("evilexample.com", "example.com")` is `true`.
4. Observe the response contains `Access-Control-Allow-Origin: https://evilexample.com`, confirming the bypass. A Go unit test calling `isAllowedOrigin("https://evilexample.com")` directly with the above config, asserting it returns `true` (when it should return `false`), demonstrates this deterministically.
