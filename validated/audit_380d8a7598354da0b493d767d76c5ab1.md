**Why the premise doesn't hold:**

1. **No such code path exists.** There is no "store-creation path that trusts any successfully-parsed `PublicKey` as the new store's controller" anywhere in the fungible asset / object model. Fungible asset stores (`FungibleStore`) are owned by an `address`, not by a `PublicKey` struct. Ownership is tracked via `object::owner` on the `Object` resource, and stores are created through `fungible_asset::create_store` / `primary_fungible_store::create_primary_store`, both of which take an `owner_addr: address` parameter derived independently of any raw `SlhDsaVerifyingKey` bytes. [1](#0-0) 

2. **`PublicKey::from_bytes_unchecked` in `slh_dsa_keys.rs` only performs format/structural validation**, not custody logic. It rejects wrong-length input and anything that fails `SlhDsaVerifyingKey::<Sha2_128s>::try_from`, but it is a crate-internal (`pub(crate)`) constructor used purely for cryptographic key material deserialization — it has no connection to the Move object/fungible-asset custody surface. [2](#0-1) 

3. **The "discrete-log" framing is a category error.** SLH-DSA is a hash-based signature scheme (stateless hash-based signatures), not an elliptic-curve/discrete-log scheme. There is no discrete-log relationship to "discover" or forge in the first place — the security property in question (owning a valid-looking public key with no known private key) is not a distinguishing weakness of this code; it is inherent to *any* public-key-derived address scheme in *any* blockchain, including Aptos accounts generally (e.g., burn addresses, resource accounts with unknown seeds). This is an accepted, intentional property, not a custody violation.

4. **No demonstrated crossing of a custody boundary.** The question does not identify an actual unprivileged transaction/entrypoint that (a) parses attacker-supplied bytes as an `SlhDsaVerifyingKey`, (b) derives an account address from it, and (c) uses that address to become the "owner" field of a real fungible asset store via `split`/`create_store`, bypassing any authorization check. Object/store creation always requires either an existing signer (the entity actually calling `create_store`/`primary_fungible_store::create_primary_store`) or an explicit `owner_addr` argument supplied by the (already-authorized) caller — the store's controller is the account owning the resulting object, and no `ConstructorRef`/`TransferRef`/authority is granted merely by an address existing without a known private key. [3](#0-2) 

Given the Decision Standard requiring the path to "cross a real custody boundary and change who can own, move, mint, burn, freeze, upgrade, or recover value," and given there is no code linking `slh_dsa_keys.rs` public-key parsing to fungible-asset store ownership assignment, this does not meet the bar.

    pub(crate) fn from_bytes_unchecked(

    ) -> std::result::Result<PublicKey, CryptoMaterialError> {

        }
        // VerifyingKey uses TryFrom<&[u8]> for deserialization
