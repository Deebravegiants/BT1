### Title
Emporium stateless-op arbitrary call lets attacker forge `CircomData.originalSender` and steal any victim's ERC20 approval via `DepositOnChainUtxosExternalAction.runAction` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol` / `contracts/external-actions/DepositOnChainUtxosExternalAction.sol`)

### Summary
`EmporiumUpgradeable.runAction`'s "Case 2: Stateless Interaction" branch forwards attacker-controlled `op.callData` to any `op.endpoint` via a raw `.call()`, with no constraint tying that inner call's payload to the zk-proof-verified outer `CircomData`. When the endpoint is another `IExternalActionV2` such as `DepositOnChainUtxosExternalAction` that trusts `circomData.originalSender` as the token owner to pull funds from, an attacker can supply a forged inner `CircomData` whose `originalSender` is any victim with a standing ERC20 approval, causing `transferERC20TokenFrom` to move the victim's tokens to the attacker's Emporium-controlled UTXO.

### Finding Description
The broken equality: **AUTHORITY** — the `from` address in `transferERC20TokenFrom(token, from, msg.sender, tokenTotal)` inside `DepositOnChainUtxosExternalAction.runAction` (`contracts/external-actions/DepositOnChainUtxosExternalAction.sol:76-81`, `userAddress = circomData.originalSender` at line 31) must equal the account that the zk-SNARK proof and `HinkalHelper.performHinkalChecks` bind as `circomData.originalSender`. `performHinkalChecks` only enforces this equality for the **outer** `CircomData` struct passed to `Hinkal.transact`:

```
require(
    (circomData.originalSender == address(0) && circomData.relay != address(0)) ||
    (circomData.originalSender == sender && circomData.relay == address(0)),
    "invalid value for originalSender"
);
``` [1](#0-0) 

The attacker's exploit path:
1. Attacker calls `Hinkal.transact(a,b,c,dimensions,circomData)` where `circomData.originalSender == attacker` (satisfies the outer check) and `circomData.externalActionData` targets `EmporiumUpgradeable`.
2. `circomData.externalActionData.externalActionMetadata` decodes to an `EmporiumStack` with `signerAddress == address(0)`. Because `verifyWallet` returns early when `stack.signerAddress == address(0)` (no ECDSA signature check at all, only the `usedMessages` nonce is marked used) [2](#0-1) , this stack requires zero authorization beyond being wrapped in the attacker's own valid proof.
3. `stack.ops[0]` is a stateless op (`invokeWallet=false`) whose `callData = abi.encodeCall(IExternalActionV2.runAction, (forgedCircomData, [0]))`, targeting `DepositOnChainUtxosExternalAction`. `EmporiumUpgradeable.runAction` executes `op.endpoint.call{value: op.value}(op.callData)` with no validation of the encoded call's contents, only rejecting `callHinkalWallet`/`doSendToRelay` selectors [3](#0-2) .
4. `DepositOnChainUtxosExternalAction.runAction` executes with `msg.sender == Emporium`, satisfying `onlyAllowedRecipient` (`isAllowedRecipient[Emporium] == true` per stated precondition) [4](#0-3) . It reads `forgedCircomData.originalSender = victim` and calls `transferERC20TokenFrom(tokenAddress, victim, msg.sender=Emporium, tokenTotal)` [5](#0-4) , which succeeds because the victim previously approved `DepositOnChainUtxosExternalAction` directly (the spender identity in the `IERC20` call is the `DepositOnChainUtxosExternalAction` contract itself, since Emporium's call is a plain external call, not a delegatecall).
5. Tokens land on `Emporium`'s balance; `EmporiumUpgradeable.runAction`'s post-loop `handleOut` then mints the attacker a UTXO for that balance increase, credited to the attacker's own `stealthAddressStructure` from the *outer* (attacker-controlled) `circomData` [6](#0-5) .

Root cause: `forgedCircomData` is arbitrary attacker-chosen bytes buried inside `EmporiumStack.ops[].callData`, which itself is only part of the metadata hashed into the *outer* proof's `calldataHash` (`getHashedCalldata1` includes `circomData.externalActionData` [7](#0-6) ). That hash only proves the attacker's own proof matches their own chosen bytes — it says nothing about whether the semantic content of those bytes (a forged, unverified inner `CircomData`) is legitimate. No component in the call chain (`Hinkal.transact`, `performHinkalChecks`, `verifyProof`, `EmporiumUpgradeable.runAction`, `ExternalActionBaseV2.onlyAllowedRecipient`) ever re-verifies that an inner `CircomData.originalSender` used by a downstream action corresponds to a real proof or to `msg.sender` of the top-level `transact` call.

### Impact Explanation
Direct theft of any ERC20 tokens a victim has approved to `DepositOnChainUtxosExternalAction` (or any other `IExternalActionV2` implementation reachable this way that trusts `circomData.originalSender` for a `transferFrom`), fully credited to the attacker as a valid shielded UTXO. This is Critical: direct theft of a victim's (pre-approved) funds without any signature or proof binding the victim to the transaction, repeatable against every victim with a standing approval, limited only by `usedMessages`/`emporiumMessage` nonce uniqueness per attacker transaction (trivially incremented for repeat attacks).

### Likelihood Explanation
Preconditions required: (1) `EmporiumUpgradeable` registered and configured as `isAllowedRecipient` on `DepositOnChainUtxosExternalAction` (a plausible/likely admin configuration since both are legitimate composable external actions meant to be chained); (2) a victim holds a nonzero standing ERC20 approval to `DepositOnChainUtxosExternalAction`. Given these, the attacker needs only their own funds and one self-generated valid proof for their own outer `transact` call — no privileged role, no victim interaction, no compromised infrastructure. This is fully within the "unprivileged attacker" threat model and trivially repeatable per distinct `emporiumMessage`.

### Recommendation
`EmporiumUpgradeable`'s stateless op path must not be allowed to invoke other `IExternalActionV2.runAction` implementations with an independently-crafted `CircomData`. Either (a) disallow stateless ops from targeting any address registered as an `IExternalActionV2` in `Hinkal.externalActionMap`/`isAllowedRecipient` sets, or (b) require every downstream action reachable via arbitrary `op.callData` to independently re-verify caller-provided `originalSender`/ownership (e.g., require an explicit signature or on-chain approval check scoped to the *actual* caller of `Hinkal.transact`, not a value passed in a nested, unverified struct). At minimum, `DepositOnChainUtxosExternalAction` (and any similar action pulling funds via `transferERC20TokenFrom(circomData.originalSender, ...)`) should never be reachable from Emporium's stateless/no-signature op path.

### Proof of Concept
Foundry fork test:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (initialized with `DepositOnChainUtxosExternalAction`'s allowed-recipient config granting Emporium as allowed recipient), `DepositOnChainUtxosExternalAction`, and a mock ERC20.
2. `victim.approve(DepositOnChainUtxosExternalAction, X)`.
3. Attacker builds outer `CircomData` with `originalSender = attacker`, `externalActionData` pointing at `Emporium`, `externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: DepositOnChainUtxosExternalAction, invokeWallet: false, callData: abi.encodeCall(IExternalActionV2.runAction, (forgedCircomData, [int256(0)]))}]})`, where `forgedCircomData.originalSender = victim`, `forgedCircomData.externalActionData.externalActionMetadata = abi.encode(uint256[][] utxoAmounts)` summing to `X`.
4. Attacker generates a valid snarkjs proof for the outer `circomData` (their own transaction).
5. Call `hinkal.transact(a,b,c,dimensions,circomData)`.
6. Assert: `mockERC20.balanceOf(victim)` decreased by `X`; attacker's minted UTXO (via `EmporiumUpgradeable.handleOut`) increased by `X`; victim never signed or submitted any transaction. [8](#0-7) [9](#0-8) [10](#0-9)

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) external override onlyAllowedRecipient returns (UTXO[] memory utxoSet) {
        uint256 tokenCount = circomData.erc20TokenAddresses.length;
        require(
            tokenCount > 0 && deltaAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: token count mismatch"
        );

        address userAddress = circomData.originalSender;
        require(
            userAddress != address(0),
            "DepositOnChainUtxosExternalAction: Invalid originalSender"
        );

        uint256[][] memory utxoAmounts = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (uint256[][])
        );
        require(
            utxoAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: metadata length mismatch"
        );

        utxoSet = new UTXO[](countUtxos(utxoAmounts));

        uint256 utxoIndex = 0;
        for (uint256 i = 0; i < tokenCount; i++) {
            require(
                deltaAmounts[i] == 0,
                "DepositOnChainUtxosExternalAction: Delta amount must be zero"
            );

            address tokenAddress = circomData.erc20TokenAddresses[i];
            uint256 tokenTotal = 0;

            for (uint256 j = 0; j < utxoAmounts[i].length; j++) {
                uint256 amount = utxoAmounts[i][j];
                require(
                    amount > 0,
                    "DepositOnChainUtxosExternalAction: UTXO amount must be positive"
                );
                tokenTotal += amount;

                utxoSet[utxoIndex] = UTXO({
                    amount: amount,
                    erc20Address: tokenAddress,
                    stealthAddressStructure: circomData.stealthAddressStructure,
                    timeStamp: circomData.timeStamp + utxoIndex
                });
                utxoIndex++;
            }

            if (tokenAddress != address(0) && tokenTotal > 0) {
                transferERC20TokenFrom(
                    tokenAddress,
                    userAddress,
                    msg.sender,
                    tokenTotal
                );
