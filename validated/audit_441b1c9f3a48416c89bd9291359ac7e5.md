### Title
`IntentGatewayV2._withdraw` reverts the entire escrow settlement if any single output token transfer fails, permanently freezing multi-token orders - ([File: evm/src/apps/intentsv2/IntentsBase.sol], mirrored in [File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2`'s escrow settlement path (`withdraw`/`_withdraw`, invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` and from `onGetResponse` for source-side cancels) marks the order as settled and then loops over every escrowed token performing a raw `.call` transfer, reverting the whole function with `TransferFailed()`/`InsufficientNativeToken()` if any single transfer fails. Exactly like Derby's `Vault.blacklistProtocol`, which coupled an emergency state change (blacklisting) to a mandatory `withdrawFromProtocol` that could revert, this coupling means one uncooperative/paused/blacklisting token among an order's several input tokens blocks the *entire* settlement — including the tokens that would have transferred fine — with no way to retry or skip the bad leg.

### Finding Description
The withdrawal helper is reached from three unprivileged-triggerable paths:
- `onAccept` for `RequestKind.RedeemEscrow`/`RefundEscrow`, delivered by any relayer relaying a Hyperbridge message [1](#0-0) 
- `onGetResponse`, delivered by a relayer completing a source-side order cancellation [2](#0-1) 

Both call into the shared withdraw logic, whose (mirrored) implementation is: [3](#0-2) 

The function:
1. Immediately marks `_filled[body.commitment] = beneficiary`, committing the order to a terminal settled state.
2. Iterates `body.tokens`, and for each ERC-20 token performs `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`, reverting the entire transaction with `TransferFailed()` if that single call fails.
3. Also force-transfers accumulated `TRANSACTION_FEES` via the same all-or-nothing pattern.

Because the state mutation (`_filled[...] = beneficiary`) and every token transfer happen inside one atomic call with no per-token fallback, a single problematic input token — e.g., a USDC-style token that blacklists the beneficiary address, a token that is paused, or one that simply reverts on transfer to a particular address — causes the *entire* multi-token order's refund/redemption to permanently fail. This is the same root-cause pattern as the Derby report: a recovery/settlement action that *must* succeed atomically with an external call whose failure is outside the caller's control, with no parameter or fallback to skip the failing leg and still finalize on the rest.

Unlike the Derby case (a privileged guardian action), here the blocked settlement is reachable and directly damaging to end users: any order with ≥2 input tokens where one of them can be made to revert (attacker-influenced token behavior, e.g. transfer-blacklist, pausable token, or a token that reverts on non-EOA/zero-code recipients) becomes permanently unsettleable — the escrow can never be redeemed by the solver nor refunded to the user, because every call into `_withdraw` for that commitment reverts identically.

### Impact Explanation
This causes **permanent freezing of user/solver funds**: once `_withdraw` is unconditionally required to succeed for every token in the order and one token transfer is unconditionally revert-prone, the escrowed assets for the *entire* order (including the otherwise-fine tokens) become permanently stuck. There is no admin/governance override to force a partial withdrawal or to net out the failing token, and repeated relayer delivery attempts (`onAccept`) or GET-response processing (`onGetResponse`) will deterministically re-revert, so the message can never be delivered/settled — matching the "route unable to deliver messages" / "permanent freezing of funds" impact classes.

### Likelihood Explanation
Reachable by any solver placing/filling a multi-input order, or by an attacker who can craft/influence one of the input tokens in an order (e.g. via calldata-driven token selection, or targeting existing tokens known to have transfer restrictions such as blacklist-capable stablecoins). No privileged role is required to trigger the freeze — only to have one qualifying token among the order's inputs, and for that token's owner (or the order's own attacker-supplied token list, depending on how tokens are chosen at order-placement time) to later block transfers to the beneficiary. This makes it a realistic, not merely theoretical, denial/freeze vector for cross-chain intents settlement.

### Recommendation
Decouple the mandatory state transition from the mandatory token transfer, mirroring the original report's recommendation:
- Process each token transfer independently (try/catch or low-level call without reverting the loop), crediting successfully transferred tokens and recording any failed-transfer amounts in a per-user, per-token "claimable" balance that can be retried later via a separate, ungated `claim(token, beneficiary)` function.
- Alternatively, allow `_withdraw` to be re-invoked/retried per-token so a single bad token cannot block settlement of the rest, and expose a governance/relayer path to mark a specific unrecoverable token balance as forfeited/swept once safe, rather than reverting the entire settlement indefinitely.

### Proof of Concept
1. User places a cross-chain order with two input tokens: `USDC` (blacklist-capable) and `DAI`.
2. Attacker (or USDC's centralized issuer, or a governance action against a compromised address) blacklists the beneficiary address in `USDC` after escrow but before settlement.
3. Order is filled/cancelled and a relayer delivers the corresponding `RedeemEscrow`/`RefundEscrow` message via `onAccept`, or the GET response via `onGetResponse`.
4. `_withdraw` sets `_filled[commitment] = beneficiary`, then loops the tokens; the `USDC.transfer` call reverts (or returns `false`), causing `TransferFailed()` to bubble up and the *whole* call reverts.
5. Because `_filled[commitment]` write is part of the same reverted transaction, the order remains in escrow forever; every subsequent relayer delivery attempt for the same commitment re-executes the same reverting path, permanently freezing both the blacklisted `USDC` and the otherwise-transferable `DAI`.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
