### Title
Permanent lock of attached NEAR in `MultisigFactory::create` due to missing success-check/refund callback - (File: `multisig-factory/src/lib.rs`)

### Summary
The external report describes ether being permanently locked in a `payable` function because the contract lacks a completion/withdrawal check that verifies the operation succeeded and refunds any funds that cannot be used. The NEAR analog is in `multisig-factory/src/lib.rs`'s `create` function: unlike its sibling factories (`staking-pool-factory`, `lockup-factory`), it attaches a deposit, creates a sub-account, deploys the multisig contract, and calls `new` — all in a single unchecked promise batch — with **no callback to verify success and no refund path** if the deployed contract's `#[init] new()` panics.

### Finding Description
`staking-pool-factory::create_staking_pool` and `lockup-factory::create` both follow the same pattern: build a promise batch (`create_account().deploy_contract(...).transfer(attached_deposit).function_call("new", ...)`), then `.then(ext_self::on_X_create(...))` a callback that checks `is_promise_success()` and, on failure, refunds the attached deposit back to the caller: [1](#0-0) [2](#0-1) 

`multisig-factory::create`, in contrast, builds the identical kind of promise batch but has **no `.then()` callback at all**: [3](#0-2) 

Within a single NEAR receipt/promise batch, a failing `FunctionCall` action (e.g. the `new()` init panicking) does not roll back the preceding actions in the same batch — `create_account`, `deploy_contract`, and `transfer` still take effect, leaving a deployed-but-uninitialized contract holding the attached deposit. `MultiSigContract` uses `PanicOnDefault`, so once `new()` fails to run to completion, the account has no state and no method can be called on it (every call falls back to `Default::default()`, which panics). This is reachable by any unprivileged caller who invokes `create` with inputs that make `multisig2::new()`'s assertions fail, such as `num_confirmations` exceeding `members.len()`: [4](#0-3) 

Because `multisig-factory` has no callback analogous to `on_staking_pool_create`/`on_lockup_create`, there is no code path that detects the failed initialization and refunds the attached NEAR — the funds are sent to a newly created account that becomes permanently unusable and unrecoverable.

### Impact Explanation
This matches the "Critical: Permanent freezing/unrecoverable lock of user or protocol funds" impact category. Any user calling `multisig-factory::create` with a deposit and an invalid `(members, num_confirmations)` combination (or any other input that makes `multisig2::new()` panic, e.g., after future validation additions) will have their attached NEAR permanently stuck in a bricked, uninitialized contract account with no administrator recovery mechanism, unlike the sibling factories which correctly refund on failure.

### Likelihood Explanation
Likelihood is high for a self-inflicted mistake (e.g., a user misconfiguring `num_confirmations > members.len()`), which is technically a "user error," but the root cause is a genuine contract defect: the other two factories in the same codebase explicitly guard against this exact scenario with a refund callback, demonstrating the intended/safe design that `multisig-factory` fails to implement. Any wallet/dApp integration bug, off-by-one, or minor input mistake by an unprivileged, first-time caller (this is the primary/only entry point for creating a multisig account) triggers irreversible loss, with no way for the caller or any administrator to recover the funds afterward.

### Recommendation
Add a callback to `MultisigFactory::create` mirroring `on_staking_pool_create` / `on_lockup_create`: after the account-creation promise, chain a callback (`ext_self::on_multisig_create`) that checks `is_promise_success()` and, if the deployment/initialization failed, transfers the attached deposit back to `env::predecessor_account_id()`.

### Proof of Concept
Not independently executed (no sandbox/build available in this environment); the vulnerability is derived directly from static comparison of `multisig-factory/src/lib.rs` against the equivalent, correctly-guarded `staking-pool-factory/src/lib.rs` and `lockup-factory/src/lib.rs` callbacks. A concrete PoC would call `multisig-factory::create` with `members = [{"account_id": "a"}]` and `num_confirmations = 2` (violating `assert(members.len() >= num_confirmations, ...)` in `multisig2::new`) while attaching NEAR, then confirm on-chain that the new account is created and funded but has no callable multisig methods and no refund receipt is issued back to the caller.
