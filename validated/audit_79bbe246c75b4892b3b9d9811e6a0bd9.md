### Title
Duplicate-assetId batch withdrawals cause `describeWithdrawal` to report the same (status, txHash) for two distinct destination payouts - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`IntentsSDK.signAndSendWithdrawalIntent` / `processWithdrawal` accept a `WithdrawalParams[]` batch with no validation preventing two POA-bridge legs from sharing the same `assetId`. `findMatchingWithdrawal` in `poa-bridge.ts:418-427` resolves a withdrawal purely by `nep141:${near_token_id} === assetId` via `Array.prototype.find`, so when two legs share an `assetId`, `describeWithdrawal` called for `index=0` and `index=1` both return the first COMPLETED entry the POA API lists, misreporting one leg's status/txHash as the other's.

### Finding Description
The broken equality: for `index=0`, `describeWithdrawal({..., index:0})` should equal the on-chain outcome of the withdrawal targeting `destinationAddress[0]`; for `index=1` it should equal the on-chain outcome of `destinationAddress[1]`. Because `findMatchingWithdrawal` (`poa-bridge.ts:418-427`) ignores `index` entirely and matches only on `assetId`: [1](#0-0) 
both calls invoke `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` with the identical `assetId`, and `.find()` returns the same first-matching element for both, regardless of `index`. [2](#0-1) 

Reachability: `IntentsSDK.signAndSendWithdrawalIntent` and `IntentsSDK.processWithdrawal` accept `WithdrawalParams[]` and build one intent per entry with no assetId-uniqueness check: [3](#0-2) 
`createWithdrawalCompletionPromises` then creates one `WithdrawalIdentifier` per array index via `createWithdrawalIdentifiers`, and each is watched/described independently: [4](#0-3) 
Nothing in `supports()`, `validateWithdrawal()`, or `createWithdrawalIdentifier()` in `poa-bridge.ts` rejects duplicate `assetId` across batch elements — `createWithdrawalIdentifier` (lines 295-311) just stores `index` and `withdrawalParams` per-element but that `index` is never used when matching the POA status response.

Attacker's exact input: an ordinary user submits a batch of two `WithdrawalParams` for the POA route with identical `assetId` (e.g., `nep141:usdc.omft.near`) but two different `destinationAddress` values (attacker-controlled address A and B). Both intents settle on NEAR in the same transaction hash `args.tx.hash`. When the integrator's code calls `describeWithdrawal` for index 0 and index 1 (e.g. via `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`), the POA `getWithdrawalStatus({withdrawal_hash: tx.hash})` API returns both withdrawal entries in unspecified order; `findMatchingWithdrawal` returns the same entry (e.g., the one destined for address A that completed) for both index=0 and index=1 lookups, since both calls pass the same `assetId` and ignore index. The file's own comment acknowledges this: "multiple withdrawals of the same token in a single transaction are not supported."

Existing guards that fail to prevent this: `validateAddress`/`compareAddresses` only validate a single destination address format, not batch-level assetId uniqueness; `supports()` and `validateWithdrawal()` operate per-leg and have no cross-leg awareness; there is no `assert` anywhere checking that POA-routed withdrawals in a batch have distinct assetIds.

### Impact Explanation
An integrator polling withdrawal status per index will see `index=1` (destination B, still pending or with a different real outcome) falsely reported as `completed` with `txHash` belonging to the payout actually sent to destination A. This is a status/hash misreport that can cause the integrator to credit or consider settled a withdrawal that either didn't happen yet or went to a different address/amount — matching the High-severity category "a status or hash misreport making an integrator credit or refund twice." Repeatable on every batch withdrawal request containing two same-`assetId` POA legs.

### Likelihood Explanation
Preconditions: the attacker must be the one submitting the withdrawal batch (it's their own funds/keys) and must choose the POA bridge route (assetId under `poaTokenFactoryContractID`) twice with the same token but different destinations in a single batch — nothing in the public SDK surface (`signAndSendWithdrawalIntent`, `processWithdrawal`) blocks this. Attacker cost is a single normal transaction; feasibility is high since it only requires calling documented public batch APIs with permitted parameter values. Fully repeatable.

### Recommendation
Make `findMatchingWithdrawal` order-aware and index-consistent: sort the POA API's `withdrawals` array deterministically (e.g., by amount, consistent with the file's own comment) and sort withdrawal params the same way, then match by position, or explicitly reject (throw) when constructing withdrawal identifiers if two POA-routed legs within the same batch share the same `assetId`, since POA API dedup by assetId is documented as unsupported.

```typescript
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```

```typescript
	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
	}
```
