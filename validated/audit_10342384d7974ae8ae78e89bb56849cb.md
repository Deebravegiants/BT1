### Title
Escrow withdrawal and dust sweep silently fail for false-returning ERC20 tokens due to unchecked return-data in `IntentGatewayV2.withdraw`/`onAccept` (Tron) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` performs ERC20 payouts for escrow redemption/refund and dust-sweep using a raw low-level `.call` with `IERC20.transfer.selector`, and only checks that the call itself did not revert (`success`). It never decodes/validates the boolean return value. For ERC20 tokens that signal failure by returning `false` instead of reverting (e.g. ZRX-style tokens), the low-level call succeeds (`success == true`) even though no tokens were transferred, while the code still mutates escrow accounting as if the payout succeeded.

### Finding Description
In `withdraw()`, which is invoked from `onAccept` when an unprivileged, ISMP-relayed `RedeemEscrow`/`RefundEscrow` request is delivered, escrowed ERC20 tokens are paid to the beneficiary via: [1](#0-0) 

The call only checks `success` from the low-level `call`, not the decoded boolean return value:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
For any ERC20 implementation that returns `false` on failed transfer instead of reverting, `success` will still be `true` (the low-level call itself does not revert), so the `!success` check never triggers. Immediately after, the code unconditionally decrements the escrow balance: [2](#0-1) 

The same faulty pattern recurs for the transaction-fee payout in the same function and for the `SweepDust` branch of `onAccept`: [3](#0-2) [4](#0-3) 

This is the same root cause the external report flags in `FootiumPrizeDistributor.claimErc20Prize` — using a transfer mechanism that does not distinguish a "false" return from a true success, and permanently updating internal accounting before/without verifying actual token movement. Notably, the sibling (non-Tron) `evm/src/apps/IntentGatewayV2.sol` contract imports and uses `SafeERC20`'s `safeTransferFrom`/`safeTransfer` throughout the equivalent input-taking flows [5](#0-4) , confirming the Tron variant's `withdraw`/`onAccept` payout paths deviate from the safe pattern used elsewhere in the same protocol.

### Impact Explanation
`onAccept` is called by the host whenever a valid ISMP proof for a `RedeemEscrow`/`RefundEscrow`/`SweepDust` request is delivered — this is reachable by any relayer submitting a legitimately authenticated cross-chain message, not a privileged actor. If the escrowed input/output/fee token is a non-reverting, boolean-returning ERC20 (a supported and expected asset class in an open intents system), a transfer that silently fails (e.g., due to a blacklist, paused state, or other implementation-specific failure condition) will still cause:
- `_orders[body.commitment][token]` to be decremented as if funds were paid out, permanently marking the order as settled (`_filled[body.commitment] = beneficiary`), while the beneficiary never receives the tokens.
- Escrowed transaction fees to be wiped (`delete _orders[body.commitment][TRANSACTION_FEES]`) without the fee recipient receiving payment.
- Swept dust tokens to be reported/emitted as delivered when they were not.

This results in permanent loss of user/solver funds locked in escrow with no path to recovery, since the order is marked filled/refunded and the escrow ledger entry is already zeroed out.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: the Tron token ecosystem historically includes tokens using the boolean-return (non-reverting) ERC20 pattern, and the Intent Gateway is explicitly designed to be token-agnostic (arbitrary ERC20 assets configured for orders). No special privilege is needed to trigger the vulnerable path — any legitimately relayed `RedeemEscrow`/`RefundEscrow`/`SweepDust` message for an order using such a token will trigger silent fund loss.

### Recommendation
Use OpenZeppelin's `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;` at the top of this contract) instead of raw `.call` + `success`-only checks in `withdraw()` (both the token loop and the fee payout) and in the `SweepDust` branch of `onAccept`. `safeTransfer` correctly reverts on both a hard revert and a `false` boolean return, ensuring escrow accounting is only mutated once the transfer has genuinely succeeded.

### Proof of Concept
1. Register/escrow an order whose input or output token is a boolean-return ERC20 that can be made to return `false` on transfer (e.g., due to a blacklist flag on the beneficiary, or a paused state).
2. A relayer submits a valid ISMP `RedeemEscrow` request for that order to `onAccept`.
3. `withdraw()` executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`; the token contract returns `false` without reverting, so `success == true`.
4. `_orders[body.commitment][token] -= amount` executes, and `_filled[body.commitment] = beneficiary` is set, permanently marking the order fulfilled/refunded.
5. The beneficiary never receives any tokens, and since the escrow entry is already decremented and the order is marked filled, there is no mechanism to retry or recover the funds — resulting in permanent loss.
