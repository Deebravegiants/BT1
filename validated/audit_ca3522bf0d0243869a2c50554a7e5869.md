### Title
Quadratic-cost EVM GET-response state-proof verification via repeated contract-proof re-parsing - (File: `modules/ismp/state-machines/evm/src/lib.rs`)

### Summary
`verify_state_proof` in the EVM `StateMachineClient` re-decodes and rebuilds an in-memory trie from the *entire* shared account (contract) proof once per distinct contract address referenced by a `GetRequest`, instead of building it once. This mirrors the Exiv2 `JpegBase::readMetadata` bug class: a shared blob is reparsed once per logical entry, turning linear work into quadratic work as the number of entries (here, distinct contract addresses in one GET batch) grows.

### Finding Description
When a `GetResponseMessage`/`ResponseMessage` is handled on the destination chain, `pallet-ismp`'s `handlers::response::handle` calls `state_machine.verify_state_proof(host, keys, state.state_root, &proof)` for each `GetRequest` in the batch [1](#0-0) .

For EVM destinations this dispatches to `verify_state_proof` in `modules/ismp/state-machines/evm/src/lib.rs`. That function groups the request's raw keys by contract address into `contract_to_keys`, then iterates every distinct contract present in the decoded `evm_state_proof.storage_proof` map and, for each one, calls:

```rust
let contract_root = get_contract_account::<H>(
    evm_state_proof.contract_proof.clone(),
    &contract_address,
    root,
)?
``` [2](#0-1) 

`get_contract_account` takes the **entire** `contract_proof` (the shared multi-account Merkle-Patricia proof that authenticates every requested contract's account leaf), clones it, and rebuilds a full in-memory trie DB from scratch:

```rust
pub fn get_contract_account<H: Keccak256 + Send + Sync>(
	contract_account_proof: Vec<Vec<u8>>,
	contract_address: &[u8],
	root: H256,
) -> Result<Account, Error> {
	let db = StorageProof::new(contract_account_proof).into_memory_db::<KeccakHasher<H>>();
	let trie = TrieDBBuilder::<EIP1186Layout<KeccakHasher<H>>>::new(&db, &root).build();
	...
}
``` [3](#0-2) 

`StorageProof::new(...).into_memory_db()` copies and hashes every node in the proof to build a `HashMap`. Because `contract_proof` covers all requested accounts (its size grows with the number of distinct contracts, roughly O(N·log N) for N accounts due to shared trie prefixes), and this clone+rebuild is repeated once *per contract* inside the `for (contract_address, storage_proof) in evm_state_proof.storage_proof` loop, the total cost of `verify_state_proof` scales with N (contracts) × O(N log N) (proof size) ≈ O(N² log N) instead of the O(N log N) a single trie build would cost.

The comments in the code already acknowledge that "resolving a contract means cloning the whole contract proof and rebuilding its trie" is a per-call cost — the code goes out of its way to reject duplicate/unrequested keys *before* this cost is incurred (see `EvmStateMachineError::DuplicateKey` and `UnrequestedContractProof` checks and their accompanying comments) [4](#0-3)  — but it does not eliminate the cost when the batch legitimately references many *distinct* contract addresses, which is exactly the case a `GetRequest` with many 52-byte keys spanning many contracts produces.

`GetRequest.keys` is an unbounded `Vec<Vec<u8>>` set by the dispatching application/user with no maximum-length or maximum-distinct-contract-count enforced anywhere in `modules/ismp/core/src/router.rs` or the dispatcher path (`modules/pallets/ismp/src/dispatcher.rs`) [5](#0-4) [6](#0-5) ; no `MAX_KEYS` bound exists in the searched codebase.

### Impact Explanation
An unprivileged application or user can dispatch a `GetRequest` whose `keys` reference a large number of distinct contract addresses on an EVM-based counterparty. Once relayed with a legitimately-generated (honest) proof, the destination chain's response handler is forced to execute `verify_state_proof`, which repeats a full clone + trie-DB rebuild of the (large) shared contract proof once per distinct contract. This is quadratic (or worse) in the number of distinct contracts, allowing computation cost to grow much faster than the size of the extrinsic/proof itself — a classic algorithmic-complexity DoS on the on-chain response-handling path (`pallet-ismp` `handlers::response::handle`), which runs inside block execution. This can stall or degrade the destination parachain's block production/weight budget when processing otherwise "valid" GET responses, and the same helper is reused by `SubstrateEvmStateMachine::verify_state_proof` for contract-info resolution, and by `verify_membership`/`verify_non_membership` paths that also call `get_contract_account` — though the primary GET-response path is the one most directly reachable and scaled by user-controlled key/contract count.

### Likelihood Explanation
Medium. The precondition (a `GetRequest` with many keys across many distinct contracts) is entirely user-controlled since there is no enforced bound on the number of keys per request or contracts touched. However, it requires the requester to pay dispatch fees for a large request and requires a relayer to actually deliver the honest, large proof (self-relaying is possible, so no cooperation from an honest relayer is strictly needed). This makes it a realistic but not trivially cheap griefing vector — unlike duplicate-key repetition (already patched with the `DuplicateKey` check), it cannot be rejected up front because every contract is legitimately distinct and requested.

### Recommendation
Build the account trie (`StorageProof::new(...).into_memory_db()` + `TrieDBBuilder`) exactly once per `verify_state_proof` invocation, hoisting it out of the per-contract loop, and pass a reference to the shared trie into `get_contract_account`/`get_values_from_proof` for each contract lookup instead of re-decoding the whole `contract_proof` per contract. Additionally, enforce an explicit upper bound on the number of keys (and/or distinct contract addresses) permitted in a single `GetRequest`/`GetResponseMessage`, consistent with the protocol's stated bounded-verification design goals evidenced by the existing `DuplicateKey`/`UnrequestedContractProof` checks.

### Proof of Concept
1. Attacker dispatches a `GetRequest` (via `DispatchGet`) to an EVM destination with `keys` = N distinct 52-byte keys `contract_i(20) || slot(32)` for N distinct contract addresses (no bound rejects this in `modules/ismp/core/src/router.rs` / `modules/pallets/ismp/src/dispatcher.rs`).
2. The attacker (or any relayer) queries an honest combined account+storage proof (as built client-side in `sdk/packages/sdk/src/chains/evm.ts::queryStateProof`), yielding an `EvmStateProof` whose `contract_proof` covers all N accounts and whose `storage_proof` map has N entries.
3. The relayer submits a `ResponseMessage` to the destination chain; `pallet-ismp`'s `handlers::response::handle` calls `verify_state_proof` once per `GetRequest`.
4. Inside `verify_state_proof` (`modules/ismp/state-machines/evm/src/lib.rs:223-238`), the `for (contract_address, storage_proof) in evm_state_proof.storage_proof` loop executes N times, and each iteration calls `get_contract_account` which clones the full `contract_proof` and rebuilds a trie DB from it (`modules/ismp/state-machines/evm/src/utils.rs:130-147`) — total work is O(N) rebuilds of an O(N log N)-sized proof, i.e., O(N² log N), verifiable by benchmarking `verify_state_proof` with increasing N and observing super-linear wall-clock growth relative to total proof-byte size.

```rust
pub fn get_contract_account<H: Keccak256 + Send + Sync>(
	contract_account_proof: Vec<Vec<u8>>,
	contract_address: &[u8],
	root: H256,
) -> Result<Account, Error> {
	let db = StorageProof::new(contract_account_proof).into_memory_db::<KeccakHasher<H>>();
	let trie = TrieDBBuilder::<EIP1186Layout<KeccakHasher<H>>>::new(&db, &root).build();
	let key = H::keccak256(contract_address).0;
	let result = trie
		.get(&key)
		.map_err(|_| EvmStateMachineError::InvalidContractAccountProof)?
		.ok_or(EvmStateMachineError::ContractAccountNotPresent)?;

	let contract_account = <Account as Decodable>::decode(&mut &*result)
		.map_err(|_| EvmStateMachineError::ContractAccountDecodeError)?;

	Ok(contract_account)
}
