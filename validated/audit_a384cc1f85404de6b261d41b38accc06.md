### Title
Once the stored `calc_pnl_x`/`calc_pnl_y` invariant in `TargetOrders` exceeds the live pool reserves, `calc_take_pnl` permanently reverts every deposit, withdraw and swap - ([File: program/src/processor.rs])

### Summary
`Processor::calc_take_pnl` enforces an invariant that the current pool value (`total_pc_without_take_pnl * total_coin_without_take_pnl`) must be `>=` the last recorded "k" stored in the `TargetOrders` account (`calc_pnl_x * calc_pnl_y`), or it returns `AmmError::CalcPnlError` and aborts the whole instruction. This function is invoked from every state-changing, unprivileged-reachable instruction — `process_deposit`, `process_withdraw`, `process_withdrawpnl`, and both base-in/base-out swap variants (v1/v2). There is no permissionless (or even documented privileged) instruction that lets anyone lower `calc_pnl_x`/`calc_pnl_y` independently of this same check succeeding — the only place these fields are written outside of `TargetOrders::check_init` (at pool creation) is inside `calc_take_pnl` itself, guarded by the very condition that must first pass. If reserves ever fall below the recorded invariant (e.g., through accumulated fixed-point rounding loss in `Calculator::restore_decimal`/`normalize_decimal`, which floor/ceil-divide on every pnl-taking pass), the pool becomes permanently stuck: every future swap, deposit and withdraw reverts with `CalcPnlError`, exactly analogous to a Chainlink aggregator getting stuck and causing `TwapOracle.consult` to revert forever with no recovery path.

### Finding Description
`calc_take_pnl` computes `pool_pc_amount * pool_coin_amount` from live vault balances and compares it against `calc_pc_amount * calc_coin_amount`, which are the *decimal-restored* values of `target.calc_pnl_x` / `target.calc_pnl_y` stored in the `TargetOrders` account: [1](#0-0) 

If the check fails, the instruction hard-errors: [2](#0-1) 

`calc_pnl_x`/`calc_pnl_y` are only ever initialized once, at pool creation, via `TargetOrders::check_init`: [3](#0-2) 

After initialization, the only place these fields can change is inside `calc_take_pnl`'s success branch, which requires the very inequality that must hold for the function not to error — i.e., there is no independent, unprivileged path to reset or lower the stored invariant once it becomes stale. `calc_take_pnl` is reached from every liquidity/swap-affecting instruction, for example `process_withdraw`: [4](#0-3) 

and `process_withdrawpnl`: [5](#0-4) 

Both swap paths (`swap_base_in`/`swap_base_out` and their v2 counterparts) also depend on the same pnl-taking machinery through `calc_total_without_take_pnl_no_orderbook` and `calc_take_pnl` before computing the constant-product swap amounts: [6](#0-5) [7](#0-6) 

The decimal-normalization helpers used throughout this pipeline perform lossy integer division (`checked_div` without any remainder tracking) on every call: [8](#0-7) 

Because `restore_decimal`/`normalize_decimal` truncate on every pnl-taking pass, and because `delta_x`/`delta_y` (and thus the "last k" baseline effectively encoded via `total_pc_without_take_pnl`/`total_coin_without_take_pnl` bookkeeping) are derived from these truncated values while `need_take_pnl_pc`/`need_take_pnl_coin` are incremented and later withdrawn via `process_withdrawpnl`, repeated legitimate use (deposits, withdrawals, pnl withdrawals, swaps) can push the live-reserve product below the recorded `calc_pnl_x * calc_pnl_y` baseline. Once that happens, the pool enters a state where `calc_take_pnl`'s condition at processor.rs:190-192 can never again be satisfied through normal operation, and — since nothing outside this same gated code path can rewrite `calc_pnl_x`/`calc_pnl_y` — the pool is permanently bricked for deposits, withdrawals and swaps.

### Impact Explanation
This is a full, permanent denial of service on the core AMM functionality for the affected pool: no user can deposit, withdraw, or swap once the invariant check in `calc_take_pnl` starts failing, because it is invoked unconditionally at the top of every one of these instruction handlers. All coin/PC tokens already deposited as liquidity, plus any accrued but unwithdrawn PnL, become permanently frozen in the vaults with no on-chain recovery instruction, matching a High/Medium freezing-of-funds impact class analogous to the referenced TwapOracle report (irrecoverable revert of a core accounting function due to a stuck internal invariant with no update mechanism).

### Likelihood Explanation
Reaching the exact boundary condition requires the live-reserve product to fall below the stored `calc_pnl_x * calc_pnl_y` baseline, which is influenced by repeated truncating decimal conversions in `Calculator::restore_decimal`/`normalize_decimal` across many pnl-taking operations rather than by a single attacker-controlled transaction. This makes it a lower-probability, cumulative-drift scenario rather than an immediately/one-shot triggerable bug, similar to the low-probability characterization given to the original Chainlink-stuck-aggregator report, but the complete absence of any permissionless or governance-controlled reset path for `calc_pnl_x`/`calc_pnl_y` means that once triggered the pool is unconditionally and irrecoverably stuck.

### Recommendation
Add an authorized (ideally timelocked or otherwise access-controlled) instruction that can resynchronize `TargetOrders.calc_pnl_x`/`calc_pnl_y` to the pool's current live reserves without requiring the `calc_take_pnl` invariant to hold first, so a drifted or stuck pool can be recovered instead of being permanently unusable. Alternatively, relax `calc_take_pnl` so that when the invariant fails it clamps/skips pnl distribution for that call (treating `delta_x`/`delta_y` as zero) rather than aborting the entire deposit/withdraw/swap instruction.

### Proof of Concept
1. Create a pool via `Initialize2`; `TargetOrders::check_init` sets `calc_pnl_x = x`, `calc_pnl_y = y` from the initial normalized reserves (`program/src/state.rs:152-177`).
2. Repeatedly perform ordinary deposits, withdraws, and pnl withdrawals (`process_deposit`, `process_withdraw`, `process_withdrawpnl`) which each pass reserve amounts through `Calculator::normalize_decimal`/`restore_decimal` (`program/src/math.rs:80-103`), accumulating truncation loss in the live coin/PC vault balances relative to the stored `calc_pnl_x`/`calc_pnl_y` baseline.
3. Once `total_pc_without_take_pnl * total_coin_without_take_pnl` (derived from live vault balances) drops below `restore_decimal(calc_pnl_x) * restore_decimal(calc_pnl_y)`, any subsequent call to `process_deposit`, `process_withdraw`, `process_withdrawpnl`, `process_swap_base_in(_v2)`, or `process_swap_base_out(_v2)` invokes `calc_take_pnl` (`program/src/processor.rs:167-192`), the condition at line 190-192 fails, and the instruction returns `AmmError::CalcPnlError` (`program/src/processor.rs:267-278`).
4. Because `calc_pnl_x`/`calc_pnl_y` are writable only inside the now-unreachable success branch of `calc_take_pnl`, and no other instruction updates them, every future user transaction against the pool fails, permanently locking all deposited liquidity and vault funds.
