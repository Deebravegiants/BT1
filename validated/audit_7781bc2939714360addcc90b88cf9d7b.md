## Finding: Unrestricted `CallDispatcher.dispatch()` allows anyone to steal tokens/ETH stranded in the shared dispatcher contract

### Title
Permissionless `dispatch()` on the shared `CallDispatcher` allows theft of any token/ETH balance left on it - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is the exact "too generic calls" pattern the LiFi report describes: an `external`, access-control-free function that performs `to.call{value: call.value}(call.data)` on attacker-supplied `to`/`data`. It is used as a shared, singleton executor by `HyperFungibleToken`/`WrappedHyperFungibleToken` (token mint/unlock + calldata execution) and by `IntentGatewayV2`/`IntentsBase` (predispatch/postdispatch order calldata), all of which route user tokens through it before or after arbitrary calldata execution. Because `dispatch()` has no caller restriction, anyone can invoke it directly at any time to sweep out whatever token or native balance happens to be sitting on the `CallDispatcher` at that moment.

### Finding Description
`CallDispatcher.dispatch()` is defined with no modifier and no caller check: [1](#0-0) 

Any address can call it and force it to execute arbitrary `Call{to, value, data}` entries as `CallDispatcher`'s own `msg.sender` context - the only check is that `to` has code (`extcodesize`), not that the caller is a trusted gateway/app.

Multiple production apps deposit tokens into this same shared contract before invoking calldata on it, and at least one of them performs no post-execution sweep:

- `HyperFungibleToken.onAccept` mints tokens directly to the `beneficiary` (which the docs instruct integrators to set to the `CallDispatcher` address so subsequent calls can spend them) and then dispatches attacker/user-supplied calldata, with **no sweep of any unspent remainder** back to a safe owner: [2](#0-1) 

- The same pattern (mint/unlock to dispatcher, then dispatch, no sweep) exists in `HyperFungibleTokenUpgradeable.onAccept`: [3](#0-2) 

- `IntentsBase._execute` and the `IntentGatewayV2` predispatch flow *do* attempt to sweep dust back to `address(this)` via another `dispatch()` call, but that sweep itself is just another unrestricted `dispatch()` invocation and only runs if execution reaches that point in the same transaction: [4](#0-3) [5](#0-4) 

The project's own documentation acknowledges the dispatcher temporarily custodies funds and explicitly warns against unlimited allowances "since the dispatcher contract holds tokens temporarily during execution" — an implicit admission that anything left on the dispatcher (dust, unconsumed approvals, unswept remainders) is at risk, but the fix applied (docs advice to use exact approvals) does not address the real gap: `dispatch()` itself is callable by anyone, not just the app that deposited the funds.

### Impact Explanation
Because `CallDispatcher` is a single, shared, persistent contract reused across `HyperFungibleToken`, `WrappedHyperFungibleToken`, and the Intents apps, any token/native balance that is not fully and atomically consumed and swept within the depositing transaction (e.g., a calldata-execution swap that leaves rounding dust, a malformed/partially-successful `Call[]`, or simply a legitimate cross-chain mint-to-dispatcher whose downstream calls under-spend) becomes permanently exposed. Since `dispatch()` has no access control, any third party can call it directly with a `Call{to: token, data: transfer(attacker, balance)}` to drain that stranded balance before the intended owner/app can reclaim it. This is theft of user/protocol funds, matching the High severity of the referenced LiFi issue.

### Likelihood Explanation
Likelihood is elevated by the fact that `HyperFungibleToken`/`WrappedHyperFungibleToken`'s `onAccept` calldata-execution path has no sweep logic at all, and the documented recommended integration pattern (minting to the `CallDispatcher` so downstream calls can spend the funds) is exactly the pattern that leaves funds on the dispatcher. Any imperfect calldata (attacker-supplied via `Message.data`, or a benign integrator's swap calldata that doesn't consume 100% of the minted amount) leaves a balance that is then trivially stealable by anyone monitoring the shared `CallDispatcher` address, since `dispatch()` requires no privilege and no proof of ownership over the residual balance.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to authorized callers (e.g., an `onlyAuthorized`/allow-list of the apps that are expected to use it, similar to how `SwapperV2` whitelisting was recommended for the LiFi facet), or make each app deploy/own its own dispatcher instance instead of sharing one contract across unrelated apps.
- Ensure every caller of `dispatch()` (especially `HyperFungibleToken`/`WrappedHyperFungibleToken`'s `onAccept`) sweeps any residual token/native balance off the dispatcher back to a safe, protocol-controlled address within the same transaction, mirroring the dust-sweep already present in `IntentsBase._execute`.
- Alternatively, redesign `CallDispatcher` so it never holds a standing balance between calls — require exact-amount, single-use approvals and have the calling app pull funds back atomically, removing any window where an unauthorized `dispatch()` call could find something to steal.

### Proof of Concept
1. A relayer delivers a legitimate cross-chain HFT transfer whose `Message.data` mints tokens to the `CallDispatcher` address and instructs it to `approve` + `swap` on a DEX, per the documented pattern.
2. The swap's actual output/input differs slightly from the exact minted amount (slippage, rounding, or a `Call[]` that intentionally under-spends), leaving a small token balance stranded on `CallDispatcher` after the `onAccept` transaction completes — no sweep step exists in `HyperFungibleToken.onAccept`.
3. An attacker observes the `CallDispatcher`'s token balance (a public on-chain balance) and submits their own transaction calling `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: transfer(attacker, balance)})]))` directly — no privilege check prevents this.
4. The attacker's call succeeds and transfers the stranded balance to themselves, repeatable for any future dust that accumulates from any app sharing the same `CallDispatcher`.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
