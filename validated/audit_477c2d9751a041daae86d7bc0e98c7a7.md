Confirmed: `WrappedHyperFungibleToken.send()` uses `params.amount` directly (nominal), not the actual received balance, when computing the message body dispatched cross-chain. This confirms the analog vulnerability.

### Title
WrappedHyperFungibleToken is incompatible with fee-on-transfer/rebasing ERC20 tokens, allowing unbacked mints and permanent freezing of bridged funds - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken` locks an underlying ERC20 on the home chain and instructs the remote `HyperFungibleToken` to mint the nominal `params.amount` to the recipient. Unlike `IntentGatewayV2`, which explicitly measures actual balances received to defend against fee-on-transfer tokens [1](#0-0) , `WrappedHyperFungibleToken.send()` never checks the actual amount of tokens it received before dispatching the cross-chain message.

### Finding Description
In `send()`, the contract calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and then immediately builds the dispatch message using the caller-supplied `params.amount`, without measuring the wrapper's actual token balance delta: [2](#0-1) 

The message body embeds `params.amount` verbatim via `_buildDispatchPost`: [3](#0-2) 

When this message is delivered on a remote chain, `HyperFungibleToken.onAccept()` unconditionally mints `message.amount` new tokens to the beneficiary — an amount that is never validated against what is actually escrowed on the home chain: [4](#0-3) 

- If `_underlying` is a **fee-on-transfer token**, the wrapper receives less than `params.amount`, yet the remote chain mints the full nominal amount — an unbacked mint that exceeds the tokens actually held in escrow.
- If `_underlying` is a **negative-rebasing token** (balances shrink over time/epoch), previously escrowed collateral held by the wrapper can decay below the cumulative amount promised to remote-chain token holders, again leaving remote mints unbacked.
- If `_underlying` is a **positive-rebasing token**, the wrapper's balance grows without any corresponding accounting update, but this excess is simply stranded (not directly a loss, though it does show the accounting model cannot track true balances).

In the fee-on-transfer/negative-rebase cases, the wrapper becomes insolvent: the sum of tokens promised (backing minted supply on remote chains, and any still-locked sender who has not yet bridged back) permanently exceeds `IERC20(_underlying).balanceOf(address(this))`. Because `onAccept()` (unlock/refund path) uses `safeTransfer(beneficiary, message.amount)` for a full nominal amount: [5](#0-4) 

once the wrapper's actual balance is insufficient, subsequent unlocks/timeout refunds will revert (`safeTransfer` failing on insufficient balance), permanently freezing funds for whichever user attempts to redeem after the shortfall manifests — a first-come-first-served insolvency race exactly analogous to the OpenQ rebasing-token report where "internal accounting will not match the proper balances... [users] will miss out."

### Impact Explanation
This breaks solvency guarantees of the lock/unlock bridge for any token with fee-on-transfer or negative-rebasing semantics (a widely deployed ERC20 category, e.g. reflection tokens, some yield-bearing/rebasing stablecoins). Any unprivileged user can trigger the unbacked mint simply by calling `send()` with such a token as `_underlying` (assuming that token was chosen/whitelisted by the wrapper owner for a given deployment) — this is a reachable single-transaction cross-chain dispatch requiring no special privileges. The result is either (a) unbacked mint of the remote representation, inflating its circulating supply beyond the collateral backing it, or (b) permanent freezing of funds for later users unable to redeem/timeout-refund once the wrapper's real balance is exhausted.

### Likelihood Explanation
Likelihood depends on the operator's choice of `_underlying` token when deploying/configuring a `WrappedHyperFungibleToken` instance; the wrapper places no restriction on token type and provides no documentation warning against fee-on-transfer or rebasing tokens (unlike `IntentGatewayV2`, which was explicitly hardened and tested for fee-on-transfer tokens). Given fee-on-transfer and rebasing tokens are common in the ERC20 ecosystem, and Hyperbridge's SDK/docs encourage third parties to deploy their own `WrappedHyperFungibleToken` for "existing ERC20 tokens" generically, the likelihood of an incompatible token being wrapped is realistic without additional protocol-level restriction or accounting fixes.

### Recommendation
Mirror the fix already applied in `IntentGatewayV2`: measure the wrapper's actual token balance before and after `safeTransferFrom` in `send()`, and use the delta (actual received amount) — not the caller-supplied `params.amount` — when building the dispatch message and the amount to be minted on the destination chain. Additionally, document/restrict rebasing tokens as unsupported underlying assets, since even a balance-delta fix at send-time does not protect against negative rebases occurring after funds are already escrowed.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` on chain A configured with `_underlying` set to a fee-on-transfer token (e.g., 1% fee, as modeled by `FeeOnTransferToken` used in `IntentGatewayV2SameChainTest.sol`).
2. Deploy the peer `HyperFungibleToken` on chain B and register both as peers via `addChain`.
3. Attacker/any user calls `send(SendParams{ amount: 1000e18, to: attacker, dest: chainB, ... })`. The wrapper's `safeTransferFrom` pulls only 990e18 tokens (1% fee burned by the token itself) into the wrapper, but the dispatched message still encodes `amount: 1000e18`.
4. On chain B, `HyperFungibleToken.onAccept()` mints 1000e18 tokens to the attacker — 10e18 more than what is actually collateralized on chain A.
5. Repeating this creates a growing shortfall between the wrapper's actual underlying balance and the cumulative minted supply on remote chains. Once other legitimate holders attempt to bridge back and call `onAccept`/unlock (or trigger a timeout refund) on chain A, `safeTransfer` reverts due to insufficient underlying balance, permanently freezing their funds.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
