### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` bind the HMAC signature only to the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. [1](#0-0)  `Webhooks::Registry.process` validates only that the body's HMAC matches, then dispatches the handler using the header-derived `shop` and `topic` values without any cryptographic link between them and the signed body. [2](#0-1) 

### Finding Description
The intended identity binding is: `hmac == HMAC(secret, shop ∥ topic ∥ body)`, i.e., the shop/topic the handler acts on should be cryptographically tied to the same bytes that were verified. Instead, the actual binding implemented is `hmac == HMAC(secret, body)` while `shop`/`topic` are taken verbatim from headers that are never part of the signed material:

- `to_signable_string` returns `@raw_body` only. [3](#0-2) 
- `shop`, `topic`, `webhook_id`, `api_version` are pulled straight from `@headers` with no involvement in `hmac`. [4](#0-3) 
- `Registry.process` raises only if the body HMAC is invalid, then immediately builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` for dispatch to the app-registered handler. [2](#0-1) 

Because the HMAC secret used for webhooks is the app's single, global `client_secret` (`ShopifyAPI::Context.api_secret_key`, the same value used everywhere else in this gem, e.g. `Utils::HmacValidator`) [5](#0-4)  and not a per-shop secret, every shop that has installed the app (any unprivileged internet user can install a public app on their own store) receives webhooks whose body+HMAC pair is valid under that same shared secret. Any such shop owner can capture one of their own legitimate webhook deliveries (body + `x-shopify-hmac-sha256`), and replay it directly to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header with a different shop's domain. `Utils::HmacValidator.validate` will still succeed (body/HMAC pair is unchanged and correctly signed), and `Registry.process` will hand the attacker-chosen body to the handler tagged with the victim's shop identity. [2](#0-1) 

Before the attacker's request: `hmac` is valid only for (secret, own-shop's-body). After the attacker's request: the gem still reports the HMAC as valid and reports `data.shop == victim-shop`, even though the body/topic never originated from, and was never signed in association with, the victim shop. The equality the gem should enforce — `verified_bytes ⊇ {shop, topic}` — is broken; only `verified_bytes == {body}` holds.

### Impact Explanation
This lets a malicious but ordinary merchant (no special privileges, no leaked credentials, no access to the app's `client_secret`) inject attacker-controlled webhook payloads that the host app believes belong to a different, arbitrary tenant. Any app logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop records, honoring `shop/redact` or `customers/data_request` compliance webhooks, disabling a competitor's shop configuration, or triggering shop-scoped side effects) can be manipulated cross-tenant. This satisfies the "cross-tenant access" Critical impact category, since one tenant's forged request causes actions attributed to another tenant.

### Likelihood Explanation
High from a capability standpoint: exploitation only requires the attacker to run a legitimate, low-cost app installation (any public/free store or dev store), capture one webhook delivery they legitimately receive, and re-POST it with a modified `shop`-domain header to the app's public webhook URL — no secret material, TLS interception, or social engineering is needed. The main precondition is that the host application relies on `WebhookMetadata#shop`/`#topic` for tenant-sensitive logic, which is the documented, expected usage pattern of this gem's webhook handler API.

### Recommendation
Bind `shop`, `topic`, and other dispatch-relevant headers into the signed material verified by `HmacValidator`, e.g. change `Webhooks::Request#to_signable_string` to canonicalize and include `shop`, `topic`, and `webhook_id` alongside `@raw_body` (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`, `host`, `code`, `state`, `timestamp` together). [6](#0-5)  If Shopify's real webhook HMAC scheme (as designed) genuinely only signs the raw body server-side, then this gem should not expose header-derived `shop`/`topic` as if they were verified fields without clearly documenting that callers must independently authenticate the request origin (e.g., via source IP allow-listing or mTLS) before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` (free/unprivileged action).
2. Attacker triggers an event (e.g., updates a product) causing Shopify to POST a legitimate webhook to the app's endpoint with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of body under app secret>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: products/update`
3. Attacker captures this raw body and HMAC header value.
4. Attacker re-sends an HTTP POST directly to the app's public webhook endpoint with the same body and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, raw_body)`. [7](#0-6) 
6. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(topic: "products/update", shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`, causing the app to act on attacker data under the victim's tenant identity. [2](#0-1)
