Found it: `TokenExchange.exchange_token` in `lib/shopify_api/auth/token_exchange.rb` derives the destination shop **exclusively from the unverified `dest` claim of the JWT**, never passing it through `ShopValidator.sanitize!`, unlike every other credential-issuing flow in this gem (`client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`'s own `migrate_to_expiring_token`) which all call `Utils::ShopValidator.sanitize!(shop)` before using the shop to build the request host.

### Title
Unsanitized JWT `dest` claim used as request host in `TokenExchange.exchange_token`, bypassing `ShopValidator` and sending `client_secret`/session token to an attacker-controlled host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the `shop` value used to build the outbound `Clients::HttpClient` (and therefore the host the app's `client_id`/`client_secret` and the caller's `session_token` are sent to) directly from the JWT's `dest` claim, via `JwtPayload#shop`, with no domain allow-list check. Every other credential-granting method in the same module and sibling modules (`client_credentials.rb`, `refresh_token.rb`, `migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!` on the shop value before using it to construct the request host.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the `dest` claim and returns whatever string is embedded: [1](#0-0) . The `initialize` method verifies the HMAC signature and the `aud` claim against `Context.api_key`, but never validates that `dest`/`iss` point to a trusted Shopify domain: [2](#0-1) .

`exchange_token` then uses this unsanitized value directly as the shop for the outbound session and HTTP client: [3](#0-2) . The `Clients::HttpClient` built with `shop_session` derives its request host from `session.shop` (via `Context.host`-relative construction based on the session's shop), so an unsanitized `dest_shop` is used to decide *where* the app's `client_id`, `client_secret`, and the caller-supplied `session_token` are POSTed as `subject_token`.

Compare this to the sibling methods in the same file and module, which treat the `shop` string as untrusted and explicitly validate it: `client_credentials.rb` line 25 and `refresh_token.rb` line 24, and `TokenExchange.migrate_to_expiring_token` line 103, all call `Utils::ShopValidator.sanitize!(shop)` [4](#0-3) [5](#0-4) [6](#0-5) . `ShopValidator.sanitize!` restricts the resulting host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [7](#0-6) . `exchange_token` alone omits this check, breaking the binding: **shop value used to build the OAuth token-exchange request host == shop value cryptographically bound to a trusted Shopify domain**. In `exchange_token`, the left side (`dest_shop` from the JWT) is authenticated only by the app's own HMAC signature (i.e., it proves the token was signed with the app's secret and had a matching `aud`), but it is never checked against the right side (an allow-list of legitimate Shopify hosts).

### Impact Explanation
This is a High-severity SSRF-with-credentials issue: if a session token bearing an attacker-influenced `dest` value can reach `exchange_token` (e.g., an app that lets a user supply/replay a crafted-but-validly-signed token, or a proxy/dev environment where `dest` is not otherwise constrained upstream), the app's `client_id`+`client_secret` and the raw `session_token` are POSTed as `subject_token` to `https://{attacker_dest}/admin/oauth/access_token`, exfiltrating the app's `client_secret` and the bearer session token to a host the attacker controls.

### Likelihood Explanation
Exploitability depends on whether an attacker can influence the `dest` claim of a token that still passes JWT signature/`aud` verification in `JwtPayload`. This is most plausible in host applications that pass through third-party or improperly scoped tokens, or in the documented "custom `myshopify_domain`"/Spin/dev-store scenarios where `dest` legitimately contains non-`myshopify.com` domains, since those cases are exactly why `ShopValidator.sanitize!` was added everywhere else. The complete absence of the identical check that guards every sibling method in this file makes this an inconsistency-driven, low-effort-to-trigger gap rather than a purely theoretical one.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` (optionally with the same `myshopify_domain:` override support) to the JWT-derived shop in `exchange_token` before constructing `shop_session`/`Clients::HttpClient`, mirroring the validation already performed in `migrate_to_expiring_token`, `client_credentials`, and `refresh_token`.

### Proof of Concept
1. Obtain or construct a session token whose `dest` claim is `https://attacker.example` (or any non-allow-listed host) but which is otherwise validly signed with the app's `api_secret_key` and has `aud == Context.api_key` — e.g., a scenario where an app forwards a token from an untrusted source without itself checking the domain.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe (per `lib/shopify_api/auth/token_exchange.rb:41-65`) that `dest_shop` is used unchecked, and the HTTP POST containing `client_id`, `client_secret`, and `subject_token: session_token` is sent to `https://attacker.example/admin/oauth/access_token` instead of being rejected — compare with the identical `shop` parameter in `client_credentials.rb`/`refresh_token.rb`, which would raise `Errors::InvalidShopError` for the same value via `ShopValidator.sanitize!`.
