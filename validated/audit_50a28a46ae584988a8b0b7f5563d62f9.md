### Title
Webhook `shop` domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively over that signable string [2](#0-1) . The `shop` attribute, however, is read directly from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which is never included in the signed bytes [3](#0-2) . `Registry.process` validates the HMAC and then forwards `request.shop` unchanged into `WebhookMetadata`, which is delivered to the app's handler as the tenant identity for the event [4](#0-3) .

### Finding Description
This breaks the intended identity binding: **shop attributed to the webhook == shop that produced the signed bytes**. In this gem, that equality does not hold, because:
- `hmac` is computed over `@raw_body` only [5](#0-4) .
- `shop`, `topic`, `webhook_id`, and `api_version` are all taken from unauthenticated headers [6](#0-5) .
- The app's `api_secret_key` used for HMAC computation is shared across every shop that has installed the app (it is the app's `client_secret`, not a per-shop secret) [7](#0-6) .

Any actor who legitimately installs the app on their own shop (an "unprivileged internet user" with respect to any other merchant's tenant) receives real webhook deliveries with a valid `hmac` for their own `raw_body`. Because that HMAC never binds to the `shop` header, they can replay the same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a victim shop. `HmacValidator.validate` still succeeds (it only checks `raw_body` against `hmac`), and `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain [4](#0-3) .

### Impact Explanation
Apps built on this gem rely on `WebhookMetadata#shop` to determine which merchant/tenant record the webhook body applies to (e.g., updating orders, inventory, or subscription state for "that shop"). Since the shop identity is unauthenticated, an attacker can inject webhook events that are misattributed to a shop they do not control, causing cross-tenant data corruption/spoofing in any host application that trusts `data.shop` from a gem-validated webhook. This satisfies the "cross-tenant access" criteria via forged tenant-scoped events validated by the gem's own (incomplete) HMAC check.

### Likelihood Explanation
Requires only that the attacker be able to install the app on a shop they control (standard, unprivileged Shopify App Store installation) to obtain a valid `raw_body`/`hmac` pair from a genuine webhook delivery, then POST a modified request (same body, same HMAC header, altered shop-domain header) to the app's public webhook endpoint. No `api_secret_key`, access token, or privileged access is needed beyond what any app-installing merchant already has.

### Recommendation
Bind the tenant identity into the verified payload: include the `shop` (and ideally `topic`/`webhook_id`) header value in the string that is HMAC-verified, or independently verify that the resolved `shop` matches a shop value embedded in/derived from the verified `raw_body`, before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the delivered request: `raw_body` and `x-shopify-hmac-sha256` header (valid for the app's shared `api_secret_key`).
2. Send a POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [8](#0-7) ; validation succeeds because it only checks `raw_body` against the HMAC.
4. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` [9](#0-8) , and the host application acts on attacker-supplied data believing it originates from `victim.myshopify.com`.
