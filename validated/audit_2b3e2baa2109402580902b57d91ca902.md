## Title
Unvalidated JWT `dest` claim used as request host for OAuth token exchange, sending `client_secret` to an unvalidated domain - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` extracts the shop domain from the session token's `dest` claim and uses it, unvalidated, as the host that receives the app's `client_id`/`client_secret` during the OAuth token-exchange POST. Unlike the sibling method `migrate_to_expiring_token` in the same file, which explicitly runs the shop string through `Utils::ShopValidator.sanitize!` before using it as a request host, `exchange_token` skips this validation entirely.

### Finding Description
In `exchange_token`, the shop used to build the outbound HTTP request is derived directly from the decoded JWT: [1](#0-0) 

`jwt_payload.shop` performs no domain validation — it simply strips the `https://` prefix from the raw `dest` claim: [2](#0-1) 

The only check performed on the JWT in `JwtPayload#initialize` is signature validity and that `aud == Context.api_key`; there is no check that `iss`/`dest` matches a trusted Shopify domain (`myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, etc.): [3](#0-2) 

That unvalidated `dest_shop` value is then wrapped in a `Session` and passed to `Clients::HttpClient`, which builds the request host directly from `session.shop` whenever `Context.api_host` is not configured (the default): [4](#0-3) 

The POST body sent to that host includes the app's `client_id` and `client_secret`: [5](#0-4) 

By contrast, the near-identical `migrate_to_expiring_token` method in the same module validates the shop string against `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before using it as the request host: [6](#0-5) [7](#0-6) 

This is the exact binding break described in the analog rules: the host that is trusted to receive the `client_secret` (`session.shop`, derived from the JWT `dest` claim) is not the same as a host that has been validated to be a genuine Shopify domain — whereas the library's own sibling method (`migrate_to_expiring_token`) demonstrates that this value is expected to be validated before being used this way.

### Impact Explanation
If `dest` can be influenced to contain a non-Shopify hostname — for example, a token accepted from an unexpected origin/environment, a mis-scoped `spin.dev`/proxy setup, or any flow where a session token with an attacker-influenced `dest` reaches `exchange_token` — the library will construct `https://#{dest_shop}/admin/oauth/access_token` and POST the app's `client_id` and `client_secret` to that attacker-influenced host, directly leaking the app's `client_secret` to a third party. This matches the "High: SSRF with the app's credentials" / credential-leakage impact category, since the `client_secret` is the credential.

### Likelihood Explanation
Exploitation requires a session token that passes the HMAC signature check (`aud == Context.api_key`) but whose `dest` claim is not itself constrained to a Shopify-controlled domain. Because `JwtPayload` performs no allow-list check on `iss`/`dest`, and `exchange_token` performs no additional sanitation (in contrast to `migrate_to_expiring_token`), any code path that produces or forwards a validly-signed token with a non-standard `dest` (e.g., a proxy, custom app-bridge integration, or multi-tenant token-signing setup sharing the same `api_secret_key`) will result in credentials being sent to that host with no defense-in-depth check in this library.

### Recommendation
Validate `jwt_payload.shop` (the `dest`-derived value) through `Utils::ShopValidator.sanitize!` in `exchange_token`, exactly as is already done in `migrate_to_expiring_token`, before constructing the `Session` / `HttpClient` used to send `client_id`/`client_secret` to the token-exchange endpoint. Consider adding the same allow-list validation directly inside `JwtPayload#shop`/`#initialize` so all consumers of the `dest` claim get this protection uniformly.

### Proof of Concept
1. Obtain (or otherwise produce) a session token that passes JWT signature and `aud` verification but whose `dest` claim is `https://attacker-controlled.example`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `JwtPayload#shop` returns `"attacker-controlled.example"` unchecked, `Session.new(shop: dest_shop)` stores it, and `Clients::HttpClient` builds `@base_uri = "https://attacker-controlled.example"`, then POSTs a body containing `client_id` and `client_secret` to `https://attacker-controlled.example/admin/oauth/access_token` — compare against `migrate_to_expiring_token`, which raises `Errors::InvalidShopError` for the same non-Shopify host via `ShopValidator.sanitize!`.
