Based on my investigation, I found a legitimate analog to the "broken sandbox check bypassed by nested/structural evasion" bug class in `SolverAccount.sol`.

### Title
Nested ERC-7821 self-call bypasses `_containsFillOrder`'s bid-forgery guard, defeating the anti-griefing control - (File: evm/src/apps/intentsv2/SolverAccount.sol)

### Summary
`SolverAccount._containsFillOrder()` is a structural, pattern-based scan of userOp calldata meant to reject any 65-byte-ECDSA-signed operation whose top-level batch directly calls `IntentGatewayV2.fillOrder`. Like the PraisonAI AST sandbox, it validates only the shallow syntactic shape of the input (`execute(mode, executionData)` → `Execution[]` → `target == INTENT_GATEWAY_V2 && selector == fillOrder`) rather than the full set of reachable code paths, so an attacker can nest the forbidden call one level deeper and the scan never sees it.

### Finding Description
`validateUserOp` treats a 65-byte ECDSA signature as "ordinary batch execution" and only blocks it if `_containsFillOrder(op.callData)` detects a direct `fillOrder` call to `INTENT_GATEWAY_V2` in the top-level `Execution[]`: [1](#0-0) 

The scan itself only inspects `calls[i].target == INTENT_GATEWAY_V2` at one level of nesting: [2](#0-1) 

Nothing prevents one of the top-level `Execution` entries from targeting the `SolverAccount` itself (`address(this)`) with `callData` that re-enters `execute(mode2, executionData2)`, where the *inner* batch is the one that actually calls `IntentGatewayV2.fillOrder`. `_containsFillOrder` never recurses into that inner batch, so `target == INTENT_GATEWAY_V2` is false at the top level and the guard returns `false`, letting `validateUserOp` fall through to `super.validateUserOp` and succeed.

The self-call at execution time is authorized: `_erc7821AuthorizedExecutor` permits `caller == address(entryPoint())` for the top-level call, and OpenZeppelin's `ERC7821`/`ERC7579` self-execution path treats `msg.sender == address(this)` as authorized for the inner nested call, so the nested `execute()` succeeds in re-entering and dispatching the disguised `fillOrder` call with `msg.sender` still equal to the solver account address. [3](#0-2) 

The comments explicitly document the threat this guard is meant to stop: a public bid embeds a valid 65-byte solver signature over the userOpHash, so anyone can strip the `select()` commitment/session data and resubmit the bid's calldata to consume the solver's nonce and gas even though `fillOrder` will ultimately revert (no session selected in transient storage): [4](#0-3) [5](#0-4) 

Wrapping the same stripped bid calldata in one extra layer of `execute(mode, executionData)` targeting `address(this)` reproduces the exact same forgeable, signature-covered payload while evading the only check meant to reject it, because the check is a single-level structural pattern match rather than a full walk of every call the batch can transitively reach — the same class of gap as validating only the top-level AST nodes of a script instead of everything the interpreter will actually execute.

### Impact Explanation
This nullifies the anti-griefing control the code explicitly documents and relies on. An unprivileged attacker who observes any public bid (bids are broadcast/public per the code comments) can resubmit its calldata — reshaped one level deeper — through the EntryPoint, forcing `validateUserOp` to succeed instead of returning `SIG_VALIDATION_FAILED`. The forged UserOperation is accepted into a bundle, consumes the solver's account nonce, and burns the solver's prefunded gas before reverting at `fillOrder` (unauthorized fill, no `select()` staged). This is unauthorized consumption of a victim solver's on-chain resources triggered purely by a guard that was supposed to prevent exactly this, i.e., an authorization-bypass class finding rather than a benign resource issue, since the entire purpose of `_containsFillOrder` is defeated by structurally-equivalent input it fails to recognize.

### Likelihood Explanation
High reachability: any address can observe a solver's public bid off-chain (as acknowledged in the code's own comments), repackage its calldata inside one additional `execute()` wrapper targeting `address(this)`, and submit it through the standard ERC-4337 `EntryPoint` without needing any private key, session key, or privileged role. No proof, consensus, or governance step is involved — it is a pure calldata-shaping bypass of an on-chain guard reachable from a single dispatched UserOperation.

### Recommendation
Make `_containsFillOrder` recursive: when a top-level `Execution.target == address(this)` and its `callData` begins with `EXECUTE_SELECTOR`, decode and recurse into the nested batch (with a bounded depth) before concluding no `fillOrder` call is present. Alternatively, reject any top-level batch containing a self-targeting `execute()` call outright when arriving via the 65-byte ECDSA path, since legitimate ordinary UserOperations for this account have no reason to recursively invoke `execute()` on themselves.

### Proof of Concept
1. Attacker observes a public solver bid: a `PackedUserOperation` with a 65-byte ECDSA `signature` and `callData = execute(mode, abi.encode(bytes32, executionData))` where `executionData` decodes to `Execution[]{ target: INTENT_GATEWAY_V2, callData: fillOrder(...) }`.
2. Attacker constructs a new `callData' = execute(mode, abi.encode(bytes32, executionData'))` where `executionData'` decodes to `Execution[]{ target: address(this) /* SolverAccount */, value: 0, callData: execute(mode, abi.encode(bytes32, executionData)) }` — i.e., the original batch wrapped one level deeper, targeting the account itself.
3. Attacker submits a UserOperation with the *same* 65-byte signature (still valid over the same `userOpHash`, since replay of the bid's own signed content is exactly what the guard is meant to stop) and `callData'`.
4. In `validateUserOp`, `_containsFillOrder(callData')` decodes the top-level batch and sees `calls[0].target == address(this) != INTENT_GATEWAY_V2`, so `hasFillOrder` is `false`; the check passes and `super.validateUserOp` succeeds.
5. At execution, the EntryPoint calls `SolverAccount.execute(...)`, which self-calls `execute(...)` again (authorized via `caller == address(this)`), which then calls `IntentGatewayV2.fillOrder(...)` — reverting because no `select()` was staged in this transaction — but the solver's nonce has already been consumed and gas already spent, reproducing the exact griefing the top-level guard was written to prevent.

    function _containsFillOrder(bytes calldata callData) private view returns (bool) {
        if (callData.length < 4 || bytes4(callData[0:4]) != EXECUTE_SELECTOR) return false;

        (, bytes memory executionData) = abi.decode(callData[4:], (bytes32, bytes));
        Execution[] memory calls = abi.decode(executionData, (Execution[]));

        for (uint256 i = 0; i < calls.length; i++) {
            bool hasFillOrder = calls[i].target == INTENT_GATEWAY_V2 && bytes4(calls[i].callData) == FILL_ORDER_SELECTOR;
            if (hasFillOrder) return true;
        }
        return false;
    }

    /**
     * @dev Verifies an EIP-712 solver selection signature and stores a commitment to
     * `keccak256(abi.encode(solver, sessionKey))` in transient storage. The hash is
     * stored using `tstore` so it is only available within the same transaction —
     * this ensures atomicity between `select` and `fillOrder` calls.
     *
     * The session key is recovered from the EIP-712 signature over the (commitment, solver)
     * tuple. At fill time, `fillOrder` re-derives the same hash from `msg.sender` and
     * `order.session` and compares it against the value stored at the commitment slot.
     *
     * @param options The selection options containing the commitment, solver address, and signature.
     * @return The recovered session key address.
     */
    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }
