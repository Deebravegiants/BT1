### Title
Relayer-controlled message body size lets a self-relayed request unbackedly mint Reputation Asset, biasing Collator selection - (File: modules/pallets/messaging-incentives/src/lib.rs)

### Summary
`pallet-messaging-incentives::on_executed` mints `ReputationAsset` to a relayer proportional to the byte-size of the `Request`/`Response` payload the relayer delivered, exactly analogous to the referenced `Unlock.recordKeyPurchase` bug where the caller controls an economically-priced input (`tx.gasprice`) that feeds directly into a mint formula benefiting themselves.

### Finding Description
`Pallet::message_bytes` computes `bytes = max(body.len(), 32)` summed over the requests in a message, and `on_executed` mints `rate * bytes` of `ReputationAsset` to whichever account's sr25519 signature is recovered from the message's `signer` field via `relayer_for`: [1](#0-0) [2](#0-1) 

The `bytes` figure is entirely dispatcher-controlled: any unprivileged account can dispatch a `POST` request from a source chain with an arbitrarily large, junk-padded `body` (dispatching is documented as free at the runtime layer for Polkadot-SDK chains, with only an optional relayer fee), then relay that same request themselves, so the account that pads the body and the account credited with `ReputationAsset` can be one and the same: [3](#0-2) 

There is no upper bound on `bytes`, no correlation to real relaying cost or delivered value, and the only defense (the 32-byte floor) protects against the opposite direction (under-sized bodies), not inflation: [4](#0-3) 

`ReputationAsset` is not a cosmetic score: it is the sole input to `pallet-collator-manager`'s `new_session` selection algorithm, which ranks candidates by their controller's `ReputationAsset` balance and grants the highest-balance accounts a Collator slot (a block-production/consensus role) each session: [5](#0-4) 

This is the same root cause pattern as the referrer-discount bug: a value-bearing mint is driven by a parameter the beneficiary fully controls (`tx.gasprice` there, message body length here), with the "trusted oracle" mitigation (fixed governance rate) applied only to the *per-unit* rate (`MintPerByte`) and not to the *quantity* (`bytes`), leaving the overall mint attacker-steerable.

### Impact Explanation
By self-dispatching padded requests and self-relaying them, an attacker can mint unlimited `ReputationAsset` for a cost bounded only by source-chain transaction fees for a large calldata payload (cheap on most chains, and dispatch itself is fee-free on Polkadot-SDK chains per the docs). Because reputation directly determines Collator selection, this lets an attacker unfairly and cheaply seize disproportionate Collator slots relative to real messaging-relay work performed, undermining the "proven economic activity" premise the Collator-selection design depends on. This is a consensus/liveness-role integrity issue reached purely by submitting a normal cross-chain message and its own delivery proof — no privileged action required.

### Likelihood Explanation
Medium. Exploitation requires only: (1) dispatching a POST request with an oversized body from any application/account the attacker controls, and (2) submitting the `handle_unsigned`/message-delivery extrinsic with a signature the attacker controls as `signer`. Both are permissionless, unprivileged actions available to any relayer/user. The only friction is `MintPerByte` being set to a non-zero value by governance (which the pallet is explicitly designed to do) and paying whatever data-inclusion cost the source/destination chain charges for a large body.

### Recommendation
Cap the per-message/per-batch `bytes` figure used in the mint calculation (e.g., an upper bound tied to realistic ISMP message-size limits or destination execution weight actually consumed) rather than trusting the raw dispatcher-supplied `body.len()`. Alternatively, tie the mint to a metric relayers cannot unilaterally inflate for their own benefit — e.g., actual bytes of *state-proof* data verified, or the destination-chain gas/weight the message consumed, both of which are consensus-determined rather than dispatcher-chosen — and/or rate-limit reputation accrual per relayer per session.

### Proof of Concept
1. Attacker deploys/uses any application on a connected source chain that can dispatch an arbitrary ISMP `POST` request (e.g., calling `IDispatcher(_host).dispatch(...)` on EVM with junk `body` bytes, or the Polkadot `IsmpDispatcher`), setting `body` to, say, 1 MB of zero-bytes, with `fee: 0` for self-relay.
2. Attacker (or a colluding relayer identity) constructs the `Message::Request(RequestMessage { requests: [that PostRequest], proof, signer })`, signing the sr25519 signature over `keccak_256(requests.encode())` with their own controller key, exactly as shown in `signed_request` in the test suite: [6](#0-5) 
3. Attacker submits this message for execution via `pallet-ismp`'s unsigned handling path, which invokes `FeeHandler::on_executed` on success.
4. `Pallet::message_bytes` returns `bytes = 1_000_000`; `on_executed` mints `MintPerByte * 1_000_000` `ReputationAsset` to the attacker's controller account, as demonstrated by the linear scaling verified in `on_executed_mints_reputation_proportional_to_bytes`: [4](#0-3) 
5. Repeating this before each session boundary lets the attacker's controller consistently outrank genuine relayers/provers in `pallet-collator-manager::new_session`'s reputation-sorted candidate list, illegitimately capturing Collator slots: [7](#0-6)

	fn message_bytes(message: &Message) -> u32 {
		match message {
			Message::Request(req) => req
				.requests
				.iter()
				.map(|p| core::cmp::max(p.body.len() as u32, 32))
				.sum::<u32>(),
			_ => 0,
		}
	}

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}

# Hyperbridge Fees

Hyperbridge no longer charges a protocol fee on Polkadot-SDK chains. Dispatching is free at the runtime layer — applications only need to attach an optional **relayer fee** if they want third-party relayers to deliver their messages.

## Relayer Fees

The relayer fee is an optional incentive provided by applications initiating cross-chain transactions. It compensates Hyperbridge's decentralized relayers for delivering messages to the destination chain. Apps that prefer to self-relay can leave the fee at zero.

The fee is collected by `pallet-ismp`'s `IsmpDispatcher` from the configured `Currency` (typically a stablecoin). It's escrowed into the `RELAYER_FEE_ACCOUNT` and paid out to the relayer that delivers the message (or refunded to the payer on timeout).

fn signed_request(relayer: &sr25519::Pair, body: Vec<u8>) -> MessageWithWeight {
	let post = PostRequest {
		source: SOURCE,
		dest: DEST,
		nonce: 0,
		from: vec![1; 32],
		to: vec![2; 32],
		timeout_timestamp: 100,
		body,
	};
	let requests = vec![post];
	let signed = keccak_256(&requests.encode());
	let sig = relayer.sign(&signed);
	let signer = Signature::Sr25519 {
		public_key: relayer.public().to_raw_vec(),
		signature: sig.to_raw_vec(),
	}
	.encode();

	MessageWithWeight {
		message: Message::Request(RequestMessage {
			requests,
			proof: Proof {
				height: StateMachineHeight {
					id: StateMachineId { state_id: SOURCE, consensus_state_id: *b"mock" },
					height: 1,
				},
				proof: vec![],
			},
			signer,
		}),
		weight: Weight::zero(),
	}
}
