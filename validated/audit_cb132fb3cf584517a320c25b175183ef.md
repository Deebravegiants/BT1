Audit Report

## Title
Username Enumeration via Differentiated Login Error Messages in Local Session Authentication - (File: `core/sessions/localauth/orm.go`)

## Summary
The local authentication `CreateSession` flow in `core/sessions/localauth/orm.go` returns three distinguishable outcomes depending on whether the email exists in the `users` table: a raw DB "no rows" error when the email is not found, `"Invalid email"` in an unreachable edge case, or `"Invalid password"` when the email exists but the password is wrong. These are propagated unmodified into the HTTP 401 response body by `SessionsController.Create` via `jsonAPIError`, letting an unauthenticated attacker distinguish registered from unregistered emails.

## Finding Description
`SessionsController.Create` forwards the raw `error` returned from `AuthenticationProvider().CreateSession` directly to the client: `jsonAPIError(c, http.StatusUnauthorized, err)` at [1](#0-0) . `jsonAPIError` in turn serializes `err.Error()` verbatim into the JSON response body when the error is not a `*models.JSONAPIErrors` type: [2](#0-1) .

In `orm.CreateSession`, the email lookup error (e.g., `sql.ErrNoRows` for a nonexistent email) is returned directly without normalization, and if found, the password mismatch produces the distinct string `"Invalid password"`: [3](#0-2) .

This confirms the exact code path and root cause described in the claim: no normalization exists between the "email not found" and "email found, password wrong" branches, and both messages reach the unauthenticated client verbatim.

## Impact Explanation
This is a classic username/email enumeration bug reachable at the unauthenticated `/sessions` endpoint. An attacker can determine which emails are registered as node operator/admin accounts without any credentials, which is a stepping stone to targeted credential stuffing or brute-force attacks against the node's Operator UI. It does not by itself grant authentication bypass, key exfiltration, or fund movement — it is an information-disclosure/reconnaissance primitive that assists a downstream attack, consistent with typically low-to-informational severity in most bug bounty frameworks, though it is a genuine, unresolved code-level flaw.

## Likelihood Explanation
The `/sessions` endpoint is intentionally unauthenticated and internet-facing [4](#0-3) . The only mitigating control is the unauthenticated rate limit (5 requests / 20s by default) [5](#0-4) , confirmed enforced in `TestSessions_RateLimited` [6](#0-5) . This slows but does not prevent a patient attacker from enumerating a candidate list of emails over time, so the vulnerability is realistically exploitable, if slowly.

## Recommendation
Normalize all failure branches in `orm.CreateSession` (nonexistent email, DB lookup error, invalid email match, and password mismatch) to a single generic message such as `"invalid email or password"` before returning, and apply the same normalization to the analogous `localLoginFallback` paths in the OIDC (`core/sessions/oidcauth/oidc.go`) and LDAP (`core/sessions/ldapauth/ldap.go`) authenticators to avoid leaking distinguishable authentication outcomes to unauthenticated clients.

## Proof of Concept
1. `POST /sessions` with `{"email":"doesnotexist@example.com","password":"x"}` — the DB lookup in `FindUser`/`findUser` fails and the raw error (e.g., `sql: no rows in result set`) is returned unmodified through `CreateSession` and serialized into the 401 JSON body by `jsonAPIError`.
2. `POST /sessions` with `{"email":"knownadmin@example.com","password":"wrong"}` — `CreateSession` reaches the password check and returns the distinct string `"Invalid password"`, also serialized into the 401 JSON body.
3. Comparing these two distinguishable response bodies across a list of candidate emails lets an unauthenticated attacker enumerate valid registered node accounts, subject to the default unauthenticated rate limit of 5 requests/20s.

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
```

```go
func TestSessions_RateLimited(t *testing.T) {
	t.Parallel()

	ctx := t.Context()
	app := cltest.NewApplicationEVMDisabled(t)
	require.NoError(t, app.Start(ctx))

	router := web.Router(t, app, nil)
	ts := httptest.NewServer(router)
	defer ts.Close()

	client := clhttptest.NewTestLocalOnlyHTTPClient()
	input := `{"email":"brute@force.com", "password": "wrongpassword"}`

	for range 5 {
		request, err := http.NewRequestWithContext(ctx, http.MethodPost, ts.URL+"/sessions", bytes.NewBufferString(input))
		require.NoError(t, err)

		resp, err := client.Do(request)
		require.NoError(t, err)
		assert.Equal(t, http.StatusUnauthorized, resp.StatusCode)
	}

	request, err := http.NewRequestWithContext(ctx, http.MethodPost, ts.URL+"/sessions", bytes.NewBufferString(input))
	require.NoError(t, err)

	resp, err := client.Do(request)
	require.NoError(t, err)
	assert.Equal(t, 429, resp.StatusCode)
}
```
