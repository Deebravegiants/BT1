Based on my review, I found a concrete analog matching the reported bug class: a `CircomData` field that is acted upon downstream but is excluded from both the on-chain `calldataHash` and the ZK proof's public-input vector for a specific code path.

### Title
Emporium "min" input path omits `stealthAddressStructure` and `rootHashHinkal` from both `calldataHash` and the proof's public-input vector - (File: `contracts/CircomDataBuilder.sol`)

### Summary
`HinkalHelper.performHinkalChecks` verifies calldata integrity via `getHashedCalldata` and then derives the proof's public inputs via `formInputForCircom`. When the external action is the Emporium action and `erc20TokenAddresses.length == 0`, the code takes the `formInputEmporiumMin` branch, which produces a public-input vector containing only `emporiumMessage`, `timeStamp`, and `calldataHash`.

### Finding Description
In the normal path, `formBasicInput` calls `getSignedMessageHash`, which binds `circomData.stealthAddressStructure.{H1x,H1y,H0x,H0y}` and `rootHashHinkal` into the proof's private/public inputs via a hash that itself flows into public input generation, and also directly places `stealthAddressStructure.{H1x,H1y,stealthAddress,H0x,H0y}` as raw public signals: [1](#0-0) [2](#0-1) 

However, `formInputEmporiumMin` skips all of this entirely: [3](#0-2) 

Neither `getHashedCalldata1` nor `getHashedCalldata2` include `stealthAddressStructure` or `rootHashHinkal` either: [4](#0-3) 

The only on-chain constraint on `stealthAddressStructure` is `H0x != 0`, unrelated to the actual stealth address value used for wallet identity: [5](#0-4) 

This means for any transaction routed through `formInputEmporiumMin` (Emporium action with zero tokens), `circomData.stealthAddressStructure` (including `stealthAddress`, which downstream code and `HinkalWallet`/Emporium logic use to identify which shielded wallet is being authorized/acted upon) and `circomData.rootHashHinkal` are not committed anywhere the Groth16 proof or the calldata-hash check can catch tampering. A relayer or any calldata-forwarding party can swap these fields after a valid proof has been produced by a legitimate user, since the verifier only checks `calldataHash` (which excludes these fields) and the 3-element public-input vector (which also excludes them).

### Impact Explanation
If `stealthAddressStructure.stealthAddress` determines which `HinkalWallet` instance an Emporium action operates on (as suggested by `EmporiumUpgradeable.sol` and `HinkalWallet.sol`), an attacker who intercepts/relays a valid Emporium-min proof could redirect the authorized action to a different wallet/target — i.e., execute a call or wallet operation the original signer/prover never authorized for that address. This falls under "executing calls or moving assets a wallet owner or prover never authorised" (High impact). I was not able to fully confirm the exact consumption of `stealthAddress` inside `EmporiumUpgradeable.sol` within the available tool budget, so the exact blast radius (whether it enables outright fund theft vs. call redirection) should be verified against that contract.

### Likelihood Explanation
Any relayer or intermediary handling a submitted transaction for the Emporium-min path (zero-token Emporium calls) can tamper with `stealthAddressStructure` and `rootHashHinkal` fields without invalidating `calldataHash` or the Groth16 proof, since neither commits to these values in this branch. No special privileges are required beyond being able to observe/relay a pending transaction (or reuse calldata), matching the "unprivileged EOA" analog condition.

### Recommendation
Include `circomData.stealthAddressStructure` and `circomData.rootHashHinkal` in either `getHashedCalldata1`/`getHashedCalldata2` (so they're covered by the `calldataHash` integrity check) or directly in the `formInputEmporiumMin` public-input vector, mirroring how `formBasicInput` handles them for the normal path. This closes the equality gap so that every `CircomData` field acted upon by the protocol is bound to `calldataHash` or the public-input vector.

### Proof of Concept
1. A user constructs a valid Emporium action with `erc20TokenAddresses.length == 0`, generating a proof whose public inputs are `[emporiumMessage, timeStamp, calldataHash]` per `formInputEmporiumMin`.
2. Since `calldataHash` (per `getHashedCalldata1`/`2`) and the public-input vector never include `stealthAddressStructure` or `rootHashHinkal`, an intermediary (e.g., the relay submitting the transaction, or anyone replaying the calldata) can substitute different values for `circomData.stealthAddressStructure` (e.g., a different `stealthAddress`) and/or `circomData.rootHashHinkal` before submission.
3. `Hinkal.transact` still passes `verifyProof` (public inputs unchanged) and `performHinkalChecks`' `calldataHash` check (unaffected fields), then proceeds to execute the Emporium action using the tampered `stealthAddressStructure`, resulting in an action being attributed to / executed against a wallet identity the original prover did not authorize.
