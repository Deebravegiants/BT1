## Divide-by-Zero Panic in `Processor::calc_take_pnl` Permanently Freezes Pool Funds - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl`, invoked unconditionally from `process_deposit` and conditionally from `process_withdraw`, performs an unchecked division `x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` where `x1` is the normalized `total_pc_without_take_pnl`. If a liquidity provider legitimately withdraws liquidity down to the point where `total_pc_without_take_pnl` becomes exactly `0`, any subsequent `Deposit` or `Withdraw` instruction on that pool will panic, permanently freezing all remaining pool funds — directly analogous to the FFmpeg `libavcodec/lpc.h` divide-by-zero (CVE-2020-20445) bug class, but here reachable from ordinary AMM instructions.

### Finding Description
`calc_take_pnl` computes a rebalancing step using pool reserves normalized to `sys_decimal_value`: [1](#0-0) 

The value `x1` is derived directly from `total_pc_without_take_pnl` via `Calculator::normalize_decimal_v2`, and is passed into `calc_take_pnl` from both `process_deposit` and `process_withdraw`: [2](#0-1) [3](#0-2) 

The branch containing the division is only entered when `pool_pc_amount.checked_mul(pool_coin_amount) >= calc_pc_amount.checked_mul(calc_coin_amount)`: [4](#0-3) 

If `total_pc_without_take_pnl == 0` (so `pool_pc_amount == 0`, making the left side `0`) and `target.calc_pnl_x` is also `0` (or small enough that `calc_pc_amount * calc_coin_amount == 0`), the condition `0 >= 0` is satisfied, the branch executes, and `x1 == 0` is used as a division denominator at line 208, causing an unchecked-panic (`.unwrap()` on `None`).

`total_pc_without_take_pnl` can be driven to exactly `0` through ordinary `Withdraw` calls: the withdrawal guard only checks against the raw vault balance (`amm_pc_vault.amount`), not against `total_pc_without_take_pnl`, so a withdrawal that removes the entire `total_pc_without_take_pnl` while `need_take_pnl_pc` (the pnl already earmarked for the pool owner but still physically sitting in the vault) keeps the raw vault balance positive passes the check: [5](#0-4) 

After such a withdrawal, `target_orders.calc_pnl_x` is also updated to reflect the near-zero remaining PC balance: [6](#0-5) 

Once both `total_pc_without_take_pnl` and `target.calc_pnl_x` are at/near zero, any later `Deposit` or `Withdraw` call by any user reaches `calc_take_pnl` and panics on the divide-by-zero at `y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()`.

### Impact Explanation
A panic inside a Solana program instruction aborts the transaction. Since `calc_take_pnl` is on the mandatory path of both `Deposit` and `Withdraw` (the only instructions that can move LP-side liquidity), once the pool reaches this zero-PC-reserve state, **all further deposits and withdrawals on the pool permanently fail**, freezing all remaining LP/user funds locked in the pool's coin and PC vaults — no user can retrieve their liquidity, satisfying the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
Reaching the trigger state requires only standard LP actions: a liquidity provider (no special privilege) submitting a `Withdraw` instruction that reduces `total_pc_without_take_pnl` to zero while leaving `need_take_pnl_pc` uncollected in the vault (a state achievable by normal withdrawal sequencing, since the code checks raw vault balances rather than the pnl-adjusted totals). No signer other than the withdrawing LP is required, and the attacker fully controls the withdrawal amount, size, and timing, making this readily reachable from a single, attacker-controlled transaction sequence.

### Recommendation
- In `calc_take_pnl` (`program/src/processor.rs`), guard the `y2` computation: check `x1 != 0` before dividing, and treat `x1 == 0` as a no-pnl-to-take case (skip the branch) rather than allowing an unchecked panic.
- Change `Withdraw`'s vault-balance check to compare against `total_pc_without_take_pnl`/`total_coin_without_take_pnl` (the pnl-excluded totals) rather than raw vault balances, so pnl reserved for the owner can't be conflated with withdrawable liquidity, preventing `total_pc_without_take_pnl` from reaching exactly zero while `lp_amount > 0`.

### Proof of Concept
1. Attacker/LP holds a portion of a pool's LP tokens where the pool's `pc` side reserve is small relative to `need_take_pnl_pc` already accrued.
2. Attacker calls `Withdraw` with an `amount` sized so `pc_amount` returned by `InvariantPool::exchange_pool_to_token` equals the pool's entire `total_pc_without_take_pnl`. Because the vault-balance guard in `process_withdraw` compares against `amm_pc_vault.amount` (which still includes `need_take_pnl_pc`), the check `pc_amount < amm_pc_vault.amount` passes even though `pc_amount == total_pc_without_take_pnl`.
3. After the withdrawal, `total_pc_without_take_pnl == 0` and `target_orders.calc_pnl_x` is updated to ~0 (per lines 1818-1839).
4. Any subsequent `Deposit` or `Withdraw` transaction (by any user) on this pool calls `calc_take_pnl`, satisfies `0 >= 0`, and panics at the `checked_div(x1).unwrap()` call (line 208), aborting the transaction and permanently blocking further deposits/withdrawals on the pool.
