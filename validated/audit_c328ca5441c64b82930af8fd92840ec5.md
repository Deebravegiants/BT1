### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, allowing tenant-spoofing of webhook payloads - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate`, which in turn calls `Request#to_signable_string`. That method returns only `@raw_body` — none of the Shopify-supplied headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included in the signed material. The `shop` value that is subsequently handed to the host application's webhook handler (via `WebhookMetadata.shop`) is read straight from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header, not from anything bound by the HMAC.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it against `verifiable_query.hmac` using `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just the raw body, and `hmac` is read from the `hmac-sha256` header. Critically, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are never mixed into the signed string: [2](#0-1) 

`Registry.process` validates only this body HMAC and then forwards `request.shop` (the unauthenticated header value) straight into the handler as the tenant identifier: [3](#0-2) 

The equality this breaks: **the shop that was cryptographically authenticated (none — HMAC only covers the body) ≠ the shop that the host application uses as its per-tenant session/lookup key (`WebhookMetadata#shop`, taken from the header)**. Because `api_secret_key` is a single, static per-app secret shared across *every* installed shop (not shop-specific), any actor who can install the app on their own shop — an unprivileged internet user, from the gem's perspective — receives legitimately-signed webhook bodies for their own tenant. Since the HMAC signs only the body and the app secret is shop-independent, that same `body`+`hmac` pair remains valid under `HmacValidator.validate` no matter what `shop-domain` header accompanies it. An attacker can therefore replay/forward a validly-signed webhook body while substituting an arbitrary victim shop's domain in the `x-shopify-shop-domain` header, and the library will report the request as authentic and hand the host app a `WebhookMetadata` claiming to be from the victim tenant.

### Impact Explanation
This is a cross-tenant boundary violation: the library's own authentication primitive (`HmacValidator`) does not bind the shop identity to the signature, yet the shop value it forwards to the handler is exactly the identifier host applications use to scope per-merchant data, access tokens and business logic. An attacker-controlled shop can cause the gem to assert a forged tenant identity for otherwise-valid HMAC-authenticated traffic, enabling cross-tenant data confusion in any host application that trusts `WebhookMetadata#shop` (which is the gem's documented, intended usage pattern) as the source of truth for which merchant a webhook belongs to.

### Likelihood Explanation
Reaching this requires only the ability to install the app on an attacker-owned development/trial shop (an unprivileged, standard OAuth flow requiring no special credentials) and control over an HTTP client capable of sending a POST request to the app's webhook endpoint with a modified `shop-domain` header while keeping the legitimately-issued body and matching HMAC digest. No leaked secrets, TLS interception, or privileged access is required, and the vulnerable code path (`Request#to_signable_string`, `Registry.process`) is exercised on every webhook delivery this gem processes.

### Recommendation
Bind the identity-carrying headers into the signed material, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the payload before trusting them. Concretely, change `Request#to_signable_string` (or `Registry.process`) to include `shop`, `topic`, and `webhook_id` alongside the raw body in the HMAC computation (matching the header set Shopify actually signs for webhooks), and reject the request if any of these are altered relative to what was signed. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be used as a sole tenant key without additional verification (e.g., cross-checking against the shop associated with the resource id in the payload).

### Proof of Concept
1. Install the target app (which uses this gem) on an attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to, e.g. `orders/create`, so Shopify delivers a legitimately HMAC-signed webhook: body `B`, header `x-shopify-hmac-sha256: H = HMAC(api_secret_key, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Capture `B` and `H` (attacker fully controls their own shop's inbound webhook endpoint/log, so this is trivial).
3. Replay a POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. In `Registry.process`, `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only checks `B` against `H`: [4](#0-3)  — the forged `shop-domain` header is never part of the signature check [5](#0-4) .
5. The handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)` as if the payload genuinely originated from the victim's tenant, even though it was fabricated using the attacker's own signed body.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
