### Title
Stale `TombStone` from soft `burn()` lets a former owner reclaim an object stolen from a legitimate later owner via `BURN_ADDRESS` - (File: aptos-move/framework/aptos-framework/sources/object.move)

### Summary
`object::burn()` performs a "soft burn": it attaches a `TombStone{original_owner}` marker to the object but does **not** change `ObjectCore.owner`. [1](#0-0)  Ordinary ownership transfers (`transfer`, `transfer_raw`, `transfer_to_object`, all routed through `transfer_raw_inner`) never check for or clear an existing `TombStone`. [2](#0-1)  Only `transfer_with_ref` (the `LinearTransferRef` path) explicitly clears a stale tombstone, with a comment showing the team already knows this is a reclaim risk. [3](#0-2)  Because the ordinary transfer path was not given the same fix, a stale tombstone recorded by a previous owner survives arbitrarily many legitimate subsequent transfers.

### Finding Description
`unburn()` allows reclaiming an object from `BURN_ADDRESS` back to the address recorded in the (possibly stale) `TombStone`, as long as that recorded address matches the caller:

```
} else if (object_core.owner == BURN_ADDRESS) {
    let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
    assert!(
        original_owner_addr == signer::address_of(original_owner),
        error::permission_denied(ENOT_OBJECT_OWNER)
    );
    transfer_raw_inner(object_addr, original_owner_addr);
}
``` [4](#0-3) 

The invariant this code implicitly assumes — "a live `TombStone` always reflects the *current* burn event, so its `original_owner` is the party who legitimately loses/regains the object at `BURN_ADDRESS`" — is never enforced. `transfer_raw_inner`, used by all normal `transfer`/`transfer_to_object` calls, silently carries a stale `TombStone` through any number of subsequent, fully legitimate ownership changes:

```
inline fun transfer_raw_inner(object: address, to: address) {
    let object_core = borrow_global_mut<ObjectCore>(object);
    if (object_core.owner != to) {
        event::emit(Transfer { object, from: object_core.owner, to });
        object_core.owner = to;
    };
}
``` [2](#0-1) 

Exploit chain:
1. Alice owns object `O`. She calls `burn(Alice, O)`, creating `TombStone{original_owner: Alice}` — `O`'s owner remains Alice, only the tombstone marker is added. [1](#0-0) 
2. Alice sells/transfers `O` to Bob using ordinary `object::transfer` (fully legitimate; the transfer succeeds because `allow_ungated_transfer` is unaffected by soft burn). The stale `TombStone{original_owner: Alice}` is never cleared. [5](#0-4) 
3. Bob, now the sole legitimate owner, later sends `O` to `BURN_ADDRESS` via an ordinary `transfer` (a plausible action — `BURN_ADDRESS` is a public, well-known constant, and users/marketplaces may use plain transfer to "burn" an item they hold, or Bob may transfer through several more hands before doing so). [6](#0-5) 
4. Alice calls `unburn(Alice, O)`. `object_core.owner == BURN_ADDRESS` matches the second branch; the stale tombstone's `original_owner_addr == Alice` passes the assert; `transfer_raw_inner` reassigns ownership of `O` to Alice — even though Alice had no relationship to the asset since step 2 and Bob (or whoever actually sent it to `BURN_ADDRESS`) is the party who should control any reclaim rights. [4](#0-3) 

This is structurally analogous to the reported bug's root cause: an unchecked assumption ("the map entry / tombstone state must be exactly what the current operation expects") that isn't actually validated against the live data, allowing an attacker-controlled precondition to corrupt program behavior — here corrupting the `owner` field of `ObjectCore`, not merely causing a panic.

The framework authors were aware of a version of this risk and patched only the `LinearTransferRef` path (`transfer_with_ref`), leaving the far more commonly used direct `transfer`/`transfer_to_object` path exposed. [7](#0-6) 

### Impact Explanation
This breaks the object-ownership custody invariant that "transfer/burn/unburn must preserve the intended controller" (Custody Pivot: "Object creation, transfer, burn, extensibility, and ownership refs must preserve the intended controller"). A former owner can silently plant a "landmine" tombstone on an object, sell it away through normal, undetectable transfers, and later steal it back from whichever bona fide holder eventually sends it to `BURN_ADDRESS`, with no signal to the victim that this risk exists. Any object (NFTs/token objects, fungible-asset-holding objects, resource-account-owning objects, etc.) using the standard `object::burn`/`unburn` lifecycle is affected. This is a direct, unauthorized owner-reassignment / theft of object-held value.

### Likelihood Explanation
The precondition (call `burn()` once, then transfer normally, then have any subsequent holder send it to `BURN_ADDRESS` through a plain transfer) requires no special privilege and no cooperation from the victim — only that the object eventually passes through `BURN_ADDRESS` via ordinary transfer, which is a natural user/marketplace action given that `BURN_ADDRESS` is a documented, public constant intended for burning objects. The bug is entirely triggerable by unprivileged accounts using publicly available entry functions (`burn`, `transfer`, `unburn`).

### Recommendation
Clear any existing `TombStone` inside `transfer_raw_inner` (or at minimum in `transfer_raw`/`transfer`/`transfer_to_object`) whenever ownership changes, mirroring the fix already applied in `transfer_with_ref`. Alternatively, disallow `unburn`'s `BURN_ADDRESS` reclaim branch entirely for tombstones created via the new soft `burn()` (e.g., by tracking whether the tombstone was created via `burn()` vs. legacy `burn_object_with_transfer()`), since only the legacy flow ever intentionally moves ownership to `BURN_ADDRESS`.

### Proof of Concept
```move
// Alice owns object O
object::burn(&alice, o);                       // soft burn, owner still Alice, TombStone{Alice} added
object::transfer(&alice, o, bob_addr);         // legitimate sale, TombStone untouched
// ... Bob now fully owns O, unaware of stale tombstone ...
object::transfer(&bob, o, object::burn_address()); // Bob "burns" O the normal way
object::unburn(&alice, o);                     // succeeds: owner == BURN_ADDRESS, tombstone.original_owner == alice
// Result: O's owner is now Alice again, stolen from Bob's chain of custody.
``` [8](#0-7)

    public entry fun burn<T: key>(owner: &signer, object: Object<T>) {
        let original_owner = signer::address_of(owner);
        assert!(is_owner(object, original_owner), error::permission_denied(ENOT_OBJECT_OWNER));
        let object_addr = object.inner;
        assert!(!exists<TombStone>(object_addr), EOBJECT_ALREADY_BURNT);
        move_to(&create_signer(object_addr), TombStone { original_owner });
    }

    /// Allow origin owners to reclaim any objects they previous burnt.
    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
