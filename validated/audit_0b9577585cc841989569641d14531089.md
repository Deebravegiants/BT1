Confirmed: `WebhookMetadata` passes `shop` and `topic` straight to the host app's `WebhookHandler#handle` [1](#0-0)  as the merchant/tenant identity for downstream business logic, while `Registry.process` only validates the HMAC and never checks that `shop`/`topic` are consistent with anything else [2](#0-1) .

### Title
Webhook `shop`/`topic`/`api_version`/`webhook_id` are trusted from unsigned headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers, but `to_signable_string` — the value actually fed into HMAC verification — returns only the raw request body [3](#0-2) . `Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and, if it passes, immediately trusts `request.topic` and `request.shop` to look up a handler and to construct `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle` [4](#0-3) . The identity binding that should hold — `hmac == HMAC(secret, body ‖ shop ‖ topic)` — is actually only `hmac == HMAC(secret, body)`, so `shop` and `topic` are fields "acted on" without being covered by the signature.

### Finding Description
`HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` using `OpenSSL.secure_compare` [5](#0-4) . For a webhook `Request`, `to_signable_string` is exactly `@raw_body` [6](#0-5) , while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers via `shopify_header` [7](#0-6) [8](#0-7) . Nothing in this gem cryptographically binds those header values to the body/signature — they can be freely modified as long as the body and its accompanying `hmac-sha256` header are kept intact.

Because `client_secret` is shared across every merchant that installs the app (it is not per-shop), any merchant who installs the app receives genuinely-signed webhook deliveries for their own shop. A malicious merchant can capture one such delivery (body + `X-Shopify-Hmac-Sha256` header) and replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header with a victim shop's domain. `HmacValidator.validate` still succeeds, because it only checks the untouched body, and `Registry.process` then dispatches to the handler with `WebhookMetadata#shop` set to the victim's domain [9](#0-8) .

This breaks the equality that should hold before/after the request: before, `shop_header == shop_that_actually_generated_and_signed_this_body`; after a forged replay, `shop_header` is attacker-controlled while the signature validity is unchanged.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an app built on this gem's webhook stack will process attacker-forged events under an arbitrary victim shop's identity, using only a legitimately-obtained signature from the attacker's own (different) shop. Depending on what the host app's `WebhookHandler` does with `data.shop` (e.g., look up/mutate victim merchant records, revoke access, trigger `shop/redact`-style flows, or update per-shop state), this can lead to cross-tenant data corruption or unauthorized actions attributed to a victim merchant — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is non-trivial but not trivial to weaponize universally: the attacker needs (a) their own working installation of the target app (any merchant/developer can install a public or unlisted app), and (b) a webhook topic/body whose content is either shop-independent or doesn't need to differ from the victim's expected content for the intended effect (e.g., topics with minimal or predictable bodies like `app/uninstalled`, `shop/update`, or webhooks where the handler trusts `data.shop` more than `data.body`). No secret material, TLS interception, or privileged account is required — only a standard merchant install of the vulnerable app, satisfying the "unprivileged internet user" constraint.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, and ideally `api_version`/`webhook_id`) in the signed payload verified by `to_signable_string`, or otherwise independently authenticate that the `shop` header matches a shop that is expected to be delivering this specific signed body (e.g., verify webhook subscriptions are scoped per-shop and reject deliveries whose `shop` header does not match a value derivable from the signed body/context). At minimum, document loudly that `request.shop`/`request.topic` are unauthenticated and must not be used for authorization decisions without additional binding.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop, `attacker.myshopify.com`, thereby obtaining the app's shared `client_secret` behavior via legitimate webhook deliveries (no secret is disclosed to the attacker; they merely receive validly-signed deliveries).
2. Shopify sends the attacker's shop a legitimate webhook, e.g. topic `app/uninstalled`, with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(client_secret, B)`, plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker POSTs the same body `B` and the same `X-Shopify-Hmac-Sha256: H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally reuses/changes `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`== B`) only, matches `H`, and returns `true` — see `lib/shopify_api/webhooks/registry.rb:190` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
5. The handler registered for that topic is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", ...)` — see `lib/shopify_api/webhooks/registry.rb:198-199` — causing the host app to process an attacker-forged event as if it originated from the victim shop.
