### Title
CEI violation in `withdraw()` allows cross-function reentrancy via native ETH callback before escrow debit - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The `withdraw()` function in the Tron-targeted `IntentGatewayV2.sol` releases escrowed native ETH/tokens to a beneficiary via an external call *before* decrementing the corresponding `_orders[commitment][token]` escrow balance, and before zeroing the transaction-fee entry. This is the same Checks-Effects-Interactions violation flagged in the external report for `CEToken`/`Core`/`DebtToken`, reproduced here in the intents settlement path.

### Finding Description
`withdraw()` sets `_filled[body.commitment] = beneficiary` once at the top [1](#0-0) , then loops over `body.tokens`, sending native ETH via a raw `.call{value: amount}("")` (or an ERC20 `transfer` call) to `beneficiary`, and only *afterward* decrements `_orders[body.commitment][token]`: [2](#0-1) 

The same pattern repeats for the transaction-fee payout: the fee token transfer happens before `delete _orders[body.commitment][TRANSACTION_FEES]`: [3](#0-2) 

Because `token == address(0)` triggers a raw `.call{value: amount}("")` to an attacker-controlled `beneficiary` address, that beneficiary's `receive()`/fallback executes *before* `_orders[body.commitment][token]` is decremented. If the beneficiary is a contract, it can reenter the gateway. `withdraw()` is reached from `onAccept()` (for `RedeemEscrow`/`RefundEscrow` requests) and from `onGetResponse()` [4](#0-3) [5](#0-4) , both of which are `onlyHost`-gated entry points invoked by the ISMP host after message/proof delivery — i.e., reachable by any relayer that delivers a validly-proven cross-chain message, not requiring privileged access.

Unlike the EVM `IntentsBase.sol`/`IntrinsicIntents.sol` version, which was already hardened (the accompanying `IntrinsicIntentsReentrancyTest.sol` documents that `_filled[commitment] = msg.sender` is now set *before* any external call specifically to defeat this class of reentrancy), the Tron contract's `withdraw()` still performs the value transfer inside the loop with escrow-decrement deferred to *after* the call, per-token, rather than before it.

### Impact Explanation
While `_filled[body.commitment]` is set once before the loop (which blocks a second full "settlement" of the same commitment), the multi-token loop itself is not protected: on a multi-asset order, reentrant calls made during the ETH transfer for token[i] can be triggered before `_orders[commitment][token[i]]` is debited. Combined with the `token.call(...)` pattern (not `safeTransfer`) for ERC20 legs and raw `.call` for the fee-token payout, a malicious beneficiary or a token with hooks (e.g., ERC777-style or an ETH beneficiary contract) can re-enter the still-`onlyHost`-gated but externally-triggerable code path (e.g., calling back into other view/state reads of `_orders` that are still stale, or into other functions that share `_orders`/escrow state) while the balance for that token has not yet been reduced, and before the transaction-fee mapping is cleared. This risks double-payout of escrowed input tokens/fees or draining shared escrow state — a concrete theft-of-funds risk in the gateway's own escrow, matching the report's Medium-severity classification for the analogous `CEToken`/`Core` CEI gaps.

### Likelihood Explanation
Reachability requires only a relayer delivering a proven cross-chain settlement message (`RedeemEscrow`/`RefundEscrow` via `onAccept`, or a GET response via `onGetResponse`) targeting an order whose beneficiary is attacker-controlled and whose output includes a native-ETH leg — both fully attacker-influenced parameters set at order-placement time on the source chain. No governance or admin privilege is needed; only a self-submitted order and standard message delivery, matching the required "single relayed proof / token transfer" reachability bar.

### Recommendation
Apply full CEI ordering in `withdraw()`: decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) *before* performing the corresponding external transfer/call for each token in the loop, mirroring the fix already applied in the EVM `IntentsBase.sol` version of the fill/withdraw paths. Additionally, consider adding a reentrancy guard around `withdraw()`/`onAccept()`/`onGetResponse()` given the multiple external calls per invocation.

### Proof of Concept
1. Attacker places (or is beneficiary of) an order with `order.output` (or via `RefundEscrow`/`RedeemEscrow` `WithdrawalRequest.tokens`) containing at least two entries, the first being native ETH (`token == address(0)`) and the beneficiary set to an attacker-deployed contract.
2. A relayer delivers the settlement message; `onAccept` decodes the `WithdrawalRequest` and calls `withdraw(body, ...)`.
3. In the loop, the first iteration sends ETH to the attacker contract via `beneficiary.call{value: amount}("")` before `_orders[commitment][token] -= amount` executes (line 710 runs only after line 703).
4. The attacker contract's `receive()` reenters a path that reads/uses the still-unmodified `_orders[commitment][token]` balance (e.g., attempting a second cancel/withdraw claim tied to the same commitment/token before the debit lands), enabling double-spend of the escrowed balance depending on what state is still stale at that point in the call.
5. Because the escrow decrement for that specific token slot only lands after the external call returns, any reentrant path that reads or debits `_orders[commitment][token]` during the callback window operates on stale accounting.
