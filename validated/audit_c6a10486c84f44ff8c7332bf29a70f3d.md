## Title
Webhook Tenant (`shop`) and Metadata Fields Not Covered by HMAC Signature Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body alone, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body's signature and then dispatches the handler using the unauthenticated `shop` header value. Because the app's HMAC secret (`Context.api_secret_key`) is shared across every shop that installs the app, an attacker who legitimately installs the app on their own shop can obtain a validly-signed `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with a forged `shop-domain` header pointing at a victim tenant, causing the app to process attacker-controlled webhook content as if it belonged to the victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate_signature` signs/verifies `verifiable_query.to_signable_string` only: [3](#0-2) 

`Registry.process` validates that HMAC, then trusts the unauthenticated `request.shop`/`request.topic` for dispatch and builds the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The documented contract explicitly tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook," which the example usage trusts directly (`shop_domain: data.shop`): [5](#0-4) [6](#0-5) 

The broken identity binding is:
`shop_bytes_covered_by_HMAC (raw_body only) != shop_used_for_tenant_dispatch (X-Shopify-Shop-Domain header)`

Since the app-level `api_secret_key` is identical for all shops that install a given app, and the signature never covers the `shop-domain` header, any tenant of the app can generate a validly-signed body/HMAC pair for their own shop and then replay that same pair with a different `shop-domain` header value to make the gem attribute the webhook to an arbitrary other shop.

### Impact Explanation
This is a cross-tenant access vulnerability (Critical): the gem's own webhook-processing API is the mechanism the host application relies on to segment webhook data per tenant, and this gem hands the handler a `shop` value that isn't bound to the signed payload. An attacker who is a legitimate (even free-tier) install of the app can forge webhook deliveries "as" any other shop known to use the app, injecting attacker-controlled JSON body content attributed to a victim's tenant. Depending on the handler (as illustrated in the gem's own docs, which pass `data.shop` straight through to job/queue processing), this can corrupt or inject data into another merchant's tenant-scoped records.

### Likelihood Explanation
Likelihood is high for any app author following the documented handler pattern (`data.shop` trusted for tenant identification) exactly as shown in `docs/usage/webhooks.md`. No privileged credentials, TLS interception, or social engineering are required — only becoming an ordinary (potentially free) install of the target app to receive one legitimately-signed webhook, then replaying it with a modified header, which is fully attacker-controlled since HTTP headers are not authenticated by this HMAC scheme.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the HMAC-signable string in `Webhooks::Request#to_signable_string` (or otherwise cryptographically authenticate them), so that a signature computed over the body cannot be replayed under a different shop/topic. At minimum, `Registry.process` should refuse to trust `request.shop` unless it's part of the material actually verified by `HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (no special privileges needed — this is standard app installation).
2. Attacker triggers any subscribed webhook topic (e.g. `orders/create`) in their own store. Shopify delivers a webhook to the app's HTTP endpoint with headers including `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and the raw JSON body — all of which the attacker can observe since it is delivered to infrastructure the attacker (as the merchant) controls/can log.
3. Attacker crafts a new POST to the app's webhook endpoint reusing the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the app's shared `api_secret_key`, which is unaffected by the header change (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: attacker_controlled_JSON, ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the app to process attacker-controlled data as if it originated from the victim's shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
