### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` never binds the `shop-domain` header to the signed payload. Any party that has obtained one valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` can replay that pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` accepts this as valid and dispatches the handler with the attacker-chosen `shop`, breaking the binding `verified_hmac_owner == shop_acted_on`.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` purely from an HTTP header: [1](#0-0) 

But the value that is actually HMAC-signed is only the raw body: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` (from the unauthenticated header) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` only checks that `hmac == HMAC(secret, to_signable_string)`, i.e. `HMAC(secret, raw_body)` — the `shop` header plays no role in the signature at all: [4](#0-3) 

Because every shop that installs the app shares the same `api_secret_key`, any merchant who installs the app (an unprivileged party with respect to other tenants) legitimately receives real webhooks with a valid `(raw_body, hmac)` pair signed under that shared secret. That merchant can then resend the identical body+HMAC to the app's webhook endpoint while forging the `shop-domain` header to name a *different* shop. `HmacValidator.validate` will report success because it never inspects the header, and `Registry.process` will invoke the topic handler claiming the data belongs to the victim shop — a `shop == hmac_signer` binding is broken, i.e. the attacker's own signed payload gets attributed to another tenant's `shop`.

### Impact Explanation
This is a cross-tenant confusion: a party who is only entitled to send/replay traffic tied to their own shop can cause the application to process fabricated webhook events (order changes, app-uninstall, GDPR data-request, etc.) as if they originated from an arbitrary other shop, since the app trusts `WebhookMetadata#shop` for tenant routing/storage keys. Depending on the host app's handler logic, this can lead to data being written into, or actions being taken against, another tenant's records — matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Likelihood is realistic: obtaining one valid `(body, hmac)` pair only requires the attacker to install the app themselves (any unprivileged internet user can do this for a public/free app) and capture one of their own legitimate webhook deliveries, then replay it with a different `shop-domain` header value. No secrets, tokens, or privileged access are required beyond being a normal app installer.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the data that is authenticated, or independently verify that the `shop` header value is one this app instance actually has an active session/install for before trusting it in `WebhookMetadata`. At minimum, `Registry.process` (or the host app via documented guidance) should cross-check `request.shop` against a known, previously-registered shop for the resolved session rather than trusting the header purely because the body-only HMAC passed.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, receiving a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — identical to the attacker-supplied HMAC — and passes.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ...)`, causing the app to process attacker-controlled data as belonging to `victim.myshopify.com`. [3](#0-2)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
