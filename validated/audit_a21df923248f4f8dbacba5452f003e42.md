### Title
Emporium wallet-invoked relay fee bypasses the variable-rate fee component - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
In `EmporiumUpgradeable.payRelayFees`, the fee charged to the relay/protocol differs depending on whether the Emporium call is routed through a `HinkalWallet` (`signerAddress != address(0)`) or executed directly (`signerAddress == address(0)`). For the non-wallet path the full fee schedule (`flatFee` **and** `variableRate`) is applied via `calculateRelayFee`, but for the wallet path only `flatFee` is ever charged, silently dropping the percentage-based component of the relay fee.

### Finding Description
`payRelayFees` computes the fee to send to the relay per token: [1](#0-0) 

When `signerAddress == address(0)`, `relayFee` is derived from `RelayStore.calculateRelayFee(sumAbs, flatFee, feeStructure.variableRate)`, which applies the full percentage-based fee schedule: [2](#0-1) 

But when `signerAddress != address(0)` (i.e. the caller routes the Emporium action through their own `HinkalWallet`), the code simply sets `relayFee = flatFee;`, entirely ignoring `feeStructure.variableRate`. The fee is then pulled straight from the wallet via `sendToRelayFromWallet` → `doSendToRelay`, bypassing Emporium's own balance accounting (`balancesBefore`/`balancesAfter`) altogether: [3](#0-2) 

`feeStructure` (containing `flatFee`/`variableRate`) is part of `calldataHash2`, so it is signed by the note-owner/prover and cannot be tampered with by a third party — the issue is not an authorization bypass but a logic bug in fee calculation that any user can trigger simply by choosing to route their own Emporium call through `invokeWallet=true`/a non-zero `signerAddress`, which is a normal, unprivileged path available to any EOA using the wallet-based Emporium flow.

### Impact Explanation
Whenever a user (or their configured `HinkalWallet`) submits an Emporium action with a non-zero `signerAddress`, the relay/protocol permanently loses the variable-rate percentage of its intended fee revenue for that transaction — only the flat fee is ever collected. This is a systematic, protocol-wide under-collection of relay/protocol fees rather than an isolated edge case, matching the "permanent freezing/loss of protocol or relay fees" impact category, analogous to the referenced report where a miscalculated balance term let a party bypass fees owed to governance/relay.

### Likelihood Explanation
High likelihood: any ordinary user who uses the wallet-invoked Emporium flow (a documented, supported code path, not requiring any special privilege) automatically underpays relay fees whenever `feeStructure.variableRate > 0`. No attacker-crafted proof forgery or signature bypass is required — it is a direct consequence of normal usage of `payRelayFees`.

### Recommendation
In the `signerAddress != address(0)` branch of `payRelayFees`, apply the same fee formula used for the non-wallet path (`hinkalHelper.calculateRelayFee(sumAbs, flatFee, feeStructure.variableRate)`) instead of hardcoding `relayFee = flatFee`, ensuring the variable-rate component is consistently charged and forwarded via `doSendToRelay` regardless of which execution path is used.

### Proof of Concept
1. User creates an Emporium `EmporiumStack` with `signerAddress = <their HinkalWallet address>` and at least one op with `invokeWallet = true`.
2. `circomData.feeStructure.variableRate` is set to a nonzero value (e.g. 100 = 1%) and `flatFee = 0`.
3. `runAction` executes the stack, then calls `payRelayFees(circomData, stack.signerAddress, deltaAmountChanges)`.
4. Because `signerAddress != address(0)`, `relayFee = flatFee = 0` is computed for the token, so `payRelay` → `sendToRelayFromWallet` sends `0` to the relay.
5. The relay receives none of the `variableRate`-based fee that would have been charged had the same transaction been submitted with `signerAddress == address(0)`, permanently denying that fee to the relay/protocol.

    function calculateRelayFee(
        uint256 balance,
        uint256 flatFee,
        uint256 variableRate
    ) public pure returns (uint256 relayFee) {
        require(balance >= flatFee, "Relay Fee is over withdraw amount");
        uint256 recipientAmount = ((10000 - variableRate) *
            (balance - flatFee)) / 10000;
        relayFee = balance - recipientAmount;
    }
