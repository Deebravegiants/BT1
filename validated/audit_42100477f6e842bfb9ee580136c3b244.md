### Title
Webhook `shop` (`X-Shopify-Shop-Domain`) is not covered by HMAC signature, allowing cross-tenant attribution forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies body integrity but never authenticates the `shopify-shop-domain` header that `Request#shop` exposes to the host app via `WebhookMetadata`. An attacker who owns a legitimate development shop with the app installed can capture their own genuinely-signed webhook and replay it with the `shop-domain` header swapped to a victim's domain; `HmacValidator.validate` still returns `true` while `request.shop`/`WebhookMetadata#shop` reports the victim.

### Finding Description
The broken binding: `Utils::HmacValidator.validate(request) == true` is expected to imply `request.shop` is the shop that actually produced/received `request.parsed_body`. In code:

- `Request#to_signable_string` at [1](#0-0)  returns only `@raw_body`.
- `Request#shop` at [2](#0-1)  reads the `shopify-shop-domain`/`x-shopify-shop-domain` header directly with no cross-check against the signed bytes or any session/shop registry.
- `HmacValidator.validate`/`validate_signature` at [3](#0-2)  computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header. The `shop` header plays no role in this computation.
- `Registry.process` at [4](#0-3)  validates the HMAC and then immediately hands `request.shop` to the handler via `WebhookMetadata.new(topic: ..., shop: request.shop, ...)` with no additional shop authentication step.

Exploit flow: the attacker registers their own development shop, installs the app, and lets Shopify deliver a real webhook to the app's endpoint. Because the webhook HMAC secret (`Context.api_secret_key`) is the app's client secret shared across every shop that installs the app - not a per-shop secret - the attacker's own captured `(raw_body, hmac)` pair is valid for any shop under that app. The attacker then sends this same body and HMAC header to the app's webhook endpoint again, but with `x-shopify-shop-domain: victim.myshopify.com`. `HmacValidator.validate` recomputes the HMAC over the unchanged raw body and still matches, so validation passes; `request.shop` now returns `victim.myshopify.com`. No component in this gem (`ShopValidator`, session lookup, `Context.setup?`/`private?`/`embedded?`, Sorbet typing) checks that the `shop` header is consistent with the signed payload or with any known session for that shop.

### Impact Explanation
If the host app trusts `WebhookMetadata#shop` (as the gem's documented flow implies once `HmacValidator.validate` passes) to route/attribute webhook data to a tenant record, an attacker can inject their own webhook payload into a victim's tenant data path while the request self-reports as validly HMAC'd. This is a cross-tenant data injection primitive, repeatable against arbitrary victim shop domains at will (the attacker only needs to change one header value per request), matching the Critical category ("cross-tenant access") from the rules.

### Likelihood Explanation
Preconditions are all attacker-controllable and match the allowed threat model: create a real development shop, install the app, receive a genuinely-signed webhook. No `api_secret_key`, access token, or any secret needs to be known or leaked - the attacker only replays bytes Shopify itself delivered to them, substituting an unsigned header. The attack cost is a single legitimate app install plus one crafted HTTP replay, and it is fully repeatable against any shop domain the attacker chooses to put in the header.

### Recommendation
Do not treat `Request#shop` (or `WebhookMetadata#shop`) as authenticated by `HmacValidator.validate` alone. Either include the shop domain in the signable string in a way that ties it to a value the app can verify against a known/registered session (not currently possible since Shopify itself doesn't sign the header), or explicitly document in this gem that `shop` is unauthenticated and callers must cross-check it against their own session store for that specific webhook `topic`/`webhook_id` before trusting it, and provide a helper that fails closed when no matching session exists for the reported shop.

### Proof of Concept
```ruby
# test/webhooks/request_shop_spoof_test.rb
require "test_helper"

class RequestShopSpoofTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
  end

  def test_shop_header_not_covered_by_hmac
    body = '{"id":1}'
    hmac = OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), "secret", body)
    hmac_b64 = Base64.strict_encode64([hmac].pack("H*"))

    request = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "x-shopify-topic" => "orders/create",
        "x-shopify-hmac-sha256" => hmac_b64,
        "x-shopify-shop-domain" => "victim.myshopify.com", # spoofed
        "x-shopify-api-version" => "2023-10",
        "x-shopify-webhook-id" => "1",
      },
    )

    assert ShopifyAPI::Utils::HmacValidator.validate(request) # signature still valid
    assert_equal "victim.myshopify.com", request.shop         # shop is unauthenticated
  end
end
```
This demonstrates `HmacValidator.validate(request) == true` while `request.shop` has been substituted to an arbitrary victim domain, proving the equality `HMAC-verified body == authenticated shop` does not hold.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
