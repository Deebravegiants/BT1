## Title
Webhook `shop` (tenant identifier) is not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable string from the raw body only, while the `shop` (tenant identity) is read from an unsigned HTTP header. `Webhooks::Registry.process` validates only that the body matches the HMAC, then passes the attacker-controllable `shop` value straight to the app's webhook handler as the authoritative tenant identity, breaking the binding `signed(shop) == used(shop)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `Request#shop` (the tenant identifier delivered to the handler) is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the raw body), never the shop header: [3](#0-2) 

`Webhooks::Registry.process` uses this validation result as the sole authentication gate, then forwards `request.shop` (an unauthenticated header) as the trusted tenant identity to the merchant's webhook handler: [4](#0-3) 

Because the HMAC is keyed with the app's single `api_secret_key` (not a per-shop secret) and only covers the body, any actor who obtains one validly-signed webhook body/HMAC pair — trivially available by installing the app on their own attacker-controlled shop and receiving a genuine webhook — can replay that exact body+HMAC directly to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` still succeeds (body/HMAC pair unchanged), and `Registry.process` reports `data.shop` as the attacker's chosen victim shop domain instead of the shop that actually produced the payload.

This is the same class of bug as the report: an identity/ownership field (`shop`, i.e., the tenant) is acted upon by the library but not included in the cryptographically verified data (`raw_body` only), so the verified bytes and the trusted identity diverge — `verified(body) != verified(shop)`.

### Impact Explanation
Any downstream application logic that keys off `WebhookMetadata#shop` (e.g., to look up a shop's session/access token, update per-shop data, or trigger tenant-scoped side effects) can be made to act on behalf of, or against, a shop the attacker does not control — a cross-tenant confusion condition. This satisfies the Critical "cross-tenant access" impact bucket, since the gem itself hands the host application a spoofable tenant identifier under the guise of "HMAC-verified".

### Likelihood Explanation
Exploitation requires only unauthenticated network access to the app's public webhook endpoint plus one legitimately-signed webhook body (obtainable by any attacker who installs the app on their own development/free store, which is standard, low-friction Shopify Partner functionality). No merchant credentials, access tokens, or `client_secret` are needed.

### Recommendation
Bind the `shop` claim into the material that is actually verified — e.g., include the `shop-domain` header in the signable string, or independently corroborate `request.shop` via the existing OAuth session store (i.e., only accept webhook shops that already have an active, previously-established session) — before handing `WebhookMetadata` to the registered handler.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop and receives a real webhook,
# capturing raw_body and the X-Shopify-Hmac-Sha256 header (both valid).
raw_body = '{"id": 1, "note": "legit payload from attacker-owned shop"}'
valid_hmac = captured_from_own_shop_webhook # computed by Shopify over raw_body with app secret

# Attacker replays the exact body/HMAC pair directly to the app's public
# webhook endpoint, but swaps the shop-domain header to a victim shop.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate passes (body unchanged); handler receives
#    data.shop == "victim-shop.myshopify.com" even though the payload
#    never originated from that shop.
``` [4](#0-3) [5](#0-4)
