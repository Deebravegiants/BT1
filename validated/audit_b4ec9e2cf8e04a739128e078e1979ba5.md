[1](#0-0) ### Title
Unconstrained strategy-route subcalls can smuggle wallet-draining transfers into the caller's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_tokens` accepts caller-supplied route bytes and invokes the configured router after creating only one contract-scoped authorization for `token_in.transfer(controller, router, amount_in)`. [1](#0-0) [2](#0-1)  The function's settlement checks measure only the controller's input and output balances, leaving unrelated `caller`-authorized token transfers executed by route contracts outside the protocol's accounting checks. [3](#0-2) 

### Finding Description
A reachable path is `swap_collateral(caller=victim, account_id=victim_account, current=..., amount=..., new=..., swap=malicious_route)`, where `malicious_route` instructs the configured router to invoke an attacker-controlled venue during the swap. [4](#0-3)  The controller authorizes the router to pull only the strategy input held by the controller, but that authorization does not constrain which token contracts or venue contracts the router subsequently invokes. [5](#0-4) 

During route execution, the malicious venue can call an unrelated listed token with `transfer(victim, attacker, victim_balance)`, causing the token to require the victim's authorization. [6](#0-5)  Transaction simulation records that required invocation as a child of the victim's controller authorization; once the victim signs the resulting tree, the nested transfer executes even though it is unrelated to the lending operation. [7](#0-6) 

The router can still return a valid output to the controller, so `actual_spent <= amount_in` and `received > 0` both pass while the victim loses unrelated wallet funds. [3](#0-2) 

### Impact Explanation
An attacker can steal arbitrary token balances from the transaction signer, not merely the collateral or input amount committed to the lending strategy. [8](#0-7)  This is theft of user funds and is bounded by the victim's wallet balance and the transfer recorded in the signed authorization tree rather than by the protocol's risk gates. [7](#0-6) 

### Likelihood Explanation
Exploitation requires the victim to submit and sign a malicious strategy transaction, but the route is opaque `Bytes` to the controller and the invoked venues are not constrained by the controller's input authorization. [9](#0-8)  A victim who relies on route bytes or a UI that does not prominently display every nested authorization can approve a tree containing the unrelated transfer while still receiving the expected strategy output. [3](#0-2) 

### Recommendation
Restrict route execution to a governance-approved allowlist of token and venue contracts, enforced by the configured router or by a decoded allowlist supplied to and validated by the controller. [10](#0-9)  Additionally reject any strategy transaction whose caller authorization contains token transfers beyond the explicitly expected funding legs, although protocol-side venue allowlisting is the stronger invariant. [2](#0-1) 

### Proof of Concept
1. Victim owns a healthy account with withdrawable collateral in `current` and holds an unrelated valuable token `T`. [11](#0-10) 
2. Attacker supplies a `swap_collateral` route that reaches an attacker-controlled venue and still returns enough `new` tokens to satisfy `verify_router_output`. [12](#0-11) 
3. Inside the venue's route callback, deploy conceptual attack code—not repository code—calling `token::Client::new(&env, &T).transfer(&victim, &attacker, &victim_balance)`. [6](#0-5) 
4. Simulation includes that `T.transfer(victim, attacker, victim_balance)` as a child of the victim's authorization for the controller call; the victim signs it. [7](#0-6) 
5. The venue's transfer drains `T`, the router delivers valid `new` output, and the controller accepts the transaction because its post-checks only compare the controller's `token_in` and `token_out` balances. [3](#0-2)

    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),

        sub_invocations: Vec::new(env),
    });
