## Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking a merchant's webhook handler with `WebhookMetadata` containing the `shop` field. In practice, the HMAC signature only authenticates the raw request body — it never covers the `x-shopify-shop-domain` header. Any actor who can obtain one validly-signed webhook body (e.g. by installing the app on their own store and triggering a webhook) can replay that exact body to the app's webhook endpoint with an arbitrary `shop-domain` header, and the gem will report the HMAC as valid and hand the (attacker-controlled) `shop` value to the handler as if it were authenticated.

### Finding Description
The HMAC check is implemented generically via `Utils::VerifiableQuery`/`HmacValidator`, and for webhooks the signable content is defined as just the raw body: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`shop` is read straight from an HTTP header with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac-sha256` header — it never incorporates `shop`, `topic`, `webhook-id`, or `api-version`: [3](#0-2) 

`Registry.process` only checks this body-only HMAC before dispatching the (header-derived) `shop` to the handler as trusted metadata: [4](#0-3) 

The documented contract explicitly frames this as an authenticity guarantee ("This will verify the request did indeed come from Shopify") and documents `shop` as "The shop domain of the webhook" — i.e., an attribute callers are expected to trust for tenant identification: [5](#0-4) [6](#0-5) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`HMAC-authenticated bytes (raw_body only) == bytes the handler treats as tenant-scoped (raw_body + shop-domain header)`.

Because `api_secret_key` is a single shared secret for the whole app (shared across every shop that installs it), any shop can legitimately produce an HMAC-valid webhook body (by generating activity in their own store). That same `(body, hmac)` pair remains valid for any other `shop-domain` header value, since the header is excluded from the signed content.

### Impact Explanation
An attacker who installs the target app on a shop they control (a normal, low-privilege action requiring no special access) can capture a genuine webhook delivery's body+HMAC, then replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header set to a victim shop's domain. `Registry.process` validates the HMAC successfully (it only checks the body) and calls the handler with `WebhookMetadata#shop` set to the victim's domain. Any host application that uses `data.shop` from a processed webhook for tenant lookup, data writes, cache keys, or triggering actions scoped to a shop (exactly as shown in the gem's own documented usage example, `perform_later(topic:, shop_domain: data.shop, webhook: data.body)`) will process attacker-supplied webhook content under the victim's tenant identity — a cross-tenant data confusion/injection primitive stemming directly from this gem's guarantees.

### Likelihood Explanation
Likelihood is high: no secrets, tokens, or privileged access are required — only the ability to install the target Shopify app on any store (which is the normal, unprivileged onboarding flow for embedded apps) and to send an HTTP POST to the app's known webhook endpoint. The attack is a pure replay with a substituted header value.

### Recommendation
Bind the `shop` domain (and ideally `topic`/`webhook-id`) into the value that is HMAC-verified, or independently verify that the `shop-domain` header corresponds to a shop that legitimately owns the webhook (e.g., cross-check against the registered webhook subscription/shop for the given `webhook_id`) before exposing `WebhookMetadata#shop` as trusted to handlers. At minimum, update `to_signable_string` to include the shop domain header in the signable string, matching what is actually asserted as verified in the documentation.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com` and trigger a subscribed webhook topic (e.g., `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` sent by Shopify (computed with the app's single shared `api_secret_key`).
2. Send a new POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256`: `H` (unchanged)
   - `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com`
   - `X-Shopify-Topic` / `X-Shopify-Webhook-Id`: unchanged or attacker-chosen.
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-controlled webhook content under the victim shop's identity.
