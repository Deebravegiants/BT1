### Title
Unchecked-length `copy_from_slice` panics the runtime when converting an attacker-supplied ECDSA BEEFY `Vote.signature` into a fixed 65-byte array - ([File: evm/rust/src/conversions.rs])

### Summary
The `From<Vote> for SignatureWithAuthorityIndex` conversion in `evm/rust/src/conversions.rs` copies an ABI-decoded, attacker-controlled `bytes` field directly into a fixed-size `[u8; 65]` buffer with `copy_from_slice` before checking its length. This mirrors the CVE-2018-5809 bug class (LibRaw's `parse_exif` copying attacker-controlled length data into a fixed buffer without validating the size first), except here the "buffer overflow" manifests as a Rust panic (trap) rather than memory corruption — but it is reachable from a single permissionless extrinsic that submits a "naive"/ECDSA BEEFY consensus proof.

### Finding Description
`beefy-consensus-proofs::Pallet::do_submit_proof` / `verify_and_apply` (`modules/pallets/beefy-consensus-proofs/src/lib.rs`) accepts a raw `proof: Vec<u8>` from any submitter. For `PROOF_TYPE_NAIVE`, it ABI-decodes the payload into `ismp_abi::ecdsa_beefy::Beefy::BeefyConsensusProof` and immediately calls `.into()` to produce a `beefy_verifier_primitives::ConsensusMessage`: [1](#0-0) 

That `Into` conversion recurses through `Commitment`, `SignedCommitment`, and each `Vote` in the ABI struct's `signatures` array. `Vote.signature` is a Solidity `bytes` field — fully attacker-controlled length, since it comes straight from calldata the submitter constructs. The conversion is: [2](#0-1) 

`signature.copy_from_slice(&sig_bytes)` requires `sig_bytes.len() == 65` or it panics with "source slice length ... does not match destination slice length". No length check precedes the copy, unlike the sibling conversions in the same file which use `.try_into().expect(...)` on integer types that are provably in range, or unlike the pattern the codebase uses elsewhere in `evm/rust/src/conversions.rs` (e.g. `to_bytes_32` in `modules/ismp/state-machines/evm/src/utils.rs`) that explicitly validates length before copying: [3](#0-2) 

The codebase has an established, repeatedly-applied fix pattern for exactly this bug class — reject-before-copy — evidenced by multiple prior regression fixes for the same root cause elsewhere in the tree (BEEFY MMR leaf-index panic, GRANDPA header-not-found panic, sync-committee multiproof panic, Pharos trie depth panic, RLP HP-prefix panic, and the `as_utf8_string`/`consensus_state_id` 4-byte panic fixes, several with explicit "must never panic on untrusted input" comments): [4](#0-3) [5](#0-4) 

`evm/rust/src/conversions.rs::From<Vote>` was missed by this hardening effort.

### Impact Explanation
Any account can call the BEEFY proof-submission extrinsic with `proof_type = PROOF_TYPE_NAIVE` and a `Vote.signature` whose byte length is not exactly 65 (e.g. 0, 64, or 66 bytes — all trivially constructible ABI-encoded `bytes`). The runtime panics inside `do_submit_proof`/`verify_and_apply` while decoding the proof, before any cryptographic or authority-set check runs. Because this executes inside the on-chain dispatch of a submitted extrinsic, an unhandled panic here is a denial-of-service on the BEEFY consensus-update path — the route by which Hyperbridge ingests new relay-chain finality and, subsequently, new cross-chain message commitments. This satisfies the "route unable to deliver messages" impact bar: any relayer attempting to advance BEEFY consensus (a prerequisite for delivering POST/GET messages secured by that consensus client) can have their legitimate submissions preceded/blocked by a malicious submitter's crafted proof, and depending on how FRAME handles panics during block execution/import, this can disrupt block production/import for the chain, not just revert a single extrinsic.

### Likelihood Explanation
High. The `submit_proof` call is permissionless and requires no special privilege — this matches the "unprivileged relayer" reachability the review scope calls out. Constructing a malformed `Vote.signature` of the wrong byte length is a single, cheap ABI encoding, requiring no cryptographic material or authority collusion.

### Recommendation
Validate `sig_bytes.len() == 65` before `copy_from_slice` in `From<Vote> for SignatureWithAuthorityIndex` (`evm/rust/src/conversions.rs`), returning a `TryFrom`/`Result` error (propagated as `Error::<T>::AbiDecodeFailed` or equivalent) instead of an infallible `From` that can panic. Audit all other infallible `From` impls in this file and in `ismp_abi`/`evm/rust` that convert Solidity `bytes`/`bytes[]` ABI fields into fixed-size arrays for the same missing-length-check pattern.

### Proof of Concept
1. Craft an ABI-encoded `ecdsa_beefy::Beefy::BeefyConsensusProof` payload whose `SignedCommitment.signatures` array contains one `Vote` with `signature` set to an arbitrary `bytes` value of length ≠ 65 (e.g. `0x00`).
2. Prepend the `PROOF_TYPE_NAIVE` discriminant byte and submit it via the pallet's proof-submission extrinsic from any account.
3. `do_submit_proof` → `verify_and_apply` ABI-decodes the payload successfully (the ABI schema only requires a `bytes` field, any length is valid ABI), then calls `abi_proof.into()`, which invokes `From<Vote> for SignatureWithAuthorityIndex` and panics at `signature.copy_from_slice(&sig_bytes)` because `sig_bytes.len() != 65`.

Note: I could not directly inspect the exact `#[pallet::call]` signature/origin annotation for `submit_proof` (only line-count matches were returned, not the call's dispatch-origin attribute), so I cannot 100% confirm whether it is `ensure_signed` (any account) vs. some other origin gate; the surrounding code (`submitter: T::AccountId`, comments about "the submitter pays the fee") strongly suggest it is a normal signed extrinsic callable by any account, consistent with the codebase's own framing of BEEFY proof submission as relayer-driven and permissionless elsewhere in the docs.
