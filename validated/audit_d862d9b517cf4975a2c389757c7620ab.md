### Title
Webhook `shop` Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop` (and `topic`/`api_version`/`webhook_id`) values are read directly from HTTP headers that are never included in the signed content. `Webhooks::Registry.process` trusts `request.shop` as the tenant identity passed to the app's handler after only confirming the body's HMAC is valid, so the shop that "authenticated" the request (implicitly, via a valid HMAC) is never actually bound to the shop value the handler acts on.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed string: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `to_signable_string` (the body) only: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately forwards `request.shop` — an unverified header value — as the tenant identity to the handler: [4](#0-3) 

The identity-binding equality that should hold is: `shop authenticated by the HMAC == shop the handler acts on`. Because the HMAC covers only `@raw_body`, this equality is never true — the `shop` header can be swapped for an arbitrary value while keeping a valid `(body, hmac)` pair, and `HmacValidator.validate` will still return `true`.

### Impact Explanation
Any party who can obtain one legitimate `(raw_body, hmac)` pair for a given topic — trivially available to any developer/merchant with their own store and app installation, since Shopify sends real webhooks to any registered endpoint — can replay that exact body/HMAC combination to the target app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a different (victim) shop's domain. `Registry.process` will validate the HMAC successfully (it only checks the body) and hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop. Any host application that uses `data.shop` from `WebhookMetadata` to route, attribute, or persist per-tenant data (a standard and expected usage pattern per this gem's `Webhooks::Request`/`Registry` API) will process/store attacker-supplied content under another tenant's identity — a cross-tenant data integrity/confusion issue.

### Likelihood Explanation
Exploitation requires no credentials, access tokens, or `client_secret` from the app — only a body/HMAC pair, which is easy for any unprivileged party with any Shopify store (including a free development store) to legitimately obtain from their own webhook deliveries, then replay directly against the target app's public webhook endpoint with a forged shop header.

### Recommendation
- Include the `shop-domain` (and ideally `topic`, `api_version`, `webhook-id`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the verified payload, so any header value used for tenant identification cannot be altered independently of the signature.
- At minimum, document (or enforce) that consuming applications must cross-check `request.shop` against a known/registered shop for the corresponding webhook subscription before trusting it for tenant-scoped operations, since the gem currently allows the header to pass validation unchecked.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` with the target app installed; app registers a webhook (e.g., `orders/create`).
2. Shopify sends a legitimate webhook: `raw_body = B`, `X-Shopify-Hmac-Sha256 = HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`. Attacker captures this exact triple.
3. Attacker POSTs to the same app's webhook endpoint reusing `raw_body = B` and the same `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `@raw_body` (`Request#to_signable_string`) — validation succeeds.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled data as though it originated from `victim-shop.myshopify.com`.
