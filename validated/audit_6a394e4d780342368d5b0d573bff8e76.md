### Title
`updateConnection` silently expands an origin's exposed asset scope by setting `connectedAssetName` without validating it against the origin's consented `assetNames` - (File: features/connected-origins/module/connections.js)

### Summary
`updateConnection` unconditionally writes any supplied `connectedAssetName` into a trusted origin's record via `#setAttributes`, with no check that the asset is already part of the origin's consented `assetNames` set. Since `getConnectedAccounts` includes `value.connectedAssetName` in the list of asset addresses returned regardless of `assetNames` membership, this allows the exposed-address scope for an already-connected origin to grow without a fresh `add()`/consent flow.

### Finding Description
`updateConnection` builds an `attributes` object and passes any truthy `connectedAssetName` straight through to `#setAttributes`, with no membership check against the existing `value.assetNames`: [1](#0-0) 

`#setAttributes` then merges these attributes into the stored connection record unconditionally: [2](#0-1) 

`getConnectedAccounts` computes the exposed `assetNames` for an origin as `[value.connectedAssetName, ...(value.assetNames ?? [])]` — i.e., `connectedAssetName` is always included in the exposed set even if it is absent from `assetNames`: [3](#0-2) 

Contrast this with `add()`, which is the consent-granting path: it always unions `connectedAssetName` into `allConnectedAssetNames`/`assetNames` as part of an explicit consent operation: [4](#0-3) 

So while `add()` is the sanctioned way to grow asset scope (and does so consistently by keeping `assetNames` and `connectedAssetName` in sync), `updateConnection` can set `connectedAssetName` to any value independently of `assetNames`, and `getConnectedAccounts` trusts `connectedAssetName` as an implicit grant. This breaks the invariant that asset exposure should only grow through explicit consent.

### Impact Explanation
If a call path exists where `updateConnection` is invoked with a `connectedAssetName` value influenced by the origin (e.g., a "switch active asset/chain" style interaction) but that value is not cross-checked against previously consented `assetNames`, the origin would gain visibility into an address of an asset it was never granted — an unauthorized address-disclosure impact scoped to a single already-trusted origin.

### Likelihood Explanation
The precondition is narrow: exploitation requires (1) the origin already being trusted with a limited `assetNames` set from a prior `add()`, and (2) some caller invoking `updateConnection` with a `connectedAssetName` value that is not validated against the origin's `assetNames`. I traced `updateConnection` to its exposure on the internal `connectedOriginsApi`: [5](#0-4) 
but I could not find, within the indexed code, a background/RPC handler that maps an untrusted dapp-originated request (e.g., a wallet_switchEthereumChain-style call) directly and solely to `updateConnection` with attacker-supplied `connectedAssetName`. The chain-switching documentation suggests chain switches are scoped per-origin and don't require re-prompting, but it's unclear from available code whether that flow calls `updateConnection` or `add` (which does keep `assetNames` consistent). This attacker-reachability link is unconfirmed with the tools available; due to index size limits some background/provider RPC dispatch files may not be fully indexed. What is confirmed is a code-level logic defect in `connections.js` itself: the function does not enforce the invariant regardless of caller.

### Recommendation
In `updateConnection`, validate that `connectedAssetName` is already present in `value.assetNames` before setting it as an attribute, or require it to also be added to `assetNames` (mirroring `add()`'s union logic) so that any change goes through the same consent-tracking path. Alternatively, have `getConnectedAccounts` intersect `connectedAssetName` with `assetNames` before including it in the exposed asset list, so an inconsistent `connectedAssetName` can never expose an unconsented asset address.

### Proof of Concept
Integration test in `features/connected-origins/module/__tests__/connections.test.js`:
1. `connectedOrigins.add({ origin: 'exodus.com', name: 'Exodus', icon: 'exodus_icon', connectedAssetName: 'solana', assetNames: ['solana'], trusted: true })`.
2. `connectedOrigins.updateConnection({ origin: 'exodus.com', connectedAssetName: 'bitcoin' })`.
3. `const accounts = await connectedOrigins.getConnectedAccounts({ origin: 'exodus.com' })`.
4. Assert: today's behavior returns `bitcoin` addresses in `accounts[*].addresses` even though `bitcoin` was never in the original `assetNames`; the expected/fixed behavior should assert `accounts[*].addresses` contains no `bitcoin` key unless a fresh `add()` call included it in `assetNames`.

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }

  updateConnection = async ({ origin, icon, connectedAssetName }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const attributes = {}

    if (icon) {
      attributes.icon = icon
    }

    if (connectedAssetName) {
      attributes.connectedAssetName = connectedAssetName
    }

    await this.#setAttributes({ origin, attributes })
