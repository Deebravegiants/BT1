### Title
Stranded relay/protocol fees in `ExternalActionSwap` become drainable via unlimited router approval + attacker-controlled swap calldata - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
When a user self-relays (`circomData.relay == address(0)`, a path explicitly allowed by `HinkalHelper.performHinkalChecks`), `ExternalActionSwap.swap` still computes `relayFee`/`hinkalFee` and subtracts them from the amount sent to Hinkal, but `Transferer.sendToRelay` silently no-ops when `relay == address(0)`, so those fee tokens are permanently stranded inside the `ExternalActionSwap` contract instead of being paid out or returned. Because `callRouter` grants the fixed LI.FI `router` an *unlimited* ERC20 allowance (`approveUnlimited`) and measures `swappedAmount` purely as a balance delta around an attacker-supplied `externalActionMetadata` call, any subsequent caller can craft router calldata that pulls more of `inputToken` than the `inputAmount` Hinkal actually sent for that transaction (up to the full standing balance, including the stranded fee residue), inflating `swappedAmount` and therefore the UTXO amount minted to the attacker's own stealth address.

### Finding Description
The broken equality: tokens actually leaving the `ExternalActionSwap` action to a party outside Hinkal's accounting in one transaction should equal `-deltaAmountChanges` that Hinkal sent it for that transaction. In practice:

1. `_internalTransact`/`_externalTransact` in `contracts/Hinkal.sol` compute `deltaAmountChanges[i]` and transfer exactly `-deltaAmountChanges[i]` of `inputToken` to the action before calling `runAction`, per `contracts/Hinkal.sol:244-260`.
2. `ExternalActionSwap.swap` (`contracts/external-actions/swaps/ExternalActionSwap.sol:40-102`) derives `inputAmount` from `deltaAmounts[0]`, then calls `callRouter(inputToken, inputAmount, outputToken, circomData.externalActionData.externalActionMetadata)`.
3. `LifiExternalAction.callRouter` (`contracts/external-actions/swaps/LifiExternalAction.sol:16-36`) does:
   - `approveUnlimited(inputToken, router)` — grants the LI.FI router `type(uint256).max` allowance over the *entire* contract balance of `inputToken`, not just `inputAmount`.
   - `router.call(externalActionMetadata)` — `externalActionMetadata` is fully attacker-controlled calldata (`circomData.externalActionData.externalActionMetadata`), never validated to only consume `inputAmount`.
   - `swappedAmount = balanceAfter - balanceBefore`, a delta measured only around this call.
4. Because the router (msg.sender = the action contract) has unlimited allowance, and the attacker chooses the exact bytes sent to the router, the attacker can encode a "fromAmount" in the LI.FI calldata larger than `inputAmount`, causing the router to pull additional standing `inputToken` balance out of the action contract via that pre-existing allowance. The extra tokens produce a larger `swappedAmount`, feeding into `amountToSendToHinkal = swappedAmount - totalFee`, which is sent to `msg.sender` (Hinkal) and turned into an on-chain UTXO for `circomData.stealthAddressStructure` — the attacker's own address.
5. A ready source of that "free" standing balance is the fee-stranding bug itself: in `swap()` (`contracts/external-actions/swaps/ExternalActionSwap.sol:70-93`), `relayFee`/`hinkalFee` are always subtracted into `totalFee`, but `sendToRelay(circomData.relay, ...)` (`contracts/Transferer.sol:178-190`) is a no-op whenever `relay == address(0)`. Since `HinkalHelper.performHinkalChecks` (`contracts/HinkalHelper.sol:213-219`) explicitly permits `relay == address(0)` (self-relay), every self-relayed swap silently leaves `relayFee + hinkalFee` worth of `outputToken`/`feeToken` sitting in the `ExternalActionSwap` contract forever — a residual balance that accumulates across transactions and is exactly the "free" balance an attacker can later pull via the router-approval path above.
6. Hinkal's balance-equality check (`contracts/Hinkal.sol:137-146`, `balanceDif == amountChanges[i] + utxoAmount` for on-chain-created commitments, which external-action outputs must be) does not catch this: it only verifies that Hinkal's own balance change matches the on-chain UTXO amount reported by the action — both of which move together when the action inflates its output using the stranded/standing balance. The circuit's `inTotal + amountChanges === outTotal` constraint governs off-chain UTXOs bound to the user's declared `amountChanges`, but the swap action's on-chain-created output UTXO amount is not derived from `amountChanges` at all — it is derived from `callRouter`'s balance delta, which the attacker can inflate.

### Impact Explanation
An unprivileged attacker can capture value that never belonged to their deposit: (a) protocol/relay fees stranded by every self-relayed swap (`relay == address(0)`), and (b) any other standing/stranded balance of a token held by the `ExternalActionSwap` contract (dust, rounding remainders, or fees from other users' self-relayed swaps). This is repeatable every time residual balance accumulates and matches "High: theft or permanent freezing of protocol/relay fees" at minimum; if the drained balance originates from another user's in-flight funds parked in the action (e.g., between a deposit and the router call within the same block, or leftover from a partially-processed multi-hop action), it escalates to "Critical: direct theft of shielded or in-flight user funds."

### Likelihood Explanation
Preconditions: (1) at least one self-relayed swap (`relay == address(0)`) must have occurred, which is a normal, sanctioned usage path (not privileged) per `performHinkalChecks`, so residual balance accrual is expected to happen naturally over time; (2) the attacker needs to construct their own valid Hinkal deposit/UTXO and generate their own proof (fully within an unprivileged attacker's capability), and craft `externalActionMetadata` bytes recognized by the fixed LI.FI router that request pulling more than `inputAmount` of `inputToken` — feasible given LI.FI's generic-swap/bridge calldata formats accept an explicit "amount" field independent of what Hinkal believes it sent. Cost is a single transaction; the attack is repeatable each time new residual balance accumulates.

### Recommendation
- Do not skip fee accounting when `relay == address(0)`: either refund `relayFee`/`hinkalFee` to the swap output when there is no relay to pay, or require `flatFee == 0` when `relay == address(0)` and route `hinkalFee` to a protocol treasury address unconditionally instead of gating it behind `sendToRelay`'s `relay != address(0)` check.
- Replace `approveUnlimited` with an exact, per-call approval equal to `inputAmount` (approve `0` then `inputAmount`, reset to `0` after the call) so the router can never pull more than what Hinkal actually sent for that transaction.
- In `callRouter`, additionally assert that the router did not consume more than `inputAmount` of `inputToken` (compare balance before/after on the input side too), independent of the approval fix, to defend in depth.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper` (with a real/whitelisted relay), `LifiExternalAction` pointed at a mock LI.FI-style router, and a standard ERC20 mock for `feeToken`/`outputToken`.
2. Execute a legitimate self-relayed swap transaction (`relay == address(0)`, `originalSender == msg.sender`) with non-zero `feeStructure.flatFee` and `variableRate`, and confirm via `outputToken.balanceOf(externalActionSwap)` that `relayFee + hinkalFee` remains stuck in the action contract after the transaction (assert `balanceOf(action) == relayFee + hinkalFee`, i.e., `sendToRelay` no-op).
3. As a second, unrelated attacker EOA, submit a new Hinkal transaction whose external action is the same swap, with `inputToken == outputToken` from step 2 (or any token where the action holds a standing balance), and craft `externalActionMetadata` for the mock router to call `transferFrom(action, router, inputAmount + strandedResidual)` (simulating a LI.FI calldata that specifies a larger `fromAmount` than Hinkal's `-deltaAmounts[0]`), then mint back `swappedOutput` proportional to the larger input to the action contract.
4. Assert: `amountToSendToHinkal` (and hence the attacker's minted on-chain UTXO amount) is strictly greater than `-deltaAmounts[0]` minus fees that correspond to the attacker's own declared deposit — i.e., `tokens_leaving_action_this_tx != -deltaAmountChanges_this_tx`, proving the equality is broken and the attacker captured the residual `relayFee + hinkalFee` from step 2 into their own UTXO.
