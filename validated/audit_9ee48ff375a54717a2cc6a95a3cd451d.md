### Title
Webhook `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are trusted despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from unauthenticated HTTP headers, while the HMAC signature that `Registry.process` validates only covers the raw request body. Any valid `(body, hmac)` pair can be replayed with a different `shop-domain`/`topic` header and will still pass validation, letting an attacker attribute a legitimate webhook payload to a different tenant or topic than the one it was actually issued for.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are not part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` gates on this same HMAC check and then unconditionally trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This breaks the intended identity binding: `hmac == HMAC(secret, body)` should imply `body` (and everything acted upon) originated from Shopify for the claimed `shop`/`topic`, but in reality `hmac` only binds `body`. The equality the code relies on is:

`valid_hmac(body) == true` ⇒ `(shop, topic, webhook_id, api_version)` are authentic

when the actual guarantee provided is only:

`valid_hmac(body) == true` ⇒ `body` is authentic for *some* shop/topic that once produced it.

Because `shop`/`topic` are parsed from bytes that were never verified, a previously-observed valid `(body, hmac)` pair (e.g. from a webhook the attacker legitimately received for their own shop, or any publicly-guessable/generic body) can be resent with an arbitrary `x-shopify-shop-domain` and/or `x-shopify-topic` header and will still satisfy `Utils::HmacValidator.validate`.

### Impact Explanation
This is a cross-tenant confusion vector: the host application's webhook handler receives `WebhookMetadata#shop` believing it has been authenticated by Shopify's HMAC, and typically uses it directly to look up/act on a specific merchant's data (per the documented handler contract in `docs/usage/webhooks.md`). An attacker able to obtain one valid signed webhook (from their own installed instance of the app, or any leaked/predictable body) can replay it while relabeling it as belonging to a different `shop` or a different `topic` (e.g., turning a benign webhook body into a spoofed `app/uninstalled` or other sensitive topic event for an arbitrary shop domain), causing the app to process actions against the wrong tenant. This matches the "cross-tenant access" Critical impact category, since the gem provides no binding between the authenticated bytes and the shop/topic values it hands to the app.

### Likelihood Explanation
Exploitation requires possession of at least one valid `(body, hmac)` pair, which is achievable by any user who has legitimately installed the app on their own store (a normal, unprivileged action) and observed one webhook delivery, or by using a body value that is constant/predictable across shops (many webhook payloads for a given topic have highly structured/guessable JSON). No access to `api_secret_key`, tokens, or any elevated privilege is required — only sending a crafted HTTP POST to the app's public webhook endpoint with substituted headers.

### Recommendation
Include the shop domain, topic, webhook id, and API version in the value that is HMAC-verified (or otherwise cryptographically bind them to the body/signature), rather than trusting header values that sit outside the signed payload. At minimum, `Request#to_signable_string` should incorporate these header fields so `HmacValidator.validate` fails if any of them are altered relative to what Shopify actually signed.

### Proof of Concept
1. Install the app on an attacker-controlled shop `attacker.myshopify.com` and capture one legitimate webhook Shopify sends, e.g. body `{}` with headers:
```
x-shopify-topic: some/topic
x-shopify-hmac-sha256: <valid-hmac-of-"{}">
x-shopify-shop-domain: attacker.myshopify.com
```
2. Replay the exact same body and `hmac-sha256` header, but swap `x-shopify-shop-domain` to `victim.myshopify.com` (and/or change `x-shopify-topic` to a different registered topic):
```ruby
headers = {
  "x-shopify-topic" => "some/other-registered-topic",
  "x-shopify-hmac-sha256" => captured_valid_hmac, # unchanged
  "x-shopify-shop-domain" => "victim.myshopify.com",
}
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: headers)
)
```
3. `Utils::HmacValidator.validate` still passes (it only re-derives the HMAC of `"{}"`), and `Registry.process` invokes the registered handler with `WebhookMetadata.shop == "victim.myshopify.com"`, even though Shopify never issued a webhook for `victim.myshopify.com` with this content, as shown by the test setup which only signs the body and freely varies the headers: [5](#0-4) .
