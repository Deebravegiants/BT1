### Title
Batch withdrawal status/txHash misreport for same-asset PoA withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain outcome of a specific withdrawal by matching purely on `assetId`, discarding the `index` that `createWithdrawalIdentifiers` assigns to disambiguate multiple withdrawals of the same asset inside one NEAR transaction. When a caller batches two or more PoA-bridge withdrawals of the same token in a single transaction (e.g., same token to two different destination addresses/amounts), both `WithdrawalIdentifier`s collapse onto the same matched record, so the integrator/watcher can receive the wrong `txHash`/status for one of the withdrawals.

### Finding Description
`createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` assigns a per-bridge sequential `index` to each `WithdrawalParams` in a batch so that a bridge can later distinguish which specific withdrawal a status query refers to: [1](#0-0) 

`PoaBridge.createWithdrawalIdentifier` builds the `WithdrawalIdentifier` but never stores or uses that `index` for matching (only `landingChain`, `withdrawalParams`, `tx` are kept): [2](#0-1) 

`describeWithdrawal` then calls `findMatchingWithdrawal`, which selects the first API-returned withdrawal whose `near_token_id` matches `assetId` — with no use of `index` or amount to disambiguate: [3](#0-2) [4](#0-3) 

The code's own comment acknowledges this limitation explicitly: *"multiple withdrawals of the same token in a single transaction are not supported."* But the SDK layer does not reject or prevent this case — `createWithdrawalIntents`/`createWithdrawalIdentifiers` happily process a batch containing two same-asset PoA withdrawals with different `destinationAddress`/`amount`, assigning them distinct indexes that are then silently dropped.

The equality broken: **the withdrawal status/txHash reported for identifier N** should equal **the actual on-chain outcome of withdrawal N**, but because matching ignores `index`, identifier 0 and identifier 1 (for the same asset) both resolve to whichever single API record matches first — so at least one of them is reported with a `status`/`txHash` belonging to a different withdrawal (different destination address and/or amount).

### Impact Explanation
`watchWithdrawal` in `withdrawal-watcher.ts` treats a `completed` status with a `txHash` as authoritative proof of settlement for that specific withdrawal identifier: [5](#0-4) 

An integrator building on `waitForWithdrawalCompletion`/batch APIs that credits or finalizes a payout per withdrawal identifier based on this status can therefore mark a withdrawal to address B as "completed with txHash X" when X actually corresponds to the transfer sent to address A (or vice versa) — a status/hash misreport that can cause the integrator to credit or refund the wrong leg twice, or fail to detect that one of the two withdrawals is still pending/failed. This matches the "High" impact category (status/hash misreport causing double credit or refund).

### Likelihood Explanation
This requires: (1) a caller/integrator building a NEAR transaction with two or more withdrawal intents for the *same* `assetId` routed through the PoA bridge (no explicit SDK-level check blocks this), and (2) the PoA bridge's off-chain status API returning multiple `COMPLETED`/`PENDING`/failure records for that transaction. The SDK's batching path (`createWithdrawalIdentifiers`) does not reject same-asset duplicates, so the precondition is reachable purely through normal SDK usage/integration patterns without any malicious relayer, RPC, or bridge-operator behavior — it only requires an unprivileged caller to submit such a batch. This is a realistic integration scenario (e.g., a user withdrawing the same token to two different destinations in one signed batch), making likelihood moderate.

### Recommendation
Have `findMatchingWithdrawal` disambiguate by `index` in addition to `assetId` (e.g., sort matching candidates deterministically — by amount or order returned — and pick the `index`-th match), or reject/guard batches containing multiple same-asset PoA withdrawals at the SDK layer until the POA API and matching logic support unambiguous per-withdrawal correlation (e.g., a stable order key or the withdrawal's specific destination/amount used to disambiguate ties).

### Proof of Concept
1. Caller constructs a batch of two `WithdrawalParams` for the same `assetId` (e.g., `nep141:usdc.omft.near`), one to `destinationAddress: A` and another to `destinationAddress: B`, both routed to `PoaBridge`.
2. `createWithdrawalIdentifiers` assigns `index: 0` to the first and `index: 1` to the second, both sharing the same NEAR `tx.hash`.
3. The batched NEAR transaction executes; the POA bridge processes two withdrawals for the same `near_token_id`, returning two distinct records (different `transfer_tx_hash`, `address`, `amount`) for the same `withdrawal_hash`.
4. Calling `describeWithdrawal` for identifier with `index: 1` still uses only `assetId` to match via `findMatchingWithdrawal`, which returns `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)` — the *first* matching record in API response order, regardless of which `index` was requested.
5. Both `watchWithdrawal` calls (for `index: 0` and `index: 1`) can resolve to the same `txHash`/status, so the integrator attributes the outcome of one withdrawal to both, misreporting completion for the withdrawal that actually corresponds to a different `transfer_tx_hash`.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
