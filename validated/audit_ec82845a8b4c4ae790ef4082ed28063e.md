### Title
Predictable, unsigned session identifier used as session cookie enables session fixation / hijacking for non-embedded apps - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` stores the plaintext `Session#id` as the value of the `shopify_app_session` cookie. That id is not a random opaque token — it is deterministically derived from public/guessable data (`"#{shop}_#{associated_user.id}"` for online sessions, `"offline_#{shop}"` for offline sessions). `ShopifyAPI::Utils::SessionUtils.current_session_id` later trusts this raw cookie value as the key to look up a stored session (and its access token) with no cryptographic binding proving the presenter ever completed OAuth.

### Finding Description
The identity binding that should hold is:

`cookie_session_id(cookies) == id of the session the *presenting browser* legitimately obtained via OAuth`

Instead what is actually checked is only:

`cookie_session_id(cookies) == <a fully predictable string>`

Session ids are generated in `Session.from`: [1](#0-0) 

This id is written directly into the browser cookie for non-embedded apps in `validate_auth_callback`: [2](#0-1) 

And the cookie's raw value is later trusted verbatim as the lookup key for restoring the merchant session, with no signature or MAC check: [3](#0-2) [4](#0-3) 

The `SessionCookie` struct itself carries only a plain `value: String` with no HMAC or signature field: [5](#0-4) 

Because `shop` (myshopify domain) is public and `associated_user.id` is a small, often sequential Shopify user id (frequently observable via other public/app surfaces, e.g. storefront/customer APIs or simply enumerable for early users), an attacker can construct the exact string `"<shop>.myshopify.com_<user_id>"` (or `"offline_<shop>.myshopify.com"`) without ever touching the target's browser or credentials.

### Impact Explanation
If a host application built on this gem stores sessions server-side keyed by `Session#id` and relies on `SessionUtils.current_session_id`/the `shopify_app_session` cookie to restore the active session (as documented for non-embedded flows), an attacker who sets `Cookie: shopify_app_session=<guessed-id>` on a request will have the application load and act as the victim merchant's already-established session — including its stored `access_token` — with no proof of possession of that session by the requester. This is a session fixation / hijacking primitive that can result in unauthorized access to a merchant's authenticated session and its access token, matching the "session fixation or forced OAuth completion" High-severity category.

### Likelihood Explanation
Exploitability depends on (a) the attacker knowing/guessing a valid `shop` domain (public), (b) knowing/guessing the online session's associated Shopify user id (often low-entropy/sequential and frequently disclosed elsewhere), and (c) the victim's session still existing in the host app's session store. No access token, secret, or privileged credential is required from the attacker — only the ability to send a request with a crafted cookie value, satisfying the "unprivileged internet user" bar. The likelihood is somewhat reduced by needing to guess the numeric user id for online sessions, but for offline sessions the id is fully deterministic (`"offline_#{shop}"`) with no unknown component at all.

### Recommendation
- Never expose the internal session-store key (`Session#id`) directly as a cookie value. Generate a separate, cryptographically random, unguessable session cookie value (e.g., `SecureRandom.uuid`/`SecureRandom.hex(32)`) that is unrelated to `shop`/user id, and map it to the internal session id server-side.
- Alternatively, HMAC-sign the cookie value with `Context.api_secret_key` and verify the signature in `SessionUtils.cookie_session_id` before trusting it, similar to `Utils::HmacValidator`.
- Rotate/regenerate the session cookie value on every successful OAuth completion to prevent fixation even if an id were guessed beforehand.

### Proof of Concept
1. Victim merchant `shop.myshopify.com` installs the app; app completes OAuth and (per `Session.from`) creates a session with `id = "shop.myshopify.com_1234567"` (online) or `id = "offline_shop.myshopify.com"`, and `validate_auth_callback` sets cookie `shopify_app_session=shop.myshopify.com_1234567` in the victim's browser and the host app persists this session server-side.
2. Attacker, without ever interacting with the victim, sends a request to the same app with header:
   `Cookie: shopify_app_session=shop.myshopify.com_1234567`
   (for offline sessions, simply `Cookie: shopify_app_session=offline_shop.myshopify.com` — fully deterministic, no guessing required).
3. The app calls `SessionUtils.current_session_id(nil, cookies, online)` → `cookie_session_id(cookies)` returns the attacker-supplied value verbatim, which the host app uses to fetch the stored `Session` (including `access_token`) for `shop.myshopify.com`.
4. The attacker is now treated as an authenticated request context for the victim's shop, with access to the merchant's stored access token via the app's normal session-restoration flow.
