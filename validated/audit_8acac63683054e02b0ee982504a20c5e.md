### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw body, then trusts the unauthenticated `shop-domain` header (and `topic`/`webhook-id` headers) as the tenant identity passed to the app's handler. Any unprivileged user who can install the app on their own store can obtain a validly-signed `(body, hmac)` pair and replay it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header, breaking the binding between the cryptographically-authenticated payload and the shop identity the handler relies on.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: ` [1](#0-0) `. The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers that are never included in the signed string: ` [2](#0-1) `.

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and, if it passes, immediately constructs `WebhookMetadata` using `request.shop` (the unauthenticated header) and hands it to the app-supplied handler: ` [3](#0-2) `.

`Utils::HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string`, i.e., the raw body, and compares it to the `hmac` header: ` [4](#0-3) `. There is no mechanism anywhere in this codepath that binds the `shop-domain` header value to the signature or cross-checks it against a known/installed shop.

Because the gem uses a single shared `api_secret_key` (the app's client secret) for HMAC validation across *all* shops that installed the app (confirmed by `Context.api_secret_key` usage in `HmacValidator`), any store owner who installs the target app receives real webhook deliveries with a valid HMAC computed over their own body content. That attacker can then replay the same `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` forwards `shop: <attacker-chosen value>` to the handler as if it were an authenticated fact.

This exactly matches the audit's bug class of "a field acted on but not covered by the HMAC" — the `shop` field used to route/attribute the webhook is not part of the equality the HMAC actually proves. What is proven is `HMAC(body) == received_hmac`; what the app trusts is `shop_header == "the shop that generated this body"`, which is a different, unverified equality.

### Impact Explanation
An app that keys any tenant-scoped action off `WebhookMetadata#shop` (e.g., selecting which shop's session/data to update, as shown in the gem's own documented handler example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` in `docs/usage/webhooks.md:26`) can have attacker-controlled body content attributed to an arbitrary victim shop. This crosses the tenant boundary that the gem is supposed to protect via HMAC authentication, since the only cryptographic guarantee provided is body integrity for *some* holder of the shared app secret, not binding to the shop claimed in the header. This satisfies the "cross-tenant access" impact criterion.

### Likelihood Explanation
Likelihood is high for any app author following the gem's documented pattern of trusting `data.shop`: the attacker only needs to install the app on their own (attacker-controlled, freely creatable) development store to receive legitimately HMAC-signed webhook deliveries, then replay the captured request to the app's public callback path with a modified `shop-domain` header. No access token, `client_secret`, or privileged account is required — this is achievable by an ordinary unprivileged internet user who can register a store.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or independently verify `request.shop` against the app's own record of shops that have a registered webhook/session before trusting it, rather than passing the raw unauthenticated header straight into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify delivers a legitimate webhook (e.g. `orders/create`) to the app with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` — valid because `secret` (`api_secret_key`) is shared across all installs.
3. Attacker captures `B` and its valid HMAC, then POSTs to the app's webhook endpoint again, keeping `B` and the HMAC header identical but setting `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` and, if it trusts `data.shop` to scope database writes as the documentation's example suggests, injects attacker-controlled order data attributed to the victim's tenant.
