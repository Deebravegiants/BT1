## Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against that same raw body only. The `shop-domain` header, which is the value handed to app-defined webhook handlers as the tenant identifier, is never part of the signed material. An attacker who controls one legitimate shop installation of the app can capture a validly-signed webhook (body + HMAC, both computed with the app's shared `api_secret_key`) and replay the identical body/HMAC pair while substituting the `shop-domain` header for a victim shop, producing a request that still passes HMAC validation but attributes the payload to the wrong tenant.

### Finding Description
`Request#to_signable_string` only exposes `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the (unsigned) header: [2](#0-1) 

`HmacValidator.validate` computes/compares the signature purely over `verifiable_query.to_signable_string`, i.e. the body — never the headers: [3](#0-2) 

`Registry.process` checks only `Utils::HmacValidator.validate(request)` and then forwards `request.shop` (the unauthenticated header value) directly to the app-registered handler as the tenant identity: [4](#0-3) 

Because the `api_secret_key` is shared across every shop installed on a given app (it is not per-shop), any shop that has installed the app can generate arbitrary bodies with a valid HMAC for that shared secret (e.g. by triggering webhooks on their own store, or if the handler ever echoes attacker-influenced content into the body). The attacker can then take that valid `(raw_body, hmac)` pair and re-send it with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a victim shop's domain. `HmacValidator.validate` still succeeds because the HMAC never covered the shop header, and `Registry.process` will invoke the handler with `WebhookMetadata` carrying the forged `shop` value.

This breaks the intended binding: **HMAC-verified bytes = the bytes acted upon**. Here, `to_signable_string` (bytes verified) ≠ `request.shop` (bytes/field acted on by the handler), i.e. the shop field is acted on but not covered by the HMAC.

### Impact Explanation
Host applications rely on `WebhookMetadata#shop` (populated straight from `request.shop`) to determine which merchant/tenant a webhook event belongs to — used for looking up sessions, updating per-shop data, or performing shop-scoped side effects. An attacker able to forge this field can cause the app to process a webhook body under an arbitrary victim shop identity, which is a cross-tenant confusion: actions, data updates, or side effects intended for the attacker's own shop get attributed/misapplied to a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to control (or have installed) at least one shop on the target app so they can obtain a validly-HMAC-signed webhook body using the app's shared `api_secret_key`, and the ability to POST a crafted request with swapped headers to the app's public webhook endpoint (no elevated credentials needed beyond a normal, unprivileged app installation). This is a realistic scenario for any app installable by unprivileged/internet users, since the shared secret is identical for all tenants of the app.

### Recommendation
Include the shop domain (and other identity-bearing headers such as `topic`/`webhook-id` if they influence handler behavior) as part of the signable string used for HMAC verification, or independently verify that `request.shop` corresponds to a shop with an active, legitimate session/installation before dispatching to handlers. At minimum, `to_signable_string` should bind body and shop together so that swapping the header invalidates the signature.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; attacker triggers/receives a legitimate webhook for their own shop with body `B` and header `x-shopify-shop-domain: attacker-shop.myshopify.com`, plus a valid `x-shopify-hmac-sha256` computed by Shopify using the app's `api_secret_key` over `B`.
2. Attacker replays the same request to the app's webhook endpoint, keeping body `B` and the same HMAC header, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because validation only checks `to_signable_string` (`B`), unaffected by the header change: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the payload originated from and was signed via the attacker's own shop context.
