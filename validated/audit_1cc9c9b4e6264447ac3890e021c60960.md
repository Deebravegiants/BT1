### Title
Unchecked `copy_from_slice` on attacker-controlled `Message.from` panics `on_accept` for non-EVM sources - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler derives the dispatch origin for optional calldata execution from `message.from`, a dynamic `bytes` field decoded from the ABI-encoded cross-chain `Message` body. For non-EVM `source` state machines it copies `from_bytes` directly into a fixed `[u8; 32]` buffer with `copy_from_slice` without first checking the slice length, unlike every other length-sensitive conversion in the same file (the `to`-bytes beneficiary conversion and the `on_timeout` sender conversion both validate length and return an `Err` on mismatch).

### Finding Description
`message.from` originates from an ABI-decoded `Message.from` field, which is a Solidity `bytes` (dynamic array), not a fixed-size `address`/`bytes20`/`bytes32`. Any peer gateway contract that constructs this message — including a misconfigured, buggy, or (for permissionless deployments) attacker-controlled counterpart registered via `ContractToAsset` — can set `from` to any byte length. When `on_accept` processes such a PostRequest with `source.is_evm() == false`, non-empty `message.data`, and no `signature` in the decoded `SubstrateCalldata`, execution reaches:
```
let mut account = [0u8; 32];
account.copy_from_slice(from_bytes);
```
`copy_from_slice` panics unless `from_bytes.len() == 32` exactly. In a Substrate/Polkadot runtime executed as Wasm, a panic during extrinsic dispatch is not caught as a `Result::Err` — it triggers a Wasm trap, aborting execution of the block/extrinsic path in a way distinctly worse than a normal dispatch failure, mirroring the "wasm trap reachable from untrusted input" pattern the codebase has already fixed at other call sites (`StateMachine::from_str`, `as_utf8_string` deserializer, `resolve_consensus_state_id`).

### Impact Explanation
This is reachable by any relayer submitting a proof-backed PostRequest that a legitimate but externally-influenced source gateway encoded with a malformed `from` field — a token-bridge/mint-path message dispatch that any unprivileged party effectively triggers once tokens are minted before the panic occurs (the mint at lines 93-117 executes before the vulnerable calldata branch, so funds are already moved). The panic aborts message execution mid-flight, leaving the request undeliverable/unresolvable (the underlying category of "a route unable to deliver messages"), and can disrupt block execution for whichever node processes it, which is a Medium/High severity availability issue for the token-bridge and message-routing path.

### Likelihood Explanation
Likelihood is bounded by the requirement that `ContractToAsset` maps the `(source, from)` pair to a known asset — i.e. a peer gateway must already be registered for that pair. Given a registered peer whose encoding logic (or an attacker able to influence it, e.g. a compromised or arbitrary-length-permitting peer implementation) emits a non-32-byte `from` alongside non-empty `data` and no signature, the panic triggers deterministically and reproducibly on every relayed delivery attempt.

### Recommendation
Mirror the length validation already used for `message.to` (lines 63-71) and for `message.from` in `on_timeout` (lines 224-232): explicitly check `from_bytes.len() == 32` (and optionally accept 20-byte left-padding as in the `to` conversion) before calling `copy_from_slice`, returning `HftError::InvalidSenderLength`/`InvalidFromLength` on mismatch instead of panicking.

### Proof of Concept
1. Register a peer gateway for a non-EVM `source` state machine via `ContractToAsset`/`Precisions` as normal.
2. Have that peer (or an attacker able to shape its message body) dispatch a PostRequest whose ABI-encoded `Message` has `to` = a valid 20/32-byte recipient, `data` = a non-empty `SubstrateCalldata` with `signature: None`, and `from` set to any byte length other than 32 (e.g., 0, 1, or 21 bytes).
3. A relayer delivers the proven request to `pallet-ismp::handle_unsigned`/`handle`, which invokes `HyperFungibleToken::on_accept`.
4. Execution mints/transfers the amount successfully, then reaches the non-EVM `else` branch at module.rs:182-186 and panics on `copy_from_slice`, producing a runtime trap instead of a graceful `DispatchError`.
