### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating an HMAC that is computed **only over the raw request body**, yet the `shop` value that the app's handler subsequently treats as the tenant identity is taken from the `X-Shopify-Shop-Domain` header, which is never part of the signed material. This breaks the intended binding `hmac_verified_bytes == bytes_the_handler_trusts_for_tenant_identity`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively against `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` gates on that same HMAC check and then immediately hands the caller's own `request.shop` (parsed straight from the `shop-domain`/`x-shopify-shop-domain` header, not from the signed body) to the handler as the tenant identity: [3](#0-2) [4](#0-3) 

Because the header is parsed but never verified, an attacker who possesses one genuinely Shopify-signed webhook (trivially obtainable for their own shop — e.g. an unprivileged merchant that installs the app and triggers `orders/create` on their own store) can replay that exact body/HMAC pair directly to the app's public webhook endpoint while swapping only the `X-Shopify-Shop-Domain` header to a victim shop's domain. `HmacValidator.validate` still succeeds (the body and HMAC are untouched and genuinely signed with `Context.api_secret_key`), and `Registry.process` calls the handler with `shop: <victim-shop>` even though the payload actually originated from, and describes data belonging to, the attacker's shop.

This is exactly the "field acted on but not covered by the HMAC" analog: the shop identity used downstream (to key session lookups, per-tenant data writes, dedup, billing, etc., in the host application's handler) is disjoint from the identity actually authenticated by the signature.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to select which tenant's session/data to act on (the pattern documented for webhook handlers) can be made to attribute attacker-controlled, but otherwise validly-signed, webhook content to an arbitrary victim shop. Depending on the handler's logic this enables cross-tenant data injection/corruption or triggers side effects (state changes, external calls, notifications) scoped to a shop the attacker does not control — a cross-tenant boundary violation reachable by an unprivileged internet user with no access to the app's `client_secret` or any victim credential.

### Likelihood Explanation
Low-to-medium: exploitation requires the attacker to (a) be a legitimate app-installing merchant able to trigger and capture one authentic webhook delivery for their own shop, and (b) be able to reach the app's public webhook endpoint directly (a normal internet-exposed POST target) to replay it with a modified header. Both preconditions are attacker-controllable and require no privileged access to Shopify or the app's secrets, matching the "unprivileged internet user" threat model in scope.

### Recommendation
Bind the trusted shop identity to the HMAC-verified payload instead of the unauthenticated header: either include the `shop-domain` (and ideally `topic`/`webhook-id`) values in the signable string used by `HmacValidator`, or — since Shopify's own webhook HMAC scheme signs only the body — cross-check that the `shop` value in the parsed JSON body (most webhook payloads include shop/domain fields, or use a merchant-scoped webhook secret) matches the header before trusting it for tenant attribution in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger `orders/create` so Shopify delivers a webhook with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body.
2. Capture the raw request (`raw_body`, all headers).
3. Replay the exact same `raw_body` and `X-Shopify-Hmac-Sha256` directly to the app's public webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (which only checks `raw_body`) succeeds, `Registry.process` invokes the topic handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the handler to act on the victim tenant using attacker-supplied body content. [3](#0-2)
