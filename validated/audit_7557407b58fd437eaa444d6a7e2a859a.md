### Title
`CallDispatcher.dispatch()` has no caller/access control, allowing any address to trigger arbitrary calls against tokens or unlimited allowances left on the shared dispatcher - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch(bytes)` is `external` with no modifier restricting the caller [1](#0-0) . It is a single shared, statically-deployed contract referenced by `IntentGatewayV2` and by `HyperFungibleToken`/`WrappedHyperFungibleToken` (`_params.dispatcher` / `_dispatcher`) [2](#0-1) [3](#0-2) . Because `dispatch()` decodes an attacker-controlled `Call[]` and executes `to.call{value}(data)` for each entry with no restriction on `to`, `data`, or on who may invoke `dispatch` itself, any unprivileged external account (an order filler, an intent solver, or an unrelated third party) can call the dispatcher directly, outside of the gateway's own atomic flow, and reach whatever balance or ERC20 allowance the dispatcher currently holds.

### Finding Description
The intended usage pattern funds the dispatcher transiently and immediately sweeps its balance back to the calling gateway within the same transaction (`predispatch`/`postdispatch` flows in `IntentGatewayV2.sol` and `IntentsBase.sol::_execute`) [4](#0-3) . The protocol's own documentation flags that this design is only safe if approvals granted from the dispatcher during a `Call[]` are exact, "since the dispatcher contract holds tokens temporarily during execution" [5](#0-4) . The `testPostdispatchTokenSweep` test demonstrates order calldata explicitly granting `type(uint256).max` allowance from the dispatcher to a router before a swap [6](#0-5) . Because `dispatch()` itself has no access control, this shared, cross-app singleton contract is reachable directly by any address at any time, not only from within the atomic gateway flow that is supposed to bound its lifetime balance to zero. Any unlimited or unswept allowance/balance left on the dispatcher between transactions (e.g. from a differently-crafted order, a partially-completed sweep, or a spender address reused across unrelated orders) is a target any caller can act on by invoking `dispatch()` themselves with a `Call[]` that pulls those funds out — the same bug class as CVE-2017-6369's insufficiently-checked "system" entrypoint: a dangerous, generic execution primitive reachable without the intended privilege gate.

### Impact Explanation
If any balance or non-exact allowance is ever present on the dispatcher outside of the single atomic transaction that is supposed to zero it out, an unprivileged caller can steal it by calling `CallDispatcher.dispatch()` directly, since the function is not gated to the gateway contracts that are meant to be its only legitimate callers. This is concrete theft of escrowed/transient funds routed through intent fills or token-bridge calldata execution.

### Likelihood Explanation
Exploitability depends on funds or allowances actually persisting on the dispatcher between transactions, which the current gateway logic tries to avoid via same-transaction sweeps, but the protocol's own docs already acknowledge unlimited-allowance calldata as a live risk pattern that solvers/users can construct [7](#0-6) . Combined with the complete absence of a caller restriction on `dispatch()`, likelihood is elevated: no proof, no relayer/consensus step, and no privileged role is required — any address can call the dispatcher the instant such a balance/allowance exists.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a set of authorized caller gateways (e.g. an `onlyAuthorizedCaller` modifier checked against a registry, or deploy a dedicated dispatcher per gateway/order rather than one shared singleton), and/or enforce that dispatcher balances are verified to be zero for all relevant tokens at the end of every `dispatch()`-driven flow so no allowance or balance can outlive a single transaction.

### Proof of Concept
1. A user or solver submits an order whose `predispatch`/`postdispatch` calldata grants an unlimited ERC20 approval from the dispatcher to some contract, per the pattern shown in `testPostdispatchTokenSweep` [6](#0-5) .
2. If that approved spender ever becomes malicious/compromised, or if any token balance is left on the dispatcher due to a sweep gap, any external account calls `CallDispatcher(dispatcher).dispatch(...)` directly — a call the contract accepts from anyone since `dispatch()` has no caller check [8](#0-7)  — with a `Call[]` that transfers the residual balance/allowance to an attacker-controlled address.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
