### Title
Unchecked-length `copy_from_slice` on attacker-controlled cross-chain message field causes panic/DoS in `hyper-fungible-token` `on_accept` / `on_timeout` — (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The `hyper-fungible-token` pallet's `IsmpModule::on_accept` handler decodes an attacker-influenced ABI-encoded `Message` from a relayed `PostRequest.body` and, in the non-EVM-source calldata-execution branch, copies the arbitrary-length `message.from` bytes directly into a fixed `[u8; 32]` buffer without validating the length first, unlike the sibling branches in the same function which do check length (32 or 20 bytes) before copying.

### Finding Description
`on_accept` decodes the incoming cross-chain message with `Message::abi_decode(&body)` [1](#0-0) . When the message carries non-empty `data` and no signature, the code determines the calldata-executing origin. For an EVM source it correctly truncates to the last 20 bytes, but for the non-EVM (substrate) branch it does:

```
let mut account = [0u8; 32];
account.copy_from_slice(from_bytes);
account.into()
``` [2](#0-1) 

`from_bytes` comes from `message.from.as_ref()`, an ABI `bytes` field fully controlled by the sender contract on the source chain, with no length restriction enforced anywhere before this call. `copy_from_slice` panics if `from_bytes.len() != 32`. This mirrors exactly the bug class in the reference CVE (a fixed-size destination buffer written from an externally supplied, unchecked-length field), and it mirrors a pattern already fixed elsewhere in this same codebase — e.g. `as_utf8_string` in `modules/utils/serde/src/lib.rs` was explicitly hardened because unchecked `copy_from_slice` on attacker/RPC-controlled input previously crashed a production node worker [3](#0-2) , and `consensus_state_id_from_str` in the fisherman/tesseract code explicitly validates length before the fixed-array copy [4](#0-3) . The sibling branches within the very same function (`beneficiary_bytes`, `sender_bytes`) do perform the length check (`to_bytes.len() == 32`/`== 20`, else `Err(...)`) before copying [5](#0-4) [6](#0-5) , confirming that the substrate-calldata-origin branch at lines 176-186 is the one place this defensive check was omitted.

### Impact Explanation
`on_accept` is invoked by `pallet-ismp`'s dispatch/handler path whenever a relayed, proof-verified `PostRequest` targets a source contract registered in `ContractToAsset` for this pallet. Any account that can get a message routed to a registered source contract (a legitimate cross-chain token transfer with attached calldata and no signature, sourced from/attributed to a non-EVM chain) can set `message.from` to any length other than 32 bytes, causing an unhandled panic inside pallet logic executed during block/extrinsic processing. In a Substrate runtime, a panic inside `on_accept` invoked from `handle_unsigned`/dispatch aborts the runtime execution for that call, and since `on_accept` runs as part of the message-delivery pathway inside deterministic on-chain execution, this can halt processing of that message batch — a reachable "route unable to deliver messages" / DoS condition triggered by a single relayed request, not merely a resource-only bug.

### Likelihood Explanation
The precondition is low-cost for an attacker: they need a valid state/consensus proof for a `PostRequest` (something any permissionless relayer can already produce for legitimate traffic) targeting a contract mapped in `ContractToAsset`, with `message.data` non-empty, `substrate_data.signature == None`, and `message.from` of a length other than 32 bytes. All of these are attacker-chosen fields in the ABI-encoded payload; no privileged role is required. This is realistically triggerable by any user who can originate a cross-chain post request through a registered bridge contract.

### Recommendation
Add the same length validation used elsewhere in this function before the fixed-size copy:
```rust
let mut account = [0u8; 32];
if from_bytes.len() != 32 {
    Err(HftError::InvalidSenderLength(from_bytes.len()))?
}
account.copy_from_slice(from_bytes);
account.into()
```
Apply the identical fix to any other unchecked `copy_from_slice` call reachable from this decode path.

### Proof of Concept
1. Register a source EVM (or non-EVM) contract address in `ContractToAsset` for some asset (normal pallet configuration).
2. Construct a `PostRequest` whose `body` ABI-encodes a `Message` where:
   - `to`/`amount` are any valid values (to pass earlier checks),
   - `data` is non-empty and decodes to a `SubstrateCalldata` with `signature = None`,
   - `from` is set to a byte string of length ≠ 32 (e.g., 5 bytes), while `source.is_evm()` is `false`.
3. Relay this request with a valid consensus/state proof through the normal ISMP delivery path so that `pallet-ismp` invokes `Pallet::<T>::on_accept`.
4. Execution reaches the substrate branch at `module.rs:183-185`, calls `account.copy_from_slice(from_bytes)` with mismatched lengths, and panics, aborting execution of the call/block.
