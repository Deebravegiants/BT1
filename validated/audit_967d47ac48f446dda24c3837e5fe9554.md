### Title
Arbitrary `flash_position` receiver can smuggle unauthorized token calls into the caller's signed authorization tree - (`contracts/controller/src/strategies/flash_position.rs`)

### Summary
`flash_position` authenticates `caller` and then invokes a caller-selected contract address as the flash receiver. [1](#0-0)  The receiver validation only requires a Wasm contract and excludes the controller and pool; it does not restrict the receiver to trusted or governance-approved contracts. [2](#0-1)  A malicious receiver can therefore place additional calls requiring the caller's authorization inside the callback, causing simulation to include them beneath the `flash_position` authorization tree. [3](#0-2) 

### Finding Description
The vulnerable path is `controller::flash_position(caller, account_id, spoke_id, mode, debt, amount, receiver, data, collaterals, refund_assets)`. [4](#0-3)  `receiver` is untrusted input supplied in the call and is reached through `invoke_receiver`, which invokes `execute_flash_position` on that exact address. [5](#0-4) 

Because `caller.require_auth()` authorizes the enclosing invocation tree, a crafted receiver can append a nested call such as `token.transfer(caller, attacker, victim_balance)` and have simulation report it as a child authorization. [1](#0-0)  The settlement code requires declared positive collateral receipts, but a funded malicious receiver can satisfy that check from its own balance so the enclosing transaction succeeds. [6](#0-5) 

### Impact Explanation
If a victim signs the simulated authorization tree without noticing the added nested transfer, the malicious receiver can move unrelated tokens out of the victim's wallet while the flash-position transaction still completes normally. [7](#0-6)  This is theft of user funds beyond the flash-borrowed amount and declared collateral flow. [6](#0-5) 

### Likelihood Explanation
Exploitation requires inducing the victim to submit a `flash_position` call naming the malicious receiver and to sign the resulting poisoned authorization tree. [1](#0-0)  The attacker does not need a privileged role, leaked key, contract upgrade, or control of governance because `receiver` is an ordinary call argument. [2](#0-1)  The signer interaction and need for a successful receiver callback make this Medium rather than Critical or High. [8](#0-7) 

### Recommendation
Do not invoke arbitrary caller-supplied contracts under the caller's account-level authorization. [9](#0-8)  Restrict `receiver` to a governance-approved receiver registry, or redesign the flow so collateral delivery and strategy execution do not require a callback into untrusted code. [5](#0-4)  Until the contract boundary changes, wallets and integrators should reject any authorization tree containing calls beyond the expected protocol/token operations. [3](#0-2) 

### Proof of Concept
1. Victim calls `flash_position` with `caller = victim`, `account_id = 0` for a new account, `mode = Multiply`, a flash-loan-enabled `debt` market, positive `amount`, attacker-controlled Wasm `receiver`, and at least one positive collateral minimum. [10](#0-9) 
2. The controller authenticates `victim`, verifies only that `receiver` is Wasm and is not the controller or pool, then calls `receiver.execute_flash_position`. [11](#0-10) 
3. The malicious receiver calls `victim_token.transfer(victim, attacker, victim_balance)` and also transfers enough declared collateral from its own balance to the controller. [7](#0-6) 
4. Simulation attaches the malicious token transfer to the victim's `flash_position` authorization tree, and the victim signs it. [1](#0-0) 
5. The callback's measured collateral receipt satisfies the declared minimum, the position remains open and solvent, and the unauthorized wallet transfer remains part of the successful transaction. [12](#0-11)
