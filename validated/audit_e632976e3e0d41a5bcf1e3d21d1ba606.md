### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted by the handler dispatch but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches to the app's handler using the `topic`, `shop`, and `webhook_id` values taken from HTTP headers that are never included in the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `topic`, `shop`, `webhook_id`, and `api_version` are read directly from HTTP headers, unauthenticated by any signature: [2](#0-1) 

`Registry.process` validates only the HMAC of the body and then dispatches the handler using the unauthenticated `request.topic` and `request.shop`: [3](#0-2) 

The HMAC computation itself only ever covers `verifiable_query.to_signable_string`, i.e., the raw body for webhooks: [4](#0-3) 

The documented contract for handlers explicitly tells app developers to trust `data.shop` as "The shop domain of the webhook" and to use it for shop-scoped dispatch (e.g. `shop_domain: data.shop`): [5](#0-4) 

This breaks the intended binding: `HMAC(body, api_secret_key) == received_hmac` should imply `(topic, shop, body)` collectively originated from Shopify for that specific shop, but the gem only proves `body` is authentic — `shop` and `topic` are not bound to the signature at all. Because the app's `api_secret_key` is identical for every shop/tenant using the same Shopify app, any merchant who installs the app (an unprivileged action available to any internet user who can install a public/dev app) receives legitimately HMAC-signed webhook deliveries for their own shop and topic. That attacker can capture one such `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `shop-domain` and/or `topic` headers to impersonate a different (victim) shop or a different topic, since neither is covered by the signature check.

### Impact Explanation
This is a cross-tenant identity-binding failure at the webhook layer: `Registry.process` will accept a body+HMAC pair from the attacker's own shop but hand it to the handler labeled as if it came from an arbitrary victim shop/topic supplied via unauthenticated headers, since `Utils::HmacValidator.validate` never inspects `shop` or `topic`. Any host application that follows the gem's documented API and keys per-shop side effects off `data.shop` (exactly as shown in the gem's own documentation example, `shop_domain: data.shop`) can be made to process attacker-controlled body content under a victim shop's identity — a cross-tenant access primitive. This matches the Critical class of "cross-tenant access."

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on their own shop (a normal, unprivileged capability for public/dev Shopify apps) to obtain one valid `(raw_body, hmac)` pair, and then send an HTTP POST to the app's public webhook endpoint with forged `x-shopify-shop-domain` / `x-shopify-topic` headers alongside the captured body/HMAC. No access token, `client_secret`, or privileged credential is needed. Likelihood is high for any app that trusts `data.shop`/`data.topic` as the gem's documentation instructs.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and any other header claimed to identify the webhook) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., derive an authenticated composite string from headers + body for signature verification) so `Utils::HmacValidator.validate` cannot pass unless all dispatch-relevant fields are authentic.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers webhook topic `orders/create`.
2. Shopify sends a legitimately-signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `api_secret_key`), `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker replays the exact same body `B` and HMAC header `H` to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different registered `x-shopify-topic`).
4. `Utils::HmacValidator.validate` in `Registry.process` recomputes the HMAC over `B` only, finds it matches `H`, and accepts the request.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, `topic: "orders/create"`, `body: B` — content the attacker fully controls (subject only to being valid JSON, since it originated from the attacker's own account), processed as if it belongs to the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
