### Title
Cross-workflow response cache poisoning/disclosure via untrusted `WorkflowOwner` field in HTTP Action responseCache - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The Gateway's HTTP Action `responseCache` deliberately scopes cached HTTP responses by `WorkflowOwner` (not `WorkflowID`), per the comment "keyed by a hash of the request (method, URL, headers, body, workflowOwner)" and confirmed by `TestRequestHash`, which asserts that requests with different `WorkflowID` produce the *same* hash while different `WorkflowOwner` produce different hashes. [1](#0-0) [2](#0-1)  The `OutboundHTTPRequest` that carries this `WorkflowOwner` value is parsed directly from a JSON-RPC message sent by a DON node, with the code's own comment acknowledging "all fields set on the request come from untrusted nodes." [3](#0-2) [4](#0-3) 

### Finding Description
The cache-scoping design in `responseCache.Fetch`/`Set` relies on `req.Hash()`, which the gateway calls without independently validating that the embedded `WorkflowOwner` corresponds to the actual authenticated owner of the workflow that produced the outbound-HTTP request. [5](#0-4) [6](#0-5)  The `makeOutgoingRequest` handler unmarshals the entire `OutboundHTTPRequest` (including whatever `WorkflowOwner`/cache settings fields it carries) straight from the node's message payload and forwards it into the shared, DON-wide `responseCache`. [7](#0-6) [8](#0-7)  Because the cache key mixes attacker-influenced request fields (URL/method/headers/body come from an untrusted workflow node per the code's own comment) with `WorkflowOwner` and nothing else uniquely tied to a verified tenant/workflow, a workflow that can control or predict these fields can either (a) read a cached response that another workflow-owner's action previously stored for a URL/method/headers/body combination if the attacker can spoof/collide the `WorkflowOwner` value, or (b) poison the shared cache entry for a URL that a victim workflow (same owner, different workflow) later calls, since `WorkflowID` is explicitly excluded from the hash. This is architecturally analogous to the podman flaw (GHSA-c3wv-qmjj-45r6), where per-request/per-container state (environment variables) leaked into a subsequent, differently-scoped instance because the isolation boundary used for caching/reuse was insufficiently granular and derived from data that should have been scoped more tightly.

### Impact Explanation
If exploited, a workflow could retrieve or influence a cached HTTP response body/headers (potentially containing another workflow's sensitive response data, e.g., tokens, PII, or business data returned from third-party HTTP APIs) that it did not itself request, purely because the `responseCache` key omits `WorkflowID` and depends on a `WorkflowOwner` value sourced from an untrusted node message rather than a value independently verified by the gateway. This matches the "cross-user response confusion" and "information disclosure" categories called out as in-scope.

### Likelihood Explanation
Exploitation requires: (1) the victim's action request to have `CacheSettings.Store=true` and a cacheable (2xx/4xx) response, (2) the attacker's workflow (same owner, or one able to induce a colliding `WorkflowOwner` value in its own outbound request) to issue a request with identical Method/URL/Headers/Body within the cache TTL window (default 10 minutes). Because the request is described as coming from "untrusted nodes" and only method/URL/headers/body/workflowOwner determine the hash, achieving a collision across different workflows of the same owner is straightforward and requires no special privilege beyond authoring/operating a workflow — an unprivileged actor from the gateway's perspective.

### Recommendation
Include `WorkflowID` (and/or `WorkflowExecutionID` if per-execution isolation is desired) as part of the `responseCache` hash key in addition to `WorkflowOwner`, so that cache entries cannot be shared across workflows. Additionally, do not trust the `WorkflowOwner`/`WorkflowID` values embedded in the untrusted node-supplied `OutboundHTTPRequest` for cache-scoping or authorization purposes; derive/verify these from an authenticated source (e.g., the node's registered workflow metadata) rather than accepting them verbatim from `json.Unmarshal(*resp.Result, &req)`.

### Proof of Concept
Conceptual PoC (not fully verifiable without live gateway/DON test harness, but supported by unit-test behavior in `response_cache_test.go`):
1. Workflow A (owner `O`) issues an HTTP Action request: `GET https://victim-api.example.com/data`, `CacheSettings{Store:true, MaxAgeMs:600000}`, `WorkflowOwner="O"`, `WorkflowID="wf-A"`. The external endpoint returns 200 with a body containing sensitive data (e.g., an access token). This gets cached under a key derived from `(method,url,headers,body,"O")` — note `WorkflowID` is excluded. [9](#0-8) 
2. Workflow B (same owner `O`, but a different, unrelated workflow, `WorkflowID="wf-B"`) later issues an outbound HTTP Action request with the identical Method/URL/Headers/Body and `CacheSettings.MaxAgeMs>0`. Because the hash ignores `WorkflowID`, Workflow B's `Fetch` call hits the cache entry stored by Workflow A and receives Workflow A's cached response body — including any sensitive data returned to Workflow A — without ever calling the external endpoint itself. [6](#0-5) 

This PoC exercises exactly the behavior validated (as expected/by-design) in `TestRequestHash`'s "having different workflowID results in same Hash" subtest. [9](#0-8)

// isExpiredOrNotCached returns true if the cached response is expired or not cached.
// IMPORTANT: this method does not lock the cache map. MUST be called with cacheMu write-locked.
func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}
