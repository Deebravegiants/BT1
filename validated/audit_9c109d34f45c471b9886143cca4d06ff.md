## Finding

### Title
Hyper-Fungible-Token cross-chain amount conversion (`convert_to_balance`) floors to zero for small nonzero amounts, permanently destroying bridged funds - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s decimal-scaling helper `convert_to_balance` performs an integer division to rescale an incoming ERC20 amount (higher precision) down to the pallet's local asset precision. For any nonzero ERC20 amount smaller than the scale factor `10^(erc_decimals - local_decimals)`, the division truncates to `0`, and the pallet proceeds to mint/transfer `0` to the beneficiary while the corresponding value was already burned/escrowed on the source chain. This is the exact "CalculateMint returns 0 for inputs > 0" rounding-error class from the referenced report, but here it results in outright loss of bridged user funds rather than a mere usability annoyance, because there is no revert/guard on a zero-value conversion result.

### Finding Description
The conversion helper: [1](#0-0) 

divides `value` (the ERC20-precision `U256` amount) by `10^(erc_decimals - local_decimals)` with plain integer (floor) division and no minimum-amount check. It is invoked in the ISMP module's `on_accept` (crediting an inbound cross-chain transfer) and `on_timeout` (refunding an outbound transfer that failed to deliver): [2](#0-1) [3](#0-2) 

The decimal mismatch is not an edge case restricted to misconfiguration — it is the pallet's normal operating mode. `BridgeToken.sol`'s own documentation states the EVM side is 18 decimals while the token is 12 decimals natively on nexus, "so the pallet scales by 10^6 in both directions": [4](#0-3) 

With a scale factor of `10^6`, any inbound ERC20 amount below `1_000_000` wei (i.e. less than `0.000001` token in 18-decimal terms) is nonzero on the source chain (it was burned/locked there via `HyperFungibleTokenUpgradeable.send`, which unconditionally does `_burn(msg.sender, params.amount)`), yet converts to exactly `0` local balance on the destination: [5](#0-4) 

Because `convert_to_balance` only fails when the resulting string fails to `parse::<B>()` — and `"0"` parses successfully for any numeric balance type — the zero-amount case is never rejected. `on_accept` then transfers/mints `0` to the beneficiary and emits `TokenReceived { amount: 0, .. }` as if nothing went wrong, while the user's real funds were already destroyed/escrowed on the source chain: [6](#0-5) 

The same defect applies to `on_timeout`'s refund path: if a dispatched transfer times out and the refund amount rounds to zero, the sender's escrowed/burned tokens are never returned, permanently locking them in `pallet_account()`.

### Impact Explanation
This is a direct, unprivileged, single-transaction path to permanent loss of user funds in the token-bridge mint/burn flow explicitly listed as in-scope. Any account (an ordinary "token bridger") calling `send` on either the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract or the pallet's `send` extrinsic with an amount smaller than the registered decimal scale factor causes:
- Source-side burn or escrow of a real, nonzero amount, and
- Destination-side credit of exactly `0`, with a legitimate-looking `TokenReceived`/`TokenRefunded` event.

There is no attacker required — a normal user attempting a small transfer, or any automated system rounding/dust-sweeping across chains, silently loses the transferred value. This matches the "unbacked mint / permanent freezing of funds" acceptance criterion: user funds vanish (burned with no destination credit), i.e., permanently destroyed value with no code path to recover it, and it is triggered purely by a legitimately signed, unprivileged transaction.

### Likelihood Explanation
High. The bug triggers on ordinary usage whenever `erc_decimals > local_decimals` (the pallet's documented normal configuration, e.g., 18 vs 12 for BRIDGE) and the transferred amount is smaller than the scale factor — no special conditions, admin error, or malicious actor are needed. Small/dust transfers, fee remainders, or amounts computed by other automated systems (e.g., partial refunds, rounding results from other contracts) are exactly the kind of values likely to fall below the scale threshold.

### Recommendation
In `convert_to_balance`, reject (or round up and require pre-approval of the rounding loss) conversions that would floor to zero for a nonzero input, e.g.:
```rust
if !value.is_zero() && value < U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)) {
    return Err(...); // amount below minimum representable unit
}
```
Apply the same minimum-amount guard on the EVM send side (`HyperFungibleToken`/`HyperFungibleTokenUpgradeable.send`) and in `on_timeout`, so dust amounts are rejected before funds are burned/escrowed rather than silently destroyed after the fact.

### Proof of Concept
1. Register a token pair where `erc_decimals = 18` and `local_decimals = 12` (as documented for BRIDGE/nexus), so `Precisions` scale factor is `10^6`.
2. From the EVM side, call `HyperFungibleTokenUpgradeable.send` with `amount = 500_000` (0.0000005 token, nonzero) — this burns `500_000` from the caller and dispatches a POST request with `message.amount = 500_000`.
3. On delivery, `pallet-hyper-fungible-token::on_accept` calls `convert_to_balance(U256::from(500_000), 18, 12)` → `500_000 / 10^6 = 0` (integer division floors to zero).
4. The pallet mints/transfers `0` to the beneficiary and emits `TokenReceived { amount: 0 }`; the `500_000` units burned in step 2 are permanently lost with no destination credit and no error raised anywhere in the pipeline.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
