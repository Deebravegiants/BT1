Based on the analysis, I've confirmed a concrete identity-binding break in the webhook HMAC verification path.

### Title
Webhook `shop-domain` and `topic` headers are not covered by HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, `api_version` and `webhook_id` values used to dispatch the webhook to application handlers are read exclusively from HTTP headers that are excluded from the signed content. `Registry.process` validates the HMAC over the body only, then unconditionally trusts the header-derived `shop`/`topic` to build the `WebhookMetadata` passed to the app's handler. This breaks the intended binding: `HMAC(body) == valid` should imply `shop header == the shop that generated this exact body`, but the gem never enforces that equality.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning `@raw_body` alone, while `shop`, `topic`, `webhook_id`, and `api_version` are all sourced from HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC strictly against `to_signable_string`, i.e., the body: [3](#0-2) 

`Registry.process` validates the HMAC of the whole `request` object and then immediately constructs `WebhookMetadata` from the *unauthenticated* header fields (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`), passing them straight to the application's handler: [4](#0-3) 

Because the HMAC only signs the body, any request whose body+HMAC pair was legitimately issued by Shopify for **some** shop/topic will pass validation regardless of which `shop-domain`/`topic` headers accompany it. The gem provides no mechanism to bind the header-asserted tenant identity to the HMAC-verified content — i.e., `signed_content` and `asserted_shop` are never checked for consistency, even though `WebhookMetadata.shop` (the value host apps use to key session/data lookups) comes entirely from the unauthenticated header.

### Impact Explanation
This is a cross-tenant identity-binding bypass. An attacker (e.g., a merchant with their own store using the same app, or anyone who can observe/capture one valid webhook body+HMAC pair sent to a public webhook endpoint) can replay the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a different, victim shop's domain. The HMAC still validates (it only covers the body), so `Registry.process` will dispatch the payload to the handler tagged with the attacker-chosen `shop`, causing the host application to process/attribute data as coming from a different tenant than the one that actually produced it. Depending on how the host processes `WebhookMetadata.shop` (e.g., writing order/customer data keyed by shop, invoking mandatory redact handlers, or triggering shop-specific business logic), this can result in cross-tenant data corruption or disclosure.

### Likelihood Explanation
Low-to-moderate effort, no privileged credentials needed: webhook endpoints are public HTTP endpoints authenticated solely by this HMAC, and any entity capable of receiving even one legitimate webhook (including a merchant using the same third-party app on their own store) can capture a valid `(body, hmac)` pair and replay it with a forged shop header to any exposed webhook URL for the same app.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signed content, or otherwise cryptographically bind them to the payload before dispatch. At minimum, `Registry.process` should independently verify that `request.shop` corresponds to an actual currently-installed/known shop for this app (e.g., cross-checked against session storage) rather than trusting the header value implicitly once body-HMAC passes. Track/require a nonce or webhook ID that binds header claims to the signed payload to prevent replay onto a different tenant.

### Proof of Concept
1. Register a handler with `ShopifyAPI::Webhooks::Registry.add_registration` and stand up a webhook endpoint using `ShopifyAPI::Webhooks::Request` / `Registry.process`, per [4](#0-3) .
2. Obtain one legitimate webhook delivery for `shop-a.myshopify.com` (attacker owns/controls `shop-a` with the same app installed) — capture the raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Send a forged HTTP POST to the app's webhook endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which equals `H`, so validation succeeds — see [5](#0-4) .
5. `Registry.process` builds `WebhookMetadata.new(topic: "victim-topic", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and invokes the handler, causing the host app to process attacker-controlled data as originating from `victim-shop.myshopify.com`.
