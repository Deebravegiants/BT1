### Title
Emporium `runAction` lets an unprivileged prover impersonate the Emporium contract's `msg.sender` identity via the unconstrained min-circuit + `signerAddress == address(0)` path - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract when `stack.signerAddress == address(0)`, so any external contract that trusts `msg.sender == Emporium` can be driven by an attacker who never proved ownership of any real UTXO. The only "authorization" gating this path — the `MainEVMCircuitMin` proof and `verifyWallet`'s no-signature branch — constrain nothing about the actual `ops` being executed, and supplying an empty `erc20TokenAddresses` array removes all of Hinkal's balance/slippage checks around the call.

### Finding Description
Broken equality: `AUTHORITY` — the on-chain call to `Victim` is supposed to be authorized by (a) a valid EIP-712 signature from `stack.signerAddress`, or (b) a ZK proof binding the executed `ops` to a real UTXO/root/nullifier. Neither holds on this path.

Trace:
- `EmporiumUpgradeable.verifyWallet` [1](#0-0)  only marks `emporiumMessage` used and **returns early with no signature check at all** when `stack.signerAddress == address(0)`.
- `runAction`'s CASE 2 branch then calls `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own execution context, so `msg.sender` seen by `Victim` is `address(Emporium)` [2](#0-1) .
- `MainEVMCircuitMin` declares `outTimeStamp` and `calldataHash` as public inputs but never constrains them to anything; the only constraint is `message <== Poseidon(1)([messageSeed])`, where `messageSeed` is a private witness the attacker freely chooses [3](#0-2) . This means any prover can produce a valid proof for any `message`/`emporiumMessage`/`calldataHash` combination — the proof never binds to the actual `ops` array (i.e., the `Victim` call) being executed.
- `runAction` is only reachable through `Hinkal.transact()` → `_externalTransact()` [4](#0-3) , gated by `onlyAllowedRecipient` which just checks `msg.sender == Hinkal` [5](#0-4) , not that the caller is a legitimate UTXO owner. `Hinkal.transact()` itself is fully permissionless for any EOA that supplies a valid proof.
- With `circomData.erc20TokenAddresses` empty, the balance-diff/slippage loop in `Hinkal.transact()` iterates zero times [6](#0-5) , so no balance-tracking or slippage guard constrains the transaction, and `_externalTransact` moves no funds out of Hinkal before the call [7](#0-6) .

Net result: an attacker crafts an `EmporiumStack{signerAddress: address(0), ops:[{endpoint: Victim, callData: <privileged call>}]}`, generates a trivially satisfiable min-circuit proof (any `messageSeed`), sets `erc20TokenAddresses = []`, and calls `Hinkal.transact()`. This reaches `Victim` with `msg.sender == address(Emporium)`, with **no** cryptographic tie to any real signer, UTXO, root, or nullifier.

### Impact Explanation
Any external contract in the ecosystem that grants privileged behavior based on `msg.sender == address(Emporium)` (e.g., a router or vault that whitelists Emporium as a trusted relayer for withdrawals/swaps) can be triggered by an unprivileged attacker, causing that external contract to release funds to `msg.sender` (the attacker, since `handleOut`/`transferERC20TokenOrETH` in `runAction` sends any Emporium balance change to `msg.sender`, i.e., the caller of `Hinkal.transact`) [8](#0-7) . This is "executing calls... that a wallet owner or prover never authorised" — categorized as **High** per the stated severity rubric (it does not directly forge or double-spend Hinkal's own shielded UTXOs; it abuses Emporium's identity against third-party trust assumptions). It is repeatable per victim contract and per transaction, at the cost of a single Hinkal `transact()` call and trivial proof generation.

### Likelihood Explanation
Preconditions: existence of any external contract that trusts `msg.sender == Emporium` for privileged operations (an integration risk outside this repo, but the enabling primitive is entirely within `EmporiumUpgradeable`/min-circuit design). No special tree state, no real UTXO, no signer key, and no relayer cooperation are required — attacker cost is one proof generation (trivial, off-the-shelf circuit) plus gas. Fully repeatable against any such victim.

### Recommendation
Do not allow `signerAddress == address(0)` combined with unconstrained min-circuit proofs to authorize arbitrary `ops.endpoint.call(...)` execution from the Emporium contract's own identity. Either (a) bind `calldataHash`/`emporiumMessage` in `MainEVMCircuitMin` (or whichever circuit is used for this verifier ID) to a real constraint tying it to the actual `ops` hash and a known UTXO/root/nullifier, or (b) require a valid `stack.signerAddress` (EIP-712 signature) for any `invokeWallet == false` (stateless) operations that execute with Emporium as `msg.sender`, or (c) restrict stateless calls to a strict allowlist of endpoints/selectors rather than arbitrary attacker-supplied `callData`.

### Proof of Concept
Foundry test plan:
1. Deploy a mock `Victim` contract with a function `withdraw(address to, uint256 amount)` gated by `require(msg.sender == address(emporium))`, and fund it with ERC20/ETH.
2. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register Emporium as `allowedRecipient` and as `externalActionMap[id]`.
3. Construct `EmporiumStack{signerAddress: address(0), ops:[{endpoint: address(Victim), invokeWallet: false, value: 0, callData: abi.encodeCall(Victim.withdraw, (attacker, amount))}], maxFee:0, deadline:0}`, ABI-encode into `externalActionMetadata`.
4. Build `CircomData` with `erc20TokenAddresses = []`, `emporiumMessage = message` computed locally as `Poseidon(messageSeed)` for an arbitrary `messageSeed`, `deltaAmountChanges = []`.
5. Generate a valid Groth16 proof against `MainEVMCircuitMin` with arbitrary `outTimeStamp`/`calldataHash` public inputs (showing they are unconstrained and any value verifies).
6. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from an attacker EOA with no prior deposits/UTXOs.
7. Assert: `Victim` balance decreases by `amount`, attacker's balance increases by `amount`, and no `usedMessages`/nullifier/root check ever validated a real UTXO ownership — confirming the authority equality (`AUTHORITY`: signed/proven identity == actual caller of `Victim`) is broken.
