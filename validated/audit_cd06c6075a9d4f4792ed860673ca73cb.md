### Title
Webhook `shop` (tenant) identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verified by `Utils::HmacValidator.validate` proves nothing about the `shop`, `topic`, or `webhook_id` values, which are read straight from attacker-controllable HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`). `Registry.process` uses this unauthenticated `shop` value to build `WebhookMetadata` that is handed to the host application's handler as the "verified" tenant identity.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
Only `@raw_body` is signed. `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are never part of the signed material: [2](#0-1) 

`Registry.process` validates only this body-only HMAC, then immediately trusts `request.shop` (and `request.topic`) to route/attribute the webhook: [3](#0-2) 

The `HmacValidator` itself confirms the check is solely `to_signable_string` vs. secret — it has no knowledge of `shop`: [4](#0-3) 

The binding that should hold is: **the shop identity attributed to a webhook == the shop identity covered by the HMAC**. Instead: the HMAC covers only `{body}` while the trusted-and-acted-upon identity is `{shop header}`, an entirely disjoint, unauthenticated value. Because `api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop secret), any unprivileged internet user who installs the app on their own (attacker-controlled) shop receives genuine webhooks whose body+HMAC pair is valid under the shared secret. That attacker can replay the exact same body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g., a victim shop's domain). `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` dispatches to the handler with `shop: request.shop` set to the victim's domain, causing the host application to process attacker-supplied webhook data as if it originated from the victim's store.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee to consuming applications: host apps are expected to trust `WebhookMetadata#shop` because the request passed `HmacValidator`. An attacker can force the application to attribute forged/attacker-chosen webhook payloads (of any topic they can legitimately trigger on their own store, e.g., `orders/create`, `app/uninstalled`, `customers/data_request`) to a different, victim shop's identity, leading to cross-tenant data corruption/processing under a false tenant. This matches the required "Critical - cross-tenant access" impact category, since the shop identity boundary is defeated using only the shared, non-privileged `api_secret_key` context already available to any developer/merchant who has installed the app.

### Likelihood Explanation
High. Any unprivileged internet user can install a public Shopify app on their own development/trial store, capture one legitimate webhook (raw body + `x-shopify-hmac-sha256`), and replay it to the app's public webhook endpoint with a modified `x-shopify-shop-domain` header. No access token, `client_secret`, or privileged account is required beyond the ordinary app-installation flow available to any merchant/attacker.

### Recommendation
Bind the shop (and topic/webhook id) into the verified material — either include these header values in the signable string (if Shopify includes them in the signature, this can't be trivially retrofitted since Shopify's actual HMAC is body-only by spec), or, more robustly, require host applications relying on this gem to cross-check `request.shop` against a shop known to be registered/subscribed for that specific `webhook_id`/topic (e.g., via a stored per-shop webhook registration record) rather than trusting the header value as an authenticated identity once `HmacValidator.validate` passes. At minimum, the gem's documentation and `WebhookMetadata` should make explicit that `shop` is **not** authenticated by the HMAC and must not be used as a trusted tenant key without additional verification.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST body `B` and header `x-shopify-hmac-sha256: H` sent to the app's webhook endpoint (both valid under the app's shared `api_secret_key`).
2. Resend an HTTP POST to the same webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (called from `Registry.process`, [5](#0-4) ) succeeds because it only checks `B` against the shared secret.
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, i.e., the application processes attacker-controlled webhook data under the victim shop's identity.
