### Title
Webhook `shop-domain` (and `topic`/`api_version`/`webhook_id`) header values are trusted without being covered by the webhook HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the webhook HMAC over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields consumed by `ShopifyAPI::Webhooks::Registry.process` are read directly from unauthenticated HTTP headers. This breaks the identity binding `shop_authenticated == shop_acted_upon`: the HMAC authenticates the body bytes, but the tenant identifier (`shop`) dispatched to the app's handler is never covered by that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from the (attacker-controllable, prior to signature scope) HTTP headers via `shopify_header`, with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the body-bound HMAC, then immediately forwards the unauthenticated `request.shop`/`topic`/`api_version`/`webhook_id` to the app-supplied handler as trusted `WebhookMetadata`: [3](#0-2) 

The documentation reinforces the false assumption that `Registry.process` fully verifies request provenance ("This will verify the request did indeed come from Shopify"), while in fact only the body bytes are verified: [4](#0-3) 

Because HMAC-SHA256 of a given secret over a given body is deterministic, any party who legitimately receives one valid `(body, hmac)` pair for their *own* shop (e.g., an attacker who installs the same public app in their own store, which is normal unprivileged usage) can replay that exact `raw_body` and `hmac-sha256` header while substituting an arbitrary `shop-domain` header value pointing at a different, victim shop. `HmacValidator.validate` will still pass because it only checks the body against the secret: [5](#0-4) 

The handler then receives `WebhookMetadata` claiming the payload originated from the victim shop, even though it did not.

### Impact Explanation
An unprivileged user who has legitimate access to a valid webhook body/HMAC pair (via their own store's installation of the app) can spoof the shop-domain identity attributed to that webhook payload, causing the host application's webhook handler to process attacker-controlled data as if it belonged to a different, arbitrary tenant. Since handlers commonly use `data.shop` as the key to look up/create/update per-tenant records (as shown in this gem's own documented usage example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this enables cross-tenant data injection/corruption — a Critical-tier cross-tenant access impact per the rules of this exercise.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker needs at least one previously observed valid `(raw_body, hmac)` pair, which they can obtain trivially and repeatedly by installing the target app in their own shop (a fully unprivileged, self-service action requiring no victim credentials). They then only need to alter the `shop-domain` header of the replayed HTTP POST — no cryptographic secret is needed. This can be done as often as the attacker likes, using any payload shape they can trigger in their own store (e.g. by creating orders/products of their choosing), effectively giving attacker-controlled body content attributed to a victim shop.

### Recommendation
Bind the tenant/topic identity into the verified signable string, or otherwise re-validate `shop`, `topic`, and `webhook_id` against data the app already trusts (e.g., cross-check `shop` against a known/installed session store before processing) rather than trusting header values that fall outside the HMAC's coverage. At minimum, update the documentation to stop asserting that `Registry.process` verifies that the *entire request* (including `shop`) came from Shopify, since currently only the body is authenticated.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the resulting raw POST body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed over `B` with the app's shared secret).
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), `X-Shopify-Topic: orders/create` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `to_signable_string` (`= B`) against the secret — the forged `shop-domain` header is never included in this computation: [1](#0-0) [6](#0-5) 
4. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, causing the host application to process attacker-supplied order data as if it belonged to `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
