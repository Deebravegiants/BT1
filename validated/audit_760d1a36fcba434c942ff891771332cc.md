## Analysis: Fee-on-Transfer / Transfer-Fee Token Analog in Raydium AMM `Deposit`

The reported Allo.sol bug is a case where a fee-on-transfer token causes the protocol to credit pool accounting for a full nominal amount while the recipient vault actually received less. The Raydium AMM has a structurally identical flaw in `process_deposit`.

### Root cause

In `process_deposit`, the pool reads the vault balances once at the start (before any transfer), derives `total_coin_without_take_pnl` / `total_pc_without_take_pnl`, and computes `deduct_coin_amount` / `deduct_pc_amount` and `mint_lp_amount` from those figures. [1](#0-0) 

It then transfers exactly `deduct_coin_amount` / `deduct_pc_amount` from the user into the vaults via `Invokers::token_transfer`, and immediately mints `mint_lp_amount` LP tokens and updates the PnL invariant (`target_orders.calc_pnl_x` / `calc_pnl_y`) using those same *intended* amounts — never re-checking what the vault actually received. [2](#0-1) 

If `coin_vault_mint` or `pc_vault_mint` is a token that takes a fee on transfer (e.g. an SPL Token-2022 mint using the `TransferFeeConfig` extension, the on-chain analog of the "reflection token"/fee-on-transfer class cited in the report), the vault receives `deduct_amount - fee`, but LP minting and the pnl invariant (`calc_pnl_x`/`calc_pnl_y`, used later by `calc_take_pnl` for every subsequent deposit/withdraw/swap-pnl operation) are computed as if the full `deduct_amount` landed in the vault. [3](#0-2) 

### Title
Fee-on-transfer/Transfer-Fee tokens cause unbacked LP minting and permanent pool insolvency in `Deposit` - (File: `program/src/processor.rs`)

### Summary
`process_deposit` computes `deduct_coin_amount`/`deduct_pc_amount` and the LP tokens to mint, plus the internal PnL invariant `calc_pnl_x`/`calc_pnl_y`, from the *intended* transfer amount rather than the actual amount that lands in the AMM vault after the SPL transfer. When either vault's mint is a fee-on-transfer token (an SPL Token-2022 mint with a `TransferFeeConfig` extension), any unprivileged depositor can mint LP shares/update accounting for value the pool never actually received.

### Finding Description
`Deposit` first snapshots vault balances and computes `total_coin_without_take_pnl`/`total_pc_without_take_pnl` from `amm_coin_vault.amount`/`amm_pc_vault.amount` [1](#0-0) . From this, `deduct_coin_amount`, `deduct_pc_amount`, and `mint_lp_amount` are derived via the `InvariantToken`/`InvariantPool` math [4](#0-3) .

The program then performs the transfer of `deduct_coin_amount`/`deduct_pc_amount` using the generic `Invokers::token_transfer` helper, which simply issues an `spl_token::instruction::transfer` for the specified amount and does not verify the resulting vault balance [5](#0-4) , [6](#0-5) .

Immediately afterward, `mint_lp_amount` LP tokens are minted to the depositor and `amm.lp_amount` is increased by that amount, and `target_orders.calc_pnl_x`/`calc_pnl_y` (the pool's core solvency-tracking invariant, consumed by `calc_take_pnl` on every future deposit/withdraw/pnl-collection call) are updated using `deduct_pc_amount`/`deduct_coin_amount` — the nominal, not the net-of-fee, amounts [7](#0-6) .

If the coin or pc mint charges a transfer fee, the vault's real balance increases by `deduct_amount - fee`, strictly less than what the accounting assumes. There is no reconciliation step (e.g., re-reading vault balance after transfer and using the delta) anywhere in this flow.

### Impact Explanation
This breaks the fundamental AMM invariant that LP-token supply must be backed 1:1 by pooled assets:
- LP tokens are minted proportionally to the *nominal* deposit amount, not the amount actually received by the vault, so a depositor using a fee-on-transfer mint receives LP shares backed by less value than credited — this dilutes existing LPs' claims on the real pool assets.
- `calc_pnl_x`/`calc_pnl_y` become permanently inflated relative to real vault balances. Since these values are used by `calc_take_pnl` in every subsequent `Deposit`, `Withdraw`, and `WithdrawPnl` call to compute pnl and by extension "amount owed", the whole pool's internal solvency accounting is skewed. This can propagate to insolvent pnl-collection (`WithdrawPnl` transferring based on `need_take_pnl_coin`/`need_take_pnl_pc` that overstate real surplus) and impaired withdrawals for other LPs.
- The effect is a durable, uncorrectable pool state that misrepresents actual holdings — meeting the "insolvent pool accounting" / "unbacked LP minting" bar.

### Likelihood Explanation
Reachable from a single `Deposit` transaction sent by any unprivileged user/liquidity provider with attacker-chosen accounts, as long as the pool's coin or pc mint is a fee-charging SPL token (SPL Token-2022 `TransferFeeConfig` mints are a native, permissionless Solana primitive analogous to the fee-on-transfer/reflection ERC-20 class cited in the report). No special privileges, off-chain component, or non-default build are required — only that the AMM operates over such a mint, which the protocol does not reject anywhere in `process_deposit` or `Initialize2`.

### Recommendation
In `process_deposit` (and analogously in `Initialize2`), read the vault's actual token balance immediately before and after the `Invokers::token_transfer` calls, and use the observed delta (actual amount received) — not the nominal `deduct_coin_amount`/`deduct_pc_amount` — to compute `mint_lp_amount` and to update `target_orders.calc_pnl_x`/`calc_pnl_y`. Alternatively/additionally, reject pool creation and deposits for mints carrying transfer-fee (or other balance-altering) extensions.

### Proof of Concept
1. Create/point an AMM pool at a coin (or pc) mint that is an SPL Token-2022 mint with a `TransferFeeConfig` extension (fee > 0), owned by the vault's authority as usual.
2. An unprivileged LP calls `Deposit` with `max_coin_amount`/`max_pc_amount` set such that `deduct_coin_amount = D`.
3. `process_deposit` computes `mint_lp_amount` and updates `target_orders.calc_pnl_x/y` based on `D` (lines 1244–1372).
4. `Invokers::token_transfer` moves `D` tokens from the user; because of the transfer fee, the vault's balance only increases by `D - fee`.
5. Result: `amm.lp_amount` and `calc_pnl_x`/`calc_pnl_y` reflect `D`, while the vault actually holds `D - fee`. Subsequent `Withdraw`/`WithdrawPnl` calls operate on this now-inflated internal accounting, diluting other LPs and permanently misstating pool solvency versus the on-chain vault balances.
