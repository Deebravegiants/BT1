# No Meaningful Deadline Protection in `EvmHost` and `IntentGatewayV2` Uniswap Swaps

### Summary
`EvmHost.dispatch()`, `EvmHost.fundRequest()`, and `IntentGatewayV2.placeOrder()` (both EVM and Tron variants) all pass `block.timestamp` as the `deadline` argument to `IUniswapV2Router02.swapETHForExactTokens`. Because the deadline is computed at call time and only checked against the timestamp of the very same transaction's execution, it can never actually expire — this is functionally equivalent to having **no deadline at all**, the same anti-pattern flagged in the referenced USSD report for `UniV3SwapInput()`.

And in `IntentGatewayV2.placeOrder()`, which any unprivileged user reaches when placing an order and paying fees in native token: [4](#0-3) 

Same pattern in the Tron variant: [5](#0-4) 

In all of these, `deadline` is set to `block.timestamp` at the moment the surrounding transaction executes — not a value derived from when the user *signed/submitted* the transaction. A validator/block-builder can hold the transaction (e.g., in a private mempool or via a delayed inclusion) for an arbitrary number of blocks and, once included, the `block.timestamp` used for the Uniswap deadline check is simply that later block's own timestamp, which trivially always satisfies `deadline >= block.timestamp`. There is no bound derived from the user's original intent/submission time, so the deadline provides zero real protection against delayed execution or same/later-block sandwiching, exactly the mechanism described in the referenced report.

### Impact Explanation
Because these calls use `swapETHForExactTokens` (exact output, with `msg.value`/`order.fees`-derived amount as the max input), the primary exploitable effect is: a delayed/sandwiched inclusion lets a validator or MEV actor manipulate the WETH/feeToken pool price before the swap executes, forcing the swap to consume close to the full `msg.value` (or `msgValue`) cap instead of the fair-market amount, extracting the difference as MEV profit at the expense of the dispatching user/order-placer. Since `EvmHost.dispatch()` is the core, unprivileged entry point used by every app dispatching POST/GET requests with native fee payment, and `IntentGatewayV2.placeOrder()` is directly reachable by any user placing an order, this is a broadly reachable loss-of-funds vector for callers paying protocol/relayer fees in native token.

### Likelihood Explanation
Likelihood is moderate: it requires either a colluding/adversarial block producer able to delay inclusion, or an MEV searcher observing the pending transaction and sandwiching it in the same or a later block. Given Hyperbridge dispatch calls are highly predictable (fixed fee amounts, public mempool), this is a realistic MEV target on public EVM chains, matching the audit-report's own risk classification (Medium).

### Recommendation
Thread an actual user-supplied `deadline` parameter through `dispatch()`, `fundRequest()`, and `placeOrder()` (e.g., as part of `DispatchPost`/`DispatchGet`/`Order`, or a dedicated parameter) so the Uniswap `deadline` reflects the time the user is willing to wait, rather than deriving it from `block.timestamp` at execution time. Additionally, consider bounding `amountInMaximum`/`msg.value` more tightly to the expected fee cost (rather than allowing arbitrary excess) to reduce MEV extraction surface even within a valid deadline window.

### Proof of Concept
1. User calls `EvmHost.dispatch(post)` with `msg.value` sized to cover `post.fee` plus a reasonable ETH-price buffer, expecting the swap to execute promptly.
2. A block builder/validator delays including this transaction for several blocks/minutes while WETH/feeToken price moves.
3. When finally included, `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` is invoked with `deadline = block.timestamp` set to the *current* (delayed) block's timestamp — the deadline check inside Uniswap's router (`require(deadline >= block.timestamp)`) trivially passes.
4. The swap executes at the now-unfavorable price, consuming a larger portion of `msg.value` than the fair-market rate would require, and the user receives a smaller refund via `msgValue -= amounts[0]` than expected — the difference is captured by the entity that delayed/sandwiched the transaction.
