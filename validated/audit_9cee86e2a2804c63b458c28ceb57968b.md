### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted for tenant identification but are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from unauthenticated HTTP headers, but `Utils::HmacValidator.validate` only verifies the HMAC over the raw request body (`to_signable_string` returns `@raw_body` only). This breaks the expected identity binding `HMAC(secret, verified_bytes) == HMAC(secret, bytes_the_app_acts_on)`, since `verified_bytes = body` while `bytes_the_app_acts_on = body + shop + topic + webhook_id`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively via: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which computes the signature only over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; the `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from headers that are never part of the signed material: [3](#0-2) 

Despite this, `Registry.process` forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` straight into `WebhookMetadata` and passes it to the app's registered handler as trusted, tenant-identifying data: [1](#0-0) 

Because only the body bytes are authenticated, any party who possesses one valid `(body, hmac)` pair — trivially obtainable by installing the app on their own store and capturing a legitimate webhook delivery to the app's public, unauthenticated webhook endpoint — can resend that exact body/HMAC pair while substituting the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers. `HmacValidator.validate` will still report success because it never inspects those headers, and the app's handler will process the (attacker's own, legitimately obtained) payload under a spoofed shop/topic identity of the attacker's choosing.

This is the same bug class as the referenced report: a field the application acts on (`shop`, used to select the tenant whose data is updated) is not covered by the integrity check (HMAC over body only), letting an attacker desynchronize "the shop verified" from "the shop trusted."

### Impact Explanation
An attacker who has legitimate access to at least one shop (e.g., installs the app themselves, a normal unprivileged path) can capture one authentic webhook body+HMAC and replay it to the app's public webhook endpoint with a forged `shop-domain` header pointing at a victim shop. The app has no way to distinguish this from a genuine webhook for the victim shop, since the shop identity is not authenticated. Depending on how the host application uses `WebhookMetadata#shop` (e.g., for `shop/redact`, `customers/redact`, `customers/data_request`, or any order/product topic to look up and mutate per-tenant records), this enables cross-tenant data confusion/injection — an unprivileged internet user forging data attributed to another merchant's shop. This satisfies the Critical "cross-tenant access" impact criterion.

### Likelihood Explanation
Webhook endpoints are, by design, public and unauthenticated aside from the HMAC check — this is the sole trust boundary the gem provides. Obtaining a valid `(body, hmac)` pair requires no privileged credentials: any developer/attacker can install the target app on a shop they control (a normal, permitted flow for public apps) and receive real webhook deliveries with valid HMACs. Replaying that payload with modified headers against the same public endpoint is straightforward and requires no TLS interception, no secret, and no host-application misconfiguration.

### Recommendation
Include the tenant-identifying headers in the material that is HMAC-verified, or otherwise cryptographically bind `shop`, `topic`, and `webhook_id` to the signed body — e.g., extend `Webhooks::Request#to_signable_string` to incorporate the shop domain and topic (matching Shopify's actual verification contract, if these headers are meant to be trusted), or have `Registry.process` cross-check the delivered `shop` against an independent authoritative source (such as looking up the webhook by its `webhook_id` via the Admin API) before dispatching to handlers. At minimum, document that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated and must not be used as sole tenant-selection keys without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of BODY>
   x-shopify-shop-domain: attacker.myshopify.com
   x-shopify-webhook-id: <id>
   BODY = {"id": 1, ...attacker-controlled order data...}
   ```
2. Attacker resends the exact same `BODY` and `x-shopify-hmac-sha256` value to the same public webhook endpoint, but changes:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only exposes/signs `BODY`; `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `BODY` alone and it matches, so `Registry.process` does not raise `Errors::InvalidWebhookError`.
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: BODY, ...)` — the app now processes attacker-controlled data under the victim shop's identity, even though the victim shop never sent anything.

          received_signature = verifiable_query.hmac
