### Title
Webhook shop-domain (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC check only to the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` fields — all taken from HTTP headers — are never part of the signed content, yet `shop` is exactly the field the gem hands to the host application's handler as the tenant identifier.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which computes an HMAC over `request.to_signable_string`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are read directly from headers, independent of the signed body: [3](#0-2) 

After validation succeeds, `Registry.process` builds `WebhookMetadata` using `request.shop` (a header value never covered by the HMAC) and passes it straight to the app's handler as the tenant identity: [4](#0-3) [5](#0-4) 

This mirrors the reported bug class exactly: a security-relevant field (`shop`, the tenant-binding key) is *acted on* by downstream logic (dispatched to the handler as the shop the webhook belongs to) but is *not covered* by the cryptographic check (`EXCEEDS_NUISANCE_GAS`/HMAC) that is supposed to guarantee authenticity. The equality that should hold — "shop bound by HMAC" == "shop used to attribute the webhook" — is broken: `hmac(raw_body, secret) == received_hmac` says nothing about `shop`.

Because a single app has one `api_secret_key` shared across every merchant that installs it, any tenant that installs the app can legitimately receive genuine webhook deliveries (valid body + valid HMAC) for their own shop. That attacker-tenant can then replay the exact same `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header (and/or `topic`, `webhook_id`) for a victim shop. `HmacValidator.validate` still passes because it only checks the body bytes against the secret; the forged `shop` header sails through untouched and is delivered to the host app's handler as if it originated from the victim's shop.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged existing tenant of a multi-tenant app can cause the app to process, store, or forward events under a different tenant's identity (`shop`) using body content and a signature that are only valid for their own tenant. Depending on how the host app's `WebhookHandler#handle` uses `data.shop` (which the gem's own documentation instructs apps to key store lookups/writes on, e.g. `perform_later(shop_domain: data.shop, ...)`), this can lead to cross-tenant data corruption or disclosure in the merchant's data store — matching the "cross-tenant access" Critical-impact category, since the tenant boundary is enforced entirely by an unauthenticated header value.

### Likelihood Explanation
Requires only that the attacker be able to install the app on their own (attacker-controlled) shop — an ordinary, unprivileged action available to any internet user for a public app — and the ability to send arbitrary HTTP requests to the app's registered webhook callback path (also typically a public, unauthenticated route). No access token, `client_secret`, or privileged account is required. This is a moderate-likelihood, low-cost attack.

### Recommendation
Include the identity-binding fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed content checked against the HMAC, or otherwise cryptographically bind them to the authenticated request (e.g., verify `shop` against the actual embedding of the shop identifier inside the signed body/payload rather than trusting the header verbatim). At minimum, `to_signable_string` should not return only `@raw_body` while `shop` is used for tenant attribution downstream.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, obtaining a valid installation under the app's single `api_secret_key`.
2. Shopify sends a legitimate webhook to the app's callback endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(B, secret)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this request and resends it to the same endpoint, keeping `raw_body = B` and the same valid HMAC header, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
4. `HmacValidator.validate` in `Registry.process` recomputes the HMAC over `B` only [6](#0-5)  — validation succeeds because `B` and the HMAC are unchanged and never depended on the shop header.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body_of_B, ...)`, causing the host app to act on attacker-controlled body content attributed to the victim tenant.
