Audit Report

## Title
Unbounded `drain_prefix` over attacker-inflatable `Attribute`/`ItemMetadataOf` storage makes NFT collection `destroy` permanently uncallable - (File: substrate/frame/nfts/src/features/create_delete_collection.rs)

## Summary
`set_attribute` allows any item owner (`AttributeNamespace::ItemOwner`) or any pre-approved delegate (`AttributeNamespace::Account`) to cheaply create new `Attribute` entries for a collection they do not administer, incrementing `Collection::attributes` with no per-collection cap. `do_destroy_collection` drains all `ItemMetadataOf` and `Attribute` entries for a collection via unbounded `drain_prefix` calls (no limit argument), unlike the adjacent `ItemConfigOf::clear_prefix` which is explicitly bounded by `witness.item_configs`, creating an asymmetric unbounded-iteration weight profile in an otherwise-witnessed extrinsic.

## Finding Description
`do_set_attribute` gates on `is_valid_namespace`, which for `ItemOwner` only requires `origin == item_details.owner` and for `Account(account_id)` only requires the origin be a delegate with an existing approval - neither requires the collection's `Admin`/owner role. [1](#0-0) 
Each new attribute key increments `collection_details.attributes` unconditionally with no maximum enforced. [2](#0-1) 
The public `set_attribute` extrinsic dispatches into this path directly for `ItemOwner`/`Account` namespaces using the caller as depositor. [3](#0-2) 

`do_destroy_collection` verifies the caller-supplied `witness` matches the real stored counters (`BadWitness` otherwise), then drains `ItemMetadataOf` and `Attribute` with **unbounded** `drain_prefix` calls (no limit argument), in contrast to `ItemConfigOf::clear_prefix(&collection, witness.item_configs, None)`, which is explicitly bounded by the witness count. [4](#0-3) 
The `destroy` extrinsic's declared weight is `T::WeightInfo::destroy(witness.item_metadatas, witness.item_configs, witness.attributes)`, so a caller must supply the true, exact counts to pass the witness check, meaning the declared/charged weight for the call does scale up in step with the real attribute/metadata count as inflated by an attacker. [5](#0-4) 

The code matches the claim's description of the mechanism: no privileged role is required to create attributes tied to a collection, and the drain in `destroy` is unbounded per-call rather than paginated. This is a real structural asymmetry versus `ItemConfigOf`'s bounded clearing.

## Impact Explanation
If an attacker can push the real `attributes` (or `item_metadatas`) count for a collection high enough that the benchmarked weight for `destroy` with the correct witness exceeds the runtime's configured `max_extrinsic`/`max_block` weight, the honest owner can never construct a valid `destroy` call (any smaller witness fails `BadWitness`, and there is no partial/paginated destroy path). This would permanently freeze the collection's reserved `owner_deposit` and prevent removal of `Collection`/`CollectionConfigOf` storage - a genuine permanent-lock condition if reachable.

However, whether this is *practically* reachable is unverified. The claim itself acknowledges this: it could not confirm production `AttributeDepositBase`/`DepositPerByte` values, nor the actual `max_block`/`max_extrinsic` weight limits, nor whether the linear weight-per-attribute benchmark component is large enough that a feasible number of attributes (bounded by the economic cost of deposits and the practical cost of submitting thousands of `set_attribute` extrinsics) would push total destroy weight past the block limit. Since fee/deposit cost for the attacker scales linearly with the number of attributes created (each requires a deposit reservation), and destroy weight also scales roughly linearly with the same count, this is fundamentally an economic race: the attacker must lock enough of their own capital in deposits to make the linear weight sum exceed a fixed block-weight ceiling. Without confirmed per-attribute weight-benchmark constants and block-weight limits for a real runtime (e.g., Asset Hub), it cannot be established that this is actually achievable rather than requiring the attacker to accumulate an infeasibly large amount of locked deposit and an infeasibly large number of on-chain transactions.

## Likelihood Explanation
The preconditions are realistic and require no privilege escalation: public/permissionless minting or a delegate approval via `approve_item_attributes` are legitimate, common collection configurations, and the attacker only needs item ownership or delegate status, not collection admin/owner rights. The attacker pays a real per-attribute deposit (`AttributeDepositBase + DepositPerByte*len`), which is a genuine capital cost providing an economic disincentive proportional to the number of attributes created - the same quantity that increases destroy's weight. This economic self-limiting relationship weakens (without disproving) the practical likelihood of reaching the point where destroy weight exceeds block limits, and the claim does not demonstrate concrete numbers proving this threshold is reachable within realistic capital and transaction-count budgets.

## Recommendation
Bound the `Attribute` and `ItemMetadataOf` drains in `do_destroy_collection` using a limited/paginated `clear_prefix` or `drain_prefix` (mirroring the `ItemConfigOf` treatment), and support a multi-call/paginated destroy flow (e.g., a dedicated `destroy_attributes`/`destroy_metadatas` step callable repeatedly) so that weight per call remains bounded regardless of how many attributes were accumulated. Consider also enforcing a maximum attribute count per collection/item in `do_set_attribute` to cap the achievable griefing surface, and/or restricting who can create `ItemOwner`/`Account`-namespace attributes tied to a collection they don't administer.

## Proof of Concept
No concrete PoC with real weight/benchmark numbers was provided or verified; the claim's own PoC plan is a proposed test sketch (mint many items, set many attributes via `ItemOwner`/`Account` namespace, burn items to reach `items == 0`, compute the real `DestroyWitness`, and assert `T::WeightInfo::destroy(...)` exceeds `BlockWeights::max_block`/`max_extrinsic`) but does not include actual computed thresholds proving the attack is achievable within realistic capital/tx-count budgets in a production runtime such as Asset Hub. This proof-of-concept step is necessary to confirm the impact and was not completed.
