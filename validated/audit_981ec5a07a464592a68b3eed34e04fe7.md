### Title
CallDispatcher.dispatch() is fully permissionless and blindly executes attacker-controlled calls as its own `msg.sender`, letting anyone drain any token/ETH balance the shared dispatcher happens to hold - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` has no caller restriction and executes an attacker-supplied array of `Call{to, value, data}` with the dispatcher contract itself as `msg.sender`. This mirrors the SushiSwap RouteProcessor2 "unchecked input data" root cause: a shared, intermediate-holding contract trusts externally supplied routing/call parameters without verifying who is allowed to invoke it or what it's allowed to move, so any balance the contract transiently or accidentally holds can be redirected by an unrelated third party.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an arbitrary `Call[]` and executes each call with only a "target has code" check — there is no `onlyGateway`/`onlyHost`/allowlist guard at all: [1](#0-0) 

`CallDispatcher` is the single shared utility used by `IntentGatewayV2` (predispatch/postdispatch), `HyperFungibleTokenUpgradeable`, and `WrappedHyperFungibleTokenUpgradeable` for arbitrary destination-chain calldata execution, and it also has a `receive()` to accept native value: [2](#0-1) 

Because `dispatch()` is callable by anyone, and the dispatcher can end up holding token/ETH balances that were not fully swept by the calling app's own bookkeeping, an attacker does not need to go through `IntentGatewayV2` at all — they can call `dispatch()` directly to move out any balance sitting on the dispatcher.

Concretely, `IntentGatewayV2.placeOrder`'s predispatch flow only sweeps tokens that are explicitly listed in `order.inputs` back from the dispatcher to the gateway: [3](#0-2) 

and `_execute`'s postdispatch sweep in `IntentsBase` likewise only sweeps tokens listed in `order.output.assets`: [4](#0-3) 

Any token produced by the predispatch/postdispatch calldata that is *not* one of the declared input/output tokens (e.g., swap-router change, an intermediate hop token, referral/rebate tokens, or tokens mistakenly sent directly to the dispatcher address by any third party) is left stranded on `CallDispatcher` indefinitely. Since `dispatch()` has no access control, anyone — not just the order's user, solver, or beneficiary — can call `CallDispatcher.dispatch()` directly with a `Call{to: strandedToken, data: transfer(attacker, balance)}` and sweep it out, exactly as SushiSwap's `ProcessRoute` let an attacker supply unchecked routing parameters to redirect funds the router held.

### Impact Explanation
Because `CallDispatcher` is shared infrastructure reused across every `IntentGatewayV2` instance and every `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment on a chain, any dust, rounding remainder, or mis-swept token/ETH left on it by any of these apps' calldata-execution flows becomes permanently and immediately stealable by an unrelated caller. This is a direct loss-of-funds vector for users/protocols whose predispatch or postdispatch calldata produces or leaves behind value not captured by the narrow "sweep only declared tokens" logic, satisfying the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
`dispatch()` requires no privilege and no proof — a single unprivileged transaction from any address can call it whenever the dispatcher holds a non-zero balance of any token, which can occur from ordinary usage (predispatch swap slippage/change tokens, output calldata side effects) rather than requiring any special setup, making this a "single submitted transaction" reachable path as required by the validation rules.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by registered/trusted apps (e.g., an allowlist of gateway/HFT addresses set at deploy time, or make each app deploy/own its own dispatcher instance instead of sharing one), and/or have the calling apps sweep the dispatcher's *entire* balance of every token touched by the executed calldata (not just the declared input/output token list) back to themselves atomically within the same transaction so nothing is ever left resident on the shared contract between transactions.

### Proof of Concept
1. A legitimate `placeOrder` predispatch call swaps ETH → DAI via Uniswap through `CallDispatcher`, but the swap path also yields a small remainder of an intermediate token (or the router returns slightly more of a token not listed in `order.inputs`); that token balance stays on `CallDispatcher` because the sweep loop in `IntentGatewayV2.placeOrder` (lines 258-287) only iterates over `order.inputs` tokens.
2. An attacker (or bot) monitoring `CallDispatcher`'s balances calls `CallDispatcher.dispatch(abi.encode([Call({to: strandedToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedBalance)})]))` directly — no permission check blocks this, per `CallDispatcher.sol` lines 44-62.
3. The stranded balance is transferred to the attacker, with no way for the original order's user/protocol to recover it.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
