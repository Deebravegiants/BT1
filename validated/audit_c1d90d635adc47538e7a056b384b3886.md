Audit Report

## Title
`AllowNext` reentrancy protection is bypassed for real-world stipend transfers because of match-arm ordering on `value.is_zero()` - ([File: substrate/frame/revive/src/vm/evm/instructions/contract.rs])

## Summary
In `run_call`, the reentrancy mode is chosen via a tuple match on `(value.is_zero(), gas_limit == CALL_STIPEND)`, but the first arm `(false, _)` matches whenever `value != 0` regardless of the gas-limit, so it short-circuits before the stipend check can select `AllowNext`. This means the classic Solidity `.transfer()`/`.send()` pattern — non-zero `value` with `gas_limit == CALL_STIPEND` (2300) — receives `ReentrancyProtection::AllowReentry` (no protection) instead of the intended `AllowNext`, exactly inverting the purpose of the heuristic for its primary target case.

## Finding Description
`run_call` builds the reentrancy mode as follows: [1](#0-0) 

Rust match arms are evaluated top-to-bottom, and `(false, _)` matches on `value.is_zero() == false` independent of the second tuple element. Consequently, any call with non-zero `value` and `gas_limit == CALL_STIPEND` (i.e., the exact shape produced by Solidity's `.transfer(amount)`/`.send(amount)`) falls into the first arm, yielding `(true, ReentrancyProtection::AllowReentry)` — stipend gas is still added, but no reentrancy protection is applied. The `(_, true) => AllowNext` arm is only reachable when `value.is_zero()` is true, i.e. zero-value calls with the stipend gas limit, which is not the scenario `.transfer`/`.send` produce (those always carry the value being paid out).

This directly contradicts the documented intent of the `AllowNext` variant, which is specifically designed for "calls that transfer value but restrict gas so that the callee only has a stipend gas amount": [2](#0-1) 

The enforcement mechanism itself (tracking `allows_reentry` per frame and denying reentry into the calling contract) is a separate, correctly-implemented piece of logic in `exec.rs`; the defect here is purely in the front-end heuristic in `contract.rs` that selects which protection mode to request, and it selects the wrong (permissive) one for the primary real-world case the mechanism was built for.

## Impact Explanation
Because `AllowReentry` is applied instead of `AllowNext` for non-zero-value stipend calls, a malicious contract's fallback function invoked during a victim's `.transfer()`/`.send()` payout is not blocked from reentering the victim contract. If the victim implements a naive interactions-before-effects withdrawal pattern, this enables the classic reentrancy fund-drain attack that the `AllowNext` mechanism was explicitly added to close (per its doc comment referencing revive's differing gas scale from Ethereum, where 2300 gas is not automatically insufficient for a callee to make another call). This is a concrete in-scope funds-loss vector for a widely-used Solidity payout idiom compiled to pallet-revive's EVM front-end.

## Likelihood Explanation
The bug is deterministic and requires no privileged access: any unprivileged user can deploy a victim contract using `.transfer()`/`.send()` for payouts (an extremely common legacy Solidity pattern) and an attacker contract with a reentrant fallback, then trigger the withdrawal through a normal `eth_transact`/extrinsic call. The vulnerable code path (`contract.rs:193-203`) is reached on every CALL/STATICCALL with non-zero value and `gas_limit == CALL_STIPEND`, making the issue fully reproducible and repeatable.

## Recommendation
Decouple the stipend-gas check from the `value.is_zero()` branch so that `AllowNext` is selected whenever `gas_limit == CALL_STIPEND`, regardless of whether `value` is zero, e.g.:
```rust
let is_stipend = gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND);
let (add_stipend, reentracy) = if is_stipend {
    (true, ReentrancyProtection::AllowNext)
} else if !value.is_zero() {
    (true, ReentrancyProtection::AllowReentry)
} else {
    (false, ReentrancyProtection::AllowReentry)
};
```
Add a regression test asserting that a non-zero-value call with `gas_limit == CALL_STIPEND` results in `ReentrancyProtection::AllowNext` being applied (i.e., reentry into the caller is denied), following the existing reentrancy test patterns in `substrate/frame/revive/src/exec/tests.rs`.

## Proof of Concept
1. Deploy a `Victim` contract whose `withdraw()` performs a low-level call equivalent to Solidity `.transfer(amount)`: `value = amount` (non-zero), `gas_limit = CALL_STIPEND (2300)`, target = `msg.sender`.
2. Deploy an `Attacker` contract whose fallback (invoked during the stipend call) re-enters `Victim.withdraw()`.
3. Fund `Victim` with balance sufficient for two withdrawals, but give `Attacker` entitlement to only one.
4. Call `Victim.withdraw()` from `Attacker` via a normal extrinsic/`eth_transact`.
5. Observe (with current code) that the reentrant call succeeds (`ReentrancyProtection::AllowReentry` was applied) and `Victim`'s balance is drained beyond `Attacker`'s entitlement.
6. After applying the fix, the reentrant call should be rejected with `Error::<Test>::ReentranceDenied`, and the balance change should equal exactly one entitled withdrawal.
