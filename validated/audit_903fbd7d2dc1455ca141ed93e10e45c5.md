## Title
Unauthenticated `send()` lets anyone drain the shared, unaccounted feeToken buffer accumulated in `HyperbridgeLzEndpoint`, stealing other OApps' pre-paid fees and permanently DOSing all cross-chain LZ message dispatch through the adapter - (File: `sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol`)

### Summary
`HyperbridgeLzEndpoint.send()` is a public, unauthenticated entry point (no restriction to registered OApps) that, when called with `msg.value == 0`, pays the Hyperbridge dispatch fee out of the **contract's entire current feeToken balance** rather than out of funds specifically supplied by the caller for that call. `quote()` intentionally instructs upstream OFTs to prepay `2x` the actual relayer fee ("a generous 2x buffer"), but `send()` only ever consumes `1x` (`relayerFee(dstEid)`) per dispatch, so every legitimate send leaves roughly `1x` fee worth of tokens permanently stranded in the endpoint with no per-sender accounting. Because `send()` is callable by anyone, an attacker can call it directly and consume that shared, unaccounted balance to pay for their own arbitrary spam messages, and can repeat this until the balance is exhausted, at which point every legitimate OApp's `send()` call reverts (DOS), exactly mirroring the reported LayerZero `CrossChainRouter` ETH-drain DOS pattern but here draining a stranded feeToken buffer instead of ETH.

### Finding Description
In `send()`:
```solidity
DispatchPost memory request = DispatchPost({
    dest: dest,
    to: abi.encodePacked(address(this)),
    body: body,
    timeout: 0,
    fee: relayerFee(_params.dstEid),
    payer: address(this)
});

if (msg.value > 0) {
    IDispatcher(_host).dispatch{value: msg.value}(request);
} else {
    address feeToken = IDispatcher(_host).feeToken();
    IERC20(feeToken).forceApprove(_host, IERC20(feeToken).balanceOf(address(this)));
    IDispatcher(_host).dispatch(request);
}
``` [1](#0-0) 

Two design flaws combine here:

1. **No per-caller fee accounting.** The `payer` on the dispatch is hardcoded to `address(this)` (the endpoint itself), and the approval/consumption is based on `IERC20(feeToken).balanceOf(address(this))` — the endpoint's *total* balance — not on tokens attributable to the current `msg.sender`. Any external account can call `send()` (there is no `onlyOApp`/allowlist check), so the fee for an attacker's arbitrary message is paid from whatever feeToken happens to sit in the contract, which was deposited there by *other* OApps' prior calls.

2. **Structural over-funding creates a permanent, growing pool for the taking.** `quote()` returns `lzTokenFee: request.fee * 2` — i.e., callers are told to prepay double the actual dispatch fee: `relayerFee(dstEid) * 2`. [2](#0-1) 
But `send()`'s `DispatchPost.fee` is only `relayerFee(_params.dstEid)` (1x), and `EvmHost.dispatch()` only pulls exactly `post.fee` via `safeTransferFrom`:
```solidity
} else if (post.fee > 0) {
    IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
}
``` [3](#0-2) 
Every legitimate OFT `send()` call therefore leaves roughly `1x relayerFee` of feeToken permanently stranded in the endpoint's balance, unclaimed by anyone and untracked per user.

Because the leftover balance sits in the endpoint and `send()`'s feeToken branch is reachable by any address with no ownership check, an attacker can:
- Call `send()` repeatedly with `msg.value = 0` and arbitrary/garbage `_params` (any `dstEid`/`receiver`/`message`), causing the endpoint to `forceApprove` and `dispatch()` using the shared balance to fund the attacker's own spam messages "for free," at the expense of tokens legitimately paid by other OApps.
- Continue until the feeToken balance/allowance is insufficient, at which point `IERC20(feeToken()).safeTransferFrom(...)` in `EvmHost.dispatch()` reverts for **every** subsequent legitimate call to `send()` through this adapter (since it also relies on the same shared balance when `msg.value == 0`), bricking cross-chain messaging for all OApps routed through this `HyperbridgeLzEndpoint` until the owner intervenes (e.g., re-funding or `setRelayerFee`/pause).

This is the direct analog of the reported issue: a shared balance meant to fund all cross-chain dispatches for a protocol can be drained via unprivileged, cheap/free repeated calls, causing loss of other users' funds and DOS of the messaging path.

### Impact Explanation
- **Theft of funds:** Attacker messages are funded using feeToken balances that legitimately belong to (were overpaid by) other OApps/users, without their consent.
- **DOS of cross-chain messaging:** Once the shared buffer is exhausted, all legitimate `send()` calls with `msg.value == 0` revert in `EvmHost.dispatch()`'s `safeTransferFrom`, halting all outbound LZ-routed ISMP messages through this adapter for every integrated OApp until manually refunded/fixed — a protocol-wide route failure, matching the "route unable to deliver messages" acceptance criterion.
- Impact scales with adapter usage: the more legitimate traffic (and therefore stranded 1x buffer) accumulates, the larger the pool an attacker can steal/drain, and native traffic is unaffected since `msg.value>0` bypasses this path, but any OApp configured to pay in feeToken (`payInLzToken`) is exposed.

### Likelihood Explanation
`send()` has no access control restricting callers to registered/trusted OApps, so exploitation requires only a single unprivileged transaction, repeated as needed — no special preconditions, no governance/admin compromise, and no reliance on a race condition. The stranded buffer builds up automatically from normal usage (`quote()`'s 2x over-quote vs. `send()`'s 1x consumption), so funds are continuously available to drain as long as the adapter is used at all.

### Recommendation
- Restrict `send()`'s feeToken-payment branch to only ever consume the amount actually required for the current call (`post.fee`) rather than approving/relying on the full contract balance, and require the caller (or the OFT on the caller's behalf) to supply the exact feeToken amount for that call via `safeTransferFrom(msg.sender, ...)` instead of drawing from a shared pool.
- Fix `quote()` to return the correct expected fee (matching what `send()` will actually consume) instead of an arbitrary `2x` buffer, eliminating the source of the stranded balance; if a buffer is retained, refund/sweep the unused portion back to the specific caller rather than leaving it in the shared contract balance.
- Consider restricting `send()` to a registered-OApp allowlist, consistent with real LayerZero endpoint semantics, so arbitrary unprivileged accounts cannot trigger dispatch consuming shared funds.

### Proof of Concept
1. Legitimate OApp `A` (configured with `payInLzToken = true`) calls `quote()` and is quoted `lzTokenFee = relayerFee(dstEid) * 2`; it transfers that amount of feeToken to `HyperbridgeLzEndpoint` via `_payLzToken`, then calls `send()`.
2. `send()`'s feeToken branch approves the full endpoint balance and calls `IDispatcher(_host).dispatch(request)`, which pulls only `relayerFee(dstEid)` (1x) from the endpoint via `EvmHost.dispatch()`'s `safeTransferFrom`. The remaining `1x relayerFee` worth of feeToken stays in the endpoint, unattributed to any account. [4](#0-3) 
3. An attacker (any EOA) calls `HyperbridgeLzEndpoint.send()` directly with `msg.value = 0` and arbitrary `MessagingParams` (fabricated `dstEid`/`receiver`/`message`). The endpoint again approves/consumes from its own balance — the leftover `1x` from step 2 — funding the attacker's message for free.
4. Repeating step 3 across many prior legitimate sends lets the attacker continually drain the accumulating buffer; once balance/allowance is insufficient, all subsequent `send()` calls by legitimate OApps revert in `EvmHost.dispatch()`, DOSing the adapter's cross-chain messaging until the owner re-funds or intervenes.
