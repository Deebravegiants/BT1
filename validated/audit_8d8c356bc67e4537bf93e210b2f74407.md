### Title
Unvalidated `shop` parameter in `Oauth.begin_auth` allows forced-OAuth redirection to attacker-controlled hosts - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the merchant-facing OAuth authorization URL directly from the caller-supplied `shop` parameter without validating that it is a genuine Shopify domain, unlike the sibling grant methods `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, which both call `Utils::ShopValidator.sanitize!(shop)` before using `shop` to build a request host.

### Finding Description
`Oauth.begin_auth` takes an unauthenticated, caller-supplied `shop:` string (per the gem's own documented usage pattern, taken straight from a request header/param before any OAuth handshake has occurred) and passes it straight into `auth_base_uri(shop)`: [1](#0-0) 

```ruby
def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
  ...
```

This is used to build the final redirect target the merchant's browser is sent to: [2](#0-1) 

No call to `Utils::ShopValidator.sanitize!` or `sanitize_shop_domain` occurs anywhere in `begin_auth`. Compare this to the two other grant flows that build a request host from a `shop:` parameter, both of which validate the domain first: [3](#0-2) [4](#0-3) 

`Utils::ShopValidator` exists specifically to enforce that a `shop` string resolves to a subdomain of a trusted Shopify domain (`myshopify.com`, `shopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`): [5](#0-4) [6](#0-5) 

The equality this breaks is: `host used to build the OAuth authorize redirect` should equal `a shop domain trusted/validated by ShopValidator`, exactly as is enforced for `ClientCredentials` and `RefreshToken`. In `begin_auth` this equality is never checked, so any string is accepted and turned into `https://#{shop}/admin/oauth/authorize?...`.

This is the same bug class as the reported `recoverERC20()` issue: one function in the codebase (`QuestBoard`/here, `ClientCredentials`/`RefreshToken`) correctly restricts/validates an identity-bound value, while a sibling function performing an analogous operation (`MultiMerkleDistributor`/here, `Oauth.begin_auth`) omits the same check.

### Impact Explanation
Because `shop` is not validated as a trusted Shopify domain, an application built on top of this gem that forwards a user-controlled `shop` value (which is the documented usage pattern shown in `docs/usage/oauth.md`, e.g. `shop = request.headers["Shop"]`) into `begin_auth` will generate an authorization redirect pointing to an attacker-chosen host (e.g. `https://evil.example.com/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=https://legitapp.com/callback&state=...`). The merchant's browser is redirected off-platform to a page that can impersonate the real Shopify consent screen, exposing the app's `client_id`, requested `scope`, and legitimate `redirect_uri` to the attacker, and enabling a forced/hijacked OAuth flow (the attacker can supply a phished, attacker-obtained authorization `code` back to the legitimate callback endpoint, since `redirect_uri` remains the app's own domain). This falls under the "forced OAuth completion" impact category.

### Likelihood Explanation
The likelihood depends entirely on the host application passing an untrusted `shop` value into `begin_auth`, which is exactly the pattern shown in this gem's own `docs/usage/oauth.md` example (`shop = request.headers["Shop"]`). No secret, token, or privileged access is required by the attacker — only the ability to influence the `shop`/`Shop` header value used to initiate login, which is the normal untrusted entry point of the OAuth flow.

### Recommendation
Validate `shop` in `Oauth.begin_auth` the same way it is validated in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, by calling `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) before it is used in `auth_base_uri`, raising `Errors::InvalidShopError` for untrusted domains.

### Proof of Concept
1. Host application implements the login route exactly as documented:
```ruby
def login
  shop = request.headers["Shop"]
  auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")
  redirect_to auth_response[:auth_route]
end
```
2. Attacker sends the victim merchant a link that triggers this login route with `Shop: evil.example.com` (header or equivalent query param depending on host app).
3. `Oauth.begin_auth` returns `auth_route = "https://evil.example.com/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=<SCOPES>&redirect_uri=https://legitapp.com/auth/callback&state=<NONCE>"` — no exception is raised, no domain check occurs, contrary to the check performed in `ClientCredentials.client_credentials` (`Utils::ShopValidator.sanitize!`).
4. The victim's browser is redirected to the attacker's host, which can present a fake Shopify consent screen and later relay a spoofed `code`/`hmac` combination to `legitapp.com/auth/callback`; the callback step (`validate_auth_callback`) does verify HMAC before completing OAuth, so the ultimate credential exchange is protected, but the initial redirect hijack and information disclosure (client_id, scope, redirect_uri exposure to an unintended host) still occurs due to the missing `shop` domain validation in `begin_auth`.
