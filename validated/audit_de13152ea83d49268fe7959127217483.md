### Title
Webhook shop attribution bypass via unsigned `shop`/`topic`/`webhook-id` headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only that the HMAC over the raw request body matches, but the `shop`, `topic`, `api_version`, and `webhook_id` values used to route and attribute the webhook are taken from unauthenticated HTTP headers that are never covered by that HMAC.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature from `verifiable_query.to_signable_string` and compares it against the received HMAC [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers with no cryptographic binding to the signed body [3](#0-2) .

`Registry.process` raises only if the HMAC is invalid, then immediately forwards the unauthenticated `request.shop` (and `topic`, `webhook_id`, `api_version`) into `WebhookMetadata` passed to the app's handler [4](#0-3) .

This breaks the intended identity binding: `HMAC-signed bytes == the tenant the app attributes the event to`. In practice, Shopify signs webhooks with the app's `client_secret`, which is shared across every shop that has installed the app — it is not shop-specific. Therefore any merchant who installs the app on their own shop legitimately receives webhook deliveries with a valid HMAC for their own shop's body. Because the `shop-domain` header sits outside the signed content, that same attacker can resend the identical `raw_body`/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `Registry.process` will accept it (HMAC still validates against the untouched body) and hand the handler a `WebhookMetadata` claiming the event came from the victim shop [5](#0-4) .

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to look up/attribute data (e.g., load the victim's session, update the victim's records, or make decisions keyed by shop), an attacker with access to only their own installed shop can forge events that are processed under another tenant's identity — a cross-tenant confusion/access primitive rooted entirely in this gem's webhook verification logic, since the gem asserts the request "did indeed come from Shopify" based solely on body HMAC while exposing `shop` as if it were equally trustworthy.

### Likelihood Explanation
Requires only that the attacker be a merchant who has legitimately installed the app (an "unprivileged internet user" relative to other tenants), no leaked secrets or elevated privileges needed. They simply capture a body+HMAC from a webhook delivered to their own shop and replay it with a modified `shop-domain` header.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-verified signable content (or otherwise cryptographically tie them to the signed body), or document/enforce that consumers must never trust `WebhookMetadata#shop` for tenant attribution without independently correlating it against the topic/body contents.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`; Shopify delivers a real webhook with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(app_client_secret, B)`), plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the same `B`/`H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` re-computes HMAC over `B` only and it matches, so `Registry.process` proceeds [6](#0-5) .
4. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` [5](#0-4)  and performs shop-scoped actions attributed to `victim.myshopify.com` despite the payload originating from the attacker's own shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
