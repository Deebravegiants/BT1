### Title
Fee-on-transfer token accounting mismatch in Tron IntentGatewayV2 escrow leads to under-collateralized escrow and fund freezing/theft - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of `IntentGatewayV2.placeOrder` computes the amount credited to escrow (`_orders[commitment][token]`) from the user-stated `order.inputs[i].amount` (minus protocol fee), instead of measuring the token balance actually received by the contract. For fee-on-transfer (FOT) tokens, this causes the escrow ledger to overstate the tokens actually held, exactly mirroring the reported bug class. Notably, the sibling contract `evm/src/apps/IntentGatewayV2.sol` was hardened against this exact issue (it snapshots balances before/after transfers and mutates `order.inputs` to the actual received amount before computing the commitment/escrow, with explicit fee-on-transfer regression tests in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`), but the Tron variant was not updated to match.

### Finding Description
In `placeOrder`, the commitment and `reducedInputs` are computed straight from the caller-supplied `order.inputs[i].amount`: [1](#0-0) 

Then, in the no-predispatch path, tokens are pulled via `safeTransferFrom` and the escrow is incremented using `reducedInputs[i].amount` — a value derived from the stated amount, not from any post-transfer balance check: [2](#0-1) 

The predispatch path has the same flaw: "dust" is computed as `balance - requiredAmount` from the *dispatcher's* balance before the final sweep transfer to the gateway, but the amount actually credited to escrow is again the pre-computed `reducedInputs[i].amount`, not the balance actually landing in the gateway after the final `IERC20.transfer` call (which can itself be taxed for FOT tokens): [3](#0-2) 

By contrast, the corrected `evm/src/apps/IntentGatewayV2.sol` measures `balanceOf` before and after every transfer, mutates `order.inputs[i].amount` to the actual received amount, and only then computes the commitment/protocol fee/escrow: [4](#0-3) 

This fix-vs-unfixed discrepancy is corroborated by dedicated fee-on-transfer regression tests that exist only against the main `IntentGatewayV2` (not the Tron copy): [5](#0-4) 

### Impact Explanation
Any user (an unprivileged order placer) submitting a `placeOrder` transaction with a fee-on-transfer input token on the Tron deployment will cause the gateway to record more escrowed tokens (`_orders[commitment][token]`) than it actually holds. Because escrow accounting is shared/aggregated per token across all orders (`_orders[commitment][token] += ...`), this creates a systemic shortfall: as more FOT-token orders are placed, the contract's on-chain balance for that token falls increasingly short of the sum of all outstanding escrow entries. This directly enables permanent freezing of funds for other users/solvers relying on that token's escrow (later withdrawals/cancellations/fills referencing the same token will revert or drain balance meant for other orders), and in adversarial scenarios a user can effectively cause insolvency of the escrow pool for a given token, harming counterparties. This matches the required impact bar of "concrete theft or permanent freezing of funds" via an unprivileged, single-transaction entry point (`placeOrder`).

### Likelihood Explanation
Likelihood is high: no special privileges are required, only calling `placeOrder` with an ordinary FOT-style ERC20 (which are common on Tron/EVM-compatible chains) as an input token. The bug is deterministic and reproducible on every such order, not an edge case requiring race conditions or governance compromise.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant: measure `balanceOf(address(this))` immediately before and after each `safeTransferFrom`/sweep call, use the actual delta as the received amount, mutate `order.inputs[i].amount` accordingly, and only then compute the commitment hash, protocol fee deduction, and the value added to `_orders[commitment][token]`. The same before/after accounting should be applied to the predispatch sweep path so the final gateway-side balance (post any second transfer fee) is what is credited to escrow, not the dispatcher-side balance.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and a fee-on-transfer ERC20 (e.g., 1% fee) analogous to `FeeOnTransferToken` used in the main-chain test suite: [6](#0-5) 
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no protocol fee.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` at line 459 actually delivers only 990e18 to the gateway (1% fee burned/redirected), but `_orders[commitment][token] += reducedInputs[i].amount` credits the full 1000e18 (since `reducedInputs = order.inputs` when `protocolFeeBps == 0`): [7](#0-6) [8](#0-7) 
4. The contract's actual FOT balance is 990e18 while escrow ledger states 1000e18 is owed for this order alone; repeating this with additional orders compounds the shortfall until a solver's legitimate fill/withdrawal against the escrowed amount reverts due to insufficient token balance, freezing funds for that and/or other orders sharing the same token bucket.

            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),

            output: output

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
