### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated headers. Because Shopify webhook HMACs are computed with the app's single, app-wide `client_secret` (identical for every shop that installs the app), any merchant who has legitimately installed the app can generate an authentic `(body, HMAC)` pair for their own shop and then replay it to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop, producing a cross-tenant identity confusion.

### Finding Description
`Registry.process` only validates that the HMAC in the request matches a signature computed over the raw body: `Utils::HmacValidator.validate(request)` at [1](#0-0)  calls `to_signable_string`, which is defined as `@raw_body` and nothing else: [2](#0-1) .

The `shop`, `topic`, and `webhook_id` values used afterward come straight from HTTP headers that are never mixed into the signable string: [3](#0-2) . Once HMAC validation passes, `Registry.process` builds `WebhookMetadata` directly from these unauthenticated header values and dispatches it to the app's handler: [4](#0-3) .

The identity binding broken here is: `HMAC-authenticated bytes (body) == identity used for tenant routing (shop header)`. These are not equal — the HMAC only proves "this body was signed with the app's secret," not "this body/shop pairing was produced by Shopify for this particular shop." Since the webhook HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every installed shop, any of the app's own merchants can trigger a webhook to their own shop, capture the legitimately-delivered `(body, HMAC)` pair, and re-POST it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a different (victim) shop. `Registry.process` will accept it as valid because the HMAC still matches the (unchanged) body, and will invoke the handler believing the webhook belongs to the victim shop's tenant.

### Impact Explanation
This crosses a tenant boundary that the HMAC is supposed to protect: the receiving application relies on `WebhookMetadata#shop` (sourced from `Request#shop`) to know which tenant's data the webhook body applies to (e.g. to look up the corresponding session/store record, write to that shop's data, or trigger tenant-scoped side effects). An attacker who is merely a regular, "unprivileged" (from the perspective of other tenants) merchant with their own valid app installation can force the app to process attacker-controlled webhook content under a victim shop's identity, without possessing the victim's access token, session, or the app's `client_secret`. This matches the Critical bucket of "cross-tenant access."

### Likelihood Explanation
The attacker only needs to be a normal merchant who has installed the app (no elevated privileges, no leaked secrets, no TLS interception). They can generate their own genuine webhook events (e.g., updating a product on their own store) to obtain a fresh, valid `(body, HMAC)` pair signed with the app's shared secret, then send a forged POST to the app's public webhook endpoint with a different `shop-domain` header. This requires no cryptographic breakage — only that the library's shop identity is taken from an unauthenticated header while the same body/secret pair is valid for all shops.

### Recommendation
Bind the shop identity to the signed content, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the HMAC:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in the signable string used by `Request#to_signable_string`, matching what is actually trusted downstream, or
- Cross-check the `shop` header value against an app-maintained registry of shops for which this app expects to receive webhooks (e.g., only accept webhooks for shops with an active, stored session/installation), rejecting shop values that don't correspond to a known installation, or
- Document prominently, and enforce in code, that `WebhookMetadata#shop` must never be trusted as an authenticated identity by itself and must always be cross-validated against the app's own installation records before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, thereby causing Shopify to send real HMAC-signed webhooks (e.g. `products/update`) to the app's public webhook endpoint using the app's single shared `client_secret`.
2. Attacker captures one such delivered request: raw body `B` and header `x-shopify-hmac-sha256: H` (a valid HMAC of `B` under the app's secret), along with `x-shopify-topic` and `x-shopify-webhook-id`.
3. Attacker crafts a new POST to the same webhook endpoint, reusing body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`= B`) and finds it matches `H` — validation succeeds [1](#0-0) .
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [5](#0-4) , causing the app to process attacker-controlled webhook data as if it originated from the victim tenant.
