The report I found concerns a genuine equality break in this repo's withdrawal-status matching logic, not the WooCommerce HTML-injection bug. Here's the analysis and finding.

### Title
PoA Bridge status matching by assetId only causes duplicate withdrawal status/hash reports for batched same-token withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves withdrawal completion status/tx hash by matching the POA API response purely on `assetId`, ignoring the `index` field that is supposed to disambiguate multiple withdrawals in the same NEAR transaction. When a caller batches two or more withdrawals of the same token (to different destination addresses) into a single intent transaction, every one of those withdrawals resolves to the same (first) matching API record, reporting an identical `txHash`/`completed` status for withdrawals that are actually distinct, unconfirmed transfers.

### Finding Description
`createWithdrawalIdentifiers` in [1](#0-0)  assigns each withdrawal an `index` per bridge route so bridges can disambiguate multiple withdrawals sharing one NEAR transaction hash. However, `PoaBridge.describeWithdrawal` never uses `args.index`; it calls `findMatchingWithdrawal`, which matches strictly by `assetId`: [2](#0-1) 

The matching helper explicitly documents this limitation: [3](#0-2) 

If a user submits two withdrawals of the same token (same `assetId`) to two different destination addresses in one NEAR intent transaction (both routed to `PoaBridge`, i.e., `route = "poa_bridge"`), `createWithdrawalIdentifiers` will produce `index: 0` and `index: 1` for them, but both calls to `describeWithdrawal` query the same `tx.hash` and `findMatchingWithdrawal` returns the array's `.find()` first match for that `assetId` — the same underlying withdrawal record — for both. `watchWithdrawal` in [4](#0-3)  then reports the same `{status: "completed", txHash}` for both withdrawal indices, even though only one of the two on-chain transfers may actually be finalized (or they finalize with two different destination tx hashes).

This breaks the equality "status/hash reported for withdrawal N == the actual on-chain outcome for withdrawal N": an integrator relying on `describeWithdrawal`/`waitForWithdrawalCompletion` per-withdrawal result to mark a specific withdrawal (to a specific destination address) as settled will incorrectly mark the second withdrawal as completed using the first withdrawal's hash, potentially crediting/reconciling it prematurely or reusing a transaction hash that belongs to a different recipient.

### Impact Explanation
This matches the High-impact class "a status or hash misreport making an integrator credit or refund twice." An integrator polling per-index withdrawal completion (as the SDK's own `withdrawal-watcher.ts`/`waitForWithdrawalCompletion` APIs are designed to support) would receive a false "completed" status with a stale or wrong `txHash` for the second (and any further) same-token withdrawal batched in one transaction, potentially causing duplicate settlement/credit logic downstream, or masking that the intended destination address withdrawal is still pending/failed.

### Likelihood Explanation
This requires only ordinary use of a documented, supported feature — batching multiple withdrawal intents in a single call (`sdk.createWithdrawalIntents`/`processWithdrawal` support arrays of `withdrawalParams`) — with two withdrawals of the same token via the PoA route. No malicious actor, RPC, relayer, or bridge operator behavior is required; it is triggered by normal caller input recognized and explicitly flagged as unhandled in the code comment itself.

### Recommendation
Extend the POA bridge withdrawal-status API/matching to disambiguate by index/amount/destination (as the code comment suggests: sort API results and withdrawal params by amount, since fees are constant per token) or reject/refuse batching multiple same-assetId withdrawals through `PoaBridge` until the API supports precise disambiguation, so `describeWithdrawal` cannot report one withdrawal's status/hash for another.

### Proof of Concept
1. Call `sdk.createWithdrawalIntents` (or `processWithdrawal`) with `withdrawalParams: [{assetId: "nep141:btc.omft.near", amount: A, destinationAddress: addr1, ...}, {assetId: "nep141:btc.omft.near", amount: B, destinationAddress: addr2, ...}]`, both resolving to `PoaBridge`.
2. `createWithdrawalIdentifiers` assigns `index: 0` to addr1's withdrawal and `index: 1` to addr2's withdrawal, both referencing the same NEAR `tx.hash` [5](#0-4) .
3. Once the POA API indexes only the first withdrawal as `COMPLETED` (with `transfer_tx_hash: "hashA"`), call `describeWithdrawal` for both `index: 0` and `index: 1` — `findMatchingWithdrawal` returns the same record for both because it matches on `assetId` alone [6](#0-5) , so `watchWithdrawal` reports `{status: "completed", txHash: "hashA"}` for addr2's withdrawal even though its actual transfer is still pending or has a different hash.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
