### Title
Webhook `shop-domain` (and topic/webhook-id) headers are trusted but not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` proves nothing about the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers. `Registry.process` accepts these headers at face value and hands them straight to the app's `WebhookHandler` as authenticated `WebhookMetadata`, breaking the identity binding `hmac(body) == hmac(body)` versus the implicit claim `shop header == originating shop`.

### Finding Description
`Registry.process` performs exactly one check before dispatching to the handler: [1](#0-0) 
This delegates to `HmacValidator.validate`, which calls `verifiable_query.to_signable_string` to build the string that is HMAC-verified: [2](#0-1) 
For `Webhooks::Request`, `to_signable_string` is defined as just the raw body: [3](#0-2) 
Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from attacker-controllable HTTP headers with no cryptographic binding to the signed body: [4](#0-3) 
These unverified values are then packaged as `WebhookMetadata` and passed to the app's handler as if they were verified: [5](#0-4) 
The documentation explicitly tells integrators that `Registry.process` "will verify the request did indeed come from Shopify," and that `data.shop` is "The shop domain of the webhook" - i.e., it is presented as a trusted, verified identifier for the sample handler to key persistence/business logic off of: [6](#0-5) [7](#0-6) 

Because only the body is signed, an attacker who possesses one valid `(raw_body, hmac)` pair for any topic - for example by installing the target app on their own store and capturing a real webhook delivery, since HMAC verification only requires knowledge of `api_secret_key` which the attacker does not have but the *replayed bytes* are still valid for any header combination - can resend that exact body/HMAC pair while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) with a different shop's domain. `HmacValidator.validate` will still pass because it only checks the body bytes against the secret, and `Registry.process` will dispatch the forged metadata to the handler as if it genuinely originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the equality the gem should enforce is `hmac_verified(body) ∧ header.shop == shop_that_generated(body)`, but it only proves the first conjunct. Any app that follows the documented pattern of using `data.shop` to look up/act on a specific merchant's stored session, token, or records (exactly as shown in the gem's own sample handler, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into attributing an attacker-supplied payload to an arbitrary victim shop domain. Depending on the topic replayed (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`), this can trigger deletion of a victim's stored access token/session, spurious GDPR redaction actions, or corruption of another merchant's data records - a cross-tenant impact.

### Likelihood Explanation
The attacker only needs to be an unprivileged user who can install the target app on their own (attacker-controlled) shop - a normal, unprivileged capability for any public Shopify app - and capture one legitimate webhook delivery to obtain a valid `(body, hmac)` pair. No access to `api_secret_key`, access tokens, or any privileged credential is required; only the header can be freely rewritten before replay to the app's public webhook endpoint.

### Recommendation
Bind the identity-carrying headers into the signed material, or independently verify `shop` against a known/expected value before trusting it:
- Since Shopify's own HMAC only signs the body, the gem should not present `shop`/`topic`/`webhook_id` header values as verified data. At minimum, document (and ideally enforce) that consuming applications must cross-check `data.shop` against an already-established/authorized shop record (e.g., an existing session for that shop) before acting on webhook content, rather than trusting the header as an authenticated identifier.
- Consider validating that the `shop` header corresponds to a shop with an active registration/session recognized by the app before dispatch, since `Registry.process` has no such check today.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery for topic `app/uninstalled` with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `B` and the same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body per [8](#0-7) ; `hmac` and `to_signable_string` are computed purely from the (unchanged) body, so `HmacValidator.validate` returns `true`.
4. `Registry.process` dispatches to the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)` per [9](#0-8) .
5. The app's handler, following the documented pattern, treats `victim.myshopify.com` as verified and takes the `app/uninstalled` action against the victim's stored session/token - despite the victim never having sent this webhook.
