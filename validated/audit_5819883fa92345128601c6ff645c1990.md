### Title
Order escrow permanently stuck when a gateway's registered instance changes while a `RedeemEscrow`/`RefundEscrow` message is in flight - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2`'s `onAccept` routes cross-chain `RedeemEscrow` and `RefundEscrow` requests through `_authenticate(incoming.request)` before releasing escrowed funds via `_withdraw`. Authentication is checked against the `_instances` mapping, which records the single registered peer gateway address per destination chain and can be rewritten at any time by a `NewDeployment`/`UpdateParams` governance message. If that mapping is updated (a normal, non-malicious redeployment/rotation operation) while a legitimate `RedeemEscrow` or `RefundEscrow` message for an already-placed order is still in flight, the message will be authenticated against the *new* instance address on delivery and fail permanently, exactly like the referenced `AutoCompound.setVault` bug where disabling a vault leaves users with no path to reclaim already-escrowed balances.

### Finding Description
`IntentsBase._instances` maps `keccak256(stateMachineId) => address`, holding the single gateway instance trusted for a given chain [1](#0-0) . `onAccept` in `ExtrinsicIntents.sol` handles `RedeemEscrow`/`RefundEscrow` by first calling `_authenticate(incoming.request)` and then unconditionally calling `_withdraw`, which is the *only* code path that releases the tokens held in `_orders[commitment][token]` back to a solver or user [2](#0-1) . Registration/updates of that trusted instance are themselves delivered as ordinary cross-chain governance messages (`NewDeployment`, `UpdateParams`), gated only by "must come from Hyperbridge" [3](#0-2) , and can land at any time, independent of in-flight order-settlement messages.

Because escrow accounting (`_orders`) and settlement authentication (`_instances`) are decoupled, once a chain's registered instance is rotated, any `RedeemEscrow`/`RefundEscrow` request that was dispatched against the *previous* instance address — for an order that already has funds locked in `_orders` — will be rejected by `_authenticate` on delivery, because `request.from` no longer matches the freshly-updated `_instances` entry. Unlike the `AutoCompound` report where the mitigation was to make vault whitelisting non-reversible, `IntentsBase` has no equivalent "leftover withdrawal" bypass function: `_withdraw` is reachable *only* through the authenticated `onAccept` path, so there is no independent recovery route for the affected commitment's escrow once the authenticating instance is superseded.

### Impact Explanation
This permanently freezes user/solver funds already locked in escrow for orders whose settlement message becomes unauthenticatable after an instance rotation — a direct funds-freezing outcome analogous to the M-10 finding, where legitimate users lost access to funds because of an administrative reconfiguration on the counterpart contract, not because of any fault of their own. Given `_withdraw` is the sole release path for `_orders` balances, there is no fallback (no analog of `withdrawLeftoverBalances`), making the freeze permanent rather than temporary.

### Likelihood Explanation
Gateway instance rotations are an expected, routine governance operation (contract upgrades, redeployments, chain-identifier changes) rather than a rare edge case, and cross-chain message delivery timing is not synchronized with governance timing — a relayer can deliver a stale `RedeemEscrow`/`RefundEscrow` message any time after a rotation lands. This mirrors the "confirmed, Medium" classification of the original finding: a DoS/freeze triggered by normal administrative operations rather than malicious intent.

### Recommendation
Before switching `_instances[chain]` to a new address, ensure no in-flight `RedeemEscrow`/`RefundEscrow` requests exist for orders still holding non-zero `_orders` balances against the old instance, or retain validation against a bounded set of prior instance addresses so already-dispatched settlement messages remain deliverable. Alternatively, add a fallback recovery function (mirroring the recommended `AutoCompound` fix) allowing the order's beneficiary to reclaim escrow once a commitment's settlement message can no longer authenticate, gated purely by escrow balance and beneficiary identity rather than the current `_instances` mapping.

### Proof of Concept
1. User places a cross-chain order on the source chain; `_orders[commitment][token]` is credited with escrowed input tokens.
2. Order is filled/cancelled on the destination chain, and a `RedeemEscrow`/`RefundEscrow` POST request is dispatched back toward the source gateway, carrying `from = <old destination-gateway address>`.
3. Before the relayer delivers this message, Hyperbridge governance dispatches `NewDeployment`/`UpdateParams` to the source gateway, rotating `_instances[keccak256(destinationChain)]` to a new address (a normal maintenance action, e.g., an upgrade to a new proxy or gateway redeployment).
4. The relayer now delivers the original `RedeemEscrow`/`RefundEscrow` message to `onAccept`; `_authenticate` compares `request.from` against the *new* `_instances` value and reverts.
5. The message can never be authenticated again (its `from` field is fixed at dispatch time and will never match the rotated instance), and no other function exposes `_orders[commitment][token]` for withdrawal, leaving the escrow permanently locked in the gateway.

*Note: I could not directly inspect the body of `_authenticate` (it lies just past the code range returned in my last tool call) to confirm its exact comparison logic beyond the `_instances` mapping and the calling pattern shown in `onAccept`; this should be verified directly against `IntentsBase.sol`'s `_authenticate` implementation before treating this as fully confirmed.*

        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
