### Title
`CallDispatcher.dispatch()` is a fully unrestricted external-call gateway, allowing anyone to drain any balance left in the shared dispatcher contract - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is the shared, singleton "flash-call" executor used by `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2` (EVM and Tron variants) to run arbitrary calldata against arbitrary target addresses on behalf of bridged transfers and cross-chain orders. Its `dispatch(bytes)` entry point has no access-control modifier at all — any externally owned account or contract can invoke it directly, supplying its own `Call[]` array, exactly as the referenced Opyn `Controller._call` finding describes for an unrestricted, callee-agnostic external call performed by a shared protocol contract.

### Finding Description
`CallDispatcher.dispatch` is declared `external` with no `onlyX` guard and no caller allow-list: [1](#0-0) 

It also exposes an unrestricted `receive()` that accepts arbitrary native-token deposits from anyone: [2](#0-1) 

`CallDispatcher` is used as a shared, well-known, singleton contract by every bridge app (its address is even referenced by a fixed constant such as `CALL_DISPATCHER` in the docs) to execute user-supplied calldata while temporarily holding bridged tokens or ETH mid-transaction, e.g. in `IntentGatewayV2.placeOrder`: [3](#0-2) 

and in `IntentsBase._execute`, which sweeps back only the tokens explicitly listed in `order.output.assets`: [4](#0-3) 

Because the sweep is bounded to `outputsLen` (the tokens the order declared), any balance that ends up on the `CallDispatcher` from a postdispatch/predispatch call sequence that is *not* one of the declared output/input assets — for example, dust produced by an intermediate DEX hop, a different token returned by a swap, native ETH remainder, or funds accidentally/mistakenly sent straight to the well-known dispatcher address — is left sitting on the contract after the transaction completes. Since `dispatch()` has no caller restriction, any third party can subsequently call it directly with `Call({to: attacker, value: <residual balance>, data: <transfer-out calldata>})` and pull that value out, exactly as the Opyn report describes forcing a shared, privileged contract to perform an undesired external call on behalf of its own identity to an attacker-chosen, non-whitelisted destination.

This is a structural analog of the Opyn `Controller._call` issue: a shared contract (`Controller` / `CallDispatcher`) performs a generic external call to a caller-supplied address with no whitelist and no interface check, so its own identity/holdings become attacker-reachable by anyone who can reach the dispatch entry point — the only difference is that in Opyn the caller must go through `operate()`, whereas here `dispatch()` is directly public.

### Impact Explanation
Any native ETH or ERC-20 tokens that transiently or accidentally accumulate on the shared `CallDispatcher` (residual dust from swaps not covered by the bounded sweep loop, rounding remainders, or funds sent directly to this documented, fixed address by users/relayers/tooling) can be permanently and irrecoverably stolen by any unrelated third party, since `dispatch()` performs `to.call{value: call.value}(call.data)` from the dispatcher's own balance with no restriction on `msg.sender`. This is concrete theft of funds affecting every app that shares this dispatcher instance (HFT, WHFT, IntentGatewayV2 on both EVM and Tron).

### Likelihood Explanation
Likelihood is Medium: exploitation does not require any privileged position, only that some value be resting on the `CallDispatcher` at a given moment (dust from partial swaps, rounding, tokens outside the declared output set, or a stray transfer to the address). Given `CallDispatcher` is deployed once and reused across many independent bridge/intents flows and chains, and its address is publicly documented and hard-coded into integration examples, such balances are a realistic and recurring occurrence, and an attacker only needs to monitor the contract's balance and front-run/opportunistically call `dispatch()`.

### Recommendation
Restrict `CallDispatcher.dispatch()` so it can only be invoked by an authorized, whitelisted set of caller contracts (e.g. the registered `HyperFungibleToken`/`WrappedHyperFungibleToken`/`IntentGatewayV2` instances), or require any residual balance to be swept back to a governance-controlled treasury rather than being permanently claimable by an arbitrary caller. At minimum, add a reentrancy/caller check and ensure no value is ever left resting on the dispatcher between transactions (e.g. by sweeping the dispatcher's full balance, not just the declared output/input token set, at the end of every `dispatch`-driven flow).

### Proof of Concept
1. A solver constructs an `Order` whose `output.call` (postdispatch) swaps the solver-provided output token through an intermediate token/route that leaves a small residual balance of a token not listed in `order.output.assets` on the `CallDispatcher` (or simply leaves ETH dust due to a rounding step), as in `IntentGatewayV2Test.testPostdispatchTokenSweep` where only the declared assets are swept back.
2. Because `IntentsBase._execute`'s sweep loop only iterates `outputsLen` (the declared output tokens), the residual balance of the undeclared token/ETH remains on `CallDispatcher` after the transaction.
3. Any external account calls `CallDispatcher.dispatch(abi.encode([Call({to: attacker, value: dispatcherEthBalance, data: ""})]))` or, for an ERC-20 remainder, `Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualBalance)})` — this succeeds because `dispatch` has no caller restriction, transferring the residual value to the attacker.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
