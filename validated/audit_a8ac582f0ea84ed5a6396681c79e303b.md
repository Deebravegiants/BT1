### Title
Position NFT transferable to an unrecoverable address permanently locks the account's collateral and debt - (File: contracts/position-nft/src/contract.rs)

### Summary
`PositionNft` is a stock OpenZeppelin non-fungible token: `transfer`/`approve` come from the `NonFungibleToken` trait with no recipient validation. The token id *is* the controller account id, so whoever holds the NFT controls the entire account — collateral, debt, and delegate grants. If the holder transfers the NFT to an address that can never produce `require_auth` for user operations — most concretely the pool contract or the controller itself — the account's supplied collateral is permanently frozen. There is no recovery path: the controller cannot move the NFT (mint and burn are controller-only, but transfer is not), and the pool/controller have no sweep or rescue entrypoint for protocol-owned assets. This is the same class as PoolTogether's backdated `_startTimestamp`: a single user-supplied, unvalidated parameter creates an irreversible state with no recovery function and total loss of the funds at stake.

### Finding Description
`contract.rs` documents that the NFT is "the stock OpenZeppelin non-fungible interface" and only overrides `mint`, `burn`, `renew`, `upgrade`, and `token_uri`. Neither `transfer` nor `approve` is intercepted, so the OZ `Base::transfer` runs with no check on `to`. [1](#0-0) 

Meanwhile the protocol already recognizes this exact stranding class elsewhere: `borrow`/`withdraw` reject `recipient` equal to the pool or the controller because "the pool debits cash without its balance moving, and the controller holds funds no balance-delta measurement can ever claim." [2](#0-1)  The same reasoning applies a fortiori to NFT `to`: every monetary controller entrypoint (`withdraw`, `borrow`, `repay` flows requiring account authority, delegate grants, `update_account_threshold`) requires auth from the NFT holder or an active delegate. A pool or controller address cannot sign, and existing delegates can at most borrow *to* a recipient — but delegates were granted by the prior owner and revocation/recipient checks don't let them extract supply either (they can borrow/withdraw "to their chosen recipient," which is a documented authority risk, but once the NFT is transferred the old owner's grants go inactive per the threat model: delegate grants "become inactive while someone else holds the NFT"). [3](#0-2) 

The NFT is never burned and cannot be transferred out again, so the position — all supply shares and any debt — is bricked permanently. `burn` is controller-only precisely because the controller must be able to retire empty accounts, but nothing in it or elsewhere rescues collateral of an account whose NFT is owned by a non-signing address. [4](#0-3) 

### Impact Explanation
Permanent freezing of the entire position: every supplied asset and all accrued yield on the account becomes unreachable by anyone. If the account carries debt, that debt is also uncollectible (no liquidation target authority needed — liquidation is permissionless — but collateral that can't move still serves liquidation; the loss is borne by the NFT transferor, whose collateral is locked and whose equity can only be extracted by liquidators over time). This matches the H-02 class: user-side loss of funds with no recovery function, judged High because a UI bug or simple mistake causes complete loss.

### Likelihood Explanation
A user or a poorly-built UI/integration supplying the pool address, the controller address, or a typo'd contract address as the `transfer` recipient is a plausible, single-transaction mistake — exactly the "simple mistake" scenario the judge used to rate the PoolTogether analog High. It requires no attacker, no race, and no privileged action; it is fully reachable by the ordinary `transfer` entrypoint.

### Recommendation
Reject transfers (and approvals that would enable them) where `to` is the pool, the controller, or the NFT contract itself — mirroring the existing `INVALID_FLASHLOAN_RECEIVER` guard on `borrow`/`withdraw`. Optionally require `to` to be a non-contract address or provide a controller-mediated rescue for accounts whose NFT is provably held by a protocol contract.

### Proof of Concept
1. Alice supplies 10,000 USDC into a spoke; her position is `token_id = N` on `PositionNft`.
2. Alice (or a buggy wallet) calls `PositionNft::transfer(alice, pool_address, N)` — or `approve` + `transfer_from` to the controller address. `contract.rs` applies no recipient check, so the transfer succeeds. [5](#0-4) 
3. The pool/controller cannot `require_auth`, so no `withdraw`, `borrow`, `repay`, delegate grant, or `update_account_threshold` can ever execute for account `N`. Delegate grants stamped to Alice are inactive while the contract holds the NFT.
4. Nothing can send the NFT back: `mint`/`burn` are controller-gated and there is no controller entrypoint that calls `transfer` on the NFT; the pool has no token-recovery entrypoint for the NFT.
5. Result: the 10,000 USDC supply (plus yield) is permanently locked in pool custody, and the debt, if any, can only be serviced by liquidation. No recovery function exists — the exact H-02 failure shape.

```rust
    /// Burns `token_id` without the holder's authorization. Controller-only.
    ///
    /// Not the OZ `Burnable` extension: `Base::burn` calls
    /// `from.require_auth()`, and the controller must burn when liquidation
    /// empties an account without the owner's signature. This replicates
    /// `Enumerable::burn` (v0.7.1) without that auth: `Base::update` removes the
    /// owner and approval and decrements the holder's balance. The enumeration
    /// helper updates owner enumeration, total supply and global enumeration.
    ///
    /// Renews the instance TTL on every account deletion.
    pub fn burn(e: &Env, token_id: u32) {
        controller(e).require_auth();
        renew_instance(e);
        let owner = Base::owner_of(e, token_id);
        Base::update(e, Some(&owner), None, token_id);
        emit_burn(e, &owner, token_id);
        Enumerable::remove_from_enumerations(e, &owner, token_id);
    }
```
