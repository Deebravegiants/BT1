### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) fields are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic for a given shop as soon as the HMAC validates, but the HMAC signature only ever covers the raw request body, never the `shop` header that the rest of the pipeline treats as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read straight from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header: [1](#0-0) [2](#0-1) 

`shop` (and `topic`, `webhook_id`, `api_version`) is read from a separate, unsigned header: [3](#0-2) 

`Utils::HmacValidator.validate` recomputes the signature purely from `to_signable_string` (the body) and the app's shared `Context.api_secret_key`, and compares it to the received value: [4](#0-3) 

`Registry.process` gates entirely on this body-only HMAC check, then forwards the *unverified* `request.shop` straight to the app's handler as the authoritative tenant identity: [5](#0-4) 

The documented contract explicitly promises shop-level authenticity: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook," and the handler is told `data.shop` is "The shop domain of the webhook." [6](#0-5) [7](#0-6) 

Because `Context.api_secret_key` (the app's `client_secret`) is identical for every shop that installs the app, the HMAC over a given body is shop-independent: **HMAC(body) == HMAC(body)** regardless of which shop the body originated from. Consequently, the binding the library implicitly promises — *"the shop that produced a valid HMAC" == "the shop attributed to the webhook payload"* — does not actually hold, because the `shop` value is never part of the signed bytes.

### Impact Explanation
Any attacker who can legitimately install the same app on a shop they control (or intercept/replay any previously delivered webhook body+HMAC pair) can capture a valid `(raw_body, hmac)` pair and resend it to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header (e.g., a victim's shop domain). `HmacValidator.validate` still passes because it never inspects `shop`, and `Registry.process` hands the forged shop identity to the handler unchanged. This is a cross-tenant boundary break: the app cannot trust `data.shop` even though the gem's own documentation and validation flow imply it can, which can lead to data being written/attributed to the wrong merchant, GDPR/redact webhooks being misapplied, or forged state changes scoped to a victim tenant — all without ever needing the victim's or the app's credentials.

### Likelihood Explanation
The attacker only needs to be able to install the target app on any shop they control (trivial for public apps) or otherwise obtain one valid webhook delivery, then replay it against the app's public endpoint with a modified `shop` header — no access token, `client_secret`, or privileged account is required. This is directly reachable through the gem's documented `Registry.process` API with unprivileged internet-facing HTTP requests.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`/`api_version`) as part of the signed payload verification — e.g., verify a signed combination of body+shop rather than trusting the `shop` header independently of the HMAC, or require callers to cross-check `request.shop` against a shop known to have an active/registered webhook subscription for that specific `webhook_id`/topic before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`. Shopify sends a legitimate webhook (e.g. `orders/create`) to the app's callback URL with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker captures `B` and `H` (e.g., via their own server logs, since it was delivered to infrastructure they control).
3. Attacker crafts a new HTTP POST to the same app endpoint, reusing body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H})` is constructed and passed to `Registry.process`.
5. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(client_secret, B)` and it matches `H` (body unchanged), so validation passes at [8](#0-7) .
6. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and processes/persists data as if it legitimately originated from the victim shop, even though it never did.
