The reported bug class is a missing ownership check on an attacker-supplied `tokenId`/`posId` parameter that indexes into another user's per-position collateral mapping (`PosManager.__posCollInfos[_posId].ids[_wLp]`), letting one position's owner drain LP tokens tied to a different position's `tokenId`. This requires a data model where state is keyed by a caller-controllable ID that maps back to a specific user's deposited collateral, and the vulnerable function trusts that ID without checking it belongs to the caller's own record.

alt.fun's in-scope reachable surface does not have this shape:
- `FeeVault.claim()` pays out `creatorBalance[msg.sender]` — keyed by `msg.sender` directly, not by a caller-supplied ID, so there is no ID to spoof [1](#0-0) .
- `FeeVault.claimProtocol()` and `sweepDonations()` always pay a fixed, admin-set `feeTo` address regardless of caller, so there's no arbitrary recipient/ID to exploit [2](#0-1) .
- `Bonding.transferCreator` is gated by an explicit creator check (`NotCreator` revert, confirmed by `test_transferCreator_onlyCreator`), so it cannot be called on behalf of a token the caller doesn't own [3](#0-2) .
- `Bonding.triggerGraduation` and `finalizeGraduation` operate on global per-token state (`tokenInfo[tokenAddress]`, `pendingGraduation[tokenAddress]`) rather than per-user position records, and are intentionally permissionless by design — there is no "victim position" whose collateral could be misdirected to an unrelated caller [4](#0-3) .
- `LPLock.recordLock` is a one-shot, locker-gated call from `Bonding` only, with no user-facing ID-based withdrawal path to spoof [5](#0-4) .

None of alt.fun's permissionless entry points (`Zap.createToken/buy/sell`, `Bonding.triggerGraduation/finalizeGraduation/transferCreator`, `FeeVault.claim/claimProtocol/sweepDonations`) accept a caller-supplied ID that indexes into another user's isolated collateral/position record the way `PosManager#removeCollateralWLpTo`'s `_tokenId` does. The protocol's state model (keyed by token address or `msg.sender`, not by attacker-choosable position/token IDs) doesn't reproduce the root cause of the H-02 report, so there is no valid analog in this codebase.

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.

        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
