### Title
Cleartext logging of embedded URL credentials in HTTP/Bridge pipeline task debug/trace logs - ([File: core/services/pipeline/task.http.go], [File: core/services/pipeline/task.bridge.go])

### Summary
CVE-2019-15508 describes an Octopus Tentacle bug where a proxy password configured for a web request is written to the deployment log in cleartext because the deployment log printing logic did not redact the credential embedded in the request configuration. The analogous bug class here is unredacted logging of secrets that are embedded inside a request URL (e.g., `https://user:password@host/path`) when a pipeline task executes an outbound HTTP request, since Go's `net/url.URL.String()` re-serializes the userinfo component (including the password) verbatim.

### Finding Description
`HTTPTask.Run` in `core/services/pipeline/task.http.go` resolves the task's `URL` parameter (which can be a job-spec-supplied literal string or a variable-interpolated value) and then logs it directly via `url.String()`: [1](#0-0) 

Because `url.String()` includes any userinfo (`user:password@`) present in the URL, if a job spec author configures an HTTP task (or a Bridge task) with a URL containing embedded basic-auth credentials, those credentials are written verbatim into the node's log output at `Debug` level.

The same pattern exists in the Bridge task, which logs the resolved bridge URL at `Trace` level right before making the outbound request: [2](#0-1) 

Additionally, `runner.go`'s `run` and `executeTaskRun` methods opportunistically attach the full task output/result (`resultValue`, `resultString`, `resultHex`) and, when `VerboseLogging` is enabled, the full `Run.Inputs`/`Outputs`/`Meta` to log lines, which can further amplify credential exposure if secrets flow through task inputs/outputs: [3](#0-2) [4](#0-3) 

Unlike the node's dedicated secrets model (`models.Secret`/`models.SecretURL`, which format as `xxxxx` when stringified) used for `Secrets.toml` config values (`core/store/models/secrets.go`), and unlike the web request/response body sanitization done in `core/web/router.go`'s `isBlacklisted`/`redact` helpers for API request logging, there is no equivalent redaction applied to job-spec-derived URLs at the pipeline-task logging call sites. A URL string is treated as a plain, safe-to-log value even though it may legitimately contain a password for basic-auth-protected data sources.

### Impact Explanation
Any actor able to create or edit a job spec containing an `http` or `bridge` task — the standard, expected way node operators configure data-fetching pipelines — that uses a URL with embedded basic-auth credentials will have that credential written to the node's log files in cleartext at Debug/Trace level. This mirrors the CVE's core defect (a legitimate node configuration value containing a secret gets written unredacted to a log), and it is directly reachable through the normal job-creation workflow rather than requiring any privileged/administrative or attacker-controlled node/network condition. Anyone with read access to node logs (which is broader than access to the job spec store, e.g. shipped to centralized logging, support bundles, or log-file volumes) can recover the credential.

### Likelihood Explanation
Exploitability depends on: (1) the node running at `Debug` (HTTP task) or `Trace` (Bridge task) log level, which is a common operational/troubleshooting configuration rather than a hardened default, and (2) a job spec that intentionally or accidentally embeds credentials directly in the URL instead of using the `Headers` parameter for auth. This is a realistic but not universal configuration; it requires no malicious peer, no network-layer manipulation, and no elevated node role beyond the ability to author job specs, which is the standard job-creation path.

### Recommendation
- Redact userinfo (username/password) from any URL before it is passed to a logger in `task.http.go` and `task.bridge.go` (e.g., strip `url.User` or replace it with a placeholder before calling `.String()` for logging purposes, while still using the real URL for the actual HTTP request).
- Apply the same redaction to any other pipeline task or telemetry path that logs a caller-supplied URL (`BridgeTelemetry`, `RunResultSaver` tracew).
- Consider extending the existing secret-redaction pattern already used for node configuration (`models.SecretURL`/`config.SecretURL`) or the web-layer blacklist redaction (`core/web/router.go`'s `isBlacklisted`) to pipeline-task logging call sites.
- Document/enforce that credentials for HTTP/Bridge tasks be passed via `Headers` (which are not logged) rather than embedded in the URL.

### Proof of Concept
1. Configure a node with `Log.Level = "debug"`.
2. Create a job with an `http` task whose `url` parameter is set to `https://myuser:mysecretpassword@example.com/api/data`.
3. Trigger the job run (e.g., via the standard job-run trigger).
4. Observe the node log output for the "HTTP task: sending request" line at `core/services/pipeline/task.http.go:89-95` — the log contains `url=https://myuser:mysecretpassword@example.com/api/data`, exposing the password in cleartext in the log file.
