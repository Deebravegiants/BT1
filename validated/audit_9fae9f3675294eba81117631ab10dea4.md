This confirms the critical finding. `ShopValidator.sanitize!` was added specifically to `client_credentials.rb`, `refresh_token.rb`, `token_exchange.rb`, and `storefront.rb` — but it was never wired into `ShopifyAPI::Auth::Oauth.begin_auth` / `auth_base_uri`. The `shop` parameter there is used raw to construct the OAuth authorization redirect URL that carries the CSRF `state` nonce.

### Title
Unsanitized `shop` in `Oauth.begin_auth` breaks the "shop is a trusted Shopify domain" binding, enabling CSRF-nonce leak and forced OAuth completion via open redirect - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the authorization redirect URL directly from the caller-supplied `shop` string without passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`, unlike every other OAuth entry point in the same commit (`client_credentials.rb`, `refresh_token.rb`, `token_exchange.rb`, `Clients::Graphql::Storefront`). This breaks the identity binding "the shop the OAuth flow targets == a verified `*.myshopify.com` (or other trusted Shopify) domain" that `ShopValidator` was specifically introduced to enforce elsewhere in the gem.

### Finding Description
`begin_auth` accepts a raw `shop:` string and passes it straight to the private `auth_base_uri` helper: [1](#0-0) 

```ruby
def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
```

No call to `Utils::ShopValidator.sanitize!` occurs anywhere in `begin_auth`: [2](#0-1) 

Compare this to the sibling flows that were hardened in the same release (per `CHANGELOG.md` entry for PR #1443 "Add `ShopifyAPI::Utils::ShopValidator`"), all of which call `Utils::ShopValidator.sanitize!(shop)` before using the shop value to build a request: [3](#0-2) [4](#0-3) 

`ShopValidator` exists precisely to reject values like `"attacker.example"`, `"myshopify.com.evil.com"`, or `"shop.myshopify.com@evil.com"`: [5](#0-4) 

Because `begin_auth` skips this check, the documented calling pattern (`shop = request.headers["Shop"]` from `docs/usage/oauth.md`) means any unprivileged internet user can supply an attacker-controlled hostname as `shop`, and the gem will construct:

```
https://<attacker-controlled-host>/oauth/authorize?client_id=...&scope=...&redirect_uri=<app-callback>&state=<CSRF-nonce>&grant_options[]=...
``` [6](#0-5) 

The equality that should hold is: `shop used to build auth_route` == `a ShopValidator-verified Shopify domain`. Before the request: `shop` is attacker-supplied, unvalidated. After `begin_auth`: `auth_route` still points at the attacker's host, unchanged — the binding is never enforced.

### Impact Explanation
The victim's browser is redirected to the attacker's server carrying the `state` CSRF nonce (which the host app also stores in a cookie for later comparison in `validate_auth_callback`) and the app's public `client_id`. The attacker's server can then redirect the victim onward to the real `https://{legit-shop}.myshopify.com/admin/oauth/authorize?...&state=<captured-nonce>` (or otherwise orchestrate completion of installation for a shop of the attacker's choosing), letting the attacker complete/force an OAuth authorization flow whose CSRF state token they now control — this is a forced OAuth completion primitive (High impact per the given rules), since `validate_auth_callback` only checks `state == auth_query.state` against the cookie, not that the authorize request actually reached the genuine Shopify domain first.

### Likelihood Explanation
`begin_auth` is a primary, documented public entry point (`docs/usage/oauth.md`, "3. Begin OAuth") explicitly meant to be called with a user-supplied shop value from a login form/header, exactly as shown in the doc's example (`shop = request.headers["Shop"]`). No credentials, prior session, or special access are needed — a purely unprivileged internet user visiting the app's login route with a crafted `shop` parameter triggers this.

### Recommendation
Sanitize the `shop` parameter in `begin_auth` the same way it is sanitized in `client_credentials`, `refresh_token`, and `token_exchange`:

```ruby
def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
  validated_shop = Utils::ShopValidator.sanitize!(shop)
  ...
  auth_route = auth_base_uri(validated_shop) + "/oauth/authorize?#{query_string}"
  ...
end
```

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", host: "https://my-app.example", ...)

result = ShopifyAPI::Auth::Oauth.begin_auth(
  shop: "attacker.example",   # not a *.myshopify.com domain
  redirect_path: "/auth/callback",
)

result[:auth_route]
# => "https://attacker.example/oauth/authorize?client_id=key&scope=...&redirect_uri=https://my-app.example/auth/callback&state=<15-char-nonce>&grant_options%5B%5D=per-user"
```
No `ShopifyAPI::Errors::InvalidShopError` is raised, and the returned `auth_route` sends the browser (carrying the CSRF `state` nonce) to a domain fully controlled by the caller-supplied string, unlike `ShopifyAPI::Auth::ClientCredentials.client_credentials(shop: "attacker.example")`, which raises `ShopifyAPI::Errors::InvalidShopError` as shown in `test/auth/client_credentials_test.rb`: [7](#0-6)

          scope = if scope_override.nil?

            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)

          end

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)
