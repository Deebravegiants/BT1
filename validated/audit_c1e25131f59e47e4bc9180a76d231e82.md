Audit Report

## Title
`ERC20Transactor` credits/moves a fixed requested amount instead of the actual ERC20 balance delta, breaking XCM asset accounting for non-standard ERC20 tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` move ERC20 tokens via `pallet_revive::Pallet::bare_call` invoking Solidity `transfer()`, and only check the boolean return value / revert status rather than verifying the actual balance change of the checking account or beneficiary. Because `ERC20Matcher` accepts any `AccountKey20` location without a registration/allow-list step, an unprivileged user can reference an arbitrary attacker-deployed fee-on-transfer or otherwise non-standard ERC20 contract, causing the XCM `AssetsInHolding` accounting to diverge from the real token balance held by the shared `ERC20TransfersCheckingAccount`.

## Finding Description
`withdraw_asset_with_surplus` builds an `IERC20::transferCall` moving `amount` from the user to the checking account and, if the call doesn't revert and decodes to `true`, unconditionally credits `AssetsInHolding` with the full requested `amount`, without checking the checking account's balance delta: [1](#0-0) . Symmetrically, `deposit_asset_with_surplus` moves `amount` out of the checking account to a beneficiary using the same trust-the-return-value pattern: [2](#0-1) .

The asset id selecting which ERC20 contract to call is not restricted to any registered/allow-listed set: `ERC20Matcher` and its underlying `IsLocalAccountKey20`/`AccountKey20ToH160` match any location of the form `(0, [AccountKey20 { key, .. }])`: [3](#0-2) . This transactor is wired directly into the runtime's `AssetTransactors` tuple used by the XCM executor on Asset Hub Westend: [4](#0-3) , with the checking account defined as a fixed `PalletId`-derived account: [5](#0-4) .

Any unprivileged account can therefore reference an arbitrary `pallet-revive` contract address as an ERC20 asset in an XCM program (e.g., via `pallet_xcm::execute` against its own local assets), with no registration step required. If the contract implements a fee-on-transfer or otherwise non-standard `transfer()`, the credited/moved amount in `AssetsInHolding` will not match the real balance change in the shared checking account, desynchronizing the XCM accounting layer from the actual ERC20 ledger state.

## Impact Explanation
Because the shared `ERC20TransfersCheckingAccount` custodies ERC20 balances for all users of the transactor, a mismatch introduced by one withdrawal (crediting more XCM-holding value than what was actually deposited) can cause a subsequent `DepositAsset` instruction to attempt moving more tokens out of the checking account than it actually holds, causing the underlying `transfer()` to revert and the XCM instruction to fail, trapping assets (`AssetsTrapped`). This is a concrete accounting-integrity break specific to this repository's code — not a hypothetical or purely external dependency issue — and matches the pattern of a state (ERC20 ledger) vs. accounting (XCM holding register) divergence.

## Likelihood Explanation
The entry path is reachable by any unprivileged account: `ERC20Matcher` accepts any `AccountKey20` location without requiring registration as a vetted asset, and XCM execution of withdraw/deposit instructions against one's own account via `pallet_xcm::execute` is a standard permissionless capability. No privileged role needs to be compromised; a user only needs to deploy a non-standard ERC20 contract via `pallet-revive` and issue an XCM program referencing it.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, query the ERC20 contract's `balanceOf` for the relevant account before and after the `transfer()` call, and use the observed balance delta — not the requested `amount` — when constructing the `AssetsInHolding` credit or reporting success/failure. Alternatively, restrict `ERC20Matcher` to an explicitly allow-listed/registered set of vetted ERC20 contracts known to implement standard, non-fee-on-transfer semantics.

## Proof of Concept
1. Deploy a `pallet-revive` contract implementing `IERC20` whose `transfer()` deducts a fee on every transfer but still returns `true`.
2. Submit an XCM program via `pallet_xcm::execute` with `WithdrawAsset` for `Asset { id: Location(0, [AccountKey20{ key: <contract address> }]), fun: Fungible(100) }` from the signed origin's own account.
3. `ERC20Transactor::withdraw_asset_with_surplus` (`erc20_transactor.rs:150-216`) calls `transfer(checking_account, 100)`; the contract moves less than 100 to the checking account but returns `true`, so the function returns `AssetsInHolding` credited with `Erc20Credit(100)` regardless.
4. Chain a `DepositAsset` instruction attempting to move the full "100" out of the checking account; `deposit_asset_with_surplus` (`erc20_transactor.rs:225-306`) issues `transfer(beneficiary, 100)` from the checking account, which holds fewer real tokens, causing a revert and the "100" units to be trapped — demonstrating the accounting/reality mismatch.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
