This is a legitimate and well-supported analog. The naive (ECDSA) BEEFY consensus path is missing the "latest MMR leaf" freshness check that the SP1 BEEFY path explicitly implements and documents as a countermeasure for exactly this class of attack — allowing a relayer to advance `latestHeight` while withholding/suppressing the true, most-recent authority-set rotation and parachain state, analogous to the forkchoice "selfish mining" pattern of withholding true chain state to bias later outcomes.

### Title
Naive BEEFY consensus client accepts a stale MMR leaf paired with a fresh signed commitment, allowing height advancement while suppressing authority-set rotation and orphaning parachain state - (File: modules/consensus/beefy/verifier/src/lib.rs)

### Summary
The SP1 (zk) BEEFY verifier explicitly pins the supplied MMR leaf to be the *latest* one for the signed commitment's block number via `parent_number.saturating_add(1) != proof.block_number` [1](#0-0) , with an explicit comment explaining why: an MMR is append-only, so a stale/historical leaf still verifies against the current signed root, and accepting it would advance height while suppressing authority-set rotation, stranding the client on an authority set the relay chain has already retired. The equivalent "naive"/ECDSA path (`verify_mmr_update_proof` / `verify_mmr_leaf` in the same crate, and its Solidity counterpart `EcdsaBeefy.sol`) never performs this check.

### Finding Description
`verify_mmr_update_proof` only checks that `latest_height` (from the freshly signed commitment) is greater than the trusted height, then calls `verify_mmr_leaf` to check inclusion of the supplied leaf in the (fresh) signed MMR root: [2](#0-1) [3](#0-2) 

`verify_mmr_leaf` verifies membership of *whatever leaf index the relayer supplies* against the signed root — it never asserts that `leaf.parent_number + 1 == commitment.block_number`: [4](#0-3) 

Because an MMR is append-only, any historical leaf (an older relay block's leaf) still produces a valid inclusion proof against the current, fresher signed root. A relayer can therefore submit:
- a signed commitment for the *current* (fresh) relay block/height (satisfying the supermajority signature check and advancing `trusted_state.latest_beefy_height`), together with
- an *old* `latest_mmr_leaf` (from many blocks earlier) that still verifies against that fresh root.

The result: `trusted_state.latest_beefy_height` is advanced to the new, higher block number, but `current_authorities`/`next_authorities` are only rotated based on the old leaf's `beefy_next_authority_set` (comparison at [5](#0-4) ), and the returned `heads_root` (`leaf_extra`) used to verify parachain headers is the *stale* block's parachain-heads root, not the true latest one.

The exact same asymmetry exists on the EVM side: `SP1Beefy.sol` has the `StaleMmrLeaf` freshness check [6](#0-5) , while `EcdsaBeefy.sol`'s `verifyMmrUpdateProof`/`verifyMmrLeaf` has no such check — it derives `leafIndex` purely from the supplied `latestMmrLeaf.parentNumber` with no comparison against `commitment.blockNumber`: [7](#0-6) 

Both `update_client` (pallet-ismp core handler) and `HandlerV2.sol` persist whatever `latestHeight`/`latest_beefy_height` the client returns and store any `IntermediateState`s (parachain state commitments) returned, without any independent freshness re-check: [8](#0-7) [9](#0-8) .

Since `trusted_state.latest_beefy_height >= latest_height` is rejected as `StaleHeight` for any *future* proof at or below that same block number [10](#0-9) , once an attacker advances height using a stale leaf, no one can ever resubmit the correct/fresh leaf for that same relay block again — the true authority rotation and the true parachain state for that height are permanently unreachable through this consensus client.

### Impact Explanation
This is reachable by any permissionless relayer submitting a `ConsensusMessage`/naive BEEFY proof — no privileged role required. Concrete impacts:
- **Suppressed/forged authority-set rotation**: the light client can be permanently stranded on a stale or already-retired authority set (a malicious actor who possesses signing keys for a retired validator set that hasn't yet been "seen" as retired by the light client can keep forging future updates under a superseded set).
- **Permanent freezing/censorship of state commitments**: any Hyperbridge (parachain) messages that were only reflected in the true/fresh `heads_root` for that relay block are permanently unprovable, because the client's height has already advanced past that block and any resubmission at the same height is rejected as stale. This is a "route unable to deliver messages" condition for whatever cross-chain requests/responses were finalized in the withheld block.
- **Unsound state commitment**: an intermediate parachain `StateCommitment` can be accepted that does not correspond to the state actually finalized by the fresh, supermajority-signed commitment being used to justify the height advance.

### Likelihood Explanation
Constructing this proof requires no more than what any legitimate relayer already has: a valid, freshly signed BEEFY commitment (obtainable from the relay chain the moment it's produced) plus a previously-observed, older MMR leaf/inclusion proof that is trivially still valid because MMR proofs are append-only. No special privileges, collusion, or governance access is needed — this is a standard, permissionless "submit a consensus proof" call.

### Recommendation
Add the same freshness constraint used in the SP1 path to the naive/ECDSA verifier(s): require `latest_mmr_leaf.parent_number_and_hash.0 + 1 == commitment.block_number` in `verify_mmr_update_proof`/`verify_mmr_leaf` (`modules/consensus/beefy/verifier/src/lib.rs`), and the equivalent `parentNumber + 1 == commitment.blockNumber` check in `EcdsaBeefy.sol`'s `verifyMmrUpdateProof`/`verifyMmrLeaf`, mirroring `SP1Beefy.sol`'s `StaleMmrLeaf` guard.

### Proof of Concept
1. Attacker (any relayer) waits for the relay chain to produce a BEEFY-signed commitment at block `N` (fresh supermajority signatures).
2. Attacker constructs a `ConsensusMessage`/`RelayChainProof` using this fresh signed commitment for block `N`, but supplies `latest_mmr_leaf` = the leaf for an earlier block `M < N-1` (still obtainable and still valid against the current signed MMR root because MMR proofs are append-only), along with a `mmr_proof` proving that historical leaf's inclusion.
3. `verify_mmr_update_proof`/`EcdsaBeefy.verifyMmrUpdateProof` accepts this: signatures check out (fresh commitment for block `N`), leaf inclusion check out (valid append-only proof), and `trusted_state.latest_beefy_height` is set to `N`.
4. `nextAuthoritySet`/`next_authorities` and `heads_root`/`leaf_extra` are taken from the stale leaf at block `M`, not from the true state at block `N`.
5. Any subsequent proof attempting to submit the correct leaf/heads_root for block `N` is rejected with `StaleHeight`/stale-height no-op, since `latest_beefy_height >= N` already. The true rotation and true parachain messages for block `N` are permanently unreachable via this consensus client.

fn verify_mmr_leaf<H: Keccak256 + Send + Sync>(
	mmr: &MmrProof,
	mmr_root: H256,
) -> Result<(), Error> {
	// `leaf_indices` is supplied by the relayer in the unsigned consensus message;
	// an empty vector previously panicked the runtime via the unchecked `[0]` index
	// after the BEEFY signature and authority membership checks had already succeeded.
	// This verifier checks a single MMR leaf, so reject any proof that does not carry
	// exactly one leaf index.
	if mmr.mmr_proof.leaf_indices.len() != 1 {
		Err(Error::InvalidMmrProof)?
	}
	let leaf_index = mmr.mmr_proof.leaf_indices[0];
	let leaf_hash = H::keccak256(&mmr.latest_mmr_leaf.encode());
	let mmr_size = leaf_index_to_mmr_size(leaf_index);

	let mmr_proof = MmrMerkleProof::<[u8; 32], KeccakMerge<H>>::new(
		mmr_size,
		mmr.mmr_proof.items.iter().map(|h| (*h).into()).collect(),
	);
	let leaf_pos = leaf_index_to_pos(leaf_index);
	let leaf = (leaf_pos, leaf_hash.into());
	let valid = mmr_proof
		.verify(mmr_root.into(), vec![leaf])
		.map_err(|e| Error::MmrVerificationFailed(e.to_string()))?;

	if !valid {
		Err(Error::InvalidMmrProof)?
	}

	Ok(())
}
