## Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `x-shopify-shop-domain` header straight to the app's handler as the tenant identifier. The shop domain is never included in the signed material, so it is not bound to the signature that authenticates the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header, a field that plays no part in `to_signable_string`: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC exclusively over `to_signable_string`: [3](#0-2) 

`Registry.process` treats a passing `HmacValidator.validate(request)` as full authentication of the request, then forwards `request.shop` unchanged to the app-registered handler as the tenant identity used to process the payload: [4](#0-3) 

This breaks the identity binding: `shop header verified-by-caller ≠ shop bound-by-HMAC`. The gem verifies "was this body signed by our secret" but the calling application (following the gem's documented `WebhookMetadata#shop` field) is led to believe "this body belongs to `shop`." Any legitimately-obtained `(body, hmac)` pair — e.g. from a webhook delivered to a shop the attacker controls (a normal, unprivileged capability, no `api_secret_key` needed) — can be replayed to the app's public webhook endpoint with the `shop-domain` header swapped to a victim shop. `HmacValidator.validate` still returns `true` because it never inspects the shop header, and `Registry.process` dispatches the (attacker-supplied-body) event tagged with the victim's shop to the handler.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged actor who can trigger any real webhook delivery to their own shop (trivial — install the app on a shop they control) can cause the host application to process and persist that payload as belonging to an arbitrary victim shop, since `WebhookMetadata.shop` (built from the unauthenticated header) is the only tenant signal the gem exposes to handlers. Depending on how the host app uses `data.shop` (e.g., to key data storage, trigger actions, or update shop-scoped records), this enables cross-tenant data injection/corruption — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only: (1) ability to install/operate the app on an attacker-controlled shop to receive one legitimately-signed webhook, and (2) ability to POST an HTTP request with modified headers to the app's public webhook receiving endpoint — both achievable by any unprivileged internet user/developer, with no access to `api_secret_key`, tokens, or victim credentials.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the HMAC before trusting it. At minimum, `Request#to_signable_string` (or `HmacValidator`) should incorporate `shop` (and ideally `topic`, `webhook_id`) into the signed payload construction actually verified, so that a signature computed for one shop's body cannot be replayed against another shop's identity. Document clearly to consuming apps that today `shop` in `WebhookMetadata` is not itself HMAC-authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggers a webhook event (e.g., `orders/create`), and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid signature of `B` under the app's real secret).
2. Attacker POSTs the same `B`/`H` pair to the app's public webhook endpoint but replaces `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body fine; `Registry.process` calls `HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only and matches `H` — validation passes.
4. `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...))` is invoked, causing the host app to process attacker-controlled webhook content as if it came from `victim-shop.myshopify.com`.
