## Analysis

The reported Solidity bug is a broken identity/authorization binding caused by trusting a value (`commitLaunch[tokenId]`) that isn't actually gated by the intended check. The instruction set maps this bug class onto Ruby analogs where "a field acted on but not covered by the HMAC" breaks a trust boundary. That maps directly onto `ShopifyAPI::Webhooks::Request`.

`ShopifyAPI::Webhooks::Request#to_signable_string` — the value HMAC-verified by `Utils::HmacValidator.validate` — returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, none of which are part of the signed payload: [2](#0-1) 

`Registry.process` verifies the HMAC (covering only the body) and then unconditionally forwards the header-derived `shop` to the handler as trusted tenant metadata: [3](#0-2) 

This exact usage pattern — passing raw request headers straight into `Request.new` — is the gem's own documented integration: [4](#0-3) 

### Title
Webhook shop-domain/topic identity is not bound to the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by `Registry.process` and handed to webhook handlers are read from unauthenticated HTTP headers that are never part of the signed data.

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)`, which checks `OpenSSL.secure_compare(computed_signature, received_signature)` where `computed_signature` is derived solely from `request.to_signable_string`, i.e. `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`). The `shop` accessor, however, is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-23`), which is not included anywhere in `to_signable_string`.

After HMAC validation succeeds, `Registry.process` builds a `WebhookMetadata` object using this unverified `request.shop` value and passes it to the app's registered handler (`lib/shopify_api/webhooks/registry.rb:188-199`):
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```

The equality that should hold is: `shop_verified_by_HMAC == shop_acted_on_by_handler`. In this implementation that equality is never enforced — the HMAC proves only that the *body bytes* were signed with the app's secret; it says nothing about which shop the header claims to be from. Anyone able to obtain one genuine signed webhook body+HMAC pair (trivially available to any merchant/developer who installs the app on their own store and receives a real webhook) can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header value. `Registry.process` will pass HMAC validation (because the body is unchanged) and will hand the handler a `WebhookMetadata` claiming to be for a shop the attacker does not own.

This is the direct Ruby analogue of the reported Solidity bug class: a value that gates a security-relevant action (`commitLaunch[tokenId]` / here, "which tenant does this webhook belong to") is not actually covered by the verification step that is supposed to make it trustworthy (the `block.number <= commitLaunch[tokenId]` check / here, the body-only HMAC check).

### Impact Explanation
Because host applications are documented to construct `Webhooks::Request` directly from unauthenticated inbound request headers (`docs/usage/webhooks.md:123-136`) and to rely on `data.shop` from `WebhookMetadata` to identify which tenant/store the event pertains to, a forged `shop-domain` header lets an attacker who controls one legitimate shop on the app cause the app to process/attribute webhook data as belonging to a different, victim shop while still passing this gem's own signature check. This is a cross-tenant confusion in the trust boundary this gem is responsible for enforcing.

### Likelihood Explanation
High. The webhook HTTP endpoint is unauthenticated by design (only the HMAC is meant to establish trust), any developer/merchant with the app installed can capture one valid body+HMAC pair from their own store's traffic, and the gem's documented processing path (`Registry.process`) never checks the `shop` header against anything derived from the signed body.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified data, or otherwise cryptographically tie the header values to the signed payload, e.g. by including them in `to_signable_string`, or by requiring/verifying `shop` against a value embedded in the signed body/known session store before it is forwarded to handlers in `Registry.process`.

### Proof of Concept
1. Install/operate the app on `attacker-shop.myshopify.com`; capture a real webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with the app's `client_secret`), plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Send a new HTTP request to the app's webhook endpoint with the exact same body `B` and the exact same `X-Shopify-Hmac-Sha256: H`, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. The host app builds `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", ...})` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` passes because `to_signable_string` only checks `B` against `H`.
5. The registered handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, causing the app to act as if this genuine (attacker-originated) payload came from `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
