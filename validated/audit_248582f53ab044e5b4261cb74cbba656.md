Based on the investigation, the closest analog to the reported bug class (integer-division truncation causing fees/rewards to round to zero, denying payment to a beneficiary) is the commission-splitting logic in `runtime/src/inflation_rewards/mod.rs`.

### Title
Integer-division truncation in stake/vote commission split can zero out a party's reward - (File: runtime/src/inflation_rewards/mod.rs)

### Summary
`commission_split` in `runtime/src/inflation_rewards/mod.rs` computes each party's share of a reward using `(on * split) / MAX_BPS_U128` for both the voter's and staker's portions independently, truncating any fractional lamports rather than allocating the remainder to either party.

### Finding Description
The function explicitly documents this behavior: "note that we intentionally discard any residual fractional lamports" [1](#0-0) . Both `mine` and `theirs` are computed independently via truncating integer division, and — analogous to the `Fund.finalizeGrant` bug — when `on` (the reward amount) is small relative to `MAX_BPS` (10,000), one or both shares can round down to zero, meaning that party receives nothing despite being entitled to a small fractional reward [2](#0-1) .

Notably, the codebase already contains an alternative, corrected implementation, `commission_split_preserve_lamports`, which computes the staker's rewards via truncating division but then derives the voter's rewards as `on.checked_sub(staker_rewards)`, guaranteeing that no lamports are lost and the total is always fully distributed [3](#0-2) . This mirrors the report's suggested fix of computing `finalGrant = grant.value - fee` instead of computing both shares independently by division.

### Impact Explanation
Where the old, lossy `commission_split` is still invoked (used for legacy/"Tower" epoch reward paths per its doc comment), a reward recipient (staker or voter) can be denied their earned reward when the reward magnitude is small relative to commission basis points, effectively creating unaccounted-for lamports that are silently discarded rather than credited to either party — a concrete value-loss condition consistent with the analog bug class.

### Likelihood Explanation
Low-to-moderate. Inflation rewards are typically large enough in lamports that truncation is negligible, and the function is explicitly documented as intentional legacy behavior reserved for "Tower" epochs, with the non-lossy variant (`commission_split_preserve_lamports`) already introduced for other epochs [4](#0-3) . This limits real-world exploitability/impact, similar to how the original report's issue was acknowledged but deprioritized because grant values are bounded.

### Recommendation
Where feasible, replace remaining call sites of `commission_split` with `commission_split_preserve_lamports` (or an equivalent complement-based calculation) so that the full reward amount is always distributed without silently discarding fractional lamports.

### Proof of Concept
For `commission_split(commission_bps, on)` with a small `on` and `commission_bps` not exactly `0` or `MAX_BPS`, e.g. `on = 1`, `commission_bps = 5000` (50%): `mine = (1 * 5000) / 10000 = 0`, `theirs = (1 * 5000) / 10000 = 0` — both computed shares truncate to `0`, so `mine + theirs = 0 != on = 1`, and 1 lamport is unaccounted for, per the arithmetic in [5](#0-4) .

**Note on confidence:** I could not verify, within the available index, all remaining call sites/conditions that route reward computation to `commission_split` vs. `commission_split_preserve_lamports` (the `vote_reward.rs` file content did not load in the final tool pass), so the precise conditions under which the lossy path is still reachable in production (vs. only in "Tower" test/legacy epochs) are not fully confirmed. A full-repo Devin session would be needed to trace the call graph and confirm production reachability with certainty.

fn commission_split(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let on = u128::from(on);
            // Calculate mine and theirs independently and symmetrically instead of
            // using the remainder of the other to treat them strictly equally.
            // In Tower, this is also to cancel the rewarding if either of the parties
            // should receive only fractional lamports, resulting in not being rewarded at all.
            // Thus, note that we intentionally discard any residual fractional lamports.
            let mine = on
                .checked_mul(u128::from(split))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let theirs = on
                .checked_mul(u128::from(
                    MAX_BPS
                        .checked_sub(split)
                        .expect("commission cannot be greater than MAX_BPS"),
                ))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;

            (mine as u64, theirs as u64, true)
        }
    }
}

fn commission_split_preserve_lamports(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let staker_bps = MAX_BPS
                .checked_sub(split)
                .expect("commission cannot be greater than MAX_BPS");
            let staker_rewards = u128::from(on)
                .checked_mul(u128::from(staker_bps))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let staker_rewards = staker_rewards as u64;
            let voter_rewards = on
                .checked_sub(staker_rewards)
                .expect("staker rewards cannot exceed total rewards");

            (voter_rewards, staker_rewards, true)
        }
    }
}
