### Title
Webhook `shop-domain` header is trusted for tenant identity but is not covered by the HMAC signature, enabling cross-tenant webhook impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, then unconditionally trusts the unauthenticated `X-Shopify-Shop-Domain` header as the tenant identity passed to the app's handler. This breaks the identity binding: `shop authenticated == shop acted upon`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) accessors are read straight from HTTP headers, never included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` accessor — for webhooks this checks the body only: [3](#0-2) 

`Registry.process` gates on this HMAC check and then builds `WebhookMetadata` using `request.shop`, the unauthenticated header, and dispatches it to the app's handler: [4](#0-3) 

Because the HMAC signs only the body bytes, any request carrying a `(raw_body, hmac)` pair that was legitimately produced by Shopify for one shop remains valid when replayed with a different `x-shopify-shop-domain` header — the signature check passes, and the app-supplied `WebhookHandler#handle` receives `WebhookMetadata#shop` set to the attacker-chosen value while `body` is unmodified. This is the "shop authenticated versus the shop stored/acted upon as identity" pattern: the equality that should hold, `hmac_verifies(shop, body) == shop_acted_on(shop, body)`, does not — the HMAC only proves `hmac_verifies(body)`, decoupled from `shop`.

An unprivileged internet user who legitimately installs the target app on their own store receives genuine Shopify-signed webhooks (valid `hmac-sha256` + body) for their own shop. They can capture one such delivery and resend it to the app's public webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and the app processes attacker-controlled webhook data as if it originated from — and pertains to — the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion in the webhook trust boundary this gem exposes to host applications. Any app that keys behavior on `WebhookMetadata#shop` (e.g., looking up the shop's session/access token, updating per-shop state, triggering redact/GDPR flows, or acting on `shop/redact`/`customers/redact` mandatory topics) can be made to associate one shop's legitimate, signed payload with an arbitrary victim shop chosen by the attacker, since nothing in the gem binds the two together before dispatch. This matches the "cross-tenant access" category.

### Likelihood Explanation
Any merchant/developer who can install the app (a normal, unprivileged action) can obtain a valid `(body, hmac)` pair for their own shop and replay it with a forged shop header — no access token, `client_secret`, or privileged access is required, only capturing one webhook delivery for their own store.

### Recommendation
Include `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or otherwise cryptographically bind the shop identity to the signed payload before `Registry.process` trusts `request.shop`. At minimum, document/require host apps to independently validate that `WebhookMetadata#shop` corresponds to a shop that actually has this app installed with an active session before acting on the payload.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger any subscribed webhook topic so Shopify delivers a genuine request with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON `raw_body`.
2. Capture that exact `raw_body` and `x-shopify-hmac-sha256` value.
3. Resend a request to the app's webhook endpoint with the identical `raw_body`/`x-shopify-hmac-sha256`, but replace the header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header, and `Utils::HmacValidator.validate` (per `lib/shopify_api/utils/hmac_validator.rb#L12-L31`) succeeds because it only checks `@raw_body` (`lib/shopify_api/webhooks/request.rb#L35-L38`).
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb#L188-L200`) invokes the app's handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's data>, ...)`, causing the app to treat attacker-supplied data as belonging to `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
