## Finding

The webhook signature verification in this gem checks only the raw request body, not the shop, topic, or webhook-id, so an attacker who has ever received one legitimately signed webhook (e.g., by installing the app on their own store) can attach that same body+HMAC pair to forged `shop-domain` / `topic` headers and have it accepted as authentic for a different tenant.

### Title
Webhook HMAC does not bind shop/topic identity, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies solely that the *body* was signed with the app's `client_secret` — it never covers `shop`, `topic`, `webhook_id`, or `api_version`. `Registry.process` trusts those unauthenticated header fields for dispatch after the body-only HMAC check succeeds.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates the HMAC and then dispatches to the handler using `request.shop` and `request.topic` as trusted tenant/topic identity, without those fields ever having been covered by the signature: [3](#0-2) 

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` using the app's single, shop-independent `client_secret`: [4](#0-3) 

Because the same `client_secret` is used to sign webhook bodies for *every* shop that installs the app, and the shop identity is never part of the signed content, a valid `(raw_body, hmac)` pair obtained from one shop's webhook delivery remains valid when replayed with a different `shop-domain` header. The binding that should hold — "shop the HMAC was computed for" == "shop the app processes the payload as" — is broken: any bytes verified only prove *a* body was authentic for *some* install of the app, not which tenant it belongs to.

### Impact Explanation
An attacker who can install the app themselves (e.g., a free development store, which almost all Shopify apps allow) can capture one legitimately signed webhook delivery (body + HMAC), then replay that exact body/HMAC pair to the app's public webhook endpoint while spoofing the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header to reference a victim shop. If the host application (following this gem's documented `WebhookMetadata#shop`/`#topic` as the trust boundary) uses these values to scope database writes, trigger tenant-specific side effects, or select behavior per shop, the attacker can inject attacker-chosen webhook content attributed to another tenant — a cross-tenant integrity/data-injection issue.

### Likelihood Explanation
Exploitation requires only: (1) ability to install the target app on an attacker-controlled store (trivial for public apps with free trials or dev stores), (2) ability to POST to the app's public webhook URL (also public by design), and (3) capturing one webhook delivery to obtain a valid `(body, hmac)` pair. No secret material, session, or privileged access is required.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is authenticated — e.g., verify the `shop-domain` header against the shop that owns the currently-active session/registration rather than trusting it purely because the body-only HMAC matched, or require the app to independently confirm the shop via a follow-up authenticated API call (as Shopify's own webhook best-practices document recommends) before trusting `WebhookMetadata#shop` for tenant-scoped actions.

### Proof of Concept
1. Attacker creates their own Shopify dev store and installs the target app; the app registers a webhook (e.g., `orders/create`).
2. Attacker triggers the event on their own store and captures the resulting HTTP request Shopify sends to the app's webhook endpoint, including `x-shopify-hmac-sha256` and the raw JSON body.
3. Attacker resends the identical raw body and `x-shopify-hmac-sha256` value to the same webhook endpoint, but sets `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` succeeds (it only checks the body), and `handler.handle` is invoked with `shop: "victim-shop.myshopify.com"`, causing the host app to process attacker-controlled data as if it originated from the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
