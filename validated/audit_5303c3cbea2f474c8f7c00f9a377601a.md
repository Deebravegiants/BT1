### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is trusted from an unauthenticated HTTP header, while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by verifying only the raw request body via HMAC, then blindly trusts the tenant-identifying `shop` value taken from an HTTP header that is never included in that signature. An attacker who controls one legitimate shop (with a valid, self-signed webhook payload from Shopify) can replay the exact same body+HMAC to the app while substituting a victim shop's domain in the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header, causing the app to process attacker-controlled data under another tenant's identity.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are completely outside the signed bytes: [3](#0-2) 

`Registry.process` verifies the HMAC and then forwards `request.shop` (the unauthenticated header value) straight into the handler as the tenant identity, with no cross-check that the signed body actually originated for that shop: [4](#0-3) 

This breaks the identity binding the whole scheme is supposed to enforce: `shop authenticated == shop the data is attributed to`. In reality, the equality that holds is only `bytes verified == raw_body`, while `shop used by the handler == unauthenticated header`. Any attacker who can get one validly HMAC-signed webhook body (e.g., by owning a shop that installs the same public app and receiving Shopify's own real webhook calls to that shop) can detach that body+HMAC pair from its true shop and re-submit it with an arbitrary `shop-domain` header value. `Utils::HmacValidator.validate` will still return `true`, because it never looks at the header at all.

This directly parallels the reported bug class: data trusted at runtime without validating that every relevant field (here, the tenant/shop binding) is actually covered by the cryptographic guarantee that the caller relies on.

### Impact Explanation
This is a cross-tenant confusion primitive: the app's webhook handlers (registered via `WebhookHandler#handle`, receiving `WebhookMetadata` built from `request.shop`) will act on a shop they did not actually receive data from. For GDPR/mandatory compliance webhooks such as `shop/redact` and `customers/redact`, or any handler that persists/looks up records keyed by `shop`, this lets one merchant with the app installed forge webhook deliveries that appear to originate from a different, victim shop, causing the app to write, delete, or otherwise process data attributed to a tenant the attacker doesn't control - a cross-tenant access impact.

### Likelihood Explanation
The attacker only needs to install the (typically public) app on their own store to legitimately receive at least one real, validly signed webhook from Shopify for a topic the app subscribes to. From then on they can replay that fixed body+HMAC pair to the app's webhook endpoint with an arbitrary `shop-domain` header, since nothing in `HmacValidator` or `Registry.process` binds the header to the signed bytes. No secret material, TLS interception, or social engineering is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signed material that is verified, or independently verify that the `shop` header matches a value derivable from the authenticated payload/session before dispatching to a handler. At minimum, cross-check `request.shop` against a known/allow-listed set of shops associated with the app installation context before trusting it as the tenant identity in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify send a real webhook (e.g. `orders/create`) to the app's endpoint; attacker captures the raw request: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared `api_secret_key`), plus header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker re-sends an HTTP POST to the same webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `to_signable_string` is still `B` and whose `shop` is `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` and it matches `H` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) → validation succeeds.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the app to process attacker-supplied content as if it came from the victim shop.
