### Title
Malicious input token in an IntentGateway order permanently freezes cross-chain escrow settlement - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2.placeOrder` accepts arbitrary, unvalidated ERC20 addresses as order inputs and escrows them without any whitelist check. `_withdraw`, which is invoked from `onAccept` when a `RedeemEscrow`/`RefundEscrow` ISMP message is delivered on the source chain, iterates over *all* of the order's escrowed tokens and performs a raw transfer for each one in a single all-or-nothing loop. A malicious order creator can include a token whose `transfer` unconditionally reverts (or is later "bricked" post-order) as one of the order's inputs. Once a solver fills the order, the settlement message that is supposed to release escrow to the solver will forever revert on delivery, since the malicious token's transfer always fails and there is no per-token error isolation.

### Finding Description
`placeOrder` builds the escrow map `_orders[commitment][token]` for every token in `order.inputs` with no token whitelist or validation beyond `amount != 0` and duplicate-token rejection: [4](#0-3) [6](#0-5) .

For cross-chain orders, when a solver fills the order on the destination chain, `_fillCrossChain` dispatches a `RedeemEscrow` message back to the source-chain gateway carrying the full `order.inputs` list: [7](#0-6) .

When that message is delivered by the ISMP host, `onAccept` calls `_withdraw` unconditionally for the whole token set: [1](#0-0) .

`_withdraw` loops through every escrowed token and calls `IERC20(token).safeTransfer(beneficiary, amount)` (or the raw `.call` variant in the Tron deployment) with no try/catch or per-token failure isolation — if any single token's transfer reverts, the whole function reverts, and consequently the whole `onAccept` handler call reverts: [2](#0-1) .

Because the ISMP delivery of this particular commitment will always hit the same malicious token and always revert, the message can never be successfully delivered — it is permanently stuck. The same applies to `RefundEscrow` (cancellation refund) and to the destination-chain GET-response refund path (`onGetResponse` → `_withdraw`), and to same-chain `cancelOrder`/`fillOrder`, all of which route through the identical `_withdraw` all-or-nothing loop over the full input set: [8](#0-7) .

This is directly analogous to the reported OpenQ issue: a user-controlled, unvalidated ERC20 address is stored alongside legitimate funds, and a single hostile token's reverting `transfer` DOSes the payout path that must move *all* tokens atomically.

### Impact Explanation
A solver who fills a cross-chain order provides real output tokens to the beneficiary on the destination chain in `_fillCrossChain` before the escrow-release message is even dispatched (output legs are settled first, at line 191-196 of `ExtrinsicIntents.sol`). If the order's input set includes a malicious/self-destructing token, the subsequent `RedeemEscrow` settlement on the source chain can never be delivered successfully, so the solver never receives the input tokens (nor any co-escrowed legitimate tokens in the same order, nor the escrowed transaction fees) it is owed. This is a permanent freezing of funds for the solver and the escrow, satisfying the "permanent freezing of funds" / "route unable to deliver messages" criteria — ISMP cannot ever successfully deliver this particular message once the malicious token is included, since the handler call for that commitment always reverts.

### Likelihood Explanation
Likelihood is high: any user can deploy a token, place an order containing that token as one of the `order.inputs`, and wait for a solver to naturally fill the order because the advertised output looks attractive. No special privileges, governance, or admin cooperation are required — this is reachable directly from a single `placeOrder` transaction by any unprivileged user, matching the required attack surface ("intents escrow and bids").

### Recommendation
Do not perform an unconditional all-or-nothing transfer loop over user-supplied token addresses in `_withdraw`. Options include: (1) wrapping each token transfer in a low-level call with try/catch and crediting failed transfers to a separately claimable balance instead of reverting the whole settlement, (2) requiring input tokens to pass a governance-controlled allow-list before they can be escrowed in `placeOrder`, or (3) decoupling escrow release into independent per-token claim calls so a single malicious token cannot block the release of the others.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer`/`transferFrom` succeed on deposit but permanently revert afterward (e.g. gated by a flag the attacker flips once escrowed).
2. Attacker calls `placeOrder` with `order.inputs = [{EvilToken, X}, {legitToken, Y}]` and an attractive `order.output` (e.g. a generous amount of a desirable token), destined for a different chain: [9](#0-8) .
3. Attacker flips `EvilToken` into its reverting mode.
4. A solver, unaware of the malicious token, calls `fillOrder` on the destination chain, delivering the required output tokens to the beneficiary and dispatching the `RedeemEscrow` message: [10](#0-9) .
5. When the relayer submits the ISMP proof for the `RedeemEscrow` message on the source chain, `onAccept` → `_withdraw` attempts to transfer `EvilToken` to the solver and reverts every time: [2](#0-1) .
6. The message can never be delivered; the solver's real output tokens are lost and both the `EvilToken` and co-escrowed `legitToken` remain frozen in the gateway forever.
