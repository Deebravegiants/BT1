This confirms the mechanism: `create_client` (called once when a consensus client is set up for a new `StateMachineId`) calls `host.store_latest_commitment_height(height)` for the initial state machine commitments, which sets `LatestStateMachineHeight` but crucially does **not** set `PreviousStateMachineHeight`, since `store_latest_commitment_height` itself is what populates `PreviousStateMachineHeight` (from the *prior* value of `LatestStateMachineHeight`, defaulting to `0`) [1](#0-0) . So after client creation, `PreviousStateMachineHeight` for that state machine is `0` (the pre-init default), even though the initial commitment height itself can be arbitrarily large (e.g. the real starting block height of an already-running chain like Ethereum).

### Title
First relayer reward for a newly created consensus client overpays because the reward baseline defaults to height 0 instead of the initial commitment height - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`calculate_reward` in `pallet-consensus-incentives` computes a relayer's reward as `(latest_height - baseline) * block_cost`, where `baseline` falls back to `previous_commitment_height`, which itself falls back to `0` via `unwrap_or_default()` [2](#0-1) . For a state machine whose consensus client was just created (or whose first-ever `StateMachineUpdated` event fires), `PreviousStateMachineHeight` has never been set to anything other than its pre-init default of `0`, so the very first reward computation spans `[0, latest_height]` instead of `[genesis_height, latest_height]`. This is structurally identical to the reported `ERC4626i.claimProtocolFees` bug: a storage value that should be seeded to a meaningful floor (the campaign start / the client's initial height) instead defaults to `0`, inflating the very first payout by the entire distance from `0` to the real starting point.

### Finding Description
The reward baseline logic is:
```rust
let previous_height = host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();
let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);
let blocks = latest_height.saturating_sub(baseline);
``` [2](#0-1) 

`previous_commitment_height` simply reads the `PreviousStateMachineHeight` storage map, returning `None` if it was never written [3](#0-2) . That map is only ever written as a side effect of `store_latest_commitment_height`, which sets `PreviousStateMachineHeight` to whatever `LatestStateMachineHeight` held *before* the call (defaulting to `0` if unset) [1](#0-0) .

When a brand-new consensus client is created via `create_client`, the very first call to `store_latest_commitment_height` for that `StateMachineId` runs with `LatestStateMachineHeight` unset, so it stamps `PreviousStateMachineHeight = 0` — regardless of what the actual initial height of the tracked chain is (which is normally a large, non-zero block number for any chain that has already been running) [4](#0-3) .

Consequently, the first time `process_message`/`calculate_reward` runs a reward computation for that state machine (`LastRewardedHeight` also unset, so it falls back to the flawed `previous_height`), `blocks = latest_height - 0 = latest_height`, i.e., the entire absolute height of the chain being bridged, not the number of new blocks actually relayed. The reward paid is `latest_height * block_cost`, which for any established chain (heights in the millions) can be orders of magnitude larger than intended and can trivially drain `T::TreasuryAccount`'s balance in a single `on_executed` call [5](#0-4) .

This is the exact analog of the reported bug class: a "last updated / baseline" value that should be floored at a meaningful initialization point (campaign start / initial commitment height) instead defaults to `0` on first use, inflating the very first payout computed from elapsed distance × rate.

### Impact Explanation
Any relayer who submits the very first valid consensus proof for a newly onboarded state machine (a routine, permissionless, unprivileged action — anyone can relay a `ConsensusMessage`) triggers a reward transfer of `latest_height * block_cost` from the treasury, rather than the intended `(latest_height - initial_height) * block_cost`. For real chains, `latest_height` at onboarding time is the chain's current block height (potentially tens of millions), so this can pay out an amount many orders of magnitude larger than the protocol intends, directly draining `T::TreasuryAccount`. This is a concrete theft/drain-of-funds vector reachable by an unprivileged relayer via `pallet_ismp::handle_unsigned` dispatching a `ConsensusMessage`.

### Likelihood Explanation
High likelihood: this triggers automatically and unconditionally the first time any state machine's consensus client is created and its first `StateMachineUpdated` event fires with `StateMachinesCostPerBlock` configured for it — no special conditions or attacker sophistication needed beyond relaying the very first valid consensus proof for a newly registered chain, which is a routine onboarding operation performed by any relayer.

### Recommendation
When creating a consensus client (`create_client` / initial `store_latest_commitment_height` call for a given `StateMachineId`), explicitly seed `PreviousStateMachineHeight` to the same initial height being stored (rather than defaulting to `0`), so the first-ever reward computation's baseline reflects the chain's actual starting point rather than height `0`. Equivalently, `calculate_reward` could special-case "no watermark and no meaningful previous height" by using `latest_height` itself as the baseline on first observation (paying `0` for the first reward and rewarding subsequent spans only), mirroring the audit's recommendation to seed `lastUpdated` to `campaignData.start` rather than leaving it at the zero default.

### Proof of Concept
1. Governance sets `StateMachinesCostPerBlock` for a new `StateMachineId` (e.g. `Polkadot(2000)`) to `block_cost = X`.
2. Governance/root calls `create_client` (via the consensus registration extrinsic) with `state_machine_commitments` containing an initial height of, say, `20_000_000` (a realistic starting height for an already-running chain) — this calls `store_latest_commitment_height` for the first time, setting `LatestStateMachineHeight = 20_000_000` and `PreviousStateMachineHeight = 0` (default) [4](#0-3) .
3. A relayer submits a subsequent `ConsensusMessage` that advances the state machine to height `20_000_001`, emitting a `StateMachineUpdated` event.
4. `FeeHandler::on_executed` → `process_message` → `calculate_reward` runs: `previous_commitment_height` returns `Some(0)`, `LastRewardedHeight` is `None` so baseline `= 0`, `blocks = 20_000_001 - 0 = 20_000_001`, reward `= 20_000_001 * block_cost` [6](#0-5) .
5. This reward is transferred from `T::TreasuryAccount` to the relayer in a single call [7](#0-6) , vastly exceeding the intended "pay only for newly relayed blocks" design, as confirmed by the pallet's own regression test comment describing the watermark as meant to scope payment "to the span that has not been paid" [8](#0-7)  — a guarantee that silently fails on the very first reward for any newly onboarded chain with a non-zero initial height.

	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a

		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
