### Title
Orb-Relay client skips sender authorization check for `RequestState` messages, allowing spoofed sender to trigger state re-broadcast - (File: `orb-relay-client/src/client.rs`)

### Summary
The Aave `executeOperation()` bug relied on the callback consumer failing to verify that inbound data actually originated from the expected counterparty before acting on attacker-controlled parameters. `orb-relay-client`'s `PollerAgent::main_loop` implements exactly this kind of sender check (`src.id != self.config.dst_id`) for incoming relay payloads, but it is bypassed for one specific message type (`self_serve::app::v1::RequestState`), letting any sender trigger a privileged action without the identity check.

### Finding Description
In the main receive loop, every incoming `RelayPayload` is supposed to be authorized by checking that `src.id` equals the configured `dst_id` of the paired session before it is handed to `handle_message`: [1](#0-0) 

However, the very first branch matches `self_serve::app::v1::RequestState` and unconditionally resends `self.last_message` via `sender_tx` *before* the `src.id != self.config.dst_id` check is evaluated. That authorization check only executes in the `else if` branch, meaning `RequestState` payloads completely skip the sender-identity verification that every other message type is subject to.

This is structurally the same root cause as the external report: a handler that processes an externally-triggered callback/message without validating that the caller/sender is the entity that is supposed to be authorized to invoke it — in Aave's case `msg.sender == lendingPool`, here `src.id == self.config.dst_id`.

### Impact Explanation
Because `RequestState` bypasses the sender check, any actor able to get a payload delivered to the orb's relay stream (regardless of whether its `src` matches the orb's actual paired app/session) can force the orb to immediately re-emit its last outbound self-serve signup message (e.g. `CaptureStarted`, `CaptureEnded`, `AgeVerificationRequiredFromOperator`, `SignupEnded`, `CaptureTriggerTimeout`) via `sender_tx`. This creates an agent-IPC trust-boundary violation: state transitions meant to be driven only by the legitimately paired self-serve app can be re-triggered by an unverified sender, which could be used to desynchronize/replay the self-serve signup state machine that drives `proceed_with_biometric_capture` and other self-serve flow gating in `src/plans/mod.rs`.

### Likelihood Explanation
Exploitability depends on whether the backend relay server enforces strict routing so that only the actual paired `app`/`orb` session can have its payloads delivered with an arbitrary `src` to the target orb's stream — that server-side enforcement is outside this repository's scope, so it cannot be fully confirmed here. Within `orb-core`'s own client code, the check that exists for every other message type is demonstrably and unconditionally absent for `RequestState`, which is the concrete, provable root cause regardless of the server-side routing assumptions.

### Recommendation
Move the `src.id != self.config.dst_id` authorization check to apply uniformly to all incoming payloads, including `RequestState`, before any type-specific handling (including the resend-last-message behavior) is performed: [2](#0-1) 

### Proof of Concept
1. An attacker (or any relay-connected client not paired with the orb's active self-serve session) sends a payload matching `self_serve::app::v1::RequestState` (see `PayloadMatcher` impl) with an arbitrary/spoofed `src.id`. [3](#0-2) 
2. In `main_loop`, the `RequestState::matches(&payload).is_some()` branch is taken first, and `self.last_message` is resent via `sender_tx` — the `src.id != self.config.dst_id` identity check is never evaluated for this message. [4](#0-3) 
3. Contrast with any other message type (e.g. a normal payload), where the identity check is enforced and mismatched senders are rejected with a logged error. [5](#0-4)
