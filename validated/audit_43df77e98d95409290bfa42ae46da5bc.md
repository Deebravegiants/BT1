### Title
Permissionless `CallDispatcher.dispatch()` allows theft of tokens held temporarily by the shared dispatcher during cross-chain deliveries - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` is the on-chain analog of the reported bug: a function meant to be reachable only as a trusted callback inside a specific, already-authorized delivery flow, but which carries **no caller restriction and no reentrancy protection** whatsoever. Just as `MarginTrading.executeOperation` never checked that `_initiator == address(this)` (allowing anyone to trigger it directly through AAVE's `flashLoan`), `CallDispatcher.dispatch(bytes)` never checks who is calling it or whether it is being invoked as part of a legitimate `HyperFungibleToken.onAccept`/`WrappedHyperFungibleToken.onAccept`/`IntentsBase._execute`/predispatch sequence.

### Finding Description
`CallDispatcher` is a single shared utility contract used by multiple apps (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleTokenUpgradeable`, and `IntentsBase`) to execute arbitrary attacker/user-supplied `Call[]` "in its own context" after tokens are minted/unlocked/escrowed to it: [1](#0-0) 

The `dispatch` function has zero access control — it is `external` with no modifier restricting the caller to the apps that are supposed to use it, and no reentrancy guard protects the balance the contract is holding mid-flow:
```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [1](#0-0) 

The intended flow is: `onAccept` mints/unlocks tokens directly to the dispatcher address, then calls `dispatch(message.data)` so the dispatcher can, e.g., approve and swap on behalf of the recipient: [2](#0-1) [3](#0-2) 

`IntentsBase` uses the same unrestricted dispatcher for `predispatch` (assets transferred to the dispatcher *before* escrow) and `postdispatch`/output execution (tokens delivered to the dispatcher for swap-then-settle patterns): [4](#0-3) 

Because `dispatch()` accepts *any* caller and *any* `Call[]`, and there is no reentrancy guard on the dispatcher itself, any external contract named as a `to` target inside a legitimate `Call[]` sequence (e.g., a router, a token with hooks, or any contract the sequence calls) can re-enter `CallDispatcher.dispatch()` mid-execution — while the dispatcher is still holding tokens/ETH minted or transferred to it for the *original*, not-yet-finished delivery — and drain that balance with an attacker-chosen `Call[]` before the legitimate sequence completes its swap/sweep. This is architecturally identical to the flash-loan bug: a callback-style executor is invoked as part of one authorized flow, but the executor itself does nothing to verify that the invocation is the authorized one, so an attacker can invoke or re-invoke it out of band and act on state (token balance) that belongs to someone else's in-flight delivery.

### Impact Explanation
Any user/relayer-supplied `data`/`predispatch.call`/`output.call` that calls into an external contract capable of yielding control (a malicious or vulnerable router, an ERC-777/ERC-1155-style token, or any contract with a callback) creates a reentrancy window into `CallDispatcher.dispatch()` while it is holding minted HFT/WHFT tokens or IntentGateway escrow/output assets. Because `dispatch()` performs no access control and no reentrancy check, the reentrant call can steal those funds via `to.call{value: call.value}(call.data)` before the original sequence's sweep/transfer-back step runs. Since `CallDispatcher` is shared across all `IApp` integrations, this is a systemic theft-of-funds primitive reachable by any user who can shape the `data`/`call` field of a cross-chain transfer or intent order (i.e., every ordinary sender), not just a privileged actor.

### Likelihood Explanation
Reachability requires only that the attacker route the `Call[]` through a contract they control (directly listed as a `to`, or reachable transitively) that can re-enter during execution — something entirely within a normal sender's control when constructing `SendParams.data` or `Order.predispatch.call`/`output.call`. No privileged role, governance, or off-chain component is needed; a single crafted cross-chain transfer or intent order is sufficient to open the window.

### Recommendation
Add a caller allowlist to `CallDispatcher.dispatch()` restricting it to the specific apps expected to invoke it (or make each app deploy/own its own dispatcher instance), and add a `nonReentrant` guard on `dispatch()` so it cannot be re-entered while a prior `dispatch()` call for the same or a different app is still executing and holding funds. At minimum, ensure no `Call[]` execution can leave the dispatcher holding value across an external call boundary that a re-entrant `dispatch()` invocation could observe and spend.

### Proof of Concept
1. Attacker crafts `HyperFungibleToken.send(SendParams{ to: CallDispatcher, amount: X, data: calls })` where `calls[0]` targets `MaliciousRouter.doSomething()`.
2. On the destination chain, `onAccept` mints `X` tokens to `CallDispatcher`, then calls `CallDispatcher.dispatch(calls)`. [5](#0-4) 
3. Inside `to.call{value:...}(call.data)` execution of `calls[0]`, `MaliciousRouter` re-enters `CallDispatcher.dispatch(attackerCalls)` with `attackerCalls = [Call{to: HFTtoken, data: transfer(attacker, X)}]`.
4. Because `dispatch()` has no caller check and no reentrancy guard, the reentrant call executes immediately, transferring the `X` tokens currently held by `CallDispatcher` to the attacker before the original `calls` array finishes. [1](#0-0)
