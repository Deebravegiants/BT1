### Title
Login endpoint leaks user existence via authentication timing side-channel - (File: `core/sessions/localauth/orm.go`)

### Summary
`CreateSession` in the local authentication provider looks up the user by email and, only if found, performs a bcrypt password comparison. When the email does not exist, the function returns immediately without ever calling the (deliberately expensive) bcrypt comparison, creating a measurable timing difference between "user does not exist" and "user exists, wrong password" responses — the same bug class as CVE-2016-6210 (OpenSSH username enumeration via password-hashing timing difference).

### Finding Description
`orm.CreateSession` first performs `FindUser` and returns an error immediately on failure, before any password hashing work is done: [1](#0-0) 

If the email exists, `utils.CheckPasswordHash` calls `bcrypt.CompareHashAndPassword`, which is intentionally slow (bcrypt cost factor): [2](#0-1) 

For a non-existent email, the request path is: parse JSON → SQL lookup (fast, indexed, sub-millisecond) → return error. For an existing email, the path additionally executes a bcrypt hash comparison at `bcrypt.DefaultCost`, which takes on the order of tens of milliseconds. No dummy/constant-time hash operation is performed for the non-existent-user case to equalize response latency, unlike the fix introduced in OpenSSH 7.3 for CVE-2016-6210 (which performs a bogus BLOWFISH hash on a static password when the user doesn't exist).

This endpoint is reachable unauthenticated via `POST /sessions`: [3](#0-2) 

The same pattern (fast failure on unknown email prior to any expensive hash work) also exists in the LDAP and OIDC local-fallback authenticators: [4](#0-3) [5](#0-4) 

### Impact Explanation
An unauthenticated remote attacker can send repeated login attempts with candidate emails and measure response latency to determine whether an email is a registered chainlink node operator/API user, without needing valid credentials. This enables user enumeration, which can be leveraged to target credential-stuffing, phishing, or brute-force attacks against confirmed valid accounts on the node's API/GUI. Impact is limited to confidentiality of account existence (no direct authentication bypass), consistent with the Medium severity of the underlying CVE.

### Likelihood Explanation
The `/sessions` endpoint is unauthenticated and internet-facing (subject to network exposure of the operator UI), and timing side channels for bcrypt (tens of ms) vs a fast SQL miss (sub-ms) are typically easy to distinguish statistically over a modest number of samples, even over a network, making exploitation practical for a patient unprivileged attacker.

### Recommendation
Perform a constant-time-equivalent operation regardless of whether the user exists — e.g., always run `bcrypt.CompareHashAndPassword` against a fixed dummy hash when `FindUser` fails, before returning the generic "invalid credentials" error, so that response timing is independent of whether the email exists. Apply the same fix to the LDAP and OIDC local login fallback paths.

### Proof of Concept
1. Send `POST /sessions` with a known-valid email and an incorrect password; measure response time (includes bcrypt compare, tens of ms).
2. Send `POST /sessions` with a random/nonexistent email and any password; measure response time (SQL miss only, sub-ms).
3. Repeat and average over many samples for statistical confidence; the consistent latency gap reveals which candidate emails correspond to real accounts, e.g. by timing `sc.App.AuthenticationProvider().CreateSession` invoked from `core/web/sessions_controller.go` `Create`.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

// CheckPasswordHash wraps around bcrypt.CompareHashAndPassword for a friendlier API.
func CheckPasswordHash(password, hash string) bool {
	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	return err == nil
}

		return
	}

	// Does this user have 2FA enabled?

		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}

func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}
