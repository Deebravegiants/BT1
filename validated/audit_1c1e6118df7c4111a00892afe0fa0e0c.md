### Title
Webhook `shop`, `topic`, and `webhook_id` identity fields are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), routing (`topic`), and idempotency (`webhook_id`) fields from raw, unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the raw request body via `to_signable_string`. `Registry.process` trusts these header-derived fields to dispatch to a handler and to populate `WebhookMetadata`, without the HMAC binding them to the body.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256`/`x-shopify-hmac-sha256` header: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` only checks the HMAC of `verifiable_query.to_signable_string` (i.e. the body) against the secret: [3](#0-2) 

`Registry.process` calls `HmacValidator.validate(request)` and, if it passes, immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (none of which are part of the signed bytes) to build `WebhookMetadata` and dispatch the handler: [4](#0-3) 

The identity binding that should hold is: `shop header == shop bound inside the HMAC-signed payload`. In this implementation that equality is never enforced — the HMAC only proves `raw_body` was signed with the app's secret; it says nothing about which shop the header claims to be. This is the same class of "bytes verified versus bytes/field acted on" mismatch described in the external report (there, the `amount` acted upon by Yearn's `withdraw()` was not the same quantity that was verified/expected; here, the `shop` field acted upon by the handler is not the field verified by the HMAC).

### Impact Explanation
Because the app's `api_secret_key` is shared across all shops that install the app (it is not per-shop), any party capable of obtaining one valid `(raw_body, hmac)` pair for the app — for example a merchant who installs the app and receives a legitimate webhook for their own shop — can replay that exact body/HMAC pair while substituting the `shop-domain` header with an arbitrary other shop's domain. `HmacValidator.validate` still returns `true` (it only checks body+secret), and `Registry.process` will hand the attacker-chosen `shop` value to the host app's handler as if it were an authentic event for that shop. If the host application uses `WebhookMetadata#shop` to key data writes, cache invalidation, or session/token lookups (the documented and expected usage pattern), this allows cross-tenant data confusion: attacker-controlled body content can be attributed to a victim shop, or a victim's legitimate payload can be relabeled to point at a shop the attacker controls, without needing the app's `client_secret` or any privileged access — only participation as an ordinary installed merchant is required.

### Likelihood Explanation
Requires only unprivileged access: install the app to any shop (or observe one legitimate webhook delivery), capture a valid `(body, hmac)` pair, then send a request to the app's webhook endpoint with a forged `shop-domain` (and optionally `topic`/`webhook-id`) header while keeping the original body and HMAC. No secret material, tokens, or elevated privileges are needed to construct the forged header set, since none of it is covered by the signature.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is HMAC-verified, or independently authenticate the header-derived `shop` against a value derived from data the app already trusts (e.g., cross-check against the shop associated with the webhook subscription id via a signed/opaque token, or require the host app to look up and pin the expected shop before trusting the header). At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are **not** covered by the HMAC and must not be used as sole tenant/routing identifiers without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers (or waits for) a real webhook, capturing `raw_body = B` and header `x-shopify-hmac-sha256 = H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body (`lib/shopify_api/webhooks/request.rb` lines 45-63) and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body` (`lib/shopify_api/webhooks/registry.rb` line 190; `lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199) and processes attacker-controlled body content as if it belonged to the victim shop. [5](#0-4) [4](#0-3)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
