### Title
Shopify Webhook `shop` (and `topic`/`webhook-id`/`api-version`) Header Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC over the raw request body only, while the tenant-identifying `shop` (and `topic`, `webhook-id`, `api-version`) values are taken from unauthenticated HTTP headers. `Registry.process` trusts these header-derived values when dispatching webhook data to the app's handler, breaking the binding: `shop that authenticated (via body+secret) == shop the app attributes the event to`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC solely over that signable string: [2](#0-1) 

Meanwhile `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read straight from HTTP headers with no cryptographic tie to the body or the HMAC: [3](#0-2) 

`Registry.process` only checks the body HMAC, then forwards the header-derived `shop`, `topic`, and `webhook_id` straight to the app's handler as authoritative identifiers: [4](#0-3) 

Because the app's `api_secret_key` is shared across all shops installed on the app (it is not per-shop), any legitimate webhook received by one merchant's own store is HMAC-valid material for that same app instance. An entity that controls or intercepts webhook delivery for their own shop (an "unprivileged" user with respect to any other tenant of the multi-tenant app) can take a genuine, HMAC-valid webhook body they received and re-submit it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header altered to name a different, victim shop. `Utils::HmacValidator.validate` still succeeds because it only inspects the body, so `Registry.process` happily calls the handler with `WebhookMetadata` claiming the event belongs to the victim shop: [5](#0-4) 

This is the exact class of bug called out in scope: "a field acted on but not covered by the HMAC" — here `shop` (and topic/webhook-id) is acted on by the handler dispatch logic but excluded from the signed material.

### Impact Explanation
Any app built on this gem that uses `data.shop` from `WebhookMetadata` to key business logic (e.g., recording uninstalls, disabling billing, updating per-shop settings, deleting per-shop records) can be made to apply that logic to a shop the attacker does not own — a cross-tenant data-integrity/authorization violation. Depending on the webhook topic used (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`), this can trigger destructive or state-changing actions against an arbitrary victim tenant of the app, which is a cross-tenant impact.

### Likelihood Explanation
Requires an attacker to install the vulnerable app on at least one shop they control (readily available to any unprivileged Shopify merchant/developer) and to capture one legitimate HMAC-valid webhook body for a topic whose payload doesn't itself expose enough shop-specific identifying data. No access to `api_secret_key`, access tokens, or the victim's credentials is required — only network-level ability to POST to the app's public webhook endpoint with attacker-chosen headers, which any internet user with the endpoint's URL has.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook-id`) into the material verified by the HMAC, or otherwise cross-check the header-derived shop against a value embedded in the verified payload / an established session record for that webhook subscription, before using it to key any state-changing operation. At minimum, document that `Request#shop` is unauthenticated and must not be trusted as a tenant identifier without additional server-side verification (e.g., matching against the app's known list of installed shop domains that this app registered webhooks for).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g. a topic whose body carries no shop-identifying fields) and captures the raw request: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
3. Attacker resends the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` passes because it only checks `B` against `H`, per [1](#0-0) .
5. `Registry.process` invokes the handler with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, per [4](#0-3) , causing the app to act on the victim tenant's behalf despite the request never having been sent by or for that tenant.
