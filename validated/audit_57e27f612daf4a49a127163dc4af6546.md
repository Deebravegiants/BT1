I have sufficient evidence to finalize the finding on the webhook HMAC scope issue.

### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` values are trusted for tenant routing despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only the raw request body against the HMAC signature, then dispatches to the topic handler using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all of which are read directly from unauthenticated HTTP headers and never enter the HMAC computation.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `api_version`, and `webhook_id` are parsed straight from the `shopify-*`/`x-shopify-*` headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC over that body-only signable string, and — once it passes — builds `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`, passing it to the app's handler as the trusted tenant/topic identity: [3](#0-2) 

The equality the gem implicitly asserts is: `HMAC_valid(raw_body) == (shop, topic, webhook_id, api_version are authentic)`. That equality does not hold, because none of those fields are part of the signed material. Since the webhook signing secret (`api_secret_key`/`client_secret`) is the same for every shop that has installed a given app (it is per-app, not per-shop), any unprivileged internet user who can install the app on a shop they control can trigger a webhook delivery with an attacker-chosen body, capture the resulting valid `(raw_body, hmac)` pair from their own shop's webhook delivery, and then directly POST that same body+HMAC pair to the app's public webhook endpoint while forging the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to name a victim shop. `Registry.process` will accept the HMAC (it is valid for that body under the shared app secret) and hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
Any host application that follows this gem's documented processing flow (`docs/usage/webhooks.md`, mirroring `Registry.process`) and uses `WebhookMetadata#shop` to attribute/store data or trigger shop-scoped side effects (e.g., updating records, calling back into the victim's session/access token, fan-out to shop-specific workflows) can be made to act on attacker-controlled content while believing it originated from a different, victim tenant. This is a cross-tenant data/action confusion enabled purely by an unauthenticated request crafted by a party with no privileges on the victim shop.

### Likelihood Explanation
Requires only (1) the ability to install the target app on any shop, including a free/dev store the attacker controls, and (2) triggering one webhook delivery whose body content the attacker can influence to any degree needed, then replaying it with forged headers. No secret key, access token, or victim credential is needed — only the shared app-level HMAC secret's *effect* is reused, not its value.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-covered signable string (or otherwise cryptographically bind them to the verified body), or document/enforce that consuming apps must independently verify `shop` against a known/installed-shop registry and correlate `webhook_id`/`topic` before trusting `WebhookMetadata` for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a real webhook (e.g., `products/update`) with a body they control, and captures the resulting `x-shopify-hmac-sha256` header — valid because it's computed as `HMAC_SHA256(api_secret_key, raw_body)`, a value independent of the shop.
3. Attacker POSTs the same `raw_body` and captured `hmac` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, forges `x-shopify-topic`/`x-shopify-webhook-id`).
4. `Utils::HmacValidator.validate(request)` succeeds (per [4](#0-3) ) since it only checks `raw_body` against the shared secret.
5. The app's handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)` and processes it as if it were a legitimate webhook from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
