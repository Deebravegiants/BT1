### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an inbound webhook by validating only the raw request body against the HMAC signature, while the `shop` (tenant identity) is read directly and unauthenticated from the `x-shopify-shop-domain` / `shopify-shop-domain` header. `Registry.process` passes this unauthenticated `shop` value straight to the app's `WebhookHandler`, so the value the handler trusts as "which merchant this webhook belongs to" is never bound by the cryptographic signature that is supposed to prove the request is genuine.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from a header with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then immediately forwards the untrusted `request.shop` value into `WebhookMetadata`, which is delivered to the app's handler as the authoritative tenant identity: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no further verification, and `WebhookHandler#handle` receives it as trusted input: [4](#0-3) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body, for webhooks) against the secret — it never incorporates the `shop` header: [5](#0-4) 

**Identity binding broken (as an equality):**
`shop_bound_by_hmac == shop_used_by_handler` is expected to hold, but in fact:
`shop_used_by_handler = request.shop` (attacker-controlled header)
`shop_bound_by_hmac = ` — nothing; the HMAC covers only `@raw_body`, so `shop_bound_by_hmac` does not exist as a checked value at all.

**Attack path (unprivileged internet user, no secrets required):**
1. Because Shopify webhook HMACs are computed with the *app's* `client_secret`, the same secret authenticates webhooks for every shop that has the app installed. An attacker who controls (or is) any one shop that has the app installed can install the app on their own store and receive a genuine webhook delivery — a legitimate `(raw_body, hmac)` pair signed with the app's secret.
2. The attacker replays that exact `raw_body` + `hmac-sha256` header to the app's public webhook endpoint, but substitutes the `x-shopify-shop-domain` header with a different (victim) shop's domain.
3. `HmacValidator.validate` succeeds, because it only checks the body against the secret — it never checks `shop`. `Registry.process` then calls the handler with `WebhookMetadata(shop: <victim-shop>, body: <attacker's own body>)`.
4. The host application, trusting the library's "signature validated" guarantee, processes/stores this body as if it originated from the victim shop — a cross-tenant data-injection / spoofing primitive (e.g. poisoning per-shop caches, order records, or triggering per-shop side effects keyed by the spoofed `shop` field).

This is exactly the “field acted on but not covered by the HMAC” class from the report, applied to this gem's own webhook-verification code rather than the referenced smart contract.

### Impact Explanation
This qualifies as **Critical — cross-tenant access**: an attacker with no privileged credentials (no access token, no `api_secret_key`, no leaked credentials) can cause the library to hand an application webhook data falsely attributed to an arbitrary victim shop, purely by controlling the unauthenticated `shop-domain` header on an otherwise-genuine signed payload. The library's `Utils::HmacValidator.validate(request)` call gives a false assurance that the *entire request* (including tenant identity) is authentic, when it only proves the body's authenticity.

### Likelihood Explanation
Likelihood is realistic but conditioned on the attacker being able to obtain at least one genuine `(body, hmac)` pair signed by the target app's secret — trivially achievable by installing the same public app on an attacker-controlled shop (any app publicly installable satisfies this). No brute-forcing of the HMAC is required; the attacker only forges the unauthenticated header, not the signature itself.

### Recommendation
- Include the `shop-domain` (and ideally `webhook-id`, `api-version`, `topic`) in the HMAC-signed material, or otherwise separately verify that the shop present in the webhook belongs to a session/installation the app recognizes before trusting it.
- At minimum, document/warn that `WebhookMetadata#shop` is not cryptographically authenticated and must not be used as a sole tenant-identity source by consuming applications; provide a library-level cross-check (e.g., verifying the shop against records of shops that have this webhook's `topic` registered) before dispatch to the handler.

### Proof of Concept
```ruby
require "shopify_api"

ShopifyAPI::Context.setup(
  api_key: "key",
  api_secret_key: "shared_app_secret", # same secret is used for every installed shop
  api_version: "2024-01",
  scope: ["read_orders"],
  is_private: false,
  is_embedded: true,
)

# Step 1: Attacker's own shop legitimately receives a webhook, giving them
# a valid (raw_body, hmac) pair signed with the app's shared secret.
genuine_body = '{"id":1,"note":"legit payload from attacker-owned shop"}'
genuine_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "shared_app_secret", genuine_body)
)

# Step 2: Attacker replays the same body+hmac, but spoofs shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => genuine_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: genuine_body, headers: forged_headers)

# HMAC validation passes because it only checks the body, not the shop header
puts ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process will now hand the handler a WebhookMetadata claiming
# this attacker-controlled body came from "victim-shop.myshopify.com"
ShopifyAPI::Webhooks::Registry.process(request)
```
`ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` even though `shop` was changed after signing, because the signable string (`request.to_signable_string`) is only `@raw_body`, confirming the shop identity is never bound by the signature.
