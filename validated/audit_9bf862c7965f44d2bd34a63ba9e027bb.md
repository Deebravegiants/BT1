### Title
Webhook `shop-domain`, `topic`, `webhook-id` and `api-version` headers are trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the shop identity, topic, webhook id and API version are read directly from HTTP headers that are never part of the signed material. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then trusts the unverified `shop` header when invoking the app's handler, breaking the binding "the shop the HMAC was generated for" == "the shop the handler is told the event belongs to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the signature only over `to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` relies solely on this body-only HMAC check, then forwards the unverified `request.shop` (and `topic`/`webhook_id`/`api_version`) straight to the app's handler: [4](#0-3) 

The documented usage pattern explicitly tells integrators to key their tenant logic off `data.shop` from the handler: [5](#0-4) 

Equality that should hold but doesn't: `shop_bound_by_hmac(raw_body, api_secret_key) == request.shop_header`. Because the HMAC only signs `raw_body`, any request carrying a `raw_body`/`hmac` pair that is valid for the app's secret (e.g. one legitimately delivered to the attacker's own shop) will pass `HmacValidator.validate` regardless of what `shop-domain` (or `topic`/`webhook-id`/`api-version`) header value accompanies it. An unprivileged merchant who has installed the app can capture a genuine webhook Shopify sent for their own store (valid body + valid HMAC, generated with the app's real `api_secret_key`, which the attacker never needs to know) and replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header value naming another (victim) merchant's shop. The signature check still succeeds because it never inspected the header.

### Impact Explanation
This crosses a tenant boundary without any credential belonging to the victim: the app's webhook handler will process attacker-controlled body content while believing it originates from the victim shop (`data.shop`), or vice-versa can be used to misattribute the attacker's own data to another tenant. Depending on how the host app uses `data.shop` (documented as the primary key for looking up sessions/tenants, per `docs/usage/webhooks.md`), this can lead to actions being executed against the wrong merchant's session/store, cross-tenant data corruption, or unauthorized state changes recorded under another merchant's account — matching the "cross-tenant access" Critical impact category. No `api_secret_key`, access token, or privileged account is required; only normal, unprivileged use of the app by any merchant that has it installed.

### Likelihood Explanation
Likelihood is high for any merchant who has installed the vulnerable app: they naturally receive genuine, validly-signed webhook deliveries for their own shop and can freely resend them with a modified `shop-domain` header (and/or `topic`/`webhook-id`) to the app's public webhook endpoint, since none of those headers factor into `to_signable_string`. No secret material or brute forcing is needed — only capturing one legitimate webhook delivery.

### Recommendation
Include the identity-critical fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them (e.g., verify `shop` against session/tenant data associated with the webhook subscription id rather than trusting the header). At minimum, `Request#to_signable_string` should incorporate the shop domain and topic so `HmacValidator.validate` fails when they are altered, and `Registry.process` should not surface an unauthenticated `shop` value to handlers as if it were verified.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(B, api_secret_key)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this request (they control the receiving endpoint/logs for their own shop).
3. Attacker resends the identical `raw_body` and `hmac` header to the app's webhook route, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(raw_body, api_secret_key)` — this still matches, so validation passes: [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, and any tenant-scoped logic keyed on `data.shop` now operates on the wrong tenant.

```ruby
          received_signature = verifiable_query.hmac
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
