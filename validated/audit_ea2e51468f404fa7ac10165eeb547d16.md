Webhook tenant identity (`shop`, `topic`, `webhook_id`, `api_version`) is not bound by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Utils::HmacValidator.validate` checks covers nothing but the body bytes. All identity fields the gem hands to app webhook handlers — `shop`, `topic`, `webhook_id`, `api_version` — are read straight from HTTP headers that are never part of the signed material. Any party that possesses one valid `(body, hmac)` pair signed with the app's secret can replay it with an arbitrary `x-shopify-shop-domain` header and the app will process it as if it came from that shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and the `shop`, `topic`, `webhook_id`, `api_version` accessors are all pulled from headers that are excluded from that signable string: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only ever verifies `verifiable_query.to_signable_string` against the computed HMAC — i.e., only the raw body: [3](#0-2) 

`Registry.process` performs exactly this body-only check and then immediately trusts the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This is the exact binding break called out by the rules: "a field acted on but not covered by the HMAC." The equality that should hold is:
`hmac-verified bytes == identity fields the handler acts on`
but in this gem:
`hmac-verified bytes (raw_body only) ⊂ identity fields acted on (raw_body ∪ shop ∪ topic ∪ webhook_id ∪ api_version)`

Since Shopify signs webhooks with the app's own `client_secret` regardless of which shop triggered the delivery, an unprivileged user who has merely installed the target app on their own (attacker-controlled) development store receives genuine `(body, hmac)` pairs signed with the real secret. Because the header set is outside the signature, that same `(body, hmac)` pair remains valid when replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to any victim shop domain — the check in `Registry.process` still passes, and the handler executes with `data.shop` equal to the attacker-chosen value.

### Impact Explanation
This breaks the tenant/shop identity boundary the app relies on to route webhook side effects (e.g., updating per-shop state, marking `app/uninstalled`, deleting shop resources, disabling features) — the handler acts on `data.shop` believing it was cryptographically bound to the specific delivery, when it was not. That constitutes cross-tenant access/confusion using only a credential the attacker already legitimately possesses (their own installation's webhook signature), matching the report's Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any unprivileged individual capable of installing the target app on a shop they control (a normal, unprivileged operation) can capture a valid webhook delivery and its HMAC, then resend it to the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged account is required — only observation of the app's own legitimately-delivered webhook traffic.

### Recommendation
Bind the tenant/topic identity into the verified material instead of trusting bare headers:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in `to_signable_string` (or otherwise cryptographically bind them, e.g., verify `shop` against a store-specific secret or a previously-registered webhook/shop record) before constructing `WebhookMetadata`.
- At minimum, require app-side verification that `request.shop` matches a shop with an active session/installation before invoking the handler, rather than passing the raw header value straight through in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own dev store `attacker.myshopify.com`, receives a real webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker resends the same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` — still equal to `H` since the body `B` is unchanged — so validation succeeds. [5](#0-4) 
4. The app's `WebhookHandler#handle` executes with `data.shop == "victim-shop.myshopify.com"`, even though the delivery never originated from that shop.
