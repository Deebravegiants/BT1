### Title
Webhook shop identity spoofing — HMAC covers only the raw body, not the `X-Shopify-Shop-Domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches to the app's handler using the `shop` value taken from an unauthenticated HTTP header. The binding `shop_authenticated == shop_dispatched_to_handler` does not hold, because `shop` is never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, independent of the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (the raw body) and compares it to the `hmac` value, using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` treats a valid HMAC as authentication for the *entire* request, then immediately forwards `request.shop` (an unauthenticated header) into `WebhookMetadata`, which is handed to the app's registered handler as the tenant identity for this event: [4](#0-3) 

Because the shop-domain header is never covered by the HMAC signature, an attacker who controls (or has installed the app on) their own Shopify store can receive a legitimately-signed webhook body/HMAC pair for their own store from Shopify, then replay that same body and HMAC to the target app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body and HMAC still match), but the handler is invoked with `WebhookMetadata.shop` set to the victim's domain rather than the attacker's own store. Any app logic that trusts `data.shop` to select which tenant's records to update/look up (a very common pattern for webhook handlers) can be tricked into acting on behalf of, or misattributing input to, a different tenant — a cross-tenant confusion condition rooted entirely in this gem's authentication primitive, not in host-application misuse.

### Impact Explanation
This breaks the identity binding "shop authenticated == shop the app acts on," letting an attacker who has valid installation on shop A but not shop B cause the app to process attacker-controlled webhook payload/shop-domain combinations as if they originated from shop B. Depending on how the host app implements handlers (a documented, expected usage pattern — passing `data.shop` straight into per-tenant lookups), this yields cross-tenant data confusion/access, matching the "cross-tenant access" Critical-impact category defined for this analysis.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app (or any app using this library) on a Shopify store they control and receive at least one genuine webhook for a topic/body they can reuse, and that they can send arbitrary HTTP requests with attacker-chosen headers to the target app's public webhook endpoint. No possession of the app's `api_secret_key` or access tokens is required — the attacker only reuses a validly-signed body+HMAC pair they legitimately received for their own store. This is squarely in-gem behavior (`Webhooks::Request`/`Registry`/`HmacValidator`), not host-application misuse of documented API, so likelihood is moderate-to-high wherever handlers key any authorization/data-access decision off `WebhookMetadata#shop`.

### Recommendation
Bind the shop identity into the authenticated material: either include the `X-Shopify-Shop-Domain` (and ideally `topic`/`webhook-id`) header value in the signable string used for HMAC verification, or independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting it in `WebhookMetadata`. At minimum, document prominently that `shop` on `WebhookMetadata` is unauthenticated by the HMAC check and must not be used for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook of a subscribed topic (e.g., `orders/create`) for that store, capturing the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since Shopify signed `B` with the shared `api_secret_key`).
2. Attacker replays the identical request to the same app's webhook endpoint but changes `X-Shopify-Shop-Domain` from `attacker-shop.myshopify.com` to `victim-shop.myshopify.com` (and, if desired, `X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over body `B` only [5](#0-4)  — validation succeeds because `B` and `H` are unchanged.
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: request.shop, body: ..., ...)` using the attacker-modified `shop` header [6](#0-5)  and invokes the app's handler, which now believes this event originated from `victim-shop.myshopify.com`.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
