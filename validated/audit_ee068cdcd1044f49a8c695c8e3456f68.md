### Title
Double-entry token accounting bypass mints unbacked shielded value via `Hinkal.transact`'s per-index `balanceDif` check - (File: contracts/Hinkal.sol)

### Finding Description
The invariant `transact` relies on is: for each index `i`, `balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]`, where `balanceDif[i]` is derived purely from `getBalancesForArray(circomData.erc20TokenAddresses)` snapshots taken via `IERC20(erc20TokenAddresses[i]).balanceOf(address(this))` before and after the action [1](#0-0) , and compared against `amountChanges[i]` at [2](#0-1) .

`erc20TokenAddresses` is fully attacker-controlled calldata and there is no uniqueness or economic-independence check on its entries anywhere in `dimensionsCheck` or `checkOnchainCreation` [3](#0-2) . An attacker can deploy two distinct token contracts, `RealToken` (address `T1`) and `AliasToken` (address `T2`), where `AliasToken.balanceOf` simply forwards to/reads the same underlying balance as `RealToken` (e.g., by delegating the view call, or by both contracts reading a shared external storage contract), but `AliasToken.transferFrom` is a no-op that returns `true` without moving any value.

For an internal transaction (`externalActionData.externalActionId == 0`), `checkOnchainCreation` forces all `onChainCreation[i] == false` [4](#0-3) , and `_internalTransact` executes a real `transferERC20TokenFromOrCheckETH` call **per index**, independently, based only on `amountChanges[i]` [5](#0-4) . The attacker sets:
- index `i`: `erc20TokenAddresses[i] = T1`, `amountChanges[i] = X` → real `transferFrom` pulls `X` real tokens into the vault, increasing the shared balance by `X`.
- index `k`: `erc20TokenAddresses[k] = T2` (alias), `amountChanges[k] = X` → `_internalTransact` calls `T2.transferFrom(...)`, which the attacker implemented as a no-op, so **no additional value enters the vault**.

When `transact` snapshots `oldBalances`/`newBalances` for both `T1` and `T2` via `getBalancesForArray`, both indices observe the *same* underlying balance increase of `X` (because `T2.balanceOf` mirrors `T1`'s storage). Thus `balanceDif[i] == X == amountChanges[i]` and `balanceDif[k] == X == amountChanges[k]` **both hold**, even though only `X` tokens (not `2X`) ever entered the vault. The circuit only enforces `inTotal + amountChanges === outTotal` per opaque token slot; it has no way to know that `erc20TokenAddresses[i]` and `erc20TokenAddresses[k]` are economically the same asset, so it happily lets the prover mint `2X` worth of shielded UTXOs (off-chain commitments) backed by only `X` real tokens. This can be repeated across every additional index up to the maximum `dimensions.tokenNumber` array length, multiplying the unbacked mint by the number of alias slots used.

None of the existing guards catch this: `performHinkalChecks`/`dimensionsCheck` only check array-length equality, not address distinctness or economic independence [3](#0-2) ; `verifyProof` only checks the circuit's internal per-slot arithmetic, not cross-slot real-world token identity; the on-chain `balanceDif` check is the only economic backstop and it is defeated because it trusts `balanceOf` per address in isolation [2](#0-1) .

### Impact Explanation
The attacker mints shielded UTXOs (off-chain commitments) representing `N*X` value while only depositing `X` real tokens into the vault, where `N` is the number of colluding alias addresses included in `erc20TokenAddresses` (bounded by `dimensions.tokenNumber`). This is a direct protocol-insolvency exploit: minting shielded value without backing, matching the "Critical" category. The attacker can later spend these UTXOs via normal nullifier-based withdrawals, draining real assets deposited by other users. The attack is repeatable per transaction and scales with the maximum permitted token-array length.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: deploying two ERC20-like contracts sharing a balance view but with an inert `transferFrom` on one of them, and calling `transact` with a self-generated proof for an internal transaction (`externalActionId == 0`, so no admin-registered external action is required). Cost is just gas plus one real deposit of `X`; no special permissions, relay, or victim interaction is needed. Feasibility is high because Solidity trivially allows constructing such an "alias" contract, and nothing in `dimensionsCheck`/`checkOnchainCreation`/`transact` rejects duplicate-address economic aliasing.

### Recommendation
Enforce that `erc20TokenAddresses` entries are pairwise distinct token identities that cannot alias the same balance, e.g.:
- Require strict `erc20TokenAddresses` array is sorted with no duplicate addresses (cheap, but does not stop cross-contract aliasing of the same underlying balance).
- More robustly, snapshot balances using a canonical/allowlisted token registry rather than raw attacker-supplied addresses, or bind the accounting to a single authoritative `balanceOf` call combined with verifying `extcodehash`/registry membership so an attacker cannot introduce a second contract that mirrors another token's balance.
- Alternatively, compute a single aggregate "net value transferred" per unique underlying balance source (e.g., require the sum of `amountChanges` per distinct address to equal the true `balanceOf` delta, and reject any two indices whose addresses are different but whose balances move identically without an independent minimal transferFrom effect) — in practice, the safest fix is restricting `erc20TokenAddresses` to a governance-controlled allowlist of vetted token contracts.

### Proof of Concept
Foundry test plan:
1. Deploy `RealToken` (standard ERC20) and `AliasToken` where `AliasToken.balanceOf(a)` returns `RealToken.balanceOf(a)` (e.g., via a static call to `RealToken`) but `AliasToken.transferFrom` returns `true` without any state change.
2. Mint the attacker `X` `RealToken` and approve `Hinkal` for `X`.
3. Build `CircomData` for an internal `transact` (`externalActionId = 0`) with:
   - `erc20TokenAddresses = [RealToken, AliasToken]`
   - `amountChanges = [X, X]`
   - `onChainCreation = [false, false]`
   - `slippageValues = [X, X]`
   - off-chain output commitments encoding `X` of `RealToken` and `X` of `AliasToken` in the shielded set (generate locally with the real circuit/prover for a valid proof).
4. Call `Hinkal.transact(...)`.
5. Assert:
   - `RealToken.balanceOf(vault) - balanceBefore == X` (only `X` real tokens entered).
   - The transaction succeeds (both `balanceDif` checks pass), and the shielded tree now contains commitments totaling `2X` (`X` under `RealToken`'s slot, `X` under `AliasToken`'s slot).
   - Confirm `2X` (credited UTXO value) > `X` (actual vault balance delta), demonstrating protocol insolvency.

    function _internalTransact(CircomData calldata circomData) private {
        bool hasPaidToRelay = false;
        for (uint64 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 deltaAmountChange = _calculateDeltaAmount(circomData, i);

            if (deltaAmountChange > 0) {
                require(
                    circomData.externalActionData.externalAddress == msg.sender,
                    "Deposit should come from the sender"
                );
                transferERC20TokenFromOrCheckETH(
                    circomData.erc20TokenAddresses[i],
                    circomData.externalActionData.externalAddress,
                    address(this),
                    uint256(circomData.amountChanges[i])
                );
            } else {
                uint256 sumAbs = uint256(-deltaAmountChange);
                uint256 relayFee = 0;
                if (circomData.relay != address(0)) {
                    uint256 flatFee = circomData.feeStructure.feeToken ==
                        circomData.erc20TokenAddresses[i]
                        ? circomData.feeStructure.flatFee
                        : 0;

                    require(
                        sumAbs >= flatFee,
                        "Relay Fee is over withdraw amount"
                    );

                    uint256 recipientAmount = ((10000 -
                        circomData.feeStructure.variableRate) *
                        (sumAbs - flatFee)) / 10000;

                    relayFee = sumAbs - recipientAmount;

                    if (relayFee > 0) {
                        transferERC20TokenOrETH(
                            circomData.erc20TokenAddresses[i],
                            circomData.relay,
                            relayFee
                        );
                    }
                    hasPaidToRelay = true;
                }
                if (sumAbs - relayFee > 0) {
                    transferERC20TokenOrETH(
                        circomData.erc20TokenAddresses[i],
                        circomData.externalActionData.externalAddress,
                        sumAbs - relayFee
                    );
                }
            }
        }
        require(
            circomData.relay == address(0) || hasPaidToRelay,
            "relay not paid"
        );
    }
