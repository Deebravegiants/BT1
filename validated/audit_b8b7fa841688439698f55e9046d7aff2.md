## Title
Any authenticated node role (including ReadOnly) can retrieve a Bridge's plaintext OutgoingToken via `GET /v2/bridge_types/:BridgeName` - (File: core/web/router.go)

## Summary
The `/v2/bridge_types/:BridgeName` `Show` route is registered with only `auth.Authenticate` and no `auth.RequiresEditRole`/`RequiresAdminRole` wrapper, unlike the sibling `Create`, `Update`, and `Destroy` routes on the same resource. The handler returns `presenters.NewBridgeResource(bt)`, which unconditionally serializes the bridge's plaintext `OutgoingToken`, so any authenticated user regardless of role (including the lowest `UserRoleView`/ReadOnly role) can retrieve this credential.

## Finding Description
In `core/web/router.go`, bridge routes are registered as: [1](#0-0) 
`Create`, `Update`, and `Destroy` are wrapped with `auth.RequiresEditRole`, but `Index` and `Show` are not, so they're reachable by any principal that passes `auth.Authenticate` (session or API token) regardless of role.

`RequiresEditRole` explicitly blocks only `UserRoleView` and `UserRoleRun`, confirming that a `View`-role (ReadOnly) authenticated user would be rejected from mutation routes but is not blocked from `Show`: [2](#0-1) 

`BridgeTypesController.Show` fetches the bridge and serializes it with no field filtering: [3](#0-2) 

`presenters.NewBridgeResource` always populates `OutgoingToken` from the raw `bridges.BridgeType.OutgoingToken` field, which has no `omitempty` tag (unlike `IncomingToken`, which is only set at creation time and tagged `omitempty`): [4](#0-3) 

The underlying `BridgeType.OutgoingToken` DB field is stored in plaintext (`db:"outgoing_token"`), in contrast to `IncomingTokenHash`/`Salt`, confirming there is no cryptographic protection preventing disclosure once read: [5](#0-4) 

No other middleware, redaction, or role check intervenes between the raw ORM fetch and JSON serialization in `Show`.

## Impact Explanation
This maps to a valid in-scope Chainlink impact category: node API role bypass / unauthorized secret disclosure. `OutgoingToken` is a bridge credential (the analog of an outbound webhook secret used when the node interacts with the bridge/external-adapter and related run-resumption flows). A low-privileged, authenticated `ReadOnly` (`UserRoleView`) user — who is expressly blocked from `Create`/`Update`/`Destroy` by `RequiresEditRole` — can still fully read every bridge's plaintext `OutgoingToken` via `Show` (and enumerate bridge names via the equally-unrestricted `Index`). This is a genuine authorization/role-scoping gap: the code's own security model (mutation routes require Edit role) is inconsistently applied to a route which discloses a sensitive credential.

## Likelihood Explanation
Exploitation requires only a valid, low-privileged authenticated session or API token (`ReadOnly`/View role) — a realistic scenario for node operators granting limited dashboard/monitoring access to third parties or automation tooling. No race conditions, admin access, host access, or social engineering are needed; a single `GET` request per bridge name is sufficient, and bridge names can be enumerated via the also-unrestricted `Index` route.

## Recommendation
Wrap `GET /v2/bridge_types/:BridgeName` (and `Index`) with `auth.RequiresEditRole` (or a comparable role check), matching the protection already applied to `Create`/`Update`/`Destroy`. Alternatively, omit `OutgoingToken` from `BridgeResource` for non-privileged roles/responses, mirroring the `omitempty`/create-only exposure pattern already used for `IncomingToken`, or hash/mask the value at rest analogous to `IncomingTokenHash`.

## Proof of Concept
1. Create a Chainlink node user with `View` (ReadOnly) role, or issue a ReadOnly-scoped API token.
2. As that user, `POST /v2/bridge_types` → expect `401 Unauthorized` (confirms `RequiresEditRole` blocks View role, per `core/web/auth/auth.go` lines 219-234).
3. As the same ReadOnly user, `GET /v2/bridge_types` to enumerate bridge names, then `GET /v2/bridge_types/<name>` for each.
4. Observe the JSON response body includes `"outgoingToken": "<plaintext token>"` (per `NewBridgeResource` in `core/web/presenters/bridges.go`) despite the caller lacking Edit/Admin privileges — this can be codified as a Go integration test hitting `BridgeTypesController.Show` with a `View`-role session/token and asserting the response contains the non-empty `outgoingToken` field.

func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
