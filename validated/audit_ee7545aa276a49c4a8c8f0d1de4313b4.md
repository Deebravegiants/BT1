Audit Report

## Title
Unscoped, user-controlled MessageID in gateway legacy handler allows cross-user callback hijack / response confusion - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`handler.HandleLegacyUserMessage` stores each pending trigger request's response callback in the shared `h.savedCallbacks` map keyed solely by the client-supplied `msg.Body.MessageID`, with no binding to the requesting client's identity (even though that identity is already recovered via signature verification). Because `Message.Validate()` only checks `MessageID` length/format and never enforces uniqueness or ties the ID to the verified `Sender`, an unprivileged client can submit a request reusing another client's `MessageID`, silently overwriting the map entry and causing a subsequent DON response to be delivered to the wrong caller.

## Finding Description
`Message.Validate()` computes and stores the cryptographically verified sender address in `m.Body.Sender` [1](#0-0) , but only validates `MessageID` for length and null-byte suffix, never for uniqueness or for being bound to that sender [2](#0-1) .

`gateway.ProcessRequest` is the internet-facing entrypoint: for any request carrying a non-empty `DonID` (a "legacy request"), it validates the message and dispatches directly to `h.HandleLegacyUserMessage`, reachable by any unprivileged client with no additional authorization [3](#0-2) .

Inside `HandleLegacyUserMessage`, the callback for the current request is stored unconditionally under `msg.Body.MessageID`, with no check for an existing entry and no association with `msg.Body.Sender`: [4](#0-3) 

When a DON node later responds with `MethodWebAPITrigger`, `handleWebAPITriggerMessage` looks up and deletes the entry purely by `MessageID`, then delivers the response to whatever callback is currently registered there: [5](#0-4) 

This confirms the broken assumption: the code treats `MessageID` as an implicit per-request nonce, but nothing prevents two different signers from using the same `MessageID`, and the second submission silently overwrites the first's callback registration. Notably, a newer/parallel mechanism (`handlers/common.RequestCache`) demonstrates the correct pattern by scoping responses to the request's `Sender`/`Receiver` pair [6](#0-5) , confirming this scoping is the intended security property that the legacy capabilities handler fails to enforce.

## Impact Explanation
This is a concrete cross-user response corruption primitive in the gateway's user-facing legacy webAPI-trigger path: an unprivileged, arbitrary client can cause another client's pending trigger response (or their own) to be misdirected by colliding `MessageID` values, since `savedCallbacks` provides no per-caller isolation despite the sender already being cryptographically known at validation time. This matches the in-scope "cross-user response corruption" impact class for the Chainlink gateway.

## Likelihood Explanation
Reachable directly from the internet-facing gateway endpoint via ordinary unprivileged legacy user requests (`gateway.ProcessRequest` → `HandleLegacyUserMessage`), with no operator/admin access, host access, or malicious-node/peer involvement required. Exploitability depends on the attacker being able to predict or intentionally reuse another client's `MessageID` and win a timing race before the legitimate response/pruning occurs; this is a design-level flaw (missing binding of the callback to the verified sender) rather than a purely theoretical one, and is fully triggerable by a single unprivileged client sending two normal-looking requests.

## Recommendation
Scope `savedCallbacks` entries by a composite key of `MessageID` plus the cryptographically verified `msg.Body.Sender` (already computed in `Message.Validate()`), and reject/reuse-check insertion if an active callback already exists for that composite key rather than silently overwriting it. Alternatively, adopt the same sender/receiver-scoped correlation pattern already used in `handlers/common.RequestCache` for this legacy handler's `savedCallbacks` map.

## Proof of Concept
1. Client A sends a legacy user message via the gateway with `MessageID = "X"`, signed by A; `Message.Validate()` succeeds and sets `Body.Sender = A`. `HandleLegacyUserMessage` stores `savedCallbacks["X"] = A's callback` (`handler.go:411-414`).
2. Before A's request completes, Client B sends its own legacy user message reusing `MessageID = "X"`, signed by B (`Validate()` has no uniqueness/ownership check against `MessageID`, `message.go:54-66`), overwriting the map entry: `savedCallbacks["X"] = B's callback`.
3. A DON node responds for the original request/ID `"X"`; `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's callback, deletes the entry, and delivers A's intended response to B instead (`handler.go:148-161`).

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
