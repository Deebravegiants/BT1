### Title
Webhook HMAC signs only the request body, not the `shop-domain`/`topic`/`webhook_id` headers, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated, attacker-controllable headers. `Utils::HmacValidator.validate` only verifies that the body matches the HMAC computed with the app's `client_secret`; it never binds the signature to those header values. Any party that can obtain one valid `(body, hmac)` pair signed with the app's secret (e.g. a merchant who legitimately installed the app and received one real webhook for their own shop) can replay that exact body/HMAC pair to the app's webhook endpoint while freely rewriting the `shop-domain`, `topic`, `webhook_id`, and `api_version` headers, since none of them are covered by the signature.

### Finding Description
`Request#hmac` and `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:10-38`) define the signed content as `@raw_body` only: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all derived from headers (`shopify_header`) that are never part of the HMAC input: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.to_signable_string` against the HMAC, i.e. it verifies only the body: [3](#0-2) 

`Registry.process` accepts any request whose body/HMAC pair validates, then dispatches the handler using `request.shop`, `request.topic`, and `request.webhook_id` taken directly from the (unverified) headers: [4](#0-3) 

Because the app's `client_secret` is a single shared secret used for every shop that has the app installed (not shop-specific), a valid `(body, hmac)` pair captured from one real, legitimately-delivered webhook remains valid forever for that body regardless of which shop or topic header accompanies it. This breaks the intended binding: `hmac(body) == valid` should imply `shop-domain header == the shop that produced this body`, but the code only enforces `hmac(body) == valid`, independent of `shop`/`topic`/`webhook_id`.

### Impact Explanation
An app-installing merchant (an "unprivileged" party relative to other tenants of the same multi-tenant app) can capture one genuine webhook payload/HMAC delivered to their own shop and replay it against the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a different, victim shop's domain (and/or the topic/webhook-id headers altered). Because `HmacValidator.validate` never checks those header values, the forged request passes validation and is routed to the registered handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain via `Registry.process`: [5](#0-4) 

If the host application uses `data.shop` to key per-tenant records (a common and documented usage pattern for this gem, matching the `MyApp::SessionRepository`/tenant model referenced in `docs/usage/oauth.md`), the attacker can inject or corrupt data attributed to a shop they do not own — a cross-tenant data-integrity/confidentiality issue. This satisfies the Critical "cross-tenant access" category since the identity binding between the cryptographically verified payload and the tenant identifier is absent.

### Likelihood Explanation
The prerequisite is modest: the attacker only needs one legitimately delivered webhook to their own installed shop (which any merchant who installs the app receives) — no leaked secret, token, or privileged access is required, satisfying the in-scope "unprivileged internet user" constraint. The attacker does not need to compute a new HMAC; they replay a previously valid one while forging non-signed headers. This is a realistic, moderately likely path for any host application that trusts `WebhookMetadata#shop` as the tenant identifier.

### Recommendation
Include the identity fields that the application relies on (`shop-domain`, `topic`, and ideally `webhook-id`) in the HMAC-signed content, or otherwise cryptographically bind them to the body (e.g., compute the signature over a canonical string containing body + shop + topic + webhook_id), so that a valid signature can only be replayed for the exact tuple of fields it was issued for. At minimum, document that `Request#shop`/`#topic` are unauthenticated and must not be trusted as tenant identifiers without additional verification (e.g., cross-checking against the shop stored for the session/access token used to register the webhook).

### Proof of Concept
1. App merchant "Attacker" installs the app on `attacker-shop.myshopify.com` and registers a webhook subscription (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Hmac-Sha256: <valid HMAC over raw body B>`
   - Body `B`
3. Attacker captures `(B, valid HMAC)`.
4. Attacker sends a new POST directly to the app's public webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a shop the attacker has never had access to).
5. `Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `hmac(B)` against the app secret and succeeds, per: [6](#0-5) 
6. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host application to process attacker-controlled content as if it originated from `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
