### Title
Precision drift between `TargetOrders.calc_pnl_x/calc_pnl_y` and actual pool reserves can permanently freeze Deposit/Withdraw on a pool - (File: program/src/processor.rs)

### Summary
`Processor::calc_take_pnl` uses a stored "high-water" invariant (`target.calc_pnl_x * target.calc_pnl_y`) as the baseline `k` that the current pool reserves must never fall below. Every `Deposit`, `Withdraw`, and `WithdrawPnl` instruction recomputes this baseline using lossy integer decimal-normalization math and enforces `pool_pc * pool_coin >= calc_pnl_x * calc_pnl_y`, erroring out otherwise. Because the baseline update math (`normalize_decimal_v2`/`restore_decimal`, which truncate) is not perfectly invertible, repeated deposit/withdraw cycles by ordinary, unprivileged LPs can drift the recorded baseline above the true reserve-derived value, permanently reverting all future `Deposit`/`Withdraw`/`WithdrawPnl` calls on that pool — an analog of the Napier "recorded scale exceeds actual backing" insolvency/freeze pattern.

### Finding Description
`calc_take_pnl` treats `target.calc_pnl_x`/`target.calc_pnl_y` as an ever-growing reference invariant, analogous to Napier's `maxScale`: [1](#0-0) 

If the actual current reserve product ever falls below this recorded baseline, the instruction hard-fails with `AmmError::CalcPnlError` instead of gracefully reconciling: [2](#0-1) 

This baseline is written on every `Deposit` (increasing it by the normalized deposited amount minus the newly realized pnl delta) and on every `Withdraw` (decreasing it by the normalized withdrawn amount minus the pnl delta): [3](#0-2) [4](#0-3) 

The normalization used throughout, `normalize_decimal_v2`/`restore_decimal`, performs integer division and is therefore lossy/non-invertible: [5](#0-4) 

Because deposit increases the baseline using one rounding path and withdraw decreases it using a different rounding path (floor-rounded LP-to-token conversion via `InvariantPool::exchange_pool_to_token`, then normalized and subtracted), the two operations are not exact inverses. Over repeated deposit/withdraw cycles — which any unprivileged LP can trigger with attacker-chosen amounts — the recorded `calc_pnl_x * calc_pnl_y` baseline can end up larger than what the actual reserves (`total_pc_without_take_pnl * total_coin_without_take_pnl`) support, causing `calc_take_pnl`'s invariant check to fail. The project's own test suite (`test_calc_pnl_precision`) explicitly exercises this exact deposit/withdraw-then-recompute cycle, indicating the precision boundary here is a recognized fragile area: [6](#0-5) 

Once `calc_take_pnl` starts failing for a pool, `process_deposit` and `process_withdraw` (both of which call it unconditionally except when status is `WithdrawOnly`) permanently revert: [7](#0-6) [8](#0-7) 

`WithdrawPnl` (owner fee collection) is likewise blocked, since it calls the same check: [9](#0-8) 

### Impact Explanation
If the accumulated rounding drift pushes the recorded baseline above the achievable reserve product, LPs lose the ability to withdraw their liquidity via the normal `Withdraw` path (only `WithdrawOnly`-status pools bypass the check), and no new liquidity can be added via `Deposit`. This constitutes a permanent freeze of LP funds under normal, permissionless pool usage — matching the "permanent freezing of user or LP funds" acceptance criterion.

### Likelihood Explanation
The path requires only repeated, unprivileged `Deposit`/`Withdraw` calls with attacker/LP-chosen amounts, no elevated privileges, and is reachable purely through normal AMM usage (small/awkward amounts chosen to maximize rounding loss asymmetry). The codebase's own dedicated precision test around this exact mechanism indicates the rounding behavior is non-trivial and has previously required careful validation, supporting that the drift is a real, triggerable condition rather than a purely theoretical one, though the number of cycles needed to accumulate a fatal drift depends on token decimals and `sys_decimal_value` configured at pool `initialize2`.

### Recommendation
Do not hard-fail the instruction when the invariant check fails; instead reconcile the baseline (e.g., clamp `calc_pnl_x`/`calc_pnl_y` down to the actual current reserve-derived values, take zero pnl for that cycle, and continue) rather than reverting `Deposit`/`Withdraw`/`WithdrawPnl`. Alternatively, recompute `calc_pnl_x`/`calc_pnl_y` directly from post-operation reserves rather than incrementally adding/subtracting normalized deltas, eliminating cross-operation rounding-direction mismatches.

### Proof of Concept
1. Initialize a pool via `Initialize2` with token decimals chosen so that `normalize_decimal_v2`/`restore_decimal` truncation is non-negligible relative to trade sizes (e.g., low-decimal PC vs high-decimal coin).
2. As an LP, call `Deposit` with a small, awkward amount; `calc_pnl_x`/`calc_pnl_y` are incremented using `normalize_decimal_v2(deduct_pc_amount, ...)` truncated math (processor.rs:1352-1371).
3. Call `Withdraw` for a partial LP amount; `calc_pnl_x`/`calc_pnl_y` are decremented using floor-rounded `exchange_pool_to_token` output run back through `normalize_decimal_v2` (processor.rs:1818-1838) — a different rounding path than step 2.
4. Repeat steps 2–3 with varying attacker-chosen amounts to accumulate a directional rounding bias in `calc_pnl_x * calc_pnl_y` relative to true reserves.
5. Once the recorded baseline exceeds the achievable `total_pc_without_take_pnl * total_coin_without_take_pnl`, any subsequent `Deposit` or `Withdraw` call triggers `calc_take_pnl`'s `else` branch and reverts with `AmmError::CalcPnlError` (processor.rs:267-278), permanently freezing all LP deposit/withdrawal on the pool.

    pub fn normalize_decimal(val: u64, native_decimal: u64, sys_decimal_value: u64) -> u64 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = Self::to_u64(
            ret_mut
                .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
                .unwrap()
                .as_u128(),
        )
        .unwrap();
        ret
    }

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)

        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();

    }
