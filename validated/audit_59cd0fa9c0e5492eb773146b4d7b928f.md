### Title
Withdraw transfers escrowed tokens before decrementing balances in the Tron IntentGatewayV2 (CEI violation) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron variant of `IntentGatewayV2`, the internal `withdraw()` function transfers native ETH and ERC-20 tokens to a beneficiary **before** decrementing the corresponding `_orders[commitment][token]` escrow balance, and it performs an external low-level `.call` to an attacker-influenced `beneficiary` address for native-token payouts. This is the same class of bug flagged in the external report (state-changing external interactions performed without CEI/reentrancy protection).

### Finding Description
`withdraw()` is reachable from `onAccept()` for `RequestKind.RedeemEscrow`/`RequestKind.RefundEscrow` and from `onGetResponse()`, both of which are delivered by the ISMP host on behalf of a relayer settling an intent order: [1](#0-0) 

The loop checks only that escrow is non-zero, then performs the external transfer, and only afterward decrements the balance:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
```
This is a Checks-Effects-Interactions violation: the `beneficiary.call{value: amount}("")` hands control to an arbitrary address (the order beneficiary, fully attacker-controlled since it is set by whoever places/fills the order) while `_orders[...]` for that token is still un-decremented. The companion mainline contract (`evm/src/apps/intentsv2/IntentsBase.sol`, `_withdraw`) was already hardened against exactly this class of issue by decrementing escrow state before performing the transfer: [2](#0-1) 
and the project's own regression tests (`IntrinsicIntentsReentrancyTest.sol`) document that the fix was specifically about moving state writes ahead of external calls to close a reentrancy window: [3](#0-2) 

The Tron contract's `withdraw()` was not updated to match this CEI pattern; it retains the pre-fix ordering (external call, then state decrement) for both the per-token loop and the transaction-fee payout.

### Impact Explanation
Because the escrow balance for a token is not decremented until after the external call returns, a beneficiary contract that reenters during the ETH `.call` (or during an ERC-20 token's transfer hook, e.g., an ERC-777/ERC-20-with-callback token) can, within the same nested call, trigger a second delivery of a message routing back into `withdraw()` for the same commitment/token pair before the first decrement is applied — the `_orders[commitment][token] == 0` check would still pass, allowing more tokens/ETH to be paid out than were ever escrowed for that order (loss of protocol/user funds, i.e., concrete theft of escrowed value). Even absent a concrete reentrant call path fully exercised by relayer batching, this is a definite deviation from the safe pattern already applied elsewhere in the codebase, and it directly matches the reported vulnerability class (state-changing functions performing external interactions without the checks-effects-interactions ordering).

### Likelihood Explanation
The unprivileged path to trigger `withdraw()` is exercised by any solver/relayer settling an order (`RedeemEscrow`/`RefundEscrow`/GET-response cancellation flow), and the beneficiary address is fully controlled by the order's placer/filler, so an attacker can trivially deploy a malicious beneficiary contract. The remaining requirement is a second inbound delivery landing inside the reentrant window, which depends on the handler/host's request-processing/batching behavior for the Tron deployment — this could not be fully confirmed against the Tron-specific `HandlerV2`/host implementation within the scope explored, so likelihood should be treated as **medium** pending verification of exactly how many `onAccept`/`onGetResponse` deliveries can be nested/batched in a single relayer transaction for this Tron contract.

### Recommendation
Apply the same CEI fix already present in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`: decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) **before** performing the native ETH `.call` or ERC-20 `transfer` call. Additionally, replace the low-level `token.call(abi.encodeWithSelector(IERC20.transfer...))` pattern (which only checks call success, not the ERC-20 boolean return value) with `SafeERC20.safeTransfer`, consistent with the mainline contract, and consider adding a reentrancy guard on `onAccept`/`onGetResponse` for defense in depth.

### Proof of Concept
1. Attacker places (or is selected as beneficiary of) an order with input `TokenInfo[]` containing token `X`, escrowing `amount` of `X` in `_orders[commitment][X]`.
2. Attacker's `beneficiary` contract is a malicious contract implementing `receive()` (for the native-token branch) that, upon receiving the ETH `.call`, attempts to trigger another delivery of the same/related withdrawal message before returning control.
3. In `withdraw()`, at the point the external `.call` fires, `_orders[commitment][X]` (or the `address(0)` native slot) has **not yet** been decremented, so a nested delivery reaching `withdraw()` again for the same commitment/token passes the `!= 0` check and pays out the escrow a second time.
4. Net effect: the beneficiary receives more than the single legitimate escrowed amount for that commitment/token, at the expense of the contract's other escrowed funds.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
