### Title
Tron `IntentGatewayV2.onAccept` omits the relayer allowlist that gates the EVM gateway, letting any relayer redeem or refund escrow - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol` / `evm/src/apps/intentsv2/ExtrinsicIntents.sol`) enforces a relayer allowlist (`_checkRelayer`) as the *first* gate inside `onAccept` and `onGetResponse`, before any request body is decoded, precisely to stop a forged/insufficiently-verified consensus proof from being turned into an unauthorized escrow release. The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements `onAccept` with `onlyHost` but never calls `_checkRelayer` (or any relayer check at all) — there is no `_relayer` state, no `setRelayer`, and no gate before `authenticate(incoming.request)` and `withdraw(...)` run for `RedeemEscrow`/`RefundEscrow`.

### Finding Description
On the reference EVM implementation, `ExtrinsicIntents._checkRelayer` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:75-78`) is called at the top of `onAccept`/`onGetResponse` before the `RequestKind` byte is even read, explicitly to close the route where a compromised/forged handler or consensus proof could report an arbitrary relayer and drain escrow (see `sdk/packages/core/docs/ai/flows/how-a-cross-chain-delivery-reaches-the-gateway-and-where-the.md` and the `2026-09-03-relayer-allowlist-on-the-intent-gateway.md` changelog, which describes this exact rationale).

In `evm/tron/contracts/apps/IntentGatewayV2.sol:629-635` the same function is:
```
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
        authenticate(incoming.request);
        WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
        return withdraw(body, kind == RequestKind.RefundEscrow);
    }
    ...
```
`onlyHost` restricts the caller to the local `EvmHost`, but only `authenticate` (which checks `request.from` equals the registered peer gateway on the source chain) gates the withdrawal — the `relayer` field on `IncomingPostRequest`, which the handler populates from `msg.sender` of whichever relayer delivered the proof, is never checked. There is no `_relayer` storage variable, `setRelayer` function, or `RelayerUpdated` event in this file at all, confirming the allowlist was simply not ported to the Tron contract.

This mirrors the MetaLabz root cause: an "authorization check bypassed" on a contract responsible for releasing locked/escrowed value, where a gate present in the design (and present in a sibling implementation of the same logical contract) is missing in this deployment target.

### Impact Explanation
Any relayer able to get a `PostRequest` proof accepted by the host's handler (i.e., anyone who can produce a message that passes consensus/state-proof verification for the `RedeemEscrow`/`RefundEscrow` path, or any relayer at all once such a message exists) can deliver escrow-release messages to the Tron `IntentGatewayV2` without being the chain's designated/whitelisted relayer. Combined with the fact that the EVM sibling treats this exact check as the primary defense against a compromised handler/forged proof reporting a wrong relayer, the Tron gateway loses that layer of defense entirely — any relayer whose delivery reaches `onAccept` can redeem or refund escrowed order funds. This is a direct path to theft/unauthorized release of escrowed user/solver funds, i.e., concrete loss of locked funds, matching Medium/High severity per the rules.

### Likelihood Explanation
The bug is reachable by an ordinary relayer message flow — no admin, governance, or malicious-node assumption is required beyond what any relayer already does to deliver proofs to `onAccept`. Given `onlyHost` still applies, the practical trigger is any message that reaches the host's `dispatchIncoming`; whether that requires additionally forging consensus (as in the EVM gate's own threat model) or is achievable by any of the currently-participating relayers depends on Tron's specific handler/consensus setup, which was not available for deeper verification in this pass. The missing check is unconditional and always active, so once any deliverable message exists, exploitation requires no further conditions on the Tron gateway's own logic.

### Recommendation
Port the `_relayer` allowlist from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` (state variable, `_checkRelayer`, `setRelayer`, `RelayerUpdated` event, and invocation at the top of `onAccept`/`onGetResponse` before the `RequestKind` byte is read) into `evm/tron/contracts/apps/IntentGatewayV2.sol`, wiring `initialize`/`migrate` to arm it exactly as the EVM version does, and add the equivalent Foundry tests (`testOnAcceptRejectsUnlistedRelayer`, `testOnGetResponseRejectsUnlistedRelayer`, etc.) against the Tron contract.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with an order escrowed on the source chain (`_orders[commitment][token] > 0`).
2. Have any relayer (not any specially-designated one, since none exists) submit a `PostRequest` with `RequestKind.RedeemEscrow`, correctly encoded `WithdrawalRequest`, and `from` set to the registered peer gateway address for the source chain, through the host's normal delivery path (`EvmHost.dispatchIncoming` → `onAccept`).
3. `onAccept` executes: `onlyHost` passes (call comes from host), `authenticate` passes (the `from` address matches the real peer gateway — this is under attacker/relayer control given the underlying message is otherwise legitimate/forged per the consensus layer), and `withdraw` is executed, releasing the escrowed tokens — with no relayer identity check performed anywhere in the call.
4. Contrast with `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, where the identical call would revert with `Unauthorized` at `_checkRelayer` if `incoming.relayer` were not the gateway's designated `_relayer`, as exercised in `testOnAcceptRejectsUnlistedRelayer` (`evm/tests/foundry/IntentGatewayV2Test.sol:4461-4476`).     function _authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        if (_instance(request.source) != module) revert Unauthorized();
    }

    /**
     * @dev Once a relayer is set, rejects deliveries from anyone else before the body is read. The
     * host records the revert as undelivered, so the authorised relayer can resubmit. While unset,
     * every delivery passes: a proxy from before the gate stays open until `migrate` arms it.
     * @param relayer The account that submitted the message to the handler.
     */
    function _checkRelayer(address relayer) internal view {
        address authorised = _relayer;
        if (authorised != address(0) && relayer != authorised) revert Unauthorized();
    }

# 2026-09-03 — Relayer allowlist on the intent gateway

The gateway now accepts `onAccept` and `onGetResponse` deliveries only from a single authorised
relayer stored at `_relayer` (slot 13, packed behind `_paused`). The check runs before the message
body is decoded, so escrow redemptions, refunds and every governance action, upgrades included, are
covered. A refused delivery reverts, which the host records as undelivered, so the authorised
relayer can submit the same message later. `setRelayer(address)` is callable by the immutable
`_owner` and by the host; the host branch exists so a governance `UpgradeContract` can carry the
call as its migration calldata and arm the relayer in the upgrade transaction (`upgradeToAndCall`
delegatecalls that calldata with the host still as `msg.sender`).

The interface gains `RelayerUpdated(address previous, address current)` and `setRelayer`, keeping
its declarations identical to `IntentsBase`. The unused `_paused` getter was dropped from the gateway
to stay under the EIP-170 size limit; it was never declared here.
