### Title
Webhook `shop`/`topic` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook request solely by checking that the HMAC of the raw body matches a signature computed with the app's `api_secret_key` [1](#0-0) . The `hmac` and `to_signable_string` methods used for that check are derived only from the request body [2](#0-1) [3](#0-2) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never part of the signed content [4](#0-3) . Since `api_secret_key` is a single shared secret used to sign webhooks for every shop that installs the app, any merchant who receives one genuine webhook can capture its valid `raw_body`+`hmac` pair and replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header value, producing a request that still passes `HmacValidator.validate` [5](#0-4) .

### Finding Description
The binding that should hold is: `shop authenticated by HMAC == shop the app acts on`. In `Registry.process`, the only equality actually checked is `computed_signature(raw_body, api_secret_key) == received_signature` [6](#0-5) . The `shop` value handed to the application's handler comes from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, entirely outside that signed input [7](#0-6) , and is passed straight through into `WebhookMetadata.shop`, which the docs explicitly instruct apps to use as the tenant identifier for follow-up work [8](#0-7) [9](#0-8) .

Before the attacker's request: `hmac` was computed by Shopify over `(raw_body_A, api_secret_key)` for the attacker's own shop A's webhook, with header `shop = A`.
After the attacker's replayed request: same `raw_body_A` and `hmac` are sent, but header `shop` is swapped to victim shop `B`. `HmacValidator.validate` still returns `true` because it only recomputes the HMAC over `raw_body_A`; it never checks that `shop` header equals the shop the signature was originally produced for. The gem therefore treats `shop == B` as authenticated when it was never bound to that value at all — this is exactly the same class of bug as the GNTDeposit report: an action (deposit / here, "this webhook body belongs to shop B") is trusted without re-validating the binding (timelock / here, shop identity) that should gate it.

### Impact Explanation
An app that keys any tenant-scoped side effect off `WebhookMetadata#shop` (exactly as the gem's own documented example does — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to process attacker-supplied body content under an arbitrary victim shop's identity, since `shop` is fully attacker-controlled and unauthenticated. This is a cross-tenant identity spoofing (impersonation of another merchant's webhook stream), matching the Critical category "cross-tenant access."

### Likelihood Explanation
Any merchant who installs the app is, by definition, an unprivileged internet user relative to other tenants, and will legitimately receive real webhooks (valid `raw_body`/`hmac` pairs signed with the app's single shared `api_secret_key`) for their own store. Capturing one such payload and replaying it to the app's public webhook endpoint with a modified `shop` header requires no special access, no leaked credentials, and no knowledge of `api_secret_key` — only observation of traffic the attacker is already authorized to receive.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or independently verify that the `shop` header corresponds to a shop the app has an active, registered webhook subscription/session for before trusting it in `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop` and `#topic` are unauthenticated and must be cross-checked by the host application against known installed shops before being used for any tenant-scoped action.

### Proof of Concept
1. App is installed on shop `attacker.myshopify.com` (shop A) and shop `victim.myshopify.com` (shop B), both registered for the `orders/create` webhook topic with the same app.
2. Shopify sends a genuine webhook to the app for shop A: body `raw_body_A`, header `x-shopify-hmac-sha256: HMAC(raw_body_A, api_secret_key)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker (who owns shop A) intercepts/logs this exact request.
4. Attacker resends the identical `raw_body_A` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body_A` only and matches the supplied signature — validation passes [10](#0-9) .
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body_A, ...)`, so the app performs order-processing side effects (e.g., enqueuing jobs, mutating stored data) attributed to `victim.myshopify.com` using content the attacker fully controls.
