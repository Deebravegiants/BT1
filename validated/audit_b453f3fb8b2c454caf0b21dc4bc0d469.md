### Title
Webhook shop-domain header is not covered by HMAC, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies covers only the raw request body. Any attacker who can obtain one valid `(raw_body, hmac)` pair generated by Shopify for the app's own webhook secret can replay it with a forged `shop-domain` header for a different shop, and the HMAC check will still pass, since the header is never part of the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the (unsigned) header: [2](#0-1) 

`Registry.process` validates the HMAC over the request via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the application-supplied handler: [3](#0-2) 

`HmacValidator.validate_signature` computes the digest purely from `verifiable_query.to_signable_string` (the raw body) and the app's `api_secret_key`, and compares it to the `hmac` header: [4](#0-3) 

The test suite confirms the signed material is only the JSON body (`"{}"`), independent of the `shopify-shop-domain` header value used in the same request: [5](#0-4) 

The broken identity binding, stated as an equality that the code fails to enforce:
`hmac == HMAC(secret, raw_body)` is verified, but the code then trusts `shop == header["shopify-shop-domain"]` for tenant attribution, with no cryptographic tie between `shop` and the signed bytes. Since Shopify signs webhooks with the single shared app `client_secret` (identical across every shop that installs the app) rather than a per-shop key, any raw body + hmac pair legitimately produced for one shop (including the attacker's own shop, which the attacker fully controls and can trigger webhook events in) remains valid when replayed with an attacker-chosen `shop-domain` header claiming to be a different, victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: a merchant/attacker who has the app installed on their own shop can capture a valid webhook (topic, body, hmac) triggered under their own control, then resend it to the app's webhook endpoint with `shopify-shop-domain` set to a victim shop's domain. `HmacValidator.validate` still returns true because the header isn't part of the signed content, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the victim shop. Any host application relying on this gem's `shop` field to select the tenant/session context (e.g., updating shop-specific data, gating `app/uninstalled` cleanup, or triggering merchant-specific side effects) can be manipulated into acting on behalf of, or against, a different merchant than the one that actually sent the payload — a cross-tenant access impact.

### Likelihood Explanation
Any actor with a valid app installation (i.e., any real merchant who installs the app) can generate legitimate `(body, hmac)` pairs at will, simply by exercising their own shop (e.g., placing a test order, or uninstalling/reinstalling the app to trigger `app/uninstalled`). No secret key, token, or elevated privilege is required to forge the header value used for tenant attribution — only capturing and replaying a raw webhook POST with a rewritten header, which is a normal unauthenticated HTTP capability once the attacker can send arbitrary requests to the app's public webhook endpoint.

### Recommendation
Bind the `shop` used for dispatch to the signed payload rather than to an out-of-band header. Options:
- Include the `shopify-shop-domain` header value in the HMAC-signed material (`to_signable_string`) so any tampering invalidates the signature, or
- Cross-check the header-derived `shop` against a shop value embedded in the signed JSON body (where Shopify includes it) before trusting it for tenant attribution, or
- Require callers to supply an expected shop (from the app's own session store) and reject processing if it doesn't match the header, rather than trusting the header value unconditionally.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and legitimately receives a webhook, e.g. `orders/create`, with raw body `B` and header `shopify-hmac-sha256: H` (a valid signature computed by Shopify using the app's shared `client_secret`).
2. Attacker resends the exact same `(B, H)` pair to the app's webhook endpoint, but replaces the header `shopify-shop-domain: attacker-shop.myshopify.com` with `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` (`B`) — it passes because `B` and `H` are unchanged: [6](#0-5) 
4. `request.shop` returns the forged `victim-shop.myshopify.com` value: [2](#0-1) 
5. The handler is invoked with `WebhookMetadata` attributing the webhook body to `victim-shop.myshopify.com`, even though the payload actually originated from, and describes, the attacker's own shop — a cross-tenant identity mismatch accepted by the gem's verification logic.
