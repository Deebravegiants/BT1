### Title
Non-EVM HOT Bridge withdrawal status is reported "completed" for any non-canonical status string, not the true on-chain outcome - (File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts)

### Summary
`HotBridge.describeWithdrawal` treats any string value returned by `hotSdk.getGaslessWithdrawStatus()` that is not a recognized enum (`Completed`/`Canceled`) as a "completed" withdrawal for non-EVM/Stellar/TON chains, instead of treating an unrecognized value as still-pending or unknown. This breaks the equality between the reported SDK status and the true on-chain settlement outcome.

### Finding Description
`describeWithdrawal` first checks for the two known terminal HOT statuses (`Completed`, `Canceled`). [1](#0-0)  For the non-EVM/Stellar/TON fallback branch, if `status` is a hex string it is reported completed with a formatted destination hash; but if it is a non-hex string (any other value the API/SDK might return, e.g. a raw error string, unexpected status text, or partial/garbled payload), the code still reports `{status: "completed", txHash: null}` instead of treating it as pending/unknown:

```
if (typeof status === "string") {
    // HOT returns hexified raw bytes without 0x prefix, any other value should be ignored.
    if (!isHex(status)) {
        args.logger?.warn("HOT Bridge incorrect destination tx hash detected", { value: status });
        return { status: "completed", txHash: null };
    }
    return { status: "completed", txHash: formatTxHash(status, args.landingChain) };
}
``` [2](#0-1) 

The code comment itself says "any other value should be ignored," yet the implementation returns `"completed"` rather than `"pending"` or a `"failed"` status. This is consumed by `watchWithdrawal`, which treats any `status: "completed"` as terminal success and immediately resolves the withdrawal-completion promise with `{hash: status.txHash}` (here `null`). [3](#0-2) 

### Impact Explanation
`waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` (built on `watchWithdrawal`) is the exact API integrators use to decide when to credit a user for a completed withdrawal. [4](#0-3)  Because the bridge reports `"completed"` for any non-hex string status—rather than for a truly finalized on-chain transfer—an integrator relying on this SDK signal could mark/credit a withdrawal as done while the underlying HOT-bridge transfer has not actually settled on the destination chain (i.e., a status misreport not matching the on-chain outcome). This falls under the High-impact category of "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This path only triggers for non-EVM/Stellar/TON HOT-bridge destinations when `getGaslessWithdrawStatus` returns a string outside the two known enum values and that is not valid hex — e.g., any unexpected/garbled/error string surfaced by the HOT SDK/API. The code's own comment acknowledges this is an anomalous value ("should be ignored"), meaning it's an edge case dependent on upstream API behavior, but the current handling actively converts that anomaly into a false-positive success rather than a safe "pending" state.

### Recommendation
For the non-hex-string branch, return `{status: "pending"}` (optionally falling back to the API indexer lookup, as already done elsewhere in the function) instead of `{status: "completed", txHash: null}`, so an unrecognized status never gets reported as a completed withdrawal.

### Proof of Concept
1. A withdrawal targets a non-EVM/Stellar/TON chain (e.g., Bitcoin via HOT bridge).
2. `hotSdk.getGaslessWithdrawStatus(nonce)` returns some string that is neither `"COMPLETED"`/`"CANCELED"` nor valid hex (e.g., an API error payload, a truncated/garbled value).
3. `describeWithdrawal` logs a warning "HOT Bridge incorrect destination tx hash detected" but still returns `{status: "completed", txHash: null}`.
4. `watchWithdrawal` sees `status.status === "completed"` and immediately resolves `{hash: null}`, ending the poll loop.
5. An integrator using `sdk.waitForWithdrawalCompletion` treats the withdrawal as finished and credits/notifies the user, even though the funds may not have actually landed on the destination chain. [2](#0-1) [3](#0-2)
