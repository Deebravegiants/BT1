### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, allowing cross-tenant shop spoofing on webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body [1](#0-0) , and `Utils::HmacValidator.validate` verifies the HMAC solely against that signable string using the app's single, shop-agnostic `Context.api_secret_key` [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` and handed to the handler as `WebhookMetadata` are read directly from HTTP headers that are never included in the HMAC-signed payload [3](#0-2) [4](#0-3) .

### Finding Description
`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler [4](#0-3) . That validation recomputes an HMAC over `verifiable_query.to_signable_string` — which for `Webhooks::Request` is just `@raw_body` [1](#0-0)  — and compares it to the value taken from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header [5](#0-4) , using the app's single `Context.api_secret_key` shared across every shop that installed the app [6](#0-5) .

Because the signature never binds to `shop`, `topic`, `webhook_id`, or `api_version`, once an attacker has legitimately received one valid `(raw_body, hmac)` pair for any shop that has this app installed (e.g., their own store, which they fully control and where all these webhook fields are visible to them), they can replay the exact same body and HMAC value while substituting the `shopify-shop-domain` header (and/or `shopify-topic`, `shopify-webhook-id`) to name a different, victim shop. `Utils::HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` forwards `request.shop` unchanged into `WebhookMetadata.shop` [7](#0-6) , which host applications use to key per-tenant records (sessions, orders, customer data) in their own storage. This breaks the intended binding `verified_shop == asserted_shop`: the gem verifies only "these bytes were signed by *some* installation of this app," not "these bytes were signed *for this shop*."

### Impact Explanation
This is a cross-tenant integrity issue: the gem hands the host application webhook data tagged with an attacker-controlled `shop` value while asserting it passed HMAC verification. A host application that trusts `WebhookMetadata#shop` as an authenticated tenant identifier (which is the documented/expected use, since the field is only populated after `HmacValidator.validate` succeeds) can be tricked into attributing another shop's webhook payload/state changes to a victim shop, or vice versa, enabling cross-tenant data corruption or disclosure without needing the app's `client_secret` or any privileged access — only participation as one legitimate installed shop of the app.

### Likelihood Explanation
Any merchant/shop that has installed the app can trivially capture legitimate `(body, hmac)` pairs from webhooks Shopify sends to their own endpoint (there is no restriction on shops receiving their own valid webhook traffic), and then re-POST that exact payload with a forged `shop` header to the app's webhook endpoint. No secret material beyond what a normal, unprivileged installed-shop tenant already legitimately possesses is required, making this readily reachable by any unprivileged internet user who is a shop-tenant of the app.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the value verified against the HMAC, or otherwise cryptographically bind `request.shop` to the signed payload before trusting it in `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop` is not authenticated by the HMAC and host applications must independently verify shop identity (e.g., cross-check against a known/installed shop list) before using it as a tenant key.

### Proof of Concept
1. App has two shops installed: `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both under the same `Context.api_secret_key`.
2. Shopify sends a legitimate webhook to the attacker's shop: `raw_body = "{...attacker order...}"`, header `shopify-hmac-sha256 = HMAC(secret, raw_body)`, `shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker replays the identical `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` builds the request from these headers [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` and matches the forwarded, still-valid signature [9](#0-8) .
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [10](#0-9)  with the attacker's own data now falsely attributed to the victim shop, despite HMAC verification having "passed."

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
