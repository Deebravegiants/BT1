### Title
Arbitrary route contracts can attach wallet-draining transfers to a victim’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs)) [1](#0-0) 

### Summary
The strategy APIs accept opaque `swap` bytes, authenticate `caller`, and invoke the configured router while that caller authorization remains the transaction’s authorization root. [2](#0-1) [3](#0-2)   
Because route-selected contracts are not restricted by the router boundary, an attacker can place a malicious venue contract in the route; that contract can request a token transfer from the victim, which simulation records as a child invocation beneath the victim’s strategy authorization. [4](#0-3)   
If the victim signs the generated authorization tree, the malicious venue can transfer unrelated wallet assets that are outside the declared routed input. [5](#0-4) 

### Finding Description
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` funnel caller-supplied `swap` data into `swap_tokens`. [6](#0-5) [7](#0-6)   
`swap_tokens` treats the payload as opaque bytes and calls `router.execute_strategy(controller, amount_in, swap)`. [8](#0-7)   
The controller separately authorizes only its own exact input-token transfer to the router, but this does not prevent route-selected code from requesting additional authorization directly from the original caller. [1](#0-0) [9](#0-8)   
The protocol’s own threat model states that route payloads name arbitrary pool and token addresses, without a venue allowlist, and that transfers requested by those contracts execute when included in the caller’s signed authorization tree. [4](#0-3) 

### Impact Explanation
A malicious route can steal arbitrary spendable token balances from the victim’s wallet, not merely the `amount_in` committed to the strategy. [10](#0-9)   
The strategy can simultaneously return a fair measured output and satisfy the controller’s output and solvency checks, so the wallet theft is not bounded or detected by `RouterOverspend`, `NoSwapOutput`, route minimums, or final account risk validation. [11](#0-10) [4](#0-3)   
The existing adversarial test demonstrates a victim wallet balance decreasing to zero while the attacker receives the full balance and the swap still completes successfully. [12](#0-11) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue contract and distribute a malicious route through a compromised quote service, malicious interface, phishing flow, or copied transaction payload. [13](#0-12)   
Exploitation requires the victim to sign a transaction whose authorization tree includes the unexpected token transfer, but honest simulation records that transfer as a nested child rather than presenting it as an independent top-level action. [14](#0-13)   
The test shows that an honest empty child tree rejects the theft, while the simulation-generated poisoned child authorizes it, making the attack practical against clients that do not explicitly decode and verify the complete route and authorization tree. [15](#0-14) 

### Recommendation
Restrict route execution to fixed, reviewed venue adapters or a governance-maintained allowlist of venue contracts rather than allowing route bytes to name arbitrary executable contracts. [16](#0-15)   
For each route leg, bind the invoked contract, function, input token, output token, and maximum caller-authorized transfers to decoded route fields before execution. [17](#0-16)   
Require official clients and integrators to reject any strategy authorization tree containing children beyond the expected controller-authorized input transfer, although this client-side check should complement rather than replace route-venue restrictions. [18](#0-17) 

### Proof of Concept
The repository contains `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`, which models a router that invokes a route-selected `hop_pool`. [19](#0-18)   
The malicious pool stores a victim address, unrelated wallet token, attacker recipient, and amount, then calls `token.transfer(victim, attacker, amount)` during route execution. [20](#0-19)   
The exploit route can be submitted as `swap_collateral(caller=victim, account_id=victim_account, current=(hub_id, USDC), amount=SWAP_IN_USDC, new=(hub_id, ETH), swap=malicious_route_xdr)`. [21](#0-20)   
During recording-mode simulation, the wallet-draining transfer is recorded as a child of the victim’s `swap_collateral` authorization, and the swap still credits the expected ETH output. [22](#0-21)   
In enforcing mode, an authorization tree containing only the honest root rejects the transfer, while the simulation-generated tree containing the malicious token-transfer child authorizes it and moves the victim’s entire unrelated token balance to the attacker. [15](#0-14)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
