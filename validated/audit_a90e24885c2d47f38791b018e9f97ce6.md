### Title
Fraudulent state commitments become permanently unchallengeable if a fisherman's veto is delayed past the `challenge_period` - (File: `modules/pallets/fishermen/src/lib.rs`, `modules/ismp/core/src/handlers.rs`)

### Summary
Hyperbridge's optimistic-bridging security model relies on fishermen submitting a `veto_state_commitment` extrinsic within a fixed `challenge_period` after a `StateMachineUpdated` event, before relayers are permitted to use that `StateCommitment` to deliver POST/GET requests, responses, or timeouts. Exactly like the depeg-trigger race condition in the source report, this is a single narrow window gated purely by wall-clock time: if the fisherman's veto transaction is delayed by network congestion, a gas-fee spike, RPC/relayer censorship, or a general liveness disruption, the window closes and the fraudulent commitment becomes usable to trustlessly authorize cross-chain message delivery, with no possibility of reversal.

### Finding Description
The delay-based safety check is `verify_delay_passed`, used by every request/response/timeout handler via `validate_state_machine`: [1](#0-0) 

Once `current_timestamp.saturating_sub(update_time) > delay_period`, any relayer can use that `StateCommitment` to deliver messages — there is no additional check for whether a veto is "in flight" or whether the fisherman infrastructure has actually had a fair opportunity to observe the update. The Solidity equivalent enforces the identical binary revert-or-proceed pattern in `HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts`: [2](#0-1) 

The only mitigation against a fraudulent `StateCommitment` is `pallet_fishermen::veto_state_commitment`, which any single active collator can call, with no proof required: [3](#0-2) 

This veto is only meaningful `"ideally still in its challenge period"` per its own doc comment — the code does not enforce that constraint, but the protocol's safety guarantee depends entirely on fishermen reacting inside that window, as documented: [4](#0-3) 

The off-chain fisherman task itself depends on live RPC quorum queries and a signed extrinsic landing on Hyperbridge before the challenge period elapses: [5](#0-4) 

If any of the following occur during the challenge window — an RPC provider outage preventing quorum, congestion on Hyperbridge's mempool delaying extrinsic inclusion, a fee spike, or a targeted DoS against fisherman nodes/relayers — the veto extrinsic simply does not land before `verify_delay_passed` returns `true` elsewhere. At that point, any relayer can submit `handle_unsigned`/`handlePostRequests` using state proofs rooted in the fraudulent commitment, and the ISMP module dispatches the (forged) request to the destination application (e.g., a token bridge mint), which is the exact "unsound state commitment / forged message delivery" outcome the validation rules call out. A subsequent veto only deletes the commitment for future use — it does not and cannot undo funds already disbursed by `IsmpModule::on_accept` from the forged request.

### Impact Explanation
A successfully-forged and unvetoed `StateCommitment` allows an attacker (a byzantine/eclipsing validator or sequencer set, or a compromised consensus-client relayer) to submit fabricated state proofs for cross-chain messages that never actually occurred on the source chain. Once past the challenge period, this is processed identically to a legitimate message: token bridges can mint unbacked assets, intents can be filled/settled fraudulently, or arbitrary `IIsmpModule::onAccept` logic can be triggered — a permanent, irreversible loss for the destination-chain application, matching "unbacked mint / forged message delivery / unsound state commitment" in the given severity classes.

### Likelihood Explanation
The `challenge_period` is a short, fixed, non-adaptive wall-clock window (documented as tunable, e.g. zero for high-security chains like Polkadot, but non-trivial for others) and fishermen depend on both external RPC availability and timely on-chain extrinsic inclusion. Any of the described DoS/censorship/congestion vectors from the source report apply directly here without needing any special privilege — anyone able to spam Hyperbridge's mempool, target fisherman RPC endpoints, or exploit a liveness gap during exactly this window can cause the same "the window quietly closes" failure mode.

### Recommendation
- Require the state-commitment veto path to fail-safe rather than fail-open: e.g., automatically extend the challenge period whenever fisherman connectivity/liveness gaps are detected, or gate message processing on a minimum number of confirmed "no veto" heartbeats rather than a bare timestamp comparison.
- Consider allowing vetoes to also invalidate/claw back messages already processed using a commitment that is vetoed shortly after the challenge period elapses (a short additional grace period), rather than only preventing future use.
- Add monitoring/alerting for fisherman extrinsic inclusion latency approaching the configured `challenge_period`, and consider dynamically lengthening it under observed relayer/mempool congestion.

### Proof of Concept
1. A byzantine validator set (or forged L2 sequencer output) submits a consensus update that gets accepted by `update_client`, creating a pending, forged `StateCommitment` at height `H` (`modules/ismp/core/src/handlers/consensus.rs`, `update_client`).
2. During the `challenge_period`, the attacker (or colluding block producers/relayers) congests Hyperbridge's mempool with high-fee unsigned/extrinsic spam, or targets the fisherman's RPC endpoints so quorum cannot be reached (`tesseract/messaging/evm/src/byzantine.rs` lines 118-156, `docs/content/developers/explore/fishermen.mdx`).
3. `veto_state_commitment` for height `H` fails to be included before `verify_delay_passed(host, H)` becomes `true` (`modules/ismp/core/src/handlers.rs`).
4. Once past the challenge period, an attacker-controlled relayer submits `handle_unsigned` (or `HandlerV2.handlePostRequests`) with a state proof rooted in the forged commitment, and the destination `IsmpModule` (e.g., a token bridge) processes it as genuine, minting/releasing funds.
5. A late veto by the fisherman deletes the commitment for future use but cannot reverse the already-dispatched mint/transfer.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

A `StateMachineUpdated` event is emitted to notify network participants (both relayers and fishermen) of some newly available `StateCommitment`s for a given state machine. Relayers will wait for the configured `challenge_period` before attempting to transmit new requests & responses. While fishermen will check if these pending `StateCommitment`s describe valid states on the counterparty network. If the `challenge_period` elapses without any fraud proofs being presented, we can safely conclude that the provided `StateCommitment`s are indeed canonical.
