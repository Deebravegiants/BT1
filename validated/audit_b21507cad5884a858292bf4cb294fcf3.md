### Title
Unbounded iteration over an account's access keys and contract data during `DeleteAccount` execution, charged only a fixed fee - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` is invoked when an account is deleted and iterates over *all* of that account's access keys (and their gas-key nonce entries) and *all* of its contract-data key/value pairs, collecting them into `Vec`s and then removing them one-by-one from the trie. [1](#0-0)  The number of these iterations is entirely controlled by the account owner (how many `AddKey` actions and how much contract storage they accumulated), yet the `DeleteAccount` action that triggers this removal is charged a single fixed gas fee (`delete_account_cost`) independent of how many keys or storage entries exist. [2](#0-1)  This mirrors the reported pattern in the external report: work that scales with a user-controlled collection size is executed inside a loop bounded only by the size of that collection, while the caller pays a cost that does not scale with the loop's true size.

### Finding Description
`remove_account` performs two unbounded scans per account deletion:
1. It iterates the trie prefix for the account's access keys, parsing every key and pushing a `TrieKey` into `keys_to_remove` for every access key and every gas-key nonce entry found, then removes them all in a second loop. [3](#0-2) 
2. It then iterates the trie prefix for the account's contract data, collecting every key into `data_keys` and removing them all. [4](#0-3) 

Both loops are bounded only by however many access keys / gas keys / contract-storage entries the account happens to have — quantities fully controlled by the account's owner via repeated `AddKey` actions or contract storage writes over time. There is no per-invocation cap analogous to `access_keys_limit` used by the (already-fixed) paginated `view_access_keys` viewer function, which explicitly caps unpaginated queries and requires callers to page through large lists. [5](#0-4)  In contrast, `remove_account` — which is called from the actual state-transition path (`DeleteAccount` action execution) rather than a read-only view query — has no such cap and no pagination mechanism, and the `DeleteAccount` action fee (`delete_account_cost`) is a single flat fee, not scaled by the number of keys/data entries being removed. [2](#0-1)  The `RuntimeFeesConfig::fee` docs and fee tables confirm `delete_account` has one fixed `send`/`execution` cost with no per-item component (unlike, e.g., `add_function_call_key_byte`, which does scale with method name bytes). [6](#0-5) 

### Impact Explanation
An account owner who accumulates a very large number of access keys and/or a large volume of contract storage (each staked and paid for incrementally over time via normal `AddKey`/storage-write transactions) can submit a single `DeleteAccount` transaction that is charged the fixed `delete_account_cost`, but which forces the runtime to synchronously scan and remove an arbitrarily large number of trie entries during chunk application. This is unpriced/underpriced execution work relative to the flat fee charged, and in the worst case can cause a chunk application to consume excessive wall-clock time or resources disproportionate to the gas actually burned for the transaction — a node resource-exhaustion / chunk-processing-cost risk directly analogous to the reported `withdrawUnstakedTokens` unbounded-loop bug, where a single call's cost scaled with unboundedly attacker/user-grown state.

### Likelihood Explanation
Reaching this path requires only ordinary, unprivileged transactions: repeatedly calling `AddKey` (or writing large amounts of contract state) from one's own account over time, then submitting a normal `DeleteAccount` action — no validator or network-level access is needed. The number of access keys per account is not otherwise capped by protocol rules other than the cost of storage staking (which is a balance requirement, not a hard count limit), so an account with sufficient balance can grow this collection arbitrarily large before the single fixed-cost deletion transaction that runs the unbounded loop.

### Recommendation
- Bound the number of access-key / contract-data entries removed per `DeleteAccount` execution (e.g., cap and require multiple `DeleteAccount`-style operations, or split removal work across chunks/receipts similar to how delayed receipts and access-key views are already paginated elsewhere in the codebase, e.g. `TrieViewer::view_access_keys`'s `access_keys_limit`/pagination model). [5](#0-4) 
- Alternatively/additionally, make the `delete_account_cost` (or an added compute/gas component) scale with the actual number of access keys, gas-key nonces, and contract-data entries removed, similar to how `storage_removes_compute` already prices bulk storage removals elsewhere by count and byte size. [7](#0-6) 
- Ensure the compute/gas accounting for `remove_account`'s work (currently only `gas_key_nonce_count`/`gas_key_nonce_total_key_bytes` are tracked and returned, with no equivalent accounting for plain access keys or contract-data entries) fully reflects all removed items so the runtime charges proportionally to work performed. [8](#0-7) 

### Proof of Concept
1. From an unprivileged account `attacker.near` with sufficient balance to cover storage staking, submit a large number of `AddKey` transactions (or write a large volume of key/value pairs via a deployed contract) to accumulate, e.g., tens of thousands of access keys and/or contract-data entries.
2. Submit a single `DeleteAccount` action for `attacker.near`. This action is charged only the flat `delete_account_cost` fee (~147,489,000,000 gas total as configured), regardless of the number of keys/entries. [2](#0-1) 
3. During execution, `remove_account` scans and removes every access key, gas-key nonce, and contract-data entry for the account in two unbounded loops, with cost proportional to the accumulated state size rather than the fixed fee charged. [9](#0-8) 

Note: I was unable to fully trace the exact call site in `runtime/runtime/src/actions.rs::action_delete_account` and confirm whether any additional compute-cost accounting is applied there beyond what `remove_account` returns (`RemoveAccountResult`), due to the final tool-call iteration cutting off before I could inspect that function body directly. This should be verified against `runtime/runtime/src/actions.rs` to confirm no additional scaling charge is applied at the call site.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }

    pub fn view_access_keys(
        &self,
        trie: &Trie,
        account_id: &AccountId,
        after: Option<&PublicKeyHandle>,
        limit: Option<NonZeroU32>,
    ) -> Result<
        (Vec<(PublicKeyHandle, AccessKey)>, Option<PublicKeyHandle>),
        errors::ViewAccessKeyError,
    > {
        let max = self.access_keys_limit;
        let paginated = after.is_some() || limit.is_some();

        let item_cap: Option<u32> = if paginated {
            // An explicit page size larger than the configured maximum is
            // clamped down rather than rejected; with no explicit page size we
            // fall back to the configured maximum.
            Some(limit.map_or(max, |requested| requested.get().min(max)))
        } else {
            None
        };

        let prefix = trie_key_parsers::get_raw_prefix_for_access_keys(account_id);
        // Bound iteration to this account's access-key range with a prune
        // condition. Unlike the per-node seek boundary, a prune condition
        // survives `seek`, so it keeps enforcing the range across the seeks we
        // use below to skip gas-key nonce blocks.
        let prefix_nibbles: Vec<u8> = prefix.iter().flat_map(|&b| [b >> 4, b & 0x0f]).collect();
        let mut iter =
            trie.disk_iter_with_prune_condition(Some(Box::new(move |key_nibbles: &Vec<u8>| {
                !nibbles_within_prefix(&prefix_nibbles, key_nibbles)
            })))?;

        match after {
            Some(handle) => {
                let after_key = TrieKey::access_key(account_id.clone(), handle.clone()).to_vec();

                    Some(next) => iter.seek(Bound::Included(next.as_slice()))?,
                    // Unreachable: access-key keys start with `col::ACCESS_KEY`,
                    // so they are never all-0xFF.
                    None => iter.seek(Bound::Excluded(after_key.as_slice()))?,
                }
            }
            None => iter.seek(Bound::Included(prefix.as_slice()))?,
        }

        let mut keys = Vec::new();
        let mut last_key = None;

        while let Some(item) = iter.next() {
            let (raw_key, _value) = item?;

                    errors::ViewAccessKeyError::InternalError {
                        error_message: "unexpected invalid access key from iterator".to_string(),
                    }
                })?;
            // A genuine access key beyond what we've already kept.
            if let Some(cap) = item_cap {
                if keys.len() as u64 >= u64::from(cap) {

                    limit: max,

/// Compute cost for `count` storage_remove operations with `total_key_bytes` total
/// key bytes and `total_value_bytes` total value bytes across all removals.
pub(crate) fn storage_removes_compute(
    ext: &ExtCostsConfig,
    count: usize,
    total_key_bytes: usize,
    total_value_bytes: usize,
) -> Compute {
    let count = count as u64;
    let total_key_bytes = total_key_bytes as u64;
    let total_value_bytes = total_value_bytes as u64;
    ext.compute_cost(ExtCosts::storage_remove_base) * count
        + ext.compute_cost(ExtCosts::storage_remove_key_byte) * total_key_bytes
        + ext.compute_cost(ExtCosts::storage_remove_ret_value_byte) * total_value_bytes
}
