### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload from the raw body only, and the shop identity (`x-shopify-shop-domain` header) is never included in that signed payload. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC of the body and then unconditionally trusts `request.shop` (and `request.topic`) to route/execute the tenant-scoped webhook handler, even though those header values are completely outside the cryptographic binding.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version` and `webhook_id` accessors are all read straight from HTTP headers with no cryptographic linkage to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC of the request (i.e., only the body) and then immediately hands `request.shop` to the registered handler as the tenant identifier, with no additional check binding `shop` to the signed content: [3](#0-2) 

`HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)`, i.e. `HMAC-SHA256(api_secret_key, raw_body)` for webhooks — again, the shop header plays no role in the digest: [4](#0-3) 

Because `api_secret_key` is a single shared secret for the entire app across **all** shops that install it, any legitimate webhook delivery for **any** tenant (including a shop the attacker fully controls, e.g. one they installed the app on themselves) yields a `(raw_body, hmac)` pair that is valid for arbitrary payload/shop combinations. An attacker who controls their own installation can capture a legitimately-signed `(raw_body, hmac)` pair and replay it directly to the app's public webhook endpoint while spoofing the `x-shopify-shop-domain` (and `x-shopify-topic`) headers to name a victim shop. `Utils::HmacValidator.validate` will pass because it only checks the body digest, and `Registry.process` will then invoke the webhook handler believing the event originates from the victim shop.

The equality this breaks: `shop_bound_by_hmac` (∅, since the signature only covers the body) ≠ `shop_used_by_handler_for_tenant_scoped_action` (`request.shop`, an attacker-controlled header).

### Impact Explanation
This is a cross-tenant confusion vulnerability: any unprivileged party who can obtain one valid, signed webhook body (trivially achievable by installing the app on their own store, a normal unprivileged action for most public apps) can forge webhook deliveries that the host application will process as belonging to a different, victim shop. Depending on how the host application's webhook handler uses `WebhookMetadata#shop` (e.g., to look up/mutate per-shop state, trigger fulfillment/inventory actions, or write to a shop-scoped database record), this can result in cross-tenant data corruption or unauthorized state changes attributed to a shop the attacker does not own — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app exposing webhook endpoints publicly (which is required for Shopify webhooks) and accepting third-party/self-serve installs: obtaining one valid `(raw_body, hmac)` pair only requires being an ordinary merchant/installer of the app — no access to `api_secret_key`, no TLS interception, and no privileged account is needed.

### Recommendation
Bind the tenant identity to the signed payload before trusting it. Options:
- Include the shop domain (and topic) inside the HMAC-covered signable string, or
- Cross-check `request.shop` (and `topic`) against a value independently obtained from an authenticated source (e.g., look up the shop associated with the specific webhook subscription/webhook-id via a signed/authenticated GraphQL query, or require the host app to correlate `webhook_id` from a database of subscriptions per shop before trusting `shop`).
At minimum, document prominently that `Request#shop`/`topic` are **not** authenticated by the HMAC and must not be trusted for tenant-scoping without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers any webhook topic the app subscribes to (e.g. `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends — both are valid under the app's single, shared `api_secret_key`.
2. Attacker replays this exact `raw_body` + `hmac` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, forges `x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which recomputes `HMAC-SHA256(api_secret_key, raw_body)` — this matches, since only the body is signed: [3](#0-2) 
4. The handler executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own store — a cross-tenant impersonation of a webhook event.
