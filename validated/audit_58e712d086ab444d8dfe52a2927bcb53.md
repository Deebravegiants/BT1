This confirms the finding: the gem's own documentation states `data.shop` — sourced directly from the `shopify-shop-domain` header — is the shop-domain field apps are expected to use for tenant identification (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), while `Utils::HmacValidator.validate(request)` only authenticates the raw body against the shared `api_secret_key`.

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. The `shop`, `topic`, `webhook_id`, and `api_version` attributes consumed by the handler are all pulled directly from HTTP headers, which are entirely outside the scope of what the HMAC covers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed in `HmacValidator.compute_signature` binds solely to the JSON body: [1](#0-0)  and [2](#0-1) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers with no cryptographic binding to the body or the HMAC: [3](#0-2) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, never checking that the header-derived `shop`/`topic` match anything the HMAC attests to: [4](#0-3) .

Because `api_secret_key` is a single per-app secret shared across every installed shop (not a per-shop secret), any actor who can obtain one validly-HMAC-signed `(body, hmac)` pair for a webhook topic - e.g., by installing the app on their own shop and receiving a genuine webhook - can present that same, still-valid, `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` (and `topic`/`webhook-id`) header. `HmacValidator.validate` will still pass because it never inspects the headers, and `Registry.process`/`WebhookMetadata` will hand the handler a `shop` value that has no relationship to the body that was actually authenticated. This breaks the identity binding: `shop asserted to HMAC-verifier == shop consumed by handler` does not hold.

### Impact Explanation
This is a case of "a shop authenticated versus the shop stored/used as an identifier not being the same value." An app using `data.shop` (as documented and demonstrated in `docs/usage/webhooks.md`) to select which tenant's session/access token to act with, or to route data into per-shop storage, can be made to associate an attacker-crafted body (from the attacker's own store) with a victim shop's identity, or vice versa - enabling cross-tenant data injection/impersonation without ever needing the app's `client_secret`, an access token, or any privileged credential.

### Likelihood Explanation
Any merchant/developer who can install the target app on their own store (an unprivileged, ordinary app-install action) can capture a legitimately-signed `(body, hmac)` pair from Shopify's own webhook delivery to their store, then replay it directly to the app's public webhook endpoint with a forged `shopify-shop-domain` header, since no additional secret or privileged access is required to modify HTTP headers on a directly-sent request.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the signable string that `HmacValidator` verifies, or otherwise cryptographically bind the header values to the payload before they are trusted, so that a header cannot be substituted independently of the body it was originally paired with.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with headers `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`, a JSON body, and a valid `shopify-hmac-sha256` computed over that body with the app's shared `client_secret`.
3. Attacker captures this exact `(raw_body, hmac)` pair.
4. Attacker sends a new HTTP request to the same webhook endpoint with the identical `raw_body` and `shopify-hmac-sha256`, but sets `shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC and succeeds [5](#0-4) .
6. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body, despite the payload never having been produced by or for `victim.myshopify.com`.
