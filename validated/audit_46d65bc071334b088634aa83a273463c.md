### Title
Webhook tenant identity (`shop-domain` header) is not covered by the HMAC signature, allowing cross-shop webhook relabeling - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) used to route and process the webhook is taken from an HTTP header that is not part of the signed content. An attacker who can obtain any single valid `(raw_body, hmac)` pair delivered by Shopify to the app (e.g. by installing the app themselves) can resend that same body/signature to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop, and the signature check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor used to identify the tenant is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the signed data: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC using `to_signable_string` (the body), and `Webhooks::Registry.process` then trusts `request.shop` — derived from the unsigned header — as the tenant identity passed to the app's handler: [3](#0-2) 

The equality that should hold is: `shop bound by HMAC == shop used to route/process the webhook`. In this implementation, the HMAC only binds `raw_body`, so `shop (header, unauthenticated) != shop (implicitly, whichever store originally produced raw_body)`. This is the same class of bug as the report's fee-recipient issue: an identity-determining field (`affiliate`/fee target ↔ `shop`) can be changed independently of the value (pending fee ↔ signed payload) that is committed under the old identity, causing the value to be misattributed to a different identity.

### Impact Explanation
Since `data.shop` is the only tenant discriminator handed to the app's `WebhookHandler.handle` callback (per the documented webhook usage pattern), an app that uses `data.shop` to decide which merchant's record to create/update/delete can be tricked into applying shop-A's webhook payload to shop-B's tenant data, constituting cross-tenant data confusion/access — a Critical-impact class per the given rubric.

### Likelihood Explanation
Medium: the attacker does not need the app's `api_secret_key`. They only need one legitimate `(raw_body, hmac)` pair emitted by Shopify to the app for any shop under their control (installing the app on their own dev/test store yields this), then a single unauthenticated POST to the app's public webhook endpoint with the header swapped. This requires no privileged credentials, TLS interception, or social engineering — only knowledge of the app's public webhook route, which is typically documented/discoverable.

### Recommendation
Include the tenant-identifying header (`shop-domain`, and ideally `topic`/`webhook-id`/`api-version`) in the HMAC-signed content (`to_signable_string`), or otherwise cryptographically bind the shop domain to the signed payload before it is trusted by `Registry.process`/`WebhookMetadata`. At minimum, document that consuming apps must independently confirm the shop belongs to a session they already trust rather than treating `data.shop` as authoritative on its own.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any webhook topic the app has registered for, capturing the resulting request body `B` and its valid header `X-Shopify-Hmac-Sha256: H` (both delivered by Shopify, using the app's real secret).
2. Attacker sends a POST to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid because it only signs `B`)
   - Header `x-shopify-shop-domain`: `victim.myshopify.com` (changed)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `to_signable_string` (`B`) against `H`.
4. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and body `B` from the attacker's own shop, and processes it as if it originated from the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
