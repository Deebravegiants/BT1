### Title
Webhook `shop` (and `topic`/`webhook-id`) claims are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC verification performed by `Utils::HmacValidator` only proves that *the body bytes* were signed with the app's `client_secret`. The `shop` (tenant identifier), `topic`, `api_version`, and `webhook_id` fields are parsed straight from unauthenticated HTTP headers and are never included in the signed payload, yet they are trusted downstream as the tenant-binding fields passed to the app's `WebhookHandler`.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` field of the query object [1](#0-0) . For webhooks, `to_signable_string` is defined to return only `@raw_body`: [2](#0-1) .

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly out of request headers with no cryptographic binding to the signature: [3](#0-2) .

`Registry.process` validates only that the body's HMAC is correct, then immediately trusts `request.shop` as the tenant identifier when constructing `WebhookMetadata` and invoking the app's handler: [4](#0-3) . `WebhookMetadata.shop` is a plain `String` field with no further validation: [5](#0-4) .

This is the same bug class as the referenced report: the value that is *acted upon* to establish identity (`shop`, the tenant binding) is not the value that is *cryptographically verified* (only the raw body is HMAC'd). By contrast, the OAuth `AuthQuery#to_signable_string` correctly includes `shop` inside the signed parameters [6](#0-5) , showing the gem's own design intent that `shop` should be part of the signed material — an intent that is not honored for webhook `Request`.

The binding that is broken: `shop_verified_by_hmac == shop_used_for_tenant_dispatch` does not hold; the left side is undefined (the HMAC does not cover `shop` at all) while the right side is attacker-controlled via the `x-shopify-shop-domain`/`shopify-shop-domain` header.

### Impact Explanation
Because the app's `client_secret` is shared across every shop that installs the app, any shop that has *legitimately* installed the app can capture one valid `(raw_body, hmac)` pair from a webhook Shopify sends to their own shop. That attacker can then replay the exact same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value (e.g., a victim shop's domain). `Registry.process` will accept it as authentic because HMAC validation never inspected the `shop` header, and the app's `WebhookHandler#handle` will receive `WebhookMetadata` claiming the event belongs to the victim shop. Any host application logic that uses `data.shop` to look up per-tenant session/state, write per-shop data, or make trust decisions can be poisoned with attacker-controlled tenant identity — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
The attacker only needs their own (unprivileged) shop's install of the app to receive one webhook — no victim credentials, tokens, or `client_secret` access are required. Forging headers on an HTTP POST to the app's public webhook endpoint is trivial. The only constraint is that the replayed body/topic must make sense for whatever shop value is forged, but many topics carry generic payloads.

### Recommendation
Include `shop` (and ideally `topic`, `api_version`, `webhook_id`) as part of the signed material verified against Shopify's HMAC scheme, or, since Shopify's own webhook HMAC only ever covers the body, cross-check the `shop-domain` header against a shop that the app has an active, legitimately-registered webhook/session for before dispatching to handlers, rejecting shops that are not currently expected to receive the given webhook `topic`/`webhook_id` combination.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — both valid, since HMAC is computed with the shared `client_secret`.
2. Attacker sends this exact `raw_body` + `hmac` header to the victim app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `to_signable_string` (`raw_body`) against the secret [2](#0-1) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [7](#0-6) , causing the host app to process attacker-supplied data under the victim shop's tenant context.
