### Title
Rebasing/balance-shrinking input tokens can permanently brick escrow withdrawal in `IntentsBase._withdraw` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2` (via `IntentsBase._withdraw`) tracks escrowed order inputs purely as an internal accounting number (`_orders[commitment][token]`) that is set once at `placeOrder` time and never reconciled against the gateway's actual on-chain token balance. When a fill, cancel, or cross-chain redeem/refund settles, `_withdraw` unconditionally attempts `IERC20(token).safeTransfer(beneficiary, amount)` for the fixed recorded `amount`. If the escrowed token is a rebasing ERC-20 (or any token whose `balanceOf` can autonomously decrease while custodied, e.g. via a negative rebase, slashing, or an external yield-bearing mechanism), the gateway's real balance can drop below the sum of internally recorded escrow amounts for outstanding orders. The `safeTransfer` then reverts, and because the withdrawal path is invoked exactly once per commitment (and often already flips `_filled[commitment]` or consumes the settlement message before the transfer), the escrowed value for that order becomes permanently unrecoverable.

### Finding Description
`_withdraw` is the single settlement primitive shared by same-chain fill, same-chain cancel, and both cross-chain settlement paths (`RedeemEscrow`/`RefundEscrow` delivered through `onAccept`): [1](#0-0) 

```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    if (finalize) _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len; i++) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (amount == 0) continue;

        uint256 escrowed = _orders[body.commitment][token];
        if (escrowed == 0) revert UnknownOrder();

        _orders[body.commitment][token] = escrowed - amount;
        if (token == address(0)) {
            _sendValue(beneficiary, amount);
        } else {
            IERC20(token).safeTransfer(beneficiary, amount);
        }
    }
    ...
```

`_orders[commitment][token]` is populated at `placeOrder` from the *actual received* amount for fee-on-transfer tokens, but this is a one-time snapshot; nothing re-checks `IERC20(token).balanceOf(address(this))` before or during `_withdraw`. This is structurally identical to the reported `Escrow.resolveDispute` bug: a fixed, previously-recorded value (`i_arbiterFee` in the report, `_orders[commitment][token]`/`amount` here) is transferred unconditionally, with no fallback if the contract's live balance has fallen below that recorded value. For the reported bug the cause was rebasing balance dynamics on the payment token; the same class of token (rebasing, or any token that can silently reduce a holder's balance while at rest, e.g. certain yield/auto-compounding or slashing-capable tokens) breaks the same invariant here, because the escrow contract holds tokens on behalf of multiple concurrent orders and its "sum of all `_orders[...]` entries" bookkeeping is assumed to always be ≤ actual `balanceOf(this)`.

Reachability: this is hit by any unprivileged party settling an order —
- Same-chain: `IntrinsicIntents._fillSameChain` → `_withdraw(body, false, isFullyFilled)` [2](#0-1) , and `_cancelSameChain` → `_withdraw(body, true, true)` [3](#0-2) , both callable by the order owner or (post-fill) any solver.
- Cross-chain: the source-chain `onAccept` handler for `RedeemEscrow`/`RefundEscrow`, reached via a Hyperbridge-relayed message, also funnels into `_withdraw`.

### Impact Explanation
If the escrow's per-token internal accounting exceeds the gateway's actual live balance (rebasing/balance-shrinking token), `safeTransfer` inside `_withdraw` reverts. Since `_filled[commitment]` is set (or the incoming settlement message already consumed) before/at the same call that performs the transfer, a revert here means:
- The order can never be re-settled through the normal path (retrying the same call reverts identically as the balance deficit persists or worsens).
- The escrowed principal for that order — potentially also `order.fees`, since the same function also unconditionally transfers a fixed `fees` amount from the fee-token balance — becomes permanently locked in the contract with no recovery mechanism, matching the report's "funds locked due to rebasing" impact.

This is a concrete permanent freezing of user/solver funds triggered by a normal user/solver transaction, satisfying the Medium/High bar (loss is contract-wide once triggered for any affected token, not merely resource exhaustion).

### Likelihood Explanation
Likelihood depends on whether a deployment allow-lists a rebasing or balance-shrinking token as an order input. `IntentGatewayV2`/`IntentsBase` place no restriction preventing arbitrary ERC-20 tokens from being used as `order.inputs`, and the fee-on-transfer handling in `placeOrder` demonstrates that exotic ERC-20 behavior is expected to occur for input tokens in production use of this gateway — but only the "received-amount" adjustment was made for fee-on-transfer tokens; no analogous safeguard exists for rebasing/balance-shrinking tokens at withdrawal time. Given intents-based bridges commonly support long-tail or yield-bearing assets as inputs, this is a realistic configuration, not a purely theoretical one.

### Recommendation
Before transferring the recorded `amount` in `_withdraw`, cap it to the token's actual available balance (or track escrow as a proportional/percentage claim against the live balance rather than an absolute snapshot), and if the available balance is insufficient, transfer what's available and either accrue a claim for the shortfall or emit an event so a permissioned recovery path can true-up the deficit instead of reverting the whole settlement. Alternatively, explicitly document and technically enforce (e.g., via governance-set allow-list) that only non-rebasing, balance-stable ERC-20 tokens may be used as `order.inputs`/`order.output.assets`.

### Proof of Concept
1. Deploy `IntentGatewayV2` with a mock rebasing ERC-20 `RBT` as the input token (`balanceOf` can be reduced by an external "rebase down" call, independent of `transfer`).
2. User A calls `placeOrder` escrowing `1000 RBT`; `_orders[commitmentA][RBT] = 1000`.
3. User B (or another concurrent order) also escrows `RBT`, or simply invoke the mock's negative rebase directly on the gateway's balance so `RBT.balanceOf(gateway)` drops to `900` while `_orders[commitmentA][RBT]` still reads `1000`.
4. Solver fills/cancels order A; `_withdraw` reads `escrowed = 1000`, attempts `IERC20(RBT).safeTransfer(beneficiary, 1000)`.
5. Transfer reverts (`ERC20: transfer amount exceeds balance`), while `_filled[commitmentA]` has already been set to the beneficiary in the same call (for cancel) — the order can never be settled again, and the escrowed value is permanently stuck.
