### Title
Checks-Effects-Interactions violation in `IntentGatewayV2.withdraw()` allows reentrancy from hookable/callback tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` still contains the vulnerable pre-fix pattern that the external report describes for `IdleCDO._deposit()`: an external token transfer is performed *before* the internal escrow accounting is updated. In `withdraw()`, each escrowed token is sent to the beneficiary via a low-level `.call` to `transfer()` (or a raw ETH `.call`) while `_orders[commitment][token]` is only decremented *after* that external call returns.

### Finding Description
`withdraw()` is invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests and from `onGetResponse()` after a cancel-from-source proof — both reachable via a relayer submitting a Hyperbridge cross-chain message/proof, which is a fully attacker/solver-influenced path (the `beneficiary` is either the solver or the user, both externally controlled). [1](#0-0) 

The loop checks `_orders[body.commitment][token] == 0` before transferring, then performs the token/ETH transfer via `.call`, and only *afterwards* decrements `_orders[body.commitment][token] -= amount`. For an ERC777-style or otherwise hook-enabled token (or a malicious ERC20 whose `transfer()` invokes a callback on `beneficiary`, e.g. via `tokensReceived`), the callback executes while `_orders[commitment][token]` still reflects the pre-withdrawal (undecremented) balance. Because `withdraw()` is only reachable through `onlyHost`-gated `onAccept`/`onGetResponse`, a single relayed proof/message cannot directly re-enter `withdraw()` itself, but the stale, not-yet-updated `_orders` mapping is exposed to any other public/external function of the same contract that reads `_orders[commitment][token]` during the callback window (e.g. state queried by cancellation flows, dust sweeps, or any future function reading this mapping), and — more importantly — it structurally reproduces exactly the bug class flagged in the source report: an internal accounting update that trails a token transfer capable of triggering reentrant callbacks, rather than preceding it.

This is a regression relative to the already-fixed logic present in the main EVM codebase, where the equivalent function (`IntentsBase._withdraw`) was hardened to update `_orders` *before* performing the transfer: [2](#0-1) 

The Tron contract's `withdraw()` was not updated to match this CEI-safe ordering.

### Impact Explanation
If the escrowed token used for settlement has any transfer-time callback capability (ERC777, or any token where `transfer` can trigger external code on the recipient/beneficiary), the stale accounting window in `withdraw()` allows the escrow state to be inconsistent with the true balance during the callback. Combined with any other path in the same contract that consults `_orders[commitment][token]` (fee sweep, further withdrawal attempts, cancellation checks), this can lead to double-payout or draining of escrowed user/solver funds beyond what was actually reserved — a direct fund-theft / accounting-corruption risk on the intents escrow, matching the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Exploitability depends on a token used in an order being hook-enabled (ERC777-like) or otherwise able to execute code on `transfer()` to a beneficiary that the solver/user controls — the beneficiary address is fully attacker-influenced (it's `order.user` or the filling solver), so an attacker can choose to route escrow through a token they control the receiving contract for. The trigger is a single relayed proof (`RedeemEscrow`/`RefundEscrow`/GET response), which is the standard, always-available intents settlement path.

### Recommendation
Update `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to follow Checks-Effects-Interactions: decrement `_orders[body.commitment][token]` (and clear `_orders[body.commitment][TRANSACTION_FEES]`) *before* performing the ETH `.call` or ERC20 `transfer()` call, mirroring the fix already applied in `IntentsBase._withdraw()` in the main EVM contracts.

### Proof of Concept
1. User places an order on the Tron `IntentGatewayV2` escrowing a hook-enabled/malicious ERC20 token (attacker deploys or selects such a token as input).
2. Solver fills the order; a `RedeemEscrow` message is relayed to the source chain and delivered via `onAccept()` → `withdraw()`.
3. Inside `withdraw()`'s loop, `token.call(transfer(beneficiary, amount))` triggers a callback on the beneficiary contract (attacker-controlled) before `_orders[commitment][token] -= amount` executes.
4. During the callback, `_orders[commitment][token]` still reports the full pre-withdrawal escrow amount. Any function reachable from that callback that reads/acts on this stale value (or a future contract upgrade that adds such a path) can be exploited to extract more value than was actually escrowed, since the accounting has not yet caught up with the transfer that already occurred.     function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
