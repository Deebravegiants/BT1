### Title
Unbounded `GetRequestsWithProof` batch/key count in `pallet-ismp-coprocessor::handle_unsigned` allows fee-less resource-exhaustion before any size check — (File: `modules/pallets/state-coprocessor/src/lib.rs`, `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
`pallet-ismp-coprocessor` exposes `handle_unsigned`, a feeless, unsigned (`ensure_none`) extrinsic that anyone can submit and that every node's transaction pool fully executes during `validate_unsigned` before it is even included in a block. The handler (`handle_get_requests`) performs full membership-proof verification and, for every `GetRequest` in the batch, full state-proof verification over an unbounded `keys: Vec<Vec<u8>>` list, with no upfront limit on the number of requests in the batch or the number of keys per request. Only after this expensive verification work is complete does the code consult the bandwidth gate to check the message size/quota. This is the same bug class as CVE-2020-27217 (Eclipse Hono): the size/quantity of an untrusted input is not validated before it is fully processed, letting an attacker force expensive work — here proof decoding and trie/storage-proof verification — before any size-based rejection occurs.

### Finding Description
`handle_unsigned` accepts a `GetRequestsWithProof` message under an unsigned origin: [1](#0-0) 

Its `ValidateUnsigned::validate_unsigned` implementation calls `Self::handle_get_requests(message.clone())` directly, meaning the *entire* proof-verification pipeline runs on every node during mempool validation, not merely at block execution: [2](#0-1) 

`handle_get_requests` iterates the full `requests` vector, and for each one calls `dest_state_machine.verify_state_proof(&host, req.keys.clone(), ...)` — where `req.keys` is an unbounded `Vec<Vec<u8>>` per the `GetRequest` type — decoding and verifying a full state/storage proof for every key, before any size/byte accounting takes place: [3](#0-2) 

The bandwidth-gate check (`BandwidthGate::try_consume`), which is the only mechanism that limits the "size" of what is processed, is applied only *after* `verify_state_proof` for each request has already run — explicitly noted in the code comment as "Charged after proof verification so the value sizes are final": [4](#0-3) 

The underlying `GetRequest.keys` field is documented as an arbitrary, unbounded list of raw storage keys: [5](#0-4) 

Because there is no upfront bound on the number of `GetRequest`s in a `GetRequestsWithProof` batch nor on the number of keys per request, and because the whole verification (`verify_membership` + per-key `verify_state_proof`, including trie decoding via `TrieDBBuilder`/`StorageProof::into_memory_db`, or EVM RLP/account-proof decoding) runs unconditionally before the bandwidth gate is even consulted, an attacker can submit a single unsigned, fee-less extrinsic carrying a very large number of requests/keys and force full cryptographic proof verification and trie construction work on every full node validating the transaction pool, with no economic cost and no upfront quantity check.

This mirrors CWE-1284 exactly as in the referenced advisory: the specified quantity in the input (number of keys / batch size, i.e., the "message size") is not validated before the expensive operation (deep proof verification / decompression-equivalent processing) is performed.

### Impact Explanation
This is reachable by any unprivileged party submitting a single unsigned extrinsic (no signature, no fee, no prior state) to `pallet-ismp-coprocessor::handle_unsigned`. Because `validate_unsigned` — which runs on *every* node in the network during transaction-pool gossip/validation — executes the full proof-verification logic before rejecting on size, a maliciously large but still well-formed `GetRequestsWithProof` (many `GetRequest`s, each with many keys, or large storage/account proofs) can consume excessive CPU/memory across the network at the mempool layer, before any fee or bandwidth accounting can reject it. This can degrade or halt the availability of the state-coprocessor's Get-request-response route (a route becoming unable to deliver messages), and in the worst case induce out-of-memory / excessive-CPU conditions analogous to the referenced AMQP adapter OOM, satisfying the "route unable to deliver messages" impact category.

### Likelihood Explanation
High likelihood: `handle_unsigned` is explicitly designed to be callable by anyone for free (`ensure_none`), and the vulnerable code path (`validate_unsigned` → `handle_get_requests` → `verify_state_proof`) is executed unconditionally by every node's transaction pool for every submitted transaction of this type, with no upfront limit on batch size or key count before the expensive work begins. No special privileges, timing, or race conditions are required — a single crafted extrinsic is sufficient to trigger the disproportionate verification cost.

### Recommendation
Enforce an upfront bound (e.g., a configurable `MaxRequestsPerBatch` and `MaxKeysPerRequest`/`MaxTotalKeys`, similar to the `T::MaxCallSize` gate already used in `pallet-call-decompressor`) on `GetRequestsWithProof.requests` and each `GetRequest.keys` length, checked immediately upon receipt — before any membership or state-proof verification is attempted, and definitely before `validate_unsigned` invokes the full verification pipeline. Consider moving the bandwidth/size check (or a cheap pre-check based on the encoded request sizes) ahead of `verify_state_proof`, consistent with the pattern already used in `pallet_call_decompressor::decompress`, which validates the claimed size against a configured maximum "at the single choke point every caller flows through" before doing any expansion work.

### Proof of Concept
1. Construct a `GetRequestsWithProof` with a very large `requests: Vec<GetRequest>`, where each `GetRequest.keys` contains a large number of storage keys (e.g., thousands of 52-byte EVM slot keys), and a syntactically well-formed (but arbitrarily large) accompanying `Proof`.
2. Submit this as an unsigned extrinsic via `Ismp::handle_unsigned` equivalent call on `pallet-ismp-coprocessor` (`Call::handle_unsigned { message }`).
3. Every node's transaction pool invokes `ValidateUnsigned::validate_unsigned`, which calls `Self::handle_get_requests(message.clone())` [2](#0-1) 
 — this decodes and verifies the membership proof and then loops over all requests running `verify_state_proof` for every key [6](#0-5) 
 before the bandwidth gate has a chance to reject on size, consuming disproportionate CPU/memory on every validating node for a transaction that costs the sender nothing and may ultimately be rejected.

**Note on verification limits:** I was unable to fully verify (within the remaining tool budget) whether any `MaxKeys`/`BoundedVec` type-level constant exists elsewhere in `modules/pallets/state-coprocessor` restricting `GetRequestsWithProof.requests` or per-request `keys` length — my greps for `MaxKeys`, `ConstU32`, and `BoundedVec<GetRequest` in that pallet returned matches in `lib.rs`/`impls.rs` I could not open before the iteration limit was reached. If the environment or config type does impose such bounds, this would reduce (but likely not eliminate) the severity, since the exact configured limits and whether they are enforced *before* proof verification would need confirmation. I recommend a Devin session with full filesystem access to confirm the presence/absence and value of any such bound before finalizing severity.
