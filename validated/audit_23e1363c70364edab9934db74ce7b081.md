## Analog Found: Permanent freeze of escrowed native tokens when a `WithdrawalRequest.beneficiary` is a contract that rejects ETH

### Title
Escrowed native ETH becomes permanently unrecoverable when the cross-chain refund/redeem beneficiary cannot accept plain ETH transfers - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The Footium bug (owner without a `receive()`/payable `fallback` bricking `withdraw()`) has a direct analog in Hyperbridge's `IntentGatewayV2` intents system. Native ETH escrowed for an order is released via a hard-coded `.call{value: ...}("")` to a beneficiary address that was fixed at order-creation/fill time and can never be changed afterward. If that beneficiary is a contract without a payable fallback, every attempt to deliver the corresponding cross-chain `RedeemEscrow`/`RefundEscrow` message reverts forever, and the escrowed ETH is permanently stuck.

### Finding Description
`IntentsBase._sendValue` performs a raw call and simply reverts if it fails, with no alternate recipient or wrapping fallback: [1](#0-0) 

This is used unconditionally by `_withdraw`, which releases escrow to `body.beneficiary` for both `EscrowReleased` and `EscrowRefunded` paths: [2](#0-1) 

The beneficiary is set once, at order placement (`order.user`) or fill time (`msg.sender`), and is embedded immutably in the cross-chain message body (`WithdrawalRequest.beneficiary`) dispatched by `_cancelFromSource`/`_cancelFromDest`: [3](#0-2) 

When that message is delivered on the source chain, `onAccept` decodes it and calls `_withdraw` directly — there is no way to redirect the beneficiary after the fact: [4](#0-3) 

Crucially, `EvmHost.dispatchIncoming` treats a reverting `onAccept` as "not yet delivered" rather than a hard failure — it deletes the request receipt and returns without reverting the whole batch, so the message stays retryable: [5](#0-4) 

Since the beneficiary encoded in the message never changes, every retry deterministically fails the same way. The message can never be delivered, and the ETH escrowed for that order (native `token == address(0)` legs, tracked in `_orders[commitment][address(0)]`) is permanently locked with no admin/governance override to redirect it — `_orders` has no sweep path for non-dust, non-`Execute` funds tied to a specific commitment.

### Impact Explanation
This is a concrete path to **permanent freezing of user/protocol funds**: any order with a native-ETH input leg whose `order.user` (for refunds) is a contract lacking a payable fallback — or any cross-chain fill whose solver address (`msg.sender`, used as beneficiary for `RedeemEscrow`) is such a contract — results in an undeliverable ISMP message and unrecoverable escrowed ETH. This also matches the accepted "route unable to deliver messages" impact class, since the specific commitment's message can never be finalized once this state is reached.

### Likelihood Explanation
Reachable by a single unprivileged `placeOrder` call using native ETH as input, followed by a normal cancellation flow (`_cancelFromSource`/`_cancelFromDest`) or a normal cross-chain fill by a solver whose address happens to be (or later becomes, e.g. via `SELFDESTRUCT`-removed code, or a proxy that reverts) a non-payable contract. No governance or privileged role is required; the affected user/solver could also trigger this accidentally by using a smart-contract wallet without a `receive()` function, or an attacker could deliberately grief a specific order by choosing such a beneficiary during a same-chain partial fill (`IntrinsicIntents`) targeting a griefed `beneficiary`.

### Recommendation
Add a WETH-wrap fallback (as already done for the analogous timeout path in `WrappedHyperFungibleToken.onPostRequestTimeout`) so that a failed native transfer re-wraps into an ERC-20 and is delivered via `safeTransfer` instead of reverting the whole withdrawal: [6](#0-5) 
Apply the same pattern inside `IntentsBase._sendValue` / `_withdraw` so escrow releases can never be permanently blocked by an unreceivable beneficiary.

### Proof of Concept
1. User calls `placeOrder` with a native-ETH input leg and `order.user` set to a pre-computed contract address `C` that will have no `receive()`/payable `fallback` (e.g., a minimal proxy or a contract that only implements ERC-20 receiver hooks).
2. Order goes unfilled past `order.deadline`; anyone calls `cancelOrder` (destination-side path), which dispatches a `RefundEscrow` `WithdrawalRequest{beneficiary: order.user}` to the source chain via Hyperbridge. [7](#0-6) 
3. A relayer delivers the message; `onAccept` → `_withdraw` → `_sendValue(C, amount)` reverts because `C` has no payable fallback.
4. `EvmHost.dispatchIncoming` catches the revert, deletes the receipt, and returns — the message is "not delivered" but can be resubmitted.
5. Every resubmission fails identically since `beneficiary = C` is immutable in the message; the escrowed native ETH for this commitment is permanently stuck in the `IntentGatewayV2` contract.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
