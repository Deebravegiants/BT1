### Title
Webhook shop-domain and topic are trusted for tenant/handler dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `HmacValidator.validate(request)` cryptographically authenticates only the request body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.) that are never included in the signed content [2](#0-1) . `Registry.process` nonetheless uses these unauthenticated header values to select the handler and to build the `WebhookMetadata` passed to the app's business logic as the trusted tenant identifier [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`shop used for HMAC verification == shop used to identify the tenant in WebhookMetadata`

In `Registry.process`, the only integrity check performed is `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `verifiable_query.to_signable_string` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is defined as just the raw body [1](#0-0) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all pulled from headers with no cryptographic linkage to the signature at all [2](#0-1) .

After `HmacValidator.validate` passes, `Registry.process` uses `request.topic` to select a handler and constructs `WebhookMetadata` with `shop: request.shop` — the exact field that was never covered by the signature — and hands it to the app's handler as authoritative tenant context [3](#0-2) . The documented app-handler contract explicitly treats `data.shop` as "The shop domain of the webhook" for use in tenant-scoped operations (e.g. `shop_domain: data.shop`) [5](#0-4) .

This lets an attacker who can obtain any single genuinely-signed `(raw_body, hmac)` pair for the app's secret — trivially available to any unprivileged internet user by installing the free app on their own development store and capturing the webhook Shopify sends them — replay that exact body/HMAC pair to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header to name a victim shop. `HmacValidator.validate` still succeeds (it only checks the unmodified body), but `Registry.process` will hand the app a `WebhookMetadata` claiming the payload belongs to the victim shop.

Before the attack: `request.shop` (header, unauthenticated) == the real originating shop, and `hmac` (over body only) matches; the two happen to agree only because Shopify itself set both consistently.
After the attack: `hmac` still validates (body unchanged) but `request.shop` is attacker-controlled and no longer equals the shop that actually generated/owns the signed body — breaking the equality the app relies on (`verified-shop == tenant-attributed-shop`).

### Impact Explanation
This is a cross-tenant identity spoofing primitive: the app's webhook processing pipeline reports events as coming from a shop the attacker chooses, while the actual payload content is the attacker's own shop's data (or vice versa, an attacker can attribute their own forged topic/webhook_id metadata to another shop's data flow). Any app that uses `data.shop` from `WebhookMetadata` to scope database writes, trigger uninstall/GDPR cleanup, or otherwise take tenant-scoped action — exactly as shown in the gem's own documented example (`shop_domain: data.shop`) — can have that action misattributed to a shop that never sent the webhook. This matches "cross-tenant access" in the Critical impact bucket, since the boundary between one merchant's tenant and another's is broken purely by header manipulation, without any credential of the victim tenant.

### Likelihood Explanation
Exploitation requires no credentials, no `api_secret_key`, and no access to a victim's data — only a single legitimately-signed webhook, which any unprivileged party can obtain for free by installing the app on their own store (a normal, permitted, unprivileged action) and observing what Shopify sends. The attacker then only needs to replay that one HTTP POST with a modified shop header to the app's public webhook endpoint. There's no rate limiting or nonce/replay defense evaluated in `HmacValidator`/`Registry.process` beyond the raw-body HMAC. Likelihood is High for exploitation feasibility, though real-world impact is capped by what a given app actually does with `data.shop`.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signed content (or otherwise cryptographically bind them), or at minimum require the app/gem to validate that `request.shop` matches an active, previously-authorized shop/session before using it as a trust anchor for dispatch. Since real Shopify webhook signatures only cover the body by protocol design, the gem should document this limitation prominently and/or provide a helper that cross-checks `shop`/`topic` against known registered shops/topics before invoking `handler.handle`, rather than passing raw, unauthenticated header values straight through as trusted `WebhookMetadata`.

### Proof of Concept

#   raw_body = '{"id":1,...}'   # attacker's own shop's order payload
#   headers  = {
#     "x-shopify-hmac-sha256"  => "<valid-hmac-of-raw_body>",
#     "x-shopify-topic"        => "orders/create",
#     "x-shopify-shop-domain"  => "attacker-shop.myshopify.com",
#   }

# Attacker replays the SAME body + hmac, but spoofs the shop-domain header:
forged_headers = {
  "x-shopify-hmac-sha256" => "<same-valid-hmac-of-raw_body>", # unchanged, still valid
  "x-shopify-topic"       => "orders/create",
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",     # forged

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (only raw_body is checked)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))

# typed: strict

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end
