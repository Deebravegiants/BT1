### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while the `shop` identity field (read from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header) is never included in the HMAC-verified data. `Registry.process` accepts any request whose body HMAC validates and then trusts `request.shop` as the tenant identity delivered to the app's webhook handler.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop` is parsed straight from an attacker-controllable HTTP header, entirely outside the signed data: [3](#0-2) 

`Registry.process` only checks the body HMAC, then forwards the unauthenticated `shop` value into `WebhookMetadata`, which is the sole tenant identifier delivered to the handler: [4](#0-3) [5](#0-4) 

The binding that is broken is: `shop header value == shop the body's HMAC was actually computed for`. Because the header is never part of the signable string, these two need not match. An attacker who can obtain any body+HMAC pair signed with the app's shared secret (e.g., by installing the app on their own store and triggering a real webhook delivery, since the same `api_secret_key` is used to sign webhooks for every shop that installs the app) can resend that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary victim `shop` value in the domain header. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will invoke the handler with `data.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant-identity binding relied on by every consumer of `WebhookMetadata#shop`, including the mandatory GDPR topics `shop/redact`, `customers/redact`, and `customers/data_request` enumerated in `Registry::MANDATORY_TOPICS`. An attacker can cause an app's webhook handler to execute shop-scoped business logic (e.g., data deletion/redaction routines, cache invalidation keyed by shop, entitlement/subscription updates, or any app logic keyed by `data.shop`) attributed to a shop the attacker does not control, which is a cross-tenant confusion/attack against apps built on this gem's documented webhook contract.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on an attacker-owned development/trial store to obtain a genuine body+HMAC pair (the app's `api_secret_key` is shared across all shops, this is normal, unprivileged use of the app), and (2) sending an HTTP POST to the app's public webhook endpoint with that captured body/HMAC and a forged shop-domain header. No access token, `client_secret`, or privileged account for the victim shop is needed, matching the credential-boundary constraints of this analysis.

### Recommendation
Bind the shop identity to the verified payload before trusting it: derive/validate `shop` from data that is itself covered by the HMAC (e.g., require the body's own JSON to carry and cross-check a shop identifier that Shopify includes in some payloads, or better, have `Request#to_signable_string` incorporate the shop-domain header into the signed string so tampering invalidates the HMAC), and reject requests where the header-derived shop cannot be corroborated against verified data.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) to capture a genuine `raw_body` and its `X-Shopify-Hmac-Sha256` value, both signed with the app's `api_secret_key`.
2. Send a POST to the app's webhook endpoint with headers:
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Hmac-Sha256: <captured value>`
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   and the same captured raw body.
3. `Utils::HmacValidator.validate` passes because it only checks `raw_body` against the HMAC (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31, `lib/shopify_api/webhooks/request.rb` lines 35-38).
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), even though that body was never generated for `victim.myshopify.com`.
