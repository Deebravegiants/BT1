### Title
Emporium `payRelayFees` skips the relay/protocol fee on value that changes token identity inside `ops` execution - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction()` lets the prover route Hinkal funds through an arbitrary sequence of external calls (`stack.ops`), then charges the relay/protocol fee only on tokens whose circuit-declared `deltaAmountChanges[i]` is negative [1](#0-0) . This lets a user perform the economic equivalent of a token swap inside Emporium (deposit token A, have `ops` swap it to token B via any external endpoint) while declaring `deltaAmountChanges[B] == 0`, so no relay fee is ever computed for the value that leaves as token B, unlike the dedicated `ExternalActionSwap.swap()` flow, which always deducts `hinkalFee`/`relayFee` from the swap output [2](#0-1) .

### Finding Description
In `runAction`, deposits (`deltaAmountChanges[i] >= 0`) are explicitly exempted from fees: [3](#0-2) 

Meanwhile `handleOut` unconditionally forwards any positive `balanceChange` for a token to the caller (Hinkal) and returns it as a new UTXO to be committed into the shielded pool, with no fee deduction of any kind: [4](#0-3) 

The `ops` array executed before fee accounting allows calling an arbitrary `endpoint` with arbitrary `callData` (only `callHinkalWallet`/`doSendToRelay` selectors are blocked in the stateless case) [5](#0-4) . A prover can therefore:
1. Declare `deltaAmountChanges[A] = +X` (deposit token A into Emporium — not fee-charged).
2. Have an `op` call any DEX router to swap A for B using Emporium's balance.
3. Declare `deltaAmountChanges[B] = 0` (neither deposit nor withdrawal for B).
4. `payRelayFees` skips token B entirely because its delta is `>= 0`.
5. `handleOut` observes `balancesAfter[B] - balancesBefore[B] > 0` (the swap proceeds) and sends the full, un-fee'd amount back to Hinkal as a new UTXO, which Hinkal.sol's balance equation happily accepts since `balanceDif == amountChanges[B] (0) + utxoAmount[B]` holds by construction [6](#0-5) .

This is directly analogous to the reported `FixedFeeSwap` bug class: value is converted from one asset to another through a "deposit" path that the fee logic treats as fee-exempt, rather than through the fee-bearing "swap" path, allowing the protocol/relay fee to be fully bypassed.

### Impact Explanation
This breaks the intended fee equality that every swap-like value conversion executed through Hinkal's external-action framework should pay the relay/protocol `variableRate`/`flatFee`. The result is systematic theft of protocol/relay fee revenue — every swap routed through Emporium instead of `ExternalActionSwap` bypasses fees entirely, which the Impact rubric classifies as High ("theft ... of protocol/relay fees").

### Likelihood Explanation
Likelihood is high for any unprivileged EOA acting as its own prover/relay-caller: it only requires constructing `circomData`/`EmporiumStack` with a zero delta for the output token and an `ops` entry pointing at any DEX router — no privileged role, relay cooperation, or admin action is needed. The only constraint is that the resulting UTXO for token B must be validly proven under the ZK circuit, but the circuit's per-token conservation check (`inTotal + amountChanges[i] === outTotal`) does not constrain `amountChanges[i]` to reflect the real value obtained from an unrelated token via `ops`, since it only checks UTXO conservation for token `i`'s own commitments [7](#0-6) .

### Recommendation
Compute the relay/protocol fee based on the actual `balanceChange` per token observed after `ops` execution (i.e., the real value gained by the shielded pool), not solely on the circuit-declared `deltaAmountChanges[i]` sign. Any positive `balanceChange` for a token that was not present in Emporium's opening balance and not declared as a deposit should be treated as a chargeable swap output, consistent with `ExternalActionSwap`'s fee model.

### Proof of Concept
Not executable from static analysis alone — a full PoC requires generating a valid Hinkal ZK proof and an `EmporiumStack` with an `EmporiumOperation` calling a real DEX router. Conceptually:
```
// circomData.erc20TokenAddresses = [A, B]
// circomData.amountChanges = [+100 (A deposit), 0 (B untouched)]
// EmporiumStack.ops = [{ endpoint: dexRouter, invokeWallet: false, value: 0,
//                         callData: swap(100 A -> B) }]
// -> payRelayFees skips token B (delta == 0)
// -> handleOut sends full swapped B amount back to Hinkal, minted as a fee-free UTXO
```
This could not be fully verified end-to-end (proof generation, actual router integration) within the scope of this static review; confirming exploitability requires running the circuit/prover and a testnet fork with a real DEX router, which is out of scope for this analysis.
