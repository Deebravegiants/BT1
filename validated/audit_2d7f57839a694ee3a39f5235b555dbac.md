Raydium's fee model is structurally different from the Mellow vault case in the report. Fees here are charged deterministically on each instruction rather than through a time-delayed accrual mechanism:

- Swap fees (`swap_fee_numerator`/`swap_fee_denominator`) are deducted on every single swap instruction, with no time-based skip logic. [1](#0-0) 
- The PnL "protocol fee" (`pnl_numerator`/`pnl_denominator`) is computed via `calc_take_pnl` and invoked unconditionally on every deposit and withdraw call (except when the AMM is in `WithdrawOnly` status, which is an admin-controlled state, not something a user can trigger via timing). [2](#0-1) [3](#0-2) 
- There is no `managementFeeChargeDelay`-style field or `elapsed < delay` early-return anywhere in the fee-charging code paths; a search across `program/src/processor.rs` and `program/src/state.rs` found no analogous "skip fee if time since last charge is below threshold" logic. [4](#0-3) 

Since fees/PnL extraction are computed fresh from live vault balances (`amm_pc_vault.amount`, `amm_coin_vault.amount`) on every deposit/withdraw/swap call rather than accrued lazily over an elapsed-time window, there is no way for a user to "sneak in" a large deposit/withdraw within a fee-free window the way the Mellow vault bug allowed. The bug class (skipping fee accrual due to a time-delay guard) does not map onto any unprivileged, single-transaction-reachable code path in this program.
