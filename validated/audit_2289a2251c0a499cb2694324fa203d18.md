## Title
`pallet-hyper-fungible-token::update_token` changes cross-chain decimal precision without settling in-flight transfers, corrupting the conversion of already-dispatched messages - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
`pallet-hyper-fungible-token` stores the EVM-side decimal precision for each `(AssetId, StateMachine)` pair in the `Precisions` storage map, used to scale amounts between local and ERC20 denominations. `update_token` lets `CreateOrigin` mutate this precision for an existing chain at any time, but `on_accept` re-reads `Precisions` *at delivery time* rather than at the time the corresponding EVM-side `send` was dispatched. This is the same bug class as the reported `AdvancedDistributor.setVoteFactor` issue: a conversion-rate parameter is changed without first draining/settling all state (in this case, in-flight ISMP messages) that was computed against the old parameter value.

### Finding Description
- `Precisions<AssetId, StateMachine> -> u8` records the ERC20 decimals of the token contract on a given remote chain. [1](#0-0) 
- `update_token`, gated only by `CreateOrigin`, overwrites `Precisions` for `add_chains` immediately, with no check for outstanding requests still traveling toward this chain: [2](#0-1) 
- On the inbound path, `on_accept` (invoked when an ISMP `PostRequest` from the peer EVM `HyperFungibleToken` contract is delivered, which can happen at an unpredictable, relayer-controlled/proof-delay time after the corresponding EVM `send`) reads `Precisions` **at the moment of delivery**, not at the moment the EVM sender encoded the amount, and uses it to convert the raw ERC20 `message.amount` into the local balance: [3](#0-2) 
- The conversion is a straight division: `amount = message.amount / 10^(erc_decimals - local_decimals)` via `convert_to_balance`: [4](#0-3) 
- The EVM side (`HyperFungibleToken.sol`) mints/burns the literal `message.amount` with no independent scaling of its own — it relies entirely on the substrate pallet applying the correct, matching decimals on both legs: [5](#0-4) 

Because `on_accept` derives the divisor from the *current* `Precisions` value rather than the value that was in effect when the EVM contract encoded `message.amount`, any message dispatched from EVM before an `update_token` precision change, but delivered after it, is converted with the wrong divisor.

### Impact Explanation
If governance updates `Precisions` for a chain (e.g., correcting a misconfigured decimal, or in the normal course of onboarding/reconfiguring a token) while user-initiated transfers are still in flight (queued/awaiting relay/consensus finality — an entirely normal condition for ISMP cross-chain messages, which can take minutes to hours):
- If `erc_decimals` is decreased, the divisor shrinks and `on_accept` mints/releases **more** local tokens than the escrowed/burned EVM-side amount actually backs — an unbacked mint that can be drained by the beneficiary, directly reducing the collateral backing all other cross-chain balances (analogous to token-total-record desync in the source report).
- If `erc_decimals` is increased, the divisor grows and `on_accept` mints/releases **far less** than owed, permanently freezing/losing the difference for the user who already had funds locked/burned on the EVM side.

This is a config-change/parameter-drift bug rather than a pure admin-malice bug: the harm is realized purely because in-flight state (dispatched-but-undelivered ISMP requests) was computed under the old parameter and there is no mechanism to drain, pause, or reconcile it before the parameter is changed — exactly mirroring "should burn existing minted token for all beneficiaries before changing voteFactor."

### Likelihood Explanation
Precision reconfiguration is an expected, periodically-exercised operation (`update_token`/`update_asset_precision` are documented pallet features, not one-off deploy-time-only settings), and ISMP cross-chain settlement inherently has a non-trivial delivery latency (consensus proof generation + relay time), so there is a realistic window during which unprivileged users' in-flight `send()` transfers coexist with a precision change. No attacker collusion with the origin controlling `CreateOrigin` is required for the loss to occur — an ordinary corrective precision update triggers it.

### Recommendation
Do not apply the current `Precisions` value to in-flight messages. Options:
- Embed the decimals (or a precision-epoch/version identifier) used at `send()` time into the dispatched `Message` body itself, and have `on_accept` use that embedded value for the conversion instead of re-reading current storage.
- Alternatively, require that `update_token`/precision changes only take effect after in-flight requests for that `(asset, chain)` pair have fully settled or timed out (e.g., via a pause + drain window), similar to the recommended fix of burning/settling all outstanding minted tokens before changing `voteFactor`.

### Proof of Concept
1. User calls `send()` on Substrate with `asset_id`, `destination = EVM chain X`; pallet reads `Precisions[asset_id][X] = 18`, computes `erc20_amount = convert_to_erc20(amount, 18, local_decimals)` and dispatches an ISMP `PostRequest` to the EVM `HyperFungibleToken` contract on chain X (`modules/pallets/hyper-fungible-token/src/lib.rs` lines 292-310). The request is in flight, awaiting relay/consensus proof.
2. Before the message is delivered, `CreateOrigin` calls `update_token` to correct/change `Precisions[asset_id][X]` to `6` (e.g., because a newly-added token on chain X genuinely uses 6 decimals), per `modules/pallets/hyper-fungible-token/src/lib.rs` lines 384-421.
3. Separately, an EVM-side `HyperFungibleToken` transfer from chain X to Substrate, encoded assuming decimals `18`, is dispatched and also in flight.
4. When this reverse message is delivered, `on_accept` reads the *now-updated* `Precisions[asset_id][X] = 6` (module.rs lines 82-90) and computes `amount = message.amount / 10^(6 - local_decimals)` instead of `/10^(18 - local_decimals)`, minting/releasing roughly `10^12`× more local tokens than the message actually represents — an unbacked mint that can be withdrawn by the beneficiary, exceeding the pallet's real custody/burn backing for that asset.

		pub fn update_token(
			origin: OriginFor<T>,
			update: TokenUpdate<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if update.asset_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					update.asset_id.clone(),
				)
			};

			for (chain, config) in update.add_chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				// Remove old reverse mapping if it exists
				if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone())
				{
					ContractToAsset::<T>::remove(chain, old_contract);
				}

				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					update.asset_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(chain, token_contract, update.asset_id.clone());
				Precisions::<T>::insert(update.asset_id.clone(), chain, config.decimals);
			}

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
