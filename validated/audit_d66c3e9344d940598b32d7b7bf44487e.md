### Title
`add_gas_key` writes up to `MAX_NONCES_FOR_GAS_KEY` trie nonce entries per `AddKey` action without charging any compute cost for the writes - (File: runtime/runtime/src/access_keys.rs)

### Summary
`add_gas_key` in `runtime/runtime/src/access_keys.rs` loops `num_nonces` times calling `set_gas_key_nonce`, performing up to `MAX_NONCES_FOR_GAS_KEY` trie writes for a single `AddKey` action, but unlike the symmetric deletion path (`delete_gas_key`), it never adds any `compute_usage` for these writes. [1](#0-0)  This creates an accounting asymmetry: the same per-nonce trie work that is explicitly metered on delete via `storage_removes_compute`/`safe_add_compute` is completely unmetered on add. [2](#0-1) 

### Finding Description
`action_add_key` dispatches to `add_gas_key` when the `AddKeyAction` carries `GasKeyInfo`. [3](#0-2)  `add_gas_key` sets the access key and then executes:
```
for i in 0..num_nonces {
    set_gas_key_nonce(state_update, account_id.clone(), public_key.clone(), i, nonce);
}
```
followed only by a `storage_usage` update via `gas_key_storage_cost`, with no `compute_usage`/gas accounting for the loop itself. [1](#0-0) 

Compare this to `delete_gas_key`, which performs the mirror-image loop (`remove_gas_key_nonce`) and explicitly computes `nonce_remove_compute` via `storage_removes_compute` and adds it to `result.compute_usage`: [4](#0-3) 

`num_nonces` is attacker-controlled via `AddKeyAction.access_key`, bounded only by `AccessKeyPermission::MAX_NONCES_FOR_GAS_KEY` in `validate_add_key_action`: [5](#0-4) 

Because the write loop is not metered with `compute_usage`, the per-node CPU/IO cost of inserting up to `MAX_NONCES_FOR_GAS_KEY` trie entries is not reflected in the compute budget that bounds per-chunk wall-clock execution time, even though the symmetric delete path treats this exact same kind of trie work as compute-relevant.

### Impact Explanation
This falls under the "gas or storage metering bypass" / "unbounded resource use" impact class. An attacker paying for a single `AddKey` action with a maximal `num_nonces` gas key forces validators to perform up to `MAX_NONCES_FOR_GAS_KEY` trie insertions worth of CPU/IO work while only the (unrelated, num_nonces-independent) storage_usage bookkeeping and base `AddKey` action fee are charged — with zero contribution to `compute_usage`, unlike the equivalent delete path. This can amplify the difference between chargeable gas and actual validator work when packing many maximal `AddKey(gas_key)` actions into transactions/receipts within the chunk's gas limit, since `compute_usage` (which gates real wall-clock work independently of gas) does not scale with the number of nonces written.

### Likelihood Explanation
Preconditions are minimal: any unprivileged account with enough balance to submit one `AddKey` action and pay the flat `AddKey` fee (not scaled by `num_nonces`) can trigger this; `num_nonces` up to `MAX_NONCES_FOR_GAS_KEY` requires no special permission beyond `ProtocolFeature::GasKeys` being enabled. [6](#0-5)  It is fully repeatable and can be batched across multiple actions/receipts to further amplify the unmetered work, since the missing charge is deterministic code behavior, not a race condition.

### Recommendation
In `add_gas_key`, compute and add a `compute_usage`/gas charge proportional to `num_nonces` for the nonce-insertion loop, symmetric to `delete_gas_key`'s `storage_removes_compute`/`safe_add_compute` treatment (e.g., an analogous `storage_writes_compute` helper), and ensure this is included in the actual burnt gas charged to the sender before/while performing the writes.

### Proof of Concept
Extend the existing test module in `runtime/runtime/src/access_keys.rs`:
1. Call `action_add_key` with a gas key where `num_nonces = MAX_NONCES_FOR_GAS_KEY`.
2. Assert that `result.compute_usage` is `0` (or unrelated to `num_nonces`), demonstrating the missing metering — contrast with `test_delete_gas_key`, which asserts `result.compute_usage == expected_nonce_remove_compute(...)`. [7](#0-6) 
3. As an integration-level PoC, measure wall-clock time / number of `set_gas_key_nonce` trie writes for `add_gas_key` at `MAX_NONCES_FOR_GAS_KEY` versus the gas actually burnt for the `AddKey` action, and assert they scale linearly with `num_nonces` (expected to fail on current code since burnt gas is flat while writes scale with `num_nonces`).
