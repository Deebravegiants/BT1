### Title
Webhook shop-domain identity is trusted for routing but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by checking `Utils::HmacValidator.validate(request)`, but the HMAC is computed only over the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that the handler receives and acts on are pulled straight from unauthenticated HTTP headers [2](#0-1) , and are never bound to, or cross-checked against, the HMAC-verified bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the HMAC solely against that signable string [3](#0-2) . Meanwhile, `Registry.process` does:

```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [4](#0-3) 

`request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are read directly from the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers [5](#0-4) [6](#0-5) . None of these headers are part of the HMAC input.

Because the same app-level `api_secret_key` is used to sign webhooks for every shop that has the app installed (it is not a per-shop secret), a merchant who has legitimately installed the app receives a genuinely-signed webhook (valid HMAC over a body they control/observe, e.g. by triggering `orders/create` on their own store). They can then replay that exact raw body and its valid `x-shopify-hmac-sha256` value in a forged HTTP request to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` (it never inspects the shop header), and `Registry.process` will invoke the handler with `shop: <victim-shop>` and the attacker-supplied body, breaking the intended binding: `shop header used for tenant routing == shop that produced the HMAC-covered body`.

### Impact Explanation
This breaks tenant isolation: the host application (per the documented handler contract in `docs/usage/webhooks.md`, which explicitly relies on `data.shop` to route/attribute webhook data per store) will attribute attacker-controlled webhook payloads to a shop the attacker does not own. Depending on how the host app persists webhook data (order records, product records, `app/uninstalled` cleanup, GDPR-mandatory webhooks, etc.), this can lead to cross-tenant data injection or corruption purely because the identity field (`shop`) used for authorization/attribution is unauthenticated relative to the payload that was actually verified.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate, unprivileged merchant of the same app (a normal "internet user" relative to other tenants) able to trigger and observe at least one real webhook delivery to their own store — no access to `api_secret_key`, access tokens, or another merchant's credentials is required. This is a realistic, low-barrier scenario for any multi-tenant Shopify app built on this gem.

### Recommendation
Do not trust the `shop`/`shop-domain` header for tenant attribution unless it can be tied to the verified request. Options:
- Include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable string, matching it against a value independently verified out-of-band (e.g., the shop stored against the webhook subscription when it was registered via `Registry.register`).
- At minimum, require host applications to cross-check `request.shop` against their own known/installed-shop list before trusting the attributed data, and document this gap prominently since the current webhook docs imply `data.shop` is trustworthy on its own [7](#0-6) .

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a real webhook, e.g. `orders/create`, capturing the raw body `B` and header `x-shopify-hmac-sha256: H` (valid, since `H = HMAC(app_secret, B)`).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(app_secret, B)` and finds it equal to `H` [3](#0-2) , so validation passes.
4. `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` and the attacker's body `B` [4](#0-3) , causing the host app to process/attribute attacker-controlled data as belonging to the victim shop.
