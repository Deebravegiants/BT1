### Title
Unsigned GetResponse handler runs full state-proof verification before the bandwidth allowance check, enabling free-of-charge resource-consumption spam - (File: modules/pallets/state-coprocessor/src/impls.rs)

### Summary
`pallet_state_coprocessor::handle_get_requests`, invoked via the fee-less `handle_unsigned` extrinsic (`ensure_none` origin) and re-executed in full inside `ValidateUnsigned::validate_unsigned`, performs the cryptographically expensive `verify_state_proof` trie-proof verification for every `GetRequest` in a batch *before* checking `BandwidthGate::try_consume`, the allowance/authorization gate for the destination app. The documented design intent was the opposite ("fails fast for apps without allowance" — see the `Config::BandwidthGate` doc comment), but the implementation charges bandwidth only *after* proof verification completes. [2](#0-1) [3](#0-2) 

### Finding Description
`handle_get_requests` executes, in order: dedup checks, timeout/source/dest metadata checks, a batch membership-proof verification (`verify_membership`) against the source chain, and only then, per-`GetRequest` in a loop, calls the expensive `verify_state_proof` against the destination-chain state root — and *only after that* calls `BandwidthGate::try_consume` to check whether `(response.get.source, response.get.from)` has any purchased/allowlisted bandwidth at all. [4](#0-3) 

Because `BandwidthGate::try_consume` can reject with `GateError::NoAllowance` (any unregistered/never-purchased app on a given source chain) or `GateError::Insufficient`, an attacker can submit `GetRequestsWithProof` batches targeting apps that have zero allowance, forcing the runtime to run full Merkle/state-trie proof verification (`verify_membership` + `verify_state_proof` per key) for work that is guaranteed to be discarded and never paid for. This mirrors the OpenClaw analog exactly: expensive preflight processing (audio transcription / state-proof verification) is performed unconditionally before the cheap authorization check (member allowlist / bandwidth allowance) that should have short-circuited it.

The severity is compounded by the dispatch path: `handle_unsigned` is a `pallet::call` with `ensure_none(origin)` (no signed account, no transaction fee) and a fixed, trivial declared weight (`DbWeight::get().reads_writes(1, 2)`) that does not reflect the actual cost of the proof verification performed inside `handle_get_requests`. Worse, `ValidateUnsigned::validate_unsigned` — which runs on every node in the network as unsigned transactions propagate through the gossip/mempool layer, prior to block inclusion — calls `Self::handle_get_requests(message.clone())` directly to determine validity. This means the full expensive verification workload runs at least twice per submitted message (once in mempool validation, once at execution) for zero fee, and can be repeated indefinitely by gossiping new unsigned messages with varying content (to bypass the `provides: [msg_hash]` tag dedup) targeting apps with no bandwidth allowance. [5](#0-4) 

### Impact Explanation
This is unauthenticated, fee-free resource consumption (CWE-770: allocation of resources without limits, CWE-408: incorrect behavior order) reachable by any relayer or network peer submitting unsigned `GetRequestsWithProof` messages — no allowlisting, signature, or fee is required to trigger full cryptographic proof verification. Sustained spam against apps with no bandwidth allowance can consume validator/collator CPU on both the mempool-validation and block-execution paths without cost to the attacker, degrading availability of the state-coprocessor/GET-response pipeline and, by extension, block production capacity generally on the affected parachain. This aligns with the "Medium" severity, availability-only (`CVSS: .../A:L`) classification of the analog report — it does not on its own enable theft, forgery, or unbacked minting, but it is a genuine reachable pre-authorization resource-consumption route through a core Hyperbridge message-handling pallet.

### Likelihood Explanation
High likelihood of exploitability: the entry point requires no signed origin, no stake, no fee, and no prior registration — an attacker only needs a validly-structured (but unauthorized-app) `GetRequestsWithProof` with a syntactically valid proof format (proof verification failure due to bad Merkle data would short-circuit earlier only if the proof itself is malformed before verification arithmetic runs; a well-formed-but-non-matching proof still costs full verification effort). The `BandwidthGate::try_consume` rejection for `NoAllowance` requires no coordination — any never-purchased `(source, app)` pair works — making this trivially and repeatably triggerable.

### Recommendation
Reorder `handle_get_requests` to call `BandwidthGate::try_consume` (using the request's declared key/context byte size, as already computed for post-verification metering) immediately after the cheap metadata checks (timeout/source/dest/dedup) and before `verify_membership`/`verify_state_proof` are invoked, matching the documented intent in the `Config::BandwidthGate` doc comment. Since the exact response payload size isn't known until after proof verification, use the pre-verification size estimate (`sum(keys.len()) + context.len()`, already documented) to gate eagerly, and reconcile/only mint reputation off the post-verification exact size as today. Additionally, consider giving `handle_unsigned`/`validate_unsigned` a weight or pre-charge proportional to the batch's proof size so mempool-level validation cost is bounded, and avoid running the full handler twice (once in `validate_unsigned`, once in dispatch).

### Proof of Concept
1. Do not purchase or allowlist any bandwidth for app `X` on source chain `S` (`Allowance` and `Allowlist` storage empty for `(S, X)` in `pallet_bandwidth`).
2. Craft a `GetRequestsWithProof` containing one or more well-formed `GetRequest`s from `(S, X)` together with a syntactically valid `source` membership proof and `response` state proof (can be a real proof from any other app/chain pair, reused/adapted so it passes the cheap metadata checks and reaches the verification stage) — the goal is only to force execution into `verify_membership`/`verify_state_proof`, not to obtain a delivered response.
3. Submit the message as an unsigned transaction (`Call::handle_unsigned { message }`) to any node's transaction pool.
4. Observe: `validate_unsigned` (see [6](#0-5) ) invokes `handle_get_requests`, running full `verify_membership` and `verify_state_proof` before ultimately failing at `BandwidthGate::try_consume` with `GateError::NoAllowance` — at zero fee cost to the submitter, and repeatable at will by varying request nonces/timestamps to change `msg_hash` and bypass the mempool's `provides` dedup tag.
