Given the scope of this task, I searched the codebase for the closest architectural analog to the Electron "untrusted content granted a powerful, unrestricted capability" bug class. The strongest match is `CallDispatcher.sol`, a shared executor contract used by `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentsBase`/`IntentGatewayV2` to run attacker-supplied calldata carried inside cross-chain messages and intent orders.

### Title
Unauthenticated `CallDispatcher.dispatch()` lets any caller drain funds held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` has no caller restriction at all — no `onlyHost`, no owner check, nothing [1](#0-0) . It is invoked from `HyperFungibleToken.onAccept`, `WrappedHyperFungibleToken.onAccept`, and `IntentsBase._execute` with fully attacker-controlled `Call[]` data decoded from cross-chain message bodies / order outputs [2](#0-1) [3](#0-2) , but since `dispatch()` itself is `external` with no modifier, anyone can call it directly on-chain as well, using the dispatcher's own token/native balance and identity as `msg.sender` for the outgoing call [4](#0-3) .

### Finding Description
The `CallDispatcher` is a single, shared, stateful contract (it has a `receive()` function and can hold ERC20 balances) reused across multiple apps: `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2`/`IntentsBase` [5](#0-4) . Its `dispatch(bytes memory encoded)` function decodes an arbitrary `Call[]` and executes `to.call{value: call.value}(call.data)` for each entry, with no access control restricting who may invoke it [6](#0-5) .

In normal flow, `IntentsBase._execute` routes an order's output tokens to the dispatcher, calls `dispatch()`, then sweeps residual balances back to the calling contract [7](#0-6) , and the `WrappedHyperFungibleToken` docs explicitly instruct setting `to = CALL_DISPATCHER` so it "holds and forwards native tokens" during a bridged calldata execution [8](#0-7) . Any residual dust left behind after a sweep (rounding, a reverted/partial sweep leg, unclaimed `Call.value` remainder, or ETH sent via `receive()`), together with any race where funds are in the dispatcher's balance between the "receive tokens" step and the "sweep" step of one transaction and the next transaction's `dispatch()` call, is directly reachable by an unprivileged third party: they need only call `CallDispatcher.dispatch()` themselves (or trigger it indirectly through any app's `onAccept`) with a `Call` whose `to` is the token/ETH held and whose `data`/`value` routes it to their own address. Because the dispatcher performs the call as itself, it needs no prior approval from anyone — if it holds a balance, it can be told to send that balance anywhere.

This mirrors the Electron `nodeIntegration` bug class: a component (`CallDispatcher`) that holds a powerful, unrestricted capability (arbitrary outbound calls using its own funds/identity) is reachable by untrusted, unauthenticated input — bridged message calldata that any user can craft, or a direct external call — with no trust-boundary check analogous to `contextIsolation`/`nodeIntegration: false`.

### Impact Explanation
Any native ETH or ERC20 tokens that transiently or permanently sit in `CallDispatcher` (dust from partial sweeps, WETH-unwrap remainders, or leftover `Call.value`) can be stolen outright by any unprivileged caller invoking `dispatch()` directly, since the function performs `to.call{value}(data)` using the dispatcher's own balance without any authorization check.

### Likelihood Explanation
The dispatcher is designed to hold balances by intent (it has `receive()` and is explicitly used as a temporary holding/forwarding point per the `WrappedHyperFungibleToken` calldata-execution flow), so residual balances arising from partial fills, failed pushes, or rounding are a realistic and recurring occurrence, and exploitation only requires one unprivileged transaction calling the public `dispatch()` function.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the specific app contract that owns the funds for that call (e.g., pass/verify the calling app as an authorized caller, or make the dispatcher stateless per-call by requiring exact-balance accounting and disallowing any balance to persist between calls), and ensure all apps sweep dust to zero or revert rather than leaving residual balances in the shared dispatcher.

### Proof of Concept
1. A cross-chain transfer/order leaves ERC20 dust or native ETH in `CallDispatcher` (e.g., a WETH-unwrap remainder, or a sweep leg that reverts/undercounts) after `IntentsBase._execute`'s sweep [9](#0-8) .
2. An unprivileged attacker calls `CallDispatcher.dispatch(encoded)` directly with `Call{ to: <dust token or self>, value: <dispatcher's ETH balance>, data: <transfer to attacker> }` [6](#0-5) .
3. Since `dispatch()` has no caller restriction, the call executes with the dispatcher's own balance, transferring the stranded funds to the attacker.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
```

### Calldata Execution

Pass a non-empty `data` field to execute arbitrary calls on the destination chain after tokens are unlocked. The `data` must be an ABI-encoded `Call[]` array (see [overview](/developers/evm/hyper-fungible-token/overview#calldata-execution) for the full `Call` struct and security details).

When `isWeth = true`, the WrappedHFT unwraps WETH to native ETH on receive. This example bridges WETH back to the home chain, where it's unwrapped to native ETH and swapped for an exact amount of USDC via UniswapV2. The `Call.value` field forwards the native ETH to the router — demonstrating that the `CallDispatcher` can hold and forward native tokens:
