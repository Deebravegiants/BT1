Confirmed: `SessionCookie` is a plain `T::Struct` with no cryptographic signature over its `value` field, and `SessionUtils.cookie_session_id` simply reads that raw cookie value back out with no verification at all.

### Title
Non-embedded OAuth session cookie value is an unsigned, predictable session identifier that can be forged to hijack another shop's session - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
For non-embedded (or embedded-without-JWT-fallback) apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets a session cookie whose `value` is the deterministic `Session#id` (`"offline_#{shop}"` or `"#{shop}_#{associated_user.id}"`), and `ShopifyAPI::Utils::SessionUtils.current_session_id`/`cookie_session_id` later trust that raw cookie value verbatim as the session lookup key, with no signature or binding back to an authenticated request.

### Finding Description
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the session id deterministically from public/guessable inputs and stores it as the cookie value: [1](#0-0) 
The `id` itself is computed in `Session.from` as `"offline_#{shop}"` or `"#{shop}_#{associated_user.id}"`: [2](#0-1) 
`SessionCookie` carries no HMAC or signature over its `value`: [3](#0-2) 
And when a request comes back in, `SessionUtils.current_session_id`/`cookie_session_id` read that cookie value straight out and return it as the trusted session id, with no cryptographic check that the value actually originated from this library's own `Set-Cookie`: [4](#0-3) [5](#0-4) 

The binding that is broken is: **the session id used to fetch a stored access token == the shop/user identity actually authenticated by this request**. Instead, the equality that actually holds is: **the session id used to fetch a stored access token == bytes taken verbatim from an incoming, unsigned `Cookie` header**. Because the id is a deterministic function of a publicly-known shop domain (and, for online tokens, an associated-user id that is often also discoverable), any unprivileged internet user who can place a cookie named `shopify_app_session` on a request to the app (e.g., via a `Set-Cookie` on a related response the attacker controls, a subdomain-cookie-tossing setup, or simply by using their own browser with a manually crafted cookie against an app that doesn't tie cookies to browser-session integrity) can cause `SessionUtils.current_session_id` to resolve to another shop's `offline_#{victim_shop}` id and have the host application load and use that shop's stored access token.

### Impact Explanation
If exploited, this results in cross-tenant access: a caller who never completed OAuth for shop A can obtain a session id that resolves to shop A's persisted `ShopifyAPI::Auth::Session` (including its access token) in the host application's session storage, purely by supplying a guessable cookie value. This matches the Critical impact category of cross-tenant access / theft of a merchant access token, since the actual boundary broken is "any caller ↔ genuine OAuth-authenticated user of shop A."

### Likelihood Explanation
Likelihood depends on the host application's cookie-setting hygiene (`secure`, `HttpOnly`, `SameSite`, and whether cookies can be set cross-origin against the app's domain), which is outside this gem's direct control but is a direct consequence of this gem returning the raw, unauthenticated cookie value as an authoritative session id with no signature. Given `Session#id` is deterministic and derivable purely from the target's public shop domain, guessing/forging the value requires no secret material—only the ability to place a cookie on a request to the app, which is a realistic condition on many deployments (open redirects, cookie tossing via sibling subdomains, apps that don't set `SameSite=Strict`, etc.).

### Recommendation
Do not use the bare `Session#id` as an unsigned cookie value trusted for lookup. Either (a) sign/HMAC the cookie value with `Context.api_secret_key` and verify it in `SessionUtils.cookie_session_id` before returning it, or (b) store an unguessable, randomly generated session token (e.g., `SecureRandom.uuid`) as the cookie value instead of the deterministic `shop`/`user_id`-derived id, with a server-side mapping to the real session id.

### Proof of Concept
1. Determine a victim's shop domain, e.g. `victim-shop.myshopify.com` (public knowledge / storefront URL).
2. As any unprivileged user, send a request to the vulnerable app with `Cookie: shopify_app_session=offline_victim-shop.myshopify.com` (achievable if the app's cookie-setting can be manipulated by the attacker's own browser, or via a cookie-tossing/subdomain vector against the app's cookie scope).
3. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `cookie_session_id(cookies)` → `"offline_victim-shop.myshopify.com"` verbatim, with no signature check: [6](#0-5) 
4. The host application looks up `"offline_victim-shop.myshopify.com"` in its session store (as instructed by this library's documented pattern) and retrieves the victim shop's real `Session` (including its access token), which the attacker's request then uses.
