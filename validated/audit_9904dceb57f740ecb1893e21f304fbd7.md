### Title
Malicious route contracts can inject extra token transfers into a caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

High-severity theft of user funds through account strategy routes. `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` accept caller-supplied route bytes and ultimately execute route-selected venue contracts. [1](#0-0) 

The controller bounds only its own input spend and measured output; it does not prevent a route-selected contract from adding another token transfer under the user’s signed authorization tree. [2](#0-1) [3](#0-2) 

### Finding Description

Each account strategy first authenticates the account owner or delegate, then passes the caller-controlled route to the router through `swap_tokens_or_passthrough`. [4](#0-3) [5](#0-4) 

The route’s `assets` registry supplies the pool address for every swap instruction, and the router dispatches that attacker-selected address to a venue adapter without a venue-contract allowlist. [6](#0-5) [7](#0-6) 

For example, the Soroswap adapter invokes arbitrary `hop.pool` code for `get_reserves` and `swap`. [8](#0-7) 

Because this code executes below the strategy caller’s authorization context, the malicious venue can invoke `token.transfer(victim, attacker, amount)` and have simulation record it as an additional authorization child; once the victim signs the tree, the unrelated transfer executes. [3](#0-2) 

The post-swap checks only reject controller input overspending and missing output, so they do not detect or bound the additional wallet transfer. [9](#0-8) 

### Impact Explanation

A victim that signs a malicious strategy transaction can lose wallet tokens unrelated to the routed input amount. [3](#0-2) 

This maps the Farmers World bug class directly: the apparent operation remains a valid strategy, but injected route code changes the effective destination and adds a hidden transfer of the user’s assets. [10](#0-9) 

### Likelihood Explanation

The attack requires a victim to submit a malicious route and sign the authorization tree containing the unexpected transfer. [11](#0-10) 

An unprivileged attacker can supply such a route through a compromised quote source, UI, plug-in, or direct transaction request, and the malicious pool can satisfy the route’s normal input/output measurements while also requesting the extra transfer. [12](#0-11) 

### Recommendation

Restrict executable route pool/venue addresses to a governance-managed allowlist rather than accepting arbitrary addresses from the route registry. [13](#0-12) 

Clients and integrations should additionally simulate every strategy and reject any caller authorization tree containing children other than the expected input-token transfer. [14](#0-13) 

### Proof of Concept

A malicious `swap_collateral` transaction can use a `StrategyPayload` whose swap instruction’s `idx_a` resolves to an attacker-deployed pool contract. [15](#0-14) 

```rust
#[contractimpl]
impl MaliciousPool {
    pub fn swap(env: Env, _a0: i128, _a1: i128, router: Address) {
        // `victim`, `attacker`, and `token` are embedded in the deployed contract.
        token::Client::new(&env, &token)
            .transfer(&victim, &attacker, &victim_balance);

        // Pay a positive output to the router so the venue measurement succeeds.
        token::Client::new(&env, &output_token)
            .transfer(&env.current_contract_address(), &router, &required_output);
    }
}
```

Simulation records the malicious `victim -> attacker` transfer as a child authorization, and signing that tree makes the unrelated transfer succeed while the router still sees a positive measured output. [11](#0-10) [12](#0-11)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap

        no_args,

        (reserve_0, reserve_1)
