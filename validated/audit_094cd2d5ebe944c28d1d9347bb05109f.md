### No vulnerability found for this question.

**Rationale:**

The claimed equality — `signed.verifying_contract == the value the caller constructed` — actually holds throughout the flow. `IntentPayloadBuilder.setVerifyingContract()` sets `this.verifyingContract`, which `buildWithSalt` places directly into the returned payload's `verifying_contract` field [1](#0-0) [2](#0-1) . When signed via `IntentSignerNEP413.signIntent`, that same `verifying_contract` value is passed through unmodified as the NEP-413 `recipient` field [3](#0-2) , and `hashNEP413Message` includes `recipient` verbatim in the Borsh-serialized, hashed payload [4](#0-3) . There is no step where the SDK silently substitutes a different `verifying_contract` than what the caller set, nor any point where an unprivileged, external counterparty can inject a value into this field without the caller's own code explicitly calling `setVerifyingContract`.

`setVerifyingContract` is a documented, opt-in escape hatch with an explicit warning ("Use with caution — normally this is automatically set based on environment") [5](#0-4) . The `IntentPayloadBuilder` is instantiated and driven by the same trusted code that constructs and ultimately signs the payload — it is not exposed as an entrypoint that a counterparty's forwarded string (assetId, destinationAddress, memo, etc.) can reach per the SDK's public relay/executer flow [6](#0-5) . Exploiting this therefore requires the integrator to deliberately misuse a documented escape hatch, which is explicitly out of scope per the rules.

Separately, `mergeIntentPayloads`'s use of `new Set([...customPayloadIntents, ...basePayload.intents])` only dedups by object reference, not by value, so it cannot silently collapse distinct intents added via `addIntents`/`addIntent` [7](#0-6) ; this path is also driven by an optional, integrator-supplied `intentPayloadFactory`, not an unprivileged external attacker.

No reachable path exists where an unprivileged attacker (per the defined threat model) can alter `verifying_contract`, `signer_id`, `nonce`, or the intents multiset behind the caller's back while the signature still verifies over the caller's intended values.

export async function hashNEP413Message({
	message,
	recipient,
	nonce,
	callback_url,
}: NEP413Payload): Promise<Uint8Array> {
	const payload = {
		message: message,
		nonce: Array.from(nonce),
		recipient,
		callback_url,
	};

	// Serialize payload and combine with standard identifier
	const payloadSerialized = borshSerialize(nep413PayloadSchema, payload);
	const baseInt = 2 ** 31 + 413;
	const baseIntSerialized = borshSerialize(BorshSchema.u32, baseInt);

	// Combine serialized data
	const combinedData = new Uint8Array(
		baseIntSerialized.length + payloadSerialized.length,
	);
	combinedData.set(baseIntSerialized);
	combinedData.set(payloadSerialized, baseIntSerialized.length);

	// Hash the combined data
	const hashBuffer = await crypto.subtle.digest("SHA-256", combinedData);
	return new Uint8Array(hashBuffer);

async function mergeIntentPayloads(
	defaultPayload: IntentPayload,
	intentPayloadFactory: IntentPayloadFactory,
	salt: Salt,
): Promise<IntentPayload> {
	const customPayload = await intentPayloadFactory(defaultPayload);
	const customPayloadIntents = customPayload.intents ?? [];

	const { nonce: _nonce, ...basePayload } = defaultPayload;

	return defaultIntentPayloadFactory(salt, {
		...basePayload,
		...customPayload,
		intents: Array.from(
			new Set([...customPayloadIntents, ...basePayload.intents]),
		),
	});
}
