### Title
Emporium Min-flow (`tokenNumber == 0`) proof path lets CASE 2 ops move tokens into Emporium/Hinkal with no balance check and no minted UTXO, permanently orphaning the funds - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which pairs with the registered `MainEVMCircuitMin` verifier (only 3 public signals) instead of `MainEVMCircuit`. Because `dimensions.tokenNumber == 0` is accepted by `dimensionsCheck`, the entire balance-accounting machinery in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` operates on an empty `erc20TokenAddresses` array, so any value moved by a CASE 2 (stateless) `EmporiumOperation` is neither checked nor minted into a UTXO.

### Finding Description
The claimed equality that should hold is: `net tokens entering Hinkal/Emporium == Σ amountChanges + Σ UTXO amounts`. The attacker can make the left side positive while forcing the right side to be provably zero.

Path:
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks(circomData, dimensions, msg.sender)` [1](#0-0) , which calls `dimensionsCheck` [2](#0-1) . This only requires `circomData.erc20TokenAddresses.length == dimensions.tokenNumber`; `tokenNumber == 0` is a legal value, nothing forbids it for the Emporium action.
2. `CircomDataBuilder.formInputForCircom` detects `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` and returns only 3 public inputs via `formInputEmporiumMin` [3](#0-2) , matching `MainEVMCircuitMin`, which only constrains `outTimeStamp`, `calldataHash`, and derives `message` from a private `messageSeed` [4](#0-3) . This circuit contains **no** `amountChanges`, no `inTotal + amountChanges === outTotal`, and no `erc20TokenAddresses` distinctness/inclusion checks at all — those live only in `MainEVMCircuit` [5](#0-4) , which is not used on this path.
3. Back in `Hinkal.transact`, both the pre/post balance snapshot loop and the slippage/UTXO-accounting loop iterate `circomData.erc20TokenAddresses`, which is empty, so they execute zero iterations [6](#0-5) .
4. `_externalTransact` calls `EmporiumUpgradeable.runAction(circomData, deltaAmountChanges)` with `deltaAmountChanges` also sized to `erc20TokenAddresses.length == 0` [7](#0-6) .
5. Inside `runAction`, `balancesBefore`/`balancesAfter` are computed via `getBalancesForArray(circomData.erc20TokenAddresses)` — an empty array — and the entire CASE 1/CASE 2 op-execution loop runs unconstrained by any of that [8](#0-7) . A CASE 2 op (`op.invokeWallet == false` or `stack.signerAddress == address(0)`) executes an arbitrary `op.endpoint.call{value: op.value}(op.callData)` [9](#0-8) . The attacker crafts `op.callData` as `token.transfer(emporium, amount)` from an ERC20 the attacker controls balance of (or any contract that pushes value to the Emporium), moving real value into the Emporium/Hinkal system.
6. The trailing loop `for (i = 0; i < circomData.erc20TokenAddresses.length; i++) { ... handleOut ... }` never executes because the length is 0 [10](#0-9) , so `utxoSet` is empty and `handleOut` (which would call `transferERC20TokenOrETH` and mint the `UTXO`) is never reached [11](#0-10) .
7. Back at `Hinkal.transact`, the `for (i; i < circomData.erc20TokenAddresses.length)` slippage/balance-diff loop that would insert `OnChainCommitment`s and require `balanceDif == amountChanges[i] + utxoAmount` also runs zero times, so no `require` fires and nothing is minted/committed [12](#0-11) .

Net effect: real ERC20/ETH value lands in the Emporium (and can be routed further into Hinkal or simply left there, or `transferERC20TokenOrETH` from the op's callData could target Hinkal directly), while zero UTXOs are created and zero on-chain commitments recorded and no `require` in the entire call chain observes or blocks this, because every guard that exists (`dimensionsCheck`, the Min-circuit's own constraints, `Hinkal.transact`'s balance loop, `EmporiumUpgradeable.runAction`'s balance loop) is keyed off `erc20TokenAddresses`, which is deliberately empty for this path.

### Impact Explanation
Value can enter the protocol's custody (Emporium/Hinkal) through a CASE 2 op triggered under a "Min" proof, with no corresponding UTXO minted to represent it and no revert anywhere in the chain. This is a permanent freeze/orphaning of funds: the tokens are stuck in the Emporium (or Hinkal) with no leaf/commitment referencing them, so no future proof can ever spend them — matching the "Critical: permanent freezing of user funds" category. It is repeatable for every Min-flow transaction the attacker crafts, and does not require any privileged role: the attacker only needs to be `onlyAllowedRecipient` caller path via `Hinkal.transact` (any unprivileged EOA can call `transact`), self-supply valid EDDSA/signature material for the trivial 3-input Min circuit, and control the `EmporiumStack`/`op.callData` fields, all of which are attacker-controlled per the stated threat model.

### Likelihood Explanation
Preconditions are modest: the attacker needs (a) `MainEVMCircuitMin`'s verifier registered under the `verifierId` computed from `(tokenNumber=0, nullifierAmount, outputAmount, HINKAL_EMPORIUM_ACTION_ID)` — this is asserted to exist per the repo's intended "Min flow" design (`CircomDataBuilder.formInputForCircom`'s explicit branch), and (b) the ability to encode an `EmporiumStack` with at least one CASE 2 op whose `endpoint`/`callData` moves tokens into Emporium/Hinkal. Both are fully within the stated attacker capability (craft every field of `CircomData`, deploy contracts, self-generate proofs). Generating the Min circuit's proof is trivial since it only requires knowledge of `messageSeed` and no merkle/nullifier witnesses. This makes the attack cheap, deterministic and repeatable per transaction.

### Recommendation
Do not decouple the CASE 2 execution loop in `EmporiumUpgradeable.runAction` from balance accounting based on `circomData.erc20TokenAddresses`. Either (a) forbid the Min-flow (`tokenNumber == 0`) path from allowing any CASE 2 op that can move ERC20/ETH value (e.g., require `stack.ops` to only contain calls that provably cannot change any token balance when `erc20TokenAddresses.length == 0`), or (b) remove the Min-flow optimization for the Emporium action entirely and always route through `MainEVMCircuit`/`formInputNormal` so that `erc20TokenAddresses` must enumerate every token touched by every op, with `distinctErc20AddressChecks` and `inTotal + amountChanges === outTotal` enforcing correctness, and additionally add an explicit on-chain check (independent of the circuit) that all tokens actually transferred during `runAction`'s op loop are present in `circomData.erc20TokenAddresses` (e.g., snapshot/compare balances of a superset of addresses reachable from `op.endpoint`, or restrict CASE 2 `op.endpoint` targets to an allowlist that cannot move Emporium-held assets).

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges
    ) external override onlyAllowedRecipient returns (UTXO[] memory) {
        EmporiumStack memory stack = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (EmporiumStack)
        );

        uint256[] memory balancesBefore = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);
            }
            // CASE 2: Stateless Interaction
            else {
                bytes4 selector = bytes4(op.callData);
                if (
                    selector == IHinkalWallet.callHinkalWallet.selector ||
                    selector == IHinkalWallet.doSendToRelay.selector
                ) {
                    revert UnauthorizedWalletCall();
                }

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
            }

            if (!success) {
                revert CallFailed(err);
            }
        }

        payRelayFees(circomData, stack.signerAddress, deltaAmountChanges);

        uint256[] memory balancesAfter = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        UTXO[] memory utxoSet = new UTXO[](
            circomData.erc20TokenAddresses.length
        );

        uint256 utxoSetLength;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 balanceChange = int256(balancesAfter[i]) -
                int256(balancesBefore[i]);

            if (deltaAmountChanges[i] < 0) {
                balanceChange -= deltaAmountChanges[i];
                // this equation reads: total change of emporium balance = what was moved to emporium (-deltaAmountChange) + how emporium balance changed through tx (balanceChange)
            }

            // the only case when balanceChange can be < 0, when there were some funds on emporium before the call
            if (balanceChange < 0) {
                revert BalanceChangeShouldBePositive();
            }

            UTXO memory utxoOut = handleOut(balanceChange, circomData, i);

            if (utxoOut.amount > 0) {
                utxoSet[utxoSetLength++] = utxoOut;
            }
        }

        if (utxoSetLength < circomData.erc20TokenAddresses.length) {
            utxoSet.skipLast(
                circomData.erc20TokenAddresses.length - utxoSetLength
            );
        }

        return utxoSet;
    }
