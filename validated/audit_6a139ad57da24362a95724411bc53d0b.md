### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop-domain` header — which the gem treats as the authoritative tenant identifier and hands to the app's webhook handler — is never included in that signed payload. Any party capable of obtaining one valid `(body, hmac)` pair from the app (e.g. by installing the app on their own free/dev store and capturing a legitimately delivered webhook) can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The signature still validates because it never covered the shop, so the handler processes the payload as if it originated from a different (victim) tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is completely independent of the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` performs an `OpenSSL.secure_compare` of the computed HMAC against `verifiable_query.hmac`, using `verifiable_query.to_signable_string` (i.e. body-only) as the signed content: [3](#0-2) 

`Registry.process` gates entirely on this HMAC check and then forwards `request.shop` — taken from the unauthenticated header — directly into `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity-binding equality this breaks is:
`shop_that_HMAC_actually_authenticates (∅, since HMAC covers only raw_body)` ≠ `shop_used_as_tenant_key (request.shop, read from an unsigned header)`.

Because the HMAC secret is the app's shared `api_secret_key`, it is identical for every shop that installs the app. An attacker who installs the app on their own store receives genuinely-signed webhooks (valid `body` + `hmac` pair) from Shopify. They can then send an HTTP POST directly to the app's webhook endpoint with that same `body`/`hmac`, but with the `shopify-shop-domain` header changed to any victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will invoke the handler with `shop: <victim-shop>`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing — a form of cross-tenant access: the handler for a specific host app will act on behalf of a shop the attacker does not control, using data the attacker fully controls (topic and body are attacker-selected, since the attacker chooses which of their own store's webhook events to capture and replay, e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, or business-logic topics that key state changes by `shop`). Depending on how the host application uses `WebhookMetadata#shop` (most apps key billing state, uninstall cleanup, GDPR redaction, or entitlement changes directly off this value), this can cause data loss, incorrect billing/entitlement changes, or corruption of another merchant's tenant record — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires no privileged credentials, no leaked secrets, and no access to the victim's environment: any unprivileged internet user can install the target app on a free development store, capture one legitimately signed webhook delivery (body + `X-Shopify-Hmac-Sha256`), and replay it to the app's public webhook endpoint with a forged `shop-domain` header. This is fully within reach of an "unprivileged internet user" per the scope of this assessment.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind the `shop-domain` header to the signed payload before trusting it as the tenant identifier — e.g., verify the header value against a shop already known/authorized for that specific request, and never let `WebhookMetadata#shop` be derived purely from an unauthenticated header.

### Proof of Concept
1. Attacker installs the target app on `attacker-store.myshopify.com` (any public app install is unprivileged).
2. Attacker triggers a webhook-generating action in their own store (e.g. update a product) and captures the raw POST from Shopify to the app's webhook endpoint, including headers `x-shopify-hmac-sha256: <HMAC>` and body `<BODY>`.
3. Attacker sends their own POST to the same webhook endpoint:
   ```
   POST /webhooks HTTP/1.1
   x-shopify-topic: products/update
   x-shopify-hmac-sha256: <HMAC>              # unchanged, still valid for <BODY>
   x-shopify-shop-domain: victim-store.myshopify.com   # forged
   x-shopify-webhook-id: <any>
   x-shopify-api-version: <any>

   <BODY>                                     # unchanged
   ```
4. `Utils::HmacValidator.validate` (via `verifiable_query.to_signable_string` = `<BODY>`) succeeds because the signature only ever covered `<BODY>`, which is unmodified. [5](#0-4) 
5. `Registry.process` calls the app's handler with `shop: "victim-store.myshopify.com"` even though the payload actually originated from the attacker's own store. [6](#0-5)
