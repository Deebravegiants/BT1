### Title
Webhook `shop` (tenant) identity is read from an unauthenticated header, not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body [1](#0-0) , while the `shop` (and `topic`/`api_version`/`webhook_id`) values used to attribute the webhook to a tenant are read straight from request headers that are never included in the signed payload [2](#0-1) . `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only and then forwards `request.shop` (the unauthenticated header) directly to the host application's handler as the tenant identity [3](#0-2) .

### Finding Description
The binding that should hold is: `shop-used-for-tenant-attribution == shop-that-the-HMAC-actually-authenticates`. In this gem that equality is broken:

- `HmacValidator.validate(request)` computes `HMAC(secret, request.to_signable_string)` and compares it to the `hmac` header [4](#0-3) .
- `to_signable_string` for a webhook `Request` returns only `@raw_body` [1](#0-0) .
- `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers (`shopify-shop-domain`, etc.) that are outside the signed bytes [5](#0-4) .
- `Registry.process` only checks that the body's HMAC is valid, then constructs `WebhookMetadata` using the header-derived `shop` and hands it to the app's handler [6](#0-5) .

Because the `shop` header is not part of what is cryptographically verified, anyone capable of producing (or replaying) one (body, hmac) pair that is valid for the app's secret — which happens naturally for every legitimate webhook a merchant's shop actually receives from Shopify — can resubmit that exact body/hmac pair to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header value. The gem will report the HMAC as valid and hand the handler a `WebhookMetadata` whose `shop` field does not match the shop that the payload's HMAC actually vouches for.

### Impact Explanation
This breaks the tenant boundary the whole webhook system is supposed to enforce: `request.shop` is documented and used by consuming apps as the tenant/shop identity for routing the payload's data (e.g., which merchant's local DB record to update) [7](#0-6) . An attacker who owns a shop that legitimately receives HTTP webhooks from Shopify for their own store can capture one valid `(raw_body, hmac)` pair, then replay it against the app's webhook endpoint with a forged `shopify-shop-domain` header pointing at a victim shop. The gem accepts the request as authentic and reports the forged shop to the handler, enabling cross-tenant data confusion/corruption in any host application that trusts `WebhookMetadata#shop` as returned by this gem (which is the intended usage pattern shown in the gem's own docs).

### Likelihood Explanation
Medium-High. No secret key, access token, or privileged credential is needed — only ordinary receipt of one legitimate webhook for a shop the attacker controls (a normal, unprivileged capability of any merchant using an app), plus the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers, which by design is unauthenticated/public.

### Recommendation
Bind the tenant-identifying fields into the signed payload verification: derive `shop` (and ideally `topic`/`webhook_id`) from data verified against Shopify's HMAC (e.g., include shop/topic in the canonical string used for signature verification, or cross-check the header-provided shop against a shop already bound to the specific `webhook_id`/subscription on record) rather than trusting the raw header value returned unconditionally by `ShopifyAPI::Webhooks::Request#shop`.

### Proof of Concept
1. App using this gem registers HTTP webhooks and implements a handler trusting `data.shop`, per the documented pattern [8](#0-7) .
2. Attacker installs the app on shop `attacker.myshopify.com` and receives one legitimate webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, header `x-shopify-shop-domain = attacker.myshopify.com`.
3. Attacker POSTs the same `raw_body = B` and the same valid `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Request#hmac`/`Request#shop` read from headers [9](#0-8) ; `HmacValidator.validate` succeeds because it only checks `B` against the secret [4](#0-3) .
5. `Registry.process` calls the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: parsed(B), ...)` [6](#0-5)  — the app now believes attacker-controlled body data belongs to `victim.myshopify.com`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
