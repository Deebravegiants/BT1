This confirms the design: `Registry.process` claims to "verify the request did indeed come from Shopify" via `Utils::HmacValidator.validate(request)`, then trusts `request.shop` and `request.topic` (sourced purely from HTTP headers) as authenticated tenant/topic identifiers when building `WebhookMetadata`, which the host app is documented to use for tenant dispatch (`data.shop`, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`).### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook attribution spoofing - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a successful HMAC check as proof that the *entire request*, including the `shop` and `topic` identity fields, is authentic and safe to hand to the app's handler. In reality, the HMAC only ever covers the raw request body; the `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for `ShopifyAPI::Webhooks::Request` that method returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` runs the HMAC check and then immediately trusts these header-derived fields to build `WebhookMetadata`, which is handed to the app's handler as if it were verified tenant/topic identity: [3](#0-2) 

`WebhookMetadata.shop` and `.topic` are exactly the fields the documented handler contract expects apps to trust for tenant dispatch (e.g. `shop_domain: data.shop`): [4](#0-3) 

This is the same bug class as the reported Bitcoin issue: a signature (HMAC / sighash) is computed over an incomplete data set, then code downstream trusts fields outside that set as if they were bound by the signature. The identity binding that should hold — `hmac_signed_bytes == authenticated_request_bytes` — is broken because `hmac_signed_bytes` covers only the body while `shop`/`topic` are separately, unauthenticated, request-controlled.

### Impact Explanation
Any actor able to produce one genuinely-signed webhook body for the app's `client_secret` (e.g. a merchant who has installed the app and receives real Shopify webhooks for their own shop, or anyone who otherwise obtains one valid `(body, hmac)` pair for this app) can replay that exact body/HMAC pair while substituting the `shop-domain`/`topic` headers to any value. `Registry.process` will accept it as a valid webhook and dispatch it to the handler labeled as coming from an arbitrary other shop and/or topic. Because host apps are documented to trust `data.shop`/`data.topic` for per-tenant routing (job enqueue with `shop_domain: data.shop`), this enables cross-tenant data confusion/injection into another merchant's processing pipeline — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation still requires possession of at least one legitimately-signed `(body, hmac)` pair, which in practice is obtainable by any merchant/tenant who has installed the app (they legitimately receive real webhooks signed with the app's shared `client_secret`, since Shopify webhook HMACs are not shop-specific — they use the single app secret for all shops). That makes this reachable by a low-privileged, unprivileged tenant against other tenants of the same app, without needing the raw `client_secret` itself.

### Recommendation
Do not treat `shop`, `topic`, `webhook_id`, or `api_version` header values as authenticated identity once HMAC validation passes. At minimum, the library should document/enforce that host applications must independently verify `request.shop` corresponds to a shop with an active session/installation before trusting `WebhookMetadata.shop`/`topic` for tenant-sensitive logic, and consider binding the shop domain into the signable string check where feasible.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, headers include `x-shopify-hmac-sha256: H` (valid, since HMAC is computed with the single shared `client_secret`), `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker POSTs the same body `B` and same `H` to the app's webhook endpoint again, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`, per `to_signable_string` returning `@raw_body`.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: request.topic, ...)` and invokes the registered handler, which processes attacker-controlled data attributed to the victim shop.
