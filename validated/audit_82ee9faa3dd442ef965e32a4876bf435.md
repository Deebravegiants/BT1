### Title
`EvmHost::dispatch` / `fundRequest` overcharge native-token payers when swapping ETH for the exact fee amount, with no refund of the Uniswap-refunded dust - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept native-token payment and forward the *entire* `msg.value` to `IUniswapV2Router02.swapETHForExactTokens`, but never account for or return the ETH that the router refunds when `msg.value` exceeds what's needed to buy the exact fee amount.

### Finding Description
In all three payable entry points, the full `msg.value` is sent to the router: [1](#0-0) 

```
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } ...
```

The same pattern repeats for the GET-dispatch path and for `fundRequest`: [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` on a standard Uniswap V2 router refunds any unspent ETH (i.e. `msg.value - amounts[0]`) to its `msg.sender`, which in this call is `EvmHost` itself (`address(this)`), *not* the original caller (`_msgSender()`). None of these three functions capture the `amounts` return value or forward any leftover ETH back to the caller — unlike the sibling contract `IntentGatewayV2.placeOrder`, which correctly captures `amounts[0]` and refunds the delta to `msg.sender`: [4](#0-3) 

```
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
```

`EvmHost.dispatch`/`fundRequest` omit this refund step entirely. Any caller — including bridge aggregators, adapters, or `HyperApp`-based apps that pass a generous `msg.value` buffer to guarantee enough ETH for the swap (as explicitly recommended in `HyperbridgeLzEndpoint.quote`, which doubles the fee to "absorb" swap slippage) — permanently loses the unspent ETH into the `EvmHost` contract with no mechanism visible in this file to return it. [5](#0-4) 

This is the same bug class as the reported `AvailBridge::sendMessage` issue: a fee-charging dispatch function silently retains any `msg.value` above what is actually required, rather than validating exact payment or refunding the excess to the caller.

### Impact Explanation
Any unprivileged caller dispatching a POST/GET request or funding a pending request with native token payment and providing `msg.value` above the exact Uniswap-quoted input will have the excess ETH trapped in `EvmHost`, with no code path in `EvmHost.sol` shown to return it to the original sender. Since slippage/price movement between quote and execution is expected, and since integrators are encouraged to over-provision `msg.value` to avoid reverts (see the LZ endpoint's 2x buffer), this is a realistic, recurring occurrence rather than an edge case — resulting in a systemic loss of user/integrator funds on every native-token dispatch that doesn't send the exact minimal amount.

### Likelihood Explanation
High: this occurs on the default/most convenient integration path (paying in native token) for `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, which are the primary externally reachable entry points used by relayers, apps, and adapters building on Hyperbridge. No special conditions are needed beyond sending `msg.value` slightly higher than the exact Uniswap input amount, which is standard practice to avoid revert due to price movement.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, and refund `msg.value - amounts[0]` back to `_msgSender()` (or `payer`), mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch(DispatchPost)` with `post.fee = 100` (feeToken units) and sends `msg.value = 2 ETH` (a generous buffer to cover a Uniswap quote of ~1 ETH, matching the pattern the SDK's `HyperbridgeLzEndpoint.quote` explicitly recommends).
2. `swapETHForExactTokens{value: 2 ether}(100, path, address(this), block.timestamp)` executes, spending only ~1 ETH and refunding the remaining ~1 ETH to `msg.sender` of the router call, i.e. `EvmHost`.
3. `dispatch` returns; `EvmHost`'s ETH balance increases by ~1 ETH, and the caller never receives it back — no refund logic exists in the function.
4. Repeated across many callers, this ETH accumulates in `EvmHost` with no caller-facing recovery mechanism evident in `EvmHost.sol`, causing an overcharge/fund loss to each caller equal to their unspent buffer.
