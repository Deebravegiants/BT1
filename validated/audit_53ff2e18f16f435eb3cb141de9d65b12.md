### Title
Hardcoded `1e12` decimal-scaling factor in `Zap._sellInternal`'s min-amount check assumes real USDC always has 6 decimals - ([File: packages/contracts/src/Zap.sol])

### Summary
`Zap._sellInternal` computes a gross USDC value estimate in 18-decimal-precision "USD" units (`ltReceived * exchangeRate() / 1e18`, where `exchangeRate()` is documented as "USDC per LT unit, 18-dp") and then converts it to the real USDC token's raw units by dividing by a hardcoded `1e12` factor, in order to compare it against `minUsdcAmount()` (BounceTech's live floor, denominated in the real USDC token's native decimals) [1](#0-0) . This exactly mirrors the reported bug class: a fixed decimal conversion constant baked into arithmetic that is only correct for one specific token decimal configuration (here, USDC = 6 decimals), analogous to the reported `1e18` constant in `collateralFactor()` that silently breaks for non-18-decimal collateral like WBTC.

### Finding Description
`minUsdcAmount()` reads BounceTech's live `minTransactionSize()` floor, denominated in the real USDC token's native units [2](#0-1) . The protocol's own test-suite/deploy comments confirm this is intentionally the *real, on-chain* USDC token, which is expected to use 6 decimals in production, while the mock USDC used in tests deliberately uses 18 decimals (OZ default) purely for test convenience [3](#0-2) .

`grossUsdcEstimate` in `_sellInternal` is computed from `ltReceived * exchangeRate() / 1e18` — always an 18-decimal-precision "USD value," independent of the actual `usdc` token's decimals — and then the code does `grossUsdcEstimate / 1e12` to rescale it down to what it assumes is a 6-decimal USDC representation before comparing to `minUsdcAmount()` [1](#0-0) . This `1e12` scaling factor (`= 10**(18-6)`) is correct only if the deployed `usdc` token has exactly 6 decimals. It is never derived from `IERC20Metadata(address(usdc)).decimals()` anywhere in `Zap.sol` — it is a bare literal. If `Zap` is ever deployed against a different stablecoin/base asset with a different decimal count (e.g. DAI with 18 decimals, or any other ERC-20 accepted as the base asset), this comparison silently miscalculates by many orders of magnitude, exactly like the audit report's `collateralFactor()` mis-scaling for WBTC's 8 decimals vs. the hardcoded `1e18`.

### Impact Explanation
If `usdc` decimals differ from 6:
- With an 18-decimal base asset, `grossUsdcEstimate / 1e12` shrinks the true 18-decimal gross amount by 1e12x too much, so the `BelowMinAmount` guard will almost always revert — a persistent, protocol-wide sell-side DoS that freezes seller funds' exit path via `Zap.sell` (they'd still be able to sell only in comically oversized batches, if at all, since the check compares against a floor that no realistic trade can clear once mis-scaled).
- With a base asset of >18 decimals or oddly configured decimals, the check could instead be trivially satisfied when it shouldn't be, letting sub-floor trades slip past the guard meant to prevent BounceTech's `redeem()` revert with the undecodable `0x05eb05ac` selector, causing sell transactions to revert deep inside `redeem()` in a way the contract explicitly tries to avoid.

This is a real freezing/availability issue on the sell path for any token/deployment where the base asset diverges from the 6-decimal assumption baked into this one literal.

### Likelihood Explanation
This is reachable by any unprivileged trader simply calling `Zap.sell`/`sellPermit` — no privileged role needed. Likelihood of it manifesting depends entirely on the deployed base-asset token's decimals matching the hardcoded assumption; since the codebase's own test mocks intentionally use 18-decimal USDC (differing from the assumed 6 decimals) to catch exactly this class of bug pattern, and comments elsewhere explicitly flag "real USDC (6dp)" vs. "mock USDC (18dp) in tests" as a known divergence, the risk of decimal mismatch at deployment time or via a future base-asset change is concrete and directly analogous to the reported class.

### Recommendation
Derive the scaling factor dynamically from the actual `usdc` token's decimals (e.g., cache `usdcDecimals` at `initialize()` via `IERC20Metadata(address(usdc)).decimals()`, or compute `10 ** (18 - usdcDecimals)` at runtime) rather than hardcoding `1e12`, mirroring the audit's recommendation to use the correct decimal factor for the specific token in question instead of an assumed constant.

### Proof of Concept
Conceptual walkthrough (cannot be executed without deploying with a non-6-decimal base asset, which the current test suite deliberately avoids by using 18-decimal mock USDC and never exercising this exact comparison against a live 6-decimal-consistent floor at scale):
1. Deploy `Zap` with a base asset token that has 18 decimals (e.g. DAI) instead of the assumed 6-decimal USDC.
2. `minUsdcAmount()` returns BounceTech's floor in the base asset's native 18-decimal units, e.g. `10e18`.
3. A trader sells tokens worth (in real terms) well above the $10 floor; `exchangeRate()` returns an 18-dp rate, so `grossUsdcEstimate` is computed correctly in 18-dp terms, e.g. `50e18`.
4. `Zap` divides by the hardcoded `1e12`: `50e18 / 1e12 = 50e6`, which is compared against `minUsdcAmount() = 10e18`. `50e6 < 10e18` is true, so the sell reverts with `BelowMinAmount` even though the trade is 5x over the real floor — a false-positive DoS baked into the hardcoded conversion factor [1](#0-0) .
