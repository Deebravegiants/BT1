Based on my research, the strongest analog I found in this codebase to the "unvalidated user input" bug class described in the report is in `pallet-hyper-fungible-token`'s handling of the cross-chain `Message.from` field when dispatching optional calldata, though I was not able to fully verify the EVM-side sender-authorization before running out of investigation budget. I present it below with that caveat noted explicitly.

### Title
Cross-chain calldata dispatch trusts an unauthenticated `Message.from` field as dispatch origin - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` decodes the ABI-encoded `Message` body of an incoming ISMP post request and, when the optional `call_data` carries no `MultiSignature`, derives the dispatch origin directly from the `message.from` bytes inside that same attacker-influenced payload, rather than from anything independently authenticated on the destination chain.

### Finding Description
`on_accept` authenticates only that the *request*'s `source`/`from` pair (the ISMP `PostRequest.from`, i.e. the registered bridge contract address) maps to a known asset via `ContractToAsset::get(source, &from)` [1](#0-0) . This confirms the *contract* is the legitimate bridge contract for that chain — it says nothing about the end-user identity carried inside the ABI-decoded `Message` body.

When `message.data` is non-empty, the pallet decodes an optional `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` [2](#0-1) . If `signature` is `Some`, the origin is verified cryptographically. If `signature` is `None`, the pallet instead falls back to deriving the origin straight from the `message.from` bytes that were carried inside the cross-chain body — converting them to an EVM address (taking the last 20 bytes) or a 32-byte Substrate `AccountId` and using that as the dispatch origin, with no cryptographic check that this value actually corresponds to any real signer: [3](#0-2) 

The runtime call is then dispatched as this unauthenticated origin (subject only to `BaseCallFilter`): [4](#0-3) 

Per the protocol docs, this field is *documented* as existing only "for timeout refunds" [5](#0-4) , yet it is repurposed here as an implicit authorization credential for arbitrary runtime-call execution. The docs state the intent is that "the origin is derived from the sender address in the cross-chain message" [6](#0-5) , i.e. the safety of this path is entirely dependent on the source-chain contract enforcing `message.from == msg.sender` when constructing the outgoing message and never allowing a caller to set an arbitrary `from`.

**I was unable to confirm within the available tool budget** whether the EVM-side `send()`/`_buildDispatchPost` path in `HyperFungibleToken.sol`/`HyperFungibleTokenUpgradeable.sol` strictly hardcodes `from = msg.sender`, or whether `from` (or an equivalent field feeding into the encoded `Message`) is caller-suppliable. If it is caller-suppliable (or if any other integrated source-chain sender of this message format allows it), an attacker could dispatch arbitrary allowed runtime calls (e.g. `Balances::transfer`, asset approvals, etc.) as any account whose EVM/Substrate address they choose to name in `from`, with no signature at all — i.e. impersonating any account for privileged dispatch. This would be a direct fund-theft/unauthorized-app-action vector, matching the external report's bug class ("input parsed and trusted without validation") almost exactly, since it is a message field with a narrower documented purpose (refunds) being reused, unchecked, as an authorization primitive.

### Impact Explanation
If the source-chain contract does not strictly bind `from` to the actual transaction sender, this allows unauthorized dispatch of arbitrary allowed runtime calls under an arbitrary victim's account identity, which can directly result in theft of funds (e.g., draining balances, approving allowances) — a Critical/High-severity, concrete-theft outcome. If the source-chain binding is in fact airtight (which I could not verify), the destination-side design is still fragile: it makes fund safety on Polkadot side wholly dependent on an unenforced invariant in a *different* codebase (the EVM app contracts) with no defense-in-depth check on the receiving pallet.

### Likelihood Explanation
Likelihood is contingent and unverified. It requires either (a) a caller-controllable `from`/sender parameter on any integrated source-chain sender contract, or (b) a bug/future change in that contract that relaxes the sender-binding invariant the pallet silently depends on. Given I could not confirm the EVM-side enforcement, I flag this as **plausible but unconfirmed** rather than proven.

### Recommendation
- Do not derive dispatch authority from any field decoded out of the cross-chain `Message` body without an explicit, destination-side cryptographic check (i.e. require `signature` to always be present for any calldata execution, or independently re-derive/verify that `from` matches the actual PostRequest sender via a dedicated, source-enforced field rather than a body field documented for a different purpose).
- Audit `HyperFungibleToken.sol` / `HyperFungibleTokenUpgradeable.sol` (and any other integrated sender) to confirm `from` is hard-set to `msg.sender` and cannot be supplied by the caller; add an explicit regression test asserting this.
- Add defense-in-depth on the pallet side: require `SubstrateCalldata.signature` to be mandatory whenever `runtime_call` is non-empty, removing the implicit "no-signature-if-you-are-the-sender" fallback entirely.

### Proof of Concept
Not constructed — a concrete PoC requires confirming whether the EVM sender contract lets a caller set an arbitrary `from` value in the outgoing `Message`; this was not verified within the available investigation budget. The exact vulnerable code paths (`modules/pallets/hyper-fungible-token/src/module.rs:176-202`) are cited above for a reviewer to complete verification against the paired EVM contracts.
