### Title
View-role users can read External Initiator `AccessKey` and `OutgoingToken` via `GET /v2/external_initiators`, enabling job-run request forgery - (File: core/web/router.go)

### Summary
The `/v2/external_initiators` list endpoint is reachable by any authenticated user regardless of role (including the lowest privilege `view` role), yet it returns each external initiator's `AccessKey` and `OutgoingToken` in the response body. This mirrors the Mattermost bug class: a coarse authentication check ("is a logged-in user") is substituted for the fine-grained authorization that should gate access to sensitive invite/credential material.

### Finding Description
The route is registered without any role-gating middleware, unlike sibling mutating routes on the same controller: [1](#0-0) 

Compare to `Create`/`Destroy` on the same controller, which are wrapped in `auth.RequiresEditRole`, while `Index` has no role wrapper at all — only the blanket `authv2` authentication group (`AuthenticateByToken`/`AuthenticateBySession`) applies: [2](#0-1) 

The handler serializes every external initiator including its `AccessKey` and `OutgoingToken`: [3](#0-2) [4](#0-3) 

This is confirmed by the codebase's own RBAC route map, which explicitly marks this endpoint as accessible to `view`-only users (`viewOnlyAllowed: true`): [5](#0-4) 

The `AccessKey` is one half of the credential pair (`AccessKey`/`Secret`) used by `AuthenticateExternalInitiator` to authenticate inbound requests that trigger job runs; the `Secret` itself is hashed and not retrievable, but the plaintext `OutgoingToken` (used by the node to authenticate its own outbound calls to the initiator's URL) is stored and returned in full: [6](#0-5) [7](#0-6) 

Note that requests authenticated via a valid external-initiator credential are automatically granted the `run` role internally: [8](#0-7) 

### Impact Explanation
A user provisioned with only the `view` role — intended to be strictly read-only and non-privileged for triggering actions — can enumerate `AccessKey` and `OutgoingToken` values for every configured external initiator. `AccessKey` is half of the credential material gating the external-initiator authentication path that internally maps to the `run` role (capable of triggering job runs), and `OutgoingToken` is a bearer-style secret meant to let the external system verify calls actually originated from the node; its disclosure enables spoofing of that verification channel. This is a broken access control / credential disclosure issue analogous to the Mattermost CWE-863 finding: a role intended to have minimal privilege gains access to sensitive material an endpoint's underlying resource requires stronger authorization to expose.

### Likelihood Explanation
Likelihood is limited by two factors: (1) exploitation requires the operator to have provisioned a `view`-role local/API user account (unprivileged actors without any account cannot reach `authv2` routes at all — this is not a pre-auth vulnerability), and (2) the `Secret` half of the incoming credential pair is never exposed (only its hash is stored), so full impersonation of inbound initiator authentication is not directly achievable from this leak alone. However, any deployment using multi-role API users (a supported, documented feature) with `view` accounts handed to lower-trust operators or automation would be exposed to `OutgoingToken` disclosure and `AccessKey` reconnaissance.

### Recommendation
Wrap `GET /v2/external_initiators` with at minimum `auth.RequiresEditRole` (or introduce a narrower permission consistent with the sensitivity of credential material, mirroring the `Create`/`Destroy` gating already applied to this controller), and/or strip `AccessKey`/`OutgoingToken` from the list/index presenter, only surfacing them at creation time (as is already done for the one-time `Secret`/`OutgoingSecret` pair in `ExternalInitiatorAuthentication`).

### Proof of Concept
1. Provision a Chainlink node user with role `view` (e.g., via `POST /v2/users` as an admin, or via LDAP/OIDC group mapping to the read/view role).
2. As that `view`-role user, authenticate and call `GET /v2/external_initiators`.
3. Observe response includes `accessKey` and `outgoingToken` fields for every external initiator on the node, per `presenters.ExternalInitiatorResource`: [9](#0-8) 
4. Confirm via the codebase's own RBAC test map that this route is intentionally allowed for `view` role (`viewOnlyAllowed: true`), unlike the mutating routes on the same resource which require `edit`: [10](#0-9)

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
