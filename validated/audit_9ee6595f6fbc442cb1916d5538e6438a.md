### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body only, while the `shop` (shop-domain), `topic`, `api_version`, and `webhook_id` values are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the body and then hands the header-derived `shop` value straight to the app's webhook handler as the tenant identifier, without that value ever being bound to the signature that supposedly proves the request came from Shopify.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the signed material: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, then dispatches `request.shop` (an unauthenticated field) to the handler as the tenant identity: [4](#0-3) 

`Utils::HmacValidator.validate` in turn calls `verifiable_query.to_signable_string`, which for webhooks is only the body — confirming the header fields are never part of the signed input: [5](#0-4) 

The binding the gem should guarantee is: `hmac_verified(body) == true` implies `shop_used_for_tenant_routing == shop_that_body_actually_belongs_to`. Because `shop` is not part of the signed string, this equality does not hold — the HMAC only proves body integrity/authenticity from *some* holder of `api_secret_key` context (i.e., genuinely from Shopify, for *some* shop that has the app installed), but it proves nothing about which shop the body is about. Any entity capable of triggering a legitimate webhook delivery for their own shop (e.g., a merchant who installs the app and edits their own store, causing Shopify to send a genuinely-signed webhook body) can capture that valid `(body, hmac)` pair and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `Registry.process` will accept it, because the HMAC check only verifies the body, and will invoke the handler with `WebhookMetadata` claiming the data belongs to the victim shop: [6](#0-5) 

Any host application following this gem's documented API for webhook processing (using `request.shop` to select/scope the tenant record to update) is exposed to cross-tenant data confusion, since the gem itself asserts this as a validated, trustworthy field once `Utils::HmacValidator.validate` passes.

### Impact Explanation
This breaks the identity binding between an authenticated payload and the tenant (`shop`) it is attributed to, enabling cross-tenant access/confusion: an attacker who controls one legitimately-installed shop can cause the app to process arbitrary attacker-chosen body content under a victim shop's identity. This matches the Critical impact category of cross-tenant access via a credential/authenticity check that does not cover the field actually used for tenant binding.

### Likelihood Explanation
Any developer using this gem's documented `Registry.process`/`Request` API is affected — this requires no special configuration, only that the attacker has (or briefly obtains) any working installation of the app on their own shop to harvest a validly-signed body/HMAC pair, then replays it with a forged `shop-domain` header. No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) values in the signed material verified by `HmacValidator`, or otherwise cryptographically bind the shop-domain header to the HMAC before trusting it as the tenant identifier in `WebhookMetadata`. At minimum, document/require that `Registry.process` cross-check `request.shop` against out-of-band knowledge (e.g., a registered/known shop list) rather than treating the header value as authenticated purely because the body's HMAC validated.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`; app receives a genuine webhook with body `B` and header `shopify-hmac-sha256: H` where `H = HMAC(secret, B)`, and header `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same `B` and `H` to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (see `lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only checks `B` against `H`; it never inspects the shop header.
4. `Registry.process` (see `lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `shop: "victim.myshopify.com"` even though the data in `B` originated from `attacker.myshopify.com`, causing the host application to apply attacker-controlled webhook data to the victim shop's tenant record.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
