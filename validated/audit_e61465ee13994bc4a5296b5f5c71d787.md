Audit Report

## Title
LDAP Authentication Bypass via Unauthenticated Bind with Empty Password - ([File: core/sessions/ldapauth/ldap.go])

## Summary
`ldapAuthenticator.CreateSession` and `ldapAuthenticator.TestPassword` forward the client-supplied password directly to `conn.Bind(searchBaseDN, sr.Password)` / `conn.Bind(searchBaseDN, password)` with no check that the password is non-empty. [1](#0-0) [2](#0-1)  Per RFC 4513 §5.1.2, a simple Bind with a non-empty DN and zero-length password is defined as an "unauthenticated bind," which many LDAP servers (e.g. unhardened OpenLDAP) will accept as successful without validating any secret.

## Finding Description
`SessionRequest.Password` is taken as-is from client input, `json:"password"` with no `required`/length validation. [3](#0-2)  `CreateSession` builds the DN from the (attacker-controlled but escaped) email and calls `conn.Bind` with the raw password before doing anything else, so if `conn.Bind` returns `nil` for an empty password (server-dependent, RFC-4513-compliant fallback behavior), the code proceeds to `FindUser`, resolves the real role via group membership, and inserts a fully valid row into `ldap_sessions` — granting a real session for that user/role. [4](#0-3)  The identical unguarded pattern exists in `TestPassword`. [5](#0-4)  No application-level guard (`if password == ""`) exists anywhere in this file or in `session.go`, confirmed by grep across the codebase.

This is a real, root-cause gap in the code: the application never independently enforces that a non-empty secret was supplied, and instead trusts the LDAP server's Bind response unconditionally — which is exactly the CVE-2020-26168-class bug described.

## Impact Explanation
If exploitable, this is a full node authentication bypass: an unauthenticated attacker submitting a known email with an empty password can obtain a valid session with that user's role, including admin, granting full node API access. This maps cleanly to the in-scope "node API authentication or role bypass" impact class.

## Likelihood Explanation
Exploitability is entirely conditional on the deployed upstream LDAP server's configuration — specifically, whether it permits RFC-4513 unauthenticated binds for non-empty DN/empty-password requests. Modern directory implementations widely deployed in enterprise contexts (Active Directory) reject or specially flag such binds, and many hardened OpenLDAP deployments disable this via `disallow bind_anon`. This is fundamentally a defense-in-depth gap in Chainlink's code (missing a belt-and-suspenders check) rather than a guaranteed bypass against a "default" configuration — the actual bypass condition depends on the operator's separate LDAP server configuration, which is external to the chainlink codebase itself. However, the code itself provides no protection regardless of the operator's LDAP setup, which is a legitimate and fixable code-level weakness, and the fix is trivial and clearly warranted regardless of upstream server posture.

## Recommendation
Add an explicit rejection of empty/zero-length passwords before calling `conn.Bind` in both `CreateSession` and `TestPassword`:
```go
if sr.Password == "" {
    return "", errors.New("password cannot be empty")
}
```
This removes reliance on the LDAP server's own unauthenticated-bind policy, making the node's own auth logic RFC-4513-safe by default.

## Proof of Concept
1. Configure a Chainlink node with LDAP auth pointed at an LDAP server that permits unauthenticated binds (RFC 4513 default absent explicit hardening, e.g. OpenLDAP without `disallow bind_anon`).
2. `POST` to the sessions endpoint (backed by `sessions_controller.go` → `ldapAuthenticator.CreateSession`) with `{"email": "admin@example.com", "password": ""}`.
3. `conn.Bind(searchBaseDN, "")` succeeds per RFC 4513 unauthenticated-bind semantics on the test server.
4. `FindUser` resolves the admin role via group search, and a row is inserted into `ldap_sessions`, returning a valid session cookie for the admin account without a correct password ever being supplied.
