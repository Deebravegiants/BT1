## Title
`SignerCapabilityOfferProofChallengeV2` omits `chain_id`, enabling cross-network replay of a signer-capability delegation signature - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
The seed report's bug class is: a security-relevant field is left out of the message that gets hashed/signed for verification, letting an attacker substitute a value that was never actually authorized by the signer. In `account.move`, the `RotationCapabilityOfferProofChallengeV2` struct was explicitly updated to add `chain_id` "to prevent replaying the challenge message" [1](#0-0) , but the sibling struct `SignerCapabilityOfferProofChallengeV2`, used to authorize delegation of full signer capability (i.e., the ability to mint a `signer` for the account and act as it, moving/withdrawing any asset), was not given the same fix and still lacks `chain_id` [2](#0-1) .

### Finding Description
`offer_signer_capability` builds the proof challenge purely from `sequence_number`, `source_address`, and `recipient_address`, then verifies the caller-supplied signature against it via `verify_signed_message`: [3](#0-2) 

Because `chain_id` is not part of the signed struct, a signature that a user produced to authorize a signer-capability delegation on one Aptos network (e.g., a devnet/testnet instance, a local network, or any future chain sharing the same account-address derivation) is byte-for-byte valid input to `offer_signer_capability` on a different chain (e.g., mainnet) — as long as `source_address`, `recipient_address`, and `sequence_number` match. This mirrors the seed bug's pattern exactly: a value that should scope/bind the signature (there: `offset`; here: `chain_id`) is left out of what is actually hashed and checked, letting an attacker present an out-of-context signature as if it authorized the current, different context.

### Impact Explanation
Successful replay grants the attacker-controlled `recipient_address` a `SignerCapabilityOffer`, letting `create_authorized_signer` mint a full `signer` for the victim's account. That signer can withdraw APT/coins, transfer or burn fungible-asset/object-held resources, and otherwise fully impersonate the account — a custody-grade takeover of owner/authority, matching the impact class "Unauthorized takeover of ... resource-account control ... tied to live assets" and "Theft ... of APT, fungible assets, token objects." This is high severity because it results in unauthorized signer capability (equivalent to key compromise) for the victim account.

### Likelihood Explanation
Exploitability depends on the same `sequence_number` (an account-scoped nonce that increments with each transaction) coinciding across the two contexts and the account owner having produced (and somehow exposed, e.g., via a devnet/testnet dApp, faucet demo, or misconfigured client library) a signed `SignerCapabilityOfferProofChallengeV2` off-chain that gets replayed on a different chain instance sharing the same address space. This is a real but narrower attack surface than a pure single-chain forgery — it requires cross-network signature exposure, which is plausible given multiple long-running Aptos networks (mainnet, testnet, devnet, local testnets) using the same account/auth-key derivation scheme. Likelihood is therefore moderate rather than trivial, but the missing field is an unambiguous, root-cause code defect, not a mere assumption.

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2` (mirroring `RotationCapabilityOfferProofChallengeV2`) and include `chain_id::get()` when constructing the challenge in `offer_signer_capability`, so signatures are bound to the specific chain instance and cannot be replayed across networks.

### Proof of Concept
1. On Chain A (e.g., testnet), account `S` calls (or a wallet/dApp produces) a valid Ed25519 signature over `SignerCapabilityOfferProofChallengeV2 { sequence_number: n, source_address: S, recipient_address: R }`.
2. This signature bytes and `n` leak or are reused (e.g., same seed phrase test account also exists at same address on Chain B, or the signature is captured from a public tx/log).
3. On Chain B (e.g., mainnet, if `S`'s address and sequence number align), an attacker submits `account::offer_signer_capability(account=S_signer_placeholder_not_needed_since_public_call, signer_capability_sig_bytes, account_scheme, account_public_key_bytes, recipient_address=R)`.
4. `verify_signed_message` succeeds because the challenge struct verified is identical to the one signed on Chain A (no `chain_id` differentiates them).
5. `R` (attacker-controlled) now holds a `SignerCapabilityOffer` for `S` and can call `create_authorized_signer` to obtain a full signer for `S`, draining assets.

*Note:* I could not find a live testnet/mainnet address-collision proof within this repo snapshot (that depends on off-chain key reuse across networks), so this analog's real-world triggerability rests on the plausible-but-unverified precondition of a leaked/replayed off-chain signature across chains sharing the same account address. This is flagged as the primary uncertainty in an otherwise clear code-level omission relative to the pattern the framework's own authors fixed in the rotation-capability analog.
