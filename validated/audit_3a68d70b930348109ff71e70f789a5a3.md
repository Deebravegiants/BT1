### Title
Permanent DoS of Withdraw/Deposit via Direct Vault Token Donation Causing Unrecoverable `checked_sub().unwrap()` Underflow Panic - (File: `program/src/processor.rs`)

### Summary
`process_withdraw` (and `process_deposit`) rely on `Calculator::calc_take_pnl` and a chain of unchecked `.unwrap()` calls on `checked_sub` to update `TargetOrders.calc_pnl_x` / `calc_pnl_y`, the AMM's internal invariant-tracking state used for PnL accounting. These values are derived from live vault token balances (`amm_pc_vault.amount`, `amm_coin_vault.amount`) fetched directly from the SPL token account, not from a value the program itself fully controls. Because SPL token vaults are ordinary token accounts, any unprivileged actor can transfer tokens directly into the AMM's coin/pc vault (a "donation") without going through `Deposit`/`Swap`, which desynchronizes the vault balance from the internal `calc_pnl_x`/`calc_pnl_y` state that `calc_take_pnl` assumes stays proportionally consistent. This can push the arithmetic in `calc_take_pnl` and the subsequent `target_orders.calc_pnl_x = x1.checked_sub(...).unwrap().checked_sub(U128::from(delta_x)).unwrap()` update into an underflow, causing a Rust panic and instruction abort on every future call.

### Finding Description
`calc_take_pnl` computes `x2`/`y2` via an integer-square-root based invariant rebalance and then does `x1.checked_sub(x2).unwrap()` / `y1.checked_sub(y2).unwrap()`: [1](#0-0) 

The resulting `delta_x`/`delta_y` (pnl to be taken) is later subtracted again from `x1`/`y1` at the end of `process_withdraw` when updating `target_orders.calc_pnl_x` / `calc_pnl_y`, again using unchecked `.unwrap()`: [2](#0-1) 

`x1`/`y1` and `total_pc_without_take_pnl`/`total_coin_without_take_pnl` (which feed `calc_take_pnl`) are derived straight from the live vault account balances: [3](#0-2) 

Because vaults are plain SPL token accounts owned by the AMM authority PDA, any account can call `spl_token::instruction::transfer` to donate tokens directly into `amm_coin_vault`/`amm_pc_vault`, bypassing all of `Deposit`'s and `Swap`'s bookkeeping. This distorts the ratio between the actual vault balance and the previously stored `calc_pnl_x`/`calc_pnl_y` (which is only updated incrementally on `Deposit`/`Withdraw`/`SetParams`/pnl-withdrawal paths), producing an `x1`/`y1` vs. `x2`/`y2` (or `x1 - normalize(pc_amount) - delta_x`) relationship the code did not anticipate, and the `.unwrap()` on `checked_sub` panics.

Since `target_orders.calc_pnl_x`/`calc_pnl_y` and `amm.state_data.need_take_pnl_*` are only mutated when the transaction succeeds, a panicking transaction leaves the corrupted/incompatible state in place. Because the *same* deterministic combination of stored `calc_pnl_x`/`calc_pnl_y` and vault balances is used on every subsequent `Withdraw`/`Deposit` call, the panic will recur on every future call to these instructions for that pool, permanently freezing all LP withdrawal and deposit paths and hence LP funds already deposited (they can no longer be redeemed).

### Impact Explanation
This is a fund-freezing denial of service: once triggered, LPs of the affected pool can never again call `Withdraw` or `Deposit` successfully, because the same panic reproduces deterministically from the persisted on-chain state. This matches "permanent freezing of user or LP funds" required by scope, analogous to the CVE's crash/hang DoS impact on the affected component (the optimizer/accounting logic), but here achieved via a reachable arithmetic invariant violation instead of a query optimizer bug.

### Likelihood Explanation
Reachability requires only a standard SPL token `Transfer` instruction sent by any unprivileged wallet holding coin/pc tokens, targeting the publicly known AMM vault addresses (`amm.coin_vault`/`amm.pc_vault`, discoverable from any `AmmInfo` account) — no signer authority over the pool, no privileged role, and no interaction with the AMM program itself is required to perform the donation. The precise numeric conditions needed to force the underflow depend on the specific pool's live balances, decimals, and current `calc_pnl_x`/`calc_pnl_y` state, so the exact donation amount must be calculated per-pool, making this a likely-but-not-trivial-to-automate-generically attack, though well within reach of a scripted attacker who reads on-chain state and computes the required amount before submitting the donation transaction.

### Recommendation
Replace the unchecked `.unwrap()` calls on `checked_sub` in `calc_take_pnl` and in the `calc_pnl_x`/`calc_pnl_y` update in `process_withdraw`/`process_deposit` with `.ok_or(AmmError::CheckedSubOverflow)?` (as is already done elsewhere in the file, e.g. `calc_total_without_take_pnl_no_orderbook`), so that an inconsistent state returns a graceful `ProgramError` instead of panicking, and additionally treat the underflow as a signal to clamp/re-derive `calc_pnl_x`/`calc_pnl_y` from the live vault balances rather than persisting an unreachable invariant.

### Proof of Concept
1. Create a Raydium AMM pool via `Initialize2` with initial coin/pc liquidity. [4](#0-3) 
2. Perform normal `Deposit`/`Withdraw` activity to establish non-trivial `target_orders.calc_pnl_x`/`calc_pnl_y` state.
3. From any wallet holding the pool's coin or pc mint, send an `spl_token::instruction::transfer` directly to `amm.coin_vault` or `amm.pc_vault` (no AMM program instruction involved) for an amount computed to skew the ratio such that `x1 - normalize_decimal_v2(pc_amount) - delta_x` (or the `x1.checked_sub(x2)` inside `calc_take_pnl`) becomes negative. [5](#0-4) 
4. Call `Withdraw` (or `Deposit`) again; the transaction panics inside `calc_take_pnl` or the `target_orders.calc_pnl_x`/`calc_pnl_y` update, aborting. [2](#0-1) 
5. Repeat `Withdraw`/`Deposit` calls with unchanged pool state: the panic recurs deterministically every time, confirming permanent denial of the withdrawal/deposit path and effective freezing of LP funds in the pool.
