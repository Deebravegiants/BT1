### Title
Unbounded GET request storage keys enable a state-verification amplification DoS - (File: `modules/ismp/core/src/handlers/response.rs`)

### Summary
`GetRequest.keys` is an unbounded `Vec<Vec<u8>>` [1](#0-0) , and both the dispatch path (`DispatchGet`) [2](#0-1)  and the response-handling path in `pallet-ismp`/`pallet-coprocessor` iterate over every key of every GET request in the batch to run full trie/storage-proof verification, with no cap found anywhere in the codebase on the number of keys per request or per batch.

### Finding Description
`handlers::response::handle` loops over `msg.requests` and, for each `GetRequest`, clones `request.keys` and calls `state_machine.verify_state_proof(host, keys, ...)`, which performs a full Merkle/Patricia trie lookup (or EVM `eth_getProof`-style verification, involving trie rebuilding and contract-account proof resolution) for every single key [3](#0-2) . The EVM implementation of `verify_state_proof` groups keys by contract, resolves the contract account proof, and rebuilds the storage trie/verifies membership per key, which is measurably expensive per key [4](#0-3) . The Substrate/child-trie implementation similarly iterates the trie for each key [5](#0-4) .

There is no maximum enforced on `keys.len()` in `DispatchGet`/`GetRequest`, nor in `handle_unsigned`'s batch processing, nor in `pallet-coprocessor`'s `handle_get_requests` path, which performs the identical per-key `verify_state_proof` loop plus a bandwidth-gate charge computed only after verification completes [6](#0-5) . `handle_unsigned`'s weight annotation is a flat static placeholder (`Weight::from_parts(300_000_000, 0)`, described as "should get overridden by the FeeHandler") [7](#0-6) , and I could not confirm from the available index whether the runtime's `FeeHandler`/`WeightToFee` implementation actually scales weight/fee proportionally with `keys.len()` before charging — this is a gap in my verification.

This mirrors the Bugsink bug class: an attacker-controlled collection size (tags → GET-request keys) is processed without a cap, and each element costs real verification work in a shared execution context (an ISMP unsigned extrinsic batch / block), delaying other message processing.

### Impact Explanation
If keys-count is truly unbounded and unpriced relative to verification cost, an attacker (any relayer submitting an unsigned `handle_unsigned` GET response, or on the coprocessor's `handle_unsigned` for `GetRequestsWithProof`) could submit a request/response with a very large number of storage keys, forcing the runtime to spend disproportionate time in trie/proof verification within a single block's execution — delaying delivery of other legitimate ISMP messages (requests, responses, consensus updates) that share the same block/extrinsic queue. This is availability-only, matching CWE-400, and does not directly enable fund theft — but I could not fully confirm the actual fee/weight charged per key from the index, which is essential to determining whether this is truly unbounded in practice.

### Likelihood Explanation
Dispatching a GET request with many keys requires only a valid application dispatching through `IsmpDispatcher`/`IDispatcher.dispatch` — no privileged role. Submitting the response batch via `handle_unsigned` is also unsigned/permissionless, gated only by proof validity [8](#0-7) . However, without confirming the actual weight/fee scaling for this call in the runtime configuration, I cannot assert with confidence that this path is currently unmitigated — it's possible weight benchmarking already scales with request size, which I was unable to verify from the indexed files.

### Recommendation
Confirm (or add, if missing) a hard cap on `GetRequest.keys.len()` at dispatch time (in `dispatch_request` for `DispatchGet`) and reject responses/requests exceeding that cap in `handlers::response::handle` and `pallet-coprocessor::handle_get_requests`, analogous to Bugsink's `MAX_EVENT_TAGS` cap. Ensure `handle_unsigned`'s benchmarked weight (and therefore its fee) scales with the total number of keys across the batch so verification cost is priced, not merely capped.

### Proof of Concept
Not constructible with confidence: I was unable to verify from the available index whether an actual numeric cap or weight-scaling mechanism already exists elsewhere in the runtime configuration (e.g., benchmarked `WeightInfo` for `handle_unsigned`/`FeeHandler`), which is required to determine whether this DoS is practically exploitable today. I recommend a Devin session with full repository access to check the benchmarked weights for `pallet_ismp::Call::handle_unsigned` and `pallet_coprocessor::Call::handle_unsigned`, and any `MaxKeys`-style bound in `Config` traits, before treating this as confirmed.
