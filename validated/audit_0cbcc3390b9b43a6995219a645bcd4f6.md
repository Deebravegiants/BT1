### Title
Unchecked ERC-20 return value in `IntentGatewayV2::withdraw()` and `onAccept()` SweepDust path lets silent-failure tokens mint free escrow payouts - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` diverges from the mainline EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol`, which uses OpenZeppelin's `SafeERC20.safeTransfer`) by paying out escrowed tokens with a raw low-level `.call()` and checking only the boolean "call succeeded" flag, not the ABI-encoded `bool` return value of `transfer()`. This is the exact bug class from the referenced eETH report: a token whose `transfer`/`transferFrom` returns `false` instead of reverting on failure will pass the check, debit the internal escrow accounting, and emit success events without moving any tokens.

### Finding Description
In `withdraw()`, escrowed input tokens and fee tokens are released like this: [1](#0-0) 

and dust sweeping in `onAccept()` follows the same pattern: [2](#0-1) 

In both places only `success` (whether the low-level call reverted) is checked; the returned calldata (the ERC-20 `bool` payload) is discarded. For an ERC-20 implementation that returns `false` on a failed transfer instead of reverting — a widely-known non-standard-but-real ERC-20 behavior, and precisely the bug class cited in the eETH report — `success` will be `true` even though zero tokens moved. `withdraw()` will still decrement `_orders[body.commitment][token] -= amount` and emit `EscrowReleased`/`EscrowRefunded` as if funds were paid.

This contrasts with the properly-guarded escrow release path elsewhere in the codebase, `IntentsBase::_withdraw()`, which uses `SafeERC20.safeTransfer` (reverts on `false` return): [3](#0-2) 

so the Tron contract's use of raw `.call()` instead of `safeTransfer`/`safeTransferFrom` is the root-cause deviation.

### Impact Explanation
`withdraw()` is the function that finalizes cross-chain intent settlement — it is invoked from `onAccept()` when a `RedeemEscrow`/`RefundEscrow` ISMP message is delivered from the paired-chain `IntentGatewayV2` instance, i.e., this is a route any relayer can trigger by delivering a legitimate cross-chain proof for a real order. If the escrowed input or fee token silently returns `false` on transfer failure (e.g. paused token, blacklist hit, insufficient balance edge case, or a token whose failure semantics differ from the reverting model the code assumes), the contract:
- Marks the order filled/refunded and decrements internal escrow accounting as if the payout succeeded, while the solver/user/beneficiary received nothing (fund freezing / loss for the intended recipient), and
- Leaves the actual token balance stuck in the contract, permanently orphaned from any accounting bucket since `_orders[...]` was already zeroed out.

This satisfies "concrete theft or permanent freezing of funds" — the tokens become permanently unrecoverable via the contract's own accounting once the escrow entry is decremented but the transfer never landed.

### Likelihood Explanation
Likelihood is High for tokens with non-reverting failure semantics deployed on Tron/EVM-compatible chains supported by this gateway; it requires no privileged role — a solver, user, or relayer simply needs an order that escrows/settles such a token, and the failure condition (e.g., a blacklist, pause, or edge-case balance check) to trigger during withdrawal or dust sweep. No admin or governance action is needed to reach this path; it fires on ordinary `fillOrder`/`cancelOrder`/`RedeemEscrow`/`RefundEscrow`/`SweepDust` message delivery.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (both the token loop and the fee-token payout) and in the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring the approach already used in `IntentsBase::_withdraw()`. This ensures both revert-on-failure ERC-20s and false-returning ERC-20s are handled uniformly and that escrow accounting is never decremented unless the transfer genuinely succeeded.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an ERC-20 token whose `transfer(to, amount)` returns `false` when, e.g., `to` is blacklisted or a balance-related edge case occurs, without reverting.
2. A user places an order escrowing this token via `placeOrder` (uses `safeTransferFrom`, so escrow deposit succeeds normally). [4](#0-3) 
3. A solver fills the order on the destination chain; the resulting `RedeemEscrow` message is delivered via `onAccept()` → `withdraw()` on the source chain.
4. Configure/trigger the token so `transfer(beneficiary, amount)` returns `false` (no revert) for the beneficiary address.
5. `withdraw()` executes `token.call(...)`; `success == true` (the call itself didn't revert), so `TransferFailed()` is never raised — `_orders[commitment][token] -= amount` runs and `EscrowReleased` is emitted, even though the beneficiary's token balance did not increase. The escrowed tokens remain stuck in the `IntentGatewayV2` contract with no remaining accounting record to reclaim them.
