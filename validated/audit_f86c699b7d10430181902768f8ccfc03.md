## Analysis

The reported bug class — an unrestricted, powerful `call()` primitive that should filter dangerous targets/selectors — has a direct analog in `CallDispatcher.dispatch()`. [1](#0-0) 

`dispatch()` is `external` with **no `msg.sender` check whatsoever** and no restriction on the `to` target or `data` selector of any call it executes — it will call *any* contract with *any* calldata and *any* value, exactly the pattern the LSSVMPair report calls out as risky and recommends restricting.

### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone execute arbitrary calls and drain funds transiently or permanently stranded in the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single shared, externally deployed contract used by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to execute user-supplied `Call[]` batches during predispatch/postdispatch swap flows. Its `dispatch(bytes)` entrypoint has no access control at all: any address can invoke it directly, at any time, to make the dispatcher execute an arbitrary `Call[]` against arbitrary targets. This is the same class of risk flagged in the source report for `LSSVMPair.call()` — an unrestricted, powerful call primitive — except here it is worse because there is *no caller restriction whatsoever* (the original report's `call()` was at least gated `onlyOwner` and target-whitelisted).

### Finding Description
`CallDispatcher.dispatch()`:
```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [1](#0-0) 

has no `onlyX` modifier, no reentrancy guard, and no allow-list of targets/selectors. Callers of the dispatcher (`IntentGatewayV2.placeOrder`, `HyperFungibleToken.onAccept`, `WrappedHyperFungibleToken.onAccept`) transfer real user or escrowed funds to the dispatcher's address *before* invoking `dispatch()` to run the swap/execution batch, then sweep the resulting balance back: [2](#0-1) 

The documentation itself acknowledges the dispatcher "holds tokens temporarily during execution" and instructs integrators to use exact-amount approvals rather than unlimited ones to limit blast radius — an explicit admission that funds transiently sit in a contract anyone can call into: [3](#0-2) 

Critically, the sweep-back logic in `placeOrder` only reclaims the specific `order.inputs[i].token` balances it expects — it has no knowledge of any other token that a predispatch/postdispatch `Call[]` might produce or leave behind (e.g. multi-hop swap remainders, slippage residue, or fee-on-transfer leftovers). Any such token remains sitting in the dispatcher's balance indefinitely. Because `dispatch()` is open to any caller, that stranded balance — as well as any balance that happens to be present at the moment of a reentrant or interleaved call — can be swept out by an unrelated third party who simply calls `CallDispatcher.dispatch()` directly with a `Call[]` pointing `to` the leftover token's `transfer`/`transferFrom` selector.

### Impact Explanation
Any unprivileged address can call `CallDispatcher.dispatch()` to move out any asset balance the shared dispatcher currently holds — dust or residue left by `IntentGatewayV2` predispatch/postdispatch swaps, or `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain calldata execution, from *any* user's order, not just the caller's own. This is concrete theft of funds that should either return to the escrowing gateway (`DustCollected`) or to the intended beneficiary, redirected instead to an arbitrary attacker. Because the same dispatcher instance is shared across all `IntentGatewayV2` orders and all HFT/WrappedHFT cross-chain deliveries, the attack surface spans every app configured to use it.

### Likelihood Explanation
Medium-to-High. No special privilege, proof, or governance access is required — a plain, permissionless transaction to `CallDispatcher.dispatch()` suffices. The only precondition is that the dispatcher holds a nonzero balance of some asset at call time, which is a normal, expected, and documented occurrence given its role as a temporary holding/execution contract for multiple concurrent flows, and given that the sweep logic in `IntentGatewayV2.placeOrder` only accounts for known `order.inputs` tokens.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by an authorized set of caller contracts (e.g., an `onlyAuthorizedCaller` allow-list of `IntentGatewayV2`/`HyperFungibleToken`/`WrappedHyperFungibleToken` instances), mirroring the acknowledged fix pattern in the source report (restricting a powerful `call()` to a whitelisted/filtered set of callers and targets). Additionally, ensure the sweep step in `IntentGatewayV2.placeOrder`/`fillOrder` accounts for or forbids arbitrary token residue left on the dispatcher, and consider adding a reentrancy guard to `dispatch()`.

### Proof of Concept
1. A user places an order via `IntentGatewayV2.placeOrder` with a `predispatch.call` batch that performs a multi-hop swap producing a small amount of an intermediate token not listed in `order.inputs` (or that simply leaves slippage residue on the token used).
2. `IntentGatewayV2`'s sweep loop only builds `transferCalls` for `order.inputs[i].token`, so the intermediate/residual token balance remains on the `CallDispatcher` contract after `placeOrder` completes. [4](#0-3) 
3. Anyone (no relation to the original order) then calls `CallDispatcher.dispatch(abi.encode([Call({to: residualToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualBalance)})]))` directly. Since `dispatch()` performs no caller check, this executes successfully and transfers the stranded balance to the attacker. [1](#0-0)

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
