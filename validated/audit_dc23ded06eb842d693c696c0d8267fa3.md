## Analysis

The `WrappedHyperFungibleToken` contract instance of this bug class is real and reachable by any unprivileged token bridger. Unlike `IntentGatewayV2.sol`, which explicitly measures actual-received balances to handle fee-on-transfer tokens, `WrappedHyperFungibleToken.send()` never validates the amount it actually locked before broadcasting the cross-chain mint/unlock message.

### Title
Fee-on-transfer token amount mismatch in `WrappedHyperFungibleToken.send()` causes unbacked cross-chain mint - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`send()` locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches an ISMP message that instructs the destination chain to credit `params.amount` verbatim — without ever checking how much the contract actually received.

### Finding Description
In `send()`, the contract calls `safeTransferFrom` for the ERC20 path and then immediately builds and dispatches the cross-chain message using the caller-supplied `params.amount`, not the token balance delta: [1](#0-0) 

If `_underlying` is a fee-on-transfer (or rebasing-on-transfer) ERC20, the contract locks `params.amount * (1 - fee)` but the dispatched `Message.amount` still equals the full `params.amount`. On the destination chain, `HyperFungibleToken.onAccept()` mints exactly `message.amount` synthetic tokens to the beneficiary with no cross-check against the source-chain lock: [2](#0-1) 

This is the same root cause flagged in the external report (unaccounted transfer fee on `safeTransferFrom`), but here it manifests as an unbacked-mint bug rather than a simple accounting/withdraw-DoS bug, because the destination side mints a synthetic representation rather than merely logging a claimable balance.

Notably, the codebase's own `IntentGatewayV2.sol` already implements the correct pattern for exactly this class of bug — it snapshots balances before/after `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual received delta before computing the commitment: [3](#0-2) 

`WrappedHyperFungibleToken` (and its upgradeable twin `WrappedHyperFungibleTokenUpgradeable.sol`) never received this fix.

### Impact Explanation
Repeatedly bridging a fee-on-transfer token through `WrappedHyperFungibleToken` mints more synthetic `HyperFungibleToken` supply on remote chains than is actually collateralized by the locked underlying balance on the home chain. When those synthetic tokens are bridged back and redeemed, `onAccept()` on the wrapper performs `IERC20(_underlying).safeTransfer(beneficiary, message.amount)`: [4](#0-3) 

This drains real underlying tokens beyond what any given user actually deposited, eventually depleting the shared lock balance and causing other legitimate users' withdrawals to revert for insufficient balance (fund freezing) or, if drained fast enough, outright theft of the pooled underlying tokens — an unbacked mint that can be redeemed for real collateral belonging to other depositors.

### Likelihood Explanation
Any unprivileged user can trigger this by configuring/wrapping any deployed fee-on-transfer ERC20 as the `_underlying` for a `WrappedHyperFungibleToken` deployment (or if a governance/owner ever configures one), and then simply calling `send()` — no special privileges are required beyond normal bridging. The bug requires no consensus/relayer collusion; it is purely a contract-logic discrepancy between locked and dispatched amounts.

### Recommendation
Mirror the fix already applied in `IntentGatewayV2.sol`: measure `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom` in `send()`, and use the actual received delta (not `params.amount`) both for the dispatched `Message.amount` and for the `Sent` event. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.sol`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken`, configure `_underlying` as a token that charges, e.g., 10% fee on transfer.
2. Attacker calls `send({amount: 1000, ...})`. The contract calls `safeTransferFrom(attacker, this, 1000)`, but only 900 tokens actually land in the contract (100 taken as fee).
3. `_buildDispatchPost` still encodes `amount: 1000` in the `Message` body; this is dispatched via ISMP.
4. On the destination chain, `HyperFungibleToken.onAccept()` mints 1000 synthetic tokens to the beneficiary — 100 more than what is actually collateralized.
5. Beneficiary bridges the 1000 synthetic tokens back; `WrappedHyperFungibleToken.onAccept()` transfers out 1000 real underlying tokens, exceeding the 900 that were actually locked, draining from the pool backing other users' locked balances.
