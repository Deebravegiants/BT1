### Title
Webhook `shop-domain` header is trusted for tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC validated by `Utils::HmacValidator.validate` in `Registry.process` binds the signature exclusively to the request body. [1](#0-0)  The `shop` value used as the tenant identifier for the handler callback is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed material. [2](#0-1) 

### Finding Description
`Registry.process` validates the webhook using `Utils::HmacValidator.validate(request)`, and on success immediately builds `WebhookMetadata` using `request.shop`, dispatching it to the host application's handler: [3](#0-2) 

The identity binding the gem is supposed to enforce is:
`hmac_signed_bytes == bytes_that_determine_tenant`

But `to_signable_string` only equals `@raw_body`, while `shop` is parsed from a header that is completely outside that signable string. [4](#0-3)  The `HmacValidator.validate` implementation confirms the signature check only ever operates on `verifiable_query.to_signable_string`, i.e. the body: [5](#0-4) 

Because the webhook receiver endpoint is a normal public HTTP endpoint (not a mTLS/IP-restricted channel enforced by this gem), any unprivileged internet user who has legitimately received one valid `(raw_body, hmac)` pair for their own store (e.g., by installing the app on a test/free shop and triggering the event) can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header naming a victim shop. `Utils::HmacValidator.validate` will still succeed, since it re-computes the signature only over the body and never over the shop header, and `Registry.process` will hand the forged `shop` value straight to the host application's webhook handler as authentic. Any host application that uses `data.shop` (per `WebhookMetadata`) to select which tenant's record to update, cancel, refund, deactivate, etc., can be manipulated into acting on behalf of a shop the attacker does not own.

### Impact Explanation
This breaks the tenant-identity boundary the HMAC is meant to guarantee: it allows an attacker to make the gem report an authenticated webhook as coming from a shop other than the one whose secret/body pair was actually used, letting the caller perform cross-tenant actions using data or event bodies not associated with the credentialed content. This is a cross-tenant access vulnerability rooted in the gem's request/verification design, not merely a host-app misuse issue, since the gem exposes `Request#shop` as if it were verified alongside the HMAC that `Registry.process` checks.

### Likelihood Explanation
Any user who can install the app on any (even their own, low-value) shop can obtain one valid `(raw_body, hmac)` pair from a real Shopify webhook delivery for a topic whose body content does not itself strongly bind to their own shop domain (common for many topics whose JSON payload doesn't repeat the shop domain, or where the same generic event/body is plausible for many shops). No secret, access token, or privileged account of the victim shop is required — only network access to the app's public webhook URL and a legitimately captured signed body from any shop.

### Recommendation
Include the shop domain (and any other header claimed as authoritative, e.g. `webhook-id`, `topic`) inside the signed/verifiable material, or independently verify that the `shop-domain` header matches the shop encoded within `raw_body`/a previously established per-shop webhook secret/context before dispatching to the handler. At minimum, `to_signable_string` should incorporate `shop` so `HmacValidator.validate` can detect header tampering, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signed string. [6](#0-5) 

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event, capturing the raw POST body `B` and its valid header `X-Shopify-Hmac-Sha256: H` (computed by Shopify over `B` with the app's shared `client_secret`).
2. Attacker sends a POST directly to the app's public webhook endpoint with the exact same body `B`, the same `X-Shopify-Hmac-Sha256: H`, and `X-Shopify-Topic`/`X-Shopify-Webhook-Id` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers; `hmac` returns the decoded `H`; `to_signable_string` returns `B` — unchanged from the legitimate capture. [7](#0-6) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds despite the forged shop header. [8](#0-7) 
5. The handler is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`, and the host application (trusting the gem's verified `shop` field) performs its tenant-scoped action against the victim shop's records.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
