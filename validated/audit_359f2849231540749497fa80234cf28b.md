### Title
`Zap._sellInternal`'s pre-fee `minUsdcAmount` floor permanently freezes token holdings once LT devaluation drops a position's redeemable value below the floor - ([File: packages/contracts/src/Zap.sol])

### Summary
`Zap._sellInternal` reverts a sell outright if the gross USDC value of the LT received (estimated before the sell fee and before `redeem` executes) falls below `minUsdcAmount()`. Because that floor is enforced on the *whole* sell attempt rather than allowing users to accumulate more balance and unstick a devalued position, a holder whose token position has shrunk in USD terms below the live floor (currently mirroring BounceTech's `$10` `minTransactionSize`) can become permanently unable to sell/exit via `Zap`, regardless of how much of their balance they attempt to sell.

### Finding Description
In `_sellInternal`: [1](#0-0) 
```
uint256 ltReceived = bonding_.isGraduated(tokenAddress)
    ? _sellOnUniswapV2(tokenAddress, lt, tokenAmount)
    : _sellOnCurve(tokenAddress, tokenAmount);

uint256 grossUsdcEstimate = (ltReceived * IBounceLeveragedToken(lt).exchangeRate()) / 1e18;
if (grossUsdcEstimate / 1e12 < minUsdcAmount()) revert BelowMinAmount();
```
`minUsdcAmount()` reads BounceTech's live `GlobalStorage.minTransactionSize`, the same floor enforced on the mint/redeem side of the LT, as documented in `_buyInternal`/`_executeBuy`'s comments about the "live BounceTech floor" [2](#0-1) .

Because `grossUsdcEstimate` scales (approximately) linearly with `tokenAmount` for a given bonding-curve/AMM state and a given `exchangeRate()`, once the *entire* remaining balance of a token sells for less than the floor at the current LT exchange rate, no sub-amount of that balance can pass the check either — every smaller `tokenAmount` produces an even smaller `grossUsdcEstimate`. The holder cannot "top up" their way out of this the way a collateral depositor could top up collateral, because:
- On the pre-graduation curve path, `Bonding.sell` is only reachable through a registered router (Zap is the router); an ordinary trader has no direct path to sell tokens against the curve outside of `Zap._sellInternal` and its floor check.
- The user's only lever to increase `grossUsdcEstimate` is to buy *more* tokens of the same launch (spending fresh USDC) and hope the combined position clears the floor at the current, possibly still-depressed, exchange rate — a forced, uncompensated top-up that mirrors exactly the "prevents topping up" restrictiveness called out in the source report, except here it blocks *exiting* a position rather than *entering* one.

This is the direct structural analog of the reported `collateralInvariant` bug: both are post-action minimum-value invariants that, rather than only preventing a user from *creating* an under-floor state, end up freezing a user who already holds an under-floor position after external price movement (LT `exchangeRate()` devaluation here, collateral devaluation there), with no way to unwind except injecting more capital.

### Impact Explanation
A holder whose remaining token balance's live LT-equivalent value drops below `minUsdcAmount()` (e.g., because the reserve LT's `exchangeRate()` falls, or because a bonding-curve token's price has fallen and only a small remainder of tokens is held) has their position permanently frozen — `Zap.sell` reverts for any amount they submit, and there is no direct path to `Bonding.sell` for a non-router address. This is a form of permanent freezing of trader funds triggered purely by an external price movement of the reserve asset, which the protocol's own design explicitly tracks live (`minUsdcAmount()` mirrors `GlobalStorage.minTransactionSize`). The freeze is total for that position: neither slippage tolerance nor amount choice can route around it.

### Likelihood Explanation
This can be triggered by ordinary market conditions without any attacker: BounceTech LTs are leveraged tokens whose `exchangeRate()` moves with the underlying and can decline materially in volatile markets, and the floor itself (`minTransactionSize`) can also be raised by BounceTech at any time (as exercised in `test_buy_revertsBelowRaisedFloor`/`test_minUsdcAmount_tracksGlobalStorageFloor`), instantly shrinking the set of sellable positions for existing holders with no action on their part. Any small/late buyer of a token, or any holder of a token that graduates and then sees LT depreciation, is exposed.

### Recommendation
Do not gate the entire sell on a pre-fee/pre-redeem *estimated* floor computed from `tokenAmount`'s implied LT value. Instead:
- Only enforce BounceTech's mint/redeem floor where it is actually required by the LT (i.e., let `redeem()` itself revert if it must, and surface that revert distinctly), or
- Allow a user to sell their *entire* remaining balance regardless of the floor when doing so would zero out their position (mirroring the `collateralInvariant`'s "either empty or above minimum" logic, but for exits rather than deposits), so devalued dust positions can always be fully unwound rather than being permanently stuck below the floor.

### Proof of Concept
1. User buys tokens via `Zap.buy` when the reserve LT's `exchangeRate()` is high, ending up holding a balance whose current USDC-equivalent value is just above `minUsdcAmount()` (e.g., $12).
2. The reserve LT's `exchangeRate()` subsequently falls (leverage decay / underlying price movement) such that the same token balance's LT-equivalent value, computed via `_sellOnCurve`/`_sellOnUniswapV2` then multiplied by `exchangeRate()`, now estimates under `minUsdcAmount()` (e.g., $8).
3. User calls `Zap.sell(tokenAddress, fullBalance, 0)`. `_sellInternal` computes `grossUsdcEstimate` from the full balance and finds it `< minUsdcAmount()`, reverting with `BelowMinAmount` — even though the user submitted their entire holding and set no slippage floor.
4. Any smaller `tokenAmount` produces a strictly smaller `grossUsdcEstimate`, so no sell size succeeds. The user has no direct `Bonding.sell` access (router-gated) and is left holding a frozen position until/unless they buy more of the same token to push its value back above the floor.

    // The floor is read live from `GlobalStorage.minTransactionSize` rather

    // a graduation floor-bump that mints at the new floor).
