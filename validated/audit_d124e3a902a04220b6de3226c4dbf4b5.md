### Title
Dropped liquidation seizure legs are not released from the repayment plan — liquidator repays debt backed by collateral that is silently never seized - (File: contracts/controller/src/positions/liquidation/math.rs)

### Summary
`calculate_seized_collateral` allocates the planned repayment pro‑rata across the borrower's supply legs, but several rounding paths drop a leg via `continue` (zero `seizure_ray`, zero `capped_ray`, zero `seized_scaled`, zero `capped_amount`) without crediting that leg's `seizure_for_asset_usd` into `unseized_usd`. Only the sub‑3‑decimal floor branch contributes to `unseized_usd`. The returned "unbacked" value is therefore understated, `release_unbacked_repayment` releases less than it should, and the liquidator's repayment stays fully planned while part of the collateral that was supposed to back it is never transferred/credited.

### Finding Description
The external report (CVE-2025-22033) is the class "a dispatch handler returns NULL for an unsupported case and the caller invokes it unconditionally instead of falling back." The analog here is a seizure leg that rounding reduces to nothing — the "no handler" case — where the code silently continues instead of falling back to releasing the repayment it no longer backs.

In `calculate_seized_collateral` (contracts/controller/src/positions/liquidation/math.rs:363-505), for each supply position the code computes `seizure_for_asset_usd` (line 396) as this leg's pro‑rata share of `repay_usd * (1 + bonus)`. The only path that records a dropped fraction is the low‑decimals floor branch: [1](#0-0) 

But four later exits drop the leg entirely without touching `unseized_usd`:

- `seizure_ray <= Ray::ZERO` → `continue` (line 419-421)
- `capped_ray <= Ray::ZERO` → `continue` (line 428-430)
- `seized_scaled <= Ray::ZERO` → `continue` (line 456-458) — reachable when `capped_ray.div_floor(supply_index)` floors to 0 on a partial close while `capped_ray` was positive
- `capped_amount <= 0` → `continue` (line 465-467) — reachable when `capped_ray.to_asset_floor(decimals)` is 0 for a positive `capped_ray` (any decimals, whenever the seized value is below one base unit; not gated on `MIN_BORROWABLE_ASSET_DECIMALS`)

The function returns `(seized, unseized_usd.div_floor(one_plus_bonus))` (line 504), and the doc contract states it returns "the repayment USD that the dropped fractions no longer back" (line 361-362). `release_unbacked_repayment` (line 509-527) then trims `repaid` and pushes refunds only by that returned amount — so repayment legs whose collateral share was dropped at lines 419/428/456/465 remain in `repaid`, and `NormalizedRepaymentPlan::validate` still passes because it only checks internal sums, not collateral backing.

### Impact Explanation
A liquidator calling `Controller::liquidate(caller, account_id, payments, seize_mode)` repays borrower debt pro‑rata priced by USD, but for every leg dropped at a zero‑conversion `continue`, the corresponding collateral (tokens under `SeizeMode::Transfer`, or pool shares under `SeizeMode::Credit`) is never delivered and the corresponding repayment is never refunded. That is a direct, unrecoverable loss of the liquidator's funds — payment without the bonus‑adjusted collateral that justified it — benefiting the borrower's debt position at the liquidator's expense.

### Likelihood Explanation
Reachable by any unprivileged liquidator on any liquidatable account. It triggers whenever a supply leg's pro‑rata seizure is positive in USD but rounds to zero in shares (`div_floor` by `supply_index`) or in asset units (`to_asset_floor`). This is plausible for low‑value dust collateral legs on multi‑asset accounts — precisely the pro‑rata multi‑leg shape this liquidation engine is built for — and for borrowers whose collateral is fragmented. It requires no privileged action and no oracle manipulation: ordinary rounding boundaries suffice, which matches Medium severity.

### Recommendation
Accumulate `unseized_usd` on every path that discards a positive planned seizure: when `seizure_ray`, `capped_ray`, `seized_scaled`, or `capped_amount` resolve to zero (or when a leg is skipped for any reason after `seizure_for_asset_usd` was computed), add the leg's `seizure_for_asset_usd` (or the appropriate capped remainder) to `unseized_usd` before `continue`. Equivalently, compute `unseized_usd` as `total_seizure_usd - Σ(kept seizure USD)` so the returned value is definitionally the unbacked remainder, then let `release_unbacked_repayment` trim/refund the liquidator's payment accordingly.

### Proof of Concept
Conceptual trace (no exploit contract needed):

1. Borrower account holds two supply legs: a large leg A and a small leg B, plus a debt leg D; the position is liquidatable (HF < 1).
2. Liquidator calls `liquidate` with a payment on D sized to the partial‑close quote.
3. `normalize_repayment_plan` keeps the repayment; `calculate_seized_collateral` computes `seizure_for_asset_usd_B > 0`, but `capped_ray.div_floor(supply_index_B)` (or `to_asset_floor`) yields 0 → `continue` at line 457/466, `unseized_usd` unchanged.
4. The plan's `repay_usd` still includes the USD value leg B was meant to back; `release_unbacked_repayment` only removes the fraction reported (which excludes B).
5. Settlement pulls the full repayment from the liquidator, writes down D, and seizes only leg A. The liquidator paid for B's share and received nothing — a permanent loss, with no protocol error raised.

Uncertainty: I could not read `plan.rs` in this session to confirm the exact call site that feeds `unseized_usd` into `release_unbacked_repayment`; the finding rests on the function's documented contract (lines 361-362, 504) and the asymmetric accumulation of `unseized_usd`. If the caller independently re‑derives unbacked repayment per seized leg, the exposure narrows to legs where both derivations disagree, but the missing accumulation on the `continue` paths is still inconsistent with the stated contract.
