### Title
Webhook shop/topic identity spoofing via header fields not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and attribute the webhook to a tenant are read from unauthenticated HTTP headers and never included in the HMAC input.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw HTTP body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to those values: [2](#0-1) 

`Registry.process` validates the webhook using `Utils::HmacValidator.validate(request)`, which computes the HMAC over `to_signable_string` (i.e., the raw body only) and compares it against the `hmac-sha256` header: [3](#0-2) [4](#0-3) 

After this check passes, `request.shop` (an unauthenticated header value) is handed directly to the host application's handler as the tenant identifier via `WebhookMetadata`: [5](#0-4) 

The identity binding this breaks is: `HMAC-verified bytes (raw_body) == bytes acted on for tenant attribution (raw_body + shop header)`. The gem verifies the former but silently trusts the latter for the security-relevant "which shop does this event belong to" decision, exactly the "field acted on but not covered by the HMAC" pattern.

Because a given app's `client_secret`/`api_secret_key` is shared across every shop that installs the app (not shop-specific), any legitimate merchant who has installed the app can capture one of their own valid `(raw_body, hmac)` pairs (any webhook topic, e.g. a benign `app/uninstalled` or `orders/create` payload delivered to their own store) — this signature will still validate for any shop, since the shop identity is never part of the signed material. They can then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a victim shop.

### Impact Explanation
If the host application trusts `WebhookMetadata#shop` (as the documented usage pattern instructs) to look up per-tenant session/state and apply the event, an attacker can inject events attributed to an arbitrary victim shop without ever needing that shop's credentials — a cross-tenant confusion/spoofing primitive. Depending on the webhook topic the host app relies on (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`, or business-data webhooks), this can trigger unwanted tenant-state mutations, data deletion, or fake business events being attributed to a shop that never sent them.

### Likelihood Explanation
The attacker only needs to be able to install the app on any shop (a normal, unprivileged action) to obtain one valid signed webhook body/HMAC pair, and no `api_secret_key` or victim credentials are required — only header substitution on a replayed HTTP request to the app's public webhook receiver.

### Recommendation
Bind the security-relevant identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the signed material verified by `HmacValidator`, or otherwise cryptographically tie the header values to the specific delivery (e.g., verify the raw body was actually delivered for the claimed shop/topic combination via an independent authenticated channel) before exposing them to handlers as authenticated tenant identifiers.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimately delivered webhook request, including its raw body and the `X-Shopify-Hmac-Sha256` header value.
2. Attacker resends this exact body and HMAC header to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and, if desired, a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the raw body against the shared `api_secret_key`: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, even though the payload was never sent by or for that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
