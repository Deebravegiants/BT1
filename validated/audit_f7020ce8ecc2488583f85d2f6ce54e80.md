### Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, never the `shop-domain` header. `Utils::HmacValidator` and `Webhooks::Registry.process` therefore authenticate *that Shopify produced this payload with the app's secret*, but never authenticate *which shop the payload is for*. An attacker who owns any store that has the app installed can capture one of their own genuinely-signed webhook deliveries and replay it against the app's webhook endpoint with a different `shop-domain` header, and it will pass validation as if it came from the victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an attacker-controllable header with no cross-check against the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (the raw body) against the shared `api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once the HMAC check passes and forwards the caller-supplied `request.shop` straight into the handler as the tenant identity, with no additional binding check: [4](#0-3) 

The identity equality that should hold is:
`shop that cryptographically produced/authorized this payload == shop the library reports to the handler (request.shop)`

Because the HMAC secret (`Context.api_secret_key`) is the same for every shop that installs the app, and the signable string never includes `shop`, `topic`, or `webhook-id`, a valid signature only proves "Shopify signed this body with this app's secret" — not "this body is for shop X." Any store owner who installs the app can trigger a webhook to obtain a validly-signed `(body, hmac)` pair, then send that exact `(body, hmac)` pair to the app's webhook endpoint while swapping the `shop-domain` (and, since it's also unauthenticated, the `topic`/`webhook-id`) header to name a different shop. `Registry.process` will accept it and hand `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: ..., ...)` to the handler, misattributing attacker-chosen webhook content to a victim tenant.

### Impact Explanation
This crosses a tenant boundary: an attacker with no access to the victim shop and no possession of the app's `client_secret`/access tokens can make the app process attacker-chosen webhook data under the victim shop's identity. Depending on how the host app's webhook handlers key data lookups/mutations by `shop`, this can lead to cross-tenant data corruption, injection of forged events (e.g., fake `orders/create`, `app/uninstalled`, `customers/data_request`) attributed to the victim shop, or triggering shop-scoped side effects using attacker-controlled payload fields. This matches the Critical/High bar for cross-tenant access via an identity-binding gap.

### Likelihood Explanation
Likelihood is moderate-to-high for any developer who is also allowed to install the target app on a store they control (very common for public/App Store apps, and trivial with a free development store): they can generate a validly HMAC-signed webhook body/signature pair on demand, then replay it directly to the app's public webhook endpoint with a forged `shop-domain` header — no secrets, tokens, or victim interaction required.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is HMAC-verified, or otherwise authenticate `request.shop` independently, before trusting it as the tenant identity passed to handlers — e.g., have `Webhooks::Request#to_signable_string` incorporate the normalized `shop-domain`/`topic`/`webhook-id` headers alongside the raw body, and reject requests where the header-declared shop does not match a value that Shopify actually attests to (mirroring how `JwtPayload`/`AuthQuery` bind `shop` into their signed material).

### Proof of Concept
1. Install the target app on an attacker-controlled development store `attacker.myshopify.com`.
2. Trigger any webhook topic the app subscribes to (e.g., update a product) so Shopify sends a webhook POST to the app's configured endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and some `raw_body`.
3. Capture `raw_body` and the valid `hmac` value.
4. Replay a forged HTTP POST to the same webhook endpoint, keeping `raw_body` and `hmac` identical, but setting `x-shopify-shop-domain: victim.myshopify.com` (and any desired `x-shopify-topic`/`x-shopify-webhook-id`).
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only checks the body-derived signature; `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) then invokes the handler with `shop: "victim.myshopify.com"` and attacker-chosen `body`, confirming the cross-tenant spoof.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
