### Title
Missing Domain Separation Between `withdraw_fees` and `accumulate_fees` Beneficiary Signatures Allows Cross-Context Replay - ([File: modules/pallets/relayer/src/accumulate.rs])

### Summary
`pallet-ismp-relayer` lets a relayer authorize a "beneficiary redirect" for accrued fees in two different unsigned extrinsics — `withdraw` (payout to a destination chain) and `accumulate` (crediting freshly-proven delivery fees) — using signed messages that are byte-identical in structure and drawn from the same per-`(address, StateMachine)` nonce counter. A signature created to authorize one action can be replayed to satisfy the other, letting anyone who observes a relayer's signed authorization on-chain front-run and consume it out of its intended context.

### Finding Description
`withdraw`'s signed payload is built by: [1](#0-0) 

`accumulate`'s beneficiary-redirect payload is built by: [2](#0-1) 

Both hash `(nonce, StateMachine, beneficiary).encode()` with `keccak_256`, and both consume the *same* `Nonce<T>` double map, keyed only by `(address, StateMachine)`: [3](#0-2) [4](#0-3) 

There is no domain tag, purpose discriminant, or destination/source distinction baked into the signed message — `state_machine` in `accumulate` is the *source* chain of a delivered request, while `dest_chain` in `withdraw` is the *payout* chain, but the pallet's `StateMachine` type is the same enum for both, so a signature minted for one call is structurally valid for the other whenever the enum values coincide and the nonce has not yet advanced. Both extrinsics are dispatched with `RuntimeOrigin::none()` (unsigned), so both the signature and the full call are public in the mempool/block the moment either is submitted: [5](#0-4) 

Because `Nonce` is shared, any third party observing a relayer's `withdraw` signature (or a relayer's `accumulate` beneficiary signature) for `StateMachine = X`, nonce `N`, can immediately resubmit it inside the *other* extrinsic before the legitimate transaction lands, consuming the shared nonce out from under the relayer.

### Impact Explanation
This lands squarely in the "relayer fee and reward accounting" reachable surface named in scope, and is reachable from a single relayed proof/extrinsic submission with no special privilege. Concretely:
- An attacker can front-run a relayer's disclosed signature to force an early/unintended fee redirection using an authorization the relayer minted for a different chain-role (source vs. destination), before the relayer's own transaction executes.
- Because the shared nonce is advanced by whichever call lands first, the relayer's own legitimately-signed transaction is invalidated (`InvalidPublicKey`/nonce mismatch on replay), a denial-of-service on the relayer's ability to withdraw or redirect fees exactly when they intend to, and one that must be manually resolved by re-signing.
- The lack of a domain separator is the same class of bug as the reference report (a security-relevant authorization channel is not bound tightly enough to the action it is meant to gate), applied here to relayer reward accounting rather than account recovery.

The severity is bounded by the fact that the beneficiary address itself is still one the legitimate signer chose (an attacker cannot forge a new beneficiary without the relayer's key), so the primary demonstrable impact is DoS/griefing of relayer payouts and unintended cross-context consumption of a signed authorization, rather than an attacker directly minting funds to themselves.

### Likelihood Explanation
Both `withdraw_fees` and `accumulate_fees` are unsigned extrinsics anyone can submit, and their arguments (including the relayer's signature) become public as soon as either is broadcast or included. Any relayer that uses the `beneficiary` feature on both endpoints for the same `StateMachine` is exposed; no special conditions or elevated access are required for an observer to attempt the replay, only mempool visibility, which is standard.

### Recommendation
Add a distinct domain separator/action tag to each signed payload (e.g., prefix `withdraw`'s hash with a distinct discriminant such as `b"HB-WITHDRAW"` and `accumulate`'s with `b"HB-ACCUM-BENEFICIARY"`), and/or split the shared `Nonce<T>` map into two independent counters (or key by `(address, StateMachine, purpose)`) so a signature valid for one extrinsic can never satisfy the other's verification, even when the `StateMachine` values coincide.

### Proof of Concept
1. Relayer `R` (address `X`) signs and submits `withdraw_fees` with `dest_chain = StateMachine::A`, `beneficiary = B`, at `Nonce[X][A] = N`. This produces `sig = Sign(keccak256((N, A, B).encode()))`, publicly visible once broadcast, per the message builder: [1](#0-0) 
2. Before `R`'s transaction is included, an observer submits `accumulate_fees` with a `WithdrawalProof` whose delivered commitments' `delivery_address == X` on `source chain == StateMachine::A`, and `beneficiary_details = Some((B, sig))`, reusing the exact same `sig` captured in step 1.
3. `accumulate`'s verification passes because the hashed message and `Nonce[X][A] == N` match exactly the structure it expects: [6](#0-5) 
4. `Nonce[X][A]` is incremented to `N+1` by the `accumulate` call.
5. `R`'s originally-submitted `withdraw_fees(nonce = N, ...)` transaction is now processed and reverts with `InvalidPublicKey`/nonce mismatch because the shared nonce has already advanced, denying `R`'s intended withdrawal and forcing a re-sign — demonstrating the cross-context replay and resulting denial of service enabled by the missing domain separation.

	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());

	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
