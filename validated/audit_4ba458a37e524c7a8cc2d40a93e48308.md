### Title
Webhook shop-domain header is not covered by the HMAC, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC only to the raw request body, while `#shop` (and `#topic`, `#api_version`, `#webhook_id`) are read directly from unauthenticated HTTP headers that are never part of the signed material. Any party who can obtain one genuine `(raw_body, hmac)` pair for their own shop — which any merchant installing the app can trivially do — can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header, and `Utils::HmacValidator.validate` will still accept it.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers with no cryptographic link to the body or the HMAC: [2](#0-1) 

`Registry.process` validates the request using exactly this signable string: [3](#0-2) 
and then forwards the header-derived, unverified `request.shop` value straight to the app's handler as `WebhookMetadata`, which the docs describe as "The shop domain of the webhook" — implying it has been authenticated, per `docs/usage/webhooks.md` lines 12-17 and 125.

The binding the app relies on is:
`shop_header == shop_that_actually_produced(raw_body, hmac)`

Before the attack, a legitimately delivered webhook for Shop A satisfies this: `(shop = A, body = body_A, hmac = HMAC(secret, body_A))`.

An attacker who is a normal, unprivileged merchant can install the target app on their own shop (Shop A) and receive genuine webhook deliveries — this requires no `api_secret_key`, access token, or privileged access, since app installation is available to any Shopify store owner. The attacker captures one such delivery's raw body and its valid HMAC. They then send a forged HTTP POST to the app's public webhook endpoint with the same `raw_body`/`hmac`, but with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to an arbitrary victim shop `B`. Because `to_signable_string` never includes the shop header, `HmacValidator.validate` recomputes and compares only against `raw_body`, and the signature still matches. `Registry.process` thus accepts the request and calls the handler with `shop: "B"` while `body` is actually Shop A's content — breaking shop/body binding.

### Impact Explanation
Depending on how the host app implements its `WebhookHandler#handle`, trusting `data.shop` as the authenticated tenant identifier (which the gem's own documentation encourages) lets the attacker inject attacker-controlled webhook payloads that are processed under an arbitrary victim shop's identity — a cross-tenant data-integrity/confusion issue. For destructive topics such as `app/uninstalled` or `shop/redact`, or for data-ingestion topics like `orders/create`, this can let an unprivileged attacker corrupt, poison, or trigger deletion flows for another merchant's tenant data without ever needing that merchant's credentials.

### Likelihood Explanation
Requires only becoming a normal (free/trial) merchant who installs the target Shopify app, receiving one real webhook, and replaying it with a modified header to the app's public webhook endpoint — no secrets, tokens, or privileged access needed. This is a realistic, low-effort attack path for any internet user able to install the app.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the verified request (e.g., by having `to_signable_string` incorporate the shop header, or by cross-checking `request.shop` against a shop that is independently known to have registered for that specific webhook/topic before trusting it in `WebhookMetadata`).

### Proof of Concept
1. Install the target Shopify app on attacker-controlled Shop A; capture a genuine webhook delivery: `raw_body_A` and header `shopify-hmac-sha256: hmac_A` (valid HMAC of `raw_body_A` with the app's shared `client_secret`).
2. Send a POST to the app's webhook route with body `raw_body_A`, header `shopify-hmac-sha256: hmac_A` unchanged, but `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: raw_body_A, headers: forged_headers)` builds a request whose `#shop` returns `"victim-shop.myshopify.com"`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which validates successfully because `to_signable_string` only checks `raw_body_A`.
5. The app's `WebhookHandler#handle` receives `data.shop == "victim-shop.myshopify.com"` together with `data.body` actually belonging to Shop A, demonstrating the shop/body binding break.
