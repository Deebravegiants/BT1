### Title
Webhook `shop`/`topic`/`webhook_id` identity is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that signable string. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from unauthenticated HTTP headers and handed to the application's webhook handler unverified, even though the library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify."

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
and `HmacValidator.validate_signature` computes the expected signature purely from that string: [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from request headers that are never mixed into the signed payload: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then dispatches to the registered handler using the unverified `request.shop`: [4](#0-3) 

The binding that should hold is: **`shop` (identity used by the handler to select a tenant) == `shop` covered by the HMAC signature**. In this implementation, the HMAC only binds the body bytes; the `shop-domain` header is a field acted upon (used to identify the tenant in `WebhookMetadata`) but not covered by the HMAC. As documented, host applications are expected to route/store incoming webhook data by `data.shop`: [5](#0-4) 

### Impact Explanation
Because a single app's `api_secret_key` signs webhooks for every shop that installs the app, an unprivileged attacker can install the same app on their own (freely obtainable) development/test store, trigger a webhook with attacker-controlled body content (e.g., an `orders/create` or `products/update` event with fields they fully control), and capture the genuine `raw_body` + `X-Shopify-Hmac-Sha256` pair sent to the app's public webhook endpoint. Since the signature never covers the `shop-domain`/`topic`/`webhook-id` headers, the attacker can replay that exact body/HMAC pair to the same public endpoint while substituting a victim shop's domain in the `shop-domain` header. `HmacValidator.validate` still succeeds, and `Registry.process` forwards attacker-controlled `body` labeled as belonging to the victim shop to the handler. This is a cross-tenant data-injection/spoofing primitive: it lets an unprivileged user impersonate another tenant's webhook stream and inject or corrupt data attributed to a shop they do not control, which maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app using this gem's standard HTTP webhook flow as documented: the attacker only needs to install the app on their own shop (a normal, unprivileged onboarding action) and reuse the request framing shown in the docs. No access token, `client_secret`, or elevated privilege is required — only observation of one legitimate outbound webhook to the attacker's own endpoint.

### Recommendation
Bind the tenant/topic identity into the signed material or otherwise cryptographically tie the headers to the shop before trusting them. Concretely, `Request#to_signable_string` (or the validator) should incorporate `shop-domain` (and ideally `topic`/`webhook-id`) into the value verified against the HMAC, or `Registry.process`/`HmacValidator` should require the caller to supply the expected shop for the current tenant/session context and reject any webhook whose header-derived `shop` disagrees. At minimum, document prominently that `shop`, `topic`, and `webhook_id` are NOT covered by the HMAC and must not be trusted for tenant routing without an independent authenticated mapping (e.g., verifying the shop is one with an active registration/session before acting on the payload).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and configures a webhook subscription the app already registers for (e.g. `orders/create`).
2. Attacker creates an order on their own store with crafted note/body content, causing Shopify to POST a webhook to the app's public callback URL with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over raw body>`, and the crafted `raw_body`.
3. Attacker intercepts/replays this exact request to the same public endpoint, only changing `X-Shopify-Shop-Domain` to `victim.myshopify.com` (a shop that also installed the app).
4. `ShopifyAPI::Webhooks::Request.new` parses the headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body`—identical to step 2—so validation passes.
5. The app's handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled body>, ...)` and, following the documented pattern of routing/storing data by `data.shop`, processes/stores the attacker's data as if it belongs to `victim.myshopify.com`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
