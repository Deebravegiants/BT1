### Title
CatFee API credentials logged in plaintext via `Debug` formatting on client init - (File: tesseract/messaging/tron/src/lib.rs)

### Summary
`TronClient::new` logs the entire `CatFeeConfig` struct with `{:#?}` when CatFee integration is enabled, and `CatFeeConfig` derives `Debug` on all its fields, including `api_key` and `api_secret`, with no redaction/masking applied before logging.

### Finding Description
`CatFeeConfig` is defined with `#[derive(Debug, Clone)]` and holds `api_key: String` and `api_secret: String` in plaintext, with no `Debug`-skip or masking wrapper on the secret fields. [1](#0-0) 

During `TronClient::new`, when both `catfee_api_key` and `catfee_api_secret` are configured, the resulting `CatFeeConfig` is passed straight to `log::info!` using the `{:#?}` (pretty Debug) format specifier, printing the credentials into the relayer's log stream: [2](#0-1) 

This mirrors the reported CWE-532 bug class in the SageMaker Training Toolkit advisory: a temporary/long-lived authorization credential (there, a CodeArtifact token; here, CatFee's `api_key`/`api_secret` used for HMAC-signed API requests) is written unredacted to log output that operators commonly forward to centralized/aggregated logging (CloudWatch there, whatever log sink the tesseract relayer operator uses here — journald, file, or a log-shipping agent). Anyone with read access to those logs can recover the credential pair and impersonate the relayer against CatFee's API for as long as the key remains valid (these are not short-lived tokens like the CodeArtifact one — they are static API credentials configured by the operator, so exposure is effectively permanent until manually rotated).

Elsewhere in the codebase, secrets are explicitly masked before being logged/rendered (e.g. `maskToml`/`maskSecret` in the Simplex filler's setup API), showing the project is otherwise aware of this class of leak and treats it as something to actively prevent — this CatFee logging path was simply missed. [3](#0-2) 

### Impact Explanation
An operator running the TRON messaging relayer with CatFee energy-purchasing enabled will have their CatFee `api_key` and `api_secret` written to the relayer's log output at `info` level on every process start. `info` is a commonly-enabled default logging level for production relayer deployments, so this is not a debug-only exposure. Any party with read access to the relayer's logs (log aggregation systems, shared hosting, misconfigured log retention/exports) can extract the credential pair and use it to place or manipulate TRON energy purchase orders billed to the relayer operator's CatFee account, or exhaust/drain their CatFee balance — a direct funds-loss vector for the relayer operator, analogous to the CodeArtifact token misuse in the original advisory.

### Likelihood Explanation
This is triggered unconditionally and automatically whenever an operator configures `catfee_api_key`/`catfee_api_secret` (a supported, documented feature for reducing TRX costs) — no attacker action beyond having log access is required. Given `info`-level logging is standard for production, and the credentials are long-lived, the exposure window is large and requires no race condition or special network position.

### Recommendation
Do not log the full `CatFeeConfig` via `Debug`. Either implement a custom `Debug` for `CatFeeConfig` that redacts `api_key`/`api_secret` (e.g., print only a prefix/hash or `"***"`), or change the log statement in `TronClient::new` to log only non-sensitive fields (e.g., `api_base`, `timeout`) instead of the whole struct.

### Proof of Concept
1. Configure `TronConfig.catfee_api_key` and `catfee_api_secret` in the relayer's config.
2. Start the relayer; `TronClient::new` runs and executes `log::info!(target: LOG_TARGET, "CatFee integration enabled: {:#?}", catfee_config);` with `info`-level logging enabled (the default operational level). [4](#0-3) 
3. Inspect the process's log output (stdout, journald, forwarded log sink): the plaintext `api_key` and `api_secret` fields of `CatFeeConfig` appear in the pretty-printed struct. [5](#0-4)
