### Title
Token exchange sends `client_secret` to a shop host that is never validated against trusted Shopify domains - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the `shop` value used to build the Admin API host directly from the JWT `dest` claim (or from the caller-supplied `shop:` argument) and never runs it through `Utils::ShopValidator.sanitize!`, unlike the other two OAuth flows in the same module/family.

### Finding Description
`exchange_token` decodes the session token and takes `dest_shop = jwt_payload.shop` [1](#0-0) , then immediately uses it, unsanitized, to build the session and the destination host for the outbound OAuth request that carries `client_secret`: [2](#0-1) 

`JwtPayload#shop` is derived only from the `dest` claim with a string substitution, with no domain allow-list check: `@dest.gsub("https://", "")` [3](#0-2) . The only binding enforced on the token is `aud == Context.api_key` [4](#0-3) ; nothing constrains `iss`/`dest` to `myshopify.com`/`myshopify.io`/etc.

Compare this to the two sibling flows that build the same kind of outbound request with `client_secret` in the body: `RefreshToken.refresh_access_token` calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host [5](#0-4) , and `TokenExchange.migrate_to_expiring_token` does the same [6](#0-5) . `ShopValidator.sanitize!` exists specifically to prevent an attacker-controlled domain from being treated as a trusted Shopify host: `raise Errors::InvalidShopError ... unless host is a member of TRUSTED_SHOPIFY_DOMAINS` [7](#0-6) .

The binding that should hold is: `host that receives client_secret == a domain in ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. In `exchange_token`, that binding is never checked — the host is simply whatever string is in the JWT's `dest` claim.

### Impact Explanation
Because `HttpClient`/`Clients::Rest::Admin` build the outbound URL from `session.shop` (as seen in the two sibling flows that rely on `ShopValidator.sanitize!` for exactly this purpose), an unsanitized `dest_shop` value used as the host in `exchange_token` means the app's `client_secret` and the raw session token are POSTed to whatever host ends up in `dest`, if that value can ever diverge from a genuine myshopify host (e.g., library callers constructing/forwarding a token payload from an untrusted source, or any future/alternate token issuer whose `dest` isn't domain-constrained). This is exactly the class of "host validated versus host that receives client_secret" identity-binding gap called out as in-scope, and leakage of `client_secret` to a non-Shopify host is a Critical-impact event (credential exfiltration/theft of the app's client secret).

### Likelihood Explanation
The JWT itself is signed with the app's `api_secret_key`, so under normal circumstances only Shopify can mint valid tokens, and normal tokens' `dest` will be a real shop domain — this limits practical exploitability under the documented flow. However, the code path itself contains no defense-in-depth check that its sibling methods (`migrate_to_expiring_token`, `refresh_access_token`) explicitly implement, which is inconsistent and removes a safety net that exists everywhere else `client_secret` is sent to a shop-derived host.

### Recommendation
Sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` before constructing `shop_session` in `TokenExchange.exchange_token`, mirroring the pattern already used in `migrate_to_expiring_token` and `RefreshToken.refresh_access_token`:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```

### Proof of Concept
1. Obtain/construct a session token whose `dest` claim is not a trusted Shopify domain (e.g., `https://attacker.example`), signed with the app's secret (or via any path where `dest` is not domain-constrained before reaching this method).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `dest_shop` is used unchecked to build `shop_session`, and `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` sends the POST body containing `client_id`/`client_secret`/`subject_token` to a host derived from `attacker.example` instead of a verified myshopify domain — contrasted with `migrate_to_expiring_token`, which would reject the same input via `Utils::ShopValidator.sanitize!` [8](#0-7) .
