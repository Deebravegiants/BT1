This is a strong, concrete finding: `ClientCredentials.client_credentials`, `RefreshToken`, `TokenExchange.migrate_to_expiring_token`, and `Clients::GraphQL::Storefront` all call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` before using the caller-supplied `shop` to build the request host and attach `client_secret`, but `ShopifyAPI::Auth::Oauth.begin_auth` does not.

### Title
`Oauth.begin_auth` builds the OAuth authorize redirect host from an unsanitized `shop` parameter, unlike every other credential-sending path in the gem - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`Oauth.begin_auth` takes a caller-supplied `shop:` string and uses it directly, via `auth_base_uri(shop)`, to build the `https://#{shop}/admin/oauth/authorize` URL that the browser is redirected to. [1](#0-0) [2](#0-1)  Every other entry point in the gem that accepts a `shop` string and then builds a request host validates it first with `Utils::ShopValidator.sanitize!`: `ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`, and `Clients::GraphQL::Storefront`. [3](#0-2) [4](#0-3) 

### Finding Description
`ShopValidator.sanitize!` exists specifically to enforce the equality "the host that will receive the app's credentials/redirect must equal a trusted `*.myshopify.com`/`myshopify.io`/`spin.dev`/`shop.dev`/`shopify.com` domain," rejecting values like `attacker.example` or `myshopify.com.evil.com`. [5](#0-4) [6](#0-5) 

`begin_auth` breaks this binding: it never calls `sanitize!` on `shop` before passing it into `auth_base_uri`, which constructs `"https://#{shop}/admin"` with no domain-suffix check at all: [2](#0-1) . Since `begin_auth`'s only job is to compute the redirect target for the merchant's browser (`auth_route`), any caller that passes through a request-derived `shop` value (a very common integration pattern for multi-tenant Shopify apps, since the whole point of this method is to start OAuth for whichever shop is installing) will send the merchant's browser to `https://<attacker-controlled-string>/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=...&state=...`, disclosing the app's `client_id`, requested `scope`, and configured `redirect_uri` to a host of the attacker's choosing, and can be used to fixate the `state` nonce/session cookie against a phishing flow that later replays a crafted callback.

### Impact Explanation
This does not leak `client_secret` (that only happens in `validate_auth_callback`, which is correctly bound by `Utils::HmacValidator.validate(auth_query)` over `code/host/shop/state/timestamp`). [7](#0-6) [8](#0-7)  The concrete damage from `begin_auth` alone is: forced/attacker-initiated OAuth flow redirect to a non-Shopify host carrying the app's `client_id` and configured `redirect_uri`, and a session-fixation surface via the `state` cookie set for that attacker-chosen flow. This maps to the rubric's "session fixation or forced OAuth completion" bucket, but it stops short of Critical since no `client_secret` or access token is exposed by this function in isolation.

### Likelihood Explanation
Likelihood depends entirely on whether the host application passes an unsanitized, request-derived `shop` value into `begin_auth` — which is the normal integration pattern (the shop parameter typically comes from the install/login request). Because `sanitize!` is applied everywhere else in the gem where a caller-supplied `shop` reaches a URL/host construction, and conspicuously not here, this looks like a real gap in the gem's own defense-in-depth rather than solely a host-app misuse issue.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` at the top of `Oauth.begin_auth` (or within `auth_base_uri`) before using `shop` to build `auth_route`, mirroring `ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", host: "https://app.example.com", ...)

result = ShopifyAPI::Auth::Oauth.begin_auth(
  shop: "attacker.example",   # not sanitized anywhere in begin_auth
  redirect_path: "/auth/callback",
)
# result[:auth_route] == "https://attacker.example/admin/oauth/authorize?client_id=key&scope=...&redirect_uri=https://app.example.com/auth/callback&state=...&grant_options%5B%5D=per-user"
```

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end
