## Title
Block-count reward accounting in `pallet-consensus-incentives` lets relayers extract disproportionate treasury payouts from state machines with variable/bursty block production - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives` pays relayers for delivering `ConsensusMessage`s using a strictly block-count-based formula, `Reward = (LatestHeight - PreviousHeight) * CostPerBlock` [1](#0-0)  implemented in `calculate_reward` [2](#0-1) . This is the same bug class as the referenced report: a value transfer is computed from a raw block-height delta rather than elapsed wall-clock time, on the (implicit) assumption that the tracked chain produces blocks at a roughly constant rate. `CostPerBlock` is configured per state machine by governance [3](#0-2)  presumably calibrated against that chain's nominal block time — but nothing in the reward path checks or bounds the real time that elapsed between `PreviousHeight` and `LatestHeight`.

### Finding Description
`process_message` is invoked from the `FeeHandler::on_executed` hook whenever a `ConsensusMessage` is processed by `pallet-ismp`'s `handle_unsigned` extrinsic — a permissionless, unsigned entry point reachable by anyone who can construct a valid consensus proof for the tracked counterparty chain [4](#0-3) . The reward is:

```rust
let blocks = latest_height.saturating_sub(baseline);
let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
let reward = blocks_as_balance.saturating_mul(block_cost);
``` [5](#0-4) 

This payout is transferred unconditionally from `TreasuryAccount` to the relayer [6](#0-5) , scaled purely by the number of new heights a single consensus proof advances the light client to. For any state machine whose block production is not fixed-rate — the exact condition the external report flags for Optimism-style chains ("each transaction … is placed in a separate block and blocks are NOT produced at a constant rate") — the number of blocks produced in a given real-time window is not predictable or bounded. A relayer needs to submit exactly one valid `ConsensusMessage`/proof to claim the reward for however many heights that proof advances the commitment to; the pallet does nothing to correlate `blocks` with the real duration or "work" the light client maintenance actually represents. If the counterparty chain experiences a burst of block production (batched blocks after congestion, an L2 producing one block per transaction under load, or simply a chain not calibrated to the `CostPerBlock` assumption), the relayer is paid for the full height jump from a single submission, disproportionate to the cost/value `CostPerBlock` was set to compensate.

### Impact Explanation
This directly drains the `TreasuryAccount` [7](#0-6)  — an unbacked/over-generous minting of value relative to the actual service rendered, reachable by any permissionless relayer submitting a single `ConsensusMessage` covering an unusually large or bursty block range. Because the watermark (`LastRewardedHeight`) only advances forward and pays for the full unpaid span in one shot [8](#0-7) , a relayer can wait for (or simply happen upon) periods of variable/rapid block production on the tracked chain and collect proportionally amplified rewards for delivering the same single proof they would have submitted anyway.

### Likelihood Explanation
Likelihood is Medium and, as the judge noted for the original report, contingent on configuration: it only materializes for state machines whose block production is not fixed-rate (variable-interval L2s, chains that can batch-produce blocks, or any chain where `CostPerBlock` was calibrated under a constant-block-time assumption that does not hold). Given Hyperbridge explicitly supports and already special-cases irregular L2 block semantics elsewhere in the codebase (e.g., the Arbitrum `ArbSys` workaround in `IntentsBase._blockNumber()` [9](#0-8) ), it is plausible that consensus-tracked chains with similar irregularities are or will be configured with `StateMachinesCostPerBlock` entries.

### Recommendation
Bound or scale the reward by elapsed real time (e.g., using the source chain's block timestamps recovered from the consensus proof, or the host's own timestamp at commitment time) rather than raw height delta, or cap the per-submission reward independent of how many heights a single proof advances, so payout tracks actual maintenance cost/time rather than a block count that can vary unpredictably on the tracked chain.

### Proof of Concept
1. Governance sets `StateMachinesCostPerBlock` for a state machine `X` whose block production is bursty/variable (analogous to Optimism's non-constant block interval) via `update_cost_per_block` [3](#0-2) .
2. A relayer waits until chain `X` has produced an unusually large number of blocks in a short real-time window (or triggers/observes this naturally), then submits a single valid `ConsensusMessage` advancing the on-chain light client from `PreviousHeight` to the new `LatestHeight` via the permissionless `handle_unsigned` path.
3. `process_message`/`calculate_reward` computes `blocks = latest_height - baseline` and pays `blocks * CostPerBlock` from the treasury in one transfer [5](#0-4) , disproportionate to the real time/effort the single proof submission represents, draining the treasury faster than the `CostPerBlock` rate was calibrated for.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}

			state_machine_id: StateMachineId,
			cost_per_block: <T as pallet_ismp::Config>::Balance,
		) -> DispatchResult {

			StateMachinesCostPerBlock::<T>::mutate(state_machine_id.clone(), |maybe_cost| {
				*maybe_cost = Some(cost_per_block);
			});

			Self::deposit_event(Event::<T>::StateMachineCostPerBlockUpdated {
				state_machine_id,
				cost_per_block,
			});

			Ok(())
		}

    /**
     * @dev Returns the current block number of the host chain. Order deadlines are
     * denominated in the block heights Hyperbridge tracks for each state machine —
     * for Arbitrum chains that is the L2 block number, but the `block.number` opcode
     * there returns the approximate L1 block number, so the ArbSys precompile is
     * queried instead. The chain id check keeps the bytecode identical across all
     * chains, preserving the deterministic CREATE2 deployment addresses.
     * @return The chain-appropriate current block number.
     */
    function _blockNumber() internal view returns (uint256) {
        if (block.chainid == ARBITRUM_ONE || block.chainid == ARBITRUM_NOVA || block.chainid == ARBITRUM_SEPOLIA) {
            return IArbSys(ARB_SYS).arbBlockNumber();
        }
        return block.number;
    }
