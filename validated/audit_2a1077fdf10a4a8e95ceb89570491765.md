### Title
Webhook shop identity spoofing via HMAC-unbound `shop-domain` header enables cross-tenant webhook injection - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The webhook signature validation in this gem only binds the raw request body to the HMAC. The `shop` (and `topic`/`webhook-id`/`api-version`) values that are extracted from HTTP headers and handed to the app's webhook handler as the tenant identifier are never included in the signed material, so an attacker who can obtain one validly-signed webhook payload (e.g. by triggering it in a shop they control) can relabel it as belonging to any other shop using the same app, and the signature will still verify.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines the bytes that are HMAC-verified as only the raw body: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from attacker-controlled HTTP headers, independent of the signed payload: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop` as the tenant identity for the handler: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the raw body) and the app's `api_secret_key`: [4](#0-3) 

The identity binding that should hold is:
`shop header used by handler == shop that produced the signed bytes`

Because the `shop-domain` header (and topic/webhook-id/api-version) is excluded from `to_signable_string`, this equality is never enforced. Since a single app's `api_secret_key` is shared across every shop that installs the app, any legitimately signed `(raw_body, hmac)` pair generated for one shop remains valid when replayed with a different `x-shopify-shop-domain` header value, because the check in `HmacValidator.validate_signature` only compares the computed signature of the body to the received one — it never checks that the claimed shop matches the shop that produced the body.

### Impact Explanation
An attacker who operates their own shop installed on a shared/multi-tenant app can:
1. Trigger a real webhook event in their own shop (fully controlling body content, e.g. by crafting a resource with attacker-chosen fields).
2. Capture the resulting valid `(raw_body, x-shopify-hmac-sha256)` pair — this requires no secret, just receiving/replaying their own app's webhook traffic.
3. Replay the same body/HMAC to the app's webhook endpoint with the `x-shopify-shop-domain` header (or `shopify-shop-domain`) changed to a victim shop that also uses the app.
4. `HmacValidator.validate` still succeeds because the header is not covered by the signature, and `Registry.process` calls the handler with `shop: <victim-shop>` alongside attacker-controlled body content.

This lets an unprivileged app user (merchant on their own store) inject data that the host application will process as belonging to another tenant (cross-tenant data confusion/injection), matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high in any app that: (a) serves multiple shops with a single `api_secret_key` (the normal Shopify app model), and (b) uses the webhook `shop` value returned by `Request#shop`/`WebhookMetadata#shop` for tenant-scoped side effects (which is the documented usage pattern in `docs/usage/webhooks.md`). The attacker only needs their own shop's install of the app — no credentials, tokens, or secrets of the target shop are required.

### Recommendation
Bind the trusted headers to the signed material, or otherwise cryptographically tie the claimed shop to the payload before dispatching to handlers:
- Include `shop`, `topic`, `webhook_id`, and `api_version` (at minimum `shop`) in the value returned by `to_signable_string`, matching what Shopify actually signs, or
- Require callers/handlers to cross-validate `request.shop` against the shop associated with the currently active/expected session or registration before trusting it, and reject processing if the webhook's claimed shop was not the one it was registered for.
- Document explicitly in `ShopifyAPI::Webhooks::Registry.process` that `shop` is unauthenticated header data and must be independently validated by the host application against the expected tenant, or add a required expected-shop parameter to `process` that is compared against `request.shop`.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both sharing the app's `api_secret_key`.
2. Attacker triggers a real webhook (e.g. `orders/create`) on `attacker-shop.myshopify.com` with attacker-chosen order fields, and captures the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker POSTs to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which equals `H`, so validation passes.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, causing the host app to act on attacker data as if it were legitimately reported by `victim-shop`.
