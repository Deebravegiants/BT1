### Title
Unbounded GRANDPA justification precommit/ancestry verification in the free, unsigned `pallet-ismp::handle_unsigned` path enables a validate_unsigned resource-exhaustion DoS — (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
The Connect2id JOSE+JWT bug (CVE-2023-52428) lets an attacker set an unbounded PBKDF2 iteration count (`p2c`) that the verifier must chew through before rejecting the message, at effectively no cost to the attacker. Hyperbridge has an analogous shape: `pallet-ismp`'s `handle_unsigned` extrinsic is validated for free, by every full node, on every submission to the transaction pool (and on re-validation), and its `validate_unsigned` implementation runs the *entire* message-execution path — including full GRANDPA justification verification — before deciding whether to reject the transaction. The number of precommit signatures and ancestry headers inside a `GrandpaJustification` is attacker-controlled and is not bounded before the expensive per-item work (ed25519 verification, ancestry-route walking) is performed.

### Finding Description
`pallet_ismp::Pallet::validate_unsigned` calls `Self::execute(messages.clone())` directly to decide transaction validity: [1](#0-0) 

`execute` runs `handle_incoming_message` for every message in the batch, which for a `ConsensusMessage` ultimately reaches `verify_grandpa_finality_proof`: [2](#0-1) 

`verify_grandpa_finality_proof` decodes the attacker-supplied `GrandpaJustification` and calls `justification.verify(...)`, which:
- Iterates `self.commit.precommits` and calls `check_message_signature` (an `ed25519_verify`) for **every** precommit, with no upper bound on the number of precommits in the message.
- For every precommit whose target isn't the base, it walks an ancestry route through `votes_ancestries` (also attacker-supplied, unbounded). [3](#0-2) [4](#0-3) 

None of this work is gated by a size cap on `commit.precommits` or `votes_ancestries` prior to being executed — the message is simply SCALE-decoded and handed to the verifier. Because this all happens inside `validate_unsigned`, it is executed by **every node's mempool** for **every submission and every re-validation**, and — being unsigned — it costs the attacker no fee at all. This mirrors the JOSE+JWT flaw precisely: an attacker-controlled "count" parameter (here, number of precommits/ancestry headers, there, PBKDF2 iterations) drives unbounded verifier work performed before the request is ultimately rejected as invalid, and this work is cheap to trigger repeatedly.

### Impact Explanation
Because `handle_unsigned` transactions are free (no tip/fee) and are validated by all full nodes in the network before being gossiped, an attacker can repeatedly submit crafted `Message::Consensus(ConsensusMessage::StandaloneChain(...))` payloads containing GRANDPA justifications padded with a very large number of precommits and/or `votes_ancestries` headers (up to the extrinsic/block length limit). Every node processing the transaction pool must perform an ed25519 signature check per precommit and an ancestry walk per header before rejecting the (ultimately invalid) justification. Submitted continuously and in parallel by multiple accounts (unsigned transactions have no account-based rate limiting), this can degrade block production and honest transaction propagation network-wide — a resource-consumption Denial of Service consistent with CWE-400/CWE-770, matching the High severity/AV:N/AC:L/PR:N/UI:N profile of the reference CVE.

### Likelihood Explanation
Likelihood is high: the path is reachable by any unprivileged party submitting an unsigned extrinsic (`ensure_none(origin)`), requires no proof of prior validity, no stake, and no fee. The only constraint is the runtime's maximum extrinsic/block size, which still permits a substantial number of 100+-byte precommit/header entries per submission, and the attack can be repeated continuously across many transactions and validators.

### Recommendation
- Bound `GrandpaJustification::commit.precommits.len()` and `votes_ancestries.len()` against the known/expected authority-set size (or a fixed protocol maximum) before doing any per-item cryptographic verification, rejecting oversized justifications immediately.
- Consider moving expensive signature verification in `validate_unsigned` behind lighter, cheaper pre-checks (e.g., structural/size checks) so that oversized or malformed payloads are rejected before ed25519 verification and ancestry-chain construction are performed.
- Apply a per-source-account or per-IP rate limit / minimum priority requirement in the transaction pool for unsigned ISMP consensus messages to reduce the value of repeated free submissions.

### Proof of Concept
1. Craft a `Message::Consensus(ConsensusMessage::StandaloneChain(...))` whose `finality_proof.justification` is a SCALE-encoded `GrandpaJustification` with `commit.precommits` populated with, e.g., tens of thousands of syntactically valid but cryptographically bogus `(precommit, id, signature)` triples (fabricated `AuthorityId`/`AuthoritySignature` bytes — decoding only requires correct byte lengths, not valid keys), and `votes_ancestries` populated with a large number of dummy headers up to the block-length limit.
2. Submit this as `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(...)] }` as an unsigned extrinsic.
3. Observe that `validate_unsigned` invokes `execute` → `verify_grandpa_finality_proof` → `justification.verify`, which performs an `ed25519_verify` for every fabricated precommit and an ancestry walk over every ancestry header before ultimately returning an error (e.g., `Error::JustificationVerify`) — the entire cost is paid before rejection, and the submission costs the attacker nothing since it's unsigned.
4. Repeating this submission across many nodes concurrently consumes CPU for every node performing mempool validation, without ever needing a valid consensus state or justification.

Note: I could not fully verify from the indexed code whether `pallet-ismp`'s `#[pallet::weight(weight())]` function or the runtime's `BlockLength`/extrinsic-size configuration impose any additional cap on the number of precommits/headers that could fit in a single submission; this would affect the practical scale of the attack and should be confirmed directly in the runtime configuration before remediation prioritization.

/// Check a message signature by encoding the message and verifying the provided signature using the
/// expected authority id.
pub fn check_message_signature<H, N>(
	message: &finality_grandpa::Message<H, N>,
	id: &AuthorityId,
	signature: &AuthoritySignature,
	round: RoundNumber,
	set_id: SetId,
) -> Result<(), anyhow::Error>
where
	H: Encode,
	N: Encode,
{
	let buf = (message, round, set_id).encode();

	let valid =
		sp_io::crypto::ed25519_verify(&signature.clone().into(), buf.as_ref(), &id.clone().into());

	if !valid {
		Err(anyhow!("invalid signature for precommit in grandpa justification"))?
	}

	Ok(())
}
