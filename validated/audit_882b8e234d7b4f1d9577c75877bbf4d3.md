### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC verification performed by `Utils::HmacValidator.validate` in `Webhooks::Registry.process` authenticates the *body bytes* only. The `shop` (`shopify-shop-domain`), `topic`, `webhook-id`, and `api-version` values are parsed straight from unauthenticated HTTP headers and are then handed to the host app's `WebhookHandler#handle` as `WebhookMetadata#shop`, which the documented usage explicitly instructs apps to trust as the tenant identifier (`shop_domain: data.shop`). This breaks the identity binding `authenticated_bytes == acted_upon_shop`.

### Finding Description
`Request#hmac` is computed from the `hmac-sha256` header, and `Request#to_signable_string` returns `@raw_body` only: [7](#0-6) [2](#0-1) 

`HmacValidator.validate_signature` recomputes `HMAC(secret, to_signable_string)` and compares it to the received signature — again, body-only: [4](#0-3) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from headers with zero cryptographic binding to that signature: [8](#0-7) 

`Registry.process` uses `request.shop` as the authoritative tenant identity forwarded to the app: [3](#0-2) 

Since HMAC-SHA256 for a given topic body is deterministic given the shared `api_secret_key`, and Shopify sends *the same body content* for identical resource states/events across different shops sharing the same app, an unprivileged internet user who controls their own shop installation of the app (a normal, unprivileged merchant relationship — no special credential needed beyond installing the public app) can:
1. Trigger/capture one legitimate webhook delivery to their own endpoint (a valid `raw_body` + `hmac-sha256` pair, signed by Shopify using the app's `client_secret`).
2. Replay that exact `raw_body`/`hmac-sha256` pair to the app's shared webhook endpoint while substituting the `shopify-shop-domain`, `shopify-webhook-id`, and `shopify-topic` headers to reference a **different, victim** shop that also installed the app.
3. `HmacValidator.validate` succeeds (body+hmac still match, since neither the shop header nor topic header participate in the signature), and `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker's captured body, ...)` to the app's handler.

The app, following the library's own documented contract that `data.shop` identifies "The shop domain of the webhook", will process attacker-supplied body content under the victim's tenant scope — e.g., writing attacker-chosen order/product/customer data into the victim's tenant records, since the gem provides no mechanism (nor documents any need) to cross-check `shop` against the HMAC.

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate (but unprivileged) installer of the app for their own store can inject arbitrary attacker-controlled webhook payloads that are processed as belonging to a completely different merchant's shop, without needing that merchant's credentials, access token, or client secret. This matches the Critical "cross-tenant access" impact category, since typical webhook handlers key their data writes and side effects by `data.shop`.

### Likelihood Explanation
Likelihood is high in any deployment that follows the gem's documented usage pattern (`shop_domain: data.shop`) to scope webhook processing per tenant, since that is the exact pattern shown in `docs/usage/webhooks.md`. Any app using a shared webhook endpoint for all installed shops (the standard/only supported model in this gem) is affected. The attacker only needs their own (attacker-owned) shop to be installed with the target app to capture a validly-signed body/hmac pair; no secrets or victim access are required.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material verified against the HMAC, or otherwise require the application to independently prove that the `shop` header corresponds to a shop that legitimately received *that* `webhook_id`/body combination (e.g., cross-check the webhook_id against Shopify's API scoped to that shop's stored access token before trusting `data.shop`, or document this as a mandatory app-side responsibility). At minimum, `Utils::HmacValidator` and `Webhooks::Request#to_signable_string` should be reviewed so that the identity fields the app is instructed to trust (`shop`, `topic`, `webhook_id`) cannot be swapped independently of the HMAC-covered payload.

### Proof of Concept
1. App `A` is installed on both `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing one webhook endpoint per the gem's documented single-registry pattern.
2. Attacker triggers a webhook event on their own shop (e.g., `products/update`), causing Shopify to POST a body `B` with header `x-shopify-hmac-sha256: H` (valid, since `H = HMAC(secret, B)`) and `x-shopify-shop-domain: attacker-shop.myshopify.com` to the app's endpoint.
3. Attacker replays the exact same body `B` and header `H` to the same endpoint, but rewrites `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a fresh `x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B) == H`, per `lib/shopify_api/webhooks/request.rb` lines 35-38 and `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
5. The registered handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)` and processes attacker-controlled data `B` under the victim's tenant scope.
