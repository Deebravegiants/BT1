### Title
Webhook Tenant Identity (`shop-domain` Header) Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw HTTP body [3](#0-2) . The `shop` value that is trusted and forwarded to the app's handler as the tenant identity comes from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signed content.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only `@raw_body`: [4](#0-3) 

The `shop` accessor is read straight from a header with no cryptographic binding to the HMAC: [5](#0-4) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the received `hmac` value: [6](#0-5) 

`Registry.process` then trusts `request.shop` unconditionally as soon as the (body-only) HMAC check passes, and hands it to the app's handler as the tenant identity for the event: [3](#0-2) 

This breaks the intended binding `shop-header == shop-that-produced-this-signed-payload`. Because `api_secret_key` is shared across **all** shops/tenants that install a given app (it is not per-shop), any party who can obtain one valid `(raw_body, hmac)` pair signed by the app's secret — for example, by installing the app on a shop they control and capturing an outgoing webhook delivery (Shopify's admin exposes recent webhook delivery details, including headers/body, for troubleshooting) — can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. The HMAC check still passes (it never inspected the header), and the app processes the payload as if it originated from the victim shop named in the forged header.

### Impact Explanation
This is a cross-tenant confusion/injection vector: an attacker can make the app believe arbitrary webhook data (of a topic/body shape they control) came from any target shop domain, including shops they have never had legitimate access to. Depending on the app's handler logic (as documented, apps enqueue jobs keyed by `data.shop`, e.g. `perform_later(topic:, shop_domain: data.shop, webhook:)` [7](#0-6) ), this can be leveraged to inject fabricated events attributed to a victim tenant, or trigger sensitive mandatory-topic handling (`app/uninstalled`, `shop/redact`, `customers/redact`) [8](#0-7)  against a shop the attacker does not control, causing unauthorized state changes (e.g. wiping/deactivating a victim shop's stored session/data) — a cross-tenant impact.

### Likelihood Explanation
Requires the attacker to obtain one valid `(body, hmac)` pair produced under the target app's secret (trivial if the attacker installs the app on their own shop, since the same `api_secret_key` signs every tenant's webhooks) and the ability to POST directly to the app's public webhook endpoint, which is internet-reachable by design. No access token, `api_secret_key`, or privileged account is required — only unprivileged use of the app as an ordinary merchant/installer plus a forged HTTP request.

### Recommendation
Bind the tenant identity into the verified content: either include the `shop` (and other trust-relevant headers) in the HMAC-signed material, or cross-check `request.shop` against a shop that is known to have actually installed/authorized the app (e.g. verifying an existing, previously-established session/access-token record for that shop) before dispatching to the handler, rather than trusting the header value outright once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (legitimate, unprivileged action).
2. Attacker triggers an event covered by a registered webhook topic (e.g. `products/update`), causing Shopify to POST `raw_body` + `X-Shopify-Hmac-Sha256` to the app's public webhook endpoint. Attacker recovers this `(raw_body, hmac)` pair (e.g. via Shopify's webhook delivery detail view, or a debugging proxy they control on their own server).
3. Attacker crafts a new HTTP POST to the same app endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` accepts the forged headers (they are only checked for presence) [9](#0-8) ; `HmacValidator.validate` succeeds because it only recomputes the HMAC over `raw_body`, which is unchanged [4](#0-3) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` [10](#0-9) , causing the app to act on attacker-controlled data under the victim shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
