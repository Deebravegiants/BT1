### Title
Webhook `shop` domain is not covered by the HMAC signature verified by `Registry.process`, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler, but the underlying HMAC check only authenticates the raw request body — never the `shop-domain` header that is handed to the handler as the trusted tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from HTTP headers, completely outside the signed payload: [2](#0-1) 

`Registry.process` validates only this body-only HMAC and then immediately trusts `request.shop` (and the other unauthenticated header fields) when constructing the metadata passed to the app's webhook handler: [3](#0-2) 

The `HmacValidator.validate` call that gates this only recomputes the signature over `to_signable_string` (i.e. the raw body) and secure-compares it to the `hmac` header — `shop` never enters the computation: [4](#0-3) 

The gem's own documentation asserts a stronger guarantee than what is actually enforced: it tells integrators that calling `Registry.process` "will verify the request did indeed come from Shopify and then call the specified handler," implying the entire `WebhookMetadata` (including `shop`) is authenticated: [5](#0-4) 
and that handlers should treat `data.shop` as "The shop domain of the webhook" without further caveat: [6](#0-5) 

This breaks the identity binding: `shop header used by handler == shop bound by HMAC` is false. Any bytes with a valid HMAC for the body (i.e., any genuinely-signed webhook the attacker has ever received, e.g. for their own shop after installing the app) can be replayed with an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header, and `Registry.process` will accept it and hand the attacker-chosen `shop` value to the app's handler as if Shopify had asserted it.

### Impact Explanation
An unprivileged user who can install the app on their own store (any merchant can do this) receives genuinely-signed webhooks for their own shop. By replaying that exact body/HMAC pair to the app's public webhook endpoint while substituting a victim shop's domain in the `shop-domain` header, they cause the library to deliver `WebhookMetadata` claiming the event belongs to the victim shop. Because the library documents this as verified/authentic, downstream app logic that keys per-tenant state, records, or side effects off `data.shop` (exactly as the docs' own example does: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be tricked into attributing attacker-controlled webhook content to another tenant — a cross-tenant confusion/access primitive rooted entirely in this gem's verification contract.

### Likelihood Explanation
High: any app that installs the gem and follows the documented `Registry.process` usage is affected. The only prerequisite is that the attacker obtain one validly-signed webhook body+HMAC pair for any topic they can trigger on their own shop (trivial — install the app, perform the action that triggers the webhook, capture the request), then resend it with a forged shop header. No access to `api_secret_key`, access tokens, or any Shopify-side credential is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified against the HMAC — e.g., require the caller/library to compare `request.shop` against a shop known to have an active session/subscription for that specific `webhook_id`/registration before dispatching to the handler, or clearly amend the documentation to state that `Registry.process` only authenticates body integrity, not the shop attribution, and that callers must independently verify `data.shop` against their own installed-shop registry before trusting it.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger a subscribed webhook topic (e.g. `orders/create`) so Shopify delivers a genuine POST with a valid `x-shopify-hmac-sha256` for the raw body.
2. Capture the raw body and the `x-shopify-hmac-sha256` header value.
3. Resend the identical raw body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because the raw body (the only signed content) is unchanged: [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim-shop.myshopify.com`, even though Shopify never asserted this shop for this payload: [8](#0-7)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          received_signature = verifiable_query.hmac

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
