### Title
Disabled overfill circuit breaker lets a manipulated/stale price extract unbounded payout from a solver's IntentGateway fill - (File: `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
The reference solver (`FXFiller`) that fills Hyperbridge `IntentGateway`/`IntrinsicIntents` orders contains an "overfill protection" circuit breaker that is supposed to cap the payout it sends to an order's beneficiary and halt the strategy after repeated abnormal pricing events. Both halves of this circuit breaker are effectively no-ops: the payout clamp is never applied and the halt trigger is never armed, so a solver running this code will pay out whatever a corrupted/manipulated price computation produces, with no in-transaction limit and no automatic shutdown — the same class of defect as the SDA bond market's circuit breaker that lets a taker extract funds before the market closes.

### Finding Description
`FXFiller.calculateProfitability` computes `rawPolicyMaxOutput` for each leg and an `overfillCeiling = output.amount * (1 + maxOverfillBps) / 10000`, intended to bound the payout to at most `maxOverfillBps` above the user-requested amount: [1](#0-0) 

However the code that follows the warning simply reassigns `policyMaxOutput = rawPolicyMaxOutput` unconditionally — the "clamp" never reduces the output — and this is confirmed as intentional/known in the repo's own design-decision note: [2](#0-1) 

The second half of the breaker — halting the strategy after `maxConsecutiveClamps` consecutive overfill events — is likewise dormant, because `recordOrderOutcome` is documented as "always called with `false`": [3](#0-2) 

The unclamped `targetOutput = policyMaxOutput` is then paid directly to the order's beneficiary via wallet balance and funding-venue withdrawals, and this exact amount is what gets transferred in `fillOrder`/`_fillSameChain` on `IntrinsicIntents.sol`: [4](#0-3) [5](#0-4) 

This mirrors the audited bond-market bug precisely: a protective threshold check exists in the code path (`overfillCeiling`, `maxOverfillBps`, `maxConsecutiveClamps`), but breaching it neither reduces the current payout nor stops future fills before further loss accrues — the guard only logs a warning after the fact, just as the SDA circuit breaker only closed the market after the over-limit transaction had already completed.

### Impact Explanation
`FXFiller` supports venue-priced pairs sourced from Uniswap V4 pools (`venuePriced`), plus offline curves that can be stale or bugged. Any transient mispricing — a manipulated/thin V4 pool, a stale cached rate, or a pricing bug — inflates `rawPolicyMaxOutput` for a leg. Because the clamp is a no-op, the solver will pay the beneficiary of an intent order the full inflated amount out of its own wallet/funding venues, with no per-transaction ceiling. Because the halt is also dormant, the same exploit can be repeated across consecutive orders without the strategy ever stopping itself, unlike the documented intended behavior. The result is unbounded loss of the solver's payout-token treasury to whichever party can influence pricing for a leg, which is directly analogous to the market maker's loss in the referenced bond report, just realized against Hyperbridge's intent-solver economics rather than a bond SDA market.

### Likelihood Explanation
The vulnerable code path executes on every order evaluation/fill (`calculateProfitability` → `executeOrder`) for any `TradingPair` configured with `venuePriced` pricing or any curve, so it is reached whenever the solver receives an intent order — something any unprivileged user can create by dispatching an order through `IntentGateway`. No special privilege beyond running the standard reference filler is needed for the solver, and no privilege at all is needed for the counterparty/attacker who only needs to move the referenced price source (e.g., a flash-loan pump/dump on the V4 pool backing a `venuePriced` pair, or trigger any stale-cache condition) before an order is evaluated. The repository's own design note explicitly flags this as a known, currently-inert safety mechanism (not merely a hypothetical), which raises confidence that this is a live gap rather than a documentation artifact.

### Recommendation
- Re-enable the payout clamp: cap `policyMaxOutput` to `overfillCeiling` (or otherwise bound total exposure) before it is used as `targetOutput`, so a single fill cannot exceed the configured `maxOverfillBps` regardless of the pricing source.
- Restore `recordOrderOutcome(clamped, orderId)` to be invoked with the true clamped state so the `maxConsecutiveClamps` halt subsystem actually engages when overfill triggers repeatedly, stopping further loss before it compounds — mirroring the SDA report's recommendation to only allow execution up to the safe limit and then close/halt rather than after the fact.
- If unclamped overfill is intentionally desired for competitiveness on legitimate curves, gate it separately from venue-sourced (manipulable) pricing, and keep a hard ceiling specifically for `venuePriced` legs where external manipulation is possible.

### Proof of Concept
1. Configure/operate an `FXFiller` pair as `venuePriced` (sourced from a Uniswap V4 pool) per `TradingPair`/`FundingVenue` wiring in `sdk/packages/simplex/src/strategies/fx.ts`.
2. An attacker manipulates the referenced V4 pool's spot price transiently (e.g., via a large swap financed by a flash loan) so that `rawPolicyMaxOutput` computed for a pending intent order is far above the legitimate/expected rate — beyond `overfillCeiling`.
3. Submit (or have already submitted) an `IntentGateway` order whose beneficiary is the attacker, requesting the manipulated-pair's output token.
4. `FXFiller.calculateProfitability`/`executeOrder` computes the inflated `policyMaxOutput`, logs the "Overfill ceiling exceeded — clamp disabled, filling unclamped amount" warning (`sdk/packages/simplex/src/strategies/fx.ts:686-701`), but does not reduce `targetOutput`.
5. The solver fills the order via `IntrinsicIntents.sol`'s `_fillSameChain`/cross-chain fill path, transferring the full inflated `targetOutput` to the attacker's beneficiary address, before the pool price reverts back — extracting value from the solver with no in-transaction cap and no automatic halt for subsequent repeats.

	private recordOrderOutcome(clamped: boolean, orderId: string | undefined) {
		if (clamped) {
			this.consecutiveClamps += 1
			if (this.consecutiveClamps >= this.maxConsecutiveClamps) {
				this.halted = true
				this.logger.error(
					{ orderId, consecutiveClamps: this.consecutiveClamps, maxConsecutiveClamps: this.maxConsecutiveClamps },
					"FXFiller HALTED — venue-priced overfill clamp triggered consecutively; restart required after investigation",
				)
			}
		} else {
			this.consecutiveClamps = 0
		}
	}

	public isHalted(): boolean {
		return this.halted
	}
