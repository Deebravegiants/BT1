### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, excluding the `shop-domain`/`x-shopify-shop-domain` header. `HmacValidator` and `Registry.process` only verify that signature, then trust the unauthenticated `shop` header value to build `WebhookMetadata` that the host app uses as the tenant identifier. Because Shopify webhook signatures are computed with the app's single shared `client_secret` (identical for every shop that installs the app), any tenant that has installed the app can obtain a validly signed request body and replay it to the app's public webhook endpoint with an arbitrary shop-domain header, spoofing another tenant's webhook.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator` computes/verifies the signature exclusively over `to_signable_string`: [2](#0-1) 

`Request#shop` is read straight from an HTTP header that is never part of the signed material: [3](#0-2) 

`Registry.process` gates acceptance solely on `HmacValidator.validate(request)`, then forwards the attacker-controlled `request.shop` value verbatim into `WebhookMetadata`, which is the tenant-identifying field handed to the host app's handler: [4](#0-3) 

The equality that should hold is: `shop bound by HMAC == shop delivered to handler`. In this implementation that equality is broken — `shop` is parsed from headers but never verified. Since Shopify webhook signatures use one `client_secret` per app (not per shop), the signature by itself does not bind the request to a specific tenant; it only proves "some install of this app produced this exact body." Any shop that installs the app can therefore generate a body+HMAC pair (e.g. by controlling attacker-influenced content fields sent to Shopify, or simply capturing a real webhook delivery for a chosen event) and then send a forged HTTP request straight to the app's public webhook endpoint, substituting a different shop's domain in the header while keeping the same body/HMAC.

### Impact Explanation
This crosses the tenant boundary the library is meant to enforce: `WebhookMetadata#shop` (constructed here) is the field host applications are documented and expected to use to scope persistence, business logic, notifications, etc. An attacker-controlled tenant can inject arbitrary (Shopify-schema-valid) webhook payloads that get attributed to a victim shop, corrupting or manipulating another merchant's data/state — this is a cross-tenant access impact.

### Likelihood Explanation
Reachable by any unprivileged internet user who can install the app on their own store (a normal, unprivileged action for any public/multi-tenant Shopify app) and can reach the app's public webhook endpoint (a requirement of Shopify webhook delivery, so it is always internet-reachable). No access token, `client_secret`, or privileged account is required — only the ability to install the app as a low-privilege third party and to send an HTTP POST with attacker-chosen headers to the app's known webhook route.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified material, or cross-check the header `shop` against the shop the request was actually routed for/known to be associated with (e.g., validate the shop domain via `Utils::ShopValidator` and, where possible, verify it against session/install records) before constructing `WebhookMetadata` and dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, obtaining a live app installation that shares the same app-level `client_secret` as every other install.
2. Attacker triggers (or crafts, where the body content is attacker-influenced, e.g. product/order fields) a webhook delivery with body `B`, and captures the resulting valid `x-shopify-hmac-sha256` value `H` computed by Shopify using the shared `client_secret` — this can be done because HMAC only covers `B`:
`lib/shopify_api/webhooks/request.rb:36-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`.
3. Attacker sends a direct HTTP POST to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (still valid, since it only signs `B`), but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B`/`H` (`lib/shopify_api/webhooks/registry.rb:189-190`), then builds `WebhookMetadata.new(... shop: request.shop ...)` using the spoofed `victim.myshopify.com` value (`lib/shopify_api/webhooks/registry.rb:198-199`), and dispatches to the app's handler as if it were a legitimate webhook from the victim shop.
