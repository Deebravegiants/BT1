## Finding

### Title
Permanent DoS/fund-freeze via hard revert in `calc_take_pnl`'s k-invariant check when decimal-normalization rounding drifts the PnL checkpoint above the real pool reserves - (File: `program/src/processor.rs`)

### Summary
The Hats report shows how a math helper (`computeCvgExpected`'s `ln` branch) can be driven into an unrepresentable/negative state by attacker-influenced inputs, causing a hard `revert` that permanently blocks the higher-level `deposit`/`getBondView` flows until an external condition (`totalOutToken`) changes. The structurally analogous defect in this AMM is `Processor::calc_take_pnl`, which performs an unconditional invariant check and returns a hard `Err` (program panic-equivalent for a Solana instruction) whenever the recorded PnL checkpoint appears larger than the live pool reserves — a condition that legitimate decimal-normalization rounding can trigger without any external validator or privileged actor involved.

### Finding Description
`calc_take_pnl` enforces:
```
if pool_pc_amount.checked_mul(pool_coin_amount).unwrap()
    >= (calc_pc_amount).checked_mul(calc_coin_amount).unwrap()
{ ... compute pnl ... }
else {
    return Err(AmmError::CalcPnlError.into());
}
``` [1](#0-0) [2](#0-1) 

`calc_pc_amount`/`calc_coin_amount` are derived by round-tripping the previously stored checkpoint (`target.calc_pnl_x`, `target.calc_pnl_y`) through `Calculator::restore_decimal`, and the live reserves are normalized through `Calculator::normalize_decimal_v2` before being compared/stored back as the new checkpoint: [3](#0-2) 

Both conversions perform **floor** integer division (`checked_div` with truncation, no rounding-up compensation), so every deposit/withdraw round-trip can lose a small amount of precision. `calc_take_pnl` is invoked unconditionally on every `Deposit`, `Withdraw`, and `WithdrawPnl` instruction: [4](#0-3) [5](#0-4) [6](#0-5) 

An unprivileged LP can freely choose `Deposit`/`Withdraw` amounts (`base_side`, `max_coin_amount`, `max_pc_amount`) across many small, back-to-back deposit/withdraw cycles. Because `exchange_coin_to_pc`/`exchange_pc_to_coin` round up on deposit while `exchange_pool_to_token` rounds down on withdraw, and `calc_pnl_x`/`calc_pnl_y` are only re-derived from these truncated intermediate values (never re-synced against ground truth), the recorded checkpoint can be nudged to sit slightly above the actual current reserve product without any swap fee ever being collected to justify it. Once `calc_pc_amount * calc_coin_amount` exceeds `pool_pc_amount * pool_coin_amount`, the `else` branch fires and `calc_take_pnl` returns `AmmError::CalcPnlError` permanently — every subsequent `Deposit`, `Withdraw`, and `WithdrawPnl` on that pool reverts, because the checkpoint that caused the failure is never corrected by any of those same instructions (they all abort before they can write a new checkpoint).

### Impact Explanation
This is not merely a transient revert: once the checkpoint drifts above the live reserve product, **every path that could otherwise fix it (`Deposit`, `Withdraw`, `WithdrawPnl`) is itself gated by the same broken check**, so all LP capital already in the pool becomes permanently unwithdrawable, and no further liquidity can be added or removed. This satisfies "permanent freezing of user or LP funds."

### Likelihood Explanation
The trigger requires only ordinary, unprivileged `Deposit`/`Withdraw` transactions with attacker-chosen amounts and `base_side` — no privileged signer, oracle manipulation, or off-chain component is needed. It is a probabilistic/precision-driven condition rather than a one-shot exploit, but is fully reachable from a single submitted transaction sequence controlled by any pool participant, and the existing `else` branch in `calc_take_pnl` demonstrates the developers were already aware this comparison can fail, they simply chose to hard-revert instead of gracefully clamping.

### Recommendation
Do not hard-revert when `pool_pc_amount * pool_coin_amount < calc_pc_amount * calc_coin_amount`; instead clamp the delta to zero (skip PnL extraction for that call) and continue processing the `Deposit`/`Withdraw`/`WithdrawPnl` logic, or re-synchronize `target.calc_pnl_x`/`calc_pnl_y` down to the live reserves in that branch so the invariant self-heals instead of permanently blocking all future calls.

### Proof of Concept
Conceptually: repeatedly call `Deposit` with `base_side = 0` (rounding `deduct_pc_amount` up via `Ceiling`) followed by `Withdraw` of the same LP amount (rounding `coin_amount`/`pc_amount` down via `Floor`) so each cycle leaves `target.calc_pnl_x`/`calc_pnl_y` (computed via `normalize_decimal_v2`/`restore_decimal` truncation) marginally larger relative to the shrinking live vault balances, as seen in the round-trip math in `program/src/math.rs:80-116` and the checkpoint updates in `program/src/processor.rs:1818-1838`. After enough cycles, `pool_pc_amount * pool_coin_amount < calc_pc_amount * calc_coin_amount` in `calc_take_pnl`, and all subsequent `Deposit`/`Withdraw`/`WithdrawPnl` calls on the pool return `AmmError::CalcPnlError` indefinitely.     pub fn normalize_decimal(val: u64, native_decimal: u64, sys_decimal_value: u64) -> u64 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = Self::to_u64(
            ret_mut
                .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
                .unwrap()
                .as_u128(),
        )
        .unwrap();
        ret
    }
