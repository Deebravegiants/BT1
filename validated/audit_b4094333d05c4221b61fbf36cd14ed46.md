### Title
Webhook `shop-domain` (and other headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that the HMAC matches the body, then hands the unverified `shop` value straight to the app's webhook handler. This breaks the identity binding `hmac-signed bytes == bytes the handler trusts as tenant identity`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop`, `topic`, `api_version`, `webhook_id` are read directly from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC (which only proves the body was signed by a secret holder for that exact body) and then immediately trusts `request.shop` as the tenant identity passed to the handler: [3](#0-2) 

Because the HMAC never covers the `shop-domain` header, any party who can obtain one valid `(body, hmac)` pair for their own shop (e.g., by installing the app on a store they control and capturing a real webhook delivery) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it only re-computes the HMAC over the raw body: [4](#0-3) 

The equality that should hold is `shop value verified by the HMAC == shop value the handler treats as the event's tenant`. Here, the HMAC verifies only the body, so the equality is broken — the `shop` value passed to `WebhookMetadata` is fully attacker-controlled while still passing HMAC validation.

### Impact Explanation
Applications built on this gem generally use the webhook's reported `shop` to select the tenant record to update, delete, or reconcile (e.g., mandatory `shop/redact`, `customers/redact`, `app/uninstalled` topics). By replaying a validly-signed body with a spoofed `shop-domain` header, an attacker can cause the host application to process/act on data as if it belongs to a different (victim) merchant — this is a cross-tenant integrity issue (data written/deleted under the wrong shop key), reachable by any unprivileged internet user with network access to the app's public webhook endpoint and no possession of the app's `client_secret` or any merchant's access token.

### Likelihood Explanation
The attacker needs one legitimately-signed `(body, hmac)` pair, which is trivially obtainable by installing the target public app on an attacker-controlled development/trial store (a normal, unprivileged action) and capturing the resulting webhook delivery. Sending a forged POST directly to the app's public webhook endpoint with the captured body/HMAC and a spoofed `shop-domain` header requires no special access.

### Recommendation
Bind the `shop`, `topic`, `webhook_id`, and `api_version` values into the HMAC-verified payload (or otherwise cryptographically bind them to the signed body), and have `Webhooks::Registry.process`/the resulting `WebhookMetadata` only surface a `shop` value that has been proven, not merely asserted by an unauthenticated header. At minimum, document prominently that `request.shop` is unauthenticated and must not be used as a tenant key without an independent cross-check (e.g., comparing against a shop the app already has an active session/install record for).

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a store they control) and captures a legitimate webhook delivery, e.g. for `orders/create`, obtaining `raw_body` and its valid `x-shopify-hmac-sha256` value.
2. Attacker sends a POST request directly to the app's public webhook endpoint with the exact same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` because it only checks the HMAC over `raw_body`, per: [1](#0-0) 
4. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, per: [5](#0-4) 
5. Any application logic keyed on `data.shop` now operates against the victim tenant using attacker-supplied data.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

        end
