### Title
Webhook Shop Attribution Not Bound to HMAC Signature Enables Cross-Tenant Data Misattribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` (tenant identity) that is passed on to the webhook handler is read from an HTTP header that is **not** covered by that signature. `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated `shop` value to attribute the (HMAC-verified) payload to a tenant, breaking the binding `HMAC-verified-bytes == tenant-attributed-bytes`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which plays no role in the signature computation at all: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `hmac == HMAC_SHA256(secret, verifiable_query.to_signable_string)`, i.e. it authenticates the body bytes, never the shop header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` — the unauthenticated header value — to the handler as the tenant identifier, alongside the HMAC-verified body: [4](#0-3) 

Because the signature never binds the shop domain to the body, any request that carries a *validly-signed body* (i.e., any body+HMAC pair that was ever legitimately produced by Shopify with the app's secret, for any shop the attacker controls or has previously observed) can be replayed to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header substituted. `HmacValidator.validate` will still return `true`, since it never inspects the shop header, and `Registry.process` will hand the handler `WebhookMetadata` claiming the (attacker-chosen) victim shop for content that actually originated from a different shop.

This is exactly the class of bug flagged in the external report (state used by the system is not the state actually authenticated) applied to an identity-binding boundary: **the shop field acted upon is not covered by the HMAC that is supposed to authenticate the message**.

### Impact Explanation
An attacker who runs their own (unprivileged) instance of the app — merely by installing it on their own store, which requires no special privilege — obtains genuine, validly-HMAC-signed webhook deliveries for their own shop. By replaying such a payload to the app's shared webhook endpoint with the `shop-domain` header rewritten to a victim shop, the attacker can make the host application ingest/act on attacker-controlled data while believing it belongs to the victim tenant. Any downstream logic that trusts `WebhookMetadata#shop` (e.g., to update per-shop records, trigger per-shop side effects, or make authorization decisions) is now cross-tenant, satisfying the Critical impact bar ("cross-tenant access").

### Likelihood Explanation
No secrets are required to exploit this beyond having a normal (attacker-owned) shop install of the app, which is the standard unprivileged path into a Shopify app. Producing a validly-signed body/HMAC pair is trivial — it happens automatically whenever Shopify fires any webhook to the attacker's own installation — and only the header needs to be modified in the replayed request, since the header is entirely outside of the signed content.

### Recommendation
Bind the tenant identity to the authenticated payload: include `shop` (and ideally `topic`/`webhook_id`) as part of the signable string, or otherwise cryptographically bind the shop domain to the body before trusting it, mirroring how `StrategyBase`-style guidance suggests validating *all* fields relied upon rather than only a subset. At minimum, `Utils::HmacValidator` or `Registry.process` should re-derive/validate the shop identity from a source that is covered by the HMAC (or from Shopify's API using the resource IDs in the verified body) instead of trusting the raw header.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic so Shopify sends a legitimately HMAC-signed payload to the app's webhook endpoint, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body under app secret>
   x-shopify-shop-domain: attacker.myshopify.com
   Body: {"id": 123, ...attacker-controlled order data...}
   ```
2. Capture this exact `raw_body` and `x-shopify-hmac-sha256` value (valid, unchanged).
3. Replay the same request to the app's webhook endpoint, only replacing the header:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC over `raw_body` only — this still matches, so validation passes: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body, causing the host application to attribute/act on attacker data under the victim tenant's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
