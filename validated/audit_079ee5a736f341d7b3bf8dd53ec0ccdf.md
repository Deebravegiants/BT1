## Title
Webhook HMAC only authenticates the raw body while `shop`, `topic`, `webhook_id`, and `api_version` are trusted from unauthenticated headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body via HMAC, but the shop identity, topic, and webhook id that the gem uses to route and label the webhook are read straight from HTTP headers that are never covered by that HMAC. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body/HMAC pair is valid, regardless of what shop or topic headers accompany it, and hands the (attacker-controlled) header values to the app's handler as trusted identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` (via `VerifiableQuery`) only ever checks `verifiable_query.to_signable_string`, i.e. the body, against the received HMAC: [3](#0-2) 

`Registry.process` validates that body/HMAC pair and then immediately trusts the unauthenticated header-derived `request.shop`, `request.topic`, and `request.webhook_id` to construct the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding the gem is supposed to enforce is: *the shop/topic asserted for a webhook == the shop/topic Shopify actually generated the HMAC for*. Because the HMAC covers only body bytes, that equality does not hold — `shop`/`topic`/`webhook_id` can be swapped on a request while keeping a previously-observed valid `(body, hmac)` pair, and `HmacValidator.validate` will still return `true`. Any actor who can obtain one legitimately-signed `(body, x-shopify-hmac-sha256)` pair for their own shop (trivial — they just install the app on their own store and receive a real webhook) can replay that exact body with a different `x-shopify-shop-domain` and/or `x-shopify-topic` header directly against the app's public webhook endpoint. The gem will validate the HMAC (it only checks the body) and hand the handler a `WebhookMetadata` claiming the victim shop/topic while the actual payload bytes are the attacker's own data.

### Impact Explanation
This breaks the shop-identity binding the whole webhook trust model rests on. A host application that uses `WebhookMetadata#shop` (as documented/intended by this gem) to attribute or persist per-tenant webhook data can be made to associate attacker-controlled body content with a victim shop, or process an attacker's ordinary body as if it arrived for a sensitive topic (e.g. `app/uninstalled`, `customers/redact`, `shop/redact`) for a different tenant. This is a cross-tenant identity confusion introduced entirely within this gem's webhook verification code, not a misuse of a documented API.

### Likelihood Explanation
Medium-to-low but concretely reachable without any privileged credential: the attacker needs one legitimately signed `(body, hmac)` pair, which they can generate at will by installing the target app on their own shop (any unprivileged internet user can do this) and capturing/replaying the webhook to the same publicly reachable endpoint with different headers.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed/verified material (or otherwise cryptographically bind them to the body, e.g. compute the HMAC over a canonical string containing these header values plus the body, or require the handler layer to independently verify shop/topic against the payload contents) so that swapping headers on a captured request invalidates the signature.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker-shop.myshopify.com`) and legitimately triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify sent — both are valid because `H = HMAC-SHA256(secret, B)` per `HmacValidator.compute_signature` [5](#0-4) .
2. Attacker sends a new POST request directly to the app's public webhook endpoint with the exact same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or `X-Shopify-Topic: customers/redact`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `request.to_signable_string` (`B`) and compares it to `H` — validation succeeds [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` [7](#0-6) , even though the payload `B` was never generated by or for `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
