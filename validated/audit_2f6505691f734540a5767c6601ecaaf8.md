### Title
Webhook `shop` (tenant) identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw JSON body. The `shop` (and `topic`/`webhook_id`) values that are handed to the host application's handler as the identity of the tenant originating the event come from HTTP headers that are **not** included in the signed payload. This breaks the equality that should hold: `shop_verified_by_hmac == shop_delivered_to_handler`. In reality, only `body_verified_by_hmac == raw_body` holds; `shop` is accepted without any cryptographic binding to that signature.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` [5](#0-4) . For webhook requests, `to_signable_string` is defined as just the raw body: [2](#0-1) 

The `shop` attribute read by `Registry.process` and forwarded into `WebhookMetadata` comes from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never mixed into the signable string: [6](#0-5) [4](#0-3) 

Because a single app's `client_secret` (`Context.api_secret_key`) is shared across **every** shop that has installed the app, any merchant who has installed the app on their own store legitimately receives genuine `(raw_body, hmac)` pairs signed with that same shared secret. Such a merchant — an unprivileged, standard user of the app with no elevated access — can capture a valid `(body, hmac)` pair from a webhook fired against their own store, then replay the identical body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a different (victim) shop. `HmacValidator.validate` will still succeed (it only checks the body against the shared secret), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop [7](#0-6) , even though it is entirely attacker-crafted for that tenant.

This is the direct structural analog of the D3Vault report's core defect: a value that drives a security-relevant action (there: token transfer target/amount; here: tenant/shop attribution) is not covered by the same integrity check (there: `safeTransferFrom`/return-value check; here: the HMAC) that is used to authenticate the rest of the operation.

### Impact Explanation
Any downstream application code that trusts `WebhookMetadata#shop` as an authenticated tenant identifier (the documented and expected usage pattern of this gem — the gem does not expose any other tenant-verification primitive for webhooks) can be made to process, store, or act on attacker-supplied data under a victim shop's identity. This is a cross-tenant access vector: an unprivileged app-installer can inject fabricated webhook events attributed to another merchant's shop, without possessing that merchant's credentials or the app's `client_secret` directly (they only rely on the secret being shared across tenants, which is normal Shopify app architecture, not a privileged secret they had to steal).

### Likelihood Explanation
High for any multi-tenant Shopify app: obtaining a valid `(body, hmac)` pair only requires installing the app on any shop (a normal, unprivileged action available to any merchant) and firing/receiving one webhook of the topic to be spoofed. No secret exfiltration, TLS interception, or social engineering is required — only reuse of a legitimately received (body, signature) pair against a different `shop` header value.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified by `HmacValidator`, or otherwise cryptographically tie the resolved tenant to the signed payload before it is handed to the handler — e.g., by including the shop domain in `to_signable_string`, or by requiring host applications to cross-check `request.shop` against a shop already known to have installed the app under the *specific* `webhook_id`/subscription that was registered for it, not just a generic HMAC-of-body check.

### Proof of Concept
1. Attacker installs the target app on their own development shop `attacker.myshopify.com`, obtaining a valid webhook delivery: body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify with the app's shared `client_secret`).
2. Attacker replays `POST /webhooks` with the same raw body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` — this succeeds [8](#0-7) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [7](#0-6) , causing the host application to process attacker-controlled data as if it originated from the victim's shop.
