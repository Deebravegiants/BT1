### Title
Fee-on-transfer / non-standard ERC20 underlying tokens cause under-collateralized cross-chain transfers in `WrappedHyperFungibleToken.send()` - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol / WrappedHyperFungibleTokenUpgradeable.sol)

### Summary
`WrappedHyperFungibleToken.send()` (and its upgradeable twin) locks the caller-specified `params.amount` of the underlying ERC20 via `safeTransferFrom`, but never checks how much the contract actually received. It then encodes the full, unreduced `params.amount` into the cross-chain `Message` that is dispatched to the peer contract. If the underlying token charges a transfer fee (or otherwise delivers less than the nominal amount, as the ERC20 standard permits), the wrapper locks less collateral than it commits to release, permanently under-collateralizing the bridge.

### Finding Description
In `send()`, the ERC20 path is: [1](#0-0) 

`params.amount` is used directly for `safeTransferFrom` and is never reconciled against the pre/post balance of the contract. The same unreduced `params.amount` is then embedded in the dispatched message: [2](#0-1) 

On the destination side, `onAccept` releases exactly `message.amount` of the underlying token from that chain's escrow to the beneficiary, with no cross-check against what was actually locked on the source chain: [3](#0-2) 

If the counterpart on the destination is instead a `HyperFungibleToken` (mint/burn model), the same unreduced amount would be minted, i.e., an unbacked mint relative to what was actually escrowed on the wrapper side. The identical pattern exists in `WrappedHyperFungibleTokenUpgradeable.send()`: [4](#0-3) 

This is the same bug class described in the referenced ACO report: `_transferFromERC20`-style code assumes `amountReceived == amountSent`, which is false for fee-on-transfer or otherwise non-compliant ERC20s. Notably, the codebase already recognizes and defends against exactly this issue elsewhere — `IntentGatewayV2.placeOrder` explicitly snapshots balances before/after `safeTransferFrom` and mutates `order.inputs[i].amount` to the actually-received amount before computing the commitment/escrow: [5](#0-4) 

with dedicated fee-on-transfer regression tests: [6](#0-5) 

`WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` lack this protection entirely — they trust `params.amount` at face value both for what was locked and for what is committed cross-chain.

### Impact Explanation
Any unprivileged user calling `send()` with a fee-charging (or otherwise non-standard) ERC20 configured as `_underlying` causes the wrapper to lock less than it promises to release on the destination chain. Repeated use progressively drains the escrow, so honest users' funds become unavailable (destination releases will eventually fail once escrow is exhausted, or - worse - the destination side mints/unlocks more value than was ever backed), i.e., unbacked mint / protocol insolvency and eventual freezing of funds for other users of the same wrapped-token pair.

### Likelihood Explanation
Triggerable by a single, ordinary `send()` transaction from any user — no privileged role, governance action, or malicious admin required. The only precondition is that `_underlying` (set once via `configure()`) is, or later becomes, a fee-on-transfer/deflationary/non-standard ERC20 — a realistic scenario given that widely used tokens (e.g., USDT) reserve the right to enable fees, exactly as called out in the referenced report.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.placeOrder`: measure `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom`, use the actual delta as the amount encoded into the dispatched `Message` (and as the amount refunded on timeout), rather than trusting `params.amount`. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.send()`.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a token that charges a 1% transfer fee (e.g. a future-fee-enabled USDT-like token).
2. User calls `send({amount: 1000e6, ...})`. `safeTransferFrom(user, address(this), 1000e6)` executes, but the contract's balance only increases by 990e6 due to the fee.
3. `_buildDispatchPost` still encodes `amount: 1000e6` in the `Message`, and this is dispatched via ISMP.
4. On the destination chain, `onAccept`/`_mint` releases/mints the full `1000e6`, exceeding the `990e6` actually escrowed on the source chain by `10e6`.
5. Repeating this drains the wrapper's real balance below what later users are owed, leaving some withdrawals permanently unfulfillable — reproducible using the existing `FeeOnTransferToken` test helper already present in the repo's test suite.

        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
