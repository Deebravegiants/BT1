### Title
Webhook shop identity spoofing — HMAC validates only the request body, not the tenant-identifying `shop` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Utils::HmacValidator` verify a webhook's HMAC over the raw request body only. The `shop` (`X-Shopify-Shop-Domain`), `topic`, and `webhook_id` values are read straight from unauthenticated HTTP headers and are never included in the signed content. `Registry.process` still forwards this unauthenticated `shop` value to the app's handler as the tenant identifier, so a genuinely-signed payload can be replayed against a spoofed shop identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (the tenant key) is pulled from a header that is completely outside that signed string: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (the raw body), so it can never detect that `shop` was altered: [3](#0-2) 

`Registry.process` checks only this body-bound HMAC, then trusts `request.shop` when constructing the data handed to the app's handler: [4](#0-3) 

The identity binding the gem is supposed to enforce is:
`shop_verified_by_hmac == shop_delivered_to_handler`

Because `shop` is never part of the signed bytes, this equality does not hold: the HMAC only proves "this body was signed with the app's secret" — it proves nothing about which shop the body belongs to. Anyone who can produce (or capture) one validly-signed webhook body/HMAC pair — which any merchant with the app installed can do simply by triggering an event on their own store — can resend that exact `body` + `hmac-sha256` header pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` still returns `true` (it never looks at the shop header), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain paired with attacker-controlled (but validly-signed) body content.

### Impact Explanation
This is a cross-tenant identity-binding break inside the gem's own webhook-processing code (not a host-application misuse of the documented API): the shop value that host apps are documented to rely on for tenant scoping (`WebhookMetadata#shop`) can be forged while carrying a payload whose HMAC the gem itself certified as authentic. A host app that keys any per-shop side effect (record updates, entitlement changes, log correlation) off `data.shop` can have that data falsely attributed to a victim shop it never came from — a cross-tenant data-integrity/confusion vulnerability delivered through the gem's own signature-verification contract.

### Likelihood Explanation
Any developer/merchant who has the target app installed on their own store can trivially capture one legitimately signed webhook for that store (it arrives on their own configured endpoint, or can be intercepted/logged) and replay it with a modified `shop-domain` header — no access to the app's `client_secret` is required, no rate limiting or race condition is needed, and Shopify's own webhook delivery infrastructure does not need to be defeated.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the material that is verified, not just trusted from headers, e.g. by fetching the expected shop's secret/session and validating that this webhook's `shop` value matches an actively registered subscription/session before dispatch, or by requiring hosts to cross-check `WebhookMetadata#shop` against a known-installed shop list keyed independently (e.g., from an offline session store) before trusting it for any tenant-scoped action, and by documenting explicitly that `shop` in `WebhookMetadata` is unauthenticated header data, not HMAC-verified.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers any subscribed event (e.g., `orders/create`), receiving a webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (H = HMAC-SHA256(app_secret, B)), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the same body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and returns `true`.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, i.e., an attacker-controlled body accepted as validly-signed data for `victim.myshopify.com`.
