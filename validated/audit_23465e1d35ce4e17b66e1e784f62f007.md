### Title
Time-of-check/time-of-use race in gateway JWT replay-protection allows single-use trigger token to be reused - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` is meant to enforce that each JWT (identified by its `jti` claim) can authorize exactly one HTTP-triggered workflow execution. Like the Tracer `withdraw()` bug — where the "check" (`marginIsValid`) and the "state update" (`userBalance.base = ...`) are separated by an external call, letting a second invocation observe stale state — this handler's "check" (`isReplay`) and "state update" (`recordUsage`) are two independent, non-atomic lock operations, letting concurrent callers observe stale (not-yet-recorded) state and both pass authorization with the same token.

### Finding Description
`jwtReplayCache` stores used JWT IDs in a map guarded by a `sync.RWMutex`, but the check and the record are performed as two separate critical sections rather than one atomic operation: [1](#0-0) 

`Authorize` calls `isReplay` (acquires and releases `RLock`), then does unrelated work (JWT signature/signer verification, workflow authorized-key lookup), and only afterwards calls `recordUsage` (a separate `Lock`/`Unlock`): [2](#0-1) 

Because the check-then-act sequence is not protected by a single lock/critical section, two concurrent `Authorize` calls presenting the *same* JWT (same `jti`) can both execute `isReplay(claims.ID)` before either has called `recordUsage(claims.ID)`. Both will see `exists == false`, both will pass the authorized-key check, and both will proceed to record usage and return a valid `*gateway.AuthorizedKey`, i.e., the "single-use" guarantee is bypassed under concurrency.

This is the same bug class as the reported reentrancy: an external/asynchronous intervening step (here, concurrent goroutine scheduling and additional verification logic) occurs between the validity check and the state mutation that is supposed to prevent reuse.

Notably, the codebase already contains the *correct* pattern for this exact problem in the sibling Vault package, where `RequestReplayGuard.CheckAndRecord` performs the check and the record under a single lock: [3](#0-2) 

The `jwtReplayCache` in `workflow_metadata_handler.go` does not follow this pattern and is vulnerable.

`Authorize` is invoked from the internet-facing gateway HTTP trigger handler (`http_trigger_handler.go`), which processes requests from unprivileged/external clients invoking `MethodWorkflowExecute`.

### Impact Explanation
An unprivileged client that can send two (or more) concurrent HTTP trigger requests carrying the identical signed JWT can cause the same token to authorize multiple workflow executions instead of exactly one. This defeats the anti-replay control explicitly designed to prevent a captured/observed trigger token from being reused (e.g., by a third party who intercepts a token, or by the legitimate caller attempting to trigger duplicate/unintended runs), potentially leading to duplicate job runs, resource exhaustion of the DON, or unintended on-chain/off-chain side effects triggered multiple times from one authorization.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker/caller to send multiple requests with the same JWT within a narrow race window (comparable to the report's note that reentrancy likelihood is "low" because it depends on precise timing/execution control). No special privilege is needed — only the ability to issue two near-simultaneous HTTP requests with the same previously obtained token, which is trivially scriptable from the client side.

### Recommendation
Merge the check and the record into a single atomic operation performed while holding one write lock, mirroring `RequestReplayGuard.CheckAndRecord`:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) bool {
    cache.mu.Lock()
    defer cache.mu.Unlock()
    if _, exists := cache.cache[jti]; exists {
        return false
    }
    cache.cache[jti] = time.Now()
    return true
}
```
and call this single method from `Authorize` immediately after (or as part of) validating `claims.ID`, removing the separate `isReplay`/`recordUsage` calls so no window exists between the check and the write.

### Proof of Concept
1. Obtain (or generate) one valid signed JWT for `MethodWorkflowExecute` with jti `J1`, authorized for workflow `W`.
2. From a client, fire two HTTP trigger requests to the gateway carrying the same JWT `J1` at (approximately) the same time, e.g. via two goroutines/parallel curl requests hitting the endpoint that eventually calls `WorkflowMetadataHandler.Authorize(workflowID, tokenString, req)`.
3. Both goroutines call `h.jwtCache.isReplay(claims.ID)` before either calls `h.jwtCache.recordUsage(claims.ID)`; both see `false` and both pass, causing the workflow to be triggered twice from a single-use token — contrary to the single-use-token guarantee tested (sequentially, not concurrently) in `workflow_metadata_handler_test.go` lines 1193-1217 ( [4](#0-3) ), which only demonstrates the sequential (non-racing) rejection path and does not test concurrent calls.

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
```

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```
