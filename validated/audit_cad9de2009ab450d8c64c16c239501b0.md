Confirmed: the `VerifiableQuery` interface only requires `hmac` and `to_signable_string`, and `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are entirely excluded from the signed content.

### Title
Webhook `shop`, `topic`, and `webhook_id` Fields Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator.validate`, but the HMAC only covers the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values consumed by `ShopifyAPI::Webhooks::Registry.process` and handed to the app's `WebhookHandler` come from unauthenticated HTTP headers, breaking the binding between "HMAC verified" and "shop/topic acted upon."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) , and `Utils::HmacValidator.validate_signature` computes/compares the HMAC solely against that signable string [2](#0-1) . Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from request headers via `shopify_header`, none of which participate in the signature [3](#0-2) .

`Registry.process` trusts these unauthenticated header values directly: it validates only the HMAC of the body, then dispatches to the handler for `request.topic` using `request.shop` as the tenant identifier in `WebhookMetadata` [4](#0-3) . `WebhookMetadata.shop` is a plain, unauthenticated `String` field passed straight to the host app's handler [5](#0-4) .

Because the `api_secret_key` is shared across all shops/tenants of the app (it is not per-shop), any legitimately installed, unprivileged merchant who receives real webhook deliveries for their own store also legitimately obtains valid `(raw_body, hmac)` pairs signed with that app-wide secret. Since the signature never binds to `shop-domain`, that attacker-controlled merchant can replay the exact same body+HMAC while substituting an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` header (and freely change `X-Shopify-Topic`/`X-Shopify-Webhook-Id` too), and `HmacValidator.validate` will still return `true`. The gem then hands the handler a `WebhookMetadata` claiming the payload originated from the victim's shop, which is false. This breaks the equality the code implicitly assumes: `hmac_valid(raw_body) == shop_and_topic_authenticated`, when in fact only `raw_body` is authenticated.

### Impact Explanation
This is a cross-tenant identity/authentication break within the gem's own webhook-verification surface: it satisfies "Critical - cross-tenant access." A merchant who is otherwise unprivileged with respect to other tenants can make the app process events "as" another shop, and any host application relying on `WebhookMetadata#shop` (as literally recommended in the gem's own webhook docs `data.shop`) to select tenant data/session/webhook-id-dedup state will act on the wrong tenant's behalf.

### Likelihood Explanation
Likelihood is high for any app: obtaining a valid `(body, hmac)` pair requires nothing more than installing the app on one's own store (a normal, unprivileged action) and receiving one legitimate webhook delivery, then replaying it with a forged `shop-domain`/`topic`/`webhook-id` header to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged access is required.

### Recommendation
Bind the tenant/topic identity into the signed content check, e.g. include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or independently verify that the `shop` on the request corresponds to a shop that has an active session/registration for the given `webhook_id`/topic before invoking the handler, so that HMAC validity and header-derived identity can't be decoupled.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` (a normal, unprivileged merchant action) and triggers a benign event (e.g. `orders/create`) so Shopify sends a legitimate webhook to the app's endpoint with a real `raw_body`, a valid `X-Shopify-Hmac-Sha256` (computed by Shopify using the app's shared `api_secret_key`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures/replays this exact `raw_body` + `X-Shopify-Hmac-Sha256` pair to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the (unchanged) HMAC [7](#0-6) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [8](#0-7)  and processes the attacker's own payload as if it belonged to `victim.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
