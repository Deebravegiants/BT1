### Title
Flash-loan-manipulable balance weighting in phantom-order bid aggregation lets a solver set a fabricated price - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
The phantom-order price aggregation pipeline weights each solver's price quote by that solver's *current* on-chain ERC-20/vault balance of the leg's output token, read via `eth_call` `balanceOf`/`maxWithdraw` at (by default) the `"latest"` block. An unprivileged intent solver reachable by submitting a phantom bid can inflate this balance momentarily (e.g. via a flash loan on the destination chain) to dominate the liquidity-weighted median and force the published `medianPrice` to an arbitrary value it chooses, exactly the same class of exploit described in the source report where a flash loan inflates voting/weight used in an on-chain decision.

### Finding Description
`getTotalSolverBalance` performs a raw `eth_call` to `balanceOf(address)` (selector `0x70a08231`) plus vault `maxWithdraw` calls, with a `blockTag` parameter defaulting to `"latest"`: [1](#0-0) 

This balance is used directly as the quote's `weight` for the leg being priced: [2](#0-1) 

The aggregation and accompanying design docs are explicit that whichever bidder holds the majority of a leg's weight sets the published price verbatim, because `weightedMedian` is a *selection*, not a blend, and the code deliberately drops zero-weight (i.e., uncapitalized) bidders precisely so that "a solver with no capital" cannot set the rate: [3](#0-2) [4](#0-3) 

That protection assumes the measured balance reflects real, durable capital. Because the read is of the *current* chain state (`"latest"`) rather than a balance that was locked/escrowed at bid time, a solver can borrow the output token via a flash loan on the destination EVM chain, hold it only long enough for the aggregator's `eth_call` to observe it, and repay the loan in the same or a following block — precisely the MakerDAO-style attack cited in the source report, where a transient, borrowed balance is used to dominate a weight-based decision.

The resulting `medianPrice` (with `lowestPrice`/`highestPrice` overwritten to equal it) is then folded into the protocol's pool rates: [5](#0-4) 

### Impact Explanation
The phantom-order snapshot feeds `PoolChainLiquidity`/`LiquidityPool` `sellRate`/`buyRate`, which other solvers and downstream consumers use as a reference price for real cross-chain intents. A solver able to momentarily dominate the weighted median (via flash-loaned balance) can force a published rate no genuinely capitalized participant quoted, poisoning the reference price the ecosystem relies on for intent pricing and enabling that solver (or a colluding party) to profit at the expense of other market participants or downstream automated pricing/fill decisions built on this feed. This is analogous to the DAO governance flash-loan finding: an artificially inflated, transient balance is substituted for real, sustained economic weight in a decision (here, price-setting instead of vote-counting) that other unprivileged system participants rely on.

### Likelihood Explanation
Reachable by any unprivileged intent solver: submitting a phantom bid is a normal, permissionless action, and the weight computation reads live chain state with no lock, escrow, or delay tying it to the moment of bid submission. Exploitation requires access to a flash-loan source for the specific output token on the destination chain and timing the loan to be outstanding when the aggregator's `eth_call` executes — feasible on chains with cheap/fast blocks and available flash-loan liquidity for the relevant token, similar to the real-world MakerDAO incident referenced in the report.

### Recommendation
Do not weight a leg's quote by an instantaneous `"latest"`-tag balance read. Instead:
- Pin the balance read to a fixed historical block that predates the bid (e.g., the block at which the bid's `userOp`/signature was produced, or a block several confirmations before the bid window closes), so a same-block flash loan cannot influence the measured weight.
- Consider requiring the balance backing a quote to be sustained/escrowed (e.g., via a time-locked commitment or averaged over a window of blocks) rather than a single spot read, mirroring the report's recommendation to use weight from previous blocks or cap individual influence.
- Cap any single solver's contribution to a leg's weighted median to bound the damage even if a spot balance is manipulated.

Note: the repository already contains an internal decision doc (`sdk/packages/sdk/docs/ai/decisions/2026-09-01-blocktag-is-a-parameter-of-the-balance-read-and-a-per-chain-map.md`) indicating the team parameterized `blockTag` per chain; it was not possible in the time available to confirm what block value the indexer actually passes in production (still `"latest"`, or a pinned historical block that would close this gap). This should be verified before treating the finding as fully open or fully mitigated.

### Proof of Concept
1. Indexer detects `PhantomBidWindowExhausted` for a phantom order leg whose output token is `T` on destination chain `C`.
2. Attacker, acting as a delegated solver, submits a phantom bid quoting an arbitrary favorable `solverAmount` for leg `T`.
3. Immediately before/around the aggregator's `eth_call` to `balanceOf(solver)` (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1031`), the attacker takes a flash loan of token `T` on chain `C`, inflating their `balanceOf` for the duration of one block, then repays it.
4. `aggregatePhantomBids` computes `weight` from this inflated balance (`phantom-aggregation.ts:1484`), giving the attacker's quote majority weight in `weightedMedian`.
5. The published `PhantomOrderPriceSnapshotV2.medianPrice` for that leg equals the attacker's arbitrary quote, and `updateLiquidityPools` folds it into the pool's `sellRate`/`buyRate` used by other market participants.

export async function getTotalSolverBalance(
	evmRpcUrl: string,
	chain: string,
	token: string,
	solver: string,
	yieldVaults: YieldVaultMap,
	blockTag = "latest",
): Promise<bigint> {
	const padded = solver.replace("0x", "").padStart(64, "0")
	const raw = await ethCallUint(evmRpcUrl, token, `0x70a08231${padded}`, blockTag) // balanceOf(address)
	const vaults = yieldVaults[chain]?.[token.toLowerCase()] ?? []
	const vaultBalances = await Promise.all(
		vaults.map((v) => ethCallUint(evmRpcUrl, v, `0xce96cb77${padded}`, blockTag)), // maxWithdraw(address)
	)
	return vaultBalances.reduce((acc, b) => acc + b, raw)
}
