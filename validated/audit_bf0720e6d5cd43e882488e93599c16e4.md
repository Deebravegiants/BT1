## Title
Trust/auto-approve grant given for one wallet account silently extends dApp access to all other wallet accounts on account switch - ([File: features/connected-origins/module/connections.js])

### Summary
The `ConnectedOrigins` module stores the `trusted`/`autoApprove` flag once per **origin**, not per wallet account, while the actual account approval flow (per the Solana provider docs) is presented to the user as approving a specific connection to a specific account. Once a dApp origin is marked `trusted` by the user, `getConnectedAccounts()` and the `onlyIfTrusted` eager-connect path expose **every enabled wallet account's address**, not just the address of the wallet account the user actually consented to when the trust was granted. This mirrors the OwnableSmartWallet finding: an approval scoped to one context (a specific account) is not properly revoked/re-scoped when the context changes (switching the active wallet account), so it silently authorizes something the user never explicitly approved.

### Finding Description
`ConnectedOrigins#add()` stores a single `trusted`/`walletAccount` value on the origin record itself [1](#0-0) . The `walletAccount` field is accepted and persisted but is never read back anywhere to scope subsequent trust checks — `grep` across the feature confirms it is only referenced at write time in `add`/`#addNewItem`.

`isTrusted()` only checks the origin string, with no per-account qualifier [2](#0-1) .

`getConnectedAccounts()` — documented as usable "while the wallet is locked" and used for the eager/auto reconnection flow — iterates over **all** entries of `connectedAccountsAtom` (which itself is populated from `enabledWalletAccountsAtom`, i.e. every wallet account the user has, not just the one that was present when trust was granted) and returns addresses for every account, with only the currently active one sorted first [3](#0-2) .

Per the Solana Provider API documentation, once a site becomes "trusted" it is allowed to `connect({ onlyIfTrusted: true })` without any further user interaction ("eagerly connecting") [4](#0-3) . Because the trust grant and the eager-reconnect check are keyed only by `origin` and not by the wallet account that was active/approved at grant time, when the user switches the active wallet account (`activeWalletAccountAtom`) — or when a new wallet account is subsequently added — that new account is automatically exposed to the already-trusted dApp without the user ever explicitly approving that specific account. This exactly matches the reported bug class: an approval (trust) intended for one specific entity/context bleeds into scope it was never granted for once the underlying "owner" (active account) changes, because the approval-store has no per-account revocation/isolation.

### Impact Explanation
A dApp that a user trusted while using Wallet Account A can silently gain the address of every other wallet account (including newly created/imported ones) the moment the user switches accounts or adds a new account, with no additional prompt shown to the user. This breaks the account-isolation model users rely on (e.g., separating a "public" trading account from a "private" cold-storage-style account) and leaks address/account information cross-account without consent — a privilege bleed across account boundaries stemming from unrevoked/unscoped approval state, analogous to the unwanted-ownership-transfer disclosure in the referenced report. It does not by itself expose private keys or enable unauthorized signing, but it is a real cross-account privilege/data bleed rooted in the same "stale approval not properly scoped/revoked" root cause.

### Likelihood Explanation
Any user who trusts even a single dApp and later switches or adds wallet accounts (a very common workflow) triggers this behavior; no attacker action beyond normal dApp connect flow is required, and the exposure happens automatically via the "eagerly connecting" (`onlyIfTrusted`) mechanism that is a documented, intended feature.

### Recommendation
Scope trust/auto-approve and the address list returned by `getConnectedAccounts` to the specific wallet account(s) that were actually present and consented at the time trust was granted, rather than to the origin alone. When new wallet accounts are added or the active account changes, require a fresh consent/connect prompt for that account before exposing its address to an already-trusted origin, instead of implicitly including it via `#getAccounts`/`updateConnectedAccounts`.

### Proof of Concept
1. User visits `dapp.example` and connects Wallet Account `exodus_0`; `connectedOrigins.add({ origin, trusted: true, ... })` stores `trusted: true` on the origin only [1](#0-0) .
2. User adds/switches to a new Wallet Account `exodus_1` (`enabledWalletAccountsAtom` updates); `updateConnectedAccounts()` runs and repopulates `connectedAccountsAtom` for all enabled wallet accounts including `exodus_1` [5](#0-4) .
3. `dapp.example` calls `solana.connect({ onlyIfTrusted: true })`; since `isTrusted({ origin })` is still `true` (unscoped to account), the dApp reconnects and, via `getConnectedAccounts`, receives `exodus_1`'s address automatically — even though the user only ever consented to `dapp.example` seeing `exodus_0` [6](#0-5) , [4](#0-3) .

  /**
   * Returns the connected accounts for a given origin with the active wallet account sorted first. Can be used while
   * the wallet is locked
   */
  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }

#### Eagerly Connecting

After the user approves a Web3 site's connection to Exodus, the site becomes
trusted. This allows the site to automatically connect to Exodus on subsequent
visits or page refreshes. This is referred to as "eagerly connecting".

If you want to try to eagerly connect, you can pass the `onlyIfTrusted` option
to `connect()`.

```typescript
try {
  await window.exodus.solana.connect({ onlyIfTrusted: true })
} catch (err) {
  // { code: 4001, message: 'User rejected the request.' }
}
```

:::tip

When using this flag, Exodus will only connect if the site is trusted and won't
bother your users with a pop-up if they have not connected to Exodus before.

:::
