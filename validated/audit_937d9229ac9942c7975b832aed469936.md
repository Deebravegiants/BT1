### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing in `Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the `X-Shopify-Hmac-Sha256` HMAC covers the payload bytes but never the `X-Shopify-Shop-Domain` header. `Webhooks::Registry.process` validates only that HMAC and then hands `request.shop` — an attacker-controlled, unauthenticated header value — straight to the app's webhook handler as the trusted tenant identity.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string`: [1](#0-0) . For webhook requests, `to_signable_string` is defined to return only `@raw_body`, while `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed content: [2](#0-1) .

`Webhooks::Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., that the body HMAC matches), then constructs `WebhookMetadata` using `request.shop` verbatim: [3](#0-2) .

This breaks the intended identity equality `hmac_verified_source == shop_acted_upon`: the HMAC proves "this body byte-stream was produced with the app's `api_secret_key`," but it proves nothing about which shop the body came from. Since every shop installation of a given app shares the same `client_secret`/`api_secret_key`, an attacker who legitimately controls Shop A (a real merchant install of the victim's app) can capture a validly-signed webhook delivery for Shop A, then replay that exact body/HMAC pair to the app's webhook endpoint while altering only the `X-Shopify-Shop-Domain` header to name Shop B (the victim shop). The HMAC still validates (it only covers the body), `Registry.process` accepts it, and the handler is invoked with `WebhookMetadata#shop == "shop-b.myshopify.com"` even though the payload was never sent by or about Shop B.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to key per-tenant storage, look up a stored `Session`/access token for that shop, or otherwise scope data by shop will process attacker-supplied data under a spoofed tenant identity — a cross-tenant access vector purely due to a gap between what is HMAC-verified and what is acted upon, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Requires only an unprivileged actor who can install the same app on one shop they control (or otherwise obtain one legitimately-signed webhook body/HMAC pair) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — no access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the shop identity into the signed material or otherwise cryptographically authenticate `X-Shopify-Shop-Domain` before trusting it — e.g., include the shop domain in `to_signable_string`, or independently verify the shop by cross-checking against a value obtained through an already-authenticated channel (such as the session/access token used to register the webhook) rather than trusting the raw header.

### Proof of Concept
1. Register the target app on attacker-controlled Shop A; capture an incoming webhook POST, including its raw body and valid `X-Shopify-Hmac-Sha256` header (both computed against the shared `api_secret_key`).
2. Replay the identical body and HMAC header to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` (and, if desired, `X-Shopify-Webhook-Id`) to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (validation only checks header *presence*, not shop authenticity): [4](#0-3) .
4. `Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over `@raw_body`: [5](#0-4) .
5. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"`, even though the data originated from the attacker's own shop: [6](#0-5) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
