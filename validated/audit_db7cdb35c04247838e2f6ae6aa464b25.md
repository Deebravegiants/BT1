No dedup/uniqueness validation exists in `sdk.ts` for batches — nothing prevents an integrator/attacker from submitting `withdrawalParams[]` with two entries for the same `assetId` on the same PoA route within a single `intentTx`.

### Title
PoaBridge `describeWithdrawal` misreports status/txHash for duplicate-token withdrawals in the same batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
When a batch (`withdrawalParams[]`) contains two or more PoA-bridge withdrawals of the same NEP-141 token in a single settled `intentTx`, `PoaBridge.describeWithdrawal` matches the destination-chain withdrawal record only by `nep141:<near_token_id>` via `findMatchingWithdrawal`, so every index sharing that asset resolves to the same (first-found) API record. This causes distinct withdrawal identifiers to report identical `(status, txHash)` results, even though they correspond to different destinations/amounts.

### Finding Description
The broken equality: for indices `i ≠ j` in the same batch with `withdrawalParams[i].assetId === withdrawalParams[j].assetId` routed via `PoaBridge`, the SDK should report `describeWithdrawal(wid_i) → status_i/txHash_i` corresponding uniquely to the i-th signed withdrawal, and `status_j/txHash_j` to the j-th. Instead both resolve to the same value.

`createWithdrawalIdentifiers` in packages/intents-sdk/src/core/withdrawal-watcher.ts assigns `index` per-route (a counter keyed by `bridge.route`), not a token-aware disambiguator: [1](#0-0) . That `index` is stored on the `WithdrawalIdentifier` but `PoaBridge.describeWithdrawal` never uses `index` to select among multiple matches — it calls `getWithdrawalStatusWithRetry` keyed by the shared NEAR tx hash (`args.tx.hash`, identical across the whole batch) and then calls `findMatchingWithdrawal`, which filters strictly by `assetId` using `Array.prototype.find` (first match only): [2](#0-1) [3](#0-2) .

The code itself documents this exact limitation in a comment: "multiple withdrawals of the same token in a single transaction are not supported" [4](#0-3) .

Exploit flow: an attacker (or integrator user) submits `withdrawalParams = [{assetId: X, destinationAddress: A}, {assetId: X, destinationAddress: B}]` in one call to `processWithdrawal`/`waitForWithdrawalCompletion`. Both go through the same `intentTx`. `watchWithdrawal` polls `PoaBridge.describeWithdrawal` independently for index 0 and index 1 [5](#0-4) . Once the PoA bridge indexer records only the withdrawal to destination A as `COMPLETED` (destination B still `PENDING` or not yet indexed), `findMatchingWithdrawal` returns the A-record for BOTH index-0 and index-1 lookups, since it only checks `nep141:<near_token_id> === assetId` with no per-index/per-tx disambiguation. The result: `waitForWithdrawalCompletion` resolves index 1 (destination B) as `completed` with A's `txHash`, before B's transfer has finalized (or ever will, if it's still queued).

Existing guards do not prevent this: `supports()`, `validateWithdrawal`, `compareAddresses`, and `FeeExceedsAmountError`-type checks all operate per-withdrawal-request and never inspect batch composition for duplicate `assetId`s; there is no dedup/uniqueness check found in `packages/intents-sdk/src/sdk.ts` for `processWithdrawal`/`signAndSendWithdrawalIntent`/`createWithdrawalCompletionPromises`. The `createWithdrawalCompletionPromises` unit tests exercise index-correspondence only against a fully mocked `Bridge` interface (bypassing `PoaBridge.describeWithdrawal`/`findMatchingWithdrawal` entirely), so this gap is untested at the HTTP/API level [6](#0-5) .

### Impact Explanation
An integrator that keys off the per-index `(status, txHash)` returned by `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` to credit or refund a user will observe two "completed" results carrying the identical `txHash`, for what are in reality two independent transfers to two different addresses/amounts. This is a status/hash misreport that can make an integrator credit or refund twice against a single actual on-chain transfer — matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. The condition is repeatable on every batch containing ≥2 same-`assetId` PoA withdrawals whenever the underlying PoA bridge API returns/orders/completes those records asynchronously relative to each other.

### Likelihood Explanation
Preconditions: the attacker (an ordinary user, or a counterparty whose withdrawal params an integrator forwards) needs only to submit a batch with two-plus withdrawals of the same NEP-141 asset routed to the PoA bridge — fully within the documented public API surface (`withdrawalParams[]` to `processWithdrawal`/`waitForWithdrawalCompletion`). No privileged access, no malicious relayer/RPC, and no reliance on any other SDK escape hatch is required. This is entirely feasible with any integrator that allows a caller to specify multiple withdrawals of the same token (e.g., splitting one output into two destinations), a common use case per the RFC design docs for batch withdrawals.

### Recommendation
Disambiguate matches by more than `assetId`: incorporate `amount` and/or `destinationAddress`/`destinationMemo` into `findMatchingWithdrawal`, or have `PoaBridge.createWithdrawalIdentifier` carry a per-asset ordinal and consume matching PoA API entries in a stable, sorted (e.g., by `amount`) order matched against a similarly sorted list of same-asset withdrawal params, consuming each API entry at most once across concurrent `describeWithdrawal` calls for the same batch/tx. At minimum, explicitly reject (throw) at the `supports()`/`validateWithdrawal` stage when a batch contains duplicate `assetId` entries routed to `PoaBridge`, until proper per-item matching is implemented.

### Proof of Concept
Vitest plan (mock only `poaBridge.httpClient.getWithdrawalStatus` HTTP call, not `Bridge`):
1. Construct `withdrawalParams = [{assetId: "nep141:zec.omft.near", destinationAddress: "A", amount: 1n}, {assetId: "nep141:zec.omft.near", destinationAddress: "B", amount: 2n}]`, both routed via `PoaBridge` with the same `intentTx`.
2. Mock `poaBridge.httpClient.getWithdrawalStatus` to return `withdrawals: [{ status: "COMPLETED", data: { near_token_id: "zec.omft.near", transfer_tx_hash: "hashA", ... } }]` (only A's record present; B's is not yet indexed).
3. Call `poaBridgeInstance.describeWithdrawal(widForIndex0)` and `poaBridgeInstance.describeWithdrawal(widForIndex1)` directly (both built via `createWithdrawalIdentifier` with index 0 and 1 respectively).
4. Assert the broken equality: both calls resolve to `{ status: "completed", txHash: "hashA" }` — i.e. `describeWithdrawal(wid_1).txHash === describeWithdrawal(wid_0).txHash === "hashA"`, even though wid_1 corresponds to destination B, whose actual transfer never occurred/was never indexed. This demonstrates `status_1`/`txHash_1` does not correspond to the 2nd signed withdrawal, violating the target invariant.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
