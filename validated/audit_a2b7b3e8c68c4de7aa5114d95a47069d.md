### Title
Undersized `pendingGraduation` amounts permanently brick `finalizeGraduation` via Uniswap V2's `MINIMUM_LIQUIDITY` floor - ([File: packages/contracts/src/Bonding.sol])

### Summary
`igc_probe()` panicked because a non-essential LED-setup step could fail and there was no fallback path — the driver treated a normally-succeeding auxiliary call as infallible. `Bonding.finalizeGraduation` has the same shape: it treats the first Uniswap V2 mint (`pair.mint()` inside `_seedDirectMint`) as infallible, using amounts (`tokensForLP`, `ltFromPair`) that were pinned once in phase 1 and are **never recomputed**. If those cached amounts are small enough to fall at or below Uniswap V2's hard-coded `MINIMUM_LIQUIDITY` (1000 wei) floor, the mint reverts with `INSUFFICIENT_LIQUIDITY_MINTED` on every call, and because `Lifecycle` is "strictly-forward" with no path back to `Curve`, the token is permanently stuck in `Lifecycle.Graduating`.

### Finding Description
`_deployAndSeed` only guards against `virtualLtReserve` being too **large** (i.e. `exchangeRate` too small): [1](#0-0) 

There is no lower bound on `exchangeRate`/`virtualLtReserve`. Since a token creator freely picks any BounceTech LT that passes `ltExists` as the reserve asset, and LTs are yield-bearing/appreciating (`exchangeRate()` grows over time or can already be high), `virtualLtReserve = VIRTUAL_LIQUIDITY_USD * 1e18 / exchangeRate` can be driven arbitrarily small.

`canGraduate`'s supply trigger fires once the curve's `tokenBalance() == 0` — the entire 750M `curveSupply` sold: [2](#0-1) 

With a tiny `virtualLtReserve`, exhausting the curve via the constant-product math costs a correspondingly tiny amount of real LT (`realLtRaised` scales with `virtualLtReserve`). `_prepareGraduationLiquidity` pins `tokensForLP`/`ltFromPair` from that state, at the very last curve price, and never revisits them: [3](#0-2) 

`finalizeGraduation` later feeds these frozen amounts straight into `_seedUniswapV2Direct` → `_seedDirectMint` on the (overwhelmingly common) empty-pair path: [4](#0-3) 

`IUniswapV2Pair(pair).mint(...)` is the vanilla V2 pair, whose first mint computes `liquidity = sqrt(amount0*amount1) - MINIMUM_LIQUIDITY` and reverts `INSUFFICIENT_LIQUIDITY_MINTED` if that underflows (i.e. `sqrt(tokensForLP*ltFromPair) <= 1000`). Because `tokensForLP`/`ltFromPair` are cached once in `PendingGraduation` and `Lifecycle` only moves forward (`Curve → Graduating → Graduated`, enforced by `NotGraduating`/`TokenIsGraduating` guards throughout `buy`/`sell`/`triggerGraduation`), there is no retry with different amounts and no way back to `Curve`. Every call to `finalizeGraduation` for that token reverts identically forever.

### Impact Explanation
Once `_enterGraduating` has fired, trading is frozen (`buy`/`sell` revert with `TokenIsGraduating`/`TokenNotTrading` while `lifecycle != Lifecycle.Curve`), and the entire curve-raised real LT (moved into `Bonding` via `_s().router.graduate(...)` in `_prepareGraduationLiquidity`) plus the `LP_RESERVE` (up to 250M) tokens minted for the LP sit in `Bonding` waiting for `finalizeGraduation`. If that call permanently reverts, both the LT and the reserved tokens are permanently frozen with zero recovery path (no admin rescue function exists in `Bonding` or `LPLock` for pre-lock funds). This is a permanent freeze of creator/trader-contributed funds, matching the "High" severity impact criteria.

### Likelihood Explanation
Any permissionless token creator chooses the paired `ltAddress` at `launch()` time. As long as they (or anyone buying on their curve) select/wait for an LT whose `exchangeRate()` is high enough to push `virtualLtReserve` down near the `MINIMUM_LIQUIDITY` boundary, and then drive the curve to full sellout (the supply-trigger path, which needs no USD threshold at all), the bug is deterministically triggered by ordinary `Zap.buy` calls — no privileged access, no oracle manipulation, and no reentrancy required. Because BounceTech LTs are designed to appreciate over the protocol's lifetime, this condition becomes easier to hit as any given LT ages, meaning even tokens launched against currently "safe" LTs can become bricked once that LT's `exchangeRate()` grows enough for a future graduation attempt.

### Recommendation
- Enforce a minimum-liquidity floor on `tokensForLP`/`ltFromPair` (or on `virtualLtReserve` at launch, mirroring the existing upper-bound `ExchangeRateTooLow` check) so `_seedDirectMint`'s first `pair.mint` can never underflow against Uniswap V2's `MINIMUM_LIQUIDITY`.
- Alternatively/additionally, wrap the `pair.mint()` call in `_seedDirectMint` with a fallback (e.g. try/catch or an owner/permissionless "abandon graduation, burn/refund escrowed LT and tokens" path) so a non-essential seeding failure degrades gracefully instead of bricking `finalizeGraduation` forever, consistent with the same "don't fail on setup error" principle from the referenced CVE.

### Proof of Concept
1. Deploy/select a BounceTech LT whose `exchangeRate()` is set (or has compounded) high enough that `VIRTUAL_LIQUIDITY_USD * 1e18 / exchangeRate` (i.e. `virtualLtReserve`) is a few thousand wei.
2. `Zap.createToken(...)` with that LT as `ltAddress` — `_deployAndSeed` succeeds since only the upper bound (`ExchangeRateTooLow`) is checked.
3. Buy through `Zap.buy` (any unprivileged trader, including the creator) until `IPair(pair).tokenBalance() == 0` (the entire 750M curve supply sold) — cheap because the tiny `virtualLtReserve` means very little real LT is needed to move the curve through its full range.
4. `_executeBuy` observes `canGraduate == true` (supply trigger) and calls `_enterGraduating`, pinning `tokensForLP`/`ltFromPair` at values whose product's square root is `<= 1000`.
5. Call `Bonding.finalizeGraduation(tokenAddress)` — it reaches `_seedDirectMint`'s `IUniswapV2Pair(pair).mint(lpLock)` and reverts with `INSUFFICIENT_LIQUIDITY_MINTED` every time, permanently locking the token in `Lifecycle.Graduating` with all curve-raised LT and the reserved 250M tokens stuck in `Bonding`.

```text
    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }
```

```text
    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }
```
