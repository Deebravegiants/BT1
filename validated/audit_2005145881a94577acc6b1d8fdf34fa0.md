## Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` header — which is *not* included in that HMAC computation — to attribute the payload to a shop. Because a single app has one `api_secret_key` shared across every shop that installs it, any shop that legitimately receives a webhook (with a valid body+HMAC pair) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a different, victim shop. The handler will process the payload as if it originated from the victim shop.

### Finding Description
The webhook authenticity check is implemented in `Utils::HmacValidator.validate`, which computes the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns just the raw request body — none of the Shopify headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) are part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (derived from the unauthenticated `shop-domain`/`x-shopify-shop-domain` header) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

This breaks the identity binding `HMAC-authenticated(raw_body) == trusted(shop)`. In reality only the raw body is authenticated; `shop` is parsed from bytes that were never covered by the signature. Since the HMAC secret (`api_secret_key`) is identical for every shop installation of a given app (it is not per-shop), a user who legitimately controls one shop that has the app installed can capture any webhook delivery they receive (body + `x-shopify-hmac-sha256`), and resend the identical body/HMAC pair to the app's webhook endpoint with the `shop-domain` header changed to an arbitrary victim shop. `HmacValidator.validate` will still succeed because it only checks the body against the shared secret, and the handler will process the forged event as belonging to the victim shop — a direct cross-tenant boundary violation analogous to the reported bug class where an entity (a lien's expiry) is trusted implicitly without being bound to the state (`liensOpenForEpoch`) that other logic depends on.

### Impact Explanation
This is a cross-tenant access vulnerability: an unprivileged internet user who is a legitimate customer of the app for their own shop can forge webhook events attributed to any other merchant shop using the same app, without needing the app's `client_secret`, an access token, or any credential belonging to the victim. Depending on how the host application's webhook handlers use `data.shop` (e.g., to look up/modify shop-scoped records, trigger billing actions, or sync data), this can lead to data corruption, unauthorized state changes, or information disclosure across tenant boundaries — satisfying the "Critical - cross-tenant access" category.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops (the common case for public/multi-tenant Shopify apps). Any existing merchant of the app can capture one of their own legitimate webhook deliveries (body + HMAC header), which requires no special access, and replay it against the app's webhook endpoint with a modified `shop-domain` header. No secrets need to be recovered or brute-forced.

### Recommendation
Do not treat `shop-domain` (or `topic`, `api-version`, `webhook-id`) as authenticated. Options:
- Cross-check the `shop-domain` header against a shop that the app actually expects/has a stored session for before dispatching to handlers, and reject unknown/mismatched shops.
- Where possible, include the shop identity inside data that is covered by the signed body, or maintain a per-shop mapping validated independently of the header.
- At minimum, document in `Webhooks::Request`/`Registry` that `shop`, `topic`, `api_version`, and `webhook_id` are unauthenticated header values and must not be used as an authorization boundary without additional shop-membership validation by the host application.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
2. Attacker resends the exact same `B`/`H` pair to the app's webhook endpoint but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(api_secret_key, B) == H`, which is unaffected by the header change (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the app to act on data as if it came from `victim-shop.myshopify.com`.
