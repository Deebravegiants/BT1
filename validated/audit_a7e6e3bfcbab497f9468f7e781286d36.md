No vulnerability found for this question.

The reported bug is a copy-paste variable-substitution error specific to Curve-style veToken `GaugeController` checkpoint math, where `Math.max(old_sum_bias + new_bias, old_sum_bias)` should have used `old_bias` instead of `old_sum_bias` — a pattern involving `bias`/`slope` accumulators for gauge weight voting with time-bucketed checkpoints.

Raydium AMM has no such gauge-controller, vote-escrow, or bias/slope checkpoint accumulator logic anywhere in scope. The closest analogous "old vs. new state with `Math.max`-style clamping" logic in this codebase is `Processor::calc_take_pnl` [1](#0-0) , which consistently pairs `x1`/`delta_x` with the pc side and `y1`/`delta_y` with the coin side without any cross-variable substitution. I checked all call sites that update `target_orders.calc_pnl_x` / `calc_pnl_y` in deposit and withdraw paths [2](#0-1) [3](#0-2) [4](#0-3) , and each consistently uses the matching `x1`/`delta_x` and `y1`/`delta_y` pair — there is no instance where a "sum" variable is mistakenly subtracted by an unrelated "bias"-equivalent variable, as in the referenced Curve finding.

Since raydium-amm has no gauge/voting checkpoint accumulator system, and no analogous copy-paste variable mixup exists in the pnl, swap, or liquidity math, there is no valid analog to this finding in-scope.
