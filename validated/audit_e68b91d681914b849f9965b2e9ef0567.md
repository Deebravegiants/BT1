## Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-validating only the raw request body, while the `shop`, `topic`, and `webhook_id` values that the gem hands to the registered handler as the *tenant identity* for that webhook are read from separate, unsigned HTTP headers. Because the app's HMAC secret is a single static value shared across every shop that installs the app (it is not shop-specific), any actor who can obtain one genuinely-signed `(body, hmac)` pair — trivially available to anyone who installs the app on a store they control — can replay that pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header to name a victim shop. `Utils::HmacValidator.validate` accepts the request because the body/hmac pair is valid, and `Registry.process` then dispatches the handler with the attacker-chosen `shop`, breaking the intended binding between "the shop whose secret produced this signature" and "the shop the payload is attributed to."

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are pulled from headers that are not part of that signable string: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then trusts `request.shop`/`request.topic` for dispatch to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature using the app's single `Context.api_secret_key`, which is identical for every shop that has the app installed — it is not shop-scoped: [4](#0-3) 

Because the same secret signs bodies for all merchants, and because `shop` is excluded from the signed content, the equality the app relies on — "shop that authenticated this request" == "shop the request is about" — does not hold. An attacker only needs one legitimately-signed `(raw_body, hmac)` pair from their *own* store (trivial: install the app on a free/test store and capture any webhook, e.g. `app/uninstalled` which frequently has a small/predictable body) to produce a request that passes HMAC validation while claiming to be for an arbitrary victim `shop-domain`.

### Impact Explanation
This is a cross-tenant integrity break: the handler processes attacker-controlled tenant data with a signature that only proves "the request body is genuine for *some* install," not "genuine for *this* shop." Depending on the handler logic (e.g., `app/uninstalled` deleting/revoking stored sessions or access tokens, `shop/redact` triggering data deletion, or any handler keyed off `shop` for authorization/lookup), an attacker can trigger tenant-scoped side effects (token revocation, data deletion, state corruption) against a victim shop they do not control, without ever needing that victim's credentials.

### Likelihood Explanation
Exploitation requires only an unprivileged actor who can install the target app on any store (including their own, e.g. via a free/dev store) to obtain one valid `(body, hmac)` pair, plus the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header — both are within reach of an ordinary internet user and require no knowledge of `api_secret_key` or any victim credential.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, and ideally `webhook_id`/timestamp/nonce) in the HMAC-signed material — or otherwise cryptographically bind them to the body — so that `Utils::HmacValidator.validate` cannot be satisfied for a header set that differs from the one Shopify actually signed. At minimum, `Request#to_signable_string` should incorporate the shop/topic headers, mirroring how `AuthQuery#to_signable_string` binds `shop` into its signable content: [5](#0-4) 

### Proof of Concept
1. Attacker installs the app on their own store (`attacker.myshopify.com`) and captures a legitimate webhook delivery, e.g. `app/uninstalled` with body `{}` and its valid `X-Shopify-Hmac-Sha256` header (computed with the app's static `api_secret_key`).
2. Attacker resends this exact `(body="{}", hmac=<captured>)` pair to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and `X-Shopify-Topic: app/uninstalled`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the hmac using the app's single secret — this succeeds since the body/hmac pair is genuinely valid: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)`, causing the app to perform uninstall-cleanup (token/session deletion) for the victim shop even though the victim never uninstalled the app.

          received_signature = verifiable_query.hmac
