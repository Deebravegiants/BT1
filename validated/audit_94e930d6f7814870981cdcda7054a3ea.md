## Finding

The decimals-scaling helpers in `pallet-hyper-fungible-token` use `u8::saturating_sub`, which silently clamps to `0` whenever the destination chain's ERC20 decimals are *lower* than the local asset's decimals — collapsing the scale factor to `10^0 = 1` instead of dividing down. Since `send()` (an unprivileged, signed extrinsic) feeds a user-controlled `amount` straight through this helper before encoding the cross-chain `Message.amount`, an attacker can burn/escrow a small local amount and cause the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract to mint an amount inflated by `10^(local_decimals - erc_decimals)`.

### Root cause

`convert_to_erc20` (and its inverse `convert_to_balance`) compute the scale exponent with `saturating_sub`: [1](#0-0) 

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

When `erc_decimals < local_decimals` (e.g. bridging a local 18-decimal asset to a `WrappedHyperFungibleToken` that custodies a real 6-decimal ERC20 like USDC — an entirely normal registration, since `WrappedHyperFungibleToken` wraps arbitrary externally-defined ERC20s, unlike the "always 18" ERC6160 recommendation for native `HyperFungibleToken` deployments), `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so the multiplier collapses to `1` instead of the correct downward division by `10^(local_decimals - erc_decimals)`.

This is invoked directly from the unprivileged `send` extrinsic with the caller-supplied `amount`: [2](#0-1) 

```rust
let amount: u128 = params.amount.into();
let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);

let token_message = Message {
    from: sender.to_vec().into(),
    to: params.recipient.to_vec().into(),
    amount: alloy_primitives::U256::from_be_bytes(erc20_amount.to_big_endian()),
    ...
};
```

`erc_decimals` comes from `Precisions::<T>::get(asset_id, destination)` (admin-configured destination decimals) and `decimals` from the local asset's own metadata (or `T::Decimals` for the native asset) — both legitimate, non-malicious values. `register_token`'s admin-set `decimals` field is only meant to record the *real* ERC20 precision of the peer contract, not to be a security boundary against this specific ordering.

## Impact

For any token pair where the destination-chain ERC20 has fewer decimals than the local asset (a routine setup, e.g. local 18-decimal asset ↔ `WrappedHyperFungibleToken` custodying 6-decimal USDC), a user calling `send()` with a tiny local `amount` (burned/escrowed for a negligible real value) causes the destination contract to mint/unlock an amount inflated by `10^(local_decimals - erc_decimals)`. On the destination side, `onAccept` mints/unlocks that inflated amount directly to the attacker's chosen recipient: [3](#0-2) 

This drains the destination-side escrow/liquidity (for `WrappedHyperFungibleToken`) or creates unbacked supply (for burn/mint `HyperFungibleToken`), i.e. concrete theft of funds / unbacked mint reachable from a single signed extrinsic — no relayer or governance collusion required (the relayer only delivers the already-malformed message; the flaw is in the amount encoding itself).

## Likelihood

High for any deployment that registers a token pair with mismatched decimals in this direction, which is a foreseeable and documented use case (wrapping externally-defined, non-18-decimal ERC20s via `WrappedHyperFungibleToken`). No special privileges are needed by the attacker — only a normal `send()` call with a chosen small `amount`.

## Recommendation

Replace the one-directional `saturating_sub` scaling in `convert_to_erc20`/`convert_to_balance` with logic that explicitly branches on whether `erc_decimals >= local_decimals` or `erc_decimals < local_decimals`, multiplying in one case and dividing (with correct rounding, and rejecting values that would round to zero) in the other — mirroring the fix pattern already used correctly in `VWAPOracle::_normalizeAmount`: [4](#0-3) 

## Proof of Concept

1. Admin registers local asset `A` (18 decimals) as non-native, with `chains[EVM-X] = { token_contract: WrappedHFT_addr, decimals: 6 }` (WrappedHFT custodies real 6-decimal USDC on EVM-X).
2. Attacker calls `send(SendParams { asset_id: A, destination: EVM-X, recipient: attacker_evm, amount: 1_000_000_000_000 (1e12, i.e. 0.000001 token in 18-decimal terms), ... })`.
3. Inside `send()`: `erc_decimals = 6`, `decimals = 18`. `convert_to_erc20(1e12, 6, 18)` computes `10u128.pow(6u8.saturating_sub(18)) = 10^0 = 1`, so `erc20_amount = 1e12` — meant to be interpreted as a 6-decimal amount, i.e. 1,000,000 USDC, despite the attacker having burned only a dust-sized 18-decimal amount.
4. The dispatched `Message.amount = 1e12` is delivered to `WrappedHyperFungibleToken` on EVM-X, which unlocks/mints 1,000,000 USDC (6-decimal raw `1e12`) to `attacker_evm`, draining the contract's USDC custody far in excess of the value actually burned on the substrate side. [5](#0-4) [6](#0-5)

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}

    function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
