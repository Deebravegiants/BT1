### Title
Webhook `shop`, `topic`, `api-version`, and `webhook-id` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, yet `Registry.process` trusts the `shop` (and `topic`/`webhook_id`/`api_version`) values taken straight from HTTP headers when invoking the merchant's webhook handler. Because the app's `api_secret_key` is a single shared secret across every shop that installs the app, any merchant (including an attacker who has simply installed the app on their own store) can capture one authentic webhook for their own shop and replay it against the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a victim shop. The HMAC still validates (it only signs the body), so the handler processes attacker-controlled data attributed to the victim's tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, that signable string is defined as just the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are parsed independently from HTTP headers that are never fed into the HMAC computation: [3](#0-2) 

`Registry.process` only checks the HMAC (i.e., that the body is authentic) and then dispatches the handler using the unauthenticated `shop` header value: [4](#0-3) 

The broken identity binding, expressed as an equality that the code fails to enforce:
`HMAC-verified(raw_body)` ⇏ `shop header used for tenant attribution`.

Since `api_secret_key` is shared by the app across all shops (it's the app's secret, not a per-shop secret), any real merchant who has installed the app receives real, validly-HMAC'd webhooks for their own shop. Nothing in `HmacValidator`, `Request`, or `Registry` ties the signed body to the specific shop header that Shopify originally sent alongside it, so that same authentic (body, hmac) pair can be replayed with an arbitrary `shop-domain` header.

### Impact Explanation
This breaks the tenant boundary that `WebhookMetadata.shop` is supposed to guarantee. A host application that keys per-shop side effects (order/customer records, GDPR data-erasure jobs, billing state, etc.) off of `WebhookMetadata#shop` will apply attacker-controlled webhook bodies to a victim shop's tenant data. This is cross-tenant access/data injection achieved purely through this gem's own webhook verification logic, without needing the app's `client_secret`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Any Shopify Partner or public-app installer can obtain a free/dev store, install the target app to receive at least one legitimate webhook (topic of their choosing, e.g. `app/uninstalled` or any subscribed topic), capture the raw body + `X-Shopify-Hmac-Sha256` header, and replay it to the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` header pointing at any known victim shop domain. No secret material or victim credentials are required, only knowledge of the victim's `myshopify.com` domain, which is typically public.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed payload before it is handed to the handler — e.g., look up/validate that the `X-Shopify-Shop-Domain` corresponds to a shop with a valid, currently-installed session/access token for this app before dispatching, rather than trusting the header value outright once the body's HMAC checks out.

### Proof of Concept
```ruby
# Attacker installs the target app on their own dev store "attacker.myshopify.com"
# and receives one real, validly signed webhook, e.g.:
raw_body = '{"id": 1, "note": "malicious payload"}'
real_hmac_header = "X-Shopify-Hmac-Sha256: <value computed by Shopify for attacker's shop>"

# Attacker replays the exact same body/HMAC but swaps the shop-domain header
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac_header_value, # unchanged, still valid because body is unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate passes (it only checks raw_body),
#    handler.handle is invoked with shop: "victim-shop.myshopify.com"
#    even though the payload was never sent by Shopify for that shop.
``` [4](#0-3) [5](#0-4)
