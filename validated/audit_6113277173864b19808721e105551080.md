## Analysis

**Equality claimed to hold:** tokens Hinkal sends to `ExternalActionSwap` for the input leg, `uint256(-deltaAmounts[0])`, must be fully accounted for as either (a) swapped via `callRouter`, or (b) paid out as a fee to `circomData.relay`. Any leftover must be zero.

Tracing `swap()` in `contracts/external-actions/swaps/ExternalActionSwap.sol`: [1](#0-0) 

`inputAmount` excludes `flatFee` when `inputToken == feeStructure.feeToken`, and the swap only moves `inputAmount` through `callRouter`. The remainder is supposed to be forwarded to the relay: [2](#0-1) 

`sendToRelay` is a no-op whenever `relay == address(0)`: [3](#0-2) 

`relay == address(0)` is a value the attacker fully controls — nothing in `_externalTransact`/`transact` forces `relay != address(0)` for swap actions (the "relay not paid" check only applies to `_internalTransact`): [4](#0-3) [5](#0-4) 

So with `relay == address(0)`:
- The `flatFee` amount of `inputToken` excluded at line 48 is never swapped (excluded from `inputAmount`) and never sent anywhere (`sendToRelay` no-ops), so it is stranded as idle `inputToken` balance in `ExternalActionSwap`.
- `hinkalFee` (computed unconditionally from `swappedAmount`) is *always* subtracted from `amountToSendToHinkal` regardless of whether `relay` is zero, yet it is likewise never actually transferred anywhere when `relay == address(0)`, so it too is stranded as `outputToken` balance.

The final transfer to Hinkal only sends `amountToSendToHinkal = swappedAmount - totalFee`, so Hinkal's own balance-conservation check in `transact` (`balanceDif == amountChanges[i] + utxoAmount`) only validates what Hinkal itself received/sent — it has no visibility into, and does not catch, the residue left behind inside `ExternalActionSwap`: [6](#0-5) 

This confirms the core claim in the question for the `feeToken == inputToken` case: the fee-sized slice of the user's principal that is deliberately excluded from `inputAmount` is neither swapped nor paid to any relay, and simply accumulates as unspent balance in `ExternalActionSwap`, with no UTXO or commitment representing it. The same root cause (unconditional fee subtraction with no-op payout when `relay == address(0)`) also strands `hinkalFee` on the output side independent of which token is the fee token.

Whether this stranded balance can later be *swept by another user's swap* (turning freezing into theft) depends on whether `callRouter`/the router's calldata can pull more `inputToken` than the nominal `inputAmount` via the unlimited approval granted in `LifiExternalAction.callRouter`: [7](#0-6) 

`swappedAmount` is derived purely from the `outputToken` balance delta, with no check that the router consumed exactly `inputAmount` of `inputToken` — this is consistent with the question's theft escalation, though the primary, directly provable impact is the permanent stranding of the fee-sized principal slice.

### Title
Fee amounts computed in `ExternalActionSwap.swap` are deducted from user output but never paid when `relay == address(0)`, permanently stranding funds - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
When a user performs a swap through `ExternalActionSwap.swap` with `circomData.relay == address(0)` (fully attacker-controlled, no relay required), the `flatFee` portion excluded from `inputAmount` and the `hinkalFee` computed from `swappedAmount` are both subtracted from what is returned to Hinkal but never actually transferred anywhere, since `sendToRelay` silently no-ops for a zero relay address. The excluded value becomes idle token balance inside `ExternalActionSwap`, unrepresented by any UTXO/commitment, and is not caught by Hinkal's balance-conservation check.

### Finding Description
Broken equality: `uint256(-deltaAmounts[0])` (input tokens Hinkal transferred into `ExternalActionSwap`) should equal (tokens swapped via `callRouter`) + (tokens paid to `relay`) + (0 residue). In `swap()` at [1](#0-0)  the `flatFee` slice is carved out of `inputAmount` before calling `callRouter`, and later fee amounts (`relayFee`, `hinkalFee`) are subtracted from `amountToSendToHinkal` unconditionally at [2](#0-1) . The payout path, `sendToRelay`, is guarded by `relay != address(0)` [3](#0-2) , so when the attacker sets `circomData.relay = address(0)` these fee amounts are deducted from the user's proceeds but never sent to anyone. Nothing in `Hinkal.sol`/`_externalTransact` requires `relay != address(0)` for external actions (only `_internalTransact` enforces "relay not paid"), so this path is fully reachable by an unprivileged caller. Hinkal's balance check only compares its own balance delta to `amountChanges`/`utxoAmount`; it has no way to detect value left behind inside `ExternalActionSwap`.

### Impact Explanation
Every swap transaction executed with `relay == address(0)` and non-zero `flatFee`/`variableRate` permanently strands the corresponding fee-equivalent value inside the `ExternalActionSwap` contract instead of it reaching either the relay or the user. This is a permanent freezing of a slice of the user's own principal on every affected transaction, and it is repeatable indefinitely by any caller. The stranded balance sits unassigned to any UTXO, matching the Critical "permanent freezing of user funds" category; whether it can subsequently be swept by another party depends on router-calldata behavior in `LifiExternalAction.callRouter`, which is not independently verified here.

### Likelihood Explanation
No privileged role is needed: the caller fully controls `circomData.relay`, `circomData.feeStructure.flatFee`, and `circomData.feeStructure.variableRate` in their own proof-generation flow. Setting `relay = address(0)` is a normal, unrestricted choice (e.g., self-relaying), making this trivially reachable in a single transaction at no special cost beyond the stranded fee amount itself.

### Recommendation
In `ExternalActionSwap.swap`, only subtract `relayFee`/`hinkalFee` from `amountToSendToHinkal` when they are actually paid out (i.e., guard the `totalFee` computation on `circomData.relay != address(0)`, or route the fee amounts back to `amountToSendToHinkal` when `relay == address(0)` instead of discarding them). Ensure `sendToRelay` and the corresponding deduction from `amountToSendToHinkal` are kept in sync so no value is subtracted without being transferred somewhere.

### Proof of Concept
Foundry test: deploy `Hinkal` + `LifiExternalAction` (mocked router), fund a user, build a valid `CircomData` for a swap with `relay = address(0)`, `feeStructure.feeToken = inputToken`, `flatFee > 0`, and `variableRate > 0`. Generate a locally computed proof for the corresponding circuit inputs. After calling `transact`, assert:
1. `IERC20(inputToken).balanceOf(externalActionSwapAddress) == flatFee` (the carved-out flat fee never left the contract).
2. `IERC20(outputToken).balanceOf(externalActionSwapAddress) == hinkalFee` (the hinkal fee never left the contract).
3. No UTXO/commitment in `outCommitments`/`onChainCommitments` corresponds to either stranded amount.
4. `circomData.relay` balance of `inputToken`/`outputToken` is unchanged (confirming it was never paid).
