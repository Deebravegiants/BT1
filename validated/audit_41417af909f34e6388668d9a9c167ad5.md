## Title
Webhook Shop-Domain Header Is Not Covered by HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the shop identity (`shop-domain` header) that gets forwarded to the app's webhook handler is read from an unauthenticated HTTP header. Any party who can obtain one legitimately-signed webhook body/HMAC pair (e.g. by installing the app on their own store) can replay that exact body to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, and `Registry.process` will accept it as valid and dispatch it to the handler attributed to the victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a value entirely outside the HMAC computation: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., the raw body) and then forwards `request.shop` verbatim to the registered handler as the tenant identity for that webhook: [3](#0-2) 

Because the app's webhook signing secret (`Context.api_secret_key`) is shared across every shop that installs the app, and the `shop-domain` header is never bound into the signature, `bytes verified` (the raw body under HMAC) and `bytes parsed for tenant identity` (the header) diverge. An attacker in control of one installation (their own store) can capture a genuine `raw_body` + `hmac-sha256` header pair sent to their own endpoint, then re-POST that same body/HMAC to the app's public webhook URL with a different `shop-domain` header value. `Utils::HmacValidator.validate` will pass because it only recomputes the signature over the (unchanged) body: [4](#0-3) 

The handler then executes business logic believing the webhook body originated from the spoofed shop, i.e. an equality the app implicitly relies on — `shop_authenticated_by_hmac == shop_used_for_tenant_routing` — is broken.

### Impact Explanation
This breaks tenant isolation: an app built on this gem that uses `WebhookMetadata#shop` (populated from the unauthenticated header) to route data, delete records, or act on a specific merchant's resources can be tricked into performing that action against an arbitrary victim shop identifier supplied by the attacker. This is especially severe for the mandatory compliance topics (`customers/redact`, `customers/data_request`, `shop/redact`) where the shop value drives destructive/data-disclosure operations. This constitutes cross-tenant access, a Critical-impact class per the accepted vulnerability categories.

### Likelihood Explanation
Any merchant who installs the app on their own store receives legitimate webhook deliveries with valid HMACs for their own shop — no privileged credentials, access tokens, or knowledge of `api_secret_key` are required. They only need to capture one raw body + HMAC pair from their own installation and replay it to the app's (necessarily internet-reachable) webhook endpoint with a modified `shop-domain` header. This is a low-effort, no-privilege attack path.

### Recommendation
Do not treat `shop-domain` (or any other header value) as an authenticated identity. Either:
- Bind the shop domain into the signed payload validation (e.g., require correlating the header value against the shop tied to the specific webhook subscription/registration that this app created), or
- Cross-check the incoming `shop-domain` against a known/expected set of shops (e.g., installed shops with active sessions) before dispatching to handlers, and document clearly that `WebhookMetadata#shop` is unauthenticated input that callers must validate independently before using it as a tenant key.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing:
   - `raw_body` = `{"id":123, ...}`
   - `shopify-hmac-sha256` = `<valid HMAC of raw_body under app's shared client_secret>`
2. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with:
   - Same `raw_body` and `shopify-hmac-sha256` header (unchanged, still valid)
   - `shopify-shop-domain: victim-shop.myshopify.com` (or any other domain of interest)
   - `shopify-topic` unchanged
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and succeeds.
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)`, causing the app to process/act on data attributed to `victim-shop.myshopify.com` despite the payload never having been sent by Shopify for that shop.
