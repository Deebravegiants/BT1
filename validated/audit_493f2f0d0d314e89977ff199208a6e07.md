### Title
Attacker-crafted V2 pre-seed can drive `pair.mint()`'s LP-share computation to zero, permanently reverting `finalizeGraduation` and freezing curve funds in `Bonding` - ([File: packages/contracts/src/Bonding.sol])

### Summary
The external report is a `CHECK`-fail DoS in TensorFlow: an unvalidated input tensor is passed into a downstream routine (`vec<T>`) whose hard invariant (`rank == 1`) is silently assumed rather than checked, so a crafted input reaches the assumption-violating code path and the process aborts. The alt.fun analog is `Bonding._routerDepositAndDispose` / `_seedDirectMint`, which pass attacker-influenceable amounts into HyperSwap V2's `pair.mint()`, whose hard invariant `require(liquidity > 0, 'UniswapV2: INSUFFICIENT_LIQUIDITY_MINTED')` is not pre-validated by `Bonding` before the call. A hostile V2 pre-seed can be shaped so the "balanced-subset deposit" that `_routerDepositAndDispose` computes rounds to a liquidity value of exactly zero, causing `pair.mint()` to revert unconditionally inside `finalizeGraduation`, with no retry or rollback path available.

### Finding Description
`finalizeGraduation` is permissionless and, once `Lifecycle.Graduating` is entered, is the *only* path back to a usable state [1](#0-0) . Phase 1 (`_prepareGraduationLiquidity`, run inline at the threshold-crossing buy or via permissionless `triggerGraduation`) irreversibly drains the curve: it burns unsold tokens, calls `Router.graduate` to pull all curve-raised LT out of the bonding `Pair` into `Bonding`, and computes the LP-bound `tokensForLP`/`ltFromPair` split [2](#0-1) . From that point the token is committed to phase 2; there is no path to reopen the curve.

Phase 2 (`finalizeGraduation` → `_seedUniswapV2Direct`) is explicitly hardened against a hostile pre-seed of the HyperSwap V2 pair, which the scope rules confirm is a reachable, unprivileged action (pre-seeding the pair before graduation). The code's own natspec documents the exact failure mode being guarded against: an extreme pre-seed could otherwise drive the rebalance swap to consume 100% of one side, leaving `_routerDepositAndDispose`'s deposit with a zero-valued side, so `finalizeGraduation` returns `liquidity = 0` and `LPLock.recordLock` would reject a zero-amount lock [3](#0-2) . The mitigation is a 99%-of-budget swap cap (`_swapBudget`) intended to guarantee both `remToken > 0` and `remLT > 0` reach `_routerDepositAndDispose`'s `addLiquidity` call [4](#0-3) .

However, `remToken > 0 && remLT > 0` is necessary but not sufficient for `pair.mint()` to succeed. Standard UniswapV2 `mint()` computes `liquidity = min(amount0 * totalSupply / reserve0, amount1 * totalSupply / reserve1)` and hard-reverts with `INSUFFICIENT_LIQUIDITY_MINTED` if that value floors to zero — this is precisely the unvalidated-invariant class the CVE describes (a downstream primitive with a hard assumption that the caller does not pre-check). `Bonding` never checks this before calling `router.addLiquidity` (which itself only validates `amountA/B` against slippage `min=1`, not the resulting LP share) [5](#0-4) . An attacker who has already minted a nonzero `totalSupply` on the pair (a "mint pre-seed", explicitly enumerated as Regime 3 in the natspec [6](#0-5) ) can choose reserves/`totalSupply` such that the post-swap, post-rebalance "matched-ratio subset" (`remToken`, `remLT`) produces `amount * totalSupply / reserve` values that both floor to 0 under integer division — even though `remToken` and `remLT` are individually nonzero. This is reachable by any unprivileged wallet: `Bonding.uniswapV2Factory`/`uniswapV2Router` addresses are fixed and public, and nothing prevents a third party from calling `createPair` + `mint` on the HyperSwap V2 factory for the (Token, LT) pair before the launch reaches graduation.

Because `finalizeGraduation` has already run phase 1 (drained the curve's LT, burned unsold tokens) before this revert path is hit, a stuck token remains permanently in `Lifecycle.Graduating`: `TokenNotTrading`/`TokenIsGraduating` reverts block all further `Zap.buy`/`Zap.sell` on it, `LPLock.recordLock` never fires so no LP is ever locked, and the entire curve-raised LT plus the 250M LP-reserve token allocation sit stranded on `Bonding` with no recovery function in the current contract.

### Impact Explanation
This is a permanent freezing of trader and creator funds: once a token has crossed the graduation threshold and entered `Lifecycle.Graduating`, all curve-raised LT (potentially tens of thousands of USD-equivalent) and the LP-reserve token allocation are moved out of the tradeable `Pair` and held by `Bonding` pending `finalizeGraduation`. If that call is made to permanently revert via a crafted V2 pre-seed, holders of the token can never sell (curve trading is frozen, no V2 pool exists), the creator's token is permanently bricked, and the LT backing it is inaccessible. This matches the "permanent freezing of trader, creator or LP funds" bar required for a valid analog.

### Likelihood Explanation
Reachable entirely by unprivileged actions: creating/pre-seeding the HyperSwap V2 pair for a specific (Token, LT) address is public and requires no special role, and graduation itself can be triggered permissionlessly via `Bonding.triggerGraduation` or an ordinary `Zap.buy` that crosses the threshold. The attacker needs to predict or target a specific token's graduation (token addresses and LT pairings are public before/at launch, and the vanity-mined token address plus its paired LT are known immediately after `launch()`), then construct a pre-seed ratio/size engineered to survive the 99%-budget rebalance and still round the final deposit's minted-LP computation to zero. This requires some precision in sizing (since `tokensForLP`/`ltFromPair` are pinned at phase-1's curve-close price and are not perfectly predictable at pre-seed time, but the attacker can front-run/observe the threshold-crossing transaction and craft the pre-seed reactively, or repeatedly re-seed cheaply before each graduation attempt). Given the developers themselves flagged and partially mitigated this exact class of attack (per the `_swapBudget` natspec) without fully closing the residual `pair.mint()` zero-liquidity edge case, likelihood is assessed as realistic for a determined attacker, though it requires more precision than a trivial call.

### Recommendation
Before returning from `_routerDepositAndDispose` (and consequently before `finalizeGraduation` calls `LPLock.recordLock`), explicitly check that the computed `liquidity` (or a pre-check equivalent of the V2 mint formula) will be nonzero, and if not, either (a) skip the `addLiquidity` call and fall back to burning/sweeping the remainder as already done for the zero-side case, recording a best-effort minimal lock, or (b) wrap the router call in a way that a rounding failure does not leave the token permanently stuck in `Lifecycle.Graduating` — e.g., add an explicit, permissioned/timelocked recovery path that can re-attempt seeding with adjusted parameters, or allow retrying `finalizeGraduation` at a later state where the pool ratio may have shifted enough to escape the zero-liquidity edge case, rather than leaving no recovery route at all.

### Proof of Concept
Conceptual (cannot be fully simulated without a fork of HyperSwap V2 + BounceTech LT, but the code path is deterministic):
1. Attacker observes a curve token approaching `canGraduate()` (public `previewLtUntilGraduation`/`canGraduate` views).
2. Attacker calls HyperSwap V2 `Factory.createPair(token, lt)` and `pair.mint(attacker)` with a small, carefully chosen `(reserveToken, reserveLT)` such that `totalSupply` is minimal and disproportionate to the eventual graduation-time `(tokensForLP, ltFromPair)`.
3. Graduation triggers (via a normal `Zap.buy` crossing the threshold, or attacker's own `triggerGraduation` call), `_enterGraduating` runs phase 1, draining the curve LT into `Bonding` and computing `tokensForLP`/`ltFromPair`.
4. Anyone calls `finalizeGraduation(token)`. `_seedUniswapV2Direct` detects `totalSupply != 0` and takes Regime 3 (`_seedRebalancing`); depending on the attacker's chosen ratio, `_pairRebalance` executes a swap capped at 99% of budget, and `_routerDepositAndDispose` is invoked with the post-swap remainders.
5. If the attacker sized the pre-seed so the resulting `remToken`/`remLT` still yield `min(remToken*totalSupply/reserveToken, remLT*totalSupply/reserveLT) == 0` under V2's mint formula, `IUniswapV2Router02.addLiquidity` reverts inside `pair.mint()` with `INSUFFICIENT_LIQUIDITY_MINTED`, `finalizeGraduation` reverts, and the token remains permanently stuck in `Lifecycle.Graduating` with all curve-raised LT and the LP token reserve stranded in `Bonding`.

Note: precise numeric parameters that trigger the zero-liquidity rounding depend on the token's actual graduation-time reserves, which are not fixed constants in the codebase and would need to be derived/tuned against a live or forked deployment; this could not be further verified without executable test infrastructure.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }
