### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are trusted from unauthenticated headers while the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never included in the HMAC computation. `Registry.process` validates the HMAC over the body alone and then hands the attacker-controlled `shop` header value to the app's webhook handler as an authenticated fact, breaking the binding `shop-verified-by-HMAC == shop-delivered-to-handler`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

which returns only `@raw_body`. Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `to_signable_string` (body only), and — once the body signature checks out — forwards the unauthenticated `request.shop` header value directly to the registered handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the body: [4](#0-3) 

The gem's own documented usage pattern instructs developers to key downstream tenant processing off this unauthenticated `shop` field, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` (`docs/usage/webhooks.md`), and the `WebhookMetadata` struct exposes `shop` as a first-class trusted attribute: [5](#0-4) 

Because the header is never covered by the signature, an unprivileged internet user who possesses **any one** valid `(body, hmac)` pair for a topic (trivially obtainable by installing the app on a free/dev store they control and capturing the real webhook Shopify sends them) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value naming a victim shop. `Registry.process` will still consider the HMAC valid (it only checks the body) and will pass `shop: "<victim-shop>.myshopify.com"` to the handler alongside the attacker's own body content.

This breaks the identity binding: `shop authenticated by HMAC` ≠ `shop stored/used as the tenant key downstream`. Before the attack: legitimate webhook has `shop == <attacker-shop>` for a body HMAC-signed by Shopify. After the attack: the same signed body is delivered to the app claiming `shop == <victim-shop>`, and nothing in this gem detects the mismatch.

### Impact Explanation
If a host application follows this gem's documented pattern and uses `data.shop` to select which tenant's records to update, enqueue jobs against, or to route mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`), an attacker can inject arbitrary (self-crafted, since they control their own shop's installed app data) webhook payloads that are processed as belonging to a victim shop — a cross-tenant data-integrity/cross-tenant access issue. For example, an attacker could trigger `app/uninstalled` or `shop/redact`-style processing, or feed falsified `orders/create`/`customers/update` payloads, attributed to a shop they do not own, purely by controlling HTTP headers on a replayed, still-validly-signed body.

### Likelihood Explanation
High. No secrets are required — the attacker only needs one legitimate webhook delivery to their own store (any developer/free plan) to obtain a valid `(body, HMAC)` pair, and full control over headers when POSTing to the app's public webhook callback endpoint, which by design must be internet-reachable and unauthenticated (that's how Shopify delivers webhooks). This is a straightforward, repeatable replay technique.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind them (e.g., derive/verify `shop` independently, such as cross-checking it against an app's known/registered shops before dispatch), so that tampering with headers invalidates the HMAC. At minimum, document prominently that `data.shop` from `WebhookMetadata` is unauthenticated and must not be used as a sole tenant-selection key without additional verification (e.g., matching against a shop that has an active, stored session/installation).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers/receives a real webhook, e.g. `orders/create`, capturing the raw body `B` and the header `x-shopify-hmac-sha256: H` (a valid Base64 HMAC-SHA256 of `B` under the app's real `api_secret_key`, computed by Shopify).
2. Attacker sends a POST to the app's public webhook callback endpoint with:
   - Body: exactly `B` (unchanged, so the HMAC in step 1 still validates)
   - Headers: `x-shopify-hmac-sha256: H`, `x-shopify-topic: orders/create`, `x-shopify-shop-domain: victim-shop.myshopify.com`, `x-shopify-webhook-id: <any>`
3. `ShopifyAPI::Webhooks::Registry.process` constructs a `Request`, calls `Utils::HmacValidator.validate(request)` which recomputes HMAC over `B` only and matches `H` — validation passes.
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, exactly as shown in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though this body was never associated with `victim-shop.myshopify.com` by Shopify.
