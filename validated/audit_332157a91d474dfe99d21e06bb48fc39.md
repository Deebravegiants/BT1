### Title
Unbounded recursive SCALE decode of cross-chain calldata causes stack-exhaustion DoS in `pallet-hyper-fungible-token` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`HyperFungibleToken::on_accept` decodes the attacker-supplied `runtime_call` bytes from an incoming ISMP `PostRequest` using plain `T::RuntimeCall::decode`, with no recursion-depth limit [1](#0-0) . The sibling pallet `pallet-call-decompressor` already recognizes this exact bug class — a deeply nested `Box<RuntimeCall>` (e.g. `Sudo::sudo` wrapped thousands of times) blowing the stack during SCALE decoding — and mitigates it with an explicit `MAX_EXTRINSIC_DECODE_DEPTH_LIMIT` of 4 via `decode_all_with_depth_limit` [2](#0-1) [3](#0-2) , with a dedicated regression test proving the attack `decompress_stack_exhaustion_poc` [4](#0-3) . The HFT calldata path was never given the same treatment.

### Finding Description
`SubstrateCalldata` carries an attacker-controlled, SCALE-encoded `runtime_call: Vec<u8>` field that is forwarded verbatim from the source-chain `HyperFungibleToken`/`WrappedHyperFungibleToken` contract's `send()` call, via `SendParams.call_data`, as the `data` field of the cross-chain `Message` [5](#0-4) . Any caller of `send()` on a registered peer contract can set this `call_data` to an arbitrary byte string; nothing on the source side validates its structure.

When the message is delivered on the destination chain, `on_accept` first decodes `SubstrateCalldata`, then decodes `substrate_data.runtime_call` directly into `T::RuntimeCall` with the unguarded `Decode::decode`: [6](#0-5) [1](#0-0) 

`RuntimeCall` is a large, deeply-nesting enum (it embeds `pallet_sudo::Call::sudo { call: Box<RuntimeCall> }`, `pallet_utility::Call::batch { calls: Vec<RuntimeCall> }`, etc.), so each level of nesting recurses through the codec's `Decode` implementation and consumes a large stack frame. This is structurally identical to the `cr_parser_parse_any_core` unbounded-recursion pattern in the reference advisory: a parser recursing once per nested construct with no depth cap, driven entirely by attacker input length/structure.

The codebase's own fix for the near-identical path in `pallet-call-decompressor` demonstrates that the default codec recursion guard is *not* sufficient to stop stack exhaustion for `RuntimeCall`-sized enums — that's why an explicit depth limit of 4 (not the codec default of 256) was introduced there [2](#0-1) . `pallet-hyper-fungible-token::on_accept` never applies any such bound.

### Impact Explanation
A crafted nested `RuntimeCall` blob delivered as HFT calldata causes the destination chain's message-handling thread to exhaust its stack while decoding, aborting/crashing block execution for that message. Because `on_accept` runs inside ISMP message dispatch (reachable by any relayer delivering a proof of a POST request that any unprivileged EVM-side caller can originate via `send()`), this is a High-severity denial-of-service on the token-bridge module: it can repeatedly stall or crash the executing node/collator whenever the malicious message is processed, which is a "route unable to deliver messages" condition for HFT traffic on that chain.

### Likelihood Explanation
Likelihood is high: `send()` calldata is fully attacker-controlled and requires no privilege beyond calling the public bridge entrypoint on a registered peer contract; the destination pallet applies no recursion/size gating before calling `Decode::decode` on the embedded call bytes, unlike the parallel call-decompressor path that was already hardened for this exact class of input.

### Recommendation
Bound the recursion depth (and/or size) when decoding `substrate_data.runtime_call`, mirroring the fix already applied in `pallet-call-decompressor`: use `T::RuntimeCall::decode_all_with_depth_limit(N, &mut &*substrate_data.runtime_call)` with a small, purpose-fit `N` (matching how deep legitimate HFT calldata calls are expected to nest), and reject with `HftError::RuntimeCallDecodeError` on failure, exactly as `decode_and_execute` does.

### Proof of Concept
Following the pattern already proven in `decompress_stack_exhaustion_poc` [4](#0-3) :
1. Build `nested_calls = RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(inner) })`, wrapped ~1000 times.
2. SCALE-encode it and place it into `SubstrateCalldata { signature: None, runtime_call: nested_calls.encode() }`.
3. Encode this as the `data` field of an ABI `Message` (as done in `should_receive_asset_with_calldata` [7](#0-6) ) and deliver via `HyperFungibleToken::default().on_accept(post)`.
4. Because `on_accept` calls `T::RuntimeCall::decode` with no depth limit [1](#0-0) , decoding recurses through ~1000 `Sudo` wrappers and exhausts the call stack, instead of returning `HftError::RuntimeCallDecodeError` as intended.

#[test]
fn decompress_stack_exhaustion_poc() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		use crate::runtime::RuntimeCall;
		use codec::Encode;

		let inner_call = RuntimeCall::System(frame_system::Call::remark { remark: Vec::new() });

		let mut nested_calls =
			RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(inner_call) });

		for _ in 1..1000 {
			nested_calls =
				RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(nested_calls) });
		}

		let encoded = nested_calls.encode();
		let mut buffer = vec![0u8; 1000000];
		let compressed = zstd_safe::compress(&mut buffer[..], encoded.as_slice(), 3).unwrap();
		let final_compressed_call = buffer[..compressed].to_vec();

		let res = pallet_call_decompressor::Pallet::<Test>::decompress_call(
			RuntimeOrigin::none(),
			final_compressed_call.to_vec(),
			encoded.len() as u32,
		)
		.err()
		.unwrap();

		assert_eq!(
			res,
			DispatchError::Module(ModuleError {
				index: 10,
				error: [3, 0, 0, 0],
				message: Some("ErrorDecodingCall")
			})
		);
	});
}
