## Title
Extreme-ratio hostile pre-seed of the HyperSwap TOKEN/LT pair forces the graduation LP to open materially off the curve-close price - (File: `packages/contracts/src/Bonding.sol`)

## Summary
The external report describes verification code that terminates a trust chain at a peer-supplied, unverified intermediate (`X509_V_FLAG_PARTIAL_CHAIN`) instead of a genuinely trusted anchor, letting an attacker substitute a certificate they control for the real root. The closest reachable analog in alt.fun is `Bonding._ensureUniswapV2Pair` / `finalizeGraduation`, which unconditionally treats whatever address `IUniswapV2Factory.getPair(token, lt)` returns — including a pair an attacker permissionlessly pre-created and pre-seeded — as the trust anchor for the protocol's one-shot, un-reversible LP lock, without any bound on how far the resulting price can be pushed from the curve close.

## Finding Description
`_ensureUniswapV2Pair` looks up or creates the HyperSwap V2 pair and returns it as-is: [1](#0-0) 

Because pair creation and `pair.mint()` are permissionless on any V2 fork, an attacker can front-run phase 2 (`finalizeGraduation`) by creating the pair and minting LP against a self-funded, arbitrarily skewed `(TOKEN, LT)` ratio (Regime 3 in the docs) — as demonstrated by `test_brick_resistance_frontRun_dust_seed` and the extreme-ratio variant `test_hostilePreSeed_budgetCappedSwap_isNotProfitable`. The protocol's defense (`_seedRebalancing` → `_pairRebalance` → `_routerDepositAndDispose`) rebalances the pool toward the cached curve-close ratio via a direct `pair.swap`, but the rebalance input is deliberately capped at 99% of the available inventory (`_swapBudget`) to guarantee `finalizeGraduation` can never revert: [2](#0-1) 

When the required corrective swap exceeds that budget — reachable with a large enough pre-seed ratio (e.g., LT reserve ≈200× target with TOKEN reserve ≈1% of target, well within an attacker's means since only the attacker's own capital is at risk) — the cap binds and `_routerDepositAndDispose` deposits the remaining inventory at a pool state that is still materially away from the curve-close ratio. The protocol's own regression test explicitly documents and accepts this outcome: [3](#0-2) 

`finalizeGraduation` then calls `LPLock.recordLock` unconditionally on whatever `liquidity` results, with no price-deviation check between the intended `p.tokensForLP / p.ltFromPair` ratio and the actual post-seed pool ratio: [4](#0-3) 

`LPLock.recordLock` itself performs no price-anchor validation either — it only checks the caller is an authorized locker and that the LP balance is sufficient, then permanently locks it (no withdraw path in v1): [5](#0-4) 

This is the structural analog to the CVE: the system accepts an untrusted, attacker-supplied intermediate (the pre-seeded pair state) as the final trust anchor for a security-critical, one-shot, irreversible action (permanent LP lock at a given price), instead of requiring the anchor to match a fully-verified reference (the exact curve-close price with no tolerance/backstop beyond a budget cap that can be deliberately exhausted).

## Impact Explanation
This matches the "Validate" criteria for "an LP seeded away from the curve close price." A sufficiently large, deliberately lopsided pre-seed (bounded only by the attacker's own capital, which does not need to be recovered) forces the permissionless `finalizeGraduation` caller (anyone, including the protocol's own keeper) to lock the protocol's real curve-raised LT and reserved tokens into a pool priced significantly (>20%, per the test's own assertion) away from the true curve-close price. Although the current test asserts the *attacker* cannot profit net-positive from this specific maneuver (the over-funded side is confiscated to the owner), the resulting mispriced, permanently-locked LP is a direct, irreversible value distortion of protocol/creator-owned LP — it opens arbitrage that extracts value from the pool at the expense of whoever holds the locked position, and there is no mechanism to correct it after `LPLock.recordLock` executes once (`AlreadyLocked` guard, no re-seed, no withdraw).

## Likelihood Explanation
Reachable by any unprivileged address: pre-create the HyperSwap pair via the public V2 factory, transfer TOKEN and LT to it in an extreme ratio, and call `pair.mint(attacker)` — entirely before `finalizeGraduation` is called. The permissionless nature of `finalizeGraduation` and the two-phase gap between `_enterGraduating` (phase 1) and `finalizeGraduation` (phase 2) give the attacker a guaranteed window to front-run every graduation. The protocol's own test suite explicitly reproduces this exact "M-02" scenario as a known, accepted residual rather than a prevented one, confirming the condition is realistically triggerable with plausible parameters (no exotic preconditions needed beyond ordinary capital to fund the pre-seed).

## Recommendation
Add a bounded price-deviation guard after the rebalance-and-deposit sequence in `_seedUniswapV2Direct`/`_routerDepositAndDispose`: if the post-seed pool ratio still falls outside an acceptable band (e.g., a few hundred bps) of `tokensForLP : ltFromPair`, do not lock the LP as final — either escalate the swap budget dynamically (funded from protocol treasury) to fully correct the ratio before minting, or route the excess mismatch into a recoverable escrow rather than an unconditional `LPLock.recordLock`, so a governance/ops path can remediate extreme pre-seed cases instead of permanently locking a mispriced pool.

## Proof of Concept
Based on the existing repository test, which already demonstrates the mechanism end-to-end: [6](#0-5) 
1. Launch a token and drive it into `Lifecycle.Graduating` (`_enterGraduating`).
2. Read `pendingGraduation` to get `tokensForLP`/`ltFromPair`.
3. As an unprivileged "griefer," create the HyperSwap pair via the factory, fund it with `reserveToken = tokensForLP/100` and `reserveLt = ltFromPair*200`, and call `pair.mint(griefer)`.
4. Call `Bonding.finalizeGraduation(tokenAddress)` (permissionless).
5. Observe: graduation succeeds (no revert/brick), but the resulting pool price is >20% off the intended curve-close price (`_poolPriceLtPerToken` assertion), and this state is now permanently recorded in `LPLock` with no correction path.

Note: this exact scenario (`M-02`) is already present as a named regression test in the target repository, indicating the underlying condition is known to the maintainers; whether it is considered "fixed/accepted by design" versus an open finding could not be fully confirmed from the available index (no changelog/audit-report file was found enumerating M-02's disposition). This should be verified against the project's issue tracker or audit history before treating it as a fresh finding.

```text
    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
```

```text
    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }
```

```text
    /// @notice M-02 reproducer. An LT-rich mint pre-seed so lopsided that the
    ///         TOKEN-side rebalance swap exhausts its full budget (~99% of
    ///         `tokensForLP`) without reaching the cached ratio, so the pool
    ///         deposits materially off curve-close. Finalize must still succeed
    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );
```

```text
    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
```
