### Title
Webhook tenant identity (`shop-domain`) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC over the raw body only (`to_signable_string` returns `@raw_body`), while the `shop` value that `Registry.process` hands to the app's webhook handler is read from an HTTP header that is never included in the signed content.

### Finding Description
The webhook verification flow is:
1. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which validates `request.hmac` against `HMAC-SHA256(secret, request.to_signable_string)` [3](#0-2) .
2. `to_signable_string` is defined to return only `@raw_body` [4](#0-3) .
3. `request.shop`, which is passed on as the tenant identifier to `WebhookMetadata` and ultimately to the app's `handler.handle` call, is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header via `shopify_header` [5](#0-4) [6](#0-5) .

Because the `client_secret` used to compute the HMAC is a single, global secret shared by the app across every shop that installs it (not shop-specific), the equality the code implicitly relies on — "the shop that produced a valid HMAC for this body" == "the shop named in the `shop-domain` header" — does not hold. Any party that has legitimately obtained a valid `(body, hmac)` pair for the app's secret (e.g., by installing the app on their own store and capturing one of their own webhook deliveries) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still pass, because it only checks the body bytes, not the header. The app then processes that payload attributed to a shop the attacker never controlled.

### Impact Explanation
This breaks the tenant/authentication boundary between shops using the same app: an unprivileged (but app-installed) user can make the host application believe an event/body originated from a victim shop. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (e.g., to look up the target shop's session/access token and act on its behalf, credit/debit shop-scoped state, or trigger shop-specific side effects), this enables cross-tenant data confusion or actions performed under a victim shop's identity — matching the "cross-tenant access" class of impact.

### Likelihood Explanation
Exploitation requires only: (a) the attacker be able to install the app on at least one shop (a normal, permissionless action for any Shopify merchant/dev-store owner) to observe one legitimate `(body, hmac)` pair, and (b) the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged credential is required. This is a realistic, low-effort attack path fully reachable through the gem's own public webhook-processing API (`Registry.process`).

### Recommendation
Bind the identity fields that the application relies on (at minimum `shop`, and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the verified body (e.g., include it in `to_signable_string`, or require the host app to cross-check `shop` against a shop-scoped secret/session rather than trusting the header). At minimum, document that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be treated as trusted tenant context on its own.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the resulting valid header `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's shared `client_secret`).
2. Attacker sends a raw POST to the app's webhook endpoint with:
   - Body: `B` (unmodified)
   - Headers: `X-Shopify-Hmac-Sha256: H` (unmodified), `X-Shopify-Topic: orders/create` (unmodified), `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(secret, B)` and matches `H` — validation succeeds because `to_signable_string` never included the shop header [4](#0-3) .
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [6](#0-5) , causing the app to process attacker-controlled data as if it belonged to the victim shop.
