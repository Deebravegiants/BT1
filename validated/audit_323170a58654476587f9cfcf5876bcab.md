### Title
Webhook Shop/Topic/Metadata Headers Are Not Covered by HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values — which are read straight from unauthenticated HTTP headers — are used by `Registry.process` to route the payload and to identify the tenant (`shop`) for the handler. Because these identity-bearing fields are not part of the signed message, an attacker who possesses one valid `(raw_body, hmac)` pair can replay it with a different `shop-domain` (or `topic`) header and still pass HMAC validation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#hmac` decodes the `hmac-sha256` header, which `HmacValidator.validate` compares against `HMAC-SHA256(secret, raw_body)`: [2](#0-1) 

However, `shop`, `topic`, `webhook_id`, and `api_version` are all read from headers that are never mixed into the signed string: [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then uses `request.topic` to select the handler and `request.shop` as the tenant identity passed to the handler's `WebhookMetadata`: [4](#0-3) 

The equality the code should be enforcing is: `shop-domain header used for tenant identity == shop bound inside the HMAC-signed message`. Instead the gem enforces only `HMAC(secret, raw_body) == received_hmac`, with `shop`/`topic`/`webhook_id` left completely unauthenticated. Since Shopify's real webhook payloads for many topics do not embed the shop domain inside the JSON body itself (it's carried purely in the header), an attacker who has legitimately received one valid webhook delivery (e.g., for their own installed shop) can capture the `(raw_body, x-shopify-hmac-sha256)` pair and resend it to the same endpoint with an altered `x-shopify-shop-domain` header (and/or altered `x-shopify-topic`), and `Utils::HmacValidator.validate` will still return `true` because it only checks the body bytes.

### Impact Explanation
This breaks the shop-domain identity binding this gem's own webhook-processing API is meant to guarantee ("this webhook body is authentically from Shopify for shop X"). A host application that keys per-tenant behavior off `WebhookMetadata#shop` (e.g., looking up the shop's session/access token, updating that shop's local records, or triggering that shop's business logic) can be made to process attacker-controlled webhook content under a different shop's identity — i.e., cross-tenant access/injection, which matches the Critical impact category (cross-tenant access) defined in scope.

### Likelihood Explanation
The attacker needs no privileged credentials, `api_secret_key`, or access token — only the ability to capture one legitimately delivered webhook body+HMAC pair (trivially available to any merchant with the app installed on their own store, or via a public webhook proxy endpoint) and resend it with a forged `shop-domain`/`topic` header to the app's public webhook endpoint. This is fully reachable through the gem's documented `Registry.process` / `Request` API with no reliance on host-app misuse beyond storing/using `request.shop` as the tenant key, which is exactly the pattern the docs recommend.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signed message construction, or otherwise cryptographically bind them to the body (e.g., verify against a signed envelope Shopify provides that covers these fields) rather than trusting them as free-standing headers once body-HMAC validation succeeds.

### Proof of Concept
1. App has webhooks registered for shop `victim.myshopify.com` and shop `attacker.myshopify.com` (attacker installed the app on their own store).
2. Attacker triggers an event on their own store producing a webhook delivery to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-for-body>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value, then resends a new HTTP request to the same endpoint with `x-shopify-shop-domain: victim.myshopify.com` (all other headers/body unchanged).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-derives `HMAC(secret, raw_body)` and compares it to the (unchanged, still valid) received HMAC — validation passes.
5. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's order data>, ...)`, causing the host application to process attacker-controlled data as if it belonged to `victim.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
