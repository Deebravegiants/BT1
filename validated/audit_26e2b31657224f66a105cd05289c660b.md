### Title
Unauthenticated arbitrary runtime-call execution via unsigned cross-chain calldata in `pallet-hyper-fungible-token` - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`HyperFungibleToken::on_accept` decodes an optional `data` field from a cross-chain ISMP `PostRequest` body and, when no substrate-side signature is attached, dispatches the embedded `RuntimeCall` under an origin derived directly from the message's `from` field — a value fully controlled by whatever EVM contract sent the message (`HyperFungibleTokenUpgradeable.send`), without any signature or capability check binding that call to the named origin.

### Finding Description
`on_accept` ( [1](#0-0) ) decodes the ABI `Message` from the incoming request body, then at [2](#0-1)  decodes an optional `SubstrateCalldata` from `message.data`, which carries an arbitrary `runtime_call` and an *optional* `signature`.

When `substrate_data.signature` is `None`, the origin used to dispatch the call is computed purely from `message.from` — converted via `EvmToSubstrate::convert` for EVM sources, or taken as a raw 32-byte account for substrate sources — with **no cryptographic proof that the party constructing the cross-chain message controls that account**: [3](#0-2) 

The only gates before dispatch are that `local_asset_id` maps from a registered peer contract (`ContractToAsset`) and that the call passes `BaseCallFilter`: [4](#0-3) 

Crucially, `message.from` is only the *stated* sender, i.e., whatever bytes the source-chain HFT/WrappedHFT contract chose to write into `Message.from` when constructing the cross-chain payload — a field explicitly documented as "the original sender (used for timeout refunds)" ( [5](#0-4) ). The registered peer contract on the source chain is the trust boundary for the token transfer itself, but nothing in this code proves that the *destination-chain account named by `from`* actually authorized the embedded `runtime_call`. Any account whose EVM/Substrate address is convertible from an attacker-influenced `from` field — including accounts the attacker does not control but can *name* — has the runtime call dispatched as `RawOrigin::Signed(origin)` on their behalf, subject only to `BaseCallFilter`.

This is structurally the same bug class as nbgitpuller's CVE-2021-39160: an external, attacker-influenced input (there, a URL parameter later fed into a shell command; here, the unauthenticated `from`/`data` fields of a cross-chain message) is used to trigger execution of arbitrary code/commands (`RuntimeCall::dispatch`) without adequate sanitization/authentication of who is actually authorizing that action.

### Impact Explanation
An attacker can craft a `send()` call (or equivalent gateway message) on any peer EVM chain, setting `data` to an unsigned `SubstrateCalldata{ runtime_call, signature: None }` and arranging for `from` to resolve (via `EvmToSubstrate::convert` or raw 32-byte copy) to a victim account. If the token transfer itself is permissionless (any address can call `send`), the attacker can then have arbitrary filtered dispatchable calls executed as `RawOrigin::Signed(victim)` — e.g. `Balances::transfer`, staking, governance voting, or other calls not blocked by `BaseCallFilter` — constituting unauthorized state-changing actions performed against an account the attacker does not control. This is an "unauthorized app action" class impact, potentially leading to theft of funds held by the named account or corruption of protocol state (e.g. draining balances, staking manipulation) depending on which dispatchables are exposed.

### Likelihood Explanation
Reachability requires only a single permissionless cross-chain token-transfer call from a registered peer chain (`HyperFungibleToken.send` / `WrappedHyperFungibleToken.send`), which per the docs is available to any external sender. Constructing the `Message.data` payload and choosing `from` is entirely attacker-controlled from the source chain, with no additional privilege needed, making this High likelihood if `send()` permits an arbitrary/attacker-supplied `from` or if the derived-origin mapping can be steered toward a chosen victim account.

### Recommendation
Require a valid signature (binding to the destination account's nonce and the exact `runtime_call`) for *every* dispatched runtime call, removing the unsigned/`from`-derived origin fallback entirely, or restrict the unsigned path so that `origin` can only ever be the pallet's own sub-account (never an arbitrary externally-named account) and cannot execute privileged/fund-moving dispatchables. At minimum, ensure `from` cannot be forged to reference other users' accounts, and add tests asserting that unsigned calldata cannot dispatch as any account other than one provably controlled by the message sender.

### Proof of Concept
1. Attacker calls `HyperFungibleTokenUpgradeable.send(SendParams{ ..., data: abi.encode(SubstrateCalldata{ runtime_call: <Balances::transfer_all(attacker)>, signature: None }) })` on the EVM source chain, with `from` in the resulting ISMP `Message` set/derived to the victim's mapped substrate address (per `EvmToSubstrate::convert`).
2. Message is relayed and delivered to `pallet-hyper-fungible-token::on_accept` on the destination chain.
3. `on_accept` decodes `Message`, sees `message.data` non-empty, decodes `SubstrateCalldata` with `signature: None`.
4. Origin resolution at [3](#0-2)  computes `origin = EvmToSubstrate::convert(H160::from(from_bytes))`, equal to the victim's account, without any proof the attacker controls it.
5. `runtime_call.dispatch(RawOrigin::Signed(origin))` executes the attacker-chosen call as the victim, e.g. transferring the victim's balance, provided the call passes `BaseCallFilter`.
