Confirmed. The webhook HMAC in this gem only covers `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are never included in the signed bytes.

### Title
Webhook `shop` identity is trusted from an unauthenticated header not covered by HMAC verification - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches the handler using a `shop` value read from an HTTP header that the HMAC never signs. This breaks the intended binding `hmac_verified(raw_body) == authenticated(shop)`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is not part of the signable string: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e. only `raw_body`), and — once that check passes — trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) [5](#0-4) 

Since `hmac-sha256` is computed by Shopify over the body only, the `shop-domain` header is not cryptographically bound to that HMAC. The equality the gem should enforce is `hmac(secret, raw_body || shop || topic) == received_hmac`, but it actually only checks `hmac(secret, raw_body) == received_hmac`, independent of `shop`.

### Impact Explanation
An attacker who owns any Shopify shop (even a free development store) can install the target app, trigger any webhook topic with content they fully control (e.g. `orders/create`, `customers/create`), and thereby obtain a body + `hmac-sha256` pair that is validly signed by Shopify with the app's real `api_secret_key`. The attacker can then replay that exact `raw_body`/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for an arbitrary victim shop domain. `HmacValidator.validate` still succeeds (it only checks the body), so `Registry.process` dispatches the forged event to the app's handler as if it were authentic data from the victim shop. Any host application that uses `WebhookMetadata#shop` to select the tenant/session/database record to update (the documented and expected usage pattern) will apply attacker-controlled data to the wrong tenant, resulting in cross-tenant data injection/corruption — a boundary the app developer has no way to detect using this gem's API.

### Likelihood Explanation
Exploitation only requires: (1) the ability to install the target app on any Shopify shop the attacker controls (trivial — free dev stores), (2) network access to the app's public webhook endpoint (required by design), and (3) freedom to set arbitrary HTTP headers on the replayed request (trivial with any HTTP client). No access to `api_secret_key`, access tokens, or the app's infrastructure is needed. This is a realistic, low-effort attack path.

### Recommendation
Bind the webhook's `shop` (and ideally `topic`) into the value that is HMAC-verified, or otherwise cryptographically tie the trusted header values to the signed body — for example by having `to_signable_string` include the shop domain, or by independently validating the `shop` header against a session/shop record established via OAuth before trusting it. At minimum, document (and better, enforce in the gem) that `request.shop` must never be used as the sole tenant-selection key without an additional authenticated binding, since only `raw_body` is HMAC-protected.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., updates an order), which is delivered to the app's webhook endpoint with a body `B` and a valid `x-shopify-hmac-sha256` header `H = HMAC-SHA256(secret, B)`.
2. Attacker captures `(B, H)` from their own webhook delivery (e.g., via a debugging proxy on their own infrastructure, which is legitimate since it's their own traffic).
3. Attacker crafts a new HTTP POST to the app's webhook endpoint using the identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` instead of their own domain.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` parses `shop` as `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(secret, B)`, which still equals `H`, so validation passes.
6. `Registry.process(request)` invokes the app's registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data as if it originated from the victim shop.
