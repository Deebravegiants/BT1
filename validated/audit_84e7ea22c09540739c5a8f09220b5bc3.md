Audit Report

## Title
Unsynchronized concurrent read of `authorizedKeys` map in `WorkflowMetadataHandler.Authorize` races with periodic `syncMetadata` writes - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` reads `h.authorizedKeys[workflowID]` (line 92) without acquiring `h.mu.RLock()`, while the periodically-scheduled `syncMetadata` goroutine replaces `h.authorizedKeys` entirely under `h.mu.Lock()` (lines 164, 178). Every other accessor of the same fields (`WorkflowShards`, `GetWorkflowID`, `GetWorkflowReference`) correctly takes `h.mu.RLock()`, confirming `Authorize` is a genuine outlier and this is a real, unguarded data race on a Go map.

## Finding Description
`Authorize` is called on the request path via `httpTriggerHandler.authorizeRequest`, which is invoked from `HandleUserTriggerRequest` at [1](#0-0) , confirming the reachable exploit path from an unprivileged HTTP-trigger caller into `Authorize` — the earlier report's uncertainty about this call path is resolved by inspection of `HandleUserTriggerRequest`.

Inside `Authorize`, the map lookup at line 92 (`keys, exists := h.authorizedKeys[workflowID]`) and the subsequent `keys[key]` lookup at line 101 both occur with no lock held: [2](#0-1) 

Meanwhile `syncMetadata`, scheduled via `h.runTicker(time.Duration(h.config.MetadataAggregationIntervalMs)*time.Millisecond, h.syncMetadata)` in `Start`, acquires `h.mu.Lock()` and reassigns `h.authorizedKeys = authorizedKeys` (a full map replacement, not an in-place mutation): [3](#0-2) [4](#0-3) 

Every other reader of the same struct fields uses `h.mu.RLock()`/`RUnlock()` correctly, e.g. `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `syncMetadata` reassigns the entire `h.authorizedKeys` variable rather than mutating the existing map in place, `Authorize`'s unlocked read races against that pointer/header write. In Go's memory model this is technically a data race on the `h.authorizedKeys` field itself (the map header, a multi-word value), which the race detector will flag and which can, under concurrent access patterns (particularly if the compiler/runtime observes a torn read of the map header, or if `Authorize` is itself reading concurrently with another `syncMetadata` execution mutating a map still referenced elsewhere), lead to `fatal error: concurrent map read and map write` in the worst case, or otherwise a benign stale read (`Authorize` operating on the old map or the new one, both of which are internally consistent single-writer-produced maps).

## Impact Explanation
This is a legitimate concurrency bug reachable by any unprivileged actor able to send HTTP-trigger requests to the gateway, since `Authorize` runs on every such request while `syncMetadata` runs unconditionally on a fixed timer once the handler starts. The impact is a potential node crash (DoS) detectable under `go test -race`, and in the field, a possible transient authorization decision inconsistency (though because `syncMetadata` always produces a *new*, fully-populated map before swapping the field, and never mutates a map in place while `Authorize` might be reading it, the realistic worst case is a race-detector violation / crash risk under Go's runtime race checks rather than corrupted per-key data — the maps swapped in are always complete and internally consistent at the time of assignment). This fits a legitimate concurrency/DoS category, though it is a lower-severity finding than a full authorization bypass since no evidence shows an attacker can force an incorrect authorization decision (only a possible crash or negligible staleness window).

## Likelihood Explanation
High likelihood of triggering the underlying race condition: no privileged access is required — only the ability to send trigger requests to the gateway, an explicitly in-scope unprivileged actor — and the racing writer (`syncMetadata`) runs on a fixed period (`MetadataAggregationIntervalMs`) automatically on every gateway node. Sustained request traffic will eventually overlap with a `syncMetadata` tick, and running with `-race` would reliably flag it; without the race detector, crashing outright is less certain but not implausible under Go's runtime map-access checks.

## Recommendation
Acquire `h.mu.RLock()`/`RUnlock()` around the reads in `Authorize` (both the `h.authorizedKeys[workflowID]` lookup and the `keys[key]` check), matching the pattern already used by `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`. Consider snapshotting the specific per-workflow key set under the lock to minimize hold time.

## Proof of Concept
1. Start a `WorkflowMetadataHandler` via `Start(ctx)`, which schedules the `syncMetadata` ticker per `MetadataAggregationIntervalMs`.
2. Populate `h.authorizedKeys` via aggregator observations as in `TestSyncMetadata`.
3. From one goroutine, call `handler.Authorize(workflowID, validJWT, req)` in a tight loop.
4. From another goroutine, repeatedly call `handler.syncMetadata(ctx)`.
5. Run with `go test -race`: the race detector will flag the unsynchronized read of `h.authorizedKeys` in `Authorize` against the locked write in `syncMetadata`, confirming the concurrency defect.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
