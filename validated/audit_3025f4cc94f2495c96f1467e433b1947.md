### Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery#to_signable_string` by returning only the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only proves that the *body* was signed by a holder of `client_secret`; it never verifies that the `shop-domain` header actually corresponds to the shop that produced that body. `Webhooks::Registry.process` then trusts `request.shop` as the tenant identity when dispatching to the registered handler.

### Finding Description
The binding that should hold is:

`shop asserted to handler == shop that the HMAC-signing party actually intended`

but the code only enforces:

`HMAC(body, client_secret) == received_hmac`

with `shop` (and `topic`, `webhook_id`, `api_version`) excluded entirely from the signed material. [1](#0-0) 

`HmacValidator.validate` computes the signature purely over `to_signable_string`: [2](#0-1) 

`Registry.process` validates the HMAC and then forwards `request.shop` — sourced from the unsigned `shopify-shop-domain` header — straight into `WebhookMetadata` for the handler: [3](#0-2) 

Because Shopify (and any app owner who installs the app on their own store) can legitimately obtain a valid `(body, hmac)` pair for a payload they control, an attacker who owns a shop can capture a genuine webhook delivery for that shop (e.g., a generic/empty-body topic, or any topic whose body content they control or does not embed the shop domain) and then replay the identical `body` + `hmac-sha256` header to the target app's webhook endpoint while substituting the `shopify-shop-domain` (and optionally `topic`/`webhook-id`) header for a victim shop. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will dispatch the handler believing the event came from the victim shop.

### Impact Explanation
This breaks the tenant-identity binding the gem is supposed to provide to host applications: `request.shop`/`WebhookMetadata#shop` is the only tenant signal the library exposes to webhook handlers, and it is unauthenticated. A host application that (reasonably, per the gem's own API) trusts `WebhookMetadata#shop` to select which tenant's data to update can be made to apply attacker-supplied webhook data under a different shop's identity — i.e., cross-tenant access/data corruption, achieved with only the attacker's own shop's legitimately-signed webhook material and no access to the app's `client_secret` or any victim credentials.

### Likelihood Explanation
Any developer/merchant can install the target app on their own shop (or observe/replay one of their own app's delivered webhooks), giving them a valid `(raw_body, hmac)` pair signed with the real `client_secret` without ever learning the secret itself. Forging the `shop-domain` header requires no cryptographic material at all, only control of the HTTP request sent to the app's public webhook endpoint. No privileged access or the target's credentials are required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the material verified against the HMAC, or otherwise cryptographically bind the header-derived `shop` to the delivery before it is exposed via `WebhookMetadata`. At minimum, document/require that host apps cross-check `shop` against an installation record (offline session/access token existing for that shop) rather than trusting it as authenticated by the HMAC check performed inside this gem.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and receives
# a legitimately-signed webhook delivery for it:
raw_body = '{"id":1}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays the SAME body/hmac to the app's webhook endpoint but swaps the
# shop-domain header to the victim shop:
forged_headers = {
  "x-shopify-topic" => "products/update",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes: HMAC only ever validated raw_body, never the shop header.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", ...))
```

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
