### Title
`flash_position` bypasses spoke borrow restrictions and can mint debt in a paused, frozen, or non-borrowable market - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
**Medium.** `flash_position` can create a new debt position in a `HubAssetKey` market without applying the spoke’s `is_borrowable`, `paused`, or `frozen` entry restrictions. An authenticated attacker can open or extend their own leveraged account, mint the restricted debt asset, forward it to their receiver, and satisfy the solvency check by delivering separate collateral during the callback.

### Finding Description
Ordinary borrowing validates every requested leg through `validate_position_entry_gates`, whose borrow branch calls `require_can_borrow`. [1](#0-0)  `require_can_borrow` requires an active listed spoke asset, rejects `paused` and `frozen` entries, and then rejects assets whose `is_borrowable` flag is false. [2](#0-1) 

`flash_position` instead validates only that the debt hub is active, the position mode is supported, the receiver is valid, and the pool market has `is_flashloanable` enabled. [3](#0-2)  Its explicit entry validation is applied only to the declared collateral list through `require_can_supply` and `AccountPositionType::Deposit`. [4](#0-3)  The function then mints and forwards the requested debt before invoking the receiver callback. [5](#0-4)  Afterward it deposits the measured callback collateral and performs final solvency checks, but those checks do not restore the omitted spoke borrow admission control. [6](#0-5) 

### Impact Explanation
The protocol can mint and pay out debt from a market whose spoke listing is intended to prohibit new debt exposure. This can place protocol liquidity into an emergency-paused, frozen, or deliberately non-borrowable asset while leaving an open loan on the attacker’s account. If the market was disabled because its price, liquidity, token behavior, or unwind path is unsafe, the resulting loan can mature into bad debt and socialize losses to suppliers. The accepted impact is potential protocol insolvency and lender fund loss, not merely a policy violation.

### Likelihood Explanation
An unprivileged user controls every parameter required by the call and can use `account_id = 0` to create a new owned account. The attacker only needs a Wasm receiver that returns sufficient declared collateral to the controller before the callback completes. Existing collateral or independently funded collateral can satisfy the final health-factor checks, so the bypass does not depend on oracle manipulation, privileged access, leaked keys, or an unsafe third-party route.

### Recommendation
Before minting the flash-position debt, apply the same borrow admission rules as `borrow`: call `require_can_borrow` for the requested `debt` market against the account’s stored spoke. Also ensure the debt leg is included in the borrow-side position/cap validation performed for other debt-creating strategies. Add regression tests proving `flash_position` rejects a debt market with `is_borrowable = false`, `paused = true`, or `frozen = true`.

### Proof of Concept
1. Configure a market `D` on spoke `S` with pool `params.is_flashloanable = true`, but set its spoke listing to `is_borrowable = false` or set either `paused = true` or `frozen = true`.
2. Configure an accepted collateral market `C` on the same spoke.
3. Deploy a receiver that accepts `execute_flash_position` and transfers `minCollateral` of `C` to the controller during the callback.
4. As an unprivileged account, call:

```rust
controller.flash_position(
    attacker,
    0,                          // creates an attacker-owned account
    S,
    PositionMode::Multiply,
    HubAssetKey { hub_id: H, asset: D },
    debt_amount,
    receiver,
    Bytes::new(&env),
    vec![&env, (HubAssetKey { hub_id: H, asset: C }, minCollateral)],
    Vec::new(&env),
)
```

5. The debt asset is minted and forwarded before callback execution. [5](#0-4)  The declared collateral is then measured and deposited, followed by ordinary finalization. [6](#0-5) 
6. Compare with `borrow(attacker, account_id, [(D, debt_amount)], None)`, which reaches the borrow-side spoke checks and rejects the same market. [1](#0-0)

pub(crate) fn require_can_borrow(
    env: &Env,
    cache: &mut Context,
    spoke_id: u32,
    hub_asset: &HubAssetKey,

    assert_with_error!(
        env,
        asset_config.is_borrowable,
        CollateralError::AssetNotBorrowable
    );
