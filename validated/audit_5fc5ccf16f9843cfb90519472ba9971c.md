### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the HMAC over the raw request body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values that `Registry.process` hands to the app's handler are taken from unauthenticated HTTP headers that are never included in the signed material.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it to the `hmac` field with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns **only** the raw body: [2](#0-1) 

But `Request#shop` (and `topic`, `webhook_id`, `api_version`) are read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is **not** part of the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC of the body, then unconditionally trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` that is delivered to the app's handler: [4](#0-3) 

The identity binding that should hold is:

`shop that produced the HMAC-valid body == shop attributed to the webhook in WebhookMetadata`

Because the `shop-domain` header is outside the signed content, and the HMAC secret (`client_secret`) is the same for every shop that installs the app (it is app-scoped, not shop-scoped), any unprivileged merchant who installs the app can trigger a real Shopify webhook against their own shop (e.g. `orders/create`, `app/uninstalled`, or any subscribed topic) to obtain a body + HMAC pair that Shopify legitimately signed. That attacker can then POST the exact same `raw_body`/`hmac-sha256` pair directly to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (any victim shop domain string). `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` passes the attacker-chosen `shop` value straight through to the handler as if Shopify itself vouched for it.

### Impact Explanation
This breaks the tenant-isolation guarantee that "if the HMAC validates, the request's `shop` field can be trusted as belonging to the shop the webhook is about." Any handler in a multi-tenant app that keys data, updates state, or looks up records by `WebhookMetadata#shop` (e.g. attributing an order, uninstall, or GDPR redact event to the wrong merchant) can be tricked into cross-tenant data association or action using a body an attacker fully controls the topic/content of via their own legitimate shop's traffic. This matches the High-severity "scope check answers permissively" / identity-binding-bypass class described in the analog report: a value (shop identity) is acted upon downstream without being covered by the authenticity check (HMAC) that is supposed to vouch for the whole message.

### Likelihood Explanation
The attack requires only that the attacker run a normal, unprivileged shop that installs the target app (to receive at least one legitimately-signed webhook with a body they choose the shape of via normal store actions) and the ability to send a raw HTTP POST to the app's public webhook endpoint — both are trivially available to any internet user with a Shopify store. No secrets, tokens, or elevated access are required.

### Recommendation
Include the shop domain (and topic/webhook id/api version) in the signed material verified against the HMAC, or otherwise cryptographically bind them to the body before trusting `request.shop` in `Registry.process`/`WebhookMetadata`. At minimum, cross-check the header-derived `shop` against an independent trust source (e.g. a shop that is already known/installed with a matching session) before acting on it, and document that the header is unauthenticated.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and legitimately receives a webhook, e.g. `orders/create`, capturing the raw body `B` and the `shopify-hmac-sha256` header `H` that Shopify computed with the app's shared `client_secret`.
2. Attacker sends a POST directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `shopify-hmac-sha256`: `H` (unchanged, still validates because `to_signable_string` only hashes the body)
   - Header `shopify-topic`: unchanged or attacker-chosen
   - Header `shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)`, attributing attacker-controlled data to the victim shop as if Shopify itself sent it for that shop.
