### Title
Webhook shop identity is not bound by the HMAC, allowing shop-domain spoofing via replay — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process` authenticate an inbound webhook solely by HMAC-verifying the raw request body, but the `shop` value that is handed to the host application's handler is taken from an unauthenticated header that is never included in the signed material. An attacker who can obtain any one legitimately-signed webhook (e.g. by triggering a webhook on their own dev/trial store that has the app installed) can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header, causing the app to process the payload as if it came from a different (victim) merchant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the raw body only) and compares it to the `hmac` header: [2](#0-1) 

`Registry.process` accepts the request once this body-only HMAC check passes, and then forwards `request.shop` — read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header — into `WebhookMetadata` for the host app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: *the shop the HMAC authenticates == the shop the handler acts on*. Because the HMAC only covers the raw body, the `shop` header is fully attacker-controllable independent of the signature. The gem's own documentation confirms host apps are expected to trust `data.shop` as the verified shop domain of the webhook, and that `Registry.process` "will verify the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

### Impact Explanation
An unprivileged internet user who can install the target app on a shop they control (e.g. a free Shopify development/trial store) can trigger any registered webhook topic (such as `app/uninstalled`, `orders/create`, `customers/data_request`, etc.) to receive one legitimately signed `(raw_body, hmac)` pair from Shopify. Because the HMAC never covers the `shop` header, that same body+HMAC can be replayed to the app's webhook endpoint with the `shop` header rewritten to point at a victim merchant's domain. Any host application logic keyed off `WebhookMetadata#shop` (e.g. uninstalling/deauthorizing a shop's session, updating per-shop billing/subscription state, processing GDPR data requests, or writing order/customer data under the wrong tenant) will act on the wrong tenant's record while believing the request was cryptographically authenticated for that shop — a cross-tenant identity-binding break.

### Likelihood Explanation
Exploitation only requires the ability to install the app on any shop (trivial and free via a Shopify dev store) and standard HTTP tooling to replay a captured request with a modified header — no access to `api_secret_key`, tokens, or the victim's infrastructure is needed. The gem does nothing to prevent this because `shop` is deliberately excluded from `to_signable_string`.

### Recommendation
- Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-supplied shop to the signed payload, so a signature computed for shop A cannot be replayed while claiming to be shop B.
- At minimum, document/require that host applications cross-check `data.shop` against an independently known, already-authorized shop (e.g. an existing session record) before trusting it, and consider exposing a way to reject webhooks whose shop is not in the app's known-installed-shops set.

### Proof of Concept
1. Attacker installs the target app on their own Shopify store `attacker.myshopify.com` and registers/triggers a webhook (e.g. `orders/create`), letting Shopify deliver a webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` for that exact raw body.
2. Attacker captures the raw body and the valid HMAC.
3. Attacker replays an HTTP request to the same endpoint with the identical raw body and HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:26-31` succeeds because it only checks the raw body, and `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim.myshopify.com"`, causing the host application to process attacker-supplied data as belonging to the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
