### Title
`LifiExternalAction.callRouter` never validates router token consumption against `inputAmount`, letting attacker-crafted `externalActionMetadata` pull stranded ERC20 balance via the persistent unlimited allowance - ([File: contracts/external-actions/swaps/LifiExternalAction.sol])

### Summary
`ExternalActionSwap.swap` computes `inputAmount = uint256(-deltaAmounts[0])` and passes it to `callRouter`, but the ERC20 branch of `LifiExternalAction.callRouter` never uses `inputAmount` to bound the router call - it only does `approveUnlimited(inputToken, router)` and then `router.call(externalActionMetadata)`, measuring result purely from the `outputToken` balance delta. Combined with `approveUnlimited`'s "top-up only, never revoke" allowance and residual token balances that can be left in `LifiExternalAction` (e.g. flat fee not forwarded when `circomData.relay == address(0)`), an attacker can craft `externalActionMetadata` that has the router pull more `inputToken` than Hinkal transferred to `LifiExternalAction` in that transaction, and mint themselves a larger output UTXO than their deposit backs.

### Finding Description
Broken equality: value consumed by the router from `LifiExternalAction`'s ERC20 balance != value that Hinkal actually transferred into `LifiExternalAction` for this transaction (`-deltaAmounts[0]`, itself derived from the caller's own proof-committed `amountChanges[0]`).

Trace:
- In `Hinkal._externalTransact` (`contracts/Hinkal.sol:244-256`), Hinkal transfers exactly `-deltaAmountChanges[i]` (a value derived from the caller's own circuit-verified `circomData.amountChanges[i]`) to the external action address, then calls `runAction`. [1](#0-0) 
- `ExternalActionSwap.swap` (`contracts/external-actions/swaps/ExternalActionSwap.sol:44-68`) computes `inputAmount = uint256(-deltaAmounts[0])` and forwards it to `callRouter`, along with the fully attacker-controlled `externalActionMetadata`. [2](#0-1) 
- `LifiExternalAction.callRouter` (`contracts/external-actions/swaps/LifiExternalAction.sol:16-36`) ignores `inputAmount` entirely in the ERC20 branch: it just re-approves the router for `type(uint256).max` (via `approveUnlimited`) and executes `router.call(externalActionMetadata)`, then measures `swappedAmount` solely as the `outputToken` balance delta - there is no check on how much `inputToken` the router actually pulled. [3](#0-2) 
- `approveUnlimited` (`contracts/TransfererBase.sol:32-43`) only re-approves if current allowance is below half of `type(uint256).max`, and is never revoked after use, so the router retains a persistent max allowance on `inputToken` across transactions/users sharing this `LifiExternalAction` instance. [4](#0-3) 
- Residual balance can genuinely accumulate in `LifiExternalAction`: when `circomData.feeStructure.feeToken == inputToken`, `inputAmount -= flatFee` reduces what's sent to the router (`ExternalActionSwap.swap`, line 47-48), and the corresponding `flatFee` is only forwarded out via `sendToRelay` (`contracts/Transferer.sol:178-190`), which is a no-op when `circomData.relay == address(0)`. In that case the flat-fee-sized chunk of `inputToken` permanently remains as ERC20 balance sitting in `LifiExternalAction`. [5](#0-4) [6](#0-5) 
- Hinkal's own accounting check in `transact` (`contracts/Hinkal.sol:97-146`) does not catch this: for the input token, `balanceDif` exactly equals `amountChanges[0]` by construction (Hinkal only moves the declared amount out, and never touches that balance again after handing it to the external action). For the output token, `balanceDif` is checked against `amountChanges[1] + utxoAmount`, but `utxoAmount` is literally set equal to whatever `LifiExternalAction` transferred back (`amountToSendToHinkal` in `ExternalActionSwap.swap`), making this check tautological - it validates that Hinkal's UTXO matches what it received, not that what it received is proportionate to the input actually deposited by this caller's proof. [7](#0-6) 

Exploit flow: (1) an earlier, unrelated legitimate swap through the same `LifiExternalAction` leaves stranded `inputToken` balance (e.g., flat fee with `relay == address(0)`, or any dust) and sets the router's allowance to `type(uint256).max` via `approveUnlimited`. (2) The attacker submits their own valid proof for a tiny `amountChanges[0]` (so Hinkal only transfers a small amount of `inputToken` to `LifiExternalAction`), but crafts `externalActionMetadata` whose encoded router call pulls an amount larger than that small transfer - fully permitted by the persistent unlimited allowance and the unvalidated `router.call`. The router converts the larger pulled amount into `outputToken`, `swappedAmount` reflects the inflated amount, and the attacker's own UTXO (`utxoSet[0].amount = amountToSendToHinkal`) is minted for that inflated value, backed by tokens that never came from the attacker's own deposit.

### Impact Explanation
This is theft of tokens stranded in the shared `LifiExternalAction` helper contract (residual fees/dust from other users' prior swaps), converted through an unauthorized router call the proof never constrained, and minted into the attacker's own shielded balance. It does not bypass nullifier/root verification or touch the Merkle tree's committed value directly, and it does not double-spend any nullifier - it exploits value sitting outside the tree in the external-action contract. This matches the **High** category ("theft ... of protocol/relay fees" / "executing calls or moving assets ... never authorised") rather than Critical, since no shielded-tree invariant or proof/nullifier check is broken. It is repeatable each time stranded balance exists in `LifiExternalAction`, and the attacker can even engineer their own dust (e.g. by doing a legitimate swap with `relay == address(0)` and `feeToken == inputToken` to intentionally strand tokens) for a later self-triggered pull.

### Likelihood Explanation
Requires: (a) `LifiExternalAction` to hold residual `inputToken` balance and a live max allowance to `router` from a prior transaction (self-inducible by the attacker, no need to wait for another user), and (b) the attacker to know/construct a router calldata blob that pulls a chosen amount via `transferFrom`-style allowance consumption (feasible for LI.FI-style aggregator routers whose calldata format is public/decodable). No privileged role is needed; the attacker only needs to submit two of their own transactions with proofs for their own UTXOs. This is a fully attacker-controlled, low-cost, repeatable exploit path.

### Recommendation
In `LifiExternalAction.callRouter`, measure and enforce the actual `inputToken` consumption against the passed `inputAmount` (e.g., `require(balanceBefore(inputToken) - balanceAfter(inputToken) <= inputAmount)`), and avoid persistent unlimited allowances - approve exactly `inputAmount` per call (or revoke to zero after use) instead of `approveUnlimited`'s top-up-only pattern. Additionally, ensure any fee amount deducted from `inputAmount` (e.g. flat fee in `inputToken`) is always swept out of the contract even when `relay == address(0)`, so no residual ERC20 balance can accumulate in the external-action contract.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `LifiExternalAction`, a mock router, and a mock ERC20 `inputToken`/`outputToken`.
2. Simulate a prior "legit" swap: send `LifiExternalAction` some `inputToken`, call `swap`/`runAction` with `circomData.relay == address(0)` and `feeToken == inputToken` so a flat-fee amount of `inputToken` is stranded in `LifiExternalAction`, and `approveUnlimited` sets router allowance to `type(uint256).max`.
3. Assert `IERC20(inputToken).balanceOf(LifiExternalAction) > 0` and `IERC20(inputToken).allowance(LifiExternalAction, router) == type(uint256).max` after tx1.
4. Craft tx2: attacker's `circomData.amountChanges[0]` is small (matching a small legit deposit/proof), but `externalActionMetadata` (mock router logic) pulls `strandedAmount + smallDeposit` of `inputToken` via `transferFrom` using the existing allowance, and mints a proportionally larger `outputToken` amount back.
5. Assert on both sides of the equality: `Hinkal` balance change of `inputToken` (`newBalances[0]-oldBalances[0]`) equals `amountChanges[0]` (passes trivially), while `swappedAmount`/`utxoAmount` for `outputToken` exceeds what a fair swap of only `amountChanges[0]` should have produced - demonstrating the attacker minted a UTXO backed by more value than deposited, and the transaction does not revert.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
