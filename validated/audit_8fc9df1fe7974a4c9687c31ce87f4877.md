### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, but the signable string used for that HMAC check is only the raw request body — it never includes the `shop`, `topic`, `webhook-id`, or `api-version` headers. The `shop` value is nonetheless treated as an authenticated tenant identifier and handed straight to the application's webhook handler. This is the exact "field acted on but not covered by the HMAC" bug class: the binding `HMAC-verified data == data acted upon` is broken because `shop` is acted upon (used to attribute the payload to a tenant) but excluded from the verified bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the (unauthenticated) `shop-domain` header: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body only) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` checks only that HMAC, then immediately trusts `request.shop` as the tenant identifier passed to the merchant's handler: [4](#0-3) 

Because Shopify apps use a single app-level `client_secret` (not a per-shop secret) to sign all webhooks regardless of which installed shop sent them, any merchant who has installed the app on their own shop receives genuinely-HMAC-valid webhook deliveries (raw body + matching `hmac-sha256` header) for their own shop. That attacker fully controls the HTTP request they send to the app's public webhook endpoint and can freely rewrite the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) headers while replaying the untouched body and HMAC header. Because those headers are excluded from `to_signable_string`, `HmacValidator.validate` still returns `true`, and `Registry.process` forwards `WebhookMetadata` with the attacker-chosen `shop` value to the handler as if it were an authenticated fact.

Equality that should hold but doesn't: `shop_used_by_handler == shop_bound_by_hmac`. In reality `shop_used_by_handler = header value (attacker-controlled)` while `shop_bound_by_hmac = ∅` (not covered at all).

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` to key tenant-scoped operations (e.g., "update data for this shop", "credit an event to this merchant's account") can be made to attribute attacker-supplied webhook bodies to an arbitrary victim shop. This is a cross-tenant integrity/confidentiality break sourced entirely in this gem's webhook-authentication primitive (`Request`/`HmacValidator`/`Registry`), matching the Critical/High "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation only requires installing the target app on an attacker-owned development/trial shop (no victim credentials, no `api_secret_key`, no TLS interception) to obtain one genuinely HMAC-signed webhook, then replaying it with a modified `shop-domain` header at the app's public webhook endpoint. This is directly reachable through the gem's documented `Registry.process` entry point with no additional privileges.

### Recommendation
Bind the header fields that are acted upon into the authenticated signable string, or explicitly require callers to independently verify `request.shop` against a known/installed session before trusting it. At minimum, `Registry.process` should not pass `request.shop` to handlers as an authenticated value unless it is verified against an existing offline/online session for that shop (proving the shop is actually installed and the webhook wasn't cross-attributed).

### Proof of Concept
1. Attacker installs the target Shopify app on their own development shop `attacker.myshopify.com`, triggering Shopify to send a real webhook (e.g., `orders/create`) to the app's webhook endpoint, with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker intercepts/replays this request to the same endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(client_secret, B)` — matches `H`, returns `true` (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` proceeds and invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-controlled data under the victim shop's tenant context.
