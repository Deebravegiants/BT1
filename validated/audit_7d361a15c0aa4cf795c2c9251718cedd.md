### Title
Webhook `shop` identity is not bound to the HMAC-verified bytes, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a request as authentic ("did indeed come from Shopify") solely because `Utils::HmacValidator.validate(request)` returns true [3](#0-2) . That validation only covers the raw request body [1](#0-0) , while the `shop` field passed on to the app's handler is read from an unsigned header [2](#0-1) [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop_header == the_shop_whose_secret_signed_this_body`. Instead, `HmacValidator.validate_signature` recomputes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` header [5](#0-4) . For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body` [1](#0-0) , and `shop` is read independently from `shopify-shop-domain`/`x-shopify-shop-domain` [2](#0-1) . Nothing cryptographically ties the `shop` header to the signed body.

Because the same `api_secret_key` is shared by the app across every shop that installs it, any merchant that has installed the app receives their own genuinely-signed webhooks from Shopify. That merchant (an unprivileged actor with respect to any other tenant) can capture one of their own valid webhook deliveries (body + valid `hmac`) and replay it to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic:, shop: request.shop, body: request.parsed_body, ...)` [4](#0-3) , i.e., attacker-controlled body content is delivered to the app labeled as belonging to a different tenant. The gem's own docs tell integrators that `Registry.process` "will verify the request did indeed come from Shopify," which is what the host application relies on before trusting `data.shop` as the tenant key.

### Impact Explanation
This breaks the tenant boundary that `shop` is supposed to represent: an attacker who legitimately controls one installed shop can inject a webhook payload that the app attributes to an arbitrary other shop/tenant. Any app logic keyed off `data.shop` (e.g., using it as a lookup/session key, per the documented handler pattern in `docs/usage/webhooks.md` lines 24-26) can be made to apply attacker-chosen webhook body content to another merchant's tenant record — a cross-tenant integrity violation that meets the "Critical - cross-tenant access" bar defined for this scan.

### Likelihood Explanation
Exploitation requires only that the attacker legitimately install the target app on a shop they control (or exploit a free/trial install), which is the normal, unprivileged path any internet user can take with a public Shopify app. No access token, `client_secret`, or leaked credential is needed — the attacker only needs a genuine webhook delivery that Shopify already sent them, and the ability to POST an HTTP request with a modified header to the app's public webhook endpoint.

### Recommendation
Include the intended shop identity in the bytes that are HMAC-verified (e.g., require the host app to independently confirm `request.shop` is a shop it has an active session/webhook registration for before trusting it, or bind shop identity to the signed payload) rather than trusting the `shopify-shop-domain` header as a bare, unauthenticated field. At minimum, document prominently in `docs/usage/webhooks.md` that `data.shop` is unauthenticated and must be cross-checked against known/installed shops before being used as a tenant key, since currently the documentation implies HMAC verification is sufficient authentication of the whole request including `shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Attacker triggers an event (e.g. `orders/create`) on their own shop and captures the resulting webhook POST, including the genuine `x-shopify-hmac-sha256` header and raw body, sent by Shopify using the app's shared `api_secret_key`.
3. Attacker resends this exact captured request to the app's public webhook endpoint, changing only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the modified headers; `Utils::HmacValidator.validate` recomputes the HMAC over the unchanged raw body and it matches, so `Registry.process` treats the request as authentic [3](#0-2) .
5. The app's registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's chosen order body, and processes/stores it as if it originated from the victim shop.
