### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` accepts any request whose HMAC matches the body and then forwards `request.shop` unchanged to the app's handler as the tenant identifier, so the "shop the webhook belongs to" binding is never actually verified by the signature.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
Only `@raw_body` is included in the signable string. `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers with no cryptographic binding to that signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `to_signable_string` (the body) and compares it against the `hmac` header — again, the headers themselves are excluded from what is verified: [3](#0-2) 

`Registry.process` relies solely on this check before trusting `request.shop` and forwarding it as the tenant identity to the app's handler: [4](#0-3) 

The documented usage pattern explicitly treats `data.shop` as the trusted tenant key for downstream processing (e.g. looking up the merchant's session/access token or enqueuing per-shop jobs): [5](#0-4) 

This contrasts with `Auth::Oauth::AuthQuery`, where `shop` is explicitly included inside the signed string, correctly binding shop identity to the signature: [6](#0-5) 

The broken binding, stated as an equality that the gem fails to enforce:
`shop authenticated by HMAC` (which is nothing, since headers aren't signed) ≠ `shop trusted as the tenant key for `data.shop`` (taken verbatim from the unauthenticated `shopify-shop-domain` header).

### Impact Explanation
An app installed on any shop receives legitimate webhooks from Shopify, correctly HMAC-signed over the body using the app's real `client_secret`. Because the signature covers only the body, that same `(raw_body, hmac)` pair remains valid no matter what the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers say. An unprivileged attacker who controls a shop where the app is installed can capture one such legitimately-signed webhook and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim merchant's domain. `Registry.process` will accept it (the HMAC still validates against the unchanged body) and hand the attacker-chosen `shop` value to the host application's handler as if it were the authentic tenant, causing data or actions to be attributed/applied to the wrong (victim) merchant — a cross-tenant integrity/confidentiality violation for any app that keys per-shop logic (data storage, side effects, access-token lookup) off `data.shop`.

### Likelihood Explanation
Any developer/merchant who can install the app (even a free/trial install) can obtain a validly-signed webhook body+HMAC pair for their own shop and only needs to modify an HTTP header value to target another shop — no access to `client_secret`, tokens, or privileged accounts required. Exploitability depends only on the host app trusting `data.shop` from `WebhookMetadata`, which is exactly the pattern the gem's own documentation recommends.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or otherwise cryptographically bind them) in the string that is HMAC-verified for webhook requests, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signed payload. At minimum, document prominently that `data.shop` is unauthenticated and must not be used to resolve per-tenant secrets/sessions without additional verification.

### Proof of Concept
1. Attacker installs the app on `evil-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw body and the resulting `x-shopify-hmac-sha256` value sent by Shopify.
2. Attacker POSTs the identical raw body and HMAC to the app's webhook callback endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally any topic supported by the same body shape).
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only recomputes the HMAC over `@raw_body`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata` with `shop: request.shop` = `"victim-shop.myshopify.com"` and invokes the app's handler, which — per the gem's documented usage — uses `data.shop` to route/attribute the event to `victim-shop`, even though the payload actually originated from `evil-shop`.
