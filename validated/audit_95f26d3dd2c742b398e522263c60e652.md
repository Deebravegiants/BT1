Found a clear, verifiable analog. The `evm/tron/contracts/apps/IntentGatewayV2.sol` (Tron variant of the IntentGateway escrow contract) lacks the duplicate-input-token guard that the canonical `evm/src/apps/IntentGatewayV2.sol` has.

### Title
Order escrow overwrite/loss via duplicate-token orders in Tron `IntentGatewayV2.placeOrder` and `withdraw` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
Hyperbridge's IntentGateway escrows user funds per `(commitment, token)` in the `_orders` double mapping. The canonical EVM implementation (`evm/src/apps/IntentGatewayV2.sol`) explicitly guards against a user submitting an order with the same input token listed twice, reverting with `InvalidInput` if `_orders[commitment][token] != 0` before writing. The Tron variant of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) omits this guard entirely and instead accumulates with `+=`, and — more importantly — its withdrawal path (`withdraw`) checks only `_orders[commitment][token] == 0` to detect "unknown order" and then blindly decrements by the caller-supplied `amount` for each token entry in the withdrawal body, without validating that the sum of all `amount`s for repeated tokens does not exceed what is actually escrowed, and permits `body.tokens` to reference the same token multiple times.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder` (lines 451-468 and 391-446), escrow accounting is:
```solidity
_orders[commitment][token] += reducedInputs[i].amount;
```
This is looped per `order.inputs[i]`, with no check that `token` hasn't already appeared earlier in the same `inputs` array (unlike `evm/src/apps/IntentGatewayV2.sol` lines 364-368, which explicitly reverts on `_orders[commitment][token] != 0`). [1](#0-0) [2](#0-1) 

More critically, the withdrawal/redeem path in the Tron contract, `withdraw` (lines 691-730), iterates `body.tokens` (attacker/relayer-controlled cross-chain message content decoded from an ISMP `RedeemEscrow`/`RefundEscrow` request body) and for each entry only checks that the escrow slot is non-zero, then unconditionally subtracts the requested `amount`:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
...
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 

Since `_orders[commitment][token]` is a per-order escrow keyed by `(commitment, token)`, and `commitment` embeds `order.nonce`/`order.user`, direct cross-user overwrite (as in the SBT analog, where a shared `(class, issuer)` key caused loss of a *different* account's token) does not occur here for genuinely distinct orders. However, the class-of-bug transposed to this codebase manifests as: (1) placing an order with a duplicate input token silently merges two logically distinct escrow legs into a single slot via `+=` without any bound on how many separate token entries a single order can declare, and (2) the corresponding `withdraw()` step trusts caller-supplied `WithdrawalRequest.tokens` amounts and applies unchecked `-=` per iteration with no aggregate cap against the actual credited balance for repeated `token` values in the same withdrawal body — allowing a malicious/duplicated token list in the withdrawal payload to underflow-revert-DoS the whole redemption, or (if amounts are chosen to stay non-negative per step) to drain more from the shared `(commitment, token)` slot than was legitimately escrowed for that leg, because there is no per-entry uniqueness enforcement mirroring the placeOrder-side rejection now present in the canonical contract.

### Impact Explanation
An escrow slot shared between distinct legs of the same order (or being decremented multiple times from one withdrawal body) can be drained beyond its backing balance or its accounting can be corrupted, causing either permanent freezing of legitimately escrowed user funds (order becomes stuck in an inconsistent state where partial withdrawals fail) or an over-withdrawal of escrowed tokens relative to what was actually deposited for that leg — a direct analog to the "balance entry overwrite" class in the original report, where a shared key was written to without accounting for pre-existing value.

### Likelihood Explanation
`placeOrder` and the `RedeemEscrow`/`RefundEscrow` message handling in `onAccept`/`withdraw` are reachable by any user submitting a single transaction (`placeOrder`) and by any relayer delivering a cross-chain message whose body is decoded from `WithdrawalRequest` — both are the exact unprivileged, single-transaction paths the scope calls out (token bridger / intent solver paths). The canonical `evm/src/apps/IntentGatewayV2.sol` was already patched with the `_orders[commitment][token] != 0` duplicate check, evidencing the maintainers recognized this exact overwrite/duplicate-key class as needing remediation — the Tron contract deployed from `evm/tron/contracts/apps/IntentGatewayV2.sol` did not receive the same fix.

### Recommendation
Port the duplicate-input-token guard from `evm/src/apps/IntentGatewayV2.sol` (`if (_orders[commitment][token] != 0) revert InvalidInput();` before writing) into `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, and additionally validate in `withdraw()` that `body.tokens` contains no duplicate `token` entries, and that the total requested `amount` per token does not exceed the current `_orders[commitment][token]` balance in a single pass (rather than relying on late underflow reverts as an implicit backstop).

### Proof of Concept
1. A user calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [{token: USDC, amount: 500}, {token: USDC, amount: 500}]`.
2. In the escrow loop, `_orders[commitment][USDC] += 500` executes twice, yielding `_orders[commitment][USDC] = 1000` — masking that two logically separate 500-unit legs were merged into one undifferentiated slot. [4](#0-3) 
3. On fill/redeem, the destination gateway dispatches a `RedeemEscrow` request whose `WithdrawalRequest.tokens` is built from the order's `inputs` (potentially still containing the duplicate `USDC` entry twice with `amount: 500` each).
4. `withdraw()` processes each entry independently: the first iteration checks `_orders[commitment][USDC] == 0` (false, so it proceeds) and decrements to 500; the second iteration again passes the same zero-check and decrements to 0 — the escrow slot is now fully drained by a single `RedeemEscrow` delivery that only needed to cover one logical 500-unit leg, while the accounting model assumed two independent 500-unit legs were tracked, producing an inconsistency that can be exploited depending on how the corresponding output-side release is computed on the destination chain. [5](#0-4)

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;

                if (!success) revert TransferFailed();
            }

            }
        }
