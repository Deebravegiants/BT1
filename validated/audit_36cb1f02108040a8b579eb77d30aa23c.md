### Title
Asymmetric decimal-scaling bug in `pallet-hyper-fungible-token` allows unbacked over-minting on the destination chain when a registered asset's local precision exceeds the destination's ERC20 precision - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The PolyYeld Finance incident stemmed from a "compatibility issue" that let the attacker mint trillions of tokens with no backing. The closest reachable analog in this codebase is a precision-conversion bug in `pallet-hyper-fungible-token`'s ERC20 decimal-scaling helpers. The helpers use the same subtraction direction for both the up-scale and down-scale conversions, so whenever a registered asset's local decimals exceed the destination chain's configured ERC20 decimals, an ordinary `send` extrinsic encodes a wildly inflated amount that the destination `HyperFungibleToken` contract mints in full — an unbacked mint reachable by any signed account, not an admin.

### Finding Description
`convert_to_erc20` and `convert_to_balance` both compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)`: [1](#0-0) 

- `convert_to_balance` (used in `on_accept`, minting on receipt) is correct: it divides the incoming ERC20 amount by `10^(erc_decimals - local_decimals)`, which is meaningful only when `erc_decimals > local_decimals`.
- `convert_to_erc20` (used in `send`, when producing the outgoing message) uses the **same** exponent, `erc_decimals.saturating_sub(local_decimals)`, to *multiply* the local balance up to ERC20 precision. This is only correct in the same direction (`erc_decimals > local_decimals`). When the asset is registered such that `local_decimals > erc_decimals` for a given destination chain, `saturating_sub` floors to zero and **no down-scaling is applied at all**, even though the destination's ERC20 precision is smaller than the local precision.

The call site in `send`: [2](#0-1) 

passes the raw local balance amount straight through as the ERC20-precision `message.amount` whenever this asymmetric condition holds, and dispatches it to the peer `HyperFungibleToken` contract, which mints exactly that raw value: [3](#0-2) 

`Precisions` (the per-`(AssetId, StateMachine)` ERC20 decimals) is set by `register_token`/`update_token` under `CreateOrigin`: [4](#0-3) 

This registration is a routine, non-malicious configuration action — it simply records the real decimals of the peer ERC20 contract, e.g. a common 6-decimal token bridged from a chain whose local `pallet-assets` representation uses 18 decimals (a very common asset-registry convention). It requires no admin wrongdoing, only an ordinary and plausible decimal mismatch, for the vulnerability to manifest, and the actual overflowing mint is triggered by any regular signed user calling `send`.

### Impact Explanation
When `local_decimals > erc_decimals` for a registered non-native/native asset and destination pair, every `send()` call encodes an ERC20 amount that is `10^(local_decimals - erc_decimals)` times larger than intended. The destination `HyperFungibleToken.onAccept` mints this inflated amount unconditionally (it has no independent bound check against what was actually escrowed/burned on the source side). A user can burn or escrow a tiny, real amount of the local asset and receive an astronomically inflated, unbacked balance on the destination EVM chain — the same class of impact as PolyYeld Finance's 4.9 trillion unbacked token mint, and it can be dumped on secondary markets, draining any liquidity or backing tied to that token.

### Likelihood Explanation
The trigger condition (`local_decimals > erc_decimals`) is a realistic, easily-overlooked registration outcome — not a contrived or malicious setup — because substrate asset registries commonly standardize on 18-decimal (or otherwise higher-decimal) local representations while many real-world ERC20 tokens use fewer decimals (e.g., 6 for USDC-style tokens). Once such a token is registered, the exploit path requires only a single ordinary signed `send` extrinsic; no privileged access, forged proof, or governance compromise is needed to trigger the over-mint.

### Recommendation
Fix the scaling direction in `convert_to_erc20` to use `local_decimals.saturating_sub(erc_decimals)` for down-scaling (dividing) and `erc_decimals.saturating_sub(local_decimals)` for up-scaling (multiplying), mirroring the inverse of `convert_to_balance`, or better, implement a single signed-scaling helper that handles both directions explicitly and rejects/rounds instead of silently truncating via `saturating_sub`. Add a regression test asserting round-trip parity of `send` → `on_accept` (and `on_timeout`) amounts for asset pairs where `local_decimals > erc_decimals`.

### Proof of Concept
1. `register_token` a non-native asset with `local_id` decimals = 18 in `pallet-assets`, and a `ChainConfig { token_contract: <EVM HyperFungibleToken>, decimals: 6 }` for a destination EVM chain (mirroring a legitimate 6-decimal ERC20 peer).
2. A user calls `send(SendParams { asset_id, destination, recipient, amount: 1_000_000_000_000_000_000 /* "1" token at 18dp */, .. })`.
3. In `send` (`modules/pallets/hyper-fungible-token/src/lib.rs:295`), `convert_to_erc20(1e18, erc_decimals=6, decimals=18)` computes exponent `6.saturating_sub(18) = 0`, so `erc20_amount = 1e18` (unscaled) instead of the intended `1e6`.
4. The dispatched `Message.amount = 1e18` is delivered to the destination `HyperFungibleToken` contract via `onAccept`, which mints `1e18` raw units to the recipient. Since the contract's ERC20 has 6 decimals, `1e18` raw units equals `1,000,000,000,000` (one trillion) whole tokens — for the cost of burning/escrowing a single local token — an unbacked mint of the same order of magnitude as the PolyYeld incident's 4.9 trillion YELD.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
