### Title
Webhook `shop` identity is taken from an unauthenticated header, not from the HMAC-covered payload, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) that gets passed to the app's `WebhookHandler` from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `HmacValidator` checks only covers the raw request body. Because the header is not part of the signed content, an attacker who can obtain one valid `(body, hmac)` pair signed with the app's `client_secret` can replay it to the app's webhook endpoint with an arbitrary `shop-domain` header and still pass verification, causing the payload to be dispatched as if it belonged to a victim shop.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` for a webhook request returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an unsigned header with no cross-check against the body or against any other authenticated field: [2](#0-1) 

`Registry.process` validates the HMAC over the request and then immediately trusts `request.shop` to build the tenant-scoped `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature only from `to_signable_string` (the body) and the app's single, shop-independent `api_secret_key`: [4](#0-3) 

This breaks the identity binding: **shop-domain header used for tenant dispatch ≠ shop bound by the HMAC signature**. Since Shopify computes webhook HMACs using the app's single `client_secret` regardless of which shop triggered the webhook, a valid `(body, hmac)` pair generated for shop A's webhook remains cryptographically valid when replayed with the `shop-domain` header changed to shop B — the signature check has no way to detect the substitution because the header was never part of the signed bytes.

### Impact Explanation
An unprivileged attacker who legitimately installs the app on their own (attacker-controlled) shop can trigger and capture a genuine webhook (e.g. `orders/create`, `customers/update`, or, more severely, `app/uninstalled`, `shop/redact`, `customers/redact`), then replay the exact same body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `X-Shopify-Topic`, which is likewise unsigned) header value with a victim shop's domain. `Registry.process` will pass HMAC validation and hand the app's `WebhookHandler` a `WebhookMetadata` claiming the data belongs to the victim shop. Depending on what the app does with webhook data (e.g., updating per-shop billing/subscription state, triggering data deletion flows for GDPR topics, invalidating/deleting the victim's stored session on a forged `app/uninstalled`), this crosses the tenant boundary and can cause state corruption, spoofed compliance actions, or denial of service against an arbitrary shop — this falls under the "cross-tenant access" Critical impact category since data attributed to one tenant can be forged against another tenant using only a valid HMAC obtained from the attacker's own store.

### Likelihood Explanation
Likelihood is realistic but requires an attacker to be a legitimate (even free/trial) merchant able to install the app to obtain one valid signed webhook of their own — a low bar, achievable by any unprivileged internet user with no special credentials, access tokens, or social engineering. No `api_secret_key`, access token, or privileged account is needed; only capture of one's own outbound webhook traffic (e.g., via a local proxy) is required, which is entirely within the attacker's own control.

### Recommendation
Bind the `shop` (and ideally `topic`) values into the HMAC-signed content, or otherwise cryptographically tie the header-supplied shop domain to the verified payload before dispatching to `WebhookHandler`. At minimum, `Utils::VerifiableQuery#to_signable_string` for `Webhooks::Request` should incorporate the `shop-domain` header (and other headers used for dispatch) into the signed string, and `HmacValidator`/`Registry.process` should reject requests where header-derived identity fields cannot be shown to correspond to the signed body (e.g., by requiring the consuming application to independently confirm the shop is a currently-installed/known shop before trusting `WebhookMetadata#shop` for any privileged action).

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and registers/receives a real webhook (e.g. `orders/create`) from Shopify, capturing the raw POST body `B` and its `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify using the app's single `client_secret`).
2. Attacker crafts a new POST to the app's webhook endpoint using the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and, if desired, a different `X-Shopify-Topic`, e.g. `app/uninstalled`).
3. Server-side, `Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `HmacValidator.validate(request)` computes `HMAC-SHA256(api_secret_key, B)` and compares to `H` via `OpenSSL.secure_compare` — this succeeds because the signature only ever covered `B`. [5](#0-4) 
4. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim.myshopify.com"`, even though the body content and Hmac were generated for `attacker.myshopify.com`. [3](#0-2) 
5. Any app logic keyed on `WebhookMetadata#shop` (billing updates, GDPR redact/erase flows, uninstall cleanup) now executes against the victim tenant using attacker-controlled webhook content.
