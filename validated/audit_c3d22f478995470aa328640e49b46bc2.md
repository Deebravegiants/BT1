### Title
Frontrunnable `initialize` on `HyperFungibleTokenUpgradeable` / `WrappedHyperFungibleTokenUpgradeable` allows hostile takeover of a cross-chain token bridge - (File: sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol / WrappedHyperFungibleTokenUpgradeable.sol)

### Summary
`HyperFungibleTokenUpgradeable.initialize(...)` and `WrappedHyperFungibleTokenUpgradeable.initialize(...)` are gated only by the vanilla OpenZeppelin `initializer` modifier, with no restriction on `msg.sender` and no atomicity guard analogous to the `onlyFresh` pattern the same codebase already applies to `IntentGatewayV2` and `SimplexPaymaster`. If a proxy for either contract is deployed in one transaction and `initialize` is called in a later, separate transaction (the pattern these contracts' own docs/deploy scripts use for the non-upgradeable siblings), any address can race the legitimate deployer's `initialize` call and become the `Ownable` owner of the bridge app.

### Finding Description
Both upgradeable token-bridge apps follow the same structure: [1](#0-0) [2](#0-1) 

The constructor only calls `_disableInitializers()` on the *implementation*; the initial owner is set from an `initialOwner` argument on `initialize`, which carries no caller check at all — unlike the codebase's own hardened pattern (`onlyFresh` + `reinitializer(VERSION)`) used in `IntentGatewayV2.initialize` and `SimplexPaymaster.initialize`: [3](#0-2) [4](#0-3) 

Those two apps are explicitly documented as safe only because deployment scripts always deploy the proxy with non-empty init data in the same constructor call (atomic CREATE2 deployment via `ERC1967Proxy(impl, initData)`), and the maintainers even wrote a dedicated design decision about this exact risk: [5](#0-4) 

`HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable`, however, have no equivalent protection or documented atomic-deployment requirement, and no in-repo deploy script wires their `initialize` into the proxy constructor call the way `DeployIntentGateway.s.sol` and `DeploySimplexPaymaster.s.sol` do for their respective contracts. The non-upgradeable siblings (`HyperFungibleTokenImpl`, `WrappedHyperFungibleToken`) instead take the owner in their *constructor* (`new WrappedHyperFungibleToken{salt}(admin)`), which is not frontrunnable, but the upgradeable variants deliberately move that binding into `initialize`, reopening the exact class of bug the report describes.

Once an attacker's `initialize(name, symbol, attackerAddr)` (or `initialize(attackerAddr)` for the wrapped variant) lands first on a bare proxy, the attacker becomes the `Ownable` owner and gains full control of all owner-gated configuration: [6](#0-5) [7](#0-6) 

`configure()` binds `_host` (only if unset) and `_dispatcher` (unconditionally, always resettable). `addChain()` registers arbitrary `(chainId, moduleId)` peer mappings that the token's mint/receive path trusts as the authoritative source module for incoming cross-chain messages.

### Impact Explanation
An attacker who wins the initialize race becomes the sole owner of the token bridge contract before the real deployer/users interact with it. As owner, the attacker can:
- Set `_dispatcher` to a malicious `CallDispatcher`, letting them execute arbitrary calldata on every incoming cross-chain receive.
- Register `addChain` peers pointing to attacker-controlled "source" module IDs, so that once the real host is configured (if the attacker sets `_host` to a legitimate host they still control the trust anchor for `source == supportedChain`) the attacker can forge `Received`/mint-triggering messages that the contract will treat as authentic, since `_supportedChains` is the sole authorization check for incoming mint/unlock messages.
- Pause/unpause, or otherwise indefinitely control a bridge application into which real users may have deposited or expect to bridge value, resulting in permanent loss/freezing of funds and forged cross-chain token mint/unlock authorization — squarely a "token bridge mint/burn" and "unauthorized app action" impact.

This meets the bar of Medium severity: concrete unauthorized control over a token-bridge app's trust configuration, enabling forged message delivery/mint authorization once the app is put into production use.

### Likelihood Explanation
Likelihood depends entirely on how a deployer instantiates the proxy. If the deployer follows the same atomic pattern the repo enforces for `IntentGatewayV2`/`SimplexPaymaster` (non-empty init data passed to the proxy constructor in the same transaction), the bug is not exploitable. However:
- Nothing in the contract itself prevents or warns against non-atomic deployment (no `onlyFresh`/atomicity design decision exists for these two contracts, unlike the other two).
- The documented deployment flow for `WrappedHyperFungibleToken`'s non-upgradeable sibling explicitly deploys first, then calls `configure()` in a separate step, illustrating the two-step deployment mentality this SDK encourages; a deployer copying that pattern for the upgradeable variant (deploy proxy, then call `initialize` separately) would be directly exposed. Any observer of the mempool/pending transactions can then frontrun the `initialize` call with their own owner address.

Given these are SDK template contracts meant for third-party integrators to deploy and configure their own bridge apps, and the codebase provides no safeguard or explicit atomic-deployment instruction for them, the likelihood of a non-atomic (and thus frontrunnable) deployment is realistic.

### Recommendation
Apply the same mitigation already adopted elsewhere in this codebase for exactly this bug class:
- Add an `onlyFresh`-style guard (revert unless `_getInitializedVersion() == 0`) is already implicit via `initializer`, but the real fix is to enforce atomic deployment: document/require that these upgradeable contracts only ever be deployed via `new ERC1967Proxy(address(implementation), initData)` with `initData = abi.encodeCall(initialize, (...))`, never via a separate proxy-then-initialize call.
- Alternatively, harden `initialize` to accept and verify an expected deployer/salt commitment (e.g., binding to `msg.sender == tx.origin`'s pre-registered deployer, or requiring a `CREATE2` factory pattern), or make the constructor of a factory contract perform proxy creation and initialization atomically so no window exists between deployment and initialization.
- Update the SDK docs (`hyper-fungible-token.mdx`, `wrapped-hyper-fungible-token.mdx`) to explicitly warn against two-step (deploy-then-initialize) proxy deployment for the upgradeable variants, mirroring the decision already recorded for `IntentGatewayV2`/`SimplexPaymaster`.

### Proof of Concept
1. Deployer deploys the implementation and an `ERC1967Proxy` with empty init data (`new ERC1967Proxy(address(implementation), "")`), intending to call `initialize` in a follow-up transaction — the same two-step flow already used for the non-upgradeable `WrappedHyperFungibleToken.configure()` step in this SDK's own documentation.
2. Attacker observes the pending/second transaction (or simply monitors newly-deployed, uninitialized proxies of this known bytecode) and submits `initialize(name, symbol, attacker)` (HFT) or `initialize(attacker)` (WHFT) with higher gas/priority, landing first.
3. `initializer` modifier only checks the OZ initialized flag, not the caller, so the attacker's call succeeds and `attacker` becomes `owner()`.
4. The legitimate deployer's own `initialize` call now reverts (`InvalidInitialization`), leaving the attacker as permanent owner.
5. Attacker calls `configure()` to point `_dispatcher` at a malicious contract and `addChain()` to register malicious peer module IDs, gaining forged-message and mint-authorization capability over the bridge app before real users interact with it.

    /// @dev `initialize` is for a bare proxy only. A proxy that an upgrade left below `VERSION` is
    /// taken there by the host-only `migrate`; without this, anyone could `initialize` it.
    modifier onlyFresh() {
        if (_getInitializedVersion() != 0) revert InvalidInitialization();
        _;
    }

    /**
     * @dev One-time init of a bare proxy: registers the peers, each bound to `address(this)`,
     * stores the params, arms the relayer gate, and lands at `VERSION`. Refused on any proxy
     * already at a version, see `onlyFresh`.
     * @param p The initial gateway configuration parameters.
     * @param peerChains State-machine ids of the cross-chain peers to register, each bound to this
     * gateway's own address so no peer address is carried in the proxy's init data.
     * @param relayer The only relayer whose deliveries are accepted. Zero leaves the gate open.
     */
    function initialize(Params memory p, bytes[] memory peerChains, address relayer)
        public
        onlyFresh
        reinitializer(VERSION)
    {
        uint256 peersLength = peerChains.length;
        for (uint256 i = 0; i < peersLength; i++) {
            Deployment memory deployment = Deployment({chain: peerChains[i], gateway: address(this)});
            _addDeployment(deployment);
        }
        _validateParams(p);
        _params = p;
        _setRelayer(relayer);
    }

# 2026-09-05 — `initialize` only on a bare proxy, rather than a version check in the upgrade path

Chosen: `initialize` is refused unless the proxy is at version 0. `migrate` is the only entry to
`VERSION` for a proxy that already has one, and it is host-only.

The hole both options close: `initialize` has no caller restriction, because a bare proxy is
initialized atomically in its constructor. An `UpgradeContract` that installs this implementation
on a version-1 proxy without `migrate` calldata would leave the proxy below `VERSION` with
`initialize` callable by anyone, who could then set the params and the relayer.
