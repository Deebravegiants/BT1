Based on my research, I found a directly analogous vulnerability pattern in `HandlerV2.sol`'s consensus-update path.

### Title
State machine commitments can never be recorded for a newly-connected chain because a zero "unsupported" sentinel is used to gate a strict-greater-than height check - (File: evm/src/core/HandlerV2.sol)

### Summary
The Sherlock report's root cause is that `movePoolPhase()` treats a legitimate zero value (`totalProtection == 0` → `leverageRatio == 0`) as a value that trivially satisfies a threshold gate, letting a phase transition proceed that should have been blocked. The same anti-pattern — a sentinel `0` return value silently and incorrectly determining the outcome of a boundary check — exists in `HandlerV2.handleConsensus`, except here it blocks a transition that should be allowed, permanently starving state-commitment storage for state machines with no prior commitment.

### Finding Description
In `handleConsensus`, after verifying a consensus proof, every `IntermediateState` returned by the consensus client is only persisted if: [1](#0-0) 

```solidity
uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
if (latestHeight != 0 && intermediate.height > latestHeight) {
    ...
    host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
}
```

`latestStateMachineHeight` is documented to return `0` specifically to mean "the state machine is unsupported / has no commitment yet": [2](#0-1) 

The guard `latestHeight != 0` was clearly meant to avoid a `0 > latestHeight` no-op check, but it also has the side effect that **the very first intermediate state ever proven for a given `stateMachineId` is silently dropped** — because `latestHeight == 0` at that point, the `&&` short-circuits to `false` regardless of `intermediate.height`, and `storeStateMachineCommitment` is never called. This is the exact same shape of bug as the ProtectionPool report: a value that legitimately means "nothing has happened yet" (zero total protection / zero prior height) is used as an implicit bypass or block condition in a threshold/ordering check, instead of being handled as its own explicit case.

Unlike the original report (where the zero sentinel wrongly *permits* an unsafe transition), here it wrongly *blocks* a legitimate one. Any counterparty state machine that is added to the consensus client's tracked set but has never yet had a commitment stored on this host can never receive its first commitment through `handleConsensus`, because that height check can never be satisfied for it.

### Impact Explanation
`storeStateMachineCommitment` populates the state root/timestamp used by every downstream message-verification path — `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, etc. all read `host.stateMachineCommitment(...)` and revert with `StateCommitmentNotFound` if it was never written: [3](#0-2) 

If a newly connected/never-before-committed state machine's first intermediate state is silently skipped, no relayer can ever deliver a request/response/timeout proof for that chain until some other, out-of-band mechanism initializes `latestStateMachineHeight` to a non-zero value. This is a "route unable to deliver messages" condition for that state machine — messages queued for it are permanently undeliverable through the normal consensus-update flow.

### Likelihood Explanation
This triggers deterministically and unprivileged: any relayer submitting the first valid consensus proof containing intermediate state(s) for a state machine whose `latestStateMachineHeight` is still `0` on this host will have that intermediate silently dropped, with no revert or error signaling the failure — the transaction succeeds and the relayer/consumers have no on-chain indication that the commitment write failed. This makes the bug easy to miss until relayers try (and are permanently unable) to deliver requests for that chain.

### Recommendation
Do not conflate "no prior commitment" with "reject this height." Store the first commitment unconditionally when `latestHeight == 0` (i.e., replace the guard with something like `if (latestHeight == 0 || intermediate.height > latestHeight)`), or track initialization with an explicit boolean/height-exists mapping instead of overloading `0` as both "not yet configured" and "genuinely height 0."

### Proof of Concept
1. Consensus client is configured to track a new `stateMachineId` (e.g., a freshly added parachain/L2) that this `EvmHost` has never received a commitment for; `host.latestStateMachineHeight(id) == 0`.
2. A relayer submits a valid `handleConsensus` proof whose `verify()` output includes an `IntermediateState` for that `stateMachineId` at some height `H > 0`.
3. In the loop, `latestHeight = 0`, so `latestHeight != 0` is `false`; `storeStateMachineCommitment` is never invoked, even though `H` is a perfectly valid, newer height.
4. Any subsequent `handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts` call referencing that state machine's height reverts with `StateCommitmentNotFound`, and no further consensus update for that chain can succeed in storing height `H` either — the check re-evaluates `latestHeight == 0` again next time (since it was never set), so the chain never gets any commitment through this path.

Note: I could not fully verify within tool budget whether some other admin-only genesis function initializes `latestStateMachineHeight` to a non-zero value for newly added state machines outside `handleConsensus`; if such a path exists, it may fully mitigate the described impact for the initial connection case, though the underlying zero-sentinel/threshold-check pattern remains present in the code.
