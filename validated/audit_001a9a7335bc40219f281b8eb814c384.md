## Title
Webhook `shop` (and `topic`, `api_version`, `webhook-id`) headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value taken from the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header — a value that is never included in the signed payload. Anyone who can produce (or capture/replay) one valid `(body, hmac)` pair from Shopify can attach an arbitrary `shop` header to it and have the app's webhook handler process that payload as if it originated from a different, attacker-chosen shop.

### Finding Description
`HmacValidator.validate` computes and compares the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns just the raw body — the shop, topic, api version, and webhook id headers are excluded from the signed content: [2](#0-1) 

`Registry.process` validates only this body-only HMAC, then builds `WebhookMetadata` — including `shop` — directly from the unauthenticated header value and passes it to the app's registered handler: [3](#0-2) 

The equality this breaks: `hmac-verified(body)` is treated as if it also implies `shop-header == shop-that-Shopify-actually-sent-this-body-for`, but no such binding exists — `shop` is attacker-controlled independent of the signature. Any party who has ever received one legitimate webhook body+HMAC (e.g., by installing the app on their own store, which is normal, unprivileged access any merchant can obtain) can replay that exact `(body, hmac)` pair against the app's webhook endpoint while substituting a different `x-shopify-shop-domain` value, and the HMAC check will still pass, because the header is never part of the signed content.

### Impact Explanation
This is a cross-tenant data-integrity/authentication issue: the webhook consumer (the host application built on this gem) will process attacker-supplied `shop` attribution for real signed payload content, allowing an attacker who controls one shop to make an app believe events belong to a shop they do not control (e.g., injecting spoofed `orders/create`, `app/uninstalled`, or other lifecycle events attributed to a victim shop). Depending on how the host app trusts `WebhookMetadata#shop` (e.g., to look up/mutate per-shop state, trigger uninstall/data-erasure flows, or select which shop's access token to act with), this can lead to cross-tenant state corruption or unauthorized actions taken against another merchant's data — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high and requires no privileged access or leaked secrets: an attacker merely needs to be a legitimate (even free/trial) installer of the app on their own shop to receive at least one authentic webhook body/HMAC pair, then replay it with a forged `shop-domain` header at the app's public webhook endpoint. No knowledge of `api_secret_key` is needed because the replayed signature was legitimately generated by Shopify for that body; only the (unsigned) header is altered.

### Recommendation
Include the shop domain (and ideally topic/api-version/webhook-id) in the HMAC-covered signable content, or otherwise cryptographically bind the shop identity to the payload before exposing it to the handler (e.g., verify the header shop against the API version/webhook registration state, or require handlers to independently corroborate `data.shop` via an authenticated channel, such as looking up the registered webhook id's owning shop through the Admin API rather than trusting the header). At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be used as a trust boundary.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimate webhook delivery, e.g. `orders/create` with body `B` and header `X-Shopify-Hmac-SHA256: H` (valid for `B` under the app's `api_secret_key`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the exact same body `B` and the exact same `X-Shopify-Hmac-SHA256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` — this succeeds: [3](#0-2) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and processes the attacker's captured payload as though it came from `victim-shop.myshopify.com`.
