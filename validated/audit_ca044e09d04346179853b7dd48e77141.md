## Analysis: Fee-on-transfer (Token-2022 transfer-fee) accounting error analog

### Title
Missing pre/post balance verification lets Token-2022 transfer-fee mints break pool accounting - (`program/src/processor.rs`, `program/src/invokers.rs`)

### Summary
The Cooler.sol bug is caused by accounting for a *requested* transfer amount instead of the amount actually received when the underlying token charges a transfer fee. Raydium's AMM has the same pattern: in `Deposit`, `Withdraw`, `SwapBaseIn`, and `SwapBaseOut`, all pool-state updates (`amm.lp_amount`, `target_orders.calc_pnl_x/y`, swap output amounts) are derived from the *specified* `deduct_coin_amount`/`deduct_pc_amount`/`swap.amount_in`/`swap_amount_out` values, and the SPL `Transfer` CPI is issued for that same specified amount via `Invokers::token_transfer` / `token_transfer_with_authority`, without ever re-reading the vault's token account balance after the transfer completes to confirm the full amount landed.

### Finding Description
`Invokers::token_transfer` simply issues an `spl_token::instruction::transfer` for the caller-supplied `deposit_amount`/`amount` and never checks the destination's balance delta: [1](#0-0) 

In `Deposit`, the pool computes `deduct_coin_amount`/`deduct_pc_amount` from the invariant, transfers exactly that amount from the user to the vaults, and then immediately mints `mint_lp_amount` LP tokens and updates `target_orders.calc_pnl_x/y` using those same requested amounts — not the vault's actual post-transfer balance: [2](#0-1) 

The same pattern repeats for `SwapBaseIn`/`SwapBaseOut`, where `swap.amount_in`/`swap_in_after_add_fee` is transferred into the vault and `swap_amount_out`/`swap.amount_out` is paid out based on the invariant computed from `total_coin_without_take_pnl`/`total_pc_without_take_pnl` (pool token balances read before this transaction's inbound transfer), with no post-transfer balance re-check: [3](#0-2) [4](#0-3) 

If the coin or pc mint used for a pool is a Token-2022 mint with a `TransferFeeConfig` extension (functionally identical to a fee-on-transfer token like USDT-with-fee in the report), the vault would receive less than `deduct_coin_amount`/`swap.amount_in`, while the program's internal accounting (`amm.lp_amount`, `calc_pnl_x/y`, swap-out amount) assumes the full amount arrived — exactly the same root cause as the Cooler.sol issue: crediting the pre-fee amount instead of the post-fee (actually received) amount.

### Impact Explanation
Because LP minting and swap payouts are calculated from the pre-fee amount while only the post-fee amount is actually deposited into the vault, the pool's real token balance progressively falls behind its accounted balance (`total_coin_without_take_pnl`/`total_pc_without_take_pnl`, `amm.lp_amount`). This causes insolvent pool accounting: swap outputs and LP redemption amounts calculated later will exceed what the vault actually holds, ultimately freezing/loss of user or LP funds when withdrawals or swaps fail or drain the vault for early actors at the expense of later ones — matching the "insolvent pool accounting" / "permanent freezing of funds" impact bar.

### Likelihood Explanation
This is only reachable if a pool can be created/used with a fee-charging mint (e.g., Token-2022 `TransferFeeConfig`). I was not able to fully confirm within available searches whether `Initialize2`/`Deposit`/`Swap` strictly hardcode and enforce the token program account against the canonical `spl_token::id()` constant, or whether `spl_token_program_id` is merely derived from the caller-supplied `token_program_info.key` and passed straight into `unpack_token_account`/`Invokers::token_transfer` without an equality check to `spl_token::id()`. The naming pattern (`spl_token_program_id` as a plain variable used to unpack accounts and issue CPIs) is consistent with the latter, which would allow an attacker/pool-creator to combine standard `Initialize2` with a Token-2022 mint carrying a transfer fee, but I could not verify this constraint with certainty in the available iterations — this should be checked directly in `Self::unpack_token_account` and the account-loading code in `processor.rs` (`Initialize2`, `Deposit`, `Swap` entry points).

### Recommendation
- Enforce that all `token_program_info` accounts passed into `Initialize2`, `Deposit`, `Withdraw`, `SwapBaseIn`, and `SwapBaseOut` equal the canonical `spl_token::id()` (rejecting Token-2022/other token programs), or
- If Token-2022 support is intended, read the vault's token balance immediately before and after every `Invokers::token_transfer` call and use the actual received delta (not the requested amount) for all subsequent accounting (`mint_lp_amount`, `calc_pnl_x/y`, swap invariant updates).

### Proof of Concept
1. Attacker creates (or uses) a Token-2022 mint with a `TransferFeeConfig` extension (e.g., 10% fee) as the `coin` or `pc` mint for a new pool via `Initialize2`, if the token-program check is not strictly enforced to `spl_token::id()`.
2. Attacker calls `Deposit` with `max_coin_amount = 100`. The program computes `deduct_coin_amount = 100` and calls `Invokers::token_transfer` for `100`, but the vault only receives `90` after the mint's transfer fee.
3. The program still mints `mint_lp_amount` and updates `target_orders.calc_pnl_x`/`amm.lp_amount` based on the full `100`, per [5](#0-4) .
4. Repeating deposits/swaps continuously understates the vault's real holdings relative to `amm.lp_amount`/`total_coin_without_take_pnl`, so later `Withdraw`/`SwapBaseOut` calls compute payouts the vault cannot fully cover, per [6](#0-5) , resulting in insolvency for later LPs/swappers.
