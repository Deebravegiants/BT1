### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let `msg.value` be counted once per entry in `Hinkal.transact`, minting unbacked on-chain UTXOs via `DepositOnChainUtxosExternalAction` - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` computes `balanceDif` for the native asset by adding `msg.value` to the raw before/after balance delta, on the assumption that `address(0)` appears at most once in `circomData.erc20TokenAddresses`. Neither `HinkalHelper.dimensionsCheck` nor any other guard enforces uniqueness of `erc20TokenAddresses`, so an attacker can list `address(0)` more than once and have `msg.value` re-added to `balanceDif` for every occurrence, letting them mint on-chain UTXOs worth a multiple of the ETH they actually sent.

### Finding Description
The claimed invariant is:

`msg.value (real ETH received) == Σ utxoAmount_native (shielded native UTXOs minted)`

In `Hinkal.transact`, for every index `i` where `circomData.erc20TokenAddresses[i] == address(0)`: [1](#0-0) 

```
if (circomData.erc20TokenAddresses[i] == address(0)) {
    balanceDif = int256(newBalances[i]) + int256(msg.value) - int256(oldBalances[i]);
} else {
    balanceDif = int256(newBalances[i]) - int256(oldBalances[i]);
}
...
require(balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + int256(utxoAmount), ...);
```

Because `msg.value` is credited to `address(this).balance` atomically before the function body runs, `oldBalances[i]` (captured at line 78) already reflects the deposited ETH. Adding `msg.value` again is intended to "undo" that pre-crediting exactly once, so the formula is correct **only if `address(0)` appears once**. Nothing in `HinkalHelper.dimensionsCheck` or `checkOnchainCreation` [2](#0-1)  rejects duplicate token addresses — it only checks array lengths against `dimensions.tokenNumber`.

If the attacker sets `erc20TokenAddresses = [address(0), address(0), ...]` (k times), each occurrence independently satisfies:

`balanceDif_i = (newBalances[i] - oldBalances[i]) + msg.value == msg.value` (since the ETH balance doesn't change again inside the loop),

so the attacker can set `utxoAmount_i = msg.value` at **every** duplicated index and pass the per-index `require` check k times, while only sending `msg.value` once.

The attacker routes this through `circomData.externalActionData.externalActionId` pointing at `DepositOnChainUtxosExternalAction`, whose `runAction`: [3](#0-2) 

only performs an ERC20 `transferFrom` when `tokenAddress != address(0)`; for native entries it does nothing at all and simply lets the caller pick arbitrary `utxoAmounts[i]` via `externalActionMetadata`, whose sole runtime constraint is `deltaAmounts[i] == 0` (satisfied automatically since `onChainCreation[i] == true` forces `_calculateDeltaAmount` to return `0`). `utxoAmounts` is never bound by the ZK proof to any real value — the proof only certifies `getHashedCalldata(circomData) == circomData.calldataHash`, i.e., that the attacker didn't get front-run, not that the values are honest.

Consequently, for k duplicated `address(0)` entries with `utxoAmount_i = msg.value` each, the contract mints `k × msg.value` in on-chain native UTXOs while receiving only `1 × msg.value` in real ETH. This is the mechanism the question describes as "the native asset listed alongside its wrapped form": the exploit doesn't actually require WETH at all — the root defect is that the native-asset branch of `balanceDif` re-adds `msg.value` per index without any uniqueness guard on `erc20TokenAddresses`, so any repetition of `address(0)` (or of the same idea if `erc20TokenAddresses` were allowed to alias two entries onto the same underlying balance source) reproduces the double-count. `performHinkalChecks`, `verifyProof`, `rootHashExists`, and `checkOnchainCreation` do not constrain the multiset of `erc20TokenAddresses` or cross-check `utxoAmounts` against `msg.value`, so none of them catch this.

### Impact Explanation
The attacker mints shielded on-chain UTXOs backed by less ETH than credited — direct minting of shielded value without backing, i.e., protocol insolvency. Each `transact` call can repeat this with as many duplicate `address(0)` entries as `dimensions.tokenNumber` allows, scaling the unbacked mint linearly with the number of duplicated entries per call, and the attack is fully repeatable across transactions. This matches the "Critical: minting shielded value without backing (protocol insolvency)" category.

### Likelihood Explanation
No privileged role is required — this is reachable by any unprivileged EOA that can call `Hinkal.transact` with a self-generated proof, choosing `erc20TokenAddresses`, `onChainCreation`, and `externalActionData.externalActionMetadata` for `DepositOnChainUtxosExternalAction`, which is a legitimate, whitelisted external action (`externalActionMap`/`isAllowedRecipient`) intended for normal use. The only preconditions are (1) `DepositOnChainUtxosExternalAction` being registered in `externalActionMap`, and (2) `dimensions.tokenNumber` being large enough to include duplicate entries, both of which are ordinary operating conditions, not special states. Cost to the attacker is just gas plus the single genuine `msg.value` deposit; the gain is `(k-1) × msg.value` in unbacked shielded value per call, and the attack is repeatable indefinitely.

### Recommendation
- In `HinkalHelper.dimensionsCheck` (or a new check invoked from `performHinkalChecks`), enforce that `circomData.erc20TokenAddresses` contains no duplicate entries.
- Alternatively/additionally, restructure the `balanceDif` computation in `Hinkal.transact` to add `msg.value` exactly once for the whole transaction (e.g., track a `nativeAssetAlreadyCredited` flag) rather than per-index whenever `erc20TokenAddresses[i] == address(0)`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and `DepositOnChainUtxosExternalAction`; register the external action and allow it as recipient.
2. Craft `circomData` with `erc20TokenAddresses = [address(0), address(0)]`, `onChainCreation = [true, true]`, `amountChanges = [0, 0]`, `slippageValues` satisfied, and `externalActionData.externalActionMetadata = abi.encode(utxoAmounts)` where `utxoAmounts[0] = [1 ether]` and `utxoAmounts[1] = [1 ether]`.
3. Generate a locally valid proof (or use a proof-bypass/mock verifier available for testing per repo test harness) satisfying `verifyProof` and `rootHashExists`.
4. Call `Hinkal.transact{value: 1 ether}(...)`.
5. Assert: `address(hinkal).balance` increased by exactly `1 ether` (real deposit), but two on-chain commitments for `address(0)` totaling `2 ether` are inserted (`insertCommitments`/`OnChainCommitment` events), i.e., `vault balance delta (1 ether) < credited UTXO value (2 ether)`.
6. Assert the two `require` statements in `Hinkal.transact` (lines 111-114 and 137-146) both pass despite the mismatch, confirming the equality `balanceDif == amountChanges + utxoAmount` holds at each index while the true global invariant `msg.value == Σ utxoAmount_native` is violated.

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) external override onlyAllowedRecipient returns (UTXO[] memory utxoSet) {
        uint256 tokenCount = circomData.erc20TokenAddresses.length;
        require(
            tokenCount > 0 && deltaAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: token count mismatch"
        );

        address userAddress = circomData.originalSender;
        require(
            userAddress != address(0),
            "DepositOnChainUtxosExternalAction: Invalid originalSender"
        );

        uint256[][] memory utxoAmounts = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (uint256[][])
        );
        require(
            utxoAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: metadata length mismatch"
        );

        utxoSet = new UTXO[](countUtxos(utxoAmounts));

        uint256 utxoIndex = 0;
        for (uint256 i = 0; i < tokenCount; i++) {
            require(
                deltaAmounts[i] == 0,
                "DepositOnChainUtxosExternalAction: Delta amount must be zero"
            );

            address tokenAddress = circomData.erc20TokenAddresses[i];
            uint256 tokenTotal = 0;

            for (uint256 j = 0; j < utxoAmounts[i].length; j++) {
                uint256 amount = utxoAmounts[i][j];
                require(
                    amount > 0,
                    "DepositOnChainUtxosExternalAction: UTXO amount must be positive"
                );
                tokenTotal += amount;

                utxoSet[utxoIndex] = UTXO({
                    amount: amount,
                    erc20Address: tokenAddress,
                    stealthAddressStructure: circomData.stealthAddressStructure,
                    timeStamp: circomData.timeStamp + utxoIndex
                });
                utxoIndex++;
            }

            if (tokenAddress != address(0) && tokenTotal > 0) {
                transferERC20TokenFrom(
                    tokenAddress,
                    userAddress,
                    msg.sender,
                    tokenTotal
                );
            }
        }

        emit BlockedUtxosCreated();
    }
