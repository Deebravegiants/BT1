### Title
Emporium `runAction` executes arbitrary unaccounted calls from its own identity when `erc20TokenAddresses.length == 0` and `signerAddress == 0` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol / contracts/Hinkal.sol / contracts/CircomDataBuilder.sol)

### Summary
Setting `externalActionId == HINKAL_EMPORIUM_ACTION_ID` with `erc20TokenAddresses.length == 0` forces `formInputForCircom` to select `formInputEmporiumMin`, which only constrains `message`, `timeStamp` and `calldataHash` in the proof, leaving `EmporiumStack` (decoded from `externalActionMetadata`) entirely proof-unconstrained. Because `Hinkal.transact`'s balance-diff/slippage loop and `EmporiumUpgradeable.runAction`'s own `balancesBefore`/`balancesAfter` loop are both sized by `circomData.erc20TokenAddresses.length`, setting that length to 0 disables all balance accounting for the transaction, while the `stack.ops` loop inside `runAction` still executes unconditionally and, with `stack.signerAddress == address(0)`, skips signature verification (`verifyWallet` returns after only a nonce check) and performs `op.endpoint.call{value: op.value}(op.callData)` directly from Emporium's own address.

### Finding Description
The broken equality is: *assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter` (Emporium) and `oldBalances`/`newBalances` (Hinkal)*.

- `formInputForCircom` in `contracts/CircomDataBuilder.sol` (lines 134-148) routes to `formInputEmporiumMin` (lines 150-161) whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`. That function only encodes `emporiumMessage`, `timeStamp`, `calldataHash` as public signals - none of `EmporiumStack`'s contents (ops, endpoints, callData, value, signerAddress) are proof-constrained. [1](#0-0) 

- In `Hinkal.transact`, the balance/slippage accounting loop iterates `circomData.erc20TokenAddresses` (lines 78-147); with length 0 it runs zero iterations, so no balance check of any kind is performed for the whole transaction. [2](#0-1) 

- `_externalTransact` computes `deltaAmountChanges` sized by `erc20TokenAddresses.length` (empty here) and calls `EmporiumUpgradeable.runAction` with that empty array. [3](#0-2) 

- Inside `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are likewise sized by `circomData.erc20TokenAddresses` (empty), so the post-loop that checks `balanceChange` and mints UTXOs never runs. But the `stack.ops` loop (lines 91-118) is completely independent of `erc20TokenAddresses` and executes unconditionally over attacker-controlled `EmporiumStack.ops`. [4](#0-3) 

- `verifyWallet` only records/checks the nonce (`usedMessages`) and returns immediately without any signature check when `stack.signerAddress == address(0)`: [5](#0-4) 

- With `signerAddress == address(0)`, the CASE 1 condition `op.invokeWallet && stack.signerAddress != address(0)` is false, so every op falls into CASE 2 and is executed as `op.endpoint.call{value: op.value}(op.callData)`, with `msg.sender` for that sub-call equal to Emporium's own address. The only guard is a selector check blocking `callHinkalWallet`/`doSendToRelay` selectors; any other call is allowed: [6](#0-5) 

Exploit flow: an unprivileged attacker calls `Hinkal.transact` with `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, and `externalActionData.externalActionMetadata` = an `EmporiumStack` with `signerAddress = address(0)` and `ops` containing a call to any target the attacker chooses (e.g. another `ExternalActionBaseUpgradeable`-derived contract that has Emporium in its `_isAllowedRecipient` set, or any contract/token where Emporium's own address holds a balance). Since `formInputEmporiumMin` doesn't constrain the stack, the attacker generates a proof only over `message`/`timeStamp`/`calldataHash` for their own trivial UTXO set (or an all-zero/empty nullifier set, subject to `dimensionsCheck`/`checkOnchainCreation`, which do not depend on the emptied token array either). `Hinkal.transact` verifies the (weak) proof, skips all balance loops (empty array), and calls into `EmporiumUpgradeable.runAction`, which performs the attacker's arbitrary call from Emporium's own identity with zero accounting anywhere in the call stack.

Existing guards fail because: `dimensionsCheck`/`checkOnchainCreation` operate on nullifier/commitment dimensions, not on `erc20TokenAddresses` size or `EmporiumStack` contents; `verifyProof` only checks the minimal Emporium public inputs; `rootHashExists`/`insertNullifiers` are orthogonal to the ops execution; and the balance equality checks in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` are gated by the very array the attacker set to zero-length.

### Impact Explanation
Any funds held at Emporium's own address (accumulated relay fees, in-flight balances left over from prior transactions where a swap dust remained, or funds the attacker deposits via `op.value`/other legitimate flows into Emporium) can be moved out via arbitrary calls with zero balance accounting anywhere in the code path. If Emporium is listed as an `_isAllowedRecipient` on another `ExternalActionBase`-derived contract, the attacker can also pivot through Emporium's trusted identity to call that other action's `runAction` (or other privileged-recipient-gated functions) directly, bypassing Hinkal's proof/root/nullifier machinery for that second contract entirely. This is direct theft of protocol/relay-held or in-flight funds with an authorization bypass (`onlyAllowedRecipient` trusts Emporium's `msg.sender`, but that call was never actually validated by any meaningful proof) - matching the Critical/High category of "executing calls or moving assets that a wallet owner or prover never authorized," and potentially direct theft of in-flight funds sitting at Emporium.

### Likelihood Explanation
Preconditions are trivial for an unprivileged attacker: they only need to craft `circomData` with `erc20TokenAddresses = []`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and an `EmporiumStack` with `signerAddress = address(0)`, then generate a valid proof for the minimal circuit (which only constrains 3 public signals, none related to the ops). No privileged role, relay, or victim cooperation is required. The attack is repeatable every time Emporium (or another contract trusting Emporium as an allowed recipient) holds any residual balance, and cost is just gas plus proof generation for the trivial circuit.

### Recommendation
Do not let the size of `erc20TokenAddresses` gate whether balance accounting happens for `EmporiumStack.ops`. Specifically:
1. In `EmporiumUpgradeable.runAction`, require that `stack.ops.length == 0` whenever `circomData.erc20TokenAddresses.length == 0`, or otherwise ensure the ops loop cannot execute without the corresponding token accounting being active.
2. Make `formInputEmporiumMin`/the min-proof path constrain (hash into the proof's public inputs) the full `EmporiumStack` content, not just `message`/`timeStamp`/`calldataHash`, so `signerAddress`, `ops`, and per-op `endpoint`/`callData`/`value` cannot be swapped in unconstrained by the prover.
3. Remove the `signerAddress == address(0)` bypass that skips all signature verification for CASE 2 stateless ops, or restrict stateless (non-wallet) calls to only occur when there is a fully-verified, non-zero signer, and always require `erc20TokenAddresses` to reflect every token whose balance an op could touch.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (with a mock verifier that accepts trivially valid proofs for the min circuit, or use the real min-circuit prover), and a victim ERC20 token; register Emporium under `HINKAL_EMPORIUM_ACTION_ID`.
2. Fund Emporium's own address directly with `victimToken` (simulating in-flight/leftover balance) - `victimToken.mint(address(emporium), 1000e18)`.
3. Build `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(victimToken), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e18))})], maxFee: 0, deadline: 0, v:0, r:0, s:0}))`.
4. Generate proof over `formInputEmporiumMin`'s three public signals (`emporiumMessage`, `timeStamp`, `calldataHash`), matching a trivial/empty nullifier set.
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker EOA.
6. Assert: `victimToken.balanceOf(attacker)` increases by `1000e18` and `victimToken.balanceOf(address(emporium))` goes to 0, while `Hinkal.transact`'s balance loop (lines 96-147) never reverted because `erc20TokenAddresses.length == 0`, and `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` (also empty) never flagged the drain - i.e., assets moved (1000e18) != assets accounted (0).

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }
    }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
