### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header — never covered by that signature — to the app as the authoritative tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `Utils::HmacValidator.validate` computes the HMAC exclusively over this signable string and compares it to the `hmac-sha256` header using `OpenSSL.secure_compare`: [3](#0-2) . None of the other Shopify headers — `shop-domain`, `topic`, `webhook-id`, `api-version` — are included in the signed material; they are parsed straight from `@headers` via `shopify_header` accessors: [4](#0-3) .

`Registry.process` performs exactly this check-then-trust sequence: it calls `Utils::HmacValidator.validate(request)` and, once it passes, builds `WebhookMetadata` directly from `request.shop` (the unauthenticated header) and hands it to the app's handler: [2](#0-1) .

Critically, the HMAC secret used here is `Context.api_secret_key` — the app's single client secret, shared across every shop that installs the app — not a per-shop secret. Any merchant who installs the app can capture a raw body + valid HMAC pair from a real webhook delivered to their own shop (the secret is the same for all tenants). They can then replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. `HmacValidator.validate` will still return `true` (the signed bytes — the body — are unchanged and correctly signed), but `Registry.process` will attribute the payload to the attacker-chosen `shop`, which is exactly the "bytes verified versus bytes parsed" / "field acted on but not covered by the HMAC" binding break: the equality the caller implicitly relies on, `shop_that_signed_the_request == shop_reported_to_the_handler`, does not actually hold — only `body_signed == body_parsed` is checked, and `shop` is entirely unauthenticated.

### Impact Explanation
This breaks the tenant identity binding the gem is documented to provide: apps are told in `docs/usage/webhooks.md` that `Registry.process` "will verify the request did indeed come from Shopify" and are shown a canonical pattern of dispatching downstream work keyed on `data.shop` (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`). Because `shop` is not authenticated, a low-privileged merchant/tenant of a multi-tenant app can forge webhook deliveries that are processed as belonging to a different shop, resulting in cross-tenant data injection/corruption (e.g., writing attacker-controlled order/product data into another merchant's records, or triggering tenant-scoped side effects under a victim's identity). This matches the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be an installed (unprivileged) merchant of the target app able to receive at least one legitimate webhook to their own shop — no access to `api_secret_key`, access tokens, or TLS interception is needed, since the secret is shared app-wide and the `shop-domain` header is never bound to it. This is a low-bar, realistically reachable condition for any multi-tenant Shopify app built on this gem.

### Recommendation
Bind the reported `shop` to the signed payload, or otherwise cryptographically tie header-derived identity to the signature: e.g., include the `shop-domain` (and ideally `webhook-id`/`topic`) in the HMAC-signed input, or require the app to independently corroborate `request.shop` against known/allow-listed shops with an active subscription for that specific `webhook_id`/topic before trusting it. At minimum, document prominently that `data.shop` is unauthenticated and must not be used as a sole tenant-scoping key without additional verification (e.g., cross-checking against the webhook subscription that was registered for that shop).

### Proof of Concept
1. App installs webhook handling per `docs/usage/webhooks.md`, dispatching `perform_later(shop_domain: data.shop, ...)` from the handler.
2. Attacker (a real, installed merchant "attacker-shop.myshopify.com") receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker POSTs the identical raw body `B` and header `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, matches `H`, and returns `true` (per `lib/shopify_api/utils/hmac_validator.rb` lines 26-31), since the signed bytes are body-only and unchanged.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and invokes the app's handler, which processes attacker-controlled data under the victim's tenant identity.
