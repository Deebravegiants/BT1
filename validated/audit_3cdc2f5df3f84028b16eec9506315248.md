### Title
Protocol fee rounds to zero for low-decimal input tokens, allowing fee bypass via order splitting - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` computes the protocol fee on order inputs using a fixed `10_000` basis-point denominator that is independent of the input token's decimals, causing the fee to floor to zero for tokens with few decimals (or small enough amounts), letting an attacker route economically significant value through the gateway while paying no protocol fee.

### Finding Description
When an order is placed, the protocol fee is computed as `protocolFee = (originalAmount * protocolFeeBps) / 10_000` and the reduced amount is escrowed, with the difference emitted as `DustCollected`: [1](#0-0) 

`protocolFeeBps` (or `_destinationProtocolFees[destinationHash]`) is a fixed fraction (e.g. 5–100 bps) applied against raw token units, regardless of the token's decimal precision: [2](#0-1) 

Because integer division truncates toward zero, any input amount smaller than `10_000 / protocolFeeBps` raw token units yields `protocolFee == 0`. For an 18-decimal token this threshold corresponds to a negligible dollar value (e.g., at 5 bps, `2000` wei ≈ $0.000000000000002), so it's irrelevant in practice. But for tokens with few decimals (e.g., 2-decimal Gemini USD or other low-decimal stablecoins), the same `2000` raw-unit threshold corresponds to a real, exploitable dollar amount (e.g. $20 with a 2-decimal token), which is exactly the bug class described in the referenced Allo `percentFee`/`getFeeDenominator` report: a fee ratio computed with a token-decimals-agnostic constant denominator, allowing the fee to be bypassed by choosing low-decimal tokens and/or splitting a large transfer into many sub-threshold orders.

An attacker (any unprivileged user calling `placeOrder`/`_fundIntent`) can split a large transfer of a low-decimal ERC-20 into many orders each below the rounding threshold, paying zero protocol fee on each while still moving value cross-chain/same-chain through the intent gateway. This directly reduces protocol revenue (`DustCollected`) with no additional cost beyond gas for extra transactions.

### Impact Explanation
This is a protocol-fee/revenue-leakage bug: fees intended to be collected by governance (`protocolFeeBps`, `_destinationProtocolFees`) can be systematically evaded for any token whose decimals are low enough relative to the configured bps, resulting in permanent loss of protocol fee income at scale. It does not directly cause fund theft or forged message delivery, but it is a concrete, repeatable loss of protocol funds (fee bypass), matching the Medium classification of the analogous Allo report.

### Likelihood Explanation
Likelihood is moderate to high in real deployments that support any low-decimal ERC-20 (2–6 decimals are common, e.g. USDC-like tokens, GUSD). Any user can trigger it without special privileges by simply placing many orders below the fee threshold — this is a low-cost, easily automatable attack once a low-decimal token pool exists with a small `protocolFeeBps`.

### Recommendation
- Enforce a minimum fee floor (e.g., revert or round up) when `protocolFeeBps > 0` and the computed fee rounds to zero but the amount is nonzero, or
- Scale the fee denominator relative to token decimals (query and cache `IERC20Metadata.decimals()` per token) so `protocolFeeBps` represents a decimal-independent percentage, or
- Enforce a minimum order size per token (denominated in a canonical unit, e.g., via price oracle) so sub-threshold orders that would round the fee to zero are rejected outright.

### Proof of Concept
1. Deploy `IntentGatewayV2` with `protocolFeeBps = 5` (0.05%, as used in current deployments per docs).
2. Use a 2-decimal ERC-20 token as `order.inputs[0].token`.
3. Place an order with `amount = 1999` (raw units, i.e. $19.99 given 2 decimals).
4. `protocolFee = (1999 * 5) / 10_000 = 0` (integer division), so `reducedAmount == originalAmount`, and no `DustCollected` fee is taken — see the fee computation at [3](#0-2) 
5. Repeating this with many sub-$20 orders lets an attacker move an arbitrarily large total value through the gateway while paying zero protocol fee, whereas a single order of the same aggregate value in an 18-decimal token would correctly incur the fee.
