Confirmed. The webhook `shop` field is not covered by the HMAC, and this is exactly the identity-binding-break pattern the rules describe.

### Title
Webhook tenant identity (`shop` domain) is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` field solely from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, while the HMAC signature verified by `Utils::HmacValidator` is computed only over the raw request body. This is the exact bug class from the external report: a field that is *acted on* (the shop used for tenant attribution in `WebhookMetadata`) is not covered by the cryptographic binding (`hmac`) that is supposed to authenticate the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic tie to that value [2](#0-1) .

`HmacValidator.validate` computes the HMAC exclusively from `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header [3](#0-2) . It never incorporates the `shop` field into the signed material.

`Registry.process` validates only this body-bound HMAC, then trusts `request.shop` as the tenant identity forwarded to the handler via `WebhookMetadata` [4](#0-3) . `WebhookMetadata.shop` is documented as "The shop domain of the webhook" and host apps are explicitly instructed to use `data.shop` to route/attribute the payload (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [5](#0-4) [6](#0-5) .

The identity binding that should hold is: `shop header used for tenant attribution == shop cryptographically bound by hmac`. It does not — the HMAC secret (`api_secret_key`) is shared across every shop that installs the same app, and the signature covers only the body, so it is valid for *any* header combination as long as the body bytes match. Any party who can obtain one valid `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own store and capturing a real webhook delivery) can replay that exact body/hmac pair while substituting an arbitrary `x-shopify-shop-domain` header. `Registry.process` will accept it as valid and hand the handler `WebhookMetadata` claiming a different shop, because the shop domain is never checked against anything derived from the signature.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide: the `shop` value handed to the application's webhook handler is supposed to reliably identify which merchant/tenant a payload belongs to, but it is fully attacker-controlled independent of the HMAC check. A host application that follows the documented pattern (using `data.shop` to look up a session/store record and process the webhook body under that shop) can be made to attribute attacker-supplied webhook content to an arbitrary victim shop — a cross-tenant data-integrity/confusion issue reachable by an unprivileged internet user who only needs their own legitimate app installation (no leaked credentials, no `api_secret_key` access, no privileged account required).

### Likelihood Explanation
High likelihood of the precondition being met: any developer/attacker can install the target app on their own store, which is a standard, unprivileged interaction, and thereby obtain a legitimately signed `(raw_body, hmac)` pair for that shared app secret. Forging arbitrary HTTP headers on a POST to the app's public webhook endpoint requires no special access.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values into the signable string used for HMAC verification, or independently verify that `request.shop` corresponds to a shop with an active session/installation before trusting it for tenant attribution, matching Shopify's documented webhook verification guidance of validating the full expected payload/header set together rather than only the body.

### Proof of Concept
1. Install the app on shop A (`attacker-shop.myshopify.com`); Shopify delivers a legitimate webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)`.
2. Attacker crafts a new HTTP POST to the same webhook endpoint with identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(api_secret_key, B)` and compares to `H` — this passes because the shop header was never part of the signed material [7](#0-6) .
4. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop = "victim-shop.myshopify.com"` and passed to the app's handler, which processes body `B` under the victim's tenant context [8](#0-7) .
