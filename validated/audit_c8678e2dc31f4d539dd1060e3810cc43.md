I have enough detail confirmed. The vulnerability is in `ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process`: the `shop-domain` header is trusted for tenant identification while `to_signable_string` only covers the raw request body in the HMAC computation.

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without being part of the signed payload [2](#0-1) . `Registry.process` validates only the HMAC of the request (i.e. the body) and then constructs `WebhookMetadata` using the unauthenticated `request.shop` value, which is handed to the host application's handler as the tenant identifier [3](#0-2) .

### Finding Description
The binding that should hold is: `hmac == HMAC(secret, body || shop || topic || webhook_id)`, i.e., the shop the handler believes sent the webhook should be cryptographically bound to the signature. Instead, the gem computes and validates `HMAC(secret, body)` only [4](#0-3) , and the `shop` field consumed by `Registry.process` and exposed to the handler via `WebhookMetadata` comes from an HTTP header that is entirely outside the signed material [2](#0-1) .

This is exactly the H-8 bug class in the report: "a field acted on but not covered by the HMAC." Docs confirm host applications are expected to use `data.shop` for tenant routing/lookups (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [5](#0-4) .

An unprivileged internet user who has ever installed the app on their own shop (a free/dev store) will legitimately receive real webhook deliveries with valid `(body, hmac)` pairs from Shopify. Because `hmac` only signs `body`, the attacker can take one such valid `(body, hmac)` pair and replay it directly to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with any victim shop's domain. `Utils::HmacValidator.validate` still passes because it only recomputes the HMAC over `body`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-chosen) victim shop sent this data [6](#0-5) .

### Impact Explanation
Since host apps (per this gem's own documented usage pattern) route/persist data keyed by `data.shop`, this breaks the tenant boundary: an attacker can inject arbitrary (self-crafted, since the body content is attacker-controlled at their own shop) webhook payloads that get attributed to any other merchant's tenant record — including mandatory topics like `shop/redact` or `customers/redact`/`customers/data_request`, which are compliance-critical topics the app must handle per-shop [7](#0-6) . This is a cross-tenant access issue caused entirely by this gem's own signature-scope decision, requiring no possession of the app's `client_secret` or any victim credential.

### Likelihood Explanation
Likelihood is realistic: any unprivileged user can install a target app on their own shop (many apps offer free installs/dev-store trials), capture one legitimate webhook body+HMAC pair via a basic HTTP proxy on their own infrastructure, and replay it against the shared public webhook endpoint with a forged `shop-domain` header. No secret material or victim access is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC validation (or otherwise cryptographically bind them, e.g. by validating each field against Shopify's published shop list/webhook registration metadata), so header values cannot be swapped independently of the signed body. At minimum, `Registry.process` should reject cases where the header-derived `shop` cannot be corroborated against data already known to belong to the shop that installed/registered the given `webhook_id`/topic.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and captures a genuine webhook delivery for topic "customers/redact":
body = '{"customer":{"id":1},"orders_to_redact":[]}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, body) # attacker doesn't need to know this;
                                                                              # they just capture the real header Shopify sent
hmac_b64 = Base64.encode64(hmac)  # captured value from a real Shopify delivery

# Attacker replays the exact same body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim shop:
forged_headers = {
  "x-shopify-topic" => "customers/redact",
  "x-shopify-hmac-sha256" => hmac_b64,       # unchanged - still validates, since it only signs body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged, not covered by HMAC
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

req = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(req)
# => HmacValidator.validate(req) returns true (only body is checked)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", ...))
# Host app now processes attacker-controlled data under the victim tenant's identity.
```
