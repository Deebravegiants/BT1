Audit Report

## Title
Missing `return` after failed email-claim extraction in `handleTokenExchange` allows OIDC session creation despite a reported HTTP 500 failure - ([File: core/sessions/oidcauth/oidc.go])

## Summary
In `handleTokenExchange`, when the `email` claim cannot be type-asserted from the verified ID token claims, the code logs the error and writes a `500` response via `c.String(...)` but does not `return`, unlike every other error branch in the same function. [1](#0-0)  Execution falls through with `email` as the empty string, and the function continues to compute the role, insert a new row into `oidc_sessions`, audit-log a successful login, and set the session cookie — all despite having already told the client the request failed.

## Finding Description
The function's error-handling convention consistently pairs each `c.String(http.StatusInternalServerError, ...)`/`c.JSON(...)` call with an immediate `return`, e.g. after the `id_token` extraction failure, ID-token verification failure, claims-parsing failure, ID-claims extraction failure, and role-mapping failure. [2](#0-1)  The `email` claim check breaks this pattern: it writes the error response but omits `return`. [1](#0-0) 

Because there is no `return`, execution proceeds to:
1. Map role from verified group claims via `oi.IDClaimsToUserRole(...)`. [3](#0-2) 
2. Insert a new `oidc_sessions` row using the empty `email` and the computed `role`. [4](#0-3) 
3. Emit an audit log entry (`AuthLoginSuccessNo2FA`) and set the session cookie via `ginSession.Set(webauth.SessionIDKey, clSession.ID)` / `ginSession.Save()`. [5](#0-4) 
4. Finally write a superfluous `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})` on top of the already-sent 500 response. [6](#0-5) 

This is a genuine "checked-but-ignored" defect: the failure signal (`ok == false`) is detected and logged, but the code proceeds to create and persist a session anyway, and delivers a working `Set-Cookie` header to the client even though the HTTP status/body indicates failure. No later check aborts or rolls back the session creation once this branch is entered.

## Impact Explanation
A client that completes an otherwise-legitimate OIDC exchange (state verified, token exchange succeeded, ID token cryptographically verified, group claims mapped to a role successfully) but whose ID token/claims payload lacks a usable `email` field ends up with:
- A persisted `oidc_sessions` row with `user_email = ''` and the correctly mapped `role`.
- A valid `Session-ID` cookie that `AuthorizedUserWithSession`/`AuthenticateBySession` will accept on subsequent requests, granting that role.

This violates the security assumption that a `500` response from the token-exchange endpoint means no session was created, and produces an orphaned/inconsistently-audited session tied to an empty identity. This maps to the in-scope "node API authentication/session-state integrity" category: authenticated state is created and usable even though the API explicitly reported failure to the caller.

## Likelihood Explanation
Triggering this only requires the OIDC provider to omit or misshape the `email` claim on an otherwise-successful exchange (e.g., a provider/scope configuration where `email` is not included), a condition entirely plausible without any node-side privilege — the exploiting party is simply completing the standard `/oidc-login` → `/oidc-login/callback` flow as an ordinary user against the configured provider. No operator, admin, database, or host access is needed, and the flow uses only the public token-exchange endpoint.

## Recommendation
Add a `return` statement immediately after the `c.String(http.StatusInternalServerError, "Failed to get email from claims")` call in the `!ok` branch, mirroring every other error branch in `handleTokenExchange`, so a missing/invalid `email` claim aborts session creation, DB insertion, and cookie issuance.

## Proof of Concept
1. Configure the node against an OIDC provider (or a test double acting as one) whose ID token/claims for an otherwise valid, successfully-verified exchange do not include an `email` field (or include a non-string value).
2. Drive the normal flow: `GET /oidc-login` → provider login → redirect → `POST` to the token-exchange endpoint handled by `handleTokenExchange` with the valid `code`/`state`.
3. Observe: response is HTTP 500 with body `"Failed to get email from claims"`, but the response also carries a `Set-Cookie` for the Gin session containing `SessionIDKey`, and a new row appears in `oidc_sessions` with `user_email = ''` and `user_role` equal to the mapped role.
4. Replay the received session cookie against an authenticated `/v2/...` endpoint and confirm the request is authenticated with the mapped role, despite the original exchange having reported failure to the client.
