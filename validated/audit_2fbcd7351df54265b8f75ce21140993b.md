### Title
Uniswap V4 spot-price venue pricing in Simplex FXFiller can be manipulated to extract solver funds - (File: sdk/packages/simplex/src/strategies/fx.ts, sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts)

### Summary
Simplex's `FXFiller` prices "venue" (curveless) trading pairs directly from a Uniswap V4 pool's instantaneous `sqrtPriceX96` mid-price, with no TWAP, no execution-size/impact term, and only an optional static-reference deviation guard. An attacker can move that pool's tick with a swap and have the solver quote and fill intents against the tainted mid, capturing the difference — the same root cause as the reported `BalancerLPComposableStableEthOracle::getPriceInEth` issue: a spot AMM state value is treated as a trusted oracle price for downstream fund-moving decisions.

### Finding Description
For curveless (venue-priced) pairs, `resolveLegRates` fetches `venueUsdPrice`, which calls `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which reads the pool's `token0Price`/`token1Price` — a direct function of the pool's current `sqrtPriceX96` — with no averaging window: [1](#0-0) 

This raw mid is used, unmodified by size, as the rate for the entire order quantity: [2](#0-1) 

The only defense is `checkPriceGuard`, which is optional per-chain config and only rejects when the quote deviates from a *static* reference price by more than `maxDeviationBps` — it does not detect or resist an in-flight manipulation, and does not model execution/slippage cost at all: [3](#0-2) 

This is documented in-repo as a known, only-partially-mitigated gap: [4](#0-3) 

The same manipulable mid also feeds `referenceRate`, which sizes an order's USD notional used for reorg-protection depth — again guarded only by the static-reference band: [5](#0-4) 

This mirrors the external report's root cause exactly: a price derived from live, atomically-movable AMM/pool state (`pool.getRate()` there, `sqrtPriceX96`-derived mid here) is consumed directly by a fund-moving component (an LMPVault price oracle there; a solver's fill-pricing/funding engine here) without manipulation resistance (no TWAP, no size-aware slippage, and an optional guard that only checks against a fixed reference, not against manipulation).

### Impact Explanation
An attacker who moves a configured Uniswap V4 pool's price (e.g., via a swap, potentially leveraged/flash-loaned) within — or in the absence of a configured — deviation guard can cause the Simplex filler to quote and fill an intent order at the manipulated mid price instead of a manipulation-resistant price. Because `computeLegPolicyOutput` extends the mid linearly across "the whole priced quantity" with no size/impact term, the attacker's realized output can exceed what an honest swap through that same pool would have produced, extracting value directly from the solver's committed liquidity/vault funds on each fill. Where `checkPriceGuard` is left unconfigured ("omit both to leave the chain unguarded" per the pricing docs) there is no bound on the deviation at all.

### Likelihood Explanation
Likelihood is Medium: the attack requires the pool used for venue pricing to have limited liquidity/moderate cost to move, and the manipulation window must persist long enough for the off-chain solver to observe the order and submit/execute the fill (not necessarily atomic in a single block, since the phantom-bid/fill pipeline is asynchronous), so it costs real capital held over that window rather than being a free flash-loan-only exploit. It is nonetheless directly reachable by any unprivileged actor who can submit a swap on the referenced pool and place an intent order — no privileged role is required — and the codebase's own documentation explicitly flags the guard as covering only "deviation from a static reference, not execution cost," confirming the gap is real and unaddressed for the trade-pricing path.

### Recommendation
- Replace or supplement the instantaneous `sqrtPriceX96` mid with a time-weighted average price (TWAP) read from the pool (or an external/aggregated price source) for both `computeDirectPoolPriceUsd` (trade pricing) and `referenceRate` (reorg-protection sizing).
- Make `checkPriceGuard` mandatory (not optional per chain) for any venue-priced pair, and additionally bound the maximum single-swap price impact/tick movement observed immediately prior to pricing, not just deviation from a stale static reference.
- Introduce a size-aware execution price (apply the pool's own fee tier and a simulated price-impact curve for the quoted quantity) instead of linearly extending the raw mid across the whole order, so a manipulated or thin pool cannot be used to extract more than genuine swap economics would allow.

### Proof of Concept
1. Attacker identifies a chain/pair configured under `[vault.uniswapV4]` for venue pricing (curveless pair, e.g. USDC/CNGN) with either no `referencePrice`/`maxDeviationBps` configured, or a wide band.
2. Attacker swaps against the referenced Uniswap V4 pool to move `sqrtPriceX96` so that `token0Price`/`token1Price` favors the attacker (within the configured band, or unbounded if unconfigured), per `computeDirectPoolPriceUsd` (`sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts:246-272`).
3. Attacker (or their contract) places an intent order on the affected pair sized so that `resolveLegRates`/`computeLegPolicyOutput` prices the full requested quantity at the now-skewed mid (`sdk/packages/simplex/src/strategies/fx.ts:1453-1465`), with `checkPriceGuard` passing because the deviation stays inside the static band or no guard is configured.
4. The Simplex filler bids and fills the order at the manipulated rate, paying out more than an honest execution through that pool would have cost the attacker, funded from the solver's wallet/vault.
5. Attacker reverses/unwinds the pool-skewing swap, realizing the price difference as profit at the solver's expense — the same pattern of a small manipulating trade producing a profitable pricing discrepancy described in the source report.

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

			return {
				exoticToken: c0,

		}

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
