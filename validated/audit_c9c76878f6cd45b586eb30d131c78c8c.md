### Title
Webhook `shop`-domain identity binding bypass: HMAC signs only the raw body, not the `shop`/`topic` headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `Utils::HmacValidator.validate` covers the JSON body bytes exclusively. The `shop`, `topic`, `webhook_id`, and `api_version` fields are read directly from HTTP headers and are never included in the signed content, yet `Registry.process` passes `request.shop` straight into `WebhookMetadata` and dispatches it to the host application's handler as the authenticated tenant identity for the event.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. Meanwhile `shop`, `topic`, `webhook_id` and `api_version` are pulled from headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC over the body, then trusts `request.shop`/`request.topic` unconditionally to build the `WebhookMetadata` handed to the app's own webhook handler: [3](#0-2) 

Because Shopify signs webhooks per-app (a single `Context.api_secret_key` is shared across every shop that installs the app, per `HmacValidator.validate`/`validate_signature`): [4](#0-3) 

an attacker who has installed the app on their own store (an "unprivileged" tenant from the app developer's perspective) can trigger any webhook topic against their own shop and legitimately obtain a `(raw_body, hmac)` pair that is valid under the same shared app secret. Because the header fields (`shop-domain`, `topic`, `webhook_id`) are outside `to_signable_string`, that attacker can replay the identical `raw_body`+`hmac` to the app's shared webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header claiming to be a victim shop. `HmacValidator.validate` still returns `true` because it only re-derives the signature from `@raw_body`, and `Registry.process` forwards the attacker-chosen `shop` value to the handler as if it were authenticated.

This breaks the intended identity binding: **shop authenticated by Shopify's signature ≠ shop the byte content was actually signed for**. The equality that should hold — `hmac == HMAC(secret, body ⧺ shop ⧺ topic)` — is instead only `hmac == HMAC(secret, body)`, letting the `shop`/`topic` fields float freely relative to the signed bytes.

### Impact Explanation
Any downstream logic in the host application that keys tenant-scoped work off `WebhookMetadata#shop` (looking up an access token/session for that shop, writing/deleting tenant data, enqueuing per-shop jobs, as shown in the gem's own documented usage) can be made to act on data intended for one shop while believing it belongs to another shop, i.e., a cross-tenant identity confusion enabled purely by this gem's failure to bind the header-derived `shop` to the signed payload. This matches the Critical bucket of "cross-tenant access" achieved without any credential of the victim shop — only requiring the attacker's own legitimate (but unprivileged) shop installation.

### Likelihood Explanation
Any merchant/developer who has (or creates) their own installation of a multi-tenant Shopify app satisfies the "unprivileged internet user" bar — they hold no elevated role, no leaked secret, and no access to the victim's credentials. They only need the ability to trigger a webhook on their own store (trivial: update a resource that has a subscribed topic) and to send an HTTP POST with custom headers to the app's public webhook endpoint, which this gem exposes as documented in `docs/usage/webhooks.md`.

### Recommendation
Bind the identity-relevant headers into the signed content check, e.g. reconstruct the signable string to include `shop`, `topic`, and `webhook_id` (in a canonical form) before validating the HMAC, or independently verify that the value of `shop` matches an app-side authorization record (e.g., a previously stored, verified session for that exact shop) before trusting it, rather than passing the raw header value straight through to the handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining a legitimate shared `client_secret`-signed webhook flow.
2. Attacker triggers a webhook (e.g. `orders/create`) on their own store, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` value Shopify computed with the app's shared secret.
3. Attacker replays that exact `raw_body` + `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any desired `X-Shopify-Topic`).
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared secret (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with the attacker's spoofed `shop`/`topic` and dispatches it to the host app's handler, which acts as if the event genuinely originated from `victim-shop.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:188-200`).
