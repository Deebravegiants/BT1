### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook using `Utils::HmacValidator.validate(request)`, which only verifies the HMAC over the raw request body [1](#0-0) [2](#0-1) . The `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers and are never included in the signed payload [3](#0-2) , yet `shop` is handed to the app's handler as the trusted tenant identifier via `WebhookMetadata` [4](#0-3) [2](#0-1) .

### Finding Description
The identity binding that should hold is:
`shop header value == shop that actually produced/authorized the signed body`

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the header HMAC [5](#0-4) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` accessors all read straight from attacker-controllable HTTP headers with no cross-check against the signed content [6](#0-5) .

`Registry.process` validates only the HMAC/body pairing, then immediately trusts `request.shop` as the tenant identity and forwards it to the app-registered handler [2](#0-1) :
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```

Because the app's `api_secret_key` is one single value shared across every shop that installs the app, any unprivileged attacker who installs the app on their own (free/dev) shop can receive a genuinely-HMAC-signed webhook from Shopify (Shopify signs it with the app's secret) for their own shop. The attacker can then replay that exact `raw_body` + `hmac-sha256` header pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will still succeed, because it only checks that `hmac == HMAC(secret, raw_body)`, and the `shop` header is not part of the signed material. The equality the code needs — "the shop I am about to act on == the shop that authorized/produced this exact body" — is broken.

### Impact Explanation
This breaks the tenant boundary the whole webhook mechanism exists to enforce, matching "cross-tenant access" in the Critical impact category. Any application built on this gem that dispatches business logic keyed off `WebhookMetadata#shop` (e.g., updating a merchant's local record, revoking access on `app/uninstalled`, processing GDPR `customers/data_request`/`shop/redact` compliance webhooks, or writing metafield/order data scoped by shop) can be made to act on a victim shop's tenant record using a body forged/triggered by the attacker's own store, purely by spoofing one unauthenticated header per request. No access token, `client_secret`, or privileged account is required — only that the attacker install the app on a shop they control, which is the normal unprivileged flow for any Shopify app.

### Likelihood Explanation
High. The attack requires no secret material: the attacker legitimately receives a Shopify-signed webhook by installing the app on their own store (dev stores are free and unprivileged), captures the raw body and `hmac-sha256`/`x-shopify-hmac-sha256` header, and re-sends it to the app's public webhook endpoint with only the `shop-domain` header modified. Compliance/mandatory webhook topics (`customers/data_request`, `customers/redact`, `shop/redact`) are especially attractive since their body content is largely fixed and predictable, making it trivial to reuse.

### Recommendation
Bind `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the value that is HMAC-verified, or independently verify that the shop asserted by the header matches an active, expected installation for that specific webhook delivery (e.g., cross-check against the session/shop record the app is currently expecting a callback for) before trusting `WebhookMetadata#shop`. At minimum, `Webhooks::Request#to_signable_string` should not allow the `shop` identity used downstream to be decoupled from what Shopify actually authenticated for that specific signed body.

### Proof of Concept
1. Attacker creates their own (free) development store `attacker-shop.myshopify.com` and installs the target app, registering for a webhook topic (e.g., `customers/data_request`).
2. Shopify delivers a legitimate webhook to the app's callback URL:
   - Headers: `X-Shopify-Topic: customers/data_request`, `X-Shopify-Hmac-Sha256: <valid HMAC of body signed with app secret>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
   - Body: `{"shop_id": ..., "shop_domain": "attacker-shop.myshopify.com", ...}` (attacker fully controls timing/content of this by triggering the topic themselves where possible, or simply captures it).
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` parses this successfully (all three required headers present) [7](#0-6) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and finds it matches — validation passes [8](#0-7) .
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the signed body/webhook was never generated for that shop, and the app's business logic (e.g., data deletion, uninstall handling) executes against the victim tenant.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|

            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
