### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC only to the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed on to the app's webhook handler as the identity of the merchant the event belongs to.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to the `hmac` header using `OpenSSL.secure_compare`: [1](#0-0) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from the `shopify-*`/`x-shopify-*` HTTP headers, which are never part of the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only that the body was signed with the app secret at some point) and then unconditionally forwards the header-derived `request.shop` and `request.topic` to the handler as the trusted tenant/event identity: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-tenant), a party who legitimately controls one installed shop can obtain a validly-HMAC-signed request body/signature pair from a real Shopify webhook delivery to their own store, then re-send that same body+HMAC to the app's webhook endpoint while substituting a different `shop-domain` (and/or `topic`) header for a victim shop. `HmacValidator.validate` will still return `true` because the signature only covers the body, so `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop: [5](#0-4) 

This breaks the intended identity binding `hmac == HMAC(shop, topic, body)`; in reality only `hmac == HMAC(body)` holds, so `shop`/`topic` are acted upon (used to route data/updates into per-tenant storage) without being covered by the signature that is supposed to authenticate the request as coming from Shopify for that tenant.

### Impact Explanation
Any host application that uses `request.shop`/`request.topic` from `WebhookMetadata` as the tenant key to write/update local records (a very common pattern, e.g. "update order X for shop Y") can be made to apply attacker-supplied payloads under another merchant's identity, corrupting or exfiltrating data across tenant boundaries — a cross-tenant integrity/confidentiality issue. This satisfies the "Critical - cross-tenant access" impact category in principle, though the attack requires the attacker to already control (and have installed the app on) at least one real shop in order to harvest a validly-signed body/HMAC pair.

### Likelihood Explanation
Moderate-to-low: it requires the attacker to (1) install the target app on a shop they control, (2) intercept/capture a real webhook delivery from Shopify to obtain a body+HMAC pair, and (3) resend that exact request to the app's webhook endpoint with forged `shop-domain`/`topic` headers. All of this is possible without needing the app's `api_secret_key`, an access token, or any Shopify credentials beyond a free app install, which fits the "unprivileged internet user" model.

### Recommendation
Include `shop`, `topic`, and other routing-relevant headers in the signable payload used for HMAC verification (or, at minimum, have `Registry.process`/the consuming app cross-check the header-derived `shop` against the set of shops actually known/installed for this app before trusting it as the tenant identity), so that a validly-signed body cannot be replayed under a different shop or topic.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`).
2. Attacker captures the resulting HTTP POST that Shopify sends to the app's webhook endpoint, including headers `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and the raw JSON body.
3. Attacker resends the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only (`lib/shopify_api/webhooks/request.rb:35-38`) and it matches, so `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) proceeds to invoke the handler with `shop: "victim-shop.myshopify.com"`, `topic: "orders/create"`, and the attacker-controlled body — even though Shopify never sent this event for `victim-shop`.
