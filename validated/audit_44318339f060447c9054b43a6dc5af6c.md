The code confirms the claim exactly as described. The root cause is precisely in [4](#0-3) , confirming the described "unbounded suffix" flaw: it treats `*.` as "any string with this text as a suffix" rather than enforcing a subdomain (`.`-delimited) boundary.

Given the code matches the claim exactly, and the bypass is triggerable by an unprivileged client sending a normal HTTP request with a crafted `Origin` header (contingent on operator wildcard configuration, which is a normal supported usage pattern, not a misconfiguration outside intended use), this is a valid, in-scope CORS allowlist-bypass finding.

Audit Report

## Title
CORS wildcard-origin matcher allows subdomain-boundary bypass leading to allowlist bypass - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's user-facing HTTP server supports wildcard CORS entries like `https://*.example.com` in `CORSAllowedOrigins`. The matching logic in `isAllowedOrigin` strips the `*.` prefix and performs a raw `strings.HasSuffix` check against the browser-supplied `Origin` header without validating that a `.` label boundary exists between the attacker-controlled prefix and the allowed domain suffix, allowing domains like `evilremix.com` to match an allowlist entry of `*.remix.com`.

## Finding Description
In `isAllowedOrigin` (`core/services/gateway/network/httpserver.go:184-190`), the wildcard branch does:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
```
For an allowlist entry `*.remix.com`, `allowedHost` becomes `remix.com`. Any `originHost` that merely ends with the literal bytes `remix.com` — such as `evilremix.com` or `not-remix.com` — passes `strings.HasSuffix`, even though it is not a subdomain of `remix.com`. This function is invoked directly from `handleRequest` (`core/services/gateway/network/httpserver.go:195-202`) on every request when `CORSEnabled` is true, and if it returns true, the attacker-controlled `Origin` header is reflected verbatim into `Access-Control-Allow-Origin`. No other validation or boundary check exists in the code path before this reflection.

## Impact Explanation
An unprivileged attacker who registers or controls a domain that merely ends with the same characters as an allowed suffix can get their origin reflected in `Access-Control-Allow-Origin`, allowing a page hosted on the attacker's domain to make cross-origin browser requests to the Gateway's user-facing JSON-RPC endpoint and read responses. This is an allowlist-bypass class impact consistent with in-scope Chainlink Gateway impacts (allowlist bypass / cross-user response exposure).

## Likelihood Explanation
Exploitability requires only that an operator configure a wildcard CORS entry (`*.<domain>`), which is a documented, supported configuration option (`CORSAllowedOrigins`), not a misuse or misconfiguration outside intended design. Given that configuration, the attacker needs no privileged access or victim interaction — only registration of a suffix-colliding domain and a normal unauthenticated HTTP/OPTIONS request with a forged `Origin` header.

## Recommendation
Require a `.` boundary immediately before the matched suffix, e.g., compare against `"."+allowedHost` after stripping `*`, or use exact-length boundary checks so only true subdomains match:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".remix.com"
    if strings.HasSuffix(originHost, suffix) || originHost == suffix[1:] {
        return true
    }
}
```

## Proof of Concept
1. Configure the Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.remix.com"]`.
2. As an unauthenticated client, send a request/preflight to the Gateway user endpoint with header `Origin: https://evilremix.com`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilremix.com`, confirming `evilremix.com` (not a subdomain of `remix.com`) is incorrectly allowlisted. This can be implemented as a Go unit test directly calling `isAllowedOrigin("https://evilremix.com")` against a server configured with `CORSAllowedOrigins: []string{"https://*.remix.com"}` and asserting it returns `true`.
