### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the unauthenticated `X-Shopify-Shop-Domain` header, while the HMAC that `Registry.process` verifies only signs the raw request body. This breaks the identity binding: `hmac == HMAC(raw_body)` is verified, but `shop` (used to attribute the webhook to a specific merchant) is never part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cross-check against the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (i.e., only the body) and compares against `request.hmac`: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `request.shop` (the unauthenticated header value) is forwarded verbatim into `WebhookMetadata#shop`, which the host app's `WebhookHandler#handle` uses to attribute the payload to a merchant/tenant: [5](#0-4) 

The binding that should hold is: `shop_used_for_attribution == shop_bound_by_hmac`. In this code, the left side comes from the `X-Shopify-Shop-Domain` header while the right side is never computed — the HMAC signs only `raw_body`, so `shop` is entirely outside the signed scope. Any party capable of producing a byte-identical body with a valid signature (e.g., replaying a previously-captured, validly-signed webhook payload — such as a `shop/redact`, `customers/redact`, or `orders/create` webhook that the attacker's own store received) can resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. The HMAC still validates (body unchanged), but `request.shop` now reports the victim's domain to the handler.

### Impact Explanation
This falls under the "cross-tenant access" Critical impact category: an app built on this gem that uses `WebhookMetadata#shop` to key session/data lookups (the intended and documented use, per `docs/usage/webhooks.md`) can be made to process attacker-supplied webhook content under a victim shop's identity. Depending on the handler logic, this can cause cross-tenant data corruption (data intended for shop A is stored/acted upon as if it belongs to shop B) or trigger destructive mandatory webhook handlers (e.g., `shop/redact`, `customers/redact`) against a shop the attacker doesn't control, since the `shop` attribute is not authenticated.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one validly-signed webhook body (achievable trivially by owning/operating their own development store and registering webhooks to an endpoint they control, or intercepting their own shop's webhook traffic) and then replay that exact body with a forged `Shop-Domain` header to the target app's public webhook endpoint. No access to the app's `client_secret` is needed because the HMAC over the (unchanged) body remains valid; only the header, which is unauthenticated, is altered. This is a realistic, low-cost external attack against any consumer of this gem that trusts `WebhookMetadata#shop` for tenant identification, matching the described bug class exactly (a field acted on but not covered by the HMAC).

### Recommendation
Include the shop domain (and other identity-relevant headers such as topic/api-version) in the HMAC-signed payload, or otherwise cryptographically bind the header values to the verified signature before exposing them via `WebhookMetadata`. At minimum, document/enforce that `shop` must be independently verified (e.g., cross-checked against a known, previously-installed shop record) before being trusted for any tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets the app register a webhook (e.g., `customers/data_request`).
2. Shopify sends a legitimate webhook to the attacker's monitored endpoint (or attacker directly crafts a body and requests it be delivered) with:
   - `X-Shopify-Hmac-Sha256`: `HMAC-SHA256(raw_body, client_secret)` — valid for that exact `raw_body`.
   - `X-Shopify-Shop-Domain`: `attacker.myshopify.com`.
3. Attacker captures the exact `raw_body` and its `X-Shopify-Hmac-Sha256` value.
4. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — signature check passes because the body is unchanged.
6. `request.shop` returns `"victim-shop.myshopify.com"` (from the forged header) and is passed to the registered `WebhookHandler#handle` via `WebhookMetadata`, causing the app to process attacker-controlled content as if it originated from `victim-shop.myshopify.com`.
