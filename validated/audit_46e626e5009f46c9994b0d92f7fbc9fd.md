### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body, while `Registry.process` trusts `request.shop`, `request.topic`, and `request.webhook_id` — all taken from unauthenticated HTTP headers — to identify the tenant and dispatch the handler. Because the HMAC never binds these header values, any actor who can produce one valid `(raw_body, hmac)` pair for the app's secret (e.g., a legitimate merchant installing the same app on their own shop, who will receive genuine webhooks with a valid signature for their own traffic) can replay that same body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will still pass because it only checks the body bytes, not the header/shop binding.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are all read straight from headers and are not part of the signed content: [2](#0-1) 

`HmacValidator.validate_signature` verifies the HMAC solely against `to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC checks out, then unconditionally forwards `request.shop` (and `request.topic`, `request.webhook_id`) to the webhook handler as the authenticated tenant identity: [4](#0-3) 

The identity binding that should hold is:
`hmac(raw_body, secret) == hmac(shop, topic, webhook_id, raw_body, secret)`—i.e., the HMAC should cover the header fields that the handler treats as trusted tenant identity. Instead it only covers `raw_body`, so `shop`/`topic`/`webhook_id` are "a field acted on but not covered by the HMAC."

### Impact Explanation
An attacker who legitimately installs the app on their own shop will receive genuine, correctly-signed webhooks from Shopify for their own shop (a normal, unprivileged action — no `api_secret_key` needed). Because the signature never binds the `shop-domain`/`topic`/`webhook-id` headers, the attacker can resend the identical `(raw_body, hmac-sha256)` pair to the app's webhook endpoint while swapping in a victim shop's domain in `x-shopify-shop-domain` (and/or a different topic/webhook-id). `HmacValidator.validate` passes because the body bytes are unchanged, and `Registry.process` calls the handler with `shop: request.shop` pointing to the victim tenant. Any host logic that trusts the gem's `shop`/`topic` fields as authenticated tenant identity (this is the entire point of exposing them on `WebhookMetadata`) can be tricked into processing attacker-chosen body content under a victim shop's identity — a cross-tenant identity-binding break.

### Likelihood Explanation
Requires no privileged secret: any user who can install the target app on a shop they control will receive real signed webhooks and can then replay them with a forged shop header against the same endpoint. This is a low-effort, unprivileged-internet-user attack path entirely within this gem's own verification logic.

### Recommendation
Include the header fields that are treated as authenticated identity (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed content, or otherwise cryptographically bind them to the body before dispatching to handlers, so that `HmacValidator.validate` cannot pass for a body/HMAC pair whose header identity has been altered.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`. Shopify sends a genuine webhook with body `{}` and header `x-shopify-hmac-sha256` computed as `HMAC-SHA256(api_secret_key, "{}")`.
2. Attacker captures this `(raw_body="{}", hmac)` pair.
3. Attacker POSTs the same body and HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, "{}")` — this still matches, so validation passes: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", ...)`, causing the app to act on attacker-controlled data attributed to the victim tenant.
