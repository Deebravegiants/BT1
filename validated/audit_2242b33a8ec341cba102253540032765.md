### Title
Multisig timelock override threshold is not rescaled when new owners are added, allowing a shrinking minority of the original owners to bypass the timelock and immediately execute transactions - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
The `MultisigAccountTimeLock.override_threshold` field is meant to represent a supermajority (often "all current owners") whose approval lets a multisig transaction skip the timelock delay and execute immediately. `update_owner_schema` only ever *clamps `override_threshold` down* when owners are removed and the owner count shrinks below it; it never re-validates or raises `override_threshold` when owners are *added*. This lets the effective bypass quorum silently degrade from "unanimous"/high-threshold to a small minority of the (now larger) owner set, letting a subset of original owners execute multisig transactions — including ones that move multisig-held APT/assets, rotate the account's authentication key, or change further config — without waiting for the timelock that the other owners rely on to review/veto the transaction.

### Finding Description
`update_owner_schema` is the single choke point used by `add_owners`, `remove_owners`, `swap_owner(s)`, and `update_signatures_required` to mutate the owner set and signature threshold [1](#0-0) .

After applying owner additions/removals and any new `num_signatures_required`, the function performs a timelock-specific fixup:

```
if (exists<MultisigAccountTimeLock>(multisig_address)) {
    let timelock = &mut MultisigAccountTimeLock[multisig_address];
    if (timelock.override_threshold.is_some() && timelock.override_threshold.borrow() > &num_owners) {
        timelock.override_threshold = option::some(num_owners);
        emit(TimelockUpdated { ... });
    };
    assert!(
        timelock.override_threshold.is_none() || timelock.override_threshold.borrow() > &multisig_account_ref_mut.num_signatures_required,
        error::invalid_state(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
    );
};
``` [2](#0-1) 

This logic only handles the case where `override_threshold` *exceeds* the new (smaller) `num_owners` — it clamps it down and re-validates it is still `> num_signatures_required`. Confirmed by the unit tests: removing an owner clamps `override_threshold` from 3 to 2 [3](#0-2) , and if the clamp collapses `override_threshold` to equal `num_signatures_required`, the whole update aborts with `EINVALID_TIMELOCK_OVERRIDE_THRESHOLD` [4](#0-3) .

However, when `add_owners` (or `swap_owners_and_update_signatures_required`, `add_owners_and_update_signatures_required`, etc.) *increases* `num_owners`, there is no corresponding step that scales `override_threshold` up to preserve its intended proportion of the owner set. `override_threshold` is only ever compared against `num_signatures_required` (`> num_signatures_required`) and against the *new, larger* `num_owners` only as an upper clamp, never as a lower bound to re-validate proportionality. Concretely:

- Owners = {A, B}, `num_signatures_required = 1`, `override_threshold = 2` (i.e., both owners must approve to bypass the timelock — full unanimity).
- Owner A (using the normal 1-of-2 threshold) calls `add_owners` to add owners C, D, E. `num_owners` becomes 5. `override_threshold` remains `2` because the clamp only fires when `override_threshold > num_owners`, which is false (2 < 5), so no adjustment or re-validation is triggered.
- Now the override quorum, which was designed to require unanimous (2-of-2) sign-off to skip the timelock, requires only 2-of-5 owners — a minority — to immediately execute any multisig transaction, bypassing the very delay that the timelock exists to give other owners time to detect/veto malicious transactions.
- A and B (or any 2 signers who reach `override_threshold`) can now propose and immediately execute a transaction (e.g., transferring the multisig account's APT/fungible-asset holdings, rotating its auth key via `account::rotate_authentication_key`, or draining a resource-account signer capability it holds) without the timelock delay that C, D, and E were relying on to intervene.

This breaks the custody invariant that the timelock's override/bypass authority must scale with (or be re-validated against) the actual owner set, so that "supermajority override" cannot silently degrade into "minority override" as the owner set grows.

### Impact Explanation
`override_threshold` gates whether a multisig transaction can execute *immediately*, bypassing the timelock delay [5](#0-4) . Multisig accounts on Aptos routinely hold APT and other fungible assets, and can hold `SignerCapability`/resource-account control. If the override threshold silently degrades relative to the owner set, a minority coalition of original owners can execute (and thus authorize transfer, mint/burn via owned refs, or auth-key rotation of) multisig-controlled funds without the delay the remaining owners depend on for oversight — effectively an unauthorized reassignment/takeover of custody authority over the multisig-held value. This is a high-severity custody control weakening: it doesn't require any malicious code path, only a normal `add_owners` operation performed under the existing (lower) `num_signatures_required`.

### Likelihood Explanation
`add_owners` is a routine, expected operation for any actively-managed multisig (onboarding new signers) and requires no special privilege beyond the multisig's own normal transaction threshold, which is typically far lower than `override_threshold`. Any multisig owner group that ever configured a strict/near-unanimous `override_threshold` for its timelock and later grows its owner set will hit this silently, with no error, warning, or forced re-configuration — making it a latent, high-likelihood condition once timelock + owner-growth are combined.

### Recommendation
When `num_owners` increases via `update_owner_schema` (i.e., `new_owners.length() > 0`), the function should also validate/rescale `MultisigAccountTimeLock.override_threshold` to preserve its intended relationship to the owner set (e.g., re-require an explicit multisig transaction to raise `override_threshold` proportionally, or store the override as a percentage of owners rather than an absolute count, or force `override_threshold` to be re-approved whenever `num_owners` changes in either direction). At minimum, adding owners should trigger the same validation path currently only triggered on removal, so the invariant "`override_threshold` reflects the configured supermajority of the *current* owner set" always holds.

### Proof of Concept
1. Create a multisig account with owners `{A, B}`, `num_signatures_required = 1`.
2. Call `upsert_timelock` to configure `override_threshold = option::some(2)` (full unanimity required to bypass timelock) — mirrors the pattern shown in `setup_timelock_multisig`/`upsert_timelock` usage in the test suite [6](#0-5) .
3. Owner A creates a transaction to `add_owners([C, D, E])` and it executes under the existing 1-of-2 threshold. `num_owners` becomes 5; `update_owner_schema`'s timelock block does not fire because `override_threshold (2) > num_owners (5)` is false [7](#0-6) .
4. `override_threshold` remains `2`. A and B (2 of the now 5 owners) create and approve a malicious transaction (e.g., transferring the multisig's APT balance to an external address) and immediately execute it, bypassing the timelock delay that C, D, and E rely on for review — despite representing only 40% of current owners instead of the originally-intended 100%.

Note: Due to index size limits, I was not able to view the full struct definition of `MultisigAccountTimeLock` or the complete bodies of `upsert_timelock`/`can_be_executed`/`can_be_rejected`; the analysis above is based on the `update_owner_schema` logic and the corresponding unit tests, which consistently confirm the clamp-only-on-decrease behavior. A Devin session with full repository access is recommended to confirm the exact `can_be_executed` gating logic and produce a runnable end-to-end PoC.

    fun update_owner_schema(
        multisig_address: address,
        new_owners: vector<address>,
        owners_to_remove: vector<address>,
        optional_new_num_signatures_required: Option<u64>,
    ) {
        assert_multisig_account_exists(multisig_address);
        let multisig_account_ref_mut =
            borrow_global_mut<MultisigAccount>(multisig_address);
        // Verify no overlap between new owners and owners to remove.
        new_owners.for_each_ref(|new_owner_ref| {
            assert!(
                !vector::contains(&owners_to_remove, new_owner_ref),

            )
        });
        // If new owners provided, try to add them and emit an event.
        if (new_owners.length() > 0) {
            multisig_account_ref_mut.owners.append(new_owners);
            validate_owners(
                &multisig_account_ref_mut.owners,
                multisig_address
            );
            emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
        };
