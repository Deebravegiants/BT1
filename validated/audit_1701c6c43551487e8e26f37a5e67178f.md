### Title
Webhook `shop`, `topic`, and `webhook_id` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body alone, while the tenant-identifying `shop`, `topic`, and `webhook_id` fields are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` verifies the HMAC and then unconditionally trusts these header-derived fields when constructing the `WebhookMetadata` passed to the host application's handler, breaking the intended binding between "bytes verified" and "bytes acted on."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from request headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Webhooks::Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)`, and then immediately forwards `request.shop`, `request.topic`, and `request.webhook_id` — none of which were covered by that HMAC check — to the app-supplied handler: [3](#0-2) 

`Utils::HmacValidator.validate` only confirms that `verifiable_query.to_signable_string` (i.e., the raw body) matches the supplied HMAC — it says nothing about the headers: [4](#0-3) 

**Broken binding (as an equality that fails to hold):**
`hmac_verified_bytes == raw_body` (true), but the handler is invoked with `tenant_shop = header["shopify-shop-domain"]`, where `tenant_shop` is not an input to `hmac_verified_bytes`. The gem's contract implicitly assumes `tenant_shop ⊆ hmac_verified_bytes`, but it is not.

### Impact Explanation
This is a cross-tenant access vector (Critical). Any unprivileged internet user can install the target app on their own (e.g. free/dev) Shopify store, trigger and capture one legitimate webhook delivery for their own shop (a valid `(raw_body, hmac)` pair signed server-side by Shopify with the app's `api_secret_key` — the attacker never needs to know the secret themselves, only to receive a delivery), and then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while altering only the unauthenticated `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header to name a victim shop. `HmacValidator.validate` will still pass because it only checks the raw body against the secret-derived HMAC, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop as the event source. Any host application that uses `data.shop` to select which merchant's data/session/store context to act on (a documented, expected use of `WebhookMetadata#shop`) can be tricked into processing attacker-controlled webhook content under another tenant's identity.

### Likelihood Explanation
Likelihood is realistic: no credentials, access tokens, or knowledge of `api_secret_key`/`client_secret` are required. The attacker only needs the ability to install the app on any shop they control (a normal, unprivileged action available to any developer/merchant) to obtain one genuine `(body, hmac)` sample, and standard HTTP tooling to replay the request with a modified header.

### Recommendation
Bind the tenant-identifying fields (`shop`, `topic`, `webhook_id`) into the HMAC-verified content, or otherwise cryptographically tie them to the signed payload before trusting them (e.g., include them in `to_signable_string`, or require the caller to independently confirm the shop via a separately authenticated channel such as the OAuth-established session for that specific shop) rather than deriving them solely from unauthenticated headers after only the body has been verified.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker-shop.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: headers (`shopify-topic`, `shopify-hmac-sha256`, `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-webhook-id`) and `raw_body`.
2. Confirm locally that `ShopifyAPI::Webhooks::Registry.process` accepts this request (valid HMAC over `raw_body`).
3. Resend the identical `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but replace `shopify-shop-domain` with `victim-shop.myshopify.com` (and optionally alter `shopify-webhook-id`/`shopify-topic` if the target topic handler differs).
4. `Utils::HmacValidator.validate(request)` still returns `true` because it only checks `raw_body` against the HMAC; `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process attacker-controlled content attributed to the victim tenant.
