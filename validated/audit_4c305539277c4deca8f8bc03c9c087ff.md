### Title
Duplicate-asset withdrawal batches cause PoA Bridge to misreport the wrong withdrawal's status/txHash - (File: packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts, packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`findMatchingWithdrawal` in both `waitForWithdrawalCompletion.ts` and `poa-bridge.ts` resolves a withdrawal's on-chain status by matching only on `assetId` via `Array.find()`, ignoring the `index` that `createWithdrawalIdentifier`/`createWithdrawalIdentifiers` assign to each entry of a `withdrawalParams` batch. When a batch contains two or more withdrawals of the same token (same `assetId`) to different destinations/amounts, every one of those withdrawals resolves to the *first* matching record returned by the PoA API, mirroring the "first appearance wins" flaw described in the external report (`CredibleAccountModule::claim` / `InvoiceManager::creditTokensToInvoice` matching only the first occurrence of a duplicated token).

### Finding Description
`createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107` assigns each withdrawal in a batch a per-route `index`, and each `WithdrawalIdentifier` carries that `index` plus the full `withdrawalParams` (including `assetId`, `amount`, `destinationAddress`). [1](#0-0) 

For the PoA bridge route, however, `describeWithdrawal` never uses that `index` to disambiguate; it calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which is a plain `.find()` keyed only on `assetId`: [2](#0-1) 

The same pattern exists in the internal-utils polling helper: [3](#0-2) 

Both call sites carry an explicit code comment acknowledging that "multiple withdrawals of the same token in a single transaction are not supported" by this matching strategy, but nothing in `createWithdrawalIdentifiers`, `enableSession`-equivalent flow, or the SDK's public `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` API prevents a caller from submitting a batch (`withdrawalParams: WithdrawalParams[]`) containing two entries with the same `assetId` but different `destinationAddress`/`amount`, e.g. sending the same NEP-141 token to two different recipients in one intent transaction. If the underlying PoA relay processes both transfers in the same NEAR transaction, the withdrawals API response contains two records with the same `near_token_id`; `.find()` always returns the first one, so **both** `WithdrawalIdentifier`s (index 0 and index 1) resolve to the same status/`txHash`, regardless of which physical withdrawal they actually represent.

This breaks the equality that "the status reported for withdrawal N corresponds to the on-chain outcome of withdrawal N." Instead, the second (or later) withdrawal in the batch inherits the first's `COMPLETED` status and `transfer_tx_hash`, exactly analogous to the report's "second lock/claim of a duplicated token can never be reached" — here, the second withdrawal's *real* completion is never independently observed; the SDK/consumer is told it already completed using someone else's proof.

### Impact Explanation
An integrator relying on `sdk.waitForWithdrawalCompletion` / `sdk.createWithdrawalCompletionPromises` to confirm off-chain that funds landed before crediting a user, releasing an escrow, or marking an order fulfilled could:
- Credit/settle withdrawal index 1 using the transaction hash and "completed" status that actually belongs to withdrawal index 0, before withdrawal index 1 has actually landed on-chain (or even if it silently fails).
- Conversely, once withdrawal index 0's completion record is consumed as "proof," any other same-asset withdrawal in the batch will report identical completion, enabling a double-credit workflow where an integrator marks two distinct withdrawals as fulfilled from one on-chain event.

This matches the “status or hash misreport making an integrator credit or refund twice” category, since two logically distinct withdrawals collapse onto one reported outcome.

### Likelihood Explanation
Requires a caller to construct a `withdrawalParams` array with duplicate `assetId` entries routed to the PoA bridge (same token withdrawn to multiple destinations within one intent transaction). This is a normal, permitted input shape — `WithdrawalParams[]` places no uniqueness constraint on `assetId`, and the SDK's batch-withdrawal design (see `docs/design/rfc-batch-withdrawal-granular-control.md`) explicitly supports independent per-index withdrawals in one call, so a legitimate multi-recipient payout of the same token is a plausible, unprivileged usage pattern rather than an edge case requiring malicious actors.

### Recommendation
Match PoA withdrawal status records using more than `assetId`: correlate by `amount` and `destinationAddress` (or an ordinal position after sorting both the API response and the requested `withdrawalParams` by amount, as suggested in the existing code comment) so that each `index`/`WithdrawalIdentifier` maps to a distinct on-chain withdrawal. At minimum, `findMatchingWithdrawal` should track and exclude already-matched withdrawals across calls within the same batch to avoid two different indices resolving to the same underlying record, and callers should be warned/blocked from submitting duplicate-`assetId` PoA withdrawals until this is fixed.

### Proof of Concept
1. Caller builds `withdrawalParams = [{ assetId: "nep141:usdc.near", amount: 100n, destinationAddress: A }, { assetId: "nep141:usdc.near", amount: 50n, destinationAddress: B }]` and submits via `sdk.waitForWithdrawalCompletion({ intentTx, withdrawalParams })`.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two entries, both routed to `PoaBridge`. [4](#0-3) 
3. The PoA relay executes both transfers under one NEAR tx hash; `getWithdrawalStatus` returns two `COMPLETED` records, both with `near_token_id: "usdc.near"` but different `transfer_tx_hash` values (`0xhashA`, `0xhashB`).
4. `describeWithdrawal` for **both** `index: 0` and `index: 1` calls `findMatchingWithdrawal(withdrawals, "nep141:usdc.near")`, which returns the same first record (`0xhashA`) for both, so the SDK reports `{status:"completed", txHash:"0xhashA"}` twice — the withdrawal to `B` is reported using `A`'s transaction proof. [5](#0-4)

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
