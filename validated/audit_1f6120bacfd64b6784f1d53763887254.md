Confirmed finding. This is a genuine identity-binding gap in this gem's own webhook verification code, not merely a host-app documentation issue.

### Title
Webhook `shop` (and `topic`/`webhook-id`) fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop`, `topic`, and `webhook_id` are read directly and unauthenticated from HTTP headers [2](#0-1) . `Registry.process` validates the HMAC over that signable string only, then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct the `WebhookMetadata` passed to the app's handler [3](#0-2) . `Utils::HmacValidator.validate` only signs/verifies `verifiable_query.to_signable_string`, never any header value [4](#0-3) .

### Finding Description
The binding that should hold is: `hmac == HMAC(secret, shop || topic || webhook_id || body)`, i.e., the authenticated shop/topic identity should be cryptographically bound to the signature. Instead the gem only enforces `hmac == HMAC(secret, body)` [1](#0-0) [5](#0-4) , leaving `shop-domain`, `topic`, and `webhook-id` headers completely outside the signed data.

Because the app's `client_secret` (used to sign webhooks) is shared across *all* shops that install the app, and not shop-specific, any unprivileged user can install the app on their own store and receive legitimately-signed webhook deliveries (valid HMAC over a given body) addressed to their own shop domain. That attacker fully controls the public webhook endpoint's HTTP interface (it's the merchant app's own internet-facing route, documented as a plain Rails controller in `docs/usage/webhooks.md` lines 125-136) and can resend the exact same raw body with the same valid HMAC, but with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header rewritten to a victim shop. `HmacValidator.validate` still returns `true` because the body is unchanged, and `Registry.process` will happily dispatch the handler with `shop` set to the victim's domain [6](#0-5) .

This is not a case of "the host app ignoring documented API" — the gem's own `process`/`validate` methods are the complete, documented mechanism for authenticating a webhook's origin (see `docs/usage/webhooks.md` lines 123-136, which states `process` "will verify the request did indeed come from Shopify"), and that mechanism itself never authenticates the shop/topic identity it hands to the handler.

### Impact Explanation
Any app handler that keys behavior on `data.shop` (session/token lookup, tenant-scoped data writes, GDPR/mandatory topic handling, webhook idempotency records, etc.) can be made to act on attacker-supplied data while believing it originated from an arbitrary victim shop — a cross-tenant identity confusion driven entirely by this gem's verification gap.

### Likelihood Explanation
Requires only an unprivileged attacker capable of installing the app on their own (free) development/trial store to obtain a validly-HMAC'd payload, then replaying it to the app's public webhook endpoint with a modified `shop-domain` header — no `api_secret_key`, stolen credentials, or privileged account needed.

### Recommendation
Bind the identity fields into the signed payload used for verification (e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or independently verify `shop` against Shopify's registered webhook metadata/subscription id before dispatch), so `HmacValidator.validate` cannot pass for a body whose header-derived identity has been altered.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`; app registers `orders/create` webhook.
2. Attacker creates an order in their own store; Shopify POSTs to the app's webhook endpoint with body `B`, `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this request (it hits their own publicly reachable endpoint) and resends identical body `B` and HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (per `to_signable_string`) — matches, returns `true` [1](#0-0) .
5. `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` and attacker-controlled body `B` [7](#0-6) .
