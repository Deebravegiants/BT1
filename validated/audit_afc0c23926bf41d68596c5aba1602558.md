### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) are not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never part of the signed content [2](#0-1) . `Utils::HmacValidator.validate` only authenticates `to_signable_string` (the body) against the app's `client_secret` [3](#0-2) . `Registry.process` accepts any request that passes this body-only check and then trusts `request.shop`, `request.topic`, and `request.webhook_id` from headers to build the `WebhookMetadata` handed to the app's handler [4](#0-3) .

### Finding Description
The identity-binding equality this breaks is: `bytes_verified_by_hmac == bytes_the_handler_acts_on`. In this code, `bytes_verified_by_hmac = raw_body` only, but `bytes_the_handler_acts_on` additionally includes the `shop-domain`, `topic`, and `webhook-id` headers, none of which flow through `to_signable_string`.

Because all shops installing the same app share the same `client_secret`, any merchant who has legitimately installed the app (an "unprivileged internet user" with respect to *other* tenants of the app) will receive real webhook deliveries with a valid `(body, hmac)` pair computed with that shared secret. Nothing in `HmacValidator.validate` or `Request#initialize` binds that pair to the `shop-domain` header it originally arrived with [5](#0-4) . That attacker can therefore resend the exact same body+HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value (any other tenant's shop) and/or a different `topic`/`webhook-id`. `HmacValidator.validate` still succeeds because it never inspects the headers, and `Registry.process` dispatches the forged event to the handler tagged with the attacker-chosen `shop` [4](#0-3) .

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` to select/write per-tenant state (e.g., updating an order or subscription record keyed by shop domain) can be made to write or act on data attributed to a shop the attacker does not control, purely from the identity of `shop` never being bound to the signature. This is a cross-tenant access primitive: one tenant of a multi-tenant app can inject events that other tenants' data pipelines will process as authentic, without needing the victim's access token or credentials.

### Likelihood Explanation
Exploitation only requires: (1) being an installed merchant of the target app (any attacker can install their own copy of a public app), and (2) network access to the app's public webhook endpoint, which by design is internet-reachable. No secrets, tokens, or privileged access are required beyond what any ordinary merchant already has, and the gem performs no additional binding of the header-derived `shop`/`topic` to the HMAC-verified bytes.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the value that is HMAC-verified, or otherwise cryptographically bind the header values that the handler consumes to the signed payload, so that `HmacValidator.validate` fails whenever any header used downstream for tenant identification has been altered from what was originally signed by Shopify.

### Proof of Concept
1. App merchant A installs the target app and receives a legitimate webhook: raw body `B`, header `x-shopify-shop-domain: shop-a.myshopify.com`, and `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Merchant A resends the identical `B` and `HMAC(secret, B)` to the app's public webhook endpoint but replaces the header with `x-shopify-shop-domain: shop-b.myshopify.com` (a victim tenant).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [5](#0-4) ; `HmacValidator.validate` succeeds because only `B` is checked [6](#0-5) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)` [4](#0-3) , causing the app to process the forged event as if it came from `shop-b`.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
