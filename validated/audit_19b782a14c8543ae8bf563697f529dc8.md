### Title
Unchecked ERC-20 boolean return value in `IntentGatewayV2.withdraw()` and `SweepDust` handling allows silent transfer failures that permanently freeze escrowed funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` inconsistently uses raw, low-level `.call()` invocations of `IERC20.transfer` and only checks the outer `success` boolean returned by `.call()`, instead of decoding and validating the ERC-20 return value as `SafeERC20.safeTransfer` does. Any ERC-20 token that returns `false` on a failed transfer (without reverting) will pass this check silently, while the contract's internal escrow accounting is still decremented and the order marked as filled/refunded — even though the beneficiary never received the tokens.

### Finding Description

and the fee payout uses the same pattern: [3](#0-2) 

The `SweepDust` handling branch of `onAccept` has the identical pattern: [4](#0-3) 

In all three cases, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` only confirms that the call did not revert (`success == true`). It never inspects `returndata` to confirm the token itself signaled success. Standard-compliant tokens that return `false` on failure instead of reverting (e.g., legacy tokens, or any token contract that intentionally returns `false` for certain guarded conditions) will cause `success` to remain `true` while no tokens are actually moved. Since `_orders[body.commitment][token] -= amount;` executes unconditionally after the call in `withdraw()`, and `_filled[body.commitment] = beneficiary;` is set at the top of the function regardless of transfer outcome, the escrow is marked settled/filled with the funds effectively lost — they cannot be re-claimed because the order commitment has already been consumed.

This is directly analogous to the reported bug class ("Silent Fails Ignored for Transfers of Funds via `transfer()` and `transferFrom()`"): return values of ERC-20 transfers are not validated per spec, allowing transfers to silently fail while the protocol proceeds as if they succeeded.

### Impact Explanation
`withdraw()` is reachable by any relayer who delivers a legitimate cross-chain `RedeemEscrow`/`RefundEscrow` POST request through the standard ISMP dispatch/delivery path (`onAccept` -> `authenticate` -> `withdraw`) [5](#0-4) . If the escrowed/fee token silently returns `false` on transfer (rather than reverting), the beneficiary's funds are neither delivered nor recoverable, and the order/commitment is marked filled or refunded (`_filled[body.commitment] = beneficiary`) so the user cannot retry. This results in permanent freezing/loss of escrowed intent funds, a direct violation of the intents-escrow value guarantee.

### Likelihood Explanation
Likelihood depends on which ERC-20 tokens are whitelisted/used as intent settlement assets on the Tron deployment. Since `IntentGatewayV2` is designed to be generic across arbitrary tokens specified in `Order.inputs`/`WithdrawalRequest.tokens`, and Tron/TRC-20 tokens in particular are known to have non-standard implementations that commonly return `false` rather than reverting, the likelihood of this path being triggered on a real deployment is not negligible, and it requires no privileged action — only a normal relayed settlement message for an order that happens to involve such a token.

### Recommendation
Replace all three raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept` with `SafeERC20.safeTransfer`, consistent with the `safeTransferFrom` usage already present elsewhere in the same file, so that any transfer which does not both succeed and (when return data is present) decode to `true` reverts the whole operation instead of silently succeeding.

### Proof of Concept
1. Configure/whitelist a TRC-20/ERC-20 token whose `transfer()` implementation returns `false` on failure instead of reverting (common on Tron and with several real-world token implementations).
2. A user creates an order that escrows this token via `IntentGatewayV2` (using the safe `safeTransferFrom` inbound path).
3. Hyperbridge dispatches a `RedeemEscrow`/`RefundEscrow` request that a relayer delivers to `onAccept`, invoking `withdraw()`.
4. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call itself doesn't revert) but the token's internal logic returns `false` (e.g., due to a blacklist, pause, or other guard condition) — the low-level `call` never decodes this `false` value.
5. `withdraw()` proceeds to decrement `_orders[body.commitment][token] -= amount` and sets `_filled[body.commitment] = beneficiary`, marking the order permanently settled while the beneficiary received zero tokens, resulting in a silent, permanent loss of the escrowed funds.
