### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives its `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but `Utils::HmacValidator.validate` only verifies the `hmac-sha256` signature against the raw request body (`to_signable_string` returns `@raw_body` only). `Registry.process` trusts these header-derived fields to route the webhook and to build the `WebhookMetadata` passed to the host app's handler, meaning the tenant (`shop`) and event (`topic`) identifiers used by the app are never covered by the cryptographic signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers, which are not part of the signed payload: [2](#0-1) 

`Registry.process` validates only that HMAC-over-body check, then immediately uses `request.topic` for handler dispatch and `request.shop`, `request.api_version`, `request.webhook_id` to build the `WebhookMetadata` delivered to the app's `handler.handle`: [3](#0-2) 

`WebhookMetadata` is a plain struct with no further verification of `shop`: [4](#0-3) 

The binding this breaks (as an equality): "the shop/topic that the app attributes to the webhook data" **should equal** "the shop/topic that the HMAC was actually computed over," but the code only enforces "HMAC == HMAC(raw_body)" while `shop`/`topic`/`webhook_id`/`api_version` are read from unsigned headers. Since the HMAC secret (`Context.api_secret_key` / `client_secret`) is a single per-app secret shared across every shop that installs the app (not a per-shop key), any entity that can obtain one validly-signed `(body, hmac)` pair for a topic — e.g., an attacker who has installed the app on their own Shopify store and triggers an event there — can resend that exact body+HMAC to the app's webhook endpoint while swapping the `shop-domain` (and/or `topic`/`webhook_id`) header. `HmacValidator.validate` still passes because it never inspects those headers, and `Registry.process` will hand the app's handler a `WebhookMetadata` claiming the body belongs to a different shop/topic than the one that actually produced it.

### Impact Explanation
This crosses the tenant boundary the library is supposed to enforce: an unprivileged attacker who legitimately installs the app on their own store (a normal, unprivileged action) can forge webhook deliveries that the app's handler will process as belonging to a different (victim) shop or topic, since the shop/topic association is not cryptographically bound to the verified body. Any host app that uses `WebhookMetadata#shop` to key data updates, cache invalidation, GDPR/redaction actions, or billing/entitlement logic (a documented, expected use of this field) can be made to apply attacker-controlled webhook content under another tenant's identity — i.e., cross-tenant data injection/spoofing through this gem's own webhook verification API.

### Likelihood Explanation
Requires the attacker to install the app on a store they control (a normal unprivileged action, not privileged access to the app's secret) and to be able to reach the app's public webhook endpoint with a replayed/modified request — both are within reach of an ordinary unprivileged internet user interacting with a multi-tenant Shopify app. No access to `client_secret`, tokens, or TLS interception is required.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable content, or otherwise cryptographically bind `shop`/`topic` to the verified body (e.g., mixing them into `to_signable_string`) so that `Utils::HmacValidator.validate` cannot pass for a request whose header-derived identity fields were substituted after the original signature was generated. At minimum, document that `WebhookMetadata#shop`/`#topic` are unauthenticated and must be cross-checked by the host app against its own known-installed-shops list before use.

### Proof of Concept
1. Attacker installs the target multi-tenant app on their own store `attacker.myshopify.com` and triggers webhook topic `X` (e.g., `orders/create`) with attacker-controlled order content.
2. Shopify sends the app a webhook with raw body `B` and header `x-shopify-hmac-sha256 = HMAC_SHA256(client_secret, B)` (the same `client_secret` is used for every shop of this app), plus `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this request and resends it to the app's webhook endpoint, replacing only `x-shopify-shop-domain` with `victim.myshopify.com` (and/or a different `x-shopify-topic`), keeping body `B` and the HMAC header unchanged.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(client_secret, B)` and matches the unchanged header — validation passes.
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, so the app processes attacker-controlled data as if it came from the victim shop. [3](#0-2) [5](#0-4)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
