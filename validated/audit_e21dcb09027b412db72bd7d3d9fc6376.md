### Title
Hardware wallet signing/address operations select any connected device matching the manufacturer, without verifying it matches the specific `walletAccount.id` - (File: features/hardware-wallets/src/module/hardware-wallets.ts)

### Summary
`HardwareWallets#getSelectedDevice` filters connected hardware wallet descriptors only by manufacturer (`ledger`/`trezor`), then unconditionally selects `descriptors[0]`. It never checks that the connected device's actual identity matches `walletAccount.id`, the value that was captured at account creation time via `device.getWalletId()`. This mirrors the Migration.sol root cause: a user-supplied identifier (`walletAccount`, analogous to `proposalId`) is used to route a sensitive operation (signing, address derivation, public key retrieval) without cross-checking it against the concrete resource (the connected device, analogous to `vault`) that is actually operated on.

### Finding Description
`#getSelectedDevice` is defined at [1](#0-0) . It narrows the candidate descriptor list only by `manufacturer` (derived from `walletAccount.source`), then always returns `descriptors[0]`:
```
if (descriptors[0]) {
  return { device: await descriptors[0].get() }
}
```
No comparison is ever made against `walletAccount.id`, even though that `id` is the unique fingerprint captured from the device during `sync`/`create` (`walletId = await device.getWalletId?.()`), stored on the `WalletAccount`, and used to key the account per-device: [2](#0-1)  and [3](#0-2) .

`#getSelectedDevice(walletAccount)` is called from `signTransaction`/`signMessage` via `#signGeneric` ( [4](#0-3) ), from `retrySigningRequest`/`cancelSigningRequest` ( [5](#0-4) ), and from address/public-key/asset-access helpers such as `canAccessAsset`, `listUseableAssetNames`, `getAddress`, `setPassphraseMode` ( [6](#0-5) ). In every one of these call sites, `walletAccount` (containing `.id`) is passed in specifically to select "the" device for that account, but the actual selection logic silently discards `.id` and picks whichever same-manufacturer device happens to be `descriptors[0]`.

### Impact Explanation
If a user has more than one hardware wallet of the same manufacturer connected at once (e.g., two Ledger devices, a scenario explicitly plausible for hardware-wallet users managing multiple physical keys), any operation intended for `walletAccount` A (created from device A, `id = walletIdA`) can be silently executed against device B instead:
- `signTransaction`/`signMessage` may request a signature from the wrong physical device/key, producing an address/signature under a different device's key than the one the user believes they are authorizing, or triggering approval prompts on the wrong device that the user did not intend to use for that account.
- `getAddress`, `getUnusedAddressIndexes`-driven flows, and XPUB/public-key sync could derive and display an address that does not correspond to the account the user selected, misleading the user about which device secures funds shown/expected for `walletAccount`.
- `setPassphraseMode` calls `#requireTrezorDevice` on whatever device is selected, potentially toggling a hidden-wallet passphrase context on the wrong Trezor unit.

This is a direct account/resource-binding confusion analogous to the reported Migration bug: the code trusts the caller-supplied `walletAccount` object as sufficient routing information without validating it against the concrete connected resource, which can misroute signing/address operations across a user's own multiple devices, leading to receiving funds at, or signing with, an unintended device/key.

### Likelihood Explanation
Likelihood is limited to users who have multiple hardware wallets of the identical manufacturer connected simultaneously — this is a normal, unprivileged usage pattern for hardware wallet owners with more than one device (no malicious peer/operator required). It does not require any adversarial input; it is purely a logic/state confusion inside `#getSelectedDevice`. It also silently reduces to a strict "first device wins" behavior any time multiple same-manufacturer descriptors are present, without erroring, so the mismatch is not detectable by the caller.

### Recommendation
In `#getSelectedDevice`, when `walletAccount?.id` is present, filter `descriptors` down to the one whose underlying device identity (`device.getWalletId()`, matched against `walletAccount.id`) equals the expected id, and throw a clear error (e.g. a new `WrongDeviceError`/`NoDeviceFoundError`) if no matching descriptor is found, instead of defaulting to `descriptors[0]`. This mirrors the recommended Migration.sol fix of validating the caller-supplied identifier against the actual resource before performing the sensitive operation.

### Proof of Concept
1. Connect two Ledger devices, Device A and Device B, to the same host.
2. Create/sync `walletAccount` from Device A via `sync()`/`create()`; `walletAccount.id` is set to Device A's `walletId` per [7](#0-6) .
3. Physically make Device B the first entry returned by `ledgerDiscovery.list()` (e.g., by connection order or USB enumeration order).
4. Call `signTransaction({ baseAssetName, unsignedTx, walletAccount })`; internally `#signGeneric` → `retrySigningRequest` → `#getSelectedDevice(walletAccount)` filters only by `manufacturer === 'ledger'` and returns `descriptors[0]`, which resolves to Device B, not the Device A that `walletAccount.id` corresponds to.
5. The transaction is signed/approved using Device B's keys/context even though the caller explicitly requested signing for the `walletAccount` bound to Device A, demonstrating the id/device mismatch is never validated. [1](#0-0)

  #getSelectedDevice = async (
    walletAccount?: WalletAccount
  ): Promise<{
    device: HardwareWalletDevice
  }> => {
    let descriptors: HardwareWalletDescriptor[]
    const manufacturer = walletAccount?.source as HardwareWalletManufacturer | undefined

    if (manufacturer === 'ledger') {
      descriptors = await this.#listLedgerDevicesOrEmpty()
    } else if (manufacturer === 'trezor') {
      descriptors = await this.#listTrezorDevicesOrEmpty()
    } else {
      const [trezors, ledgers] = await Promise.all([
        this.#listTrezorDevicesOrEmpty(),
        this.#listLedgerDevicesOrEmpty(),
      ])
      descriptors = [...trezors, ...ledgers]
    }

    if (descriptors[0]) {
      return { device: await descriptors[0].get() }
    }

    throw new NoDeviceFoundError()
  }

  retrySigningRequest = async (id: string) => {
    const request = this.#signingRequest
    if (request?.id !== id) {
      this.#logger.warn(`No signing request found for id: ${id}`)
      return
    }

    if (this.#isRetrying) {
      this.#logger.debug(`Retry already in progress for id: ${id}, ignoring duplicate call`)
      return
    }

    this.#isRetrying = true

    try {
      this.#logger.debug(`Attempting to get selected device for signing request with id: ${id}`)
      const { device } = await this.#getSelectedDevice(request.walletAccount)
      this.#logger.debug(`Attempting to sign for signing request with id: ${id}`)
      const result = await request.sign({ device })
      await this.#deleteSigningRequest(id)
      request.resolve(result)
    } catch (error) {
      if (this.#signingRequest?.id !== id) {
        this.#logger.warn(`Signing request with id: ${id} was cancelled, not retrying`)
        return
      }

      const _error = error as Error

      if (['DisconnectedDevice', 'DisconnectedDeviceDuringOperation'].includes(_error.name)) {
        // When an application is opened on the device, it may disconnect
        // the USB / BLE connection because the firmware hands over control
        // to the application, this involves a USB / BLE reset to flush any
        // pending messages. In this case, we wait a little bit and retry the signing request.
        this.#logger.debug(
          `Device disconnected during signing request, likely due to app opening: ${id}`,
          _error
        )
        await delay(300)

        this.#isRetrying = false
        await this.retrySigningRequest(id) // Retry the signing request
        return
      }

      // Errors for which we won't retry
      if (_error.message.includes('timeout') || _error.name === 'UserRefusedError') {
        // User refused the action on the device
        await this.cancelSigningRequest(id, false)
        return
      }

      // Allow the user to retry the signing request
      await this.#updateSigningRequest({
        id,
        scenario: 'error',
        error: _error,
        baseAssetName: this.#signingRequest.baseAssetName,
      })
    } finally {
      this.#isRetrying = false
    }
  }

  cancelSigningRequest = async (id: string, fromUI: boolean) => {
    const request = this.#signingRequest
    this.#logger.debug(`Cancelling signing request for id: ${id}, fromUI: ${fromUI}`)
    if (request?.id !== id) {
      this.#logger.warn(`No signing request found for id: ${id}`)
      return
    }

    await this.#deleteSigningRequest(id)

    // Ensure we cancel the action on the device
    if (fromUI) {
      this.#logger.debug(`Cancelling signing request on device for id: ${id}`)
      try {
        const { device } = await this.#getSelectedDevice(request.walletAccount)
        await device.cancelAction()
        this.#logger.debug(`Succesfully cancelled signing request on device for id: ${id}`)
      } catch (error: any) {
        this.#logger.error(`Failed to cancel signing request on device for id: ${id}`, error)
      }
    }

    // Now reject the promise returned to the asset caller
    request.reject(new UserRefusedError(!fromUI))
  }

  sync = async ({ accountIndex: index, isMultisig }: SyncParams = {}): Promise<SyncedKeysId> => {
    const keysToSync: KeyToSyncData[] = []

    // Retrieve the public keys from the device to our wallet
    const { device } = await this.#getSelectedDevice()
    const source = device.descriptor.manufacturer
    const accountIndex = index ?? this.#walletAccounts.getNextIndex({ source })
    // Compute the walletId fingerprint in the currently selected session context.
    // The caller is responsible for putting the device in the desired context
    // (standard/hidden) prior to calling sync (e.g. via setPassphraseMode()).
    // Fallback to randomly generated id, since Ledger doesn't support this..
    const walletId = (await device.getWalletId?.()) ?? randomBytes(32).toString('hex')

    const useableAssetNames = new Set(await device.listUseableAssetNames())
    for (const assetName of useableAssetNames) {
      const asset = this.#assetsModule.getAsset(assetName)
      if (!asset) {
        this.#logger.warn(`asset with ${assetName} was not found`)
        continue
      }

      const baseAsset = asset.baseAsset
      const supportedPurposes = baseAsset.api.getSupportedPurposes?.({
        compatibilityMode: source,
        isMultisig,
      }) ?? [44]
      for (const purpose of supportedPurposes) {
        const {
          keyIdentifier,
          xpub,
          publicKey,
        }: Partial<GetXPUBResult> & Partial<GetPublicKeyResult> =
          (await this.#getXPUB({ device, baseAsset, purpose, accountIndex })) ||
          (await this.#getPublicKey({ device, baseAsset, purpose, accountIndex }))

        keysToSync.push([keyIdentifier, { xpub, publicKey }] as KeyToSyncData)
      }
    }

    // Generate a random id and map it to the public keys
    // this prevents a bunch of serialization issues.
    const id = randomBytes(16).toString('hex')
    this.#syncedKeysMap.set(id, {
      accountIndex,
      model: device.descriptor.model,
      assetNames: useableAssetNames,
      keysToSync,
      walletId,
    })

    return id
  }
