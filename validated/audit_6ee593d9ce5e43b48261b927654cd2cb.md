### Title
PoA Bridge withdrawal status matches only by `assetId`, causing wrong-withdrawal status/hash misreport in batch withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` resolves withdrawal completion status by looking up the POA bridge indexer response and matching it to the requested withdrawal using `findMatchingWithdrawal`, which only compares `assetId` (`nep141:${w.data.near_token_id}`). It does not verify the destination address, amount, or per-withdrawal index/nonce that was actually supplied by the caller for that specific withdrawal.

### Finding Description
In a batch withdrawal (`sdk.processWithdrawal`/`waitForWithdrawalCompletion` with an array of `WithdrawalParams`), each withdrawal item gets its own `WithdrawalIdentifier` with an `index` [1](#0-0) . When polling status, `describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which performs `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` and returns the **first** match — ignoring `index`, `destinationAddress`, and `amount` entirely [2](#0-1) .

If a batch contains two or more withdrawals of the same token (same `assetId`) — e.g., withdrawing the same asset to two different destination addresses/amounts in one batch — every one of those withdrawal identifiers will resolve to the *same* first-matching bridge-side withdrawal record, and thus the *same* `status` and `txHash`, regardless of which specific withdrawal it actually corresponds to on-chain. The code comment even acknowledges this: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." [2](#0-1) 

This breaks the equality that "a status/hash reported to the integrator equals the actual on-chain outcome for *that specific* withdrawal." Instead, a status/txHash that belongs to one withdrawal (destination A) can be reported for a different withdrawal (destination B) in the same batch.

### Impact Explanation
An integrator using `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`/`processWithdrawal` with batched same-asset withdrawals could:
- Receive the same `completed` status + `txHash` for two distinct withdrawals, one of which may still be pending or failed on-chain, leading the integrator to credit/mark-complete a withdrawal that never actually landed at its destination address.
- Conversely, cause a withdrawal that did complete to be reported against the wrong logical withdrawal record, confusing reconciliation and refund/credit logic downstream.

This matches the "High" impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no malicious actor — it is triggered by ordinary usage: an integrator or user batching two withdrawals of the same token (e.g., same asset to two recipients) via `sdk.processWithdrawal({ withdrawalParams: [...] })`. Batch withdrawals of identical assetId are not blocked or validated against anywhere in the reachable code (`sdk.ts`, `withdrawal-watcher.ts`, `poa-bridge.ts`), so the condition is realistically reachable in normal integrator flows, not just adversarial ones.

### Recommendation
`findMatchingWithdrawal` should disambiguate withdrawals within the same batch beyond `assetId` — e.g., by also matching `destinationAddress` and `amount` (or, if the POA API is enhanced, an explicit correlation id/index) — and should not return the same withdrawal record for two different `WithdrawalIdentifier`s in a batch. If exact disambiguation with the current API is impossible, the SDK should explicitly detect and reject (or clearly document as unsupported and throw) batches containing multiple withdrawals of the same `assetId` for the PoA bridge route, rather than silently returning duplicate/wrong status.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ { assetId: "nep141:btc.omft.near", amount: 100000n, destinationAddress: addrA, feeInclusive: false }, { assetId: "nep141:btc.omft.near", amount: 250000n, destinationAddress: addrB, feeInclusive: false } ] })`.
2. Both withdrawals get distinct `index` (0 and 1) via `createWithdrawalIdentifier` [1](#0-0) .
3. When the POA bridge API returns the withdrawal list for the NEAR tx (which may contain both records, possibly still unsorted/out of order), `describeWithdrawal` for **each** index calls `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which returns the very first entry in `response.withdrawals` matching that assetId for *both* index 0 and index 1 lookups [3](#0-2) .
4. Both withdrawal promises resolve with the identical `{status: "completed", txHash: ...}` even though only one of the two on-chain BTC transfers to `addrA`/`addrB` has actually completed — the integrator's polling logic (`watchWithdrawal`) reports both as done based on this misreport [4](#0-3) .

				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
