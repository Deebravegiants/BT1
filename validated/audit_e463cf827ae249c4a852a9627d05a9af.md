### Title
Permanent Freeze of Escrowed Curve-Raised LT and Tokens if `finalizeGraduation` Computes Zero LP Liquidity - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding`'s two-phase graduation drains all curve-raised LT and 250M reserve tokens into escrow inside the `Bonding` contract during phase 1 (`_enterGraduating`), and only releases/locks them during phase 2 (`finalizeGraduation`). If `finalizeGraduation`'s LP-seeding computes a zero-sized liquidity result, the mandatory call to `LPLock.recordLock` reverts, and because no state is mutated on a revert, the token is permanently stuck in `Lifecycle.Graduating` with its escrowed LT/tokens unrecoverable — there is no owner or emergency function to release them. This is the direct analog of the external report's escrow-with-no-recovery bug class.

### Finding Description
Phase 1, `_enterGraduating`, calls `_prepareGraduationLiquidity`, which immediately drains all curve-raised LT out of the `Pair` via `_s().router.graduate(tokenAddress, ltFromPair)` and burns the LP-excess tokens, caching `(tokensForLP, ltFromPair, lpBurned, unsoldBurned)` in `pendingGraduation[token]` and flipping `lifecycle` to `Graduating`: [1](#0-0) 

At this point the `ltFromPair` LT and `tokensForLP`/`lpBurned` tokens sit in `Bonding`'s balance, escrowed until phase 2 completes. Phase 2, `finalizeGraduation`, is permissionless and unconditionally calls `LPLock.recordLock(tokenAddress, lpPair, liquidity)` after seeding the LP: [2](#0-1) 

`LPLock.recordLock` reverts with `ZeroAmount()` if `amount == 0`: [3](#0-2) 

The protocol's own natspec on `_swapBudget` explicitly documents that a `liquidity == 0` result is a reachable code path under an "extreme hostile pre-seed" that exceeds the 1% rebalance-swap budget, causing `_routerDepositAndDispose` to skip `addLiquidity` when `remToken == 0` or `remLT == 0`, which propagates a zero `liquidity` back to `finalizeGraduation`: [4](#0-3) 

This comment describes the (now-mitigated) pre-fix behavior as `LPLock.recordLock(...)` "records a zero-sized lock," but the live `LPLock.recordLock` code actually **reverts** on a zero amount rather than silently recording one. That means any surviving code path — whether from an even more extreme pre-seed than the 1% cap defends against, or from independent rounding-to-zero inside `router.addLiquidity`'s `quote()`-based optimal split for very small `(tokensForLP, ltFromPair)` pairs, or inside `_seedDirectMint`'s `pair.mint()` (which subtracts V2's `MINIMUM_LIQUIDITY` and can floor to `0` for dust-sized graduations) — causes `finalizeGraduation` to revert instead of completing.

Because `finalizeGraduation` performs `LPLock.recordLock` as its last state-changing call with no `try/catch`, a revert here unwinds the entire transaction: `pendingGraduation[token]` is never cleared and `Lifecycle` never advances past `Graduating`. Every subsequent call to `finalizeGraduation` (by the keeper or by any rescuer) re-derives byte-identical cached values and hits the exact same revert deterministically — there is no way to retry with different parameters, no admin override, and `triggerGraduation` cannot re-fire (it requires `Lifecycle.Curve`, and the token is stuck in `Graduating`).

### Impact Explanation
The escrowed `ltFromPair` LT and `tokensForLP` tokens (already drained from the curve pair into `Bonding`'s balance in phase 1) become permanently frozen. Trading is also permanently frozen (`buy`/`sell` revert with `TokenIsGraduating` while in this lifecycle state), so LP holders/traders who bought into the curve lose access to their raised LT and the token can never reach a tradeable `Graduated` state. This matches "permanent freezing of trader, creator, or LP funds" — the escrow has no rescue path, exactly analogous to the `oft_adapter_fa.move` escrow that the external report flags as lacking a recovery mechanism for a stuck remote pathway.

### Likelihood Explanation
Low but non-zero, matching the "unlikely edge case, acknowledged design gap" character of the original report. The protocol has invested heavily in brick-resistance (99% swap budget cap, `min=1` addLiquidity guards, direct-mint fallbacks) specifically to avoid a zero-liquidity outcome, and the team's own comments show they are aware zero-liquidity is a real, reachable failure mode under sufficiently extreme pre-seed conditions or rounding at dust scale. The dedicated end-to-end hostile-pre-seed regression suite (`test/HostilePreSeed.t.sol`) that would have caught regressions here was explicitly removed per `AGENTS.md`, so this exact scenario is no longer covered by automated tests.

### Recommendation
Add an explicit guard/handling for `liquidity == 0` before calling `LPLock.recordLock` in `finalizeGraduation` — either widen the LP-seeding math so a zero result is provably impossible under all reserve shapes (re-derive and test the invariant given the current `LPLock.recordLock` semantics, since the existing comment no longer matches the code), or add a permissioned/timelocked emergency path (e.g., an owner-gated `rescueStuckGraduation` that can release `pendingGraduation` escrow back to a designated recipient) so a pathological pre-seed cannot permanently strand curve-raised funds.

### Proof of Concept
1. Attacker (or extreme market conditions) pre-seeds the HyperSwap pair with reserves so imbalanced that even after the 1% `_swapBudget` cap and rebalance swap, `_routerDepositAndDispose`'s `router.addLiquidity` call rounds one side of the deposit to `0` (or the graduation is dust-sized enough that `_seedDirectMint`'s `pair.mint` returns `0` after subtracting V2's `MINIMUM_LIQUIDITY`).
2. `_enterGraduating` has already run for a prior threshold-crossing buy, draining `ltFromPair` LT and setting `Lifecycle.Graduating`.
3. Any caller invokes `finalizeGraduation(tokenAddress)`; `_seedUniswapV2Direct` returns `liquidity == 0`; `LPLock($.lpLock).recordLock(tokenAddress, lpPair, 0)` reverts with `ZeroAmount()`.
4. The transaction reverts entirely — `pendingGraduation[tokenAddress]` and `Lifecycle.Graduating` remain unchanged.
5. Every future call to `finalizeGraduation(tokenAddress)` deterministically repeats step 3, permanently freezing the escrowed LT/tokens and the token's trading state with no recovery function available in `Bonding.sol` or `LPLock.sol`.

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
