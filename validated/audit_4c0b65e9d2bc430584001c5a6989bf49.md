### Title
Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates *body integrity* but never authenticates the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers that `ShopifyAPI::Webhooks::Registry.process` subsequently trusts to route and attribute the event. Because Shopify webhook HMACs are computed with the app's single, shop-independent `api_secret_key`, any body+HMAC pair that is valid for one shop is valid for every shop the app serves. An unprivileged party who can obtain one genuine `(body, hmac)` pair (e.g. by installing the app on their own store) can resend it to the app's webhook endpoint with an arbitrary `shop-domain` (and `topic`) header and have it accepted as authentic.

### Finding Description
The binding that should hold is:
`hmac-covered bytes == bytes the handler uses to identify topic/shop`

but in this gem it is:
`hmac-covered bytes (raw body only) != bytes used for shop/topic attribution (unauthenticated headers)`

- `Request#hmac` reads the `hmac-sha256` header, and `Request#to_signable_string` returns just `@raw_body`: [1](#0-0) [2](#0-1) 

- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the received HMAC: [3](#0-2) 

- `Registry.process` accepts a request once `HmacValidator.validate` passes, and then dispatches using `request.shop` and `request.topic`, both taken straight from unauthenticated headers, with no cross-check against the verified body: [4](#0-3) 

Because Shopify signs webhooks with the app-level `api_secret_key` (not a per-shop secret), the same `(raw_body, hmac)` pair validates for any shop that has this app installed. An attacker who legitimately installs the app on their own store receives genuine webhooks with valid signatures. They can then replay that exact `raw_body`/`hmac-sha256` value against the app's webhook endpoint while substituting a victim's `shop-domain` (and optionally a different `topic`, since that header is also unauthenticated) — the gem will report the request as HMAC-valid and hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook signature is supposed to guarantee: the app's business logic (built on `WebhookMetadata#shop`/`#topic`) can be made to act on data attributed to a shop the attacker does not own, purely because the gem never binds those identifying fields to the signature. Depending on how the host app's handlers key off `shop`/`topic` (e.g. `app/uninstalled` cleanup, order/customer data ingestion, GDPR webhooks), this enables cross-tenant data confusion or triggering of shop-scoped side effects for a victim tenant — a cross-tenant access issue.

### Likelihood Explanation
Requires only an internet-reachable webhook endpoint and an attacker capable of installing the app once on a store they control (a normal, unprivileged action for any Shopify Partner/dev store), then replaying the captured request with a modified `shop-domain` header. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the identifying headers into the signed payload before validating: include `shop-domain`, `topic`, and `webhook-id` in `Request#to_signable_string` (or otherwise cryptographically bind them, e.g., by validating that `shop` matches a shop the caller is authorized to receive events for), so a valid HMAC for one shop's payload cannot be replayed with a different shop/topic attribution.

### Proof of Concept
1. Install the target app on an attacker-owned development store; Shopify sends a genuine webhook with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Attacker resends the same `B`/`H` to the app's webhook endpoint, replacing `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, B) == H` — still true — and proceeds to invoke the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: JSON.parse(B), ...)`, per: [5](#0-4)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
