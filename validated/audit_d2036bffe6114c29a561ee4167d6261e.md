### Title
Unfunded `recapitalize` pays out custody the cash book still claims — pool book/custody divergence freezes supplier funds - (File: contracts/pool/src/lib.rs)

### Summary
The vim modeline class — trusting an externally supplied value without validating that the claimed state actually exists — maps onto the pool's `recapitalize` entrypoint. The pool validates and commits a refund/recapitalization against its internal `cash` book without ever verifying that the tokens backing the operation were actually received, so a single unprivileged call can transfer out real custody while the accounting still reports the cash as present.

### Finding Description
The pool's `recapitalize` updates its hub-market books and executes an outbound token transfer to a `payer`/receiver address, but it performs no measured-receipt check: it never snapshots the pool's token balance before/after, never requires an inbound transfer to have settled, and never reconciles the payout against actual custody. The liquidity and solvency guards that protect exits — `require_liquidation_buffer`, `require_backed_market`, and `backing_shortfall` — all read the in-memory `Cache` cash book rather than the token balance, so after an unfunded recapitalize the book still asserts `cash >= deposit` even though the pool holds zero tokens (contracts/pool/src/guards.rs:19-66).

The committed regression test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` demonstrates exactly this: a supplier deposits `10_000_000_000`, the caller drains the entire custody via `recapitalize(&hub, &payer, &custody)` paying nothing in, and the book still reports `cash >= deposit` (contracts/pool/tests/flows.rs:3407-3439). The subsequent supplier `withdraw` then passes every pool guard (`require_reserves` reads the book and admits the exit) and only fails deep inside the SAC `transfer` with a raw `BalanceError(10)`, because there is no custody to pay (contracts/pool/tests/flows.rs:3441-3477).

### Impact Explanation
Permanent freezing of user funds and silent protocol insolvency. The attacker (or even an honest keeper) who triggers an unfunded recapitalize walks away with the drained custody, while every supplier's claim remains on the books. Withdrawals revert inside the token contract — not at a pool guard — so the market reports itself solvent yet cannot pay; suppliers' funds are unrecoverable since no book entry was ever debited and `recapitalize` mints no shares and writes down no index. This is exactly the accepted impact class "contract unable to operate from lack of token funds" / "permanent freezing of funds."

### Likelihood Explanation
`recapitalize` is an in-scope unprivileged entrypoint callable with an attacker-chosen `payer` and `amount`. No timing window, privileged role, leaked key, or oracle manipulation is required — the only precondition is a liquid market with cash to drain. The absence of a measured-receipt or funded-check in the recapitalize path makes the payout unconditional.

### Recommendation
Make `recapitalize` measured-receipt: snapshot `token::balance(pool)` before bookkeeping, require either a prior inbound transfer or a same-tx inbound payment equal to the recapitalized amount, or restructure so that recapitalize only *credits* cash that is verifiably present (e.g., pull the tokens via `transfer_from` inside the call, or gate payout on `balance_after - balance_before >= amount`). Additionally, reconcile `cash` against actual custody on exits, or have `require_reserves`/`backing_shortfall` compare the book against the real token balance so book/custody divergence fails loudly instead of stranding suppliers.

### Proof of Concept
The existing test is the PoC (contracts/pool/tests/flows.rs:3407-3483):

```rust
// contracts/pool/tests/flows.rs — condensed
let deposit = 10_000_000_000i128;
token_admin.mint(&t.pool, &deposit);                       // custody in
t.client().supply(&t.sup(0, deposit));                     // book = custody

let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &payer, &custody); // unfunded payout
assert_eq!(token.balance(&t.pool), 0);                     // custody gone
assert!(t.state_snapshot().cash >= deposit);               // book still claims it

// Supplier exit clears pool guards, then fails inside the SAC transfer:
// err == SAC BalanceError(10), NOT InsufficientLiquidity / PoolInsolvent.
let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
assert!(outcome.is_err());                                 // funds frozen forever
```

Root cause: `recapitalize` credits/debits the cash book without validating that corresponding token custody exists, and all downstream guards (`guards.rs:19-66`) trust the book — the same "unvalidated option value executes" shape as the modeline bug, transplanted from vim options to the pool's cash accounting.
