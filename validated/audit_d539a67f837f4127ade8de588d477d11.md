### Title
Truncating division in `convert_to_balance` silently discards dust on every inbound `HyperFungibleToken` transfer, permanently losing user funds - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` and `on_timeout` handlers convert an incoming ERC20 `uint256` amount to the pallet's local `Balance` type via `convert_to_balance`, which performs an integer division by `10^(erc_decimals - local_decimals)` and drops the remainder. When the EVM-side contract's decimals exceed the local asset's decimals (the documented, typical configuration), any amount that is not an exact multiple of the scaling factor has its remainder truncated and permanently lost — mirroring the reported `SolverVaults.sol` bug class where `amountInSolverVaultTokenDecimals` truncation strands collateral.

### Finding Description
`convert_to_balance` always divides, never rounds or tracks remainder: [1](#0-0) 

The typical deployment has `local_decimals` (e.g. 10 or 12, set via `T::Decimals`) smaller than the EVM contract's `erc_decimals` (typically 18, per the docs: `chains[].decimals` "typically 18 for EVM"): [2](#0-1) 

On the EVM side, `HyperFungibleToken.send()` burns the caller's *exact* `params.amount` with no rounding or minimum-granularity check: [3](#0-2) 

When the pallet's `on_accept` receives this message, it converts the amount down to local decimals using `convert_to_balance`, truncating any remainder below the scale factor before minting/releasing to the beneficiary: [4](#0-3) 

Because the EVM side already burned the *full* `params.amount` (exact), while the pallet only credits the *floor-divided* amount, the difference (up to `10^(erc_decimals - local_decimals) - 1` in ERC20-denominated units) is destroyed — it is neither minted to the beneficiary, nor kept in escrow, nor recoverable by any subsequent action. The same truncating conversion is used in `on_timeout` for refunds of pallet-originated sends, though that path recomputes the exact original scaled amount so it is not itself lossy; the lossy path is specifically inbound `on_accept` from the EVM side.

### Impact Explanation
This is a straightforward, permanent loss of user funds on every cross-chain transfer whose EVM-side amount is not an exact multiple of `10^(erc_decimals - local_decimals)`. Given `erc_decimals` is normally 18 and `local_decimals` is normally 10-12 (a scale factor of `10^6`-`10^8`), essentially any "natural" wei-denominated amount a user enters will contain nonzero low-order digits and lose value on every single transfer. Over the aggregate of transfers this creates an unaccounted-for and unrecoverable discrepancy between the EVM-side burned supply and the Substrate-side credited balance — permanent freezing/loss of funds, matching the required "Medium" bar.

### Likelihood Explanation
High likelihood: this is triggered by the default/unprivileged path of any user calling `HyperFungibleToken.send()` (or the counterpart Substrate `send` in the reverse direction with mismatched decimals) with an amount that isn't a round multiple of the decimals scale factor — no special conditions, privileges, or attacker cooperation required. It happens on ordinary usage.

### Recommendation
Do not silently discard the remainder in `convert_to_balance`. Either:
- Reject the transfer/message when `value % 10^(erc_decimals - local_decimals) != 0` (mirroring the reverted-if-not-representable pattern used elsewhere in this codebase, e.g. `BandwidthManager`'s `PriceNotRepresentable` check), or
- Track and refund/credit the truncated remainder to the beneficiary (e.g. via a small remainder-carry balance) so no value is destroyed, or
- Require callers to pre-round `amount` to the destination's precision before burning on the EVM side, and validate that on-chain before burning.

### Proof of Concept
1. Deploy `pallet-hyper-fungible-token` with `T::Decimals = 12` and register a token with `erc_decimals = 18` for an EVM chain (scale factor = `10^6`), per `register_token` docs.
2. A user calls `HyperFungibleToken.send()` on the EVM contract with `params.amount = 1_000_000_000_500_000` (i.e., not a multiple of `1e6`). The contract burns exactly this amount: [5](#0-4) 
3. The relayer delivers the POST request; the pallet's `on_accept` computes `amount = convert_to_balance(1_000_000_000_500_000, 18, 12)` = `1_000_000_000_500_000 / 10^6 = 1_000_000_000` (integer division), discarding the `500_000` remainder: [6](#0-5) 
4. The beneficiary is credited/minted `1_000_000_000` local units (equivalent to `1_000_000_000_000_000` in erc20 terms), permanently losing `500_000` erc20-denominated units that were burned on the EVM side but never credited anywhere on the Substrate side.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
