### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload solely from the raw request body via `to_signable_string`, while the `shop` (from header `x-shopify-shop-domain`), `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers that are never included in the signed bytes. `Registry.process` accepts any request whose body HMAC matches the app's secret and then unconditionally trusts these header values to route and identify the tenant for the webhook handler.

### Finding Description
The core identity binding this gem is supposed to enforce is: **bytes verified by HMAC == bytes used to identify the tenant/shop and topic**. Here that binding is broken:

- `hmac` is computed over `@raw_body` only [1](#0-0) .
- `shop`, `topic`, `webhook_id`, and `api_version` are parsed from headers, which are never fed into `to_signable_string` [2](#0-1) .
- `HmacValidator.validate` only checks `to_signable_string` against the HMAC, so it has no way to detect header tampering [3](#0-2) .
- `Registry.process` validates the HMAC, then immediately trusts `request.shop` and `request.topic` from those unverified headers to select a handler and build `WebhookMetadata` [4](#0-3) .

Because the app's `client_secret`/webhook signing secret is shared across every shop that installs the app, any tenant of a multi-tenant app can legitimately receive a genuinely-signed webhook for their own shop (with a body they can influence to some degree depending on topic, e.g., metafields/product update payloads containing attacker-controlled text) and then replay that exact body with only the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header rewritten to point at a victim shop. The HMAC still validates because it only covers the body, but the handler now believes the event originated from, and applies to, the victim's shop.

### Impact Explanation
This crosses a tenant boundary: an app relying on `request.shop` from `ShopifyAPI::Webhooks::Request` to scope data access, trigger per-shop side effects (e.g., disabling a shop, updating shop-scoped records, revoking access, syncing inventory) can be made to act on a victim shop's data/session while the payload was actually authored/triggered by a different, attacker-controlled shop. This matches "cross-tenant access" (Critical) since the app has no cryptographic assurance that the `shop` identity it acts on matches the entity that produced the signed bytes.

### Likelihood Explanation
Any unprivileged internet user can install the target app on their own shop (a normal, unprivileged action), giving them a stream of validly HMAC-signed webhook requests for their own tenant. They control the outbound HTTP request to the app's webhook endpoint (headers are just HTTP headers, easily rewritten) while the body's HMAC remains valid because the header is not part of the signed content. No access to `api_secret_key`, tokens, or any other credential is required beyond being an app installer.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, and ideally `webhook_id`, `api_version`) in the HMAC-signable bytes, or otherwise cryptographically bind them to the verified payload (e.g., verify the `shop` returned in a JSON body field itself, or require the caller to independently confirm the shop via a previously-stored, offline-token-associated session) rather than trusting them from headers alone. At minimum, document that `request.shop`/`request.topic` are NOT covered by the HMAC and must not be used to make tenant-scoping decisions.

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
      end
    end
  end
end
