### Title
Bandwidth-Fee Bypass via `is_purchase_message` Sender-Only Check Lets Any Message From the Registered Manager Skip Metering - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`ProxyModule::on_accept` in the gargantua/nexus runtimes skips the bandwidth gate for "purchase messages" using `pallet_bandwidth::Pallet::<Runtime>::is_purchase_message(&request)`. That helper only checks that `request.from` equals the registered `BandwidthManager` address for `request.source` — it never checks `request.to` (the destination module) or the message body/discriminant. This mirrors the GraphQL Armor flaw: a bypass condition intended for one specific "kind" of node (an actual purchase message addressed to `pallet-bandwidth`) is granted based on a field shared by many different messages (the sender address), without confirming the message is actually the privileged kind.

### Finding Description
`is_purchase_message` is defined as: [1](#0-0) 

It is consulted in the runtime's `IsmpModule::on_accept` before the bandwidth gate runs: [2](#0-1) [3](#0-2) 

The check only verifies `request.from == BandwidthManager[request.source]`. It does not verify `request.to == PALLET_BANDWIDTH` (the module the message is actually addressed to), nor that the body actually decodes as a `PurchaseMessage`. If the registered `BandwidthManager` contract on a given source chain can be induced to (or is compromised to) originate any `PostRequest` — or if the manager contract itself dispatches other kinds of messages (e.g., to `pallet_ismp_demo` or `pallet_hyper_fungible_token`) besides purchases — every such message from that same sender address bypasses the bandwidth gate entirely, regardless of its true destination module or purpose, exactly as the GraphQL depth-check was bypassed by matching a shared `name` field without checking the node's `kind`.

Downstream, `on_accept` in `Pallet<T>: IsmpModule` for pallet-bandwidth does perform a stronger sender check plus body decoding (`request.from != manager.0.to_vec()` and `PurchaseMessage::try_from`), so a forged non-purchase body sent *to* `pallet-bandwidth` would be rejected there. However, the vulnerability is in the *gate-skip decision itself*: any message from the registered manager address that is routed to a *different* destination module (`pallet_ismp_demo`, `pallet_hyper_fungible_token`, etc., per the `ProxyModule::on_accept` match arms) never gets metered, because the gate is skipped purely on sender identity rather than on the message actually being a bona fide purchase addressed to `pallet-bandwidth`.

### Impact Explanation
Bandwidth metering is the chain's DoS/resource-exhaustion economic control for all inbound ISMP messages (per the module doc: "insufficient balance → rejected"). A gate-skip that keys only on sender identity, not destination+message kind, allows an attacker who controls (or spoofs, via a compromised/rogue manager deployment) the registered manager address to route unlimited free-of-bandwidth-charge messages to any other module on the chain, undermining the bandwidth economic model. This is a freezing/DoS-adjacent impact on the bandwidth accounting invariant guarding message-processing resources — an unbacked "free bandwidth" grant scoped incorrectly.

### Likelihood Explanation
Exploitability requires the message to originate from `request.from == BandwidthManager[source]`, i.e., from the registered EVM manager contract address on the source chain. This is a real reachable path if the manager contract (a full Solidity contract, `BandwidthManager.sol`) is later extended to dispatch other message kinds from the same address, or if its owner/admin privileges are used to send arbitrary payloads (`BandwidthManager` inherits `Ownable`, per `evm/src/apps/BandwidthManager.sol`), since the pallet-side gate-skip trusts the sender address alone. It is a lower-likelihood analog than the original GraphQL bug (which required no privileged party at all) since it depends on the manager contract's owner or future functionality, but the root-cause pattern — bypass keyed on a field shared across message kinds rather than the actual kind being checked — is identical.

### Recommendation
Tighten `is_purchase_message` to require the message is genuinely addressed to `pallet-bandwidth` and structurally is a purchase, mirroring the fix pattern in the advisory (check the specific discriminant, not just a shared field):

```rust
pub fn is_purchase_message(request: &PostRequest) -> bool {
    request.to == PALLET_BANDWIDTH.0.to_vec()
        && BandwidthManager::<T>::get(&request.source)
            .map(|m| request.from == m.0.to_vec())
            .unwrap_or(false)
}
```

### Proof of Concept
1. Admin registers `BandwidthManager[Evm(chain_x)] = 0xManager`.
2. `0xManager` (owner-controlled or otherwise induced) dispatches a `PostRequest` with `from = 0xManager`, `source = Evm(chain_x)`, but `to = pallet_ismp_demo::PALLET_ID` (not `pallet-bandwidth`), and an arbitrarily large body.
3. In `ProxyModule::on_accept`, `is_purchase_message(&request)` returns `true` solely because `request.from == 0xManager`, so the bandwidth gate `try_consume` is skipped.
4. The message is routed to `pallet_ismp_demo` and processed for free, regardless of size, bypassing the byte-metered economic control intended to apply to all non-purchase inbound requests.

impl IsmpModule for ProxyModule {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Bandwidth gate. Always-enforce unless the `no-bandwidth` flag
		// is set; skipped for purchase messages so the recharge flow
		// itself doesn't need bandwidth. With the flag on the gate is a
		// no-op and this block is compiled out entirely.
		#[cfg(not(feature = "no-bandwidth"))]
		if !pallet_bandwidth::Pallet::<Runtime>::is_purchase_message(&request) {
			let bytes = ismp::abi::encode_post_request(&request).len() as u32;
			<pallet_bandwidth::Pallet<Runtime> as pallet_bandwidth::BandwidthGate>::try_consume(
				&request.source,
				&request.from,
				bytes,
			)
			.map_err(|err| {
				anyhow!(
					"bandwidth gate: {err} (source={:?}, from={:x?})",
					request.source,
					request.from
				)
			})?;
		}
