## Title
Webhook `shop` Attribution Is Not Bound By The HMAC Signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` value that the registry hands to application webhook handlers is read from an unauthenticated HTTP header. Any party who can produce one valid `(body, hmac)` pair for the shared app secret can replay it with an arbitrary `shop-domain` header and have it accepted as coming from a different shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns only `@raw_body`: [2](#0-1) 

but `shop` is derived independently from a plain header, never mixed into the signed material: [3](#0-2) 

`HmacValidator.validate` only recomputes/compares the HMAC over `to_signable_string`, i.e., only the body: [4](#0-3) 

`Registry.process` trusts this after only checking `Utils::HmacValidator.validate(request)`, then forwards `request.shop` (the header value) to the application handler as the tenant identifier, unchanged and unverified against the signed payload: [5](#0-4) 

The broken identity binding is:
`hmac_signed(shop) == shop_used_by_handler(header["shop-domain"])`
is never enforced — the gem verifies `hmac == HMAC(secret, raw_body)` but hands out `shop = header["shop-domain"]`, a value entirely outside that signature.

### Impact Explanation
Any unprivileged attacker who can obtain one legitimately-signed `(body, hmac)` pair for the app's shared `client_secret` (e.g., by installing the app on their own store and receiving a real webhook delivery) can replay that exact body/hmac pair directly against the app's webhook endpoint while substituting an arbitrary `shop-domain` header pointing at a victim tenant. `HmacValidator.validate` still returns `true` because only the body is checked, and `Registry.process` will hand the forged `shop` value to the app's `WebhookHandler`. Any host application that uses `WebhookMetadata#shop` to select which merchant's session, access token, or database row to act on will misattribute the payload to the victim tenant — a cross-tenant data-integrity break rooted entirely in this gem's `Request`/`HmacValidator`/`Registry` code, not merely a downstream app mistake.

### Likelihood Explanation
The only prerequisite is being able to install the target app on any single Shopify store (the normal state for any external developer/attacker) and capturing one real, validly-signed webhook body for that store — both trivially available to any unprivileged app installer. No access token, `api_secret_key`, or privileged access is required; only the header is forged, which is not covered by the signature at all. This is a self-contained defect in how `ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry` bind (or fail to bind) `shop` to the verified bytes.

### Recommendation
Include the header-derived `shop` (and ideally `topic`/`webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind the header-supplied `shop` to the signed body before handing it to `WebhookMetadata`/handlers. At minimum, document and/or enforce that `request.shop` must never be trusted as a tenant key unless it is cross-checked against an independently-established, previously-stored session/shop record rather than accepted as-is from `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery: body `B`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint using the exact same body `B` and hmac header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`; `Utils::HmacValidator.validate(request)` succeeds because it only recomputes the HMAC over `@raw_body` (`B`), which is unchanged.
4. `request.shop` returns `"victim-shop.myshopify.com"` from the forged header at [3](#0-2) , and `WebhookMetadata.new(... shop: request.shop ...)` is passed to the app's handler as if `victim-shop` had sent that webhook payload.
