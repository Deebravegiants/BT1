## Title
Webhook shop/topic identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` values used for dispatch entirely from unauthenticated HTTP headers, while the HMAC signature that `HmacValidator` verifies covers only the raw request body. Any actor who can obtain one valid `(body, hmac)` pair for a shop they control can replay that exact body with a forged `shop-domain` header, and the registry will process it as an authentic webhook for the victim shop whose identity was never bound to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from headers that are never mixed into the signable string: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` compute the HMAC strictly over `verifiable_query.to_signable_string` (i.e., the body), and compare it with the `hmac-sha256` header: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC checks out, then dispatches using the header-derived `shop`, `topic`, and `webhook_id` fields without any additional binding to the signature: [4](#0-3) 

This is the same bug class as the referenced report — a value used by downstream logic (there, `rewards.length`; here, `shop`) is not constrained/covered by the enforcing check (there, no gas bound; here, no HMAC coverage). Concretely, the broken identity equality is:

`hmac_signed_bytes(body) == bytes_the_app_trusts_as("shop", "topic", "webhook_id")`

The right-hand side is taken from unauthenticated headers, so it can diverge from the left-hand side (the actual signed payload) without invalidating the signature check.

### Impact Explanation
Because the shared app `client_secret` is the same across all merchant installs of a multi-tenant app, once any shop owner captures a legitimate `(body, hmac)` pair for an event on their own store (e.g., via webhook delivery logs, a debugging proxy, or a "resend" feature), they can replay that identical body to the app's webhook endpoint with an attacker-chosen `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because the body is unmodified and the secret matches. `Registry.process` then invokes the registered handler with `WebhookMetadata#shop` set to the forged victim shop, causing the app to process attacker-controlled webhook content under a different tenant's identity — a cross-tenant integrity/isolation violation for any handler logic that trusts `data.shop` to select or mutate that shop's stored state.

### Likelihood Explanation
Exploitation requires only: (1) being able to trigger or otherwise obtain one valid webhook body+HMAC pair for a shop the attacker controls (achievable without any privileged credential, since shop owners routinely receive/can inspect their own webhook deliveries), and (2) sending an HTTP POST with a modified `shop-domain` header to the app's public webhook endpoint — no `api_secret_key`, access token, or TLS interception is needed. This fits squarely within the "unprivileged internet user" threat model.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified material, or otherwise bind them to the HMAC — e.g., by validating them against a second, independently authenticated channel (such as a per-shop webhook secret, or cross-checking `shop` against session/installation records) rather than trusting header values whose only "protection" is a signature computed over unrelated bytes (the body).

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and triggers an event so Shopify sends a webhook; attacker captures the raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed with the shared `api_secret_key`), e.g. via a delivery log/proxy they control.
2. Attacker POSTs to the app's webhook endpoint with:
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <same topic>`
   - body: `B` (unchanged)
3. `ShopifyAPI::Webhooks::Request.new` builds the request from these headers/body; `HmacValidator.validate` recomputes the HMAC over `B` only and it matches `H`, so validation succeeds: [5](#0-4) 
4. `Registry.process` dispatches the handler with `shop: request.shop` = `"victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop: [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
