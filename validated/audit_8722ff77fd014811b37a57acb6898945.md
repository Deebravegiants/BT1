Confirmed: `HinkalWallet.isValidSignature` (EIP-1271) is **not called anywhere else in the codebase** outside of `HinkalWallet.sol` itself — the actual authorization path for `EmporiumUpgradeable.runAction` uses `verifyWallet`, which recovers the signer directly via `ECDSA.tryRecover` against a hash produced by `_hashTypedDataV4(keccak256(abi.encode(EMPORIUM_SIGNATURE_TYPEHASH, circomData.emporiumMessage, _hashEmporiumOps(stack.ops), stack.maxFee, stack.deadline)))`. [1](#0-0) 

This `_hashTypedDataV4` call comes from `EIP712Upgradeable`, whose domain separator (per OpenZeppelin's implementation) is computed from `keccak256(abi.encode(EIP712_TYPEHASH, hashedName, hashedVersion, block.chainid, address(this)))` — meaning the signed hash is already bound to both the chain ID and the Emporium contract address. This directly contradicts the premise of the question, which claims "no chainid/emporium binding in the signed hash itself — only address(this) is checked" and that the recovered check goes through `IHinkalWallet(W).isValidSignature`. [2](#0-1) [3](#0-2) 

The `HinkalWallet.isValidSignature` function that the question targets is real, but nothing in `EmporiumUpgradeable.runAction` or `verifyWallet` ever calls `IHinkalWallet(signerAddress).isValidSignature(...)`. `stack.signerAddress` is only used to call `callHinkalWallet`/`doSendToRelay` (both gated by `onlyEmporium` on the wallet side) after the signature has already been separately verified via direct ECDSA recovery against `stack.signerAddress` (an EOA check, not a contract-wallet 1271 check). [4](#0-3) 

Additionally, `verifyWallet` marks `circomData.emporiumMessage` as used in the `usedMessages` mapping before validating the signature, and this mapping is chain-local storage on the Emporium contract on each chain — so even if a signature and hash were somehow accepted on chain B that were only meant for chain A, the operations (`_hashEmporiumOps(stack.ops)`) it authorizes are hashed and included inside the domain-separated signed payload itself, meaning any different op set on chain B would produce a different `hashedMessage` and fail to recover to `stack.signerAddress`. [5](#0-4) 

The attack as described — reusing a signature meant for `isValidSignature` on chain A to authorize a different, unauthorized op set via `runAction` on chain B — is not reachable: `isValidSignature` is dead code with respect to `runAction`'s authorization flow, and the actual authorization hash (`EMPORIUM_SIGNATURE_TYPEHASH`) is already chain- and contract-bound via EIP-712, and it hashes over `stack.ops` directly, so a signature can never authorize a different op set than the one it was signed for, regardless of chain.

    function _hashEmporiumOps(
        EmporiumOperation[] memory ops
    ) private pure returns (bytes32) {
        bytes32[] memory opHashes = new bytes32[](ops.length);

            opHashes[i] = keccak256(
                abi.encode(
                    EMPORIUM_OPERATION_TYPEHASH,
                    ops[i].endpoint,
                    ops[i].invokeWallet,
                    ops[i].value,
                    keccak256(ops[i].callData)

            );
        }
        return keccak256(abi.encodePacked(opHashes));
