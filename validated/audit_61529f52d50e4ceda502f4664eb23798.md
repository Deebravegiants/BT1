### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` verifies the webhook `hmac-sha256` header against the raw request body only. The `shop-domain` header — which becomes the `shop` field the host application uses to attribute the webhook to a tenant — is never part of the signed material. Any party capable of obtaining one validly-HMAC'd webhook for the app (e.g., a merchant who installs the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, and `Registry.process` will accept it as coming from the spoofed shop.

### Finding Description
The identity binding that should hold is:
`hmac == HMAC(secret, raw_body || shop)` for the shop the webhook is attributed to.

Instead, the gem implements:
- `hmac` is read straight from the `hmac-sha256` header [1](#0-0) 
- `to_signable_string`, the material actually HMAC-verified, returns only `@raw_body` [2](#0-1) 
- `shop` is read from the `shop-domain` header, completely outside the signed payload [3](#0-2) 

`Registry.process` validates only this body HMAC and then forwards `request.shop` unchanged into `WebhookMetadata`, which the host app's handler uses to determine which tenant/shop the payload belongs to: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated string field passed to every handler: [5](#0-4) 

Because a single `api_secret_key` is shared across every shop that installs the app, an attacker who installs the app on their own store legitimately receives correctly-HMAC'd webhooks. The attacker can then POST the same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `Utils::HmacValidator.validate` (used by `Registry.process`) will report success because it only checks `to_signable_string`, i.e., the body — never the shop header — against the shared secret: [6](#0-5) 

### Impact Explanation
This breaks the binding "shop authenticated" vs. "shop trusted by the handler." A malicious merchant can forge webhooks that a host application will process as if they originated from a different tenant/shop of the same app, leading to cross-tenant data injection (e.g., triggering `orders/create`, `app/uninstalled`, `customers/data_request`, or other handler logic against another merchant's `shop` identifier). Depending on how the host app keys storage/side effects off `WebhookMetadata.shop`, this can corrupt or leak another tenant's data — a cross-tenant access impact.

### Likelihood Explanation
Any unprivileged individual who can install the app on a store they control (which is the normal onboarding flow for any multi-tenant Shopify app) automatically obtains valid HMAC'd webhook traffic signed with the app's shared secret. Forging the `shop-domain` header on a replayed POST requires no special access, credentials, or interception — only a basic HTTP client. This makes the attack straightforward and repeatable.

### Recommendation
Include the authenticated shop identity in the HMAC-verified material, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it (e.g., verify the shop against a known/expected value for the webhook subscription being processed, or require callers to supply and separately validate the shop out-of-band via Shopify's registered webhook endpoint per shop). At minimum, document that `WebhookMetadata.shop` is unauthenticated header data and must not be used as a sole tenant-identity gate without additional server-side verification (e.g., confirming an active session/installation exists for that shop before trusting the payload).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to send a legitimate webhook (e.g., `orders/create`) to the app's endpoint with headers:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   ```
2. Attacker captures the raw body and the `X-Shopify-Hmac-Sha256` value.
3. Attacker resends the identical body and HMAC header to the same endpoint, but sets:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Utils::HmacValidator.validate` in `Registry.process` succeeds because it only checks the body against the shared secret [7](#0-6) , and the handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` despite the payload never having been produced or authorized by Shopify for that shop.
