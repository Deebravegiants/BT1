### Title
Webhook Shop Attribution Not Covered by HMAC Signature Enables Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-validating only the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used to attribute the webhook to a specific merchant are taken from unauthenticated HTTP headers. An attacker who can obtain any one genuine, HMAC-valid webhook delivery (e.g., by installing the app on their own shop) can replay that payload against the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop, and the signature check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` is read straight from an attacker-controllable header with no cryptographic binding to the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` and HMACs only that string against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` uses this single HMAC check as the sole authenticity gate, then trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the data handed to the app's business logic: [4](#0-3) 

The equality the gem implicitly claims to enforce is:
`shop_header == shop_that_the_HMAC_authenticates`

But in reality the HMAC only authenticates `raw_body`, so the true invariant is:
`HMAC_valid(raw_body) ∧ shop_header == arbitrary_attacker_value`

Since the `api_secret_key` is a single per-app secret (not per-shop), any shop that has the app installed can generate a genuinely-signed webhook body/HMAC pair for itself, then reuse that valid `(raw_body, hmac)` pair against the same endpoint with the `shopify-shop-domain` header (and other unsigned headers) changed to name a different, victim shop. `HmacValidator.validate` still returns `true` because it only recomputes the HMAC over `raw_body`, and `Registry.process` will invoke the app's handler with `WebhookMetadata` claiming the forged `shop`.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing (cross-tenant access), the same trust-assumption class as the referenced report: a value that downstream logic implicitly relies on as "verified" (shop attribution) is actually never covered by the cryptographic check the code relies on (`Utils::HmacValidator.validate`). Any host application that uses `request.shop` from `Registry.process`/`WebhookMetadata` to select which merchant's data to update (a common and documented pattern, see `docs/usage/webhooks.md`) can be tricked into applying an attacker's payload to a victim shop's tenant, meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own shop with the target app installed (an unprivileged, ordinary integration), to legitimately receive one HMAC-valid webhook delivery for a body they control (or influence via normal store actions), and (2) the ability to POST directly to the app's public webhook endpoint with modified headers, which is trivial since webhook endpoints are unauthenticated HTTP endpoints by design. No access token, `client_secret`, or privileged credentials are required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed content that is verified, or independently verify that the `shop` header corresponds to a shop session/registration the app expects before trusting it. At minimum, `Utils::HmacValidator.validate`/`Registry.process` should bind the verified body to the specific shop header value (e.g., by including `shop-domain` in the HMAC input, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop`) so an HMAC valid for one shop cannot be replayed under another shop's identity.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), receiving a genuine request with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC_SHA256(api_secret_key, B)`.
2. Attacker resends this exact `(B, H)` pair to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only [3](#0-2)  — it matches, so validation passes.
4. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` [5](#0-4) , causing the app to act on data attributed to `victim.myshopify.com` even though it never sent this webhook.
