### Title
Webhook `shop-domain`/`topic`/`webhook-id` headers are not bound by the HMAC, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id` and `api_version` identity fields are read straight from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only the body HMAC and then hands the header-derived shop identity to the app's handler as trusted `WebhookMetadata`. Because Shopify signs webhooks with the single app-wide `client_secret` shared across every merchant/shop that installs the app, this breaks the identity binding `hmac ≟ f(shop, topic, body)` down to just `hmac ≟ f(body)`, mirroring the report's bug class ("a field acted on but not covered by the HMAC").

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers with no cryptographic binding to those values: [2](#0-1) 

`Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)` — which, per `VerifiableQuery`, checks `hmac` against `to_signable_string` (the body) — and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

`HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` with the shared `Context.api_secret_key`: [5](#0-4) 

Because the same `api_secret_key` (the app's `client_secret`) is used to sign webhooks for *every* shop that installs the app, `hmac = HMAC(secret, raw_body)` is identical regardless of which shop the event actually originated from. The equality the gem should enforce is:

`hmac == HMAC(secret, shop ‖ topic ‖ body)` (shop/topic bound into the signed material)

but what it actually enforces is:

`hmac == HMAC(secret, body)` (shop/topic unbound)

**Exploit path:** An unprivileged attacker who owns/operates their own shop (Shop A) installing the target app can trigger a legitimate webhook whose body they substantially control (e.g. `products/update`, `orders/create`, `customers/update` where fields like title/note/name are attacker-editable). Shopify sends the real webhook to the app's endpoint with a valid HMAC over that body, signed with the app's shared secret, and headers `X-Shopify-Shop-Domain: shop-a.myshopify.com`. The attacker captures this raw HTTP POST (body + `X-Shopify-Hmac-Sha256` header) and replays it directly to the same endpoint, only rewriting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to name Shop B (a victim shop that also installed the app). Since `HmacValidator` never looks at those headers, the forged request still validates successfully, and `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "shop-b.myshopify.com", body: <attacker-controlled>, ...)`, i.e. cross-tenant injection of attacker-controlled data attributed to a victim tenant.

### Impact Explanation
This is a cross-tenant integrity/confidentiality break: an unprivileged merchant of one tenant (Shop A) can make an app process attacker-controlled webhook data as if it originated from a different tenant (Shop B), without ever compromising Shop B's credentials or the app's `client_secret`. Depending on how the host app uses `WebhookMetadata.shop` (e.g. to look up/update per-shop records, sync inventory, issue refunds, or trigger downstream automation), this can lead to data corruption, unauthorized state changes, or information leakage across tenant boundaries — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker must (a) be a merchant with an installed instance of the same app so they receive a genuine, validly-signed webhook, and (b) be able to influence the webhook body content enough to matter, and (c) know/guess a valid target shop domain header value (shop domains are often discoverable/guessable, e.g. `*.myshopify.com`). No secret material, TLS interception, or privileged access is required — only normal use of one's own shop plus direct HTTP requests to the app's public webhook endpoint, which satisfies the "unprivileged internet user" threat model.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the HMAC-verified material rather than trusting raw headers post-hoc:
- Extend `Request#to_signable_string` (or add a companion check in `HmacValidator`/`Registry.process`) to include `shop`, `topic`, and `webhook_id` header values in the data that is verified, if Shopify's webhook signing scheme allows it, or
- Since Shopify's HMAC only covers the body by design, applications/gem consumers must independently verify that `shop-domain` corresponds to a shop actually known/installed by the app (e.g. cross-check against a stored session/shop registry) before trusting `WebhookMetadata.shop`; the gem should document this gap explicitly and/or provide a helper that requires callers to supply the list of valid installed shop domains to `Registry.process`, rejecting webhooks whose `shop-domain` isn't in that set.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and edits a resource (e.g., product title) to embed attacker-controlled content, triggering Shopify to send a `products/update` webhook to the app's registered endpoint with a valid `X-Shopify-Hmac-Sha256` header (HMAC over the JSON body, using the app's shared `client_secret`).
2. Attacker captures this raw request (`raw_body`, `X-Shopify-Hmac-Sha256`, other headers) via any HTTP proxy under their control.
3. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a real shop the app is installed on).
4. `Webhooks::Request.new` parses headers/body normally: `lib/shopify_api/webhooks/request.rb` lines 45-63.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` and compares to the (still valid, unchanged) received HMAC — validation succeeds because `to_signable_string` never referenced `shop`: `lib/shopify_api/webhooks/registry.rb` line 190, `lib/shopify_api/webhooks/request.rb` lines 35-38.
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)`, causing the app to process attacker-controlled data under the victim's tenant identity: `lib/shopify_api/webhooks/registry.rb` lines 198-199.
