### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier used to process a webhook (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that authenticates the request only covers the raw request body. An attacker who possesses one validly-HMAC-signed webhook payload (e.g., a webhook for their own shop, since a merchant fully controls their own shop's webhook traffic reaching their app) can resend it with a different `shop-domain` header value, and the gem will accept the signature as valid while attributing the payload to an arbitrary shop.

### Finding Description
`Request#hmac` is computed purely from the shopify hmac-sha256 header value, and `to_signable_string` (which `HmacValidator`/callers use to verify the signature) returns only `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop` accessor, which downstream webhook-handling code relies on to know which merchant/tenant the webhook belongs to, is read directly and unconditionally from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, with no cryptographic binding to the signed body: [3](#0-2) [4](#0-3) 

This is the same bug class as the referenced BloomPool report: a value that is *acted upon* (here, the tenant/shop used to route/process the webhook) is not covered by the authentication check (here, the HMAC), while a different, unrelated value (the raw body) is what's actually verified. The broken identity binding, stated as an equality that should hold but doesn't, is:

`shop_covered_by_hmac == shop_used_for_processing`

Before the attack: a legitimate webhook for shop A arrives with `raw_body` (containing/matching shop A data), `hmac = HMAC(secret, raw_body)`, and header `X-Shopify-Shop-Domain: shop-a.myshopify.com`. Verification passes, and `Request#shop` correctly returns `shop-a.myshopify.com`.

After the attacker's request: the attacker (who legitimately received this real webhook for their own installed shop, or intercepted/replayed one) resends the exact same `raw_body` and `hmac` value, but overwrites the `X-Shopify-Shop-Domain` header to `shop-b.myshopify.com`. Since `hmac`/`to_signable_string` never include the shop-domain header, `HmacValidator.validate` still succeeds (the signature only ever attested to the body bytes), yet `Request#shop` now returns `shop-b.myshopify.com`. Any handler built on this gem's `Webhooks::Registry`/`WebhookHandler` that looks up a session, credential, or tenant record keyed by `request.shop` will operate on shop B's tenant context using data/hmac validity that was only ever proven for shop A.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an app relying on this gem's `Webhooks::Request#shop` to select which merchant's session/access token to use, or to write incoming webhook data into per-shop storage, can be made to process an attacker-controlled shop identity under a signature that never authenticated that identity. This is a cross-tenant access vector consistent with the Critical impact bucket (cross-tenant access) defined in scope.

### Likelihood Explanation
The header is fully attacker-controlled at the HTTP layer since it is not part of the cryptographically verified content; anyone who can present one valid `(raw_body, hmac)` pair — trivially available to any developer/merchant who has installed the app and receives a genuine webhook — can replay it with an arbitrary `shop-domain` header. No secrets, tokens, or privileged access are required beyond normal receipt of one legitimate webhook, which is a realistic capability for an "unprivileged internet user" who is also a merchant using the app.

### Recommendation
Bind the shop identity into the authenticated material: either include the `shop-domain` header value in the HMAC signable string used for webhook verification, or independently verify that the `shop` header matches the shop domain embedded/expected inside the parsed payload before trusting `Request#shop` for any tenant-scoped lookup, in `lib/shopify_api/webhooks/request.rb`.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
2. Attacker (who owns/operates shop A, or has otherwise obtained this one valid webhook delivery) resends an HTTP request with the same body `B` and the same HMAC header, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks `B`. [2](#0-1) 
4. `request.shop` returns `"shop-b.myshopify.com"`, which the host application uses to pick shop B's session/credentials/data store, even though the signature never authenticated anything about shop B. [3](#0-2)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
