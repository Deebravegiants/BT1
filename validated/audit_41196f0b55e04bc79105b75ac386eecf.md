### Title
Unguarded fee subtraction in `createWithdrawalIntents` allows negative withdrawal amount when `feeInclusive: true` - (File: `packages/intents-sdk/src/sdk.ts`)

### Summary
`IntentsSDK.createWithdrawalIntents` computes `actualAmount = args.withdrawalParams.amount - args.feeEstimation.amount` whenever `feeInclusive` is true, with no check that `amount >= feeEstimation.amount` before it's used to build bridge intents. This lets a caller-supplied `feeEstimation` (or a stale/mismatched one) drive the computed amount negative.

### Finding Description
The broken equality: `actualAmount` (the amount debited/withdrawn) should always satisfy `actualAmount >= 0` and represent `amount - fee` with `amount >= fee`. In `createWithdrawalIntents`: [1](#0-0) 

the subtraction is performed unconditionally with no `FeeExceedsAmountError` guard, unlike the comment in the audit question suggests exists elsewhere. I confirmed by inspecting `_estimateWithdrawalFee` and the referenced `FeeExceedsAmountError` class [2](#0-1)  that this error type exists in the codebase but is not referenced anywhere in `sdk.ts`'s `createWithdrawalIntents` path (only defined, used presumably elsewhere for the `estimateWithdrawalFee` flow, not in this method).

I also checked `bridge.validateWithdrawal` (using `HotBridge` as a representative implementation) and found it validates destination address format, token-address collisions, and Stellar trustlines only — it does **not** check `amount` bounds or sign at all: [3](#0-2) 

and `HotBridge.createWithdrawalIntents` itself does not validate that `withdrawalParams.amount` is non-negative before using it to build the withdraw intent: [4](#0-3) 

The only "sanity check" present is `assert(intent.amounts[0] === amount.toString(), "Amount is not correct")`, which merely confirms internal consistency between the computed `amount` and what the HOT SDK echoes back — it does not reject negative values.

Exploit flow: an attacker calls `sdk.createWithdrawalIntents({ withdrawalParams: { amount: 100n, feeInclusive: true, ... }, feeEstimation: { amount: 150n, ... } })` directly (bypassing `estimateWithdrawalFee`). `actualAmount` becomes `-50n`, which is passed into `bridge.validateWithdrawal` (no bounds check) and then into `bridge.createWithdrawalIntents`, ending up serialized as a negative-looking value fed into `buildGaslessWithdrawIntent`/intent construction.

### Impact Explanation
A negative or malformed `amount` reaching the intent-building/bridge SDK call is anomalous input to a funds-moving code path. However, I was not able to fully trace how the downstream `ft_withdraw`/`mt_withdraw` intent primitives (or `buildGaslessWithdrawIntent` internals in `@hot-labs/omni-sdk`) actually serialize a negative bigint, nor whether such an intent would even be constructable/signable to something the intents contract would accept (NEAR contract-side amount fields are typically `U128` and would likely fail to parse a negative string, causing a hard failure rather than an unintended debit). I could not conclusively verify within this repo that a negative amount produces "unintended debit semantics" as opposed to simply throwing/reverting at intent construction or contract execution time — the bridging library (`@hot-labs/omni-sdk`) is a third-party dependency outside this repo's scope.

### Likelihood Explanation
Preconditions are easy to meet: any caller can invoke `createWithdrawalIntents` directly with a `feeEstimation` object they control (it's a plain argument, not fetched internally), and set `feeInclusive: true` with `amount` smaller than `feeEstimation.amount`. No special privileges or route state are required beyond finding a bridge that `supports()` the given `withdrawalParams`.

### Recommendation
Add an explicit guard in `createWithdrawalIntents` (mirroring whatever check exists in the `estimateWithdrawalFee` path) that throws `FeeExceedsAmountError` when `args.withdrawalParams.feeInclusive && args.withdrawalParams.amount < args.feeEstimation.amount`, before computing `actualAmount`, e.g. immediately after entering the bridge loop in `packages/intents-sdk/src/sdk.ts` (around line 342).

### Proof of Concept
Vitest test plan (mocks HTTP only, e.g. mocking bridge's underlying fee-quote HTTP calls if needed, or directly unit-testing `createWithdrawalIntents` with a stub bridge):
1. Construct `withdrawalParams = { amount: 100n, feeInclusive: true, assetId, destinationAddress, routeConfig }`.
2. Construct `feeEstimation = { amount: 150n, quote: null, underlyingFees: {...} }`.
3. Call `sdk.createWithdrawalIntents({ withdrawalParams, feeEstimation })`.
4. Assert (side A): expected — `createWithdrawalIntents` should throw `FeeExceedsAmountError` before any bridge call.
5. Assert (side B, current behavior): call proceeds, `bridge.createWithdrawalIntents` is invoked with `amount: -50n`, and no error is thrown — demonstrating the equality `actualAmount >= 0` is violated.

Note: I could not verify inside this repo whether the negative value ultimately gets rejected further downstream by the `@hot-labs/omni-sdk`'s `buildGaslessWithdrawIntent` (third-party, out of scope) or by contract-side `U128` parsing — this final-stage behavior should be confirmed with a live/mocked HOT SDK call as part of the PoC to determine exact failure mode.
