### Title
Webhook HMAC validation signs only the raw body, allowing forged `shop-domain`/`topic` headers to spoof tenant identity - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` as plain, unauthenticated HTTP header reads, while `to_signable_string` (used for HMAC verification) returns only `@raw_body`. `Webhooks::Registry.process` verifies the HMAC and then immediately trusts these header-derived fields to build `WebhookMetadata` and dispatch to the app's handler — but the HMAC never bound the shop/topic identity to the body it signs.

### Finding Description
`Request#to_signable_string` is defined as just the raw body: [1](#0-0) 

`Request#shop` and `Request#topic` are read straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the HMAC against `Utils::HmacValidator`, and on success unconditionally trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to construct the metadata handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received signature — for `Request`, that's `HMAC(secret, raw_body)` only: [4](#0-3) 

The identity binding that should hold is: `hmac_valid(body) == true` implies `shop-domain header is authentic`. In reality the equality that holds is only `hmac_valid(body) == true` implies `body bytes are authentic under the app's shared api_secret_key`; the `shop`, `topic`, `webhook_id`, and `api_version` headers are completely outside that signature. Since `api_secret_key` is shared across *all* shops that install the app (not per-tenant), any merchant who has installed the app can capture a legitimate webhook delivery to their own endpoint (a correctly HMAC-signed `{body, hmac}` pair) and replay that exact body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header. `Utils::HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will hand the attacker-chosen `shop`/`topic` straight to the app's handler as if Shopify itself had sent that event for that shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook authenticity: an unprivileged merchant of a multi-tenant app can forge webhook events (including mandatory topics such as `app/uninstalled`, `shop/redact`, `customers/data_request`) attributed to a shop domain they do not own, since `shop`/`topic` are never part of the signed payload. If the host app's handler (following this gem's documented `WebhookMetadata#shop`/`#topic` contract) uses those fields to select which tenant's session/data to act on, this yields cross-tenant data manipulation/deletion without ever needing that victim's credentials — a boundary crossing the gem itself creates by presenting these fields as verified once `HmacValidator.validate` passes.

### Likelihood Explanation
Any user capable of installing the app on their own store (a normal, unprivileged action) can capture one legitimate webhook delivery and replay it with modified headers; no secret material, access token, or elevated privilege is required — only observing traffic to their own registered endpoint, which they fully control as the app's authenticated recipient of their own shop's webhooks.

### Recommendation
Bind the identity headers into the signed payload check: canonicalize and include `topic`, `shop-domain`, `webhook-id`, and `api-version` (or at minimum `shop` and `topic`) into `to_signable_string`, or perform a secondary authenticated check (e.g., re-deriving/confirming the shop from a server-side registration record rather than trusting the header) before constructing `WebhookMetadata`. At minimum, document loudly that `request.shop`/`request.topic` are NOT covered by the HMAC and must not be used for authorization decisions without independent verification against a known-installed-shop store.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; attacker receives a legitimate webhook, e.g. body `{"id":123}` with headers `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and a valid `X-Shopify-Hmac-Sha256` computed as `HMAC-SHA256(api_secret_key, '{"id":123}')`.
2. Attacker resends the identical body and the identical HMAC value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or `X-Shopify-Topic: app/uninstalled`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-hashes `raw_body` — the check passes because the body/HMAC pair is untouched.
4. `Registry.process` builds `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: {"id"=>123}, ...)` and dispatches it to the app's handler as if Shopify had generated this event for `victim-shop.myshopify.com`. [3](#0-2) [5](#0-4)
