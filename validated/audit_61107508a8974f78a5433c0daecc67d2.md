Based on my investigation, I found a genuine identity-binding gap in the webhook processing path.

### Title
Webhook `shop` used to route/attribute events without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
The `HonestPathTimer` bug class (a value being trusted/used in a security decision when it wasn't actually validated by the mechanism relied upon) maps onto `ShopifyAPI::Webhooks::Request` in this gem: the `shop` (and `topic`) values that are handed to the app's webhook handler are taken from unauthenticated HTTP headers and are never included in the HMAC-signed payload the gem verifies.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/verifies the signature purely against that signable string [2](#0-1) . However, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) with no cryptographic binding to those header values [3](#0-2) . `Registry.process` validates the HMAC over the body only, then immediately forwards `request.shop`, `request.topic`, and `request.webhook_id` straight to the app's handler as trusted `WebhookMetadata` [4](#0-3) .

This means the equality the gem implicitly claims to guarantee — "`shop` attributed to this event" == "`shop` covered by the verified signature" — does not hold. The signature only proves the body is unmodified/from Shopify (assuming the true HMAC leaks nowhere), but the `shop-domain` header sent alongside that body is unauthenticated and attacker-controllable if the attacker can influence headers reaching the app (e.g., via a misconfigured reverse proxy, header-forwarding CDN, or any component that lets user input set `X-Shopify-Shop-Domain` while a legitimate signed body from a *different, attacker-owned* shop is replayed).

Concretely: an unprivileged user who operates their own Shopify dev shop can trigger a legitimate webhook delivery (with a correctly signed body for *their own* shop, since HMAC uses the single shared `api_secret_key` across all shops using the app), then replay that exact `raw_body`/HMAC pair while substituting a victim shop's domain in the `shop-domain` header. `HmacValidator.validate` will pass (body+HMAC match), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is `shop: victim-shop.myshopify.com`, even though the payload content is really the attacker's own shop's data. If the host application's handler uses `data.shop` to key persistence, cache invalidation, or trust decisions (as the gem's own documentation/examples imply, e.g. `MyApp::SessionRepository`-style usage keyed by shop), this creates cross-tenant data confusion driven entirely by an identity field the gem itself does not bind into the signature it verifies.

### Impact Explanation
This falls under **Critical - cross-tenant access**: the gem asserts a `shop` identity for a webhook event that is not actually authenticated, enabling an attacker who legitimately controls one shop to cause the host application to process/attribute webhook data under a different tenant's identity, as long as they can influence how headers reach the app process (e.g., transparent proxies, load balancers, or CDNs that don't strip/canonicalize Shopify webhook headers before forwarding).

### Likelihood Explanation
Exploitability depends entirely on whether the deployment environment allows an unprivileged party to control or spoof the `shop-domain` header while the body+HMAC remain valid for a webhook they legitimately received (from their own shop). In a standard raw HTTP delivery pipeline directly from Shopify to the app, Shopify sets these headers itself, so this is not directly remotely exploitable without an intermediary that trusts client-supplied headers. Likelihood is therefore conditional on infrastructure, but the root cause — the gem's own signature scope excluding `shop`/`topic`/`webhook_id` — is a real, verifiable design gap in this codebase, not merely a hypothetical about host-application misuse of documented behavior.

### Recommendation
- **Short term**: Document explicitly that `shop`, `topic`, `api_version`, and `webhook_id` in `ShopifyAPI::Webhooks::Request` are unauthenticated header values not covered by the HMAC, and that host applications must not trust them without additional validation (e.g., cross-check `shop` against an existing installed-shop record before acting).
- **Long term**: Where feasible, incorporate the header-derived identity fields into the value verified against Shopify (e.g., validate that the `shop` header matches a shop actually expected by the app for a webhook of that `topic`/`webhook_id`), or extend `to_signable_string` to bind these fields where Shopify's delivery protocol supports it, closing the gap between "signature covers `raw_body`" and "handler trusts `shop`".

### Proof of Concept
1. Register a webhook handler that keys behavior on `data.shop`, per the documented pattern: [4](#0-3) 
2. Attacker installs the app on their own shop (`attacker-shop.myshopify.com`) and triggers a real webhook event, capturing the valid `raw_body` and its correct `x-shopify-hmac-sha256` value (computed by Shopify with the shared `api_secret_key`).
3. Attacker relays this exact `raw_body` + HMAC to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (feasible wherever the app is reachable through a component that forwards client-influenced headers, e.g. a proxy that doesn't overwrite Shopify's headers).
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the HMAC: [5](#0-4) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to attribute attacker-controlled data to the victim tenant: [6](#0-5)

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
