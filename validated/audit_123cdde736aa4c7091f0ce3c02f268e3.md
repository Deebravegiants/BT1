### Title
Webhook `HmacValidator` signs only the raw body, letting an attacker replay a legitimately-signed payload under a forged shop identity - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements the `VerifiableQuery` contract by returning only the raw HTTP body as the signable string, so the HMAC verified by `Utils::HmacValidator.validate` never covers the `shop`, `topic`, or `webhook_id` values that `Webhooks::Registry.process` subsequently uses to identify the tenant and route the payload to the app's handler.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are populated straight from HTTP headers that are never mixed into the signed string: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC and then trusts `request.shop`, `request.topic`, and `request.webhook_id` verbatim when building the `WebhookMetadata` handed to the app's registered handler: [3](#0-2) 

`HmacValidator.validate` only compares `computed_signature` (over the signable string) with the received HMAC — it has no way to know the signature was ever tied to a specific shop: [4](#0-3) 

The broken identity binding is: `HMAC_valid(body) == true` is treated as proof of `shop_header == authentic_source_shop`, but the equality that is actually verified is only `HMAC_valid(body)`; `shop_header` is never part of the signed material. Any unprivileged actor who legitimately receives one Shopify webhook for their own shop (any merchant/developer who installs the app) obtains a valid `(raw_body, hmac)` pair. They can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because the body is byte-for-byte identical to what was originally signed, and `Registry.process` passes the attacker-chosen `shop` straight into the handler.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: a multi-tenant app relies on `WebhookMetadata#shop` (sourced from this gem) to scope the incoming data to the correct merchant. Because `shop` is not covered by the signature, an attacker can inject a replayed, validly-signed payload under a different shop's identity, producing cross-tenant data corruption/spoofing without ever possessing the app's `client_secret` or any access token. This matches the "Critical - cross-tenant access" impact class.

### Likelihood Explanation
Requires only: (1) being an unprivileged merchant/developer able to install the target app on their own shop and capture one legitimate webhook delivery (`raw_body` + `X-Shopify-Hmac-Sha256`), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with modified headers — both trivially available to any internet user, no credentials or TLS interception needed.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is actually verified: e.g., derive the signing input from `shop-domain + raw_body`, or have `Registry.process` additionally require that the `shop` header matches a shop the app has an active session/installation for before dispatching to the handler, rather than trusting the header as-is once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker POSTs to the app's public webhook endpoint with the same `raw_body`/HMAC but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `raw_body`: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload was never signed for that shop, letting the attacker inject/spoof data attributed to the victim tenant.
