### Title
Cross-tenant webhook spoofing via `shop-domain` header not covered by HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read from separate, unauthenticated HTTP headers. `Registry.process` validates the body HMAC and then forwards the header-derived `shop` value, unauthenticated, straight to the app's handler as the trusted tenant identifier, exactly as the gem's own documentation instructs apps to do.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content at all: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` that is handed to the app's handler, without any check binding these header values to the signed body: [4](#0-3) 

`HmacValidator.validate` itself is generic and simply compares `verifiable_query.hmac` against a signature computed from `verifiable_query.to_signable_string` (the body only, for webhooks): [5](#0-4) 

The `WebhookMetadata` struct exposes `shop` as a first-class trusted field: [6](#0-5) 

Critically, the gem's own documentation instructs integrators to use `data.shop` directly as the tenant key for subsequent processing (e.g., looking up the shop's session/access token to act on the payload): [7](#0-6) 

Because `shop` is never covered by the HMAC, the equality the app relies on — "the shop that authenticated this HMAC" == "the shop attributed to this event" — does not hold. Anyone who obtains one valid `(raw_body, hmac)` pair for any topic/shop (e.g., a webhook naturally delivered to the app for shop A, which the app itself can observe on its own endpoint, or a replayable pair from a public/log source) can resubmit that exact body/HMAC pair to the app's webhook endpoint with a different `shop-domain` header value (shop B). `HmacValidator.validate` still succeeds because it only checks the body bytes against the secret, and `Registry.process` will then dispatch `WebhookMetadata(shop: "B", body: <shop A's payload>)` to the handler, which per the gem's own documented usage pattern will use `data.shop` as the trusted tenant identifier for that data.

### Impact Explanation
This breaks the identity binding "shop authenticated via HMAC" == "shop the payload is attributed to," letting an attacker cause cross-tenant data to be processed/stored under the wrong shop identity. Depending on the handler logic (queued job keyed by `shop_domain`, as shown in the gem's own doc example), this can lead to a shop's webhook data being applied to another merchant's tenant record — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Requires the attacker to first obtain one legitimate `(raw_body, hmac)` pair, which is a normal event for any app under this attacker's own control (they can install the target app on their own shop and legitimately receive signed webhooks), then replay it against the shared multi-tenant webhook endpoint with a forged `shop-domain` header for a victim shop. This is straightforward and does not require the `api_secret_key`, an access token, or any credential beyond passive observation of the attacker's own webhook traffic.

### Recommendation
Include the shop domain (and topic, webhook id) in the signable content the gem verifies, or otherwise cryptographically bind them to the body before exposing `WebhookMetadata#shop` as trusted. At minimum, the gem should not present the header-derived `shop` as an authenticated field, and documentation should not instruct consumers to treat `data.shop` as verified identity independent of the signed payload.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: raw body `B` with header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `api_secret_key`) and header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs to the app's shared webhook endpoint the same raw body `B` and same `hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`: [8](#0-7) 
4. The handler receives `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker's payload B>)` and, per the gem's documented pattern, processes/stores it under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
