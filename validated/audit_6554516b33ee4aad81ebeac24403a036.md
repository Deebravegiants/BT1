The user is asking to identify instances of the "fee-on-transfer" vulnerability pattern within the `AllProjects` codebase. This vulnerability occurs when a contract credits a user for a requested token amount without verifying the actual amount received, which can be less due to transfer fees imposed by certain ERC-20 tokens. This discrepancy can lead to an inflated internal balance within the contract compared to its actual holdings.

A systematic scan for this vulnerability class was performed across the `AllProjects` corpus, as documented in `issues.md` . The scan specifically looked for functions that pull tokens into `address(this)`, perform share/credit accounting, and do not measure a balance delta or refuse fee-bearing tokens .

### Finding Description

One instance of this pattern was identified in the `gamma` project, specifically within the `xGamma.enter` function . The `enter` function calculates shares based on `_amount` (the requested amount) and `totalGamma` (the contract's balance), without explicitly accounting for potential transfer fees . This means that if a fee-on-transfer token were used, the `totalGamma` could be inflated relative to the actual tokens received.

### Impact Explanation

The `xGamma` contract's share price is derived from a balance that can be manipulated by direct token transfers . If a fee-on-transfer token is used, the `totalGamma` (the contract's balance of the underlying token) would be less than the `_amount` credited, leading to an incorrect share price calculation. This could allow an attacker to be the first depositor, donate a large balance directly to the contract (which would incur a fee, reducing the actual amount received but not the credited amount), and then subsequent depositors' shares would round to zero, effectively allowing the attacker to own the entire pool with a minimal initial deposit .

### Likelihood Explanation

While the structural weakness exists, the exploit is currently not economically feasible at the live scale of the `xGamma` contract . The `xGamma` vault is already populated with a significant `totalSupply` of shares, making it impossible to be the "first depositor" . Furthermore, to force subsequent deposits to round to zero, an attacker would need to donate an astronomically large amount of GAMMA tokens, far exceeding the token's entire supply . Therefore, the likelihood of exploitation is currently very low.

### Recommendation

The recommendation for this class of vulnerability is to record the amounts of tokens both before and after the transfer to accurately determine the actual amount received by the strategy contract . This involves measuring the balance delta of the token within the contract.

### Proof of Concept

The `xGamma` contract, specifically the `enter` function, exhibits the vulnerable pattern .

```solidity
function enter(uint256 _amount) public {
    uint256 totalGamma = gamma.balanceOf(address(this));   // inflatable by a direct transfer
    uint256 totalShares = totalSupply();
    if (totalShares == 0 || totalGamma == 0) {
        _mint(msg.sender, _amount);
    } else {
        uint256 what = _amount.mul(totalShares).div(totalGamma);
        _mint(msg.sender, what);                           // no require(what > 0)
    }
    gamma.transferFrom(msg.sender, address(this), _amount); // return value unchecked
}
```


In this snippet, `_amount` is the requested amount. The calculation for `what` (the number of shares to mint) uses `totalGamma`, which is `gamma.balanceOf(address(this))`. If `gamma` is a fee-on-transfer token, the actual amount received by `address(this)` after `gamma.transferFrom` would be less than `_amount`, but `totalGamma` would reflect the higher, pre-fee amount if not properly measured. This discrepancy could lead to an incorrect share price.

## Notes

The `issues.md` document explicitly notes that this finding, while a real structural weakness, is "NOT EXPLOITABLE at live scale" due to the current state of the deployed contract . It is recorded for reasoning and as a potential vulnerability if a fresh `xGamma`-style vault were deployed . Other projects like `veda`, `listadao`, `silofinance-v2`, `twyne`, and `ondofinance` were also scanned for this class but were found to be clean due to access controls, specific asset types, or reconciliation mechanisms . Some `SCOPE.md` files, such as `balancer/SCOPE.md`  and `whitechain-bridge/SCOPE.md` , explicitly state that fee-on-transfer tokens are out of scope for their bug bounty programs, indicating an awareness of this issue.
