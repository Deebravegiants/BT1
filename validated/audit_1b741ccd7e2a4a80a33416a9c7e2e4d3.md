Based on my investigation, I found a mismatch between the `Bonding.sol` natspec's stated mitigation and the actual `LPLock.recordLock` behavior, which constitutes a real, reachable permanent-freeze analog to the CVE's "malformed data → unrenderable/unprocessable state" class.

### Title
Hostile HyperSwap-pair pre-seed can drive `finalizeGraduation`'s liquidity to zero, permanently reverting graduation via `LPLock.recordLock`'s `ZeroAmount` guard - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` seeds LP into a HyperSwap V2 TOKEN/LT pair that any unprivileged address can pre-create and pre-seed before phase 2 runs. The hostile-pre-seed defense (`_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance` → `_routerDepositAndDispose`) documents in its own comments a residual failure mode where the router deposit leg is skipped because one side of the balance is zero, yielding `liquidity = 0`. The code's own natspec claims this is safe because `LPLock.recordLock(...) records a zero-sized lock`, but the deployed `LPLock.recordLock` actually reverts with `ZeroAmount` when `amount == 0` [1](#0-0) . Since `recordLock` is called at the tail of `finalizeGraduation`, a revert there unwinds the entire transaction, including the `Lifecycle.Graduating → Graduated` flip and the `delete pendingGraduation[tokenAddress]` [2](#0-1) . Because `pendingGraduation`'s `(tokensForLP, ltFromPair)` are pinned deterministically at phase 1 and never recomputed [3](#0-2) , any retry of `finalizeGraduation` against the same hostile pool state reproduces the same zero-liquidity outcome and reverts again — a permanent brick of that token's graduation, stranding the curve's raised LT (`ltFromPair`) and the 250M `LP_RESERVE` tokens inside `Bonding` forever with no owner-level rescue path.

### Finding Description
The 99%-cap safeguard in `_swapBudget` is explicitly designed to keep `remToken`/`remLT` non-zero after the rebalance swap so the deposit in `_routerDepositAndDispose` always lands [4](#0-3) . The comment on that function explicitly walks through the failure mode it is guarding against: an extreme hostile pre-seed could otherwise drive the rebalance swap to consume 100% of one side, causing `_routerDepositAndDispose` to skip `addLiquidity` (because `remToken == 0` or `remLT == 0`), which causes `finalizeGraduation` to return `liquidity = 0` [5](#0-4) . `_routerDepositAndDispose` indeed defaults `liquidity` to `0` (Solidity's implicit initial value) whenever `remToken == 0 || remLT == 0`, skipping the `addLiquidity` call entirely [6](#0-5) .

The comment then asserts the consequence is that "`LPLock.recordLock(...)` records a zero-sized lock — the attacker's pre-existing LP becomes 100% of the pool," implying the call *succeeds* with `amount = 0`. But `LPLock.recordLock` unconditionally reverts on `amount == 0`:
```solidity
if (amount == 0) revert ZeroAmount();
``` [7](#0-6) 

This means the protocol's own threat model for this exact scenario is stale/incorrect relative to the shipped `LPLock` code: instead of degrading gracefully to "attacker captures the LP but graduation completes," the actual behavior is "the entire `finalizeGraduation` transaction reverts," which is strictly worse because `finalizeGraduation` is the *only* path out of `Lifecycle.Graduating` and there is no owner-level override, no timeout, and no alternate LP-lock target — `LPLock`'s locker allowlist is add-only and has no rescue/removal function [8](#0-7) .

While the `_swapBudget` 1% reservation is intended to prevent `remToken`/`remLT` from hitting exactly zero after the rebalance-swap path, `_seedDirectMint` (the fallback used both for tiny pre-seeds and when `_pairRebalance` returns `false`) calls the raw `IUniswapV2Pair.mint` directly [9](#0-8) . When this fires against a pool where `totalSupply() != 0` (i.e., inside `_seedRebalancing`'s hostile mint-pre-seed regime), standard `UniswapV2Pair.mint` computes `liquidity = min(amount0 * totalSupply / reserve0, amount1 * totalSupply / reserve1)`; if either side is disproportionately small relative to the attacker's chosen reserve ratio (a hostile actor can freely choose that ratio when pre-minting into a pair *they* create before phase 2 runs), the raw V2 pair itself either reverts with `INSUFFICIENT_LIQUIDITY_MINTED` (also unwinding the whole tx) or, if it doesn't revert, still routes through `LPLock.recordLock`, which will revert on any resulting `amount == 0`. Both outcomes give an attacker — an unprivileged, unrelated wallet — a griefing vector: pre-create the HyperSwap TOKEN/LT pair for a token about to graduate, mint an adversarially-shaped tiny/skewed reserve into it, and force every subsequent `finalizeGraduation(tokenAddress)` call (permissionless, callable by anyone) to revert deterministically, since the cached `(tokensForLP, ltFromPair)` never change.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any unrelated wallet with no special privilege: the target token's `LP_RESERVE` (250M tokens) and the curve's entire raised LT (`ltFromPair`) sit trapped inside `Bonding` in `Lifecycle.Graduating` forever, unreachable by traders (buy/sell revert with `TokenIsGraduating`) and un-rescuable (no owner override, `LPLock` has no removal/rescue mechanism). This matches the "permanent freezing of trader, creator, or LP funds" impact bar in scope.

### Likelihood Explanation
The attack requires only: (1) pre-creating the HyperSwap V2 pair for the about-to-graduate TOKEN/LT pair — permissionless via `IUniswapV2Factory.createPair`, reachable ahead of `finalizeGraduation` since phase 1/phase 2 are two separate transactions with an observable window; and (2) minting a small, adversarially-ratioed reserve into it before the keeper or anyone else calls `finalizeGraduation`. The protocol's own code comments show the team was aware of and tried to engineer around exactly this shape of attack, but the mitigation (`_swapBudget`) does not cover the `_seedDirectMint` path taken when `_pairRebalance` returns `false`, and the assumption underpinning even the covered path ("recordLock accepts amount = 0") is contradicted by the actual `LPLock.recordLock` code.

### Recommendation
- Update `LPLock.recordLock` (or `Bonding.finalizeGraduation`) so a computed `liquidity == 0` cannot revert the entire graduation transaction — either allow a zero-amount lock record explicitly (matching the original design comment), or add a dedicated recovery path in `finalizeGraduation`/`LPLock` for this degenerate case.
- Audit every call path that can reach `_seedDirectMint` with `totalSupply() != 0` (i.e. `_seedRebalancing`'s "below the band" fast path and the `_pairRebalance == false` fallback) to guarantee `IUniswapV2Pair.mint` cannot return/revert on zero liquidity against an attacker-chosen pre-seed ratio.
- Add a fuzz/invariant test that pre-seeds the HyperSwap pair with an adversarially skewed ratio sized to deliberately zero out one side of `_routerDepositAndDispose`'s deposit, and assert `finalizeGraduation` still succeeds (not reverts) on every retry.

### Proof of Concept
1. Launch a token via `Zap.createToken`; buy through the curve until `canGraduate` fires phase 1 (`_enterGraduating` caches `(tokensForLP, ltFromPair)`), leaving the token in `Lifecycle.Graduating`.
2. Before anyone calls `finalizeGraduation`, an unrelated attacker wallet calls `IUniswapV2Factory.createPair(token, lt)` directly on the configured HyperSwap V2 factory, then transfers a small, adversarially-ratioed amount of `lt` (or `token`, minted from a prior curve buy) into the pair and calls `pair.mint(attacker)`, establishing a live `totalSupply() != 0` with a hostile reserve ratio sized to fall in `_seedRebalancing`'s degenerate band.
3. Anyone calls `bonding.finalizeGraduation(tokenAddress)`. Depending on the exact ratio chosen, either `_routerDepositAndDispose` computes `remToken == 0 || remLT == 0` (skipping `addLiquidity`, `liquidity = 0`) and `LPLock.recordLock` reverts with `ZeroAmount`, or `_seedDirectMint`'s raw `pair.mint(lpLock)` call reverts with `INSUFFICIENT_LIQUIDITY_MINTED`.
4. Every subsequent call to `finalizeGraduation(tokenAddress)` recomputes against the same cached `pendingGraduation` values and the same hostile pair state, reverting identically forever — the token is permanently stuck in `Lifecycle.Graduating` with its LP reserve and raised LT unrecoverable.

    function _routerDepositAndDispose(
        address tokenAddress,
        address lt,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        BondingStorage storage $ = _s();
        address routerAddr = $.uniswapV2Router;
        address lpLock_ = $.lpLock;
        uint256 remToken = IERC20(tokenAddress).balanceOf(address(this));
        // Subtract `protectedLT` (LT that doesn't belong to this graduation
        // — concurrent escrows or stray dust, snapshotted at the top of
        // `finalizeGraduation`) so the deposit allowance can never pull
        // another graduation's earmark or accidentally absorb dust into a
        // locked LP.
        uint256 ltBal = IERC20(lt).balanceOf(address(this));
        uint256 remLT = ltBal > protectedLT ? ltBal - protectedLT : 0;

        if (remToken > 0 && remLT > 0) {
            IERC20(tokenAddress).forceApprove(routerAddr, remToken);
            IERC20(lt).forceApprove(routerAddr, remLT);
            (,, liquidity) = IUniswapV2Router02(routerAddr)
                .addLiquidity(tokenAddress, lt, remToken, remLT, 1, 1, lpLock_, block.timestamp);
            IERC20(tokenAddress).forceApprove(routerAddr, 0);
            IERC20(lt).forceApprove(routerAddr, 0);
        }

        // Burn off-ratio TOKEN remainder (`Bonding` is the Token owner).
        // Hostile pre-seeds reduce circulating supply by the attacker's
        // wasted-side share, net positive for honest holders.
        uint256 leftoverToken = IERC20(tokenAddress).balanceOf(address(this));
        if (leftoverToken > 0) {
            Token(tokenAddress).burn(address(this), leftoverToken);
        }
        // LT remainder is third-party — we cannot burn it. It stays in
        // this contract until `finalizeGraduation`'s post-bookend sweeps
        // it to the owner. Honest graduations never reach this code path,
        // so the residue is zero outside attack scenarios.
