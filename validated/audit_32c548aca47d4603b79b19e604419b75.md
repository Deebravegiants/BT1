### Title
Webhook `shop-domain` (and `topic`) header is trusted without HMAC coverage, allowing shop identity spoofing in processed webhooks - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw HTTP body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` directly to the handler as the identity of the merchant the event is "for," without that value ever being covered by the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` (and sibling) headers, which are never fed into the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC (over body) and then forwards `request.shop` (and `request.topic`) as trusted identity to the handler: [3](#0-2) 

`HmacValidator.validate` confirms `verifiable_query.hmac` against `verifiable_query.to_signable_string` only — i.e., the body — using the app's `api_secret_key`: [4](#0-3) 

The identity binding that should hold is: `shop-domain header == shop that the HMAC-signed body was generated for`. In this gem, that binding does not exist — the HMAC only proves "this body was produced by an entity with this app's `api_secret_key`" (Shopify), it says nothing about which shop's header value is presented alongside it. Because Shopify signs webhook bodies with the **app's** secret (the same secret for every shop that installs the app), any shop that installs the app — including one an attacker fully controls — receives genuine `(body, hmac)` pairs signed with the app's secret. Since `shop-domain`/`topic`/`webhook_id` headers are not part of the signed content, an attacker who operates their own (attacker-owned) shop installation of the target app can capture a legitimately-signed webhook delivery and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain (and/or the `topic` header changed to a topic whose payload shape matches). `HmacValidator.validate` will still return `true` because it only checks the body/HMAC pair, and `Registry.process` will invoke the handler believing the event originates from the victim shop.

This satisfies the requested analog: "a field acted on but not covered by the HMAC" — `shop` (and `topic`) is acted upon (used to route/attribute the webhook) but is excluded from the HMAC-protected signable string.

### Impact Explanation
Host applications built on this gem commonly use the webhook's reported `shop` to look up/update per-tenant state (e.g., process `app/uninstalled`, `shop/redact`, `customers/redact`, GDPR mandatory topics, or business-logic topics like `orders/create`) keyed by that shop. Because the shop identity is unauthenticated relative to the signed content, an attacker can cause the app to process webhook data under an arbitrary victim shop identity — a cross-tenant data/state confusion. This matches the "High" bucket ("scope or expiry check bypass" class of identity-binding failures / cross-tenant), since a per-tenant authorization boundary (which shop a given signed event applies to) can be crossed without the victim's or Shopify's credentials.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be an unprivileged developer/merchant capable of installing the target public app on their own store (a normal, low-privilege action), (2) the attacker be able to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers alongside a replayed legitimate body/HMAC pair. No `api_secret_key`, access token, or TLS interception is needed — the attacker legitimately receives the signed body via their own store's webhook delivery. This is a realistic, low-effort attack path for any app author whose webhook handler logic branches on `shop`/`topic` from `WebhookMetadata`.

### Recommendation
- Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable content (or otherwise cryptographically bind them to the payload) so that `HmacValidator.validate` fails if any of these are tampered with or replayed under a different shop context.
- Short of a signature scheme change, cross-check the webhook's `shop` header against the shop associated with the specific `webhook_id`/subscription on record (fetched via the Admin API) before dispatching to handlers, rather than trusting the header value directly.
- Document for gem consumers that `request.shop`/`request.topic` are **not** authenticated by the HMAC check and must not be used as an authorization boundary without additional verification.

### Proof of Concept
1. Attacker creates a Shopify development store and installs the vulnerable public app, receiving genuine webhook deliveries signed with the app's `api_secret_key` (e.g., for `orders/create`).
2. Attacker's store triggers an event so Shopify sends: headers `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, plus `raw_body`.
3. Attacker replays this exact `raw_body` and `x-shopify-hmac-sha256` value to the same app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged `shop` header; [5](#0-4) 
`Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because only `@raw_body` is verified; [6](#0-5) 
the handler is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`, even though the signed body originated from the attacker's own store. [7](#0-6)
