### Title
Webhook HMAC signature does not bind the `shop-domain` or `topic` headers, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` directly from unauthenticated HTTP headers, while `to_signable_string` — the value that is actually HMAC-verified — returns only the raw request body: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it against the `hmac-sha256` header: [2](#0-1) 

`Registry.process` only checks this body-only HMAC before dispatching to the handler with the caller-supplied, unauthenticated `shop` and `topic` values: [3](#0-2) 

This breaks the identity binding: `HMAC(secret, body) == signature` is verified, but the equality that the host application actually relies on — `shop header == tenant that produced this body` — is never checked. Because the shop/topic headers sit outside the signed payload, any two independent (`body`, `hmac`) pairs that are valid for the *same app* (e.g. two webhooks legitimately delivered to two different shop installations of the same app, or a replay across topics) can have their `shop-domain`/`topic` headers swapped without invalidating the HMAC.

### Impact Explanation
An attacker who controls (or can observe/replay) a genuinely-signed webhook body for one shop can present it to the app's webhook endpoint with a different `shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` will accept it (the body-only HMAC still matches) and hand the handler a `WebhookMetadata` claiming to be from a different, arbitrary shop — see `data.shop` passed straight through: [4](#0-3)  . Host applications key their persistence and business logic off `data.shop` (as documented), so this allows cross-tenant data injection/corruption without needing the app's `client_secret`, an access token, or any privileged account — meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitability depends on the attacker being able to obtain at least one valid `(raw_body, hmac)` pair for the target app (e.g., from their own shop's legitimate webhook traffic, which is visible to them as the receiving merchant/developer). No secret material is required to forge the pairing itself — only reuse/replay of an already-valid signature with substituted header values, since the signed payload never included the shop or topic in the first place.

### Recommendation
Include the tenant-identifying fields (`shop-domain`, and ideally `topic`/`webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body before `Registry.process` dispatches to a handler. Failing that, document loudly that `data.shop`/`data.topic` are not authenticated by the gem's HMAC check and must not be trusted as tenant identifiers by the host application.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; attacker (an unprivileged party who can observe/receive genuine webhook traffic for shop A, e.g. as a developer/merchant of their own installation) captures a valid webhook delivery: `raw_body = '{"id":1,...}'`, header `x-shopify-hmac-sha256 = HMAC(secret, raw_body)`, `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker resends the identical `raw_body` and `hmac` header to the app's webhook endpoint but sets `x-shopify-shop-domain: shop-victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes `HMAC(secret, raw_body)` — passes.
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: "shop-victim.myshopify.com", body: ...)` and processes it as if `shop-victim` sent this data, even though `shop-victim` never produced it.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
