### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` field that identifies the tenant is read from an unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands the header-derived `shop` value straight to the app's webhook handler as trusted tenant identity, without ever binding it to the signed bytes.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

The `shop` accessor is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which plays no part in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then immediately forwards `request.shop` to the registered handler as the authoritative tenant identity, with no additional check that the header matches the body or any other signed value: [3](#0-2) 

`HmacValidator.validate` only ever calls `verifiable_query.to_signable_string`, so whatever `to_signable_string` omits is never cryptographically bound to the caller's shop claim: [4](#0-3) 

The identity-binding break, stated as an equality that the gem fails to enforce:
`HMAC-covered bytes (raw_body signed with api_secret_key)` ≠ `shop claim acted upon (shopify-shop-domain header, unsigned)`.

Because a single app's `api_secret_key` is shared across every shop that installs the app, any merchant who has legitimately installed the app (an unprivileged internet user with respect to *other* tenants of the same app) can trigger a webhook event in their own store to obtain a body + valid HMAC pair signed with the app's real secret. They can then replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will pass (the body/HMAC pair is genuinely valid), and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, `body` unchanged.

### Impact Explanation
This breaks the shop-authentication guarantee that host applications rely on `ShopifyAPI::Webhooks` to provide: any app logic that uses `WebhookMetadata#shop` to look up the tenant's stored access token/session, write to the tenant's data, or make authenticated API calls on the tenant's behalf can be tricked into acting as if the event originated from a different shop. This is a cross-tenant access vector reachable by an unprivileged multi-tenant user of the same app (no access token, secret, or privileged account required), matching the "cross-tenant access" Critical/High impact category.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the target app on their own store (a normal, unprivileged action any merchant can take) and trigger any webhook-eligible event, then replay the resulting body/HMAC pair with a forged shop-domain header to the app's public webhook endpoint. No secrets, tokens, or elevated privileges are required, and the flaw is inherent to how `ShopifyAPI::Webhooks::Request`/`Registry` construct and trust the `shop` field.

### Recommendation
Do not treat the `shop`/`shop-domain` header as trusted tenant identity on its own. Either include the shop domain (and ideally webhook id / topic) inside the HMAC-signed payload check, or require host applications to cross-validate `WebhookMetadata#shop` against an independently known, previously-registered shop record (e.g. reject the webhook if the shop-domain header does not match a shop that this specific app installation actually owns) before using it to key any tenant-scoped data or credentials.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and legitimately receives a webhook delivery, e.g. for `orders/create`, with body `B` and a valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because the body is unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`, per `lib/shopify_api/utils/hmac_validator.rb:12-22` and `lib/shopify_api/webhooks/request.rb:35-38`.
4. The registered handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` (per `lib/shopify_api/webhooks/registry.rb:198-199`), even though the event body actually originated from the attacker's own shop, letting the attacker inject/impersonate webhook traffic attributed to a shop they do not control.
