### Title
Solvers can be defrauded via a malicious input token in `IntentGatewayV2` orders — `safeTransfer` on a fake ERC-20 gives no indication of a failed release - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2.placeOrder` lets any unprivileged caller specify arbitrary ERC-20 addresses for the escrowed input tokens [1](#0-0) . When a solver later fills the order, the escrowed input is released to the solver via `IERC20(token).safeTransfer(beneficiary, amount)` in `_withdraw` [2](#0-1) . If the order creator supplies a crafted token contract that has code (so it passes `SafeERC20`'s `codesize` check) but implements no real `transfer`/`transferFrom` logic — only a non-reverting `fallback()` plus a `balanceOf()` that lies to defeat the gateway's balance-diff accounting — the release call returns success with empty returndata even though no value moves, exactly the failure mode described in the external report for `ICHI`/`IIchiV2`.

### Finding Description
- `placeOrder` computes the actual escrowed amount for a non-predispatch input by diffing `balanceOf(address(this))` before and after `safeTransferFrom`: [3](#0-2) . A malicious token contract can implement `balanceOf` to report an increasing fake balance on each call (independent of any real transfer), so the gateway records a non-zero "escrowed" `order.inputs[i].amount` for a token that never actually moved any value into the contract, and `transferFrom`/`transfer` on that same contract can be a no-op reached only through a non-reverting fallback (returns empty returndata, success=true).
- `IntentsBase._withdraw`, used by both same-chain fills (`IntrinsicIntents._fillSameChain` → `_withdraw`) and cross-chain redemptions, releases the "escrowed" input to the filler using `SafeERC20.safeTransfer` without any check that the call actually performed a state-changing transfer: [4](#0-3) .
- Because `SafeERC20.safeTransfer` only reverts if the call itself reverts or (when returndata is non-empty) decodes to `false`, a target with code but a permissive fallback and no real `transfer` logic satisfies all of `SafeERC20`'s checks while transferring nothing — the exact scenario the external report describes for `IIchiV2`/`safeTransfer`.
- A solver has no visibility into whether the input-token release actually succeeded; `fillOrder` unconditionally provides its real output tokens to the beneficiary in `_fillSameChain` before `_withdraw` runs [5](#0-4) , so the solver's genuine assets leave its control while the "compensating" escrow transfer to the solver silently no-ops.

### Impact Explanation
A solver that fills an order believing the escrowed input token is genuine ERC-20 value provides its own real output tokens to the beneficiary, but receives nothing back because the input-token release silently "succeeds" without transferring value. This is a direct, permissionless theft vector against any unprivileged solver interacting with `IntentGatewayV2`, satisfying "concrete theft ... of funds."

### Likelihood Explanation
Any user can call `placeOrder` with a token address of their choosing — this requires no privileged role, governance action, or admin compromise. The only requirement is that a solver chooses to fill such an order without independently verifying the input token's transfer semantics, which is a realistic scenario for automated/bot solvers scanning on-chain order books for profitable fills.

### Recommendation
Do not trust the pre/post `balanceOf` diff alone to establish that a real transfer occurred, and do not rely solely on `SafeERC20`'s optional-return handling for tokens that are entirely attacker-supplied. Consider: (1) requiring solvers to pre-approve/allowlist acceptable input tokens, (2) verifying with a low-level call that the target actually exposes `transfer`/`transferFrom` with the expected selector and non-trivial bytecode behavior, or (3) re-checking the destination balance actually increased by the expected amount immediately after the `safeTransfer` in `_withdraw`, reverting otherwise.

### Proof of Concept
1. Attacker deploys a "token" contract `EvilToken` with: a `balanceOf(address)` that returns `block.timestamp` (or an incrementing counter) regardless of any real transfer, and a bare `fallback() external {}` (no `transfer`/`transferFrom` implementation).
2. Attacker calls `IntentGatewayV2.placeOrder` with `order.inputs[0].token = EvilToken`, `amount = X`, and a legitimate desired `output` token/amount.
3. In `placeOrder`, `balBefore`/`balAfter` diff via `EvilToken.balanceOf` reports `X` as "received," even though `safeTransferFrom` to the gateway performed no real transfer (hits `EvilToken`'s fallback, returns empty data, `SafeERC20` treats it as success): [3](#0-2) .
4. A solver observes the order, calls `fillOrder`, and sends real output tokens to the beneficiary in `_fillSameChain`: [6](#0-5) .
5. `_withdraw` attempts to pay the solver the "escrowed" `EvilToken` amount via `safeTransfer`, which again hits the fallback and returns success without moving any value: [2](#0-1) .
6. The solver has permanently lost its real output tokens for a worthless "confirmed" transfer of `EvilToken`.
