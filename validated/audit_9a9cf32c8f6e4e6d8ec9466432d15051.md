This confirms the vulnerability class. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (which signs/verifies `to_signable_string`, i.e. the body only) and then dispatches the handler using `request.topic` and passes `request.shop` straight into `WebhookMetadata` without any cross-check against the body or the HMAC [3](#0-2) .

### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by the HMAC, allowing forged shop attribution on a validly-signed body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that the app relies on to route and attribute the webhook to a tenant are taken from HTTP headers that are never included in the signed payload.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field [4](#0-3) . For webhooks, `to_signable_string` is defined as simply `@raw_body` [1](#0-0) . This means the equality actually being checked is:

`HMAC(secret, raw_body) == received_hmac`

but the equality the app *needs* to hold before trusting `request.shop` as the tenant that produced this event is:

`shop header == shop that Shopify actually signed this body for`

That second equality is never checked anywhere — `shop`, `topic`, `webhook_id`, and `api_version` are read directly off attacker-controllable headers [2](#0-1) , and `Registry.process` uses `request.shop` and `request.topic` to route to a handler and build `WebhookMetadata` immediately after the body-only HMAC check passes [5](#0-4) .

Because Shopify signs the same raw JSON body for identically-shaped payloads regardless of shop (e.g. a `shop/redact` or `app/uninstalled` payload can have an identical or attacker-reproducible body/shape across shops), and the header fields are entirely outside the signature, a party who can obtain one genuine `(raw_body, hmac)` pair signed with the app's `client_secret` (e.g. by installing the app on their own test/trial shop and capturing the webhook their own store legitimately receives) can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` will still return `true` because it never inspected the header at all, and the handler will process the event as if it originated from the victim shop.

### Impact Explanation
This breaks the tenant-isolation boundary the HMAC is supposed to provide: an unprivileged internet user who legitimately installed the app on any shop (including their own) can forge webhook deliveries attributed to a different merchant's shop domain. Depending on the app's webhook handlers, this enables cross-tenant effects such as: triggering `app/uninstalled` cleanup logic for a shop that never uninstalled, triggering `shop/redact` or `customers/redact` (GDPR) data-deletion logic against another merchant's data, or injecting attacker-chosen `webhook_id`/`api_version` values used for idempotency/dedup logic under another shop's identity. This matches the Critical "cross-tenant access" category since the shop-scoping guarantee of the webhook signature is broken.

### Likelihood Explanation
Requires the attacker to be able to obtain at least one genuinely signed webhook body from the app (achievable by installing the app on a shop they control, since webhook bodies for many topics are attacker-influenced or predictable in shape) and to be able to send arbitrary HTTP requests (with arbitrary headers) to the app's public webhook receiving endpoint, which is inherent to how webhook endpoints work (they must accept unauthenticated POSTs and rely solely on the HMAC for trust). No access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` header values into the signed payload verification — e.g. include them in `to_signable_string` (Shopify's actual HMAC only covers the body per their spec, so instead the app-side check should independently re-derive/authenticate `shop` from a source that is cryptographically tied to the request, or compare the header `shop` against a previously known/authorized shop record before trusting it) and reject processing if headers were altered post-signing. At minimum, document and enforce that consumers of `WebhookMetadata.shop` must not use it for privileged, cross-tenant-sensitive actions without an additional authenticated lookup (e.g., confirming the shop has an active, matching session/webhook registration) rather than trusting the header value directly.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `app/uninstalled`) to their own controlled endpoint, capturing the raw body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify computed with the app's real `client_secret`.
2. Attacker sends a POST to the victim app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, since HMAC is computed only over `B`), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and (optionally) a chosen `X-Shopify-Topic`/`X-Shopify-Webhook-Id`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and finds it matches `H` [6](#0-5) , so validation passes.
4. The registered handler for that topic is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...)` [7](#0-6) , causing the app to perform shop-scoped actions against the victim shop's data despite the payload never having been signed for that shop.
