### Title
Webhook `shop` (tenant) identity is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. The `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` values used downstream by the host application's webhook handler come from HTTP headers that are excluded from the HMAC-signed content, so they can be freely rewritten by anyone who can produce a validly-signed body.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated headers: [2](#0-1) 

`Registry.process` verifies only the HMAC of that signable string (the body) before dispatching: [3](#0-2) 

The `HmacValidator` computes and compares the signature using `verifiable_query.to_signable_string` (the raw body only) against the app's shared `Context.api_secret_key`: [4](#0-3) 

Because `api_secret_key` is a single secret shared by the app across **all** installing shops (it is not per-tenant), any party who can obtain one validly-signed webhook body/HMAC pair for their own shop (e.g., by installing the app on their own store and receiving a genuine webhook) can replay that exact body+HMAC while substituting the `x-shopify-shop-domain` (and `topic`/`webhook_id`/`api_version`) headers to any value. `Utils::HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will forward the attacker-chosen `shop` value straight into `WebhookMetadata` handed to the host application's handler as the authenticated tenant identity: [5](#0-4) 

This breaks the intended identity binding: **shop authenticated by the HMAC ≠ shop attributed to the event and trusted by the handler as the tenant key**.

### Impact Explanation
This enables cross-tenant impersonation: an attacker with legitimate (even unprivileged, single-tenant) access to the app can cause the host application to process webhook events under an arbitrary victim shop's identity. Depending on how the host application uses `WebhookMetadata#shop` (commonly used to look up the tenant's session/store record before acting on the payload), this can lead to cross-tenant data corruption or unauthorized actions attributed to another merchant's store — a cross-tenant access impact.

### Likelihood Explanation
Moderate-to-high: exploitation requires only that the attacker control an app installation (a single legitimate tenant) capable of receiving at least one real webhook, and control of the HTTP request to the app's webhook endpoint (headers are fully attacker-modifiable when replaying/crafting the request, since the transport is a plain HTTP POST authenticated only by the HMAC/body pair). No access token or `client_secret` disclosure is required.

### Recommendation
Include the tenant-identifying headers (`shop`, and ideally `topic`/`webhook_id`) in the HMAC-signed content, or otherwise cryptographically bind them to the body before `Registry.process` trusts them, so that `Utils::HmacValidator.validate` fails whenever any of these attacker-controllable fields are altered relative to what was originally signed by Shopify.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker (or any party with network access to the app's webhook endpoint) sends a new POST to the webhook endpoint with the same body `B` and the same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`.
4. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim.myshopify.com", ...)`, causing the host application to process the payload as if it legitimately originated from `victim.myshopify.com`.
