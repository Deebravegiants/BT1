### Title
Webhook shop/topic headers are not covered by the HMAC signature, allowing shop impersonation via header substitution - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a given shop once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC is computed only over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by the handler are read from unauthenticated HTTP headers. This breaks the intended binding `hmac == HMAC(secret, body ‖ shop)`; in this gem it is only `hmac == HMAC(secret, body)`, independent of `shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `hmac` is parsed from the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the signature purely from `to_signable_string` (the body) and compares it to the `hmac` header value; it never incorporates `shop`, `topic`, or any other header into the signed material: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC, then immediately trusts `request.shop` (parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header) to build `WebhookMetadata` and dispatch to the registered handler: [4](#0-3) 

Because `shop` is not part of the signed bytes, any party that has observed one valid `(body, hmac)` pair for a webhook topic (e.g., from their own development store, or a publicly-diffable sample payload) can replay that exact body and hmac to a target app's webhook endpoint while substituting the `shop` header for a victim's shop domain. `HmacValidator.validate` still returns `true` (the body and hmac still match), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop — even though the `shop` field was never bound by the HMAC. This is the same class of defect as the reported bug: a field that is acted upon (`active`/here `shop`) is not the field that was actually verified/covered by the authenticator (HMAC).

### Impact Explanation
This allows cross-tenant confusion: a handler built on this gem's documented contract (`data.shop` identifies the shop that the webhook body pertains to) can be made to process attacker-controlled shop attribution for a legitimately-signed body. Depending on what the host app does with `data.shop` (e.g., look up which merchant's records to update, or which access token/session to act with), this can lead to writing another tenant's data into the wrong tenant's records, i.e., cross-tenant access, which is explicitly in the Critical impact bucket for this scope.

### Likelihood Explanation
Exploitation requires no credentials, tokens, or `api_secret_key` knowledge — only one previously observed valid `(body, hmac)` pair for any shop and topic (easily obtained by registering a webhook against one's own store) and the ability to POST to the victim app's public webhook endpoint with a forged `shop` header. This is a realistic unprivileged-internet-user attack path entirely through this gem's own verification logic.

### Recommendation
Bind the shop (and ideally topic) into the material that is HMAC-verified, or otherwise cryptographically tie the shop domain to the signed payload before trusting it in `WebhookMetadata`. At minimum, `Utils::HmacValidator.validate` should be changed so `Webhooks::Request#to_signable_string` also encodes the `shop` (and `topic`) header value, and/or `Registry.process` should cross-check `request.shop` against an independently known/registered shop for the webhook subscription instead of trusting the header verbatim.

### Proof of Concept
1. Register a webhook handler and capture one legitimate webhook delivery for `attacker-shop.myshopify.com` — note the raw body and the `x-shopify-hmac-sha256` header value (both are attacker-obtainable since the attacker owns that shop).
2. POST the same raw body and the same `x-shopify-hmac-sha256` value to the victim app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; since the check is `HMAC(secret, body) == hmac_header`, it succeeds regardless of the shop header value: [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the body/hmac pair was minted for `attacker-shop.myshopify.com`, causing the host application to attribute the payload to the wrong tenant.
