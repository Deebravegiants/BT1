### Title
Unbounded recursive `RuntimeCall` decode in `hyper-fungible-token::on_accept` enables relayer/attacker-triggered node crash (DoS) - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The ZoneMinder CVE's root cause is that an unauthenticated PHP endpoint deserializes user-controlled data into an arbitrary object graph without validating its structure, letting the attacker craft a payload the deserializer cannot safely handle, resulting in DoS/RCE. The direct analog here is `on_accept` in the `hyper-fungible-token` pallet's ISMP module, which decodes an attacker-supplied, recursively-defined `RuntimeCall` type from cross-chain message payload using `Decode::decode` with no depth limit, unlike the sibling `call-decompressor` pallet, which explicitly guards the same decode with `decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, ..)` [3](#0-2) .

### Finding Description
`SendParams::call_data` is optional attacker-supplied bytes accepted at the point a user initiates a cross-chain transfer [1](#0-0) . These bytes are packed into `Message.data` (an ABI-encoded struct shared with the Solidity side) and delivered to the destination chain as the body of an ISMP `PostRequest`. On the receiving side, `IsmpModule::on_accept` for the HFT pallet does:

- `Message::abi_decode(&body)` to recover `message.data`.
- `SubstrateCalldata::decode(&mut &message.data[..])` to recover `runtime_call: Vec<u8>` [4](#0-3) .
- `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` — a **plain** SCALE `Decode::decode` call with no depth limit — to recover the call to dispatch [5](#0-4) .

`RuntimeCall` in a Substrate runtime is a deeply recursive enum (e.g. `pallet_utility::Call::batch`/`batch_all`/`as_derivative` wraps `Box<RuntimeCall>` or `Vec<RuntimeCall>`). SCALE's default `Decode` implementation recurses once per nesting level with no built-in bound; this is exactly why the codebase's own `call-decompressor` pallet was hardened to call `decode_all_with_depth_limit` instead of a bare `decode` for the structurally identical operation (decoding and dispatching an attacker/relayer-supplied `RuntimeCall`) [6](#0-5) . The HFT module's decode of `substrate_data.runtime_call` was not given the same treatment, so a message with a sufficiently deeply nested call type (e.g. thousands of nested `Utility::batch` wrappers) drives the decoder into unbounded recursion, exhausting stack and crashing the collator/full node — a Substrate-node DoS. This is analogous to the ZoneMinder bug in that the destination pallet deserializes attacker-controlled, type-directed data into a complex object graph (a dispatchable call tree) without bounding its structure before doing so.

The pre-existing signature check and `BaseCallFilter` check [7](#0-6)  occur **after** or independent of the vulnerable decode step — the crash happens inside `T::RuntimeCall::decode` itself, before any authorization or filtering logic runs, so neither mitigates it.

### Impact Explanation
Any account that can send a `PostRequest` recognized by the HFT module — i.e., any user of a source-chain `HyperFungibleToken`/`WrappedHyperFungibleToken` contract that is registered via `ContractToAsset` — can set `call_data` to a maliciously deep, recursively-nested SCALE-encoded `RuntimeCall`. When a relayer delivers this message (relayers are typically permissionless/unprivileged bandwidth purchasers), every full node/collator that processes the ISMP `handle`/`handle_unsigned` call executing `on_accept` for this message will attempt the unbounded decode and can crash or hang, taking down block production/finality for the chain running the pallet — a network-wide DoS reachable from a single relayed message, satisfying "a route unable to deliver messages" / permanent disruption criteria.

### Likelihood Explanation
High. No special privilege is needed beyond being able to initiate a normal HFT cross-chain transfer with non-empty `call_data`, and having any relayer deliver the resulting message (relayers are economically incentivized to deliver any valid, fee-paying message, which is the intended trust model). The vulnerable code path is on the "happy path" of `on_accept`, executed automatically once the request is authenticated by source/`from` mapping — no admin or governance action is required to trigger it.

### Recommendation
Replace the plain `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` in `on_accept` [5](#0-4)  with a depth-limited decode, mirroring the pattern already used in `call-decompressor::decode_and_execute` (`decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, ..)`) [3](#0-2) , and reject calls exceeding the configured limit before any recursive decoding begins. Additionally consider bounding `SubstrateCalldata::runtime_call`'s raw byte length at the SCALE-decode boundary (similar to the existing `ByteVector` length-checked decode pattern [8](#0-7) ) so a message cannot smuggle an oversized calldata blob in the first place.

### Proof of Concept
1. On the source EVM chain, call the HFT contract's send/transfer function with `call_data` set to the SCALE encoding of a `RuntimeCall::Utility(pallet_utility::Call::batch { calls: vec![RuntimeCall::Utility(pallet_utility::Call::batch { calls: vec![ ... nested thousands of times ... ] }) ] })` (or any recursive `RuntimeCall` variant available in the destination runtime, e.g. `Utility::as_derivative`/`batch_all`), wrapped in a `SubstrateCalldata { signature: None, runtime_call: <nested bytes> }`, itself wrapped as `message.data`.
2. Have any relayer submit the resulting ISMP `PostRequest` with a valid consensus/membership proof to the destination chain's `pallet-ismp` `handle`/`handle_unsigned` extrinsic.
3. During processing, `Pallet::<T>::on_accept` calls `T::RuntimeCall::decode` on the crafted bytes; because there is no depth limit, the decoder recurses until it overflows the node's stack, crashing the node process handling the extrinsic (and any other node/collator that later re-executes the same block/extrinsic).

Note: the exact stack-overflow threshold (number of nesting levels) depends on the concrete `RuntimeCall` type size and the runtime's stack configuration, and was not empirically measured here — this would need to be validated in an actual test runtime to confirm the practical byte size needed to trigger the crash.
