### Title
`describeWithdrawal` misattributes withdrawal status/tx-hash across batch entries sharing the same `assetId` - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` and its `findMatchingWithdrawal` helper resolve which withdrawal record from the POA bridge API corresponds to a given `WithdrawalIdentifier` by matching `assetId` (via `near_token_id`) only, ignoring `index` and `destinationAddress`/`amount`. When a batch (`withdrawalParams[]` passed to `IntentsSDK.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises`) contains two withdrawals of the same asset to different destinations, both indices resolve to whichever matching record `Array.prototype.find` returns first, silently misreporting one withdrawal's completion status and destination tx hash as belonging to the wrong index.

### Finding Description
The documented invariant from the README/RFC is `promises[i]` corresponds to `withdrawalParams[i]`, i.e., the equality:

`describeWithdrawal(wid for index i).txHash == the on-chain outcome of withdrawalParams[i]`

is expected to hold for each `i` independently.

The code path is:
1. `IntentsSDK.createWithdrawalCompletionPromises` (`packages/intents-sdk/src/sdk.ts:557-608`) builds one `WithdrawalIdentifier` per array element via `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`), which sets `wid.index` as a per-bridge-route counter and stores the corresponding `withdrawalParams[i]` on the `wid`.
2. Each promise calls `watchWithdrawal` → `bridge.describeWithdrawal(wid)` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:20-78`).
3. `PoaBridge.describeWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`) calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` (lines 318-322), explicitly commented: *"Response list is unsorted, so we match by assetId instead of index."*
4. `findMatchingWithdrawal` (lines 418-427) does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — it returns the **first** API record whose asset matches, with no consideration of `destinationAddress`, `amount`, or `index`. The code's own NOTE comment (lines 409-416) states: *"multiple withdrawals of the same token in a single transaction are not supported."*

The identical unguarded pattern also exists in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts:144-153` (`findMatchingWithdrawal` there too matches by `assetId` only).

Nothing upstream prevents the attacker precondition. `Bridge.validateWithdrawal` (called per-withdrawal in `createWithdrawalIntents`, `packages/intents-sdk/src/sdk.ts:334-372`) validates a single withdrawal's constraints (min amount, trustlines) and has no cross-batch duplicate-`assetId` check. `createWithdrawalIdentifiers` only tracks a bridge-route index counter (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) and does not reject duplicate `assetId` entries. There is no `compareAddresses`/`matchesRequest` style check between the API's returned `address`/`amount` and the specific `withdrawalParams[i].destinationAddress`/`amount` before returning a match.

Attacker input: any unprivileged caller that controls `withdrawalParams` for a batch (a NEAR Intents user withdrawing to two different addresses of the same token in one batched intent) supplies `withdrawalParams = [{assetId: X, destinationAddress: A, amount: a1}, {assetId: X, destinationAddress: B, amount: a2}]`. When the POA bridge processes both legs and the SDK polls `describeWithdrawal` for index 0 and index 1, both calls query the same `getWithdrawalStatus` response list and `findMatchingWithdrawal` returns the same first-matching record (or, if the underlying `Array.prototype.find` returns different records at different polling times as the API list grows, an incorrect record) for both indices, so `promises[0]` and `promises[1]` can both resolve to the record actually belonging to the other index.

### Impact Explanation
An integrator relying on `sdk.waitForWithdrawalCompletion({ withdrawalParams, intentTx })` or `sdk.createWithdrawalCompletionPromises(...)` to credit/refund a user based on `(status, txHash)` per index can credit withdrawal `i` with the transfer tx hash and completion status that actually belongs to withdrawal `j` (different destination). This can cause a double-credit (crediting the same destination twice while the other legitimate withdrawal is left unaccounted) or a completed withdrawal being reported as unresolved/failed for the wrong recipient. This matches the "High" severity category: *"a status or hash misreport making an integrator credit or refund twice."* It is repeatable any time a batch contains ≥2 withdrawals of the same `assetId` to different destinations — which is an ordinary, permitted usage pattern (the SDK's own batch withdrawal feature explicitly supports multiple entries with the same `assetId`, e.g. a user splitting one token to two destinations).

### Likelihood Explanation
Precondition: the batch `withdrawalParams` contains two or more entries with the same `assetId` but different `destinationAddress`/`amount` — nothing in the SDK API rejects this; it is explicitly a supported, common shape of batch withdrawals (the "Batch Withdrawals" feature is documented for withdrawing different assets, but nothing stops an ordinary user/integrator from submitting the same asset twice to two destinations). Attacker cost is zero beyond crafting two array entries; the flaw is deterministic and acknowledged by the code's own NOTE and inline comment. It is triggerable on every occurrence of this batch shape, not just once.

### Recommendation
In `findMatchingWithdrawal` (both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`), disambiguate matches by also comparing `destinationAddress` (and ideally `amount`) against the API record's `address`/`amount` fields, and track already-consumed records per `describeWithdrawal` call sequence (e.g., match by `assetId` + `destinationAddress`, falling back to sorted-by-amount pairing only when addresses collide too, as the existing NOTE comment suggests). At minimum, when multiple withdrawals of the same `assetId` exist in a batch and `destinationAddress` differs, refuse to silently pick the first match — throw/return `pending` until a unique match can be established, rather than returning a possibly-wrong record.

type WithdrawalStatusResponse = Awaited<
	ReturnType<typeof poaBridge.httpClient.getWithdrawalStatus>
>;

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
