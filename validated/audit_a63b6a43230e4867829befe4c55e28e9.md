### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw HTTP body only, while the `shop` value dispatched to app handlers is read straight from the unauthenticated `shopify-shop-domain` HTTP header. The HMAC therefore binds `secret == body`, not `secret == (body, shop)`. Any actor able to produce or replay a body/HMAC pair valid for one tenant can attach an arbitrary `shop-domain` header and have `Registry.process` deliver that payload to the app's webhook handler tagged with a different, attacker-chosen shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` (the raw body) and the app's secret — it never incorporates the shop header: [4](#0-3) 

The broken identity-binding equality is:
`shop authenticated by HMAC (implicitly, whichever tenant's body/secret produced a valid signature) != shop attributed to the delivered event (`request.shop`, taken from an unauthenticated header)`.

Because the header is outside the HMAC's scope, the value returned by `request.shop` can be modified after a valid `(body, hmac)` pair is obtained, without invalidating the HMAC check, and the handler still receives it as the authoritative shop for that event.

### Impact Explanation
This is a cross-tenant identity confusion in exactly the sense flagged by the rules: a field (`shop-domain` header) that is acted upon (used to build `WebhookMetadata#shop`, typically used by host apps to look up per-tenant credentials/records) is not covered by the authentication primitive (HMAC) that is supposed to prove the payload's authenticity/origin. A host application that trusts `WebhookMetadata#shop` as an authenticated tenant identifier (which the gem's own `Webhooks::Request`/`Registry` design encourages, since it delivers `shop` alongside HMAC-validated data) can be made to apply one tenant's webhook payload (e.g., `orders/create`, `app/uninstalled`) to a different tenant's stored session/state, i.e., cross-tenant access to/modification of another merchant's data through this gem's webhook processing pipeline.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair — achievable trivially by an app's own installed shop (a legitimate, unprivileged merchant) triggering a real webhook for its own store, since Shopify only signs the body and not the shop header. That merchant can then resend the identical body/HMAC to the app's webhook endpoint with a different `shop-domain` header value. No access to `api_secret_key` or another tenant's credentials is needed — only a normal webhook delivery already receivable by any app-installing merchant.

### Recommendation
Include the shop (and other identity-relevant headers) as part of the value bound to the HMAC check, or otherwise verify that `request.shop` corresponds to a shop actually authorized/known to the app before dispatching to handlers, e.g.:
```diff
- def to_signable_string
-   @raw_body
- end
+ def to_signable_string
+   "#{shop}\n#{@raw_body}"
+ end
```
and document that consuming apps must not treat `WebhookMetadata#shop` as authenticated unless the gem itself binds it into the signature check.

### Proof of Concept
1. App's own test shop `attacker.myshopify.com` triggers an `orders/create` webhook. Shopify sends `raw_body = B`, `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker (the merchant who owns `attacker.myshopify.com`) captures this request and resends it to the app's webhook endpoint, keeping `raw_body = B` and the same HMAC header, but replacing `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates fine because it only checks `HMAC(secret, B)` against `B`, independent of the shop header: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(... , shop: "victim.myshopify.com", body: parsed(B), ...)` — data legitimately generated for `attacker.myshopify.com` is now attributed to `victim.myshopify.com`.
