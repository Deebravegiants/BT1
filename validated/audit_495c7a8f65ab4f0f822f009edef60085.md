### Title
`TendermintEvmStateMachine::verify_membership` proves against the wrong IAVL key (unhashed slot), permanently blocking message delivery from Tendermint/Ethermint-style state machines - (File: modules/ismp/state-machines/evm/src/tendermint.rs)

### Summary
`verify_membership` is the sibling check to `verify_non_membership` and `verify_evm_kv_proofs`/`verify_state_proof` in the same file, all of which verify ISMP request/response commitments against a Tendermint/Ethermint-style consensus state's app hash via ICS23 merkle proofs over an IAVL tree. The non-membership and state-proof paths correctly keccak256-hash the 32-byte EVM storage slot before folding it into the IAVL key (`prefix || address || keccak256(slot)`), as documented inline. `verify_membership` alone skips this hashing step and builds the IAVL key from the raw, unhashed slot — exactly analogous to the reported bug class where a validity check is performed against the wrong target (`_ens.nic.<tld>` instead of the root TLD): here the membership check is performed against a key that "never exists in the tree" instead of the key that actually backs the commitment.

### Finding Description
In `TendermintEvmStateMachine::verify_membership` (lines 99–151), the per-commitment loop computes the ICS23 path directly from the raw slot returned by `commitment_state_trie_key`:
```
let key = storage_key_for(
    proof.height.id.state_id,
    &contract_address.0,
    slot.clone().try_into().map_err(|_| TendermintEvmError::UnsupportedKeyLength)?,
);
```
No `keccak256` is applied to `slot` here. Contrast this with `verify_non_membership` (lines 209–221) and `verify_evm_kv_proofs` (lines 301–310), which both explicitly compute `let hashed_slot = ICS23HostFunctions::keccak256(&slot).0;` before calling `storage_key_for`, with comments stating that Ethermint-style Tendermint EVM stores only expose storage under `prefix || address || keccak256(slot)`, and that using the unhashed slot "resolves to a key that never exists in the tree."

Because `commitment_state_trie_key` (line 153–157) returns `keccak256(commitment)` (the ISMP commitment key derivation), that value is treated by `verify_membership` as the raw EVM storage slot — the same value the fixed sibling paths additionally hash a second time before building the trie path. `verify_membership` skips that second hash, so the constructed IAVL path targets a location distinct from where the value genuinely lives on an Ethermint-style chain.

### Impact Explanation
Since the on-chain data for `_commitments[commitment]` on an Ethermint-style EVM host is only ever stored under the correctly-hashed IAVL key, no genuine ICS23 membership proof can exist for the wrong (unhashed) key that `verify_membership` constructs. A correct, honestly-generated relayer proof for a real, finalized `PostRequest`/`PostResponse` commitment will therefore fail merkle verification against the app hash every time `handleMessages`/`update_client`-derived membership checks are exercised for a Tendermint/Ethermint (e.g. Sei, or any chain routed through `DefaultEvmKeys`) consensus client. This permanently blocks delivery of ISMP requests/responses whose destination or counterparty state machine is verified via this state-machine client — a "route unable to deliver messages" condition, freezing any funds or actions gated behind successful delivery (e.g., cross-chain token/intents flows) for that route.

### Likelihood Explanation
This triggers on every single relayed message that relies on `verify_membership` for a Tendermint/Ethermint EVM state machine — no adversarial input is needed, an honest relayer submitting a correct proof is guaranteed to fail. This makes the likelihood effectively certain for any deployment routing messages through `TendermintEvmStateMachine`.

### Recommendation
Apply the same `keccak256(slot)` hashing in `verify_membership` that is already applied in `verify_non_membership` and `verify_evm_kv_proofs`, so all three code paths derive the IAVL storage key identically: `let hashed_slot = ICS23HostFunctions::keccak256(&slot).0; let key = storage_key_for(proof.height.id.state_id, &contract_address.0, hashed_slot);`

### Proof of Concept
1. Deploy/point a Tendermint consensus client at an Ethermint-style EVM chain (e.g. Sei) whose ISMP host stores `_commitments[commitment]` under IAVL key `prefix || address || keccak256(slot)`.
2. Have a relayer submit a genuine `PostRequest` whose commitment is finalized in that store, together with a correct ICS23 membership proof for the properly-hashed key.
3. Call the message handler path that invokes `TendermintEvmStateMachine::verify_membership` with this commitment and proof.
4. Observe `merkle_proof.verify_membership` fail with `MerkleProofVerificationFailed`, because `key` was built from the raw (unhashed) slot rather than `keccak256(slot)`, so it does not match any real leaf in the IAVL tree — even though the same commitment and proof format succeed against the hashed key when run through `verify_evm_kv_proofs`/`verify_non_membership`.
