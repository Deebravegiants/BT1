This confirms the vulnerability. The `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed bytes [2](#0-1) . `Registry.process` validates HMAC over `request` (i.e., over the raw body only) and then passes `request.shop` straight into the handler as the tenant identifier [3](#0-2) .

### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body [4](#0-3) . The tenant-identifying field, `shop`, is read from the `shopify-shop-domain` header and is never included in the HMAC-signed material, since `to_signable_string` only returns `@raw_body` [5](#0-4) . The gem still forwards this unauthenticated `shop` value to the host application's handler as `WebhookMetadata#shop` [6](#0-5) .

### Finding Description
The binding that should hold is: `hmac_signed_bytes == bytes_that_determine_the_tenant_acted_upon`. In this gem, `hmac_signed_bytes = raw_body` only (`Request#to_signable_string` at [1](#0-0) ), whereas `bytes_that_determine_the_tenant_acted_upon = headers["shopify-shop-domain"]` (`Request#shop` at [2](#0-1) ). These are disjoint byte ranges of the HTTP request. `HmacValidator.validate` only recomputes and compares the HMAC over `verifiable_query.to_signable_string`, i.e. the body [7](#0-6) . Because a valid HMAC only proves "Shopify sent this exact body," and says nothing about which shop the body pertains to, any party capable of producing a body/HMAC pair valid for the app's `client_secret` (e.g., an attacker who owns/controls a shop that is genuinely subscribed to the app's webhooks, or who otherwise obtains one authentic body+HMAC pair for a topic with attacker-controllable/replayable body content) can present that same authentic body+HMAC together with an arbitrary `shopify-shop-domain` header naming a different, victim shop. `Registry.process` will accept it as authentic and dispatch it to the handler labeled with the attacker-chosen `shop` [3](#0-2) .

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce: the docs tell integrators that `Registry.process` "will verify the request did indeed come from Shopify" before invoking their handler [8](#0-7) , implying the whole `WebhookMetadata` (including `shop`) is trustworthy. Host applications that key merchant data updates, deletions, or session lookups off `WebhookMetadata#shop` without independent verification would perform cross-tenant writes/reads driven by attacker-chosen shop values, despite a "successfully validated" HMAC. This matches the report's underlying bug class: a value that participates in a downstream authorization/identity decision is not covered by the integrity check that is supposed to authenticate the whole message.

### Likelihood Explanation
Exploitability is bounded by needing a body+HMAC pair that is valid for the target app's webhook subscription. This is trivially achievable by any merchant who has legitimately installed the app and is thus a recipient of genuine webhooks for their own shop — a webhook payload with attacker-influenced/malleable body content (e.g., topics with attacker-supplied fields, or simply replaying the exact bytes of an already-received webhook) paired with a forged `shopify-shop-domain` header is sufficient, since only the body is authenticated. This requires no access to the `client_secret`, no privileged account beyond ordinary shop-owner-level webhook receipt, and no host-application misuse beyond following the gem's own documented API.

### Recommendation
Either (a) include the `shop` (and ideally `topic`, `webhook-id`) header values in the signed material checked by `HmacValidator`, which is not possible since Shopify itself only signs the body — so instead, (b) have `Registry.process`/`WebhookMetadata` treat `request.shop` as merely a hint and require host applications to cross-check it against the shop domain of the merchant's own stored, authenticated session/install record before acting, and document this explicitly; alternatively, expose a helper that validates `request.shop` against the caller-provided expected shop before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and receives a genuine webhook, e.g. `orders/create` with body `{}` and a correct `x-shopify-hmac-sha256` computed by Shopify over that body using the app's `client_secret`.
2. Attacker replays this exact `raw_body` and `hmac` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers and `Utils::HmacValidator.validate` succeeds because it only checks the body/HMAC pair [9](#0-8) .
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` [6](#0-5) , and any host logic trusting this field acts on the victim's tenant using attacker-supplied data.
