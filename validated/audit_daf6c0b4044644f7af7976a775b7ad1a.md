### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on otherwise-authentic webhook deliveries - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` only ever proves the integrity of the body bytes, never of the `shop`, `topic`, `api_version`, or `webhook_id` values that are read straight from HTTP headers [2](#0-1) . `Registry.process` accepts the request once the body HMAC checks out and then forwards the header-derived, unauthenticated `request.shop` value straight into `WebhookMetadata` for the app's handler to act on [3](#0-2) . This is exactly the bug class in the report: a field ("shop") is acted upon by the tenant-scoping logic but is not bound by the cryptographic check ("HMAC") that is supposed to authenticate the message.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` supplied by the caller [4](#0-3) . For OAuth callbacks, `AuthQuery#to_signable_string` correctly folds `code`, `host`, `shop`, `state`, and `timestamp` into the signed string [5](#0-4) , so `shop` is bound to the signature there.

For webhooks, however, `Request#to_signable_string` returns `@raw_body` only [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that Shopify sends unsigned alongside the request [2](#0-1) [6](#0-5) . `Registry.process` validates only the body's HMAC and then trusts `request.shop` and `request.topic` when constructing `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle` as the source of truth for which tenant ("shop") the payload belongs to [3](#0-2) [7](#0-6) .

The broken identity binding, expressed as an equality that the gem fails to enforce:
`HMAC-authenticated bytes (raw body only) ≠ bytes the app trusts for tenant scoping (shop-domain header + body)`

### Impact Explanation
An attacker who is any unprivileged internet user with their own Shopify development/trial store can install the target app and receive genuine webhook deliveries with valid `X-Shopify-Hmac-Sha256` signatures for their own store. Because the signature only covers the JSON body, the attacker can:
1. Capture a legitimate `(raw_body, hmac)` pair from their own shop.
2. Replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's `myshopify.com` domain (and optionally `X-Shopify-Topic`, which is also unsigned).
3. `Utils::HmacValidator.validate` still returns `true` because the signature check only examines `@raw_body`, and `Registry.process` dispatches the (attacker-controlled) `shop` value to the handler as if it were a genuine victim-shop event.

Any host application whose webhook handler uses `data.shop` (from `WebhookMetadata`) to scope database writes, cache invalidation, `customers/data_request`/`shop/redact` compliance actions, or reprocessing logic will act on the wrong tenant, or process attacker-chosen data (attacker fully controls their own webhook body content) as if it originated from the victim's store. This is a cross-tenant integrity break rooted directly in this gem's webhook verification code, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: obtaining a valid `(body, hmac)` pair requires nothing more than installing the app on any store the attacker controls (a normal, unprivileged action available to any developer), and forging headers on an HTTP request to the app's public webhook endpoint requires no credentials, no access token, and no knowledge of `api_secret_key`. The only prerequisite is that the target app relies on `ShopifyAPI::Webhooks::Registry.process`/`Request` (the gem's documented webhook-verification path) as its authentication boundary, which is exactly what the gem is designed and marketed to provide.

### Recommendation
Bind the tenant/topic identity to the HMAC the same way `AuthQuery` does: include the `shop-domain` (and ideally `topic`, `api_version`, `webhook_id`) header values into `to_signable_string`, or otherwise cryptographically validate that the header-provided `shop` matches an actively provisioned session/shop known to the host app before dispatching `WebhookMetadata`. At minimum, document clearly that `request.shop`/`request.topic` are unauthenticated and must not be trusted for tenant scoping without an out-of-band check, and consider having `Registry.process` reject requests whose `shop` does not correspond to an existing installed session for the app.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and receives a legitimate webhook, e.g.:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: attacker-crafted JSON (attacker fully controls the order/customer payload sent to their own store, then triggers a webhook for it).
2. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. Server calls `Registry.process(request)`:
   - `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, request.to_signable_string)` = `HMAC(secret, raw_body)`, which still matches the header HMAC because the body is unchanged [1](#0-0) [8](#0-7) .
   - Validation passes; `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop = "victim-shop.myshopify.com"` [3](#0-2) .
   - The app's `WebhookHandler#handle` executes attacker-controlled business logic against the victim shop's tenant context, e.g. writing attacker data into the victim's records or triggering compliance/data actions scoped to the wrong shop.

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
