### Title
Webhook `shop` and `topic` identifiers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC verification performed by `Registry.process` proves nothing about the `shop-domain` or `topic` headers. Those headers are still used, unauthenticated, to select the handler and to identify which merchant/tenant the webhook belongs to. This is the same class of bug as the M-4 Hats Protocol report: a value that is *acted on* (the toggle address / here, the shop identity) is not the value that was actually verified (the toggle status / here, the signed body), so the code trusts stale/attacker-controlled state instead of the freshly-verified source of truth.

### Finding Description
The HMAC binding is defined here: [1](#0-0) [2](#0-1) 

`hmac` is computed from the Shopify-supplied `hmac-sha256` header, and `to_signable_string` returns `@raw_body` only — `shop` and `topic` (also read straight from unauthenticated headers) are excluded from the signed content.

`Registry.process` verifies the HMAC and then unconditionally trusts `request.topic` and `request.shop` to route and label the event: [3](#0-2) 

The equality the code assumes is:
`shop_identity_used_by_handler == shop_domain_header`

but the only thing actually authenticated is:
`HMAC_secret(raw_body) == received_hmac`

There is no cryptographic relationship enforced between `shop`/`topic` and the verified body, i.e. **bytes verified (`raw_body`) ≠ bytes parsed for identity (`shop-domain`/`topic` headers)**.

### Impact Explanation
Because the app's shared `api_secret_key` is used to sign every webhook regardless of which shop installed the app, any store owner who has installed the app (an unprivileged internet user relative to *other* tenants of the same app) can capture one legitimate, correctly-signed webhook delivered to their own endpoint (or the shared endpoint) and replay it with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` still succeeds, because it only checks `raw_body` against the HMAC — the attacker did not need to forge any signature, only to relabel an already-valid one. `Registry.process` then calls `handler.handle` with `WebhookMetadata.new(shop: request.shop, ...)` pointing at the victim shop, potentially causing the host application to write, delete, or reprocess data (e.g. GDPR redact, app uninstall, order/customer sync) under the wrong tenant's identity. This is a cross-tenant integrity breach through this gem's own verification primitive, which the rules classify as Critical (cross-tenant access).

### Likelihood Explanation
Any app that has at least one merchant installation can be abused by that merchant (or anyone who can trigger a webhook for their own shop, e.g. by placing a test order) to relabel the event toward an arbitrary victim `shop` domain string, since no additional secret or privilege is required beyond having one valid webhook delivery to copy the body/HMAC from. The `topic` header is equally unauthenticated, compounding handler-selection confusion.

### Recommendation
Include `shop` and `topic` in the signable content the gem verifies, or otherwise cryptographically bind them to the payload (e.g., require the host app to cross-check `shop`/`topic` against a value embedded in the verified JSON body, or have `HmacValidator` verify a composite string of `headers + raw_body` matching Shopify's documented signing scheme). At minimum, document loudly that `request.shop`/`request.topic` are **not** covered by `HmacValidator.validate` and must not be used as the sole tenant/topic identifier without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any subscribed webhook (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header value sent to the app's webhook endpoint.
2. Attacker resends the identical body and HMAC header to the same endpoint, but rewrites `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only checks `raw_body`, which is unchanged.
4. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: ...))`, causing the host application to act on `victim-shop.myshopify.com` using data that was never actually sent by or about that shop.
