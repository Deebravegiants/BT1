Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)` and then forwards `request.shop` unchanged into `WebhookMetadata` passed to the app's handler [3](#0-2) . `HmacValidator` itself only recomputes the signature over `to_signable_string` (i.e., the body) and never incorporates the shop header [4](#0-3) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw body only. The `shop` value that the library passes to the app's `WebhookHandler` is read from the `X-Shopify-Shop-Domain` HTTP header, which is not included in the signed payload. Any user who can obtain one validly-signed webhook body (e.g., a merchant receiving webhooks for their own shop, since Shopify signs webhooks with the app's single `client_secret`, not a shop-specific secret) can resend that same body to the app's webhook endpoint while substituting the `shop-domain` header for a different, victim shop. `Utils::HmacValidator.validate` will still report the HMAC as valid because it only checks `raw_body` against the signature, so `Registry.process` will call the app's handler with `data.shop` set to the attacker-chosen victim shop.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively [1](#0-0) , and `Request#shop` is derived purely from request headers without any cryptographic binding to the body or its signature [2](#0-1) . `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC [5](#0-4) , meaning the shop identity is never part of what's authenticated. `Registry.process` trusts `request.shop` as the tenant identity handed to the app-level handler once the (body-only) HMAC passes [3](#0-2) .

This breaks the identity binding: `shop authenticated (via HMAC) == shop used by the handler for tenant-scoped processing`. In reality, the HMAC authenticates only the body bytes; the `shop` field asserted to the handler is attacker-controllable independent of that signature.

### Impact Explanation
Because Shopify signs all webhooks for an app with the same `client_secret` regardless of which shop they originate from, an attacker who operates or controls one shop installed on the app can capture a legitimately-signed webhook body from their own shop's webhook deliveries and replay it to the app's public webhook endpoint with a forged `shop-domain` header naming a different (victim) shop. The app's handler, trusting `data.shop`, will process/store the data as if it originated from the victim tenant — a cross-tenant data-integrity/confusion issue for any app whose webhook handler branches or persists data keyed by `data.shop` without independently verifying that the shop is actually subscribed to receive that specific webhook.

### Likelihood Explanation
The webhook endpoint is a public HTTP endpoint by design (Shopify must reach it over the internet), so no privileged access, TLS interception, or leaked credentials are required. The only requirement is possession of one valid signed webhook body, obtainable by any unprivileged party who runs the app on a shop they control (a normal use case, not a privileged one). Likelihood is high for apps that key any downstream logic off `data.shop` without further validation, which is precisely the intended way to consume this API per the gem's own documentation.

### Recommendation
Include the shop domain (and ideally topic and webhook id) in the signed payload validated by `HmacValidator`, or otherwise cryptographically bind the `shop-domain` header to the HMAC-verified body (e.g., verify the shop against a per-shop registered webhook secret/subscription rather than trusting the header verbatim). At minimum, document that host applications must cross-check `data.shop` against their own known/installed shop list before trusting it as a tenant boundary.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g., `orders/create`), receiving a real Shopify-signed delivery with a valid `X-Shopify-Hmac-Sha256` for some body `B`.
2. Attacker POSTs the same raw body `B` and the same valid HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `B` and succeeds [6](#0-5) .
4. The app's handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [7](#0-6) , causing the app to process attacker-supplied data under the victim shop's identity.

          received_signature = verifiable_query.hmac
