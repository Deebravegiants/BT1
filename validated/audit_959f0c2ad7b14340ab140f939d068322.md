### Title
Loss of user-supplied native ETH in `EvmHost.dispatch`/`fundRequest` due to non-atomic Uniswap refund landing on the Host instead of the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` accept native ETH and swap it for the exact fee-token amount needed via `IUniswapV2Router02.swapETHForExactTokens`. Any ETH sent in excess of the exact amount required for the swap is refunded by the Uniswap router to `msg.sender` of the swap call — which is the `EvmHost` contract itself, not the original transaction sender (the app/user who supplied the ETH). This mirrors the reported bug class: a wrap/swap operation and its "refund of unused native token" are not atomic with respect to the correct beneficiary, so surplus ETH is misdirected and effectively trapped on the Host rather than returned to whoever paid it.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 
when `msg.value > 0`, the Host calls `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. UniswapV2Router's `swapETHForExactTokens` computes `amounts[0]` needed to buy `post.fee` of the fee token and, if `msg.value > amounts[0]`, refunds `msg.value - amounts[0]` to `msg.sender` — which, from the router's perspective, is `EvmHost`, since `EvmHost` is the direct caller of the router. The same pattern exists in `dispatch(DispatchGet)` at lines 974-985 and in `fundRequest` at lines 1031-1042.

Callers such as `WrappedHyperFungibleToken.send()` / `HyperFungibleTokenUpgradeable.send()` explicitly document that "the remainder of `msg.value` after wrapping is forwarded as native payment for dispatch fees" and pass the whole remainder as `msg.value` to `IDispatcher(_host).dispatch{value: msgValue}(request)`: [2](#0-1) 
Any amount over-provisioned for fee estimation (e.g. due to slippage buffers, or price movement between quoting off-chain and execution, as flagged in the SDK/docs: "Apply a generous 2x buffer to absorb… Excess native is refunded by the uniswap router") ends up refunded to `EvmHost`'s own balance instead of back to the calling app/user: [3](#0-2) 

Unlike the intents-based contracts in this codebase (`IntentGatewayV2`, `IntentsBase`, `ExtrinsicIntents`/`IntrinsicIntents`), which correctly track a `msgValue` counter and atomically `_sendValue(msg.sender, msgValue)` any leftover native ETH back to the caller in the same transaction: [4](#0-3) [5](#0-4) 
`EvmHost.dispatch`/`fundRequest` perform no such refund-forwarding step — they simply forward the entirety of `msg.value` to the router and let the router's own refund mechanism silently return the excess to the Host contract's own balance.

### Impact Explanation
Every app or end-user that dispatches an ISMP POST/GET request or funds a pending request using native ETH and supplies more ETH than the router needs for the fee-token swap permanently loses that excess to the `EvmHost` contract's balance. This is a direct, protocol-wide loss-of-funds vector reachable by any unprivileged dispatcher/relayer/app caller that pays fees in native ETH — which the documentation explicitly recommends as a normal payment path (`docs/content/developers/evm/messaging/post-requests.mdx`, `docs/content/developers/evm/api/idispatcher.mdx`). Because quoting fees off-chain via `quote()` (which itself warns of sandwich-attack risk and inherent staleness) or applying safety buffers is the expected practice, any user is exposed to overpaying and losing the difference on essentially every native-ETH-funded dispatch. Given the confirmed absence of a native-ETH withdrawal/sweep path visible in `EvmHost.sol`'s public interface (only `IHostManager.updateHostParams` and feeToken-oriented withdrawal logic were found), this ETH is not straightforwardly recoverable by governance either, resulting in a functional freeze of these funds. This satisfies the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
High likelihood: this triggers on the ordinary, documented native-ETH payment path for `dispatch()`/`fundRequest()`, not an edge case or malicious actor. Fee estimation via `quote()` is inherently approximate (subject to price movement between quote-time and execution-time, and explicitly buffered 2x in at least one integration), so overpayment is a routine occurrence rather than a rare condition, closely matching the "delay between transaction submission and execution" root cause described in the reference report.

### Recommendation
After the Uniswap swap in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, check `EvmHost`'s ETH balance delta (or capture the `amounts[0]` returned by `swapETHForExactTokens`) and forward any leftover `msg.value - amounts[0]` back to `_msgSender()` atomically within the same transaction, mirroring the pattern already implemented correctly in `IntentGatewayV2`/`IntentsBase` (`_sendValue(msg.sender, msgValue)`), instead of relying on the router's refund-to-caller behavior that misattributes the refund to the Host contract.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch(DispatchPost)` (directly, or indirectly via `WrappedHyperFungibleToken.send()`/`HyperFungibleTokenUpgradeable.send()`) with `msg.value` intentionally or accidentally larger than the ETH required to buy `post.fee` fee-tokens (e.g., using a slippage buffer, or because the price moved between off-chain `quote()` and on-chain execution).
2. `EvmHost.dispatch` executes:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
``` [6](#0-5) 
3. Uniswap's router computes `amounts[0] < msg.value`, performs the swap, and calls `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])` — `msg.sender` here is `EvmHost`.
4. The refunded ETH increases `EvmHost`'s native balance permanently; the original caller (user/app) receives nothing back despite having paid the excess, and no code path in `EvmHost.sol`'s visible interface returns or sweeps this balance to the payer.
