### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and exposes `hmac` and `to_signable_string`, but `to_signable_string` returns only `@raw_body` [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` only calls `Utils::HmacValidator.validate(request)`, which verifies the signature against `to_signable_string` (the body), and then forwards `request.shop`/`request.topic`/`request.webhook_id` unchecked into `WebhookMetadata` passed to the app's handler [3](#0-2) . The identity binding broken is: `shop` field acted upon by the handler ≠ `shop` field actually covered by the HMAC signature.

### Finding Description
The documented contract states that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook" [4](#0-3) , implying the shop attribution is authenticated. In reality, `HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`, i.e., the raw body [5](#0-4) . The `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers are never included in the signed material [6](#0-5) .

Any unprivileged internet user can install the target app on their own (free/trial) Shopify store and receive genuinely-signed webhook deliveries for that store. Because only the body bytes are bound to the signature, that attacker can replay the exact same signed body to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header to claim the event originated from a different, victim shop. `HmacValidator.validate` still succeeds (the body and secret are unchanged), and `Registry.process` forwards the attacker-chosen `shop` value straight into `WebhookMetadata` for the handler [7](#0-6) , with no re-validation that the header-derived shop matches the shop that actually produced/signed the body.

### Impact Explanation
Applications built on this gem are documented to trust `data.shop` as the authenticated tenant identifier for webhook processing (e.g., enqueuing background jobs keyed by `shop_domain`) [8](#0-7) . Since the shop identity is not bound to the signature, an attacker-controlled shop-domain header lets an unprivileged, self-onboarded attacker inject genuinely HMAC-valid webhook traffic under an arbitrary victim shop domain, i.e., cross-tenant data confusion/injection without needing the merchant's access token or `api_secret_key`.

### Likelihood Explanation
High for any app that trusts `WebhookMetadata#shop` (as instructed by this gem's own documentation) to key per-tenant processing, since exploitation requires nothing more than a normal (free-tier) Shopify store to obtain a validly-signed webhook body and a way to POST to the app's public webhook endpoint with a modified header.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or otherwise cryptographically bind `request.shop` to the signature verification step — e.g., include the `shop-domain` header in `to_signable_string`, or require the host application to cross-check `request.shop` against an out-of-band trusted session/store record before acting on the webhook, and document this requirement explicitly rather than implying `Registry.process` fully authenticates the shop field.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a legitimate webhook POST with a valid `X-Shopify-Hmac-SHA256` header computed over the request body.
2. Attacker resends the identical raw body to the app's webhook endpoint but changes the `X-Shopify-Shop-Domain` header to `victim.myshopify.com` (and optionally the topic/webhook-id headers).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the unchanged raw body) and successfully matches the unchanged signature [9](#0-8) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` despite the payload never having been produced/authorized for that shop, demonstrating the identity-binding break.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
