## Finding

### Title
Multisig timelock bypass via live (mutable) timelock config instead of value pinned at transaction creation - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`MultisigAccountTimeLock`'s timelock/override check (`can_execute_with_timelock`) reads the *current* global `timelock_period` / `override_threshold` at execution time instead of the values that were in effect when the specific pending transaction was created (`creation_time_secs`). This is the same class of bug as the reported `StreamsLookup` issue: a check that should be anchored to "the time/context at which the request was created" instead consults "whatever the current state is right now," letting a mutable, attacker-influenceable value corrupt an authority decision — here, whether a multisig custody transaction may execute.

### Finding Description
`MultisigTransaction` stores only `creation_time_secs` per pending transaction: [1](#0-0) 

The timelock gate, however, is not evaluated against a value snapshotted for that transaction — it pulls the *live* `MultisigAccountTimeLock` resource (`timelock_period`, `override_threshold`) at the moment `can_execute_with_timelock` / `validate_multisig_transaction` runs: [2](#0-1) [3](#0-2) 

Only `creation_time_secs` is fixed at creation; `timelock_period` and `override_threshold` are read fresh from global storage on every check. This means that between the time a transaction was proposed (and other owners/watchers began relying on the currently-configured delay to review it) and the time it is executed, any subsequent multisig transaction that changes the timelock config (shortening `timelock_period`, lowering/adding an `override_threshold`, or removing the `MultisigAccountTimeLock` resource entirely) retroactively and immediately weakens or eliminates the delay protecting *every other already-pending* transaction — including ones created specifically to benefit from the longer window (e.g., a suspicious `add_owners`, `swap_owner`, or fund-transfer payload that a minority of owners flagged and expected to have time to react to).

This mirrors the reported bug precisely: the correct semantic is "use the reference value fixed at creation of the request" (`log.timestamp` / the timelock policy in force when the transaction was proposed); the actual code uses "the current, mutable value" (`block.timestamp` / the live `MultisigAccountTimeLock`), producing a decision inconsistent with what was promised to the parties who relied on the original context.

Of the candidate custody paths considered — (1) `object.move` `transfer_with_ref`/`verify_ungated_and_descendant` (found correctly bound to owner-at-generation-time via `LinearTransferRef`, no bug), (2) `dispatchable_fungible_asset` hook dispatch (correctly gated by `TransferRef`/`module_lock`, no unprivileged bypass found), (3) `resource_account::retrieve_resource_account_cap` (properly checks container ownership, no bug), and (4) the multisig timelock — this timelock live-config re-evaluation is the only path with a clear, self-contained authority-timing break rooted in local code.

### Impact Explanation
Multisig accounts on Aptos directly custody APT, fungible assets, and control ownership/upgrade authority for resource accounts and code objects. The timelock feature exists specifically as a custody safeguard — giving owners/observers a guaranteed window to detect and react to malicious pending transactions (e.g., adding a rogue owner, swapping an owner, draining funds) before they can execute. Because the enforcement re-reads live global config instead of binding to the transaction's own creation-time policy, a quorum of colluding or compromised owners can shorten or remove that guaranteed window for **all currently pending transactions simultaneously**, not just future ones — silently defeating the safety property depositors and other owners rely on to protect custody-held value. This is a direct break of a custody invariant ("multisig-owned assets... must not leak... transfer authority" / "custody invariants should hold across ... transfer" paths) with high impact given multisig accounts are commonly used to hold significant treasury/asset value.

### Likelihood Explanation
Exploitation requires the same quorum (`num_signatures_required`) that could already execute transactions, so it is not an unprivileged-stranger attack — but it does not require additional privilege beyond what any config-change transaction has, and it defeats a security control (the timelock) that other owners specifically rely on for out-of-band scrutiny/veto. Realistic scenario: an attacker who has compromised or colludes with enough owner keys to hit quorum queues a malicious drain/ownership-change transaction, and separately queues a "reduce timelock"/"remove timelock" transaction; once the config-change transaction executes, the malicious transaction (still pending, created earlier under the longer delay) becomes immediately executable without ever having waited its originally-configured window. Likelihood is medium given the quorum precondition, but the loss of the delay guarantee for *pre-existing* pending transactions (not just future ones) is a design/implementation flaw regardless of whether it's actively exploited.

### Recommendation
Snapshot the applicable timelock policy (`timelock_period` and `override_threshold`, or a computed `unlock_time_secs`) into `MultisigTransaction` at the moment the transaction is created (alongside `creation_time_secs`), and have `can_execute_with_timelock` / `validate_multisig_transaction` evaluate against that stored, immutable snapshot rather than re-reading the live `MultisigAccountTimeLock` resource. This ensures a change to global timelock configuration only affects transactions created after the change, consistent with how the external report recommends binding the check to the value captured at the time of the original request.

### Proof of Concept
1. Create multisig account `M` with owners `{A, B, C}`, `num_signatures_required = 2`, and `MultisigAccountTimeLock { timelock_period: 14 days, override_threshold: none }` (long delay intentionally configured for scrutiny of sensitive ops).
2. Owner `A` (compromised) creates transaction T1: `add_owners([Attacker])` at `t0`. `T1.creation_time_secs = t0`. Owner `A` also gets approval from colluding owner `B` (2-of-3 quorum reached, but `can_execute_with_timelock` still requires `elapsed >= 14 days` since no override_threshold — T1 cannot execute yet).
3. Owners `A` and `B` create and execute transaction T2: a self-call multisig transaction that reduces `timelock_period` to `MIN_TIMELOCK_PERIOD` (1 hour) via the timelock-update function (this T2 itself must satisfy whatever timelock currently applies, but since it can be created and approved quickly and, depending on ordering/threshold, this only needs to happen once).
4. Once T2 executes, `MultisigAccountTimeLock.timelock_period` becomes 1 hour globally.
5. Owner `A`/`B` now call execute on T1 (still using its original `creation_time_secs = t0`). `can_execute_with_timelock` computes `elapsed = now_seconds() - t0 >= 1 hour` (true, since more than an hour has passed since T1 was created while T2 was being processed), so T1 executes immediately — years/days before the originally-configured 14-day review window for T1 would have elapsed, giving owner `C` no chance to detect/react to the malicious `add_owners` before it takes effect.

This demonstrates that the timelock guarantee for an already-pending transaction is not fixed at creation and can be shortened by later, unrelated governance actions — the exact "wrong reference value at check time" pattern from the seed report.

```text
    /// Return true if the transaction with given transaction id can be executed immediately, or it has to wait
    /// for the timelock to expire.
    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
```
