### Title
Webhook shop-domain identity is trusted from an unauthenticated header while the HMAC only covers the raw body, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw HTTP body [1](#0-0) , while the tenant-identifying `shop` value is read from the `x-shopify-shop-domain` header, which is never included in the signed content [2](#0-1) . `Registry.process` validates only the HMAC of the body and then trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler [3](#0-2) . This is the same class of inconsistency as the referenced report: a field that is *acted on* (the shop identity used by the handler) is not the field that is *covered by the cryptographic check* (only the body bytes).

### Finding Description
The identity binding that should hold is:
`shop used for tenant dispatch == shop cryptographically bound to the verified HMAC`

In this gem that equality does not hold. `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received `hmac` [4](#0-3) . For webhooks, `to_signable_string` returns only `@raw_body` [1](#0-0) ; none of `shop-domain`, `topic`, `webhook-id`, or `api-version` headers are part of the signed content.

`Registry.process` then does:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [3](#0-2) 

Because the `secret` used for HMAC computation is the app's single `api_secret_key` shared across every shop that has installed the app (not a per-shop secret) [5](#0-4) , a valid `(body, hmac)` pair captured from one legitimately-installed shop remains cryptographically valid when replayed with a forged `x-shopify-shop-domain` header pointing at a different shop the attacker does not control. The HMAC check passes (it only verifies the body was signed by the app's secret), but the `shop` value handed to the application's webhook handler is completely unauthenticated.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing: an entity that merely has one installed instance of the app (an "unprivileged" merchant relative to other tenants) can produce webhook payloads that `Registry.process` will accept as HMAC-valid for an arbitrary victim shop domain, since the shop field is never bound to the signature. Any host application that relies on `WebhookMetadata#shop` (as returned directly by this gem's public API) to select the tenant/session context - the documented and intended way to consume this API - can be made to apply attacker-supplied webhook data (e.g., replayed `orders/create`, `app/uninstalled`, or other topic payloads) under a different shop's identity. This is a cross-tenant identity-confusion vector reachable purely from processing a crafted/replayed webhook request, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to (1) control or install the app on at least one shop to legitimately obtain one valid `(raw_body, hmac)` pair from a real webhook delivery, and (2) resend that exact body with the same HMAC but a different `x-shopify-shop-domain` header value to the app's webhook endpoint. Both steps are within reach of any user capable of installing the app (no access to `api_secret_key`, tokens, or privileged accounts is needed) and rely only on documented gem behavior (`Registry.process` reading `request.shop` from headers). Likelihood is Medium-High for apps that key any per-tenant logic off the webhook's `shop` field.

### Recommendation
Bind the tenant-identifying header(s) into the signed content, or independently verify that `request.shop` corresponds to a shop with an active, known session/installation before dispatching to the handler. At minimum, document that `WebhookMetadata#shop` is not cryptographically authenticated and must not be trusted for tenant selection without corroboration (e.g., cross-checking against the app's own installation/session store keyed by a value derived independently of the untrusted header).

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and capture a real webhook delivery: raw JSON body `B` and header `x-shopify-hmac-sha256: H` (valid against the app's shared `api_secret_key`), plus `x-shopify-topic: orders/create`.
2. Replay the request to the app's webhook endpoint with the same body `B` and same `H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks `B` against `H` [5](#0-4) [1](#0-0) .
4. `Registry.process` dispatches to the registered handler with `shop: "victim-shop.myshopify.com"` [3](#0-2) , causing the host application to act as though `victim-shop` sent this webhook, despite the attacker never having installed on or gained access to `victim-shop`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
