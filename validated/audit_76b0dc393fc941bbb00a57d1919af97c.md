### Title
Same-chain `cancelOrder` on the Tron IntentGatewayV2 refunds the pre-fee `order.inputs` amount instead of the actual escrowed balance, causing the refund to underflow-revert and permanently freeze escrow whenever a protocol fee is set - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.cancelOrder` builds the same-chain refund's `WithdrawalRequest` directly from `order.inputs` (the pre-protocol-fee amounts) rather than from the actual escrowed balance recorded in `_orders[commitment][token]`. Since `placeOrder` only escrows the *reduced* (post-protocol-fee) amount, `withdraw()` will try to subtract more than what is actually escrowed, reverting on arithmetic underflow whenever `protocolFeeBps > 0`. This is analogous to the RubiconMarket `cancel` bug: a refund/cancel code path passes the wrong value into a downstream transfer/validation routine, and that mismatch causes the cancel operation to always revert, permanently blocking users from ever recovering their escrow.

### Finding Description
In `placeOrder`, the amount actually escrowed per token is the fee-reduced amount: [1](#0-0) [2](#0-1) 

This stores `reducedInputs[i].amount = originalAmount - protocolFee` into `_orders[commitment][token]`, which is strictly less than `order.inputs[i].amount` whenever `protocolFeeBps > 0`.

However, the same-chain branch of `cancelOrder` constructs the withdrawal request using the raw, un-reduced `order.inputs` amounts: [3](#0-2) 

`withdraw()` then reads `amount = body.tokens[i].amount` (the un-reduced amount) and attempts to subtract it from `_orders[body.commitment][token]` (the reduced escrow balance): [4](#0-3) 

Because `amount > _orders[commitment][token]`, the line `_orders[body.commitment][token] -= amount;` underflows and reverts under Solidity 0.8's checked arithmetic. `withdraw()` also attempts to transfer the too-large `amount` to the beneficiary before this underflow check, so in some paths the transfer would also fail on insufficient contract balance — either way, the transaction reverts.

This directly mirrors the reported RubiconMarket root cause: a cancel/refund helper is fed a parameter that is valid in one code path (the correct, escrow-actual amount used in `IntrinsicIntents.sol`'s `_cancelSameChain`, which reads `_orders[commitment][token]` rather than `order.inputs`) but invalid in another (the Tron reimplementation, which reuses the raw order struct), causing an unconditional revert that blocks the operation for a class of legitimate callers.

Compare with the correct implementation in the primary EVM contract, which reads the *escrowed* remaining balance instead of the original order input amount: [5](#0-4) 

### Impact Explanation
Whenever `_params.protocolFeeBps` (or a destination-specific override) is non-zero — which is the expected production configuration for a fee-charging protocol — every same-chain `cancelOrder` call on the Tron gateway will revert. Because the escrowed tokens can never be withdrawn through this code path, and there is no alternate recovery function, user funds placed in same-chain orders become **permanently frozen** in the contract once the order cannot otherwise be filled (e.g., no solver takes it, or the user simply wants to cancel). This satisfies the "permanent freezing of funds" impact bar.

### Likelihood Explanation
The bug triggers deterministically and unconditionally any time `protocolFeeBps > 0` for the relevant destination, which is the normal fee-charging configuration for the IntentGateway. Any unprivileged user who calls `placeOrder` then `cancelOrder` on a same-chain order on the Tron deployment will hit this revert on the very first attempt — no adversarial setup or race condition is required, so likelihood is high.

### Recommendation
In the Tron `cancelOrder` same-chain branch, build the `WithdrawalRequest.tokens` from the live escrow balances (`_orders[commitment][token]`) as done in `IntrinsicIntents.sol::_cancelSameChain`, not from `order.inputs`. Additionally, harden `withdraw()` to bound the requested amount by the escrowed balance (or explicitly revert with a clear error) rather than relying on implicit underflow reversion, and add a regression test asserting that same-chain cancellation succeeds and refunds the correct (fee-reduced) amount when `protocolFeeBps > 0`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and call `setParams` with `protocolFeeBps > 0` (e.g., 50 bps).
2. User calls `placeOrder` with a same-chain order (`order.source == order.destination`) and `order.inputs[0].amount = 1000e6 USDC`.
   - `placeOrder` computes `protocolFee = 1000e6 * 50 / 10000 = 5e6`, escrows `_orders[commitment][usdc] = 995e6` (see `evm/tron/contracts/apps/IntentGatewayV2.sol:359-385, 450-469`).
3. User calls `cancelOrder(order, options)` before the order is filled.
   - `cancelOrder`'s same-chain branch sets `body.tokens = order.inputs`, i.e., `amount = 1000e6` (see `evm/tron/contracts/apps/IntentGatewayV2.sol:536-539`).
4. Inside `withdraw()`, `_orders[commitment][usdc] (995e6) -= amount (1000e6)` underflows and reverts (`evm/tron/contracts/apps/IntentGatewayV2.sol:691-714`).
5. The order remains permanently escrowed and un-cancellable; `_filled[commitment]` is never set (revert rolls it back), so the order stays stuck with no way to ever redeem the 995e6 USDC through this function.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
