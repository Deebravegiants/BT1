### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant impersonation of the tenant field passed to handlers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request **body**, but the `shop` value that is subsequently handed to the application's webhook handler is read from an HTTP **header** that is never part of the signed material. An attacker who can obtain one validly-signed webhook body for the shared app secret (e.g. by triggering a webhook on their own store, which is installed on the same multi-tenant app and therefore shares the same `api_secret_key`) can replay that body with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a victim shop domain. The HMAC check still passes because the signature never covered the header, so the forged tenant identity flows straight into the handler as authenticated data.

### Finding Description
`Utils::HmacValidator.validate` computes/verifies the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns just the raw body, while `shop` is read independently from an HTTP header: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed into the handler: [3](#0-2) 

The equality the code implicitly assumes is:
`hmac_valid(body) == shop_header_is_authentic_for_that_body`

But those are independent: the HMAC is keyed by the app's single shared `api_secret_key` (or `old_api_secret_key`), which is the same across every shop that has the app installed — it is not shop-specific. Any tenant of the app can generate a legitimately-signed body (e.g., by causing a webhook to fire on their own development/test store) and then present it to the app's webhook endpoint with the `shopify-shop-domain` header swapped to another tenant's domain. `Utils::HmacValidator.validate` will still return `true` because it only re-computes the signature from `@raw_body`, never from the header set.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is expected to enforce for webhook processing (host applications rely on `WebhookMetadata#shop` — set directly from `request.shop` — to decide which shop's data/session the payload pertains to). A malicious but legitimate merchant of a multi-tenant app can forge the `shop` field for a webhook whose body they fully control (topic and JSON body of their choosing, since they trigger it on their own store) and have it processed as if it belonged to an arbitrary victim shop, since the gem asserts the HMAC is sufficient authentication and passes the header-derived shop straight through as trusted metadata. This is a cross-tenant identity/authentication issue reachable purely through the gem's documented webhook processing API (`ShopifyAPI::Webhooks::Registry.process`), matching the "field acted on but not covered by HMAC" analog class.

### Likelihood Explanation
Moderate-to-high: the only prerequisite is that the attacker be a merchant with the target app installed on at least one shop they control (a normal, unprivileged condition for any public app), enough to receive one real, validly-signed webhook delivery. No access to `api_secret_key`, tokens, or infrastructure is required — only observing/replaying an HTTP request with a modified header, which any user who can install the app and trigger a webhook (e.g., `orders/create`) can do.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values into the signed material, or otherwise cross-validate the header-derived shop against a known/expected session/shop registered for that webhook subscription before handing it to the handler. At minimum, document prominently that `request.shop` is unauthenticated header data and must be independently verified (e.g., against a shop that is known to have valid, stored session/access-token state) before being used as a tenant key.

### Proof of Concept
1. App shares one `api_secret_key` across all installs (standard Shopify app model).
2. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. updates an order) to receive a body `B` with a valid `x-shopify-hmac-sha256` computed over `B` using the shared secret.
3. Attacker POSTs body `B` (unmodified) to the app's webhook endpoint but sets header `x-shopify-shop-domain: victim-shop.myshopify.com` (keeping the same, still-valid `x-shopify-hmac-sha256`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL.secure_compare(computed_signature, hmac)` over the raw body — validation succeeds. [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, `body: B` — attacker-controlled data now impersonating the victim tenant.

          received_signature = verifiable_query.hmac

        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
