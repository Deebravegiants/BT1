### Title
Webhook `shop` field is not covered by HMAC verification, allowing shop/tenant spoofing on replayed webhook payloads - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` succeeds [1](#0-0) , and then forwards `request.shop` — read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header — into `WebhookMetadata` for the app's handler to key its per-tenant logic on [2](#0-1) . However, the HMAC signature only ever covers the raw request body, not the shop header: `to_signable_string` returns `@raw_body` alone [3](#0-2) , and `HmacValidator.validate_signature` computes/compares the digest solely over that signable string [4](#0-3) . This breaks the binding `shop_authenticated == shop_used_for_tenant_dispatch`.

### Finding Description
Every shop that installs an app which uses this gem shares the same `Context.api_secret_key` for webhook HMAC signing — the secret is per-app, not per-shop. An attacker who controls (or is) any shop with the app installed can trigger a legitimate webhook delivery to their own shop (e.g. `orders/create`), capturing a body + valid `x-shopify-hmac-sha256` pair signed by Shopify with the shared app secret. Because `Request#to_signable_string` only ever hashes `@raw_body` [3](#0-2) , the attacker can then POST that same, unmodified body + HMAC directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header value with an arbitrary victim shop domain. `HmacValidator.validate` will still return `true`, since it never inspects headers [5](#0-4) , and `Registry.process` will happily dispatch to the registered handler with `WebhookMetadata#shop` set to the forged victim domain [1](#0-0) . The gem's own documentation instructs integrators to trust `data.shop` as "the shop domain of the webhook" once `Registry.process` has "verif[ied] the request did indeed come from Shopify," and shows using it directly to key job/queue dispatch by shop [6](#0-5) . Any app following that documented pattern will attribute attacker-controlled data to a shop the attacker does not control, crossing a tenant boundary.

### Impact Explanation
This is a cross-tenant integrity/authentication issue: an unprivileged attacker who is merely a legitimate merchant of the app (not privileged, no leaked credentials, no access to `api_secret_key`) can make the host application process forged webhook data under an arbitrary victim shop identity. Depending on how the host app uses `data.shop` (e.g. selecting the tenant session/database record to update), this can lead to cross-tenant data corruption or state confusion, which maps to "cross-tenant access" in the Critical impact category.

### Likelihood Explanation
High. Registering a webhook for one's own shop, capturing the raw body and HMAC header from a genuine delivery, and replaying it against the public webhook endpoint with a modified shop header requires no special access — any account able to install the app and trigger webhook-eligible events (e.g., creating an order) can do this. The signing secret is shared across all installs of the app, so no per-shop secret needs to be known.

### Recommendation
Bind the shop domain to the authenticated payload before trusting it: either (a) include the `x-shopify-shop-domain` header value in `to_signable_string` so it is HMAC-covered (this would require a corresponding server-side change on Shopify's part, so more practically) (b) cross-check `request.shop` against the shop derived from an authenticated source the app already controls (e.g. the known set of shops with an active offline session/webhook registration for the given `webhook_id`/topic combination) before dispatching to the handler, and reject webhooks whose header shop cannot be corroborated. At minimum, update the documentation to warn integrators that `data.shop` is not itself HMAC-authenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. As shop `attacker.myshopify.com` (a legitimate install of the target app), trigger a webhook-eligible event (e.g., create an order) so Shopify delivers a genuine webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Capture `B` and `H` (e.g., via a proxy/logging on infrastructure the attacker controls, or by having the app echo the payload back).
3. Send a new HTTP POST directly to the app's public webhook route with the identical raw body `B` and identical header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a request object whose `shop` returns `"victim.myshopify.com"` [2](#0-1)  while `to_signable_string` still returns `B` [3](#0-2) .
5. `Registry.process` calls `HmacValidator.validate`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — it matches, so validation succeeds [7](#0-6) .
6. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body, ...)` [8](#0-7) , causing the host app to process attacker-supplied data as if it belonged to the victim shop.
