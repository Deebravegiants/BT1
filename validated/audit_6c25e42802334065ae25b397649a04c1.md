### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC — ([File: lib/shopify_api/webhooks/request.rb](file))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (and `topic`/`webhook_id`) values used by `ShopifyAPI::Webhooks::Registry.process` to route/act on the webhook are taken from HTTP headers that are never part of that signed string. Because Shopify signs webhooks with the app's single `client_secret` (shared across every merchant that installed the app, not a per-shop secret), a valid HMAC only proves "this body was produced by Shopify for *some* installation of this app" — it does not bind the body to the shop asserted in the `shopify-shop-domain` header.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` verifies the HMAC solely against that signable string using `Context.api_secret_key`, which is the app-wide `client_secret`, identical for every shop that has installed the app: [2](#0-1) 

`Registry.process` only checks this body HMAC, then trusts `request.shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding this breaks (as an equality) is:

`shop asserted by header (request.shop, used by handler.handle) == shop actually bound by the cryptographic signature (none — HMAC covers only raw_body)`

Because the HMAC key is the app's single shared secret rather than a per-shop secret, and the shop domain is never included in the signed material, **any two shops that both have the app installed share the same valid HMAC for identical body bytes**. A merchant who installs the target app on their own shop (`attacker-shop.myshopify.com`) receives genuine, correctly-signed webhook deliveries for their own shop. They can capture one such delivery (raw body + valid `hmac-sha256` header) and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain (`victim-shop.myshopify.com`). `HmacValidator.validate` still succeeds because it only checks the untouched body against the shared secret, and `Registry.process` forwards `shop: "victim-shop.myshopify.com"` to the handler as if Shopify itself had asserted it.

### Impact Explanation
This is a cross-tenant identity confusion at the point the gem hands verified data to the host application. Any app whose webhook handler uses `WebhookMetadata#shop` to select which tenant's session/data to act on (the documented and expected usage pattern) can be made to apply attacker-controlled webhook bodies to a victim shop's context — e.g. spoofing `customers/data_request`, `customers/redact`, `shop/redact` (the `MANDATORY_TOPICS` in `Registry`) or ordinary business webhooks against a shop the attacker does not own, without possessing the victim's access token or the app's `client_secret`. This meets the Critical bar of cross-tenant access, since the gem's own verification primitive (`HmacValidator`/`Registry.process`) is what lets this pass as "verified."

### Likelihood Explanation
Any unprivileged actor can install the target app on a shop they control (many Shopify apps are freely installable), which gives them a stream of validly-signed webhook bodies signed with the same `client_secret` as every other installation. Replaying that body with a forged `shopify-shop-domain` header requires only the ability to send an HTTP POST to the app's public webhook endpoint — no credentials, tokens, or secrets beyond what is trivially obtainable via a self-installed instance of the app.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) inside the HMAC-signed material, or independently verify that the `shop` header corresponds to a shop with a known, previously established installation/session before trusting it in `WebhookMetadata`. At minimum, document/require that consuming apps must not treat the webhook `shop` field as authenticated by HMAC alone.

### Proof of Concept
1. Install the target Shopify app on `attacker-shop.myshopify.com` and register a webhook (e.g. `orders/create`).
2. Capture the raw webhook POST Shopify sends, including `X-Shopify-Hmac-Sha256` and body.
3. Replay the exact same request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts it (headers present), `HmacValidator.validate` returns `true` because it only hashes `@raw_body` with the shared `client_secret`.
5. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-supplied data as if it originated from the victim's store.
