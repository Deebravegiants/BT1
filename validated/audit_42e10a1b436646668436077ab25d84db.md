### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [2](#0-1) , while `#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers with no cryptographic binding to that body [3](#0-2) . `Registry.process` validates only the HMAC over the body and then dispatches the handler using the unauthenticated `shop` header as the tenant identifier [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop_used_by_handler == shop_that_the_HMAC_actually_authenticates`. In this gem that equality is broken:

- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it with the `hmac` header [5](#0-4) .
- For webhooks, `to_signable_string` is just `@raw_body` [2](#0-1) . The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers play no role in the signed material.
- `Registry.process` raises only if the body HMAC is invalid, then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and hands it to the app's handler [4](#0-3) .

Because the app's secret (`Context.api_secret_key`) is shared across every shop that installs the app, any attacker who legitimately installs the app on their own store receives genuine webhooks with a valid HMAC for their own shop's body. That same `raw_body` + `hmac-sha256` header pair remains valid no matter what `shop-domain` header accompanies it, since the header isn't part of the signed data. The attacker can replay the captured body/HMAC to the app's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header, and `Registry.process` will accept it and hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to select which merchant record to update, delete, redact, or read (a very common pattern, especially for the mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics) can be made to act on a shop the attacker does not own, using data/body content the attacker fully controls. This is a cross-tenant confusion primitive, matching the "cross-tenant access" criterion.

### Likelihood Explanation
The attacker only needs to be able to install the app on a store they control (an ordinary, unprivileged action — no leaked credentials, no `api_secret_key`, no TLS interception, and no privileged account are required) and then send an HTTP POST to the app's webhook endpoint with a modified header. This is a realistic, low-effort attack path.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) values in the signed material the gem verifies, or otherwise cryptographically/contextually bind the asserted shop to the specific HMAC before it is handed to `WebhookHandler#handle`. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host app against the shop's own stored session before being trusted for tenant-scoped operations.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Resend the exact same request to the app's webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
3. `HmacValidator.validate` recomputes `HMAC-SHA256(secret, B)`, which still equals `H`, so `Registry.process` accepts the request and invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` [4](#0-3) , causing any handler logic keyed on `data.shop` to operate against the victim tenant using attacker-supplied body content.
