### Title
Permissionless `TransferToGasKeyAction` deposits let anyone grief a victim's key/account deletion by pushing gas-key balance above the burn cap - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`action_transfer_to_gas_key` credits an arbitrary deposit to *any* gas key on *any* account without checking that the caller is the account owner or otherwise authorized. An unprivileged actor can therefore inflate a victim's gas-key balance past `GasKeyInfo::MAX_BALANCE_TO_BURN`, which is exactly the threshold `delete_gas_key`/`action_delete_account` use to decide whether the key (and thus the account) can be deleted. This mirrors the GOAT Protocol bug class: a security-critical threshold check is driven by a balance that can be unilaterally inflated by an unprivileged third party via a plain deposit, breaking a legitimate operation for the victim.

### Finding Description
`action_transfer_to_gas_key` looks up the access key on the receipt's target `account_id` and unconditionally adds the attached deposit to `gas_key_info.balance`, with no predecessor/ownership check: [1](#0-0) 

Because `TransferToGasKeyAction` is delivered like any other action inside a receipt (receiver is chosen by the sender, exactly like `Transfer`), any account on the network can send this action against a gas key that belongs to someone else, growing that key's `balance` field at will.

That same `balance` is later used as a hard gate for key deletion: [2](#0-1) 

If `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN`, `delete_gas_key` refuses to delete the key and returns `ActionErrorKind::GasKeyBalanceTooHigh` instead of proceeding — this is enforced both for standalone `DeleteKey` actions and, per the protocol spec, for `action_delete_account`, which sums all gas-key balances against the same threshold before allowing account deletion. [3](#0-2) 

Because there is no cap on inbound `TransferToGasKeyAction` deposits and no ownership check, an attacker can send a single transaction that funds the victim's gas key just over `MAX_BALANCE_TO_BURN`. The victim's only recourse is `WithdrawFromGasKeyAction`, but that action must be authorized with that same key/account, and it only reduces the balance — the attacker's donation permanently occupies that balance until the account itself withdraws it (assuming it still can), so the DoS persists at the attacker's choosing (they can keep re-funding it as fast as the victim withdraws, at negligible relative cost per griefing round since the amount needed is only marginally above the cap).

### Impact Explanation
This lets an unprivileged, arbitrary account permanently or repeatedly block another account's ability to delete a specific access key or delete the account itself (`DeleteAccountStaking`-style DoS via `GasKeyBalanceTooHigh`). This is a concrete "unauthorized state effect + node/account availability DoS" reachable purely from a submitted transaction — no validator or node compromise required, matching the report's bug class of "a balance-based validation gate that can be manipulated by an unprivileged third party depositing funds to force it to fail."

### Likelihood Explanation
The attack requires only knowledge of the victim's account id and gas-key public key (both are public on-chain data visible via `view_access_keys`), and a single `TransferToGasKeyAction` transaction with a deposit just above `MAX_BALANCE_TO_BURN`. No special timing, front-running, or validator collusion is needed, since ownership is never checked at all — this is strictly easier to execute than the original front-running GOAT exploit.

### Recommendation
Restrict `TransferToGasKeyAction` (and by extension any balance top-up of a gas key) so that it can only be executed by the account itself (require `predecessor_id == account_id`), analogous to how self-only actions such as `DeleteKey`/`AddKey` are scoped. Alternatively, decouple the deletion-eligibility check from an externally-fundable balance field, e.g. by capping how much unsolicited `TransferToGasKeyAction` deposits can add, or by allowing deletion to burn/refund excess balance instead of unconditionally rejecting the action when `balance > MAX_BALANCE_TO_BURN`.

### Proof of Concept
1. Victim `alice.near` creates a gas key with `AddKeyAction { access_key: AccessKey::gas_key_full_access(n) }`, resulting in `gas_key_info.balance == 0` [4](#0-3) .
2. Attacker `mallory.near` submits a transaction/receipt to `alice.near` containing `Action::TransferToGasKey(TransferToGasKeyAction { public_key: alice_gas_key, deposit: MAX_BALANCE_TO_BURN + 1 })`. `action_transfer_to_gas_key` performs no ownership check and credits the deposit [5](#0-4) .
3. Alice later submits `DeleteKeyAction` for that gas key (or `DeleteAccountAction` for her whole account). `delete_gas_key` sees `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN` and fails the action with `GasKeyBalanceTooHigh` instead of deleting the key [6](#0-5) , blocking Alice's legitimate deletion at Mallory's discretion.

Note: I was unable to locate and directly confirm the concrete numeric value of `GasKeyInfo::MAX_BALANCE_TO_BURN` in the indexed content (only referenced via `core/primitives-core/src/account.rs:554` in the architecture spec), so the exact minimum griefing deposit could not be verified in this pass; a Devin session with full repo access would be needed to confirm that constant and any additional guard rails elsewhere in the codebase that this search did not surface.

```rust
fn delete_gas_key(
    config: &RuntimeConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    gas_key_info: &GasKeyInfo,
) -> Result<(), RuntimeError> {
    if gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: Some(Box::new(public_key.clone())),
            balance: gas_key_info.balance,
        }
        .into());
        return Ok(());
    }
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_info.balance).ok_or(IntegerOverflowError)?;
```

```rust
pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
```
