### Title
Funders other than the original payer permanently lose their `fundRequest`/`fund_message` top-ups on timeout because `FeeMetadata` tracks only a single refund recipient for a pooled relayer fee - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.fundRequest()` (and its Substrate analog `pallet_ismp::fund_message`) let any unprivileged account add to the relayer fee of an in-flight POST/GET request or response. The contribution is merged into a single `FeeMetadata.fee` value keyed by commitment, and the existing `sender`/`payer` field is never updated to reflect multiple funders. On timeout, `dispatchTimeOut`/`on_request_timeout` refunds the *entire* accumulated fee to the single `payer` recorded at dispatch time.

### Finding Description
`EvmHost._requestCommitments[commitment]` stores a `FeeMetadata { fee, sender }` struct set once at `dispatch()` time [5](#0-4) . `fundRequest()` allows *any* caller to add `amount` to `metadata.fee` for an existing, still-pending commitment — it does not require the caller to be the original `payer`, nor does it record the funder's identity or their contributed share [1](#0-0) . The Foundry test suite explicitly documents "someone else can fund your request" as intended behavior [6](#0-5) .

When the request subsequently times out, `dispatchTimeOut()` refunds the *whole* `meta.fee` (original fee plus all top-ups from any number of distinct funders) to `meta.sender` only [2](#0-1) . There is no per-funder accounting or pro-rata distribution logic anywhere in the refund path.

The identical pattern exists in `pallet-ismp`'s `fund_message`: any signed account can top up `RequestCommitments`/`ResponseCommitments` fee metadata, merging `message.amount` into the single `metadata.fee.fee`, again without tracking who contributed what [3](#0-2) .

This mirrors the analog bug class exactly: N unprivileged parties each deposit into what is effectively a shared pot (the fee on one commitment), but only one address is entitled to reclaim the whole pot on refund — the "first" or originally-recorded depositor takes everything, and every other funder's deposit is permanently lost.

### Impact Explanation
Any third party that calls `fundRequest`/`fund_message` to help incentivize delivery of someone else's slow-moving cross-chain request is exposed to full, permanent loss of their contributed funds if that request ever times out — the refund goes entirely to the original dispatcher/payer, not to the actual funder. Because `fundRequest` is explicitly documented and tested as being usable by "someone else" (i.e., unprivileged third parties, such as protocol integrators or bots incentivizing delivery on behalf of users), this is a realistic, permanent freezing/misdirection of a third party's funds — a real value-at-risk condition, not merely a rounding/dust issue, since the entire top-up amount can be lost.

### Likelihood Explanation
This requires no special privilege and is reachable through the standard, documented `IDispatcher.fundRequest()` / `fund_message` entry points available to any account. It only requires: (1) a pending, not-yet-delivered request/response, (2) a call to `fundRequest`/`fund_message` by an account other than the original `payer`, and (3) the request eventually timing out (which is a normal, expected outcome for cross-chain messaging and can also be forced by users unwilling to relay). Given that `fundRequest` is marketed specifically as a mechanism to "increase fees for in-flight requests" when gas prices spike (a scenario where timeouts are more, not less, likely), the likelihood of this scenario occurring in production is moderate-to-high.

### Recommendation
Track fee contributions per-funder (e.g., a mapping from commitment to a list/mapping of `(funder, amount)`), and on timeout, refund each funder their own contributed amount rather than paying the entire accumulated fee to the single recorded `sender`/`payer`. Alternatively, restrict `fundRequest`/`fund_message` to only the original `payer` (removing the "someone else can fund your request" capability) so that any single address remains solely and correctly entitled to the full refund.

### Proof of Concept
1. Alice dispatches a POST request via `EvmHost.dispatch()` with `fee = 0`, `payer = alice`. `_requestCommitments[commitment] = {fee: 0, sender: alice}`.
2. Bob calls `fundRequest(commitment, 100e18)`, transferring 100 fee-tokens from himself into the host and updating `_requestCommitments[commitment].fee` to `100e18`. `sender` remains `alice` [7](#0-6) .
3. Carol calls `fundRequest(commitment, 50e18)`, adding her 50 fee-tokens; `_requestCommitments[commitment].fee` becomes `150e18`, `sender` still `alice`.
4. No relayer delivers the request before its timeout elapses.
5. Anyone submits a valid timeout proof; `dispatchTimeOut()` is invoked, calling `onPostRequestTimeout` on Alice's app, then transferring the full `150e18` fee-token balance to `meta.sender` (Alice) [2](#0-1) .
6. Bob and Carol receive nothing back — their combined 150e18 contribution is paid entirely to Alice, who put up none of it.

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
