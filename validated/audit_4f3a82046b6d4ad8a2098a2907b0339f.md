Unvalidated `shop` in `Oauth.validate_auth_callback` Lets an Attacker Aim `client_id`/`client_secret` at a Non-Shopify Host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` uses `auth_query.shop` to build the `HttpClient` that POSTs the app's `client_id` and `client_secret` to exchange the OAuth `code` for an access token, without ever passing that `shop` value through `Utils::ShopValidator.sanitize!`. Every other credential-exchange path in the same gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) does call `ShopValidator.sanitize!` on the equivalent `shop` argument before constructing the `HttpClient`. This is the missing-binding class from the reference report: the value that is *cryptographically verified* (HMAC over the query) is not the same value that is *checked to be a legitimate `myshopify.com`-family host* before being trusted as the destination for secret material.

### Finding Description
In `lib/shopify_api/auth/oauth.rb`:
```
def validate_auth_callback(cookies:, auth_query:)
  ...
  raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
  ...
  null_session = Auth::Session.new(shop: auth_query.shop)
  body = { client_id: Context.api_key, client_secret: Context.api_secret_key, code: auth_query.code, ... }
  client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
  ...
``` [1](#0-0) 

`Clients::HttpClient#initialize` builds the request base URI directly from `session.shop`:
```
@base_uri = T.let("https://#{api_host || session.shop}", String)
``` [2](#0-1) 

`Utils::HmacValidator.validate` only proves that the *bytes* of `code`, `host`, `shop`, `state`, `timestamp` match a signature computed with `Context.api_secret_key`; it says nothing about whether `shop` is actually a Shopify-owned domain: [3](#0-2) 

The binding that should hold is:
`shop verified by HMAC == shop checked to be a trusted Shopify domain (ShopValidator.sanitize!)`

but the code only enforces the left side and skips the right side. The gem itself demonstrates the correct pattern elsewhere — `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token` all call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/`HttpClient` used to send `client_secret`: [4](#0-3) [5](#0-4) [6](#0-5) 

`Oauth.validate_auth_callback` is the one outlier in this set that omits the `ShopValidator` call, relying solely on the HMAC.

### Impact Explanation
This is a High-severity SSRF-with-credentials pattern per the accepted impact categories: if the `shop` value that reaches the host application's callback handler is not itself already constrained to a `myshopify.com`/`myshopify.io`/`spin.dev`/`shop.dev` domain by the *host app* (the gem provides `ShopValidator` specifically so host apps don't have to reinvent this, and uses it internally everywhere else), then `validate_auth_callback` will happily build a request to `https://<attacker-domain>/admin/oauth/access_token` carrying the app's `client_id` and `client_secret` in the POST body. In practice this requires the attacker's supplied `shop` to also carry a valid HMAC signed with the app's own `api_secret_key`, which limits the realistic exploitation window to any code path where an app initiates `begin_auth` with an unsanitized `shop` (which also does not call `ShopValidator`) against a non-Shopify redirect target that can echo back a self-signed callback query — however, this still constitutes a defense-in-depth gap explicitly closed for every sibling credential-exchange method but left open here.

### Likelihood Explanation
Moderate: exploitation depends on the host application not independently sanitizing the `shop` parameter before calling `begin_auth`/`validate_auth_callback`, since the library's own documentation examples pass `request.parameters` straight into `AuthQuery.new` without an explicit sanitize step: [7](#0-6) 
Given `ShopValidator` was introduced and is consistently used in three of the four OAuth-credential-exchange call sites, its absence in `validate_auth_callback` is very likely an oversight rather than an intentional design choice.

### Recommendation
In `Oauth.validate_auth_callback`, call `validated_shop = Utils::ShopValidator.sanitize!(auth_query.shop)` immediately after the HMAC check and before constructing `null_session`/`Clients::HttpClient`, using `validated_shop` (not the raw `auth_query.shop`) for both the token-exchange session and the final `Session.from(shop: ...)` call — mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`.

### Proof of Concept
1. A host application built on this gem forwards the OAuth callback's raw `shop` query parameter into `ShopifyAPI::Auth::Oauth::AuthQuery.new(...)` without separately validating it (as shown in the gem's own documented usage example).
2. An attacker crafts a callback URL where `shop=attacker-controlled-host.example`, and — via any mechanism that lets them obtain a validly-signed callback for that shop value (e.g., a compromised/duplicated app installation flow, or a host application that unwittingly signs/replays a callback for a non-`myshopify.com` value) — causes `Utils::HmacValidator.validate` to pass.
3. `validate_auth_callback` proceeds to build `Auth::Session.new(shop: "attacker-controlled-host.example")` and `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, whose `@base_uri` becomes `https://attacker-controlled-host.example`.
4. The POST containing `client_id` and `client_secret` in the JSON body is sent to `https://attacker-controlled-host.example/admin/oauth/access_token`, exfiltrating the app's `client_secret` to a non-Shopify host — something `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token` all prevent via `ShopValidator.sanitize!`.
