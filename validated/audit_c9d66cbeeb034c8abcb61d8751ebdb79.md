### Title
Pool `repay` refunds a declared-but-never-transferred amount out of real custody — overpayment sized by input, not by measured receipt - (File: contracts/pool/src/ops/repay.rs)

### Summary
The kernel fix in CVE-2025-37923 clamps a copy length to `min(used, PAGE_SIZE)` because the writer trusted a caller-influenced size over the bounded destination. The same shape exists in `ops::repay::accounting`: the overpayment refund is computed from the *declared* `action.amount` minus the outstanding debt, then transferred out of the pool's real token custody, with no check that `amount` was ever paid in. The function's own comment states "The controller transfers the repay amount into the pool before this call" — an unenforced precondition. The analog of "use the smaller of the two" is "refund only `min(declared, measured inbound)`"; the code uses the declared amount unconditionally. A pinned regression test proves the drain end-to-end.

### Finding Description
`accounting` in `contracts/pool/src/ops/repay.rs` resolves the repay via `cache.resolve_repay(amount, position)`, which returns `(burned, overpayment)` where `overpayment` is the portion of the *declared* `amount` above `current_debt_ceil`. `apply` then calls `outcome.cache.transfer_out(payer, outcome.overpayment)`, paying that excess from the pool's token balance. Neither the refund nor `credit_cash(net_repay)` verifies that the pool actually received `amount` tokens for this call — settlement trusts the declared amount instead of measuring the inbound transfer (contrast `payments::balance_delta_since` / `transfer_amount_measured` used by controller strategy legs, and the exact-balance asserts in `ops/flash.rs`).

The test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` in `contracts/pool/tests/flows.rs:3584-3610` documents exactly this: a repay against a market with zero debt makes the whole declared amount an overpayment (`resolve_repay` takes the full-close branch, `net_repay == 0`), the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct, and the entire amount is refunded "out of real custody with the book untouched" — with nothing transferred in. The helper `assert_unfunded_refund_drained_custody` confirms custody decreased while the cash book was unchanged. The file's own comment generalizes the gap: `ops::recapitalize::apply` has the same shape — refund derived from a declared inbound amount, not from the cash book, and neither refund debits `cash` or passes `require_reserves`.

Reachability: `repay` is invoked in the test with a freshly generated `payer` and an arbitrary `PoolAction`; the pool entrypoint imposes no controller-only gate on this leg, so an unprivileged address reaches it directly (repay is also a listed in-scope entrypoint).

### Impact Explanation
Theft of user funds. The pool's token balance backs supplier cash (`cash` book = custody in the fixture guard). An attacker calls `pool.repay` (or `controller.repay`/`recapitalize` where the same declared-amount refund exists) with `action.amount` set to the pool's full custody and a zero/debtless position, receiving a "refund" of tokens they never paid — draining suppliers' underlying liquidity. Even where debt exists, only `amount - debt` is stolen per call, so debt does not cap the attack: repay any dust debt and declare `amount = custody + debt`. This is a direct, single-transaction theft reachable by any address.

### Likelihood Explanation
Deterministic and permissionless: no price manipulation, no timing, no privileged role, no defective token required. The only preconditions are a market whose `borrowed` is less than the declared amount (trivially satisfiable, including a fully repaid or unused market) and an `amount` value the token transfer can encode. The pinned test already reproduces the drain with a generated payer, zero debt, and `amount = custody_before`, so exploitation requires no novel path — it is the documented behavior of the refund branch.

### Recommendation
Measure the inbound transfer rather than trusting `action.amount`: snapshot the pool's token balance before the repay leg and compute the applied/refundable quantities from `min(declared_amount, measured_inbound)`, or require `overpayment <= balance_delta` in `apply`. Apply the identical fix to `ops::recapitalize::apply`, which the code comments acknowledge shares the same unfunded-refund gap. The existing measured-receipt helpers (`transfer_amount_measured`, `balance_delta_since` in `contracts/controller/src/payments.rs`) are the established pattern to reuse.

### Proof of Concept
Pinned in-repo: `contracts/pool/tests/flows.rs:3589-3610` (`test_unfunded_repay_overpayment_refund_also_pays_out_of_custody`). Steps: supply the pool so `cash == custody` and `borrowed == 0`; from a fresh address call `repay` with `PoolAction { position.scaled_amount: 0, amount: custody_before }`; `resolve_repay` returns `overpayment = custody_before`, `net_repay = 0`, and `transfer_out` moves the full custody to the payer while `cash` and `revenue` are unchanged — `assert_unfunded_refund_drained_custody` verifies the drain. Repeating the construction against any market with debt `D` by declaring `amount = D + target` yields the same theft bounded only by pool custody.

Confidence note: I verified the refund path, the pinned failing-custody test, and that the test's payer is an unprivileged generated address; I did not fully re-confirm every auth gate on the public `repay` entrypoint signature in `contracts/pool/src/lib.rs`, but the test exercises it without controller context, which demonstrates reachability.
