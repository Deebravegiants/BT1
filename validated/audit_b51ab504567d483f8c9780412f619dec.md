### Title
Batch-wide `BridgeNotFoundError` in one withdrawal corrupts the status promise of every other unrelated withdrawal - (File: packages/intents-sdk/src/sdk.ts)

### Summary
`createWithdrawalCompletionPromises` builds a single shared `widsPromise` via `createWithdrawalIdentifiers` and every per-index promise `await`s that same shared promise before doing any index-specific work. If resolving identifiers for any single withdrawal in the batch fails (`BridgeNotFoundError`), the shared promise rejects and **every** per-index promise in the array rejects with that same error, regardless of whether that individual withdrawal is valid, supported, and already executing/executed on-chain.

### Finding Description
The claimed invariant is: `promise[i]`'s rejection reason should reflect the actual on-chain state of withdrawal `i` only.

Code path:
- `sdk.ts:562-566` — a single shared promise is created: `const widsPromise = createWithdrawalIdentifiers({ bridges, withdrawalParams, intentTx })`.
- `sdk.ts:573-608` — `withdrawalParams.map(async (_, index) => { const wids = await widsPromise; const entry = wids[index]; ... })`. Every closure awaits the *same* `widsPromise`.
- `withdrawal-watcher.ts:80-107` — `createWithdrawalIdentifiers` iterates the array with a plain `for` loop and calls `throw new BridgeNotFoundError()` as soon as `findBridgeForWithdrawal` returns `undefined` for **any** entry, aborting resolution for the whole array. There is no per-index isolation (e.g. `Promise.allSettled`), and the function does not partially resolve — it's all-or-nothing.

Because all `index` closures depend on this single shared promise, a `BridgeNotFoundError` thrown while resolving the identifier for withdrawal `j` (e.g. an unsupported `assetId`/`routeConfig` combination that no `bridge.supports()` accepts) causes `widsPromise` to reject, which in turn causes `promise[i]` for every other index `i` (including `i` before `j` in the array, whose withdrawal may already be signed/broadcast and successfully completing on the destination chain) to reject with the identical `BridgeNotFoundError`. This is confirmed directly from the code with no per-index try/catch or `Promise.allSettled` isolation anywhere in this path.

`routeConfig`/`assetId`/`destinationAddress` are exactly the kind of counterparty-supplied strings an integrator forwards into the SDK (explicitly listed as attacker-controlled in the rules), so a malicious counterparty can supply a withdrawal leg with an assetId/routeConfig combination unsupported by any configured bridge (`bridge.supports()` returns `false` for all bridges) alongside an otherwise-valid, already-executing withdrawal leg in the same batch.

No existing guard prevents this: `findBridgeForWithdrawal`/`supports()` ordering only determines which bridge handles a *given* index — it does nothing to isolate failures between indices; there is no `Promise.allSettled`, per-index try/catch, or partial-result handling in `createWithdrawalIdentifiers` or `createWithdrawalCompletionPromises`.

### Impact Explanation
An integrator that follows the documented per-promise API (`for (const promise of promises) { promise.then/catch(...) }`, as shown in the SDK's own JSDoc example at `sdk.ts:544-554`) will see the promise for a healthy, already-executed withdrawal reject with `BridgeNotFoundError`. If the integrator's error-handling logic treats a rejected withdrawal-status promise as "this withdrawal failed" and triggers a refund/credit, the user (or counterparty) can force the integrator to double-pay: once via the successful on-chain withdrawal and once via the improperly triggered refund. This matches the "a status or hash misreport making an integrator credit or refund twice" High-severity category, and is deterministic and repeatable in any batch containing one unsupported leg.

### Likelihood Explanation
Preconditions: the integrator must call `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` with a batch (`withdrawalParams` array) containing more than one withdrawal, where at least one entry is a valid/supported route and at least one other entry has an assetId/routeConfig combination unsupported by any registered bridge. An unprivileged counterparty who controls the destination asset/route parameters for one leg of a multi-withdrawal intent can trigger this every time such a batch is processed — no special privileges, timing races, or infrastructure compromise required. It is fully deterministic (confirmed by tracing `createWithdrawalIdentifiers`'s all-or-nothing `for` loop) rather than probabilistic.

### Recommendation
Resolve withdrawal identifiers per-index independently instead of via one shared promise, e.g., change `createWithdrawalIdentifiers` to return a `PromiseSettledResult` per index (or wrap each `findBridgeForWithdrawal`/`createWithdrawalIdentifier` call in its own try/catch), and have each `map` closure in `createWithdrawalCompletionPromises` reject only with the error pertaining to its own index. Never let an error for withdrawal `j` propagate to the promise for withdrawal `i`.

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
