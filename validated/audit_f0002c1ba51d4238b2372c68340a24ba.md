I found a solid analog to the reroll-DNA binding gap: the webhook HMAC in this gem only signs the raw body, while the `shop` (tenant) is taken from an unsigned header field, breaking the identity binding `HMAC-covered bytes == bytes trusted for tenant attribution`.### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while the tenant-identifying `shop` value is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed content [2](#0-1) . `Registry.process` validates only the body's HMAC and then forwards the unauthenticated `shop` header value to the app's webhook handler as the tenant identity [3](#0-2) .

### Finding Description
The identity binding that should hold is: `bytes verified by HMAC == bytes trusted for tenant attribution`. Here that equality is broken:
- Verified bytes: `@raw_body` only [4](#0-3) , checked against `Utils::HmacValidator.validate(request)` [5](#0-4) .
- Trusted-for-attribution bytes: the `shop-domain` header, exposed via `Request#shop` and passed straight into `WebhookMetadata.new(shop: request.shop, ...)` for the handler [2](#0-1) [6](#0-5) .

Because the `topic`, `shop-domain`, `api-version`, and `webhook-id` headers are excluded from the HMAC computation, a valid signature only proves that Shopify (holder of `client_secret`) produced that exact JSON body at some point — it proves nothing about which shop, topic, or webhook-id the body is associated with. Any unprivileged actor who can install the app on their own store (a normal, unprivileged action for any public/embeddable app) will receive real, validly-signed webhook deliveries containing their own shop's body and a valid HMAC. This confirms as a matter of code review that `hmac`, `topic`, and `shop-domain` are three independent header/body fields, verified only in the "hmac-sha256 over body" dimension, while `Registry.process` uses `shop-domain` unconditionally as ground truth for the tenant the payload is "about" [7](#0-6) .

### Impact Explanation
This satisfies the "field acted on but not covered by the HMAC" analog: the app's webhook handler consumes `data.shop` (and `data.topic`/`data.webhook_id`) to decide what tenant/record to act on, but none of these values are cryptographically bound to the body they arrive with. An attacker who controls the delivery of the HTTP request to the app's webhook endpoint (e.g., replaying/relaying a captured legitimate delivery with a substituted `shop-domain`/`topic` header, which is possible whenever the endpoint is reachable over plain HTTP or via any intermediary that is not the literal Shopify-to-app TLS channel) can cause the app to process an attacker-supplied, validly-HMAC'd body under an arbitrary victim shop identity. This is a cross-tenant identity-binding gap: the gem gives host applications a `shop` value that looks HMAC-verified (it comes from a `Request` object whose HMAC validation already succeeded) but is in fact attacker-controllable independent of that verification.

### Likelihood Explanation
This is a Medium/High-likelihood-of-misuse issue rather than a directly exploitable network attack from this gem alone: the gem's public API only proves "body was signed by this app's secret"; it does not claim to prove "and this body came addressed to this shop/topic." Because the gem exposes `request.shop` and `request.topic` as if they were validated fields (they sit right next to `hmac`, all satisfying the same `VerifiableQuery` interface conceptually), host applications reasonably but incorrectly rely on them as authenticated. Exploitation still requires an attacker able to influence the exact bytes/headers delivered to the app's webhook endpoint (e.g., a reverse proxy misconfiguration, non-TLS delivery path, or any component that forwards Shopify webhooks with attacker-modifiable headers) — this is consistent with the "SSRF/credential-leak/cross-tenant" bug classes accepted by the rules, since it directly produces cross-tenant data corruption/processing without requiring the attacker to hold `api_secret_key` or an access token.

### Recommendation
Include the tenant- and topic-identifying headers in the signed content that the HMAC covers, or otherwise cryptographically bind them (e.g., compute the signature over `shop-domain|topic|webhook-id|raw_body` instead of `raw_body` alone) in `ShopifyAPI::Webhooks::Request#to_signable_string`. At minimum, document clearly that `Request#shop`, `Request#topic`, and `Request#webhook_id` are NOT covered by the HMAC and must not be treated as authenticated by host applications without additional verification (e.g., cross-checking against the shop associated with the currently registered webhook subscription).

### Proof of Concept
1. App registers a webhook (e.g., `orders/create`) and exposes an HTTP endpoint that calls `ShopifyAPI::Webhooks::Registry.process(request)`.
2. Attacker installs the app on their own throwaway shop `attacker.myshopify.com` and triggers an `orders/create` event, capturing the legitimate Shopify delivery: raw body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`).
3. Attacker (or any intermediary capable of manipulating the request before it reaches the app, e.g., a compromised/naive proxy) resends the same body `B` and header `H` to the app's webhook endpoint but with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` still succeeds because it only checks `HMAC(client_secret, B) == H` [8](#0-7) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body_of_B, ...)` [3](#0-2) , causing the app to process attacker-controlled order data as if it belonged to `victim.myshopify.com`.
