### Title
Cross-identity face/iris frame mixing bypasses identity-binding in `Plan::is_success` — ([File: src/plans/biometric_capture/mod.rs])

### Summary
`Plan::is_success` and `into_capture` only check that all five frame slots (`left_ir`, `left_rgb`, `right_ir`, `right_rgb`, `self_custody_candidate_rgb`) are `Some`, with no cross-check that the iris frames and the self-custody face frame belong to the same physical person. The only downstream mechanism that could enforce this — the "fraud checks" run in `biometric_pipeline`/`fraud_check.rs` — is a stub that always returns an empty `Report{}` (`N_FRAUD_CHECKS = 0`), so no actual identity-consistency verification exists in this repo build.

### Finding Description
`handle_ir_net`/`handle_rgb_net` populate `left_ir`/`right_ir`/`left_rgb`/`right_rgb` purely from per-frame sharpness/score/side thresholds [1](#0-0) . `handle_face_identifier` independently swaps in a new `self_custody_candidate_rgb` whenever a later frame's `output.score` exceeds the previous highest score, with no comparison against the iris/eye frames already captured [2](#0-1) . `is_success` merely checks presence of all five `Option`s [3](#0-2) , and `into_capture` unconditionally merges whatever frames are in those slots into a single `Capture` [4](#0-3) . There is no embedding/identity comparison at this layer, so an attacker (subject A) and an accomplice (subject B) swapping places during the session — A providing sharp iris/eye RGB frames, B momentarily presenting a higher-scoring face for `self_custody_candidate_rgb` — produces a `Capture` that passes `is_success` and proceeds to `into_capture`/`biometric_pipeline`.

Downstream, the `Capture` is fed into `biometric_pipeline::Plan::new`, which sends `frame_left`, `frame_right`, and `frame_self_custody_candidate` to the `FaceIdentifier::Estimate` model, producing `fraud_checks: FraudChecks` and `bundle: Bundle` [5](#0-4) . This is the theoretical enforcement point for identity consistency across the three face-bearing frames. However, in this repository, `fraud_check.rs` is a stub: `N_FRAUD_CHECKS = 0`, `fraud_checks()` returns `[]`, `fraud_detected()` iterates an empty array and always returns `false`, and `FraudChecks::run()` returns an empty `Report{}` [6](#0-5) . Additionally, the Python `FaceIdentifier::estimate` stub in this build returns a hardcoded fixed embedding/bundle without performing any actual identity comparison [7](#0-6) . Thus even the one call site designed to accept multiple face-bearing frames for cross-checking performs no real identity consistency validation in this codebase.

### Impact Explanation
If exploitable, this allows a "successful" signup whose IR iris data (used for iris code enrollment, biometric matching, and dedup) originates from one physical person (subject A), while the self-custody face bundle (used for image-based recovery/self-custody flows and thumbnail/embeddings uploaded via `personal_custody_package`) originates from a different person (subject B) [8](#0-7) . This is a wrong-identity/composite-identity binding under a single `signup_id`, which is a scoped, real integrity impact matching "wrong identity binding" bounty categories.

### Likelihood Explanation
The described attack requires two people cooperating within the same signup session and requires the accomplice's face to be judged as valid (`is_valid == true`) with a higher `score` than the true subject's earlier face frames — feasible since `handle_face_identifier`'s selection is a pure greedy score-max with no identity gate. In this stubbed build, there is no fraud-check or backend-side rejection based on cross-frame identity mismatch (`fraud_checks_strict` always yields "no fraud"), so nothing in the traced code path would block or flag it. Feasibility depends on whether a production (non-FOSS/stubbed) build of `face_identifier`/`fraud_check` performs real identity-similarity checks — this repository's visible implementation does not.

### Recommendation
Add an identity-consistency check in `biometric_capture::Plan` (or immediately after `into_capture`) that compares face-embedding/similarity between `left_rgb`/`right_rgb` frames and `self_custody_candidate_rgb` before accepting the capture as successful, rejecting or resetting slots on mismatch rather than relying solely on independent per-frame score thresholds. Ensure the fraud-check / face-identifier cross-check (`FraudChecks`, `FaceIdentifier::Estimate`) actually performs and enforces a same-identity comparison across `frame_left`, `frame_right`, and `frame_self_custody_candidate`, and that a failed check blocks signup rather than only producing telemetry.

### Proof of Concept
Integration test plan for `Plan` in `src/plans/biometric_capture/mod.rs`:
1. Construct `Plan` via `Plan::new` with test wavelengths.
2. Simulate `handle_ir_net`/`handle_rgb_net` calls with frames/estimates tagged as "identity A" for both left and right eye objectives, satisfying `IRIS_SCORE_MIN`/brightness/side conditions to populate `left_ir`, `left_rgb`, `right_ir`, `right_rgb`.
3. Simulate two `handle_face_identifier` calls: first with a lower-score "identity A" face frame, then with a higher-score "identity B" (accomplice) face frame with `is_valid = true`.
4. Assert `self_custody_candidate_rgb` now holds the "identity B" frame (demonstrating the swap succeeded), and that `is_success()` returns `true`.
5. Assert that no mechanism in `Plan` rejects this state — expected (failing) invariant: a same-identity cross-check between `left_rgb`/`right_rgb` and `self_custody_candidate_rgb` embeddings should fail and prevent `is_success` from returning `true`, but current code has no such check, and downstream `fraud_check::Report::fraud_detected()` will also return `false` for any such input given `N_FRAUD_CHECKS = 0`.

/// User feedback message types in case of failed pipeline.
/// This is not an exhaustive list of the true failure modes, the true
/// failure modes are more low level. This list doesn't include the actual
/// fraud based failure modes.
#[derive(Debug, Clone, SerdeSerialize, JsonSchema)]
pub enum PipelineFailureFeedbackMessage {
    /// Contact Lenses detected
    ContactLenses,
    /// Face occluded by eye glasses detected
    EyeGlasses,
    /// Face occluded by mask
    Mask,
    /// Generic face occlusion
    FaceOcclusion,
    /// Multiple faces during signup
    MultipleFaces,
    /// Eyes were occluded during signup
    EyesOcclusion,
    /// Head pose not straight up
    HeadPose,
    /// Underaged
    Underaged,
    /// Poor Image Quality
    LowImageQuality,
}

impl Report {
    const DATADOG_TAGS: [&'static str; N_FRAUD_CHECKS] = [];

    fn fraud_checks(&self) -> [Option<bool>; N_FRAUD_CHECKS] {
        []
    }

    /// If fraud data are missing, we assume fraud is detected.
    fn fraud_checks_strict(&self) -> [bool; N_FRAUD_CHECKS] {
        self.fraud_checks().map(|v| v.unwrap_or(true))
    }

    fn enabled_checks_from_config(_config: &BackendConfig) -> [bool; N_FRAUD_CHECKS] {
        []
    }

    fn feedback_messages() -> [Option<PipelineFailureFeedbackMessage>; N_FRAUD_CHECKS] {
        []
    }

    /// Get the || result of all fraud checks, but under the Orb configuration.
    /// The end result might be different from the || of all fraud booleans as
    /// we might decide to not block a signup even if it's fraudulent.
    #[must_use]
    pub fn fraud_detected_with_config(
        &self,
        config: &BackendConfig,
    ) -> (bool, Vec<PipelineFailureFeedbackMessage>) {
        let enabled_checks = Self::enabled_checks_from_config(config);
        let fraud_results = self.fraud_checks_strict();
        let feedback_msgs = Self::feedback_messages();

        let feedback: Vec<PipelineFailureFeedbackMessage> = enabled_checks
            .iter()
            .zip(fraud_results.iter())
            .zip(feedback_msgs.iter())
            .filter_map(
                |((&enabled, &result), feedback_msg)| {
                    if enabled && result { feedback_msg.clone() } else { None }
                },
            )
            .collect();

        (!feedback.is_empty(), feedback)
    }

    /// If any fraud check fails or is missing data, fraud is reported.
    #[must_use]
    pub fn fraud_detected(&self) -> bool {
        self.fraud_checks_strict().iter().any(|&v| v)
    }

    /// Report fraud checks as Datadog tags.
    pub fn as_datadog_tags(&self) -> impl Iterator<Item = String> {
        Self::DATADOG_TAGS.iter().zip(self.fraud_checks()).map(|(tag, res)| {
            format!("{}{}", tag, res.map_or("none".to_owned(), |b| b.to_string()))
        })
    }

    /// Report fraud checks as Datadog tags, but exclude reports of any fraud
    /// check that is not enabled in config.
    pub fn as_datadog_tags_with_config(
        &self,
        config: &BackendConfig,
    ) -> impl Iterator<Item = String> {
        self.as_datadog_tags()
            .zip(Self::enabled_checks_from_config(config))
            .filter_map(|(tag, is_enabled)| is_enabled.then_some(tag))
    }
}
