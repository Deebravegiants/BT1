### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then passes the `shop` value taken from an **unauthenticated header** to the app's `WebhookHandler`. Because the `X-Shopify-Shop-Domain` header is not part of the signed payload, any actor who can produce one genuinely-HMAC-signed webhook body (e.g. by installing the app on their own store and receiving a real webhook) can replay that same body/HMAC pair while substituting an arbitrary value for the shop-domain header, and the gem will report it as a validly-authenticated webhook "from" that arbitrary shop.

### Finding Description
`Registry.process` performs authentication like this: [1](#0-0) 

The HMAC check itself only covers the raw HTTP body: [2](#0-1) 

`hmac` is derived from the `hmac-sha256` header and `to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from HTTP headers that are never mixed into the signable string: [3](#0-2) 

`HmacValidator.validate` confirms only that `to_signable_string` (the body) matches the secret-derived signature — it has no knowledge of, and does not bind, the `shop` header: [4](#0-3) 

The broken identity binding is:
`shop_the_HMAC_actually_authenticates (implicit: whichever shop Shopify generated this signed body for) == shop_the_gem_hands_to_the_handler (request.shop, read from an unauthenticated header)`

These are not the same value once an attacker can control the header independently of the body, since only the body is covered by the signature.

### Impact Explanation
Any party capable of installing the target app on a shop they control (a normal, unprivileged flow) can capture one legitimately Shopify-signed webhook body/HMAC pair for their own shop, then replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to a victim shop's domain. `Registry.process` will pass HMAC validation (body/signature match untouched) and invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain: [5](#0-4) 

Any host application that uses this `shop` value to key per-tenant state, trigger per-tenant side effects, or select which merchant's data/session to act on (the documented and expected usage pattern of `WebhookMetadata.shop`) will attribute attacker-supplied webhook content to a shop the attacker does not own — a cross-tenant data-integrity/confusion issue reachable by an unprivileged app installer, without needing the app's `api_secret_key` or any merchant's access token.

### Likelihood Explanation
Moderate-to-high: exploitation requires only (1) becoming an app user/installer on any shop (a normal, low-privilege action for public or even single-tenant apps that many actors can perform), and (2) capturing and replaying one legitimately delivered webhook while modifying a header field — no cryptographic secret is required since the header is simply not part of what's signed.

### Recommendation
Include the shop domain (and other Shopify identity headers relied upon downstream, e.g. `topic`) in the HMAC-signed material verified by the gem, or otherwise cryptographically bind `request.shop` to the signed body before exposing it via `WebhookMetadata`. At minimum, document loudly that `shop`/`topic`/`webhook_id` are unauthenticated and must be independently corroborated (e.g., cross-checked against the session/shop that the app expects to receive that topic from) by host applications before being trusted for tenant attribution.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `X-Shopify-Hmac-Sha256: <valid-for-body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same body and HMAC header to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` builds the request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC: [1](#0-0) 
4. The registered `WebhookHandler#handle` is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, even though Shopify never generated or authorized a webhook naming that shop.
