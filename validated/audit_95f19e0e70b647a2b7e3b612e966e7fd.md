### Title
Untrusted route XDR invokes arbitrary contracts under the caller's signed auth tree, letting a rogue hop pool drain the signer's wallet - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
The swap aggregator decodes a fully user-controlled `StrategyPayload` (`assets` registry + instruction stream) and calls whatever `pool` address each hop names, with no venue or pool allowlist. When the `sender` is an end user calling `execute_strategy` directly, or a lender user signing a `swap_collateral` / `swap_debt` / `multiply` / `repay_debt_with_collateral` authorization tree, a malicious route can place attacker code on the call stack beneath the caller's `require_auth` entry. That code can issue `token.transfer(caller, attacker, amount)` for any token the caller holds; Soroban simulation records it as a child of the caller's authorization, and if the caller signs the simulated tree the theft executes. This is the on-chain analog of CVE-2025-3466: unsanitized input is executed as code with the caller's privileges before any security boundary applies.

### Finding Description
`execute::run` decodes `ops`/`assets` purely by shape (`Program::decode` checks indices and modes, never address identity), then `execute_op` builds a `SwapHop` whose `pool` field is `ctx.assets.get_unchecked(op.idx_a)` — an address fully supplied by the payload [1](#0-0) . `dispatch_hop` then invokes venue adapters that call `env.invoke_contract(&ctx.hop.pool, ...)` on that arbitrary address [2](#0-1) . The only signature in the whole flow is `sender.require_auth()` [3](#0-2) , so any `from.require_auth()` a rogue pool issues for a `token.transfer(sender, ...)` resolves against the sender's signed authorization tree.

The controller path grants the router only a scoped invoker-contract auth (`authorize_transfer_as_current` for the exact input pull, then `router.execute_strategy(controller, amount_in, swap)`) [4](#0-3) , which protects the controller's own balances. But the *user's* signature on `swap_collateral` covers the whole recorded tree, and the router keeps no allowlist of the pool or token addresses its payload names. The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the full mechanics: a rogue hop pool calling `token.transfer(alice, attacker, WALLET_BALANCE)` is recorded under Alice's `swap_collateral` auth entry in simulation mode, is rejected only if she signs a tree without it, and executes fully when she signs the simulation-produced (poisoned) tree — draining 77,770,000,000 units of a token the protocol never listed [5](#0-4) . The threat model itself documents that "the router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization... The loss is then the caller's wallet, not the routed amount" [6](#0-5) .

### Impact Explanation
Theft of user funds far exceeding the routed amount. The attacker does not need to steal the swap output — the venue output, `min_out`, `RouterOverspend`, and `NoSwapOutput` checks are all satisfiable honestly while the rogue pool simultaneously issues a `transfer` for every liquid token in the victim's wallet (any SEP-41 token, not just listed assets). For direct `execute_strategy` callers the exposure is unconditional on signing the simulated tree; for controller entrypoints (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, `flash_position` strategies carrying a `StrategySwap`) the same applies to the account owner's signature. Wallets and clients that sign the simulator-returned auth tree verbatim — the standard Soroban flow — are exploitable.

### Likelihood Explanation
A single unprivileged attacker crafts a route quoting a fair or slightly-better price and distributes it to victims (fake quote API, phishing frontend, malicious aggregator UI). The victim must sign the simulation-produced tree; since honest routes produce a tree with only the input transfer child, the attack reduces to whether the client inspects children — which the threat model explicitly admits is the only defense ("a client must decode the route it signs and refuse an authorization tree with any other child"). The attacker pays only gas; success steals the victim's entire wallet balance of the targeted token. No privileged role, timing, or oracle condition is required. Rated High: requires victim interaction (signing a poisoned route) but yields unbounded wallet theft.

### Recommendation
Enforce an on-chain allowlist of callable venue pool addresses in the router (owner-managed, verified at `execute_op`/`dispatch_hop` time before any `invoke_contract`), or constrain hop pools to addresses resolvable from a venue registry rather than the attacker-controlled `assets` array. Additionally, pin the `token_in`/`token_out` addresses of each hop against a declared pair and reject any token address not declared in the program header. Until pool allowlisting exists, document and enforce at the client layer that a signed auth tree for `execute_strategy` must contain exactly one child (the input `transfer`), and for controller strategies exactly the children an honest route produces.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`, which demonstrates end-to-end:

1. Attacker deploys `RogueHopPool` whose `swap` executes `token::Client::new(&env, &wallet_token).transfer(&victim, &attacker, &amount)` [7](#0-6) .
2. A `RoutedSwap` route names the rogue pool as `hop_pool`; `UnlistedPoolRouter.execute_strategy` performs `sender.require_auth()`, pulls `total_in`, invokes the named pool, and returns fair output — mirroring the real router's lack of an address allowlist [8](#0-7) .
3. In recording mode (what `simulateTransaction` returns to a signing client), the wallet drain is attached as a child of Alice's `swap_collateral` entry: `assert_eq!(recorded, vec![(alice, poisoned_root)])` [9](#0-8) .
4. In enforcing mode, signing the simulation tree executes the theft: `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while the protocol-level swap still settles normally (`supply_balance_raw(ALICE, "ETH") == FAIR_OUT_ETH`) — every slippage and risk gate passes [10](#0-9) .

The identical exposure exists for a direct `execute_strategy` caller, since `run` performs only `sender.require_auth()` and the venue call inherits the caller's signed tree.

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
