## Analog Found

### Title
Attacker can front-run `EvmHost.dispatch()`/`fundRequest()` native-fee swaps to DoS message dispatch or drain user's overpaid ETH buffer - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` let a caller pay the Hyperbridge relayer fee in native ETH by having the host perform an on-chain Uniswap V2 `swapETHForExactTokens` for an exact `fee`/`amount` of `feeToken`, exactly analogous to the `InfiltrationPeriphery.healWithEth()` pattern in the referenced report.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)` and `fundRequest()`: [2](#0-1) [3](#0-2) 

Each of these dispatches ETH sent via `msg.value` through `swapETHForExactTokens(post.fee, path, address(this), block.timestamp)` against the pool the host is configured to use (`_hostParams.uniswapV2`). This is the same "exact-output amid an attacker-manipulable AMM price" pattern the report flags: the WETH/`feeToken` pool price can be pushed up by any attacker in a front-run, no privilege required, since anyone can trade against the configured Uniswap V2 pool.

Two consequences mirror the report's two scenarios:
1. **DoS**: if a user sizes `msg.value` tightly to the fee needed at current price, an attacker front-running the `dispatch`/`fundRequest` call by buying `feeToken` inflates its price; the router then needs more ETH input than `msg.value` provides and `swapETHForExactTokens` reverts, so the dispatch (or timely `fundRequest` top-up before timeout) fails.
2. **Loss of user's slippage buffer**: `swapETHForExactTokens` refunds unused ETH to `msg.sender` of the router call — which is `EvmHost` itself (since `EvmHost` is the direct caller of the router), not the original transaction sender. Any ETH a user over-sends as a slippage cushion is retained by the `EvmHost` contract rather than returned to the user, so users who pad `msg.value` to avoid the DoS above lose the excess permanently — it becomes stuck host balance recoverable only via governance's `withdraw` path, not returned to the original payer.

The team's own documentation confirms the underlying price-manipulation exposure of this fee-swap design and explicitly separates it from the on-chain `dispatch` payment path, but only warns against using the *view* `quote()` helper off-chain — it does not address the exact-output swap executed inside `dispatch`/`fundRequest` itself: [4](#0-3) 

### Impact Explanation
An attacker can, from a single transaction of their own (no privilege needed), reliably prevent specific users from dispatching cross-chain POST/GET requests paid in native token, or from topping up (`fundRequest`) a pending request's relayer fee before it times out on the destination chain — a route-unable-to-deliver-messages condition for that request. Additionally, refunded ETH from the router swap is misdirected to the `EvmHost` contract instead of the caller, causing a permanent loss of the user's overpaid native token (unbacked by any corresponding fee-token credit), which the user cannot reclaim.

### Likelihood Explanation
Any address can submit ordinary swap transactions against the same Uniswap V2 pool the host uses for `WETH -> feeToken` (`_hostParams.uniswapV2`), and can observe pending `dispatch`/`fundRequest` transactions in the mempool to front-run them. No special permissions, governance access, or insider knowledge are required — this is reachable by any unprivileged sender of a `dispatch()`/`fundRequest()` transaction, matching the "attacker can prevent user healing" reachability of the original report.

### Recommendation
- Replace `swapETHForExactTokens` with a caller-supplied `amountOutMinimum`/`deadline` pattern where the user explicitly bounds acceptable slippage rather than the host silently reverting on shortfall or absorbing excess.
- Route the router's leftover-ETH refund back to the actual transaction sender (`_msgSender()`/`post.payer`) rather than leaving it credited to `EvmHost`, e.g. by tracking `address(this).balance` before/after the swap and forwarding the delta to the payer.
- Consider quoting via a TWAP or requiring fee-token payment for latency-sensitive `fundRequest` top-ups, since these must land before a request's timeout, and are especially exposed to a griefing front-run that only needs to hold the DoS window open long enough for timeout.

### Proof of Concept
1. User calls `IDispatcher(host).dispatch{value: v}(post)` where `v` was sized off-chain to just cover `post.fee` in `feeToken` at the current WETH/`feeToken` V2 pool price.
2. Attacker observes the pending transaction and front-runs it with a large `feeToken`-buying swap on the same V2 pool, raising the WETH/`feeToken` price.
3. User's transaction executes `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: v}(post.fee, path, address(this), block.timestamp)` (`evm/src/core/EvmHost.sol:927-929`); since `v` is now insufficient to buy `post.fee` tokens at the manipulated price, the router reverts with `INSUFFICIENT_INPUT_AMOUNT`, causing the whole `dispatch` (and thus the cross-chain message) to fail.
4. Alternatively, if the user instead over-provisions `v` as a slippage buffer to avoid failure, any leftover ETH from the swap is refunded to `EvmHost` (the router's caller) instead of the user, permanently stranding the user's buffer in the host contract.
