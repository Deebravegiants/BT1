### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely via `Utils::HmacValidator.validate(request)`, and that validation is computed over `Request#to_signable_string`, which returns only the raw HTTP body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's handler are read directly from HTTP headers and are never included in the signed content [2](#0-1) .

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [3](#0-2) 

`HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns `@raw_body` only [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from the `shopify-*`/`x-shopify-*` headers with no cryptographic binding to that HMAC [2](#0-1) .

This breaks the identity binding the gem's own validation is supposed to establish:
`HMAC(secret, signed_bytes) == received_hmac` should imply `tenant_identified_by_shop == tenant_that_produced_signed_bytes`, but here `signed_bytes = raw_body` while `tenant_identified_by_shop = header value`, i.e. **bytes verified ≠ bytes parsed for tenant identity**. Any request whose body+hmac pair is valid for the secret will pass validation regardless of what `shop` (or `topic`/`webhook_id`) header accompanies it, because those fields are never part of `to_signable_string`.

The gem's own documentation instructs host apps to trust `data.shop` from `WebhookMetadata` as the shop the event pertains to, and to use it directly for shop-scoped work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [5](#0-4)  and [6](#0-5) . Nothing in the gem cross-checks that the shop header is consistent with anything cryptographically verified.

### Impact Explanation
An attacker who is a merchant on their own Shopify store receives genuine, validly-signed webhooks from Shopify for their own store's events (the body and HMAC are legitimate and observable by them, since it is delivered to an endpoint they control/receive). Because the HMAC only signs the body, the attacker can replay the exact same `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a value naming a different, victim shop. `HmacValidator.validate` still succeeds (it never inspected those headers), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop, with the attacker's own body content. Any host application that follows the documented pattern and uses `data.shop` to select the tenant/session or gate shop-scoped side effects (queueing jobs, updating per-shop state, GDPR redact processing, cache invalidation, etc.) will process attacker-supplied data under the victim shop's identity — a cross-tenant data/identity confusion enabled entirely by this gem's request/validation design.

### Likelihood Explanation
Exploitation requires only:
1. The attacker to install/operate the target app on their own store (unprivileged, self-service action any Shopify merchant can take) to obtain at least one valid `(body, hmac)` pair.
2. The ability to send an arbitrary POST with custom headers to the app's public webhook endpoint (the endpoint address is typically discoverable/documented as `path` in `add_registration`) [7](#0-6) .

No access token, `client_secret`, or privileged credential is required — the attacker only needs the `api_secret_key`-independent ability to capture their own legitimately-delivered webhook once. This is fully within reach of an "unprivileged internet user" as defined by the rubric.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` values into the material that is HMAC-verified (e.g., include them, or a canonical representation combining them with the body, in `to_signable_string`), or otherwise require the host application/gem to independently verify that `request.shop` corresponds to a shop domain the app has an active, previously-established session/install record for before trusting `WebhookMetadata#shop`. At minimum, document prominently that `shop`/`topic`/`webhook_id` are **not** covered by the HMAC and must be independently validated by the host application against known installed shops before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook, e.g. `orders/create`, to the app's endpoint. Attacker captures the raw body `B` and the real `x-shopify-hmac-sha256` header `H` (valid because Shopify computed `HMAC(secret, B) = H`).
2. Attacker sends a new POST to the same public webhook endpoint with:
   - body = `B`
   - `x-shopify-hmac-sha256` = `H`
   - `x-shopify-shop-domain` = `victim-shop.myshopify.com` (instead of their own domain)
   - `x-shopify-topic`, `x-shopify-webhook-id` unchanged or freely modified.
3. `ShopifyAPI::Webhooks::Request.new` builds a `Request` whose `to_signable_string` returns `B` [1](#0-0) ; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and it matches `H`, so validation succeeds [8](#0-7) .
4. `Registry.process` invokes the host handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)` [3](#0-2) , causing the app to process attacker-controlled event data as if it originated from `victim-shop.myshopify.com`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
