### Title
Token Exchange sends the app's `client_secret` to a shop host taken from an unvalidated JWT claim - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` derives the destination host for the OAuth token-exchange POST directly from the JWT `dest` claim without ever passing it through `Utils::ShopValidator.sanitize!`, unlike the sibling methods `migrate_to_expiring_token` and `ClientCredentials.client_credentials`, which both sanitize the `shop` value before building a session/host. This breaks the intended equality "host that is validated as a trusted Shopify domain == host that receives the `client_id`/`client_secret`" for this specific code path.

### Finding Description
`TokenExchange.exchange_token` does:
```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
body = { client_id: ..., client_secret: ShopifyAPI::Context.api_secret_key, ... }
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
``` [1](#0-0) 

`JwtPayload#shop` simply strips `"https://"` off the `dest` claim [2](#0-1) , and `JwtPayload#initialize` only checks `aud == Context.api_key`; it never checks that `dest`/`iss` is a real, trusted Shopify domain (e.g. via `ShopValidator`) [3](#0-2) .

`Clients::HttpClient#initialize` then uses `session.shop` as the literal request host: `@base_uri = "https://#{api_host || session.shop}"` [4](#0-3) . So whatever string is present in `dest_shop` becomes the exact host that the `client_id`/`client_secret` POST body is sent to.

Compare this to the two other credential-issuing entry points in the same module/area, which both call `Utils::ShopValidator.sanitize!(shop)` before building the session and host:
```ruby
validated_shop = Utils::ShopValidator.sanitize!(shop)
shop_session = ShopifyAPI::Auth::Session.new(shop: validated_shop)
``` [5](#0-4) [6](#0-5) 

`ShopValidator.sanitize!` is the gem's designated mechanism for ensuring a shop string maps to a trusted Shopify domain (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`) before it's allowed to become a request host [7](#0-6) . `exchange_token` is the one path in this family that skips this validation entirely, relying solely on JWT signature verification to imply the `dest` value is trustworthy — an implicit binding ("signed token ⇒ trusted host") that is never actually checked/enforced in code the way the other two methods do.

### Impact Explanation
If the identity binding between "verified session-token signature" and "trusted destination host" is not enforced by an explicit domain check (as it is in the parallel `migrate_to_expiring_token`/`client_credentials` methods), any code path that later relaxes or bypasses strict signature verification (e.g., an app using `old_api_secret_key` during rotation, a misconfiguration, or a future change to `JwtPayload`) would immediately leak the `client_id`/`client_secret` to an attacker-controlled host with no defense-in-depth check remaining. This matches the report's class of bug: a value trusted for one purpose (JWT signature validity) is used unchecked as the value governing a security-sensitive destination (the host receiving the `client_secret`), while sibling code paths in the same file demonstrate the correct pattern of validating the shop/host explicitly.

### Likelihood Explanation
Low-to-moderate: under the current, correct implementation of `JwtPayload#decode_token` (strict HS256 signature verification against `Context.api_secret_key`), an unprivileged attacker without the app's secret cannot forge a token with an arbitrary `dest`, so exploitation today requires either a secret-key compromise or a defect in JWT verification — both of which are outside strict "no special access" scope. The finding is best characterized as a missing defense-in-depth/consistency gap rather than a directly, unconditionally exploitable bug under the stated threat model.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token` and `ClientCredentials.client_credentials`) before constructing `shop_session`/making the HTTP request, so the host that receives `client_id`/`client_secret` is always confirmed to be a trusted Shopify domain independent of JWT verification correctness.

### Proof of Concept
Not independently reproducible as a standalone exploit within this gem alone under the stated constraints (it requires either a forged/weak-verified JWT or secret compromise, both out of scope for an "unprivileged internet user"). The concrete, reproducible evidence is the code-level inconsistency itself:
- `exchange_token` uses `dest_shop = jwt_payload.shop` unsanitized: [8](#0-7) 
- `migrate_to_expiring_token` and `client_credentials` both call `Utils::ShopValidator.sanitize!(shop)` first: [5](#0-4) [9](#0-8) 
- The unsanitized `shop` value directly becomes the literal request host including credentials: [4](#0-3)

        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
