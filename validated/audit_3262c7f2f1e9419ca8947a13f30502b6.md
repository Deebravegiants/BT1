## Finding: Permanently Stranded APT/FA Reserves After Bonding-Curve Graduation

### Title
10% of pool reserves become permanently unrecoverable after `graduate()` locks the liquidity pair - (File: `aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move`)

### Summary
When a bonding-curve liquidity pair reaches its APT threshold, `graduate()` deliberately migrates only 90% of the pair's APT and FA reserves to the external DEX and leaves the remaining 10% behind on the `LiquidityPair` object [1](#0-0) . Once graduation completes, `is_enabled` is permanently set to `false` [2](#0-1) , and there is no code path in the module that can ever move APT or FA out of the `LiquidityPair` object again — leaving the 10% remainder permanently stranded, mirroring the "leftover custody tokens with no sweep path" pattern from the original DAO/POL report.

### Finding Description
The `LiquidityPair` struct holds its FA balance in `fa_store` and its APT balance directly on the object's own account address (moved via `aptos_account::transfer`) [3](#0-2) . Both balances can only be moved by functions inside this module that first obtain the object's signer via `object::generate_signer_for_extending(&liquidity_pair.extend_ref)` — namely `swap_fa_to_apt`, `swap_apt_to_fa`, and `graduate` [4](#0-3) [5](#0-4) .

All three access paths are gated by `assert!(liquidity_pair.is_enabled, ELIQUIDITY_PAIR_DISABLED)` (swap functions) [6](#0-5) [7](#0-6) , or are `graduate` itself, which is only invoked once, from inside `swap_apt_to_fa`, when `is_enabled` is still `true` and the threshold is first crossed [8](#0-7) . Inside `graduate()`, `is_enabled` is flipped to `false` before the 10%-retention logic executes and there is no subsequent re-enable/withdraw function anywhere in the module [9](#0-8) .

As a direct consequence:
- The 10% of `apt_updated_reserves` retained in the object's own APT balance can never be withdrawn again — no function anywhere generates the object's extend-ref signer once `is_enabled == false`.
- The 10% of `fa_updated_reserves` retained inside `liquidity_pair.fa_store` is likewise permanently locked, since the only withdrawal paths from `fa_store` (`swap_fa_to_apt`/`swap_apt_to_fa`) are also gated by `is_enabled`.

This is precisely the custody invariant break described in the external report: "leftover token balances that the accounting model does not account for get permanently lost because no sweep/recovery path exists." Here it isn't the result of an atomic-arbitrage race — it's a deterministic, guaranteed 10% loss on every single successful graduation event, which is worse (100% likelihood vs. probabilistic in the original report).

### Impact Explanation
Every graduation permanently locks 10% of both the APT and the launched FA that were accumulated in the bonding-curve pool at graduation time (potentially tens of thousands of APT, since the threshold `APT_LIQUIDITY_THRESHOLD` is `600_000_000_000` octas = 6,000 APT, meaning roughly ≥600 APT plus a proportional amount of the FA token is orphaned on every graduation) [10](#0-9) . This is a permanent, non-recoverable loss of object-held value with no admin or recovery mechanism, satisfying the custody-grade "permanent lock of object-held value" impact class.

### Likelihood Explanation
This is not a race condition or edge case — it triggers deterministically on every graduation, which is the intended, expected lifecycle event of any successful bonding-curve FA launch. Any unprivileged swapper who pushes `apt_updated_reserves` past `APT_LIQUIDITY_THRESHOLD` via `swap_apt_to_fa` will trigger `graduate()` and cause the loss, with no privileged action required.

### Recommendation
Before or after calling `router::create_pool_coin`/`add_liquidity_coin_entry_transfer_ref` in `graduate()`, sweep the remaining `apt_reserves/10` and `fa_reserves/10` (i.e., whatever balance remains in the `LiquidityPair`'s own account and `fa_store`) to a specified recipient (e.g., protocol treasury or the FA creator) while `is_enabled` is still being flipped, using the same `liquidity_pair_signer` that is already available in scope at that point in `graduate()`. Alternatively, do not retain any residual amount at all — deposit 100% of `apt_updated_reserves`/`fa_updated_reserves` into the new DEX pool.

### Proof of Concept
Given the read-only nature of this analysis, a concrete Move test was not executed, but the flaw can be demonstrated conceptually by code tracing:
1. Repeated calls to `swap_apt_to_fa` accumulate `apt_reserves` until `apt_updated_reserves > APT_LIQUIDITY_THRESHOLD` [11](#0-10) .
2. `graduate()` computes `apt_updated_reserves - (apt_updated_reserves / 10)` and `fa_updated_reserves - (fa_updated_reserves / 10)` as the amounts sent to the new DEX pool, implicitly leaving 10% behind on the `LiquidityPair` object [12](#0-11) .
3. `is_enabled` is already `false` by this point [13](#0-12) , so no subsequent call to `swap_fa_to_apt`/`swap_apt_to_fa` (the only two functions capable of moving funds out of the pair) will succeed — confirmed by the `is_enabled` assertions at lines 223 and 281.
4. Querying `coin::balance<AptosCoin>(liquidity_pair_address)` and `fungible_asset::balance(fa_store)` after graduation will show non-zero, permanently frozen balances with no remaining function in the module capable of withdrawing them.

**Note on verification limits:** I was unable to fully trace whether `bonding_curve_launchpad.move` (the friend module holding the FA's `TransferRef`) exposes any privileged emergency-withdrawal entry point that could reach `fa_store` independently of `liquidity_pairs.move`; the index did not surface such a function. If one exists, it would only mitigate the FA-side loss, not the APT-side loss (which strictly depends on `liquidity_pair.extend_ref`, private to this module). A full Devin session with file-system access would be needed to confirm there is no such escape hatch elsewhere in the package.

```text
    fun graduate(
        liquidity_pair: &mut LiquidityPair,
        fa_object_metadata: Object<Metadata>,
        transfer_ref: &TransferRef,
        apt_updated_reserves: u128,
        fa_updated_reserves: u128
    ) {
        // Disable Bonding Curve Launchpad pair and remove global freeze on FA.
        liquidity_pair.is_enabled = false;
        liquidity_pair.is_frozen = false;
        // Offload onto third party, public DEX.
        router::create_pool_coin<AptosCoin>(fa_object_metadata, false);
        let liquidity_pair_signer = object::generate_signer_for_extending(&liquidity_pair.extend_ref);
        add_liquidity_coin_entry_transfer_ref<AptosCoin>(
            transfer_ref,
            &liquidity_pair_signer,
            liquidity_pair.fa_store,
            fa_object_metadata,
            false,
            ((apt_updated_reserves - (apt_updated_reserves / 10)) as u64),
            ((fa_updated_reserves - (fa_updated_reserves / 10)) as u64),
            0,
            0
        );
        // Send liquidity provider tokens to dead address.
        let apt_coin_wrapped = coin_wrapper::get_wrapper<AptosCoin>();
        let liquidity_obj = liquidity_pool::liquidity_pool(apt_coin_wrapped, fa_object_metadata, false);
        let liquidity_pair_address = signer::address_of(&liquidity_pair_signer);
        liquidity_pool::transfer(
            &liquidity_pair_signer,
            liquidity_obj,
            @0xdead,
            primary_fungible_store::balance(liquidity_pair_address, liquidity_obj)
        );
        // Emit event informing all that the liquidity pair has graduated and which DEX it graduated to.
        event::emit(
            LiquidityPairGraduated {
                fa_object_metadata,
                dex_address: @swap
            }
        );
    }
```
