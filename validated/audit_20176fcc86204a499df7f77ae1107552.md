### Title
Webhook `shop` header is not covered by HMAC, letting an attacker relabel a legitimately-signed webhook as belonging to a different tenant - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the webhook HMAC over the raw body only, but exposes `shop` (the `shopify-shop-domain` / `x-shopify-shop-domain` header) as trusted tenant-identifying data that is handed unmodified to the app's `WebhookHandler`. Because the HMAC signature never covers the header, the binding "shop that receives/authenticates this webhook" == "shop the HMAC was actually computed for" does not hold. An attacker who controls any shop with the same app installed (or otherwise obtains one validly-signed webhook body) can resend it to the app's webhook endpoint with an arbitrary `shop-domain` header, and the gem will report it as a valid webhook for that other shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC purely over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body — no headers are part of the signed input: [2](#0-1) 

Yet `shop` is derived straight from an attacker-controllable HTTP header and is never itself authenticated: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC (over the body) and then immediately trusts `request.shop` as the tenant identity, forwarding it into `WebhookMetadata` that is passed to the app's handler: [5](#0-4) [6](#0-5) 

The equality that should hold is:
`shop that the HMAC-verified payload was actually generated for == shop value the gem/handler trusts as the event's tenant`

Because the header is outside the signed bytes, this equality can be broken: the HMAC only proves "Shopify (using this app's `client_secret`) signed this exact body," it says nothing about which shop the header claims it came from. Since `api_secret_key`/`client_secret` is shared by the app across *all* shops that install it (not shop-specific), any tenant that has installed the app can generate a validly-signed body (by triggering a real webhook event on their own store) and then replay that signed body to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop's domain. `HmacValidator.validate` will still return `true` because it only checks the body, and the handler will process the event believing it originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary that host applications rely on `WebhookMetadata#shop` to enforce — the value is architecturally treated as authenticated because it passed HMAC validation, but it is not actually bound to the signature. Applications typically use `data.shop` to look up the corresponding merchant session/access token and perform per-tenant actions (e.g. loading the victim's stored session, writing to the victim's record, triggering data-request/redact flows, updating cached shop state) using attacker-supplied body content. This is a cross-tenant confusion vulnerability: an attacker who controls one tenant of a multi-tenant app can make the app believe attacker-chosen webhook data (topic/body they can influence via their own store's events) belongs to a different, victim tenant, directly matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Exploitation requires only that the attacker installs the target app on a shop they control (or is otherwise a normal merchant of a multi-tenant app) — no access to `api_secret_key`, access tokens, or the app's `client_secret` is needed, since the attacker can obtain validly-signed webhook bodies simply by using their own store normally and capturing the request Shopify sends. They then replay the captured raw body to the webhook endpoint while altering only the `shopify-shop-domain` header, which is not covered by the signature. This is a low-effort, credential-free attack path fully reachable through this gem's own webhook-verification code (`HmacValidator` + `Webhooks::Registry.process`), not a host-app misuse.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise authenticate `shop-domain` before trusting it:
- Reject/flag webhooks where the header-derived shop does not match an independently known, already-authenticated shop for the delivery endpoint (e.g., per-shop endpoint or session lookup keyed by an already-verified identifier), or
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) in the string that is hashed/compared, so `to_signable_string` incorporates the full set of security-relevant fields, not just the body, or
- Explicitly document/enforce that consumers must independently verify `WebhookMetadata#shop` against a shop-specific secret/session before trusting it for tenant-scoped actions, and add a check in `Webhooks::Registry.process` to reject when body-derived shop identifiers (if any exist in payload, e.g. `myshopify_domain` fields in some payloads) disagree with the header value.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com` (same app, same `client_secret` used for all installs).
2. Trigger a webhook event on the attacker's store (e.g. update a product) and capture the raw POST body plus the legitimate `shopify-hmac-sha256` header Shopify computed for that body.
3. Resend that exact raw body and HMAC header to the app's webhook endpoint, but replace `shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged shop header; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the (still-valid) HMAC.
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own store's event body>, ...)`, and the app processes attacker-influenced data as if it were an authenticated event from the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
