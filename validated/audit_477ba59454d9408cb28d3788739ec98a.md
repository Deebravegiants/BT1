### Title
Stray/stranded balance in `EmporiumUpgradeable` can be diverted to an attacker's own address via an unauthenticated op + a persistently-approved router - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` only checks the *delta* of the action's own token balance across a single call, not its absolute balance, and allows fully unauthenticated (`stack.signerAddress == address(0)`) arbitrary `endpoint.call(callData)` ops with no signature check. This lets an attacker plant a persistent ERC20 `approve()` to a self-controlled router in one op, then in the same or a later call use that allowance to route pre-existing/stray token balance in `EmporiumUpgradeable` straight to their own EOA, while the on-chain equality checks still balance out because the diverted amount is silently absorbed into a smaller legitimate shielded output.

### Finding Description
The claimed invariant is: *tokens leaving the action in a tx == `-deltaAmountChanges` Hinkal sent it that tx*. In `runAction`: [1](#0-0) 

`balancesBefore`/`balancesAfter` are taken around the ops loop, and `balanceChange` is adjusted by `-deltaAmountChanges[i]` only when negative, then any positive `balanceChange` is swept out via `handleOut` to `msg.sender` (the Hinkal contract, which mints a new shielded UTXO for the caller): [2](#0-1) 

Critically, `balancesBefore` is captured **after** Hinkal already transferred `-deltaAmountChanges[i]` tokens into the action (see `Hinkal._externalTransact`): [3](#0-2) 

so `balancesBefore` silently absorbs any pre-existing/stray token balance `R` already sitting in `EmporiumUpgradeable` (e.g., dust left over, or tokens stranded by an incompletely-consumed prior action). The equation only enforces the *delta caused by ops in this call* plus the declared deposit, never the action's absolute closing balance.

The ops themselves are attacker-controlled and, when `stack.signerAddress == address(0)`, require **no signature at all** — `verifyWallet` just marks the message used and returns: [4](#0-3) 

and the stateless branch executes `op.endpoint.call{value: op.value}(op.callData)` verbatim: [5](#0-4) 

Exploit flow:
1. In one Emporium transaction, an unprivileged attacker (using `signerAddress = address(0)`, no signature needed) includes an op that calls `token.approve(attackerRouter, type(uint256).max)` from `EmporiumUpgradeable`. This approval is never revoked afterward.
2. In a later Emporium transaction, the attacker supplies real `amountChanges`/`deltaAmountChanges[i] = -X` for token `T`, backed by their own real UTXOs (so `X` tokens are legitimately sent to `EmporiumUpgradeable` before `runAction` runs). At this point `balancesBefore[T] = R + X` (`R` being the stray/stranded balance from step 1's era).
3. An op calls the attacker's router, which uses the persistent allowance to `transferFrom(EmporiumUpgradeable, attackerEOA, R)`, sending `R` directly to the attacker's own wallet, bypassing `EmporiumUpgradeable`/Hinkal balance tracking entirely.
4. `balancesAfter[T] = X` (R having left), so `balanceChange = X - (R+X) = -R`; after the `-deltaAmountChanges` adjustment, `balanceChange = X - R`. As long as `X >= R` this stays non-negative, so `BalanceChangeShouldBePositive` never reverts, and `handleOut` mints the attacker a legitimate new shielded UTXO worth `X - R`.
5. In `Hinkal.transact`'s closing invariant, `balanceDif` on Hinkal's own balance nets to `-R` and `amountChanges[T] + utxoAmount = -X + (X-R) = -R` — the equality holds exactly, hiding the diversion.

Net result: the attacker walks away with `R` (stolen, sent directly to their EOA) plus a legitimate shielded UTXO of `X - R` backed by their own real spend of `X` — i.e., they extracted the stray/stranded balance `R` for free, while every on-chain check passes.

### Impact Explanation
Real ERC20/ETH value sitting in `EmporiumUpgradeable` (stray dust, or tokens stranded from an incompletely-consumed prior Emporium interaction that were destined to become a user's shielded UTXO) can be redirected to an unrelated attacker's EOA, bypassing the pool's shielded-balance ledger entirely. If the stranded balance corresponds to another user's in-flight funds, this is direct theft of user funds (Critical); at minimum it is theft of protocol-held funds via unauthorized/unaccounted asset movement (High). The attack is repeatable any time residual/stray balance exists and the attacker has enough of their own legitimate withdrawal `X` to mask the diversion without tripping the non-negative check.

### Likelihood Explanation
Preconditions: (1) some prior op left a persistent ERC20 approval from `EmporiumUpgradeable` to an attacker-influenceable/attacker-deployed contract — trivially achievable by the attacker themselves since `stack.signerAddress = address(0)` requires no authorization and ops accept arbitrary `endpoint`/`callData`; (2) any nonzero residual balance in the action contract. Both preconditions are fully within an unprivileged attacker's control (they can create the approval and the residual conditions themselves, e.g. via a deliberately partial/no-op interaction in a first transaction), and the follow-up extraction only needs the attacker's own legitimate deposit sized `>= R`, which they can size arbitrarily (even self-deposit-then-withdraw). This is realistically executable with no reliance on privileged roles.

### Recommendation
Do not derive the action's "amount to sweep out" from a before/after delta that already includes pre-existing balance. Instead, require the action's balance to return to zero (or to a value explicitly tracked in persistent storage) for each token at the end of `runAction`, and/or revoke every `approve()` set during ops before the call returns. Additionally, require `stack.signerAddress` to be validated (or forbid the fully-unauthenticated `address(0)` path from calling into arbitrary attacker-supplied `endpoint`/`callData` that can perform ERC20 `approve`), and consider tracking/accounting the action's balance per-token in storage rather than trusting a single `getBalancesForArray` snapshot that can silently include stranded value.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, an ERC20 test token, and a malicious "router" contract with a function `drain(address token, address to, uint256 amount)` that calls `IERC20(token).transferFrom(EmporiumUpgradeable, to, amount)`.
2. Tx1 (attacker, `signerAddress = address(0)`, no signature): craft `circomData` with one op `token.approve(router, type(uint256).max)` executed via `EmporiumUpgradeable`; also seed a residual `R` of `token` directly into `EmporiumUpgradeable` (simulating a stranded prior balance) by transferring `R` tokens to it out-of-band.
3. Tx2 (attacker, using their own real UTXO of value `X >= R`): craft `deltaAmountChanges[T] = -X` and one op calling `router.drain(token, attackerEOA, R)`.
4. Assert: `token.balanceOf(attackerEOA)` increased by exactly `R` directly (outside of any minted UTXO), and the newly minted shielded UTXO for the attacker has `amount == X - R` (not `X`), while `Hinkal.transact`'s invariant checks (`balanceDif == amountChanges[i] + utxoAmount`, `BalanceChangeShouldBePositive`) do not revert — demonstrating `R` left the protocol uncounted against `-deltaAmountChanges`.
