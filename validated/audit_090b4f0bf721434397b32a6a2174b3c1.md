This confirms the finding. The docs at `docs/usage/webhooks.md:125` explicitly promise that `Registry.process` "will verify the request did indeed come from Shopify" — but the verification only covers the raw body, not the `shop` field that the handler relies on for tenant identification.

### Title
Webhook `shop` field is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to identify which tenant the event belongs to when invoking the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only `@raw_body` [1](#0-0) . The `shop` accessor is read directly from the `shop-domain`/`x-shopify-shop-domain` header without being part of the signed data [2](#0-1) .

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body only) and compares it with `OpenSSL.secure_compare` [3](#0-2) . Once this passes, `Registry.process` immediately forwards `request.shop` — the unauthenticated header value — into `WebhookMetadata` and calls the app's handler with it [4](#0-3) .

The broken identity binding is: `hmac_valid(raw_body) == true` is treated as equivalent to `shop_header == shop_that_actually_generated(raw_body)`, but the gem never enforces that equality — the `shop` header can be swapped for any value while the same `(raw_body, hmac)` pair remains valid, since the signature never covers `shop`.

Because any unprivileged internet user can install the app on their own store (a normal, unprivileged action) and thus receive genuine, correctly-HMAC-signed webhook deliveries for their own shop, they can capture one such `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to any victim shop domain. `HmacValidator.validate` still succeeds (the body and secret are unchanged), and `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` even though the payload never originated from that shop [4](#0-3) . Docs explicitly claim this flow "will verify the request did indeed come from Shopify," reinforcing that host apps rely on this guarantee for tenant attribution [5](#0-4) .

### Impact Explanation
This is a cross-tenant identity confusion: an attacker with only their own (free/legitimate) shop install can inject webhook events that the host application's handler will process as if attributed to an arbitrary victim shop, since `data.shop` is the only tenant-identifying field the gem exposes to handlers and it is unauthenticated. Any host app that uses `data.shop` to key data storage, trigger per-shop side effects, or make authorization decisions (a usage pattern the gem's own documentation recommends) can be tricked into performing tenant-scoped actions for the wrong shop, or storing attacker-supplied data under a victim's tenant record.

### Likelihood Explanation
Likelihood is high: no secret, token, or privileged access is required beyond installing the app on one's own store (available to any unprivileged internet user) and being able to POST arbitrary headers to the app's public webhook endpoint — a capability inherent to any HTTP client.

### Recommendation
Bind the `shop-domain` header into the signed material, e.g., include it (and other Shopify-controlled headers/metadata relevant to routing) in `to_signable_string`, or independently verify the `shop` value against a record the app already trusts (e.g., cross-check against the shop associated with the specific webhook registration/session) before dispatching to the handler.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) so Shopify delivers a real webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` header computed over the raw body using the app's `client_secret`.
2. Capture `(raw_body, hmac_header)` from that legitimate delivery.
3. Replay the exact same `raw_body` and `hmac_header` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks `raw_body` [1](#0-0) ; `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` [4](#0-3) , causing the host app to process attacker-supplied data as belonging to the victim tenant.
