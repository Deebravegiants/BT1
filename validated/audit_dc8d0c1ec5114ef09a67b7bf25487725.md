Confirmed: the gem's documented API (`docs/usage/webhooks.md`, `BREAKING_CHANGES_FOR_V15.md`) tells app developers that `data.shop` on `WebhookMetadata` is "The shop domain of the webhook" and shows it being used directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) with no mention that `shop` is unauthenticated. This confirms the binding break is in the gem's own contract, not a misuse of a documented caveat.

### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken straight from HTTP headers — none of which are part of the signed data — when building the `WebhookMetadata` passed to the app's handler.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` value [1](#0-0) . For webhooks, `Webhooks::Request#to_signable_string` returns only the raw request body — `@raw_body` — completely excluding the `shop`, `topic`, `webhook_id`, and `api_version` values [2](#0-1) . Those four values are instead read directly, and unauthenticated, from HTTP headers such as `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` [3](#0-2) .

`Registry.process` then validates only the HMAC of the body, and immediately uses the unauthenticated header values to look up the handler by topic and to construct `WebhookMetadata`, which is handed to the app's handler as trusted data:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The identity-binding invariant that the library implicitly promises — and that its own documentation encodes — is `shop_signed == shop_delivered_to_handler`. In reality the check performed is only `body_signed == body_delivered_to_handler`; `shop` (and `topic`/`webhook_id`/`api_version`) are never bound to the signature at all. This is the same class of bug as the reported `Strategy::checkPoolActivity()` flaw: a value that gates trust (a valid-looking timestamp / a "valid HMAC") is treated as proof of an unrelated property (freshness / correct-shop-attribution) that it does not actually establish.

Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app, any body that Shopify has ever HMAC-signed for one shop remains validly signed under that same secret. An attacker who controls or has installed the app on shop A can capture a genuine webhook delivery for shop A (valid body + valid HMAC), then replay that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to name victim shop B. `Utils::HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` accepts the request and calls the app's handler with `data.shop == "shop-b.myshopify.com"`.

The gem's own documentation instructs developers to treat `data.shop` as an authenticated shop identifier and to key their per-tenant work off of it directly, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [5](#0-4) , and the migration guide likewise documents `shop` as "The shop domain of the webhook" with no caveat that it is unauthenticated [6](#0-5) . There is no code anywhere in `lib/shopify_api/webhooks/**` that cross-checks `request.shop` against the shop that a stored session/webhook subscription actually belongs to.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: cross-tenant access. An app relying on `WebhookMetadata#shop` as an authenticated tenant identifier (exactly as the gem's own docs instruct) can be made to process attacker-replayed webhook data under an arbitrary victim shop's identity — e.g. triggering `app/uninstalled` cleanup, GDPR data-request, or other topic handlers for shop B using only a body the attacker captured from shop A, with a signature that still validates. Depending on the handler's logic (e.g. deleting/deactivating data keyed by `data.shop`, or firing shop-scoped side effects), this can cause state corruption or denial of a victim tenant's app functionality attributable to a different, attacker-controlled shop.

### Likelihood Explanation
Any entity that can install the app on one shop (including a free/trial shop the attacker controls, or a legitimate merchant who is themselves the "unprivileged internet user" relative to other tenants) automatically receives genuinely-signed webhook deliveries and can immediately replay their bodies against the same app's public webhook endpoint with forged identity headers. No access token, `client_secret`, or privileged account is required beyond ordinary use of the app.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the data that is authenticated before trusting them, or, at minimum, have `Registry.process` independently verify `request.shop` against a known/registered shop (e.g. an existing session or subscription record) before invoking the handler, rather than passing header-derived `shop` straight into `WebhookMetadata`. At the very least, the gem's HMAC validator should not be presented as validating the whole webhook `Request` object (`VerifiableQuery`) when in fact it only covers the body.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and receives a genuine webhook, e.g. for topic "customers/data_request":
raw_body = '{"customer": {...}}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), Context.api_secret_key, raw_body)
# Shopify sends this with headers naming attacker.myshopify.com; HMAC validates.

# 2. Attacker replays the SAME raw_body/hmac, only changing the shop header,
#    to the app's public webhook endpoint:
headers = {
  "x-shopify-topic" => "customers/data_request",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),   # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",   # forged
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (only body+secret checked),
#    handler.handle is invoked with data.shop == "victim-shop.myshopify.com"
