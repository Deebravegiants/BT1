### Title
Order escrow amount can be truncated to zero by the protocol fee without any post-fee minimum check - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder()` validates that a user's raw input amount is non-zero before deducting the protocol fee, but never validates the amount that actually gets escrowed and committed to *after* the fee is subtracted. This mirrors the SecondSwap `spotPurchase()` bug: a "too small" check is applied to the pre-discount/pre-fee value while the value that is actually used downstream is the post-fee value, which can be smaller — including zero.

### Finding Description
In `placeOrder`, Phase 1 rejects a zero raw input amount: [1](#0-0) 

Phase 2 then computes the protocol-fee-reduced amount that is actually escrowed and hashed into the order commitment: [2](#0-1) 

The only zero-check here (`if (originalAmount == 0) revert InvalidInput();`) is on `originalAmount`, i.e., the amount *before* the fee is applied. There is no check that `reducedAmount = originalAmount - protocolFee` (the value that is actually stored as escrow via `_orders[commitment][token] = reducedInputs[i].amount` and included in the EIP-712-style commitment hash) is non-zero: [3](#0-2) 

This is structurally identical to the SecondSwap bug: `_getDiscountedPrice()`/the fee-adjusted amount is computed and used for the real economic effect, but the "amount too small" guard is checked against the un-adjusted (pre-discount / pre-fee) figure. In `SecondSwap_Marketplace`, the effect was that `baseAmount` could round to zero and the transaction would always revert, permanently blocking legitimate purchases. In `IntentGatewayV2`, the analogous effect is that a leg of a multi-input order can be silently escrowed with `amount == 0` while still being included in the order's commitment and being emitted in `OrderPlaced`, i.e., the order is accepted with a "phantom" input leg the user paid nothing for (once truncated) yet the order structure and any downstream accounting (dust events, escrow bookkeeping, and by extension a solver's expectations built from the `OrderPlaced` event) treat it as a valid, distinct token leg.

### Impact Explanation
Whether `protocolFeeBps` can realistically reach values large enough to zero out `reducedAmount` for realistic amounts depends on the bound enforced by `_validateParams` in `IntentsBase.sol`, which I was not able to fully confirm within the available tool budget (the search located references to `protocolFeeBps` validation in `IntentsBase.sol` but I did not retrieve the exact numeric cap before running out of iterations). If governance/admin-configured `protocolFeeBps` (global or the per-destination override in `_destinationProtocolFees`) is not tightly bounded well below 10 000 bps, or if a user places an order with a very small raw amount (e.g., 1 wei of a token) against a non-trivial fee, `reducedAmount` truncates to 0 for that leg while `placeOrder` still succeeds, emits `OrderPlaced`, and records a duplicate-token check based on a zero-valued escrow entry. This can corrupt the invariant that every input token entry in a placed order corresponds to non-zero escrowed value, potentially affecting solver fill logic, dust/duplicate-token bookkeeping (`if (_orders[commitment][token] != 0) revert InvalidInput();`), and order cancellation refund logic that iterates over `order.inputs`. Given the uncertainty about the exact fee cap, I classify this conservatively as Medium — a rounding/validation-order defect reachable directly by any unprivileged `placeOrder` caller, in the same bug class as the referenced report, but whose maximum severity depends on a bound I could not fully verify.

### Likelihood Explanation
`placeOrder` is a fully permissionless, single-transaction entry point reachable by any caller submitting an order with a small `TokenInfo.amount` for one of its inputs. No privileged role is required. The only precondition is that `protocolFeeBps` (or a per-destination override) combined with a sufficiently small `order.inputs[i].amount` produces `protocolFee == originalAmount` under floor division. This is easy to trigger deliberately (attacker picks the smallest amount for a given fee) and is analogous to the reproduced PoC in the original report.

### Recommendation
Move the "amount too small" validation to operate on the post-fee (`reducedAmount`) value rather than (or in addition to) the raw `originalAmount`, mirroring the fix recommended for `SecondSwap_Marketplace`: after computing `reducedAmount = originalAmount - protocolFee`, add `if (reducedAmount == 0) revert InvalidInput();` before it is written into `reducedInputs[i]` and used for the commitment/escrow. This guarantees every input leg that survives `placeOrder` represents genuine, non-zero escrowed value regardless of the configured protocol fee.

### Proof of Concept
Conceptual PoC (mirrors the cited report's structure), pending confirmation of the exact `protocolFeeBps` upper bound in `IntentsBase._validateParams`:
1. Governance/admin sets (or a destination override sets) `protocolFeeBps` close to `10_000` (or the maximum allowed by `_validateParams`, whatever that turns out to be).
2. A user calls `placeOrder` with one `order.inputs[i].amount` set to a very small value (e.g., `1`), passing the `originalAmount == 0` check.
3. In Phase 2, `protocolFee = (1 * protocolFeeBps) / 10_000` floors to `1` (or to `originalAmount`) for a sufficiently large `protocolFeeBps`, making `reducedAmount = 0`.
4. `placeOrder` proceeds, `_orders[commitment][token] = 0` is stored, `OrderPlaced` is emitted with a zero-amount input leg, and no revert occurs — unlike the intended "reject dust orders" behavior.

Because I could not verify the concrete `protocolFeeBps` ceiling enforced elsewhere in the contract within the remaining tool budget, the numeric feasibility of reaching `reducedAmount == 0` for practical fee configurations is unconfirmed and should be validated directly against `IntentsBase._validateParams` before treating this as exploitable at current default fee levels (test fixtures in the repo use fees like 100/200/500/1000 bps, which for realistic multi-decimal token amounts would not zero out `reducedAmount`; the risk is concentrated in edge cases of extremely small `amount` values or unusually high configured fees).
