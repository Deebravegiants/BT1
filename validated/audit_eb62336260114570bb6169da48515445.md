### Title
Webhook `shop-domain` and `topic` headers are trusted as authenticated tenant identity even though the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then forwards the unauthenticated `shop-domain`, `topic`, `webhook-id`, and `api-version` headers straight into `WebhookMetadata` and on to the app's handler. Because the HMAC signable string is only the raw body, none of these header-derived fields are cryptographically bound to that body, so a value acted upon by app logic (`data.shop`) is not covered by the signature that is supposed to authenticate the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no relation to the signed content: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate`, which only recomputes the HMAC over `to_signable_string` (i.e., the raw body) with `Context.api_secret_key`: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `request.topic` (unauthenticated) is used to look up the handler, and `request.shop` (unauthenticated) is passed straight into `WebhookMetadata`, which the app's `WebhookHandler#handle` receives as the trusted tenant identifier: [5](#0-4) [6](#0-5) 

**Binding that is broken:** the identity used for authorization decisions, `data.shop` (asserted `shop-domain` header), is expected to equal the shop that Shopify's signature actually attests to, but the signature (`Utils::HmacValidator.validate`) only attests to `raw_body`. Formally: `authenticated(body) == true` is treated as `authenticated(shop_header) == true`, which does not hold because `shop_header ∉ signed_bytes`.

Because a single app-level `client_secret` is shared across every shop that has installed the app, any unprivileged user who can install the app on their own shop can capture a batch of legitimately-signed `(raw_body, hmac)` pairs from webhooks delivered to their own store. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) headers to claim the payload belongs to a different, victim shop. `HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will hand the forged `shop`/`topic` straight to the handler as if Shopify itself vouched for that tenant/topic pairing.

### Impact Explanation
This breaks the tenant isolation the HMAC check is meant to provide: an attacker-controlled webhook body can be attributed to any other shop that uses the same app, letting the attacker drive business logic keyed on `WebhookMetadata#shop` (installation state changes, GDPR data-request/redact handling, subscription/billing updates, order or customer processing, etc.) for a merchant they do not control. This is a cross-tenant identity confusion issue reachable by any user who can install the app, with no access token, api_secret_key knowledge, or privileged account required — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app that (a) installs on multiple shops (the normal SaaS multi-tenant model for a Shopify app) and (b) uses `data.shop`/`data.topic` from `WebhookMetadata` as an authoritative tenant/topic identifier in its `WebhookHandler#handle` implementation — which is exactly the pattern the gem's own `WebhookMetadata` struct and documented API encourage, since `HmacValidator.validate` is presented as the complete authenticity check for a webhook `Request`. An attacker only needs to install the target app once (a normal, unprivileged action) to harvest valid `(body, hmac)` pairs and can then freely forge the shop/topic headers server-side.

### Recommendation
- Extend the webhook signable string (or add a secondary check) so that `shop-domain`, `topic`, and `webhook-id` are cryptographically bound to the signature, not just the body — or, at minimum, document and enforce that `Registry.process` (or the calling app) must cross-check the asserted `shop-domain` against a shop that is known to have actually installed the app (e.g., verified via a stored offline session) before trusting `WebhookMetadata#shop`/`#topic` for any authorization decision.
- Alternatively, have `HmacValidator`/`Request` incorporate the relevant Shopify-supplied headers into the value that is verified, so header tampering invalidates the signature.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, receiving legitimately signed webhooks, e.g. for `customers/data_request`:
   ```
   POST /webhooks
   x-shopify-topic: customers/data_request
   x-shopify-hmac-sha256: <valid HMAC of body B>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: wh_123
   Body: B
   ```
2. Attacker captures `(B, valid_hmac)` from their own delivered webhook — `HmacValidator.validate` only ever checks `HMAC(secret, B)`; see: [7](#0-6) 
3. Attacker replays the exact same body/HMAC to the app's webhook endpoint, changing only the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac`/`to_signable_string` are unaffected by the header change: [8](#0-7) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes (same body, same HMAC), then dispatches `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` to the app's handler: [5](#0-4) 
6. Any handler logic keyed on `data.shop` now believes this attacker-controlled webhook body originated from `victim-shop.myshopify.com`, achieving cross-tenant impersonation without ever needing the app's `client_secret`, `api_secret_key`, or any credential belonging to the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
