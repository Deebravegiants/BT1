### Title
Pool `repay`/`recapitalize` computes the excess refund from the declared amount, not from a measured receipt, paying unbacked refunds out of pool custody - (File: contracts/pool/src/ops/repay.rs)

### Summary
The Linux qla2xxx bug is an incorrect dereference: the code reads a control block through the wrong pointer, so the bytes it consumes do not correspond to the object it meant to operate on. The analog in XOXNO Lending is a refund computed through the wrong source of truth. In `ops::repay::apply` (and identically `ops::recapitalize::apply`), the "excess repayment" is derived from the *declared* `amount` argument and the *accounting book* (`resolve_repay` against `borrow_index`), then paid out of real token custody, without measuring that the declared amount actually arrived. When the market carries no debt, `current_debt_ceil` is zero, `resolve_repay` takes the full-close branch, `net_repay` is zero, and the entire declared amount becomes a refundable "excess" that is transferred out of custody while the `cash` book is left untouched. The codebase's own test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` in `contracts/pool/tests/flows.rs:3578-3611` documents the custody drain.

### Finding Description
`resolve_repay` (`common/src/rates/scaling.rs:171-192`) returns `(pos_scaled, amount - current_debt_ceil)` whenever `amount >= current_debt_ceil`. With `pos_scaled == 0`, `unscale_borrow_ceil` yields 0, so the excess equals the full `amount`. The repay op then routes that excess back to the payer as a token transfer funded by the pool's custody, while — per the test's own comment at `contracts/pool/tests/flows.rs:3578-3588` — "Neither refund debits `cash` or passes `require_reserves`", and the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct. So a call that moves zero shares and retires zero debt still emits a payout sized purely by a caller-supplied integer. The same shape exists in `ops::recapitalize::apply`, where the excess over the computed shortfall is refunded the same way. This is the dereference bug: the settlement value is dereferenced from the declared parameter instead of from the measured balance delta of the inbound transfer, exactly like reading the ICB through the wrong pointer.

### Impact Explanation
If the pool `repay` entrypoint does not itself pull the declared tokens (measured-receipt settlement lives in the controller, which pre-transfers before calling the pool), then any path where the declared amount exceeds what actually arrived converts bookkeeping into real payouts: custody decreases, `cash` does not, and the backing invariant `floor(supply_value) - (cash + ceil(debt_value))` silently breaks. Suppliers' claims are then under-collateralized by the drained amount — protocol insolvency / theft of user funds. I could not confirm within the available index whether `repay` enforces a controller-only caller check; if it does, the residual exposure is any controller path that declares a repayment amount larger than the balance delta it actually delivered, plus direct token donations or rounding gaps between the controller's transfer and the pool's expectation.

### Likelihood Explanation
Reachability hinges on the auth boundary between controller and pool. The listed in-scope entrypoints include `repay` and `recapitalize`; if either is invocable with only the payer's `require_auth` (the harness test calls `client().repay(&payer, ...)` directly, which under `mock_all_auths` does not prove or disprove a controller guard), exploitation is a single call against any debt-free or under-declared market. If the pool is controller-gated, the same wrong-dereference shape still applies wherever the controller declares amounts it has not measured, e.g. repayment legs refunded under `SeizeMode`/excess-payment handling — though the controller paths observed (`calculate_repayment_amounts`, `process_excess_payment`) do measure and cap inputs correctly.

### Recommendation
Settle refunds against measured receipts, not declared amounts: snapshot the pool's token balance before the leg, compute `received = balance_after - balance_before`, and cap the refund at `min(declared_excess, received_surplus)`. Alternatively, have the pool perform the inbound `transfer` itself so the declared amount and the custody movement are the same value. Apply the same fix to the `recapitalize` excess path. Add an invariant check that no op leaves `cash` unchanged while token custody decreases.

### Proof of Concept
From `contracts/pool/tests/flows.rs:3590-3611` (already in the repo):

```rust
let payer = Address::generate(&t.env);
// market has zero debt; nothing is transferred in
let credited = t.client()
    .repay(&payer, &t.ract(0, custody_before))   // declare amount = full custody
    .get_unchecked(0)
    .actual_amount;
assert_eq!(credited, 0);                        // no debt retired, no shares burned
assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
// => payer received `custody_before` tokens; book `cash` unchanged
```

If `repay` is gated to the controller, the equivalent trigger is any controller flow that declares a repayment without a preceding measured transfer for the full declared amount.

Note: the reachability step (whether pool `repay`/`recapitalize` require controller auth) could not be fully verified from the indexed sources; the accounting-side root cause — refund derived from a declared amount rather than a measured delta, refunding out of custody while leaving `cash` untouched — is confirmed by `common/src/rates/scaling.rs:171-192` and the in-repo characterization test.
