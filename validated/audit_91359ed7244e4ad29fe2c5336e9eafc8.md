### Title
Webhook `shop` (tenant) identifier is trusted from an unauthenticated header while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process` verify the *body* of an incoming webhook against an HMAC, but the `shop` value delivered to the app's handler is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is **not** part of the signed material. This breaks the intended binding `authenticated_payload == (shop, body)`; in reality it only enforces `authenticated_payload == body`, letting any caller pair a validly-signed body with an arbitrary `shop` value.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from a header, independent of that signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC only over `to_signable_string` (the raw body) and compares it with the `hmac` header: [3](#0-2) 

`Registry.process` validates that HMAC and then immediately hands the handler `request.shop`, unverified, as the tenant identity for the webhook: [4](#0-3) 

The `api_secret_key` used to compute the webhook HMAC is the *app-wide* secret (identical for every shop that installs the app), not a per-shop secret. Consequently, a body+HMAC pair that is valid for shop A's data is also a valid HMAC for the exact same bytes regardless of which `shop-domain` header accompanies it — the signature says nothing about which shop the payload belongs to. An attacker who controls one tenant (installs the app on their own store, or otherwise obtains one legitimately-signed webhook body/HMAC pair) can resend that identical body to the app's public webhook endpoint with the `shopify-shop-domain` header changed to a victim shop. `HmacValidator.validate` will still return `true` (it never looked at the shop header), and `Registry.process` will pass the victim's shop name to the handler as if Shopify itself attested to that shop, i.e. it violates the equality `attacker-controlled header shop == HMAC-verified sender shop`.

This is exactly the "field acted on but not covered by the HMAC" identity-binding failure: the webhook endpoint is a public, unauthenticated internet-facing endpoint by design (Shopify calls it without any other credential besides the HMAC), so this gem is the only line of defense verifying request authenticity, and it fails to bind the tenant identifier to the signature.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (as documented and as exercised in the gem's own tests, e.g. `assert_equal(@shop, data.shop)`) to select which merchant's data/session to act on will process/attribute a forged shop-tagged event. Because webhook handlers routinely write/update per-shop state (inventory, orders, customer data, uninstall/GDPR handling, etc.) keyed by this `shop` value, this enables cross-tenant data corruption or disclosure — an attacker acting as one authenticated tenant can inject events attributed to another tenant. This matches the "Critical - cross-tenant access" impact category, since the boundary crossed is the tenant/shop boundary enforced (nominally) by this gem's webhook verification.

### Likelihood Explanation
Likelihood is moderate-to-high for any attacker who can install the app on a shop they control (a very low bar — free/dev stores are trivially available) and observe at least one real webhook delivery from Shopify to obtain a validly-signed `(body, hmac)` pair signed with the shared `api_secret_key`. No access to the app's `client_secret`/access tokens or another merchant's credentials is required — only network access to the app's public webhook endpoint and a header change.

### Recommendation
Bind the tenant identity into the signed material, or otherwise independently authenticate the shop domain claimed in the webhook request:
- Include the `shop-domain` (and ideally `webhook-id`/`topic`) in the string that is HMAC-verified, e.g. extend `Request#to_signable_string` to incorporate the shop header alongside the raw body, and update `HmacValidator`/`Registry.process` accordingly, OR
- Cross-check `request.shop` against the shop stored for the session/installation associated with the delivered `webhook_id`/topic before invoking the handler, rejecting mismatches.
- Document in `docs/usage/webhooks.md` that the `shop` field is currently unauthenticated so integrators are warned if they rely on it for tenant isolation.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# receives one legitimate webhook delivery from Shopify:
body    = '{"id": 12345, "note": "hello"}'
hmac    = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(hmac),
  "x-shopify-shop-domain"  => "attacker.myshopify.com", # will be swapped below
}

# Attacker now replays the SAME body+hmac to the app's public webhook
# endpoint, but swaps the shop-domain header to the victim shop:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

ShopifyAPI::Webhooks::Registry.process(forged_request)
# => HmacValidator.validate(forged_request) returns true, because it only
#    checks OpenSSL.secure_compare(computed_signature, hmac) against `body`,
#    never inspecting `shop-domain`.
# => the registered handler receives WebhookMetadata with
#    shop: "victim-shop.myshopify.com" even though Shopify never sent this
#    payload for that shop.
```
