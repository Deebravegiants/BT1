## Title
Webhook `shop` identity is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC of the raw request **body**, then unconditionally trusts the `shop` value taken from an HTTP header that is never part of the signed material. Because a single `api_secret_key` is shared across every shop that has installed the app, any merchant who receives a genuine webhook for their own store can replay that exact (body, HMAC) pair to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header, and the request will still pass validation as if it belonged to the victim shop.

### Finding Description
`Registry.process` performs exactly one authentication check before dispatching to the handler: [1](#0-0) 

The HMAC check itself only signs the raw body, never the shop, topic, or webhook id: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, which for `Request` is just `@raw_body` — the `shop` header is excluded from the signed string entirely: [4](#0-3) 

The equality this breaks is: `shop authenticated by Shopify == shop attributed to the webhook data`. Only the body's integrity/authenticity is proven; the `shop` field used to key `WebhookMetadata` (and therefore any tenant-scoped action the host app takes, e.g. record lookups keyed by shop) is taken from an attacker-controllable, unauthenticated header.

Since `api_secret_key` is one value per app (shared by all installed shops), any merchant that receives a legitimately Shopify-signed webhook for their own store can capture the `(raw_body, X-Shopify-Hmac-SHA256)` pair and re-POST it to the same public webhook endpoint with `X-Shopify-Shop-Domain` changed to a different (victim) shop. `HmacValidator.validate` recomputes the HMAC purely from the body and the shared secret, so it validates identically regardless of which shop header is attached.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged merchant of the app can make the host application process (and attribute) Shopify-signed webhook data as belonging to a different merchant's shop. Depending on how the host app implements its handler (most apps use `data.shop` to select which tenant record to create/update, e.g. inventory, orders, subscription state), this enables cross-tenant data injection/corruption without requiring any credential belonging to the victim.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even free/trial) installer of the target app on their own store — no special privilege, secret, or victim credential is needed. They passively receive a real webhook via their own public endpoint/proxy, then replay body+HMAC with a forged shop header. This is a realistic, low-effort attack path for anyone using the app.

### Recommendation
Bind the trusted shop identity to the signed material instead of an unauthenticated header:
- Reject/flag webhook requests where `shop` cannot be corroborated against a value derived from data covered by the HMAC (e.g., require the host application to look up an active session for the shop and validate the webhook was expected for that specific shop/topic pair before dispatch), or
- At minimum, document prominently that `request.shop` is unauthenticated and must never be used by consuming applications to select or authorize tenant-scoped operations without an additional binding (e.g., cross-checking against a known/registered shop list per topic).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers an event (e.g., `orders/create`) that the app has registered a webhook for.
2. Shopify POSTs the webhook to the app's public endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and the raw JSON body.
3. Attacker captures `raw_body` and the valid `X-Shopify-Hmac-Sha256` value (both fully visible to them, since it is their own webhook).
4. Attacker re-sends an HTTP POST to the same webhook endpoint using the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the shared `api_secret_key` — the forged `shop` header is never verified. [5](#0-4) 
6. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled body content, and the host application processes it as data belonging to the victim tenant.
