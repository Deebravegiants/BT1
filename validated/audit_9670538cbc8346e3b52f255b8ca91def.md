Audit Report

## Title
CORS wildcard origin allowlist bypass via unanchored suffix match - (File: core/services/gateway/network/httpserver.go)

## Summary
The gateway HTTP server's CORS wildcard-origin check in `isAllowedOrigin` uses `strings.HasSuffix(originHost, allowedHost)` without requiring a `.` boundary before the matched suffix, so a domain like `evilremix.com` or `fakeethereum.org` incorrectly satisfies a `*.remix.com` / `*.ethereum.org` allowlist entry even though it is not a subdomain. This lets an attacker-controlled origin have its value reflected into `Access-Control-Allow-Origin`, granting it CORS access intended only for legitimate subdomains.

## Finding Description
`isAllowedOrigin` strips the `*.` prefix from a configured wildcard entry and then performs a bare suffix check: [1](#0-0) . Because `strings.HasSuffix` has no notion of a label/dot boundary, an origin host that merely ends with the same character sequence as the allowed domain (without a preceding `.`) will pass — e.g., for allowed origin `*.remix.com`, an attacker registering `evilremix.com` also satisfies `strings.HasSuffix("evilremix.com", "remix.com")`.

This function is invoked directly from `handleRequest` using the unauthenticated, attacker-controlled `Origin` request header on every request to the gateway's configured path: [2](#0-1) . When `isAllowedOrigin` returns true, the raw `Origin` value is reflected back verbatim in `Access-Control-Allow-Origin`, with no additional boundary validation performed anywhere else in the request path — the existing checks only compare scheme, port, and the flawed suffix, and there is no code that re-validates the dot boundary before setting the header.

The existing unit tests (`core/services/gateway/network/httpserver_test.go`) only test the negative case where the origin doesn't end with the allowed suffix at all (e.g. `https://ethereum.remix.org` vs `*.ethereum.org`), not the boundary-bypass case (e.g. `fakeethereum.org` vs `*.ethereum.org`), confirming this specific bypass is untested and unguarded. [3](#0-2) 

## Impact Explanation
This is a concrete allowlist-bypass in the gateway's CORS logic (in-scope impact category: "allowlist or subscription bypass"). An operator who legitimately configures a wildcard entry such as `*.remix.com` in `CORSAllowedOrigins` (a supported, documented configuration option, see `core/scripts/gateway/sample_config.toml`) unintentionally also grants CORS access to any attacker-registered domain sharing that literal suffix, e.g. `evilremix.com`. Browsers on such attacker sites would then be permitted to read the gateway's HTTP-facing responses via the reflected `Access-Control-Allow-Origin` header, which is a genuine cross-origin trust violation of the intended allowlist boundary.

## Likelihood Explanation
Exploitation requires only that (1) the operator has enabled `CORSEnabled` and configured at least one wildcard entry in `CORSAllowedOrigins`, and (2) an attacker registers a cheap domain sharing the allowed suffix (e.g. `evilremix.com`) and gets a victim's browser to issue a request with that `Origin` to the gateway. No authentication, special network position, or privileged role is needed on the attacker's part — this is directly reachable by an unprivileged web client via the `Origin` header, matching the described bug class exactly.

## Recommendation
Change the wildcard match in `isAllowedOrigin` (core/services/gateway/network/httpserver.go:184-190) to require a proper subdomain boundary — compare against the allowed host prefixed with a literal dot (e.g. `.remix.com`) rather than the bare `remix.com`, so that only true subdomains (`foo.remix.com`) match and lookalike domains (`evilremix.com`) are rejected:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".remix.com"
    if originHost == allowedHost[2:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```

## Proof of Concept
1. Configure the gateway with `CORSEnabled: true` and `CORSAllowedOrigins: ["https://*.remix.com"]`.
2. Send `POST` to the gateway's configured path with header `Origin: https://evilremix.com`.
3. Observe `isAllowedOrigin` returns `true` and the response includes `Access-Control-Allow-Origin: https://evilremix.com`, confirmed by tracing through `splitURL` → `strings.HasSuffix("evilremix.com", "remix.com")` = true, even though `evilremix.com` is not a subdomain of `remix.com`. This can be verified as a Go unit test analogous to the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, substituting origin `https://evilethereum.org` against allowed `https://*.ethereum.org` and asserting the header is (incorrectly) set.
