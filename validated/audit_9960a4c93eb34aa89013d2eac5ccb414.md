### Title
Overfill circuit breaker (`maxOverfillBps`) is disabled and only warns instead of capping the fill, letting a single order drain unbounded solver funds under a stale or manipulated price - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
`FXFiller.calculateProfitability` in `sdk/packages/simplex/src/strategies/fx.ts` computes an "overfill ceiling" (`(1 + maxOverfillBps) × userRequested`) meant to bound how much more than the user asked for the solver will ever pay out on a fill. Instead of clamping the payout to that ceiling, the code only logs a warning when the ceiling is exceeded and then pays out the full, unclamped `policyMaxOutput`. This is the same bug class as Sherlock M-6 in BondBaseSDA: a protective threshold exists conceptually, but the current transaction is allowed to fully complete past it instead of being capped/reverted at the limit, so a single stale/manipulated price read can drain funds far beyond the intended safety bound in one fill.

### Finding Description
In `calculateProfitability`, for each order leg the filler computes `rawPolicyMaxOutput` from `computeLegPolicyOutput`, which is derived from `rates.rate` (a venue/curve price, potentially sourced from an on-chain venue such as Uniswap V4 via `getVenueUsdPrice`). [1](#0-0) 

The code computes an explicit ceiling and detects when the unclamped output exceeds it, but — per its own comment — the clamp is disabled and the filler proceeds with the full unclamped amount anyway, only emitting a warning log: [2](#0-1) 

```
// Overfill detection is warn-only: the clamp is DISABLED, so the filler
// fills the full computed amount even when it exceeds
// (1 + maxOverfillBps) × user-requested — including venue-priced legs
// (e.g. Uniswap V4). NOTE: this removes the per-leg loss bound that
// previously protected against a bug / stale cache / manipulated venue
// price. Output is no longer capped; we only emit a warning.
const overfillCeiling = (output.amount * (10000n + this.maxOverfillBps)) / 10000n
const policyMaxOutput = rawPolicyMaxOutput
if (rawPolicyMaxOutput > overfillCeiling) {
    this.logger.warn(..., "Overfill ceiling exceeded — clamp disabled, filling unclamped amount")
}
```

That unclamped `policyMaxOutput` (`targetOutput`) is then what the filler actually pays out and sources from its wallet/funding venues in the very same call: [3](#0-2) 

The parallel design-decision doc explicitly documents that this is a known-disabled safety mechanism, not a design choice validated as safe, and flags it as future work: [4](#0-3) 

This mirrors the BondBaseSDA `term.maxDebt` circuit breaker flaw exactly: a bound designed to stop excessive extraction (`term.maxDebt` there, `maxOverfillBps` here) is checked only after the fact, and the current operation is allowed to complete in full regardless of the breach, rather than being capped to the safe amount or reverted before the loss is realized. Just as in the original report where the fastest taker could extract free payout tokens when the quote token collapsed in value, here whenever the venue/curve rate the filler reads is stale, manipulated (e.g., via a flash-loan price move against a Uniswap V4 pool used as a price source, per `getVenueUsdPrice`), or simply mispriced, the filler pays out the full unclamped amount for that single order, with no ceiling enforced in-transaction.

`checkPriceGuard` is a separate, optional, static-reference deviation guard applied only to venue quotes when a `priceGuard` config exists per chain; it does not substitute for the overfill ceiling, is not shown to be applied on this specific `rawPolicyMaxOutput`/`policyMaxOutput` decision inline for every leg, and per operator config can be absent entirely (`if (!guard || guard.reference.lte(0)) return true`). [5](#0-4) 

### Impact Explanation
Because the ceiling check is a warn-only no-op, a single order fill can force the solver to pay out an arbitrarily large amount above `(1+maxOverfillBps) × userRequested` whenever the priced rate is wrong (stale cache, misconfigured curve, or a manipulated/exploited on-chain venue price feed). This is the analog of "extraction of payout tokens beyond the intended cap in a single transaction, before the breaker can act" — funds are lost to the counterparty of that specific fill, with no per-transaction cap protecting the solver's balance. Given intent solvers are explicitly an in-scope actor, and the disabled clamp is documented as removing "the per-leg loss bound that previously protected against a bug / stale cache / manipulated venue price," this is a concrete theft-of-funds vector against solver capital, satisfying a Medium/High severity bar analogous to the original M-6 finding.

### Likelihood Explanation
The mechanism is unconditionally reachable on every order that resolves to a venue-priced or curve-priced leg — no privileged action is required, and any order placer/venue-price mover can trigger it. It requires either (a) an existing stale/incorrect rate read (`resolveLegRates`/venue price), or (b) direct manipulation of the venue price source (e.g., flash-loan attack on the Uniswap V4 pool used by `getVenueUsdPrice`) in the same block as order fill, both of which are realistic conditions the code's own comment anticipates ("a bug / stale cache / manipulated venue price"). The disabled state is a deliberate, currently-shipped configuration, not a hypothetical edge case.

### Recommendation
Re-enable the overfill ceiling as an actual clamp (or hard-revert the leg fill) rather than warn-only: cap `policyMaxOutput` to `overfillCeiling` before it is used to compute `targetOutput`/`walletContribution`/`needed`, so a mispriced or manipulated rate can never cause a single fill to exceed the configured `maxOverfillBps` bound. If unconditional overfilling is intentionally desired as a competitive feature, gate the removal of the clamp behind a strict, always-enforced price-deviation guard (not an optional per-chain config) applied to every venue/curve-priced leg, and/or introduce a hard per-order/per-block loss ceiling independent of the advertised curve price.

### Proof of Concept
1. Configure an `FXFiller` pair whose leg is venue-priced (Uniswap V4-backed) or curve-priced from `resolveLegRates`, with `maxOverfillBps` set to a small value (e.g. 500 = 5%).
2. Cause the priced rate (`rates.rate`) fed into `computeLegPolicyOutput` to spike well above its expected value — via a flash-loan manipulation of the underlying venue pool, a stale cache read, or a misconfigured curve — such that `rawPolicyMaxOutput` is, say, 10x `output.amount`.
3. Submit an order whose leg matches this pair and call `fillOrder`/have the filler evaluate `calculateProfitability`.
4. Observe that `overfillCeiling = output.amount * (10000+500)/10000` is computed and the code detects `rawPolicyMaxOutput > overfillCeiling`, but only logs a warning (`"Overfill ceiling exceeded — clamp disabled, filling unclamped amount"`) at [6](#0-5) ; `policyMaxOutput` remains `rawPolicyMaxOutput` and is used unclamped as `targetOutput` at line 736, causing the solver to pay out the full 10x amount in a single transaction instead of being capped at the 5% ceiling.

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
