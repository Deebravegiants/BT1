### Title
Periodic scheduled task can be permanently dropped via agenda-slot exhaustion at the predictable rescheduling block - (File: substrate/frame/scheduler/src/lib.rs)

### Summary
`Pallet::service_task` reschedules a periodic task by calling `Self::place_task(wake, s)` where `wake = now + period` is fully predictable in advance. `place_task` delegates to `push_to_agenda`, which fails with an `Exhausted`-style error once `Agenda::<T>::get(wake)` already holds `MaxScheduledPerBlock` non-empty slots. When that failure happens for a periodic reschedule, the task is not retried or deferred — it is dropped and only an `Event::PeriodicFailed` is emitted.

### Finding Description
`Pallet::place_task` at [1](#0-0)  inserts a task into the agenda for block `when` via `Self::push_to_agenda(when, what)`. `push_to_agenda` operates on the `BoundedVec<_, T::MaxScheduledPerBlock>` stored in `Agenda::<T>` for that block [2](#0-1) ; when the vector has no empty ("hole") slot and is already at `MaxScheduledPerBlock` capacity, insertion fails and the error propagates back through `place_task` as `Err((DispatchError, ScheduledOf<T>))`.

When `service_task` executes a periodic task, it computes the next `wake` block deterministically as `now.saturating_add(period)` and calls `place_task(wake, s)` to reinsert the task for its next occurrence. If that call fails (agenda full at `wake`), the scheduler pallet does not retry, does not search for a nearby free block, and does not persist the task elsewhere for manual recovery — it drops the call's preimage and emits `Event::PeriodicFailed`, permanently losing the periodic task.

Because `wake` is a simple, publicly computable function of the current block number and the task's configured `period` (both visible on-chain), an attacker holding a `ScheduleOrigin`-permitted origin can:
1. Observe/predict `wake` for a known periodic governance task.
2. Submit `MaxScheduledPerBlock` `schedule` calls (e.g., trivial remarks or no-op calls, possibly at low priority) targeting exactly block `wake`, filling `Agenda::<T>::get(wake)` to capacity before the periodic task's `service_task` executes.
3. When the periodic task's own `service_task` runs and calls `place_task(wake, ...)`, the bounded agenda vector for `wake` is full, insertion fails, and the periodic task is dropped with `PeriodicFailed` instead of being retried.

This is a genuine gap: the codebase's own migration/legacy comments and the historical `PeriodicFailed` event acknowledge that a failed reschedule is an unrecovered, drop-on-failure path rather than a retried/deferred one.

### Impact Explanation
A periodic task — potentially a critical governance or protocol maintenance call (e.g., a recurring `Preimages::bound`-referenced dispatch) — can be permanently and silently removed from the schedule by an attacker who can predict the deterministic `wake` block and win the race to fill that block's agenda first. This violates the invariant that critical queues must not be permanently halted by valid user input, since after `PeriodicFailed` the task is gone and requires manual governance intervention to re-schedule, rather than automatic recovery.

### Likelihood Explanation
Exploitability is fully deterministic (no race against unknown state — `wake` is computable from public on-chain data), and repeatable every period as long as the attacker maintains the ability to fill the target agenda slot before the periodic task's own placement runs. The only material precondition is `ScheduleOrigin` access: in most production runtimes (Polkadot, Kusama, system parachains) `ScheduleOrigin` is restricted to governance/Root-derived origins, not arbitrary signed accounts, which significantly narrows real-world exploitability. However, any runtime or parachain that configures `ScheduleOrigin` to allow a broader signed-based or permissionless origin (as the question's stated precondition assumes) is directly exposed, and the underlying logic flaw in the scheduler pallet itself is real and origin-agnostic.

### Recommendation
When `place_task` fails during periodic rescheduling in `service_task`, do not simply drop the task on `Exhausted`/agenda-full errors. Instead, retry insertion at the next block(s) after `wake` (bounded by a reasonable search window) before giving up, and/or preserve the failed task's data (e.g., in a dedicated "failed periodic tasks" storage item) so governance can manually re-schedule it, rather than fully discarding the call and only emitting `PeriodicFailed`.

### Proof of Concept
Rust integration test in `substrate/frame/scheduler/src/tests.rs`:
1. Schedule a periodic task `T_period` with `maybe_periodic = Some((period, count))` at block `N`.
2. Compute `wake = N + period`.
3. Before block `N` executes, issue `MaxScheduledPerBlock` separate `Scheduler::schedule` calls all targeting `DispatchTime::At(wake)`, filling `Agenda::<Test>::get(wake)` to `T::MaxScheduledPerBlock::get()` non-empty entries.
4. Advance to block `N`, letting `on_initialize` run `service_task` for `T_period`.
5. Assert:
   - `System::events()` contains `Event::PeriodicFailed { task: (N, index), id }` for `T_period`.
   - `Agenda::<Test>::get(wake)` does NOT contain `T_period`'s call (task lost).
   - Advancing past `wake` shows the periodic task never executes again, confirming permanent loss rather than deferral/retry.

	fn place_task(
		when: BlockNumberFor<T>,
		what: ScheduledOf<T>,
	) -> Result<TaskAddress<BlockNumberFor<T>>, (DispatchError, ScheduledOf<T>)> {
		let maybe_name = what.maybe_id;
		let index = Self::push_to_agenda(when, what)?;
		let address = (when, index);
		if let Some(name) = maybe_name {
			Lookup::<T>::insert(name, address)
		}
		Self::deposit_event(Event::Scheduled { when: address.0, index: address.1 });
		Ok(address)
	}
