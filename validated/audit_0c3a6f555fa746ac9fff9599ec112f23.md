### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC of the raw request body, then trusts an out-of-band, non-signed HTTP header (`x-shopify-shop-domain` / `shopify-shop-domain`) as the tenant identity handed to the app's webhook handler. Because the header is not part of the HMAC-signed payload, any party who can present a body+HMAC pair that is valid for the shared `api_secret_key` (trivially obtainable by installing the app on their own store and capturing one of their own legitimate webhook deliveries) can attach an arbitrary `shop-domain` header value and have the app process the request as if it belonged to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an HTTP header with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it only against the received `hmac` — it never touches `shop`: [3](#0-2) 

`Registry.process` uses this validation as the sole authenticity gate, then forwards the unauthenticated `request.shop` straight to the app's handler as the tenant identifier: [4](#0-3) 

The identity binding that should hold is:
`HMAC(secret, raw_body) == received_hmac` **AND** `shop-domain header is bound to that same signed payload`.

What actually holds is only the first half — `verified_bytes (raw_body)` ≠ `used_identity_bytes (shop-domain header)`. The header can be swapped freely without invalidating the HMAC, since the HMAC never covers it.

The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole request (including its shop attribution) is authenticated: [5](#0-4) 
In reality only the body is authenticated; `data.shop` handed to every registered handler is attacker-controllable header data.

### Impact Explanation
An unprivileged internet user who can install the target app on their own (e.g., free development) store receives genuine webhook deliveries for that store, each with a valid body+HMAC pair signed with the app's shared `api_secret_key`. Because the HMAC never covers the `shop-domain` header, the attacker can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic and invoke the handler with `data.shop` set to the victim's domain, alongside the attacker-controlled `data.body`. Any host application that uses `data.shop` to look up per-tenant state (as the gem's own documentation example does: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will attribute attacker-controlled webhook data to another tenant — a cross-tenant integrity/authentication violation rooted entirely in this gem's webhook verification logic.

### Likelihood Explanation
Low difficulty: no secrets, tokens, or privileged access are required beyond installing the app once on an attacker-owned store (a normal, permitted action for any Shopify merchant/developer) to obtain one valid `(raw_body, hmac)` pair, then re-sending it with a modified header. This mirrors exactly the reported bug class: an identity-relevant field (the shop/tenant) is trusted while not being covered by the HMAC that is supposed to authenticate the whole interaction.

### Recommendation
- Short term: Bind the shop identity to the signed payload — either include the `shop-domain` header value in the HMAC signable string, or independently verify that `request.shop` matches a shop the app actually has an active, previously-authenticated session/webhook registration for before dispatching to the handler.
- Long term: Document clearly in `docs/usage/webhooks.md` that `Registry.process` only authenticates body integrity, not header-supplied identity fields, and provide/require an explicit shop-registration check API so host apps don't implicitly trust `data.shop`.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header value (both valid under the app's shared `api_secret_key`).
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Topic: orders/create
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` accepts the forged headers, and `Registry.process`:
   ```ruby
   raise Errors::InvalidWebhookError unless Utils::HmacValidator.validate(request) # passes, HMAC over raw_body only
   handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)) # shop == "victim-shop.myshopify.com"
   ```
4. The host app's handler processes attacker-controlled `body` attributed to `victim-shop.myshopify.com`, demonstrating the cross-tenant identity spoof.
