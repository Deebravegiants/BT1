### Title
Webhook HMAC does not bind the `shop-domain` (or `topic`) header, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` proves nothing about the `x-shopify-shop-domain` (or `x-shopify-topic`) header. Because the same `api_secret_key` signs webhook bodies for every shop installed on the app, any tenant who receives a legitimate webhook for their own store can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting a different shop's domain in the header, and the request will pass validation and be dispatched to the handler as if it came from the victim shop.

### Finding Description
`Registry.process` validates a webhook solely via: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value pulled from the header: [2](#0-1) 

For `Webhooks::Request`, `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers, but `to_signable_string` — the only value actually covered by the signature — is just the raw body: [3](#0-2) 

This breaks the identity binding `HMAC-authenticated bytes == shop the handler acts on`. The HMAC only proves "this body was signed by Shopify with this app's secret" — it says nothing about which shop the body belongs to, because the `shop-domain` header is never part of the signed material. Since `api_secret_key` is identical for every shop connected to the app, a webhook body+HMAC pair that Shopify legitimately sent for tenant A's store is equally "valid" when replayed with tenant B's domain in the header. The handler then receives the attacker-chosen shop as authoritative: [4](#0-3) 

### Impact Explanation
This is a cross-tenant access issue: an unprivileged holder of one valid tenant's webhook traffic can forge webhook events attributed to a different, arbitrary tenant recognized by the multi-tenant app, since the gem provides no mechanism binding the signed body to the shop header. Any app logic keyed off `WebhookMetadata#shop` (order processing, billing, uninstall handling, data sync, etc.) can be triggered against a victim shop's account using data that was never actually sent by Shopify for that shop.

### Likelihood Explanation
Any merchant who installs the app receives real Shopify webhooks for their own store and therefore always possesses a valid `(raw_body, hmac)` pair signed with the app's shared secret. Capturing their own webhook traffic (e.g., via a proxy) and replaying it to the app's public webhook endpoint with a modified `x-shopify-shop-domain` header requires no special privilege beyond being a normal, authenticated user of their own shop — no access token, `client_secret`, or credential theft is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the material that is HMAC-verified, or otherwise cryptographically bind the header values to the signed body before trusting `request.shop`/`request.topic` in `Registry.process`. Short of protocol changes on Shopify's side, the gem should at minimum document that `WebhookMetadata#shop` is not cryptographically authenticated by the current HMAC check and instruct consumers to independently verify that the shop is one they have an active session/installation for before acting on the payload.

### Proof of Concept
1. App is installed on `tenant-a.myshopify.com` and `tenant-b.myshopify.com`, both using the same app `api_secret_key`.
2. Attacker controls `tenant-a.myshopify.com` and captures a genuine Shopify webhook POST to the app's webhook route, e.g. body `B` and header `x-shopify-hmac-sha256: H` (valid per `HmacValidator.validate_signature`, since `H = HMAC(api_secret_key, B)`, matching `lib/shopify_api/utils/hmac_validator.rb:26-31`).
3. Attacker resends the identical `B`/`H` pair to the same endpoint, but sets `x-shopify-shop-domain: tenant-b.myshopify.com` (and optionally changes `x-shopify-topic`).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates via `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`), i.e., the body — unaffected by the header change — so validation succeeds.
5. The handler executes with `WebhookMetadata.new(shop: "tenant-b.myshopify.com", ...)`, causing the app to process attacker-supplied data as if it originated from `tenant-b`'s store.

          received_signature = verifiable_query.hmac
