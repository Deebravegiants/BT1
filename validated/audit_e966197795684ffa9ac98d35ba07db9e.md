### Title
Missing sanity-bound validation on Chainlink oracle price in `SimplexPaymaster` allows a depegged/clamped feed to mis-price gas fees, over-charging or under-collecting from every UserOp sender - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster._getOraclePrice` only rejects a Chainlink answer that is `<= 0` or older than `maxOracleAge`. It never checks the reported price against any sane min/max band. Every priced action in the contract — `_tokenPrice` (used by `_fetchDetails`/`_validatePaymasterUserOp` to compute the ERC-20 amount charged for gas on every UserOp) and `swapAndDeposit` (used to size `amountOutMin` for fee-recycling swaps) — consumes this unbounded value directly. This is the exact bug class from the referenced report: a fresh, positive, but economically wrong price (stablecoin depeg, or a Chainlink aggregator clamped at its configured `minAnswer`/`maxAnswer` during a crash) is accepted as truth.

### Finding Description
`_getOraclePrice` in `evm/src/utils/SimplexPaymaster.sol` performs only two checks: [1](#0-0) 

There is no `minPrice`/`maxPrice` bound, and no cross-check against a secondary source. `_setParams` similarly bounds `markupBps`, `maxOracleAge`, and `swapSlippageBps` but has no field for a price sanity band: [2](#0-1) 

This price feeds directly into `_tokenPrice`, which every UserOp's `_fetchDetails` calls to determine how many ERC-20 tokens a sender is charged for gas: [3](#0-2) [4](#0-3) 

It is also used to size the minimum acceptable swap output in `swapAndDeposit`: [5](#0-4) 

Chainlink aggregators are commonly configured with hard `minAnswer`/`maxAnswer` bounds; during a sharp de-peg or crash the feed can continue returning a clamped, stale-looking-but-"fresh" value that no longer reflects the true market price (the exact scenario cited in the source report for USDC/USDT/DAI/LUSD). Because `_getOraclePrice` accepts any positive, non-stale answer unconditionally, this contract has no defense against that failure mode.

### Impact Explanation
- If the gas-payment token's oracle under-reports the token's true (depegged) value — i.e. the feed still reports close to $1 while the token trades materially below par — `_tokenPrice` computes too low a `tokenPrice`, meaning users are charged too few tokens relative to the real gas cost the paymaster pays in native currency. This drains the paymaster's native EntryPoint deposit/treasury reserves relative to the (devalued) ERC-20 it collects — a protocol-level loss reachable by every ordinary UserOp sender ("bandwidth purchaser") with no privileged action required.
- Conversely, if the feed over-reports the token's value (or the native-asset feed misreports), users are charged more ERC-20 tokens than the gas is worth — direct value extraction from unprivileged senders on every sponsored operation.
- The same unbounded price also under-protects `swapAndDeposit`'s `amountOutMin`, which can misprice the router trade against the fair market value, degrading the fee-recycling swap even while nominally respecting `swapSlippageBps` (bounded at 10%), because the reference price itself, not just the slippage, is wrong.

This satisfies the "concrete theft" bar: no admin/governance misbehavior is required, only a naturally occurring stablecoin de-peg or aggregator clamp event — after which every ordinary UserOp continues to be priced off the same faulty oracle.

### Likelihood Explanation
Stablecoin de-pegs and Chainlink aggregator min/max clamps are documented, recurring real-world events (USDC to ~$0.83 in 2023, USDT/DAI/LUSD volatility cited in the source report). `SimplexPaymaster` is intended to accept exactly these assets ("USDC, USDT, or any token with a Chainlink feed"), and every UserOp routed through it during such an event is mispriced with no additional attacker action needed — this is a systemic, not merely theoretical, risk.

### Recommendation
Add a governance-configurable `minAnswer`/`maxAnswer` (or percentage deviation band relative to a reference/previous price) per registered oracle in `TokenConfig`/`Params`, and enforce it inside `_getOraclePrice`:
```solidity
require(answer >= minAnswer && answer <= maxAnswer, "Oracle price out of bounds");
```
Additionally consider cross-checking against a secondary price source (e.g. a TWAP) before using a Chainlink answer to price gas, and pausing token acceptance automatically when the bound is breached rather than silently continuing to price off a clamped feed.

### Proof of Concept
1. Register a stablecoin `T` in `SimplexPaymaster` with its Chainlink `T/USD` feed via `RegisterToken` governance.
2. The underlying stablecoin de-pegs to $0.80 while its Chainlink aggregator, due to a configured `minAnswer` floor, continues to return `answer = 1e8` (i.e. $1.00) with a fresh `updatedAt`.
3. A user submits a UserOp paying gas in `T`. `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` accepts the clamped $1.00 answer (positive, fresh) without any bound check.
4. The user is charged `T` tokens as if `T` were worth $1.00, while it is actually worth $0.80 on the open market — the paymaster (and ultimately its treasury) is under-collateralized by 20% relative to the native gas it fronts on every such operation, and this repeats for every UserOp until governance manually re-registers a corrected oracle.     /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
