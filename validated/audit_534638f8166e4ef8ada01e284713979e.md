## Title
Challenge period is enforced as a live, mutable global value instead of being pinned to the state commitment it protects — retroactively shrinking the security window for already-stored commitments - ([File: evm/src/core/HandlerV2.sol], [File: modules/ismp/core/src/handlers.rs], [File: modules/pallets/ismp/src/lib.rs])

### Summary
The challenge period is the delay window that gives fishermen time to veto a fraudulent `StateCommitment` before it can be used to deliver requests, responses, or timeouts. Rather than being fixed at the moment a `StateCommitment` is stored, the delay check reads the *current* `challengePeriod` value at the moment a relayer submits a message, and compares it against a fixed `update_time` recorded when the commitment was stored. This is the same root-cause pattern as the referenced report: a wait time that should be pinned to a specific record at creation time is instead checked against a mutable global variable at execution time, so a later change to that variable silently changes the effective delay for records that already exist.

### Finding Description
On the EVM side, `HandlerV2.handlePostRequests` (and the analogous `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) computes the elapsed delay from the fixed `stateMachineCommitmentUpdateTime(height)` but compares it to the live `host.challengePeriod()`: [1](#0-0) 

`challengePeriod` is a single mutable value in `HostParams`, changeable at any time via `IHostManager.updateHostParams` (invoked cross-chain via governance), with no validation tying it to already-stored, pending commitments: [2](#0-1) [3](#0-2) 

The same pattern exists in the ISMP core (used by pallet-ismp): `verify_delay_passed` computes `current_timestamp - update_time` and compares it to `host.challenge_period(proof_height.id)`, again the *current* value, not the value in effect when the commitment at `update_time` was stored: [4](#0-3) 

Challenge periods are updatable per-state-machine at any time via a signed extrinsic through `update_consensus_state`, and take effect immediately for every commitment already sitting in storage, not just future ones: [5](#0-4) 

Because the recorded `update_time`/`stateMachineCommitmentUpdateTime` is fixed but the period it's checked against is not, any reduction of the challenge period retroactively shortens the fraud-detection window that was promised for commitments finalized before the change — commitments a fisherman may have been in the process of vetting on the assumption of the original, longer window. A relayer (an unprivileged dispatcher of ISMP messages) simply needs to call `handlePostRequests`/`handle_unsigned` with a proof at a height whose `update_time` predates the reduction; the check passes purely because the global variable moved, not because the intended delay for that specific commitment ever elapsed.

### Impact Explanation
This breaks the core security invariant of the optimistic-bridging design described in the protocol's own docs — that a fixed challenge window is guaranteed between consensus verification and usage of a state commitment so fishermen can catch byzantine commitments: [6](#0-5) 

If the configured challenge period for a state machine is lowered while commitments made under the previous, larger period are still within their original window, those commitments become immediately actionable — before the fraud-detection time that was in effect (and presumably relied upon by fishermen and the market) when they were stored has elapsed. This permits requests/responses/timeouts to be delivered from a state commitment that has not actually cleared its promised veto window, i.e. an unsound state commitment being consumed to deliver otherwise-unauthenticated cross-chain messages — a forged/prematurely-trusted message delivery risk, not merely a UX inconvenience. This is a protocol-wide, systemic issue reachable through the exact "EvmHost and HandlerV2 dispatch and delivery" / "pallet-ismp handle_unsigned" surfaces the scope calls out.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: challenge periods are expected to be tuned over the life of the protocol (e.g. lowered as confidence in a chain's finality grows, or during incident response), and every such change silently applies to all commitments already in flight. No malicious actor is required to trigger the exposure — a normal, well-intentioned parameter update combined with the pre-existing check design produces the unsafe window; any relayer can then opportunistically submit a message during that window with no additional privilege.

### Recommendation
Pin the challenge period to the state commitment at the moment it is stored (store `(update_time, challenge_period_at_commit)` per height, or equivalently derive the applicable delay from the value that was configured when `store_state_machine_commitment`/`storeStateMachineCommitment` ran) rather than re-reading the live parameter at verification time. Configuration changes should only affect commitments recorded after the change, exactly as the original report recommends storing the delay per-request rather than checking it against a mutable global at collection time.

### Proof of Concept
1. Governance calls `update_consensus_state` (or `updateHostParams` on EVM) to lower `challenge_period`/`challengePeriod` for state machine `S` from `T_old` to `T_new` (`T_new < T_old`).
2. A `StateCommitment` at height `H` for `S` was stored at `update_time = t0` under `T_old`, i.e. it was meant to only be usable at `t0 + T_old`.
3. Governance's change lands at `t1`, where `t0 < t1 < t0 + T_new < t0 + T_old`.
4. Any relayer calls `handlePostRequests` (or `handle_unsigned` with a `RequestMessage`) with a proof at height `H`: `delay = now - t0 >= T_new` passes the check even though `now < t0 + T_old`, so the message is delivered before the originally-promised challenge window for commitment `H` elapsed. pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

### Optimistic Bridging

To prevent the damage that can be done to our bridge in the event of a byzantine attack, **we must introduce a challenge window in the form of a time delay between when consensus proofs are verified by our consensus client and when state proofs associated with those headers can be used to process cross-chain messages.**

During this challenge window, consensus clients can detect byzantine attacks. Off-chain consensus clients can do this by participating in the P2P network. On-chain consensus clients, on the other hand, will need to rely on off-chain parties, which we'll call fishermen<sup>[3]</sup>, to provide the proofs of fraud to the client.

These fishermen will need some incentive to watch for byzantine attacks and report the fraud proofs which will safeguard the consensus client. As such, we will require relayers who submit consensus proofs to be staked, in the event of byzantine attacks, relayer’s stake can be used to incentivise fishermen to submit fraud proofs.
