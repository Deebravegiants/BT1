### Title
Escrow withdrawal in Tron `IntentGatewayV2.withdraw()` doesn't check ERC20 return value, causing silent loss of escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed tokens using a raw low-level `.call()` to the ERC20 `transfer` selector and only checks that the call itself didn't revert, never decoding/validating the boolean return value. Tokens that fail silently (return `false` instead of reverting) — a common pattern on TRC20/legacy ERC20 tokens — will cause the escrow accounting to be finalized as if the transfer succeeded while the beneficiary receives nothing, permanently losing escrowed funds.

### Finding Description
In `withdraw()`, escrowed tokens are released to a beneficiary via: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
```

The `success` variable here only reflects whether the low-level `call` itself reverted — it does **not** decode the ABI-encoded `bool` returned by a conforming `transfer()` implementation. Per EIP-20, `transfer()` is only required to return `true`/`false` to indicate success; it is not required to revert on failure. Many deployed tokens (and this is especially prevalent among TRC20 tokens on Tron, which this file specifically targets, per its own docstring "Implements the IntentGatewayV2 contract for Tron") return `false` on failed transfers instead of reverting.

The same unchecked pattern is repeated for `SweepDust` handling and fee token payout in the same file: [2](#0-1) [3](#0-2) 

Immediately after the unchecked transfer, `withdraw()` unconditionally decrements the escrow accounting and marks the order as filled: [4](#0-3) 

This is directly reachable by any unprivileged relayer delivering a `RedeemEscrow`/`RefundEscrow` POST request or a storage-proof `GET` response, both of which route into `withdraw()`: [5](#0-4) [6](#0-5) 

Notably, the main EVM `IntentGatewayV2`/`IntentsBase` implementation correctly uses `SafeERC20.safeTransfer` for the equivalent operation, confirming this Tron variant is inconsistent with the intended safety guarantee: [7](#0-6) 

### Impact Explanation
If the escrowed input token silently fails to transfer (returns `false` without reverting), `_orders[body.commitment][token]` is still decremented and `_filled[body.commitment]` is set, permanently marking the order as resolved. The beneficiary (solver or user, depending on redeem/refund) never receives the tokens, and there is no retry/recovery path since the escrow accounting has already been zeroed out — this is a direct, permanent loss of escrowed user/solver funds for any non-standard/fee-token integrated on Tron via this gateway.

### Likelihood Explanation
Likelihood is High for tokens with non-standard, non-reverting `transfer()` semantics deployed on Tron (a widely used pattern for TRC20). Any user or solver escrowing such a token through `IntentGatewayV2` on Tron, and any relayer delivering the corresponding cross-chain message, triggers the vulnerable code path without any special privileges.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (and the `SweepDust` and fee-token payout paths) with OpenZeppelin's `SafeERC20.safeTransfer`, which is already imported and used elsewhere in this same contract (`using SafeERC20 for IERC20;`). This ensures both call-level reverts and ERC20 boolean-false return values cause the transaction to revert, keeping escrow accounting and actual token movement atomic and consistent.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an ERC20/TRC20 token whose `transfer()` returns `false` on failure instead of reverting (e.g., due to a paused state, blacklist, or insufficient balance edge case that the token's implementation handles by returning `false`).
2. A user places an order escrowing this token via `placeOrder`.
3. A solver fills the order cross-chain; the source-chain gateway later receives a `RedeemEscrow` request and calls `onAccept` → `withdraw()`.
4. The token's `transfer()` call returns `false` (no revert). `success` in `token.call(...)` is `true` because the low-level call itself succeeded; the code proceeds.
5. `_orders[commitment][token] -= amount` executes, escrow is marked filled, `EscrowReleased` is emitted — but the beneficiary's token balance never increased.
6. The escrowed funds are unrecoverable: the order is finalized and no further withdrawal path exists.
