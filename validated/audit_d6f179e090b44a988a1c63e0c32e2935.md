## Title
Missing decimal-scaling branch in `convert_to_balance`/`convert_to_erc20` causes incorrect mint/refund amounts when local decimals exceed ERC20 decimals - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s `on_accept` and `on_timeout` handlers convert an incoming ERC20 `U256` amount into the pallet's local balance type via `convert_to_balance`, using `erc_decimals.saturating_sub(local_decimals)` to compute the scaling divisor. This is directly analogous to the reported `mintlvlUSD` bug: an arithmetic branch that is only correct for one ordering of the two decimal values, silently producing a wrong (unscaled) result in the other case instead of scaling in the opposite direction.

### Finding Description
`convert_to_balance` and `convert_to_erc20` are defined as: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions only implement the scaling logic for the case `erc_decimals >= local_decimals` (division in `convert_to_balance`, multiplication in `convert_to_erc20`). When `erc_decimals < local_decimals`, `saturating_sub` clamps to `0`, so `10u128.pow(0) == 1`, and the function performs **no scaling at all** instead of scaling in the other direction (multiplying in `convert_to_balance`, or dividing in `convert_to_erc20`). This is precisely the same bug class as the external report: a conditional/scaling calculation that omits (or mishandles) one of the two possible decimal relationships, defeating the amount conversion that the receiver relies on for correctness.

This function is invoked directly in the reachable, unprivileged message-delivery path: [2](#0-1) 

`on_accept` decodes an incoming cross-chain `PostRequest`, looks up `erc_decimals` from `Precisions::<T>::get(...)`, and calls `convert_to_balance` with the local asset's `decimals` to determine the `amount` that is then minted or transferred to the beneficiary. The same call occurs in `on_timeout` when refunding the original sender: [3](#0-2) 

Any relayer delivering a message (an unprivileged path — delivery is gated only by module/source checks, not by relayer identity for the pallet side) triggers this conversion. If a registered ERC20 peer token has fewer decimals than the local asset/native currency it is mapped to (e.g., an ERC20 with 6 decimals bridging into an 18-decimal local asset), `erc_decimals.saturating_sub(local_decimals)` evaluates to `0`, and the beneficiary is minted/transferred the raw ERC20 integer value unscaled — i.e., `10^12` times smaller than the correct amount instead of being multiplied up.

### Impact Explanation
This causes a systematic under-crediting of the beneficiary any time `erc_decimals < local_decimals` for a given registered pair, i.e. permanent value loss/freezing of funds on every mint or refund through this path. Depending on which direction the misconfiguration goes it could also, in principle, allow the pallet to mint far larger amounts than intended for the reverse configuration (were `convert_to_erc20`'s missing division to trigger inflated ERC20 amounts sent outward), which would be an unbacked-mint/inflation risk on the EVM side. Since `Precisions` is a governance-configured mapping (per asset/chain), whether this path is reachable in practice depends on whether any registered token pair has `erc_decimals < local_decimals`; where it is, the bug directly and silently miscalculates amounts credited to users on every single cross-chain transfer for that pair, which is a systemic asset-conversion defect functionally identical in class to the reported `mintlvlUSD` issue (missing branch in decimal-scaling logic that a user relies on for correct minted amount).

### Likelihood Explanation
Likelihood depends on deployment configuration: it triggers only for token pairs where `erc_decimals < local_decimals` is registered via `Precisions`. Given ERC20 tokens commonly use 18 decimals and local Substrate assets/native currencies are also frequently 18, or in cases where a locally-registered asset intentionally uses higher precision than a lower-decimal ERC20 peer (e.g. 18-decimal local vs 6-decimal USDC-like ERC20 peer, which is a realistic bridging scenario, e.g., BRIDGE token doc mentions 18 vs 12 decimals with the pallet explicitly scaling by `10^6` "in both directions"), it is plausible this exact scenario is hit in production. The `BridgeToken.sol` documentation explicitly states: "`decimals()` is the inherited ERC20 default of 18 while BRIDGE is 12 decimals on nexus, so the pallet scales by 10^6 in **both directions**" [4](#0-3) , which is the ERC20-decimals(18) > local-decimals(12) case — correctly handled by the existing subtraction. However, I could not fully verify (tool budget exhausted) whether any currently-registered `Precisions` entry has `erc_decimals < local_decimals`, which would be needed to confirm the reverse-direction bug fires today, versus being a dormant defect that would only be triggered by a future/misconfigured registration.

### Recommendation
Fix both `convert_to_balance` and `convert_to_erc20` to branch on the relative ordering of `erc_decimals` and `local_decimals`, symmetric to the external report's recommendation:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```

### Proof of Concept
1. Governance registers an ERC20 peer token with `erc_decimals = 6` mapped to a local asset/native currency with `local_decimals = 18` in `Precisions`.
2. A user bridges `1_000_000` (i.e., 1.0 token at 6 decimals) from the EVM side; the message is delivered by any relayer and processed in `on_accept`.
3. `convert_to_balance(1_000_000, 6, 18)` computes `erc_decimals.saturating_sub(local_decimals) = 6.saturating_sub(18) = 0`, so it divides by `10^0 = 1`, yielding `1_000_000` — instead of the correct `1_000_000 * 10^12 = 1_000_000_000_000_000_000` (1.0 token at 18 decimals).
4. The beneficiary is credited `1_000_000` local-decimal units (effectively `0.000000000001` of a token) instead of `1.0` token — a `10^12`x under-credit, with no error raised.
