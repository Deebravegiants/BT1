### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating only the raw request body against the `X-Shopify-Hmac-Sha256` header, but it then hands the handler a `shop` (tenant identifier), `topic`, and `webhook_id` that are read straight from unauthenticated HTTP headers. This breaks the identity binding `authenticated_bytes == acted_upon_bytes`: the HMAC binds the body, not the shop that the rest of the pipeline treats as the source of truth.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is likewise derived only from the `hmac-sha256` header [2](#0-1) . `Registry.process` validates that signable string/hmac pair via `Utils::HmacValidator.validate` [3](#0-2)  and, if it passes, immediately builds a `WebhookMetadata` object using `request.shop`, `request.topic`, and `request.webhook_id` [4](#0-3)  — all three of which are pulled directly from `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers [5](#0-4)  and are never included in `to_signable_string`.

Because a given app's `api_secret_key` is shared across every shop that installs the app (it is not a per-shop secret; the `HmacValidator` simply HMACs the signable string with `Context.api_secret_key`/`old_api_secret_key`) [6](#0-5) , any merchant who installs the app can legitimately trigger a webhook and thereby obtain a valid `(body, hmac)` pair signed with that shared secret. Nothing prevents that same merchant from replaying the identical body/hmac pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header for a different, victim shop. `HmacValidator.validate` will still accept it because it only checks the body against the secret, and `WebhookMetadata.shop` will be populated with the attacker-chosen value.

This is exactly the "field acted on but not covered by the HMAC" class described in the report: the gem authenticates the payload but binds the tenant-identifying `shop` field out of band from that authentication, then trusts it downstream (`data.shop`) as if it had been verified.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as the library's own documentation and `WebhookHandler#handle` interface encourage) to look up a merchant's session/access token or to route data to the correct tenant's records, an attacker who has installed the app on their own shop can forge the `shop` value to another shop's domain and cause the handler to process data under a different tenant's identity — a cross-tenant confusion condition. This matches the High/Critical bar of cross-tenant access if the host acts on `data.shop` for authorization or record lookups, which is the intended use of that field per the `WebhookMetadata` struct exposed by this gem [7](#0-6) .

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a shop they control (an "unprivileged internet user" with respect to other tenants) and be able to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint — no access to `api_secret_key`, access tokens, or any privileged account belonging to the victim is required. The replay is entirely mechanical: capture one legitimate `(raw_body, hmac)` pair from a webhook Shopify sends to the attacker's own shop, then resend it with a spoofed `shopify-shop-domain` header.

### Recommendation
Bind the tenant/topic identity into the authenticated material, or otherwise cryptographically tie the `shop` value to the signed payload before trusting it in `WebhookMetadata`. Concretely, `Webhooks::Request#to_signable_string` should not be the sole basis for identifying the shop; the gem should either verify that the `shop` returned in the webhook body itself (where Shopify includes shop information in many payloads) matches the header-derived `shop`, or document/enforce that host applications must not use the unauthenticated `shop`/`topic`/`webhook_id` headers as an authorization boundary without an additional check (e.g., confirming the shop is one which currently holds an active, previously-issued OAuth session, and rejecting mismatches).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g., `orders/create`) to the app's registered endpoint. Capture the raw body `B` and the `X-Shopify-Hmac-Sha256` value `H` — both are valid because `HmacValidator` accepts any `(body, hmac)` pair signed with the app's shared `api_secret_key` [8](#0-7) .
2. Attacker sends a new HTTP request to the same webhook endpoint with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)` [9](#0-8)  — validation succeeds because only the body is HMAC-checked.
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` [4](#0-3) , i.e., attacker-controlled data processed under a spoofed tenant identity, despite the HMAC check having passed.
