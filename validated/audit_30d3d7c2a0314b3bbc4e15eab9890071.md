### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, while the `shop` (and `topic`/`webhook_id`) values are read directly from unauthenticated HTTP headers. Because Shopify signs webhooks with a single, app-wide `client_secret` (not a per-shop secret), any attacker who controls a shop that has the app installed can legitimately trigger a webhook, capture its valid `(body, hmac)` pair, and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to point at an arbitrary victim shop. The signature still validates because the header is not part of the signed payload, causing the receiving application to process attacker-controlled data as if it originated from a different merchant.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`, and `hmac` reads a header value, but nothing else in the request (shop, topic, webhook_id, api_version) participates in the HMAC computation: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` verifies the signature purely against `to_signable_string` (the body) using the app's global `Context.api_secret_key`, which is identical for every shop that installs the app — it is not shop-specific: [3](#0-2) 

`Registry.process` then trusts `request.shop` unconditionally to build `WebhookMetadata` handed to the host application's handler, without any additional binding between the verified bytes (body) and the `shop` header: [4](#0-3) 

The equality that should hold but doesn't: `shop authenticated by the HMAC == shop the handler acts on`. Here, the HMAC only authenticates the body bytes, while the `shop` value that the handler uses to attribute the event to a tenant comes from an unauthenticated header. Since the signing secret is shared across all shops of the app (unlike, e.g., OAuth HMAC which is tied to a specific authorization flow), a legitimately-signed payload from shop A's genuine webhook can be replayed with the shop header swapped to shop B, and it will still pass `HmacValidator.validate`.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): an attacker who operates their own store with the app installed can generate a real webhook (e.g., `orders/create` with attacker-chosen content), intercept it, and resend it directly to the app's webhook endpoint with the `shop-domain`/`x-shopify-shop-domain` header altered to a victim shop's domain. If the host application uses `WebhookMetadata#shop` to look up the tenant session, write to tenant-scoped storage, or otherwise attribute the payload, the attacker can inject fabricated data into another merchant's account context, satisfying the "Critical — cross-tenant access" bar.

### Likelihood Explanation
This is exploitable by any unprivileged internet user who can install the target app on their own test/dev store (a realistic and cheap precondition for public Shopify apps), since it requires no access to the app's `client_secret`, access tokens, or any privileged account — only the ability to trigger a webhook for their own shop and replay it with a modified header value to the public webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material used for verification, or otherwise cryptographically tie the header-derived `shop` to the request that was actually signed by Shopify (e.g., include the relevant headers in `to_signable_string`, or independently validate that the shop asserted in the header matches a shop known to be associated with the specific HMAC via an out-of-band, per-shop lookup) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Attacker triggers a genuine webhook (e.g., updates an order) causing Shopify to POST a signed payload: `raw_body = B`, `X-Shopify-Hmac-Sha256 = HMAC(client_secret, B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker intercepts this request (e.g., by pointing the webhook subscription at a proxy they control) and resends the exact same `B` and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` reads the unchanged body and hmac header; `HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb) succeeds because it only checks `B` against the shared app secret.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb, lines 188-200) invokes the host handler with `shop: "victim.myshopify.com"`, causing the application to process attacker-supplied content as belonging to the victim's shop.

          received_signature = verifiable_query.hmac
