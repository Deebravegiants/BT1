### Title
Caller-authenticated flash-position callbacks can append wallet-draining token transfers - ([File: contracts/controller/src/strategies/flash_position.rs](contracts/controller/src/strategies/flash_position.rs))

### Summary
`flash_position` authenticates the caller once, then invokes a caller-selected Wasm contract inside the same authorization tree. [1](#0-0) [2](#0-1)  A malicious receiver can request additional authorization from the supplied initiator and add an unrelated `token.transfer(initiator, attacker, amount)` beneath the victim’s signed `flash_position` invocation. [3](#0-2)  If the victim signs the simulated authorization tree containing that child transfer, the callback drains wallet assets unrelated to the lending operation. [4](#0-3) 

### Finding Description
`process_flash_position` begins with `require_authorized_caller`, which is only a broad `caller.require_auth()` plus the flash-loan reentrancy check. [5](#0-4)  The function accepts a caller-provided `receiver`, requires it to be Wasm, and excludes only the controller and pool addresses. [2](#0-1) 

The controller mints debt, forwards the measured tokens to that receiver, and then calls `execute_flash_position` while the caller’s authorization remains part of the transaction invocation tree. [6](#0-5)  The callback receives the original caller as `initiator`, giving malicious code the exact address from which to request further authorization. [7](#0-6) 

The harness demonstrates that a nested `token.transfer(caller, attacker, amount)` is recorded as a child of the caller’s top-level authorization and steals an unrelated token when the poisoned tree is signed. [8](#0-7) [4](#0-3)  The callback can simultaneously return enough collateral for the newly minted debt, after which the controller deposits the measured receipts and finalizes the solvent position. [9](#0-8) 

### Impact Explanation
A successful attack steals arbitrary token balances from the user’s wallet, including assets never supplied to or listed by the protocol. [10](#0-9) [11](#0-10)  This is direct theft of user funds because the malicious callback names the authenticated `initiator` as `from` and chooses the attacker as `to`. [7](#0-6) [12](#0-11) 

### Likelihood Explanation
The attacker only needs to deploy a valid Wasm receiver and cause a victim to submit `flash_position` with that receiver, for example through a malicious interface or copied transaction parameters. [13](#0-12)  The victim must sign the recorded authorization tree containing the unexpected transfer, so the attack requires authorization-tree phishing rather than working without a signature. [14](#0-13)  No privileged role, leaked key, malicious listed token, or control of protocol infrastructure is required. [5](#0-4) [15](#0-14) 

### Recommendation
Do not invoke arbitrary caller-selected contracts under a broad account-owner authorization root. Prefer a fixed protocol-controlled receiver or a governance-reviewed receiver allowlist, and treat any design that permits arbitrary callbacks after `caller.require_auth()` as exposing the caller’s full nested authorization surface. [5](#0-4) [2](#0-1)  If arbitrary receivers remain necessary, document that wallets and integrators must reject any authorization child other than the explicitly expected token movements before signing. [3](#0-2) 

### Proof of Concept
1. The victim owns an existing solvent Multiply-compatible account and also holds a token unrelated to the lending markets. [16](#0-15) 
2. The attacker deploys a receiver whose `execute_flash_position` calls `token.transfer(initiator, attacker, victim_balance)` for that unrelated token, then transfers enough declared collateral back to the controller. [12](#0-11) [15](#0-14) 
3. The victim is induced to call `controller.flash_position(victim, account_id, spoke_id, mode, debt, amount, malicious_receiver, data, collaterals, refund_assets)`. [17](#0-16) 
4. The controller authenticates `victim`, forwards the minted debt asset to the receiver, and invokes the malicious callback. [5](#0-4) [6](#0-5) 
5. Transaction simulation records the receiver’s unrelated token transfer under the victim’s `flash_position` authorization root. [18](#0-17) 
6. Once the victim signs that tree, the callback transfers the victim’s unrelated balance to the attacker while returning collateral sufficient to satisfy the declared minimums and final solvency checks. [4](#0-3) [9](#0-8)
