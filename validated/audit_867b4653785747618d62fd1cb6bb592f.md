### Title
Webhook Tenant Spoofing via Unauthenticated `shop-domain` Header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value taken from an HTTP header that is never covered by that HMAC. This breaks the identity binding `shop authenticated (HMAC) == shop acted upon (header value)`, letting an attacker who possesses one valid `(raw_body, hmac)` pair (e.g., from their own installed/dev shop) relabel it as coming from any other shop merely by changing the header, and have the app's webhook handler process it under the victim shop's tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic binding to the signed payload: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the HMAC — it never touches the `shop` header: [3](#0-2) 

`Registry.process` validates HMAC and then immediately trusts `request.shop` as the tenant identity passed to the app's handler: [4](#0-3) 

Because the shared secret (`Context.api_secret_key`) used to compute the HMAC is the *app's* `client_secret`, not something shop-specific, any shop that has installed the app can obtain from Shopify a fully valid `(raw_body, hmac)` pair for a webhook Shopify sends to *that* shop's endpoint. Since the header carrying the `shop` value is completely outside the signed material, an attacker in control of an installed shop can replay that same `raw_body`/`hmac` pair to the shared webhook endpoint while substituting the `x-shopify-shop-domain` header for any other shop that uses the same app. `Registry.process` will pass HMAC validation (the body/HMAC pair is genuinely signed) and dispatch the handler with `shop: <victim-shop>` and the attacker-controlled body, exactly matching the identity-binding break class named in the rules: "a field acted on but not covered by the HMAC."

The documentation instructs integrators to trust this exact flow without any additional per-shop verification: `ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" and then calling the handler with `data.shop` as the trusted tenant identifier, with no guidance to cross-check `shop` against anything else. [5](#0-4) [6](#0-5) 

### Impact Explanation
This yields cross-tenant access: the app's own gem-level "authenticity" check (`Registry.process`) certifies a webhook body as legitimate and attaches an attacker-chosen shop identity to it, which the host app is told is safe to act on (per the documented contract). Any downstream logic keyed off `data.shop` (persisting shop-scoped data, triggering shop-scoped side effects, etc.) can be poisoned to operate against a victim tenant using data that only proves authenticity of the *body*, not of the *shop* it's attributed to. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only an unprivileged internet user who can install the target app on any shop (including their own free/dev store) to receive one legitimately signed webhook, then replay it to the shared webhook endpoint with a modified `shop-domain` header — no access token, `api_secret_key`, or privileged account is needed. The webhook endpoint is a public HTTP endpoint by design. The only variable is whether the specific webhook topic/body content is useful for an attack against another tenant, but the binding failure itself is deterministic and always reachable via `Registry.process` as documented.

### Recommendation
Bind the `shop` domain into the material verified by the HMAC (Shopify's own webhook signing does not include headers in the signature by protocol, so this must be enforced by the app/gem):
- Require the host application to independently confirm that the receiving shop for a given topic/webhook_id was actually registered by that specific shop's session (e.g., by tracking registered `webhook_id`s per shop and rejecting webhooks whose `shop` header doesn't match the shop that owns that `webhook_id`), or
- Document explicitly and prominently that `data.shop` must never be trusted as an authenticated value and must be independently verified against the app's session store before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a real shop under their control) and subscribes to a topic (e.g., `orders/create`).
2. Shopify sends a legitimate webhook to the app's shared endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, and some `raw_body`.
3. Attacker captures this `(raw_body, hmac)` pair and replays it to the same endpoint, only changing `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC computed with the shared `api_secret_key`, per `lib/shopify_api/utils/hmac_validator.rb:12-22` and `lib/shopify_api/webhooks/request.rb:35-38`.
5. `Registry.process` calls the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body, per `lib/shopify_api/webhooks/registry.rb:188-200`, causing the host application to act on victim-shop data/identity using attacker-supplied content.

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
