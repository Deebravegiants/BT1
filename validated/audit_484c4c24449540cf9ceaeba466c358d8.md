# ANALOG FOUND

### Title
Unsanitized `shop` parameter in `Oauth.begin_auth` allows forced-OAuth redirection to attacker-controlled host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the Shopify-authorization redirect URL directly from the caller-supplied `shop` string without ever validating that it is a trusted `*.myshopify.com` (or otherwise allow-listed) domain, unlike every other entry point in the same auth surface that accepts a raw shop string.

### Finding Description
`begin_auth` takes `shop:` and feeds it straight into `auth_base_uri(shop)`, which is interpolated into an `https://` URL used as the OAuth authorization endpoint: [1](#0-0) [2](#0-1) 

No call to `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` exists anywhere in `begin_auth` or `auth_base_uri`. Compare this to the two other places in the gem that accept a bare shop string and correctly bind it to the `TRUSTED_SHOPIFY_DOMAINS` allow-list before using it to build a URL that will carry the app's `client_id`/`client_secret`: [3](#0-2) 

`Utils::ShopValidator` exists specifically to prevent exactly this class of bug — binding an unauthenticated "shop" string to a network destination: [4](#0-3) 

The gem's own documentation instructs integrators to source `shop` for `begin_auth` straight from an inbound, unauthenticated request header, reinforcing that this is the gem's intended, in-scope entry point rather than host-application misuse: [5](#0-4) 

The identity binding that is broken is: **shop parameter used to construct the OAuth-authorize host == a value proven to be a real Shopify shop domain**. Before the request: the `shop` string is attacker-supplied and unauthenticated (no HMAC, no signature, no session binds it yet — the HMAC/state binding only occurs *after* the redirect, in `validate_auth_callback`). After the request: `begin_auth` has already emitted a 307 redirect (`auth_route`) pointing the victim's browser at `https://#{attacker_shop}/oauth/authorize?...client_id=...&redirect_uri=...&state=...`, and has minted and returned a `state` nonce cookie tied to that flow — all before any validation that `attacker_shop` is even a Shopify-controlled host. The downstream HMAC check in `validate_auth_callback` does protect the token-exchange step, but it cannot undo the fact that the app already committed the user's browser and a live CSRF `state` value to a flow initiated against a host the app never verified.

### Impact Explanation
This matches the "forced OAuth completion" High-impact category explicitly in scope: an unprivileged internet user (or a host app trivially reflecting a request header/param into `shop`, which is exactly the documented usage pattern of this gem) can force a victim's browser into an OAuth authorization flow against an arbitrary, attacker-chosen host while the app's own `client_id` and callback `redirect_uri` are exposed to that host in the query string, and a session-establishment cookie (`state`) is set in the victim's browser tied to that flow. This is precisely the class of host/identity-binding defect called out in the rules ("a shop authenticated versus the shop stored as a session key … a scope or expiry check that answers permissively") — here the "shop" is used to pick a destination host before it is authenticated at all, whereas sibling code paths (`ClientCredentials`, `TokenExchange.migrate_to_expiring_token`) correctly authenticate the shop string against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` first.

### Likelihood Explanation
High: `begin_auth` is the first-called, most heavily used entry point of the OAuth flow, and the gem's own usage documentation shows it fed directly from an inbound request header/param, so any app following the documented pattern is exposed by default with no host-app misuse required.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `begin_auth`, exactly as is already done in `TokenExchange.migrate_to_expiring_token` and `ClientCredentials.client_credentials`, and raise `Errors::InvalidShopError` for any non-trusted domain before constructing `auth_base_uri`.

### Proof of Concept
1. A host application implements the OAuth "login" step exactly as documented: `shop = request.headers["Shop"]; ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")`.
2. An attacker sends `Shop: attacker-controlled.example` (or links a victim to a page that triggers this) — no secret, token, or prior session is required.
3. `begin_auth` computes `auth_base_uri("attacker-controlled.example")` → `"https://attacker-controlled.example/admin"` with no validation, and returns a 307 redirect plus a fresh `state` cookie.
4. The victim's browser is redirected to `https://attacker-controlled.example/oauth/authorize?client_id=<real_client_id>&scope=...&redirect_uri=<real_app_callback>&state=<nonce>`, an attacker-controlled endpoint, before any check that this is a genuine Shopify domain — confirmed absent by inspection of `lib/shopify_api/auth/oauth.rb` lines 22-128, contrasted with the sanitize calls present in `lib/shopify_api/auth/token_exchange.rb` lines 97-104 and `ClientCredentials`.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end

  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
