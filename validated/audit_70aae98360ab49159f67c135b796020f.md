Found it: `Webhooks::Request#to_signable_string` returns the raw HTTP body used to compute the HMAC, but `Webhooks::Request#shop` and `#topic` are read directly from HTTP headers, which are never covered by the HMAC signature.

### Title
Webhook `shop-domain` and `topic` headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC of the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `VerifiableQuery` contract used by the HMAC validator signs only `to_signable_string`, which for `Webhooks::Request` is just `@raw_body` [2](#0-1) . However, `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers and are never included in the signed string [3](#0-2) . These unauthenticated header values are then passed directly to the merchant's webhook handler as trusted identity fields: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [4](#0-3) .

### Finding Description
This mirrors the report's bug class: a field (`spender_`/owner identity) is acted upon but not covered by the authorization check that is supposed to bind it. Here, the "identity binding" the gem is supposed to enforce is: `hmac_valid_for(body) == true` should imply `shop header == the shop that produced this body`. In reality the check only proves the body's HMAC validity; it says nothing about which shop the request claims to be from, since `shop` (and `topic`) live outside the signed bytes.

Concretely, if any two merchants installed on the same app share the identical raw JSON payload for a given webhook topic (which is common — many Shopify webhook payloads, e.g. `app/uninstalled`, `shop/redact`, or empty-body test topics, are byte-identical or attacker-predictable/replayable across shops since the signature is computed from `secret + body` with a single shared `client_secret` for the whole app across all its installed shops), an unprivileged party who can capture or replay one shop's legitimately-signed webhook body can resend it with a forged `X-Shopify-Shop-Domain` header for a different shop. `HmacValidator.validate` will pass because the HMAC only checks the body against the app's single `Context.api_secret_key` [5](#0-4)  — it has no shop-specific key and never inspects `shop-domain` — yet the handler receives an attacker-chosen `shop` value it will treat as authoritative for routing/state changes (e.g. deactivating the wrong tenant's session, or triggering shop-scoped business logic under a different shop's identity).

### Impact Explanation
This breaks the identity binding `verified_hmac(body) == request_belongs_to(shop_header)`. Because the gem hands the unauthenticated `shop` header to the app's handler as if it were verified, an attacker can achieve cross-tenant confusion: actions intended for one shop are attributed to another shop chosen entirely by the attacker via header manipulation, with no requirement to know the `client_secret` — only requires replaying/observing one previously valid signed body (e.g. from a webhook delivered to their own test/dev shop) and resending it with a different `shop-domain` header value.

### Likelihood Explanation
Likelihood is High: reaching the vulnerable code only requires POSTing to the app's public webhook endpoint with an HMAC that is valid for the body under the app's secret and an arbitrary `shop-domain`/`topic` header — no access token, no `client_secret`, and no privileged account are needed. An attacker who is themselves a merchant installing the app receives legitimately signed webhook bodies for their own shop and can trivially replay them with a different `shop-domain` value against the same public endpoint.

### Recommendation
Bind `shop`, `topic`, `api_version`, and `webhook_id` into the signed material, or otherwise cryptographically tie the header-derived shop to the verified payload, e.g. by including these header values in `to_signable_string` (matching how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`, `state`, etc. into its HMAC input [6](#0-5) ), so that a valid HMAC can only be produced for the exact combination of body and shop/topic that Shopify actually signed.

### Proof of Concept
```ruby
# Attacker records their own legitimately-delivered webhook (any topic with a fixed/known body,
# or any topic whose body they can predict/observe from their own shop's install).
raw_body = '{}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body)

# Attacker resends the same raw_body/hmac pair but swaps the shop-domain header
# to a victim shop of their choosing.
forged_headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) returns true because it only checks raw_body against app_secret;
# the handler receives shop: "victim-shop.myshopify.com" as if it were authenticated.

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
