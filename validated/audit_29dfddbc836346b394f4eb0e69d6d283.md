### Title
Webhook `shop` domain is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` header from the HMAC-signed material. `Registry.process` validates the HMAC over that signable string and, once it passes, unconditionally trusts `request.shop` (parsed straight from the unauthenticated header) as the tenant identity handed to the app's webhook handler. Any party who possesses one valid `(raw_body, hmac)` pair — trivially available to any merchant who owns a store subscribed to the app's webhooks — can resend that same body/HMAC to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header, and the app will process it as if it originated from that other shop.

### Finding Description
The equality the code should enforce is:
`shop bound inside the HMAC-signed payload == shop attributed to the event by the handler`

Instead the code implements:
`HMAC(raw_body, api_secret_key) == received_hmac` (shop absent) while separately trusting `headers["shopify-shop-domain"]` for `request.shop`. [1](#0-0) 

`to_signable_string` returns `@raw_body` only — the `shop`, `topic`, and other identity fields are never mixed into the signed string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which calls `request.to_signable_string`, i.e., body-only), then immediately builds `WebhookMetadata` using `request.shop`/`request.topic`, taken straight from the unauthenticated headers: [3](#0-2) 

`request.shop` and `request.topic` are simple header readers with no cryptographic binding: [4](#0-3) 

`HmacValidator.validate` uses `verifiable_query.to_signable_string`, so for `Request` objects it only ever authenticates the body: [5](#0-4) 

Because the app's `api_secret_key` is the same for every shop that installs the app, and the HMAC only covers the body, **any webhook body produces an identical valid HMAC value regardless of which shop it is "for."** A merchant who legitimately receives a webhook for their own shop can capture the `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `shop-domain` header set to a *different*, victim shop domain. `Registry.process` will pass HMAC validation (body/secret matched) and then hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop, even though it never came from Shopify for that shop.

### Impact Explanation
This breaks tenant isolation: the gem itself hands the host application a tenant identifier (`data.shop`) that is not authenticated, despite the API being documented and used specifically to determine "which shop" an event is for (see `docs/usage/webhooks.md`, which shows handlers keying storage/queuing off `data.shop`). An attacker with their own (or any) store subscribed to the app can force the app to process arbitrary webhook payloads under another merchant's shop identity — a cross-tenant data-integrity/confusion attack, matching the Critical "cross-tenant access" category, since it is the gem's own HMAC design (binding only body, not shop) that fails to provide the tenant-authentication guarantee its documented API implies.

### Likelihood Explanation
Moderate-to-high: no secrets are required beyond one's own legitimate webhook traffic (which every installing merchant naturally receives), no privileged access is needed, and the only tool required is the ability to POST an HTTP request with a spoofed header to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material for `Webhooks::Request`, or otherwise cryptographically bind the identity fields used by `Registry.process`/`WebhookMetadata` to the verified payload, so that the `shop` value trusted by handlers cannot be altered independently of the signed body.

### Proof of Concept
1. App merchant "shop-a.myshopify.com" installs the app and receives a legitimate webhook: `raw_body = "{...}"`, `X-Shopify-Hmac-Sha256 = H`, `X-Shopify-Shop-Domain = shop-a.myshopify.com`.
2. Attacker (the merchant of shop-a, or anyone who intercepted/observed this request) resends the exact same `raw_body` and `H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` from the (unauthenticated) header as `shop-victim.myshopify.com`.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(raw_body, api_secret_key)` — identical to `H` since only the body is signed — validation succeeds.
5. The registered handler receives `WebhookMetadata.new(shop: "shop-victim.myshopify.com", ...)` and processes the payload attributing it to the victim shop, even though Shopify never sent this event for that shop.

          received_signature = verifiable_query.hmac
