### Title
Stake distribution consistency assertion can panic on legitimate stake-account mutation between reward calculation and distribution - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
Partitioned epoch rewards in agave are computed in an early "calculation" phase and stored, then applied several blocks/partitions later during a separate "distribution" phase. In `Bank::build_updated_stake_reward`, when the `relax_post_exec_min_balance_check` feature (`adjust_delegations_for_rent`) is not active, the code hard-asserts that the delegation stake loaded from the live `StakesCache` at distribution time, plus the previously-computed inflation reward, exactly equals the pre-computed expected new delegation from the calculation phase: [1](#0-0) 

This is structurally the same class of bug described in the 1inch report: a downstream accounting step relies on a strict/frozen quantity computed earlier ("distributed amount") while the underlying tracked value (the live stake account/delegation) can float due to state that is not controlled by the rewards module itself.

### Finding Description
The reward pipeline separates calculation from distribution across a multi-block window: [2](#0-1) 

During distribution, `store_stake_accounts_in_partition` re-reads the *current* `StakesCache` for each stake account and calls `build_updated_stake_reward` with the account's *current* delegation `stake`, plus the delegation/reward values snapshotted during calculation (`partitioned_stake_reward.inflation`): [3](#0-2) 

Inside `build_updated_stake_reward`, when `adjust_delegations_for_rent` is `false`, the function does not tolerate any divergence between the current on-chain delegation and the value assumed at calculation time — it panics via `assert_eq!` instead of gracefully reconciling: [1](#0-0) 

The code comment at `store_stake_accounts_in_partition` explicitly acknowledges the underlying assumption is fragile: "Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned" [4](#0-3) . This is the same failure mode 1inch flagged: the reward math implicitly assumes the tracked balance/quantity is immutable between "recording" and "payout," but the actual value is free to change from other legitimate paths (there, rebasing; here, any stake-account mutation — e.g. `Split`, `Merge`, `Withdraw`, `Deactivate`, `Redelegate` — issued by the ordinary, unprivileged stake/withdraw authority) before distribution completes.

I could not conclusively verify from the available code index whether the stake program itself blocks these instructions while `EpochRewardStatus` is `Active`; the comment claims such a restriction exists ("further state mutation prevents by stake-program restrictions"), but I was unable to locate the actual enforcement code (e.g., a check against `epoch_reward_status` or similar in the stake program instruction handlers) in the indexed content. This is the key open question determining exploitability: if the restriction is real and complete, this is only a latent defensive-assertion risk (i.e. a correctness invariant guarded by an assert with no legitimate way to violate it); if the restriction is missing, incomplete, or bypassable (e.g., via account closure/`Withdraw`, `Merge` combined with the deactivated no-vote-account carve-out path already visible in `redeem_delegation_rewards`, or via the feature-flag-gated `adjust_delegations_for_rent` being false on some cluster configuration/testnet), a normal user could deterministically trigger the `assert_eq!` panic on every validator processing that distribution partition.

### Impact Explanation
If reachable, this is a bank-commit-path panic reached deterministically by all validators executing the same slot (since `distribute_partitioned_epoch_rewards`/`store_stake_accounts_in_partition` run identically for every node), which would cause a coordinated crash across the cluster — a liveness/availability impact matching a consensus halt, not merely a single-node crash. This is far more severe than the analogous 1inch bug (silent reward-accounting drift): here the failure mode is fail-stop across the fleet rather than value miscalculation.

### Likelihood Explanation
Likelihood is uncertain and hinges on the unverified stake-program-level restriction mentioned in the comment, and on whether `adjust_delegations_for_rent` (`relax_post_exec_min_balance_check`) is unconditionally active on all live clusters. If the restriction is enforced and the feature is always active, this path is unreachable by an unprivileged user in current mainnet conditions, and the `assert_eq!` is only a defense-in-depth invariant. Given the explicit code comment flags this exact assumption as important and fragile, and that reward distribution windows can span up to 10% of an epoch's slots (`MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH`) [5](#0-4) , giving a real window for a stake-authority-controlled account mutation, this is worth a focused review of the stake program's instruction handlers to confirm whether mutation is truly blocked during that window and whether `adjust_delegations_for_rent` is unconditionally active.

### Recommendation
- Verify whether stake-program instruction processing checks `Bank::epoch_reward_status`/`EpochRewardPhase` (or an equivalent guard) before permitting `Split`, `Merge`, `Withdraw`, `Deactivate`, or `Redelegate` on a stake account that has a pending, uncredited partitioned reward. Confirm this guard is unconditional and covers every path that can change `Stake.delegation.stake` outside of the rewards module.
- Independently confirm `relax_post_exec_min_balance_check` is permanently active (fully activated feature, not merely a feature-set default) on all supported clusters; if not, the `assert_eq!` branch is live.
- Regardless, replace the `assert_eq!` panic in `build_updated_stake_reward`'s non-adjusted branch with a recoverable error path (as already exists for `AccountNotFound`/`ArithmeticOverflow`/`UnableToSetState`) so that any unexpected divergence degrades to a burned/logged reward rather than crashing bank processing — consistent with how the other `DistributionError` variants are already handled in `store_stake_accounts_in_partition`.

### Proof of Concept
Not independently reproducible from the indexed code alone: reproducing this requires confirming (1) that a stake-authority-controlled instruction can mutate `Stake.delegation.stake` for an account with a pending, calculated-but-undistributed partitioned reward, and (2) that `adjust_delegations_for_rent` is `false` at that time. The existing test `test_delegation_adjustment_at_distribution` in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` demonstrates the general scenario of "lamports transferred into a stake account before distribution time" being tolerated only because `adjust_delegations_for_rent` is exercised in that test; the same setup with that flag forced false and a delegation-stake-modifying operation (rather than a lamport-only transfer) would drive the `assert_eq!` panic in `build_updated_stake_reward` [6](#0-5) .

    fn test_delegation_adjustment_at_distribution() {
        let (mut genesis_config, _mint_keypair) =
            create_genesis_config(1_000_000 * LAMPORTS_PER_SOL);
        genesis_config.epoch_schedule = EpochSchedule::custom(432000, 432000, false);
        let bank = Bank::new_for_tests(&genesis_config);

        // Set up epoch_rewards sysvar with rewards with 10e9 lamports to distribute.
        let total_rewards = 10 * LAMPORTS_PER_SOL;
        let block_rewards = 0;
        let num_partitions = 2; // num_partitions is arbitrary and unimportant for this test
        let total_points = (total_rewards * 42) as u128; // total_points is arbitrary for the purposes of this test
        bank.create_epoch_rewards_sysvar(
            0,
            42,
            num_partitions,
            &PointValue {
                rewards: total_rewards,
                points: total_points,
            },
            block_rewards,
        );
        let pre_epoch_rewards_account = bank.get_account(&sysvar::epoch_rewards::id()).unwrap();
        let expected_balance =
            bank.get_minimum_balance_for_rent_exemption(pre_epoch_rewards_account.data().len());
        // Expected balance is the sysvar rent-exempt balance
        assert_eq!(pre_epoch_rewards_account.lamports(), expected_balance);

        // Use lower lamports per byte for creating, bank has higher amount
        let mut lower_rent = bank.rent_collector.rent.clone();
        lower_rent.lamports_per_byte /= 10;

        // Below new minimum, small reward, should normally be destaked
        let reward_lamports = 1;
        let reward = PartitionedStakeReward::new_with_lamport_amounts(reward_lamports, 0, 1);
        let rewards_to_distribute = reward.inflation.stake_reward;
        let stake_pubkey = reward.stake_pubkey;
        let stake_rewards = [reward];
        populate_starting_stake_accounts_from_stake_rewards(&bank, &lower_rent, &stake_rewards);
        let mut stake_account = bank.get_account(&stake_pubkey).unwrap();

        let expected_num = 1;

        let partitioned_rewards = StartBlockHeightAndPartitionedRewards {
            distribution_starting_block_height: bank.block_height() + REWARD_CALCULATION_NUM_BLOCKS,
            all_stake_rewards: Arc::new(stake_rewards.into_iter().collect()),
            partition_indices: vec![(0..expected_num).collect::<Vec<_>>()],
        };

        // But we transfer in more lamports before distribution time
        stake_account.checked_add_lamports(1_000_000_000).unwrap();
        bank.store_account(&stake_pubkey, &stake_account);

        // Distribute rewards
        let pre_cap = bank.capitalization();
        bank.distribute_epoch_rewards_in_partition(&partitioned_rewards, 0);
        let post_cap = bank.capitalization();
        let post_epoch_rewards_account = bank.get_account(&sysvar::epoch_rewards::id()).unwrap();

        // Assert that epoch rewards sysvar lamports balance does not change
        assert_eq!(post_epoch_rewards_account.lamports(), expected_balance);

        let epoch_rewards: sysvar::epoch_rewards::EpochRewards =
            from_account(&post_epoch_rewards_account).unwrap();
        assert_eq!(epoch_rewards.total_rewards, total_rewards);
        assert_eq!(epoch_rewards.distributed_rewards, rewards_to_distribute,);

        // Assert that the bank total capital changed by the amount of rewards
        // distributed
        assert_eq!(pre_cap + rewards_to_distribute, post_cap);

        // Check that delegation just gets rewards
        let post_account = bank.get_account(&stake_pubkey).unwrap();
        let post_stake_state: StakeStateV2 = post_account.state().unwrap();
        let pre_stake_state: StakeStateV2 = stake_account.state().unwrap();
        assert_eq!(
            post_stake_state.delegation().unwrap().stake,
            pre_stake_state.delegation().unwrap().stake + reward_lamports
        );
    }
