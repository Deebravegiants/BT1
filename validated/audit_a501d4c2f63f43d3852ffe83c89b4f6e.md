Based on my investigation, I found a concrete identity-binding break in the webhook verification path.

### Title
Webhook shop-domain identity is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `api_version`, `webhook_id`) values purely from HTTP headers, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies only covers the raw request body. Any unprivileged app-installer can capture a genuinely-signed webhook from their own shop and replay it against the app's webhook endpoint with a forged `x-shopify-shop-domain` header, causing the host application to process the payload under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from an unauthenticated header: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` verifies only that HMAC, and then forwards `request.shop` — the unauthenticated header value — directly into the metadata passed to the app's handler as the trusted tenant identifier: [4](#0-3) 

This breaks the intended identity binding: `hmac == HMAC(secret, body)` is verified, but the code implicitly treats this as also proving `shop == authenticated_shop`. Since the `shop-domain` header is not part of the signed content, the two are not actually bound together. An attacker who legitimately installs the app on their own store (any unprivileged internet user can install a public Shopify app) receives real, validly-HMAC-signed webhook deliveries. They can then resend that exact body (with its still-valid HMAC, since the shared secret and body are unchanged) to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with any victim shop domain of their choosing. `HmacValidator.validate` still returns `true` because the body/HMAC pair is untouched, and `Registry.process` will hand the handler `shop: "<victim-shop>.myshopify.com"` alongside the attacker-controlled body content.

### Impact Explanation
This is a cross-tenant identity confusion: the gem asserts an authenticity guarantee ("this payload was verified as coming from `shop`") that it does not actually provide, because `shop` is outside the signed envelope. Any host application that uses `WebhookMetadata#shop` (as documented/intended, e.g., to select tenant DB records, scope multi-tenant storage, or key idempotency/audit logs) can be made to attribute attacker-supplied body content to an arbitrary victim shop. This matches the Critical "cross-tenant access" impact bucket described in scope, since it lets one merchant's traffic inject or overwrite data associated with a different, unrelated merchant's tenant scope purely through this gem's own trust decision.

### Likelihood Explanation
Exploitation requires no privileged credentials, tokens, or secrets — only the ability to install the target public app on one's own store (an ordinary, unprivileged action any merchant can take) and the ability to POST an HTTP request with attacker-chosen headers to the app's public webhook URL, which is not secret. The HMAC check, being body-only, offers no protection against this header substitution, making this a straightforward, reliably-reproducible replay.

### Recommendation
Bind the shop identity into the signed material, or independently authenticate it: e.g., require the app to correlate `shop-domain` against a shop that is known to have an active webhook subscription/session, or (preferably) have the gem reject requests unless the caller supplies the expected shop out-of-band and cross-checks it, rather than exposing an unauthenticated `shop` accessor from `Webhooks::Request` as if it were verified. At minimum, the gem's documentation and `Registry.process` should not imply that a passing `HmacValidator.validate(request)` check authenticates `request.shop`.

### Proof of Concept
1. Install the target Shopify app on an attacker-owned store `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) — Shopify delivers a POST with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = Base64(HMAC-SHA256(client_secret, B))`.
2. Capture that raw request (`B`, headers).
3. Replay the exact same `B` and `H` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` instead of `attacker.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, B) == H`, per [5](#0-4) .
5. `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body `B`, per [6](#0-5) , despite the payload never having been produced by or for `victim-shop`.
