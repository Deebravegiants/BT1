### Title
Precision loss / permanent fund loss in `pallet-hyper-fungible-token` when converting ERC20 amounts to lower-decimal local balances - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`convert_to_balance` in the `hyper-fungible-token` pallet floors ERC20-denominated amounts when scaling down to a lower-decimal local asset. Since the EVM-side `HyperFungibleToken.send()` lets a caller burn an arbitrary raw `uint256 amount` with no minimum/alignment check, a sender can burn tokens on the EVM chain whose value is fully consumed while the substrate side credits less (or exactly zero) to the beneficiary, permanently losing the difference.

### Finding Description
Cross-chain amounts are carried in the message as raw ERC20-decimal integers (`Message.amount`). On the receiving substrate side, `on_accept` (and `on_timeout`) convert this value to the local asset's balance with: [1](#0-0) 

which computes `value / 10^(erc_decimals - local_decimals)` — an integer floor division. This is invoked directly on the attacker/user-supplied `message.amount` in the receive path: [2](#0-1) 

The design assumes `erc_decimals >= local_decimals` (documented for BRIDGE: EVM side is 18 decimals, nexus native is 12 decimals, scaled by `10^6`): [3](#0-2) 

On the *outgoing* substrate leg (`send`), the local balance is always converted to the ERC20 amount by exact multiplication (`convert_to_erc20`), so amounts leaving nexus are always exact multiples of `10^6` and round-trip losslessly: [4](#0-3) 

However, the EVM-side entry point that originates the reverse direction, `HyperFungibleToken.send()`, takes an arbitrary `uint256 amount` from the caller with no requirement that it be a multiple of the decimal-scaling factor: [5](#0-4) 

Consequently a user can burn e.g. `500000` wei of the 18-decimal BRIDGE token on an EVM chain (a real, non-zero, burned amount) and dispatch a message with that raw value. When nexus processes `on_accept`, `convert_to_balance(500000, 18, 12)` computes `500000 / 10^6 = 0`, so `Pallet::pallet_account()` releases `0` to the beneficiary. The tokens are irrevocably burned on the source chain while nothing is credited on the destination chain, and no refund path exists for a *successfully delivered* message (refunds only occur `on_timeout`, and even then the same floor-division re-applies to the message's already-fixed ERC20 amount, so any dust below the scaling factor is unrecoverable there too): [6](#0-5) 

This is a direct analog to the reported bug class: downscaling collateral/token amounts by decimal difference truncates the low-order digits, and here the truncated amount is not merely "lost precision" in accounting — it is real value burned on one chain that is never minted/released on the other, and the discrepancy is not tracked or reconciled anywhere in the pallet.

### Impact Explanation
Any unprivileged user calling `send()` on a `HyperFungibleToken`/`BridgeToken` deployment whose local (substrate) asset has fewer decimals than the EVM token can lose up to `10^(erc_decimals - local_decimals) - 1` units of value per transfer, and for amounts smaller than the scaling factor, 100% of the sent amount is destroyed with zero received. This is a direct, permanent loss of user funds reachable from a single unprivileged transaction (a bridge `send`), matching the "permanent freezing/loss of funds" impact bar.

### Likelihood Explanation
High likelihood: no special conditions are required beyond calling the public `send()` function with an amount that is not an exact multiple of the decimal-scaling factor (e.g., any amount ending in non-zero digits below `10^6` for the documented BRIDGE token). This can happen accidentally (a user manually entering an amount, or a dApp computing a non-round amount) or be triggered deliberately to demonstrate/exploit the loss.

### Recommendation
- Enforce, in `HyperFungibleToken.send()` (EVM side), that `amount % (10 ** (localDecimals scaling factor))` for the destination chain is zero, or round to the nearest valid unit and refund/reject the dust before burning.
- Alternatively, on the substrate side, use `convert_to_balance` with `mulmod`/remainder tracking, and either revert the whole `on_accept` when the remainder is nonzero and no rounding policy is defined, or maintain a per-chain dust-escrow accounting so truncated remainders are provably still backed and eventually reconciled instead of silently disappearing.
- Ensure any conversion between differing-decimal representations either rejects non-representable amounts pre-burn or guarantees an exact round-trip, consistent with the recommendation in the original report (never allow silent precision loss across a burn/mint or lock/release boundary).

### Proof of Concept
1. Deploy/assume `BridgeToken` on an EVM chain (18 decimals) paired with nexus's native BRIDGE asset (12 decimals), as configured via `register_token`/`Precisions` (`erc_decimals = 18`, `local_decimals = 12`).
2. A user with `500000` wei of BRIDGE (i.e. `0.0000000000005` BRIDGE, less than `10^6`) calls `send()` on the EVM `BridgeToken` contract with `amount = 500000`, targeting a nexus recipient.
3. The EVM contract burns the full `500000` wei from the user's balance and dispatches an ISMP `PostRequest` carrying `Message.amount = 500000`. [7](#0-6) 
4. On nexus, `on_accept` computes `convert_to_balance(500000, 18, 12) = 500000 / 10^6 = 0` and transfers `0` from the pallet's escrow account to the beneficiary. [8](#0-7) 
5. Result: the user's `500000` wei were burned on the EVM chain, the beneficiary on nexus receives nothing, and there is no timeout/refund mechanism for a message that was successfully delivered — the value is permanently lost.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
