### Title
Stale `PendingSwap` entry survives `deregister`, letting a re-registered `ParaId`'s new manager complete an unconsented swap - (File: polkadot/runtime/common/src/paras_registrar/mod.rs)

### Summary
`Pallet::swap` stores a one-sided pending swap request as `PendingSwap::<T>::insert(id, other)`, keyed by the initiator's para. `Pallet::do_deregister` only clears `PendingSwap::<T>::remove(id)` for the para being deregistered itself, never scanning for or clearing entries where that para is the *target* value of someone else's pending swap. This lets a new, unrelated manager who later re-registers the deregistered `ParaId` complete the stale swap and seize the original initiator's on-chain parachain data/deposit mapping without the initiator's consent to swap with the new entity.

### Finding Description
- `swap(origin, id, other)` at [1](#0-0)  checks `ensure_root_para_or_owner(origin, id)` (an unprivileged manager of `id` can call this), then if there is no reciprocal pending swap it just does `PendingSwap::<T>::insert(id, other)`.
- The confirming call happens when the owner of `other` calls `swap(other, id)`: the code checks `PendingSwap::<T>::get(other) == Some(id)`... actually the reciprocal check is `PendingSwap::<T>::get(other) == Some(id)` from the second caller's perspective, matching the first caller's stored `(id -> other)` mapping. This check is purely storage-based; it does not verify that the manager who confirms the swap is the same "logical" para that was intended when the first request was created (i.e., it does not bind the request to a manager identity or a session/generation counter).
- `do_deregister(id)` at [2](#0-1)  only removes `PendingSwap::<T>::remove(id)` — the entry keyed by the para being deregistered. It does **not** remove or invalidate any other entry `PendingSwap[x] = id` where `id` is referenced as the *target* of someone else's pending swap.
- Exploit flow:
  1. Manager A owns `ParaId` `A_id` (Parachain), Manager B owns `ParaId` `B_id` (Parathread/Parachain).
  2. A calls `swap(A_id, B_id)` → `PendingSwap[A_id] = B_id` is stored.
  3. Before B confirms, B calls `deregister(B_id)` (valid since B is `ParaId`'s owner and it's a Parathread) → `do_deregister` removes `PendingSwap[B_id]` (which doesn't exist) and unreserves B's deposit, but leaves `PendingSwap[A_id] = B_id` untouched.
  4. A new, unrelated user C reserves and registers the same numeric `ParaId` `B_id` (`reserve` + `register`), becoming its new manager, all in the same session, since `NextFreeParaId` only affects *new* reservations, not blocking reuse of a previously deregistered specific ID via direct `reserve`... Actually `reserve()` uses `NextFreeParaId` sequentially so C would need to reserve exactly `B_id`; but `force_register`/direct `register`+`reserve` model reserves the *next* free id, not an arbitrary one — reuse of the exact same numeric ID would require it to still be `NextFreeParaId`'s next slot or the ID must not be `contains_key`. Since `do_deregister` calls `Paras::<T>::take(&id)`, the entry is removed and `paras::Pallet::<T>::lifecycle(id)` becomes `None` after cleanup completes (note: `schedule_para_cleanup` may cause the actual lifecycle removal to complete only after the *next* session boundary, so `id` may still show a lifecycle for a session before it can be re-reserved via `do_reserve`, which explicitly checks `paras::Pallet::<T>::lifecycle(id).is_none()`).
  5. Once `B_id` is re-registered by C and reaches `Parathread`/`Parachain` lifecycle, C (or anyone controlling `B_id`) calls `swap(B_id, A_id)`. This passes `ensure_root_para_or_owner(origin, B_id)` (C is the new manager), passes the lifecycle check for `B_id`, and then `PendingSwap::<T>::get(A_id) == Some(B_id)` — the stale entry from step 2 — is `true`, since it was never invalidated.
  6. The swap executes: depending on lifecycles either `T::OnSwap::on_swap(A_id, B_id)` or `do_thread_and_chain_swap` runs, transferring/exchanging deposit and scheduling metadata between A's para and C's newly registered para, even though A never intended to swap with C's new registration.
- No check exists tying the pending swap to a "generation" of the para or its manager identity; the check is purely `ParaId`-keyed and survives a full deregister/re-register cycle of the counterparty ID.

### Impact Explanation
An unprivileged attacker (the new manager of a re-registered `ParaId`) can force-complete a swap that the original initiator (A) never agreed to with the attacker's newly registered para, causing `T::OnSwap::on_swap`/`do_thread_and_chain_swap` to run against a `ParaId` whose associated on-chain manager/deposit lineage has changed. This can result in an unintended swap of parachain/parathread lifecycle status and any registrar-tracked deposit/leases data (via `OnSwap` implementers such as slots/crowdloan) between A and an unrelated new manager C, which A did not consent to transact with — a form of unauthorized state change/resource seizure on the scoped registrar/OnSwap data.

### Likelihood Explanation
Requires two independently-owned `ParaId`s, one of the parties (the "other" side) to deregister and successfully re-register the exact same `ParaId` within the same session window (before the reciprocal swap call fires), and for `do_reserve`'s `lifecycle(id).is_none()` gate to pass, which depends on cleanup timing (`schedule_para_cleanup`) relative to session rotation. This makes exact `ParaId` reuse timing-sensitive but not impossible for a determined attacker who can also act as the confirming caller in a race within a single session, since all of `deregister`, `reserve`, `register`, and `swap` are ordinary signed extrinsics reachable by any user owning/reserving IDs.

### Recommendation
When `do_deregister(id)` (or lifecycle transition cleanup) runs, also clear any `PendingSwap` entries where `id` appears as the *value* (not only as the key), e.g. by iterating/removing reverse references, or better, redesign `PendingSwap` to store a generation/manager-bound token (e.g., `(ParaId, AccountId, session_or_nonce)`) that is invalidated whenever the counterparty’s registration record changes (deregister, re-register, or manager change), so a stale pending swap can never be confirmed against a different registration epoch of the same `ParaId`.

### Proof of Concept
Rust integration test (extending `parachain_swap_works` in `polkadot/runtime/common/src/integration_tests.rs`):
1. Register `para_1` (Parachain, manager = Alice) and `para_2` (Parathread, manager = Bob).
2. Alice calls `Registrar::swap(para_1, para_2)` → assert `PendingSwap::<Test>::get(para_1) == Some(para_2)`.
3. Bob calls `Registrar::deregister(para_2)` → assert `Paras::<Test>::get(para_2).is_none()` and assert (bug) `PendingSwap::<Test>::get(para_1) == Some(para_2)` still `Some`.
4. Advance session(s) until `paras::Pallet::<Test>::lifecycle(para_2).is_none()`.
5. Carol calls `reserve()` then `register(para_2, ...)` to become the new manager of `para_2`.
6. Carol calls `swap(para_2, para_1)`.
7. Assert failure expected (`Error::NotRegistered`/`CannotSwap`) but actual current behavior: the call succeeds and `Swapped` event fires, `T::OnSwap::on_swap`/lifecycle swap executes between `para_1` (Alice) and `para_2` (Carol) — demonstrating the invariant "swap must only execute between the same manager-owned paras that initiated it" is violated.

		pub fn swap(origin: OriginFor<T>, id: ParaId, other: ParaId) -> DispatchResult {
			Self::ensure_root_para_or_owner(origin, id)?;

			// If `id` and `other` is the same id, we treat this as a "clear" function, and exit
			// early, since swapping the same id would otherwise be a noop.
			if id == other {
				PendingSwap::<T>::remove(id);
				return Ok(());
			}

			// Sanity check that `id` is even a para.
			let id_lifecycle =
				paras::Pallet::<T>::lifecycle(id).ok_or(Error::<T>::NotRegistered)?;

			if PendingSwap::<T>::get(other) == Some(id) {
				let other_lifecycle =
					paras::Pallet::<T>::lifecycle(other).ok_or(Error::<T>::NotRegistered)?;
				// identify which is a lease holding parachain and which is a parathread (on-demand
				// parachain)
				if id_lifecycle == ParaLifecycle::Parachain &&
					other_lifecycle == ParaLifecycle::Parathread
				{
					Self::do_thread_and_chain_swap(id, other);
				} else if id_lifecycle == ParaLifecycle::Parathread &&
					other_lifecycle == ParaLifecycle::Parachain
				{
					Self::do_thread_and_chain_swap(other, id);
				} else if id_lifecycle == ParaLifecycle::Parachain &&
					other_lifecycle == ParaLifecycle::Parachain
				{
					// If both chains are currently parachains, there is nothing funny we
					// need to do for their lifecycle management, just swap the underlying
					// data.
					T::OnSwap::on_swap(id, other);
				} else {
					return Err(Error::<T>::CannotSwap.into());
				}
				Self::deposit_event(Event::<T>::Swapped { para_id: id, other_id: other });
				PendingSwap::<T>::remove(other);
			} else {
				PendingSwap::<T>::insert(id, other);
			}

	fn do_deregister(id: ParaId) -> DispatchResult {
		match paras::Pallet::<T>::lifecycle(id) {
			// Para must be a parathread (on-demand parachain), or not exist at all.
			Some(ParaLifecycle::Parathread) | None => {},
			_ => return Err(Error::<T>::NotParathread.into()),
		}
		polkadot_runtime_parachains::schedule_para_cleanup::<T>(id)
			.map_err(|_| Error::<T>::CannotDeregister)?;

		if let Some(info) = Paras::<T>::take(&id) {
			<T as Config>::Currency::unreserve(&info.manager, info.deposit);
		}

		PendingSwap::<T>::remove(id);
		Self::deposit_event(Event::<T>::Deregistered { para_id: id });
		Ok(())
	}
