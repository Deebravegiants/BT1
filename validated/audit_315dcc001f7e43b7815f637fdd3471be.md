### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values that `Registry.process` uses to authorize and dispatch the webhook are read straight from HTTP headers that are excluded from that signature. An attacker who can obtain one validly-signed `(body, hmac)` pair (e.g. by installing the app on a shop they control) can replay it with forged `x-shopify-shop-domain` / `x-shopify-topic` headers, and the gem will still report the HMAC as valid while attributing the (unrelated) body to an arbitrary shop and topic.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` — all of which drive trust decisions downstream — are parsed directly from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC over the `Request` object and then, having only checked the body's signature, dispatches based on the unsigned `topic` and forwards the unsigned `shop` straight into the handler payload: [3](#0-2) 

`Utils::HmacValidator.validate` simply recomputes the HMAC over `to_signable_string` and compares against the `hmac` accessor — it has no way to know that `shop`/`topic` exist at all, since they're not part of the signed string: [4](#0-3) 

This breaks the intended identity binding: `shop signed by HMAC == shop trusted for handler dispatch` never holds, because the left-hand side is always empty (no shop is signed) while the right-hand side is attacker-controlled header content. This is the same class of bug as the reported `St1inch._deposit` issue — a value (`duration`/here `shop`+`topic`) is *acted upon* by privileged logic without being *covered* by the integrity check (`amount>0` guard/here the HMAC digest) that governs the rest of the operation.

### Impact Explanation
An attacker who can trigger even one legitimately-signed webhook for a shop they control (for example, installing the target app on their own development store and generating any webhook event) can capture that valid `(raw_body, hmac)` pair. They can then replay it against the app's webhook endpoint with `x-shopify-shop-domain` set to an arbitrary victim shop and/or `x-shopify-topic` set to any registered topic (including mandatory GDPR topics like `customers/redact`, `shop/redact`, `customers/data_request`). Because the gem's HMAC check never inspects these headers, `Registry.process` will accept the forged request as authentic and invoke the handler with `WebhookMetadata.shop` set to the victim shop and/or route the body to a handler for a topic it was never actually signed for. This is a cross-tenant identity confusion allowing an attacker to make the app process fabricated data as if it originated from a shop they do not control, and to misroute signed payloads to unintended handler logic (e.g., turning ordinary order data into a "customer data erasure" trigger for another tenant).

### Likelihood Explanation
The precondition — obtaining one valid `(body, hmac)` sample — is trivial for any developer who can install the target app on a store, which is an ordinary unprivileged action available to any internet user with a Shopify development store. No access to `api_secret_key`, access tokens, or the victim's credentials is required, and the replay itself is a simple unauthenticated HTTP POST to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the value that is HMAC-verified, or otherwise cryptographically bind these header-derived identity fields to the signed body before they are used for dispatch/authorization in `Registry.process`. At minimum, the shop/topic used to route and label a webhook must not be trusted unless they are covered by the same signature that authenticates the payload.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers any webhook subscription (e.g. `orders/create`), capturing the legitimate request:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`
   - Body: `{"id": 123, ...}` (attacker-controlled content, since it's their own order)
2. Attacker replays the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: customers/redact` (or any other registered topic)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the raw body against the HMAC — see: [3](#0-2) 
4. The registered handler for the (forged) topic executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and attacker-supplied body content, despite the payload never having been signed for that shop or topic.
