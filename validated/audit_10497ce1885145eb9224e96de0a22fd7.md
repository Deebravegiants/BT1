### Title
Front-runnable `initialize()` on `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable` allows ownership hijack of a token-bridge app - (File: `sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol`)

### Summary
`HyperFungibleTokenUpgradeable.initialize` and `WrappedHyperFungibleTokenUpgradeable.initialize` are `public`/`virtual` functions guarded only by OpenZeppelin's `initializer` modifier, with no caller restriction (`onlyOwner`, `onlyProxy`, or a fresh-proxy version gate). This mirrors exactly the reported bug class: an `initialize` function that anyone can call to seize ownership, unlike the hardened pattern (`onlyFresh` + atomic `ERC1967Proxy` construction with init data) used elsewhere in this same repository for `IntentGatewayV2` and `SimplexPaymaster`.

### Finding Description
`HyperFungibleTokenUpgradeable` is meant to be deployed behind a proxy (raw implementation is locked via `_disableInitializers()` in its constructor), and its `initialize` sets `Ownable`'s owner: [1](#0-0) 

`__HyperFungibleToken_init` calls `__Ownable_init(initialOwner)`, and the owner then controls `configure`, `addChain`, `removeChain`, `pause`/`unpause`: [2](#0-1) [3](#0-2) 

The identical pattern exists in `WrappedHyperFungibleTokenUpgradeable`: [4](#0-3) 

Unlike `IntentGatewayV2` and `SimplexPaymaster`, which explicitly close this gap with an `onlyFresh` modifier that reverts unless `_getInitializedVersion() == 0` and are deployed atomically via `new ERC1967Proxy{salt}(implementation, initData)` in the same transaction as proxy creation: [5](#0-4) [6](#0-5) 

`HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable` carry no such `onlyFresh` guard, and no deployment script in this repo wires them up via atomic `ERC1967Proxy` construction with `initData` (only the non-upgradeable `HyperFungibleToken`/`WrappedHyperFungibleToken`, whose constructors take the owner directly, are used in `DeployHFT.s.sol`/`DeployWrappedHFT.s.sol`): [7](#0-6) 

Since these `Upgradeable` variants are shipped in the SDK as reusable templates for third-party integrators to deploy behind a proxy, any deployment flow that deploys the proxy and then calls `initialize` in a *separate* transaction (rather than passing `initData` atomically to the proxy constructor) leaves a window where anyone can front-run the intended deployer's `initialize` call and become the `Ownable` owner of the token-bridge contract.

### Impact Explanation
Whoever wins the `initialize` race becomes the `Ownable` owner and gains exclusive control of `configure` (sets `_host`/`_dispatcher`) and `addChain`/`removeChain` (sets which peer chain/address `onAccept` trusts as the source of incoming mint messages). Because `onAccept` mints tokens purely based on the registered `_supportedChains` peer and the message body, an attacker-controlled owner can point `_supportedChains` at an address they control and forge `onAccept` mint messages (subject to `onlyHost` gating, but the attacker also controls which host/peer is trusted via `configure`/`addChain`), leading to unbacked minting of the bridged token — a direct theft/inflation vector for a token-bridge mint/burn application, squarely in the accepted impact class ("unbacked mint", "unauthorized app action").

### Likelihood Explanation
Exploitability is fully conditioned on the deployment pattern used by whoever adopts these SDK templates: if a proxy is initialized atomically (init data passed to the proxy's own constructor, as done for `IntentGatewayV2`/`SimplexPaymaster` in this codebase), the race is impossible. The vulnerability only manifests if an integrator deploys the proxy and calls `initialize` in a separate transaction — a plausible but not certain deployment pattern for a template contract with no explicit deployment script or `onlyFresh` guard enforcing atomicity. No first-party deploy script in this repo currently exercises this vulnerable pattern for these specific contracts, so likelihood depends on downstream SDK consumers.

### Recommendation
Add the same protections already applied to `IntentGatewayV2`/`SimplexPaymaster` in this codebase: gate `initialize` with an `onlyFresh`-style check (`_getInitializedVersion() == 0`) is already implicit via `initializer`, but more importantly, document/enforce that these `Upgradeable` templates must only be deployed via an `ERC1967Proxy` (or equivalent) constructed with `initData` in the same transaction, exactly like `DeployIntentGateway.s.sol`/`DeploySimplexPaymaster.s.sol` do, so that no two-step deploy-then-initialize window can be front-run. Consider also making `initialize` require `msg.sender == <expected deployer>` or embedding the intended owner in the CREATE2 salt/init bytecode.

### Proof of Concept
1. Deployer deploys `HyperFungibleTokenUpgradeable` implementation and an `ERC1967Proxy` pointing to it **without** passing `initData` in the proxy constructor (i.e., a bare proxy, as is possible since nothing in the contract enforces atomic construction).
2. Deployer's `initialize(name, symbol, initialOwner)` transaction is broadcast to the mempool.
3. Attacker observes the pending transaction and submits their own `initialize(name, symbol, attacker)` call with higher gas, which lands first; `initializer` only prevents a *second* call, not front-running the *first*.
4. Attacker is now `Ownable` owner of the token-bridge contract and can call `configure`/`addChain` to register a malicious peer address, then trigger `onAccept` mints to arbitrary beneficiaries once the (attacker-controlled) `_host`/peer conditions are satisfied.

    /// @dev `initialize` is for a bare proxy only. A proxy that an upgrade left below `VERSION` is
    /// taken there by the host-only `migrate`; without this, anyone could `initialize` it.
    modifier onlyFresh() {
        if (_getInitializedVersion() != 0) revert InvalidInitialization();
        _;
    }

    /**
     * @dev One-time init of a bare proxy: registers the peers, each bound to `address(this)`,
     * stores the params, arms the relayer gate, and lands at `VERSION`. Refused on any proxy
     * already at a version, see `onlyFresh`.
     * @param p The initial gateway configuration parameters.
     * @param peerChains State-machine ids of the cross-chain peers to register, each bound to this
     * gateway's own address so no peer address is carried in the proxy's init data.
     * @param relayer The only relayer whose deliveries are accepted. Zero leaves the gate open.
     */
    function initialize(Params memory p, bytes[] memory peerChains, address relayer)
        public
        onlyFresh
        reinitializer(VERSION)
    {
        uint256 peersLength = peerChains.length;
        for (uint256 i = 0; i < peersLength; i++) {
            Deployment memory deployment = Deployment({chain: peerChains[i], gateway: address(this)});
            _addDeployment(deployment);
        }
        _validateParams(p);
        _params = p;
        _setRelayer(relayer);
    }
