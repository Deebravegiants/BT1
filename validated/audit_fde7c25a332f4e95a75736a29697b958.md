## Title
Webhook shop/topic attribution is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC signature only over the raw request body, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` values used to attribute the webhook to a specific tenant are taken directly from unauthenticated HTTP headers. This mirrors the audited bug class: a value that is *acted on* (here, the shop identity that downstream app code trusts to scope data updates) is not *covered* by the cryptographic check (the HMAC), breaking the intended binding between "HMAC-verified sender" and "shop the payload is attributed to."

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers, none of which participate in the HMAC computation: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., the body), and says nothing about the headers: [3](#0-2) 

`Registry.process` relies on this validation and then forwards the **unverified** `request.shop` value straight into the handler as the tenant identifier: [4](#0-3) 

The equality the code implicitly assumes is:
`shop bound by HMAC == shop delivered to the app handler`

But in reality:
`shop covered by HMAC == body only`
`shop delivered to handler == unauthenticated header value`

Any request whose body+HMAC pair is valid for the app's shared `api_secret_key` (the same secret is shared across all shops installed on that app) will pass `Utils::HmacValidator.validate`, regardless of what `shop-domain` header accompanies it. This is confirmed by the test suite, which builds the HMAC purely from the body and independently sets the shop header: [5](#0-4) 

### Impact Explanation
An app installed on multiple shops uses one shared `api_secret_key` (this is standard Shopify app architecture, not tied to a single tenant). A merchant who has the app installed on their own store legitimately receives a genuine webhook (body + valid HMAC) from Shopify. Because the `shop-domain` header is not part of the signed content, that merchant can replay the identical body/HMAC pair to the app's webhook endpoint while substituting a different `shop-domain` header value. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` object attributing the payload to the spoofed shop: [6](#0-5) 

If the host application (as documented/intended by this gem's API) uses `WebhookMetadata#shop` to look up and mutate per-tenant records, this results in cross-tenant data corruption/access — one merchant causing data changes attributed to another merchant's shop, without needing the `api_secret_key`, an access token, or any privileged account. This satisfies the "cross-tenant access" criterion under the Critical impact bucket, since the binding between "cryptographically-verified sender" and "which tenant this data belongs to" is broken.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must already be a legitimate (if unprivileged, relative to other tenants) user of the app — i.e., have the app installed on at least one shop so they can receive one authentic webhook body/HMAC pair to replay. No secret material, TLS interception, or social engineering is required; only observation of one's own legitimately-delivered webhook traffic and the ability to send an HTTP POST with modified headers to the app's public webhook endpoint.

### Recommendation
Include the identity-carrying headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) inside the HMAC-signable content, or otherwise cryptographically bind them to the verified body (e.g., derive the shop attribution only from a value cross-checked against the app's own per-shop session/token store rather than trusting the header verbatim). At minimum, document that `Webhooks::Request#shop`/`#topic` are unauthenticated and must be revalidated by the host application against known installed shops before being used for tenant-scoped operations.

### Proof of Concept
1. App shares one `api_secret_key` across all installed shops (standard multi-tenant SaaS model).
2. Attacker's own shop, `attacker.myshopify.com`, has the app installed and receives a real webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the exact same body `B` and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only (per `Request#to_signable_string`) and it matches — validation passes: [7](#0-6) 
5. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` even though the payload actually originated from/was crafted by the attacker's own shop, achieving cross-tenant attribution.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
