### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb, lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` header verbatim as the tenant identity handed to the host application's handler. Since the HMAC secret (`Context.api_secret_key`) is a single value shared across *all* shops that installed the app, and the signature does not cover the `shop-domain` header, any party who legitimately receives one valid `(body, hmac)` pair for their own shop can replay it against the app's webhook endpoint while swapping the `shop-domain` header to name a different shop — the HMAC still validates and the handler executes as if the data belongs to the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, excluding the `shop`, `topic`, `webhook_id`, and `api_version` headers from what is HMAC-signed: [1](#0-0) 

`Registry.process` verifies only that HMAC and then constructs `WebhookMetadata` using the unauthenticated `request.shop` value pulled straight from the attacker-controllable header: [2](#0-1) 

`HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, raw_body)` and compares it to the supplied signature — again, `shop` plays no role in the computation: [3](#0-2) 

The identity binding that should hold is: **the shop attributed to a webhook event == the shop whose install actually produced that signed payload**. Because `api_secret_key` is one value for the whole app (identical for every shop that installs it) and the shop is excluded from the signed content, that equality is not enforced. A user who controls one shop's webhook stream (e.g., by installing the app themselves) possesses valid `(raw_body, hmac)` pairs signed with the same secret used for every other shop. Replaying that exact body/HMAC pair to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop passes `Utils::HmacValidator.validate` (per its own logic and the docs at `docs/usage/webhooks.md`), and the host application's `WebhookHandler#handle` is invoked believing the data originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary between shops sharing one app installation — a core assumption of every downstream webhook consumer. Any host application that uses `data.shop` from `WebhookMetadata` to route or persist per-tenant data (as demonstrated in the gem's own documentation and tests) can be made to attribute a valid, replayed order/customer/shop event to the wrong merchant, resulting in cross-tenant data injection/corruption. This satisfies the "cross-tenant access" Critical-impact category since it lets an attacker (a merchant installing the app) inject events under another tenant's identity, bypassing the intended per-shop isolation enforced by the webhook signature.

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP endpoint by design (Shopify posts to it directly), so anyone able to record their own shop's webhook traffic (trivial for any merchant/tester who installs the app) can immediately attempt this replay against the same shared endpoint for other shops, requiring no secrets, tokens, or privileged access — only the ability to modify one HTTP header and resend a captured request.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the webhook payload to the shop it was issued for (e.g., verify the shop against Shopify's per-shop metadata via API lookup, or fold the shop header into `to_signable_string` if Shopify's signing scheme supports it) before trusting `request.shop` for tenant routing. At minimum, document that consumers must independently corroborate `data.shop` against a known/installed shop list before using it as a tenant key, since the library only guarantees the raw body's authenticity, not the header's.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = Base64(HMAC-SHA256(api_secret_key, B))`.
2. Attacker resends the exact same request to the app's public webhook callback URL, but changes the header `x-shopify-shop-domain` from `attacker-shop.myshopify.com` to `victim-shop.myshopify.com` (all other headers/body unchanged).
3. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` over `raw_body` only — this succeeds because `B` and `api_secret_key` are unchanged. [4](#0-3) 
4. The host app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes/attributes attacker-controlled order data as belonging to the victim shop.
