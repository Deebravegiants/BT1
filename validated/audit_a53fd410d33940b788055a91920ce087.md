### Title
Permanent DoS of `finalizeGraduation` via `Math.mulDiv` overflow in `_noFeeSwapInput` when a low-exchange-rate LT inflates `ltFromPair` - ([File: packages/contracts/src/Bonding.sol])

### Summary
An unprivileged attacker who pre-seeds the HyperSwap V2 `TOKEN/LT` pair with an ordinary (non-extreme) `mint` before phase-2 graduation can permanently brick `Bonding.finalizeGraduation` for a token whose curve raised LT in a depressed-exchange-rate regime, because `_noFeeSwapInput`'s `Math.mulDiv` call is not guarded against the resulting overflow.

### Finding Description
`Bonding._prepareGraduationLiquidity` caches `ltFromPair` at the last curve price with no upper bound other than `uint256`: [1](#0-0) 
`ltFromPair = assetReserve - virtualLtReserve`, where `assetReserve` (`Pair._pool.assetReserve`) is a plain `uint256`, unbounded by any `uint112`-style cap: [2](#0-1) 
Because the reserve asset is a legitimate, externally-priced BounceTech LT (`exchangeRate()`), a normal (non-buggy) drop in `exchangeRate` lets the same USD-threshold in `canGraduate` be crossed only after depositing a very large *quantity* of LT into the curve — `ltFromPair` can legitimately reach magnitudes far beyond `uint112`, as the code itself acknowledges when explaining why `PendingGraduation.ltFromPair` is kept as a full `uint256`.

`tokensForLP`, in contrast, is capped at `LP_RESERVE` (≈2.5e26): [3](#0-2) 

During phase 2, if an attacker has permissionlessly pre-created and `mint`-seeded the HyperSwap V2 pair (Regime 3 of `_seedUniswapV2Direct`), `_seedRebalancing` branches on the ratio between the pool's reserves and the (`ltFromPair`, `tokensForLP`) target: [4](#0-3) 
When `ltFromPair` is astronomically large relative to `tokensForLP`, essentially *any* ordinary pre-seed ratio (even a balanced one) satisfies `reserveToken * ltFromPair > reserveLT * tokensForLP`, routing execution into `_pairRebalance` with `targetN = ltFromPair`, `targetD = tokensForLP`: [5](#0-4) 
`_noFeeSwapInput` then computes: [6](#0-5) 
`reserveIn * reserveOut` is bounded by `(2^112)^2 ≈ 1.68e67` (V2 reserves are `uint112`), but `Math.mulDiv(that product, targetN, targetD)` must still fit the final quotient into 256 bits. With `targetN = ltFromPair` potentially ≫ `2^32 × targetD`, the true mathematical result of `product × ltFromPair / tokensForLP` exceeds `type(uint256).max`, and OpenZeppelin's `Math.mulDiv` reverts (`MathOverflowedMulDiv`) rather than silently truncating — this is exactly the class of "no bounds check on a crafted/attacker-influenced input causing a crash" that CVE-2025-55663 describes, translated to Solidity's revert-as-crash semantics.

That revert is never caught: `_pairRebalance` → `_seedRebalancing` → `_seedUniswapV2Direct` → `finalizeGraduation` have no `try/catch`, so every call to `finalizeGraduation(tokenAddress)` for this token reverts, forever — `tokensForLP`/`ltFromPair` are pinned in `pendingGraduation[tokenAddress]` at phase 1 and the pre-seeded pair's reserves are permanent on-chain state, so nothing about the failure self-heals.

### Impact Explanation
The token is permanently stuck in `Lifecycle.Graduating`: it can never sell, buy, or reach `Lifecycle.Graduated`. All curve-raised LT already moved into `Bonding` via `Router.graduate` in phase 1, plus up to `LP_RESERVE` (250M) tokens earmarked for the LP, are permanently frozen inside `Bonding` with no rescue path (`LPLock.recordLock` is never reached, and there is no owner-level unstick function for a poisoned `pendingGraduation` entry). This is a permanent freezing of curve-raised LT and launch tokens belonging to every trader who bought into that curve, triggerable by a single unprivileged attacker.

### Likelihood Explanation
Reaching the vulnerable branch requires only two permissionless actions: (1) buying enough LT into the curve while the paired LT's `exchangeRate()` is depressed (a normal market condition for a leveraged/rebasing asset, not a bug in the LT) so that `ltFromPair` becomes very large relative to `LP_RESERVE`, and (2) pre-creating the HyperSwap V2 pair and calling its ordinary `mint` with any non-trivial reserve ratio before `finalizeGraduation` runs — both are explicitly enumerated as in-scope attacker actions. No special timing, flash loans, or privileged role is needed; the attacker only needs to win the race to seed the pair ahead of the keeper's ~60s `finalizeGraduation` call, which the contract's own extensive brick-resistance commentary already flags as an inherently attacker-favorable window (`AGENTS.md` also notes the dedicated hostile-pre-seed test suite covering this exact class of scenario was removed after deployment and "is no longer enforced by automated tests").

### Recommendation
Bound the `Math.mulDiv` inputs in `_noFeeSwapInput` (or clamp `targetN`/`targetD` before the call) so an extreme `ltFromPair`/`tokensForLP` skew cannot produce a result exceeding `type(uint256).max`, and/or wrap the `_pairRebalance` call in `_seedRebalancing` with a guard that falls back to `_seedDirectMint` on any revert (mirroring the existing `s == 0` / `expectedOut == 0` fallback logic) so a pathological ratio degrades to the safe direct-mint path instead of permanently reverting `finalizeGraduation`.

### Proof of Concept
1. Launch a token paired with an LT; wait for (or induce, via normal market activity) the LT's `exchangeRate()` to drop significantly.
2. Buy LT into the curve until `canGraduate` trips the USD threshold — because the rate is low, this requires a very large *quantity* of LT, making `ltFromPair` (cached at phase 1 into `pendingGraduation[token]`) enormous relative to `LP_RESERVE`.
3. Before the keeper (or anyone) calls `finalizeGraduation`, call `IUniswapV2Factory.createPair(token, lt)` and `pair.mint(attacker)` with any ordinary token/LT amounts (no need for extreme values — since `ltFromPair ≫ tokensForLP`, almost any pre-seed ratio satisfies the "TOKEN-rich" branch).
4. Anyone calling `finalizeGraduation(token)` now reverts inside `_noFeeSwapInput`'s `Math.mulDiv(reserveIn * reserveOut, ltFromPair, tokensForLP)` because the true quotient exceeds `type(uint256).max`.
5. The token remains permanently in `Lifecycle.Graduating`; the LT drained by `Router.graduate` in phase 1 and the earmarked launch tokens remain stuck in `Bonding` indefinitely.

```text
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
```
