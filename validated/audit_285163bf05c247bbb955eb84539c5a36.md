### Title
Webhook HMAC only signs the request body, not the shop/topic headers, allowing cross‑tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC verification performed by `Utils::HmacValidator.validate` authenticates the *body bytes* but never the `shop`, `topic`, `webhook_id`, or `api_version` values that `Webhooks::Registry.process` subsequently trusts and hands to the app's handler. This is the same class of defect as the referenced report: a field that is *acted on* (here, the `shop` identity attributed to an incoming webhook) is not covered by the cryptographic binding that is supposed to authenticate it.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `hmac`, `shop`, `topic`, `api_version`, and `webhook_id` are all separately pulled straight from HTTP headers with no cryptographic tie to each other: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)` — which internally calls `verifiable_query.to_signable_string` (i.e., only the raw body) and compares it against the computed HMAC — and, once that single check passes, dispatches the handler using the *header-derived* `shop`, `topic`, and `webhook_id`, none of which were part of the signed data: [3](#0-2) 

`HmacValidator.validate` confirms the signable string is the only thing checked against the secret: [4](#0-3) 

**Identity binding broken:** the equality that should hold is `shop_attested_to_handler == shop_that_the_HMAC_actually_authenticates`. Because the HMAC is computed only over `@raw_body`, this equality is never enforced — any request whose body matches a previously-observed valid (body, HMAC) pair will pass validation regardless of what `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers accompany it.

An unprivileged attacker who has installed the app on their own Shopify store (a normal, unprivileged merchant action, not requiring `api_secret_key` or any victim credential) can trigger a real webhook to their own endpoint, capture the legitimate `(raw_body, hmac)` pair that Shopify computed with the app's shared secret, and replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header naming a victim shop. Because the secret and HMAC only ever cover the body — which is often small/predictable (e.g., `{}`, or a webhook body whose fields the attacker fully controls through their own store's data) — the forged request validates successfully and is dispatched to the handler as if it originated from the victim shop.

### Impact Explanation
This crosses the tenant boundary that `WebhookMetadata#shop` is meant to represent: a host application's webhook handler will process attacker-supplied data believing it came from an arbitrary victim shop. Depending on how the host app's handler acts on `shop` (e.g., updating per-shop records, revoking access, writing order/fulfillment data, or de-provisioning a merchant), this enables cross-tenant data corruption or state manipulation attributed to a shop the attacker does not control — matching the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
The attacker only needs to be a normal merchant capable of installing the app (or otherwise triggering a webhook addressed to themselves) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-chosen headers — both requirements an ordinary unprivileged internet user/merchant satisfies. No access token, `client_secret`, or privileged account is required; the exploit relies purely on the fact that `to_signable_string` in `lib/shopify_api/webhooks/request.rb` omits the shop/topic/webhook-id fields from the signed data.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable string (or otherwise cryptographically bind them, e.g. by having `Registry.process` re-derive/verify the shop against a channel Shopify itself authenticates, such as comparing to the app's known installed shops after body-HMAC verification), so that spoofing any of these header values invalidates the signature.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook subscription (e.g., `app/uninstalled`) whose body content is attacker-known/predictable (many webhook payloads are `{}` or attacker-controlled JSON since they reflect the attacker's own store data).
2. Shopify sends the webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: <topic>`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`.
3. Attacker captures `raw_body` and the valid `x-shopify-hmac-sha256` value.
4. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `to_signable_string` (== `raw_body`) against the HMAC — validation succeeds.
6. The handler is invoked via `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", ...))`, causing the app to act as if the (forged) event originated from the victim shop. [5](#0-4)
