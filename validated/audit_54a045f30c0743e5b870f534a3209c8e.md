### Title
Webhook `shop-domain` / `topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the *unauthenticated* `shop-domain`, `topic`, `api-version`, and `webhook-id` headers straight to the host app's handler as trusted `WebhookMetadata`. Because these header values are never part of the signed content, any party who can obtain one validly-signed `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own store and receiving a real webhook) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header for a victim shop. The library reports this forged request as authentic and originating from the victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body — none of the identifying headers are included in the signed content: [2](#0-1) 

`Registry.process` performs exactly one authentication check — `Utils::HmacValidator.validate(request)` — and then immediately trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` (all sourced from unauthenticated HTTP headers) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The equality the code implicitly (and incorrectly) assumes is:
`shop-domain header == shop that produced/authorized this signed body`

but the HMAC only proves:
`hmac == HMAC(api_secret_key, raw_body)`

It says nothing about which shop the body belongs to. Since the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are fields acted upon (used to route/attribute the event) but not covered by the HMAC, an attacker who has ever received one legitimately-signed webhook payload from Shopify for the app (trivially obtainable by installing the app on their own free/dev store and triggering any subscribed event) can:
1. Capture the real `raw_body` and its valid `hmac-sha256` value from a webhook delivered for their own shop.
2. POST that identical body + hmac to the app's public webhook endpoint again, but with `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) rewritten to point at any other shop domain.
3. `HmacValidator.validate` succeeds (body/hmac match), and `Registry.process` forwards `WebhookMetadata` claiming the forged `shop`.

Any host application that uses `data.shop` (as the documentation explicitly recommends: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) to look up per-tenant records, apply the payload, or trigger tenant-scoped side effects will act on attacker-chosen data under an arbitrary victim tenant's identity — a cross-tenant confused-deputy condition rooted entirely in this gem's webhook verification/metadata construction, not in host misuse of an undocumented API.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), matching the Critical impact category: a single low-privilege attacker (any user who installs the app once) can make the gem attest that data belongs to any other merchant's shop, causing host applications built exactly as the shipped documentation instructs to process/store forged events against a victim shop's data.

### Likelihood Explanation
Likelihood is high and requires no privileged credentials: any user can self-install the target app to receive one genuinely-signed webhook, then replay the untouched body/HMAC pair to the app's public webhook URL with a spoofed `shop-domain` header. No knowledge of `api_secret_key` or any access token is needed — the attacker relies purely on the fact that identifying headers are outside the signed payload.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the value that is HMAC-verified (e.g., include them in `to_signable_string`, or independently verify `shop` against the session/shop the app registered the webhook for) so `HmacValidator.validate` cannot succeed unless the header values match what Shopify actually signed for that specific shop and topic.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop "attacker.myshopify.com"
#    and receives a legitimate webhook, capturing:
raw_body = '{"id":1,"note":"hello"}'
real_hmac_header = "<value copied from X-Shopify-Hmac-Sha256 of the real request>"

# 2. Attacker replays the exact same body/hmac to the app's public
#    webhook endpoint, but swaps the shop-domain header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac_header,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks raw_body,
# and the handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
