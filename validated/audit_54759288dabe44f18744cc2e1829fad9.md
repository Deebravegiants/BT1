### Title
Cross-origin trust and connection state forgery via unauthenticated `origin` parameter in ConnectedOrigins module - ([File: features/connected-origins/module/connections.js])

### Summary
The `ConnectedOrigins` module (`features/connected-origins/module/connections.js`) exposes state-mutating methods — `add`, `untrust`, `setAutoApprove`, `setFavorite`, `connect`, `disconnect`, `updateConnection`, `clearConnections` — that all take a caller-supplied `origin` string and use it directly as the key to read/write the trust and connection state for that origin, with no verification that the caller actually *is* that origin.

### Finding Description
Every mutating method in `ConnectedOrigins` accepts `{ origin, ... }` as a plain parameter and uses it as-is to look up and mutate the corresponding entry in `connectedOriginsAtom`: [1](#0-0) [2](#0-1) 

These are exposed unmodified through the public API surface: [3](#0-2) 

and the module itself is marked `public: true`: [4](#0-3) 

This mirrors the `CollateralManager#commitCollateral` bug class: a sensitive state-mutating function that identifies "whose" state to touch via a caller-supplied identifier (bidId → borrower there, `origin` string here) with no check that the actual caller is authorized to act on behalf of that identifier. In the Teller case, anyone could commit collateral to *any* bid; here, if the RPC/bridge layer that connects a website's web3 provider (`window.exodus.solana`, `window.cardano.exodus`, etc.) to this module passes through the client-supplied `origin` field instead of the browser/webview-verified sender origin, any connected website can call these methods with an arbitrary `origin` string to manipulate another site's trust record.

Concretely, if `origin` is trusted client input at the RPC boundary, a malicious page could:
- Call `setAutoApprove({ origin: 'https://some-other-trusted-dapp.com', value: true })` to force auto-approval (skip user confirmation) for a different, legitimate site's future connections.
- Call `untrust({ origin: 'https://some-other-trusted-dapp.com' })` or `disconnect({ id, origin: ... })` to forcibly revoke another site's trusted/connected status (denial of service / social engineering setup).
- Call `add({ origin: 'https://some-other-trusted-dapp.com', trusted: true, assetNames: [...] })` to expand another origin's granted `assetNames`, or `connect({ id, origin })` to fabricate active-connection records for origins the caller does not control.
- Since `getConnectedAccounts({ origin })` reveals wallet account addresses for a trusted origin, forging trust/connection records tied to another origin could also be used to route address disclosure incorrectly if the RPC boundary keys authorization off the record set by these unauthenticated calls.

### Impact Explanation
This breaks the origin-isolation trust model that `connected-origins` is meant to enforce ("the connected origins module maintains a list of the third-party websites that the user has authorized to interact with Exodus" — [5](#0-4) ). If reachable from an untrusted webpage without the RPC layer overriding the client-provided `origin` with the actual verified sender origin, this is a cross-origin privilege-bleed: an attacker site can silently grant itself/another origin elevated `autoApprove` trust (bypassing the user-approval popup design described in the Solana provider docs — [6](#0-5) ), or tamper with another origin's connection/trust state, undermining the "ask user for approval on each new site" security control that is Exodus's primary defense against unauthorized dApp interaction.

### Likelihood Explanation
Likelihood depends entirely on whether the RPC/content-script bridge that exposes `connectedOriginsApi` to web pages (via `@exodus/browser-extension-rpc`, `@exodus/sdk-rpc`) re-stamps the `origin` argument with the actual browser-verified sender origin before invoking `connectedOrigins.add/setAutoApprove/connect/...`, or whether it forwards the caller-supplied object (including `origin`) verbatim. The module itself performs zero such verification — the authorization boundary, if it exists, must live entirely in a layer this index could not confirm the contents of (the concrete background-script wiring that maps a specific tab/page's dApp provider calls to this API). This is analogous to the original Teller finding where the vulnerable function itself had no access control and relied entirely on an assumption that callers would behave — an assumption that was false.

### Recommendation
- In `ConnectedOrigins`, do not trust a client-supplied `origin` for any mutating method. Require the caller's origin to be derived server-side (from the verified `sender`/`tab.url` in the RPC/message-passing layer, as already partially plumbed via `senderMetadata` in `libraries/browser-extension-rpc/content.js` and `libraries/browser-extension-channels/channel.js`), and pass that verified value into `connections.js`, ignoring or asserting-equal any origin field submitted by the dApp-facing caller.
- Add an explicit authorization check in `add`, `setAutoApprove`, `untrust`, `connect`, `disconnect`, and `updateConnection` that the acting origin matches the target `origin`, or restrict these mutating methods so they are only callable from the trusted wallet UI process (not from the dApp-facing bridge) analogous to restricting `commitCollateral` to `TellerV2`/borrower.
- Add regression tests asserting that a call purporting to act as one origin cannot mutate another origin's trust/connection record when routed through the actual dApp-facing RPC surface (not just the in-process unit tests currently present, which call `connections.js` methods directly and therefore do not exercise the origin-authentication boundary).

### Proof of Concept
Not independently reproducible from the indexed code alone: the unit and headless-SDK tests found (`features/connected-origins/module/__tests__/connections.test.js`, `sdks/headless/__tests__/connected-origins.test.js`) call `connectedOrigins.setAutoApprove/add/connect` directly with attacker-chosen `origin` values and demonstrate the method **will** perform the state mutation for any `origin` string supplied, with no ownership check: [7](#0-6) 

What could not be confirmed from the available index is the exact code path in the browser-extension/content-script bridge that connects a web page's `window.exodus`/`window.cardano.exodus` provider calls to `connectedOriginsApi`, specifically whether it substitutes the verified sender origin for the client-supplied one. Due to index size limits, some file contents (particularly the concrete background-script wiring for the dApp provider bridge) may not be fully available — a Devin session with full repository access would be needed to trace that exact call path and confirm exploitability end-to-end before treating this as a confirmed, exploitable vulnerability rather than a design/analog concern.

  add = async ({
    connectedAssetName,
    origin,
    name,
    icon,
    assetNames = [],
    trusted,
    favorite,
    walletAccount,
  }) => {
    const value = await this.#getOrigin({ origin })

      ...(value?.assetNames ?? []),

        origin,
        attributes: {

          name: name ?? value.name,
          connectedAssetName: connectedAssetName ?? value.connectedAssetName,

          favorite: favorite ?? value.favorite,
          assetNames: [...allConnectedAssetNames],
          walletAccount: walletAccount ?? value.walletAccount,

      })

      return

      origin,
      icon,
      name,
      connectedAssetName,
      trusted,
      favorite,
      assetNames: [...allConnectedAssetNames],

    })
  }

  isAutoApprove = async ({ origin }) => {
    const value = await this.#getOrigin({ origin })
    return value?.autoApprove || false
  }

  setAutoApprove = async ({ origin, value }) => {
    return this.#setAttributes({ origin, attributes: { autoApprove: value } })
  }

  setFavorite = async ({ origin, value, assetNames = [] }) => {
    return this.#setAttributes({ origin, attributes: { favorite: value, assetNames } })
  }

  connect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnection = { id, createdAt: Date.now() }
    const newConnections = uniqBy([...activeConnections, newConnection], 'id')

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }

#### Eagerly Connecting

After the user approves a Web3 site's connection to Exodus, the site becomes
trusted. This allows the site to automatically connect to Exodus on subsequent
visits or page refreshes. This is referred to as "eagerly connecting".

If you want to try to eagerly connect, you can pass the `onlyIfTrusted` option
to `connect()`.

```typescript
try {
  await window.exodus.solana.connect({ onlyIfTrusted: true })
} catch (err) {
  // { code: 4001, message: 'User rejected the request.' }
}
```

:::tip

When using this flag, Exodus will only connect if the site is trusted and won't
bother your users with a pop-up if they have not connected to Exodus before.

:::
