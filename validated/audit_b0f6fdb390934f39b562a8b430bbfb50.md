### Title
Unallowlisted route venues let user-supplied `swap_xdr` put arbitrary contract code on the call stack, enabling theft of router-held funds and signer wallet funds via injected token transfers - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The Rabby incident class — user-controlled parameters producing arbitrary external calls that move a victim's tokens — maps directly onto XOXNO Lending's router strategy path. `swap_tokens` forwards an opaque, caller-supplied `swap_xdr` blob to `SwapAggregatorClient::execute_strategy`, which decodes a `StrategyPayload` naming arbitrary pool and token addresses and invokes them with no allowlist. A malicious "pool" contract named in a hop executes with the router as its direct invoker, which grants it the router's invoker-contract authority over `token.transfer(router, …)`, and any `token.transfer(victim, …)` it issues is recorded as a child of the signer/controller's authorization tree and executes if that tree is signed. The codebase itself proves the second channel: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` drains a user's unrelated wallet balance to zero through a rogue hop pool inside `swap_collateral`.

### Finding Description
`swap_tokens` (contracts/controller/src/strategies/swap.rs:13-55) is reached by every router strategy entrypoint (`swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `multiply`, `flash_position` swap legs). It authorizes exactly one input transfer (`authorize_transfer_as_current`, line 34), then calls `router.execute_strategy(&controller, &amount_in, swap)` where `swap` is the raw `swap_xdr` bytes supplied in the entrypoint arguments — never decoded or validated by the controller (line 37). The router's `execute_strategy` (contracts/swap-aggregator/src/lib.rs:250-255) decodes the payload and runs the instruction stream; venue adapters call `env.invoke_contract(&ctx.hop.pool, "swap", …)` on whatever pool address the payload names (e.g. contracts/swap-aggregator/src/venues/phoenix.rs:23-25). The threat model confirms the router "keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (docs/explanation/threat-model.md:154-158).

Two theft channels result:

1. **Invoker-auth drain of router custody.** A payload-named pool is invoked directly by the router, so the router's address is the invoker. In Soroban, `require_auth` on the direct invoker contract address is satisfied by invoker contract auth, so the rogue pool can call `token.transfer(router → attacker, amount)` on any token — sweeping the router's custodied vault balances mid-route and, more importantly, the accumulated `AdminFee`/`ReferralFee` token balances the router holds until `claim_admin_fees`/`sweep_balance`. An unprivileged attacker executes this through their own `execute_strategy` or `swap_collateral` call with a self-crafted `swap_xdr`; no victim signature is needed.

2. **Poisoned auth tree against the signer.** The rogue pool can instead issue `token.transfer(victim → attacker, amount)` for an arbitrary token. The harness test shows recording mode attaches this transfer as a child of the caller's `swap_collateral` auth entry, and enforcement executes it if signed — the test drains Alice's entire `WALLET_BALANCE` of an unlisted token while her swap still receives fair output (tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-227). The threat model states "the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (docs/explanation/threat-model.md:158-161).

### Impact Explanation
Channel 1 is theft of accrued admin and referral fee balances held by the router — theft of unclaimed yield, reachable by any unprivileged address with a self-made payload, plus any residual tokens in router custody. Channel 2 is theft of the signer's unrelated wallet funds, unbounded by `amount_in`, min-out, or the controller's `RouterOverspend`/`NoSwapOutput` checks (swap.rs:40-54), triggered when a user signs a route delivered by a malicious or compromised quote/client. Both are Critical/High-severity loss-of-funds primitives matching the Rabby pattern.

### Likelihood Explanation
Channel 1 requires only that the attacker deploy a contract and encode a payload naming it as a hop pool — the decoder performs no venue allowlisting (payload.md documents instruction fields as plain `assets` indices). Execution is fully on-chain and permissionless via `execute_strategy` or `swap_collateral`. Channel 2 additionally requires the victim to sign a poisoned authorization tree, which is realistic because `swap_xdr` is opaque bytes that standard clients forward untouched (composition.md: "the controller forwards those bytes to the router as `swap_xdr` without decoding them"), and Soroban simulation presents the injected transfer inside a legitimate-looking invocation tree. The dedicated harness test demonstrates both recording and enforcement behavior end-to-end.

### Recommendation
- Enforce a venue/pool allowlist in the router: maintain owner-managed whitelisted pool addresses per venue and reject hops whose `pool` (or `token_in`/`token_out`) is not registered, mirroring the input-transfer-only grant the controller already uses.
- Alternatively, sandbox venue calls so hop code cannot act with router invoker auth — e.g., route through a per-hop forwarder contract that holds no standing balances, and keep fee balances in a separate contract the router never exposes as invoker.
- On the controller side, decode `swap_xdr` before forwarding (or require the router to return a structured route manifest) so `swap_tokens` can reject payloads naming unexpected contracts.
- Document and enforce client-side auth-tree verification: refuse any `swap_collateral`/`execute_strategy` signature whose recorded tree contains children other than the single expected input `transfer`, as the threat model already prescribes (docs/explanation/threat-model.md:162-165).

### Proof of Concept
```rust
// Attacker-deployed contract named as a hop pool in swap_xdr.
// Invoked BY the router → router is the invoker → invoker auth
// satisfies token.transfer(from = router) automatically.
#[contract]
pub struct RoguePool;

#[contractimpl]
impl RoguePool {
    pub fn swap(env: Env) {
        let router = /* router address */;
        // Drain accrued fee balances and vault-custodied tokens.
        for token in victim_tokens {
            let bal = token::Client::new(&env, &token).balance(&router);
            if bal > 0 {
                token::Client::new(&env, &token)
                    .transfer(&router, &attacker, &bal); // invoker auth: passes
            }
        }
        // Return a dust positive output so dispatch_hop's `received > 0` passes.
    }
}
```
Attack: `RouterClient::execute_strategy(attacker, total_in, crafted_xdr)` or `ctrl.swap_collateral(attacker, acct, usdc, amount, eth, crafted_xdr)` where `crafted_xdr` encodes a `StrategyPayload` whose `assets` includes `RoguePool` and a Swap instruction with `idx_a = RoguePool`. No privileged role or victim interaction required for the fee-drain variant.

For the signer variant, `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-227` already implements it: `RogueHopPool::swap` issues `token::Client::transfer(alice → attacker, WALLET_BALANCE)` inside the hop, the recorded tree places it under Alice's `swap_collateral` entry, and on signature `balance(alice) == 0`, `balance(attacker) == WALLET_BALANCE`.
