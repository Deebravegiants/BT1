### Title
Omni Bridge withdrawal status is matched by array position, not by content, letting `describeWithdrawal` report the wrong destination hash for a batched withdrawal - (File: `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`)

### Summary
`OmniBridge.describeWithdrawal` selects the on-chain transfer to report on purely by its position (`args.index`) in the array returned by `omniBridgeAPI.getTransfer({transactionHash})`, without checking that the transfer's recipient, token, or amount actually correspond to the withdrawal the caller is asking about.

### Finding Description
When a single NEAR transaction contains multiple withdrawal intents routed through the Omni Bridge (a supported and expected flow — see `createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts`), each withdrawal is assigned a sequential `index` per bridge route: [1](#0-0) 

`OmniBridge.describeWithdrawal` then fetches all transfers for that NEAR tx hash and blindly indexes into the returned array to find "its" transfer: [2](#0-1) 

It never checks that `transfer.recipient` equals `args.withdrawalParams.destinationAddress`, nor that `transfer.token_id`/amount corresponds to `args.withdrawalParams.assetId`/`amount`. The reported `txHash` is taken from whatever transfer object happens to sit at that array index and is returned as `completed` with that hash: [3](#0-2) 

This is the same bug class as the Guzzle host-only cookie flaw: an identity/scope check that should be based on an exact match (cookie ↔ exact host; withdrawal ↔ exact recipient/asset) is instead approximated by an unrelated positional/derived proxy (domain string reused from request host; array index reused from submission order), so data intended for one entity is returned for another whenever the two orderings diverge.

Critically, the codebase itself demonstrates that this positional assumption is unsafe: the sibling `PoaBridge.describeWithdrawal` explicitly avoids indexing by position because the API's response list is *not* guaranteed to preserve submission order, and instead matches by `assetId`: [4](#0-3) 
This is reinforced by an explicit poa-bridge test asserting "matches withdrawal by assetId, not by index": [5](#0-4) 

`OmniBridge` has no analogous content-based matching or guard, so if the Omni Bridge indexer's `getTransfer` array order does not exactly mirror the order withdrawals were submitted within the NEAR transaction (e.g. because the indexer sorts/returns by internal processing/finalization order rather than intent order), `describeWithdrawal` reports the transaction hash of a *different* withdrawal (different asset, different destination, different amount) as the completion of the queried one.

### Impact Explanation
`watchWithdrawal` in `withdrawal-watcher.ts` treats a `completed` status with a `txHash` as authoritative proof that the specific withdrawal succeeded on the destination chain: [6](#0-5) 
An integrator relying on this SDK to confirm/settle a specific user withdrawal (e.g., to credit an off-chain balance, mark an order fulfilled, or release custody) could be told withdrawal A (to address X) is "completed" with a hash that actually belongs to withdrawal B (to address Y), or vice versa. This is a status/hash misreport that can cause an integrator to credit or refund the wrong withdrawal, or to credit twice while the actually-requested transfer remains unconfirmed/stuck — matching the High-severity bucket ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
This requires no malicious actor — it triggers whenever a single NEAR transaction batches more than one Omni Bridge withdrawal intent (a normal, supported usage pattern via `sdk.createWithdrawalIntents`/multiple `withdrawalParams`) and the Omni Bridge indexer's transfer ordering for that tx hash does not exactly match submission order. Since ordering guarantees of the external indexer are not controlled by this SDK and the sibling `PoaBridge` implementation already had to work around exactly this non-guarantee, the likelihood of divergence is non-trivial in production batched-withdrawal scenarios.

### Recommendation
In `OmniBridge.describeWithdrawal`, do not select the transfer solely by `args.index`. Instead, match the on-chain transfer to `args.withdrawalParams` using content that identifies it (recipient address decoded from the omni address, token id, and amount), similar to the `findMatchingWithdrawal`-by-`assetId` approach used in `PoaBridge`. If no unambiguous content match is found, return `pending` rather than reporting a positionally-adjacent transfer's hash.

### Proof of Concept
1. User submits one NEAR transaction containing two Omni Bridge withdrawal intents in the same call: withdrawal #0 = 100 USDC to `0xAAA...` on Ethereum, withdrawal #1 = 5 ETH to `0xBBB...` on Ethereum.
2. `createWithdrawalIdentifiers` assigns `index: 0` to the USDC withdrawal and `index: 1` to the ETH withdrawal, per submission order (`packages/intents-sdk/src/core/withdrawal-watcher.ts:88-104`).
3. The Omni Bridge indexer processes/returns transfers for that NEAR tx hash, but returns the ETH transfer first and the USDC transfer second (e.g., because the ETH transfer finalized/was indexed sooner) — an ordering not controlled by or verified against by the SDK.
4. `describeWithdrawal({index: 0, ...})` for the USDC withdrawal returns `transfer[0]`, which is actually the ETH transfer to `0xBBB...`, and reports `{status: "completed", txHash: <ETH tx hash>}` for what the caller believes is the USDC withdrawal.
5. An integrator polling withdrawal #0 sees it "completed" with a valid-looking hash and credits/settles the USDC withdrawal, while the real USDC transfer status (still pending or on a different hash) is never correctly attributed — the wrong transaction hash is recorded as proof of the USDC withdrawal's completion.
