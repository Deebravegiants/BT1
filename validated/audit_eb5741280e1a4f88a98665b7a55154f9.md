### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only authenticates the raw request **body**; the `shop-domain` header that the gem hands to app handlers as the tenant identifier is never included in the HMAC computation, so it can be freely rewritten by anyone who can produce one legitimately-signed webhook payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (i.e., the body) against the app's single, global `api_secret_key`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to trust the request wholesale, then forwards the attacker-controlled `request.shop` straight to the app's handler as the tenant identity: [4](#0-3) 

The documented equality the app developer is led to believe holds is: `hmac_valid? == true` implies `shop == the shop that generated this event`. In reality the equality that holds is only `hmac_valid? == true` implies `raw_body == the body Shopify actually signed`; `shop` is an independent, unauthenticated header. Because `api_secret_key` is a single per-app secret shared across every merchant install (not per-shop), **any merchant who has installed the app** can capture one of their own genuinely-signed webhook deliveries (valid HMAC over that body) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` (it never looks at the header), so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain while carrying the attacker's crafted body content (subject to whatever body Shopify itself signed for the attacker's own shop/topic — the attacker can also influence body-affecting fields like `fields`/`filter` configured for the topic they registered).

The gem's own docs advertise `Registry.process` as verifying "the request did indeed come from Shopify" (implying full authenticity, including attribution) and explicitly recommend using `data.shop` to key downstream work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that host apps are expected to trust `shop` as authenticated: [5](#0-4) [6](#0-5) 

### Impact Explanation
This breaks the tenant-identity binding that host applications rely on: `data.shop` returned by a "verified" webhook is not actually authenticated by this gem. A malicious merchant (an unprivileged actor relative to other tenants of the same app, requiring no special credentials, access tokens, or `api_secret_key` knowledge) can inject events attributed to a victim shop into the host app's ingestion pipeline, causing cross-tenant data corruption/injection (e.g., false orders/create, false app/uninstalled, false shop/redact events processed under the victim's tenant record). This satisfies the "cross-tenant access" criterion via a credential/tenant boundary crossing achieved purely through this gem's own webhook verification logic.

### Likelihood Explanation
Any user who can install the app on their own store (a normal, unprivileged action) and register at least one webhook topic can capture a validly-signed body/HMAC pair from Shopify's real webhook delivery to their own endpoint, then replay it with a modified `shop-domain` header — no interception of TLS, no leaked secrets, and no privileged account is required.

### Recommendation
Bind the tenant identity to the signature. Options:
- Have `Registry.process` require the caller to supply the expected/authenticated shop (e.g., resolved from an authenticated session or from Shopify's separate mandatory webhook verification flow) and compare it against `request.shop`, rejecting mismatches.
- At minimum, document loudly that `data.shop`/`data.topic` are **not** covered by the HMAC and must be independently authorized (e.g., checked against a known list of

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
