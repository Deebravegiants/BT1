Found the exact identity-binding break: the webhook HMAC (`Webhooks::Request`) signs only the raw body, while the `shop` value that the gem hands to the application's webhook handler is read from an unauthenticated HTTP header.

### Title
Webhook `shop` identity is trusted from an HMAC-unverified header, breaking the "verified bytes == acted-upon bytes" binding - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity using `Utils::HmacValidator.validate(request)`, which computes the HMAC only over `request.to_signable_string`, i.e. the raw body [1](#0-0) . However, the `shop` that is subsequently passed to the app's registered webhook handler comes from the `X-Shopify-Shop-Domain` HTTP header, not from the signed body [2](#0-1) .

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [3](#0-2) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is derived from the `X-Shopify-Hmac-Sha256` header [4](#0-3) . The `shop` field used downstream is read directly from the `X-Shopify-Shop-Domain` header [2](#0-1) , a field that is never part of the signed bytes.

`Registry.process` passes this unverified `shop` straight into the `WebhookMetadata` object delivered to the app's handler: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` after only checking `HmacValidator.validate(request)` [5](#0-4) .

This breaks the intended identity binding: `HMAC-verified bytes == bytes acted upon`. Concretely: `signed(raw_body) != (raw_body, shop_header)` — the `shop` value that a host application typically uses as the tenant key to look up the merchant's stored session/access token is not covered by the signature at all. An attacker who can produce (or replay/relay) a validly-signed body for their own shop's webhook could pair it with a spoofed `X-Shopify-Shop-Domain` header claiming a victim shop's domain, and the signature would still validate successfully because the header value is entirely outside the signed content.

### Impact Explanation
Any host application built on this SDK that trusts `WebhookMetadata#shop` (as returned by this gem's own `Registry.process`) as the tenant identity for loading the merchant's access token, without independently re-validating that value against the signed payload, is exposed to cross-tenant confusion: a webhook whose signature is valid (for the attacker's own shop) but whose declared `shop` field points at a different, victim tenant. Since the gem's own API (`Registry.process` / `WebhookMetadata`) is the one supplying this unauthenticated `shop` value as if it were verified, this is not a case of the host ignoring documented behavior — the gem itself conflates "HMAC valid" with "shop field trustworthy." This is a cross-tenant access class of bug per the impact criteria.

### Likelihood Explanation
Exploitation requires the attacker to have a legitimate app installed on at least one shop (to legitimately trigger a validly-HMAC-signed webhook delivery, e.g. via `shop/redact` self-service GDPR triggers or normal store events), then relay/replay that request while altering only the `X-Shopify-Shop-Domain` header before forwarding it to the app's webhook endpoint. This is unprivileged with respect to the victim shop (no victim credentials needed) but does require control of/traffic interception between Shopify and the app's endpoint, or an app endpoint that is reachable and does not enforce TLS/IP-based origin checks beyond this SDK's `process` call. This is realistically exploitable when the host relies solely on `ShopifyAPI::Webhooks::Registry.process`'s pass/fail result as the sole trust signal, which is exactly the documented, intended usage of this gem.

### Recommendation
Include the shop domain (and ideally topic/api-version) as part of the HMAC-signed content, or fail closed if the app cannot independently corroborate `X-Shopify-Shop-Domain` against another authenticated channel (e.g., cross-check with the `shop` recorded when the corresponding webhook subscription was registered). At minimum, document prominently that `WebhookMetadata#shop` is derived from an unauthenticated header and must not be used as a sole tenant-identity source for token lookup.

### Proof of Concept
1. App registers webhooks and its endpoint calls `ShopifyAPI::Webhooks::Registry.process(request)` per documented usage.
2. Attacker (with an app installation on `attacker-shop.myshopify.com`) triggers a webhook so Shopify sends a validly signed request: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker intercepts/replays this request to the app's public webhook endpoint but changes only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`, leaving body `B` and the HMAC header untouched.
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/hmac_validator.rb`/`request.rb` still returns `true`, because the check only covers `@raw_body`, per [1](#0-0) .
5. `Registry.process` proceeds and calls the app's handler with `shop: "victim-shop.myshopify.com"`, per [6](#0-5) , causing the app (if it trusts this value, as the API implies is safe post-validation) to act on/for the victim tenant using attacker-controlled body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
