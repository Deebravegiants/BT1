### Title
`DirectBridge.describeWithdrawal` reports NEAR withdrawals as "completed" without verifying the on-chain outcome of the transfer - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.describeWithdrawal()` unconditionally returns `{ status: "completed", txHash: args.tx.hash }` as soon as it is called, without querying any indexer, receipt outcome, or the token contract to confirm the withdrawal (`ft_withdraw`/token transfer) actually succeeded. This mirrors the reported bug class: a reporting function assumes a transfer happened without validating the actual on-chain result.

### Finding Description
Every other bridge implementation in the SDK derives its `"completed"` status from an external source of truth that reflects the *actual* destination-chain or indexer-confirmed state:
- `PoaBridge.describeWithdrawal` only reports `completed` after `getWithdrawalStatusWithRetry` returns `status === "COMPLETED"` from the POA indexer [1](#0-0) .
- `OmniBridge.describeWithdrawal` inspects `transfer.finalised` / `transfer.utxo_meta` data from the Omni Bridge API before returning `completed` [2](#0-1) .
- `HotBridge.describeWithdrawal` cross-checks the HOT contract view method, the bridge indexer, and an API fallback before reporting `completed` [3](#0-2) .

In contrast, `DirectBridge.describeWithdrawal` performs none of this verification:
```
async describeWithdrawal(
	args: WithdrawalIdentifier,
): Promise<WithdrawalStatus> {
	return { status: "completed", txHash: args.tx.hash };
}
``` [4](#0-3) 

It simply echoes back the NEAR transaction hash of the intent-publishing transaction (`args.tx.hash`) as proof of completion. The actual token movement is executed by a cross-contract call (`ft_withdraw`/token transfer) created in `createWithdrawalIntents` via `createWithdrawIntentPrimitive` [5](#0-4) . On NEAR, a transaction being included and returning a "Success" execution outcome for the *outer* receipt does not guarantee that every *asynchronous* nested receipt (e.g., the actual `ft_transfer`/`ft_resolve_transfer` callback to the destination token contract) also succeeded — such failures surface in separate receipts and can occur after the transaction hash is already considered final. `DirectBridge` never inspects receipt outcomes, logs, or a balance delta to confirm the transfer's actual outcome; it treats "the intent transaction was submitted" as equivalent to "the withdrawal landed."

This breaks the intended equality: *status reported == actual on-chain outcome*. Here the reported status is derived only from "a transaction hash exists," not from confirmation that the destination account's balance increased or that the withdrawal receipt succeeded.

### Impact Explanation
`watchWithdrawal()` (used by `sdk.waitForWithdrawalCompletion`) treats a `"completed"` status as the final answer and stops polling immediately [6](#0-5) . Any integrator (custodian, exchange, bridge operator) that relies on `describeWithdrawal`/`waitForWithdrawalCompletion` to decide whether to credit a user, release an off-chain balance, or mark an order settled for NEAR-native withdrawals routed via `DirectBridge` would receive a false "completed" confirmation even if the underlying token transfer receipt actually failed (e.g., due to a race in storage-balance validation, gas exhaustion in a nested callback, or contract-side panic). This matches the "status or hash misreport making an integrator credit or refund twice" High-impact category: the integrator could credit the withdrawal as delivered while the tokens never actually left/arrived, and there would be no automatic re-check or retry mechanism to catch the discrepancy.

### Likelihood Explanation
`DirectBridge` handles the `RouteEnum.NearWithdrawal` route, i.e., any withdrawal whose asset and destination resolve to a plain NEAR account [7](#0-6) . This is a commonly used, default route (no external bridge needed), so the flawed `describeWithdrawal` executes on a normal, frequent code path — not an edge case. `validateWithdrawal` does mitigate the most common failure mode (missing destination account/storage) by checking account existence and comparing addresses [8](#0-7) , but this check is done pre-flight and is itself cached with a 1-hour TTL LRU cache [9](#0-8) , so it does not guarantee the actual settlement receipt succeeds. The likelihood that the underlying async receipt fails while the outer tx hash is still returned is dependent on NEAR runtime specifics (gas, callback logic in the token contract), which I could not fully verify from the SDK code alone — the repo does not include NEAR runtime/receipt-outcome parsing logic to cross-check this claim (`ExecutionOutcome`/receipt-status handling was not found anywhere in the SDK, confirming there is no defensive check).

### Recommendation
Before returning `"completed"`, `DirectBridge.describeWithdrawal` should fetch the transaction's execution outcome (and nested receipt outcomes) via the NEAR RPC provider (`this.nearProvider`) and confirm that the `ft_transfer`/withdrawal receipt succeeded (not just that the outer transaction was included), or otherwise verify a balance delta on the destination account, before reporting `"completed"`. If the receipt failed, it should report `"failed"` with the corresponding reason, consistent with how other bridges (`PoaBridge`, `OmniBridge`, `HotBridge`) resolve their status.

### Proof of Concept
1. Call `sdk.createWithdrawalIntents` for a NEP-141 token with `routeConfig` resolving to `RouteEnum.NearWithdrawal` (handled by `DirectBridge`), targeting an explicit NEAR account.
2. Sign and publish the intent; obtain `NearTxInfo` (`tx.hash`).
3. Suppose the nested `ft_transfer` call inside the intent execution panics/fails asynchronously (e.g., destination account's storage was deregistered between the `validateWithdrawal` cache check and settlement, or gas runs out in the nested callback) while the outer transaction's top-level receipt still finalizes as `SuccessValue`.
4. Call `sdk.waitForWithdrawalCompletion` / `bridge.describeWithdrawal({ ...wid, tx: { hash: txHash } })`.
5. `DirectBridge.describeWithdrawal` immediately returns `{ status: "completed", txHash }` — regardless of whether the nested transfer receipt actually succeeded — causing `watchWithdrawal` to resolve as completed [10](#0-9) , even though on-chain the tokens were never actually delivered to the destination account.

		args: WithdrawalIdentifier & { logger?: ILogger },

		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
