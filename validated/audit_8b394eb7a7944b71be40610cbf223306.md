Based on my thorough investigation, I found the strongest candidate analog in the `orb_relay_announce_orb_id` flow, where an identity/session binding decision is finalized in a single unconfirmed step.

### Title
Single-step, unconfirmed binding of Orb signup session to attacker-controlled `orb_relay_app_id` — ([File: src/plans/mod.rs])

### Summary
The `do_signup` function reads `orb_relay_app_id` directly out of `qr_codes.user_data` (sourced from `backend::user_status::UserData`, populated from the backend's `authenticated_app_data`) and immediately uses it as the destination identity for the entire signup session via `orb_relay_announce_orb_id`, permanently committing `orb.orb_relay` to that identity in one step, with no secondary confirmation/acceptance step analogous to a "propose then accept" pattern.

### Finding Description
In `src/plans/mod.rs`, `do_signup` extracts `orb_relay_app_id` from the resolved QR/user data and passes it straight into `orb_relay_announce_orb_id`, which connects to the relay backend and, upon a single acknowledged send, irreversibly assigns `orb.orb_relay = Some(relay)` for the rest of the signup session: [1](#0-0) [2](#0-1) 

This mirrors the reported bug class: a privileged/identity-binding operation (here, binding the physical signup/biometric session to a specific app/session identity) is committed in a single atomic step based on externally supplied data, with no two-phase "propose → accept" handshake that would allow the bound party to confirm the pairing before it is used to route signup completion signals (`SignupEnded`) and app-facing state.

The `orb_relay_app_id` itself originates from the backend-supplied, QR-derived `UserData` structure and is bound into `credentials`/session state without any independent, human-verifiable second step: [3](#0-2) 

### Impact Explanation
If a wrong or attacker-influenced `orb_relay_app_id` is bound (e.g., due to a QR-code mixup, replay, or backend data error), the Orb announces itself to, and thereafter exchanges signup-lifecycle messages (including `SignupEnded`) with, that relay identity for the remainder of the session — with no opportunity to reject/undo the binding before proceeding into biometric capture and enrollment. This creates a risk of cross-signup state bleed or misattributed signup completion notifications between an app session and an Orb session, since the binding is single-step and not later re-validated against the actual enrolling user's identity.

### Likelihood Explanation
The likelihood is difficult to assess as concretely exploitable purely from static analysis: `orb_relay_app_id` is asserted (in `do_signup`) to come from `authenticated_app_data`, which is validated against `user_data_hash` in `user_status::request` under normal (non-test) builds. Exploitability would depend on whether that upstream validation can be bypassed or on backend-side data integrity, which is outside this repository's scope to confirm.

### Recommendation
Introduce a two-step confirmation before treating a relay/app identity binding as final and using it for session-critical routing: after `orb_relay_announce_orb_id` succeeds, require an explicit acknowledgment/confirmation message from the app side (or a distinguishing token echoed back) before committing to `orb.orb_relay = Some(relay)`, or before allowing the bound identity to receive `SignupEnded`/other completion signals. Additionally, document all points where QR/backend-supplied identifiers are trusted to bind a live signup session, per the "long term" recommendation in the referenced report.

### Proof of Concept
Not independently reproducible from static repository inspection alone — the trust boundary is: `user_data.orb_relay_app_id` (backend/QR supplied) → `orb_relay_announce_orb_id` (single send/ack) → `orb.orb_relay` assignment (irreversible for the rest of `do_signup`), as shown in the cited call chain in `src/plans/mod.rs` lines 527-548 and 2108-2156.

    orb: &mut Orb,
    orb_relay_app_id: String,
    is_self_serve_enabled: bool,
    reties: u32,
    timeout: Duration,
    wait_for_pending_messages: Duration,
    wait_for_shutdown: Duration,
) -> Result<()> {
    let mut relay = Client::new_as_orb(
        RELAY_BACKEND_URL.to_string(),
        get_orb_token()?,
        ORB_ID.to_string(),
        orb_relay_app_id,
    );
    if let Err(e) = relay.connect().await {
        dd_incr!("main.count.orb_relay.failure.connect");
        return Err(eyre::eyre!("Relay: Failed to connect: {e}"));
    }
    for _ in 0..reties {
        let now = Instant::now();
        if let Ok(()) = relay
            .send_blocking(
                common::v1::AnnounceOrbId {
                    orb_id: ORB_ID.to_string(),
                    mode_type: if is_self_serve_enabled {
                        common::v1::announce_orb_id::ModeType::SelfServe.into()
                    } else {
                        common::v1::announce_orb_id::ModeType::Legacy.into()
                    },
                    hardware_type: if identification::HARDWARE_VERSION.contains("Diamond") {
                        common::v1::announce_orb_id::HardwareType::Diamond.into()
                    } else {
                        common::v1::announce_orb_id::HardwareType::Pearl.into()
                    },
                },
                timeout,
            )
            .await
        {
            // Happy path. We have successfully announced and acknowledged the OrbId.
            dd_timing!("main.time.orb_relay.announce_orb_id", now);
            orb.orb_relay = if is_self_serve_enabled {
                Some(relay)
            } else {
                relay.graceful_shutdown(wait_for_pending_messages, wait_for_shutdown).await;
                None
            };
            return Ok(());
