This confirms the asymmetry: in the OAuth flow, `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters ( [1](#0-0) ), so the shop identity is cryptographically bound to the HMAC. In the webhook flow, no such binding exists.

### Title
Webhook shop-domain identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `HmacValidator` only covers the raw request body, never the shop header. Any actor who can obtain one genuine, validly-signed webhook delivery (e.g., by installing the app on their own shop) can replay that exact body+HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will accept it as authentic and hand it to the host application's webhook handler tagged with the attacker-chosen shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`Webhooks::Request#shop` is read straight from an attacker-controlled header, entirely outside the signed content: [3](#0-2) 

`HmacValidator.validate` computes and compares the HMAC using exactly `to_signable_string` (i.e. the raw body) — the `shop` value never enters the computation: [4](#0-3) 

`Registry.process` trusts this unverified `request.shop` and forwards it directly into the `WebhookMetadata` dispatched to the app's handler, with no separate check that the header matches the shop the body was actually generated for: [5](#0-4) 

This is the exact identity-binding break the report's bug class describes: the field the host application relies on for tenant identification (`shop`) is "acted on but not covered by the HMAC." Contrast this with the OAuth path, where `AuthQuery#to_signable_string` explicitly folds `shop` into the signed parameter set before HMAC verification: [1](#0-0) 
— proving the library's own design intent is that `shop` should be bound by the signature, which it fails to do for webhooks.

**Equality that should hold but doesn't:** `shop_covered_by_hmac == shop_used_for_tenant_dispatch`. Before the attack: both are the legitimate shop for a real delivery. After the attack: `request.shop` (attacker-forged header) diverges from the shop whose secret actually produced the HMAC (which is the same `Context.api_secret_key` for every shop in this single-tenant-app model, but the *body content* — order data, customer data, etc. — still belongs to the attacker's own shop while now being labeled as belonging to a different shop of the attacker's choosing).

### Impact Explanation
Because the app-wide `api_secret_key` is shared across all shops using the app (it's not shop-specific), any unprivileged user who installs the app on a shop they control can generate a validly HMAC-signed webhook body. By replaying that valid body+HMAC with a forged `shop-domain` header naming a different, victim shop, they cause the host application's webhook handler to process attacker-controlled data under a false tenant identity. For mandatory compliance topics such as `customers/redact`, `customers/data_request`, or `shop/redact` — or any custom handler that uses `data.shop` to look up/mutate per-tenant records — this enables cross-tenant data corruption, spoofed deletion/redaction requests against a shop the attacker doesn't own, or injection of fabricated data into another merchant's records. This matches the "Critical - cross-tenant access" impact tier.

### Likelihood Explanation
Exploitation requires only: (1) being an app user with any legitimate shop installation (no special privilege), and (2) capturing one real webhook delivery for that shop (trivial, since the app itself receives these). No access to `api_secret_key`, access tokens, or the merchant's credentials of the victim shop is needed. The forged header field is not validated against anything else in the request, making this a low-effort, repeatable spoof.

### Recommendation
Include the shop-domain (and other trust-relevant headers, such as webhook topic and API version) in the HMAC-signed payload verification, e.g. by validating them out-of-band via a signed relationship (mapping the request's origin domain to an offline session/access token known to be associated with that shop), or by having `HmacValidator` bind `to_signable_string` to a canonical representation that includes the shop header, rather than trusting the raw header value implicitly once body-HMAC succeeds.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST body and its `X-Shopify-Hmac-Sha256` header — both valid under `Context.api_secret_key`.
2. Replay this exact body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks the raw body against the HMAC [6](#0-5) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` using the forged `victim.myshopify.com` value [7](#0-6) , causing the host app to act as if the (attacker-supplied) payload originated from the victim shop.
