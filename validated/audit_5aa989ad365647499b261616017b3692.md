### Title
Panic-inducing missing length validation on `message.from` in `pallet-hyper-fungible-token`'s `on_accept` — (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` (the `IsmpModule::on_accept` implementation for the hyper‑fungible‑token pallet) derives the calldata-dispatch `origin` from the ABI-decoded `message.from` bytes without validating their length before slicing/copying them into a fixed-size buffer. This is the same bug class as CVE‑2022‑1649 (missing bounds check before indexing attacker-influenced bytes leading to a crash), reachable through the unprivileged ISMP message-delivery path (`pallet_ismp::handle_unsigned` → router → `on_accept`).

### Finding Description
In [1](#0-0)  the recipient field `message.to` is explicitly length-checked (32 or 20 bytes) before being copied, with a typed error (`HftError::InvalidRecipientLength`) on any other length.

By contrast, when the message carries optional calldata (`message.data` non-empty) and no signature is attached, the sender field `message.from` is used to derive the dispatch `origin` with **no equivalent length check**: [2](#0-1) 

- If `source.is_evm()` is true, `&from_bytes[from_bytes.len() - 20..]` is computed. If `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows (`usize` subtraction), producing a huge start index and causing an out-of-bounds slice panic inside `H160::from_slice`.
- If `source` is not EVM, `account.copy_from_slice(from_bytes)` requires `from_bytes.len() == 32` exactly; any other length panics immediately (`copy_from_slice` panics on a length mismatch), with no `try_into`/length guard as used elsewhere in the same function (see the `to_bytes` handling and the `try_into().map_err(...)` pattern used for signature-based origin derivation just above at lines 134-137/145-148).

`message.from` is a dynamic `bytes` field decoded from the ABI-encoded POST-request `body` via `Message::abi_decode(&body)` at [3](#0-2) . Its length is determined entirely by whatever the dispatching contract/pallet on the source chain encoded — the pallet performs no defensive validation of that length before using it for pointer-style slicing, unlike the parallel `to_bytes` handling in the same function that was clearly hardened for this exact reason.

### Impact Explanation
A panic during `on_accept`, which executes inside `handle_unsigned`'s `#[frame_support::transactional]` extrinsic (an unsigned, permissionless dispatch path reachable by any relayer that submits a valid request/proof, see [4](#0-3)  and its `validate_unsigned` counterpart at [5](#0-4) ), aborts message execution non-gracefully instead of returning a typed `DispatchResult` error. This can render that HFT deployment's message-delivery route unable to process any request carrying such a malformed `from` field — a denial-of-service on the token-bridge relay path (matching the "route unable to deliver messages" impact bar).

### Likelihood Explanation
Exploitability depends on whether a source-chain dispatcher that pallet governance has registered via `ContractToAsset`/`Precisions` ever emits a `from` field whose length is not exactly 20 (EVM) or 32 (Substrate) bytes. The reference `HyperFungibleToken.sol` contract always encodes `from = bytes20(msg.sender)`, so the officially shipped contract cannot trigger this. However, HFT is designed as generic, governance-extensible bridge infrastructure supporting many independently deployed token contracts/pallets as trusted sources; nothing in the on-chain code enforces that every registered source contract encodes `from` at a fixed length, and the receiving pallet's own defensive posture elsewhere (`to_bytes` validation) shows the team is aware this class of input must be checked. This makes the bug a plausible, low-effort DoS vector for any HFT deployment onboarding a third-party or slightly-nonstandard source implementation, without requiring a malicious admin/governance action — only an already-approved but imperfectly-encoding source dispatch.

### Recommendation
Add the same explicit length validation used for `message.to` to the `message.from` handling: require exactly 20 bytes when `source.is_evm()` and exactly 32 bytes otherwise, returning a typed `HftError` (e.g., a new `InvalidSenderLength(usize)` variant) instead of slicing/copying unconditionally. This should be applied at [2](#0-1) .

### Proof of Concept
1. Register (via normal `ContractToAsset` configuration) a source contract/pallet whose dispatch path can be induced to (or is buggy and does) encode a `Message.from` field shorter than 20/32 bytes — or, more directly, note that ABI decoding only enforces the `Message` tuple *shape*, not the concrete byte-length invariants the receiving pallet implicitly assumes for `from`.
2. Craft/dispatch a POST request on the source chain whose ABI-encoded body decodes to a `Message` with `data` non-empty, `substrate_data.signature = None`, and `from` of length ≠ 20 (if destination treats `source.is_evm()`) or ≠ 32 (otherwise).
3. Relay this request with a valid membership proof through `pallet_ismp::handle_unsigned`.
4. During `on_accept`, execution reaches `&from_bytes[from_bytes.len() - 20..]` (EVM path) or `account.copy_from_slice(from_bytes)` (Substrate path) and panics, aborting message processing instead of returning a typed error.

Note: I could not fully confirm an unprivileged path exists to make an *already-trusted* HFT source contract encode a wrong-length `from` in the current codebase (the reference Solidity implementation always uses `msg.sender`, 20 bytes), so real-world exploitability hinges on non-reference/third-party source deployments that the ecosystem's generic bridge design explicitly anticipates.
