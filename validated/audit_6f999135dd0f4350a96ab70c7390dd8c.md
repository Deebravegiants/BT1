### Title
Caller-supplied swap route can inject a rogue pool that joins the signer's authorization tree and drains their wallet - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The analog of path traversal — an unvalidated user-supplied locator being resolved against a trusted base — maps onto the controller's strategy-swap path: `swap_tokens` forwards a caller-supplied `swap` byte blob verbatim to the configured router, and the router invokes whatever pool/token addresses the payload names with no allowlist. A malicious route can place an attacker contract on the call stack beneath the victim's `require_auth` tree; any `token.transfer(victim, attacker, ...)` that contract performs is recorded by simulation as a child of the victim's `swap_collateral` authorization entry and executes once the victim signs the simulated tree. The stolen amount is unbounded by the routed funds or the risk gates.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` calls `router.execute_strategy(&controller, &amount_in, swap)` with the raw `StrategySwap` bytes supplied by the caller of `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply`. It guards only the controller's own funds: it authorizes exactly one `token_in` transfer of `amount_in` (`swap.rs:34`), asserts `in_after <= in_before` and `actual_spent <= amount_in` (`swap.rs:42-48`), refunds the leftover, and requires positive measured output (`swap.rs:75-83`). Nothing validates which contract addresses the route invokes.

The threat model states this plainly: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization. A token transfer that such code makes from the caller is recorded by an honest simulation as a child of the caller's authorization entry, and it executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount" (`docs/explanation/threat-model.md:154-161`).

The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves it end-to-end through the real `swap_collateral` entrypoint: `RogueHopPool::swap` calls `token::Client::transfer(&victim, &to, &amount)` (`lines 62-71`), and the recorded auth tree shows the wallet-draining transfer as a child of Alice's `swap_collateral` invocation (`lines 206-222`), after which `assert_eq!(s.wallet(&s.alice), 0)` (`line 224`).

### Impact Explanation
Theft of user funds beyond the protocol's accounting. The victim's `swap_collateral` signature — which a client obtains by simulating the transaction — silently authorizes an arbitrary `transfer` of any token from the victim's address to the attacker. Neither `amounts[min_out]`, `RouterOverspend`, `NoSwapOutput`, nor the post-swap health-factor gate bounds the loss, because the stolen funds are the victim's wallet balance, not routed or collateral funds. The victim can even receive a fair swap output while being drained (`line 226` asserts the full fair ETH output is credited).

### Likelihood Explanation
Medium. It requires user interaction (the victim must sign a poisoned route, e.g., served by a compromised or malicious quote source — matching the CVE's UI:R profile), and the theft is visible in the simulated auth tree to a client that decodes it. But the protocol pushes the entire verification burden onto off-chain clients; an unprivileged attacker only needs to get a victim to submit one crafted `swap_collateral(account_id, token_in, amount, token_out, route)` call. No privileged role, leaked key, or protocol misconfiguration is needed.

### Recommendation
Constrain routes at the trust boundary rather than relying on client-side auth-tree inspection: maintain an on-chain allowlist of vetted pool/venue contracts the router may invoke (rejected by the rules as a fix to router internals — alternatively, have the controller reject routes whose declared venue set is not a governance-approved subset), and ship/enforce the documented client-side check that refuses to sign any authorization tree containing children other than the single expected input `token_in.transfer(sender, router, total_in)`.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Attacker deploys `RogueHopPool` with plan `(victim=Alice, wallet_token, to=attacker, amount=WALLET_BALANCE)` (`lines 56-60`).
2. Attacker crafts a route naming that pool as the hop venue; a router double calls `env.invoke_contract(&route.hop_pool, "swap", ...)` (`line 44`) — matching the production router's no-allowlist dispatch.
3. Alice calls `swap_collateral(alice, account_id, USDC, SWAP_IN_USDC, ETH, route)` (`lines 150-157`).
4. During simulation, `RogueHopPool::swap` executes `wallet_token.transfer(Alice, attacker, WALLET_BALANCE)`, recorded as a sub-invocation of Alice's `swap_collateral` auth entry (`lines 206-222`).
5. Alice signs the simulated tree; on execution her entire `WALLET_BALANCE` moves to the attacker while she still receives the fair `ETH` swap output (`lines 224-226`).
