### Title
Solver-selection signature does not bind fill output amounts, allowing a selected solver to bait-and-switch to the minimum required output - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
When `solverSelection` is enabled, the user's session key signs `SelectSolver(commitment, solver)` — only the order commitment and the solver's *address*, not the output amounts the solver quoted during the off-chain auction. `fillOrder` re-derives `keccak256(abi.encode(msg.sender, order.session))` and checks it against the transient-storage value written by `_select`, but this check only authenticates *which address* may fill — it places no constraint on the `FillOptions.outputs` supplied at fill time beyond the order's own minimum (`order.output.assets`). A solver who won the auction with a high bid can therefore call `fillOrder` with outputs equal to the bare minimum required by the order, taking the escrowed input at the price the user picked them for while delivering only the floor amount.

### Finding Description
The selection binding is built in `IntentsBase._select`: [1](#0-0) 

Only `(commitment, solver)` is signed and stored (`selectionHash = keccak256(abi.encode(options.solver, sessionKey))`). The actual output amounts the solver promised during the Hyperbridge auction (conveyed off-chain via the coprocessor/bid mechanism, see `sdk/packages/sdk/src/protocols/intents/Bid.ts`) are never included in this commitment.

`fillOrder` then only re-checks `msg.sender`/`order.session` against that stored hash: [2](#0-1) 

`options.outputs` (the actual amounts delivered) is caller-supplied calldata at fill time, and the contract's only constraint on it is `solverAmount >= totalRequired` (`order.output.assets[i].amount`, fixed by the user at `placeOrder` time as the floor) — enforced deep in `_fillSameChain`/cross-chain fill logic:



So the user's off-chain selection process ("I pick solver X because they quoted 100 DAI") is not cryptographically bound to that quoted amount. Once selected, solver X is free to call `fillOrder` with outputs at the order's floor (e.g. the minimum acceptable amount set at placement) instead of the higher amount that won the auction — a direct structural analog of the RFP report: the winning bid can be swapped for a worse one at the moment of execution because the selection/acceptance step and the value-bearing step are not atomically bound to the same number.

The `FillOptions.validUntil` field even documents awareness of a related but distinct risk (a stale quote being executed later), but that field only bounds *when* the fill can happen, not *what amount* it must deliver: [3](#0-2) 

### Impact Explanation
Users relying on `solverSelection` to pick the "best bid" among competing solvers get no on-chain guarantee that the selected solver's fill will match the promised amount. Because the whole point of solver selection is to let users pick the highest quote, a solver can win selection with an inflated quote and then deliver only the order's floor amount, silently capturing the difference between the promised and minimum output — a bait-and-switch that fully undermines the auction mechanism and results in the user receiving less than they were led to expect, while the solver still claims the full escrowed input. This is a concrete asset-value loss to the order placer/beneficiary, reachable by any solver in the intent-fill path (unprivileged, single transaction).

### Likelihood Explanation
High. Any solver participating in the auction can exploit this by simply calling `fillOrder` with `options.outputs` set to the order's minimum instead of their quoted amount, once they know (or are told/see on Hyperbridge) they've been selected. No special timing, front-running, or privileged access is required — the vulnerability is that the selection signature simply never bound the promised amount in the first place, so *any* selected solver's honest cooperation is required for the auction to work as intended; nothing on-chain enforces it.

### Recommendation
Include the promised output amounts (and any other economically material bid terms) in the `SELECT_SOLVER_TYPEHASH` struct signed by the session key, e.g. `SelectSolver(bytes32 commitment, address solver, bytes32 outputsHash)`, and have `fillOrder` recompute `outputsHash` from `options.outputs` and require it to match what was signed, in addition to the existing solver/session check. This atomically binds the winning bid amount to the fill, closing the bait-and-switch window analogous to the referenced `RFPSimpleStrategy.allocate()` issue.

### Proof of Concept
1. User places an order via `placeOrder` with `order.output.assets[i].amount = 100` (minimum) and enables `solverSelection`.
2. Off-chain, Solver A bids 1000 (via the coprocessor auction). The user picks Solver A based on that quote and has their session key sign `SelectSolver(commitment, solverA)` (per `IntentsBase._select`/`SELECT_SOLVER_TYPEHASH`).
3. Solver A (or anyone able to submit on their behalf) calls `select(options)` and then `fillOrder(order, FillOptions{outputs: [100]})` in the same transaction — passing only the floor amount, not the promised 1000.
4. `fillOrder`'s selection check only compares `keccak256(abi.encode(msg.sender, order.session))` against the stored hash from step 2/3 — it never checks that `options.outputs` matches 1000, per `evm/src/apps/IntentGatewayV2.sol` lines 464-483 and `evm/src/apps/intentsv2/IntrinsicIntents.sol` lines 65-78.
5. The fill succeeds with only 100 delivered; Solver A claims the full escrowed input priced for a 1000 bid, at the user's expense.

    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }
