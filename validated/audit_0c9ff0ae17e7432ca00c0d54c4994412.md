### Title
Unsafe raw ERC20 `transfer` calls in Tron `IntentGatewayV2` ignore return-data, allowing silent transfer failure and permanent freezing/loss of escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) escrows arbitrary, user-specified ERC20 tokens via `placeOrder` and later releases them to solvers/beneficiaries via `withdraw()` and to dust-sweep beneficiaries via `handleIsmpMessage`'s `SweepDust` branch. Unlike the main EVM `IntentGatewayV2.sol`, which consistently uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (see [1](#0-0) ), the Tron contract instead makes raw low-level `.call()`s to `IERC20.transfer` and only checks the outer `success` boolean from `.call()`, never decoding/validating the ABI-encoded `bool` return value.

### Finding Description
In `withdraw()` and the `SweepDust` handler of `evm/tron/contracts/apps/IntentGatewayV2.sol`, outbound token payouts are done like this: [2](#0-1) 

and in the dust-sweep branch of `handleIsmpMessage`: [3](#0-2) 

Both call sites do `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...)); if (!success) revert TransferFailed();`. This only verifies that the external call did not revert — it does **not** inspect the returned data to confirm the token itself reports `true`. Per EIP-20, a compliant token *may* return `false` on failure instead of reverting (this is exactly the class of non-standard token cited in the source report, e.g. old-style implementations, or any custom ERC20 used inside an intent order since `IntentGatewayV2` accepts arbitrary caller-supplied token addresses in `Order.inputs`/`Order.output.assets`/`body.tokens`). If such a token returns `false` (call succeeds, `success == true`, but no balance actually moved), the escrow accounting (`_orders[commitment][token] -= amount` at line 710, or the dust-sweep event at line 680) is updated as if the transfer succeeded, while the recipient never received the tokens.

This is worse than the same-pattern used only for the fee-token release path elsewhere; the accompanying `IntentGatewayV2.sol` (main/non-Tron) mitigates the entire class by uniformly using `safeTransfer`/`safeTransferFrom` via `using SafeERC20 for IERC20;`, e.g. [4](#0-3) , but the Tron contract only applies `safeTransferFrom` on the *inbound* escrow path (line 405) and reverts to raw, return-data-blind calls on the *outbound* payout paths (`withdraw`, `SweepDust`).

### Impact Explanation
Any order that escrows a non-standard ERC20 (one that returns `false` on failed transfer rather than reverting) can result in the contract believing it has paid out escrowed funds to the solver/beneficiary (via `RedeemEscrow`/`RefundEscrow`) or swept dust, decrementing internal accounting and emitting `EscrowReleased`/`EscrowRefunded`/`DustSwept`, while the tokens remain permanently stuck in the `IntentGatewayV2` contract with no accounting entry left to reclaim them (since `_orders[body.commitment][token]` was already decremented to zero, or dust was "swept" without being sent). This is a concrete, unrecoverable freezing/loss of escrowed user/solver funds reachable by any user simply placing an order with such a token, or triggered by whichever ERC20 the Hyperbridge-authenticated dust-sweep message references — no privileged access needed to trigger the loss path once such a token is in use.

### Likelihood Explanation
Likelihood is medium: it requires the escrowed/output token to be a non-standard ERC20 that returns `false` instead of reverting on failed transfer (a known and still-encountered pattern among older or non-audited tokens), or a transient failure condition on such a token (e.g., paused-but-returns-false tokens, blacklist tokens). Because `IntentGatewayV2` is explicitly designed to support arbitrary user-supplied ERC20 addresses for orders, this is fully within the normal, unprivileged transaction flow (`placeOrder` → cross-chain `RedeemEscrow`/`RefundEscrow` → `withdraw`), not a contrived edge case.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` (lines 706, 720) and the `SweepDust` handler (line 674) with `IERC20(token).safeTransfer(beneficiary, amount)` using OpenZeppelin's `SafeERC20`, exactly as already done for the inbound path (`safeTransferFrom` at line 405) and as done throughout the main `evm/src/apps/IntentGatewayV2.sol`/`IntentsBase.sol`. This ensures both call-revert and false-return failures are treated uniformly as failures, preventing state from being finalized on a no-op transfer.

### Proof of Concept
1. Deploy a mock ERC20 whose `transfer` function returns `false` (instead of reverting) whenever, e.g., the recipient is blacklisted or a fee condition isn't met — this mirrors real non-standard tokens.
2. A user calls `placeOrder` on `evm/tron/contracts/apps/IntentGatewayV2.sol` escrowing this token via the inbound `safeTransferFrom` path (which succeeds normally).
3. A cross-chain `RedeemEscrow` (or `RefundEscrow`) request arrives and is routed to `withdraw()`; the mock token's `transfer(beneficiary, amount)` call returns `false` but does not revert, so `success == true` at line 706.
4. `_orders[body.commitment][token] -= amount` executes, `EscrowReleased`/`EscrowRefunded` is emitted, and the beneficiary balance never changed — funds are now stuck in the gateway contract with no live escrow entry to claim them via any other code path.
