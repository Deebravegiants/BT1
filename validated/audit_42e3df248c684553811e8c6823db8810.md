The claim is accurate: `isReplay` and `recordUsage` in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go` are indeed two separate lock-acquiring operations with no atomic check-and-set, exactly as cited, and this pattern differs from the atomic `CheckAndRecord` used in `core/capabilities/vault/request_replay_guard.go` [1](#0-0) [2](#0-1) . The `Authorize` function reads `isReplay` and only later, after synchronous business logic, calls `recordUsage`, leaving a genuine TOCTOU window [3](#0-2) . Audit Report

## Title
JWT replay-protection check-then-act race allows single-use HTTP trigger tokens to be reused for concurrent requests - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize`, the authorization gate for externally-supplied HTTP-trigger JWTs, checks single-use status via `jwtCache.isReplay(claims.ID)` and, only after unrelated authorized-key validation, marks the token used via `jwtCache.recordUsage(claims.ID)`. Because these are two separate lock-acquiring operations rather than one atomic check-and-insert, two concurrent requests presenting the identical JWT can both pass the replay check before either records usage, defeating the single-use guarantee.

## Finding Description
`Authorize` verifies the JWT, then calls `h.jwtCache.isReplay(claims.ID)` under an `RLock`, and later — after independent business logic (workflow-ID lookup and signer authorization) — calls `h.jwtCache.recordUsage(claims.ID)` under a separate `Lock`. `isReplay` and `recordUsage` are each their own critical section with no shared atomicity between the read and the write. This is a textbook check-then-act TOCTOU: any two goroutines/requests carrying the same `jti` can both observe "not yet used" in `isReplay` before either calls `recordUsage`, allowing both to pass. This is confirmed directly from the code, and the codebase itself demonstrates awareness of the correct pattern elsewhere — `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go` performs the existence check and insertion inside a single mutex-protected critical section, which `jwtReplayCache` does not do.

## Impact Explanation
This breaks the documented single-use guarantee of the JWT-based HTTP trigger authorization path, allowing a workflow-owner-issued, single-use trigger token to be used to invoke the same workflow execution more than once via concurrent requests. This maps to the in-scope "unauthorized job run" impact category — the caller has one legitimately obtained valid JWT but can cause duplicate/unauthorized executions beyond what the token was intended to authorize.

## Likelihood Explanation
Exploitation only requires an unprivileged caller who already possesses one valid signed JWT (a normal artifact for HTTP-triggered workflow clients) and the ability to fire multiple requests with that identical token concurrently over the network — no special privileges, credentials, or host access are required, and the race window is realistically hittable given network round-trip timing.

## Recommendation
Make the replay check and usage recording atomic by merging `isReplay`/`recordUsage` into a single method (e.g., `CheckAndRecord(jti string) error`) that performs the existence check and map insertion within one critical section while holding a single `Lock` (not `RLock` then `Lock`), mirroring the existing correct pattern in `RequestReplayGuard.CheckAndRecord`. Update `Authorize` to call this single atomic method in place of the separate `isReplay`/`recordUsage` calls.

## Proof of Concept
1. Obtain one valid signed JWT (`jti = X`) authorized for a workflow ID via the HTTP trigger method.
2. Concurrently fire two `HandleUserTriggerRequest` gateway requests using the identical JWT (e.g., two goroutines both calling `WorkflowMetadataHandler.Authorize(workflowID, token, req)` with the same token).
3. Both goroutines call `h.jwtCache.isReplay(X)`; if scheduled such that both execute before either reaches `recordUsage`, both return `false`.
4. Both requests pass authorization and trigger workflow execution, demonstrating the single-use token executes the workflow more than once — reproducible as a Go unit test directly against `jwtReplayCache`/`WorkflowMetadataHandler.Authorize` using two goroutines synchronized to call `isReplay` before either calls `recordUsage` (e.g., using a barrier/WaitGroup to force the interleaving).

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()

}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
