### Title
RAY-valued market totals can overflow `i128` before the borrow-index cap, permanently freezing the market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
Interest accrual converts aggregate scaled supply and debt back into RAY values before applying the borrow-index ceiling, so a sufficiently large market can reach an `i128` value overflow while `borrow_index` is still below `MAX_BORROW_INDEX_RAY`. [1](#0-0) [2](#0-1)  Once that occurs, the same accrual runs before ordinary pool mutations and repeatedly panics, preventing withdrawals and repayments. [3](#0-2) [4](#0-3) 

### Finding Description
`Controller::update_indexes` is callable by an authorized but otherwise unprivileged caller and forwards the supplied `Vec<HubAssetKey>` to the pool. [5](#0-4) [6](#0-5)  The pool's `update_indexes` path loads each market and calls `interest::global_sync`, which splits elapsed time into chunks and executes `accrue_step` for every chunk. [7](#0-6) [8](#0-7)  `accrue_step` evaluates `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` before calculating utilization, the new rate, and the capped borrow index. [1](#0-0)  The mul-div helper widens the intermediate product to `I256`, but still requires the final RAY quotient to fit in `i128`; an unrepresentable quotient returns `None` and `mul_div_half_up` raises `MathOverflow`. [9](#0-8) 

The admitted cap only ensures that the token amount's asset-to-RAY representation fits `i128`; it does not ensure that `scaled_amount * index / RAY` remains representable after interest accrues. [10](#0-9) [11](#0-10)  The borrow-index ceiling is applied only inside `update_borrow_index`, after the aggregate value calculation has already overflowed. [2](#0-1) [12](#0-11) 

### Impact Explanation
This is a permanent freezing of user funds and can also freeze unclaimed protocol revenue: after the aggregate RAY value crosses `i128::MAX`, every pool mutation that first syncs interest reaches the same panic. [3](#0-2) [8](#0-7)  The repository's regression test explicitly demonstrates that a valid large market reaches `MathOverflow` before `MAX_BORROW_INDEX_RAY`, after which both a withdrawal and a repayment fail. [4](#0-3)  Because the panicking call is rolled back before `last_timestamp` can advance, later transactions start from the same stale state and fail again rather than recovering. [8](#0-7) [13](#0-12) 

### Likelihood Explanation
Triggering the condition requires a very large market and sustained high utilization, so it is not reachable with ordinary balances. [14](#0-13)  However, the tested sizes are inside the protocol's admitted cap domain, and the triggering transaction itself is the permissionless controller `update_indexes` call. [10](#0-9) [5](#0-4)  Once the market is near the cliff, any user can advance the ledger naturally and submit `update_indexes(caller, vec![hub_asset])`; the overflow is caused by stored aggregate shares and indexes rather than a malformed argument or privileged parameter. [13](#0-12) [1](#0-0) 

### Recommendation
Make accrual total-value calculations overflow-safe instead of requiring the resulting RAY value to fit in `i128`. [15](#0-14) [16](#0-15)  In particular, `accrue_step` should calculate utilization and interest using `I256` values, or detect that the borrow index has reached `MAX_BORROW_INDEX_RAY` and skip further debt growth rather than revaluing the full book. [17](#0-16) [2](#0-1)  The market should also enforce a cap based on both token units and the current index headroom, and repayment or withdrawal should retain an emergency path that does not require a doomed aggregate accrual. [10](#0-9) [3](#0-2) 

### Proof of Concept
The in-repository test constructs an 18-decimal market, supplies `1_000_000_000 * 10^18` base units, borrows 98% of it, advances ledger time in one-year chunks, and calls `update_indexes` until `MATH_OVERFLOW` occurs. [18](#0-17)  The asserted postcondition shows that the stored `borrow_index` remains below `MAX_BORROW_INDEX_RAY`, while subsequent `withdraw` and `repay` calls fail with the same overflow. [19](#0-18) 

```rust
// Triggering transaction after the market reaches the overflow boundary:
controller.update_indexes(
    attacker,
    vec![&env, HubAssetKey {
        hub_id,
        asset: large_market_asset,
    }],

// -> pool::update_indexes -> market::accrue -> global_sync
// -> accrue_step -> scaled_to_original(borrowed, borrow_index)
// -> MathOverflow before update_borrow_index can clamp to MAX_BORROW_INDEX_RAY
```

The call chain is `Controller::update_indexes` → `pool_update_indexes_call` → pool `market::accrue` → `global_sync` → `accrue_step` → `scaled_to_original`. [5](#0-4) [13](#0-12) [15](#0-14)

```rust
/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {

        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);

        assert!(
            years <= 40,
```

```rust
/// per market.

/// Always commits state so same-ledger simulation records the write footprint

        interest::global_sync(env, &mut cache);
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```

```rust
/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
}
```
