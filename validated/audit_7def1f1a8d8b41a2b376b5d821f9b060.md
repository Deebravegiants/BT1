### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the request body, then trusts the unsigned `X-Shopify-Shop-Domain` / `X-Shopify-Topic` headers as the tenant identity passed to the app's handler. This is the same class of bug described in the report: a field that is acted upon (`shop`) is not covered by the integrity check (`hmac`) that is used to authorize the request.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are never included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `to_signable_string` (the body) only and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` gates entirely on this body-only HMAC check, and then forwards the *unsigned* `request.shop` and `request.topic` values into `WebhookMetadata`, which is handed to the host app's handler as the authenticated identity of the webhook: [4](#0-3) 

The binding that should hold is:
`shop used by handler == shop cryptographically bound to this specific signed payload`

but the implementation only guarantees:
`hmac-verified bytes == raw_body` while `shop header == whatever the client sent, unverified`.

Because the signature never covers the shop/topic headers, two different (shop, topic) header values can be paired with the *same* signed body and both will pass `HmacValidator.validate`. Any party capable of obtaining one validly-signed webhook delivery (e.g., a merchant who installs the app on their own store, or anyone who can observe a webhook payload/HMAC pair in transit) can replay that exact body with a different `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to the app's webhook endpoint. The gem will report the request as HMAC-valid, and `WebhookMetadata.shop`/`.topic` will reflect the attacker-chosen values, not the values the signature actually vouches for.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as returned by this gem) to key per-merchant state — e.g., to decide which shop's records to update/delete, or to route `customers/redact`, `shop/redact`, `orders/*` payloads to the correct tenant — an attacker can cause the app to associate a validly-signed body with an incorrect shop identity. This is a cross-tenant identity-binding break: the app believes "this data came from shop X" purely because the gem said HMAC validation passed, when in fact only the body (not the shop claim) was verified. Depending on how the host app trusts `data.shop`, this can lead to writing/deleting data under the wrong tenant, or triggering privileged compliance actions (e.g., redact/data-request handlers) against the wrong shop — a cross-tenant access issue.

### Likelihood Explanation
Reachability requires only a normal (unprivileged) HTTP client that can POST to the app's public webhook endpoint and possesses one legitimately-signed webhook payload (trivially obtainable by installing the app on any store, including the attacker's own, or via traffic observation) plus knowledge of another shop's domain (public information — myshopify.com shop names are not secret). No access to `api_secret_key`, access tokens, or any privileged credential is required, and no interception of Shopify infrastructure is needed — the vulnerable behavior is entirely inside `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`, in scope for this gem.

### Recommendation
Bind the identity fields into the signed message, or otherwise cryptographically tie the header-derived `shop`/`topic` to the request before trusting them:
- At minimum, document/enforce that `WebhookMetadata#shop` and `#topic` are **not** authenticated by `HmacValidator.validate` and must be independently corroborated (e.g., against a known/installed shop list) by the host application before being used for tenant-scoped actions.
- Alternatively, extend `Webhooks::Request#to_signable_string` to include a canonicalized representation of the identity headers (shop, topic, webhook_id) so that tampering with them invalidates the HMAC, matching the recommendation in the report to avoid mixing "verified bytes" with "acted-upon fields" that are outside the verified scope.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or otherwise captures) and receives a legitimate webhook delivery, e.g.:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-hmac-of-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   X-Shopify-Webhook-Id: ...
   Body: {"id": 1, "...": "..."}
   ```
2. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (`@raw_body`) — unchanged from step 1 — so validation succeeds: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {...}, ...)` — the app is told this order payload belongs to `victim-shop.myshopify.com`, even though the signature only ever certified the body, not the shop claim.
