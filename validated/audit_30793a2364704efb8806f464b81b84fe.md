### Title
Webhook `shop` field is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, never the `shop-domain` header. `Utils::HmacValidator.validate` therefore authenticates *only the body bytes*, not the shop the event is attributed to. `Registry.process` accepts the request once the body-only HMAC passes and forwards the unauthenticated `shop` header straight to the app's webhook handler as trusted tenant identity.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [2](#0-1) 

Note `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is read independently and is **not** included in `to_signable_string`, which returns only `@raw_body`.

`Utils::HmacValidator.validate_signature` computes and compares the signature against `verifiable_query.to_signable_string` only: [3](#0-2) 

`Registry.process` gates on this body-only HMAC, then trusts `request.shop` for tenant attribution when invoking the handler: [4](#0-3) 

This is the equality the code is supposed to enforce but does not:
`HMAC_verified(shop_header) == shop_used_by_handler`

Before the request: `shop_header` is attacker-controlled, unauthenticated. `HMAC` covers only `raw_body`.
After validation "passes": the library still emits `WebhookMetadata` with `shop: request.shop`, i.e. the unauthenticated header value, as if it had been cryptographically bound to the verified body.

Concretely, an unprivileged internet user who owns any shop that has the target app installed (trivial — anyone can install a public app on their own free/dev store) can:
1. Trigger a webhook event on their own shop (e.g. `orders/create`), capturing the genuine `raw_body` and its valid `x-shopify-hmac-sha256` value computed by Shopify with the app's `client_secret`.
2. Replay that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint, but with the `x-shopify-shop-domain` header changed to the victim shop's domain.
3. `HmacValidator.validate` passes (body and HMAC are untouched and genuinely valid), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain.

Any host application that uses `data.shop` for tenant routing/attribution (exactly as instructed in this gem's own docs and example handler) will process the attacker's own webhook payload under the victim shop's identity — a cross-tenant identity binding break in the library's core webhook-processing surface.

### Impact Explanation
Critical — cross-tenant access. The library documents `Registry.process` as verifying "the request did indeed come from Shopify" [5](#0-4) , and ships an example handler that keys all downstream processing off `data.shop` [6](#0-5) . Because `shop` is never bound to the HMAC, any host app following this gem's documented pattern can be made to attribute attacker-controlled webhook content/events to an arbitrary victim shop, corrupting per-tenant state, queues, or side effects keyed by `data.shop`.

### Likelihood Explanation
High. No secrets are required — only a body/HMAC pair from any shop with the target app installed (trivially obtainable by installing a free/dev app instance), plus the ability to POST to the app's public webhook URL with custom headers, which is inherent to how webhook endpoints work.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified signable content, or otherwise cross-check the header-supplied `shop` against an independently-verified source (e.g., look up the shop via the registered webhook subscription/session rather than trusting the header) before passing it to `WebhookMetadata`. At minimum, document prominently that `shop` is unauthenticated and must not be used for tenant attribution without independent verification.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop "attacker.myshopify.com"
#    and triggers e.g. an orders/create event, capturing the real delivery:
raw_body = '{"id":123,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)
# (attacker doesn't know app_client_secret, but Shopify computed and delivered this HMAC
#  to the attacker's own webhook endpoint/log for their own shop)

# 2. Attacker replays the untouched (raw_body, hmac) pair to the target app's public
#    webhook endpoint, only swapping the shop-domain header to the victim:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # untouched, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The host app now processes attacker-controlled data under the victim's tenant identity.
```
