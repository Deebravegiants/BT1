### Title
Webhook `shop` (and `topic`/`webhook_id`) header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read directly from unauthenticated HTTP headers and are never incorporated into the signed content. `ShopifyAPI::Webhooks::Registry.process` validates only that `hmac(raw_body)` matches, then dispatches the handler using `request.shop`/`request.topic` taken from those unverified headers. This breaks the identity binding the bug-class hints at: `hmac_valid(raw_body) == true` should imply `shop == the shop that produced this exact webhook`, but it does not — the header value is free to differ from the value used to derive the HMAC.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from caller-supplied headers with no cryptographic tie to the body/HMAC: [2](#0-1) [3](#0-2) 

`Registry.process` verifies only the body HMAC and then trusts `request.shop`/`request.topic` for dispatch: [4](#0-3) 

`HmacValidator.validate` computes the HMAC purely from `to_signable_string` (i.e., the body) and compares it to the header-supplied HMAC — it has no knowledge of, and does not bind, the shop-domain header: [5](#0-4) 

Because the shop field is "acted on" (used to build `WebhookMetadata` and route to shop-specific logic) but not covered by the HMAC that authenticates the request, any unprivileged internet user who obtains one legitimately-signed `(raw_body, hmac)` pair for a given topic — trivially available by installing the app on their own free development store and triggering the event themselves — can replay that exact body+hmac to the app's public webhook endpoint while substituting an arbitrary victim `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` invokes the registered handler with `shop: <victim-shop>`.

### Impact Explanation
This is a cross-tenant boundary violation supplied entirely by the gem's own verification logic (not a host-app misuse of undocumented behavior): the gem exposes `Registry.process`/`HmacValidator.validate` as the sanctioned way to authenticate a webhook, and that authentication does not bind the `shop` identity it hands to the handler. Since `MANDATORY_TOPICS` includes GDPR-sensitive topics like `shop/redact` and `customers/redact`, and ordinary handlers key their side effects (data sync, deletion, session invalidation, etc.) off `WebhookMetadata#shop`, an attacker can cause the app to perform shop-specific processing against a shop they do not control, using data/signature material from a shop they do control. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own instance of the app installed on any shop (a normal, unprivileged action), (2) triggering or observing one webhook delivery for a topic of interest, and (3) sending that captured body+HMAC to the target app's public webhook endpoint with a forged shop-domain header. No knowledge of `api_secret_key` or any victim credential is needed — an attacker never needs to compute a valid HMAC for the forged shop, only replay one they already legitimately received.

### Recommendation
Include the shop-domain (and topic) in the signed/verified content, or otherwise cryptographically or out-of-band bind the header-derived `shop` value used for dispatch to the HMAC verification path, e.g., by requiring the consuming application to cross-check `request.shop` against a shop for which a session is already known/expected, and by documenting/enforcing that `shop` must not be treated as authenticated purely because `HmacValidator.validate` returned true.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a legitimate webhook, e.g. for topic `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for secret `S`).
2. Attacker POSTs to the app's webhook endpoint:
   - Body: `B` (unchanged)
   - Headers: `X-Shopify-Hmac-Sha256: H` (unchanged), `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: victim.myshopify.com` (forged)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(S, B)` and matches `H` — validation succeeds.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied order data as if it belonged to `victim.myshopify.com`.
