### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing cross-tenant request forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers. `Registry.process` trusts these header-derived values to dispatch the webhook and to populate `WebhookMetadata` passed to the host application's handler, without the HMAC ever binding them to the signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` calls `Utils::HmacValidator.validate(request)` — which only checks the body — and then unconditionally trusts `request.shop` and `request.topic` to look up the handler and build `WebhookMetadata`: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated string field handed to the host application's `WebhookHandler#handle`: [5](#0-4) 

This is the exact identity-binding violation described in the analog hint ("a field acted on but not covered by the HMAC"). It is also directly contradicted by this gem's own OAuth `AuthQuery`, which — correctly — includes `shop` and `host` inside the signed string: [6](#0-5) 

Because the app's `api_secret_key` is shared across *all* shops installed on the app, any merchant (an "unprivileged" tenant relative to other merchants) can trigger Shopify to send them a real, validly-signed webhook for their own store. Since the HMAC covers only the JSON body, the attacker can capture a genuine `(body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with any victim shop domain / topic of their choosing. `HmacValidator.validate` still passes because the body is byte-for-byte unchanged, yet `Registry.process` will dispatch the payload to the handler tagged as having come from the victim shop and/or a different topic than actually occurred.

### Impact Explanation
This breaks the equality `shop authenticated by HMAC == shop delivered to the handler as the event's tenant`. Any downstream handler logic that trusts `WebhookMetadata#shop` to select per-tenant state, credentials, or authorization decisions (a common integration pattern) can be confused into acting on the wrong tenant's behalf using attacker-controlled body content signed under the attacker's own shop. This is a cross-tenant identity-confusion vector reachable by any unprivileged app-installing merchant, without needing the app's `api_secret_key`, access token, or any privileged access — satisfying the "cross-tenant access" criterion for High/Critical impact.

### Likelihood Explanation
Likelihood is high for any host application that installs a webhook handler and trusts `data.shop`/`data.topic` from `WebhookMetadata` for tenant-scoped actions (the intended and documented use of the field). The attacker only needs to run their own installed instance of the app (a normal, unprivileged merchant capability) to obtain a validly-signed `(body, hmac)` pair, then replay it with modified headers — no cryptographic secret is required to forge the `shop`/`topic` fields since they sit entirely outside the signed envelope.

### Recommendation
Extend the signed envelope to bind the identity headers to the HMAC (mirroring `Auth::Oauth::AuthQuery`), e.g. include `shop`, `topic`, `webhook_id`, and `api_version` in `Webhooks::Request#to_signable_string`, or otherwise validate that the actual Shopify HMAC computation for webhooks would need cooperation from Shopify's webhook signing scheme — since Shopify's real webhook HMAC is computed over the body only by design, the safer mitigation is for the gem to explicitly document/enforce that `shop`/`topic` must additionally be cross-checked against the body's own shop identifier where present, and/or that the gem should not expose these unauthenticated header fields as if they were verified, cryptographically-bound values in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Shopify sends a legitimate webhook to the app: body `B`, headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(secret, B)`.
3. Attacker intercepts/replays this exact request to the app's webhook endpoint, changing only the header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally `X-Shopify-Topic`).
4. `Webhooks::Request#hmac` and `#to_signable_string` are computed only from `B` (unchanged), so `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:26-31` returns `true`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:188-200` dispatches `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` to the host's handler, which now believes the event originated from `victim-shop.myshopify.com` despite the payload's cryptographic provenance being tied only to `attacker-shop.myshopify.com`.
