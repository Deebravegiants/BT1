### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied, unauthenticated `shop-domain` header straight to the app's handler as the tenant identity. The binding that should hold is `HMAC-verified bytes == identity attributed to the request`, but here `HMAC-verified bytes (raw_body) ⊂ identity fields used (shop, topic, webhook_id)`. A merchant who has installed the app (an unprivileged multi-tenant actor, not a privileged account) can capture a legitimately HMAC-signed webhook body generated from their own shop's events and replay it with a forged `shop-domain` header pointing at a different tenant, causing the app to process attacker-controlled data under another merchant's identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are never mixed into the signed material: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the body) against the shared `api_secret_key`: [3](#0-2) 

`Registry.process` runs that HMAC check and then immediately trusts `request.shop` (the unauthenticated header) as the tenant identity forwarded to the app's handler, with no cross-check that the body actually originated from that shop: [4](#0-3) 

Because the `api_secret_key` is the app's single client secret shared across every installing shop (not a per-shop secret), any merchant who has installed the app can trigger a webhook on their own store, capture the resulting `(raw_body, hmac)` pair — which will always validate — and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a victim shop's domain. `Utils::HmacValidator.validate(request)` still succeeds because it only checks `raw_body` against the secret, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the spoofed victim domain while `body` contains the attacker's data.

This breaks the identity binding `authenticated bytes (HMAC-verified raw_body) == shop the app attributes the event to`. Downstream, this is exactly the class of issue described in the external report: a piece of the operation (here, the tenant/shop identity, analogous to `totalSupplyAmount` not being accrued/bound before mutation) is acted upon without being covered by the verification step that is supposed to establish trust.

### Impact Explanation
Cross-tenant access: an app that uses `WebhookMetadata#shop` to select which merchant's session/store record to update, invalidate, resync, or delete (a common and expected use documented for `handler.handle(data:)`) can be made to apply attacker-supplied data to another merchant's tenant context in a single HTTP request, with no privileged credentials required — only that the attacker be an existing, unprivileged installer of the app. This matches the Critical bar of cross-tenant access.

### Likelihood Explanation
Any developer who installs the app for a shop can generate qualifying webhook traffic for that shop at will (e.g., by editing a product, creating an order, etc.), inspect the resulting `raw_body`/`X-Shopify-Hmac-Sha256` pair from their own endpoint logs, and replay it against the same endpoint with a forged `shop-domain` header — no secret material or elevated access is needed beyond being a normal app installer. This is a low-effort, repeatable, unauthenticated-header attack.

### Recommendation
Bind the shop/topic identity to the signed payload before trusting it: either (a) require the app-side webhook handler to independently look up and confirm that the shop named in the `shop-domain` header corresponds to a session/subscription the app itself created and expects for that topic/webhook_id, or (b) include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string (mirroring the OAuth `AuthQuery` pattern, where `shop` is included in the signed query) so that the identity fields cannot be swapped independently of the verified body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal, unprivileged onboarding).
2. Attacker triggers an event (e.g., updates a product with attacker-controlled JSON payload) that causes Shopify to send a legitimately HMAC-signed webhook to the app's endpoint for `attacker-shop.myshopify.com`.
3. Attacker's own server (or a proxy they control in front of the app) captures the exact `raw_body` and the `x-shopify-hmac-sha256` value from that request.
4. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` computes the HMAC over `raw_body` only and it matches, so `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)`, as shown at: [5](#0-4) 
6. Any app logic keyed off `data.shop` now operates on attacker-controlled data while believing it originates from `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
