### Title
Webhook shop identity (`x-shopify-shop-domain`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content solely from the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and then trusted downstream as the tenant identity for the webhook handler.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing an HMAC computed over `to_signable_string` against the supplied `hmac` [1](#0-0) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are all derived from HTTP headers that are never included in the signed material [3](#0-2) .

`Registry.process` validates only the HMAC and then immediately trusts `request.shop` and `request.topic` to construct the `WebhookMetadata` passed to the app's handler: [4](#0-3)  The `WebhookMetadata` struct carries `shop` as a plain field consumed by `WebhookHandler#handle` implementations [5](#0-4) .

This is the exact bug class from the external report, translated to this gem: "a field acted on but not covered by the HMAC." The equality that should hold is:
`bytes_verified_by_HMAC == bytes_the_handler_trusts_for_tenant_identity`
but instead:
`bytes_verified_by_HMAC (raw_body only) != bytes_the_handler_trusts_for_tenant_identity (shop header, unauthenticated)`

Because the app's `api_secret_key` is shared across all shops installed on a multi-tenant app, any merchant who has installed the app can obtain a legitimately-signed `(raw_body, hmac)` pair for their own store's webhook (e.g. by triggering a webhook on their own test/dev shop and capturing the delivered request). Since the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers are not part of the signed content, that attacker can replay the same body+HMAC pair while substituting a different value in the `x-shopify-shop-domain` header (or `x-shopify-topic`/`x-shopify-webhook-id`). `HmacValidator.validate` still succeeds because it only checks `raw_body`, and `Registry.process` will dispatch the attacker-controlled body to the handler labeled as coming from the victim shop of the attacker's choosing.

### Impact Explanation
This breaks the shop-identity binding that `Registry.process` implicitly relies on for correct request handling, allowing an authenticated-but-unprivileged app installer to make the host application process forged webhook data attributed to an arbitrary shop name/topic/webhook id, i.e. a cross-tenant confused-deputy condition inside the gem's webhook processing path. Depending on how the host app's `WebhookHandler#handle` implementation trusts `data.shop`/`data.topic` (e.g., to look up or mutate per-shop records, or to short-circuit topic-specific compliance handling such as `customers/redact`), this can lead to cross-tenant data corruption or bypass of shop-scoped logic — matching the "cross-tenant access" impact class.

### Likelihood Explanation
Exploitability requires the attacker to be a legitimate installer of the target app on at least one shop (to obtain one validly-signed body/HMAC pair from their own store) and the ability to send an arbitrary HTTP request to the app's webhook endpoint with forged Shopify headers — both are within reach of an "unprivileged internet user" who is simply an app user, since nothing on the gem side authenticates the header values. This is a design property of Shopify's webhook HMAC (body-only signing) that this gem faithfully passes through to `Registry.process`, so likelihood depends on the exact header trust assumptions of the host handler, which is outside the gem itself.

### Recommendation
`Webhooks::Request` should not present `shop`, `topic`, and `webhook_id` as part of the trusted request surface unless they are cryptographically bound to the payload. At minimum, the gem's documentation and `WebhookMetadata` should make explicit that `shop`/`topic`/`webhook_id` are unauthenticated header values and must not be used by handlers for authorization or data-scoping decisions without additional verification (e.g., cross-checking against a `Session` already established for that shop, or requiring the app to independently confirm the shop is one it has installed and that the topic matches what was registered for the delivered `webhook_id` via Shopify's Admin API).

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on `victim-shop.myshopify.com` (both use the same app `api_secret_key`).
2. Attacker triggers a webhook on their own shop (e.g., `orders/create` with attacker-controlled order payload `raw_body`), capturing the legitimately Shopify-signed `x-shopify-hmac-sha256` header for that exact `raw_body`.
3. Attacker POSTs directly to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [6](#0-5) , `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the secret [1](#0-0) , and `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: attacker_payload, ...)` to the app's handler [4](#0-3) , which now processes attacker-controlled data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
