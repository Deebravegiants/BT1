### Title
Webhook Shop-Domain Identity Spoofing via Unauthenticated Header Not Covered by HMAC - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` documents that it "will verify the request did indeed come from Shopify" before invoking the app's handler with a `WebhookMetadata` struct that includes `shop` — "The shop domain of the webhook" [1](#0-0) [2](#0-1) . In reality, the HMAC signature only covers the raw request body, never the `shop-domain` (or `topic`/`webhook-id`) header, so the `shop` value handed to the app's handler is never actually authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) . The `shop` accessor, however, is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header and is never included in what gets HMAC-verified: [4](#0-3) .

`Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string` and compares it against the `hmac-sha256` header value: [5](#0-4) . Since `to_signable_string` for webhook requests is just the raw body, this check only proves the body bytes were signed by someone possessing `Context.api_secret_key` — it proves nothing about which shop the header claims to be from.

`Registry.process` then raises only if the HMAC fails, and otherwise builds `WebhookMetadata` using `request.shop` verbatim, handing it to the app's handler as an authenticated tenant identifier: [6](#0-5) . The documented example explicitly uses `data.shop` to key application data (`shop_domain: data.shop`) [7](#0-6) .

Critically, `Context.api_secret_key` (the app's `client_secret`) is a single, app-wide secret shared across every shop that installs the app — it is not shop-specific. Any user who installs the app on their own shop (an ordinary, unprivileged action for any public app) legitimately receives webhook deliveries HMAC'd with that same shared secret. Because the header carrying the shop identity is excluded from the signed content, that same attacker can capture one such legitimately-signed webhook (body + valid `hmac-sha256`) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to name a victim shop. `HmacValidator.validate` will still pass (the body and secret are unchanged), and `Registry.process` will dispatch the payload to the handler tagged with the victim's shop domain.

This breaks the identity binding: `shop authenticated by HMAC` ≠ `shop value trusted as the session/tenant key downstream`. The equality the gem implicitly promises — "HMAC-valid request" ⇒ "the `shop` field in `WebhookMetadata` is the true origin shop" — does not hold, because `shop` is parsed from bytes that were never verified.

### Impact Explanation
This is a cross-tenant identity-confusion vector: it lets one merchant (an unprivileged actor with respect to any other tenant) inject webhook events that the host application will process as belonging to a different, victim shop, since the gem's documented and only verification step (`HmacValidator.validate`) does not bind the `shop` field to the signed content. Any host app that follows the documented pattern of using `data.shop` to select which tenant's data to update (exactly as shown in the gem's own docs) is exposed to cross-tenant data corruption/injection. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that: (a) is installable by arbitrary shops (public/free apps, or any shop that can complete OAuth), and (b) has at least one webhook topic whose body content is static, predictable, or attacker-influenced (e.g., `app/uninstalled`, `shop/redact`, `app/scopes_update`, or topics with attacker-controlled resource content the attacker can trigger on their own store). The attacker only needs their own legitimate install to harvest a validly-signed body/HMAC pair, then reissue it with a different `shop-domain` header value — no access to `api_secret_key`, tokens, or the victim's credentials is required.

### Recommendation
Bind the claimed shop identity to the cryptographic verification: include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable string used for HMAC computation, or independently verify that the shop asserted in the header corresponds to a shop with an active, registered webhook subscription/session known to the app before trusting it. At minimum, update `Webhooks::Request#to_signable_string` to incorporate the shop-domain header so `HmacValidator.validate` actually authenticates the tenant, not merely the body bytes.

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key # same secret for every installed shop
body = "{}" # e.g. a topic whose payload is static/predictable, such as app/uninstalled

# Attacker's own shop legitimately receives this from Shopify:
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
legit_headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}

# Attacker replays the identical body+hmac but swaps the shop header:
forged_headers = legit_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only body is checked),
#    handler.handle receives WebhookMetadata with shop: "victim-shop.myshopify.com"
```
`HmacValidator.validate` succeeds because it only recomputes the HMAC over `body` [8](#0-7) , while `request.shop` is taken unchecked from the forged header [4](#0-3) , and `Registry.process` forwards it as-is to the handler [9](#0-8) .
