### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body [1](#0-0) . The `shop` identity that the gem hands to the app's webhook handler comes from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed material [2](#0-1) . This breaks the equality "shop asserted in the trusted header == shop cryptographically bound by the HMAC," letting anyone who obtains one valid `(raw_body, hmac)` pair replay it while relabeling the shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string using the shared `Context.api_secret_key` [4](#0-3) . The `topic`, `shop`, `api_version`, and `webhook_id` fields are all pulled straight out of unauthenticated headers [5](#0-4) , and `Registry.process` passes `request.shop` directly to the app-supplied handler as the tenant identity, without any additional verification [6](#0-5) .

Because a single `api_secret_key` (the app's `client_secret`) is shared across every merchant install of the app, any entity that has installed the app on any shop it controls (a normal, unprivileged action any internet user can perform for a public app) can trigger a real webhook delivery from Shopify, capture a valid `(raw_body, hmac)` pair, and then replay that exact body/HMAC combination against the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and `topic`/`webhook-id` headers) for a victim shop. The signature still validates because none of those headers are part of the signed bytes — only the body is checked, and the body can be attacker-chosen content from the attacker's own store.

The identity-binding break, expressed as an equality that is expected but false here:
`HMAC-verified(raw_body) == authenticated(shop_header)` — false, since `shop_header` is outside the HMAC's scope entirely.

### Impact Explanation
This is a cross-tenant confusion vector: the host application's webhook handler will process attacker-supplied topic/body content while believing it originates from an arbitrary victim shop (`data.shop` in the documented handler contract, see `docs/usage/webhooks.md`) [7](#0-6) . Depending on how the host app uses `data.shop` (e.g., to look up or mutate per-tenant records, trigger `customers/redact`/`shop/redact` compliance flows, or key background jobs as shown in the documented usage example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), this can lead to cross-tenant data corruption, spoofed compliance/GDPR webhooks, or forged business events attributed to a shop the attacker does not control. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only: (1) a public webhook HTTP endpoint reachable by any internet user (the gem's own documented integration pattern), and (2) one legitimately captured `(body, hmac)` pair, obtainable by any user who installs the target app on a shop they control — no privileged credentials, no access token, and no knowledge of `api_secret_key` is needed. The header-vs-signed-bytes gap is a structural property of `Request`/`HmacValidator`, not a misuse by the host app of a documented API, since the gem's own header parsing (`shopify_header`) is what silently accepts attacker-controlled `shop`, `topic`, and `webhook-id` fields.

### Recommendation
Bind the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) into the signed material — e.g., include them in `to_signable_string`, or require per-shop verification (compare `request.shop` against the shop of the session/registration expected to receive that topic) before invoking the handler in `Registry.process`.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop (`attacker-shop.myshopify.com`), a normal unprivileged action.
2. Trigger a webhook event with attacker-chosen body content (e.g., register `orders/create` and place a favorable test order), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header from Shopify's real delivery.
3. Replay that exact `raw_body` + `hmac-sha256` value to the app's public webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared `api_secret_key` [8](#0-7) ; `Registry.process` then calls the handler with `shop: "victim-shop.myshopify.com"` and the attacker's body content [9](#0-8) .
