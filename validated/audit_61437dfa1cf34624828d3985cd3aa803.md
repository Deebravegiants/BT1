### Title
Webhook shop-domain header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used downstream from an unauthenticated HTTP header, while `Utils::HmacValidator` (invoked by `Registry.process`) only verifies the raw request body against the HMAC. This breaks the binding: `shop asserted to handler` ≠ `shop bound by the cryptographic signature`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header without any cryptographic binding to that value [2](#0-1) . `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `to_signable_string` (the body) [3](#0-2)  and [4](#0-3) . After the HMAC check passes, `request.shop` is handed directly to the handler as the tenant identifier in `WebhookMetadata.new(topic:, shop: request.shop, ...)` [5](#0-4) .

Because the signature only covers the body, any request carrying a body+HMAC pair that was legitimately generated by Shopify for shop A remains valid even if the `shop-domain` header is changed to shop B. The equality the code implicitly assumes — `hmac-verified content` binds `shop` — does not hold, since `shop` is parsed from headers that sit outside the signed content.

### Impact Explanation
This is a cross-tenant identity-binding break (High/Critical class per the report criteria: "cross-tenant access"). In a multi-tenant app, an attacker who operates their own shop (a legitimate, low-privilege position — merely "install the app on your own store") can capture one authentic webhook delivery (raw body + valid `X-Shopify-Hmac-Sha256`) sent to their own endpoint, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header value for a victim merchant's domain. `HmacValidator.validate` still returns `true` (body unchanged), and `Registry.process` proceeds to invoke the registered handler with `shop: "<victim-shop>.myshopify.com"`. Any host application that uses the `shop` value from `WebhookMetadata` to look up per-tenant data, write to a tenant's records, or make authorization decisions will act on attacker-supplied data attributed to the victim's tenant — a cross-tenant data-injection/spoofing primitive.

### Likelihood Explanation
Moderate-to-high likelihood: it only requires the attacker to be a valid but unprivileged installer of the app on their own shop (no leaked credentials, no access token theft, no social engineering) to obtain one genuine, replayable body+HMAC pair, then craft an HTTP request with a different `shop-domain` header. No secret material is needed because the header is never part of the signed content.

### Recommendation
Bind the shop identity to the signed payload before trusting it: 
- Have `Request#to_signable_string` (or a separate verification step) include the `shop-domain` header value (and ideally `topic`) alongside the body so `HmacValidator` fails when it is altered, or
- Cross-check `request.shop` against the shop present in the parsed webhook body payload (Shopify webhook payloads generally embed shop/store identifying fields) before dispatching to handlers, or
- Document/require that consuming apps independently verify `shop` against a known, registered tenant list rather than trusting it implicitly from `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers a webhook for a topic the app handles.
2. Shopify delivers a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for body `B` under the app's `client_secret`), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays an HTTP request to the same webhook endpoint with the identical body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) , which succeeds because only the body is hashed [7](#0-6) .
5. The handler is invoked with `shop: "victim.myshopify.com"` [5](#0-4) , causing the host application to process attacker-controlled data as belonging to the victim tenant.
