### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the `X-Shopify-Hmac-SHA256` header against the raw request **body**. The `shop` identity that the gem hands to the app's handler (`data.shop`), along with `topic` and `webhook_id`, comes from separate HTTP headers that are never included in the signed material. This breaks the intended binding `authenticated_bytes == identity_bytes`.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from separate headers that are **not** part of `to_signable_string` and therefore not covered by the HMAC at all: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the identity passed to the app's handler, without any additional check that the `shop` header matches the body or any registered/expected shop: [4](#0-3) 

The identity binding the gem implicitly promises to the host app is:
`hmac_valid(body) == shop_header_is_authentic`

But the actual relationship implemented is:
`hmac_valid(body) == body_bytes_are_untampered` (unrelated to `shop_header`)

Because the app's `client_secret` (and therefore the webhook signing secret) is shared across **every shop that installs the app**, any unprivileged internet user can install a public app on their own store, receive a genuine webhook with a valid `body` + `hmac-sha256` pair for a topic that echoes attacker-controlled data (e.g. a webhook with a body they control, or any webhook topic at all since the signature covers only the body, not which shop it was for), and then replay that exact `body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to name a **different, victim shop**. `HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This is a **cross-tenant access** issue (Critical per the given classification): a party that only has legitimate access to their own shop's tenant data can forge webhook deliveries that the host application will process as if they originated from a different merchant's shop. Any app whose webhook handler acts on `data.shop` (e.g., looks up that shop's session/access token from storage keyed by `data.shop` and performs actions, or writes attacker-supplied body content into records associated with the victim's shop) can have its per-tenant isolation defeated, entirely through the API surface this gem exposes (`Webhooks::Request`, `Webhooks::Registry.process`), with no host-application misuse required — the host app is following the documented usage pattern exactly as shown in `docs/usage/webhooks.md`.

### Likelihood Explanation
Likelihood is realistic for any app that is publicly installable (which is the typical case for Shopify apps): an attacker only needs to install the target app on a shop they control to obtain a validly-signed `raw_body`/`hmac-sha256` pair, then can freely re-send that payload with a forged `shop-domain` header to the same public webhook endpoint. No access token, `client_secret`, or privileged account is required — only ordinary installation of the app, which is available to any unprivileged internet user for public apps.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the material that is authenticated, or otherwise cryptographically bind them to the verified body — e.g., require host applications to cross-check `request.shop` against an out-of-band expected value (the currently active session's shop) before trusting it, and update `Webhooks::Request#to_signable_string`/`HmacValidator` or `Registry.process` to reject a webhook if the `shop-domain` header does not correspond to a shop the app expects for that webhook subscription. At minimum, the documentation should explicitly warn that `data.shop` is **not** covered by HMAC verification and must not be trusted as an authenticated tenant identifier on its own.

### Proof of Concept
1. Attacker installs the target (public) Shopify app on their own store `attacker.myshopify.com`, completing OAuth normally (an action available to any unprivileged internet user).
2. Shopify sends a genuine webhook to the app's registered endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`, and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this `(B, H)` pair.
4. Attacker sends a new HTTP request to the same webhook endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but with `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
5. `Utils::HmacValidator.validate` recomputes the signature over `B` only [5](#0-4)  — it matches `H`, so validation succeeds.
6. `Registry.process` invokes the app's handler with `WebhookMetadata` whose `shop` field is `"victim.myshopify.com"` [4](#0-3) , causing the app to act on data it believes came from the victim's store.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
