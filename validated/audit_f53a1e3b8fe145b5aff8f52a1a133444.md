### Title
Tron `IntentGatewayV2.onAccept` omits the relayer gate that the EVM version treats as a security boundary, allowing any relayer to trigger escrow release/refund — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The mainline EVM `IntentGatewayV2`/`ExtrinsicIntents.onAccept` calls `_checkRelayer(incoming.relayer)` before processing any request kind, and the test suite explicitly documents this as a security control (relayer allow-listing gates escrow redemption/refund and governance actions). The Tron variant of the same contract implements `onAccept` without any relayer check at all, going straight to `authenticate(incoming.request)` for `RedeemEscrow`/`RefundEscrow`.

### Finding Description
On the primary EVM deployment, `onAccept` in `ExtrinsicIntents.sol` starts with `_checkRelayer(incoming.relayer)`, and the accompanying tests (`testOnAcceptRejectsUnlistedRelayer`, `testOnAcceptGovernanceRejectsUnlistedRelayer`, `testSetRelayerToZeroReopensTheGate`, `testFreshProxyIsOpenUntilGovernanceArmsIt`) show that a solver-selection/intents gateway is designed with an *additional* relayer allow-list beyond the ISMP host authentication, and that removing/omitting this check is a deliberate behavior change with security consequences (an "open gate" state that governance must consciously arm/disarm): [1](#0-0) [2](#0-1) 

In the Tron deployment of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`), `onAccept` handles `RedeemEscrow`/`RefundEscrow` by calling `authenticate(incoming.request)` directly — with no `_checkRelayer` call anywhere in the function, and no relayer field is even inspected before `withdraw()` runs: [3](#0-2) 

`withdraw()` on this path unconditionally transfers escrowed tokens (or refunds them) to the beneficiary named in the message body, and also sweeps any accrued transaction fees: [4](#0-3) 

Because the relayer allow-list is the mechanism the EVM version relies on to bound who can trigger `RedeemEscrow`/`RefundEscrow`/governance deliveries once armed by governance (`setRelayer`), its absence on Tron removes a layer of the protocol's intended defense-in-depth for a single-key-governance system that explicitly documents "no second key" risk models elsewhere in the codebase (e.g. `SimplexPaymaster`'s relayer gating comment block). I could not fully verify from the index whether `HyperApp.onlyHost` combined with ISMP's proof verification is considered by the team to make the relayer check purely defense-in-depth (in which case this is a lower-severity hardening gap) or a load-bearing authorization control on Tron specifically (Tron's TVM/consensus and host implementation were not indexed here) — this is a genuine gap in my ability to verify root-cause impact without inspecting Tron's ISMP host/consensus client, which the index does not appear to expose. Given the ambiguity and that the underlying request must still pass `onlyHost` and per-message source verification, I cannot confirm this rises to the "unsound state commitment" or "forged message delivery" threshold required by the validation rubric without further confirmation of the Tron host's proof-verification guarantees.

### Impact Explanation
If the relayer gate is in fact a load-bearing control on Tron (e.g., because Tron's host contract accepts a wider class of provers/relayers than the EVM host, or because governance elsewhere assumes the gate exists), then any relayer able to get a valid ISMP-delivered `RedeemEscrow`/`RefundEscrow`/governance message through the host could redirect escrowed funds sooner or under conditions the EVM sibling deliberately restricts, undermining the "governance can arm the gate" security model documented for the sibling contract.

### Likelihood Explanation
Low-to-moderate confidence overall: this is a source-divergence between two deployments of the same logical contract rather than a proven exploitable path, since `onlyHost` and ISMP proof verification on Tron were not available to inspect. I flag this as uncertain rather than confirmed.

### Recommendation
Align `evm/tron/contracts/apps/IntentGatewayV2.sol::onAccept` with the EVM `ExtrinsicIntents.sol::onAccept` by adding the same `_checkRelayer(incoming.relayer)` gate (and corresponding `relayer()`/`setRelayer()` state) before dispatching on `RequestKind`, and add Tron-side tests mirroring `testOnAcceptRejectsUnlistedRelayer` and `testSetRelayerToZeroReopensTheGate` to lock in parity.

### Proof of Concept
Not independently reproducible from the indexed context: I could not find/verify a Tron ISMP host or Tron-specific test harness in the index to construct an end-to-end PoC transaction; the finding is based on direct code comparison between the two `onAccept` implementations cited above.
