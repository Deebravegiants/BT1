### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop-domain` header — which the registry hands to app webhook handlers as the authenticated tenant identifier — is never included in the signed payload. Any party who possesses one valid `(body, hmac)` pair produced with the app's shared webhook secret can resend it with an arbitrary `shop-domain` header and the signature will still validate, letting them attribute forged webhook content to any other merchant using the app.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against this signable string: [2](#0-1) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is fully attacker-controlled on the HTTP request and is not part of `to_signable_string`: [3](#0-2) 

`Webhooks::Registry.process` validates only the HMAC, then forwards the unverified `request.shop` straight into the tenant-identifying `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The `api_secret_key` used to sign webhooks is a single, app-wide secret shared across every installed shop — it is not per-tenant. This is confirmed by the shared HMAC computation logic keyed only on `Context.api_secret_key`: [5](#0-4) 

Because any legitimate merchant using the app receives genuine webhooks signed with this same app-wide secret for actions on their own store, such a merchant (an unprivileged, non-credentialed-for-other-tenants user) can capture one valid `(raw_body, hmac)` pair from their own webhook traffic and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` because the signature check never inspects the `shop` field, and `Registry.process` will dispatch the handler with `shop: <victim-shop>` and the attacker's chosen body. The identity binding that should hold — `hmac-authenticated bytes == the tenant those bytes are attributed to` — is broken: the bytes are authenticated for "the app," not for the specific shop named in the unauthenticated header.

### Impact Explanation
This crosses a tenant boundary: an app author's webhook handler code, following this gem's documented API, has no way to detect that the `shop` field of `WebhookMetadata` was not covered by the signature it just verified. A merchant who is only entitled to act as their own tenant can inject arbitrary attacker-chosen webhook payloads (e.g. fake `orders/create`, `app/uninstalled`, `shop/update` events) attributed to any other merchant's shop domain, causing the app to perform tenant-scoped side effects (data writes, session/token revocation logic, billing actions, etc.) against a victim tenant. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Any existing installed merchant of the app already holds one or more valid signed webhook bodies from ordinary use (Shopify sends real webhooks for real store events), which is all that's needed to forge the header. No access token, `api_secret_key`, or privileged account is required — only the ability to send an HTTP request to the app's public webhook endpoint with a captured `(body, hmac)` pair and a modified `shop-domain` header.

### Recommendation
- Bind the `shop-domain` header into the signed material verified by `HmacValidator`, or otherwise cryptographically bind the shop identity to the webhook payload before trusting it (e.g. cross-check `request.shop` against a shop that is actually known/subscribed to that specific `webhook_id`/topic combination via a stored, per-shop webhook registration, rather than trusting the header value directly).
- Document clearly in `ShopifyAPI::Webhooks::Registry` that `WebhookMetadata#shop` is not authenticated by the HMAC and that consuming applications must not treat it as a trusted tenant identifier without additional verification (e.g. correlating `webhook_id` against a per-shop registration table).

### Proof of Concept
1. Attacker is a legitimate merchant `attacker.myshopify.com` with the app installed; they capture a genuine webhook request the app sent them: `raw_body = '{"id":1}'`, `x-shopify-hmac-sha256 = <valid signature computed by Shopify over raw_body with the app's shared api_secret_key>`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. Server builds `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only returns `raw_body`, which is unchanged (`lib/shopify_api/webhooks/request.rb` line 36-38, `lib/shopify_api/utils/hmac_validator.rb` line 26-31).
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: ..., ...))`, so the app processes attacker-controlled webhook content attributed to `victim.myshopify.com` — a cross-tenant data-integrity/authentication-boundary violation.
