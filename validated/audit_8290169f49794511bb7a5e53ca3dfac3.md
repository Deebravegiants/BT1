## Analog Found

### Title
Unguarded relayer fee-token transfer in `EvmHost.dispatchIncoming(GetResponse)` / `dispatchTimeOut` can revert and block delivery of an entire relayed batch - (File: `evm/src/core/EvmHost.sol`)

### Summary
The Sherlock report flags that a downstream ERC20 transfer inside a Chainlink VRF callback must never revert, because a revert there permanently blocks all future processing. Hyperbridge's `EvmHost` explicitly engineered around this exact class of bug for POST-request delivery (`dispatchIncoming(PostRequest,...)`), but the same protection was not applied to the relayer fee payout in `dispatchIncoming(GetResponse,...)`, `dispatchTimeOut(GetRequestTimeout,...)`, and `dispatchTimeOut(PostRequestTimeout,...)`.

### Finding Description
For POST requests, `EvmHost.dispatchIncoming` isolates the module callback behind a low-level `.call()` and explicitly rolls back only the receipt on failure, letting the rest of the batch proceed: [1](#0-0) 

By contrast, `dispatchIncoming(GetResponse,...)` performs the module callback the same isolated way, but then makes an **unguarded** `safeTransfer` to the relayer immediately afterward, with no try/catch or isolation: [2](#0-1) 

The same unguarded pattern repeats in the GET-timeout and POST-timeout paths: [3](#0-2) [4](#0-3) 

These three functions are called directly (not via try/catch, not via delegatecall-with-isolation) inside `HandlerV2`'s per-message loops, so a single reverting call reverts the entire `for` loop and thus the whole extrinsic/transaction: [5](#0-4) [6](#0-5) [7](#0-6) 

If `feeToken()` is (or later becomes) a token with transfer restrictions — e.g. a Circle-USDC-style blacklist, a pausable token, or a token that reverts on transfers to a contract without a `receive`/fallback that reverts internally — and the `relayer` address for that message is restricted, the `safeTransfer(relayer, fee)` call reverts. Because it is not isolated the way the `onAccept`/`onGetResponse`/`onPostRequestTimeout` module calls are, the revert propagates all the way up through `HandlerV2.handleGetResponses` / `handlePostRequestTimeouts` / `handleGetRequestTimeouts`, aborting the entire batch — including every other, unrelated, perfectly valid response/timeout bundled in the same Merkle-proof submission.

### Impact Explanation
This is analogous to the reported "fulfillRandomWords must not revert" issue: a single downstream ERC20 transfer failure, reachable from a permissionless relayed-proof submission, can make delivery of an entire batch of otherwise valid GET responses or timeouts impossible. Since the fee token is a protocol-wide configuration (`feeToken()`), any state change to it (blacklisting, pausing, or a governance-controlled/upgradeable fee token behaving adversarially) can render the affected relayer's fee-claim path permanently reverting, and every message bundled together with that fee claim becomes undeliverable through that proof — a route unable to deliver messages, matching the acceptance criteria for this class of finding.

### Likelihood Explanation
The reachable trigger is a single relayed transaction (`handleGetResponses`, `handlePostRequestTimeouts`, or `handleGetRequestTimeouts`) submitted by any relayer — no privileged role required. The only external dependency is that `feeToken()` has some transfer-blocking condition for at least one relayer address at delivery time, which is plausible for stablecoin fee tokens with blacklist/pause functionality that Hyperbridge is documented to use (e.g. Hyper USD/USDC-style tokens per `docs/content/developers/evm/messaging/get-requests.mdx`).

### Recommendation
Isolate the relayer fee payout the same way the module callback is isolated: wrap the `IERC20(feeToken()).safeTransfer(relayer, fee)` calls in `dispatchIncoming(GetResponse,...)`, `dispatchTimeOut(GetRequestTimeout,...)`, and `dispatchTimeOut(PostRequestTimeout,...)` in a low-level `call` (or try/catch) and handle failure by crediting the fee to a claimable balance for the relayer instead of transferring inline, so a stuck/blacklisted transfer cannot revert the surrounding batch or block delivery of unrelated messages.

### Proof of Concept
1. Governance/admin configures `feeToken()` to a blacklist-capable stablecoin (as documented for fee payments).
2. The fee token issuer blacklists a specific relayer address (independent of Hyperbridge).
3. That relayer (or anyone forced to route fee accounting through that address, e.g., via `recordEpoch`/relayer-fee routing) submits a `handleGetResponses` batch containing N valid GET responses, one of which has `meta.fee != 0` destined to the blacklisted relayer.
4. `EvmHost.dispatchIncoming(GetResponse,...)` succeeds through `onGetResponse`, then calls `safeTransfer(relayer, fee)`, which reverts due to the blacklist.
5. Because `HandlerV2.handleGetResponses` calls `host.dispatchIncoming` directly without isolation, the revert propagates, and the entire batch of N responses fails atomically — none are delivered, even though N-1 of them had no issue at all. [8](#0-7) [9](#0-8)

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

    function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 responsesLength = message.responses.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](responsesLength);

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // don't check for timeouts because it's checked on Hyperbridge

            // known request? also serves as source check
            FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
        }

        bytes32 root = host.stateMachineCommitment(message.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, message.proof.multiproof, leaves, message.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // duplicate response?
            if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.response, _msgSender());
        }
    }
