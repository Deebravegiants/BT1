### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (and `topic`/`webhook_id`) values used to route and label webhook data are read from unauthenticated HTTP headers that are excluded from the signed bytes. This breaks the identity binding "bytes verified == bytes acted on": the gem verifies the integrity of the body, but trusts the header-derived `shop` value used by the host application to determine which tenant the payload belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the signed payload: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which compares `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` to the request-supplied `hmac` header — i.e. it checks only the raw body bytes: [3](#0-2) 

After the HMAC check passes, `Registry.process` builds `WebhookMetadata` directly from `request.shop` (and `request.topic`, `request.webhook_id`) and hands it to the registered handler, which the app uses to determine which merchant/tenant record to update: [4](#0-3) 

The equality that should hold is: `bytes_verified_by_HMAC == bytes_the_app_acts_on_for_tenant_identity`. Here, `bytes_verified_by_HMAC = raw_body` while `bytes_the_app_acts_on = shopify-shop-domain header`, which is disjoint from the signed content. Because the header is not part of the signable string, any request carrying a *body* that was legitimately signed by Shopify for a given webhook delivery can be replayed with the `shopify-shop-domain` header altered to name a different shop, and the HMAC check will still pass — `Utils::HmacValidator.validate` never inspects the header at all.

### Impact Explanation
An unprivileged actor who controls (or has visibility into) a legitimate Shopify shop that has this app installed will receive real, correctly-HMAC-signed webhook deliveries for their own shop. Because the signature covers only the body, that actor can capture one such delivery (body + valid `hmac-sha256` header) and resend it to the app's public webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with the domain of a different shop that also uses the same app. `HmacValidator.validate` will accept the replayed request unchanged, and `Registry.process` will construct `WebhookMetadata` with the attacker-chosen `shop` value, causing the app's handler to attribute the webhook body to the wrong tenant. Depending on how the host app uses `data.shop` (e.g., to select which store record to update, to authorize the payload, or to key data storage per merchant), this enables cross-tenant data injection/corruption — the app processes data under an identity binding that was never cryptographically verified. This matches the "cross-tenant access" Critical impact category, since the tenant boundary (which shop a webhook belongs to) is not authenticated by the mechanism the gem provides.

### Likelihood Explanation
Likelihood is moderate to high for any actor who is a legitimate (unprivileged) merchant with the target app installed on their own store — no special privileges beyond a normal shop account are needed, and no access to `api_secret_key` is required, since the attacker reuses a genuinely-signed body/HMAC pair they already legitimately received. The only work required is capturing one webhook and replaying it with a modified header at the HTTP layer, which any unprivileged internet-connected client with knowledge of the app's public webhook URL can attempt.

### Recommendation
Include the tenant-identifying fields (at minimum `shop`, and ideally `topic`/`webhook_id`) in the HMAC-signed content, or otherwise cryptographically bind the header values to the verified body (e.g., have `Utils::HmacValidator.validate` verify a canonical string composed of body + relevant headers). Alternatively/additionally, `Registry.process` should cross-check `request.shop` against the set of shops for which the app currently holds an active session/installation before dispatching to a handler, rather than trusting the header value implicitly once the body HMAC passes.

### Proof of Concept
1. App has two independent Shopify merchants installed: `victim-shop.myshopify.com` and `attacker-shop.myshopify.com`, both subscribed to the same webhook topic (e.g., `orders/create`).
2. The attacker, as the legitimate owner of `attacker-shop.myshopify.com`, triggers an action that causes Shopify to deliver a webhook to the app's endpoint. Shopify signs the request with `HMAC-SHA256(api_secret_key, raw_body)` in the `X-Shopify-Hmac-Sha256` header, per `Request#hmac`/`#to_signable_string`.
3. The attacker captures this HTTP request (raw body + `X-Shopify-Hmac-Sha256` header) — no secret needed since they simply observe traffic they legitimately receive/control.
4. The attacker replays the identical body and `hmac-sha256` header value to the app's webhook endpoint, but overwrites `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` where `#to_signable_string` still returns the (unmodified) `raw_body`, and `#shop` returns `victim-shop.myshopify.com`.
6. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and finds it matches — validation succeeds despite the header spoof, per `hmac_validator.rb` lines 12-31.
7. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`, so the app-level handler receives the attacker's order data labeled as belonging to `victim-shop.myshopify.com`, per `registry.rb` lines 198-199.
8. If the host app uses `data.shop` to select which merchant's records to update (as documented in `docs/usage/webhooks.md` lines 12-26, where apps are told to key on `data.shop`), the attacker has injected data across the tenant boundary despite never possessing `victim-shop`'s credentials or the app's `api_secret_key`.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
