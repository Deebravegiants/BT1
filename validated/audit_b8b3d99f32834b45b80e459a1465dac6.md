### Title
Webhook shop/topic identity is trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats the incoming `shop` and `topic` as authenticated once `Utils::HmacValidator.validate(request)` passes, but the HMAC signature only binds the raw request body — never the `X-Shopify-Shop-Domain` or `X-Shopify-Topic` headers. This breaks the equality that the framework's contract implies: `hmac_verified(body) == tenant_identity_trusted(shop_header)`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 
`to_signable_string` returns only `@raw_body`: [2](#0-1) 
while `shop` and `topic` are read straight from attacker-suppliable HTTP headers, not from the signed payload: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, to_signable_string)` and compares it to the `hmac-sha256` header: [4](#0-3) 

`Webhooks::Registry.process` accepts the request as authentic once this check passes, then dispatches to the handler using `request.shop` (and `request.topic`) taken from the unauthenticated headers: [5](#0-4) 

Because the app's `client_secret` is shared across every shop that has installed the app (it is not per-shop), any two shops that share the same app produce webhook payloads signed with the identical key. If a body/HMAC pair leaks or is replayed (e.g., a merchant/attacker who can trigger a webhook on their own store, or capture one over an unencrypted channel/logging pipeline, or via a shared body format across topics), it remains a *valid* signature for that exact body regardless of which `shop-domain` header accompanies it. The gem's `HmacValidator` says nothing about tenant identity — it only proves "signed with this app's secret," yet `Registry.process` (and any host application following the documented contract in `docs/usage/webhooks.md`) uses `request.shop` post-validation as the trusted tenant identifier to route data into shop-scoped storage.

This is the exact bug class called out by the rules: "a shop authenticated versus the shop stored/used as identity key" and "bytes verified versus bytes parsed" — the bytes cryptographically verified (`raw_body`) are not the bytes used to establish tenant identity (`shop-domain` header).

### Impact Explanation
If an app implementer (following this gem's own `WebhookHandler`/`WebhookMetadata` contract) trusts `request.shop` to scope data writes/reads per merchant, an attacker who can obtain one valid `(body, hmac)` pair for shop A (e.g., by installing the app on their own store and capturing their own legitimate webhook, which is trivial and requires no special access) can replay that exact body to the app's webhook endpoint with the `Shopify-Shop-Domain` header rewritten to shop B. The HMAC check still passes because it only verifies the body was signed by the app's secret — it does not verify which shop it was signed *for*. This allows cross-tenant data injection into another merchant's scope (e.g., a redact/data webhook, order/customer webhook, etc., depending on what topics share body shapes), which maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Low-to-Medium. Exploitation requires the attacker to already control at least one legitimate install of the target app (to obtain a validly-signed body), and requires the payload structure to be generic/reusable across shops for the topic of interest (e.g., mandatory `shop/redact` or `customers/redact` webhooks, whose bodies contain shop/customer identifiers that a naive handler might not additionally cross-check). No credentials, TLS interception, or access to `api_secret_key` are needed — only a legitimate app installation, which any internet user can obtain by installing a public app on their own store.

### Recommendation
Bind the shop/topic identity to the HMAC-verified content instead of trusting unauthenticated headers:
- Include the `shop-domain` and `topic` header values in the signable string used by `HmacValidator`, or
- Cross-check `request.shop` against an independently trusted source (e.g., an offline session record keyed by the shop the webhook subscription was registered for, verified via mutual TLS/IP allow-listing, or Shopify's documented practice of validating that the shop is a known installed shop) before invoking `handler.handle`.
- At minimum, document prominently that `request.shop`/`request.topic` are **not** covered by the HMAC and that host applications must not treat them as authenticated without additional verification (e.g., checking against a shop that has an active session/install record).

### Proof of Concept
1. Install a Shopify app (`App`) on attacker-owned store `attacker-shop.myshopify.com`.
2. Trigger a webhook whose body format is shop-agnostic or attacker-controllable in content but not in structure (e.g., `customers/redact` mandatory webhook), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
3. Replay the exact same HTTP request to the same app's webhook endpoint, but modify the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com` (and, if desired, `X-Shopify-Topic`, since `topic` is also unauthenticated).
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` in [6](#0-5) 
returns `true` because it only re-hashes `@raw_body`, which is unchanged.
5. `Registry.process` in [5](#0-4) 
dispatches to the handler with `shop: "victim-shop.myshopify.com"` even though the payload was never generated for that shop, letting the attacker inject/replay data attributed to `victim-shop`.

          received_signature = verifiable_query.hmac
