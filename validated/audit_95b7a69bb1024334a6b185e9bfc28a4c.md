Audit Report

## Title
Ethereum claim signatures are replayable across independent `mint_claim` cycles, allowing redirection of a newly re-minted claim to a stale `dest` - (File: polkadot/runtime/common/src/claims/mod.rs)

## Summary
`Pallet::claim`/`Pallet::claim_attest` validate an Ethereum ECDSA signature that only covers `prefix || dest` (optionally `+ statement`), with no nonce, claim value, or mint-cycle identifier bound into the signed payload. Because `validate_unsigned` gates acceptance solely on `Claims::<T>::contains_key(&signer)` [1](#0-0)  and `Claims` is a flat map keyed only by `EthereumAddress` [2](#0-1) , any historical valid `claim` extrinsic for an address remains replayable against any later, independent `mint_claim` for that same address, silently redirecting the newly minted funds to the stale `dest`.

## Finding Description
`claim` recovers the signer from `dest.using_encoded(to_ascii_hex)` alone and dispatches `process_claim(signer, dest)` [3](#0-2) . The signed message construction in `ethereum_signable_message`/`eth_recover` mixes in only the configured `prefix`, the `dest` bytes, and an optional `statement`/`extra` — no nonce, value, or claim-instance identifier [4](#0-3) .

`validate_unsigned` re-derives the same signer for `Call::claim`/`Call::claim_attest` and only checks `Claims::<T>::contains_key(&signer)` plus the `Signing` statement match [5](#0-4) . `mint_claim` is a root-only call that simply does `Claims::<T>::insert(who, value)` [6](#0-5) , re-populating the storage entry for `who` with no tracking of which "cycle" it belongs to. `process_claim` pays out the currently stored balance to whatever `dest` was passed and then clears `Claims`, `Vesting`, `Signing` for the signer [7](#0-6) .

Exploit flow, confirmed against the current code:
1. `mint_claim(eth_addr, v1)` — `Claims[eth_addr] = v1`.
2. The key holder signs `prefix || dest_A` and submits `claim(dest_A, sig)`. `process_claim` pays `v1` to `dest_A` and deletes `Claims[eth_addr]`. The `(dest_A, sig)` pair remains publicly visible in chain history.
3. Later, root calls `mint_claim(eth_addr, v2)` again for the same address (e.g., re-issuance/top-up), expecting a fresh signature bound to a new destination.
4. Anyone resubmits the old `claim(dest_A, sig)` bytes. `validate_unsigned` recovers `eth_addr` again, `Claims::contains_key(eth_addr)` is now `true` (step 3), so the transaction is accepted with no new signing required.
5. `process_claim` pays `v2` to `dest_A` — the stale destination — with no involvement from the Ethereum key holder or governance's intended recipient for the second mint.

No existing check ties the signature to a specific mint instance, amount, or block; the address-keyed `contains_key` check is the only gate, and it is trivially satisfied by any subsequent `mint_claim` for the same address.

## Impact Explanation
Funds from a second, independent `mint_claim` for a previously fully-claimed Ethereum address can be unconditionally and automatically redirected to the stale `dest` from the first claim cycle, with no consent or fresh signature from the Ethereum key holder. This is an unauthorized redirection of claim funds — the loss is concrete (whoever controls `dest_A`, which need not be the same party entitled to the second mint, receives `v2`), and the trigger step (resubmitting old, publicly visible transaction bytes) requires no privilege at all.

## Likelihood Explanation
The precondition — governance/root calling `mint_claim` twice for the same Ethereum address across its lifetime (once fully claimed and removed, then re-minted) — is a plausible administrative action (correcting an error, additional funding, re-issuance) rather than a purely theoretical scenario. Given that precondition, exploitation is trivial and requires no privileged access, no new cryptographic material, and no interaction with the Ethereum private key: any unprivileged actor can resubmit the historical `claim` extrinsic bytes from chain history/explorers.

## Recommendation
Bind the signed message to the specific claim instance rather than only to `dest`. Introduce a per-address claim epoch/nonce (incremented on every `mint_claim` for that address) or otherwise mix a unique claim-instance identifier (e.g., mint block number or value) into `ethereum_signable_message`, and validate that identifier in both `validate_unsigned` and `process_claim`. Alternatively, disallow re-minting into an address whose previous claim was fully processed and removed unless a mechanism explicitly invalidates prior signatures (e.g., by requiring `move_claim` to a fresh address instead of `mint_claim` on the same address).

## Proof of Concept
Rust unit test pattern (in `polkadot/runtime/common/src/claims/tests.rs`):
1. `mint_claim(RuntimeOrigin::root(), eth(&alice_secret()), 100, None, None)`.
2. Build `sig = sig::<Test>(&alice_secret(), &42u64.encode(), &[])`, call `Claims::claim(RuntimeOrigin::none(), 42, sig.clone())`; assert success and `Balances::free_balance(42) == 100`, `Claims::claims(eth(&alice_secret())).is_none()`.
3. `mint_claim(RuntimeOrigin::root(), eth(&alice_secret()), 200, None, None)` (second, independent mint, intended for a different destination requiring a fresh signature not yet produced).
4. Call `Claims::validate_unsigned(TransactionSource::External, &Call::claim { dest: 42, ethereum_signature: sig.clone() })` — observe it returns `Ok(ValidTransaction { .. })`; dispatch `Claims::claim(RuntimeOrigin::none(), 42, sig)` and observe `Balances::free_balance(42) == 300`, showing the second mint's funds were redirected to the stale `dest = 42` with no new signature ever produced.

impl<T: Config> Pallet<T> {
	// Constructs the message that Ethereum RPC's `personal_sign` and `eth_sign` would sign.
	fn ethereum_signable_message(what: &[u8], extra: &[u8]) -> Vec<u8> {
		let prefix = T::Prefix::get();
		let mut l = prefix.len() + what.len() + extra.len();
		let mut rev = Vec::new();
		while l > 0 {
			rev.push(b'0' + (l % 10) as u8);
			l /= 10;
		}
		let mut v = b"\x19Ethereum Signed Message:\n".to_vec();
		v.extend(rev.into_iter().rev());
		v.extend_from_slice(prefix);
		v.extend_from_slice(what);
		v.extend_from_slice(extra);
		v
	}

	// Attempts to recover the Ethereum address from a message signature signed by using
	// the Ethereum RPC's `personal_sign` and `eth_sign`.
	fn eth_recover(s: &EcdsaSignature, what: &[u8], extra: &[u8]) -> Option<EthereumAddress> {
		let msg = keccak_256(&Self::ethereum_signable_message(what, extra));
		let mut res = EthereumAddress::default();
		res.0
			.copy_from_slice(&keccak_256(&secp256k1_ecdsa_recover(&s.0, &msg).ok()?[..])[12..]);
		Some(res)
	}

	fn process_claim(signer: EthereumAddress, dest: T::AccountId) -> sp_runtime::DispatchResult {
		let balance_due = Claims::<T>::get(&signer).ok_or(Error::<T>::SignerHasNoClaim)?;

		let new_total =
			Total::<T>::get().checked_sub(&balance_due).ok_or(Error::<T>::PotUnderflow)?;

		let vesting = Vesting::<T>::get(&signer);
		if let Some(_) = vesting {
			if T::VestingSchedule::vesting_balance(&dest).is_some() {
				return Err(Error::<T>::VestedBalanceExists.into());
			}

			// A vesting schedule installs a balance lock, which requires the account to stay alive,
			// otherwise it is dusted and the lock placed on a non-existent account. The `dest` may
			// already hold funds, so a small claim that tops an existing account over the ED is
			// valid.
			let free_after = CurrencyOf::<T>::free_balance(&dest).saturating_add(balance_due);
			ensure!(
				free_after >= CurrencyOf::<T>::minimum_balance(),
				Error::<T>::ClaimBelowExistentialDeposit,
			);
		}

		// We first need to deposit the balance to ensure that the account exists.
		let _ = CurrencyOf::<T>::deposit_creating(&dest, balance_due);

		// Check if this claim should have a vesting schedule.
		if let Some(vs) = vesting {
			// This can only fail if the account already has a vesting schedule or its balance is
			// below the existential deposit, both of which are checked above.
			T::VestingSchedule::add_vesting_schedule(&dest, vs.0, vs.1, vs.2)
				.map_err(|_| Error::<T>::VestedBalanceExists)?;
		}

		Total::<T>::put(new_total);
		Claims::<T>::remove(&signer);
		Vesting::<T>::remove(&signer);
		Signing::<T>::remove(&signer);

		// Let's deposit an event to let the outside world know this happened.
		Self::deposit_event(Event::<T>::Claimed {
			who: dest,
			ethereum_address: signer,
			amount: balance_due,
		});

		Ok(())
	}
