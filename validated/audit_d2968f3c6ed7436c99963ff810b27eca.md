### Title
Malicious route payload can append arbitrary victim-token transfers to a signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller accepts opaque route bytes in `swap_collateral(caller, account_id, current, amount, new, swap)` and forwards them to the configured router. [1](#0-0)  The controller bounds only its own exact input transfer, while the route can invoke attacker-controlled venue code capable of requesting additional authorization from `caller`. [2](#0-1)  If the victim signs the authorization tree produced by simulation, the transaction can both complete the requested collateral swap and transfer unrelated wallet tokens to the attacker. [3](#0-2) 

### Finding Description
`swap_tokens` passes the user-supplied `swap` bytes directly to `SwapAggregatorClient::execute_strategy` after authorizing only `token_in.transfer(controller, router, amount_in)` for the controller. [4](#0-3)  That exact authorization bounds the controller’s own input grant, but it does not constrain authorization requested later by contracts reached through the route. [5](#0-4) 

The router dispatches each payload-selected hop to a venue adapter without an on-chain pool allowlist. [6](#0-5)  A malicious pool can therefore execute arbitrary contract code while the caller’s top-level `swap_collateral` authorization is active. [7](#0-6) 

The repository’s adversarial test records a malicious `token.transfer(victim, attacker, amount)` as a child of the victim’s `swap_collateral` authorization. [8](#0-7)  In enforcing mode, the transfer fails if it is absent from the signed tree but succeeds when the simulated poisoned tree is signed. [9](#0-8) 

### Impact Explanation
An attacker can steal tokens held directly by the victim, including assets unrelated to the lending position, rather than merely receiving an unfavorable swap. [10](#0-9)  The measured output check and final account-risk checks do not detect this theft because the malicious transfer is an unrelated balance movement authorized by the victim’s signed tree. [11](#0-10) 

The demonstrated result is complete loss of the targeted wallet balance while the requested collateral swap still succeeds and credits fair output. [12](#0-11) 

### Likelihood Explanation
The attack requires the victim to submit a strategy transaction containing the attacker’s crafted route and to sign the authorization tree returned by simulation. [13](#0-12)  This is plausible when route bytes are obtained from an untrusted quote, link, strategy marketplace, or compromised frontend because the malicious child authorization is encoded in opaque route-dependent simulation data. [14](#0-13) 

No privileged protocol role or leaked key is required to construct the malicious route or venue contract. [15](#0-14)  The reliance on a victim signature and client behavior makes this Medium rather than Critical or High. [16](#0-15) 

### Recommendation
Bind route execution to authenticated venue/pool registrations instead of accepting arbitrary pool addresses from route bytes, or otherwise reject route-generated authorization requests outside the expected input transfer. [6](#0-5)  The expected authorization shape is one input-token transfer for a direct router swap and no unrelated child transfer for a controller strategy. [17](#0-16) 

Clients must additionally decode the signed authorization tree and reject any child token transfer other than the expected swap input. [18](#0-17)  Client validation should be treated as mitigation rather than a substitute for an on-chain verified venue registry because the malicious transfer is protocol-valid once signed. [3](#0-2) 

### Proof of Concept
1. Victim supplies `USDC` collateral and holds an unrelated token balance. [19](#0-18) 
2. Attacker deploys a venue-compatible contract configured to call `token.transfer(victim, attacker, victim_balance)` during the hop. [20](#0-19) 
3. Attacker supplies route bytes that use that contract as a swap hop while producing enough output to satisfy the router and controller checks. [21](#0-20) 
4. Victim invokes `swap_collateral(caller=victim, account_id, current=USDC market, amount, new=ETH market, swap=malicious_route)`. [22](#0-21) 
5. Simulation records the unrelated victim-token transfer as a child of `swap_collateral`; after the victim signs that returned tree, the swap succeeds and the attacker receives the victim’s full targeted balance. [3](#0-2)

/// call on `token_addr` made deeper in the next contract call (for example by

    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,

    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
