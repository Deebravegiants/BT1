### Title
Interest accrual overflows RAY valuation and permanently freezes a large market - (File: common/src/rates/simulate.rs)

### Summary
A sufficiently large supplied or borrowed market can grow beyond the `i128` RAY-value domain before either index reaches its configured ceiling, causing every subsequent accrual to revert with `MathOverflow`. Because `update_indexes`, supply, borrow, withdraw, repay, and other pool mutations synchronize the market before acting, the overflow permanently blocks exits, repayments, liquidations, and further accrual for that market.

### Finding Description
`accrue_step` computes `borrowed_original` and `supplied_original` by multiplying scaled RAY share balances by the corresponding index through `scaled_to_original`. [1](#0-0)  `scaled_to_original` calls `Ray::mul`, which invokes `mul_div_half_up`. [2](#0-1)  `mul_div_half_up` uses an exact widened intermediate product, but still returns `None` and panics with `GenericError::MathOverflow` when the final RAY value does not fit in `i128`. [3](#0-2) 

The configured index ceilings only cap the indexes themselves at `10^36`; they do not prevent `shares * index / RAY` from exceeding `i128::MAX`. [4](#0-3)  Accrual also multiplies `borrowed` by both borrow indexes in `calculate_supplier_rewards`, and multiplies `supplied` by both supply indexes in `supply_index_reward_shortfall`, so either side of a large market can independently hit the same boundary. [5](#0-4) [6](#0-5) 

Every market mutation loads the market through `synced_market`, which calls `interest::global_sync` before the requested action. [7](#0-6)  `global_sync` invokes `accrue_step` for each elapsed chunk and only then commits updated indexes and revenue. [8](#0-7)  Consequently, once the next valuation product is unrepresentable, no state-changing path touching that market can progress past accrual.

An unprivileged user can create the precondition through ordinary controller `supply` and `borrow` calls, wait for interest to accumulate, and then trigger the overflow through `update_indexes`, `withdraw`, `repay`, or any other operation that synchronizes the market. The included regression test demonstrates this exact state using an 18-decimal market, a one-billion-whole-token supply, 98% utilization, repeated yearly accrual, and a final `MATH_OVERFLOW` before the borrow-index cap. [9](#0-8)  The test then proves that both withdrawal and repayment hit the same overflow after the index fails to advance. [10](#0-9) 

### Impact Explanation
This is permanent freezing of user funds and market shutdown. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot force the pool through interest synchronization, and protocol revenue cannot be claimed because each path first recomputes an unrepresentable RAY market value. [7](#0-6) [11](#0-10) 

The issue is not merely a rejected oversized transaction. Once the committed scaled balances and indexes reach a product outside `i128`, the next call panics before state is updated, leaving the old last-accrual timestamp and the same unrecoverable inputs for every later transaction. [12](#0-11) 

### Likelihood Explanation
Likelihood is conditional on very large market value and sustained interest accrual. The demonstrated configuration is within protocol-valid token precision, caps, interest parameters, and ordinary user actions, but it requires balances on the order of one billion whole tokens at 18 decimals and enough time for the index to multiply the market value beyond roughly `170 × 10^36` raw RAY. [9](#0-8) 

The documentation confirms that a valid token-to-RAY input and bounded indexes do not independently bound accrued market values, and that value overflow can occur before the index ceiling. [13](#0-12)  This lowers the ambiguity around exploitation: the attacker does not need malformed parameters, privileged access, oracle manipulation, or an invalid market—only a sufficiently large position and time.

### Recommendation
Represent market and position values in a wider type throughout accrual and valuation, or add an explicit market-cap invariant that prevents any state where `scaled_shares * index / RAY` can exceed `i128::MAX`. At minimum, accrual should clamp or stop before reaching the unrecoverable product boundary and must preserve repayment, withdrawal, liquidation, and bad-debt cleanup paths even when additional interest can no longer be represented. The cap must account for both sides of the market because `borrowed * borrow_index` and `supplied * supply_index` are calculated separately. [14](#0-13) 

### Proof of Concept
1. Create an 18-decimal asset market using the XLM-style rate curve and raise its caps to admit the large position. [15](#0-14) 
2. Supply `1_000_000_000 × 10^18` base units to the pool through the ordinary controller supply path. [16](#0-15) 
3. Borrow approximately 98% of the supplied amount from a collateralized account. [17](#0-16) 
4. Advance ledger time and repeatedly call `update_indexes`; the accrual eventually fails with `MATH_OVERFLOW` while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [18](#0-17) 
5. Attempt `withdraw` or `repay`; both fail with `MATH_OVERFLOW` because each operation invokes `synced_market` and therefore reaches `accrue_step` before processing the requested action. [7](#0-6) [19](#0-18)

```rust
/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```

```rust
pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```
