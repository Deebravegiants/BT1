### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` validates webhook authenticity by HMAC-signing only the raw request body, while the `shop` (tenant) field is read directly and unauthenticated from the `shopify-shop-domain` / `x-shopify-shop-domain` header. This breaks the identity binding that `HmacValidator.validate` is supposed to enforce: the header used to attribute a webhook to a specific merchant is not part of the signed material, so a request with a valid HMAC for one shop's payload can be relabeled as belonging to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from an unauthenticated header with no cryptographic tie to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) using `Context.api_secret_key`, and compares it to the value derived from the `hmac-sha256` header: [3](#0-2) 

The equality the gem is meant to establish is: `hmac == HMAC(secret, body) AND shop_header == shop_that_the_secret_holder(Shopify) actually signed for`. In reality only the first half is checked; `shop` is accepted as-is from `Request#shop` and handed to app handlers untouched, e.g. in the registry dispatch: [4](#0-3) 

Because the API secret key (`Context.api_secret_key`) is one shared secret for the whole app (not per-shop), any merchant who has installed the app can receive genuinely-signed webhooks for their own shop (e.g. by triggering a `products/create` event on their own store) and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass because the body and HMAC are unchanged and valid, but `request.shop` — the field application code uses to select which tenant/session/store the payload belongs to — now lies.

### Impact Explanation
This crosses a tenant boundary: a webhook payload legitimately signed for merchant A can be attributed to merchant B purely by the attacker (merchant A) controlling the header value. Any application logic that trusts `Webhooks::Request#shop` (or `WebhookHandler` implementations, which typically use it to look up the session/store to act on) to select which tenant's data to update can be tricked into writing attacker-controlled data (the body content, e.g. product/order/customer payloads a merchant fully controls on their own store) into another shop's context. This is a cross-tenant integrity issue enabled directly by the gem's own HMAC/identity design, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is limited by two factors: (1) the attacker must be a legitimate merchant with the app installed so that they can generate a validly-signed webhook body for content they control, and (2) they need network access to POST directly to the host app's webhook endpoint bypassing Shopify's dispatch (bypassing Shopify's IP/dispatch is not prevented by this gem, since only body+HMAC are checked). Given that any installer of the app can trigger events on their own store to obtain a signed body/HMAC pair, and the gem performs no additional binding of `shop` to the signature, this is realistically exploitable without any privileged credentials, matching the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally `topic`/`webhook-id`) as part of the signed material verified against Shopify's HMAC, or — since Shopify's HMAC scheme only signs the body by design — have `HmacValidator`/`Webhooks::Registry` require callers to independently verify that `request.shop` corresponds to a shop with an active, known session/installation before dispatching to handlers, and document that `shop` must not be trusted as authenticated by `hmac`. At minimum, update `to_signable_string`/`HmacValidator.validate` documentation and `Webhooks::Registry.process` to make it explicit that `shop` is unauthenticated header data and must be revalidated by the host app against its own tenant records, not treated as verified by `Utils::HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and configures a webhook (e.g. `products/create`).
2. Attacker creates a product on their own store; Shopify sends a webhook POST with a body `B` and header `shopify-hmac-sha256: HMAC(secret, B)`, `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays this exact `B` and HMAC value to the app's public webhook endpoint, but changes the header to `shopify-shop-domain: victim.myshopify.com`.
4. The app constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com"...})` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
5. `HmacValidator.validate` succeeds because it only checks `HMAC(secret, B)` against the header — see [5](#0-4)  and [6](#0-5) .
6. The registered handler receives `data.shop == "victim.myshopify.com"` and `data.body == <attacker-controlled B>`, causing the app to process attacker-controlled data under the victim shop's tenant context.
