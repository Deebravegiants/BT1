### Title
Front-running griefing DoS on `bonding_curve_launchpad::create_fa_pair` via shared, attacker-guessable named-object seed - (File: `aptos-move/move-examples/bonding_curve_launchpad/sources/bonding_curve_launchpad.move`)

### Summary
`create_fa_pair` derives the fungible-asset object's address deterministically from a single shared internal "FA Generator" signer plus a caller-supplied `name`/`symbol` seed, with no per-caller (creator) component in the seed. Any unprivileged account can pre-compute this address off-chain via the public view function `get_fa_obj_address` and front-run a legitimate creator's `create_fa_pair` call using the same `name`/`symbol`, permanently squatting that address and causing the legitimate creator's transaction to abort. This is a direct Aptos-native analog of the reported `create2`/`cloneDeterministically` salt front-running griefing bug, but here the deterministic address is used to gate fungible-asset creation instead of clone deployment.

### Finding Description
`create_fa` computes the object address as `object::create_named_object(&fa_generator_signer, fa_key_seed)` where `fa_generator_signer` is always the same internal signer for the whole module (obtained from `LaunchPad.fa_generator_extend_ref`) and `fa_key_seed = name || "-" || symbol` is fully attacker-controlled input, with no `msg.sender`/creator-address component mixed in: [2](#0-1) 

Because `create_named_object` internally calls `create_object_internal`, which asserts `!exists<ObjectCore>(object)` and aborts with `EOBJECT_EXISTS` otherwise: [1](#0-0) 

...any account can call the public entry function `create_fa_pair` first with the exact same `name`/`symbol` a legitimate creator intends to use (observable via mempool or simply guessed/copied), causing the legitimate creator's later call to `create_fa_pair` to abort deterministically at `create_named_object`. The address is also fully predictable in advance through the public view function `get_fa_obj_address`, which performs the identical derivation: [3](#0-2) 

The existence check `does_fa_exist = object::object_exists<FAController>(...)` in `create_fa` only prevents duplicate *successful* creations; it does not prevent an attacker from being the first successful creator of that (name, symbol) object address, thereby permanently denying the intended creator's ability to ever use that exact name/symbol pair: [4](#0-3) 

### Impact Explanation
This maps to the "Permanent lock or non-recoverable loss of object-held ... value" and "custody accounting corruption that moves value to the wrong holder" custody pivots: an attacker can permanently seize the on-chain identity (name/symbol combination and its deterministic object address) intended for a legitimate token launch, front-run the fungible-asset creation, and become the owner/mint-authority holder of the `FAController`/`MintRef`/`TransferRef` for that FA instead of the intended creator. Since named objects cannot be deleted, this squatting is irreversible — the legitimate creator can never mint their intended FA under that name/symbol at that address again, and any brand/liquidity association with that name is permanently controlled by the attacker.

### Likelihood Explanation
Likelihood is medium: exploitation only requires calling a public entry function (`create_fa_pair`) with attacker-chosen matching `name`/`symbol` values, which is trivial to do by observing a pending mempool transaction or by monitoring popular/anticipated token names, and requires no privileged role — this is a `move-examples` reference contract, so it is illustrative of the pattern rather than the framework's production hardened path, but it demonstrates the exact same architectural weakness the report describes (deterministic derivation without binding to the true caller).

### Recommendation
Bind the creator's own address (the actual `signer::address_of(creator)` in `create_fa_pair`) into the seed used for `create_named_object`/`create_object_address`, analogous to adding `msg.sender` to the `salt`, e.g. `fa_key_seed = creator_address || name || "-" || symbol`. This ensures only the intended creator can ever occupy that specific object address, eliminating cross-user front-running of the deterministic address while still allowing per-name/symbol uniqueness to be enforced per creator (or globally, if that uniqueness is combined with creator identity as part of the guaranteed collision-free scheme).

### Proof of Concept
1. Victim broadcasts (or is about to broadcast) `create_fa_pair(creator, apt_amount_in, name="MOON", symbol="MOON", ...)`.
2. Attacker observes the pending transaction (or simply anticipates the popular name) and independently computes `get_fa_obj_address("MOON", "MOON")`, confirming it is unoccupied.
3. Attacker submits their own `create_fa_pair(attacker, ..., name="MOON", symbol="MOON", ...)` with higher gas priority, which succeeds first, creating `ObjectCore`/`FAController` at the deterministic address under `fa_generator_signer` + seed `"MOON-MOON"`.
4. Victim's original transaction now executes `create_fa` → `object::create_named_object(&fa_generator_signer, b"MOON-MOON")` → `create_object_internal` → `assert!(!exists<ObjectCore>(object), EOBJECT_EXISTS)` fails, aborting the victim's transaction permanently for that name/symbol pair, with the attacker now holding full mint/transfer/liquidity control of the "MOON" FA.
