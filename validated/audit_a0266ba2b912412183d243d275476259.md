### Title
Webhook `shop` field is trusted by handlers but not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's handler, but the HMAC verification only authenticates the raw request body. The `shop` (and `topic`/`webhook_id`/`api_version`) values, which are read straight from HTTP headers and handed to the handler as the tenant identifier, are never covered by the HMAC. Any party that can obtain one validly-signed webhook payload for the shared app secret can replay that body with a forged `x-shopify-shop-domain` header and have the app process it as if it came from a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes/verifies the signature purely over that signable string: [2](#0-1) 

`Registry.process` uses this same HMAC check to authorize the request, then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` (all sourced from unauthenticated headers) to build the metadata passed to the app's handler: [3](#0-2)  and `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the HMAC: [4](#0-3) 

The documentation explicitly promises that `process` "will verify the request did indeed come from Shopify" before calling the handler, and instructs apps to key their tenant logic (e.g. `shop_domain: data.shop`) directly off `data.shop`: [5](#0-4) [6](#0-5) 

The identity binding that should hold is:
`shop_bound_by_hmac == shop_used_for_tenant_attribution`

In this gem, the left side is never computed — the HMAC binds nothing about the shop, topic, webhook id, or API version — so any value can be substituted on the right side while the HMAC check still passes, as long as the attacker has one HMAC-valid `raw_body` for the shared `api_secret_key`.

Since Shopify webhook HMACs are computed with the app's single `client_secret`, shared across every shop that installs the app (not a per-shop secret), a merchant who has installed the app receives at least one genuinely-signed webhook body. That body/HMAC pair remains valid regardless of which `shop-domain` header accompanies it, because the header is outside the signed material.

### Impact Explanation
An attacker who has installed the target app on their own store (an unprivileged, non-privileged-relative-to-other-tenants actor) can capture one valid `(raw_body, hmac)` pair from their own webhook traffic, then replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a victim shop. `Registry.process` will pass HMAC validation (since only `raw_body` is checked) and hand the handler a `WebhookMetadata` claiming to be from the victim shop with attacker-chosen body content, including the mandatory `shop/redact` / `customers/redact` / `customers/data_request` compliance topics. Any handler logic keyed on `data.shop` — exactly the pattern the gem's own documentation recommends — performs actions or data mutations attributed to the wrong tenant, i.e. cross-tenant access/spoofing. This meets the Critical bar ("cross-tenant access").

### Likelihood Explanation
Moderate-to-high: it requires the attacker to be (or control) a legitimate shop with the app installed, which is a low bar for a public app, and simply requires replaying a captured payload with a modified header — no cryptographic secret is needed. Front-running/timing games are not required; the attacker can act any time after receiving a single real webhook.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-covered signable string, or otherwise cryptographically bind the shop attribute the handler receives to the verified payload, so `Registry.process` cannot be tricked into presenting attacker-controlled tenant identity for a validly-signed body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any registered webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` that Shopify sent (both signed with the app's shared `api_secret_key`).
2. Attacker (or a party who intercepts the webhook delivery) replays a POST to the app's webhook route with:
   - body = `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` optionally forged too.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes HMAC over `B`: [7](#0-6) 
4. The app's handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and, following the gem's own documented handler pattern, performs actions against `victim-shop`'s records — a cross-tenant compromise using data/HMAC that were never actually issued for that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
