### Title
Unregulated `protocolFeeBps`/destination fees in Tron `IntentGatewayV2.onAccept` UpdateParams path enables total loss of escrowed order funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` applies governance-supplied `Params` and per-destination protocol fees directly in `onAccept` without any bounds validation, unlike the canonical EVM implementation. A `protocolFeeBps` (or `destinationFeeBps`) value at or above `10_000` (100%) — or even just very close to it — is accepted and stored, and is then applied to every subsequent `placeOrder` call, deducting up to the entire escrowed input amount as "protocol fee"/dust before the commitment is even computed. This mirrors the TrueFi `joiningFee` bug class: an unregulated fee parameter set via a privileged-but-remote update path can reach 100%, and the funds-loss surface is reachable by any ordinary user calling the unprivileged `placeOrder` entrypoint.

### Finding Description
In the canonical EVM contract, parameter updates are routed through `IntentsBase._validateParams` and `_updateParams`, which explicitly bound the fee parameters: [1](#0-0) 

This enforces `p.protocolFeeBps < 10_000`, `p.surplusShareBps <= 10_000`, and per-destination `feeBps < 10_000` before committing any change to `_params` or `_destinationProtocolFees`.

The Tron deployment of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements its own `onAccept` handler for `RequestKind.UpdateParams` that bypasses this validation entirely — it decodes the incoming `ParamsUpdate` and writes it straight into storage with no bound checks: [2](#0-1) 

Note `_params = update.params;` is applied unconditionally, and `_destinationProtocolFees[stateMachineId] = feeBps;` is set with no `feeBps < 10_000` guard, in contrast to the corresponding EVM `_updateParams` implementation. A grep for `_validateParams`/`initialize`/`setParams` in this file confirms there is no equivalent parameter-bounding logic defined or invoked in the Tron contract.

That unbounded `protocolFeeBps` value is then consumed directly by `placeOrder`, which computes and deducts the fee from every user's input before escrowing and computing the order commitment: [3](#0-2) 

If `protocolFeeBps` is set to `10_000` (100%) or any very high value, `reducedAmount = originalAmount - protocolFee` collapses to (near) zero for every order — i.e., every user's deposited input is effectively confiscated as "dust"/protocol fee, and the resulting near-zero escrow is committed as the order amount, meaning the user receives nothing in return (no output token, no refund path recovers the confiscated fee).

### Impact Explanation
This directly parallels the reported bug class: an admin/governance-settable fee parameter with no enforced upper bound, reachable by ordinary user transactions (`placeOrder`), can be configured (whether via a compromised, buggy, or simply unvalidated cross-chain governance message reaching `onAccept`) to consume up to 100% of every user's deposited/escrowed funds with no possibility of reverting or limiting the loss on the user side. This is a permanent, protocol-level loss-of-funds vector on the Tron deployment specifically, since the parallel EVM contract already defends against it via `_validateParams`.

### Likelihood Explanation
The `UpdateParams` message is only accepted from Hyperbridge governance (`onlyHost` + source-is-hyperbridge check), so triggering the fee to reach 100% requires a governance-originated cross-chain message. However, the missing bound check means this is a purely accidental/operational risk (a governance misconfiguration, encoding bug, or unvalidated relay of a malformed `ParamsUpdate`) rather than a hardened invariant — exactly the failure mode the original TrueFi report flags, and exactly the invariant the parallel EVM contract enforces but the Tron contract omits. Given fee parameters are routinely updated via this path (as shown by existing test coverage exercising `protocolFeeBps`/`destinationFeeBps` updates on the EVM side), the missing check on Tron is a live, exploitable gap rather than a purely theoretical one.

### Recommendation
Add the same bounds validation used in `IntentsBase._validateParams`/`_updateParams` to the Tron `IntentGatewayV2.onAccept` `UpdateParams` branch: require `update.params.protocolFeeBps < 10_000`, `update.params.surplusShareBps <= 10_000`, and each `update.destinationFees[i].destinationFeeBps < 10_000` before writing to `_params` / `_destinationProtocolFees`, reverting the whole `onAccept` call (or at minimum that specific message) otherwise. Ideally, factor a shared `_validateParams` helper (as `IntentsBase` already does) and reuse it in the Tron contract to avoid future drift between the two implementations.

### Proof of Concept
1. Hyperbridge governance (or a malformed/erroneous relayed message) dispatches a `PostRequest` to the Tron `IntentGatewayV2` with `RequestKind.UpdateParams` and `ParamsUpdate.params.protocolFeeBps = 10_000` (or any near-100% value).
2. `onAccept` (lines 644-660) accepts this with no validation and sets `_params = update.params`.
3. A user calls `placeOrder` with e.g. 1000 USDC as input.
4. In `placeOrder` (lines 359-374), `protocolFee = originalAmount * 10_000 / 10_000 = originalAmount`, so `reducedAmount = 0`; the escrowed/commitment amount for the order becomes 0 while the full 1000 USDC has already been pulled from the user via `safeTransferFrom` elsewhere in the flow.
5. The user's entire deposited amount is retained by the gateway as "dust"/protocol fee with no path to reclaim it, and the order effectively cannot be filled for any meaningful amount — a complete loss of the user's funds.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
