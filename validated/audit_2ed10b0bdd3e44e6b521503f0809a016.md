## Finding: Webhook `shop`/`topic` Headers Not Covered by HMAC Verification - (`lib/shopify_api/webhooks/request.rb`)

### Summary

`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `ShopifyAPI::Webhooks::Registry.process` are read directly from unauthenticated HTTP headers. This breaks the intended identity binding: `HMAC-verified bytes == raw_body` but `data trusted by handler == raw_body + shop-domain header (unverified)`.

### Finding Description

`Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors instead read directly from HTTP headers, none of which participate in the signature: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC header — it has no knowledge of, and does not bind, the shop/topic headers: [3](#0-2) 

`Registry.process` gates on this body-only HMAC check, then unconditionally trusts `request.shop` and `request.topic` (straight from headers) to build `WebhookMetadata` passed to the host app's handler: [4](#0-3) 

Because Shopify computes the webhook HMAC only over the raw body (this is expected/standard Shopify behavior), any party that has received one genuine webhook delivery for their **own** shop — i.e., any merchant who has installed the app — possesses a body + HMAC pair that remains valid under `HmacValidator.validate` no matter what `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, or `X-Shopify-Api-Version` headers accompany it. A malicious merchant can therefore replay their own legitimately-signed webhook body while substituting a victim shop's domain in the `shop-domain` header (and/or a different topic), and the gem will report it as a validly-authenticated webhook attributed to the victim shop.

### Impact Explanation

This is a cross-tenant identity-binding break: the value the gem verifies (raw body bytes) is not the value the host application acts on to determine *which tenant* the event belongs to (`request.shop`). Any host application that uses `WebhookMetadata#shop` to look up per-shop state, sessions, or access tokens (a documented, expected usage pattern of this field) can be tricked into processing forged data under another shop's identity, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation

Requires only that the attacker be an installed/unprivileged merchant of the app who receives ordinary webhook deliveries (no special privilege, no secret needed) — well within the "unprivileged internet user" threat model described. No `client_secret` or access token theft is required; the attacker only reuses their own genuine webhook payload+HMAC pair with substituted headers.

### Recommendation

Bind the tenant-identifying fields into the signed material, or otherwise cryptographically bind `shop`, `topic`, etc. to the HMAC — e.g., by having `to_signable_string` include shop/topic/webhook_id alongside the body (would require coordinated verification logic), or, at minimum, document/enforce that `shop`/`topic` from `Webhooks::Request` must never be trusted for authorization decisions without additional out-of-band verification (such as cross-checking against the shop associated with a currently active, independently-authenticated session).

### Proof of Concept

1. App merchant "Attacker Shop" installs the app and receives a legitimate `orders/create` webhook: body `B`, with header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends this exact body `B` and HMAC header unchanged to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` — matches, returns `true` (per `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` proceeds, builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)` (per `lib/shopify_api/webhooks/registry.rb:198-199`), and invokes the host handler as if this event legitimately originated from `victim.myshopify.com`.
