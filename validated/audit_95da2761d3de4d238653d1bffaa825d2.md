Audit Report

## Title
Missing `return` After Failed Email-Claim Extraction Lets OIDC Token Exchange Silently Continue and Issue an Authenticated Session - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `handleTokenExchange`, the type-assertion check `email, ok := claims["email"].(string)` logs an error and writes an HTTP 500 body on failure but is missing the `return` statement that every other error branch in this function has. Execution falls through to role mapping, `oidc_sessions` DB insertion (with an empty-string `user_email`), audit logging, session cookie persistence via `ginSession.Save()`, and finally an unconditional `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})` overwrite, so the client ends up with a working authenticated session tied to an empty/invalid identity, despite the server having detected the failure.

## Finding Description
The code at [1](#0-0)  is:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
```
Unlike the other seven error branches in the same function (all of which call `return` immediately after writing an error response — see e.g. [2](#0-1)  and [3](#0-2) ), this branch omits `return`. Execution proceeds into `IDClaimsToUserRole`, the `oidc_sessions` INSERT with `strings.ToLower(email)` (empty string when the assertion fails), the audit log call, and the session save/response block at [4](#0-3) . The same missing-`return` pattern recurs at the DB-insert error path [5](#0-4) , compounding the issue: a session that fails to persist is still followed by `ginSession.Save()` and a 200 OK. Existing checks (state validation, token exchange, ID token verification, claims parsing, role mapping) are all correctly gated with `return`, so this is an isolated control-flow defect rather than a systemic authentication bypass, but it directly undermines the intended "abort on claim failure" behavior.

## Impact Explanation
This is an authentication/session-integrity defect: on any OIDC provider response lacking a proper string `email` claim (a realistic edge case depending on IdP scope configuration, e.g., omitting the `email` scope, or a malicious/compromised IdP), the server still mints a valid, cookie-backed Chainlink session and reports `Success: true` at HTTP 200, while `oidc_sessions.user_email` is stored as an empty string. This causes identity confusion (multiple such failures collapse to the same empty-string identity) and, since role mapping via `IDClaimsToUserRole` runs unaffected by this bug, a session with an elevated role could be granted without a valid bound email identity. This maps to the in-scope impact category of node API authentication/session integrity being violated by application logic rather than any external actor abuse.

## Likelihood Explanation
This code path is the primary handler for the OIDC login callback and is reachable by any client completing the standard OAuth2/OIDC redirect flow with a valid `code`/`state` once the operator has enabled and configured OIDC authentication. No operator/admin privilege is needed to trigger it — the fault is purely a missing-`return` bug that fires whenever the ID token's claims lack a string `email` field, which is plausible in normal, non-malicious OIDC deployment configurations (e.g., missing `email` scope) and directly under an attacker-or-misconfigured-IdP's control if they can influence what claims are returned.

## Recommendation
Add the missing `return` immediately after the error response in the `email` claim check:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Also add `return` after the DB-insert error block at lines 257-260 so a failed session-creation is never followed by `ginSession.Save()` and a success response.

## Proof of Concept
1. Configure an OIDC authenticator provider whose returned ID token/claims omit `email` (or return it as non-string/null) — realistic if IdP scope config excludes `email`.
2. Complete the standard OAuth2 redirect and call the token-exchange endpoint (`handleTokenExchange`) with a valid `code` and matching `state`.
3. Token exchange, ID-token verification, and claims parsing (`idToken.Claims`, `ExtractIDClaimValues`) all succeed, but `claims["email"].(string)` fails; the handler logs the error and writes an interim 500 body without returning.
4. Execution continues into `IDClaimsToUserRole`, inserts into `oidc_sessions` with `user_email = ""`, calls `ginSession.Save()`, and finally emits `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})`.
5. Verify with a subsequent authenticated request using the returned session cookie that a valid session now exists tied to the empty-string identity, despite the earlier logged/written claim-validation failure.
