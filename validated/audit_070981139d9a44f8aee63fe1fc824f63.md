### Title
Webhook `shop` identity is read from an unauthenticated header while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` for HMAC verification, but its `to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled directly from HTTP headers that are never included in the signed content. `Registry.process` verifies the HMAC of the body and then forwards `request.shop` — an unauthenticated value — to the app's webhook handler as the tenant identifier.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header. [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop` (and `topic`, `api_version`, `webhook_id`) is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic binding to the signature at all: [3](#0-2) 

`Registry.process` validates only the body's HMAC, then passes the *unverified* `request.shop` on to the app's handler as the tenant identity: [4](#0-3) 

This breaks the identity binding: `HMAC-valid(raw_body) == HMAC-valid(shop-domain header)` is assumed by any host application that trusts `WebhookMetadata#shop` as authenticated (per the gem's own documented usage in `docs/usage/webhooks.md`), but the two are not actually the same — the header can be freely altered without invalidating the signature, since the signature never covers it.

### Impact Explanation
Any unprivileged internet user who can obtain one valid `(raw_body, hmac)` pair for the app — trivially available to any merchant who installs the app on their own store and receives one legitimate webhook — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still pass (it never looks at the header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the attacker-chosen shop. Any host application that keys tenant-scoped logic (e.g., data updates, session lookups, per-shop side effects) off `WebhookMetadata#shop` as if it were authenticated will act on behalf of, or attribute data to, a shop the attacker does not control — a cross-tenant identity confusion.

### Likelihood Explanation
High for any developer following the gem's documented pattern (`Registry.process` -> handler receiving `WebhookMetadata`) without additionally re-validating shop identity out-of-band. The attacker needs no secrets — only a body/HMAC pair from their own legitimate install, which is trivial to obtain, plus the ability to send arbitrary HTTP headers to the app's public webhook route.

### Recommendation
Include the tenant-identifying header(s) (`shop-domain`, and ideally `topic`/`webhook-id`) in the signable content used for HMAC verification, or independently bind/verify the `shop-domain` header against the shop derivable from the signed payload before it is exposed via `WebhookMetadata`. At minimum, document loudly that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier by consuming applications.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and receives one legitimate webhook delivery, capturing `raw_body` and the `shopify-hmac-sha256` header (valid because Shopify signed it with the app's real secret).
2. Attacker POSTs to the app's public webhook endpoint with the exact same `raw_body` and `hmac` header, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses this successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the (correct) HMAC. [5](#0-4) 
4. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and performs tenant-scoped actions as if the event genuinely originated from `victim-shop.myshopify.com`.
