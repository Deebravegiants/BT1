### Title
Webhook Shop/Topic Identity Not Bound by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `HmacValidator.validate` verifies the HMAC exclusively against that raw body. The `shop`, `topic`, and `webhook_id` values are read straight from HTTP headers and are never included in the signed material, yet `Registry.process` trusts `request.shop` to identify the tenant that the webhook belongs to when constructing `WebhookMetadata` and dispatching it to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop`/`topic`/`webhook_id` are pulled from unauthenticated headers: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC purely over `to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` accepts any request whose body/HMAC pair validates, then builds `WebhookMetadata` using `request.shop` — a value that was never part of the signed bytes — and hands it to the app's handler as the tenant identity: [4](#0-3) 

The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler, i.e. it advertises that the resulting `shop` attribution is trustworthy: [5](#0-4) 

This breaks the identity binding `shop authenticated == shop used by the handler`. Because the HMAC signs only the body, any valid (body, HMAC) pair generated for one shop (which the app itself legitimately receives whenever that shop’s webhooks fire) remains valid when replayed with a different `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header value. The `topic` header suffers the same gap.

### Impact Explanation
An unprivileged actor who installs the app on their own store (a normal, unprivileged action requiring no leaked credentials) will receive legitimately signed webhooks for their own shop. By replaying the exact same body+HMAC to the app's webhook endpoint while substituting the shop-domain header with a victim merchant's domain, the attacker causes the app to process attacker-controlled webhook content under the identity of a different, non-consenting tenant (`WebhookMetadata#shop` becomes the victim's domain while the body is entirely attacker-supplied). Any app logic that trusts `data.shop` to scope database writes, job enqueuing, or per-tenant business logic (as encouraged by the gem's own docs example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be corrupted with attacker data attributed to the victim tenant — a cross-tenant integrity issue.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple merchants: obtaining a valid (body, HMAC) pair requires nothing more than operating your own store with the app installed (no secrets, no privileged access), and swapping an HTTP header on the replayed request is trivial.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signed material (or otherwise cryptographically bind them to the body), and reject requests where the header-derived shop/topic do not match what a signed envelope attests to, matching Shopify's guidance that only the raw body is HMAC-covered but requiring the app to independently confirm the request's shop domain is one it has an active, registered webhook/session for before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify sends a legitimately signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker crafts `B` to contain arbitrary attacker-controlled JSON (they control the order/resource on their own store) before triggering the event, so `B`'s content is attacker-chosen.
3. Attacker POSTs the same `B` and `H` to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` in [6](#0-5)  succeeds because it only checks `B` against `H`.
5. `Registry.process` in [4](#0-3)  dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` to the app's handler, which processes attacker data as if it belonged to the victim tenant.
