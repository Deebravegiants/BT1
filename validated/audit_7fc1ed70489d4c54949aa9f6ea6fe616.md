### Title
Session-key private keys for IntentGatewayV2 order solver-selection are persisted to local disk in plaintext, unencrypted and without restrictive file permissions - ([File: sdk/packages/sdk/src/storage/index.ts])

### Summary
`createSessionKeyStorage` in the Hyperbridge SDK persists the disposable **session private key** used to authorize solver selection for IntentGatewayV2 orders. On Node.js — the SDK's default/production environment — this data is written via `unstorage`'s filesystem driver to `./.hyperbridge-cache` as plain JSON, with no encryption and no restrictive file mode, unlike other secret-handling code in the same monorepo (e.g. `tunnel/keys.ts`, which explicitly writes private keys with `mode: 0o600`). This mirrors the CWE-312 root cause in the Spark advisory: sensitive key material reaches local disk unencrypted.

### Finding Description
`createSessionKeyStorage` stores `SessionKeyData`, which includes `privateKey: HexString`, keyed by `session-key:<commitment>` and `session-key-address:<address>`: [1](#0-0) 

The value is serialized with plain `JSON.stringify` and handed to the underlying storage driver with no encryption step: [2](#0-1) 

On Node.js, `load-driver.ts` always resolves to the Node driver: [3](#0-2) 

and that driver is a plain `unstorage` filesystem driver writing under a predictable, unencrypted local directory (`./.hyperbridge-cache` by default) with no key encryption and no explicit file-mode hardening: [4](#0-3) 

This session key is not cosmetic — it is the cryptographic authority that decides which solver is allowed to fill a user's escrowed intent order. `BidImpl.signSelection` fetches the cached session key from this storage and signs the on-chain `SelectSolver` EIP-712 message with it: [5](#0-4) 

The signature is verified on-chain and stored in transient storage to gate which solver's `fillOrder` call is authorized: [6](#0-5) 

and enforced by the solver's ERC-4337 account during `validateUserOp`: [7](#0-6) 

Compare this to the codebase's own secure pattern for equivalent secret material — the tunnel private keys are written atomically with `mode: 0o600`: [8](#0-7) 

No equivalent protection (encryption or restrictive permissions) exists for the IntentGatewayV2 session key store, so it is written with the process umask default (commonly world/group-readable), unencrypted, for the lifetime the key remains cached.

### Impact Explanation
Whoever can read this unencrypted, unrestricted file (a co-tenant process on a shared host, another user on the same machine, a container filesystem snapshot/backup, or any local malware/dependency with fs read access) obtains the raw session private key for a live, escrowed order. With it, an attacker can forge the `SelectSolver` EIP-712 signature themselves and call `IntentGatewayV2.select`/drive `SolverAccount.validateUserOp` to authorize a colluding or attacker-controlled solver for that order — hijacking solver selection away from the best/legitimate bid the user actually intended to accept. Because the filled output amount is determined by whichever solver is authorized to execute `fillOrder`, this allows an attacker to force settlement at a worse price than the honest auction would have produced, directly extracting value from the user's escrowed funds. This is a concrete route to theft of value reachable from a single order placement, matching the "unauthorized app action" / fund-loss bar in the validation rules.

### Likelihood Explanation
Any user of the SDK's default Node.js session-key storage (used for every IntentGatewayV2 order with solver selection enabled) is exposed as long as the process's local filesystem is not fully single-tenant and hardened — a common condition in shared hosting, CI runners, containerized deployments with shared volumes, or any environment with another local process/service. No special privilege is needed beyond local file read access to the `.hyperbridge-cache` directory; no on-chain privilege or governance action is required.

### Recommendation
- Encrypt session-key material at rest before writing to the Node filesystem driver, or bind the file to an ephemeral OS keychain/secure enclave when available.
- At minimum, apply restrictive file permissions (e.g., `mode: 0o600`) as already done in `tunnel/keys.ts`, and avoid writing the raw plaintext value straight from `JSON.stringify`.
- Consider reducing the exposure window by minimizing how long a session private key is retained on disk (e.g., clearing it immediately after the order is finalized/cancelled) and defaulting `basePath` to a directory with locked-down permissions rather than a predictable relative path.

### Proof of Concept
1. A user places an IntentGatewayV2 order with `solverSelection` enabled via the SDK; the SDK generates a session keypair and calls `setSessionKey`, which persists `{ privateKey, address, commitment, createdAt }` as plaintext JSON under `./.hyperbridge-cache/session-key:<commitment>` on the host filesystem (`sdk/packages/sdk/src/storage/index.ts` `setSessionKey`, using the Node fs driver in `drivers/node.ts`).
2. Any local actor with read access to that path (co-tenant process, container volume mount, backup) reads the file and extracts `privateKey`.
3. The attacker signs their own `SelectSolver(commitment, solver)` EIP-712 message with the stolen key (`CryptoUtils.signSolverSelection`) naming a solver of their choosing.
4. The attacker (or colluding solver) submits this signature through `SolverAccount.validateUserOp` → `IntentGatewayV2.select`/`fillOrder`, which recovers the session key from the signature and authorizes the attacker-chosen solver instead of the legitimate winning bidder, settling the order at the attacker's chosen (worse) output amount.

	private async signSelection(): Promise<HexString> {
		if (this.cachedSignature) return this.cachedSignature

		const commitment = this.order.id as HexString
		const sessionKeyAddress = this.order.session as HexString

		const sessionKeyData = this.sessionPrivateKey
			? { privateKey: this.sessionPrivateKey }
			: await this.ctx.sessionKeyStorage.getSessionKeyByAddress(sessionKeyAddress)
		if (!sessionKeyData) {
			throw new Error(`SessionKey not found for commitment: ${commitment}`)
		}

		const signature = await CryptoUtils.signSolverSelection(
			commitment,
			this.solverAddress,
			this.domainSeparator,
			sessionKeyData.privateKey,
		)
		if (!signature) {
			throw new Error("Failed to sign solver selection")
		}

		this.cachedSignature = signature
		return signature
	}

    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }
