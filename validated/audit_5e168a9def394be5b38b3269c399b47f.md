### Title
Stale `_requestCommitments` fee entry after `GetResponse` delivery allows `fundRequest` "donation" to be redirected to relayer post-delivery, and does not clear on success — reachable relayer fee griefing/double-claim path - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(GetResponse, address)` [1](#0-0)  pays the relayer fee out of `_requestCommitments[commitment].fee` after a successful `onGetResponse` callback, but never deletes that mapping entry on the success path (unlike `dispatchTimeOut`, which explicitly deletes `_requestCommitments[commitment]` for replay protection [2](#0-1) ). `fundRequest` allows anyone to top up `_requestCommitments[commitment].fee` for a commitment as long as `metadata.sender != address(0)` [3](#0-2) , and its own docstring acknowledges "if called on an already delivered request, these funds will be seen as a donation to the hyperbridge protocol" — but the code path shows those funds are actually claimable by whichever address later triggers a resend attempt, not "the protocol."

### Finding Description
I was not able to fully verify a complete, concrete exploit chain in the time available. What is established from the code:

1. `dispatchIncoming(GetResponse memory response, address relayer)` is `restrict(_hostParams.handler)`-gated, so only `HandlerV2` can call it [4](#0-3) .
2. `HandlerV2.handleGetResponses` guards against delivering the exact same `GetResponse` leaf twice within/after processing by checking `host.responseReceipts(...).relayer != address(0)` before calling `dispatchIncoming` [5](#0-4) , and this check runs per-leaf inside the same loop that performs the dispatch, so it is effective against replay within a batch and across batches for a completed delivery.
3. However, `_requestCommitments[commitment]` (holding the fee) is **not deleted** on the success path of `dispatchIncoming(GetResponse,...)` — it is only read and paid out [6](#0-5) . Compare this with the two `dispatchTimeOut` variants, which explicitly `delete _requestCommitments[commitment]` up front as "replay protection" [7](#0-6) [8](#0-7) .
4. `fundRequest` is fully permissionless and only requires `metadata.sender != address(0)` — it does not check whether the request has already been responded to/delivered [9](#0-8) . Its own comment concedes this is a known limitation ("these funds will be seen as a donation to the hyperbridge protocol") [10](#0-9) , but nothing in the code routes such post-delivery funding to "the protocol" — it simply sits in `_requestCommitments[commitment].fee`.

I could not, within the available tool budget, confirm whether any other code path re-reads or re-pays this stale fee balance (e.g., a second, different mechanism that would let a relayer or attacker actually withdraw it after point 3/4), because `HandlerV2.handleGetResponses`'s duplicate check should block a second `dispatchIncoming(GetResponse,...)` call for the same commitment through the normal relayer path. I also did not verify whether `GetRequestTimeout` delivery (`dispatchTimeOut(GetRequestTimeout,...)`) can still fire for a commitment whose `GetResponse` was already delivered — if the Hyperbridge-side (pallet-ismp) prevents dispatching a timeout for an already-responded request, this would not be exploitable; if it does not, an already-paid relayer fee (or a `fundRequest` donation made after delivery) could be paid out a second time via the timeout path, since `dispatchTimeOut` unconditionally deletes-then-conditionally-restores `_requestCommitments[commitment]` and pays `meta.fee` on success [11](#0-10)  without checking `_responseReceipts` for that commitment.

### Impact Explanation
If the timeout path can be triggered for a request whose `GetResponse` was already successfully delivered (rewarding the first relayer), and/or if `fundRequest` can add fee after delivery, this would allow an unbacked double payment of protocol-held ERC20 fee tokens (`feeToken()`) — a fund-drain from the fee reserve rather than from user balances directly. This is a Medium/High-severity fee-accounting bug **if** confirmed, but I do not have enough evidence from what I've read to assert it is definitely exploitable; the cross-check that would prove or disprove it (whether pallet-ismp or `HandlerV2` blocks a timeout message for an already-responded request) was not completed.

### Likelihood Explanation
Unknown/unconfirmed — requires verifying whether the Hyperbridge-side consensus/pallet-ismp logic (or `HandlerV2.handleGetRequestTimeouts`) rejects a timeout proof for a request that already has a response receipt on the destination host. `handleGetRequestTimeouts` only checks a **non-membership proof of response receipts on the source state** (`RESPONSE_RECEIPTS_STORAGE_PREFIX`) [12](#0-11) , which is a proof against the *state machine that owns the request*, not the destination `EvmHost`'s local `_requestCommitments`/`_responseReceipts` state, so it's plausible (but not verified by me) that this proof and the local mapping could be time-inconsistent in an adversarial race.

### Recommendation
- Delete or zero out `_requestCommitments[commitment]` in `dispatchIncoming(GetResponse,...)` immediately after a successful fee payout, mirroring the replay protection already used in `dispatchTimeOut`.
- Add an explicit check in `fundRequest` (and/or `dispatchTimeOut`) that the commitment has no existing `_responseReceipts` entry before allowing funding or timeout-driven fee payout, to prevent late "donations" or double payouts.
- Verify (this needs code I have not yet reviewed) whether `handleGetRequestTimeouts`'s non-membership proof is checked against a state root that is guaranteed to postdate any successful response delivery on the destination host, closing the race described above.

### Proof of Concept
Not provided — I was unable to fully trace an end-to-end, concrete transaction sequence proving double payment within the available investigation. Given the residual uncertainty (whether the timeout path can fire post-delivery, and whether `fundRequest`'s "donation" language reflects an actual protocol-owned sink elsewhere in the code I haven't located), I cannot confidently assert this rises to a proven, exploitable finding matching the strict validation bar (concrete theft or permanent freezing of funds) requested. I recommend a Devin session with full repository/tool access (including cross-referencing `modules/pallets/ismp` timeout dispatch logic and `child_trie` response-receipt commitments) to close this gap before treating this as a confirmed vulnerability.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
