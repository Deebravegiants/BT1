### Title
Webhook shop/topic identity spoofing via HMAC that only signs the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content purely from the raw HTTP body, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by `Registry.process` to dispatch and label the webhook come from unauthenticated HTTP headers. This is the same "field acted on but not covered by the HMAC" defect shape as the `GorplesCoin._update()` report: the code validates one artifact (the body bytes) but acts on a different, unauthenticated artifact (the shop-domain header) as though it were verified.

### Finding Description
`VerifiableQuery#to_signable_string` for `Webhooks::Request` returns only `@raw_body`: [1](#0-0) 
and `hmac` is read straight from the `hmac-sha256` header: [2](#0-1) 
`shop`, `topic`, `api_version`, and `webhook_id` are all pulled from separate, un-signed headers: [3](#0-2) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [4](#0-3) 

`Registry.process` treats a passing HMAC check as authorization to trust `request.shop`, `request.topic`, and `request.webhook_id` verbatim and hands them to the host app's handler: [5](#0-4) 

The binding that should hold is: `hmac-verified payload == (body, shop, topic, webhook_id)`. In reality it is only `hmac-verified payload == body`; `shop`/`topic`/`webhook_id` are asserted by the caller and taken on faith. Anyone who can capture (or otherwise legitimately obtain, e.g. via their own store's installed app) one valid `(body, hmac)` pair can replay it to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` header. The signature still validates, because those headers are outside the signed content, yet `WebhookMetadata.shop`/`topic`/`webhook_id` — the values the host application uses to decide which tenant's data store to write into — reflect attacker-controlled headers rather than the true origin.

### Impact Explanation
This breaks the tenant boundary the HMAC check is supposed to enforce: it lets a party with any single valid `(body, hmac)` pair impersonate a different shop's webhook to the host application, causing that application to attribute attacker-supplied payload data (order/customer/product content) to a victim tenant, or to fire mandatory-compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) against a shop of the attacker's choosing. This is a cross-tenant data-integrity/identity-binding failure reachable by an unprivileged actor holding no merchant credential, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate: the attacker needs at least one legitimately observed `(body, hmac)` pair, which they can obtain simply by installing the app on their own store and capturing the resulting webhook call (no secret or privileged credential required), then replaying it against the shared public webhook endpoint with a modified shop header.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content (or otherwise cryptographically bind them to the body), and have `Registry.process`/`HmacValidator.validate` verify the full tuple rather than just the raw body before constructing `WebhookMetadata`.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; capture a real webhook POST, including its body and `X-Shopify-Hmac-Sha256`/`X-Shopify-Shop-Domain` headers.
2. Replay the identical body and HMAC header to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the body against the secret; `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, so the host application's downstream logic (data storage, redaction, compliance action) is executed as if it genuinely originated from `victim.myshopify.com`.
