### Title
Webhook `shop` (and topic/webhook-id) identity is not covered by the HMAC, enabling cross-tenant webhook replay/confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) and routing metadata (`topic`, `api_version`, `webhook_id`) from raw HTTP headers, while `to_signable_string` used for HMAC verification only covers `@raw_body`. `Registry.process` trusts `request.shop`/`request.topic` for handler dispatch and forwards them unchecked to the app's webhook handler as `WebhookMetadata`.

### Finding Description
`HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` field [4](#0-3) . For webhook requests, `to_signable_string` is only the raw body [2](#0-1) , so the `shopify-shop-domain`, `shopify-topic`, `shopify-api-version`, and `shopify-webhook-id` headers are entirely outside the cryptographic binding. `Registry.process` uses `request.topic` to look up the handler and forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to the handler as authenticated-looking `WebhookMetadata`, after only checking the body HMAC [1](#0-0) .

Because `api_secret_key` is shared by the app across *all* installed shops (it is not per-tenant), any party capable of obtaining one legitimately-signed webhook body+HMAC pair for their own shop (e.g., by installing the app themselves) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a different, victim shop. The equality the code implicitly (and incorrectly) assumes is:

`shop authenticated by the HMAC == shop delivered to the handler via request.shop`

but in reality only the body is authenticated; the `shop` binding is asserted from an attacker-controllable header.

### Impact Explanation
This breaks the tenant boundary between shops sharing the same app installation: an attacker-controlled/replayed request can cause the host application's webhook handler to process data under an arbitrary victim shop's identity, since `data.shop` (used by host apps to select/persist per-tenant records) originates from an unauthenticated header rather than from the HMAC-verified payload. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one valid `(body, hmac)` pair, which any shop that has installed the app can obtain for its own legitimate webhook deliveries (no leaked credentials or privileged access required — merely being one of many merchants using the app, a normal, unprivileged flow). They then need only craft an HTTP request to the app's public webhook endpoint with the captured body/HMAC and a spoofed `x-shopify-shop-domain` header — no host-app misuse or credential theft is needed, and the gem provides no cross-check between header shop and any body-derived tenant identifier.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string (or otherwise cryptographically bind them to the body, e.g. by requiring the host app to verify the shop domain against its own webhook subscription registration/session store before trusting `request.shop`), so `Request#shop` cannot be forged independently of the signed payload. Document to consumers that the shop header is currently unauthenticated and must be cross-validated against a known/expected shop before use in tenant-scoped operations.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both under the same `api_secret_key`.
2. Attacker's shop receives a legitimate webhook: `raw_body = '{"id":123}'`, `x-shopify-hmac-sha256 = Base64(HMAC-SHA256(api_secret_key, raw_body))`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object whose `hmac` still validates against `raw_body` [5](#0-4) , because the shop-domain header was never part of the signed content.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true`, and dispatches to the handler with `shop: request.shop` == `"victim-shop.myshopify.com"` [6](#0-5) , causing the host app to process attacker-controlled data under the victim shop's tenant context.
