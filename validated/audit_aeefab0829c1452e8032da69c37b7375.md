### Title
Unaccounted assets received by Emporium in CASE 2 stateless calls can be stolen by any subsequent caller - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 branch executes an arbitrary `op.endpoint.call{value: op.value}(op.callData)` as `msg.sender == Emporium`, but the only bookkeeping performed afterward is an ERC20/ETH balance diff over `circomData.erc20TokenAddresses`. Any non-enumerated asset (e.g. an ERC721 minted or transferred to Emporium's own address) is left sitting at the shared Emporium contract with zero on-chain tracking, and because `op.endpoint` is unrestricted in CASE 2, any other unprivileged user can submit their own valid proof/transact whose CASE 2 op calls `transferFrom`/`safeTransferFrom` on that same asset contract to sweep it out.

### Finding Description
The equality that should hold is: `asset_owner_after_victim_tx == circomData.stealthAddressStructure.stealthAddress_of_victim` (i.e., anything the victim's authorized action produces should end up attributable/returnable to the victim). Instead, because CASE 2 routes the call directly through Emporium (`address(this)` inside the call is Emporium, a contract shared by all users) rather than through a per-user `HinkalWallet` (which is what CASE 1 stateful ops use, and which is the only contract in the codebase specifically built with `onERC721Received`/EIP-1271 semantics for a *single* signer), the resulting `fakeNFT.ownerOf(tokenId)` is simply `address(emporium)`.

`runAction`'s post-processing loop (`balancesBefore`/`balancesAfter`, `handleOut`) only iterates `circomData.erc20TokenAddresses` [4](#0-3) ; there is no code path anywhere in `Hinkal.sol` or `EmporiumUpgradeable.sol` that inspects or protects arbitrary ERC721/ERC1155 balances at the Emporium address. Nothing in `verifyWallet`, `performHinkalChecks`, `dimensionsCheck`, or the circuit constraints (`inTotal + amountChanges === outTotal`) constrains non-ERC20 assets at all — they are entirely outside the proof's public-input vector. Consequently, once any user's CASE 2 op causes Emporium to become the owner/holder of such an asset, a second, completely unrelated and unprivileged attacker can call `transact` with their own valid proof (for their own UTXOs) and an `externalActionData` whose `EmporiumStack.ops` includes `{endpoint: fakeNFT, invokeWallet: false, value: 0, callData: transferFrom(emporium, attacker, tokenId)}`. Since CASE 2 places no restriction on `op.endpoint` (only on the callData selector matching `callHinkalWallet`/`doSendToRelay`), this call succeeds, and `fakeNFT.ownerOf(tokenId)` becomes the attacker's stealth address — never the original depositor's.

### Impact Explanation
The attacker (or any observer) can steal any non-ERC20/non-ETH asset that transiently ends up owned by the Emporium contract as a byproduct of another user's CASE 2 stateless op (e.g., NFTs from a marketplace purchase, airdrop claim, or mint routed through Emporium). This is "executing calls or moving assets a wallet owner or prover never authorised," matching the High severity category. It is repeatable against any future asset left at Emporium's address by any user who (knowingly or not) routes an NFT-producing action through the stateless CASE 2 path instead of the per-user `HinkalWallet` CASE 1 path.

### Likelihood Explanation
Preconditions: some prior transaction (by any user) must have caused Emporium to hold an asset not enumerated in `erc20TokenAddresses` (e.g., a CASE 2 call to an NFT contract's `mint`/`transferFrom` targeting `address(emporium)`). This requires no privileged role — the attacker only needs their own valid ZK proof for their own UTXOs and full control over `externalActionData`/`EmporiumStack` as already permitted by design. Given that `Transferer.sol` implements `onERC721Received`/`onERC1155Received` [5](#0-4) , the protocol clearly anticipates non-ERC20 assets reaching this contract, making the scenario realistic rather than purely theoretical, though it does require a specific sequence (an asset-producing CASE 2 op followed by a sweep) rather than being triggerable in isolation.

### Recommendation
Restrict CASE 2 (`invokeWallet == false`) stateless calls so they cannot leave non-enumerated assets custodied at the shared `Emporium` address: either (a) require that any endpoint invoked in CASE 2 whose result is a non-ERC20 asset must route the asset directly to a per-user `HinkalWallet` (never to `address(this)`/Emporium), (b) add an allowlist of endpoints usable in CASE 2, or (c) add generic NFT/1155 accounting and force `handleOut`-style forwarding for any asset received during the call, tied to `circomData.stealthAddressStructure`.

### Proof of Concept
1. Deploy `EmporiumUpgradeable` plus a `FakeERC721` with `mint(address to)`.
2. Victim (user A) calls `transact` with a valid proof, `circomData.erc20TokenAddresses` containing only unrelated ERC20s, and `externalActionData` encoding an `EmporiumStack` with one CASE 2 op: `{endpoint: fakeNFT, invokeWallet:false, value:0, callData: abi.encodeWithSelector(FakeERC721.mint.selector, address(emporium))}`. Assert `fakeNFT.ownerOf(tokenId) == address(emporium)`.
3. Attacker (user B, unrelated) calls `transact` with their own valid proof and their own `EmporiumStack` containing a CASE 2 op: `{endpoint: fakeNFT, invokeWallet:false, value:0, callData: abi.encodeWithSelector(IERC721.transferFrom.selector, address(emporium), attackerStealthAddress, tokenId)}`.
4. Assert `fakeNFT.ownerOf(tokenId) == attackerStealthAddress` and `attackerStealthAddress != victimStealthAddress`, proving the asset produced by the victim's authorized action was stolen by an unrelated, unprivileged party.
