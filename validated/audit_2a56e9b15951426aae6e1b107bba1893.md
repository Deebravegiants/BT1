### Title
Session cookie `MaxAge` hardcoded to 30 days, contradicting documented `SessionTimeout` idle-expiry behavior - ([File: core/services/chainlink/config_web_server.go])

### Summary
The `WebServer.SessionOptions()` function hardcodes the gin session cookie `MaxAge` to `86400 * 30` (30 days) regardless of the operator-configured/documented `SessionTimeout` value, which is documented and defaulted to `15m`. [1](#0-0) [2](#0-1) 

### Finding Description
`docs/CONFIG.md` and `core/config/docs/core.toml` document `SessionTimeout` as "the amount of idle time to elapse before session cookies expire. This signs out GUI users from their sessions," with a default of `15m`. [3](#0-2) 

However, the actual browser-facing cookie's expiry (`MaxAge`) set via `sessionStore.Options(config.WebServer().SessionOptions())` in `core/web/router.go` is a hardcoded constant of 30 days, completely decoupled from the `SessionTimeout` config value: [1](#0-0) [4](#0-3) 

Server-side idle expiry is enforced separately in the DB query (`last_used + $2 >= now()`), using `sessionDuration` (derived from `SessionTimeout`), which correctly reaps sessions server-side: [5](#0-4) 

This is the same bug class as the reported `HALVING_INTERVAL` issue: a hardcoded value that contradicts documented, configurable behavior. Here, the discrepancy means the browser cookie itself will remain valid/sent for up to 30 days regardless of the operator's configured `SessionTimeout`, even though the documentation implies the cookie's lifetime is tied to that setting.

### Impact Explanation
The practical security impact is limited because server-side session validity is still enforced independently via `findValidSession`, which checks `last_used + sessionDuration >= now()`. So even if the browser retains the cookie for 30 days, an idle session will be rejected server-side once `SessionTimeout` (default 15m) elapses. The main consequence is a stale, unusable cookie persisting in the browser/session storage far longer than documented — a minor client-side artifact/persistence issue and a documentation/config-behavior mismatch, not a direct authentication or session bypass.

### Likelihood Explanation
This triggers on every authenticated session for every user by default (no special conditions needed) since `SessionOptions()` is always used to configure the cookie store. [4](#0-3) 

### Recommendation
Derive the cookie's `MaxAge` from the configured `SessionTimeout` (and/or `SessionReaperExpiration`) rather than a hardcoded constant, so client-side cookie lifetime matches the documented, operator-configurable idle-timeout behavior.

### Proof of Concept
Not applicable as an exploit PoC — this is a configuration/documentation-behavior mismatch, not a bypassable vulnerability, since server-side enforcement in `findValidSession` independently limits session validity to `SessionTimeout`. No unauthorized access, secret disclosure, or authentication bypass results from this discrepancy.

// findValidSession finds an unexpired session by its ID and returns the associated email.
func (o *orm) findValidSession(ctx context.Context, sessionID string) (email string, err error) {
	if err := o.ds.GetContext(ctx, &email, "SELECT email FROM sessions WHERE id = $1 AND last_used + $2 >= now() FOR UPDATE", sessionID, o.sessionDuration); err != nil {
		o.lggr.Infof("query result: %v", email)
		return email, pkgerrors.Wrap(err, "no matching user for provided session token")
	}
	return email, nil
}
