## Title
Fee-on-Transfer tokens cause unbacked LP minting and pool insolvency due to nominal-amount accounting instead of balance-delta accounting - (File: program/src/processor.rs)

### Summary
Raydium's AMM program computes deposit/mint and swap amounts using the *nominal* (declared) transfer amount rather than the actual delta of tokens received in the vault. When a fee-on-transfer (deflationary) SPL token is used as `coin`/`pc` mint of a pool, the vault receives less than the amount the program assumes was transferred, causing LP over-minting on deposit and pool-reserve insolvency on swap, eventually leading to failed/DOS'd operations for later users — the same root cause described in the referenced Allo `_fundPool`/`increasePoolAmount` report (accounting on assumed amount instead of `balanceBefore`/`balanceAfter`).

### Finding Description
In `process_deposit`, the pool's current reserves are read live from vault balances via `Self::unpack_token_account` [1](#0-0) , and `mint_lp_amount` is derived from the requested `deduct_coin_amount`/`deduct_pc_amount` against these reserves *before* any transfer occurs [2](#0-1) . The program then calls `Invokers::token_transfer` for the nominal `deduct_coin_amount`/`deduct_pc_amount` and unconditionally mints `mint_lp_amount` LP tokens based on that nominal amount, without re-checking the vault's actual post-transfer balance [3](#0-2) . `Invokers::token_transfer` is a thin wrapper around `spl_token::instruction::transfer` with no balance-before/after verification [4](#0-3) .

If either mint is a fee-on-transfer token, the vault actually receives less than `deduct_coin_amount`/`deduct_pc_amount`, but LP tokens are minted as if the full nominal amount arrived, meaning the depositor receives LP tokens backed by fewer real tokens than accounted for — diluting/under-collateralizing existing LP holders.

The same nominal-amount pattern exists in all four swap instructions (`SwapBaseIn`, `SwapBaseOut`, `SwapBaseInV2`, `SwapBaseOutV2`). `swap_amount_out`/`swap.amount_out` is computed from `total_pc_without_take_pnl`/`total_coin_without_take_pnl` (live vault balances) together with the full nominal `swap.amount_in`, then the program transfers the nominal input amount in via `Invokers::token_transfer` and unconditionally pays out the computed output via `Invokers::token_transfer_with_authority`, again without verifying how much was actually received in the input vault [5](#0-4) [6](#0-5) [7](#0-6) . If the input token charges a transfer fee, the vault receives less than `swap.amount_in`/`swap_in_after_add_fee`, yet the program still pays out the full output computed as if the entire nominal input arrived. Each swap therefore drains slightly more value from the paying-out side of the pool than it actually received, progressively under-collateralizing the pool.

Because reserves for the *next* instruction are always re-read live from the vault (`unpack_token_account`), the deficit is not immediately visible as a stale cached counter (unlike Allo's `poolAmount`), but it compounds every deposit/swap cycle: LP shares minted are backed by less than their nominal value, and swap outputs are paid from reserves that were never fully replenished by the corresponding input transfer. Eventually a vault can be drained to the point that `SwapDirection` checks like `if swap_amount_out >= total_pc_without_take_pnl` or the underlying SPL transfer fail with insufficient funds, blocking further swaps/withdrawals for legitimate participants — mirroring the "DOS on distribution/withdrawal" impact of the source report.

Nothing in `process_initialize2` (permissionless, reachable via `Initialize2`) restricts `coin_mint`/`pc_mint` to non-fee-on-transfer tokens, so any pool creator can set up such a pool [8](#0-7) , and this is reachable purely through user-submitted `Deposit`/`SwapBaseIn`/`SwapBaseOut` instructions with attacker-chosen (fee-on-transfer) mints.

### Impact Explanation
- Unbacked LP token minting: LPs providing fee-on-transfer tokens receive full-value LP shares while the vault holds less, socializing losses onto other LPs upon withdrawal.
- Insolvent pool accounting: repeated swaps involving a fee-on-transfer input token pay out full computed amounts while receiving less, progressively depleting the counter-asset vault.
- End-state DOS: once reserves are sufficiently drained, `InsufficientFunds` checks in swap/withdraw paths [9](#0-8)  and `process_withdraw`'s `coin_amount < amm_coin_vault.amount && pc_amount < amm_pc_vault.amount` guard [10](#0-9)  begin failing, freezing remaining LPs' ability to withdraw their share.

This satisfies "unbacked LP minting" and "insolvent pool accounting" impact criteria.

### Likelihood Explanation
Any unprivileged user can create a pool via `Initialize2` for an arbitrary SPL mint pair (including a fee-on-transfer token), then deposit/swap normally — no privileged signer or off-chain component is required. The likelihood depends on the market choosing to list such a token pool, which is plausible given permissionless pool creation is a core feature of Raydium.

### Recommendation
For deposit, LP-mint calculation and swap accounting should measure the actual vault balance delta (`balance_after - balance_before` read via `unpack_token_account` immediately before and after `Invokers::token_transfer`) rather than relying on the nominal instruction-supplied amount, mirroring the standard mitigation for fee-on-transfer tokens.

### Proof of Concept
1. Attacker creates a pool via `Initialize2` where `coin_mint` is a deflationary/fee-on-transfer SPL token (e.g., charges 1% on transfer) and `pc_mint` is a normal token.
2. Attacker (or any LP) calls `Deposit` with `max_coin_amount = 100_000_000` and a matching `max_pc_amount`. The program computes `mint_lp_amount` from the nominal `deduct_coin_amount = 100_000_000` [2](#0-1) , but `Invokers::token_transfer` only delivers 99_000_000 to `amm_coin_vault_info` due to the token's transfer fee [11](#0-10) . LP tokens minted correspond to 100M worth of coin, but vault only holds 99M — an immediate 1% under-collateralization.
3. Repeated `SwapBaseIn`/`SwapBaseOut` calls against this pool compute `swap_amount_out` from `swap.amount_in` as fully-received [12](#0-11) , but the vault only receives `amount_in * (1 - fee)`, while the full computed `swap_amount_out` of the counter-asset is paid out unconditionally [5](#0-4) , compounding the reserve deficit with every swap until withdrawals/swaps start failing due to insufficient vault balance.
