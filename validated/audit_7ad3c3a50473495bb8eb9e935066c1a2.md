This confirms the finding: the gem's documented API and workflow (`docs/usage/webhooks.md:125-136`) explicitly instructs developers to trust `ShopifyAPI::Webhooks::Registry.process` as verifying "the request did indeed come from Shopify," and to key business logic off `data.shop` (`docs/usage/webhooks.md:14,25-26`). The gem itself computes the HMAC only over the raw body, never the `shopify-shop-domain` header, so `Registry.process` gives no actual guarantee about which shop a webhook is attributed to.

### Title
Cross-Tenant Webhook Shop Spoofing via HMAC Bypass of Unsigned `shopify-shop-domain` Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, excluding all HTTP headers from the HMAC-signed content, yet `Request#shop` is derived exclusively from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header. `Registry.process` treats a valid HMAC as proof the whole request — including the shop attribution — came from Shopify, and forwards `request.shop` directly into `WebhookMetadata#shop`, which host apps are documented to trust as the tenant identifier for business logic.

### Finding Description
The binding that should hold is: `shop attribute trusted by handler == shop bound by the HMAC signature`. In this gem that equality does not hold.

- `Request#hmac` and `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:10-13,35-38`) show the signature only ever covers `@raw_body`.
- `Request#shop` (`lib/shopify_api/webhooks/request.rb:20-23`) reads the shop purely from a header, which is never part of `to_signable_string`.
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the HMAC via `Utils::HmacValidator.validate(request)` and then unconditionally builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, passing the unauthenticated header value straight to the app's handler.
- `Utils::HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) confirms only `verifiable_query.to_signable_string` (the raw body) is checked against the secret — headers are never included in the comparison.

Because the app's `client_secret` (`api_secret_key`) is shared across every shop that installs a given app, any merchant who has installed the app receives real, validly-signed webhook deliveries addressed to their own shop. Since the header carrying shop attribution is outside the HMAC, that merchant can capture one genuine `(raw_body, hmac header)` pair from their own tenant and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because the body and secret are unchanged, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain — a cross-tenant identity confusion the gem's own documentation encourages apps to rely on for authorization/routing decisions.

### Impact Explanation
This breaks the binding between "cryptographically verified sender" and "shop the payload is attributed to," enabling cross-tenant access: a malicious merchant can make the host application perform tenant-scoped actions (e.g., mandatory GDPR topics like `shop/redact`, `customers/redact`, `customers/data_request`, or any custom handler keyed by `data.shop`) against a shop they do not control, since the gem provides no mechanism to bind the header to the signed body.

### Likelihood Explanation
Any user who can install the app to their own store (the normal, unprivileged path for a public Shopify app) automatically gets a stream of validly-HMAC'd webhook bodies. Replaying a captured body with a modified `shopify-shop-domain` header against the app's own publicly reachable webhook endpoint requires no secret material and no elevated privilege beyond a routine app install.

### Recommendation
Include the shop domain (and topic/webhook id) in the HMAC-signed material, or independently verify `request.shop` against a shop already known to be associated with the requesting webhook subscription/session, before handing `WebhookMetadata` to handlers in `Registry.process`.

### Proof of Concept
1. Install the target public app on attacker-controlled shop `attacker.myshopify.com`; receive a legitimate webhook POST with header `shopify-shop-domain: attacker.myshopify.com`, some `raw_body`, and `shopify-hmac-sha256` computed over `raw_body` with the app's shared `client_secret`.
2. Replay the exact same `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but change the header to `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) returns `true` because it only checks `raw_body` against the secret.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the app to perform the webhook's action attributed to the victim tenant. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
