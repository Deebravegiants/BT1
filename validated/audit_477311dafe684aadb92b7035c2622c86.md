## Title
Webhook `shop-domain` header not bound by HMAC, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Utils::HmacValidator` verify a webhook's authenticity by computing an HMAC over the raw request body only. The `shop-domain` header — the value the gem hands to application handlers as the tenant identifier — is read independently and is never included in the signed bytes. This is the same "double counting" class of bug as the reported bug (two logically distinct fields treated as equivalent/interchangeable when they should be bound together): here, the field that is cryptographically verified (`raw_body`) and the field that is trusted as the tenant identity (`shop-domain` header) are not the same bytes, breaking the intended binding `verified_bytes == identity_bytes`.

### Finding Description
`Request#hmac` reads the `hmac-sha256`/`x-shopify-hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is a completely separate accessor pulled straight from the `shop-domain` header, outside of the signed content: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` compute and compare the HMAC using only `verifiable_query.to_signable_string` (i.e. the raw body) against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` checks only this body HMAC, then forwards `request.shop` — the unverified header — directly to the app's handler as the tenant identity: [4](#0-3) 

The gem's own documentation instructs apps to trust `data.shop` from `WebhookMetadata` as "The shop domain of the webhook" and to use it to route/store data per-tenant (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) [6](#0-5) 

Because the `api_secret_key` used to sign webhooks is shared across every shop that has installed a given app (it is the app's client secret, not a per-shop secret), any shop that has installed the app can obtain a genuinely-signed `(raw_body, hmac)` pair by triggering a real webhook on its own store. Since the HMAC never covers the `shop-domain` header, that same `(raw_body, hmac)` pair remains valid when replayed with an arbitrary `shop-domain` header value pointing at a different, victim shop.

**Binding broken:** `hmac_verified(raw_body)` ⇏ `shop_trusted_by_handler(header)`. The gem asserts these are equivalent (a validated webhook request implies a validated `(shop, body)` pair) but they are not — the equality `verified_bytes == identity_bytes` does not hold.

### Impact Explanation
This crosses a tenant boundary without needing the app's `client_secret`, an access token, or any privileged credential — only the ability to install the app on any shop (including the attacker's own free/dev store) and capture one legitimate webhook delivery. The attacker can then submit an HMAC-valid webhook to the app's public callback endpoint while asserting an arbitrary victim `shop-domain`. If the host application follows this gem's documented pattern of trusting `WebhookMetadata#shop` for tenant routing/storage (as shown in the gem's own docs example), this results in cross-tenant data injection/corruption — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is high for any app that: (1) allows public installation (typical for Shopify apps), and (2) follows the gem's own documented webhook-handling pattern of trusting `data.shop` without independently re-verifying shop ownership against the resource in the payload. No secrets need to be extracted — a legitimate webhook capture from the attacker's own shop is sufficient raw material to construct the forged request.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signable content so that a change to the asserted shop invalidates the signature, or alternatively require that the gem independently validate the received `shop-domain` header against the same shop context used to establish the app's registered session for that webhook subscription before dispatching to the handler. At minimum, the docs and `WebhookMetadata` should clearly warn that `shop` is not covered by the HMAC and must not be trusted as an unforgeable tenant identifier without additional binding.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com` (any user can do this for a public app).
2. Trigger any subscribed webhook topic (e.g., `orders/create`) on `attacker.myshopify.com`; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this pair is valid because it's signed with the app's shared `api_secret_key`.
3. Replay this exact `(raw_body, hmac)` pair to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) succeeds because it only checks `raw_body` against the HMAC.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's payload>, ...)`, causing the app to process attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
