Based on the code, `livestream::Agent` is a thread-based agent (`agent::Thread`), and per `agentwire/src/agent/thread.rs` its `run` method's own `match` only catches an `Err` return from `run` — a Rust panic (which is what `vec![0; huge_size]` allocation failure/OOM abort triggers) inside a spawned OS thread is not caught by anything here and will typically abort the whole process (memory allocation failures in Rust call `handle_alloc_error`, which aborts the process, not just the thread) [1](#0-0) . This means the DoS is not confined to the livestream thread but can bring down the entire `orb-core` binary, including in-progress signup state managed by the `Orb` broker.

However, this feature is strictly opt-in: `livestream` is a Cargo feature (`#[cfg(feature = "livestream")]`) and even when compiled in, the agent is only enabled at runtime via an explicit CLI flag (`cli.livestream` → `orb.enable_livestream()?`) [2](#0-1) [3](#0-2) . When enabled, `Upstream::new` binds `0.0.0.0:9201` [4](#0-3) , and `EventReader::poll_stream` reads a 4-byte big-endian length prefix and immediately allocates `vec![0; u32::from_be_bytes(self.len) as usize]` with no upper-bound check [5](#0-4) , confirming the unbounded-allocation primitive described in the question.

### Title
Unbounded 4-byte length-prefixed allocation in `EventReader::poll_stream` causes DoS - (File: `src/agents/livestream/upstream.rs`)

### Summary
`EventReader::poll_stream` reads an attacker-controlled 4-byte big-endian length prefix from a raw TCP connection on port 9201 and allocates a `Vec<u8>` of that size with no upper bound, allowing an unauthenticated network client to force allocations up to ~4 GiB. Because `livestream::Agent` runs as a `Thread` agent whose panics/OOM aborts are not isolated from the rest of the process, this can crash `orb-core` entirely, not just the livestream feature.

### Finding Description
`Upstream::new` binds a plain TCP listener on `0.0.0.0:9201` [4](#0-3) . Once a client connects, `EventReader::poll_stream` reads exactly 4 bytes into `self.len` and, as soon as they are available, computes `self.buf = vec![0; u32::from_be_bytes(self.len) as usize]` with no sanity check on the value [6](#0-5) . An attacker sending `0xFFFFFFFF` as the length prefix forces a ~4 GiB allocation attempt before a single payload byte has been validated or authenticated. `livestream::Agent` executes on a dedicated OS thread via `agentwire::agent::Thread::spawn_thread` [1](#0-0) ; this wrapper only handles a normal `Err` return from `run`, not a Rust allocation-failure abort or panic, so on a constrained/embedded target (the Orb's Jetson hardware) this can abort the whole process rather than just the agent thread.

### Impact Explanation
If reachable, this is a remote, unauthenticated denial-of-service against the `orb-core` process, which also hosts signup, capture, and camera-frame agents (`image_notary`, `mega_agent_one/two`, camera sensors) inside the same `Orb` broker [7](#0-6) . A process-wide crash mid-signup would interrupt biometric capture/upload flows, matching a DoS-class impact rather than the identity-binding/fraud-bypass/attestation categories the audit rubric requires for a "valid" finding.

### Likelihood Explanation
Exploitation requires: (1) the `livestream` Cargo feature compiled in, and (2) the operator/CLI explicitly passing the livestream flag to call `orb.enable_livestream()` [2](#0-1)  — this is an opt-in debug/support capability, not enabled by default in production signup flow. Given that precondition, exploitation itself is trivial and fully repeatable (any TCP client to port 9201 sending a crafted length prefix).

### Recommendation
Add an explicit maximum-size check on the parsed length prefix (e.g., reject/close the connection if `len > MAX_EVENT_SIZE`) before allocating `self.buf` in `EventReader::poll_stream`, at `src/agents/livestream/upstream.rs:96-98`.

### Proof of Concept
Add a unit test constructing an `EventReader`, feeding it a 4-byte prefix of `u32::MAX` via a mock `AsyncRead`, and asserting `poll_stream` returns an error (connection rejected) instead of proceeding to allocate; alternatively a fuzz harness that varies the length prefix and asserts memory usage never exceeds a fixed cap.

---

Given the audit's explicit validation rule — accepting only unauthorized signup, wrong-identity binding, biometric disclosure, liveness/fraud bypass, attestation forgery, cross-signup state bleed, or signup-state wedge — a pure DoS on an opt-in debug feature does not squarely fit those categories unless the resulting crash is shown to reliably wedge signup state specifically (not just terminate the process generally, which restarts and re-initializes cleanly on most deployments). I cannot confirm from the available code whether a crash mid-signup leaves persistent corrupted signup state versus a clean restart, so I present this as a real, reproducible unbounded-allocation bug with real but debug/opt-in-scoped DoS impact, rather than a definitive signup-compromise finding under the strict rubric.
