### Title
Unrestricted swap-route contracts can attach unauthorized token transfers to the caller's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Medium. Controller strategy entrypoints authenticate the caller once, then execute an attacker-influenceable swap route through the configured router; a malicious route contract can invoke an unrelated token transfer from the caller, causing Soroban simulation to place that transfer under the caller's signed `swap_collateral` authorization tree. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` calls `require_authorized_caller`, verifies that the caller owns or delegates for the account, and passes the user-supplied `swap` payload into the router path. [3](#0-2)  `require_authorized_caller` performs a broad `caller.require_auth()` rather than limiting authorization to only the intended collateral movement. [4](#0-3) 

`swap_tokens` authorizes only the controller's exact input transfer to the configured router, but it does not constrain which downstream contracts the route names. [5](#0-4)  A route-selected contract can therefore execute `token.transfer(victim, attacker, amount)` while the caller authorization remains active, and simulation records that transfer as a child of the caller's `swap_collateral` authorization. [6](#0-5) [7](#0-6) 

### Impact Explanation
A malicious swap route can cause a signed strategy transaction to transfer arbitrary caller-held tokens unrelated to the lending position to an attacker. [8](#0-7)  The checked swap output can still satisfy the account operation, so the wallet-token theft is additive rather than being caught by input-spend or output checks. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
Exploitation requires the account owner or delegate to sign a poisoned authorization tree produced for an attacker-selected route, but route payloads are opaque bytes and the reachable `swap_collateral(caller, account_id, current, amount, new, swap)` entrypoint is caller-authorized rather than privileged. [11](#0-10)  The enforced-auth test shows that the attack succeeds precisely when the simulated tree contains the rogue child transfer and fails when it does not. [12](#0-11) 

### Recommendation
Restrict route-selected pool and token addresses to a governance-approved allowlist, or replace opaque route execution with venue adapters bound to previously validated contracts. [13](#0-12)  Until route contracts are constrained, clients must simulate every strategy transaction, decode the complete authorization tree, and reject any child invocation other than the expected input transfer. [14](#0-13) 

### Proof of Concept
1. Alice owns a funded lending account and holds an unrelated wallet token. [15](#0-14) 
2. The malicious payload names a route contract whose `swap` function calls `token::Client::transfer(alice, attacker, WALLET_BALANCE)`. [16](#0-15) 
3. Alice calls `swap_collateral(alice, account_id, usdc, SWAP_IN_USDC, eth, malicious_route)`. [17](#0-16) 
4. Simulation records the unauthorized wallet-token transfer as a child invocation under Alice's `swap_collateral` authorization. [7](#0-6) 
5. Signing that tree completes the strategy and moves the entire unrelated wallet-token balance to the attacker. [8](#0-7)

```rust
        sub_invocations: std::vec![],
```

```rust
#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
```

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
