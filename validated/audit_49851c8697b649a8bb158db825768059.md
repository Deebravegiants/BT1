### Title
Cross-chain fill/cancel marks the order permanently settled before the redeem/refund message is confirmed delivered - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`ExtrinsicIntents._fillCrossChain` and `_cancelFromDest` both write `_filled[commitment]` on the destination chain *before* the outbound ISMP `RedeemEscrow`/`RefundEscrow` POST request to the source chain is known to have been delivered and processed. This is the same root-cause pattern as the reported `order.func` bug: local "done" state is committed on the strength of merely *sending* the message, not on confirmation that the counterparty successfully executed it.

### Finding Description
In `_fillCrossChain`, `_filled[commitment] = msg.sender` is set, the solver's output tokens are transferred to the beneficiary, and only afterward is a `RedeemEscrow` `DispatchPost` sent to the source chain via `_post(...)` [1](#0-0) . Likewise, `_cancelFromDest` sets `_filled[commitment] = address(uint160(uint256(order.user)))` and then dispatches a `RefundEscrow` message back to the source [2](#0-1) . In both cases the destination-side `_filled` flag is the *only* record on this chain that the order was resolved — there is no `onPostRequestTimeout` handler in `ExtrinsicIntents`/`IntentsBase` that reverses this flag if the dispatched POST request later times out or is rejected on the source chain.

On the source chain, `onAccept` only releases escrow when the `RedeemEscrow`/`RefundEscrow` message is actually delivered and passes `_authenticate` [3](#0-2) . If that message never arrives (times out due to relayer inaction, or the destination gateway registered on the source no longer matches — analogous to the multisig wallet's parameters changing in the reported bug), the ISMP host on the destination chain will eventually call `onPostRequestTimeout`, but the gateway does not implement any handling to unmark `_filled` or otherwise recover. The result: the destination chain believes the order is filled/cancelled forever (blocking any retry of `fillOrder`/`cancelOrder`), while the source chain's escrow was never released, exactly mirroring the order contract that marks `executed? = true` on a bounced/failed execution message.

This is structurally different from (and worse than) the pattern used elsewhere in the codebase, e.g. `EvmHost.dispatchIncoming`, which explicitly deletes the receipt on a failed `onAccept` call so delivery can be retried [4](#0-3) , and `HyperbridgeLzEndpoint.onAccept`, which stores a retryable payload hash instead of silently dropping/losing state on failure [5](#0-4) . `ExtrinsicIntents` has no equivalent safety valve for its own outbound dispatch.

### Impact Explanation
If the `RedeemEscrow`/`RefundEscrow` message from the destination chain times out or is otherwise never processed on the source chain (e.g., relayer never submits it before `timeout`, or governance rotates the registered gateway instance on the source chain — `UpdateParams`/`NewDeployment` are dispatcher-controlled actions in the same contract, per `onAccept`) [6](#0-5) , the solver has already paid out the output tokens (fill) or the user's cancellation intent has been recorded (cancel), yet the source-chain escrow is never released. Because `_filled[commitment]` is already set on the destination, the order can never be retried or filled by another solver, and the user has no route to recover the escrowed input tokens on the source chain — this is a permanent freezing-of-funds condition for the escrowed inputs.

### Likelihood Explanation
Cross-chain messages routinely time out (`timeout: 0` is used for these dispatches, meaning no expiry is set at all in `_post`, so a stuck message could sit indefinitely) [7](#0-6) , and the ISMP request-handling model explicitly documents that a failed `on_accept` must not persist a receipt precisely so it can be retried — implying the framework designers consider non-delivery a real, expected event [8](#0-7) . A solver or user does not need any privileged access to trigger this — a normal `fillOrder`/`cancelOrder` call combined with ordinary relayer unavailability or destination-gateway reconfiguration is sufficient.

### Recommendation
Do not treat "message dispatched" as "order settled" on the initiating chain. Either (a) delay setting `_filled` until the source chain confirms delivery/execution (not feasible synchronously, so instead) (b) implement `onPostRequestTimeout` in `ExtrinsicIntents` for `RedeemEscrow`/`RefundEscrow` dispatches that clears `_filled[commitment]` (or moves it to an explicit "failed"/"retryable" state) so the order can be re-filled or re-cancelled, and set a non-zero `timeout` on these dispatches so a stuck message is guaranteed to eventually resolve one way or the other, mirroring the `HyperbridgeLzEndpoint` retry-payload pattern already used elsewhere in this codebase.

### Proof of Concept
1. Solver calls `fillOrder` for a cross-chain order; `_fillCrossChain` sets `_filled[commitment] = solver` and transfers output tokens to the beneficiary, then dispatches `RedeemEscrow` to the source chain with `timeout: 0` [1](#0-0) .
2. No relayer ever submits the `RedeemEscrow` proof to the source chain (or the source-chain gateway's `_instance(order.source)` registration was rotated via `UpdateParams`/`NewDeployment` before delivery, making `_authenticate` in `onAccept` fail permanently).
3. Source-chain escrow for `commitment` is never released to the solver.
4. On the destination chain, `_filled[commitment]` is already non-zero, so the order can never be re-filled, and the user has no on-chain path to reclaim source-chain escrow — funds are permanently stuck, and the solver's paid-out output tokens are simply lost.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value

The request `handle` is used to notify onchain `IsmpModule`s of new requests to be processed. A relayer will construct the `RequestMessage` which holds a batch of new `PostRequest`s, as well as a _multi-proof_<sup>[1]</sup> of their existence on the source chain. The handler will perform the following operations

- Assert that the state machine's consensus client is not frozen
- Assert that the configured `challenge_period` for the `StateCommitment` has elapsed
- Assert that the requests have not been previously processed
- Assert that the requests have not timed out
- Assert that the membership proof for the requests verify
- Finally dispatch the requests to the relevant `IsmpModule::on_accept` and store a receipt for each request to prevent requests from being replayed.

<Callout title={'Danger'} type={"warn"}>
It's important to note that if the `IsmpModule::on_accept` does not return `Ok`, the receipt of this request will not be persisted, allowing the request to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying it's internal state to prevent partial state changes that could result in critical vulnerabilities in their request handler. This model ensures that if a request cannot be executed successfully on a destination state machine, it can time out gracefully on the source.
</Callout>
