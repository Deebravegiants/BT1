## Analysis: Rounding-down erosion in `accrue()`'s treasury fee-dilution — analog found

The Sherlock report's root cause is generic: **a value is computed and split into per-call/per-tier increments, each rounded down independently, so repeatedly triggering the calculation on small increments loses more value in aggregate than a single larger computation would.** Zest's vault `accrue()` function has the same structural flaw in its treasury fee mechanism, and unlike the PoolTogether tier-count case (informational bookkeeping only), this one directly erodes actual protocol fee revenue and is triggerable by any unprivileged caller.

### Root cause

`accrue()` is `define-public` with **no caller-authorization check** (unlike `system-borrow`/`system-repay`/`socialize-debt`, which all call `check-caller-auth`), so any address can invoke it at will: [1](#0-0) 

Inside it, the fee taken for the DAO treasury is computed from the *incremental* interest accrued since the last call: [2](#0-1) 

`debt-delta` is `mul-div-down(scaled-principal, next-idx-idx, PRECISION)`, and `reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)` — both round down. `treasury-lp` (the DAO's dilution-based fee share) is only minted `(if (> reserve-inc u0) ...)`.

### Why this breaks the "fees charged vs fees forwarded" identity

If `accrue()` is called with very small `time-delta` between calls (e.g., back-to-back in adjacent blocks), `debt-delta` per call is tiny relative to `scaled-principal`. Once `debt-delta * fee-reserve / BPS < 1`, `reserve-inc` rounds to `0` and **no treasury-lp is minted for that slice of interest at all** — yet the interest itself is still fully reflected in `total-assets-preview()`/`total-debt()` and benefits share price for existing zft holders: [3](#0-2) 

A caller can therefore continuously call the public, unauthenticated `accrue()` (e.g., every block) to fragment the interest-accrual timeline into slices small enough that the reserve fee rounds to zero on every single slice, whereas a single larger natural accrual (e.g., accrue only called once a day via normal deposit/borrow/repay traffic) would have produced a nonzero `debt-delta` and correctly minted `treasury-lp`. This is the same "rounding-down-the-sum" defect as the Sherlock report, but instead of skewing an informational tier estimate, it results in **permanent, cumulative loss of the protocol's fee-reserve share of interest** — value that is fully captured by the un-diluted zft holders instead of the DAO treasury. This is present identically in every vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`), confirmed by the shared `accrue`/`calc-treasury-lp-preview` logic: [4](#0-3) 

### Title
Public, unauthenticated `accrue()` lets an attacker fragment interest accrual to permanently avoid the treasury fee-reserve mint — (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent per-asset vaults)

### Summary
`accrue()` in every Zest vault is `define-public` with no `check-caller-auth`, and computes the DAO treasury's fee-reserve share (`reserve-inc`/`treasury-lp`) from the interest accrued strictly *since the last accrue call* using `mul-div-down`. By spamming `accrue()` at high frequency (small `time-delta`), an attacker keeps each incremental `debt-delta` low enough that `reserve-inc` rounds to zero every time, so `treasury-lp` is never minted, while the interest is still fully realized in `total-assets` for existing depositors.

### Finding Description
`accrue()` (mainnet/contracts/vault/v0-vault-stx.clar:835-863) has no authorization gate, unlike `system-borrow`/`system-repay`/`socialize-debt` which explicitly call `check-caller-auth` (lines 877, 918, 960). Its fee logic:
```
old-debt = mul-div-down(scaled-principal, idx, PRECISION)
new-debt = mul-div-down(scaled-principal, next-idx, PRECISION)
debt-delta = new-debt - old-debt
reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)
treasury-lp minted only if reserve-inc > 0
```
Both `mul-div-down` operations truncate. When `accrue()` is called with a very small `time-delta` (attacker calls it every block instead of letting normal usage call it at natural, larger intervals), `debt-delta` shrinks proportionally, and `reserve-inc = debt-delta * fee-reserve / BPS` truncates to `0` whenever `debt-delta < BPS/fee-reserve`. The interest itself (`debt-delta`) is still baked into `total-debt()`/`total-assets-preview()` used for `convert-to-assets`/`convert-to-shares`, so it still raises the value of existing zft shares — it's just that the treasury's proportional dilution share is skipped. Aggregated over many high-frequency calls, the treasury permanently loses the fee it would have collected had `accrue()` only been called at natural larger intervals, because the summed rounding-down losses (`Σ round_down(debt_delta_i)` per tiny slice) are strictly less than `round_down(Σ debt_delta_i)` on one larger slice — structurally identical to the reported `TieredLiquidityDistributor` bug of "rounding down when calculating the sum."

### Impact Explanation
This is a direct, permanent loss of protocol-owned yield (the fee-reserve's claim on interest, expressed via `treasury-lp` dilution) with no way to recover it after the fact — the interest has already been "spent" raising the share price for existing zft holders instead of being split with the treasury. This falls under theft/permanent freezing of unclaimed yield/fees, since fees that should have been forwarded to `.dao-treasury` are systematically never charged at all due to the caller's control over call cadence.

### Likelihood Explanation
`accrue()` requires no privilege, no capital, and no complex setup — any address can call it directly and repeatedly (e.g., once per block) at negligible cost, for as long as the vault exists, to suppress the treasury fee indefinitely. The precondition (`fee-reserve` set to a nonzero value and vaults accruing interest from outstanding debt) is the normal operating state of the protocol.

### Recommendation
Track the fee-reserve accrual using an accumulator/remainder pattern (carry forward the truncated fractional fee-reserve dust across `accrue()` calls) instead of resetting rounding error to zero on every call, or gate `accrue()` behind a minimum time-delta / authorized-caller check so an attacker cannot force sub-threshold, fee-avoiding accrual slices.

### Proof of Concept
1. DAO sets `fee-reserve` to a nonzero value (e.g., 1000 bps) via `set-fee-reserve`.
2. Vault has outstanding `principal-scaled` debt and a nonzero `interest-rate()`.
3. Attacker calls the public `accrue()` (mainnet/contracts/vault/v0-vault-stx.clar:835) every block instead of waiting.
4. For each call, `time-delta` is minimal (one block), so `debt-delta = new-debt - old-debt` is a very small integer; `reserve-inc = mul-div-down(debt-delta, 1000, 10000)` truncates to `0` for any `debt-delta < 10`.
5. `treasury-lp` is never minted (`(if (> reserve-inc u0) ...)` branch never triggers), while `index`/`lindex` still advance and raise share value for existing zft holders each call.
6. Compare against the counterfactual where `accrue()` is called once after the same elapsed time: `debt-delta` would be the full sum and `reserve-inc` would be nonzero, correctly minting `treasury-lp` to `.dao-treasury`. The difference is the fee permanently lost to the protocol.
