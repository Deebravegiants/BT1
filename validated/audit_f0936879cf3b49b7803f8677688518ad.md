### Title
PoA Bridge batch withdrawal status matching by `assetId` alone causes cross-withdrawal hash misreport - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain completion status/tx hash for a specific withdrawal in a batch by matching PoA API records **only on `assetId`**, ignoring the withdrawal's `index`, `destinationAddress`, or `amount`. When a batch withdrawal contains two or more entries with the same `assetId` (e.g. same token withdrawn to two different destination addresses in one intent), `findMatchingWithdrawal` returns the *first* record in the (unordered) API response for that asset for every matching index, so a caller polling completion for withdrawal #1 can be handed the transaction hash that actually belongs to withdrawal #0 (or vice versa).

### Finding Description
`describeWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (lines 313-344) is: [1](#0-0) 

It calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which — per the analogous helper and its documented limitation in the sibling implementation — matches purely by `near_token_id`/`assetId`: [2](#0-1) 

The code comment explicitly acknowledges: *"multiple withdrawals of the same token in a single transaction are not supported."* This is confirmed by the project's own test, which shows correct behavior only when the two batched withdrawals use *different* `assetId`s (`eth.omft.near` vs `btc.omft.near`): [3](#0-2) 

`createWithdrawalIdentifiers`/`createWithdrawalCompletionPromises` in `sdk.ts` build one `WithdrawalIdentifier` per withdrawal (carrying `index`, `withdrawalParams`, `tx`) and hand each independently to `bridge.describeWithdrawal`: [4](#0-3) [5](#0-4) 

Because `findMatchingWithdrawal` disregards `index`/`destinationAddress`, if a batch withdrawal contains two PoA-bridged transfers of the same token (e.g., splitting one token to two recipients, a normal and fully legitimate batch withdrawal use case supported by `processWithdrawal`/`waitForWithdrawalCompletion` for arrays of `WithdrawalParams`), the promise for withdrawal index 0 and index 1 can both resolve using the same underlying API record (the first one `Array.prototype.find` encounters), reporting one recipient's `transfer_tx_hash` as the completion for the other's withdrawal.

### Impact Explanation
This breaks the equality "the reported destination transaction hash belongs to the specific withdrawal being tracked." An integrator that persists `withdrawalParams[i]` alongside the resolved `TxInfo` (a documented pattern in the SDK's own README/RFC for recovery/state persistence) can end up crediting the wrong destination address as having received funds, or mark a still-pending withdrawal as completed with a hash that actually funded a different recipient. This matches the "status/hash misreport... integrator credit or refund twice" High-impact category: a caller could release/credit a downstream resource for a withdrawal that hasn't actually settled to that destination, while the same on-chain hash may get attributed to two different logical withdrawals in the caller's records.

### Likelihood Explanation
No privileged access is required. Any normal user of `processWithdrawal`/`waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` with a batch containing multiple PoA-bridge withdrawals of the same `assetId` (a supported, documented usage pattern for batch withdrawals) triggers this ambiguous matching. The bug is baked into `findMatchingWithdrawal`'s matching key and is not dependent on adversarial input beyond constructing a normal batch with duplicate asset IDs, so likelihood is high for any integrator issuing multi-destination withdrawals of the same token.

### Recommendation
Change `findMatchingWithdrawal` (both in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate by additional withdrawal-specific fields present in the PoA API response (e.g. `destinationAddress`/`address`, `amount`, and consumption/removal of matched entries so each API record is only attributed to one logical withdrawal), or track/consume matched indices so repeated calls for the same batch don't reuse the same record across different logical withdrawals.

### Proof of Concept
1. Call `sdk.processWithdrawal` (or `createWithdrawalIntents` + `waitForWithdrawalCompletion`) with `withdrawalParams = [ { assetId: "nep141:eth.omft.near", destinationAddress: addrA, amount: X }, { assetId: "nep141:eth.omft.near", destinationAddress: addrB, amount: Y } ]` — a legitimate batch withdrawal of the same token to two different recipients.
2. After settlement, the PoA relay's `getWithdrawalStatus` returns two `COMPLETED` records, both with `near_token_id: "eth.omft.near"` but different `transfer_tx_hash`/`address`.
3. `createWithdrawalCompletionPromises` invokes `describeWithdrawal` independently for index 0 and index 1; both calls invoke `findMatchingWithdrawal(withdrawals, "nep141:eth.omft.near")`, which returns the same first-matching record for both indices (as confirmed by the `find`-based, index-agnostic implementation and the code's own "not supported" comment).
4. The caller's promise for withdrawal index 1 (addrB) resolves with the `transfer_tx_hash` that actually corresponds to the on-chain transfer sent to addrA, causing the integrator to record/credit the wrong destination transaction for that withdrawal.

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.

			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;

					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.

					}

						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
