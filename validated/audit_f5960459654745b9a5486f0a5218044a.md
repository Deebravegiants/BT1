Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `Request#to_signable_string` used for that HMAC computation returns only `@raw_body`, while `topic`, `shop`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never included in the signed material [2](#0-1) . This breaks the intended binding: `hmac_valid(raw_body) == true` should imply `shop == the tenant Shopify actually sent this webhook for`, but in this implementation the `shop` field is decoupled from the signed bytes.

### Finding Description
This mirrors the ENS bug class: a name/identity (`OwnedSubnode.SigmaPrime.stateofus.eth`) was accepted and trusted despite not being validated/bound by the parent authority. Here, the trusted identity is the `shop` (tenant) associated with a webhook event, and the "signature" is the app's HMAC verification of Shopify webhook deliveries — but the `shop` value is never part of what's signed.

- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against `verifiable_query.hmac` [3](#0-2) .
- For webhooks, `to_signable_string` is defined as just the raw JSON body [4](#0-3) .
- `shop`, `topic`, `webhook_id`, and `api_version` are pulled from `shopify-*`/`x-shopify-*` headers, none of which feed into `to_signable_string` [5](#0-4) .
- `Registry.process` validates the HMAC and then unconditionally trusts `request.shop`, `request.topic`, etc. to build `WebhookMetadata`, which is handed to the app's handler [1](#0-0) [6](#0-5) .

Equality that should hold but doesn't: `hmac_valid(body) ⇒ shop_header == shop_that_Shopify_sent_the_event_for`. Because the header is unauthenticated, an attacker who can replay/forward *any* legitimately-HMAC-signed webhook body captured from Shopify (e.g., their own installed shop's `app/uninstalled` or any topic they subscribe to) can resend the identical body to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header for a *different* shop domain. Since the raw body is unchanged, the HMAC check still passes, and `Registry.process` dispatches the event to the app's handler labeled as coming from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the app's webhook processing pipeline can be made to believe an event (and its accompanying body/payload) originated from shop B when it actually was captured from a delivery to shop A. Depending on how the host app's `WebhookHandler#handle` implementation uses `data.shop` (e.g., to look up per-tenant records, trigger `customers/redact` or `shop/redact` GDPR flows, update per-shop entitlements/state, or invalidate/rotate credentials), this enables cross-tenant data corruption or disclosure using another merchant's identifier while the payload is fully attacker-choosable in terms of which legitimate signed body they replay. This falls under "cross-tenant access," a Critical-severity outcome per the given impact taxonomy, because the trust boundary between shops (tenants) is defeated using only a previously observed, legitimately-signed webhook body plus a forged header — no `api_secret_key`, access token, or privileged access is required.

### Likelihood Explanation
Any unprivileged actor who can trigger webhook deliveries to their own app instance (e.g., by installing/uninstalling the app on their own dev/test store, which is normal, unprivileged usage) can capture a validly-signed webhook request. Replaying it to the app's public webhook endpoint with a modified `shop-domain` header requires no cryptographic material and no cooperation from Shopify or the victim; it is a straightforward header substitution against an endpoint that necessarily must be internet-reachable for Shopify to deliver webhooks to it. Exploitability is high wherever the host application trusts `WebhookMetadata#shop` for tenant-scoped effects (a very common pattern), which is the gem's documented usage.

### Recommendation
Bind the `shop` (and other identity-relevant fields like `topic`) into the signed material, or otherwise cryptographically verify that the header value matches the tenant the HMAC-secret-bearing sender intended. Since Shopify signs only the raw body over HTTP webhooks industry-wide, the fix should be at the integration layer: require the consuming application to independently correlate `shop-domain` against an already-known, previously-installed shop record (session store) before trusting it, and document this expectation; alternatively, if Shopify's webhook contract allows including shop in the signed payload/topic verification via GraphQL webhook subscription data, prefer deriving shop from the payload body itself (which is signed) rather than from headers. At minimum, update documentation to explicitly warn that `WebhookMetadata#shop` is derived from an unauthenticated header and must not be used as an authorization boundary without additional verification (e.g., cross-checking against a known/installed shop list).

### Proof of Concept
1. Attacker installs the target app on their own controlled test shop `attacker.myshopify.com`, causing Shopify to deliver a legitimately HMAC-signed webhook (e.g. `app/uninstalled`) to the app's webhook endpoint, with headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw body>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `X-Shopify-Topic: app/uninstalled`
2. Attacker captures the raw request (body + valid HMAC header) via any request-logging proxy under their control.
3. Attacker resends the identical raw body and HMAC header to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only hashes `@raw_body` [4](#0-3) [7](#0-6) .
5. `request.shop` returns `"victim-shop.myshopify.com"` (read directly from the forged header) [8](#0-7) , and the registered handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)` [9](#0-8) , causing the app to process an uninstall (or any other subscribed) event against the victim tenant's records despite that shop never actually sending this webhook.
