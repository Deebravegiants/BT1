### Title
Webhook shop identity spoofing via unsigned `X-Shopify-Shop-Domain` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, but then dispatches to the app's handler using the `shop` value taken from an HTTP header that is not covered by that HMAC. This breaks the identity binding `hmac-verified bytes == bytes that determine tenant identity`, allowing the shop attribution passed to the handler to be forged independently of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., only the body) and then immediately builds `WebhookMetadata` using `request.shop` — the unverified header value — without any cross-check against a signed field: [3](#0-2) 

`HmacValidator.validate` confirms this: it computes the signature only from `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header — it never touches the shop header: [4](#0-3) 

Root cause: the gem verifies "did this body come from someone holding `Context.api_secret_key`?" but the value it hands to the app as the authenticated tenant identifier (`shop`) is not part of what was verified. The binding the code implicitly assumes — `hmac_covers(shop) == true` — does not hold; the actual equality is `hmac_covers(raw_body) == true` while `shop` is sourced from an independent, unauthenticated header.

Because `Context.api_secret_key` (the app's client secret) is a single value shared across every shop that has installed the app, any merchant who installs the app on their own store legitimately receives real webhooks — bodies with a valid HMAC computed under the app's shared secret. That merchant (an otherwise unprivileged actor with respect to any other tenant of the app) can replay such a webhook to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `Registry.process` still reports `Utils::HmacValidator.validate(request)` as true (the body/HMAC pair is unchanged and valid), and the handler receives `WebhookMetadata` with `shop` set to the attacker-chosen victim domain.

### Impact Explanation
Any app built on this gem that keys per-tenant data, session/token lookups, or side effects off `WebhookMetadata#shop` (the documented/intended usage per `docs/usage/webhooks.md`) can be induced to attribute attacker-supplied webhook content to another tenant. This is a cross-tenant identity-confusion vector at the library level: the gem's own "verified" boolean does not actually attest to the shop field it exposes to the handler, despite `Registry.process` presenting HMAC validation as the sole trust gate for the whole request.

### Likelihood Explanation
Exploitation requires only the ability to install the app on any shop (an unprivileged, self-service action any merchant can perform) and to make an arbitrary HTTP POST to the app's public webhook endpoint with attacker-controlled headers — both are within reach of an ordinary internet-facing app deployment and require no leaked secrets, no TLS interception, and no privileged account on the victim's shop.

### Recommendation
Bind the shop identity to the signed content, e.g., include the shop domain (and topic) in the signable string used for HMAC validation, or independently verify that the header-derived `shop` matches a value embedded in the signed payload before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for per-tenant authorization without additional verification (e.g., cross-referencing against the app's own installed-shop registry).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; Shopify delivers a legitimate webhook with a valid `X-Shopify-Hmac-Sha256` computed over the body using the app's `api_secret_key`.
2. Capture that request: `raw_body`, and `x-shopify-hmac-sha256` header.
3. Replay it to the app's webhook endpoint, replacing only:
   `X-Shopify-Shop-Domain: victim.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the unmodified HMAC: [3](#0-2) 
5. The registered handler receives `WebhookMetadata` with `shop == "victim.myshopify.com"`, even though the payload actually originated for `attacker.myshopify.com`.
