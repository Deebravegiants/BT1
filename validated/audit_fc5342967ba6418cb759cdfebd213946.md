## Title
Webhook `shop` identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking `Utils::HmacValidator.validate(request)`, but the HMAC signature only ever covers the raw request body — never the `shop-domain` header that identifies which tenant the webhook belongs to. Because the `shop` value handed to the app's webhook handler is read straight from an HTTP header outside the signed data, an unprivileged actor who can obtain one validly-signed webhook body (e.g. from their own store, which anyone can create and install a public app on) can replay that same body with a forged `shop-domain` header claiming to be any other shop, and the signature check will still pass.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is derived independently from a header that is not part of that signable string: [2](#0-1) 

`HmacValidator.validate_signature` compares the received HMAC against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. only the body is authenticated: [3](#0-2) 

`Registry.process` accepts the request once the HMAC check passes, then forwards the header-derived, unauthenticated `request.shop` straight to the handler as the tenant identity: [4](#0-3) 

The equality that should hold is: `shop bound by the cryptographic signature == shop the handler acts on`. Here, `shop` is never part of the signed bytes, so this equality is not enforced — only the body content is authenticated, and the `shop-domain` header (and `topic`, `webhook-id`, `api-version` headers) can be freely substituted by anyone who possesses one valid `(body, hmac)` pair.

### Impact Explanation
An unprivileged internet user (any developer able to install the app on their own free/dev store, which is a normal, credential-free interaction with the app) can capture a legitimate webhook delivery for their own shop and replay the identical body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header for an arbitrary victim shop domain. Because `HmacValidator.validate` still succeeds (it only checks the body), `Registry.process` will dispatch to the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. If the host application uses this `shop` value to look up the tenant's stored session/access token, update tenant records, or otherwise scope actions (the documented and expected usage of `WebhookMetadata`), this results in cross-tenant action/data confusion — the app performs shop-scoped mutations, cache invalidations, or data writes attributed to a shop the attacker does not own, using data the attacker controls (the JSON body).

### Likelihood Explanation
Likelihood is High: no secret, access token, or privileged account is required — only the ability to install/interact with the app on any dev store to receive one genuine webhook, then replay it with a modified header field. No cryptographic material needs to be forged since the header is outside the MAC.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the signed payload before it is trusted and handed to handlers. At minimum, `Webhooks::Request#to_signable_string` should incorporate `shop` so `HmacValidator.validate_signature` fails when the shop header is altered independently of the body.

### Proof of Concept
1. Install the target app (as any developer) on `attacker-shop.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a legitimate delivery:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, body `B`.
2. Replay the exact same body `B` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) recomputes the HMAC over `B` only, matches the replayed HMAC, and returns `true`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) dispatches to the handler with `shop: "victim-shop.myshopify.com"`, even though Shopify never sent this webhook for that shop.
