## Title
Timed-out message included in a relayer's `handlePostRequests` batch reverts delivery of every unrelated message in that batch, enabling cheap gas-griefing/DoS - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handlePostRequests` verifies an entire MMR-proven batch of POST-request leaves and dispatches them atomically. The very first per-leaf check is a timeout check that reverts the **whole call** if any single leaf in the batch has crossed its timeout, before the expensive MMR proof verification even runs. Since relayers batch multiple unrelated pending messages into one `handlePostRequests` call (and further into one `IHandlerV2.batchCall`) for gas efficiency, a single cheap, short-timeout message dispatched by any unprivileged sender can be bundled by the relayer together with unrelated legitimate messages. If that message's timeout elapses before the relayer's transaction lands (mempool delay, gas-price retries, rate limiting, etc.), the entire transaction reverts, and none of the bundled legitimate messages are delivered — mirroring the JOJO `requestWithdraw`/`permitWithdrawRequests` griefing pattern where a cheap, time-sensitive item spoils an atomic batch operated by another party.

### Finding Description
In `handlePostRequests`:
```solidity
for (uint256 i = 0; i < requestsLen; ++i) {
    PostRequestLeaf memory leaf = request.requests[i];
    if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
    if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
    leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
}
``` [1](#0-0) 

This loop runs over **every** leaf batched into a single call; a `MessageTimedOut()` revert on any one leaf aborts the whole transaction, including all other leaves in `request.requests` that are still valid and would otherwise be delivered. The relayer's own tooling batches multiple pending ISMP messages into one `IHandlerV2.batchCall` transaction specifically to amortize gas:

```rust
/// Submit a full batch of ISMP messages as a single `IHandlerV2.batchCall` transaction.
/// ... Atomic: if any inner call reverts, the whole transaction reverts.
pub async fn submit_batch_messages(...)
``` [2](#0-1) 

and `batchCall` itself is fully atomic — any inner call failure reverts everything:
```solidity
function batchCall(bytes[] memory calls) external {
    uint256 len = calls.length;
    for (uint256 i = 0; i < len; ++i) {
        (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
        if (!success) revert BatchCallFailed(i, returnData);
    }
}
``` [3](#0-2) 

Any application built on Hyperbridge dispatches POST requests with a caller-chosen `timeout` (e.g. `IntentGatewayV2`, `HyperFungibleToken.send`, or any custom ISMP module). Nothing prevents an unprivileged sender from dispatching a large number of low-value messages with a very short `timeout` targeting the same destination chain as ordinary traffic. If the relayer's outbound batching groups such a message together with legitimate, unrelated messages headed to the same destination in a single MMR-proof batch (as it does to reduce per-message gas overhead), and delivery is delayed past the short timeout for any reason (congestion, retry backoff, rate limiting — the relayer code explicitly retries with backoff on rate limits: `tokio::time::sleep(Duration::from_secs(10))`), the entire `handlePostRequests`/`batchCall` transaction reverts with `MessageTimedOut`, and none of the batched messages — including unrelated, still-valid ones — are delivered in that attempt. [4](#0-3) 

This is structurally the same bug class as the JOJO report: a cheap, permissionless, time-sensitive submission (`requestWithdraw` ↔ a short-timeout dispatch) is later bundled into an atomic batch operation performed by a third party (`permitWithdrawRequests` ↔ `handlePostRequests`/`batchCall`), and a state-drift-induced failure of that one item (index drift ↔ timeout elapsing) reverts the whole batch, wasting the batch operator's gas and denying service to the other, legitimate items bundled alongside it.

### Impact Explanation
- Relayers repeatedly retry and re-batch failed transactions; a batch that always contains at least one near-expiry message will always revert, forcing the relayer to burn gas on each attempt (`estimate_gas`, transaction submission, and on-chain revert gas) with no delivery progress.
- Legitimate, unrelated messages bundled in the same batch (which can include time-sensitive cross-chain settlement messages, e.g. `IntentGatewayV2` `RedeemEscrow`, token bridge mints, etc.) are delayed or fail to be delivered before their own timeouts elapse, which can cause them to time out and be refunded/cancelled instead of settled — a route-unable-to-deliver-messages condition and a potential funds-timing/DoS impact for otherwise-unaffected users.
- The attack cost is the dispatch fee/gas of many small-timeout POST requests on the source chain, which is cheap relative to the relayer's repeated gas expenditure and the potential loss/delay for third-party settlements bundled alongside it — the same asymmetric cost profile flagged as Medium in the original report.

### Likelihood Explanation
Exploitability depends on the relayer's batching heuristics actually co-locating an attacker-controlled short-timeout message with legitimate messages in the same MMR-proof batch/`handlePostRequests` call, and on real-world delivery delay (mempool congestion, rate-limit backoff already present in the code) being sufficient to cross the short timeout window before the transaction lands. Both conditions are plausible but environment/relayer-configuration dependent, and I was not able to fully verify from the indexed code whether the batching logic that assembles `PostRequestMessage.requests` filters out near-expiry messages or caps timeout skew before grouping (the relevant grouping code in `tesseract/messaging/messaging/src/events.rs` / `outbound.rs` was only partially inspectable given tool-call limits). This uncertainty should be treated as a caveat on likelihood rather than a refutation of the root cause, which is clearly present in `HandlerV2.sol`.

### Recommendation
- Do not let a single timed-out leaf abort the whole `handlePostRequests`/`handleGetResponses` call: skip/timeout-report the offending leaf (similar to how `accumulate_fees` in `modules/pallets/relayer/src/accumulate.rs` defensively filters out already-claimed/missing commitments from the batch rather than reverting the whole extrinsic — [5](#0-4) ) and only include still-valid leaves in the MMR proof/dispatch loop, or require relayers to pre-filter near-expiry messages before proof generation.
- Alternatively, have the relayer's batching logic strictly exclude messages whose `timeout` is within a safety buffer of the current time from being co-batched with other messages, and/or fall back to `batchCall`'s BatchCallFailed index to retry only the failing portion instead of the entire set.

### Proof of Concept
1. Attacker dispatches many cheap POST requests (via any app using `IDispatcher.dispatch`) to state machine `X` with `timeout = block.timestamp + T` for a small `T` (e.g. a few minutes) — cost is minimal on the source chain.
2. The relayer's outbound task collects pending messages for destination `X`, including the attacker's short-timeout message alongside legitimate messages, and builds a single MMR proof batch, submitting via `HandlerV2.handlePostRequests` (directly or wrapped in `IHandlerV2.batchCall`) — see `submit_batch_messages` [6](#0-5) .
3. If chain congestion, gas-price competition, or rate-limit retry delay (`tokio::time::sleep(Duration::from_secs(10))` loop) [4](#0-3)  pushes inclusion past `T`, the transaction reverts entirely at:
```solidity
if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
``` [7](#0-6) 
4. None of the batched messages are delivered; the relayer must retry, and repeating step 1 with fresh short-timeout spam perpetuates the failure, griefing the relayer's gas and delaying/denying delivery of the co-batched legitimate messages.
