The `validate_account_locks` function operates on the fully resolved `AccountKeys` view, which is explicitly documented and tested to merge static account keys with ALT-resolved (dynamic) addresses before performing duplicate detection via `has_duplicates`. [1](#0-0) 

The duplicate check in `has_duplicates` iterates over the entire merged `AccountKeys` (static + dynamic) and detects any exact pubkey match anywhere in that combined list, returning `TransactionError::AccountLoadedTwice`. [2](#0-1) 

This is directly exercised by `test_validate_account_locks_duplicate_dynamic`, where a static key that also appears among the ALT-resolved (dynamic) readonly keys is correctly rejected with `AccountLoadedTwice`. [3](#0-2) 

Additionally, in the transaction-view/banking-stage path, the lock validation is explicitly performed *after* ALT resolution specifically to catch this exact scenario, per the code comment "Validate no duplicate accounts (must be after resolution to catch ALT duplicates)". [4](#0-3) 

So the attacker scenario described — "nonce account key appears twice via different case... achievable via ALT-resolved address equal to nonce account" and "validate_account_locks passes (single occurrence via AccountKeys view merges static+ALT)" — does not hold. The merge does not silently deduplicate/hide collisions; it is precisely the mechanism used to detect and reject them. A nonce account referenced both statically and via an ALT-resolved address pointing to the same pubkey would fail sanitization/lock validation with `TransactionError::AccountLoadedTwice` before reaching the execution/commit/nonce-advance path in `bank.rs` or `blockstore_processor.rs`'s `validate_entry_transactions`. /// Validate account locks before locking.
pub fn validate_account_locks(
    account_keys: AccountKeys,
    tx_account_lock_limit: usize,

        Err(TransactionError::TooManyAccountLocks)
    } else if has_duplicates(account_keys) {
        Err(TransactionError::AccountLoadedTwice)

    }

/// Check for duplicate account keys.
fn has_duplicates(account_keys: AccountKeys) -> bool {
    // Benchmarking has shown that for sets of 32 or more keys, it is faster to
    // use a HashSet to check for duplicates.
    // For smaller sets a brute-force O(n^2) check seems to be faster.
    const USE_ACCOUNT_LOCK_SET_SIZE: usize = 32;
    if account_keys.len() >= USE_ACCOUNT_LOCK_SET_SIZE {
        HAS_DUPLICATES_SET.with_borrow_mut(|set| {
            let has_duplicates = account_keys.iter().any(|key| !set.insert(*key));
            set.clear();
            has_duplicates
        })
    } else {
        for (idx, key) in account_keys.iter().enumerate() {
            for jdx in idx + 1..account_keys.len() {
                if key == &account_keys[jdx] {
                    return true;
                }
            }
        }
        false
    }
}

/// Validate an entry's transactions before scheduling: each transaction's account
/// locks (count and duplicates), and rejection of duplicate message hashes within
/// the entry. Does not take account locks - the unified scheduler orders conflicts.
/// Post-SIMD-83 the duplicate-message-hash check is what rejects an entry that
/// replays the same transaction twice (it no longer conflicts on locks).
fn validate_entry_transactions(
    transactions: &[RuntimeTransaction<SanitizedTransaction>],
    tx_account_lock_limit: usize,
) -> Result<()> {
    let mut batch_message_hashes = AHashSet::with_capacity(transactions.len());

    for transaction in transactions {
        validate_account_locks(transaction.account_keys(), tx_account_lock_limit)?;
        if !batch_message_hashes.insert(transaction.message_hash()) {
            return Err(TransactionError::AlreadyProcessed);
        }
    }

    Ok(())
}
