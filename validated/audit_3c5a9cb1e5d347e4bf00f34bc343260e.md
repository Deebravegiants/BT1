### Title
Permissionless `CallDispatcher.dispatch()` lets anyone drain residual token/ETH balances left in the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, ungoverned utility contract used by both `IntentGatewayV2`/`ExtrinsicIntents` (predispatch/postdispatch calldata) and `HyperFungibleToken`-style apps to execute arbitrary `Call[]` batches with the dispatcher's own balance and identity. Its `dispatch(bytes memory encoded)` function has **no access control at all** — any address can call it directly and force the dispatcher to `.call` any target with any value it currently holds.

### Finding Description
`CallDispatcher.dispatch` decodes an ABI-encoded `Call[]` and executes each entry with `to.call{value: call.value}(call.data)` [1](#0-0)  — there is no `onlyGateway`/`onlyHost`/caller check whatsoever, and the contract also has an unconditional `receive()` that accepts ETH from anyone [2](#0-1) .

The dispatcher is designed to *temporarily* hold funds mid-flow: `IntentGatewayV2.placeOrder`/`fillOrder` send predispatch/postdispatch assets to `_params.dispatcher`, call `dispatch()` to run swap/DeFi calldata, and then explicitly sweep any leftovers back with a second `dispatch()` call containing transfer calls [3](#0-2) , and `IntentsBase._execute` does the same dust-sweep pattern after order fills [4](#0-3) . The `HyperFungibleToken` flow, however, mints tokens straight to the dispatcher and only executes the caller-supplied `Call[]` — the documented security model states the dispatcher "holds tokens temporarily during execution" and warns callers to use exact-amount approvals, but describes no automatic sweep-back of any token balance left on the dispatcher afterward [5](#0-4) .

Because `dispatch()` itself is permissionless and the same `CallDispatcher` instance is shared across gateways/apps ("Existing `CallDispatcher` deployments are listed on the contract addresses page" [6](#0-5) ), any dust, rounding remainder, partially-consumed swap output, or ETH sent to the dispatcher's `receive()` — from any app, any order, any cross-chain message — sits in a contract with no owner-tracking and is claimable by whoever calls `dispatch()` next with a `Call` that transfers that balance to themselves. This is analogous to the CVE's "execution with unnecessary privileges": a component intended to be invoked only as an internal step of a privileged flow is instead an unrestricted, balance-holding executor reachable directly by any unprivileged caller.

### Impact Explanation
Any accumulated balance (native ETH sent directly to the dispatcher, leftover ERC20 from imprecise swap/postdispatch calldata, or funds left mid-flow if a caller's own transaction structure doesn't sweep) can be permanently stolen by an unrelated third party simply by calling `CallDispatcher.dispatch()` with a `Call[]` that moves the balance to an address they control. This is concrete theft of funds reachable from a single, unprivileged transaction, satisfying the "concrete theft ... of funds" bar.

### Likelihood Explanation
Medium-High. It requires the dispatcher to actually be holding value at the moment of attack, which depends on usage patterns (fee-on-transfer tokens, swap slippage leaving remainder, users/relayers mistakenly sending ETH to the dispatcher address, or any app that doesn't perform an explicit end-of-flow sweep like `IntentGatewayV2` does). Given the dispatcher is a public, well-known, shared contract address, an attacker can simply monitor its balance and front-run/react whenever it goes non-zero.

### Recommendation
Add a caller allowlist (e.g., a mapping of authorized gateways/apps set by governance, or restrict to `msg.sender == tx.origin` won't help — use an explicit `onlyAuthorizedCaller` modifier) to `CallDispatcher.dispatch()`, and/or make the dispatcher non-shared per app (deploy one per consuming contract) so no cross-app balance can accumulate to be swept. At minimum, ensure every integrating flow (including `HyperFungibleToken`) sweeps 100% of any residual balance back to itself atomically within the same transaction before returning control, and reject `receive()` value from unrelated senders.

### Proof of Concept
1. Observe that `HyperFungibleToken.onAccept` (or any other integrator) mints tokens to the shared `CallDispatcher`, then calls `dispatcher.dispatch(calls)` where `calls` include a swap that doesn't consume the full minted amount (e.g., due to slippage or a fee-on-transfer token), leaving a nonzero ERC20 balance on the dispatcher.
2. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: leftoverToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, leftoverBalance)})]))` directly — no permission check exists, so this succeeds and transfers the leftover balance to the attacker.
3. Repeat opportunistically whenever the shared dispatcher's balance is observed to be nonzero from any integrating app's flow.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
