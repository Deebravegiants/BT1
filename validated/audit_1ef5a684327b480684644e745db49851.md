## Title
Webhook `shop` identity not covered by HMAC verification, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) purely from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies is computed **only over the raw request body**. The `shop` field that the registry later trusts and dispatches on is never part of the signed bytes, breaking the binding between "HMAC verified" and "shop the data is attributed to."

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from headers, none of which feed into `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header value — i.e., it only proves the body bytes weren't tampered with, using the app's single shared `api_secret_key` (the app's `client_secret`, identical for every shop that installs the app): [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) — fields never covered by that HMAC — to select the handler and to build the `WebhookMetadata` that is handed to the app's business logic as the authoritative tenant identifier: [4](#0-3) 

Because the `api_secret_key` is shared across all shops using the app (it is not shop-specific), any real merchant/tenant of a multi-tenant app receives genuine webhooks from Shopify with a valid HMAC computed over a body that they fully observe. That attacker-tenant can replay the exact same body + HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still succeed (the body and secret are unchanged), and `Registry.process` will hand the attacker's body to the handler labeled as coming from the victim shop.

Binding broken (equality that should hold but doesn't):
`shop authenticated-by-HMAC == shop used-as-tenant-key-in-WebhookMetadata`
Before request: both sides agree by construction (Shopify sets header = signer's shop).
After attacker's replay with a forged header: HMAC still validates (body/secret unchanged) but `request.shop` now equals the victim's domain while the signed bytes carry no relation to that shop at all — the two sides diverge, and the gem never checks that divergence.

### Impact Explanation
This is a cross-tenant data-injection path in a security-relevant gem primitive: an unprivileged party who is a legitimate user of the multi-tenant host app (not requiring `api_secret_key`, an access token, or any credential theft) can cause webhook data they fully control to be processed and attributed to a different merchant's shop. Depending on the handler (e.g., `shop/redact`, `customers/data_request`, order/product sync handlers), this can lead to unauthorized cross-tenant state changes or data leakage keyed to the wrong shop — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires being any existing installer/tenant of the target app (to legitimately receive a signed webhook body+HMAC) and the ability to POST an HTTP request with a custom header to the app's public webhook endpoint — no secret material, TLS interception, or social engineering needed. This is a purely mechanical HTTP replay against `Registry.process`.

### Recommendation
Include the tenant-identifying fields (`shop-domain`, and ideally `topic`/`webhook-id`) in the signed material actually verified, or otherwise cryptographically bind them to the HMAC-covered body (e.g., verify the header-derived `shop` against a value embedded/covered by the signature) before `Registry.process` uses `request.shop` to construct `WebhookMetadata`.

### Proof of Concept
1. App is a multi-tenant Shopify app; Attacker installs it on their own store `attacker-shop.myshopify.com` and the app registers a webhook handler for topic `orders/create`.
2. Shopify sends a legitimate webhook to the app: body `B`, headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: HMAC(secret, B)`. Attacker observes/records this request (their own webhook, fully visible to them).
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same body `B` and the same `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into `topic`, `shop = "victim-shop.myshopify.com"`, `hmac`, using `to_signable_string == B` only.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`; since `to_signable_string` is unchanged and `secret` is shared across tenants, validation passes.
6. `handler.handle` is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` — attacker-controlled body processed under the victim's shop identity. [4](#0-3) [5](#0-4)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
