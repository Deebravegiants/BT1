### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, allowing tenant-identity spoofing on otherwise-valid webhook deliveries - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity using an HMAC computed only over the raw request body, but the shop that owns the webhook (`shop-domain` header), along with `topic` and `webhook-id`, are read directly from unauthenticated HTTP headers and are never included in the signed material.

### Finding Description
`Webhooks::Request` mixes in `Utils::VerifiableQuery` and defines `to_signable_string` to return `@raw_body` only: [1](#0-0) 

The HMAC itself is likewise pulled from a header (`hmac-sha256`) and verified via `HmacValidator.validate`, which computes `HMAC(secret, to_signable_string)` and compares it to the received value: [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` — the fields a host application uses to route the webhook to the correct tenant and handler — are read straight from headers with no binding to the signed body: [3](#0-2) [4](#0-3) 

This mirrors the report's bug class exactly: "a field acted on but not covered by the HMAC." The identity binding that should hold is:
`shop used by the host app to attribute/act on the webhook == shop that Shopify actually signed the payload for`.

Because only the raw body bytes are signed, an attacker who can produce or intercept any single genuine, valid Shopify webhook delivery (its body + valid `hmac-sha256`) for shop A can replay it while substituting the `shop-domain` (and `topic`/`webhook-id`) headers to attribute the payload to shop B. `HmacValidator.validate` will still return `true` because the signature check only covers `@raw_body`, which is unchanged.

### Impact Explanation
If a host application trusts `Request#shop` (as intended and documented usage of this gem) to determine which merchant/tenant a webhook event belongs to — e.g., to look up that shop's session/access token or to update tenant-scoped data — an attacker who can capture or send altered headers alongside a legitimately-signed body can cause the event to be recorded/actioned against the wrong shop. This is a cross-tenant data-integrity issue: data or events belonging to one shop can be attributed to another shop purely by header manipulation, without needing the app's `client_secret`. This matches the "cross-tenant access" impact category, since the shop-scoping boundary that the HMAC is supposed to enforce is not actually enforced for the `shop-domain` field.

### Likelihood Explanation
Exploitation requires the attacker to control or replay the delivery to the app's webhook endpoint with attacker-chosen headers alongside a validly-signed body (e.g., an attacker with any means to send arbitrary HTTP requests to the app's public webhook endpoint, which is inherently internet-reachable). No access token, `api_secret_key`, or privileged account is needed — only network reachability to the endpoint and a single legitimate body+hmac pair to replay (which can come from any shop that has this app installed, including a shop the attacker controls/installed themselves, since the attacker only needs *a* valid signature, not one belonging to the specific victim shop).

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` (or otherwise bind the shop identity) into the signed material, or independently verify that the `shop-domain` header corresponds to an installation that this signature could plausibly belong to. At minimum, document/enforce that consumers must not treat `Request#shop` as authenticated unless it is cross-checked against a shop known independently (e.g., resolved via the access token used to look up the session), since the HMAC alone does not bind the header value.

### Proof of Concept
1. Attacker installs the app on a shop they control (`attacker-shop.myshopify.com`) and triggers a webhook, capturing a valid `raw_body` and its correct `hmac-sha256` header for a chosen topic.
2. Attacker sends a POST to the victim app's webhook endpoint with:
   - `X-Shopify-Hmac-Sha256`: the captured valid signature (unchanged)
   - body: the captured raw body (unchanged)
   - `X-Shopify-Shop-Domain`: replaced with `victim-shop.myshopify.com`
   - `X-Shopify-Topic` / `X-Shopify-Webhook-Id`: optionally replaced
3. The host app calls `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` then `Utils::HmacValidator.validate(request)`: [5](#0-4) 
   Validation succeeds because `to_signable_string` only returns `@raw_body`, which the attacker did not modify.
4. The app, following the gem's documented API, reads `request.shop` and processes/attributes the (unmodified) event data as belonging to `victim-shop.myshopify.com`, even though it was never signed by Shopify as pertaining to that shop.
