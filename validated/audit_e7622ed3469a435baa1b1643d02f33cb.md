### Title
Immutable Uniswap V3 pool-fee tier in `UniV3UniswapV2Wrapper` can permanently deny native-fee order placement in `IntentGatewayV2::placeOrder` - (File: evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol)

### Summary
When a user places a cross-chain intent order and elects to pay the solver/relayer fee (`order.fees`) with native token, `IntentGatewayV2::placeOrder` swaps that native value into the fee token through whatever contract is configured as `IDispatcher(host).uniswapV2Router()`. In production deployments this router is `UniV3UniswapV2Wrapper`, which routes the ERC-20-router-shaped calls through a single, immutable Uniswap V3 pool fee tier (`Params.maxFee`) fixed once at `init()` time. This is the same bug class as the CodeHawks report: a hardcoded/fixed pool fee tier used to reach liquidity that can migrate to a different tier over time, causing failed swaps.

### Finding Description
`IntentGatewayV2::placeOrder` performs the fee-token acquisition swap unconditionally whenever a user pays with native value: [1](#0-0) 

The router used is `IDispatcher(hostAddr).uniswapV2Router()` — a `IUniswapV2Router02`-shaped address that, per the deployment script, is actually `UniV3UniswapV2Wrapper`: [2](#0-1) 

`UniV3UniswapV2Wrapper` stores a single `maxFee` (the Uniswap V3 fee tier, e.g. 500/3000/10000) in `Params`, set exactly once via `init()` (guarded by `_initialized`), and every subsequent swap call unconditionally uses that same fixed value: [3](#0-2) 

`swapETHForExactTokens` — the exact function invoked by `IntentGatewayV2::placeOrder` for the WETH→feeToken leg — always builds its `ExactOutputSingleParams` with `fee: _params.maxFee`, with no way for the caller (`IntentGatewayV2`, or the end user) to choose a different fee tier or fall back to another tier if the configured one has insufficient liquidity: [4](#0-3) 

Because `_initialized` prevents `init()` from ever being called again, `maxFee` is permanently fixed for the lifetime of the wrapper — there is no admin escape hatch to update it if liquidity later migrates to a different fee tier for the WETH/feeToken pair.

### Impact Explanation
The WETH/feeToken swap is not optional configuration — it is the only mechanism `IntentGatewayV2::placeOrder` provides for paying `order.fees` in native token, which the SDK/docs present as the primary UX path for order placement (`nativeValue` fee payment). If the Uniswap V3 pool at the hardcoded `maxFee` tier for the WETH/feeToken pair runs dry or liquidity concentrates in a different tier (a routine, expected DEX dynamic, not an attack), every `placeOrder` call that pays fees with native token reverts inside `swapETHForExactTokens` (insufficient liquidity to satisfy the exact-output request within `msg.value`). Because `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(order.fees, ...)` reverts, `placeOrder` reverts entirely — this permanently disables the native-fee order-placement route until the wrapper is redeployed and the host's `uniswapV2Router()` pointer is repointed by governance, which itself requires migrating all downstream integrations. This matches the impact class of the referenced report (failed swaps due to liquidity mismatch with a fixed pool fee), manifesting here as a denial-of-service on a core, unprivileged entry point of the Intent Gateway.

### Likelihood Explanation
Likelihood is driven entirely by ordinary DEX liquidity migration, not by any attacker action — Uniswap V3 fee-tier liquidity concentration for a given pair commonly shifts over time as market makers rebalance. Any user calling `placeOrder` with `msgValue > 0` and `order.fees > 0` triggers the affected path; this is the default/expected flow documented for native-token fee payment, so exposure is continuous and not gated by any privileged actor.

### Recommendation
- Do not hardcode/fix a single Uniswap V3 fee tier for the lifetime of the wrapper. Either allow the fee tier to be passed per-call (mirroring the audited fix applied to `SmartVaultV4::swap` in the referenced report — accept a caller-supplied `fee` parameter validated against an allowlist), or have `UniV3UniswapV2Wrapper` probe multiple standard fee tiers (500/3000/10000) via the quoter and pick the best-liquidity tier at call time, with a slippage-bounded fallback.
- Add a governance-gated `setMaxFee()`/re-init path (or a tier-selection mapping) so the configured tier can be updated without redeploying the wrapper and repointing `IDispatcher.uniswapV2Router()`.
- In `IntentGatewayV2::placeOrder`, consider a fallback that lets the user pay `order.fees` directly in the fee token if the native-swap leg fails, rather than reverting the entire order placement.

### Proof of Concept
1. Governance deploys `UniV3UniswapV2Wrapper` and calls `init()` with `maxFee = 3000` (0.3% tier), matching the WETH/feeToken pool with the best liquidity at deployment time; `EvmHost`'s `uniswapV2Router()` is set to this wrapper.
2. Over time, liquidity providers migrate WETH/feeToken liquidity to the 0.05% (500) tier as is common on Uniswap V3; the 3000-tier pool's liquidity drops sharply or is fully withdrawn.
3. A user calls `IntentGatewayV2::placeOrder` with `order.fees > 0` and sends native `msgValue` to pay the fee, as documented in the SDK guide. [5](#0-4) 
4. `swapETHForExactTokens` on the wrapper builds `ExactOutputSingleParams{ fee: 3000, amountOut: order.fees, amountInMaximum: msg.value, ... }` and calls the V3 router; because the 3000-tier pool no longer has sufficient liquidity, the swap reverts. [6](#0-5) 
5. The revert bubbles up through `placeOrder`, reverting the entire order placement transaction. Every subsequent attempt to place an order paying fees in native token fails identically until the wrapper's `maxFee` (immutable post-`init`) is somehow replaced — which is not possible without deploying a new wrapper and updating the host configuration.

Note: I was unable to fully verify from the indexed code whether every production EVM deployment actually points `uniswapV2Router()` at `UniV3UniswapV2Wrapper` versus a plain V2 router (this is chain-specific deployment configuration set via scripts/config, not hardcoded in `EvmHost.sol` itself); confirming the exact per-chain router configuration would require live deployment data outside the indexed repository content.

    /**
     * @notice Initializes the Uniswap V3 to V2 wrapper module
     * @dev Can only be called once
     * @param params Initialization parameters.
     */
    function init(Params memory params) public {
        if (_initialized || msg.sender != _deployer) revert Unauthorized();
        // approve the swap router to spend WETH
        IERC20(params.WETH).approve(params.swapRouter, type(uint256).max);

        _params = params;
        _initialized = true;
    }

    function swapETHForExactTokens(uint256 amountOut, address[] calldata path, address recipient, uint256 deadline)
        external
        payable
        returns (uint256[] memory)
    {
        address weth = _params.WETH;
        if (path[0] != weth) revert InvalidWethAddress();

        (bool sent,) = weth.call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IV3SwapRouter.ExactOutputSingleParams memory params = IV3SwapRouter.ExactOutputSingleParams({
            tokenIn: weth,
            tokenOut: path[1],
            fee: _params.maxFee,
            recipient: recipient,
            amountOut: amountOut,
            amountInMaximum: msg.value,
            sqrtPriceLimitX96: 0
        });

        bytes memory swapCall = abi.encodeWithSelector(IV3SwapRouter.exactOutputSingle.selector, params);

        bytes[] memory data = new bytes[](1);
        data[0] = swapCall;

        bytes[] memory results = IMulticallExtended(_params.swapRouter).multicall(deadline, data);
        uint256 spent = abi.decode(results[0], (uint256));

        if (spent < msg.value) {
            uint256 refund = msg.value - spent;
            IWETH(weth).withdraw(refund);

            (bool success,) = msg.sender.call{value: refund}("");
            if (!success) revert RefundFailed();
        }

        uint256[] memory amounts = new uint256[](2);
        amounts[0] = spent;
        amounts[1] = amountOut;

        return amounts;
    }
