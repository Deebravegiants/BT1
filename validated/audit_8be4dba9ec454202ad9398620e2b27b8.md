### Title
`AccountLocks::try_lock_transaction_batch` fails to detect intra-batch read/write account-lock conflicts, allowing two conflicting transactions in the same lock batch to both succeed - (File: accounts-db/src/account_locks.rs)

### Summary
`try_lock_transaction_batch` first validates every transaction in the batch against the account-lock state, and only afterwards applies the locks for all transactions that passed validation. Because validation for every transaction in the batch is checked against the *same pre-batch* lock snapshot instead of being interleaved with lock application, two transactions submitted together in one batch that conflict only with *each other* (e.g. one declares key `K` writable, the other declares `K` read-only, with `K` unlocked beforehand) will both pass validation and both have their locks applied, violating the write/read exclusivity invariant the module is documented to enforce.

### Finding Description
`try_lock_transaction_batch` is implemented as a two-pass "validate-then-apply" routine: [1](#0-0) 

Pass 1 (`iter_mut().for_each`) calls `self.can_lock_accounts(keys)` for each transaction's keys, checking them against `self`'s *current* lock maps, but it never calls `self.lock_accounts(...)` here — it only marks the entry as `Err` on failure. Pass 2 (`.into_iter().map(...)`) then unconditionally calls `self.lock_accounts(keys)` for every entry that was **not** marked `Err` in pass 1.

`can_lock_accounts`/`can_write_lock`/`can_read_lock` enforce the exclusivity invariant only against whatever is already recorded in `write_locks`/`readonly_locks` at the moment they are called: [2](#0-1) 

Consider a batch containing transaction A (declares key `K` writable) followed by transaction B (declares key `K` read-only), with `K` not locked by any prior batch. During pass 1, `can_lock_accounts` is evaluated for A against the pre-batch state (no lock on `K`) → `Ok`. It is then evaluated for B, but because pass 1 never applies A's lock, B is also checked against the *same* pre-batch state (still no lock on `K`) → `Ok`. In pass 2, both A's and B's locks are applied unconditionally: A calls `lock_write(K)`, then B calls `lock_readonly(K)`, resulting in `write_locks[K] == 1` and `readonly_locks[K] == 1` simultaneously — a state that `can_write_lock`/`can_read_lock` are specifically designed to prevent from ever being reached.

This is reachable by an unprivileged attacker: any two transactions that reference the same account with conflicting write/read declarations, submitted so that they land in the same call to `Accounts::lock_accounts` (which forwards the whole `txs` iterator straight into `try_lock_transaction_batch` while holding the `account_locks` mutex), will trigger this: [3](#0-2) 

`Accounts::lock_accounts` is invoked from `Bank::prepare_sanitized_batch_with_results`, which is called by BankingStage's consumer/replay paths to lock an entire packet/entry batch at once: [4](#0-3) [5](#0-4) 

An attacker fully controls the account list, writable/readonly declarations (via account keys ordering, signer flags, or ALT writable/readonly lists) and can freely broadcast multiple transactions that will be pulled into the same processing batch, satisfying the precondition without needing any privileged role.

The existing regression test `test_accounts_locks` does not catch this because its "conflict" case relies on a lock that was already applied by a *separate, prior* call to `lock_accounts`, not a conflict purely internal to a single batch call: [6](#0-5) 

That prior-call conflict is correctly detected because the conflicting lock is already present in `self` *before* pass 1 begins — it is not a same-batch, same-pass conflict, so the existing test suite has a blind spot for exactly this scenario.

### Impact Explanation
This breaks the core write/read exclusivity invariant of `AccountLocks`, which is the sole in-process synchronization primitive protecting concurrent/overlapping transaction processing from touching the same account inconsistently (documented explicitly as "This function will prevent multiple threads from modifying the same account state at the same time"). An attacker can force a validator to grant a write lock and a read lock on the same account simultaneously within one processing batch, defeating the guarantee that `AccountInUse` retries are supposed to provide for intra-batch conflicts. This corresponds to the "undeclared/uncommitted account mutation visibility" and "loading/locking invariant bypass" bounty category referenced in the question (turbine/cluster_nodes lock-invariant class): a downstream reader transaction can be scheduled/loaded believing it holds an exclusive read lock while another transaction concurrently holds a write lock on the same key, exactly matching the invariant violation the question asks about.

### Likelihood Explanation
The bug triggers deterministically whenever a batch contains two or more transactions that (a) reference the same account key, (b) declare conflicting access (one writable, one read-only), and (c) the key was not already locked before the batch call. No privileged role, timing race across threads, or special validator configuration is required — the "race" is not a true concurrency race, it is a deterministic ordering bug in the single-threaded two-pass algorithm executed under the `account_locks` mutex. Any unprivileged user broadcasting two ordinary transactions referencing a shared account with mismatched write/read declarations satisfies the precondition, and standard BankingStage batching (multiple transactions locked together per `prepare_sanitized_batch_with_results` call) provides the reachable code path.

### Recommendation
Change `try_lock_transaction_batch` to interleave validation and lock application per-transaction (check-then-lock atomically per entry, in order), so subsequent transactions in the same batch see the effects of previously locked transactions in that same batch, e.g.:
```rust
validated_batch_keys
    .into_iter()
    .map(|available_keys| {
        available_keys.and_then(|keys| {
            self.can_lock_accounts(keys.clone())?;
            self.lock_accounts(keys);
            Ok(())
        })
    })
    .collect()
```
This restores the original single-pass "check and lock immediately" semantics and ensures intra-batch conflicts are correctly rejected with `AccountInUse`.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (add to `mod tests`)
#[test]
fn test_intra_batch_write_read_conflict_not_detected() {
    let mut locks = AccountLocks::default();
    let key = Pubkey::new_unique();

    // Neither lock exists yet on `key`.
    let tx_a = std::iter::once((&key, true));  // writable
    let tx_b = std::iter::once((&key, false)); // read-only

    let results = locks.try_lock_transaction_batch(vec![Ok(tx_a), Ok(tx_b)]);

    // Correct behavior: one of the two must fail with AccountInUse.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(
        ok_count, 1,
        "both a write-lock and a read-lock on the same key were granted \
         within the same batch: {results:?}"
    );
}
```
Expected (correct) result: exactly one `Ok(())` and one `Err(TransactionError::AccountInUse)`. With the current implementation, both entries return `Ok(())`, demonstrating that `write_locks[key] == 1` and `readonly_locks[key] == 1` are simultaneously non-zero, violating the invariant asserted by `can_read_lock`/`can_write_lock`.

An invariant/fuzz extension: generate many random batches of writable/readonly claims on a small key universe, run them through `try_lock_transaction_batch`, and after each batch assert that for every key, `write_locks.get(key).unwrap_or(&0) > 0` implies no successfully-locked transaction in the same batch declared that key read-only (and vice versa) — this fails reliably whenever a batch contains a first-time write/read conflict on a previously-unlocked key.

    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    fn lock_accounts<'a>(&mut self, keys: impl Iterator<Item = (&'a Pubkey, bool)>) {
        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }
        }
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_readonly(&self, key: &Pubkey) -> bool {
        self.readonly_locks.get(key).is_some_and(|count| *count > 0)
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_write(&self, key: &Pubkey) -> bool {
        self.write_locks.get(key).is_some_and(|count| *count > 0)
    }

    fn can_read_lock(&self, key: &Pubkey) -> bool {
        // If the key is not write-locked, it can be read-locked
        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
        !self.is_locked_readonly(key) && !self.is_locked_write(key)
    }

    /// This function will prevent multiple threads from modifying the same account state at the
    /// same time, possibly excluding transactions based on prior results
    #[must_use]
    pub fn lock_accounts<'a>(
        &self,
        txs: impl Iterator<Item = &'a (impl SVMMessage + 'a)>,
        results: impl Iterator<Item = Result<()>>,
        tx_account_lock_limit: usize,
    ) -> Vec<Result<()>> {
        // Validate the account locks, then get keys and is_writable if successful validation.
        // We collect to fully evaluate before taking the account_locks mutex.
        let validated_batch_keys = txs
            .zip(results)
            .map(|(tx, result)| {
                result
                    .and_then(|_| validate_account_locks(tx.account_keys(), tx_account_lock_limit))
                    .map(|_| TransactionAccountLocksIterator::new(tx).accounts_with_is_writable())
            })
            .collect::<Vec<_>>();

        let account_locks = &mut self.account_locks.lock().unwrap();
        account_locks.try_lock_transaction_batch(validated_batch_keys)
    }
