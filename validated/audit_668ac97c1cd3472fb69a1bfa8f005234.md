### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only that the raw request body is HMAC-signed with the app's `client_secret`; the `shop`, `topic`, and `webhook_id` values used to dispatch and attribute the webhook come from unauthenticated HTTP headers that are never included in the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Webhooks::Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(raw_body, api_secret_key)` and compares it to the `hmac` header: [2](#0-1) [3](#0-2) 

Once the HMAC over the body checks out, `request.shop`, `request.topic`, and `request.webhook_id` are read straight from attacker-controllable HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`) and passed unmodified into `WebhookMetadata`, which is handed to the app's registered handler: [4](#0-3) [2](#0-1) 

The identity binding that should hold is:
`shop_that_produced(body, hmac)` == `shop_attributed_to_handler(data.shop)`

But `data.shop` comes from a header that is completely outside the HMAC's scope, so this equality is never enforced. Because `api_secret_key` is a single, app-wide secret (not per-shop), *any* merchant that has installed the app can obtain a genuinely Shopify-signed `(body, hmac)` pair for their own store (e.g. by triggering a webhook whose body content they influence, such as a `customers/create` or `products/update` payload containing attacker-chosen field values). That merchant can then replay the identical `raw_body` + `hmac` header to the app's webhook endpoint while forging the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) headers to any other tenant's shop domain. `HmacValidator.validate` still passes (it only checks the body bytes), and the handler will process attacker-controlled data as if it originated from the victim shop.

### Impact Explanation
This breaks tenant isolation: an unprivileged app installer (any merchant who can install the app on their own store) can inject attacker-controlled webhook payloads that are attributed to a different, victim shop. Depending on how the host application's webhook handlers use `data.shop` (e.g., to update per-shop shopify-side records, trigger shop-scoped side effects, or key persistent state), this is a cross-tenant data-integrity/confidentiality issue — the "shop" identity that authorized the byte stream (via the shared HMAC secret) does not equal the "shop" the bytes are processed against.

### Likelihood Explanation
Any entity that can install the app on their own shop (a completely unprivileged, self-service action for any Shopify merchant) can obtain a valid `(body, hmac)` pair and immediately replay it with a forged shop header — no access token, `client_secret`, or privileged access is required.

### Recommendation
Bind the shop (and topic) into the value that is actually verified, e.g., include the `x-shopify-shop-domain` and `x-shopify-topic` header values in the signable string (or independently verify that the shop present in the parsed JSON payload matches the header), so a forged header cannot be paired with a legitimately-signed body from a different shop context.

### Proof of Concept
1. Attacker installs the target app on their own shop (`attacker.myshopify.com`), a normal, unprivileged step.
2. Attacker triggers a webhook whose JSON body they can influence (e.g., updates a product title to a payload of their choosing) so Shopify sends `POST /webhook` to the app with a body `B` and a valid `x-shopify-hmac-sha256` header `H = HMAC(B, client_secret)`.
3. Attacker replays `B` and `H` unchanged to the same webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(B, client_secret)` and it matches `H`, so `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` — attacker-controlled data is processed under the victim's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
