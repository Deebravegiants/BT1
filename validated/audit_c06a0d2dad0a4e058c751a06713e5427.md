## Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the shop identity (`shop-domain` header) that is later handed to the app's webhook handler is never included in the signed bytes. Any party able to trigger a genuine webhook delivery for the app (e.g., a merchant who has installed the app in their own store) can capture a legitimately-signed body/HMAC pair and resend it to the shared webhook endpoint with an arbitrary `shop-domain` header, since that header is not part of what is verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC over the request (which, per above, only certifies `raw_body`), then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The HMAC secret (`api_secret_key`) is a single per-app secret shared across every shop that has the app installed — it is not shop-specific. Consequently:

- The equality that should hold is `HMAC-authenticated-tenant == tenant used for handler dispatch`.
- What actually holds is `HMAC-authenticated-bytes == raw_body only`, while `tenant used for handler dispatch == unauthenticated shop-domain header`.

Because the same app-wide secret signs webhooks for every installed shop, an attacker who installs the app on their own store (an ordinary, unprivileged action) can trigger a genuine webhook (e.g. `orders/create`) with a body of their choosing and obtain a body+HMAC pair that Shopify computed with the app's secret. They can then replay that exact body and HMAC to the app's single shared webhook endpoint while substituting the `shop-domain` header for a victim shop's domain. `Utils::HmacValidator.validate` will still pass because it only checks `raw_body` against the signature: [4](#0-3) 

The handler then receives `WebhookMetadata` claiming to be from the victim shop, with attacker-controlled body content, breaking the shop-to-signature binding entirely.

### Impact Explanation
This is a cross-tenant identity-binding break: the library lets an attacker forge the *shop of origin* for otherwise validly-signed webhook payloads. Any app logic keyed off `data.shop` (e.g., updating per-shop state, writing to a shop-scoped database record, triggering shop-specific side effects, or associating attacker-controlled body data with a victim's session/shop) can be corrupted or hijacked cross-tenant, without the attacker ever possessing the victim's credentials or the app's `client_secret`. This matches the "Critical - cross-tenant access" impact bucket.

### Likelihood Explanation
Medium-to-high: it requires the attacker to be an app installer (any merchant can install a public app on their own store — no special privilege), be able to trigger at least one webhook topic subscribed by the app with attacker-influenced body content, and be able to send an HTTP request directly to the app's public webhook endpoint with a modified `shop-domain` header. All of these are within reach of an ordinary unprivileged internet user/merchant; no access token, `client_secret`, or victim credential is required.

### Recommendation
Include the shop domain (and ideally other identifying headers such as `topic`/`webhook_id`) inside the signed material, or otherwise cryptographically bind `request.shop` to the HMAC-verified payload before it is trusted for dispatch in `Registry.process`. At minimum, document/enforce that consuming apps must independently verify that `data.shop` corresponds to a shop that installed the app with the same session/token context, rather than trusting the header as authenticated by the HMAC check alone.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Attacker triggers a subscribed webhook topic (e.g. `orders/create`) with a body they control (their own order data).
3. Attacker captures the resulting POST to the app's webhook endpoint, including headers `x-shopify-hmac-sha256: <HMAC>` and `x-shopify-shop-domain: attacker.myshopify.com`, and the raw JSON body.
4. Attacker resends the identical body and `x-shopify-hmac-sha256` value to the same endpoint, but with header `x-shopify-shop-domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds (it only checked the body bytes), and `Registry.process` dispatches the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, i.e., attacker-controlled data is processed as if originating from the victim shop.
