### Title
Webhook topic/shop headers are not covered by the HMAC signature, letting a valid signature for one topic/shop be replayed under attacker-forged headers - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes the signature purely from `to_signable_string` [2](#0-1) . `Registry.process` trusts `request.topic` and `request.shop` (both derived from headers, not from the signed body) to dispatch the handler and construct `WebhookMetadata` [3](#0-2) . The `initialize` method in `Request` only checks that `topic`, `hmac-sha256`, and `shop-domain` headers *exist*, not that they are well-formed or bound to the body [4](#0-3) .

### Finding Description
The claimed broken binding: `HMAC_valid(raw_body) == authenticated(topic, shop)` is assumed by `Registry.process`, but it does not hold. `HmacValidator.validate` only proves `hmac == HMAC_secret(raw_body)`; it never touches `request.topic` or `request.shop` [5](#0-4) . `Request#topic` and `Request#shop` are read straight from the (attacker-controlled, framework-supplied) header hash via `shopify_header` [6](#0-5) [7](#0-6) .

Regarding the specific header-normalization mechanism cited in the question: `initialize` normalizes header keys with `k.to_s.downcase.sub("http_", "").gsub("_", "-")` and folds them into a single hash via `to_h` [8](#0-7) . If two distinct incoming keys collapse to the same normalized key (e.g. a literal `http_shopify-topic` header colliding with the framework's own `HTTP_X_SHOPIFY_TOPIC`→normalized form), `to_h` keeps only the last value for that key — a real "second claimant" collision. However, whether an attacker can actually inject a raw header that Rack/Rails will hand to this method as a *literal* string starting with `http_` (rather than the framework already prefixing/uppercasing it to `HTTP_...` from `env`) depends entirely on the host app's `headers:` argument construction, which is outside this gem. This gem's code does not fetch headers from `request.env` itself — it just accepts whatever hash the host app passes in. So the specific collision mechanic described in the question is not demonstrably reachable from this gem's own code; it is contingent on host-app behavior not present in this repo.

What *is* verifiable purely within this gem is the broader, root-cause issue: **topic and shop are never included in the signed content**, so *even without any header-key collision*, an attacker who owns a legitimately-registered webhook subscription on their own development shop can take one validly-HMAC-signed payload and resend it to the app's webhook endpoint with a different `X-Shopify-Topic` or `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` will still return `true` (the body/HMAC pair is unchanged), and `Registry.process` will dispatch it to whichever handler is registered for the forged topic, and will construct `WebhookMetadata` with the forged `shop` [3](#0-2) .

### Impact Explanation
This allows an attacker to feed a handler attacker-chosen `topic`/`shop` metadata alongside a body that was never actually generated for that topic/shop, as long as they can produce *any* validly-signed webhook body (trivially available to them via their own shop's genuine webhook deliveries). Depending on what the host application's handler does with `WebhookMetadata#shop` (e.g., looking up a session/access token for that shop, or trusting `topic` to select which merchant-facing action to take), this can lead to cross-tenant confusion. This does not, by itself, exfiltrate another merchant's `X-Shopify-Access-Token` from this gem — no code path in `lib/shopify_api/webhooks/**` reads or transmits access tokens. Actual token theft would require a downstream handler in the host app to trust `request.shop`/`request.topic` to look up and expose a token, which is host-app-specific and cannot be confirmed from this repo alone.

### Likelihood Explanation
Preconditions: the attacker needs a real, validly-signed webhook body, which they can obtain by installing the app on their own development shop and having Shopify deliver a signed webhook to their own endpoint (fully within the described "unprivileged attacker" capabilities). They then need to be able to POST to the target app's webhook endpoint with custom headers — again within scope. The specific `http_` prefix-collision variant described in the question additionally requires the host app to pass a header hash to `Request.new` in which an attacker-controlled key can literally collide with the framework-derived Shopify header after normalization; this is not verifiable as reachable purely from this gem's code.

### Recommendation
Bind `topic` and `shop` cryptographically to the request by including them in `to_signable_string` if Shopify's signature scheme supports it, or independently validate that `shop` corresponds to a shop that actually has an active webhook subscription for the given `topic`/`webhook_id` before dispatch. Additionally, harden the header-normalization in `initialize` to reject or explicitly detect collisions (e.g., raise if a `http_`-prefixed and non-prefixed variant of the same canonical header disagree) rather than silently letting `to_h` pick the last value.

### Proof of Concept
Not provided — the collision precondition (attacker able to supply a literal `http_`-prefixed key that collides with the framework's own Shopify header key inside the `headers:` hash passed to `Request.new`) could not be confirmed as reachable using only this gem's code; confirming it requires inspecting how the specific host framework (e.g., Rails `ActionDispatch::Http::Headers`/`env`) constructs and passes that hash, which is outside `lib/shopify_api/webhooks/**` and this repository.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
