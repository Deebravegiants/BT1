## Finding: `CallDispatcher.dispatch()` is a fully unauthenticated function that lets any address drain assets stranded on a persistent, shared dispatcher contract

### Title
Unauthenticated `CallDispatcher.dispatch()` allows anyone to steal residual token/ETH balances left on the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` has no caller restriction whatsoever - unlike `PeripheryPayments.sweepToken`/`refundETH` in the referenced report, which at least require the funds to already be sitting in the contract, `dispatch()` is a strictly more powerful unguarded primitive: it lets **any address** command the dispatcher to execute **arbitrary calls with the dispatcher's own ETH balance and any ERC20 tokens it currently holds**. Because `CallDispatcher` is a persistent, publicly documented, shared singleton reused by `HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`, and their Tron counterparts, any tokens/ETH that end up parked on it outside of a single atomic sweep-and-forward transaction are permanently up for grabs.

### Finding Description
`CallDispatcher.dispatch` [1](#0-0)  takes an ABI-encoded `Call[]` and executes each call with `to.call{value: call.value}(call.data)`, with **no `onlyOwner`, `onlyHost`, or any msg.sender check at all**. Anyone can call this function directly on the deployed `CallDispatcher` address and instruct it to send its own held ETH or invoke `transfer`/`transferFrom` on any ERC20 it holds a balance/allowance for, to any recipient.

Several call sites route tokens through this same dispatcher **without a guaranteed dust-sweep-back**:
- `HyperFungibleToken.onAccept` mints tokens directly to a beneficiary that documentation explicitly recommends setting to the `CallDispatcher` address so that attached calldata can spend them, then invokes `ICallDispatcher(_dispatcher).dispatch(message.data)` [2](#0-1) . There is no balance-before/after accounting or forced sweep-back of any leftover tokens after `message.data` executes, unlike the intent-gateway flows.
- The documented usage pattern explicitly states: "mint to the `CallDispatcher` so the swap can spend the tokens" [3](#0-2) , and the security notes acknowledge the dispatcher "holds tokens temporarily during execution" [4](#0-3)  without mandating full consumption/sweep of the balance.
- `CallDispatcher` implements `receive() external payable {}` [5](#0-4) , so it can silently accumulate native ETH from any of the many `Call.value` forwards used throughout `IntentGatewayV2`/`IntentsBase` flows (e.g. `_execute`) [6](#0-5) , if slippage, partial swap fills, or fee-on-transfer edge cases leave a remainder that isn't captured by every downstream sweep loop.
- Docs confirm `CallDispatcher` is a **persistent, well-known, shared deployment** reused across integrations rather than a fresh ephemeral contract per call: "Existing `CallDispatcher` deployments are listed on the contract addresses page" [7](#0-6) .

Any residual token/ETH balance left on this shared dispatcher - whether from a partial swap, a fee-on-transfer shortfall, an incomplete calldata sequence supplied by an integrator, or simple user error sending funds to a documented, public contract address - can be swept out by literally anyone by calling `dispatch()` directly with a `Call` that transfers the dispatcher's balance to themselves. This is architecturally identical to the reported bug class (an externally-callable, unauthenticated function capable of extracting a contract's held assets), except here the "sweep" primitive is even more general (arbitrary call execution rather than a fixed transfer-to-recipient).

### Impact Explanation
Any ETH or ERC20 balance that legitimately or accidentally lands on the shared `CallDispatcher` (dust from swaps executed on behalf of `HyperFungibleToken`/`WrappedHyperFungibleToken`/`IntentGatewayV2` users, or direct mistaken transfers to this documented address) can be permanently stolen by any unprivileged third party. This is a direct, unauthorized loss-of-funds vector affecting end users of the token-bridge and intent-gateway apps that route calldata through this dispatcher, satisfying the "concrete theft ... of funds" bar.

### Likelihood Explanation
`CallDispatcher` is deployed once and reused across many apps/chains per the documentation, so it is a high-value, well-known target. Any integrator building calldata for the documented swap-then-forward pattern (e.g., the exact ETH→USDC or DEX-swap examples in the docs) that does not perfectly consume 100% of the minted/unlocked balance — due to slippage tolerances, partial fills, or fee-on-transfer tokens — leaves exploitable dust. Because `dispatch()` requires no special permission and no proof, exploitation is a single trivial transaction for any observer monitoring the dispatcher's balance.

### Recommendation
Restrict `CallDispatcher.dispatch()` so it can only be invoked by an authorized caller (e.g., only the app/`onlyHost`/an allowlisted set of gateway contracts), or make the dispatcher ephemeral (deploy-per-call via `CREATE2`/factory pattern) so no shared, persistent contract accumulates cross-user balances. If a shared singleton is retained, add explicit balance accounting so any residual ETH/token dust is force-swept back to the originating caller/app at the end of every `dispatch()` invocation rather than being left recoverable by arbitrary third parties.

### Proof of Concept
1. A user calls `HyperFungibleToken.send(...)` (or triggers cross-chain delivery) with `to = CallDispatcher` and `data` containing a swap call that, due to slippage tolerance, leaves 5% of the minted tokens unspent on the `CallDispatcher`.
2. `onAccept` mints the tokens to the `CallDispatcher` and calls `ICallDispatcher(_dispatcher).dispatch(message.data)`; the swap consumes 95% of tokens, 5% remains on `CallDispatcher`.
3. Attacker observes the `CallDispatcher`'s ERC20 balance on-chain and submits `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualBalance)})]))` directly - no permission check exists, so the call succeeds and the residual tokens are transferred to the attacker.     function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
