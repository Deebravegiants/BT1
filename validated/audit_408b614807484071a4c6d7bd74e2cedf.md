### Title
Item-attribute delegate approvals (`ItemAttributesApprovalsOf`) survive ownership transfer, allowing a former owner to retain write/clear access to `Account(delegate)` namespace attributes on the buyer's NFT - ([File: substrate/frame/nfts/src/features/transfer.rs] / [File: substrate/frame/nfts/src/features/attributes.rs])

### Summary
`do_transfer` (transfer.rs, lines 90-103) explicitly clears `details.approvals` (transfer delegates), `ItemPriceOf`, and `PendingSwapOf` when an item changes hands, with a code comment stating this is done specifically to prevent a "pre-approve attack." It does **not** clear `ItemAttributesApprovalsOf` for the item, and `is_valid_namespace` (attributes.rs, lines 474-479) only checks that the caller is present in that per-item approval set — it never checks against the item's *current* owner. This lets a seller who pre-approved themselves as an `Account` delegate keep writing/clearing attributes on the item after selling it.

### Finding Description
- `do_approve_item_attributes` (attributes.rs, lines 372-394) lets the current owner insert an arbitrary `delegate` into `ItemAttributesApprovalsOf::<T, I>` for the item, requiring only `check_origin == details.owner` at call time.
- `do_transfer` (transfer.rs, lines 46-113) updates `Account`, `Item.owner`, clears `details.approvals`, `ItemPriceOf`, `PendingSwapOf` — but never touches `ItemAttributesApprovalsOf::<T, I>(collection, item)`. [1](#0-0) 
- After transfer, `is_valid_namespace` for `AttributeNamespace::Account(account_id)` only checks `account_id == origin && approvals.contains(&origin)` — it does not re-validate against the new owner at all: [2](#0-1) 
- Consequently, the attacker (former owner) can still call `set_attribute`/`clear_attribute` with `namespace = Account(attacker)` on the item post-sale, and the call passes permission checks because the stale approval entry is still present.
- The developers' own rationale for clearing `details.approvals` on transfer ("otherwise pre-approve attack would be possible, where the owner can approve their second account before making the transaction and then claiming the item back") applies identically to `ItemAttributesApprovalsOf`, but the same mitigation was not applied there — an inconsistency in the invariant enforcement.

Important correction to the scoped-impact claim: the deposit for attributes set in the `Account` namespace is reserved from the **depositor passed into `do_set_attribute`**, which for the normal `set_attribute` extrinsic is the signer itself (the attacker), not the victim: [3](#0-2) 
So the "forcing new deposit reservations... without the new owner's consent" part of the scoped impact does not hold against the victim's funds — the attacker pays their own deposit to keep writing. The genuine, concrete impact is unauthorized persistent write/clear access to `Account(attacker)`-namespaced metadata on an item the victim now owns, without the victim's knowledge or consent, until the victim discovers and proactively revokes it.

### Impact Explanation
The new owner does retain the ability to remove the stale approval via `do_cancel_item_attributes_approval` (attributes.rs, lines 412-453), which checks `check_origin == details.owner` against the *current* owner — so the victim, once aware, can self-remedy in one extrinsic. However, until they do so, the former owner/attacker retains unauthorized write and clear access to attribute data in the `Account(attacker)` namespace tied to an item they no longer own, which is not communicated or consented to by the buyer and violates buyer-exclusive control expectations, especially since the pallet explicitly resets analogous approvals (`details.approvals`) on transfer for exactly this class of attack.

### Likelihood Explanation
Fully feasible with only unprivileged extrinsics: `approve_item_attributes` (self-approval, owner-only check succeeds trivially since attacker is owner at call time) → `transfer`/sale → `set_attribute`/`clear_attribute` with `namespace = Account(attacker)`. No special privileges, signatures, or races are required; it is deterministic and repeatable for any item and any collection with the `Attributes` pallet feature enabled.

### Recommendation
Clear `ItemAttributesApprovalsOf::<T, I>::remove(&collection, &item)` inside `do_transfer`, mirroring the existing `details.approvals.clear()` treatment and the removal of `ItemPriceOf`/`PendingSwapOf`, so that item-attribute delegate approvals do not survive ownership changes. If backward compatibility for continuity use-cases (e.g., game contracts writing stats) is desired, consider unreserving/refunding delegate deposits for attributes under the cleared approvals (similar to `do_cancel_item_attributes_approval`) at transfer time, or requiring explicit re-approval by the new owner.

### Proof of Concept
```rust
#[test]
fn stale_item_attribute_approval_survives_transfer() {
    new_test_ext().execute_with(|| {
        let attacker = 1;
        let victim = 2;
        let collection = 0;
        let item = 0;

        // setup: attacker mints collection/item (existing helper flow)
        // ...

        // attacker approves self as Account delegate while still owner
        assert_ok!(Nfts::approve_item_attributes(
            RuntimeOrigin::signed(attacker),
            collection, item, attacker
        ));

        // attacker transfers item to victim
        assert_ok!(Nfts::transfer(
            RuntimeOrigin::signed(attacker),
            collection, item, victim
        ));

        // BUG: attacker can still write attributes in Account(attacker) namespace
        assert_ok!(Nfts::set_attribute(
            RuntimeOrigin::signed(attacker),
            collection, Some(item),
            AttributeNamespace::Account(attacker),
            b"key".to_vec(), b"value".to_vec(),
        ));

        // Expected (post-fix) behavior: this should fail with Error::NoPermission
        // because ItemAttributesApprovalsOf should have been cleared on transfer.
        assert!(ItemAttributesApprovalsOf::<Test>::get(collection, item).contains(&attacker));
    });
}
```
Expected assertion after fix: `set_attribute` from `attacker` in `Account(attacker)` namespace fails with `Error::<T,I>::NoPermission` immediately after transfer, and `ItemAttributesApprovalsOf` for the item is empty post-transfer.
