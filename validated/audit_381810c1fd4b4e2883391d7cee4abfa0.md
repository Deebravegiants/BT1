### Title
Webhook Shop Domain Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (tenant identifier) is read from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header. `Webhooks::Registry.process` validates the HMAC over the body only, then forwards the unauthenticated `shop` header value to the app's handler as the tenant identity. This breaks the binding `authenticated_bytes == identity_bytes`, letting anyone who can produce one valid (body, HMAC) pair replay it with an arbitrary `shop` header value.

### Finding Description
`HmacValidator.validate` computes/verifies the HMAC solely over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body, excluding topic, shop, webhook-id, and api-version: [2](#0-1) 

`shop` is read straight from an HTTP header with no cryptographic binding to the signed payload: [3](#0-2) 

`Registry.process` validates only the HMAC and then trusts `request.shop` as the tenant identity passed to the handler: [4](#0-3) 

The equality the code implicitly relies on is:
`hmac_valid(body) == true` implies `shop_header == authentic_tenant_for(body)`

but the HMAC only proves `body` was signed with the app's secret — it says nothing about which shop the request is attributed to. Any actor able to obtain one genuine `(body, hmac)` pair (e.g. from a webhook legitimately delivered to their own, attacker-controlled shop that has this app installed) can resend that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still returns `true` because the header is not part of the signed material, and the handler receives `WebhookMetadata` with the attacker-chosen `shop`, misattributing the payload to the victim tenant.

### Impact Explanation
This crosses a tenant boundary: an app that keys per-shop state (installation records, order/customer sync state, entitlements, etc.) off `WebhookMetadata#shop` can be made to apply attacker-supplied webhook data under a different merchant's tenant identity — a cross-tenant access/data-integrity issue reachable by any user who can get one app-installed shop (their own) to deliver a webhook.

### Likelihood Explanation
Requires only that the attacker operate one shop with the target app installed (to receive a genuinely-signed webhook body) and the ability to POST to the app's public webhook endpoint with a modified `shop` header — no access to `client_secret`/access tokens, no privileged account, no TLS interception needed.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the material verified against the HMAC, or independently authenticate that `request.shop` corresponds to a shop with an active installation/session before trusting it as the tenant key, rather than accepting it solely from the unauthenticated header alongside a body-only HMAC check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers a webhook for a topic (e.g. `orders/create`).
2. Shopify delivers a webhook to the app with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and its HMAC, then sends a new POST to the app's webhook endpoint with the same body `B` and same HMAC header, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds (only `B` is checked). `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled data under the victim tenant.
