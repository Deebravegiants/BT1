**Why the premise doesn't hold:**

The cache key for `SyncScriptCache` in the script-cache path is not an arbitrary "resource-account Key" — it's the SHA3-256 hash of the serialized script bytecode itself, computed at each call site before insertion: [1](#0-0) [2](#0-1) 

Since the key is `hash = sha3_256(serialized_script)`, two *distinct* verified scripts cannot legitimately collide on the same key unless there is a SHA3-256 preimage/collision, which is outside any realistic attacker capability and outside this custody review's scope (no repo-level cryptographic weakness is present). The `test_sync_insert_verified_multithreaded`-style scenario in the codebase only demonstrates that *identical-key* races (i.e., the same script hash, submitted by many racing threads) resolve deterministically to whichever verified script wins the `DashMap::entry` race — not that attacker-chosen distinct scripts can be substituted under a victim's key: [3](#0-2) [4](#0-3) 

Additionally, even setting aside the hash-collision requirement, this cache is a purely in-process, per-block (or per-execution-session) performance optimization inside `MVHashMap`/loader machinery — it holds no on-chain state, is rebuilt per execution, and has no relation to code-object ownership, resource-account authority, or dispatch permissions recorded on-chain: [5](#0-4) 

Winning a race for this cache only determines which `Arc<Script>` object instance is reused for verification-avoidance within that execution; it does not "permanently bind" any code object nor does it change who can own, move, mint, burn, freeze, upgrade, or recover value. There is no unprivileged path from this mechanism to any custody-grade impact as defined in the review's Custody Impact Gate.
