In `lib/shopify_api/webhooks/request.rb`, the HMAC is computed only over `@raw_body` (`to_signable_string` returns `@raw_body`), while `shop` (the `shopify-shop-domain`/`x-shopify-shop-domain` header) is never part of the signed material yet is trusted directly to build `WebhookMetadata` and dispatched to the app's handler.### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, but the `shop` (tenant) identifier is read from an unauthenticated HTTP header and passed on to the app's webhook handler without being part of the signed material.

### Finding Description
`Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)` [1](#0-0) , which in turn calls `to_signable_string` on the `VerifiableQuery` (the `Request` object) and compares an HMAC computed over that signable string against the presented `hmac`. For `Webhooks::Request`, `to_signable_string` returns only the raw body: `@raw_body` [2](#0-1) .

The tenant-identifying field, `shop`, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header via `shopify_header` [3](#0-2)  and [4](#0-3) . This header is never included in `to_signable_string`, so it is **not covered by the HMAC**. After HMAC validation passes (based only on the body bytes and the real secret), `Registry.process` builds `WebhookMetadata` using `request.shop` taken straight from that unauthenticated header, and dispatches it to the app's handler as the trusted tenant identity [1](#0-0) .

This breaks the intended binding: `hmac == HMAC(secret, signed_material)` should imply `signed_material` (and every field derived from the request that the app trusts as authenticated, including the tenant) is what Shopify actually sent. Here, `shop` is excluded from `signed_material`, so `shop` can be forged independently of the (otherwise valid) HMAC over the body.

### Impact Explanation
An unprivileged internet user who has ever obtained one legitimate, correctly-HMAC-signed webhook payload for their own shop (or replays/observes one, e.g. via their own trial/dev store, from public webhook payload samples, or by triggering a webhook on a shop they control) can resend that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. Because the header is not part of the signed data, `HmacValidator.validate` still returns `true` (the body and secret are unchanged), and `Registry.process` will hand the forged `shop` value to the app's handler as if it came from the victim tenant. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up a session/store record, to write to per-tenant data, or to trigger tenant-scoped side effects such as `customers/redact` or `shop/redact` handling), this is a cross-tenant data/identity confusion vector — an app could act on, or attribute, data to the wrong merchant.

### Likelihood Explanation
Likelihood is moderate: exploitation requires only a legitimately signed webhook body (which an attacker can obtain for a shop they themselves control, since anyone can install/develop a Shopify app and receive their own webhooks) and does not require the app's `client_secret` or any privileged account belonging to the victim. No TLS interception or credential theft is needed — only crafting an HTTP request with a substituted header, which is fully in the "unprivileged internet user" threat class.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signed material used for HMAC verification, or otherwise cryptographically bind the tenant identity to the verified payload before trusting `request.shop` in `Registry.process`. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should not allow any field consumed downstream as an authenticated/tenant-identifying value to be excluded from what is HMAC-verified.

### Proof of Concept
1. Attacker installs the target app on their own shop (`attacker-shop.myshopify.com`) and receives a legitimately signed webhook, e.g. `orders/create`, with body `B` and valid header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(client_secret, B)`.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the same body `B` and the same valid `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` recomputes `HMAC(client_secret, B)` (per `to_signable_string` returning only `@raw_body`), matches `H`, and returns `true` — regardless of the forged `shop-domain` header [2](#0-1) [5](#0-4) .
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `request.shop` is `"victim-shop.myshopify.com"` [1](#0-0) , even though the payload never actually originated from or concerned that shop.
