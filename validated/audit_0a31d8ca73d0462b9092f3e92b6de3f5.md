### Title
Webhook `shop` (and topic/id) header trusted for tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight to the app's handler as the trusted tenant identifier. The HMAC never covers that header, so the binding "shop authenticated == shop acted on" does not hold: any party who can obtain one genuine, validly-signed webhook body (e.g., by installing the app on their own store, since `api_secret_key` is shared across all shops of a given app) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` (and `topic`/`webhook-id`/`api-version`) header, causing the host application to process another shop's webhook data (or attacker-supplied data) as if it originated from a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers: [2](#0-1) 

`HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` (i.e., the body) against the shared `api_secret_key`: [3](#0-2) 

`Registry.process` performs this body-only HMAC check and then immediately trusts `request.shop` (and the other header-derived fields) as the tenant/topic identity passed to the handler, with no cross-check that the signed body actually belongs to that shop: [4](#0-3) 

Because the same `api_secret_key` is shared by every shop that has the app installed, an unprivileged user who installs the app on their own (free) development store receives genuine webhook deliveries with a valid HMAC computed over a body they fully control/observe. They can capture that `(body, hmac)` pair and re-POST it to the app's webhook endpoint with the `shop-domain` header changed to a different, victim shop. `HmacValidator.validate` still returns `true` (the body/HMAC pair is untouched and valid for the shared secret), and `Registry.process` forwards `shop: request.shop` (attacker-chosen) to the handler. Any host application that keys its data mutations off `WebhookMetadata#shop` — the documented and expected usage pattern for this gem, since it no longer manages session storage as of v13.0.0 — will apply the attacker-controlled body to the wrong tenant's records.

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold is `shop_header == shop_that_produced(raw_body, hmac)`, but the gem cannot and does not enforce it because `shop` is excluded from `to_signable_string`.

### Impact Explanation
This allows an unprivileged internet user (anyone who can install the target app on any shop) to spoof the tenant identity of a webhook delivery for a body they can influence or capture, causing cross-tenant data confusion in the host application — e.g., an `orders/create`, `customers/data_request`, or `app/uninstalled` payload attributed to a shop that never sent it. This matches the High-impact category of scope/tenant-boundary bypass via a credential (HMAC) that does not bind to the field the application trusts for tenant selection.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to be able to install the target app on a shop they control (trivial for public apps with free installs) and to be able to send arbitrary HTTP requests to the app's public webhook endpoint (which by definition must be internet-reachable to receive real Shopify webhooks). No access to `api_secret_key`, tokens, or Shopify infrastructure is needed — only observation/capture of one legitimately delivered webhook from the attacker's own installation.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the signable material used for HMAC verification, or otherwise cryptographically bind them to the body before `Registry.process` exposes them to handlers. At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and that host applications must independently verify the shop is a currently installed/known tenant (e.g., by checking against stored session/shop records) before trusting it, rather than treating a passing `HmacValidator.validate` as proof that the whole `WebhookMetadata` payload — including `shop` — is authentic.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a store they control) and lets it complete OAuth normally.
2. Attacker triggers/observes a real webhook delivery to the app's webhook endpoint, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC over the raw body, using the app's shared api_secret_key>
x-shopify-shop-domain: attacker-shop.myshopify.com
Body: {"id": 123, ...attacker-controlled order data...}
```
3. Attacker replays the identical body and identical `x-shopify-hmac-sha256` value, but changes only the shop header:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <same value as step 2, unchanged>
x-shopify-shop-domain: victim-shop.myshopify.com
Body: {"id": 123, ...attacker-controlled order data...}   (unchanged)
```
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over the (unchanged) raw body with the shared secret and it matches, so validation passes.
5. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the app's handler, which now processes attacker-supplied order data under `victim-shop`'s identity.
