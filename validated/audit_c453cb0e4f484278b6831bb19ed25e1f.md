Audit Report

## Title
CORS origin allowlist bypass via unanchored domain-suffix matching in gateway HTTP server - ([File: core/services/gateway/network/httpserver.go])

## Summary
The Chainlink Gateway's public HTTP server validates the `Origin` header against a configured allowlist (`CORSAllowedOrigins`) before reflecting it back in `Access-Control-Allow-Origin`. The wildcard-matching logic in `isAllowedOrigin` uses an unanchored `strings.HasSuffix` check without requiring a `.` boundary, allowing any attacker-registered domain that merely ends with the allowed domain string (not a real subdomain) to be treated as trusted.

## Finding Description
`isAllowedOrigin` strips the `*.` prefix from a configured wildcard entry and checks `strings.HasSuffix(originHost, allowedHost)` with no requirement that the preceding character be a literal `.`: [1](#0-0) 

Given an allowed pattern like `https://*.example.com` (`allowedHost = "example.com"`), an attacker who registers the completely independent domain `xexample.com` (a valid public second-level domain, unrelated to `example.com`) passes the check because `"xexample.com"` literally ends with `"example.com"`. The same applies to `attacker-example.com`. This function gates the CORS response reflection in the gateway's public request handler: [2](#0-1) 

No other validation exists upstream — `handleRequest` is registered directly against the configured request `Path` with no additional origin checks, and any unauthenticated client can send a request with a crafted `Origin` header. [3](#0-2) 

The existing test coverage only validates true subdomain matches (`remix.ethereum.org` against `*.ethereum.org`, etc.) and does not cover the confusable-domain edge case, confirming this bypass is unguarded. [4](#0-3) 

## Impact Explanation
When the crafted origin matches, the server reflects it via `Access-Control-Allow-Origin`, telling browsers that the attacker-controlled origin is trusted. A page hosted on the attacker's confusable domain can issue cross-origin requests to the gateway and read the JSON response via browser fetch/XHR, defeating the intended origin allowlist. This is a genuine allowlist-bypass, an in-scope impact category for the internet-facing gateway component.

## Likelihood Explanation
Exploitation requires only that the operator configure a wildcard CORS entry (`*.<domain>`) — a supported and documented configuration pattern (see `sample_config.toml`) — and that an attacker register any public domain ending with that string. No credentials, privileged access, or victim social engineering beyond visiting the attacker's page are required; the crafted `Origin` header is trivially sent by any browser-based client and the check executes on every request to `handleRequest`.

## Recommendation
Fix `isAllowedOrigin` to require the character immediately preceding the suffix match to be a literal `.`, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".example.com"
    if originHost == suffix[1:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```

## Proof of Concept
1. Configure gateway with `CORSAllowedOrigins = ["https://*.example.com"]` and `CORSEnabled = true`.
2. Send an HTTP request to the gateway's configured `Path` with header `Origin: https://xexample.com`.
3. Observe the response includes `Access-Control-Allow-Origin: https://xexample.com`, matching the reflect-back behavior shown in the existing wildcard test at `core/services/gateway/network/httpserver_test.go` lines 152-186, but using a non-subdomain confusable host instead of a genuine subdomain.
4. This can be codified as a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`, asserting that origin `https://xexample.com` against allowed `https://*.example.com` incorrectly returns `true` from `isAllowedOrigin`.
