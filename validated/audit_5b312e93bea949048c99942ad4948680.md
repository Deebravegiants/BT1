### Title
Interest accrual can permanently freeze a market after RAY value overflow - (File: `common/src/rates/simulate.rs`)

### Summary
The pool accrues interest before every market mutation. During accrual, `accrue_step` multiplies scaled debt by `borrow_index` and scaled supply by `supply_index` before the borrow index is capped. If either product exceeds `i128::MAX`, the fixed-point multiplication panics instead of saturating. Once a large, highly utilized market reaches that state, every subsequent operation touching the market fails during the same mandatory accrual, permanently freezing supplier withdrawals, borrower repayments, and liquidations.

### Finding Description
Every market leg loaded through `ops::load_leg` calls `synced_market`, which calls `interest::global_sync`. [1](#0-0)  `global_sync` runs `accrue_step` for every elapsed interval before allowing the requested operation to proceed. [2](#0-1) 

`accrue_step` computes `borrowed * borrow_index` and `supplied * supply_index` as RAY values before updating or clamping the indexes. [3](#0-2)  These operations use `Ray::mul`, which calls `mul_div_half_up` and panics with `MathOverflow` when the result cannot fit in `i128`. [4](#0-3) [5](#0-4) 

The configured borrow-index ceiling does not prevent this failure because `update_borrow_index` computes the unbounded product `old_index * interest_factor` before comparing the result to `MAX_BORROW_INDEX_RAY`. [6](#0-5)  Separately, the earlier `borrowed * borrow_index` valuation can overflow before the index itself reaches its configured ceiling. [7](#0-6) 

Repayment and withdrawal are both reachable through this path: `repay::accounting` calls `ops::load_leg`, and `withdraw::accounting` does the same. [8](#0-7) [9](#0-8)  Controller entrypoints including `borrow`, `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, and permissionless `update_indexes` all ultimately encounter the same market synchronization requirement. [10](#0-9) 

### Impact Explanation
Once `borrowed * borrow_index` or `supplied * supply_index` exceeds the `i128` RAY domain, no operation that synchronizes the market can complete. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot reduce unsafe debt, and bad-debt cleanup cannot execute. Token principal remains in the pool contract but cannot be accessed through protocol paths, resulting in permanent freezing of user funds and potential protocol insolvency for an overborrowed market.

### Likelihood Explanation
Triggering this condition requires an exceptionally large market value and sustained positive interest accrual, so it is unlikely in normal market sizes. However, the protocol explicitly admits values near the token-to-RAY maximum and does not bound total scaled market value tightly enough to ensure `scaled_shares * index` always fits `i128`. A sufficiently funded unprivileged borrower can establish the large debt position through `borrow`, while any later user can trigger the freeze with `update_indexes` or another market operation. No privileged access, malformed state, or oracle dishonesty is required.

### Recommendation
Make accrual arithmetic saturating or explicitly bounded before multiplication. In particular:

- Detect `borrowed * borrow_index` overflow in `accrue_step` and clamp the computed market value or index before panicking.
- Compute the capped borrow index using a quotient comparison, such as `interest_factor <= MAX_BORROW_INDEX_RAY / old_index`, instead of multiplying first.
- Store or compare market values in `I256` through accrual, then clamp values that must be represented as `i128`.
- Add a regression test showing that a near-limit market reaching the borrow-index ceiling can still repay, withdraw, liquidate, and update indexes.

### Proof of Concept
1. Supply enough supported collateral to a controller account to satisfy post-borrow solvency.
2. Supply a very large amount of debt asset to the target market.
3. Call `Controller::borrow(caller, account_id, [(debt_asset, amount)], to)` with a debt amount close to the market’s admitted RAY value limit.
4. Allow the ledger timestamp to advance while utilization remains high.
5. Call `Controller::update_indexes` or any operation touching that market, such as `repay` or `withdraw`.
6. `ops::synced_market` invokes `global_sync`; `accrue_step` evaluates `scaled_to_original(borrowed, borrow_index)`, which overflows `i128` and panics.
7. Repeat `repay`, `withdraw`, or `liquidate`; all fail at the same accrual step before mutation or token settlement, leaving the market permanently stuck.

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
