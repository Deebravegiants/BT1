### Title
Unrestricted `CallDispatcher.dispatch` lets anyone drain any ETH or ERC-20 balance sitting in the contract - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch(bytes)` is `external` with **no access control** — any address can call it and force the `CallDispatcher` to execute arbitrary `to.call{value: ...}(data)` sequences. `CallDispatcher` is designed by protocol architecture to temporarily hold ETH and ERC-20 tokens (it even implements `receive() external payable {}` for that purpose) between phases of `IntentGatewayV2` order execution (predispatch/postdispatch, output-calldata sweep) and `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution flows. This is structurally identical to the `RollerPeriphery.approve` bug: a helper/periphery contract that is expected to only transiently hold value, but whose privileged-looking action is exposed with zero access control, letting anyone sweep out any balance left behind.

### Finding Description
`CallDispatcher.dispatch` has no caller restriction: [1](#0-0) 

Any account can call `dispatch` directly with an ABI-encoded `Call[]` whose `to` is any ERC-20 token and whose `data` is `IERC20.transfer(attacker, balance)` (or a native ETH transfer via `Call.value`), since the only guard is that `to` must have code (`extcodesize(to) != 0`) — this does not restrict which contract is targeted or what it does.

`CallDispatcher` is documented and used by the protocol precisely as a temporary holder of value:
- It receives ETH via `receive()` explicitly for calldata-execution flows. [2](#0-1) 
- `IntentGatewayV2`/`IntentsBase` transfer predispatch assets and output tokens into the dispatcher, invoke `ICallDispatcher(dispatcher).dispatch(...)`, and then sweep back the resulting/residual balances — meaning normal, expected operation regularly leaves ETH/ERC-20 balances sitting in `CallDispatcher` between the transfer-in and sweep-back steps, or as leftover "dust" if a sweep call misses a token or reverts partway. [3](#0-2) [4](#0-3) 
- The docs explicitly acknowledge the dispatcher "holds tokens temporarily during execution" and "can hold and forward native tokens," and describe minting/transferring bridged tokens directly to the `CallDispatcher` address for swap-then-settle patterns. [5](#0-4) [6](#0-5) 

Because `dispatch` is permissionless, any window where `CallDispatcher` transiently or accidentally holds funds — mid-flow value between transfer-in and sweep-back, a stuck token from a partially-failed multi-token sweep, tokens sent by an integrator who (per the docs) points a bridge `to` address at `CALL_DISPATCHER`, or simple user error sending tokens/ETH to the address — is directly and immediately stealable by any unprivileged caller.

### Impact Explanation
Unlike `RollerPeriphery` in the original report (a niche periphery contract), `CallDispatcher` is a core, shared, protocol-referenced contract wired into `IntentGatewayV2` order settlement and the `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution path across chains. Any ETH or ERC-20 balance it holds at any point — even transiently mid-transaction from a reentrant/atomic perspective is not exploitable within the same tx, but any balance surviving to the end of a transaction (leftover dust from partial sweeps, native ETH dust from rounding, tokens sent by mistake, or tokens deliberately routed `to = CALL_DISPATCHER` per the documented pattern) is permanently and trivially stealable by a front-running or opportunistic third party calling `dispatch` directly. This is a direct theft-of-funds vector against a shared, high-value protocol contract, not merely a low-value periphery helper.

### Likelihood Explanation
High. No special conditions, proofs, or privileged access are required — a single unprivileged transaction calling `CallDispatcher.dispatch()` with an ERC-20 `transfer` or native-value call is sufficient. Any dust or leftover balance that appears in `CallDispatcher` (via the documented usage patterns above, ordinary sweep failures, or accidental sends) is immediately exploitable by any observer monitoring the chain for a non-zero balance on the `CallDispatcher` address.

### Recommendation
Restrict `dispatch` to only be callable by the trusted caller(s) that are supposed to route calls through it (e.g., `IntentGatewayV2`/`HyperFungibleToken`/`WrappedHyperFungibleToken` contracts), for example via an `onlyAuthorizedCaller` modifier set at construction/configuration, or make `CallDispatcher` a single-use/ephemeral contract deployed per call. Additionally, add an owner/governance-gated sweep function so any accidental leftover balance can be recovered safely rather than being left as `dispatch`-callable bait for any address.

### Proof of Concept
1. Some ETH or ERC-20 balance ends up in the `CallDispatcher` contract (e.g., residual dust from a partial output sweep in `IntentsBase._execute`, or a token deliberately/accidentally sent to the dispatcher address as the docs' pattern of setting bridge `to = CALL_DISPATCHER` suggests, or via `receive()` accepting stray ETH).
2. Attacker (any address, no special role) constructs `Call[] calls = [Call({ to: <token>, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance) })]` (or, for ETH, `Call({ to: attacker, value: address(dispatcher).balance, data: "" })`).
3. Attacker calls `CallDispatcher.dispatch(abi.encode(calls))` directly — no authentication check exists in: [7](#0-6) 
4. The call succeeds since the only validation is that `to` has code; the token/ETH balance is transferred to the attacker.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
