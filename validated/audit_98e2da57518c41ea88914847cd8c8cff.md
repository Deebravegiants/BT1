### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` validates a webhook's authenticity using an HMAC computed only over the raw request body, but the `shop` (tenant) identifier used to dispatch the event to application handlers is read from an HTTP header that is completely outside that signed content. Any unprivileged party who can obtain one valid `(body, hmac)` pair signed with the app's shared secret can replay it with an arbitrary `shop-domain` header and have the webhook attributed to a different, victim tenant.

### Finding Description
`Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

and `Registry.process` validates the request purely against that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac-sha256` header value: [3](#0-2) 

However, the tenant-identifying `shop` value dispatched to the application's handler comes from the unsigned `shop-domain` header, not from the signed payload: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop-domain header == shop covered by HMAC`. Because the HMAC only covers `@raw_body`, this equality is never checked — the `shop` field is acted upon (passed straight into `WebhookMetadata` and to the host app's handler) but is not part of what's cryptographically verified.

### Impact Explanation
This breaks tenant isolation for any app using this gem's webhook processing. An attacker who legitimately installs the app on their own (attacker-controlled) shop will receive genuine webhooks whose bodies are HMAC-signed with the app's real `client_secret` (known only to Shopify/the app, not to the attacker — but the attacker doesn't need the secret, they just need one valid signed body). The attacker can then replay that exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header to name a victim shop. `Utils::HmacValidator.validate` will still pass because the header is not part of the signed content, and `Registry.process` will hand the forged event to the handler tagged with the victim's shop, e.g. triggering `shop/redact`, `customers/redact`, `app/uninstalled`, or any subscribed business-logic webhook against a tenant the attacker does not control. This is a cross-tenant identity-binding bypass (Critical: cross-tenant access via the app's own webhook trust boundary).

### Likelihood Explanation
Likelihood is high for any app that (a) allows self-serve installs (so an attacker can become a legitimate, if low-privileged, tenant and harvest a valid signed webhook), and (b) has any webhook topic whose body is shop-independent or attacker-influenceable (e.g., `app/uninstalled`, `shop/redact`, or topics with attacker-controlled content such as order/product webhooks the attacker triggers on their own shop). No credentials, tokens, or the `api_secret_key` are needed by the attacker — only the ability to capture one legitimate webhook delivery from their own store and resend it with a different header value.

### Recommendation
Bind the `shop` identity into the signed material that `Utils::HmacValidator` verifies, or otherwise cryptographically tie the `shop-domain` header to the request before trusting it — e.g., require the host application to independently confirm that the shop asserted by the header actually owns/matches an active, previously established session/subscription for that specific webhook, rather than trusting the header value merely because the body's HMAC matches. At minimum, document prominently that `Request#shop` is unauthenticated and must not be used as a sole tenant-routing key without additional verification (such as looking up the topic+webhook_id combination against Shopify's API for that specific shop before processing).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g. `app/uninstalled`, which typically has an empty/minimal body).
2. Shopify delivers a legitimate webhook to the app: body `{}` (or fixed content), header `X-Shopify-Hmac-Sha256: <hmac of "{}" with app's client_secret>`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this exact HTTP request.
4. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over the (unchanged) raw body and succeeds, per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`.
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...)`, causing the host application to process an attacker-forged event as if it originated from the victim tenant.
