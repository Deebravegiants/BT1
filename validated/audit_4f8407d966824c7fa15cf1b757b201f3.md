### Title
Simplex venue-priced legs quote pool mid without fee tier or size impact, and the overfill clamp is disabled — an intent submitter can drain a solver's funds - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The Saddle Finance postmortem describes a forked StableSwap AMM whose pricing math diverged subtly from the audited reference, letting arbitrageurs extract ~$275K from early liquidity providers within minutes of launch because the quoted price didn't reflect true execution cost/slippage. The closest reachable analog in this codebase is Hyperbridge's Simplex intent-filler: for curve-less ("venue-priced") pairs it prices legs directly off a Uniswap V4 pool's raw mid (`sqrtPriceX96`) with no fee-tier deduction and no size/impact term, and separately the per-leg overfill clamp that used to bound the filler's loss has been intentionally disabled (fills the full unclamped amount with only a warning log). Together these let an unprivileged intent submitter construct an order against a thinly-configured venue-priced pair that gets filled at a price worse than the pool's real, fee-inclusive execution price, extracting value from the solver's on-chain funds analogous to how Saddle's mis-derived invariant let arbitrageurs extract value from LPs.

### Finding Description
Venue-based pricing is documented and implemented as follows: [1](#0-0) 

`computeDirectPoolPriceUsd` derives the USD price straight from the pool's `token0Price`/`token1Price` (raw `sqrtPriceX96` mid): [2](#0-1) 

`resolveLegRates` uses this venue quote directly as the fill rate for the leg, gated only by `checkPriceGuard` (a static-reference deviation check, not an execution-cost check): [3](#0-2) 

`computeLegPolicyOutput` then extends this single mid price *linearly* across the entire quantity being filled — there is no square-root-invariant / concentrated-liquidity slippage curve applied, unlike a real swap through the pool: [4](#0-3) 

Separately, and compounding the exposure, the per-leg overfill protection that used to cap payout at `(1 + maxOverfillBps) × user-requested` has been deliberately disabled — the code computes the ceiling, logs a warning if it's exceeded, but pays out the full unclamped amount regardless: [5](#0-4) 

The design decision doc explicitly acknowledges this trade-off was left unresolved: "the clamp at the overfill-ceiling block is still a no-op assignment... Restoring the payout makes that ceiling meaningful again and it should be either re-armed or deleted outright": [6](#0-5) 

The fee tier is captured on the hydrated position but never applied to the quoted price, and there is no size-impact term — exactly the flow doc's own diagnosis: "A venue-priced pair that has to swap through its own pool to source inventory pays a fee tier it never quoted against."

This mirrors the Saddle Finance root cause: a pricing surface that departs from the true execution-cost curve of the underlying invariant (Curve's StableSwap in Saddle's case; Uniswap V4's concentrated-liquidity curve here), with no slippage/impact protection, letting anyone submitting a transaction (here, an intent order) capture the difference between the quoted price and the real cost.

### Impact Explanation
On the `IntentGatewayV2`/`IntrinsicIntents.sol` escrow, the solver's `fillOrder()` output is paid from the solver's own wallet/vault, and any solver-provided output above the user-requested amount is *not* refunded — it's split via `_splitSurplus` between the beneficiary and protocol dust: [7](#0-6) 

Because Simplex's own overfill clamp is a documented no-op, and the venue price feeding `computeLegPolicyOutput` ignores both the pool's fee tier and size impact, a solver operating this pricing strategy pays out more than the pool would actually yield if the solver has to source inventory by swapping through that same pool (as `UniswapV4FundingPlanner` does to fund a shortfall). Under adverse or thin-liquidity pool conditions, or a series of orders sized to walk the pool price, the solver's on-chain treasury/vault suffers real, uncapped loss with no automated stop — directly analogous to the LP fund loss in the Saddle exploit. This is a Medium-severity fund-loss vector reachable by any ordinary intent submitter (no special privilege required), though the magnitude depends on the operator's configured pool depth and `spreadBps`.

### Likelihood Explanation
Likelihood is moderate: it requires an operator to have configured a curve-less, venue-priced pair (`[vault.uniswapV4]` with no `bidPriceCurve`/`askPriceCurve`), and it requires either thin/movable pool liquidity or repeated orders large enough for the linear-mid pricing and missing fee-tier deduction to diverge meaningfully from the pool's real execution price. Documentation explicitly recommends `referencePrice`/`maxDeviationBps` guards, but these only catch gross price manipulation relative to a static reference — not the structural fee-tier/size-impact gap or the disabled overfill clamp, both of which apply on every fill of a venue-priced pair regardless of manipulation.

### Recommendation
1. Re-arm (or intentionally and safely delete) the `maxOverfillBps` clamp in `sdk/packages/simplex/src/strategies/fx.ts` so a per-leg loss bound is enforced rather than only logged.
2. Apply the pool's actual fee tier (`pos.fee`) and a size/impact term (via the V4 SDK's real swap-quote math, not the raw mid) in `computeDirectPoolPriceUsd`/`computeLegPolicyOutput` when the solver expects to source inventory from that same pool.
3. Consider extending `checkPriceGuard` to bound execution cost (expected slippage for the quoted size) in addition to deviation from a static reference.

### Proof of Concept
1. Operator configures a curve-less USDC/EXOTIC pair funded by a Uniswap V4 position with moderate liquidity and no `referencePrice` guard (or one wide enough to not trip).
2. Attacker (any intent submitter) crafts an order (or a sequence of orders) sized so that: (a) the true pool execution cost including fee tier and price impact is materially worse than the pool's instantaneous mid, and (b) `output.amount` requested slightly exceeds the "fair" amount, relying on the disabled overfill clamp at `fx.ts:684-701` to guarantee the filler still pays the full unclamped `policyMaxOutput`.
3. Simplex's `resolveLegRates`/`computeLegPolicyOutput` price and pay the order at the raw pool mid, linearly extended, ignoring the fee tier the solver will actually pay when it later withdraws liquidity through `UniswapV4FundingPlanner` to cover the shortfall.
4. Repeated over multiple orders, the solver's on-chain vault/positions are drained by the fee-tier/impact gap plus the always-uncapped overfill, exactly mirroring the arbitrage extraction pattern in the Saddle Finance rekt report.

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

	private computeLegPolicyOutput(
		inputAmount: bigint,
		inputIsToken0: boolean,
		token0Decimals: number,
		token1Decimals: number,
		/**
		 * Token0 left in the pair's per-order exposure budget, or `null` to price the whole
		 * input unbudgeted. Only a price probe passes `null`: it commits no capital, so there
		 * is no exposure to ration, and a clamped quantity would silently misprice it.
		 */
		remainingToken0: Decimal | null,
		rate: Decimal,
	): { token0Used: Decimal; policyMaxOutput: bigint } | null {
		let legMaxToken0: Decimal
		if (inputIsToken0) {
			legMaxToken0 = new Decimal(formatUnits(inputAmount, token0Decimals))
		} else {
			legMaxToken0 = new Decimal(formatUnits(inputAmount, token1Decimals)).div(rate)
		}

		const token0ForLeg = remainingToken0 === null ? legMaxToken0 : Decimal.min(legMaxToken0, remainingToken0)
		if (token0ForLeg.lte(0)) {
			return null
		}

		let policyMaxOutput: bigint
		if (inputIsToken0) {
			// Output is token1: convert the token0 allocation at the pair rate.
			policyMaxOutput = BigInt(
				token0ForLeg.mul(rate).mul(new Decimal(10).pow(token1Decimals)).floor().toFixed(0),
			)
		} else {
			// Output is token0: pay out the token0 equivalent of the token1 input.
			policyMaxOutput = BigInt(token0ForLeg.mul(new Decimal(10).pow(token0Decimals)).floor().toFixed(0))
		}

		return { token0Used: token0ForLeg, policyMaxOutput }
	}

	private async resolveLegRates(
		orderId: string | undefined,
		leg: ResolvedLeg,
		cappedPairNotional: Decimal,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<LegRates | null> {
		// Explicitly configured curves always win — the venue only prices pairs
		// with no curves at all (and never same-token pairs, where a venue quote
		// would just be the asset's own USD price, not a spread).
		const curveless = !leg.pair.bidPricePolicy && !leg.pair.askPricePolicy
		if (curveless && !isSameTokenPair(leg.pair) && USD_STABLE_SYMBOLS.has(normalizeSymbol(leg.pair.token0))) {
			const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
			if (venueUsd) {
				// Guard compares the venue's token1-per-USD quote against the static reference.
				if (!this.checkPriceGuard(orderId, leg.token1Chain, new Decimal(1).div(venueUsd))) {
					return null
				}
				// A pool mid is ONE price, not a book: there is no opposite side
				// to report a round-trip margin against. The price guard above is
				// the venue-specific defense.
				const venueRate = new Decimal(1).div(venueUsd)
				return { rate: venueRate, oppositeRate: null, priceSource: "venue" }
			}
