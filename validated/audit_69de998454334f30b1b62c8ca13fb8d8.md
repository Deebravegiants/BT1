### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` validates a webhook by computing an HMAC over the raw request body only, while the `shop` (tenant identity) used by the handler is read from an HTTP header that is never included in that signature.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` accepts a webhook only if `Utils::HmacValidator.validate(request)` succeeds: [1](#0-0) 

`HmacValidator.validate` verifies the signature against `verifiable_query.to_signable_string`: [2](#0-1) 

For a webhook `Request`, `to_signable_string` is defined as just the raw body: [3](#0-2) 

But the tenant identity (`shop`) that the handler receives is pulled straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is **not** part of the signed material: [4](#0-3) [5](#0-4) 

This unauthenticated `shop` value is then handed to the app's handler as the tenant identity for the event: [6](#0-5) 

The binding that should hold is: `shop-domain header == shop covered by hmac`. In reality: `hmac covers only raw_body`, so `shop-domain header ∉ signed-bytes`. Because the HMAC secret (`api_secret_key`) is shared across all shops that install the same app, any unprivileged user who installs the app on their own store receives genuine, correctly-signed webhook deliveries for events they can trigger themselves (e.g. `orders/create`, `customers/create` with attacker-supplied content in the body). That attacker can capture the raw body + valid `hmac-sha256` header from their own webhook, then replay the identical body/HMAC pair to the app's webhook endpoint while substituting a different `shop-domain` header value (any other merchant's `myshopify.com` domain). `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` dispatches the handler with the attacker-chosen `shop`.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): the application's webhook handler will process attacker-controlled data believing it originates from a victim shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up/creating records keyed by shop, triggering GDPR data-erasure for `shop/redact`-style flows, or driving business logic scoped to "the shop the event is about"), this lets an unprivileged attacker inject or corrupt data attributed to another merchant's tenant, or trigger actions (such as data deletion in mandatory compliance webhooks) against a shop they do not own.

### Likelihood Explanation
Any actor can install a public/dev app on their own store to legitimately obtain real, correctly-signed webhook bodies and HMAC values, since the signing key is per-app, not per-shop. Forging the `shop-domain` header on a replayed request requires no secret knowledge — only crafting an HTTP request with a modified header, which is trivial for anyone who can send HTTP requests to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the material that is actually verified. Either (a) include the `shop-domain` (and ideally `topic`/`webhook-id`) header value inside the string that is HMAC-verified, deriving `shop` only from data that participated in the signature, or (b) require host applications to cross-check `request.shop` against an already-known/authenticated shop record (e.g. an existing session for that shop) before trusting it, and document this requirement prominently since the gem currently does not enforce it.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with a body of their choosing.
2. Attacker captures the raw POST body and the `X-Shopify-Hmac-Sha256` header from that genuine delivery — both are valid because `to_signable_string` only covers the raw body.
3. Attacker resends the exact same raw body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (in `lib/shopify_api/utils/hmac_validator.rb`) succeeds because the body is unchanged; `Registry.process` (in `lib/shopify_api/webhooks/registry.rb`) invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though nothing about `victim-shop.myshopify.com` was ever verified.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
