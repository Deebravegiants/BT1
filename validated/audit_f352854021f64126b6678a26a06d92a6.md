Confirmed: the Tron variant of `IntentGatewayV2::placeOrder` credits escrow based on the *requested* input amount rather than the amount actually received by the contract, unlike the fixed main EVM version.

### Title
Fee-on-transfer / deflationary tokens cause escrow over-crediting and permanent fund freezing in Tron `IntentGatewayV2::placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron deployment of `IntentGatewayV2.sol`, the non-predispatch branch of `placeOrder` calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived from the user-specified `order.inputs[i].amount`, not from the actual balance change of the contract. [1](#0-0)  If the input token charges a transfer fee (fee-on-transfer/deflationary token) or otherwise delivers less than the requested amount, the gateway's real token balance will be less than the sum of `_orders[...]` claims recorded against it.

### Finding Description
The main EVM `IntentGatewayV2.sol::placeOrder` was hardened specifically against this class of bug: it snapshots `balanceOf(address(this))` before and after `safeTransferFrom`, and overwrites `order.inputs[i].amount` with the actual delta received before it is used to compute the commitment and the escrowed amount. [2](#0-1)  This logic is explicitly documented as "Phase 1: Transfer tokens and record actual received amounts. For fee-on-transfer tokens, the gateway receives less than the requested amount." [3](#0-2)  The fix is also validated by dedicated tests such as `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` and `testPlaceAndFill_FeeOnTransferToken_RoundTrip`. [4](#0-3) 

The Tron variant of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`), however, was not updated with this protection. In its non-predispatch escrow branch, it simply calls `safeTransferFrom` for `order.inputs[i].amount` and unconditionally adds `reducedInputs[i].amount` (a value computed purely from the caller-supplied `order.inputs[i].amount`, minus protocol fee) to the escrow accounting, without ever checking the contract's actual token balance delta. [1](#0-0)  The predispatch branch has a partial balance check (`if (balance < requiredAmount) revert`) for the dispatcher-side balance, but it forwards the entire dispatcher balance to the gateway via a second `transfer` call whose actual received amount on the gateway side is never re-measured either, so a second fee hit on that final transfer also goes unaccounted. [5](#0-4) 

Later, `withdraw()` pays out `body.tokens[i].amount` (the recorded escrow claim) via a raw `token.call(transfer, beneficiary, amount)`, decrementing `_orders[body.commitment][token] -= amount` without verifying the gateway actually holds that balance. [6](#0-5) 

### Impact Explanation
Any user can `placeOrder` with a fee-on-transfer or deflationary ERC20 as an input, causing `_orders[commitment][token]` to be credited for more than the tokens actually held by the gateway. When the solver later redeems escrow (RedeemEscrow) or the user cancels/refunds (RefundEscrow) via `onAccept` → `withdraw`, the contract will attempt to transfer out an amount exceeding its real balance. Because multiple orders/commitments share the same token's pooled balance in the contract, this creates an insolvency: whichever claim is processed last for that token can fail to be paid (transfer reverts due to insufficient contract balance, causing `TransferFailed`), permanently freezing funds and/or causing legitimate earlier claims to consume balance that rightfully belongs to other orders. This matches a concrete permanent freezing-of-funds impact reachable by an ordinary, unprivileged user submitting `placeOrder` with such a token — no special privileges required.

### Likelihood Explanation
Likelihood is moderate: it requires the deployer/governance to permit a fee-on-transfer or "transfer-less-than-amount" token (e.g., cUSDCv3-like tokens, tokens with burn/tax mechanics) as a valid input asset for the gateway, which is plausible on Tron given TRC-20 tokens include several deflationary/fee tokens. Given that the maintainers already identified and fixed this exact issue on the main EVM `IntentGatewayV2.sol` contract (with tests specifically for fee-on-transfer tokens), it demonstrates this is a recognized, realistic threat model for this codebase, and the parity gap in the Tron variant is a straightforward oversight rather than a purely theoretical concern.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` (and after the dispatcher-to-gateway sweep in the predispatch branch), and use that actual delta — not the caller-supplied `order.inputs[i].amount` — both for computing `reducedInputs`/the commitment hash and for the amount credited to `_orders[commitment][token]`.

### Proof of Concept
1. Deploy a fee-on-transfer TRC-20 token (e.g., 1% fee) and mint balance to `user`.
2. `user` calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000e18}`; `user` approves `1000e18`.
3. Inside `placeOrder`, `safeTransferFrom(user, address(this), 1000e18)` executes, but the gateway's real balance only increases by `990e18` (1% fee burned/retained).
4. `_orders[commitment][FOT] += reducedInputs[0].amount` credits (approximately) `1000e18` (minus any protocol fee), i.e., more than the `990e18` actually held.
5. When the order is later filled cross-chain and `onAccept`/`withdraw` is invoked to pay the solver/beneficiary `1000e18` (or whatever was recorded), the raw `token.call(transfer, beneficiary, amount)` either fails outright (insufficient balance) reverting the withdrawal (permanent freeze), or succeeds by draining balance escrowed for other unrelated commitments on the same token, causing those other legitimate claims to subsequently fail. This is the same shortfall behavior already regression-tested against on the main EVM side, e.g. `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, but absent here. [4](#0-3)

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
