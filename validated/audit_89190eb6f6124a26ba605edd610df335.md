### Title
Webhook shop/topic attribution is not covered by the HMAC, allowing tenant spoofing via signed-body replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook-id`, and `api-version` fields consumed by the application come exclusively from unauthenticated HTTP headers. `Registry.process` verifies the body's HMAC and then trusts those header-derived fields to route the payload to a handler and identify the tenant. Because the signature never binds the shop/topic identity to the body, a valid (secret-signed) body from one installation can be replayed with a different `shop` header to make the app attribute that data to another tenant.

### Finding Description
`Request#hmac` and `Request#to_signable_string` derive the HMAC subject strictly from `@raw_body`: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `to_signable_string` (the raw body), never touching the shop header: [4](#0-3) 

`Registry.process` validates that body HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the data delivered to the handler: [5](#0-4) 

The equality the gem needs to guarantee is: `hmac_valid(raw_body) ⇒ shop_header == shop_that_produced(raw_body)`. In fact `hmac_valid(raw_body)` only proves the body bytes are authentic for *some* shop possessing the shared `client_secret`; it says nothing about which shop's header should accompany that body. Any merchant who has installed the app (an unprivileged actor with no special access) legitimately receives a correctly signed `(raw_body, hmac)` pair for their own shop. They can resend that identical pair to the app's public webhook endpoint while swapping `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to name a victim shop. `HmacValidator.validate` still passes because it never inspects the shop header, and `Registry.process` calls the handler with `shop: request.shop` set to the victim's domain — a cross-tenant identity binding break carried entirely through this gem's own webhook-processing code.

### Impact Explanation
This breaks the tenant (shop) identity binding that host applications rely on `ShopifyAPI::Webhooks::Registry.process`/`Request` to enforce: data that is only proven authentic for shop A can be delivered to the handler labeled as belonging to shop B. Any host application that keys business logic (e.g., which merchant's order/customer record to update) off `WebhookMetadata#shop` without independently re-verifying it is exposed to cross-tenant data confusion — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any internet user can install the target app on their own free/dev shop, which is unprivileged and requires no leaked credentials, TLS interception, or `api_secret_key`. They then only need to capture and replay their own legitimately delivered webhook HTTP request with a modified shop-domain header against the app's public webhook endpoint — a straightforward, repeatable action fully within this gem's documented processing flow (`Registry.process` / `Request.new`), not dependent on the host app ignoring documented behavior.

### Recommendation
Bind the shop (and ideally topic/webhook-id) identity into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived identity to the signed payload before it is passed to handlers. Concretely, extend `Request#to_signable_string` (or add a secondary check in `Registry.process`) to incorporate `shop`, `topic`, and `webhook_id` alongside the raw body so `HmacValidator.validate` fails if any of those headers are altered relative to what was actually signed by Shopify for that delivery.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: `{"id": 123, ...}` (order belonging to attacker's own shop)
2. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `@raw_body` [2](#0-1) .
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)` [5](#0-4) , causing the host application to process/store attacker-controlled data under the victim shop's identity.
