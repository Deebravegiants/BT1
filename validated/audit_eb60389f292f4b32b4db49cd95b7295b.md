### Title
Webhook shop identity is not covered by HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC that covers only the raw request body, then trusts the `shop-domain` header — which is *not* covered by that HMAC — as the tenant identity passed to the app's handler. Any holder of one validly-signed webhook body (e.g., an attacker who owns their own shop and receives legitimate webhooks from the shared app) can replay that body with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop, and the signature check still passes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate header that is never part of the signed material: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e. the body), and compares it against the `hmac-sha256` header value: [3](#0-2) 

`Registry.process` uses this single check as the sole authentication gate, then forwards the *unauthenticated* `request.shop` value straight into the handler as the tenant identity: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop acted upon by the handler`

Here, the HMAC only authenticates `(topic, body)` — it says nothing about which shop the payload belongs to. Because a single `api_secret_key` (the app's client secret) is shared across *every* shop that installs the app, any merchant/unprivileged actor who installs the app can:
1. Trigger or receive a legitimate webhook for their own shop, capturing a valid `(raw_body, hmac-sha256)` pair signed with the app's shared secret.
2. Replay that exact body/HMAC pair to the app's webhook endpoint, but substitute `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) with a victim shop's domain.
3. `HmacValidator.validate` still succeeds (it never inspected the header), and `Registry.process` calls `handler.handle` with `shop: request.shop` set to the attacker-chosen victim domain.

This breaks the tenant boundary the host application relies on to route/authorize per-shop data updates driven by webhook events.

### Impact Explanation
This is a cross-tenant identity confusion: the gem hands the host application a shop identity that was never bound to the cryptographic proof of authenticity. Any application that keys webhook side effects (e.g., updating billing status, revoking access, syncing order/customer data, deleting records) off `WebhookMetadata#shop` as produced by this library can be made to apply another tenant's webhook payload to an arbitrary victim shop, or vice versa. This matches the Critical "cross-tenant access" impact category, since it requires no access token, no leaked credential, and no privileged account — only that the attacker has installed the app on their own shop (the normal, unprivileged path).

### Likelihood Explanation
The attacker only needs: (a) to install the app on a shop they control (freely obtainable, no special privilege), (b) to receive at least one real webhook for their own shop (guaranteed by the app's own operation), and (c) to be able to send an HTTP request to the app's public webhook endpoint with a modified header — all standard, low-effort steps for an unprivileged internet user with no need for `api_secret_key`, access tokens, or social engineering.

### Recommendation
- **Short term**: Include the shop identity (and topic/webhook-id) as part of the material verified against `hmac-sha256`, or independently verify that the shop domain in the header matches the shop associated with the webhook subscription (e.g., cross-check against the session/store used to register the webhook) before invoking the handler.
- **Long term**: Treat `shop-domain`/`topic`/`webhook-id` headers as untrusted metadata until cryptographically bound to the payload; document this clearly for consumers of `ShopifyAPI::Webhooks::Registry.process`, and consider exposing a lower-level API that lets host apps supply their own out-of-band shop verification before dispatching to handlers.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and captures a legitimately-signed webhook body they received, e.g. body = '{"id":1}'
secret = ShopifyAPI::Context.api_secret_key # shared across all installs of this app
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, '{"id":1}')

forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: '{"id":1}', headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (body unchanged),
#    handler.handle receives shop: "victim-shop.myshopify.com"
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
