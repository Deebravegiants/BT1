**Analysis:**

The premise of concurrent access to the same `TransactionDataCache` instance doesn't hold given Aptos's execution model.

`TransactionDataCache::insert_resource` is only reachable via `MoveVmDataCacheAdapter::load_resource_mut`, which holds an exclusive `&'a mut TransactionDataCache` reference [1](#0-0) . Rust's borrow checker enforces that only one mutable reference to this cache can exist at a time, and the call path from `load_resource_mut` (check `contains_resource` → `create_data_cache_entry` → `insert_resource` → `get_resource_mut`) executes synchronously and sequentially within a single Move VM interpreter call stack [2](#0-1) . There is no code path that spawns threads or async tasks to execute two `load_resource_mut` calls concurrently against the same `TransactionDataCache`.

More broadly, `TransactionDataCache` is a per-transaction, single-threaded structure ("Keep updates within a transaction so they can all be published at once when the transaction succeeds") [3](#0-2) . Aptos's parallel execution engine (Block-STM) achieves concurrency across different transactions, not within the execution of a single transaction's VM interpreter loop — each transaction gets its own isolated `TransactionDataCache` instance, and results are validated/committed to the shared MVHashMap only after execution, outside the scope of this file. So two concurrent "loads" of the same `(address, type)` pair for the same code object would only occur across different transactions, each operating on its own separate cache instance, meaning `insert_resource`'s `Entry::Occupied` branch guards against double-insertion within a single transaction's execution, not against cross-transaction races (which are handled elsewhere by Block-STM's conflict detection/re-execution machinery).

Additionally, even hypothetically, the `Entry::Occupied` error path in `insert_resource` (lines 394-399) is not silently swallowed — it returns a `PartialVMError` with `UNKNOWN_INVARIANT_VIOLATION_ERROR`, which propagates up through `load_resource_mut`'s `?` operator [4](#0-3)  and aborts the transaction rather than allowing silent state desynchronization.

Since no real concurrent-mutation scenario exists against a shared `TransactionDataCache` from unprivileged input, and the error path properly aborts rather than being swallowed, this does not cross a custody boundary or corrupt code-object ownership/upgrade authority.

            Some(bytes_loaded)
