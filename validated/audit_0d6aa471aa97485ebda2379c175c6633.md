Audit Report

## Title
Nil pointer dereference in `vault.publicKey.get` handling crashes the node - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` routes `vaulttypes.MethodPublicKeyGet` requests directly to `handlePublicKeyGet` without going through the `requestProcessor.ProcessRequest` validation pipeline used by every other vault method, and `handlePublicKeyGet` unconditionally dereferences `*req.Params` with no nil check. A crafted `vault.publicKey.get` JSON-RPC message with a missing `params` field triggers a nil pointer dereference panic in the node's Gateway connector `readLoop` goroutine, which has no `recover()`, crashing the entire node process.

## Finding Description
In `core/capabilities/vault/gw_handler.go`, the switch statement in `HandleGatewayMessage` sends `MethodSecretsCreate/Update/Delete/List` through `h.requestProcessor.ProcessRequest`, while `MethodPublicKeyGet` bypasses this pipeline entirely and calls `h.handlePublicKeyGet(ctx, gatewayID, req)` directly: [1](#0-0) 

`handlePublicKeyGet` unmarshals `*req.Params` with no nil guard: [2](#0-1) 

By contrast, `GatewayVaultRequestProcessor`'s handlers for create/update/delete/list all explicitly check `req.Params == nil` before dereferencing and return `InvalidVaultParamsError` instead of panicking: [3](#0-2) 
This confirms nil `Params` is an expected, reachable condition that the codebase elsewhere guards against — but `handlePublicKeyGet` is the one handler that skips this check entirely, since it never enters `ProcessRequest`.

The message reaches this code via `gatewayConnector.readLoop`, which decodes the raw JSON-RPC envelope from the Gateway and dispatches it to the registered handler with no panic recovery: [4](#0-3) 
No `recover()` exists anywhere in the connector package, so a panic here is unrecovered and crashes the entire node process (Go semantics: an unrecovered panic in any goroutine terminates the whole program).

Searching `core/capabilities/vault/gw_handler_test.go` for `PublicKeyGet`/`handlePublicKeyGet` coverage returns no matches, confirming there is no existing test validating nil-params behavior for this specific method (unlike the well-tested nil-params rejection path for `MethodSecretsCreate` visible in `core/services/gateway/handlers/vault/handler_test.go`'s `TestVaultHandler_PreAuthValidationSkipsAuthorization`, which is a different, gateway-side handler package, not the node-side `GatewayHandler` under review).

Tracing back further, `MethodPublicKeyGet` is explicitly designed to skip authorization (`authResult` stays `nil` and `ProcessRequest` is never invoked for this method), so no allowlist entry or JWT is required to reach `handlePublicKeyGet`.

## Impact Explanation
A crafted, unauthenticated JSON-RPC request (`{"jsonrpc":"2.0","id":"1","method":"vault.publicKey.get"}` with no `params`) reaching the node's Gateway connector causes a nil pointer dereference panic that is not recovered anywhere in the call path, crashing the entire Chainlink node process. This is a denial-of-service vulnerability triggerable by any client capable of reaching the Gateway's endpoint that forwards to the vault DON, with no privilege or credential requirement — this matches the described CVE bug class of a NULL-pointer-dereference crash from crafted input in a message-parsing routine.

## Likelihood Explanation
The trigger requires only sending a single JSON-RPC request with method `vault.publicKey.get` and an absent/null `params` field. `MethodPublicKeyGet` is intentionally exempted from `ProcessRequest`'s authorization/validation gate, so this can be sent by any unprivileged caller able to reach the Gateway's public request path, making the attack trivially and repeatably executable.

## Recommendation
Add an explicit `req.Params == nil` check at the top of `handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go`, returning an `api.UserMessageParseError`/`InvalidParamsError` response instead of dereferencing, mirroring the pattern already used in `gateway_vault_request_processor.go`. As defense-in-depth, wrap the handler invocation in `gatewayConnector.readLoop` (`core/services/gateway/connector/connector.go`) with a `recover()` so a panic in any single handler cannot take down the whole node process.

## Proof of Concept
1. Configure a node with the Vault capability's `GatewayHandler` registered on a `gatewayConnector`.
2. From the Gateway side (or a test harness simulating `gatewayState.conn.ReadChannel()`), send the bytes for:
   ```json
   {"jsonrpc":"2.0","id":"1","method":"vault.publicKey.get"}
   ```
3. `readLoop` unmarshals this into `jsonrpc.Request[json.RawMessage]{Method: "vault.publicKey.get", Params: nil}` and dispatches to `GatewayHandler.HandleGatewayMessage`.
4. Execution reaches `handlePublicKeyGet`, which executes `json.Unmarshal(*req.Params, r)` with `req.Params == nil`, panicking with a nil pointer dereference inside the `readLoop` goroutine, crashing the node process since no `recover()` exists in the call chain. [5](#0-4) [6](#0-5) 

A Go unit test can directly call `GatewayHandler.HandleGatewayMessage` (or `handlePublicKeyGet`) with a `req` whose `Params` field is `nil` and method `vaulttypes.MethodPublicKeyGet` to reproduce the panic deterministically, analogous to the existing `TestGatewayVaultRequestProcessor_ProcessRequest_RejectsNilParams` test pattern but demonstrating the missing guard for this specific method.

```go
func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
```
