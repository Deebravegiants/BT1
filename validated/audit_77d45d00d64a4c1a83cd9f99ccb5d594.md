### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC over the raw request body only, then hands the handler a `shop` value that is read from an HTTP header that is not part of that signature. This breaks the identity binding `shop_authenticated == shop_acted_on`: the signature proves the *body* came from someone holding the app's `client_secret`, but it proves nothing about which shop the body belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never fed into the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` directly from `request.shop`, i.e. from the unsigned header, and dispatches it to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no further verification against the signed payload: [4](#0-3) 

The HMAC is computed with a single shared secret (`Context.api_secret_key`, the app's `client_secret`), the same for every merchant that installs the app: [5](#0-4) 

Consequently, `validate_signature` only proves "this body was signed with this app's secret" — it never proves "this body belongs to shop X." Any party who can obtain one valid `(raw_body, hmac)` pair for the app (e.g. a merchant who installs the app themselves and receives their own legitimate webhooks) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a different (victim) shop's domain. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will invoke the handler with `shop: <victim-shop>` even though the payload content actually originated from the attacker's own shop. This is the exact bug-class named in the rules: "a field acted on (`shop`) but not covered by the HMAC."

### Impact Explanation
This meets the High-severity bar of "cross-tenant access" via forged/faked webhook identity: an app that keys any per-tenant state, authorization decision, or data write off `WebhookMetadata#shop` (as recommended in the gem's own webhook usage docs, which pass `shop_session` derived from the topic/shop pairing) can be made to process or store data under an incorrect tenant, or to trigger tenant-scoped side effects (e.g. re-triggering billing/actions, injecting data into another merchant's records) using only a legitimately-signed webhook that the attacker's own shop received. It does not require the app's `client_secret`, an access token, or TLS interception — only possession of one webhook the attacker's own shop legitimately receives, plus the ability to send an HTTP request with attacker-controlled headers to the app's public webhook endpoint.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment: any merchant who installs the app is, by design, able to receive real webhooks for their own shop (this requires no special privilege beyond ordinary app installation). Capturing one's own webhook payload/HMAC and replaying it with a different `shop-domain` header is a trivial HTTP-level manipulation requiring no cryptographic capability, since only the body is protected. The main variable is whether the host application uses `WebhookMetadata#shop` for authorization/tenant-scoping without independent cross-checks — which is the intended and documented usage pattern shown in the gem's own webhook docs.

### Recommendation
Bind the shop identity into the authenticated material, not just the body:
- Compute/validate the HMAC over a canonical string that includes the `shop-domain` (and ideally `topic`, `webhook-id`) header value, not the raw body alone, so that tampering with the shop header invalidates the signature.
- Alternatively/additionally, cross-check `request.shop` against an independently known, already-authenticated per-shop record (e.g. the shop associated with the `webhook_id` via a prior registration, or a session store keyed by shop) before dispatching to the handler.
- Document prominently that `WebhookMetadata#shop` is derived from an unauthenticated header and must not be trusted for tenant-scoping without additional verification, until the signature is fixed to cover it.

### Proof of Concept
1. App App-A is installed on both Shop-Attacker and Shop-Victim, sharing one `client_secret`.
2. Shop-Attacker triggers a webhook event on their own shop; Shopify sends the app a request such as:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-raw_body>
   x-shopify-shop-domain: shop-attacker.myshopify.com
   x-shopify-webhook-id: <id>
   {"id": 123, ...}   # raw_body
   ```
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (both are visible to them as the account owner of Shop-Attacker, e.g. via server logs, browser devtools on a webhook viewer, or simply by controlling the receiving endpoint if they self-host a proxy).
4. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256`, but sets:
   ```
   x-shopify-shop-domain: shop-victim.myshopify.com
   ```
   to the app's public webhook endpoint.
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) succeeds because it only recomputes the HMAC over `raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`).
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches `WebhookMetadata.new(shop: "shop-victim.myshopify.com", body: <attacker's data>, ...)` to the app's handler, which now processes attacker-supplied data under the victim shop's identity.
