### Title
Predictable, unsigned offline/online session identifiers enable session fixation via cookie injection - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
The gem's session-cookie value is simply the plaintext session id (`"offline_#{shop}"` for offline sessions or `"#{shop}_#{user_id}"` for online sessions), and `SessionUtils.cookie_session_id` reads that same raw, unsigned cookie value back to select which stored session/access-token to activate. Because the identifier is fully deterministic from public data (the shop's `myshopify.com` domain) and carries no HMAC or other binding to the browser that legitimately completed OAuth, an attacker who can place this exact string into a victim's (or their own) `shopify_app_session` cookie can force the host application — following this gem's documented API exactly — to activate another merchant's session and use that merchant's access token on the attacker's behalf.

### Finding Description
When OAuth completes, `ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the session id from `Session.from`: [1](#0-0) 

For offline (store-level) sessions the id is always exactly `"offline_#{shop}"` — no random or secret component — and it is placed directly as the value of the `shopify_app_session` cookie: [2](#0-1) 

The cookie value is never signed or MAC'd; `SessionCookie` is a plain struct with `name`, `value`, `expires`: [3](#0-2) 

On subsequent requests, `SessionUtils.current_session_id` for non-embedded apps (and as a fallback for embedded apps) simply returns whatever raw string is present in that cookie, with no verification that it was ever produced by this gem's own OAuth flow for the current browser: [4](#0-3) [5](#0-4) 

The documented app pattern (per `docs/getting_started.md`) is to take this id and hand it to the app's `SessionRepository.find_session_by_id`/`retrieve` to load the stored `access_token` for that id and use it for authenticated API calls: [6](#0-5) 

The binding that should hold is: *the identity presented in the session cookie == the identity that actually completed HMAC/OAuth-verified authentication in that browser session*. Instead, the gem accepts `cookie_session_id(cookies) == cookies[SESSION_COOKIE_NAME]` unconditionally — bytes parsed, never bytes verified. Since offline ids are `"offline_<shop-domain>"` and shop domains are public, any attacker who knows a target's `myshopify.com` domain can construct the exact session id string for that shop's offline session without ever completing OAuth, without the `client_secret`, and without an access token.

### Impact Explanation
If an attacker can get this crafted string written into the `shopify_app_session` cookie of a session that a host app will subsequently look up (e.g., cookie injection through a shared parent domain, response-splitting, or any mechanism that lets a value be written into that specific cookie name), the host app — using only this gem's documented `SessionUtils.current_session_id` / `cookie_session_id` API exactly as intended — will retrieve and activate the target merchant's stored offline session, including its access token, for the attacker's request context. This is a session fixation vulnerability leading to cross-tenant use of another merchant's access token, matching the High-impact class "session fixation ... credential leakage."

### Likelihood Explanation
The offline session id has zero entropy beyond the shop domain, which is not secret (it's the store's own hostname). No cryptographic secret (`api_secret_key`, access token, etc.) is required to compute the target value — only knowledge of a target shop's domain, which is trivially discoverable. The remaining requirement (getting the crafted value into the relevant cookie) depends on delivery mechanics outside this gem, but the root defect — an identifier with no integrity binding being trusted verbatim by `cookie_session_id` — is entirely inside this library's code path.

### Recommendation
Do not use the raw, deterministic session id as the literal cookie value. Instead, HMAC-sign the cookie value (or store a random, unguessable token mapped server-side to the session id) using `Context.api_secret_key`, and have `SessionUtils.cookie_session_id` verify that signature/mapping before returning a session id to the caller, mirroring the existing `Utils::HmacValidator` pattern already used for the OAuth callback.

### Proof of Concept
1. App A installs the target shop `victim-shop.myshopify.com` as an offline (non-embedded) installation; per `Session.from`, the resulting session id is deterministically `offline_victim-shop.myshopify.com` (`lib/shopify_api/auth/session.rb:116`), and this exact string is written unsigned into the `shopify_app_session` cookie (`lib/shopify_api/auth/oauth.rb:106-109`).
2. An attacker, knowing only the public shop domain `victim-shop.myshopify.com`, sets their own `shopify_app_session` cookie to the value `offline_victim-shop.myshopify.com` (via any cookie-injection vector reachable in the host's cookie scope).
3. The attacker calls the host app's authenticated endpoint. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `cookie_session_id(cookies)` unmodified — i.e., the attacker-supplied string — with no signature check (`lib/shopify_api/utils/session_utils.rb:19-37,68-71`).
4. The host app looks up its session repository by that id and finds/reuses `victim-shop`'s stored offline session (including its access token), then makes Shopify API calls in that session on the attacker's behalf.

```markdown
### Sessions

Sessions are required to make requests with the REST or GraphQL clients. This Library provides helpers for creating sessions via OAuth. Helpers are provided to retrieve session ID from a HTTP request from an embedded Shopify app or cookies from non-embedded apps.

Session persistence is handled by the [ShopifyApp](https://github.com/Shopify/shopify_app) gem and is recommended for use in the Rails context. See that gem for documentation on how to use it.

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
```
