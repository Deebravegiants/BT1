Unauthenticated `superApprove(owner, spender)` in `HyperFungibleTokenImpl` Allows Theft of Any Holder's Token Balance - (File: `evm/src/utils/HyperFungibleTokenImpl.sol`)

### Summary
`HyperFungibleTokenImpl.sol`, a role-gated ERC20 used as a deployable fungible token (deployed from `evm/script/DeployIsmp.s.sol` and used by `evm/src/utils/TokenFaucet.sol`), exposes a public function `superApprove(address owner, address spender)` that calls `_approve(owner, spender, type(uint256).max)` with no access control. This is the same bug class as the Canto WETH.sol H-02 finding: an "approve" primitive that lets the caller specify the token owner instead of deriving it from `msg.sender`. Any address can call `superApprove(victim, attacker)` to grant itself unlimited allowance over `victim`'s balance, then drain it via the standard inherited `transferFrom(victim, attacker, amount)`.

### Finding Description
`HyperFungibleTokenImpl` is an `ERC20` + `AccessControlEnumerable` contract. Its `mint` and `burn` functions are properly gated behind `onlyRole(MINTER_ROLE)` / `onlyRole(BURNER_ROLE)`: [2](#0-1) 

However, `superApprove` has no modifier at all and takes the owner as a caller-supplied parameter: [1](#0-0) 

Despite the comment "Helper function for tests," the function lives in the production source tree (`evm/src/utils/`, not a `tests/` directory) and is `public`, so it is part of the deployed contract's live interface. Since `ERC20.transferFrom` is inherited unmodified, any address can:
1. Call `superApprove(victim, attacker)` — sets `allowance[victim][attacker] = type(uint256).max`.
2. Call `transferFrom(victim, attacker, victim_balance)` — drains the victim's entire balance.

This mirrors the WETH.sol root cause exactly: an approve-shaped function parameterized on `owner` rather than `msg.sender`, bypassing the owner-consent guarantee that ERC20's standard `approve(spender, amount)` provides.

### Impact Explanation
Any holder of tokens minted from this contract (e.g., tokens distributed via `TokenFaucet.sol`, or any HyperFungibleTokenImpl deployment referenced in `DeployIsmp.s.sol`) can have their entire balance stolen by an unprivileged attacker in a single transaction, with no proof, consensus verification, or relayer interaction required. This is a direct, concrete theft-of-funds vulnerability reachable by any address holding no special privilege — satisfying the High severity bar of the analogous WETH finding.

### Likelihood Explanation
Likelihood is high: the function requires no privileged role, no proof submission, and no special preconditions — a single call to `superApprove` followed by `transferFrom` (both public, standard-ABI calls) is sufficient. Exploitability depends only on the contract being deployed and holding user balances, which the presence of `TokenFaucet.sol` and `DeployIsmp.s.sol` usages indicates is the case.

### Recommendation
Remove `superApprove` from the production contract entirely, or, if genuinely needed for test scaffolding, move it into a test-only mock/wrapper contract that is never deployed as `HyperFungibleTokenImpl`. If any caller-restricted "super approve" capability is required in production (e.g., for a privileged operator), it must be gated behind an explicit role check (e.g., `onlyRole(DEFAULT_ADMIN_ROLE)`) and ideally should not allow arbitrary third parties to set allowances on behalf of token owners who never consented.

### Proof of Concept
1. Deploy `HyperFungibleTokenImpl` (as done in `evm/script/DeployIsmp.s.sol`), and have `victim` acquire a balance (e.g., via a `MINTER_ROLE` holder or `TokenFaucet.sol`).
2. From `attacker` (unprivileged), call:
   `superApprove(victim, attacker)` → sets `allowance[victim][attacker] = type(uint256).max`.
3. From `attacker`, call:
   `transferFrom(victim, attacker, hft.balanceOf(victim))` → transfers the victim's full balance to `attacker`.

No revert occurs at any step because `superApprove` carries no access-control modifier, unlike `mint`/`burn` in the same contract.

**Uncertainty/limitations**: I could not fully trace every production deployment path (e.g., whether `HyperFungibleTokenImpl` instances hold significant real value versus being test/faucet tokens only) within the available tool budget — `evm/script/DeployIsmp.s.sol` and `evm/src/utils/TokenFaucet.sol` reference the contract, but I was unable to read their full contents to confirm the exact deployment context (mainnet vs. testnet-only faucet). This should be verified with a full read of those files before treating the impact as certain on mainnet.
