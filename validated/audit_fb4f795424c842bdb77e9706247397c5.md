## Title
Direct SPL-token donation to `amm_coin_vault`/`amm_pc_vault` inflates `total_*_without_take_pnl`, diluting depositor LP minting — (File: `program/src/processor.rs`, `process_deposit`)

### Summary
`process_deposit` computes the LP tokens to mint using the *live* SPL-token balances of `amm_coin_vault` / `amm_pc_vault` rather than any internally-tracked reserve value. Because any account holder can transfer SPL tokens into these vaults without going through the AMM program (no authority check is required to be the *destination* of a token transfer), an attacker can inflate `total_pc_without_take_pnl` / `total_coin_without_take_pnl` immediately before a victim's `Deposit` instruction executes. This is directly analogous to the reported `WithdrawProxy` bug, where `totalAssets()` (a live balance read) could be manipulated by an arbitrary token transfer to corrupt a share-based accounting calculation before the legitimate state-transition (`transferWithdrawReserve` / vault claim) occurred.

### Finding Description
`process_deposit` derives the pool's reserves purely from the vault token accounts' `amount` fields: [1](#0-0) 

These reserves (`total_pc_without_take_pnl`, `total_coin_without_take_pnl`) are then used to compute how many LP tokens a depositor receives: [2](#0-1) [3](#0-2) 

`mint_lp_amount = lp_amount * deduct_amount / total_without_take_pnl` (floor rounding). There is no reserve value cached in `AmmInfo`/`TargetOrders` that is independent of the live vault balance — `Calculator::calc_total_without_take_pnl_no_orderbook` simply subtracts the tracked `need_take_pnl_*` amounts from the raw vault `.amount` field: [4](#0-3) 

`amm_coin_vault` and `amm_pc_vault` are ordinary SPL token accounts owned by the AMM `$authority` PDA. SPL Token's `Transfer` instruction only requires the *source* account owner to sign — anyone can transfer tokens **into** any token account, including these vaults, without any interaction with the Raydium program at all. This means an attacker can, in the same or a preceding transaction, directly transfer coin/pc tokens into the vaults, inflating the reserves used by the very next `Deposit` instruction.

`DepositInstruction` only exposes `max_coin_amount`, `max_pc_amount`, `base_side`, and `other_amount_min`: [5](#0-4) 

`other_amount_min` only protects the *ratio* between coin and pc (the counter-asset amount), not the number of LP tokens minted. If the attacker donates coin and pc proportionally to the current pool ratio (preserving price), no ratio-based slippage check is triggered, yet `total_*_without_take_pnl` in the denominator of the LP-minting formula is inflated relative to `amm.lp_amount`, silently reducing `mint_lp_amount` for the victim's contribution. The only floor protection is a revert on `mint_lp_amount == 0`: [6](#0-5) 

which does not protect against partial dilution (only a total-failure case). The victim's real assets are added to the vaults but minted proportionally less LP than their fair share, permanently diluting their value into the pool for the benefit of existing LP holders (including the attacker if the attacker holds LP before the donation), exactly mirroring the reported pattern of a live/manipulable balance read replacing an explicit, attacker-independent accounting checkpoint.

### Impact Explanation
This allows a value-transfer/theft of funds from unsuspecting depositors to whoever holds LP tokens at the time of the attack (potentially the attacker themselves, if they hold LP or briefly acquire it around the donation). Since the deposit accounting depends solely on live token-account balances with no supply-independent internal reserve tracking and no minimum-LP-out slippage parameter, this is a High severity, unprivileged, single-transaction-reachable issue affecting the `Deposit` instruction — a core user-facing entry point.

### Likelihood Explanation
Likelihood is high: the attack requires no special privileges, uses only a standard SPL Token `Transfer` CPI (fully permissionless as a destination), and can be executed opportunistically by front-running or bundling with any victim `Deposit` transaction (e.g., via mempool observation or same-transaction composition where the attacker controls ordering).

### Recommendation
Track pool reserves as internal state (e.g., persisted `coin_amount`/`pc_amount`/checkpoint fields in `AmmInfo`/`TargetOrders`) updated only through program-controlled instructions (`Deposit`, `Withdraw`, swaps, `withdrawpnl`), rather than reading live SPL-token balances directly for LP-minting math. Alternatively/additionally, add an explicit minimum-LP-out parameter to `DepositInstruction` so depositors can enforce a lower bound on `mint_lp_amount`, protecting against reserve-inflation/donation attacks that don't alter the pool price ratio.

### Proof of Concept
1. Attacker holds (or briefly acquires) a portion of the pool's LP supply, or simply intends to donate and immediately withdraw after the victim's deposit lands.
2. Attacker transfers, via a plain SPL Token `Transfer` instruction (not through the Raydium program), coin and pc tokens proportional to the current `amm_coin_vault`/`amm_pc_vault` ratio directly into those vault accounts.
3. Attacker submits (or front-runs) a `Deposit` transaction for the victim in the same slot, immediately after the donation.
4. `process_deposit` reads the now-inflated `amm_coin_vault.amount` / `amm_pc_vault.amount` via `calc_total_without_take_pnl_no_orderbook`, and computes `mint_lp_amount` using the inflated `total_*_without_take_pnl` as denominator — see [1](#0-0) ; [2](#0-1) .
5. The victim's `deduct_coin_amount`/`deduct_pc_amount` are transferred in full into the vaults, but `mint_lp_amount` is smaller than it would have been absent the donation, since `other_amount_min` only checks the coin/pc ratio, not LP output.
6. The victim's contributed value is diluted into the pool; the attacker's pre-existing LP share (or newly re-acquired LP share after this) now represents a larger portion of the pool's total value, realizing a profit at the depositor's expense.

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
