## Title
Webhook shop/topic/webhook-id are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that string. [1](#0-0) [2](#0-1)  The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and are never part of the signed payload. [3](#0-2)  `Registry.process` trusts `request.shop` (and `request.topic`) as the tenant identity after only validating the body's HMAC. [4](#0-3) 

### Finding Description
This mirrors the report's bug class: a value that is *acted on* (the tenant/shop binding) is not covered by the cryptographic check that is supposed to authenticate the request (the HMAC), while a different value (the raw body bytes) is what's actually verified.

Concretely:
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` field. [5](#0-4) 
- For webhooks, `to_signable_string` is defined as `@raw_body` only — the shop domain, topic, webhook id and api version headers are excluded from the signed string. [1](#0-0) 
- These header-derived fields are parsed directly from the raw headers hash passed into `Request.new`, with no cross-check against the body or against the shop the app expects. [6](#0-5) 
- After HMAC validation succeeds, `Registry.process` builds a `WebhookMetadata` using `request.shop` from those unauthenticated headers and dispatches it to the registered handler for the topic — the handler receives an attacker-controlled `shop` value with no further verification. [4](#0-3) 

The identity binding that is broken: `hmac(raw_body) == valid` is treated as proof of `(shop, topic, webhook_id) == authentic`, but the equality that's actually checked is only `hmac(raw_body) == valid`; `shop`/`topic`/`webhook_id` are unauthenticated header echoes.

Because Shopify signs webhooks with the app's single `client_secret` shared across every shop that installs the app, any actor who legitimately receives one valid `(raw_body, hmac)` pair from their own installation (e.g., by installing a public app on a shop they control and triggering a webhook event) can replay that exact body+hmac to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header. The HMAC check still passes because it only verifies the body, and the app's handler is invoked believing the event originated from the victim shop.

### Impact Explanation
This is a cross-tenant spoofing vector: an unprivileged app installer can forge webhook events that the host application will process as if they came from a different, victim tenant (`WebhookMetadata#shop`). Depending on how the host application uses `WebhookMetadata.shop` (e.g., to look up sessions, update per-tenant records, or trigger mandatory GDPR webhooks like `shop/redact`), this can lead to cross-tenant data corruption or state confusion attributed to a shop the attacker does not own, which falls under the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is moderate-to-high for any gem consumer that installs the SDK's webhook `Registry`/`Request` as documented: any user who can install the app on at least one shop (common for public apps) can capture one legitimate `(body, hmac)` pair and replay it against the endpoint with a forged `shop-domain` header, without needing the app's `client_secret`, an access token, or any other credential.

### Recommendation
Include the identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify `shop` against the session/tenant the webhook subscription was registered for) before dispatching to handlers — mirroring the report's fix of accounting for all values that are acted upon within the value that is verified.

### Proof of Concept
1. Attacker installs the target public app on their own shop `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed over `B` with the app's shared `client_secret`.
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...forged shop...})` builds a request whose `to_signable_string` is still `B`. [1](#0-0) 
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`. [7](#0-6) 
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host app to process an event as originating from a shop the attacker does not control. [8](#0-7)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
