### Title
`describeWithdrawal` misattributes withdrawal status/txHash across same-token batch entries via assetId-only matching - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the status for a specific `WithdrawalIdentifier` by calling `findMatchingWithdrawal`, which matches purely on `nep141:<near_token_id> === assetId` and ignores the identifier's `index`. When a batch of withdrawals contains two entries for the same PoA token (e.g., two `nep141:dash.omft.near` withdrawals to different destinations in one signed intent), both entries produce identical `assetId` values, so `findMatchingWithdrawal` always returns the same array element (`Array.prototype.find` returns the first match) for every caller regardless of which withdrawal it actually corresponds to.

### Finding Description
The broken equality: for withdrawal identifiers `wid0` (index 0, destination A) and `wid1` (index 1, destination B), both for `assetId = "nep141:dash.omft.near"`, the code assumes
`findMatchingWithdrawal(response.withdrawals, wid0.assetId) !== findMatchingWithdrawal(response.withdrawals, wid1.assetId)`
whenever `wid0.assetId === wid1.assetId` — but the implementation guarantees the opposite: both calls resolve to the exact same `withdrawals[]` element.

Code path:
- `createWithdrawalIdentifiers` (in `withdrawal-watcher.ts`) assigns a per-bridge-route `index` to each withdrawal param, so two `dash.omft.near` withdrawals in one batch get `index: 0` and `index: 1` respectively, both routed to `PoaBridge`, both sharing the same `tx.hash` (the settled intent tx). [1](#0-0) 
- `describeWithdrawal` fetches the withdrawal status list for `args.tx.hash` (same for both entries) and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`. [2](#0-1) 
- `findMatchingWithdrawal` matches solely by `nep141:${w.data.near_token_id} === assetId`, with no use of `index`, destination address, or amount, and the function's own doc comment admits: "multiple withdrawals of the same token in a single transaction are not supported." [3](#0-2) 

Root cause: the POA bridge status API's `withdrawal_hash` lookup returns an unsorted list of all withdrawals within the tx, and the SDK has no per-index correlation key (no destination address/amount check) to disambiguate two same-token entries. When `watchWithdrawal` polls independently for `wid0` and `wid1` (both via `PoaBridge.describeWithdrawal`), both polls hit the same code and — as soon as any one of the two withdrawals completes — `.find()` returns that single completed entry to *both* callers, even though only one of the two payouts has actually landed. The other identifier (still pending or destined elsewhere) gets falsely reported `completed` with the wrong `txHash`.

Existing guards do not prevent this: `supports()`, `validateWithdrawal`, `compareAddresses`, and `FeeExceedsAmountError` all validate assetId/amount/destination at withdrawal-creation time per individual `WithdrawalParams` entry, but none of them reject a *batch* containing two entries with the same PoA `assetId`, and none of them are consulted during `describeWithdrawal`/`findMatchingWithdrawal` to disambiguate results.

### Impact Explanation
An integrator using `sdk.waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` for a batch with two same-token PoA withdrawals will receive a `status: "completed"` + `txHash` for the wrong destination on one of the two identifiers, while the truly-completed withdrawal for the other destination may separately also resolve to the same (wrong) `txHash`. This causes a status/hash misreport that could make the integrator credit a user's payout as completed for a destination that has not actually received funds yet (or double-credit based on the same txHash for two distinct expected payouts) — matching the "High" impact category (status/hash misreport making an integrator credit or refund twice). The issue is fully repeatable any time a batch has ≥2 PoA withdrawals of the identical `nep141` asset, and requires no special privilege — a normal user (or any batch built by an integrator/counterparty) can trigger it simply by including two same-token PoA withdrawals in one signed intent.

### Likelihood Explanation
Preconditions: the batch must contain two or more withdrawals whose `assetId` resolves to the same PoA-bridged NEP-141 token (e.g. two legs both `nep141:dash.omft.near`) within a single signed intent/tx. Nothing in `createWithdrawalIntents`, `signAndSendWithdrawalIntent`, or `validateWithdrawal` rejects such a batch — each entry is validated independently and the batch composition itself is never checked for assetId collisions. This is directly attacker/integrator-controllable (batch composition with repeated assetId is explicitly called out as achievable), cheap (just build a batch withdrawal request), and reproducible on demand.

### Recommendation
Disambiguate `findMatchingWithdrawal` beyond assetId — e.g., match on `(assetId, destination_address)` pairs when the POA API response includes destination data, or, per the existing code comment's own suggestion, sort both the API response and the withdrawal params deterministically by amount (since fees are equal for same-token withdrawals, relative ordering is preserved) and pair by position/index instead of `.find()`'s first match. Alternatively, explicitly detect and reject (fail fast) batches containing duplicate PoA `assetId` entries in `createWithdrawalIdentifiers`/`signAndSendWithdrawalIntent` until proper per-entry correlation is implemented, rather than silently returning misleading status data.

### Proof of Concept
Vitest plan (mock only the HTTP layer, `poaBridge.httpClient.getWithdrawalStatus`):
1. Construct two `WithdrawalIdentifier`s for the same `tx.hash`, same `assetId = "nep141:dash.omft.near"`, `index: 0` (destinationAddress A) and `index: 1` (destinationAddress B).
2. Mock `poaBridge.httpClient.getWithdrawalStatus` to return `withdrawals: [{ status: "COMPLETED", data: { near_token_id: "dash.omft.near", transfer_tx_hash: "0xB", destination_address: "B", amount: ... } }, { status: "PENDING", data: { near_token_id: "dash.omft.near", destination_address: "A", ... } }]` (i.e., only B's payout has completed).
3. Call `poaBridge.describeWithdrawal(wid0)` (index 0, destination A) and `poaBridge.describeWithdrawal(wid1)` (index 1, destination B).
4. Assert the pre-fix (broken) behavior: **both** calls return `{ status: "completed", txHash: "0xB" }` — i.e. `describeWithdrawal(wid0).txHash === describeWithdrawal(wid1).txHash === "0xB"`, even though `wid0`'s real destination (A) withdrawal is still `PENDING`.
5. Assert the invariant that should hold post-fix: `describeWithdrawal(wid0)` must report `pending` (matching A's true state) and only `describeWithdrawal(wid1)` should report `completed` with `txHash: "0xB"` — i.e., each `WithdrawalIdentifier` resolves to the withdrawal entry with the matching destination address/amount, not just matching `assetId`.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
