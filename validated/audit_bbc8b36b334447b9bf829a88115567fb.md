### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, so `HmacValidator` never binds the `shop` header to the signature. An entity that can obtain one genuine, validly-signed webhook (e.g. by installing the app on their own shop) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. The signature still validates, and `Registry.process` hands the handler a `WebhookMetadata` object whose `shop` is the attacker-chosen value, even though the body/HMAC did not originate from that shop.

### Finding Description
The identity binding that should hold is: `HMAC_valid(request) ⇒ shop_header == originating_shop`. In this gem that equality is broken:

- `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) signs only `@raw_body`.
- `HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) computes the HMAC exclusively over that signable string and compares it to the `hmac-sha256` header.
- `shop` (`lib/shopify_api/webhooks/request.rb:20-23`), `topic`, `api_version`, and `webhook_id` are all read from headers that play no part in the signed bytes.
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) verifies only `Utils::HmacValidator.validate(request)` and then forwards `request.shop` unchanged to the handler as the tenant identifier for the webhook.

Because `shop` is "bytes parsed" rather than "bytes verified," any party capable of obtaining one legitimately-signed webhook payload for any topic (trivial for a self-serve/public Shopify app — install the app on an attacker-controlled shop and let Shopify deliver a real webhook) can capture `raw_body` + its valid `hmac-sha256`, then POST it again to the same public endpoint with the `shop-domain` header changed to a victim's shop. `HmacValidator.validate` still returns `true` because it never inspects the header, and the handler receives `WebhookMetadata#shop` set to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee to host applications: verifying the HMAC is documented as proof "the request did indeed come from Shopify" for the shop asserted in the metadata (see `docs/usage/webhooks.md`), but the shop assertion itself is unauthenticated. A host app that trusts `WebhookMetadata#shop` (as the docs' example and `Registry.process` encourage) to look up/update per-tenant records can be made to write attacker-controlled webhook content into another merchant's tenant data — cross-tenant access/injection, one of the specified Critical impacts.

### Likelihood Explanation
Requires only unauthenticated internet access to the app's public webhook endpoint plus the ability to obtain one genuinely-signed webhook (achievable for any app that supports self-serve installs, since the attacker can install the app on their own store to receive real, validly-signed webhooks). No access token, `client_secret`, or privileged credential is required — only replay of previously observed bytes with a modified header.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified content, or otherwise cross-check the header-derived `shop` against an independently authenticated value before calling the handler. At minimum, `Registry.process` should reject requests whose `shop` cannot be corroborated against known/registered installations rather than trusting the header value implicitly once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app's public callback URL, capturing the raw body and the `x-shopify-hmac-sha256` header value.
2. Attacker replays the identical request to the same endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` untouched, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the tampered headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only [1](#0-0)  and succeeds because the body/HMAC pair is genuinely valid.
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [2](#0-1)  where `shop` is `"victim.myshopify.com"`, causing the host app to process attacker-supplied content under the victim tenant. [3](#0-2) [4](#0-3) [5](#0-4)
