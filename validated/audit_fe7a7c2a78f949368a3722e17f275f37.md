### Title
Fee-on-transfer tokens cause escrow over-crediting in Tron `IntentGatewayV2.placeOrder` (unbacked withdrawal / insolvency) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of `IntentGatewayV2.placeOrder` credits escrow with the user-requested (fee-reduced by protocol fee only) amount instead of the amount actually received by the contract via `safeTransferFrom`, unlike the canonical EVM implementation which measures actual balance deltas to account for fee-on-transfer tokens.

### Finding Description
In the mainline EVM contract, `placeOrder` explicitly snapshots balances before/after each `safeTransferFrom` (and after the predispatch sweep) and uses the *actual received* amount to build `order.inputs`/`reducedInputs` and to credit escrow, with an inline comment acknowledging fee-on-transfer tokens: [1](#0-0) [2](#0-1) 

In contrast, the Tron variant of the same function performs `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` (the *requested* amount) and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount` — which is derived from the requested amount minus only the protocol fee, with no adjustment for actual tokens received: [3](#0-2) 

There is no balance-before/balance-after check in this branch (the non-predispatch path), so if the input token deducts a transfer fee (or otherwise delivers less than requested), the gateway's actual token balance will be strictly less than the sum of `_orders[commitment][token]` entries recorded in escrow. Even the predispatch branch, while it computes a `dust` value from `balance - requiredAmount`, still credits the escrow with the fixed `reducedInputs[i].amount` rather than the actual measured balance: [4](#0-3) 

This is the direct analog of the reported AaveProvider issue: the contract assumes the requested transfer amount is exactly what lands in the contract, which is false for fee-on-transfer tokens, and the mismatch is not detected or corrected — it silently corrupts the escrow ledger instead of reverting or adjusting.

### Impact Explanation
Because escrow accounting (`_orders[commitment][token]`) no longer matches the gateway's actual token balance, the contract becomes under-collateralized for that order. When the order is later filled (`fillOrder`/`withdraw`) or cancelled (`cancelOrder` → `withdraw`), the contract will attempt to pay out the recorded (inflated) escrow amount to the solver/beneficiary. This can be settled by drawing down other users' escrowed token balances of the same token, since a shared `IERC20` balance backs all commitments — i.e., one user placing an order with a fee-on-transfer token creates a permanent shortfall that is paid for out of other orders' collateral, leading to insolvency/fund freezing for other order owners or a preventable direct loss for the protocol/solvers who are shorted.

### Likelihood Explanation
Any unprivileged user can trigger this by simply placing an order (`placeOrder`) using a fee-on-transfer or deflationary ERC20 token as an input — no special privileges, front-running, or governance action needed. The Tron deployment does not appear to restrict allowed input tokens to a known-safe allowlist, so if any such token is ever whitelisted/used as an input asset, the accounting corruption is deterministic and reproducible on every `placeOrder` call for that token.

### Recommendation
Mirror the mainline EVM logic in the Tron contract: measure the gateway's token balance before and after `safeTransferFrom` (and after the predispatch sweep) and use the actually-received delta — not the caller-requested amount — both to build the commitment's `order.inputs`/`reducedInputs` and to credit `_orders[commitment][token]`. Alternatively, explicitly disallow fee-on-transfer/rebasing tokens as inputs via a strict post-transfer balance-delta check that reverts on mismatch, rather than silently crediting the nominal requested amount.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee on transfer, as used in the EVM test suite's `FeeOnTransferToken`) and register/allow it as an input token on the Tron `IntentGatewayV2`.
2. User A calls `placeOrder` with `inputs[0] = {token: FOT, amount: 1000e18}`. The contract executes `safeTransferFrom(user, gateway, 1000e18)`, but due to the 1% fee the gateway's actual FOT balance only increases by `990e18`.
3. The contract nonetheless sets `_orders[commitment][FOT] += reducedInputs[0].amount` (≈1000e18 minus only protocol fee, e.g. ~995e18 if a 0.5% protocol fee applies, or the full 1000e18 if no protocol fee), which exceeds the 990e18 actually held.
4. User B independently places another order with the same FOT token, adding their (correctly discounted, but from B's perspective) tokens to the shared gateway balance.
5. When A's order is filled or cancelled, `withdraw` pays out the escrowed (inflated) amount recorded for A, drawing on the pooled FOT balance that includes B's escrowed collateral, leaving B's order under-collateralized when B later tries to cancel/fill — demonstrating the insolvency/fund-freezing impact.

Note: I was unable to fully verify the exact `withdraw` function body in the Tron contract (only its signature/call sites were confirmed) due to the final iteration cutoff; the finding depends on `withdraw` transferring the amount recorded in `_orders[commitment][token]`, which is consistent with the design pattern seen in `cancelOrder`'s `WithdrawalRequest` construction.
