### Title
`DirectBridge.describeWithdrawal` unconditionally reports every withdrawal as `completed`, breaking per-index STATUS TRUTH - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.describeWithdrawal` ignores `args.index` and any on-chain outcome entirely, always returning `{ status: "completed", txHash: args.tx.hash }`. In a batch withdrawal where multiple `ft_withdraw`/`native_withdraw` intents are settled by one signed intent (and thus share one `NearTxInfo`), a failure of the async `ft_transfer`/`ft_transfer_call` receipt for withdrawal index `j` (e.g. missing storage deposit on the receiving token contract, receiver rejecting the transfer, `native_withdraw` receiver account issue) is invisible to the SDK — it will be reported as `completed` exactly like a truly successful index `i`.

### Finding Description
The claimed equality is: `describeWithdrawal(wid_j).status` must equal the true on-chain outcome of the `ft_withdraw`/`native_withdraw` intent at `wid_j.index` within the settlement tx. Instead, the implementation is: [1](#0-0) 

which returns `{ status: "completed", txHash: args.tx.hash }` for any `WithdrawalIdentifier`, regardless of `args.index`, and without querying the NEAR provider for the transaction's receipt outcomes at all.

Tracing the reachable path: `IntentsSDK.processWithdrawal` → `signAndSendWithdrawalIntent` (builds one `token_diff` + N `ft_withdraw`/`native_withdraw` intents via `DirectBridge.createWithdrawalIntents`, one intent per withdrawal index) → `waitForIntentSettlement`, which only confirms the *outer* intent-settlement tx status through the solver relay (`SETTLED` vs `NOT_FOUND_OR_NOT_VALID`/`FAILED`) — see [2](#0-1) .
This only detects failure of the whole verifying-contract call (e.g. out of gas at the top level); it does not, and cannot, detect failure of the individually dispatched `ft_transfer`/`ft_transfer_call` cross-contract promises that each `ft_withdraw` intent schedules — those are separate NEAR receipts that can fail independently (e.g. NEP-141 receiver lacking storage, as explicitly called out in the contract-types schema note: *"NOTE: No refund will be made in case of insufficient `storage_deposit` on `token` for `receiver_id`"*, see [3](#0-2) ).

`waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` then calls `describeWithdrawal` once per index via `watchWithdrawal` [4](#0-3)  — but for `DirectBridge`-routed withdrawals there is no differentiation whatsoever between indices; every call returns the same hard-coded `completed` status with the shared `args.tx.hash`. Contrast this with other bridges (`HotBridge`, `OmniBridge`, `PoaBridge`) which query real per-withdrawal API/indexer state before reporting status, as seen in their respective `.test.ts` files exercising pending/failure states (`hot-bridge.test.ts` lines 729-758 return `{ status: "pending" }` on unresolved lookups).

None of the listed guards (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `supports()` ordering, `FeeExceedsAmountError`, `getUnderlyingFee`, `matchesRequest`, `assert` sanity checks, or the intents contract's signature/nonce verification) touch this code path at all — they operate at intent-construction time, before the tx is even sent, and have no bearing on the post-hoc status query performed by `describeWithdrawal`.

### Impact Explanation
An integrator building on `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`/`processWithdrawal` for a batch of `DirectBridge`-routed withdrawals (all `nep141` assets routed via `RouteEnum.NearWithdrawal`) will receive `completed` for every index even if the underlying `ft_transfer`/`ft_transfer_call` receipt for a specific index reverted on-chain. This is a status/hash misreport that can cause an integrator to credit/settle a withdrawal whose funds never reached the destination — matching the High severity category ("a status or hash misreport making an integrator credit or refund twice"). The bug is deterministic and repeatable on every call for every `DirectBridge` withdrawal, not just in the batch/shared-tx scenario described in the prompt — a single, non-batched `DirectBridge` withdrawal whose `ft_withdraw` receipt fails will also be misreported as `completed`. The batch scenario the question describes (index i succeeds, index j fails, same `args.tx`) is a valid instance of this broader defect, since the function doesn't even look at `args.index` or the tx receipts.

### Likelihood Explanation
No special privilege is required. Any ordinary user withdrawing via `DirectBridge` (NEAR-native NEP-141 withdrawal) whose destination `receiver_id` lacks the token's storage deposit (a very common real-world condition, since storage deposits aren't guaranteed to exist for arbitrary receiver accounts) will trigger a failed `ft_transfer` receipt while the outer intent-settlement tx still reports success at the relay level. The integrator (using the SDK "as documented") then calls `describeWithdrawal`/`waitForWithdrawalCompletion`, which will report `completed` unconditionally. No malicious relayer/RPC/contract-admin behavior is needed — this reproduces under fully honest, correct external services, purely due to the SDK's stub implementation.

### Recommendation
Implement `DirectBridge.describeWithdrawal` to actually verify the on-chain outcome for the specific withdrawal `index`: fetch the transaction's execution outcome (including receipts) via `this.nearProvider`, locate the receipt corresponding to the `ft_transfer`/`ft_transfer_call`/`native_withdraw` triggered by intent `index`, and only return `completed` if that specific receipt succeeded; otherwise return `failed`/`pending` as appropriate. This mirrors how `HotBridge`, `OmniBridge`, and `PoaBridge` verify real destination-chain state before reporting `completed`.

```ts
// direct-bridge.describeWithdrawal.test.ts
import { describe, it, expect, vi } from "vitest";
import { DirectBridge } from "./direct-bridge";
import { Chains } from "../../lib/caip2";

describe("DirectBridge.describeWithdrawal per-index status", () => {
  it("reports completed for a failed index sharing the same intent tx", async () => {
    const nearProvider = {
      // Mock a tx_status result where receipt for index 1's ft_transfer failed
      txStatus: vi.fn().mockResolvedValue({
        status: { SuccessValue: "" }, // outer tx "succeeded"
        receipts_outcome: [
          { outcome: { status: { SuccessValue: "" } } },      // index 0 receipt: success
          { outcome: { status: { Failure: { /* error */ } } } }, // index 1 receipt: failed
        ],
      }),
    } as any;

    const bridge = new DirectBridge({
      envConfig: {} as any,
      nearProvider,
    });

    const sharedTx = { hash: "sharedTxHash", accountId: "intents.near" };

    const wid0 = bridge.createWithdrawalIdentifier({
      withdrawalParams: { assetId: "nep141:usdt.near", amount: 100n, destinationAddress: "alice.near" } as any,
      index: 0,
      tx: sharedTx,
    });
    const wid1 = bridge.createWithdrawalIdentifier({
      withdrawalParams: { assetId: "nep141:usdt.near", amount: 100n, destinationAddress: "bob.near" } as any,
      index: 1,
      tx: sharedTx,
    });

    const result0 = await bridge.describeWithdrawal(wid0);
    const result1 = await bridge.describeWithdrawal(wid1);

    // Both sides of the claimed equality:
    // LHS: describeWithdrawal(wid1).status  (currently always "completed")
    // RHS: true on-chain outcome for index 1 (mocked as failed)
    expect(result1).toEqual({ status: "completed", txHash: sharedTx.hash }); // current (buggy) behavior
    // Desired/fixed behavior should instead assert:
    // expect(result1.status).not.toBe("completed");
    expect(result0).toEqual({ status: "completed", txHash: sharedTx.hash }); // index 0 correctly "completed" but by coincidence, not by verification
  });
});
```
This demonstrates that `describeWithdrawal` returns identical `completed` results for both indices regardless of the mocked per-receipt outcome, because the current implementation never reads `nearProvider`/receipts data — confirming the broken equality between reported status and true per-index on-chain outcome.

```typescript
	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
	}
```
