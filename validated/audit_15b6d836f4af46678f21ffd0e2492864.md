### Title
Incorrect decimal-based minimum-liquidity burn in `process_initialize2` allows first-depositor share-inflation attack - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` computes the pool's minted LP supply as `sqrt(pc_vault.amount * coin_vault.amount)` and then burns/locks a "minimum liquidity" amount computed as `10^(lp_mint.decimals)`, where `lp_mint.decimals` is hard-set to the coin mint's decimals rather than a value tied to the actual precision unit the AMM uses internally (`sys_decimal_value`). This is the same class of bug as the external report: a decimal exponent is picked from a single token's decimals and blindly applied to a value whose magnitude actually depends on the combination/ratio of two different token decimals, producing wildly wrong results whenever the two mints' decimals diverge from the implicitly assumed case.

### Finding Description
In `process_initialize2`: [1](#0-0) 
`lp_decimals` is set equal to `coin_mint.decimals` and used to create the LP mint.

Later, the same value is used to compute the “minimum liquidity” subtracted from the newly minted LP supply: [2](#0-1) 

`liquidity` is `sqrt(pc_vault.amount * coin_vault.amount)`, a quantity whose scale depends on **both** `pc_decimals` and `coin_decimals` (it lives in a "mixed decimal" space, roughly `10^((pc_decimals+coin_decimals)/2)`). The subtracted floor amount, however, is `10^(coin_decimals)` only — it ignores `pc_decimals` entirely and has no relationship to `amm.sys_decimal_value`, which the rest of the program (`Calculator::normalize_decimal_v2`/`restore_decimal`, `calc_take_pnl`, swap math) correctly derives as `10^(max(pc_decimals, coin_decimals))`: [3](#0-2) 

There is no validation anywhere in `process_initialize2` bounding the relationship between `coin_mint.decimals` and `pc_mint.decimals` (any unprivileged user can call `Initialize2` with attacker-chosen mints, including a coin mint with very low decimals — SPL Token allows creating a mint with 0 decimals — paired with a pc mint of high decimals, e.g. 9). When `coin_decimals` is small relative to `pc_decimals`, `10^(coin_decimals)` is a negligible fraction of the actual `sqrt(pc*coin)` liquidity value, so almost the entire computed liquidity is minted to the pool creator instead of being locked, defeating the anti-inflation purpose of the burn (exactly analogous to how the PegOracle used a fixed decimal assumption that silently broke for non-8-decimal feeds).

### Impact Explanation
A negligible effective "minimum liquidity" lock means the classic first-depositor / share-price-manipulation attack becomes far cheaper: the pool creator can seed the pool with a ratio that mints them almost all LP shares (since barely anything is burned), then donate tokens directly to the vaults to inflate `total_pc_without_take_pnl`/`total_coin_without_take_pnl` before a victim's deposit, rounding the victim's minted LP down to zero or a much smaller share than deposited, effectively stealing the victim's deposited funds. This is a direct threat to LP funds (theft/insolvent pool accounting), matching the “Medium/High” bar for concrete theft of LP funds.

### Likelihood Explanation
Reachable in a single transaction via the fully public, unprivileged `Initialize2` instruction with attacker-chosen coin/pc mints and attacker-chosen `init_pc_amount`/`init_coin_amount`. No privileged signer or special build config is required — only a low-decimal SPL mint (trivially creatable) as the "coin" side of the pool.

### Recommendation
Compute the minimum-liquidity burn using `amm.sys_decimal_value` (or a fixed protocol-wide constant independent of either mint's decimals) instead of `lp_mint.decimals`/`coin_mint.decimals`, ensuring the locked amount is always a fraction of `liquidity` proportional to the actual precision used throughout the rest of the program, regardless of which decimals the coin or pc mint happen to use.

### Proof of Concept
1. Attacker creates two SPL mints: `coin_mint` with `decimals = 0`, `pc_mint` with `decimals = 9`.
2. Attacker calls `Initialize2` (`program/src/processor.rs::process_initialize2`) supplying `init_coin_amount = 1` and `init_pc_amount = 10^18` (or any ratio favorable to them).
3. `liquidity = sqrt(1 * 10^18) = 10^9`; `lp_mint.decimals = coin_mint.decimals = 0`, so `user_lp_amount = 10^9 - 10^0 = 999_999_999`, i.e., essentially 100% of the computed liquidity goes to the attacker instead of being locked.
4. Attacker then transfers additional pc/coin tokens directly into the vaults to skew `total_pc_without_take_pnl`/`total_coin_without_take_pnl` before a victim's `Deposit`, causing the victim's minted LP (computed via `InvariantPool`/`exchange_token_to_pool` proportional math) to round down disproportionately, allowing the attacker to later withdraw more value than they contributed.
