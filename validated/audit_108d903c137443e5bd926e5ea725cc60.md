### Title
Wallet Contract's `has_in_flight_tx` Single-Slot Lock Has No Cancellation/Timeout Mechanism — Permanent Denial-of-Service Analogous to BlueprintCore's Stalled Deployment Request - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` enforces exactly one in-flight Ethereum-style transaction at a time via a single boolean flag `has_in_flight_tx`, exactly like BlueprintCore's `requestDeploymentID == 0` single-slot invariant. Unlike BlueprintCore, the wallet contract relies on the fact that NEAR's `.then()` promise callback is *guaranteed* to fire regardless of the predecessor's success/failure to reset the flag — but the flag reset itself lives inside the *same* callback receipt whose other logic can fail, and NEAR receipts are atomic: if that terminal callback fails for any reason (e.g. insufficient statically-attached gas, or any panic after the entry point), **all its state writes — including the `has_in_flight_tx = false` reset — are rolled back**, leaving the contract permanently locked with no cancellation or timeout path.

### Finding Description
`WalletContract` stores `nonce` and `has_in_flight_tx` and documents the invariant explicitly: [1](#0-0) 

Every call to `rlp_execute` is rejected outright while `has_in_flight_tx` is `true`, with no way for the account owner to cancel or reset it: [2](#0-1) 

The flag is only ever cleared inside private callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`), each of which sets `self.has_in_flight_tx = false` as its very first statement, and then may set it back to `true` if it spawns another promise: [3](#0-2) [4](#0-3) 

The terminal callback `rlp_execute_callback` is scheduled with a small fixed static gas budget, `RLP_EXECUTE_CALLBACK_GAS = Gas::from_tgas(5)`: [5](#0-4) 

Because NEAR function-call receipts are atomic, if this terminal callback exhausts its attached gas or otherwise fails/panics during execution, the entire receipt (including the `has_in_flight_tx = false` reset that already executed as the first statement) is reverted along with any refund logic further down. Since this is the *last* link in the promise chain (no subsequent `.then()`), there is no further receipt that could re-attempt clearing the flag. The contract has no owner-triggered reset, timeout, or cancellation function analogous to BlueprintCore's missing "cancel stalled deployment" capability — `has_in_flight_tx` remains `true` forever, and every future `rlp_execute` call is permanently rejected with `"transaction already in progress"`.

This mirrors the reported bug class precisely: a single-slot state variable gating all future unprivileged requests, set by an in-flight action, cleared only by a downstream step that can fail, and with no timeout/cancellation escape hatch.

### Impact Explanation
Once the flag becomes permanently stuck, the wallet-contract account is bricked for the RLP-execute flow — no `rlp_execute` transaction (i.e., no Ethereum-style transaction routed through this NEAR account) can ever be processed again. Any $NEAR balance, deposits, or delegated authority tied to the wallet's transaction pipeline become unusable, matching BlueprintCore's impact of stalled deployments and unusable fees.

### Likelihood Explanation
Triggering requires the terminal callback (`rlp_execute_callback`, or `nep_141_storage_balance_callback`/`address_check_callback` mid-chain) to fail after already having (transiently) executed the flag-reset line — e.g., by the callback running out of its narrowly fixed 5 Tgas static budget, or a downstream refund/serialization panic. This is a narrower trigger than BlueprintCore's simple "worker never submits proof," since normal NEAR promise semantics *do* guarantee the callback fires even when the called external contract fails. The concrete exploitability therefore depends on whether an attacker (e.g. a malicious `target` or NEP-141 token contract) can force execution paths inside the callback that exceed the allotted 5 Tgas, which was not fully verifiable from the indexed code alone.

### Recommendation
Add an explicit, permissionless (or owner-gated) recovery path: e.g. a `reset_in_flight_tx` method guarded by a block-height/timestamp timeout recorded alongside `has_in_flight_tx`, so that if the terminal callback never successfully clears the flag within N blocks, the account owner (or anyone) can force-reset it, mirroring the timeout-based mitigation adopted for BlueprintCore.

### Proof of Concept
Not independently reproducible from the indexed code alone — the trigger condition (terminal-callback gas exhaustion or panic causing state rollback of the flag reset) requires exact NEAR VM gas-accounting figures for `rlp_execute_callback`'s worst-case execution path, which are not available in this index. This should be validated with an actual test-loop/sandbox reproduction (e.g., forcing `RLP_EXECUTE_CALLBACK_GAS` to be insufficient for the `PromiseResult::Failed` refund branch and confirming `has_in_flight_tx` remains `true` after the failed receipt).

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
