### Title
Webhook shop-identity header not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only (`to_signable_string` → `@raw_body`), but derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers that are excluded from the signed bytes. `Registry.process` validates the body's HMAC and then trusts the unsigned `shop` header to build `WebhookMetadata` passed to the app's handler, breaking the binding: `hmac_signed_bytes == identity_used_for_dispatch`.

### Finding Description
The HMAC-over-body-only design is Shopify's real webhook signing scheme, so this by itself is expected behavior for legitimate Shopify-originated requests. However, the gem's contract here is exactly the analog of the reported bug class: a field (`shop`) is *acted on* (used to attribute the webhook to a tenant and passed to the handler) but is *not covered by* the value that was cryptographically verified (`@raw_body`).

Concretely:
- `Request#hmac` and `Request#to_signable_string` compute/verify only the body. [1](#0-0) 
- `Request#shop`, `#topic`, `#webhook_id` come from headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`), none of which participate in `to_signable_string`. [3](#0-2) 
- `Registry.process` validates `Utils::HmacValidator.validate(request)` (body-only check) and then unconditionally forwards `request.shop` to the handler as the tenant identity. [2](#0-1) 

Because the app-level `api_secret_key`/webhook secret is shared across *all* shops that install the app (it is not per-shop), any merchant who has legitimately installed the app receives genuine `(body, hmac)` pairs from Shopify for their own shop's real events. That merchant, acting as an unprivileged internet user with respect to *other tenants* of the same app, can capture a legitimately-signed `(body, hmac-sha256)` pair from their own webhook deliveries and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because the body is unchanged, and `Registry.process` will dispatch the (attacker-controlled-timing, attacker's own body content) webhook to the handler labeled as coming from the victim shop.

### Impact Explanation
This breaks the identity binding "bytes verified versus bytes parsed": the gem verifies the request body but parses/trusts a completely separate, unverified header for tenant attribution. Any host application that uses `WebhookMetadata#shop` to look up per-shop session/access-token state, gate per-tenant logic, or trigger tenant-scoped side effects (e.g. mandatory `customers/data_request`, `customers/redact`, `shop/redact`, or app-specific topics) can be tricked into performing that action against the wrong shop's stored data — a cross-tenant confusion condition.

### Likelihood Explanation
Requires the attacker to be a real (if malicious) merchant with a working installation of the target app on their own store — no `api_secret_key`, access token, or client secret theft is needed, since they only need webhooks Shopify already legitimately delivers to them. This is a realistic "unprivileged internet user" scenario relative to any other tenant of the same multi-tenant app.

### Recommendation
Include the tenant-identifying headers (at minimum `shop`, and ideally `topic`/`webhook_id`) in the signed/verified material, or independently bind the verified body's shop/tenant reference (many webhook payloads include `shop_id`/`shop_domain` fields) against the header value before trusting it, rejecting the request on mismatch.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers/receives any webhook topic handled by the app (e.g. `orders/create`).
2. Shopify delivers a legitimately HMAC-signed webhook: headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid>`, plus a JSON body.
3. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unmodified) body against the (unmodified) HMAC. [4](#0-3) 
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host application to process attacker-controlled data under the victim shop's tenant identity. [5](#0-4)
