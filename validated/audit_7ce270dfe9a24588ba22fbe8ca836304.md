### Title
Webhook `shop` (and `topic`/`webhook_id`) fields are unauthenticated by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request by checking `Utils::HmacValidator.validate(request)`, but `Webhooks::Request#to_signable_string` returns only the raw request body. The `shop`, `topic`, and `webhook_id` values consumed later (and forwarded to the app's handler) are read directly from unauthenticated HTTP headers, never included in the HMAC-signed material.

### Finding Description
`Webhooks::Request` implements `VerifiableQuery` with: [1](#0-0) 
`hmac` is derived from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body` — the `shop`, `topic`, and `webhook_id` fields are read straight from headers and are not part of what gets HMAC-verified.

`Registry.process` verifies only this body-bound HMAC before trusting the header-derived shop/topic and dispatching to the handler: [2](#0-1) 

Because the api_secret_key used to compute the HMAC is the same for every shop that has the app installed, any actor who can obtain one genuine, HMAC-signed webhook delivery for a shop they control (e.g., by installing the app on their own store and triggering a webhook) can replay the identical body + `hmac-sha256` header while substituting a different `shop-domain` header value. `HmacValidator.validate` will still succeed because it only checks the body signature — it establishes the equality "HMAC covers `raw_body`" but the code actually acts on "`shop` header == authenticated shop," which is never proven. This mirrors the reported bug class: a value that is *acted upon* (the deposited asset / here, the shop identity) is not covered by the cryptographic check that is supposed to authorize the action (the `permit` signature / here, the webhook HMAC).

### Impact Explanation
A malicious actor with legitimate access to the app on their own store can forge a webhook payload that the app believes originates from a different, victim merchant's shop, since `WebhookMetadata.shop` passed to handlers is taken from the unauthenticated header. If the host application uses this `shop` value to key session/data lookups (which is the intended usage pattern based on `WebhookMetadata`), this allows cross-tenant data injection/processing under another merchant's identity.

### Likelihood Explanation
This requires the attacker to be a real (even free/unprivileged) app installer on at least one shop to obtain one genuine signed webhook body, after which forging the header is trivial (no secret needed). This is a design characteristic shared with Shopify's official documented webhook verification flow (HMAC is documented to cover only the body), so it is uncertain whether this is treated as a gem-level defect versus expected/documented behavior that host apps are expected to additionally guard against by validating shop against known installed sessions. I could not confirm from the available files whether `docs/webhooks.md` explicitly warns integrators that `shop` in `WebhookMetadata` is unauthenticated and must be cross-checked — this should be verified before treating it as a novel vulnerability rather than intended/documented API behavior.

### Recommendation
If not already documented, explicitly warn integrators in `docs/usage/webhooks.md` that `WebhookMetadata#shop`, `#topic`, and `#webhook_id` are not covered by HMAC verification and must be cross-referenced against known installed shop sessions before being trusted, or consider binding these header values into the signable string comparison surface (e.g., validating `shop` against an allow-list of active sessions before dispatch) in `Registry.process`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST body plus its `X-Shopify-Hmac-Sha256` header.
2. Replay the exact same body and `hmac-sha256` header to the app's webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds (body/HMAC pair unchanged), and `Registry.process` dispatches to the handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the payload/signature was never generated for that shop.

**Uncertainty note:** I was unable to confirm from the indexed files whether `docs/` for webhooks explicitly documents this as the integrator's responsibility (in which case, per the rules, this analog should be rejected as "host application ignoring documented API"). Given the size limits on the indexed content, I recommend confirming the full contents of `docs/usage/webhooks.md` and `lib/shopify_api/webhooks/*` via a full Devin session before treating this as an actionable, non-duplicate finding.
