This confirms the vulnerability. The gem's documented API explicitly tells app developers to trust `data.shop` as "The shop domain of the webhook" for tenant-scoped processing, while `Registry.process` only validates the HMAC over the raw body and never binds the `shop` field to that HMAC.

### Title
Webhook shop-domain header not covered by HMAC verification allows cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` verifies the HMAC solely against that body [1](#0-0) . The `shop` accessor is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header and is never included in the signed content [2](#0-1) . `Registry.process` validates only the HMAC and then forwards `request.shop` unchanged as the tenant identifier to the app's handler [3](#0-2) .

### Finding Description
The equality the gem is supposed to guarantee is: `shop_identified_for_tenant_processing == shop_that_the_HMAC-verified_body_actually_originated_from`. That binding is broken because the HMAC in `HmacValidator.validate_signature` is computed over `verifiable_query.to_signable_string`, which for webhooks is just `@raw_body` [4](#0-3) [1](#0-0) . Since the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app, a valid `(body, hmac)` pair obtained from any one tenant (e.g., an attacker's own test/trial store) will validate successfully no matter what shop domain header is attached to the forged request. `Registry.process` raises only if `Utils::HmacValidator.validate(request)` is false [5](#0-4) , then immediately builds `WebhookMetadata` with `shop: request.shop` taken straight from the unauthenticated header [6](#0-5) . The documented API explicitly instructs app authors to treat `data.shop` as "The shop domain of the webhook" for tenant-scoped processing [7](#0-6) , making this a directly reachable trust boundary break rather than a documentation-ignoring misuse.

### Impact Explanation
An attacker who installs the app on their own (attacker-controlled) shop receives legitimate webhook deliveries with a valid HMAC computed using the app's shared `client_secret`. By replaying that exact body/HMAC pair while substituting the `x-shopify-shop-domain` header with a victim shop's domain, the attacker can make the app process attacker-controlled webhook data attributed to the victim tenant. Any app logic keyed off `data.shop` (e.g., looking up the victim's stored access token/session, updating victim-scoped local records, or triggering shop-scoped side effects) would then act on behalf of, or against, the victim shop — a cross-tenant access impact.

### Likelihood Explanation
Any developer/attacker can freely install the target app on their own shop (or a Shopify dev/trial store) to obtain valid, HMAC-signed webhook bodies signed with the app's real `client_secret`. Forging the HTTP header is trivial once a valid body+HMAC pair is captured, requiring no secrets belonging to the victim.

### Recommendation
Bind the shop domain into the HMAC-verified content, or independently authenticate it — for example, include the `shop` header value in `Request#to_signable_string`, or cross-check `request.shop` against a shop known to be legitimately registered/installed (with a valid stored access token) before trusting it as the processing tenant.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`.
2. Attacker triggers a webhook (e.g. `orders/create`) and captures the raw body and the resulting `x-shopify-hmac-sha256` header — both valid, since signed with the app's real `client_secret`.
3. Attacker resends the same body + HMAC header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks the body against the HMAC [8](#0-7) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)` [6](#0-5) , causing the app to process attacker-supplied data as if it came from the victim tenant.
