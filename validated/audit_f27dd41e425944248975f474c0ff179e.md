### Title
Webhook `shop-domain` header is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by HMAC-verifying only the raw request body, then dispatches the handler using the `shop` value taken from an unauthenticated header. Because the identity ("which shop this event belongs to") is not covered by the same signature that authenticates the payload, an attacker who controls one shop where the app is installed can capture a real, validly-signed webhook body and replay it with a forged `X-Shopify-Shop-Domain` header for a different (victim) shop. The gem will treat this as an authentic webhook for the victim shop.

### Finding Description
The equality the code should enforce is: `shop attributed to the event == shop bound by the HMAC signature`. Instead:

- `Utils::HmacValidator.validate` computes the signature exclusively over `to_signable_string`, which for webhooks returns only the raw body: [1](#0-0) 
- The `shop` accessor reads directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed content at all: [2](#0-1) [3](#0-2) 
- `Registry.process` only checks the HMAC over the body, then immediately forwards the unauthenticated `request.shop` value to the handler as the tenant identifier: [4](#0-3) 

Crucially, the HMAC secret (`Context.api_secret_key` / `client_secret`) is a single app-wide secret shared across every shop that installs the app — it is not shop-specific: [5](#0-4) 

This means "the body+HMAC pair is valid" only proves the payload came from Shopify (or someone with the app secret) for *some* shop with this app installed — it proves nothing about *which* shop, since the `shop-domain` header is never mixed into the signed material. Any actor who can install the app on a shop under their own control (a normal, unprivileged action) can trigger a genuine event (e.g. creating an order or updating a product) to obtain a real body + valid HMAC pair, then replay that exact pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `Registry.process` will pass HMAC validation (since only the body matters) and dispatch to the handler with `shop: "victim-shop.myshopify.com"`.

### Impact Explanation
This breaks the tenant boundary the gem is trusted to enforce: host applications key their session/data lookups off `WebhookMetadata#shop` (e.g., `Session.from(shop: ...)`/`offline_#{shop}` pattern seen throughout `lib/shopify_api/auth/session.rb` and `lib/shopify_api/utils/session_utils.rb`), relying on the webhooks subsystem to have authenticated that field. An attacker can inject falsely-attributed webhook events for a shop they do not own/control, causing the host app to act on forged data believing it originates from the victim's store — this is a cross-tenant data-integrity/confusion issue reachable purely through this gem's own webhook-processing code path, matching the "Critical: cross-tenant access" impact category.

### Likelihood Explanation
Any actor can freely create/install the target app on a shop they control (this is normal app-installation, not a privileged action), generate real webhook traffic, capture body+HMAC, and replay with a different `shop-domain` header value to the same publicly reachable webhook endpoint. No access token, `api_secret_key`, or credential theft is required — only observation of one's own legitimately delivered webhook and a header substitution in the replayed HTTP request. Likelihood is therefore high for any app that keys business logic off the `shop` field from `WebhookMetadata` without independent verification.

### Recommendation
Bind the identity field into the same signed material that authenticates the payload, or independently verify it: either (a) require the host-provided webhook secret/registration data to be looked up per-shop and mixed the shop domain into the HMAC input at generation time (not possible to change Shopify's wire format, so instead) (b) have `Registry.process`/`Webhooks::Request` cross-check `shop` against a shop that is known to have an active, registered webhook subscription matching the `webhook_id`/topic before dispatch, or (c) document/require host apps to validate `shop` independently (e.g., against an active installed-shop registry) rather than trusting the header outright, and treat `WebhookMetadata#shop` as unauthenticated input in the gem's own contract.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Attacker triggers a real event (e.g., updates a product) causing Shopify to deliver a webhook to the app's endpoint with a valid body and a correctly computed `X-Shopify-Hmac-Sha256` header (signed with the app's single shared `client_secret`).
3. Attacker intercepts/replays this exact HTTP request to the same endpoint, changing only `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unchanged) raw body against the (unchanged) HMAC — validation succeeds: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's real payload>, ...)`, and the host application processes it as an authentic event for the victim shop.

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
