### Title
Meta-transaction deposit refunds are misdirected to the delegate-action sender instead of the relayer who actually funded the deposit - (File: `runtime/runtime/src/actions.rs`)

### Summary
In NEP-366 meta transactions, the relayer prepays all attached deposits and gas for the inner actions on behalf of the delegate-action's `sender_id`. When the inner receipt executes and fails, nearcore's deposit-refund logic sends the refunded balance back to the `predecessor_id` of the failed receipt — which is the delegate-action's `sender_id` (e.g. "Alice") — rather than to the relayer who actually supplied the deposit. This mirrors the ZetaChain finding: the protocol refunds value to the immediate/nominal originator of the receipt rather than the party who actually contributed the funds, enabling that nominal party to capture funds it never owned.

### Finding Description
When a `DelegateAction` is unwrapped, `apply_delegate_action` builds a new `Receipt` with `predecessor_id: sender_id.clone()` (the delegate action's `sender_id`, e.g. Alice) while `signer_id`/`signer_public_key` remain the relayer's, and forwards it to `receiver_id` with the inner actions (which may carry an attached deposit funded entirely by the relayer): [1](#0-0) 

The code comment even states explicitly that the relayer prepays everything, but the deposit refund on failure goes to the predecessor (sender_id), not the relayer: [2](#0-1) 

The actual refund mechanism, `refund_unspent_gas_and_deposits`, confirms this: on failure the entire attached deposit is refunded via `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)`, which routes to the receipt's `predecessor_id` (Alice), while only the *gas* portion is refunded to `action_receipt.signer_id()` (the relayer): [3](#0-2) 

`Receipt::new_balance_refund` and `Receipt::new_gas_refund` show the split explicitly — deposit refunds go to whatever `receiver_id` is passed (the predecessor of the failed receipt), gas refunds go to `signer_id`: [4](#0-3) 

The project's own architecture documentation names this exact scenario and its financial-incentive risk: [5](#0-4) 

This is structurally identical to the ZetaChain bug class: a value-forwarding intermediary (the relayer, analogous to the "intermediary contract" fronting ERC-20 funds) has its funds attributed to a different, unprivileged party (Alice/`sender_id`, analogous to the EOA `msg.sender`/tx signer) for refund purposes. If the receiver-side receipt fails, the refund goes to the wrong account and can be “stolen” by the party who never actually funded it.

### Impact Explanation
A malicious `sender_id` (Alice) can sign a `DelegateAction` containing an action with a large attached deposit and craft the receiver/action such that execution predictably fails on the receiver's shard (e.g., failing a precondition, insufficient storage stake, receiver contract logic that reverts, etc.), while the relayer pays for and attaches the deposit believing it will be delivered to the receiver. When the action fails, the deposit is refunded to Alice (the `predecessor_id`) instead of the relayer who supplied it — resulting in Alice extracting tokens that were never hers, at the relayer's expense. This is a genuine unauthorized balance transfer / token theft vector reachable purely through a submitted meta-transaction, matching "concrete token theft" and "unauthorized balance change" impact criteria.

### Likelihood Explanation
This requires a relayer that funds deposits for inner delegate actions on behalf of a user it does not fully trust — a normal and encouraged use case for meta-transactions/relayer services (e.g., relayers subsidizing users, or intermediary/aggregator relayer contracts servicing many users). The trigger conditions (attach a deposit, make the receiver-side action fail) are entirely controllable by the delegate-action's `sender_id`, requiring no special privileges, validator status, or network-layer access — only a normal signed transaction submission. The nearcore team is aware of this at a documentation level (it is called out in `docs/architecture/how/meta-tx.md`) as a relayer trust caveat, but the runtime code has no on-chain mitigation (no per-inner-action deposit refund routed to the actual depositor, no requirement that relayers escrow/verify before it is too late).

### Recommendation
Route deposit refunds for actions originating from a `DelegateAction`'s prepaid deposit to the relayer (the outer transaction `signer_id`) rather than to the inner `sender_id`/`predecessor_id`, or otherwise clearly separate "delegate-funded deposit" attribution from `predecessor_id` so refund semantics track the actual value provider. At minimum, since this is a documented trust assumption rather than a code defect being newly discovered, ensure relayer implementations enforce collateral/escrow so an untrusted `sender_id` cannot cause the relayer to lose attached deposits through predictable failures.

### Proof of Concept
1. Relayer R receives a `SignedDelegateAction` from user A (`sender_id = A`, `receiver_id = B`) containing an inner action with a large attached deposit (e.g., a `FunctionCall` with `deposit = X` NEAR), which R funds by wrapping it in a transaction it signs and pays gas/deposit for.
2. R submits the transaction; `apply_delegate_action` creates a new receipt with `predecessor_id = A`, `receiver_id = B`, forwarding the inner action with deposit X (`runtime/runtime/src/actions.rs:483-497`).
3. A ensures (in collusion, or simply by picking a receiver/method call it knows will fail, e.g., a contract method that reverts on some easily-triggerable condition) that action execution on B's shard fails.
4. `refund_unspent_gas_and_deposits` refunds the full deposit X via `Receipt::new_balance_refund(receipt.balance_refund_receiver(), X)`, which resolves to `predecessor_id = A` (`runtime/runtime/src/lib.rs:1346-1353`, `core/primitives/src/receipt.rs:496-510`).
5. A receives X tokens that were paid entirely by relayer R; R receives nothing back for the lost deposit (only gas is separately refunded to R as `signer_id`).

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
