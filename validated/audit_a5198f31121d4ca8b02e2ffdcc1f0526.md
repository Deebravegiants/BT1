Line 476 (`if (order.inputs.length != outputsLen) revert InvalidInput();`) enforces `order.inputs.length == order.output.assets.length`, but there is no check that `outputsLen > 0` or that any individual `order.output.assets[i].amount` is non-zero. Since `placeOrder` also does not reject an order whose `output.assets` array is empty or whose entries are all zero-amount (it only checks `order.inputs.length == 0` and rejects duplicate output tokens), a user can place an order with `output.assets = []` (and therefore `inputs.length == 0`... but `inputs.length == 0` is itself rejected) — however a user *can* set `output.assets` to a single zero-amount entry, keeping `inputs.length == outputsLen == 1`.

In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:65-119`), for each output index `i`: `totalRequired = order.output.assets[i].amount` (attacker-chosen as 0), `alreadyFilled = 0`, so `remaining = 0`. The loop hits `if (remaining == 0 || solverAmount == 0) { ...; continue; }` immediately — `isFullyFilled` stays `true`, and `escrowedInputs[i]` is left as the zero-initialized default `TokenInfo` rather than the actual escrowed input amount (`_orders[commitment][token]`). The function then proceeds to `_withdraw(body, false, isFullyFilled)` with `isFullyFilled == true`, and separately calls `_execute(order, outputsLen)`, treating the order as fully and legitimately filled without the filler ever having transferred anything (`msgValue` stays `0`, no `safeTransferFrom` call occurs because the loop `continue`d before those lines).

This mirrors the reported bug class exactly: an aggregate/loop-driven fill-completion flag (`isFullyFilled`, analogous to Yolo's `expectedValue == msg.value` check) is derived without validating that each individual required amount is non-zero, letting a caller satisfy "full fill" for zero cost and claim the reward (here, the input escrow and any attached `_execute` calldata) reserved for a genuine filler.

I was not able to fully trace `_withdraw`'s exact release amount when `escrowedInputs[i].amount == 0` (i.e., whether it releases `0` tokens — in which case impact is limited to `_execute`/`OrderFilled` semantics rather than fund theft — or whether some other accounting path releases the true escrowed amount for that token elsewhere). Confirming whether the user could set `order.output.assets[i].amount = 0` on a *non-zero-value* order and still walk away with the escrowed input requires reading the full `_withdraw` implementation and the order-placement invariants (whether `placeOrder` allows `output.assets` amounts of 0) in `evm/src/apps/intentsv2/IntentsBase.sol`, which I did not fully retrieve.

### Title
Zero-required-output leg lets a filler claim `isFullyFilled` and drain escrow/execute calldata for free - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntentGatewayV2.fillOrder` only checks that `order.inputs.length == order.output.assets.length` [1](#0-0) ; it never checks that `outputsLen > 0` or that individual output amounts are non-zero, and `placeOrder` performs no such check either [2](#0-1) . `_fillSameChain` treats a leg with `totalRequired == 0` as automatically satisfied and continues the loop without requiring any transfer from the solver [3](#0-2) .

### Finding Description
The fill loop computes, per output leg `i`:
```
uint256 totalRequired = order.output.assets[i].amount;
uint256 solverAmount = options.outputs[i].amount;
uint256 alreadyFilled = _partialFills[commitment][outputToken];
uint256 remaining = totalRequired - alreadyFilled;
if (remaining == 0 || solverAmount == 0) {
    if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
    continue;
}
``` [3](#0-2) 
If `totalRequired == 0` (a user-chosen output requirement of zero), `remaining` is `0` for every caller regardless of `solverAmount`, so the branch is entered and the loop `continue`s without transferring any token to the beneficiary and without updating `isFullyFilled` to `false`. `isFullyFilled` is initialized to `true` and never flipped for this leg [4](#0-3) . The rest of the function proceeds as if the order were genuinely and fully filled, calling `_withdraw(body, false, isFullyFilled)` and `_execute(order, outputsLen)` and emitting `OrderFilled` [5](#0-4) . This is structurally identical to the YoloV2 bug: an aggregate/loop-derived success condition (`expectedValue == msg.value` in Yolo, `isFullyFilled` here) is computed without validating that each individual per-item amount is non-zero, letting an attacker satisfy the aggregate condition for free and claim a reward gated by it.

### Impact Explanation
An attacker who places (or can induce placement of) an order with an output leg whose required amount is `0` can call `fillOrder` supplying `0` for that leg, causing the gateway to mark the order as fully filled and to run `_execute` (arbitrary attached output calldata) and release/withdraw escrow, without providing any of the value that a legitimate solver would have to supply. This can result in theft/misappropriation of escrowed input funds or unauthorized execution of attached calldata — a concrete fund-safety violation reachable from a single unprivileged `fillOrder` call.

### Likelihood Explanation
Reachable by any unprivileged caller who places an order (or is the order's own creator) with a `0`-amount output leg and then calls `fillOrder` — no special privileges, proofs, or governance actions are required. The only gate is `placeOrder`'s duplicate-output-token check, which does not reject zero-amount outputs [6](#0-5) .

### Recommendation
In both `_fillSameChain` and `_fillCrossChain`, reject orders/legs where `order.output.assets[i].amount == 0` — either enforce this at `placeOrder` time (revert if any output asset amount is `0`) or explicitly treat a `totalRequired == 0` leg as not contributing to `isFullyFilled` unless it was never a real requirement, and ensure `escrowedInputs[i]` is only released for legs that were actually paid for.

### Proof of Concept
1. User calls `placeOrder` with `inputs = [{token: USDC, amount: X}]` and `output.assets = [{token: DAI, amount: 0}]` (single leg, zero requirement) — accepted because `placeOrder` never checks output amounts are non-zero [6](#0-5) .
2. Any caller (the attacker) calls `fillOrder(order, options)` with `options.outputs = [{token: DAI, amount: 0}]`. Length checks pass (`inputs.length == outputsLen == 1`) [1](#0-0) .
3. Inside `_fillSameChain`, `totalRequired = 0`, `remaining = 0`, so the loop `continue`s immediately; no token transfer occurs, but `isFullyFilled` remains `true` [3](#0-2) .
4. `_execute(order, outputsLen)` runs and `_withdraw`/`OrderFilled` are triggered as though the order were legitimately and fully filled, at zero cost to the caller [5](#0-4) .
