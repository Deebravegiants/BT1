### Title
Unvalidated `walletAccount` object parameter allows signing/key-selection with an arbitrary `seedId` bypassing enabled-account authorization - (File: `features/tx-signer/src/api/index.ts`, `features/message-signer/src/module/message-signer.ts`)

### Summary
The Astaria bug's root cause is that a caller-supplied struct field (`StrategyDetailsParam.vault`) is trusted as the authoritative source-of-truth for a privileged operation (which vault's asset to use) without validating it against the vault actually being invoked. The analogous pattern in this codebase is that the transaction/message signing APIs accept a `walletAccount` parameter that can be either a plain string (safely resolved against the wallet's own `walletAccountsAtom`) or a full `WalletAccount`-shaped object, which is used **as-is** without validating it against the set of accounts actually enabled/known to the SDK instance.

### Finding Description
`createTransactionSignerApi` in [1](#0-0)  only performs a lookup against `walletAccountsAtom` when `params.walletAccount` is a `string`. If the caller instead passes an object, it is forwarded unchanged to `transactionSigner.signTransaction`:
```
const walletAccount =
  typeof params.walletAccount === 'string'
    ? await getWalletAccount(params.walletAccount)
    : params.walletAccount
```
The same pattern exists in `MessageSigner.#normalizeWalletAccount` in [2](#0-1) , which only resolves via `#walletAccountsAtom` for string inputs and returns any provided object verbatim.

Downstream, the object's `seedId` field is used directly to select key material in the keychain, with no re-check that this `seedId` corresponds to the enabled walletAccount for that name/index:
- `SeedBasedTransactionSigner.#getSignerForWalletAccount` pulls `walletAccount.seedId` straight from the object and uses it for all keychain operations: [3](#0-2) 
- `SeedBasedMessageSigner.signMessage` similarly uses `walletAccount.seedId` directly to build the signer that calls `keychain.signBuffer`: [4](#0-3) 
- The keychain itself performs no cross-check that a `seedId` belongs to a currently enabled/known wallet account — it simply looks up whatever seed was previously added via `addSeed`/`addExternalPrivateKey`: [5](#0-4) , [6](#0-5) 

This is structurally identical to the Astaria flaw: a field embedded in an attacker-influenced parameter (`walletAccount.seedId`, analogous to `StrategyDetailsParam.vault`) is trusted implicitly by the signing pipeline for a security-critical selection (which private key material to use) instead of being independently re-derived/validated from the SDK's own authoritative state (`walletAccountsAtom`/`enabledWalletAccountsAtom`).

### Impact Explanation
If any caller in the trust chain — including feature code, RPC-exposed API surfaces, or another loaded module — can pass a `WalletAccount`-shaped object rather than the plain string name expected by the "safe" lookup path, the effective identity/key-derivation used for signing is determined by attacker-controlled data rather than the wallet's own enabled-account/keychain state. Because `keychain.signBuffer`/`getPublicKey` derive the signing key purely from `seedId` + `keyId` with no ownership check tying it back to `walletAccount.toString()`/`enabledWalletAccountsAtom`, a mismatch between the claimed `walletAccount` (index, name) and its embedded `seedId` would not be caught, and a transaction/message could be signed against a seed that is not the one the caller/UI believes is in use. This is a "confused deputy" pattern for signing operations analogous to the vault confusion in Astaria, and if reachable from an untrusted call site (e.g., a compromised or malicious feature/module composed into the IoC container, or a dApp-facing API that forwards structured input instead of the plain string identifier) it results in unauthorized use of key material / signature with the wrong account.

### Likelihood Explanation
Exploitability depends on whether any reachable API surface actually forwards a raw, externally-influenced object into `walletAccount` instead of the safe string form. From the code available in the index, the documented public consumer-facing entry points (`exodus.messageSigner.signMessage`, `exodus.transactionSigner.signTransaction`, and provider docs like `docs/web3-providers/*`) show usage with a `walletAccount` string or an internally-constructed `WalletAccount` instance, and internal callers such as `features/assets-feature/client/asset-client-interface.js:361-365` resolve the name safely via `#getWalletAccount` before calling the signer. I could not confirm, within the indexed files, a concrete externally-triggerable (dApp/RPC) code path that supplies a raw attacker-controlled object to these APIs — this would require checking every module that composes `transactionSigner`/`messageSigner` for full traceability, which may exceed the indexed content available to Ask. This should be verified with a full-repository session before concluding definite exploitability.

### Recommendation
In `createTransactionSignerApi` and `MessageSigner.#normalizeWalletAccount`, always re-resolve the wallet account from the authoritative `walletAccountsAtom`/`enabledWalletAccountsAtom` by its stable identifier (name/index), regardless of whether the input was passed as a string or an object, and reject/ignore any caller-supplied `seedId`/`source`/`index` fields that don't match the trusted stored record. This mirrors the Astaria fix of enforcing `address(this) == params.lienRequest.strategy.vault` — i.e., enforce `resolvedAccount.seedId === trustedAccount.seedId` (and other identity fields) before invoking `keychain.signBuffer`.

### Proof of Concept
Not executed — this is a code-review-level finding based on statically tracing the parameter flow:
1. `transactionSignerApi.signTransaction({ walletAccount: { source: 'seed', index: 0, seedId: '<victim-or-arbitrary-seedId>' }, ... })` — object form bypasses the `walletAccountsAtom` lookup entirely ( [7](#0-6) ).
2. `TransactionSigner.signTransaction` routes based on `walletAccount.isSoftware`/`isHardware` computed from the object, then calls `SeedBasedTransactionSigner.signTransaction` ( [8](#0-7) ).
3. `#getSignerForWalletAccount` extracts `seedId` directly from the untrusted object and calls `keychain.signBuffer({ seedId, keyId, ... })` ( [9](#0-8) ), with no check that this `seedId` matches the record for that walletAccount name in `walletAccountsAtom`.

A full runnable PoC would require constructing a test harness (similar to `features/message-signer/src/module/__tests__/index.test.ts`) that supplies an object with a `seedId` differing from the one stored under the target account name, and verifying that the keychain signs against the untrusted `seedId`.
