### Title
Webhook shop-domain and topic are not covered by the HMAC signature, allowing tenant-spoofed webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` only feeds the raw HTTP body into HMAC verification, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated headers and passed straight through to the app's `WebhookHandler`. Since the HMAC secret (`api_secret_key`) is shared by the app across *all* installing shops, a valid signature only proves "this body was HMAC'd with this app's secret" — it proves nothing about which shop or topic the body belongs to. This breaks the intended binding `hmac_valid(body) == (shop, topic, body) actually originated together from Shopify`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only from `to_signable_string` (the body) and compares it against the received HMAC using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` validates only that HMAC, then immediately builds `WebhookMetadata` — trusting `request.shop` and `request.topic` as if they were verified together with the body — and dispatches it to the host app's handler: [4](#0-3) 

`WebhookMetadata` bundles `topic`, `shop`, and `body` as a single struct the handler trusts as an atomic, verified unit: [5](#0-4) 

Because `api_secret_key` is one shared secret for the entire app (identical across every shop that installs it), any party who can obtain one genuine, validly-signed webhook body from Shopify for *any* shop (e.g., their own free development store) possesses a `(raw_body, hmac)` pair that will pass `HmacValidator.validate` regardless of which `shop-domain`/`topic` header accompanies it. The equality the gem should enforce — `hmac_covers(shop, topic, body) == true` — is instead only `hmac_covers(body) == true`, with `shop` and `topic` unauthenticated. An attacker can therefore replay/relay the same signed body while substituting an arbitrary `x-shopify-shop-domain` header naming a victim tenant; `Registry.process` will pass this forged `WebhookMetadata` (with the victim's shop but attacker-supplied/attacker-obtained body) to the handler as if Shopify itself attested to that combination.

### Impact Explanation
This is a cross-tenant identity-binding failure inside the gem's own webhook-verification code path (not a host-app misuse): the library asserts a webhook is authentic and hands the handler a `shop` value that was never actually verified. A host app that relies on the documented `ShopifyAPI::Webhooks::Registry.process` / `WebhookMetadata.shop` contract (as instructed in the gem's own webhook docs) to attribute incoming data to a tenant can be made to process attacker-supplied/replayed data under a victim shop's identity, i.e., cross-tenant access facilitated by the gem's verification logic.

### Likelihood Explanation
Requires an attacker to have received at least one genuine webhook (trivial — install the app on any shop, including a free/dev store, and trigger any webhook topic) and the ability to POST to the app's public webhook endpoint with modified headers — both are unprivileged, no leaked credentials, access tokens, or `api_secret_key` knowledge needed.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable payload used for HMAC verification (or otherwise cryptographically bind them to the body/signature), so a valid signature attests to the full tuple that `WebhookMetadata` exposes to handlers, not just the raw body bytes.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw request: headers `x-shopify-hmac-sha256: <H>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, and body `B`. `H` is `HMAC-SHA256(api_secret_key, B)` — valid because it only signs `B` (`lib/shopify_api/webhooks/request.rb` `to_signable_string` / `lib/shopify_api/utils/hmac_validator.rb`).
2. Replay the exact same body `B` and HMAC `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header as `shop` (`lib/shopify_api/webhooks/request.rb:21-23`); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which still passes because it only checks `B` against `H` (`lib/shopify_api/webhooks/registry.rb:190`).
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` and invokes the app's handler, which now processes attacker-controlled/replayed data as if it were verified data belonging to `victim.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:198-199`, `lib/shopify_api/webhooks/webhook_handler.rb:6-12`).

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
