### Title
Unchecked UTF-8 conversion of attacker-controlled request body causes undefined behavior in `pallet-ismp-demo::IsmpModuleCallback::on_accept` - (File: `modules/pallets/demo/src/lib.rs`)

### Summary
`IsmpModuleCallback::on_accept` builds an event payload from an incoming ISMP `PostRequest` body using `String::from_utf8_unchecked`, which skips UTF-8 validation entirely. This is directly analogous to CVE-2017-7522, where OpenVPN failed to validate an externally supplied string (a certificate field) before treating it as a well-formed C string, leading to a crash. Here, a relayer delivering a message from an EVM source can submit an arbitrary byte sequence as `request.body`; because this is dispatched from `EvmHost`/`HandlerV2` message delivery through `ProxyModule::on_accept` into the pallet without any validation, the pallet constructs a `String` that violates Rust's UTF-8 invariant.

### Finding Description
In `modules/pallets/demo/src/lib.rs`:
```rust
StateMachine::Evm(_) => Pallet::<T>::deposit_event(Event::Request {
    source: source_chain,
    data: unsafe { String::from_utf8_unchecked(request.body) },
}),
``` [1](#0-0) 

`request.body` is fully attacker-controlled: any relayer or message submitter can construct a `PostRequest` with `from = <EVM source module>`, `to = pallet_ismp_demo::PALLET_ID` (`b"ismp-ast"`), `source = StateMachine::Evm(_)`, and an arbitrary `body`, and deliver it through the normal EVM→Substrate ISMP message pipeline (`HandlerV2` on the EVM side, routed on the destination through `ProxyModule::on_accept`, which resolves the destination module and forwards to `IsmpModuleCallback::on_accept` when `to == pallet_ismp_demo::PALLET_ID`): [2](#0-1) 

`String::from_utf8_unchecked` is `unsafe` precisely because callers must guarantee the input is valid UTF-8; the compiler and every downstream consumer of `String` (including SCALE `Encode`, string formatting, and any future code operating on `.as_bytes()`/`.chars()`) relies on that invariant holding. Supplying invalid UTF-8 (e.g., a lone continuation byte, an overlong encoding, or bytes that form a truncated multi-byte sequence — the same "malformed/embedded-invalid-byte" bug class as CVE-2017-7522's embedded NULL in a certificate) produces a `String` whose bytes are not guaranteed valid UTF-8, which is undefined behavior in Rust. This is a real regression relative to the rest of the codebase's careful handling of untrusted byte-to-string conversions elsewhere (e.g. the `StateMachine::from_str`/`Display` paths and `as_utf8_string` serde adapter in `modules/utils/serde/src/lib.rs`, both of which were hardened specifically because "this runs on untrusted... input, so it must never panic"). [3](#0-2) 

### Impact Explanation
The consequence is undefined behavior triggered by fully unprivileged, external, attacker-controlled input reaching a live parachain runtime (`gargantua-runtime`, `nexus-runtime` via `pallet-ismp-demo`). Depending on optimizer behavior and how the malformed `String` is subsequently consumed (event encoding, RPC serialization of events, or any string operation performed on it), this can manifest as a runtime panic (denial of service, halting block production or the node process) or, in the worst case, memory corruption, since UB is not confined to a "safe" fallback the way the rest of the codebase now guarantees. This matches the "resulting in a route unable to deliver messages" / DoS impact class called out as in-scope.

### Likelihood Explanation
Likelihood is high: dispatching a `PostRequest` with attacker-chosen body bytes is the normal, permissionless act of relaying an ISMP message from any EVM source chain — no privileged role, governance action, or special relayer status is required. The vulnerable code path is reached on every message delivered to the `ismp-ast` module id, and the codebase's own regression tests for adjacent code (`as_utf8_string_rejects_non_four_byte_input`, `from_str_rejects_non_four_byte_consensus_ids`) show this exact "untrusted bytes → string" bug class has previously caused a production node crash, underscoring that it is realistically triggerable.

### Recommendation
Replace `String::from_utf8_unchecked(request.body)` with a checked conversion, e.g. `String::from_utf8(request.body).map_err(...)` and reject (or lossily substitute, matching the pattern already used in `StateMachine::Display`) invalid UTF-8 rather than invoking undefined behavior.

### Proof of Concept
1. As any account with access to the EVM ISMP host, dispatch a `PostRequest` via `HandlerV2`/`EvmHost` with:
   - `source = StateMachine::Evm(<any registered EVM chain id>)`
   - `to = b"ismp-ast"` (the wire-form bytes of `pallet_ismp_demo::PALLET_ID`)
   - `body = [0x80]` (a single stray UTF-8 continuation byte — invalid UTF-8, analogous to an embedded malformed byte in a certificate string)
2. Relay this message to the destination Substrate chain (`gargantua`/`nexus`) through the standard message delivery pipeline.
3. `ProxyModule::on_accept` resolves `to` to `pallet_ismp_demo::PALLET_ID` and forwards to `IsmpModuleCallback::on_accept`.
4. `String::from_utf8_unchecked(vec![0x80])` executes, producing a `String` backed by invalid UTF-8 bytes — undefined behavior, which the Rust compiler is entitled to miscompile around or which will corrupt any downstream logic that trusts the `String` invariant (e.g. panicking when re-validated, or corrupting encoded event data).
