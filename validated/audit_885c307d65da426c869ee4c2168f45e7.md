### Title
Webhook shop-domain header is trusted for tenant identification but not covered by HMAC verification - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant identity) used by webhook handlers from an unauthenticated HTTP header, while the HMAC signature that this gem verifies covers only the raw request body. Since the app's `client_secret`/`api_secret_key` used to compute this HMAC is the same across every shop that has installed the app, any shop that has installed the app can produce a validly-signed webhook body and then have it delivered/replayed with a spoofed `shop-domain` header pointing at a different (victim) shop, and `Utils::HmacValidator.validate` will still accept it.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; none of the Shopify headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included in the signed data. `shop` is read straight from an HTTP header with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string` (i.e., the raw body) and the app's `api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, then builds `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, and `request.parsed_body`, handing this tenant identity straight to the app's registered handler: [4](#0-3) 

The identity binding that should hold is: `shop_that_produced_the_HMAC == shop_the_handler_believes_sent_the_webhook`. Because the header carrying the second value is not part of the signed bytes, this equality is never enforced by the gem — it only proves "some shop with a valid Shopify HMAC secret sent this body," not "this specific shop sent this body." Since the HMAC secret (the app's `client_secret`) is shared across all shops that installed the app, a merchant/attacker who has installed the target app on their own store can obtain a genuinely-signed webhook (e.g., by triggering an event on their own shop, or via any actor who can reach the app's webhook endpoint with a valid signature for arbitrary self-controlled body content) and then submit it with the `shop-domain`/`x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` passes because it never inspected the shop header, and the handler processes attacker-controlled data as if it originated from the victim tenant.

### Impact Explanation
This breaks the tenant-authentication boundary that a webhook handler relies on: the gem hands the host application a `shop` value that appears HMAC-verified (because `process` calls `HmacValidator.validate` before invoking the handler) but is actually unauthenticated attacker input. Any app logic that trusts `WebhookMetadata#shop` for per-tenant data writes, cache invalidation, credential/session lookups, or state changes can be manipulated cross-tenant by a party who legitimately installed the app on any shop. This matches the "cross-tenant access" impact category, since it enables one tenant to inject data attributed to another tenant.

### Likelihood Explanation
Exploitation requires only that the attacker have (or create) a shop with the target app installed — a standard, unprivileged action — and the ability to send an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header, which is entirely within reach of an unprivileged actor and does not require the app's `client_secret`, an access token, or any credential theft.

### Recommendation
Bind the shop identity into the verified signature space: include the `shop-domain` (and ideally `topic`, `webhook-id`) header value in `to_signable_string`, or otherwise cryptographically bind the claimed shop to the payload before trusting `request.shop` in `Registry.process`, so that a valid HMAC for one shop cannot be replayed/relabeled as originating from another shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, giving Shopify's platform (not the attacker) a genuine app-secret-signed webhook for any event on that shop, e.g. `orders/create` with body `B`.
2. Attacker intercepts/replays this webhook request to the app's endpoint but rewrites the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`, keeping the original `x-shopify-hmac-sha256` header and body `B` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: spoofed_headers)` builds successfully; `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `B` using the shared `api_secret_key`, ignoring the shop header — see [5](#0-4)  and [6](#0-5) .
4. `Registry.process` proceeds to invoke the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` — see [7](#0-6) , causing the app to process attacker-supplied data as belonging to `victim-shop`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
