The webhook `hmac` signature is computed only over the raw request body via `to_signable_string` returning `@raw_body`, while the `shop` field (from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is read separately and passed unauthenticated into the handler.### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `ShopifyAPI::Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) authenticates the request body but never authenticates the `shop` value read from the `x-shopify-shop-domain`/`shopify-shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb`) trusts this unauthenticated `shop` header and forwards it to the app's `WebhookHandler#handle` via `WebhookMetadata` (`lib/shopify_api/webhooks/webhook_handler.rb`), which apps use to key per-tenant data.

### Finding Description
The identity binding broken here is: `hmac(raw_body, api_secret_key)` should equal an authenticated statement of "this event body belongs to shop S", but the gem only proves `hmac == HMAC(raw_body, secret)`; it never binds `shop` into that computation.

- `Request#hmac` decodes the `x-shopify-hmac-sha256` header and `Request#to_signable_string` returns just `@raw_body`: [1](#0-0) [2](#0-1) 
- `Request#shop` is read straight from the `shop-domain` header with no cryptographic tie to the HMAC: [3](#0-2) 
- `HmacValidator.validate`/`validate_signature` only ever hash `verifiable_query.to_signable_string` (i.e. the body), never the shop header: [4](#0-3) 
- `Registry.process` accepts the request once the body-only HMAC passes, then hands the header-derived, unauthenticated `request.shop` straight to the merchant's handler: [5](#0-4) 

Because the same `api_secret_key` is shared by the app across all installed shops, any body+HMAC pair that is valid for one tenant is also a valid signature for that same body under a *different* `shop` header — the signature says nothing about which shop it belongs to. This is exactly the class of bug the reference finding describes: a field acted on (`shop`, used for tenant routing) but not covered by the HMAC (which only covers `raw_body`).

### Impact Explanation
An unprivileged user who installs the app on their own shop (Tenant A) legitimately receives correctly-HMAC-signed webhooks addressed to the app's single shared webhook endpoint. Tenant A can capture one such `(raw_body, hmac)` pair from their own shop, then resend it to the app's webhook endpoint with the `x-shopify-shop-domain`/`shopify-shop-domain` header rewritten to Tenant B's (victim) domain. `HmacValidator.validate` still succeeds because it never checked the shop header, and `Registry.process` dispatches the forged event with `WebhookMetadata#shop == "tenant-b.myshopify.com"` and attacker-controlled `body`. Any app logic keyed on `data.shop` (order/customer sync, redact handling, billing/inventory updates, etc.) processes attacker-supplied data under the victim tenant's identity — a cross-tenant data-integrity/authentication-boundary violation.

### Likelihood Explanation
The attacker needs only their own legitimate app installation (no privileged credentials, no access token, no `api_secret_key`) — install the app, capture one webhook payload sent to the shared endpoint, and replay it with a modified header. This is directly reachable by any unprivileged Shopify merchant/user of the host app.

### Recommendation
Bind the `shop` (and ideally `topic`, `api-version`) into the signed material that `HmacValidator` checks, or otherwise cryptographically verify the shop header value against the HMAC-covered body/context before trusting `request.shop`, so a valid signature for one shop's payload cannot be replayed under a different shop's identity.

### Proof of Concept
1. App is installed on `attacker.myshopify.com`; the shared endpoint receives a legitimate webhook: body `{"id":1}"`, header `x-shopify-shop-domain: attacker.myshopify.com`, header `x-shopify-hmac-sha256: <valid HMAC of body>`.
2. Attacker resends the identical raw body and HMAC to the app's webhook endpoint, only replacing the header to `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only recomputes HMAC over `raw_body` (unchanged) — see `lib/shopify_api/utils/hmac_validator.rb` lines 26-31 and `lib/shopify_api/webhooks/request.rb` lines 35-38.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: {"id":1}, ...)`, so the app processes attacker-controlled data as if it originated from the victim shop.
