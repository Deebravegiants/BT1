## Finding

### Title
Front-running `permit()`/`Permit2.permitTransferFrom` signatures allows DOS of `SimplexPaymaster` UserOps and solver bids - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` executes an EIP-2612 `permit()` call (mode `0x00`) or a `Permit2.permitTransferFrom` call (mode `0x02`) using a signature embedded in `paymasterData`, which is visible in the mempool before the UserOp is included. Both calls are permissionless (callable by anyone holding the signature), so an attacker can front-run the paymaster's own call with the exact same signature, consuming the EIP-2612 nonce or the Permit2 nonce bitmap slot. When the paymaster's `_validatePaymasterUserOp`/`_prefund` subsequently attempts the same call, it reverts, and the contract's `try/catch` unconditionally re-reverts (`PermitFailed`/`Permit2Failed`) instead of checking whether the resulting allowance/authorization already suffices. This DOSes the underlying UserOp — either a solver's first-time chain delegation (mode 0) or a sponsored bid (mode 2).

### Finding Description
`_executePermit` calls `IERC20Permit(tokenAddr).permit(...)` inside a `try/catch` that reverts `PermitFailed` on any failure, with no fallback check of the resulting allowance: [1](#0-0) 

Similarly, `_prefund`'s Permit2 branch calls `PERMIT2.permitTransferFrom(...)` with the signature taken straight from `paymasterData`, and reverts `Permit2Failed` unconditionally on failure: [2](#0-1) 

Both `permit()` and `Permit2.permitTransferFrom` are permissionless functions — any address can submit the same `(owner, spender, value/permitted, deadline, v, r, s)` tuple once it is observable (e.g., in the mempool as part of a pending UserOp/bundler submission, or the transaction that carries it). An attacker who copies the signature and submits it first consumes the EIP-2612 nonce or the Permit2 nonce bitmap bit ahead of the paymaster's own call. The paymaster's subsequent identical call then reverts because the nonce/bitmap slot is already spent, and since there is no check of whether the allowance/authorization already exists or is otherwise sufficient (no try/catch fallback logic as recommended by the referenced report), the whole UserOp validation reverts.

This is the same bug class as the reported `privateMint()`/`selfPermit()` DOS: a signature intended to authorize the caller's own transaction is trivially replayable by any third party to burn its nonce and grief the legitimate flow.

Notably, the project's own decision log explicitly acknowledges this exact consequence was accepted rather than mitigated when APPROVE mode was removed: "a front-run permit still loses the bid, and no allowance fallback was added to `_executePermit` because that would be APPROVE by the back door" [3](#0-2) 

### Impact Explanation
An attacker monitoring pending UserOps can grief a solver's sponsored bid or first-time chain delegation by front-running the permit/Permit2 signature, causing `_validatePaymasterUserOp`/`_prefund` to revert and the UserOp to fail. This directly targets the intent solver/bid flow explicitly documented as in scope ("intents escrow and bids"): a solver's bid UserOp using mode `0x02` Permit2 authorization can be forced to fail by a third party who never needed the solver's private key, just the observable signature. Repeated targeting can degrade a solver's ability to win bids on Hyperbridge, or block a solver's onboarding (mode `0x00` delegation bootstrap) on a chain, requiring resignature each time.

### Likelihood Explanation
Likelihood is medium: the attacker only needs to observe the pending calldata (mempool or bundler submission) and race a transaction against the paymaster's own inclusion — no privileged access, key compromise, or governance role is required. Both code paths (`_executePermit` and the Permit2 branch of `_prefund`) are reachable by any UserOp sender attempting to use `SimplexPaymaster`.

### Recommendation
Before reverting on a failed `permit()`/`permitTransferFrom` call, check whether the resulting state already satisfies the requirement (e.g., for mode `0x00`, check `IERC20(tokenAddr).allowance(owner, address(this)) >= permitAmount` after a failed permit and proceed if so, per the referenced remediation of "if the current allowance is bigger than the spending amount allow logic to be executed"). For Permit2, since nonces are single-use by design, consider allowing the bundler/paymaster to detect a pre-consumed nonce and treat it as already-authorized when the front-run transfer already delivered funds to the correct recipient, or otherwise document/require a per-attempt retry path (fresh nonce) as an accepted mitigation rather than a hard failure that must propagate all the way to UserOp rejection.

### Proof of Concept
1. Solver signs an EIP-2612 permit (or Permit2 transfer authorization) naming `SimplexPaymaster` as spender and submits a UserOp with `paymasterData` mode `0x00` (or `0x02`) containing `(v, r, s)`.
2. Attacker observes the pending UserOp/bundler submission and extracts `(owner, value/permitted, deadline, v, r, s)`.
3. Attacker submits a plain transaction calling `token.permit(owner, SimplexPaymaster, value, deadline, v, r, s)` (or `Permit2.permitTransferFrom(...)` with the same signature) directly, which lands first and consumes the nonce/bitmap slot.
4. The bundler's `handleOps` call reaches `_validatePaymasterUserOp` → `_executePermit` (or `_prefund`'s Permit2 branch); the paymaster's own `permit`/`permitTransferFrom` call now reverts because the nonce is already used.
5. The `catch` block unconditionally reverts (`PermitFailed`/`Permit2Failed`), failing the solver's UserOp even though the intended party (or nobody) already has/could have the required authorization state.
