### Title
Webhook `shop-domain` Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (tenant identifier) is read from an HTTP header that is never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` trusts this unsigned `shop` value when invoking the app's webhook handler, so an attacker who can obtain one genuinely-signed webhook body (e.g. by installing the app on their own store) can replay that body with a different `shop-domain` header value and have it processed as if it came from a different (victim) tenant.

### Finding Description
The binding that should hold is:
`hmac_valid(body, secret) == true` **and** `shop_header == shop_that_the_HMAC_authenticates`

but the gem only enforces the first half.

- `Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 
- `Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is not part of the signed string: [2](#0-1) 
- `HmacValidator.validate` verifies the signature purely as a function of `to_signable_string` (i.e., the body) and the secret, never touching headers: [3](#0-2) 
- `Registry.process` validates the HMAC, then immediately trusts `request.shop` (an unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the shop domain is never covered by the signature, `hmac_valid == true` proves only "this body was produced with the app's secret at some point," not "this body belongs to shop X." An attacker who installs the app on their own store receives a genuinely-signed webhook (valid HMAC, arbitrary body content they can influence to some extent depending on topic, e.g. `customers/redact`, `shop/redact`, `app/uninstalled`) and can then re-POST the exact same body to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will hand the victim's shop identifier to the handler together with attacker-controlled body data.

### Impact Explanation
This breaks the tenant identity binding (`shop_header == authenticated_shop`) that host applications rely on to route webhook data (e.g., deleting data, marking uninstalls, updating settings) to the correct tenant's session/storage. Depending on how a host app implements its handler (looking up `WebhookMetadata#shop` to fetch/mutate stored per-shop state), this enables cross-tenant data manipulation, e.g. triggering GDPR redaction/uninstall logic or forged state changes against a shop the attacker does not control. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is bounded by the fact that this replicates exactly how Shopify's real webhook signing scheme behaves upstream (Shopify itself only signs the raw body with HMAC-SHA256; it does not sign headers) — this is a known limitation of the webhook protocol, not something introduced uniquely by a bug in this gem's logic beyond faithfully implementing the same scheme without additional tenant binding. Any attacker needs only to control an installation of the target app on a store they own, capture a real signed webhook, and replay it with a swapped `shop-domain` header — no privileged credentials required, satisfying the "unprivileged internet user" threat model.

### Recommendation
When processing webhooks, additionally verify that the `shop` header value corresponds to a shop for which the app currently holds a session/is installed, rather than trusting it purely because the body HMAC validated. Alternatively/additionally, incorporate the `shop-domain` header into the material used for a secondary application-level check (e.g., cross-reference against `iss`/`dest` of any accompanying session token, or a shop allow-list maintained by the host app) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a genuine webhook (e.g. `customers/redact`) to the app with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON body.
3. Attacker captures the raw body and valid HMAC value, then sends their own POST directly to the app's webhook endpoint, keeping the body and HMAC identical but changing the header to `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts this (headers only checked for presence): [5](#0-4) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the secret: [6](#0-5) 
6. The handler is invoked with `shop: "victim.myshopify.com"` and the attacker-supplied body, despite the HMAC never having authenticated that shop value: [7](#0-6)

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
