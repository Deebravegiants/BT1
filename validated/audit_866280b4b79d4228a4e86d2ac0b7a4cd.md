### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating only the raw request body against the app's shared `api_secret_key`, while the `shop-domain` (and `topic`/`webhook-id`) headers that identify which merchant the event belongs to are read directly from unauthenticated HTTP headers and never included in the HMAC computation.

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)` before dispatching to a handler: [1](#0-0) 

`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#shop` is a separate accessor read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding to that header: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` compute the HMAC purely over `to_signable_string` (i.e., the body) using the app's `api_secret_key`: [3](#0-2) 

The identity binding that should hold is: `hmac == HMAC(secret, body ∥ shop)`. Instead, the code only enforces `hmac == HMAC(secret, body)`, and the `shop` value used afterward (`request.shop`) is taken from a field that was never verified. Since `api_secret_key` is a single value shared by the app across every merchant/shop that has it installed, any party who can obtain one genuinely-signed `(body, hmac)` pair — for example a merchant who has installed the app themselves and thus legitimately receives real webhook deliveries signed with the app's secret — can resend that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The HMAC check still passes because it never inspected the shop header, and `Registry.process` passes that attacker-controlled `request.shop` straight into `WebhookMetadata` for the handler: [4](#0-3) 

### Impact Explanation
This lets an unprivileged user of a multi-tenant app (any merchant with the app installed) forge a webhook event that appears to originate from a different, victim shop, since the handler trusts `data.shop` from `WebhookMetadata` to attribute the event to a tenant. Depending on how host applications key their data by `data.shop` (which is the gem's documented contract), this is a cross-tenant data-integrity/confusion issue reachable without any leaked credentials belonging to the victim — only the attacker's own legitimately-received webhook traffic is needed.

### Likelihood Explanation
Moderate-to-high: any merchant with the app installed on their own store receives real, validly-signed webhook payloads from Shopify and can capture and replay them against the app's public webhook endpoint with a modified shop header. No secrets need to be exfiltrated from Shopify or from another merchant.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signed material, or otherwise cryptographically bind the shop-domain header to the signed body (e.g., by having `Utils::HmacValidator` require and check a canonical string containing shop+body), so that the header cannot be swapped independently of the signed payload. Reject requests where the shop the body was actually generated for does not match the request headers.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and lets it receive a legitimate webhook, capturing the raw HTTP request: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the app's shared secret), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs the same body `B` and header `H` to the app's webhook endpoint again, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate` succeeds because it only recomputes HMAC over `B` [5](#0-4) , and `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)` [6](#0-5) , causing the host application to process attacker-controlled webhook content as if it belonged to the victim shop.
