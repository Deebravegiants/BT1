## Title
Local (Orb-side) signup success determination bypasses backend duplicate/fraud validation for user-centric signups - (File: `src/plans/mod.rs`)

### Summary
The external report describes a class of bug where an authoritative-looking action (an admin "signing off") is treated as valid with no independent check that the underlying claim (the deposit) actually exists or is legitimate. The same bug class is reachable in orb-core's signup flow: for "user-centric" signups, the Orb determines signup **success** purely from its own local pipeline result, entirely skipping the one code path (`enroll_user::Plan::run`) that asks the backend to verify the signup is not a duplicate/fraudulent/in-flight registration.

### Finding Description
In `do_signup` in [1](#0-0) , the final `success` value used for the signup result is computed as:

```rust
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups {
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(orb, debug_report, &capture, pipeline.as_ref(), signup_reason)).await.is_success()
};
```

When `user_centric_signup` is `true`, `enroll_user` (and therefore the backend `signup_post`/`signup_poll` round trip) is never invoked. That backend round trip in [2](#0-1)  is explicitly the mechanism that is documented to catch "Backend duplicates," "Backend inflight matches," and "Backend detected fraud" — i.e., the only real check of global signup validity/uniqueness.

Compounding this, the local `signup_reason` is derived from `detect_fraud`, whose implementation has been stripped in this build:

```rust
// FOSS: WE HAVE DELETED ALL FRAUD CHECKS
Ok(false)
``` [3](#0-2) 

So for the user-centric path, `signup_reason` will be `SignupReason::Normal` whenever the local biometric pipeline merely completes without an internal agent error — see the reason selection logic at [4](#0-3) . There is no cross-check with the backend's uniqueness/duplicate/fraud database before the Orb reports `SignupEnded { success: true, ... }` over `orb_relay` to the app, as seen at [5](#0-4) .

This mirrors the reported bug class exactly: a locally-determined "everything looks fine" signal (analogous to the admin's sign-off) is treated as final and valid, with no independent validity check against the authoritative backend state (analogous to the missing deposit-existence check).

### Impact Explanation
Because the backend's dedup/fraud verification (`signup_post`/`signup_poll`) is skipped entirely on the user-centric path, and local fraud detection is a no-op, a signup can be reported as successful/unique to the user-facing app without the backend ever confirming that the presented biometrics are not already enrolled. This directly threatens the uniqueness/anti-Sybil guarantee that is the core value proposition of the system, and can result in misattributed or duplicate signups being locally certified as successful.

### Likelihood Explanation
This path is exercised whenever the backend flags a QR code's `user_data.user_centric_signup` as `true` (a supported, non-debug production flow, since `ignore_user_centric_signups` defaults to not overriding it), combined with `detect_fraud` always returning `false` in this build. No special privileges are required by the person undergoing the signup; the condition is met by ordinary use of the app-centric signup flow.

### Recommendation
Do not treat a purely local pipeline outcome as final signup success for user-centric signups. Always route the signup outcome through the backend's uniqueness/fraud verification (the `enroll_user` / `signup_post`+`signup_poll` flow), or otherwise ensure that the backend independently confirms uniqueness/non-duplication before `SignupResult.success` is set to `true` and before `SignupEnded{success: true}` is relayed to the app.

### Proof of Concept
1. Complete a signup where the backend-provided QR data sets `user_centric_signup = true` (a legitimate, supported flow) — see the flag flowing through `backend::user_status::request` at [6](#0-5) .
2. Undergo biometric capture with iris/face data already enrolled previously (i.e., attempt a duplicate signup).
3. Because `detect_fraud` unconditionally returns `Ok(false)` [3](#0-2) , `signup_reason` becomes `SignupReason::Normal` as long as the pipeline completes.
4. In `do_signup`, since `user_centric_signup` is `true`, `enroll_user` (and its backend duplicate/fraud check) is never called [1](#0-0) ; `success` becomes `true` purely from the local `signup_reason`.
5. The Orb reports `SignupEnded { success: true, .. }` to the app [5](#0-4)  despite the backend never having validated that this is not a duplicate/fraudulent enrollment.
