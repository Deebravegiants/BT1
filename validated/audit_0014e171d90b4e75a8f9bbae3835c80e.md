### Title
`HotBridge.fetchWithdrawalHashFromApi` reports withdrawal as `completed` without checking `verified_withdraw` - ([File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts])

### Summary
`HotBridge.describeWithdrawal` uses `fetchWithdrawalHashFromApi` as a fallback source of truth when the on-chain contract view or bridge indexer cannot confirm a withdrawal. The HOT API response schema explicitly carries a `verified_withdraw: boolean` field per withdrawal record, but the code that decides whether to report the withdrawal as `completed` never reads or checks this field before returning a `txHash` and `status: "completed"`.

### Finding Description
`HotApiWithdrawalSchema` defines `verified_withdraw: v.boolean()` as a required field of each withdrawal record returned by the HOT API [1](#0-0) . However, `fetchWithdrawalHashFromApi` only matches the record by `nonce` and checks that `withdrawal?.hash` is a truthy, valid hex string; it never inspects `withdrawal.verified_withdraw` before returning the hash as authoritative [2](#0-1) .

This hash is then used directly by `describeWithdrawal` to report `{ status: "completed", txHash: ... }` in both the EVM/Stellar/TON bridge-indexer-failure fallback path and the non-EVM primary fallback path [3](#0-2) [4](#0-3) . That "completed" status is treated as terminal by the polling watcher, which returns the resolved transaction hash to the caller as soon as `status.status === "completed"` [5](#0-4) .

This is directly analogous to the reported bug class: a status/outcome is reported to the caller without checking a flag that indicates the record is not yet confirmed/final — just as `setIncentive` checked only elapsed time and ignored whether incentives were actually distributed, `fetchWithdrawalHashFromApi` checks only hash presence and ignores whether the withdrawal is actually `verified_withdraw`.

### Impact Explanation
An integrator relying on the SDK's `describeWithdrawal`/`watchWithdrawal` result to credit a user, release funds, or mark an off-chain ledger entry as settled would do so based on a HOT API record that the API itself has not verified (`verified_withdraw: false`). If the withdrawal is later reverted, does not settle, or the API record proves to be provisional/incorrect, the integrator has already acted on a finalized state that wasn't actually confirmed on-chain — a status misreport that can lead to premature/duplicate crediting. This matches the High severity bucket: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This path is only reached as a fallback (when the bridge indexer is unavailable/fails, or for the non-EVM primary path when contract state is inconsistent), so it is not the primary path for every withdrawal, but it is a normal, externally-reachable failure/fallback condition (bridge indexer outage or delay), not a privileged or adversarial action — any withdrawal polled during a bridge-indexer hiccup can trigger it. No malicious actor input is required; the bug is purely in the SDK's own trust of an unverified upstream flag.

### Recommendation
In `fetchWithdrawalHashFromApi`, only accept and return `withdrawal.hash` when `withdrawal.verified_withdraw === true`. If `verified_withdraw` is `false`, keep the withdrawal status as `pending` regardless of `hash` presence.

### Proof of Concept
1. A user withdraws BNB via HOT Bridge; `describeWithdrawal` is polled.
2. The bridge indexer request fails (or, for non-EVM chains, the contract view returns null).
3. `fetchWithdrawalHashFromApi` is called and the HOT API returns a withdrawal record matching the nonce with `hash: "0x...", verified_withdraw: false` (a not-yet-finalized/failed record that nonetheless carries a hash value, as shown by the schema explicitly modeling this field separately from `hash`) [1](#0-0) .
4. Current code ignores `verified_withdraw` and returns `{ status: "completed", txHash: "0x..." }` [2](#0-1) .
5. `watchWithdrawal` resolves the polling loop as finished with that hash [5](#0-4) , and any integrator consuming this result treats the withdrawal as settled despite it not being verified by HOT.

Note: I could not find any existing test case in `hot-bridge.test.ts` that exercises `verified_withdraw: false` with a non-null hash, so I cannot confirm whether this exact combination occurs in HOT's real API responses in practice — this should be verified against the actual HOT API behavior before treating this as fully confirmed.
