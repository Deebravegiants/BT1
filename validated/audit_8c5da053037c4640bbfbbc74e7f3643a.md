### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verification performed by `Utils::HmacValidator.validate` only proves that the *body* was signed by Shopify with the app's `api_secret_key`. It does not bind the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers to that signature. `Registry.process` nonetheless takes `request.shop` (read straight from the unauthenticated header) and hands it to the app's `WebhookHandler#handle` as trusted tenant identity via `WebhookMetadata`.

### Finding Description
The binding that should hold is:
`shop header used to attribute webhook data == shop that the signed body actually originated from`

`Request#to_signable_string` breaks this equality by signing only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are pulled from HTTP headers that are never part of the signed material: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it to the received `hmac` header — it never touches the shop header: [3](#0-2) 

`Registry.process` validates only that HMAC, then forwards `request.shop` (an unverified header) straight into `WebhookMetadata`, which is the sole tenant-identity signal handed to the app's handler: [4](#0-3) [5](#0-4) 

Because the shop header is not covered by the signature, an unprivileged attacker who is a merchant installing the app on their **own** shop can receive a genuine, validly-signed webhook for their own store (body + HMAC valid), then replay the exact same HTTP request to the app's public webhook endpoint after changing only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to a victim shop's domain. The HMAC still validates (it only checks the body, unchanged), but `Registry.process` will invoke the app's handler with `data.shop` set to the victim's domain. Any app that uses `data.shop` to decide which tenant's records to create/update/delete (exactly as shown in the gem's own documented usage pattern, `shop_domain: data.shop`) will perform that mutation against the wrong tenant — a cross-tenant data-integrity/confusion attack achieved purely by an attacker abusing their own legitimately-issued webhook.

This matches the report's bug class (an operation trusting an input channel that is not actually covered by the cryptographic check meant to authenticate it): here it's the `shop` identity header versus the HMAC-protected body, rather than ether vs. ERC20 token assumptions, but the underlying flaw is the same — code trusts an unauthenticated field for a security-relevant decision while believing it has been verified.

### Impact Explanation
Rated **High**: this allows cross-tenant confusion of webhook-triggered tenant identity. Because `shop` is the exact field host applications are documented to use as the tenant key to route/persist webhook-derived data (`docs/usage/webhooks.md` shows `shop_domain: data.shop`), an attacker with any legitimate storefront on the app can inject fabricated tenant-attributed events into a victim shop's processing pipeline. No access token, session, or credential of the target is required — only a body+HMAC pair the attacker legitimately received for their own store.

### Likelihood Explanation
Rated moderately high: obtaining a valid webhook payload only requires installing the app on any shop (something any internet user can normally do for public apps) and capturing one webhook delivery to the app's endpoint. The attacker then simply resends the untouched body/HMAC pair with a modified `shop-domain` header — no cryptography needs to be broken.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the signed material, or otherwise cryptographically tie the header values to the request. Concretely, change `Request#to_signable_string` to include the `shop`, `topic`, and other trust-relevant headers in the signed payload (matching how `AuthQuery#to_signable_string` binds `code`, `host`, `shop`, `state`, and `timestamp` together, per `lib/shopify_api/auth/oauth/auth_query.rb`), or validate the `shop` header value against Shopify's response/webhook metadata via an independent authenticated channel (e.g., cross-check against the registered webhook's shop via a follow-up API call) before trusting it for tenant attribution.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) so Shopify sends a webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` for the given JSON body and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Capture the raw request (body + headers) using a proxy/log on the attacker's own infrastructure.
3. Replay the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because only the body is signed (`Request#to_signable_string` returns `@raw_body`) — see [1](#0-0) .
5. `Registry.process` invokes the app handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, and any app logic keyed on `data.shop` (as documented in `docs/usage/webhooks.md`) now operates against the victim tenant using attacker-supplied data.
