Audit Report

## Title
Fee-on-transfer / non-standard ERC20 tokens cause XCM holding over-crediting in `ERC20Transactor` - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` credits the XCM `AssetsInHolding` register with the full nominal `amount` requested for withdrawal as soon as the ERC20 contract's `transfer()` call returns `true`, without verifying that the `TransfersCheckingAccount` actually received `amount` of the token. [1](#0-0)  Because `ERC20Matcher` matches any local `AccountKey20` location without any allow-list or registry check, this transactor accepts arbitrary user-deployed `pallet-revive` contracts as valid XCM assets, so a fee-on-transfer or otherwise non-standard ERC20 contract that returns `true` while transferring less than `amount` will cause the runtime's XCM holding accounting to diverge from the checking account's real token balance.

## Finding Description
In `withdraw_asset_with_surplus`, the flow is: encode and `bare_call` an ERC20 `transfer(checking_address, amount)`, and if the call did not revert and `abi_decode_returns_validate` yields `true`, immediately construct `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — crediting the declared `amount`, never reading `balanceOf` on the checking account before/after the call. [2](#0-1)  The symmetric `deposit_asset_with_surplus` function has the same pattern: it calls `transfer(beneficiary, amount)` from the checking account and treats `Ok(true)` as full success without confirming the beneficiary's balance increased by `amount`. [3](#0-2) 

The `Matcher` generic (`ERC20Matcher` in the concrete Asset Hub Westend config) is a structural matcher based on location shape (`MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, ...>`), not an asset registry — it accepts any local `AccountKey20` address as a valid asset id, meaning any deployed contract can be referenced this way with no admin/allow-list gate at the transactor level. This is consistent with the code path shown: `Matcher::matches_fungibles(what)` is the only gating check before the `transfer` call is issued, and it is purely a decode/shape match, not a permission check. [4](#0-3) 

This root cause is real and verified directly in the code: the transactor trusts the boolean return value and the caller-declared `amount` rather than measuring the actual balance delta, which is the exact anti-pattern that breaks accounting invariants for fee-on-transfer, deflationary, or otherwise non-standard ERC20 tokens.

## Impact Explanation
If a contract's `transfer()` returns `true` while moving fewer tokens than `amount` (e.g., burns/fees a portion), `withdraw_asset_with_surplus` will still credit the full `amount` into the XCM holding register, creating an accounting entry not fully backed by the checking account's real balance. Subsequent `DepositAsset`, cross-chain reserve transfers, or other consumers of that holding treat the unbacked credit as genuine, and repeated use can desynchronize the shared `TransfersCheckingAccount`'s real balance from what the runtime's XCM logic believes is custodied for that asset — an internal accounting-integrity defect within a component (`ERC20Transactor`) that is explicitly designed to let arbitrary user-deployed `pallet-revive` contracts participate in XCM as fungible assets. This is a genuine in-scope Polkadot SDK code defect (not a privileged-only, node-only, or bridge-only issue), and it is reachable by unprivileged users, since anyone can deploy a `pallet-revive` contract and reference its address in ordinary XCM programs.

## Likelihood Explanation
The attack requires no special privilege: an attacker deploys their own `pallet-revive` contract implementing a non-standard `transfer()` (fee-on-transfer/deflationary, but still returning `true`), then issues a standard XCM instruction referencing that contract's address as an `AccountKey20` asset. `ERC20Matcher`'s structural matching (rather than a curated allow-list) means the transactor will process any such contract without additional gating at this layer. This makes the finding practically and repeatably triggerable, assuming `ERC20Transactor` is wired into the live `AssetTransactors` tuple for a deployed chain (as claimed for Asset Hub Westend, though this specific wiring in `asset-hub-westend/src/xcm_config.rs` was not independently re-verified in this session beyond the citation provided in the claim).

## Recommendation
In `withdraw_asset_with_surplus`, read the checking account's `balanceOf` before and after the `transfer` call and credit `Erc20Credit` with the actually observed delta rather than the requested `amount`, failing the operation if the delta is less than requested. Apply the analogous before/after balance check to the beneficiary account in `deposit_asset_with_surplus` before treating the deposit as fully successful. Alternatively/additionally, restrict `ERC20Matcher` (or add an additional check) to only allow vetted, standard-conforming ERC20 contracts.

## Proof of Concept
1. Deploy a `pallet-revive` contract `FeeERC20` whose `transfer(to, amount)` deducts a fee (e.g., burns `amount/10`) but still returns `true`.
2. Mint the attacker a `FeeERC20` balance.
3. Submit an XCM program (via `pallet_xcm::execute` or `transfer_assets`) with `WithdrawAsset` for asset `{parents:0, interior: AccountKey20{key: FeeERC20_address}}` and amount `A`.
4. Observe `ERC20Transactor::withdraw_asset_with_surplus` returns `AssetsInHolding` credited with the full `A` (per code at lines 195-203), while `TransfersCheckingAccount`'s actual `FeeERC20` balance increased by only `A - A/10`.
5. Follow with `DepositAsset` to a beneficiary for the full `A`, demonstrating the beneficiary/destination is credited more than what the checking account actually holds, confirmed against the code path at lines 253-287 for the deposit side.
