### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unauthenticated headers while only the raw body is HMAC-verified, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable value from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` verifies only the body HMAC and then forwards those unauthenticated header values, unmodified, to the app's `WebhookHandler` as the trusted tenant/topic identity (`WebhookMetadata`). Anyone possessing one valid `(body, HMAC)` pair for the app's shared secret (e.g. a real webhook delivered to their own installed shop) can replay that pair to the app's webhook endpoint with arbitrary `shop-domain`/`topic`/`webhook-id` headers and have it accepted as authentic.

### Finding Description
The HMAC binding is defined in `to_signable_string`, which returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from request headers that are never included in the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (which covers the body only) and then trusts `request.topic` and `request.shop` to route and to build the `WebhookMetadata` passed to the host application's handler: [3](#0-2) 

`WebhookMetadata.shop` and `.topic` are exactly what host apps are documented to use as the authoritative tenant/topic identity for the webhook: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop/topic authenticated by HMAC == shop/topic acted on by the handler`. Because the HMAC covers only `@raw_body`, this equality does not hold — the `shop` and `topic` fields that the handler treats as authenticated tenant/event identity are not covered by the cryptographic check at all, only the body content is.

### Impact Explanation
This crosses the "field acted on but not covered by the HMAC" boundary called out in the rules. Any party who can obtain one genuine `(raw_body, hmac)` pair signed with the app's shared secret — trivially available to any merchant who installs the app and receives a real webhook, or to anyone who can trigger a webhook with attacker-controlled/minimal body content (e.g. `app/uninstalled`, `shop/redact`, or other topics with sparse bodies) — can forge the `shop-domain` header to impersonate any other merchant using the app, and forge the `topic`/`webhook-id` headers to relabel the event. Since `Registry.process` never checks that the signed body actually corresponds to the claimed shop/topic, the host application's handler executes tenant-scoped logic (e.g. data deletion, uninstall handling, order processing) attributed to a shop that never sent the corresponding webhook. This is a cross-tenant impersonation impacting any app built on this gem's webhook facility, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only: (1) obtaining one valid `(body, hmac)` pair for the target app's secret — achievable by any legitimate merchant installing the app once, since the secret is shared across all shops of that app — and (2) sending a direct HTTP POST to the app's webhook endpoint with the same body/HMAC but attacker-chosen `shop-domain`/`topic` headers, bypassing Shopify's delivery infrastructure entirely (this gem does not verify the request originates from Shopify's IPs, nor bind headers into the signature). No access token, `client_secret`, or privileged account is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the HMAC-signable string in `Request#to_signable_string`, or otherwise validate that these header-derived fields match values independently obtained/verified (e.g., by only trusting `shop`/`topic` combinations that the app itself registered via `Registry.add_registration`/webhook subscription IDs it created, and rejecting any request whose header set cannot be tied to a signature computed over those exact values).

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the target app and receives a genuine webhook for topic `app/uninstalled` with body `{}` and a valid `X-Shopify-Hmac-Sha256` header computed by Shopify using the app's `api_secret_key`.
2. Attacker captures this `(raw_body="{}", hmac)` pair.
3. Attacker sends a POST directly to the app's webhook endpoint with headers:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: app/uninstalled`
   - `X-Shopify-Hmac-Sha256: <captured hmac>`
   - body: `{}`
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `hmac` against `to_signable_string` (`@raw_body`), which is unchanged. [6](#0-5) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: {})`, causing the app to run uninstall/cleanup logic for a shop that never actually uninstalled the app.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
