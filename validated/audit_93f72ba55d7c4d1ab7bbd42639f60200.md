### Title
Insufficient Staleness Check in `PassphraseCache.get()` Allows Auto-Unlock With a Passphrase Cached Beyond the Configured `maxTtl` - ([File: features/application/src/modules/passphrase-cache.ts])

### Summary
`PassphraseCache.get()` validates a cached passphrase against two mutually-exclusive time bounds — `inactiveAt + ttl` (if the app was ever backgrounded) or `addedAt + maxTtl` (only when it never went inactive). Once `inactiveAt` is set, the absolute `maxTtl` bound from `addedAt` is never re-checked, mirroring the `GasTankPaymaster.updateCachedPrice()` bug class: a cache-freshness check that validates against one threshold while silently ignoring the second, stricter threshold that the security model actually requires.

### Finding Description
`get()` in [1](#0-0) :
```
if (passphrase) {
  if (inactiveAt) {
    if (inactiveAt + ttl > Date.now()) {
      return passphrase
    }
  } else if (addedAt + this.#maxTtl > Date.now()) {
    return passphrase
  }
  void this.clear()
}
```
`scheduleClear()` sets `INACTIVE_AT_KEY = Date.now()` and reschedules the alarm every time it is invoked [2](#0-1) , and it is called both from `unload()` (app entering background) and from the public `restartAutoLockTimer()` API [3](#0-2) [4](#0-3) .

Once `inactiveAt` is set (which happens on essentially every backgrounding event), the validity check switches entirely to `inactiveAt + ttl > Date.now()` and never again compares against `addedAt + maxTtl`. Because `inactiveAt` is refreshed to `Date.now()` on every background/foreground cycle (or via `restartAutoLockTimer`), each cycle resets the clock, so the cached passphrase can remain "fresh" indefinitely as long as the app is repeatedly backgrounded within `ttl` of each other — with no absolute cap coming from `maxTtl`/`addedAt` after the first inactivation. This is structurally identical to the `GasTankPaymaster` flaw: the code checks freshness against *one* max-age (`ttl`, analogous to `nativeMaxAge`) but drops the second, more restrictive bound (`maxTtl` from `addedAt`, analogous to `tokenMaxAge`) that was intended to be an additional restriction on the very same cached value.

`changeTtl()` does clamp a newly-set `ttl` to `Math.min(this.#maxTtl, ttl)` [5](#0-4) , so a single `ttl` value can never itself exceed `maxTtl`. However, that clamp only bounds one inactivity interval — it does not bound the sum of many inactivity intervals, since each call to `scheduleClear()` resets `inactiveAt` to "now" and the `get()` check only ever looks at the most recent `inactiveAt`, never the original `addedAt`.

### Impact Explanation
`PassphraseCache.get()` is consumed by `Application.#autoUnlock()`, which uses the returned passphrase to silently unlock the wallet without user interaction: `await this.#wallet.unlock({ passphrase })` [6](#0-5) . `maxTtl` is explicitly documented/configured as the hard ceiling for how long a passphrase may be auto-unlockable from cache (`passphraseCacheMaxTtl` config) [7](#0-6) . Because the absolute bound is dropped after the first backgrounding event, the wallet can remain silently auto-unlockable well past the operator-configured `maxTtl`, undermining the intended re-authentication requirement — an auth-bypass-class impact on the very control meant to force the user to re-enter their passphrase after a maximum elapsed time.

### Likelihood Explanation
The unprivileged trigger path requires only normal, everyday device usage: any user backgrounding/foregrounding the app repeatedly (or the wallet UI calling `restartAutoLockTimer()`, a public API [8](#0-7) ) resets `inactiveAt` and thus extends the passphrase-cache lifetime beyond `maxTtl` without any additional restriction ever being enforced. No special privileges, malicious peers, or mocked-only conditions are needed — it's reachable through ordinary lifecycle events in the shipped application module.

### Recommendation
In `get()`, add the missing "second restriction" analogous to the paymaster fix: always require `addedAt + maxTtl > Date.now()` in addition to the `inactiveAt + ttl` check, e.g.:
```js
if (inactiveAt) {
  if (inactiveAt + ttl > Date.now() && addedAt + this.#maxTtl > Date.now()) {
    return passphrase
  }
} else if (addedAt + this.#maxTtl > Date.now()) {
  return passphrase
}
```
This ensures the cached passphrase is treated as stale once the absolute `maxTtl` from `addedAt` elapses, regardless of how many times `inactiveAt` has been refreshed.

### Proof of Concept
1. Configure `passphraseCacheMaxTtl` (e.g. 60 minutes) and an auto-lock `ttl` (e.g. 5 minutes) via `changeLockTimer` [9](#0-8) .
2. Unlock the wallet with a passphrase; `set()` stores `addedAt = now` [10](#0-9) .
3. Every ~4 minutes, background/foreground the app (or call `restartAutoLockTimer`), which calls `scheduleClear()` and resets `inactiveAt = now` each time [2](#0-1) .
4. Repeat this cycle for several hours, well past the configured 60-minute `maxTtl`.
5. On each app start, `#autoUnlock()` calls `passphraseCache.get()`, which only checks `inactiveAt + ttl > Date.now()` (true, since it's refreshed every cycle) and never re-checks `addedAt + maxTtl` — the wallet keeps silently auto-unlocking far beyond the intended `maxTtl` cap.
