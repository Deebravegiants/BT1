### Title
Webhook shop-domain spoofing due to unauthenticated tenant identifier outside HMAC scope - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from an HTTP header that is never covered by the webhook HMAC signature, while `ShopifyAPI::Webhooks::Registry.process` trusts that header value as the authenticated tenant for dispatching to the host app's handler.

### Finding Description
The webhook verification flow computes and checks an HMAC, but the signed material is limited to the raw body only: [1](#0-0) 

```ruby
def to_signable_string
  @raw_body
end
```

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from request headers and are **not** part of `to_signable_string`: [2](#0-1) 

`Registry.process` validates only this body-scoped HMAC, then forwards the unauthenticated `request.shop` value to the host app's handler as if it were an authenticated tenant identifier: [3](#0-2) 

The binding that should hold is:
`shop value trusted by the handler == shop value cryptographically bound to the signed payload`

but the actual binding enforced by the code is only:
`HMAC(raw_body, api_secret_key) == received_hmac`

with `shop` sitting entirely outside that equality. Any HTTP header can be freely set by whoever sends the POST request to the app's public webhook endpoint; the library performs no check that the `shop` header matches the shop that Shopify actually generated the signed body for.

### Impact Explanation
`WebhookMetadata.shop` is the only tenant identifier exposed to the host app's `WebhookHandler#handle` implementation: [4](#0-3) 

Because this field is not bound to the HMAC, an unprivileged attacker who is themselves a legitimate installer of the app (e.g., on their own free/dev store — no special credentials of the target merchant are required) can:
1. Trigger any webhook topic on their own shop for which they control body content (e.g., `products/update`, `orders/create` with attacker-controlled note/line-item fields, or a mandatory GDPR topic).
2. Capture the raw body and the resulting `x-shopify-hmac-sha256` value — both valid, since they were legitimately signed with the app's `client_secret` for the attacker's own installation.
3. Replay that exact body/HMAC pair to the app's webhook endpoint while overwriting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain.
4. `HmacValidator.validate` still succeeds because the header is not part of the signed string, and `Registry.process` dispatches the payload to the handler with `shop: <victim-domain>`.

This is a cross-tenant confusion: attacker-controlled data (or attacker-triggered mandatory compliance events such as `customers/redact`, `shop/redact`) is delivered to the host application labeled as belonging to a shop the attacker does not control and has no relationship to. Depending on how the host app uses this `shop` value (e.g., looking up/mutating stored per-shop data, revoking access, redacting customer data, updating cached product/catalog info attributed to a tenant), this can result in cross-tenant data corruption or state changes — the same class of "critical" impact called out in the analogous report (a critical action executed against the wrong identity because an attacker-influenced field was excluded from the integrity check).

### Likelihood Explanation
Likelihood is high for any app author who relies on `WebhookMetadata#shop` (the field this gem explicitly hands back after "verifying" the webhook) as an authenticated tenant identifier — which is exactly how the gem's own webhook API is documented to be used. No secrets, tokens, or elevated privileges are needed: only the ability to install the app on any shop (including a free development store) and send one crafted HTTP POST to the app's existing webhook endpoint.

### Recommendation
Bind the tenant/topic identifiers into the signed material actually verified, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the payload before exposing them to handlers — e.g., include the relevant headers in `to_signable_string`, or have `Registry.process` cross-check `request.shop` against session/shop state already known to be valid for the delivered `webhook_id` (fetched via the Admin API), rather than trusting the raw header value once the body HMAC passes.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop "attacker.myshopify.com"
#    and triggers e.g. a products/update webhook with attacker-controlled body:
raw_body = '{"id":1,"title":"attacker-controlled"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)
# This hmac is valid because it's genuinely signed by Shopify for attacker's own install.

# 2. Attacker replays the same body/hmac to the app's public webhook endpoint,
#    but swaps only the shop-domain header:
spoofed_headers = {
  "x-shopify-topic" => "products/update",
  "x-shopify-hmac-sha256" => hmac,                 # unchanged, still valid
  "x-shopify-shop-domain" => "victim.myshopify.com" # spoofed, NOT covered by hmac
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (only raw_body is checked)
# => handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", ...))
#    is invoked, attributing attacker-controlled data to "victim.myshopify.com".
```
