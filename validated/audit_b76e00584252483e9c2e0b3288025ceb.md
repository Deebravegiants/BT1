### Title
Fixed-size on-chain-bid read cap (`MAX_ON_CHAIN_BIDS = 30`) lets any unprivileged filler flood and hide real solver bids from `intents_getBidsForOrder` - ([File: modules/pallets/intents-coprocessor/rpc/src/lib.rs])

### Summary
The `Bids` double-map in `pallet-intents-coprocessor` is unbounded per commitment, but the custom RPC that exposes on-chain bids to solvers/relayers/SDK consumers (`get_bids_for_order`) only reads the first `MAX_ON_CHAIN_BIDS = 30` raw storage keys under a commitment's prefix. `place_bid` only requires a small, fully-refundable `StorageDepositFee` reservation, so an unprivileged account can cheaply submit (and later retract) far more than 30 bids for a single order commitment, occupying every slot the RPC will ever read and causing legitimate solver bids to be silently dropped from bid discovery — the same "fill the bounded list with fake/cheap entries to lock out real participants" pattern described in the OtterSec `MAX_NUMBER_OF_DELEGATIONS` finding.

### Finding Description
`pallet-intents-coprocessor` stores bids in an unbounded `StorageDoubleMap`: [1](#0-0) 

Placing a bid only reserves a governance-set flat deposit (`StorageDepositFee`), refunded on `retract_bid`, and is open to any signed account: [2](#0-1) 

The RPC handler that surfaces on-chain bids for coordination — used by solvers and by the SDK's phantom-bid aggregation pipeline — caps how many on-chain entries it will ever inspect at a hard-coded constant, iterating storage keys in raw key order (not by recency, fee, or fairness) and stopping after the first 30: [3](#0-2) 

Because:
1. `Bids` has no per-commitment cap (`#[pallet::without_storage_info]`, `OptionQuery`, no `BoundedVec`), and
2. the deposit is cheap and refundable, and
3. the RPC consulted by downstream logic (`getBidsForOrder` in the SDK, `aggregatePhantomBids`) only ever returns the first 30 on-chain entries plus whatever happens to still be in the ephemeral mempool cache,

an attacker can submit >30 bids from distinct throwaway accounts against a target commitment before a legitimate solver's bid lands, permanently occupying every slot `get_bids_for_order` will read for that commitment (the iterator order is fixed by the trie key layout, so once 30 attacker keys sort/are read first, honest bids placed afterward under the same prefix are never reached by the `.take(MAX_ON_CHAIN_BIDS)` cutoff). This mirrors the OtterSec-reported delegation-service DoS: a bounded, unprivileged-fillable slot with a low/refundable cost is used to crowd out real, meaningful participants.

### Impact Explanation
Any component that relies on `intents_getBidsForOrder` (relayers routing fills, the SDK's `getBidsForOrder`, and the phantom-order solver-bid aggregation used to price and select fills — `aggregatePhantomBids`) can be made blind to legitimate solver bids on a targeted commitment. This is a denial-of-service against the intent-fulfillment discovery/coordination path reachable directly from an unprivileged, single extrinsic submitter, and can be used to bias or block price/solver discovery for phantom order fulfillment at negligible, fully-refundable cost — a free, repeatable exploit against the intents coprocessor bidding mechanism.

### Likelihood Explanation
High. `place_bid` is callable by anyone with a signed account and minimal balance (deposit is refundable via `retract_bid`), requires no special permission, and the RPC-level truncation is a fixed constant with no anti-spam/priority ordering. An attacker only needs to generate >30 signed accounts (or reuse retracted ones across targets) and batch the calls (e.g., via `utility.forceBatch`, already used elsewhere in the SDK for bid batching) ahead of or alongside a targeted commitment.

### Recommendation
- Remove the arbitrary `MAX_ON_CHAIN_BIDS` truncation, or make bid discovery exhaustive/paginated so no bid is silently dropped regardless of volume.
- Bound `Bids` per-commitment (e.g., `BoundedVec`/`BoundedBTreeMap`) with a cap enforced at the pallet level, and reject `place_bid` once the cap is reached — but pair this with either (a) a meaningfully-priced deposit (scaling with congestion) rather than a flat, cheaply-refundable fee, or (b) an allow-list/whitelist of solver keys, so the bounded slots cannot be trivially monopolized by dust bids, closing the same "combine with cheap minimum bypass" free-exploit path OtterSec flagged for the delegation service.
- Consider ordering the RPC read by bid recency or deposit size instead of raw storage-key order, so even under load the most economically meaningful bids are surfaced first.

### Proof of Concept
1. Attacker generates 31+ funded throwaway `AccountId32` keys.
2. Attacker submits `pallet_intents_coprocessor::place_bid(commitment, dummy_user_op)` from each key for a specific phantom-order `commitment`, each reserving only `StorageDepositFee` (refundable later via `retract_bid`), e.g. as exercised in `multiple_fillers_can_bid_on_same_order`: [4](#0-3) 
3. A legitimate solver subsequently calls `place_bid` with a genuine `user_op` for the same `commitment`.
4. Any caller of `intents_getBidsForOrder` (SDK `getBidsForOrder`, `aggregatePhantomBids`) receives at most the mempool-cached bids plus the first 30 on-chain keys read via `bids_storage_prefix`/`storage_keys(...).take(MAX_ON_CHAIN_BIDS)`: [5](#0-4) 
   Once the attacker's 30+ dummy bids occupy the enumerated prefix range and the mempool cache entry expires/rotates out, the genuine solver's bid is never returned by the RPC, hiding it from downstream bid aggregation/fill-selection logic.
5. Attacker retracts all dummy bids to reclaim the full deposit, repeating the attack against future commitments at negligible net cost.

fn place_bid_works() {
	new_test_ext().execute_with(|| {
		let filler = AccountId32::new([1; 32]);
		let commitment = H256::random();
		let user_op = BoundedVec::try_from(vec![1u8, 2u8, 3u8]).unwrap();

		// Place a bid
		assert_ok!(Intents::place_bid(
			RuntimeOrigin::signed(filler.clone()),
			commitment,
			user_op.clone()
		));

		// Verify bid was stored (deposit amount for discoverability and refunds)
		assert!(Bids::<Test>::contains_key(&commitment, &filler));
		assert_eq!(Bids::<Test>::get(&commitment, &filler), Some(Intents::storage_deposit_fee()));

		// Verify deposit was reserved
		assert_eq!(Balances::reserved_balance(&filler), Intents::storage_deposit_fee());
	});
}
