### Title
Failing transactions can under-report `loaded_accounts_data_size` via `RollbackAccounts::data_size` fallback, underpricing the cost model - ([File: svm/src/account_loader.rs])

### Summary
When a transaction fails during `load_transaction_accounts` (e.g. an invalid/missing program id after all accounts have already been read from accounts-db) and the `define_ltds_fee_only_semantics` feature is not active, `FeesOnlyTransaction::loaded_accounts_data_size` is set to `RollbackAccounts::data_size()` instead of the actual bytes read (`LoadedTransactionDataSize`). Since `RollbackAccounts` only tracks the fee-payer (and optional nonce) account(s), any other accounts referenced in the transaction — including large ones the runtime actually loaded from accounts-db — are excluded from the cost-model's `loaded_accounts_data_size_cost`, letting an attacker touch large accounts for free in a failing transaction.

### Finding Description
`load_transaction` in `svm/src/account_loader.rs` computes the real amount of account data touched during loading via `LoadedTransactionDataSize`, tracked while iterating every account in `load_transaction_accounts`. On an `Err` result (fees-only path), the reported size is gated on the feature flag: [1](#0-0) 

When `define_ltds_fee_only_semantics` is *not* active, the code falls back to `tx_details.rollback_accounts.data_size() as u32`, whose implementation only sums the fee-payer and nonce account(s) data: [2](#0-1) 

`RollbackAccounts` only ever tracks 1–2 accounts (`FeePayerOnly`, `SameNonceAndFeePayer`, or `SeparateNonceAndFeePayer`): [3](#0-2) 

An attacker can craft a transaction that references several large accounts (read-only, no nonce) plus an instruction targeting a nonexistent/invalid program id. The account loader will read (and pay accounts-db I/O cost for) all referenced accounts while validating them, then fail with an error such as `ProgramAccountNotFound`, producing a `FeesOnlyTransaction`. Because there is no nonce and the fee payer is a plain (empty-data) system account, `RollbackAccounts::data_size()` returns 0 (or a small value), even though the actual loaded bytes may be many KB. This exact divergence is reproduced and asserted upon in the repo's own test suite: [4](#0-3) 

which explicitly states: "violating constraints *after* passing size ... otherwise ... it is the raw sum of rollback sizes which here is zero." The comment on `RollbackAccounts::data_size` itself flags this as a known, temporary gap: "This function will be removed by the fee-payer data size amendment to SIMD-186," i.e. `define_ltds_fee_only_semantics`.

This under-reported value flows unmodified into cost accounting: `Bank::create_commit_results` copies `fees_only_tx.loaded_accounts_data_size` into `CommittedTransaction.loaded_account_stats.loaded_accounts_data_size`: [5](#0-4) 

which is then used by `get_transaction_costs` to compute the actual post-execution cost via `CostModel::calculate_cost_for_executed_transaction`: [6](#0-5) 

and `calculate_loaded_accounts_data_size_cost` translates bytes directly into compute-unit cost pages used for block cost-tracking: [7](#0-6) 

Because the reported size (near 0) is far below the true bytes loaded, the block cost tracker (`check_block_cost_limits`) undercounts the real work the leader performed loading these accounts, allowing more such transactions to fit within the loaded-accounts-data-size block limit than actually justified by leader processing time.

No existing sanitization, lock, signature, nonce, status-cache, budget, or rent guard corrects this: the account loading itself succeeds (reads happen), only the post-hoc *accounting* of that read size is wrong, and this is purely a function of feature-activation state, not something a validator/operator config can filter out per-transaction.

### Impact Explanation
This is a materially underpriced execution / cost-model spam vector: an unprivileged attacker can submit ordinary (non-nonce) transactions that intentionally reference several large accounts and target a nonexistent program, causing them to fail as `FeesOnlyTransaction`s while the cost model attributes near-zero `loaded_accounts_data_size_cost` to them. Submitted repeatedly and cheaply (fee-only cost), this lets an attacker consume leader account-loading I/O/CPU cheaper than the cost model intends, degrading throughput for legitimate transactions without being reflected in the `loaded_accounts_data_size` component of block cost limits. This matches the "underpriced cost-model / spam vector consuming leader processing time cheaply" impact category described in the prompt.

### Likelihood Explanation
Feasible and repeatable by any unprivileged user: it requires no special account state, no nonce, no leader/validator control — only a normal transaction referencing multiple pre-existing large accounts and an instruction pointing at a program id known not to exist (or otherwise causing a load-phase failure after account reads, such as `ProgramAccountNotFound`/`InvalidProgramForExecution`-class errors). The condition is gated purely on whether `define_ltds_fee_only_semantics` is active for the cluster in question; while inactive, every such transaction reproduces the gap deterministically, as demonstrated by the repo's own parametrized test (`old_fee_only` case) at `svm/tests/integration_test.rs::fee_only_loaded_transaction_data_size`.

### Recommendation
Activate/backport `define_ltds_fee_only_semantics` (SIMD-186 amendment) everywhere feasible, and until then, avoid relying on `RollbackAccounts::data_size()` for cost-model accounting of `FeesOnlyTransaction`; instead always use the `LoadedTransactionDataSize` accumulated during `load_transaction_accounts`, matching the `define_ltds_fee_only_semantics = true` branch, regardless of feature-gate state, or clamp cost accounting to at least the sum of bytes actually read from accounts-db before failure.

### Proof of Concept
Extend the existing test `fee_only_loaded_transaction_data_size` (already in `svm/tests/integration_test.rs`) into a standalone regression assertion: with `define_ltds_fee_only_semantics = false`, construct a transaction referencing several large (e.g. 8 KB) pre-funded accounts plus an instruction to a nonexistent program id, so it fails during/after loading with `ProgramAccountNotFound`. Assert that:
```rust
let fail_program_id_loaded_size = output.processing_results[2]
    .as_ref().unwrap().loaded_accounts_data_size();
assert!(
    fail_program_id_loaded_size >= loaded_fee_payer_size + other_accounts_size,
    "cost model must not undercount loaded bytes for failed tx: got {fail_program_id_loaded_size}"
);
```
This assertion currently fails (the test file shows the actual value is `0` in the `old_fee_only` case), demonstrating the cost-model violates the invariant that loaded-accounts-data-size must upper-bound real bytes read.

    // Size of accounts tracked for rollback, used internally when calculating the actual
    // loaded transaction data size for the cost model. This function will be removed by
    // the fee-payer data size amendment to SIMD-186.
    pub(crate) fn data_size(&self) -> usize {
        let mut total_size: usize = 0;
        for (_, account) in self.iter() {
            total_size = total_size.saturating_add(account.data().len());
        }
        total_size
    }

// Get actual transaction execution costs from transaction commit results
fn get_transaction_costs<'a, Tx: TransactionWithMeta>(
    bank: &Bank,
    commit_results: &[TransactionCommitResult],
    sanitized_transactions: &'a [Tx],
) -> Vec<Option<TransactionCost<'a, Tx>>> {
    assert_eq!(sanitized_transactions.len(), commit_results.len());

    commit_results
        .iter()
        .zip(sanitized_transactions)
        .map(|(commit_result, tx)| {
            if let Ok(committed_tx) = commit_result {
                Some(CostModel::calculate_cost_for_executed_transaction(
                    tx,
                    committed_tx.executed_units,
                    committed_tx.loaded_account_stats.loaded_accounts_data_size,
                    &bank.feature_set,
                ))
            } else {
                None
            }
        })
        .collect()
}
