### Title
Direct SPL-token donations to `amm_coin_vault`/`amm_pc_vault` corrupt the pnl-skimming accounting and permanently divert LP funds - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
The Raydium AMM program derives all of its internal "true" reserve figures (`total_pc_without_take_pnl`, `total_coin_without_take_pnl`) directly from the live SPL Token account balances of `amm_pc_vault`/`amm_coin_vault` (i.e., the on-chain analog of `balanceOf(address(this))`), rather than from state tracked independently by the program. Because these vault token accounts are ordinary SPL Token accounts, any unprivileged actor can transfer extra tokens into them directly via the SPL Token program, bypassing any AMM-side accounting. This inflates the invariant used by `calc_take_pnl`, causing the program to misclassify the donated balance as legitimate trading "pnl" and reserve it for the (privileged) `pnl_owner`, permanently reducing the funds available to LPs on `Withdraw`.

### Finding Description
`calc_total_without_take_pnl_no_orderbook` computes the pool's authoritative reserves straight from the raw vault balances: [1](#0-0) 

These values are then fed as `x1`/`y1` into `calc_take_pnl`, which compares the current `pool_pc_amount * pool_coin_amount` (current "k") against the previously recorded `target_orders.calc_pnl_x * calc_pnl_y` snapshot to determine how much "profit" has accrued since the last skim, and increments `amm.state_data.need_take_pnl_pc/coin` accordingly: [2](#0-1) 

This function is invoked unconditionally inside `process_deposit`, `process_withdraw`, and `process_withdrawpnl` — all reachable by unprivileged users (any depositor/withdrawer triggers it): [3](#0-2) [4](#0-3) 

Since `amm_coin_vault`/`amm_pc_vault` are plain SPL Token accounts owned by the AMM authority PDA, nothing on the receiving side gates incoming `Transfer` instructions — an attacker can send arbitrary extra coin or pc tokens straight into either vault in the same transaction (or a preceding one) that calls `Deposit` or `Withdraw`. This artificially inflates `pc_amount`/`coin_amount` used for the k-invariant comparison, causing `calc_take_pnl` to treat the injected balance as genuine price appreciation and move a fraction of it (scaled by `pnl_numerator`/`pnl_denominator`) into `need_take_pnl_pc`/`need_take_pnl_coin`.

Because `Withdraw` computes each LP's redeemable share from `total_coin_without_take_pnl`/`total_pc_without_take_pnl` (vault balance minus `need_take_pnl_*`): [5](#0-4) 

any value siphoned into `need_take_pnl_pc/coin` by this donation-triggered miscalculation is permanently removed from the pool of assets available to ordinary LPs on withdrawal, to be later claimed exclusively by `pnl_owner` via `process_withdrawpnl`: [6](#0-5) 

This is the direct on-chain analog of the reported "artificial asset balance inflation" bug class: the program's core accounting relies on the raw, externally-influenceable balance of its own vault accounts (the Solana/SPL equivalent of `balanceOf(address(this))`) instead of an internally tracked reserve figure, so any unprivileged actor can distort it with a single, ordinary token transfer.

### Impact Explanation
An unprivileged attacker can, with a single transaction (donate tokens to a vault, then call `Deposit` or `Withdraw` with dust amounts), force the program to reclassify part of the donated (or even pre-existing, if the price ratio has drifted) reserve as `need_take_pnl_*`. This is state that is earmarked exclusively for `pnl_owner` and is deducted from the pool balances used to compute every LP's redemption amount. Because the trigger (calling `calc_take_pnl`) fires on every `Deposit`/`Withdraw`, the attacker can repeat the donate-then-touch sequence to progressively divert value away from the LP pool into the `pnl_owner`-claimable bucket, resulting in insolvent/incorrect pool accounting for LPs (LPs collectively redeem less than their true pro-rata share of vault assets).

### Likelihood Explanation
The precondition is trivial: an SPL Token `Transfer` instruction to a public, well-known vault address followed by a normal `Deposit`/`Withdraw` call, both of which are core user-facing instructions with no special permissions required. No malicious validator, privileged signer, or off-chain component is needed to trigger the corrupted state transition; only the final extraction step (`withdrawpnl`) requires the `pnl_owner` signer, but the harmful accounting mutation (shrinking LP-available reserves) already occurs at the unprivileged `Deposit`/`Withdraw` step.

### Recommendation
Do not derive `total_pc_without_take_pnl`/`total_coin_without_take_pnl` purely from the live vault token balances. Track deposited/withdrawn amounts and accrued trading fees internally in `AmmInfo`/`TargetOrders` state, and treat any excess vault balance beyond the internally tracked total as a value that must not be attributed to price-based pnl (e.g., ignore surplus balance not resulting from a swap fee event, or require that `calc_take_pnl`'s "k growth" only be attributed to amounts moved through `SwapBaseIn`/`SwapBaseOut`, not raw vault balance deltas).

### Proof of Concept
1. Attacker identifies a live pool's `amm_coin_vault` (or `amm_pc_vault`) public key from `AmmInfo`.
2. Attacker submits a standard SPL Token `Transfer` instruction moving an arbitrary amount of the coin (or pc) mint directly into `amm_coin_vault`, with no interaction with the Raydium AMM program at all.
3. Attacker (or any user) then calls `Deposit` or `Withdraw` with a minimal amount.
4. Inside processing, `calc_total_without_take_pnl_no_orderbook` (math.rs:238) picks up the inflated `amm_coin_vault.amount`, and `calc_take_pnl` (processor.rs:167) computes an inflated `x2_power`/diff, incrementing `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin` beyond what real trading fees would justify.
5. Subsequent `Withdraw` calls by legitimate LPs compute their redemption from the now-reduced `total_coin_without_take_pnl` (processor.rs:1719-1761), receiving less than their true pro-rata share, while the diverted amount sits in `need_take_pnl_*` awaiting extraction by `pnl_owner` via `process_withdrawpnl` (processor.rs:1505-1526).

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
