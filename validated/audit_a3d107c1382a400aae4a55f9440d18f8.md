Confirmed root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` computes and verifies the HMAC exclusively over the request body [2](#0-1) . The `shop` accessor, however, is taken straight from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header [3](#0-2) , and `Registry.process` forwards that unverified header value directly into `WebhookMetadata` handed to the app's handler after only checking the body HMAC [4](#0-3) .

### Title
Webhook `shop` identity is not bound to the HMAC, enabling cross-tenant webhook spoofing — (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw JSON body via HMAC-SHA256, while the `shop` (and `topic`/`webhook_id`/`api_version`) fields come from HTTP headers that are entirely outside the signed material. `Registry.process` trusts this header-derived `shop` and passes it straight to the app's webhook handler once the body HMAC checks out.

### Finding Description
The binding that should hold is: `hmac_valid(raw_body) ⇒ shop_header_is_authentic`. In reality the code only proves `hmac_valid(raw_body)`; the `shop-domain` header is never included in `to_signable_string` [1](#0-0) , so there is no cryptographic link between the verified body bytes and the shop attribution. `HmacValidator.validate` blindly recomputes the signature from `to_signable_string` and compares it to the supplied `hmac` [5](#0-4) ; it has no visibility into, and does not care about, the `shop` header. `Registry.process` then raises only if the HMAC over the body is bad, and otherwise builds `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., all sourced from headers [4](#0-3) .

Since every merchant/app-installer legitimately receives HMAC-valid webhook bodies for their own shop (e.g. `app/uninstalled`, `orders/create`, etc., which the gem's own docs show being processed by an app-controlled HTTP endpoint [6](#0-5) ), an attacker who controls a shop with the app installed can capture one of their own genuinely-signed webhook deliveries and replay the exact same body to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. Because the header is not part of the signed content, the HMAC still validates, and the handler executes application logic believing the data originated from the victim shop specified in the header.

### Impact Explanation
This breaks the tenant isolation the HMAC check is supposed to provide. If a webhook handler uses `WebhookMetadata#shop` to key any shop-scoped side effect (looking up/creating records, invalidating sessions, triggering `app/uninstalled` cleanup, writing merchant data, etc.), an attacker can force the app to perform that action against a shop they do not control, using only a webhook payload they legitimately received for their own store. This is cross-tenant access achieved without ever possessing the victim's credentials or access token, meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
Any developer/attacker can install the app on a shop they own (self-service in Shopify's app ecosystem), receive a validly HMAC-signed webhook for a real topic, and replay that exact HTTP body against the app's known/public webhook endpoint with a forged shop header — no secrets, tokens, or privileged access needed. The only requirement is that the target app's webhook handler keys off `shop` from `WebhookMetadata`, which is the documented, expected usage pattern for this gem [6](#0-5) .

### Recommendation
Bind the shop identity to the verified signature. Options: include the `shop-domain` header value in the signable string used for HMAC computation, or, upon successful body HMAC validation, cross-check that the `x-shopify-shop-domain` header matches a shop for which the app holds a known, previously-established relationship (e.g. an existing offline session) before invoking the handler, rejecting the webhook otherwise.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `app/uninstalled`) for that shop, capturing the raw HTTP request Shopify sends, including the valid `x-shopify-hmac-sha256` header for the JSON body.
2. Attacker resends the identical raw body and `x-shopify-hmac-sha256` header to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request` parses the forged headers; `HmacValidator.validate` recomputes the HMAC over `@raw_body` only [1](#0-0)  and it matches, since the body was untouched.
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [7](#0-6) , causing the app to act as though the event came from the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
