### Title
Webhook HMAC does not bind to the `shop`, `topic`, or `webhook_id` headers, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` only validates the HMAC over that body and then trusts the header-derived `shop`/`topic`/`webhook_id` to build the metadata handed to the app's webhook handler [3](#0-2) . This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold is `hmac_signed_bytes == (shop, topic, webhook_id, body)` but in fact `hmac_signed_bytes == body` only.

### Finding Description
`Webhooks::Request` normalizes headers and requires `topic`, `hmac-sha256`, and `shop-domain` to be present [4](#0-3) , but the value used to compute/verify the HMAC (`to_signable_string`) is solely `@raw_body` [1](#0-0) . The `shop`, `topic`, and `webhook_id` accessors read straight from the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers, none of which participate in the signature [2](#0-1) .

`Utils::HmacValidator.validate` simply recomputes an HMAC over `to_signable_string` and compares it to the `hmac` value [5](#0-4) , so it never detects that the headers were altered. `Registry.process` accepts the request purely based on this body-only HMAC check, then dispatches to the topic handler using the (unauthenticated) header values for `shop` and `webhook_id`: [3](#0-2) 

Because any given `(topic, body)` pair produces a fixed valid HMAC for the app's `client_secret`, once an attacker obtains one valid `(hmac, body)` pair for a topic (e.g., by triggering that same webhook event on a shop they control, since app developers can install their own app on their own dev/test store), they can replay that identical body+hmac to the app's public webhook endpoint while substituting the `shop-domain` (and/or `webhook_id`) header for a different, victim shop. The library will validate the HMAC successfully (it only checks the body) and hand the handler a `WebhookMetadata` claiming the victim shop, topic, and webhook id, with attacker-chosen body content applicable to that topic schema.

### Impact Explanation
This breaks the tenant-isolation binding between the cryptographically authenticated content (body) and the claimed origin (shop). A host application that trusts `WebhookMetadata#shop` to attribute incoming webhook data to a specific merchant (e.g., to update that shop's local records, revoke access, process `shop/redact`/`customers/redact` compliance actions, etc.) can be made to apply attacker-controlled webhook payloads under a victim shop's identity — a cross-tenant data-integrity/confusion issue reachable by an unprivileged party who can reach the app's public webhook endpoint and possesses at least one legitimately signed `(topic, body)` pair for that same app.

### Likelihood Explanation
Exploitability requires the attacker to first obtain one valid `hmac` for a chosen body/topic under the target app's secret. This is realistic in typical deployments: an attacker can install the same app on a shop they control (many Shopify apps are freely installable) and capture the resulting legitimately-signed webhook request, then replay it to the app's public webhook endpoint with a substituted `shop-domain` header. No possession of the app's `client_secret`, access tokens, or the victim shop's credentials is required — only a body+hmac pair that Shopify already delivered for some (any) shop.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or bind the full raw header set) in the HMAC-verified signable content, or otherwise cryptographically bind the header-derived identity fields to the signed payload, so that changing the `shop-domain`/`topic`/`webhook_id` header invalidates the signature. At minimum, document and enforce that consumers must not trust `WebhookMetadata#shop`/`webhook_id` without an independent verification against Shopify's known webhook delivery source (e.g., verifying the request truly originates from Shopify's IP ranges or re-fetching webhook state via the Admin API) since this gem does not itself bind them.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control) and triggers a webhook event (e.g., `orders/create`) with body `B`. Shopify sends a request with headers `shop-domain: attacker-shop.myshopify.com`, `hmac-sha256: H(secret, B)`, `topic: orders/create`.
2. Attacker captures `B` and `H(secret, B)`.
3. Attacker sends a forged HTTP POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H(secret, B)` (unchanged, still valid), but `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-webhook-id`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H(secret, B)`  — validation passes despite the shop header being attacker-controlled.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, webhook_id: attacker_chosen_id, ...)` [6](#0-5) , causing the host app to process attacker-controlled data attributed to the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
