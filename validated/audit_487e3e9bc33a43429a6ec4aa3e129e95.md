### Title
Webhook shop-domain/topic identity headers are trusted but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) from HTTP headers that are never included in the HMAC signature check, while `ShopifyAPI::Webhooks::Registry.process` only validates the HMAC and then forwards `request.shop` to the host application's handler as trusted tenant identity.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the HMAC (which covers the body bytes only) and then passes the unverified `shop` header straight through to the registered handler as the tenant identity for that webhook delivery: [3](#0-2) 

`HmacValidator.validate_signature` confirms this: the "verifiable" surface is whatever `to_signable_string` returns (body only), compared with `OpenSSL.secure_compare` against the computed signature: [4](#0-3) 

The identity binding that should hold is: **the shop/topic asserted to the handler == the shop/topic Shopify actually signed for**. Before the request sequence, that equality holds only for genuine, unmodified Shopify deliveries. After an attacker's request sequence — capturing any valid `(raw_body, hmac)` pair that was legitimately signed with the app's `client_secret` (e.g., from a webhook Shopify sent to the attacker's own shop/app installation, which the attacker fully controls and can trigger at will) and replaying it to the app's webhook endpoint with a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header — the equality breaks: `Utils::HmacValidator.validate` still returns `true` (it only checks the body signature), but `request.shop` now names an arbitrary shop of the attacker's choosing. Because a single app has one `client_secret` shared across every shop that installs it, any shop that installs the app can harvest a valid signed body from its own legitimate webhook traffic and forge headers to attribute that payload to a victim tenant.

### Impact Explanation
This breaks the shop-authenticated-versus-shop-trusted binding described in the analog rules: an unprivileged party who has merely installed the app on their own store (no `client_secret`, no access token, no privileged account required) can cause the host application's webhook handler to process attacker-chosen body content under an arbitrary victim `shop` value. If the host application uses `data.shop` to look up per-tenant session/state (a well-documented usage pattern shown in `docs/usage/webhooks.md`), this is a cross-tenant data-integrity/confusion vector qualifying as "cross-tenant access" under the Critical impact category, since the tenant boundary (which shop a webhook event is attributed to) is not authenticated by the gem despite being fully within its trust boundary.

### Likelihood Explanation
Likelihood is High for any app that has more than one installer (i.e., virtually any public or multi-merchant app): any merchant who installs the app can trigger webhooks to themselves (e.g., by creating an order to fire `orders/create`), capture the exact `raw_body` and `x-shopify-hmac-sha256` value Shopify sent them, and replay that pair to the app's public webhook endpoint with a forged `x-shopify-shop-domain`/`x-shopify-topic` header. No secrets, tokens, or elevated access are required beyond a standard app installation.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., verify `shop` against the session/store the app expects for that endpoint, or require Shopify's newer signed webhook envelope that ties headers to the signature) so that `Utils::HmacValidator.validate` fails whenever any of these fields are altered from what was actually signed by Shopify for that specific delivery.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` (attacker's own store, no special privileges needed).
2. Attacker triggers a webhook (e.g., creates an order) and captures the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent to the app's callback URL for `attacker-shop.myshopify.com`.
3. Attacker replays the exact same body + HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `OpenSSL::HMAC.hexdigest(sha256, client_secret, raw_body)` against the header HMAC — unaffected by the `shop-domain`/`topic` header values. [5](#0-4) 
5. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, i.e., the host app processes attacker-supplied data attributed to a shop the attacker never installed the app on. [6](#0-5)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
