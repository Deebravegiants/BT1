Confirmed: the gem's `to_signable_string` for webhooks binds the HMAC to `@raw_body` only, while `shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, entirely outside the signed bytes.### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only signs the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute that is read directly from the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. `Registry.process` validates the HMAC and then hands `request.shop` straight to the app's `WebhookHandler` as an authenticated tenant identifier, without the `shop` header ever being bound to the signature.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` for the webhook `Request` class returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers that are not part of this signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` field, so it never authenticates the `shop-domain` header: [3](#0-2) 

`Registry.process` raises only if the HMAC (body) check fails, and otherwise dispatches to the handler using `request.shop`/`request.topic` taken verbatim from headers: [4](#0-3) 

The identity binding broken here is: `shop header used to route/attribute the webhook == shop bytes covered by the HMAC signature`. The library computes HMAC over `body` only, but the `shop` value handed to the app-level handler (and typically used by hosting apps to key into per-tenant session/data lookups, per this gem's own webhook doc) is an unauthenticated header, i.e. `shop_used_for_tenant_dispatch != shop_bound_by_signature`.

### Impact Explanation
If an unprivileged party can capture one legitimate webhook delivery for shop A (its raw body plus its valid HMAC — webhook bodies/headers are commonly observable in logs, error trackers, proxies, or a previously-installed/uninstalled instance of the same app), they can replay that exact body+hmac to the app's public webhook endpoint while substituting `x-shopify-shop-domain` for shop B. `Registry.process` will validate successfully (the HMAC only checks the untouched body) and invoke the handler with `WebhookMetadata#shop == "shop-B"` even though the payload actually belongs to shop A. Any host application that trusts `data.shop` from this gem to select the tenant session/account (a documented, encouraged pattern in this repo's own `docs/usage/webhooks.md`) will attribute shop A's webhook data to shop B's tenant context — a cross-tenant data/attribution break reachable without any credentials, `api_secret_key`, or access token.

### Likelihood Explanation
Medium-High: obtaining one previously-delivered legitimate `(raw_body, hmac)` pair for any shop using the app (an attacker's own trial/dev store, a shared bug/testing store, or a leaked/logged webhook) is enough; the header value is fully attacker-controlled and unauthenticated, and no other secret material is required to replay it. This is a direct architectural consequence of the gem signing only the body, and every app that consumes `WebhookMetadata#shop` from this gem inherits this weak binding.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the bytes that are HMAC-verified, or otherwise fail closed if a caller relies on `request.shop` before independently corroborating it, and clearly document in `Registry.process`/`WebhookMetadata` that `shop` is not covered by the signature so host apps cannot mistake it for an authenticated field.

### Proof of Concept
```ruby
# 1. Capture a legitimate webhook delivery for "shop-a.myshopify.com":
raw_body = '{"id":1}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# 2. Replay the identical body/hmac, but swap the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "shop-b.myshopify.com", # attacker-chosen, unrelated shop
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HMAC validation passes (body untouched); handler receives
# WebhookMetadata(shop: "shop-b.myshopify.com", body: order data belonging to shop-a)
```
