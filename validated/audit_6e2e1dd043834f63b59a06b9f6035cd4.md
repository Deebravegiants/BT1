### Title
Shared, unrestricted `CallDispatcher` allows any user to plant a standing token allowance and drain funds transiting through it from unrelated orders - (File: `evm/src/utils/CallDispatcher.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`CallDispatcher.dispatch()` executes arbitrary attacker-supplied `Call[]` data with no caller restriction and no state isolation between callers. Because the same `CallDispatcher` instance is a shared, address-persistent utility reused by every order placed through `IntentGatewayV2` (and by `HyperFungibleToken`/`WrappedHyperFungibleToken`), a single unprivileged user can embed a `token.approve(attacker, type(uint256).max)` call inside their own order's `predispatch`/`postdispatch` calldata. This plants a permanent, unlimited ERC20 allowance from the `CallDispatcher` to the attacker that persists after the attacker's own transaction completes. Because the dispatcher is subsequently reused by every other user's orders — which transiently move tokens through it during the same atomic `predispatch`/`postdispatch` flow — the attacker's standing allowance lets them pull any of that token left in (or later held by) the dispatcher, even dust the post-execution sweep in `_execute`/`IntentsBase.sol` does not account for (since the sweep is scoped only to `order.output.assets`, not to every token an arbitrary `Call[]` might have touched).

### Finding Description
`CallDispatcher.dispatch()` has no access control: [1](#0-0) 

It is invoked with fully attacker-controlled calldata from `IntentsBase._execute` (postdispatch) and from the predispatch flow in `IntentGatewayV2.sol` (`ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`), both using the single `_params.dispatcher` address shared by the whole gateway deployment: [2](#0-1) 

The sweep-back logic that is supposed to return residual dispatcher balances only iterates over the specific `order.output.assets` tokens declared by *that* order: [3](#0-2) 

Nothing prevents a user's own `Call[]` from calling `approve(attacker, type(uint256).max)` on any arbitrary ERC20 token — this call succeeds (it doesn't move balance, so it passes unnoticed by dust/sweep accounting) and leaves a standing allowance from the `CallDispatcher` address to the attacker that is never revoked by the protocol. The project's own documentation acknowledges the dispatcher "holds tokens temporarily during execution" and warns integrators to "use exact amounts rather than unlimited allowances," confirming the contract provides no on-chain protection against this and relies purely on caller discipline: [4](#0-3) 

Because the dispatcher address is a single shared piece of infrastructure reused across every unrelated order and every `HyperFungibleToken`/`WrappedHyperFungibleToken` transfer that carries calldata, any token that subsequently transits the dispatcher (predispatch assets, postdispatch outputs, or any dust missed by a sweep that is scoped only to the current order's known assets) becomes claimable by the attacker's earlier-planted allowance — with no compromise of governance or any privileged role required, unlike the original report which needed a malicious/compromised protocol governance.

### Impact Explanation
This allows direct theft of user/protocol funds that transit the shared `CallDispatcher`: any ERC20 amount left in or passing through the dispatcher for a token the attacker previously targeted with a planted `approve()` can be pulled out via a plain `transferFrom` call, entirely outside the protocol's own dust-sweep accounting. This is a fund-theft vector reachable from a single unprivileged order placement.

### Likelihood Explanation
Likelihood is high: placing an order with a crafted `predispatch`/`postdispatch` `Call[]` is the normal, permissionless entry point for any user of `IntentGatewayV2`, `HyperFungibleToken`, or `WrappedHyperFungibleToken`. No special privileges, timing races, or governance compromise are needed to plant the allowance; only a subsequent transit of the targeted token through the same dispatcher (which happens continuously as it is shared infrastructure) is needed to realize the theft.

### Recommendation
Do not allow calldata executed on behalf of one order to leave standing state (e.g., allowances) on the shared `CallDispatcher`. Options: (1) deploy a fresh, ephemeral dispatcher (e.g., via `CREATE2`/minimal proxy) per order/execution so no allowance can outlive a single atomic call; (2) have `CallDispatcher` revoke any allowance it granted to non-protocol addresses at the end of `dispatch()`; (3) restrict `dispatch()` to be callable only by the registered gateway/app contracts, and have those contracts explicitly disallow `approve`-selector calls whose spender is not an allow-listed protocol contract (e.g., a router configured by governance) rather than an arbitrary order-supplied address.

### Proof of Concept
1. Attacker places an `Order` on `IntentGatewayV2` whose `predispatch.call` (or `output.call` for postdispatch) is `abi.encode([Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})])`. `_execute`/`ICallDispatcher(dispatcher).dispatch(...)` executes it as-is; there is no balance check that would flag the missing corresponding `output.assets` entry for USDC, since `approve` moves no balance and the sweep only inspects `order.output.assets`.
2. This grants `CallDispatcher -> attacker` an unlimited USDC allowance that persists on-chain indefinitely.
3. Later, any unrelated order (from any other user) whose `predispatch.assets`/`output.assets` includes USDC transiently moves USDC balance into the same `_params.dispatcher` address as part of its own atomic flow, or leaves USDC dust the sweep in that order does not fully collect (e.g., a token received as an intermediate/unlisted asset from a nested swap call).
4. The attacker calls `USDC.transferFrom(dispatcher, attacker, amount)` directly using the standing allowance from step 2 to drain any USDC balance sitting on the dispatcher, without needing to call `CallDispatcher.dispatch()` again or interact with `IntentGatewayV2` at all.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
