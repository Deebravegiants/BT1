Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `api_version`, and `webhook_id` values taken directly from unauthenticated HTTP headers when constructing `WebhookMetadata` passed to the host app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with `to_signable_string` returning only `@raw_body`: [1](#0-0) [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read from the `shopify-*`/`x-shopify-*` HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates HMAC over the body only, then blindly forwards the header-derived `shop` (and other header fields) to the registered handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body for webhooks) and compares it against the received HMAC using the app-wide `Context.api_secret_key`: [4](#0-3) 

The identity binding that should hold is: `shop header == shop whose HMAC-signed body this is`. Because `shop` is excluded from `to_signable_string`, this equality is never checked. Since Shopify signs webhook bodies using the single app-wide `client_secret` (the same secret for every shop that installs the app), a genuine webhook delivery for Shop A (valid body + valid HMAC computed with the app's secret) remains HMAC-valid even if the `shop-domain` (and `topic`/`webhook_id`/`api_version`) headers are swapped to claim it originated from Shop B. `Registry.process` has no code path that cross-checks the claimed `shop` against anything tied to the signed content, so the swapped identity passes straight through to the host application's webhook handler as authenticated `WebhookMetadata`.

### Impact Explanation
Any entity able to install the app on one shop (an ordinary, unprivileged merchant/internet user — no `api_secret_key`, access token, or privileged account required) can capture a legitimately HMAC-signed webhook body delivered to their own shop's endpoint, then replay it to the app's webhook endpoint with a forged `shop-domain` header naming a different, unrelated tenant. Because the gem's `HmacValidator` only authenticates the body and never binds it to the shop header, the request is accepted as valid, and the host application's webhook handler receives attacker-controlled `shop`/`topic`/`webhook_id`/`api_version` values it will typically use to look up and mutate that victim shop's records (session lookup, order/customer state, mandatory GDPR redact flows, etc.). This is a cross-tenant identity-binding break rooted in this gem's own verification logic, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is meaningful: obtaining a legitimately signed webhook body only requires installing the app on any shop (the barrier all Shopify apps expect anyway), and forging or replaying HTTP headers to the app's public webhook endpoint requires no secret material at all — just observing one's own valid webhook traffic and re-POSTing it with a different `shop-domain`/`topic` header combination that matches a topic registered in the app's `Registry`.

### Recommendation
Bind the claimed `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified content, e.g., have `Webhooks::Request#to_signable_string` incorporate the shop header (or verify shop ownership independently, such as cross-referencing against a session/store previously established via OAuth for that exact shop) before trusting `request.shop` in `Registry.process`. At minimum, document and enforce that host applications must independently verify the `shop` header against their own stored tenant registry rather than trusting it as authenticated solely because the body's HMAC passed.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a real webhook delivery, e.g. for `orders/create`, to the app's registered webhook endpoint. Shopify signs the raw JSON body with the app's single `client_secret` and sends headers:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body computed with app client_secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: ...
   x-shopify-api-version: 2024-01
   ```
2. Attacker captures this raw body + `x-shopify-hmac-sha256` value (both are visible to them as the endpoint owner of the traffic, or via any reverse proxy/logging they control in front of their own app instance in multi-tenant deployments).
3. Attacker resends the identical body and HMAC header to the same webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only (see `lib/shopify_api/utils/hmac_validator.rb:26-31`) and it matches, since the body/signature pair is untouched.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) passes HMAC validation and calls the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's order body>, ...)`, causing the host app to act on `victim-shop.myshopify.com` using attacker-supplied/forged shop identity, despite the request never actually being signed by/for that shop.
