### Title
Unauthenticated relayer-address spoofing in `handle_get_requests` allows theft of GET-request reputation rewards and forged fee/receipt attribution - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
`handle_get_requests` accepts a caller-supplied `address: Vec<u8>` field inside `GetRequestsWithProof` and uses it, completely unverified, both to mint reputation rewards and to permanently record who "delivered" a GET response — the same trust-an-unauthenticated-identity-claim pattern as the CF-Connecting-IP bug (trusting a spoofable, attacker-controlled field as if it were a verified identity).

### Finding Description
`GetRequestsWithProof` carries an `address: Vec<u8>` field documented as "Address that should be credited with fees" [1](#0-0) . `handle_get_requests` cryptographically verifies the *requests* (membership proof of commitments) and the *responses* (state proof of the requested keys) against Hyperbridge's stored state commitments [2](#0-1) , but never verifies that `address` — the claimed relayer/deliverer identity — actually corresponds to the caller or to any signature over the payload. It is simply destructured out of the submitted message and trusted as-is.

That unverified `address` is then used for two consequential, security-relevant actions:

1. **Reputation minting**: if `address` decodes to 32 bytes, it is minted `ReputationAsset` tokens proportional to `total_bytes` at the configured per-byte rate, with no ownership or signature check tying the address to whoever actually paid for/verified the bandwidth being metered [3](#0-2) .
2. **Permanent on-chain attribution**: `host.store_response_receipt(&get_response, &address)` writes `address` into the `RequestReceipts`/response-receipt storage as the recorded "delivering relayer" for that GET response, and `dispatch_get_response` is called with the same unverified address [4](#0-3) .

This mirrors the HestiaCP class of bug precisely: a value that should represent a verified network/identity fact (the CF-Connecting-IP "true client IP", here the "delivering relayer identity") is instead taken directly from an untrusted, attacker-controlled input field with no cryptographic binding (no signature check comparable to the `Signature::Evm`/`Signature::Sr25519` recovery-and-match pattern used elsewhere in the codebase, e.g. in `pallet_ismp_relayer`'s outbound-request delivery claim, where the signer recovered from a signature must equal the address proven in `RequestReceipts` [5](#0-4) , or the `accumulate_fees` beneficiary-redirect flow which requires a signature over `beneficiary_message` before crediting a different address [6](#0-5) ). `handle_get_requests` has no equivalent check at all — `address` is accepted at face value.

### Impact Explanation
Any caller who can submit a valid `GetRequestsWithProof` (an unauthenticated/unsigned dispatch path, matching the same "unsigned extrinsic reachable by anyone" pattern used throughout `pallet-relayer`'s claim extrinsics) can name an arbitrary 32-byte address as the "relayer" and:
- Mint themselves (or any address they choose) reputation tokens for bandwidth they may not have actually delivered/paid for, since the address has no relationship to the entity that produced or funded the proofs.
- Poison the on-chain `RequestReceipts`/response-receipt record with a forged relayer identity, which downstream relayer-fee-accounting logic (`decode_receipt_relayer` in `modules/pallets/relayer/src/accumulate.rs`) treats as the authoritative record of who delivered a request/response when attributing withdrawal fees [7](#0-6) . Because this attribution is written unauthenticated, an attacker can direct future GET-related fee credit toward an address they control instead of the actual deliverer, resulting in theft of relayer rewards — the same "authentication bypass via spoofed identity field" impact class as the reference CVE, applied to fund flows instead of login controls.

### Likelihood Explanation
High: `handle_get_requests` is reachable from any submitted message carrying valid request/response proofs (the same proofs any relayer must already produce to deliver GET requests), and the only additional requirement to exploit the flaw is choosing an arbitrary value for `address` instead of one's own key — no signature, no extra proof, no privileged origin needed.

### Recommendation
Require `address` to be authenticated the same way other reward/fee-attribution paths in this codebase are: bind it to a signature over the response/commitment set (mirroring `outbound_request_delivery_message`/`beneficiary_message` signing) and verify the recovered signer equals `address` before minting reputation or writing it into `store_response_receipt`. Alternatively, derive the credited address from the transaction's verified signer/origin rather than an unchecked payload field.

### Proof of Concept
1. Attacker (or colluding submitter) constructs valid `requests`, `source` proof, and `response` proof exactly as an honest relayer would (these are independently verifiable and don't require attacker identity).
2. Attacker sets `address` to their own 32-byte account instead of the account of whichever party actually produced/paid for the underlying delivery work.
3. Submit `GetRequestsWithProof` via `handle_get_requests`.
4. Verification of requests/responses passes (proofs are legitimate); `address` is never checked against any signature.
5. `Pallet::<T>::deposit_event(Event::ReputationMinted { relayer: attacker_account, ... })` mints reputation to the attacker, and `store_response_receipt(&get_response, &attacker_address)` permanently records the attacker as the delivering relayer, later consumed by `decode_receipt_relayer` in fee-accumulation flows.

impl<T: Config> Pallet<T> {
	/// Decode a proven `RequestReceipts[commitment]` value into the delivering
	/// relayer's bytes. EVM stores the address RLP encoded, substrate stores the
	/// signer bytes or a signature to recover the signer from. Used by both fee
	/// accumulation and the outbound request delivery claim.
	pub fn decode_receipt_relayer(state_id: StateMachine, raw: &[u8]) -> Result<Vec<u8>, Error<T>> {
		match state_id {
			s if crate::is_pharos(&s) =>
				if raw.len() == 32 {
					Ok(Address::from_slice(&raw[12..]).0.to_vec())
				} else {
					Err(Error::<T>::ProofValidationError)
				},
			s if s.is_evm() => {
				use alloy_rlp::Decodable;
				Ok(Address::decode(&mut &*raw)
					.map_err(|_| Error::<T>::ProofValidationError)?
					.0
					.to_vec())
			},
			s if s.is_substrate() => {
				use codec::Decode;
				let bytes =
					<Vec<u8>>::decode(&mut &*raw).map_err(|_| Error::<T>::ProofValidationError)?;
				Ok(if bytes.len() > 32 {
					Signature::decode(&mut &*bytes)
						.map_err(|_| Error::<T>::SignatureDecodingError)?
						.signer()
				} else {
					bytes
				})
			},
			_ => Err(Error::<T>::MismatchedStateMachine),
		}
	}
