### Title
Webhook HMAC only signs the request body, leaving the `shop-domain` (and `topic`/`webhook-id`) header completely unauthenticated, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies its HMAC exclusively over the raw JSON body, while the shop identity attached to the processed event is taken from an unsigned HTTP header. Any party that can obtain one valid `(body, hmac)` pair for the app's shared `client_secret` (e.g. by installing the same public app on their own store) can replay that exact payload against the webhook endpoint while substituting the `shop-domain` header for a different, victim tenant, and the gem will accept and process it as if it belonged to that victim shop.

### Finding Description
The `to_signable_string` used to verify the webhook signature only returns the raw body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` fields that are handed to the application's handler are all pulled straight from HTTP headers, none of which are included in the HMAC computation: [2](#0-1) 

`HmacValidator.validate` only checks the signature against `to_signable_string` (i.e., the body) using the app's single, shop-independent `api_secret_key`: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC and then dispatches the handler using the unverified `request.shop`: [4](#0-3) 

Binding that should hold: `Verified(bytes) == Trusted(shop)` for the tenant context passed to the handler. In reality `Verified(bytes) = HMAC_secret(raw_body)` and `Trusted(shop) = header["x-shopify-shop-domain"]` — two disjoint sets of bytes. Because the same `client_secret` is used to sign webhooks for every shop that installs the app, a `(raw_body, hmac)` pair valid for shop A is *also* a cryptographically valid pair for any other shop, since the shop is never part of the signed content. An attacker who legitimately installs the app on a store they control (an unprivileged action open to any internet user for a public app) will receive genuine webhooks with valid HMACs for their own shop's body. They can then POST that identical body/HMAC to the app's webhook endpoint with `shop-domain` header rewritten to a victim shop, and the gem's own validation logic will accept it and hand the victim's identity to the handler.

### Impact Explanation
This breaks the tenant-identity binding the handler relies on (`WebhookMetadata#shop`), letting one tenant forge webhook events attributed to a different tenant (cross-tenant access), which the rules classify as Critical impact. Downstream effects depend on the host app's handler (e.g. jobs keyed by `shop_domain`, as shown in the docs example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), but the gem itself provides no way to distinguish "this body was really destined for this shop" — it hands over attacker-controlled tenant attribution as if it were verified. [5](#0-4) 

### Likelihood Explanation
Likelihood is realistic: obtaining a public app on the Shopify App Store and installing it on an attacker-controlled development/trial store is an unprivileged action; genuine webhooks (with valid HMAC over body) will then be delivered to the attacker for their own shop. Replaying that body with a modified `shop-domain` header against the shared webhook endpoint requires no secret knowledge and no privileged access — only the ability to send an HTTP POST.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed content verified by `HmacValidator`, or otherwise cryptographically bind the shop identity to the payload (e.g., verify the shop against a previously-stored per-shop webhook secret or session record) before handing `request.shop` to the handler in `Registry.process`.

### Proof of Concept
1. Install the target public app on an attacker-controlled store `attacker.myshopify.com`.
2. Trigger a subscribed webhook topic (e.g. `orders/create`); capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because it is computed with the app-wide `client_secret`, not a per-shop secret.
3. Resend the identical raw body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the (unchanged) body against the (unchanged) HMAC.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim.myshopify.com"`, causing the host application to process attacker-controlled data as though it originated from the victim tenant.
