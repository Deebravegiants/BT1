## Title
Webhook `shop-domain` (and `topic`/`api_version`/`webhook_id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching webhook data to the app's handler, but the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. The `shop-domain`, `topic`, `api_version`, and `webhook_id` values — all taken verbatim from unauthenticated HTTP headers — are then passed straight through to the handler as trusted, verified metadata.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` checks only this body-only HMAC, then immediately builds `WebhookMetadata` using `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` — all of which come from HTTP headers that are never part of the signed content: [3](#0-2) 

`request.shop`, `request.topic`, etc. are read straight from headers with no cross-check against the body or the HMAC: [4](#0-3) 

The gem's own documentation reinforces the false assumption that `process` fully authenticates the request: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook." [5](#0-4) 

**The broken identity binding, stated as an equality that should hold but doesn't:**
`hmac_valid(raw_body) == true` is treated by `Registry.process` as equivalent to `shop_header == actual_tenant_that_generated(raw_body, hmac)`. In reality the HMAC binds only `raw_body`↔`api_secret_key`; it says nothing about which shop, topic, or webhook id the body belongs to, since those fields travel in unsigned headers.

### Impact Explanation
Any merchant/tenant using a multi-tenant app built on this gem automatically receives legitimately-signed webhook deliveries for their own store (this happens by design once webhooks are registered). Because the signature covers only the body, that same merchant can capture one of their own valid `(raw_body, X-Shopify-Hmac-Sha256)` pairs and replay it directly against the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with an arbitrary victim shop's domain. `HmacValidator.validate` still passes (it only hashes the body), and `Registry.process` hands the handler a `WebhookMetadata` object claiming the (attacker-chosen) body belongs to the victim shop. Any host application that — per the gem's documented contract — trusts `data.shop` after `process` succeeds (e.g., to select the victim's access token/session, update the victim's local records, or attribute the payload to the victim tenant) will process attacker-controlled data as if it originated from a different tenant. This is a cross-tenant data-integrity/confusion vulnerability reachable without any credentials, TLS interception, or privileged access — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops (the normal SaaS model for Shopify apps): every installed shop is itself a source of at least one valid `(body, hmac)` pair, and the webhook endpoint is a public, unauthenticated HTTP endpoint by design (Shopify webhook receivers must accept POSTs without prior session state). No secret material is required — only a previously-received, legitimate webhook for the attacker's own shop.

### Recommendation
Bind the tenant-identifying and routing fields into the signed content, or otherwise verify them out-of-band before trusting them:
- Extend `VerifiableQuery`/`to_signable_string` (or add a separate check in `HmacValidator`/`Registry.process`) to include `shop`, `topic`, `webhook_id`, and `api_version` in the signable material, matching how Shopify actually authorizes the delivery, and/or
- Require the caller to supply the expected shop (from an already-established, authenticated relationship, e.g. a registered webhook's shop) and assert `request.shop == expected_shop` before dispatch, and
- Correct the documentation so it no longer states that `process` "verifies the request did indeed come from Shopify" as a blanket guarantee — clarify that only the body is authenticated and that `shop`/`topic`/`webhook_id` must be independently validated by the host application against known, previously-registered tenants.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both subscribed to the `orders/create` topic.
2. Shopify delivers a legitimate webhook to the app's public endpoint for `attacker-shop.myshopify.com`:
   ```
   POST /callback/orders/create
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of raw_body computed with api_secret_key>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: <attacker's own order JSON, fully attacker-controlled since it's their own store>
   ```
   The attacker (who owns this shop) captures this raw body and HMAC.
3. Attacker replays the exact same raw body and HMAC to the app's same public endpoint, but sets:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the unchanged raw body and succeeds — `verify` passes.
5. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` and calls the app's handler as if `victim-shop.myshopify.com` sent this attacker-controlled order payload, achieving cross-tenant data injection/confusion.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
