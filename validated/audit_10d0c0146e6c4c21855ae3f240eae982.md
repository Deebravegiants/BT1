### Title
Cross-tenant webhook forgery via `shop-domain` header not bound by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request **body**, then trusts the unauthenticated `shopify-shop-domain` HTTP header to decide which shop the event belongs to. Because the HMAC never covers the shop identity, an attacker who can obtain one valid `(body, hmac)` pair for the app (trivially, by installing the app on their own development store) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header of any victim shop, causing the app to process the webhook as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `topic`, `shop`, `api_version`, and `webhook_id` from HTTP headers: [1](#0-0) 

but the value it signs and verifies (`to_signable_string`) is only the raw JSON body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e. the body, using the app's single, tenant-agnostic `api_secret_key`: [3](#0-2) 

`Registry.process` uses this body-only HMAC check as its sole authentication gate, then dispatches the handler using the **unverified** `request.shop` header: [4](#0-3) 

Because the same `api_secret_key` is used for every shop that installs the app, and the HMAC signs only the body (not the shop, topic, or webhook-id headers), any body whose content is identical or predictable across shops (e.g. the empty-body `app/uninstalled`/mandatory-compliance topics, or any webhook payload an attacker can learn) yields the exact same HMAC value for every tenant. An attacker who installs the app on their own store receives real, validly-signed webhooks; they can capture the `(body, hmac)` pair from their own tenant and then forge an HTTP POST directly to the app's webhook endpoint with the victim's `shopify-shop-domain` header, an arbitrary/duplicated `webhook-id`, and any `topic` the attacker's captured body also matches. `HmacValidator.validate` accepts it because the body's HMAC is correct, and `Registry.process` builds `WebhookMetadata` with `shop: request.shop` — the attacker-chosen victim shop — before invoking the app's business-logic handler.

The identity binding that should hold is:
`shop authenticated by HMAC == shop the handler acts on`
but in this implementation:
`shop covered by HMAC (none) ≠ shop used for dispatch (request.shop header)`

### Impact Explanation
This is a cross-tenant access vulnerability (Critical): an unprivileged internet user who can install the target app on their own store (a normal, unprivileged action available to any Shopify merchant) can then trigger the app's webhook-driven business logic — data deletion (GDPR `shop/redact`, `customers/redact`), cache invalidation, order/inventory sync, uninstall cleanup, etc. — under the identity of any other shop that uses the same app, without possessing that shop's credentials, access token, or `client_secret`. Depending on what the app does inside its webhook handlers, this can lead to unauthorized data mutation, deletion, or disclosure scoped to a victim tenant.

### Likelihood Explanation
Any Shopify merchant/developer can freely install a public app (or the attacker's own copy of a private app they're testing) to obtain real, correctly-signed webhook deliveries. Many mandatory/administrative webhook topics have empty or highly predictable bodies (`"{}"`, as used even in this repo's own test fixtures), making the HMAC trivially replayable across tenants. No secret material belonging to the victim or the app itself needs to be obtained — the gem's own signing key naturally produces identical signatures for identical bodies regardless of which shop they came from, and the library does nothing to bind the header-derived shop to that signature.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the value that gets HMAC-verified, or otherwise cryptographically bind the `shopify-shop-domain` header to the signed payload before trusting it for dispatch. At minimum, `Registry.process` should cross-check the `shop` header against an expected/registered shop for the given webhook subscription (e.g., by looking up the session/shop associated with the delivery) rather than trusting the header value outright once body-HMAC validation succeeds.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, receives a real webhook for a topic with a fixed/empty body, e.g.:
   - Headers: `shopify-topic: app/uninstalled`, `shopify-hmac-sha256: <valid-hmac-for-"{}"->`, `shopify-shop-domain: attacker.myshopify.com`
   - Body: `"{}"`
2. Attacker computes/observes that `hmac = OpenSSL::HMAC.digest(SHA256, api_secret_key, "{}")` is identical for any shop, since the signable string used by `HmacValidator` never depends on the shop: [5](#0-4) 
3. Attacker sends a forged POST directly to the app's public webhook endpoint using the same body `"{}"` and same valid `hmac`, but sets:
   - `shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new` parses these headers successfully (they only check presence, not authenticity of shop): [6](#0-5) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because the body HMAC matches, then invokes the app's handler with `shop: request.shop` = `"victim-shop.myshopify.com"`: [7](#0-6) 
6. The app's webhook handler executes business logic (e.g., deleting the app's stored data, triggering redaction flows, invalidating sessions) believing the event genuinely originated from `victim-shop.myshopify.com`, achieving cross-tenant impact without any credential belonging to the victim.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
