### Title
Accrual panics on `supplied × index` i128 overflow before the index cap engages, permanently freezing a whale-scale market — (`contracts/pool/src/interest.rs`)

### Summary
The analog of CVE-2020-37182 (oversized input overflowing a fixed-size buffer and crashing the process) is a numeric overflow on the pool's accrual path. Every state-mutating entry point in the pool first runs `global_sync`, which calls `accrue_step`. Inside `accrue_step`, `scaled_to_original`/`update_supply_index`/`calculate_supplier_rewards` compute `scaled.mul(index)`, a RAY×RAY product that must fit in `i128`. The borrow index is nominally capped at `MAX_BORROW_INDEX_RAY = 10^36`, but at ~1e36 scaled `supplied` (≈1 billion whole units of an 18-decimal token) the product `supplied × index` overflows `i128` (max ≈ 1.7e38) once the index merely reaches ~170× — far below the cap. The panic is unrecoverable, so the market is frozen forever: no withdraw, repay, liquidation, or bad-debt cleanup can execute.

### Finding Description
`global_sync` runs on every mutating pool call and iterates `accrue_chunk` until caught up [1](#0-0) . Each chunk calls `accrue_step`, which first computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` [2](#0-1) , both of which are plain `scaled.mul(index)` [3](#0-2)  that widen to `I256` only for the intermediate product — the result still must fit `i128`. `update_supply_index` and `calculate_supplier_rewards` repeat the same multiply [4](#0-3) [5](#0-4) . `update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY` only after the multiply [6](#0-5) , so the cap cannot prevent the value-product overflow. The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the cliff on the XLM curve at 98% utilization, after which `try_withdraw_raw` and `try_repay` both revert with `MathOverflow` [7](#0-6) .

### Impact Explanation
Permanent freezing of funds. Once `borrowed_scaled × new_borrow_index` (or `supplied_scaled × supply_index`) exceeds `i128::MAX`, every entry point — `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, `update_indexes` — accrues first and panics atomically. Suppliers cannot exit, borrowers cannot repay, liquidators cannot seize. The condition is monotone (indexes only grow, modulo bad-debt write-down that only lowers the supply index), so the freeze cannot be undone by anyone, including governance. All token balances backing the frozen market are locked in the pool contract forever.

### Likelihood Explanation
An unprivileged user can set it up: supply ~1e9 whole units of a high-decimals listed asset (caps must be lifted or absent on that market — caps are a config choice, not a code invariant) and borrow to high utilization via normal `supply`/`borrow` calls, optionally using `multiply`. From there it is purely time-driven: sustained high utilization grows the index deterministically, and any subsequent interaction (or anyone's `update_indexes` call) trips the overflow. It requires whale-scale capital in one market and the index must grow ~170×, so it is a slow-burn rather than an instant attack — but no privileged action is involved, and once triggered it is irreversible. Likelihood is gated mainly by whether a high-decimals market can reach ~1e36 scaled supplied; the repository's own test confirms the arithmetic path is reachable within the tested time horizon.

### Recommendation
Saturate rather than panic on the value ceiling. In `update_supply_index`/`calculate_supplier_rewards`/`scaled_to_original`, clamp the product at `i128::MAX` (or at the index cap boundary) instead of reverting, mirroring how `update_borrow_index` already clamps the index itself and how `mul_div_floor_saturating` clamps elsewhere. Alternatively, cap `borrow_index`/`supply_index` at a level derived from the live `supplied`/`borrowed` scaled amounts (`MAX = i128::MAX / scaled`) so the index stops growing before the value product overflows — effectively moving the existing index cap lower for whale markets. A short-term mitigation is enforcing per-market supply caps that keep `scaled × MAX_SUPPLY_INDEX_RAY < i128::MAX` at listing time via `require_cap_within_asset_domain`.

### Proof of Concept
Reproduced by the in-repo harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`:

1. List `BIG18` (18 decimals) on the XLM rate curve; disable/lift utilization and supply caps (`lift_caps`, `with_max_utilization_disabled_all_markets`).
2. BOB: `supply(BIG18, 1e9 × 10^18)` → scaled `supplied ≈ 1e36` raw ray.
3. ALICE: supply `COL` collateral, `borrow(BIG18, 0.98 × supplied)` → 98% utilization on the steep curve segment.
4. Advance time year-by-year calling `update_indexes`. On the iteration where `borrowed_scaled × new_borrow_index > i128::MAX`, `accrue_step` panics with `GenericError::MathOverflow` inside `scaled_to_original`/`calculate_supplier_rewards`, while `borrow_index < MAX_BORROW_INDEX_RAY` (the cap never engaged).
5. Thereafter `withdraw(BIG18, 1)` and `repay(BIG18, 1.0)` both revert with `MathOverflow` — asserted in the test — and every other mutating verb shares the same accrue-first path. The market is permanently frozen.

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
