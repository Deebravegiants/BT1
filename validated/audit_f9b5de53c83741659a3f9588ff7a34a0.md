## Title
Unauthenticated pipeline run resumption endpoint allows unauthorized state mutation of job runs - ([File: core/web/router.go])

### Summary
The report's bug class is a state-mutating function missing an access-control modifier, allowing any caller to reach it and lock/manipulate state that only a privileged actor should control. The strongest analog in this codebase is the `/v2/resume/:runID` route, which is registered under the unauthenticated route group and lets any unprivileged caller resume a pipeline run.

### Finding Description
In `core/web/router.go`, the `v2Routes` function registers most pipeline-run routes under `authv2`, which requires authentication via `auth.Authenticate(...)` (token or session). However, the `Resume` endpoint is explicitly registered on the unauthenticated group: [1](#0-0) 

```
unauthedv2 := r.Group("/v2")

prc := PipelineRunsController{app}
psec := PipelineJobSpecErrorsController{app}
unauthedv2.PATCH("/resume/:runID", prc.Resume)

authv2 := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(),
	auth.AuthenticateByToken,
	auth.AuthenticateBySession,
))
```

The handler itself, `PipelineRunsController.Resume`, performs no authorization check of its own — it parses the `runID` from the path, decodes an arbitrary JSON body into a `pipeline.ResumeRequest`, and directly calls `prc.App.ResumeJobV2(ctx, taskID, result)` to mutate pipeline-run state: [2](#0-1) 

The audit log entry name `audit.UnauthedRunResumed` confirms this route is intentionally unauthenticated by design (likely to support async bridge/external-adapter callbacks using the run's UUID as an implicit bearer token). The security of this endpoint therefore depends entirely on the `runID` UUID being unguessable and never disclosed to third parties. I was unable to fully verify within the available index whether `runID` (the pending task's UUID) is ever exposed to less-trusted contexts (e.g., returned in API responses to lower-privileged users, logged, or included in outbound bridge/adapter requests in a way that could leak to a third party), which would be necessary to escalate this into a genuine unauthorized-mutation vulnerability rather than an intentional capability-token design.

### Impact Explanation
If the run UUID used as `runID` can be observed or guessed by an unprivileged actor (e.g., via logs, error messages, or a bridge/adapter response), that actor could resume/complete a pending pipeline task with arbitrary attacker-controlled JSON data without any authentication, effectively forging the completion of an async task (such as an ETH tx confirmation callback or an external bridge response) that only the corresponding integration should be able to submit. This is analogous to the original issue's fund-lock/asset risk: an arbitrary caller can push protected state machinery it should not control, potentially disrupting job execution, corrupting pipeline results consumed downstream (including those that drive on-chain transactions), or causing runs to be marked complete/failed maliciously.

### Likelihood Explanation
Likelihood is uncertain without further investigation. The endpoint is deliberately unauthenticated (per the `UnauthedRunResumed` audit event name), meaning this may be an accepted design tradeoff relying on UUID secrecy rather than a genuine oversight like the original `PureTokenAdapter.deposit()` missing-modifier bug. I could not confirm from the indexed code whether the `runID` value is adequately protected from disclosure to unprivileged parties in all code paths (e.g., whether it's ever surfaced in a response body, webhook payload echoed back to less-trusted callers, or verbose logs). Without that confirmation, this should be treated as a design pattern to review rather than a confirmed vulnerability.

### Recommendation
- Audit every code path where the resume-task UUID is generated and transmitted (e.g., outbound bridge/adapter HTTP requests, logs) to confirm it is never exposed to a party less trusted than the intended resumer.
- Consider requiring an additional secret/HMAC signature bound to the task alongside the UUID for the `/v2/resume/:runID` callback, rather than relying solely on UUID unguessability.
- If the endpoint must remain unauthenticated for async callback compatibility, ensure `ResumeJobV2` validates that the task is still in a pending/awaiting state expecting external input, rejecting resumes for tasks not in that specific state, to reduce the blast radius of a leaked/guessed UUID.

### Proof of Concept
Not verified end-to-end due to indexing limits on how `runID` values are generated/propagated (`core/services/pipeline/runner.go`, `task.eth_tx.go`, `task.bridge_test.go`). Conceptually:
1. Obtain or guess a pending task's `runID` (UUID) for a job run awaiting external resumption.
2. Send `PATCH /v2/resume/<runID>` with an arbitrary JSON body without any authentication header/cookie.
3. `PipelineRunsController.Resume` ( [2](#0-1) ) accepts the request and calls `App.ResumeJobV2`, mutating pipeline-run state with attacker-supplied data.

Because I could not confirm actual disclosure of `runID` values to unprivileged actors within the indexed codebase, I recommend starting a Devin session to trace `runID` generation and propagation through `core/services/pipeline/runner.go` and related bridge/eth_tx task code to conclusively determine exploitability.

func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
