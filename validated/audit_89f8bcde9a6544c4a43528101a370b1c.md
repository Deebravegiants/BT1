The relevant identity-binding gap here is in the webhook verification path, where the HMAC signature only ever covers the raw request body, while the shop identity that gets propagated to the app's business logic is taken from an unsigned header.

### Title
Webhook Shop Domain Header Not Covered by HMAC, Allowing Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that body [1](#0-0) . The `shop` value used everywhere downstream, however, is read straight from the `x-shopify-shop-domain` HTTP header, which is not part of the signed payload [2](#0-1) . `Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, without ever binding that shop value to the signature that was checked [3](#0-2) .

### Finding Description
The identity binding that should hold is: `bytes verified by HMAC == bytes that determine the shop the webhook is attributed to`. In this gem that equality does not hold:

- `HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header [4](#0-3) .
- For webhook requests, `to_signable_string` is simply `@raw_body` [1](#0-0) .
- `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read from HTTP headers that are never included in the signed string [5](#0-4) .
- `Registry.process` raises only if the HMAC over the body fails; it then unconditionally forwards `request.shop` to the registered handler as the authoritative tenant identifier [3](#0-2) .

Because the shop-domain header is unauthenticated, any unprivileged internet user who can obtain one validly-signed webhook body (trivially available: they can create their own free/dev shop, trigger a webhook such as `orders/create` for an order in their own store, and capture the raw POST including its `x-shopify-hmac-sha256` value) can then replay that exact body to the victim app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. The HMAC check still passes because it only ever validated the body, not the shop header, so `Registry.process` calls the app's handler with `data.shop` set to whatever domain the attacker chose [6](#0-5) .

This lets an attacker who controls only their own shop's webhook traffic inject events that the app attributes to a different, victim shop — i.e., a cross-tenant identity confusion at the exact seam the analog targets (shop authenticated vs. shop used as the record/session key), mirroring the original report's pattern of an unchecked identity field letting an unprivileged caller manipulate operations meant to be scoped to a specific tenant (e.g. order data).

### Impact Explanation
This is a cross-tenant boundary break: a webhook payload legitimately signed for shop A can be replayed and re-attributed to shop B purely by changing an unsigned header. Any app logic that uses `WebhookMetadata#shop` to select which merchant's records to create/update/delete (the same class of impact as the referenced "Arbitrary Delete of Orders" report — an identity check that is bypassable lets one tenant's data be manipulated using another tenant's traffic) is affected. This meets the Critical bar of cross-tenant access.

### Likelihood Explanation
Likelihood is realistic: no access token, `client_secret`, or privileged credentials are required. The attacker only needs a webhook body legitimately signed for a shop they control (freely obtainable via a development store) and the ability to POST an HTTP request to the target app's public webhook receiver endpoint with a spoofed `x-shopify-shop-domain` header — both are unprivileged-internet-user actions.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) header content in the signed string checked by `HmacValidator`, or otherwise cryptographically bind the shop identity to the verified payload, mirroring the `execute_coin_precheck`-style pattern from the referenced report where the type/identity parameter is checked against the authenticated value before the value is trusted. At minimum, `Registry.process` should independently corroborate that `request.shop` corresponds to a shop domain the app already has an active session/installation for, rather than trusting the header outright once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own development shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) with a body they choose, capturing the raw POST and its valid `x-shopify-hmac-sha256` header.
2. Attacker sends the same raw body and same HMAC header to the app's public webhook endpoint, but replaces `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `HmacValidator.validate` passes because it only checks `HMAC(secret, raw_body)` [7](#0-6) ; `Registry.process` then invokes the app's handler with `data.shop == "victim.myshopify.com"` [6](#0-5) , causing the app to act on the victim shop's data using attacker-controlled content.
