Based on my investigation, I have enough to confirm the finding regarding the webhook `shop` field not being covered by the HMAC.

### Title
Webhook `shop-domain`, `topic`, `webhook-id` and `api-version` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its `to_signable_string` from the raw request body only, while `shop`, `topic`, `webhook_id` and `api_version` are all read from unauthenticated HTTP headers. `Registry.process` validates the HMAC over the body and, once it passes, trusts `request.shop` (from the header) as the tenant identity passed to the app's webhook handler. Any attacker in possession of a valid `(body, hmac)` pair for the app — which they can trivially obtain by installing the app on their own shop and receiving legitimate webhooks, since the webhook HMAC is computed with the app's shared `client_secret`, not a per-shop secret — can replay that body/HMAC pair to the victim's webhook endpoint while forging the `x-shopify-shop-domain` header to name a different (victim) shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from headers that are never part of the signed material: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` — i.e., body integrity/authenticity under the app's `client_secret` — and then immediately trusts `request.shop` as the tenant to hand to the registered handler: [3](#0-2) 

The identity binding broken is: `shop authenticated (by HMAC) == shop acted upon (used to route/attribute webhook data to a tenant)`. Because the webhook HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that has installed the app, a low-privileged attacker who installs the app on their own store legitimately receives real webhooks whose bodies are HMAC-signed with that same shared secret. The attacker can capture one such `(raw_body, hmac)` pair and replay it against the host application's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header rewritten to name a victim shop. `HmacValidator.validate` only recomputes the HMAC over `@raw_body`, so it still passes, and `Registry.process` calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` carrying the attacker-forged shop value.

### Impact Explanation
This is a cross-tenant identity confusion: the app-level webhook handler receives data purportedly belonging to `shop: victim-shop.myshopify.com` while HMAC only proved the body originated from *some* installation of the app (potentially the attacker's own shop), not that the body/data legitimately belongs to the named shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to select which merchant record to update, credit, or clear data for based on `shop/redact`, `customers/redact`, `app/uninstalled`, order/webhook topics), this can lead to cross-tenant data corruption, incorrect redaction/deletion targeting another merchant's data, or state confusion between tenants — satisfying the "cross-tenant access" criteria.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on any shop they control (a normal, unprivileged action for any Shopify merchant/developer with a dev store) to obtain a validly HMAC-signed webhook body, and then replay it with a forged `shop-domain` header to the victim app's public webhook endpoint. No access token, `client_secret`, or elevated privilege is required — the `client_secret` is never directly obtained by the attacker, only its effect (a valid signature over a body they already legitimately received).

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the HMAC-signed/verified material, or otherwise validate `request.shop` against an expected/registered shop for the installation making the request before passing it to `WebhookMetadata`. Shopify's official recommendation is to independently verify that the shop in the payload/headers corresponds to a shop actually known to have installed the app (e.g., cross-check against stored session/shop records) rather than trusting the header value implicitly once HMAC-on-body passes.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, receiving a legitimate webhook, e.g. topic `customers/data_request`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker sends a forged HTTP request to the app's webhook endpoint with:
   - body `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged, still valid because HMAC only covers `B`)
   - header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - header `x-shopify-topic: customers/data_request` (unchanged or forged)
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`; `Utils::HmacValidator.validate(request)` passes because it only checks `B` against `H`.
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to act on behalf of `victim-shop` using attacker-supplied data, despite the attacker never having any credential to `victim-shop`.
