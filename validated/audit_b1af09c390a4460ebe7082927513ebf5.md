## Title
Attacker-controlled `U256`→`u32`/`u64` truncation panics (`.expect("... out of bounds")`) in SP1 BEEFY proof conversion, reachable from a permissionless proof submission - ([File: evm/rust/src/conversions.rs])

### Summary
`impl From<crate::sp1_beefy::SP1Beefy::SP1BeefyProof> for Sp1BeefyProof` in `evm/rust/src/conversions.rs` (lines 397-416) converts ABI-decoded, attacker-supplied `U256` fields (`commitment.blockNumber`, `commitment.validatorSetId`) into `u32`/`u64` using `.try_into().expect("block number out of bounds")` / `.expect("validator set id out of bounds")`. [1](#0-0) 

This mirrors the CVE-2017-8284 bug class: an unbounded/unchecked size-like field taken from untrusted, ABI-encoded input is used without validating that it fits the destination representation, and the failure mode is a hard crash (panic) rather than a rejected proof.

### Finding Description
`modules/pallets/beefy-consensus-proofs/src/lib.rs::do_submit_proof` and `verify_and_apply` accept a raw `proof: Vec<u8>` from a caller, and for `PROOF_TYPE_SP1` proofs they ABI-decode it directly into `ismp_abi::sp1_beefy::SP1Beefy::SP1BeefyProof` via `abi_decode_params`, then call `.into()` to convert to the SCALE `Sp1BeefyProof` used by the verifier: [2](#0-1) [3](#0-2) 

`abi_decode_params` only checks ABI-encoding validity, not that a `uint256 blockNumber`/`uint256 validatorSetId` fits into `u32`/`u64`. The `.into()` conversion then does:
```
block_number: value.commitment.blockNumber.try_into().expect("block number out of bounds"),
validator_set_id: value.commitment.validatorSetId.try_into().expect("validator set id out of bounds"),
``` [1](#0-0) 

If a submitter crafts a proof whose ABI-encoded `blockNumber` or `validatorSetId` exceeds `u32::MAX`/`u64::MAX` respectively, this `.expect()` panics before any cryptographic/consensus check (`Groth16Verifier::verify`) runs, because the conversion happens *before* `verify_sp1_consensus` is invoked. This is exactly the "unbounded/unvalidated field size leads to unsafe processing" pattern of CVE-2017-8284, except here the impact is an unhandled panic on untrusted input rather than a buffer overflow. The same pattern repeats for `Vote::authorityIndex`, `RelayChainProof::mmrProof.leafIndex`, and `IntermediateState::stateMachineId/height/timestamp` in the same file (lines 356-365, 368-389, 419-436), all of which are `.expect()`-based truncations of attacker-influenced `U256`/`uint256` values coming from ABI-decoded proof bytes. [4](#0-3) 

A panic inside pallet dispatch logic (rather than a typed `DispatchError`) aborts the current transaction execution path in a way that is not gracefully handled by `ensure!`/`Result` plumbing the rest of the codebase carefully uses everywhere else (note the codebase's own extensive, recently-added guards against exactly this class of bug: `ByteVector::decode` length checks, `nibble_at_depth` bounds, `MAX_PROOF_DEPTH` checks, `as_utf8_string` deserialize fix — all explicitly added as "must never panic on untrusted input" regressions). This conversion path was missed by that hardening effort.

### Impact Explanation
A panic triggered during `do_submit_proof`/`verify_and_apply` while dispatching a submitted extrinsic can abort block execution for that transaction in an uncontrolled way (Substrate pallets are expected to return `Result`, not panic; a panic here is caught by the executive's panic handler at best, but historically in this codebase such unhandled panics on RPC/consensus-input paths have been treated as critical, node-crashing conditions — see the explicit regression tests added for `as_utf8_string_rejects_non_four_byte_input` and `nibble_at_depth`, which state the prior panics "crashed the node" / "took the process down"). Since `submit_proof` is the entry point for the BEEFY consensus update route into Hyperbridge, an attacker who can call it (with a fee-bearing but otherwise unprivileged account) can repeatedly submit malformed SP1 proofs to panic block-authoring/validation logic, denying consensus updates and blocking the BEEFY route from delivering messages — matching the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
High: constructing an ABI-encoded `SP1BeefyProof` with an out-of-range `blockNumber`/`validatorSetId`/`authorityIndex`/`leafIndex` requires no special access — it is exactly the shape of input the pallet already accepts from any submitter of `submit_proof`, before any cryptographic proof check occurs (the truncation happens ahead of `Groth16Verifier::verify`). No signature forgery or consensus knowledge is needed; only crafting an oversized integer field in the ABI encoding.

### Recommendation
Replace every `.try_into().expect(...)` in the `From<...SP1BeefyProof>` / `From<Vote>` / `From<RelayChainProof>` / `From<IntermediateState>` conversions in `evm/rust/src/conversions.rs` with fallible conversions that surface a typed error (e.g., implement `TryFrom` instead of `From`, or clamp/validate at the ABI-decode boundary in `do_submit_proof`/`verify_and_apply`), so that out-of-range values are rejected with `Error::<T>::AbiDecodeFailed` (or an equivalent) rather than panicking. Add regression tests analogous to the existing `ByteVector`/`nibble_at_depth`/`as_utf8_string` ones that specifically submit a `U256` field exceeding `u32::MAX`/`u64::MAX` and assert a clean `Err` rather than a panic.

### Proof of Concept
1. Craft an ABI-encoded `SP1Beefy::SP1BeefyProof` (the Solidity/alloy-generated struct) where `commitment.blockNumber` (a `uint256`) is set to a value `> u32::MAX` (e.g., `0x1_0000_0000`), and any structurally valid values for the remaining fields sufficient to pass `abi_decode_params`.
2. Prefix it with the `PROOF_TYPE_SP1` discriminator byte and submit it via the pallet's `submit_proof` extrinsic (`modules/pallets/beefy-consensus-proofs/src/lib.rs`), as any account able to pay the extrinsic fee.
3. `do_submit_proof` → `abi_decode_params` succeeds (ABI decoding doesn't range-check against `u32`) → `Into::<Sp1BeefyProof>::into(abi_proof)` executes `value.commitment.blockNumber.try_into().expect("block number out of bounds")` in `evm/rust/src/conversions.rs:401-404`, which panics before `verify_sp1_consensus` (and thus before any Groth16 signature check) ever runs. **Uncertainty note:** I was not able to fully confirm from the indexed snippets (a) the exact dispatch-weight/origin restrictions on the `submit_proof` extrinsic (whether it is `ensure_signed` open to any account or gated further), and (b) whether Substrate's `try-runtime`/`frame_support` panic-catching wraps this specific panic into a graceful `DispatchError` at the runtime level in this codebase's configuration, which would downgrade the impact from "node/validator crash" to "reverted extrinsic, fee lost."
