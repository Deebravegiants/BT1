## Finding

### Title
Permanent denial-of-service of the ETH-wallet contract via a stuck `has_in_flight_tx` lock with no recovery path - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the on-chain eth-implicit account emulator) uses a single boolean flag, `has_in_flight_tx`, as a mutual-exclusion lock so only one relayed Ethereum-style transaction can be "in flight" at a time. This mirrors the reported bug class exactly: a single-step process is gated behind one actor/one execution path completing successfully, and if that step fails to run to completion, the lock is never released and there is no alternate path, no owner override, and no timeout to recover it.

### Finding Description
`WalletContract::rlp_execute` refuses to do anything while `has_in_flight_tx == true`: [1](#0-0) 

The flag is set to `true` right before returning a `Promise`, and is only ever reset to `false` as the **first statement** of one of the three callback methods (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`, `ban_relayer`): [2](#0-1) [3](#0-2) 

Crucially, `address_check_callback` and `nep_141_storage_balance_callback` do more work *after* clearing the flag: they parse a cross-contract call result and then schedule a further promise (`ban_relayer`, or the actual action followed by `rlp_execute_callback`), using a gas budget that was fixed at scheduling time (`ADDRESS_CHECK_CALLBACK_GAS.saturating_add(action.gas())` / `NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())`): [4](#0-3) 

On NEAR, a function call is atomic: if execution runs out of the gas that was attached to that specific receipt (`GasExceeded`/`GasLimitExceeded`), the **entire** call aborts and none of its state mutations are persisted: [5](#0-4) [6](#0-5) 

This means that if `address_check_callback` (or `nep_141_storage_balance_callback`) runs low on gas *after* the point where it wrote `self.has_in_flight_tx = false` but *before* it finishes scheduling the follow-up promise, the whole receipt fails and rolls back — including the write that cleared `has_in_flight_tx`. The flag reverts to (remains) `true`, exactly as it was before this callback executed, and there is no other code path in the contract that ever sets it back to `false`. Every subsequent call to `rlp_execute` (from any relayer, or the owner) is immediately rejected because of the guard at line 97, permanently.

There is no owner/admin function to reset `has_in_flight_tx`, no timeout, and no alternate finalization path — the same structural weakness as the reported `VaultBitcoinWallet` issue: a single unfinished step, gated on one specific execution succeeding, becomes an unrecoverable deadlock for the whole contract.

### Impact Explanation
Once stuck, the wallet contract account becomes permanently unusable: no relayer (honest or otherwise) can ever submit another `rlp_execute` transaction on behalf of the account holder, since the very first check in `rlp_execute` unconditionally rejects all calls while `has_in_flight_tx` is `true`. This is a full, irreversible denial of service on that account's ability to use its NEAR-hosted Ethereum-style wallet — funds and permissions tied to that flow become inaccessible via this contract, with no protocol-level recovery mechanism (deploying a new contract to the same account is the only path, which is a privileged/out-of-band action, not something the protocol offers).

### Likelihood Explanation
Reaching the vulnerable window requires only a normal `rlp_execute` transaction whose gas allocation for the callback receipt is tight relative to the work still to be done (parsing the registrar/storage-balance response and scheduling the next promise). This is influenced by the gas amounts embedded in the underlying Ethereum-style transaction (`action.gas()`) and can occur unintentionally (a relayer/user under-provisioning gas) as well as be deliberately engineered by a relayer that controls how it submits transactions to this contract. No validator or protocol-level privilege is required — this is reachable purely through normal transaction/receipt execution against a deployed `WalletContract`.

### Recommendation
Do not rely on a single unconditional in-flight boolean cleared only by the "happy path" of a callback that itself still performs work afterward. Options:
- Clear `has_in_flight_tx` as the very last state mutation of the callback chain, only once all subsequent promises have been *successfully scheduled* — or better, restructure so that any failure state (including out-of-gas) is caught by a guaranteed follow-on callback that unconditionally clears the flag (since a `.then()` chained callback runs even if the preceding promise fails).
- Add an explicit "abandoned transaction" recovery mechanism (e.g., allow `has_in_flight_tx` to be reset if a certain number of blocks has passed since it was set, similar to a timeout), so that any single failed execution cannot brick the account forever.

### Proof of Concept
1. Deploy `WalletContract` on an eth-implicit account.
2. Craft/relay an RLP transaction whose `target` is an eth-implicit account not equal to the `to` address, forcing the `address_check_callback` registrar-lookup path (`address_check: Some(_)`), and submit the outer `rlp_execute` call with just enough attached gas to schedule `address_check_callback` (`callback_gas = ADDRESS_CHECK_CALLBACK_GAS + action.gas()`), i.e. exactly at the boundary of the amount needed for the callback's remaining work (parsing the JSON registrar response plus scheduling `create_ban_relayer_promise` or the subsequent action + `rlp_execute_callback`).
3. When `address_check_callback` executes, it clears `has_in_flight_tx = false`, then attempts to schedule the next promise; because the receipt's prepaid gas is exhausted at that point, the call aborts with `GasExceeded`/`GasLimitExceeded` and the whole state mutation (including the `has_in_flight_tx = false` write) is discarded, per [6](#0-5) .
4. Any subsequent `rlp_execute` call against the account now unconditionally returns `"Error: transaction already in progress, please try again later."` forever, since `has_in_flight_tx` remains `true` with no code path to clear it.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

    pub(crate) fn process_gas_limit(&mut self, new_burnt_gas: Gas, new_used_gas: Gas) -> HostError {
        use std::cmp::min;
        // Never burn more gas than what was paid for.
        let hard_burnt_limit = min(self.prepaid_gas, self.max_gas_burnt);
        self.fast_counter.burnt_gas = min(new_burnt_gas.as_gas(), hard_burnt_limit.as_gas());
        debug_assert!(hard_burnt_limit.as_gas() >= self.fast_counter.burnt_gas);

        // Technically we shall do `self.promises_gas = 0;` or error paths, as in this case
        // no promises will be kept, but that would mean protocol change.
        // See https://github.com/near/nearcore/issues/5148.
        // TODO: consider making this change!
        let used_gas_limit = min(self.prepaid_gas, new_used_gas);
        // [CONTINUATION OF THE PREVIOUS COMMENT]
        //
        // Now, there are two distinct ways an attacker can attempt to exploit this code given
        // their full control of the `new_used_gas` value.
        //
        // 1. `self.prepaid_gas < new_used_gas` This is perfectly fine and would be the happy path,
        //    were the computations performed with arbitrary precision integers all the time.
        // 2. `new_used_gas < new_burnt_gas` means that the `new_used_gas` computation wrapped
        //    and `used_gas_limit` is now set to a lower value than it otherwise should be. In the
        //    past this would have triggered an unconditional assert leading to nodes crashing and
        //    network getting stuck/going down. We don’t actually need to assert, though. By
        //    replacing the wrapping subtraction with a saturating one we make sure that the
        //    resulting value of `self.promises_gas` is well behaved (becomes 0.) All a potential
        //    attacker has achieved in this case is throwing some of their gas away.
        self.promises_gas =
            used_gas_limit.saturating_sub(Gas::from_gas(self.fast_counter.burnt_gas));

        // If we crossed both limits prefer reporting GasLimitExceeded.
        // Alternative would be to prefer reporting limit that is lower (or
        // perhaps even some other heuristic) but old code preferred
        // GasLimitExceeded and we’re keeping compatibility with that.
        if new_burnt_gas > self.max_gas_burnt {
            HostError::GasLimitExceeded
        } else {
            HostError::GasExceeded
        }
