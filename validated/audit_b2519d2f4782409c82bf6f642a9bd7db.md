Webhook `shop` Tenant Identifier Not Covered by HMAC Signature Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop` value taken directly from an HTTP header that was never included in the signed content. This breaks the intended binding of "shop authenticated == shop acted upon," letting an attacker who legitimately owns Shop A relabel a validly-signed webhook payload as if it came from Shop B.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, entirely outside the HMAC computation: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`, i.e. it verifies the body bytes, not the shop header: [3](#0-2) 

`Registry.process` then uses the *unverified* `request.shop` as the tenant identity handed to the app's webhook handler: [4](#0-3) 

The identity binding this breaks is: `HMAC-authenticated bytes (raw_body only) != shop identifier acted upon (shop-domain header)`. Because a single app-wide `client_secret` is used to sign webhooks for *every* shop that installs the app, an attacker who controls (or is granted a webhook delivery from) Shop A obtains a raw body + HMAC pair that is valid for that secret regardless of which shop it nominally came from. That attacker can then submit a forged HTTP request to the app's webhook endpoint with the original valid `raw_body`/`hmac-sha256` pair but a substituted `shopify-shop-domain` header naming Shop B (a shop the attacker does not control). `Registry.process` will pass `Utils::HmacValidator.validate`, because validation only checks the body against the shared secret, and will then invoke the app's handler with `shop: "shop-b.myshopify.com"` and attacker-controlled body content, spoofing a cross-tenant webhook event.

### Impact Explanation
This crosses a tenant boundary using only information available to any unprivileged merchant/installer of the app (a legitimately delivered webhook to their own shop), qualifying as Critical cross-tenant access: the host application's webhook handler processes attacker-supplied data under another merchant's shop identity, potentially triggering data mutations, cache/database writes keyed by `shop`, or GDPR-webhook-driven redaction logic (`shop/redact`, `customers/redact`, `customers/data_request`) against the wrong tenant.

### Likelihood Explanation
Any developer/merchant who can install the app on one shop (unprivileged internet user relative to other tenants) can capture a real, validly-signed webhook body/HMAC pair from Shopify for their own shop, then replay it to the app's public webhook endpoint with a forged `shop-domain` header — no access token, `client_secret`, or leaked credential is needed, only the ability to craft an HTTP POST with modified headers.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable content, or otherwise cryptographically bind the header-derived `shop` value to the signed body (e.g., require the app to independently confirm the shop is registered/known and that the specific webhook id/shop pairing was actually requested), rather than trusting `shopify-shop-domain` as an unauthenticated header.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger any webhook event so Shopify delivers a POST with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and some `raw_body`.
2. Capture `raw_body` and the valid `hmac-sha256` value.
3. Replay the same `raw_body` and `hmac-sha256` to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#initialize` accepts it since all required headers are present: [5](#0-4) 
5. `Utils::HmacValidator.validate(request)` passes because it only checks `raw_body` against the shared `client_secret`.
6. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled data as if it originated from the victim's store.
