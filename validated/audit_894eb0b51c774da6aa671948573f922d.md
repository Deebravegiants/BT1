### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands `request.shop` — a value taken verbatim from the `x-shopify-shop-domain`/`shopify-shop-domain` header — to the app's handler as the tenant identity, without that header ever being part of the signed material.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop` (the tenant identity used downstream) is read directly from an HTTP header that is never mixed into the signed bytes: [3](#0-2) [4](#0-3) 

`Registry.process` only checks the body HMAC before dispatching, then constructs `WebhookMetadata` from the unauthenticated `request.shop`: [5](#0-4) 

This is the exact class of bug the CDP.sol analog highlights: a value that is consumed as ground truth (`totalCredit` in the original report; here, the `shop` tenant binding) is derived/overwritten independently of the check that is supposed to protect it (`_earnedYield.sub(...)` ignoring prior state; here, `hmac` ignoring the `shop` header). The equality that should hold — `hmac == HMAC(secret, body ‖ shop)` — is never enforced; only `hmac == HMAC(secret, body)` is checked, so `shop` floats free of the authenticated payload.

### Impact Explanation
Since the `shop` header is not bound by the signature, an attacker who legitimately controls their own shop (an ordinary, unprivileged merchant/installer of the target app — no `api_secret_key`, no victim's access token, no TLS interception required) can:
1. Trigger a webhook to their own shop and capture the resulting `(raw_body, hmac)` pair delivered to the app endpoint (or replay any request to that endpoint with attacker-supplied headers, since the endpoint itself performs no shop-binding).
2. Re-send that exact body/HMAC pair to the app's public webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop's domain.
3. `HmacValidator.validate` still returns `true` (the body and HMAC are consistent with each other), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

Any app logic that uses `data.shop` to select which tenant's records to create/update/delete (a very common pattern, e.g. `customers/redact`, `app/uninstalled`, order processing) can be made to act against a different tenant's data using attacker-controlled body content, achieving cross-tenant access/state corruption without holding any victim credential.

### Likelihood Explanation
Moderate-to-high: it requires no secret material, no OAuth token, and no privileged access — only the ability to reach the app's public webhook endpoint and to have (or fabricate, for topics with attacker-controlled shape) a `(body, hmac)` pair from any shop, including the attacker's own. The gem's own test suite demonstrates the header is fully attacker-suppliable and independent from the HMAC check.

### Recommendation
Bind the tenant identity into the authenticated material: include the `shop`/`x-shopify-shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) values in `to_signable_string`, or otherwise verify that the shop asserted in the header matches a shop the handler already expects/owns before dispatching, so that `hmac` cryptographically covers every field the handler relies on for tenant identity.

### Proof of Concept
1. App registers a handler for `customers/redact` that uses `data.shop` to select the tenant record to delete, per the pattern in `ShopifyAPI::Webhooks::Registry.process`.
2. Attacker owns Shop A (installed app legitimately) and observes/produces a valid `(raw_body="{}"; hmac=HMAC(secret_of_app, "{}"))` webhook delivery — this is possible because the signature is only over the body, and the attacker's own shop deliveries carry a valid HMAC for that exact body.
3. Attacker POSTs to the app's webhook endpoint with headers `x-shopify-shop-domain: victim-shop.myshopify.com`, `x-shopify-topic: customers/redact`, and the captured `x-shopify-hmac-sha256`, reusing the same `raw_body`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks body-vs-hmac; `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the handler with `shop: "victim-shop.myshopify.com"`, causing the app to act on the victim tenant using attacker-supplied webhook content.
