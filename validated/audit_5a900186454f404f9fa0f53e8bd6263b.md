### Title
Webhook shop/topic identity spoofing via unauthenticated headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively from the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identity for dispatching the webhook payload to the app's handler, without that identity ever being cryptographically bound to the signature. This breaks the equality "bytes verified by HMAC == bytes/identity acted upon by the handler," letting an attacker who can obtain one validly-signed webhook body (e.g., by installing the app on their own store and triggering a webhook) replay that exact body with a forged `shop-domain` header for a different (victim) shop, causing the app to process the data as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from client-controlled headers and are never included in the signed content: [2](#0-1) 

`HmacValidator.validate` only checks `request.to_signable_string` (the raw body) against the HMAC computed with `Context.api_secret_key`: [3](#0-2) 

`Registry.process` then uses the *unverified* `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build `WebhookMetadata` and dispatch to the app's handler, once the body-only HMAC check passes: [4](#0-3) 

The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," implying host applications can trust `data.shop` as an authenticated tenant identifier without extra checks: [5](#0-4) 

Since `api_secret_key` is a single value shared by the app across *all* installed shops (it's the app's client secret, not a per-shop secret), `HMAC(api_secret_key, body)` is deterministic given only the body — it carries no shop-specific binding. Any actor able to install the app on a shop they control (any internet user who can create a Shopify dev/partner store, no privileged credentials required) can capture a legitimately-signed `(body, hmac)` pair from their own shop's webhook delivery, then replay that identical body+hmac to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header to name a different, victim shop. `HmacValidator.validate` still passes (body unchanged), and `Registry.process` will hand the attacker-chosen `shop` value to the host application's handler as if Shopify had confirmed that shop as the source.

### Impact Explanation
This breaks the tenant/identity boundary the gem is documented to enforce ("verify the request did indeed come from Shopify"): an attacker can inject webhook events under an arbitrary shop's identity into the host application's cross-tenant data model (e.g., trigger `orders/create`-style data attributed to a shop they don't own, poison per-shop caches/queues, or spoof `shop/redact`, `app/uninstalled`, etc. against a shop they don't control). Because most `shopify_api`-based apps (including the officially referenced `shopify_app` gem pattern) key persistence, job dispatch, and business logic off `data.shop`, this is a cross-tenant access primitive — the highest-severity category listed for this analysis (Critical: cross-tenant access).

### Likelihood Explanation
Exploitation only requires the ability to install the target app on a shop the attacker controls (trivial for any public app, and free via Partner/dev stores) to obtain one valid `(body, hmac)` pair, plus the ability to send an HTTP POST with attacker-controlled headers to the app's public webhook endpoint. No access to `api_secret_key`, no privileged credentials, and no TLS interception are required — this is reachable by any unprivileged internet user targeting an app that follows the gem's documented usage exactly as shown in `docs/usage/webhooks.md`.

### Recommendation
Bind the shop/topic identity into the verified signature material, or independently verify `request.shop` against the shop that installed/authorized the app (e.g., cross-check `request.shop` against a known, previously-authenticated shop record, and/or verify webhook `webhook_id` uniqueness per shop) before dispatching to handlers. At minimum, `Registry.process` should not present `request.shop`/`request.topic` to handlers as "verified" identity data derived solely from a body-only HMAC check — the documentation and API contract should be corrected to make clear that only the payload bytes are authenticated, not the header-derived shop/topic/webhook metadata, and host apps must independently confirm the shop is one they actually have an active session/install for.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (any free/dev store) and triggers a webhook (e.g., `orders/create`) to their own registered endpoint, capturing the raw POST body `B` and the valid header `X-Shopify-Hmac-Sha256: H` (computed by Shopify as `HMAC-SHA256(api_secret_key, B)`).
2. Attacker sends a POST to the app's public webhook endpoint with the exact same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds `request.shop == "victim-shop.myshopify.com"` while `to_signable_string` still returns `B`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(api_secret_key, B)`, which equals `H`, so validation succeeds.
5. `Registry.process(request)` dispatches `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` to the app's handler, which processes/stores attacker-supplied data under the victim shop's identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
