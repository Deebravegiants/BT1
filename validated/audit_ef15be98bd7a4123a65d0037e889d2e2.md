Based on the analysis, this is a genuine finding. The `data.shop` field is documented as trusted webhook identity (used in `docs/usage/webhooks.md:14` and `docs/usage/webhooks.md:26` for job routing/tenant identification), yet it is never covered by the HMAC signature.

### Title
Webhook `shop` Domain Is Not Covered by HMAC Signature, Allowing Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` is read from the `x-shopify-shop-domain` header, which is completely outside the HMAC-signed payload. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only and then trusts the unauthenticated `shop` header when constructing `WebhookMetadata`, which host applications use as the tenant identifier for the event.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is derived from the `x-shopify-hmac-sha256` header and `to_signable_string` returns only `@raw_body`. The `shop` accessor is derived independently from the `x-shopify-shop-domain` header, which is never included in the signable string.

`Registry.process` validates the HMAC exclusively via `Utils::HmacValidator.validate(request)` (which calls `to_signable_string`, i.e., the body only) and then immediately builds `WebhookMetadata` using `request.shop`: [2](#0-1) 

The equality this breaks: **the shop identity acted upon by the handler (`WebhookMetadata#shop`) ≠ the bytes actually covered by the HMAC (`@raw_body` only)**. `HmacValidator.validate` proves only that the *body* was produced with knowledge of `Context.api_secret_key`; it says nothing about which shop header accompanied that body.

Because a single app's `client_secret` is shared across every shop that installs the app, an attacker who legitimately installs the target app on their own shop will receive genuinely-signed webhook deliveries (valid body + valid HMAC) for their own shop. The attacker can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with any victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` forwards the attacker-chosen `shop` value straight into `WebhookMetadata`, which the app's documented handler pattern uses as the tenant key (see `docs/usage/webhooks.md` example using `data.shop` for `perform_later(... shop_domain: data.shop ...)`).

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged internet user (any merchant who installs the app) can make the gem report webhook events as originating from an arbitrary victim shop, with attacker-controlled body content (since it's the attacker's own webhook data) while spoofing the shop identifier. Downstream host applications that key business logic, background jobs, or data writes off `WebhookMetadata#shop` (as the library's own documentation instructs) can be tricked into processing attacker data under a victim's tenant context — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High likelihood: this requires no special privileges beyond installing the app on a shop the attacker controls (the normal, unprivileged path for any Shopify merchant), knowledge of the fixed, low-entropy webhook body/HMAC pair they receive from their own installation, and a simple HTTP replay with one modified header. No access to `api_secret_key` or any credential belonging to the app or the victim is required.

### Recommendation
Bind the shop domain into the verified payload. Options include:
- Including the `x-shopify-shop-domain` header value in `to_signable_string` is not viable since Shopify itself only signs the body — instead, the gem should cross-check `request.shop` against a known/expected shop domain (e.g., a session lookup keyed by webhook ID or an app-supplied expected shop) before constructing `WebhookMetadata`, or
- Document loudly and enforce that `Registry.process` callers pass an expected/allow-listed shop for the endpoint being hit, and reject mismatches, rather than trusting the header value implicitly.
- At minimum, update `WebhookHandler` documentation to explicitly warn that `data.shop` is unauthenticated and must not be used as a sole tenant key without corroboration (e.g., validating against a stored session for `webhook_id`/topic).

### Proof of Concept
1. Attacker creates their own shop `attacker.myshopify.com` and installs the target app (a normal, unprivileged action). The app's `client_secret` is the same for all installs.
2. Shopify delivers a legitimate webhook to the app for `attacker.myshopify.com`:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker.myshopify.com
   Body: {"id": 1, "note": "hello"}
   ```
3. Attacker captures this exact `Body` and `x-shopify-hmac-sha256` value (HMAC over the body only).
4. Attacker replays the identical request to the app's webhook endpoint, changing only the header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same-valid-hmac-of-body>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: {"id": 1, "note": "hello"}
   ```
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `@raw_body` only, matches, and returns `true`.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the app's handler, which — per the gem's own documented usage pattern — treats `data.shop` as the authenticated tenant identifier.
