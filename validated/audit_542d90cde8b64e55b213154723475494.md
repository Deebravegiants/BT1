## Analysis

The external report's bug class is: **a response/refund is unconditionally routed based on unauthenticated context (`msg.sender`) instead of verifying the intended counterparty, and a security check that would normally validate the destination/source is bypassed for a specific code path.**

The closest reachable analog in `orb-core` is in the Orb↔App relay client used for self-serve signups, in `PollerAgent::main_loop`.

### Title
Unauthenticated `RequestState` handling bypasses source-identity validation, allowing cached signup-session state to be replayed to an unverified peer — (`orb-relay-client/src/client.rs`)

### Summary
`PollerAgent::main_loop` validates that every incoming relay message originates from the expected paired peer (`src.id == self.config.dst_id`) before processing it — except for messages that match `self_serve::app::v1::RequestState`, which are handled *before* that check and unconditionally trigger a reply with the locally cached `self.last_message`.

### Finding Description
In the main receive loop: [1](#0-0) 

the logic is:
```rust
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source...");
} else {
    self.handle_message(...).await?;
}
```
Every other payload type is rejected unless `src.id == self.config.dst_id` (i.e., unless it comes from the specific app/session or orb this `Client` was paired with for the current signup, per `Client::new_as_orb`/`new_as_app`, and `orb_relay_announce_orb_id`, which creates a fresh relay `Client` keyed to `orb_relay_app_id` for each signup). [2](#0-1) 

However, the `RequestState` branch is checked *first* and is not subject to the `src.id != self.config.dst_id` guard at all. Any relay message whose payload matches `RequestState` — regardless of the `src` entity attached to it — causes the client to resend `self.last_message`, which is the most recently sent payload for this session (e.g. `AnnounceOrbId`, or `self_serve::orb::v1::SignupEnded{ success, failure_feedback }` sent at the end of a signup). [3](#0-2) 

This mirrors the reported bug class exactly: a trust-relevant parameter (`refundAddress`/counterparty identity) that is validated everywhere else in the flow is skipped for one specific operation, because the code path was not updated to apply the existing authorization check uniformly.

### Impact Explanation
Because the `src.id` check is skipped for `RequestState`, any entity able to place a message on this bidirectional relay stream (the client's own comment notes the relay "multiplexes messages from different sources," which is exactly the condition this check exists to defend against) can force the Orb (or App) side to re-emit the last signup-related state message without proving it is the legitimate paired counterpart for that session. This can disclose a specific signup session's outcome/state (e.g. `SignupEnded.success`/`failure_feedback`) to a party that never authenticated as that session's paired peer — a violation of the identity-binding guarantee the `src.id == dst_id` check is meant to enforce for the self-serve signup relay channel.

### Likelihood Explanation
Exploitability depends entirely on whether an unauthenticated or wrongly-scoped relay message can reach the client's `response_stream` with a `RequestState` payload and an arbitrary/incorrect `src`. The relay server's own authorization/session-routing controls (out of scope here) determine how hard this is to trigger, but the orb-core client code itself provides no defense-in-depth for this specific message type even though it does so for every other message type — this is a straightforward missing-check bug in first-party code, not a "malicious relay operator" precondition.

### Recommendation
Apply the same `src.id == self.config.dst_id` validation to the `RequestState` branch before replying with `self.last_message`, so that only the verified paired counterpart can trigger a state replay:
```rust
if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}", src.id);
} else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else {
    self.handle_message(...).await?;
}
```

### Proof of Concept
1. During a self-serve signup, the Orb creates a relay `Client` bound to `dst_id = orb_relay_app_id` for that session. [4](#0-3) 
2. The Orb sends `SignupEnded{ success, failure_feedback }` as its last message to the app at the end of the signup. [5](#0-4) 
3. A relay message with payload matching `self_serve::app::v1::RequestState`, carrying an arbitrary/unverified `src`, is delivered to the Orb's `response_stream`.
4. `main_loop` matches the `RequestState` branch first and replies with `self.last_message` (the cached `SignupEnded` payload) without ever checking `src.id != self.config.dst_id`. [6](#0-5) 
5. The sender of the spoofed `RequestState` (or any relay-connected entity able to induce this reply) learns the signup outcome/state for a session it was never authenticated for.
