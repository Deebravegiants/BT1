### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and is validated by `Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process`. The HMAC is checked only against `@raw_body` via `to_signable_string`, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated headers and are never included in the signed material. The registry then hands `request.shop` straight to the webhook handler as the tenant identifier. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The intended binding is: `HMAC(body, headers) == received_hmac` should authenticate every field the application acts on, i.e. `shop == the tenant the signed payload actually belongs to`. In this gem's implementation, `to_signable_string` returns only the raw request body:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

while `shop`, `topic`, and `webhook_id` are pulled from the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers with no cryptographic tie to the signature:

```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```

`Registry.process` validates only the body-bound HMAC and then trusts `request.shop` as the tenant identity passed to the handler:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

Because the signature never covers `shop`, an attacker who legitimately owns/operates any shop connected to the app (an unprivileged actor with no special access to `api_secret_key`, access tokens, or the target tenant) can capture one of their own genuinely-delivered webhooks — which carries a valid HMAC for that exact `raw_body` — and resend it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop. The body-only signature remains valid because header content is entirely outside the signed string, so `HmacValidator.validate` returns `true`, and the handler receives `WebhookMetadata` claiming the payload originated from the victim tenant.

### Impact Explanation
This breaks the shop/HMAC identity binding and results in cross-tenant confusion: any host application that keys per-tenant state (order records, inventory, fulfillment triggers, GDPR/compliance actions, billing events, etc.) off `WebhookMetadata#shop` can be made to attribute another tenant's data/action to an attacker-chosen victim shop, or vice versa, despite a "successfully verified" HMAC. This matches the High-impact category of a scope/identity binding bypass leading to cross-tenant access, since the shop identity used to route/attribute webhook effects is not actually authenticated by the signature that gates processing.

### Likelihood Explanation
Likelihood is Medium-High: no secret material is required — only ordinary access to a shop that already has this app installed (which any merchant can obtain by installing a public/normal app) and the ability to observe one legitimate webhook body plus its valid HMAC (visible via test webhooks in the Shopify admin or normal delivery logs), and knowledge/guess of another tenant's `myshopify.com` domain (often discoverable/public). The replay only requires resending the identical raw body with a substituted `shop-domain` header to the app's public webhook endpoint.

### Recommendation
Bind the identity fields into the signed material, or otherwise cryptographically tie the header values to the verified payload, e.g. include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or independently verify `shop` against the value returned by Shopify's public shop-resolution/HMAC verification metadata rather than trusting an unauthenticated header. At minimum, document clearly that `request.shop`/`topic`/`webhook_id` are unauthenticated and must not be trusted for tenant routing without an additional binding check, and provide a built-in mechanism in the gem that couples them to the verified body.

### Proof of Concept
1. Shop A (attacker-controlled, legitimately using the app) receives a real webhook from Shopify:
   - Headers: `shopify-shop-domain: shop-a.myshopify.com`, `shopify-hmac-sha256: <valid HMAC of raw_body>`
   - Body: `{"id": 123, ...}` (any legitimate event body signed by Shopify with the app's real `client_secret`, unknown to the attacker).
2. Attacker resends the exact same `raw_body` to the app's webhook endpoint but changes only the header:
   - `shopify-shop-domain: shop-b.myshopify.com` (victim tenant)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) — unchanged from step 1 — so validation passes.
4. The handler is invoked with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)`, even though the payload actually originated from and was signed for shop A, demonstrating the identity-binding break: [4](#0-3)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
