### Title
`swallowDecryptionErrors` silently swallows all AEAD authentication failures, not just genuine wrong-key mismatches - ([File: adapters/storage-encrypted/src/storage.ts])

### Summary
`isDecryptionError()` decides whether to swallow a `decrypt()` failure by matching the substring `'wrong secret key for the given ciphertext'` in the thrown `Error.message`. This message is the generic authentication-failure message emitted by `crypto_secretbox_open_easy` (via `@exodus/libsodium-wrappers`) for *any* MAC/authentication verification failure - it does not distinguish between "decrypted with the wrong key" and "ciphertext was corrupted/tampered/truncated-but-above-minimum-length." Because `libraries/browser-extension-adapters/encrypted-storage/encrypted-storage.js` defaults `swallowDecryptionErrors` to `true`, any attacker-controlled malformed-but-sufficiently-long base64 blob written into the underlying storage (e.g. via a restored/synced backup) will trigger this same generic message and be silently swallowed and merely logged, rather than propagated as an integrity-break signal.

### Finding Description
`transformOnRead` calls `decrypt(ciphertext)` [1](#0-0) , backed in practice by `decryptSecret` in `libraries/sodium-crypto/index.js`, which only performs a length assertion (`'Encrypted data too short'`) before calling `sodium.crypto_secretbox_open_easy(ciphertext, nonce, secretKey)` [2](#0-1) . Once the length check passes, `crypto_secretbox_open_easy` performs Poly1305/secretbox MAC verification, which fails identically — with the exact same library-generated error text — whether the ciphertext was encrypted under a different key, or whether it is arbitrary corrupted/tampered/bit-flipped bytes of matching length. There is no code path in libsodium's `crypto_secretbox_open_easy` that produces a different message for "wrong key" vs. "corrupted authenticated ciphertext"; AEAD/secretbox authentication by design cannot distinguish these two cases at all — a failed MAC check is a single, generic outcome. `isDecryptionError` therefore does not (and structurally cannot) verify that failure was a "genuine wrong-key" event [3](#0-2) ; it only checks a string that is present for every MAC failure. When `swallowDecryptionErrors=true` (the default in `createEncryptedStorage`) [4](#0-3) , any ciphertext of at least `crypto_secretbox_NONCEBYTES + crypto_secretbox_MACBYTES` bytes that fails to authenticate — regardless of cause — is logged via `logger.warn` and treated as if the key/value simply doesn't exist (`return` undefined) [5](#0-4) , instead of throwing and alerting the caller to data corruption/tampering.

### Impact Explanation
An attacker who can write/import an attacker-crafted, malformed-but-length-valid base64 ciphertext into a storage key backed by this adapter (e.g. via a corrupted/tampered backup import, or a synced remote value under attacker influence) can cause the wallet to silently treat that key as "absent" rather than surfacing an integrity error. This masks genuine tampering/corruption as an innocuous "wrong key" scenario, defeating the intended purpose of `swallowDecryptionErrors` (which is meant only to tolerate legitimate cross-account/cross-key mismatches) and suppressing a signal that should alert the caller/user to storage integrity compromise.

### Likelihood Explanation
Feasibility is high in the sense that essentially all authentication failures (100% of malformed/corrupted ciphertext of sufficient length) trigger the same message, so the "genuine wrong key" filter provides effectively no discrimination — but exploitation requires `swallowDecryptionErrors=true` (true by default for the browser-extension encrypted storage adapter) and requires the attacker to have a path to overwrite the underlying (unencrypted-key-value) storage entry, such as through backup import or remote sync of storage values — a precondition explicitly allowed by this question's scope.

### Recommendation
Do not rely on decrypted-error message string matching to distinguish "wrong key" from "corrupted data" since AEAD authentication cannot make that distinction. Instead, only swallow decryption errors for keys/values that are explicitly known to be affected by legitimate key rotation/multi-account scenarios (e.g., via a whitelist of keys or an explicit "try alternate key" mechanism performed before giving up), and always propagate authentication failures by default so that generic ciphertext corruption is surfaced to the caller rather than silently discarded.

### Proof of Concept
Fuzz/integration test plan:
1. Using the existing test harness in `adapters/storage-encrypted/test/index.spec.ts`, create `storage` with `swallowDecryptionErrors: true`.
2. Write N (e.g. 1000) random buffers of varying lengths ≥ `crypto_secretbox_NONCEBYTES + crypto_secretbox_MACBYTES` (24+16=40 bytes) as base64 directly into `inMemoryStorage` under distinct keys (bypassing `storage.set` to simulate attacker-supplied ciphertext from an import/sync path).
3. For each key, call `storage.get(key)` and record whether it resolves to `undefined` (swallowed) or throws.
4. Separately attempt decryption of the same buffers with the correct key via `sodiumEncryptor.decryptSecretBox` directly, and independently verify none of them are actually valid ciphertexts encrypted under a *different, real* key (i.e., all are pure garbage/corruption, not genuine wrong-key ciphertexts).
5. Expected (vulnerable) result: a large fraction (approaching 100% of syntactically-valid-length garbage) resolves to `undefined`, i.e., `isDecryptionError` returns `true` for corrupted-but-not-genuinely-wrong-key data, confirming the message-matching heuristic cannot distinguish corruption from key mismatch.

    const { decrypt } = await cryptoFunctions
    if (!ciphertextB64) return

    const ciphertext = Buffer.from(ciphertextB64, 'base64')
    let decrypted
    try {
      decrypted = await decrypt(ciphertext)
    } catch (err) {
      if (swallowDecryptionErrors && isDecryptionError(err as Error)) {
        logger.warn(`Failed to decrypt value for key: ${key}`, err)
