### Title
`cancelOrder()` is `payable` but the same-chain cancellation path never consumes or refunds `msg.value`, permanently locking sent Ether - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.cancelOrder()` is marked `payable` so that cross-chain cancellations can pay the Hyperbridge relayer fee in native token via the GET dispatch. However, when the order is a same-chain order, `cancelOrder()` routes to `_cancelSameChain()`, which only refunds the escrowed input tokens and never touches, refunds, or reverts on `msg.value`.

### Finding Description
`cancelOrder` computes `isSameChain` and dispatches accordingly: [1](#0-0) 

For the same-chain branch it calls `_cancelSameChain(order, commitment)`, described in the sibling contract as simply refunding remaining escrow balances to the order creator — it performs no dispatch and has no reason to consume native token: [2](#0-1) 

This is the same bug class as the reported issue: `placeOrder()` and `fillOrder()` in this codebase carefully track `msgValue` and refund any unspent amount back to the caller at the end of every code path (`_sendValue(msg.sender, msgValue)`): [3](#0-2) [4](#0-3) [5](#0-4) 

But `cancelOrder()` has no equivalent refund/consumption logic for the same-chain path, unlike `placeOrder`/`fillOrder`. If a caller mistakenly attaches `msg.value` (e.g., by copying the same call pattern used for `fillOrder`/`placeOrder`, or because a cross-chain cancel UI path is reused against a same-chain order) when invoking `cancelOrder()` for a same-chain order, that ETH is transferred into the contract and neither escrowed, refunded, nor used — it is stuck in the `IntentGatewayV2` contract with no recovery mechanism reachable by the sender.

### Impact Explanation
Ether sent along with a same-chain `cancelOrder()` call becomes permanently locked in the `IntentGatewayV2` contract, since there is no code path that returns or applies it. This is a real (if user-error-triggered) permanent loss of user funds with no recovery path for the original sender, consistent with the "Medium" severity classification used in the referenced report for the identical bug class.

### Likelihood Explanation
Likelihood is lower than for `placeOrder`/`fillOrder` because `cancelOrder` is not typically expected to carry value for a same-chain cancel, and SDK-generated calls likely set `value: 0` correctly for this case. However, nothing in the contract enforces `msg.value == 0` on the same-chain branch, so any integrator, script, or user manually constructing the transaction (or reusing cross-chain cancel calldata patterns) can trigger the loss.

### Recommendation
Add a guard so that the same-chain cancellation path rejects unexpected native token: `if (isSameChain && msg.value > 0) revert InvalidInput();` inside `cancelOrder()`, or alternatively refund `msg.value` back to `msg.sender` before/after invoking `_cancelSameChain`, mirroring the refund pattern already used in `placeOrder` and `fillOrder`.

### Proof of Concept
1. User places a same-chain order via `placeOrder()`.
2. Before the order is filled, the user (or any caller) calls `cancelOrder{value: X}(order, options)` for this same-chain order, where `X > 0`.
3. `cancelOrder` routes to `_cancelSameChain`, which refunds only the ERC20/native escrow recorded in `_orders[commitment]` — the extra `msg.value` sent as transaction value is never referenced.
4. The `X` ether remains in the `IntentGatewayV2` contract balance permanently, unassociated with any escrow accounting, with no function able to withdraw it back to the sender.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        // Emitted here, once, rather than from each of the three routes below. Every check those
        // routes make — Unauthorized, NotExpired, UnknownOrder — reverts, and a revert discards
        // logs, so an early emit can never announce a cancellation that did not happen. Emitting
        // before the branch also keeps `EscrowRefunded` the last log on the same-chain route, where
        // the refund is processed in this same transaction. Three emit sites cost bytecode this
        // contract does not have: it sits within ~100 bytes of the EIP-170 limit.
        emit OrderCancelled({commitment: commitment, canceller: msg.sender});

        if (isSameChain) {
            // Checked here rather than inside `_cancelSameChain`, which used to re-read `host()`,
            // re-query the host's state machine id and re-hash `order.source` to reach the same
            // answer this function already has. Same check, one external call fewer.
            if (currentChain != orderSource) revert WrongChain();
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
