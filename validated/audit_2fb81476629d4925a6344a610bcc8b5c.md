### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant shop impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as verified once `Utils::HmacValidator.validate` succeeds, and then forwards `request.shop` — taken directly from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) HTTP header — to the app's handler as the authenticated tenant identity. However, the HMAC signature only covers the raw request body, not the shop-domain header, so the "verified" shop and the shop the handler acts on are not the same binding.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `hmac` is derived from the `hmac-sha256` header: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `to_signable_string` (i.e. the body only) and compares it against the received signature using the app-wide `Context.api_secret_key`: [2](#0-1) 

`Registry.process` raises only if this body-HMAC check fails, then dispatches `request.shop` (the unauthenticated header) straight into `WebhookMetadata`, which the handler uses as the tenant identifier: [3](#0-2) [4](#0-3) 

Because `Context.api_secret_key` is the app's single `client_secret`, shared across *every* shop that has installed the app, any unprivileged user who installs the app on their own store (a normal, free action) can capture a legitimately Shopify-signed webhook body/HMAC pair for their own shop, then replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim merchant's domain. The body-only HMAC still validates (the secret and body are unchanged), so `Registry.process` accepts the request and calls the handler with `data.shop` equal to the attacker-chosen victim domain while `data.body` is the attacker's own (or crafted, if the attacker controls their own shop's webhook content) payload.

This breaks the identity binding "shop authenticated by HMAC" = "shop the handler acts upon", since only the body is authenticated and the shop domain travels unauthenticated in a header. The gem's own documentation describes `Registry.process` as verifying "the request did indeed come from Shopify," implying `data.shop` can be trusted as the webhook's origin shop — which is not actually guaranteed: [5](#0-4) 

### Impact Explanation
An app that keys any per-shop state, authorization decisions, session/token lookups, or data writes off `data.shop` (as the gem's own example — `shop_domain: data.shop` — encourages) can be made to act on behalf of, or write data attributed to, a shop the attacker does not control. This is a cross-tenant boundary violation reachable by any user who can install the app on a store they control, i.e. an unprivileged internet user, without needing the app's `client_secret`, an access token, or any other privileged credential.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple independent merchants (the standard SaaS embedded-app model): obtaining a legitimately-signed webhook only requires installing the app once as an ordinary merchant, which is normal, unauthenticated (from the gem's perspective) self-service action.

### Recommendation
Do not trust the shop-domain header as an authenticated identity by itself. Either:
- Include the shop domain (and ideally webhook id/topic) in the signed payload used for HMAC verification, and reject mismatches, or
- Cross-check `request.shop` against an independently stored expected shop per registered webhook, or
- Bind webhook verification per-shop (e.g., verify against a per-shop secret/session) rather than relying solely on the app-wide `client_secret` for identity.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a normal, unprivileged action).
2. Shopify sends a legitimately signed webhook to the app: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays the same body `B` and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC(secret, B)` — unchanged since the body `B` is identical — and it matches, so `Registry.process` proceeds: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, despite the request never having originated from or been authorized for that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
