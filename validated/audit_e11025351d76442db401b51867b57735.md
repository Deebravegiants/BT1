### Title
`Pallet::execute` in pallet-ismp reverts the entire batched `handle_unsigned` extrinsic if a single ISMP message in the batch is invalid, causing all other valid messages in the same batch to fail delivery - (File: modules/pallets/ismp/src/impls.rs)

### Summary
`pallet_ismp::Pallet::execute`, invoked from the permissionless, unsigned `handle_unsigned` extrinsic, processes a `Vec<Message>` by mapping each message through `handle_incoming_message` and collecting the results with `.collect::<Result<Vec<_>, _>>()`. Because the extrinsic is also marked `#[frame_support::transactional]`, a single invalid/failing message anywhere in the batch causes the whole call to error out and all storage effects from every other, individually-valid message in that same batch to be rolled back.

### Finding Description
`handle_unsigned` is a public, unsigned (`ensure_none(origin)`), permissionless extrinsic that anyone can submit with a batch of arbitrary ISMP `Message`s (consensus updates, POST requests, GET responses, timeouts, etc.): [1](#0-0) 

It delegates to `Pallet::execute`, which processes the whole `Vec<Message>` as a single fallible unit: [2](#0-1) 

The `.map(|msg| handle_incoming_message(&host, msg.clone())).collect::<Result<Vec<_>, _>>()` pattern means that if `handle_incoming_message` returns `Err` for *any single message* in the batch (e.g. one message hits `Error::DuplicateRequest`, `Error::RequestTimeout`, `Error::InvalidRequestDestination`, a stale consensus height, or any other per-message validation failure), the entire `execute` call short-circuits with `Error::InvalidMessage`, and `handle_unsigned` propagates this via the `?` operator: [3](#0-2) 

Because `handle_unsigned` is annotated `#[frame_support::transactional]`, any error return rolls back *all* storage writes performed during that extrinsic — including the consensus state updates, request/response receipts, and dispatched events for every other message in the batch that was itself fully valid and would have succeeded independently.

This mirrors the referenced audit finding exactly: a loop/batch of independent external operations (there: `moneyMarket.withdrawAll` calls across adapters; here: `handle_incoming_message` calls across ISMP messages) is wrapped so that one item's failure reverts the entire batched operation, even though the other items were individually valid and important progress (fee accrual, request delivery, consensus advancement) is lost.

The EVM-side `HandlerV2.batchCall` has the identical atomic-revert semantics by design (`if (!success) revert BatchCallFailed(...)`), and the tesseract relayer explicitly batches multiple heterogeneous messages (consensus + several PostRequests/GetResponses) into one `batchCall`/`handle_unsigned` transaction to save gas: [4](#0-3) [5](#0-4) 

On the substrate side, comments in the ISMP message handler explicitly acknowledge cross-message interaction inside a single batch (duplicate detection, reentrancy protection between requests in the same batch), confirming that message batches routinely contain multiple, otherwise-independent requests dispatched together: [6](#0-5) 

### Impact Explanation
This is a liveness/griefing issue affecting the core message-delivery path (`pallet-ismp handle_unsigned`), one of the explicitly in-scope reachable paths. When a relayer batches multiple valid messages together with even one message that becomes invalid between proof-construction time and on-chain inclusion (a very likely race: e.g. a competing relayer already delivered the same request in an earlier block making it a `DuplicateRequest`, or a request timed out by the time the block executed), the entire extrinsic reverts. All the other valid requests/responses/consensus updates bundled in that same transaction fail to be delivered/processed even though they were fully valid, and their associated relayer fees are not paid. This can delay or indefinitely block message delivery on a given route if batching is used aggressively or if an adversary can predictably induce one message in a victim's batch to become stale (e.g. by racing to deliver a duplicate of one entry first), matching the "route unable to deliver messages" impact class called out as acceptable for this scan.

### Likelihood Explanation
Likelihood is elevated because:
- `handle_unsigned` is fully permissionless/unsigned — reachable by any relayer or attacker with a valid proof for at least part of the batch.
- Batching multiple messages together is a normal, encouraged operational pattern to minimize gas/weight overhead (mirrored explicitly on the EVM side via `HandlerV2.batchCall`), so batches of size > 1 are expected in production relayer software.
- Races that invalidate a single message in a batch (competing relayer delivering the same request first, request timing out during the window between proof construction and inclusion) are realistic and not attacker-exclusive — they occur naturally under normal multi-relayer operation, making the failure mode likely to manifest without any special attacker capability, and easily weaponizable by an attacker who front-runs a single entry of a known victim batch.

### Recommendation
Change `Pallet::execute` to process each message independently and record per-message success/failure instead of short-circuiting the whole batch via `.collect::<Result<Vec<_>, _>>()`. For messages that fail individually-recoverable validation (duplicate, timeout, invalid destination, stale height for that message alone), emit an `Error`/`Errors` event for that specific message and continue processing the remaining messages in the batch, applying their storage effects and event deposits normally. Only truly batch-fatal failures (e.g., proof/membership verification failure that invalidates the whole message envelope) should abort processing of the messages proven under that envelope.

### Proof of Concept
1. A relayer builds a `handle_unsigned` extrinsic containing `[msg_A, msg_B]`, where `msg_A` is a valid, freshly-provable POST request and `msg_B` is a POST request for a commitment that, due to a race with a competing relayer, already has a `request_receipt` stored (making it a duplicate) by the time the block executes.
2. `Pallet::execute` calls `handle_incoming_message` for both; `msg_B` returns `Err(Error::DuplicateRequest)`.
3. `.collect::<Result<Vec<_>, _>>()` short-circuits, the whole `execute` returns `Err(Error::InvalidMessage)`, and `handle_unsigned` propagates the error under `#[transactional]`.
4. Result: `msg_A`'s valid delivery (and any fee accrual/event emission for it) is rolled back and never lands on-chain, even though it was perfectly valid, and the relayer who submitted `msg_A` receives no payment despite doing legitimate work — the request must be resubmitted, delaying delivery of `msg_A`.

     * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls
     */
    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }
