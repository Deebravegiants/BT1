### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then trusts the `shop-domain` header verbatim to populate `WebhookMetadata#shop`, which is the field apps are documented to use as the tenant key. Because the `shop` field is never part of the signed content, any request whose body can produce a valid signature (most straightforwardly, a webhook payload legitimately delivered by Shopify for one shop that installed the same app) can be replayed with an attacker-controlled `shop-domain` header, causing the app to process/attribute that payload to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` uses this validation as the sole authentication gate, then immediately trusts `request.shop` (read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with zero cross-check against the signed body) when constructing the object handed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop attributed to the webhook == shop bound by the HMAC-verified content`. Here, `shop` (header, attacker-controllable, echoed into `WebhookMetadata#shop`) ≠ `body` (the only content actually bound by the HMAC). This is a textbook "field acted on but not covered by the HMAC" gap.

`WebhookMetadata#shop` is a plain `const :shop, String` populated from `request.shop`: [5](#0-4) 

The gem's own documentation instructs app authors to key tenant-specific work directly off `data.shop`, confirming this field is treated as an authenticated tenant identifier by consuming apps: [6](#0-5) 

### Impact Explanation
An attacker who controls a shop that has installed the target app (a normal, unprivileged path — installing a public/dev app on their own store) can capture a legitimate webhook (body + valid `x-shopify-hmac-sha256`) delivered by Shopify for their own store, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. Since `Registry.process` only checks the body HMAC and never checks that the `shop` header is consistent with anything cryptographically bound, the app's handler will process/attribute attacker-supplied webhook data as if it originated from the victim shop — e.g., enqueuing background jobs, updating per-shop caches/state, or triggering tenant-scoped side effects keyed by `data.shop`. This is a cross-tenant data/action confusion vulnerability rooted entirely in this gem's verification logic.

### Likelihood Explanation
High reachability: the only prerequisite is that the attacker operates their own shop with the target app installed (a completely unprivileged, self-service action) and can send arbitrary HTTP POSTs to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is required. The vulnerable code path (`Registry.process` → `HmacValidator.validate` → trusting `request.shop`) is exactly the path documented as the intended way to consume webhooks in this gem.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed content, or otherwise cryptographically bind the `shop-domain` header to the verified body before exposing it via `WebhookMetadata#shop`. At minimum, document prominently that `shop`/`topic`/`webhook_id` headers are unauthenticated and must not be used as a sole tenant-routing key without additional verification (e.g., cross-checking against a shop's registered webhook subscription or session).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header value Shopify sent — this HMAC is valid because it is computed only over the body using the app's `api_secret_key`, which the attacker never needs to know.
2. Attacker replays the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks the (untouched) body against the (untouched) HMAC: [7](#0-6) 
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though nothing about that value was verified: [8](#0-7) 
5. Any app logic keyed on `data.shop` (per the gem's documented usage pattern) now performs a tenant-scoped action attributed to `victim-shop.myshopify.com` using attacker-supplied body content.
