This is exactly the analog described by the rule: **"bytes verified versus bytes parsed"** — the identity binding between the HMAC signature and the trusted `shop` value breaks apart in `ShopifyAPI::Webhooks::Request`.

### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing shop spoofing on a validly-signed webhook body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts `request.shop`, which is read straight from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that gates the request only covers the raw JSON body (`to_signable_string` returns `@raw_body`). The `shop` value is never part of the bytes that are HMAC-verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read from the `shop-domain` header, entirely independent of that body [2](#0-1) . `HmacValidator.validate` only calls `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header [3](#0-2) . `Registry.process` performs this HMAC check and then unconditionally passes `request.shop` into the handler's `WebhookMetadata` as the authoritative tenant identifier [4](#0-3) .

The binding that should hold is:
`shop_value_verified_by_hmac == shop_value_delivered_to_handler`

Because `shop-domain` is outside the signed bytes, this equality never actually holds — the HMAC only proves "this exact JSON body was signed with our secret at some point," not "this body was destined for shop X." Since the body is attacker-visible (webhook payloads for many topics are not secret, and an attacker who is a legitimate merchant on their own shop receives correctly-signed webhooks for their own shop), an attacker can capture a validly-signed `(raw_body, hmac)` pair from a webhook sent to their own store, then replay the identical `raw_body`/`hmac` pair to the same app endpoint while substituting a **different** `x-shopify-shop-domain` header value (any shop string, including another merchant's shop). The HMAC check in `HmacValidator.validate` still passes (it only checks `@raw_body` against the secret), but `Registry.process` reports `request.shop` as the attacker-chosen value to the host app's handler. This constitutes a cross-tenant identity confusion: the handler acts on data it believes is authenticated for shop B while it was only ever proven to originate from shop A's payload.

### Impact Explanation
This maps to the "cross-tenant access" / credential-binding-bypass category. A host application that uses `WebhookMetadata#shop` from `ShopifyAPI::Webhooks::Registry.process` (e.g., to look up per-shop data, credentials, or to route side effects) can be tricked into associating a validly-HMAC'd payload with the wrong tenant, since the tenant identifier is not covered by the signature. This is a genuine break of the "shop authenticated versus shop used" identity binding called out in the rules.

### Likelihood Explanation
Requires the attacker to control (or have received) at least one legitimately-signed webhook body for any shop (trivial for any real merchant installing the app, since webhook bodies are not secret to the receiving merchant) and the ability to POST arbitrary headers to the app's webhook endpoint (typically an open HTTP endpoint, no additional credentials needed). No `api_secret_key`, access token, or privileged access is required — only interception/reuse of an already-delivered webhook body plus header manipulation, which is fully within the reach of an unprivileged internet user or app-installing merchant.

### Recommendation
Bind `shop-domain` (and other Shopify webhook headers that a handler relies on, e.g. `topic`) into the HMAC-signable content, or otherwise verify server-side that the `shop-domain` header matches a shop the app actually has an active session/webhook subscription for before trusting it. At minimum, `to_signable_string` should incorporate the shop domain header so `HmacValidator.validate` cannot pass with a mismatched shop.

### Proof of Concept
1. As a legitimate merchant `shop-a.myshopify.com`, install the app and receive a real webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`).
2. Replay a POST to the app's webhook endpoint with the same body `B` and same header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a different, victim shop).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) only [1](#0-0)  — validation succeeds because `B` and `H` still match.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-supplied `shop-b.myshopify.com` [5](#0-4) , and the host app's handler processes shop A's payload data believing it is for shop B.
