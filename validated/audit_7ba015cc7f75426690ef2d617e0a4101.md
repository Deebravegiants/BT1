### Title
Operator QR-code authorization schema is format-identical to user QR-code schema, collapsing the operator/user trust boundary into a single client-side parser - (File: `src/plans/qr_scan/operator.rs`)

### Summary
The Ambire report describes how fallback handlers can be crafted with a function signature that "clashes" with a base-contract selector, so a call that looks like it goes to the extension actually executes a privileged base-contract function. The orb-core signup flow has an analogous format-clash: the "operator" QR-code schema, which is supposed to represent a distinct, privileged identity (the person who owns/operates the orb and authorizes a signup session), is parsed by literally re-using the "user" QR-code parser. There is no structural/cryptographic marker that separates an operator QR-code from an ordinary end-user identity QR-code at the point where the orb decides "this code just scanned is an operator."

### Finding Description
`qr_scan::operator::Data::try_parse` does not have its own wire format for the "normal" (non-magic) operator code. Instead it directly calls the user-schema parser and wraps the result: [1](#0-0) 

```
fn try_parse(code: &str) -> Option<Self> {
    let normal = user::Data::try_parse(code)
        .filter(|d| if d.signup_extension() { d.signup_extension_config.is_some() } else { true })
        .map(Data::Normal);
    if normal.is_some() {
        return normal;
    }
    ...
```

`user::Data::try_parse` accepts several equivalent representations of the same "userid" concept (a `decode_qr`-encoded link, the `userid:<uuid>:<policy>` regex, and — under the `internal-data-acquisition` feature — a signup-extension variant): [2](#0-1) 

Because `operator::Data::try_parse` performs no independent structural check (no operator-specific prefix, signature, or backend-issued token embedded in the QR content itself), *any* string that is syntactically valid as a "user" QR-code is also syntactically valid as an "operator" QR-code, and vice versa. The two roles share exactly one wire "selector" (`userid:<uuid>[:policy]` or the equivalent `decode_qr` link), just like two Solidity functions sharing one 4-byte selector.

The only place the operator/user distinction is actually enforced is a subsequent, purely remote check: [3](#0-2) 

`verify_operator_qr_code` calls `backend::operator_status::request(qr_code)` and trusts whatever the backend says about that `user_id` being a valid operator. Locally, the orb has already:
- accepted the code as a *syntactically valid* `qr_scan::operator::Data::Normal`,
- displayed the "operator scan succeeded" UX progression,
- and stored it into `OperatorData` which subsequently gates the entire signup session (location data, `operator_qr_expiration_time`, and is sent back to the backend as `operator_id` in the user-status request): [4](#0-3) 

The client-side code has no way to tell, from the QR content alone, whether it is looking at an operator badge or a signup identity code — exactly the "no whitelisting/validation around the selector will work" problem called out in the Ambire report, except here the "contract" is the orb software and the "fallback handler" is the ordinary user-identity code path being fed into the operator-identity code path.

### Impact Explanation
If the remote `backend::operator_status::request` check were ever weakened, bypassed offline (e.g. via the CLI/test override path `operator_qr_code_override`, or a future change adding a local fast-path), or if an operator ID were ever guessable/enumerable, the lack of any local structural distinction means the orb has no independent way to reject a spoofed operator identity — the local schema will happily parse and forward it as `Data::Normal`. This collapses what should be two structurally distinct trust levels (operator vs. signee) into one shared format, pushing the entire boundary onto a single remote call. Any defect or drift in that one remote check directly translates into unauthorized "operator" acceptance for a signup session, analogous to how the fallback-handler clash in the Ambire contract let an attacker's crafted call silently execute the base contract's privileged function.

### Likelihood Explanation
Exploitability today is bounded, because the current flow does perform a mandatory backend call (`verify_operator_qr_code`) before treating the scanned code as an authorized operator, and there is no local privileged action gated purely on the client-side parse result. However, the likelihood that this format-clash could be silently exploited increases with any future refactor that adds a local optimization/override (the repo already contains one such override, `operator_qr_code_override`, used for CLI/testing) or any backend regression, since the client code offers zero independent defense-in-depth against a user-code being accepted as an operator-code.

### Recommendation
Give the operator QR-code schema a distinct, non-overlapping wire format from the user QR-code schema (e.g., a distinguishing prefix/tag that is never valid input to `user::Data::try_parse`, or a signed/backend-issued operator token rather than a bare UUID), so that `operator::Data::try_parse` cannot succeed on input that is also valid `user::Data`. This restores a structural (not purely remote) boundary between the two roles, consistent with avoiding "selector clashing" between logically distinct handlers.

### Proof of Concept
1. Take any valid end-user signup QR-code string, e.g. `userid:66ad4897-0ca7-4727-8365-ca808348e3cd:1` (this exact string is even used as `DUMMY_OPERATOR_QR_CODE` in [5](#0-4) , demonstrating the two schemas are literally interchangeable strings).
2. Present it during the "operator QR-code scanning" phase (`scan_operator_qr_code` in `src/plans/mod.rs`).
3. `qr_scan::Plan::<qr_scan::operator::Data>::new(...)` calls `operator::Data::try_parse`, which delegates to `user::Data::try_parse`, succeeds, and returns `Data::Normal(user::Data { user_id: "66ad4897-...", .. })` — the orb UI reports a successful operator scan before any backend verification occurs.
4. Only afterward does `verify_operator_qr_code` ask the backend whether this `user_id` is a legitimate operator; if that single remote check is ever bypassed, weakened, or overridden (as already possible via the `operator_qr_code_override` CLI/test path shown in [6](#0-5) ), the exact same string that is meant to identify an ordinary signee is accepted as a valid operator identity with no additional local check.

    #[allow(clippy::cast_possible_truncation)]
    async fn verify_operator_qr_code(
        &self,
        orb: &mut Orb,
        qr_code: &qr_scan::user::Data,
        qr_capture_start: Instant,
    ) -> Result<Option<(u64, backend::operator_status::LocationData)>> {
        if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
            return Ok(Some((0, backend::operator_status::LocationData {
                team_operating_country: "DEV".to_string(),
                session_coordinates: Coordinates { latitude: 0.0f64, longitude: 0.0f64 },
                stationary_location_coordinates: None,
            })));
        }
        let http_start = Instant::now();
        match backend::operator_status::request(qr_code).await {
            Ok(backend::operator_status::Status { valid: true, location_data, reason: _ }) => {
                let location_data = location_data
                    .expect("to always have a result from the backend if valid == true");
                orb.ui.qr_scan_success(QrScanSchema::Operator);
                dd_incr!("main.count.global.distr_code_validated");
                tracing::info!("Operator QR-code validated: {qr_code:?}");
                dd_timing!("main.time.signup.distr_qr_code_capture", qr_capture_start);
                return Ok(Some((http_start.elapsed().as_millis() as u64, location_data)));
            }
            Ok(backend::operator_status::Status { valid: false, .. }) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
                dd_incr!("main.count.signup.result.failure.distr_qr_code", "type:invalid_qr");
            }
            Err(_) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
            }
        }
        Ok(None)
    }
