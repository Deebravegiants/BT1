Audit Report

## Title
Unauthenticated `/discovery`, `/plugins/:name/metrics`, and `/plugins/:name/debug/pprof/*` endpoints disclose internal service/plugin details and debug data - (File: core/web/router.go)

## Summary
`loopRoutes` is mounted directly on the shared `api` gin group in `NewRouter` without any `auth.Authenticate` wrapper, unlike `debugRoutes`, `sessionRoutes`, and `v2Routes`, which explicitly require session or token authentication. This allows any unauthenticated client with network access to the node's API port to enumerate LOOP plugins via `/discovery`, pull prometheus metrics via `/plugins/:name/metrics`, and — most seriously — retrieve full Go `pprof` debug/profiling output via `/plugins/:name/debug/pprof/*`, which is proxied verbatim from an internal-only plugin endpoint.

## Finding Description
In `NewRouter`, the top-level `api` group only applies rate limiting and a session-cookie middleware (not authentication) [1](#0-0) . `debugRoutes` deliberately wraps `/debug/vars` in `auth.Authenticate` [2](#0-1) , `sessionRoutes` gates `DELETE /sessions` behind `auth.Authenticate` [3](#0-2) , and `v2Routes` requires token or session auth for its `authv2` group [4](#0-3) . In contrast, `loopRoutes` registers `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, and `/plugins/:name/debug/pprof/symbol` directly on `r` with zero auth middleware [5](#0-4) .

`discoveryHandler` returns hostnames, exposed prometheus port, and all registered LOOP plugin names as JSON to any caller with no auth check [6](#0-5) . `pluginPPROFHandler` builds a URL to the internal plugin's `/debug/pprof/` endpoint using the caller-supplied `profile` path segment and forwards the raw response back to the caller [7](#0-6) , and the comment `// unlike discovery, this endpoint is internal btw the node and plugin` explicitly acknowledges that this proxies into an internal-only channel [8](#0-7) . There is no authentication middleware anywhere in this code path, confirming the broken security assumption relative to `debugRoutes`.

## Impact Explanation
An unauthenticated attacker reaching the node's API port can enumerate internal LOOP plugin topology, scrape prometheus metrics, and pull raw `pprof` debug dumps (`heap`, `goroutine`, `profile`, `trace`) for any named plugin without credentials. This is a genuine information-disclosure finding: it discloses internal service/plugin details and debug output to unauthenticated network clients, analogous in class (though the plugin-name enumeration is fairly narrow) to CVE-2024-9802-style unauthenticated info leaks. It does not by itself grant authentication bypass, key/secret exfiltration, unauthorized job execution, or fund movement — the impact is confined to confidentiality of internal operational/debug data, matching a low/informational severity rather than a high-impact compromise.

## Likelihood Explanation
Exploitation requires no credentials and is a trivial unauthenticated GET request, so likelihood is high wherever the node's API port is network-reachable by untrusted clients. This is the standard threat model in scope for the node's HTTP API (the Chainlink node API is intended to be reachable by API-token holders for `/v2` routes, but `loopRoutes` bypasses that boundary entirely), so this is reachable by an unprivileged actor consistent with the validation rules.

## Recommendation
Wrap `loopRoutes` in the same `auth.Authenticate` middleware used by `debugRoutes`/`v2Routes` (session or token auth), and additionally validate/allowlist the `profile` path segment in `pluginPPROFHandler` before concatenating it into the internal plugin URL to prevent path/query injection into the internal request.

## Proof of Concept
Against a running node with at least one LOOP plugin registered:
```
curl http://<chainlink-node>:6688/discovery
curl http://<chainlink-node>:6688/plugins/<plugin-name>/metrics
curl http://<chainlink-node>:6688/plugins/<plugin-name>/debug/pprof/goroutine?debug=2
```
No `Authorization` header or session cookie is required; compare against `curl http://<chainlink-node>:6688/debug/vars`, which returns 401 due to `auth.Authenticate` in `debugRoutes`, demonstrating the inconsistency. A Go integration test asserting `loopRoutes` handlers respond 200 without any session/token, while `debugRoutes`/`v2Routes` require one, would confirm the gap.

```go
// discoveryHandler implements service discovery of prom endpoints for LOOPs in the registry
func (l *LoopRegistryServer) discoveryHandler(w http.ResponseWriter, req *http.Request) {
	w.Header().Set("Content-Type", "application/json")
	groups := make([]*targetgroup.Group, 0, 1+len(l.registry.List()))

	// add node metrics to service discovery
	groups = append(groups, pluginGroup(l.discoveryHostName, l.exposedPromPort, "/metrics"))

	// add all the plugins
	for _, registeredPlugin := range l.registry.List() {
		group := pluginGroup(l.discoveryHostName, l.exposedPromPort, pluginMetricPath(registeredPlugin.Name))
		group.Labels[LabelMetaPluginName] = model.LabelValue(registeredPlugin.Name)
		groups = append(groups, group)
	}
```

```go
func (l *LoopRegistryServer) pluginPPROFHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/"+gc.Param("profile"), l.loopHostName, p.EnvCfg.PrometheusPort)
	urlVals, timeout := pprofURLVals(gc)
	if s := urlVals.Encode(); s != "" {
		pluginURL += "?" + s
	}
	l.logger.Infow("Forwarding plugin pprof request", "plugin", pluginName, "url", pluginURL)
	l.doRequest(gc, "GET", pluginURL, nil, timeout, pluginName)
}
```
