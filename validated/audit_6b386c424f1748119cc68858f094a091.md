### Title
Deposit mints LP tokens based on the pre-transfer-fee amount, not the amount actually received by the vault - ([File: program/src/processor.rs])

### Summary
`process_deposit` computes `deduct_coin_amount`/`deduct_pc_amount` from the pool's exchange ratio and then calls `Invokers::token_transfer` to move that exact amount from the user into the AMM vaults, using the plain (non fee-aware) SPL `transfer` instruction. `mint_lp_amount` is computed from those same pre-transfer amounts, and `amm.lp_amount` is incremented by `mint_lp_amount` immediately, without ever re-checking the vault's actual post-transfer balance.

### Finding Description
In `process_deposit`, the deducted amounts are derived purely from the `InvariantPool`/`InvariantToken` math against `deposit.max_coin_amount`/`deposit.max_pc_amount`: [1](#0-0) [2](#0-1) 

These `deduct_coin_amount`/`deduct_pc_amount` values are then transferred via `Invokers::token_transfer`, and `mint_lp_amount` (computed before the transfer, from the same nominal amounts) is minted to the user and added to `amm.lp_amount`: [3](#0-2) 

`Invokers::token_transfer` issues a plain `spl_token::instruction::transfer` (not `transfer_checked` with fee-aware handling, and there is no post-transfer balance re-read): [4](#0-3) 

If `amm.coin_vault_mint` or `amm.pc_vault_mint` is a token with a fee-on-transfer mechanism (e.g. SPL-Token-2022 `TransferFeeConfig`, or a legacy SPL token that later activates a fee), the vault actually receives `deduct_amount - fee`, but the code:
1. Mints LP tokens as if the full `deduct_amount` arrived (`mint_lp_amount` calculated pre-fee).
2. Increments the internal `amm.lp_amount` accounting by the same over-stated `mint_lp_amount`.

This directly parallels the referenced report's root cause: minting pool-share tokens off of the nominal transfer amount instead of the amount actually credited to the receiving account.

### Impact Explanation
Every deposit into a pool backed by a fee-on-transfer token mints LP tokens that are not fully backed by vault assets, silently diluting/insolvent-izing the pool's coin:pc:lp_amount ratio used by `calc_total_without_take_pnl_no_orderbook` and `InvariantPool`. Over repeated deposits, this compounds: the pool's internally tracked `amm.lp_amount` grows faster than real backing, so later withdrawers (via `process_withdraw`, which pays out proportional to `amm.lp_amount`) can drain more real tokens than were actually deposited, at the expense of other LPs/the pool. This is an unbacked LP minting / insolvent pool accounting condition affecting all LP holders, not just the depositor.

### Likelihood Explanation
This is reachable by any unprivileged user calling the `Deposit` instruction against a pool whose `coin_vault_mint`/`pc_vault_mint` is a fee-on-transfer token (e.g., an SPL-Token-2022 mint with `TransferFeeConfig` enabled, or a would-be fee-enabled USDT/USDC-style token as referenced in the report). No special privileges or account substitution is needed beyond depositing into a pool for such a mint; the vulnerability triggers automatically on every such deposit. The severity depends on such tokens being paired in a pool, which is plausible since coin/pc mints are attacker/pool-creator chosen at `Initialize2` time.

### Recommendation
Read the vault's actual token balance before and after the `token_transfer` call (or use `transfer_checked`/read balance deltas) and use the **actual received delta** — not the nominal `deduct_coin_amount`/`deduct_pc_amount` — when computing `mint_lp_amount` and updating `amm.lp_amount`/`target_orders.calc_pnl_x/y`. Equivalently, reject deposits/pool creation for mints that report a nonzero transfer-fee configuration (for Token-2022 mints) at `Initialize2` time.

### Proof of Concept
1. `Initialize2` a pool where `amm_pc_mint` (or `amm_coin_mint`) is a Token-2022 mint with `TransferFeeConfig` set (e.g., 2% fee) — `process_initialize2` performs no check rejecting fee-configured mints (see `program/src/processor.rs` initialize2 flow read/unpack of mint at lines 742-745 with no `TransferFeeConfig` extension check).
2. Call `Deposit` with `max_pc_amount = 1_000_000`, `base_side = 1` (base pc). `deduct_pc_amount = 1_000_000` is computed and transferred via `token_transfer`.
3. Because of the 2% fee, `amm_pc_vault` only receives `980_000`, but `mint_lp_amount` was already computed from `total_pc_without_take_pnl` assuming the full `1_000_000` had/will arrive, and `amm.lp_amount` is incremented by that inflated `mint_lp_amount`.
4. Subsequent `Withdraw` calls compute payout proportional to `amm.lp_amount` vs actual vault balances, letting LP holders redeem more than the vault actually holds, draining real coin/pc from other depositors.
