## Title
Reward-Dilution Sandwich on `internal_ping()` Epoch Reward Distribution — (`File: staking-pool/src/internal.rs`)

## Summary
The NEAR staking-pool reference contract distributes validator staking rewards to delegators purely pro-rata over `total_stake_shares` at the moment `internal_ping()` realizes them, with no accounting for how long each shareholder's capital was actually staked with the validator during the period that generated the reward. An unprivileged user can deposit/stake immediately before a reward-realizing `ping()` (triggered by any account action after an epoch change) and unstake immediately after, capturing a disproportionate share of rewards that their own capital did not help earn — diluting genuine long-term stakers. This is the same "sandwich the pooled-reward accrual event" root cause as the Sherlock Carapace `accruePremiumAndExpireProtections()` finding (H-12/#26), just instantiated against `internal_ping()`'s share-price update instead of `totalSTokenUnderlying` update.

## Finding Description
Every state-mutating entry point (`deposit`, `deposit_and_stake`, `stake`, `stake_all`, `unstake`, `unstake_all`, `withdraw`, `withdraw_all`, `ping`) calls `internal_ping()` first: [1](#0-0) 

`internal_ping()` only realizes a reward once per epoch (`last_epoch_height` guard), and when it does, it computes `total_reward` from the actual change in `account_locked_balance() + account_balance()`, then distributes the *entire* reward across the *current* `total_stake_shares`: [2](#0-1) 

Because `total_reward` reflects rewards earned by the amount that was actually staked with the validator in the *prior* epoch(s) (NEAR's stake-proposal activation is delayed by design), but is distributed over whatever `total_stake_shares` exist at the moment `ping()` finally runs, a user who deposits/stakes new capital in the epoch *before* the reward is realized receives shares that participate fully in that reward distribution — despite that capital never being staked with the validator when the reward was earned. This dilutes the fair entitlement of the real long-term stakers, exactly analogous to the `accruePremiumAndExpireProtections()` case where a late depositor captured a slice of premium accrued from other users' underwritten capital.

Sequence: any unprivileged account can call `deposit_and_stake()` in epoch N (a no-op ping since the epoch hasn't changed, so no reward gate blocks the deposit at the pre-reward price), then after the epoch boundary passes, call (or wait for someone else to call) any action which triggers `internal_ping()` for epoch N+1, realizing the accrued validator reward pro-rata across shares including the attacker's freshly added ones, then immediately call `unstake_all()` — which itself re-runs `internal_ping()` (no-op, same epoch) and converts the now-inflated shares to unstaked balance at the diluted price via `inner_unstake`: [3](#0-2) 

## Impact Explanation
This falls under the "Share, reward ... accounting divergence that lets an unprivileged user over-credit value ... or withdraw more than fair entitlement" impact class. Using the same numbers as the original report: 1,000,000 staked / 1,000,000 shares; attacker deposits 100,000 before the reward window closes (1,100,000 staked / 1,100,000 shares, price still 1:1); a genuine 100,000 validator reward is then realized over the new 1,100,000 shares (price becomes 1,200,000/1,100,000 ≈ 1.0909); attacker's 100,000 shares convert to ≈109,090 — a ≈9,090 profit taken directly from the honest stakers who actually earned that reward, who now hold ≈1,090,909 instead of the 1,100,000 they were entitled to.

## Likelihood Explanation
Reachable by any unprivileged NEAR account with no special role, purely through the public `deposit_and_stake`/`unstake_all`/`withdraw_all` entry points — no trusted role, key, or validator control needed. The only friction versus the original one-block EVM sandwich is the ~epoch-length holding period (funds convert to "unstaked" balance immediately at the inflated price upon `unstake_all()`; only the final NEAR transfer via `withdraw` is subject to the 4-epoch unbonding delay), so the unfair profit is locked in well before withdrawal completes. This is a lower-frequency, higher-latency variant of the same reward-dilution sandwich class, but it is deterministically exploitable by any depositor who times deposits around epoch boundaries and pool activity.

## Recommendation
- Track a time- or epoch-weighted stake basis (e.g., only allow newly deposited/staked capital to participate in reward distribution starting from the epoch in which it actually becomes bonded with the validator, rather than immediately minting shares that participate in the very next realized reward).
- Alternatively, apply a cooldown/vesting on newly staked shares before they are eligible to receive a `ping()`-realized reward, or realize/checkpoint pending rewards against the pre-existing share set before minting new shares for a deposit that arrives in the same epoch a reward is about to be recognized.
- Consider streaming/time-decaying reward crediting instead of instantaneous full pro-rata crediting at `ping()` time, mirroring the Sherlock recommendation of delivering value over a delivery period rather than atomically at accrual time.

## Proof of Concept
1. Pool state: `total_staked_balance = 1_000_000`, `total_stake_shares = 1_000_000` (price 1:1).
2. Attacker calls `deposit_and_stake(100_000)` in epoch N. `internal_ping()` is a no-op (same epoch), so shares are minted at the pre-reward 1:1 price: `total_staked_balance = 1_100_000`, `total_stake_shares = 1_100_000`, attacker holds 100,000 shares.
3. Epoch advances to N+1; the validator's actual locked balance grows by a real reward of 100,000 (earned only by the original 1,000,000 that was actually bonded with the validator).
4. Any account (including the attacker) triggers an action that calls `internal_ping()`; per [4](#0-3)  the full 100,000 reward is added to `total_staked_balance` (now 1,200,000) and distributed pro-rata over `total_stake_shares` (1,100,000), giving a price of ≈1.0909.
5. Attacker immediately calls `unstake_all()`; `inner_unstake` converts the attacker's 100,000 shares into ≈109,090 unstaked balance per [5](#0-4) , a ≈9,090 profit extracted from the honest stakers' rightful reward share.

    pub(crate) fn inner_unstake(&mut self, amount: u128) {
        assert!(amount > 0, "Unstaking amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);

        assert!(
            self.total_staked_balance > 0,
            "The contract doesn't have staked balance"
        );
        // Calculate the number of shares required to unstake the given amount.
        // NOTE: The number of shares the account will pay is rounded up.
        let num_shares = self.num_shares_from_staked_amount_rounded_up(amount);
        assert!(
            num_shares > 0,
            "Invariant violation. The calculated number of \"stake\" shares for unstaking should be positive"
        );
        assert!(
            account.stake_shares >= num_shares,
            "Not enough staked balance to unstake"
        );

        // Calculating the amount of tokens the account will receive by unstaking the corresponding
        // number of "stake" shares, rounding up.
        let receive_amount = self.staked_amount_from_num_shares_rounded_up(num_shares);
        assert!(
            receive_amount > 0,
            "Invariant violation. Calculated staked amount must be positive, because \"stake\" share price should be at least 1"
        );

        account.stake_shares -= num_shares;
        account.unstaked += receive_amount;
        account.unstaked_available_epoch_height = env::epoch_height() + NUM_EPOCHS_TO_UNLOCK;
        self.internal_save_account(&account_id, &account);

        // The amount tokens that will be unstaked from the total to guarantee the "stake" share
        // price never decreases. The difference between `receive_amount` and `unstake_amount` is
        // paid from the allocated STAKE_SHARE_PRICE_GUARANTEE_FUND.
        let unstake_amount = self.staked_amount_from_num_shares_rounded_down(num_shares);

        self.total_staked_balance -= unstake_amount;
        self.total_stake_shares -= num_shares;

    /// Distributes rewards after the new epoch. It's automatically called before every action.
    /// Returns true if the current epoch height is different from the last epoch height.
    pub(crate) fn internal_ping(&mut self) -> bool {
        let epoch_height = env::epoch_height();
        if self.last_epoch_height == epoch_height {
            return false;
        }
        self.last_epoch_height = epoch_height;

        // New total amount (both locked and unlocked balances).
        // NOTE: We need to subtract `attached_deposit` in case `ping` called from `deposit` call
        // since the attached deposit gets included in the `account_balance`, and we have not
        // accounted it yet.
        let total_balance =
            env::account_locked_balance() + env::account_balance() - env::attached_deposit();

        assert!(
            total_balance >= self.last_total_balance,
            "The new total balance should not be less than the old total balance"
        );
        let total_reward = total_balance - self.last_total_balance;
        if total_reward > 0 {
            // The validation fee that the contract owner takes.
            let owners_fee = self.reward_fee_fraction.multiply(total_reward);

            // Distributing the remaining reward to the delegators first.
            let remaining_reward = total_reward - owners_fee;
            self.total_staked_balance += remaining_reward;

            // Now buying "stake" shares for the contract owner at the new share price.
            let num_shares = self.num_shares_from_staked_amount_rounded_down(owners_fee);
            if num_shares > 0 {
                // Updating owner's inner account
                let owner_id = self.owner_id.clone();
                let mut account = self.internal_get_account(&owner_id);
                account.stake_shares += num_shares;
                self.internal_save_account(&owner_id, &account);
                // Increasing the total amount of "stake" shares.
                self.total_stake_shares += num_shares;
            }
            // Increasing the total staked balance by the owners fee, no matter whether the owner
            // received any shares or not.
            self.total_staked_balance += owners_fee;
