### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` are trusted from HTTP headers that are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone, while the tenant-identifying `shop` value (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers that are never part of the signed payload. `Registry.process` verifies only the body's HMAC and then dispatches the handler using these unauthenticated header values, breaking the intended binding `hmac_valid(raw_body) == authentic(shop, topic, ...)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` signs/verifies exactly that string: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from request headers, none of which feed into `to_signable_string`: [3](#0-2) 

`Registry.process` validates only the (body-only) HMAC, then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to build `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The equality the code relies on is: `hmac_valid(raw_body)` (proves the *body bytes* originated from a source with the shared secret) versus `shop == actual_originating_shop` (used to attribute the payload to a merchant tenant). These are two independent facts, but the code treats a valid body signature as if it also authenticates the header-derived `shop`/`topic`/`webhook_id` values, since none of them are bound into the HMAC input.

### Impact Explanation
Any unprivileged internet user who controls a store where the app is installed (any developer/trial store obtains one legitimately) can capture one authentic webhook delivery (raw body + valid HMAC) generated by their own shop, and replay the exact same bytes to the app's webhook endpoint while freely spoofing the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers, since the HTTP request being crafted is not itself a Shopify-originated request signature-bound to those headers — only the raw body is. The HMAC check in `Registry.process` still passes because the body is unmodified, but the app's handler will process the attacker's own shop's webhook body while believing (`WebhookMetadata#shop`) it belongs to any shop of the attacker's choosing. Depending on how the host application keys tenant data/session lookups off `WebhookMetadata#shop`, this enables cross-tenant data injection/attribution — an authenticated-looking webhook event is written into another merchant's tenant context using attacker-supplied body content.

### Likelihood Explanation
Reachable by any unprivileged actor who can install the target app on a store they control (a normal, low-friction action for any Shopify developer) — no `api_secret_key`, access token, or privileged account is required to mount the replay itself. The only prerequisite is capturing one legitimate webhook delivery from a shop the attacker controls, which is trivial and self-servable.

### Recommendation
Bind the header-derived identity fields into the signed payload, e.g. compute the HMAC over a canonical string that includes `shop`, `topic`, and `webhook_id` in addition to the raw body (matching Shopify's documented practice of validating the full request context, not just the body), or otherwise cryptographically verify that the `shop-domain` header corresponds to the same webhook subscription/secret used to sign the body before constructing `WebhookMetadata`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic to receive a body `B` with valid header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`).
2. Replay an HTTP POST to the app's webhook endpoint with the identical body `B` and identical `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B) == H` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the body actually originated from `attacker.myshopify.com`.
