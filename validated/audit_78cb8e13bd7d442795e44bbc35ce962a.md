### Title
Webhook `shop` (tenant) identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop-domain` header, which is the only tenant identifier delivered to the app's handler, is never included in the signed payload. Because the HMAC key (`Context.api_secret_key`) is the app's single, shop-independent secret, any body+HMAC pair that is valid for one shop is also valid, verbatim, for every other shop — the signature proves "this body came from Shopify for this app," not "this body belongs to this shop."

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)` before dispatching to a handler [5](#0-4) . `HmacValidator.validate_signature` recomputes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` accessor [2](#0-1) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are pulled directly from HTTP headers that are never mixed into the signed string [6](#0-5) . Once validation passes, `request.shop` is forwarded as the tenant identity into `WebhookMetadata` and handed to the app's handler [7](#0-6) .

The equality the code implicitly assumes is:
`shop authenticated (bytes covered by HMAC) == shop acted upon (header value passed to handler)`

That equality does not hold: the HMAC covers zero bytes of the `shop` field. Since the signing key is the app's shared `api_secret_key` (identical for every shop that installs the app), any unprivileged internet user can:
1. Install the target app on a shop they control (or otherwise cause Shopify to deliver one legitimate webhook to the app for their own shop), and capture the exact `raw_body` + `x-shopify-hmac-sha256` header Shopify sent.
2. Replay that identical body and HMAC directly to the app's public webhook endpoint, but substitute the `x-shopify-shop-domain` header with an arbitrary victim shop's domain.
3. `HmacValidator.validate` still succeeds (it never looked at the header), and the handler processes the payload believing it originates from the victim shop.

This is the direct analog of the report's core defect: a value that influences reward/state accounting (there, pool liquidity attribution; here, tenant attribution) is mutable by an unprivileged party independent of the cryptographic check that is supposed to gate it — because the check's protected surface (body only) doesn't cover the field being acted upon (shop header).

### Impact Explanation
This breaks the tenant/authentication boundary between shops for any app relying on this gem's webhook signature verification as the sole authenticity/tenancy check (as documented and demonstrated in `docs`/tests, this is the intended usage: `HmacValidator.validate` is presented as the full trust boundary for `Registry.process`). An attacker can inject fabricated webhook events attributed to a victim merchant's shop (e.g., fake `orders/create`, `app/uninstalled`, `shop/update`, GDPR/mandatory webhooks) into the app's business logic, causing cross-tenant data corruption, spoofed state transitions, or triggering shop-specific side effects (billing, fulfillment, data deletion via mandatory privacy webhooks) for a shop the attacker does not own. This qualifies as cross-tenant access under the Critical impact bucket.

### Likelihood Explanation
High. No credentials beyond a normal, unprivileged Shopify Partner/dev-store account are required — a real merchant installation on any shop under the attacker's control yields a valid, replayable body+HMAC pair, since the signing secret is shared across all tenants of the app. The victim's shop domain is a public, guessable/observable value (`{shop}.myshopify.com`). No interaction with the app's private `client_secret` value itself is needed — only its side effect (a validly-signed body).

### Recommendation
Bind the tenant identity into the signed material, or otherwise cryptographically verify that the `shop-domain` header matches the shop the webhook was registered for. Concretely:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) header value in the HMAC-signed string (`to_signable_string`) rather than only the raw body, or
- After HMAC validation, independently verify that the `shop` extracted from the request corresponds to a shop with an active session/registration known to the app, rejecting mismatches, or
- Document explicitly (and enforce in code) that host applications must not treat the `shop` header from `Webhooks::Request` as trusted without additional out-of-band verification.

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end
