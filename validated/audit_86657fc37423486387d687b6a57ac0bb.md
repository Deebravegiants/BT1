Based on my investigation, I found an analog to the stETH peg-assumption bug (H-06 mitigation gap): Zest's `stSTXbtc` asset — described in `docs/vaults.md:232-235` as "Liquid staked STX (BTC yield)" — is priced using the wrong oracle feed with no accrual ratio applied, unlike its sibling `stSTX`, which correctly uses a staking ratio.

### Title
Incorrect/missing yield-ratio price transformation for stSTXbtc breaks collateral-value identity - (File: `mainnet/contracts/utility/v0-1-data.clar`)

### Summary
The `get-asset-price` helper prices `stSTXbtc` (a yield-bearing liquid-staking derivative, analogous to stETH) using the raw `PYTH-STX` feed with no ratio/accrual adjustment, while its sibling `stSTX` correctly multiplies the base price by a live staking ratio. This mirrors exactly the class of bug described in the H-06 mitigation report: assuming a fixed peg for a derivative token instead of applying its true, time-varying conversion rate to the underlying.

### Finding Description
`get-asset-price` in `mainnet/contracts/utility/v0-1-data.clar:546-549` correctly transforms `stSTX`'s price by multiplying the STX price by a live `get-ststx-ratio()` value: [1](#0-0) 

But for `stSTXbtc`, the same function just returns the raw STX price with no ratio applied at all: [2](#0-1) 

The comment on that line even says "stSTXbtc - BTC price (liquid staked STX with BTC yield)" yet the code calls `get-pyth-price PYTH-STX`, not a BTC feed, and applies no accrual/ratio factor at all — unlike `stSTX`, there is no `get-ststxbtc-ratio` helper anywhere in the codebase (confirmed via `grep_search`, no matches). The `zstSTXbtc` price computation compounds this by taking this flawed base price and multiplying only by the vault's own liquidity index: [3](#0-2) 

The same pattern repeats identically in `local-testing/contracts/utility/protocol-data.clar:588-594` and in the market oracle-resolution path, `resolve-callcode`, where `CALLCODE-ZSTSTXBTC` routes straight to `resolve-ztoken p stSTXbtc` with **no** preceding ratio transform, unlike `CALLCODE-ZSTSTX` which first calls `resolve-ststx`: [4](#0-3) 

This breaks the identity that collateral-value (USD) must equal `shares × true-conversion-rate × underlying-price`. Instead, the protocol is either: (a) using the wrong underlying entirely (STX price instead of a BTC-denominated or ratio-adjusted price), or (b) assuming a permanent 1:1 relationship between `stSTXbtc` and STX/BTC that ignores its "BTC yield" accrual, exactly the flaw the H-06 mitigation report flags for stETH.

### Impact Explanation
If `stSTXbtc`'s true value diverges from the raw STX price used here (which it will, given the vault's own documentation states it accrues BTC-denominated yield over time), then:
- Collateral backed by `stSTXbtc`/`zstSTXbtc` will be systematically mispriced in `calculate-asset-notional-value` and the liquidation engine (`process-collateral-asset`, `v0-4-market.clar:789-829`), letting borrowers either extract undercollateralized loans (protocol insolvency / theft of principal) or letting liquidators seize excess/insufficient collateral relative to true value (theft of principal / unclaimed yield), since all downstream LTV, health-factor, and liquidation math depends on this price.
- This qualifies as High/Critical per the rubric: protocol insolvency or theft of principal through systematic oracle mispricing caused by a bug in Zest's own price-resolution code (in scope per the rules, since "Oracle manipulation caused by a bug in THIS code stays in scope").

### Likelihood Explanation
This is not a one-off edge case — it triggers on every price lookup for `stSTXbtc`/`zstSTXbtc` collateral or debt, i.e., every deposit, borrow, health-factor check, and liquidation touching that asset. No attacker action is needed beyond holding/using stSTXbtc-backed positions once its true value diverges from the raw STX price, which will happen naturally as staking/BTC yield accrues.

### Recommendation
Add a proper `get-ststxbtc-ratio` (or equivalent BTC-denominated conversion) analogous to `get-ststx-ratio`/`resolve-ststx`, and apply it consistently in `get-asset-price` (`v0-1-data.clar` and `protocol-data.clar`) and in `resolve-callcode`/`CALLCODE-ZSTSTXBTC` (`v0-4-market.clar`), verifying against the actual `stSTXbtc` token's documented yield mechanism (BTC-denominated) rather than reusing the STX price feed unmodified.

### Proof of Concept
I could not execute code in this environment, so this is a logical/static trace rather than an executed exploit:
1. `stSTXbtc` accrues yield over time per `docs/vaults.md:232-235` ("Liquid staked STX (BTC yield)").
2. Compare `get-asset-price` for `stSTX` (ratio-adjusted, `v0-1-data.clar:546-549`) vs `stSTXbtc` (raw STX price, no ratio, `v0-1-data.clar:581-582`) — the asymmetry confirms the missing transformation.
3. Confirm no `get-ststxbtc-ratio`-style helper exists anywhere in the repo (`grep_search` for `ststxbtc-ratio|STSTXBTC-RATIO` returned no matches), meaning there is no mechanism to correct for this drift, unlike stSTX.
4. Any USD valuation of `stSTXbtc`/`zstSTXbtc` collateral or debt in `calculate-asset-notional-value` (`v0-4-market.clar:544-574`) and the liquidation path (`process-collateral-asset`/`process-debt-asset`, `v0-4-market.clar:761-829`) will therefore use a stale/incorrect price as soon as `stSTXbtc`'s true value diverges from the raw STX feed.

I was unable to locate the actual `stSTXbtc` token contract's implementation of its yield mechanism within the index, so I cannot fully confirm the magnitude or direction of the price divergence — a Devin session with full repo/filesystem access would be needed to inspect the `ststxbtc-token-v2` contract (referenced only via its principal in comments, e.g. `local-testing/contracts/utility/protocol-data.clar:898`) to quantify the drift precisely.
