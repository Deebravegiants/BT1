**Why the reported scenario is not exploitable:**

The `create_resource_account` logic explicitly handles the front-running case by design: [1](#0-0) 

The key defense is that `resource_addr` is computed as `sha3_256(bcs(source) || seed || DERIVE_RESOURCE_ACCOUNT_SCHEME)` where `DERIVE_RESOURCE_ACCOUNT_SCHEME = 255`, a value intentionally distinct from `ED25519_SCHEME`, `MULTI_ED25519_SCHEME`, `SINGLE_KEY_SCHEME`, and `MULTI_KEY_SCHEME`: [2](#0-1) 

This domain separation exists precisely to prevent an adversary from constructing a real keypair whose derived address collides with a resource-account address, as stated in the function's own doc comment: "the probability of a collision where someone has legitimately produced a private key that maps to a resource account address is less than `(1/2)^(256)`": [3](#0-2) 

The proof idea requires the attacker to "submit a transaction from a signer at that address to set sequence_number > 0." To do that on Aptos, the transaction's sender address must match the address derivable from the authenticator's public key/scheme (this is how implicit account creation binds address to auth key). Bumping `sequence_number` above 0 at `resource_addr` therefore requires possessing a private key whose derived address equals a SHA3-256 output the attacker does not control the preimage of — i.e., it requires inverting SHA3-256, which is computationally infeasible (not an "unprivileged, practically achievable" action).

Separately, merely funding/depositing to the predicted address (e.g. via `aptos_account::transfer`) does **not** raise the sequence number and does **not** block the legitimate flow — the code explicitly re-derives ownership in that case (confirmed by `test_resource_account_and_create_account`): [4](#0-3) 

Since the described attack path requires breaking SHA3-256 preimage resistance rather than exercising a genuine logic flaw reachable by realistic unprivileged input, it does not cross a real custody boundary and is already mitigated by the scheme-separation design documented directly in the code.

```text
        let bytes = bcs::to_bytes(source);

        from_bcs::to_address(hash::sha3_256(bytes))
```

```text
    public fun create_resource_account(source: &signer, seed: vector<u8>): (signer, SignerCapability) acquires Account {
        let resource_addr = create_resource_address(&signer::address_of(source), seed);
        let resource = if (exists_at(resource_addr)) {
            if (resource_exists_at(resource_addr)) {
            let account = &Account[resource_addr];
            assert!(
                account.signer_capability_offer.for.is_none(),
                error::already_exists(ERESOURCE_ACCCOUNT_EXISTS),
            );
            };
            assert!(
                get_sequence_number(resource_addr) == 0,
                error::invalid_state(EACCOUNT_ALREADY_USED),
            );
            create_signer(resource_addr)
        } else {
            create_account_unchecked(resource_addr)
        };

        // By default, only the SignerCapability should have control over the resource account and not the auth key.
        // If the source account wants direct control via auth key, they would need to explicitly rotate the auth key
        // of the resource account using the SignerCapability.
        rotate_authentication_key_internal(&resource, ZERO_AUTH_KEY);

        let account = &mut Account[resource_addr];
        account.signer_capability_offer.for = option::some(resource_addr);
        let signer_cap = SignerCapability { account: resource_addr };
        (resource, signer_cap)
    }
```
