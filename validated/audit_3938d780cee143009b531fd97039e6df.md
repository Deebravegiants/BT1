### Title
Same-chain partial fill escrow-release rounds to zero, letting a solver pay output tokens and receive no escrowed input - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntrinsicIntents._fillSameChain` computes the proportional escrow amount to release to a solver on a partial fill using integer division, and never checks whether the result is zero before proceeding with the transfer and state updates. This mirrors the reported bug class (fund loss in `deposit()`/`withdraw()` due to unchecked division-to-zero) but is reachable by any unprivileged solver filling a same-chain intent order.

### Finding Description
In `_fillSameChain`, on a partial fill the escrowed input amount released to the solver is: [1](#0-0) 

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

`fillAmount` is solver-controlled (bounded only by `remaining`), and `order.inputs[i].amount` / `totalRequired` are set by the order creator. When `order.inputs[i].amount * fillAmount < totalRequired`, this division truncates to `0`. Meanwhile, immediately before this computation, the solver has already unconditionally paid real tokens to the beneficiary: [2](#0-1) 

```solidity
uint256 amountFilled = alreadyFilled + fillAmount;
_partialFills[commitment][outputToken] = amountFilled;
uint256 beneficiaryTotal = fillAmount + beneficiaryShare;

if (token == address(0)) {
    ...
    (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
    ...
} else {
    IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
    ...
}
```

There is no check that `escrowedAmount > 0` before proceeding. `_withdraw()` (called afterward) simply skips zero-amount token entries silently rather than reverting: [3](#0-2) 

```solidity
for (uint256 i; i < len; i++) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (amount == 0) continue;
    ...
}
```

So a solver who submits a `fillAmount` small enough relative to `totalRequired`/`order.inputs[i].amount` transfers real output tokens (or ETH) to the beneficiary, `_partialFills` is permanently incremented (consuming part of the order's remaining fillable amount), yet the solver's `escrowedInputs[i].amount` for that leg is `0` — no input tokens are released to them. This is functionally identical to the referenced Sherlock finding: a division that can legitimately equal zero is used to move value without a revert-on-zero guard, causing silent fund loss.

### Impact Explanation
Any solver interacting with `IntentGatewayV2`'s same-chain fill path (`IntrinsicIntents._fillSameChain`) can lose the tokens they send to the beneficiary on a small partial fill while receiving zero input tokens in return, if `order.inputs[i].amount * fillAmount < totalRequired`. This is a real transfer of value (ERC-20 `safeTransferFrom` or native ETH) with no compensating output, i.e. concrete theft/loss of solver funds through a code path with no protective check. Because `_partialFills` is updated regardless, the loss is also not recoverable by simply resubmitting — the "used" fraction of the order's output requirement has already been consumed for that solver's fill. This satisfies the "concrete theft ... of funds" bar via a legitimate on-chain call path (a single `fillOrder` transaction), not requiring any privileged role.

### Likelihood Explanation
This can be triggered unintentionally by any solver whose fill-sizing logic (or an adversarial order crafted with skewed `inputs[i].amount`/`output.assets[i].amount` ratios) produces a small `fillAmount` relative to `totalRequired`. It requires no special permissions — it is directly reachable by calling the public `fillOrder` entrypoint on `IntentGatewayV2` (which internally routes to `_fillSameChain`), making it a normal transaction from an unprivileged solver. Orders with large `totalRequired` and small `inputs[i].amount` (e.g., a low-decimal input token paired against a high-decimal/high-value output) make this scenario easy to hit even without intentional exploitation, and a malicious order-placer could deliberately construct ratios to bait solvers into loss.

### Recommendation
Revert (or reject the fill) when the computed `escrowedAmount` for a partial fill would be zero for any output where `fillAmount > 0`, e.g.:
```solidity
escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
if (escrowedAmount == 0) revert InvalidInput();
```
Alternatively, enforce a minimum fill size (e.g., require `fillAmount * order.inputs[i].amount >= totalRequired`) before allowing a partial fill for that leg, so solvers cannot pay in without receiving a nonzero proportional share.

### Proof of Concept
Given an order leg with `order.inputs[i].amount = 100` and `order.output.assets[i].amount (totalRequired) = 100_000`:
1. A solver calls `fillOrder` with `options.outputs[i].amount = fillAmount = 500` (a legitimate partial fill, well under `totalRequired`).
2. `IntrinsicIntents._fillSameChain` computes `beneficiaryTotal = fillAmount (+ beneficiaryShare, 0 here since no surplus)` and transfers 500 units of the output token from the solver to the beneficiary via `safeTransferFrom` (evm/src/apps/intentsv2/IntrinsicIntents.sol:102).
3. `_partialFills[commitment][outputToken]` is updated to `500` (evm/src/apps/intentsv2/IntrinsicIntents.sol:92), permanently consuming that portion of the order.
4. `escrowedAmount = (100 * 500) / 100_000 = 0` (evm/src/apps/intentsv2/IntrinsicIntents.sol:115) — integer division truncates to zero.
5. `_withdraw` is called with `escrowedInputs[i].amount = 0`, which is silently skipped (evm/src/apps/intentsv2/IntentsBase.sol:459) — the solver receives none of the escrowed input token.
6. Net result: the solver paid 500 units of the output token and received 0 input tokens, a straightforward and irreversible fund loss, with no revert anywhere in the call path.
