### Title
SQL Injection via unparameterized `dot_id` interpolation in `FindTaskResultByRunIDAndTaskName` - (File: core/services/job/orm.go)

### Summary
`orm.FindTaskResultByRunIDAndTaskName` builds a SQL query by directly interpolating the `taskName` parameter into the query string with `fmt.Sprintf`, instead of using a bound parameter, which is the same bug class as the ZoneMinder `minTime`/`maxTime` SQL injection (unvalidated request-derived string spliced directly into a SQL statement).


Only `runID` is passed as a bound parameter (`$1`); `taskName` is spliced directly into the literal string via `%s` and single-quoted, exactly the pattern that causes SQL injection when the value contains a `'` or SQL metacharacters (e.g. `x' OR '1'='1`, `x' UNION SELECT ...`, or a subquery to exfiltrate other tables' data).

### Impact Explanation
If `taskName` reaches this function from any externally-influenced value (e.g., a DAG task's `dot_id`, which is user-supplied when a job spec/pipeline DAG is authored, or any other caller that forwards user text as `taskName`), an attacker could break out of the string literal and execute arbitrary SQL against the `pipeline_task_runs` table and, depending on Postgres permissions, other tables reachable from the same connection — enabling data exfiltration (`UNION SELECT`), or denial of service via expensive/blocking queries. This mirrors the reachable-path/high-severity bug class in the ZoneMinder CVE (unvalidated parameter spliced into SQL).

However, I was unable to locate any concrete, non-test/non-mock production call site for `FindTaskResultByRunIDAndTaskName` in the indexed codebase — grep only surfaced its interface declaration, its generated mock (`core/services/job/mocks/orm.go`), and the function body itself. `dot_id` values in the DAG (task names) are typically set by the DAG author (job spec creator), not an unprivileged end-user of a running job, so the "unprivileged actor" reachability of this specific sink could not be confirmed from what the index exposes.

### Likelihood Explanation
Likelihood cannot be confidently assessed as "reachable from an unprivileged client request" because no HTTP/GraphQL/gateway handler was found in the index that calls this ORM method with attacker-controlled `taskName`. Job creation (which sets `dot_id`s) already requires an authenticated/admin API user in Chainlink, which would place this outside the "unprivileged actor" scope required by the rules unless a lower-privilege path invokes it. Given the tool coverage limits (index size limits may exclude some call sites), this cannot be fully ruled in or out.

### Recommendation
Regardless of current reachability, this is a defect that should be fixed: bind `taskName` as a query parameter instead of interpolating it into the SQL string, e.g.:
```go
stmt := "SELECT * FROM pipeline_task_runs WHERE pipeline_run_id = $1 AND dot_id = $2;"
err := o.ds.SelectContext(ctx, &taskRuns, stmt, runID, taskName)
```
Also audit all other callers/consumers of `taskName`/`dot_id` values to confirm whether any are populated from unprivileged/external input.

### Proof of Concept
Could not be constructed/validated because no reachable unprivileged-caller path to `FindTaskResultByRunIDAndTaskName` was found in the codebase index; a PoC would require identifying that a live caller passes attacker-controlled `taskName` (e.g. `foo' OR '1'='1`) to this function, which I could not confirm with the available tools.
