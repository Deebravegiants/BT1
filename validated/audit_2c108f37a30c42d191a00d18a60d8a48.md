### Title
Webhook `shop` (and `topic`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator.validate` authenticates the *body bytes* only. The `shop-domain` and `topic` headers — which `Registry.process` uses to route and tenant-scope the webhook — are read straight from unauthenticated HTTP headers and are never part of the signed material.

### Finding Description
The identity binding that should hold is:

`hmac_verified(bytes) == bytes_that_determine_tenant(shop)`

but in this gem it is:

`hmac_verified(raw_body) != shop_header_used_for_tenant_attribution`

Concretely: [1](#0-0) 
`to_signable_string` returns only `@raw_body`. [2](#0-1) 
`shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the body or the HMAC. [3](#0-2) 
`Registry.process` validates only `Utils::HmacValidator.validate(request)` (which checks `to_signable_string`, i.e. the body) and then immediately dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the app-registered handler — `shop` and `topic` are passed through unauthenticated. [4](#0-3) 
The validator only ever compares `verifiable_query.to_signable_string` against the received signature — for webhooks that is the raw body only.

Because the webhook HMAC secret (`Context.api_secret_key`, the app's client secret) is a single **app-level** secret shared across every shop that installs the app — not a per-shop secret — any two shops that install the same app share the exact same signing key. This means a `(raw_body, hmac)` pair that is valid for shop A's webhook delivery is *also* a cryptographically valid `(raw_body, hmac)` pair when replayed with the `shop-domain` header changed to shop B, because the signature never covered the shop identity in the first place.

### Impact Explanation
This breaks the tenant-identity binding for webhook processing (cross-tenant access, Critical per the given impact taxonomy). An attacker who can install the app on their own store (a normal, unprivileged action any internet user can perform against a public Shopify app) will legitimately receive Shopify-signed webhooks for their own shop. Because the signature covers only the body — not `shop-domain` or `topic` — the attacker can resend that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` (and/or `topic`) header for a victim shop. `Utils::HmacValidator.validate` will still return `true`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop/topic. Any host application that uses `WebhookMetadata#shop`/`#topic` to scope tenant data (e.g., marking a shop uninstalled, updating shop-specific settings, deleting shop data on `app/uninstalled`, etc., all of which are legitimate common webhook handler patterns) can be tricked into performing that tenant-scoped action against a shop the attacker does not own — a cross-tenant integrity/availability breach reachable without any credentials belonging to the victim.

### Likelihood Explanation
High enough to be practical: any user can install a public/test instance of the target app on their own dev shop (no special privilege required), capture one real webhook delivery (body + `X-Shopify-Hmac-Sha256`), and replay it directly to the app's public webhook URL with a forged `shop-domain`/`topic` header. No secret material or account access belonging to the victim is required.

### Recommendation
Bind the tenant/topic identity into the verified signature material, or otherwise cryptographically tie `shop`/`topic` to the request before trusting them: e.g., include `shop`, `topic`, and `webhook_id` in the signable string (if compatible with Shopify's documented HMAC scheme this may require an additional application-level check), or require the host app to cross-check `shop` against a shop it already has an active session/installation for before acting on webhook content. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must not be trusted for tenant-scoping without independent verification (e.g., confirming the shop has an existing stored session).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (normal, unprivileged install flow).
2. Shopify delivers a legitimate webhook to the app's public endpoint:
   - Body: `{"id": 1}`
   - Headers: `x-shopify-topic: shop/update`, `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
3. Attacker replays this exact request to the same public endpoint, but changes only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com` (leaving body and HMAC untouched).
4. `Utils::HmacValidator.validate` in [5](#0-4)  passes because it only checks the body against the HMAC.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and any tenant-scoped logic in the host app executes against the victim shop's data.
