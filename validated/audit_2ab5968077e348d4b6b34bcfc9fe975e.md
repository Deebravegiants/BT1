### Title
Unvalidated `stealthAddressStructure` in `prooflessDeposit` permanently freezes deposited funds - ([File: contracts/HinkalHelper.sol])

### Summary
`HinkalHelper.performProoflessDepositChecks`, the only validation applied to `Hinkal.prooflessDeposit`, never checks that the caller-supplied `StealthAddressStructure` (`H0x`, `H0y`, `H1x`, `H1y`, `stealthAddress`) is well-formed or that `stealthAddress` is actually the value derivable from `H0/H1` and a recipient's key. [1](#0-0)  By contrast, the ordinary `transact()` path enforces at least `H0x != 0` in `dimensionsCheck`. [2](#0-1)  Because the on-chain commitment inserted into the Merkle tree is a pure function of `amount`, `erc20Address`, `utxo.stealthAddressStructure.stealthAddress`, and `timeStamp`, an unvalidated/incorrect `stealthAddress` still produces a leaf that is happily inserted and irreversibly locks the deposited tokens.

### Finding Description
`prooflessDeposit` lets any EOA pull its own ERC20/ETH into the Hinkal contract and directly create an on-chain UTXO commitment, with no ZK proof involved: [3](#0-2) 

The only guard is `hinkalHelper.performProoflessDepositChecks`, which validates array-length consistency, a cap on entries, non-empty encrypted outputs, and `amounts[i] > 0` — but never touches `stealthAddressStructures[i].H0x/H0y/H1x/H1y` or checks that `stealthAddress` corresponds to those points: [4](#0-3) 

The commitment inserted into the tree is computed purely from the raw `stealthAddress` scalar supplied by the depositor, with no cryptographic binding to `H0x/H0y/H1x/H1y`: [5](#0-4) 

In the legitimate flow, `stealthAddress` (the circuit's `out` value from `StealthAddressCalculator`) must equal `Poseidon(sign, H0Ay, H1Ay, spendingPublicKey[0], spendingPublicKey[1], nullifyingPrivateKey)`, i.e. it is only spendable later by someone who can reconstruct that Poseidon hash from a `nullifyingPrivateKey` matching the `H0/H1` shared secret used at creation time: [6](#0-5) 

Because `prooflessDeposit` never enforces this relationship (nor even that `H0x != 0`), a caller (or a front-end/relayer bug, or funds sent via the `HinkalWrapper.prooflessDeposit` passthrough) can submit a `stealthAddressStructure` whose `stealthAddress` scalar is not tied to any real `H0/H1` key material — e.g. an arbitrary or malformed value. The deposit still succeeds: tokens are transferred into Hinkal, the check `require(balanceAfter - balanceBefore == amount, ...)` in `_handleTransfersFromProoflessDeposit` passes, and a commitment leaf for that bogus `stealthAddress` is permanently inserted into the Merkle tree. [7](#0-6) 

Once inserted, that leaf's value is unrecoverable: `transact()` requires a proof that reconstructs the commitment/nullifier through `StealthAddressCalculator` using a `nullifyingPrivateKey` and `H0Ax/H0Ay` that reproduce the exact `stealthAddress` on-chain — impossible if the deposit-time `stealthAddress` was never derived from a real key pair. There is no recovery/refund mechanism anywhere in the deposit path (no rollback, no admin refund, no retry counter), unlike Atlas's later remediation for the analogous BTC-deposit issue.

### Impact Explanation
This breaks the equality that every value-bearing leaf inserted into the commitment tree must be provably spendable by exactly one key holder. A leaf can be created (and real funds locked behind it) that the tree/circuit combination can never produce a valid spend proof for, permanently freezing user funds with no recovery path — a Critical-severity "permanent freezing of user funds" per the scope's impact classes.

### Likelihood Explanation
This requires no privileged access — any unprivileged EOA calling `prooflessDeposit` (directly or via `HinkalWrapper`) controls the `stealthAddressStructures` argument and can trigger it, whether by an honest mistake in an integrating dApp/relayer that fails to derive `stealthAddress` correctly, or simply because the contract itself never checks the derivation. Given the field is entirely attacker/caller-supplied with essentially zero on-chain validation, this is straightforward to trigger.

### Recommendation
Add on-chain validation in `performProoflessDepositChecks` mirroring `dimensionsCheck`'s intent but stronger: at minimum require `H0x != 0` (and ideally verify `H0`/`H1` lie on the BabyJubjub subgroup, as the circuit's `StealthAddressCalculator` does via `BabyJubjubSubgroupCheck`), and consider requiring the caller to additionally prove knowledge of a `nullifyingPrivateKey` that reproduces the supplied `stealthAddress` from `H0/H1`, or otherwise document/enforce that `prooflessDeposit` callers must derive `stealthAddress` off-chain following the exact circuit formula before submission, with front-end/SDK-level integration tests to guarantee correctness before mainnet loss.

### Proof of Concept
1. Attacker (or a buggy integrator) calls `Hinkal.prooflessDeposit` with a real ERC20 token, a nonzero `amount`, a non-empty `onChainEncryptedOutputs[i]`, and a `stealthAddressStructure` where `H0x = H0y = H1x = H1y = 0` and `stealthAddress` is an arbitrary nonzero value (e.g. `keccak256("test") % p`).
2. `hinkalHelper.performProoflessDepositChecks` passes because it never inspects `H0x`/`H0y`/`H1x`/`H1y`/`stealthAddress` correctness. [4](#0-3) 
3. `_handleTransfersFromProoflessDeposit` pulls `amount` tokens from the attacker into the Hinkal contract, satisfying the balance-equality check. [7](#0-6) 
4. `_createProoflessDepositCommitments` → `createOnchainCommitment` computes `commitment = hash4(amount, erc20Address, stealthAddress, timeStamp)` using the bogus `stealthAddress`, and `insertCommitments` writes it into the Merkle tree as a permanent leaf. [5](#0-4) 
5. No holder of any real `nullifyingPrivateKey`/`spendingPublicKey` pair can ever reconstruct this specific `stealthAddress` value through `StealthAddressCalculator`, since it was never derived from `H0/H1` scalar multiplication and Poseidon hashing. [8](#0-7)  Therefore `transact()` can never produce a valid proof spending this UTXO — the deposited tokens are permanently stuck in the Hinkal contract with no rollback/refund mechanism, unlike the remediated Atlas Bitcoin deposit flow this analog is drawn from.

    function _handleTransfersFromProoflessDeposit(
        TokenWithAmount[] memory uniqueTokens,
        uint256 uniqueCount
    ) private {
        for (uint256 i = 0; i < uniqueCount; i++) {
            address erc20Address = uniqueTokens[i].erc20Address;
            uint256 amount = uniqueTokens[i].amount;

            uint256 balanceBefore = getERC20OrETHBalance(erc20Address);
            if (erc20Address == address(0)) balanceBefore -= msg.value;

            transferERC20TokenFromOrCheckETH(
                erc20Address,
                msg.sender,
                address(this),
                amount
            );

            uint256 balanceAfter = getERC20OrETHBalance(erc20Address);

            require(
                balanceAfter - balanceBefore == amount,
                "proofless deposit balances must be equal"
            );
        }
    }

template StealthAddressCalculator() {
    signal input H0Ax;
    signal input H0Ay;
    signal input spendingPublicKey[2];
    signal input nullifyingPrivateKey;
    signal input nullifyingPrivateKeyBits[250];

    signal output H1Ax;
    signal output H1Ay;
    signal output out;

    component h0SubgroupCheck = BabyJubjubSubgroupCheck();
    h0SubgroupCheck.Ax <== H0Ax;
    h0SubgroupCheck.Ay <== H0Ay;

    signal H1[2];
    H1 <== EscalarMulAny(250)(nullifyingPrivateKeyBits, [H0Ax, H0Ay]);

    component calcStealthAddressCompressed = StealthAddressCompressor();
    calcStealthAddressCompressed.H0Ax <== H0Ax;
    calcStealthAddressCompressed.H0Ay <== H0Ay;

    calcStealthAddressCompressed.H1Ax <== H1[0];
    calcStealthAddressCompressed.H1Ay <== H1[1];

    H1Ax <== H1[0];
    H1Ay <== H1[1];

    component calcRandomizedPublicKey = Poseidon(6);
    calcRandomizedPublicKey.inputs[0] <== calcStealthAddressCompressed.signs;
    calcRandomizedPublicKey.inputs[1] <== H0Ay;
    calcRandomizedPublicKey.inputs[2] <== H1[1];
    calcRandomizedPublicKey.inputs[3] <== spendingPublicKey[0];
    calcRandomizedPublicKey.inputs[4] <== spendingPublicKey[1];
    calcRandomizedPublicKey.inputs[5] <== nullifyingPrivateKey;
    out <== calcRandomizedPublicKey.out;
}
