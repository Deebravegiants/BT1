### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body via `to_signable_string`. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body-HMAC validates and then forwards `request.shop` unchanged to the registered handler as the tenant identifier, without any binding between the signed bytes and the shop field.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` reads the shop straight from an HTTP header, with no relation to the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body and then trusts `request.shop` as the tenant for the handler call: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e., the body only, and never incorporates `shop`: [4](#0-3) 

This is the same bug class as the referenced report: a field (`shop`) is acted on by the consumer (`Registry.process` → handler) but is not part of the bytes verified by the HMAC (`raw_body` only). The equality that should hold — "the shop bound to the verified signature" == "the shop used to identify the tenant for handler processing" — is broken, because the shop is parsed from an attacker-controllable header that sits entirely outside the signed payload.

### Impact Explanation
An attacker who controls a legitimate (even free/dev) Shopify shop installed on the target app can receive real webhooks from Shopify for their own shop, each with a valid HMAC computed over the raw body using the app's shared secret. Because the header carrying the shop domain is not part of the signed bytes, the attacker can capture a `(raw_body, hmac)` pair generated for their own tenant and replay it to the app's webhook endpoint with `shopify-shop-domain` swapped to a victim shop domain. Any HMAC check in `Utils::HmacValidator.validate` still passes because it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata` whose `shop` is the victim's domain. If the host application uses `data.shop` from `WebhookMetadata` to look up sessions, apply data mutations, or trigger tenant-scoped side effects (as is the intended/documented usage), this results in cross-tenant data confusion — one merchant's webhook payload can be attributed to and processed as belonging to another merchant.

### Likelihood Explanation
Exploitation requires the attacker to operate/install the app on their own shop (a normal unprivileged merchant role, not a privileged internal account) so they can observe a valid `(body, hmac)` pair from a real webhook delivery, then re-POST it to the app's public webhook endpoint with a modified shop header. No access token, `api_secret_key`, or TLS interception is needed — this is achievable purely by an internet-reachable, unprivileged actor controlling their own installation. Effectiveness of the resulting cross-tenant confusion depends on whether the consuming app uses the unauthenticated `shop` field for tenant-sensitive decisions, but the gem itself provides no protection or documented warning against this and surfaces the field as if it were trustworthy, matching the "trusted-but-unbound field" pattern from the referenced finding.

### Recommendation
Include the shop domain (and other identifying headers such as topic/api-version if they drive control flow) in the HMAC-signed payload used for verification, or independently verify that the shop header corresponds to a shop for which the app holds/expects an active installation before dispatching to handlers. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop` value so `HmacValidator.validate` binds the header to the same secret-keyed proof as the body, restoring the equality between "verified bytes" and "bytes acted upon."

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures/receives a real webhook (e.g., `orders/create`), obtaining a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared secret.
2. Attacker POSTs that exact `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header: [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only reproduces the HMAC over `request.to_signable_string` (the body) — this passes because the body/hmac pair is genuine.
5. The handler executes with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"` even though the payload was never signed for, nor originated from, that shop: [6](#0-5)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
