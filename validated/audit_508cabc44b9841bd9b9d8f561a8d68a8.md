### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , so `Utils::HmacValidator.validate` only proves the *body bytes* were signed by Shopify's `client_secret` — it proves nothing about the `shop-domain`, `topic`, or `webhook-id` headers, which are read verbatim from unauthenticated HTTP headers [2](#0-1) . `Registry.process` nonetheless treats the request as fully verified after this single HMAC check and forwards `request.shop` directly to the app's webhook handler as the tenant identifier [3](#0-2) .

### Finding Description
The binding that should hold is: `shop header value == shop that produced/authorized the signed body`. Instead, the gem only checks `HMAC(body, client_secret) == received_signature`; the `shop-domain` header is never part of the signed content and is passed through unauthenticated:
- `HmacValidator.validate_signature` computes the HMAC solely from `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns `@raw_body` alone [4](#0-3) [1](#0-0) .
- `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic tie to the body/HMAC [5](#0-4) .
- `Registry.process` gates all further work on `HmacValidator.validate(request)` succeeding, then immediately builds `WebhookMetadata` using the unauthenticated `request.shop` and `request.topic` and dispatches it to the app-supplied handler [3](#0-2) .
- The gem's own documentation instructs developers to trust `data.shop` as "The shop domain of the webhook" coming out of a request that "will verify the request did indeed come from Shopify" — i.e. the gem itself documents `shop` as verified output of `Registry.process` [6](#0-5) [7](#0-6) .

Because the `shop-domain` header is outside the HMAC coverage, any request whose body+HMAC pair is valid for *some* shop can be replayed at the app's public webhook endpoint with an arbitrary `shop-domain` header substituted, and the HMAC check will still pass — `Registry.process` will hand the handler a `WebhookMetadata` claiming the body belongs to the attacker-chosen shop.

### Impact Explanation
This breaks the tenant boundary the host application relies on (`shop` field trusted as the origin of the payload, per the gem's own documented contract). An attacker who can obtain one valid `(raw_body, hmac)` pair — for example by installing the app on their own store and capturing a legitimate webhook delivery to their own publicly reachable endpoint — can resend that exact body/HMAC to the victim app's endpoint with the `shop-domain`/`x-shopify-shop-domain` header changed to a different (victim) shop. The HMAC check still succeeds because it only ever validated the body. The handler then processes attacker-controlled data as though it originated from, and applies it to, the victim tenant, which is cross-tenant data injection/impersonation.

### Likelihood Explanation
The webhook HTTP endpoint is by design a public, unauthenticated endpoint (that is the entire reason HMAC-over-body exists), so no credentials, TLS interception, or privileged access are required — only network reachability to the app's webhook URL and possession of one valid `(body, hmac)` pair, which any real or trial merchant who installs the app can obtain from their own store's webhook traffic. No `api_secret_key` or access token is needed by the attacker.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header bytes in the signed content used for HMAC verification, or otherwise cryptographically bind the shop identity to the verified payload before it is handed to `WebhookMetadata`/handlers, so that `Registry.process` cannot be tricked into attributing a verified body to an attacker-chosen shop.

### Proof of Concept
1. Attacker installs the target app on their own dev/trial shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `x-shopify-hmac-sha256` header `H` that Shopify sent to the app's public webhook URL.
2. Attacker sends a new POST to the same public webhook URL with body `B` unchanged, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and it matches `H`, so validation passes [8](#0-7) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: <attacker's parsed body>, ...)` [9](#0-8) , causing the host application to process attacker-supplied data under the victim shop's tenant context.
