### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates an HMAC over the raw request body only, while the `shop` (tenant) identity used to route and process the webhook is read from an unauthenticated HTTP header that is never part of the signed data. This breaks the intended binding `hmac-verified bytes == shop the webhook is attributed to`.

### Finding Description
`Registry.process` accepts a webhook only if `Utils::HmacValidator.validate(request)` succeeds: [1](#0-0) 

The HMAC validator computes/compares the signature purely from `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `hmac` is read straight from the `hmac-sha256` header — but the `shop` value that is later trusted as the tenant identity is taken from the `shop-domain` header, which is **not** included anywhere in the signed string: [3](#0-2) [4](#0-3) 

After HMAC validation passes, the handler is invoked with `request.shop` used as the tenant identifier for the event, with no further check that this shop matches whatever shop the HMAC was actually computed for: [1](#0-0) 

Because the `api_secret_key`/`client_secret` used to compute the webhook HMAC is a single per-app secret shared across every shop that installs the app (not per-shop), the HMAC of a given body is identical no matter which shop it was generated for. Any party who can obtain one valid `(raw_body, hmac)` pair for the app — e.g., by installing the app on their own store, which is an ordinary unprivileged action open to anyone — can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it never looks at the shop header, and `Registry.process` will hand the forged event to the topic handler tagged with the attacker-chosen `shop`.

This is the same class of defect as the reported `isLeverageEnabled` bug: an operation (processing/attributing a webhook to a tenant) is performed while a critical field (`shop`) bypasses the security check (`HmacValidator.validate`) that is supposed to gate it.

### Impact Explanation
This breaks the equality `shop the HMAC authenticates == shop the handler acts on`, letting one tenant forge webhook events attributed to a different, arbitrary tenant of the same app — a cross-tenant access primitive. Depending on how the host application's webhook handlers use `WebhookMetadata#shop` (e.g. `app/uninstalled` cleanup, `customers/redact`, `orders/*` processing, billing/plan changes), this can trigger destructive or state-changing actions against a victim shop's data using only a body/HMAC pair the attacker legitimately obtained for their own shop. This qualifies as Critical (cross-tenant access) per the specified impact rubric.

### Likelihood Explanation
Likelihood is High: obtaining a valid `(body, hmac)` pair requires nothing more than installing the target app on an attacker-controlled test store (a normal, unprivileged action any internet user can perform), and many webhook topics have small, fixed, or fully predictable bodies (e.g., `"{}"` for several mandatory/system topics), making the captured pair trivially reusable. No access token, `api_secret_key`, or privileged account is needed — only network access to the app's public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is actually authenticated, not just the raw body:
- Include the `shop-domain` (and `topic`) header values in the signable string that is HMAC-verified, mirroring how OAuth's `AuthQuery#to_signable_string` includes `shop` alongside other fields (`lib/shopify_api/auth/oauth/auth_query.rb`), or
- After validating the body HMAC, cross-check the claimed `shop` against an independently trusted source (e.g., the shop associated with the specific webhook subscription/session in the host app's storage) before dispatching to handlers, rather than trusting the header value unconditionally.

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker.myshopify.com`, triggering a real webhook (e.g. `app/uninstalled`) to the app's public webhook endpoint. Attacker captures the raw request:
   - Headers: `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <H>`, `x-shopify-shop-domain: attacker.myshopify.com`
   - Body: `"{}"`
2. Since `H = HMAC-SHA256(app_client_secret, "{}")` depends only on the shared app secret and the body — not the shop — `H` is valid for `"{}"` regardless of shop.
3. Attacker crafts a new POST to the same webhook endpoint with:
   - `x-shopify-topic: app/uninstalled`
   - `x-shopify-hmac-sha256: <H>` (same value)
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - Body: `"{}"`
4. `Utils::HmacValidator.validate` recomputes the HMAC over `"{}"` and compares to `<H>` — it matches, per `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the host app to process an `app/uninstalled` (or other) event for a shop that never sent it.
