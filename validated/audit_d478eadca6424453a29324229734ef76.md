## Title
Server-Side Template Injection (SSTI) via unsanitized workflow-controlled body/header values in `DirectConfidentialHTTPAction.SendRequest` - (File: `core/capabilities/fakes/confidential_http_action.go`)

### Summary
`DirectConfidentialHTTPAction.SendRequest` takes the caller-supplied HTTP request body and header values and parses/executes them directly as Go `text/template` templates with the loaded secrets map as template data, before making the outbound HTTP call. [1](#0-0) 

### Finding Description
The body string (`req.GetBodyString()`) and every header value (`req.GetMultiHeaders()`) are passed straight into `template.New(...).Parse(...)` and then `.Execute(...)` against `templateData`, which is populated from `fh.secretsConfig.SecretsNames` — i.e., the secrets meant to be injected as placeholders (e.g. `{{.API_KEY}}`). [2](#0-1) 
Since the template text itself comes from caller-controlled request fields (`req.GetBodyString()`, header values) rather than from a fixed, developer-authored template string, an unprivileged caller who can shape the HTTP request body/headers passed to this capability can inject arbitrary Go template directives. Go's `text/template` supports control-flow constructs (`{{if}}`, `{{range}}`, `{{with}}`) and, critically, dot-field access into the supplied data map — allowing an attacker to reference and exfiltrate any secret key present in `templateData` (e.g. `{{.AESGCMEncryptionKeyName}}` or any other loaded secret name) regardless of whether that secret was intended to be used in that particular request. This mirrors the OFBiz CVE-2026-31380 pattern: user-influenced input is fed into a server-side expression/template evaluator without restricting which template variables/expressions can be referenced. [3](#0-2) 
The same unrestricted template-parsing-of-attacker-input pattern also exists in the sibling `DirectHTTPAction` fake capability handler. [4](#0-3) 

### Impact Explanation
If reachable from an unprivileged workflow/request path, this allows secret disclosure (any secret loaded into `secretsConfig.SecretsNames`, including the AES-GCM encryption key `AESGCMEncryptionKeyName` used for response encryption) by crafting a body/header value like `{{.san_marino_aes_gcm_encryption_key}}`, which would be rendered into the outbound request body/header and reflected back or observable, defeating the "confidential" guarantees of this capability. [5](#0-4) 

### Likelihood Explanation
Exploitability depends entirely on whether the `fakes` package's `DirectConfidentialHTTPAction`/`DirectHTTPAction` is compiled into and reachable in a production node/gateway binary, versus being confined to local dev/test tooling (`standalone_engine.go` in `cmd/cre/utils`). I could not confirm this reachability before running out of tool calls — the plugin manifest (`plugins/plugins.public.yaml`) points the real `confidential-http` capability at an external module (`chainlink-confidential-compute`), suggesting the in-repo `fakes` implementation may only be a local/dev stand-in, not the production capability binary. [6](#0-5) 

### Recommendation
Do not execute caller-supplied strings as Go templates. If templating of secrets into request bodies/headers is required, use a restrictive placeholder syntax (e.g., simple `${SECRET_NAME}` string replacement against an explicit allow-list of secret names declared by the workflow author) instead of full `text/template` parsing/execution, and ensure this code path cannot be reached by unauthenticated/unprivileged external callers in production builds.

### Proof of Concept
1. Load a secrets file mapping `AESGCMEncryptionKeyName` (`san_marino_aes_gcm_encryption_key`) to a real key via env var, as in `NewDirectConfidentialHTTPAction`. [7](#0-6) 
2. Send a `ConfidentialHTTPRequest` with `Method: "POST"` and `BodyString: "{{.san_marino_aes_gcm_encryption_key}}"`.
3. `SendRequest` parses and executes this as a template against `templateData` (built from all loaded secrets) and sends the rendered body — now containing the raw encryption key — to the target URL. [8](#0-7) 

**Caveat:** I was not able to confirm within the available tool budget whether this `fakes` package is compiled into a production, internet-facing gateway/node binary reachable by unprivileged callers, or whether it is confined to local development/testing tooling only. If it is test/dev-only, per the scan rules this would not qualify as a valid analog.
