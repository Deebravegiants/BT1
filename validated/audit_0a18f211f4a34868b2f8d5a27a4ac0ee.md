### Title
`HttpClient#initialize` sends `X-Shopify-Access-Token` to `session.shop` with no `ShopValidator.sanitize!` call - ([File: lib/shopify_api/clients/http_client.rb])

### Summary
`HttpClient#initialize` builds `@base_uri` directly from `session.shop` (`"https://#{api_host || session.shop}"`) and unconditionally attaches `X-Shopify-Access-Token` to every request built from that URI, with no call to `Utils::ShopValidator.sanitize!` anywhere in this file. `Auth::Session#initialize` also performs zero validation on the `shop:` argument (`@shop = shop`), so nothing in the object's lifecycle constrains it to a `*.myshopify.com`/trusted domain before it reaches `HttpClient`.

### Finding Description
Binding under test: for every outgoing request, `request_host == ShopValidator.sanitize!(session.shop)` must hold before `X-Shopify-Access-Token` is attached. In the actual code: [1](#0-0) 

`api_host` comes only from `Context.api_host` (nil in the standard, non-dev-server configuration), so `@base_uri` is `"https://#{session.shop}"` verbatim, and `@headers["X-Shopify-Access-Token"]` is set right after, tied to that same `@base_uri`. There is no call to `Utils::ShopValidator.sanitize!`, `Utils::ShopValidator.sanitize_shop_domain`, or any regex/domain check on `session.shop` in this method or anywhere else in `http_client.rb`.

Tracing `Auth::Session`, the constructor also performs no validation: [2](#0-1) 

`Utils::ShopValidator.sanitize!` exists in the gem and is used in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, but is never invoked by `Session.new`, `Session.from`, or `HttpClient#initialize`: [3](#0-2) 

I also checked the standard OAuth callback path (`Oauth.validate_auth_callback`), which builds the offline session directly from `auth_query.shop` and passes it straight into `HttpClient.new(session: null_session, ...)`, again with no `ShopValidator` call: [4](#0-3) 

In that flow, `HmacValidator.validate(auth_query)` confirms the callback query was HMAC-signed by an entity holding `api_secret_key` (normally Shopify), which is a real, independent guard against an unprivileged attacker forging `shop` in *that specific* code path. So for the gem's own built-in OAuth flow, this file alone is not sufficient to prove exploitability by an unprivileged attacker — the HMAC check upstream currently constrains `auth_query.shop`.

However, the question's premise is scoped differently: it assumes a `Session` object is obtained through some other path (e.g., a host application's session storage keyed by an attacker-influenced session id, referred to as "the offline_session_id hijack" in the audit context) that yields a `Session` whose `shop` field is attacker-controlled and never re-validated. I did not find and could not verify such a hijack within this gem's own code in this investigation — it is asserted as a precondition external to `http_client.rb`, and its existence/validity in this codebase is not established here. What **is** established and verifiable purely within `lib/shopify_api/clients/http_client.rb` and `lib/shopify_api/auth/session.rb` is that neither performs any sanitization of `shop`, so if such a `Session` is ever handed to `HttpClient`, there is no defense-in-depth in this file to stop the token from being sent to the attacker's host.

### Impact Explanation
If a `Session` with an attacker-chosen `shop` reaches `HttpClient.new`, the merchant's `X-Shopify-Access-Token` (offline or online) is sent verbatim as an HTTP header to `https://#{shop}`, fully exposing the credential to whoever controls that host — Critical severity (access token exfiltration via SSRF), repeatable for every request made through that client instance, and applicable to any tenant whose session object is manipulated this way. The blast radius is bounded by whichever precondition supplies the malicious `Session` to `HttpClient`; within this file itself, there is no mitigating control.

### Likelihood Explanation
Within `http_client.rb` and `session.rb` alone, likelihood of a directly attacker-triggerable exploit is **not established** — the gem's own OAuth callback path is guarded by `HmacValidator.validate`, which requires possession of `api_secret_key` to forge `auth_query.shop`, something the stipulated unprivileged attacker does not have. Exploitability therefore depends entirely on the separate, unverified precondition (a session-store/lookup vulnerability elsewhere) referenced by the question. That prerequisite was not confirmed in this investigation.

### Recommendation
Regardless of upstream guards, add defense-in-depth in `HttpClient#initialize` by calling `Utils::ShopValidator.sanitize!(session.shop, myshopify_domain: Context.custom_shop_domains)` (or equivalent) before using `session.shop` to build `@base_uri`, and/or enforce the same sanitization inside `Auth::Session#initialize`/`shop=` so that no `Session` can ever carry an untrusted host value regardless of how it was constructed.

### Proof of Concept
Not reproducible as a standalone attacker-triggerable exploit using only this gem's code and an unprivileged attacker, because the one concrete path that constructs a `Session` from attacker-influenced input (`Oauth.validate_auth_callback`) is gated by `Utils::HmacValidator.validate`, which requires `api_secret_key` to forge. A minitest such as:

```ruby
session = ShopifyAPI::Auth::Session.new(shop: "evil.attacker.com", access_token: "shpat_x")
client = ShopifyAPI::Clients::HttpClient.new(session: session, base_path: "/admin/api")
assert_equal "https://evil.attacker.com", client.instance_variable_get(:@base_uri)
```
would confirm the *mechanical* lack of validation in this file, but does not by itself demonstrate that an unprivileged remote attacker can cause the gem to construct such a `Session` — that requires the separate, unverified vulnerability referenced in the question's premise ("offline_session_id hijack above"), which is outside what I could confirm to exist in this repository's code during this investigation.
