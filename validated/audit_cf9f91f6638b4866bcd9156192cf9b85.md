Found a concrete SSRF-with-credentials analog: `TokenExchange.exchange_token` in `lib/shopify_api/auth/token_exchange.rb` sends the app's `client_secret` to a host built from `jwt_payload.shop` (the `dest` claim of a Shopify session token) **without ever passing it through `Utils::ShopValidator.sanitize!`**, unlike every other credential-sending method in the gem.

### Title
Unsanitized `dest` claim host used to build the token-exchange request URL, allowing `client_secret` exfiltration to a non-Shopify host - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` both call `Utils::ShopValidator.sanitize!(shop)` before using the shop value to build the request host that receives the app's `client_secret` [1](#0-0) [2](#0-1) . `TokenExchange.exchange_token`, however, takes the shop value directly from `jwt_payload.shop` (derived from the JWT's `dest` claim) and uses it to build the session/host for the outgoing HTTP request without any call to `ShopValidator.sanitize!` [3](#0-2) .

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the raw `dest` claim string with no host/domain restriction: `@dest.gsub("https://", "")` [4](#0-3) . `JwtPayload#initialize` only checks `aud == Context.api_key`; it performs no validation that `dest` is a `*.myshopify.com`/trusted Shopify domain, and no cross-check that `dest` is consistent with `iss` [5](#0-4) .

`TokenExchange.exchange_token` then builds `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` directly from this unvalidated value and passes it to `Clients::HttpClient.new(session: shop_session, ...)` [6](#0-5) . `HttpClient#initialize` builds the outbound request host straight from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"` [7](#0-6) . The request body for this call includes `client_secret: ShopifyAPI::Context.api_secret_key` [8](#0-7) .

The identity binding broken is: *the host that receives the app's `client_secret`* should equal *a validated Shopify/myshopify host*, but here it equals *whatever string is present in the token's `dest` claim*, with no equality check enforced by `ShopValidator`. Every sibling method that builds a credential-bearing request from an externally-influenced `shop` string (`client_credentials`, `refresh_access_token`, `migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!` to enforce this binding [9](#0-8) , confirming that its absence in `exchange_token` is an inconsistency rather than an intentional design choice.

### Impact Explanation
If a `dest` claim value that is not a legitimate Shopify domain reaches `exchange_token` (e.g., because the host application does not itself independently validate the `dest`/shop before calling this library method, or because of any lower-layer JWT confusion), this code path will make an outbound HTTPS POST containing the app's `client_id` and `client_secret` to an attacker-influenced host. This is a Critical-class primitive under the stated impact rubric (SSRF carrying the app's credentials to an arbitrary host), since it directly exfiltrates the `client_secret` — the same secret protected everywhere else in the gem by `ShopValidator.sanitize!`.

### Likelihood Explanation
Exploitability depends entirely on whether `dest` can ever be attacker-influenced in practice — JWTs presented to `exchange_token` are meant to be Shopify-issued and signed with `Context.api_secret_key`, and `JwtPayload` does verify the HS256 signature and `aud` [10](#0-9) . I could not find, within the in-scope library, any additional restriction on the `dest` claim's contents beyond signature/audience checks, and no cross-check against `iss`. Whether Shopify's own token-issuance guarantees `dest` is always a safe host is outside this gem's code and could not be verified from the indexed files. Given the library's own defense-in-depth pattern (sanitizing shop everywhere else), the missing `sanitize!` call here is a real gap, but likelihood of a fully attacker-controlled token reaching this code (i.e., bypassing Shopify's token issuance) is uncertain and could not be confirmed purely from this repository's code.

### Recommendation
Call `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent) on `jwt_payload.shop` in `TokenExchange.exchange_token` before constructing `shop_session`/`HttpClient`, matching the pattern already used in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
Not independently reproducible from this gem alone: constructing a valid JWT requires `Context.api_secret_key`, which an external attacker does not possess. This finding documents a code-level inconsistency (missing `ShopValidator.sanitize!` call on the token-exchange path) rather than a demonstrated end-to-end exploit; end-to-end exploitability would require confirming, outside this repository, that Shopify (or any intermediary) can ever cause a `dest` claim value that is not a trusted Shopify host to reach `exchange_token`.
