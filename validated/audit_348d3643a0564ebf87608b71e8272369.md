### Title
Reserve-rounding drift in `Router._computeBuy`/`_computeSell` can underflow-revert, permanently DoS-ing a curve's buy/sell path - (File: `packages/contracts/src/Router.sol`, `packages/contracts/src/Pair.sol`)

### Summary
The Sherlock report's root cause is a state accumulator (`totalContractsSold`) that is allowed to drift past a hard cap (`auction.totalContracts`) without a bounding check before a later subtraction runs, causing an unconditional revert that DoSes withdrawals. Alt.fun's `Pair`/`Router` AMM has the same shape of bug: `Pair.swap` enforces the K-invariant with a `+1` slack (`(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k`) rather than an exact product check, and `Router._computeBuy`/`_computeSell` derive outputs with floor division against the immutable `k`. This combination lets the *actual* stored `(tokenReserve, assetReserve)` product legally drift below `k`, and, through an alternating buy/sell sequence, this drift can flip sign relative to what the next `_computeBuy` call assumes, producing a bare Solidity subtraction that underflows and reverts.

### Finding Description
`Pair.mint` fixes `k = tokenReserve * assetReserve` once, at launch, and never updates it [1](#0-0) . Every subsequent `swap` only checks the loosened invariant `(newTokenReserve + 1) * (newAssetReserve + 1) >= k`, not `newTokenReserve * newAssetReserve >= k` [2](#0-1) .

`Router._computeBuy` computes `tokensOut = reserveToken - (k / newReserveAsset)` using floor division against the *original* immutable `k`, not the pair's live product [3](#0-2) . Symmetrically, `_computeSell` computes `assetOut = reserveAsset - (k / newReserveToken)` [4](#0-3) .

Each buy leaves the pair in a state where `reserveToken == floor(k / reserveAsset)` exactly (by construction of the formula), and each sell leaves it in a state where `reserveAsset == floor(k / reserveToken)` exactly. Because floor division is not invertible, chaining a buy then a sell (or vice versa) — i.e. `floor(k / floor(k / n))` — can round back up above the original value `n`. Concretely, after a sell sets `reserveAsset = floor(k / reserveToken)`, it is provable that `floor(k / reserveAsset) >= reserveToken`, with the inequality often being *strict* (`> reserveToken`) whenever the floor step lost more than a negligible fraction — which happens routinely when `reserveToken` is large relative to `reserveAsset` (i.e., late in the curve, near the 750M-token exhaustion point that the protocol's own overflow-cap logic already treats as a hazard zone [5](#0-4) ).

Once that strict inequality exists, the very next buy's `tokensOut = reserveToken - (k / newReserveAsset)` computes `k / newReserveAsset <= k / reserveAsset` (monotonic decrease) but this can still be `> reserveToken` if the added `amountIn` is small enough not to erase the drift — causing a bare Solidity `uint256` subtraction underflow and an unconditional revert of the entire `Bonding.buy` → `Router.buy` call, for any caller, with no recovery path other than a sufficiently large buy that outpaces the drift (which itself is unbounded from a caller's perspective and worsens near curve exhaustion).

### Impact Explanation

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
