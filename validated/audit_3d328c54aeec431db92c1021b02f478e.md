This confirms the design pattern is fully client-controlled: `MessageID` is a free-form string chosen entirely by the caller (`*messageID := flag.String("id", "12345", ...)` in `core/scripts/gateway/web_api_trigger/invoke_trigger.go`, and hardcoded test values like `"12345"` in `handler_test.go`), and `ProcessRequest` in `core/services/gateway/gateway.go` only checks length (`len(jsonRequest.ID) > 200`) with no uniqueness or entropy requirement.

Audit Report

## Title
Client-supplied `MessageID` used as sole key for `savedCallbacks` allows cross-caller response hijacking in gateway capabilities handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`HandleLegacyUserMessage` stores each caller's response callback in `h.savedCallbacks` keyed only by the attacker-controllable `msg.Body.MessageID`, with no binding to the caller's signed identity (`msg.Body.Sender`) and no collision/uniqueness check. `handleWebAPITriggerMessage` later looks up and delivers a DON node's response purely by this same `MessageID`, so a second caller who submits a request using the same `MessageID` while the first is still in flight will overwrite the map entry and receive the first caller's response instead.

## Finding Description
In `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` does:
```go
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
```
(lines 411-414) — the key is `msg.Body.MessageID` alone, never combined with `msg.Body.Sender` or any other caller-bound value. `msg.Validate()` in `core/services/gateway/api/message.go` (lines 54-88) only checks length/format of `MessageID` and derives `Sender` from the signature, but the signature only proves who authored *that specific message* — it does nothing to prevent an unrelated party from independently choosing the same `MessageID` string for their own signed message. `Message.Sign`/`ExtractSigner` bind the signature to the full body including `MessageID`, but two different signers can each produce a validly-signed message with `MessageID = "X"`.

When a DON node responds, `handleWebAPITriggerMessage` (lines 148-162) does:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageID]
delete(h.savedCallbacks, msg.Body.MessageID)
...
return savedCb.SendResponse(...)
```
This routes the response to whichever `savedCallback` is currently registered under that ID — the identity of the original requester is never re-checked against the response recipient.

Confirmed from the codebase that `MessageID` is fully attacker-chosen, free-form, with no server-side generation or entropy requirement: the reference client (`core/scripts/gateway/web_api_trigger/invoke_trigger.go`, line 56/100) takes it as a CLI flag `--id` defaulting to the literal `"12345"`, and `core/services/gateway/gateway.go`'s `ProcessRequest` (lines 220-265) only enforces `len(jsonRequest.ID) > 200` as its sole validation — no uniqueness check across concurrent in-flight requests, no per-sender scoping. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

## Impact Explanation
An unprivileged external caller of the gateway's legacy user-facing endpoint (`gateway.ProcessRequest` → `handler.HandleLegacyUserMessage`) who reuses a `MessageID` currently in flight from a different, unrelated caller will have their request overwrite the earlier registration in `h.savedCallbacks`. When the DON subsequently responds to the *original* (victim) request, the raw response is delivered to the attacker's callback via `codec.EncodeLegacyResponse(msg)`, leaking the victim's trigger response content — a concrete cross-user response corruption / impersonation scenario, which is an in-scope Chainlink bounty impact category.

## Likelihood Explanation
This is exploitable by any unprivileged actor able to send signed messages to the gateway's legacy `web_api_trigger` endpoint (this only requires an ECDSA keypair, not any elevated role — signature validity is per-message, not tied to any allowlist enforced in this handler, per the `// TODO: apply allowlist and rate-limiting here` comment at line 384). The attack window is bounded by `defaultCallbackMaxAgeSec` (120 seconds, configurable), during which an attacker can send a colliding request. Because `MessageID` has no server-enforced uniqueness or randomness requirement — confirmed by the reference CLI tool defaulting to a static literal ID and only a max-length check being enforced gateway-side — an attacker who can predict, observe, or brute-force victim IDs (e.g., low-entropy/sequential/shared IDs commonly used by simple clients or scripts) can realistically win the race within the 120-second window. This is a genuine architectural weakness in correlation-ID handling, not a hypothetical one.

## Recommendation
- Scope `savedCallbacks` keys by combining `MessageID` with the authenticated `msg.Body.Sender` (or another server-bound session/connection identifier), so collisions across distinct senders cannot occur.
- Reject (rather than silently overwrite) a new registration when an unexpired entry already exists for the same key.
- When delivering a node response in `handleWebAPITriggerMessage`, verify that the responding flow corresponds to the same sender who originally submitted the request, not solely the `MessageID`.
- Consider generating the correlation ID server-side, never trusting a client-supplied value for callback routing.

## Proof of Concept
1. Victim signs and sends a `web_api_trigger` request with `MessageID = "X"` via `HandleLegacyUserMessage`; this stores `h.savedCallbacks["X"] = victimCallback` (line 412).
2. Before any DON node responds, attacker (a different keypair, no special privilege) signs and sends their own `web_api_trigger` request also using `MessageID = "X"`; this overwrites `h.savedCallbacks["X"] = attackerCallback`.
3. A DON node responds to the victim's original request; `HandleNodeMessage` → `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]`, finds `attackerCallback`, deletes the entry, and calls `attackerCallback.SendResponse(...)` with the victim's response payload — delivering it to the attacker's HTTP connection instead of the victim's.
4. This can be implemented as a Go unit test on `handler_test.go`'s existing `setupHandler` harness: call `HandleLegacyUserMessage` twice with different signers but identical `MessageID`, then call `HandleNodeMessage` once, and assert that the *second* caller's callback (not the first's) receives the response.

		return newError(jsonRequest.ID, api.UserMessageParseError, err.Error())
	}

		// Arbitrary limit to prevent abuse

	}

	var h handlers.Handler
	var handlerKey string
	if msg == nil || msg.Body.DonID == "" {

		} else if donID, ok := g.serviceNameToDonID[serviceName]; ok {

				h = handler
				handlerKey = donID
			}
		}
