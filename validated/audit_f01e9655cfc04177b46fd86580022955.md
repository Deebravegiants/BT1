### Title
Zero-token (`tokenNumber = 0`, "Min0") proof path lets `EmporiumUpgradeable.runAction` execute unrestricted `op.endpoint.call` from Emporium with zero balance accounting, draining any ERC20/ETH the contract holds - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`Hinkal.transact` and `EmporiumUpgradeable.runAction` both compute `balancesBefore`/`balancesAfter` only over `circomData.erc20TokenAddresses`, and both loops that enforce "balance change == accounted change" iterate over that same array. A dedicated zero-token circuit/verifier pair (`mainEVMCircuitMin0v4.sol` / `VerifierEVMMin0v4.sol`) exists and is registered, allowing `dimensions.tokenNumber = 0` and an empty `erc20TokenAddresses` array to produce a valid proof with no per-token constraints at all. With that empty array, every balance/slippage/accounting check degenerates to a no-op, while the `EmporiumStack.ops` executed inside `runAction` still perform arbitrary `op.endpoint.call{value: op.value}(op.callData)` **from Emporium itself**, letting the attacker directly call `transfer()`/ETH-send on any token Emporium happens to hold.

### Finding Description
The broken equality is: *"set of assets `EmporiumUpgradeable.runAction` can move via `op.endpoint.call`"* (everything the EVM allows, since `endpoint`/`callData` are attacker-chosen and unrestricted, per [1](#0-0) ) *!=* *"set of assets accounted for in `balancesBefore`/`balancesAfter`"* (nothing, because `dimensions.tokenNumber = 0` forces `circomData.erc20TokenAddresses` to length 0, per [2](#0-1)  and [3](#0-2) ).

Path traced:
- `dimensionsCheck` only requires `erc20TokenAddresses.length == dimensions.tokenNumber` and all sibling arrays to match; `tokenNumber = 0` is accepted with no minimum enforced [4](#0-3) .
- A verifier/circuit pair specifically for the zero-token case exists and is presumably registered like all other size variants: `contracts/verifiers/VerifierEVMMin0v4.sol` and `contracts/verifiers/mainEVMCircuitMin0v4.sol`. For `tokenCount = 0`, `MainEVMCircuit`'s entire per-token loop (nullifier checks, Merkle-root checks, commitment checks) never executes [5](#0-4) , so the proof only needs a self-consistent EdDSA signature/stealth-address computation that any attacker can generate off-chain with a fresh key pair - no real UTXO ownership or deposit is required.
- `rootHashHinkal`/`rootHashHinkalIndex` just need to reference any existing (public) root; nothing constrains it further when `tokenCount=0`.
- In `Hinkal.transact`, `oldBalances`/`newBalances` are computed via `getBalancesForArray(circomData.erc20TokenAddresses)`, an empty array, and the reconciliation loop (`balanceDif` check, `slippageValues` check, `amountChanges` equality) iterates `circomData.erc20TokenAddresses.length` times, i.e., zero times [6](#0-5) .
- `_externalTransact` calls `EmporiumUpgradeable.runAction`, which decodes `EmporiumStack` (containing `ops: EmporiumOperation[]`) from `externalActionData.externalActionMetadata` [7](#0-6) . `verifyWallet` is bypassed entirely if `stack.signerAddress == address(0)` [8](#0-7) , so no signature is even needed for the stateless op path.
- Each `op` is executed as `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium`, with no allowlist on `op.endpoint` beyond blocking the `callHinkalWallet`/`doSendToRelay` selectors [9](#0-8) . This means the attacker can set `endpoint = <any ERC20 Emporium holds>` and `callData = transfer(attacker, amount)`, which succeeds because Emporium is the caller and holds the balance.
- Because `circomData.erc20TokenAddresses` is empty, the post-op reconciliation loop in `runAction` (balance-change vs `deltaAmountChanges` vs UTXO creation) never runs for the drained token [10](#0-9) , and back in `Hinkal.transact` the same is true. The transaction completes successfully with `insertNullifiers`/`insertCommitments` operating on empty arrays - no on-chain protocol state records any of this.

None of the listed guards catch this: `performHinkalChecks`'s `dimensionsCheck`/`checkOnchainCreation` only validate internal array-length consistency, not that `tokenNumber > 0`; `verifyProof` succeeds because a legitimate zero-token verifier is registered and the circuit for `tokenCount=0` imposes no token-related constraints; `rootHashExists` only requires *a* valid historical root, unrelated to the drained token; the balance/slippage `require`s are vacuous over an empty array; `verifyWallet`'s signature check is optional (`signerAddress == 0`).

### Impact Explanation
This allows an unprivileged attacker to steal any ERC20 token balance or ETH physically held by the `Emporium` contract - which backs the shielded UTXO pool for potentially many other users' funds routed through Emporium-based external actions - by crafting a zero-token `transact()` call whose Emporium ops directly call `transfer()`/send ETH out of Emporium to the attacker. This is direct theft of protocol/shielded funds with zero on-chain accounting, matching the Critical severity bar ("direct theft of shielded or in-flight user funds"). It is fully repeatable: each successful call can be re-run to drain any newly accrued balance, and the attack cost is limited to generating a trivial zero-token proof, which requires no deposit and no privileged role.

### Likelihood Explanation
Preconditions are minimal and attacker-controllable: (1) a Min0 verifier/circuit configuration exists in the repo and is the intended mechanism for zero-token external actions, implying it is registered in production the same way as other size variants; (2) the attacker needs only a self-generated EdDSA key pair (no deposit, no existing UTXO) and any currently valid Merkle root (public data) to build a valid proof for `tokenCount=0`; (3) Emporium must hold some non-zero balance of a token/ETH (which happens naturally as part of normal protocol operation, e.g., residual balances backing other users' external-action flows, or via `receive()`/plain transfers). No admin, relay, or victim cooperation is required. This is a low-cost, self-serve, and repeatable exploit.

### Recommendation
- Reject `dimensions.tokenNumber == 0` for any external action that can move value (specifically actions like `EmporiumUpgradeable` that perform arbitrary `.call`s), or require `circomData.erc20TokenAddresses.length > 0` whenever `externalActionData.externalActionId != 0`.
- In `EmporiumUpgradeable.runAction`, independently track and reconcile the balance of every distinct `op.endpoint` (or any token actually touched during op execution) against `balancesBefore`/`balancesAfter`, not just the tokens declared in `circomData.erc20TokenAddresses`.
- Alternatively, restrict `op.endpoint` to an explicit allowlist of external protocols (never Emporium's own held ERC20 contracts, or any token that Hinkal treats as pooled backing) rather than allowing arbitrary addresses/calldata in the stateless path.

### Proof of Concept
Foundry test plan:
1. Deploy Hinkal + `EmporiumUpgradeable` with a registered `VerifierEVMMin0v4` for `dimensions = {0,0,0}` and `externalActionId` mapped to Emporium.
2. Have a benign user deposit USDC through a normal Hinkal flow such that Emporium ends up holding a USDC balance (e.g., through any legitimate external-action flow that leaves Emporium temporarily holding tokens, or simulate residual balance by direct transfer for test setup).
3. As attacker (fresh EOA, no Hinkal deposit), generate a Min0 (`tokenCount=0`) proof locally using a self-generated EdDSA key and any existing root hash from the Merkle tree.
4. Build `CircomData` with `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, `externalActionData.externalActionId` pointing to Emporium, and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{endpoint: USDC, invokeWallet: false, value: 0, callData: transfer(attacker, EmporiumUSDCBalance)}`.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from the attacker EOA.
6. Assert: call succeeds; `USDC.balanceOf(Emporium)` before != after (drained to 0 or reduced by the transferred amount); `USDC.balanceOf(attacker)` increased by the same amount; and no nullifier/commitment was inserted for this transaction, i.e., total recorded UTXO value backed by USDC did not change even though Emporium's physical USDC balance dropped - demonstrating the equality break between "assets moved" and "assets accounted."
