### Title
Predispatch sweep in `IntentGatewayV2.placeOrder` credits an order's escrow from the CallDispatcher's raw `balanceOf`, letting an attacker fund their escrow with residue left by unrelated orders - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`placeOrder`'s predispatch flow measures how much of an input token to escrow by reading the **total current balance** of the shared `CallDispatcher` contract, not the amount actually produced by the caller's own predispatch call. Because the `CallDispatcher` (`_params.dispatcher`) is a single contract reused across every `placeOrder` call to the gateway, any token that is left behind in it by one transaction (e.g. a swap byproduct not listed among that order's `inputs`) is picked up wholesale by whichever *later, unrelated* order happens to declare that same token as an input — exactly the "shared pot + `balanceOf()`" commingling pattern described in the reference report (`SdtBlackHole.pullSdStakingBribes` using `bribeToken.balanceOf(address(this))`).

### Finding Description
In `placeOrder`, when `order.predispatch.call` and `order.predispatch.assets` are set, the gateway:
1. Sends the caller's predispatch assets to the shared `dispatcher` and executes `order.predispatch.call` [1](#0-0) .
2. For each declared input token, reads `IERC20(token).balanceOf(dispatcher)` — the dispatcher's **entire** balance, not the delta produced by this call — checks it against `requiredAmount`, and builds a sweep call that transfers the *whole* balance back to the gateway [2](#0-1) .
3. Measures `received` as the gateway's balance delta from before/after the sweep and credits the escrow: if `received <= order.inputs[i].amount`, the order is escrowed for the requested amount; any excess is treated merely as `DustCollected` [3](#0-2) .

The `dispatcher` is a single, gateway-wide `CallDispatcher` instance (config parameter `_params.dispatcher`), used by *every* `placeOrder` call and also by `_execute`'s postdispatch sweep in `IntentsBase.sol` [4](#0-3) . `CallDispatcher.dispatch` executes arbitrary attacker-supplied calls with no state isolation between orders [5](#0-4) .

Because step 2 uses the dispatcher's raw `balanceOf` rather than tracking the amount that *this specific* predispatch call actually produced, any token balance stranded in the dispatcher from an earlier transaction (a partially-converted intermediate token from a multi-hop swap, unspent native token, or any token not listed in that earlier order's `inputs` and therefore never swept back) persists in the shared contract. A subsequent, completely unrelated `placeOrder` call that lists that same token as an input will have it silently absorbed into its own escrow via the `balance >= requiredAmount` check — with essentially no real value contributed by that caller for the amount already present. This mirrors the report's root cause: an unprivileged actor uses a shared, `balanceOf`-keyed pool to appropriate value that was never designated for them, because the contract has no notion of "whose" balance is currently sitting there.

### Impact Explanation
An attacker can construct a `placeOrder` predispatch call that is a near-no-op (minimal or zero real value transferred, just enough to satisfy `order.predispatch.call.length > 0`), while declaring `order.inputs[i].amount` equal to (or less than) whatever balance is currently stranded in the dispatcher for that token. The sweep logic will pass the `balance >= requiredAmount` check and credit the attacker's order with a fully-funded escrow entry for a token they did not actually supply. The attacker can subsequently cancel the order (source or destination-chain cancel path) to redeem the escrowed tokens for cash, or have a colluding/self solver fill the order and collect the equivalent output — directly converting stranded protocol-owned residue (which should ultimately be recoverable only as governance-swept dust) into personal profit. This is a direct theft of funds vector reachable by any unprivileged address that can call `placeOrder`.

### Likelihood Explanation
Exploitability depends on the dispatcher actually holding a stray, unswept balance of some ERC-20/native token at the time of the attack. This can arise naturally from routine predispatch swaps whose calldata produces an intermediate/byproduct token not listed among that order's own `inputs` (common with multi-hop router calldata or approximate slippage handling), or can be manufactured deliberately by the attacker across two of their own transactions — first seeding the dispatcher with a token not declared as that order's input (so it is never swept), then harvesting it in a second `placeOrder` call that declares it as an input. Because the `dispatcher` is a single long-lived, gateway-wide contract with unrestricted arbitrary-call execution, an attacker fully controls both the seeding and harvesting steps, making the attack self-triggerable without needing another party's mistake.

### Recommendation
Do not key the sweep on the dispatcher's absolute `balanceOf`. Instead, snapshot the dispatcher's balance for each relevant token immediately before executing `order.predispatch.call`, and only sweep/credit the **delta** produced by that specific dispatch (i.e., `balanceOf(dispatcher)_after - balanceOf(dispatcher)_before`), reverting if the delta is insufficient. Any balance already resident in the dispatcher before the call should never be attributable to the current order — it should instead be swept separately by a permissioned "collect dust" path (e.g., only callable by governance/treasury), analogous to how the reference report recommends giving `SdtBlackHole` explicit per-recipient accounting instead of relying on `balanceOf`.

### Proof of Concept
1. Attacker A calls `placeOrder` with `order.inputs = [tokenX: 0]`... (not directly, since `amount == 0` reverts) — instead Attacker A crafts `order.predispatch.call` whose calldata performs a multi-hop swap (e.g. ETH → tokenX → tokenY) but only lists `tokenY` in `order.inputs`; a rounding/slippage remainder of `tokenX` (say 1,000 units) is left unswept in the shared `dispatcher` because `tokenX` is not part of this order's `inputs` loop at [6](#0-5) .
2. In a later transaction, Attacker B (can be the same address) calls `placeOrder` with `order.inputs = [tokenX: 1000]` and a trivial predispatch call (e.g., a call to the dispatcher itself with empty calldata, valid since `CallDispatcher` has a `receive()`), supplying only dust-level real predispatch assets.
3. At [7](#0-6) , `balance = IERC20(tokenX).balanceOf(dispatcher)` reads the stranded 1,000 units left by step 1 and passes `balance >= requiredAmount`.
4. The sweep transfers the full 1,000 `tokenX` to the gateway; `received == order.inputs[i].amount` so the escrow is credited with the full 1,000 `tokenX` at [8](#0-7)  even though Attacker B contributed no real `tokenX`.
5. Attacker B cancels the order (or has it filled) to redeem the escrowed `tokenX`, realizing funds that were never theirs to deposit.
