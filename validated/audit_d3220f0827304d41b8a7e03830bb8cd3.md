### Title
On-orb fraud detection is a permanent stub that always returns `false`, bypassing the local fraud/liveness gate before signup submission - ([File: src/plans/mod.rs])

### Summary
`MasterPlan::detect_fraud` is the on-device gate that is supposed to classify a completed biometric pipeline as fraudulent before the signup is tagged and submitted to the backend. In this repository the function body has been reduced to an explicit stub that unconditionally returns `Ok(false)`, so no capture can ever be locally flagged as fraud regardless of the pipeline contents. This mirrors the reported analog bug class: a security-relevant function whose implementation deviates from its intended contract (an interface/function that should perform real checks instead is an empty/stub body that always yields the "safe" default), leading to unexpected behavior for any code path that depends on its result.

### Finding Description
`detect_fraud` is declared as the authoritative check used to decide whether a signup should be reason-tagged `SignupReason::Fraud`: [1](#0-0) 

The function takes the completed biometric `pipeline` as input — exactly the data that would need to be inspected to make a real fraud/liveness determination — but the body contains only the comment `// FOSS: WE HAVE DELETED ALL FRAUD CHECKS` and immediately returns `Ok(false)`, without evaluating `_pipeline` at all.

This function is not dead code. It is wired directly into the main signup pipeline: [2](#0-1) 

Here `fraud_detected` is computed from `self.detect_fraud(...)` and used to set `signup_reason` to `SignupReason::Fraud` versus `SignupReason::Normal`. Because `detect_fraud` always returns `false`, `fraud_detected` is always `false`, and `signup_reason` can never become `SignupReason::Fraud` through this on-orb path — the branch is unreachable dead code from a security-behavior standpoint.

This is structurally the same defect class described in the external report: a function meant to enforce a security property (`lookup`/`Certifier` checks in the Solidity report) is replaced by an empty stub that always returns the value corresponding to "nothing wrong," silently defeating any downstream logic that trusts its result (`Bob's smart contract... since lookup always returns 0`).

### Impact Explanation
Any downstream logic, telemetry, or backend heuristics that rely on the orb tagging a signup as `SignupReason::Fraud` based on local pipeline analysis will never receive that signal from this code path, since the tag is hardcoded to `Normal`/`Failure` only. If any local, orb-side fraud/liveness enforcement was intended to gate or annotate signups prior to backend submission, it is completely disabled — allowing any biometric capture, regardless of fraud characteristics detectable from the pipeline, to be submitted and processed as `SignupReason::Normal` (or `SignupReason::Failure` only when the pipeline itself is `None`). This is a concrete fraud/liveness-enforcement bypass in the reachable, production signup flow (`src/plans/mod.rs` `do_signup`), not a test-only or hardware-only artifact.

### Likelihood Explanation
This is not a conditionally triggered bug — it is unconditional. Every signup that completes the biometric pipeline invokes `detect_fraud`, and the function always returns `false` unless `skip_fraud_checks` also short-circuits it earlier via `!self.skip_fraud_checks() && self.detect_fraud(...)`. There is no code path in this repository that can make `detect_fraud` return `true`. This is deterministic and reachable on every successful pipeline run, which is the normal/common execution path for the orb software.

### Recommendation
- Either remove the `detect_fraud` call and the `SignupReason::Fraud` branch entirely if fraud detection is intentionally not part of this open-source build (to avoid dead/misleading code implying a security control exists when it does not), or
- Restore/implement real fraud-check logic in `detect_fraud` that actually inspects `pipeline` data, rather than leaving a stub that always returns `false`.
- Add a code comment/doc and, ideally, a compile-time or config-time visible indicator (e.g., a `cfg` feature flag) making explicit that on-orb fraud detection is disabled in this build, so integrators/operators are not misled into thinking a local fraud gate is active.
- Audit other similarly "FOSS-stripped" stub functions for the same silent no-op pattern, since they are indistinguishable from a real implementation at the call site.

### Proof of Concept
1. Start a signup and let it proceed through `do_signup` in `src/plans/mod.rs` up through `biometric_pipeline` completion.
2. Observe that `self.detect_fraud(orb, debug_report, pipeline.as_ref())` is called with a valid `Some(pipeline)`.
3. Regardless of the pipeline’s content (e.g., patterns that would represent replay, spoofing, or other fraud indicators detectable from pipeline data), `detect_fraud` returns `Ok(false)` unconditionally (`src/plans/mod.rs:1397-1406`), so `fraud_detected` is always `false`.
4. `signup_reason` is consequently computed as `SignupReason::Normal` (assuming `pipeline.is_some()`), never `SignupReason::Fraud`, confirming the on-device fraud tag can never be emitted (`src/plans/mod.rs:565-571`).
