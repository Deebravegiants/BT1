### Title
Webhook shop/topic identity is not covered by the HMAC, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the value that is HMAC-verified from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook to a tenant are taken from unauthenticated HTTP headers that are never included in the signed bytes. Any party who can obtain one validly-signed webhook for the shared app secret (e.g., a merchant who has installed the app themselves) can replay that exact body/HMAC pair while swapping the `x-shopify-shop-domain` header to a victim shop, and the signature check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read straight from HTTP headers that are not part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e., the body) against the HMAC, so it never binds the `shop` header to the signature: [3](#0-2) 

`Registry.process` performs this HMAC check and then trusts `request.shop` unconditionally when building the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop_bound_by_hmac == shop_used_by_handler`

In this code, the left side does not exist — the HMAC binds nothing but the raw body — so the equality trivially fails: `shop_used_by_handler` (a raw, attacker-controllable header) is accepted as authoritative tenant identity with no cryptographic tie to the signature that "authenticates" the request.

Because Shopify apps use one shared `api_secret_key` for every shop that installs the app (not a per-shop secret), any merchant who installs the app can trigger a real event (e.g. `orders/create`) in their own store to obtain one genuinely, validly HMAC-signed webhook body+signature pair from Shopify. That attacker-merchant fully controls the JSON body content of that webhook (order fields, notes, customer data, etc., depending on topic) and can then replay the identical body+HMAC directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) for a victim shop that also installed the same app. `HmacValidator.validate` still succeeds because it never examines the header, and `Registry.process` forwards `shop: request.shop` (now the victim's domain) to the app's handler as if Shopify itself had reported that event for the victim shop.

### Impact Explanation
This breaks the tenant/authentication boundary between two independent merchants installed on the same app: an unprivileged merchant-attacker can inject attacker-controlled, falsely-attributed webhook payloads into another shop's tenant context without possessing that shop's access token, session, or the app's `client_secret`. Downstream host applications (which rely on `WebhookMetadata#shop` from this gem as the trusted tenant key, per the gem's documented webhook processing contract) will store or act on forged data as if it originated from the victim shop — this is cross-tenant access/data corruption, matching the Critical impact category.

### Likelihood Explanation
Exploitation only requires becoming a legitimate installer of the target app (a normal, low-privilege action any internet user can take by installing a public Shopify app) and triggering one event in their own store to harvest a valid signed webhook, then replaying it with a modified header to the app's public webhook endpoint. No access token, refresh token, or `client_secret` needs to be stolen; the shared `api_secret_key` is never exposed to the attacker, it is exploited only because it fails to bind the header-derived shop identity.

### Recommendation
Include the tenant-identifying fields (at minimum `shop`, and ideally `topic`/`webhook_id`) in the bytes that are HMAC-verified, or independently verify that the `x-shopify-shop-domain` header corresponds to a shop session/installation record already known to the host app before trusting it, e.g. mirror Shopify's actual webhook contract by treating `shop` as untrusted metadata and requiring the receiving application to cross-check it against installation state, or provide a helper that combines HMAC validation with shop authorization instead of leaving `Registry.process` to unconditionally trust `request.shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers an `orders/create` event in their store; Shopify POSTs a webhook to the app's endpoint with a body the attacker fully controls and a valid `x-shopify-hmac-sha256` computed over that body with the shared `api_secret_key`.
3. Attacker captures `raw_body` and the `x-shopify-hmac-sha256` value.
4. Attacker sends a new POST directly to the app's public webhook endpoint with the identical `raw_body`/`hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (only body bytes are checked): [5](#0-4) 
6. `Registry.process` invokes the app handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, as shown in the handler dispatch: [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
