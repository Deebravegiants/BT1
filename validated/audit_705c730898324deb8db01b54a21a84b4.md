### Title
Webhook shop/topic identity is not bound by the HMAC signature, enabling cross-tenant webhook injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` — the value that `Utils::HmacValidator` authenticates — only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values, which are read from HTTP headers and then trusted to route and tenant-scope the webhook, are never included in the signed content. This is the same bug class as TRST‑M‑2: an identity-relevant field (the shop/topic acted upon) is not covered by the same authentication check (HMAC) that is supposed to bind trust to the payload.

### Finding Description
`Request#hmac` decodes the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the signature purely over `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [2](#0-1) 

But `Registry.process` uses the *unsigned* `request.topic` and `request.shop` header values to route to a handler and to build the tenant context handed to application code: [3](#0-2) 

Because the `shop-domain` and `topic` headers sit outside the HMAC-covered bytes, the equality the code implicitly relies on — "bytes verified == bytes used to identify the tenant" — does not hold. `bytes_verified = raw_body` while `bytes_used_for_tenant_routing = headers[shop-domain]`, and these are never bound together cryptographically.

### Impact Explanation
An unprivileged internet user who operates their own shop with the app installed can receive a legitimate webhook for their own tenant (valid body + valid HMAC, since the app's `api_secret_key` is shared across all shops using the same app). They can then replay that exact raw body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with a victim shop's domain. `HmacValidator.validate` still passes because it only checks the body, so `Registry.process` will hand the attacker-controlled body to the handler tagged with the victim's shop identity via `WebhookMetadata`. Any host application logic that trusts `request.shop`/`WebhookMetadata#shop` to scope data writes, deletions, or session/token invalidation (e.g., `app/uninstalled`, `customers/data_request`, `shop/redact`) can be tricked into acting on the wrong tenant — a cross-tenant integrity/confidentiality impact.

### Likelihood Explanation
Exploitation only requires installing the app on an attacker-controlled shop (a normal, unprivileged action any merchant/developer can perform), capturing one legitimate webhook delivery, and replaying it with a modified `shop-domain`/`topic` header to the same public callback URL. No access to `api_secret_key`, tokens, or the victim's infrastructure is required.

### Recommendation
Bind the identity-relevant headers into the value that is HMAC-verified, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the signed body (e.g., verify that the shop domain reported in the header matches an out-of-band trusted value, or extend `to_signable_string` to canonically include these headers if compatible with Shopify's signing scheme). At minimum, document and enforce that host applications must independently corroborate `request.shop` against a known/installed-shop list before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers an event (e.g., updates an order) causing Shopify to deliver a signed webhook: body `B`, headers including `X-Shopify-Hmac-Sha256: H` (valid for `B` with the app's secret) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because only the body `B` is verified.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the host app to process attacker-supplied data under the victim tenant's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
