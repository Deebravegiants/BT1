### Title
Unbounded `ltFromPair`/reserve inputs can overflow `Math.mulDiv` inside `_noFeeSwapInput`, permanently bricking `finalizeGraduation` - ([File: packages/contracts/src/Bonding.sol])

### Summary
The external report is a classic "unvalidated input size causes an internal buffer/arithmetic overflow" bug. The closest reachable analog in alt.fun is `Bonding._noFeeSwapInput`, the closed-form swap-sizing helper used by the hostile-mint-pre-seed defense inside `finalizeGraduation`. Its own natspec documents the exact same failure mode as the report: unbounded inputs can push the internal product past `uint256`, and the code's safety argument rests on an assumption ("`tokensForLP` and `ltFromPair`... bounded by token supply") that does not actually hold for `ltFromPair`, whose raw magnitude depends on the LT's `exchangeRate()` rather than on `Token.TOTAL_SUPPLY()`.

### Finding Description
`_seedRebalancing` calls `_pairRebalance`, which calls `_noFeeSwapInput`: [1](#0-0) 

The function's own natspec states the invariant it depends on and what happens if it's violated: [2](#0-1) 

and the test suite's overflow-safety test explicitly relies on the assumption that `targetN`/`targetD` (i.e. `tokensForLP` and `ltFromPair`) are bounded near `Token.TOTAL_SUPPLY` (~2^90): [3](#0-2) 

That assumption is false for `ltFromPair`. `ltFromPair` is the real LT (raw token units) raised by the curve, computed in `_prepareGraduationLiquidity` as `assetReserve - virtualLtReserve`: [4](#0-3) 

Crucially, the USD graduation trigger is `(storedAssetReserve − virtualLtReserve) × exchangeRate ≥ $9K` — i.e. it is a *USD*-denominated threshold, and the *raw* LT amount needed to satisfy it is inversely proportional to `exchangeRate()`. For an LT with a very low `exchangeRate()` (a legitimate, low-priced/depegged BounceTech LT — nothing prevents pairing a bonding curve with such an LT, `Bonding.launch` only rejects retired LTs, not low-rate ones), reaching `$9K` in value requires a correspondingly enormous *raw* LT quantity, since `Zap`/`Bonding` place no cap on how much LT a buyer can route into a curve (`docs/contracts-scope.md` explicitly states "no upper bound on the seed" and buys are otherwise only capped by the overflow-buy protection on the *token* side, not on the *LT* side).

In the hostile-pre-seed rebalance path, when the pool is TOKEN-rich, `_seedRebalancing` sets `targetN = ltFromPair` (the large, LT-scale value) and `targetD = tokensForLP` (bounded to ≤ `LP_RESERVE` = 250M·1e18 ≈ 2^88): [5](#0-4) 

`_noFeeSwapInput` then computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` where `reserveIn`/`reserveOut` are the live V2 pair reserves (each up to `uint112`, i.e. up to 2^112, attacker-influenceable via a self-funded mint pre-seed as described in the "HyperSwap Pre-Seed Defense" documentation). With `targetN = ltFromPair` scaled arbitrarily large by a low-rate LT and `targetD` small/bounded, the discriminant `reserveIn·reserveOut·targetN/targetD` can exceed `2^256`, causing OZ `Math.mulDiv` to revert (it reverts rather than truncate on overflow) instead of returning a capped/degraded value.

Because `_pairRebalance`/`_seedRebalancing`/`_seedUniswapV2Direct` do not catch this revert, it propagates all the way up through `finalizeGraduation`, which has no other entry point to complete graduation. This directly violates the protocol's own stated invariant that "`_seedUniswapV2Direct` MUST never revert under any pre-seed shape" and that brick-resistance "ranks above the LP-capture defense, because a brick locks every holder in `Graduating` forever": [6](#0-5) 

### Impact Explanation
If `finalizeGraduation` reverts unconditionally for a given token (because the discriminant permanently overflows for that token's `ltFromPair`/`tokensForLP` ratio), the token is permanently stuck in `Lifecycle.Graduating`:
- All curve-raised LT and the 250M reserved tokens (`lpReserve`) sit frozen inside `Bonding` with no rescue path (`finalizeGraduation` is the only function that transitions out of `Graduating`, and `Router.buy`/`sell` already reject trades once a token is `Graduating`).
- Holders can never redeem to a live pool, and the creator/protocol lose the LP entirely.
- This matches the "permanent freezing of trader, creator or LP funds" criterion.

The overflow requires a specific, attacker-influenced combination: (1) a curve paired with a sufficiently low-`exchangeRate()` LT so that `ltFromPair` grows very large in raw units to cross the USD threshold, and (2) an attacker-funded mint pre-seed pushing `reserveIn`/`reserveOut` large enough that the product with `ltFromPair` exceeds `2^256` once divided by `tokensForLP`. Both levers (LT selection at launch and the mint pre-seed) are reachable by an unprivileged actor — a token creator picks the LT at `Zap.createToken`, and anyone can front-run `finalizeGraduation` with a mint pre-seed as already documented for the standard hostile-pre-seed class.

### Likelihood Explanation
Medium. The magnitude analysis is data-dependent (it needs a real BounceTech LT with a sufficiently small `exchangeRate()` combined with a large enough attacker-funded pre-seed to push the discriminant over `2^256`), and I could not fully enumerate the real-world exchange-rate range of deployed BounceTech LTs from the indexed code alone. However, the code's own comments and tests concede the theoretical overflow exists and only argue it's unreachable "because no real call site can construct such inputs" — a claim that rests solely on bounding `tokensForLP`/`ltFromPair` by `Token.TOTAL_SUPPLY`, which is true for `tokensForLP` but not established anywhere in the code for `ltFromPair`, whose magnitude is a function of `exchangeRate()`, not `TOTAL_SUPPLY()`. This gap between the documented safety assumption and the actual data flow is the root cause and is present regardless of whether a specific attacker can trivially hit it today.

### Recommendation
- Add an explicit bound/normalization on `ltFromPair` (or on the discriminant itself) before calling `_noFeeSwapInput`, e.g. cap the target ratio's numerator/denominator to a fixed-precision ratio (scale down both `targetN` and `targetD` proportionally) so the product can never approach `2^256` regardless of the paired LT's `exchangeRate()`.
- Wrap the `_noFeeSwapInput` call (or the whole rebalance attempt) in a `try/catch` (or pre-check the discriminant bound) inside `_pairRebalance`, treating an overflow as "cannot rebalance" and falling back to `_seedDirectMint`, mirroring the existing `s == 0` / `expectedOut == 0` fallbacks — this preserves the "never revert" brick-resistance guarantee that the rest of `_seedUniswapV2Direct` already provides.
- Update `test/NoFeeSwapInput.t.sol`'s overflow-safety fuzz/stress tests to include LT-scale (not just token-supply-scale) magnitudes for `targetN`/`targetD`, since the current tests only stress `tokensForLP`-sized values and do not reflect `ltFromPair`'s real, exchange-rate-dependent range.

### Proof of Concept
Conceptual PoC (illustrative, not run against the repo since Ask mode has no execution access):
1. Creator launches a token paired with an LT whose `exchangeRate()` is very small (e.g., a low-priced/deleveraged BounceTech LT — permitted, since `Bonding.launch` only rejects retired LTs, not low-rate ones).
2. Buyers route enough USDC through `Zap.buy` over time so that the *raw* LT raised (`ltFromPair`) needed to cross the `$9K` USD graduation threshold becomes very large (inversely proportional to the low `exchangeRate()`), while `tokensForLP` stays bounded near its parabola peak (≤ 250M tokens).
3. Once the token enters `Lifecycle.Graduating` (`_enterGraduating` fires on the threshold-crossing buy), an attacker front-runs `finalizeGraduation` by calling `factory.createPair(token, lt)` themselves, then `transfer`+`mint`s a large (but attacker-affordable) TOKEN-heavy dust/pre-seed into the pair to push `reserveToken`/`reserveLT` up, per the already-documented hostile-mint-pre-seed technique in `AGENTS.md`.
4. Anyone calls `Bonding.finalizeGraduation(token)`. Inside `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput`, the discriminant `reserveIn·reserveOut·ltFromPair / tokensForLP` exceeds `2^256`, `Math.mulDiv` reverts, and the revert propagates out of `finalizeGraduation`, permanently bricking the token in `Graduating`.

Note: I was not able to fully pin down the exact numeric exchange-rate/reserve thresholds required to trigger the overflow from the indexed code alone (BounceTech LT's real-world `exchangeRate()` range is external to this repo), so the concrete numeric feasibility of step 2–4 should be verified with a Foundry fuzz/PoC test against `NoFeeSwapInputHarness` (extending the existing `testFuzz_overflowSafety`/`test_overflowSafety_atRealisticMax` tests to use LT-scale `targetN` values) before treating this as fully confirmed exploitable in production. If the maintainers can show BounceTech LTs are hard-floored to a rate range that keeps `ltFromPair` within the ~2^90 envelope already assumed by the tests, this finding would be downgraded to defense-in-depth rather than an exploitable freeze.

    /// @dev Smallest swap input that drives the pool's reserve ratio
    ///      `(reserveIn + s) / (reserveOut - out)` to `targetN/targetD`
    ///      under the no-fee constant-product model:
    ///        `(reserveIn + s)² = reserveIn * reserveOut * targetN/targetD`
    ///      ⇒ `s = sqrt(reserveIn * reserveOut * targetN/targetD) - reserveIn`,
    ///      capped at `maxSwap`. The actual swap is fee-charging (the pair's
    ///      live fee), so the post-swap ratio drifts from the target by the
    ///      fee; the balanced-subset deposit absorbs the residual without
    ///      donating.
    ///
    ///      `Math.mulDiv` keeps the intermediate product
    ///      `reserveIn * reserveOut * targetN` inside its 512-bit working
    ///      space, but the final result `... / targetD` must still fit in
    ///      uint256. Call sites must keep that invariant — in practice
    ///      both the V2 uint112 reserve cap and the bound that
    ///      `tokensForLP` ≤ `LP_RESERVE` and `ltFromPair` ≤ raised LT
    ///      are well inside the safe envelope. Constructed adversarial
    ///      inputs that violate this would `revert` rather than silently
    ///      truncate, which is the correct failure mode.
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }

### Brick-resistance contract

`_seedUniswapV2Direct` MUST never revert under any pre-seed shape. The brick-resistance contract is the load-bearing security property — it ranks above the LP-capture defense, because a brick locks every holder in `Graduating` forever. The pre-seed defense is layered to honour this:

- **Regime 1/2 don't touch the router.** Even if the V2 router is misbehaving, the empty + donation paths run on direct pair calls.
- **`_pairRebalance` falls back to a direct mint when no swap can run.** `_noFeeSwapInput` may return `s == 0`, or the pair's fee-charging `getAmountOut(s)` may round to zero, against a pre-seed whose swap-output side is dust — `pair.swap` would otherwise revert with `INSUFFICIENT_OUTPUT_AMOUNT`. (truncated)
- **`_routerDepositAndDispose` uses `min0=1, min1=1`.** Slippage protection on `addLiquidity` exists to defend against a third party moving the pool ratio between quote and execution; here we set the ratio ourselves in `_pairRebalance` in the same atomic tx, so there's no third party to defend against. The `=1` (rather than `=0`) trips V2's degenerate-ratio guard so the call can't silently land at near-zero.
