## Title
Unbounded per-message work in `pallet_ismp::handle_unsigned` / `pallet_state_coprocessor::handle_unsigned` is billed at a fixed, size-independent weight, permitting a single unsigned extrinsic to exceed its declared block weight — (File: `modules/pallets/ismp/src/lib.rs`, `modules/pallets/state-coprocessor/src/lib.rs`)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic accepts an unbounded `Vec<Message>`, each element of which can itself carry an unbounded `Vec<PostRequest>`/`Vec<GetRequest>` batch requiring proof verification, hashing, dedup, and module dispatch — yet the extrinsic is billed a single, constant `Weight::from_parts(300_000_000, 0)` regardless of how large the batch is. `pallet-state-coprocessor`'s `handle_unsigned` has the identical shape: an unbounded `requests: Vec<GetRequest>` billed at a flat `reads_writes(1, 2)`. Both calls are permissionless (`ensure_none`) and, worse, are fully executed a second time inside `validate_unsigned` — meaning every node that merely receives the extrinsic over the network (before it is even included in a block) performs the full, unbounded verification workload. This is the same bug class as CVE-2023-27900: a library/handler that processes an attacker-controlled number of "parts" (here, batched ISMP messages/requests) without a limit tied to the resource cost charged, enabling a denial-of-service.

### Finding Description
`pallet_ismp::Call::handle_unsigned` is declared with a static weight function: [1](#0-0) 

```rust
/// Static weights because these should get overridden by the FeeHandler
fn weight() -> Weight {
	Weight::from_parts(300_000_000, 0)
}
```

and the call itself takes an unbounded `Vec<Message>`: [2](#0-1) 

Each `Message::Request`/`Message::Response`/`Message::Timeout` variant wraps its own unbounded `Vec<PostRequest>`/`Vec<GetRequest>` — see `RequestMessage`/`ResponseMessage`: [3](#0-2) 

`Pallet::execute` maps `handle_incoming_message` over every message in the `Vec`, and each `handle_incoming_message` call in turn iterates every request inside it, performing: `dedup_requests` (a `BTreeSet` insert per request), a Merkle/state membership or non-membership proof verification (`state_machine.verify_membership`/`verify_state_proof`, which itself walks proof nodes proportional to batch size), a `hash_request` keccak per item, and a full module `on_accept`/`on_response` dispatch per item: [4](#0-3) [5](#0-4) 

None of this work is reflected in the declared weight of `300_000_000` — a constant regardless of whether `messages` contains 1 element or thousands, each carrying thousands of requests. The only limits on the size of this input are the runtime's max block/extrinsic length (a byte-size cap), not a cap on the number of items nor a weight computed from that count.

Crucially, this same unbounded execution runs a second time, unconditionally, inside `validate_unsigned` — which every node performs merely to accept the extrinsic into its transaction pool for gossip, well before any block-authoring weight limit is even consulted: [6](#0-5) 

The `pallet-state-coprocessor::handle_unsigned` call, which the rules explicitly call out (`pallet-ismp handle_unsigned and child-trie commitments`), has the identical defect: an unbounded `requests: Vec<GetRequest>` billed at a fixed `reads_writes(1, 2)`, with per-request proof verification and dispatch inside `handle_get_requests`: [7](#0-6) [8](#0-7) 

Both `IsmpCallFilter` implementations in the Gargantua and Nexus runtimes only filter out consensus-carrying `handle_unsigned` batches and `fund_message`; they do not filter or bound batch size: [9](#0-8) 

The docs even acknowledge unsigned messages are processed "for free" and rely on tx-pool validity checking (which is exactly the expensive path that gets abused) rather than any resource cap: [10](#0-9) 

### Impact Explanation
An attacker crafts a single unsigned extrinsic (`pallet_ismp::handle_unsigned` or `pallet_state_coprocessor::handle_unsigned`) carrying the maximum number of requests/messages that fits within the block-length limit (a byte budget, not a work budget). Because the declared weight is a flat constant, `frame_system::CheckWeight` and block-authoring logic will treat this extrinsic as cheap, admitting it into a block (or many such extrinsics into the same block) whose real execution time — driven by hundreds/thousands of Merkle proof verifications, hashings, and dispatcher callbacks — vastly exceeds the block's actual time/weight budget. Additionally, because `validate_unsigned` performs the identical full execution merely to gossip the extrinsic, every full node on the network pays this unbounded cost the moment the extrinsic reaches its transaction pool, independent of whether it is ever included in a block. This is a network-wide denial-of-service vector: block production stalls/overruns, and honest relayer traffic is starved out by the flood of pool-validation work. This satisfies the "route unable to deliver messages" impact criterion.

### Likelihood Explanation
The call is fully permissionless (`ensure_none`) and reachable from a single submitted extrinsic — no privileged role, governance, or prior state is required. The only gate is that requests carry a technically-valid (though possibly commercially worthless/duplicate-free, since `dedup_requests` and receipt checks run) proof; an attacker with access to real historical proofs of many already-known requests (or freshly dispatched ones from a chain they control) can trivially assemble a maximal batch. Given this needs no special access and the weight/validation asymmetry is structural (not a corner case), likelihood is high.

### Recommendation
Compute the declared `Weight` for `handle_unsigned` (both pallets) as a function of the actual number of messages/requests in the batch (and ideally their proof sizes), rather than a fixed constant, so `CheckWeight` can reject over-budget batches before execution. Additionally, enforce an explicit maximum batch length (e.g., a `BoundedVec` with a `ConstU32` cap tuned to the block's weight budget) on `Message::requests`/`GetRequestsWithProof::requests`, and consider skipping or bounding the full `Self::execute` re-run inside `validate_unsigned` once basic structural/size checks fail, so pool-validation cost cannot be forced past a bounded ceiling.

### Proof of Concept
1. Construct N `PostRequest`/`GetRequest` entries (N large enough to stay under the runtime's max extrinsic/block length but with N in the thousands) referencing valid, provable commitments (e.g., requests dispatched from a colluding or previously-used source chain), each with a valid membership proof for the batch.
2. Submit a single `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Request(RequestMessage { requests, proof, signer })] }` (or the equivalent `pallet_state_coprocessor::Call::handle_unsigned`) as an unsigned transaction.
3. Observe that `validate_unsigned` executes `Self::execute(messages.clone())` fully (`modules/pallets/ismp/src/lib.rs:624-625`) — every node's mempool acceptance now performs O(N) proof verifications/hashes/dispatches — while `#[pallet::weight(weight())]` reports a constant `300_000_000` regardless of N (`modules/pallets/ismp/src/lib.rs:370,728-730`), and if included, block execution time for this single extrinsic scales with N far beyond its declared weight.

```rust
	pub fn handle_get_requests(
		GetRequestsWithProof { requests, source, response, address }: GetRequestsWithProof,
	) -> Result<(), Error> {
		// 1. Verify source proofs
		// 2. Extract fees
		// 3. Verify response proof
		// 4. insert GetResponse into mmr and request receipts
		// 5. emit Response events
		let host = <<T as Config>::IsmpHost>::default();

		// Reject duplicate requests within the batch.
		let wrapped: Vec<Request> = requests.iter().cloned().map(Request::Get).collect();
		dedup_requests::<<T as Config>::IsmpHost>(&wrapped)?;

		for req in requests.iter() {
			let full = Request::Get(req.clone());

			// Get requests time out are relative to Hyperbridge
			if full.timed_out(host.timestamp()) {
				Err(Error::RequestTimeout { meta: full.clone().into() })?
			}

			// Source of the request must match the proof
			if full.source_chain() != source.height.id.state_id {
				Err(Error::RequestProofMetadataNotValid { meta: full.clone().into() })?
			}

			// Proof must come from the requested chain
			if full.dest_chain() != response.height.id.state_id {
				Err(Error::RequestProofMetadataNotValid { meta: full.clone().into() })?
			}

			// This request has already been responded to. Mirror `handlers/response.rs:61`:
			// dedup against `response_receipt`, which the dispatch path writes for this exact
			// GetRequest hash after producing a response. The receipt also binds the response
			// commitment, so external auditors can attest "Hyperbridge produced response X for
			// request Y" from one map.
			let probe = GetResponse { get: req.clone(), values: Default::default() };
			if host.response_receipt(&probe).is_some() {
				Err(Error::DuplicateResponse { meta: (&probe).into() })?
			}
		}

		// Ensure the proof height is equal to each retrieval height specified in the Get
		// requests
		if !requests.iter().all(|get| get.height == response.height.height) {
			Err(Error::InsufficientProofHeight)?
		}

		// Verify source proof
		let source_state_machine = validate_state_machine(&host, source.height)?;
		let state_root = host.state_machine_commitment(source.height)?;

		// Verify membership proof to ensure that requests where committed on source chain
		let commitments = requests
			.iter()
			.map(|get| hash_request::<<T as Config>::IsmpHost>(&Request::Get(get.clone())))
			.collect();
		source_state_machine.verify_membership(&host, commitments, state_root, &source)?;
```

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
