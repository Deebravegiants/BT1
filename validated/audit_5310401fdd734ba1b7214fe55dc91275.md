Confirmed root cause. The webhook signature only covers the raw body — `to_signable_string` in [1](#0-0)  returns just `@raw_body`, while the `shop`, `topic`, and `webhook-id` fields consumed by the app are pulled unauthenticated from HTTP headers ( [2](#0-1) ). `Registry.process` validates only that HMAC before dispatching the header-derived `shop` to the handler ( [3](#0-2) ).

### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC computed only over the raw request body, but the `shop` (tenant identifier), `topic`, and `webhook-id` fields that the application actually acts on are taken directly, and unauthenticated, from HTTP headers. Because the HMAC secret (`Context.api_secret_key`) is the app's single client secret — shared across every shop that has installed the app — any shop that has genuinely installed the app receives real webhook deliveries with a *valid* signature for that raw body. That party can then replay the same `raw_body` + `hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header, since the shop field is never part of the signed content.

### Finding Description
`Utils::HmacValidator.validate` verifies `request.hmac` against `request.to_signable_string`, and for `Webhooks::Request` that signable string is defined as:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are parsed straight from caller-supplied headers with no cryptographic binding to the body or to each other:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Registry.process` only checks the HMAC and then forwards the unauthenticated `shop` value straight to the app's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

The identity binding the app relies on is: *"the HMAC proves this payload really is a webhook for shop X."* The equality this code implicitly assumes is `hmac_valid(raw_body) == shop_is_authentic(header)`, but since the HMAC secret is per-app (not per-shop), `hmac_valid(raw_body)` only proves "signed by Shopify for this app," not "for this specific shop." Any shop with the app installed can obtain a genuinely-signed `raw_body`/`hmac` pair from its own legitimate webhook deliveries and resend it to the app's public webhook controller with a forged `x-shopify-shop-domain` (or `shopify-shop-domain`) header pointing at a different, victim shop. `Registry.process` will accept it as authentic and hand `WebhookMetadata` with the victim's `shop` value (and the attacker-controlled body/topic combination that was already validly signed) to the app's business logic.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-acted-on binding described in the rules: the value used by the host application to select tenant context (`request.shop`) is not the value covered by the cryptographic check (`request.to_signable_string` == raw body only). Any downstream logic that trusts `WebhookMetadata#shop` for tenant-scoped operations (e.g., updating a specific merchant's records, looking up per-shop stored credentials, or triggering shop-scoped side effects) can be manipulated by another app-installer to appear as though it originated from a different, arbitrary shop — a cross-tenant identity confusion enabled purely through this gem's webhook verification API.

### Likelihood Explanation
Exploitation requires only that the attacker's own shop has installed the target app (an unprivileged internet user relative to other tenants) — no access token, `client_secret`, or other privileged credential is needed. The attacker simply captures one of their own legitimate webhook deliveries (raw body + `hmac-sha256` header, both attacker-visible) and replays it directly to the app's public webhook endpoint with a modified `shop-domain` header. This is straightforward, requires no timing race, and is inherent to how `Webhooks::Request`/`Registry.process` construct and validate the signable content.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the signed content rather than trusting it purely from headers. Since Shopify does not include shop-domain in the payload signature itself, mitigations belong at the design level exposed by this gem: e.g., document/require that `WebhookMetadata#shop` alone must never be used as the sole tenant selector without cross-checking it against an independently known/expected shop (such as the shop tied to the registered webhook subscription or a stored session), or provide an API that lets consumers verify the header-derived shop against the set of shops the app has valid sessions/webhooks for before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g., `orders/create`).
2. Shopify delivers a real webhook to the app's public endpoint with a body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `B` and `H` (both visible to them as the receiving party, or obtainable by triggering their own webhook).
4. Attacker sends a new POST to the same webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged/valid), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `HmacValidator.validate` passes because it only checks `B` against `H`; `Registry.process` dispatches `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` to the handler, which the application code has no gem-level way to verify against the true source shop.
