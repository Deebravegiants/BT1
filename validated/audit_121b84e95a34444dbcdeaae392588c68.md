### Title
Webhook shop-domain used for tenant routing is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by HMAC-verifying only the raw request body, then trusts the unauthenticated `X-Shopify-Shop-Domain` / `shopify-shop-domain` header to identify which tenant the payload belongs to. This breaks the intended identity binding: `hmac_verified_bytes == body` but `tenant_identity_used == header['shop-domain']`, and the header is not part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is pulled straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, with no cross-check against the signed body: [2](#0-1) 

`Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)` (which in turn calls `request.to_signable_string`, i.e. the raw body) and then hands `request.shop` straight to the handler as the tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` computes/compares the signature purely against `verifiable_query.to_signable_string`, i.e. the body, never the shop header: [4](#0-3) 

Because the shop-domain header is never part of the signed bytes, any request with a valid `hmac-sha256` signature for *some* body (e.g. one the attacker legitimately obtained for their own installed shop) can be replayed with an arbitrary `shopify-shop-domain` header value naming a different shop, and `Registry.process` will still accept it and dispatch it to the app's handler tagged as belonging to that other shop.

### Impact Explanation
This breaks the equality that should hold: `authenticated_bytes (body signed by client_secret) == bytes_used_to_derive_tenant_identity (shop header)`. Since the gem hands the unauthenticated `shop` value to the handler as the trusted tenant identifier (`WebhookMetadata#shop`), a host application following this gem's documented API for webhook processing has no way, using this gem alone, to detect that the tenant label is forged — enabling cross-tenant data confusion/access (e.g., writing or acting on data intended for shop A under shop B's identity).

### Likelihood Explanation
Exploitation requires the attacker to possess at least one HMAC-valid webhook body (trivial for an attacker who has installed the app on their own shop and captured a webhook their own shop legitimately received) and then resend it with the target's shop domain in the header. No access token, `client_secret`, or privileged account is required — only the ability to send arbitrary HTTP requests to the app's public webhook endpoint, which is inherently unauthenticated for this use case.

### Recommendation
Include the shop domain (and preferably topic/webhook-id) in the signed material, or have `Registry.process` cross-validate that the authenticated shop-domain matches an app-known installed shop before trusting it, and document that host apps must independently authorize the shop domain rather than treat header-derived `WebhookMetadata#shop` as authenticated.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST with a valid `X-Shopify-Hmac-Sha256` for some raw body `B`.
2. Attacker resends the exact same body `B` and valid HMAC header, but replaces `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a `Request` whose `hmac` still equals the value in the header, and whose `to_signable_string` is still `B`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` with the app's own `client_secret` and matches the attacker-supplied hmac header, since only `B` (unchanged) is signed — the shop header is never part of the signature.
5. Validation succeeds; the handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process/act on data under the wrong tenant's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
