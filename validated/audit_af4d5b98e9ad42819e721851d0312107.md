### Title
Order placers cannot enforce a minimum received amount for `predispatch` calldata execution, allowing silent loss of escrowed value to sandwich/price manipulation - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` allows a user to attach arbitrary `predispatch` calldata (e.g. to unwrap LP tokens or otherwise convert assets before escrow) that is executed through the `CallDispatcher`, and the actually-received token amount is measured and silently substituted for the user's declared `order.inputs[i].amount` with no minimum-received check. [1](#0-0)  This mirrors the Sherlock Velar-Artha M-3 finding, where an LP could not enforce a minimum base/quote amount when burning LP tokens, letting price movement between quote and execution silently reduce received value with no revert.

### Finding Description
In `placeOrder`, when `order.predispatch.call.length > 0`, the contract forwards the caller's assets to the `CallDispatcher`, executes `order.predispatch.call` (documented example: "unwrapping LP tokens"), then measures the resulting balance delta for each declared input token: [2](#0-1) 

Critically, the code that reconciles the measured `received` amount against the user's originally declared `order.inputs[i].amount` contains no lower bound / minimum-received guard:

```solidity
if (received > order.inputs[i].amount) {
    uint256 dust = received - order.inputs[i].amount;
    emit DustCollected(token, dust);
} else {
    order.inputs[i].amount = received;
}
``` [3](#0-2) 

There is no `minAmount`/slippage parameter on `DispatchInfo`/`Order` that the transaction can be required to satisfy before this branch executes; whatever amount happens to come out of `CallDispatcher.dispatch(order.predispatch.call)` is unconditionally accepted, exactly like the Velar-Artha `burn()` function accepting whatever `calc_burn`-computed value the pool state yields at execution time with no `min_base_amount`/`min_quote_amount` parameter.

Because the predispatch calldata typically routes through external DEX pools or unwrap logic whose output depends on live, externally-influenceable state (reserves, prices), an attacker who can front-run/sandwich the `placeOrder` transaction (a public mempool transaction, reachable by anyone) can move that external state so that `received` comes back lower than what the user computed off-chain when constructing the order. The contract then silently reduces `order.inputs[i].amount` to this lower `received` value and proceeds to escrow the reduced amount, rather than reverting.

### Impact Explanation
This is directly analogous to the referenced Sherlock Medium finding: the transaction that converts an asset into the value ultimately at stake (LP burn / predispatch unwrap) offers no user-specified minimum acceptable output. A single-transaction sandwich attack against `placeOrder` (when it carries predispatch calldata sourcing value from a price-sensitive external call) permanently and silently reduces the value the user obtains from their assets, with the difference captured by the attacker, and the contract records no failure — the order is placed successfully with degraded input value. This is a direct, unbacked loss of user funds during intents escrow placement, matching the accepted severity class of the original report (Medium: definite loss of funds under externally-influenced conditions, without needing further conditions beyond a mempool front-run).

### Likelihood Explanation
Any account can submit a `placeOrder` transaction with `predispatch.call` sourcing value from an AMM or other price-sensitive external contract; MEV searchers routinely watch the public mempool for such value-extracting opportunities. No privileged role or protocol misconfiguration is required — only an order that includes predispatch calldata whose output is price/state dependent, which the docstring explicitly anticipates ("e.g., unwrapping LP tokens"). [4](#0-3) 

### Recommendation
Add a per-input `minAmount` (or overall minimum-received) field to `DispatchInfo`/predispatch input specification, and revert `placeOrder` if the measured `received` amount for any predispatch-sourced input falls below the caller-specified minimum, instead of silently substituting the reduced value into `order.inputs[i].amount`.

### Proof of Concept
1. User constructs an `Order` with `predispatch.call` that unwraps an LP position (or otherwise swaps/converts assets) into the declared input token, expecting `order.inputs[i].amount = X` based on current pool state.
2. User submits `placeOrder(order, graffiti)`.
3. Attacker observes the pending transaction in the mempool and sandwiches it (front-run trade that shifts the pool price the predispatch calldata will execute against, back-run trade to restore price and capture the difference).
4. `placeOrder` executes; `CallDispatcher.dispatch(order.predispatch.call)` returns fewer tokens than the user expected (`received < X`).
5. The code at [3](#0-2)  silently sets `order.inputs[i].amount = received` and proceeds — no revert occurs, and the user's order is escrowed at the sandwiched, reduced value while the attacker keeps the extracted difference.
