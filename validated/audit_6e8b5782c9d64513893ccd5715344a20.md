### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates its HMAC over the raw request body only, while the `shop` attribute used to attribute a webhook to a specific merchant (tenant) is read from an HTTP header that is never included in the signed material. Any party who can obtain one valid `(body, hmac)` pair for the shared `api_secret_key` (e.g. a merchant who has installed the app and thus receives real webhooks for their own store) can replay that payload against the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still passes because it never checks the shop header, so `Registry.process` dispatches attacker-controlled webhook data under a victim shop's identity.

### Finding Description
`Request#hmac` and `Request#to_signable_string` define the signable content: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; the `shop` accessor is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header and is never mixed into the signed string: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC strictly against `verifiable_query.to_signable_string` (the body), with no binding to the shop header: [3](#0-2) 

`Registry.process` trusts `request.shop` as the tenant identity once the HMAC check passes, and forwards it unchecked into the handler's `WebhookMetadata`: [4](#0-3) 

The broken identity binding is:
`HMAC(secret, raw_body)` is verified, but the equality that actually matters for tenant isolation — `shop_header == shop_that_produced(raw_body, hmac)` — is never checked. Because every shop that has the app installed shares the same `api_secret_key`, a valid `(raw_body, hmac)` pair generated from webhooks delivered to *any* shop remains valid when replayed with a different `shop-domain` header value.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), matching the "Critical - cross-tenant access" impact category. An attacker who operates or compromises Shop A (or otherwise obtains one legitimate webhook delivery, e.g. via a captured HTTP request) can trigger the app's webhook handler with Shop A's payload content but Shop B's `shop` attribution. If the host application uses `WebhookMetadata#shop` to select which merchant's records to create/update/delete (the intended and documented use, per the `shop:` field on `WebhookMetadata`), the attacker can inject or corrupt data attributed to a shop they do not control, entirely by replaying a request the gem itself accepts as authentic.

### Likelihood Explanation
Likelihood is high for any attacker who is themselves a legitimate merchant of the app (a normal, unprivileged, unauthenticated-relative-to-other-tenants actor): they receive real webhook deliveries with valid HMACs for their own shop and can trivially resend them with a modified shop header. No access to `api_secret_key`, access tokens, or victim credentials is required — only the ability to replay an HTTP request with a different header value, which is standard "unprivileged internet user" capability against a public webhook endpoint.

### Recommendation
Bind the shop identity to the signed content the same way Checks-Effects-Interactions requires binding effects to verified state before acting on them: include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable string, or independently verify that the shop asserted in the header matches a shop the app expects/has an active session/installation for before dispatching to handlers. At minimum, `Request#to_signable_string` should not omit tenant-identifying headers from the value that `HmacValidator` verifies.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of body B>
x-shopify-shop-domain: attacker-shop.myshopify.com
Body: B
```
2. Attacker resends the identical request to the app's webhook endpoint, only changing the shop header:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <same valid HMAC of body B>
x-shopify-shop-domain: victim-shop.myshopify.com
Body: B
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` — it succeeds, per [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, as built from `request.shop` and `request.parsed_body` in [6](#0-5) , causing any per-shop side effects in the host application to be executed against the victim shop's data using attacker-chosen content.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
