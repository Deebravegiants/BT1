### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by the handler dispatch logic are taken from unauthenticated HTTP headers. Because the app's webhook signing secret (`Context.api_secret_key`) is shared across every shop that installs the app, any shop where the attacker has legitimately installed the app can obtain a validly-HMAC'd webhook body and then replay it with a forged `shop-domain` header pointing at a different (victim) shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

but `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers that are never included in the signed bytes: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC once (over the body only) and then dispatches the handler using the unauthenticated `request.topic` and `request.shop`, passing them into `WebhookMetadata`: [4](#0-3) 

The equality that should hold is: `bytes verified by HMAC == bytes that determine tenant/topic identity used by the handler`. Here it does not — `bytes verified` = `raw_body` only, while `bytes that determine identity` = `raw_body ∪ {shop-domain header, topic header, webhook-id header}`. Since the webhook signing secret (`api_secret_key`) is the same across all shops/tenants that install the app (it is the app's own client secret, not per-shop), an attacker who controls one legitimately-installed shop can capture a genuine webhook (valid HMAC over some captured body) and replay it to the same endpoint with the `shopify-shop-domain` (and/or `shopify-topic`) header rewritten to a victim shop/topic. The HMAC check still passes because it only reprocesses the untouched body, but the handler now believes the event originated from, and pertains to, the victim's shop/topic.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: a handler that uses `WebhookMetadata#shop` to look up per-shop state, trigger per-shop side effects, or fetch/use an access token keyed by that shop will act on the attacker-chosen victim shop instead of the actual originating shop. This is a cross-tenant access vector: one merchant's installation can be leveraged to inject events that appear to come from another merchant's shop into the app's webhook processing pipeline.

### Likelihood Explanation
Exploitation requires the attacker to operate at least one shop where the target app is installed (i.e., be able to receive one legitimate, validly-signed webhook), which is a low bar for any public/multi-tenant Shopify app. No access token, `client_secret`, or privileged account is needed — only replay of a normal webhook delivery with a modified header, which any unprivileged internet user capable of installing the app on a test/dev store can obtain.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC validation, or otherwise cryptographically bind them to the body (e.g., validate that the `shop` header matches an expected/registered shop for the given topic/session before dispatch). At minimum, document that consumers of `WebhookMetadata#shop`/`#topic` must not treat these fields as verified by the HMAC check and must independently validate them against known shop/session state.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and its valid `x-shopify-hmac-sha256` value.
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC is computed only over the unchanged `raw_body`: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the event never originated from that shop, allowing the attacker to inject spoofed cross-tenant events.
