### Title
PoA bridge `describeWithdrawal` matches batched same-asset withdrawals by `assetId` only, causing status/hash misreport - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` deliberately ignores the per-withdrawal `index` that the SDK assigns to disambiguate withdrawals sharing the same bridge route, and instead resolves the on-chain withdrawal record solely by `assetId`. When a caller batches multiple withdrawals of the same asset (a normal, unprivileged usage of `IntentsSDK.processWithdrawal`/`waitForWithdrawalCompletion` with an array of `WithdrawalParams`), every withdrawal entry for that asset resolves to the same matched record, so the SDK can report the wrong transaction hash/status for a given withdrawal identifier even though a different transfer actually happened on-chain.

### Finding Description
`IntentsSDK` explicitly supports batch withdrawals: `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` accept `WithdrawalParams[]`, and each withdrawal is assigned a bridge-scoped sequence number via `createWithdrawalIdentifiers`: [1](#0-0) 

This `index` is meant to let each bridge adapter identify *which* of several concurrent withdrawals on the same route/asset a status query refers to. However, `PoaBridge.describeWithdrawal` throws away that index and matches purely by `assetId`: [2](#0-1) 

The comment "Response list is unsorted, so we match by assetId instead of index" confirms this is intentional, but it breaks the equality the caller relies on: *withdrawal identifier N should report the status of the on-chain transfer originating from withdrawal N*, not "any completed transfer of the same asset in this NEAR tx." If a single intent transaction contains two or more PoA withdrawals of the same `assetId` (e.g., sending the same token to two different `destinationAddress`/`amount` pairs — a pattern the SDK's own batching API supports), `findMatchingWithdrawal` will return the same underlying withdrawal record (or an arbitrarily-selected one) for both `index=0` and `index=1` calls, since destination address and amount are not part of the match criteria.

### Impact Explanation
This is a status/hash misreport analogous to the `shareKey` class of bug — an internal equality (`withdrawal[i]` status corresponds to `on-chain transfer i`) is broken by a caller-triggerable but unprivileged action (batching two same-asset withdrawals). A downstream integrator that calls `sdk.processWithdrawal`/`waitForWithdrawalCompletion` with a batch of same-asset withdrawals and credits/marks a destination as paid based on the returned `txHash`/`status` could:
- Mark the wrong withdrawal as completed using a transaction hash that actually belongs to a different destination address/amount.
- Potentially credit/refund the same on-chain transfer against two different logical withdrawals (double credit), or mark a still-pending withdrawal as completed.

This matches the "High" impact bucket: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Reachable by any unprivileged caller of the public SDK simply by supplying an array of `WithdrawalParams` where two entries share the same `assetId` and route to the PoA bridge (no admin/relayer collusion required). Batch withdrawals are a first-class, documented SDK feature, so hitting two same-asset entries in one batch is a realistic usage pattern, not a contrived edge case.

### Recommendation
Have `findMatchingWithdrawal` (and the underlying `getWithdrawalStatus`/`waitForWithdrawalCompletion` helper in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) disambiguate using more than `assetId` — e.g., additionally match on `destinationAddress`, `amount`, and consume matched entries once so repeated calls with different `index` values cannot resolve to the same underlying withdrawal record. If the PoA bridge API cannot provide a stable per-withdrawal identifier, the SDK should track already-consumed withdrawal records per NEAR tx hash and exclude them from subsequent matches for the same batch.

### Proof of Concept
1. Call `sdk.processWithdrawal` (or `waitForWithdrawalCompletion`) with `withdrawalParams: [{assetId: X, destinationAddress: A, amount: 100}, {assetId: X, destinationAddress: B, amount: 200}]`, both routed to the PoA bridge.
2. `createWithdrawalIdentifiers` assigns `index: 0` to the first and `index: 1` to the second (see [1](#0-0) ).
3. When the NEAR intent transaction settles and both PoA withdrawals appear in `response.withdrawals`, `PoaBridge.describeWithdrawal` is invoked once per index, but both invocations call `findMatchingWithdrawal(response.withdrawals, assetId)` with the identical `assetId` (see [3](#0-2) ), so both index-0 and index-1 status calls can resolve to the same matched withdrawal record (e.g., the one destined for address `A`), even though the caller expects index-1's status to correspond to the transfer to address `B`.
4. The integrator observing `waitForWithdrawalCompletion` for withdrawal index 1 receives a `txHash`/`completed` status that actually corresponds to the transfer destined for address `A`, not `B`.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
