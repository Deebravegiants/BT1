## Analysis

`onlyAllowedRecipient` in `contracts/external-actions/ExternalActionBaseUpgradeable.sol` restricts `runAction` to `msg.sender == Hinkal` (the only address registered as `_isAllowedRecipient`), so `EmporiumUpgradeable.runAction` is only reachable through `Hinkal.transact` → `_externalTransact`, exactly the path the question describes. [1](#0-0) [2](#0-1) 

An attacker can indeed set `externalActionId == HINKAL_EMPORIUM_ACTION_ID` with `erc20TokenAddresses.length == 0`, which routes `formInputForCircom` to `formInputEmporiumMin`, proving only `emporiumMessage`, `timeStamp`, `calldataHash`. [3](#0-2) 

`dimensionsCheck` in `HinkalHelper.sol` only requires internal consistency between `dimensions.tokenNumber` and the various `circomData` array lengths — it never forces `tokenNumber > 0`, so `tokenNumber == 0` (matching the empty `erc20TokenAddresses`) passes cleanly. [4](#0-3) 

In `EmporiumUpgradeable.runAction`, when `stack.signerAddress == address(0)`, `verifyWallet` returns immediately with no ECDSA signature check on `stack.ops` at all — only `usedMessages[emporiumMessage]` is marked. [5](#0-4) 

Then the ops loop executes CASE 2 (`op.invokeWallet && signerAddress != 0` is false), performing an arbitrary `op.endpoint.call{value: op.value}(op.callData)` **from Emporium's own identity** (msg.sender = Emporium contract), the only restriction being that the call selector isn't `callHinkalWallet`/`doSendToRelay`. [6](#0-5) 

Because `circomData.erc20TokenAddresses.length == 0`, `getBalancesForArray` returns an empty array both before and after, so the `balancesBefore`/`balancesAfter` loop in `runAction` and the corresponding balance/slippage loop in `Hinkal.transact` never execute for any token. [7](#0-6) [8](#0-7) 

This means any ERC20 that Emporium holds an unspent standing approval on (or holds directly) can be pulled out of Emporium by the attacker-controlled `op.endpoint.call(op.callData)` — e.g. `spender.transferFrom(emporium, attacker, amount)` on a token/router Emporium had previously approved — with zero accounting anywhere in the call stack. This is a genuine break of the invariant "assets Emporium can move in a tx == assets accounted in balancesBefore/balancesAfter" for the Min-circuit path.

However, the specific "same-token second leg processed twice" detail in the question is **not applicable** here: since `erc20TokenAddresses.length == 0`, the per-token loops (`balancesBefore`/`balancesAfter` in `EmporiumUpgradeable.runAction`, and the slippage loop in `Hinkal.transact`) never iterate at all — there is no token list to process once, let alone twice. That specific mechanic described in the question does not exist in this code path; the real root cause is simply that the empty token array means *zero* accounting occurs for *any* token moved by the ops, not that a duplicate-token entry is double-counted.

### Title
Emporium Min-circuit path allows unsigned arbitrary calls from Emporium's identity with zero token accounting - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
By choosing `externalActionId == HINKAL_EMPORIUM_ACTION_ID` with an empty `erc20TokenAddresses` array, an attacker forces the Min-circuit input path (`formInputEmporiumMin`), which proves nothing about the operations performed. Combined with `EmporiumStack.signerAddress == address(0)` (which skips the EIP-712 signature check in `verifyWallet` entirely), the attacker can make `EmporiumUpgradeable` execute arbitrary `op.endpoint.call(op.callData)` from its own address, while every balance-accounting loop (`balancesBefore`/`balancesAfter` in `runAction`, and the slippage loop in `Hinkal.transact`) is empty because the token array length is zero.

### Finding Description
Broken equality: "assets Emporium can move in a tx" should equal "assets accounted in balancesBefore/balancesAfter", but with `erc20TokenAddresses.length == 0` the right side is unconditionally the empty set regardless of what the ops actually do.

Path: `Hinkal.transact` → `hinkalHelper.performHinkalChecks` → `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin` (only 3 public signals) because `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` [9](#0-8)  → proof verifies against this minimal input → `dimensionsCheck` passes trivially with `tokenNumber == 0` [10](#0-9)  → `_externalTransact` calls `EmporiumUpgradeable.runAction` with the attacker's `externalActionMetadata` decoded as `EmporiumStack` [11](#0-10)  → `verifyWallet` no-ops for `signerAddress == address(0)` [12](#0-11)  → the ops loop executes attacker-chosen `op.endpoint.call{value: op.value}(op.callData)` as Emporium [13](#0-12)  → both `balancesBefore`/`balancesAfter` in `runAction` and the outer slippage/balance loop in `Hinkal.transact` iterate over the empty `erc20TokenAddresses`, so nothing is checked [8](#0-7) .

Root cause: the Min-circuit optimization assumes an empty token array implies no assets move, but nothing in the contract enforces that the arbitrary `op.callData` cannot move assets Emporium controls (e.g., consuming a standing ERC20 approval previously granted by Emporium to some spender via `token.approve(spender, amount)` in a prior legitimate op, then having the attacker's stateless op call `spender.transferFrom(emporium, attacker, amount)`, or directly calling `token.transfer(attacker, amount)` if Emporium holds a raw balance).

The "duplicate token in same call" mechanic from the question does not apply: with `erc20TokenAddresses.length == 0` there is no per-token loop at all to process a token twice — the vulnerability is simpler and more severe: zero tokens are checked, period.

### Impact Explanation
Critical: direct theft of any ERC20 balance or standing approval held by the Emporium contract, executed via an unsigned, unprivileged call from any attacker able to submit a valid Min-circuit proof (which requires only knowledge of a Poseidon preimage the attacker chooses themselves, not any user secret). Fully repeatable against any funds/approvals Emporium accumulates, and each `emporiumMessage` is single-use via `usedMessages`, but new distinct messages can be minted freely by the attacker to repeat the attack across separate approvals/balances.

### Likelihood Explanation
Preconditions: Emporium must hold ERC20 balance and/or an unrevoked standing approval to some spender (a normal side effect of legitimate prior swap/wallet ops). No signer privilege, whitelisting, or relay role required — the attacker only needs to call `Hinkal.transact` with a self-generated Min-circuit proof and a crafted `EmporiumStack` with `signerAddress == address(0)`. Attacker cost is a single transaction plus proof generation.

### Recommendation
Do not allow the Min-circuit / empty-token path to be combined with `signerAddress == address(0)` for stateless calls; require `stack.ops.length == 0` (or ops must not perform any external `call` with nonzero risk) whenever `erc20TokenAddresses.length == 0`, or reject the Min path entirely unless `stack.ops` is proven empty/constrained by the circuit. Alternatively, always require a valid EIP-712 signature for any Emporium ops regardless of `signerAddress`, and ensure balance accounting occurs for every token any op could conceivably touch, not just those in the caller-supplied `erc20TokenAddresses` array.

### Proof of Concept
1. Deploy Emporium, fund it with ERC20 `X` and have it `approve(maliciousSpender, amount)` via a legitimate prior op (or simply transfer `X` directly to Emporium).
2. Attacker crafts a Min-circuit proof for `HINKAL_EMPORIUM_ACTION_ID` with `erc20TokenAddresses = []`, `emporiumMessage` of their choosing, generating a valid proof for the 3-signal `formInputEmporiumMin` circuit.
3. Attacker encodes `externalActionMetadata` as `EmporiumStack{ signerAddress: address(0), ops: [{ endpoint: maliciousSpender, invokeWallet: false, value: 0, callData: transferFrom(emporium, attacker, amount) }], maxFee: 0, deadline: ... }`.
4. Call `Hinkal.transact(a,b,c,dimensions{tokenNumber:0,...}, circomData)`.
5. Assert: `token.balanceOf(attacker)` increases by `amount`, `token.balanceOf(emporium)` decreases by `amount`, and `Hinkal.transact` succeeds without reverting on any balance/slippage check — proving `assets moved != assets accounted (0)`.
