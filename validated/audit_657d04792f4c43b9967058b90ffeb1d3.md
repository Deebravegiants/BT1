### Title
Concurrent index-bin insertions from unprivileged transactions can panic the validator via `Reallocated::add_reallocation`'s `assert_eq!(0, ...)` in `bucket_map/src/bucket.rs`

### Summary
`BucketApi::grow` only acquires a **read** lock on the `RwLock<Option<Bucket<T>>>`, unlike `insert`/`update`/`try_write`/`set_anticipated_count`/`batch_insert_non_duplicates`, which all go through `get_write_bucket()` and take an exclusive write lock. Because multiple readers can execute `Bucket::grow` concurrently on the same underlying `Bucket<T>` instance, two threads that each independently receive a `BucketMapError` (index or data bucket full) for the same accounts-index bin can call `grow()` at nearly the same time, both eventually calling `Reallocated::add_reallocation`, whose `assert_eq!(0, self.active_reallocations.fetch_add(1, Ordering::Relaxed), "Only 1 reallocation can occur at a time")` is not idempotent against concurrent callers and will panic on the second caller.

### Finding Description
`BucketApi::grow` is documented as intentionally taking only a read lock: [1](#0-0) 
while all the "real" mutation paths — `insert`, `update`, `try_write`, `set_anticipated_count`, `batch_insert_non_duplicates` — call `get_write_bucket()`, which takes an exclusive write lock and consumes any pending reallocation via `handle_delayed_grows()` before the mutation proceeds: [2](#0-1) 

The reallocation bookkeeping itself relies on a bare `AtomicUsize` guarded only by an `assert_eq!` invariant, not on any lock that would serialize concurrent `grow()` invocations for the same bucket instance: [3](#0-2) 

The intended flow (as used inside `Bucket::insert`) is: attempt `try_write`, and if it errors with `BucketMapError`, call `grow(err)` then `handle_delayed_grows()` in a retry loop, all while the write lock is held continuously by a single caller — safe by construction: [4](#0-3) 

However, `BucketApi::grow` is exposed as an independent public entry point that release-and-reacquire callers (outside `Bucket::insert`'s own retry loop, e.g. higher-level retry code in the accounts index that calls `try_write`/`try_insert`, observes the error, and separately invokes `api.grow(err)`) can call while holding only a read lock. If two distinct worker threads are each inserting brand-new, distinct pubkeys that hash into the *same* accounts-index bin, and both threads' `try_write` calls fail with a `BucketMapError` because that bin's index/data bucket is full, both threads can call `grow(err)` concurrently since the read lock does not exclude other readers. If neither thread's reallocation has yet been consumed by `handle_delayed_grows()` (which requires the exclusive write lock and only runs on the next write), the second thread's call path through `Bucket::grow` → `Reallocated::add_reallocation` will observe `active_reallocations == 1` already set by the first thread, and `fetch_add` will return `1` instead of the expected `0`, tripping the `assert_eq!` and panicking the thread that processes that transaction.

The attacker's inputs are simply: many `System Program::CreateAccount` (or any instruction creating a fresh, non-conflicting account) transactions for freshly generated keypairs, chosen offline so their pubkeys hash into the same accounts-index bin (bin selection is a deterministic, attacker-computable function of the pubkey bytes), submitted so that the runtime's parallel execution/commit machinery processes several of them concurrently against the same, nearly-full bin.

No existing guard stops this: there is no signature/nonce/rent/budget check involved — this is purely an internal data-structure invariant violated by lock-scoping choices (write lock for mutation, but only read lock for `grow`), and the invariant is enforced by an `assert_eq!` that panics rather than being handled by `Result`.

### Impact Explanation
A validator thread executing this code path panics with `"Only 1 reallocation can occur at a time"`. Depending on how the accounts index/commit pipeline handles a panicking worker, this can crash the validator process or corrupt in-flight accounts-index state, producing a liveness/availability impact (validator crash / DoS) — this falls under Agave's "loss of liveness"/crash bounty category since the trigger comes from unprivileged, ordinary transaction traffic (creating many accounts) rather than any privileged or misconfigured path.

### Likelihood Explanation
Triggering requires: (1) attacker-computable pubkeys colliding into the same accounts-index bin — feasible offline since bin assignment is a public, deterministic function of pubkey bytes and attackers can generate unlimited keypairs; (2) genuine thread-level concurrency of two `try_write`/`grow` sequences against the same bin's `Bucket<T>` before `handle_delayed_grows()` consumes the first pending reallocation — this depends on the runtime's parallel scheduling of independent (non-conflicting) transactions during account creation/commit. I was not able to fully inspect the interior of `Bucket::grow`/`grow_data`/`grow_index` (ran out of tool budget) to confirm there is no additional path-specific serialization beyond the `RwLock`/`assert_eq!` pair shown above, so the exact concurrency window size (and whether it is realistically hittable under the real accounts-db threading model) could not be fully verified from the retrieved code and should be validated with a live reproduction.

### Recommendation
Serialize the decision to grow using the same lock that guards mutation (i.e., require a write lock, or an additional dedicated mutex per bucket, before performing the "is a reallocation needed" check and calling `add_reallocation`), or change `add_reallocation`/`get_reallocated` to be safely re-entrant (e.g., using `compare_exchange` to no-op if a reallocation is already pending instead of asserting), so that concurrent `grow()` calls degrade to a harmless retry rather than panicking.

### Proof of Concept
Integration test plan (bucket_map crate):
```rust
// bucket_map/src/bucket_api.rs (test module) or a new integration test
#[test]
fn test_concurrent_grow_panics() {
    use std::{sync::Arc, thread};
    // Construct a BucketApi<u64> (or reuse existing test helpers) with a tiny
    // max_search / small initial capacity so a small number of inserts forces
    // a BucketMapError (IndexNoSpace/DataNoSpace).
    let api = Arc::new(make_test_bucket_api()); // helper mirroring existing tests in bucket.rs

    // Fill the bucket to just below capacity via api.insert(...) so the next
    // insert on either thread triggers BucketMapError.

    let api1 = Arc::clone(&api);
    let api2 = Arc::clone(&api);

    // Precompute two pubkeys/keys that are known (from BucketMap internals)
    // to hash into the same single-bucket instance under test.
    let key1 = /* pubkey A */;
    let key2 = /* pubkey B */;

    let t1 = thread::spawn(move || {
        // Directly exercise try_write + grow without the write-lock-protected
        // retry loop, mimicking an external caller of BucketApi::grow.
        if api1.try_write(&key1, (&[1u64], 1)).is_err() {
            api1.grow(BucketMapError::IndexNoSpace(0));
        }
    });
    let t2 = thread::spawn(move || {
        if api2.try_write(&key2, (&[2u64], 1)).is_err() {
            api2.grow(BucketMapError::IndexNoSpace(0));
        }
    });

    // Expect one of the joins to return an Err due to a panic unwind,
    // demonstrating the assert_eq! in Reallocated::add_reallocation fired.
    let r1 = t1.join();
    let r2 = t2.join();
    assert!(r1.is_err() || r2.is_err(), "expected a panic from concurrent grow()");
}
```
Expected result: one of the joined threads returns `Err` because the spawned thread panicked with message `"Only 1 reallocation can occur at a time"`, confirming the race in `Reallocated::add_reallocation` is reachable via two concurrent callers of `BucketApi::grow` on the same bucket instance without holding the write lock.

pub struct Reallocated<I: BucketOccupied, D: BucketOccupied> {
    /// > 0 if reallocations are encoded
    pub active_reallocations: AtomicUsize,

    /// actual reallocated bucket
    /// mutex because bucket grow code runs with a read lock
    pub items: Mutex<ReallocatedItems<I, D>>,
}

impl<I: BucketOccupied, D: BucketOccupied> Default for Reallocated<I, D> {
    fn default() -> Self {
        Self {
            active_reallocations: AtomicUsize::default(),
            items: Mutex::default(),
        }
    }
}

impl<I: BucketOccupied, D: BucketOccupied> Reallocated<I, D> {
    /// specify that a reallocation has occurred
    pub fn add_reallocation(&self) {
        assert_eq!(
            0,
            self.active_reallocations.fetch_add(1, Ordering::Relaxed),
            "Only 1 reallocation can occur at a time"
        );
    }
    /// Return true IFF a reallocation has occurred.
    /// Calling this takes conceptual ownership of the reallocation encoded in the struct.
    pub fn get_reallocated(&self) -> bool {
        self.active_reallocations
            .compare_exchange(1, 0, Ordering::Acquire, Ordering::Relaxed)
            .is_ok()
    }
}
