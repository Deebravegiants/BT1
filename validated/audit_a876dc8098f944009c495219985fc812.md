## Title
Username Enumeration via Distinct Login Error Messages - (File: `core/web/sessions_controller.go`)

### Summary
The `/sessions` login endpoint returns the authentication provider's raw error message directly to the unauthenticated client. The local, LDAP, and OIDC authenticators all return textually distinct errors depending on whether the *email* or the *password* check failed ("Invalid email" vs "Invalid password"), which is exactly the bug class described in the CasaOS advisory (GHSA-c967-2652-gfjm): an attacker can distinguish "user does not exist" from "wrong password" and enumerate valid usernames/emails.

### Finding Description
`SessionsController.Create` forwards the error returned from `CreateSession` straight into the HTTP response with no normalization: [1](#0-0) 

The default local authenticator's `CreateSession` produces two distinguishable error strings depending on which check fails: [2](#0-1) 

The same pattern is repeated in the LDAP authenticator's local-admin fallback path: [3](#0-2) 

and in the OIDC authenticator's local-admin fallback path: [4](#0-3) 

Because `jsonAPIError(c, http.StatusUnauthorized, err)` is called with the raw `err` object (not a generic sanitized message), and this project's `jsonAPIError` helper serializes the error's message text into the JSON:API response body, a caller submitting `POST /sessions` with a candidate email/password pair receives a body whose error text differs depending on whether the email was wrong ("Invalid email"/"invalid email") or the password was wrong ("Invalid password"/"invalid password"). This is unauthenticated, pre-session, internet-facing surface — the `/sessions` route sits in the unauthenticated route group: [5](#0-4) 

I was not able to fully re-verify the exact byte-for-byte JSON serialization of `jsonAPIError` (its definition in `core/web/helpers.go` was located but not read to completion before the tool budget ran out), so I cannot 100% confirm the exact wire format of the leaked string. However, the error value passed to it is unambiguously the distinct "Invalid email"/"Invalid password" (or lower-case "invalid email"/"invalid password") error created in the authenticator layer, and no sanitization/normalization step exists between authenticator and controller in the code I reviewed.

### Impact Explanation
An unauthenticated attacker can use the differing error content on `/sessions` to enumerate valid CasaOS-Chainlink node operator emails/usernames. Confirmed valid usernames materially assist follow-on credential-stuffing, targeted phishing, or brute-force attacks against the node's admin/API-token login, which controls fund-moving and job-management privileges. Per the CVSS from the analog report (`AV:L/AC:L/PR:N/UI:N/C:H`), the primary impact is confidentiality (disclosure of valid principal identifiers), consistent with CWE-204 (Observable Response Discrepancy).

### Likelihood Explanation
The rate limiter on `/sessions` (`rl.UnauthenticatedPeriod()`/`rl.Unauthenticated()`) throttles bulk requests but does not prevent enumeration outright, only slows it: [6](#0-5) 
Given the endpoint is unauthenticated, internet-facing (in a non-firewalled deployment), and requires no special conditions to trigger the divergent error path, likelihood is Medium — matching the source advisory's Medium severity rating.

### Recommendation
Return a single, generic error (e.g., "invalid email or password") from `SessionsController.Create` regardless of whether the email or password check failed, and avoid forwarding authenticator-internal error text to the client for any of the three authenticators (local, LDAP, OIDC). Continue to log the specific reason server-side (audit logs already capture `AuthLoginFailedEmail` vs `AuthLoginFailedPassword` distinctly for internal telemetry) while collapsing the client-visible message.

### Proof of Concept
1. `POST /sessions` with `{"email":"nonexistent@example.com","password":"anything"}` → response contains "Invalid email" (or equivalent) text sourced from `core/sessions/localauth/orm.go:156`.
2. `POST /sessions` with `{"email":"<known-or-guessed-valid-email>","password":"wrong"}` → response contains "Invalid password" text sourced from `core/sessions/localauth/orm.go:161`.
3. Diffing these two responses across a wordlist of candidate emails lets an attacker determine which emails are registered node users, without needing valid credentials.

func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}
