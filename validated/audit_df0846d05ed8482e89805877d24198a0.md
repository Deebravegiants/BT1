### Title
Webhook `shop` identity is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds the HMAC signature only to the raw request body, while the `shop` (tenant) field consumed by the app's `WebhookHandler` is read straight from an unauthenticated HTTP header. An unprivileged internet user who has access to any single, genuinely-signed webhook payload (e.g., because they operate their own shop with the app installed and legitimately receive webhooks from Shopify) can replay that payload to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a different, victim shop. The HMAC check still passes because it never inspects the shop header, so the gem hands the handler a `WebhookMetadata` claiming the victim's shop while the body content actually belongs to the attacker's own shop.

### Finding Description
`Registry.process` is the sole gate before a webhook's body is delivered to app code:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

`Utils::HmacValidator.validate` computes and compares the signature against `verifiable_query.to_signable_string`:

```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [5](#0-4) 

For a webhook `Request`, `to_signable_string` is defined as only the raw body, and every other field — including `shop`, `topic`, `webhook_id`, and `api_version` — is parsed from HTTP headers that are never fed into the signature:

```ruby
def to_signable_string
  @raw_body
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [6](#0-5) 

This breaks the intended identity binding `shop header == shop cryptographically bound to body`. Because `hmac(secret, body)` is independent of the `shop` header, any request whose `(body, hmac)` pair was legitimately produced by Shopify for one shop remains valid when replayed with a different `shop-domain` header. Since Shopify sends genuine, correctly-signed webhooks to any shop that installs the app — including a shop the attacker fully controls — the attacker can capture one of their own real webhook deliveries and resend it to the app's public webhook endpoint with the header swapped to a victim shop's domain. `HmacValidator.validate` will report the request as valid, and `Registry.process` will call `handler.handle` with `WebhookMetadata#shop` set to the victim's domain while `body` is actually the attacker's own shop's data.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented/intended by this gem) to select which tenant's session/store the webhook body should be applied to — the common pattern for multi-tenant Shopify apps — this allows a low-privileged, unauthenticated-relative-to-other-tenants attacker (any merchant who installs the app) to inject attacker-controlled webhook content that is attributed to an arbitrary victim shop by domain name alone. This is a cross-tenant data-integrity/authentication issue: the gem is asserting an identity (`shop`) it never actually verified, and downstream app logic that trusts this gem's verification will act on forged tenant identity.

### Likelihood Explanation
The attack requires no secrets, no access token, and no privileged account — only that the attacker install the app on a shop they control (the normal, unprivileged path for any Shopify merchant) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint, which by design is internet-reachable. Capturing a legitimate `(body, hmac)` pair from one's own shop and replaying it with a different `shop-domain` header is trivial and requires no cryptographic material.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) as part of the value bound by the HMAC verification, or independently cross-check `request.shop` against the shop associated with the offline session/access token that this specific webhook subscription was registered under before invoking `handler.handle`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be used by host apps as a trusted tenant identifier without additional verification.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; Shopify delivers a legitimate webhook with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Capture `B` and `H`.
3. Send a new HTTP request to the app's webhook endpoint with the identical raw body `B` and header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` builds a `Webhooks::Request` from these headers/body; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` which equals `H`, so validation passes.
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, causing the app to process attacker-controlled content as if it were sent by the victim's shop.
