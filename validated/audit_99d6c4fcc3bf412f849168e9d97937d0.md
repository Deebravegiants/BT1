## Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (i.e. `shop-domain`), `topic`, `api_version`, and `webhook_id` fields are read straight from unauthenticated HTTP headers and passed on to the registered webhook handler. Because the identity of the tenant (`shop`) is never bound into the HMAC digest, an attacker who can obtain one legitimately-signed webhook body (e.g. by triggering a webhook on their own development/trial store) can replay that exact body to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. The signature still validates, and the application processes the payload as if it belonged to the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled directly out of request headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` verifies only the body's HMAC and then trusts `request.shop` (and the other header-derived fields) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms only that `computed_signature` (over `to_signable_string`, i.e. the body) matches the received signature — it never touches the `shop-domain` header: [4](#0-3) 

The broken identity binding, stated as an equality that fails to hold:
`shop_authenticated_by_hmac == shop_used_by_handler` is **false** — the HMAC authenticates `(secret, raw_body)`, while `WebhookMetadata.shop` is populated from the caller-controlled `shop-domain` header, which is completely outside the HMAC computation.

### Impact Explanation
An unprivileged internet user who can install the app on their own store (a normal, unprivileged tenant onboarding flow) can trigger a legitimate webhook for their own shop, capture the `(raw_body, x-shopify-hmac-sha256)` pair, and replay it against the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate(request)` still returns `true` because the digest only depends on `raw_body` and the shared secret, both of which are correct/valid, and the `shop` field forwarded to the handler is the attacker-controlled header value. Any host application that uses this library's `WebhookMetadata#shop` to determine which tenant's data/session to mutate (the intended purpose of this field, and the standard pattern documented for consumers of this gem) will apply the replayed payload to the victim tenant's context — enabling cross-tenant data injection/corruption without ever possessing the victim's credentials. This satisfies the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic: obtaining a validly-signed webhook body only requires becoming an ordinary (unprivileged) merchant/installer of the target app — no special access, leaked secrets, or social engineering is required. Constructing and sending an HTTP POST with a forged `shop-domain` header to the app's public webhook route requires no privileges either, since this is exactly the boundary the host application relies on this gem to protect.

### Recommendation
Bind the tenant identity into the authenticated material, or independently verify it out-of-band before trusting it:
- Reject/flag replayed webhooks by tracking `webhook_id` (already extracted) per shop and rejecting duplicates/mismatches, and/or
- Cross-check that the `shop-domain` header's shop matches a shop known to have an active session/installation before dispatching to handlers, and
- Document/enforce that consuming applications must not rely solely on `WebhookMetadata#shop` from unauthenticated headers without an additional installation-state check, since this gem provides no cryptographic guarantee that the header matches the HMAC-signed body's origin.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the POST body `B` and header `x-shopify-hmac-sha256: H` sent by Shopify (this is a fully legitimate signature computed by Shopify with the app's real secret).
2. Attacker sends a new POST to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim.myshopify.com` (rewritten)
   - Header `x-shopify-topic`, `x-shopify-webhook-id` unchanged or attacker-chosen.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `B` — see [1](#0-0)  and [5](#0-4) .
4. `WebhookMetadata.new(... shop: request.shop ...)` is constructed with `shop == "victim.myshopify.com"` and passed to the app's handler, even though the payload actually originated from, and was only ever signed for, `attacker.myshopify.com` — see [3](#0-2) .
