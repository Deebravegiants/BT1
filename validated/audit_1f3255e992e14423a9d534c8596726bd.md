### Title
Webhook `shop` (and `topic`, `webhook_id`, `api_version`) headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `Registry.process` trusts `request.shop` (and other headers) to identify the tenant. An attacker who can obtain any one validly-signed webhook body/HMAC pair (trivial to do by installing the target app on their own store, since public app installation requires no privileged credential) can replay that exact body+HMAC while swapping the `x-shopify-shop-domain` header to a victim shop. `Utils::HmacValidator.validate` will still report success because the signature only ever covered the JSON body, never the shop header, breaking the intended binding `hmac == HMAC(secret, body_bytes_and_shop)`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only the raw body is included, and `hmac` computed by Shopify covers only the raw body as well: [2](#0-1) 

`Registry.process` verifies this HMAC, then unconditionally trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`, none of which participate in the signature: [3](#0-2) 

`request.shop` itself is read straight from the `shop-domain` header with no cross-check against the signed payload: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body ∥ shop)` (or the shop being otherwise authenticated), but the actual binding enforced is only `hmac == HMAC(secret, body)`. This is exactly the "field acted on but not covered by the HMAC" bug class: `shop` is consumed by the handler (`WebhookMetadata.new(... shop: request.shop ...)`) yet is entirely outside the cryptographic envelope.

### Impact Explanation
An unprivileged internet actor who has legitimately installed the target app on their own (attacker-controlled) shop will receive real webhooks with valid `hmac-sha256` signatures for that shop's body content. Because the header carrying the tenant identity (`x-shopify-shop-domain`) is not part of the signed material, the attacker can resend the identical body/HMAC pair to the app's public webhook endpoint with the `shop-domain` header rewritten to any victim shop domain. `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` dispatches the handler believing the event (and its body-derived side effects, e.g. order/customer data) belongs to the victim shop. Any app logic that uses `WebhookMetadata#shop` to select which tenant's records to create/update/delete is now operating cross-tenant using attacker-controlled data — this is a cross-tenant access / data-integrity break attributable to the gem's HMAC binding.

### Likelihood Explanation
Likelihood is high for any app: the only prerequisite is the ability to install the target app once as an unprivileged merchant, capture one webhook delivery (raw body + `x-shopify-hmac-sha256` + topic), and replay it with a modified `shop-domain` header to the app's public webhook route. No access token, `client_secret`, or privileged account is required — this satisfies the "unprivileged internet user" constraint.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value verified against the HMAC, or otherwise cryptographically/out-of-band bind the `shop-domain` header to the specific signed delivery (e.g., look up the shop's own secret/session rather than trusting the unauthenticated header value) before using `request.shop` for tenant resolution. At minimum, document that `request.shop` is not authenticated by the HMAC and must be independently verified/looked up by callers before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering Shopify to send a real webhook, e.g. `orders/create`, to the app's public webhook endpoint with body `B` and header `x-shopify-hmac-sha256: H` (valid for `B`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures `B` and `H`.
3. Attacker crafts a new HTTP POST to the same public webhook endpoint with identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` computes `HMAC(secret, B)` (via `Request#to_signable_string` returning only `@raw_body`) which still equals `H`, so validation succeeds: [5](#0-4) 
5. `Registry.process` dispatches the handler with `shop: request.shop` = `"victim.myshopify.com"` and the attacker-controlled body `B`, causing the host application to process attacker data under the victim tenant's identity: [6](#0-5)
