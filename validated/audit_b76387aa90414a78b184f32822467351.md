### Title
Emporium wallet-signature does not bind `feeStructure.feeToken`, allowing fee to be charged in an unauthorized asset - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.verifyWallet` validates an EIP-712 signature from a smart-wallet owner (`stack.signerAddress`) that is supposed to authorize a batch of wallet operations paid for through the relay-fee mechanism. The signed payload only commits to `emporiumMessage`, the hash of `stack.ops`, `maxFee`, and `deadline`. It does **not** commit to `circomData.feeStructure.feeToken` (or to `erc20TokenAddresses`/`deltaAmountChanges`), even though `feeStructure.feeToken` determines which ERC-20 the wallet is drained of when paying the relay.

### Finding Description
`verifyWallet` builds the signed hash as: [1](#0-0) 

The only fee-related check performed against the signature is a raw numeric comparison of `flatFee` to `maxFee`, with no linkage to which token that fee is denominated in: [2](#0-1) 

When `signerAddress != address(0)`, `payRelayFees` pays the relay directly out of the signer's wallet using whichever `erc20TokenAddress` happens to match `feeStructure.feeToken` in `circomData.erc20TokenAddresses`: [3](#0-2) [4](#0-3) 

Whoever assembles `circomData` and the accompanying ZK proof (the tx submitter, not necessarily the wallet owner) fully controls `feeStructure.feeToken` and `erc20TokenAddresses`. Because `feeStructure` is only bound into `circomData.calldataHash` (a value the submitter itself computes from its own chosen witness — no secret knowledge is required to keep the hash self-consistent), the ZK proof does not tie `feeStructure.feeToken` to anything the wallet owner actually approved: [5](#0-4) 

The `maxFee` bound the owner did sign is a bare numeric value with no unit/token context, so `flatFee <= maxFee` provides no real economic protection once the token is swapped for a more valuable one. As a result, the equality the signature is supposed to enforce — "the wallet only pays what its owner authorized" — is broken: the submitter, not the signer, chooses the asset actually debited from the wallet via `doSendToRelay`.

### Impact Explanation
This allows an unprivileged transaction submitter to cause the smart wallet to pay the relay fee in a token of the attacker's choosing (e.g., a high-value token the wallet holds) while the numeric `flatFee` value stays under the owner-approved `maxFee` ceiling. This is an unauthorized asset movement from the wallet — funds are moved through a wallet operation the signer never approved for that specific asset — matching the "executing calls or moving assets a wallet owner ... never authorised" High-impact category.

### Likelihood Explanation
Likelihood is moderate: it requires the invokeWallet/Emporium signature flow to be used (`stack.signerAddress != address(0)`) and the target wallet to hold multiple ERC-20 balances of differing value, but no privileged role, relayer trust, or admin key is needed — any party that can submit `Hinkal.transact()` with a self-consistent `circomData`/proof can exploit it.

### Recommendation
Include `feeStructure.feeToken` (and ideally the full `feeStructure`, or the exact fee amount in a specific token) inside the EIP-712 `EMPORIUM_SIGNATURE_TYPEHASH` payload that the wallet owner signs, so the signature deterministically commits to which asset and how much of it can be withdrawn as a relay fee, rather than relying on an unbound numeric `maxFee` comparison.

### Proof of Concept
1. Wallet owner signs an Emporium operation batch with `maxFee = 10` (intending 10 units of, e.g., USDC) and `deadline`.
2. A malicious submitter builds `circomData` with `feeStructure.feeToken` set to a high-value token the wallet holds (e.g., WETH) and `feeStructure.flatFee = 10`, generates a self-consistent `calldataHash`/proof (no secret knowledge required for this value), and calls `Hinkal.transact()`.
3. `verifyWallet` succeeds because the signature never checked `feeToken`; `payRelayFees` -> `sendToRelayFromWallet` -> `IHinkalWallet.doSendToRelay` debits 10 WETH from the wallet to the relay instead of the ~10 USDC the owner intended, resulting in an unauthorized, far larger value transfer out of the wallet.

Note: I could not inspect the `IHinkalWallet` implementation (e.g., `doSendToRelay`) since it was not returned by the tools available; if that contract independently validates the fee token against signer intent, this would mitigate the issue, but nothing in the reviewed `EmporiumUpgradeable.sol`/`CircomDataBuilder.sol` code performs that check.
