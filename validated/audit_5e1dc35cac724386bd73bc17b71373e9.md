### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable content solely from the raw request body, while the `shop` (tenant) identity used by the handler is taken from an unauthenticated HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identifier passed to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the signed body: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` only ever verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. against the raw body — it never touches `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` calls the HMAC validator and, once it returns true, immediately builds `WebhookMetadata` using `request.shop` as the tenant identity handed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `{shop identity used by handler}` == `{shop identity covered by the HMAC}`. Because `shop` is excluded from `to_signable_string`, this equality does not hold — the HMAC only binds `body`, not `body ∧ shop`.

Since Shopify apps share a single `api_secret_key` across every installed shop, any tenant that has legitimately installed the app can obtain a valid `(raw_body, hmac)` pair for their own shop's webhook deliveries (e.g., from `orders/create` or any event they can trigger in their own store). That pair remains cryptographically valid for the exact same body regardless of which `shop-domain` header accompanies it, because the header is never part of the signed content.

### Impact Explanation
An attacker who controls one legitimate shop installation of a multi-tenant app can replay a validly-signed webhook body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `Registry.process` will validate the HMAC (since it only checks the body), then dispatch `WebhookMetadata` claiming the payload originated from the victim shop. If the host application uses `data.shop` to select which tenant's session/records to update (the intended and documented use of `WebhookMetadata#shop`), the attacker can inject their own controlled payload as if it came from the victim's store — a cross-tenant data integrity/confusion issue.

### Likelihood Explanation
Exploitation requires only an app installation the attacker controls (a normal, unprivileged capability for any merchant who installs a public app) — no access token, `client_secret`, or privileged account is needed. The attacker simply triggers/receives a webhook to their own store to obtain a valid signature and body, then re-POSTs it to the shared webhook endpoint with a modified shop header.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the signable content used by `to_signable_string`, or otherwise cryptographically bind the shop domain to the payload before trusting it (e.g., cross-check `request.shop` against a previously known/installed shop record before invoking the handler, in addition to the raw HMAC check).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) with a body they fully control.
2. Attacker's server receives the real webhook with headers `x-shopify-hmac-sha256: <valid-hmac-for-body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker re-sends the exact same raw body and HMAC header to the app's webhook endpoint, but rewrites `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate`, which passes because it only checks `@raw_body` against the HMAC — unaffected by the header change.
5. The app's registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, processing it as authentic data for the victim tenant.
