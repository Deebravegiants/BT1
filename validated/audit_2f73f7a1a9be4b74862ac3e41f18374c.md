### Title
Webhook `shop` attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the HMAC over the raw request body only, while the `shop` (tenant) attribution comes from an unauthenticated HTTP header that is never included in the signed bytes. This mirrors the report's bug class ("a field acted on but not covered by the HMAC"): the host application receives a cryptographically valid webhook whose *tenant identity* was never actually verified, letting any shop that has the app installed relabel its own legitimately-signed webhook payload as belonging to a different (victim) shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`Webhooks::Request#shop` is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header, with no format validation and, critically, no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (i.e., the raw body) against the app's shared `client_secret`: [3](#0-2) 

`Webhooks::Registry.process` validates that HMAC and then immediately forwards `request.shop` — the unauthenticated header value — to the app's handler as the tenant identifier, with no further check that it matches the body's true origin: [4](#0-3) 

The identity binding that should hold is:
`verified(body, client_secret) == true` **⇒** `shop` used by the handler is the shop that generated `body`.

In this gem, that equality does not hold: the HMAC secret (`client_secret`) is shared across **every shop that installs the app**, not scoped per shop, and the `shop` header sits entirely outside the signed content. Any unprivileged actor who controls (or has legitimately installed the app on) shop A can:
1. Capture/observe a validly-signed webhook body+HMAC for shop A (trivial — they can trigger webhooks themselves, e.g., by updating one of their own products/orders).
2. Replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with shop B's domain (the "good" tenant).
3. `HmacValidator.validate` still returns `true` (same body, same shared secret), and `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: "shop-b.myshopify.com", body: <attacker's data>, ...)`.

The host application, trusting that a validated webhook implies the `shop` field is authentic, will process attacker-controlled data under the identity of a different merchant/tenant.

### Impact Explanation
This breaks the tenant/shop boundary that host applications rely on when the gem tells them "this webhook, verified via HMAC, belongs to shop X." It enables cross-tenant data injection/confusion: an attacker with access to any single shop (installed app) can cause the application to attribute arbitrary attacker-chosen payload data (order data, product data, GDPR/customer data payloads, app-uninstall notifications, etc.) to an unrelated victim shop, since the gem exposes no verified linkage between the cryptographically-validated bytes and the claimed `shop`. This matches the "cross-tenant access" impact category, since the shop identity used for authorization/data-routing decisions downstream is forged despite passing this gem's own HMAC check.

### Likelihood Explanation
High reachability: webhook endpoints are public HTTP endpoints by design, and any actor can install the app on a shop they control (a normal, unprivileged action) to obtain a validly HMAC-signed body for a chosen payload/topic, then forge the `shop-domain` header when POSTing to the app's webhook route. No `api_secret_key`, access token, or leaked credential is required — the shared secret is only needed by Shopify's servers to compute the original signature, and the attacker reuses that exact untouched body/signature pair, only forging the out-of-band header.

### Recommendation
Include the `shop` (and ideally `topic`, `api-version`, `webhook-id`) values in the bytes that are HMAC-verified, or otherwise cryptographically bind them (e.g., require the host application to independently confirm the shop is one it has an active session/installation record for before trusting `WebhookMetadata#shop`), so that `Utils::HmacValidator.validate` fails whenever the claimed shop does not match the shop that actually produced the signed payload.

### Proof of Concept
```ruby
# Attacker controls shop "attacker-shop.myshopify.com" and has installed the app.
# Shopify sends the attacker a legitimately signed webhook for their own shop:
raw_body = '{"id":1,"note":"legit payload from attacker'\''s own shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker now replays the exact same body/HMAC, but swaps the shop header to the victim's domain:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),   # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...))
# The host app now processes attacker-controlled data as if it belongs to "victim-shop.myshopify.com".
```
