## Title
`SessionUtils.offline_session_id` / `cookie_session_id` accept unauthenticated cookie bytes as an authoritative shop identity, colliding with the JWT-derived identity format - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`SessionUtils.offline_session_id(shop)` is a bare `"offline_#{shop}"` string interpolation with no signature, MAC, or randomness, and `cookie_session_id` returns the raw, attacker-controlled cookie value verbatim as the session id with zero verification. Because both the JWT-authenticated path and the unauthenticated cookie path produce identically-formatted strings, an attacker who knows or guesses a victim's `shop` domain can set their own cookie to the exact string a real JWT-derived offline session would use, and any downstream session store that keys off this id treats the forged value as if it came from a verified source.

### Finding Description
The claimed binding is: `session_id == f(authenticated_shop_claim)` for every code path that reaches `current_session_id`. In reality:

- In the embedded+JWT branch, `session_id_from_shopify_id_token` extracts `shop` from a cryptographically verified `Auth::JwtPayload` and calls `offline_session_id(shop)` / `jwt_session_id(shop, sub)`: [1](#0-0) 
- `offline_session_id` itself performs no MAC/signature check at all — it is a pure string template: [2](#0-1) 
- In the non-embedded branch (and in the embedded branch when no `shopify_id_token` is supplied), `cookie_session_id` returns the cookie's value untouched, with no shop binding, no HMAC, no signature: [3](#0-2) [4](#0-3) 

Because `offline_session_id(shop)` and the raw cookie value share the exact same string space (`"offline_#{shop}"`), and shop domains are public/discoverable information (they appear in storefront URLs, JWT `iss`/`dest` claims, webhook payloads, etc.), an attacker can send a request with `Cookie: shopify_app_session=offline_<victim>.myshopify.com` (or `<victim>.myshopify.com_<user_id>` for the online variant, matching `jwt_session_id`'s format at `lib/shopify_api/utils/session_utils.rb:58-61`) and `current_session_id` will hand back that exact string as "the session id" with no indication to the caller that it was never cryptographically verified.

The root cause is that this session-id scheme carries **no unpredictable/secret component of its own** — it is 100% a deterministic function of already-public data (`shop`, and for online sessions a `user_id` that's also often discoverable). A cookie-based bearer identifier with no server-issued randomness or MAC is not distinguishable from a value an attacker invents themselves. Existing guards do not intervene here: `HmacValidator.validate` and `ShopValidator.sanitize!` are only invoked in the OAuth callback flow (`lib/shopify_api/auth/oauth.rb:60-71`), not in `current_session_id`/`cookie_session_id`; `Auth::JwtPayload`'s `aud` check only applies when an actual JWT is present, and the cookie fallback path in `current_session_id` bypasses it entirely by design; Sorbet typing only enforces `String`, not provenance.

Downstream, per the docs, this returned id is the literal lookup key applications (e.g. the `shopify_app` gem) use to fetch the stored `Session` (including `access_token`) from their session storage: [5](#0-4) . The OAuth callback itself sets the browser cookie to this same deterministic value with no additional entropy: `cookie.value = session.id` where `session.id` for offline sessions is `"offline_#{shop}"`: [6](#0-5)  and [7](#0-6) .

### Impact Explanation
If a host application (following this gem's documented pattern) stores sessions keyed by the id returned from `current_session_id`/`offline_session_id`, an attacker who supplies a forged cookie of the deterministic, publicly-derivable form receives that victim's stored session object, including their `access_token`, on lookup — full cross-tenant access to read or mutate another merchant's data. This is repeatable against any shop whose domain the attacker can learn (myshopify.com domains are commonly public via storefronts, app listings, or JWT claims observed in the attacker's own installs), and scales to every merchant using the affected app, so the blast radius spans the whole multi-tenant app population. This matches Critical - cross-tenant access.

### Likelihood Explanation
Preconditions: the app must have previously completed OAuth for the victim shop (so a session exists to be looked up), and the host app's session storage must trust `current_session_id`'s output as an authoritative key without further authentication — this is exactly the pattern the gem's own docs recommend (`docs/getting_started.md`, `docs/usage/oauth.md`). The attacker's cost is trivial: they only need to know/guess the victim's `myshopify.com` domain and craft one HTTP request with a custom `Cookie` header; no secrets, no MITM, no XSS is required since the attacker fully controls the cookies on requests they themselves send. This is directly repeatable against arbitrary victim shops.

### Recommendation
Do not use a purely deterministic string derived from public data (`shop`, `user_id`) as the sole bearer credential for cookie-based session lookup. Either (a) bind the cookie value to a cryptographically random, server-issued session identifier (as is standard practice for session cookies) so the shop/user mapping is never inferable from the identifier itself, or (b) sign/MAC the returned session id (e.g., HMAC over `shop`/`user_id` with `api_secret_key`) and verify that MAC in `cookie_session_id` before treating the cookie value as trusted, rejecting any value that fails verification.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_forged_cookie_matches_deterministic_offline_session_id_format
  ShopifyAPI::Context.stubs(:embedded?).returns(false)

  victim_shop = "victim-shop.myshopify.com"
  forged_cookie_value = "offline_#{victim_shop}" # attacker-guessed, no server secret involved
  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value }

  # Binding under test: session_id should only equal offline_session_id(shop)
  # when shop was derived from a verified source (JWT), never from a raw client cookie.
  returned_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  # This assertion demonstrates the violation: the unauthenticated cookie value
  # is returned identically to what a verified JWT flow would produce.
  assert_equal(
    ShopifyAPI::Utils::SessionUtils.offline_session_id(victim_shop),
    returned_id,
  )
end
```
This shows `current_session_id` returns the exact same value for an attacker-forged cookie as it would for a legitimately JWT-verified offline session, with no marker distinguishing provenance — confirming that any consumer keying session storage off this id cannot tell an authenticated identity from a forged one.

        def session_id_from_shopify_id_token(id_token:, online:)
          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end
        end

        sig { params(shop: String, access_token_response: Oauth::AccessTokenResponse).returns(Session) }
        def from(shop:, access_token_response:)
          is_online = access_token_response.online_token?

          if is_online
            associated_user = T.must(access_token_response.associated_user)
            associated_user_scope = access_token_response.associated_user_scope
            id = "#{shop}_#{associated_user.id}"
          else
            id = "offline_#{shop}"
          end

          if access_token_response.expires_in
            expires = Time.now + access_token_response.expires_in.to_i
          end

          if access_token_response.refresh_token_expires_in
            refresh_token_expires = Time.now + access_token_response.refresh_token_expires_in.to_i
          end

          new(
            id: id,
            shop: shop,
            access_token: access_token_response.access_token,
            scope: access_token_response.scope,
            is_online: is_online,
            associated_user_scope: associated_user_scope,
            associated_user: associated_user,
            expires: expires,
            shopify_session_id: access_token_response.session,
            refresh_token: access_token_response.refresh_token,
            refresh_token_expires: refresh_token_expires,
