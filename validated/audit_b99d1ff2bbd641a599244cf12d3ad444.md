### Title
Unvalidated JWT `dest` claim used to route the OAuth token-exchange request that carries the app's `client_secret` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, the shop host used to send the app's `client_id`/`client_secret` is taken directly from the JWT's `dest` claim (`jwt_payload.shop`) with no domain validation, unlike the sibling method `migrate_to_expiring_token` in the same file, which explicitly runs the shop through `Utils::ShopValidator.sanitize!` before using it. This breaks the equality that should hold everywhere else in the gem: `shop used to build the request host == shop validated as a trusted Shopify domain`.

### Finding Description
`JwtPayload#shop` simply strips the scheme off the `dest` claim with no further constraints: [1](#0-0) 

The only validation performed on the token is that `aud == Context.api_key`; `dest` is never checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`), nor is it checked for consistency against `iss`: [2](#0-1) 

`exchange_token` then takes this unvalidated value and uses it directly to construct the `Session` (and therefore the request host) that receives the OAuth token-exchange POST containing `client_id` and `client_secret`: [3](#0-2) 

`Clients::HttpClient` builds the request URL straight from `session.shop`: [4](#0-3) 

Compare this with `migrate_to_expiring_token` in the very same module, which sanitizes the shop before using it in an identical HTTP request pattern: [5](#0-4) 

and with `client_credentials`, which likewise sanitizes the shop before sending `client_secret`: [6](#0-5) 

This is precisely the "field acted on but not covered by the equivalent binding check" pattern from the bug-class hint: in the reference report, a downstream value (`follows_price_after_wrapper_fees`) was used in a calculation instead of the value that was actually meant to represent trust (`follows_price`); here, a downstream value (`dest`, taken from an unvalidated JWT claim) is used to pick the destination host for a credential-bearing request instead of the value the rest of the codebase treats as trusted (`ShopValidator.sanitize!`-approved shop).

### Impact Explanation
If the `dest` claim can ever diverge from a genuine, trustworthy Shopify domain — including via any HS256 key confusion, misconfigured `old_api_secret_key` fallback, or any host application that passes through attacker-influenced session tokens without additional checks — `exchange_token` will POST the app's `client_id` and `client_secret` to that host. That is a High-severity SSRF-with-credentials primitive: the app's OAuth `client_secret` (a long-lived, high-value credential) would be exfiltrated to an attacker-controlled endpoint. This exactly matches the "SSRF with the app's credentials" and "credential leakage" impact categories in scope.

### Likelihood Explanation
Exploitability is bounded by the fact that `JWT.decode` in `decode_token` enforces HS256 signature verification using `Context.api_secret_key` (and optionally `old_api_secret_key`), so a token with an attacker-chosen `dest` cannot be forged without knowledge of one of those secrets under normal operation: [7](#0-6) 

This makes the issue primarily a defense-in-depth gap rather than a directly demonstrable end-to-end exploit purely from an unprivileged internet position — I could not find a code path in this gem where an unauthenticated user supplies or influences the `dest` value without already possessing a validly-signed session token. The inconsistency with `migrate_to_expiring_token`/`client_credentials` (which both sanitize the shop) strongly suggests this validation was intentionally required elsewhere and was simply omitted here, but I could not fully verify from the indexed files whether any other code path (e.g., a proxy, a rotated/old secret, or host-application misuse) could inject an untrusted `dest` value into a token that still passes signature verification.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, validate `jwt_payload.shop` (the `dest` claim) with `Utils::ShopValidator.sanitize!` before constructing `shop_session`/`Session.from`, matching the pattern already used in `migrate_to_expiring_token` and `client_credentials`. This ensures the shop used to route the `client_secret`-bearing request is always confirmed to be a trusted Shopify domain, regardless of what is embedded in the JWT `dest` claim.

### Proof of Concept
Could not construct a concrete unprivileged end-to-end PoC purely within this gem, because forging a `dest` value requires bypassing or possessing the HS256 signing secret (`api_secret_key`/`old_api_secret_key`), which is out of scope per the rules (requires `api_secret_key`/leaked credentials). The finding is reported as a root-cause/structural inconsistency (missing `ShopValidator.sanitize!` call) rather than a demonstrated exploit chain; a background Devin session with the full repo and any host-application integration could further verify whether any reachable path allows an untrusted `dest` to reach `exchange_token` with a token that still passes signature verification.
