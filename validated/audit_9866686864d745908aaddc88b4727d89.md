This is a confirmed, documented limitation directly in the code — not a hidden bug.

### Title
`findMatchingWithdrawal` matches by `assetId` only, so `describeWithdrawal` can return the wrong record's `txHash`/status for one of multiple same-asset withdrawals in an intent - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which selects the first API record whose `nep141:${near_token_id}` equals the requested `assetId`, ignoring `amount`, `destinationAddress`, and `index` entirely. If an intent contains two withdrawals of the same `assetId` (e.g. 100000n at index 0 and 50000n at index 1), and the indexer returns both COMPLETED records in an order that doesn't correspond to intent order, `describeWithdrawal({index:0})` can return the `txHash` belonging to the record actually settling 50000n, not 100000n.

### Finding Description
The equality the SDK implicitly relies on is: "the withdrawal record returned for `index i` corresponds to the withdrawal that was requested at `index i`." The code only checks `nep141:${w.data.near_token_id} === assetId` [1](#0-0) , with no comparison of `amount`, `destinationAddress`, or the requested `index` against `w.data`. Both `describeWithdrawal` calls for index 0 and index 1 would call `getWithdrawalStatusWithRetry` with the same `args.tx.hash` (both withdrawals are part of the same NEAR transaction) [2](#0-1) , so both calls receive the identical unsorted `response.withdrawals` array containing both COMPLETED records, and `Array.prototype.find` returns whichever record appears first in the array — regardless of which index the caller actually asked about. Consequently, `describeWithdrawal({index:0})` can return `txHash` from the record whose settled `amount` was 50000n, while the caller signed/expects 100000n for index 0.

This is explicitly acknowledged as a known, unhandled limitation in the code comment directly above the function: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported. POA API doesn't currently support this case either." [3](#0-2) 

No other guard intervenes: `validateWithdrawal`, `supports()`, `FeeExceedsAmountError`, and `getUnderlyingFee` operate at withdrawal-creation/fee-estimation time, not at status-reporting time, and none of them compare per-record amounts during `describeWithdrawal`.

### Impact Explanation
`describeWithdrawal` is the SDK's authoritative status-reporting function; an integrator calling it for index 0 gets back `{status: "completed", txHash}` sourced from a record that may actually correspond to a different withdrawal amount. This causes the integrator to associate/credit a `txHash` (and by extension, an on-chain settled amount) against the wrong withdrawal id — a status/hash misreport that can lead an integrator to credit the wrong amount to the wrong withdrawal. This matches the High severity category: "a status or hash misreport making an integrator credit or refund twice" (here, credit against the wrong id). It's repeatable for any intent submitted with two-or-more same-`assetId` withdrawals, and this is inherent to the current matching logic, not a one-off race.

### Likelihood Explanation
Preconditions: an ordinary user (or integrator on the user's behalf) submits a single intent containing two withdrawals of the same `assetId` to the same or different `destinationAddress`, with different `amount`s — a normal use case, not requiring any malicious relayer/indexer/admin. The only external dependency is that the POA indexer's `getWithdrawalStatus` response ordering doesn't match request-index ordering, which the code's own comment admits is expected/unhandled ("Response list is unsorted") [4](#0-3) . No special attacker cost; this arises just from normal multi-withdrawal intents.

### Recommendation
Extend `findMatchingWithdrawal` to disambiguate by `amount` (and `destinationAddress`/`destinationMemo` where available) in addition to `assetId`, or pass the intended `amount`/`destinationAddress` from `args.withdrawalParams` into the matcher and require an exact match on all of `assetId`, `amount`, and `destinationAddress` before returning a record; if multiple records still tie, track already-consumed records per `describeWithdrawal` call sequence (e.g., sort both withdrawal params and API results by `amount` as suggested in the existing comment) rather than returning the first `assetId` match.

```ts
it("must not attribute the wrong amount's txHash to index 0 when two same-asset withdrawals are unordered", async () => {
  const assetId = "nep141:zec.omft.near";
  vi.spyOn(poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({
    withdrawals: [
      { status: "COMPLETED", data: { near_token_id: "zec.omft.near", amount: "50000", transfer_tx_hash: "hash_for_50000" } },
      { status: "COMPLETED", data: { near_token_id: "zec.omft.near", amount: "100000", transfer_tx_hash: "hash_for_100000" } },
    ],
  });

  const bridge = new PoaBridge({ envConfig, xrplRpcUrls: [] });

  const resultIndex0 = await bridge.describeWithdrawal({
    index: 0,
    landingChain: Chains.Zcash,
    tx: { hash: "sharedTxHash", accountId: "x" },
    withdrawalParams: { assetId, amount: 100000n, destinationAddress: "addr" } as WithdrawalParams,
  });

  // Broken equality under test:
  // resultIndex0.txHash should correspond to the record whose data.amount === "100000"
  // (the amount actually requested at index 0), not whichever record appears first.
  expect(resultIndex0).toEqual({ status: "completed", txHash: "hash_for_100000" });
  // Current implementation returns "hash_for_50000" because it matches array order, not amount -> test fails.
});
```

```typescript
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
