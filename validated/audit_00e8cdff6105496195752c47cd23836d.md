## Title
Governance can change `surplusShareBps` after orders are placed and capture surplus that was owed to the beneficiary - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The IntentGatewayV2 splits any solver overpayment ("surplus") between the protocol and the order's beneficiary using `_params.surplusShareBps`. Unlike the protocol fee (`protocolFeeBps`), which is read once at `placeOrder` and baked into the order commitment hash, `surplusShareBps` is read live from mutable storage at fill time via `_splitSurplus`. Governance can update `surplusShareBps` at any time up to 100% through `_updateParams`, and that new value applies immediately to every order that was placed under the old split, letting the protocol capture surplus that solvers and beneficiaries expected to share under the original terms — the same "mutable fee rate applied at settlement instead of commitment" bug class as the Cally `feeRate` finding.

### Finding Description
`_splitSurplus` computes the protocol/beneficiary split using the *current* `_params.surplusShareBps` at the moment a solver fills an order, not the value that existed when the order was placed: [1](#0-0) 

This value comes from the mutable `Params` struct, which can be replaced wholesale by governance through `_updateParams`, validated only to be `<= 10_000` (i.e., up to 100% to the protocol): [2](#0-1) 

`_splitSurplus` is invoked on every fill path — same-chain (`_fillSameChain`) and cross-chain (`_fillCrossChain`) — to divide a solver's overpayment between the beneficiary and the protocol: [3](#0-2) [4](#0-3) 

Contrast this with `protocolFeeBps`, which is deliberately read once at `placeOrder` and folded into `order.inputs` before the commitment hash is computed, so a later governance change cannot retroactively affect an already-placed order: [5](#0-4) 

The docs confirm this asymmetry explicitly — protocol/destination fees are charged "at order placement," but surplus share is applied "at fill time": [6](#0-5) 

Because `surplusShareBps` is not locked into the order commitment the way `protocolFeeBps` is, a governance update between order placement and fill changes the economic terms of an order the beneficiary already agreed to, exactly mirroring the referenced Cally bug where `feeRate` could be changed by the owner between vault creation and option exercise to consume value intended for the counterparty.

### Impact Explanation
An intent solver willing to overpay (intentionally, to win order flow, or via price movement) fills an order expecting the surplus to be split per the `surplusShareBps` in effect when the order was quoted/placed. If governance raises `surplusShareBps` to 10,000 (100%) before the fill lands, the entire surplus goes to the protocol instead of being shared with the beneficiary, silently reducing the value delivered to end users versus what was quoted (`quotePhantomFill`/`quoteIntent` price the split using the currently-read `surplusShareBps`, so any change after a quote is issued invalidates the quoted terms without the user's knowledge). This is a real, unbacked value transfer away from unprivileged order placers/beneficiaries and toward the protocol/governance, without any way for affected users to detect or opt out beforehand, since the parameter that governs their payout is mutable global state, not part of the immutable order they signed.

### Likelihood Explanation
Triggering the loss requires only a normal fill by any solver on a pending order combined with a permissionless-timing governance update; no attacker needs elevated access to the order itself — any solver's ordinary overpayment fill after a parameter change realizes the loss. Given that `surplusShareBps` updates arrive via the same governance channel already used for `protocolFeeBps`/destination fee updates (`_updateParams`), and no protections (timelock, per-order snapshot, or restriction) exist to prevent it from retroactively affecting orders placed under a prior rate, the issue is straightforward to trigger whenever governance is malicious or compromised — the same threat model the original Cally finding and its judge's remediation assumed.

### Recommendation
Snapshot `surplusShareBps` (and/or the full fee configuration relevant to settlement) into the order at `placeOrder` time, the same way `protocolFeeBps` is baked into `order.inputs` and the commitment hash, so that `_splitSurplus` at fill time uses the rate that was in effect — and disclosed to the user — when the order was created, rather than reading live mutable governance state.

### Proof of Concept
1. User places an order via `placeOrder` while `_params.surplusShareBps = 5000` (50/50 split), expecting any solver overpayment to be split evenly, per `_splitSurplus`: [7](#0-6) 
2. Before the order is filled, governance dispatches an `UpdateParams` request that is processed through `onAccept`/`_updateParams`, setting `surplusShareBps = 10_000`: [8](#0-7) 
3. A solver fills the order, overpaying the output as usual (e.g., for MEV/price-improvement reasons); `_fillSameChain`/`_fillCrossChain` call `_splitSurplus` with the new 100% rate, so `beneficiaryShare = 0` and the entire surplus is retained by the protocol as dust instead of the 50% the user expected when the order was placed: [3](#0-2) 
4. The existing test suite demonstrates the mechanics of this split (only with a static rate) — e.g. `testSameChainSwap_WithSurplus` shows the beneficiary receiving exactly `surplusShareBps`-determined proportions of surplus at fill time: [9](#0-8)  — replacing the fixed `SURPLUS_SHARE_BPS` with a value changed between `placeOrder` and `fillOrder` reproduces the loss of expected beneficiary surplus.

```text
    /// @dev Splits overpayment between protocol and beneficiary. An order with output calldata
    /// gives the beneficiary nothing, since the surplus is not the caller's to give.
    function _splitSurplus(uint256 dust, bool hasOutputCall)
        internal
        view
        returns (uint256 protocolShare, uint256 beneficiaryShare)
    {
        if (hasOutputCall) return (dust, 0);
        protocolShare = (dust * _params.surplusShareBps) / 10_000;
        beneficiaryShare = dust - protocolShare;
    }
```

```text
    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
```

```text
### Fees

| Fee | When | Who Pays |
|-----|------|----------|
| **Protocol fee** (`protocolFeeBps`) | At order placement | Deducted from user's input tokens |
| **Destination fee** | At order placement (per-destination override) | Deducted from user's input tokens |
| **Surplus share** (`surplusShareBps`) | At fill time, when solver provides more than requested | Split between protocol and beneficiary |
| **Fill fee** (`order.fees`) | At order placement | User (in fee token or native ETH) |
| **Relayer fee** | At fill time (cross-chain) or cancel time | Solver or user |

Protocol fees are retained as "dust" in the gateway and can be swept to a treasury via Hyperbridge governance. When a solver provides more tokens than required, the excess is split according to `surplusShareBps` (100% to protocol if the order has calldata). Surplus only applies on the first fill of each output token pair.
```
