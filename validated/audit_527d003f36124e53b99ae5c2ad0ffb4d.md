Confirmed: `Oauth.begin_auth` never calls `Utils::ShopValidator.sanitize!` on `shop` before constructing `auth_route`. `auth_base_uri` at [1](#0-0)  returns `"https://#{shop}/admin"` directly for any non-dev-server shop value, and `begin_auth` uses this unsanitized result to build the redirect at [2](#0-1) . `ShopValidator.sanitize!` exists in the codebase at [3](#0-2)  but is never invoked anywhere in `oauth.rb`.

### Title
Unvalidated `shop` parameter in `Oauth.begin_auth` produces attacker-controlled OAuth redirect host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`Oauth.begin_auth` builds the OAuth authorize redirect URL via `auth_base_uri(shop) + "/oauth/authorize?..."`, where `auth_base_uri` returns `"https://#{shop}/admin"` for any `shop` value not matching the dev-server special case, with no call to `Utils::ShopValidator.sanitize!` anywhere in the method. Since host apps are documented to pass the raw `shop` query parameter from an unauthenticated request into `begin_auth`, an attacker can force the app to redirect the merchant's browser (with `client_id`, `redirect_uri`, `state`, and `scope`) to an arbitrary attacker-controlled host.

### Finding Description
The broken binding is: `shop_used_as_redirect_host == Utils::ShopValidator.sanitize!(shop)`. Tracing the code: `begin_auth` (lib/shopify_api/auth/oauth.rb:22-52) takes `shop` as a plain `String` with no domain validation, computes `state`/`cookie`, then calls `auth_base_uri(shop)` (lines 117-128), which for any shop not containing `.my.shop.dev` returns `"https://#{shop}/admin"` literally — the raw attacker-supplied string is concatenated straight into the URI scheme+host position. This value is then concatenated with `/oauth/authorize?#{query_string}` and returned as `auth_route`, which the host app is expected to redirect the browser to. No guard in this call path — `Context.setup?`, `Context.private?`, `SecureRandom.alphanumeric` for `state` — restricts or validates `shop`'s format; `Utils::ShopValidator.sanitize!` is defined and used elsewhere (e.g. `TokenExchange`, `ClientCredentials`, `RefreshToken` per grep results) but is not called in `oauth.rb` at all. An attacker sends `GET /auth?shop=evil.com` to the host app, which (per documented usage) passes `shop: "evil.com"` into `begin_auth`; the returned `auth_route` becomes `https://evil.com/admin/oauth/authorize?client_id=...&redirect_uri=...&state=...`, and if the host app redirects there, the merchant's browser sends the app's `client_id`, `redirect_uri`, and freshly generated `state` nonce to the attacker's server.

### Impact Explanation
This is a forced OAuth completion / open redirect (SSRF-like redirect to an unintended host) that leaks `client_id`, `redirect_uri`, and the `state` nonce to an attacker-controlled server for any shop string the attacker chooses, and is repeatable against arbitrary victims since each request generates a fresh `state`/cookie pair sent to the attacker's chosen host. This matches the High severity category: forced OAuth completion driven by an unvalidated host in a security-relevant redirect.

### Likelihood Explanation
Preconditions are minimal: the host app must be a non-private app (`Context.private?` false, the default/documented mode) and must pass the raw `shop` query parameter to `begin_auth` as documented — which is exactly how the gem's own usage pattern is designed (accepting `shop` from an incoming `/auth` request). The attacker needs no credentials, only the ability to send an unauthenticated GET request with a crafted `shop` value, making this trivially and repeatably exploitable.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop, myshopify_domain: Context.host_name)` (or equivalent) at the top of `Oauth.begin_auth`, and use the sanitized/normalized shop domain — not the raw `shop` parameter — when constructing `auth_base_uri`, raising `Errors::InvalidShopError` for any shop that isn't a trusted Shopify domain.

### Proof of Concept
Add a test to `test/auth/oauth_test.rb` (not shown in repo excerpt, but following existing test conventions):
```ruby
def test_begin_auth_with_untrusted_shop_should_raise_or_not_redirect_to_attacker_host
  ShopifyAPI::Context.setup(
    api_key: "key", api_secret_key: "secret", host_name: "app-host.com",
    scope: "read_products", is_private: false, is_embedded: false, api_version: "2023-01",
  )
  result = ShopifyAPI::Auth::Oauth.begin_auth(shop: "evil.com", redirect_path: "/cb")
  refute_match(/^https:\/\/evil\.com/, result[:auth_route])
end
```
Currently this assertion fails: `result[:auth_route]` starts with `https://evil.com/admin/oauth/authorize?...`, confirming `shop_used_as_redirect_host` (`evil.com`) diverges from what `Utils::ShopValidator.sanitize!("evil.com")` would produce (raising `Errors::InvalidShopError` since `evil.com` is not in `TRUSTED_SHOPIFY_DOMAINS`), proving the redirect host is never validated against a trusted domain list.
