### Title
i128 overflow in RAY-scaled position valuation permanently freezes a market — every verb accrues first - (File: common/src/rates/simulate.rs)

### Summary
All pool mutations and even the read-only index projection run `accrue_step`, which values `borrowed` and `supplied` share balances as `shares × index` in RAY (`i128`). The borrow/supply indexes grow monotonically up to `MAX_BORROW_INDEX_RAY`/`MAX_SUPPLY_INDEX_RAY` = 10³⁶, but nothing bounds `shares × index` to the `i128` domain. Once `borrowed × borrow_index` or `supplied × supply_index` exceeds `i128::MAX`, `scaled_to_original` panics with `MathOverflow` inside the pre-mutation accrual, so `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, `claim_revenue`, and `update_indexes` all revert permanently for that market — an integer-overflow privilege-escalation analog (unprivileged depositors/borrowers permanently seize control of the market's liveness).

### Finding Description
- `accrue_step` (`common/src/rates/simulate.rs:60-61`) computes `scaled_to_original(env, borrowed, borrow_index)` and `scaled_to_original(env, supplied, supply_index)` before anything else.
- `scaled_to_original` (`common/src/rates/scaling.rs:14-16`) is `Ray::mul` → `fp_core::mul_div_half_up`, which uses an exact `I256` intermediate and panics with `GenericError::MathOverflow` when the result does not fit `i128` (`common/src/math/fp_core.rs:145-159`).
- `update_borrow_index` (`common/src/rates/index.rs:13-19`) multiplies `old_index × interest_factor` before clamping at 10³⁶; the index itself never overflows, but the derived *value* `borrowed × index` does at roughly `i128::MAX / index` shares.
- `contracts/pool/src/interest.rs:20-53` (`global_sync`/`accrue_chunk`) runs this on every mutating entrypoint through `Cache`, so the panic gates all verbs; `simulate_update_indexes` (`simulate.rs:136-181`) means the overflow also poisons `get_bulk_indexes`, `Context::cached_market_index`, and every controller view/risk computation touching that market.
- The repository's own harness test proves the cliff: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361` shows a whale market at ~98% utilization reaches `MathOverflow` in accrual years before the index cap engages, after which `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all revert — "the market is frozen: no repay, no withdraw, no liquidation". `docs/reference/formulas.md:432-437` documents that "value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first."

An unprivileged address reaches this purely through `supply`/`borrow`: caps are validated only against `cap` in native units (`require_cap_within_asset_domain`), and the token-to-RAY upscale admits up to ~1.7×10²⁹ base units (~170B whole 18-decimal tokens) per leg — orders of magnitude above the overflow threshold when the index has grown to ~170× RAY. No privileged action is needed to trigger the panic once state crosses the bound; any call that accrues detonates it.

### Impact Explanation
Permanent freezing of funds. Once `supplied × supply_index` or `borrowed × borrow_index` exceeds `i128::MAX`, every path that could move tokens or shares on that market — `withdraw`, `repay`, `liquidate`, `net_settle`, `seize_positions`, `claim_revenue`, `recapitalize`, `flash_loan` — calls `global_sync` first and reverts with `MathOverflow`. Supplier principal and unclaimed protocol revenue are locked forever; there is no escape hatch that skips accrual, and the borrow-index cap cannot retroactively shrink stored share counts. This is not a transient fail-closed DoS: no state transition is available that restores operation, matching the "permanent freezing of funds" impact class.

### Likelihood Explanation
Low-to-moderate. Triggering requires a market whose scaled share total is large enough that index growth pushes `shares × index` past `i128::MAX` — e.g., the harness uses 10³⁰ base units (~1B whole 18-decimal tokens) at ~98% utilization on a steep curve, reaching the cliff after roughly a decade of accrual. For high-decimals, low-value-per-unit tokens with lifted caps this is reachable by a single whale supplying/borrowing through normal `supply`/`borrow` calls; smaller markets or low utilization never reach it. No attacker timing or privileged cooperation is needed — ordinary protocol use over time suffices.

### Recommendation
Bound the *value* domain, not just the index:
- In `accrue_step`, cap `borrowed`/`supplied` such that `shares × MAX_*_INDEX_RAY` fits `i128` (reject `supply`/`borrow` mutations that would make `scaled_amount` exceed `i128::MAX / MAX_SUPPLY_INDEX_RAY`), so accrual can never overflow regardless of index growth; or
- Make `scaled_to_original`/`Ray::mul` saturate at `i128::MAX` inside `accrue_step` only (keeping panics for position-scaling math), so accrual completes and indexes clamp at their ceilings instead of bricking the market.
- Add the harness cliff scenario (`large_positions_and_long_horizons.rs:321`) to the enforced invariant set rather than a documented limit.

### Proof of Concept
```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);

let principal = BILLION * 10i128.pow(18);          // ~1e30 base units, within cap domain
t.supply_raw(BOB, "BIG18", principal);
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // 98% utilization, steep curve

// Advance years; each update_indexes call accrues via accrue_step.
loop {
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() { break; }  // -> MathOverflow
}

// From here the market is permanently bricked: every verb accrues first and
// hits scaled_to_original's i128 overflow before doing any work.
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
// liquidate / clean_bad_debt / recapitalize / claim_revenue revert identically.
```

Root cause chain: `controller::borrow/supply/withdraw/repay/liquidate/...` → pool op → `Cache` → `global_sync` → `accrue_step` → `scaled_to_original(borrowed, borrow_index)` → `mul_div_half_up` → `to_i128` fails → `MathOverflow` panic, at `borrow_index < MAX_BORROW_INDEX_RAY`, so no cap or accrual-elision ever rescues it.
