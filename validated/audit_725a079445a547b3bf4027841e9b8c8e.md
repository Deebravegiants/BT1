The reported analog exists in webhook processing: HMAC validation covers only the raw request body, not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers, letting an unprivileged sender re-attribute a validly-signed payload to an arbitrary shop/topic.

### Title
Webhook HMAC does not bind `shop-domain`/`topic`/`webhook-id` headers, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated headers and passed straight into the handler.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively [1](#0-0) , and `hmac` is derived purely from the `hmac-sha256` header [2](#0-1) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from separate, unsigned headers [3](#0-2) .

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it against the received signature [4](#0-3) . `Registry.process` calls this validator, then immediately builds `WebhookMetadata` using `request.topic` and `request.shop` — values that were never covered by the HMAC — and dispatches them to the registered handler for that topic [5](#0-4) .

The identity binding broken is: `shop authenticated by HMAC` ≠ `shop the handler is told to act on`. A valid HMAC only proves "this body's bytes were produced with the app's `api_secret_key`" (i.e., it once came from a real Shopify webhook for *some* shop/topic the sender controls); it says nothing about which shop or topic the request now claims to be for.

### Impact Explanation
Any party that can get one legitimate, validly-signed webhook delivery from Shopify (e.g., by installing the app on their own store and triggering an event such as `orders/create`) can capture the `raw_body` + `x-shopify-hmac-sha256` pair and replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` and/or `x-shopify-topic` header. Since `HmacValidator.validate` still succeeds (it only checks the body/secret), the app-defined handler executes as if the payload legitimately belongs to the victim shop and/or a different topic than what was actually signed, this is a cross-tenant identity confusion at the gem's trust boundary between "who produced these bytes" and "who these bytes are attributed to" when the host application relies on `WebhookMetadata#shop`/`#topic` (which nearly all consuming apps do, e.g. to look up per-shop `Session`/access tokens) for tenant-scoped decisions.

### Likelihood Explanation
Obtaining one authentic signed webhook body requires only installing the target app on a shop the attacker controls (or otherwise triggering any webhook topic the app subscribes to) — no `api_secret_key`, access token, or privileged account is required, satisfying the "unprivileged internet user" bar. Swapping headers on the replayed HTTP request is trivial.

### Recommendation
Include the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values in the HMAC-signable string (or otherwise cryptographically bind them to the body), so that a signature is only valid for the exact shop/topic/id it was issued for. At minimum, `Registry.process` should reject requests where the shop is not one the app expects to receive for that HMAC context.

### Proof of Concept
1. Install the app on `attacker.myshopify.com`; trigger `orders/create` there so Shopify delivers a real webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's secret).
2. Replay a POST to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `HmacValidator.validate` (checking only `B` and `H`) passes [6](#0-5) .
4. `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: ..., body: B)` [5](#0-4) , causing the app to process attacker-supplied data under the victim shop's identity.
