### Title
Tron `IntentGatewayV2.withdraw`/`onAccept` (SweepDust) use raw `.call` for ERC20 transfers and only check call success, not the returned boolean, allowing escrow/dust to be marked settled while tokens are never delivered - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` deviates from the rest of the codebase (which consistently uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, e.g. `evm/src/apps/intentsv2/IntentsBase.sol` `_withdraw`) by making raw low-level `.call()` invocations to `IERC20.transfer` and treating the call as successful whenever `success` (the low-level call didn't revert) is `true`, without decoding/validating the ABI-encoded boolean return value that ERC20's `transfer` is supposed to return. [1](#0-0) [2](#0-1) 

### Finding Description
This is the exact bug class described in the external report: an ERC20 token that "returns false on failure instead of reverting" (or otherwise doesn't strictly follow the standard) defeats naive success checks. `SafeERC20.safeTransfer` protects against this by decoding the return data and reverting if it decodes to `false` (or if the call has no return data, treating that as success only per EIP-20 convention). The Tron `IntentGatewayV2.withdraw` function does not do this:

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    for (uint256 i; i < len;) {
        ...
        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }
        _orders[body.commitment][token] -= amount;
        ...
``` [3](#0-2) 

The same pattern (raw `.call` checking only `success`) is repeated in the `SweepDust` handling inside `onAccept`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [4](#0-3) 

For a token whose `transfer` function returns `false` on failure (does not revert) — a real category of non-conforming ERC20s cited in the referenced OpenZeppelin `SafeERC20` documentation and precisely the misconception flagged in the external report — the low-level `.call` still "succeeds" (no revert), so `success == true`. The code then proceeds to decrement `_orders[body.commitment][token] -= amount` (marking the escrow as paid out) even though the beneficiary never received any tokens. This is a state/fund accounting desync directly analogous to the "flash loan doesn't check balance before/after" bug: the contract trusts the return of an untrusted call without verifying the actual effect (token balance movement), the same root cause the report calls out.

By contrast, every other transfer-out path in the same protocol family (`evm/src/apps/intentsv2/IntentsBase.sol` `_withdraw`, and the EVM-mainnet `IntentGatewayV2.sol`) uses `IERC20(token).safeTransfer(beneficiary, amount)` — the correct pattern — confirming the Tron file is an inconsistent, weaker implementation of the same logic. [5](#0-4) 

### Impact Explanation
Escrowed user/solver funds can be permanently frozen (locked in the gateway with no path to recovery) whenever the configured input/output token silently returns `false` on transfer failure instead of reverting: the escrow ledger (`_orders[commitment][token]`) is decremented as if the beneficiary was paid, and `_filled[commitment]` is set, finalizing the order, so the beneficiary has no further way to claim the tokens through the protocol's normal flow. This is a permanent freezing/loss-of-funds condition reachable by any unprivileged actor who fills or triggers settlement of an order denominated in such a token — no special privileges are required, only that the deployment lists (or a user/solver chooses) a non-conforming ERC20 as an input/output asset, which the protocol's design explicitly allows ("any ERC20 token can be used").

### Likelihood Explanation
Likelihood is Medium: it requires a specific class of non-standard ERC20 tokens (those that return `false` rather than revert on failure) to be used as an intent input/output asset. This is a known-common token quirk (deflationary/fee/blocklist tokens, some legacy ERC20s), and since IntentGatewayV2 is explicitly designed to support arbitrary ERC20 tokens with no allow-list enforcement visible in this code path, an attacker or unwitting user configuring an order with such a token (or a token becoming non-conforming due to blocklisting one of the parties) would trigger the issue during normal settlement (`onAccept` → `withdraw`) or dust sweeping.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in both `withdraw` (evm/tron/contracts/apps/IntentGatewayV2.sol lines ~706-707) and the `SweepDust` branch of `onAccept` (lines ~674-675) with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`IntentsBase.sol`, mainnet `IntentGatewayV2.sol`). This library is already imported and `using SafeERC20 for IERC20;` is already declared in this file, so the fix is a drop-in replacement:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```
This ensures both call success and, where the token returns data, a `true` boolean are enforced before escrow accounting is decremented.

### Proof of Concept
1. Deploy a malicious/non-conforming ERC20 `token` where `transfer(to, amount)` performs no state change (or fails an internal condition) and returns `false` instead of reverting.
2. A user places an order via `placeOrder` (in the paired source-chain `IntentGatewayV2`) using `token` as an input, escrowing funds.
3. A solver fills the order on the destination chain; the `RedeemEscrow` message is relayed and delivered to the Tron `IntentGatewayV2.onAccept`, which calls `withdraw(body, false)`.
4. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, abi.encode(false))` — the call itself doesn't revert, so `success == true`.
5. The code does not decode/check the returned boolean, so it proceeds: `_orders[body.commitment][token] -= amount;` and, on finalize, `_filled[body.commitment] = beneficiary;` and fee release.
6. The beneficiary's token balance never increased, but the escrow record shows the order as fully settled — the tokens are stuck in the `IntentGatewayV2` contract with no remaining accounting path to withdraw them, resulting in a permanent loss for the beneficiary and locked funds in the contract.
