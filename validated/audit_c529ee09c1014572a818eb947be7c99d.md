### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-attribution spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  while `Registry.process` validates the HMAC over that signable string and then hands `request.shop` — sourced entirely from an unauthenticated header — to the app's webhook handler as the trusted tenant identifier [2](#0-1) . The `shop` accessor is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [3](#0-2) , which is not part of the HMAC-signed payload.

### Finding Description
This mirrors the reported bug class: a piece of state relevant to authorization/tenant binding (`isShutdown` in the original report; here, `shop`) is fetched and acted on by the flow-gating function, but is not included in the check that is supposed to secure that flow (the `s.isShutdown` flag / here, the HMAC signature).

Concretely:
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the provided `hmac` [4](#0-3) .
- For a webhook `Request`, `to_signable_string` is only `@raw_body` — the `shop` header value is completely excluded from what's signed/verified [1](#0-0) .
- `Registry.process` treats a passing HMAC check as proof the whole request (including `request.shop`) is authentic, then constructs `WebhookMetadata` with that unauthenticated `shop` value and dispatches it to the app-defined handler [2](#0-1) .

The binding that should hold is: `shop attributed to the event == shop that produced the signed body`. Before the attack, for a genuine webhook delivered by Shopify to the merchant's own registered endpoint, this holds. After the attack, an unprivileged app-installing user (merchant on Shop A, a legitimate but low-privileged tenant of a multi-tenant app) can capture one of their own genuine webhook deliveries (raw body + valid `x-shopify-hmac-sha256`, both computed with the same `client_secret`-derived key shared across all shops using this app) and replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g., Shop B, a victim tenant). Because the header is not covered by the HMAC, `HmacValidator.validate` still succeeds, and the handler receives `WebhookMetadata` claiming the event belongs to Shop B, even though the body content came from Shop A. Per the gem's own webhook documentation, `data.shop` is meant to identify which shop the webhook data belongs to, and apps are expected to use it directly (e.g., to look up per-shop session/data) [5](#0-4) .

### Impact Explanation
This breaks the cross-tenant isolation guarantee of the shop identity binding: an attacker who is a legitimate but unprivileged merchant/tenant of the app can forge webhook events attributed to any other shop, without needing the app's `client_secret`, an access token, or any privileged account for the victim shop. Depending on how the host app uses `data.shop` (commonly to look up the target shop's session, write/update shop-scoped data, or trigger shop-scoped side effects), this enables cross-tenant data injection or corruption — matching the "Critical: cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is High: any app user can register their own shop with the vulnerable app, trivially capture one legitimate webhook delivery (raw body + `hmac-sha256` header) they naturally receive for their own store, and immediately replay it with a spoofed `shop-domain` header. No cryptographic secret needs to be broken and no interaction with the victim is required.

### Recommendation
Include the `shop` value (and ideally `topic`/`webhook_id`) as part of the data covered by the HMAC verification, or independently verify that the `shop-domain` header corresponds to a shop for which this exact `(raw_body, hmac)` pair was actually intended (e.g., by requiring apps to only accept webhooks for currently known/registered shop sessions, and by documenting that the header is unauthenticated so apps must not trust it as an unforgeable tenant identifier without additional binding).

### Proof of Concept
1. As a merchant of Shop A (unprivileged w.r.t. the app's `client_secret`), install the app and let it register webhooks; capture one genuine callback HTTP request sent by Shopify: note `raw_body` and the `x-shopify-hmac-sha256` header value.
2. Send a new POST request to the app's webhook endpoint with the identical `raw_body`, identical `x-shopify-hmac-sha256`, but `x-shopify-shop-domain` set to Shop B's domain.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only [1](#0-0)  and succeeds since `raw_body` and `hmac` are unmodified and match.
4. The handler is invoked with `WebhookMetadata` whose `shop` is Shop B [6](#0-5) , despite the payload actually originating from Shop A's store activity.

          received_signature = verifiable_query.hmac
