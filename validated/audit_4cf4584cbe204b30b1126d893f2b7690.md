Audit Report

## Title
Data race on `authorizedKeys` map allows unsynchronized authorization check in `WorkflowMetadataHandler.Authorize` - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` reads `h.authorizedKeys[workflowID]` at line 92 without holding `h.mu`, while `syncMetadata` fully replaces `h.authorizedKeys` under `h.mu.Lock()` at line 178 on a background timer. This is an unsynchronized concurrent read/write of a Go map, which is undefined behavior and can crash the gateway process or, in principle, yield inconsistent authorization results.

## Finding Description
`WorkflowMetadataHandler` protects its state (`authorizedKeys`, `workflowIDToRef`, `workflowRefToID`, `workflowShards`) with `h.mu sync.RWMutex`. Every other accessor correctly takes the lock: `syncMetadata` takes `h.mu.Lock()` before reassigning `h.authorizedKeys`, and `GetWorkflowID`, `GetWorkflowReference`, and `WorkflowShards` all take `h.mu.RLock()`. However `Authorize` — invoked on every incoming HTTP trigger request via `httpTriggerHandler.authorizeRequest` — reads `h.authorizedKeys[workflowID]` directly with no lock at all. `syncMetadata` runs periodically via `h.runTicker(time.Duration(h.config.MetadataAggregationIntervalMs)*time.Millisecond, h.syncMetadata)` and performs a full map reassignment under lock, concurrently with unlocked reads from `Authorize`. This breaks the synchronization discipline enforced everywhere else in the struct and constitutes a genuine, code-provable data race.

## Impact Explanation
Concurrent unsynchronized map access in Go is undefined behavior enforced at the runtime level: the Go runtime detects many such races and calls `fatal error: concurrent map read and map write`, crashing the process (denial of service of the gateway). Since `Authorize` gates whether an external, unauthenticated caller's HTTP trigger request is accepted for a given `workflowID`, this bug is reachable purely from unprivileged, external HTTP trigger traffic and maps to an in-scope DoS/availability impact on the gateway component; a possible secondary effect is an inconsistent read of the authorization set, though the runtime does not guarantee any particular corrupted value (torn reads aren't reliably exploitable for a deterministic bypass, they mainly manifest as crashes).

## Likelihood Explanation
`syncMetadata` runs continuously on a fixed timer (`MetadataAggregationIntervalMs`), and `Authorize` is invoked on the hot path of every incoming HTTP trigger request, reachable by any external, unprivileged client that can send requests to the gateway's HTTP trigger endpoint. No special credentials beyond a validly-signed JWT for some workflow are required to hit the `Authorize` path repeatedly, so the race window is realistically and repeatably exercised under moderate load.

## Recommendation
Take `h.mu.RLock()` / `defer h.mu.RUnlock()` around the `h.authorizedKeys[workflowID]` lookup in `Authorize`, consistent with `GetWorkflowID`, `GetWorkflowReference`, and `WorkflowShards`, so the read cannot race with `syncMetadata`'s write path.

## Proof of Concept
Run `go test -race` against a test in `core/services/gateway/handlers/capabilities/v2` that spins up one goroutine repeatedly calling `syncMetadata(ctx)` (or drives it via the ticker) while concurrently calling `Authorize(workflowID, token, req)` from multiple goroutines for the same `workflowID`. The Go race detector should flag the concurrent map read (line 92, unlocked) against the concurrent map write (line 178, under `h.mu.Lock()`), and under sufficient load without `-race` this can trigger `fatal error: concurrent map read and map write`, crashing the gateway process.
