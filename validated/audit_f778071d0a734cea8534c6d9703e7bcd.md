### Title
CostModel's `calculate_allocated_accounts_data_size` ignores CPI-triggered System Program allocations, allowing real account-data growth to bypass the `CostTracker` block-wide `allocated_data_size` budget - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::calculate_allocated_accounts_data_size` only inspects `transaction.program_instructions_iter()`, which yields exclusively the sanitized top-level compiled instructions of a transaction, never instructions dispatched via CPI. An attacker can deploy an unprivileged wrapper BPF program that CPIs into `system_program::CreateAccountWithSeed`/`AllocateWithSeed`/`Allocate`, causing real, persisted account-data growth that the cost model statically evaluates as `0` for that transaction, letting the true per-block account-data growth exceed `CostTrackerLimits.allocated_data_size` (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`) while the tracker still reports the block as within budget.

### Finding Description
`CostModel::calculate_allocated_accounts_data_size` [1](#0-0)  walks `instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>`, which for both `calculate_cost` and `calculate_cost_for_executed_transaction` is populated exclusively from `transaction.program_instructions_iter()` [2](#0-1) . This iterator only decompiles the top-level, sanitized instructions of the transaction message; instructions dispatched by a program via cross-program invocation are not present in it because they don't exist until the SBF program actually executes and calls `invoke`/`invoke_signed`.

`calculate_account_data_size_on_instruction` only recognizes an allocation when `program_id == &system_program::id()` at that top level [3](#0-2) . If the attacker's top-level instruction instead targets an arbitrary wrapper BPF program (which then internally CPIs to the System Program to call `CreateAccountWithSeed`/`AllocateWithSeed`/`Allocate`), `program_id` at the top level is the wrapper program's ID, not the System Program's ID, so `SystemProgramAccountAllocation::None` is returned and the resulting `tx_attempted_allocation_size` contribution is `0`, no matter how much data the CPI-triggered instruction actually allocates.

This estimated `allocated_accounts_data_size` (capped by `MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION`) is exactly what `CostTracker::would_fit`/`add_transaction_cost` accumulate against the *block-wide* budget `CostTrackerLimits.allocated_data_size` (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` = 100,000,000 bytes) [4](#0-3) [5](#0-4) . Since the CPI-driven allocation contributes `0` to this running total, the leader's scheduler never rejects such transactions with `CostTrackerError::WouldExceedAccountDataBlockLimit`, even though the real account bytes are actually persisted.

There *is* a separate, correct hard cap that stops any single transaction from allocating unbounded data: `TransactionAccounts::can_data_be_resized` enforces `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` (≈20 MiB, `MAX_ACCOUNT_DATA_LEN * 2`) transaction-wide, for both top-level and CPI-triggered resizes [6](#0-5) . This guard limits growth *per transaction* correctly regardless of call depth, but it does nothing to protect the separate, coarser *per-block* budget (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`) tracked by `CostTracker`, which is the mechanism this question targets. Because `CostTracker`'s admission-control accounting is blind to CPI allocations, a leader packing many independent CPI-allocation transactions (each touching distinct write-locked accounts to avoid the per-account CU limit, each safely under the ~20 MiB per-tx cap and well within the 60M CU block compute budget) can accumulate real account-data growth in a single block that is many times larger than the intended `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100 MB), all while `CostTracker.allocated_accounts_data_size` stays at (or near) `0`.

The comment in the code itself acknowledges the blind spot but only in the context of a single transaction's internal allocate/free interplay ("if there are any custom bpf instructions in the transaction it's tricky to know whether a newly allocated account will be freed") — it does not address the fact that custom BPF instructions can themselves *cause* allocation via CPI that is never counted at all.

### Impact Explanation
This is a costing/DoS-adjacent bug: it defeats the block-wide account-data-growth budget (`COST_UPPER_BOUND` for `allocated_data_size`) that exists specifically to bound how fast account/accounts-index/snapshot storage can grow per block. An attacker can drive real per-block account-data growth well beyond `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` using only unprivileged, ordinary transactions (deploy one small wrapper program, then broadcast many independent CPI-allocation transactions), causing materially underpriced execution relative to the cost model and undeclared resource consumption invisible to the leader's cost tracker. Over repeated blocks/epochs this accelerates accounts-index and validator storage growth beyond the rate the cost-model's block limit is meant to enforce — a resource-exhaustion / state-growth style impact, not funds theft or consensus-halting by itself, but a genuine violation of the documented cost-tracking invariant.

### Likelihood Explanation
Fully reachable by an unprivileged actor: deploying a BPF program and invoking CPI to the System Program are ordinary, permissionless operations. No leader/validator/staked cooperation is required — a normal user submits transactions to any public RPC/TPU. The exploit is deterministic and repeatable per block/epoch and requires no timing games beyond normal transaction submission (well under the "one RPC call per half slot" DoS carve-out, since these are ordinary signed transactions, not RPC scans).

### Recommendation
Extend `calculate_allocated_accounts_data_size` (or the cost-estimation pipeline generally) to also account for instructions reachable via CPI, or — more practically given static instructions can't be fully enumerated ahead of execution — switch the *actual* (post-execution) cost accounting path (`calculate_cost_for_executed_transaction` / commit-time cost tracking) to use the real `AccountsDeltas::accounts_resize_delta` (already computed per-transaction in `svm/src/transaction_processor.rs` and used for `Bank::update_accounts_data_size_delta_on_chain`) instead of re-deriving `allocated_accounts_data_size` from `program_instructions_iter()`. This way, the value fed into `CostTracker`'s block-wide `allocated_data_size` bookkeeping reflects real, CPI-inclusive account growth rather than a static top-level-only estimate.

### Proof of Concept
Integration test plan (in `cost-model`/`runtime` bank test style):
1. Deploy a minimal wrapper BPF program `cpi_allocate` that takes a `space: u64` argument and CPIs into `system_program::create_account_with_seed` (or `allocate`) for a target account, using `invoke_signed`/PDA seeds so the wrapper can be the allocator without needing the caller's private key.
2. Build a transaction whose single top-level instruction invokes `cpi_allocate` (program_id = wrapper program) with `space = 10_000_000` (under the ~20 MiB per-tx cap).
3. Compute `tx_cost = CostModel::calculate_cost(&sanitized_tx, &feature_set)` and assert `tx_cost.allocated_accounts_data_size() == 0`.
4. Execute the transaction against a `Bank` (`bank.process_transaction(&tx)`), and read `bank.load_accounts_data_size_delta_on_chain()` before/after; assert the delta equals `10_000_000` (i.e., real growth occurred).
5. Assert the discrepancy: `tx_cost.allocated_accounts_data_size() (0) != actual_bank_accounts_data_size_delta (10_000_000)`.
6. Extend to a block-level test: submit N such transactions (each with distinct destination accounts to avoid `WouldExceedAccountMaxLimit`) into one `CostTracker`/bank slot such that `N * 10_000_000 > MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100_000_000), while `CostTracker::try_add` never returns `Err(CostTrackerError::WouldExceedAccountDataBlockLimit)` for any of them, yet `bank.load_accounts_data_size_delta_on_chain()` after replaying the block exceeds `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`, proving the block-wide budget was violated undetected.

        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no

                    return 0;

                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
