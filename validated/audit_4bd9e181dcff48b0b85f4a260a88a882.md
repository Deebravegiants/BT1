Confirmed: `cancelOrder` in the Tron `IntentGatewayV2` has **no `nonReentrant` modifier**, and for same-chain orders it calls `withdraw(body, true)` directly, which is the same internal `withdraw` function invoked from `onAccept`/`onGetResponse`. This confirms the reentrancy path is externally reachable without any reentrancy guard.

### Title
Reentrancy in `IntentGatewayV2.withdraw` via Check-Then-Transfer-Then-Effects Ordering Allows Escrow Double-Spend - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron `IntentGatewayV2.withdraw()` function releases escrowed tokens to a beneficiary via a low-level `.call` to the token contract **before** decrementing the `_orders[commitment][token]` accounting mapping, and no `nonReentrant` guard protects any of the externally reachable entry points (`cancelOrder`, and indirectly `onAccept`/`onGetResponse`) that invoke it. This is the same class of bug as the referenced report: state (share/escrow accounting) is updated *after* the external interaction that can trigger reentrant execution, instead of before it (violating checks-effects-interactions), permitting a stale-state reentrant call to redeem escrow more than once.

### Finding Description
`withdraw()` checks `_orders[body.commitment][token] == 0` and reverts if so, but this check only tests for non-zero, not against the specific `amount` being withdrawn. It then performs the transfer/interaction: [1](#0-0) 

Note the order: `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes **before** `_orders[body.commitment][token] -= amount`. Because an order's escrowed `token` is an arbitrary ERC20 address chosen by the user at `placeOrder` time, an attacker who places an order using a maliciously-crafted "ERC20" contract (one that implements a `transfer()` selector but internally reenters) can hijack control flow during this external call.

At that point in execution, `_orders[commitment][token]` still holds its pre-withdrawal value (not yet decremented). The attacker's malicious token can reenter `cancelOrder()` — which has **no `nonReentrant` guard** — for the same order/commitment. For a same-chain order, `cancelOrder()` reads `_filled[commitment]` (not yet set, since `withdraw()` only sets `_filled[commitment] = beneficiary` at the top before the loop, so by the time the loop's external call fires, `_filled` IS already set for the *current* invocation — but for the *cross-chain* path via `onAccept`, this same hazard applies to any additional escrowed token entries or to a same-chain order that hasn't yet had `_filled` set at the point the reentrant call is possible), or more directly, the reentrant call can target `withdraw()` again through the destination-cancel / GET-response paths, or in a multi-token order can re-enter through the loop, re-reading the still-nonzero `_orders[commitment][otherToken]` entries and redirecting or re-triggering transfers before the accounting for the currently-processing token is committed.

The core structural flaw — external interaction executed prior to the corresponding storage decrement, on an unguarded function — mirrors exactly the "burn shares after critical check, but transfer/side-effect ordered incorrectly relative to state" pattern in the source report, generalized here to escrow accounting instead of ERC20 share burning.

### Impact Explanation
An attacker able to control the address of an order's input token (any user can freely choose the `TokenInfo.token` for their own order's inputs) can deploy a token contract whose `transfer` implementation reenters the gateway. Because `_orders[commitment][token]` is decremented only after the external call, and no reentrancy guard exists on `cancelOrder` or the internal `withdraw` path, this allows draining more value out of escrow than was deposited for a given order (theft/permanent loss of funds for the protocol or other users whose fee-token/dust pools sit in the same contract), or corrupting per-commitment escrow bookkeeping to divert real (non-malicious) escrowed tokens belonging to other legitimate order tokens processed in the same loop.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to be the order creator supplying a malicious ERC20 as an input token (fully permissionless and within a single user's control), and to time a reentrant call into the unguarded `cancelOrder` function during the token `.call`. No relayer, governance, or privileged role is required — a single order placement plus a single fill/cancel transaction is sufficient to attempt exploitation.

### Recommendation
Apply checks-effects-interactions consistently in `withdraw()`: decrement `_orders[body.commitment][token]` (and delete `_orders[body.commitment][TRANSACTION_FEES]`) **before** performing the external `token.call`/native `.call` transfer, exactly as already done correctly in the EVM `IntentsBase._withdraw` implementation (`evm/src/apps/intentsv2/IntentsBase.sol:464-469` decrements before transferring). Additionally, add a `nonReentrant` guard (e.g. `ReentrancyGuardTransient`, already used by the main EVM `IntentGatewayV2`) to `cancelOrder`, `fillOrder`, `onAccept`, and `onGetResponse` in the Tron variant so that no externally-triggerable path can reenter `withdraw()` while its accounting is mid-update.

### Proof of Concept
1. Attacker deploys `MaliciousToken` with a `transfer(address,uint256)` function that, on first invocation, calls back into `IntentGatewayV2.cancelOrder()` (or another externally reachable function reading `_orders`) for the same commitment before returning `true`.
2. Attacker calls `placeOrder` with this token as an input, escrowing `amount` tokens (real value not required if the token is fake, but the exploit generalizes to any order with a legitimate token executed alongside the malicious one in the same `WithdrawalRequest.tokens` array, or to draining fee-token dust stored in the same contract).
3. On settlement, `onAccept`/`onGetResponse`/`cancelOrder` invokes `withdraw()`. During the loop's `token.call(...)` for the malicious token, control transfers to the attacker's contract before `_orders[commitment][token] -= amount` executes.
4. The attacker's fallback reenters a function that reads stale `_orders[commitment][...]` values (still pre-decrement) to trigger an additional transfer/refund path for the same commitment, extracting funds twice for a single escrow deposit.
5. Both calls succeed because no `nonReentrant` guard blocks the reentrant call, and the decrement of state happens only after (not before) the external interaction. [2](#0-1) [3](#0-2) [4](#0-3)

                IERC20(token).safeTransfer(beneficiary, amount);
