### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers. `Utils::HmacValidator` only checks the body against the HMAC, so any actor who possesses one valid `(body, hmac)` pair for their own shop can replay it with a forged `shop-domain` header naming a victim shop, and `Webhooks::Registry.process` will accept it and hand the attacker-controlled data to the app's handler tagged as belonging to the victim shop.

### Finding Description
`Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` purely from HTTP headers: [1](#0-0) 

But `to_signable_string`, which is the value that gets HMAC-verified, only ever returns the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature exclusively over `to_signable_string` and compares it to the `hmac` header — it has no visibility into `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Webhooks::Registry.process` trusts this validation result and then forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` straight into `WebhookMetadata`, which is passed to the app's registered handler: [4](#0-3) 

The identity binding that should hold is:
`shop header used by the app == shop the HMAC-signed body was actually generated for by Shopify`

Because the HMAC only signs the body, this equality is never actually checked — the gem effectively verifies "these bytes came from Shopify for *some* shop" but the calling app is told "these bytes are for *this* shop," where "this shop" is taken from an attacker-controllable header.

### Impact Explanation
Any unprivileged internet user can install the target public app on their own (even free/dev) Shopify store. Doing so makes Shopify send them genuine webhooks — each with a real HMAC computed over the raw body using the app's `client_secret` — for their own shop's events. Because the signature never binds the body to a specific `shop-domain` header, the attacker can capture one such `(raw_body, hmac)` pair and replay it directly to the app's webhook endpoint with the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) headers rewritten to name a victim shop that also installed the app. `Registry.process` will validate successfully and invoke the app's handler with `WebhookMetadata` claiming the (attacker-chosen) body content belongs to the victim shop. As documented, apps use `data.shop` from `WebhookMetadata` to key merchant-specific data/session lookups, so this allows a cross-tenant data injection/confusion attack. This meets the Critical bar of "cross-tenant access."

### Likelihood Explanation
Exploitation requires no privileged credentials, tokens, or secrets — only becoming an app user on any shop (something any internet user can do for a public app) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers. The only constraint is that the attacker must produce a body whose content is useful for impersonation; because they fully control their own shop's data (products, orders, customers, etc. as far as they can influence via their own store), they can shape the eventual body content to a meaningful degree before triggering the real webhook from Shopify. This makes the attack realistically achievable without any insider access.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) inside the HMAC-covered signable content, or otherwise cryptographically bind them to the body (e.g., verify the HMAC and additionally require that the receiving application independently confirms the shop from the header against the shop context associated with that webhook subscription). At minimum, document clearly that `Registry.process`/`Webhooks::Request` does not authenticate `shop`, `topic`, or `webhook_id`, so consuming applications must not trust these fields for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real event (e.g., updates a product) so Shopify sends a webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` computed over the raw JSON body using the app's `client_secret`.
2. Attacker intercepts/captures this `(raw_body, hmac)` pair.
3. Attacker sends a new HTTP POST to the same webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` header, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and adjusts `x-shopify-topic`/`x-shopify-webhook-id` if desired).
4. `Webhooks::Request.new` accepts the forged headers (only checks presence, not correlation) — see `lib/shopify_api/webhooks/request.rb:45-63`.
5. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` vs `hmac` — see `lib/shopify_api/utils/hmac_validator.rb:12-22`.
6. `Registry.process` dispatches to the app handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the body/content actually originated from the attacker's own shop — see `lib/shopify_api/webhooks/registry.rb:188-200`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
