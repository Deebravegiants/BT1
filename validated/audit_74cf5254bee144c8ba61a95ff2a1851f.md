### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, while the `shop` field that the gem hands to the app's webhook handler (and that the gem's own documentation tells developers to use as the tenant key) comes from the unauthenticated `x-shopify-shop-domain` header. The identity binding "shop authenticated == shop used as tenant key" is broken because only the body bytes are signed.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`ShopifyAPI::Webhooks::Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cross-check against the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC over that signable string, and then trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes/compares the HMAC purely against `verifiable_query.to_signable_string` (the body), never incorporating the shop header: [4](#0-3) 

Because the `client_secret` used to compute this HMAC is shared across every shop that installs the app (it is not per-shop), any shop that has installed the app can trigger a legitimate webhook delivery for itself and thereby obtain a valid `(raw_body, hmac)` pair signed with the app's secret. The header carrying the shop domain is never part of the signed material, so that same valid `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to name a *different* installed shop (the victim). `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` forwards the attacker-chosen `shop` value straight to the handler as trusted tenant context — exactly matching the documented usage pattern (`shop_domain: data.shop`) shown in the gem's own webhook documentation.

The break in binding, stated as an equality that should hold but doesn't:
`shop value cryptographically authenticated by the HMAC` ≠ `shop value delivered to and trusted by the handler`.

### Impact Explanation
This is a scope/credential boundary bypass: an app that keys its per-tenant data access (session/token lookup, database writes, entitlement checks) off `WebhookMetadata#shop` can be made to act on/for a shop the request did not actually originate from, because the gem provides no authenticated binding between the HMAC-verified bytes and the shop identifier the handler consumes. This is a cross-tenant confusion vector reachable by any unprivileged party capable of installing the target app on their own store (a normal, low-privilege action), directly through this gem's own `Registry.process`/`Request` implementation rather than host-app misuse.

### Likelihood Explanation
Requires only: (1) attacker installs the target app on a shop they control (ordinary, unauthenticated action any Shopify user can perform), (2) attacker triggers/crafts a webhook delivery whose body content they can influence or fully control, (3) attacker replays the captured `(raw_body, hmac)` pair to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header naming the victim shop. No access token, `client_secret`, or privileged credential is needed — only network access to the app's public webhook callback URL.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind `request.shop` to the validated body (e.g., require the host app to only trust `shop` values that also match a known, previously-onboarded session/tenant record rather than passing the raw header value straight through as authenticated context). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must be independently verified against installed-shop records before being used as a tenant key.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` (self-service, no privilege needed).
2. Attacker triggers a webhook (e.g. `orders/create`) with attacker-controlled body content on their own shop, capturing the raw body `B` and the corresponding `x-shopify-hmac-sha256` header `H` sent by Shopify (computed with the app's shared `client_secret`).
3. Attacker POSTs to the app's webhook endpoint with `raw_body = B`, `x-shopify-hmac-sha256 = H` (unchanged, since it is a function only of `B` and the shared secret), but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present); `Utils::HmacValidator.validate` returns `true` because `to_signable_string` only ever hashes `B`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under the victim shop's tenant context.
