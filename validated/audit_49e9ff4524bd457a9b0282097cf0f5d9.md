Webhook `shop` field used for tenant identification is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by validating only the raw request body against the `x-shopify-hmac-sha256` header, but it then trusts the unauthenticated `x-shopify-shop-domain` header to identify which tenant/shop the webhook belongs to. This breaks the identity binding `shop_verified_by_hmac == shop_used_for_tenant_context`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 
`to_signable_string` returns only `@raw_body` — the HMAC computed by Shopify (and verified via `HmacValidator.validate`) covers **only the JSON body**, not any HTTP header.

`HmacValidator.validate` confirms this: it computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` value: [2](#0-1) 

Meanwhile, the `shop` accessor used to identify the tenant is read directly from the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header, which is fully attacker-controlled and never covered by the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` directly from `request.shop`, passing it to the host application's handler as the tenant identity: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no further validation: [5](#0-4) 

Since a single `api_secret_key` is shared by an app across all of its shop installations, the HMAC is valid for the same raw body/secret pair regardless of which shop it nominally came from. An attacker who controls (or has installed the app on) one shop, or who can otherwise obtain a body+HMAC pair for their own shop's legitimate webhook delivery, can replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary value in `x-shopify-shop-domain`. `HmacValidator.validate` will still pass (it never inspects the shop header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop of the attacker's choosing.

### Impact Explanation
This is a cross-tenant identity-confusion vector: the gem provides the host application no verified linkage between the HMAC-authenticated bytes and the shop identity attached to them. A host application that uses `WebhookMetadata#shop` (as documented/intended — see `docs/usage/webhooks.md`) to key per-tenant state, look up sessions, or apply per-shop authorization will act on data associated with the wrong tenant, since the gem itself asserts the request is verified ("Invalid webhook HMAC." check passed) while `shop` is forgeable. This matches the Impact category of cross-tenant access.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one valid `(raw_body, hmac)` pair — obtainable trivially from any shop they control/install the app on (a legitimate, unprivileged action), or from any webhook delivery to their own endpoint, since the app-level `api_secret_key` is shared across all shops using the app. No access to the app's `client_secret`/access tokens is needed and no privileged account is required beyond installing the app as any ordinary merchant. This makes the likelihood realistic for any app relying on this gem's webhook shop identification for tenant scoping.

### Recommendation
Bind the shop identity into the verified signable content, or otherwise cryptographically bind `shop` to the HMAC-covered payload before exposing it via `WebhookMetadata`. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated and must not be used for tenant/session lookup without independently confirming the shop against the recipient's own registered webhook subscription id/topic combination server-side (e.g., cross-check against Shopify's registered `webhook_id` to shop mapping) rather than trusting the header value directly.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the resulting HTTP request: `raw_body` and the `x-shopify-hmac-sha256` header value computed by Shopify with the app's shared `api_secret_key`.
2. Attacker resends this exact `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes/compares the HMAC over `raw_body`: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, and any application logic keyed on `data.shop` now operates under the victim's tenant identity despite the payload/HMAC not actually originating from Shopify on behalf of that shop.
