Based on my research, I found a directly analogous vulnerability pattern in `pallet-bandwidth`.

### Title
Unbounded per-message weight in `handle_unsigned` via O(n) bandwidth-gate drain loop bypasses the `#[pallet::weight(weight())]` declaration - (File: `modules/pallets/ismp/src/lib.rs`, `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-ismp::handle_unsigned` is an unsigned, permissionless extrinsic that executes a batch of relayed ISMP messages "for free" [1](#0-0) . When a message targets a bandwidth-gated app, `ProxyModule::on_accept` invokes `BandwidthGate::try_consume`, which mutates the app's `Allowance` `BoundedVec<Subscription, MaxSubscriptions>` (capped at 1024) with an O(n) `retain` sweep plus an O(n) FIFO drain loop [2](#0-1) . This is exactly the `remove()`/FIFO-queue gas-cost pattern described in the external report, translated to Substrate weight/PoV cost instead of EVM gas.

### Finding Description
`try_consume` sweeps expired entries with `list.retain(|s| s.expires_at > now)` and then drains from the head in a `while left > 0` loop, calling `list.get_mut(0)` / `list.remove(0)` per exhausted entry [3](#0-2) . Because subscriptions never stack (repurchases append rather than merge) and the list is bounded at `MAX_SUBSCRIPTIONS = 1024` with oldest-eviction on overflow [4](#0-3) , any account can permissionlessly call `BandwidthManager.purchase()` many times (each purchase is a POST dispatched to the pallet's `on_accept`, which appends a `Subscription` row) to grow a target `(app_chain, app)` allowance list toward the 1024-entry cap.

The critical flaw is that `handle_unsigned`'s dispatch weight is declared as a fixed/static `weight()` value [5](#0-4) , and the actual per-message module callback cost (`on_accept`/`on_response`/`on_timeout`) is only used for *fee accounting* after the fact via `IsmpModuleWeight` (`WeightFeeHandler`) [6](#0-5) [7](#0-6)  — it is not used to bound the pre-dispatch weight limit charged/consumed for block-inclusion or `validate_unsigned` execution. `handle_unsigned` is unsigned and "free" specifically because it's expected to do bounded work; but the bandwidth gate's list-length-dependent sweep/drain means the same call can cost anywhere from O(1) to O(1024) storage mutations depending on attacker-controlled prior purchases against that `(chain, app)` key. `validate_unsigned` itself unconditionally re-executes `Self::execute(messages.clone())` for every submitted unsigned transaction that reaches the pool [8](#0-7) , so the expensive gate computation runs at least twice per landed message (once in validation, once in on-chain execution), and identically for every unsigned resubmission attempt that reaches validation before being rejected for other reasons.

### Impact Explanation
An attacker can cheaply pre-load a target app's `(app_chain, app)` allowance list toward its 1024-entry cap by issuing many small `purchase()` calls (paying only the tier's dust price, if any tier is configured with a low price, or by targeting an app that already accumulates entries through normal legitimate use over time). Once loaded, every subsequent legitimate message destined for that app forces `try_consume` to walk/retain/drain up to 1024 `Subscription` entries per call — and this happens inside `handle_unsigned`, a call declared with a fixed weight that does not scale with this cost, and which additionally executes the same expensive path twice (`validate_unsigned` + `execute`) for every relayed batch. This inflates real block-execution time disproportionately to the weight actually charged/reserved for the extrinsic, degrading block production or letting an attacker fill blocks with more such calls than the declared weight budget assumes — a resource-exhaustion condition matching the "spam a FIFO queue to blow out the gas/weight of a downstream permissionless function" bug class from the report, and it specifically threatens message delivery liveness for the gated app (a route "unable to deliver messages" case).

### Likelihood Explanation
Reaching this requires only unprivileged, permissionless actions: (1) calling `BandwidthManager.purchase()` on any EVM source chain repeatedly to grow a target app's subscription list, each of which is a normal user-facing dispatch path with no minimum-amount protection beyond the tier's configured price, and (2) submitting `handle_unsigned` messages destined for the loaded app, which any relayer is already incentivized to do continuously. The 1024 cap bounds the worst case, but the pallet's own documentation confirms per-call cost scales linearly with active list length up to that cap, and the declared extrinsic weight does not vary with it.

### Recommendation
- Charge/declare `handle_unsigned`'s pre-dispatch weight (or at least the portion attributable to the module callback) proportional to `IsmpModuleWeight::on_accept`, so the weight system, not just the after-the-fact fee handler, accounts for the list traversal.
- Avoid recomputing the full `execute` (including bandwidth-gate mutation) twice per message — once in `validate_unsigned` and once in the dispatched call — or make `validate_unsigned`'s check bandwidth-independent/cheap.
- Consider bounding drain/sweep cost independent of `MAX_SUBSCRIPTIONS`, e.g. by requiring a minimum purchase size/tier floor (mirroring the report's "set a minimum unstake amount" mitigation) so an attacker cannot cheaply fill the FIFO list with many low-value entries.

### Proof of Concept
Conceptual, not executed:
1. Attacker registers/targets an app `(app_chain, app)` and repeatedly calls `BandwidthManager.purchase()` with the lowest-priced/shortest configured tier and `months = 1`, each purchase dispatching a POST that pallet-bandwidth's `on_accept` appends to `Allowance::<T>` — repeat close to 1024 times [9](#0-8) .
2. Any relayer now submits a normal message for that app via `handle_unsigned`; `ProxyModule::on_accept` calls `try_consume`, which must `retain` and potentially drain across up to 1024 `Subscription` entries in a single unsigned, "free" extrinsic [3](#0-2) .
3. Because `handle_unsigned`'s declared weight is static [5](#0-4)  and `validate_unsigned` re-runs the same `execute` path for every submission attempt [8](#0-7) , repeated submissions (valid or replay-adjacent) against the loaded app impose outsized real execution cost relative to what the runtime's weight system assumes, which is not independently benchmarked/verified in the provided index — flagged as uncertain and worth confirming via a Devin session with full repo/benchmark access.

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;
