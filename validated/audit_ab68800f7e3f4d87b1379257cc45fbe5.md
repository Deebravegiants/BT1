### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify," but the HMAC signature it checks only binds the raw JSON body — it never binds the `shop`, `topic`, `webhook_id`, or `api_version` values that the handler is told to trust and act on. An unprivileged internet user who can obtain any one genuinely-signed webhook body (trivially available by installing the target app on their own store/dev shop) can replay that exact body+HMAC pair to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to impersonate a different, victim tenant.

### Finding Description
`Registry.process` performs exactly one authenticity check: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC using only `to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns `@raw_body` only — none of the header-derived accessors (`shop`, `topic`, `webhook_id`, `api_version`) participate in the signature: [3](#0-2) 

Yet `Registry.process` passes these unauthenticated header values straight into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant identity: [4](#0-3) 

The gem's own documentation instructs developers to key their per-tenant processing off `data.shop` directly, treating it as verified because "This will verify the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

The broken identity binding is:
`shop authenticated by HMAC(raw_body, api_secret_key)` ≠ `shop asserted in the X-Shopify-Shop-Domain header used by the handler`.

Because only the body is signed, the same (body, HMAC) pair remains valid no matter what `shop`/`topic`/`webhook_id` headers accompany it. An attacker only needs one legitimately-signed webhook for their *own* shop (any installed app fires these automatically, e.g. on `app/uninstalled`, `customers/create`, etc.) to obtain a valid body+HMAC pair signed with the app's `client_secret` — which they never need to know themselves.

### Impact Explanation
This breaks the tenant boundary the whole webhook subsystem is meant to enforce: an attacker can make the app process a webhook payload while claiming it belongs to an arbitrary victim shop domain (and arbitrary topic), because `shop`/`topic` are read from unauthenticated headers rather than the signed body. Any app that follows the documented pattern of dispatching or persisting data keyed by `data.shop` (as shown in the gem's own example) is exposed to cross-tenant data corruption/impersonation triggered entirely by an unprivileged internet user — satisfying the "cross-tenant access" Critical impact criterion.

### Likelihood Explanation
High. No privileged access, leaked secrets, or credentials are required. An attacker merely needs to install the target app on any shop they control (a normal, low-friction action any internet user can take with a public Shopify app or dev store) to receive a genuinely HMAC-signed webhook, then replay that body with the HMAC unchanged but headers pointed at a different shop.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-covered signable string (or otherwise cryptographically bind them, e.g. by validating the `shop` domain against an authenticated session/webhook subscription lookup) so the fields consumed by `WebhookMetadata` cannot diverge from the payload actually authenticated by Shopify.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. edits a customer to fire `customers/update`). Shopify sends:
   - Headers: `X-Shopify-Topic: customers/update`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: `{"id": 123, ...}`
2. Attacker captures this exact `(raw_body, hmac)` pair.
3. Attacker sends a forged HTTP POST directly to the app's public webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::HmacValidator.validate` recomputes the HMAC over `raw_body` only, finds it matches, and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, body: <attacker's own data>, ...)` — the app now processes attacker-controlled data as if it belonged to the victim tenant.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
