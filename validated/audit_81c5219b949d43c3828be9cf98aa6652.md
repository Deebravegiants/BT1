### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook replay/relabeling - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate`, which checks the HMAC against `to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`. The `shop`, `topic`, and `webhook_id` values are read straight from HTTP headers and are never included in the signed bytes, yet they are passed unauthenticated into the dispatched `WebhookMetadata` that the host application's handler acts on.

### Finding Description
`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` value: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

`shop`, `topic`, and `webhook_id` are all derived from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` validates only this body-only HMAC, then dispatches using the unauthenticated header values: [4](#0-3) 

This breaks the intended identity binding `authenticated_bytes == acted_upon_bytes`: the HMAC only proves "Shopify produced this exact `raw_body` for *some* legitimate webhook," but the app's dispatch logic treats the header-supplied `shop` and `topic` as if they too were verified. Concretely:

- **Shop mismatch**: A merchant who legitimately installs the app on their own shop (`shop-a.myshopify.com`) receives real, validly-signed webhook deliveries for their own shop. Because headers are excluded from the signature, that merchant can resend the exact same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting `x-shopify-shop-domain: shop-b.myshopify.com`. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` calls the handler with `shop: "shop-b.myshopify.com"` — an attacker-chosen tenant identifier, matching an unauthenticated body that was never Shopify-signed for that shop.
- **Topic mismatch**: The same replay technique lets the attacker relabel a body originally signed for a benign topic (e.g. `orders/updated`) as a security/compliance topic such as `customers/redact` or `shop/redact`, causing the app's data-erasure or de-provisioning handler to run on attacker-controlled/mismatched data.

### Impact Explanation
This is a cross-tenant identity-binding failure: the value the gem treats as "the shop this webhook is for" is not covered by the same authentication check that proves the payload is genuine. Any host application that follows the documented pattern of using `WebhookMetadata#shop` (or `#topic`) to select which merchant/session/data to act on — the pattern shown in this gem's own docs and tests — inherits a cross-tenant write/manipulation vector, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The only prerequisite is having received at least one legitimately HMAC-signed webhook body for the target app (trivially available to any unprivileged merchant who installs the app on their own store, or to anyone who can otherwise capture one signed delivery). No access token, `client_secret`, or privileged credential is required — only header manipulation against the gem's webhook endpoint, which is exactly the "unprivileged internet user" threat model in scope.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (or otherwise cryptographically authenticate them), e.g. by including the relevant headers in `to_signable_string`, or by separately requiring the app to corroborate the header-derived `shop`/`topic` against server-side webhook subscription state before dispatch, so that `Registry.process` cannot be tricked into acting on header values that were not covered by the signature Shopify actually produced.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com`, topic `orders/updated`, with `raw_body = B` and header `x-shopify-hmac-sha256 = HMAC(secret, B)`.
2. Attacker (the merchant of shop-a, or anyone who captured this one delivery) resends a POST to the app's webhook route with the identical `raw_body = B` and identical `hmac`, but headers changed to `x-shopify-shop-domain: shop-b.myshopify.com` and/or `x-shopify-topic: customers/redact`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers per [5](#0-4) ; `HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC.
4. `Registry.process` looks up the handler for the (attacker-controlled) topic and invokes it with `shop: "shop-b.myshopify.com"`, per [6](#0-5) , causing the host app's business logic to run under a shop/topic identity that Shopify never actually signed for that body.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
