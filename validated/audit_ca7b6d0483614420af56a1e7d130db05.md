### Title
Operator QR-code session expiration is checked against a live, mutable config value instead of a value snapshotted at scan time - ([File: src/plans/mod.rs])

### Summary
The Orb's operator QR-code authorization window is bounded by `operator_qr_expiration_time`, a value that is fetched fresh from the shared, mutable `orb.config` at every check site rather than being captured once and stored alongside the `OperatorData` it protects. This mirrors the reported bug class exactly: an entity ("the action"/here, the scanned-operator session) has a time-bound validity, but the bound is re-evaluated using the *current* value of a runtime-updatable parameter instead of the value that was in effect when the entity was created.

### Finding Description
`OperatorData` is created with a `timestamp: Instant` captured at the moment the operator's QR code is scanned and verified: [1](#0-0) 

Every place that decides whether this operator session is still valid re-reads `operator_qr_expiration_time` live from the shared `Config` object at the top of `MasterPlan::run`/`do_signup`, and compares it against `operator_data.timestamp.elapsed()`: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

The config is periodically downloaded from the backend and swapped into the shared `Arc<Mutex<Config>>` at runtime: [6](#0-5) 

Because `operator_qr_expiration_time` is never pinned to the `OperatorData` at the time it was created (unlike `timestamp`, which *is* pinned), any config refresh that changes this duration retroactively changes the validity window of an *already scanned* operator session. This is the same root-cause pattern as the reported issue: a time-bound state object's expiration should be evaluated using the parameter value that was current at creation time, not a value that can be changed after the fact.

### Impact Explanation
The operator-scan step exists to (a) verify the operator is authorized and (b) capture fresh location data used later to validate the user's identity/authorization (`operator_data.location_data`, used in `user_status::request`). The elapsed-time check against `operator_qr_expiration_time` is the only mechanism preventing a stale operator session (and its stale location/authorization context) from being reused indefinitely. If the expiration duration is increased between the time the operator QR was scanned and the time it's checked (e.g. via a config refresh mid-loop, mid self-serve idle-wait, or mid-signup), sessions that were meant to have already expired remain "valid," allowing the orb to keep authorizing signups (including self-serve signups reachable by unprivileged end users) against stale operator/location context well past the originally intended bound. This directly parallels the reported class of bug: a mutable global parameter unintentionally extends the validity of an already-created, time-bound authorization.

### Likelihood Explanation
Config downloads happen periodically during normal long-running orb operation while the master loop is scanning QR codes / idling / running self-serve flows, so the race window is realistically reachable without any special operator privilege — it only requires the orb to still be within its idle/signup loop when a backend config update changes `operator_qr_expiration_time`. No attacker-controlled input is needed to trigger the check; the flaw is structural (same as the reported analog) rather than requiring an adversarial config push.

### Recommendation
Snapshot `operator_qr_expiration_time` into `OperatorData` at the moment the operator QR code is scanned/verified (alongside `timestamp`), and use that pinned value for all subsequent expiration checks (`scan_initial_qr_codes`, `idle_scan_user_qr_code`, `scan_remaining_qr_codes`, `do_signup`) instead of re-reading the live config value each time.

### Proof of Concept
1. Operator scans QR code; `OperatorData { timestamp: t0, .. }` is created while `operator_qr_expiration_time = T1` (small value, e.g. from live config).
2. Orb enters `idle_wait_for_signup_request` and remains idle without a user QR scan for close to `T1`.
3. Backend config refresh occurs (`Config::download_and_store`), updating `operator_qr_expiration_time` to `T2 > T1`.
4. All subsequent expiration checks (e.g. `scan_remaining_qr_codes`, line `operator_data.timestamp.elapsed() < operator_qr_expiration_time`) now use `T2`, so a session that should have expired under `T1` is treated as still valid, allowing the stale operator/location context to keep authorizing a signup beyond its originally intended window.
