### Title
Balance aliasing via a two-address "double-entry" token lets a single real deposit be counted twice by `Hinkal.transact`'s per-token balance check, minting unbacked shielded UTXOs - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` snapshots and validates per-token balances purely by calling `balanceOf()` on each address the caller lists in `circomData.erc20TokenAddresses`, and validates each index independently against `balanceDif == amountChanges[i] + utxoAmount[i]`. Nothing in the contract or the circuit checks that two distinct addresses in that array actually represent two economically distinct assets. An attacker who deploys a pair of addresses that both read/write the same underlying "balance" (a classic double-entry-point token pattern) can make one real balance movement satisfy the equality twice, minting shielded UTXOs worth 2X while the vault's real backing only moved by X.

### Finding Description
The equality claimed broken: `net tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts minted)`. Concretely, per index `i`:
```
balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]
``` [1](#0-0) 

`getBalancesForArray` computes each snapshot by calling `balanceOf(address(this))` on whatever address is supplied at `erc20TokenAddresses[i]`: [2](#0-1) 

The only uniqueness constraint on `erc20TokenAddresses` is enforced in the circuit, and it only checks that the raw field-element (address-as-uint256) values differ pairwise - it has no way to know whether two different addresses' `balanceOf` calls resolve to the same underlying ledger entry: [3](#0-2) 

Exploit flow using `EmporiumUpgradeable.runAction` (Emporium external action, attacker fully controls `stack.ops[].endpoint`/`callData`):
1. Attacker deploys `TokenA` and `TokenB`, two distinct contract addresses whose `balanceOf(hinkal)` both read the same shared storage/counter (e.g., a "fake deposit" counter), and whose `transfer()` is a no-op that returns `true` without ever decrementing that shared value.
2. Attacker calls `Hinkal.transact` with `erc20TokenAddresses = [TokenA, TokenB]`, `onChainCreation = [true, true]`, `amountChanges = [0, 0]` (required by `checkOnchainCreation` since `onChainCreation` is only legal for external actions and forces `amountChanges[i] == 0`): [4](#0-3) 
3. Inside `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are taken via the same aliasing `getBalancesForArray`, so a single op that bumps the shared counter by `X` is observed as `+X` for both `TokenA` and `TokenB`. `handleOut` then fires twice, once per index, each creating an on-chain UTXO of amount `X` (`TokenA`, `X`) and (`TokenB`, `X`): [5](#0-4) 
4. Back in `Hinkal.transact`, since both `transfer()` calls are no-ops, the shared value never actually decreases, so `newBalances[0] == newBalances[1] == oldBalances[0] + X`, giving `balanceDif[0] = balanceDif[1] = X`, which independently satisfies `balanceDif[i] == 0 + utxoAmount[i]` for both `i=0` and `i=1`. Both `require`s pass.
5. Two on-chain commitments of value `X` each are inserted into the tree - `2X` of shielded value minted - even though only a single fake counter bump of `X` (or, in the real-world "double entry point" case, only a single genuine deposit of `X`) ever happened.

The root cause is that the balance/UTXO accounting invariant is checked per-array-index using `balanceOf()` as the sole source of truth for "how much value moved," with no cross-index consistency check that different `erc20TokenAddresses` entries correspond to independent, non-aliased assets. This is the well-known "double entry point token" class of vulnerability (as previously exploited against protocols like PoolTogether via legacy/new TUSD address pairs), and Hinkal's unrestricted, user-supplied `erc20TokenAddresses` array (no token allowlist visible in `HinkalHelper`/`dimensionsCheck`/`checkOnchainCreation`) gives the attacker full freedom to pick or construct such a pair. The 6-decimal framing does not change the mechanics - all accounting in Solidity and the circuit is done in raw integer units; decimals only affect off-chain UI/circuit-input scaling, not the on-chain equality being exploited.

### Impact Explanation
An unprivileged attacker can mint shielded UTXOs backed by less real value than credited - directly matching "Critical: minting shielded value without backing (protocol insolvency)". In the fully-fake-token variant shown above, the attacker only harms themselves/gains worthless shielded balances of a token they created (no protocol harm, since nobody else holds `TokenA`/`TokenB`). The genuinely Critical instantiation requires a *real* third-party token with the double-entry-point property (legacy+new address pair resolving to the same ledger) being listed by Hinkal/used by victims; if the attacker deposits real value once through such a token and forces both address entries to be recognized, they can withdraw/redeem 2x the value later, at the expense of other depositors of that same real token - a direct insolvency/theft vector. The exploit is repeatable per double-entry-point token found and per Emporium transaction.

### Likelihood Explanation
Feasibility is high for the "self-controlled worthless token" instantiation (fully reproducible, no external dependency), but has no protocol impact by itself since the attacker only creates value in tokens nobody else holds. The Critical-severity instantiation is conditional on a genuinely valuable, real double-entry-point ERC20 being usable within Hinkal (no allowlist prevents listing arbitrary tokens, so this is plausible but depends on such a token existing/being deployed on the target chain and having non-negligible TVL routed through it in Hinkal). Attacker cost is limited to gas and, for the real-token case, one legitimate deposit of `X`.

### Recommendation
Do not rely solely on independent per-index `balanceOf()` deltas to authorize UTXO minting. Either (a) maintain Hinkal's own internal accounting ledger per canonical token identity instead of trusting external `balanceOf()`, (b) require/verify that all `erc20TokenAddresses` entries used in a single `transact` call are on an admin-curated allowlist of tokens known not to exhibit balance aliasing, or (c) sum all balance deltas and all UTXO amounts across the whole array and check the *aggregate* equality is consistent with a single unified real-token registry mapping, rejecting any two entries that resolve, via canonicalization, to the same underlying asset.

### Proof of Concept
Foundry test plan:
1. Deploy `SharedLedger` contract holding `uint256 balance`.
2. Deploy `TokenA` and `TokenB`, each implementing `balanceOf(address) => SharedLedger.balance` and a no-op `transfer()` that returns `true` without touching `SharedLedger.balance`; add a `fakeDeposit(uint256 x)` that increments `SharedLedger.balance`.
3. Register an `Emporium` external action instance whose `stack.ops` include one op calling `SharedLedger.fakeDeposit(X)`.
4. Craft `circomData` with `erc20TokenAddresses = [TokenA, TokenB]`, `onChainCreation = [true, true]`, `amountChanges = [0, 0]`, generate a valid proof (attacker's own keys/UTXOs, distinct address values satisfy circuit's `distinctErc20AddressChecks`).
5. Call `Hinkal.transact`; assert:
   - Real value change to Hinkal (`TokenA.balanceOf(hinkal) - oldBalance`, sampled once, ignoring aliasing) `== X`.
   - Sum of on-chain UTXO amounts minted (`TokenA` UTXO amount `X` + `TokenB` UTXO amount `X`) `== 2X`.
   - `2X != X` demonstrates minted shielded value exceeds real backing, breaking the stated invariant.
