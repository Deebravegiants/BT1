### Title
Orb Core skips backend-side biometric enrollment/duplicate verification for "user-centric" signups, allowing signups to be locally marked successful without any uniqueness check - ([File: src/plans/mod.rs])

### Summary
The reported Axelar ITS bug allows a bridging operation to be treated as valid and finalized locally even though the destination-side state (interchain token balance) was never actually initialized/verified against the canonical source of truth, causing a balance/state mismatch that can be exploited. The analogous flaw in `orb-core` is in `do_signup` (`src/plans/mod.rs`): when `user_centric_signup` is set, the Orb marks a signup as `Success` purely from a local, unverified signal, entirely skipping the one code path (`enroll_user::Plan::run` → `signup_post`/`signup_poll`) that queries the backend for identity uniqueness/duplicate detection.

### Finding Description
In `MasterPlan::do_signup`, after the biometric pipeline completes, the plan decides how to conclude enrollment: [1](#0-0) 

If `user_centric_signup` (taken directly from `qr_codes.user_data.user_centric_signup`, sourced from `backend::user_status::UserData`) is `true` and the orb config does not override it via `ignore_user_centric_signups`, the code **never calls `enroll_user`**. Instead it locally sets:
```rust
debug_report.enrollment_status(match signup_reason {
    SignupReason::Normal => enroll_user::Status::Success,
    _ => enroll_user::Status::Error,
});
success = signup_reason == SignupReason::Normal;
```
`signup_reason` is computed purely from local information — whether the biometric pipeline produced a result and whether local fraud detection flagged it: [2](#0-1) 

Crucially, the only real duplicate/uniqueness verification against the backend's enrolled-iris database happens inside `enroll_user::Plan::run`, via `signup_post::request` followed by polling `signup_poll::request`, whose response explicitly encodes backend duplicate detection: [3](#0-2) 

That backend round-trip is the source of truth for whether this identity/iris has already been enrolled elsewhere (analogous to the ITSHub balance check confirming the token is deployed/tracked on the destination chain). When `user_centric_signup` is true, this verification step is skipped entirely, exactly as the ITS bug skips balance-initialization enforcement on the destination chain and lets the transfer proceed regardless.

Compounding this, the on-orb fraud-detection logic that could otherwise catch some duplicate/liveness issues has been stubbed out to always return `false`: [4](#0-3) 

So for any `user_centric_signup` signup, "Normal" is guaranteed whenever the biometric pipeline itself succeeds, with zero backend confirmation of uniqueness — mirroring the report's root cause: local success/state is asserted without confirming initialization/validity against the authoritative external system.

### Impact Explanation
`result.success` and the enrollment status become divorced from what the backend actually knows about this identity, just as the ITSHub balance became divorced from real on-chain token supply once a transfer was accepted despite the destination not being initialized. Concretely:
- The Orb (and the self-serve app, via `SignupEnded { success, .. }` over Orb Relay) reports a “successful” unique signup even though the backend never checked this iris/identity for duplicates.
- This creates cross-signup state bleed: state that should only be asserted after backend-confirmed enrollment (uniqueness) is asserted purely from local, unauthenticated signup outcome, opening the door to the same identity being "signed up" multiple times as `Success` without the backend's own duplicate ledger ever being consulted for this signup.
- Downstream systems and the debug report/telemetry pipeline treat this as a normal, verified signup (`debug_report.signup_successful()`, `dd_incr!("main.count.signup.result.success.successful_signup")`), propagating an incorrect trust signal.

### Likelihood Explanation
This is not a race condition requiring front-running by an external attacker; it is a deterministic code path triggered whenever the backend-provided `user_centric_signup` flag is true (and `ignore_user_centric_signups` is not set), which is an intended production configuration path (not test-only, not requiring privileged/malicious infrastructure access). Any signup routed through this flag — the normal "user-centric"/self-serve flow — bypasses backend uniqueness verification, making the likelihood of divergence between locally-declared success and backend-confirmed identity state high whenever this mode is active.

### Recommendation
Do not fully bypass backend confirmation for `user_centric_signup` signups. At minimum:
- Still invoke the backend duplicate/uniqueness check (`signup_post`/`signup_poll` or an equivalent lightweight verification call) before declaring `enroll_user::Status::Success`, even if the full enrollment record differs for user-centric flows.
- Treat `signup_reason == SignupReason::Normal` as necessary but not sufficient for success; require an explicit backend acknowledgment analogous to the ITS team's fix of "restrict[ing] transfers if the token/balance isn't initialized yet."
- Reinstate or replace the fraud-detection path (`detect_fraud`) so that at least local fraud/liveness heuristics are not always short-circuited to `false`, reducing reliance on an entirely-skipped backend check.

### Proof of Concept
1. Configure the Orb backend to return `user_centric_signup: true` for a user QR-code session (as `backend::user_status::request` already supports and passes through unchanged) and ensure `ignore_user_centric_signups` is `false` (default). [5](#0-4) 
2. Run a signup through `do_signup`. The biometric pipeline succeeds (`pipeline.is_some()`), and `detect_fraud` unconditionally returns `false`. [6](#0-5) 
3. `signup_reason` resolves to `SignupReason::Normal`, and the success branch never calls `enroll_user` (i.e., never calls `signup_post`/`signup_poll` against the backend for duplicate/uniqueness verification). [1](#0-0) 
4. `result.success` is `true` and `SignupEnded { success: true, .. }` is relayed to the app, even though the backend's own biometric-duplicate database was never consulted for this specific signup — the same "operation proceeds despite unverified/uninitialized authoritative state" pattern as the ITS report.
