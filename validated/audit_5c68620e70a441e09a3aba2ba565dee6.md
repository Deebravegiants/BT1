### Title
NFT ownership can change during `flash_position` before the newly created debt and collateral are persisted - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` authorizes the original caller and mints the position NFT before invoking an arbitrary Wasm receiver. The borrowed position is kept in memory while the receiver executes, so the receiver can transfer the NFT during its callback. After the callback returns, the controller persists the debt and collateral to the account ID without rechecking NFT ownership. An attacker can therefore atomically sell an apparently empty position NFT and leave the buyer owning an account with newly created debt.

### Finding Description
`process_flash_position` authenticates only `caller` before account loading. For `account_id = 0`, `load_or_create_account` mints the NFT to the caller and returns the in-memory account. [1](#0-0) [2](#0-1) [3](#0-2) 

The function then mints debt into the in-memory account, forwards the measured tokens to `receiver`, and invokes `execute_flash_position` on that receiver. [4](#0-3) [5](#0-4) 

The position NFT is transferable through the normal non-fungible-token interface; the contract only restricts mint, burn, and upgrade to the controller. [6](#0-5) [7](#0-6) 

After the callback, the controller converts measured receiver payments into supply positions and calls `strategy_finalize`, which performs solvency checks and persists both account sides under the same account ID. There is no ownership recheck before persistence. [8](#0-7) [9](#0-8) 

A production-equivalent harness already demonstrates the critical sequence: during `execute_flash_position`, the receiver sends collateral to the controller and calls `PositionNft.transfer(from=self, to=target, token_id=account_id)`. [10](#0-9) 

### Impact Explanation
An attacker-controlled receiver can complete a sale or swap inside the callback, transfer the NFT to the buyer, and then let the controller finish writing the leveraged account. The buyer receives the NFT together with debt that was not visible as persisted account state when the callback began. [11](#0-10) 

The transferred account can remain solvent and still be worth materially less than the purchase price because its collateral is offset by newly recorded debt. The victim must repay the debt or undergo liquidation to recover collateral, while the attacker retains the sale proceeds and has no remaining authority over the position. [12](#0-11) [13](#0-12) 

### Likelihood Explanation
A single unprivileged user can reach this path through `Controller.flash_position(caller=receiver_contract, account_id=0, receiver=receiver_contract, ...)`; the receiver only needs to be a deployed Wasm contract and must return enough declared collateral for the final solvency checks. [14](#0-13) [15](#0-14) 

The attack requires a buyer or marketplace transaction to authorize payment and accept the NFT in the same transaction, but it does not require privileged access, oracle manipulation, leaked keys, or control of a listed asset. The existing test proves that the NFT transfer succeeds during the callback and that the account is finalized under the new owner. [16](#0-15) 

### Recommendation
Prevent an ownership change while a strategy has uncommitted account mutations. A robust fix is to make the position NFT non-transferable while a controller-managed pending-position lock is active, clear that lock only after `strategy_finalize` succeeds, and restore ownership state on failure by reverting the whole transaction.

Alternatively, persist a pending-position flag before the receiver callback and have `PositionNft.transfer`/`transfer_from` query the controller and reject transfers while the account has pending state. Merely rechecking ownership after the callback is insufficient if the intended semantics allow the receiver to sell the NFT before finalization.

### Proof of Concept
1. Deploy an attacker-controlled Wasm receiver that implements `execute_flash_position`.
2. The attacker calls `Controller.flash_position` with `caller = receiver`, `account_id = 0`, a flash-loanable `debt`, `receiver = receiver`, and `collaterals` naming collateral the callback can deliver.
3. `load_or_create_account` mints a new position NFT to the receiver, and `mint_and_forward` creates in-memory debt and sends the borrowed tokens to the receiver. [17](#0-16) [18](#0-17) 
4. Inside `execute_flash_position`, the receiver accepts the victim's purchase payment, transfers the required collateral to the controller, and calls `PositionNft.transfer(receiver, victim, account_id)`. [10](#0-9) 
5. The callback returns; the controller measures the collateral, deposits it, enforces solvency, and persists both supply and debt positions to the NFT account now owned by the victim. [8](#0-7) [9](#0-8) 
6. The harness test confirms this ownership change succeeds and leaves the new owner with positive supply and borrow balances. [19](#0-18)

                mode,

                amount,
                receiver: &receiver,
                data: &data,
                collaterals: &collaterals,
                refund_assets: &refund_assets,
            },
        )
    }
