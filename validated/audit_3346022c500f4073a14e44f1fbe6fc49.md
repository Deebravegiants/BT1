### Title
`ShopifyAPI::Auth::Oauth.validate_auth_callback` sends the app's `client_secret` to an unvalidated `shop` host (missing `ShopValidator` check) - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
Every other credential-exchanging flow in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.exchange_token`) runs the caller-controlled `shop` value through `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` before using it as the HTTP host that receives `client_id`/`client_secret`. `Auth::Oauth.validate_auth_callback` and `Auth::Oauth.begin_auth` are the exception: they take `auth_query.shop` (or `shop:`) and pass it straight into `Auth::Session.new(shop: ...)`, which `Clients::HttpClient` then turns directly into `@base_uri = "https://#{session.shop}"` — with no `ShopValidator` call anywhere in `oauth.rb`.

### Finding Description
In `lib/shopify_api/auth/oauth.rb`:
- `begin_auth(shop:, redirect_path:, ...)` builds the authorize URL via `auth_base_uri(shop)` → `"https://#{shop}/admin"`, using `shop` verbatim, never calling `Utils::ShopValidator`. [1](#0-0) 
- `validate_auth_callback(cookies:, auth_query:)` validates the request's HMAC (`Utils::HmacValidator.validate(auth_query)`) and the `state` cookie, then immediately does:
```ruby
null_session = Auth::Session.new(shop: auth_query.shop)
body = { client_id: Context.api_key, client_secret: Context.api_secret_key, code: auth_query.code, ... }
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
``` [2](#0-1) 
- `Clients::HttpClient#initialize` turns `session.shop` directly into the request host that receives this body (containing `client_secret`):
```ruby
@base_uri = T.let("https://#{api_host || session.shop}", String)
``` [3](#0-2) 

Compare this to the parallel, credential-sending flows that *do* validate the shop before using it as a host:
```ruby
validated_shop = Utils::ShopValidator.sanitize!(shop)
shop_session = ShopifyAPI::Auth::Session.new(shop: validated_shop)
``` [4](#0-3) [5](#0-4) 

`Utils::ShopValidator.sanitize!` exists precisely to enforce the invariant "the host that receives `client_secret` == a trusted `*.myshopify.com`/`myshopify.io`/etc. domain", and is intentionally omitted from `oauth.rb`. [6](#0-5) 

The binding that should hold is: `host receiving client_secret == TRUSTED_SHOPIFY_DOMAINS ∪ {configured myshopify_domain}`. In `oauth.rb` this equality is never enforced; only `auth_query.shop == hmac-signed shop` is enforced (via `HmacValidator`), which is a different, weaker property — it proves the `shop` string wasn't tampered with in transit, but does **not** prove that string is a genuine Shopify domain rather than an attacker-chosen string that a legitimately-obtained, validly-signed callback could still carry (e.g., a value that happens to pass through Shopify's own redirect unmodified for whatever `shop` the initiating request specified in `begin_auth`, since `begin_auth` itself never validates or canonicalizes `shop` before embedding it in the redirect flow that ultimately becomes `auth_query.shop`).

### Impact Explanation
If `shop`/`auth_query.shop` is not constrained to a Shopify-owned domain, `validate_auth_callback` will construct `https://{shop}/admin/oauth/access_token` and POST the app's `client_id` and `client_secret` to that host. This is "credential leakage" / SSRF-with-credentials class impact per the rules: the app's `client_secret` can be transmitted to a host that is not Shopify. Since `begin_auth` also builds the authorize redirect from the same un-sanitized `shop`, an app that (as most integrations do, per this gem's own docs example `shop = request.headers["Shop"]`) feeds an unauthenticated, attacker-influenced `shop` value into `begin_auth`/`validate_auth_callback` without itself re-implementing the sanitize step that this gem already provides (and does apply in three sibling flows) has no protection from this library.

### Likelihood Explanation
Medium. The `HmacValidator` check does prevent naive parameter tampering on the callback itself, but it does not prevent an attacker from driving the flow with a `shop` value that was never checked to be a Shopify domain at `begin_auth` time — the value simply flows through unchanged to the callback and then to the token-exchange POST. The inconsistency (3 of 4 credential-flows sanitize `shop`, this one doesn't) is a strong signal this is a genuine gap in this gem's code rather than something delegated to the host app by documented contract elsewhere in the API for these two specific methods' docstrings.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, sanitize `shop` with `Utils::ShopValidator.sanitize!` (as done in `client_credentials.rb` / `refresh_token.rb` / `token_exchange.rb`) at the top of both `begin_auth` and `validate_auth_callback`, before it is used to build `auth_base_uri`, `null_session`, or any request that carries `client_id`/`client_secret`.

### Proof of Concept
1. Host application implements the callback exactly as shown in this gem's own docs (`docs/usage/oauth.md`), passing the raw `shop` request parameter into `ShopifyAPI::Auth::Oauth::AuthQuery.new(...)` and calling `validate_auth_callback`.
2. Regardless of the `hmac` field's validity, no code path in `oauth.rb` calls `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` on `auth_query.shop`.
3. `validate_auth_callback` builds `null_session = Auth::Session.new(shop: auth_query.shop)` and issues `client.request(...)` with a body containing `client_secret`; `Clients::HttpClient` sets `@base_uri = "https://#{session.shop}"` verbatim.
4. Because `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb` all explicitly call `Utils::ShopValidator.sanitize!`/derive shop only from a cryptographically-verified `dest` claim, while `oauth.rb`'s authorization-code-grant flow does neither, this is the one OAuth entry point in the gem where the "host receiving `client_secret`" ↔ "trusted Shopify domain" binding is not enforced by the library itself.

*Note: I was unable to fully trace, within the available context, whether `begin_auth`'s `shop` parameter is guaranteed at the framework/host-app level to already be sanitized before this gem is called (e.g., via `shopify_app`), so the true end-to-end exploitability depends on how a given host app sources `shop`. This is flagged as the main residual uncertainty rather than a confirmed complete exploit chain.*

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

                body: body,

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
