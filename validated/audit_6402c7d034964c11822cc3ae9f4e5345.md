### Title
Extension-node length truncation via oversized storage key causes validator panic - (File: core/store/src/trie/mem/flexible_data/extension.rs)

### Summary
`EncodedExtensionHeader::from_input` truncates `extension.len()` to `u16` when building a memtrie extension node header, and `RawEncoder`/`encode_flexible_data` then uses this truncated length to size the allocation while copying the full untruncated slice, causing a slice-length-mismatch panic in `copy_from_slice`. Because `max_length_storage_key` is 4 MiB, an ordinary account can create a single `ContractData` trie key whose shared nibble path (extension) length exceeds `u16::MAX` (65535) bytes, triggering this on any node using memtrie.

### Finding Description
`TrieKey::ContractData::len()` is `col::CONTRACT_DATA.len() + account_id.len() + ACCOUNT_DATA_SEPARATOR.len() + key.len()` [2](#0-1) , and `key.len()` is bounded only by `max_length_storage_key = 4_194_304` [1](#0-0) . This byte string becomes the nibble path in the trie [3](#0-2) .

When a leaf/extension node's nibble path (the whole key minus common branch prefixes) has to be materialized as a memtrie extension node, `EncodedExtensionHeader::from_input` computes `length: extension.len() as u16` [4](#0-3) . If `extension.len()` exceeds 65535, this cast silently wraps/truncates. `flexible_data_length()` then reports the truncated (small) length [5](#0-4) , which `RawEncoder::encode_flexible` uses to allocate the target sub-slice: `let length = header.flexible_data_length(); header.encode_flexible_data(data, &mut self.data.subslice_mut(self.pos, length));` [6](#0-5) . But `encode_flexible_data` still calls `target.raw_slice_mut().copy_from_slice(&extension)` with the *original, untruncated* `extension` slice [7](#0-6) . `copy_from_slice` panics if source and destination slices have different lengths, so this call will panic deterministically whenever the extension exceeds 65535 bytes.

Since a single storage key of ~4 MiB is well within protocol limits and no code path clamps or rejects a trie extension/leaf nibble-path length against `u16::MAX` before reaching this encoder, a normal `FunctionCall` receipt performing `storage_write` with a key just under `max_length_storage_key` is sufficient — no need for "deeply nested colliding keys" as hypothesized in the question, since a single sufficiently long key already produces a leaf/extension node whose own nibble path exceeds 65535 nibbles/bytes.

This is reachable from an unprivileged account: submit a `FunctionCall` action invoking a contract that calls `storage_write` with an ~4 MiB key (or split across multiple calls if a single receipt's `max_arguments_length`/`max_receipt_size` is a constraint — `max_receipt_size` is effectively unbounded at `4_294_967_295`, and `max_arguments_length` is 4_194_304, matching `max_length_storage_key`, so the whole key can be passed in one call). This triggers `MemTrieUpdate` insertion into memtrie during chunk application on any node tracking that shard with memtrie enabled (default).

### Impact Explanation
This is a node panic / crash triggerable by any account holder against any validator or RPC node tracking the affected shard, causing a chain stall (all validators applying the same chunk deterministically panic) — this matches NEAR's "chain halt / consensus-critical node crash" bounty impact class, one of the most severe classes since it can as a liveness/DoS vulnerability affecting all nodes processing the malicious receipt.

### Likelihood Explanation
Highly feasible and fully reproducible: the only precondition is that the target account tracks the shard with memtrie (default configuration for all validators/chunk producers today), and the attacker needs one `storage_write` call with a key close to the 4 MiB `max_length_storage_key` limit — a standard, permitted operation requiring only sufficient gas/deposit for storage staking, no special privileges.

### Recommendation
- Add an explicit length check in `EncodedExtensionHeader::from_input` (and analogous flexible-data headers using `u16`/`u32` truncating casts) that returns an error or asserts the input length fits the header's width instead of silently truncating via `as u16`.
- Alternatively/additionally, enforce a protocol-level maximum nibble-path length for trie extension/leaf nodes (derived from `max_length_storage_key`/`max_length_returned_data` and column/account-id overhead) that is validated before the value ever reaches memtrie encoding, so an oversized key is rejected with a clean charged error rather than reaching an internal invariant violation.
- Add a debug/production assertion in `RawEncoder::encode_flexible`/`encode_flexible_data` that the header's computed flexible length equals the actual `InputData` length before calling `copy_from_slice`, converting a silent corruption/mismatched-panic into an immediate, clear internal-error signal for easier detection in testing.

### Proof of Concept
Unit test in `core/store/src/trie/mem/flexible_data/extension.rs` tests module (or a new test in `core/store/src/trie/mem/`):
1. Build a `Vec<u8>` extension byte slice of length `70_000` (> 65535).
2. Call `EncodedExtensionHeader::from_input(&extension)` and assert `header.length` wrapped to `70_000 as u16` (i.e., a small/incorrect value), demonstrating truncation.
3. Using `RawEncoder::new(arena, header.flexible_data_length())` (which allocates only the truncated size) then `encoder.encode_flexible(&header, &extension)`, assert the test panics inside `encode_flexible_data`'s `target.raw_slice_mut().copy_from_slice(&extension)` due to length mismatch (`target` slice length = truncated value, `extension` length = 70000).
4. Higher-level integration reproduction: construct a `TrieKey::ContractData` with a `key` of length approaching `max_length_storage_key` (4_194_304) such that its trie-encoded nibble path (accounting for shared prefixes with other keys under the same account) exceeds 65535 bytes, insert it via `MemTrieUpdate`/`Trie::update` with memtrie enabled, and assert the chunk application panics rather than returning a `StorageError`.
