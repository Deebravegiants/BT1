### Title
Liquidation reverts on stale/invalid oracle prices instead of falling back, risking positions becoming unliquidatable - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The `liquidate()` function relies on `price-resolve` to obtain both collateral and debt USD values. `price-resolve` unconditionally reverts (`ERR-ORACLE-INVARIANT`) whenever a price fails a freshness or "price > 0" legality check, with no fallback to a previous valid price. This mirrors the Tapioca finding where `Market.updateExchangeRate` reverted on an invalid rate during liquidation instead of falling back to the old rate, even though the code explicitly intends liquidations to proceed despite oracle trouble.

### Finding Description
`price-resolve` validates the resolved price with `oracle-price-legal` (price must be `> 0`) and `oracle-timestamp-fresh` (timestamp must be within `max-staleness` and not older than the last recorded update), and reverts the entire call with `ERR-ORACLE-INVARIANT` if either check fails: [1](#0-0) 

This function underlies `get-asset-value`, which is used to compute collateral/debt USD values inside `liquidate()`'s notional evaluation: [2](#0-1) 

It is also called directly for disabled collateral assets in `process-collateral-asset`, one of the core steps of the `liquidate()` flow, via `unwrap-panic`, which is even stricter (aborts on any error rather than propagating a typed error): [3](#0-2) 

`liquidate()` itself pulls in `notional-valued-assets`/`assets` derived from these price resolution paths before performing the health check and computing liquidation amounts: [4](#0-3) 

If a Pyth/DIA feed becomes stale (exceeds `max-staleness`) or momentarily reports a zero/invalid price — a transient, non-malicious oracle hiccup, not an attacker-caused manipulation — every call into `price-resolve` for that asset reverts. Since `liquidate()` needs prices for both the debt asset and every collateral asset (including disabled collateral resolved on-demand), a single unavailable feed is enough to make the entire liquidation transaction for that position revert, exactly analogous to the referenced Tapioca bug where the exchange-rate fetch inside the liquidation path reverted instead of degrading gracefully to a previously known rate.

### Impact Explanation
While the price feed for an asset is stale/unavailable, positions collateralized in or borrowing that asset cannot be liquidated at all — `liquidate()` unconditionally reverts rather than falling back to the last valid cached price (the `last-update` map already tracks a previous timestamp but not a previous valid price value that could be reused). During this window, an undercollateralized position's health can continue to deteriorate (e.g., due to continued interest accrual or the underlying market moving further) with no way to trigger liquidation, which can push the protocol toward bad debt / insolvency for that market, matching the "protocol insolvency" and "temporary freezing of funds" impact classes.

### Likelihood Explanation
Oracle staleness/temporary unavailability is a realistic, low-attacker-effort operational condition (feed update lag, no fresh Pyth submission within `max-staleness`, DIA update delay), not a deliberate design decision like disabled-collateral liquidation exclusion. Because `liquidate()` requires successful price resolution for potentially multiple assets (debt + all collateral, including a fallback on-demand resolve for disabled collateral via `unwrap-panic`), the probability that at least one required feed is stale during a liquidation attempt is non-trivial, especially during volatile markets when liquidations are most needed and oracle networks are most likely to lag.

### Recommendation
In `price-resolve` (and the `unwrap-panic` disabled-collateral fallback in `process-collateral-asset`), do not hard-revert the entire liquidation when a price is stale or invalid. Instead, cache the last legal/fresh price per `{type, ident}` alongside `last-update`, and when freshness/legality checks fail, fall back to that last-known-good price so `liquidate()` can still proceed (optionally gated behind a liquidation-only code path, mirroring the "Oracle can fail but we still need to allow liquidations" intent from the referenced report). Non-liquidation flows (borrow/withdraw health checks) can continue to use the strict revert-on-stale behavior.

### Proof of Concept
1. Asset X's oracle feed (Pyth or DIA) stops updating, or a submitted update's timestamp exceeds `max-staleness` relative to `stacks-block-time`, or transiently returns/normalizes to a `0` price.
2. A borrower holding/borrowing asset X becomes undercollateralized (LTV crosses `ltv-liq-partial`).
3. A liquidator calls `liquidate()`; internally this reaches `price-resolve` for asset X (via `get-asset-value`/notional evaluation, or via `process-collateral-asset`'s on-demand resolve for disabled collateral).
4. `oracle-price-legal`/`oracle-timestamp-fresh` fails, causing `(asserts! ... ERR-ORACLE-INVARIANT)` (or the `unwrap-panic` in the disabled-collateral path) to abort the transaction.
5. The liquidation cannot execute until the feed recovers, during which the position's risk to the protocol persists or worsens. [5](#0-4)

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
