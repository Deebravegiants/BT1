I have enough evidence now to confirm the finding. `CallDispatcher.dispatch()` is `external` with zero access control, yet the contract's `receive()` makes it a routine holder of ETH/ERC20 balances during the intent-fill and HFT calldata-execution flows. Any address left with a transient balance is drainable by anyone.

### Title
Unrestricted `CallDispatcher.dispatch()` allows anyone to drain funds temporarily held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch(bytes)` is declared `external` with no caller restriction (no `onlyOwner`, no allow-listed caller, no reentrancy/ownership check of any kind). It also implements `receive() external payable {}`, and by design is used as a temporary escrow: `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents` route predispatch/postdispatch assets through it, and `HyperFungibleToken`/`WrappedHyperFungibleToken` mint/unlock tokens directly to it when a cross-chain message carries calldata (`to: CALL_DISPATCHER`). Anyone observing (or front-running) a pending balance on the dispatcher — or exploiting a partial/failed multi-step flow that leaves residue there — can call `dispatch()` directly with an arbitrary `Call[]` whose `to`/`value`/`data` they fully control, and move out any ETH or ERC20 balance currently sitting on the contract.

### Finding Description
`CallDispatcher.dispatch()` has no access control: [1](#0-0) 

This mirrors exactly the bug class in the external report: a fund-moving function reachable by any `msg.sender`, whose transfer target and amount are attacker-supplied parameters (`Call.to`, `Call.value`, `Call.data`), with the only guard being that `to` must have code (`NotContract`) — trivially bypassed by deploying a minimal attacker-controlled contract.

The dispatcher is intentionally designed to hold balances between the moment tokens/ETH land on it and the moment the owning app (`IntentGatewayV2`, `HyperFungibleToken`, etc.) issues the sweep-back `dispatch()` call:
- Predispatch: `IntentGatewayV2.placeOrder` sends predispatch assets to `_params.dispatcher`, then calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, and only afterwards sweeps required inputs back — there is a window, and any call the dispatcher makes to external protocols (swaps, etc.) can also leave leftover balance: [2](#0-1) 
- Postdispatch: `IntentsBase._execute` dispatches solver-supplied output calldata to the dispatcher and only sweeps residue back afterward: [3](#0-2) 
- Cross-chain token bridging: `HyperFungibleToken.onAccept` mints tokens straight to the `to` address from the message, which documented usage sets to the `CallDispatcher` address so bridged funds are available to spend, before the dispatcher runs the attached calldata: [4](#0-3) 

Because one `CallDispatcher` instance is shared across all callers that route calldata through it (a single deployment address is referenced from `DeployHFT.s.sol`, `DeployWrappedHFT.s.sol`, `DeployIntentGateway.s.sol`, and used by every user's predispatch/postdispatch/cross-chain calldata), any value it is holding at any point in time — including native ETH forwarded via `Call.value` for a Uniswap swap, per the documented WETH-mode example — is a shared pool an attacker can sweep out with a single unauthenticated `dispatch()` call before the legitimate sweep-back transaction executes.

### Impact Explanation
Direct theft of user/protocol funds: any ETH or ERC20 tokens that transiently sit on `CallDispatcher` (from IntentGateway predispatch/postdispatch legs, HyperFungibleToken/WrappedHyperFungibleToken calldata-mint flows, or any other integrator routing assets through this dispatcher) can be redirected to an attacker-controlled contract by simply calling `dispatch()` with a `Call[]` naming the attacker's contract as `to`. Given the dispatcher is a single shared, permissionless-execution contract used across the intents and token-bridging surfaces, this is a Critical/High severity fund-theft primitive, directly reachable from a single unprivileged transaction with no proof, signature, or state verification required — matching the external report's "distributive function with no access control" bug class.

### Likelihood Explanation
High. No special conditions, races, or privileged roles are needed beyond timing a call to land while the dispatcher briefly holds value — something that naturally occurs on every predispatch/postdispatch/cross-chain-calldata flow, and can additionally be triggered/amplified by front-running or by a reverted downstream call in a multi-step batch that leaves residual balance. Because `dispatch()` requires no proof at all (unlike the correctly-restricted `onAccept`/`onGetResponse`/governance paths reviewed elsewhere in this codebase, which all gate on `onlyHost` plus source/relayer checks), this is trivially and repeatedly exploitable by any address, including MEV bots watching the mempool for transactions that fund the dispatcher.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the specific app contract(s) that are meant to use it (e.g., an `onlyOwner`/allow-listed-caller pattern set at construction, or deploying a dedicated dispatcher instance per calling contract instead of sharing one globally), and/or ensure balances never persist on the dispatcher across transactions (e.g., enforce atomic zero-balance invariants at the end of `dispatch()`, or have callers pre-fund and sweep in the same call with a reentrancy-safe pattern). At minimum, gate the function so only the registered `IntentGatewayV2`/`HyperFungibleToken` instances (or their configured admin) may invoke it.

### Proof of Concept
1. Attacker deploys a trivial contract `Sink` with a payable fallback (or a function to receive an ERC20 `transfer`).
2. Attacker monitors the mempool/chain state for any transaction that causes `CallDispatcher` to (temporarily) hold ETH or ERC20 balance — e.g., a user's `IntentGatewayV2.placeOrder` predispatch leg (`evm/src/apps/IntentGatewayV2.sol:244-256`) sending native ETH/ERC20 to the dispatcher before the sweep-back call, or a `HyperFungibleToken.send(...)` cross-chain transfer whose destination `to` is the `CallDispatcher` address (per the documented pattern in `docs/content/developers/evm/hyper-fungible-token/hyper-fungible-token.mdx`).
3. Before the legitimate sweep-back `dispatch()` call executes (or immediately after, if any residue remains), attacker calls:
   ```solidity
   Call[] memory calls = new Call[](1);
   calls[0] = Call({ to: address(Sink), value: address(callDispatcher).balance, data: "" });
   // or an ERC20 transfer call moving the full token balance to Sink
   callDispatcher.dispatch(abi.encode(calls));
   ```
4. `dispatch()` executes unconditionally (only requiring `Sink` to have code), transferring the dispatcher's ETH/token balance to the attacker-controlled `Sink` contract, with no ownership, source, or proof check anywhere in the call path.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
