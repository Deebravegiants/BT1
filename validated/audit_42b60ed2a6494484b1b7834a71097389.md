### Title
Webhook `shop`, `topic`, and `webhook-id` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `HmacValidator` covers `@raw_body` alone [1](#0-0) . However, `Registry.process` dispatches the webhook using the unauthenticated `shop-domain`, `topic`, and `webhook-id` headers taken directly from the request and passes them straight into the handler as trusted tenant/routing metadata [2](#0-1) .

### Finding Description
The intended binding is: `hmac == HMAC(secret, bytes_verified)` should equal `HMAC(secret, bytes_the_app_acts_on)`. Here, `bytes_verified` is only `@raw_body` [3](#0-2) , while the fields the app actually acts on for tenant identification (`shop`) and routing (`topic`), and idempotency (`webhook_id`), come from HTTP headers that are entirely outside the signed payload:

```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [4](#0-3) 

`Registry.process` validates only the body's HMAC and then forwards `request.shop`, `request.topic`, and `request.webhook_id` unchanged to the registered handler:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [2](#0-1) 

Because `shop`, `topic`, and `webhook_id` are not part of `to_signable_string`, any party who possesses one valid `(body, hmac)` pair signed with the app's real secret — e.g. by legitimately receiving a webhook for their own store from Shopify, or by capturing/replaying any previously delivered webhook body — can resubmit that exact body/HMAC pair to the app's webhook endpoint while substituting arbitrary `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` header values. `HmacValidator.validate` will still return `true` because it only recomputes and compares the HMAC of the untouched body [5](#0-4) .

### Impact Explanation
Host applications built on this gem commonly key their per-tenant data operations off `WebhookMetadata#shop` (e.g., "delete data for shop X", "update installation state for shop X") since that is the field the library exposes as the authenticated tenant identifier. Because `shop` is not bound to the signed body, an attacker can cause the receiving app to attribute a captured/valid webhook body to a different, victim shop of their choosing — a cross-tenant data-integrity/confidentiality issue. Re-labelling the `topic` header can also cause the same signed body to be routed to a different handler than the one Shopify intended, expanding the blast radius further (e.g., invoking a `customers/redact` handler with an unrelated body, or bypassing per-topic business logic).

### Likelihood Explanation
Any unprivileged internet user who operates their own Shopify development/test store connected to the target app can trivially obtain a legitimately-signed `(body, hmac)` pair for their own shop (a normal, unprivileged webhook delivery), then replay that exact body to the target app's public webhook endpoint with forged `shop-domain`/`topic`/`webhook-id` headers. No access token, `api_secret_key`, or privileged account on the victim tenant is required — only the ability to send an HTTP request to the app's webhook receiver, which is by design internet-reachable.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the body, e.g., via Shopify's webhook event ID), so tampering with any of these headers invalidates the HMAC. At minimum, document that `WebhookMetadata#shop`/`#topic` must be cross-checked by the host app against expected/subscribed values before being used to select tenant data, since this gem does not itself bind them to the signature.

### Proof of Concept
1. Attacker installs the target app on their own `attacker-shop.myshopify.com` development store.
2. Shopify delivers a legitimate webhook (e.g., `orders/create`) to the app's endpoint, signed with the app's real `api_secret_key`; attacker captures the raw body `B` and header `x-shopify-hmac-sha256: H`.
3. Attacker replays the same `B`/`H` pair to the app's endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over `B`, which is unmodified [6](#0-5) .
5. `Registry.process` invokes the topic handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [7](#0-6) , causing the host app to act on attacker-controlled data under the victim shop's identity.
