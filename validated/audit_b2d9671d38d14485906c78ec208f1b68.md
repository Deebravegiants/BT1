### Title
Unrestricted `superApprove` in `HyperFungibleTokenImpl` Allows Anyone to Grant Themselves Unlimited Allowance Over Any Holder's Balance - (File: `evm/src/utils/HyperFungibleTokenImpl.sol`)

### Summary
`HyperFungibleTokenImpl.superApprove(address owner, address spender)` is a `public` function with **no access control** (no `onlyRole`, no `msg.sender == owner` check, no modifier at all) that directly calls the internal `_approve(owner, spender, type(uint256).max)`. Any unprivileged address can call this function to grant an arbitrary `spender` (including itself) unlimited ERC-20 allowance over any `owner`'s balance, without that owner's consent, then drain the tokens via `transferFrom`.

### Finding Description [1](#0-0) 

```solidity
/**
 * @notice Helper function for tests - approves unlimited tokens
 * @param owner The owner of the tokens
 * @param spender The spender address
 */
function superApprove(address owner, address spender) public {
    _approve(owner, spender, type(uint256).max);
}
```

The comment states this is a "Helper function for tests," but it ships as a normal `public` function in the production contract `HyperFungibleTokenImpl`, with no gating whatsoever — unlike every other privileged function in the same file (`mint`, `burn`, `grantMinterRole`, `grantBurnerRole`, `revokeMinterRole`, `revokeBurnerRole`), all of which correctly use `onlyRole(...)` [2](#0-1) .

`HyperFungibleTokenImpl` is not a mock/test-only artifact — it is deployed in the production deployment script as the protocol's fee token when no external fee token is configured: [3](#0-2) 

```solidity
faucet = new TokenFaucet{salt: salt}();
feeTokenInstance = new HyperFungibleTokenImpl{salt: salt}(admin, "Hyper USD", "USD.h");
// Grant minter role to faucet so it can mint tokens
feeTokenInstance.grantMinterRole(address(faucet));
feeToken = address(feeTokenInstance);
```

This fee token (`USD.h`) is set as `HostParams.feeToken` on `EvmHost`, meaning it is the token used to pay ISMP relayer/protocol fees for dispatching cross-chain messages [4](#0-3) . Any holder of this token (users funding cross-chain dispatch fees) is exposed: an attacker calls `superApprove(victim, attacker)` to self-approve unlimited spending rights over the victim's balance, then calls `transferFrom(victim, attacker, balance)` to drain it — no signature, permission, or interaction from the victim is required.

### Impact Explanation
This is a direct, unauthorized-control/theft-of-funds primitive on a token used within the Hyperbridge fee-payment path. Any unprivileged address can seize full spending control over any other holder's balance of this token and steal all their funds, mirroring the "unchecked ownership/control transfer" bug class from the referenced report — except here the blast radius is every current and future holder of the token, not just a single owner slot.

### Likelihood Explanation
The function is `public`, requires no privileged role, and is directly reachable in a single transaction by any address. Given `HyperFungibleTokenImpl` is used as the deployed fee token in `DeployIsmp.s.sol`, exploitation only requires the attacker to identify token holders (trivial via `Transfer`/`Approval` events or on-chain balance scans) and call the two functions.

### Recommendation
Remove `superApprove` from the production contract entirely, or restrict it to a test-only build (e.g., move it into a test harness/mock contract that inherits `HyperFungibleTokenImpl`, not into the shipped implementation). If any similar unrestricted helper exists elsewhere, gate it behind `onlyRole(DEFAULT_ADMIN_ROLE)` or remove it before deployment.

### Proof of Concept
```solidity
// Victim holds `feeTokenInstance` (USD.h) tokens to pay dispatch fees.
// Attacker, with no role/permission:
feeTokenInstance.superApprove(victim, attacker);
// Now attacker has type(uint256).max allowance over victim's balance
feeTokenInstance.transferFrom(victim, attacker, feeTokenInstance.balanceOf(victim));
// Victim's entire balance is drained without consent.
```
