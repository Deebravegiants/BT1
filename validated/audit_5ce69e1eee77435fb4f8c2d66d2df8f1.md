### Title
Consensus-Incentive Reward Misattribution via `messages[0]`-only Signer Extraction Allows Reward Theft from Legitimate Relayers - (File: modules/pallets/consensus-incentives/src/impls.rs)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic accepts an unsigned, permissionless batch of `Message`s (including `ConsensusMessage`s whose proofs are public data that anyone can fetch and re-submit, per the project's own relayer docs). After the batch executes, `pallet-consensus-incentives::on_executed` is invoked once with the *entire* batch's `messages` and `events`. It derives the rewarded `relayer_account` **exclusively from `messages.get(0)`** [1](#0-0)  and then pays that single account for **every** `StateMachineUpdated` event collapsed from the whole batch [2](#0-1) , regardless of which message/signer actually produced each state-machine advancement.

### Finding Description
The reward mechanism is meant to pay "the relayer that delivered a consensus update" (per-block cost × blocks advanced) [3](#0-2) . However, attribution of *who* gets paid is computed once per batch, from only the first message's embedded `signer` field, not per-message:

```
let maybe_relayer_account = messages.get(0).and_then(|first_message| {
    if let Message::Consensus(consensus_msg) = &first_message.message {
        ...
        Signature::decode(&mut &consensus_msg.signer[..])
            .ok()
            .and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
            .map(|pub_key| pub_key.into())
``` [1](#0-0) 

Then it loops over the highest `latest_height` seen per `state_machine_id` across *all* `StateMachineUpdated` events in the batch and pays that single `relayer_account` for each one:

```
for (state_machine_id, latest_height) in highest_per_state_machine {
    ...
    let _ = Self::process_message(state_machine_height, state_machine_id, relayer_account.clone().into());
}
``` [4](#0-3) 

Since `handle_unsigned` takes a caller-supplied `Vec<Message>` with no origin check (it's `ensure_none`), any account can compose a batch consisting of:
1. A trivial/cheap `ConsensusMessage` (e.g., a 1-block, low-`cost_per_block` chain) signed with the attacker's own key as `messages[0]`.
2. One or more *other* consensus messages for higher-value chains (an expensive authority-set rotation, or a chain with a high `StateMachinesCostPerBlock`) whose underlying `consensus_proof` bytes are public and freely obtainable by anyone (per the project's stated design that proofs "can be generated by anyone, as they are freely provided by its connected chains").

Because attribution only reads `messages[0]`, the attacker collects the reward for advancing *every* state machine touched in the batch, not just the one they authored in position 0. A legitimate relayer who already produced/broadcast a signed `ConsensusMessage` for the valuable chain (e.g., visible in the transaction pool, since this is an unsigned extrinsic with no submitter-binding) can have that message's on-chain effect (the state advance) captured and its associated reward redirected to whoever manages to be `messages[0]` in the batch that ultimately executes it.

This is structurally analogous to the LunaFi "flaw in reward calculation" root cause: the protocol computes/attributes a reward using data that does not actually correspond one-to-one with the entity that performed the rewarded work, allowing an attacker to redirect funds meant for others.

### Impact Explanation
This allows an unprivileged submitter of `pallet-ismp::handle_unsigned` to drain `pallet-consensus-incentives`' treasury reward for state-machine advances that another relayer actually delivered proofs for, and to mint the associated `ReputationAsset` for themselves instead [5](#0-4) . This is a direct theft-of-funds vector against the relayer incentive treasury and undermines the reward accounting the pallet exists to guarantee, meeting the Medium/High bar for "relayer fee and reward accounting" analogs in scope.

### Likelihood Explanation
Exploitation requires only the ability to submit an unsigned extrinsic with a crafted `Vec<Message>` and observability of other pending/broadcastable consensus proofs, both of which are explicitly permitted/expected by design (proofs are "freely provided," and `handle_unsigned` has no origin restriction). No privileged role, governance, or off-chain collusion is needed—only mempool visibility or independently reproducing another chain's public consensus proof, making this reachable from a single relayed transaction.

### Recommendation
Attribute the reward for each `StateMachineUpdated` event to the signer of the *specific* `ConsensusMessage` that produced that state machine's height increase, not to `messages[0]` for the whole batch. This requires correlating each `Message::Consensus` entry with its resulting `StateMachineUpdated` event(s) (e.g., by processing per-message rather than aggregating `events` independently of `messages`), and verifying each message's own embedded signature before crediting that message's chain-specific reward.

### Proof of Concept
Conceptual (verification of exact reachability/exploitability of `handle_unsigned` batching semantics was not fully completed due to iteration limits — see caveat below):
1. Attacker watches for (or independently reconstructs) a valid `ConsensusMessage` proof for state machine `B`, a high-`CostPerBlock` chain, originally intended to be submitted/rewarded to relayer `V`.
2. Attacker submits `handle_unsigned(origin_none, [ConsensusMessage_A_signed_by_attacker (cheap chain, e.g. 1 block), ConsensusMessage_B (proof for chain B)])` in a single unsigned extrinsic, ahead of `V`'s own submission.
3. `pallet_ismp` processes both messages, producing `StateMachineUpdated` events for chains `A` and `B`.
4. `pallet_consensus_incentives::on_executed` extracts `relayer_account = attacker` from `messages[0]` only, then iterates `highest_per_state_machine` (containing both `A` and `B`), calling `process_message` for **both** state machines with `relayer_account = attacker` [4](#0-3) .
5. Attacker is paid the treasury reward for chain `B`'s block-span advancement (`(latest_height − baseline) * block_cost`) despite not being the legitimate deliverer, and `V`'s intended reward is lost/misdirected.

**Caveat:** I was unable to fully inspect `pallet-ismp`'s `handle_unsigned`/`ValidateUnsigned` implementation in this session (ran out of tool iterations) to confirm whether it de-duplicates or otherwise restricts batch composition (e.g., rejecting mixed-signer batches, or requiring the extrinsic submitter's identity to match `messages[0]`'s signer). This should be verified against `modules/pallets/ismp/src/lib.rs`'s `handle_unsigned`/`validate_unsigned` logic before treating this as fully confirmed; if such a check exists, this analog would need re-scoping.

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
