### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant shop-attribution forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw JSON body for HMAC verification, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook are taken from unauthenticated HTTP headers that are never part of the signed payload. This breaks the identity binding `authenticated_shop == attributed_shop`, mirroring the `MsgCreate2` class of bug where a field that determines a critical identity/outcome (the salt/address) is not actually covered by the mechanism meant to constrain it (EIP-1014 spec vs. the narrower `uint64` type). Here, the mechanism meant to authenticate the whole webhook (HMAC-SHA256) does not cover the header fields that determine *which tenant* the webhook is attributed to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are outside the HMAC's scope: [2](#0-1) 

`HmacValidator.validate` only checks the `hmac` field against `to_signable_string` (i.e., the body), never touching `shop`/`topic`/`webhook_id`: [3](#0-2) 

`Registry.process` relies on this same validated-body/unvalidated-headers split: it verifies the HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the host app's handler: [4](#0-3) 

Because the signature only binds the body bytes, any party who possesses one genuine `(raw_body, hmac)` pair for a topic that is signed with the app's secret (for example, a merchant who has installed the app in their own store and thus legitimately receives webhooks with valid HMACs for their own shop) can replay that exact body+HMAC to the app's webhook endpoint while substituting a different `shopify-shop-domain` (and/or `shopify-topic`/`shopify-webhook-id`) header value. `HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the body belongs to an arbitrary shop the attacker chooses. This breaks the equality that should hold: `shop authenticated by HMAC == shop attributed to the data`.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker who legitimately holds one valid `(body, hmac)` pair (trivially obtainable by installing the app themselves, since Shopify signs every webhook it sends to any installed shop with the same `api_secret_key`) can forge the shop attribution of that payload to any other shop domain string of their choosing. Any host application that uses `WebhookMetadata#shop` to route/attribute state (e.g., write order/customer data, trigger uninstall/redact flows, or key persistence) under the assumption that a passing HMAC guarantees the header-reported shop is correct, is exposed to cross-tenant data confusion/injection under another tenant's identity. This matches the Critical "cross-tenant access" impact category, since a shop-scoped signal (topic/shop/webhook_id) that the host app relies on for tenant separation is not actually bound by the cryptographic check that gem callers are told guarantees authenticity.

### Likelihood Explanation
Likelihood is realistic for any unprivileged internet user who can install the app as a merchant in their own low-value test/free store: they obtain genuine `(raw_body, hmac)` pairs signed with the app's real secret for any topic, then replay those bytes with a forged `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` header to the app's public webhook endpoint. No access to `api_secret_key`, TLS interception, or social engineering is required — only ordinary use of the app as a legitimate but hostile merchant.

### Recommendation
Bind the routing/attribution headers into the signed material, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the HMAC check (e.g., verify them against Shopify's `X-Shopify-*` values that Shopify itself derives from the same signed delivery, or require the host app to independently confirm the reported shop against a known/installed-shop allowlist before trusting `WebhookMetadata#shop`). At minimum, document prominently that `Registry.process`'s HMAC check does not authenticate the `shop`/`topic`/`webhook_id` headers, since callers currently treat a passing `HmacValidator.validate` result as authenticating the entire `Request`, including these header-derived fields.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, completing OAuth normally (no special privilege).
2. Shopify sends a legitimate webhook to the app's endpoint, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — valid per `HmacValidator.compute_signature`.
3. Attacker replays the exact same request but sets `shopify-shop-domain: victim-shop.myshopify.com` (leaving `B` and `H` untouched).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully since only header presence is checked, not header authenticity.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares it to `H` — this passes because `B` is unchanged. [5](#0-4) 
6. The registered handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, attributing the attacker's own order payload to `victim-shop.myshopify.com` in the host application, despite the HMAC never having authenticated that shop value.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
