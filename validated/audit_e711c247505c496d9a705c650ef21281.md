### Title
Webhook `shop` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` returns the value of the `shopify-shop-domain`/`x-shopify-shop-domain` header, but `Request#to_signable_string` — the data actually HMAC-verified in `Utils::HmacValidator.validate` — only ever returns `@raw_body`. The `shop` field used downstream to identify the tenant is therefore never part of the signed payload.

### Finding Description
`Webhooks::Registry.process` validates the request with `Utils::HmacValidator.validate(request)` and, if it passes, immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and dispatches it to the app's registered handler [1](#0-0) .

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` [2](#0-1) , and for `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [3](#0-2) . Meanwhile `shop` is pulled from an HTTP header that is not part of `@raw_body` at all [4](#0-3) .

This breaks the identity binding: `shop trusted by handler == shop covered by HMAC`. Before the request: `hmac = HMAC(secret, raw_body)`, `shop header = S1`. After an attacker's substitution: `hmac` unchanged (still valid because it's only over `raw_body`), `shop header = S2` (any other onboarded shop's domain). `HmacValidator.validate` returns `true` in both cases because it never inspects the header, so `Registry.process` calls the handler believing the event originated from `S2` while the signature only proves the *body* came from Shopify (or a previous legitimate webhook capture), not that `S2` is the originating shop.

### Impact Explanation
An app handler that trusts `WebhookMetadata#shop` (returned by `Registry.process`) to select which merchant's data/session to act on can be tricked into performing a cross-tenant action — e.g., processing a `shop/redact` or `orders/create`-style payload under a different shop's identity, or looking up/mutating another tenant's stored session or data — despite passing HMAC "verification". This matches a cross-tenant access / authentication-bypass style impact, since the trust boundary the gem is supposed to enforce (an HMAC-verified webhook is deemed authentic for the shop it claims) does not actually bind `shop` to the signature.

### Likelihood Explanation
Exploitation requires only a network-reachable webhook endpoint of an app using this gem and knowledge of one valid `(raw_body, hmac)` pair for the correct topic (webhooks of the same shape/topic are frequently near-identical across shops, and an attacker who has ever received/observed one legitimate webhook delivery — e.g., to their own installed test shop for `app/uninstalled` or a similar topic — can replay the body with a different `shop-domain` header). No `api_secret_key`, access token, or privileged account is required; only the ability to send an HTTP POST to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally other identifying headers) inside the HMAC-covered signable string, or otherwise independently re-verify that the `x-shopify-shop-domain` header corresponds to a shop the app actually has an active session/installation for before dispatching to the handler. At minimum, document that `WebhookMetadata#shop` is not cryptographically bound by `Utils::HmacValidator.validate` and must be revalidated by the consuming application (e.g., cross-checked against `SessionRepository`) before being trusted for tenant-sensitive operations.

### Proof of Concept
1. Capture one legitimate webhook delivery to any endpoint using this gem: raw body `B`, header `x-shopify-hmac-sha256: H` (valid for `B`), and `x-shopify-shop-domain: victim-shop.myshopify.com`.
2. Replay the exact same `B` and `H`, but change the header to `x-shopify-shop-domain: attacker-owned-shop.myshopify.com` (or vice-versa, spoofing as `victim-shop`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4) ; since validation only checks `raw_body` against `H`, it returns `true` unchanged.
4. `request.shop` [4](#0-3)  now returns the attacker-supplied shop domain, and `WebhookMetadata.new(shop: request.shop, ...)` is passed to the handler [6](#0-5) , which will act on that shop's identity with a payload the gem still reports as "HMAC valid."

          received_signature = verifiable_query.hmac
