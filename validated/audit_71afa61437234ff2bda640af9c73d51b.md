## Title
`Webhooks::Request` HMAC verification covers only `@raw_body`, letting the attacker-supplied `shop-domain`/`topic`/`webhook-id` headers be trusted unauthenticated — (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` proves nothing about the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers [1](#0-0) . `Registry.process` nonetheless forwards the raw, unverified `request.shop` and `request.topic` straight into `WebhookMetadata`, which the host app treats as the authenticated tenant identity for the delivered `parsed_body` [2](#0-1) . An attacker who has ever received one legitimately signed webhook (from their own dev shop, using the app's shared `api_secret_key`) can replay that exact `(raw_body, hmac)` pair to the host app's endpoint with an arbitrary `shop-domain`/`topic` header, and it will pass `HmacValidator.validate` unchanged.

## Finding Description
The intended binding is: `HmacValidator.validate(request) == true` should imply that **all** attacker-observable identity fields used downstream (`shop`, `topic`, `webhook_id`, `body`) were authenticated together as issued by Shopify for that shop/topic. In reality the binding that holds is only `hmac == HMAC(api_secret_key, raw_body)` — nothing else.

Trace:
- `Utils::HmacValidator.validate` calls `validate_signature`, which computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac` [3](#0-2) .
- For `Webhooks::Request`, `to_signable_string` is defined as `@raw_body` only — headers are excluded from the signed payload [1](#0-0) .
- `shop`, `topic`, and `webhook_id` are read directly from attacker-controlled HTTP headers with no cross-check against the signature [4](#0-3) .
- `Registry.process` validates the HMAC once, then unconditionally builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and dispatches to `@registry[request.topic]&.handler` — routing decision and tenant attribution both derive from the unauthenticated headers [2](#0-1) .
- `webhook_id` is read but never tracked/deduplicated anywhere in `Registry` or `Request`, so a captured `(raw_body, hmac)` pair can be replayed indefinitely with different header combinations.

Exploit flow: the attacker creates their own development shop, installs the app, and receives one legitimately signed webhook delivery from Shopify — giving them a valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` (the same secret is used for every merchant of that app, since `Context.api_secret_key` is app-level, not per-shop). The attacker then sends their own HTTP POST directly to the host app's webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but substituting `x-shopify-shop-domain` with the victim merchant's domain (and/or `x-shopify-topic` with a different registered topic, e.g. `app/uninstalled`). `HmacValidator.validate` still returns `true` because it only checks `raw_body`. `Registry.process` dispatches the handler for the spoofed topic with `WebhookMetadata#shop` set to the victim's domain and `parsed_body` containing attacker-chosen content. Any host-app handler that uses `data.shop` to decide "whose records to touch" (e.g., delete/rotate the stored access token on `app/uninstalled`, write order/customer data, etc.) now acts on the victim tenant using attacker-supplied data — a cross-tenant authentication bypass.

No existing guard prevents this: `HmacValidator.validate` only covers the body; there is no `ShopValidator.sanitize!` call on `request.shop`, no `state` comparison, and no webhook-id replay tracking anywhere in `lib/shopify_api/webhooks/`.

## Impact Explanation
This breaks the SINGLE IDENTITY invariant: the shop identity used by the handler (`WebhookMetadata#shop`, from the raw header) is not the same authenticated identity as the one that actually produced the signed body. Any host app that authorizes per-tenant actions (updating shop records, revoking/rotating access tokens on `app/uninstalled`, writing order/customer data) based on `WebhookMetadata#shop` can be made to attribute attacker-controlled data/actions to an arbitrary victim shop, or dispatch a signed body under an unintended topic. This is a cross-tenant access issue, repeatable at will against arbitrary victim shop domains once the attacker has captured any single valid signed webhook body from their own installation.

## Likelihood Explanation
Preconditions are low-cost and fully within an unprivileged attacker's stated capabilities: install the app on their own dev shop, receive one legitimately signed webhook (or generate an empty-body one, e.g. some topics send `{}`), then craft raw HTTP requests to the app's public webhook endpoint with spoofed `shop-domain`/`topic` headers. No secret material is required — the header spoofing works precisely because the gem never covers headers in the HMAC signable string. This is fully repeatable and does not depend on race conditions or timing.

## Recommendation
Include `shop-domain`, `topic`, and `webhook_id` in the signed/verified material (or otherwise cryptographically bind them to the body before trusting them), and/or require the host app to independently verify the shop identity against its own session/install records rather than trusting `WebhookMetadata#shop` directly. At minimum, document that `request.shop`/`request.topic` are NOT covered by HMAC verification so host apps don't misuse them as an authenticated identity, and add webhook-id tracking to prevent replay of previously seen deliveries.

## Proof of Concept
```ruby
# test/webhooks/registry_spoofed_shop_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistrySpoofedShopTest < Test::Unit::TestCase
      def test_shop_and_topic_headers_are_not_covered_by_hmac
        body = "{}"
        hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
        encoded_hmac = Base64.encode64(hmac)

        victim_called = false
        attacker_topic_called = false

        victim_handler = TestHelpers::FakeWebhookHandler.new(lambda do |data|
          assert_equal("victim-shop.myshopify.com", data.shop) # attacker-controlled header, not authenticated
          victim_called = true
        end)

        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "app/uninstalled", path: "path", delivery_method: :http, handler: victim_handler,
        )

        # Attacker's own legitimately-signed (body, hmac) pair, replayed with a spoofed shop header
        # and a different topic than whatever it was originally delivered for.
        spoofed_headers = {
          "x-shopify-topic" => "app/uninstalled",
          "x-shopify-hmac-sha256" => encoded_hmac,
          "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker chooses this
          "x-shopify-webhook-id" => "replayed-id-attacker-controls",
        }

        request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: spoofed_headers)

        assert(ShopifyAPI::Utils::HmacValidator.validate(request)) # passes despite spoofed shop/topic
        ShopifyAPI::Webhooks::Registry.process(request)

        assert(victim_called, "handler executed with attacker-chosen shop identity despite no verification of shop header")
      end
    end
  end
end
```
Assertions on both sides of the binding: `HmacValidator.validate(request)` returns `true` (body-only check passes) while `request.shop` equals the attacker-chosen `"victim-shop.myshopify.com"` — demonstrating that a valid HMAC over the body does not imply the shop/topic headers are authentic, violating the intended `verified(shop, topic, body) == true` binding.
