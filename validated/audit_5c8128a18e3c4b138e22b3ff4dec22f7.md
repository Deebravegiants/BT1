### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook by HMAC-validating only the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` header as the tenant identity passed to the app's handler. Because the shop domain is not part of the signed material, an attacker who controls one legitimate shop can replay a captured (body, hmac) pair while swapping the `shop-domain` header to impersonate a different, victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the unauthenticated header and never checked against the HMAC: [2](#0-1) 

`Registry.process` validates only that the body's HMAC matches the app's shared secret, then forwards `request.shop` (attacker-controllable) straight into the handler's metadata, with no re-check that this shop is the one the HMAC was actually issued for: [3](#0-2) 

`Utils::HmacValidator.validate` (and `validate_signature`) only ever consumes `verifiable_query.to_signable_string`, i.e. the body — the shop header plays no role in the signature computation: [4](#0-3) 

Since a single app-wide `api_secret_key` signs webhooks for every shop that installs the app, the signature over the body is shop-agnostic. The binding the gem should enforce is:
`shop_the_HMAC_was_computed_for == shop_delivered_to_handler`
but the gem only enforces `hmac(body) == received_hmac`, entirely independent of `shop`. Any attacker who has installed the app on their own store (a normal, unprivileged action) can capture a genuine `(raw_body, hmac)` pair from their own webhook deliveries, then POST that exact `raw_body`/`hmac` pair to the target app's public webhook endpoint while substituting `x-shopify-shop-domain` for a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the shop header), and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` reporting the victim's shop, while the body content is entirely attacker-controlled from their own store.

### Impact Explanation
This breaks the tenant-isolation boundary the HMAC is supposed to provide: an app relying on `WebhookMetadata#shop` (as returned by this gem) to select which merchant's data store/session to update can be made to apply attacker-controlled webhook payloads under a victim shop's identity — a cross-tenant access/data-integrity issue, since the host app has no way, using only what this gem's `Webhooks::Request`/`Registry` exposes, to detect that the shop and the signed body are not actually correlated.

### Likelihood Explanation
The attack requires only a free Shopify Partner/development store, installation of the target app, and capturing one legitimate webhook delivery to that store — all achievable by any unprivileged user with no special credentials, no access to `api_secret_key`, and no leaked tokens. No timing constraints are needed since HMAC validation and shop selection are done independently of any nonce/replay protection tied to the shop.

### Recommendation
Bind the `shop` (and ideally `webhook_id`/topic) into the signed material, or at minimum have `Registry.process`/`HmacValidator.validate` cross-check the delivered `shop` header against a shop known to be associated with the specific webhook subscription (e.g., via `webhook_id` lookup) rather than trusting the header verbatim once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, capturing `raw_body`, `x-shopify-hmac-sha256`, and other headers.
2. Attacker sends an HTTP request to the app's public webhook route with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `raw_body` against the secret.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the registered handler with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though the signature was never bound to that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
