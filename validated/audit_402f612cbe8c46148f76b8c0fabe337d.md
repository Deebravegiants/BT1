### Title
Unsigned, predictable session cookie value lets an attacker impersonate any shop's offline session - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
`SessionUtils.cookie_session_id` returns the raw `shopify_app_session` cookie value with no signature, MAC, or ownership check. Because `SessionUtils.offline_session_id(shop)` is defined as the fully deterministic, non-secret string `"offline_#{shop}"`, and non-embedded apps rely solely on this cookie for `current_session_id`, an attacker can set `Cookie: shopify_app_session=offline_<victim-shop>.myshopify.com` on a request and have the host app resolve and use the victim's real offline `Session` (including its access token) from the app's session storage.

### Finding Description
The broken binding: the code implicitly assumes `cookie_session_id(cookies) == <session id actually issued by this gem to this browser>`. In reality `cookie_session_id` just does: [1](#0-0) 

with no verification that the value originated from this app's own OAuth flow. `offline_session_id` is: [2](#0-1) 

which is 100% derivable from the shop's public `.myshopify.com` domain — no secret, nonce, or per-install randomness is mixed in.

For non-embedded apps, `current_session_id` unconditionally trusts the cookie: [3](#0-2) 

The only place the gem legitimately sets this cookie is after a successful, HMAC-validated OAuth callback, where it sets `cookie.value = session.id` (i.e., `offline_#{shop}` for offline sessions): [4](#0-3) 

But `SessionCookie` itself carries no cryptographic binding to the browser or to the OAuth transaction — it's just a `name`/`value`/`expires` struct with no signature: [5](#0-4) 

Attack: attacker knows (or guesses) `victim-shop.myshopify.com` (public information). They send any request to the non-embedded app with `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`. `current_session_id` calls `cookie_session_id`, which returns that exact attacker-chosen string unchanged. The host app (per this gem's documented pattern) then looks up `Auth::Session` from its session storage keyed by that id and finds the victim's real, previously-persisted offline session — including its live access token — and uses it for the current request. No HMAC, JWT, or state check is ever consulted in this code path, because those guards (`HmacValidator.validate`, `JwtPayload`'s `aud` check, `Context.embedded?` branch) only apply to the embedded/OAuth-callback paths, not to the plain cookie fallback for non-embedded apps.

### Impact Explanation
This is a cross-tenant authentication bypass: an unprivileged attacker forces the host app to operate as the victim merchant, using the victim's real offline access token for API calls, data reads/writes, and any privileged actions the app performs on the merchant's behalf. It is repeatable against any shop whose `.myshopify.com` domain the attacker knows (which is public/guessable), with zero cost per attempt (just a header on an HTTP request). This matches "Critical - cross-tenant access."

### Likelihood Explanation
Preconditions: the host app must be non-embedded (or fall back to the cookie path), use this gem's documented `current_session_id`/session-store pattern, and have previously completed OAuth for the victim shop (i.e., the victim installed the app — a normal, expected state, not an attacker precondition). No secrets, no valid HMAC, no access token are required from the attacker. The shop domain is public. This is trivially and repeatably exploitable.

### Recommendation
Do not trust the raw cookie value as a session identifier. Either (a) sign/MAC the cookie value with a per-app secret (e.g., HMAC using `Context.api_secret_key`) and verify it in `cookie_session_id`, or (b) store an unguessable random session token in the cookie that indirectly maps to the shop's session server-side, decoupling the cookie value from the deterministic `offline_#{shop}` id, or (c) use Rails' encrypted/signed cookie jar exclusively so `value` can't be forged.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_cookie_session_id_accepts_forged_offline_session_id
  victim_shop = "victim-shop.myshopify.com"

  # Binding 1: offline_session_id is fully deterministic/public
  predicted = ShopifyAPI::Utils::SessionUtils.offline_session_id(victim_shop)
  assert_equal "offline_victim-shop.myshopify.com", predicted

  # Binding 2: attacker-supplied cookie equal to that predicted string
  forged_cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => predicted }

  result = ShopifyAPI::Utils::SessionUtils.cookie_session_id(forged_cookies)

  # No verification performed: attacker's guess is returned verbatim
  assert_equal predicted, result
  assert_equal "offline_victim-shop.myshopify.com", result
end
```
This demonstrates both sides of the equality (`offline_session_id(victim_shop)` and the attacker-forged cookie value) match with zero additional verification inside `cookie_session_id`, confirming the host app's session store would resolve the victim's real offline `Auth::Session`.
