### Title
Token address collision via ambiguous seed concatenation in `create_token_seed` allows squatting/collision of distinct (collection, name) token objects - (File: `aptos-move/framework/aptos-token-objects/sources/token.move`)

### Summary
`create_token_seed` builds the deterministic seed for a token's object address by naively concatenating `collection_bytes || "::" || name_bytes` with no delimiter-escaping or length-prefixing, and no restriction preventing `"::"` from appearing inside either `collection` or `name`. This is structurally the same bug class as the reported Solidity issue: different logical inputs can serialize to the identical byte sequence, which is then fed into a single deterministic derivation (there, `abi.decode`; here, `sha3_256` via `create_object_address`), producing identical outputs for distinct inputs.

### Finding Description [1](#0-0) 
constructs the seed as `*collection.bytes()` + `b"::"` + `*name.bytes()`. This seed is passed unmodified into [2](#0-1) 
which hashes `source || seed || 0xFE` to derive the token's object address deterministically. Because the concatenation uses a two-character separator that is not guaranteed to be absent from either component, two distinct `(collection, name)` pairs can produce byte-identical seeds — e.g. `collection = "A::B", name = "C"` yields `"A::B::C"`, and `collection = "A", name = "B::C"` also yields `"A::B::C"`. Both map to the exact same derived object address for a given creator.

Length checks only bound the total length: [3](#0-2) 
There is no validation rejecting `"::"` substrings inside `collection` or `name`, so an attacker fully controls both fields (both are plain `String` inputs to token/collection creation entry functions) and can engineer such collisions at will.

### Impact Explanation
If an attacker can predict or control both `collection` and `name` strings passed to token creation, they can pre-create (front-run) a named object at the address that a legitimate creator's distinct `(collection, name)` pair would later resolve to. Since named objects cannot be deleted once created (per `object::create_named_object` semantics) and `create_object_internal` will abort with `EOBJECT_EXISTS` if the address is already occupied, the legitimate creator's token creation transaction will permanently fail once the address is squatted — denial of legitimate token/collection minting and irreversible loss of the intended, deterministic namespace for that creator (the "custody" of the object address/identity is broken: two logically distinct assets are forced to contend for one physical storage slot, and the attacker's earlier occupation wins). This can also be leveraged to block re-deployment of specific collection/token names that integrators rely on for deterministic addressing (e.g., marketplaces, indexers, and other tooling that compute expected token addresses off-chain via `create_token_address`) — the attacker can occupy a computed address ahead of the real owner, effectively hijacking the identity slot for value that has not yet been created, which the Custody Pivots explicitly call out ("Object creation ... must preserve the intended controller" and "Permanent lock or non-recoverable loss of object-held ... value").

### Likelihood Explanation
This requires an attacker to control or predict both `collection` and the future `name` for a not-yet-created token before the legitimate creator, and to craft a colliding string containing `"::"`. This is a real but not fully unprivileged path: exploitation depends on the attacker being able to observe/predict the exact strings a specific creator will use, and creation itself still requires the attacker to hold a signer that can call `create_named_object`/`create_token_address`/collection creation entry points. Given these constraints, likelihood is moderate rather than trivially critical: it is a genuine collision bug rooted in this codebase (unlike the external report, which is a decode-length issue), but the attack window/precondition (predicting exact future collection/name strings) limits practical exploitability compared to fully unprivileged, always-available attacks.

### Recommendation
Use a collision-resistant, unambiguous encoding for the seed in `create_token_seed` (and any other place concatenating variable-length strings for address derivation), e.g., BCS-serialize `(collection, name)` as a tuple (which length-prefixes each field) rather than raw byte concatenation with a static separator, or reject `"::"` and other separator sequences from collection/token names outright.

### Proof of Concept
```
let creator = @0xCAFE;

// Attacker precomputes collision:
let collection_a = string::utf8(b"A::B"); let name_a = string::utf8(b"C");
let collection_b = string::utf8(b"A");    let name_b = string::utf8(b"B::C");

let addr_a = token::create_token_address(&creator, &collection_a, &name_a);
let addr_b = token::create_token_address(&creator, &collection_b, &name_b);

assert!(addr_a == addr_b, 0); // both resolve to sha3_256(creator || "A::B::C" || 0xFE)
```
Attacker calls `create_named_object`/token-creation flow with `(collection_a, name_a)` first to claim `addr_a`; the legitimate creator's later attempt to create the token/collection identified by `(collection_b, name_b)` aborts with `EOBJECT_EXISTS` in `object::create_object_internal`, permanently blocking that creator's intended token identity at the deterministic address.

*Note: I was unable to fully verify from the index whether any upstream entry-function-level validation (outside `token.move`/`collection.move`) rejects `"::"` in name/collection strings before reaching `create_token_seed`; the code I reviewed shows only length checks (`ETOKEN_NAME_TOO_LONG`, `ECOLLECTION_NAME_TOO_LONG`). If such content restriction exists elsewhere in the entry-function wrappers, this finding would not hold — I recommend confirming this in the full `aptos_token::token` / `aptos_token_objects::token`/`collection` public entry function bodies, which were only partially covered by the index.*

    /// Named objects are derived from a seed, the token's seed is its name appended to the collection's name.
    public fun create_token_seed(collection: &String, name: &String): vector<u8> {
        assert!(name.length() <= MAX_TOKEN_NAME_LENGTH, error::out_of_range(ETOKEN_NAME_TOO_LONG));
        let seed = *collection.bytes();
        seed.append(b"::");
        seed.append(*name.bytes());
        seed
    }

    public fun create_object_address(source: &address, seed: vector<u8>): address {
        let bytes = bcs::to_bytes(source);
        bytes.append(seed);
        bytes.push_back(OBJECT_FROM_SEED_ADDRESS_SCHEME);
        from_bcs::to_address(hash::sha3_256(bytes))
    }
