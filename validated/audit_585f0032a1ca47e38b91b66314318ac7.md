Based on my research, I found a concrete analog to the Derby M-24 flashloan bug in Hyperbridge's phantom-order price aggregation / inventory-fold pipeline.

### Title
Solver can flashloan token balance to force a permanently-inflated `PoolBidder.liquidity` reading that manipulates published `LiquidityPool` swap rates - (File: `sdk/packages/indexer/src/services/liquidityPool.service.ts`)

### Summary
`aggregatePhantomBids` prices a phantom order's leg by a liquidity-weighted **selection** (`weightedMedian`), where a solver's weight is a live, unauthenticated point-in-time ERC-20/ERC-4626 balance read (`getBalance`/`getTotalSolverBalance`). A solver holding over half the leg's weight sets the exact published price. That price and the solver's balance then propagate into `PoolBidder.liquidity`, which is folded via `foldInventoryReadings` in a way that only ever raises the stored value from a new `SolverInventoryReading`, never lowers it on a stale/older-postdated key, and the merged `LiquidityPool.sellRate`/`buyRate` is depth-weighted by this same, possibly transiently-inflated, liquidity. Because balance-of-record is a raw spot read triggerable by the solver's own actions (a bid, a vault deposit/withdraw, a fill), a solver can transiently inflate its own on-chain balance (e.g. via a flashloan or self-funded transient deposit) at the moment its balance is swept/read, permanently biasing the weight/price/rate the protocol publishes and that `IntentGateway.quoteIntent` subsequently uses to price real orders for other users — mirroring the Derby `Game.sol` bug where a user flashloans capital to skew a weight (`DeltaAllocations`) that determines subsequent protocol behavior, all bracketed by the same window of control the attacker holds.

### Finding Description
Per leg, a phantom bid's price influence is weighted by "the solver's total balance for that token (native + ERC-4626 vault venues)" [1](#0-0) , read live via `getBalance`/`getTotalSolverBalance` inside `runAggregation` [2](#0-1) , itself a plain `balanceOf`/`maxWithdraw` call with no time-lock or vesting [3](#0-2) .

`weightedMedian` is explicitly documented as a **selection, not a blend**: "a solver holding over half the leg's weight sets the published price verbatim" [4](#0-3) , confirmed in the flow doc: "a solver holding over half the leg's weight sets the published price verbatim, and inventory in the wrong token buys no influence on that leg" [5](#0-4) .

The resulting `medianPrice` and bidder weight become `PoolBidder.liquidity` and feed `LiquidityPool.sellRate`/`buyRate` via a depth-weighted mean [6](#0-5) . Separately, when an on-chain event (fill, escrow release, or a **vault Deposit/Withdraw**) re-reads a solver's balance and publishes a `SolverInventoryReading`, `foldInventoryReadings` applies it to `PoolBidder.liquidity` if it merely postdates the row's last snapshot/refresh time — with no check that the balance is genuinely durable capital [7](#0-6) . The parallel `LiquidityProviderBalanceV2` series is explicitly "only ever raised, never lowered" when two readings land on the same key [8](#0-7) . Both mechanisms are triggerable by the solver itself: `YieldVaultService.recordLedger` publishes a fresh reading on the solver's own vault `Deposit`/`Withdraw` [9](#0-8) , and the read is pinned to that event's own block [10](#0-9) .

`IntentGateway.quoteIntent` prices real user orders directly from this aggregate `LiquidityPool.buyRate`/`sellRate` [11](#0-10) , so a manipulated rate directly determines what real users receive when filling intents.

### Impact Explanation
Since the balance read is a raw spot check with no minimum holding period, a solver can transiently inflate the exact balance that is about to be swept (e.g. via a flashloaned deposit into the tracked ERC-4626 vault, or a large transient wallet balance right before triggering its own Deposit/Withdraw event) to:
1. Win `weightedMedian` outright for a leg and set the exact published price for a phantom order, or
2. Push a much larger `PoolBidder.liquidity`/depth value into the pool merge, since a subsequent reading can only raise (never lower) the recorded value at that key.

The resulting skewed `sellRate`/`buyRate` is then consumed by `IntentGateway.quoteIntent` to price real orders for other users, meaning a malicious solver can cause real users to receive quotes at a manipulated exchange rate — directly analogous to the flashloan-driven allocation manipulation in the Derby report, where a single attacker-controlled window of inflated capital is used to bias a weight/allocation value that downstream logic treats as trustworthy.

### Likelihood Explanation
The attack requires no privileged role — any address that can act as (or spoof, via a delegated EIP-7702 solver account) a phantom bidder, or any tracked vault depositor, can trigger the balance re-read at a moment of their choosing by depositing/withdrawing from the tracked vault or submitting/timing a phantom bid. The read is a simple RPC call against "latest" chain state with no snapshot delay or averaging, so a flashloan-sized, single-block balance inflation is sufficient to dominate the weighted median or ratchet up the sticky "only raised, never lowered" liquidity figure.

### Recommendation
- Do not weight `weightedMedian` or `PoolBidder.liquidity` by a single spot balance read; require a time-weighted average balance (TWAB) or a minimum holding duration before a balance change is credited.
- Remove or bound the "only raised, never lowered" rule for `LiquidityProviderBalanceV2`/folded `PoolBidder.liquidity` so a reading can also decrease the recorded value once it is confirmed stale, closing the ratchet that lets a single inflated reading persist.
- Consider requiring balance/inventory reads used for pricing to be sourced from a delayed or averaged block rather than the block in which the triggering event (bid, deposit, fill) occurred, to remove same-block flashloan manipulation.

### Proof of Concept
1. Attacker controls (or is delegated to) a `SolverAccount` that bids on a phantom order leg whose output token the attacker holds little of.
2. In one transaction: flashloan a large amount of the leg's output token, deposit it into the tracked ERC-4626 vault (or simply hold it in wallet) long enough for `getBalance`/`getTotalSolverBalance` (called by `aggregatePhantomBids` or `publishReadings`) to observe it at "latest" — repay the flashloan once the balance-affecting on-chain action (bid submission / vault deposit event) has been recorded on-chain.
3. `weightedMedian` selects the attacker's quoted price as the leg's `medianPrice` (per weight-majority rule) [12](#0-11) , or the vault `Deposit` triggers `publishProviderInventory`, writing a `SolverInventoryReading` with the inflated balance [13](#0-12) .
4. `foldInventoryReadings` applies this reading to `PoolBidder.liquidity` (raised, since it postdates prior samples) and re-merges `LiquidityPool.sellRate`/`buyRate` depth-weighted by the now-inflated liquidity [14](#0-13) .
5. A subsequent, smaller, genuine balance reading cannot fully correct the `LiquidityProviderBalanceV2` figure because it "is only ever raised, never lowered" [15](#0-14) , and `PoolBidder.liquidity` remains at the inflated value until another reading happens to postdate it.
6. Real users calling `IntentGateway.quoteIntent` now receive a quote priced off the manipulated `sellRate`/`buyRate`, extracting value from users trading against the skewed rate.

// Liquidity-weighted median of solver quotes. Each quote's influence is proportional to `weight` —
// the solver's total balance for the output token across native + vault venues — so a solver that
// can actually deliver size moves the price more than one quoting on thin liquidity. Returns the
// lower weighted median: the smallest price whose cumulative weight reaches half of the total.
// Zero-weight quotes contribute nothing.
//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price

// The one rate-merge policy: depth-weighted average, falling back to the unweighted mean when
// the whole sample set carries zero depth (so a price is still reported). Every merge in this
// file — collapsed legs, the cross-chain pool merge, and the divergence alarm's consensus —
// must agree on this, hence the single home.
function weightedRate(samples: { rate: bigint; depth: bigint }[]): bigint {
	const depth = samples.reduce((acc, sample) => acc + sample.depth, 0n)
	return depth > 0n
		? samples.reduce((acc, sample) => acc + sample.rate * sample.depth, 0n) / depth
		: samples.reduce((acc, sample) => acc + sample.rate, 0n) / BigInt(samples.length)
}
