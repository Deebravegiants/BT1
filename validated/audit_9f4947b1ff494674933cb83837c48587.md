### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are taken from unauthenticated HTTP headers and are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body. Every other piece of identifying data handed to the app's handler — `shop`, `topic`, `webhook_id`, `api_version` — is read straight from HTTP headers that are excluded from the signed content. Anyone who can produce (or replay) one valid `(body, hmac)` pair can freely vary these headers, so the gem will deliver attacker-chosen shop/topic/webhook_id metadata to the app's `WebhookHandler` as if it were authenticated.

### Finding Description
`Webhooks::Request` implements `VerifiableQuery` and defines the signable content as the raw body only: [1](#0-0) [2](#0-1) 

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
```

`Registry.process` validates the request using exactly this HMAC/`to_signable_string` pair, then forwards the header-derived `shop`, `topic`, `webhook_id`, and `api_version` straight to the registered handler without any further binding check between the signed body and these header fields: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

`HmacValidator.validate` confirms only that `hmac == HMAC(secret, raw_body)`: [4](#0-3) 

The broken identity binding is the equality that the gem implicitly assumes but never enforces:
`HMAC_signed_content == {shop, topic, webhook_id, api_version, body}` — in reality `HMAC_signed_content == {body}` only. `shop` (the tenant identity) is not part of what is cryptographically bound.

### Impact Explanation
Because `shop` (and `topic`/`webhook_id`) are unauthenticated, an unprivileged internet user who can obtain any single legitimately-signed `(body, hmac)` pair for the app (e.g., by installing the app on their own store and capturing a real webhook delivery, or by discovering a leaked/replayed webhook payload) can resend that exact body/hmac to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `Registry.process` will accept it as valid (the HMAC still matches the unchanged body) and hand the handler a `WebhookMetadata` claiming the event came from a different, victim shop. Any app logic that trusts `WebhookMetadata#shop` to scope data writes, lookups, or session selection is exposed to cross-tenant data confusion/injection — the app processes attacker-supplied data under another merchant's identity. This satisfies the Critical "cross-tenant access" category.

### Likelihood Explanation
Any actor who can install the app on a shop they control (a normal, unprivileged flow for public/embedded Shopify apps) can capture a real webhook payload with a valid HMAC and then freely replay it to the app's public HTTP endpoint with a forged `shop-domain` header, since the endpoint accepts unauthenticated internet traffic and only checks the body-only HMAC. No secret material or privileged access is required beyond normal app installation.

### Recommendation
Include the routing/identity headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content that the HMAC covers, or otherwise cryptographically bind them (e.g., have the app independently look up/verify that the `shop` belongs to a session/installation that is expected to receive this topic) before trusting `WebhookMetadata#shop` in `Registry.process`. At minimum, document prominently that `shop`/`topic`/`webhook_id` are unauthenticated and must be independently validated by consuming apps.

### Proof of Concept
1. Install the target app on attacker-controlled shop `evil.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: headers `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-shop-domain: evil.myshopify.com`, `x-shopify-topic: orders/create`, plus `raw_body`.
2. Resend the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, raw_body)` — unchanged — and returns `true`.
4. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's original body>, ...)` and invokes the handler, which now operates on `victim.myshopify.com`'s tenant context using attacker-supplied event data.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
