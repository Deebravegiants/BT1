### Title
Webhook shop-domain identity spoofing via unauthenticated header — HMAC only covers the body, not `shop`/`topic`/`webhook-id` (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the `shop-domain` (and `topic`, `webhook-id`, `api-version`) HTTP headers — none of which are covered by that HMAC — as the identity of the shop that generated the event.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against this signable string [2](#0-1) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from HTTP headers with no cryptographic binding to the body or to the HMAC at all [3](#0-2) .

`Registry.process` validates the HMAC and, if it matches, immediately constructs `WebhookMetadata` using `request.shop` as the trusted tenant identity passed to the app's handler [4](#0-3) . There is no check anywhere in this path that the `shop-domain` header is consistent with the body, with a stored session, or with any value covered by the signature.

The binding that should hold is:
`shop_header == shop_that_produced(raw_body)`

but the code only proves:
`HMAC(raw_body, secret) == received_hmac`

which says nothing about which shop the body belongs to. Since the same app-level shared secret is used to sign webhooks for *every* shop that has the app installed, anyone who can install the app on their own shop (an ordinary, unprivileged merchant/tenant — no `api_secret_key`, access token, or Shopify admin credentials required) can legitimately receive a genuine `raw_body` + valid `hmac` pair for their own store, then replay that exact body/HMAC pair to the target app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to claim to be a different, victim shop. `Registry.process` will accept it (HMAC still matches, since it only checks the body) and dispatch the handler with `shop: <victim-domain>` [5](#0-4) .

### Impact Explanation
This breaks the tenant-isolation guarantee the gem is documented to provide via webhook HMAC verification (`docs/usage/webhooks.md` states `process` "will verify the request did indeed come from Shopify"). If a host application's webhook handler uses `WebhookMetadata#shop` to look up a stored session/access token, update per-shop records, or take shop-scoped action (a common and encouraged pattern, e.g. `shop/redact`, `customers/redact`, `customers/data_request` mandatory topics), an attacker with only an unprivileged app install on their own shop can inject attacker-controlled body content that the host app will process under a victim shop's identity — a cross-tenant data-integrity issue. This qualifies as a "cross-tenant access" style impact from the given severity classes, since the app's downstream trust of `shop` is compromised without any privileged credential in the attacker's possession.

### Likelihood Explanation
The prerequisite — being able to install the app on one's own shop and receive a genuinely-signed webhook — is available to any unprivileged internet user in typical app-install flows (public apps installable by any merchant). Forging arbitrary HTTP headers on an outbound POST to a public webhook endpoint requires no special access. The only non-trivial part is that the attacker needs the target app's webhook endpoint to react on `data.shop`/`data.topic` in a sensitive way, which is a normal and encouraged usage pattern documented by this gem.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) values in the signed payload, or otherwise cryptographically bind them before trusting them — e.g., verify the header-derived shop against a shop that is already known/onboarded for this specific topic/webhook_id combination server-side, or require applications to cross-check `request.shop` against an independently maintained registration record before acting on it. At minimum, update `lib/shopify_api/webhooks/request.rb` / `registry.rb` and the documentation to make clear that `shop`, `topic`, and `webhook_id` are **not** authenticated by the HMAC, so consuming applications do not implicitly trust them as tenant identity.

### Proof of Concept
1. Attacker registers a merchant account and installs the target Shopify app on `attacker-shop.myshopify.com`, enabling a webhook topic (e.g. `orders/create`) with `path` pointing to the app's public webhook endpoint.
2. Shopify (using the app's real secret) sends a legitimately-signed webhook to the app:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC of body>`
   - Body: attacker-controlled order JSON (attacker fully controls contents of their own order).
3. Attacker captures this raw body and HMAC, then sends their own HTTP POST directly to the app's webhook endpoint, keeping body+HMAC identical but replacing the header:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` — validation succeeds [2](#0-1) .
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` [5](#0-4) , causing the host application to process attacker-controlled data under the victim shop's identity.
