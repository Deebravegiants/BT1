### Title
Webhook `shop-domain` header is trusted for tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-validating only the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used downstream to identify the tenant are read from unauthenticated HTTP headers. This breaks the identity binding `HMAC-verified bytes == data acted upon`, analogous to the GithubHint report's pattern of validating one thing while acting on another that isn't equally protected.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read from separate HTTP headers that are never included in the signed string: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., the body's HMAC) before dispatching the handler with `request.shop` as the tenant identity: [4](#0-3) 

The dispatched `WebhookMetadata` struct carries `shop` as a plain, unauthenticated field that the host application's handler will use to select which merchant/tenant record the payload applies to: [5](#0-4) 

Because `api_secret_key` is a single shared secret for the whole app (not per-shop), any merchant who installs the app receives genuine webhooks whose body+HMAC pair is valid under that same secret. Since the HMAC never covers the `shopify-shop-domain` header, an attacker who controls or intercepts delivery of their own shop's webhook (e.g., a malicious merchant operating a proxy/webhook relay in front of their own store, or replaying a webhook they legitimately received) can resend the exact same `raw_body` (with its still-valid HMAC) to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass because only the body is checked, and `Registry.process` will dispatch the handler with `WebhookMetadata.shop` set to the victim's domain.

This is exactly the class of bug described in the report: `hint`/`hintURL` associate content with an identity based on unguarded state, mirrored here by `shop` being an identity field that is "acted on but not covered by the HMAC."

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to select which tenant's stored session/data a webhook payload should be applied to (the intended and documented use, per `docs/usage/webhooks.md` handler examples), this allows a malicious/compromised merchant to inject a validly-signed payload that the app attributes to a different shop, causing cross-tenant data corruption/injection under a spoofed tenant identity — matching the "cross-tenant access" Critical impact class, since data intended to be scoped to Shop A's session/access token is instead applied against Shop B's session context.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuine, validly-signed webhook body (obtainable by installing the app on their own shop, which is available to any unprivileged internet user who can install a public/embedded app) and control over the request sent to the app's webhook endpoint (e.g., by not relying on Shopify's direct delivery, or by replaying a captured delivery through a proxy they control). It does not require access to `api_secret_key`, an access token, or any credential beyond what an ordinary merchant/installer already has. This depends on the host application actually keying tenant lookup off `WebhookMetadata.shop` without independent corroboration — a pattern the gem's own documentation encourages.

### Recommendation
- Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values in the HMAC-signed string (`to_signable_string`) so any header value used for identity/routing decisions is cryptographically bound to the signature, not just the body.
- Alternatively, document explicitly and enforce in the gem that `WebhookMetadata.shop` must never be trusted as an authenticated tenant identifier unless corroborated by a separate mechanism (e.g., a lookup of an expected shop for the topic/registration).

### Proof of Concept
1. App installed by attacker on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook to the app with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
2. Attacker intercepts/proxies this delivery (e.g., configures their own relay/webhook URL, or replays a captured request) and resubmits it to the app's public webhook endpoint, changing only the header `x-shopify-shop-domain` to `victim-shop.myshopify.com`, leaving `raw_body` and `x-shopify-hmac-sha256` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` — this still matches, since it wasn't tampered with. [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's raw_body content>, ...)`, causing the host app to process attacker-controlled payload data under the victim shop's identity. [7](#0-6)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
