### Title
Unrefunded native-token dust from `swapETHForExactTokens` is permanently stuck in `EvmHost` on `dispatch`/`fundRequest` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept `msg.value` and swap it for the exact fee-token amount needed via `swapETHForExactTokens`, but any leftover native token from that swap is never forwarded back to the original caller.

### Finding Description
When a user or an application contract pays Hyperbridge dispatch/relayer fees in native token, `EvmHost` performs an exact-output swap: [1](#0-0) 

`swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` swaps only the exact amount of ETH needed to obtain `post.fee` fee tokens. The underlying router refunds unspent ETH dust — but the refund destination is `msg.sender` of the router call, which is `EvmHost` itself (`address(this)` is only the token recipient, not the ETH-refund recipient in `UniswapV2Router02`/its wrapper implementations). This means any `msg.value` supplied above the amount actually consumed by the swap lands in `EvmHost`'s own balance instead of being returned to the caller who paid it.

The identical pattern repeats in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

None of these three functions compute or forward back a remainder, unlike the analogous flows in `IntentGatewayV2.placeOrder` and `ExtrinsicIntents`/`IntrinsicIntents` in the same repo, which explicitly track `msgValue` after the swap and call `_sendValue(msg.sender, msgValue)` to refund the excess: [4](#0-3) [5](#0-4) 

A search of `evm/src/core/EvmHost.sol` for `receive()`, `fallback()`, or any withdraw/sweep function found none, so ETH that accumulates in the host from this dust has no built-in path back to the payer.

This is a direct analog of the reported `LMPVaultRouterBase.mint` bug class: a `payable` entry point that computes the actual required amount only after receiving `msg.value`, and fails to return the unused portion to the sender.

### Impact Explanation
Any user or integrating contract (e.g., `HyperFungibleToken.send`, `WrappedHyperFungibleToken.send`, the LayerZero endpoint adapter, or any `HyperApp` dispatching with native value) that overestimates the native-token amount needed for a POST/GET dispatch or a `fundRequest` call permanently loses the excess ETH/native token — it becomes stuck in `EvmHost` with no recovery mechanism for the depositor. Because fee estimation off-chain (via `quote()`) is inherently imprecise (documented as vulnerable to sandwich attacks and not to be relied on for exact amounts) and slippage/price movement between quoting and execution is expected, overpayment is a normal occurrence, not an edge case — meaning funds loss is expected on essentially every native-fee dispatch that doesn't precisely match the swap's actual cost.

### Likelihood Explanation
High. Any caller using the documented "Native Token Payment" pattern (`dispatch{value: msg.value}(post)`) is exposed every time it sends slightly more ETH than the swap actually consumes, which the docs themselves acknowledge is likely given AMM price movement between off-chain quoting and on-chain execution.

### Recommendation
Track the ETH actually spent by the swap and refund the difference to `msg.sender`/`_msgSender()` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder` and `ExtrinsicIntents`/`IntrinsicIntents` (compute `msgValue -= amounts[0]` after the swap, then call `_sendValue(msg.sender, msgValue)` if `msgValue > 0`).

### Proof of Concept
1. A user calls `EvmHost.dispatch(DispatchPost)` (or an app contract like `HyperFungibleToken.send`) sending `msg.value = 5 ETH` to cover a `post.fee` that only requires `0.1 ETH` worth of swap input.
2. Inside `dispatch`, `swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)` executes; the router only consumes ~0.1 ETH and refunds the remaining ~4.9 ETH — to `EvmHost` (the caller of the router), not to the original user.
3. `dispatch` returns normally with the request committed; the 4.9 ETH now sits in `EvmHost`'s balance.
4. There is no function in `EvmHost.sol` that lets the user reclaim this ETH; it is permanently lost to them (analogous to the reported `LMPVaultRouterBase.mint` issue where `msg.value - amountIn` is never returned).
