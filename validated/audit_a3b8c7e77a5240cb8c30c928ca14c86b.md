### Title
Webhook shop identity spoofing via unsigned `x-shopify-shop-domain` header - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `Utils::HmacValidator.validate` covers exclusively the JSON body and never the `x-shopify-shop-domain` / `shopify-shop-domain` header. `Registry.process` still uses that unverified header value (`request.shop`) to populate `WebhookMetadata#shop`, which is the value host apps use to select which merchant's session/access token to act on, so a validly signed webhook body from one shop can be replayed with a different shop header to make the app operate on another tenant's data.

### Finding Description
The invariant that should hold is: `signed_value(shop) == trusted_value(shop)` — the shop identity used by the handler should be the one the HMAC signature actually authenticates. Tracing the code:

- `Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `Webhooks::Request#shop` reads the raw, attacker-suppliable header with no cross-check against the signature: [2](#0-1) 
- `HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and the app-level `Context.api_secret_key`, which is shared by every merchant installation of the app, not per-shop: [3](#0-2) 
- `Registry.process` validates the HMAC, then builds `WebhookMetadata` directly from `request.shop` (the unverified header) and hands it to the host app's handler as trusted tenant identity: [4](#0-3) 
- `WebhookMetadata#shop` is a plain `const` with no further validation: [5](#0-4) 

Because the app's `api_secret_key` is one value for the whole app (shared across all merchant installs), an attacker who owns their own development shop can install the app, receive a validly-signed webhook for their own shop, capture the raw body + `X-Shopify-Hmac-Sha256` header, and resend that exact body/HMAC pair to the app's webhook endpoint with `x-shopify-shop-domain` rewritten to a victim merchant's `*.myshopify.com` domain. `HmacValidator.validate` recomputes the signature purely from the untouched body and the shared secret, so it passes. `Registry.process` then dispatches to the handler with `WebhookMetadata#shop` equal to the victim's domain, even though nothing about the request was ever signed by or associated with that shop. No component in this gem re-derives or cross-checks `shop` against anything authenticated — `ShopValidator`/OAuth session logic is not consulted in the webhook path at all.

### Impact Explanation
Any host app that uses `WebhookMetadata#shop` to look up the merchant's stored session/access token (the documented and expected pattern) can be made to perform token-scoped actions — API calls, redactions, data lookups — against an arbitrary victim shop that the attacker never installed on, using an attacker-crafted body. This is a cross-tenant identity confusion: one HTTP request's "verified" component (the HMAC-covered body) and its "used" component (the shop header) diverge, satisfying the SINGLE IDENTITY invariant being violated. Depending on host app logic this can escalate to unauthorized actions taken with the victim's Admin API access token (e.g., forced processing of a fabricated `customers/data_request` or `orders/*` payload attributed to the victim shop), which maps to the Critical cross-tenant-access / credential-abuse class.

### Likelihood Explanation
The attacker needs only: (1) their own free development shop with the target app installed (explicitly permitted under the rules), (2) one legitimately delivered, validly signed webhook to capture body+HMAC, and (3) the ability to POST directly to the app's public webhook endpoint with a modified header — no secret, token, or victim cooperation required. This is fully repeatable against any victim shop domain the attacker chooses, at will, since the shared secret and signature never change per shop.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the signable string, or otherwise have `Registry.process` validate `request.shop` against an authenticated source (e.g., cross-check against the app's known installed-shop list / session store) before constructing `WebhookMetadata`, rather than trusting the raw `x-shopify-shop-domain` header as-is.

### Proof of Concept
```ruby
# test/webhooks/shop_spoof_test.rb
require "test_helper"

class ShopSpoofTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @body = '{"id":123}'
    @hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", "secret", @body))
  end

  def test_hmac_ignores_shop_header
    legit = ShopifyAPI::Webhooks::Request.new(
      raw_body: @body,
      headers: {
        "x-shopify-topic" => "orders/create",
        "x-shopify-hmac-sha256" => @hmac,
        "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
        "x-shopify-api-version" => "2024-01",
        "x-shopify-webhook-id" => "1",
      },
    )
    spoofed = ShopifyAPI::Webhooks::Request.new(
      raw_body: @body,
      headers: {
        "x-shopify-topic" => "orders/create",
        "x-shopify-hmac-sha256" => @hmac, # same signature, unchanged body
        "x-shopify-shop-domain" => "victim-shop.myshopify.com", # different tenant
        "x-shopify-api-version" => "2024-01",
        "x-shopify-webhook-id" => "1",
      },
    )

    assert ShopifyAPI::Utils::HmacValidator.validate(legit)
    assert ShopifyAPI::Utils::HmacValidator.validate(spoofed) # still passes!
    assert_equal "victim-shop.myshopify.com", spoofed.shop
    refute_equal legit.shop, spoofed.shop # divergent identity under identical valid signature
  end
end
```
This demonstrates that `to_signable_string`/`HmacValidator.validate` accept the identical signature for two requests whose `shop` values differ, proving the shop identity used downstream (`WebhookMetadata#shop`) is not the value the signature actually authenticates.
