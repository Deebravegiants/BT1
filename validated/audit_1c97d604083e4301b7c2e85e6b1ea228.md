### Title
`BidManager.sortByRawAmountFallback` ranks intent bids by summing raw amounts of different output tokens, misordering fills across mixed-asset orders - (File: `sdk/packages/sdk/src/protocols/intents/BidManager.ts`)

### Summary
`BidManager.sortMixedOutputs` falls back to `sortByRawAmountFallback` whenever on-chain DEX pricing for one or more of an order's mixed output tokens is unavailable. That fallback sums the raw token amounts of every output leg — regardless of decimals or per-unit value — into a single `totalOffered` `Decimal` and ranks competing solver bids by that sum, exactly the same bug class as the referenced Olympus `getCategoryBalance` report (summing balances/amounts of assets with different decimals/values as if they were fungible).

### Finding Description
`sortBids` (`BidManager.ts:239-274`) dispatches to one of three strategies depending on the order's output composition. For "mixed outputs" (at least one non-stable token), `sortMixedOutputs` (`BidManager.ts:393-429`) tries to price every token via on-chain DEX quotes (`computeOutputsUsdValue`); if that pricing fails for any reason (illiquid pool, RPC failure, no quoter route, etc.), it falls back to `sortByRawAmountFallback` (`BidManager.ts:437-485`).

`sortByRawAmountFallback` computes, per bid:
```
totalOffered = totalOffered.plus(new Decimal(matching.amount.toString()))
```
for every output token the order requires, then sorts bids by `totalOffered` descending — with no decimals normalization and no per-token pricing at all. A bid offering, e.g., a large raw amount of an 18-decimal, low-value token plus a small amount of a 6-decimal, high-value token could rank above a bid offering genuinely more USD value, purely because raw integer units of different tokens were added together as if fungible. This is structurally identical to the reported `OlympusTreasury.getCategoryBalance` flaw: summing quantities of heterogeneous assets without accounting for decimals/value produces a meaningless total that is nonetheless used to drive a selection decision.

### Impact Explanation
The ranking produced by `sortBids`/`sortByRawAmountFallback` determines which solver's `UserOperation` is treated as "best" and consequently is the one selected for on-chain execution (`fillOrder`) for a same-chain or cross-chain intent order with mixed, non-stable output tokens. Because the fallback path is reachable any time DEX pricing cannot be resolved for at least one output asset (a condition an attacker-solver can help engineer by bidding in an illiquid/unrouted token), a solver can craft a bid whose raw-unit sum is inflated (via a token with many decimals) while its true USD value is inferior, and have it ranked ahead of an honestly better bid. The end-user (or the automated caller selecting `sortBids[0]`) then executes an inferior fill, i.e., receives strictly less value than they should — an economic loss for the order's beneficiary, reachable from a single dispatched/placed order and a submitted bid, with no privileged role required.

### Likelihood Explanation
Likelihood is moderate: the fallback only triggers when `computeOutputsUsdValue` returns `null` (pricing failure on at least one leg), which is a normal, attacker-influenceable occurrence for orders with mixed non-stable outputs — a solver can bid a token that has no configured USDC/WETH Uniswap route today (or none the SDK's price-resolution path can quote), forcing every competing solver's fallback comparison into raw-amount space where the attacker's inflated-decimals bid then wins comparison.

### Recommendation
Never compare raw amounts of different tokens directly. When per-token USD pricing is unavailable for one or more legs of a mixed-output order, either: (1) reject bids that cannot be fully priced rather than falling back to a raw-amount sum, or (2) normalize every token amount by its own decimals before any cross-token aggregation, and refuse to rank/aggregate across tokens whose USD price cannot be independently established (mirroring the "refuse to estimate" pattern already used elsewhere in this codebase, e.g. `availableStablecoins`/`getOrderUsdValue`, which return `null` rather than silently summing unlike quantities).

### Proof of Concept
1. Construct a cross-chain or same-chain order whose `output.assets` includes at least one non-stable token for which the configured Uniswap quoter path (`computeOutputsUsdValue`/`quoteTokenToUsdc`) cannot resolve a price (e.g., a token with no configured pool on the destination chain) — `sortMixedOutputs` then returns `null` from `computeOutputsUsdValue` and falls back to `sortByRawAmountFallback` (`BidManager.ts:396-398`).
2. Solver A bids honestly: required stable-equivalent value in a high-decimals-per-value token, e.g. `1_000_000e18` units of a token worth $0.0001 (true value ≈ $100).
3. Solver B bids a genuinely more valuable basket, e.g. `50e6` USDC-equivalent units of a 6-decimal token worth $2 (true value ≈ $100) plus a modest additional output, but with fewer raw integer units overall.
4. `sortByRawAmountFallback` sums `matching.amount` directly (`BidManager.ts:455`) without dividing by decimals, so Solver A's bid (`1_000_000e18`) ranks far above Solver B's (`~50e6`) despite comparable or superior true value from B, and `sortBids` returns Solver A's bid first — causing the caller to select and execute the objectively worse-value bid.
