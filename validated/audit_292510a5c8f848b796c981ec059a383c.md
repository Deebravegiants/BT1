### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop-identity spoofing on otherwise-valid webhook deliveries - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, but exposes `shop` (and `topic`, `api_version`, `webhook_id`) from separate, unsigned HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` straight to the app's handler as the tenant identifier, without ever binding that header value to what was actually signed.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, a value that is never included in `to_signable_string` and therefore never covered by the HMAC: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e., against the body — the shop header plays no role in the signature at all: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding broken here is: **shop authenticated (bytes actually verified by the HMAC = request body) ≠ shop acted upon (the `shop-domain` header value trusted by `Registry.process` and forwarded to the handler)**. Because the app's `client_secret`/`api_secret_key` is shared across every shop that has installed the app, any merchant who has installed the app (an unprivileged, non-malicious-by-default internet actor from the gem's perspective) can capture one legitimate webhook delivery for their own shop — a valid `(raw_body, hmac)` pair — and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. The HMAC still validates because it never covered the header, so `Registry.process` accepts the request and calls the handler with `WebhookMetadata.new(shop: <victim shop>, body: <attacker's original payload>, ...)`. Any host application that uses `request.shop` (as the library's own `WebhookMetadata` does) to select the tenant/session/data record to update will write or process data under the wrong tenant.

### Impact Explanation
This lets an authenticated app installer forge the tenant binding of an otherwise cryptographically valid webhook, causing the host application to attribute webhook data to a different merchant/shop than the one that actually produced it — a cross-tenant data injection into the app's per-shop processing pipeline. This matches the Critical bucket ("cross-tenant access") because the shop identity, which the library presents as verified once `Utils::HmacValidator.validate` passes, is not actually bound to the signature at all.

### Likelihood Explanation
Medium-High: exploitation requires only an app installation (any merchant of a multi-tenant app can obtain a genuine `(body, hmac)` pair for their own shop) and the ability to POST to the app's public webhook endpoint with a modified header — no access to `api_secret_key`, no privileged account, and no TLS interception is needed. The gem's documented API (`Registry.process` / `WebhookMetadata`) actively encourages developers to treat `request.shop` as trustworthy once HMAC validation succeeds, since it is the library, not the host app, that performs the "security check" and then forwards the shop value.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) header in the signable content or, at minimum, require the caller to supply/verify an expected shop for reconciliation before dispatching to a handler. Concretely, `Request#to_signable_string` should not be the sole gate on identity — `Registry.process` should cross-check `request.shop` against an out-of-band source of truth (e.g., the registered/expected shop or the shop associated with the delivering webhook subscription id) rather than trusting the unsigned header verbatim.

### Proof of Concept
1. App has two installs: Shop A (attacker-controlled) and Shop B (victim), both sharing the app's single `api_secret_key`.
2. Shopify sends a legitimate webhook for Shop A: `POST /webhooks` with headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and some `raw_body`.
3. Attacker captures this request (it was sent to their own endpoint, so they have full access) and replays it with the header changed to `x-shopify-shop-domain: shop-b.myshopify.com`, keeping the same `raw_body` and `x-shopify-hmac-sha256`.
4. `HmacValidator.validate(request)` in `Registry.process` recomputes the HMAC over `request.to_signable_string` (= `raw_body`), which is unchanged, so validation succeeds: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: <shop A's original payload>, ...)`, causing shop A's data to be processed/stored as if it belonged to shop B.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
