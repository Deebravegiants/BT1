Audit Report

## Title
Metering `Settle` Fails to Deduct Balance When Capability Spend Exceeds Earmarked Reservation - (File: core/services/workflows/metering/metering.go)

## Summary
In `Report.Settle`, when a capability's self-reported spend (`spentCredits`) exceeds the amount earmarked in the earlier `Deduct` call (`step.Deduction`), the code attempts to apply the negative difference via `balanceStore.Add`, which explicitly rejects negative amounts and returns `ErrInvalidAmount`. This error is only logged, so the local credit balance is never debited for the overage, leaving more usable balance available for subsequent capability calls within the same workflow execution than should exist.

## Finding Description
`Report.Settle` computes `spentCredits` from capability-reported `metadata.Metering` node details, then attempts to reconcile the local balance against the earmarked deduction:
```go
if err := r.balance.Add(step.Deduction.Sub(spentCredits)); err != nil {
    r.lggr.Info("invariant: spend exceeded reserve")
}
r.balance.AddSpent(spentCredits)
```
`balanceStore.Add` rejects any negative amount:
```go
if amount.LessThan(decimal.Zero) {
    return ErrInvalidAmount
}
```
When `spentCredits > step.Deduction` (i.e., a capability reports spend exceeding the reserved earmark), `step.Deduction.Sub(spentCredits)` is negative, `Add` fails, and the balance is left unchanged at `X - Deduction` instead of the correct `X - spentCredits`. `AddSpent` still records the full `spentCredits` for reporting, but the actual deductible `balance` field used by future `Minus`/`MinusAs` calls in `ByResource`/`ByDerivedAvailability` is never reduced by the overage. This is a genuine logic bug present in the code exactly as described, confirmed by direct inspection of both `metering.go` and `balance_store.go`.

## Impact Explanation
This under-charges the tracked in-execution credit balance whenever reported spend for a step exceeds its earmark, leaving an inflated balance available for subsequent `Deduct` calls in the same execution. This could let a workflow (in combination with a capability that reports inflated/uncapped spend) perform more capability calls than its true credit allotment permits, undermining the credit/billing enforcement intended by `Reserve`/`Deduct`/`Settle`. This maps to the "unauthorized fund movement / billing bypass" impact category, though the exploit requires a capability whose self-reported spend metadata is not otherwise bounded — the report notes this is plausible for capabilities on separate/less-trusted DONs.

## Likelihood Explanation
Reachable on the standard `CallCapability` → `Deduct` → capability execution → `Settle` path whenever a capability reports metering spend above its granted `SpendLimit`. Since spend metadata is self-reported by the capability implementation (not independently verified against actual resource consumption by the engine), a capability that reports spend above the earmark — whether due to a bug or by design — triggers this silently-ineffective branch every time.

## Recommendation
In `Report.Settle`, when `spentCredits.GreaterThan(step.Deduction)`, explicitly call `r.balance.Minus(spentCredits.Sub(step.Deduction))` to actually debit the overage, rather than relying on `Add` with a negative value whose error is merely logged. Consider also treating a materially large overage as an error condition or metering-mode trigger to prevent repeated exploitation within a single execution.

## Proof of Concept
1. Call `Report.Reserve` to set `balance = X`.
2. Call `Report.Deduct(ref, opt)` earmarking `D` credits; `balance` becomes `X - D`.
3. Call `Report.Settle(ref, metadata)` with `metadata.Metering` node details whose aggregated/converted credit value `S > D`.
4. Observe `r.balance.Add(D - S)` returns `ErrInvalidAmount` (logged, not surfaced as an error from `Settle`), and `r.balance.Get()` still returns `X - D` instead of the correct `X - S`.
5. A subsequent `Deduct` call in the same execution succeeds against the inflated `X - D` balance, when it should have been checked against `X - S`, demonstrating a workflow can retain more available balance than its true remaining credit allotment permits.

func ByResource(
	spendType, capabilityID string,
	amount decimal.Decimal,

		if r.meteringMode {

	}
