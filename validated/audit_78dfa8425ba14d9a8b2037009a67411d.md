### Title
Excess/unused native token sent to `EvmHost.dispatch()`, `dispatch(DispatchGet)` and `fundRequest()` is permanently locked instead of refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native token payment and swap it for the exact `feeToken` amount required via `swapETHForExactTokens`. Unlike the sibling `IntentGatewayV2` contract, which explicitly tracks the leftover `msgValue` after the swap and refunds it to the caller, `EvmHost` never tracks or refunds the unspent native token. Any ETH sent in excess of what the swap actually consumes is refunded by the UniswapV2 router to `EvmHost` itself (since `EvmHost` is the caller of the router), and then has no path back to the original `_msgSender()`.

### Finding Description
In `EvmHost.dispatch(DispatchPost memory post)`: [1](#0-0) 
the function swaps the *entire* `msg.value` for an exact output amount (`post.fee`) via `swapETHForExactTokens{value: msg.value}(...)`. Standard UniswapV2Router02 semantics for `swapETHForExactTokens` refund any unused ETH to `msg.sender` of that call — which is `EvmHost`, not the end user who called `dispatch()`. The function never reads a return value from the swap, never computes `msg.value - amountSpent`, and never forwards any leftover ETH back to `_msgSender()`.

The exact same pattern repeats in `dispatch(DispatchGet memory get)`: [2](#0-1) 
and in `fundRequest()`: [3](#0-2) 

This contrasts directly with `IntentGatewayV2.placeOrder`, which performs the identical fee-swap-with-native-token pattern but correctly tracks and refunds the surplus: [4](#0-3) 
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
```
`EvmHost` lacks this bookkeeping entirely. Any caller who overpays `msg.value` relative to the actual amount needed to acquire `post.fee`/`get.fee`/`amount` in `feeToken` via the swap loses the difference — it becomes native balance stuck in `EvmHost` with no mechanism exposed to a normal caller to reclaim it. The only withdrawal path found is `IHostManager.withdraw(WithdrawParams)`, which is a governance/host-manager-only function for withdrawing protocol *bridge revenue*, not a per-user refund mechanism, and is not tied to tracking of overpaid swap remainders at all.

### Impact Explanation
Because Hyperbridge explicitly documents and encourages native-token fee payment for `dispatch()`/`fundRequest()` (per `docs/content/developers/evm/messaging/post-requests.mdx` and `get-requests.mdx`), any user or integrating `IApp` contract that estimates fees imprecisely, or intentionally overpays for safety margin (as the SDK docs and Foundry tests for `IntentGatewayV2` demonstrate is a normal/expected pattern), will have the unspent ETH trapped in `EvmHost` on every call to `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()`. This is a direct, permanent freezing-of-funds bug reachable by any unprivileged caller dispatching a cross-chain message or funding a pending request — exactly the "message dispatcher" surface named in scope.

### Likelihood Explanation
High likelihood: `dispatch()` is the primary, most frequently used entry point for all outbound ISMP messages paid in native token, and the documentation explicitly instructs users to "send with `msg.value`" without requiring exact fee computation on-chain (client-side estimation is inherently imprecise due to swap price movement between quote and execution, exactly as demonstrated by the existing `IntentGatewayV2` test `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` which sends 5 ETH for a fee that costs a fraction of that, and asserts a refund is required). `EvmHost` has no such refund, so the loss occurs on essentially every overestimated native-fee dispatch call.

### Recommendation
Track the actual amount spent by `swapETHForExactTokens` (its return value) in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund `msg.value - amountSpent` back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`.

### Proof of Concept
1. User calls `IHost(evmHost).dispatch{value: 5 ether}(DispatchPost({..., fee: 1e18 feeToken units, ...}))` (analogous to `evm/tests/foundry/IntentGatewayV2Test.sol` line 3745's `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`, but targeted at `EvmHost.dispatch` directly).
2. Inside `dispatch`, `swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)` is called; suppose only 0.1 ETH is needed to acquire `post.fee` in `feeToken`.
3. UniswapV2Router02 refunds the unused 4.9 ETH to `msg.sender` of the swap call, i.e. `EvmHost`.
4. `EvmHost.dispatch` returns normally; the 4.9 ETH now sits in `EvmHost`'s balance.
5. There is no code path in `EvmHost` for the original user to reclaim that 4.9 ETH — `withdraw()` is restricted to the `hostManager` and is designed for bridge-revenue accounting, not user refunds — so the funds are permanently locked from the user's perspective.
