## Finding

### Title
Webhook shop/topic identity spoofing via unsigned headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only the raw request body against the HMAC signature, but delivers `shop`, `topic`, `webhook_id`, and `api_version` — all taken from unauthenticated HTTP headers — to the handler without any of them being covered by that HMAC. An attacker who controls one legitimate installation of the host app (their own shop) can capture a genuinely Shopify-signed webhook delivery and replay its body against the same app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header, causing the handler to process attacker-supplied data under a victim tenant's identity.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for `ShopifyAPI::Webhooks::Request` that method returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers, none of which contribute to the signed string: [2](#0-1) 

`Registry.process` checks the HMAC and, if valid, hands the *header-derived* `shop`/`topic`/`webhook_id` straight to the registered handler as trusted `WebhookMetadata`: [3](#0-2) 

Because the gem's `Context.api_secret_key` is a single app-wide secret shared across every shop that installs the app (not a per-shop secret), any successful HMAC check only proves "this body/secret pair is genuine," not "this body was delivered for shop X." An attacker who installs the app on their own store receives real, correctly HMAC-signed webhook deliveries. They can then replay the same raw body (and therefore the same valid HMAC) to the app's public webhook endpoint while changing the `x-shopify-shop-domain` header to a victim shop's domain (and optionally the topic). `HmacValidator.validate` still succeeds because it only checks the body/secret, and `Registry.process` passes the attacker-chosen `shop` value straight through to the handler as if Shopify itself asserted it for that domain.

This is the exact bug class from the report: a field that is acted upon (`shop`, used by host-app handlers to select the tenant record to read/write) is not covered by the cryptographic binding (`hmac`, which only covers `raw_body`), breaking the equality `hmac-verified data == data acted on`.

### Impact Explanation
Handlers built on top of `Webhooks::Registry.process` are expected to trust `WebhookMetadata.shop` to determine which tenant's data the webhook body applies to (this is exactly the pattern shown in the gem's own webhook docs, where handlers key persistence/side effects off `data.shop`). Because `shop` is unauthenticated relative to the HMAC, an attacker with an unprivileged, self-service app installation can forge cross-tenant webhook events for any other shop that has this app installed, leading to cross-tenant data confusion (e.g., a handler updating/deleting or acting on records keyed by shop domain, or writing attacker-supplied body content under another store's identity). This matches the "cross-tenant access" criterion for Critical impact.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker needs at least one legitimate, self-provisioned installation of the target app (i.e., attacker's own store must have the app installed and topics registered) to obtain a genuinely-signed body/HMAC pair, and the specific impact depends on how the host app's handler uses `data.shop`/`data.topic`. No access token, `api_secret_key`, or privileged account is required — only the attacker's own unprivileged merchant account and network access to the app's public webhook endpoint, which satisfies the "unprivileged internet user" requirement.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (e.g., include them, or a canonical representation of the full header set, in `to_signable_string`), or otherwise cryptographically bind the header set to the signed body so that a replayed-but-header-modified request fails verification. At minimum, document/require that host applications independently authenticate `shop` against their own tenant records rather than trusting the webhook's `shop-domain` header as HMAC-verified.

### Proof of Concept
1. Attacker installs the host app (built on this gem) on their own shop `attacker.myshopify.com` and registers a webhook topic (e.g. `orders/create`) via `ShopifyAPI::Webhooks::Registry`.
2. Shopify delivers a legitimately-signed webhook to the app's endpoint:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body over Context.api_secret_key>
   x-shopify-shop-domain: attacker.myshopify.com
   body: {"id": 123, ...attacker-controlled order payload...}
   ```
3. Attacker replays the identical raw body and HMAC header to the same endpoint, only changing:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks `raw_body` against the shared `api_secret_key`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)`, and the host app's tenant-scoped logic acts on `victim.myshopify.com` using attacker-supplied data.
