### Title
Unbounded per-block growth of `pallet-mmr`'s `IntermediateLeaves` buffer forces an unweighted, uncapped loop in the mandatory `on_finalize` hook - (File: modules/pallets/mmr/src/lib.rs)

### Summary
Every ISMP request/response dispatched in a block (permissionless — any account can trigger `dispatch_request`/`dispatch_response`, and pallets like `intents-coprocessor` bid/order flows dispatch on behalf of users too) pushes one entry into `pallet-mmr`'s `IntermediateLeaves` `CountedStorageMap` via `OffchainDBProvider::push`. There is no cap on how many entries can accumulate in a single block. `pallet-ismp`'s `on_finalize` hook unconditionally calls `T::OffchainDB::finalize()`, which iterates the *entire* buffer (`0u64..buffer_len`) to push every leaf into the runtime MMR and then clear the map — mirroring the OpenQ bug class where an ever-growing array must be entirely processed/encoded in one call, eventually becoming unable to complete.

### Finding Description
`push()` appends unconditionally with no per-block limit: [1](#0-0) 

`finalize()` is the unconditionally-invoked drain of that buffer, looping over the full `buffer_len` regardless of size, then calling `IntermediateLeaves::<T, I>::clear(buffer_len as u32, None)`: [2](#0-1) 

This `finalize()` is invoked from `pallet-ismp`'s `on_finalize` hook, which is a mandatory, non-optional hook executed every block regardless of the extrinsics' individually-metered weights: [3](#0-2) 

Because `on_finalize` runs after all extrinsics in the block have already been weighed and included, the cost of draining `IntermediateLeaves` (one storage read + one MMR-tree push + one offchain-index write per buffered leaf, `O(n)` in the number of leaves pushed during the block) is not itself gated by the block's extrinsic weight budget the way a normal dispatchable call would be. Any transaction that ends up dispatching an ISMP request (a `PostRequest`/`GetRequest` from IntentGateway, HyperFungibleToken, BandwidthManager, or any downstream ISMP module) contributes one leaf to this buffer per dispatch, and nothing in the dispatch path caps how many such dispatches can land in a single block via a full block's worth of independent extrinsics.

### Impact Explanation
If enough independent unprivileged dispatches (from many accounts, or one attacker submitting many small dispatch-triggering transactions) land in a single block, `IntermediateLeaves` can grow to a size whose `finalize()` drain exceeds the actual computational/proof-size budget available for block execution. Unlike a normal extrinsic that can simply fail/revert when it runs out of weight, `on_finalize` is mandatory and unskippable — if it cannot complete, block production for that block is disrupted, which is a "route unable to deliver messages" condition at the block-production level: no request commitments get finalized into the MMR, no relayer can produce valid proofs for any request from that block, and the finalize failure path currently only logs an error and returns without state changes, silently corrupting the correspondence between `NumberOfLeaves`/`RootHash` and the dispatched requests that already updated other pallet state (e.g., fee escrow, nonce, receipt) earlier in the block.

### Likelihood Explanation
Reaching this requires packing a single block with many ISMP-dispatching transactions, which any unprivileged user can attempt (each request dispatch is cheap relative to the incremental MMR-append cost imposed later). It is bounded in practice by the parachain's block weight/proof-size limits on the individual extrinsics that trigger dispatch, so the severity depends on how much cheaper a "dispatch" extrinsic is metered relative to the `on_finalize` cost it defers — I could not find a per-block cap on `IntermediateLeaves` count or a weight-limiting mechanism referenced from the dispatch path in the time available, so this remains a plausible-but-unconfirmed DoS surface rather than a proven one.

### Recommendation
- Enforce an explicit maximum number of leaves that may be buffered into `IntermediateLeaves` per block (reject or defer dispatches once the cap is hit), so the `finalize()` drain cost is bounded and can be safely weighed.
- Alternatively, account for `IntermediateLeaves` growth in the weight charged to each dispatch-triggering extrinsic (proportional weight fee per pushed leaf) so the block-weight system naturally limits how many leaves can accumulate before hitting the block limit.
- Add explicit handling (rather than silent `log::error!` + early return) for the case where `finalize()` cannot complete, to avoid leaving `RequestCommitments`/other pallet state inconsistent with the MMR's `NumberOfLeaves`/`RootHash`.

### Proof of Concept
Not independently reproduced against a running node in this analysis; the code-level demonstration is the structural point that `push()` (line 221) has no cap check and `finalize()` (lines 229–270) always iterates `0u64..buffer_len` and is called unconditionally from the mandatory `on_finalize` hook (`modules/pallets/ismp/src/lib.rs:324-342`), so any block containing enough dispatch-triggering extrinsics grows `buffer_len` unboundedly before that mandatory drain executes. A full PoC would require constructing a chain of extrinsics (e.g., repeated `dispatch_to_evm`/IntentGateway order placements) within one block and measuring whether `on_finalize`'s actual execution time/weight exceeds the block's proof-size or execution budget — this was not verified end-to-end due to the scope of static analysis available here.

	fn finalize() -> Result<H256, Error> {
		let buffer_len = IntermediateLeaves::<T, I>::count() as u64;
		// no new leaves? early return
		if buffer_len == 0 {
			return Ok(RootHash::<T, I>::get().into());
		}

		let leaves = NumberOfLeaves::<T, I>::get();
		let mut mmr: ModuleMmr<mmr::storage::RuntimeStorage, T, I> = mmr::Mmr::new(leaves);

		// append new leaves to MMR
		let range = 0u64..buffer_len;
		for index in range {
			let leaf = IntermediateLeaves::<T, I>::get(index).ok_or(Error::Push)?;
			// Mmr push should never fail
			match mmr.push(leaf) {
				None => {
					log::error!(target: "pallet-mmr", "MMR push failed ");
					// MMR push never fails, but better safe than sorry.
					Err(Error::Push)?
				},
				Some(position) => {
					log::trace!(target: "pallet-mmr", "MMR push {position}");
				},
			}
		}

		// Update the size, `mmr.finalize()` should also never fail.
		let (leaves, root) = match mmr.finalize() {
			Ok((leaves, root)) => (leaves, root),
			Err(e) => {
				log::error!(target: "pallet-mmr", "MMR finalize failed: {:?}", e);
				Err(Error::Commit)?
			},
		};

		let _ = IntermediateLeaves::<T, I>::clear(buffer_len as u32, None);
		NumberOfLeaves::<T, I>::put(leaves);
		RootHash::<T, I>::put(root);

		Ok(root.into())
	}
