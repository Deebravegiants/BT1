### Title
Webhook `shop-domain` (and `topic`) header is trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw request body only, while the `shop` (tenant identifier) and `topic` fields are read directly from unauthenticated HTTP headers and passed downstream to webhook handlers as trusted data. This breaks the intended binding `HMAC-verified bytes == data attributed to the request`, letting an unprivileged internet user replay a validly-signed body under a different `shop-domain` header and have the library present attacker-chosen data as if it originated from a victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be *only* the raw body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, none of which are included in the signed material: [3](#0-2) 

`Registry.process` validates only the HMAC of the body and then forwards the unauthenticated `request.topic` and `request.shop` fields straight to the app's handler as trusted metadata: [4](#0-3) 

Because `api_secret_key` is a single shared HMAC secret used for **every shop** installed on the app (it's the app's client secret, not a per-shop secret), any body+HMAC pair that validates for one shop also validates for a spoofed `shop-domain` header pointing at a different shop — the signature says nothing about which tenant the body belongs to. This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold is `authenticated(body) == shop-attributed(body)`, but the code only enforces `authenticated(body)`, leaving `shop` (and `topic`) attacker-controlled.

An unprivileged attacker can trivially obtain a validly-signed body/HMAC pair by installing the target app on their own free/trial Shopify store (which anyone can create) and capturing one of the resulting legitimate webhook deliveries (or by triggering a webhook whose body is fully predictable/empty, e.g., certain lifecycle topics), then replaying that exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting `shop-domain` with a victim shop's domain. `Registry.process` will accept it, because HMAC validation only checks the body, and will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop.

### Impact Explanation
This crosses a tenant boundary: any host application that relies on `WebhookMetadata#shop` (as documented/intended usage of this gem) to determine which shop's data/session to act on can be made to process attacker-supplied webhook content attributed to an arbitrary victim shop domain, since the shop identity is never bound to the HMAC-verified bytes. This is a cross-tenant identity confusion rooted entirely in this gem's `Webhooks::Request`/`Registry` design, independent of how any particular host app implements its handlers.

### Likelihood Explanation
Likelihood is high: no privileged credentials, tokens, or secrets are required. The attacker only needs (a) the ability to create their own Shopify store and install the target app to legitimately receive one signed webhook, or the ability to send a raw HTTP POST with a known/empty body, and (b) knowledge of the public webhook endpoint URL, which is required by design for Shopify to deliver webhooks to it.

### Recommendation
Bind the shop identity to the signed payload rather than trusting the `shop-domain` header independently of the HMAC. At minimum, cross-check the `shop-domain` header against a shop that is independently known to be associated with a valid installation/access-token record before treating `request.shop` as trustworthy, or extend `to_signable_string` (or a separate verification step) to incorporate the shop/topic headers so the signature is tenant-scoped rather than body-only. Document clearly that `Webhooks::Request#shop`/`#topic` are unauthenticated header values and must not be used as sole tenant discriminators by consuming applications.

### Proof of Concept
1. Attacker creates a free Shopify development store `attacker.myshopify.com` and installs the target app, triggering a webhook (e.g., `app/uninstalled` with body `"{}"`), capturing the resulting `X-Shopify-Hmac-Sha256: <hmac>` header value computed over body `"{}"` with the app's shared `api_secret_key`.
2. Attacker sends a forged POST to the app's webhook endpoint with:
   - body: `"{}"`
   - `x-shopify-hmac-sha256`: `<hmac>` (captured, still valid because it only signs the body)
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (spoofed)
   - `x-shopify-topic`: any registered topic
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `request.to_signable_string` (`"{}"`, unchanged) against the secret — see [2](#0-1) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: {}, ...)`, i.e., the app now believes this attacker-controlled webhook event legitimately originated from the victim shop, even though the shop field was never covered by the HMAC — see [4](#0-3) .

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
