## Analog Found

### Title
Malicious ERC20 input token permanently blocks escrow withdrawal/refund and can revert an entire relayer batch - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2` lets any user create an order with an arbitrary set of ERC20 `TokenInfo[]` as `order.inputs` — there is no token whitelist. All escrow release paths (`RedeemEscrow`, `RefundEscrow`, same-chain cancel, cross-chain cancel-from-source) funnel through a single loop, `IntentsBase._withdraw()`, that transfers every token in the withdrawal request in one atomic pass. A single reverting/blacklisting ERC20 placed anywhere in `order.inputs` causes the whole withdrawal — and therefore the release of every *other*, legitimate, escrowed token in the same order — to revert permanently.

### Finding Description
`_withdraw` iterates over `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for every entry with no isolation between tokens: [1](#0-0) 

This function is the single choke point for:
- `onAccept` handling `RedeemEscrow` (pays the solver who filled a cross-chain order) and `RefundEscrow` (refunds the user on cancel): [2](#0-1) 
- `onGetResponse` refunding escrow after a source-chain cancellation is proven unfilled: [3](#0-2) 
- Same-chain cancellation, which collects *all remaining escrowed tokens* for the order and refunds them in one `_withdraw` call: [4](#0-3) 

Because `order.inputs` (and thus `body.tokens`) can be any combination of ERC20 addresses chosen by the order's creator — there is no allow-list check anywhere in `IntentsBase`/`IntentGatewayV2` — an attacker can place an order whose input list mixes one legitimate token (e.g. USDC) with a token they control that always reverts on `transfer`. This mirrors the original report's root cause: iterating over an unrestricted set of token contracts and requiring every transfer to succeed atomically.

The blast radius is worse than a single order:
- `HandlerV2.handlePostRequests` iterates a *batch* of requests and calls `host.dispatchIncoming(leaf.request, ...)` for each with no try/catch isolating one request's failure from another: [5](#0-4) 
If `dispatchIncoming` ultimately invokes `IntentGatewayV2.onAccept`, which reverts due to the malicious token in `_withdraw`, the revert propagates up through `dispatchIncoming` and reverts the entire `handlePostRequests` transaction — every other, unrelated `RedeemEscrow`/`RefundEscrow`/app request batched by the relayer in the same call also fails, and none of them get a receipt recorded, so a relayer cannot make forward progress on the batch without first identifying and excluding the poisoned message.

### Impact Explanation
- **Cross-chain solver griefing / fund loss**: `_fillCrossChain` in `ExtrinsicIntents.sol` pays the beneficiary in output tokens *before* dispatching the `RedeemEscrow` message that later triggers `_withdraw` on the source chain. If the order's `inputs` include a malicious/blacklisting token, `_withdraw` reverts forever, so the solver who already paid out the output side can never redeem the escrowed input tokens — a direct, irrecoverable loss for the solver.
- **Permanent freezing of legitimate escrow**: For same-chain cancellation (`_cancelSameChain`) and for cross-chain cancel-from-source (`onGetResponse` → `_withdraw`), all remaining escrowed tokens for an order are refunded together. If any one input token is malicious, the user can never cancel/reclaim *any* of their escrowed tokens (including fully legitimate ones), permanently locking funds.
- **Batch-wide relayer DoS**: Because `HandlerV2.handlePostRequests` processes a whole batch atomically and `batchCall` is likewise all-or-nothing (`evm/src/core/HandlerV2.sol` lines 129–135), one poisoned settlement message can block delivery of unrelated, legitimate messages submitted in the same transaction, degrading relayer throughput/liveness for the route.

This satisfies "permanent freezing of funds" and "route unable to deliver messages" criteria — rated High.

### Likelihood Explanation
Placing an order with attacker-chosen ERC20 addresses as `order.inputs` is a normal, permissionless user action (`placeOrder`), requiring no privileged role. Crafting an ERC20 contract that reverts on `transfer`/`transferFrom` selectively (e.g., always reverting, or blacklisting the withdrawal beneficiary/gateway) is trivial and standard in known "malicious token" exploits. The attack requires only that the attacker themselves creates the order (no cooperation needed from other users), making this straightforward and repeatable.

### Recommendation
- Do not process multiple token releases atomically in a single all-or-nothing loop. Use a pull-based/withdrawal-per-token pattern, or wrap each individual token transfer in `_withdraw` in a low-level call with try/catch, crediting failed transfers to an internal per-user, per-token balance that can be claimed independently once retried, instead of reverting the whole batch.
- Alternatively, enforce a token allow-list for `order.inputs`/`order.output.assets`, or require a minimum liquidity/verification bond on any newly used ERC20 before it can be escrowed, closing off the ability for an attacker to introduce a hostile token contract into a settlement path.
- In `HandlerV2.handlePostRequests`/`dispatchIncoming`, consider isolating per-request failures (e.g., recording a failed-delivery status instead of reverting the whole batch) so that one malicious application-level revert cannot block delivery of unrelated messages in the same relayer transaction.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer`/`transferFrom` always reverts except when the caller is the attacker's own EOA during the initial deposit.
2. Attacker calls `placeOrder` with `order.inputs = [ {token: USDC, amount: X}, {token: EvilToken, amount: Y} ]`, depositing both tokens into escrow (deposit-time `transferFrom` from attacker's own address succeeds because attacker controls when `EvilToken` allows transfers).
3. A solver fills the cross-chain order via `_fillCrossChain` (`ExtrinsicIntents.sol`), paying the beneficiary in output tokens and dispatching a `RedeemEscrow` message back to the source chain.
4. On the source chain, `onAccept` decodes the `RedeemEscrow` body and calls `_withdraw(body, false, true)`, which loops over `[USDC, EvilToken]`; the `EvilToken.transfer` call reverts, causing the entire `_withdraw` — and hence `onAccept` and the enclosing `handlePostRequests`/`batchCall` — to revert.
5. The solver never receives the escrowed USDC despite having already delivered the output tokens; if the relayer had batched other unrelated requests in the same `batchCall`, those are reverted too. Repeating this on every retry permanently freezes the USDC escrow for this order (see `IntentsBase._withdraw`, `evm/src/apps/intentsv2/IntentsBase.sol:451-485`, and `HandlerV2.handlePostRequests`, `evm/src/core/HandlerV2.sol:181-210`).
