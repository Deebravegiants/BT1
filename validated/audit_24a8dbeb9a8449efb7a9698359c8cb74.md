### Title
Rounding-favorable sells via `Pair.swap`'s `+1` K-slack can push `assetReserve` below the launch-time virtual floor, causing a permanent underflow-revert DoS of `canGraduate` that freezes all buy/sell/graduation on the token - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.canGraduate` (and `previewLtUntilGraduation`) compute `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(...)` on the unchecked assumption that the pair's live `assetReserve` can never fall below the launch-time virtual reserve baked into `k`. `Router._computeSell` combined with `Pair.swap`'s intentional `+1` K-invariant slack lets an unprivileged trader extract slightly more LT than the exact constant-product amount on ordinary sells, which can drive `assetReserve` below that floor. Any subsequent call into `canGraduate` then reverts with an arithmetic-underflow panic — and `canGraduate` is unconditionally invoked inside every `buy()` and `sell()` on the token, so once tripped, the token is permanently bricked with no admin or user rescue path.

### Finding Description
`Bonding.canGraduate` reads: [1](#0-0) 

`_launchTimeVirtualLtReserve` recovers the launch-time virtual LT reserve as `k() / TOTAL_SUPPLY()`, an immutable value fixed at `mint`: [2](#0-1) 

The subtraction `assetReserve - _launchTimeVirtualLtReserve(...)` assumes `assetReserve` is always ≥ that virtual baseline. This baseline is exactly the initial `assetReserve` set at `mint`: [3](#0-2) 

Sells are priced by `Router._computeSell`, which floors the post-swap invariant term instead of rounding toward the pool: [4](#0-3) 

Because `k / newReserveToken` is floored, `assetOut = reserveAsset - floor(k/newReserveToken)` is **greater than or equal to** the exact K-preserving amount whenever `newReserveToken` does not divide `k` evenly — the seller is paid a fractional-wei bonus taken out of `assetReserve`. `Pair.swap` tolerates this because of its documented `+1` slack: [5](#0-4) 

`(newTokenReserve+1)*(newAssetReserve+1) < k` only reverts if the invariant is violated by *more* than the 1-unit buffer, so a sequence of sells at token amounts that don't cleanly divide `k` can each leak sub-wei-to-1-wei of `assetReserve` beyond what a strict K-preserving trade would remove. There is no protocol fee (per the Router's own natspec: "No fees here") to counteract this drift, and nothing re-anchors `assetReserve` to the virtual floor. Repeated sell transactions (economically nearly free at 18-decimal scale, purely griefing-motivated) can accumulate this drift until `assetReserve` drops below `_launchTimeVirtualLtReserve`.

Once that happens, the subtraction in `canGraduate` underflows and panics. Every hot-path function that calls `canGraduate` is now permanently broken for that token:
- `Bonding.buy` → `_executeBuy` unconditionally calls `canGraduate` after every buy: [6](#0-5) 
- `Bonding.sell` calls `canGraduate` before allowing a sell to proceed: [7](#0-6) 
- `triggerGraduation` also calls `canGraduate` directly: [8](#0-7) 

With all three entry points reverting on the same underflow, the token becomes permanently un-tradable and un-graduatable: the curve-raised LT sitting in `Pair`, the unsold curve tokens, and the creator's economic position are frozen forever, with no owner/admin override anywhere in `Bonding.sol` to bypass or reset `canGraduate`.

This mirrors the referenced nimiq-primitives class: an unvalidated invariant about externally-influenced data (here, cumulative rounding-favorable sells rather than a malformed BLS key) reaches a shared, unguarded arithmetic operation (`unwrap()` there, unchecked subtraction here) inside a function that many other operations transitively depend on, and panics — permanently denying service to everyone relying on that shared function, rather than just the caller who triggered it.

### Impact Explanation
Any single unprivileged trader can, given enough sell transactions (each individually cheap — a floor-rounding trade, not requiring any privileged role, permit, or flash loan), drive a specific token's `assetReserve` below its immutable virtual floor. From that point on:
- No one can `buy` or `sell` the token via `Zap`/`Bonding` ever again (permanent DoS of the market).
- `triggerGraduation` also reverts, so the token can never graduate to the HyperSwap V2 LP.
- All LT previously raised on the curve, and all unsold/creator tokens, are permanently locked in `Pair`/`Bonding` with no rescue mechanism — a full freeze of trader, creator, and prospective LP funds for that launch.

This is High severity: concrete, permanent freezing of funds triggerable by any address with only trading-level access.

### Likelihood Explanation
The precondition — sells whose `newReserveToken` does not evenly divide `k` — is the overwhelmingly common case (an exact-divisor sell size is a razor-thin edge case), so essentially every ordinary sell has some (tiny) chance of nudging `assetReserve` favorably by a wei. An attacker motivated purely by griefing (no capital requirement beyond gas and the tokens/LT needed for round-trip sells) can deliberately size sells to maximize the rounding bonus and repeat until the cumulative drift exceeds the (typically very small, since `virtualLtReserve` itself can be a small integer relative to 18-decimal LT amounts) floor gap. Likelihood is Medium-to-High: no privileged access is needed, and the number of transactions required scales with the size of the virtual floor, which is bounded and computable by the attacker in advance via `previewLtUntilGraduation`/`getReserves`/`k()`.

### Recommendation
- Anchor `assetReserve` never to fall below `_launchTimeVirtualLtReserve` at the `Pair.swap` level (e.g., an explicit floor check on `newAssetReserve` in `Pair.swap`, not just the loose `+1` K-invariant check), or
- Remove the sell-side rounding-in-favor-of-trader behavior by rounding `assetOut` down (ceil the subtracted term) in `Router._computeSell` so sells never pay out more LT than the exact K-preserving amount, and
- Use `Math.max(assetReserve, virtualFloor) - virtualFloor` (saturating subtraction) in `canGraduate`/`previewLtUntilGraduation` as defense-in-depth so a rounding-drift edge case degrades to "not yet graduatable" instead of permanently reverting the whole token's trading.

### Proof of Concept
1. Token launches; `Pair` is minted with `tokenReserve = totalSupply`, `assetReserve = virtualLtReserve = V`, `k = totalSupply * V` (`packages/contracts/src/Pair.sol:55-63`, `packages/contracts/src/Bonding.sol:460-495`).
2. Attacker performs an ordinary `buy` (via `Zap`/`Bonding.buy`) for LT amount `a`, receiving `tokensOut` tokens; `assetReserve` becomes `V + a`.
3. Attacker performs a partial `sell` of some amount of tokens whose resulting `newReserveToken` does not exactly divide `k` (trivial to arrange by choosing a sell size other than the exact reverse of step 2). `Router._computeSell` (`packages/contracts/src/Router.sol:172-182`) floors `k/newReserveToken`, so `assetOut` is rounded up in the seller's favor by up to 1 wei of LT versus the exact K-preserving amount; `Pair.swap`'s `(newTokenReserve+1)*(newAssetReserve+1) < k` check (`packages/contracts/src/Pair.sol:65-79`) tolerates this.
4. Repeat steps 2–3 (or size sells directly to maximize rounding bonus without an intervening buy, as budget allows) across many transactions. Each iteration nudges `assetReserve` down slightly faster than pure buys/sells would under exact math.
5. Once cumulative drift exceeds `V` such that `assetReserve < _launchTimeVirtualLtReserve(...)`, the next call to `canGraduate` (`packages/contracts/src/Bonding.sol:680-695`) executes `assetReserve - _launchTimeVirtualLtReserve(...)`, underflows, and reverts with a Solidity arithmetic panic.
6. From this point, `Bonding.buy`, `Bonding.sell`, and `triggerGraduation` all revert for this token permanently (each calls `canGraduate` unconditionally), freezing all LT/tokens already committed to the curve with no recovery path in `Bonding.sol`.

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
    }
