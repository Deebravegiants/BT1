### Title
Stale per-timestamp index cache in `market.clar` lets bad-debt socialization be bypassed within the same block, causing over-redemption of ztokens - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` caches each vault's borrow/liquidity index in a map keyed only by `{timestamp, aid}` and returns the cached value on any subsequent call in the same block, regardless of whether the vault's real index changed in between. Because `socialize-debt` is invoked directly on the vault contract (via `vault-socialize-debt`) and is not itself the function that populates or invalidates this cache, a same-block transaction sequence of "accrue (cache index) → default/bad-debt socialization → withdraw/redeem" can cause the market to keep using the pre-default (higher) liquidity index while the vault's real backing (`assets`/`total-borrowed`) has already been written down. This mirrors exactly the Blend fee-vault M-11 bug class: an unprivileged actor exploits a timestamp-equality escape hatch that skips re-fetching the up-to-date exchange rate after a default event in the same block.

### Finding Description
The market maintains:
```clarity
(define-map index-cache- 
  { timestamp: uint, aid: uint }
  { index: uint, lindex: uint })

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache- cache-key)))
    (match cached?
      existing existing  ;; cache HIT: never re-derives from vault state
      (let ((fresh (vault-accrue aid)))
        (map-set index-cache- cache-key fresh)
        fresh))))
``` [1](#0-0) 

This is the exact analog of the Blend fee-vault's `if now == self.last_update_timestamp { return; }` escape: any operation within the same `stacks-block-time` for a given `aid` returns the cached `(index, lindex)` pair unconditionally, without re-verifying the vault's true current state.

Separately, bad-debt write-off is routed straight to the vault, bypassing this accrual/caching path entirely:
```clarity
(define-private (vault-socialize-debt (aid uint) (amount uint))
  (if (is-eq aid STX) (contract-call? .v0-vault-stx socialize-debt amount)
  ...))
``` [2](#0-1) 

Because `socialize-debt` is a vault-level state mutation that is not funneled through `accrue-and-cache`, it does not (and structurally cannot, since the cache key is `{timestamp, aid}` and is only ever written by `accrue-and-cache`) invalidate an already-populated cache entry for the current block timestamp.

**Broken identity (equation):**

`vault-real-index(t) = f(assets(t), total-borrowed(t))` should always equal `market-cached-index(t)` used for zToken conversion.

Attack sequence bundled in one block (same `stacks-block-time`):
1. tx1 — any ordinary vault op (e.g. `deposit`) triggers `accrue-and-cache`, which computes and **caches** `(index, lindex)` for `{timestamp: T, aid: STX}` — call this `lindex_cached = L0`.
2. tx2 — a liquidation results in bad debt; `vault-socialize-debt` writes down the vault's `assets`/`total-borrowed`, causing the vault's *actual* recoverable value per share to drop (analogous to Blend's `b_rate` drop). The market's `index-cache-[{T, STX}]` entry is **not** touched.
3. tx3 — `redeem`/withdraw calls `accrue-and-cache` again in the same block; since `map-get? index-cache- {timestamp: T, aid: STX}` is a **cache HIT**, the market returns the stale `L0` instead of re-deriving the post-default (lower) index.

Redemption math (e.g. `convert-to-assets`) then pays out underlying using the stale, higher `lindex`, while the vault's true backing has already been reduced by the default. Just as in the Blend PoC (pool burns b_tokens at the true rate 1.05 while the vault accounts at the stale rate 1.1, creating a 43-token deficit), the zToken holder(s) who redeem after tx3 receive more underlying than the vault's post-default assets can support, leaving a deficit for whoever redeems last.

### Impact Explanation
This breaks the core share-vs-backing identity (shares minted/burned vs. actual underlying backing them). The mismatch directly causes protocol insolvency in the affected vault: the sum of ztoken claims after the exploited redemption exceeds the vault's real remaining assets, and the last redeemer(s) cannot be made whole. This satisfies the Critical impact bar (protocol insolvency / theft of principal by inflated redemption at others' expense).

### Likelihood Explanation
Exploitation requires: (a) a liquidation that produces bad debt beyond backstop coverage causing `socialize-debt` to be invoked, and (b) an attacker (or anyone) bundling a prior same-block operation that pre-populates the index cache, then redeeming immediately after the default in the same block. This is a rare, edge-case scenario dependent on an actual bad-debt event, matching the "extremely edge case" characterization in the original Blend report, but it requires no privileged access and no DAO compromise — any user can construct the bundled sequence once a default occurs, so likelihood is Low but the path is unprivileged and reachable.

### Recommendation
Invalidate or bypass the `index-cache-` entry whenever `socialize-debt` (or any other function that force-writes vault `assets`/`total-borrowed`/index state outside the normal accrual path) is executed, or simply remove the timestamp-based cache HIT short-circuit and always re-derive the index from the vault's live state when bad-debt events are possible in the same block. Alternatively, have `vault-socialize-debt` explicitly `map-delete` (or update) the corresponding `index-cache-` entry for the current `stacks-block-time` before returning.

### Proof of Concept
1. Block N, tx1: user calls a normal vault op on `vault-stx` (e.g. `deposit`) → `accrue-and-cache` computes fresh `(index, lindex)` and caches it under `{timestamp: N, aid: STX}`.
2. Block N, tx2: a liquidation triggers `vault-socialize-debt` on `vault-stx`, writing down `assets`/`total-borrowed` (bad debt), which would produce a lower true `lindex` if recomputed — but `index-cache-[{N, STX}]` still holds the pre-default value from tx1.
3. Block N, tx3: attacker calls `redeem` on `zSTX`; `accrue-and-cache` hits the cache and returns the stale, higher `lindex`, so `convert-to-assets` overpays the attacker relative to the vault's actual post-default backing.
4. Later redeemers in subsequent blocks find the vault's `assets` insufficient to honor remaining ztoken claims at the correct (now properly recomputed) index — protocol insolvency for the vault.

Note: I was not able to fully read the complete `socialize-debt` implementation body in `v0-vault-stx.clar` within the available tool budget to see every line mutating `assets`/`total-borrowed`, so the precise numeric write-down mechanics are inferred from the analogous `next-index`/`next-liquidity-index` accrual logic and the `vault-socialize-debt` dispatch function; a full review of `socialize-debt`'s body in `mainnet/contracts/vault/v0-vault-stx.clar` is recommended to confirm it never touches `index-cache-`.
