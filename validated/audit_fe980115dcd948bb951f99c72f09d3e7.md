### Title
Webhook topic header is unauthenticated and trusted by `Registry.process` for handler dispatch - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`Utils::HmacValidator.validate` authenticates a webhook by recomputing an HMAC over `Request#to_signable_string`, which returns only `@raw_body` [1](#0-0) . `Registry.process` then reads `request.topic`, which is parsed straight from the `X-Shopify-Topic`/`Shopify-Topic` HTTP header and is not covered by the signature, to select which registered handler to invoke [2](#0-1) . Because the topic (and shop-domain, webhook-id, api-version) headers are excluded from the signed content, an attacker who owns a validly-signed `(raw_body, hmac)` pair from their own dev shop can rewrite the topic header and have it accepted by `HmacValidator.validate` while being routed to a different handler than the one that was actually authentically triggered.

### Finding Description
The binding the app relies on is: `handler dispatched by Registry.process == handler for the topic that Shopify actually signed`. Tracing the code shows this is false. `Request#hmac` reads `shopify-hmac-sha256` header value, and `Request#topic` reads `shopify-topic`/`x-shopify-topic` header value [3](#0-2) . `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` via `OpenSSL.secure_compare` [4](#0-3) . `to_signable_string` returns `@raw_body` only [1](#0-0) , so the topic header (and shop-domain, webhook-id, api-version headers) never enter the HMAC computation. `Registry.process` calls `Utils::HmacValidator.validate(request)`, then immediately uses `request.topic` (the unauthenticated header) as the registry key to fetch `handler = @registry[request.topic]&.handler`, and forwards `request.topic`/`request.shop` into `WebhookMetadata` without any secondary check that the topic matches the body's actual event type [2](#0-1) .

Given a legitimately-issued webhook `(B, HMAC(B))` delivered by Shopify to the attacker's own dev-shop endpoint for topic `orders/create`, the attacker can resend a POST with the same body `B` and the same `X-Shopify-Hmac-Sha256` header, but with `X-Shopify-Topic` rewritten to `customers/redact`. `HmacValidator.validate` still returns `true` because it only checks `B` against the HMAC, and `Registry.process` dispatches to the `customers/redact` handler instead of the `orders/create` handler that Shopify actually generated and signed.

No existing guard closes this gap: `HmacValidator.validate` only checks body integrity, not header integrity; `Registry.process` performs no comparison between the body's semantic content and the header-derived topic; and there is no Sorbet typing or `Context` check that constrains header values to match the signed payload.

### Impact Explanation
This breaks the implicit trust assumption that `request.topic` (and equally `request.shop`, `request.webhook_id`, `request.api_version`) is authenticated alongside the body. Because none of these headers are covered by the signature, an attacker can freely rewrite them on any request carrying a validly-signed body from their own shop, causing the app to invoke an arbitrary registered handler (e.g., a compliance handler like `customers/redact` or `shop/redact`) with mismatched/attacker-influenced routing metadata. Since `request.shop` is also excluded from the signature, an attacker could similarly forge the shop-domain header, meaning the app's handler code, if it trusts `request.shop` from `WebhookMetadata` as an authenticated tenant identifier, could be made to associate one tenant's signed body with another shop's identifier — a cross-tenant integrity issue. The blast radius depends on what handlers do with `topic`/`shop`, but the underlying primitive — headers presented as verified but never included in the signature — is a genuine authentication-bypass class issue matching the "forged webhook accepted" category.

### Likelihood Explanation
The attacker only needs their own development shop and control of their own webhook receiving endpoint (a normal, unprivileged capability), and the ability to relay/replay one HTTP POST with modified headers. No secrets are required. The precondition is that `Registry.process`/`HmacValidator.validate` is used as documented — which is the standard integration pattern for this gem — and that the app has handlers registered for more than one topic. This is trivially repeatable per request and does not require any race condition or timing dependency.

### Recommendation
Include the security-relevant headers (`topic`, `shop-domain`, `webhook-id`, `api-version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them to the body before trusting them for dispatch (e.g., verify that the body's own shop/topic-identifying fields match the headers before using the headers for routing). At minimum, `Registry.process` should not treat `request.topic`/`request.shop` as authenticated for dispatch purposes if they are not covered by the signature.

### Proof of Concept
Add a minitest under `test/webhooks/registry_test.rb` (or extend `test/utils/hmac_validator_test.rb`) using WebMock/Mocha with no live shop:
1. Build `raw_body = '{"id":1}'` and compute `hmac = OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), Context.api_secret_key, raw_body)`, base64-encode it as `X-Shopify-Hmac-Sha256` would appear.
2. Construct `request_a = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: {"x-shopify-topic" => "orders/create", "x-shopify-hmac-sha256" => hmac_b64, "x-shopify-shop-domain" => "attacker.myshopify.com"})`.
3. Construct `request_b` identically except `"x-shopify-topic" => "customers/redact"`.
4. Assert `ShopifyAPI::Utils::HmacValidator.validate(request_a) == true` and `ShopifyAPI::Utils::HmacValidator.validate(request_b) == true` — proving the same signed body validates under two different topic claims.
5. Register two mock handlers via `Registry.add_registration` for `orders/create` and `customers/redact`, call `Registry.process(request_a)` and `Registry.process(request_b)`, and assert that different handlers' `handle` methods are invoked — proving the header-derived topic (not the signature) determines dispatch.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
