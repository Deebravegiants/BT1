## Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted for handler dispatch and tenant identification but are never covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. Because the app's `api_secret_key` is shared across every shop that installs the app (it is not a per-shop secret), any unprivileged merchant who has installed the app can capture one legitimately-signed webhook body/HMAC pair from their own shop and replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`) header. `HmacValidator.validate` will accept it, and `Registry.process` will hand the attacker-chosen `shop`/`topic` straight to the app's handler as if the event genuinely originated from that shop/topic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., the raw body) with the shared `Context.api_secret_key`: [3](#0-2) 

`Registry.process` trusts the HMAC check alone before dispatching to the handler using the header-derived, unauthenticated `topic` and `shop`: [4](#0-3) 

The equality this breaks: **bytes verified by HMAC** (`raw_body`) **≠ bytes acted upon for tenant/topic identification** (`shopify-shop-domain`, `shopify-topic` headers). Since `api_secret_key` is a single app-wide secret shared by all installing shops (not shop-specific), any shop that installs the app can legitimately obtain a valid `(raw_body, hmac)` pair for itself, then replay that exact pair to the app's public webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop's domain (and/or the `x-shopify-topic` header to a different registered topic). The signature still validates because it only ever covered the body, so `Registry.process` will invoke the handler believing the event came from the victim shop/topic.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged app-installing merchant can forge webhook events that the host application will attribute to any other shop using the app, without needing the victim's credentials, access token, or `client_secret`. Any host application logic that trusts `WebhookMetadata#shop`/`#topic` for tenant-scoped side effects (updating that shop's records, billing, triggering per-shop workflows) can be manipulated cross-tenant purely from data the attacker legitimately possesses for their own shop.

### Likelihood Explanation
Any user who installs the app (a completely unprivileged action) can capture a valid webhook delivery for their own shop and replay it against the app's public HTTP webhook endpoint with modified headers — no secret, token, or elevated access is required.

### Recommendation
Bind the shop/topic identity into the signed material, or otherwise cryptographically tie the header-derived fields to the verified payload — e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or require that the webhook's declared shop matches the shop for which the app registered that specific webhook subscription (validated server-side, not merely inferred from the header) before dispatching to a handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets the app register a webhook (e.g., `orders/create`).
2. Attacker captures a real webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — valid because `api_secret_key` is the same for every shop installing this app.
3. Attacker POSTs the same body `B` and header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, a different `x-shopify-topic`).
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only checks `B` against `H`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the host app to process attacker-supplied data under the victim's tenant identity.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
