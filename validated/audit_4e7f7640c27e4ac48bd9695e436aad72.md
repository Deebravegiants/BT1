### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , so `Utils::HmacValidator.validate` only proves that the request body was signed with the app's shared webhook secret (`Context.api_secret_key`) [3](#0-2) . However, `request.shop` (and `topic`/`webhook_id`) are read straight from HTTP headers that are never included in the signed payload [4](#0-3) , yet `Registry.process` still uses this unauthenticated `request.shop` as the tenant identifier delivered to the app's webhook handler [1](#0-0) .

### Finding Description
The binding that should hold is: `hmac-verified bytes == bytes the handler trusts as belonging to a specific shop`. Here it does not: `to_signable_string` == `@raw_body` only, while the field actually consumed as the tenant/shop identity, `request.shop`, comes from a separate, unsigned header [5](#0-4) . Because the webhook HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that has the app installed, any shop that installs the app receives genuine webhook deliveries containing valid `(raw_body, hmac)` pairs. An attacker who controls a shop with the app installed can capture one of their own legitimately-signed webhook deliveries and resend the exact same `raw_body`/`hmac` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` will still pass, because it only checks the raw body against the secret [6](#0-5) , and `Registry.process` will hand the handler a `WebhookMetadata` claiming the forged shop as the source [7](#0-6) .

### Impact Explanation
This breaks the `shop authenticated == shop used for tenant identification` binding described in the rules. A host application that (reasonably, per this gem's documented contract) trusts `WebhookMetadata#shop` as an authenticated tenant identifier can be tricked into writing/processing data under, or attributing events to, a shop the attacker does not control — a cross-tenant confusion/injection primitive that satisfies the "cross-tenant access" impact bar, since the attacker (an unprivileged merchant who merely installed the app) never needs the victim's credentials to make the gem report events "from" the victim shop.

### Likelihood Explanation
Likelihood is moderate to high in any deployment that follows this gem's own webhook processing API as documented: installing the app on any single shop provides the attacker with a validly-signed `(body, hmac)` pair (since the secret is app-wide, not per-shop), and replaying it with a substituted shop header requires no cryptographic work — only a direct HTTP request to the app's webhook endpoint.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`/timestamp) in the signed/verified material, or otherwise cryptographically bind the shop identity to the HMAC-covered bytes before exposing it via `WebhookMetadata`. At minimum, document prominently that `request.shop` is unauthenticated and must be cross-checked against a shop known to have registered/subscribed to that webhook (e.g., verified against stored shop/session records) before being trusted as a tenant identity.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a legitimate webhook delivery, capturing `raw_body` and the corresponding `x-shopify-hmac-sha256` value (both valid because the app's shared secret signs the body only).
2. Attacker sends a POST to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the shared secret [6](#0-5) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` despite the request never having been signed with any binding to that shop [7](#0-6) .
