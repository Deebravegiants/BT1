Audit Report

## Title
`DynamicMaxBlockWeight`'s position-based transaction window can be exhausted by weight-refunding extrinsics, denying legitimate large extrinsics full-core access in the same block - (File: cumulus/pallets/parachain-system/src/block_weight/transaction_extension.rs)

## Summary
`DynamicMaxBlockWeight::pre_validate_extrinsic` gates entry into `PotentialFullCore` mode using `transaction_index - first_transaction_index < MAX_TRANSACTION_TO_CONSIDER`, where `first_transaction_index` is fixed once on the very first non-inherent transaction of the block and never advances. Because `post_dispatch_extrinsic` reverts `PotentialFullCore` back to `FractionOfCore` whenever the actual (post-refund) class weight is not above `target_weight`, an attacker can submit `MAX_TRANSACTION_TO_CONSIDER` transactions with high declared pre-dispatch weight but low actual/refunded weight to consume the position-based window without ever using full-core capacity, causing a subsequent legitimate large extrinsic in the same block to be unconditionally rejected with `InvalidTransaction::ExhaustsResources`.

## Finding Description
The code confirms the claim's mechanics exactly as described:

- `first_transaction_index` is set once, either when entering `PotentialFullCore` (`first_transaction_index.or(transaction_index)`) or when settling into `FractionOfCore` (`first_transaction_index.or(transaction_index)`), and is preserved thereafter via `.or()` short-circuiting once `Some`. [1](#0-0) [2](#0-1) 

- The window check that gates `PotentialFullCore` entry (and rejects with `ExhaustsResources` otherwise) uses `transaction_index - first_transaction_index < MAX_TRANSACTION_TO_CONSIDER`, i.e., raw extrinsic position relative to a fixed anchor, not a count of genuine full-core attempts. [3](#0-2) 

- In `post_dispatch_extrinsic`, `PotentialFullCore` reverts to `FractionOfCore` (preserving the fixed `first_transaction_index`) whenever the post-dispatch class weight is not above `target_weight`, which is fully controllable by the extrinsic's `PostDispatchInfo::actual_weight` refund — a standard, legitimate SDK pattern (many pallets report a smaller actual weight than the worst-case declared weight). [4](#0-3) 

Combining these: each crafted "declared-heavy/refunded-light" extrinsic advances `transaction_index` by one but never advances `first_transaction_index`, so the window's remaining budget (`MAX_TRANSACTION_TO_CONSIDER` slots) is consumed strictly by *position*, regardless of whether the block ever consumed real full-core weight. No mechanism resets or advances the anchor after an oscillation back to `FractionOfCore`, and `class_allowed`/`is_first_block` checks are satisfied identically by both crafted and legitimate transactions, so they provide no protection against this specific pattern. This matches the existing unit tests: `tx_extension_large_tx_with_refund_goes_back_to_fractional` demonstrates the bounce-back behavior per transaction, and `tx_extension_large_tx_after_limit_is_rejected` demonstrates that once past the window, a genuinely large extrinsic is rejected with `ExhaustsResources` while the mode stays `FractionOfCore` (never reaching `FullCore`). [5](#0-4) [6](#0-5) 

## Impact Explanation
The described effect is real and traceable in code: a block that never used full-core weight can be left unable to accept a legitimate oversized extrinsic (e.g., a runtime upgrade or other large operational call) submitted within the same first-block-of-core window, because the bounded attempt budget was consumed by cheap declared-heavy/refunded-light transactions. This is a denial-of-service against inclusion of high-weight extrinsics scoped to a specific block, matching a resource-accounting/availability bug rather than a funds-loss or privilege-escalation issue. The severity is bounded: it affects only the specific block(s) where the attacker's transactions land before the legitimate large extrinsic, and the legitimate extrinsic can simply be resubmitted in a later first-block-of-core window.

## Likelihood Explanation
The preconditions are narrow but not unrealistic: `DynamicMaxBlockWeight` must be configured with `ALLOW_NORMAL = true` (the documented default), the target block must be the first block of a core, and the attacker's transactions with declared weight above `target_weight` but refundable actual weight must be ordered before the legitimate extrinsic in the same block — achievable in an open mempool via tip/priority. This requires no special privilege, only crafting calls that exploit the standard SDK weight-refund pattern (`PostDispatchInfo::actual_weight`). This is repeatable per qualifying block. However, exploitation depends on runtime-specific factors (whether such refund-capable calls with sufficiently high declared/low actual weight gaps exist in the deployed runtime, and whether the attacker can reliably win ordering against the legitimate extrinsic), which the report does not fully demonstrate with a runtime-specific example, though the existing unit tests corroborate the state-machine mechanics in isolation.

## Recommendation
Anchor and advance the window based on actual "over-target" attempts (i.e., increment a counter only when an extrinsic enters the over-target branch, independent of raw extrinsic position), or reset/advance `first_transaction_index` appropriately after each `PotentialFullCore → FractionOfCore` bounce-back so that non-triggering transactions interleaved in the block do not consume the shared budget intended for genuine full-core candidates. Alternatively, track window consumption keyed off the declared-vs-actual weight discrepancy so that only extrinsics whose actual weight remains close to declared weight consume the limited attempts.

## Proof of Concept
Extend `cumulus/pallets/parachain-system/src/block_weight/tests.rs` as follows:
1. Build test ext with `first_block_in_core(true)`, `number_of_cores(2)`, call `initialize_block_finished()`.
2. Loop `i in 0..MAX_TRANSACTION_TO_CONSIDER`: set `System::set_extrinsic_index(i)`, build `DispatchInfo` with `call_weight = target_weight + small_over_amount`, call `TxExtension::validate_and_prepare(...)` and assert `Ok` with mode `PotentialFullCore { first_transaction_index: Some(fixed_idx), .. }`; then call `post_dispatch` with `PostDispatchInfo { actual_weight: Some(small_refunded_weight), .. }` and assert mode reverts to `FractionOfCore { first_transaction_index: Some(fixed_idx), .. }` (per `tx_extension_large_tx_with_refund_goes_back_to_fractional`).
3. Set `System::set_extrinsic_index(MAX_TRANSACTION_TO_CONSIDER)`, build a genuinely large `DispatchInfo` (e.g. runtime-upgrade-sized weight), call `validate_and_prepare`, and assert it returns `Err(InvalidTransaction::ExhaustsResources.into())`.
4. Assert `crate::BlockWeightMode::<Runtime>::get()` never transitioned to `FullCore` for the block, confirming denial of the legitimate large extrinsic despite the block never using full-core capacity (mirrors `tx_extension_large_tx_after_limit_is_rejected`).

#[test]
fn tx_extension_large_tx_with_refund_goes_back_to_fractional() {
	TestExtBuilder::new()
		.number_of_cores(2)
		.first_block_in_core(true)
		.build()
		.execute_with(|| {
			initialize_block_finished();

			System::set_extrinsic_index(1);

			// Create a transaction larger than target weight
			let target_weight = MaximumBlockWeight::target_block_weight();
			let large_weight = target_weight
				.saturating_add(Weight::from_parts(WEIGHT_REF_TIME_PER_SECOND, 1024 * 1024));

			let info = DispatchInfo {
				call_weight: large_weight,
				class: DispatchClass::Normal,
				..Default::default()
			};

			assert_ok!(TxExtension::validate_and_prepare(
				TxExtension::new(Default::default()),
				SystemOrigin::Signed(0).into(),
				&CALL,
				&info,
				100,
				0,
			));

			assert_matches!(
				crate::BlockWeightMode::<Runtime>::get(),
				Some(BlockWeightMode::PotentialFullCore { first_transaction_index: Some(1), .. })
			);

			let mut post_info = PostDispatchInfo {
				actual_weight: Some(Weight::from_parts(5000, 5000)),
				pays_fee: Default::default(),
			};

			assert_ok!(TxExtension::post_dispatch((), &info, &mut post_info, 0, &Ok(())));

			assert_matches!(
				crate::BlockWeightMode::<Runtime>::get(),
				Some(BlockWeightMode::FractionOfCore { .. })
			);
			assert!(!has_use_full_core_digest());
			assert_eq!(MaximumBlockWeight::get(), target_weight);
		});
}

#[test]
fn tx_extension_large_tx_after_limit_is_rejected() {
	TestExtBuilder::new()
		.number_of_cores(2)
		.first_block_in_core(true)
		.build()
		.execute_with(|| {
			initialize_block_finished();

			// Set some index above the limit.
			System::set_extrinsic_index(20);

			// Create a transaction larger than target weight
			let target_weight = MaximumBlockWeight::target_block_weight();
			let large_weight = target_weight
				.saturating_add(Weight::from_parts(WEIGHT_REF_TIME_PER_SECOND, 1024 * 1024));

			let info = DispatchInfo { call_weight: large_weight, ..Default::default() };

			assert_eq!(
				TxExtension::validate_and_prepare(
					TxExtension::new(Default::default()),
					SystemOrigin::Signed(0).into(),
					&CALL,
					&info,
					100,
					0,
				)
				.unwrap_err(),
				InvalidTransaction::ExhaustsResources.into()
			);

			assert_eq!(
				crate::BlockWeightMode::<Runtime>::get(),
				Some(BlockWeightMode::fraction_of_core(None))
			);
			assert!(!has_use_full_core_digest());
		});
}
