### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the shop-identifying header (`shop-domain`) and other routing headers are read separately and never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identity after validating only the body's HMAC, breaking the intended binding `HMAC(secret, signed_bytes) == HMAC(secret, received_bytes)` where `signed_bytes` should equal `bytes_the_handler_acts_on` but instead `signed_bytes = raw_body` while `bytes_the_handler_acts_on = raw_body + shop_header`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are instead pulled directly from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e. only the raw body) and then immediately trusts `request.shop` to build the tenant-identifying `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

Because `Context.api_secret_key` is a single app-wide secret shared across every merchant that installs the app (not a per-shop secret), any merchant who installs the app legitimately receives real, validly-signed webhook deliveries for their own shop. Since the signature covers only the body bytes, that same `(body, hmac)` pair remains valid no matter what `shop-domain` (or `topic`/`webhook_id`) header value accompanies it. An attacker who controls their own shop can therefore capture a legitimately-signed webhook body and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop. `HmacValidator.validate` still succeeds because it only recomputes the signature over `to_signable_string` (the raw body): [5](#0-4) 

The app's `WebhookHandler` then processes attacker-controlled `body` content under the false belief that it originated from the victim shop, since `data.shop` is taken verbatim from the unauthenticated header.

### Impact Explanation
This breaks the tenant/shop identity binding the gem is supposed to guarantee for webhook payloads, enabling cross-tenant data injection: an attacker-controlled webhook body can be attributed to a shop the attacker doesn't own. Any downstream logic keyed off `WebhookMetadata#shop` (the documented and recommended pattern, e.g. persisting or acting on data "for shop X") can be poisoned with attacker data mislabeled as belonging to another merchant, which is a cross-tenant access impact.

### Likelihood Explanation
Requires only that the attacker be an unprivileged merchant/installer of the target public app (no special credentials, no access to `api_secret_key`, no access to the victim's data) and the ability to send an HTTP request to the app's public webhook endpoint with modified headers — both conditions any internet user satisfies once they've installed the app on their own shop and captured one real webhook delivery.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`/`api_version`) header values in the signed material, or otherwise cryptographically bind them to the raw body before verifying, e.g. by having `to_signable_string` incorporate the shop domain, or by requiring hosts to additionally verify shop identity against their session/installation records rather than trusting `WebhookMetadata#shop` derived solely from an unauthenticated header.

### Proof of Concept
1. Attacker installs the target public app on their own shop `attacker-shop.myshopify.com`.
2. Attacker performs an action that triggers a real webhook (e.g. `orders/create`) with a body they control/can predict, and captures the genuine `X-Shopify-Hmac-Sha256` value Shopify sent along with it — this HMAC is valid because it is computed with the app's single shared `api_secret_key` over just the raw body, per `Request#to_signable_string` / `HmacValidator.compute_signature`.
3. Attacker resends this exact `(raw_body, hmac)` pair directly to the app's webhook endpoint, but replaces the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes the signature over the raw body only and it matches, so `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: attacker_controlled_body))`, per `lib/shopify_api/webhooks/registry.rb:188-199`.
5. The app's handler processes attacker-controlled data believing it belongs to `victim-shop.myshopify.com`.
