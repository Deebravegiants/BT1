This confirms the vulnerability: the webhook HMAC in `to_signable_string` at [1](#0-0)  only covers `@raw_body`, while `topic`, `shop`, `api_version`, and `webhook_id` are all read from HTTP headers via `shopify_header` at [2](#0-1)  and are never part of the signed content. `Registry.process` validates only the body HMAC and then passes the unauthenticated `request.shop` and `request.topic` straight to the handler as tenant/event identity: [3](#0-2) .

### Title
Webhook HMAC does not bind `shop-domain`/`topic` headers, enabling cross-tenant webhook forgery via signature replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so the HMAC validated by `Utils::HmacValidator.validate` in `Registry.process` never covers the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Any request whose body matches a previously-observed, validly-signed body will pass HMAC validation regardless of which shop or topic headers are attached, breaking the binding `hmac == HMAC(secret, shop || topic || body)` down to `hmac == HMAC(secret, body)`.

### Finding Description
`Request#hmac` decodes the `hmac-sha256` header, and `Request#to_signable_string` returns `@raw_body` only: [4](#0-3) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controllable HTTP headers with no cryptographic tie to the signed body: [5](#0-4) 

`Registry.process` validates the HMAC over the body and then trusts `request.shop`/`request.topic` to route and label the event to the handler as the tenant identity: [3](#0-2) 

Because many webhook topics (e.g. `app/uninstalled`, `shop/redact`) have small, fixed, or fully predictable JSON bodies (the test suite even signs a body of `"{}"`: [6](#0-5) ), a genuine merchant/app-installer who legitimately receives such a webhook for their own shop can capture the `(body, hmac)` pair and resend it to the app's public webhook endpoint with a different `shopify-shop-domain` (and/or `shopify-topic`) header. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) will accept the forged request because it only recomputes the HMAC over `to_signable_string`, which is identical to the original, legitimate one. The handler then processes the forged event believing it came from the victim shop, i.e. the equality the app relies on — "shop authenticated == shop the handler acts on" — is broken because the shop is never part of what is authenticated.

### Impact Explanation
This yields cross-tenant confusion at the webhook layer: an attacker who controls one legitimate installation can forge webhook deliveries attributed to any other shop for topics with predictable/static bodies (mandatory topics `shop/redact`, `customers/redact`, `customers/data_request` are especially exposed since their payload shape is fixed and documented). Host applications built on this gem's stated contract (`WebhookMetadata#shop`/`#topic` reflect the authenticated sender) will act on forged shop/topic data — e.g., triggering data deletion, uninstall cleanup, or state changes for a shop the attacker does not control — a cross-tenant impact.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint and access to one legitimate `(body, hmac)` pair, obtainable by installing/uninstalling the app on the attacker's own shop (no `api_secret_key` or access token needed). The predictability of certain payloads (empty or fixed-shape bodies for mandatory GDPR topics and `app/uninstalled`) makes this practically exploitable rather than theoretical.

### Recommendation
Bind the tenant/event identity into the signed material actually verified — e.g., have `to_signable_string` incorporate `shop`, `topic`, and `webhook_id` alongside the raw body (matching what Shopify itself signs), or independently verify that the `shopify-shop-domain` header corresponds to a shop with an active session/registration for the given `webhook_id` before dispatching to the handler.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger `app/uninstalled` (body `{}`), capturing headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: app/uninstalled`.
2. POST to the app's webhook endpoint with the same raw body `{}` and same `hmac-sha256: H`, but `shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only (`lib/shopify_api/webhooks/request.rb:35-38`) — validation succeeds because the body is unchanged.
4. The handler receives `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim.myshopify.com", ...)` and performs uninstall-cleanup logic for `victim.myshopify.com`, even though Shopify never sent this webhook for that shop.
