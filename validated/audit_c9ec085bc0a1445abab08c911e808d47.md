### Title
Webhook `shop-domain`/topic/`webhook_id` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw HTTP body only, while the shop identity (`shop-domain` header), `topic`, `webhook_id` and `api_version` are read from unauthenticated HTTP headers that are never included in the signed content. `Registry.process` treats a passing HMAC check as proof the whole request "did indeed come from Shopify" for the shop named in the header, but the signature never binds that header to the body.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from HTTP headers, none of which participate in the signable string: [2](#0-1) 

`Registry.process` validates only the body’s HMAC and then dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

`HmacValidator.validate` computes the signature over `to_signable_string` (the raw body) and compares it to the `hmac-sha256` header, with no reference to any other header: [4](#0-3) 

The identity binding the app relies on is:
`hmac == HMAC(secret, raw_body)` ⇒ "request authentic for `shop = header['shop-domain']`"

but the actual equality proven is only `hmac == HMAC(secret, raw_body)` — it says nothing about which shop, topic, or webhook id the header claims. Because the gem's shared `api_secret_key` is the same across every shop that installs the app, any tenant that receives a legitimate webhook (a valid `(raw_body, hmac)` pair for their own shop) can capture that pair and replay the identical body to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header pointing at a different shop. The HMAC check still passes because it only verifies the body bytes, so `Registry.process` calls the app's handler with `WebhookMetadata.shop` set to the victim shop while the body content is attacker-controlled/attacker-sourced.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide: the docs explicitly tell integrators that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook," directing them to use it directly for per-shop dispatch (e.g. `perform_later(shop_domain: data.shop, webhook: data.body)`). An attacker who is a legitimate, unprivileged merchant on their own shop can therefore inject attacker-controlled webhook bodies attributed to an arbitrary victim shop, including for mandatory compliance topics such as `customers/redact`, `shop/redact`, and `customers/data_request`, resulting in cross-tenant data processing/corruption in any host app that trusts `data.shop` as the gem instructs.

### Likelihood Explanation
Moderate-to-high. Any app installer (an unprivileged internet user relative to other tenants) automatically receives valid `(body, hmac)` pairs from Shopify for their own shop's webhooks and can replay them with a forged shop header to the same public webhook endpoint; no access to `api_secret_key`, access tokens, or other shops' secrets is required.

### Recommendation
Include the trust-sensitive headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable string, or otherwise cryptographically bind them to the body before dispatch, so that `HmacValidator.validate` proves authenticity of the header-derived identity, not just the body bytes.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; Shopify sends a legitimate webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(secret, B)`.
2. Attacker captures `(B, H)` from their own webhook delivery (e.g. via their own server logs).
3. Attacker POSTs to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally forges `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Request#hmac` decodes `H`; `HmacValidator.validate` recomputes `HMAC(secret, B)` — matches, since `B` is unchanged — so `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`.
5. The host app, following the gem's documented pattern of trusting `data.shop`, processes body `B` as if it originated from `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
