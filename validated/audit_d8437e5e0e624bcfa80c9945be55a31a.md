### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The webhook signature validation in this gem only authenticates the raw request body; the tenant-identifying `shop` field (and `topic`, `webhook_id`, `api_version`) are read directly from unauthenticated HTTP headers and handed to the app's handler as if they were verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then forwards the header-derived `shop` (and `topic`) unchanged to the app's handler as trusted tenant metadata: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` value — for webhooks this signable string is exactly the raw body, so the signature carries no information about which header set (`shop`, `topic`, `webhook_id`) was delivered alongside it: [4](#0-3) 

The identity binding this breaks is: `shop header used by handler.handle(shop: request.shop, ...)` should equal `shop cryptographically bound to the signed payload`, but instead only `HMAC(secret, body) == received_hmac` is checked, independent of `shop`. Because the same `(body, hmac)` pair remains valid under *any* `shop-domain`/`topic`/`webhook-id` header combination, any party who can obtain one genuine `(body, hmac)` pair for the app's secret — e.g., by installing the app on their own store and receiving a real webhook delivery — can replay that exact body/HMAC pair while substituting a different shop's domain in the `shop-domain` header (and/or a different `topic`/`webhook-id`). `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` dispatches the attacker-chosen `shop`/`topic` metadata to the handler as if Shopify had certified that binding.

### Impact Explanation
This lets an unprivileged user who merely installs the app on their own (attacker-controlled) shop forge webhook deliveries that the receiving app will attribute to an arbitrary other shop domain and/or arbitrary topic, since the gem never verifies that the `shop`/`topic`/`webhook_id` headers correspond to the signed body. Any host application that uses `WebhookMetadata#shop` (as documented/intended) to select tenant-scoped data, sessions, or access tokens would then process attacker-supplied data under another tenant's identity — a cross-tenant access vector, which maps to the Critical impact category.

### Likelihood Explanation
Obtaining a valid `(body, hmac)` pair only requires the attacker to install the app on a store they control and receive one genuine webhook; no access token, `client_secret`, or privileged account is required. Replaying it with modified headers against the app's public webhook endpoint is trivial for anyone who can send HTTP requests.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC validation, or otherwise cryptographically bind them to the payload, rather than validating the body alone while trusting headers unconditionally.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw request body `B` and its `x-shopify-hmac-sha256` header value `H` from the genuine delivery.
2. Resend a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com` (and, if desired, a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` parses the spoofed headers; `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B) == H`. [3](#0-2) 
4. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` and the attacker's own webhook body, causing the app to treat attacker-controlled data as belonging to `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
