Audit Report

## Title
Unauthenticated exposure of LOOP plugin metrics and pprof debug endpoints - (File: core/web/router.go)

## Summary
The `loopRoutes` handler group in `NewRouter` is registered directly on the `api` router group, which only has rate-limiting and session middleware attached, with no `auth.Authenticate(...)` wrapper. This exposes `/discovery`, `/plugins/:name/metrics`, and `/plugins/:name/debug/pprof/*` to any unauthenticated client. [1](#0-0) 

## Finding Description
The `api` group is created with only rate limiting and session middleware — no authentication middleware is attached at this level. [2](#0-1)  Every other route group registered under `api` that exposes sensitive data explicitly wraps itself with `auth.Authenticate(...)`: `debugRoutes` requires `auth.AuthenticateBySession` [3](#0-2) , `sessionRoutes`'s destroy route requires session auth [4](#0-3) , and `v2Routes`'s `authv2` subgroup requires token or session auth [5](#0-4) .

In contrast, `loopRoutes` registers its handlers directly on the raw `api` group with zero authentication wrapper: `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, and `/plugins/:name/debug/pprof/symbol` are all reachable unauthenticated. [6](#0-5) 

This is corroborated by the analogous `metricRoutes` function, which defines nearly identical `/debug/pprof/*` endpoints but is only ever invoked nested inside the authenticated `authv2` group, confirming that the pattern of protecting pprof/debug endpoints with auth is intentional and consistently applied everywhere except `loopRoutes`. [7](#0-6) [8](#0-7) 

The handler implementations confirm the internal/sensitive nature of the data being exposed: `discoveryHandler` returns Prometheus service-discovery groups including internal hostnames and plugin names [9](#0-8) ; `pluginMetricHandler` proxies raw metrics from an internal LOOP plugin process, with a code comment explicitly noting "this endpoint is internal btw the node and plugin" [10](#0-9) ; and `pluginPPROFHandler`/`pluginPPROFPOSTSymbolHandler` proxy full Go pprof debug data (heap, goroutine, CPU profile, symbol resolution) of the internal plugin process to the unauthenticated caller. [11](#0-10) 

No other middleware in the request pipeline (rate limiter, session middleware, CORS, helmet, secure/TLS redirect) performs any authentication or authorization check — they only rate-limit or set security headers, none of which requires a valid credential. [12](#0-11) 

## Impact Explanation
This maps to an in-scope information-disclosure impact: an unauthenticated client can enumerate internal LOOP plugin names/topology via `/discovery`, read raw Prometheus metrics via `/plugins/:name/metrics`, and pull full pprof heap/goroutine/CPU profiling data via `/plugins/:name/debug/pprof/*` — all without any credential. Heap and goroutine dumps can leak in-memory data and internal architecture details of the node's plugin processes, which is a legitimate information-disclosure/hardening issue, though it does not itself grant direct fund movement, job-run forgery, or credential/key exfiltration.

## Likelihood Explanation
High and trivially reproducible: no token, cookie, or role check is required — any client capable of reaching the node's web port over the network can issue a plain GET/POST and receive a `200 OK` response with internal diagnostic data. The routes are always registered unconditionally whenever `NewRouter` builds the engine.

## Recommendation
Wrap the `loopRoutes` group with the same `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` middleware used by `v2Routes`'s `authv2` group (or nest `loopRoutes` under `authv2` alongside `metricRoutes`), so that `/discovery`, `/plugins/:name/metrics`, and `/plugins/:name/debug/pprof/*` all require a valid session/API token before being served.

## Proof of Concept
1. Start a Chainlink node with at least one LOOP plugin registered and the web server listening on its configured port (e.g. 6688), per `NewRouter` / `loopRoutes` registration. [13](#0-12) 
2. Without any authentication (no cookie, no API token header), issue:
   - `curl http://<node>:6688/discovery`
   - `curl http://<node>:6688/plugins/<plugin-name>/metrics`
   - `curl http://<node>:6688/plugins/<plugin-name>/debug/pprof/heap`
3. Each request reaches `discoveryHandler`, `pluginMetricHandler`, or `pluginPPROFHandler` respectively and returns `200 OK` with internal plugin diagnostic data, since no `gin.HandlerFunc` in the chain performs an authentication check. [14](#0-13)

func (l *LoopRegistryServer) discoveryHandler(w http.ResponseWriter, req *http.Request) {
	w.Header().Set("Content-Type", "application/json")
	groups := make([]*targetgroup.Group, 0, 1+len(l.registry.List()))

	// add node metrics to service discovery
	groups = append(groups, pluginGroup(l.discoveryHostName, l.exposedPromPort, "/metrics"))

	// add all the plugins
	for _, registeredPlugin := range l.registry.List() {
		group := pluginGroup(l.discoveryHostName, l.exposedPromPort, pluginMetricPath(registeredPlugin.Name))
		group.Labels[LabelMetaPluginName] = model.LabelValue(registeredPlugin.Name)
		groups = append(groups, group)
	}
