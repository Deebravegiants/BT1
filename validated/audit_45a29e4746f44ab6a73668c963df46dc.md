## Title
Webhook HMAC only covers the request body, not the `shop-domain` header — allows cross-tenant shop impersonation via webhook replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC signature, but the HMAC is computed only over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken from unauthenticated HTTP headers — are then trusted and handed directly to the app's webhook handler as the tenant identity. Because the HMAC secret (`Context.api_secret_key`) is the app's single client secret shared across every shop that installs the app, any shop that installs the app can capture a validly-signed webhook (e.g. one with a generic/predictable body such as `{}`) and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, producing a request that still passes HMAC validation while impersonating another tenant.

### Finding Description
The HMAC binding is: `hmac == HMAC(api_secret_key, signable_string)`, where `signable_string` is defined as: [1](#0-0) 

which is just `@raw_body`. The `shop` accessor is read straight from a header with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` verifies the signature strictly against `to_signable_string` (the body), never the headers: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` (the header) as the tenant identity passed to the app's handler: [4](#0-3) 

Because `Context.api_secret_key` is the app's single client secret — identical for every shop that has the app installed — the value of the HMAC depends only on the body content, not on which shop sent it. Any shop that has installed the app can therefore:
1. Receive a real, validly-signed webhook from Shopify for its own store (many topics have small or predictable bodies, e.g. `app/uninstalled`, or bodies that are attacker-influenced, e.g. by triggering an event with attacker-chosen content on their own store).
2. Replay that exact `raw_body`/HMAC pair to the app's webhook endpoint, but with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain.
3. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` calls the handler with `shop: request.shop` set to the forged victim domain.

This breaks the equality the host application relies on: `shop authenticated by HMAC == shop used as the tenant/session key by the handler`. In reality, only `body authenticated by HMAC` holds; `shop` is attacker-controlled.

### Impact Explanation
Host applications built on this gem commonly key session/data lookups by `WebhookMetadata#shop` (e.g. to find the merchant's stored access token, update per-shop state, or trigger per-shop side effects) trusting that the webhook framework has already authenticated the sender. This finding allows any shop with legitimate (unprivileged) access to the app to forge webhook events "from" another shop, achieving cross-tenant data/state confusion in the host application — matching the Critical "cross-tenant access" impact category, since the attacker (a shop-level, unprivileged app user) can cause the app to attribute webhook-driven actions/data to a different tenant without possessing that tenant's credentials.

### Likelihood Explanation
Requires only that the attacker's own shop have the app installed (an unprivileged, ordinary merchant relationship) and be able to trigger or already possess one webhook delivery with a body it can predict/replay — a routine capability (e.g. `app/uninstalled` has an empty or fixed body across every shop). No access to `api_secret_key`, tokens, or victim credentials is needed.

### Recommendation
Bind the shop (and other routing metadata used by the handler) into the HMAC-signed material, or otherwise cryptographically verify that the `shop-domain` header matches the shop embedded in the signed body/payload before passing it to handlers. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be trusted as a tenant key without additional verification (e.g. cross-checking against a shop known to have registered that specific `webhook_id`/topic combination).

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`.
2. Shopify sends a real webhook (e.g. `app/uninstalled`, body `{}`) to the app, signed with `HMAC-SHA256(api_secret_key, "{}")`.
3. Attacker captures this raw body + valid `X-Shopify-Hmac-Sha256` value.
4. Attacker sends a new POST to the app's webhook endpoint with the same body/HMAC but `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the shared secret (see `lib/shopify_api/utils/hmac_validator.rb` lines 26-31 and `lib/shopify_api/webhooks/request.rb` lines 35-38).
6. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host app to process an event as if it originated from the victim shop.
