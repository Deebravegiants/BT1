Audit Report

## Title
Missing role restriction on `GET /v2/external_initiators` discloses initiator credentials to view-only users - (File: core/web/router.go)

## Summary
The `GET /v2/external_initiators` route is registered without any `auth.RequiresEditRole`/`RequiresAdminRole` wrapper, unlike the `POST` and `DELETE` routes on the same resource, allowing any authenticated user with the lowest-privilege `view` role to list all configured External Initiators. The returned `presenters.ExternalInitiatorResource` includes the `AccessKey` and `OutgoingToken` fields, which are authentication material used to gate inbound/outbound job-run interactions with the initiator.

## Finding Description
In the v2 router, `GET /v2/external_initiators` is mapped directly to `eia.Index` behind only the generic `paginatedRequest` wrapper and the base `auth.Authenticate` middleware for the `/v2` group, while the mutating routes for the same resource (`POST`, `DELETE`) are wrapped in `auth.RequiresEditRole`: [1](#0-0) 

The handler queries all external initiators from the DB and serializes each one via `presenters.NewExternalInitiatorResource`, with no filtering based on caller role: [2](#0-1) 

That presenter type directly exposes `AccessKey` and `OutgoingToken` in JSON, unlike `HashedSecret`/`OutgoingSecret`, which are appropriately omitted from the list resource: [3](#0-2) 

`AccessKey` and `OutgoingToken` are generated as authentication/credential material for the initiator alongside the hashed incoming secret: [4](#0-3) 

The project's own RBAC route-matrix test explicitly documents and asserts this behavior as intentional — `viewOnlyAllowed: true` for `GET /v2/external_initiators` — confirming that a `view`-role token is expected/allowed to succeed on this route: [5](#0-4) 

This is inconsistent with the write operations on the same resource (`POST`/`DELETE`), which require `edit` role, per the same test table: [6](#0-5) 

## Impact Explanation
Any authenticated API user provisioned with the minimal `UserRoleView` role — intended for read-only dashboard/API access — can retrieve `AccessKey` and `OutgoingToken` for every configured External Initiator via a single `GET /v2/external_initiators` call. This is a concrete, code-confirmed credential/secret disclosure to an under-privileged role, matching the "key/secret exfiltration" and role-bypass impact categories. The severity is bounded by the fact that External Initiators are an optional, deployment-specific feature and exploitation of the leaked `OutgoingToken` further depends on how the third-party initiator service validates that token — but the disclosure itself, to a role explicitly meant to be read-only/non-sensitive, is real and directly caused by application code (route wiring + presenter), not by any external/dependency/host factor.

## Likelihood Explanation
Exploitation requires only a valid `view`-role API credential — a role class that Chainlink explicitly supports and documents for less-privileged consumers — and a single authenticated GET request; no race condition, misconfiguration, or additional bug is needed. Any deployment that issues `view`-role tokens to less-trusted consumers (a supported, intended use case per the RBAC design) is automatically exposed.

## Recommendation
Wrap `GET /v2/external_initiators` with `auth.RequiresEditRole` (matching `POST`/`DELETE` on the same resource), or introduce a separate list-only presenter that omits `AccessKey`/`OutgoingToken` for non-privileged roles, consistent with how `HashedSecret`/`OutgoingSecret` are already excluded.

## Proof of Concept
1. Create/provision an API user with `UserRoleView`.
2. Authenticate as that user and issue `GET /v2/external_initiators` (routed at `core/web/router.go:264`).
3. Observe HTTP 200 with a response body containing `accessKey` and `outgoingToken` for each configured external initiator (per `presenters.ExternalInitiatorResource`), confirmed reachable by `view` role per the RBAC test table entry `{"GET", "/v2/external_initiators", true, true, true}` in `core/web/auth/auth_test.go:224`.
4. Contrast with `POST /v2/external_initiators` and `DELETE /v2/external_initiators/:Name`, which correctly reject `view`-role tokens (`false, false, true` in the same table), demonstrating the asymmetry is a routing gap rather than intended design for the GET endpoint.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```

// NewExternalInitiator generates an ExternalInitiator from an
// auth.Token, hashing the password for storage
func NewExternalInitiator(
	eia *auth.Token,
	eir *ExternalInitiatorRequest,
) (*ExternalInitiator, error) {
	salt := utils.NewSecret(utils.DefaultSecretSize)
	hashedSecret, err := auth.HashedSecret(eia, salt)
	if err != nil {
		return nil, pkgerrors.Wrap(err, "error hashing secret for external initiator")
	}

	return &ExternalInitiator{
		Name:           strings.ToLower(eir.Name),
		URL:            eir.URL,
		AccessKey:      eia.AccessKey,
		HashedSecret:   hashedSecret,
		Salt:           salt,
		OutgoingToken:  utils.NewSecret(utils.DefaultSecretSize),
		OutgoingSecret: utils.NewSecret(utils.DefaultSecretSize),
	}, nil
}
```
