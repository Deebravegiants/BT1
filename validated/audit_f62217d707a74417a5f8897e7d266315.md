### Title
Single `maxOracleAge` staleness bound applied to two Chainlink feeds with materially different heartbeats permits underpriced/overpriced gas charges - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-4337 gas payments using two independent Chainlink feeds — `nativeOracle` (native asset/USD) and each token's `tokenOracle` (token/USD) — but validates staleness for both using a single shared `maxOracleAge` value, exactly the anti-pattern described in the referenced report of using one heartbeat threshold for feeds that have very different actual update cadences.

### Finding Description
`_getOraclePrice` is called once for the `nativeOracle` and once for the registered `tokenOracle` inside `_tokenPrice`, and both calls are checked against the same `maxOracleAge` bound: [1](#0-0) 

The contract's own comments acknowledge that heartbeats differ drastically per chain/asset — native asset feeds like BNB/USD can update roughly every 27 seconds while stablecoin feeds on Base/Ethereum can go up to 24 hours between updates: [2](#0-1) [3](#0-2) 

Because `maxOracleAge` must be configured large enough to accommodate the slower stablecoin feed's heartbeat (e.g. up to 24h+ per deployment comments), that same bound is silently applied to the faster native-asset feed as well. This means a native-asset price that is many hours stale — far beyond its actual ~27s–1h heartbeat and thus potentially very divorced from the true market price — will still pass the staleness check in `_getOraclePrice`, since `block.timestamp - updatedAt > maxOracleAge` only reverts once the *stablecoin-sized* window is exceeded.

`_setParams` only enforces a single global sanity ceiling (`MAX_ORACLE_AGE = 7 days`) and a non-zero floor, with no per-oracle differentiation: [4](#0-3) 

`_tokenPrice`, which is read by any unprivileged UserOperation sender through `_fetchDetails`/`validate` during ERC-4337 validation, combines both prices without any per-feed heartbeat awareness: [5](#0-4) 

### Impact Explanation
`tokenPrice` returned from `_fetchDetails` directly determines `prefundAmount`, the ERC-20 amount pulled from the user via `transferFrom`/Permit2 to cover gas — reachable by any unprivileged UserOperation sender, not a privileged role: [6](#0-5) [7](#0-6) 

If the native-asset oracle answer is stale (up to the shared, stablecoin-sized `maxOracleAge` window) while the actual native asset price has since moved materially, users are charged token amounts derived from a wrong native/USD rate. If the native price stale value is too low relative to current market price, users are overcharged (an unbacked economic loss to depositors); if too high, the paymaster's treasury is undercompensated for gas actually spent, silently draining the paymaster's economics over many operations. This is a fund-loss/mispricing issue reachable from a normal, permissionless dispatch path (any account submitting a UserOperation), matching the "Medium: stale-price consumption from oracle" bug class in the source report.

### Likelihood Explanation
Every UserOperation routed through this paymaster invokes `_tokenPrice` → `_getOraclePrice` for both feeds; no privileged action or malicious admin/governance is required. The condition is simply: native oracle update lags while the value moves, within a window bounded by the stablecoin-tuned `maxOracleAge` (deployment defaults it to ~90,000s ≈ 25h per `DeploySimplexPaymaster.s.sol`) — well beyond the native feed's expected heartbeat. Native/USD feeds (e.g., ETH/USD, BNB/USD) are known to be volatile intraday, so a 25-hour-wide staleness window realistically allows meaningfully stale native prices to be used on every paymaster interaction during any period the sequencer/oracle network is slow to update, congested, or during a deviation-threshold gap between updates.

### Recommendation
Track and enforce a separate staleness bound per oracle — e.g. `maxNativeOracleAge` distinct from each `TokenConfig.maxOracleAge` (or a per-token field) — so the native/USD feed's heartbeat is validated against its own realistic cadence instead of inheriting the wider bound configured for slow-moving stablecoin feeds.

### Proof of Concept
1. Deploy `SimplexPaymaster` with `maxOracleAge = 90_000` (per the deploy script default) to accommodate a 24h stablecoin heartbeat.
2. Let the `nativeOracle` (e.g. ETH/USD, real heartbeat ~1h) go unrefreshed for 20+ hours while the true ETH/USD price moves by, say, 15%.
3. A user submits a UserOperation using this paymaster; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice(nativeOracle, ...)` passes the staleness check (20h < 90,000s ≈ 25h) despite the price being far outside the native feed's actual heartbeat/update cadence.
4. `prefundAmount` is computed from the stale native/USD price, causing the user to be charged (or the paymaster to be under/over-compensated) at a materially wrong rate versus current market conditions — without any revert, because the check was tuned for the token oracle, not the native oracle.

        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */

        internal
        view
        override
        returns (uint256 validationData, IERC20 token, uint256 tokenPrice)
    {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode != 0x00 && mode != 0x02) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);

        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction

            // Surfacing the permit deadline as validUntil lets bundlers drop
            // expiring ops instead of discovering it through a Permit2 revert.

            validationData = ERC4337Utils.packValidationData(true, 0, validUntil);

    function _prefund(
        PackedUserOperation calldata userOp,
        bytes32 userOpHash,
        IERC20 token,
        uint256 tokenPrice,
        address prefunder_,
        uint256 maxCost
    )
        internal
        override
        returns (bool prefunded, uint256 prefundAmount, address prefunder, bytes memory prefundContext)
    {
        bytes calldata data = userOp.paymasterData();
        if (uint8(data[0]) != 0x02) {
            return super._prefund(userOp, userOpHash, token, tokenPrice, prefunder_, maxCost);
        }

        (, uint256 permitAmount, uint256 nonce, uint256 deadline, uint8 v, bytes32 r, bytes32 s) =
            _parsePermit2Data(data);
        prefundAmount = _erc20Cost(maxCost, userOp.maxFeePerGas(), tokenPrice);
        if (prefundAmount > permitAmount) revert InsufficientPermitAmount(permitAmount, prefundAmount);
        // Solidity's own extcodesize revert on a code-less target is not caught by try/catch.
        if (address(PERMIT2).code.length == 0) revert Permit2NotDeployed();

        // Charge the token _fetchDetails already validated as registered and active, rather
        // than re-trusting the mode byte's token field, so the external call never depends
        // on the caller-ordering of the base contract.
        address tokenAddr = address(token);
        // `prefunder_` is who the base says funds the op (userOp.sender today); use it so this
        // branch stays aligned with the mode-0 branch that forwards it to super._prefund.
        address owner = prefunder_;
        try PERMIT2.permitTransferFrom(
            ISignatureTransfer.PermitTransferFrom({
                permitted: ISignatureTransfer.TokenPermissions({token: tokenAddr, amount: permitAmount}),
                nonce: nonce,
                deadline: deadline
            }),
            ISignatureTransfer.SignatureTransferDetails({to: address(this), requestedAmount: prefundAmount}),
            owner,
            abi.encodePacked(r, s, v)
        ) {
            emit Permit2Executed(tokenAddr, owner, prefundAmount, nonce);
        } catch (bytes memory reason) {
            revert Permit2Failed(tokenAddr, reason);
        }

        return (true, prefundAmount, owner, "");
    }

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
