Confirmed: `approveUnlimited` sets a permanent max allowance to `router` for `inputToken` if not already near-max [1](#0-0) , and it persists across unrelated future `transact` calls that reuse the same input token against the same `LifiExternalAction`/router pair.

### Title
Unaccounted input-token dust in `LifiExternalAction` is permanently frozen and can be siphoned by a later swapper via the pre-existing unlimited router allowance - ([File: contracts/external-actions/swaps/LifiExternalAction.sol])

### Summary
`LifiExternalAction.callRouter` only measures `outputToken` balance delta (`swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore`) and never verifies that the router actually consumed the full `inputAmount` transferred to it [2](#0-1) . Any input-token amount the router does not pull (whether refunded to the caller `LifiExternalAction` or simply left unspent) becomes stranded balance inside `LifiExternalAction` with no UTXO ever minted for it, and — because `approveUnlimited` leaves a standing max allowance from `LifiExternalAction` to `router` for that token [3](#0-2)  — a later, unrelated depositor swapping the same input token can craft `externalActionMetadata` whose encoded `amountIn` pulls more than their own newly transferred `inputAmount`, sweeping the stranded dust into their own swap and capturing the resulting extra `outputToken` as a bonus, uncompensated UTXO.

### Finding Description
The equality that should hold per swap is: `Hinkal-recorded amountChanges[0]` (input debited from the depositor's shielded balance) `== actual input tokens consumed by the router for that depositor's benefit`. Hinkal.sol's own ledger check only verifies that the *Hinkal contract's* balance change matches `amountChanges[i] + utxoAmount` [4](#0-3) ; it says nothing about what happens to funds once they leave Hinkal and enter `LifiExternalAction`. Inside `_externalTransact`, the full `deltaAmountChanges[i]` (negative) is transferred out of Hinkal to `LifiExternalAction` before `runAction` even executes [5](#0-4) , so Hinkal's own accounting is always self-consistent and cannot detect what fraction of that transferred amount the router actually used.

Inside `ExternalActionSwap.swap`, `inputAmount = -deltaAmounts[0]` (minus flat fee) is handed to `callRouter` along with attacker-fully-controlled `externalActionMetadata` [3](#0-2) . `LifiExternalAction.callRouter` calls `router.call(externalActionMetadata)` with no restriction on the encoded amount and never checks the post-call `inputToken` balance of `LifiExternalAction` [2](#0-1) . Two consequences follow:

1. **Freeze**: If a depositor's own crafted (or naturally partial-fill) router call under-consumes `inputAmount`, the unspent remainder stays in `LifiExternalAction` forever — `swap()` only forwards `amountToSendToHinkal` of the *output* token back to Hinkal [6](#0-5) , with no mechanism to return or account for leftover input token. That depositor's shielded balance was already fully debited at the Hinkal level, so the dust is an unrecoverable loss to them.
2. **Theft by a later caller**: Since `approveUnlimited` already grants `router` a standing max allowance over `LifiExternalAction`'s balance of that input token [1](#0-0) , any subsequent unrelated depositor who reuses the same input token can encode an `amountIn` in their own `externalActionMetadata` larger than their own freshly transferred `inputAmount`, up to `inputAmount + strandedDust`. The router will pull that combined balance via the pre-existing allowance and swap it, and `swappedAmount = balanceAfter - balanceBefore` will include the extra output generated from the stranded dust. That excess is credited entirely to the new depositor's `utxoSet[0].amount` and thus minted as a UTXO backed by funds that belonged to a different, unrelated depositor's earlier transaction. Nothing in `Hinkal.sol`'s equality check (which only compares Hinkal's own balance to `amountChanges`+`utxoAmount` for the *current* proof) or in `ExternalActionSwap`/`LifiExternalAction` prevents this, because both simply trust `swappedAmount` as computed from the raw balance diff without verifying it derives solely from the depositor's own declared `inputAmount`.

### Impact Explanation
- The original depositor whose refunded/unspent input tokens get stranded suffers a **permanent freeze of their own funds** for the dust portion (they were fully debited in Hinkal's ledger but never fully swapped or credited).
- A later, unrelated, unprivileged depositor who reuses the same input token and crafts an inflated `amountIn` in `externalActionMetadata` can mint themselves a UTXO containing value that came from another user's stranded/frozen funds — this is **direct theft of another depositor's in-flight/frozen funds**, matching the Critical category ("theft of shielded or in-flight user funds", "minting shielded value without backing"). This is repeatable any time dust accumulates for a given input token/router pair.

### Likelihood Explanation
- Requires the router to leave unconsumed input token behind at least once (a legitimate LI.FI multi-hop/partial-fill refund pattern, or a depositor's own imprecise calldata) — plausible and not attacker-exotic.
- The attacker needs no special privileges: they only need to be a normal depositor who can craft `externalActionMetadata` (already an explicit assumption in the threat model) and choose to reuse the same input token as a prior swap that left dust.
- Cost to the attacker is a normal swap transaction; gain is the value of any accumulated dust for that token, which persists indefinitely due to the standing `approveUnlimited` allowance.
- The main uncertainty is whether the real LI.FI router's calldata format lets the caller freely specify an `amountIn` decoupled from the tokens actually pre-approved/pre-funded for that specific call (i.e., whether a normal "swap" facet call can be pointed at a larger amount than intended). This is standard for most swap-router ABIs (amount is just a calldata parameter), so it is very likely feasible without relying on any router-side defect — the vulnerable behavior is that this repo's `LifiExternalAction`/`ExternalActionSwap` never constrains or verifies input-token consumption against `inputAmount`, which is squarely in-scope, in-repo code.

### Recommendation
In `LifiExternalAction.callRouter` (and generally `ExternalActionSwap`), snapshot the `inputToken` balance before the router call and require the balance decrease equals exactly `inputAmount` after the call (revert otherwise), or explicitly sweep/return any leftover input-token balance back into the swap's accounting (e.g., refund it to the depositor as part of `utxoSet`, or forward the difference to `msg.sender`/Hinkal so it can be reflected in `amountChanges`). Additionally, revoke or reset the `router` allowance to exactly `inputAmount` per call instead of leaving a standing `type(uint256).max` allowance, to prevent any future call from pulling more than the amount explicitly authorized for that specific swap.

### Proof of Concept
Foundry fork test plan:
1. Deploy `LifiExternalAction` with a mock router that, on `callRouter`'s first invocation, only pulls `Y < inputAmount` of `inputToken` via `transferFrom` and performs the swap for `Y`, leaving `inputAmount - Y` sitting in `LifiExternalAction`.
2. Assert `LifiExternalAction`'s `inputToken` balance is `inputAmount - Y` after transaction 1 (dust frozen), and that depositor 1's Hinkal-side UTXO output only reflects `Y`'s worth of `outputToken` (confirming Hinkal.sol's own equality check at contracts/Hinkal.sol lines 134-146 passes trivially despite the dust never being recovered).
3. Have an unrelated depositor 2 submit a second `transact` reusing the same `inputToken`, with `externalActionMetadata` encoding `amountIn = inputAmount2 + (inputAmount - Y)`, relying on the standing allowance from `approveUnlimited` (contracts/TransfererBase.sol lines 32-43) set during transaction 1.
4. Assert depositor 2's resulting `swappedAmount`/minted UTXO for `outputToken` exceeds what `inputAmount2` alone would produce by exactly the value derived from the stranded dust, and that `LifiExternalAction`'s `inputToken` balance returns to zero — demonstrating depositor 2 captured depositor 1's frozen funds with no corresponding debit anywhere in Hinkal's ledger.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
