### Title
Webhook `shop` (tenant) identity is trusted without HMAC coverage, enabling cross-tenant webhook confusion - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook delivery solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, `webhook-id`, and `api-version` values taken from HTTP headers to build the `WebhookMetadata` handed to the app's handler. Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is identical for every shop that has installed the app, and the signature never covers the `shop` header, any shop owner who has installed the app can capture one legitimate webhook delivered to their own store and replay it to the app's webhook endpoint with the `shop` header rewritten to a victim shop domain. The signature will still validate, and the app will process the event as if it belongs to the victim tenant.

### Finding Description
`Registry.process` performs exactly one authenticity check before dispatching to the app-supplied handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [5](#0-4) 

For `Webhooks::Request`, `to_signable_string` is defined as the raw body only:
```ruby
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are read from headers that are entirely outside the signed data:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [6](#0-5) 

The identity binding that the app actually needs to trust is: *"the `shop` value passed to the handler equals the shop that Shopify's servers generated this specific payload for."* The library instead only proves: *"the body bytes were signed with the app's `client_secret`."* Since the `client_secret` is shared by every shop installation of the app, and the `shop` header is not part of the signed bytes, these two are not equivalent — `hmac_valid(body, api_secret_key) == true` does **not** imply `shop_header == originating_shop`.

An unprivileged internet user who has simply installed the app on their own store (no special privileges, no access token, no leaked credentials) receives real webhook deliveries with valid HMACs computed over bodies that, for many topics, are either fully or partially predictable/replayable (e.g., re-deliverable test webhooks, or webhooks whose body content the attacker fully controls, such as `app/uninstalled`, `shop/redact`, or metafield-topic bodies the attacker can shape via their own store data). They can then POST the exact same `raw_body` + `hmac-sha256` header to the app's webhook route while substituting `x-shopify-shop-domain` for the victim's shop domain. `HmacValidator.validate` still succeeds because it only checks the body signature, and `Registry.process` forwards `shop: request.shop` (the attacker-supplied victim domain) to the handler.

### Impact Explanation
This breaks the tenant boundary the gem's webhook-processing feature is supposed to enforce: the app's business logic (session lookup, data mutation, GDPR/redaction actions, billing state changes, etc.) keyed off `WebhookMetadata#shop` can be triggered against a shop the attacker does not own, using a signature that was never generated for that shop. This is cross-tenant access — the impact category explicitly listed as Critical.

### Likelihood Explanation
Likelihood is constrained by needing at least one genuine webhook delivery to the attacker's own installation with a body the attacker can reuse or replay, and by the app's own handler logic determining what damage results from a shop-mismatched event. It requires no access token, no `api_secret_key`, and no privileged account — only ordinary participation as a shop merchant who installed the app, which any internet user can do for many public apps. The mechanism is deterministic once a suitable body/HMAC pair is obtained; no timing/race window is needed the way it was in the referenced Solidity report.

### Recommendation
- Include the `shop` (and ideally `topic`, `webhook_id`) values in the signable material used for `HmacValidator`, or otherwise cryptographically bind them to the signature, so verification proves the header values, not just the body bytes.
- Alternatively, require app code to independently confirm that the `shop` in `WebhookMetadata` corresponds to a shop with a currently valid, previously stored session/access token before acting on the payload, and document this requirement clearly since the current API surface (`Registry.process`) implies the value is already trustworthy.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimate webhook delivery, e.g. an `app/uninstalled` POST with body `raw_body` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, raw_body)`.
2. Attacker crafts a new HTTP request to the same app webhook endpoint with:
   - `x-shopify-topic: app/uninstalled`
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim.myshopify.com` (rewritten)
   - body: the identical `raw_body`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, raw_body)` and matches `H` — validation succeeds [7](#0-6) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)` [8](#0-7) , causing the app to act as though `victim.myshopify.com` sent this event, even though Shopify never generated or delivered this payload for that shop.
