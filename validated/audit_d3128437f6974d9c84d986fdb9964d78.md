This confirms the vulnerability. The `HmacValidator` only signs `to_signable_string`, and for webhooks that string is the raw body only — no header, including `shopify-shop-domain` and `shopify-topic`, is bound into the signature.

### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the raw-body HMAC via `Utils::HmacValidator.validate(request)` and then dispatches the handler using `request.shop` and `request.topic` taken directly from those unauthenticated headers [3](#0-2) . The identity binding that should hold is: `hmac == HMAC(secret, raw_body || shop || topic)`, but the actual check is `hmac == HMAC(secret, raw_body)` — `shop` and `topic` are verified against nothing.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` header using `OpenSSL.secure_compare` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight out of HTTP headers with no cryptographic binding to that signature [2](#0-1) .

`Registry.process` trusts these header-derived values completely once the body HMAC passes: it looks up the handler by `request.topic` and calls it with `shop: request.shop` [3](#0-2) . This is the same bug class as the Bond.sol report: a field that is *acted on* (here, `shop`/`topic`, used to route data and identify the tenant) is not covered by the cryptographic check that is supposed to guarantee authenticity (the HMAC). By contrast, the OAuth callback path correctly binds `shop` into the signed string via `AuthQuery#to_signable_string`, which includes `code`, `host`, `shop`, `state`, and `timestamp` [5](#0-4) , showing this gem's own convention is to bind identity fields into the signed payload — a convention the webhook path violates.

### Impact Explanation
In a multi-tenant app that serves many merchants from a single webhook endpoint, an attacker who has captured (or, more directly, who legitimately receives, since they can install the app on their own shop) one valid `(raw_body, hmac)` pair from Shopify can replay that exact body to the same endpoint while substituting the `shopify-shop-domain` and/or `shopify-topic` headers to arbitrary values. Because the signature check only covers `raw_body`, it will still pass `HmacValidator.validate`, and `Registry.process` will invoke the handler believing the payload originated from, and pertains to, a different shop/topic than it actually did. This crosses the tenant boundary the equality `hmac == HMAC(secret, raw_body || shop || topic)` was meant to enforce, since the actual check silently drops `shop`/`topic` from the equality.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint plus one previously-observed valid `(body, hmac)` pair, which any merchant who installs the app can trivially obtain from their own store's real webhook deliveries (e.g. by capturing their own `orders/create` webhook). No access to `api_secret_key` or any credential is required to perform the replay itself — only to have received one legitimate webhook, which is expected for any app user.

### Recommendation
Bind the `shop`, `topic` (and ideally `webhook_id`/`api_version`) headers into the signed material checked by `HmacValidator`, or otherwise independently verify that `request.shop` corresponds to the tenant that owns the currently active session/credentials before invoking the handler, rather than trusting `Registry.process`'s header-derived `request.shop`/`request.topic` implicitly once only the raw body passes HMAC validation.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers/receives a legitimate webhook, capturing the raw body `B` and its valid header `shopify-hmac-sha256: H` (computed by Shopify over `B` using the app's real secret).
2. Attacker POSTs to the same app webhook endpoint with body `B`, header `shopify-hmac-sha256: H` unchanged, but `shopify-shop-domain: victim.myshopify.com` and/or `shopify-topic: <different-topic>`.
3. `ShopifyAPI::Webhooks::Request#to_signable_string` returns `B` only [1](#0-0) ; `Utils::HmacValidator.validate` recomputes the HMAC over `B` and it matches `H`, so validation passes [6](#0-5) .
4. `Registry.process` proceeds to call the handler for the attacker-chosen topic with `shop: "victim.myshopify.com"` [3](#0-2) , even though that shop never sent this webhook and this data never came from Shopify for that tenant.
