### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain`, `topic`, and `webhook-id` HTTP headers straight through to the app's handler as trusted tenant-identifying metadata. Those headers are never part of the signed payload, so they can be modified freely without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all pulled from HTTP headers instead: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC using `verifiable_query.to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient authentication, then builds `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` header values and forwards it to the host app's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no further validation performed by the gem: [5](#0-4) 

This is a direct violation of the "field acted on but not covered by the HMAC" identity-binding pattern. For contrast, in the OAuth flow the gem correctly binds `shop` into the signed data: `AuthQuery#to_signable_string` includes `shop`, `code`, `host`, `state`, and `timestamp` in the HMAC-covered string: [6](#0-5) 

Because every shop installing a public/multi-tenant app authenticates its own genuine webhooks with the same app-level `Context.api_secret_key` (not a per-shop secret), any shop that is a legitimate merchant of the app can capture a valid `(body, hmac)` pair from a webhook it legitimately receives, and replay that same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because the signature check never touches the `shop` header, so `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain instead of the shop that actually produced/authorized the payload.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented/intended) to select which tenant's data record to create, update, or delete, an attacker who is merely a legitimate customer of the app (not privileged, no stolen credentials) can inject or corrupt data belonging to a different merchant's tenant by relabeling their own legitimately-signed webhook payload with a different shop domain. This crosses the tenant boundary that the HMAC is meant to enforce, matching the "cross-tenant access" Critical impact category defined in scope.

### Likelihood Explanation
Exploitation requires only network access to the app's webhook endpoint and possession of one legitimately delivered webhook for the attacker's own shop (any merchant who installs the app gets these automatically) — no access token, no `client_secret`, and no privileged account are needed. The only constraint is that the resulting body must make sense for the topic/handler being targeted, which is generally satisfiable since webhook topics like `app/uninstalled`, `customers/data_request`, `shop/update`, etc. carry attacker-influenced or predictable content.

### Recommendation
Bind the tenant-identifying header(s) into the signed material, or otherwise cryptographically or out-of-band verify that `shop-domain` corresponds to the shop whose secret produced the HMAC (e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or require the host app to independently confirm the shop exists/is installed and matches an expected value before trusting `WebhookMetadata#shop`). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used for tenant-sensitive operations without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimately signed webhook, e.g. for `customers/data_request`, with body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` using the app's shared `client_secret`).
2. Attacker replays the exact same request to the app's webhook endpoint, keeping `x-shopify-hmac-sha256: H` and body `B` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` reads the unchanged `H`; `HmacValidator.validate` recomputes HMAC over `B` (unchanged) and matches `H`, so validation passes: [7](#0-6) 
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the payload never originated from or was authorized for that shop.
5. If the app's handler uses `data.shop` to key its data store, victim-shop's records are affected by attacker-controlled content.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
