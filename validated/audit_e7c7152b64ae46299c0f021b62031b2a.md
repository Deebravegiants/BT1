### Title
Webhook `shop`, `topic`, `webhook-id` and `api-version` fields are not covered by the HMAC signature, letting an attacker relay a legitimately-received webhook to spoof a different shop's identity - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only the raw request body against the HMAC, then trusts the `shop`, `topic`, and `webhook_id` values taken directly from HTTP headers when it builds `WebhookMetadata` and dispatches to the app's handler. Since those header fields are excluded from the signed payload, any party who can obtain one genuine, validly-signed webhook (e.g., by installing the app on their own shop and receiving real webhook traffic) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The signature still validates, and the handler receives attacker-chosen shop attribution together with genuine-looking body content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All other Shopify-supplied identity fields — `shop`, `topic`, `webhook_id`, `api_version` — are read straight from HTTP headers and are never part of the signed string: [2](#0-1) 

`Registry.process` performs exactly one check — HMAC over the body — and then unconditionally forwards the unauthenticated header-derived `shop`/`topic`/`webhook_id` values into `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` confirm this: the comparison is solely between `verifiable_query.hmac` and a signature computed from `verifiable_query.to_signable_string` (the body), never incorporating headers: [4](#0-3) 

The documented guarantee is stronger than what the code actually provides — the docs claim `process` will "verify the request did indeed come from Shopify," without qualifying that only the body bytes are authenticated, not the shop/topic identity headers: [5](#0-4) 

This is the "field acted on but not covered by the HMAC" identity-binding break: the equality the app relies on is `verified_bytes == (body, shop, topic)`, but what is actually verified is only `verified_bytes == body`. An unprivileged actor who can obtain any single genuine `(body, hmac)` pair for a topic they legitimately receive (e.g., by installing the target app on their own store) can resubmit that identical body+HMAC to the webhook endpoint with a forged `shop-domain` header pointing at a victim shop, and the gem will report it as an authenticated Shopify webhook for that victim shop.

### Impact Explanation
This breaks the tenant-identity binding the webhook subsystem is supposed to enforce: a host application that keys any per-tenant logic (session lookups, data writes, entitlement checks) off `WebhookMetadata#shop` as sourced from this gem will act on behalf of a shop it never actually received an event for, using data whose authenticity was verified against different parameters (the attacker's own shop's data, not the header-declared shop). This falls in the cross-tenant-access category among the accepted impacts, since the gem attests authenticity for a `(shop, body)` combination it never actually verified as a unit.

### Likelihood Explanation
Likelihood is constrained by the fact that the attacker must first legitimately receive at least one real webhook (e.g., by installing the target app on a shop they control), which is achievable by any unprivileged internet user for public apps, and does not require the app's `client_secret` or an access token. Replaying that captured `(body, hmac)` pair with a substituted `shop-domain` header against the app's public webhook endpoint is a purely mechanical, no-credential operation.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC validation, or otherwise cryptographically bind them to the body before trusting them in `WebhookMetadata`. At minimum, update the documentation to state precisely that only the raw body is authenticated by `Registry.process`, and require host apps to independently corroborate the `shop` header (e.g., against a locally stored, oauth-authenticated shop record) before acting on the webhook payload.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers/receives a webhook for topic `X`; they capture the raw request body `B` and the `x-shopify-hmac-sha256` header value `H` (a valid HMAC of `B` under the app's secret).
2. Attacker POSTs to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `to_signable_string` returns `B` only. [1](#0-0) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` and finds it matches `H`, so validation passes. [4](#0-3) 
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using `request.shop == "victim.myshopify.com"` (taken from the forged header) and dispatches it to the app's handler as an authenticated event for the victim shop. [3](#0-2)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
