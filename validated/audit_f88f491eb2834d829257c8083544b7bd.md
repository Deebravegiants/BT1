### Title
Prefunded-token withdrawal fee estimate reports `amount: 0n` while a nonzero storage deposit is actually debited - ([File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts])

### Summary
In `estimateWithdrawalFee`, when `args.withdrawalParams.assetId` is in `this.bridgeConfig.prefundedNativeFeeTokens` and `totalAmountToQuote > 0n` (driven solely by a nonzero `storageDepositFee`), the quoting branch is skipped and `amount` is never incremented, so the function returns `feeEstimation.amount = 0n` even though `underlyingFees.storageDepositFee` is nonzero. Since `deriveOmniWithdrawIntentParams` derives the actual `storage_deposit` intent amount from `underlyingFees.storageDepositFee` (not from `feeEstimation.amount`), the SDK debits more from the user than the fee it reported.

### Finding Description
The broken equality: `feeEstimation.amount` (displayed to the caller) should equal the total value debited from the user beyond `withdrawalParams.amount` (i.e., `underlyingFees.relayerFee` converted amount + `underlyingFees.storageDepositFee`, as actually spent by the emitted intents).

Code path in `estimateWithdrawalFee` (`packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts:590-632`):
- `totalAmountToQuote` starts at `fee.native_token_fee` and is increased by `storageDepositFee` when `storageDepositFee > 0n` [1](#0-0) .
- `amount` is initialized to `0n`, and only incremented inside the `if` block that requires `totalAmountToQuote > 0n && !prefundedNativeFeeTokens.includes(assetId)` [2](#0-1) .
- For a prefunded token, this condition is false regardless of `totalAmountToQuote`, so `amount` remains `0n` while `underlyingFees.storageDepositFee` is still nonzero and returned in the `FeeEstimation` object [3](#0-2) .

`underlyingFees.storageDepositFee` is later read directly by `deriveOmniWithdrawIntentParams` (`omni-withdraw-params.ts`), which independently computes/emits a `storage_deposit` intent using that value, confirmed by matches for `storageDepositAmount` and `storage_deposit` in that file. This value is completely decoupled from `feeEstimation.amount`, which is the number surfaced to the caller/integrator as "the fee".

Attacker/trigger: any caller (integrator or end user) withdrawing a token that (a) is configured in `prefundedNativeFeeTokens` and (b) currently has `minStorageBalance > currentStorageBalance` for its NEP-141 storage on the intents contract — a state that arises naturally, not through malicious input, whenever the intents contract account has not yet registered enough storage for that token. No special crafted input is needed beyond choosing an assetId that is prefunded and has an outstanding storage deposit.

Existing guards do not catch this: there is no assertion anywhere in `estimateWithdrawalFee` or `createWithdrawalIntents` that `feeEstimation.amount` matches the sum of `underlyingFees` fields actually spent; `FeeExceedsAmountError` and `getUnderlyingFee` govern comparisons against `withdrawalParams.amount`, not the internal consistency between `amount` and `underlyingFees.storageDepositFee`.

### Impact Explanation
The user is charged a `storage_deposit` amount via an intent that is never reflected in the `feeEstimation.amount` shown to them or to the integrating application. This is an undisclosed debit — value leaves the user's balance beyond what was quoted as the fee, with no way for the caller to detect it from the returned `FeeEstimation`. This matches "fee error draining a portion of the amount" (Critical/High per the given severity mapping) since the fee reported (0) diverges from the fee actually charged.

### Likelihood Explanation
Requires: (1) an asset configured in `prefundedNativeFeeTokens`, and (2) that asset's storage balance on the intents-near contract currently below `minStorageBalance` (i.e., `storageDepositFee > 0n`). Both conditions are governed by bridge configuration and on-chain state, not attacker-controlled inputs, but they are realistic operational states (first-time storage registration for a token, or storage being reclaimed) that any ordinary user can trigger simply by withdrawing that token when the condition holds. No special privilege needed; repeatable each time the underfunded-storage condition recurs for that asset.

### Recommendation
In `estimateWithdrawalFee`, always add `storageDepositFee` (in its NEAR-denominated form or its quoted-token equivalent) into `amount` for prefunded tokens too, rather than skipping the entire block. E.g., restructure so quoting is skipped only for the relayer-fee/native portion when prefunded, but `storageDepositFee` is still accounted for in the returned `amount` (converting it via `getFeeQuote` against the withdrawal asset, or documenting/enforcing that prefunded tokens must also prefund storage so `storageDepositFee` is always `0n` for them, with an explicit assertion to catch violations).

### Proof of Concept
Vitest plan (mock only HTTP calls: `omniBridgeAPI.getFee`, storage-balance fetch used by `getCachedStorageDepositValue`, and `getFeeQuote`'s underlying solver-relay HTTP call):
1. Configure `bridgeConfig.prefundedNativeFeeTokens` to include a test assetId `T`.
2. Mock `omniBridgeAPI.getFee` to return `native_token_fee: 0n`.
3. Mock `getNearNep141MinStorageBalance`/`getNearNep141StorageBalance` (via the cached helper) so that `minStorageBalance - currentStorageBalance = storageDepositFee = 1_000_000n > 0n`.
4. Call `omniBridge.estimateWithdrawalFee({ withdrawalParams: { assetId: T, ... } })`.
5. Assert `feeEstimation.amount === 0n` and `feeEstimation.underlyingFees[RouteEnum.OmniBridge].storageDepositFee === 1_000_000n` — demonstrating the divergence.
6. Call `createWithdrawalIntents` (or directly `deriveOmniWithdrawIntentParams`) with the same params and the fee estimation from step 4; assert the emitted intents include a `storage_deposit` entry with amount `1_000_000n` (or equivalent), proving actual debited value (`0 + 1_000_000n`) exceeds `feeEstimation.amount` (`0n`), breaking the claimed equality.
