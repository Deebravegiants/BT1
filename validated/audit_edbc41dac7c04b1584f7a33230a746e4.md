### Title
Wrong destination-tx-hash reported for batched same-asset POA Bridge withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the completion status/destination-hash of a withdrawal by matching the POA Bridge API response only on `assetId`, not on the specific withdrawal index/amount/destination. When a caller batches multiple withdrawals of the *same* asset (e.g. two different USDC withdrawals to two different addresses in one NEAR transaction), the lookup can report the wrong (or duplicate) `transfer_tx_hash`/status for a given withdrawal index.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (lines 409-427) selects the first withdrawal entry whose `near_token_id`-derived assetId equals the caller-supplied `assetId`: [1](#0-0) 

This function is called from `describeWithdrawal` for every index of a batched withdrawal set, without disambiguating by `index`, `amount`, or `destinationAddress`: [2](#0-1) 

The equality that should hold is: *the status/tx-hash reported for withdrawal index N must correspond to the on-chain outcome of withdrawal index N specifically*. Instead, the code only proves "some withdrawal exists for this assetId in this NEAR tx," and returns that entry's `transfer_tx_hash`/status for every index sharing the same `assetId`. If the NEAR intent transaction batches two withdrawals of the same token (e.g., `nep141:usdt.tether-token.near` to address A with amount X, and the same token to address B with amount Y), `Array.prototype.find` will return the same (first-matching) entry for both calls to `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})`. The identical companion function and identical caveat exist in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`: [3](#0-2) 

The code's own comment acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported"), but nothing in `sdk.ts`/`processWithdrawal`/`waitForWithdrawalCompletion` blocks callers from constructing such a batch — the SDK's public API (`createWithdrawalIntents`, `signAndSendWithdrawalIntent`, `waitForWithdrawalCompletion`) accepts arrays of `WithdrawalParams` and there is no visible guard rejecting duplicate `assetId` entries in a batch before calling into `PoaBridge.describeWithdrawal`.

### Impact Explanation
If an integrator batches two withdrawals of the same POA-bridged asset in one NEAR transaction (e.g., sending funds to two different users/addresses), `describeWithdrawal` can report the **same destination tx hash and "completed" status for both withdrawal indices**, even though only one of the two on-chain transfers has actually landed. This breaks the equality "status/hash reported == actual on-chain outcome for that specific withdrawal," and matches the report's High-impact class: *"a status or hash misreport making an integrator credit or refund twice."* An integrator relying on `sdk.waitForWithdrawalCompletion`/`processWithdrawal` per-withdrawal results could mark both withdrawals as completed/credited based on one real completion, or associate the wrong recipient's transaction hash with the wrong withdrawal record for reconciliation/support purposes.

### Likelihood Explanation
This requires the integrator (not a malicious external attacker) to batch two or more withdrawals of the identical `assetId` via the POA route within a single call. This is plausible in normal batch-processing usage (e.g., paying out multiple users the same token) since the SDK's public interfaces accept batched `WithdrawalParams` arrays without rejecting duplicate assetIds for the POA route. The bug is deterministic once that precondition holds — no external cooperation or malicious behavior is needed, only ordinary usage of batching. Note: I could not fully confirm from available context whether `sdk.ts`'s public batch methods actively validate/reject duplicate-assetId batches before delegating to `PoaBridge.describeWithdrawal` (the relevant `sdk.ts` section could not be read in this session due to a tool error), so the exact reachability from the public `IntentsSDK` batch APIs is not 100% confirmed, though the bridge-level bug itself is clearly reachable via direct `Bridge` usage and is explicitly acknowledged as unhandled in the code's own comments.

### Recommendation
Disambiguate matching in `findMatchingWithdrawal` (both in `poa-bridge.ts` and `internal-utils/poaBridge/waitForWithdrawalCompletion.ts`) beyond `assetId` alone — e.g., additionally match on `amount` and `destinationAddress`, or track/consume matched entries so the same API withdrawal record cannot be attributed to two different local withdrawal indices. Until the POA API supports disambiguating multiple same-asset withdrawals per transaction, the SDK should explicitly reject (throw) batches containing duplicate `assetId` entries routed through the POA Bridge rather than silently risking a duplicate/misattributed status report.

### Proof of Concept
1. Caller submits one NEAR transaction containing two `ft_withdraw` intents for the same POA-bridged asset (`nep141:usdt.tether-token.near`): withdrawal index 0 to address A (amount 100), withdrawal index 1 to address B (amount 200).
2. POA Bridge API eventually returns `withdrawals: [{status:"COMPLETED", data:{near_token_id:"usdt.tether-token.near", transfer_tx_hash:"0xAAA", ...}}]` (only index-0's transfer has landed; index-1 is still pending on the POA side, or the array temporarily contains just one matching entry).
3. Calling `bridge.describeWithdrawal({..., index:0, withdrawalParams:{assetId:"nep141:usdt.tether-token.near", ...}})` and `bridge.describeWithdrawal({..., index:1, withdrawalParams:{assetId:"nep141:usdt.tether-token.near", ...}})` both invoke `findMatchingWithdrawal(withdrawals, "nep141:usdt.tether-token.near")`, which returns the **same** first-matching entry for both calls.
4. Both calls resolve to `{status:"completed", txHash:"0xAAA"}`, even though the transfer to address B never happened — an integrator polling per-index completion via `sdk.waitForWithdrawalCompletion` would incorrectly mark B's withdrawal as completed with A's tx hash.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
