## Title
Webhook HMAC validation does not bind the signed body to the `shop-domain` header, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` only returns the raw request body, while the shop-identifying header (`shop-domain`) is read separately and is never part of the signed content. `Registry.process` trusts `request.shop` to attribute the webhook payload to a tenant after validating only the body's HMAC, so the equality "shop the HMAC was computed over" == "shop the handler is told the data belongs to" does not hold.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, completely independent of the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it only proves that the *body* was signed by Shopify using the app's secret — it says nothing about which shop the body was signed for: [3](#0-2) 

`Registry.process` then uses this same `request` object to authorize dispatch and to build the tenant-scoped `WebhookMetadata` handed to the app's handler, taking `shop: request.shop` straight from the unauthenticated header: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-shop), any merchant that has installed the app can generate their own genuine, HMAC-valid webhook deliveries (e.g. by creating an order, customer, etc. in their own store) and capture the raw body + valid HMAC. That attacker-controlled (but validly-signed) body can then be replayed to the app's webhook endpoint with the `shop-domain` header swapped to an arbitrary victim shop domain that also installed the app. `HmacValidator.validate` still succeeds because it only checks the body signature, and `Registry.process` will hand the handler `WebhookMetadata.new(shop: "<victim-shop>", body: <attacker-controlled-body>, ...)`. This breaks the intended identity binding: shop authenticated by the HMAC ≠ shop the handler is told owns the data.

### Impact Explanation
This is a cross-tenant confusion vector: the gem's own webhook-processing API misattributes attacker-controlled payload data to another tenant (shop) whose webhook secret material was never involved in producing the signature the attacker replayed. Any host application that keys business logic (e.g., "for shop X, upsert this order/customer/GDPR record") off `WebhookMetadata#shop` as authenticated by `Registry.process` will act on forged, cross-tenant data, since the library represents the HMAC check as authenticating the whole webhook (topic/shop/body triple) when it only authenticates the body bytes.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate, unprivileged merchant of the same app (a normal, publicly obtainable relationship for any public/multi-tenant Shopify app) and the ability to send an arbitrary HTTP POST with a spoofed `X-Shopify-Shop-Domain` header to the app's webhook endpoint — no access token, `client_secret`, or privileged account is required, since the attacker only needs a webhook body they themselves validly triggered.

### Recommendation
Include the shop domain (and topic) in the signable string used for HMAC verification, or otherwise cryptographically bind `request.shop` to the same authenticated bytes that produced `request.hmac`, so that `Utils::HmacValidator.validate` cannot succeed for a body that was signed for a different shop than the one asserted in the `shop-domain` header.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) whose body they control (order note, line items, etc.).
2. Shopify delivers this webhook with header `X-Shopify-Hmac-Sha256: <valid hmac>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays the exact raw body and the exact `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com` (a shop that also installed the app).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the shared `api_secret_key`: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body, processing forged data as if it originated from the victim shop.

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
