### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the application's webhook handler are read directly from unauthenticated HTTP headers. `Registry.process` validates only that the body's HMAC matches, then dispatches the handler with header-derived, unsigned identity fields, breaking the binding between "the entity that produced a validly-signed body" and "the shop the handler believes the event came from."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never included in the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate`, and, if it passes, immediately builds a `WebhookMetadata` object from the header-derived, unverified `request.shop` / `request.topic` / `request.webhook_id` / `request.api_version` and dispatches it to the app's handler: [3](#0-2) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against the received `hmac`: [4](#0-3) 

The identity binding that should hold is:
`shop_attributed_to_handler == shop_that_shopify_actually_signed_this_body_for`

Because the HMAC only covers `raw_body` and not `shop-domain`/`topic`, this equality is not enforced by the gem. Any party in possession of one validly-signed `(raw_body, hmac)` pair — for example an attacker who owns their own store and receives genuine outbound webhooks from Shopify for it — can resend that same body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for an arbitrary victim shop domain and/or a different registered topic. `Registry.process` will accept it, because the HMAC check only validates the body bytes, and will invoke the handler believing the event legitimately originated from the victim shop / topic.

### Impact Explanation
This crosses the tenant boundary the gem is documented as enforcing (`WebhookMetadata#shop` and `#topic` are meant to identify which merchant/event triggered the handler; see `docs/usage/webhooks.md`). If a host application's handler uses `data.shop` to select which tenant's stored session/data to act on (a pattern the gem's own usage docs recommend), an attacker can cause the handler to execute business logic attributed to a shop they do not own and never authenticated as — a cross-tenant integrity violation. Depending on the handler (e.g. `app/uninstalled`, data-erasure, or order-processing handlers), this can result in unauthorized state changes scoped to another merchant's tenant, which the reporting rubric classifies as Critical (cross-tenant access).

### Likelihood Explanation
Exploitation requires an attacker to be in possession of at least one validly HMAC-signed `(raw_body, hmac)` pair for the app's `client_secret`. This is realistically obtainable by any developer/merchant who has installed the app on their own store and received a real webhook delivery (webhook bodies/HMACs are delivered to the app's public endpoint over the open internet and are not otherwise protected by additional binding of headers to the signature). No access to `api_secret_key`, access tokens, or privileged accounts is needed — only normal use of the app as an unprivileged merchant/attacker followed by a single crafted replay with modified headers.

### Recommendation
Bind the identity fields into the signed payload before verification, e.g. include `shop-domain`, `topic`, and `webhook_id` in the string that `HmacValidator` verifies (or independently verify these values against Shopify's response before trusting them), so that the HMAC check cannot pass when these header values have been altered from what Shopify actually signed for. At minimum, document that host applications must not trust `data.shop`/`data.topic` without additional verification, and consider validating requests via mTLS/IP allow-listing or Shopify's newer webhook verification mechanisms that cover header-derived identity.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers/receives a legitimate webhook, e.g. `orders/create`, capturing the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` that Shopify sent (validly computed with the app's real `client_secret` over `B`).
2. Attacker sends a new POST to the app's webhook endpoint with:
   - body: `B` (unchanged)
   - `x-shopify-hmac-sha256`: `H` (unchanged)
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (changed)
   - `x-shopify-topic`: unchanged or changed to any topic the app has registered a handler for
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and successfully matches `H` — [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)` — [6](#0-5) , causing app logic to run as if the event legitimately originated from the victim shop, despite the attacker never controlling or authenticating to that shop.
