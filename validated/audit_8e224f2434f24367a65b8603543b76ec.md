Confirmed: `Registry.process` uses `request.shop` (the `X-Shopify-Shop-Domain` header) as the tenant identifier passed to the app's `handler.handle(...)`, [1](#0-0)  while `HmacValidator.validate(request)` only checks `request.hmac` against `request.to_signable_string`, which is exactly `@raw_body` and does not include the `shop-domain` header. [2](#0-1) [3](#0-2)  This means `Shop(HMAC-verified) != Shop(acted-on)` — the shop-domain header is a field acted on but not covered by the HMAC signature, matching the M-05 bug class.

However, exploiting this requires the attacker to produce a request whose `raw_body` + `hmac-sha256` header pair validates against `Context.api_secret_key` — i.e., a genuine Shopify-signed webhook body (which the attacker can legitimately obtain for their own shop) replayed with a forged `shop-domain` header pointing at a victim shop. This is a real cross-tenant spoofing primitive purely within this gem's own webhook-processing code (`Webhooks::Registry.process` / `Webhooks::Request`), not dependent on the host app ignoring documented behavior — the gem itself derives the tenant identity from an unauthenticated header and hands it to the handler as trusted, so it satisfies the "field acted on but not covered by the HMAC" analog class.

### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `X-Shopify-Shop-Domain` header. `Registry.process` validates the HMAC over that signable string and, once valid, unconditionally trusts `request.shop` (read from the unauthenticated header) as the tenant identity passed to the app's webhook handler.

### Finding Description
`HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac` using a constant-time comparison. [4](#0-3)  For webhooks, `to_signable_string` is defined as `@raw_body` only [5](#0-4) , while `shop` is read separately from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the HMAC at all [6](#0-5) .

`Registry.process` verifies the HMAC, then immediately forwards `request.shop` into the handler's `WebhookMetadata` as the shop for which the event applies: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [1](#0-0) . There is no check anywhere in this gem that the `shop` header matches any value bound into the signed payload/HMAC.

This is precisely the reported bug class: an identity-relevant field (`shop`) is acted upon by trusted code, but that field is not part of what is cryptographically verified (the HMAC only binds the body bytes, not the shop header) — i.e. `HMAC-verified-bytes != identity-used-for-tenant-routing`.

### Impact Explanation
An attacker who possesses one genuinely Shopify-signed webhook body+HMAC pair (trivially obtainable by installing the app on any of their own — even a free development — store and capturing/replaying webhook deliveries for that store) can resend that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value (e.g., a victim merchant's shop domain). `Utils::HmacValidator.validate` will still pass because it only checks the raw body, and `Registry.process` will hand `WebhookMetadata` labeled with the victim's shop to the app's handler. Any app logic that trusts `shop` from `WebhookMetadata` to select tenant data (e.g., "delete this shop's data", "update this shop's subscription state", GDPR redact endpoints, uninstall handling) will act cross-tenant on behalf of the attacker's forged shop identity — a cross-tenant access/data-integrity issue satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic: obtaining one valid signed webhook (body+HMAC) requires only installing the target app on any Shopify store (including the attacker's own trial/dev store) or capturing one legitimate delivery — no `client_secret` or victim access token is needed. Replaying it against the app's public webhook HTTP endpoint with a modified `shop-domain` header is trivial for any unprivileged internet user, since HTTP headers are entirely attacker controlled in an unauthenticated POST.

### Recommendation
Bind the `shop` (and ideally `topic`/`api-version`) header values into the HMAC-verified signable string, or otherwise cryptographically tie the shop identity to the verified payload before it is trusted. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop-domain` header (and other identity-bearing headers used downstream) so that `HmacValidator.validate` fails if any of those headers are tampered with, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`/`host`/`state` into its signature. [7](#0-6) 

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; capture one webhook delivery: raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify using the app's real `client_secret`, which the attacker never needs to know).
2. Send a forged HTTP POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H, ...})` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only re-hashes `B`. [5](#0-4) 
4. `Registry.process(request)` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))`, delivering an attacker-controlled body under the victim shop's identity to the app's webhook handler. [8](#0-7)
