## Analysis

The Forta issue is a "missing zero-address validation on a privileged parameter" class of bug: a role that means well (not malicious) can configure a critical address parameter to `address(0)`, and because the token/transfer semantics revert on transfers to the zero address, a core protocol flow becomes permanently bricked for all downstream, unprivileged users.

Hyperbridge's `EvmHost` has the exact same structural gap. `updateHostParamsInternal` in [1](#0-0)  explicitly validates `hostManager`, `handler`, and `consensusClient` against `address(0)` (and against missing code/ERC165 support) to "prevent the host from getting bricked," and even validates that the fee token cannot be swapped away while a balance remains via `CannotChangeFeeToken`. However, there is **no check that the new `feeToken` itself is non-zero**. Nothing stops governance (via `HostManager.onAccept` → `updateHostParams`) or the initial `admin` (via `initialize`, which calls the same `updateHostParamsInternal`, see [2](#0-1) ) from setting `feeToken = address(0)`.

Once `feeToken()` returns `address(0)`, every fee-paying outbound dispatch path breaks. `dispatch(DispatchPost)` and `dispatch(DispatchGet)` call `IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee)` whenever a POST/GET fee is supplied without native token: [3](#0-2) [4](#0-3) . OpenZeppelin's `SafeERC20`/`Address.functionCall` reverts with "Address: call to non-contract" when the target has no code, so any unprivileged message dispatcher (any app/user calling `dispatch` with `post.fee > 0` or `get.fee > 0`) is permanently unable to submit fee-bearing cross-chain requests — mirroring exactly how the Forta slashing mechanism was permanently reverted once `_treasury` was zero.

### Title
Missing zero-address validation on `feeToken` in `EvmHost.updateHostParamsInternal` can permanently brick fee-based dispatch - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.updateHostParamsInternal` validates `hostManager`, `handler`, and `consensusClient` against `address(0)` to avoid bricking the host, but omits an equivalent check for `feeToken`. If `feeToken` is ever set to `address(0)` — during `initialize()` or via a cross-chain governance `updateHostParams` call — any subsequent fee-paying `dispatch()` call reverts, permanently denying message dispatch for every unprivileged caller of the host until governance issues a fix.

### Finding Description
`updateHostParamsInternal` performs multiple invariant checks "to prevent the host from getting bricked" [5](#0-4) , and separately guards against changing `feeToken` while funds remain in the old one [6](#0-5) . There is no equivalent guard rejecting `params.feeToken == address(0)`. This same unvalidated struct is applied both at one-shot `initialize()` [2](#0-1)  and via governance-triggered `updateHostParams` [7](#0-6) .

Once `feeToken` is `address(0)`, `dispatch(DispatchPost)` and `dispatch(DispatchGet)` unconditionally call `IERC20(feeToken()).safeTransferFrom(...)` for any fee-paying request that isn't funded via native-token swap [8](#0-7) [9](#0-8) . `safeTransferFrom` internally reverts when the target address has no contract code, which is always true for `address(0)`, so these calls revert unconditionally.

### Impact Explanation
This is a "route unable to deliver messages" condition: any unprivileged application or user attempting to dispatch a fee-bearing POST/GET request through this `EvmHost` deployment is blocked entirely — not merely the party who mis-set the parameter. Because `EvmHost` is a shared, chain-wide dispatch entrypoint used by all IsmpModules/relayers/apps on that chain, the blast radius is the entire chain's outbound message flow, not a single subject as in the Forta case, making this potentially more severe.

### Likelihood Explanation
The trigger is a single missing validation on a value that is otherwise routinely rotated (the code comments show the protocol anticipates changing `feeToken`, e.g. "before changing this parameter, that all funds have been drained from the previous feeToken" in `evm/rust/src/host_params.rs`). An operational or scripting mistake when constructing the `HostParams`/`EvmHostParamUpdate` payload (e.g., leaving `fee_token: None`/zero-initialized in a partial update, or an admin oversight during `initialize`) is sufficient — no malicious intent is required, matching the "accidental misconfiguration" likelihood profile of the original Forta finding.

### Recommendation
Add an explicit check in `updateHostParamsInternal` rejecting `params.feeToken == address(0)` (and, ideally, requiring it to be a contract), consistent with the existing checks on `hostManager`, `handler`, and `consensusClient`.

### Proof of Concept
1. Deploy `EvmHost` and call `initialize()` (or a subsequent governance `updateHostParams`) with `HostParams.feeToken = address(0)`; all other params pass existing validation (`hostManager`, `handler`, `consensusClient` non-zero, valid `hyperbridge` id, valid `stateMachines`, `unStakingPeriod >= 1 days`), so the call succeeds.
2. Any user calls `dispatch(DispatchPost{ fee: X > 0, ... })` without sending `msg.value`.
3. Execution reaches `IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee)` with `feeToken() == address(0)`.
4. The call reverts (`Address: call to non-contract`/equivalent SafeERC20 revert), so `dispatch` cannot complete — reproducible by any caller with `post.fee > 0`, for as long as `feeToken` remains `address(0)`.

```text
    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }

        // otherwise cannot process new cross-chain governance requests
        if (keccak256(params.hyperbridge) == keccak256(bytes(""))) revert InvalidHyperbridgeId();

        // otherwise cannot process new datagrams
        uint256 stateMachinesLen = params.stateMachines.length;
        if (stateMachinesLen == 0) revert InvalidStateMachinesLength();

        // otherwise cannot process new datagrams
        if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();

        address oldFeeToken = feeToken();
        if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
            uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
            if (balance != 0) revert CannotChangeFeeToken();
        }
```
