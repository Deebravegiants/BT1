### Title
Floor-division precision loss in `convert_to_balance` permanently burns bridged dust on every incoming HFT transfer - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `pallet-hyper-fungible-token` HFT bridge converts inbound ERC20-denominated amounts to the local asset's balance type via integer division that truncates the remainder rather than rounding or accounting for it. This is the same bug class as the reported `computeCvgExpected` precision-loss finding — an unrounded division on a value that determines how much value is credited to a user — except here the truncated remainder is simply discarded permanently rather than merely mis-pricing a bond.

### Finding Description
`convert_to_balance` scales an incoming `U256` ERC20 amount down to the local balance precision using plain integer division with no rounding, no remainder tracking, and no refund of the truncated dust: [1](#0-0) 

This function is called from `IsmpModule::on_accept` (minting/releasing tokens to a beneficiary on receipt of a cross-chain message) and from `IsmpModule::on_timeout` (refunding the original sender): [2](#0-1) [3](#0-2) 

Both call sites are on the unprivileged, permissionless delivery path of a relayed ISMP `PostRequest` — any relayer can trigger `on_accept`/`on_timeout` for a message that was dispatched by `HyperFungibleToken.sol`/`WrappedHyperFungibleToken.sol` on an EVM chain. The `erc_decimals` value is looked up per `(asset, chain)` from `Precisions` storage, and is enforced to be `>= local_decimals` (see `Error::ErcDecimalsBelowLocal`), meaning `erc_decimals - local_decimals` is always `>= 0` and the division always discards `value mod 10^(erc_decimals - local_decimals)` — up to `10^(erc_decimals - local_decimals) - 1` ERC20-denominated units — with no mechanism to credit, accumulate, or refund that remainder.

Contrast this with the opposite direction, `convert_to_erc20`, which only multiplies and therefore never loses precision: [4](#0-3) 

### Impact Explanation
On the EVM→Substrate leg of every `HyperFungibleToken` transfer (and refund-on-timeout), the fractional remainder below local-asset precision is silently dropped:
- For **native/escrow-model assets** (`native = true`), the EVM side burned/escrowed the full ERC20 amount, but the pallet transfers out of the pallet's custodial account only the floor-divided amount — the dust remainder stays trapped in the pallet account forever, unbacked and unaccounted for by any user balance (permanent, uncorrectable value freezing).
- For **non-native/mint-model assets** (`native = false`), the pallet mints strictly less than the value that was locked/burned on the source chain, so the recipient (or, on timeout, the original sender being refunded) permanently loses the truncated remainder.

Because this fires on the standard delivery path for every single transfer and timeout-refund, the effect is systematic rather than a one-off edge case, and there is no code path that ever recovers, sweeps, or credits the accumulated dust — it is a genuine, permanent loss of user funds proportional to the decimals gap between the EVM token and the local asset (up to `10^(erc_decimals - local_decimals) - 1` per transfer).

### Likelihood Explanation
Any user or relayer completing a normal cross-chain transfer or timeout refund triggers this path — no special conditions, privileges, or race are required. The precision loss occurs deterministically whenever `erc_decimals > local_decimals` for the registered `(asset, chain)` pair, which is a common configuration (e.g., an 18-decimal EVM ERC20 bridged to a asset with fewer local decimals).

### Recommendation
Preserve the remainder instead of discarding it: either (a) round using ceiling division on refund-relevant amounts combined with tracking of accumulated dust that is periodically swept/credited, or (b) require `erc_decimals == local_decimals` for any newly registered pair, or (c) accumulate the truncated remainder into a pallet-level ledger keyed by `(asset, chain)` that can be reconciled/withdrawn by governance so the value is not simply destroyed. At minimum, emit an event with the truncated amount so operators can monitor the drift and back it with an on-chain accounting entry rather than dropping it silently.

### Proof of Concept
1. Register an asset with `local_decimals = 6` and `erc_decimals = 18` for an EVM chain (allowed since `erc_decimals >= local_decimals`).
2. From `HyperFungibleToken.sol` on the EVM chain, send `amount = 1_000_000_000_000` wei (i.e., `10^12`, which is `< 10^(18-6) = 10^12`... use `amount = 999_999_999_999` to be strictly below one local unit).
3. On delivery, `convert_to_balance` computes `999_999_999_999 / 10^12 = 0` — the beneficiary is credited `0` local units while the full ERC20 amount was burned/locked on the EVM side, permanently destroying the transferred value.
4. Repeating with `amount = 1_999_999_999_999` yields the same credited balance as `amount = 1_000_000_000_000` (`1` local unit both times), demonstrating loss of the `999_999_999_999` remainder on every such transfer — directly analogous to the `cvgExpectedA`/`cvgExpectedB` equality demonstrated in the original report's PoC.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
