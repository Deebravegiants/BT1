### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant impersonation via header tampering - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The report's bug class — a value used for downstream trust decisions being computed from state that is not covered by the authenticity check — has a direct analog in `ShopifyAPI::Webhooks::Request`/`Registry`. The webhook HMAC only signs the raw request body, while the `shop` (tenant identifier) passed to the app's handler is taken from an unauthenticated header, breaking the binding `hmac_signed_bytes == bytes_the_handler_trusts_for_tenant_identity`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `#shop` (and `#topic`, `#webhook_id`, `#api_version`) are read straight from HTTP headers, entirely outside the signed material: [2](#0-1) 

`Registry.process` validates the HMAC over that same body-only signable string, then immediately trusts `request.shop` as the tenant identity forwarded to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no relation to the HMAC-verified bytes: [4](#0-3) 

Contrast this with `Oauth::AuthQuery`, where the analogous field (`shop`) IS included in `to_signable_string` alongside `code`, `host`, `state`, `timestamp` — showing the codebase's own OAuth path correctly binds `shop` into the signed payload: [5](#0-4) 

`HmacValidator.validate` simply recomputes the HMAC over whatever `to_signable_string` returns and compares it — it has no way to know the webhook `shop` header was excluded from signing: [6](#0-5) 

**The broken identity binding, as an equality:**
`bytes_verified_by_HMAC (raw_body only) != bytes_the_handler_uses_to_identify_the_tenant (raw_body + shop_header)`

### Impact Explanation
Any actor who can obtain one genuinely HMAC-signed webhook body for the app (e.g., because they run their own shop that installed the app, or because webhook bodies for common topics are largely predictable/replayable across shops using this HMAC-body-only scheme) can replay that body to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header. `Registry.process` will validate successfully because the signature only checks body bytes — it never checks that the header-derived shop matches anything cryptographically. The forged request is then delivered to the app's `WebhookHandler#handle` as `WebhookMetadata` claiming to be from a victim shop. If the host application's handler uses `data.shop` to select which tenant's records/session/access token to act on (the standard integration pattern shown in this library's own docs), this results in cross-tenant data corruption/disclosure — one merchant's webhook forging actions against another merchant's tenant.

### Likelihood Explanation
Likelihood is bounded by two factors that keep this at a real-but-moderate severity rather than trivial exploitation: (1) the attacker must possess at least one HMAC-valid `(body, hmac)` pair — practically achievable by an app-installing merchant replaying their own received webhooks, or observing bodies for topics with static/predictable payloads; (2) exploitability of the cross-tenant impact depends on the host app trusting `WebhookMetadata#shop` without independently cross-checking it against a stored, verified session/shop association — which is exactly the documented, expected usage pattern of this field (`handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))`). Given the header is never covered by HMAC by construction in this gem, exploitation only requires header manipulation on replay, no cryptographic secret is needed.

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable material that `HmacValidator` verifies for webhooks, or otherwise cryptographically bind them (e.g., re-deriving/validating `shop` against a value embedded in the signed body, or documenting/enforcing that `Registry.process` callers must independently verify `request.shop` against a known, authenticated session before trusting it). At minimum, update `Request#to_signable_string` to include the headers currently excluded from the HMAC check, mirroring how `Oauth::AuthQuery#to_signable_string` already binds `shop` into its signed string.

### Proof of Concept
1. App merchant A installs the app and receives (or can construct/predict) one legitimate webhook delivery: body `B` with header `x-shopify-shop-domain: shop-a.myshopify.com` and a valid `x-shopify-hmac-sha256` computed over `B` using the app's `api_secret_key` (unknown to the attacker, but the value is provided by Shopify to A's endpoint).
2. Attacker (merchant A) resends the exact same `(B, hmac)` pair to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: shop-victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`, unchanged) — validation succeeds: [7](#0-6) 
4. `handler.handle` is invoked with `WebhookMetadata.new(topic: request.topic, shop: "shop-victim.myshopify.com", body: ..., ...)`, and the host application processes the webhook as if it genuinely originated from `shop-victim`.
