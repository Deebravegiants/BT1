### Title
Unallowlisted route addresses let attacker-chosen pool code execute under the sender's auth tree and drain unrelated wallet tokens - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The swap aggregator executes venue hops against pool and token addresses taken verbatim from the caller-supplied `swap_xdr` payload, with no allowlist or code identity check. A malicious route can name an attacker-deployed contract as a hop "pool", and any `token.transfer(victim, attacker, amount)` that contract performs is recorded by the host as a child of the sender's `require_auth` entry. If the sender signs the simulation-produced authorization tree (the standard workflow), the rogue contract steals arbitrary tokens from the sender's wallet — funds the protocol never touched.

### Finding Description
CVE-2018-11805's class is "untrusted configuration interpreted as executable behavior": SpamAssassin `.cf` files could be configured to run system commands. The analog in XOXNO Lending is the swap route payload: `swap_xdr` is untrusted caller-supplied configuration that determines which contracts get invoked mid-transaction.

In `dispatch_hop` (`contracts/swap-aggregator/src/venues/mod.rs:23-40`), each `SwapHop` is dispatched to a venue adapter purely on the `venue` enum tag; the `hop.pool`, `hop.token_in`, and `hop.token_out` addresses come from the payload's `assets` registry. The adapters then `invoke_contract` on the payload-named pool (e.g. `contracts/swap-aggregator/src/venues/comet.rs:30-34`) — there is no allowlist of pools or tokens anywhere in the router (confirmed by `docs/reference/invariants.md` INV-STRAT-03 note and `docs/explanation/threat-model.md:154-165`, which states the router "keeps no allowlist" of payload-named addresses).

The only sender authorization is `sender.require_auth()` at the top of `execute_strategy`. Under Soroban recording mode, `simulateTransaction` attaches every auth-requiring child call — including a `transfer` the rogue pool makes *from the sender's address* — beneath the sender's root entry. The test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates exactly this: a `RogueHopPool` named by the route calls `token.transfer(alice, attacker, WALLET_BALANCE)`, simulation records it as a child of Alice's `swap_collateral`/`execute_strategy` auth entry (lines 194-227), and signing that tree executes the theft (lines 258-268).

The same exposure reaches controller strategies (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`) and direct `execute_strategy` calls, since the controller's `authorize_transfer_as_current` grant does not bound what route-named code does under the *account owner's* auth tree.

### Impact Explanation
Theft of user funds beyond the routed amount: the rogue pool can move any token the victim holds (the test drains an unrelated, never-listed wallet token of 77,770 units). Neither the payload's `min_out` nor the controller's measured-output and risk gates bound the loss, because the stolen transfer is not part of the swap's measured balance deltas. Impact class: theft of user funds, qualifying for Medium/High.

### Likelihood Explanation
Exploitation requires the victim to sign a poisoned authorization tree produced by simulation. Users who blindly sign simulated auth trees — the default wallet/SDK workflow — are exposed; a malicious frontend or route quote can inject the rogue hop. The threat model documents the mitigation ("a client must decode the route it signs"), but nothing in the contracts prevents it, and the reachable path is fully on-chain via a single unprivileged call. Medium likelihood.

### Recommendation
Enforce a governance-managed allowlist of venue pool addresses (and/or token addresses) in the swap aggregator, checked in `dispatch_hop` before any `invoke_contract` — mirroring the Blend-pool approval model used for `migrate_from_blend` (INV-STRAT-03). Alternatively, validate that each hop's pool address matches a registered adapter contract hash. This converts "untrusted route config names arbitrary code" into "route config selects among vetted venues".

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Alice supplies USDC and holds `WALLET_BALANCE` of an unrelated token.
2. Attacker deploys `RogueHopPool` with a `PLAN` naming `(alice, wallet_token, attacker, WALLET_BALANCE)` and crafts a route whose `hop_pool` is that contract.
3. Alice calls `swap_collateral` (or `execute_strategy`) with the poisoned `swap_xdr`; simulation records `wallet_token.transfer(alice → attacker, WALLET_BALANCE)` as a child of her auth entry.
4. Signing the simulated tree executes the swap normally (fair output received, risk gates pass) while her entire `wallet_token` balance moves to the attacker — asserted at lines 266-268.
