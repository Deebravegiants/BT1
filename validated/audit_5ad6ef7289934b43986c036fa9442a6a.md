### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken from HTTP headers that are never included in that HMAC computation. This breaks the intended binding `hmac == HMAC(secret, body + shop + topic + webhook_id)`; in reality `hmac == HMAC(secret, body)` only. An unprivileged internet user who can obtain any single valid `(body, hmac)` pair can resend it to the app's public webhook endpoint with an arbitrary `shop-domain`/`topic`/`webhook-id` header set and still pass validation.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are read straight from HTTP headers, which are attacker-controlled on any public webhook endpoint and are not part of the signed data: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (the raw body only) and `verifiable_query.hmac` (from the `hmac-sha256` header) — see `lib/shopify_api/utils/hmac_validator.rb` lines 26-31 and `lib/shopify_api/utils/verifiable_query.rb`. After that single check passes, the handler is invoked with the *unauthenticated* `shop` (and `topic`/`webhook_id`) values: [3](#0-2) 

Because the HMAC only ever covers `@raw_body`, an attacker does not need the app's secret to produce a valid signature for an arbitrary `shop`/`topic` combination — they only need to capture (or generate, e.g. by triggering an event on a shop they legitimately control) any one valid `(raw_body, hmac)` pair and then replay it to the same public endpoint with different `x-shopify-shop-domain` / `x-shopify-topic` / `x-shopify-webhook-id` headers. `Registry.process` will still accept it, since `HmacValidator.validate` never looks at those headers, and will hand the forged `shop` value to the app's webhook handler as `WebhookMetadata#shop`.

### Impact Explanation
This crosses a tenant boundary equality the library is supposed to enforce: "the shop the webhook is authenticated for" should equal "the shop the handler acts on," but here the acted-on `shop` is never bound to the HMAC. A host application that keys any per-shop side effect (updating shop records, disabling features, writing audit logs, revoking access, etc.) off `WebhookMetadata#shop`/`#topic` can be tricked into applying data or actions intended for one tenant onto a different tenant, using nothing but a replayed, validly-signed body captured from an unrelated legitimate delivery. This is a cross-tenant data/action confusion vulnerability reachable by any unauthenticated internet user who can POST to the app's public webhook URL.

### Likelihood Explanation
Webhook endpoints built with this gem are, by design, public and unauthenticated aside from the HMAC check — that's the entire point of `Webhooks::Registry.process`. Obtaining one valid `(body, hmac)` pair is trivial for an attacker who owns any development/test shop that installs the app (Shopify will deliver real signed webhooks to them), or who can otherwise observe a single webhook delivery. No access token, `client_secret`, or privileged credential is required to exploit this — only the ability to POST to the endpoint with attacker-chosen headers, which satisfies the "unprivileged internet user" bar.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` in the signable string used by `HmacValidator`, or otherwise cryptographically bind them to the signed payload (e.g., compute the HMAC over a canonical string containing body + these headers), so that any header tampering invalidates the signature. At minimum, document that host applications must not trust `WebhookMetadata#shop`/`#topic`/`#webhook_id` as authenticated identifiers derived from the HMAC.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook-eligible event (e.g., `orders/create`), causing Shopify to POST a body `B` with a valid `x-shopify-hmac-sha256: H` to the app's public webhook endpoint.
2. Attacker captures `(B, H)`.
3. Attacker POSTs the identical body `B` and header `x-shopify-hmac-sha256: H` to the same public endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only (`lib/shopify_api/webhooks/request.rb:35-38`) — it matches `H`, so validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), where `shop` is `"victim-shop.myshopify.com"` even though the body/content came from the attacker's own shop event — demonstrating the shop/topic values are not bound to the HMAC and can be spoofed cross-tenant.
