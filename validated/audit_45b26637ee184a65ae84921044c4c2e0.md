## Analysis

I found a status-misreport analog to the Optimism bug: **`findMatchingWithdrawal` in the PoA bridge integration reports the on-chain outcome of a withdrawal based on `assetId` alone, ignoring `amount`, `destinationAddress`, and `index`.** When a batch contains more than one withdrawal of the same asset, this breaks the equality "status reported == actual on-chain outcome for *this* withdrawal", exactly like the referenced bug where a stale/wrong state slot was used to answer "was this specific message already relayed?".

### Title
Same-asset batched PoA withdrawals are matched by `assetId` only, causing status/hash misreport that can make an integrator credit a withdrawal twice - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` resolves the status of a specific withdrawal (identified by `index` within a batch) by calling `findMatchingWithdrawal(withdrawals, assetId)`, which does `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)` — matching only on token identity, not on `amount`, `destinationAddress`, or ordering. [1](#0-0) [2](#0-1) 

The same weak-matching pattern also exists in `internal-utils`'s `waitForWithdrawalCompletion`, which is explicitly documented as not supporting "multiple withdrawals of the same token in a single transaction." [3](#0-2) 

### Finding Description
Batch withdrawals are indexed per bridge route by `createWithdrawalIdentifiers`, which assigns a sequential `index` per bridge but passes that index through only for bookkeeping — it is never used to disambiguate the actual API-returned withdrawal record. [4](#0-3) 

When `sdk.signAndSendWithdrawalIntent`/`waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` process a batch containing two or more withdrawals of the **same** `assetId` (e.g., two USDC withdrawals to two different destination addresses or amounts), each call to `describeWithdrawal({index: i, withdrawalParams: {assetId, amount, destinationAddress}})` performs `findMatchingWithdrawal(response.withdrawals, assetId)`, which always returns the **first** array element whose `near_token_id` matches — regardless of which index is being queried. The code comment confirms this is a known, accepted constraint rather than an incidental bug, but it still produces the following equality break:

`status reported for withdrawal[i]` ≠ `actual on-chain outcome of withdrawal[i]`

Both `describeWithdrawal({index:0, ...})` and `describeWithdrawal({index:1, ...})` for the same `assetId` will resolve to the same underlying PoA record and its `transfer_tx_hash`, even though they correspond to two independent on-chain transfers (different destinations/amounts). If withdrawal #1 has completed on-chain but withdrawal #2 has not (e.g., still pending, or failed and requires manual retry), polling for #2 can report `status: "completed"` with `#1`'s `transfer_tx_hash`.

### Impact Explanation
This falls into the "status or hash misreport making an integrator credit or refund twice" bucket. An integrator using `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` to gate downstream actions (e.g., releasing custody, marking a ledger entry paid, notifying a user their funds landed) could:
- Mark two logically distinct withdrawals as "completed" using the same destination tx hash, when only one actually settled — leading to a double credit/double payout acknowledgment on the integrator's side for funds that were only sent once.
- Conversely, report the wrong tx hash against the wrong withdrawal, breaking any downstream hash-based reconciliation (e.g., auditing, refund logic) and potentially causing a refund to be triggered against a withdrawal that actually succeeded.

### Likelihood Explanation
The likelihood is real but requires an unprivileged usage precondition: the caller (integrator, not the SDK) must submit a batch containing two-or-more withdrawals of the same underlying NEP-141 asset (any distinct destination/amount is enough) via `signAndSendWithdrawalIntent` batch mode. This is a supported, first-class SDK feature (batch withdrawals), so this precondition is easily reachable by any normal integrator use, not requiring any admin/relayer misbehavior.

### Recommendation
- Disambiguate `findMatchingWithdrawal` (both in `intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) using `amount` and `destinationAddress` in addition to `assetId`, consuming matched entries so the same PoA record cannot satisfy two different indices/queries in the same batch.
- If the POA API truly cannot disambiguate same-asset withdrawals in one transaction (as the code comments claim), explicitly reject/flag batches containing duplicate `assetId` withdrawals routed through PoA rather than silently returning a possibly-wrong match.

### Proof of Concept
1. Submit `signAndSendWithdrawalIntent` with two withdrawals sharing the same `assetId` (e.g., `nep141:usdc.token.near`) but different `destinationAddress`/`amount`.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to both under the PoA route. [5](#0-4) 
3. Suppose only withdrawal #0 settles on the PoA bridge (COMPLETED with `transfer_tx_hash: "0xA"`), while #1 is still PENDING or REFUNDED.
4. Both `describeWithdrawal({index:0, assetId, ...})` and `describeWithdrawal({index:1, assetId, ...})` call `findMatchingWithdrawal(withdrawals, assetId)`, which returns the same first matching record for both calls. [6](#0-5) 
5. The watcher for withdrawal #1 resolves with `{status:"completed", txHash:"0xA"}` even though withdrawal #1 never actually settled — an incorrect status/hash is reported for a withdrawal that did not occur, which an integrator could use to credit the user twice.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
