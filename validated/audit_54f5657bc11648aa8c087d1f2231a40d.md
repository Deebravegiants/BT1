### Title
`dispatchIncoming`/`dispatchTimeOut` GET-response and timeout handling can be permanently blocked by a paused/blacklisted fee token - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(GetResponse, ...)`, `EvmHost.dispatchTimeOut(GetRequestTimeout, ...)` and `EvmHost.dispatchTimeOut(PostRequestTimeout, ...)` each perform the application callback (`onGetResponse`/`onGetTimeout`/`onPostRequestTimeout`) and, if it succeeds, unconditionally attempt an `IERC20(feeToken()).safeTransfer(...)` to refund or reward the relayer/sender in the same transaction. Since `feeToken()` is expected to be a stablecoin (per the docs in `IDispatcher.sol`), and many stablecoins (e.g. USDC, USDT) implement pause/blacklist mechanisms that block transfers to or from specific addresses, a paused token or a blacklisted relayer/sender address will cause the `safeTransfer` call to revert — reverting the entire transaction, including the otherwise-successful delivery of the underlying message.

The same pattern is used in `dispatchTimeOut(PostRequestTimeout, ...)`: [3](#0-2) 

Unlike `dispatchIncoming(PostRequest, ...)`, which returns early on a failed `onAccept` call (mimicking a "retry" pattern) and does not have the fee refund gate the whole call, the GET-response and both timeout paths execute a `safeTransfer` *after* the delivery callback succeeds, in the same external call guarded by `restrict(_hostParams.handler)`. Because `IERC20.safeTransfer` reverts on failure (`SafeERC20`), if:
- the `feeToken()` contract is globally paused (e.g. via an external pause switch like WBGL/WBTC in the referenced report, or USDC's/USDT's blacklist), or
- the specific recipient address (`relayer` or `meta.sender`) is blacklisted by the feeToken,

then the entire external call reverts. Since Solidity reverts unwind all state changes from the call, the already-successful application-level delivery (`onGetResponse`, `onGetTimeout`, `onPostRequestTimeout` state mutations) is also rolled back. There is no code path in these three functions that separates "delivery succeeded" from "fee transfer succeeded" — they are atomically coupled.

This directly parallels the referenced bug class: an external token's pause/blacklist mechanism, entirely outside the protocol's control, can block a core dispatcher function indefinitely, and once the host's admin capability is revoked/renounced or the feeToken cannot be swapped, there is no way to bypass the block. `IDispatcher.feeToken()` is described as returning "the ERC20 contract address for fees" which will "typically be in stablecoins" — a class of tokens well-known for pause/blacklist mechanisms. [4](#0-3) 

### Impact Explanation
If the configured `feeToken()` is a pausable or blacklistable stablecoin and either becomes paused, or the specific relayer/sender address that is due a fee transfer becomes blacklisted, then:
- Legitimate GET responses can never be finalized via `dispatchIncoming(GetResponse, ...)` — the commitment can never be cleared/handled since the transaction always reverts at the fee-payment step, permanently blocking that response's delivery.
- GET and POST timeouts can never be finalized via `dispatchTimeOut(...)` — the sender can never receive their timeout refund, and the corresponding `onGetTimeout`/`onPostRequestTimeout` callback effects (e.g., unlocking escrowed funds in downstream apps) can never be committed, because the whole transaction reverts every time it's attempted.
- This causes a permanent freezing of funds/state for the specific request/response and blocks delivery of that message route, matching "a route unable to deliver messages" and "permanent freezing of funds" impact categories, since neither the relayer nor the affected app ever receives a determinate outcome for that commitment.

Since `_hostParams.handler` is the only allowed caller and no admin path exists in these functions to skip or reroute the fee transfer, once such a block occurs it cannot be resolved except by changing the fee token or unblocklisting the specific address — actions that require external, off-protocol cooperation and may become impossible if governance is renounced (as anticipated per the referenced report).

### Likelihood Explanation
Likelihood is moderate to high in the long run: fee tokens used for cross-chain messaging protocols are typically established stablecoins (USDC, USDT) that have documented blacklist functionality used regularly by their issuers for compliance reasons (e.g., OFAC sanctions, exploit recovery). Any relayer or requester address that becomes sanctioned/blacklisted — which has happened multiple times historically for USDC/USDT — would trigger this condition without requiring any malicious action within Hyperbridge itself. The relayer is a permissionless role (`IApp.onGetResponse` accepts `IncomingGetResponse(response, relayer)`), so any address can act as a relayer and could theoretically already be blacklisted, or fall onto a blacklist later.

### Recommendation
Decouple fee transfers from the delivery/timeout state transitions so a reverting `safeTransfer` cannot roll back an otherwise successful callback:
- Wrap the `safeTransfer` calls in `dispatchIncoming(GetResponse, ...)` and both `dispatchTimeOut` functions in a try/catch (or a low-level `call`) so a failing fee transfer does not revert the whole transaction.
- On transfer failure, credit the fee to an internal, pull-based ledger (e.g., a mapping from address to claimable fee balance) that the relayer/sender can withdraw later once the token issue is resolved, rather than pushing the transfer inline.
- Apply the same non-blocking pattern already used for the delivery callback (`if (!success) { ...; return; }`) to the fee-payment step.

### Proof of Concept
1. Configure `EvmHost` with `feeToken()` pointing to a stablecoin that supports address blacklisting (e.g., USDC).
2. A user dispatches a GET request with a non-zero fee via `IDispatcher.dispatch(DispatchGet)`, recorded in `_requestCommitments[commitment]`.
3. A relayer submits the state proof for the GET response; `HandlerV2` calls `EvmHost.dispatchIncoming(GetResponse, relayer)`.
4. Before this call is mined (or afterward for retries), the feeToken issuer blacklists `relayer`'s address (e.g., due to a sanctions list update, unrelated to Hyperbridge).
5. `dispatchIncoming` executes `onGetResponse` successfully, then calls `IERC20(feeToken()).safeTransfer(relayer, fee)`, which reverts because `relayer` is blacklisted by the token contract.
6. The entire transaction reverts; `_responseReceipts[commitment]` is never set and the app-level `onGetResponse` effects are rolled back.
7. Any relayer retries `dispatchIncoming` for the same response — every attempt reverts identically because the fee must still go to the same blacklisted `relayer` address recorded in the call, or (in the case of `dispatchTimeOut`) to the same `meta.sender`, permanently blocking finalization of that specific request/response commitment.

    /**
     * @dev Dispatch an incoming GET response to source module
     * @param response - get response
     */
    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
