## Title
IntentGatewayV2 (Tron variant) escrow accounting is broken for fee-on-transfer/deflationary ERC-20 tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron build of `IntentGatewayV2.placeOrder` credits the internal escrow ledger with the *nominal* (requested/fee-reduced) token amount instead of the amount the contract actually received via `safeTransferFrom`. For any fee-on-transfer or deflationary ERC-20 accepted as an order input, this causes the on-chain escrow accounting to be overstated relative to the gateway's real token balance, mirroring exactly the reported "Vault doesn't handle fee-on-transfer/deflationary collaterals" bug class.

### Finding Description
In the non-predispatch branch of `placeOrder`, the contract does: [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
```

The token transfer is performed with `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` but the actual balance delta on the gateway is never measured; `_orders[commitment][token]` is unconditionally incremented by `reducedInputs[i].amount`, which is derived purely from the user-supplied `order.inputs[i].amount` minus a protocol-fee percentage — not from what the contract actually holds. If `token` charges a transfer fee (deflationary/fee-on-transfer token), the gateway receives less than `order.inputs[i].amount`, yet records the full (fee-reduced-only) amount as escrowed collateral for that commitment.

This is a regression relative to the fixed logic present in the mainline EVM contract, which explicitly measures balance-before/after to compute the actual received amount before crediting escrow or computing the commitment hash: [2](#0-1) 

The Tron predispatch branch also correctly uses `IERC20(token).balanceOf(dispatcher)` to measure actual balance before crediting escrow: [3](#0-2) 

but the direct (non-predispatch) transfer path — the common/default path used by `placeOrder` — skips this check entirely.

### Impact Explanation
`_orders[commitment][token]` is the ledger that `fillOrder`/`onAccept` (redeem escrow) rely on to release funds to solvers/fillers. Because this value is inflated beyond the gateway's actual token balance for fee-on-transfer inputs, the protocol becomes under-collateralized: the sum of all outstanding escrow claims can exceed the gateway's real token holdings. This leads to insufficient balance on later legitimate redemptions/fills (for this or other orders sharing the same token), i.e., permanent freezing of funds / broken accounting and potential inability to deliver on committed escrow obligations — a fund-safety issue reachable by any unprivileged user simply by placing an order with a fee-on-transfer token as input.

### Likelihood Explanation
Reachable directly by any external user calling `placeOrder` with an `_input.token` address that is a fee-on-transfer/deflationary ERC-20 and no `predispatch` set (the common path). No special privileges, governance, or admin actions are required — only that such a token is accepted as a valid input asset by the gateway (the contract does not restrict inputs to a fixed allowlist of non-deflationary tokens).

### Recommendation
In the non-predispatch else-branch of `placeOrder` (mirroring the fix already applied in `evm/src/apps/IntentGatewayV2.sol`), measure the gateway's token balance before and after `safeTransferFrom` and use the actual delta (rather than the nominal `order.inputs[i].amount`) both for computing `reducedInputs`/the commitment hash and for crediting `_orders[commitment][token]`, e.g.:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```
then recompute `reducedInputs`/commitment from the actual received amounts, consistent with the mainline EVM implementation and its regression tests (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol`, `testPlaceOrder_FeeOnTransferToken_*`).

### Proof of Concept
1. Deploy a fee-on-transfer ERC-20 `FOT` (e.g., 1% fee on transfer) and have the gateway accept it as a valid input token.
2. User approves the Tron `IntentGatewayV2` for `1000 FOT` and calls `placeOrder` with `order.inputs = [{token: FOT, amount: 1000}]`, no `predispatch`.
3. `safeTransferFrom` moves `1000 FOT` from user; due to the 1% fee, the gateway's actual balance only increases by `990 FOT`.
4. `_orders[commitment][FOT]` is nonetheless credited with `reducedInputs[0].amount` (990 if no protocol fee, else `1000 - protocolFee`, still not equal to the real `990` received minus any effects) — in general terms, the escrow value is derived from `order.inputs[i].amount` (1000), not the actual `IERC20(FOT).balanceOf(gateway)` delta.
5. When a solver later calls `fillOrder`/the order is redeemed, the escrow ledger claims more `FOT` than the gateway actually holds, causing insufficient-balance failures for redemption of this or other orders drawing from the same token pool. [4](#0-3)
