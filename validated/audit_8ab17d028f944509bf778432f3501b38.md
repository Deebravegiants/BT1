### Title
POA Bridge withdrawal status/tx-hash matched only by `assetId`, causing status misreport for batch withdrawals of the same token - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
When multiple withdrawals of the **same** `assetId` are included in one batch (e.g. two USDT withdrawals to two different destination addresses signed and published in the same intent), `PoaBridge.describeWithdrawal()` and the underlying `findMatchingWithdrawal()` helper select the matching withdrawal record by `assetId` alone, ignoring `index` and `destinationAddress`. This causes the SDK to report the transfer status/destination-tx-hash of the wrong withdrawal entry for a given `WithdrawalIdentifier`.

### Finding Description
`PoaBridge.describeWithdrawal()` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which returns the first withdrawal whose `near_token_id`/`defuse_asset_identifier` matches `assetId`: [1](#0-0) 

This matching key deliberately omits `index`, as confirmed by the code comment ("Response list is unsorted, so we match by assetId instead of index") and the accompanying test that explicitly asserts this behavior — `describeWithdrawal` is called with `index: 0` for a BTC withdrawal but succeeds only because the mock returns a single BTC entry: [2](#0-1) 

The equivalent helper in `internal-utils`, used by `waitForWithdrawalCompletion`, has the exact same limitation and documents it explicitly: [3](#0-2) 

The SDK's public API supports batch withdrawals with multiple `WithdrawalParams` entries of the same `assetId` to *different* `destinationAddress` values (see `README.md` batch example and `sdk.ts` `createWithdrawalIdentifier`/`waitForWithdrawalCompletion` flows), and nothing in `sdk.ts` rejects or de-duplicates same-asset batch entries before dispatching to `PoaBridge`. Consequently, when a batch contains two withdrawals of the same token, `describeWithdrawal`/`waitForWithdrawalCompletion` can return the **status and `txHash` belonging to the other withdrawal** — i.e., the on-chain outcome reported to the caller is not the actual outcome for the requested `WithdrawalIdentifier`/`destinationAddress`.

This breaks the required equality: *status/txHash reported == actual on-chain outcome for that specific withdrawal*.

### Impact Explanation
An integrator or the SDK's `waitForWithdrawalCompletion`/`processWithdrawal` orchestration relies on the returned `{status, txHash}` to decide whether a specific withdrawal (to a specific destination address) has completed. If withdrawal A (to address X) is still pending while withdrawal B (to address Y, same token) has completed, the SDK can report withdrawal A as "completed" with B's `txHash`. An integrator using this status to credit/release funds or mark a specific withdrawal complete could act on a false completion signal for the wrong destination, potentially crediting or reporting completion twice for withdrawals that have not actually settled to the intended address — matching the "status or hash misreport making an integrator credit or refund twice" High-impact class.

### Likelihood Explanation
This requires only a normal user/integrator action already supported by the public API: submitting a batch withdrawal (`sdk.processWithdrawal`/`sdk.signAndSendWithdrawalIntent` with an array of `withdrawalParams`) containing two or more entries with the same POA-bridge `assetId` but different destination addresses. No malicious relayer, bridge operator, or admin behavior is needed — it is a straightforward logic gap reachable by ordinary batch usage, and the code/tests explicitly acknowledge that only single-withdrawal-per-asset batches are correctly supported.

### Recommendation
Match withdrawal status records using `index` in combination with `destinationAddress` (and `destinationMemo` where applicable), not only `assetId`. If the POA Bridge API cannot disambiguate multiple same-asset withdrawals server-side, either: (1) sort both the API response and local `withdrawalParams` by amount/address and pair them positionally as hinted in the existing code comment, or (2) reject/flag batches containing duplicate `assetId` entries at `sdk.ts` validation time until the bridge API supports proper disambiguation, so the SDK never silently reports a misattributed status.

### Proof of Concept
1. Build a batch withdrawal with two `withdrawalParams`, both `assetId: "nep141:usdt.tether-token.near"`, `destinationAddress` A and B respectively, and submit via `sdk.signAndSendWithdrawalIntent`.
2. Suppose the POA bridge processes B's withdrawal (COMPLETED, `transfer_tx_hash: "0xB"`) while A is still `PENDING`.
3. Call `sdk.waitForWithdrawalCompletion` (or `bridge.describeWithdrawal`) for the identifier corresponding to A (`index: 0`).
4. `findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (and the internal-utils equivalent) matches purely on `assetId`, so it returns B's completed record — the caller receives `{status: "completed", txHash: "0xB"}` for withdrawal A, even though A has not settled on-chain to address A.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
