The critical determinism point here is that during replay, `Bank::load_addresses_from_ref` and `Accounts::load_lookup_table_addresses_into` resolve ALT addresses against `self.ancestors` — the accounts state of the specific Bank being replayed at a specific slot on a specific fork [1](#0-0) , and `current_slot = ancestors.max_slot()` is fixed by the bank/slot being replayed, not by wall-clock timing [2](#0-1) .

### Why this is not exploitable

For a given slot in a given fork, every honest validator constructs the Bank by replaying the exact same sequence of transactions from slot 0 (or a snapshot) through all ancestor slots in the exact same order, since transaction order within a block is fixed by the block producer and encoded in the ledger/shreds. This means:

1. **The account state an ALT resolves against is derived, not observed.** Any mutation of the ALT account (lamports drained, owner reassigned) must itself happen via a transaction included in some ancestor slot. That mutating transaction is part of the replayed block content, so every honest validator that replays the same chain of blocks will apply that exact same mutation at the exact same point in the same slot, before executing the transaction in question [3](#0-2) .

2. **There is no "leader's resolution slot" vs "validator's resolution slot" divergence for the same block.** Both the leader (during banking-stage execution) and the replaying validators (during replay) resolve the ALT lookup against the bank being built for that exact slot with the exact same ancestor set — `ancestors.max_slot()` is the working bank's slot, not some independently-observed wall-clock state [4](#0-3) . The banking stage's speculative resolution (in `receive_and_buffer.rs`/`translate_to_runtime_view`) is explicitly re-validated: `resanitize_transaction_minimally` re-runs `load_addresses_from_ref` against the actual bank if the ALT invalidation slot could have passed, guarding exactly against ALT state changing between initial resolution and final inclusion [5](#0-4) .

3. **Committed execution results are derived from the final resolution done against the transaction-processing bank at inclusion time**, not from any earlier speculative resolution done by banking stage workers. So even if a leader resolves ALT addresses early (banking stage) then the ALT account changes before the transaction is actually processed into the block, the final resolution used for the committed transaction is the one done at actual processing time against the working bank, and this is what gets replayed identically by all validators, because it's this deterministic sequence of operations (not the wall-clock state) that is being replayed.

4. **AccountNotFound / InvalidAccountOwner errors are also deterministic outcomes**, since they only depend on the account state at that point in the deterministically-replayed slot sequence, which is identical across honest nodes for the same fork.

The "differential test" proof idea proposed in the question — replaying the same slot on two `Bank` instances "with different ancestor/root timing for the ALT account" — is not something an unprivileged attacker can induce. Ancestor sets and root timing are internal validator bookkeeping determined by the consensus/fork-choice and snapshotting logic, not by attacker-supplied transaction content, and they do not vary between honest validators replaying the identical block sequence for a given slot. An attacker cannot control when a validator roots or which ancestors are attached to a bank at replay time in a way that changes the deterministic result of `load_lookup_table_addresses_into` for the same committed block.
