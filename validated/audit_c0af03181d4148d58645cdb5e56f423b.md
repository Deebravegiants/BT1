### Title
`findMatchingWithdrawal` misattributes status/txHash for batches with duplicate assetId - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves each `WithdrawalIdentifier` to a withdrawal record solely by matching `nep141:<near_token_id> === assetId`, ignoring `index`, `destinationAddress`, and `amount`. When a NEAR intents batch contains two or more POA withdrawals of the same token (same `assetId`) to different destinations, both `WithdrawalIdentifier`s deterministically resolve to the *same* array entry returned by `findMatchingWithdrawal`, so one destination's completion status/txHash is reported for the other's withdrawal.

### Finding Description
The broken equality is: `describeWithdrawal(wid_i).txHash` should equal the `transfer_tx_hash` of the withdrawal whose `destinationAddress`/`amount` match `wid_i.withdrawalParams`, for every `i` in a batch.

The code path:
- `IntentsSDK.createWithdrawalCompletionPromises` (`packages/intents-sdk/src/sdk.ts:557-608`) calls `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`), which builds one `WithdrawalIdentifier` per `WithdrawalParams` entry in the batch, with only a per-bridge-route `index` counter and no de-duplication or rejection of repeated `assetId` values within the same route/tx.
- Each identifier is then polled independently via `watchWithdrawal` → `bridge.describeWithdrawal` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:20-78`, `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`).
- `describeWithdrawal` calls `getWithdrawalStatusWithRetry` (which retries `Withdrawals not found` for up to `NOT_FOUND_RETRY_TIMEOUT_MS` = 3s and then returns `{ withdrawals: [] }`, yielding `pending` — matching the question's premise) and then `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` (`poa-bridge.ts:418-427`), which is a plain `Array.prototype.find` keyed only by `nep141:${w.data.near_token_id} === assetId`.
- The function's own comment admits the limitation: *"Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported."* (`poa-bridge.ts:409-417`, duplicated in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts:135-153`).

Root cause: nothing in `supports()`, `validateWithdrawal()`, `createWithdrawalIdentifier()`, or `createWithdrawalIdentifiers()` rejects or de-duplicates batches containing repeated `assetId` for the POA route; the API contract is silently violated instead of erroring. For two withdrawals with the same `assetId` but different `destinationAddress`, both `describeWithdrawal` calls query the exact same `withdrawal_status` HTTP response (keyed by `withdrawal_hash: args.tx.hash`, identical for both) and both invoke `.find()` with the identical predicate, so both return the *same* array entry (whichever appears first in the unsorted `withdrawals` list) — not each other's correct entry, but literally the identical status/`transfer_tx_hash` object for both `WithdrawalIdentifier`s regardless of which one truly corresponds to which destination.

Existing guards do not prevent this: `validateWithdrawal` only checks per-item destination address validity/min-amount, not batch-level uniqueness; `supports()` only checks token-factory prefix; there is no `matchesRequest`-style check by destination/amount in `findMatchingWithdrawal`, contrary to the invariant "each WithdrawalIdentifier resolves to the withdrawal with the same destination address and amount."

### Impact Explanation
Two POA withdrawals in one batch that share `assetId` will both be reported with the same `status`/`txHash` by `watchWithdrawal`. If an integrator relies on `IntentsSDK.waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` per-identifier results to credit a user's account for a specific destination once its withdrawal completes, this can cause: (a) crediting/confirming a destination that has not actually received funds yet (its identifier reports the other's `completed` status and `txHash`), or (b) reporting `pending`/`failed` incorrectly for a withdrawal that already completed. This matches the "status or hash misreport making an integrator credit or refund twice" High-severity category, since the same tx hash/completion state can be attributed to two different payouts.

### Likelihood Explanation
Preconditions: the batch must contain ≥2 POA-bridge withdrawals for the same NEP-141 token (same `assetId`) within the same NEAR intents transaction, submitted by any ordinary user or forwarded to the SDK by an integrator (attacker fully controls batch composition, including duplicate `assetId`s, per the caller-controlled `WithdrawalParams[]`). No special privileges, timing, or race conditions are needed beyond composing an intents batch — this is deterministic, not probabilistic (`Array.prototype.find` always returns the same element for both identical predicates given a fixed response array), and repeatable on every such batch.

### Recommendation
In `findMatchingWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`), match on additional discriminating fields (`destinationAddress`, normalized `amount`, and/or `destinationMemo`) in addition to `assetId`, and throw/return an explicit unsupported-batch error (instead of silently misattributing) when multiple candidates remain ambiguous. Alternatively, reject batches with duplicate `assetId` for the POA route at `createWithdrawalIdentifiers`/`validateWithdrawal` time until the POA API supports disambiguation, so integrators fail fast rather than receive a wrong `completed` status.

### Proof of Concept

```ts
// packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts (new case)
it("misattributes status when batch has duplicate assetId withdrawals", async () => {
  vi.mocked(poaBridge.httpClient.getWithdrawalStatus).mockResolvedValue({
    withdrawals: [
      { status: "COMPLETED", data: { tx_hash: "near-tx-hash", transfer_tx_hash: "hash-to-addrA",
          chain: "arbitrum", defuse_asset_identifier: "nep141:arb-0xaf...omft.near",
          near_token_id: "arb-0xaf88d065e77c8cc2239327c5edb3a432268e5831.omft.near",
          decimals: 6, amount: 1000000, account_id: "test.near", address: "0xAAAA...",
          created: "2024-01-01T00:00:00Z" } },
      // second withdrawal, same token, different destination, still pending in reality
    ],
  });

  const bridge = new PoaBridge({ envConfig: configsByEnvironment.production, xrplRpcUrls: [] });

  const widA = { landingChain: Chains.Arbitrum, index: 0,
    withdrawalParams: { assetId: "nep141:arb-0xaf...omft.near", amount: 1000000n,
      destinationAddress: "0xAAAA...", feeInclusive: false },
    tx: { hash: "near-tx-hash", accountId: "test.near" } };

  const widB = { ...widA, index: 1,
    withdrawalParams: { ...widA.withdrawalParams, destinationAddress: "0xBBBB..." } };

  const resultA = await bridge.describeWithdrawal(widA);
  const resultB = await bridge.describeWithdrawal(widB);

  // Equality claimed by the invariant: each identifier should resolve to ITS OWN destination's status.
  // BUG: resultB equals resultA even though destinationAddress differs and no matching
  // withdrawal record for 0xBBBB... exists.
  expect(resultA).toEqual({ status: "completed", txHash: "hash-to-addrA" });
  expect(resultB).not.toEqual(resultA); // <-- currently FAILS: resultB === resultA
});
```
