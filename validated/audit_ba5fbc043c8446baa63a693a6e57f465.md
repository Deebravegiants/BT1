### Title
Vetoing the latest EvmHost state commitment resets `_latestStateMachineHeight` to a hardcoded `1` instead of the true previous height, permanently corrupting the availability guarantee that consensus updates rely on - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.deleteStateMachineCommitmentInternal` resets `_latestStateMachineHeight[stateMachineId]` to a hardcoded `1` whenever the vetoed height happens to be the currently recorded latest height, rather than restoring it to the actual last-verified height (as the analogous `pallet-ismp` implementation does via `PreviousStateMachineHeight`). This is the same class of bug as the referenced report: a boundary/tracking value used to gate what heights can be accepted (analogous to `proposalCount`/`proposalId` gating which proposal `state()` is readable) is computed incorrectly, corrupting the "latest" pointer that downstream logic (`HandlerV2.handleConsensus`) relies on to decide whether newly delivered state commitments are accepted.

### Finding Description
`storeStateMachineCommitment` sets `_latestStateMachineHeight[height.stateMachineId] = height.height` on every accepted commitment [1](#0-0) .

`deleteStateMachineCommitmentInternal`, called by a fisherman veto, deletes the commitment and — "technically any state commitment can be vetoed, safety check that it's the latest before resetting it" — resets `_latestStateMachineHeight` to the literal value `1` if the vetoed height equals the current latest height: [2](#0-1) 

There is no `_previousStateMachineHeight` tracking in `EvmHost.sol` at all — unlike the Substrate `pallet-ismp` host, which explicitly persists `PreviousStateMachineHeight` and restores it on veto of the latest height: [3](#0-2) 

`HandlerV2.handleConsensus` uses `host.latestStateMachineHeight(...)` as the sole gate for accepting new intermediate state commitments during consensus verification: [4](#0-3) 

Because the EVM host collapses the "previous height" to `1` instead of the real prior verified height, any height strictly between `1` and the true previous height will satisfy `intermediate.height > latestHeight` after a veto. This mirrors the report's bug class: an incorrectly maintained boundary/counter value (there, `proposalCount` vs `proposalId`; here, `_latestStateMachineHeight` vs the true previous height) causes a component that should gate access/acceptance based on "latest" to behave incorrectly, either wrongly restricting or wrongly permitting operations relative to what the true state actually is.

### Impact Explanation
`_latestStateMachineHeight` is the sole gate EvmHost/HandlerV2 use to reject stale or already-verified consensus intermediate states, and it is also exposed publicly via `latestStateMachineHeight()` and consumed by relayers/provers (`tesseract/messaging/evm/src/provider.rs::query_latest_height`) to determine what height state machine updates should be submitted from [5](#0-4) . After a veto of the latest height, this pointer silently regresses all the way down to `1` rather than to the actual previous honest height, meaning:
- Any legitimate consensus update for the counterparty state machine that reports intermediate heights between `1` and the true previous height will be wrongly accepted (`intermediate.height > latestHeight` passes when it shouldn't), because they are no longer correctly bounded against the real prior verified height.
- Relayers/provers computing "what the host has already verified" via `latestStateMachineHeight()` will get an incorrect, artificially depressed value, causing them to attempt resubmission or catch-up logic against a height far below the real state, which can desynchronize the availability of the messaging pipeline for that state machine until enough new commitments are stored to bring the pointer back up.

This is a route-availability / message-delivery correctness issue directly reachable from a single relayed veto proof (fisherman-submitted, permissionless-relay flow), matching the required impact class of "a route unable to deliver messages" / "unsound state commitment" tracking.

### Likelihood Explanation
This triggers deterministically any time a fisherman legitimately vetoes the most recently stored state commitment for a state machine (a normal, expected, permissionless part of the fisherman/veto flow, not a malicious-admin or malicious-node scenario) — no attacker collusion is required. It only requires that a state machine has more than one verified height at the time of veto (i.e., `latest > 1`), which is the common case in production.

### Recommendation
Track the actual previous verified height in `EvmHost.sol` (mirroring `PreviousStateMachineHeight` in `modules/pallets/ismp/src/host.rs`) and update it every time `storeStateMachineCommitment` advances `_latestStateMachineHeight`. In `deleteStateMachineCommitmentInternal`, when the vetoed height equals the current latest height, restore `_latestStateMachineHeight` to this tracked previous height instead of the hardcoded `1`.

### Proof of Concept
1. Handler stores commitments at heights 10 and 11 for state machine `id`, so `_latestStateMachineHeight[id] == 11`.
2. A fisherman vetoes height 11 via `deleteStateMachineCommitment` (the only path reaching `deleteStateMachineCommitmentInternal`).
3. Since `_latestStateMachineHeight[id] == 11 == height.height`, the code sets `_latestStateMachineHeight[id] = 1` [6](#0-5) , discarding the fact that height 10 was still honestly verified and is the true "previous" height.
4. A subsequent consensus proof reporting an intermediate state at height 5 (which is stale relative to the real previous height of 10, and should be rejected) now passes `latestHeight != 0 && intermediate.height > latestHeight` (`5 > 1`) in `HandlerV2.handleConsensus` and gets stored via `storeStateMachineCommitment`, silently corrupting/regressing the state commitment history for that state machine and confusing relayers relying on `latestStateMachineHeight()` to determine what has already been proven.

     * @dev Delete the state commitment at given state height.

    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }
