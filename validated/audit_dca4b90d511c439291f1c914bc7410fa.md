Based on the code, `next_leaders()` in `core/src/forwarding_stage.rs` (the `LeaderUpdater` impl at line 490-493) and the underlying `next_leaders` function in `core/src/next_leader.rs` are purely part of the **forwarding path** — they compute TPU/QUIC socket addresses of upcoming leaders to forward packets to, based on `poh_recorder.leader_after_n_slots()` and `cluster_info.lookup_contact_info()`. They have no involvement in transaction execution, banking, commit, or consensus state. [1](#0-0) [2](#0-1) 

Key facts that invalidate the premise of this question:

- `next_leaders` returns `Vec<SocketAddr>` — a list of network addresses to forward packets to. It has no "error branch" with side effects; it simply filters/collects results from `leader_after_n_slots` and `lookup_contact_info`, both of which are read-only lookups [3](#0-2) .
- There is no committed/bank state touched anywhere in this function or its caller `get_non_vote_forwarding_addresses`/`get_vote_forwarding_addresses` [4](#0-3) .
- Forwarding is a best-effort, non-consensus-critical operation: packets forwarded to the wrong/no address just fail to be forwarded (`ForwardingClientError::LeaderContactMissing` / `Failed`), which affects only whether a transaction gets included in a future block sooner — it cannot cause two honest nodes to compute different bank hashes for the same already-included transaction [5](#0-4) .
- The scheduler referenced here (`ConnectionWorkersScheduler` in `tpu-client-next`) governs network connection/send ordering to leaders for forwarding, not the execution/replay order of transactions within a bank. Banking/replay ordering and commit logic live entirely elsewhere (banking stage / replay stage), not in this file.

Since `next_leaders` has no role in transaction execution, sanitization, fee/rent computation, or bank commit, there is no code path by which its "scheduler ordering" could influence committed bank state or cause bank-hash divergence between honest validators.

pub(crate) fn next_leaders(
    cluster_info: &impl LikeClusterInfo,
    poh_recorder: &RwLock<PohRecorder>,
    max_count: u64,
    port_selector: impl ContactInfoQuery<Option<SocketAddr>>,
) -> Vec<SocketAddr> {
    let recorder = poh_recorder.read().unwrap();
    let leader_pubkeys: Vec<_> = (0..max_count)
        .filter_map(|i| {
            recorder.leader_after_n_slots(
                FORWARD_TRANSACTIONS_TO_LEADER_AT_SLOT_OFFSET
                    + i * NUM_CONSECUTIVE_LEADER_SLOTS.get() as u64,
            )
        })
        .collect();
    drop(recorder);

    leader_pubkeys
        .iter()
        .filter_map(|leader_pubkey| {
            cluster_info.lookup_contact_info(leader_pubkey, &port_selector)?
        })
        .collect()
}
