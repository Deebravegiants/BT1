## Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` is refunded to the Host contract instead of the original caller, permanently trapping user overpayments - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and swap it for the exact `feeToken` amount required via Uniswap V2's `swapETHForExactTokens`. Any ETH sent beyond what the swap consumes is never routed back to the original transaction sender — it is refunded by the router to `EvmHost` itself (the immediate caller of the router), and the host has no logic to forward that dust onward.

### Finding Description
In all three payable entry points, the pattern is identical: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } ...
```

`swapETHForExactTokens` computes the exact amount of ETH (`amounts[0]`) needed to buy `post.fee` units of `feeToken`, and refunds `msg.value - amounts[0]` to `msg.sender` of the router call — which is `EvmHost`, not the app/user who originally sent `msg.value` to `dispatch()`. The same pattern exists in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

None of these functions compare the actual ETH consumed against `msg.value` and return the difference to `_msgSender()`. The leftover ETH accumulates as untracked balance on `EvmHost`. It can only ever be moved out via the privileged, cross-chain-governance-gated `withdraw()` function: [4](#0-3) 

That function sends funds to whatever `beneficiary` governance specifies — there is no accounting that ties the trapped dust back to the specific depositor, so the original overpayer has no on-chain mechanism to recover it. This mirrors the "remaining ether is not returned to the user" pattern from the Allo.sol report (`baseFee + amount` vs `msg.value` mismatch), except here the fee amount is computed dynamically through an AMM swap, and the AMM's own excess-refund logic sends it to the wrong recipient (the contract instead of the caller).

Callers reach this from any app built on `IDispatcher`/`HyperApp`, e.g. `HyperFungibleToken.send()`, `WrappedHyperFungibleToken.send()`, and `IntentGatewayV2`/`ExtrinsicIntents` cross-chain dispatch paths, all of which forward `msg.value` (or a computed remainder) straight into `IDispatcher(_host).dispatch{value: ...}(request)`: [5](#0-4) 

Because the exact swap input required (`amounts[0]`) depends on live AMM reserves at execution time — which can differ from whatever `quote()` returned earlier, or from a value the caller intentionally over-supplies as slippage buffer — normal usage is very likely to generate leftover ETH on every dispatch call that pays natively.

### Impact Explanation
Any unprivileged user/app dispatching a POST/GET request or funding a request with native ETH, whose supplied `msg.value` exceeds the exact amount the router consumes, permanently loses that excess to `EvmHost`. Since the contract does not track which depositor the excess belongs to, there is no way for the affected user to reclaim it; the funds sit as accumulated dust the host manager could later sweep for a different destination (governance-defined beneficiary), which is a genuine, if slow, freezing/loss of user funds. This can occur on every fee-paying dispatch that goes through the native-token path, not just a one-off misconfiguration.

### Likelihood Explanation
High likelihood in practice: `quote()` is an estimate computed in a separate call/transaction using `getAmountsIn`, and AMM reserves move between quoting and dispatching (arbitrage, other swaps, block delay). Users/integrators commonly add a safety buffer to `msg.value` to avoid reverts from price movement, guaranteeing leftover ETH on many calls. No special conditions or malicious actors are required — this is triggered by ordinary use of the fee-payment feature.

### Recommendation
After calling `swapETHForExactTokens`, compare `msg.value` against the actual ETH spent (the returned `amounts[0]`) in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund the difference directly to `_msgSender()` (or `post.payer`) via a low-level call, reverting on failure. Alternatively, use `swapExactETHForTokens` with a minimum-out check that consumes the entire `msg.value` and forwards any resulting fee-token surplus to `post.payer`, but the direct refund-of-native-dust approach is simplest and matches the ecosystem convention already used in `IntentGatewayV2`/`ExtrinsicIntents`, which explicitly refund unspent native tokens to the caller.

### Proof of Concept
1. App/user calls `IDispatcher(host).dispatch{value: X}(post)` where `post.fee = F` (feeToken units), using `X` slightly larger than the current `quote()` value (e.g., to protect against slippage or simply because `quote()` was stale).
2. `EvmHost.dispatch` calls `swapETHForExactTokens{value: X}(F, path, address(this), deadline)`.
3. Uniswap V2 router spends only `amounts[0] < X` ETH to acquire `F` feeToken, and refunds `X - amounts[0]` ETH to `msg.sender` of the swap call, which is `EvmHost`.
4. `EvmHost.dispatch` returns without forwarding the `X - amounts[0]` refund to the original caller; it remains part of `EvmHost`'s ETH balance indefinitely.
5. The original caller has no function to reclaim their `X - amounts[0]` excess; only cross-chain governance via `HostManager`/`withdraw()` can later move that native balance, and to an arbitrary beneficiary unrelated to the original depositor.
