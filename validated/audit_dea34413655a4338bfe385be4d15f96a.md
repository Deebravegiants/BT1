### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-validating the raw request body, then unconditionally trusts the `shop-domain` header to build the `WebhookMetadata` object handed to the app's handler. The shop identity used for tenant routing is never part of the signed material, so the binding "HMAC-authenticated bytes == the shop the payload is attributed to" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers and are not part of the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately forwards the (unauthenticated-w.r.t.-signature) `request.shop`, `request.topic`, and `request.webhook_id` into `WebhookMetadata`, which the app handler uses to decide what tenant/topic the webhook belongs to: [3](#0-2) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field consumed by the handler to key per-tenant logic: [4](#0-3) 

This is the same bug class described in the report: a value that is *used* in a security-relevant decision (there: CR calculation ignoring `vault.interest`; here: tenant identity ignoring the fact that `shop` is outside the HMAC) is not bound to the value that was actually cryptographically verified (there: `vault.debt` alone; here: `raw_body` alone). The equality that should hold — `authenticated(shop, body) == attributed(shop, body)` — is broken because only `body` is authenticated while `shop` is attributed independently from an unauthenticated header.

Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` *is* explicitly included in `to_signable_string` alongside `code`/`host`/`state`/`timestamp`, showing the library's own pattern for correctly binding shop identity to the HMAC where it matters for OAuth: [5](#0-4) 

### Impact Explanation
Because the app's api_secret_key is shared across all shops that install the app, any unprivileged internet user who is a legitimate merchant/tester of the app (i.e., has their own shop installed, and can therefore obtain one authentic `(raw_body, hmac)` pair for a real webhook delivered to their own store) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` (and/or `topic`/`webhook-id`) header for an arbitrary victim shop. `Registry.process` will accept it as valid (the HMAC check only covers the body) and will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop. Depending on what the host app's handler does with `data.shop` (e.g. update records, mark subscription state, process `app/uninstalled` cleanup, GDPR data-request/erasure actions), this enables cross-tenant data corruption or state manipulation attributed to a shop the attacker does not control — i.e., cross-tenant access, which is one of the accepted "Critical" impact categories.

### Likelihood Explanation
Exploitation requires only: (1) the app being installed by the attacker on their own (unprivileged) shop so they can capture one legitimate webhook delivery, and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with modified headers — both trivially available to any external, unprivileged party interacting with a multi-tenant app built on this gem, and no possession of `api_secret_key`, access tokens, or other privileged credentials is required. The core weakness (header not covered by the signature) is inherent to the gem's `Webhooks::Request`/`Registry` implementation, not a misuse of a documented API by the host app.

### Recommendation
Bind the tenant/topic identity to the authenticated content: include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or, at minimum, require the host application to independently re-verify that the shop attributed to the webhook corresponds to a shop with an active, previously-established session/webhook registration before acting on `WebhookMetadata`). At a minimum, document prominently that `WebhookMetadata.shop`/`topic`/`webhook_id` are *not* authenticated by `HmacValidator.validate` and must not be trusted for tenant-scoped side effects without additional verification (e.g., cross-checking against `Registry`'s known registrations or session store).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `customers/data_request`).
2. Shopify delivers a legitimate webhook to the app: body `B`, headers including `x-shopify-hmac-sha256: H` (valid for `B`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and sends their own HTTP POST to the app's public webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `request.to_signable_string` (`== B`), so it succeeds: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: ...)` and performs shop-scoped actions attributed to `victim-shop.myshopify.com`, even though the victim shop never sent or authorized this data.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
