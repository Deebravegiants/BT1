### Title
Webhook `shop` identity is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, while `#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signable string used by `HmacValidator`. `Registry.process` validates only the HMAC over the body and then trusts `request.shop` as the tenant identity handed to the app's handler, breaking the binding `shop_verified_by_hmac == shop_used_for_tenant_dispatch`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`, completely excluding the `shop` header: [2](#0-1) 

`Registry.process` verifies the HMAC (over the body only) and then unconditionally forwards `request.shop` to the app's registered handler as the authenticated tenant identity: [3](#0-2) 

`WebhookMetadata.shop` is a `const` field that host applications rely on to route/attribute the webhook to a specific merchant/tenant: [4](#0-3) 

Because `shop` is not cryptographically bound to the HMAC, any entity that possesses one valid `(raw_body, hmac)` pair — for example, an unprivileged merchant who installs the app on their own store and thus legitimately receives correctly signed webhooks from Shopify (all installs share the same app `client_secret`/`api_secret_key`) — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Request.new` and `HmacValidator.validate` will both accept the forged request as fully valid, since neither checks that the `shop` header matches anything covered by the signature.

### Impact Explanation
This breaks the tenant/authentication boundary the gem is supposed to enforce for webhook delivery: an attacker-controlled `shop` value reaches the host application's business logic (order/customer/data-redaction processing, GDPR mandatory topics, etc.) as if it were verified by Shopify. Depending on how the host app uses `WebhookMetadata.shop` (e.g., looking up the offline session/access token for that shop, or writing/deleting cross-tenant data), this enables cross-tenant data access or corruption — exactly the class of impact called out as Critical ("cross-tenant access").

### Likelihood Explanation
Any developer/merchant with a working app installation can obtain a validly-signed webhook payload from their own Shopify store, since all app installs share one `api_secret_key`. No access to the merchant's or victim's credentials, access tokens, or `client_secret` is needed — only the ability to POST an HTTP request with attacker-controlled headers to the app's public webhook endpoint, which is by definition internet-reachable. This is a low-effort, unprivileged attack path.

### Recommendation
Include `shop` (and ideally `topic`, `api_version`, `webhook_id`) in the HMAC-signed payload check, or otherwise cryptographically bind the `shop-domain` header to the signature — e.g., have `Webhooks::Request#to_signable_string` incorporate the shop domain, or have `Registry.process` reject the request unless the shop header is verified against a separately-authenticated value (such as the shop stored against the resolved offline session). At minimum, document that `WebhookMetadata.shop` is unverified and must not be trusted for tenant dispatch without additional validation by the host app.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`. Shopify sends a correctly HMAC-signed webhook, e.g. body `{"id":123}` with header `x-shopify-hmac-sha256: <valid_hmac_of_body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this `(raw_body, hmac)` pair (it is delivered to the attacker's own configured webhook URL, so no interception of others' traffic is required).
3. Attacker crafts a new HTTP POST to the app's public webhook endpoint with the same `raw_body` and same `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks `raw_body`, which is unmodified.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))`, so the host application processes attacker-supplied data as if it authentically originated from `victim-shop.myshopify.com`.
