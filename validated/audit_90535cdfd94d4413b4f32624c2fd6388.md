### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop-domain` and `topic` values that the handler subsequently trusts to identify *which shop* and *which event* the payload belongs to are taken straight from unauthenticated HTTP headers and are never included in the signed material. Any bearer of one valid `(body, hmac)` pair (e.g. an attacker who legitimately owns/installs the app on their own store and thus receives real, correctly-signed webhooks for that store) can replay that exact body/hmac pair to the app's public webhook endpoint while substituting arbitrary `shopify-shop-domain` and `shopify-topic` headers, causing the handler to process the payload as if it belonged to a different shop and/or topic.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature using only `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns the raw body only — no headers are included: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards the header-derived `shop` and `topic` values to the app's handler without any additional binding check tying them to the signed body: [3](#0-2) 

The equality the HMAC is supposed to guarantee is:

`hmac == HMAC(secret, body)` for the specific `(shop, topic, body)` tuple that Shopify actually sent.

What the code actually verifies is only:

`hmac == HMAC(secret, body)`

with `shop` and `topic` completely unbound to that proof. Since `body` alone determines the signature, any party who has ever received one legitimately-signed webhook (for their own store, from their own app installation — not requiring `api_secret_key`) can capture that `(body, hmac)` pair and POST it directly to the app's public webhook controller with different `shopify-shop-domain` / `shopify-topic` header values. `HmacValidator.validate` still returns `true` because it never looks at those headers, and `Registry.process` dispatches the attacker-chosen `shop`/`topic` metadata to the handler as if it were authentic.

### Impact Explanation
This breaks the tenant-isolation guarantee the HMAC is meant to provide. An app author using `ShopifyAPI::Webhooks::Registry` reasonably assumes that once `Utils::HmacValidator.validate` passes, the `shop` and `topic` values handed to their `handler.handle` call are authentic and can be trusted to key into per-shop state (e.g. app/uninstalled cleanup, GDPR shop/customer redact, billing webhooks, subscription state changes). Because `shop` and `topic` are forgeable independently of the signature, an attacker can trigger shop-scoped business logic for a victim shop they have no access to, using nothing but a webhook body/signature pair obtained from their own, unrelated store — a cross-tenant access vulnerability with no credentials, no privileged account, and no interaction from the victim.

### Likelihood Explanation
Likelihood is realistic: the webhook HTTP endpoint is by design internet-reachable (Shopify must be able to POST to it), so no network position or credential is required to reach it. The only prerequisite is possession of one valid `(body, hmac)` pair, which any user who has installed the app on their own (attacker-controlled) shop will legitimately receive the first time any webhook fires for that shop — no secrets need to be extracted.

### Recommendation
Include the identity-relevant headers (`shopify-shop-domain`, `shopify-topic`, and ideally `shopify-webhook-id`/`api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting them, so that `to_signable_string` reflects the full authenticated context rather than just the raw body. At minimum, `Registry.process` should re-derive/require the caller to supply the expected shop out-of-band (e.g. from an authenticated session) and cross-check it against `request.shop`, rather than trusting the header value outright.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook topic that is registered (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` that Shopify sent (a legitimately signed pair, no secret needed).
2. Attacker POSTs to the app's public webhook controller endpoint with:
   - `raw_body = B`
   - headers: `x-shopify-hmac-sha256: H`, `x-shopify-topic: app/uninstalled` (or any topic of choice), `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds because `to_signable_string` never included the shop/topic headers.
4. `handler.handle(data: WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: ..., ...))` is invoked, causing the app to execute uninstall/cleanup (or whatever topic-specific) logic against `victim-shop.myshopify.com`'s stored data, despite the attacker having no relationship with that shop.
