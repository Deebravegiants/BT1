### Title
Malicious swap route can hide an unrelated wallet-token transfer inside the caller’s authorization tree - (contracts/controller/src/strategies/swap.rs)

### Summary
The controller accepts an opaque `swap` payload and invokes the configured router without restricting which pool contracts the route can reach. A pool reached by the route can invoke an unrelated `token.transfer(victim, attacker, amount)` while the transaction is under the victim’s authorization context. Soroban simulation can include that transfer as a child invocation of the victim’s signed root call; if the victim signs the generated tree, the malicious pool can steal wallet assets unrelated to the lending position while still returning a valid swap output.

### Finding Description
`swap_collateral` authenticates the caller and verifies account ownership/delegation, then forwards the user-controlled `swap` payload into `withdraw_and_swap_from_supply`. [1](#0-0) 

The controller invokes the configured aggregator and grants one exact input transfer from the controller to that router, but the route itself remains opaque to the controller. [2](#0-1) 

After the router returns, the controller checks only that input spending did not exceed `amount_in` and that the controller received positive `token_out`. It does not inspect or constrain authorization activity performed by contracts reached through the route. [3](#0-2) 

The repository includes a regression test demonstrating this exact authorization-tree behavior: a rogue hop pool calls `token.transfer(victim, attacker, amount)`, simulation records that transfer as a child of Alice’s `swap_collateral` authorization, and signing the poisoned tree moves Alice’s unrelated wallet token while the lending swap succeeds. [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker who convinces a victim to submit a crafted route can steal arbitrary SAC/token balances from the victim’s wallet, including assets that were never supplied to or listed by the lending protocol. The routed lending operation can still satisfy the controller’s measured-output and final-risk checks, so the theft succeeds atomically with an apparently valid collateral swap.

This is theft of user funds. The stolen amount is bounded only by the victim’s token balances and the additional transfer included in the authorization tree.

### Likelihood Explanation
The attack requires user interaction: the victim must submit and sign a transaction containing the malicious route and the extra authorization subtree. That matches the bug class hinted by CVE-2020-15984: the signer is shown or expects one operation while the generated authorization tree can contain another hidden token transfer.

No compromised key, administrator action, protocol parameter error, or oracle manipulation is required. The malicious pool merely needs to implement the expected venue-facing calls, pass the measured input/output checks, and perform the additional victim-token transfer during its callback window.

### Recommendation
Do not rely on users or wallets to detect malicious children in a simulated authorization tree. At minimum:

- Restrict route hop pools/venues to an explicit governance-approved allowlist.
- Prefer routes expressed as explicit structured operations rather than opaque controller-level bytes.
- Have the client/wallet display every child authorization and reject any entry outside the expected input transfer.
- Consider a router policy that records or constrains the exact external contract invocation graph expected for a route and rejects unlisted calls.

### Proof of Concept
The repository’s `rogue_hop_pool_transfer_joins_caller_auth_tree` test provides the complete pattern:

1. Alice supplies USDC and holds `WALLET_BALANCE` of an unrelated token.
2. A route names an attacker-deployed hop pool.
3. The pool’s `swap` calls `token::Client::transfer(alice, attacker, WALLET_BALANCE)`. [6](#0-5) 
4. Alice invokes `swap_collateral(alice, account_id, USDC, amount, ETH, route)`. [7](#0-6) 
5. Simulation records the wallet-token transfer as a sub-invocation of Alice’s signed `swap_collateral` entry. [8](#0-7) 
6. When that poisoned tree is signed, the wallet token is transferred to the attacker while Alice receives the expected swap output. [5](#0-4)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
