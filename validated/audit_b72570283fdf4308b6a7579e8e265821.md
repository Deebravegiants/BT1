### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value that is subsequently trusted and handed to the host application's webhook handler is taken from an HTTP header that is never included in the signed bytes. This breaks the identity binding: **bytes verified (raw body) ≠ bytes that determine the tenant (shop-domain header)**.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is completely independent of the signed payload: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header value: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, and then forwards the unauthenticated `shop` field to the merchant-specific webhook handler as the tenant identifier: [4](#0-3) 

Because `shop` is not part of the signed material, any request whose body+HMAC pair is a valid (body, HMAC) pair for the app's `client_secret` will be accepted regardless of which shop-domain header accompanies it. An attacker who obtains one genuine `(raw_body, hmac)` pair (e.g., a webhook delivery a merchant can trigger for their own shop, replayed through a proxy, logs, or any channel where the payload transits in the clear) can resend that exact body with an arbitrary `x-shopify-shop-domain` header. The signature still validates — it was never bound to the shop — and the host application's handler will process the payload as if it originated from the attacker-chosen shop.

The equality the code should enforce is:
`hmac == HMAC(secret, raw_body ‖ shop ‖ topic)` (or otherwise binding `shop`/`topic` into the signed string),
but the actual check is:
`hmac == HMAC(secret, raw_body)`,
independent of `shop`.

### Impact Explanation
This allows cross-tenant webhook injection: an attacker can cause a merchant app to process a webhook payload under a different shop's identity, potentially triggering shop-scoped side effects (e.g., data updates, order/customer processing, GDPR webhook mishandling) attributed to a shop that never sent that data. This matches the Critical "cross-tenant access" impact category, since the trust boundary between tenants (shops) is not cryptographically enforced by this gem, even though the gem's API implies the validated request's `shop` is authentic.

### Likelihood Explanation
Exploitation requires an attacker to obtain a valid `(raw_body, hmac)` pair, typically for the attacker's own shop, since Shopify only sends fully valid signed webhooks for that shop's data. The attacker then only needs to alter the unauthenticated `shop-domain` header and resend it to the same app endpoint. This is a single, deterministic HTTP replay with no cryptographic material required beyond a webhook the attacker can legitimately trigger against their own store — a bar low enough for any unprivileged Shopify merchant/attacker who installs the target app.

### Recommendation
Bind the `shop` (and ideally `topic`) into the signed material checked by `HmacValidator`, e.g., by overriding `to_signable_string` in `ShopifyAPI::Webhooks::Request` to include the shop-domain and topic headers alongside the raw body, or by independently verifying that the `shop` header matches an expected/registered shop before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) for their own store, capturing the raw POST body `B` and the valid `x-shopify-hmac-sha256` header `H` computed by Shopify with the app's `client_secret`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint using the identical body `B` and HMAC header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body successfully (all required headers present).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`B` only) and finds it matches `H` — validation passes. [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, and the host app processes it as a legitimate webhook for the victim shop.
