Audit Report

## Title
Missing `return` after failed `email` claim type-assertion in `handleTokenExchange` allows OIDC session creation with an empty/unattributed identity - (File: `core/sessions/oidcauth/oidc.go`)

## Summary
In `handleTokenExchange`, the OAuth2/OIDC authorization-code callback handler, the failure of the `email, ok := claims["email"].(string)` type assertion writes a `500` error body but does not `return`, unlike every other error branch in the same function [1](#0-0) . Execution falls through to role mapping, session-row insertion, audit logging, and a final `200 OK` response, producing a persisted, cookie-backed `oidc_sessions` row with `user_email = ""` and a legitimate RBAC role.

## Finding Description
Every other failure branch in `handleTokenExchange` (invalid state, `Exchange` failure, missing `id_token`, `Verify` failure, claims parsing failure, `ExtractIDClaimValues` failure, `IDClaimsToUserRole` failure, `ginSession.Save()` failure) writes an error response and then calls `return` [2](#0-1) [3](#0-2) . The `email` type-assertion branch is the sole exception — it logs, writes `c.String(http.StatusInternalServerError, ...)`, and continues without `return` [1](#0-0) .

Because `IDClaimsToUserRole` operates on `idClaims` derived from `ExtractIDClaimValues`/`ClaimName()` group claims and does not depend on `email`, role resolution proceeds normally and independently of the missing email [4](#0-3) . The code then inserts a new `oidc_sessions` row with `user_email = ""` and the resolved role, and the insert-error branch at line 257 has the identical missing-`return` defect [5](#0-4) . It emits an audit entry attributing the login to an empty email [6](#0-5) , sets the session cookie, and finally responds `200 {"success":true}` [7](#0-6) . `AuthorizedUserWithSession` will subsequently resolve this session normally, returning a `clsessions.User{Email:"", Role: <mapped role>}` [8](#0-7) .

This confirms the reported root cause exactly as described: an unchecked/ignored type-assertion failure lets execution continue past what was clearly intended to be a fatal error, mirroring every sibling branch's fail-closed pattern which this one alone violates.

## Impact Explanation
The resulting session is fully functional and role-privileged (RBAC checks key on `Role`, not `Email`), but carries no attributable identity: the `oidc_sessions.user_email` column is empty, the audit log records `{"email": ""}`, and any admin session listing via `Sessions()` will show an unattributed session [9](#0-8) . This breaks accountability/audit-trail integrity for privileged actions taken under such sessions and allows multiple distinct principals lacking an email claim to collapse into indistinguishable sessions in the audit trail. This is a genuine, in-scope defect in the internet-facing OIDC callback handler's fail-closed guarantee, though it does not by itself escalate privileges beyond what the IdP's group claim already grants — the severity is best characterized as an accountability/audit-integrity weakness rather than a full authentication or role bypass.

## Likelihood Explanation
Triggering this requires an IdP flow in which the returned ID token omits the standard `email` claim while still including a group claim mapping to a configured role (`AdminClaim`/`EditClaim`/`RunClaim`/`ReadClaim`). This depends on operator-chosen OIDC provider behavior (e.g., providers that do not guarantee `email` for all accounts) rather than any node/operator misconfiguration of chainlink itself, and the flow (`/oidc-login` → provider consent → token exchange) is reachable by any external client able to complete the standard OAuth2 code exchange — it does not require any special chainlink privilege.

## Recommendation
Add `return` immediately after the error response in the `email` type-assertion failure branch, consistent with all other error branches in `handleTokenExchange`:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Apply the same fix to the `oi.ds.ExecContext` session-insert error branch at line 257, which has the identical missing-`return` defect.

## Proof of Concept
1. Configure `oidcAuthenticator` against an OIDC provider that issues a token containing a group claim matching a configured role claim (e.g. `RunClaim()`), but no `email` claim.
2. `GET /oidc-login` to obtain `state` via `handleSignIn`, complete provider consent, then `POST` the resulting `code`/`state` to the token-exchange endpoint (`handleTokenExchange`).
3. Observe: server logs `"Failed to get email from claims"` and writes a `500` body, but execution continues — `IDClaimsToUserRole` resolves the role, an `oidc_sessions` row is inserted with `user_email=''`, `AuthLoginSuccessNo2FA` audit entry records `{"email": ""}`, the session cookie is set, and the final response is `200 {"success": true}`.
4. Use the returned cookie against any role-gated endpoint (`RequiresRunRole`) to confirm the session is fully functional and role-privileged, while `Sessions()`/audit logs show an empty-email, unattributed session — a Go integration test asserting `oidc_sessions.user_email == ""` after step 2/3 confirms the defect.

// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}

// Sessions returns all sessions limited by the parameters.
func (oi *oidcAuthenticator) Sessions(ctx context.Context, offset, limit int) ([]clsessions.Session, error) {
	var sessions []clsessions.Session
	sql := `SELECT * FROM oidc_sessions ORDER BY created_at, id LIMIT $1 OFFSET $2;`
	if err := oi.ds.SelectContext(ctx, &sessions, sql, limit, offset); err != nil {
		return sessions, nil
	}
	return sessions, nil
}
