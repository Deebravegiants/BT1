## Title
Unchecked Integer Multiplication in Fee Burn Calculation Can Overflow/Panic - (File: `runtime/src/bank/fee_distribution.rs`)

### Summary
`Bank::calculate_reward_and_burn_fee_details` computes the burned portion of a slot's accumulated transaction fees using raw, unchecked `u64` multiplication and division, in contrast to every other fee/cost/rent computation path in the codebase (`solana_fee::calculate_signature_fee`, `ComputeBudgetLimits::get_prioritization_fee`, `CostModel::get_signature_cost`/`get_write_lock_cost`, `core/src/transaction_priority.rs`, `core/src/forwarding_stage.rs`), which consistently use `saturating_add`/`saturating_mul`/`checked_div` or `u128` intermediate math specifically to avoid overflow.

### Finding Description
`calculate_reward_and_burn_fee_details` is: [1](#0-0) 

```rust
pub fn calculate_reward_and_burn_fee_details(
    &self,
    fee_details: &CollectorFeeDetails,
) -> FeeDistribution {
    let burn = fee_details.transaction_fee * self.burn_percent() / 100;
    let deposit = fee_details
        .priority_fee
        .saturating_add(fee_details.transaction_fee.saturating_sub(burn));
    FeeDistribution { deposit, burn }
}
```

`fee_details.transaction_fee` is `CollectorFeeDetails::transaction_fee`, an accumulated `u64` that is built up across every transaction processed within a slot (via `self.collector_fee_details`, referenced in `runtime/src/bank.rs`). Unlike the sibling arithmetic in this exact function (`saturating_add`/`saturating_sub` on the very next lines), the burn calculation uses a raw `*` and `/`. Every comparable fee calculation elsewhere in the codebase deliberately avoids this pattern: [2](#0-1) [3](#0-2) 

This is called from `distribute_transaction_fee_details`, which runs unconditionally at the end of every slot as part of bank commit processing: [4](#0-3) 

### Impact Explanation
If `fee_details.transaction_fee` (the slot-accumulated signature-fee total) grows large enough that `transaction_fee * self.burn_percent()` (burn_percent is a constant 50) exceeds `u64::MAX`, the multiplication will:
- panic in debug/overflow-checked builds, halting the validator (this executes unconditionally in the block-commit path, so a single such slot would crash every validator that processes it — a cluster-wide halt), or
- silently wrap in release builds (Rust's default `--release` behavior is wrapping unless `overflow-checks` is enabled), producing an incorrect `burn` value, which flows directly into `deposit = priority_fee + (transaction_fee - burn)` and thus into `self.capitalization.fetch_sub(total_burn, Relaxed)` — corrupting both the leader's fee reward and the total token supply accounting (undeclared value creation/destruction).

This matches the reported bug class: an unguarded multiply/divide in fee computation that can overflow and either miscalculate fees or make the routine misbehave, exactly as described for `appendUtxos`.

### Likelihood Explanation
Reaching the overflow threshold requires the *slot-accumulated* `transaction_fee` total to approach `u64::MAX / 50` (~3.68×10^17 lamports), which is far beyond realistic per-slot signature-fee totals under normal fee-rate governance. This substantially reduces practical likelihood compared to the original per-transaction Bitcoin fee bug (where a single miscalculated fee could break a transaction). It is not clear from the available code whether `collector_fee_details.transaction_fee` accumulation elsewhere in `runtime/src/bank.rs` uses saturating or checked arithmetic (I was unable to fully inspect this before running out of tool calls), which affects whether an attacker could realistically drive this value close to `u64::MAX` within a slot (e.g., via pathological fee-rate-governor states or extreme signature counts across many transactions). This is a real code-quality/defense-in-depth gap, not a demonstrated practical exploit path.

### Recommendation
Replace the raw arithmetic with saturating (or checked, with explicit error handling) operations, consistent with the rest of the fee-calculation code:
```rust
let burn = fee_details.transaction_fee.saturating_mul(self.burn_percent()).saturating_div(100);
```

### Proof of Concept
Not independently verified with a live overflow trigger; the finding is based on static code review showing `transaction_fee * self.burn_percent() / 100` uses unchecked multiplication, unlike every other reachable fee-calculation function in the same call chain (`solana_fee::calculate_fee_details`, `ComputeBudgetLimits::get_prioritization_fee`, `CostModel`), all of which explicitly use saturating arithmetic to guard against exactly this overflow class. Full confirmation of the accumulation path for `collector_fee_details.transaction_fee` in `runtime/src/bank.rs` (to establish whether/how it could reach overflow-inducing magnitudes) was not completed due to tool-call limits.
