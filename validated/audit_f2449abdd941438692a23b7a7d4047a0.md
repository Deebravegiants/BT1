## Title
Backend Config Overwrites Signup Authorization Parameters Mid-Signup, Allowing Inconsistent QR-Validation Rules Within a Single Signup Session - (File: src/brokers/observer.rs, src/plans/mod.rs)

### Summary
`DefaultPlan::config_update()` in `src/brokers/observer.rs` unconditionally re-downloads the backend `Config` every `CONFIG_UPDATE_INTERVAL` (10 seconds) and overwrites the entire shared `Arc<Mutex<Config>>` in place, with no check for whether a signup is currently in progress. `src/plans/mod.rs::verify_user_qr_code()` reads `user_qr_validation_use_full_operator_qr` and `user_qr_validation_use_only_operator_location` fresh from that same mutable config at the moment the user QR is validated, and other authorization-relevant fields (`self_serve`, `ignore_user_centric_signups`, `pcp_v3`, etc.) are similarly re-read from the shared config at different points of `do_signup`. This is the same bug class as the reported `HarTokenSale.setWhitelistReserve()` issue: a security-relevant configuration parameter that is supposed to govern how a single "transaction" (there: a deposit round; here: a signup session) is processed can be silently rewritten mid-flight, so different phases of the same signup may be evaluated under inconsistent authorization rules.

### Finding Description
The orb's configuration is stored in `Arc<Mutex<Config>>` and is refreshed from the backend on a fixed timer, independent of signup state: [1](#0-0) 

This background task fires every `CONFIG_UPDATE_INTERVAL` from `poll_extra`, which is gated only on `network_unblocked`, not on whether a signup is active: [2](#0-1) [3](#0-2) 

Within a single signup, `MasterPlan::do_signup()` reads a snapshot of `Config` at the start (`self_serve`, `pcp_v3`, QR/relay timeouts, etc.): [4](#0-3) 

but the operator/user QR-code authorization check (`verify_user_qr_code`) — which decides whether the scanned user QR is *valid at all* for this orb/operator — takes its own independent snapshot of the two flags that control how the user is authorized against the operator (`user_qr_validation_use_full_operator_qr`, `user_qr_validation_use_only_operator_location`) at the exact moment of that call: [5](#0-4) 

These flags directly change which backend authorization query is performed — validating against the full operator QR, only the operator's location, or neither: [6](#0-5) 

Because the shared `Config` can be overwritten in full by the 10-second background poll at any point during a signup (QR scanning → biometric capture → pipeline → PCP upload can span well over 10 seconds), the authorization rule applied to `verify_user_qr_code` — and the `self_serve`/`ignore_user_centric_signups`/`pcp_v3` values snapshotted earlier in `do_signup` — are not guaranteed to be the same values that were in effect when the signup/session started. There is no freeze, snapshot-at-start, or version pinning of the authorization-relevant configuration for the duration of an in-flight signup, exactly mirroring the reported `setWhitelistReserve()` pattern where a rule governing an in-progress commitment can be rewritten before the commitment is finalized.

### Impact Explanation
If the backend pushes a config change (e.g., toggling `user_qr_validation_use_only_operator_location` or `user_qr_validation_use_full_operator_qr`, intentionally or due to an operational mistake/misconfiguration/compromised management-backend response) while a signup session is between QR scanning and finalization, the authorization check applied to that specific user's QR code can differ from the rule that was active when the operator/session was initiated. This can result in a user being authorized under a different (potentially weaker) validation rule than the one the operator/session was supposed to enforce, or a legitimate session being invalidated by a rule change it never agreed to. Because there is no re-validation or abort of an in-progress signup when the authorization rule set changes, a signup can silently straddle two different rule regimes — this is a state-consistency/authorization-integrity flaw of the same class as the reported issue, applied to signup authorization rather than fund allocation. It is Medium risk: it does not by itself force unauthorized enrollment, but it removes the guarantee that a single signup is validated under one fixed, known-good rule set.

### Likelihood Explanation
This requires the management backend's config endpoint to return different `user_qr_validation_*` (or other authorization-impacting) values within a signup's duration — plausible given the config is polled every 10 seconds and signups routinely last much longer (QR idle wait, biometric capture, pipeline, PCP upload). No attacker-controlled input is needed on the orb side to trigger the race; only a backend-side config change during an active session, making this a real operational condition rather than a purely theoretical one. Likelihood is Low-Medium given it depends on backend-side timing of config pushes rather than a directly attacker-triggerable path from an unprivileged user.

### Recommendation
Snapshot the authorization-relevant configuration (particularly `user_qr_validation_use_full_operator_qr`, `user_qr_validation_use_only_operator_location`, `self_serve`, `ignore_user_centric_signups`, `pcp_v3`) once at the start of a signup (e.g., inside `start_signup`/`do_signup`) and thread that fixed snapshot through the entire signup instead of re-reading `orb.config.lock().await` at each usage site (`verify_user_qr_code`, later parts of `do_signup`). Alternatively, defer/skip the background `config_update()` while `signup_flag` is set (the flag already exists and is checked elsewhere, e.g. `src/plans/mod.rs:367,371`), applying the queued config only after the signup concludes.

### Proof of Concept
1. Start `orb-core.rs`/`MasterPlan::run`, which spawns the `Observer`/`DefaultPlan::config_update` background task with `CONFIG_UPDATE_INTERVAL = 10s` (`src/consts.rs:88`, `src/brokers/observer.rs:187-205,475-480`).
2. Operator scans an operator QR code; a signup session begins and `do_signup` snapshots `Config` (`src/plans/mod.rs:497-506`), e.g. with `user_qr_validation_use_only_operator_location = false`.
3. While the orb is still waiting for/validating the user QR code (`idle_scan_user_qr_code` / `scan_user_qr_code` → `verify_user_qr_code`, which may take well over 10 seconds in practice), the management backend's `/api/v1/orbs/{id}` response changes `UserQrValidationUseOnlyOperatorLocation` to `true`.
4. The background task in `config_update()` downloads the new config and overwrites the shared `Arc<Mutex<Config>>` (`src/brokers/observer.rs:196-202`), regardless of the in-progress signup.
5. `verify_user_qr_code()` re-reads `orb.config.lock().await` at line `src/plans/mod.rs:1588-1592` and now applies the new rule (`use_only_operator_location = true`) to validate the same session — a different authorization check than the one that was active when the session/operator QR was accepted, with no detection or abort of the mismatch.

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,

                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }
