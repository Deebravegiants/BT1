Confirmed root cause: `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from HTTP headers that are never included in the HMAC-signed material [2](#0-1) . `HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the HMAC [3](#0-2) , so `Registry.process` dispatches to a handler and passes an unauthenticated `shop` value straight into `WebhookMetadata` after only validating the body's HMAC [4](#0-3) .

### Title
Webhook `shop`/`topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The gem's webhook HMAC validation authenticates only the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values, which are the fields host applications use to attribute and route webhook data to a specific tenant, are read from HTTP headers that are completely outside the HMAC's protected input.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) . `ShopifyAPI::Utils::HmacValidator.validate` computes the signature over exactly that signable string and compares it to the `hmac` header via `OpenSSL.secure_compare` [5](#0-4) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all derived from separate, unsigned headers (`shopify-shop-domain`, `shopify-topic`, etc.) [2](#0-1) .

`Registry.process` only gates on `Utils::HmacValidator.validate(request)` before trusting `request.shop` and `request.topic` to select a handler and construct `WebhookMetadata` [4](#0-3) . Because `api_secret_key` is shared by the app across every shop that installs it (it is not per-tenant), any merchant who installs the app on their own store legitimately receives real webhook deliveries whose `raw_body` + `hmac` pair is valid under that shared secret. That merchant can then replay the exact same `raw_body`/`hmac` pair directly to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain (and/or the `x-shopify-topic` header for a different topic). `HmacValidator.validate` will still succeed because it never inspects those headers, and the app will process attacker-supplied body content as though it originated from, and belongs to, the victim tenant.

Equality that should hold but doesn't: `shop attributed to the processed webhook data == shop that produced the HMAC-verified bytes`. In this code path, the `shop` used downstream is taken from an unauthenticated header, not from anything bound to the verified body.

### Impact Explanation
This is a cross-tenant identity binding break: a merchant/attacker with no elevated privileges beyond installing the app (an unprivileged action open to any Shopify merchant) can inject data attributed to a different tenant into any host application built on this gem's webhook-processing API, since the gem's `WebhookMetadata.shop` value handed to the handler is unauthenticated. Any host app that uses `data.shop` from `ShopifyAPI::Webhooks::WebhookMetadata` to look up/update per-tenant records (the intended and expected usage pattern shown in the gem's own docs) is exposed to cross-tenant data confusion/injection. This matches the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker must install the app on a shop they control to obtain genuine `raw_body`/`hmac` pairs (since they don't know `api_secret_key` directly), then replay the raw HTTP POST with a modified `shop-domain` (and optionally `topic`) header directly to the app's public webhook endpoint. No secret material needs to be extracted — only a normal, legitimate app installation is required, which is within reach of any unprivileged internet user for a public app.

### Recommendation
Include `shop`, `topic`, and any other header fields the host application relies on for identity/dispatch decisions in the HMAC-signed material (e.g., construct the signable string from a canonical combination of headers and body), or otherwise cryptographically bind these header values to the request before exposing them via `WebhookMetadata`. At minimum, document prominently that `shop`/`topic` are unauthenticated and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against a known/stored shop record before writing data).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, becoming a legitimate, authorized webhook recipient for that shop.
2. Shopify delivers a genuine webhook to the app's endpoint, e.g. `orders/create` with body `B`, headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: H` (computed by Shopify with the app's shared `client_secret` over `B`).
3. Attacker captures `(B, H)` (they control their own network path/app server, or intercept before their own app logic consumes it).
4. Attacker crafts a new raw HTTP POST directly to the same app webhook endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only checks presence, not binding) [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [7](#0-6) .
6. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [8](#0-7) , and any host application that stores/updates data keyed by `data.shop` now attributes attacker-controlled order/customer data to the victim tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
