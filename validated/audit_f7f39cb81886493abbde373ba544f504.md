### Title
Accrual `MathOverflow` permanently freezes an oversized market before the index cap engages - (File: common/src/rates/index.rs)

### Summary
The borrow index is nominally capped at `MAX_BORROW_INDEX_RAY` (1e36 raw), but every accrual first computes `borrowed * new_borrow_index` inside `calculate_supplier_rewards` via `scaled_to_original`, which panics with `MathOverflow` when the product exceeds `i128::MAX`. Scaled debt and the index are both monotone non-decreasing, so once the product crosses the i128 ceiling every accrual reverts forever — and every market verb accrues first. The bug class of CVE-2023-30085 (numeric overflow → denial of service) maps directly onto this path.

### Finding Description
`accrue_step` calls `calculate_supplier_rewards`, which evaluates `borrowed.mul(env, old_borrow_index)` and `borrowed.mul(env, new_borrow_index)` [1](#0-0) . `Ray::mul` ultimately runs `fp_core` mul-div, which widens to `I256` but still panics with `MathOverflow` when the *result* does not fit `i128` [2](#0-1) . The cap in `update_borrow_index` is applied only after this multiplication [3](#0-2) , so the value ceiling (~1.7e38) is hit before the index ceiling. `global_sync` runs `accrue_chunk` unconditionally at the head of every pool mutation [4](#0-3) , and the shipped test demonstrates the freeze: after the cliff, `try_update_indexes`, `try_withdraw`, and `try_repay` all revert with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` [5](#0-4) .

An unprivileged attacker reaches this by calling `supply` and `borrow` on the controller: open a whale-sized debt position in a high-decimal market at high utilization (the test uses ~1e36 raw units, 98% utilization, XLM steep curve) [6](#0-5) , then let interest compound at up to `MAX_BORROW_RATE_RAY` (2 RAY, ~200% APR per chunk) until `borrowed * index` overflows. Since scaled debt shares never shrink and the index never decreases, no parameter the attacker controls needs to persist — the freeze is self-sustaining once the threshold is crossed.

### Impact Explanation
Permanent freezing of funds: once `borrowed * borrow_index` exceeds `i128::MAX`, `global_sync` reverts on every entrypoint touching that market — `withdraw`, `repay`, `borrow`, `supply`, `net_settle`, `seize_positions`, `claim_revenue`, `flash_loan`, and `recapitalize` (which itself can overflow) are all dead. Suppliers' principal and unclaimed revenue are locked indefinitely, borrowers cannot deleverage, and liquidations cannot execute even as positions deteriorate — effectively insolvency-by-freeze for that market. `clean_bad_debt`/socialization also accrues first, so it cannot rescue the book.

### Likelihood Explanation
Low-to-moderate. It needs (a) a listed market with caps and decimals permitting a scaled debt of ~1e29+ raw ray (large, but `calculate_scaled_cap` saturates rather than bounds supply below this), and (b) sustained near-max utilization so the index compounds at the steep segment for several years before the i128 product overflows. The attacker must post real collateral for the borrow, but gains nothing beyond griefing — there is no profit motive, which lowers likelihood. The codebase's own threat model acknowledges "finite RAY value capacity can be exhausted before the index ceiling," indicating the authors treat it as a residual risk rather than eliminated [7](#0-6) .

### Recommendation
Apply the `MAX_BORROW_INDEX_RAY` clamp *before* computing debt values in `calculate_supplier_rewards`, or clamp `new_borrow_index` inside `accrue_step` prior to `scaled_to_original`. Alternatively, make `scaled_to_original` saturate at `i128::MAX` for accrual-only paths (as `protocol_fee_shares` already does for `supplied` growth [8](#0-7) ), so accrual sticks at the ceiling instead of reverting. Enforce `max_utilization` caps and per-market caps sized so `cap * MAX_BORROW_INDEX_RAY / RAY` stays within `i128` — `require_cap_within_asset_domain` should take the index ceiling into account, not just the asset domain.

### Proof of Concept
Reproduced by the existing test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321): supply 1e9 whole 18-decimal tokens, borrow 98% of it, advance time in 1-year steps; `try_update_indexes_for(["BIG18"]` fails with `MATH_OVERFLOW` within 40 years while `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `try_withdraw`/`try_repay` fail identically — a permanent market freeze.

pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
