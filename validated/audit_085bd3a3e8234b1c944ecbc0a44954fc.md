Audit Report

## Title
Nil-Pointer Dereference DoS in Vault Node `MethodPublicKeyGet` Handler via Unrecovered Gateway Read Loop - (File: core/capabilities/vault/gw_handler.go)

## Summary
`GatewayHandler.handlePublicKeyGet` in the vault node's gateway-message handler unmarshal-dereferences `*req.Params` without a nil check, while the gateway-side vault handler forwards `vault.publicKeyGet` requests to nodes without ever validating that `params` is present. A crafted `vault.publicKeyGet` request with `params` omitted or `null` therefore reaches the node process and triggers a nil-pointer dereference panic, and because the connector's `readLoop` dispatches handlers synchronously with no `recover()`, the panic crashes the node.

## Finding Description
`gateway.ProcessRequest` only decodes the outer JSON-RPC envelope and routes by service/method; it does not require `Params` to be present for new-style requests before calling `handler.HandleJSONRPCUserMessage`. The gateway-side vault `handler.HandleJSONRPCUserMessage` special-cases `MethodPublicKeyGet`, routing it straight to `handlePublicKeyGet` → `fanOutToVaultNodes` → `don.SendToNode`, with no `req.Params` inspection at all — unlike the secrets write/list methods, which pass through `requestProcessor.ProcessRequest` (params validation). The raw request (with `Params == nil`) is thus forwarded verbatim to the node(s).

On the node side, `connector.readLoop` decodes the incoming message into `jsonrpc.Request[json.RawMessage]` and dispatches to the registered handler synchronously, with no panic recovery. `GatewayHandler.HandleGatewayMessage` routes `MethodPublicKeyGet` directly to `handlePublicKeyGet`, which immediately does `json.Unmarshal(*req.Params, r)`. If `req.Params` is `nil`, this dereferences a nil pointer and panics. Because there is no `recover()` anywhere in this call chain, the panic is unhandled and crashes the entire node process.

This differs from the pattern used by `confidentialrelay/handler.go`'s `handleSecretsGet`, which explicitly checks `req.Params == nil` before use — demonstrating that the codebase is aware of and normally guards against this exact class of bug, but the vault node's `handlePublicKeyGet` (and its `handleSecrets*` siblings) lack that guard.

## Impact Explanation
This is a Denial-of-Service against the vault node process: an unhandled panic in the gateway connector's single per-gateway read goroutine crashes the whole Go process by default (no `recover()` present anywhere in `readLoop` or the handler chain). Since `vault.publicKeyGet` requires no prior authorization (it's explicitly carved out of the authorization pipeline both on the gateway and node side, "public key requests don't require authorization"), this is reachable without any credential, and a single malicious request can knock a subscribed vault node offline. This maps to an in-scope "Denial of Service against node process via unauthenticated gateway-facing request" impact class.

## Likelihood Explanation
High. Any actor able to send an HTTP request to the gateway's public ingress endpoint can issue `{"jsonrpc":"2.0","id":"1","method":"vault_publicKeyGet"}` with `params` omitted. Neither the gateway HTTP layer, `gateway.ProcessRequest`, nor the gateway-side vault handler's `MethodPublicKeyGet` path perform any params-presence check before forwarding to nodes, and the node-side handler dereferences the params pointer unconditionally. No authorization, allowlist membership, or prior handshake is required for this specific method.

## Recommendation
Add an explicit `req.Params == nil` check in `handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go` (returning a `UserMessageParseError`/`InvalidParamsError` response instead of dereferencing), mirroring `confidentialrelay/handler.go`'s `handleSecretsGet`. Apply the same defense-in-depth guard to `handleSecretsCreate`, `handleSecretsUpdate`, `handleSecretsDelete`, and `handleSecretsList`. Additionally, wrap the handler dispatch inside `gatewayConnector.readLoop` in a `recover()` so that any single handler bug cannot crash the entire node process, and consider adding an equivalent nil-params guard on the gateway-side vault handler's `MethodPublicKeyGet` path before forwarding to nodes.

## Proof of Concept
1. Send to the gateway's HTTP ingress: `{"jsonrpc":"2.0","id":"1","method":"vault_publicKeyGet"}` (no `params` field).
2. `gateway.ProcessRequest` decodes the envelope, routes it to the vault gateway-side `handler.HandleJSONRPCUserMessage`, which forwards the request unchanged to subscribed vault node(s) via `SendToNode` (no params validation for `MethodPublicKeyGet`).
3. Node's `connector.readLoop` decodes into `jsonrpc.Request[json.RawMessage]{Params: nil}` and calls `GatewayHandler.HandleGatewayMessage`, which dispatches to `handlePublicKeyGet`.
4. `json.Unmarshal(*req.Params, r)` panics on nil-pointer dereference.
5. No `recover()` exists in `readLoop` or the handler chain, so the panic crashes the node process.

A Go unit test reproducing this: call `GatewayHandler.HandleGatewayMessage` (or `handlePublicKeyGet` directly) with a `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` and observe the panic (`require.Panics` or equivalent), then verify no recovery mechanism exists in `connector.readLoop`.

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
