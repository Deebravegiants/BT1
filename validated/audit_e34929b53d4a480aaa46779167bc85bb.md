## Finding

The report describes Frontier's fix for a race condition where `eth_getTransactionReceipt` could return a receipt for a transaction that wasn't yet actually finalized/confirmed on-chain. The closest analog in this repo is in `OmniBridge.describeWithdrawal`, which reports a withdrawal as `"completed"` using a transaction hash that is explicitly documented as **not** the finalized on-chain hash for UTXO-chain withdrawals when running in a browser context. [1](#0-0) 

### Title
Omni Bridge reports UTXO withdrawal as "completed" using a non-final `pending_sign_id` hash that can change - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`OmniBridge.describeWithdrawal` returns `{ status: "completed", txHash }` for UTXO-chain (e.g., BTC) withdrawals using `transfer.utxo_meta?.pending_sign_id` when executed in a browser environment (`typeof window !== "undefined"`), instead of waiting for `transfer.finalised?.transaction_hash`. The code's own comment states this `pending_sign_id` "is not the finalised tx hash" and "may change if the BTC transfer fails to be submitted." [2](#0-1) 

### Finding Description
`watchWithdrawal` treats any `status: "completed"` response from a bridge as final and immediately returns the reported hash to the caller, stopping polling entirely: [3](#0-2) 

For UTXO chain withdrawals routed through `OmniBridge`, when the SDK runs in a browser (`typeof window !== "undefined"`), `describeWithdrawal` returns `status: "completed"` with `txHash = transfer.utxo_meta?.pending_sign_id` rather than waiting for the finalized hash. This breaks the equality that "status reported = on-chain outcome": the SDK is signaling `"completed"` (a terminal, on-chain-confirmed state per the `Bridge`/`WithdrawalStatus` contract used elsewhere, e.g. `waitForWithdrawalCompletion` in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` which only reports completion once `transfer_tx_hash` from a `COMPLETED` withdrawal is known) while the actual destination transaction hash is not yet finalized and, per the inline comment, can still change if the BTC transfer submission fails.

### Impact Explanation
An integrator consuming `sdk.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` in a browser context receives a terminal `"completed"` status and a `txHash` for a BTC/UTXO withdrawal that has not actually been finalized on-chain. If the integrator credits/records the withdrawal as done and the underlying BTC submission subsequently fails and is resubmitted with a different hash, the integrator's record now references a stale/incorrect hash — a status/hash misreport that can cause a double-credit or a permanently wrong record of the destination transaction, with no automatic correction mechanism since polling has already stopped. This falls under the "High" impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This code path is intentionally reachable any time the SDK is used in a browser environment (`typeof window !== "undefined"`) for a UTXO-chain (e.g., Bitcoin) withdrawal via Omni Bridge — no attacker action is required beyond the pre-existing, acknowledged rare failure mode of BTC transfer submission mentioned in the code's own comment. It is a deterministic behavior of normal operation under a known edge case (BTC submission failure/resubmission), not a hypothetical race requiring adversarial timing.

### Recommendation
Do not report `status: "completed"` for UTXO-chain withdrawals until `transfer.finalised?.transaction_hash` is available, even in browser environments. If a faster UI update is desired, expose the pending hash via a separate, explicitly non-terminal status (e.g., `"pending"` with an optional `provisionalTxHash` field) so `watchWithdrawal` continues polling until the finalized hash is confirmed, mirroring the approach used in `waitForWithdrawalCompletion` for POA bridge withdrawals.

### Proof of Concept
1. Initiate a BTC withdrawal through `OmniBridge` from a browser context.
2. `describeWithdrawal` returns `{ status: "completed", txHash: <pending_sign_id> }` before the BTC transfer is finalized (per the code path at lines 714-721 in `omni-bridge.ts`).
3. `watchWithdrawal` immediately resolves with `{ hash: <pending_sign_id> }`, and any caller (e.g., an integrator's backend crediting a user) records this as the final destination transaction.
4. If the underlying BTC broadcast subsequently fails and is retried with a different transaction hash (an acknowledged possibility per the source comment), the recorded hash no longer matches the actual on-chain outcome, and no further update/callback is issued since the SDK already reported completion.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
