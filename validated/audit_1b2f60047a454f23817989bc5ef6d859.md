### Title
POA Bridge withdrawal status matched only by `assetId`, causing status/txHash mix-up between multiple same-token withdrawals in one transaction - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves the status of a specific withdrawal by calling `findMatchingWithdrawal()`, which selects an entry from the bridge API's response solely by comparing `assetId` (`nep141:${w.data.near_token_id}`), ignoring the withdrawal's index and destination address. When a single NEAR transaction contains more than one withdrawal intent for the same token (e.g., two `ft_withdraw` intents for `usdc.omft.near` to two different destination addresses/amounts), `describeWithdrawal()` can return the wrong withdrawal's `status` and `txHash` for a given `WithdrawalIdentifier`.

### Finding Description
`describeWithdrawal` is the function the SDK uses to report the on-chain outcome of a specific withdrawal leg identified by `WithdrawalIdentifier` (built via `createWithdrawalIdentifier`, which only carries `index`, `withdrawalParams`, and `tx`) [1](#0-0) .

`describeWithdrawal` fetches all withdrawals associated with the transaction hash and then picks one using `findMatchingWithdrawal`, explicitly commented as unsorted/matched only by `assetId`: [2](#0-1) [3](#0-2) 

The comment itself states: "This means multiple withdrawals of the same token in a single transaction are not supported." That means the equality the code is supposed to preserve — *(this specific withdrawal's identifier) == (the status/txHash reported for it)* — is broken whenever two or more withdrawal intents for the same token exist in one composed transaction. Since the multi-intent architecture of the intents SDK explicitly supports composing multiple intents/withdrawals atomically in one NEAR transaction (see `signAndSendIntent`'s `composedPayloads`/multi-intent handling) [4](#0-3) , this is a realistic, reachable scenario rather than a purely theoretical one: any integrator batching multiple withdrawals of the same POA-bridged token (to different destination addresses or with different amounts) into a single transaction will get non-deterministic/incorrect per-withdrawal status resolution, because the underlying API response list is unsorted and `findMatchingWithdrawal` returns `Array.prototype.find`'s first assetId match regardless of which logical withdrawal (index) actually completed.

### Impact Explanation
This is a status/hash misreport for a withdrawal that an SDK consumer relies on to determine finality. Concretely:
- `describeWithdrawal` for withdrawal-A could return `{status: "completed", txHash: <B's txHash>}` while A is still pending or failed, and vice versa.
- An integrator that credits/refunds a user or marks a withdrawal record complete based on this status could credit the wrong withdrawal as complete, potentially reporting the wrong destination/txHash pairing to a user, or prematurely closing out a pending withdrawal while the other one silently remains unresolved.
- This matches the "status or hash misreport making an integrator credit or refund twice" impact class described in scope, since two same-token withdrawals in one tx can have their completion status/txHash swapped.

The severity is bounded by the precondition that multiple same-token withdrawals must be batched in a single transaction — this is a "Medium/High" style analog rather than "Critical" (no direct fund debit is caused by the SDK itself; the underlying chain transfer proceeds correctly, only the SDK's/consumer's *reporting* of which specific withdrawal succeeded is wrong).

### Likelihood Explanation
The intents SDK explicitly supports composing/atomically executing multiple withdrawal intents in a single signed transaction, so an integrator building batch withdrawals for the same token (a common real use case — e.g. a service processing a queue of pending same-token payouts and batching them for gas efficiency) will trigger this path without any malicious behavior; it is a self-inflicted-by-legitimate-usage bug, not one requiring an attacker. The comment in the code confirms the developers were already aware this case was unhandled, showing it's a known-but-unfixed gap rather than a purely theoretical concern.

### Recommendation
Disambiguate withdrawal matching beyond `assetId`:
- Match using an additional discriminator that uniquely identifies each withdrawal leg from the bridge API response and from `WithdrawalIdentifier.withdrawalParams` (e.g., destination address, amount, and/or memo), and fall back to sorting both the SDK's per-token withdrawal amounts and the API's per-token entries into corresponding order (as suggested in the existing comment) before matching by `index`.
- If the POA API cannot yet disambiguate reliably (as noted "POA API doesn't currently support this case either"), the SDK should detect the ambiguous case (more than one API entry matching the same `assetId` within a transaction) and return an explicit unresolved/ambiguous status rather than silently picking `Array.find`'s first match, to avoid delivering a false "completed" status paired with the wrong `txHash`.

### Proof of Concept
1. Build a NEAR transaction containing two `ft_withdraw` intents for the same POA-bridged token (`usdc.omft.near`) with different `receiver_id`/amounts, executed atomically via the intents SDK's multi-intent composition (`signAndSendIntent` with `signedIntents`) [4](#0-3) .
2. After the transaction lands, call `describeWithdrawal` for withdrawal index `0` and index `1` using their respective `WithdrawalIdentifier`s created via `createWithdrawalIdentifier` [1](#0-0) .
3. Because `getWithdrawalStatusWithRetry` returns all withdrawals tied to `tx.hash` in an unsorted list, and `findMatchingWithdrawal` filters purely by `assetId` [5](#0-4) , both `describeWithdrawal` calls can resolve to the *same* API entry (e.g., always the first same-asset entry in the array), reporting identical/incorrect `status`/`txHash` for what are two distinct withdrawals with different destinations and amounts.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
