### Title
Webhook `shop-domain`, `topic`, `api_version`, and `webhook_id` headers are trusted for tenant dispatch without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches to app-defined handlers using the `shop`, `topic`, `api_version`, and `webhook_id` values taken from unauthenticated HTTP headers. Because those header values are not part of the signed content, an attacker who can obtain one genuine, validly-signed webhook (e.g., from any shop that has the app installed) can replay that exact body with a forged `x-shopify-shop-domain`/`shopify-shop-domain` header to make the gem accept the payload as belonging to a different, victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes/compares the HMAC exclusively over that signable string: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, none of which are included in the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC and then uses `request.shop` (and `request.topic`) — unauthenticated header values — directly to build the `WebhookMetadata` passed to the app's handler, which is the trust boundary the host application relies on to attribute the webhook payload to a tenant: [4](#0-3) 

The identity binding that should hold is: `shop authenticated (bytes covered by HMAC) == shop acted on (header parsed and handed to handler)`. Here, the HMAC only authenticates `body`, while the shop identity used for tenant dispatch comes from a header that is verified to be *present* (`Request#initialize` only checks the header exists) but never verified to be *the byte range the HMAC signs over*: [5](#0-4) 

### Impact Explanation
This qualifies as cross-tenant access under the Critical bucket: any user who can trigger a legitimately signed webhook for one shop (e.g., their own store where the app is installed, or any store willing to trigger webhook activity) can capture that valid `(body, hmac)` pair and replay it to the app's webhook endpoint while swapping the `shop-domain` header to point at an arbitrary victim shop. Since `WebhookMetadata.shop` is what host applications use to select the shop's session/data record when processing the event, the app may write, cache, or act on data under the wrong tenant's identity, and the webhook is accepted as authentic because HMAC validation only checked the (attacker-replayable) body bytes, not the header the app trusts for tenant identity.

### Likelihood Explanation
Obtaining one valid signed webhook body/HMAC pair is trivial for anyone who has (or can create) a shop with the app installed, since webhooks fire on ordinary shop events. Replaying the same body with a modified shop-domain header requires no cryptographic material and no access to `api_secret_key`. The main constraint is that the payload content (order data, customer data, etc.) will be the attacker's own shop's data rather than the victim's, so the practical damage is scoped to what a handler does when told "this order/customer JSON belongs to shop X" — for handlers that create/update local records keyed by `shop`, this can inject or overwrite data under a victim tenant's identity.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signed content (or otherwise cryptographically bind them to the body), or have `Registry.process` cross-check that the header-derived shop actually corresponds to a shop with a matching active installation/session before invoking the handler, rather than trusting header values that sit outside the HMAC's coverage.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to capture a real request with headers `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-shop-domain: attacker.myshopify.com`, body `B`.
2. Replay the exact same `B` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `B`, which is unchanged.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: parsed(B), ...))`, causing the host app's handler to process attacker-controlled data as if it originated from `victim.myshopify.com`.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
