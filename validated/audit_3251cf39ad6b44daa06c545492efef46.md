### Title
Permanent market freeze: accrued debt/supply value overflows `i128` inside accrual, trapping all deposits — (`common/src/rates/scaling.rs` / `common/src/rates/simulate.rs`)

### Summary
The MySQL report is a remotely-triggerable crash yielding a complete denial of service. The direct analog in XOXNO Lending is an arithmetic crash in interest accrual: `accrue_step` computes `borrowed_original = borrowed * borrow_index` and `supplied_original = supplied * supply_index` via `Ray::mul`, which panics with `GenericError::MathOverflow` once the RAY-scaled market value exceeds `i128::MAX`. Because every unprivileged entrypoint (`update_indexes`, `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `claim_revenue`) calls `global_sync` first and `global_sync` unconditionally calls `accrue_chunk`, a single panic makes the entire market permanently uncallable — a deterministic, state-pinned crash, not a transient failure.

### Finding Description
`pool::interest::global_sync` loops `accrue_chunk` over elapsed time chunks, delegating to `common::rates::accrue_step`. The first two lines of `accrue_step` unscale the stored scaled totals:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
let supplied_original = scaled_to_original(env, supplied, supply_index);
```

`scaled_to_original` is `scaled.mul(env, index)` (`common/src/rates/scaling.rs:14-16`), and `Ray::mul` panics on `i128` overflow (`common/src/math/fp.rs`, `checked_sub_nonneg`/`mul` via `fp_core`, error `MathOverflow`).

The borrow index is capped at `MAX_BORROW_INDEX_RAY = 1e36` (`common/src/rates/index.rs:13-19`), but the cap clamps the *index*, not the *value*. With an index range of up to 10⁹× initial, a market holding enough whole-token value (≈170 billion whole units at 18 decimals per `docs/reference/formulas.md` numeric-limits table) reaches `borrowed * borrow_index > i128::MAX` or `supplied * supply_index > i128::MAX` while the index is still far below its cap. The repo's own harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` proves this: at ~98% utilization on a steep (175% max APR) curve, accrual panics inside `scaled_to_original`, `last.borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `try_withdraw_raw` and `try_repay` both revert with `MATH_OVERFLOW` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-360`).

Crucially, the panic is *sticky*: `set_borrow_index`/`set_supply_index`/`mark_accrued` never run because the panic aborts `accrue_step` before commit, so the overflowing scaled totals and index remain stored. Every future call re-enters `global_sync` and panics at the same multiply — the market is permanently frozen exactly like the MySQL hang/crash, except it never recovers. `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `claim_revenue`, `recapitalize`, and `update_indexes` all traverse this path, so no operation can advance the market or touch its pool-held tokens.

### Impact Explanation
Permanent freezing of funds and a permanently inoperable market: once `borrowed_original` or `supplied_original` overflows, no supplier can withdraw, no borrower can repay, no liquidator can seize collateral, and no governance or keeper path unblocks it (accrual precedes all of them). All token balances held by the pool for that market are irrecoverable, and any collateral/d debt positions crossing the market are frozen along with them. This maps directly to the CVE's "complete DOS" but upgraded to permanence.

### Likelihood Explanation
An unprivileged attacker can force the preconditions: supply the maximum allowed token amount (caps can reach the admitted maximum ~170 billion whole units), and borrow near the utilization cap using collateral in another market (`supply` then `borrow` are caller-auth entrypoints; utilization ceilings up to 100% and rates up to 200% APR are governance-configured, and at least the XLM listing uses a steep curve). Then the freeze requires only letting interest accrue — the attacker does not even need to act again; any caller's `update_indexes` triggers the crash, and `update_indexes` is ungated. The index grows monotonically (`INV-IDX-01`), so once near the boundary the cliff is guaranteed to be crossed. The main mitigating factor is capital cost and the accrual time needed at the steep segment (the harness reaches the cliff by advancing time year-by-year), plus the requirement that a market supports ≥18-decimal assets at whale scale caps — governance-set parameters, but within admitted ranges rather than a misconfiguration.

### Recommendation
Make accrual fail-safe instead of panicking:
- In `accrue_step`/`global_sync`, compute `borrowed_original`/`supplied_original` with saturating or checked arithmetic; on overflow, clamp the index advance (e.g., pin borrow index at `MAX_BORROW_INDEX_RAY` and stop accruing) rather than reverting.
- Alternatively, cap admitted supply/borrow amounts so that `scaled_total * MAX_INDEX` cannot exceed `i128::MAX` — i.e., enforce `scaled ≤ i128::MAX / MAX_*_INDEX_RAY` at entry, matching the bound the docs admit is missing.
- Emit an event or flag when a market hits the value ceiling so keepers can observe the frozen-equivalent state.

### Proof of Concept
Mirrors the existing harness test:
1. Attacker calls `supply` on an 18-decimal market (`BIG18`) with `principal = 10^9 * 10^18` raw (caps lifted to max), then `supply` collateral in a second market and `borrow` ~98% of `BIG18` — all caller-auth, no privilege.
2. Wait while `last_timestamp` drifts; each chunk compounds at up to 175% APR on the steep curve.
3. Anyone calls `pool`/`controller` `update_indexes` (ungated) for `BIG18`. `global_sync → accrue_chunk → accrue_step → scaled_to_original(borrowed, borrow_index)` panics with `MathOverflow` before the index cap engages.
4. Every subsequent `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `claim_revenue`, `recapitalize`, and `update_indexes` on that market re-panics at the same multiply. Funds are permanently locked. Confirmed by `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`, which asserts `MATH_OVERFLOW` on `update_indexes`, `withdraw`, and `repay` after the cliff.

Caveat: the cliff requires whale-scale totals and months-to-years of accrual at high utilization; it is a documented arithmetic limit in `docs/reference/formulas.md` ("Value overflow can occur before the index ceiling and block repayment/withdrawal"), which may be treated as a known limitation, but the code provides no guard, alarm, or recovery path, so the permanent-freeze impact stands as reported.
