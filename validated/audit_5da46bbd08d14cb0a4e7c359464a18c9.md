### Title
Webhook `shop` (tenant identity) header is not covered by the HMAC signature, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` validates a webhook's authenticity using an HMAC computed over the raw request body only, while the `shop` (tenant identity) is read from an HTTP header that is excluded from the signed payload. Any actor capable of producing (or replaying) one valid HMAC/body pair for the app's shared `api_secret_key` can attach an arbitrary `shopify-shop-domain` header and have `ShopifyAPI::Webhooks::Registry.process` accept it as authentic for a different tenant.

### Finding Description
The bug class from the external report is: an operation trusts an identity/ownership field that is not actually covered by the cryptographic binding used to authenticate the request (burn targets `msg.sender`, a value never verified to hold the tokens, instead of `address(this)`, the value that actually does). The equality that should hold is:

`bytes verified by HMAC == bytes the code treats as authoritative for tenant identity`

In `ShopifyAPI::Webhooks::Request`, the value fed into the HMAC comparison is only the raw body: [1](#0-0) 

But the `shop` attribute, which the library treats as the tenant identifier for the webhook, is parsed straight from an attacker-controlled HTTP header, with no cryptographic tie to the signature: [2](#0-1) 

`Registry.process` verifies only the HMAC of the body, then immediately hands the unauthenticated `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to the app's webhook handler as trusted metadata: [3](#0-2) 

Because `Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for `Webhooks::Request` that string is `@raw_body` alone, the header set (`shop`, `topic`, `webhook_id`, `api_version`) is never part of the signed material: [4](#0-3) 

Since the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every merchant/tenant that installs the app, a valid `(body, hmac)` pair generated for tenant A's webhook delivery remains cryptographically valid no matter which `shop-domain` header is later attached to it. An attacker who operates their own Shopify store with the same app installed can legitimately receive a real Shopify webhook (valid body + valid HMAC for their own shop), then resend that exact body/HMAC pair to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop. `HmacValidator.validate` will pass (it only checks the body against the secret), and `Registry.process` will dispatch the handler believing the event originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: the `shop` value delivered to the host application's handler is not bound to the authenticated bytes, so an attacker-controlled shop can inject events that are processed under a different shop's identity. Any host application logic keyed off `WebhookMetadata#shop` (loading that shop's session/access token, updating that shop's records, etc.) is exposed to cross-tenant confusion/access — this maps to the "cross-tenant access" Critical impact category, since the identity binding (HMAC-authenticated bytes vs. bytes trusted as the tenant) is exactly the class of break the rules call out.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on their own store (a normal, unprivileged action available to any merchant/developer), capture one legitimate webhook delivery Shopify sends them, and replay it with a modified `shop-domain` header against the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the target's infrastructure is needed, and the flow uses only the gem's documented `Registry.process` / `Webhooks::Request` API as intended.

### Recommendation
Bind the tenant-identifying fields into the authenticated payload before trusting them, e.g. include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise cryptographically bind them, mirroring how Shopify's own webhook signing scheme is documented), or require the caller to independently corroborate `request.shop` against a known/authorized shop for the delivery before invoking the handler.

### Proof of Concept
1. Install the target Shopify app on attacker-owned store `attacker.myshopify.com`; Shopify sends a legitimate webhook: body `B`, header `shopify-shop-domain: attacker.myshopify.com`, header `shopify-hmac-sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends the same `B` and `H` to the app's webhook endpoint but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header successfully (headers are only checked for presence, not binding to the HMAC) [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` (`B`) only and compares it to `H` — this passes because `B` and `H` are the untouched legitimate pair [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim.myshopify.com"`, even though the event never originated from that shop [7](#0-6) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
