The docs explicitly state `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (docs/usage/webhooks.md L125), and the `data.shop` field is documented simply as "The shop domain of the webhook" (docs/usage/webhooks.md L14) with no caveat that it is unauthenticated — so the gem itself presents this field as verified/trustworthy tenant identity, which it is not.

### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing shop-identity spoofing on otherwise-valid webhook requests - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authenticated once `Utils::HmacValidator.validate(request)` passes, and then forwards `request.shop` to the app's handler as the trusted tenant identifier. However, the HMAC is computed and verified over the raw body only — the `shop-domain` header is never part of the signed content — so the shop identity delivered to the handler is not bound to the cryptographic proof that "protects" the request.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the raw body for webhooks: [2](#0-1) 

`Registry.process` gates on this HMAC check and then immediately trusts `request.shop` (read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) as the tenant identity handed to the app's handler: [3](#0-2) 

`Request#shop` simply reads the header with no cross-check against the signed payload: [4](#0-3) 

The equality the gem implicitly claims to guarantee after `process` succeeds is:
`shop delivered to handler == shop that produced/owns the HMAC-signed body`

What is actually guaranteed is only:
`HMAC(secret, raw_body) == received_hmac`

These are not the same binding. Because the shop header sits entirely outside the signed bytes, any unprivileged actor who can obtain one validly-signed webhook body (e.g., from their own store, a public webhook payload leak, or a proxy/CDN log) can replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (the body/signature pair is untouched), so `Registry.process` calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` where `shop` is attacker-controlled while `body` still legitimately validates.

### Impact Explanation
This is a cross-tenant identity confusion: the handler is documented to receive `shop` as "The shop domain of the webhook" (implying it is verified), and apps commonly use this field to route webhook data into per-shop storage/state (as shown in the gem's own documented example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`). An attacker can cause data belonging to their own controlled shop to be attributed to and processed under a victim shop's identity in the host application, without ever needing the app's `api_secret_key`, an access token, or any privileged account — satisfying the "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation requires only: (1) triggering or otherwise obtaining one genuine webhook body+HMAC pair (trivially done by installing the app on the attacker's own shop and triggering the subscribed event), and (2) replaying that raw body to the victim app's public webhook endpoint with a forged `shop-domain` header. No secret material, TLS interception, or social engineering is needed — only network access to the app's public webhook route, which is unprivileged internet exposure by design.

### Recommendation
Bind the shop identity into the value actually verified by the HMAC, or independently authenticate it, e.g.:
- Include the shop domain in the signable string used for HMAC verification (would require change on Shopify's signing side, so more practically:)
- Require callers of `Registry.process` to pass the shop derived from an authenticated source (the app's own per-shop webhook subscription record / registered `webhook_id` to shop mapping) rather than trusting the header value directly, and have `Registry.process` reject/flag when the header-derived shop does not match a known, previously-registered shop for that `webhook_id`.
- At minimum, update the documentation to explicitly state that `data.shop` is **not** authenticated by the HMAC and must not be used as a trust boundary without independent verification against the app's session/installation store.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body and its valid `x-shopify-hmac-sha256` header sent by Shopify.
2. Attacker replays this exact body and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because the HMAC only ever covered `raw_body`, which is unmodified: [5](#0-4) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the host app to process/store attacker-controlled data under the victim tenant's identity.
