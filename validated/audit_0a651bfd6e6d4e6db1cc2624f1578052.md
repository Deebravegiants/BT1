### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from unauthenticated headers while the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then hands the caller-supplied `shop-domain` (and `topic`/`webhook-id`) HTTP headers straight through to the application's handler as trusted tenant identity. Because those headers are never included in the signed content, any request whose body+HMAC pair is valid can carry an arbitrary, attacker-chosen `shop` value, breaking the binding `shop authenticated == shop the HMAC actually vouches for`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are never part of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies exactly that signable string against the secret via `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient proof of the request's authenticity, then forwards `request.shop` (the unauthenticated header) directly into `WebhookMetadata`, which is the only tenant identifier the application handler receives: [4](#0-3) [5](#0-4) 

The equality that should hold is: `shop the HMAC authenticates == shop attributed to the payload by the library`. In this implementation the HMAC authenticates only the *body bytes*; the `shop` field is parsed but never bound into that proof, so the equality does not hold.

### Impact Explanation
Any actor able to obtain one validly-signed webhook body for the shared app secret (e.g., a merchant who installs the app themselves and triggers a normal webhook to their own endpoint) can replay that exact body+HMAC pair while substituting the `x-shopify-shop-domain` header for a different, victim shop. `Registry.process` will still consider the HMAC valid (it only checks the body) and will invoke the registered handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain. Any application that uses this `shop` field to route data into per-tenant storage (which is exactly what `WebhookMetadata` is designed for) will attribute attacker-controlled webhook content to another tenant - a cross-tenant data-integrity/access issue reachable purely through this gem's own webhook-verification code path (`Registry.process` → `HmacValidator.validate` → `Request#shop`).

### Likelihood Explanation
Likelihood is high for any adopter that relies on this gem's webhook signature verification as the sole authentication mechanism for the `shop` field (which is the documented usage pattern - the library exposes no other way to authenticate the `shop-domain` header). Because Shopify webhooks for a given app are all signed with the same app secret regardless of which shop sent them, any shop that has installed the app can generate a validly-signed body, and the header spoofing itself requires no cryptographic material at all since headers aren't covered by the signature.

### Recommendation
Bind the tenant-identifying fields into the authenticated data instead of only signing the body: e.g., include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (mirroring the OAuth `AuthQuery#to_signable_string`, which already includes `shop` in its signed parameters at `lib/shopify_api/auth/oauth/auth_query.rb:34-43`), or otherwise cryptographically bind the header values to the payload before trusting them, so that `Registry.process` cannot be fed a validly-signed body with an attacker-controlled shop identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or is otherwise able to trigger any real webhook delivery to an endpoint they control), and captures a legitimate delivery: raw body `B` with header `x-shopify-hmac-sha256: H` (H = HMAC-SHA256(app_secret, B)) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and signature `H` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC over `B` only (`to_signable_string` returns `@raw_body`) and it matches `H` - validation passes.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, so the application processes attacker-controlled data under the victim shop's identity, despite no cryptographic proof that `victim-shop.myshopify.com` ever sent anything.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
