### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable payload from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers. `Registry.process` validates only the body's HMAC and then trusts the header-derived `shop` when building `WebhookMetadata` passed to the host app's handler, breaking the binding between "HMAC-authenticated payload" and "shop the payload is attributed to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates the HMAC over the signable string (i.e., the body) via `Utils::HmacValidator.validate`, and then, if valid, constructs `WebhookMetadata` using `request.shop` taken from the (unsigned) header: [3](#0-2) 

`Utils::HmacValidator.validate_signature` confirms this: it only compares `verifiable_query.hmac` against a signature computed from `verifiable_query.to_signable_string` (the body), never incorporating the `shop` header: [4](#0-3) 

The identity binding the gem is supposed to enforce is: `shop the HMAC authenticates == shop the handler acts on`. Here that equality does not hold — the HMAC authenticates only the body bytes, while the `shop` (and `topic`/`webhook_id`/`api_version`) fields that the host application uses to route/attribute the webhook are taken from headers that are never covered by that signature.

### Impact Explanation
An attacker who controls or intercepts any single legitimately-signed webhook delivery (e.g., a webhook fired for a shop they own, or a captured request) can replay it to the app's webhook endpoint after rewriting the `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header to name a different, victim shop. Because the HMAC only covers the raw body, `HmacValidator.validate` still succeeds, and `Registry.process` forwards `WebhookMetadata` with the attacker-chosen `shop` to the app's handler as if the event genuinely originated from the victim tenant. Since host applications commonly key session/data lookups off `WebhookMetadata#shop` (e.g., app uninstall handling, GDPR redact handlers, order/customer processing), this allows cross-tenant data confusion/injection — data attributed to, or actions taken against, the wrong merchant tenant.

### Likelihood Explanation
Exploitation requires only a single valid webhook body+HMAC pair (from any shop, including one the attacker legitimately controls, since app installers can trigger many webhook types themselves) and the ability to POST an HTTP request with attacker-controlled headers to the app's public webhook endpoint — no access token, `api_secret_key`, or privileged account is needed. This is a purely unauthenticated-network-request attack against the gem's webhook processing.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived shop to the signed body before it is used to build `WebhookMetadata`. At minimum, `Registry.process` should independently corroborate `request.shop` against a trusted source (e.g., cross-check with the resolved session for that shop) rather than trusting it solely from an unauthenticated header.

### Proof of Concept
1. Attacker installs the app on shop `attacker-shop.myshopify.com` (or otherwise obtains one valid webhook delivery) and captures a webhook POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker sends a new POST to the app's webhook endpoint reusing body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Request#to_signable_string` returns `B`; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(secret, B)` and finds it equal to `H`, so validation passes (`lib/shopify_api/utils/hmac_validator.rb`, lines 26-31).
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled `shop` header (`lib/shopify_api/webhooks/registry.rb`, lines 188-200), and the handler processes the payload as belonging to `victim-shop.myshopify.com`.
