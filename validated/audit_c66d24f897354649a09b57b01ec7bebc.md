### Title
Global, single `challengePeriod` on `EvmHost` cannot express per-source-chain fraud-detection windows - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost` stores exactly one `challengePeriod` value in `HostParams` that is applied uniformly to every whitelisted source `StateMachine` accepted by the host, even though the ISMP protocol's own design (pallet-ismp) models the challenge period as a per-`StateMachine` value (`BTreeMap<StateMachine, u64>` / `challenge_period(state_machine: StateMachineId)`). This mirrors the reported oracle bug class: a single timing threshold is forced onto multiple independent trust domains that legitimately require different values, so operators must pick a single compromise value — and any value that is safe/short enough for a fast state machine is necessarily insufficient for a state machine that needs a longer fisherman/veto window.

### Finding Description
`HostParams.challengePeriod` is a single `uint256` field: [1](#0-0) 

It is exposed as a single global getter with no state-machine argument: [2](#0-1) 

and this single value is used identically for every message class and every source `StateMachineId` in `HandlerV2`: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

By contrast, the ISMP protocol's canonical (pallet-ismp / core) design deliberately keys the challenge period by `StateMachine`/`StateMachineId`, because different source chains are expected to need different challenge windows: [7](#0-6) [8](#0-7) [9](#0-8) 

The `challengePeriod` is not a consensus-finality parameter — it is the window during which a fisherman/relayer can detect and veto a fraudulent state commitment before it is trusted for dispatching requests/responses/timeouts (see the byzantine-detection logic that races against this window): [10](#0-9) [11](#0-10) 

`HostParams.stateMachines` is an array, meaning a single `EvmHost` explicitly whitelists commitments from multiple distinct source `StateMachineId`s: [12](#0-11) 

Because `EvmHost` has only one `challengePeriod` field for all of these whitelisted state machines, an admin/governance update that sets a challenge period appropriate for one connected chain (e.g. a low-risk, fast, well-monitored chain) is silently applied to every other connected chain as well — including ones for which that window is too short to give fishermen enough time to detect and veto a forged commitment before `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, or `handleGetRequestTimeouts` treat that commitment as final and dispatch it.

### Impact Explanation
If the single `challengePeriod` is tuned (via governance/`updateHostParams`) to suit the least conservative connected state machine, every other state machine sharing that host effectively loses part or all of its intended fraud-detection buffer. A relayer that manages to get a forged/invalid `StateCommitment` accepted (e.g. through provider collusion, RPC compromise, or any weakness in the byzantine-veto pipeline) has less time than the protocol's own design intends before that state can be used to dispatch incoming requests/responses or process timeouts — i.e., "unsound state commitment" being trusted/acted upon. This can result in unauthorized dispatch of application-level requests/responses or improper timeout processing against one of the multiple state machines sharing the host, which the protocol's own multi-state-machine `challenge_periods: BTreeMap<StateMachine, u64>` model was explicitly designed to prevent.

### Likelihood Explanation
Any `EvmHost` deployment that whitelists more than one `StateMachineId` (which the `stateMachines` array is explicitly built to support) is affected as soon as those state machines have differing appropriate challenge/veto windows — a routine configuration choice, not a malicious-admin scenario, since governance is simply constrained by the contract's data model to one value for all connected chains.

### Recommendation
Change `EvmHost`'s `challengePeriod` from a single `uint256` to a mapping keyed by `stateMachineId` (mirroring `modules/ismp/core/src/host.rs`'s `challenge_period(state_machine: StateMachineId)` and the `challenge_periods: BTreeMap<StateMachine, u64>` design), and update `HandlerV2.sol`'s four call sites (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) to look up the challenge period for the specific `stateMachineId` referenced by each proof height, instead of a single host-wide value.

### Proof of Concept
1. Governance/admin calls `updateHostParams` on an `EvmHost` that whitelists two source state machines, A (needs a 6-hour veto window for its fisherman monitoring cadence) and B (a fast chain, safe with a 10-minute window), via a single `HostParams.challengePeriod`. [13](#0-12) 
2. Because only one value can be set, the operator sets `challengePeriod = 10 minutes` to keep messages from chain B fast.
3. A forged/invalid state commitment is stored for chain A (e.g., through a relayer/provider fault the byzantine monitor hasn't yet caught, per `tesseract/messaging/*/src/byzantine.rs`).
4. After only 10 minutes (chain B's safe window, but far short of chain A's required detection window), `handlePostRequests`/`handleGetResponses` for chain A pass the `challengePeriod` check and dispatch requests/responses derived from the unsound commitment, before fishermen for chain A have had their intended opportunity to veto it. pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
