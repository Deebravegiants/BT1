### Title
Webhook `shop-domain`, `topic`, `webhook-id` and `api-version` headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by calling `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `request.to_signable_string` and compares it to the `hmac` returned by the request object. [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body (`@raw_body`) - it does not include any of the Shopify-supplied headers: [2](#0-1) 

However, `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from unauthenticated HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-api-version`, `x-shopify-webhook-id`): [3](#0-2) 

These header-derived values are then handed directly to the host application's webhook handler as trusted, verified metadata: [1](#0-0) [4](#0-3) 

This breaks the identity binding the report's bug class targets: the field acted upon (`shop`, used by host apps to select which tenant/session/access-token record a webhook payload belongs to) is not the field cryptographically bound by the HMAC (only the raw body is). In equality terms, the gem implicitly assumes `header.shop-domain == hmac_signed_shop`, but the actual guarantee provided is only `hmac_signed_bytes == raw_body`, with `shop-domain` completely outside that signed byte range.

### Impact Explanation
Any unprivileged internet user who legitimately controls one Shopify shop (e.g., by installing the target app on a shop they own, or by capturing/replaying a webhook they legitimately received for their own shop) obtains a raw body + valid HMAC pair for that body. Because the HMAC never covers the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers, the attacker can freely rewrite those headers - for example, changing `x-shopify-shop-domain` from their own shop to a victim shop's domain, or changing `x-shopify-topic` to a more sensitive topic - while keeping the same valid HMAC digest, since `HmacValidator.validate` only checks the body.

Any app built on this gem that trusts `WebhookMetadata#shop` (or `#topic`/`#webhook_id`) to select which merchant/tenant record, credential, or business logic branch to act on - which is exactly the intended and documented use of this field per `docs/usage/webhooks.md` and the `WebhookHandler` interface - can be tricked into processing forged, cross-tenant webhook data as if it came from a different shop than the one that actually authenticated the request. This is a cross-tenant identity-binding failure consistent with the "Critical - cross-tenant access" impact class, since the gem itself asserts the delivered `WebhookMetadata` (including `shop`) has been HMAC-verified when in fact it has not.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on their own shop (or observe one legitimate webhook delivery, e.g., via a mandatory compliance webhook or by triggering an event in their own store) - no access token, `client_secret`, or privileged account is required, only the ability to replay an HTTP POST with attacker-controlled headers and the previously-observed valid HMAC/body pair.

### Recommendation
Include the security-relevant Shopify headers (`shop-domain`/`X-Shopify-Shop-Domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable payload, or otherwise cryptographically bind them to the body before verification, so that spoofing any of these fields invalidates the HMAC. At minimum, `Webhooks::Request#to_signable_string` should not silently drop headers that downstream code treats as authenticated (`shop`, `topic`, `webhook_id`), matching how Shopify's actual webhook signing scheme is documented to work per-shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST with body `B`, and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same request to the app's webhook endpoint, keeping `body = B` and `x-shopify-hmac-sha256 = H` unchanged, but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and/or altering `x-shopify-topic`/`x-shopify-webhook-id`).
3. `Utils::HmacValidator.validate(request)` recomputes the HMAC only over `request.to_signable_string` (`@raw_body`), which is unchanged, so validation succeeds: [5](#0-4) 
4. `Registry.process` calls the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: ..., ...)`, and the host application, trusting this gem's HMAC validation, processes the forged payload as if it genuinely originated from `victim-shop.myshopify.com`. [1](#0-0)
