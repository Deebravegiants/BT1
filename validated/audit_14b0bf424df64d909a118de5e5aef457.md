### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from an unauthenticated HTTP header, while `Utils::HmacValidator` only verifies the raw request body against the HMAC. The shop attribution used by the app's webhook handlers is therefore never bound to the cryptographic signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) reads directly from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header: [1](#0-0) 

But `Request#to_signable_string`, which is what `HmacValidator` actually verifies, returns only the raw body — none of the headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a successful HMAC check as proof of authenticity for the whole request, then forwards `request.shop` (and topic/webhook_id) straight to the handler as trusted tenant context: [4](#0-3) 

This is the asymmetric-binding bug class: the field the app *acts on* (`shop`) is not the field the HMAC *covers* (`raw_body` only). By contrast, the OAuth callback verifier in `Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop`, `host`, `code`, `state`, and `timestamp` into the signed string, so tampering with `shop` there invalidates the HMAC: [5](#0-4) 

No equivalent binding exists for webhooks. Concretely, the equality the gem should guarantee is:
`shop-used-by-handler == shop-authenticated-by-HMAC`
but what it actually guarantees is only:
`raw_body-used-by-handler == raw_body-authenticated-by-HMAC`,
leaving `shop` (and other headers) completely unauthenticated.

### Impact Explanation
An app's shared `client_secret` (`api_secret_key`) is the same for every shop that installs the app. An unprivileged attacker can install the app on their own (attacker-controlled) store and thereby receive genuine webhook deliveries — bodies with valid HMAC signatures computed by Shopify using that shared secret. Because the HMAC never covers the `shop-domain` header, the attacker can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop domain. `HmacValidator.validate` still succeeds (it only checks the body), yet `WebhookMetadata.shop` passed to the handler is now the forged victim shop. This causes the host application to process, store, or act on data under the wrong tenant's identity — a cross-tenant confusion/attribution bypass, including against the mandatory `shop/redact`, `customers/redact`, and `customers/data_request` compliance topics.

### Likelihood Explanation
Any developer can obtain a free Shopify development store and install a public app to receive real, validly-signed webhook payloads for that shop, giving them a legitimate `(body, hmac)` pair signed with the app's shared secret. Forging the `shop-domain` header on the replayed HTTP request requires no special access beyond internet connectivity to the app's public webhook endpoint.

### Recommendation
Bind the tenant-identifying fields into the HMAC-verified material, or independently authenticate `shop` against the session store looked up via a value that *is* covered by the signature (e.g., verify that the `shop` returned by Shopify's `webhook_id`/topic lookup matches records created only for the shop that installed the app), and/or require the host application to cross-check `request.shop` against a shop known to have an active session/webhook registration before trusting the header for tenant attribution. At minimum, document prominently that `Request#shop`/`#topic`/`#webhook_id` are **not** authenticated by `HmacValidator.validate` and must not be used as the sole tenant boundary.

### Proof of Concept
1. Attacker registers a store `attacker.myshopify.com` and installs the target app (using the app's public `client_id`); no privileged credentials required.
2. Shopify delivers a genuine webhook to the app's endpoint: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `client_secret`), and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same request to the app's webhook endpoint but changes only `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `to_signable_string` (`= B`) — still matches `H`, since headers aren't part of the signed string: [2](#0-1) 
5. `Registry.process` passes `request.shop == "victim.myshopify.com"` to the app's handler as authenticated tenant context: [4](#0-3) 
6. The app now performs whatever webhook-triggered action (data sync, deletion, redaction, notifications, etc.) against the victim shop's tenant record, even though the actual signed content originated from the attacker's own shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
