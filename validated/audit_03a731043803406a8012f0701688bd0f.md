### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity is trusted from headers but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook only by HMAC-verifying the raw request body, then forwards the unauthenticated `shop` header value straight into the app's handler as the tenant identity. This breaks the binding `shop-domain header == HMAC-authenticated data`, allowing a replay of a legitimately-signed body under a different shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers and are never included in the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `to_signable_string` (the body) and compares it with the `hmac` header: [3](#0-2) 

`Registry.process` gates only on this body-HMAC check, and then trusts `request.shop` (plus `topic`, `api_version`, `webhook_id`) to build the `WebhookMetadata` that is handed to the app's handler as the tenant identity: [4](#0-3) [5](#0-4) 

By contrast, in the OAuth flow the analogous `shop` field *is* included in the signed payload (`AuthQuery#to_signable_string` includes `shop`), so this is not simply "how Shopify signs things" being copied consistently — the webhook path specifically omits `shop` (and other headers) from what is cryptographically verified: [6](#0-5) 

The equality that should hold is: `shop claimed in x-shopify-shop-domain == shop covered by the verified HMAC`. In this gem, `shop` is asserted (used for dispatch/tenant scoping) but is not part of the set of bytes verified — only the body is.

### Impact Explanation
An unprivileged internet user who can install the app on their own store (any public app install, no special privilege) receives real, Shopify-signed webhook deliveries: valid `(body, hmac)` pairs for topics/bodies they can trigger or predict (e.g., topics with fixed/minimal bodies). Because `HmacValidator.validate` never binds the signature to the shop header, the attacker can replay that exact `(body, hmac)` pair directly against the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Registry.process` will accept it (HMAC of body still matches) and call the app's `WebhookHandler#handle` with `WebhookMetadata#shop` set to the attacker-chosen victim domain and the attacker's own body content. If the host app uses `data.shop` to key persistence/tenant scoping (the gem's own documentation and `WebhookMetadata` struct model `shop` as the trusted tenant key for the handler), this enables cross-tenant data injection/spoofing without ever needing the app's `api_secret_key`, an access token, or TLS interception.

### Likelihood Explanation
Medium-High: no leaked credential is required, only a genuine (even free) app install to harvest a signed body/HMAC pair, plus a direct HTTP request to the app's public webhook endpoint with a forged `shop-domain` header — well within reach of a normal unprivileged internet actor. Exploitability for a given app depends on whether that app's handler trusts `data.shop` without corroborating it against installed-shop records, but the gem provides no protection against this and actively hands the unauthenticated header value to the handler as if it were verified.

### Recommendation
Include the identity fields that the handler will rely on (at minimum `shop`, and ideally `topic`/`webhook-id`) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind them to the HMAC-covered body (e.g., verify `shop` against a value looked up from the recipient's own installed-shop store keyed by webhook id/topic, not from the unauthenticated header). At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#api_version` are NOT covered by the HMAC and must not be trusted for tenant scoping without independent verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (no privilege required) and triggers a webhook topic with a body they can predict/control (e.g., an empty-body or attacker-authored payload).
2. Attacker captures the legitimate `x-shopify-hmac-sha256` header and raw body Shopify sent for that delivery.
3. Attacker sends a raw HTTP POST directly to the app's public webhook endpoint with:
   - the captured raw body (unchanged, so HMAC still matches)
   - the captured `x-shopify-hmac-sha256` header (unchanged)
   - `x-shopify-shop-domain: victim.myshopify.com` (forged)
   - `x-shopify-topic`/`x-shopify-webhook-id` of choice
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC — this passes.
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker body>, ...)`, i.e., attacker-controlled data is now processed under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
