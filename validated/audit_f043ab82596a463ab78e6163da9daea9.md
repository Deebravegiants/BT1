### Title
Webhook HMAC does not cover the shop-domain (or topic/api-version/webhook-id) headers, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields — which are read straight from unauthenticated HTTP headers — are handed to the webhook handler as trusted, verified identity for the tenant that supposedly sent the webhook. This breaks the identity-binding invariant `hmac(payload) == hmac(everything the handler trusts)`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are all pulled directly from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)`, and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` when constructing the metadata passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute `OpenSSL::HMAC.hexdigest` purely over `verifiable_query.to_signable_string`, i.e., the raw body: [4](#0-3) 

Because the shop identity that the handler acts on (`request.shop`) is never included in the signable string, the equality that should hold — `shop authenticated by HMAC == shop delivered to handler` — does not hold. Any two shops running the same app (a very common configuration, since one merchant can trivially install a public app in their own store) will receive webhooks whose HMAC is computed with the same `client_secret` but whose body can be identical or attacker-controlled for equivalent event types. A merchant who controls their own shop (an "unprivileged internet user" relative to *other* tenants of the app) can capture a legitimately-signed webhook delivered to their own store, then re-POST it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header (and optionally `topic`/`webhook-id`) rewritten to point at a victim shop. `Utils::HmacValidator.validate` still succeeds because it only checks the (unmodified) body, and `Registry.process` dispatches the handler with `shop: <victim shop>`.

### Impact Explanation
This lets one tenant of a multi-tenant app forge a webhook that the host app believes originated from a different merchant. Depending on how the app’s webhook handlers use `WebhookMetadata#shop` (typically to look up that shop's session/access token and perform actions, or to update per-shop billing/state), this can result in cross-tenant data corruption or cross-tenant actions being taken with the credentials associated with the spoofed shop — a cross-tenant access primitive squarely in the "Critical: cross-tenant access" impact bucket.

### Likelihood Explanation
Any merchant who installs the app in their own store gets validly-signed webhooks and can trivially manipulate HTTP headers on a replayed request. No access token, `client_secret`, or privileged account is required — only ordinary use of the app as any tenant. This makes the attack straightforward and reliably reproducible for apps that trust `WebhookMetadata#shop` (the pattern the gem itself provides and documents).

### Recommendation
Include the `shop`, `topic`, `api_version`, and `webhook_id` header values in the HMAC-signed material for webhooks (i.e., bind them cryptographically to the request), or otherwise document/derive the shop identity strictly from an independently-authenticated channel rather than an unauthenticated header echoed back into `WebhookMetadata`.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; capture a legitimate webhook POST (body `B`, header `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`).
2. Replay the exact same body `B` and HMAC `H` to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only [5](#0-4) , which still matches `H`, so `Registry.process` calls the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...)` [3](#0-2) , causing the app to process attacker-controlled webhook content under the victim's tenant identity.

          received_signature = verifiable_query.hmac
