This confirms the vulnerability. The webhook `Request` HMAC is validated only against `to_signable_string`, which is the raw body (`lib/shopify_api/webhooks/request.rb:36-38`), while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from unauthenticated headers (`lib/shopify_api/webhooks/request.rb:20-33`) and passed straight into the handler payload without any cross-check against the HMAC.

### Title
Webhook `shop` (and other routing fields) are excluded from the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the `X-Shopify-Hmac-Sha256` header against the raw request body via `Utils::HmacValidator.validate` [1](#0-0) . The `Request#to_signable_string` method used for that HMAC computation returns only `@raw_body` [2](#0-1) . However, `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never part of the signed material [3](#0-2) , and `shop` is forwarded unchanged into the data handed to the app's webhook handler [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop authenticated by HMAC == shop used to route/attribute the webhook payload`. Here that equality is broken. The `X-Shopify-Hmac-Sha256` signature Shopify computes is `HMAC-SHA256(api_secret_key, raw_body)` — it never incorporates the `X-Shopify-Shop-Domain` header. Since the same `api_secret_key` is shared by the app across every shop that installs it, any merchant who installs the app (an unprivileged actor with respect to other tenants) can capture one legitimate webhook delivery to their own shop — which carries a *valid* HMAC for that body — and replay the identical `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g., a victim shop). `HmacValidator.validate` verifies only the body signature and returns `true` [5](#0-4) ; `Registry.process` then trusts `request.shop` for attribution without any further check [6](#0-5) .

### Impact Explanation
This is a cross-tenant integrity/confidentiality issue: an attacker-controlled webhook body (from their own store) gets processed by the app's handler as if it belonged to a victim shop. Any app logic keyed off `WebhookMetadata#shop` (e.g., upserting shop-scoped records, triggering shop-scoped side effects, or looking up per-shop session/data using the forged `shop` value) can be manipulated to write or act on the wrong tenant's data — a cross-tenant access primitive, which the rules classify as Critical impact.

### Likelihood Explanation
Exploitation requires no leaked secrets, no TLS interception, and no elevated privileges — only the ability to install the app on one's own development/test store (a normal, unprivileged action any developer/merchant can take) to obtain one genuine `(body, hmac)` pair, followed by a single forged HTTP request with a spoofed `X-Shopify-Shop-Domain`/`shopify-shop-domain` header. The gem performs no validation that the shop header corresponds to a shop actually entitled to that HMAC.

### Recommendation
Do not trust the `shop` (or `topic`/`webhook_id`) header value for tenant attribution unless it is cryptographically bound to the request. Options:
- Include the shop domain in the HMAC-signed material (not possible to change Shopify's wire format, but the app can independently verify that `shop` corresponds to a shop with a currently valid, stored session/installation before processing).
- Require callers of `Registry.process` to cross-check `request.shop` against a known/authorized shop list (e.g., an installed-shop registry) before invoking the handler, rejecting webhooks for shops without a valid installation for this API credential context.
- Document explicitly that `HmacValidator` only proves body integrity/authenticity of the payload, not the shop attribution, so downstream handler implementations must independently verify shop legitimacy.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, and receives a legitimate webhook, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of body B>
x-shopify-shop-domain: attacker.myshopify.com
Body: B
```
2. Attacker resends the exact same body `B` and the exact same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes the shop header:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of body B>   (unchanged, still valid)
x-shopify-shop-domain: victim-shop.myshopify.com
Body: B
```
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers and `hmac` [7](#0-6) . `HmacValidator.validate` succeeds because it only checks `body` against `hmac`, both of which are unchanged and mutually consistent [8](#0-7) .
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [4](#0-3) , causing the app to process attacker-supplied data as if it originated from the victim shop.
