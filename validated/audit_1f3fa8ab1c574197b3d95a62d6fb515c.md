Audit Report

## Title
JWT replay-check TOCTOU allows concurrent replay of the same HTTP-trigger JWT - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` checks whether a JWT `jti` has already been used via `isReplay` (RLock read) and records its usage via `recordUsage` (Lock write) as two separate, non-atomically-combined critical sections, with authorized-key lookup work happening in between. Two concurrent requests carrying the identical JWT can both pass the `isReplay` check before either calls `recordUsage`, letting the same single-use token authorize two separate workflow-execute requests.

## Finding Description
`Authorize` is the authentication entry point for unprivileged `MethodWorkflowExecute` (HTTP Trigger) requests reaching the gateway via `httpTriggerHandler.authorizeRequest` → `WorkflowMetadataHandler.Authorize`. Inside `Authorize`, the sequence is: `h.jwtCache.isReplay(claims.ID)` (RLock/RUnlock), workflow-ID and authorized-key lookups, then `h.jwtCache.recordUsage(claims.ID)` (Lock/Unlock). Because these are independent lock acquisitions rather than one atomic "check-and-record," a race window exists where two goroutines processing the same JWT concurrently can both observe `isReplay == false` before either records usage, allowing both to pass authorization with the same token.

This is confirmed structurally by the `jwtReplayCache` implementation, where `isReplay` and `recordUsage` are two distinct methods each independently acquiring/releasing the mutex, in contrast to the correct atomic pattern already used elsewhere in the codebase for Vault's `RequestReplayGuard.CheckAndRecord`, which performs the existence-check and the write under a single lock acquisition. The gateway's per-`requestID` dedup in `setupCallback` happens later in the pipeline and keys on `requestID`, not the JWT `jti`, so it does not close this gap — two requests with the same JWT but different `requestID`s pass straight through.

## Impact Explanation
An attacker (or legitimate holder) of one signed, valid JWT authorizing a workflow-execute request can send it concurrently with two different `requestID`s and, if timed within the narrow race window, have both authorized as valid by the replay guard, defeating the "single-use token" invariant. This maps to the "gateway request impersonation"/replay-bypass impact class. The severity is bounded because the attacker must already hold a validly signed JWT (this doesn't grant new privilege, only lets an already-valid single-use credential be used more than once), and actual duplicate execution still depends on unrelated downstream behavior.

## Likelihood Explanation
Medium: the race requires firing two requests with an identical JWT within the small window between `isReplay`'s `RUnlock` and `recordUsage`'s `Lock`, which also includes intervening map lookups. This is realistic to trigger deliberately (parallel/synchronized delivery of the same token) and does not require any attacker-controlled callback, network manipulation, or privileged access — just concurrent submission of a token the caller already possesses.

## Recommendation
Merge `isReplay` and `recordUsage` into a single atomic check-and-record method (e.g., `checkAndRecordJTI(jti)`), guarded by one mutex acquisition, mirroring `RequestReplayGuard.CheckAndRecord`. Call this single atomic method from `Authorize` in place of the separate `isReplay`/`recordUsage` calls so the check and the effect happen within the same critical section.

## Proof of Concept
1. Register a workflow and an authorized signer key as in the existing `TestWorkflowMetadataHandler_Authorize` test.
2. Sign one JWT (`tokenString`) for a `MethodWorkflowExecute` request.
3. Launch two goroutines calling `handler.Authorize(workflowID, tokenString, req)` concurrently (optionally add a short `time.Sleep` between `isReplay` and `recordUsage` inside a test-only build to widen the window, or run repeatedly under `go test -race -count=100`).
4. Observe that both calls can return `(key, nil)` instead of exactly one succeeding and one returning `"JWT token has already been used"`, demonstrating the check-then-act race in `WorkflowMetadataHandler.Authorize` / `jwtReplayCache`.
