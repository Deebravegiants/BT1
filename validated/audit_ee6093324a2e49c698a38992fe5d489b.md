### Title
Cross-tenant webhook shop-spoofing — `shop-domain` header is trusted but not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value that is handed to the application's webhook handler from an HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`), while the HMAC signature that `Registry.process` validates is computed only over the raw request body. Because the shop identity is not part of the signed material, any party that can produce (or capture) one validly-signed webhook body for this app can replay that body with an arbitrary `shop-domain` header and have the app process it as if it originated from a different, victim tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it (via `OpenSSL.secure_compare`) to the `hmac` field of the query object: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [2](#0-1) 

but `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from attacker-controllable HTTP headers, none of which are covered by the signature: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the metadata that is handed to the app's registered handler: [4](#0-3) 

Because `Context.api_secret_key` is a single, app-wide secret shared across every installing shop (it is not per-tenant), any shop that installs the app can legitimately receive a webhook from Shopify with a valid HMAC over some body `B`. That attacker-controlled tenant can then replay the exact same `(body=B, hmac=HMAC(B))` pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still succeed because it only checks the body bytes, and `Registry.process` will invoke the handler with `shop: request.shop` set to the victim's domain and `data.body` set to attacker-controlled content — i.e., the binding `shop-header-processed == shop-that-signed-the-body` is broken.

This is exactly the class of bug described in the analog report: a field (`shop`) is acted upon by downstream logic (`WebhookMetadata.new(... shop: request.shop ...)`) without being covered by the integrity check (`to_signable_string` / HMAC) that gates that logic.

### Impact Explanation
Any handler that keys persistence, authorization, or business logic off `WebhookMetadata#shop` (the documented contract of this gem, e.g. to look up or mutate the corresponding shop's local records — the standard pattern for `orders/*`, `customers/*`, `app/uninstalled`, `shop/redact`, etc.) can be made to write, delete, or otherwise process data under a victim shop's identity using content actually chosen by the attacker's own shop. This is a cross-tenant identity-binding violation: an unprivileged party who merely installs the app on their own store (no elevated privileges, no access to the app's `client_secret`) can forge webhook traffic attributed to any other tenant of the same app.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on an attacker-owned shop to legitimately capture one HMAC-signed webhook body, and (2) sending an HTTP POST directly to the app's public webhook endpoint with that captured body/HMAC pair and a forged `shopify-shop-domain` header. No secrets, tokens, or elevated access are required beyond normal, unprivileged app installation — the webhook endpoint is inherently internet-facing.

### Recommendation
Bind the shop identity to the signed payload before trusting it: either (a) include the `shop-domain` (and `topic`/`webhook_id`) header values in the signable string used for HMAC verification, or (b) require the host application to cross-check `request.shop` against a shop that is independently known to have a currently valid, stored session/webhook registration for the given `webhook_id`/topic before acting on the payload, and document this requirement clearly for consumers of `WebhookMetadata`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to (e.g. `orders/create`) and capture the raw POST: body `B` and header `shopify-hmac-sha256: H` (valid for `B` under the app's shared `client_secret`).
2. Replay directly to the app's public webhook endpoint:
   ```
   POST /webhooks HTTP/1.1
   shopify-topic: orders/create
   shopify-hmac-sha256: H
   shopify-shop-domain: victim-shop.myshopify.com
   shopify-webhook-id: <any>

   B
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only re-hashes `B`.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the app to act on attacker-supplied content under the victim's tenant identity.
