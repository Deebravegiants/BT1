Audit Report

## Title
Unbounded `savedCallbacks` map growth in gateway legacy Web API handler enables memory-exhaustion DoS - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` in the WebAPI gateway handler validates payload structure and staleness but has no allowlist, authentication-based throttling, or per-request cap before unconditionally inserting an entry into `h.savedCallbacks` at line 412. The only bound (`MaxSavedCallbacks`, default 20000) is enforced lazily by a `pruneCallbacks` goroutine that runs once per `CallbackPruneIntervalSec` (default 30s), so a caller submitting requests faster than that interval can grow the map unbounded between prune cycles, consuming gateway memory/CPU.

## Finding Description
Tracing the call path confirms the upstream gateway ingress (`gateway.ProcessRequest` in `core/services/gateway/gateway.go`) only calls `msg.Validate()` on legacy requests, which checks structural fields (ID/method/DonID length, signature format) and extracts the signer, but performs no allowlist or rate-limiting check against the sender before dispatching to `h.HandleLegacyUserMessage`: [1](#0-0) . Any address that can produce a validly-formed signed message (an unprivileged, unregistered key is sufficient — `Validate()` only checks signature format, not membership in any allowlist) reaches the handler.

Inside `HandleLegacyUserMessage`, the code explicitly marks the gap with `// TODO: apply allowlist and rate-limiting here` immediately before the method dispatch and subsequent unconditional map insertion: [2](#0-1) . Although the `handler` struct does contain a `nodeRateLimiter *ratelimit.RateLimiter` field, its config and usage are for outbound/node-facing messaging (`NodeRateLimiter` in `HandlerConfig`), not for gating the incoming legacy user-message ingestion path: [3](#0-2) .

The only mitigation, `pruneCallbacks`, runs asynchronously on a fixed ticker and evicts entries only after a `CallbackPruneIntervalSec` (default 30s) has elapsed: [4](#0-3) [5](#0-4) . Because insertion is synchronous/unconditional per request and eviction is periodic/asynchronous, an attacker sending requests faster than the prune interval drains them causes `savedCallbacks` to grow without an enforced ceiling at insertion time.

## Impact Explanation
Uncontrolled growth of the `savedCallbacks` map (plus periodic `sort.Slice` over its full contents during pruning) consumes gateway node memory and CPU, degrading or crashing the gateway process that routes all Web API/HTTP capability traffic for the DON — a denial-of-service against a shared gateway component, not merely a single caller's resources. This is an availability impact against gateway request routing infrastructure.

## Likelihood Explanation
High likelihood: the exploit requires only the ability to send a validly-formatted, self-signed message to the gateway's public HTTP ingress with a valid but arbitrary (unregistered) key — there is no allowlist check gating who may reach `HandleLegacyUserMessage`, confirmed by tracing `gateway.ProcessRequest` → `msg.Validate()` → `h.HandleLegacyUserMessage` with no intervening authorization step [1](#0-0) . Repeating this faster than the 30-second prune window is trivially achievable by an unprivileged remote client.

## Recommendation
- Enforce `MaxSavedCallbacks` synchronously at insertion time in `HandleLegacyUserMessage` (reject with an error response, or evict-oldest immediately) instead of relying solely on the periodic `pruneCallbacks` sweep.
- Implement the allowlist/per-sender rate-limiting referenced by the `// TODO` comment on this ingress path, consistent with the sender-scoped rate limiting pattern used elsewhere (e.g., `ratelimit.RateLimiter` usage patterns already present in the codebase, such as `core/capabilities/webapi/outgoing_connector_handler.go`).

## Proof of Concept
1. Stand up a gateway configured with a DON handler using `capabilities.NewHandler` and default `HandlerConfig` (`MaxSavedCallbacks` unset → 20000, `CallbackPruneIntervalSec` unset → 30s).
2. From an unregistered/arbitrary ECDSA key, construct and sign `api.Message` objects with unique `MessageID`s, method `web_api_trigger`, and a valid `TriggerRequestPayload.Timestamp`, per `api.Message.Sign`/`Validate` (see `core/services/gateway/api/message_test.go`).
3. POST these signed legacy requests to the gateway's HTTP endpoint (`gateway.ProcessRequest`) in a tight loop, at a rate exceeding entries evicted per 30-second prune cycle.
4. Observe `h.savedCallbacks` (or gateway process RSS) grow continuously without being capped synchronously, confirming lack of an insertion-time bound — this can be verified as a Go unit test directly against `handler.HandleLegacyUserMessage` by calling it in a loop and asserting `len(h.savedCallbacks)` exceeds `MaxSavedCallbacks` before the next `pruneCallbacks` tick fires.

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
