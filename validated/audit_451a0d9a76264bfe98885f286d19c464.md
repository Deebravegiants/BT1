Audit Report

## Title
Failed refund-swap fallback silently overcharges users and misreports full pre-correction fee via `AssetTxFeePaid` - (File: substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs)

## Summary
In `SwapAssetAdapter::correct_and_deposit_fee`, when the reverse quote `S::quote_price_exact_tokens_for_tokens` returns `None`/zero, or the `can_deposit` check on the refund fails, the fallback branch forwards the *entire* pre-correction `fee_paid` credit to `OU::on_unbalanceds` and returns the unadjusted `fee_asset_amount`, which is then emitted verbatim as `actual_fee` in `AssetTxFeePaid`. [1](#0-0) [2](#0-1)  This means a user can be charged the full estimated fee in `asset_id` terms rather than the weight-corrected amount whenever the AMM refund-swap quote fails.

## Finding Description
The code path is confirmed exactly as described: `correct_and_deposit_fee` computes `refund_amount = fee_paid.peek() - corrected_fee` [3](#0-2) , and when the asset is not the target asset `A`, it attempts to quote the reverse swap of `refund_amount` into `asset_id` via `S::quote_price_exact_tokens_for_tokens` [4](#0-3) . If that quote returns zero/`None`, or the subsequent `can_deposit` check fails, the code takes the entire `fee_paid` (pre-correction) and forwards it to `OU::on_unbalanceds`, returning the original, unadjusted `fee_asset_amount` [5](#0-4) . This returned value flows straight into the `AssetTxFeePaid` event as `actual_fee` [6](#0-5) . There is no bound tying the forwarded/kept amount to `corrected_fee`, and no distinguishing on-chain signal for this fallback case — it is indistinguishable from a legitimate "nothing to refund" scenario handled earlier in the function [7](#0-6) .

I was unable to locate an `AssetRefundFailed` event variant actually defined/emitted anywhere in this pallet's `lib.rs` (only 3 unrelated matches for `Event<T>`/`AssetTxFeePaid` were found, no `AssetRefundFailed` definition), so the claim's assertion that this "intended" event exists but is simply not deposited in this path could not be fully verified from the index — this is a minor factual uncertainty in the report but does not change the core validity of the underlying accounting bug.

## Impact Explanation
This is a genuine, concrete accounting bug: the pallet's fee-correction mechanism (whose entire purpose is to refund users the difference between the pre-dispatch weight estimate and the actual post-dispatch weight) can silently fail to apply that correction when the AMM pool used for the refund-direction quote lacks sufficient liquidity or price stability at the moment `post_dispatch_details` runs. The user is charged (and the event reports) the full pre-correction fee rather than the weight-corrected fee, with no compensating signal. This is an economic/accounting defect, not a memory-safety or fund-theft-from-other-users bug — the "overcharge" stays within normal fee-payment bounds (the user pays at most what they would have without any correction at all), but the deviation from `corrected_fee` is real and unbounded in the sense that it depends entirely on transient pool liquidity/spot price, which can be manipulated within the same block.

## Likelihood Explanation
The described attack requires an adversary to manipulate the specific `(Native, asset_id)` pool's liquidity/price between a victim's transaction validation and its `post_dispatch_details` execution, within the same block, via ordinary permissionless swap extrinsics in `pallet-asset-conversion`. This is plausible on chains with thin/low-liquidity pools, and it requires no privileged access — consistent with a valid, unprivileged-user-triggerable path. The precondition (drainable/skewable pool) is realistic though environment-dependent (thin liquidity), and the described front-running mechanic (swap before victim's post-dispatch, reverse after) is a known AMM risk class.

## Recommendation
- Emit a distinguishing event (e.g., `AssetRefundFailed`) when the fallback "no refund" path is taken in `correct_and_deposit_fee`, so indexers/users can detect and potentially be compensated for this case.
- Consider bounding fallback exposure using a stored/oracle reference price with slippage tolerance rather than relying purely on the spot AMM quote for the refund direction.
- Ensure `actual_fee` reported in `AssetTxFeePaid` can be distinguished between "fully corrected" and "fallback/no-refund" cases.

## Proof of Concept
Extend the "no refund" test case in `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/tests.rs`:
1. Set up a `(Native, asset_id)` pool, submit `ChargeAssetTxPayment` with a high estimated fee.
2. Before `post_dispatch_details`, swap/drain the pool so `quote_price_exact_tokens_for_tokens(Native, asset_id, refund_amount, true)` returns `None` (or the resulting deposit fails `can_deposit`).
3. Dispatch with low actual weight, call `post_dispatch_details`.
4. Assert `converted_fee`/emitted `AssetTxFeePaid.actual_fee` equals the full pre-correction `fee_asset_amount`, and that `OU::on_unbalanceds` receives the full `fee_paid.peek()` rather than an amount reflecting `corrected_fee`, demonstrating the unrefunded overcharge.
