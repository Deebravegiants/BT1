### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant (`shop`) for a webhook exclusively from the `X-Shopify-Shop-Domain` HTTP header, but `Utils::HmacValidator` only verifies the raw request body against the HMAC. The `shop` value is never included in the signed payload, so it is not cryptographically bound to the verified HMAC before being handed to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC against the body only, then immediately trusts `request.shop` (and other header-derived fields) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body for webhooks) and secure-compares it to the header HMAC: [4](#0-3) 

The broken identity binding is: `shop_used_by_handler == shop_covered_by_hmac` does not hold. The library verifies `hmac == HMAC(body)`, but the tenant identity attached to that verified body is taken from a header that carries no cryptographic relationship to the body or the HMAC. Any attacker who possesses one valid `(body, hmac)` pair — trivially obtainable by triggering a real webhook on their own development store, which they legitimately own — can replay that exact body/HMAC to the victim app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. The HMAC check still passes (it only checks the body), and the library will construct `WebhookMetadata` with the attacker-chosen `shop`, causing the host application to process/act on data under the wrong tenant.

### Impact Explanation
This is a cross-tenant identity confusion: the gem provides no guarantee that the `shop` value passed to `WebhookMetadata`/handler is the tenant that actually produced the signed payload. Any app that uses `request.shop` from the metadata to key merchant-specific data (the intended and documented usage pattern) can be tricked into attributing another store's legitimate webhook payload (or a replayed payload) to an attacker-chosen shop domain, since the shop identity is not bound by the HMAC that the library itself validates. This matches the "field acted on but not covered by the HMAC" analog class and can enable cross-tenant data confusion within apps that trust this library's shop-binding guarantee.

### Likelihood Explanation
Moderate-to-high: no credentials, tokens, or `api_secret_key` are required. The attacker only needs to capture one valid webhook body+HMAC (e.g., by triggering an event on their own store, which any developer/merchant can do) and can then replay it against the target app's public webhook endpoint with a forged shop header, since the HMAC never covers the shop field.

### Recommendation
Bind the shop identity into the verified material before trusting it: include the shop domain (and topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically tie the `X-Shopify-Shop-Domain` header to the signed body (e.g., by having `Registry.process`/`Request` reject requests whose header-derived shop cannot be corroborated against data inside the signed body, or by using a per-shop secret/registration lookup keyed off values proven by the HMAC rather than raw headers).

### Proof of Concept
1. Attacker owns/operates their own Shopify development store `attacker-shop.myshopify.com` with the target app installed, and registers a webhook (e.g. `orders/create`).
2. Attacker triggers the webhook and captures the raw POST body and its `X-Shopify-Hmac-Sha256` header value — this is a fully valid `(body, hmac)` pair signed with the app's real secret.
3. Attacker replays this exact body and HMAC header to the victim app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` succeeds because it only checks `HMAC(body)`: [5](#0-4) 
5. `WebhookMetadata` is built with `shop: request.shop` == `"victim-shop.myshopify.com"`, even though the payload actually belongs to `attacker-shop.myshopify.com`, and this is passed to the app's `WebhookHandler#handle`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
