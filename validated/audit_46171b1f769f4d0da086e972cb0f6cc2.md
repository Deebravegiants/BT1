Based on my investigation, I found a plausible "permanent deadlock" analog rooted in alt.fun's own two-phase graduation state machine — mapping the CVE-2023-0160 bug class (a state that can never make progress, permanently hanging the system) onto a contract path that can permanently strand a token in `Lifecycle.Graduating`.

### Title
Zero-liquidity edge case in `_prepareGraduationLiquidity` permanently deadlocks `finalizeGraduation`, freezing curve funds forever - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.finalizeGraduation` is permissionless and relies on values cached once, at end of phase 1, in `pendingGraduation[token]` (`tokensForLP`, `ltFromPair`) computed by `_prepareGraduationLiquidity`. [1](#0-0)  If `ltFromPair` rounds to a value small enough that `tokensForLP = (ltFromPair * tokenReserve) / assetReserve` rounds down to `0`, phase 2's direct-mint seeding path (`_seedDirectMint`) transfers `0` tokens to the freshly created HyperSwap pair and calls `pair.mint`, which reverts on a standard UniswapV2 pair because minted liquidity is `0`. [2](#0-1)  Because `tokensForLP`/`ltFromPair` are pinned at phase 1 and never recomputed, every retry of `finalizeGraduation` follows the exact same path and reverts identically — the token is permanently stuck in `Lifecycle.Graduating`.

### Finding Description
`triggerGraduation`/the inline post-buy path fires phase 1 (`_enterGraduating`) whenever `canGraduate` is true, which includes the USD trigger `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K`. [3](#0-2)  This design deliberately allows graduation to be armed purely by LT rate appreciation with little or no real trading volume — the `triggerGraduation` natspec explicitly documents this as the reason it exists. [4](#0-3)  When the real LT raised (`ltFromPair`) is tiny relative to the launch-time virtual reserve baked into `assetReserve`, `tokensForLP = (ltFromPair * tokenReserve) / assetReserve` in `_prepareGraduationLiquidity` can round down to `0`. [5](#0-4) 

Phase 2 (`finalizeGraduation`) reads this cached, frozen `tokensForLP`/`ltFromPair` pair verbatim — by design, to preserve the zero-gap invariant across the tx split, with no staleness/recompute path. [6](#0-5)  On the (~99% happy-path) empty-pair regime, `_seedUniswapV2Direct` calls `_seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair)` directly. [7](#0-6)  `_seedDirectMint` transfers `tokensForLP` (== 0) tokens and `ltFromPair` LT to the pair and calls `IUniswapV2Pair(pair).mint(lpLock)`. [8](#0-7)  A canonical UniswapV2 pair's `mint` reverts with `INSUFFICIENT_LIQUIDITY_MINTED` whenever the computed liquidity is `0`, which is guaranteed when one deposited amount is `0` on a fresh pair. Because `finalizeGraduation` is a single atomic call and the entire lifecycle transition happens after the seeding call, this revert unwinds the whole transaction — the lifecycle is never flipped to `Graduated`, and because the cached `pendingGraduation` values are byte-identical on every call (by design, per the natspec quoted above), **every subsequent call to `finalizeGraduation` for that token reverts identically forever.**

This is functionally a deadlock: the token's lifecycle state machine (`Curve → Graduating → Graduated`) can enter `Graduating` but never leave it, `buy`/`sell` are frozen for the entire remaining life of the token (`Bonding.buy`/`sell` revert with `TokenIsGraduating`/`TokenNotTrading` outside `Curve`), and all curve-raised LT plus the 250M reserve tokens parked on `Bonding` for graduation are permanently unreachable — there is no owner rescue path for a stuck `Graduating` token in the contracts as documented (only `LPLock` is called out as having no rescue path, but the described bricked-`finalizeGraduation` scenario is exactly the one the two-phase design's brick-resistance testing focuses on for hostile *pre-seed* shapes, not for a legitimate zero-`tokensForLP` cache produced entirely by `_prepareGraduationLiquidity` itself before any pre-seed exists). [9](#0-8) 

### Impact Explanation
Permanent freezing of trader and creator funds: every LT a trader spent buying the token on the curve, plus the 250M reserve tokens meant to seed the LP, become permanently stuck in `Bonding` with no code path to recover or retry successfully. Post-graduation trading (via `Zap`/HyperSwap) can never open because `finalizeGraduation` can never succeed, and the pre-graduation curve is frozen (`TokenIsGraduating`). This satisfies "permanent freezing of trader, creator or LP funds."

### Likelihood Explanation
Reachable from an ordinary unprivileged flow: any trader can buy a small seed amount, and the token's `canGraduate` can flip true purely from the reserve LT's `exchangeRate()` appreciating (a normal, expected event for a leveraged reserve asset, explicitly anticipated by the protocol's own `triggerGraduation` design), with no additional buy volume needed. If the real LT raised is small enough relative to the virtual reserve at that moment, `tokensForLP` rounds to `0` and the token is bricked the next time anyone (permissionlessly) calls `finalizeGraduation`. No malicious pre-seeding of the HyperSwap pair is required — the bug is purely in `_prepareGraduationLiquidity`'s rounding, independent of the extensively-tested hostile-pre-seed defenses.

### Recommendation
In `_prepareGraduationLiquidity` (or `_enterGraduating`), reject/defer entry into `Lifecycle.Graduating` when the computed `tokensForLP == 0` (or `ltFromPair` is below some minimum), or add a floor so `tokensForLP` is never smaller than a value that keeps `pair.mint` viable. Alternatively, have `finalizeGraduation` detect an unmintable cached state and fall back to a safe, funds-preserving lifecycle transition (e.g., allow recomputation, or an admin/permissionless rescue path that returns the parked LT/tokens instead of looping on a guaranteed revert).

### Proof of Concept
1. `Bonding.launch` a token against an LT with a large `virtualLtReserve` (sized per `VIRTUAL_LIQUIDITY_USD`).
2. Have a trader buy the minimal seed amount (a tiny real LT amount) — small enough that `ltFromPair` (`assetReserve - virtualLtReserve`) stays tiny.
3. Call `lt.setExchangeRate(...)` (or wait for genuine LT appreciation) to a large enough multiple that `(ltFromPair) × exchangeRate ≥ $9K`, flipping `canGraduate` true while `ltFromPair` is still tiny relative to `tokenReserve/assetReserve`.
4. Call `Bonding.triggerGraduation(tokenAddress)` — phase 1 fires, caching `tokensForLP == 0` in `pendingGraduation[token]` because `(ltFromPair * tokenReserve) / assetReserve` rounds to zero.
5. Call `Bonding.finalizeGraduation(tokenAddress)` — `_seedDirectMint` calls `pair.mint(lpLock)` with `0` tokens deposited, which reverts with `INSUFFICIENT_LIQUIDITY_MINTED` on a canonical UniswapV2 pair.
6. Any subsequent call to `finalizeGraduation(tokenAddress)` reverts identically (cached values are unchanged), permanently freezing the token in `Lifecycle.Graduating` with all curve LT and reserve tokens trapped on `Bonding`.

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    function _seedDirectMint(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair

Dual trigger — fires on whichever hits first:

- **USD trigger:** `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` (HYPE pumps raise the USD value of already-raised LT above the threshold). Reads the pair's STORED reserves; the launch-time `virtualLtReserve` is recovered on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()` because `_pool.k = totalSupply * virtualLtReserve` is locked in at `Pair.mint` and never modified by swaps.
- **Supply trigger:** `IPair.tokenBalance() == 0` (all 750M curve tokens sold; handles flat/bear markets where $9K is never reached). This IS a live `balanceOf` read but is donation-resistant in the opposite direction — token donations can only INCREASE the balance and can never satisfy `== 0`. Any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`.
