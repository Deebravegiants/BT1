### Title
Unchecked ERC20 `transfer` return value in `withdraw()` and `SweepDust` can permanently strand escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2` on Tron settles escrowed input tokens and protocol fees using a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks whether the *call itself* reverted, never decoding/validating the returned boolean payload. Both the escrow-release path (`withdraw`) and the `SweepDust` handler decrement internal accounting (`_orders[...] -= amount`, `delete _orders[...][TRANSACTION_FEES]`) unconditionally once the call doesn't revert, even if the token's `transfer` function returned `false` to signal failure.

The same unchecked pattern appears in the `SweepDust` handler: [3](#0-2) 

In all three sites, `success` reflects only whether the low-level call reverted — it does **not** decode the ABI-returned `bool`. A standards-compliant ERC20 token whose `transfer()` returns `false` on failure (without reverting) — a well-documented real-world pattern (e.g. old BNB/ZRX-style tokens, paused/blacklist-gated tokens) — will make `success == true` here even though no tokens moved. The code then unconditionally decrements `_orders[commitment][token]` (in `withdraw`) or deletes the `TRANSACTION_FEES` entry, permanently erasing the accounting record for funds that never left the contract.

This directly contrasts with (and is the mirror-image failure mode of) the referenced report: instead of reverting on non-boolean-returning tokens, this code *silently succeeds* on false-returning tokens, and the escrow bookkeeping is destroyed regardless of the real outcome. Notably, the input-side escrow flow in the same file correctly uses `IERC20.safeTransferFrom` (OpenZeppelin `SafeERC20`, which validates return data), showing the codebase is aware of and normally guards against this exact class of bug — but the withdrawal/fee/dust-sweep paths were written with a raw, unchecked `.call` instead.

Compare with `IERC20.safeTransferFrom` used correctly elsewhere in the very same contract: [4](#0-3) 

### Impact Explanation
Once `withdraw()` silently "succeeds" against a token that actually returned `false`:
- `_orders[commitment][token]` is decremented to zero even though the tokens remain in the `IntentGateway` contract's balance, with no accounting entry left to reference or recover them — the funds are permanently stranded/unrecoverable through the gateway's own logic (permanent freezing of funds).
- For the `TRANSACTION_FEES` path, the solver's/relayer's fee entitlement is deleted even though the fee token transfer failed, causing a direct loss of the fee payout owed to the solver.
- `SweepDust` similarly emits `DustSwept` and treats dust as collected by the beneficiary even if the transfer silently failed.

Given `order.inputs[i].token` is an arbitrary, user-supplied ERC20 address at `placeOrder()` time, and settlement of `withdraw()` is triggered by anyone relaying a valid cross-chain proof (`onAccept`), this is reachable by any user/solver interacting with the permissionless Intent Gateway flow. This qualifies as permanent freezing of escrowed user/solver funds — a Medium-severity issue.

### Likelihood Explanation
Exploitation requires the involved ERC20 token to return `false` rather than revert on a failed transfer (e.g., paused, blacklisted, or non-standard tokens). Such tokens are common in the wild, and because `order.inputs[i].token` is fully attacker-controlled at order-placement time, a malicious order creator can deliberately use/deploy such a token to grief the settlement path, or an innocuous but rare failure (e.g., a temporarily paused stablecoin) could trigger it accidentally, silently and irreversibly losing accounting for the escrowed funds. Likelihood is moderate: it depends on token choice/behavior, but it is trivially triggerable by a motivated attacker.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only checks in `withdraw()`, the `TRANSACTION_FEES` redemption, and `SweepDust` with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the `safeTransferFrom` usage already present elsewhere in the same contract. `SafeERC20` correctly treats "no return data" as success (avoiding the original report's revert problem) while still reverting when a token explicitly returns `false`.

### Proof of Concept
1. Deploy a malicious ERC20 token `EvilToken` where `transferFrom` always returns `true` (so escrow deposit succeeds) but `transfer` always returns `false` without reverting.
2. Attacker calls `placeOrder` with `order.inputs[0].token = address(EvilToken)`, escrowing `EvilToken` into the `IntentGateway` via `safeTransferFrom` (succeeds).
3. A solver fills the order on the destination chain, delivering real value (e.g., USDC) to the beneficiary, and the cross-chain `RedeemEscrow` message is dispatched.
4. Any relayer submits the proof; `onAccept()` → `withdraw()` executes: `token.call(abi.encodeWithSelector(IERC20.transfer.selector, solver, amount))` returns `(true, abi.encode(false))`. Since only the outer `success` bool is checked, the code proceeds as if the transfer succeeded.
5. `_orders[commitment][EvilToken] -= amount` zeroes out the accounting entry. The solver never receives the `EvilToken` payout, and the tokens remain unrecoverable inside `IntentGateway`, while the attacker has already received the solver's real-value output tokens.
