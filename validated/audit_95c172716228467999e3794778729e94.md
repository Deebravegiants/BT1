### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` checks is computed over the raw request body only. This breaks the intended binding `shop (HMAC-verified) == shop (used for tenant routing)`, since the header is not part of the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an unauthenticated header, entirely independent of the signed bytes: [2](#0-1) 

`Registry.process` validates the request purely via `HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (the body) and compares it against the received `hmac`: [3](#0-2) [4](#0-3) 

Once the HMAC check passes, `Registry.process` hands the *header-derived* `shop` straight to the app's webhook handler as the tenant identity, with no further binding to the signed body: [5](#0-4) 

Because `shop` is excluded from `to_signable_string`, any `(raw_body, hmac)` pair that is valid for one shop remains a valid `(raw_body, hmac)` pair no matter which `shop-domain` header value accompanies it — the signature makes no statement about which tenant the body belongs to.

### Impact Explanation
An attacker who can obtain one legitimately-signed `(body, hmac)` pair (e.g., by owning/operating their own shop that has this app installed, and triggering any webhook event on it) can replay that exact body+HMAC to the host app's public webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` will still succeed (it never looks at the header), and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Any host application that uses this `shop` value to select which merchant's data/session to act on (the intended and documented usage of `WebhookMetadata`) can be made to attribute attacker-controlled webhook data to an arbitrary victim tenant — a cross-tenant confusion/injection primitive that maps to the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Any internet user who has (or can obtain, e.g., via a free/trial installation) their own shop where this app is installed can generate arbitrarily many valid `(body, hmac)` pairs for themselves at will and no other credential (api_secret_key, access token, or client_secret) is ever needed — the exploit only requires knowledge that Shopify webhook bodies are frequently near-identical structurally across shops for the same topic, or crafting a topic/body where the actual `shop` field embedded in the JSON payload is irrelevant to the host's trust decision (since hosts are documented to rely on the `WebhookMetadata#shop` field, not on parsing the shop out of the JSON body themselves). This is a purely network-reachable, unauthenticated-endpoint issue.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) header values in the bytes that are HMAC-verified, or otherwise cryptographically bind the header-derived tenant identity to the signed payload before it is exposed via `WebhookMetadata`, so that a signature valid for shop A cannot be replayed and reattributed to shop B.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify computed with the app's real `api_secret_key`.
2. Attacker sends `POST /webhooks` (the host app's Shopify webhook endpoint) with:
   - Body: `B` (unmodified)
   - Header `X-Shopify-Hmac-Sha256: H` (unmodified)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (attacker-modified)
   - Header `X-Shopify-Topic`: same topic as originally captured
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds: [3](#0-2) 
4. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body(B), ...)`, causing the host app to process attacker's own webhook payload as though it originated from the victim shop: [6](#0-5)
