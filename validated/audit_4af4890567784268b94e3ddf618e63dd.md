## Title
Direct LT (or Token) donations to a curve `Pair` are permanently unretrievable — no sweep/skim path exists (analogous to stuck ETH via unaccounted `receive()`) - ([File: packages/contracts/src/Pair.sol], [File: packages/contracts/src/Router.sol])

### Summary
This is the exact class flagged in the external report: value can be sent into an accounting contract in a state where the internal accounting variable never reflects it, permanently stranding the funds. In alt.fun, `Pair.sol`'s accounted reserves (`_pool.tokenReserve` / `_pool.assetReserve`) are updated only by `mint`/`swap`, never by tracking raw ERC20 balance. Any unrelated wallet can `IERC20(lt).transfer(pair, amount)` or `IERC20(token).transfer(pair, amount)` directly to a bonding-curve `Pair`, which increases the pair's real ERC20 balance without moving `_pool.assetReserve`/`tokenReserve`. Unlike a standard UniswapV2 pair, `Pair.sol` exposes **no `skim()` / `sync()`** and has no owner/admin rescue function — the only way LT ever leaves a `Pair` is `Router.sell` and the one-shot `Router.graduate` call (bounded to the exact `ltFromPair` computed from stored reserves), and the only way tokens leave is `Router.buy`/`_prepareGraduationLiquidity`'s burn of `unsoldBurned`. Donated LT is explicitly excluded from `ltFromPair` by design (`Router.graduate`'s natspec: *"any LT that was donated directly to the pair via IERC20.transfer is left behind and excluded from LP seeding"*), and after graduation `Bonding` never calls `Router.graduate` again for that token, so the leftover balance sits in the `Pair` contract forever, reachable by nobody.

### Finding Description
`Pair.sol` tracks reserves in a separate `Pool` struct (`_pool.tokenReserve`, `_pool.assetReserve`) rather than reading live `balanceOf`: [1](#0-0) 

`swap`/`mint` are the only functions that mutate `_pool`, and `transferAsset`/`transferToken` (the only exits for value) are `onlyRouter`-gated but take an explicit `amount`, not "sweep the balance": [2](#0-1) 

`Router.graduate` — the single function that drains LT from a `Pair` at graduation — deliberately transfers only `amount = storedAssetReserve - virtualLtReserve`, explicitly leaving any donated LT behind, and is unreachable after the token leaves `Lifecycle.Curve`: [3](#0-2) 

The Router's own natspec states this leftover is only "locked" by a *trust assumption*, not an on-chain guarantee, and confirms no other code path can reach it once past `Curve` lifecycle: [4](#0-3) 

Compare this to the HyperSwap V2 pair used post-graduation, which the protocol itself relies on having a real `skim()` to recover donations during `_seedUniswapV2Direct`'s Regime 2: [5](#0-4) 

`Pair.sol` — the curve pair — has no equivalent. Any LT sent directly to a curve `Pair` (pre- or post-graduation) is permanently unrecoverable by the depositor, the creator, `Bonding`'s owner, or the protocol. This mirrors precisely the reported bug class: value enters a contract, contributes nothing to the internal accounting state that governs payouts, and there is no function anywhere in the system capable of retrieving it.

### Impact Explanation
Any unrelated wallet, or a trader/creator who mistakenly sends LT (or the launched `Token`) directly to a curve `Pair` address instead of going through `Zap.buy`/`sell`, permanently loses those funds — a concrete freezing of an unrelated wallet's/trader's assets with zero recovery path, matching the "permanent freezing of trader ... funds" acceptance criterion. Because the reserve asset here is a BounceTech LT (a yield-bearing asset), any donated LT continues to accrue no benefit to anyone and is simply orphaned forever — economically equivalent to burning real value with no offsetting effect (no burn event, no accounting update, no beneficiary). This is Medium severity: it requires an errant/careless direct transfer to trigger (not attacker-forced against a victim), but the loss is total and permanent once it happens, exactly the same severity classification given to the original report ("Medium", "Acknowledged").

### Likelihood Explanation
The protocol's own documentation and code comments repeatedly discuss "direct LT donations to the pair" as an anticipated, non-adversarial scenario (used throughout the graduation-invariant tests, e.g., "Donation resistance" invariant #7), meaning this is a state the contracts are known to enter regularly, not a contrived edge case. Since `Pair` addresses are public and permissionless ERC20 `transfer` calls are always possible, any wallet — trader, creator, or unrelated party — can trigger this by simply sending LT to the wrong address (a `Pair` rather than `Zap`), which is a realistic user-error / griefing scenario in a system where curve pairs are separate deployed contracts distinct from the user-facing `Zap`.

### Recommendation
Add a `skim()`/rescue mechanism to `Pair.sol`, gated by `onlyRouter` (mirroring `Router.graduate`'s access model), that lets `Bonding` sweep `IERC20(assetToken).balanceOf(pair) - _pool.assetReserve` (and the analogous excess on the token side) to a recoverable destination — e.g., back to the depositor if attributable, or to the protocol owner/FeeVault as unbacked-donation sweep, similar to `FeeVault.sweepDonations()`'s pattern. At minimum, expose a permissionless "sweep excess to owner" function on `Pair` so donated value is not permanently stranded, consistent with the treatment given to HyperSwap-side donations (`_sweepLTToOwner`/`skim`) in the graduation path.

### Proof of Concept
1. `Bonding.launch(...)` a token; note its `Pair` address via `Bonding.getTokenInfo(token).pair`.
2. From any unrelated EOA, call `IERC20(ltAddress).transfer(pairAddr, X)` (a direct donation, no `Zap` interaction).
3. Observe `IPair(pairAddr).assetBalance()` increases by `X` while `IPair(pairAddr).getReserves()` (the stored `_pool.assetReserve`) is unchanged.
4. Drive the token through graduation (`Bonding.triggerGraduation`/inline threshold trigger + `finalizeGraduation`). `Router.graduate` drains only `ltFromPair = storedAssetReserve - virtualLtReserve`, per `Router.sol` lines 203-211 — the donated `X` LT is never transferred out.
5. Post-graduation, confirm no function in `Bonding`, `Router`, `Zap`, or `Pair` can move the residual `X` LT out of the (now-abandoned) curve `Pair` — `graduate` is `onlyRole(BONDING_ROLE)` but `Bonding` only invokes it once, from `_prepareGraduationLiquidity`, which is unreachable once `lifecycle != Curve` (`Bonding.sol` `_prepareGraduationLiquidity`/`canGraduate` gating). The donated LT is permanently stuck in the `Pair` contract.

        uint256 tokenReserve,
        uint256 assetReserve
    ) external onlyRouter returns (bool) {
        if (_pool.k != 0) revert AlreadyMinted();
        _pool = Pool({tokenReserve: tokenReserve, assetReserve: assetReserve, k: tokenReserve * assetReserve});
        emit Mint(tokenReserve, assetReserve);
        return true;
    }

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }

    /// @notice Transfer exactly `amount` of LT out of the pair to the caller.
    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }
