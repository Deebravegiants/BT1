Confirmed. This is a real, concrete finding: the webhook HMAC in this gem covers only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` are taken from unauthenticated HTTP headers.

### Title
Webhook shop/topic identity is not bound by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw body alone, and validation (`Utils::HmacValidator.validate`) only proves that the body bytes were signed with the app's `api_secret_key`. The `shop`, `topic`, `webhook_id`, and `api_version` fields — read from HTTP headers and handed to the app's handler as trusted identity — are never covered by that signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
while `shop`, `topic`, `webhook_id` are pulled straight from attacker-controllable headers: [2](#0-1) 

`Registry.process` validates only via `Utils::HmacValidator.validate(request)`, i.e. only the body's HMAC, then immediately trusts `request.shop` and `request.topic` to build the handler payload: [3](#0-2) 

`HmacValidator.validate` in turn calls `verifiable_query.to_signable_string`, which for `Request` is just the body: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`HMAC-verified bytes (body only)` ≠ `identity fields acted upon (shop-domain, topic, webhook-id headers)`.

Because any merchant who installs the app is themselves an "unprivileged internet user" with respect to other tenants, they legitimately receive real `(body, hmac)` pairs from Shopify for their own shop's events. Nothing in this gem prevents that attacker from replaying the exact same body+HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with a victim tenant's domain — `Utils::HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim>`.

### Impact Explanation
This is a cross-tenant identity forgery at the trust boundary the gem is responsible for enforcing: an app author calling `ShopifyAPI::Webhooks::Registry.process` reasonably assumes that a passing HMAC check means the entire webhook — including which shop it's attributed to — was authenticated by Shopify. In apps that key persistence, entitlement, or side-effects (e.g., `GDPR` redact handlers, order/fulfillment sync, billing state) off `WebhookMetadata#shop`/`#topic` without independent verification, this allows one tenant to inject data or trigger handler logic attributed to another tenant's shop — a cross-tenant access impact.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even trial/free) installer of the target app so they receive at least one genuine webhook, plus the ability to POST arbitrary headers to the app's public webhook endpoint — both trivially available to an unprivileged internet user with no access token, `client_secret`, or privileged account needed.

### Recommendation
Include the identity-bearing fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify `shop` against the session/tenant the body's content refers to) before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. Install the target app as shop `attacker.myshopify.com`; trigger an event so Shopify sends a real webhook: body `B`, header `shopify-hmac-sha256: H` (valid for `B`), `shopify-shop-domain: attacker.myshopify.com`.
2. Capture `(B, H)`.
3. POST to the app's webhook endpoint with the same body `B` and header `shopify-hmac-sha256: H`, but `shopify-shop-domain: victim.myshopify.com` (and optionally a different `shopify-topic`/`shopify-webhook-id`).
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (body unchanged), and `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, i.e. the app processes attacker-authored content as if it originated from the victim shop.

            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
