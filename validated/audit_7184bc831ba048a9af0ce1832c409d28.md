### Title
`validate()` accepts structurally unbalanced/mismatched SVG tag nesting, allowing parser-differential DOM escape - ([File: libraries/svg-safe/src/validate.mjs])

### Finding Description
`validate()` tokenizes the SVG into individual tags via `tokenizeFile`/`tokenizeLine` and, for every token, only checks that the bare tag name (open, `/tag` close, or self-closing `tag/`) is a member of the `allTags` allowlist, and that closing tags (`tag.startsWith('/')`) carry no attribute options: [1](#0-0) 

There is no stack maintained anywhere in the function to track which tag is currently open, so nothing verifies that a `</mask>` actually matches a preceding `<mask>`, that `</svg>` isn't emitted twice, or that closing tags appear in the correct LIFO order relative to their openers. `allTags` itself is built purely as a flat set of allowed name variants with no structural relationship encoded between an opening and its corresponding closing entry: [2](#0-1) 

Consequently, an SVG such as `<svg><mask><path d="M0 0"/></svg></mask>` or `<svg><g><path d="M0 0"/></g></svg></svg>` (extra/misordered closers) passes `validate()` unchanged, because each token individually is allowlisted and closing tags have zero attributes. `validate()` is invoked directly on attacker/remote-influenced icon data in both the browser and mobile icon-storage adapters — `getIcon` calls `validate(icon)`/`validateSVG(data)` on stored icon bytes, and `cleanup()` (used when unzipping incoming token icons) calls `validate(clean)` after only stripping comments/titles and collapsing whitespace, with no structural re-serialization: [3](#0-2) [4](#0-3) [5](#0-4) 

Because the sanitizer emits the original (only lightly-mutated) SVG text rather than re-serializing a verified tree, whatever malformed nesting the attacker submitted is passed through byte-for-byte to whatever downstream engine ultimately renders it (WebView/DOMParser/react-native-svg). If that engine's error-recovery behavior for mismatched tags differs from the "no-op" model implicitly assumed by `validate()` (which does not reject mismatches at all), elements intended to be confined to a non-rendering or transform-limited container (e.g., `<mask>`, `<clipPath>`, `<defs>`) can end up promoted to render directly in the visible tree, or vice versa.

### Impact Explanation
The impact is confined to DOM/render-tree structure divergence for wallet-displayed token icons — e.g., content intended to be hidden inside a `<mask>`/`<clipPath>`/`<defs>` could become visible, or a shape meant to be clipped could render unclipped, allowing a spoofed/misleading icon to be displayed in the wallet UI. Because the tag allowlist itself excludes `<script>`, event-handler attributes, `foreignObject`, and interactive/external references, this does **not** provide script execution, secret disclosure, or signing bypass — it is a UI/rendering spoofing issue limited to visual misrepresentation of asset icons, not a fund-theft or auth-bypass primitive.

### Likelihood Explanation
Preconditions are modest: an attacker only needs to control the bytes of an SVG icon (e.g., via a malicious/spoofed token entry whose icon field flows through `storeIcons`/`unzipIcon`/`cleanup`, or a tampered locally-cached icon file read by `getIcon`), and every individual tag they use must already be on the allowlist (so no exotic tags/attributes are needed, only mismatched ordering). Because `validate()` performs zero structural/stack checks, generating an accepted-but-malformed input is trivial and fully repeatable. However, actually achieving a differing render outcome further depends on the specific downstream renderer's (WebView `DOMParser`, `react-native-svg`, etc.) tag-recovery behavior, which was not verified in this codebase and would require an external differential test against the real rendering engine used for icons.

### Recommendation
Add explicit stack-based nesting validation to `validate()`: maintain a stack of open tag names, push on open tags, and on each closing tag assert the stack top matches the tag name being closed (popping it), and assert the stack is empty at the end of iteration. Reject (`assert(false, ...)`) on any mismatch, extra closer, or unclosed tag before returning from `validate()`.

### Proof of Concept
Unit test to add to `libraries/svg-safe/src/__tests__/validate.test.js`:
```js
import { validate } from '../validate.mjs'

test('rejects mismatched/unbalanced tag nesting even though all tags are allowlisted', () => {
  const svgs = [
    '<svg><g><path d="M0 0"/></g></svg></svg>', // extra closing svg
    '<svg><mask><path d="M0 0"/></svg></mask>', // interleaved/misordered closers
    '<svg><g><path d="M0 0"/></svg>', // missing </g>, extra content structurally unclosed
  ]
  for (const svg of svgs) {
    expect(() => validate(svg)).toThrow() // currently does NOT throw -> demonstrates the gap
  }
})
```
Expected (current, buggy) result: `validate()` does not throw for these inputs because each token's bare tag name is allowlisted and closers carry no options — demonstrating that no nesting/balance check exists. After the fix (stack-based matching), all three inputs should throw an assertion error.

export function validate(raw) {
  assert(typeof raw === 'string', `validate: raw is not a string`)
  assert(!/['`]/u.test(raw), `validate: "${raw}" is not valid`) // just an extra check
  for (const token of tokenizeFile(raw)) {
    if (token.trim() === '') continue
    const [tag, ...options] = tokenizeLine(token)
    assert(allTags.has(tag), `validate: invalid tag "${tag}"`)
    if (tag.startsWith('/')) assert(options.length === 0, `validate: "${tag}" starts with /`)
    for (const option of options) validateOption(tag, option.replace(/^ +/u, ''))
  }
}
