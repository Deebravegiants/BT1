### Title
Duplicate input tokens in a single order let solvers over-release escrow (unpatched in Tron `IntentGatewayV2`) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.placeOrder` credits the `_orders[commitment][token]` escrow map using accumulation (`+=`) and performs no check that a token has already been credited for the same commitment. The mainline EVM implementation (`evm/src/apps/IntentGatewayV2.sol`) was patched to explicitly reject duplicate input tokens (`if (_orders[commitment][token] != 0) revert InvalidInput();`), but the Tron contract still allows a user to place an order with the same input token listed multiple times, silently merging the escrowed amounts under one key — exactly the same root cause pattern as the referenced report (a value keyed by an address/commitment gets overwritten/merged instead of being validated as unique before being trusted downstream).

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, escrow accounting is: [1](#0-0) [2](#0-1) 

There is no rejection of duplicate `order.inputs[i].token` entries, unlike the hardened mainline version, which explicitly guards against this: [3](#0-2) 

On the fill side (`IntrinsicIntents._fillSameChain`, shared by both deployments through the same architecture), the escrowed amount released per output index `i` is read as `_orders[commitment][order.inputs[i].token]`: [4](#0-3) 

If the order has two (or more) output legs whose corresponding `order.inputs[i].token` is the *same* address (which the Tron contract permits because it never checks for duplicates), each of those output-indexed fill legs will read and release the *full* escrow amount stored under that one shared `(commitment, token)` slot — even though the token was only escrowed once. This is confirmed by the regression test that exists for the already-fixed mainline path: [5](#0-4) 
The test's own comment describes precisely this bug class: "same-chain partial fills over-release repeated input escrow." The Tron contract lacks the corresponding fix, so this exact over-release remains reachable there.

This mirrors the referenced Teller `CollateralManager` bug: a mapping keyed by an identifier (there, `collateral address`; here, `(commitment, token)`) is written without verifying it hasn't already been populated, letting one nominal deposit be "stretched" to cover more than it actually backs — enabling extraction of value the escrow does not actually hold.

### Impact Explanation
An attacker (any ordinary user/solver) can place an order on the Tron gateway with duplicate input tokens across multiple output legs. Escrow for that token is only actually deposited once, but because the escrow map merges/duplicates the reference across output indices, a colluding or self-filling solver can drain more of the escrowed token (or drain protocol/dust funds) than was ever deposited, causing theft of funds/insolvency of the gateway's escrow — the same class of "obtain more value than deposited" impact as the original report, meeting the High severity bar (concrete theft of escrowed funds).

### Likelihood Explanation
Any user can call `placeOrder` directly with attacker-chosen `order.inputs`/`order.output.assets` — no privileged role is required. The Tron gateway is a production deployment target (separate `evm/tron/contracts/apps/IntentGatewayV2.sol` tree exists specifically for it), and the vulnerable code path is the default, unguarded `placeOrder`/`fillOrder` flow used by every intent.

### Recommendation
Port the duplicate-input-token guard from the mainline `evm/src/apps/IntentGatewayV2.sol` (reject if `_orders[commitment][token] != 0` before writing, instead of using `+=`) into `evm/tron/contracts/apps/IntentGatewayV2.sol`, for both the predispatch and direct-transfer escrow loops, and add the same duplicate-output-asset check that mainline performs via transient storage in `placeOrder`.

### Proof of Concept
1. On the Tron deployment, craft `Order` with `inputs = [ {token: USDC, amount: 1000}, {token: USDC, amount: 1000} ]` and matching `output.assets` of length 2 (two output legs).
2. Call `placeOrder`; only 1000 USDC total is transferred in, but `_orders[commitment][USDC]` ends at `1000 + 1000 = 2000` due to the `+=` merge (or, if only one input leg used, is referenced twice by index).
3. Call `fillOrder` as a solver: for output index 0, `_fillSameChain` reads `_orders[commitment][USDC]` and releases the full stored amount; for output index 1, the same escrow slot is read again and released again — resulting in the solver being paid escrow that exceeds what was actually deposited, matching the mainline regression test's documented failure mode.
