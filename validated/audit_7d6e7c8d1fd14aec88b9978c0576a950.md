### Title
Webhook shop/topic identity not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and attribute the webhook are taken directly from unauthenticated HTTP headers. This breaks the identity binding: **shop cryptographically authenticated ≠ shop attributed to the processed webhook data**, exactly the "field acted on but not covered by the HMAC" pattern from the source report (fee computed on the wrong quantity vs. the quantity actually validated).

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field of the same object: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers, entirely outside the signed material: [3](#0-2) 

`Registry.process` validates only the HMAC of the request, then unconditionally trusts the header-derived `shop`/`topic`/`webhook_id` to build the `WebhookMetadata` that is handed to the app's handler: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, not a per-shop secret, any body that was legitimately signed for one shop (e.g. one the attacker controls and receives real webhooks for) produces a `hmac` value that is valid for that *same body* regardless of which `shop`/`topic` headers accompany it. The signature check in `HmacValidator.validate_signature` (`OpenSSL.secure_compare(computed_signature, received_signature)` against `to_signable_string == @raw_body`) cannot detect that the header-carried identity was swapped: [5](#0-4) 

### Impact Explanation
An attacker who legitimately receives webhooks for their own store (a normal merchant capability) can capture a `(raw_body, hmac)` pair that is valid under the app's shared secret, then replay it against the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header pointing at a different, victim tenant. `Registry.process` still passes HMAC validation (only the body is checked) and calls the app's handler with `WebhookMetadata` claiming the attacker-chosen shop. Any host application that trusts `WebhookMetadata#shop` to select which tenant's records to create/update/delete is exposed to cross-tenant data corruption/injection — data belonging to shop A is applied under the identity of shop B, without the app ever needing shop B's credentials.

### Likelihood Explanation
High. Any app integrator that installs the app for multiple shops (the common case) is affected, and the attack requires nothing more than an unprivileged internet user who is also an installed merchant capturing their own legitimate webhook payload/signature and replaying it with modified headers to the public webhook endpoint. No access token, `client_secret`, or privileged account is needed — only a body/hmac pair the attacker is entitled to receive for their own shop.

### Recommendation
Include the `shop`, `topic`, and any other header fields that are acted upon (used for routing/tenant attribution) inside the signed material, or otherwise cryptographically bind them to the body before validation — e.g., compute the signable string over a canonical concatenation of `shop-domain + topic + webhook-id + raw_body`, mirroring Shopify's requirement that consumers derive the shop from a trusted, request-specific source rather than an unauthenticated header. At minimum, document/require host apps to cross-check `shop` against the record that requested/registered the specific `webhook_id`, and reject any request where the header-derived shop cannot be corroborated by data internal to the signed body.

### Proof of Concept
1. App is installed on `victim.myshopify.com`, and attacker's own shop `attacker.myshopify.com` is also a legitimate installed tenant.
2. Shopify sends attacker a genuine webhook: body `B`, headers include `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: H` (computed by Shopify over `B` using the app's shared `client_secret`).
3. Attacker captures `(B, H)` and replays a POST to the app's webhook endpoint with `x-shopify-shop-domain: victim.myshopify.com`, unchanged `B` and `H`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`== B`) and compares to `H` — validation succeeds because only `B` is signed: [6](#0-5) 
5. `handler.handle` is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: B, ...)`, and any app logic keyed on `metadata.shop` now applies attacker-originated data to the victim tenant.
