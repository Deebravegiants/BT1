### Title
Arbitrary `endpoint.call` in `EmporiumUpgradeable.runAction`'s stateless op branch lets an attacker plant a standing ERC-20 approval and later drain any balance parked in the shared action contract - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` executes attacker-supplied `EmporiumOperation[]` ops with the action contract itself as `msg.sender` when `stack.signerAddress == address(0)` (CASE 2, stateless interaction). The only restriction on `op.callData` is a selector blacklist for `callHinkalWallet`/`doSendToRelay` — arbitrary `endpoint` and `callData` are otherwise unconstrained, so an attacker can make Emporium call `token.approve(attacker, type(uint256).max)` on any ERC-20. Because approvals persist across transactions (the same pattern as `TransfererBase.approveUnlimited`, which never revokes unless allowance drops below `type(uint256).max/2`), the attacker can later call `transferFrom` directly on the token, outside of `Hinkal.transact` entirely, and pull out any balance ever left sitting in the shared `EmporiumUpgradeable` contract.

### Finding Description
Invariant claimed: *tokens leaving an action in a tx == `-deltaAmountChanges` Hinkal sent it that tx.*

`EmporiumUpgradeable.runAction` decodes `stack` fully from attacker-controlled `circomData.externalActionData.externalActionMetadata`: [1](#0-0) 

For each op, if `stack.signerAddress == address(0)` (attacker's free choice), `op.invokeWallet && stack.signerAddress != address(0)` is false, forcing CASE 2: [2](#0-1) 

Only two selectors are blocked; any other `op.endpoint`/`op.callData` executes with `EmporiumUpgradeable` as `msg.sender`. This means the attacker can encode `op.endpoint = someERC20`, `op.callData = approve(attacker, type(uint256).max)`. This call does not move any token balance, so `balancesAfter == balancesBefore` for that index, and by choosing `deltaAmountChanges[i] == 0` (no in/out flow for that token in this transaction), `handleOut` returns an empty UTXO (`balanceChange <= 0`): [3](#0-2) 

All of Hinkal's checks pass for this crafted transaction: `verifyWallet` no-ops when `stack.signerAddress == 0`: [4](#0-3) 

and `Hinkal.transact`'s balance-equality check (`balanceDif == amountChanges[i] + utxoAmount`) is satisfied trivially since balance never moved for the approved token: [5](#0-4) 

After this transaction, `EmporiumUpgradeable` (a single shared contract used by all users, not per-user) holds a standing `type(uint256).max` approval to the attacker's address on that ERC-20. `EmporiumUpgradeable` legitimately, if only momentarily, holds token balances during other users' `transact()` calls — Hinkal transfers `-deltaAmountChanges[i]` tokens into the action address *before* invoking `runAction`: [6](#0-5) 

Any dust, rounding remainder, failed/partial op execution leftover, or balance from a subsequent user's deposit-into-Emporium flow that is present at the moment the attacker chooses to act constitutes a "residual/stranded" balance. Since the approval was already granted, the attacker calls `token.transferFrom(EmporiumUpgradeable, attacker, amount)` directly on the ERC-20 contract — completely outside `Hinkal.transact`, bypassing `performHinkalChecks`, `verifyProof`, `rootHashExists`, the balance/slippage `require`s, and `insertNullifiers` — because none of those guards govern direct third-party calls to the ERC-20 token contract. The invariant "tokens leaving the action == `-deltaAmountChanges` Hinkal sent it that tx" is broken in the *later* transaction: zero tokens are sent by Hinkal in that transaction (it isn't a Hinkal transaction at all), yet tokens leave the action to the attacker.

### Impact Explanation
Direct theft of in-flight/shielded user funds parked in the shared `EmporiumUpgradeable` external-action contract. Any balance that transiently or accidentally rests in Emporium (deposits pending a follow-up op, dust from a partially-successful multi-op stack, or funds another concurrent user's transaction is in the process of moving through) can be permanently redirected to the attacker, matching the Critical category: "direct theft of shielded or in-flight user funds." The attack is repeatable — the attacker can re-run the self-approve op periodically (or approve a wide set of tokens in one crafted stack) and poll/drain whenever a balance appears.

### Likelihood Explanation
- Precondition: attacker only needs to be an "allowed recipient" caller path through `Hinkal.transact` with `externalActionId` pointing at Emporium — this is available to any depositor since `runAction` is `onlyAllowedRecipient`, and `Hinkal` itself is registered as the caller (`msg.sender` to Emporium is `Hinkal`, which is allow-listed). The attacker fully controls `externalActionMetadata` (the `EmporiumStack`), needing no signature (`signerAddress = address(0)`), no special role, and no cooperation from the victim.
- Cost: one ordinary `transact()` call with a trivial deposit (or even a zero-value/self-loop) to plant the approval, plus a plain ERC-20 `transferFrom` call whenever a balance is observed in Emporium.
- The main uncertainty is how often/how much residual balance genuinely accumulates in `EmporiumUpgradeable` under normal operation (this depends on other ops' behavior and is not fully traced here); the standing-approval primitive itself, however, is unconditionally plantable by any attacker via the code path identified.

### Recommendation
- Disallow open-ended `endpoint.call` targets in the stateless branch of `EmporiumUpgradeable.runAction`; restrict `op.endpoint` to an owner-controlled allow-list, or forbid calls whose selector matches common approval/transfer functions (`approve`, `increaseAllowance`, `transfer`, `transferFrom`, `setApprovalForAll`) on the `erc20TokenAddresses` set.
- Alternatively/additionally, after every `runAction` completes, explicitly zero out (or re-verify) allowances Emporium may have granted during the ops loop for all tokens in `circomData.erc20TokenAddresses`, so no approval survives past the transaction boundary.
- Require `stack.signerAddress != address(0)` (mandatory signed operator stack) for any state-mutating call on ERC-20 contracts the action holds balances of, so arbitrary anonymous callers cannot script contract-level actions from Emporium's identity.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (registered as external action), and a mock ERC-20 `TOKEN`.
2. Seed a "residual" balance in `EmporiumUpgradeable` by transferring `TOKEN` directly to it (simulating dust/stranded funds from a prior legitimate transact flow), e.g. `TOKEN.mint(emporium, 100e18)`.
3. Attacker (unprivileged EOA) crafts `CircomData` with `externalActionData.externalActionId` = Emporium's id, `erc20TokenAddresses = [TOKEN]`, `amountChanges[0] = 0`, `onChainCreation[0] = false`, and `externalActionMetadata = abi.encode(EmporiumStack({v:0,r:0,s:0, signerAddress:address(0), ops:[EmporiumOperation({endpoint: TOKEN, invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.approve,(attacker, type(uint256).max))})], maxFee:0, deadline:0}))`. Generate a valid proof for this configuration (all in/out amounts zero except the crafted metadata) and call `Hinkal.transact(...)`.
4. Assert: `TOKEN.allowance(emporium, attacker) == type(uint256).max` after the transaction.
5. As attacker, directly call `TOKEN.transferFrom(emporium, attacker, 100e18)` (no interaction with `Hinkal` at all).
6. Assert: `TOKEN.balanceOf(attacker) == 100e18` and `TOKEN.balanceOf(emporium) == 0`, i.e., tokens left the action while `deltaAmountChanges` sent by Hinkal in that (non-Hinkal) transaction was `0` — violating the stated invariant.
