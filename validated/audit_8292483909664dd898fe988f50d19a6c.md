### Title
Fixed liquidity-burn threshold based only on coin-token decimals blocks legitimate pool creation for low-decimal/low-value token pairs - (File: program/src/processor.rs)

### Summary
`process_initialize2` computes the initial LP mint amount by subtracting a fixed decimal-based minimum-liquidity burn from the raw geometric mean of the deposited coin/pc amounts. The burn amount is derived solely from the **coin** mint's decimals (`lp_decimals = coin_mint.decimals`), completely ignoring the pc (quote) token's decimals or its actual value. This mirrors the reported bug class: a decimals-derived bound that is disconnected from the actual economic value of the tokens, causing legitimate token pairs to be permanently rejected.

### Finding Description
In `process_initialize2`, the LP mint is created with decimals equal to the coin mint's decimals: [1](#0-0) 

The initial liquidity check then subtracts `10^lp_mint.decimals` (i.e. `10^coin_decimals`) from the raw geometric mean `sqrt(pc_amount * coin_amount)`, reverting with `InitLpAmountTooLess` if the result underflows: [2](#0-1) 

This threshold is computed purely from `coin_mint.decimals` and is applied to **raw, un-normalized** token amounts (`amm_pc_vault.amount`, `amm_coin_vault.amount`), without any adjustment for `pc_mint.decimals`. Just as the referenced bond-protocol bug rejects legitimate strike prices because the decimals bound is computed relative to only one side of the pair, here the minimum-liquidity floor is computed relative to only the coin side, ignoring the pc side entirely.

Consider a coin token with high decimals (e.g. 9) paired with a low-value/low-decimal pc (quote) token (e.g. a token with few decimals representing a very cheap asset, analogous to SHIB in the original report). To provide meaningful, economically legitimate liquidity, a user may need `coin_amount` in the billions of raw units while `pc_amount` remains numerically small (because the quote token is cheap). The geometric mean `sqrt(pc_amount * coin_amount)` can then be smaller than `10^coin_decimals` (e.g. `10^9`), even though the pool is economically sound and both vault balances are non-zero and pass all other checks (`InvalidSupply`, etc.). The `checked_sub` then returns `None` and `Initialize2` reverts with `AmmError::InitLpAmountTooLess`, permanently preventing pool creation for that legitimate token pair/amount combination, exactly as low-value quote tokens could not be used for high strike prices in the original report.

### Impact Explanation
This is a denial-of-service on pool creation for certain legitimate coin/pc token decimal and value combinations reachable directly through the public `Initialize2` instruction with attacker/user-chosen mints and amounts — no privileged signer is required. Legitimate token pairs with a wide decimal/value disparity between coin and pc tokens can never form a Raydium AMM pool, since the fixed, decimals-derived burn threshold is unrelated to the actual value being supplied and only considers the coin side.

### Likelihood Explanation
Likelihood is high for any token pair where the coin token has high decimals (e.g. 9, the Solana default) and is paired against a pc token with low decimals or low unit value, a common scenario when new/low-value SPL tokens are used as the quote asset. Any user attempting to create such a pool with economically reasonable (but numerically small in raw geometric-mean terms) amounts will hit this revert deterministically.

### Recommendation
Compute the minimum-liquidity burn threshold using both `coin_decimals` and `pc_decimals` (e.g., normalize both vault amounts via `Calculator::normalize_decimal_v2` against `sys_decimal_value` before computing/subtracting the geometric mean), rather than deriving the LP mint decimals and burn floor from `coin_mint.decimals` alone. This decouples the minimum-liquidity check from an arbitrary single-token decimal count and aligns it with the pool's actual normalized value, as is already done elsewhere in `process_deposit`/`process_withdraw` via `normalize_decimal_v2`.

### Proof of Concept
1. Create mint `COIN` with 9 decimals and mint `PC` with 2 decimals (or any low-decimal token intended to represent a low unit value).
2. Call `Initialize2` supplying `init_coin_amount` and `init_pc_amount` such that `sqrt(init_pc_amount * init_coin_amount) < 10^9` (e.g. `init_coin_amount = 1_000_000` (0.001 COIN) and `init_pc_amount = 500` (5.00 PC) — economically plausible small pool), while both vault amounts are non-zero and pass the `InvalidSupply` checks.
3. `process_initialize2` reaches: [2](#0-1) 
`liquidity = sqrt(500 * 1_000_000) ≈ 22360`, which is far less than `10^9`, so `checked_sub` returns `None` and the instruction reverts with `AmmError::InitLpAmountTooLess`, permanently blocking creation of this otherwise valid pool — regardless of how the user adjusts amounts within realistic economic bounds, since the LP-decimals-derived floor (`10^9`) dwarfs the achievable geometric mean for this decimal combination.
