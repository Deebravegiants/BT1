## Analog Found

### Title
Solvers partially filling proportionally small amounts receive zero escrowed input tokens due to integer division truncation - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntrinsicIntents::_fillSameChain` computes the escrow released to a solver on a **non-final** partial fill as `(order.inputs[i].amount * fillAmount) / totalRequired`, an integer division that truncates toward zero. When a solver's `fillAmount` for a given output pair is small relative to `totalRequired / order.inputs[i].amount`, this expression rounds to exactly `0`, exactly analogous to `previewPoints` in the referenced report zeroing out `amount * duration / MAX_DURATION` for small stakes.

### Finding Description
In `_fillSameChain`: [1](#0-0) 

the escrow release branch only special-cases the fill that exactly completes the pair (`amountFilled == totalRequired`), which was patched (per `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` "Finding #4") to hand the *final* solver the full remaining balance instead of a truncated share. Every **non-final** partial fill still goes through the raw truncating division:
```solidity
escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
```
Meanwhile the solver's output tokens are transferred unconditionally and in full to the beneficiary before this computation, via `beneficiaryTotal = fillAmount + beneficiaryShare`: [2](#0-1) 

There is no minimum-fill-amount check, no precision scaling, and no revert when `escrowedAmount` computes to `0`. If `order.inputs[i].amount < totalRequired` (e.g. a 6-decimal input token escrowed against an 18-decimal output requirement, or any input/output amount pair where the input side is small relative to the output side), any `fillAmount` below `totalRequired / order.inputs[i].amount` truncates the released escrow to zero while the solver still pays out real output tokens to the beneficiary.

### Impact Explanation
A solver executing a legitimate, non-final partial fill can deliver real value (`fillAmount` output tokens to the beneficiary, funded from the solver's own balance) and receive **zero** escrowed input tokens in return — a direct, permanent loss of funds for that fill (the escrow simply remains locked in the contract, to eventually be split among other fills or refunded to the order owner on cancellation, never made whole to the shortchanged solver). This is the same "small amount / small duration → rounds reward to zero" bug class as the referenced report, but manifests as concrete value transfer to the beneficiary at the truncated solver's expense rather than a missed yield.

### Likelihood Explanation
This path is reached by any unprivileged solver calling the permissionless `fillOrder` with a partial amount — no special privileges are required, and the trigger condition (`order.inputs[i].amount * fillAmount < totalRequired`) is easily satisfied whenever the input token has fewer decimals than the output token or the order's amounts are otherwise skewed, which is common for cross-token, cross-decimal same-chain intents (e.g. USDC input vs. DAI/WETH output).

### Recommendation
Apply the same "top up to true remaining balance" logic that was added for the final fill to intermediate escrow computations as well — e.g. track cumulative released escrow (`releasedSoFar`) and release `min(proportional_share, remainingEscrowBalance)` while ensuring `escrowedAmount > 0` whenever `fillAmount > 0`, or revert the fill with a `DustFill`/`AmountTooSmall` style error when the computed `escrowedAmount` would be `0` for a non-zero `fillAmount`, so a solver can never deliver value while receiving nothing.

### Proof of Concept
1. User places a same-chain order with `inputs[0].amount = 100e6` (USDC) and `output.assets[0].amount = 1000e18` (DAI), i.e. `totalRequired = 1000e18`.
2. Solver A calls `fillOrder` with `outputs[0].amount = 1` (1 wei of DAI) as a partial fill.
3. `fillAmount = 1`; `escrowedAmount = (100e6 * 1) / 1000e18 = 0` (floors to zero).
4. Solver A's `beneficiaryTotal = fillAmount = 1` DAI wei is transferred from Solver A to the beneficiary via `IERC20.safeTransferFrom`, per lines 101-102 of `IntrinsicIntents.sol`.
5. `escrowedInputs[0] = TokenInfo({token: usdc, amount: 0})` is what gets released to Solver A via `_withdraw` — Solver A paid real tokens and received nothing back. [3](#0-2)
