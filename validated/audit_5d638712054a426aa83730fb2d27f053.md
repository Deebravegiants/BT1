## Title
`MultiKey`/`multi_key_authentication_key` construction has no uniqueness check on constituent public keys, letting a single keyholder satisfy a K-of-N custody threshold alone - (File: `aptos-move/framework/aptos-stdlib/sources/cryptography/multi_key.move`)

### Summary
The external report's bug class is "a K-of-N authority list is validated for size/order but never checked for duplicates, letting one party count as multiple distinct authorities and silently weaken the threshold." The Aptos-native analog is the `MultiKey` public-key scheme (`aptos_std::multi_key`), which underlies AIP-55 "K of N, mixed-scheme" account authentication (and is used as an alternative to `multisig_account.move` for controlling accounts/resource accounts that may hold APT or object-owned assets).

### Finding Description
`new_multi_key_from_single_keys` validates only count and threshold bounds — it never checks that the `public_keys` vector contains distinct keys: [1](#0-0) 

Compare this with `multisig_account.move`'s `validate_owners`, which *does* enforce uniqueness of the owner list for the classic `MultisigAccount` resource: [2](#0-1) 

The `MultiKeyAuthenticator` verification path (Rust side) confirms that authentication is driven purely by an index-count/bitmap-style check, not by distinctness of the underlying key material — a test in the codebase explicitly demonstrates that a single private key, referenced at two different indices of the same `MultiKey`, can satisfy a `signatures_required = 2` threshold by producing two signatures over the same message with the *same* key: [3](#0-2) [4](#0-3) 

This mirrors the SSVNetwork pattern exactly: `registerValidator()` checked order/count of operator IDs but not uniqueness, allowing one operator to occupy multiple "slots" and undermine consensus among supposedly-independent operators. Here, `new_multi_key_from_single_keys`/`to_authentication_key` check count/threshold bounds but not uniqueness of keys, allowing one keyholder to occupy multiple "slots" and undermine the K-of-N custody guarantee.

### Impact Explanation
Accounts, resource accounts, or object-controlling signers protected by a `MultiKey` authentication key (e.g., a "2-of-3" or "3-of-5" custody policy meant to require independent co-signers before authorizing a transfer of APT, fungible-asset withdrawal, object `TransferRef` usage, or code-object upgrade) can be constructed — either at account creation or via `rotate_authentication_key`/rotation-capability flows that accept an arbitrary `MultiKey` — with a duplicated public key entry. If any party responsible for supplying/approving the key list (a service provisioning custody wallets, a co-signer submitting their own key twice, or a compromised single co-signer) inserts the same key twice, the effective number of *independent* signers required drops below the intended threshold, while `signatures_required` still nominally shows the original K. That single keyholder can then unilaterally authorize transactions from the account, defeating the entire purpose of the multi-party custody control and enabling unauthorized transfer/drain of any APT, fungible assets, or object ownership tied to that account's authentication key.

### Likelihood Explanation
This requires that a `MultiKey`-controlled account's key list is not independently vetted for uniqueness by the party relying on the K-of-N guarantee (e.g., an exchange or custody provider generating multi-key wallets, or a smart contract/rotation flow that accepts a `MultiKey` blob from user input without off-chain deduplication). Because the framework itself performs no on-chain uniqueness check, any downstream code that trusts `new_multi_key_from_single_keys`'s success as proof of "K independent authorizers" is silently unsafe. This is a plausible, unprivileged root cause (any account owner/co-signer choosing the key list), though it depends on off-chain custody tooling not separately deduplicating keys — which is a reasonable operational assumption to violate given no on-chain guard exists.

### Recommendation
Add a duplicate check in `new_multi_key_from_single_keys` (and correspondingly in `deserialize_multi_key`/`new_public_key_from_bytes`) analogous to `multisig_account::validate_owners`, aborting if any two `AnyPublicKey` entries in `public_keys` are equal, so that `signatures_required` always reflects the true number of independent authorizers.

### Proof of Concept
1. Construct `MultiKey { public_keys: [pk_A, pk_A, pk_B], signatures_required: 2 }` via `new_multi_key_from_single_keys`, which succeeds since only length/threshold are checked.
2. Derive the authentication key via `to_authentication_key` and rotate an account (or create a new one) to this key, intending "2 of {A,B}" custody.
3. Holder of `pk_A` alone signs the same message twice, submitting a `MultiKeyAuthenticator` with two entries at the indices corresponding to `pk_A`'s two slots (as shown feasible by the existing `mk_auth_12`-style test at `types/src/transaction/authenticator.rs:1920-1926`, generalized to `pk_A` occupying both indices).
4. The bitmap-count/threshold check in the verifier is satisfied with `num_ones_in_bitmap == 2 == threshold`, and `signer B` was never required — `pk_A`'s holder alone can authorize withdrawal/transfer of any custody-controlled asset.

Note: I was not able to trace a concrete production call site (e.g., a specific custody-provisioning module in this repo) that constructs `MultiKey` from externally-supplied, unvalidated key lists without its own deduplication — that would be needed to fully confirm exploitability end-to-end on a live custody flow. Given index-size limits on the codebase search, a Devin session with full repo access is recommended to check all callers of `new_multi_key_from_single_keys`/`rotate_authentication_key` for any missing deduplication before treating this as fully confirmed at Critical severity versus a High/informational framework-level gap.

        );
        assert!(
            (signatures_required as u64) <= num_keys,
            error::invalid_argument(E_INVALID_MULTI_KEY_SIGNATURES_REQUIRED)
        );
        MultiKey { public_keys: single_keys, signatures_required }
    }
