Now I have enough to confirm the analog precisely: `build_tx_receipts` correctly reconciles per-request success against the on-chain event set, so the actual `TxReceipt`s emitted are per-`PostRequest`, not per-`Message`. However, the "coarse status" (`unsuccessful`) that drives retry/parking is decided at the *message* level, not the request level, in `submit_messages`.

### Title
Relayer marks an entire multi-request batch as delivered when only some `PostRequest`s inside it landed on-chain, silently dropping the rest — ([File: tesseract/messaging/evm/src/tx.rs])

### Summary
`submit_messages` (the legacy, one-tx-per-`Message` submission path used for single-item batches and by `tesseract/messaging/tron/src/tx.rs`) decides whether a `Message::Request` is "unsuccessful" (and therefore eligible to be parked and retried) purely on whether the transaction's log set is *empty*, not on which individual `PostRequest` commitments inside that message actually emitted a `PostRequestHandled` event.

### Finding Description
A single ISMP `RequestMessage` batches many `PostRequest` leaves in one on-chain call to `EvmHost.dispatchIncoming` / `HandlerV2.handlePostRequests`. `EvmHost.dispatchIncoming` deliberately swallows a reverting per-request module callback rather than reverting the whole transaction — this is documented at [1](#0-0) . That means a mined, successful transaction can deliver a strict subset of the batch's requests while silently dropping others (analogous to a GSO super-frame where some inner segments are lost but the aggregate transmit path reports success).

The relayer's serial-submission loop only asks "did this transaction emit *any* commitment logs at all?" to decide whether the whole `Message` needs to be retried: [2](#0-1) 

If `evs` is non-empty (i.e., at least one of the many requests inside that message succeeded), the entire `Message` — including any requests whose commitment never appeared in `evs` — is treated as fully delivered and is never added to `unsuccessful`. Downstream, `build_tx_receipts` does correctly recompute receipts per individual `PostRequest` by checking `receipts.contains(&commitment)`: [3](#0-2) 

But that finer-grained check only produces the *delivered* receipt list; it is never used to compute which requests were *not* delivered. `unsuccessful` (the only signal fed to retry/parking logic in `park_undelivered`/`retries.rs`) remains whole-message granularity: [4](#0-3) [5](#0-4) 

So any `PostRequest` inside a partially-successful message is neither recorded as delivered (no receipt, no relayer fee claim) nor recorded as failed (not parked, never retried). It is permanently lost from the relayer's bookkeeping even though the source chain still shows it as pending. The same "only-check-overall-emptiness" pattern is used identically in the TRON transport at [6](#0-5) , and `submit_batch_messages`/`build_tx_receipts` for the atomic `IHandlerV2.batchCall` path is safe by contrast because Solidity's atomic revert guarantees "all or nothing" — the bug is specific to the non-atomic `dispatchIncoming` swallow-per-request behavior combined with message-level (not request-level) unsuccessful tracking in the serial path.

### Impact Explanation
A request that is silently dropped by `EvmHost.dispatchIncoming`'s per-request callback swallow, inside an otherwise-successful `submit_messages` transaction, is never retried by any relayer (because it's not parked as `unsuccessful`) and never claims delivery fees (because it has no `TxReceipt`). The end-user's cross-chain message (a token mint, an intent fill instruction, etc.) is permanently unable to be delivered through this relayer path — a route unable to deliver messages, matching the "permanent freezing" / "route unable to deliver" impact bar in the validation rules. This is a Medium-severity finding: it requires a specific coincidence (a multi-request `Message` sent via the non-batch `submit_messages` path where `dispatchIncoming` swallows one inner callback but the tx as a whole still emits at least one other request's event) and its scope is limited to that one relayer's tracking of stuck requests (another relayer's independent submission attempt is unaffected), rather than an attacker-forced, reliably-reproducible fund loss.

### Likelihood Explanation
Likelihood is limited by the fact that `submit_messages` (the affected serial path) is exercised only for single-item batches or non-EVM-HandlerV2 transports per `handle_message_submission`'s doc comment ( [7](#0-6) ) — the primary batching path (`submit_batch_messages`) is atomic and unaffected. However, a single `Message::Request` can still legitimately carry multiple `PostRequest` leaves (see `RequestMessage.requests: Vec<PostRequest>` used throughout `build_tx_receipts`), so the "one message, multiple requests, partial callback failure" scenario is a normal traffic pattern, not a contrived edge case, whenever any per-request module callback can revert (e.g. a receiving pallet/contract rejecting a malformed or economically unprofitable payload) while the surrounding request batch still contains at least one deliverable request.

### Recommendation
Compute `unsuccessful` in `submit_messages` (and the TRON equivalent) at the `PostRequest` level, mirroring the granularity already used in `build_tx_receipts`: for each `Message::Request`, diff its `requests` against the commitments actually present in the transaction's receipt logs, and only retain the ones *not* found as the request-level unsuccessful set (reconstructing a `Message::Request` containing just the missing leaves, or otherwise surfacing per-request status) rather than gating retry eligibility on `evs.is_empty()` for the whole message.

### Proof of Concept
1. A relayer collects a `RequestMessage` containing `PostRequest`s A and B addressed to the same destination module, and submits it via the single-tx path in `submit_messages`.
2. The destination `EvmHost.dispatchIncoming` processes A successfully (emits `PostRequestHandled` for A) but the module callback for B reverts; `dispatchIncoming` swallows that revert per its documented behavior and the transaction still succeeds overall.
3. `wait_for_success` returns `evs = {commitment_A}` (non-empty) at [8](#0-7) .
4. In `submit_messages`, `evs.is_empty()` is `false`, so the `RequestMessage` (carrying both A and B) is never pushed to `unsuccessful` ( [9](#0-8) ).
5. `build_tx_receipts` produces a `TxReceipt` for A only (B's commitment is absent from `receipts`), and `unsuccessful` is empty, so B is never parked for retry by `park_undelivered`/`retries.rs`. B's request is stuck forever from this relayer's perspective.
