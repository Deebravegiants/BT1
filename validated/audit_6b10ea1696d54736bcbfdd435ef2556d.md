### Title
Unconditional `calc_take_pnl` invariant check in `Deposit`/`Withdraw`/`WithdrawPnl` can permanently freeze LP funds due to decimal-normalization rounding drift - (File: program/src/processor.rs)

### Summary
`Processor::calc_take_pnl` enforces a hard invariant that the current pool value (`total_pc_without_take_pnl * total_coin_without_take_pnl`) must be `>=` the tracked "last-pnl" snapshot (`target_orders.calc_pnl_x * calc_pnl_y`), otherwise it returns `AmmError::CalcPnlError` and aborts the whole instruction. This function is called unconditionally inside `process_deposit`, `process_withdraw` (unless `status == WithdrawOnly`), and `process_withdrawpnl`. If the tracked snapshot ever drifts above the real pool value due to integer-division rounding in the decimal-normalization helpers, all future deposits/withdrawals/pnl-withdrawals for that pool revert permanently, analogous to the referenced report's stateful "claim" check that can permanently block legitimate user actions once triggered.

### Finding Description
`calc_pnl_x`/`calc_pnl_y` are the normalized ("sys-decimal") snapshot of pool reserves at the last time PnL was taken, and they are updated on every `Deposit`/`Withdraw`/`WithdrawPnl` using `Calculator::normalize_decimal_v2` / `Calculator::restore_decimal`: [1](#0-0) 

These helpers perform `val * sys_decimal_value / 10^native_decimal` and `val * 10^native_decimal / sys_decimal_value` respectively, both using truncating integer division: [2](#0-1) 

`calc_take_pnl` then requires the real pool value to be `>=` the restored (`restore_decimal`) snapshot value, or it fails hard: [3](#0-2) [4](#0-3) 

This check is invoked unconditionally in `process_deposit`: [5](#0-4) 

and in `process_withdraw`, gated only by the (admin-controlled) `AmmStatus::WithdrawOnly` flag: [6](#0-5) 

and in `process_withdrawpnl`: [7](#0-6) 

Because the `normalize_decimal_v2`/`restore_decimal` round-trip is lossy (floor division on both legs), repeated deposit/withdraw cycles accumulate small discrepancies between the true vault balances and the tracked `calc_pnl_x`/`calc_pnl_y` snapshot. The project's own unit test `test_calc_pnl_precision` exercises exactly this scenario (successive withdraws recomputing `calc_pnl_x`/`calc_pnl_y` via the same normalize/restore round trip) to probe precision behavior: [8](#0-7) 

If the accumulated rounding ever pushes `calc_pnl_x * calc_pnl_y` (restored) above the real current `pc_vault * coin_vault` product — e.g., through a sequence of small deposits/withdraws that a normal unprivileged LP can perform — `calc_take_pnl` returns `AmmError::CalcPnlError` on every subsequent call. Since `Deposit` always calls it, and `Withdraw` only skips it when the pool has been set (by an admin) to `WithdrawOnly` status, ordinary users lose the ability to deposit or withdraw LP tokens through the normal, permissionless path once the state is reached, without exploit-specific admin cooperation.

### Impact Explanation
Once triggered, this is a self-inflicted, permanent denial-of-service on core AMM operations (`Deposit`, `Withdraw`, `WithdrawPnl`) reachable purely through repeated unprivileged deposit/withdraw calls with attacker-chosen amounts. Because `Withdraw` also calls `calc_take_pnl` under default statuses, LPs can be unable to redeem their LP tokens for underlying coin/pc — i.e., permanent freezing of LP funds — until/unless an admin manually flips the pool to `WithdrawOnly` (a privileged, out-of-band remediation not guaranteed to happen). This matches the "permanent freezing of user or LP funds" bar.

### Likelihood Explanation
This requires no privileged action or malicious validator — only a series of ordinary `Deposit`/`Withdraw` calls with attacker- or naturally-occurring amounts that maximize rounding loss (e.g., repeated deposits/withdraws with amounts chosen at the boundary of the decimal-normalization division). The likelihood of hitting this exact edge in practice under organic trading is uncertain without a full arithmetic proof of a concrete amount sequence that flips the inequality (I was not able to fully construct and confirm a numeric counter-example within this investigation), so confidence in exploitability at any given `sys_decimal_value`/decimals configuration is moderate, not certain.

### Recommendation
- Avoid a strict inequality that can hard-fail transaction processing based on lossy round-tripped decimal math; instead, clamp/saturate the restored snapshot to the actual current reserves (e.g., `min(calc_pc_amount, total_pc_without_take_pnl)`) rather than reverting.
- Alternatively, track `calc_pnl_x`/`calc_pnl_y` in the same native units as the vault balances (or use consistently rounding in the "safe" direction, i.e., always floor `calc_pnl_x`/`calc_pnl_y` down relative to actual reserves) so the invariant can never be violated by rounding alone.
- Add an admin/permissionless recovery path that can reset `target_orders.calc_pnl_x`/`calc_pnl_y` to the current reserve values without requiring `calc_take_pnl` to succeed first, breaking the circular dependency that currently prevents recovery via normal Deposit/Withdraw.

### Proof of Concept
A concrete failing amount sequence was not fully derived and verified in this session (would require enumerating `normalize_decimal_v2`/`restore_decimal` rounding error under specific `pc_decimals`/`coin_decimals`/`sys_decimal_value` combinations across many deposit/withdraw iterations, similar to the existing `test_calc_pnl_precision` test at program/src/processor.rs:3090-3212, which already demonstrates the mechanism of iterative snapshot drift via the same normalize/restore round trip, but stops short of showing the inequality flip). This should be validated with a dedicated fuzz/property test that repeatedly calls `process_deposit`/`process_withdraw` with small amounts and asserts whether `calc_take_pnl`'s invariant can be violated for realistic decimal configurations.

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }
