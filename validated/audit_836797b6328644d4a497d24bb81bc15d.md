### Title
Webhook shop-domain header is trusted for tenant identification but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC digest over the raw request body only, while the `shop` (tenant identifier), `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers and handed to the host application's webhook handler as trusted data. This breaks the intended identity binding: `shop_authenticated == shop_acted_upon` does not hold, because `shop` is parsed from headers that are never part of the signed payload.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC-SHA256 over `verifiable_query.to_signable_string` with the app's `api_secret_key` and comparing it (via `OpenSSL.secure_compare`) to the `hmac` value: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body — never the headers: [2](#0-1) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all extracted directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the signed body: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` validates only the HMAC of the body and then dispatches directly to the registered handler, passing the header-derived `shop` value into `WebhookMetadata` without any additional check that ties it to the signed content: [4](#0-3) [5](#0-4) 

The gem's own documentation confirms host applications are expected to use `data.shop` as the trusted tenant identifier for downstream actions (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [6](#0-5) 

Because a single app-level `api_secret_key` is used to sign webhooks for every merchant shop that installs the app, an attacker who controls (or installs) their own shop can capture a legitimately-signed webhook (valid `hmac-sha256` header for a given raw body from Shopify), and replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value naming a victim shop. `HmacValidator.validate` will still succeed, because the signature only covers the body, not the shop header — so `Registry.process` will accept the request and hand the handler a `WebhookMetadata` object claiming to be for the victim shop, with attacker-controlled `topic`/`body` semantics fixed only by what the attacker's own account produced.

This is the exact bug class from the analog report: a field (`shop`) that is acted upon by downstream logic but not covered by the authentication/integrity check (the HMAC), producing an equality break of `shop_that_signed_this_HMAC == shop_the_handler_believes_sent_it`.

### Impact Explanation
This enables cross-tenant confusion: the receiving application (via the gem's documented usage pattern) will process the forged webhook as if it originated from the victim shop, potentially triggering tenant-scoped side effects (e.g., data sync, cache invalidation, order/customer processing, or uninstall cleanup for `app/uninstalled`) attributed to the wrong merchant. Depending on how the host app uses `data.shop` (e.g., looking up and mutating that shop's stored session/data), this can result in cross-tenant data corruption or unauthorized actions against a shop the attacker does not control — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is constrained by two factors: (1) the attacker must have a real, working installation of the target app on their own shop to obtain a validly-signed webhook body/HMAC pair, and (2) the impact depends on the host application's handler logic trusting `data.shop` for authorization/tenant-scoping decisions, which is exactly the pattern the gem's own documentation recommends. Given the documented usage pattern actively encourages trusting `data.shop`, and Shopify's real-world webhook signing scheme genuinely only signs the body (not headers) system-wide, this is a plausible, low-cost replay once initial app installation is obtained.

### Recommendation
- Include `shop`, `topic`, and `webhook_id` (at minimum `shop`) as part of the signable content used for HMAC verification, or independently verify the `shop` header against a known/expected value (e.g., cross-check against the shop associated with the `webhook_id`/subscription, or maintain a mapping of installed shops and reject webhooks whose header shop was never registered for that `webhook_id`).
- Document explicitly in `docs/usage/webhooks.md` that `data.shop` is not itself cryptographically bound to the payload and must not be used as the sole tenant-authorization key without additional verification (e.g., matching against `webhook_id` registered per shop, or shop allow-listing).
- Consider following Shopify's guidance to deduplicate/verify webhooks using `webhook_id` plus a per-shop registry lookup rather than trusting the raw header value directly.

### Proof of Concept
1. App developer installs their own copy of the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimately HMAC-signed webhook, e.g. `app/uninstalled`, to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some raw JSON body.
3. Attacker captures this full raw request (body + HMAC header) since it is delivered to infrastructure they control.
4. Attacker replays the identical raw body and identical `x-shopify-hmac-sha256` value to the same endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request#hmac` reads only the (unchanged) HMAC header value, and `#to_signable_string` returns only the (unchanged) raw body — so `HmacValidator.validate` in `Registry.process` succeeds: [7](#0-6) 
6. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes it as an authentic event for the victim tenant, per the documented handler pattern.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
