Confirmed: `HttpClient#initialize` builds `@base_uri` directly from `session.shop` (unless `Context.api_host` is set), with no sanitization performed inside the client itself. [1](#0-0)  This makes `session.shop` the sole trust boundary for where `client_secret` gets sent for any OAuth grant flow.

### Title
Token Exchange sends `client_secret` to an unvalidated host derived from JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` extracts the shop host from the JWT `dest` claim and uses it, unsanitized, to build the HTTP client that transmits the app's `client_secret` to `https://{shop}/admin/oauth/access_token`. Every sibling OAuth-grant method in this gem (`client_credentials`, `refresh_token`, `migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before using the shop value for the same purpose — `exchange_token` is the one exception.

### Finding Description
`JwtPayload#shop` simply strips the `"https://"` prefix from the token's `dest` claim with no domain allow-listing: [2](#0-1) 

`exchange_token` takes this unvalidated value and uses it directly to build the session/client that will carry the `client_secret`: [3](#0-2) 

Contrast this with the other three grant flows in the same module/family, which all call `Utils::ShopValidator.sanitize!(shop)` — which restricts the host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before constructing the session used for the credentialed request: [4](#0-3) [5](#0-4) [6](#0-5) 

`Clients::HttpClient#initialize` performs no host validation of its own — it builds the request base URI directly from `session.shop`: [7](#0-6) 

`Utils::ShopValidator.sanitize_shop_domain`/`sanitize!` is precisely the mechanism designed to close this gap by binding "the host that receives the `client_secret`" to a trusted Shopify domain: [8](#0-7) 

The binding this breaks is: *host validated (none, in `exchange_token`)* ≠ *host that receives the `client_secret` (`dest_shop`, taken as-is from the JWT `dest` claim)*.

### Impact Explanation
Note on exploitability/confidence: the `dest` claim is inside a JWT that this gem decodes and verifies with `JWT.decode(token, api_secret_key, true, ...)`, keyed on the app's own `api_secret_key` (or `old_api_secret_key`) — i.e., a genuine Shopify-issued session token for this app. [9](#0-8)  Given the merchant/browser context in which embedded-app session tokens are issued, it is not established that an unprivileged internet user (without possessing or forging a token signed by the app's own secret) can supply an arbitrary `dest` value here without already controlling something equivalent to the app's secret — which the task's own scope rules explicitly exclude ("anything requiring `api_secret_key` ... leaked credentials"). I could not find, within `lib/shopify_api/**` (excluding `rest/resources`), a code path that lets an unauthenticated caller mint or relay a `dest` value into `exchange_token` without already holding a validly-signed session token.

### Likelihood Explanation
Low/unconfirmed under this gem's own trust model: the identified inconsistency (missing `ShopValidator.sanitize!` call in `exchange_token` versus its sibling methods) is a real code-level asymmetry and a latent defense-in-depth gap, but a concrete exploitation path that crosses an authentication boundary without already needing the app's `client_secret`-derived signing capability was not established from the code alone.

### Recommendation
For defense-in-depth and consistency with the other grant flows in the same file, `exchange_token` should validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` (or an equivalent allow-list check against `TRUSTED_SHOPIFY_DOMAINS`) before constructing `shop_session`/`Clients::HttpClient`, exactly as `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token` already do.

### Proof of Concept
Not established as concretely exploitable from this codebase alone — see the confidence caveat in "Impact Explanation." No proof-of-concept demonstrating an unprivileged-internet-user path to a forged/attacker-controlled `dest` claim (without already holding secret-signing capability) could be constructed from the available code.

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
