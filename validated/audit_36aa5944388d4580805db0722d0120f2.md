Confirmed: `ShopValidator.sanitize!` exists in the codebase but is never invoked anywhere in the webhook processing path, and `Utils::HmacValidator.validate` only signs `to_signable_string` which returns `@raw_body` in `Request#to_signable_string` — the `shop-domain` header is never part of the signed material.

### Title
Webhook `shop` identity spoofing via unsigned `X-Shopify-Shop-Domain` header - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`Registry.process` validates only the HMAC of the raw webhook body via `Utils::HmacValidator.validate`, then trusts `request.shop` (read straight from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header) when building `WebhookMetadata` passed to the app's handler. Because the HMAC signature never covers the shop header, and `Utils::ShopValidator.sanitize!` is never called anywhere in this path, an attacker can take a validly-signed webhook body from their own shop and resend it with an arbitrary `shop` header value, causing the host app's handler to process attacker-controlled data under any shop identity of the attacker's choosing.

### Finding Description
The intended binding is: `shop the handler believes generated the data (WebhookMetadata#shop) == shop that Shopify actually authorized/signed that payload for`. This binding is broken.

- `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read purely from an HTTP header with no cryptographic tie to the body: [2](#0-1) .
- `Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received HMAC header — it never includes the shop header in the signed material: [3](#0-2) .
- `Registry.process` gates only on that body HMAC, then immediately builds `WebhookMetadata` using `request.shop` with no call to `ShopValidator.sanitize!` or any other check binding shop to the signature: [4](#0-3) .
- `Utils::ShopValidator.sanitize!` exists in the codebase and is used elsewhere (OAuth/token exchange/refresh flows), but is never invoked in the webhook path, confirmed by `grep_search` showing no reference to `ShopValidator` in `registry.rb` or `request.rb`.

Exploit flow: the attacker creates a development shop, installs the target app, and lets it register a webhook topic that the target app already handles (topics are public/documented). Shopify sends the attacker a legitimately HMAC-signed webhook for their own shop. The attacker intercepts/replays that exact request to the app's webhook endpoint, changing only the `X-Shopify-Shop-Domain` header to an arbitrary string (e.g. `victim-shop.myshopify.com` or any string, since no domain-format check even runs). Because the signature covers only the body, `HmacValidator.validate` still returns `true`, `Registry.process` finds the handler for the topic, and calls `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))`. The host application logic keyed off `data.shop` treats attacker data as data belonging to an arbitrary shop.

### Impact Explanation
This is a cross-tenant authentication bypass: the app's webhook handler — and any business logic keyed off `WebhookMetadata#shop` (e.g., updating merchant records, triggering per-shop side effects, writing to per-shop stores) — executes under a shop identity fully chosen by the attacker, with no relation to the shop that actually produced the signed payload. Any topic the app has registered a handler for is exploitable this way, and the attack is trivially repeatable against arbitrary shop identifiers per request (no need to know or compromise the victim's shop credentials), matching the Critical — cross-tenant access / authentication bypass category.

### Likelihood Explanation
Preconditions are minimal and entirely attacker-controlled: create a free development shop, install the target app (a standard, unprivileged action), and let the app register at least one webhook (`Registry.add_registration`/`register`) — a near-universal configuration for real apps. The attacker needs no `api_secret_key`, access token, or other secret; they only need to relay their own legitimately-received webhook HTTP request with one header changed. Feasibility is high and the attack is fully repeatable with different spoofed shop values.

### Recommendation
Bind the trusted shop identity to the verified signature. Either (a) include the shop header (and topic) as part of the HMAC-signed material check, comparing it against a shop value obtained independently (e.g., cross-checked against the session/shop that the webhook subscription was registered for), or (b) run `Utils::ShopValidator.sanitize!(request.shop, myshopify_domain: ...)` in `Registry.process` and additionally verify that `request.shop` matches a shop the app actually has an active installation/session for before invoking the handler, rejecting the webhook otherwise.

### Proof of Concept
Minitest plan (no live shop, no WebMock needed since `Registry.process` takes a `Request` object directly):
```ruby
def test_process_trusts_spoofed_shop_header_with_valid_body_hmac
  ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)

  raw_body = '{"id":1}'
  valid_hmac = Base64.encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", raw_body)
  ).strip

  spoofed_request = ShopifyAPI::Webhooks::Request.new(
    raw_body: raw_body,
    headers: {
      "X-Shopify-Topic" => "orders/create",
      "X-Shopify-Hmac-Sha256" => valid_hmac,
      "X-Shopify-Shop-Domain" => "victim-shop-the-attacker-does-not-own.myshopify.com",
      "X-Shopify-Api-Version" => "2024-01",
      "X-Shopify-Webhook-Id" => "abc",
    },
  )

  received_shop = nil
  handler = ->(data:) { received_shop = data.shop }
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "orders/create", delivery_method: :http, path: "/webhooks",
    handler: handler_double(handler),
  )

  ShopifyAPI::Webhooks::Registry.process(spoofed_request)

  # Binding check: shop handler received == shop attacker actually owns? -> FALSE, proving the break
  assert_equal "victim-shop-the-attacker-does-not-own.myshopify.com", received_shop
end
```
Assertions: (1) `HmacValidator.validate(spoofed_request)` returns `true` despite the shop header being unrelated to the attacker's real shop; (2) `WebhookMetadata#shop` delivered to the handler equals the spoofed value, not any shop the attacker legitimately controls, proving `shop the handler believes it received data for != shop that authorized the data`.
