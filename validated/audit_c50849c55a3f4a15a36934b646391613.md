Based on the investigation, I found a valid analog in `IntentGatewayV2.sol`'s predispatch flow. The bug-class match to the Uniswap `skim()` report is: using raw `balanceOf()` of a shared, un-owned helper contract as the amount to sweep, rather than tracking the delta actually produced for a specific operation — exactly the accounting pattern CFC's attacker exploited on the LP pair.

### Title
Predispatch calldata can leave tokens permanently stranded in the shared `CallDispatcher` because `placeOrder` only sweeps balances for tokens declared in `order.inputs` - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`placeOrder`'s predispatch path funds the singleton `CallDispatcher` contract, executes arbitrary attacker-supplied calldata against it, then sweeps back only the token types that appear in `order.inputs`, using the dispatcher's raw `balanceOf()`/`.balance` as the swept amount rather than a delta computed against what the predispatch call was supposed to produce.

### Finding Description
In `placeOrder` (`evm/src/apps/IntentGatewayV2.sol`), when an order has `predispatch.call` and `predispatch.assets`, funds are moved to the shared, stateless `_params.dispatcher` contract and `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` executes fully attacker-controlled calldata against it [1](#0-0) .

The sweep-back loop then iterates only over `order.inputs` (`inputsLen`), reading `IERC20(token).balanceOf(dispatcher)` / `address(dispatcher).balance` as the amount to sweep, for each token declared as an input of *this* order: [2](#0-1) 

Because the caller fully controls `order.predispatch.call`, they can route the escrowed predispatch assets through a swap or multi-hop call that produces one or more token types that are *not* listed in `order.inputs`. Only tokens matching `order.inputs[i].token` are ever transferred back to the gateway; anything else the predispatch call produced (or that the caller's own calldata leaves behind, e.g. partial swap output, unrelated dust tokens, extra hop outputs) stays on the `CallDispatcher` forever.

`CallDispatcher` (`evm/src/utils/CallDispatcher.sol`) has no owner, no rescue/withdraw function, and only exposes `dispatch(bytes)`, which executes arbitrary `Call[]` but requires the caller to supply the exact calls — there is no privileged sweep path: [3](#0-2) . Since the contract is a fixed, publicly known address shared by every order (both `placeOrder`'s predispatch path and `IntentsBase._execute`'s postdispatch path use the same `_params.dispatcher`), any token type that ends up there without a matching `order.inputs`/`order.output.assets` entry for some future order is permanently unrecoverable — nobody, including governance, can pull an arbitrary token off it because `dispatch` only forwards calls the caller supplies, and the caller cannot forge a call that transfers dispatcher-held tokens to themselves without going through the constrained `placeOrder`/`_execute` sweep logic that only recognizes declared token sets.

This is the same root-cause shape as the CFC/Uniswap `skim()` report: the sweep amount is derived from the shared contract's live `balanceOf()`/`.balance` rather than a value tied to a specific, attributable flow, so any balance sitting on the shared contract outside the expected token set is either (a) unrecoverable dust that gets permanently stuck, or (b) — if it does happen to match a *future* order's declared input token — swept in full and misattributed as that unrelated order's "dust", diverging from the actual owner's intent.

### Impact Explanation
Tokens produced by a predispatch call that fall outside the order's declared `inputs` set are permanently frozen in the `CallDispatcher`, with no privileged or unprivileged path to recover them (satisfies "permanent freezing of funds"). This is triggerable by any ordinary user submitting a single `placeOrder` transaction with predispatch calldata that produces more/other token types than it declares as inputs — no special privileges, relayer/consensus proof, or governance action required.

### Likelihood Explanation
Predispatch calldata routing through DEX swaps or multi-hop calls commonly produces intermediate or leftover token amounts (slippage remainders, multi-token swap outputs, fee-on-transfer residues); the codebase's own documentation and tests describe predispatch as an open swap-then-escrow mechanism (`evm/tests/foundry/IntentGatewayV2Test.sol` predispatch/Uniswap tests), so ordinary usage — not just an adversarial construction — can produce untracked leftover balances on the shared dispatcher. Any user error or partially-successful swap path reaches this condition without any adversarial intent required, making likelihood high for accidental fund loss and straightforward for a deliberate attacker to also misdirect matching-token dust into their own order.

### Recommendation
Track and sweep every token type actually touched by the predispatch/postdispatch calldata (e.g., by having callers declare the full set of tokens the `CallDispatcher` may end up holding, or by measuring per-call deltas against a snapshot taken immediately before/after each individual `Call`), and add a privileged rescue path on `CallDispatcher`/`IntentGatewayV2` (gated by governance/host) to recover any token balance not matched by a pending order, so that dust or mis-produced tokens are not permanently unrecoverable.

### Proof of Concept
1. User A calls `placeOrder` with `predispatch.assets = [TokenX: 100]` and `predispatch.call` that swaps `TokenX` into `TokenY` and `TokenZ` (e.g., via a multi-hop router call), but sets `order.inputs = [TokenY: amount]` only (omitting `TokenZ`).
2. `dispatch(order.predispatch.call)` executes the swap; `CallDispatcher` now holds both `TokenY` and `TokenZ`.
3. The sweep loop in `placeOrder` (`evm/src/apps/IntentGatewayV2.sol:263-287`) only builds a `transferCalls` entry for `TokenY` (the sole entry in `order.inputs`); `TokenZ` is never referenced.
4. `TokenZ`'s balance remains on `CallDispatcher` indefinitely — `CallDispatcher.dispatch` has no function that lets any account, privileged or not, extract `TokenZ` without another order coincidentally declaring `TokenZ` as one of its `order.inputs`, and even then only up to that order's declared amount is escrowed to the rightful flow (the rest becomes generic "dust" attributed to an unrelated order), demonstrating both permanent freezing and fund misattribution.

contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
}
