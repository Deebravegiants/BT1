### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verification performed by `ShopifyAPI::Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` only proves the body was signed by Shopify. The `shop`, `topic`, `webhook_id` and `api_version` values — which are read straight from unauthenticated HTTP headers — are never included in the signed content, yet they are trusted and passed directly into the app's webhook handler as the tenant-identifying `shop` field.

### Finding Description
`Registry.process` verifies authenticity like this: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`: [2](#0-1) 

But `Request#to_signable_string` is defined as just the raw body: [3](#0-2) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight out of attacker-controllable headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.) with no cryptographic binding to the body or to each other: [4](#0-3) 

Those unauthenticated header values are then forwarded verbatim into the app's `WebhookMetadata`/handler as the shop-of-record for the event: [5](#0-4) 

This breaks the equality the gem's documentation implies it enforces — "This will verify the request did indeed come from Shopify" — because the signature only proves *some* valid body was signed by Shopify for *some* shop; it does not prove the `x-shopify-shop-domain`/`x-shopify-topic` headers accompanying that body are the ones Shopify actually sent with it: [6](#0-5) 

**Broken binding (equality that should hold but doesn't):**
`shop header value used by handler == shop the HMAC was computed for`

Before attack: Shopify sends body B with `X-Shopify-Shop-Domain: shop-A.myshopify.com`, HMAC = `HMAC(secret, B)`. Both sides agree the event is for shop A.

After attack: Attacker (who legitimately owns/operates `shop-A` and can trigger events there, e.g. any merchant installing the victim app on their own free store) captures a valid `(B, HMAC(secret,B))` pair, then replays it to the app's webhook endpoint with `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`). `HmacValidator.validate` still succeeds because it never looked at those headers, and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"`.

### Impact Explanation
Any downstream app logic that trusts `WebhookMetadata#shop` (or `#topic`) to route/store/act on data per-tenant — which is exactly the intended usage pattern documented in `docs/usage/webhooks.md` — can be made to attribute attacker-supplied webhook content to an arbitrary victim shop. This is a cross-tenant data/identity confusion: the attacker doesn't need the victim's or the app's credentials, only one legitimately signed body from their own (attacker-controlled) shop, which they can trivially obtain by installing the app and triggering any webhook-generating action on their own store.

### Likelihood Explanation
High. Obtaining a valid signed webhook body is trivial for any unprivileged user who can install the target app on a shop they control (free dev stores are readily available), and replaying it with a modified `X-Shopify-Shop-Domain`/`x-shopify-topic` header requires only basic HTTP tooling — no access to `api_secret_key`, tokens, or TLS interception.

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable content, or otherwise cryptographically bind them to the verified body (e.g., require the HMAC to cover a canonical string of `shop|topic|webhook_id|body`, matching Shopify's actual signing scheme if it does so) before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document loudly that `Request#shop`/`#topic` are NOT authenticated by the HMAC and must be independently verified by the host app (e.g., against a known list of installed shops) before use.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent by Shopify.
2. Attacker sends a forged HTTP request to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — matches `H` because `to_signable_string` only returns `B`.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: JSON.parse(B), ...)`, causing the app to process/store attacker-controlled data under the victim shop's identity.
