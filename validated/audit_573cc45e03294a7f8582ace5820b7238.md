## Title
Unprivileged gateway users can overwrite another in-flight request's callback via MessageID collision, causing DoS and cross-user response confusion - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` writes a newly submitted request's callback into the shared `savedCallbacks` map keyed solely by the client-supplied `msg.Body.MessageID`, with no check for an existing in-flight entry and no binding to the sender's identity. Since `MessageID` uniqueness/ownership is never validated or enforced anywhere in the request path, an unprivileged client can submit a colliding `MessageID` to hijack another user's in-flight request slot.

## Finding Description
The gateway's public entry point `ProcessRequest` in `core/services/gateway/gateway.go` decodes the request, calls `msg.Validate()`, and dispatches directly to `h.HandleLegacyUserMessage(ctx, msg, callback)` [1](#0-0) [2](#0-1) . `Message.Validate()` only checks length/format of `MessageID` (non-empty, ≤128 bytes, no trailing null byte) and derives `Sender` from the signature — it never checks uniqueness across senders or binds the ID to the sender [3](#0-2) .

Inside `HandleLegacyUserMessage`, the callback is stored unconditionally, overwriting whatever entry currently exists at that key: [4](#0-3) . There is no existence/conflict check prior to this write, unlike the newer `httpTriggerHandler.setupCallback`, which explicitly checks `if _, found := h.callbacks[requestID]; found` and rejects with `ErrConflict` [5](#0-4) .

When a DON node later responds, `handleWebAPITriggerMessage` looks up and deletes the entry purely by `msg.Body.MessageID` and delivers the response to whichever callback occupies that slot: [6](#0-5) . This confirms the full exploit chain: if attacker B submits a message with the same `MessageID` as victim A's in-flight request (only the differs signature/sender, since `MessageID` is entirely attacker-chosen and not bound to sender), B's callback overwrites A's in the map. A's original request is orphaned (never invoked, resulting in the gateway-side timeout path in `ProcessRequest`'s `callback.Wait(ctx)` returning a timeout error to A), while B receives the DON's response destined for A — cross-user response confusion.

No middleware, allowlist, or per-sender namespacing exists in this path to prevent the collision; the only identity check anywhere near this code is in `HandleNodeMessage`, which validates that responses come from the expected `nodeAddr` [7](#0-6)  — this protects against malicious DON members impersonating other nodes, but does nothing to protect against two different *users* choosing the same `MessageID`.

## Impact Explanation
This is a concrete, in-scope vulnerability affecting the internet-facing gateway: an unprivileged client (any valid signer, which is the same capability required to be a legitimate caller) can perform (1) a targeted DoS against a specific concurrent request by guessing/observing its `MessageID` and colliding with it, and (2) cross-user response confusion, receiving a response payload intended for another user's request. Both map directly to the accepted impact categories "gateway request impersonation" / "cross-user response corruption."

## Likelihood Explanation
Exploitability requires only the ability to submit a validly signed `api.Message` — the same baseline requirement as any legitimate user of this endpoint — and knowledge or a race-based guess of a colliding `MessageID` for a request currently in flight. `MessageID` is fully attacker-controlled and unbound to sender identity, so no cryptographic or authorization barrier prevents the collision; the window is bounded only by DON round-trip latency, which is realistically exploitable via automated flooding with predictable/observed `MessageID`s (e.g. shared/predictable ID schemes used by clients, or repeatedly guessed common IDs). The codebase's parallel v2 HTTP trigger handler and Vault handler already implement the missing protections (duplicate-ID rejection and sender-namespaced keys respectively), confirming this is a recognized class of bug that the legacy handler alone fails to mitigate.

## Recommendation
- Namespace `savedCallbacks` keys by sender identity, e.g. `msg.Body.Sender + separator + msg.Body.MessageID`, mirroring the Vault handler's `owner + RequestIDSeparator + requestID` pattern.
- Before inserting into `savedCallbacks` in `HandleLegacyUserMessage`, check for an existing non-expired entry under that key and reject with a conflict error, mirroring `httpTriggerHandler.setupCallback`.
- Consider enforcing `MessageID` uniqueness/idempotency scoped to sender at message validation time.

## Proof of Concept
1. Legitimate user A signs and submits an `api.Message` with `Body.MessageID = "X"` and method `web_api_trigger` to the gateway's user HTTP endpoint, handled via `gateway.ProcessRequest` → `HandleLegacyUserMessage`. The handler stores A's callback at `savedCallbacks["X"]` (handler.go:412) and forwards the request to all DON members.
2. Before the DON responds, attacker B — using B's own distinct valid private key — signs and submits a different message body but with the same `Body.MessageID = "X"`. `Validate()` accepts it since uniqueness is never checked (message.go:54-87). `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with B's callback (handler.go:412).
3. When a DON node responds to A's original forwarded request (`resp.Body.MessageID == "X"`), `HandleNodeMessage` → `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's callback, deletes the entry, and invokes `savedCb.SendResponse(...)`, delivering A's intended response to B (handler.go:148-162).
4. A's HTTP request stalls until `callback.Wait(ctx)` in `gateway.ProcessRequest` times out (gateway.go:281-288), producing a `RequestTimeoutError` for A — confirming DoS — while B has received a response payload for a request B did not originate — confirming cross-user response confusion.

A Go unit test exercising `handler.HandleLegacyUserMessage` twice with the same `MessageID` from two different callbacks, followed by a single `HandleNodeMessage` call with a response matching that `MessageID`, would demonstrate that only the second (attacker) callback is invoked and the first (victim) callback is silently dropped, proving the vulnerability deterministically.
