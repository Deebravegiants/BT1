### Title
Missing decimal round-trip validation in `pallet-hyper-fungible-token` causes silent dust truncation and permanent loss of escrowed value - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token` scales amounts between a chain's local decimal precision and the ERC20 decimal precision of the paired EVM contract using `convert_to_erc20` (scale up, multiply) and `convert_to_balance` (scale down, integer divide). Unlike the analog Wormhole/Synonym pattern where ERC20 deposits are protected by an explicit `requireAssetAmountValidForTokenBridge`-style assertion enforcing that amounts survive a normalize/denormalize round trip, this pallet performs the scale-down division with no validation at all, for either native or non-native assets. Any user-submitted `send` amount whose ERC20-denominated value is not an exact multiple of `10^(erc_decimals - local_decimals)` silently loses the remainder ("dust") on receipt, with no accounting, no refund, and no revert.

### Finding Description
`send()` in [1](#0-0)  escrows the *exact* local-denomination amount from the sender, then computes the wire amount with `convert_to_erc20`, which only multiplies — this leg is always exact. The mismatch occurs at the receiving end (or, symmetrically, when the counterpart EVM contract sends a raw wei amount that is not aligned to the destination chain's precision): `on_accept` in [2](#0-1)  calls `convert_to_balance`, which is defined as an integer division with no remainder check: [3](#0-2) 

There is no equivalent of the original report's `requireAssetAmountValidForTokenBridge` assertion anywhere in this path — neither for the native asset nor for non-native `Assets`-backed tokens. The pallet unconditionally truncates on `on_accept`, and the same unchecked division is reused for refunds in `on_timeout`: [4](#0-3) .

Because the sending side (this pallet's `send`, or the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contracts encoding `Message.amount` in full `uint256` wei precision) never validates that the amount is exactly representable in the destination's lower precision, any amount with non-zero low-order digits beyond the destination's precision boundary results in the beneficiary receiving `floor(amount / scale)` while the full (unrounded) amount was escrowed/locked/dispatched on the source side. The truncated remainder is not tracked in any storage item, not refunded, and not recoverable — it is permanently and silently lost from the economic value transferred, remaining unaccounted for in the sending chain's custody account (`pallet_account()`) or burned/escrowed underlying token.

### Impact Explanation
This is reachable by any unprivileged user calling the `send` extrinsic (or the EVM-side `send()`), i.e., an ordinary token-bridge transfer, with an amount that is not an exact multiple of the decimal scaling factor between the two chains. It results in a permanent, silent loss of value for the user (the dust portion of every transfer is lost with no path to recovery), which the "Accept only concrete theft or permanent freezing of funds" validation criterion covers under permanent freezing/loss of user funds. Because `Precisions` is broadly configurable per asset/chain pair and commonly differs (e.g., 18-decimal EVM ERC20 vs 6- or 12-decimal substrate assets), essentially every cross-chain transfer whose raw amount doesn't align to a round number in the lower-precision chain triggers this loss.

### Likelihood Explanation
High likelihood: this triggers on ordinary usage, not a crafted attack. Any user who sends an amount that isn't a clean multiple of the scale factor (e.g., non-round wei amounts, or amounts denominated with more precision than the destination chain supports) will unknowingly lose the fractional remainder on every single transfer, with the pallet providing no warning, no revert, and no partial-refund mechanism.

### Recommendation
Enforce a round-trip validity check analogous to `requireAssetAmountValidForTokenBridge` before escrowing/burning in `send()` (`modules/pallets/hyper-fungible-token/src/lib.rs`): compute `convert_to_erc20(convert_to_balance(...))` (or equivalently check `amount % 10^(erc_decimals - local_decimals) == 0` for the scale-down direction, and reject/refund the dust) prior to moving funds, so an amount that cannot be represented losslessly at the destination's precision is rejected up front rather than silently truncated at `on_accept`/`on_timeout`. Alternatively, explicitly track and refund the truncated remainder to the original sender instead of discarding it.

### Proof of Concept
1. Register an asset with `Precisions` = 18 for the EVM peer chain and the local substrate asset with 6 decimals (`decimals()` on the `Assets` implementation returns 6).
2. Call `send` with `amount` such that the corresponding ERC20 wire amount computed by `convert_to_erc20` is, e.g., `1_000_000_000_000_000_001` wei (18 decimals) — one wei above a clean multiple of `10^12`.
3. On the destination chain, `on_accept` computes `convert_to_balance(1_000_000_000_000_000_001, 18, 6)` = `1_000_000_000_000_000_001 / 10^12` = `1000000` (truncated), discarding the `1` unit of extra precision.
4. The beneficiary receives `1000000` local units; the sender's escrowed/burned amount corresponded to the full `1_000_000_000_000_000_001` wei — the dust is permanently unaccounted for, with no event, no storage entry, and no way to reclaim it. Repeating this at scale (e.g., systematically sending amounts with maximal fractional remainder) causes cumulative, permanent loss of user funds across the bridge.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
