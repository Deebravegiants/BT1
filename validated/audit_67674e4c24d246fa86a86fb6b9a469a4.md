### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted for tenant identity without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches to the registered handler using the `shop`, `topic`, and `webhook_id` values taken directly from HTTP headers. Those header values are never included in the HMAC-signed payload, so nothing binds the "authenticated" body to the shop/topic the handler is told the data belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

`shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the body: [3](#0-2) 

`Registry.process` checks only the HMAC and then trusts `request.shop`/`request.topic`/`request.webhook_id` when building the metadata handed to the app's business logic: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop the handler is told owns the payload`. Because the header is outside the signed bytes, this equality is never enforced — the gem authenticates "these bytes came from someone who knows the client secret," not "these bytes describe shop X." Any webhook a merchant legitimately receives for their own shop (a genuine, validly signed body they can capture, e.g. from their own installed instance of the app) can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header swapped to name a different, victim shop. `Utils::HmacValidator.validate` still returns `true` because it only checks the body bytes against the secret, and `Registry.process` proceeds to invoke the handler with `WebhookMetadata.new(shop: request.shop, ...)` pointing at the victim shop.

### Impact Explanation
This breaks the tenant boundary the whole webhook system exists to enforce: an unprivileged actor who merely has access to their own shop's legitimately-delivered webhook (something any installer of the app can obtain without any special privilege) can make the app process that payload under a different shop's identity. Any host application that uses `WebhookMetadata#shop` from the processed request to select which tenant's records to update/delete/redact (which is the documented purpose of this field, e.g. GDPR `customers/redact` / `shop/redact` mandatory webhooks) is exposed to cross-tenant data mutation using attacker-supplied but nominally "verified" webhook calls. This matches the Critical class of cross-tenant access.

### Likelihood Explanation
Likelihood is elevated by the fact that no privileged credential is needed: any merchant who installs the app can trigger events in their own shop to receive a validly-signed webhook body, then simply resend it with a different `shop-domain` header value to the same public webhook endpoint. No knowledge of `client_secret` or any token is required to perform the header swap, only network access to the app's public callback URL.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-covered signable string (or otherwise cryptographically bind them, e.g. by validating them against an out-of-band registered/expected value per delivery), so that `Utils::HmacValidator.validate` fails if any of these identity-bearing headers are altered independently of the signed body.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger an event so Shopify sends a legitimate webhook, e.g. `customers/redact`, to the app's public endpoint with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` using the app's `client_secret`).
2. Capture that exact HTTP request (`B`, `H`, and other headers).
3. Resend the identical request to the same endpoint, changing only `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) recomputes the HMAC over `@raw_body` (`B`), which is unchanged, so validation succeeds.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)`, causing the app to act on `victim-shop.myshopify.com`'s tenant data using attacker-supplied (but "HMAC-verified") payload `B`.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
