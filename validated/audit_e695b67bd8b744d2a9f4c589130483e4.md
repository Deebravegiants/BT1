### Title
Unrestricted `CallDispatcher.dispatch()` Allows Anyone to Steal Residual Tokens Left By Predispatch/Postdispatch Swaps - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` has no caller restriction whatsoever — any address can invoke it directly with an arbitrary `Call[]` payload to make the shared `CallDispatcher` execute calls on its own behalf, exactly like an unprotected escrow whose "claim" step is not paired to the "deposit" step. This mirrors the root cause of the Mochi H-13 finding: a function that lets an outsider act on balances that were only supposed to be moved by the legitimate owner/flow, because the credit/claim path is not atomically and exclusively bound to the deposit path.

### Finding Description
`IntentGatewayV2.placeOrder()` (and `IntentsBase._execute()` for postdispatch) uses the shared, singleton `CallDispatcher` to execute user-supplied `predispatch`/`output` calldata (e.g., "swap ETH to DAI via Uniswap before escrow"). After the arbitrary call runs, the gateway sweeps the dispatcher's *known* input/output tokens back to itself: [1](#0-0) 

The sweep only iterates `order.inputs[i].token` (predispatch) or `order.output.assets[i].token` (postdispatch, `_execute`), based on the tokens the order declared: [2](#0-1) 

`CallDispatcher.dispatch()` itself performs no authorization check — it is a bare public entrypoint that executes whatever `Call[]` it's handed: [3](#0-2) 

Because the sweep logic only knows about the tokens explicitly listed in `order.inputs` / `order.output.assets`, any token the predispatch/postdispatch call happens to leave on the `CallDispatcher` that is *not* one of those declared tokens (e.g., swap dust, a reward/airdrop token returned by the target DEX/protocol, excess from a multi-hop route, or a fee-on-transfer refund) is never swept and remains sitting on the `CallDispatcher`'s balance after the transaction completes. Since `dispatch()` has no `onlyGateway`/`onlyOwner` guard, any third party can subsequently call `CallDispatcher.dispatch()` directly with a `Call` that transfers that residual token balance to themselves — stealing value that rightfully belongs to the order placer or the protocol, with nothing to stop them from doing so ahead of the legitimate sweep or a governance rescue.

This is the same class of bug as the Mochi H-13 report: the "deposit" (predispatch transfer + arbitrary call) and the "claim" (sweep) are not exclusively bound together — a permissionless intermediary contract holds funds transiently and any unprivileged party can race to claim them via a directly-callable function that performs no ownership check.

### Impact Explanation
Any solver, relayer, or bystander who observes a `placeOrder`/`fillOrder` transaction whose predispatch/postdispatch calldata leaves a non-order-listed token balance on the shared `CallDispatcher` can permissionlessly drain it by calling `dispatch()` directly, before Hyperbridge governance or the protocol can sweep/rescue it. This is a concrete theft-of-funds vector reachable by any unprivileged actor with no special permissions, using only public functions (`placeOrder`'s attacker-crafted or attacker-observed predispatch call, plus a direct call to `CallDispatcher.dispatch()`).

### Likelihood Explanation
Likelihood depends on predispatch/postdispatch calldata routing through DEXes or protocols that can return tokens beyond the declared `order.inputs`/`order.output.assets` set (common with multi-hop swaps, referral/reward tokens, or protocols that issue incidental token dust). Given that `predispatch.call` and `output.call` are attacker/solver/user-supplied arbitrary calldata routed through a single globally shared `CallDispatcher` instance, and `dispatch()` enforces zero access control, the window for exploitation exists on every transaction that leaves any non-swept token balance, and exploitation itself is a single trivial call.

### Recommendation
Restrict `CallDispatcher.dispatch()` to be callable only by the authorized gateway contract(s) (e.g., an `onlyGateway`/allowlist modifier), or make the dispatcher single-use / ephemeral (deployed per-call via `CREATE2` and self-destructing or becoming inert afterward) so no third party can ever act on its balance out-of-band. Additionally, generalize the sweep logic to drain *all* ERC20 balances the dispatcher ends up holding (not just the tokens declared in `order.inputs`/`order.output.assets`), so no residual value is left exposed even transiently.

### Proof of Concept
1. A user places an order with `predispatch.call` that swaps token A for token B via a router that also returns a small amount of token C (e.g., a reward/referral token, or dust from slippage) as a side effect. `order.inputs` only lists token B.
2. `placeOrder()` executes the predispatch call through `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` [4](#0-3) , then sweeps only token B back to the gateway [5](#0-4) . Token C remains on the `CallDispatcher`.
3. Any third party, in the very next transaction (or in the same block via higher gas), calls `CallDispatcher.dispatch()` directly with `Call({to: tokenC, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})` [6](#0-5) . Since `dispatch()` has no caller check, the call succeeds and token C is stolen.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
