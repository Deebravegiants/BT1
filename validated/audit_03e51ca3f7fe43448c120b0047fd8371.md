This confirms the vulnerability: the HMAC signature in `ShopifyAPI::Webhooks::Request` is computed only over `@raw_body` via `to_signable_string`, defined at `lib/shopify_api/webhooks/request.rb:35-38`, while `topic`, `shop`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers via `shopify_header` at `lib/shopify_api/webhooks/request.rb:20-33,67-70`, and are never included in the signed bytes. `Registry.process` at `lib/shopify_api/webhooks/registry.rb:189-199` validates only the HMAC (`Utils::HmacValidator.validate(request)`) and then passes `request.shop` straight into the `WebhookMetadata` given to the host app's handler — so the identity binding "shop attributed to the event" == "shop whose secret validated the event" is broken: the `shop-domain` header can be swapped after a legitimate webhook was captured (e.g., a byte-for-byte replay of a webhook body legitimately delivered for the attacker's own shop, but with the `x-shopify-shop-domain`/`shopify-shop-domain` header rewritten to a victim shop) and the library will still report `hmac` valid and hand the victim's shop identity to the app's webhook handler.

### Title
Webhook shop-domain, topic, api-version and webhook-id headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw JSON body, while `shop`, `topic`, `api_version`, and `webhook_id` are taken from HTTP headers that are excluded from the HMAC computation, letting an attacker who controls one legitimately-signed webhook body reuse it under an arbitrary `shop-domain` header.

### Finding Description
`Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:12-22` verifies the HMAC over `verifiable_query.to_signable_string`. For webhooks, `to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`). The `shop`, `topic`, `api_version`, and `webhook_id` accessors instead read straight from request headers (`lib/shopify_api/webhooks/request.rb:15-33`, `67-70`) which are never part of the signed payload.

`Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) does:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
It checks HMAC validity, then trusts `request.shop`/`request.topic` from headers unconditionally. The equality the library implicitly claims to guarantee is:
`shop delivered to handler == shop whose secret produced the verified HMAC`
but the actual binding enforced is only:
`HMAC(raw_body, secret) == received_hmac`,
with no cryptographic tie between `shop-domain` (or `topic`/`webhook_id`) and the signed bytes. Any entity holding one validly-signed raw body (for example the operator's own shop, a legitimate recipient of webhooks for their own store) can resubmit that same body to the app's webhook endpoint with a different `x-shopify-shop-domain` value, and `HmacValidator.validate` still returns `true` because it never looks at the header.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook consumers: a host application that trusts `WebhookMetadata#shop` (as `Registry.process` explicitly documents/promotes as the authenticated shop) can be made to process/attribute a webhook body as belonging to a different merchant, or under a forged `topic`/`webhook_id`. Depending on handler logic (e.g., session lookup by `data.shop`, redact/deletion handlers, mandatory compliance topics), this enables cross-tenant data confusion — for example causing a `shop/redact` or `customers/data_request` handler to run against the wrong store, or spoofing the `topic` field the handler dispatches on while keeping a validly-signed body. This matches the report's underlying bug class: a field acted upon (`shop`) is not covered by the authentication check (HMAC), letting an attacker rebind trusted output to an unintended identity.

### Likelihood Explanation
Exploitation requires the attacker to possess one genuinely HMAC-signed webhook body — trivially available to any merchant/developer who installs the app and receives their own store's webhooks, since Shopify always signs bodies with the app's shared secret regardless of which shop triggers the event. No access to `api_secret_key` or the access token is needed; only a header rewrite of an otherwise-untouched replayed payload. This makes the analog concretely reachable by any unprivileged party who can install the app on a shop they control.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the bytes that are HMAC-verified (or otherwise cryptographically bind them to the raw body, e.g. by validating that the header values match values embedded in the signed payload/JWT), so `Utils::HmacValidator.validate` cannot pass for a body whose accompanying metadata headers have been altered. At minimum, document/enforce that `WebhookMetadata#shop` must never be trusted without a secondary shop-authorization check by the host app.

### Proof of Concept
1. App receives a legitimate webhook for `attacker-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(secret, B)`.
2. Attacker resends the exact same body `B` and the exact same `x-shopify-hmac-sha256: H` header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...changed shop-domain...})` is constructed; `Utils::HmacValidator.validate(request)` calls `compute_signature(request.to_signable_string, secret)` which only hashes `B`, so it still equals `H` — validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:27-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` proceeds and invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to act on victim-shop identity despite the payload never having been signed in association with that shop.
