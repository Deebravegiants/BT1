## Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`/`webhook_id`/`api_version`) from HTTP headers that are never included in the HMAC signature computation. `ShopifyAPI::Webhooks::Registry.process` verifies only the raw body's HMAC and then trusts `request.shop`/`request.topic` unconditionally to dispatch the webhook to the host application's handler. This breaks the equality that should hold between "the tenant whose signature was verified" and "the tenant the handler is told the data belongs to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from request headers, which are not part of the signed material: [2](#0-1) 

`HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it against the `hmac` accessor, i.e. it only proves that `@raw_body` was signed with the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` performs this single HMAC check and then immediately hands `request.shop`, `request.topic`, and `request.webhook_id` — all unsigned header values — to the host application's `WebhookHandler`: [4](#0-3) 

Because the `api_secret_key` is a single value shared across **all** shops that install the app (it is not a per-shop secret), any two shops that install the same app can produce identically-valid `(raw_body, hmac)` pairs relative to that secret whenever the raw body is byte-for-byte equal. Because the `shop-domain`/`topic`/`webhook-id` headers are excluded from the signable string, a merchant who has legitimately installed the app can capture a real, HMAC-valid `(raw_body, hmac)` pair delivered to their own webhook endpoint (they fully control that HTTP endpoint) and replay it to the app's webhook receiver while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still returns `true` (it only checks the body), and `Registry.process` will invoke the handler believing the event originated from the victim shop.

This is the same class of defect as the report's `shell.openExternal` issue: a value that is *acted upon* (there, the URI scheme used for a security-relevant OS call; here, the `shop` value used to key the tenant for a security-relevant application callback) is not validated/bound by the mechanism (there, protocol whitelisting; here, HMAC) that is supposed to establish trust for that exact value.

### Impact Explanation
This breaks the equality `shop authenticated by HMAC == shop attributed to the webhook payload`. A malicious merchant can make the host application believe an arbitrary attacker-chosen shop domain sent a specific webhook payload/topic (e.g. `app/uninstalled`, `customers/redact`, `shop/update`), causing the host app to act on another tenant's data/session under a forged identity — a cross-tenant integrity violation directly enabled by this library's `Registry.process`/`Request` design, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate, unprivileged merchant of the target app (or otherwise obtain one valid `(raw_body, hmac)` pair, which is possible since delivery endpoints the merchant controls receive both values in plaintext over HTTP(S)). No access to `api_secret_key`, access tokens, or Shopify infrastructure is required — only a replay of previously-observed, validly-signed bytes with a substituted header.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-verified signable material (or otherwise cryptographically bind them to the raw body/signature), so that the verified signature also authenticates which shop/topic/webhook the payload is claimed to represent. At minimum, `Registry.process` should not trust `request.shop` for any tenant-sensitive action unless it is cross-checked against an independently-verified value (e.g., the shop associated with the stored session/access token that would be used to process that webhook).

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw HTTP request delivered to the app's webhook endpoint, including the `X-Shopify-Hmac-Sha256` header and raw body.
2. Replay that exact raw body and HMAC header to the same webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body`; the check succeeds because the body/HMAC pair is unchanged.
4. `request.shop` returns `"victim-shop.myshopify.com"` (from the attacker-controlled header) and is passed to the app's `WebhookHandler` as the tenant identity, causing the host app to process attacker-supplied data as if it came from the victim shop.
