### Title
Webhook `shop`/`topic`/`webhook_id` identity headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers that are never part of the signed material. This breaks the identity binding `shop authenticated by HMAC == shop attributed to the webhook payload`, allowing any party who possesses one valid `(raw_body, hmac)` pair to relabel it as belonging to a different shop/topic.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, which are not covered by the signature at all: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the body) against the `hmac`: [3](#0-2) 

`Registry.process` performs exactly that check and then immediately trusts the unauthenticated header-derived fields to build `WebhookMetadata` handed to the app's handler: [4](#0-3) 

Because the signature only binds the body, and the headers carrying `shop`, `topic`, and `webhook_id` are excluded from `to_signable_string`, the equality the app relies on — "the shop whose secret produced this HMAC" == "the shop reported in `request.shop`" — does not actually hold. Anyone who legitimately receives one authentic `(body, hmac)` pair for their own shop/topic (e.g., a merchant triggering a webhook event on their own store, which is fully within an "unprivileged internet user"'s control) can replay that exact body+hmac directly to the app's public webhook endpoint while substituting arbitrary `shop-domain`, `topic`, and `webhook-id` header values. The HMAC check still passes (it only checks the body), and the handler executes with attacker-chosen shop/topic/webhook_id metadata.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker-controlled request can be attributed to any shop of the attacker's choosing (not their own), and to any topic the app has a handler for, while still passing HMAC verification. Any app logic that branches on `WebhookMetadata#shop` or `#topic` (e.g., loading a different tenant's session/data, updating per-shop state, triggering shop-specific side effects) can be driven under a forged tenant identity. This matches the Critical "cross-tenant access" impact category, since the binding between the cryptographically-verified sender and the shop/topic acted upon is broken.

### Likelihood Explanation
Likelihood is bounded by the requirement that the attacker first obtain one authentic `(raw_body, hmac)` pair — trivially achievable by any merchant using the app on their own store (triggering any webhook event, e.g. an order/product update, and capturing the resulting POST via their own infrastructure/proxy), which is fully within reach of an unprivileged internet user with no special credentials. The replay itself is a simple direct HTTP POST to the app's public webhook endpoint with modified headers.

### Recommendation
Include the identity-critical fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable material verified by HMAC, or otherwise cryptographically bind them to the body (e.g., verify that the shop/topic in headers match values embedded in and covered by the signed payload) before constructing `WebhookMetadata` and invoking handlers.

### Proof of Concept
1. Attacker owns/operates `attacker-shop.myshopify.com`, which has the target app installed, and triggers any webhook event (e.g., `products/update`) on their own store.
2. Attacker captures the resulting POST request body and its `X-Shopify-Hmac-Sha256` header — a valid `(raw_body, hmac)` pair, verifiable via `Utils::HmacValidator.validate`.
3. Attacker sends a new POST directly to the app's webhook endpoint with the same `raw_body` and `hmac`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which passes because only the body is checked (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the HMAC was never computed over or bound to that value, letting the attacker's request masquerade as originating from the victim shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
