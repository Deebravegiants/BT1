### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that raw body. The `shop` identifier, however, is read directly from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header and is never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body/HMAC pair validates and then forwards `request.shop` to the app's webhook handler as the authoritative tenant identifier for that payload.

### Finding Description
The binding that should hold is:
`HMAC-verified bytes == bytes the app treats as authoritative for the webhook (topic, shop, webhook-id, api-version, body)`

In this gem that binding is broken:
- `to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `shop` is derived purely from an unauthenticated header, never entering the signable string: [2](#0-1) 
- `Registry.process` validates only the HMAC of the request (i.e., the body) and, once that passes, hands `request.shop` straight to the handler as trusted tenant data: [3](#0-2) 
- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and the app's shared `api_secret_key`: [4](#0-3) 

Because the `api_secret_key` (the app's `client_secret`) is a single shared secret across every shop that installs the app — not a per-shop secret — any unprivileged user who has installed the app on their own shop can capture a legitimate `(raw_body, hmac)` pair from a webhook delivered to their own endpoint, then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` value for a victim shop. The HMAC still validates (it only ever covered the body), so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` where `shop` is the attacker-chosen victim domain: [5](#0-4) 

If the host application (as essentially all Shopify apps do) uses `shop` from `WebhookMetadata` to look up per-tenant state, credentials, or to write data keyed by shop, the attacker can inject data attributed to, or overwrite state belonging to, a different tenant — a direct violation of the shop-domain binding this gem is trusted to enforce.

### Impact Explanation
This is a cross-tenant identity-binding break: the field (`shop`) that downstream integrators treat as the verified source-of-truth for which merchant a webhook belongs to is not covered by the cryptographic check the gem performs. An attacker who is merely an installer of the app (unprivileged relative to other tenants) can forge webhook events that the gem asserts as originating from an arbitrary other shop, enabling cross-tenant data confusion/injection in any host application that trusts `WebhookMetadata#shop` — which is the documented and expected usage pattern in `docs/usage/webhooks.md`.

### Likelihood Explanation
The attacker only needs the ability to install the app themselves (no special privilege, no leaked secrets, no TLS interception) — a genuinely unprivileged internet user relative to other merchants. Capturing their own webhook body/HMAC and replaying it with a modified shop header requires no cryptographic knowledge of `api_secret_key`, only observation of their own traffic.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the signed material the gem checks, or independently verify that the shop header corresponds to a shop associated with a valid session/installation before trusting `request.shop`, rather than relying solely on a body-only HMAC to authorize header-derived identity fields.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving legitimate webhooks with valid `(raw_body, x-shopify-hmac-sha256)` pairs signed with the app's shared `api_secret_key`.
2. Attacker resends that exact `(raw_body, hmac)` to the app's webhook endpoint, replacing only the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the shared secret: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, despite the request never having been sent by Shopify on behalf of that victim shop.
