### Title
Emporium stateless ops (`signerAddress == address(0)`) allow unrestricted arbitrary calls, including `approve()` on tokens outside the accounted token set, as Emporium itself - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`/`verifyWallet` let any attacker who can obtain a valid proof for their own (even trivial) UTXOs submit an `EmporiumStack` with `signerAddress == address(0)` and have its `ops[]` executed with `op.endpoint.call(...)` where `msg.sender == Emporium`. The only gate on the calldata is a selector check preventing `callHinkalWallet`/`doSendToRelay`; arbitrary calls such as `IERC20.approve(attacker, type(uint256).max)` are permitted, and the post-call accounting only diff-checks tokens the attacker chose to list in `circomData.erc20TokenAddresses`. If Emporium holds a residual balance of a token not included in that array, the attacker can grant itself an allowance over it with zero accounting impact, then drain it later with `transferFrom` in a separate transaction.

### Finding Description
Broken equality: *"assets moved/authorized by a stateless Emporium op == assets accounted for by `deltaAmountChanges`/`circomData.erc20TokenAddresses` for that transaction."* In reality, the set of calls Emporium executes is unconstrained by that accounting.

- In `verifyWallet` (lines 302-316), when `stack.signerAddress == address(0)` the function marks the `emporiumMessage` nonce used and returns immediately — no EIP-712 signature is required. This is by design for "stateless" ops (the caller's own ZK proof/UTXOs are meant to be the sole authorization). [1](#0-0) 

- In `runAction`, the stateless branch (CASE 2, lines 102-113) only blocks the `callHinkalWallet`/`doSendToRelay` selectors; every other selector/calldata (including `approve`) is executed as `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium`. [2](#0-1) 

- The only post-call safety net is the balance-diff loop, but it iterates strictly over `circomData.erc20TokenAddresses`, an array the attacker fully controls when constructing their own `CircomData`. [3](#0-2) 

- `performHinkalChecks` only verifies `calldataHash` self-consistency (that the attacker's own submitted fields match what they signed into the hash) and dimension consistency; it does not restrict which tokens/endpoints an Emporium op may touch, nor does it require that every token an op interacts with be present in `erc20TokenAddresses`. [4](#0-3) 

Exploit flow: the attacker builds their own `CircomData` with `erc20TokenAddresses` excluding the target `ERC20_TOKEN` (or including unrelated tokens), an `EmporiumStack{signerAddress:0, ops:[{endpoint:ERC20_TOKEN, invokeWallet:false, value:0, callData:approve(attackerSpender, max)}]}`, and a proof for their own UTXOs (which can be a no-op/zero-amount transaction). They submit it via the standard Hinkal transaction flow that routes to `Emporium.runAction` (the `onlyAllowedRecipient` path used by any user). `verifyWallet` skips signature checks (line 314-316), the loop calls `approve()` with Emporium as owner (line 112), and because `ERC20_TOKEN` is absent from `erc20TokenAddresses`, no balance check ever inspects it. The attacker walks away having granted themselves (or a controlled spender) unlimited allowance over any `ERC20_TOKEN` balance Emporium happens to hold — from residual balances (explicitly acknowledged as possible per the code comment at line 141: "there were some funds on emporium before the call") — and can later call `transferFrom` directly on the token, outside of Emporium, to steal those funds.

Note: the precondition framing in the question ("a third-party approval where Emporium is the spender") is not quite accurate — `approve()` called with `msg.sender == Emporium` makes Emporium the *owner/approver*, not the spender of an existing allowance. The actually exploitable precondition is that Emporium holds an ERC20 balance (residual/parked funds) of the target token, which the code's own comments acknowledge as a reachable state.

### Impact Explanation
An unprivileged attacker can turn Emporium into a confused deputy: by crafting a stateless `EmporiumStack` op that is never authenticated (no signature) and never accounted (token excluded from the diff-checked array), they can call `approve()` (or any other state-changing function) on any ERC20 the contract holds, granting themselves standing allowance to drain balances belonging to other users/flows that are temporarily or persistently held by Emporium. This is theft of funds not authorized by any wallet/signer and not tied to the attacker's own deposited value — matching the Critical category ("permanent freezing/theft path... executing calls or moving assets a wallet owner or prover never authorised"). It is repeatable per residual balance and per token.

### Likelihood Explanation
Preconditions required: Emporium must hold a non-zero balance of the targeted ERC20 token at the time of the attacker's transaction (acknowledged as reachable by the contract's own inline comment). The attacker needs only the ability to submit a normal Hinkal transaction with a self-generated proof of their own (possibly zero-value) UTXOs and a crafted `externalActionMetadata`/`EmporiumStack` — capabilities explicitly granted to the "unprivileged attacker" persona in this audit's rules. No signature from any third party, admin role, or relay privilege is needed. Cost is a single transaction (plus a follow-up `transferFrom`).

### Recommendation
- Require that every `op.endpoint` touched by a stateless op, and every token affected by its `callData` (e.g., `approve`/`transferFrom`/`transfer` targets), be restricted to addresses present in `circomData.erc20TokenAddresses`, or otherwise disallow calls to arbitrary ERC20 `approve` selectors from the stateless path.
- Alternatively/additionally, revoke any allowances granted during `runAction` before returning (e.g., `approve(spender, 0)` sweep) or disallow `approve` calls entirely from stateless ops, permitting only a narrowly scoped "swap-and-consume-in-same-tx" pattern.
- Ensure Emporium never carries residual token balances across transactions (or if intentional, isolate residual balances per-depositor so a stateless op from one transaction cannot affect another depositor's funds).

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, an `ERC20Mock`, and mint/transfer tokens directly to the Emporium contract address to simulate a residual balance (`seedBalance`).
2. Construct a `CircomData` with `erc20TokenAddresses` = `[]` (or an unrelated token), zero `amountChanges`/`deltaAmountChanges`, and `externalActionData.externalActionMetadata` = `abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: address(erc20), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.approve, (attacker, type(uint256).max))}], maxFee: 0, deadline: type(uint256).max})`, with a fresh `emporiumMessage`.
3. Invoke the standard Hinkal transaction path (or directly call `runAction` from the allowed-recipient address per test harness) with this `circomData` and `deltaAmountChanges = [0]` (or matching the empty token array).
4. Assert `verifyWallet` did not revert and no signature was required (equality check: pre-tx `erc20.allowance(emporium, attacker) == 0` vs post-tx `== type(uint256).max`).
5. From the attacker EOA, call `erc20.transferFrom(emporium, attacker, seedBalance)` and assert `erc20.balanceOf(attacker) == seedBalance` and `erc20.balanceOf(emporium) == 0`, confirming funds never accounted for in `circomData.erc20TokenAddresses`/`deltaAmountChanges` were drained.
