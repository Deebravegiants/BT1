### Title
Stale cached user authorization/status data reused for signup enrollment instead of re-validating - ([File: src/plans/mod.rs])

### Summary
`MasterPlan` caches the backend's user validation result (`backend::user_status::UserData`, containing eligibility flags, encryption keys, and enrollment mode) inside the `QrCodes::Both` variant at the moment the user QR code is scanned. `scan_remaining_qr_codes` later reuses this cached `user_data` without re-querying the backend, gating reuse solely on whether the *operator's* QR code timestamp has expired rather than on the freshness of the user's own validation. This is the same bug class as the reported staking issue: a value snapshotted at one point in time (`stakeInfo.liquidity` / here, `user_data`) is trusted at a later, security-relevant point (reward calculation / here, signup enrollment) without being refreshed, even though the real-world state it represents can change in between.

### Finding Description
`QrCodes::Both` stores `operator_data`, `user_qr_code`, and `user_data` together: [1](#0-0) 

`user_data` is produced by `backend::user_status::request`, which performs a live backend call and encodes user-specific state such as `user_centric_signup`, `orb_relay_app_id`, and per-user encryption keys at the moment of the call: [2](#0-1) [3](#0-2) 

In `scan_remaining_qr_codes`, when the previously scanned `QrCodes::Both { operator_data, user_qr_code, user_data, .. }` is passed in, the code short-circuits and reuses the stored `user_data` as long as the *operator* QR expiration timer (`operator_data.timestamp.elapsed() < operator_qr_expiration_time`) hasn't lapsed — there is no independent check of when `user_data`/`user_qr_code` were actually validated, and no fresh call to `backend::user_status::request`: [4](#0-3) 

This reused, unrefreshed `user_data` then drives the rest of the signup flow: whether app-centric or user-centric enrollment logic is used, and whether relay announcement/PCP tier upload proceeds: [5](#0-4) [6](#0-5) 

The freshness gate is tied to `OperatorData.timestamp`, which is a property of the operator's QR-code scan, not the user's status — exactly analogous to `UniswapV3Staking` gating reward computation on `stakeInfo.liquidity`, a value captured at `stake()` time, rather than the current on-chain liquidity.

### Impact Explanation
Because the actual freshness condition (`operator_qr_expiration_time`) is decoupled from when the user's own eligibility/status was determined, a signup can proceed to full biometric capture and enrollment using a `user_data` snapshot that no longer reflects the user's current backend state (e.g., their eligibility, enrollment mode `user_centric_signup`, or `orb_relay_app_id` binding could have changed between validation and enrollment). This risks the orb enrolling/completing a signup under stale authorization data rather than the up-to-date one the backend would return if re-queried immediately before enrollment, i.e., a cross-time state bleed between the validation step and the final signup decision.

### Likelihood Explanation
This path is reachable during ordinary self-serve/normal signup flows without any privileged access — it triggers whenever the flow re-enters `scan_remaining_qr_codes` with an already-populated `QrCodes::Both` and the operator QR hasn't yet expired, which is the expected common case rather than an edge case. No attacker-controlled malicious peer/hardware access is required, matching the allowed "malicious normal user / unprivileged" attacker profile.

### Recommendation
Re-validate the user's status via a fresh `backend::user_status::request` call (or otherwise bound the reuse window independently) immediately before it is used for the final signup/enrollment decision, rather than gating reuse only on the operator QR code's expiration timer. At minimum, track a separate timestamp for when `user_data` itself was obtained and expire/refresh it on its own schedule, analogous to fetching current liquidity in `_calculateRewards` instead of relying on the value captured at `stake()` time.

### Proof of Concept
1. Operator scans their QR code; `operator_qr_expiration_time` is configured to a non-trivial window (e.g., minutes), per `scan_initial_qr_codes`/`scan_remaining_qr_codes` logic (src/plans/mod.rs:749-868).
2. User scans their QR code; `verify_user_qr_code` calls the backend once and the result is cached into `QrCodes::Both` (src/plans/mod.rs:1085-1090, src/backend/user_status.rs:147-162).
3. Time passes within the operator QR's validity window while the orb proceeds through OS-version checks, relay announcement, and the 3-second pre-capture delay (src/plans/mod.rs:507-551).
4. If `scan_remaining_qr_codes` is invoked again with the same `QrCodes::Both` (e.g., due to a retry loop before reaching biometric capture), it reuses the original `user_data` unconditionally because only `operator_data.timestamp` is checked (src/plans/mod.rs:794-805) — no fresh backend call occurs to confirm the user's status/eligibility is still current at the time enrollment actually happens.
