## Analysis

The bug class in the report is: methods intended to only be invoked by a trusted, verified caller (using `_msgSender()`/an identity claim) but missing the actual modifier that restricts who can invoke them — i.e., the caller-identity binding is asserted but never enforced.

The closest analog in `orb-core` is in the `orb-relay-client` crate's connection message-handling loop, `PollerAgent::main_loop`, in `orb-relay-client/src/client.rs`. Every inbound `RelayPayload` is supposed to be validated against the expected session peer before being trusted and forwarded into the client's message buffer: [1](#0-0) 

Specifically:
```rust
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: ...");
} else {
    self.handle_message(...).await?;
}
```

The `else if src.id != self.config.dst_id` branch is exactly the authorization check analogous to `onlyGelatoRelay` — it verifies that an inbound message really originates from the entity that is supposed to be the counterpart of this session (`dst_id`, bound at connection-establishment time via `Client::new_as_orb`/`new_as_app`) before the payload is trusted and processed.

For `self_serve::app::v1::RequestState` messages, this identity check is completely bypassed: the handler replies with `self.last_message.clone()` unconditionally, without ever checking `src.id`. This mirrors the reported bug precisely: a function meant to act on behalf of / respond to a specific identified caller (`ForUser`-style) but omitting the modifier/check that ties the action to that caller's verified identity.

### Impact
`self.last_message` holds the most recently sent payload for the session (e.g. `AnnounceOrbId`, `CaptureStarted`, `SignupEnded`, or other self-serve session-state messages tied to a specific signup session) — see the assignment at: [2](#0-1) 

Because the `RequestState`-triggered reply skips the `src.id != self.config.dst_id` check, any entity able to send a `RequestState` payload over the established relay stream — not just the legitimate session peer bound to `dst_id` — can trigger a replay of that session's last state message. This is a cross-session state disclosure: it defeats the purpose of the `src.id` binding that every other message type in the same loop is subject to, exactly like the `TradableSideVault` methods that used `_msgSender()` but omitted `onlyGelatoRelay`, defeating the purpose of having a caller-restricted variant at all.

I did not find, however, any evidence that this relay session/identity mechanism handles raw biometric data, QR/MECARD parsing, secure-element signing, or the actual PCP/enrollment payloads themselves — those flows (`src/plans/mod.rs::do_signup`, `enroll_user`, PCP upload) are gated separately and are not reachable through this bypass. The `RequestState` bypass is confined to the self-serve session-state replay mechanism.

### Title
Missing peer/source authorization check for `RequestState` message handling in orb-relay client - (File: orb-relay-client/src/client.rs)

### Summary
In `orb_relay_client::client::Client`'s connection loop (`PollerAgent::main_loop`), every inbound `RelayPayload` is checked against `src.id != self.config.dst_id` before being accepted, except for `self_serve::app::v1::RequestState` messages, which are always answered with a replay of `self.last_message` regardless of the sender's identity.

### Finding Description [1](#0-0)  shows the branch structure: the `RequestState::matches(&payload).is_some()` arm is evaluated first and unconditionally triggers `sender_tx.send(self.last_message.clone())`, before the `src.id != self.config.dst_id` check that guards the `else if` branch and protects `handle_message`. This means the identity-binding enforcement that exists for every other message type in this loop is skipped specifically for `RequestState`.

### Impact Explanation
`self.last_message` is the last payload the client sent on this session (e.g. self-serve `AnnounceOrbId`, `CaptureStarted`, `SignupEnded`), set at [3](#0-2) . Any entity capable of injecting a `RequestState` payload into the stream — without being the authenticated `dst_id` peer for that session — can force a replay of that session's last state, leaking session/state information intended only for the legitimate counterpart bound at connection time.

### Likelihood Explanation
Exploitability depends on whether the underlying relay transport allows a connected entity to present an arbitrary `src` on a `RelayPayload` that is not enforced server-side; the client-side code's own `src.id != self.config.dst_id` check exists specifically because such a possibility is anticipated (as evidenced by the check protecting every other message type). The `RequestState` branch bypasses that same protection.

### Recommendation
Move the `src.id != self.config.dst_id` check ahead of the `RequestState` special case (or apply it inside that branch as well), so that a replay of `last_message` is only ever sent to the verified session peer, consistent with how every other inbound message type is handled.

### Proof of Concept
1. Establish a relay connection as the app/orb using valid credentials for the session.
2. Have a third entity (not bound as `dst_id` for that specific session) send a `self_serve::app::v1::RequestState` payload over the relay for that session's stream.
3. Observe that `PollerAgent::main_loop` replies with `self.last_message.clone()` without ever validating `src.id` against `self.config.dst_id`, unlike any other message type, at [4](#0-3) .
