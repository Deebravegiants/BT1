### Title
Excess native token overpayment on `EvmHost.dispatch()`/`fundRequest()` fee swaps is permanently retained by the contract instead of being refunded to the caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and internally call `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` to buy exactly `fee`/`post.fee`/`amount` worth of the fee token. This is structurally the same bug class as the Sense M-5 finding: a user-supplied amount is used to acquire an exact output via a swap whose input requirement is only a maximum, and any unconsumed input is not returned to the original caller.

### Finding Description
In `swapETHForExactTokens`, UniswapV2Router02 refunds unused ETH to `msg.sender` of the swap call. Because `EvmHost` itself calls the router (not the end user), the refund is paid to `address(this)` (the `EvmHost` contract), not to `_msgSender()` who originally sent the overpaid `msg.value`. [1](#0-0)  The same pattern repeats in the GET dispatch path [2](#0-1)  and in `fundRequest` [3](#0-2) .

None of these three functions computes or returns any leftover ETH to `_msgSender()`. The contract does have a `receive()` function explicitly documented as existing "to collect all dust native tokens" from the router refund [4](#0-3) , confirming that the design intentionally routes the refund into the contract's own balance rather than back to the caller who overpaid.

This mirrors exactly the Sense audit finding: a contract quotes/estimates an amount needed for a swap, pulls in the caller's full input, and the swap's actual consumption is less than or equal to what was supplied — but the excess is not sent back to the payer.

### Impact Explanation
Any caller (an app integrating `HyperApp`/`dispatchWithFeeToken`, or any contract/user directly calling `IDispatcher.dispatch`/`fundRequest` with native value) who supplies `msg.value` greater than what the Uniswap V2 pool actually needs to produce `fee` fee-tokens loses the difference permanently to the `EvmHost` contract. This is a direct, permanent loss of user funds (native ETH/gas token) with every native-fee dispatch, GET request, or `fundRequest` call whenever the caller doesn't compute the exact swap input required (which is generically hard for a caller to predict precisely due to pool state changes between quote and execution). Given `dispatch`/`fundRequest` are called on essentially every outbound ISMP message paid in native token across all EVM deployments, this is a widely reachable, recurring loss vector, not a one-off edge case.

### Likelihood Explanation
High likelihood: any app using `HyperApp`'s native-payment path (as documented) or any direct caller passing `msg.value` slightly above the exact swap requirement — which is the normal/expected case since callers typically send a buffered amount to guard against slippage or router-fee changes — will trigger this loss on every such transaction. No malicious actor is required; it happens under normal legitimate usage.

### Recommendation
Track the actual ETH consumed by `swapETHForExactTokens` (it returns `amounts[0]` = ETH spent) and refund `msg.value - amounts[0]` back to `_msgSender()` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, following the same pattern already used correctly elsewhere in the repo (e.g., `UniV3UniswapV2Wrapper.sol`'s refund of unspent ETH to `msg.sender`, and `IntentGatewayV2`'s `msgValue -= amounts[0]` refund pattern).

### Proof of Concept
1. Caller `Alice` calls `EvmHost.dispatch{value: X}(post)` where `post.fee = F` and, due to router liquidity, only `Y < X` ETH is actually required by `swapETHForExactTokens` to buy `F` fee-tokens.
2. `IUniswapV2Router02.swapETHForExactTokens{value: X}(F, path, address(this), deadline)` spends `Y` ETH and refunds `X - Y` ETH to `msg.sender` of that call, which is `EvmHost` (`address(this)`), landing in `EvmHost`'s `receive()`.
3. `dispatch()` returns without ever inspecting or refunding the `X - Y` surplus to Alice.
4. Alice's excess ETH (`X - Y`) is now stuck in `EvmHost`'s balance, and the function that intentionally collects "dust" confirms this is retained by the contract rather than the user, with no user-facing recovery path. [1](#0-0) [4](#0-3)

```text
    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }
```
