### Title
Unbounded, user-chosen `Order.deadline` in IntentGatewayV2 grants order placers a free, indefinitely-exercisable option against solvers - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder()` accepts an `Order` struct where `deadline` is chosen entirely by the order placer with no protocol-enforced ceiling, mirroring the FrankenDAO `_unlockTime` bug class: a user-supplied time/duration parameter is fed directly into downstream economic logic (bid/quote validity and fill eligibility) without any maximum bound. This lets an unprivileged order placer keep an order — and the solver's committed quote/output — executable indefinitely, effectively writing themselves a long-dated option on the solver's inventory at no premium.

### Finding Description
`fillOrder(order, options)` checks only `order.deadline >= block.number` (cross-chain, `evm/tron/contracts/apps/IntentGatewayV2.sol:590` and its cross-chain analog) — there is no upper bound on how large `order.deadline` can be at order-placement time. The repository's own changelog documents this precisely: `order.deadline` is "placer-controlled with no ceiling" [1](#0-0) , and the accompanying Foundry test explicitly documents the design: *"A solver's quote is a firm price the order placer may take up whenever they choose — `order.deadline` is placer-controlled with no ceiling."* [2](#0-1) 

The mitigation that was actually shipped is off-chain and solver-side only: the Simplex filler SDK now adds its own `FillOptions.validUntil` bound to the *bid it signs*, so a stale bid it submits will revert with `FillExpired` [3](#0-2) . This is a client-side risk-limiting patch by one particular filler implementation — it does not change the on-chain contract, and it does nothing for:
- Solvers/fillers running other implementations (or none) that don't add a `validUntil` bound to their bids.
- Same-chain fills where a solver directly calls `fillOrder` with `validUntil = 0` ("unbounded"), which the test suite documents is "the right default for a solver filling directly" [4](#0-3) .
- Any solver-side quote that predates or omits `validUntil` handling on gateways where "the bound is dropped — there is nowhere to put it" for legacy fillOrder selectors [5](#0-4) .

The root cause remains in the on-chain contract: `Order.deadline` (an unprivileged, user-submitted field of a `placeOrder` transaction) is never capped against a protocol-level maximum window at `placeOrder` time, unlike the FrankenDAO fix pattern of clamping `_unlockTime`/derived `time` against `stakingSettings.maxStakeBonusTime`.

### Impact Explanation
Because `deadline` is unbounded, any order placer can escrow tokens with an arbitrarily long expiry and hold open a firm price quote (the solver's committed `output` amounts encoded in the auction bid) indefinitely. The placer can wait for the market to move in their favor, then execute the fill at the stale, favorable rate — a risk transferred entirely to the solver/filler with no premium paid, since Hyperbridge intent auctions are quote-then-fill (bid now, execute whenever before `deadline`). For volatile pairs this can force solvers into losses whenever price moves against their originally quoted rate, and because `deadline` has no ceiling, this window can be made effectively permanent. This is a Medium-severity value-extraction/economic-drain vector directly reachable by any intent-placing user via a single `placeOrder` transaction — squarely in the "intent solver" attack surface named in scope.

### Likelihood Explanation
High likelihood of being triggered unintentionally and readily exploitable intentionally: `placeOrder` is a completely unprivileged, permissionless entry point; setting a large `deadline` costs nothing extra and requires no special conditions. The vulnerability class is confirmed by the project's own audit finding and changelog, which shows the team recognized the unbounded window as a real economic risk but only patched it at the filler/bidding layer for one specific SDK — not in the on-chain `IntentGatewayV2` contract that governs all fillers.

### Recommendation
Enforce a protocol-level maximum order lifetime in `placeOrder` (and the cross-chain/same-chain fill paths), analogous to the FrankenDAO fix that clamps user-supplied `_unlockTime`/`time` against `stakingSettings.maxStakeBonusTime`:
- Add a `maxOrderDeadlineWindow` (in blocks) to `Params`, settable only via the existing privileged `updateHostParams`-style governance path.
- In `placeOrder`, revert if `order.deadline > block.number + maxOrderDeadlineWindow`.
- Optionally, allow solvers to specify their own `validUntil` cap on-chain in `FillOptions` (already present) as a secondary, solver-controlled defense-in-depth layer, but do not rely on it as the sole mitigation since it depends on solver-side integration.

### Proof of Concept
1. Attacker (order placer) calls `placeOrder(order, ...)` with `order.deadline = block.number + N` for arbitrarily large `N` (e.g., effectively unbounded), escrowing input tokens.
2. Attacker requests bids from solvers; a solver signs a `UserOperation`/bid quoting `output` amounts based on current market rates.
3. Attacker holds the signed bid without executing `fillOrder`.
4. Time passes; market price moves such that the previously quoted `output` becomes favorable to the attacker (unfavorable to the solver).
5. Attacker (or attacker-controlled relayer) submits the stale bid to `fillOrder` at any point before `order.deadline`, which is still far in the future — the solver is forced to deliver output tokens at the stale rate since there is no on-chain check tying bid execution to a protocol-enforced maximum window from `placeOrder`.
6. The solver realizes the loss with no compensating premium, while the attacker profits from the unbounded optionality — repeatable across many orders for a systemic drain against solver liquidity, as `evm/src/apps/IntentGatewayV2.sol` and `evm/tron/contracts/apps/IntentGatewayV2.sol` impose no maximum `deadline` check on `placeOrder`.
