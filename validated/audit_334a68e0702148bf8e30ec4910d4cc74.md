### Title
Webhook `shop-domain` header trusted for tenant attribution while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC of the raw body only, then hands the caller-supplied `shop-domain` header (unauthenticated) to the app's handler as the tenant identifier. The equality the app relies on - "HMAC-verified bytes == the shop the data is attributed to" - does not hold, because `shop` is never part of the signed bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/verifies the HMAC exclusively against that signable string: [2](#0-1) 

`Registry.process` gates on this HMAC check and then builds the metadata handed to the app's handler directly from the unauthenticated `shop-domain` header: [3](#0-2) 

`Request#shop` simply reads the header with no cross-check against the signed payload: [4](#0-3) 

Consequently, the `shop` value that the handler uses to attribute the webhook body to a specific merchant/tenant is not bound by the HMAC at all - only the body bytes are. Any party who possesses one validly-signed webhook body/HMAC pair for shop A (which they can obtain by simply installing the app on their own Shopify development/trial store - an unprivileged act any internet user can perform) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `shop-domain` header with shop B's domain. `HmacValidator.validate` still returns true (body/HMAC unchanged), so `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` attributing shop A's signed data to shop B.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an app that keys any per-tenant logic (data storage, entitlement changes, uninstall/GDPR handling, billing state, etc.) off `WebhookMetadata#shop` can be made to apply attacker-controlled but validly-signed webhook content to a victim shop's record, i.e., cross-tenant data injection through the gem's own webhook processing API used exactly as documented.

### Likelihood Explanation
Medium-to-High for a would-be attacker: obtaining a validly HMAC'd webhook only requires installing/using the app on a shop the attacker legitimately controls (freely available via Shopify partner/dev stores) - no leaked secrets, tokens, or privileged access are needed. The only additional step is sending a normal HTTP POST to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header, which any internet client can do since the header is not authenticated.

### Recommendation
Bind the shop identity into the verified bytes, e.g., include `shop-domain` (and ideally `topic`/`webhook-id`) in `to_signable_string`, or independently cross-validate the header value against a value derivable from the signed body/subscription registration before trusting `WebhookMetadata#shop`. At minimum, document that `shop` in `WebhookMetadata` is not authenticated and must not be trusted for tenant attribution without an independent check (e.g., comparing to the shop associated with the specific subscribed webhook_id via a stored mapping).

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store (`attacker.myshopify.com`) and triggers a webhook (e.g., `orders/create`). Shopify delivers:
   - Headers: `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over raw body B>`, body `B`.
2. Attacker captures this exact `(B, HMAC)` pair.
3. Attacker POSTs to the app's webhook endpoint again with the same body `B` and the same valid `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` even though `B` never originated from `victim-shop`, confirming the shop/HMAC binding is broken.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
