### Title
Unvalidated reserve-offset subtraction in `canGraduate`/`previewLtUntilGraduation`/`_prepareGraduationLiquidity` causes a permanent revert (curve bricking) once K-slack drains `assetReserve` below the recovered virtual reserve - ([File: packages/contracts/src/Bonding.sol])

### Summary
CVE-2018-7320 is a class of bug where a protocol dissector computes an offset from untrusted/derived input and subtracts it from a buffer bound without validating that the offset is actually within range, causing a crash. `Bonding.sol` has the same structural flaw: it repeatedly computes `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` without ever checking that `assetReserve` is still ≥ the recovered virtual reserve. `Pair.swap`'s K-invariant check has a `+1` slack (`(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k`) that lets `assetReserve` be pushed to a smaller value than the invariant that held at mint time, so after enough buy/sell round trips `assetReserve` can end up strictly below `_launchTimeVirtualLtReserve`. Every call site that performs this unguarded subtraction then reverts with a `Panic(0x11)` arithmetic-underflow instead of failing gracefully.

### Finding Description
`_launchTimeVirtualLtReserve` recovers the launch-time virtual LT reserve purely from the immutable `k`/`TOTAL_SUPPLY` identity: [1](#0-0) 

This value is subtracted from the *live, mutable* stored `assetReserve` in three separate unvalidated places:

1. `canGraduate` (called on every buy that could cross the threshold, and directly by `triggerGraduation`, and by `sell` to check it isn't un-ripening a graduation): [2](#0-1) 

2. `previewLtUntilGraduation` (a view, but same pattern): [3](#0-2) 

3. `_prepareGraduationLiquidity` (the phase-1 graduation entry that computes `ltFromPair`): [4](#0-3) 

`assetReserve` starts life exactly equal to `virtualLtReserve` at `Pair.mint`: [5](#0-4) 

and is thereafter only mutated by `Pair.swap`, whose K-invariant check tolerates a `+1` rounding slack on *both* sides simultaneously: [6](#0-5) 

Because `Router._computeBuy`/`_computeSell` round `amountInUsed`/`assetOut` using integer division (`k / newReserveAsset`, `k / newReserveToken`) rather than exact algebra, and the overflow cap in `_computeBuy` performs a ceil-division re-derivation of `amountInUsed`: [7](#0-6) [8](#0-7) 

a sequence of buys and sells (especially ones that repeatedly hit the `OverflowCapDegenerate`-avoiding cap branch near curve sellout, or many small round trips that each leak a fraction of a wei via floor/ceil rounding in opposite directions) can walk `assetReserve` down below the immutable `virtualLtReserve` baked into `k` at mint. Once that happens, `assetReserve - _launchTimeVirtualLtReserve(...)` underflows and every caller of `canGraduate` — i.e. `sell()`, `buy()`'s post-trade graduation check inside `_executeBuy`, and `triggerGraduation()` — reverts with a `Panic(0x11)`.

### Impact Explanation
Once `assetReserve` dips below the recovered virtual reserve:
- `Bonding.sell` unconditionally calls `canGraduate(tokenAddress)` before allowing the sell to complete, so **all sells on that curve permanently revert**, freezing every trader's tokens on that curve (no way to exit).
- `Bonding.buy`'s `_executeBuy` calls `canGraduate` after every buy, so **all buys on that curve also permanently revert**, freezing further curve trading entirely.
- `triggerGraduation` reverts as well, so the token can never be pushed into `Lifecycle.Graduating`/`Graduated` — it is permanently stuck mid-curve with no upgrade path (graduation is one-shot and permissionless only from `Lifecycle.Curve`).
- The creator's raised LT and the traders' tokens are permanently locked in the `Pair` contract with no rescue path (`Router.graduate`/`Pair.transferAsset` are only reachable through the now-unreachable graduation flow).

This is a concrete permanent freeze of trader and creator funds on the affected curve — matching the "permanent freezing of trader, creator or LP funds" bar, and structurally the same root cause class as CVE-2018-7320: an offset value is subtracted from a bound without validating that the bound is still ≥ the offset, and the resulting crash (here, an EVM revert) denies further protocol operation.

### Likelihood Explanation
No privileged role is required — a single unprivileged trader (or several colluding/independent ones, since `buy`/`sell` are open to all) can repeatedly buy and sell on the same curve through `Zap.buy`/`Zap.sell`. Each round trip leaks or gains a wei-scale amount of `assetReserve` from the floor/ceil rounding asymmetry between `_computeBuy`'s cap-branch ceil-division and `_computeSell`'s floor-division. Given the permissionless, gas-cheap nature of curve trades and the many round trips available before a curve reaches its graduation threshold, this is a realistic-though-not-trivial griefing/DoS vector on any single-token curve, and it requires no special curve state beyond ordinary trading.

### Recommendation
- In `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity`, guard the subtraction: if `assetReserve <= _launchTimeVirtualLtReserve(...)`, treat `realLtRaised`/`ltFromPair` as `0` instead of underflowing.
- Alternatively (or additionally), tighten `Pair.swap`'s K-invariant check to eliminate the two-sided `+1` slack that allows `assetReserve` to be pushed below its mint-time floor over repeated trades, or explicitly clamp `assetReserve` to never fall below the immutable `virtualLtReserve` recovered from `k`.
- Add an invariant test asserting `assetReserve >= k / TOTAL_SUPPLY` holds after arbitrary sequences of buys/sells, to catch any future regression of this class.

### Proof of Concept
Conceptually (exact wei-level trade sequence to be confirmed with a Foundry fuzz/invariant test against `Router._computeBuy`/`_computeSell` and `Pair.swap`):
1. Launch a token via `Zap.createToken`, seeding the curve normally (`assetReserve == virtualLtReserve`).
2. Have an unprivileged trader alternate small `Zap.buy` / `Zap.sell` calls near the curve's sellout region, deliberately sized to repeatedly trigger `_computeBuy`'s `OverflowCapDegenerate`-avoiding ceil-division branch (`amountInUsed = cappedReserveAsset - reserveAsset`) followed by a `_computeSell` floor-division sell of the same tokens back.
3. Each such round trip nets a small downward drift in stored `assetReserve` relative to `virtualLtReserve` because the two branches round in opposite directions.
4. After enough round trips, `assetReserve` drops to `<= virtualLtReserve`.
5. The next call to `Bonding.sell`, `Bonding.buy`, or `Bonding.triggerGraduation` executes `assetReserve - _launchTimeVirtualLtReserve(...)` inside `canGraduate`/`_prepareGraduationLiquidity`, underflows, and reverts with `Panic(0x11)`, permanently bricking the curve.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
