### Title
Webhook HMAC does not bind the shop domain, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" purely via `Utils::HmacValidator.validate(request)` before dispatching to the app's handler with the shop taken from an unauthenticated header. Because the HMAC signable string only covers the raw body, the `shop`, `topic`, and `webhook_id` fields that are handed to host application handlers as trusted, verified data are never bound to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) . The `shop`, `topic`, and `webhook_id` accessors simply read the corresponding `shopify-*`/`x-shopify-*` HTTP headers with no cryptographic protection: [3](#0-2) .

`Registry.process` validates only this HMAC-over-body and, if it passes, immediately constructs `WebhookMetadata` from `request.shop`, `request.topic`, and `request.webhook_id` and calls the app's handler with them: [4](#0-3) . `HmacValidator.validate` computes an HMAC-SHA256 of `verifiable_query.to_signable_string` under `Context.api_secret_key` and compares it to the `hmac-sha256` header value [5](#0-4)  — it never incorporates the `shop`, `topic`, or `webhook_id` headers into the signed material.

The gem's own documentation tells developers that `Registry.process` "will verify the request did indeed come from Shopify," and that the resulting `data.shop` is a trusted field they can safely use, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`: [6](#0-5)  and [7](#0-6) . `WebhookMetadata.shop` is a plain, unauthenticated `String` field, with no mechanism tying it to the signature: [8](#0-7) .

The identity binding that should hold is: `shop domain authenticated by the HMAC == shop domain delivered to the handler`. Because the HMAC only covers the JSON body bytes, an attacker who can obtain any one validly-HMAC-signed webhook body/signature pair for the app (e.g., by installing the app on their own store — a normal, unprivileged action — and capturing a real webhook Shopify sends them) can replay that exact `(raw_body, hmac-sha256)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and optionally `shopify-topic`/`shopify-webhook-id`) for any victim shop's domain. `HmacValidator.validate` still returns `true` because the body and signature are unchanged and correctly HMAC'd with the real `Context.api_secret_key`, and `Registry.process` will happily hand `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` — with the attacker's chosen body content — to the app's handler as if it were an authentic event from the victim's shop.

### Impact Explanation
This breaks the shop/tenant identity binding across an authentication boundary that the gem explicitly claims to enforce ("verify the request did indeed come from Shopify"). Any app that uses `data.shop` from `WebhookMetadata` to key persistence, trigger per-tenant business logic, or attribute data (exactly as the gem's own example code does: `shop_domain: data.shop`) can be made to process attacker-crafted body content under an arbitrary victim shop identity. This is a cross-tenant data injection / spoofing primitive stemming directly from this gem's signature scope, not from host-application misuse of a documented contract — the contract itself (`Registry.process` "verifies the request came from Shopify") is broken for the `shop` field.

### Likelihood Explanation
The only prerequisite is that the attacker be able to install the app on their own store (a completely unprivileged, self-service action for any public app) to receive one legitimate webhook and its valid signature, then replay the body+signature to the app's public webhook endpoint with a forged `shopify-shop-domain` header. No access to `api_secret_key`, tokens, or victim credentials is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation before dispatching to handlers. At minimum, document that `data.shop` is not itself authenticated by the HMAC and must not be trusted without additional verification by the host app.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, completing real OAuth.
2. Shopify sends a legitimate webhook, e.g. `orders/create`, to the app's endpoint with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`; attacker controls the content of `B` (e.g., by creating an order with attacker-chosen fields on their own store).
3. Attacker captures `(B, H)` and re-sends a POST to the same webhook endpoint with headers `shopify-shop-domain: victim-shop.myshopify.com`, `shopify-topic: orders/create`, `shopify-hmac-sha256: H`, and body `B`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)` and it matches `H`, so validation passes [9](#0-8) .
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to treat attacker-controlled data `B` as belonging to `victim-shop.myshopify.com`.
