### Title
Webhook `shop-domain` (and `topic`) header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body for HMAC verification, while the `shop` (and `topic`, `api_version`, `webhook_id`) values used to route the webhook to a handler are read from unauthenticated HTTP headers. This breaks the identity binding `hmac_signed(shop) == shop_used_by_handler`, allowing an attacker who possesses one valid `(raw_body, hmac)` pair to relabel that payload as belonging to an arbitrary shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from HTTP headers that are never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then dispatches to the handler using the unauthenticated header-derived `shop`: [3](#0-2) 

`HmacValidator.validate` calls `validate_signature`, which computes the HMAC over `verifiable_query.to_signable_string` (the raw body for `Request`) and compares it to the `hmac` header value — it never incorporates `shop`, `topic`, or any other header: [4](#0-3) 

The resulting `WebhookMetadata` (containing the attacker-controlled `shop`) is what's handed to the app's `WebhookHandler#handle`: [5](#0-4) 

Binding that should hold: `hmac_signed_scope == shop_identity_used_for_handler_routing`. Before the request: the gem only proves "this exact `raw_body` was HMAC-signed with the app's secret" — it proves nothing about which shop the payload is for. After processing: the handler receives `WebhookMetadata#shop` taken verbatim from the `shopify-shop-domain` header, with no cryptographic tie between that value and the signed body. An attacker (or a malicious/compromised merchant of the same app) who owns/receives one legitimate webhook delivery for shop A can resend that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`, `shopify-webhook-id`) with shop B's domain (or any other topic). `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` happily dispatches the request to shop B's/that topic's handler with the forged metadata.

### Impact Explanation
This is a cross-tenant identity-binding failure: the value the app relies on to know "which merchant this webhook event belongs to" is entirely attacker-controllable while the request still passes signature verification. Depending on how a downstream app's `WebhookHandler#handle` implementation uses `data.shop` (e.g., looking up that shop's session/access token to act on data, writing records keyed by shop, or triggering redact/GDPR flows for a different shop than the one that actually generated the event), this can lead to cross-tenant data corruption, spoofed mandatory-webhook compliance actions (`shop/redact`, `customers/redact`, `customers/data_request`) against the wrong tenant, or event/topic confusion (since `topic` is also unsigned) causing a payload for one topic to be processed by a handler intended for another. This matches the report's bug class: a field (`shop`/`topic`) is *acted upon* for tenant identity but is *not covered by the HMAC* that is supposed to authenticate the whole request.

### Likelihood Explanation
Exploitation requires an attacker to obtain at least one valid `(raw_body, hmac)` pair — trivially available to any merchant using the app (they receive their own webhooks) or to anyone who can observe one delivery (e.g., logging, replay from a compromised low-privilege environment). No `client_secret`, access token, or privileged credential is needed; the attacker only replays a previously-seen valid signed body against the app's own public webhook endpoint with forged headers. This is a realistic, unprivileged-internet-facing exposure inherent to how this gem structures webhook verification.

### Recommendation
Bind the identity fields used for routing into the HMAC-verified scope, or otherwise cryptographically tie `shop`/`topic` to the signed payload — e.g., require the app to independently confirm that `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting it for any privileged action, and treat `topic`/`shop` headers as merely a routing hint rather than an authenticated claim. At minimum, document prominently that `Webhooks::Request#shop` and `#topic` are unauthenticated and must not be used as the sole tenant-identity source for privileged operations, and consider rejecting/replay-protecting duplicate `webhook_id` values combined with mismatched shop headers.

### Proof of Concept
```ruby
# Attacker captures ONE legitimate webhook delivery for shop-a.myshopify.com:
raw_body = '{"id":123,"note":"legit order"}'
valid_hmac_header = "<value captured from the real X-Shopify-Hmac-Sha256 header>"

# Attacker replays it to the app's public webhook endpoint, but swaps the shop header:
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => valid_hmac_header,   # unchanged, still matches raw_body
  "shopify-shop-domain" => "shop-b.myshopify.com", # forged - attacker-controlled
  "shopify-api-version" => "2024-01",
  "shopify-webhook-id" => "forged-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# HmacValidator only checks raw_body against the secret - passes:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process now calls the handler with shop == "shop-b.myshopify.com",
# even though the payload/HMAC actually belongs to shop-a.
ShopifyAPI::Webhooks::Registry.process(request)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
