## Finding [1](#0-0)  contains the reachable analog of the reported rounding bug.

### Title
Rounding to Zero in `balanceStore.convertToBalance` Lets an Unprivileged Workflow Owner Consume Billed Resources Without Being Charged Credits - (File: core/services/workflows/metering/balance_store.go)

### Summary
The Sherlock report describes `addWETHRewards` rounding a small deposit's `accRewardPerShare` down to zero, silently losing value. The chainlink `metering` package has the same rounding-to-zero pattern in the gas-spend conversion path used to bill workflow executions for capability resource usage.

### Finding Description
`convertToBalance` converts a resource amount (e.g. gas spent by a capability node) into a universal-credit amount to debit from the workflow's balance: [2](#0-1) 

For gas spend types, the conversion is `amount.Div(rate).Round(defaultDecimalPrecision)` where `defaultDecimalPrecision` is fixed at 10 decimal places: [3](#0-2) 

If a capability's per-call gas usage is small relative to the configured `rate` (units-per-credit), the quotient rounds down to `0`. This function is invoked in `Report.Settle`, which is called after every capability step in a workflow execution, to compute `spentCredits` from the actual node-reported spend and reconcile it against the amount earmarked by `Deduct`: [4](#0-3) 

When `spentCredits` for a step rounds to zero, `Settle` refunds essentially the full earmarked deduction back to the balance instead of debiting the real cost: [5](#0-4) 

A workflow owner (an unprivileged CRE user who only controls the content of their own workflow) fully controls how many capability invocations are made and can shape each invocation to have low enough per-call gas/resource spend that each individual `Settle` call rounds `spentCredits` to zero, while the underlying capability work is still performed by the DON. Repeating this over many small calls lets the workflow consume real capability/compute resources while being billed zero (or near-zero) credits.

### Impact Explanation
This is a billing/accounting bypass reachable purely from workflow content supplied by any unprivileged workflow owner — no special role or node compromise required. Systematic exploitation causes the platform (or the DON operators who don't get properly reimbursed) to eat the cost of executing capability work that should have been metered, i.e., an "unauthorized" quota/fund bypass analogous to the locked/lost WETH in the original report (there, funds get stuck; here, funds/credits that should be spent are never collected).

### Likelihood Explanation
Likelihood is limited by how granular capability spend reporting is and by the specific `rate` values configured by the billing service for a given resource type; an attacker would need per-call spend values that are small enough relative to the configured rate to round below 10^-10 credits, and would need to repeat this across many invocations to accumulate meaningful "free" usage. It's plausible but requires workflow crafting and knowledge of current rate cards.

### Recommendation
Avoid rounding the per-call converted spend down to zero when the underlying amount is non-zero — e.g., accumulate the truncated remainder across settlements for the same execution/resource dimension instead of discarding it, or round up (ceiling) rather than round-to-nearest/down when converting resource spend to credits for debiting purposes.

### Proof of Concept
Conceptual PoC (would need to be validated against a running billing/metering setup):
1. A workflow owner deploys a workflow that invokes a paid capability (e.g. gas-metered) many times per execution, each call performing minimal real work so that the capability's reported `SpendValue`/`SpendValueInGasUnits` is very small relative to the resource's configured `rate` (`GAS.<chainSelector>` units-per-credit).
2. For each invocation, `Report.Settle` calls `balance.ConvertToBalance(unit, value)` → `convertToBalance` → `amount.Div(rate).Round(10)`, which evaluates to `0` for sufficiently small `amount`.
3. `spentCredits` for that step is `0`, so `balance.Add(step.Deduction.Sub(spentCredits))` refunds nearly the entire earmarked deduction back to the workflow's balance.
4. Repeating steps 1–3 across many calls in the same or successive executions lets the workflow consume capability compute/gas resources while its credit balance is barely debited, eventually submitting a `SubmitWorkflowReceipt` with `CreditsConsumed` far below actual resource cost. [6](#0-5)

// convertToBalance converts a resource dimension amount to a credit amount.
// This method should only be used under a read lock.
func (bs *balanceStore) convertToBalance(fromResourceType string, amount decimal.Decimal) (decimal.Decimal, error) {
	rate, ok := bs.conversions[fromResourceType]
	if !ok {
		return amount, ErrResourceTypeNotFound
	}

	// Special case for gas as gas token conversions are provided in amount per credit.
	// Other rates are provided as the inverse.
	if isGasSpendType(fromResourceType) {
		if rate.IsZero() {
			return decimal.Zero, nil
		}

		return amount.Div(rate).Round(defaultDecimalPrecision), nil
	}

	return amount.Mul(rate), nil
}
