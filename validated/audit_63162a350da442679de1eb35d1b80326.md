### Title
Unprotected re-initialization of `LockupContract::new()` allows account takeover and theft of locked NEAR - (File: lockup/src/lib.rs)

### Summary
The `LockupContract::new()` initializer is missing the explicit re-initialization guard (`assert!(!env::state_exists(), ...)`) that every sibling contract in this repo enforces manually. Because the codebase's other `#[init]` constructors (`lockup-factory`, `multisig`, `staking-pool`, `staking-pool-factory`, `voting`, `whitelist`) all rely on this same manual `assert!(!env::state_exists(), "Already initialized")` / `"The contract is already initialized"` check rather than any automatic protection from the `#[init]` macro itself, its absence in `lockup/src/lib.rs::new` means the lockup contract can be re-initialized after deployment by any unprivileged caller.

### Finding Description
`LockupContract::new()` is marked `#[init]` but performs no check that the contract has not already been initialized: [1](#0-0) 

Compare this to every other production initializer in the repository, which explicitly guards against re-initialization inside the function body: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

The consistent presence of this manual check across every other contract in the repo strongly indicates that, for the near-sdk-rs version used here, `#[init]` does not automatically prevent a method from being invoked again after state already exists — the protection is opt-in and must be written by the developer. `lockup/src/lib.rs::new` omits it.

Because `new()` is a normal public entrypoint with no access control (any account can send a `FunctionCall` transaction targeting `new` on the deployed lockup account), an attacker can call it again after the contract has been deployed and funded. This resets the entire `LockupContract` state, including:
- `owner_account_id` → attacker-controlled value
- `lockup_information.lockup_amount` → recomputed from `env::account_balance()` (i.e., the account's current, already-funded balance)
- `vesting_information` → attacker can set to `VestingInformation::None`, wiping out any pending vesting/termination hash
- `staking_information` → reset to `None`
- `foundation_account_id` → attacker can omit it (removing the Foundation's ability to terminate vesting) [8](#0-7) 

Once the attacker becomes `owner_account_id`, `assert_owner()` passes for all subsequent owner-only calls, so the attacker can invoke `transfer()` to move the account's liquid NEAR balance to their own account, `select_staking_pool`/`stake`/`unstake`/`withdraw_from_staking_pool` to redirect staked funds, and eventually `add_full_access_key()` to fully take over the account: [9](#0-8) [10](#0-9) 

This is a direct structural analog of the reported `TokenDrop.initialize()` bug: an unprotected initializer that can be re-called to hijack the privileged role (`owner`/`factory`) that gates fund movement.

### Impact Explanation
This is Critical. An unprivileged attacker who re-calls `new()` on an already-deployed, already-funded `LockupContract` can install themselves as `owner_account_id`, bypass any vesting/termination restrictions, and subsequently drain the contract's locked/liquid NEAR balance via the owner-only `transfer` and staking methods, or gain full access to the account entirely. This matches "Unauthorized transfer, withdrawal, spending, or release of locked... NEAR through public-call... accounting failure reachable by an unprivileged user" and "Permanent freezing... or irrevocable loss of user or protocol funds in lockup release... flows."

### Likelihood Explanation
High, assuming the deployed near-sdk-rs version does not itself block re-invocation of `#[init]`-marked methods once state exists (which the consistent manual guards elsewhere in this same codebase strongly imply). The attack requires only a single unauthenticated `FunctionCall` transaction to the target lockup account's `new` method with attacker-chosen arguments — no privileged role, key compromise, or race condition is needed. The only uncertainty is whether the specific near-sdk-rs version pinned in `lockup/Cargo.lock` might add this protection at the macro/runtime level independent of the manual check; this could not be fully confirmed since the near-sdk-rs macro source itself is not present in this repository.

### Recommendation
Add the same explicit guard used in every other production contract to `lockup/src/lib.rs::new`:
```rust
assert!(!env::state_exists(), "The contract is already initialized");
```
Additionally, add regression tests asserting that calling `new()` a second time on an already-initialized `LockupContract` panics, mirroring the tests recommended for `TokenDrop.initialize()`.

### Proof of Concept
1. Deploy and initialize `LockupContract` normally via the `lockup-factory`, funding it with NEAR under `owner_account_id = victim`.
2. Attacker sends a `FunctionCall` transaction directly to the deployed lockup account, calling `new` again with:
   - `owner_account_id = attacker`
   - `vesting_schedule = None`
   - no `foundation_account_id`
   - arbitrary `staking_pool_whitelist_account_id`
3. Because `new()` has no `state_exists` check, the call succeeds and overwrites contract state; `owner_account_id` is now `attacker`.
4. Attacker calls `transfer(amount, attacker_account)` — `assert_owner()` at [11](#0-10)  passes, and the account's liquid NEAR balance is transferred to the attacker.

    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,

                "The transfer poll account ID is invalid"

        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),

            lockup_timestamp: lockup_timestamp.map(|d| d.0),

            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
