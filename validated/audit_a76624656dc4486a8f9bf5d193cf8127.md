### Title
Missing requester-to-node ownership check allows arbitrary Node-bound ServiceAccount token forgery - (pkg/registry/core/serviceaccount/storage/token.go)

### Summary
`(r *TokenREST) Create` validates a `BoundObjectRef{Kind:"Node"}` only by fetching the named Node and comparing the caller-supplied UID against the actual Node UID, with no check that the requesting identity has any relationship to that Node. This is asymmetric with the `Pod` binding branch, which explicitly enforces `name == pod.Spec.ServiceAccountName` before allowing the bind.

### Finding Description
In the `BoundObjectRef` switch statement, the `Pod` case enforces an ownership relationship: `if name != pod.Spec.ServiceAccountName { return nil, errors.NewBadRequest(...) }` [1](#0-0) . The `Node` case, however, only performs an unconditional `Get` of the referenced Node and sets `uid = node.UID`, with no check relating the requester, the target service account, or any workload to the referenced Node: [2](#0-1) 
The only later validation is `if ref.UID != "" && uid != ref.UID { return nil, errors.NewConflict(...) }` [3](#0-2) , which merely confirms the caller's supplied UID matches the current Node's UID (anti-staleness check), not that the caller is authorized to assert affiliation with that specific node.

The RBAC verb gating this endpoint is `create` on `serviceaccounts/token`, which is granted to any subject bound to the built-in `edit` ClusterRole via `rbacv1helpers.NewRule("create").Groups(legacyGroup).Resources("serviceaccounts/token").RuleOrDie()` [4](#0-3) , which aggregates into `admin` as well [5](#0-4) . This confirms the "create serviceaccounts/token" precondition is a commonly-granted namespace permission, not a privileged/rare one. Node names and UIDs are readable via `get nodes`, a broad cluster-scoped grant present in many roles (e.g. `system:node-proxier`, `system:kubelet-api-admin`, `view`-aggregate roles referencing nodes indirectly, or explicit custom grants).

The `NodeRestriction` admission plugin and the Node authorizer are specifically scoped to identities in the `system:nodes` group (actual kubelets) — the code comment in `NodeRules()` confirms this restricts *nodes* creating tokens bound to *pods on themselves*, not general users creating tokens bound to arbitrary Node objects [6](#0-5) . A regular non-node identity authorized only via `edit`/`admin` on `serviceaccounts/token` is not a member of `system:nodes` and is therefore not restricted by that admission logic at all for this call path.

### Impact Explanation
An attacker with ordinary namespace-scoped `create` on `serviceaccounts/token` (a common permission bundled in the built-in `edit`/`admin` ClusterRoles) and cluster-scoped `get` on `nodes` (a commonly granted read permission) can mint a token whose claims falsely assert binding to an arbitrary Node they do not operate, via `token.Claims(*svcacct, pod, secret, node, ...)` [7](#0-6) . Any downstream system that inspects `node`-bound token claims as a trust signal for node identity/affiliation (rather than relying on the mTLS node client certificate / Node authorizer group membership) could be deceived into treating the caller as operating that node — this is an identity/claims-forgery and isolation-invariant violation, matching the "authentication/token forgery" and "serviceaccount/identity confusion" bounty impact classes.

### Likelihood Explanation
Feasibility is high given the stated preconditions are common: `create serviceaccounts/token` is part of the default `edit` ClusterRole aggregation, and `get nodes` is broadly granted in many clusters. No collusion with a node, kubelet, or cluster-admin is required. The exploit is fully reproducible by any authenticated identity meeting these two RBAC grants.

### Recommendation
Add an ownership/ relationship check to the `Node` case analogous to the `Pod` case — e.g., require that the calling identity is itself the node in question (verified via `user.Info` group membership in `system:nodes` and node name matching), or otherwise restrict `BoundObjectRef{Kind:"Node"}` binding to be initiated only by the Node's own kubelet identity, consistent with the intent described in the `NodeRestriction`/Node-authorizer comments for the `system:node` role.

### Proof of Concept
Integration test modeled on the "bound to service account and node" sub-test in `test/integration/auth/svcaccttoken_test.go`, but modified so that:
1. The calling user/service account is a plain namespaced identity bound to the `edit` ClusterRole (or an explicit `create` grant on `serviceaccounts/token`) plus `get` on `nodes` — not a `system:nodes` identity.
2. A target Node object is created that has no relation to the caller (different node name than any node the caller "owns").
3. Call `CreateToken(sa, BoundObjectRef={Kind:"Node", Name:<arbitrary-node>, UID:<node.UID>})` through the TokenREST endpoint.
4. Assert the call succeeds (200) and the returned token's claims (`kubernetes.io.node.name` / node UID) reference the arbitrary node, demonstrating `Create()` never validated any relationship between the caller and the target Node — only the supplied UID against the actual Node UID.
