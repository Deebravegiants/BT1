### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while the `shop-domain` header (exposed via `#shop` and forwarded to the handler as `WebhookMetadata#shop`) is read out-of-band and never included in the signed material. `Registry.process` trusts this header as the tenant identifier without any additional binding to the HMAC-verified bytes, breaking the equality `shop_used_for_dispatch == shop_covered_by_hmac`.

### Finding Description
`HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it to the `hmac` field using `OpenSSL.secure_compare`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

but `shop` is parsed from a separate, unauthenticated header: [3](#0-2) 

`Registry.process` validates the HMAC over the body only, then unconditionally dispatches the handler using `request.shop` taken from that unsigned header: [4](#0-3) 

Because the `shop-domain` header is never part of the signed bytes, any `(raw_body, hmac)` pair that is valid for one shop (i.e., a webhook the attacker legitimately receives for a shop they control, or any topic whose body content is generic/predictable) remains valid when replayed with an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header value. The gem's own signature check cannot distinguish "HMAC valid for shop A's payload" from "HMAC valid for payload, shop header set to victim shop B" — the binding `bytes verified == identity acted on` does not hold. This is exactly the class of bug in the report: a value that downstream logic relies on for correctness/authorization (there, `lastUpdated`/liquidity gating; here, tenant identity) is advanced/used without being covered by the check meant to guard it (there, the liquidity gate; here, the HMAC).

### Impact Explanation
The webhook `shop` value is the tenant key the host application is expected to use to look up sessions/data for that merchant (this is the documented purpose of `WebhookMetadata#shop`). Since it is unauthenticated relative to the HMAC, an attacker who controls a shop that has installed the app (unprivileged, ordinary merchant/dev-store access — no leaked secret needed) can capture one valid `(raw_body, hmac)` pair from their own store's webhook delivery and replay it toward the app's webhook endpoint with the `shop-domain` header rewritten to any other merchant's domain. Any handler logic keyed off `data.shop` (e.g., session/data mutation, cache invalidation, compliance actions) will be executed against the wrong tenant, i.e., cross-tenant access/action — a Critical-class impact per the given rubric.

### Likelihood Explanation
Likelihood is bounded by the need to obtain a genuine `(body, hmac)` pair, which any developer/merchant who installs the app can trivially produce by triggering a webhook topic against their own store (webhooks are delivered to any registered/mandatory endpoint upon ordinary store events, requiring no special privilege). The header fields are then attacker-controlled at the HTTP layer before reaching `Webhooks::Request.new`, and the gem performs no cross-check between the signed body and the shop header.

### Recommendation
Bind the shop identity to the signed content, or otherwise validate it out of band against the app's own installed-shop/session store before dispatch:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in the value that is HMAC-verified, or
- After HMAC validation, require `Registry.process` (or the caller) to cross-check `request.shop` against a shop for which the app holds/expects an active session before invoking `handler.handle`, rather than trusting the header unconditionally.

### Proof of Concept
1. Register the app's webhook endpoint and install the app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any webhook topic with a stable/predictable body (many compliance/lifecycle topics send minimal or attacker-influenceable bodies) — capture the genuine `X-Shopify-Hmac-Sha256` value Shopify computed for that body using the app's real `client_secret`.
3. Replay the same raw body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against `hmac`: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload originated from the attacker's own shop, causing the host app to act on/associate data with the victim tenant.
