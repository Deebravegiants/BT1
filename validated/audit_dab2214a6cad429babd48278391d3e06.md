### Title
Unbounded ABI `uint256` fields in BEEFY/SP1 proof conversions panic the runtime via `.expect()`, allowing any signed account to halt consensus updates - (File: `evm/rust/src/conversions.rs`)

### Summary
`do_submit_proof` → `verify_and_apply` in `modules/pallets/beefy-consensus-proofs/src/lib.rs:805-838` ABI-decodes an attacker-controlled `SP1BeefyProof`/`BeefyConsensusProof` and immediately converts it to the SCALE `beefy_verifier_primitives` types via `.into()`. Those `From` impls, in `evm/rust/src/conversions.rs`, blindly call `.try_into().expect("... out of bounds")` on Solidity `uint256` fields (`blockNumber`, `validatorSetId`, `authorityIndex`, `leafIndex`, `para_id`, MMR-leaf `version`, etc.) to narrow them into Rust `u32`/`u64`/`u8`. None of these fields are range-checked before the conversion.

### Finding Description
The ABI proof format encodes these values as `uint256` (see `evm/rust/src/conversions.rs:334-366`, `:249-274`, `:307-332`, `:391-400`, and the SP1 test conversion at `modules/consensus/beefy/verifier/src/test.rs:326-330`), so a submitter fully controls their magnitude on the wire. `pallet-beefy-consensus-proofs::verify_and_apply` (`modules/pallets/beefy-consensus-proofs/src/lib.rs:818-838`) performs:
```
let abi_proof = <ismp_abi::sp1_beefy::SP1Beefy::SP1BeefyProof as SolType>::abi_decode_params(abi_payload)...;
let scale_proof: beefy_verifier_primitives::Sp1BeefyProof = abi_proof.into();
```
before any cryptographic verification takes place. The `.into()` call runs through the `.expect()`-guarded narrowing conversions in `conversions.rs` (e.g. `value.blockNumber.try_into().expect("block number out of bounds")` at line 347, `value.authorityIndex.try_into().expect("authority index out of bounds")` at line 363, `value.leafIndex.try_into().expect("mmr leaf index out of bounds")` at line 371, `value.version.try_into().expect("mmr leaf version out of bounds")` at lines 251/309). Supplying any of these fields with a value exceeding the target integer's range (e.g. `blockNumber = 2^40`) makes the `expect()` panic. This is functionally the same bug class as ALPINE-CVE-2023-46842: an internal sanity/range check that assumes an untrusted external value has already been "translated" or truncated to a legal range, and treats a violation as an unrecoverable fault (`revert("Code should be unreachable")`-style crash) instead of a caught, rejected error.

### Impact Explanation
`submit_proof` is reachable by any `ensure_signed` account, with no stake, permission, or reputation gate (`modules/pallets/beefy-consensus-proofs/src/lib.rs:360-374`). A panic raised inside on-chain runtime execution during extrinsic dispatch is not a normal `DispatchError` — since it originates from Rust's panic machinery (`.expect()`) rather than a `Result::Err`, it unwinds inside the WASM/host runtime call for that extrinsic. Depending on how the executive/panic handler treats this, it can abort block-authoring for validators executing that block, effectively denying the BEEFY consensus route the ability to process further proofs (a stalled/unable-to-deliver-messages condition for the consensus pipeline that feeds `pallet-ismp`), satisfying the "route unable to deliver messages" impact class explicitly in scope.

### Likelihood Explanation
High: constructing an ABI-encoded `SP1BeefyProof`/`BeefyConsensusProof` with an out-of-range `uint256` field (e.g. `blockNumber` or `authorityIndex` > `u32::MAX`) requires no cryptographic break and no special access — only a signed extrinsic with the malformed bytes, which is exactly the shape `submit_proof` accepts as untrusted input before any SP1/ECDSA verification occurs.

### Recommendation
Replace every `.try_into().expect(...)` in the ABI→SCALE `From` impls in `evm/rust/src/conversions.rs` (and the mirrored ones in `modules/consensus/beefy/verifier/src/test.rs`) with fallible `TryFrom` conversions that return an error the pallet can map to `Error::<T>::AbiDecodeFailed` (or a dedicated variant), performing range validation on `blockNumber`, `validatorSetId`, `authorityIndex`, `leafIndex`, `para_id`, and MMR-leaf `version` before dispatch reaches `handlers::handle_incoming_message`.

### Proof of Concept
1. Craft an ABI-encoded `SP1BeefyProof` (or `BeefyConsensusProof` for the naive path) where `commitment.blockNumber` (or `validatorSetId`/`authorityIndex`/`leafIndex`) is set to a `uint256` value greater than `u32::MAX` (or `u64::MAX` for 64-bit fields).
2. Submit it via `submit_proof(origin, proof)` as any signed account, prefixed with the appropriate `PROOF_TYPE_SP1`/`PROOF_TYPE_NAIVE` byte (`modules/pallets/beefy-consensus-proofs/src/lib.rs:818-837`).
3. `Self::do_submit_proof` → `verify_and_apply` executes `abi_proof.into()`, which panics inside `evm/rust/src/conversions.rs` at the corresponding `.expect("... out of bounds")` call before any signature or ZK proof is checked, crashing extrinsic execution.
