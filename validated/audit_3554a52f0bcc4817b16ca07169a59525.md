### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC-signable string solely from the raw request body, while the `shop` (tenant identifier) is read from a separate, unauthenticated header. `ShopifyAPI::Webhooks::Registry.process` validates only that HMAC before dispatching `data.shop` to the app's handler as the trusted tenant identity, breaking the intended binding `HMAC(shared_secret, verified_bytes) == HMAC(shared_secret, bytes_the_app_acts_on)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to that body [2](#0-1) . `HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string`, i.e. the body bytes, never incorporating the shop header [3](#0-2) . `Registry.process` treats a passing HMAC check as proof the whole request "did indeed come from Shopify" and immediately constructs `WebhookMetadata` using `request.shop`, handing it to the app's handler as the authoritative tenant identity [4](#0-3) . The equality the gem implicitly claims is `verified(bytes) == acted_on(shop)`, but in reality only the body is verified while the shop header is parsed and trusted unverified — exactly the "bytes verified versus bytes parsed" / "field acted on but not covered by the HMAC" pattern.

Because all Shopify shops share the same app-level `client_secret` used to sign every shop's webhooks, a malicious or compromised merchant (an authenticated, but unprivileged, member of one tenant) can capture one of their own legitimate webhook deliveries (valid body + valid HMAC), then replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. The signature still validates because it never covered the header, so `Registry.process` accepts the forged shop identity and forwards it to the handler [4](#0-3) . The gem's own documentation instructs developers to treat `data.shop` as the trusted shop for storage/dispatch (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`), which host apps follow in good faith since the library claims to have verified the request came from Shopify [5](#0-4) .

### Impact Explanation
This crosses a tenant boundary: an attacker with a legitimate account/webhook on their own shop can inject attacker-chosen payload data tagged as belonging to a different, victim shop into any downstream logic keyed off `data.shop` (e.g., per-tenant data stores, job queues, or session/session-token lookups keyed by shop). Depending on the host application, this can lead to cross-tenant data corruption/injection — a Critical-class cross-tenant access impact, since it undermines the one binding (`shop` domain) that this gem is responsible for authenticating in webhook processing.

### Likelihood Explanation
Exploitation requires only capturing one's own legitimate webhook (trivial — any merchant/dev account can trigger webhooks on their own store) and replaying it to the same public webhook endpoint with a modified `shop-domain` header — no access to the app's `client_secret`, access tokens, or other shops' credentials is required. This is straightforward for any unprivileged, authenticated merchant of the app.

### Recommendation
Include the shop domain (and ideally topic/api-version/webhook-id) in the HMAC-signable string, or otherwise cryptographically bind the shop header to the verified body, e.g. by validating `shop` against an独立 out-of-band source of truth (such as a previously stored session for that shop id extracted only after signature validation of a canonicalized string that includes the shop). At minimum, `HmacValidator`/`Request#to_signable_string` should not allow the tenant identifier to be read from data that isn't covered by the signature it validates.

### Proof of Concept
1. App exposes the standard webhook endpoint per the docs:
```ruby
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
)
```
2. Attacker owns `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app; attacker captures the raw body `B` and the valid header `x-shopify-hmac-sha256: H` computed as `HMAC-SHA256(client_secret, B)`.
3. Attacker resends a request to the same endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid because `to_signable_string` is only `B`), but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds (it only checks `B` against `H`) [6](#0-5) ; `Registry.process` builds `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [7](#0-6)  and the app's handler executes attacker-controlled body content attributed to `victim-shop.myshopify.com`.
