## Analysis

The reported bug pattern — a governance/admin setter accepting a percentage-like coefficient without validating its upper bound, which then causes downstream arithmetic to go out of bounds — has a direct, unprivileged-reachable analog in the Tron variant of `IntentGatewayV2`.

### Title
Unvalidated `protocolFeeBps` in Tron `IntentGatewayV2.setParams` permanently bricks `placeOrder` via arithmetic underflow - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical EVM `IntentGatewayV2` validates `protocolFeeBps` and `surplusShareBps` on every parameter update through `IntentsBase._validateParams`, which explicitly rejects `protocolFeeBps >= 10_000` to prevent the fee-deduction arithmetic from underflowing. [1](#0-0)  The Tron port of the same contract, however, implements `setParams` with no such bound check at all — it simply overwrites `_params` wholesale. [2](#0-1) 

### Finding Description
`placeOrder` (the unprivileged, user-facing entry point every order placer calls) computes the protocol fee and the reduced escrow amount as:
```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
``` [3](#0-2) 

This mirrors exactly the AMM Governance flaw's shape: a coefficient meant to stay within `0 <= value < 1 (10_000 bps)` is accepted with no upper-bound enforcement, and downstream arithmetic (here, a subtraction rather than a `wln()` computation) is not defensively guarded against the invalid value. If `protocolFeeBps` (set via `setParams`, which has no validation on the Tron variant) is ever configured `>= 10_000`, `protocolFee` exceeds or equals `originalAmount`, and `reducedAmount = originalAmount - protocolFee` underflows. Since the contract is Solidity `>=0.8`, this reverts unconditionally — but it reverts *every* call to `placeOrder` for every input token, permanently. There is no separate governance-only setter to fix the fee afterward — the constructor path is `setParams`, called by `_admin`, which then zeroes `_admin`, so there is no path to correct a bad value once set. [2](#0-1) 

Contrast with the validated path, where `_validateParams` is invoked on both `initialize` and every `UpdateParams` governance message and would revert the configuration attempt itself rather than let a broken parameter into storage. [4](#0-3) 

### Impact Explanation
Once `protocolFeeBps >= 10_000` lands in storage on the Tron deployment, `placeOrder` becomes permanently unusable for any input whose fee path is taken (i.e., whenever `protocolFeeBps > 0`, which is the case here). This is a route unable to deliver/process intents at all — a full denial of service on the IntentGateway's core user-facing function, with no on-chain recovery mechanism since `_admin` is cleared after the one-shot `setParams` call.

### Likelihood Explanation
This requires only that the initial `setParams` call (the only place this value is ever set on the Tron variant) is passed an out-of-range value — no attacker action against unprivileged users is required beyond this single misconfiguration, which the parallel, audited EVM implementation treats as dangerous enough to explicitly guard against. The absence of any equivalent check in the Tron port is a straightforward code-parity defect rather than a hypothetical.

### Recommendation
Add the same bound check used in `IntentsBase._validateParams` to the Tron `IntentGatewayV2.setParams` (and any future update path): reject `protocolFeeBps >= 10_000` and `surplusShareBps > 10_000` before committing to `_params`. Consider replacing the raw subtraction in `placeOrder` with a defensive check (e.g., `require(protocolFee <= originalAmount)`) as belt-and-braces, and audit all other admin-set percentage/bps fields across the Tron contracts for the same missing-bound-check pattern.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and call `setParams` with `Params.protocolFeeBps = 10_000` (or higher) and any nonzero destination/base fee path exercised. [2](#0-1) 
2. `_admin` is zeroed after this call, so the value can never be corrected via `setParams` again.
3. Any user calls `placeOrder` with `order.inputs` containing a token with `amount > 0`; `protocolFeeBps` resolves to the stored value (>=10_000). [5](#0-4) 
4. `protocolFee = (originalAmount * protocolFeeBps) / 10_000 >= originalAmount`, so `reducedAmount = originalAmount - protocolFee` underflows and reverts, bricking `placeOrder` for every future caller.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }
