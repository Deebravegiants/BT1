### Title
`findMatchingWithdrawal` misattributes status/txHash between two same-token withdrawals in one intent - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` matches a NEAR-side `WithdrawalIdentifier` to a POA-bridge withdrawal record solely by `nep141:<near_token_id>` via `findMatchingWithdrawal`, with no disambiguation by destination address or amount. When a single intent contains two withdrawals of the same POA token (e.g. `nep141:bch.omft.near`) to different destinations, both `WithdrawalIdentifier`s can resolve to the same (first-matching) record, so one leg's completion status/txHash gets attached to the other leg.

### Finding Description
The broken equality is: `WithdrawalIdentifier[i].status/txHash` should equal the status/txHash of the withdrawal whose `destinationAddress`/`amount` matches `withdrawalParams` for leg `i`. Instead, `describeWithdrawal` (poa-bridge.ts:313-343) calls `getWithdrawalStatusWithRetry` (queried by `args.tx.hash`, the shared NEAR intent tx hash, identical for both legs) and then `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` [1](#0-0) . `findMatchingWithdrawal` uses `Array.prototype.find`, returning only the first entry whose `nep141:${w.data.near_token_id}` equals `assetId` [2](#0-1) . The function's own doc comment explicitly admits: "multiple withdrawals of the same token in a single transaction are not supported" [3](#0-2) .

Nothing upstream prevents such a batch: `createWithdrawalIdentifiers` in `withdrawal-watcher.ts` iterates `withdrawalParams` and calls `bridge.supports()`/`createWithdrawalIdentifier()` per item, tracking only a per-route counter for `index`, with no uniqueness check on `assetId` combined with `destinationAddress`/`amount` [4](#0-3) . `watchWithdrawal` then polls `bridge.describeWithdrawal({...args.wid, ...})` independently for each `WithdrawalIdentifier` [5](#0-4) , so both legs query the same POA `withdrawal_status` response (since both share the same NEAR intent tx hash) and both apply `findMatchingWithdrawal`, which is blind to `index`, `destinationAddress`, and `amount`.

Exploit flow: an integrator (or a user's own batch call) submits one intent with two `nep141:bch.omft.near` withdrawals to two different destination addresses. The POA bridge processes and completes both, returning a `withdrawal_status` response with two entries for the same `near_token_id` but different `address`/`transfer_tx_hash`/`amount`. When the SDK calls `describeWithdrawal` for withdrawal-identifier #2 (destination B), `findMatchingWithdrawal` still returns entry #1 (destination A) because it just does `.find()` on `near_token_id` match, so identifier #2 gets reported `completed` with entry #1's `txHash`, even though the payout to destination B may still be pending, failed, or went to a different destination.

None of the existing guards catch this: `validateAddress`/`compareAddresses`/`validateWithdrawal` operate on a single withdrawal in isolation and do not compare across sibling withdrawals in the same batch; `supports()` only classifies bridge eligibility per param; there is no `assert` anywhere checking `withdrawals.length <= 1` or disambiguating by amount/address when multiple candidates match the token.

### Impact Explanation
An integrator polling `IntentsSDK.waitForWithdrawalCompletion` for withdrawal-identifier #2 (destination B) would receive `{status: "completed", txHash: <entry-#1's-hash>}` while the actual funds for destination B might not have arrived (or arrived to a different address/amount), and vice versa for withdrawal-identifier #1. This is a status/hash misreport that can cause an integrator to credit a user or release downstream funds/refunds based on the wrong withdrawal record — matching "High: a status or hash misreport making an integrator credit or refund twice." It is repeatable for every batch containing two-or-more same-`assetId` POA-bridge withdrawals.

### Likelihood Explanation
Preconditions: the integrator (or attacker crafting the batch on the integrator's behalf, since assetId/amounts/destinationAddress are attacker-controlled inputs forwarded by the integrator) must submit an intent containing 2+ withdrawals of the same POA token (`nep141:bch.omft.near` or any other POA-bridge token) with different destinations in one intent. No special privilege or timing needed — nothing in `supports()`, `validateWithdrawal()`, or `createWithdrawalIdentifiers()` blocks or dedupes such batches. Attacker cost is a normal withdrawal-batch call. This is fully attacker-reachable through the public SDK entrypoint `IntentsSDK.waitForWithdrawalCompletion` and is deterministically repeatable any time the POA API returns ≥2 entries for the same `near_token_id` tied to one intent transaction.

### Recommendation
Disambiguate `findMatchingWithdrawal` by more than `assetId`: match on `assetId` plus `destinationAddress` (compare via `compareAddresses`) and `amount` (accounting for fee), falling back to an explicit error/`pending` state (not a silent "completed" mismatch) when multiple ambiguous candidates remain. Alternatively, reject/flag batches at withdrawal-identifier creation time (`createWithdrawalIdentifiers`) when the same bridge route + assetId appears more than once, until the POA bridge API provides a per-withdrawal correlation ID that the SDK can propagate and match on unambiguously.

  const widA = { landingChain: Chains.BCH, index: 0,

  const widB = { landingChain: Chains.BCH, index: 1,
    withdrawalParams: { assetId: "nep141:bch.omft.near", amount: 200000n, destinationAddress: "DEST_B", feeInclusive: false },
    tx: { hash: "near-tx-hash", accountId: "test.near" } };

  const resultA = await bridge.describeWithdrawal(widA);
  const resultB = await bridge.describeWithdrawal(widB);

  // EXPECTED (broken today): resultB incorrectly equals resultA's completed status/hash
  // instead of reflecting DEST_B's own PENDING record.
  expect(resultA).toEqual({ status: "completed", txHash: "dest-A-hash" });

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
