### Title
Unauthorized deposit spend via FunctionCall-permission access key when `FixDelegateActionDepositWithFunctionCallError` is disabled - ([File: runtime/runtime/src/actions.rs])

### Summary
In `validate_delegate_action_key`, the deposit>0 check for `FunctionCallPermission` keys sets `result.result` to `DepositWithFunctionCall` but only returns early if `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError` is enabled. Without the early return, execution falls through to the `receiver_id` and `method_names` checks; if those checks pass (receiver matches and method is allowed/unrestricted), no error is ever set and the function returns `Ok(())` with `result.result` untouched, allowing a non-zero-deposit `FunctionCall` under a deposit-restricted access key to be validated as authorized.

### Finding Description
The relevant code: [1](#0-0) 
sets `result.result = Err(DepositWithFunctionCall)` when `function_call.deposit > Balance::ZERO`, but only returns early (`return Ok(())`) when the fix flag is enabled: [2](#0-1) 
If the flag is disabled, execution continues into the `receiver_id` mismatch check and the `method_names` mismatch check. Both of these are independent `if` blocks that only set `result.result` to a *different* error and return early when they themselves detect a violation. If the delegate action's receiver matches `function_call_permission.receiver_id` and the method name is empty-restricted or matches an allowed method, neither of those checks triggers, so no error is ever assigned and execution falls through to the end of the `if let Some(function_call_permission) = ...` block: [3](#0-2) 
The function then proceeds to update the nonce and returns `Ok(())` with `result.result` still in its default/unset state — meaning the FunctionCall action carrying `deposit > 0` is treated as validated and permitted to execute under an access key whose entire security model (`FunctionCallPermission`) is predicated on making zero-deposit calls only. This is a genuine authorization/spend-restriction bypass, not merely an error-message overwrite: attacker-supplied deposit funds could be transferred from the sender's balance via a receipt with `deposit > 0`, which the access key was never authorized to grant.

### Impact Explanation
This maps to an authorization bypass / unauthorized fund transfer from a deposit-restricted access key (NEAR bounty class: balance/fund loss via authorization bypass). An account owner who grants a `FunctionCallPermission` key (e.g., to a dApp or automation service) with an implicit or explicit expectation of zero-deposit calls could have that key used to move NEAR tokens as a deposit to the permitted receiver/method, exceeding the key's intended authority.

### Likelihood Explanation
The bypass is entirely conditioned on `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError` being disabled for the transaction's `current_protocol_version`. The code and comments in `runtime/runtime/src/actions.rs` confirm this was a real, previously-shipped bug that was fixed by adding the early return; the fix is only active once the associated protocol version is reached/enabled on the network. I could not verify from the available index whether this feature is currently stabilized/enabled by default on the version this codebase targets (the enum entry and its associated protocol version constant were not found via search in `core/primitives-core/src/version.rs`, likely due to index size limits truncating that file). If the feature is already enabled at the network's current protocol version, this path is not exploitable; if it is not yet enabled (e.g., on a pre-upgrade protocol version, in tests targeting older `current_protocol_version`, or if the feature is ever reverted/disabled), the bypass is trivially and repeatably triggerable by any unprivileged holder of a `FunctionCallPermission` key by submitting a `DelegateAction`/meta-transaction with one `FunctionCall` action, a receiver matching the key's permission, an allowed method name, and `deposit > 0`.

### Recommendation
Remove the protocol-feature gate on the early return for the deposit check (or ensure the feature is unconditionally enabled/stabilized) so that `DepositWithFunctionCall` always returns immediately regardless of protocol version, preventing any fallthrough into the receiver/method checks. Alternatively, restructure the validation to short-circuit all three checks (deposit, receiver, method) via early return unconditionally, independent of feature flags, since deposit-with-FunctionCall-permission should never be a version-gated behavior once the fix is intended to be permanent.

### Proof of Concept
Unit test in `runtime/runtime/src/actions.rs` test module:
1. Construct an access key with `AccessKeyPermission::FunctionCall` restricting `receiver_id` to `"receiver.test"` and empty `method_names` (any method allowed).
2. Build a `DelegateActionV2` with exactly one `Action::FunctionCall` action targeting `"receiver.test"`, method `"foo"`, and `deposit = 1` (non-zero).
3. Run `validate_delegate_action_key` twice:
   - With `apply_state.current_protocol_version` set below the `FixDelegateActionDepositWithFunctionCallError` activation version: assert that `result.result` is `Ok(())` (bug manifests — no error set) or, per the described PoC, assert it is not `Err(DepositWithFunctionCall)`, demonstrating the deposit restriction was silently bypassed.
   - With protocol version at/above the fix activation: assert `result.result == Err(ActionErrorKind::DelegateActionAccessKeyError(InvalidAccessKeyError::DepositWithFunctionCall))`.
4. Additionally assert that in the pre-fix case, no error prevents the nonce update and action from being scheduled for execution (i.e., that a receipt with `deposit > 0` would be produced), confirming actual fund-movement impact rather than a cosmetic error-message issue.
