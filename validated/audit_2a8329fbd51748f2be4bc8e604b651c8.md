Audit Report

## Title
Unvalidated Negative `offset` in GraphQL Pagination Causes Out-of-Bounds Slice Panic - (File: core/web/resolver/query.go)

## Summary
`pageOffset` in [1](#0-0)  casts a client-supplied `*int32` offset straight to `int` with no lower-bound check, and `Resolver.Chains` in [2](#0-1)  only validates `offset >= count` (an upper bound), never `offset < 0`, before executing `chains[offset:end]`. A negative offset therefore reaches a Go slice expression with a negative index, which triggers a runtime panic (`slice bounds out of range`). The same unguarded pattern feeds `EthTransactions`/`EthTransactionsAttempts` [3](#0-2)  and `CoreRelayerChainInteroperators.ChainStatuses`/`NodeStatuses` [4](#0-3) .

## Finding Description
The root cause is confirmed: `pageOffset` performs no negativity check [5](#0-4) , and `Chains` only guards the upper bound before slicing [6](#0-5) . Authentication is enforced only via `authenticateUser`, which merely requires a valid session with any role (including the lowest, view-only, role) [7](#0-6) ; it performs no input validation on pagination arguments, so it does not mitigate this issue. This confirms the exploit path is reachable by any authenticated GraphQL user regardless of role.

However, the GraphQL resolver layer runs on `graph-gophers/graphql-go`, a library whose field-execution engine wraps each resolver invocation with panic recovery, converting a panic raised inside a resolver (such as the slice panic here) into a GraphQL error entry in the response for that field, rather than allowing the panic to propagate up and crash the HTTP handler, the goroutine, or the node process. I was not able to inspect the vendored copy of that library in this index to re-confirm the exact recovery code inline, but this is a well-documented, stable behavior of `graph-gophers/graphql-go` across its versions (resolver panics are caught and surfaced as `errors` in the GraphQL response). This significantly changes the realistic worst-case outcome described in the original claim.

## Impact Explanation
The concrete, verifiable impact is: an authenticated user (any role) can cause the `chains` (or `ethTransactions`/`ethTransactionsAttempts`) query to panic internally instead of returning the documented client error path ("offset out of range" style validation), resulting in an unhandled runtime panic within resolver execution. Given the library's per-field panic recovery, the realistic consequence is a malformed/error GraphQL response for that single request rather than a node-wide crash or destabilization. The original claim's higher-severity outcome ("crash or destabilize the node process") is speculative and explicitly flagged by the reporter as unconfirmed ("could not be fully confirmed within the scope of this scan"). Absent evidence that the panic escapes per-request recovery, this does not meet the bar for a Denial-of-Service impact against the node process; it is, at most, a robustness/input-validation defect producing an unexpected panic-derived error response for a single request.

## Likelihood Explanation
Triggering the panic condition itself requires only a valid authenticated session of any role and a single GraphQL query with a negative `offset` — this part is high likelihood and easily reproducible. But escalating this to actual node-level DoS/crash is unconfirmed and, based on the well-known panic-recovery behavior of the underlying GraphQL execution library, unlikely under default configuration.

## Recommendation
Regardless of the bounded blast radius, this is a legitimate input-validation gap that should be fixed: validate `offset` (and `limit`) for negativity immediately in `pageOffset`/`pageLimit` (and any `ParsePaginatedRequest`-equivalents), returning a client-facing GraphQL error instead of relying on panic recovery. Add explicit `offset < 0` / `offset > len(slice)` checks before every slice expression in `Chains`, `ChainStatuses`, and `NodeStatuses`.

## Proof of Concept
Send, as any authenticated node API/GraphQL user:
```graphql
query {
  chains(offset: -1, limit: 10) {
    results { id }
  }
}
```
Expected/confirmed behavior: `offset := pageOffset(args.Offset)` = `-1` passes the `offset >= count` check and reaches `chains[offset:end]` = `chains[-1:end]`, panicking inside the resolver. Under `graph-gophers/graphql-go`'s standard execution model this panic is expected to be recovered and surfaced as a GraphQL error for that query rather than crashing the server process — this last point should be confirmed with an integration test against the actual running GraphQL handler (`core/web/router.go`) to verify whether the HTTP response is a clean error (expected) or the server/process is disrupted (would need separate confirmation).

```go
func (r *Resolver) Chains(ctx context.Context, args struct {
	Offset *int32
	Limit  *int32
}) (*ChainsPayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	offset := pageOffset(args.Offset)
	limit := pageLimit(args.Limit)

	relayersMap := r.App.GetRelayers().GetIDToRelayerMap()

	chains := make([]chainlink.NetworkChainStatus, 0, len(relayersMap))
	for k, v := range relayersMap {
		s, err := v.GetChainStatus(ctx)
		if err != nil {
			return nil, err
		}

		chains = append(chains, chainlink.NetworkChainStatus{
			ChainStatus: s,
			Network:     k.Network,
		})
	}

	count := len(chains)
	if count == 0 {
		// No chains are configured, return an empty ChainsPayload, so we don't break the UI
		return NewChainsPayload(nil, 0), nil
	}

	// bound the chain results
	if offset >= count {
		return nil, fmt.Errorf("offset %d out of range", offset)
	}
	end := count
	if limit > 0 && offset+limit < end {
		end = offset + limit
	}

	sortByNetworkAndID(chains)
	return NewChainsPayload(chains[offset:end], safeInt32(count)), nil
}
```
