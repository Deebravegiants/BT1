This confirms the finding: the docs explicitly promise that `Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and the returned `WebhookMetadata.shop` is documented as "The shop domain of the webhook" that handlers are meant to trust and act on (`docs/usage/webhooks.md:14`, `lib/shopify_api/webhooks/webhook_handler.rb:6-12`) — yet the `shop` value is taken directly from an unauthenticated header.

### Title
Webhook shop/topic/webhook-id headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` (used in `Registry.process`) only proves that the body bytes were signed with the app's `api_secret_key` [2](#0-1) [3](#0-2) . The `shop`, `topic`, `webhook_id`, and `api_version` fields consumed by `Registry.process` and forwarded to the app's handler via `WebhookMetadata` are all read straight from HTTP headers that are entirely outside that signature [4](#0-3) .

### Finding Description
The identity binding broken is: **shop authenticated by the HMAC (none) ≠ shop acted upon by `Registry.process`/`WebhookMetadata`**.

`HmacValidator.validate_signature` recomputes the HMAC purely over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that string is just `@raw_body` [1](#0-0) [5](#0-4) . The `shop`, `topic`, and `webhook_id` accessors instead read the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers with no cryptographic tie to the signed body [4](#0-3) .

`Registry.process` validates only the body HMAC and then unconditionally trusts these headers, dispatching to the registered handler with a `WebhookMetadata` built from them: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id)` [3](#0-2) . Because the `api_secret_key` used to sign webhooks is a single per-app secret shared across every merchant that installs the app (the same secret validates OAuth callbacks for all shops, see `HmacValidator.validate` used identically in `Auth::Oauth.validate_auth_callback` [6](#0-5) ), any merchant who has installed the app can obtain a validly-signed `(body, hmac)` pair by triggering a real webhook on their own store (e.g. `customers/data_request`, `app/uninstalled`, `orders/create`). Since the header fields are not part of the signed content, that same body+hmac pair can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header swapped to name a different, victim shop that also has the app installed. `HmacValidator.validate` still returns `true` because the body/hmac pair is genuine, and `Registry.process` forwards the forged `shop` value to the handler as if it were authoritative [3](#0-2) .

The gem's own documentation reinforces that host apps are expected to trust this value without further checks: it states that `process` "will verify the request did indeed come from Shopify" [7](#0-6)  and describes `data.shop` simply as "The shop domain of the webhook" [8](#0-7) , with the sample handler using `data.shop` directly to route/enqueue work for "that shop" [9](#0-8) .

### Impact Explanation
This crosses the tenant boundary the gem is responsible for maintaining: a shop that legitimately installed the app can cause the app to process attacker-chosen webhook body content under the identity of a different, victim shop that also installed the app. Depending on how the host app uses `WebhookMetadata.shop` (looking up the victim's session/access token, writing to the victim's records, or actioning mandatory compliance webhooks like `customers/redact`/`shop/redact` against the victim), this enables cross-tenant data injection or unauthorized mandatory-webhook actions attributed to a shop the attacker does not control — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation only requires the attacker to be a normal merchant who has installed the app (no special privilege, no access to `api_secret_key`, no TLS interception). They trigger a real webhook against their own store to obtain a validly signed body, then POST that same body/HMAC pair to the app's public webhook endpoint with a rewritten `shop-domain` (and optionally `topic`/`webhook-id`) header naming any other installed shop.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the verified signature rather than trusting raw headers:
- Include `shop`, `topic`, and `webhook_id` in the signable content used for HMAC verification (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`/`host`/`state` into its HMAC [10](#0-9) ), or
- Require the caller to supply the expected shop for the webhook (e.g. resolved from a route or a known active session) and have `Registry.process` reject the request if `request.shop` doesn't match, instead of unconditionally forwarding the header-derived value to `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and subscribes to a registered topic (e.g. `customers/data_request`).
2. Attacker triggers that webhook from their own store's admin, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — both valid per `HmacValidator.validate` since they were genuinely signed with the app's shared `api_secret_key`.
3. Attacker replays the identical body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a different shop that has installed the app).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the HMAC [1](#0-0) .
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the registered handler as though the event genuinely originated from the victim shop [3](#0-2) .
