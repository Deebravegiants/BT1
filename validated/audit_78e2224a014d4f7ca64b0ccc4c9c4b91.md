## Title
Unchecked ERC20 `transfer()` return value in IntentGatewayV2 (Tron) permanently freezes escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed intent funds using a raw low-level `.call()` with the `IERC20.transfer` selector and only checks that the *call itself* did not revert (`success`). It never inspects the ABI-encoded boolean returned by the token. Any ERC20/TRC20 token that follows the "return false on failure" convention (rather than reverting) will cause the escrow accounting and order-finalization logic to proceed as if funds were delivered, while the tokens never actually leave the contract — permanently freezing the beneficiary's funds. This is the exact bug class described in the RealityCards H-01 report: relying on a non-reverting ERC20 `transfer`/`transferFrom` without validating its return value.

### Finding Description
In `withdraw()`, which is invoked from `onAccept()` when a `RedeemEscrow`/`RefundEscrow` cross-chain message is delivered by any relayer: [1](#0-0) 

the order is marked filled (`_filled[body.commitment] = beneficiary`) and the escrow ledger is decremented (`_orders[body.commitment][token] -= amount`) unconditionally, based solely on whether the low-level `.call` succeeded — not on the decoded return value:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

The same unchecked pattern is used for fee release in the same function and for `SweepDust` handling: [3](#0-2) [4](#0-3) 

A low-level `call` to a contract's `transfer(address,uint256)` succeeds (`success == true`) as long as the callee does not revert — regardless of whether the ABI-encoded return data actually decodes to `true`. Many TRC20/ERC20 tokens (including some historically deployed on Tron) return `false` on failure instead of reverting. Under this pattern:
1. `token.call(...)` returns `success = true` even though the transfer failed and no tokens moved.
2. `_orders[body.commitment][token]` is decremented and `_filled[body.commitment]` is set, permanently marking the order as settled.
3. The beneficiary never receives the tokens, and there is no other code path to retry or reclaim the now-stranded escrow — the funds are permanently locked in the contract.

By contrast, the non-Tron `IntentGatewayV2` at `evm/src/apps/intentsv2/IntentsBase.sol` uses OpenZeppelin's `SafeERC20.safeTransfer`, which reverts on a false return, correctly reverting the whole message-handling attempt if a transfer silently fails: [5](#0-4) 

This confirms the Tron variant deviates from the hardened pattern and reintroduces exactly the vulnerability class the RealityCards report warns about.

### Impact Explanation
Any relayer delivering a legitimate `RedeemEscrow`/`RefundEscrow`/`SweepDust` message for an order that escrows a non-standard, non-reverting ERC20/TRC20 token can trigger this. Because `_filled`/escrow bookkeeping is updated as if the payout succeeded, the beneficiary (a user or a solver who filled the order) permanently loses access to their escrowed tokens — the tokens remain stuck in the `IntentGatewayV2` contract with no recovery path. This is a concrete, permanent freezing/loss of user funds in the intents escrow flow, satisfying the "permanent freezing of funds" impact criterion.

### Likelihood Explanation
No privileged role is needed — the trigger is simply a normal `onAccept` execution of a cross-chain settlement message from Hyperbridge, once any order escrows a token that returns `false` on failed transfers instead of reverting. Since this is Tron's ERC20/TRC20 ecosystem — which historically has tokens with such non-standard `transfer` implementations — the likelihood of this token behavior being encountered in production is materially higher than on typical EVM chains, making exploitation plausible without any attacker action beyond escrowing such a token in an order.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`/`safeTransferFrom` (already imported and used via `using SafeERC20 for IERC20;` at the top of the contract), so that a token returning `false` reverts the whole settlement attempt instead of silently marking escrow as settled.

### Proof of Concept
1. User places an order on the Tron `IntentGatewayV2` escrowing a TRC20 token `T` whose `transfer()` returns `false` on failure instead of reverting (e.g., due to being paused, blacklisted, or insufficient contract-side balance under some edge condition).
2. Solver fills the order on the destination chain; Hyperbridge relays a `RedeemEscrow` message back to the source chain.
3. Any relayer submits the proof, triggering `onAccept()` → `withdraw()`.
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call executed without reverting) even though `T.transfer` internally returned `false` and moved no tokens.
5. `_orders[commitment][token] -= amount` and `_filled[commitment] = beneficiary` are committed; `EscrowReleased` is emitted.
6. The beneficiary never receives token `T`; the tokens remain stuck in the `IntentGatewayV2` contract with no further code path to reclaim them, since the order is already marked filled.
