Audit Report

## Title
Missing `return` after failed OIDC session persistence (and after failed email-claim extraction) causes false "login success" audit event and success response - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `oidcAuthenticator.handleTokenExchange`, two error branches (missing `email` claim at lines 226-230, and failed `oidc_sessions` INSERT at lines 257-260) log the error and write an HTTP 500 body but fail to `return`, unlike every other error branch in the same function. Execution falls through to emit an `audit.AuthLoginSuccessNo2FA` audit event and set/save a session cookie referencing a session ID that was never persisted to the database, and potentially returns `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})` on top of the already-written 500 body.

## Finding Description
`handleTokenExchange` at [1](#0-0)  handles a missing `email` claim without `return`, and at [2](#0-1)  handles a failed session INSERT without `return`, in contrast to every other error branch in the function which consistently calls `return` (e.g., [3](#0-2) ). Because of these missing `return` statements, control flow proceeds to [4](#0-3) , which unconditionally emits an `AuthLoginSuccessNo2FA` audit event, sets/saves a gin session cookie for `clSession.ID`, and returns `Success: true` to the client — even though the session row was never written to `oidc_sessions`. The stale cookie is later validated via `AuthorizedUserWithSession` at [5](#0-4) , which will fail lookup against the (non-existent) row and return `ErrUserSessionExpired`, so no actual privilege bypass results.

## Impact Explanation
This is a state/log-integrity issue rather than an authentication bypass: the audit trail records logins that never completed, and the client may receive a misleading `Success: true` response (or a garbled double body) despite backend failure. Since the DB lookup on subsequent use fails (`sql.ErrNoRows` → `ErrUserSessionExpired`), no unauthorized access, session hijack, or privilege escalation is achieved. This does not map to a concrete in-scope impact category (node API authentication/role bypass, key/secret exfiltration, unauthorized job run/fund movement, gateway impersonation, allowlist/subscription bypass, or cross-user response corruption) — it is purely an audit-logging/response-consistency defect.

## Likelihood Explanation
Triggering requires an OIDC INSERT failure (transient DB error/constraint violation) concurrent with an otherwise-successful OIDC exchange — not something an unprivileged remote attacker can reliably force, and even when triggered, produces no actionable exploit beyond a misleading log entry.

## Recommendation
Add `return` after both error branches, consistent with the rest of the function, so that a failed session persistence or claim extraction halts the flow before the audit-success event and cookie are set.

## Proof of Concept
N/A — no concrete exploit path exists; the bug is confirmed by code inspection but has no in-scope security impact since the resulting session cookie cannot be used to authenticate (the DB row lookup fails on `AuthorizedUserWithSession`).
