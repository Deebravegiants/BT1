### Title
Webhook shop identity not covered by HMAC signature allows cross-tenant webhook spoofing - (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC signature over the raw request body only, while the `shop` identity used by `Registry.process` to route the webhook to the merchant's handler is read from an unsigned HTTP header. The HMAC therefore proves the body wasn't tampered with, but it proves nothing about which shop the payload belongs to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that body [2](#0-1) .

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (i.e., the raw body) and compares it against the computed HMAC — the `shop` field plays no part in this check [3](#0-2) . `HmacValidator.validate_signature` confirms the signable string used for comparison is exactly `to_signable_string`, i.e. body-only [4](#0-3) .

Once the HMAC check passes, `Registry.process` immediately trusts `request.shop` and forwards it, unauthenticated, to the handler via `WebhookMetadata.new(topic: ..., shop: request.shop, ...)` [5](#0-4) . Host applications are documented to use this `shop` value to resolve which merchant's session/store the payload belongs to.

Binding broken (as an equality): `shop_used_for_tenant_routing (request.shop, from header)` ≠ `shop_covered_by_hmac (bytes verified, which is raw_body only)`. Any attacker who can obtain one valid `(raw_body, hmac)` pair — trivially available since it's their own shop's webhook delivery, or any webhook whose body content they can predict/replay — can resubmit that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` will succeed (it never inspected the header), and the forged shop identity will flow into the handler as if genuinely delivered for that victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: it lets one merchant (or anyone who obtains a single valid webhook body+HMAC combination) impersonate a different shop's webhook delivery in the eyes of the host application, since this gem's own validation logic reports the spoofed request as authentic. Depending on how the host app uses `WebhookMetadata#shop` (e.g., mandatory `shop/redact`/`customers/redact` compliance webhooks, or app-specific data sync), this can lead to cross-tenant data corruption or disclosure — meeting the "cross-tenant access" critical impact bar.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP POST to the app's public webhook endpoint with a previously-observed valid `(body, hmac)` pair and an attacker-chosen `shop-domain` header — no access to `api_secret_key`, tokens, or Shopify infrastructure is needed. Obtaining one legitimate `(body, hmac)` sample is straightforward for any app-installing merchant (their own webhook deliveries), making this reachable by an unprivileged internet user with an installed instance of the app.

### Recommendation
Bind the shop identity into the material that is HMAC-verified, or otherwise cryptographically tie `shop-domain` to the signed payload before trusting it — e.g., include the shop domain header (or verify it against Shopify's IP ranges/mTLS) as part of `to_signable_string`, or require the caller to independently confirm the shop domain against a per-shop webhook secret rather than a single shared `api_secret_key` covering all tenants.

### Proof of Concept
1. App owner (attacker) installs the target app on their own shop `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker POSTs that exact captured body and HMAC header to the app's webhook endpoint again, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses the forged headers [6](#0-5) ; `Registry.process` calls `HmacValidator.validate(request)`, which only re-hashes `raw_body` and matches the still-valid signature [7](#0-6) .
4. The handler is invoked with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"` even though the payload never originated from Shopify for that shop, achieving cross-tenant spoofing purely through this gem's own validation path.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
