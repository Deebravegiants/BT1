### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `Utils::HmacValidator.validate` authenticates the *body bytes only*. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from HTTP headers and are never part of the signed data, yet `Webhooks::Registry.process` uses those same unauthenticated header values to select the handler and to build the `WebhookMetadata` (`shop:`, `topic:`) that is handed to the app's business logic.

### Finding Description
`Request#hmac` decodes the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header, and `Request#to_signable_string` is defined as: [1](#0-0) 

`HmacValidator.validate_signature` only ever compares the HMAC against `verifiable_query.to_signable_string`, i.e. the raw body: [2](#0-1) 

`Registry.process` performs this single check and then dispatches using `request.topic` and constructs `WebhookMetadata` using `request.shop`, both of which come straight from headers that were never included in the HMAC computation: [3](#0-2) 

`Request#shop` and `Request#topic` simply read the corresponding header with no cross-check against the signed body: [4](#0-3) 

**Binding that should hold:** `shop_used_by_handler == shop_that_the_signed_bytes_originated_from`. In this implementation the equality is: `shop_used_by_handler == header("shopify-shop-domain")`, a value entirely disjoint from `to_signable_string` (`@raw_body`), so nothing cryptographically ties the claimed shop/topic to the signed payload — this is the direct analog of the reward-calc report's "rewards acted upon (tracked balance) not being bound to the value that was actually verified (claimed rewards)": here, the tenant identity acted upon (`shop`) is not bound to the value that was actually HMAC-verified (the body).

**Exploit path:** The app's shared `client_secret` (`Context.api_secret_key`) is the same for every shop that installs the app; it is not shop-specific. An unprivileged internet user can install the target public app on their own (e.g. free trial/dev) store and passively receive legitimately-signed webhooks for actions they trigger themselves. Because the signature only covers the body, the attacker can capture one such valid `(raw_body, hmac)` pair and replay it directly to the app's webhook endpoint while rewriting only the `shopify-shop-domain` and/or `shopify-topic` headers (e.g. spoofing a victim shop, or relabeling the topic as `app/uninstalled`, `shop/redact`, `customers/redact`, etc.). `HmacValidator.validate` still returns `true` because it only recomputes the HMAC over `@raw_body`, which is unmodified. `Registry.process` then invokes the handler registered for the spoofed topic with `WebhookMetadata#shop` set to the victim's domain, even though nothing about the victim shop was ever authenticated.

### Impact Explanation
This breaks the tenant isolation boundary the gem is supposed to provide to host applications: a request that Shopify never sent for the victim shop is delivered to the app's webhook handlers as if it were an authentic, HMAC-verified event for that shop. Depending on what the host app does with `WebhookMetadata#shop`/`#topic` (uninstall cleanup, GDPR redaction, session invalidation, order/customer state changes, billing state changes, etc.), this enables cross-tenant state corruption purely by leveraging the gem's own (mis-)designed verification surface — qualifying as cross-tenant access under the given Critical impact category.

### Likelihood Explanation
Requires only: (1) an attacker-controlled install of the app on any shop (unprivileged, self-serve), and (2) the ability to send an HTTP POST with custom headers to the app's public webhook endpoint. No access token, secret, or privileged account is required — the shared `client_secret` never needs to be known by the attacker, since they simply replay bytes Shopify itself signed for their own store.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material that is verified, or otherwise cryptographically tie the header values to the authenticated body (e.g., require the body/topic/shop to be checked against fields embedded in the payload itself, or include the relevant headers in `to_signable_string` if Shopify's signing scheme is updated to support it) before trusting `request.shop`/`request.topic` for dispatch and business-logic identity decisions.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., updates a product) so Shopify sends a legitimately HMAC-signed webhook to the app's endpoint, with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC(client_secret, B)`.
3. Attacker captures `(B, H)` and POSTs to the same webhook endpoint again, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and (optionally) `x-shopify-topic: app/uninstalled`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC(client_secret, B)` and it matches `H`, so validation passes.
5. `Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches to the handler for the spoofed topic and builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though `victim-shop` never sent this webhook.
