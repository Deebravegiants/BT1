## Title
WrappedHyperFungibleToken locks/mints the user-specified `amount` instead of the actual tokens received or held, causing insolvent minting or permanently stuck refunds with non-standard ERC20 tokens - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` but encodes the *requested* `params.amount` — not the amount actually received by the contract — into the cross-chain `Message.amount` field that is dispatched to the peer chain. The peer contract mints or unlocks exactly that cached `message.amount` on `onAccept`, and re-mints/unlocks the same cached amount on `onPostRequestTimeout`. For fee-on-transfer or rebasing ERC20 underlyings, the contract's actual token balance can diverge from this cached figure, producing either unbacked minting on the destination chain or a permanently reverting/stuck timeout refund on the source chain — the same root cause described in the referenced Zerem finding (cached locked amount diverging from actual held balance for non-standard ERC20s).

### Finding Description
In `send()`: [1](#0-0) 

the contract calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and then builds the dispatch message via `_buildDispatchPost`, which encodes `params.amount` directly: [2](#0-1) 

No post-transfer balance check is performed to confirm the contract actually received `params.amount` of the underlying token — unlike the `IntentGatewayV2` code path, which explicitly measures `balanceOf` before and after transfers to account for fee-on-transfer tokens (`evm/src/apps/IntentGatewayV2.sol:260-300`, and the same pattern in `evm/tron/contracts/apps/IntentGatewayV2.sol:391-446`). `WrappedHyperFungibleToken` has no equivalent protection.

On the destination chain, `onAccept` unconditionally unlocks/mints `message.amount`: [3](#0-2) 

If a message times out, `onPostRequestTimeout` on the *source* chain attempts to refund the same cached `message.amount` back to the sender by transferring from the contract's own balance of the underlying: [4](#0-3) 

Two concrete divergence scenarios:
1. **Fee-on-transfer underlying**: `safeTransferFrom` delivers less than `params.amount` to the contract, but `message.amount == params.amount` is still dispatched. The destination peer mints/unlocks the full, uncollateralized `params.amount` — an unbacked mint / permanent over-crediting of the destination chain relative to what is actually escrowed on the source.
2. **Rebasing underlying (Ampleforth-style) or any balance-modifying mechanism**: Tokens are locked at `params.amount`, but before the message is delivered or before a timeout is processed, a negative rebase reduces the contract's actual token balance below the cached `message.amount`. When `onPostRequestTimeout` tries to `safeTransfer(refundee, message.amount)`, the transfer reverts because the contract's actual balance is insufficient — permanently freezing the locked funds, exactly mirroring the Zerem `_lockFunds`/unlock scenario in the referenced report. Conversely, a positive rebase leaves excess tokens permanently stuck in the contract with no rescue mechanism.

### Impact Explanation
This can result in either (a) unbacked minting of the wrapped token on the destination chain relative to what is actually escrowed on the source chain (loss of the 1:1 backing guarantee documented as central to the HFT/Wrapped-HFT design), or (b) permanent freezing of a user's locked funds when a timeout refund reverts due to insufficient real balance. Both are concrete fund-safety violations reachable by any unprivileged user who calls `send()` with a non-standard ERC20 configured as the `_underlying` token. Severity is Medium, consistent with the referenced report, since it requires the deploying owner to configure a fee-on-transfer/rebasing token as `_underlying` — a scenario the contract does not guard against or document as unsupported.

### Likelihood Explanation
Any external, unprivileged caller can trigger this simply by calling `send()` on a `WrappedHyperFungibleToken` deployment whose configured `_underlying` is a fee-on-transfer or rebasing ERC20 — no privileged role or special conditions are needed beyond that token choice, which the contract's `configure()` function permits without restriction on token type. Given that Hyperbridge integrations may wrap arbitrary ERC20s (as documented for "any existing ERC20"), the surface for encountering such a token is realistic.

### Recommendation
- Measure the actual balance delta (`balanceOf(address(this))` before/after `safeTransferFrom`) in `send()` and use that measured amount — not the caller-supplied `params.amount` — when building `Message.amount`, mirroring the pattern already used in `IntentGatewayV2`.
- In `onPostRequestTimeout` and `onAccept`, cap the transferred/minted amount to `min(message.amount, IERC20(_underlying).balanceOf(address(this)))`, or otherwise support partial refunds, to avoid permanent reverts if the balance has since changed.
- Document that rebasing/fee-on-transfer ERC20s are unsupported as `_underlying`, and/or add an owner-only rescue function to sweep excess balances that arise from positive rebases.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` with `_underlying` set to a fee-on-transfer token (e.g., 1% transfer fee) or an Ampleforth-style rebasing token.
2. Alice calls `send(params)` with `params.amount = 1000`. `safeTransferFrom` delivers only 990 tokens to the contract (fee-on-transfer case), but `_buildDispatchPost` still encodes `amount: 1000` in the dispatched `Message`.
3. The peer `WrappedHyperFungibleToken`/`HyperFungibleToken` on the destination chain receives the POST request and unlocks/mints the full 1000 in `onAccept` — 10 tokens more than what is actually backing it on the source chain.
4. Alternatively, if the message times out before delivery and the underlying rebases downward such that the contract's balance falls below 1000, `onPostRequestTimeout` reverts on `IERC20(_underlying).safeTransfer(refundee, 1000)` — permanently freezing Alice's original deposit with no rescue path.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
