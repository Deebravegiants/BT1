## Finding

### Title
Webhook shop domain and topic are trusted for tenant/handler dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from unauthenticated HTTP headers, but `to_signable_string` — the value that `Utils::HmacValidator` actually verifies — covers only the raw request body. This breaks the identity binding the docs claim: `HMAC(body) == HMAC(body)` is verified, while `shop header == authenticated shop` is never checked.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from attacker-controllable HTTP headers: [2](#0-1) 

`Registry.process` validates only this body-only HMAC, then immediately dispatches to the registered handler using the unverified `request.shop` and `request.topic`: [3](#0-2) 

The gem's own documentation instructs developers to treat `data.shop` (and `data.topic`) as the trusted tenant identifier for the webhook, and characterizes `Registry.process` as verifying "the request did indeed come from Shopify": [4](#0-3) [5](#0-4) 

Because the HMAC never covers the `shop-domain`/`topic` headers, any request with a **previously-seen valid `(raw_body, hmac)` pair** — e.g. one that was legitimately delivered to the app for the attacker's own shop — can be replayed to the same public webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header rewritten to a different, victim shop. `HmacValidator.validate` still succeeds because it only recomputes the HMAC over the untouched body bytes: [6](#0-5) 

The forged `shop` value is then passed straight through as the tenant identity in `WebhookMetadata`, matching the exact documented usage pattern (`shop_domain: data.shop`).

### Impact Explanation
This breaks the identity binding `authenticated_shop == shop_used_by_handler`, letting an unprivileged internet user who controls one tenant (their own Shopify store using the target app) forge webhook events attributed to an arbitrary victim shop domain. Any app that follows this gem's documented pattern of using `data.shop` as the tenant key for storing/dispatching webhook data will process cross-tenant, spoofed events — a cross-tenant access/data-injection vulnerability that the gem's own "verifies the request did indeed come from Shopify" documentation claims does not exist.

### Likelihood Explanation
Any user with a working store connected to the target app can trivially capture one legitimate `(raw_body, hmac)` webhook delivery (their own webhook logs/reverse proxy), then replay the identical body/HMAC with a modified `shop-domain` header to the app's public webhook endpoint. No `api_secret_key` or privileged access is required — only a normal, unprivileged merchant/tenant relationship with the app.

### Recommendation
Include the `shop-domain` and `topic` header values (not just the raw body) in the HMAC signable content, or otherwise cryptographically bind them (e.g., validate `shop` against the shop associated with `webhook_id`/subscription) before passing them to the handler as trusted identifiers.

### Proof of Concept
1. Attacker's own store `attacker.myshopify.com` triggers a webhook (e.g. `orders/create`); attacker's server logs the raw body `B` and the valid header `x-shopify-hmac-sha256: H` that Shopify sent.
2. Attacker POSTs to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation passes.
4. `request.shop` returns `"victim-shop.myshopify.com"`; the registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes/stores order data as if it belonged to the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
