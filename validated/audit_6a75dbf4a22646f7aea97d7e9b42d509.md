### Title
IntentGatewayV2 (Tron) `placeOrder` fails to refund unspent native ETH after fee-swap, permanently stranding funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` swaps leftover `msg.value` into the fee token via `swapETHForExactTokens` but never tracks or refunds the native ETH surplus that Uniswap's router sends back to the gateway contract itself. This mirrors the Tokemak `LMPVaultRouterBase` bug class: native value taken from the user is over-consumed/mis-accounted and gets stranded in the contract, where it can be swept by any unrelated caller.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the `order.fees` handling block performs:
```solidity
if (msgValue > 0) {
    address uniswapV2 = IDispatcher(hostAddr).uniswapV2Router();
    address WETH = IUniswapV2Router02(uniswapV2).WETH();
    address[] memory path = new address[](2);
    path[0] = WETH;
    path[1] = IDispatcher(hostAddr).feeToken();
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
        order.fees, path, address(this), block.timestamp
    );
} else {
    IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
}
_orders[commitment][TRANSACTION_FEES] = order.fees;
``` [1](#0-0) 

`swapETHForExactTokens` is called with the *entire* remaining `msgValue`, but that function only spends up to `order.fees` worth of ETH and refunds the excess ETH back to `msg.sender` of the call — which is the `IntentGatewayV2` contract itself (`{value: msgValue}` is sent by the contract, so the router's ETH refund lands back on the contract, not the original user). Unlike this, the return value `amounts[0]` (actual ETH spent) is never captured, so `msgValue` is never decremented, and the function proceeds directly to `emit OrderPlaced` with no refund step.

Compare this to the canonical (non-Tron) `IntentGatewayV2.sol`, which correctly captures the swap's actual consumption and refunds the remainder to the user:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
// Refund any unspent native tokens to the user.
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
``` [2](#0-1) 

The Tron file lacks both the `amounts[0]` subtraction and the trailing refund block entirely.

### Impact Explanation
Any user placing an order on the Tron chain who pays the solver fee in native token and includes any surplus (which is expected/documented behavior — see `docs/content/developers/evm/intent-gateway/placing-orders.mdx` describing `nativeValue` overpayment being refunded) will have that surplus permanently trapped in the `IntentGatewayV2` contract. Because the contract accepts native tokens via a `receive()` fallback and there is no accounting entry created for this leftover balance, the stuck ETH is not tied to any order or user and becomes free-floating value in the contract, effectively lost to the depositor and extractable by whoever can trigger any code path that sweeps the contract's raw balance (e.g., dust sweep/withdrawal logic operating on `address(this).balance`, or subsequent unrelated order flows that assume `msgValue` accounting is exact). This is a direct loss of user funds with no recovery path for the affected user, matching the "High" impact class of the original Tokemak finding — real value sent by the user for one purpose is not applied and becomes strandable/spendable by other parties.

### Likelihood Explanation
This is triggered on every ordinary `placeOrder` call on Tron that (a) has `order.fees > 0` and (b) pays fees with native ETH via nonzero `msgValue` where the caller doesn't send the *exact* amount required by the AMM swap (which is expected and normal since `order.fees` is a fee-token amount quoted off-chain, and users routinely overprovision native value to guarantee sufficient slippage coverage, as documented in the SDK guides). No malicious actor is needed — normal usage patterns guarantee non-zero excess in the overwhelming majority of transactions, making this a high-likelihood, unprivileged-user-reachable bug.

### Recommendation
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirror the logic already present in `evm/src/apps/IntentGatewayV2.sol`: capture the `amounts` array returned from `swapETHForExactTokens`, subtract `amounts[0]` from `msgValue`, and add a trailing refund of any remaining `msgValue` back to `msg.sender` before `emit OrderPlaced`.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with an order that has `order.fees = 10 (feeToken units)` and sends `msg.value = 1 ether` intending to cover both a native input leg and fee-swap slippage buffer.
2. After input-leg accounting, suppose `msgValue = 0.5 ether` remains for the fee swap.
3. `swapETHForExactTokens{value: 0.5 ether}(order.fees, path, address(this), deadline)` only consumes, say, `0.01 ether` worth of ETH to obtain exactly `order.fees` fee tokens; the router refunds the remaining `0.49 ether` back to `address(this)` (the gateway contract), since the gateway was the caller.
4. The Tron contract does not read the swap's `amounts[0]`, never updates `msgValue`, and never refunds it — the `0.49 ether` sits in the contract's balance with no corresponding entry in `_orders[commitment][...]`.
5. `emit OrderPlaced` fires as if all `msg.value` was properly used; the user has no way to reclaim the `0.49 ether`, and the contract's balance is inflated by unaccounted ETH extractable through any code path that later moves `address(this).balance` (e.g., dust-sweep logic or accounting bugs elsewhere), i.e., it is available for arbitrary third parties to eventually claim.
