## Finding: Predictable, unsigned session identifier allows cross-tenant session hijacking for non-embedded apps

### Title
Session hijacking via unsigned, deterministic session-ID cookie - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps, the gem authenticates a request by trusting the raw value of a browser cookie as the session lookup key, without any cryptographic binding between that value and a completed OAuth flow. Because offline (and online) session IDs are deterministic strings derived entirely from public information (the shop's domain, and for online sessions, the numeric Shopify user id), any unauthenticated party can construct a valid-looking session id and, if the host stores the cookie in the plain form the library's own documentation demonstrates, hijack another merchant's session.

### Finding Description
`ShopifyAPI::Utils::SessionUtils.cookie_session_id` returns the cookie value verbatim as the session id, with no signature or validation check on it: [1](#0-0) 

That value is used as the authoritative session id via `current_session_id`, which host apps use directly to retrieve a stored `Session` (and its access token) for making authenticated Shopify API calls: [2](#0-1) 

The session id itself is not a secret — it is deterministically derived from public data. Offline sessions get id `"offline_#{shop}"`, and this exact same construction is used both when the ID is generated and set into the cookie, and when the library computes the same id independently: [3](#0-2) [4](#0-3) 

During `validate_auth_callback`, for non-embedded apps the library sets the session cookie's `value` directly to `session.id` — i.e. `"offline_<shop>.myshopify.com"` or `"<shop>_<user_id>"` — with no HMAC or other integrity protection applied by the gem: [5](#0-4) 

The gem's own documented integration pattern stores this cookie value in a plain (unsigned/unencrypted) Rack/Rails cookie jar (`cookies[name] = { value: ..., secure: true, http_only: true }`), not `cookies.signed[]` or `cookies.encrypted[]`: [6](#0-5) [7](#0-6) 

The `SessionCookie` struct itself carries no signature/MAC field — only a plain `value`, `name`, and `expires`: [8](#0-7) 

The identity binding that is broken is:
`session_id trusted by SessionUtils.current_session_id == session_id issued to this specific authenticated browser after a completed OAuth flow`

but what is actually checked is only:
`session_id trusted by SessionUtils.current_session_id == bytes present in an arbitrary incoming cookie header`

Since the "bytes" (`"offline_" + shop`) require no secret to construct — only knowledge of the target's public `.myshopify.com` domain — this binding is not actually enforced. This is a direct analog of the report's core bug class: a value (the session cookie) is *acted on* as if it were verified/derived from a trusted secret-bound process, when in fact it is unauthenticated attacker-controlled bytes.

### Impact Explanation
An unprivileged internet user who knows (or guesses) a victim shop's `.myshopify.com` domain — public information, often visible in storefront URLs — can set a forged `shopify_app_session` cookie value of `offline_<victim-shop>.myshopify.com` when hitting the app's endpoints. If the host app follows the library's documented cookie-storage pattern and session-retrieval flow (`SessionRepository.retrieve_session(session_id)` keyed by this id, as shown in the docs), the attacker's request will resolve to the victim's stored offline `Session`, including its access token, and the host app will make Shopify Admin API calls against the victim shop on the attacker's behalf. This is cross-tenant access to another merchant's authenticated session and access token — Critical impact per the specified severity list.

### Likelihood Explanation
Likelihood is high for any non-embedded app that follows the gem's own documented integration (plain, unsigned cookie storage) — which is exactly what is shown in `docs/usage/oauth.md`. No secret material, brute forcing, or timing side-channel is required; the attacker only needs the target shop's domain name, which is typically public.

### Recommendation
- Do not use the raw session id as bearer material in a client-writable cookie. Either (a) require the host app to store the session id only in a signed/encrypted cookie jar and document this as mandatory rather than optional, or (b) have the library issue an unguessable, per-session opaque token (e.g., a `SecureRandom` value bound server-side to the actual `Session`, similar to the OAuth `state` nonce) instead of exposing the deterministic `offline_<shop>` / `<shop>_<user_id>` id as the cookie value.
- At minimum, update `docs/usage/oauth.md` to mandate `cookies.signed[]=`/`cookies.encrypted[]=` and clarify that `SessionUtils.cookie_session_id` provides no integrity guarantee on its own.

### Proof of Concept
1. Attacker identifies victim's shop domain, e.g. `victim-shop.myshopify.com` (public/guessable).
2. Attacker computes the deterministic offline session id: `offline_victim-shop.myshopify.com` (per `SessionUtils.offline_session_id` / `Session.from`).
3. Attacker sends a request to the host app's authenticated route with cookie `shopify_app_session=offline_victim-shop.myshopify.com`.
4. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns the attacker-supplied value unchanged via `cookie_session_id`.
5. Host app looks up and loads the victim's real `Session` (with its access token) using this id and proceeds to serve the attacker as if they were the victim shop, including making authenticated Shopify Admin API calls with the victim's access token.
