## Analysis

The external report's underlying bug class is "trusting attacker-influenced data that was never covered by the mechanism meant to authenticate it." The strongest analog in this gem is in the webhook verification path.

`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC to the raw body only: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, none of which are part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC only against `to_signable_string` (the body), then hands the unauthenticated header-derived `shop`/`topic`/`webhook_id` straight to the app's handler as trusted tenant-identifying metadata: [3](#0-2) 

The `HmacValidator.validate` call only proves the body was signed by someone holding `api_secret_key`; it proves nothing about which shop the body came from: [4](#0-3) 

### Title
Webhook shop attribution is not bound to the HMAC signature, enabling cross-tenant event spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request` verifies only the raw request body against the HMAC signature. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that the library hands to the app's webhook handler as authenticated tenant/event context are taken from HTTP headers that are excluded from the signed content, so they carry no cryptographic binding to the shop that actually triggered the webhook.

### Finding Description
The equality the library implicitly claims to the host application is:
`shop asserted in "shopify-shop-domain" header == shop that produced the HMAC-signed body`

But `to_signable_string` returns only `@raw_body` [1](#0-0)  while `shop`, `topic`, and `webhook_id` are read from separate headers that `HmacValidator.validate` never inspects [2](#0-1) . Because any app that has installed the merchant's app (any unprivileged Shopify merchant, including an attacker's own test store) receives webhooks signed with the same app-wide `api_secret_key`, an attacker who controls one shop can capture a legitimate, validly-signed webhook delivery for a topic whose body is shop-agnostic (or attacker-shop-only data, e.g. `{}` for `app/uninstalled`-style payloads) and resend it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop. The signature still validates because the signature never covered the shop header, and `Registry.process` forwards the forged `shop` straight into `WebhookMetadata` for the handler [5](#0-4) .

### Impact Explanation
This meets the "Critical - cross-tenant access" bar: the app is misled into acting on data or triggering shop-scoped side effects (e.g. deauthorizing/resetting state, redaction workflows, cache invalidation, session revocation) attributed to a shop the attacker does not own, purely by replaying a signature-valid payload under a spoofed tenant identity.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled shop to legitimately receive a correctly-HMAC'd webhook, and (2) resending that exact body to the app's public webhook endpoint with a different `shopify-shop-domain` header. No secrets, tokens, or privileged access are required beyond normal merchant-level app installation, which is exactly the "unprivileged internet user" bar this scan targets.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable content used for HMAC verification, or otherwise cryptographically bind the asserted `shop-domain` header to the verified payload before it is trusted as tenant context — e.g., reject/flag when the `shop-domain` claimed in the header cannot be independently corroborated (webhook subscription lookup by id, or per-shop signing) rather than passing it through unauthenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify delivers a webhook (e.g. topic with a constant/generic body such as `{}`) to the app's endpoint, signed with `hmac = HMAC-SHA256(api_secret_key, raw_body)` — same `api_secret_key` is used for every shop that installs the app.
3. Attacker captures the `raw_body` and the valid `shopify-hmac-sha256` header value.
4. Attacker replays the identical body/HMAC to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` and any desired `shopify-topic`/`shopify-webhook-id`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC [6](#0-5)  — validation succeeds — and the handler receives `WebhookMetadata` claiming the event is from `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
