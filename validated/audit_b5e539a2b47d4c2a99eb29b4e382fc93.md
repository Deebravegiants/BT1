### Title
Excess native ETH sent to `EvmHost.dispatch()` / `fundRequest()` is permanently trapped because the Uniswap V2 router refunds dust to the Host, not to the user - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept `msg.value` and forward it to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` [1](#0-0)  without capturing or refunding any unspent ETH back to the original caller.

### Finding Description
`swapETHForExactTokens` is an exact-output swap: it only spends the amount of ETH needed to buy exactly `fee` units of the fee token, and the Uniswap V2 router refunds the unused ETH dust to `msg.sender` of the *swap call* — which is `EvmHost` itself, since `EvmHost` is the direct caller of the router. This refund behavior ("refund returns to caller") is explicitly documented and asserted in the project's own wrapper test: [2](#0-1) .

In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, the code does the swap but never reads the router's returned `amounts` and never sends any leftover ETH back to `_msgSender()`: [1](#0-0) [3](#0-2) [4](#0-3) 

This is analogous to the reported `createPool()` bug class: a caller supplies `msg.value` sized to cover a required fee (here, `post.fee`/`get.fee`/`amount`), but any surplus over the amount actually needed is not returned to the sender — it is silently absorbed, except here it's worse: the surplus doesn't even remain "in the contract balance accessible via later accounting" for the user, it becomes indistinguishable native ETH sitting in `EvmHost`'s balance with no code path that returns it to the original payer. Contrast this with `IntentGatewayV2.placeOrder()`, in the same codebase, which correctly captures the swap's `amounts[0]` and explicitly refunds the unspent `msgValue` to `msg.sender`: [5](#0-4) . `EvmHost` omits this refund logic entirely.

### Impact Explanation
Any user who overestimates the ETH needed for `dispatch()`/`fundRequest()` (e.g., because Uniswap pool price shifted since they estimated off-chain via `quote()`, or they intentionally pad for slippage as the docs recommend) loses the entire surplus permanently. There is no user-facing withdraw/refund mechanism for this stuck ETH in `EvmHost`; the funds are folded into the Host's contract balance with no accounting tying them to the depositor, making this a permanent, protocol-wide loss of user funds. Given that `dispatch()` is the core, most-frequently-used entry point for every cross-chain POST/GET, this affects a wide surface of routine transactions, not an edge case.

### Likelihood Explanation
This will trigger on essentially any real-world usage of native-token payment for `dispatch()`/`fundRequest()`, since callers must send `msg.value` that is at least sufficient and Uniswap V2 exact-output pricing fluctuates block-to-block; the documentation itself instructs users to pad `msg.value` for slippage, guaranteeing dust remains after every native-token dispatch: [6](#0-5) .

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, compute `msg.value - amounts[0]`, and refund that surplus back to `_msgSender()` (or `post.payer`/the appropriate payer), mirroring the pattern already implemented in `IntentGatewayV2.placeOrder()` [7](#0-6) .

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost)` sending `msg.value = 2 ETH` with `post.fee = 100 feeToken`, expecting a small dust refund per Uniswap slippage padding guidance.
2. `EvmHost` calls `swapETHForExactTokens{value: 2 ether}(100e18, path, address(this), block.timestamp)`; suppose only `0.5 ETH` is actually needed to buy `100` fee tokens.
3. Uniswap V2 router refunds `1.5 ETH` to `msg.sender` of the swap call, which is `EvmHost` (not the original transaction sender).
4. `dispatch()` returns without ever forwarding that `1.5 ETH` back to the user; `EvmHost`'s native balance permanently increases by `1.5 ETH` with no tracking of which user is owed it and no function to reclaim it for that user.

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
}
