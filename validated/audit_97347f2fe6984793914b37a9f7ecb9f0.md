### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field entirely from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while `ShopifyAPI::Utils::HmacValidator.validate` only verifies the HMAC over the raw request body. Because the body and the shop identity are signed/verified independently of each other, an attacker who is able to obtain any one genuine, validly-signed webhook body (e.g. by installing the app on their own store and capturing a webhook Shopify sends them) can replay that exact body to the app's webhook endpoint while substituting an arbitrary victim shop's domain in the header. The HMAC still validates (it only covers the body), and the app's handler is invoked believing the event belongs to the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from a request header with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC (over the body) and then forwards `request.shop` — the unauthenticated header value — straight to the app's handler as the tenant identity: [3](#0-2) 

The identity binding that should hold is:
`hmac_valid(raw_body) == true` should imply `shop_header == shop_that_the_signed_body_actually_belongs_to`.

In reality, `HmacValidator.validate` proves only that *some* request body with a valid signature was received; it says nothing about which shop the header claims it came from. `shop` (the field acted on downstream — used to select tenant data/session, per the library's own docs: "`shop`, `String` - The shop domain of the webhook") is never included in `to_signable_string`, so it is not covered by the signature at all.

### Impact Explanation
Any user who can install the app on a store they control (an ordinary, unprivileged action available to any merchant/user) can capture a legitimate webhook (raw body + valid `hmac-sha256` header) that Shopify sends to the app for their own shop. They can then replay that identical body/HMAC pair to the app's webhook endpoint with the `shopify-shop-domain` header changed to any other shop that also has the app installed. `HmacValidator.validate` will still return `true` because it only checks the body against the secret, and `Registry.process` will call the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. Depending on how the host application uses `data.shop` (e.g., to look up the victim's session/access token and act on their store, or to write attacker-controlled webhook data into the victim's tenant records), this results in cross-tenant data confusion/injection — the host app processes attacker-supplied event data under a different merchant's identity.

### Likelihood Explanation
Exploitation requires only that the attacker can install the target app on a shop they control (a normal unprivileged flow for any public app) and can send an arbitrary HTTP POST to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed. All shops share the same app-level `api_secret_key`, so the HMAC check does not differentiate shops, making this a low-effort, no-secret attack once the attacker has one captured legitimate payload.

### Recommendation
Bind the shop identity to the signed payload rather than trusting the header on its own:
- Include the `shop` (and ideally `topic`/`webhook_id`) header value inside the HMAC-signable string, or
- Require the calling application to independently verify that `request.shop` matches a shop for which the app has legitimate session state/expects webhooks, before trusting `WebhookMetadata#shop`, and document this requirement prominently, or
- Have `Webhooks::Registry.process` cross-check `request.shop` against known/registered shops for the topic if such a mapping is available.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`. Shopify sends a legitimate webhook, e.g. body `{"id":1}` with header `shopify-shop-domain: attacker-shop.myshopify.com` and a valid `shopify-hmac-sha256` computed over that body with the app's `api_secret_key`.
2. Attacker captures this body + HMAC value.
3. Attacker sends a new POST to the app's webhook endpoint with the same body and same `shopify-hmac-sha256`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present); `HmacValidator.validate` computes the signature over `to_signable_string` (`@raw_body` only) and it matches, so validation succeeds: [4](#0-3) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: request.shop ...)`, i.e. `shop: "victim-shop.myshopify.com"`, even though the payload never actually originated from or was validated against that shop: [5](#0-4)
