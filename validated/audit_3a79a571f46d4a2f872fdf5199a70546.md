## Title
Webhook shop identity spoofing due to HMAC covering only the raw body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop-domain` HTTP header (never covered by that HMAC) to decide which merchant/tenant the payload belongs to. An attacker who can obtain one valid `(body, hmac)` pair for the app — e.g., by installing the app on their own store and letting Shopify deliver a legitimate webhook to them — can replay that exact body/hmac while substituting an arbitrary `shopify-shop-domain` header. The signature still validates (it never covered the shop header), and the handler is invoked believing the event came from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is completely independent of the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body) and compares it to the supplied HMAC — it never folds in `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` performs exactly that check and then dispatches the handler using the *unauthenticated* `request.shop` value as the tenant identity for the event: [4](#0-3) 

The identity binding that should hold is:

`shop that produced/signed the payload == shop attributed to the event by the handler`

Because the HMAC only signs the body, this equality is never enforced — an attacker can take a `(raw_body, hmac)` pair that is valid for the app's secret (obtained from a webhook legitimately delivered to their own shop) and re-POST it to the app's public webhook endpoint with the `shop-domain` header rewritten to any victim shop domain. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `WebhookMetadata.shop` is populated from the forged header.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide via `Utils::HmacValidator.validate(request)` — apps rely on this check as proof that a webhook both came from Shopify and belongs to the named shop. Any app that trusts `WebhookMetadata#shop` for shop-scoped logic (e.g., disabling access, deleting shop data on `app/uninstalled`, updating billing/subscription state, writing merchant-scoped records) can be made to apply attacker-chosen data to an arbitrary victim shop, i.e. cross-tenant impact, without needing the app's `client_secret`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
An attacker only needs to be able to install the target app on a shop they control (a normal, unprivileged action for any Shopify developer/merchant) and capture one legitimately delivered webhook (body + valid HMAC) for that shop. They can then replay it to the app's public webhook endpoint with a modified `shop-domain` header. No secret material, session, or victim-owned credential is required — only network access to the app's public webhook URL, which is by design internet-reachable.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is cryptographically verified, or otherwise establish the shop identity from data that is itself covered by the signature/trusted channel rather than from an unauthenticated header:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string`/the HMAC computation (this would require coordinating with Shopify's delivery format), or
- Require callers to cross-check `request.shop` against a shop already known to be installed/entitled for this specific `webhook_id`/payload before invoking the handler, or at minimum document explicitly that `HmacValidator.validate` does not authenticate the `shop`/`topic` headers and that host applications must independently verify shop identity (e.g., against their session store) before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`). Shopify delivers:
   - Body: `raw_body_A`
   - Header `shopify-hmac-sha256`: `HMAC(api_secret_key, raw_body_A)` — valid, since `HmacValidator.validate` only checks body bytes: `lib/shopify_api/utils/hmac_validator.rb` lines 12-31.
   - Header `shopify-shop-domain`: `attacker-shop.myshopify.com`
2. Attacker resends the exact same `raw_body_A` and `shopify-hmac-sha256` value to the app's public webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` because only `raw_body_A` was checked (`lib/shopify_api/webhooks/registry.rb` line 190; `lib/shopify_api/webhooks/request.rb` lines 20-38).
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: attacker-controlled parsed body ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), causing the host app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
