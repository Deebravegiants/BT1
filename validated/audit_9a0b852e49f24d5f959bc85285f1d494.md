### Title
PoA bridge status misreport for duplicate same-asset withdrawals in a batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`createWithdrawalIdentifiers` assigns per-route indexes (0, 1, ...) to disambiguate multiple withdrawals of the same bridge in one batch, but `PoaBridge.describeWithdrawal` never consults `WithdrawalIdentifier.index` — it matches solely by `assetId` via `findMatchingWithdrawal`. When a batch contains two PoA legs with the same `assetId` but different `destinationAddress`/`amount`, both legs' `describeWithdrawal` calls resolve to the identical matched withdrawal record, so `watchWithdrawal(wid0)` and `watchWithdrawal(wid1)` report the same status/txHash regardless of which underlying withdrawal actually completed.

### Finding Description
Broken equality: `describeWithdrawal({..., index:0})` should return the status of leg 0 exactly, and `describeWithdrawal({..., index:1})` should return the status of leg 1 exactly — these should differ whenever the two withdrawals differ in destination/amount/settlement. Instead both calls compute the same `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` result [1](#0-0) , which filters purely by `nep141:${w.data.near_token_id} === assetId` [2](#0-1)  — `index` is not part of the match key at all, and the code comment explicitly documents this: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported" [3](#0-2) .

Upstream, `createWithdrawalIdentifiers` computes indexes purely as a per-route counter with no assetId-awareness and no validation preventing duplicate `(route, assetId)` pairs in the same batch [4](#0-3) . `findBridgeForWithdrawal` only checks `bridge.supports(params)`, which for `PoaBridge` only validates the `assetId`/`routeConfig`, not uniqueness against other batch items [5](#0-4) . So nothing in the reachable path prevents or detects the duplicate-assetId scenario before it reaches `describeWithdrawal`.

Exploit flow: an integrator-facing batch withdrawal request containing `[PoA:BTC→A, PoA:BTC→B, HOT:ETH→C]` is submitted (BTC assetId/destination strings are attacker/counterparty-supplied inputs forwarded by the integrator). `createWithdrawalIdentifiers` assigns index 0 to the A leg and index 1 to the B leg, both routed to `PoaBridge`. `watchWithdrawal` polls each identifier independently and calls `describeWithdrawal`; both calls hit the same POA `getWithdrawalStatus` HTTP response and both run `findMatchingWithdrawal` against the same `assetId`, returning the same entry. If only the withdrawal to A has completed on-chain, `describeWithdrawal(wid1)` for B still returns that same "completed" status/`txHash`, because `findMatchingWithdrawal` cannot tell A's withdrawal from B's.

None of the existing guards catch this: `validateAddress`/`compareAddresses`/`validateWithdrawal` validate destination format and min-amount but do not detect batch-level duplicate assetId; `supports()` only classifies routing, not batch uniqueness; there is no `matchesRequest`/index check anywhere in the PoA describe path.

### Impact Explanation
This is a status/hash misreport: the SDK reports a "completed" withdrawal with a specific `txHash` for a leg (B) that was never actually paid, while the same status is (correctly) reported for the leg (A) that was paid. An integrator relying on `watchWithdrawal`/batch-completion promises per leg to credit downstream ledgers or trigger fulfillment would credit/confirm B's leg based on A's completion, causing either a double-credit (both A and B's off-chain obligations marked settled) or masked non-delivery (B's user never receives funds but the integrator believes it did). This matches the "status or hash misreport making an integrator credit or refund twice" High-severity category. It is repeatable for every batch containing ≥2 same-assetId PoA legs.

### Likelihood Explanation
Preconditions: the integrator/SDK consumer must submit (or be induced to submit, via attacker/counterparty-controlled `assetId`/`destinationAddress` strings forwarded into a batch) a multi-leg withdrawal where two or more legs share the same PoA `assetId`. Nothing in `supports()`, `createWithdrawalIdentifiers`, or `describeWithdrawal` blocks this combination — it is a structurally reachable state, not a hypothetical one, and is explicitly acknowledged as unsupported/broken by the code's own comment. Attacker cost is minimal since only the `assetId`/`destinationAddress` fields of a batch entry need to coincide; no privileged access is required. This is repeatable on every such batch.

### Recommendation
Extend the POA bridge's withdrawal status API usage (or the identifier scheme) to disambiguate same-asset withdrawals — e.g., match on `destinationAddress` + `amount` in addition to `assetId`, or reject/flag batches containing duplicate `(route, assetId)` pairs in `createWithdrawalIdentifiers`/`supports()` until the POA API supports index-based or positional matching, per the remediation already sketched in the code comment (sort withdrawals and params by amount to preserve relative ordering).

```ts
// poa-bridge.test.ts (illustrative)
it("misreports leg B as completed when only leg A settled (duplicate assetId)", async () => {
  const bridge = new PoaBridge({ envConfig, xrplRpcUrls: [] });

  const tx = { hash: "shared-tx", accountId: "user.near" };
  const widA = bridge.createWithdrawalIdentifier({
    withdrawalParams: { assetId: "nep141:btc.omft.near", amount: 100n, destinationAddress: "addrA", feeInclusive: false },
    index: 0, tx,
  });
  const widB = bridge.createWithdrawalIdentifier({
    withdrawalParams: { assetId: "nep141:btc.omft.near", amount: 200n, destinationAddress: "addrB", feeInclusive: false },
    index: 1, tx,
  });

  // Mock HTTP: only A's withdrawal is completed; B never appears/settled
  vi.spyOn(poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({
    withdrawals: [
      { status: "COMPLETED", data: { near_token_id: "btc.omft.near", transfer_tx_hash: "0xA_TX" } },
    ],
  });

  const statusA = await bridge.describeWithdrawal(widA);
  const statusB = await bridge.describeWithdrawal(widB);

  // Broken equality: both resolve identically despite B never being paid
  expect(statusA).toEqual({ status: "completed", txHash: "0xA_TX" });
  expect(statusB).toEqual({ status: "completed", txHash: "0xA_TX" }); // should differ / be pending, but isn't
});
```

```typescript
	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
```

```typescript
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
