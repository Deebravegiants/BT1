### Title
POA Bridge withdrawal status misreport causes duplicate "completed" confirmation for batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain destination status for a withdrawal by matching entries returned from the POA bridge status API using `findMatchingWithdrawal()`, which selects the record purely by `assetId` (via `near_token_id`) and ignores the withdrawal's `index`/position [1](#0-0) . When a caller batches two or more withdrawals of the **same token** in a single NEAR transaction (supported by the SDK's `processWithdrawal`/`waitForWithdrawalCompletion` batch API), each withdrawal's independent status poll resolves to the **same first-matching** API record, so a single completed withdrawal is reported as "completed" for every same-asset withdrawal in the batch, regardless of whether the other withdrawal(s) actually finalized.

### Finding Description
`findMatchingWithdrawal()` is explicitly documented as matching only by `assetId` and not disambiguating multiple withdrawals of the same token: [2](#0-1) 

The same limitation (and same first-match semantics) exists in the shared implementation used by `waitForWithdrawalCompletion`: [3](#0-2) 

The SDK's batching path in `IntentsSDK.createWithdrawalCompletionPromises()` fans out one independent `watchWithdrawal`/`describeWithdrawal` poll per `withdrawalParams` index, with no cross-index correlation of which underlying API record was already consumed by a sibling withdrawal: [4](#0-3) 

The equality broken: the status/hash reported for withdrawal index N should reflect the *specific* on-chain outcome of the withdrawal transfer created for index N. Instead, when `assetId` is shared across indices, `Array.prototype.find()` always returns the first entry for every caller, so index N's reported status is the outcome of some other withdrawal's transfer, not its own.

### Impact Explanation
If a batch contains two withdrawals of the same NEP-141 asset (e.g. `["nep141:btc.omft.near", "nep141:btc.omft.near"]` in one signed intent transaction, or two separate `signAndSendWithdrawalIntent` calls that land in the same NEAR tx), and the POA bridge has completed only the first transfer while the second is still pending or fails, both `watchWithdrawal` promises resolve `"completed"` with the **same** destination `txHash`. An integrator relying on `processWithdrawal`/`waitForWithdrawalCompletion` to gate crediting a user or marking an off-chain ledger entry as settled would credit/mark **both** withdrawals as completed based on a single actual on-chain transfer — a status misreport that can cause the integrator to double-credit a user or double-settle an internal balance, matching the "status or hash misreport making an integrator credit twice" impact class.

### Likelihood Explanation
This requires no malicious relayer, RPC, or bridge operator behavior — it is triggered purely by legitimate usage of the SDK's documented batch withdrawal API (`processWithdrawal`/`signAndSendWithdrawalIntent`/`waitForWithdrawalCompletion` with an array of `withdrawalParams`) when two withdrawals of the same asset happen to be included in one batch. Nothing in `supports()`, `validateWithdrawal()`, or `createWithdrawalIntents()` in `PoaBridge` rejects or warns about duplicate-asset batches, so the unsafe path is silently reachable rather than guarded.

### Recommendation
Disambiguate `findMatchingWithdrawal()` beyond `assetId`: either (a) reject/throw during `validateWithdrawal`/`createWithdrawalIntents` when a batch contains more than one withdrawal for the same `assetId` routed through the POA bridge, or (b) implement the ordering-based matching described in the existing code comment (sort API results and withdrawal params by amount) and only mark an entry as consumed once matched to a given index, preventing two different local withdrawal indices from resolving to the same remote record.

### Proof of Concept
1. Caller invokes `sdk.processWithdrawal({ withdrawalParams: [wdA, wdB] })` where `wdA.assetId === wdB.assetId === "nep141:btc.omft.near"` (two BTC withdrawals batched in one signed intent transaction).
2. Both withdrawals settle on NEAR in the same `intentTx`; the POA bridge indexer eventually reports two entries in `getWithdrawalStatus`, one `COMPLETED` (say `wdA`'s real transfer) and one still `PENDING` (`wdB`'s real transfer).
3. `createWithdrawalCompletionPromises` spawns one `watchWithdrawal` per index; both call `PoaBridge.describeWithdrawal()`, which calls `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")` — both invocations return the **same first array entry** (the `COMPLETED` one) per `Array.prototype.find` semantics [5](#0-4) .
4. Both promises resolve `{ status: "completed", txHash: <wdA's real tx hash> }`, even though `wdB`'s actual transfer has not landed on-chain, leading the integrator to treat both withdrawals as finalized.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
	}
