### Title
`findMatchingWithdrawal()` matches PoA withdrawal status by `assetId` alone, causing cross-index status/txHash misreporting for same-token multi-withdrawal batches - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain withdrawal status by calling `findMatchingWithdrawal()`, which selects the first entry in the POA API response whose `near_token_id` matches the withdrawal's `assetId`, ignoring `index` and `destinationAddress` entirely. When a single signed NEAR transaction contains two `ft_withdraw` intents for the same `assetId` to two different destination addresses, both `describeWithdrawal(index=0)` and `describeWithdrawal(index=1)` calls resolve to the identical withdrawal record, so one destination's status/txHash gets reported for the other.

### Finding Description
The broken equality is: `(status, txHash)` reported for withdrawal at `index=i` should equal the actual on-chain outcome of the withdrawal at `index=i` specifically (bound to that index's `destinationAddress`/`amount`). Instead, `findMatchingWithdrawal()` at [1](#0-0)  returns `withdrawals.find((w) => \`nep141:${w.data.near_token_id}\` === assetId)` — the very first array element matching `assetId`, with no comparison against `index`, `amount`, or `destinationAddress`.

The code's own comment acknowledges this limitation explicitly: [2](#0-1)  "multiple withdrawals of the same token in a single transaction are not supported."

`describeWithdrawal()` calls this matcher directly and returns its `status`/`txHash` unconditionally: [3](#0-2) .

Nothing upstream prevents constructing such a batch. `createWithdrawalIdentifiers()` in `withdrawal-watcher.ts` assigns per-bridge sequential indexes without any uniqueness check on `assetId` + `destinationAddress`: [4](#0-3) . `supports()` and `validateWithdrawal()` on `PoaBridge` validate each withdrawal in isolation (asset support, destination address format, min amount) and have no cross-item duplicate-asset check: [5](#0-4) . An unprivileged user (or an integrator following documented multi-withdrawal batch flows) can freely construct a signed intents transaction with two `ft_withdraw` intents for the same NEP-141 token to different destinations — nothing in the SDK's public API rejects this.

`watchWithdrawal()` (used by `createWithdrawalCompletionPromises`) simply forwards each `WithdrawalIdentifier` to `describeWithdrawal()` and reports back `{hash}`/failure per promise index, with no cross-check that the returned record actually pertains to that index's destination: [6](#0-5) .

### Impact Explanation
An integrator polling withdrawal completion for two same-asset, different-destination withdrawals in one batch will receive identical `{status, txHash}` for both indexes (whichever the POA API happens to return first). This can cause the integrator to mark both withdrawals "completed" with the same txHash while only one destination actually received funds, or to treat a still-pending/failed withdrawal as completed. This is a status/hash misreport that can lead an integrator to credit or refund the same withdrawal twice, or credit the wrong destination as completed while the other silently fails to be tracked — matching the "High" impact category (status/hash misreport causing double credit/refund), reachable purely by an ordinary user submitting a batch withdrawal with duplicate-asset different-destination intents.

### Likelihood Explanation
Preconditions: two or more `ft_withdraw` intents for the identical `nep141:` `assetId` targeting different `destinationAddress` values, signed and submitted in a single NEAR transaction via `PoaBridge`. This requires no special privilege — any SDK user constructing a batch withdrawal can trigger it, and no validation in `supports()`/`validateWithdrawal()`/`createWithdrawalIdentifiers()` blocks such batches. The bug is deterministic and repeatable on every poll while the POA API returns multiple entries for that token.

### Recommendation
Extend `findMatchingWithdrawal()` (or the POA API request/response) to disambiguate by `destinationAddress` and/or `amount` in addition to `assetId`, or reject/serialize same-asset withdrawals within a batch at `createWithdrawalIdentifiers()`/`validateWithdrawal()` time until the POA API supports index-based disambiguation, as the existing comment anticipates.

### Proof of Concept
Vitest plan (mock only `poaBridge.httpClient.getWithdrawalStatus`):
1. Mock `poaBridge.httpClient.getWithdrawalStatus` to resolve with a single withdrawal record: `{ withdrawals: [{ data: { near_token_id: "X", transfer_tx_hash: "0xabc" }, status: "COMPLETED" }] }`.
2. Construct two `WithdrawalIdentifier`s, both with `withdrawalParams.assetId = "nep141:X"` but `index: 0` / `destinationAddress: "addrA"` and `index: 1` / `destinationAddress: "addrB"` respectively, sharing the same `tx.hash`.
3. Call `poaBridge.describeWithdrawal(identifier0)` and `poaBridge.describeWithdrawal(identifier1)`.
4. Assert both calls resolve to `{ status: "completed", txHash: "0xabc" }` — i.e., `result0 === result1` in content — despite `identifier0.withdrawalParams.destinationAddress !== identifier1.withdrawalParams.destinationAddress`, proving the per-index status equality is broken.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
