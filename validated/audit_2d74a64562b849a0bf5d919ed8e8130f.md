## Title
Debug/pprof endpoints reachable by any authenticated role (no RBAC check) - ([File: core/web/router.go])

## Summary
`metricRoutes` registers the full set of `net/http/pprof` handlers under `/v2/debug/pprof/*` with no role-based authorization wrapper, unlike every other sensitive endpoint in the same route group. Any authenticated user — including the lowest-privilege `view` role — can therefore reach CPU/heap/goroutine/trace profiling endpoints on a running Chainlink node.

## Finding Description
`metricRoutes` mounts `pprof.Index`, `pprof.Cmdline`, `pprof.Profile`, `pprof.Symbol`, `pprof.Trace`, and the `allocs`/`block`/`goroutine`/`heap`/`mutex`/`threadcreate` handlers directly, with no `auth.Requires*Role` wrapper: [1](#0-0) 

It is invoked as `metricRoutes(authv2)` inside `v2Routes`, where `authv2` is protected only by `auth.Authenticate(..., AuthenticateByToken, AuthenticateBySession)` — verifying the caller is authenticated but performing no role check: [2](#0-1) [3](#0-2) 

This is inconsistent with the rest of the `authv2` group, where nearly every other handler is explicitly wrapped with `auth.RequiresAdminRole` or `auth.RequiresEditRole`, e.g. user management and vault/forwarder operations immediately adjacent to the `metricRoutes` call: [4](#0-3) [5](#0-4) 

Chainlink's role model defines four strictly increasing privilege levels (`view` < `run` < `edit` < `admin`), with `view` intended as read-only/lowest-privilege, confirming the severity gap this bug creates. The project's own RBAC regression test (`routesRolesMap`-style table in `core/web/auth/auth_test.go`) enumerates nearly all `/v2/*` routes and expected role requirements but contains no entries for `/v2/debug/pprof/*`, confirming this route family is excluded from role-enforcement testing.

## Impact Explanation
This maps to an in-scope "node API authentication/role bypass" impact category. A low-privilege authenticated user (e.g., `view` role, typically issued to read-only/monitoring integrations) can:
- Read runtime internals via `/v2/debug/pprof/heap`, `/goroutine`, `/allocs`, potentially exposing sensitive in-memory data (stack traces, buffers, internal state).
- Trigger attacker-controlled-duration CPU profiling (`/v2/debug/pprof/profile?seconds=N`) or tracing (`/v2/debug/pprof/trace`), consuming node CPU and degrading availability on a node whose responsiveness affects OCR round participation and on-chain transaction submission timing.

This is a genuine authorization-boundary defect rooted in the node's own routing code, not a misconfiguration, dependency issue, or requiring host/operator access.

## Likelihood Explanation
Exploitation requires only a single valid low-privilege credential (session cookie or API token with `view` role) and one HTTP GET request — no race conditions, no additional bypass, and no special setup. `view`-role credentials are commonly distributed to monitoring/read-only integrations in multi-user deployments, making this readily reachable in realistic operational scenarios.

## Recommendation
Wrap `metricRoutes(authv2)` with an explicit role check consistent with the rest of the `authv2` group (e.g., `auth.RequiresAdminRole` on each pprof sub-route), and add `/v2/debug/pprof/*` entries to the RBAC regression test table in `core/web/auth/auth_test.go` so future changes cannot silently reintroduce this gap.

## Proof of Concept
1. Create/obtain a Chainlink node user with `view` role and valid session cookie or API token (`X-API-KEY`/`X-API-SECRET`).
2. Send `GET /v2/debug/pprof/heap?debug=1` with those credentials.
3. Observe HTTP 200 with a full heap dump returned — no `403 Forbidden`, unlike calling an admin-only route (e.g. `GET /v2/users`) with the same credentials.
4. Repeat with `GET /v2/debug/pprof/profile?seconds=30` to confirm the same low-privilege user can force 30 seconds of CPU profiling on the node.
5. As a regression test, add a case to the role-matrix table in `core/web/auth/auth_test.go` for `GET /v2/debug/pprof/heap` (and siblings) asserting only `admin` should succeed, and observe it currently fails (i.e., `view`/`edit`/`run` all succeed).
