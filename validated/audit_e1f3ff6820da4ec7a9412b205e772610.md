### Title
Unsigned relayer identity accepted without signature verification when `signer` bytes ≤ 32 - (File: `modules/pallets/ismp/src/host.rs`)

### Summary
`pallet-ismp`'s `extract_signer` function, used to attribute delivered ISMP messages to a relayer for fee/reward accounting, only cryptographically verifies the `signer` field when it is longer than 32 bytes. When the caller-supplied `signer` bytes are 32 bytes or fewer, the function returns them verbatim as the attributed signer with **no signature check at all**: [1](#0-0) 

```rust
fn extract_signer(signer: &[u8]) -> Result<Vec<u8>, Error> {
	if signer.len() > 32 {
		Signature::decode(&mut signer.as_ref())
			.map(|sig| sig.signer())
			.map_err(|_| Error::SignatureDecodingFailed)
	} else {
		Ok(signer.to_vec())
	}
}
```

### Finding Description
This mirrors the ALPINE-CVE-2018-12551 bug class: data that fails to parse as a well-formed credential (there, a malformed password-file line; here, a `signer` payload too short to be a real `Signature::Evm/Sr25519/Ed25519` enum) is silently accepted as valid identity data instead of being rejected. `handle_unsigned` is a fully unsigned, permissionless extrinsic reachable by any relayer submitting a message batch — `RequestMessage`/`ResponseMessage` carry an attacker-controlled `signer: Vec<u8>` field that flows into `store_request_receipt`/`store_response_receipt`, which call `extract_signer`, and the resulting bytes are used as the "relayer" identity emitted in `RequestResponseHandled` events and consumed downstream by fee/reward pallets (e.g. `pallet-messaging-incentives`'s `relayer_for`, and `pallet-ismp-relayer`'s fee-accumulation/outbound-delivery-reward logic) to determine who gets paid. [2](#0-1) 

By submitting a `signer` of ≤32 bytes set to an arbitrary account/address (e.g., a victim relayer's AccountId or an attacker-chosen address), an attacker can impersonate that relayer for message-delivery-attribution purposes without possessing any private key or valid signature — exactly analogous to mosquitto treating a malformed password-file entry as an authenticated, password-less user.

### Impact Explanation
Reward/fee-accounting logic keyed off the "signer" of a delivered message can be manipulated by any unsigned-extrinsic submitter to divert relayer incentives (delivery rewards, reputation minting, or fee escrow attribution) to an address that never signed anything. Where such attribution feeds actual token transfers (fee accumulation, `RequestResponseHandled.relayer`, `pallet-messaging-incentives::relayer_for` minting reputation tokens), this becomes a fund-diversion/theft vector rather than a purely cosmetic issue — a relayer's rightful reward can be redirected to an attacker-chosen account with zero cryptographic cost, since the "signature" need only be ≤32 raw bytes to bypass verification entirely.

### Likelihood Explanation
High likelihood: `handle_unsigned` is explicitly designed to be callable by anyone for free (unsigned transaction, validated only for proof correctness, not signer authenticity in this code path), and constructing a 32-byte-or-shorter `signer` field requires no cryptographic material — it is the trivial, zero-cost path compared to producing a real signature.

### Recommendation
Require `extract_signer` to always validate a real signature/public-key structure and reject any `signer` payload that cannot be decoded as a well-formed `Signature` variant, rather than falling back to "trust the raw bytes" for short inputs. If a raw-account-id-without-signature mode is intentionally supported for a specific message class, it must be gated so it cannot influence reward/fee attribution, and should be clearly distinguished (e.g., via explicit tagging) from a verified signer.

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
