### Title
Address Registrar contract silently retains excess attached deposit instead of refunding it to the caller - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `AddressRegistrar::register` method, part of the Wallet Contract's Ethereum-address-to-NEAR-account mapping infrastructure, accepts a `#[payable]` deposit that must cover the on-chain storage cost of the new mapping. If the caller attaches more NEAR than the computed `required_deposit`, the excess is only returned in the narrow case of an address collision; in the normal success path the entire `given_deposit` (including any overpayment) is retained by the contract with no refund path, permanently locking the caller's excess funds — the exact bug class described in the RubiconRouter report where overpaid ETH was never returned to `msg.sender`.

### Finding Description
`register` computes `required_deposit` from the storage bytes needed for the new `(address, account_id)` entry and reads `given_deposit = env::attached_deposit()`: [1](#0-0) 

It only validates a lower bound (`given_deposit < required_deposit` panics); there is no upper-bound check or refund of the difference. In the success ("Vacant") branch, the entry is inserted and the deposit is fully consumed with no transfer back to the caller: [2](#0-1) 

By contrast, in the "Occupied" (collision) branch, the developers explicitly recognized that the deposit must be returned since no storage was updated, and issue a `promise_batch_action_transfer` back to `predecessor_account_id`: [3](#0-2) 

This asymmetry confirms the omission is a bug rather than an intentional design: refund logic exists for one path but was not applied to the (much more common) successful-registration path. This is unlike the core runtime's deposit-refund mechanism (e.g. `action_deterministic_state_init`), which explicitly calculates and refunds any deposit beyond what is required for storage staking: [4](#0-3) 

The registrar contract does not follow this same pattern for excess deposits.

### Impact Explanation
Any unprivileged account calling `register` on the deployed Address Registrar (account id `address-map.near`, per `ADDRESS_REGISTRAR_ACCOUNT_ID`) with a deposit larger than the exact required storage cost — e.g. rounding up, using a generic "sufficient deposit" convention, or simply guessing — permanently loses the excess NEAR to the contract's account balance, with no way to reclaim it. Given this contract is a supporting piece of the Wallet Contract / eth-implicit-account tooling that real users and relayers interact with, this results in concrete, unrecoverable user fund loss (a balance/economic-accounting bug), matching the "unauthorized balance change"/fund-loss criteria.

### Likelihood Explanation
Likelihood is high in practice: callers have no reliable way to know the exact required deposit ahead of time (it depends on `account_id.len()` and current `storage_byte_cost()`), so many callers would naturally overpay (e.g., by using a round number or a safety margin), and every such overpayment is silently forfeited on any successful registration.

### Recommendation
In the `Vacant` branch of `register`, compute `excess = given_deposit - required_deposit` and, if nonzero, issue a `promise_batch_action_transfer` refund of `excess` back to `env::predecessor_account_id()`, mirroring the refund already implemented in the `Occupied` branch and in the core runtime's `action_deterministic_state_init` deposit-refund logic.

### Proof of Concept
1. Deploy/use the Address Registrar contract (`address-map.near`).
2. Call `register({"account_id": "birchmd.near"})` attaching a deposit larger than the exact `required_deposit` (e.g., attach `1 NEAR` when the storage-based requirement is a few hundred microNEAR, as shown in the existing test `test_register_without_deposit`, which attaches a fixed `320000000000000000000` yoctoNEAR regardless of the exact requirement): [5](#0-4) 
3. Observe that `register` succeeds and returns `Some(address)`, but the caller's balance is debited the full attached deposit while only the storage-bytes cost was actually needed — the difference is never transferred back, unlike the collision-refund path.

/// Test asserting the address registrar requires a deposit.
#[tokio::test]
async fn test_register_without_deposit() -> anyhow::Result<()> {
    let TestContext { worker, address_registrar, .. } = TestContext::new().await?;

    let method = "register";
    let args = br#"{"account_id": "birchmd.near"}"#;
    let result = address_registrar.call(method).args(args.to_vec()).transact().await?;
    assert!(result.is_failure(), "Call without deposit must fail");

    let pre_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    let deposit_amount = NearToken::from_yoctonear(320000000000000000000);
    let result = worker
        .root_account()?
        .call(address_registrar.id(), method)
        .args(args.to_vec())
        .deposit(deposit_amount)
        .transact()
        .await?;

    let output: Option<String> = result.json()?;
    assert_eq!(output.as_deref(), Some("0x4bfcff9a964925adf801c866f6ada98bd7ec40ca"));
    let post_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    assert!(
        post_tx_account_balance.as_yoctonear() - pre_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );
