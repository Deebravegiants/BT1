Audit Report

## Title
Plaintext JWT bearer token disclosed in gateway vault handler debug/info logs - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` logs the entire `*jsonrpc.Request[json.RawMessage]` object (including its `Auth` field, which carries the caller's raw JWT bearer token) at Debug level, and a related code path in `core/services/gateway/handlers/vault/handler.go` does the same at the gateway's HTTP entrypoint. Since `jsonrpc.Request`/`Response` are plain structs passed via the sugared logger's key-value mechanism with no visible redaction wrapper, enabling debug logging causes end-user JWT credentials to be written to node/gateway logs in plaintext.

## Finding Description
`GatewayHandler.HandleGatewayMessage` logs the raw request object wholesale: [1](#0-0) 
and logs the raw response object at Info level: [2](#0-1) 

`jsonrpc.Request[json.RawMessage]` carries the caller's JWT in its `Auth` field, confirmed by usages elsewhere in the vault code (e.g., test construction and mint helpers): [3](#0-2) 

The HTTP entrypoint extracts the bearer token from the `Authorization` header and forwards it into `req.Auth`, and this raw `req` (with `Auth` populated) is also logged wholesale by the gateway-side handler before authorization: [4](#0-3) 

Elsewhere in the same package, the team explicitly avoids logging `req.Auth` and instead logs a boolean `"hasAuth", req.Auth != ""`: [5](#0-4) 

This shows the discipline of not directly logging `Auth` exists elsewhere in the codebase, but was not applied to the two call sites above that log the entire `req`/`resp` struct. No `MarshalLogObject`/redaction override for `jsonrpc.Request`/`Response` was found in this repo's index (the type is defined in the external `chainlink-common` module), so absent such an override, the sugared logger will serialize all exported fields, including `Auth`, when Debug (or Info, for the response) logging is enabled.

## Impact Explanation
A leaked JWT is a full authentication credential for the vault gateway JSON-RPC flow used to authorize secret create/update/delete/list operations tied to a specific workflow owner/org. If an attacker (or any party with subsequent access to node/gateway logs, e.g., log aggregation systems or support staff) obtains this token, they can replay it (until expiry) to impersonate the original caller for vault secret operations — a credential/secret-exfiltration class impact consistent with in-scope disclosure findings.

## Likelihood Explanation
The vulnerable log lines only fire when Debug logging is enabled (or Info level for the response), so exploitation requires the operator to run with a non-default log level and requires the attacker to have subsequent read access to emitted logs. No additional privilege is required from the requesting client: the log statement is reached by ordinary, unprivileged/authenticated vault JSON-RPC traffic sent through the gateway HTTP endpoint (`vault_secretsList`, etc.), with the token embedded in the `Authorization: Bearer` header. The `hasAuth`-style guarding pattern used elsewhere in `authorizer.go` demonstrates the team is aware `Auth` is sensitive, but that protection was not extended to the whole-`req`/whole-`response` log statements in `gw_handler.go` and `handler.go`.

## Recommendation
Remove or redact the `Auth` field before logging request/response objects in `GatewayHandler.HandleGatewayMessage` (`core/capabilities/vault/gw_handler.go`) and in `handler.HandleJSONRPCUserMessage` (`core/services/gateway/handlers/vault/handler.go`). Log only non-sensitive fields (method, ID, gatewayID) or a sanitized copy with `Auth` cleared, mirroring the `"hasAuth", req.Auth != ""` pattern already used in `authorizer.go`. Consider adding a redacting `MarshalLogObject`/wrapper for `jsonrpc.Request`/`Response` so this protection is centrally enforced across all gateway handlers instead of per call site.

## Proof of Concept
1. Run a Chainlink node with the vault gateway capability configured and `Log.Level = 'debug'`.
2. As an unprivileged client, send a valid vault JSON-RPC request (e.g., `vault_secretsList`) to the gateway HTTP endpoint with header `Authorization: Bearer <jwt-token>`.
3. The gateway extracts the token into `req.Auth` and logs the full request via `h.lggr.Debugw("handling vault request", ..., "request", req)` in `core/services/gateway/handlers/vault/handler.go` (line 403).
4. On the node side, `GatewayHandler.HandleGatewayMessage` receives and logs the same request wholesale via `reqLggr.Debugw("received message from gateway", "req", req)` in `core/capabilities/vault/gw_handler.go` (line 182).
5. Inspect the debug log output — the caller's JWT bearer token appears in plaintext under the `"req"`/`"request"` field, confirming disclosure.

Note: I could not locate the `jsonrpc.Request`/`Response` type definitions or any `MarshalLogObject` implementation within this repo's index (they live in the external `chainlink-common` module), so I cannot fully rule out upstream redaction logic in that dependency. Based on the code reachable in this repo, however, the two logging call sites clearly pass the full struct (including `Auth`) to the logger with no local redaction, consistent with the claim.
