### Title
Webhook `shop-domain` header is trusted by handlers but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC over the body and then forwards `request.shop` straight into the handler as the tenant identifier, with no check that the shop in the header matches any shop the HMAC could vouch for [3](#0-2) .

### Finding Description
The intended identity binding is: `shop authenticated by the HMAC` == `shop the handler acts on`. In `Registry.process`, `Utils::HmacValidator.validate(request)` is invoked, which recomputes an HMAC purely from `to_signable_string` (the raw body) via `HmacValidator.validate_signature` [4](#0-3) . The `shop-domain` header consumed by `WebhookMetadata.new(shop: request.shop, ...)` is never part of that signable string [5](#0-4) , `lib/shopify_api/webhooks/request.rb:20-23`. As a result, the byte range that is HMAC-verified (the body) and the byte range that is parsed and acted upon for tenant identification (the `shop-domain` header) are disjoint: bytes verified != bytes used to determine the tenant.

The gem's own documentation confirms this is the exact mechanism apps are told to rely on: handlers receive `data.shop` and are expected to use it as the shop identifier for further processing (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [6](#0-5) . Nothing in `Request` or `Registry` cross-checks that the `shop-domain` header corresponds to the shop whose data produced the signed body, because the HMAC secret is the same for every shop/install of a given app (`Context.api_secret_key`) [7](#0-6) .

### Impact Explanation
An attacker who is a legitimate but unprivileged installer of the app on their own store (Shop A) will legitimately receive Shopify-signed webhooks for Shop A, with a valid `hmac-sha256` over some body plus a `shop-domain: shop-a.myshopify.com` header. Because the HMAC never covers the header, the attacker can resend that exact body/HMAC pair to the app's webhook endpoint while substituting `shop-domain: shop-b.myshopify.com` (the victim's shop). `HmacValidator.validate` will still return `true` because it only checks the body against the secret [7](#0-6) , and `Registry.process` will pass the forged `shop` straight to the app's handler as if it were an authenticated event from Shop B [3](#0-2) . Any host application following the documented pattern of using `data.shop` to route work to a per-shop job queue or update per-shop records is exposed to cross-tenant data injection/corruption.

### Likelihood Explanation
This does not require the app's `client_secret`/`api_secret_key`; it only requires the attacker to be an ordinary merchant with the app installed on their own store, which is an unprivileged, internet-accessible position (mandatory redact webhooks like `shop/redact` and `customers/redact` are even delivered to every installed app [8](#0-7) ). No TLS interception, credential leak, or social engineering is required — only capturing one's own genuine webhook traffic and replaying it with a modified header, which is straightforward for any developer/merchant who can inspect their own webhook endpoint traffic.

### Recommendation
Bind the `shop-domain` (and ideally `topic`) header into the HMAC-verified surface, e.g. by including the shop header in `to_signable_string`, or by having `Registry.process` independently verify that the `shop` header is one that the app currently has an active session/webhook registration for before invoking the handler with it. At minimum, document prominently that `data.shop` is not cryptographically bound to the signed body and must not be trusted for tenant-sensitive branching without an independent lookup against a known shop record.

### Proof of Concept
1. Attacker installs the target app on their own shop, `shop-a.myshopify.com`, and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker resends the same `B` and same HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop the attacker does not control).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "shop-b.myshopify.com"...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and returns `true` [9](#0-8) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "shop-b.myshopify.com", body: parsed_body, ...)` [5](#0-4) , and the host app's handler (per the documented pattern) performs shop-B-scoped work using attacker-supplied `body` data, achieving cross-tenant access.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
