### Title
Mutable `operator_qr_expiration_time` config re-read mid-flow causes inconsistent operator-QR expiration ("time travel") in signup authorization - ([File: src/plans/mod.rs], [File: src/config.rs])

### Summary
`MasterPlan::run`/`do_signup` re-read the shared, remotely-mutable `Config.operator_qr_expiration_time` value at multiple independent points during a single signup session, while comparing it against a fixed `operator_data.timestamp` captured earlier. Because the config value can change concurrently (via a full config replacement from the backend) between those reads, the effective expiration window used to validate the same operator QR-code session is inconsistent within one signup flow — directly analogous to the Dopex `fundingDuration` "time travel" bug, where a mutable duration parameter combined with a fixed epoch anchor produces inconsistent boundary calculations.

### Finding Description
`Config::download_and_store` atomically replaces the *entire* `Config` object (including `operator_qr_expiration_time`) behind a `Mutex`: [1](#0-0) 

`operator_qr_expiration_time` itself is a plain, backend-controlled `Duration` field with no invariants tying it to a specific session or anchor timestamp: [2](#0-1) 

In `MasterPlan::run`, the config (including `operator_qr_expiration_time`) is locked and destructured once at the top of the loop and used for `scan_initial_qr_codes` and `idle_wait_for_signup_request`: [3](#0-2) 

Later, inside `do_signup`, the config is locked and destructured **again**, producing a potentially different value of `operator_qr_expiration_time` than the one used earlier in the same signup attempt, and this second value is passed into `scan_remaining_qr_codes`: [4](#0-3) 

`scan_remaining_qr_codes` then compares the *fixed* `operator_data.timestamp` (captured when the operator QR was scanned, under the first config snapshot) against the *newly re-read* `operator_qr_expiration_time`: [5](#0-4) 

`idle_scan_user_qr_code` and `scan_initial_qr_codes` perform the same pattern — capturing `operator_data.timestamp = Instant::now()` at one point, then later evaluating `operator_data.timestamp.elapsed() {<,>} operator_qr_expiration_time` using whatever value happens to be in the shared `Config` at the time of the check: [6](#0-5) [7](#0-6) 

This exactly mirrors the root cause of the referenced report: an "epoch"/window boundary is computed as `anchor_timestamp + duration`, where `duration` is a mutable value that can change at any time set independently of the `anchor_timestamp`. Any change to `operator_qr_expiration_time` between the moment the operator QR-code session started (`anchor_timestamp = operator_data.timestamp`) and any later expiration check in the same signup flow causes the effective expiration boundary to jump forward or backward in time relative to what was in effect when the session began.

### Impact Explanation
If `operator_qr_expiration_time` is increased mid-flow (e.g. by a backend config push), an operator QR-code session that should have expired continues to be treated as valid for authorization purposes in `scan_remaining_qr_codes`/`idle_scan_user_qr_code`, extending the window in which a given operator identity is bound to a user signup beyond what was configured when the session started. If the value is decreased, an in-progress, still-legitimate operator-to-signup binding can be prematurely invalidated, forcing a reset of the operator/user QR association and creating an unauthorized-signup-adjacent binding inconsistency — i.e. the actual protection intended by the expiration check (ensuring stale operator authorization is not reused for a user QR-code binding) becomes non-deterministic and dependent on a race with a background config update, rather than on a fixed policy in effect at scan time.

### Likelihood Explanation
The change requires no attacker action beyond the operator/backend config update cadence that is already a normal part of orb operation (periodic config refresh). Because `Config` is a single object replaced wholesale and re-read independently at several call sites within one signup attempt (`run`, `scan_initial_qr_codes`, `idle_wait_for_signup_request`/`idle_scan_user_qr_code`, `do_signup`/`scan_remaining_qr_codes`), any config refresh landing between these reads during an active signup will trigger the inconsistency. This is a realistic, non-adversarial timing window rather than a contrived edge case, though it depends on the backend actually changing `operator_qr_expiration_time` while a signup is mid-flight, which is likely infrequent.

### Recommendation
- Capture `operator_qr_expiration_time` once per signup attempt (at the same time `operator_data.timestamp` is set) and thread that single, immutable-for-the-session value through all subsequent expiration checks (`scan_initial_qr_codes`, `idle_wait_for_signup_request`, `idle_scan_user_qr_code`, `do_signup`, `scan_remaining_qr_codes`), instead of re-reading `orb.config.lock().await` at each call site.
- Alternatively, store an absolute `operator_qr_expiry_instant = Instant::now() + operator_qr_expiration_time` alongside `OperatorData` at scan time, and compare against that fixed instant everywhere, so later configuration changes cannot retroactively alter the expiration boundary of an already-started session.

### Proof of Concept
1. Operator QR-code is scanned; `OperatorData.timestamp = Instant::now()` is recorded under `Config` snapshot A where `operator_qr_expiration_time = T1` (`src/plans/mod.rs:775-781`).
2. Concurrently, a background config refresh (`Config::download_and_store`, `src/config.rs:357-368`) replaces the shared `Config` with `operator_qr_expiration_time = T2` (e.g. much larger than `T1`), before the signup flow proceeds to `do_signup`.
3. `do_signup` re-locks the config and obtains `operator_qr_expiration_time = T2` (`src/plans/mod.rs:497-509`), then calls `scan_remaining_qr_codes(orb, qr_codes, T2)`.
4. `scan_remaining_qr_codes` evaluates `operator_data.timestamp.elapsed() < T2` (`src/plans/mod.rs:797,807`) — even though the operator session should have already expired under the originally-configured `T1`, it is now treated as still valid because the comparison uses the newly fetched `T2`, demonstrating the same "time travel" boundary inconsistency described in the referenced report.
