### Title
Direct token transfers (including cross-chain HyperFungibleToken mints) bypass `addYield`'s streaming gate and instantly reprice `StreamingYieldVault` shares - ([File: sdk/packages/core/contracts/vaults/StreamingYieldVault.sol])

### Summary
`StreamingYieldVault` is documented as composable with bridged assets — its own docs describe "transfer-and-stake" flows where a `HyperFungibleToken`/`WrappedHyperFungibleToken` mint or unlock can deliver tokens to an arbitrary destination address chosen by the sender of a cross-chain `send()`. The vault's exchange rate (`totalAssets()`) is computed directly from the underlying asset's raw `balanceOf(vault)`, minus only the currently-vesting tranche recorded via the owner-gated `addYield` path. Any token movement that lands in the vault outside of `addYield` — including a cross-chain mint/unlock whose `to` field is set to the vault's own address — is **not** tracked by `_vestingAmount`/`_lockedYield`, so it is counted as backing assets immediately, in the same block, with no vesting delay. This reproduces the same bug class as the Umee report: an external, module-agnostic mint/burn/transfer event (there IBC transfer via the bank keeper, here a HyperFungibleToken cross-chain mint or a plain ERC-20 transfer) changes the accounting base of an asset/share ratio that the module's own logic assumes can only move through its sanctioned path (`addYield`'s streamed vesting).

### Finding Description
`totalAssets()` is defined as:
```
sdk/packages/core/contracts/vaults/StreamingYieldVault.sol:94-96
function totalAssets() public view override returns (uint256) {
    return IERC20(asset()).balanceOf(address(this)) - _lockedYield();
}
``` [1](#0-0) 

`_lockedYield()` only masks the not-yet-vested portion of a tranche that was explicitly armed through `addYield` (owner-only) or the ERC-1363 `onTransferReceived` hook (also owner-gated) [2](#0-1) . Any other increase in `asset.balanceOf(vault)` — a plain `transfer()`/`transferFrom()` to the vault, or, per the project's own composability model, a cross-chain `HyperFungibleToken`/`WrappedHyperFungibleToken` mint or unlock where the bridging sender sets `to` = the vault's address — is invisible to `_vestingAmount` and is folded into `totalAssets()` the instant it lands, with **no vesting delay and no deposit-window restriction**. `maxDeposit`/`maxMint` only gate the vault's *own* `deposit`/`mint` entrypoints while a tranche is vesting; they do nothing to prevent raw asset transfers into the vault contract at any time [3](#0-2) .

Because `HyperFungibleToken.send()` lets an unprivileged token bridger specify an arbitrary destination `to` on the receiving chain, and the resulting mint/unlock on `onAccept` is delivered by any relayer at a time the bridger effectively controls (submit the dispatch, then race/relay), an attacker can:
1. Watch for (or engineer) an upcoming transfer of bridged assets destined for the vault's address, or simply prepare their own cross-chain mint targeted at the vault.
2. Deposit into `StreamingYieldVault` immediately beforehand, during an open deposit window.
3. Let the mint/transfer land, which is credited to `totalAssets()` instantly (unlike `addYield`, which streams over 22 hours).
4. Immediately `redeem()`, capturing a share of the newly arrived assets pro-rata with existing depositors — diluting/stealing value from LPs who were in the vault before the attacker's deposit and had no chance to react.

This directly parallels the audited Umee flaw: an accounting invariant ("exchange rate changes only via the module's sanctioned mechanism — interest accrual there, `addYield`'s streamed vesting here") is broken because a *different*, permissionless mint/transfer path (IBC transfer there, `HyperFungibleToken` cross-chain mint / plain ERC-20 transfer here) is not accounted for by the module that computes the ratio.

### Impact Explanation
An attacker can extract value from existing vault depositors by sandwiching any large, unvested inflow of the underlying asset into the vault contract — whether that inflow is an accidental transfer, a bridged mint targeted (deliberately or by mistake) at the vault address, or an attacker-funded cross-chain transfer used purely as a vector to create an instant, undiscounted price jump. Because the entire design goal of `StreamingYieldVault` (per its own NatSpec and docs) is to prevent exactly this kind of instant repricing/yield-sniping, and the vector bypasses that protection entirely, this is a fund-theft path (Medium-High), not merely a griefing issue: LPs holding shares through the sandwich lose value equal to the fraction the attacker captures. This satisfies the "concrete theft of funds" bar.

### Likelihood Explanation
Reachability requires only unprivileged actions: calling `HyperFungibleToken.send()`/`WrappedHyperFungibleToken` with an arbitrary `to`, or a bare ERC-20 `transfer`, plus normal `deposit`/`redeem` calls on the vault — no governance, admin, or node compromise needed. The main precondition is that a deployment configures a `StreamingYieldVault` over a bridged HFT/BridgeToken asset (explicitly advertised as a supported composability pattern in the docs) and that the vault already has other depositors at the time of the attack, which is the vault's normal operating state.

### Recommendation
- Track the vault's asset backing internally (an explicit `_principal` accounting variable incremented only by `deposit`/`mint`/`addYield`) rather than deriving `totalAssets()` from the raw `balanceOf(vault)` minus a vesting mask. Any balance above the tracked principal + vesting tranche should be swept/attributed to the next `addYield` tranche (streamed), not recognized instantly.
- Alternatively/additionally, if a `HyperFungibleToken` peer is intended to fund the vault directly, route that inflow through the same `onTransferReceived`/`addYield` gate (owner-only, streamed) instead of allowing arbitrary senders to target the vault's raw balance.
- Document/enforce (at the integration layer) that vault deployments over bridged assets must never be a valid `to` target for third-party cross-chain sends, or add a check in `totalAssets()`/deposit flow that rejects/streams unexpected balance deltas between calls.

### Proof of Concept
1. Deploy `StreamingYieldVault` over a `HyperFungibleToken` (`asset`), seed-and-burn per the docs.
2. Depositor A deposits 1000 units; vault's `totalAssets() == totalSupply()` (par value), `convertToAssets` at 1:1.
3. Attacker observes that a cross-chain `send()` call (their own, or a third party's) is about to mint/unlock 500 units of the underlying with `to = address(vault)` on this chain (composability pattern documented for "transfer-and-stake"/direct funding).
4. Immediately before the mint lands, attacker deposits X units into the vault (deposit window is open, no tranche vesting).
5. The 500-unit mint lands via `onAccept` on the `HyperFungibleToken`, crediting `balanceOf(vault)` by 500 instantly; `_lockedYield()` is 0 for this inflow because it never went through `addYield`. `totalAssets()` jumps immediately by 500.
6. Attacker calls `redeem()` for all their shares, extracting X + (X/(1000+X)) * 500 units — capturing part of the 500-unit inflow that depositor A did not have a chance to react to, at A's expense (A's post-attack share of `totalAssets` is diluted below what A would have received had the attacker not sandwiched the inflow).

Note: full exploit economics (exact solver/relayer timing assumptions for guaranteeing "before" vs "after" ordering on a specific L2) were not independently re-verified against a live testnet in this review; the code path proving the missing accounting gate (`totalAssets()` reading raw `balanceOf` with no protection against non-`addYield` inflows) is confirmed directly in the cited source.
