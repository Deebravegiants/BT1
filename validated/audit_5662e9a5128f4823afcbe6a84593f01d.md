The documentation explicitly makes the identity-binding claim I identified: it states that `ShopifyAPI::Webhooks::Registry.process`/`ShopifyAPI::Webhooks::Request` "will verify the request did indeed come from Shopify" (docs/usage/webhooks.md line 125), and documents `data.shop` as "The shop domain of the webhook" (a trusted field, docs/usage/webhooks.md line 14) that the sample handler uses directly to key work (`shop_domain: data.shop`, line 26). This confirms the gem itself documents `shop` as a verified/trusted identity field, while the actual verification never binds it to the HMAC.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `HmacValidator` only checks that HMAC-SHA256(raw_body, api_secret_key) matches the `hmac-sha256` header. The `shop-domain`, `topic`, and `webhook-id` headers used to build `WebhookMetadata` are never included in the signed content, so the gem authenticates the body but not the shop identity it hands to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop` purely from an HTTP header: [1](#0-0) 
and its `to_signable_string` (the value that gets HMAC-verified) is only the raw body: [2](#0-1) 

`Registry.process` verifies only this HMAC and then constructs `WebhookMetadata` directly from the unauthenticated `request.shop` header: [3](#0-2) 

`HmacValidator.validate` computes the signature purely over `to_signable_string` (the raw body) with the app's `api_secret_key`: [4](#0-3) 

Since the HMAC secret (`api_secret_key`) is global to the app (identical for every shop that installs it), and the signed content excludes the shop identity, any raw body + valid HMAC pair obtained from one shop's real webhook delivery remains a valid `(raw_body, hmac)` pair regardless of which `shop-domain` header accompanies it. The documentation asserts that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is a trustworthy "shop domain of the webhook" field passed straight to application logic — but the shop identity itself carries no cryptographic binding to the verified bytes.

**Binding that should hold:** `shop_bound_by_HMAC == shop_delivered_to_handler`. **Binding that actually holds:** only `HMAC(raw_body) == header_hmac`; `shop` is disjoint from the verified bytes.

### Impact Explanation
An unprivileged internet user who can install the app on their own store (a normal, unprivileged Shopify merchant action requiring no special credentials) receives real webhook deliveries containing a valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key`. They can replay that exact body/HMAC pair directly to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header naming a victim shop. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain and attacker-controlled body content. Any handler that uses `data.shop` as a tenant key (exactly as shown in the gem's own documented example) will process/store attacker data under another tenant's identity — a cross-tenant data injection/confusion vulnerability, which maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Moderately likely: it requires the attacker to be able to install the target app on a shop they control (no elevated privilege) and simply modify one HTTP header on a raw HTTP request replayed to the app's public webhook endpoint. No access to `api_secret_key`, session tokens, or victim credentials is required — only a legitimate, unmodified `(raw_body, hmac)` capture from the attacker's own installation.

### Recommendation
Bind the shop identity to the verified content. Concretely, include `shop`, `topic`, and `webhook_id` in the HMAC-signable content (e.g., verify against a canonical string composed of these headers plus raw body), or independently authenticate the shop identity against a shop known to be installed/subscribed for that specific webhook_id/topic before invoking the handler. At minimum, document that `WebhookMetadata#shop` is unauthenticated relative to the signature and must be independently cross-checked by the host application (e.g., against session storage) before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and configures a webhook topic (e.g. `orders/create`).
2. Shopify delivers a real webhook: `raw_body = B`, header `shopify-hmac-sha256 = H` (valid because `H == HMAC(api_secret_key, B)`), `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same `B` and `H` directly to the app's public webhook endpoint but changes the header to `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim.myshopify.com", "shopify-hmac-sha256" => H})` is constructed; `to_signable_string` still returns `B`.
5. `HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and it still equals `H` — validation passes (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31).
6. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb` lines 188-199), causing the app to act on attacker-controlled data as if it belonged to the victim shop.
