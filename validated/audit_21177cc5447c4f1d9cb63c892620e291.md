### Title
Webhook `shop-domain` (and `topic`/`api-version`) header trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC validated by `Utils::HmacValidator.validate` never covers the `shop-domain`, `topic`, or `api-version` headers. `Registry.process` nonetheless trusts `request.shop` and forwards it, unauthenticated, into the handler that acts on behalf of that shop.

### Finding Description
The webhook pipeline is:

1. `HmacValidator.validate(request)` computes `HMAC(secret, request.to_signable_string)` and compares it to `request.hmac`. [1](#0-0) 
2. `Request#to_signable_string` is defined as just `@raw_body` — it never includes `shop`, `topic`, or `api_version`. [2](#0-1) 
3. `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the verified body. [3](#0-2) 
4. `Registry.process` validates the HMAC, then immediately hands `request.shop` (and `topic`) to the app's registered handler as authoritative identity information. [4](#0-3) 

This is structurally identical to the reported bug class: a value that is acted upon downstream (`shop`, used by the host app to select which tenant's session/data the webhook body applies to) is not bound by the equality the system relies on for authentication — here, `verified_bytes(body) == signed_bytes(body)` says nothing about `header.shop == the shop the body actually came from`. Just like the treasury bug updates yield for the wrong chain because the liquidation/yield identity isn't bound to the collateral's actual chain, this gem lets webhook processing attribute a signed body to an arbitrary attacker-chosen shop, because the shop identity isn't bound to the signature.

Because the app's `api_secret_key` is shared across all shops that install the app (it is the app's own client secret, not a per-shop secret), any attacker who can obtain one valid `(body, hmac)` pair — e.g., by installing the app on their own store and receiving a legitimate webhook — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the handler believing the event originates from the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: `authenticated_shop` (none, in fact) is conflated with `header_shop` used to act on merchant data. A host application built on this gem (per its documented `WebhookHandler` contract) will process/store data keyed to `data.shop` from `WebhookMetadata`, meaning an attacker-controlled body can be attributed to and mutate state for a shop the attacker doesn't own — a cross-tenant access scenario, matching the Critical impact category ("cross-tenant access").

### Likelihood Explanation
Any developer/merchant who can install the target app on a shop they control (a normal, unprivileged flow — no leaked credentials, no access token theft, no TLS interception needed) can capture one legitimate webhook body+HMAC pair from their own store and replay it against the app's public webhook endpoint with a forged `shop-domain` header. This requires only observing the gem's documented behavior (`Registry.process`/`Request`), not violating it.

### Recommendation
Bind the shop (and ideally topic) identity into the verified data rather than trusting an unauthenticated header:
- Have `to_signable_string` incorporate `shop`/`topic`/`api_version` (if Shopify's webhook HMAC scheme allows this), or
- Independently confirm `request.shop` against a shop known to be associated with the specific webhook subscription/session (e.g., cross-check against the shop tied to the webhook ID via a GraphQL lookup) before invoking handlers, or
- At minimum, document explicitly that `data.shop` in `WebhookMetadata` is NOT cryptographically authenticated and must not be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) so Shopify sends a genuine request with headers `x-shopify-hmac-sha256: <HMAC>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and some `raw_body`.
2. Attacker captures this exact `(raw_body, hmac)` pair.
3. Attacker POSTs to the app's public webhook endpoint with the same `raw_body`/`hmac` but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against `hmac` [5](#0-4) ; `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host app to process attacker-controlled data as if it originated from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
