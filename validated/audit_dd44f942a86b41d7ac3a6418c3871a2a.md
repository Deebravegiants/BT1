## Analysis Result

<title>
Single Blocklisted/Reverting Token in a Multi-Token Order Permanently Freezes All Escrowed Assets in `_withdraw` - (File: evm/src/apps/intentsv2/IntentsBase.sol)
</title>

### Summary
`IntentsBase._withdraw` releases escrowed order funds by iterating over the order's `TokenInfo[] tokens` array and calling `safeTransfer`/`_sendValue` for each token in a single loop. If any single token in that array reverts on transfer (e.g., a blocklisted USDC/USDT account, a paused token, or any ERC20 with transfer-side restrictions), the entire loop — and therefore the whole withdrawal — reverts, permanently locking every other (otherwise transferable) token escrowed for that order commitment. This mirrors the reported `Account.sweepTo`/`_liquidate` issue where an all-or-nothing loop over multiple assets causes a full-transaction DoS from one bad asset.

### Finding Description
`_withdraw` is the single funds-release primitive shared by same-chain cancellation, cross-chain refund, and cross-chain redeem paths: [1](#0-0) 

It loops over `body.tokens` (derived from `order.inputs`, which is a user-supplied `TokenInfo[]` that can contain multiple distinct ERC20 tokens for a single order) and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each entry without any per-token isolation or try/catch. A revert on any single transfer call (`safeTransfer` bubbles up the underlying ERC20's revert) aborts the whole function, including the release of all previously-iterated, perfectly healthy tokens in the same order.

This function is reachable from multiple unprivileged entry points:
- `_cancelSameChain` refunding escrow directly on cancellation: [2](#0-1) 
- `onAccept` processing a `RedeemEscrow`/`RefundEscrow` cross-chain message delivered by any relayer: [3](#0-2) 
- `onGetResponse` refunding escrow after a GET-request proof round trip: [4](#0-3) 

Since `order.inputs` is chosen by the user placing the order and can list several tokens, an order that mixes a normal token with a token subject to admin-controlled blocklisting (USDC/USDT-style `transfer` reverts for blocked accounts) creates a single point of failure: once that token's transfer to `beneficiary` starts reverting (beneficiary or the gateway itself gets blocked, or the token pauses transfers), `_withdraw` can never succeed for that commitment again, freezing all co-escrowed tokens indefinitely — regardless of whether the caller is the legitimate order owner attempting cancellation/refund.

### Impact Explanation
This causes permanent freezing of user funds: once one token in a multi-token order's escrow becomes untransferable, none of the escrow — including entirely unrelated, freely-transferable tokens bundled in the same order — can ever be withdrawn, refunded, or redeemed, because `_withdraw` has no partial-success/partial-liquidation mode and is the only code path that decrements `_orders[commitment][token]` and moves tokens out of escrow. This qualifies as a concrete, permanent loss-of-access to escrowed funds under a realistic threat (blocklist-capable stablecoins are widely used as intent inputs).

### Likelihood Explanation
Likelihood is moderate-to-high in practice: users routinely construct multi-input orders (e.g., splitting funding across several assets), and stablecoins with admin blocklist capability (USDC, USDT) are extremely common intent inputs. An attacker/griefer does not need special privileges — they only need the beneficiary or gateway address for one of the order's tokens to become blocklisted (which can happen through normal issuer compliance actions unrelated to Hyperbridge, or be adversarially induced by getting the user's own withdrawal address flagged), and any relayer delivering a `RefundEscrow`/`RedeemEscrow` message, or the user itself calling cancel, will trigger the revert.

### Recommendation
Make `_withdraw` resilient to a single failing token transfer:
- Wrap each per-token transfer in a try/catch (or use a low-level `call` and check success) so a failing transfer for one token does not block release of the others, tracking any un-transferred tokens for later retry/sweep by the beneficiary.
- Alternatively, support partial/selective withdrawal, allowing the beneficiary to specify which subset of escrowed tokens to withdraw, so a stuck token does not block the rest.
- Emit an event/leave escrow state intact for tokens that failed to transfer so they can be retried independently once the underlying restriction is lifted.

### Proof of Concept
1. User places a cross-chain order with `order.inputs = [TOKEN_A (healthy ERC20), TOKEN_B (USDC-like with blocklist)]`, escrowing both on the source chain via `IntentGatewayV2`/`ExtrinsicIntents`.
2. Before the order is filled, `order.user`'s address (the escrow beneficiary) is added to `TOKEN_B`'s blocklist by its issuer (a normal, expected admin action independent of Hyperbridge), or the order is cancelled after `TOKEN_B` operations are paused.
3. User calls `cancelOrder` → same-chain path invokes `_cancelSameChain` → `_withdraw`, which iterates `[TOKEN_A, TOKEN_B]`; the `TOKEN_B.transfer` reverts due to the blocklist, reverting `_withdraw` entirely: [5](#0-4) .
4. Result: `TOKEN_A`, which has no issue, is also stuck in escrow forever, because `_withdraw` never separates or retries per-token, and there is no alternate withdrawal path for `_orders[commitment][TOKEN_A]`.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
