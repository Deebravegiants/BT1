Audit Report

## Title
Missing `return` after failed type assertion on OIDC `email` claim allows session creation and audit logging with invalid identity data - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `handleTokenExchange`, the type assertion `email, ok := claims["email"].(string)` at line 226 is not followed by a `return` when it fails, so a malformed or missing `email` claim from the OIDC identity provider does not halt request processing. Execution continues to create a valid, functioning session (`oidc_sessions` row, session cookie, audit log entry) using an empty-string `email`, and the handler ultimately returns HTTP 200 `{"success": true}` even though a 500 error body was already written earlier in the same handler invocation.

## Finding Description
This is confirmed directly in the code: after the failed assertion at lines 226-230, the function does not `return`, and continues to compute `role` from `idClaims` (independent of `email`), insert a row into `oidc_sessions` with `user_email` set to `strings.ToLower(email)` (i.e., empty string), emit `audit.AuthLoginSuccessNo2FA` with `email: ""`, set the session cookie via `ginSession.Set(webauth.SessionIDKey, clSession.ID)`, and finally respond `200 OK`. [1](#0-0)  This matches the pattern of the sibling error branches in the same function that correctly `return` after writing an error response, showing the omission here is inconsistent with the surrounding code's own error-handling convention. [2](#0-1) 

Downstream, `AuthorizedUserWithSession` looks up sessions strictly by the random `sessionID`, not by email, so the blank email does not let an attacker impersonate a specific existing account. [3](#0-2)  However, `ClearNonCurrentSessions` deletes `oidc_sessions` rows by `lower(user_email) = lower($1)`, so multiple sessions sharing the empty-email marker would cross-affect each other's session cleanup. [4](#0-3) 

## Impact Explanation
A working authenticated session with a legitimately derived RBAC role (from IdP group claims, unaffected by the email bug) is created and persisted despite the server having detected and logged an identity-extraction failure. This corrupts audit-log integrity (blank identity recorded for a "successful" login) and can cause unrelated sessions that share the empty-email marker to be purged by `ClearNonCurrentSessions`, a cross-user session-management defect. There is no privilege escalation beyond what the legitimate group claims already grant, and no ability to hijack a specific victim's session by email, since session lookup is keyed by `sessionID` only.

## Likelihood Explanation
Triggering this requires the OIDC identity provider's ID token to omit the `email` claim or return it in an unexpected type—an edge case dependent on the provider/scope configuration used by the node operator, not something an unauthenticated external attacker controls directly. Any user completing a normal `/oidc-exchange` flow against such a provider configuration would hit this path without needing elevated privileges, making it plausible in real-world OIDC deployments with incomplete scope/claim configuration.

## Recommendation
Add a `return` immediately after `c.String(http.StatusInternalServerError, "Failed to get email from claims")` at line 229 so the handler aborts before deriving a role, inserting the `oidc_sessions` row, emitting the audit log, or setting the session cookie. More generally, avoid writing multiple HTTP response bodies within a single handler invocation, and require a well-formed, non-empty `email` claim before proceeding with session establishment and audit logging.

## Proof of Concept
1. Configure an OIDC identity provider (or a test double) whose ID token claims omit `email` (or set it to `null`/non-string), while including valid group claims that map to a role via `IDClaimsToUserRole`.
2. Complete the OAuth2 flow and POST the resulting code/state to `/oidc-exchange`.
3. Observe (via logs) that `claims["email"].(string)` fails at line 226, a 500 body is written, but the handler does not return.
4. Confirm the response is ultimately `200 {"success": true}`, a new row exists in `oidc_sessions` with `user_email = ''`, and `audit.AuthLoginSuccessNo2FA` was logged with `email: ""`.
5. Verify the returned session cookie is valid via `AuthorizedUserWithSession`, confirming a functioning session was established despite the earlier detected failure.

// ClearNonCurrentSessions removes other oidc_sessions for the user tied to sessionID.
func (oi *oidcAuthenticator) ClearNonCurrentSessions(ctx context.Context, sessionID string) error {
	var email string
	if err := oi.ds.GetContext(ctx, &email, "SELECT user_email FROM oidc_sessions WHERE id = $1", sessionID); err != nil {
		return err
	}
	_, err := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE lower(user_email) = lower($1) AND id != $2", email, sessionID)
	return err
}
