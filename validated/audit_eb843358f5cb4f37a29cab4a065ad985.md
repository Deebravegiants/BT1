### Title
Zero-token "Min path" in Emporium bypasses all balance conservation checks, enabling unbounded fund extraction - (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`Hinkal.transact` allows a designated "Min" flow for the Emporium external action when `circomData.erc20TokenAddresses.length == 0` [1](#0-0) , which uses a minimal proof (`formInputEmporiumMin`, only 3 public signals: `emporiumMessage`, `timeStamp`, `calldataHash`) [2](#0-1) . In this path, both `Hinkal.transact`'s balance-diff loop [3](#0-2)  and `EmporiumUpgradeable.runAction`'s balance-conservation loop [4](#0-3)  iterate zero times, since both iterate over `circomData.erc20TokenAddresses`. Meanwhile the `stack.ops` loop that performs the actual external calls (including arbitrary `op.endpoint.call{value: op.value}(op.callData)`) is fully unbounded by token count and executes regardless [5](#0-4) .

### Finding Description
**Broken equality**: `balancesAfter[i] - balancesBefore[i] == -deltaAmountChanges[i] + (value paid out via handleOut)` for every token actually touched by `stack.ops`. When `erc20TokenAddresses.length == 0`, this equality is never evaluated for any of the `N` tokens actually moved by `stack.ops`, because both `balancesBefore`/`balancesAfter` arrays and `deltaAmountChanges` are length-0. There is literally no accounting array indexed by the tokens the ops touch.

Root cause: `runAction`'s conservation check is driven entirely by `circomData.erc20TokenAddresses`, an attacker-supplied array whose length the attacker fully controls and which the "Min" circuit path (designed for signature-authenticated wallet flows) explicitly permits to be zero, bypassing `dimensionsCheck`'s equality requirement (`erc20TokenAddresses.length == dimensions.tokenNumber`) simply by also setting `dimensions.tokenNumber = 0` [6](#0-5) .

Attacker's call: submit `Hinkal.transact` with `dimensions.tokenNumber = nullifierAmount = outputAmount = 0`, `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `circomData.erc20TokenAddresses = []`, `circomData.stack.signerAddress = address(0)` (so `verifyWallet` skips the EIP-712 signature check entirely at [7](#0-6)  and only requires a fresh, attacker-chosen `emporiumMessage` nonce), and `stack.ops = [{endpoint: attackerEOA, invokeWallet: false, value: <EmporiumBalance>, callData: ""}]`. The attacker generates a trivial proof for the registered `VerifierEVMMin0v4`/`mainEVMCircuitMin0v4` (3 public signals, no nullifier/merkle constraints) [8](#0-7) . On execution, `runAction`'s CASE 2 branch performs `op.endpoint.call{value: op.value}(op.callData)`, transferring native ETH held by the `EmporiumUpgradeable` contract to the attacker [9](#0-8) , with zero pre/post balance checks anywhere in the call chain and no UTXO emitted.

None of the existing guards catch this: `dimensionsCheck` only enforces internal array-length consistency, not a minimum token count; `checkOnchainCreation` iterates `onChainCreation` (also length 0); `verifyWallet` is skipped for `signerAddress == 0`; the Min circuit intentionally constrains nothing about balances (only `emporiumMessage`/`timeStamp`/`calldataHash`); and `Hinkal.transact`'s own balance loop is likewise zero-length.

### Impact Explanation
Any ETH sitting in the shared, singleton `EmporiumUpgradeable` contract instance — from protocol fee residue, rounding dust, or any other user's in-flight/leftover funds from prior legitimate Emporium interactions — can be drained by an unprivileged attacker to an address of their choosing with zero on-chain accounting or revert. This is a direct theft of funds in flight through the protocol, matching the Critical severity bar (direct theft of shielded/in-flight funds with no proof-of-ownership verification). The attack is repeatable every time the Emporium contract's balance is non-zero.

### Likelihood Explanation
Preconditions: (1) an Emporium `VerifierEVMMin0v4`-class verifier must be registered by the owner for the Emporium action ID (a normal deployment/configuration state, not an attacker privilege), and (2) the Emporium contract must hold a nonzero ETH (or token, if `erc20TokenAddresses` were nonzero but mismatched) balance at call time — plausible given `receive() external payable {}` accepts arbitrary ETH [10](#0-9)  and normal Emporium flows can leave residual balances. The attacker's cost is a single trivial ZK proof generation for a 3-signal circuit and one transaction — fully within an unprivileged EOA's capability as defined by the rules.

### Recommendation
Do not gate the balance-conservation loop on `circomData.erc20TokenAddresses.length`. For the Emporium "Min" path, either (a) forbid `op.value > 0` / disallow raw `.call` with value entirely unless `invokeWallet` routes through a wallet that independently accounts for its own balance, or (b) require the Min path to still snapshot and verify the contract's native ETH balance before/after `stack.ops` execution (independent of `erc20TokenAddresses`), reverting if the contract's balance decreases beyond what is explicitly authorized by a verified signer.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register `VerifierEVMMin0v4` for the Emporium `(tokenNumber=0, nullifierAmount=0, outputAmount=0, HINKAL_EMPORIUM_ACTION_ID)` verifier id, and register the Emporium external action.
2. Fund `EmporiumUpgradeable` with 10 ETH via any legitimate flow (e.g., a normal Emporium op that leaves ETH un-swept, or a direct `receive()` transfer to simulate dust/residual funds).
3. Craft `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and `ops = [{endpoint: attacker, invokeWallet: false, value: 10 ether, callData: ""}]`, and `dimensions.tokenNumber = 0`.
4. Generate a valid proof for `mainEVMCircuitMin0v4` over public signals `[emporiumMessage, timeStamp, calldataHash]`.
5. Call `hinkal.transact(a, b, c, dimensions, circomData)` from the attacker EOA.
6. Assert: (a) transaction succeeds without reverting `BalanceChangeShouldBePositive` or any other check; (b) attacker's ETH balance increased by 10 ether; (c) `EmporiumUpgradeable`'s ETH balance is 0; (d) no `UTXO`/commitment was inserted (`insertCommitments` received an empty `onChainCommitments` array) — proving 10 ETH left the protocol with zero on-chain accounting.
