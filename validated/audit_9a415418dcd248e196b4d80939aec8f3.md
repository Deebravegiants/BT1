### Title
Predictable, deterministic session identifiers used directly as the bearer session cookie value for non‑embedded apps enable cross‑tenant session hijacking - (File: `lib/shopify_api/auth/session.rb`, `lib/shopify_api/auth/oauth.rb`)

### Summary
For non-embedded apps, the OAuth callback sets the session cookie's value to `session.id` [1](#0-0) . That `id` is not a high-entropy secret — it is deterministically computed from the shop domain and the merchant user's numeric id: `"#{shop}_#{associated_user.id}"` for online tokens or `"offline_#{shop}"` for offline tokens [2](#0-1) . This deterministic identifier is later read back verbatim from the cookie by `SessionUtils.cookie_session_id` with no additional verification, and is used to look up the stored session [3](#0-2) .

### Finding Description
The identity binding that should hold is: `cookie value the browser presents == a secret, unguessable token bound to this specific authenticated session`. Instead, the equality that actually holds is: `cookie value == "#{shop}_#{associated_user_id}"` (or `"offline_#{shop}"}`), i.e., a value fully derivable from public/enumerable data rather than from any secret material.

- `Session#initialize` normally defaults `id` to `SecureRandom.uuid` when not supplied [4](#0-3) , showing the library's own baseline expectation that a session id should be unguessable.
- However, `Session.from`, which is the path used after every OAuth completion, overrides this with the deterministic value [2](#0-1) .
- `validate_auth_callback` then uses this deterministic `session.id` as the literal cookie value for non-embedded apps [5](#0-4) .
- On subsequent requests, `SessionUtils.current_session_id` → `cookie_session_id` trusts whatever value is present in the cookie and returns it directly as the session id used to fetch the session, with no signature or freshness check [3](#0-2) .

Shop domains (`*.myshopify.com`) are public, and merchant/associated-user ids are small sequential integers that are frequently observable (e.g., leaked in webhooks, API responses, or simply guessable by brute force over a small integer space). An attacker who can predict or learn a target shop's `shop` string and `associated_user.id` can construct the exact cookie value `"#{shop}_#{associated_user.id}"` (or `"offline_#{shop}"` for the offline/merchant-wide session) themselves and set it as their own `shopify_app_session` cookie, without ever having captured the victim's real cookie.

### Impact Explanation
If the host app's session store keys purely off this id (the intended, documented pattern for this gem's cookie-based session flow), setting a forged, predictable cookie value grants the attacker's browser session lookups against another tenant's/merchant's stored `Session` — cross-tenant access to that shop's session context. This matches the Critical "cross-tenant access" impact category, since it breaks the tenant isolation boundary using only publicly derivable strings and no credential/token of the victim.

### Likelihood Explanation
Likelihood is moderate-to-high in offline-token-only setups since `offline_#{shop}` requires only the public shop domain (no secret guessing of a user id needed at all). For online tokens, exploitability depends on how easily `associated_user.id` can be learned or brute-forced for the target shop; in many apps user ids are low-cardinality integers, making enumeration practical. The attack requires no access to the real access token, `client_secret`, or any cookie belonging to the victim.

### Recommendation
Do not use `Session.from`'s deterministic id as the bearer value of the session cookie for non-embedded apps. Either generate a separate high-entropy random token for the cookie value while keeping the deterministic id only as an internal lookup key, or make the cookie carry the deterministic id plus an unguessable random nonce that is validated against server-stored state on each request.

### Proof of Concept
1. App runs in non-embedded mode; a merchant completes OAuth. `validate_auth_callback` returns cookie `{ name: "shopify_app_session", value: session.id }`, where `session.id == "offline_shop-a.myshopify.com"` (offline token case) [1](#0-0) [6](#0-5) .
2. Attacker, knowing only the public shop domain `shop-a.myshopify.com`, sets a cookie `shopify_app_session=offline_shop-a.myshopify.com` in their own browser against the app.
3. On the next request, `SessionUtils.current_session_id` extracts this attacker-supplied value via `cookie_session_id(cookies)` unchanged [3](#0-2)  and the host app looks up and uses the real merchant's stored `Session` (including access token) for that id — the attacker never needed to see the merchant's actual cookie.
