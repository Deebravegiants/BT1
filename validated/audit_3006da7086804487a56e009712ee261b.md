## Title
Missing Chainlink `minAnswer`/`maxAnswer` circuit-breaker check in `SimplexPaymaster._getOraclePrice()` allows stale/saturated price to under- or over-charge sponsored gas — ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster._getOraclePrice()` validates that a Chainlink `answer` is positive and that `updatedAt` is not older than `maxOracleAge`, but it never checks the returned `answer` against the underlying aggregator's `minAnswer`/`maxAnswer` bounds. When the real market price of the native asset or a registered fee token moves outside those bounds, Chainlink's `AggregatorV3Interface` will keep publishing the saturated boundary value with a fresh `updatedAt`, passing both of the paymaster's checks while reporting a materially wrong price. This is the exact bug class from the external report (missing recency *and* min/max bound checks on `getPriceFromChainlink`), except here only the recency check has been implemented — the min/max bound check is still missing.

### Finding Description
`_getOraclePrice()` is the sole price-fetching primitive used to compute what an unprivileged UserOp sender (a "solver"/gas sponsee submitting a sponsored ERC-4337 UserOp through this paymaster) is charged in ERC-20 tokens for gas: [1](#0-0) 

```solidity
function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
    (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

    if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
    if (block.timestamp - updatedAt > maxOracleAge) {
        revert StaleOraclePrice(address(oracle), updatedAt);
    }
    ...
}
```

This is called from `_tokenPrice()` for both the native-asset oracle and each registered token's oracle: [2](#0-1) 

The two guards mirror only the *first half* of the original vulnerability class (`answer == 0` and staleness). Chainlink aggregators internally clamp `answer` to a configured `[minAnswer, maxAnswer]` range; when the real off-chain price crosses that boundary, the aggregator keeps posting the boundary value with a normally-updating `updatedAt` (this is precisely why the original report calls out that recency alone is insufficient — the saturated value is "fresh" but wrong). Because `_getOraclePrice` never fetches or compares against `minAnswer`/`maxAnswer`, a saturated feed for either `nativeOracle` or any `tokenConfigs[token].tokenOracle` is silently accepted as a valid, current price and fed directly into the gas-cost/token-cost formula that governs both `_prefund` charging and `swapAndDeposit`'s minimum-output calculation.

### Impact Explanation
`_tokenPrice()`'s output directly sets how many ERC-20 tokens are pulled from a sponsored UserOp sender for a given amount of gas, and `swapAndDeposit`'s `amountOutMin` (its only slippage protection) is derived from the same saturated inputs: [3](#0-2) 

If a registered fee token's USD price drops (or the native asset's price rises) enough to hit the feed's `minAnswer`/`maxAnswer` clamp, the paymaster will systematically under-price gas relative to the true market rate for as long as the feed remains saturated. Any unprivileged party submitting sponsored UserOps through this paymaster during that window pays materially less in tokens than the gas actually cost, draining the paymaster's EntryPoint deposit and accumulated token surplus — a direct, permissionless loss of protocol/treasury funds. The reverse direction (overcharging users) is also possible and constitutes an unauthorized-app-action-style harm to legitimate users. `swapAndDeposit`'s `amountOutMin` computed from the same tainted price similarly fails to bound slippage correctly, letting a saturated-price swap execute at a bad rate.

### Likelihood Explanation
This requires no privileged access and no compromise of keys or governance — it is purely a function of the underlying market moving outside the Chainlink feed's configured deviation bounds (a documented, real-world occurrence for volatile or de-pegging assets), combined with any ordinary user/solver submitting a sponsored UserOp during that window. The contract's own documentation acknowledges dependence on oracle correctness ("bounding exposure to the residual allowance even against a malicious oracle") but the mitigation described (small permit amounts) does not close this gap for the swap/pricing math itself, and does not eliminate exploitable mispricing.

### Recommendation
- In `_getOraclePrice`, additionally read `minAnswer`/`maxAnswer` for the aggregator (via `AggregatorV2V3Interface`/underlying aggregator, or by configuring them alongside `TokenConfig`/`nativeOracle` at registration time) and revert if `answer <= minAnswer || answer >= maxAnswer`, consistent with the existing `revert`-based validation style.
- Alternatively, maintain an off-chain-configured sanity band per oracle (min/max USD price) that governance can update via the existing `RequestKind` governance flow, and enforce it the same way `maxOracleAge` is enforced.

### Proof of Concept
1. Register a token whose Chainlink feed has `minAnswer = X` configured (as all production Chainlink feeds do).
2. Simulate the underlying market price falling below `X` (as `MockOracle` in the test suite does not model `minAnswer`, this is testable by pointing `_getOraclePrice` at a mock that returns a fixed "clamped" `answer` with a continuously updating `updatedAt`, mirroring real aggregator behavior): [4](#0-3) 
3. Call `paymaster.getTokenPrice(token)` / submit a sponsored UserOp through `fetchDetails`/`_prefund`. The paymaster accepts the clamped `answer` because it only checks `answer <= 0` and `block.timestamp - updatedAt <= maxOracleAge`, both of which hold for a saturated-but-fresh feed.
4. The resulting `_tokenPrice()` misprices gas relative to the true market rate, letting the caller under-pay (or forcing another user to over-pay) for the duration of the saturation — draining the paymaster's deposit/surplus over repeated sponsored operations.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
