### Title
Dogecoin address checksum is never verified, allowing withdrawals to unowned addresses - ([File: packages/intents-sdk/src/lib/validateAddress.ts])

### Summary
`validateDogeAddress` only checks a base58 character-set/length regex and never decodes/verifies the base58Check sha256d checksum, unlike the Bitcoin, Tron, Litecoin, and Dash validators in the same file. A Dogecoin `destinationAddress` with a corrupted checksum (e.g., one flipped trailing character) still matches the regex, so `validateAddress` returns `true`, `PoaBridge.validateWithdrawal` accepts it, and `createWithdrawIntentPrimitive` embeds it verbatim in the `WITHDRAW_TO:<address>` memo sent to the PoA relayer.

### Finding Description
The broken equality: DESTINATION TRUTH — "address paid" must equal "a valid, checksum-correct address the caller controls." `validateDogeAddress` at [1](#0-0)  is:
```
function validateDogeAddress(address: string) {
	return /^[DA][1-9A-HJ-NP-Za-km-z]{25,33}$/.test(address);
}
```
This is purely a regex check on charset/length/prefix. It never calls `base58.decode` or verifies the trailing 4-byte sha256d checksum, unlike its siblings in the same file: `validateBtcBase58Address` (lines 140-158), `validateTronBase58Address` (lines 384-403), `validateLitecoinBase58Address` (lines 537-567), and `validateDashAddress` (lines 801-831), all of which decode and compare `sha256(sha256(payload)).subarray(0,4)` against the trailing bytes.

`PoaBridge.validateWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:181-188`) rejects only when `validateAddress(...) === false`. Since a checksum-corrupted Doge string still matches the regex, `validateAddress` returns `true` and no error is thrown. The function then proceeds through `compareAddresses` (self-address check) and amount checks, none of which re-validate the base58 structure, and finally `createWithdrawIntentPrimitive` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts:6-26`) writes `WITHDRAW_TO:<address>` into the intent memo verbatim (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts:20-23,42`). Base58Check strings with a corrupted checksum still decode to *some* 21-byte payload (version + hash160), but that hash160 is essentially arbitrary/unintended — it is not the hash160 the user derived their address from, so the relayer would pay out to an address nobody controls (or the relayer/bridge, operating off-chain against Dogecoin's own consensus rules, would itself reject the malformed checksum before broadcasting — but the SDK provides no such guarantee and does not perform its own checksum validation).

### Impact Explanation
If the PoA relayer trusts the SDK-validated `destinationAddress` (or if any other SDK consumer skips its own additional checksum validation), an intent gets signed and submitted with `memo: "WITHDRAW_TO:<checksum-broken-address>"`. Funds would be debited from the user's NEAR intents balance and the relayer would attempt payout to a functionally unrecoverable Dogecoin address (checksum mismatch means the derived hash160 is not one the user controls), matching the Critical criterion: "funds delivered to a wrong address/chain/contract with no recovery." This is repeatable on every withdrawal call for Dogecoin assets, at zero cost to the caller (any authenticated intents user constructing their own withdrawal parameters).

### Likelihood Explanation
Preconditions are minimal: caller must select `assetId` mapped to `Chains.Dogecoin` (e.g. `nep141:doge.omft.near`) and supply a Doge-formatted `destinationAddress` string of correct length/charset but with one or more corrupted checksum bytes. No special privileges, RPC manipulation, or relayer collusion needed — this is purely a client-side/SDK format gate. Feasibility is high since generating such a string is trivial (flip a character in a real address, keeping it within the regex's charset and length bounds).

### Recommendation
Update `validateDogeAddress` to fully decode the base58 payload and verify the sha256d checksum and version byte, following the same pattern as `validateBtcBase58Address`/`validateLitecoinBase58Address`/`validateDashAddress` (decode with `base58.decode`, check length === 25, verify version byte (0x1e for Dogecoin P2PKH mainnet, 0x16 for P2SH), and verify `sha256(sha256(payload)).subarray(0,4)` equals the last 4 bytes).

function validateBtcBase58Address(address: string): boolean {
	const decoded: Uint8Array = base58.decode(address);

	// version (1) + hash160 (20) + checksum (4) = 25 bytes
	if (decoded.length !== 25) return false;

	const version = decoded[0];
	// 0x00 = P2PKH mainnet, 0x05 = P2SH mainnet
	if (version !== 0x00 && version !== 0x05) return false;

	const payload = decoded.subarray(0, 21);
	const checksum = decoded.subarray(21, 25);
	const expectedChecksum = sha256(sha256(payload)).subarray(0, 4);

	for (let i = 0; i < 4; i++) {
		if (checksum[i] !== expectedChecksum[i]) return false;
	}
	return true;
}

		amount: params.amount.toString(),

		min_gas: MIN_GAS_AMOUNT,
	};
}

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
