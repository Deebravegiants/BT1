No vulnerability found for this question.

**Reasoning:** `reflect::resolve` only resolves functions that are already declared `public` in their defining module, and returns a closure with zero captured arguments <cite repo="Alyssadaypin/aptos-core--034" path="aptos-move/framework/move-stdlib/sources/reflect.move" start="24="/> [1](#0-0) . Calling such a resolved function value is semantically identical to calling the same `public fun` directly by its ordinary name — no capabilities, signer objects, or resource-account credentials are captured or smuggled through the closure; only the plain arguments the caller supplies are passed, exactly as in a normal call. The doc comment explicitly states this is the intended security boundary: "In order to be accessible, the resolved function must be public. This prevents reflection to work around the language's modular encapsulation guarantees." [2](#0-1) 

Therefore reflection cannot turn a trusted-only, non-public internal helper into an attacker-invokable one — it can only reach functions an attacker could already call directly without using `reflect` at all. If a hypothetical module exposed a `public fun` that internally called `account::create_signer_with_capability` and transferred fungible assets to an attacker-supplied recipient, that would be a bug in that module's own visibility/access-control design (calling it directly, with no reflection needed, would already drain funds) — not a vulnerability in `reflect.move` or the reflection native itself. No such public function exists in the reviewed Aptos framework production custody modules (resource-account signer capabilities are only used inside `public(friend)`/private helper functions gated by proper caller checks, e.g. in `account.move`, `staking_contract.move`, `function_info.move`) [3](#0-2) . Additionally, `reflect::resolve` explicitly forbids resolving a small hardcoded list of framework functions whose call-site rules are enforced by the bytecode verifier [4](#0-3) , further showing the design already accounts for call-site-sensitive access.

Since the described attack requires either (a) a pre-existing bug in some other module (out of scope / speculative, not present in the reviewed custody code) or (b) reflection bypassing visibility (it does not — it only reaches already-public functions), this does not cross a real custody boundary introduced by `reflect.move`.

    /// Resolves the function referenced by `self` into a function value of type `FuncType`.
    /// Aborts with `EINVALID_FUNCTION` on failure; unreachable for targets validated via
    /// `check_dispatch_type_compatibility`, whose signatures are frozen by upgrade rules.
    public(friend) fun load_function_value<FuncType>(self: &FunctionInfo): FuncType {
        let result = reflect::resolve<FuncType>(
            self.module_address,
            &self.module_name,
            &self.function_name,
        );
        assert!(result.is_ok(), EINVALID_FUNCTION);
        result.unwrap()
    }
