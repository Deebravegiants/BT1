### Title
Duplicate input tokens merge into a single escrow bucket, enabling over-release of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron `IntentGatewayV2.placeOrder` accumulates escrow for each input token with `_orders[commitment][token] += reducedInputs[i].amount` and never rejects duplicate input tokens. When an order specifies the same token twice (or more) as separate input legs, both legs' amounts are merged into one shared per-token counter. This is the same bug class as the SecondSwap report: separate, logically distinct allocations get "inherited"/merged into one accumulator, so downstream code that assumes the counter corresponds 1:1 to a single input leg computes incorrect release amounts.

### Finding Description
In `placeOrder`, escrow is credited per input index using `+=` into a shared `_orders[commitment][token]` mapping: [1](#0-0) 

There is no check equivalent to the one added in the audited/fixed EVM contract, which explicitly rejects duplicate input tokens before crediting escrow: [2](#0-1) 

The regression test suite for the fixed contract documents exactly this class of bug and its consequence — "same-chain partial fills over-release repeated input escrow" — confirming that merging two input legs of the same token into one escrow bucket previously allowed a solver to receive more escrow than a single leg was entitled to: [3](#0-2) 

The proportional escrow release logic (`IntrinsicIntents._fillSameChain` / equivalent Tron fill logic) computes `escrowedAmount` per output-index using `order.inputs[i].amount` (the *per-leg* declared amount) as the numerator basis, while the actual escrow balance stored under that token key is the *sum* of all legs sharing that token: [4](#0-3) 

Because the Tron contract's `placeOrder` still performs unconditional `+=` accumulation without the duplicate-token guard, an order with two (or more) input legs of the same token lets a solver claim escrow computed from the merged/combined balance while withdrawal/fill code assumes the balance reflects only the single leg's declared `totalRequired`/`amount` ratio — directly analogous to how SecondSwap's `SecondSwap_VestingManager` merges a new listing's allocation into a pre-existing `stepsClaimed`/`totalAmount` bucket, corrupting the per-user accounting used to compute claimable/releasable amounts.

### Impact Explanation
An attacker (order creator) can craft an order with duplicate input-token legs to inflate the escrow "unit" a solver can claim relative to what a single output pair's fill should release, or to desynchronize the escrow ledger from the amounts the withdrawal/cancel logic expects per leg. This can result in over-release of escrowed tokens to a solver (theft of user-escrowed funds) or in a solver being under/over paid relative to fills, and in cancellation refunding an incorrect (potentially double-counted) amount for a single token key across multiple legs. This is a direct fund-safety issue in the token-escrow accounting of the Intent Gateway, reachable by any unprivileged user submitting a single `placeOrder` transaction.

### Likelihood Explanation
Likelihood is high: `placeOrder` is a fully permissionless, single-transaction entry point; no special privileges are required to submit an order with duplicate input tokens on the Tron deployment. The exact same construction was already demonstrated to be exploitable on the primary EVM `IntentGatewayV2.sol` (per the regression test comment referencing "same-chain partial fills over-release repeated input escrow"), and that fix (the duplicate-token revert) was not carried over to the Tron variant.

### Recommendation
Add the same duplicate-input-token rejection used in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`: before crediting `_orders[commitment][token]`, revert with `InvalidInput()` if the slot is already non-zero, instead of using `+=` to silently accumulate. This ensures each token in `order.inputs` maps to exactly one escrow credit, matching the assumptions made by the proportional fill/withdraw/cancel logic.

### Proof of Concept
Not independently re-verified against Tron-specific fill/withdraw code (only `placeOrder` and `_filled`/`RequestKind` declarations were retrievable for the Tron contract within the available index; the Tron contract's `fillOrder`/withdrawal implementation body was not returned by the tools in this session, so exact exploit mechanics for the Tron path could not be fully traced).
