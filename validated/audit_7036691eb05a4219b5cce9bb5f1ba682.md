### Title
Unallowlisted user-supplied route venues let a crafted swap payload execute arbitrary contract code under the victim's authorization tree and drain wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
CVE-2024-6345 is a code-injection class bug: setuptools' download functions executed commands derived from user-controlled URLs. The structural analog in XOXNO Lending is the router-strategy path: `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` accept a caller-supplied `swap` payload (`StrategySwap` XDR), forward it verbatim to the configured swap aggregator, and the aggregator dispatches hops to pool/token addresses read directly from that payload's `assets` registry. Because Soroban records child `require_auth` calls made by that third-party code under the caller's authorization tree, a malicious route can transfer any token out of the victim's wallet — not just the routed input — and it executes if the victim signs the simulated tree.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` authorizes exactly one input-token transfer to the router and then invokes `router.execute_strategy(&controller, &amount_in, swap)` with the caller-supplied bytes, measuring only input/output balance deltas afterward (`RouterOverspend`, `NoSwapOutput`) [1](#0-0) . The `swap` bytes decode to `StrategyPayload`, whose `assets` registry holds arbitrary `Address` values and whose `ops` instruction stream picks venues and pools purely by index [2](#0-1) . `dispatch_hop` then calls venue adapters against `hop.pool` — a payload-named address with no allowlist — so attacker-controlled contract code runs inside the swap call [3](#0-2) .

That code inherits the caller's authorization context: when a rogue "pool" calls `token.transfer(victim, attacker, x)` on an unrelated token, recording mode attaches the transfer to the victim's auth entry and enforcing mode executes it if the victim signs the simulated tree. The threat model itself describes this exposure — "a route can put third-party code on the call stack below the caller's authorization ... The loss is then the caller's wallet, not the routed amount" — and the harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates a rogue pool pulling an unlisted wallet token from Alice during `swap_collateral` [4](#0-3) . The controller's measured-output check does not bound this loss, because the stolen transfer is orthogonal to the swap's input/output deltas [5](#0-4) .

### Impact Explanation
Theft of user funds. An unprivileged attacker deploys a rogue venue contract, embeds its address in the `assets` registry of a `StrategyPayload`, and gets a victim to execute a strategy (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, or direct `execute_strategy`) with that route. During the hop, the rogue venue issues `token.transfer(victim, attacker, amount)` for any token the victim holds; the victim's signed auth tree covers it, so the transfer succeeds regardless of the swap's economics. The controller's `RouterOverspend`/`NoSwapOutput` checks see a normal swap and cannot detect or bound the wallet drain.

### Likelihood Explanation
Reaching the path requires the victim to sign a transaction whose auth tree contains the injected child transfer — i.e., serving a poisoned route through a compromised/malicious quoting front-end or social engineering. Simulation honestly records the child entry, so a careful client can refuse it, but most users sign the simulated tree as-is. There is no on-chain mitigation: the router intentionally keeps no venue allowlist and the controller intentionally defers to payload-specified addresses. Per the audit's own threat model, the protocol's defense is entirely off-chain (client-side route inspection), which is precisely the "user-controlled input reaches a dangerous function" condition the CVE class describes.

### Recommendation
Constrain route execution on-chain rather than relying on clients to inspect auth trees:
- Maintain an on-chain allowlist of venue pool addresses (or venue share/pool WASM hashes) in the swap-aggregator, set by the router owner, and have `dispatch_hop` reject hops whose `pool` is not registered.
- Alternatively, pin each venue to a small set of known contract WASM hashes and verify `pool`'s executable before invoking it, so payload bytes can only select among audited pool implementations.
- At minimum, have the controller refuse `swap` payloads whose `assets` registry contains addresses outside a governance-curated set for the strategies it sponsors.

### Proof of Concept
The repo already contains the exploit shape in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `RogueHopPool::swap` reads a stored `(victim, wallet_token, to, amount)` plan and calls `token::Client::transfer(victim, to, amount)` when invoked as a route hop [6](#0-5) . A victim calls `controller.swap_collateral(caller, account_id, asset_in, amount_in, asset_out, route)` where `route` is a `StrategyPayload` whose `assets` registry includes the rogue pool address; the controller authorizes the input transfer and calls `execute_strategy` [7](#0-6) ; the router decodes the payload and dispatches the hop to the payload-named pool [8](#0-7) ; the rogue pool's nested `transfer` is appended under the victim's authorized invocation and drains an unrelated wallet token while the swap still returns a fair-looking output that passes `verify_router_output`.

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

/// Attacker-deployed "pool". `amount == 0` is the benign control.
#[contract]
pub struct RogueHopPool;

#[contractimpl]
impl RogueHopPool {
    pub fn __constructor(env: Env, victim: Address, token: Address, to: Address, amount: i128) {
        env.storage()
            .instance()
            .set(&symbol_short!("PLAN"), &(victim, token, to, amount));
    }

    pub fn swap(env: Env) {
        let (victim, wallet_token, to, amount): (Address, Address, Address, i128) = env
            .storage()
            .instance()
            .get(&symbol_short!("PLAN"))
            .expect("plan is set by the constructor");
        if amount > 0 {
            token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
        }
    }
}
