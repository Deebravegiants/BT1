### Title
Webhook Shop/Topic/ID Headers Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC signature to the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values — all of which come from unauthenticated HTTP headers — are trusted and passed straight into the registered handler after HMAC validation succeeds.

### Finding Description
`Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which checks the HMAC against `request.to_signable_string`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` — the identity fields that the handler actually acts on (`WebhookMetadata.new(topic:, shop:, body:, api_version:, webhook_id:)`) — are pulled directly from HTTP headers that are never part of the signed material: [3](#0-2) [4](#0-3) 

The equality the code implicitly assumes is: `bytes verified (raw body) == bytes acted on (shop/topic/webhook_id headers)`. That equality does not hold — the signature only proves the body is untampered, it says nothing about which shop, topic, or webhook the body belongs to.

### Impact Explanation
Any internet-reachable actor who can obtain one valid `(raw_body, hmac)` pair — for example by installing the target app on their own store and capturing a genuine webhook Shopify sends them — can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers to point at a victim shop. `HmacValidator.validate` will still succeed (it only checks the body), and the app's registered handler will process the attacker's data believing it originated from the victim shop. This is a cross-tenant data-integrity/authentication issue: the handler is invoked with attacker-controlled `shop`/`topic`/`webhook_id` while the app has no gem-level assurance those fields are genuine.

### Likelihood Explanation
No credentials, TLS interception, or privileged access are required — only the ability to (a) receive one legitimate webhook for an attacker-owned shop (trivial for anyone who can install/trial the app) and (b) send an HTTP POST directly to the app's public webhook URL with modified headers. This is squarely within reach of an unprivileged internet user.

### Recommendation
Include the identity-relevant fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document that host applications must independently verify the `shop` header corresponds to a known, previously-installed store before acting on webhook data, since the gem itself provides no such binding.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; capture a genuine webhook POST (raw body `B` and header `X-Shopify-Hmac-Sha256: H`) sent by Shopify to the app's webhook endpoint.
2. Replay the same body `B` and `X-Shopify-Hmac-Sha256: H` directly to the app's public webhook endpoint, but set:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - `X-Shopify-Topic: <topic of choice registered by the app>`
   - `X-Shopify-Webhook-Id: <arbitrary>`
3. `ShopifyAPI::Webhooks::Request.new` builds successfully (all required headers present), and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against `H`.
4. The app's handler executes with `shop: "victim.myshopify.com"`, `body: JSON.parse(B)`, processing attacker-controlled data as if it belonged to the victim's store.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
