### Title
Webhook shop-domain identity spoofing due to HMAC not covering shop, topic, or webhook-id headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content solely from the raw HTTP body, while the `shop` (tenant identity), `topic`, and `webhook_id` fields are read directly from unauthenticated HTTP headers and passed downstream to the app's webhook handler without any cryptographic binding to the HMAC signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.) with no relation to the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC over the raw body via `HmacValidator.validate`, then immediately trusts `request.shop` and `request.topic` to build the `WebhookMetadata` object handed to the app's registered handler: [3](#0-2) 

`HmacValidator.validate_signature` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the received signature — for a `Webhooks::Request`, `to_signable_string` is just the raw body, so the shop/topic/webhook_id headers are entirely outside the signed data: [4](#0-3) 

The identity binding this breaks is: `HMAC-verified(bytes)` should equal `bytes-that-determine-shop-identity`, but here `HMAC-verified(raw_body)` ≠ `shop header used for tenant attribution`. Any entity capable of obtaining one genuine `(raw_body, hmac)` pair for a given app — e.g., an unprivileged attacker who installs the target app on their own store (a normal, unprivileged action any internet user can perform) and receives a real webhook — can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) headers to any value they choose. `HmacValidator.validate` still succeeds because it only checks the body bytes, and the app's handler will process the payload believing it originates from the spoofed shop.

### Impact Explanation
This breaks the tenant identity guarantee that `Registry.process`/`WebhookMetadata` is supposed to provide to app developers: the `shop` value handed to `WebhookHandler#handle` is not authenticated by Shopify at all, only the body content is. Depending on how the host application's handler uses `WebhookMetadata#shop` (commonly used to look up the tenant's stored session/access token, trigger data mutations, or decide on subscription/billing lifecycle for `shop/redact`, `app/uninstalled`, etc.), this enables cross-tenant confusion: an attacker-controlled shop's legitimate webhook body can be attributed to a victim shop of the attacker's choosing, or a victim's replayed webhook body can be attributed to a topic (e.g., `app/uninstalled`, `shop/redact`) different from what was actually signed. This falls under "cross-tenant access" territory since the shop attribution — the core tenant boundary — is unauthenticated.

### Likelihood Explanation
High. Any unprivileged party who can install the target Shopify app on a store they control can trivially capture a valid `(body, x-shopify-hmac-sha256)` pair from a real webhook delivery (no special access to `client_secret` needed) and then replay it directly to the app's public webhook endpoint with a forged `x-shopify-shop-domain`/`x-shopify-topic` header, since nothing in this gem's `Request`/`Registry.process` code verifies these headers are bound to the signed body.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable content (or otherwise cryptographically bind them, e.g. by having Shopify sign a canonical string containing these fields) so `HmacValidator.validate` fails if any of them are altered independently of the body. Short term, document prominently that `WebhookMetadata#shop`/`topic` are not covered by the HMAC and must not be trusted for authorization decisions without additional verification (e.g., cross-checking against a known/installed shop list).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install any internet user can do) and configures/triggers a webhook (e.g., `orders/create`) — capturing the real `raw_body` and the corresponding `x-shopify-hmac-sha256` value computed by Shopify with the app's `client_secret`.
2. Attacker sends a POST request to the app's webhook endpoint with the same `raw_body`, the same `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`, e.g. `shop/redact`).
3. `ShopifyAPI::Webhooks::Registry.process` runs `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — validation succeeds because the body is unchanged.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` from the forged headers and invokes the app's handler, which now believes the (attacker-supplied) topic/body legitimately originated from `victim-shop.myshopify.com`. [3](#0-2) [5](#0-4)
