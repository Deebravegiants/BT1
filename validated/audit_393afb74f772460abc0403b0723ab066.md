### Title
Missing input validation in Tron `IntentGatewayV2.setParams`/`UpdateParams` can permanently brick order placement - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) omits the bounds and zero-address checks that the canonical EVM `IntentGatewayV2`/`IntentsBase._validateParams` enforces (`evm/src/apps/intentsv2/IntentsBase.sol:592-628`). Both `setParams` (one-time admin init) and the `RequestKind.UpdateParams` branch of `onAccept` write `Params`/`DestinationFee` values straight into storage with no validation, mirroring exactly the "unbounded `boosterMultiplier`/`pointsPerBlock`" bug class from the external report: a value that is technically an unbounded `uint256` can be set to a value that causes downstream arithmetic to revert for every ordinary user thereafter.

### Finding Description
In the reference implementation, `IntentsBase._validateParams` rejects `protocolFeeBps >= 10_000`, `surplusShareBps > 10_000`, zero/EOA `host`/`dispatcher`, and EOA `priceOracle`, and `_updateParams` additionally rejects any `destinationFeeBps >= 10_000`: [1](#0-0) 

The Tron fork's `setParams` performs none of this: [2](#0-1) 

and its `onAccept` handler for `RequestKind.UpdateParams` writes `_params` and `_destinationProtocolFees` directly from the decoded message body with no bound checks at all: [3](#0-2) 

`placeOrder` — the unprivileged, user-facing entry point every intent placer calls — then computes the protocol fee unchecked: [4](#0-3) 

If `protocolFeeBps` (either the global `_params.protocolFeeBps` or a per-destination `_destinationProtocolFees[hash]`) is ever set to `>= 10_000`, then for any `originalAmount`, `protocolFee = originalAmount * protocolFeeBps / 10_000 >= originalAmount`, so `originalAmount - protocolFee` underflows. Because the contract targets Solidity `^0.8.24` (checked arithmetic), this reverts every single `placeOrder` call unconditionally — there is no way to place any order on that destination (or globally, if it is the default fee) once such a value lands in storage. Similarly, an unvalidated `host`/`dispatcher` set to the zero address bricks `placeOrder`'s calls to `IDispatcher(hostAddr).host()`/`.feeToken()`/`.uniswapV2Router()` permanently, since `_admin` is zeroed after the first `setParams` call and cannot be corrected.

### Impact Explanation
This is a route-unable-to-deliver-messages condition exactly matching the accepted-impact list: once a bad `protocolFeeBps`/`destinationFeeBps`/`host`/`dispatcher` value is written (a single non-malicious mistake in an `UpdateParams` message, or a bug in whatever builds that message), every unprivileged intent placer's `placeOrder` transaction reverts, permanently denying new orders on that gateway/destination. Because `UpdateParams` messages arrive via ordinary ISMP POST delivery (the same `onAccept` unprivileged-relayer-driven dispatch path used throughout the protocol) with no defense-in-depth validation at the receiving contract, a single malformed but "legitimately sourced" parameter update — not requiring any malicious governance action, merely a missing bounds check that the reference implementation already treats as mandatory — freezes the intent-fulfillment route indefinitely. This matches the client's own classification of the original bug ("break pools indefinitely… deny … withdrawals") and its remediation approach (adding explicit upper-bound validation), which was applied to the canonical contract but missed in the Tron fork.

### Likelihood Explanation
Medium-High: this requires no attacker capability beyond what already exists in the normal message flow — any `UpdateParams` payload with `protocolFeeBps`/`destinationFeeBps` at or above 10,000 bps (a boundary value, not an extreme one, and one the sibling implementation explicitly tests for and rejects) triggers the bug the moment the next `placeOrder` is submitted by any ordinary user. Given the reference contract in the same repo demonstrates the intended fix (bounds + zero-address checks) and explicit tests (`testRevert_SetParams_ProtocolFeeBpsTooHigh`, `testRevert_UpdateParams_DestinationFeeBpsTooHigh`), the Tron variant's omission looks like an unintentional divergence/missed backport rather than a deliberate design choice.

### Recommendation
Backport `IntentsBase._validateParams`-equivalent checks into the Tron `IntentGatewayV2`:
- Reject `protocolFeeBps >= 10_000` and `surplusShareBps > 10_000` in both `setParams` and the `UpdateParams` `onAccept` branch.
- Reject `destinationFeeBps >= 10_000` for every entry in `update.destinationFees`.
- Reject zero-address / non-contract `host`, `dispatcher`, and (if applicable) `priceOracle`.
- Consider validating `protocolFeeBps < 10_000` defensively inside `placeOrder` as well, so a future divergence cannot silently re-introduce the same DoS.

### Proof of Concept
1. Hyperbridge (or whatever legitimately dispatches `UpdateParams` messages to this gateway) sends a `RequestKind.UpdateParams` POST request with `update.params.protocolFeeBps = 10_000` (100%) or `update.destinationFees[i].destinationFeeBps = 10_000` for some destination.
2. `onAccept` (`evm/tron/contracts/apps/IntentGatewayV2.sol:644-660`) writes this value into `_params`/`_destinationProtocolFees` unconditionally — no revert occurs.
3. Any user calls `placeOrder` with a non-zero `order.inputs[i].amount` targeting that destination (or globally, if the global fee was set).
4. Inside `placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol:359-374`), `protocolFee = originalAmount * 10_000 / 10_000 = originalAmount`, so `reducedAmount = originalAmount - protocolFee = 0`... for `protocolFeeBps` strictly greater than `10_000` (e.g., `10_001`), `protocolFee > originalAmount` and `originalAmount - protocolFee` underflows, reverting the transaction under Solidity 0.8 checked arithmetic.
5. Every subsequent `placeOrder` call against that destination reverts identically — the route is permanently unable to accept new orders until another `UpdateParams` message corrects the value (and there is no on-chain way to detect/reject the bad value before it is committed, unlike the canonical `IntentGatewayV2`).

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
