### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only proves that the *body* bytes were signed by the app's `api_secret_key`; it never binds the header-derived `shop` value into that signature. Any party who can obtain one valid `(body, hmac)` pair signed with the app's secret can replay it with an arbitrary `x-shopify-shop-domain` header and have `Registry.process` treat the payload as belonging to a different, victim shop.

### Finding Description
`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from attacker-controllable HTTP headers, none of which are part of the signed string: [3](#0-2) 

`Registry.process` only checks that the body HMAC is valid, then dispatches the handler using the unverified `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

and these values are packaged verbatim into `WebhookMetadata`, which is the sole identity information handed to the app's `WebhookHandler#handle`: [5](#0-4) 

Crucially, `api_secret_key` is the app's single client secret shared across **every shop** that installs the app — it is not shop-specific. Any shop that has legitimately installed the app receives real webhooks whose bodies are signed with this same shared secret. An unprivileged merchant/tenant (an "unprivileged internet user" relative to *other* tenants of the same app) can therefore capture a `(raw_body, hmac)` pair from a webhook legitimately delivered to their own shop, and replay that exact body/HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `topic`/`webhook-id`) header to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the (unchanged) body bytes, and `Registry.process` will invoke the handler believing the event originated from the victim shop.

This is the structural analog of the reported bug class: a value that is *acted upon* (the identity-binding `shop` field, analogous to the price index) is not covered by the cryptographic verification (the HMAC, analogous to the signed price array), letting an attacker substitute it after the fact.

### Impact Explanation
This breaks the identity binding `hmac-verified-body ⇔ shop-domain-header` and allows cross-tenant webhook forgery: a webhook consumer app relying on `WebhookMetadata#shop` for tenant scoping (e.g., to select which merchant's DB record to update, or to trigger per-shop side effects) can be made to act on forged/attacker-chosen shop identifiers while still believing the HMAC proved Shopify origin. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to have access to at least one genuine `(body, hmac)` pair produced by the shared app secret — trivially obtainable by any merchant/tenant who has installed the app (a normal, unprivileged use case, not requiring `api_secret_key` itself, an access token, or any credential leak). The webhook endpoint is public by design. The only extra step is sending a crafted HTTP request with a substituted header, which is straightforward.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material, or otherwise cryptographically bind the header-derived identity fields to the HMAC verification — e.g., by having `to_signable_string` incorporate `shop`, `topic`, and `webhook_id` alongside the raw body, so that any header tampering invalidates the signature.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both driven by the same `api_secret_key`.
2. Attacker triggers or waits for a genuine webhook delivered to their own shop and records `raw_body` and the `x-shopify-hmac-sha256` header value (valid because it's genuinely signed by the shared secret). [6](#0-5) 
3. Attacker POSTs to the app's webhook endpoint reusing the same `raw_body`/`hmac` but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` passes (body/HMAC unchanged), and `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"`: [7](#0-6) 
5. The host application processes attacker-controlled data under the victim shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
