Based on the code I reviewed, the strongest analog is the `_cancelFromDest` flow in `ExtrinsicIntents.sol`, which mirrors the D3MM bug's root cause: a state-mutating step is taken that irreversibly forecloses one path to completion, without atomically guaranteeing the second half of the two-step process will actually succeed.

### Title
Destination-side cancel finalizes `_filled` before the cross-chain refund is guaranteed, permanently freezing escrow on send failure - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`_cancelFromDest` immediately writes `_filled[commitment] = order.user` and dispatches a `RefundEscrow` POST request, exactly like D3MM's `removeD3Pool()` forcing the pool into a liquidation state before the value needed to complete the process (`liquidationTarget`) is fixed. Here the "irrevocable state" is `_filled`, and the thing not fixed atomically is guaranteed delivery/authentication of the `RefundEscrow` message that alone can release the source-chain escrow.

### Finding Description
`_cancelFromDest` (evm/src/apps/intentsv2/ExtrinsicIntents.sol:297-307) sets `_filled[commitment]` unconditionally on the destination chain, then calls `_post(...)` to dispatch a Hyperbridge POST carrying `RequestKind.RefundEscrow`. Once `_filled` is set:
- The order can never be filled again on the destination (`fillOrder` checks `_filled[commitment] != address(0)` and reverts with `Filled()`).
- There is no destination-side retry or rollback path if the POST dispatch is not eventually delivered and accepted on the source chain (e.g. `_instance(order.source)` misconfiguration, authentication mismatch in `_authenticate` at line 63-67, or the source gateway being paused/upgraded incompatibly at delivery time).

On the source chain, `onAccept` (ExtrinsicIntents.sol:330-337) only releases escrow via `_withdraw` if `_authenticate` succeeds and the decoded `WithdrawalRequest` matches escrowed amounts in `_orders[commitment][token]` (`IntentsBase._withdraw`, line 451-470, reverts `UnknownOrder` on any mismatch/zero). If any of these preconditions fail — the source-side "finish" step — the order is permanently dead: destination has already foreclosed re-fill, and there is no mechanism to re-trigger or fall back to a different resolution once `_filled` has been set on the destination.

This is structurally identical to the reported M-14 pattern: step 1 (`removeD3Pool` / `_cancelFromDest`) forces an irrevocable state transition without first ensuring the data/authorization needed for step 2 to finish (`liquidationTarget` / successful cross-chain authenticated delivery) is guaranteed; step 3 (`finishLiquidation` / the source-side `_withdraw`) can be permanently blocked, and there is no recovery path back to the pre-step-1 state. ### Impact Explanation
If the `RefundEscrow` message never gets validly delivered/accepted (revert on the source side for any reason: wrong `_instance` mapping, relayer not yet authorized/rotated mid-flight per `_checkRelayer`, escrow amount mismatch, or the source gateway being upgraded/reconfigured out of sync with the destination), the escrowed input tokens on the source chain become permanently frozen: the destination has already marked the order filled/cancelled so it can never be re-filled or re-cancelled, and the source-side escrow can only be released by a correctly authenticated `RefundEscrow` (or `RedeemEscrow`) message referencing that exact commitment. This is a permanent freezing-of-funds condition, matching the Medium/High bar required.

### Likelihood Explanation
This requires cross-chain message delivery/authentication to diverge from destination-side expectations after the destination has already committed to `_filled`. This is a normal risk in any bridge-mediated finalize-then-message pattern and is triggerable by: relayer rotation timing (`setRelayer`/`migrate`), gateway instance mapping changes (`_addDeployment` racing with in-flight cancels), or governance updating `_params`/`_instances` between the two legs — all of which are reachable through ordinary/permissionless usage plus expected governance operations, not requiring a malicious actor. Likelihood is best characterized as low-to-medium (requires timing overlap of a governance/relayer change with an in-flight cross-chain cancel) but the impact (permanent fund freeze, no recovery path) is severe.

### Recommendation
Do not finalize `_filled` on the destination chain until the refund is provably deliverable, or provide a compensating recovery path:
1. Delay marking `_filled` until the source chain actually confirms/accepts the `RefundEscrow` (harder given the destination-authoritative design), OR
2. Add a governance/permissionless "finalize" or "retry" mechanism that can re-dispatch `RefundEscrow` for a commitment already marked filled-by-cancellation on the destination if the original dispatch times out or fails to be accepted, ensuring the escrow-releasing leg can always eventually be completed.
3. At minimum, ensure the POST request's `timeout` (currently `0`, meaning it never times out per `_post`) combined with strict authentication checks doesn't create a state where the message can be dropped/undelivered indefinitely with no way to reconstruct or resubmit it referencing the already-committed `_filled` state. ### Proof of Concept
Conceptual (index-only; not independently executed against a live deployment):
1. User places a cross-chain order; destination is chain B, source is chain A.
2. Before the order fills, user calls `cancelOrder` on chain B after deadline (or before, as owner). `_cancelFromDest` executes: `_filled[commitment] = order.user;` then dispatches `RefundEscrow` POST to chain A.
3. Suppose governance rotates `_instances[keccak256(chainB)]` on chain A (e.g. a gateway redeploy/migration) between dispatch and delivery, or `_relayer` is rotated such that the in-flight relayer is no longer authorized (`_checkRelayer`).
4. When the relayer submits the message to chain A's `onAccept`, `_authenticate` (comparing `_instance(request.source)` to `request.from`) or `_checkRelayer` reverts.
5. The message delivery fails permanently (no automatic retry with updated parameters is implied by the code shown); chain B's order is irreversibly `_filled`, so no further cancel/fill path exists on chain B.
6. Chain A's escrow for `commitment` remains locked in `_orders[commitment][token]` indefinitely, with no code path shown that can re-derive and redeliver a valid `RefundEscrow` for that exact commitment. [5](#0-4) 

Note: I could not verify from the indexed code whether an off-chain relayer/SDK-level retry mechanism exists that resubmits the same `PostRequestEvent` with updated routing after such a failure — this is a gap in what the index surfaces (SDK `OrderCanceller.ts` only streams status via the indexer and does not show a resubmission path for a rejected `onAccept`). If a Devin session with full repo access confirms such a retry/resubmit path exists, this weakens the freezing-of-funds impact to a temporary delay rather than permanent freeze.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
