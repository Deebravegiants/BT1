### Title
CatFee API key/secret logged in plaintext on relayer startup - (File: tesseract/messaging/tron/src/lib.rs)

### Summary
The TRON relayer's bandwidth/energy purchasing integration (CatFee) logs its full configuration struct — including the plaintext `api_key` and `api_secret` used to authenticate and HMAC-sign every CatFee order request — to the relayer's log stream at `info` level on every startup.

### Finding Description
`CatFeeConfig` derives `Debug` and stores `api_key: String` and `api_secret: String` in plaintext with no masking `Debug`/`Display` implementation: [1](#0-0) 

When a TRON relayer operator configures `catfee_api_key`/`catfee_api_secret` (to enable bandwidth/energy purchasing before broadcasting transactions), `TronClient::new` constructs the `CatFeeConfig` and immediately logs it in full with the `{:#?}` (pretty Debug) formatter: [2](#0-1) 

This is functionally the same bug class as GHSA-6w87-g839-9wv7 (Argo CD logging Helm OCI repo credentials): a long-lived API credential used to authenticate against a remote service is written verbatim into the process log stream instead of being redacted, purely because a config/struct value was passed to a debug-formatting log call.

The `api_secret` is the HMAC-SHA256 signing key for every CatFee order request (`generate_signature` in `catfee.rs:93-101`), and the `api_key` is sent as the `CF-ACCESS-KEY` header on every request (`catfee.rs:153`, `catfee.rs:203`). Anyone with read access to the tesseract relayer's process logs — stdout/stderr capture, a log aggregator, container log driver, or `docker logs` (explicitly documented as the operator's way to access relayer logs: `docker logs -f tesseract`) — can recover both credentials.

### Impact Explanation
With the leaked `api_key`/`api_secret`, an attacker can forge authenticated requests to the CatFee API on the relayer operator's account: create energy/bandwidth purchase orders billed to the operator's CatFee balance, and potentially redirect delegated energy/bandwidth to an address of the attacker's choosing (since `create_order` takes an arbitrary `receiver_address`). This is a direct funds-drain vector against the relayer operator's CatFee account balance, distinct from and outside the operator's TRON private key exposure. It does not affect message-delivery correctness or on-chain committed state, but it does cause concrete financial loss (unauthorized CatFee order spend) for the relayer operator whose logs are read.

### Likelihood Explanation
This fires unconditionally whenever a TRON relayer is configured with CatFee credentials (`catfee_api_key`/`catfee_api_secret` present in `TronConfig`) — it happens on every single startup/restart of the relayer, at `info` log level (not behind a debug/trace flag), so it will reliably appear in any log aggregation or `docker logs` output an operator or their infra team routinely captures.

### Recommendation
Implement a custom `Debug`/`Display` for `CatFeeConfig` (or wrap `api_key`/`api_secret` in a redacting newtype, e.g. `Secret<String>`, similar to the masking pattern already used elsewhere in this monorepo for the simplex filler config's `maskToml`/`maskSecret`) so the credential fields never render in plaintext, and change the startup log line in `tesseract/messaging/tron/src/lib.rs` to print only non-sensitive fields (e.g. `api_base`, `timeout`) or a fixed `"CatFee integration enabled"` message without embedding the config.

### Proof of Concept
1. Configure a TRON relayer with `catfee_api_key = "<real key>"` and `catfee_api_secret = "<real secret>"` in the TOML config (`tesseract/messaging/tron/src/lib.rs:247-249` reads these into `CatFeeConfig`).
2. Start the relayer (`docker run ... polytopelabs/tesseract:latest --config=...`) and read its logs via `docker logs -f tesseract` as documented in `docs/content/developers/network/relayer.mdx:161-165`.
3. Observe the log line `CatFee integration enabled: CatFeeConfig { api_key: "<real key>", api_secret: "<real secret>", ... }` emitted from `tesseract/messaging/tron/src/lib.rs:257`, exposing both credentials to anyone with log access. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

	fn generate_signature(&self, timestamp: &str, method: &str, request_path: &str) -> String {
		let message = format!("{}{}{}", timestamp, method, request_path);

		let mut mac = HmacSha256::new_from_slice(self.config.api_secret.as_bytes())
			.expect("HMAC can take key of any size");
		mac.update(message.as_bytes());

		BASE64.encode(mac.finalize().into_bytes())
	}
