## Analog Found

### Title
Passphrase cache renewal logic never re-enforces `passphraseCacheMaxTtl`, allowing indefinite retention of the cached passphrase - (File: features/application/src/modules/passphrase-cache.ts)

### Summary
The Olympus finding describes a system where a time/threshold-based counter (`_status.high.count` vs `regenThreshold`/`regenWait`) is used to gate a sensitive action (fund redeployment) without ever re-validating the actual underlying condition (price back inside the wall). Once the counter-based gate is satisfied, the system acts as if the condition holds indefinitely, even though the real state never recovered. Hydra's `PassphraseCache` module has the same structural flaw: a "hard cap" configuration value (`maxTtl`) is only checked on one code path, and a separate "renewal" mechanism (`inactiveAt`) can be triggered repeatedly to keep the gate permanently satisfied, bypassing the hard cap entirely.

### Finding Description
`PassphraseCache.get()` decides whether to hand back the cached passphrase (used for `#autoUnlock`, i.e., unlocking the wallet without the user re-entering the passphrase) using two disjoint checks: [1](#0-0) 

```
if (passphrase) {
  if (inactiveAt) {
    if (inactiveAt + ttl > Date.now()) {
      return passphrase   // <-- no maxTtl check on this branch
    }
  } else if (addedAt + this.#maxTtl > Date.now()) {
    return passphrase
  }
  void this.clear()
}
```

`addedAt + this.#maxTtl` (the intended hard ceiling configured via `passphraseCacheMaxTtl`, see [2](#0-1) ) is only consulted when `inactiveAt` is falsy. As soon as `inactiveAt` is set once, the `maxTtl` bound is permanently bypassed for the remainder of that cache's lifetime — validity is thereafter governed solely by `inactiveAt + ttl`, i.e., a sliding auto-lock timer window (`ttl`, default 60 minutes, see [3](#0-2) ).

`inactiveAt` is set by `#scheduleClear`/`scheduleClear()`, which is invoked from `Application.restartAutoLockTimer()`: [4](#0-3) [5](#0-4) 

`restartAutoLockTimer` is exposed on the public SDK/API surface as `exodus.application.restartAutoLockTimer()` (also aliased under the deprecated `wallet.restartAutoLockTimer`): [6](#0-5) [7](#0-6) 

Any caller of this API method (UI code triggered on normal user interaction, or any code path with access to the headless API surface) resets `INACTIVE_AT_KEY` to `Date.now()`. As long as this call happens more often than `ttl` (the auto-lock timer interval), the cached passphrase's expiry window keeps sliding forward forever and `maxTtl` — the configured absolute cap meant to bound how long a plaintext passphrase can live in session storage — is never re-evaluated again for that cache entry. `set()` (called after a manual unlock) also never clears `INACTIVE_AT_KEY`, so a previously-established sliding window persists across passphrase changes: [8](#0-7) 

This mirrors the root cause of the Olympus bug: a "recovery/renewal" signal (`inactiveAt` renewal / `_status.high.count`) is trusted to keep an action valid without re-checking the actual hard boundary (`maxTtl` / true market price), so the intended cap is silently bypassed for as long as the renewal keeps firing.

### Impact Explanation
`maxTtl` (`passphraseCacheMaxTtl`) is the wallet's designed hard limit on how long a decrypted/cached passphrase may sit in (session) storage. Bypassing it means the passphrase — a secret capable of unlocking the wallet and, indirectly, all signing/key material — can remain retrievable from storage indefinitely instead of being bounded, as long as `restartAutoLockTimer`/`changeTtl` keeps being invoked more frequently than the auto-lock `ttl`. Any code or attacker with the ability to read session storage (e.g., a compromised/malicious extension component, or process with storage access) is not limited by the wallet's configured `maxTtl` security control, extending the secret-disclosure exposure window far beyond intended policy. This is a genuine secret-disclosure/auth-bypass class issue in an unprivileged-reachable code path, matching the required impact category.

### Likelihood Explanation
`restartAutoLockTimer` and `changeTtl` (via `changeLockTimer`) are both legitimately part of normal app operation and are reachable by any code with access to the `exodus.application`/`exodus.wallet` API surface — no special privilege is required, only the ability to invoke a documented public SDK method repeatedly (e.g., on every user interaction, as its name and stated purpose imply it should be called on activity). No exotic parameterization or attacker-controlled external price feed is needed as in the original report — merely calling a normal, intended API method at a normal cadence is sufficient to keep `inactiveAt` fresh and therefore bypass `maxTtl` permanently, making this more directly reachable than the original finding.

### Recommendation
Enforce `maxTtl` unconditionally as an absolute bound, independent of the `inactiveAt` sliding-window path, e.g.:
```
if (addedAt + this.#maxTtl <= Date.now()) { clear(); return }
if (inactiveAt) { if (inactiveAt + ttl > Date.now()) return passphrase }
else if (addedAt + this.#maxTtl > Date.now()) return passphrase
```
Also clear `INACTIVE_AT_KEY` whenever a new passphrase is cached via `set()` so stale sliding-window state cannot leak across sessions.

### Proof of Concept
1. Configure `cachePassphrase: true` with `passphraseCacheMaxTtl` (e.g., 60 minutes) via `application()` feature config — [2](#0-1) .
2. Unlock the wallet with a passphrase; `PassphraseCache.set()` stores `addedAt = Date.now()` — [8](#0-7) .
3. Call `exodus.application.restartAutoLockTimer()` (or `changeLockTimer`) at an interval shorter than the auto-lock `ttl` (e.g., every 30 minutes when `ttl` is 60 minutes), simulating routine UI activity — this repeatedly sets `INACTIVE_AT_KEY = Date.now()` via `scheduleClear()` — [4](#0-3) .
4. Let more than `maxTtl` elapse since step 2 (e.g., 3 hours) while step 3 keeps being invoked.
5. Call `PassphraseCache.get()` (indirectly via `#autoUnlock`): because `inactiveAt` is always recent, the `addedAt + maxTtl` check at line 75 is never reached, and the passphrase is still returned as valid — [9](#0-8)  — demonstrating the `maxTtl` hard cap has been bypassed.
