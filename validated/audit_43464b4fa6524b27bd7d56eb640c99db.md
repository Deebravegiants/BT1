## Title
Webhook HMAC Verification Does Not Cover `shop`, `topic`, or `webhook_id` — Signed Body Can Be Replayed Under a Different Shop Identity - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers and handed to the app's webhook handler as trusted, tenant-identifying data. This breaks the intended binding: `shop` used by the handler for tenant identification ≠ `shop` covered by the verified HMAC.

### Finding Description
`Registry.process` validates the webhook by calling `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string`: [1](#0-0) 

`to_signable_string` is defined to be exactly `@raw_body` — nothing else: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled unauthenticated from HTTP headers, with no cryptographic tie to the HMAC that was validated: [3](#0-2) 

After `HmacValidator.validate` succeeds (proving only that `raw_body` was HMAC-signed with `api_secret_key`), `Registry.process` immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` and forwards them into `WebhookMetadata`, which is what host application handlers use to select the tenant/session context: [4](#0-3) 

This is exactly the pattern called out in the analog rules: a field (`shop`) that is *acted on* (used as the tenant identity for dispatching webhook data) but is *not covered by the HMAC* that gates trust in the request. Contrast this with the OAuth flow's `AuthQuery`, where `shop` is one of the query parameters that is itself part of the signed content, so `shop` is bound to the HMAC there. No such binding exists for `Webhooks::Request`.

### Impact Explanation
An attacker who legitimately installs the target Shopify app on their own store (an "unprivileged internet user" with respect to any other merchant's data) will receive real webhook deliveries from Shopify for their own store — each with a body and an HMAC signature computed by Shopify using the app's `api_secret_key`, which the attacker never needs to know. Because the signature covers only the raw body, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` will still pass (the body/HMAC pair is genuinely valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming this payload belongs to the victim shop. Any host application that uses `data.shop` to select which tenant record to update (the standard, documented usage pattern shown in `docs/usage/webhooks.md`) will apply attacker-supplied data under the victim's tenant identity — a cross-tenant data injection into another merchant's account, which meets the Critical bar (cross-tenant access) defined by the rules.

### Likelihood Explanation
The prerequisite is modest: the attacker only needs to be able to install the app on any store they control (standard, unprivileged Shopify merchant/dev-store access) in order to legitimately receive a validly-signed webhook body/HMAC pair from Shopify — no leaked secrets, TLS interception, or privileged access are required. They then simply resend that payload to the app's public webhook endpoint with a forged shop-domain header. Because `to_signable_string` unconditionally returns only `@raw_body`, this works for every topic and every host application built on this gem's documented webhook-processing API.

### Recommendation
Bind the identity-bearing headers into the verified signable content, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the HMAC before they are trusted. At minimum, `Utils::HmacValidator.validate` (or `Registry.process`) should reject/flag webhooks where the `shop` header does not correspond to a shop the receiving app actually expects for that specific webhook subscription (e.g., by having callers supply the expected shop and comparing it, since Shopify's HMAC scheme for webhooks does not sign headers). Document prominently that `request.shop` is unauthenticated and must not be used as the sole tenant selector without additional verification (e.g., matching against `webhook_id` registered per-shop, or validating the shop is one that has an active, previously-established session in the host app's own session storage).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (self-service, no special privilege needed) and triggers a webhook event (e.g. `orders/create`).
2. Shopify sends the app's webhook endpoint a raw JSON body `B` with header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and the valid HMAC value (they receive both directly from Shopify; no secret disclosure needed).
4. Attacker POSTs the same `B` and same HMAC header to the app's webhook endpoint again, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `raw_body` against the HMAC — it never checks the `shop` header. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` then dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` to the handler, which the host app uses to write/update data under `victim-shop`'s tenant record.
