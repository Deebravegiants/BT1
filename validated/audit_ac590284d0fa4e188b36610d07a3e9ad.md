### Title
Unsigned cross-chain calldata dispatch trusts attacker-controlled `message.from` as a substrate origin - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`Pallet::on_accept` in `pallet-hyper-fungible-token` decodes the ABI-encoded, cross-chain `Message` body (fully attacker-controlled, since it comes from an ISMP POST request delivered by any relayer) and, if `message.data` is non-empty, SCALE-decodes it into a `SubstrateCalldata{ signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` and dispatches the embedded `runtime_call` [1](#0-0) . When `substrate_data.signature` is `None`, the dispatch origin is derived directly from `message.from` — an attacker-supplied byte field inside the same untrusted message — with no cryptographic proof that the actual caller controls that address [2](#0-1) . The decoded `runtime_call` is then dispatched with `RawOrigin::Signed(origin)`, subject only to `BaseCallFilter` [3](#0-2) .

### Finding Description
This is the bug-class analog to CWE-502 (deserialization of untrusted data driving unintended execution): here, the "untrusted, attacker-supplied bytes" are the ABI-decoded `Message.from`/`Message.data` fields carried inside an ISMP `PostRequest`, which the destination pallet trusts as an authentication assertion for dispatching a signed extrinsic, instead of requiring a real signature check on every path.

Concretely:
1. `on_accept` decodes `Message` from the POST request body via `Message::abi_decode(&body)` [4](#0-3) . Every field of `Message` — including `from` and `data` — is fully controlled by whichever source-chain contract/account originated the transfer; it is not otherwise authenticated (only `ContractToAsset::<T>::get(source, &from)` binds the *contract* address, not the embedded sender).
2. If `message.data` is non-empty, it's SCALE-decoded into `SubstrateCalldata { signature, runtime_call }` [5](#0-4) .
3. The `signature` field is *optional*. When absent, the code falls back to deriving the dispatch origin straight from `message.from` via `T::EvmToSubstrate::convert` (for EVM sources) or a raw 32-byte copy (for substrate sources) [6](#0-5) , with **no signature or proof-of-control check at all** on this branch.
4. `runtime_call` is then decoded as `T::RuntimeCall` and dispatched with `RawOrigin::Signed(origin)` [7](#0-6) , gated only by the `BaseCallFilter`, which filters dispatchable *kinds*, not callers.

Because `message.from` is just a byte array embedded in the sender-controlled cross-chain message (comparable to how a deserializer blindly trusts fields of an untrusted payload as authoritative), any account able to dispatch a token transfer to the pallet (from any registered EVM/Substrate peer contract) can set `from` to any 20/32-byte value it likes and attach arbitrary `runtime_call` bytes. This causes the destination pallet to execute an arbitrary allowed runtime call as `RawOrigin::Signed(derived_account)` for an account the attacker never proved control of.

### Impact Explanation
This allows any unprivileged cross-chain sender (an "unprivileged token bridger", squarely in scope) to have the destination chain execute arbitrary, filter-permitted `RuntimeCall`s "signed" by an account the attacker does not control, provided they can guess or target an `EvmToSubstrate`-derived account (deterministic function of an EVM address they fully choose in `from`). Any dispatchable not blocked by `BaseCallFilter` — e.g. asset transfers, staking operations, governance votes, or other pallet calls reachable from a signed origin — can be triggered against that derived account's balance/permissions without its holder's consent. This is unauthorized app action on behalf of a spoofed origin, directly reachable from a single cross-chain message dispatch.

### Likelihood Explanation
High reachability: the calldata path is exercised on every `on_accept` call whenever `message.data` is non-empty, which is a normal, permissionless feature of the HFT bridging flow (documented as intentional "calldata execution"). No relayer collusion, governance, or privileged role is needed — only a standard token-transfer message from a registered peer contract with attacker-chosen `from`/`data`.

### Recommendation
Require signature verification unconditionally for any embedded `runtime_call` dispatch — remove the unauthenticated fallback that derives origin from `message.from` when `signature` is `None`. If the design intends to allow the token beneficiary or a self-authenticated relayer to trigger calls, bind the dispatch origin strictly to a value the message's actual source contract/account is cryptographically proven to control (e.g., always require and verify a signature, or restrict calldata dispatch to only affect the transfer beneficiary derived from the token mint itself, not an arbitrary `from`).

### Proof of Concept
1. Attacker controls (or uses) a registered peer contract on an EVM source chain that can call `send()`/dispatch an HFT POST request.
2. Attacker crafts `Message.data` = SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <encoded RuntimeCall performing some allowed action, e.g. a token transfer_all from an account> }`, and sets `Message.from` to the 20-byte EVM address whose `EvmToSubstrate::convert` maps to the victim account they want to impersonate.
3. Relayer delivers the POST request; `on_accept` decodes the message, takes the `else` branch (no signature) at [6](#0-5) , and dispatches `runtime_call` as `RawOrigin::Signed(origin)` with `origin` derived purely from the attacker-supplied `from` field [8](#0-7) .
4. The call executes with no proof the attacker controls that account.

Note: I was unable to fully confirm within this session whether the EVM-side `HyperFungibleToken.sol`/`WrappedHyperFungibleToken.sol` `send()` function binds `Message.from` to `msg.sender` (which would reduce, but likely not eliminate, the practical blast radius) — the grep for the Solidity `send()` construction of `Message.from` did not complete before the session ended. If `from` is bound to `msg.sender` on all legitimate contract paths, the severity is reduced to "self-impersonation of one's own derived account" (still bypasses intended signature-based authorization design) rather than fully arbitrary third-party impersonation. Confirming this binding (and whether any other pallet/precompile can set `from` freely) is necessary to finalize exploitability scope.
