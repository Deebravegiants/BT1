### Title
Status of the wrong same-asset withdrawal is reported by `PoaBridge.describeWithdrawal` due to index-blind matching - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`describeWithdrawal` for the POA bridge route matches the POA API's unsorted withdrawal list to a caller's `WithdrawalIdentifier` by `assetId` alone via `findMatchingWithdrawal`, never using the per-bridge `index` that `createWithdrawalIdentifiers` assigns to disambiguate multiple withdrawals of the same asset created in one NEAR transaction.

### Finding Description
When a caller batches two or more withdrawal intents for the *same* `nep141` asset (e.g., two `ft_withdraw` intents for `zec.omft.near` to two different destination addresses) within one NEAR transaction, `createWithdrawalIdentifiers` assigns them indices `0` and `1` respectively [4](#0-3) . Each `WithdrawalIdentifier` carries this `index`, but `PoaBridge.describeWithdrawal` never consults it: it calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — returning the first entry in an explicitly "unsorted" API response that matches the asset id, regardless of which of the two withdrawals it actually is [5](#0-4) . The code comment itself acknowledges: "multiple withdrawals of the same token in a single transaction are not supported" and that the POA API doesn't support this case either [6](#0-5) .

This breaks the equality that should hold between "the status returned for withdrawal `i`" and "the actual on-chain outcome of withdrawal `i`." If one of the two same-asset withdrawals completes and the other fails (e.g., is refunded due to a destination-side issue), `watchWithdrawal`/`waitForWithdrawalCompletion` for *both* identifiers can observe the *same* matched record — since `.find()` returns only the first match for both index-0 and index-1 identifiers — causing one withdrawal's status to be misreported as the other's.

### Impact Explanation
`watchWithdrawal` (in `withdrawal-watcher.ts`) turns a `"completed"` status into a resolved promise with a `txHash`, and a `"failed"` status into a thrown `WithdrawalFailedError` [7](#0-6) . An integrator relying on the SDK's per-withdrawal completion promise (e.g., `sdk.waitForWithdrawalCompletion`) to credit or refund a user could: (a) see the failed withdrawal reported as "completed" with a `txHash` belonging to the sibling withdrawal, causing it to credit the user as if funds were delivered when they were actually refunded/failed, or (b) see the completed withdrawal erroneously reported as "failed", causing a duplicate/erroneous refund path while the funds were already delivered on-chain. This matches the High-impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no malicious actor — merely a normal user or integrator batching two or more withdrawal intents of the *same* NEP-141 asset (different destinations or amounts) within a single NEAR transaction using the POA bridge route, which the SDK's public API (`createWithdrawalIntents`, multiple `WithdrawalParams`) does not prevent. Given the POA bridge is the default route for many supported tokens, and batching multiple withdrawals in one transaction is a natural usage pattern for efficiency, likelihood is moderate — it depends on integrator batching behavior rather than on adversarial input, and the divergent-outcome scenario (one succeeds, one fails) additionally requires a partial-failure condition on the bridge side.

### Recommendation
Have `findMatchingWithdrawal` respect the `index` provided in `WithdrawalIdentifier`, e.g., by filtering matches by `assetId` and then selecting by ordinal position consistent with a deterministic sort (as the existing comment suggests — sort both API results and withdrawal params by amount, since relayer fees are identical for same-token withdrawals so relative amount ordering is preserved), rather than returning `Array.prototype.find`'s first match irrespective of which of several same-asset withdrawals is being queried. Until the POA API can return this disambiguating information, `PoaBridge` should refuse (throw) rather than silently misattribute status when more than one matching withdrawal exists in the response for the given `assetId`.

### Proof of Concept
1. Build a NEAR transaction with two `ft_withdraw` intents for `nep141:zec.omft.near`: withdrawal A to `destA`, withdrawal B to `destB`.
2. `createWithdrawalIdentifiers` assigns `index: 0` to A and `index: 1` to B (same bridge route) [8](#0-7) .
3. On-chain, suppose B fails/gets refunded while A completes normally; the POA indexer returns both records in its (unsorted) `withdrawals` array, one `COMPLETED` (A) and one `REFUNDED` (B).
4. Calling `describeWithdrawal` with B's identifier (`index: 1`, `assetId: "nep141:zec.omft.near"`) invokes `findMatchingWithdrawal`, which does `withdrawals.find(...)` and returns whichever record appears first in the array — potentially A's `COMPLETED` record — reporting B (which actually failed) as `{ status: "completed", txHash: <A's tx hash> }`.
5. `watchWithdrawal` for B resolves successfully with a (wrong) `txHash`, and an integrator waiting on B's completion may credit the user for a withdrawal that never actually landed.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
