### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed by the app's `client_secret`. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers and are never bound into the signed bytes, yet `Registry.process` trusts `request.shop` and hands it, unverified, to the host application's webhook handler as the tenant identifier.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Only `@raw_body` is fed into `to_signable_string`, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from HTTP headers via `shopify_header`, none of which participate in the signature at all.

`Registry.process` verifies the HMAC and then immediately trusts the header-derived `shop`: [2](#0-1) 

The equality that should hold but doesn't:
`bytes-covered-by-HMAC (raw_body)` == `bytes-the-handler-acts-on (raw_body + shop + topic + webhook_id)`.

Because `client_secret`/`api_secret_key` is per-app (shared across every shop that installed the app), any tenant of the app can legitimately register a webhook to an endpoint they control and obtain a `(raw_body, hmac)` pair that is valid for the shared secret. That pair can then be replayed to the app's real webhook endpoint with the `X-Shopify-Shop-Domain` header (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) rewritten to name a different shop. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` forwards the forged `shop` value straight to the handler: [3](#0-2) 

The library's own documentation reinforces the false assumption that the whole request, not just the body, is authenticated: "This will verify the request did indeed come from Shopify." [4](#0-3) 

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on to route webhook data (per the gem's own documented `WebhookMetadata.shop` contract). A malicious app-installer (an unprivileged, ordinary merchant using the app — no `api_secret_key`, access token, or privileged account required) can forge the `shop` associated with a webhook payload they legitimately received for their own store, causing the host app to write/act on data under another tenant's identity — a cross-tenant access condition, which maps to the "Critical" impact class (cross-tenant access breaking the shop/session identity binding).

### Likelihood Explanation
Any merchant who installs the app can register an http webhook pointing at an endpoint they control, capture a real `(body, X-Shopify-Hmac-Sha256)` pair, and replay it against the app's real webhook callback URL with a forged `X-Shopify-Shop-Domain` header. No credentials beyond ordinary app installation are needed, and the webhook callback endpoint is by design open to unauthenticated HTTP POSTs (it can only be authenticated via the HMAC, which does not cover the shop header). This makes the likelihood high for any app that trusts `WebhookMetadata#shop` (as the gem's own docs and example handler encourage).

### Recommendation
Bind the identity fields into the signed content, or otherwise verify `shop` (and `topic`) independently before trusting them: e.g., include `shop`/`topic`/`webhook_id` in `to_signable_string`, or require `Registry.process` to cross-check `request.shop` against the set of shops known to have an active session/webhook registration for that specific `webhook_id`/topic before invoking the handler. At minimum, update the documentation to stop asserting that "the request did indeed come from Shopify" when only the body bytes are verified.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`) pointing to a URL they control.
2. Shopify sends the attacker a genuine webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` using the app's shared `client_secret`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays `B`/`H` unchanged to the app's real, public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`: [5](#0-4) 
5. `request.shop` returns the forged `victim-shop.myshopify.com`, and the host app's handler processes attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
