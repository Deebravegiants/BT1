## Title
Blanket `WeightToFee for T: WeightToFeePolynomial` prices execution by `ref_time` only, silently underpricing `proof_size`-heavy extrinsics unless a runtime opts into a manual max-of-components override - (File: substrate/primitives/weights/src/lib.rs)

## Summary
The default blanket impl `impl<T> WeightToFee for T where T: WeightToFeePolynomial` evaluates the fee polynomial only against `weight.ref_time()`, completely ignoring `weight.proof_size()`. This is a real, confirmed gap: system parachains and the relay chains deliberately work around it with a hand-written `WeightToFee::weight_to_fee` that takes `time_poly.eval(ref_time).max(proof_poly.eval(proof_size))`, but any runtime that plugs a plain `WeightToFeePolynomial` type directly as `pallet_transaction_payment::Config::WeightToFee` inherits the ref_time-only pricing.

## Finding Description
`substrate/primitives/weights/src/lib.rs` defines:
```rust
impl<T> WeightToFee for T
where
    T: WeightToFeePolynomial,
{
    fn weight_to_fee(weight: &Weight) -> Self::Balance {
        let poly: FeePolynomial<Self::Balance> = Self::polynomial().into();
        poly.eval(weight.ref_time())
    }
}
``` [1](#0-0) 
This is invoked from `pallet_transaction_payment` fee computation (`Pallet::<T>::weight_to_fee` → `T::WeightToFee::weight_to_fee(&capped_weight)`), and it never reads `proof_size()`.

Confirmed instances of the safe pattern (max of both components), used by the actual production system-parachain/relay-chain fee configs (Westend, Rococo, Penpal): [2](#0-1) [3](#0-2) [4](#0-3) 

However, several other runtimes/templates directly implement `WeightToFeePolynomial` for their `WeightToFee` type and rely on the blanket impl, meaning only `ref_time` is priced: [5](#0-4) [6](#0-5) [7](#0-6) 

I was unable to fully confirm, within this session's remaining tool budget, exactly which of `polkadot/runtime/westend/src/lib.rs`, `polkadot/runtime/rococo/src/lib.rs`, `substrate/bin/node/runtime/src/lib.rs`, `templates/parachain/runtime/src/configs/mod.rs`, `templates/minimal/runtime/src/lib.rs`, and `templates/solochain/runtime/src/configs/mod.rs` bind `pallet_transaction_payment::Config::WeightToFee` to the ref_time-only `WeightToFeePolynomial` type vs. a max-of-components wrapper — the grep only located the line reference, not its resolved target type, and no further tool calls were available. Based on what was found: `polkadot/runtime/westend/constants::fee::WeightToFee` (a plain `WeightToFeePolynomial` impl) exists as a distinct type from `parachains_common`'s max-of-components `WeightToFee` used by system parachains, suggesting at minimum the relay chain constants crate defines a ref_time-only variant that could be wired into `pallet_transaction_payment::Config` for the relay chain or other consumers.

## Impact Explanation
Where a runtime's `pallet_transaction_payment::Config::WeightToFee` resolves to a plain `WeightToFeePolynomial`-only type (not the max-of-components wrapper), an attacker can submit extrinsics/precompile calls with disproportionately high `proof_size` (e.g., reads that produce a large state proof) but low `ref_time`, paying a fee computed purely from the small ref_time component while consuming a large share of the block's PoV (`BlockLength`/PoV budget). Repeated across blocks, this lets an unprivileged, ordinary signed account cheaply exhaust the scarcest resource (PoV) relative to its true cost, systemically underpricing PoV-heavy execution — matching the scoped impact.

## Likelihood Explanation
This is not a universal SDK bug but a configuration-dependent footgun: exploitability strictly depends on whether a given runtime's `WeightToFee` associated type is bound to a plain `WeightToFeePolynomial` implementation rather than a max-of-components wrapper. The design already anticipates this failure mode — production system parachains and the penpal test runtime explicitly override `weight_to_fee` to take the max of ref_time-fee and proof_size-fee — evidencing that the SDK maintainers are aware and mitigate it where they've applied the pattern. The risk is real for any downstream/derived runtime (including templates, which are commonly copied as a starting point) that forgets or is unaware of this pattern, since the blanket impl gives no compile-time or runtime warning that `proof_size` is being ignored.

## Recommendation
- Add a prominent doc-comment warning on the blanket `impl<T> WeightToFee for T where T: WeightToFeePolynomial` in `substrate/primitives/weights/src/lib.rs` stating explicitly that it only accounts for `ref_time` and that runtimes with meaningful PoV costs must implement `WeightToFee` manually (max-of-components) instead of relying on `WeightToFeePolynomial`.
- Consider providing a reusable, exported helper/combinator in `substrate/primitives/weights` (e.g., a `MaxOf<TimePoly, ProofPoly>` `WeightToFee` wrapper) so runtime authors don't need to hand-roll the pattern seen in `cumulus/parachains/runtimes/constants/src/{westend,rococo}.rs` and `penpal`.
- Add an `integrity_test`/static assertion in `pallet_transaction_payment` (or a lint in the runtime-builder tooling) that flags when `WeightToFee` is a bare `WeightToFeePolynomial` blanket impl and the runtime's `BlockWeights::max_block.proof_size() > 0`, to catch this misconfiguration at genesis/build time.
- Audit all production runtimes in this repo (`polkadot/runtime/*`, `substrate/bin/node/runtime`, templates) to confirm each binds `WeightToFee` to a max-of-components implementation, not the raw `WeightToFeePolynomial`-derived one.

## Proof of Concept
Rust unit test in `substrate/primitives/weights/src/lib.rs` or a new test crate:
```rust
struct RefTimePoly;
impl WeightToFeePolynomial for RefTimePoly {
    type Balance = u128;
    fn polynomial() -> WeightToFeeCoefficients<u128> {
        smallvec![WeightToFeeCoefficient { degree: 1, negative: false, coeff_frac: Perbill::zero(), coeff_integer: 1 }]
    }
}

#[test]
fn blanket_impl_ignores_proof_size() {
    let w = Weight::from_parts(1_000 /* low ref_time */, 1_000_000_000 /* huge proof_size */);
    let fee = <RefTimePoly as WeightToFee>::weight_to_fee(&w);
    // Fee only reflects ref_time=1_000, not the 1_000_000_000 proof_size component.
    assert_eq!(fee, 1_000u128);

    // Reference max-of-components implementation charges based on the dominant (proof_size) term.
    let expected_if_priced_correctly = w.proof_size() as u128; // using same 1:1 coefficient for illustration
    assert!(fee < expected_if_priced_correctly, "ref_time-only fee underprices PoV-heavy extrinsic");
}
```
Expected assertion: the blanket-impl fee (`1_000`) is orders of magnitude smaller than what a max-of-components implementation (as used in `cumulus/parachains/runtimes/constants/src/westend.rs`) would charge for the same `Weight`, demonstrating the underpricing for any runtime that has not adopted the max-of-components pattern.
