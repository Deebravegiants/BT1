### Title
Selector guard in `EmporiumUpgradeable.runAction` CASE 2 only blocks two selectors, allowing arbitrary calls that drain any ERC20/ETH balance Emporium holds when `erc20TokenAddresses` is empty - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s stateless branch (CASE 2) only rejects `callData` whose selector equals `IHinkalWallet.callHinkalWallet` or `IHinkalWallet.doSendToRelay`; any other payload (e.g. `IERC20.transfer`, `approve`) is executed unchecked via `op.endpoint.call{value: op.value}(op.callData)`. Because both `EmporiumUpgradeable.runAction`'s and `Hinkal.transact`'s balance-accounting loops only iterate over `circomData.erc20TokenAddresses`, an attacker who submits a self-generated proof with an empty `erc20TokenAddresses` array can direct Emporium to call `transfer`/`approve` on any token it happens to hold, with zero balance checks performed anywhere in the call.

### Finding Description
The claimed equality — "set of assets Emporium can move" == "set of assets accounted in `balancesBefore`/`balancesAfter`" — is broken whenever `circomData.erc20TokenAddresses` is empty.

Code path:
1. `EmporiumUpgradeable.runAction` computes `balancesBefore`/`balancesAfter` strictly over `circomData.erc20TokenAddresses`: [1](#0-0) , [2](#0-1) 
2. In CASE 2, the only guard is a selector check against two specific `IHinkalWallet` functions; any other selector (including `IERC20.transfer`/`approve`/`transferFrom`) passes and is executed via a raw low-level `.call`: [3](#0-2) 
3. The post-loop reconciliation only iterates `circomData.erc20TokenAddresses.length`, so if that array is empty, the loop body never executes and no revert can occur regardless of what CASE 2's arbitrary call did: [4](#0-3) 
4. `Hinkal.transact` performs the identical restriction — its own `oldBalances`/`newBalances` and slippage/balance-diff `require`s are also scoped to `circomData.erc20TokenAddresses` only: [5](#0-4) , [6](#0-5) 

Attacker's exact call: craft `CircomData` with a valid self-generated proof over the attacker's own (possibly zero-value) UTXOs, `erc20TokenAddresses = []`, `externalActionData.externalActionId` pointing at Emporium, and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{ endpoint: targetToken, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, amount) }`. Call `Hinkal.transact(...)`. `_externalTransact` routes to `EmporiumUpgradeable.runAction`, which falls into CASE 2, passes the selector check (since it's neither `callHinkalWallet` nor `doSendToRelay`), and executes `targetToken.transfer(attacker, amount)` with Emporium as `msg.sender`, moving out any `targetToken` balance Emporium currently holds — none of which is checked before or after because `erc20TokenAddresses` is empty at every accounting layer.

Existing guards fail because: `verifyWallet` only checks a signature when `signerAddress != address(0)` and returns early otherwise (no restriction on `ops` content) [7](#0-6) ; `onlyAllowedRecipient` only checks the caller is Hinkal, not that the action is benign [8](#0-7) ; and the balance-diff checks in both `Hinkal.transact` and `runAction` are keyed only to the attacker-chosen `erc20TokenAddresses` list, which the attacker fully controls and can set to empty.

### Impact Explanation
Any ERC20 or ETH balance transiently or persistently held by the Emporium contract (e.g., dust left from swap slippage, leftover balances from other users' in-flight transactions, or tokens Emporium is holding mid-multi-op-sequence) can be transferred out to an attacker-controlled address with zero on-chain accounting. This is direct theft of in-flight/protocol-held user funds routed through Emporium, matching the Critical category ("direct theft of shielded or in-flight user funds"). The action is repeatable for every token Emporium ever holds outside the caller-chosen `erc20TokenAddresses` set, and requires no privileged role.

### Likelihood Explanation
Preconditions: Emporium must hold some balance of a token the attacker targets (this occurs naturally from swap dust, rounding leftovers, or other users' funds transiently parked in Emporium during multi-op interactions). The attacker only needs to generate a self-consistent proof for their own dummy/zero UTXOs with `erc20TokenAddresses = []` and craft `externalActionMetadata` — both are explicitly attacker-controlled fields per the threat model. No relay, admin, or other privileged role is required; cost is limited to gas and proof generation.

### Recommendation
In CASE 2, restrict `op.endpoint` to a pre-approved allowlist (e.g., DEX routers) and/or restrict which selectors are permitted (allowlist rather than denylist) instead of only blacklisting two `IHinkalWallet` selectors. Additionally, make the balance reconciliation in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` cover every token actually touched by `op.endpoint`/`op.callData` (e.g., by decoding/whitelisting the token argument of `transfer`/`approve`/`transferFrom` calls, or by never allowing Emporium to hold a lingering ERC20 balance across transactions — sweeping all balances at the end of every `runAction`, not just the ones enumerated in `circomData.erc20TokenAddresses`).

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC20, and pre-fund the Emporium contract directly with `mockToken.mint(emporium, 1000e18)` to simulate stuck/dust balance.
2. Build a minimal valid `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId` set to Emporium's registered id, and `externalActionMetadata` encoding `EmporiumStack{ signerAddress: address(0), ops: [EmporiumOperation{ endpoint: address(mockToken), invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, 1000e18) }] }`.
3. Generate a matching proof for a trivial (zero-value/zero-token) circuit instance (Min circuit) and call `Hinkal.transact(...)` as `attacker`.
4. Assert `mockToken.balanceOf(attacker) == 1000e18` and `mockToken.balanceOf(emporium) == 0` after the call, while confirming `balancesBefore`/`balancesAfter` arrays inside `runAction` were length-0 (i.e., no revert occurred despite the token move) — proving the equality "assets Emporium can move" != "assets accounted for" is broken.
