### Title
Unprotected `initialize()` on `EmporiumUpgradeable` allows front-running to seize ownership and bypass proof-gated fund flows - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.initialize()` is a `public` function guarded only by OpenZeppelin's `initializer` modifier, with no `onlyOwner`/factory-restricted access control. This mirrors the reported `CsFeeOracle.initialize()` front-running class of bug: whoever calls it first becomes the contract's owner and sets `allowedRecipients`/`hinkalHelper`.

### Finding Description
```solidity
function initialize(
    IHinkalHelper _hinkalHelper,
    address[] memory _allowedRecipients,
    address _owner
) public initializer {
    __EIP712_init("Emporium", "1.0.0");
    __ExternalActionBase_init(_allowedRecipients);
    ...
    _transferOwnership(_owner);
}
``` [1](#0-0) 

There is no access-control check on who may call `initialize`; any caller can supply their own `_owner`, `_hinkalHelper`, and `_allowedRecipients` argument. `runAction`, the only entry point that moves value through the Emporium and is normally intended to be reachable exclusively from the Hinkal contract after ZK-proof verification, is gated solely by `onlyAllowedRecipient`: [2](#0-1)  and `setAllowedRecipients` is `onlyOwner`-gated: [3](#0-2) .

If an attacker front-runs the legitimate deployer's `initialize()` call (e.g., in the window between proxy deployment and the intended initialization transaction), they become the contract `owner`. As owner, they can call `setAllowedRecipients` to add their own address, then invoke `runAction` directly — bypassing the Hinkal main contract's ZK-proof verification entirely. Inside `runAction`, the balance-equation check relies on caller-supplied `deltaAmountChanges`, not on any proof-verified transfer: [4](#0-3) . Because `deltaAmountChanges` is a raw calldata parameter under attacker control (normally it is derived from a verified proof in `Hinkal.sol`), the attacker can claim a fabricated "deposit" (`deltaAmountChanges[i] < 0`) that never actually occurred, artificially inflating `balanceChange` and passing the `BalanceChangeShouldBePositive` check while withdrawing real ERC-20 balances the Emporium contract already holds via `handleOut`.

### Impact Explanation
This breaks the fundamental balance equality that `runAction` is supposed to enforce (value moved in vs. value moved out), letting an attacker who has stolen ownership through initializer front-running drain any tokens already held by the `EmporiumUpgradeable` contract without a corresponding real deposit or valid ZK proof — a direct theft of protocol/user-deposited funds and a proof-verification bypass, matching the Critical impact category (proof/nullifier bypass, direct theft of funds).

### Likelihood Explanation
This requires the attacker to win a front-running race against the legitimate `initialize()` call — a real-world MEV/mempool-monitoring scenario, not a privileged-key requirement, and is directly analogous to the referenced `CsFeeOracle` finding. Likelihood is highest if `EmporiumUpgradeable` is deployed via a standard proxy pattern where deployment and initialization are two separate transactions (deployment scripts are out of scope for this repo so this cannot be fully confirmed from `contracts/**`/`circuits/**` alone, but the contract code itself provides no in-contract protection regardless of deployment method).

### Recommendation
Restrict `initialize()` so it can only be called by the intended deployer/factory (e.g., check `msg.sender == expectedDeployer`, or deploy the proxy and call `initialize()` atomically in the same transaction via a factory contract, as `HinkalFactory.sol` already does for the main `Hinkal` contract) so that ownership and `allowedRecipients` cannot be front-run.

### Proof of Concept
1. Deployer deploys the `EmporiumUpgradeable` proxy but has not yet sent the `initialize()` transaction (or it is pending in the mempool).
2. Attacker observes the pending deployment/initialize transaction and front-runs it by calling `initialize(attackerHinkalHelper, [attackerAddress], attackerAddress)` with higher gas.
3. The legitimate `initialize()` call now reverts (`initializer` modifier prevents re-init), leaving the attacker as `owner` and an allowed recipient.
4. Attacker calls `setAllowedRecipients([attacker])` (already achieved in step 2) and then calls `runAction(circomData, deltaAmountChanges)` directly, supplying `erc20TokenAddresses` for tokens already sitting in the Emporium contract balance and a fabricated negative `deltaAmountChanges[i]` to make `balanceChange` appear non-negative, extracting real token balance via `handleOut` without any actual deposit or ZK proof verification from `Hinkal.sol`.
