Confirmed and cross-validated: the EVM `HandlerV2.sol` implements the identical pattern, and its own comment explicitly states `// The consensus client has now expired to mitigate long fork attacks, this is unrecoverable.` This confirms the deadlock is a known, unrecoverable state on both the Substrate (`pallet-ismp`) and EVM (`HandlerV2`/`EvmHost`) sides, which is the strongest and best-documented analog to the KintoID staleness-gate bug class.

### Title
Consensus client expiry check (`unStakingPeriod`/`unbonding_period`) permanently and irreversibly bricks a route if no relayer submits an update within the window - ([File: evm/src/core/HandlerV2.sol], [File: modules/ismp/core/src/handlers/consensus.rs])

### Summary
Both Hyperbridge's EVM (`HandlerV2.handleConsensus`) and Substrate (`pallet-ismp` via `ismp::handlers::consensus::update_client`) consensus-update paths gate every new consensus proof on a staleness check: the elapsed time since the last successful update must be less than a configured unbonding/unstaking period. Critically, the timestamp that is compared (`consensusUpdateTime` / `consensus_update_time`) is *only* ever advanced by a **successful** call to this same gated function. If no relayer submits a valid consensus update before the window elapses, the check begins failing, and because the failing call never reaches the point where it would refresh the timestamp, the gap between "now" and "last update" can only grow — the client can never recover. This mirrors the `KintoID.lastMonitoredAt` bug class exactly: a single staleness timestamp gates a critical check but is refreshable only through one narrow code path, and once that path is missed, the gate fails for everyone/everything, permanently in this case.

### Finding Description
On EVM, `HandlerV2.handleConsensus` computes: [1](#0-0) 
`delay = block.timestamp - host.consensusUpdateTime()`; if `delay >= host.unStakingPeriod()`, it reverts with `ConsensusClientExpired()` — and the function's own comment states this is `unrecoverable`. `consensusUpdateTime` is only written after a proof successfully verifies, later in the same function, so a reverted call never advances it: [2](#0-1) .

On the Substrate side, `ismp::handlers::consensus::update_client` performs the analogous check via `host.is_expired(...)` *before* verifying the new proof, and only calls `store_consensus_update_time` after verification succeeds: [3](#0-2) 

The default `is_expired` trait implementation compares `host_timestamp - last_update >= unbonding_period`: [4](#0-3) 

This handler is reachable by anyone: `pallet_ismp::Pallet::handle_unsigned` is an unsigned, permissionless extrinsic that dispatches `Message::Consensus` batches to this exact handler, with no staking or whitelisting required to submit: [5](#0-4) , and Hyperbridge's own docs describe consensus relaying as fully permissionless: [6](#0-5) .

Because the timestamp is refreshed only inside the very call that the staleness check gates, there is no self-healing path: once `now - last_update >= unbonding_period` becomes true, every subsequent `update_client`/`handleConsensus` call for that consensus state will observe an even larger (or equal) gap and fail identically, forever. This is the same root cause pattern as the external report: a single critical timestamp gate that is refreshable through only one narrow path (here, a successful proof verification instead of `monitor()`), with no alternate/fallback refresh mechanism, and whose failure mode denies service to the entire dependent surface rather than to a single caller.

### Impact Explanation
Once a consensus client expires this way, `validate_state_machine` (Substrate) and `handleConsensus`/state-commitment reads (EVM) can never again accept new state commitments for that state machine: [7](#0-6) 
This means the affected route (source or destination chain tied to that consensus client) can no longer deliver *any* new requests or responses, since state-membership/non-membership proofs can never be verified against a fresher height. Any relayer fees escrowed for in-flight requests destined through that route become permanently unrecoverable in practice (barring privileged `create_consensus_client` re-initialization by `AdminOrigin`, which is a distinct trust boundary and not a protocol-level recovery). This satisfies "permanent freezing of funds" and "a route unable to deliver messages."

### Likelihood Explanation
Reaching the expired state does not require any malicious actor — it only requires that no relayer (out of the fully permissionless relayer set) submits a valid consensus update within the configured unbonding/unstaking period, which can happen from relayer outages, insufficient economic incentive for a low-traffic route, RPC/prover downtime, or a griefer deliberately front-running/crowding out honest relayer submissions near the deadline. Given the permissionless, unsigned, first-to-submit design described in Hyperbridge's own relayer documentation, sustained submission is an operational assumption rather than a protocol-enforced guarantee, making this a realistic Medium-to-High likelihood liveness/freezing condition for less-trafficked or economically-unincentivized routes.

### Recommendation
Decouple the "is this client stale" check from the single narrow refresh path, or provide a protocol-level recovery mechanism that does not depend solely on trusted `AdminOrigin`/governance re-initialization, e.g.:
- Allow the unbonding period to be extended/refreshed by any valid, verifiable heartbeat/attestation short of a full state-advancing proof (analogous to updating `lastMonitoredAt` from multiple legitimate code paths rather than one).
- Consider widening the incentive/priority for consensus-relay submissions as the unbonding deadline approaches, or emit an on-chain early-warning event well before expiry so relayers/monitoring can react before the irreversible threshold is crossed.
- Document and/or enforce a permissionless re-anchoring flow (e.g., accept an update proof anchored to a checkpoint newer than the expired state, rather than requiring the trusted `create_consensus_client` call) so that expiry does not require a privileged party to unfreeze funds.

### Proof of Concept
1. Let a consensus client for state machine `S` have `unbonding_period` (Substrate) / `unStakingPeriod` (EVM) = `T`.
2. Ensure no relayer submits a `ConsensusMessage`/`handleConsensus` call for `S` for any window `>= T` (e.g., simulate by not running the tesseract relayer, or by time-warping a test past `T` as done in `check_client_expiry`): [8](#0-7) 
3. Submit a subsequent, otherwise-valid `handle_unsigned([Message::Consensus(...)])` (Substrate) or `handleConsensus` (EVM) call with a fresh, valid consensus proof.
4. Observe the call reverts with `Error::UnbondingPeriodElapsed` / `ConsensusClientExpired()` — because the check runs before the timestamp is refreshed, `consensus_update_time` never advances, so every future call to the same handler, no matter how valid the proof, fails the same way indefinitely: [9](#0-8) , [1](#0-0) .
5. Any request/response destined through state machine `S` can no longer be delivered since no new state commitment can ever be accepted, permanently freezing associated relayer fees/escrows for that route.
