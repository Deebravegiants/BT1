This confirms the asymmetry clearly: for OAuth callbacks, `AuthQuery#to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb:33-43`) explicitly includes `shop` in the HMAC-signed payload, binding the shop identity to the signature. For webhooks, `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns only `@raw_body` — the `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers via `shopify_header` and are never included in the HMAC computation.

### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`, and that validator's signed input is `request.to_signable_string`, which for `ShopifyAPI::Webhooks::Request` returns only `@raw_body`. The `shop` value handed to the app's handler comes from the `shop-domain`/`x-shopify-shop-domain` HTTP header, a field that is never included in the signed bytes.

### Finding Description
`Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
`HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header. For `Webhooks::Request`, `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) is just `@raw_body`; `shop` (`request.rb:20-23`) and `topic` (`request.rb:15-18`) are pulled directly from unauthenticated headers (`shopify_header`, `request.rb:67-70`) and are never mixed into the HMAC input.

This differs from the OAuth callback binding in this same gem: `Auth::Oauth::AuthQuery#to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb:33-43`) explicitly folds `shop`, `host`, `code`, `state`, and `timestamp` into the signed string, so `shop` there is cryptographically bound to the signature. No equivalent binding exists for the webhook `shop`/`topic` headers.

The intended identity binding is: `hmac == HMAC(secret, bytes-that-include-shop)`. What the gem actually verifies is: `hmac == HMAC(secret, raw_body)`, with `shop` sourced from a separate, unsigned channel. Any legitimate webhook body+hmac pair the attacker has ever observed for any shop/topic combination remains valid under this check no matter what `shop-domain` or `topic` header value is substituted, because those header values are outside the HMAC-covered bytes.

### Impact Explanation
An unprivileged attacker who has observed even one legitimate Shopify webhook delivery (e.g. to their own dev/test store, which they can freely provision and receive webhooks for) obtains a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`. By replaying that exact body+hmac while substituting the `shop-domain` header for a different (victim) shop and/or a different `topic`, `Registry.process` still passes the HMAC check (`registry.rb:190`) and dispatches `WebhookMetadata` claiming an arbitrary victim `shop`/`topic` to the app's handler (`registry.rb:198-199`). Because host applications are documented (`docs/usage/webhooks.md:125`, "This will verify the request did indeed come from Shopify") to trust that `Registry.process` fully authenticates the webhook — including which shop it is "for" — this is a genuine cross-tenant identity-binding break within this gem's own verification logic, not a misuse of a documented contract. Depending on how the host app keys work off `data.shop` (e.g., looking up that shop's session/access token to act on data, marking that shop's data as updated, or crediting billing/webhook counts), this can produce cross-tenant data confusion attributed to the wrong merchant.

### Likelihood Explanation
Requires no possession of `api_secret_key`, no privileged account, and no interception of another shop's traffic — only a single self-observed legitimate webhook delivery (any topic/shop the attacker can trigger themselves, e.g., in a personal dev store) plus the ability to POST to the app's public webhook endpoint with modified headers, which is inherent to how HTTP requests to that endpoint are made. The header substitution is trivial (plain text HTTP headers, not part of the signature).

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the HMAC-verified input for webhooks (e.g., include the relevant headers in `to_signable_string`, mirroring what `Auth::Oauth::AuthQuery` already does for `shop`), or otherwise cryptographically tie the header-derived identity fields to the signed body before they are exposed via `WebhookMetadata`.

### Proof of Concept
1. Attacker runs their own dev store `attacker.myshopify.com` with the target app installed, and triggers a webhook (e.g. `orders/create`) themselves, capturing the raw POST body and the legitimate `x-shopify-hmac-sha256` value Shopify computed with the app's real `api_secret_key`.
2. Attacker replays that exact `raw_body` and `hmac` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` (`registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` (`webhooks/request.rb:35-38`, `utils/hmac_validator.rb:26-31`) — validation succeeds despite the substituted `shop`/`topic` header.
4. `handler.handle` is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` (`registry.rb:198-199`), where `shop` is `"victim-shop.myshopify.com"` even though the HMAC never covered that value — the app's handler now processes/attributes data under an attacker-chosen shop identity that was never actually authenticated. ## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
