### Title
Webhook shop/topic/api_version/webhook_id headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC and then hands the caller a `WebhookMetadata` object whose `shop`, `topic`, `webhook_id`, and `api_version` fields are read straight from HTTP headers. The HMAC signature, however, is computed only over the raw request body, not over these header values. This is the same class of bug as the report's deposit/withdraw asymmetry: one identity-bearing field (the request body) is cryptographically bound to the request, while another identity-bearing field (`shop`, used by host apps as the trusted tenant identifier) is not.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from HTTP headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` only recomputes and compares the signature over `to_signable_string` (the body): [3](#0-2) 

`Registry.process` validates that body-only HMAC, then immediately forwards the header-derived `shop` (and other header fields) to the host application's handler as authenticated `WebhookMetadata`, with no secondary check that this `shop` actually corresponds to the tenant whose data appears in the signed body: [4](#0-3) 

The broken equality is: `hmac == HMAC(secret, raw_body)` is verified, but `shop_header == tenant_owning(raw_body)` is never checked — the two are treated as one authenticated unit by consumers of `WebhookMetadata#shop`, even though only the body is actually signed.

### Impact Explanation
An attacker who can obtain one valid `(raw_body, hmac)` pair for any shop (e.g., their own installed test store, or a topic whose body carries no shop-specific secret, such as `app/uninstalled` or a metafield/product event with attacker-controlled content) can replay that exact body and HMAC while substituting the `X-Shopify-Shop-Domain` header for a victim shop domain. Because the signature never covers the header, the replayed request still passes `HmacValidator.validate`, and `Registry.process` dispatches it to the handler with `data.shop` set to the victim's domain. If the host application (as intended and documented by this gem's `WebhookMetadata` contract) uses `data.shop` to select which merchant record/session to act on, this results in cross-tenant data injection or state corruption — one shop's webhook event applied to another shop's tenant context. This matches the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control or capture at least one legitimately-signed webhook body (achievable via their own store subscribing to any webhook topic under their own app credentials, or via topics where they can influence body content, e.g., `orders/create` with attacker-chosen line item text) and to be able to reach the app's public webhook endpoint with modified headers, which is trivial since the endpoint accepts arbitrary HTTP requests from the internet. No possession of `api_secret_key` is needed.

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) inside the HMAC-signed payload verification, or at minimum have `Registry.process` cross-check that the `shop` header matches a shop identifier embedded in/derivable from the signed body before constructing `WebhookMetadata`. Barring that, document explicitly that `WebhookMetadata#shop` is unauthenticated header data and must not be used by host apps as a tenant boundary without additional verification (e.g., matching against an existing stored session for that shop).

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a webhook (e.g. `app/uninstalled`) whose body is `{}` (fixed, shop-agnostic payload), capturing the resulting `X-Shopify-Hmac-Sha256` header — this is a validly signed `(body, hmac)` pair using the app's real `client_secret`.
2. Attacker sends a POST to the app's webhook endpoint with the same body/hmac, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks `body` against `hmac` per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`.
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)`, causing the host app to act (e.g., wipe/deactivate) on the victim tenant's record despite the event never having been sent by Shopify for that shop.           raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
