### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`) that the app's handler trusts as the webhook's origin are taken from unauthenticated HTTP headers that are never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers, independent of the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., of the body) and, once that passes, forwards `request.shop` unchanged into `WebhookMetadata`, which the app's handler treats as the authenticated tenant identity: [3](#0-2) 

`WebhookMetadata` and `WebhookHandler` expose `shop` as a plain, trusted field to app code with no further validation: [4](#0-3) 

The HMAC validator itself only compares the computed signature of `to_signable_string` (the body) against the received signature — it never binds any header value into that comparison: [5](#0-4) 

This breaks the intended identity binding: `HMAC-authenticated bytes == the shop asserted to the handler`. Because the same `api_secret_key` is shared by the app across all shops that install it, any user who controls a shop with the app installed can legitimately trigger a real webhook delivery to their own endpoint, capture the body + valid HMAC signature for that delivery, and then replay it against the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to name a different, victim shop. Since `shop` is not part of the signed content, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` will happily hand the (attacker-chosen) `shop` value to the handler alongside the replayed body.

### Impact Explanation
This is a cross-tenant identity-binding failure at the app's trust boundary: the gem asserts a `shop` value to application code as if it were authenticated, when it is actually an unauthenticated header. Any app that keys per-tenant side effects (writing/updating records, triggering GDPR redaction flows such as `shop/redact`, `customers/redact`, `customers/data_request`, adjusting billing, inventory, etc.) off `WebhookMetadata#shop` can be made to apply another merchant's webhook body under a victim shop's identity, or vice versa attribute an attacker-controlled body to a victim's shop. This matches the "cross-tenant access" criteria (Critical) as defined by the scope, since the vulnerability lets one authenticated shop (webhook sender) impersonate another shop's identity in the same app installation, purely through this gem's own webhook-verification logic.

### Likelihood Explanation
Likelihood is credible but not trivial: it requires the attacker to control (or have installed) the app on at least one shop, so they can legitimately receive one or more real webhook deliveries with valid HMACs for arbitrary body content of their choosing (many webhook topics let the shop-side owner influence body content, e.g. product/order updates on their own store), and requires the app's webhook endpoint to be reachable and to trust `data.shop` for tenant-scoped actions — a normal integration pattern encouraged by the gem's own `WebhookHandler` API (`WebhookMetadata#shop`). No secrets, TLS interception, or privileged Shopify staff access are needed.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the HMAC-covered signable string, or otherwise assert that the webhook's `shop` domain matches a shop the app itself is expecting to receive delivery for (e.g., checked against currently known/installed shops using `ShopifyAPI::Utils::ShopValidator`) before handing it to `WebhookHandler#handle`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant-scoping without independent verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and legitimately receives a real webhook delivery for topic `customers/data_request` (or any topic) with body `B` and a correctly computed header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker replays this exact HTTP request to the app's webhook endpoint, keeping `x-shopify-hmac-sha256` and the body `B` unchanged, but modifying `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the modified headers because `shop` is not part of any required-signed-value check [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches the unchanged header, returning `true` [7](#0-6) .
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` and performs whatever tenant-scoped action the app implements for that topic against the victim shop's identity, despite the request never having been produced or authorized by Shopify for that shop.

**Note on completeness:** I was unable to locate/verify whether any downstream consumer within this gem itself (outside `lib/shopify_api/webhooks/**`) revalidates `shop` against a known/installed-shop list before use; the finding is scoped strictly to the gem's own webhook request/registry/validator code as shown above.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
