### Title
Unbounded `open_time` in `Initialize2` Allows an Unprivileged Pool Creator to Freeze Swaps Indefinitely - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` accepts an attacker-controlled `open_time: u64` from `InitializeInstruction2` with no upper-bound validation against the current chain time, directly mirroring the reported XOracle `putPrice` bug class (a timestamp accepted without an upper bound, permitting the state to be pushed into a locked/waiting condition indefinitely).

### Finding Description
`InitializeInstruction2` carries a raw, caller-supplied `open_time: u64` field that is unpacked verbatim from instruction data with no range check. [1](#0-0) [2](#0-1) 

In `process_initialize2`, this value is stored as `amm.state_data.pool_open_time` (via `amm.initialize(...)` → `StateData::initialize`) and used to decide the pool status: if `init.open_time` is greater than the current `Clock::get()?.unix_timestamp`, the pool is set to `AmmStatus::WaitingTrade` instead of `SwapOnly`. There is no check that `open_time` is within any reasonable bound (e.g., a few days/weeks from now) — it can be set to `u64::MAX`. [3](#0-2) [4](#0-3) 

This `pool_open_time` is later enforced as a hard gate in every swap entrypoint (`process_swap_base_in`, `process_swap_base_out`, `process_swap_base_in_v2`, `process_swap_base_out_v2`): while `amm.status == WaitingTrade`, swaps are rejected with `AmmError::InvalidStatus` until `clock.unix_timestamp >= amm.state_data.pool_open_time`. [5](#0-4) [6](#0-5) 

`Initialize2` is callable by any user as a pool creator (only requires `user_wallet_info.is_signer` and correct PDA/account derivations — no admin/owner signature is required for this instruction), so an attacker can create a pool, seed it with initial liquidity themselves, and set `open_time` to an arbitrarily far future value. [7](#0-6) 

### Impact Explanation
Once `pool_open_time` is set to an extreme future value, the pool is permanently locked in `WaitingTrade` and cannot transition to `SwapOnly` naturally — swap instructions perpetually fail the `clock.unix_timestamp < amm.state_data.pool_open_time` check. Any coin/pc liquidity deposited into that pool (by the creator or by later unaware LPs/depositors who see an apparently valid pool) becomes unusable for trading for the effective lifetime of the chain, since the timestamp can be set beyond any realistic recovery window. This matches the report's bug class: a timestamp field lacking an upper-bound check that can freeze functionality until an attacker-chosen future time.

### Likelihood Explanation
High reachability: this requires only a single `Initialize2` transaction from an unprivileged user with attacker-chosen instruction data (`open_time`) and attacker-controlled accounts (the new pool, its own vaults, its own target-orders account). No elevated privileges, validator collusion, or off-chain component is needed.

### Recommendation
Enforce an upper bound on `open_time` in `process_initialize2` before storing it, e.g. reject the instruction if `init.open_time > Clock::get()?.unix_timestamp + MAX_OPEN_TIME_DELAY` (a small, protocol-defined window), analogous to the recommended `require(block.timestamp >= timestamp, ...)`-style bound in the referenced report, adapted here to bound future time rather than reject past time.

### Proof of Concept
1. Attacker calls `Initialize2` for a new pool with `nonce`, valid PDA/vault/mint accounts they control, and `open_time = u64::MAX` (or any value far beyond present time). [3](#0-2) 
2. `amm.status` is set to `AmmStatus::WaitingTrade` and `amm.state_data.pool_open_time = u64::MAX`. [4](#0-3) 
3. Any subsequent `SwapBaseIn`/`SwapBaseOut`/`SwapBaseInV2`/`SwapBaseOutV2` call against this pool fails with `AmmError::InvalidStatus` forever, because `clock.unix_timestamp < amm.state_data.pool_open_time` is always true. [5](#0-4) 

Note: I was unable to fully confirm within the available context whether `Deposit`/`Withdraw`/`WithdrawPnl` permission checks (`withdraw_permission`/`deposit_permission` on `AmmStatus`) also block or allow LP fund recovery while a pool sits in `WaitingTrade`; the tool session ended before I could inspect the `AmmStatus` permission-table implementation in `program/src/state.rs`. This affects whether the impact is "swap functionality frozen" versus "swap and LP-fund-recovery both frozen" — I recommend verifying this permission table directly in the repository (or via a Devin session with full file access) before finalizing severity.
