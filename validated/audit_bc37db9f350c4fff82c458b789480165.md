Audit Report

## Title
CORS wildcard-origin allowlist bypass via unanchored suffix match - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` in the gateway's HTTP server treats any `CORSAllowedOrigins` wildcard entry like `*.example.com` as matched by `strings.HasSuffix(originHost, allowedHost)` after stripping the `*.` prefix, without verifying the matched suffix is preceded by a `.` or equals the full host. This allows attacker-controlled domains that merely end with the same character sequence (e.g. `fakeethereum.org` for an allowlisted `*.ethereum.org`) to be treated as an allowed CORS origin.

## Finding Description
`isAllowedOrigin` parses the request `Origin` header and each configured allowed origin, then for wildcard entries strips the leading `*.` and checks `strings.HasSuffix(originHost, allowedHost)`: [1](#0-0) 

This is not a valid subdomain boundary check — it only verifies that `originHost` ends with the same character sequence as `allowedHost`, not that it is `allowedHost` itself or a proper subdomain (`*.allowedHost`) separated by a dot. If an operator configures `CORSAllowedOrigins = ["https://*.ethereum.org"]`, an attacker hosting content at `https://fakeethereum.org` satisfies `strings.HasSuffix("fakeethereum.org", "ethereum.org")` and is treated as an allowed origin.

This check gates `handleRequest`, which reflects the `Origin` back in `Access-Control-Allow-Origin` and enables `Access-Control-Allow-Methods`/`Access-Control-Allow-Headers` for that origin: [2](#0-1) 

The existing test suite covers only non-matching-suffix negative cases (`https://ethereum.remix.org` vs `*.ethereum.org`, scheme/port mismatches) and does not test the boundary-confusion case where the attacker origin shares a raw character suffix without a dot separator: [3](#0-2) 

## Impact Explanation
The gateway HTTP server is the internet-facing entry point that forwards the raw request body into the configured `HTTPRequestHandler.ProcessRequest`, which decodes and routes JSON-RPC requests to per-DON/per-service handlers: [4](#0-3) 

If an operator relies on a wildcard CORS entry to scope browser-originated access to a legitimate UI domain (e.g. `*.mycompany.com`), an attacker who registers a lookalike domain sharing the same suffix (`evilmycompany.com`) gets `Access-Control-Allow-Origin`/`Allow-Methods`/`Allow-Headers` reflected for their origin, defeating the intended same-origin restriction. Combined with credentialed browser requests, this enables cross-origin request forgery against the gateway API from an unprivileged attacker-controlled page, matching the "allowlist bypass" impact class.

## Likelihood Explanation
Exploitability depends on the operator using a wildcard entry in `CORSAllowedOrigins`, which is a supported and documented configuration option in `HTTPServerConfig`: [5](#0-4) 
Registering a domain that shares a raw string suffix with the allowed domain (without being a true subdomain) is a normal domain-registration action requiring no special privilege, victim interaction beyond visiting the attacker's page, or node/operator access. Given wildcard CORS is an explicit supported feature, this is a realistic bug reachable purely from an unprivileged remote HTML page.

## Recommendation
Fix `isAllowedOrigin` to require a proper subdomain boundary: after stripping `*.`, only match when `originHost == allowedHost` or `originHost` ends with `"." + allowedHost` (i.e., check `strings.HasSuffix(originHost, "."+allowedHost)` in addition to the exact-match branch), rather than a bare `HasSuffix` check.

## Proof of Concept
1. Configure the gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send an HTTP `POST` (or `OPTIONS` preflight) to the gateway's configured request path with header `Origin: https://fakeethereum.org`.
3. Observe the response includes `Access-Control-Allow-Origin: https://fakeethereum.org`, `Access-Control-Allow-Methods: GET, POST, OPTIONS`, and `Access-Control-Allow-Headers: Content-Type`, because `strings.HasSuffix("fakeethereum.org", "ethereum.org")` returns `true` even though `fakeethereum.org` is not a subdomain of `ethereum.org`.
4. This can be encoded as a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, but asserting that origin `https://fakeethereum.org` against allowed origin `https://*.ethereum.org` currently returns a non-empty `Access-Control-Allow-Origin` header (proving the bypass), which should be empty after the fix.
