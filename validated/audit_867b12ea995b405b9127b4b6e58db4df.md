### Title
Hardware wallet signing subsystem can be permanently blocked by an untrapped exception in the signing-retry callback - (File: `features/hardware-wallets/src/module/hardware-wallets.ts`)

### Summary
`HardwareWallets.#signGeneric` guards **all** hardware-wallet signing (every asset, every wallet account) with a single global concurrency-1 lock. The promise that releases this lock is only settled by `retrySigningRequest` (via `resolve`) or `cancelSigningRequest` (via `reject`). If an unclassified error occurs while trying to update signing-request state, the resulting exception is never caught, `retrySigningRequest` is invoked "fire-and-forget" (`void`), and the lock-releasing promise is left pending forever — permanently blocking all future `signTransaction`/`signMessage` calls, exactly like the GMX vault getting stuck in the `Deposit` state after a failed refund push.

### Finding Description
`#signGeneric` is wrapped in `restrictConcurrency(..., { concurrency: 1 })`, a single global lock shared by *every* asset and *every* hardware wallet account in the wallet: [1](#0-0) 

Its only exit paths are `request.resolve(result)` on success (inside `retrySigningRequest`) or `request.reject(...)` inside `cancelSigningRequest`: [2](#0-1) [3](#0-2) 

`retrySigningRequest` has a single `try { ... } catch (error) { ... } finally { this.#isRetrying = false }` block. Inside the `catch`, once errors are classified for `DisconnectedDevice*` (retry) and `timeout`/`UserRefusedError` (auto-cancel), the fallback branch for *any other error* calls `#updateSigningRequest(...)` and simply `return`s — it neither resolves nor rejects the deferred promise, relying on the UI to later call `retrySigningRequest`/`cancelSigningRequest`: [4](#0-3) 

`#updateSigningRequest` persists the signing-request state (including the raw caught error object) to a shared atom, which — in the multi-process SDK architecture — is serialized and pushed across the RPC bridge to the UI process: [5](#0-4) 

If this `set()` call itself throws (e.g., because the thrown error object from the asset's `signHardware`/`signMessage` implementation is unusual/non-serializable, or any other exception surfaces in that fallback branch), the exception escapes the single `catch` block entirely uncaught. Since `#signGeneric` invokes `retrySigningRequest` without awaiting it — `void this.retrySigningRequest(id)` — this becomes an unhandled promise rejection and `deferred.resolve`/`deferred.reject` are **never called**: [6](#0-5) 

Because the promise returned by `#signGeneric` never settles, the `restrictConcurrency(concurrency: 1)` wrapper never releases its single permit — this is functionally identical to `GMXVault` being stuck in the `Deposit` state after `processDepositCancellation` reverts on an unpayable refund target: a callback in the "rollback"/"error" path fails to run to completion, and the shared lock/state machine is never returned to an idle state.

### Impact Explanation
Once triggered, every subsequent call to `signTransaction` or `signMessage` for **any** asset or **any** hardware wallet account queues on `#signGeneric`'s single concurrency permit and hangs indefinitely. This is a wallet-wide denial of service of hardware-wallet transaction/message signing — the exact class of impact described in the source report (a shared resource permanently stuck in a "processing" state, blocking all future legitimate operations of that kind).

### Likelihood Explanation
The trigger requires only that the `sign` callback (ultimately backed by an asset's `signHardware`/device implementation, invoked with attacker-influenced transaction/message data) throw an error whose `.name`/`.message` doesn't match the explicitly retried/auto-cancelled categories, combined with a failure while persisting that error to the signing-request atom/RPC layer. This is plausible but not fully proven end-to-end from static review alone — the reachability of a serialization failure in `#updateSigningRequest` specifically (as opposed to other kinds of exceptions in that branch) would need to be confirmed dynamically, since the exact atom/RPC serialization code path outside this file was not inspected.

### Recommendation
Wrap the fallback error-handling branch (and ideally the entire `catch` block body) of `retrySigningRequest` in its own `try/catch`, and guarantee that `deferred.resolve`/`deferred.reject` is always eventually called (e.g., via a `finally`-based safety-net that rejects the pending request if none of the branches settle it) so that `#signGeneric`'s concurrency lock can never be held indefinitely by an unhandled exception.

### Proof of Concept
Not independently reproduced in this session (no test harness/build run); the finding is derived from static analysis of `features/hardware-wallets/src/module/hardware-wallets.ts`. A concrete PoC would need to: (1) initiate `signTransaction`/`signMessage` for a hardware wallet account, (2) force the underlying `sign` callback to throw an error that falls through all classified branches, and (3) make `#updateSigningRequest`'s `atom.set()` throw (e.g., via a non-serializable `error` payload), then observe that a second, unrelated `signTransaction` call for any asset never resolves.

  cancelSigningRequest = async (id: string, fromUI: boolean) => {
    const request = this.#signingRequest
    this.#logger.debug(`Cancelling signing request for id: ${id}, fromUI: ${fromUI}`)
    if (request?.id !== id) {
      this.#logger.warn(`No signing request found for id: ${id}`)
      return
    }

    await this.#deleteSigningRequest(id)

    // Ensure we cancel the action on the device
    if (fromUI) {
      this.#logger.debug(`Cancelling signing request on device for id: ${id}`)
      try {
        const { device } = await this.#getSelectedDevice(request.walletAccount)
        await device.cancelAction()
        this.#logger.debug(`Succesfully cancelled signing request on device for id: ${id}`)
      } catch (error: any) {
        this.#logger.error(`Failed to cancel signing request on device for id: ${id}`, error)
      }
    }

    // Now reject the promise returned to the asset caller
    request.reject(new UserRefusedError(!fromUI))
  }
