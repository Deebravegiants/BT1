### Title
Unbounded external calls in `HandlerV2`'s batch-processing loops let a single poisoned fee refund revert the entire batch of timeouts/responses - ([File: evm/src/core/HandlerV2.sol])

### Summary
`HandlerV2.handlePostRequestTimeouts`, `handleGetRequestTimeouts`, and `handleGetResponses` each iterate over a relayer-submitted array of leaves and, for every item, make an external call into `EvmHost` (`dispatchTimeOut` / `dispatchIncoming`) with no isolation (no `try/catch`, no per-item success flag). Inside `EvmHost`, the callback to the destination `IApp` is defensively wrapped in a raw `.call()` with an explicit success check, but the subsequent relayer/payer fee `safeTransfer` is not — it is a plain call that reverts the whole external call (and therefore the whole batch) if the ERC-20 transfer fails.

Note the asymmetry: the `IApp` callback is called with a low-level `.call()` and its failure is handled gracefully (receipt/commitment restored, function returns without reverting), but the `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` right after is a normal Solidity call — if it reverts, it bubbles all the way up through `dispatchTimeOut` → `HandlerV2`'s loop → the entire `handlePostRequestTimeouts`/`handleGetRequestTimeouts` transaction, reverting every other item batched in the same call.

`meta.sender` is the original `payer`/`_msgSender()` recorded when the request was dispatched (`EvmHost.dispatch(DispatchGet)` sets `sender: _msgSender()`), so it is attacker-controllable: an attacker dispatches their own GET/POST request with a non-zero fee from an address that is guaranteed to fail an ERC-20 transfer (e.g., an address later added to the fee token's blacklist, such as USDC-style tokens, or a token with a receive hook that reverts). Later, when a relayer batches this timeout together with unrelated users' timeouts into a single `handlePostRequestTimeouts`/`handleGetRequestTimeouts` call (which is the intended gas-optimization use of these batched arrays, and also composable via `HandlerV2.batchCall`), the poisoned entry's failing transfer reverts the entire call, denying delivery/refund for every other unrelated timeout in that batch.

This is precisely the bug class from the referenced report: an external call is made inside a loop over an array whose contents are influenced by an unprivileged caller, and a revert in any single iteration DoS's the whole batch rather than being isolated to that iteration — even though the same file already demonstrates the correct mitigation pattern (low-level `.call()` + explicit success check) for the callback half of the same function, just not for the fee-transfer half.

### Impact Explanation
This is a griefing/DoS vector against the permissionless relaying path: a low-cost attacker (pays only their own small request fee) can permanently or repeatedly block batched processing of `handlePostRequestTimeouts`/`handleGetRequestTimeouts` for any other timeouts bundled alongside their poisoned entry, delaying refunds and message finality for unrelated users/relayers. Because relayers are economically incentivized to batch multiple pending timeouts into one call for gas efficiency, this materially raises the cost/complexity of relaying (relayers must submit timeouts one-by-one and skip poisoned entries) and can be used to stall legitimate users' fee refunds indefinitely if the relayer keeps re-batching. This matches the Medium severity of the analog report (DoS from external calls inside a loop).

### Likelihood Explanation
Likelihood is moderate: it requires (1) an attacker to dispatch a request whose `payer`/`sender` address will fail ERC-20 receipt (achievable with a blacklist-capable fee token or a malicious ERC-777/hook-style fee token configuration) and (2) a relayer to batch that timeout together with other timeouts in the same call. Since `Hyperbridge` explicitly supports fee tokens like stablecoins (which commonly implement blacklisting), and batching is the documented/optimized relayer workflow (`handlePostRequestTimeouts`/`handleGetRequestTimeouts` taking arrays, plus `HandlerV2.batchCall`), this is a realistic operational scenario rather than a purely theoretical one.

### Recommendation
Isolate the fee-refund transfer the same way the app callback is isolated: wrap `IERC20(feeToken()).safeTransfer(...)` in a low-level `.call()` (or `try/catch` for token contracts implementing the try-pattern) with an explicit success check, and if it fails, retain the ability to retry the refund later (analogous to how a failed `onAccept`/`onPostRequestTimeout` callback preserves state for retry) instead of letting the failure revert the whole batched transaction. Additionally, consider allowing `HandlerV2`'s per-leaf loops to skip failing items (recording them for later resubmission) rather than reverting the entire batch, consistent with the mitigation already applied to `dispatchIncoming(PostRequest)`.

### Proof of Concept
1. Attacker calls `EvmHost.dispatch(DispatchGet)` (or `DispatchPost`) with `fee > 0`, setting `payer`/`from` to an address they control, e.g. `Attacker`.
2. Attacker gets `Attacker` blacklisted on the configured `feeToken` (or uses a fee-token/receiver combination guaranteed to revert on transfer to `Attacker`).
3. The request times out; a relayer collects several pending timeouts (attacker's poisoned one plus several legitimate unrelated ones) and submits them together via `HandlerV2.handleGetRequestTimeouts` (or `handlePostRequestTimeouts`).
4. Inside the loop, when the handler reaches `host.dispatchTimeOut(...)` for the attacker's entry, the app callback (`onGetTimeout`/`onPostRequestTimeout`) succeeds, but `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` reverts because `Attacker` cannot receive the token.
5. The revert propagates out of `dispatchTimeOut`, out of the `for` loop in `HandlerV2`, reverting the entire `handleGetRequestTimeouts`/`handlePostRequestTimeouts` call — none of the other unrelated, legitimate timeouts in the same batch are processed, even though their proofs and callbacks were valid.

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
