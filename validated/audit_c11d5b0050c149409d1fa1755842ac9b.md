Based on the investigation, there's a genuine (developer-acknowledged) equality-breaking issue in the POA bridge's withdrawal status matching logic.

### Title
Withdrawal status misattribution when multiple withdrawals of the same token exist in one NEAR transaction - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` matches a withdrawal's on-chain status/hash to a caller-supplied `withdrawalParams` by `assetId` alone, not by the position (`index`) of the withdrawal within the batch. When a single NEAR intent transaction contains two or more POA-bridge withdrawals of the same token (e.g., two different destination addresses/amounts, both in `zec.omft.near`), the SDK will report the same status/txHash for both, potentially attributing one withdrawal's completed destination hash to the other.

### Finding Description
`findMatchingWithdrawal` explicitly matches only on `assetId`: [1](#0-0) 

This is invoked from `describeWithdrawal`, which uses this match to decide `status`/`txHash`: [2](#0-1) 

The `index` parameter that uniquely identifies a specific withdrawal within a multi-withdrawal transaction is accepted by `createWithdrawalIdentifier` but is never consulted by `describeWithdrawal`/`findMatchingWithdrawal`: [3](#0-2) 

Upstream, `createWithdrawalIdentifiers` assigns a distinct `index` per bridge route to each withdrawal in a batch, under the assumption that bridges use it to disambiguate: [4](#0-3) 

But the PoA bridge implementation silently drops that index at the matching stage. If withdrawal #0 (assetId X, amount 5, address A) and withdrawal #1 (assetId X, amount 3, address B) are in the same NEAR tx, `withdrawals.find(w => nep141:${near_token_id} === assetId)` in the POA API response returns whichever entry appears first (list is explicitly documented as unsorted), regardless of which one the caller is polling for.

This breaks the intended equality: *"the txHash/status reported for withdrawal[i] corresponds to the on-chain outcome for withdrawal[i]"*. Instead, both `watchWithdrawal` calls (for index 0 and index 1) can resolve against the same underlying POA record, so at least one of the two logical withdrawals gets a completed status/txHash that does not belong to it.

### Impact Explanation
This matches the "status or hash misreport making an integrator credit or refund twice" impact category. An integrator relying on `sdk.createWithdrawalCompletionPromises` / `watchWithdrawal` to confirm on-chain settlement before crediting a user could:
- Mark withdrawal #1 (still pending/failed) as "completed" using withdrawal #0's txHash, prematurely releasing funds or crediting a user twice, or
- Attribute the wrong destination hash to the wrong withdrawal in an audit trail, causing operational/reconciliation errors.

The code's own comment acknowledges this: *"multiple withdrawals of the same token in a single transaction are not supported."* That is precisely the gap between developer's stated invariant and what the surrounding code (`createWithdrawalIdentifiers`, `createWithdrawalCompletionPromises`) actually allows callers to construct (batches of same-asset withdrawals).

### Likelihood Explanation
Likelihood is limited by an important mitigating factor: this requires the SDK caller to legitimately construct a batch containing two-or-more POA-bridge withdrawals of the identical `assetId` within one signed intent — a normal use pattern (e.g., splitting one deposit into payouts to two different addresses in the same token), not an attacker action. Since no malicious input is needed to trigger the mismatch (an ordinary "unprivileged" call pattern triggers it), it satisfies the rules' bar, but the *practical* severity depends on how often integrators build such batches and on the POA API's list ordering. There is no code-level protection (no assertion/throw) when more than one match exists — `Array.prototype.find` just silently returns the first.

### Recommendation
**Short term:** Have `findMatchingWithdrawal` fail loudly (throw) when more than one candidate withdrawal for the given `assetId` exists in the response, so integrators are alerted rather than silently getting misattributed results. Alternatively, disambiguate using `amount`/`address` from `withdrawalParams` in addition to `assetId`, as the existing code comment suggests ("sorting both API results and withdrawal params by amount").

**Long term:** Extend the POA bridge HTTP API (or its consumer) to return/accept a stable per-withdrawal identifier (matching the `index` already threaded through `WithdrawalIdentifier`) so status lookups are unambiguous regardless of how many same-asset withdrawals share a NEAR transaction.

### Proof of Concept
1. Construct `withdrawalParams` with two entries sharing the same `assetId` (e.g., `nep141:zec.omft.near`), different `amount`/`destinationAddress`, both routed through `PoaBridge`.
2. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams, intentTx })`, which internally calls `createWithdrawalIdentifiers` producing `wid.index = 0` and `wid.index = 1` for the two entries (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`).
3. Both `watchWithdrawal` calls invoke `PoaBridge.describeWithdrawal`, which calls `getWithdrawalStatusWithRetry` (keyed only by NEAR tx hash) and then `findMatchingWithdrawal(response.withdrawals, assetId)` (`poa-bridge.ts:313-322`, `409-427`) — `index` is never passed to the matcher.
4. If the POA API returns withdrawal #0 as `COMPLETED` with `transfer_tx_hash: "0xAAA"` and withdrawal #1 as still `PENDING`, both `describeWithdrawal` calls for index 0 and index 1 return the entry found first by `.find()`, which can be the same object for both callers — resulting in the pending withdrawal being reported as `{status: "completed", txHash: "0xAAA"}` even though `0xAAA"` belongs to the other withdrawal.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
