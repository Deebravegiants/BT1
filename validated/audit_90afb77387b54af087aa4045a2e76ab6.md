### Title
Webhook HMAC does not bind the `shop-domain` header, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `HmacValidator.validate` covers the body bytes but never the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers that `Webhooks::Registry.process` later trusts and hands to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

The signable string is exactly `@raw_body`; none of the Shopify headers are part of it. `Registry.process` validates the HMAC over that signable string and then, on success, unconditionally trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` (all read straight from headers) to build the data passed to the handler: [2](#0-1) 

`HmacValidator.validate` only proves "these bytes were signed with `api_secret_key`" — it says nothing about which shop, topic, or webhook id the signer intended: [3](#0-2) 

Because `api_secret_key`/`client_secret` is shared by the app across every installed shop, any webhook body+HMAC pair that Shopify legitimately delivered for Shop A remains a valid signature for that same body when replayed with a forged `x-shopify-shop-domain: shop-b.myshopify.com` header (and/or a different topic/webhook-id header) to the app's webhook endpoint. `HmacValidator.validate` will still return `true` because it never inspects the headers, and `Registry.process` will call the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`.

The broken identity binding, stated as an equality that should hold but doesn't:
`shop authenticated by the HMAC` == `shop the handler is told the payload came from`
Currently the left side is undefined (the HMAC authenticates zero shop identity), while the right side is taken verbatim from an attacker-controllable header.

### Impact Explanation
This is a cross-tenant integrity failure: a merchant who has the app installed (an "unprivileged internet user" from every other tenant's perspective) can capture one legitimately-signed webhook body/HMAC pair delivered to their own shop, then replay it to the app's public webhook endpoint while claiming it belongs to a victim shop. Any host application that keys business logic off `WebhookMetadata#shop` (e.g., updating that shop's local records, billing, inventory sync, uninstall/GDPR handling, etc., driven by `handler.handle(data: WebhookMetadata.new(topic:, shop:, body:, ...))`) will act on attacker-supplied data attributed to another tenant. This crosses the tenant boundary the gem is supposed to enforce via HMAC verification, matching the "cross-tenant access" High-impact category.

### Likelihood Explanation
Likelihood is meaningful but requires the attacker to already be able to observe at least one valid webhook delivery for some shop under the same app (trivial if the attacker installs the app on their own store, or if any webhook payload is otherwise observable/logged). No secret material (`api_secret_key`, access tokens) is needed — only replaying already-signed bytes with different headers, which this library's verification logic does not defend against.

### Recommendation
Include the identity-relevant headers (`shop-domain` at minimum, ideally `topic` and `webhook-id`) in the string that gets HMAC-verified, or otherwise cryptographically bind them to the signed payload, so that a signature valid for one shop/topic cannot be replayed with a different shop/topic combination. This requires changing `Request#to_signable_string` (and coordinating with Shopify's webhook signing implementation) to incorporate the header values, not just `@raw_body`.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; capture a legitimate webhook delivery, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Replay the exact same `B`/`H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:27-31`) recomputes `HMAC(api_secret_key, B)` and finds it equal to `H` — validation succeeds because it never looks at the shop header.
4. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) invokes the registered handler with `shop: "victim-shop.myshopify.com"`, even though that shop never sent this webhook.
