### Title
Webhook `topic` and `shop-domain` are not covered by the HMAC signature, allowing cross-tenant/topic forgery of `Registry.process` - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`Registry.process` authenticates a webhook solely by verifying the HMAC of the raw request body, then passes the request's `topic` and `shop-domain` headers straight into `WebhookMetadata` unauthenticated. Because `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and Shopify's app-level HMAC secret (`api_secret_key`) is shared across all shops that install the app, an attacker who legitimately receives a validly-signed webhook on their own shop can swap the `X-Shopify-Topic` and `X-Shopify-Shop-Domain` headers to any value while keeping the same body/HMAC, and the request still passes `HmacValidator.validate`.

### Finding Description
The intended binding is: `hmac == HMAC(secret, body)` should imply that `topic` and `shop` reported alongside that body are also authentic for that specific request. In this codebase that binding does not hold:

- `Registry.process` does: `HmacValidator.validate(request)` then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and dispatches to `handler.handle` [2](#0-1) .
- `request.topic` and `request.shop` are read directly from HTTP headers (`shopify-topic`/`x-shopify-topic`, `shopify-shop-domain`/`x-shopify-shop-domain`) with no cryptographic tie to the signature [3](#0-2) .
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received `hmac` header [4](#0-3) .
- `to_signable_string` for `Request` returns only the raw body bytes, never the topic or shop headers [1](#0-0) .

Because the signed content is body-only, and `api_secret_key` is the app's single client secret (identical for every merchant shop that installs the app, not a per-shop key), an attacker who installs the app on their own development shop can:
1. Register a webhook for a topic with a minimal/predictable body (e.g. `app/uninstalled`).
2. Receive the genuinely-signed callback `{topic: "app/uninstalled", shop: "attacker.myshopify.com", hmac: H, body: B}`.
3. Replay `B` and `H` unchanged directly to the app's webhook endpoint, but with `X-Shopify-Topic: shop/update` and `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Request#hmac`/`to_signable_string` only look at the (unchanged) body, so `HmacValidator.validate` returns `true`.
5. `Registry.process` calls the `shop/update` handler with `WebhookMetadata(topic: "shop/update", shop: "victim.myshopify.com", body: B)`, where `B` is attacker-controlled content that was never actually validated for that topic or that shop.

No other guard in the traced path (`ShopValidator`, `Context.setup?`, JWT `aud` checks, etc.) applies to webhook processing — those are OAuth/session-token concerns, not `Registry.process`. `Registry.process` performs no comparison of `request.shop` against any known/expected tenant, and no comparison of `request.topic` against what was actually signed.

### Impact Explanation
This lets an unprivileged attacker (their own shop's credentials only) inject a body of their choosing into any handler registered for any topic, labeled as coming from any victim shop, as long as they can get one genuinely-signed webhook payload from their own tenant. If the host app's handler for a topic like `shop/update` (or any handler that trusts `data.body` for tenant-scoped writes, e.g., custom domain, callback URL, webhook config) writes into storage keyed by `data.shop`, the attacker corrupts another tenant's stored data — cross-tenant data corruption, and potentially SSRF if a corrupted "host" value is later used by `HttpClient`. This matches the Critical category ("cross-tenant access"): the shop/topic label attached to an authenticated payload is not itself authenticated, and the exploit is repeatable against any victim shop the attacker chooses, using only a single genuine webhook obtained from their own account.

### Likelihood Explanation
Preconditions: the host app must have registered a webhook handler that trusts `WebhookMetadata#body` content for tenant-scoped writes keyed by `WebhookMetadata#shop` (a very common integration pattern, e.g. `shop/update` handlers persisting shop attributes). The attacker needs only: their own development/install shop, ability to receive one signed webhook, and direct HTTP access to the app's public webhook endpoint (no interception, no secrets, no victim access required). This is low-cost and fully repeatable — the same captured (body, hmac) pair can be replayed with different forged topic/shop header combinations indefinitely, since neither header is bound by the signature or checked for freshness/idempotency by `Registry.process`.

### Recommendation
`Request#to_signable_string`/`hmac` verification should bind the authenticated headers (`topic`, `shop-domain`, and ideally `webhook-id`) to the signature check, or `Registry.process` should independently validate that `request.shop` belongs to a shop with an active installation known to the host app before dispatching. At minimum, document prominently that `WebhookMetadata#shop` and `#topic` are unauthenticated header values and must never be used to key trust decisions without an independent shop-installation check, and that handlers must not blindly trust `body` contents for security-sensitive writes.

### Proof of Concept
```ruby
# test/webhooks/registry_forgery_test.rb
require "test_helper"

class RegistryForgeryTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @store = {}
    handler = Class.new do
      define_method(:handle) do |data:|
        @store_ref[data.shop] = data.body
      end
    end
    # inject shared store via instance_variable or closure
  end

  def test_forged_topic_and_shop_pass_hmac
    body = '{"note":"hi"}'
    hmac = OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), "secret", body)
    hmac_b64 = Base64.encode64(hmac).chomp

    # Attacker relabels topic/shop while keeping body+hmac from their own genuine webhook
    request = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "X-Shopify-Topic" => "shop/update",
        "X-Shopify-Hmac-Sha256" => hmac_b64,
        "X-Shopify-Shop-Domain" => "victim.myshopify.com",
      },
    )

    assert ShopifyAPI::Utils::HmacValidator.validate(request)
    # Registry.process would now dispatch to the shop/update handler with
    # shop == "victim.myshopify.com" and body == '{"note":"hi"}',
    # neither of which was actually signed for that shop/topic.
  end
end
```
Assertions: (1) `HmacValidator.validate(request)` returns `true` despite `topic`/`shop-domain` never being part of the signed content; (2) after `Registry.process(request)`, the stub handler's in-memory store contains an entry for `"victim.myshopify.com"` populated from an attacker-chosen body that was signed for a different topic/shop, demonstrating the broken binding `hmac == HMAC(secret, body)` ⇏ `(shop, topic)` authentic.
