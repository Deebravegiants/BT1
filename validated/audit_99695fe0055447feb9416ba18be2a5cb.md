## #VulnerabilityFound

### Title
`compareAddresses` uses case-sensitive equality for Bech32 addresses (BTC/LTC) and CashAddr (BCH), bypassing the self-transfer guard — ([File: packages/intents-sdk/src/lib/compareAddresses.ts])

### Summary
`compareAddresses` is the routine used to detect when a withdrawal's destination address is actually the token's own on-chain address, so the SDK can block the transfer (`DestinationAddressMatchesTokenAddressError`) before it is executed by the PoA bridge. For Bitcoin, Litecoin and Bitcoin Cash, the function falls back to a byte-for-byte `a === b` string comparison, even though `validateAddress` (which gates whether the destination is even accepted) explicitly permits case variants of Bech32/CashAddr addresses for these same chains. This is structurally the same class of bug as the Caddy advisory: a comparison meant to be case-insensitive skips normalization on one code path, letting a caller flip case to make two logically identical addresses look different and bypass a security check.

### Finding Description
In [1](#0-0) , `compareAddresses` special-cases hex-based chains (Aptos/Movement/Sui/Starknet lowercased via `normalizeHexAddress`), Stellar (`toUpperCase()`), TON, and Tron with canonical-form comparisons, but for `Chains.Bitcoin`, `Chains.BitcoinCash`, `Chains.Litecoin`, `Chains.Dogecoin`, `Chains.Zcash`, `Chains.Near`, `Chains.Solana`, `Chains.Fogo`, `Chains.XRPL`, `Chains.Cardano`, `Chains.Aleo`, `Chains.Dash` it falls through to plain `a === b`.

This is incorrect for Bitcoin/Litecoin Bech32 (BIP173) and Bitcoin Cash CashAddr addresses, both of which are explicitly case-insensitive formats, and `validateAddress` in the same package accepts case variants:
- `validateBtcBech32Address` normalizes the HRP with `decoded.prefix.toLowerCase()` and the test suite in [2](#0-1)  confirms fully-uppercase Bech32 BTC addresses (`BC1Q973XRRGJE6ETKKN9Q9AZZSGPXEDDATS8CKVP5S`) are accepted as valid.
- `validateBchCashAddr` explicitly lowercases the input before validating: [3](#0-2) .
- `validateLitecoinBech32Address` also lowercases the HRP before checking: [4](#0-3) .

So `validateAddress` treats case variants of the same Bech32/CashAddr address as valid and equivalent, but `compareAddresses` treats them as different strings when checking for a self-transfer.

The only caller that uses `compareAddresses` for this security-relevant purpose is `PoaBridge.validateWithdrawal`: [5](#0-4) . It fetches `tokenInfo.origin_chain_address` from the PoA bridge API (a canonical-case string) and compares it against the caller-supplied `args.destinationAddress` to decide whether to throw `DestinationAddressMatchesTokenAddressError`. Because `validateAddress` (called earlier at line 182) already accepted a case-flipped Bech32/CashAddr `destinationAddress` as a legitimate address, and `compareAddresses` performs a naive `a === b`, an attacker can supply the token's own address with different letter casing and have the equality check silently fail, letting the withdrawal proceed to the address that should have been blocked.

### Impact Explanation
This breaks the guarantee that a withdrawal cannot be routed to the token's own on-chain address. The bridge is designed to reject this because such a transfer causes stuck/unrecoverable funds. By simply flipping the case of a Bech32 (BTC/LTC) or CashAddr (BCH) address that is otherwise identical to `origin_chain_address`, the equality check misses the match, `validateWithdrawal` returns successfully, and the withdrawal intent is created and submitted — funds delivered to the token's own address with no recovery path, matching the High-impact category (funds delivered to a wrong/self address with no recovery).

### Likelihood Explanation
Likelihood is high: no privileged access is required, the "attack" is simply passing a differently-cased but otherwise valid address string, which `validateAddress` explicitly accepts for these chains. The only precondition is that the token's `origin_chain_address` for a BTC/LTC/BCH-native asset is a Bech32/CashAddr-format address returned in one canonical case by the bridge API, and the destination address the caller submits is a case-flipped variant.

### Recommendation
In `compareAddresses` (`packages/intents-sdk/src/lib/compareAddresses.ts`), canonicalize case before comparing Bech32/CashAddr address families the same way `validateAddress` does — e.g. lowercase before comparing for `Chains.Bitcoin`, `Chains.Litecoin`, `Chains.BitcoinCash` (and any other chain whose valid address encoding is case-insensitive), instead of relying on raw `a === b`.

### Proof of Concept
1. Suppose a BTC-native token's `origin_chain_address` (as returned by the PoA bridge's `getSupportedTokens`) is the Bech32 address `bc1qar0srrr7xfkvy5l643lydnw9re59gtzzwf5mdq`.
2. Caller invokes `PoaBridge.validateWithdrawal` with `destinationAddress = "BC1QAR0SRRR7XFKVY5L643LYDNW9RE59GTZZWF5MDQ"` (identical address, uppercase).
3. `validateAddress(destinationAddress, Chains.Bitcoin)` returns `true` (per `validateBtcBech32Address`, which lowercases the HRP before checking) — see the accepted uppercase example in [2](#0-1) .
4. `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, Chains.Bitcoin)` executes the `Chains.Bitcoin` branch `return a === b;` in [6](#0-5) , comparing `"bc1qar0srrr7xfkvy5l643lydnw9re59gtzzwf5mdq"` to `"BC1QAR0SRRR7XFKVY5L643LYDNW9RE59GTZZWF5MDQ"` — returns `false`.
5. `validateWithdrawal` therefore does **not** throw `DestinationAddressMatchesTokenAddressError` and the withdrawal to the token's own address proceeds, whereas the exact-case address in step 2 (per the existing test at [7](#0-6) ) would correctly be blocked.
