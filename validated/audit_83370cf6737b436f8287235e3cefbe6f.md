Based on available evidence, I found a concrete analog: the Tron port of the Intent Gateway is a standalone, unguarded reimplementation that lacks the reentrancy protection present in the canonical EVM contract.

### Title
Missing reentrancy guard on escrow/fee release path in Tron `IntentGatewayV2.withdraw` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The canonical EVM `IntentGatewayV2` inherits `ReentrancyGuardTransient` and applies a checks-effects-interactions (CEI) pattern (`_filled[commitment]` is set *before* any token transfer) in both `IntrinsicIntents._fillSameChain`/`_withdraw` and `ExtrinsicIntents._fillCrossChain`, specifically to close a reentrancy hole that previously allowed a malicious beneficiary to steal escrowed inputs and fees during the ETH/token transfer loop [1](#0-0) . This was verified by the dedicated Foundry test suite `IntrinsicIntentsReentrancyTest.sol`, which documents the exact pre-fix attack: a malicious beneficiary re-enters `fillOrder`/`_withdraw` from a `receive()` callback triggered by the native-token transfer, before the fill/finalize state is committed [2](#0-1) .

The Tron variant of this same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, is a separate, monolithic implementation (`contract IntentGatewayV2 is HyperApp, EIP712`) that does **not** inherit `ReentrancyGuardTransient` and does not share the `IntrinsicIntents`/`ExtrinsicIntents` split where the CEI fix lives [3](#0-2) .

### Finding Description
In the Tron contract, `cancelOrder`'s same-chain branch calls `withdraw(body, true)` directly to refund escrowed tokens (and any escrowed transaction fees) to the order owner, with no `nonReentrant` modifier anywhere in the contract and no visible pre-transfer commit of `_filled[commitment]` in that branch (only the "destination chain" cancellation branch explicitly sets `_filled[commitment]` before dispatching, and only for the cross-chain path) [4](#0-3) . The same `withdraw` function is also the settlement path invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` messages, which transfers escrowed input tokens and the escrowed fee-token balance to a beneficiary address supplied via the order/withdrawal request [5](#0-4) .

This mirrors exactly the `collectFees` bug class described in the report: a token/fee-release function that performs external transfers (native TRX `.call{value:}` or TRC-20/ERC-20 `transfer`/`transferFrom`) to an attacker-controlled `beneficiary` without a reentrancy guard. If the beneficiary is a contract, or if any of the escrowed tokens has a transfer hook (fee-on-transfer / callback tokens — which the codebase's own test suite explicitly exercises, e.g. `FeeOnTransferToken` in `IntentGatewayV2SameChainTest.sol` [6](#0-5) ), the transfer can re-enter `cancelOrder`/`withdraw`/`fillOrder` before the per-token escrow accounting (`_orders[commitment][token]`) or the `_filled` flag is updated, allowing the same escrow (including the collected transaction fee, `TRANSACTION_FEES`) to be drained multiple times — the same "drain tokens" primitive Spearbit flagged in the `collectFees` report.

### Impact Explanation
Because escrow accounting and the `_filled` sentinel are the only guards preventing double-payout of a single order's escrowed inputs and fees, and this Tron deployment has neither a reentrancy modifier nor a confirmed CEI ordering equivalent to the fixed EVM contract, a malicious order beneficiary/solver could repeatedly re-enter during token transfer to drain the contract's held liquidity for that trading pair/order, directly stealing user-escrowed funds — a concrete theft-of-funds impact, matching the "High Risk" severity of the original report.

### Likelihood Explanation
Likelihood is High for any order whose beneficiary is a contract with a receive/fallback hook, or whose escrowed/output token implements a transfer callback — both are permissionless, attacker-controllable choices at order-placement time (`beneficiary`, `token`), so no privileged access is required to trigger the reentrant call. This exactly matches the "unprivileged... token bridger, intent solver" reachability required by the analog rules.

### Recommendation
Port the same fix applied to `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: add a `nonReentrant`-equivalent guard (Tron's Solidity version supports standard `ReentrancyGuard`, since transient storage may be unavailable, so use the storage-based `ReentrancyGuard` rather than `ReentrancyGuardTransient`) to `fillOrder`, `cancelOrder`, and `withdraw`; and/or ensure `_filled[commitment]` (and any per-token escrow debit) is written *before* any external token transfer in every code path of `withdraw`, mirroring `IntentsBase._withdraw`'s ordering in the canonical EVM contract.

### Proof of Concept
Not independently verified — I was unable to read the full body of the Tron contract's `withdraw` function within the available tool budget to confirm whether it internally reorders state writes before transfers (a partial CEI fix without the explicit guard). The finding is based on: (1) the contract's declared inheritance omitting `ReentrancyGuardTransient` unlike the canonical EVM version, and (2) the `cancelOrder` same-chain branch invoking `withdraw` without first setting `_filled[commitment]`, unlike its destination-chain branch. A Devin session with full file access should read the complete `withdraw` function body in `evm/tron/contracts/apps/IntentGatewayV2.sol` to confirm the exact state-write ordering relative to the external transfer calls, and build a Foundry/Tron-compatible reentrant-beneficiary PoC analogous to `IntrinsicIntentsReentrancyTest.sol` before treating this as fully confirmed.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);
