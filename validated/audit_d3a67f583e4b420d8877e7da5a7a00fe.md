### Title
Missing zero-address validation on `Order.output.beneficiary` permits permanent burn of solver funds on native-token fills - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol` / `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntentGatewayV2.placeOrder` never validates that `order.output.beneficiary` (a `bytes32`-encoded address supplied by the unprivileged order-placing user) is non-zero. When a solver later calls `fillOrder`, the beneficiary is decoded and, for native-token outputs, the solver's payment is sent via a raw low-level `call` that succeeds even when the destination is `address(0)`, permanently burning the solver's funds while the order is still finalized and the escrowed input is released to the solver.

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol` (and the Tron variant `evm/tron/contracts/apps/IntentGatewayV2.sol`) accepts a fully user-supplied `Order` struct, including `order.output.beneficiary`, with no sanity check that this value is non-zero [1](#0-0) .

When a solver fills the order, both the same-chain and cross-chain code paths decode the beneficiary directly from the order without validation:

```
address beneficiary = address(uint160(uint256(order.output.beneficiary)));
``` [2](#0-1) [3](#0-2) 

For a native-token output (`token == address(0)`), the payment is delivered with `_sendValue`, which performs a raw low-level call and only reverts if the call itself reverts:
```
function _sendValue(address to, uint256 amount) internal {
    (bool sent,) = to.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
}
``` [4](#0-3) 

A call with value to `address(0)` succeeds (there is no code executing and no revert reason), so `_sendValue(address(0), amount)` silently sends ETH to the zero address, burning it irretrievably. This is invoked from `_fillSameChain`:
```
if (token == address(0)) {
    ...
    _sendValue(beneficiary, beneficiaryTotal);
    ...
``` [5](#0-4) 
and from `_fillCrossChain`:
```
if (token == address(0)) {
    if (msgValue < solverAmount) revert InsufficientNativeToken();
    uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
    _sendValue(beneficiary, beneficiaryTotal);
    msgValue -= (beneficiaryTotal + protocolShare);
``` [6](#0-5) 

Crucially, after this "delivery," the fill still proceeds to completion: `_execute` runs any attached calldata, and for cross-chain fills a `RedeemEscrow` message is dispatched back to the source chain to release the escrowed input tokens to the solver, regardless of whether the native-token payment to the beneficiary actually reached anyone [7](#0-6) . For same-chain fills, `_withdraw`/escrow release proceeds identically and the order is finalized with `_filled[commitment] = beneficiary` even when `beneficiary == address(0)` [8](#0-7) .

This is directly analogous to the reported issue: a fund-routing address parameter (`CoverageFundAddress` in the original report, here `order.output.beneficiary`) is never checked against `address(0)`/`bytes32(0)`, so a downstream fund-moving function (`_pullCoverageFunds` there, `_sendValue`/native-token payout here) silently proceeds with a zero address, but here the consequence is worse: the payer's real funds are irreversibly burned rather than merely skipped.

Note that for ERC20-denominated outputs, `IERC20.safeTransfer(beneficiary, amount)` would typically revert on a standards-compliant token if `beneficiary == address(0)` (OpenZeppelin's ERC20 explicitly reverts transfers to the zero address), so the practical impact is confined to native-token ("ETH-like") outputs, which is still a directly reachable, unprivileged path — any user can place such an order and any solver's bot that fills it automatically without validating the beneficiary loses its native-token payment.

### Impact Explanation
A malicious or careless order placer can craft an `Order` whose `output.beneficiary` is `bytes32(0)` and whose output asset is the native token. Any solver that fills this order via `fillOrder` — same-chain or cross-chain — has its native-token payment sent to `address(0)` and permanently burned, while the order is finalized and (for cross-chain orders) the user's escrowed input assets are still released to the solver via the dispatched `RedeemEscrow` message. This is a concrete, irrecoverable loss of solver funds triggered by a single unprivileged `placeOrder` transaction plus a normal `fillOrder` call — meeting the "concrete theft or permanent freezing of funds" bar. Because solver bots are typically automated and may not defensively check `beneficiary != 0` before committing capital, this is exploitable at scale against any solver that doesn't independently guard against it.

### Likelihood Explanation
Likelihood is high: `placeOrder` is fully permissionless and requires no special privilege, and `fillOrder` is the expected/normal interaction any solver performs to earn escrowed input tokens. No consensus proof, governance action, or privileged role is needed — only a maliciously (or accidentally) crafted order with a zero beneficiary and a native-token output, and a solver willing to fill it without validating the beneficiary client-side.

### Recommendation
Add an explicit zero-address check on `order.output.beneficiary` in `placeOrder` (rejecting `bytes32(0)`), and/or add a defensive check in `_fillSameChain`/`_fillCrossChain`/`_withdraw` before calling `_sendValue`/`safeTransfer`, reverting if the decoded beneficiary is `address(0)`. This mirrors the audit's recommendation to add a sanity check inside the setter (`CoverageFundAddress.set`) rather than silently allowing a zero-valued fund-routing address to reach a fund-movement function.

### Proof of Concept
1. Attacker (order placer) calls `placeOrder` with:
   - `order.output.assets = [{ token: bytes32(0), amount: X }]` (native token output)
   - `order.output.beneficiary = bytes32(0)`
   - valid `order.inputs` escrowed normally (e.g., USDC)
2. A solver bot observes the order and calls `fillOrder(order, options)` supplying `options.outputs[0].amount >= X` in native token (`msg.value`).
3. Inside `_fillSameChain` (or `_fillCrossChain` for cross-chain orders), `beneficiary = address(uint160(uint256(bytes32(0)))) = address(0)`.
4. `_sendValue(address(0), X)` executes `address(0).call{value: X}("")`, which succeeds (no code to revert), burning the solver's `X` native tokens.
5. The fill proceeds to completion: escrow is released/`RedeemEscrow` is dispatched, crediting the solver with the escrowed input tokens as if the native-token payment had been delivered — but the solver's native-token payment is permanently lost to `address(0)`.
