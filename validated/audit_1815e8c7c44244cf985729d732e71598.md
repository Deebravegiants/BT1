### Title
Webhook `shop-domain` (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, which signs/verifies only the raw HTTP body [1](#0-0) . The `shop` value used to identify *which tenant* the webhook belongs to is read from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is completely outside the signed material returned by `to_signable_string` [2](#0-1) . This breaks the identity binding: `hmac_valid(raw_body) == true` is treated as equivalent to `hmac_valid(raw_body) ∧ shop == authenticated_shop`, but the `shop` header is never part of what was signed.

### Finding Description
`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` accessor [3](#0-2) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [4](#0-3) , while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers that are never mixed into the signed string [5](#0-4) .

`Registry.process` then forwards `request.shop` directly into `WebhookMetadata`, which is the only tenant identifier passed to the app's `WebhookHandler#handle` [6](#0-5) [7](#0-6) . Because `shop` carries no cryptographic binding to the signed body, any two values `(raw_body, hmac)` that pass validation remain valid for *any* `shop-domain` header value an attacker chooses to send alongside them — the gem provides no mechanism, and the documented usage pattern gives the host application no signal, to detect that the header was swapped.

This is the direct analog of the Sherlock finding's root cause: a value that is *acted upon* downstream (there, `vaultShares` driving debt repayment; here, `shop` driving which tenant's data the handler mutates) is not covered by the same integrity check that gates the rest of the operation (there, `poolClaim` deriving from `strategyTokens`; here, HMAC deriving from `raw_body` only).

### Impact Explanation
An unprivileged actor who can install the app on their own store (a normal, unprivileged merchant — no special credentials required) can trigger a real Shopify-signed webhook for their own shop with an attacker-chosen resource (e.g., create a product/order with attacker-controlled fields), capture the genuine `(raw_body, hmac)` pair Shopify sends, and then resend that exact request to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks `raw_body` against the shared secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originates from the victim shop. If the host application (as documented/intended) uses `WebhookMetadata#shop` to select the tenant's DB record, credentials, or session, this yields cross-tenant data injection/corruption — satisfying the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's documented webhook-processing pattern [8](#0-7) : the attacker only needs the ability to install the app for their own store and to trigger any webhook topic they subscribe to (a routine unprivileged action), then replay the captured request with one modified header. No secrets, tokens, or privileged access are required — only the endpoint's public reachability.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) header values as part of the signed material verified against the HMAC, or independently authenticate the `shop` value (e.g., cross-check it against a known/expected shop for the webhook subscription, or require the host app to validate `shop` against its own webhook registration state before trusting `WebhookMetadata#shop`). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted to select tenant context without additional verification (e.g., matching against the shop that registered the specific webhook subscription/callback URL).

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and registers a webhook (e.g., `products/create`).
2. Attacker creates a product on their own store, causing Shopify to POST a genuinely HMAC-signed webhook to the app's callback:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: attacker-controlled JSON payload.
3. Attacker captures this exact `(raw_body, hmac)` pair.
4. Attacker resends the identical body and HMAC header to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only re-derives the HMAC from `raw_body` [3](#0-2) .
6. `Registry.process` constructs `WebhookMetadata` with `shop: "victim.myshopify.com"` and invokes the app's handler [9](#0-8) , causing the app to apply the attacker-crafted payload to the victim's tenant data.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
