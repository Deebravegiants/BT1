## Cross-Workflow HTTP Response Cache Confusion — Session/Cookie Data Served to Unrelated Workflow Executions

### Title
Gateway HTTP Action response cache key omits `WorkflowID`, allowing session-bearing cached responses (e.g. `Set-Cookie`) to be served across different workflow executions - (`File: core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
The Shopware CVE is a cache-key/scope bug: a session-cookie-bearing response gets cached and later served to unrelated visitors because the cache didn't account for session state. The chainlink gateway's `responseCache` has an analogous flaw: its cache key (`OutboundHTTPRequest.Hash()`) is documented as being "scoped by workflow ID to prevent cross-workflow data leakage" [1](#0-0) , but the implementation's own test suite proves `WorkflowID` is explicitly excluded from the hash while only `WorkflowOwner` participates [2](#0-1) .

### Finding Description
Outbound HTTP Action requests from workflow nodes are cached keyed by `req.Hash()`, which per test evidence is derived from method/URL/headers/body/`WorkflowOwner` but is invariant to `WorkflowID` [3](#0-2) . The cache `Set`/`Fetch` operations use this hash directly [4](#0-3) , and `makeOutgoingRequest` decides whether to read/write the shared cache purely from per-request `CacheSettings`, independent of which specific workflow execution issued the request [5](#0-4) .

Cached responses are full HTTP response objects, including arbitrary response headers such as `Set-Cookie`. The handler explicitly forwards `Set-Cookie`/session-bearing headers from the external endpoint into the cached `OutboundHTTPResponse` without stripping them [6](#0-5) , and this is exercised by tests using `sessionid=...` and `csrf_token=...` cookies [7](#0-6) .

Consequently, two distinct workflow executions belonging to the same `WorkflowOwner` that happen to issue an identical outbound request (same method/URL/headers/body) will collide on the same cache entry even though the README claims workflow-level isolation. If the external endpoint's response is session- or execution-specific (e.g., a `Set-Cookie` reflecting a per-call auth/session token, or a per-execution authorization artifact), the second workflow's node will receive the first workflow's cached response — including any session cookie/secret material — via `sendResponseToNode` [8](#0-7) .

### Impact Explanation
This is a cross-execution response confusion: unrelated workflow executions (owned by the same address but logically distinct, e.g. different workflow definitions or different runs) can receive another execution's cached HTTP response, potentially including session cookies, CSRF tokens, or other sensitive per-call data returned by the external endpoint. This mirrors the Shopware bug class (CWE-524, Information Exposure Through Caching) but manifests as cross-workflow leakage inside the gateway rather than cross-browser-session leakage on a CDN edge.

### Likelihood Explanation
Exploitability requires two workflow executions under the same owner to issue outbound HTTP Action requests with identical method/URL/headers/body and `Store`/`MaxAgeMs` cache settings enabled — a realistic scenario for workflows that periodically call the same external API endpoint with static headers (e.g., polling a webhook or API that sets a session cookie per response). No special privilege beyond normal workflow-node participation is needed; it is triggered purely through the documented HTTP Action + caching feature.

### Recommendation
Include `WorkflowID` (not just `WorkflowOwner`) in the cache key hash used by `responseCache`, matching the documented isolation guarantee, and/or strip session-identifying response headers (`Set-Cookie`, auth-bearing headers) before storing responses in the shared cache.

### Proof of Concept
1. Workflow A (owner `0xabc`, workflow ID `wf-1`) issues an `OutboundHTTPRequest` to `https://api.example.com/data` with `CacheSettings{Store:true, MaxAgeMs:600000}`; the external endpoint responds `200` with `Set-Cookie: sessionid=A-secret`.
2. `responseCache.Set`/`Fetch` stores this response keyed by `Hash()`, which does not include `wf-1` [3](#0-2) .
3. Workflow B (same owner `0xabc`, different workflow ID `wf-2`) issues an identical request (same method/URL/headers/body) with caching enabled before TTL expiry.
4. `responseCache.Fetch` returns the cached entry from step 1, and workflow B's node receives workflow A's `Set-Cookie: sessionid=A-secret` header via `sendResponseToNode`, despite belonging to a distinct workflow execution.

```go
// isExpiredOrNotCached returns true if the cached response is expired or not cached.
// IMPORTANT: this method does not lock the cache map. MUST be called with cacheMu write-locked.
func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}

// Fetch fetches a response from the cache if it exists and
// the age of cached response is less than the max age of the request.
// If the cached response is expired or not cached, it fetches a new response from the fetchFn
// and caches the response if it is cacheable and storeOnFetch is true.
//
// The mutex is only held during cache map access (microseconds), not during fetchFn execution.
// Singleflight deduplicates concurrent requests to the same cache key so only one fetchFn
// runs per key, while requests to different keys execute in parallel.
// Cache read and write happen inside the singleflight callback to ensure the key remains
// in-flight until the result is stored, preventing duplicate fetches.
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
```
