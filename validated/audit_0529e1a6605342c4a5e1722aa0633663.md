### Title
Unauthenticated `intents_getBidsForOrder`/`intents_subscribeBids` RPC exposes every filler's full signed bid (UserOperation) for an order, enabling front-running/theft of solver fills - ([File: modules/pallets/intents-coprocessor/rpc/src/lib.rs])

### Summary
The `pallet-intents-coprocessor` RPC extension exposes two endpoints — `intents_getBidsForOrder` and the `intents_subscribeBids` subscription — that return the full contents of every bid placed on an order commitment (mempool and finalized), with no access control at all: any caller with RPC access, including any unprivileged filler/bidder or bystander, can read or subscribe to every other filler's signed `PackedUserOperation` for an in-progress order. This is the same bug class as CVE-2022-23490: a client-facing collection/subscription endpoint discloses the full contents of competing participants' submissions (poll responses / bid payloads) to any subscriber, not just to parties entitled to see them.

### Finding Description
`place_bid` lets any signed filler submit a bid for an order commitment, storing a deposit on-chain and the actual `Bid { filler, user_op }` payload in offchain storage: [1](#0-0) 

The RPC handler `get_bids_for_order` merges the in-memory mempool bid cache with on-chain/offchain bid data and returns the raw `user_op` bytes for **every filler** that has bid on the given commitment — with no origin/signature/permission check on the RPC call itself: [2](#0-1) [3](#0-2) 

There is also a push-based subscription, `intents_subscribeBids`, that streams every `BidPlaced` event's full payload to any subscriber the moment a bid enters the mempool — before the block is even produced: [4](#0-3) [5](#0-4) 

The RPC and SDK are explicitly designed to be called by anyone (fillers, the indexer, the Simplex solver's phantom-bid aggregation) to "discover" bids in real time: [6](#0-5) 

The disclosed `user_op` is not a price quote alone — it is a fully signed, executable `PackedUserOperation` (sender, calldata, signature) that a solver intends to submit to the ERC-4337 EntryPoint to perform `select()`/`fillOrder()` on the destination chain, per the documented solver-selection flow: [7](#0-6) 

Because this signed operation is broadcast to unauthorized third parties before the order's winner is finalized on-chain, any RPC caller can:
1. Observe a competing filler's exact fill parameters and pricing the instant the bid enters the mempool (via subscription) or via a single unauthenticated query, and undercut it with a marginally better bid before the bid window / selection closes.
2. Extract another filler's already-signed, valid `PackedUserOperation` and resubmit/front-run it to the EntryPoint on the destination chain ahead of the original submitter, since the bundler/EntryPoint has no additional binding to the original submitter beyond the signature carried on the exposed operation.

This mirrors the BigBlueButton flaw precisely: a client-facing collection (`current-poll` / `Bids`) that is supposed to reveal only the requester's own submission instead reveals every participant's submission to any subscriber, because the publish/RPC layer performs no per-caller authorization check.

### Impact Explanation
Exposing every competing filler's signed bid/UserOperation to any unauthenticated party allows systematic front-running and bid-sniping of the intents solver market: a malicious actor can always observe and beat or steal every other solver's fill before it settles, extracting the fee/spread that should accrue to the original bidder and, in the front-run case, directly hijacking somebody else's already-signed authorization to execute the fill and collect the reward. This is a concrete theft-of-value vector (solver fees/spread) that specifically targets the "relayer fee and reward accounting" / "intents escrow and bids" surface reachable by any unprivileged bidder or bystander — no privileged role is required, matching Medium severity for information disclosure enabling value extraction.

### Likelihood Explanation
The RPC methods are unauthenticated by design (no origin check, no filter on caller identity) and are documented/used by external tooling (SDK, indexer, Simplex filler) precisely because they are meant to be publicly callable for bid aggregation. Any actor who can reach the node's RPC endpoint — which is the same trust level as "an unprivileged filler/bidder" explicitly in scope — can call `intents_getBidsForOrder` or subscribe via `intents_subscribeBids` with zero cost and no special access, making exploitation trivial and continuous for every order placed.

### Recommendation
Scope disclosure of another filler's `user_op` payload: either (a) only return a caller's own bid via an authenticated/signed RPC call, (b) redact/hash the sensitive fields (calldata, signature) until the bid window closes or the order is finalized, revealing full payloads only after selection is locked in, or (c) rate/permission-gate the subscription to the order's owner/selected session key rather than broadcasting every bid to any subscriber.

### Proof of Concept
1. Filler A submits `place_bid(commitment, user_op_A)` via `author_submitExtrinsic`.
2. Any unauthenticated third party calls `intents_getBidsForOrder(commitment)` (or is already subscribed via `intents_subscribeBids`) and immediately receives `user_op_A` in full, including its calldata and valid signature, per the RPC handler: [3](#0-2) 
3. The third party either (a) crafts a competing bid with a marginally better price before Filler A's bid window closes, or (b) resubmits `user_op_A` directly to the destination chain's EntryPoint ahead of Filler A, executing the fill and collecting the associated fee/reward that Filler A intended to earn — demonstrated functionally by the existing test that any RPC caller (not just the bidder) can retrieve all bids for a commitment: [8](#0-7)

```rust
		#[pallet::weight(T::WeightInfo::place_bid())]
		pub fn place_bid(
			origin: OriginFor<T>,
			commitment: H256,
			user_op: BoundedVec<u8, ConstU32<1_048_576>>,
		) -> DispatchResult {
			let filler = ensure_signed(origin)?;

			// Validate user_op is not empty
			ensure!(!user_op.is_empty(), Error::<T>::InvalidUserOp);

			// Phantom orders have stricter rules: one bid per filler, no updates, and only
			// within the configured acceptance window after the order was registered. Every
			// chain's active order is checked, not just the most recently generated one.
			if let Some(active) = CurrentPhantomOrder::<T>::get() {
				if let Some((_, info)) = active.iter().find(|(c, _)| *c == commitment) {
					let window: BlockNumberFor<T> = Self::phantom_bid_window().into();
					ensure!(
						frame_system::Pallet::<T>::block_number() <= info.created_at_block + window,
						Error::<T>::PhantomOrderBidWindowClosed
					);
					ensure!(
						!Bids::<T>::contains_key(&commitment, &filler),
						Error::<T>::DuplicatePhantomBid
					);
				}
			}

			// If a bid already exists, unreserve the old deposit first
			if let Some(old_deposit) = Bids::<T>::get(&commitment, &filler) {
				<T as Config>::Currency::unreserve(&filler, old_deposit);
			}

			let deposit = Self::storage_deposit_fee();

			// Reserve the new deposit
			<T as Config>::Currency::reserve(&filler, deposit)
				.map_err(|_| Error::<T>::InsufficientBalance)?;

			// Store the bid in offchain storage
			let bid = Bid { filler: filler.clone(), user_op: user_op.to_vec() };
			let offchain_key = Self::offchain_bid_key(&commitment, &filler);
			offchain_index::set(&offchain_key, &bid.encode());

			// Store deposit amount in onchain storage for discoverability and accurate refunds
			Bids::<T>::insert(&commitment, &filler, deposit);

			Self::deposit_event(Event::BidPlaced { filler, commitment, deposit });
```

```rust
	fn get_bids_for_order(&self, commitment: H256) -> RpcResult<Vec<RpcBidInfo>> {
		// Get mempool bids from in-memory cache
		let mut bids =
			self.bid_cache.get_bids(&commitment).map_err(runtime_error_into_rpc_error)?;

		// Query on-chain bids via StorageProvider and read bid data from offchain storage.
		let best_hash = self.client.info().best_hash;
		let prefix = bids_storage_prefix(&commitment);
		let prefix_key = sp_core::storage::StorageKey(prefix.clone());

		let keys = self
			.client
			.storage_keys(best_hash, Some(&prefix_key), None)
			.map_err(runtime_error_into_rpc_error)?;

		const MAX_ON_CHAIN_BIDS: usize = 30;

		for key in keys.take(MAX_ON_CHAIN_BIDS) {
			// Key layout after prefix: blake2_128(filler) ++ filler_encoded
			let filler_start = prefix.len() + 16;
			if key.0.len() > filler_start {
				let filler_encoded = &key.0[filler_start..];

				let offchain_key =
					pallet_intents_coprocessor::offchain_bid_key_raw(&commitment, filler_encoded);

				if let Some(data) = self.offchain_storage.get(STORAGE_PREFIX, &offchain_key) {
					// Bid encoding: filler.encode() ++ user_op.encode()
					if data.len() > filler_encoded.len() {
						if let Ok(user_op) = Vec::<u8>::decode(&mut &data[filler_encoded.len()..]) {
							bids.insert(RpcBidInfo {
								commitment,
								filler: filler_encoded.to_vec(),
								user_op,
							});
						}
					}
				}
			}
		}

		Ok(bids.into_iter().collect())
	}
```

```rust
	async fn subscribe_bids(
		&self,
		pending: PendingSubscriptionSink,
		commitment: Option<H256>,
	) -> SubscriptionResult {
		let mut rx = self.bid_sender.subscribe();
		let sink = pending.accept().await.map_err(|e| {
			runtime_error_into_rpc_error(format!("Failed to accept subscription: {e}"))
		})?;

		tokio::spawn(async move {
			while let Ok(bid) = rx.recv().await {
				if let Some(ref filter) = commitment {
					if &bid.commitment != filter {
						continue;
					}
				}
				if let Ok(msg) = SubscriptionMessage::from_json(&bid) {
					if sink.send(msg).await.is_err() {
						break;
					}
				}
			}
		});

		Ok(())
	}
```

```typescript
	private async getBidsViaRpc(commitment: HexString): Promise<FillerBid[]> {
		const api = await this.http()
		// eslint-disable-next-line @typescript-eslint/no-explicit-any

			return { filler, userOp, deposit: 0n }
		})
```

```text
## Solver Selection

When `solverSelection` is enabled in the intent gateway parameters, orders are protected from unauthorized fills. At order placement, the user specifies a `session` key — a temporary keypair generated for this order. Only a solver explicitly authorized by the session key can fill the order.

### `SolverAccount`

The SolverAccount is a smart account designed for solvers that combines [ERC-4337](https://eips.ethereum.org/EIPS/eip-4337) (account abstraction), [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702), and [ERC-7821](https://eips.ethereum.org/EIPS/eip-7821) (batch execution) to batch `gateway.select(...)` and `gateway.fillOrder(...)` into a single atomic UserOperation. Solvers delegate their EOA to the SolverAccount via EIP-7702 and submit bundled operations through the ERC-4337 EntryPoint.
```
