## Title
Griefable `_executePermit` in `SimplexPaymaster` can be front-run to permanently burn a solver's PERMIT-mode delegation bootstrap - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster`'s mode `0x00` (`PERMIT`) path executes a raw EIP-2612 `permit()` call using signature data that is fully visible on-chain/in the alt-mempool inside the UserOperation's `paymasterData`. Because `permit()` is permissionlessly callable by anyone with the (owner, spender, value, deadline, v, r, s) tuple, an observer can front-run the intended UserOperation with a direct call to the token's `permit()`, consuming the signer's EIP-2612 nonce before the paymaster's own call executes. This is the same class of vulnerability described in the analog report for `wstToken.depositWithSignature()`.

### Finding Description
`_executePermit`, invoked from `_validatePaymasterUserOp` for mode `0x00` paymasterData, calls the token's `permit()` directly and reverts the whole validation if that call fails: [1](#0-0) 

```solidity
function _executePermit(PackedUserOperation calldata userOp) internal {
    ...
    address owner = userOp.sender;

    try IERC20Permit(tokenAddr).permit(owner, address(this), permitAmount, deadline, v, r, s) {
        emit PermitExecuted(tokenAddr, owner, permitAmount);
    } catch {
        revert PermitFailed(tokenAddr);
    }
}
```

This is called from `_validatePaymasterUserOp` before the base prefund logic runs: [2](#0-1) 

The `catch` block has no fallback that checks whether the required allowance already exists (e.g. via `token.allowance(owner, address(this)) >= permitAmount`); it simply reverts. The (v, r, s) fields are embedded in plaintext in `paymasterData`, which is broadcast to the ERC-4337 alt-mempool before inclusion, exactly mirroring the mempool-visibility precondition in the original report. An attacker can extract these fields and submit a standalone `permit()` call for the same `(owner, spender, value, deadline)` tuple, consuming the owner's sequential EIP-2612 nonce. When the original UserOperation is subsequently processed, `_executePermit`'s `permit()` call reverts (nonce mismatch), and the `catch` unconditionally reverts `PermitFailed`, failing `_validatePaymasterUserOp` for the entire UserOperation.

Per the codebase's own design docs, mode `0x00` PERMIT is intentionally scoped to exactly one caller path — the one-time, per-chain delegation bootstrap UserOp sent by a solver account with no existing Permit2 allowance: [3](#0-2) . This is precisely the "single sequential counter per owner" nonce hazard the SDK team already identified as fatal for concurrent ops but accepted as safe here "because the delegation... provably has no concurrent sibling" — that reasoning addresses self-collision, not adversarial front-running.

### Impact Explanation
An unprivileged third party observing the alt-mempool can grief a solver's chain-bootstrap operation: every time the solver signs and submits a PERMIT-mode delegation UserOp, the attacker front-runs the raw `permit()` call, forcing `_executePermit` to revert and the entire UserOperation to fail validation. Since the signed permit's nonce is now burned, the solver must generate an entirely new signature with a fresh nonce, and the attacker can repeat this indefinitely at negligible cost (one `permit()` call, no funds at risk). This permanently denies the solver the ability to bootstrap through the gas-sponsored, zero-native PERMIT path on that chain, forcing a fallback to native-funded `approve(Permit2, max)` transactions — degrading or entirely blocking the low-cost intent-solving bootstrap path on any chain where the solver holds fee-token stablecoins but no native gas.

### Likelihood Explanation
High for a targeted actor: PERMIT-mode paymasterData (including v, r, s) is plainly visible to anyone watching the ERC-4337 bundler/alt-mempool prior to inclusion, exactly as in the referenced report. No special privileges, capital, or timing precision beyond ordinary front-running are required, and the attack is cheap and infinitely repeatable against a specific solver/chain pair.

### Recommendation
Wrap the permit call so a nonce-race caused by front-running does not brick the entire UserOperation, mirroring the report's suggested fix: in the `catch` branch of `_executePermit`, check `IERC20(tokenAddr).allowance(owner, address(this)) >= permitAmount` before reverting, and proceed if the allowance is already sufficient (i.e., the front-run granted the exact intended allowance) rather than unconditionally reverting `PermitFailed`.

### Proof of Concept
1. Solver signs an EIP-2612 permit `(owner=solverAccount, spender=SimplexPaymaster, value=permitAmount, deadline, v, r, s)` and submits a PERMIT-mode (`0x00`) UserOperation to the bundler.
2. Attacker observes the pending UserOperation in the alt-mempool, extracts `(v, r, s, permitAmount, deadline)` from `paymasterData`.
3. Attacker calls `token.permit(solverAccount, SimplexPaymaster, permitAmount, deadline, v, r, s)` directly with higher priority fee, consuming the solver's EIP-2612 nonce.
4. Bundler includes/simulates the solver's original UserOperation; `_executePermit` (`evm/src/utils/SimplexPaymaster.sol:644`) calls `permit()` again with the same nonce, which reverts; the `catch` block unconditionally reverts `PermitFailed`, failing `_validatePaymasterUserOp` for the whole op.
5. Attacker repeats steps 2–4 on every subsequent bootstrap attempt, permanently denying the solver the sponsored, zero-native PERMIT bootstrap path on that chain.

# 2026-09-08 — EIP-2612 is the bootstrap authorization, and nothing else

Chosen: the `permitBootstrap` flag, set only by `DelegationService`'s first-time delegation
op, lets that one op authorize with an EIP-2612 permit when the fee token has no Permit2
allowance yet. The same op carries `approve(Permit2, max)` in its callData. Every other
sponsored op — fills, bids, vault sweeps, token sends — authorizes through Permit2 with no
way to reach the permit path.

Alternatives considered: dropping 2612 outright (the previous entry) and accepting that a
fresh solver needs native dust per chain; or restoring 2612 as the general preference for
permit-capable tokens, as it was before.

Why the scoping is the whole design. The objection to 2612 is its nonce: one sequential
counter per owner, so two permits signed for the same solver carry the same value and only
one lands. That is fatal for fills, which are the ops that actually run concurrently. It is
free for the delegation, which happens once per chain and provably has no concurrent
sibling — the account is not even delegated yet. Confining the permit to that op keeps the
serialization hazard away from everything that could hit it.

Dropping it outright lost more than it looked. The permit is the only authorization that
needs no prior on-chain state, so it is the only way an account with stablecoins and zero
native can pay for anything. Requiring native dust per chain sounds minor until it is the
operator's first run on a new chain and the failure is "send ETH here" rather than "it
worked".
