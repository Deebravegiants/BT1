## Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request` computes its HMAC-verifiable content from the raw body only, while `shop` (parsed from the `X-Shopify-Shop-Domain` header) is passed on, unverified, as the tenant identity for the webhook handler. Because the header is not part of the signed data, a valid signature obtained for one shop's webhook payload remains valid if the `shop-domain` header is swapped for a different (victim) shop, breaking the binding `HMAC-verified-bytes == identity-used-by-handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC solely against `to_signable_string`, i.e. the raw body: [3](#0-2) 

`Webhooks::Registry.process` trusts this validation result and then forwards `request.shop` — the unauthenticated header value — as the tenant identity to the app's registered handler: [4](#0-3) 

Because the shop domain is never part of the signable string, any request body+HMAC pair that Shopify legitimately signs for shop A (e.g. a webhook delivered to an app installed on the attacker's own store) remains a **valid** HMAC for the exact same body when replayed with the `shop-domain` header changed to shop B. The equality the code implicitly assumes — "bytes verified by HMAC" == "identity (`shop`) acted on by the handler" — does not hold, since `shop` is outside the HMAC-covered bytes.

### Impact Explanation
An attacker who controls their own Shopify store (unprivileged relative to any other merchant) can install the target app on their store, trigger a webhook of a topic they control (e.g. `products/update` with attacker-chosen resource IDs/body), capture the valid `X-Shopify-Hmac-Sha256` + raw body pair Shopify sends, and replay it to the app's webhook endpoint with `X-Shopify-Shop-Domain` rewritten to a victim shop's domain. `Registry.process` will treat this as an authentic webhook for the victim tenant because `HmacValidator.validate` only checks body integrity, not origin/tenant binding. This is a cross-tenant identity-spoofing vector at the point where the app's `WebhookHandler` consumes `WebhookMetadata#shop` to decide which tenant's data to update/act on, satisfying the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only an unprivileged Shopify merchant account (attacker's own store) with the target app installed and a webhook subscription for at least one topic — a low bar, no special credentials, TLS interception, or leaked secrets needed. The attacker fully controls both the raw body (via the resource they modify) and the HTTP headers of the replayed request.

### Recommendation
Include the shop domain (and ideally topic / webhook id) in the HMAC-signed content, or independently bind the verified request to the claimed shop before dispatching to handlers — e.g. verify that the `shop-domain` header matches a shop the app has an active session/webhook registration for, or compute the signature over `shop + topic + raw_body` rather than `raw_body` alone.

### Proof of Concept
1. Install the app on attacker-controlled `attacker-shop.myshopify.com`; register/receive a webhook (e.g. `products/update`).
2. Capture the genuine POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `HMAC(secret, B) == H`).
3. Resend the exact same body `B` and header `H` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb:190` still returns `true` (signature only covers `B`), so `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled data under the victim's tenant identity.
