## Finding

### Title
Webhook HMAC signature covers only the raw body, not the `shop-domain` header, allowing a valid webhook signature to be replayed with a spoofed shop identity - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator` validates the HMAC exclusively against that body. The `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which the `Registry` hands to the app's webhook handler as the authoritative tenant identifier, is never part of the signed material. Consequently, an attacker who possesses any single valid `(body, hmac)` pair for their own store's webhook delivery can resend that exact request to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop, and it will still pass `HmacValidator.validate`.

### Finding Description
The identity binding that should hold is:
`hmac == HMAC(secret, body || shop)` for the `shop` value that the handler subsequently treats as the tenant.

Instead, the actual binding implemented is:
`hmac == HMAC(secret, body)` only, independent of `shop`.

Concretely:
- `Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 
- `Webhooks::Request#shop` is read straight from an HTTP header with no cryptographic binding to the signed content: [2](#0-1) 
- `Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the body, and compares it to the received HMAC: [3](#0-2) 
- `Registry.process` gates on this body-only HMAC check and then forwards the unauthenticated `request.shop` value straight to the app's handler as the tenant identity, alongside the verified body: [4](#0-3) 

Because `shop` is not covered by the signature, any request whose body+hmac pair is valid for *some* shop will also be judged valid regardless of which `shop-domain` header value is attached to it. An attacker who legitimately receives (or triggers) one authentic webhook delivery — e.g. by installing the app on their own store, or on any store they control, and capturing one webhook body+HMAC — can replay that same body/HMAC pair to the app's public webhook endpoint while substituting a different value in `x-shopify-shop-domain`, and the gem will report the webhook as authentic (`Utils::HmacValidator.validate` returns `true`), then hand `WebhookMetadata` with the attacker-chosen `shop` to the app's handler as if Shopify itself vouched for that shop/body pairing.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is supposed to enforce for webhook delivery: the `shop` value passed to the app's `handler.handle` is treated by downstream app code as an authenticated statement "this body event happened for this shop," but the gem provides no cryptographic guarantee that `shop` and `body` are truly paired by Shopify. This satisfies the cross-tenant access criterion — an attacker can cause the app to process/attribute webhook data under a shop identity of their choosing, using a signature that was never computed over that identity, which can lead to cross-tenant state confusion or unauthorized actions being taken against a shop the attacker does not control.

### Likelihood Explanation
The only prerequisite is a single authentic webhook delivery for a shop the attacker controls or can trigger (e.g., their own free/dev install), and network access to the target app's public webhook receiver endpoint (a normal exposed HTTP endpoint by design). No `api_secret_key`, access token, or other privileged credential is required — the attacker never needs to compute a new HMAC, only to relay one they already legitimately hold. Whether this is exploitable in practice depends on what individual host applications do with `data.shop`, but the gem itself provides no protection or documentation warning that `shop` is unauthenticated, so any handler that trusts `data.shop` for tenant scoping (a natural and common pattern) inherits the flaw directly from the gem's verification contract.

### Recommendation
- Document explicitly (and ideally enforce) that `Registry.process`'s `request.shop` is not covered by the HMAC and must not be trusted as a tenant identifier on its own.
- Where feasible, extend the verification so that the `shop` header is cross-checked against a shop known/registered by the app (e.g., matching an existing installed-shop session store) before dispatching to the handler, or surface a distinct "verified body only" vs. "claimed shop" attribute so integrators cannot conflate the two.
- Consider exposing a combined verification helper that requires the caller to supply the expected shop and fails closed if the header does not match a caller-supplied expectation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or otherwise legitimately receives one webhook delivery), capturing the exact raw body `B` and the associated `X-Shopify-Hmac-Sha256` value `H` that Shopify sent for a webhook topic the app subscribes to.
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint using:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256`: `H` (unchanged)
   - Header `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (changed)
   - Header `X-Shopify-Topic`: unchanged
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and it matches `H`, so validation passes: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` even though Shopify never issued this body for that shop: [6](#0-5) 
6. Any app logic keyed off `data.shop` (e.g., updating per-shop records, triggering shop-scoped side effects) now executes under the wrong tenant identity, using an attacker-supplied header the gem never authenticated.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
