### Title
Unvalidated `assets` pool address in the swap payload puts attacker-controlled code inside the caller's authorization tree, enabling wallet drain via `swap_collateral`/`execute_strategy` - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
The advisory's bug class is "a caller-supplied configuration field names a resource that is resolved and consumed without validation" (CWE-73 external control of path / CWE-641 restricted name). The exact analogue exists in the swap router: every hop's `pool` address comes straight out of the caller-supplied `StrategyPayload.assets` registry, and there is no allowlist of pools or tokens. The router invokes whatever contract the payload names during `dispatch_hop`, so attacker-chosen code executes inside the `sender`'s `require_auth` subtree. A malicious venue contract can issue `token.transfer(victim, attacker, amount)` for any token in the victim's wallet; Soroban records that transfer as a child of the victim's auth entry, and if the victim signs the simulated tree, it executes. This turns a routed swap into theft of the caller's entire wallet, not just the routed `total_in`.

### Finding Description
`execute_op` builds each `SwapHop` by indexing the untrusted `assets` registry: `pool: ctx.assets.get_unchecked(op.idx_a)`, `token_in`, `token_out` — all attacker-controlled [1](#0-0) . `dispatch_hop` then calls the venue adapter, which invokes `hop.pool` (e.g., Soroswap/Phoenix/Sushi/Aquarius adapters call `swap`-like functions on that address) [2](#0-1) . Nothing validates that `hop.pool` is a legitimate pool contract or that `token_in`/`token_out` are listed assets — the only checks are measured balance deltas on the router itself (`ZeroOutput`, `spent != amount_in → InvalidAmount`) [3](#0-2) .

Because the router's only user authorization is `sender.require_auth()` [4](#0-3) , any `require_auth` on the `sender` issued by the rogue pool contract is recorded as a child invocation under the sender's auth entry. The project's own test proves this: `RogueHopPool::swap` calls `token::Client::transfer(victim, attacker, amount)` on an unrelated wallet token, simulation records the stolen transfer as a `sub_invocation` of the caller's `swap_collateral` auth entry, and enforcing mode accepts it if signed [5](#0-4) [6](#0-5) . The threat model acknowledges the exposure: "the router calls the pool and token addresses its payload names and keeps no allowlist of them... The loss is then the caller's wallet, not the routed amount" [7](#0-6) .

This is reachable by a single unprivileged address through `execute_strategy` directly (any swap user) and through the controller strategy verbs `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`, all of which accept the same `swap_xdr` bytes as an argument.

### Impact Explanation
Theft of user funds. A crafted payload routes through an attacker-deployed contract that, while on the stack, transfers arbitrary tokens held by the victim (or any allowance/auth the victim's signature covers) to the attacker. The measured-delta accounting and `total_min_out` check bound only the routed amount; they do not bound the rogue contract's use of the victim's authorized signature. A victim swapping 5,000 USDC can lose an unrelated wallet balance of any size, as demonstrated in the test where `WALLET_BALANCE` of a token the protocol never listed is drained to the attacker [8](#0-7) .

### Likelihood Explanation
Exploitation requires the victim to sign a poisoned authorization tree, which an honest client can detect — the documented mitigation is entirely client-side ("a client must decode the route it signs and refuse an authorization tree with any other child") [9](#0-8) . However, routes are built off-chain and passed as opaque XDR bytes that most wallets render poorly, so a malicious or compromised quote source — or any phishing path supplying a crafted `swap_xdr` — yields silent wallet drain. The on-chain contract does nothing to restrict which contracts the payload may name, so the trust boundary is unenforced at the contract layer. Medium severity mirrors the advisory: real impact, conditional on user signing behavior, no protocol-side mitigation.

### Recommendation
Maintain an on-chain allowlist (registry) of approved venue pool/token addresses per venue opcode, set administratively, and reject any `Swap`/`Burn`/`Mint` instruction whose `assets`-resolved pool is not registered — failing closed with `InvalidRouteXdr`. Alternatively, at minimum, document-enforce that the router never calls an address that is not a token contract it already custodies for that call. Clients should additionally verify decoded payload `assets` before signing, per `verifyRouteBytes` [10](#0-9) .

### Proof of Concept
The repository already contains an executable PoC in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Attacker deploys `RogueHopPool` whose `swap` entrypoint calls `token.transfer(victim, attacker, WALLET_BALANCE)` on a wallet token the protocol never listed [5](#0-4) .
2. A route payload names the rogue contract as `hop_pool` via `route_through_pool_stealing`, embedded in a normal `swap_collateral` call by Alice [11](#0-10) .
3. The recorded auth tree shows the stolen `transfer` attached as a `sub_invocation` of Alice's `swap_collateral` entry [12](#0-11) .
4. Result: Alice's wallet balance of the unrelated token is 0, the attacker holds `WALLET_BALANCE`, and the swap itself still completes normally [8](#0-7) .

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
