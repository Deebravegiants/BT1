### Title
Liquidity index (`lindex`) used for zToken oracle pricing can diverge from the vault's actual redeemable share price - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The Pendle report describes an oracle that prices collateral using a formula (`SY.exchangeRate()`) that is *independent* of what a real redemption actually returns, so the two values can drift apart and collateral gets over-valued. In Zest, the market's collateral oracle for zTokens does exactly the analogous thing: it prices a zToken as `underlying_price * lindex / INDEX-PRECISION` (`resolve-ztoken` in `mainnet/contracts/market/v0-4-market.clar`), while the *actual* redeemable amount per zToken share is computed by the vault via a completely separate formula, `convert-to-assets-preview` = `total-assets-preview / total-supply-preview` (`mainnet/contracts/vault/v0-vault-usdc.clar`). These two values are supposed to track the same economic quantity (net-of-reserve-fee value per share) but are derived through different, independently-compounded computations.

### Finding Description
`resolve-ztoken` prices a zToken purely from the compounding `lindex` variable: [1](#0-0) 

`lindex` is advanced every accrual using `next-liquidity-index`, which compounds a synthetic "liquidity rate" (`borrow_rate * utilization * (1 - fee_reserve)`) over the elapsed time, rounding **down**: [2](#0-1) 

The *actual* redeemable underlying per share, however, is computed completely independently in `convert-to-assets-preview`, using `total-assets-preview` (gross interest added to `assets`, rounded **up** via `next-index`) divided by `total-supply-preview` (current supply plus treasury shares minted to dilute for the reserve fee): [3](#0-2) 

These two paths — (a) direct compounding of a "liquidity rate" applied to `lindex`, and (b) diluting `total_supply` by treasury shares while growing `total_assets` by the full/gross interest — are mathematically different operations. They are only approximately equal in the general case; they are not driven by the same value identity and there is no code that reconciles them. The oracle-facing value (`lindex`) is exactly analogous to Pendle's `SY.exchangeRate()`: it's a formula-derived approximation of redeemable value that the market treats as ground truth for collateral valuation, while the vault's own `redeem()` function computes the actually-enforced (`min-out`) redeemable amount via the separate `convert-to-assets-preview` path: [4](#0-3) 

### Impact Explanation
If `lindex`-based pricing structurally overstates the true `convert-to-assets-preview` ratio (due to the different rounding directions/compounding math — `lindex` rounds down but grows only by the *net* rate, while `total-assets-preview` grows by the *gross*/rounded-up rate before treasury dilution is subtracted from supply), the market will systematically over-value zToken collateral relative to what a real `redeem()` call returns. This mirrors the Pendle report's core mechanism: at redemption/liquidation time the borrower's collateral (in real underlying terms) is worth less than the oracle says, shrinking or eliminating the liquidation bonus for liquidators and potentially producing unrecoverable bad debt in the market, i.e., protocol insolvency risk from persistently over-valued collateral.

### Likelihood Explanation
This requires no attacker action — it is a passive divergence between two independently-maintained accrual formulas that both run on every accrual cycle under normal operation. However, I was not able to conclusively prove within the available context that the divergence is large enough, or persistently one-directional, to produce a *concrete, exploitable* overstatement (the two formulas may be tuned to stay close enough in practice, and the actual delta depends on interest-rate curves, utilization, and fee-reserve settings that I could not fully trace with the tools available). Without being able to execute or fully simulate the compounding math end-to-end, I cannot confirm a guaranteed, reproducible loss — this is a plausible analog but not proven.

### Recommendation
Verify analytically or via simulation whether `lindex` growth (net liquidity rate compounding) can exceed the true `convert-to-assets-preview` ratio under any realistic utilization/fee-reserve/time-delta combination. If it can, either (a) derive the oracle price for zTokens directly from `total-assets-preview`/`total-supply-preview` instead of the separately-compounded `lindex`, or (b) apply a conservative haircut/rounding-down discipline in `resolve-ztoken` so the oracle price can never exceed the real redeemable value.

### Proof of Concept
Not able to construct a concrete numeric PoC with the tools available — this would require simulating multiple accrual cycles with specific `interest-rate`, `utilization`, and `fee-reserve` parameters across `next-liquidity-index` vs. `total-assets-preview`/`total-supply-preview` to show a persistent, unbounded divergence, which is beyond what I could verify through static code reading alone.
