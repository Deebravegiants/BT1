### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted for tenant routing without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, then hands the caller-supplied `shop-domain`, `topic`, and `webhook-id` HTTP headers to the app's handler as trusted identity fields, even though none of those headers are part of the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: ` [1](#0-0) `. The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read straight from HTTP headers with no cryptographic binding to the body: ` [2](#0-1) `.

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively from `to_signable_string`: ` [3](#0-2) `.

`Registry.process` performs only this body-HMAC check and then constructs `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` header values, passing them straight to the app-supplied handler as the tenant/topic identity for the event: ` [4](#0-3) [5](#0-4) `.

**Identity binding broken (as an equality):** the gem's contract implies `request.shop (as validated) == request.shop (as consumed by handler)`, but the HMAC only proves `secret == secret used to sign @raw_body`; it proves nothing about `shop-domain header == shop the body actually pertains to`. Since Shopify apps use a single `api_secret_key` shared across every shop that installs the app, any merchant that installs the app (an unprivileged, non-credentialed party from the app's perspective) can capture a genuinely-signed webhook (valid body + valid HMAC) delivered to their own store, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim shop's domain in the `shop-domain` header (and any topic/webhook-id values). `Utils::HmacValidator.validate` will still return `true` because it only checks the body against the shared secret, so `Registry.process` will invoke the handler with `shop: <victim-shop>` and attacker-controlled body content, i.e., cross-tenant data injection at the identity-check boundary this gem is responsible for enforcing.

### Impact Explanation
This crosses the tenant boundary that `Registry.process`/`HmacValidator.validate` is meant to enforce: it lets an attacker who is a legitimate installer on their own shop forge webhook events attributed to a different shop, without needing the app's `client_secret`, an access token, or any other privileged credential — only their own valid installation of the app. Downstream host applications typically use `WebhookMetadata#shop` to select the tenant record/session to mutate (e.g., mark subscription/uninstall status, update order data keyed by shop), so this can produce cross-tenant state corruption purely through fields this gem asserts are trustworthy after `HmacValidator.validate` succeeds.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on a shop they control (a normal, unprivileged action for any Shopify merchant/app installer) and be able to send a raw HTTP POST to the app's public webhook endpoint with edited headers — no secret material, TLS interception, or social engineering is needed. This is a low-effort, reliably reproducible header-substitution replay.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-covered signable string (or otherwise cryptographically bind them to the body, e.g., via an HMAC-then-derive scheme keyed per-shop) so header substitution invalidates the signature. At minimum, document/enforce that the shop identity used downstream must be independently reconciled with a known/registered shop for that webhook rather than trusted purely from the header once body HMAC succeeds.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, satisfying `api_secret_key` sharing across all installs.
2. Shopify delivers a genuine webhook to the app for `attacker-shop.myshopify.com`, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body B>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: w-1
   Body: B
   ```
3. Attacker captures `B` and its valid `x-shopify-hmac-sha256` value.
4. Attacker replays the identical request to the app's webhook endpoint, changing only the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
   keeping body `B` and the original HMAC unchanged.
5. `ShopifyAPI::Webhooks::Request#hmac` decodes the unchanged header value; `HmacValidator.validate` recomputes HMAC over `B` with the shared `api_secret_key` and it matches (per `lib/shopify_api/utils/hmac_validator.rb:12-31`), so `Registry.process` proceeds and calls the app handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, topic: ..., webhook_id: ...)` (per `lib/shopify_api/webhooks/registry.rb:188-200`), even though the payload was never generated for `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
