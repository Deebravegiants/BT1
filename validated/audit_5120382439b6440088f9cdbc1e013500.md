### Title
Webhook shop-domain identity is not bound by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the `shopify-shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are never included in the HMAC computation performed by `HmacValidator`. Any attacker who can obtain one genuinely-signed `(raw_body, hmac)` pair from Shopify — trivially available to any merchant/developer who owns a store and receives their own webhooks — can resend that exact body/HMAC pair to a host application's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. The gem will report the HMAC as valid and dispatch the payload to the host's handler tagged with the attacker-chosen shop, breaking the binding between "shop authenticated by the HMAC" and "shop the handler acts on."

and `HmacValidator.validate`/`validate_signature` recompute the HMAC only over `verifiable_query.to_signable_string`: [2](#0-1) 

For webhooks, `to_signable_string` is hard-coded to the raw body only: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers via `shopify_header`: [4](#0-3) [5](#0-4) 

That unauthenticated `shop` value is exactly what gets propagated to the host application's handler as the tenant identity: [1](#0-0) 

By contrast, the OAuth callback's `AuthQuery#to_signable_string` correctly folds `shop` into the signed string, so that code path does bind shop to the HMAC: [6](#0-5) 

This asymmetry confirms the webhook path is the defective one: `HMAC-valid(raw_body) == HMAC-valid(shop-domain header)` is treated as true by the gem, when in fact the shop header is never part of the signed material. An attacker who owns/controls any shop that has this app installed (or that has any of this app's webhook subscriptions enabled) will legitimately receive `(raw_body, hmac)` for their own tenant, then can POST that identical `(raw_body, hmac)` pair to the host's webhook endpoint with `shopify-shop-domain` (or `x-shopify-shop-domain`) rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because the header is not part of the signed content, and `Registry.process` hands the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the gem lets an attacker present webhook data as belonging to an arbitrary target shop while only proving authenticity of the (attacker-controlled) body. Depending on how the host application keys per-tenant state/session data off `WebhookMetadata#shop`, this can lead to cross-tenant data corruption, injection of attacker-chosen payload content attributed to a victim tenant, or triggering tenant-scoped side effects (e.g., mandatory compliance webhooks like `shop/redact`) against the wrong shop.

### Likelihood Explanation
Likelihood is moderate to high: the only prerequisite is that the attacker operates (or briefly installs the app on) any shop capable of receiving one legitimate webhook delivery for a registered topic — no access to `api_secret_key`, access tokens, or the target's credentials is required. The replay itself is a simple unauthenticated HTTP POST with a modified header, well within reach of an unprivileged internet user.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material for webhooks, or otherwise cryptographically bind the `shop` claim to the payload before trusting it for tenant dispatch — mirroring the approach already used in `AuthQuery#to_signable_string`, which folds `shop` into the signed string.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a subscribed webhook topic (e.g., `orders/create`), receiving a legitimately signed request: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's secret), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same body `B` and header `x-shopify-hmac-sha256: H` to the host application's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `HmacValidator.validate`, which recomputes HMAC over `to_signable_string` (== `B` only) and finds it matches `H` — validation succeeds.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`, i.e., the host processes attacker-supplied content under the victim shop's identity despite no cryptographic binding of `shop` to the signature.
