### Title
Webhook shop-domain identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator` verifies the HMAC exclusively against that body. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from unauthenticated HTTP headers and are never included in the signed material, yet `ShopifyAPI::Webhooks::Registry.process` forwards `request.shop` directly into the `WebhookMetadata` passed to the host application's handler as the tenant identifier.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Only `@raw_body` is signable. The `shop` accessor reads the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the HMAC computation: [2](#0-1) 

`HmacValidator.validate_signature` computes and compares the signature only over `to_signable_string` (the body): [3](#0-2) 

`Registry.process` calls `HmacValidator.validate` and, upon success, immediately trusts `request.shop` as the merchant identity, passing it straight to the app-provided handler: [4](#0-3) 

The gem's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" and describes `data.shop` as "The shop domain of the webhook" — implying it is a trustworthy, verified value: [5](#0-4) [6](#0-5) 

Because the HMAC binds only the body bytes, an unprivileged attacker who can install the same app on their own store (or otherwise legitimately trigger a webhook for a shop they control) receives a request whose `hmac-sha256`/body pair is validly signed with the app's shared secret. Since the header carrying the shop identity is not part of that signed material, the attacker can replay the identical body+HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuine), so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "<victim-shop>", ...)`, spoofing the request as if it originated from the victim tenant.

This breaks the intended identity binding: `shop asserted to handler == shop that produced the HMAC`. In reality `shop header (attacker-controlled, unauthenticated) != shop bound by HMAC (none, since shop is not covered)`.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` to select which tenant's data to update/create/delete (the intended and documented use of this field) can be tricked into applying a webhook payload to the wrong shop's records, or into believing an event occurred for a shop it did not occur for. This is a cross-tenant data integrity/access issue directly enabled by the gem's identity-binding gap — the exact bug class called out in the rules (a field acted on but not covered by the HMAC).

### Likelihood Explanation
Exploitation requires only the ability to install the vulnerable app on an attacker-controlled shop (a normal, unprivileged action available to any Shopify merchant/developer) to legitimately obtain a valid HMAC-signed webhook body, then replay it with a modified shop header to the app's shared webhook endpoint. No access to the app's `client_secret`, a merchant access token, or privileged credentials is required.

### Recommendation
Include the shop domain (and other identity-relevant headers such as `topic`/`webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind them (e.g., verify `shop` against a previously-stored, session-registered shop rather than trusting the header outright). At minimum, `ShopifyAPI::Webhooks::Request#to_signable_string` should incorporate the shop-domain header so `HmacValidator.validate` fails when the header has been tampered with relative to the value Shopify actually signed for.

### Proof of Concept
1. Install/authorize the target app on attacker-owned store `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) so Shopify sends a genuinely signed request: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `api_secret_key`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Capture this request.
3. Resend the same body `B` and same `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks `H` against `B` — this still passes.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, causing the host app to process/attribute an attacker-controlled payload as belonging to the victim shop.
