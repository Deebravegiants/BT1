### Title
Swap fee is deducted from output even when no relay is set, permanently stranding the fee amount in `ExternalActionSwap` - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
In `ExternalActionSwap.swap()`, the relay/protocol fee (`relayFee` + `hinkalFee`) is unconditionally computed and subtracted from `amountToSendToHinkal`, but the actual payout of that fee only happens if `circomData.relay != address(0)` (enforced inside `sendToRelay`). When a transaction is submitted with `circomData.relay == address(0)` (a valid, unprivileged, self-submitted transaction — nothing in `HinkalHelper` or `ExternalActionSwap` requires `relay != address(0)`), the fee amount is silently retained in the `ExternalActionSwap` contract instead of being paid to anyone or returned to the user, and there is no rescue/withdraw function to recover it.

### Finding Description
`ExternalActionSwap.swap()` computes fees independent of whether a relay is present: [1](#0-0) 

```
uint256 relayFee = circomData.feeStructure.flatFee;
uint256 hinkalFee = hinkalHelper.calculateRelayFee(swappedAmount, 0, circomData.feeStructure.variableRate);

if (circomData.feeStructure.feeToken == outputToken) {
    sendToRelay(circomData.relay, relayFee + hinkalFee, outputToken);
} else {
    sendToRelay(circomData.relay, relayFee, circomData.feeStructure.feeToken);
    sendToRelay(circomData.relay, hinkalFee, outputToken);
}

uint256 totalFee = hinkalFee + (outputToken == circomData.feeStructure.feeToken ? relayFee : 0);
uint256 amountToSendToHinkal = swappedAmount - totalFee;

transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal);
```

`sendToRelay` (in `Transferer.sol`) only performs a transfer when `relay != address(0)`: [2](#0-1) 

Nowhere in the pipeline is `circomData.relay != address(0)` enforced when `feeStructure.variableRate` or `flatFee` is non-zero. `HinkalHelper.relayerIsValid()` only checks relayer whitelisting/`tx.origin` *if* `relay != address(0)`, and does not require a relay to be present for fees to apply: [3](#0-2) 

By contrast, `Hinkal._internalTransact()` correctly gates *all* fee computation (`relayFee`/`recipientAmount`) behind `if (circomData.relay != address(0))`, so when there is no relay, the full withdrawal amount goes to the recipient with zero fee deducted: [4](#0-3) 

`ExternalActionSwap.swap()` does not follow this pattern — it deducts `totalFee` from `amountToSendToHinkal` unconditionally, but only pays it out conditionally. When `circomData.relay == address(0)`, `sendToRelay` is a no-op, so `totalFee` tokens simply remain in the `ExternalActionSwap` contract's balance. The contract has no `owner`/rescue function to recover stray tokens: [5](#0-4) 

Because the outer `Hinkal.transact()` balance-equation check only verifies the *Hinkal* contract's own balance delta against `circomData.amountChanges`/`utxoAmount` (not the `ExternalActionSwap` contract's balance), this fee leakage inside `ExternalActionSwap` is invisible to that invariant and passes normal proof verification: [6](#0-5) 

This is the analog of the GMX M-26 pattern: a fee that is computed/owed to a fee-collecting party is silently dropped/misdirected on a particular code path (there: liquidation collateral-covers-funding-fee branch giving the fee-receiver's share to the pool; here: relay == address(0) branch giving the relay/protocol's share to no one, stuck in the external-action contract) — breaking the equality between "fee computed" and "fee actually paid out."

### Impact Explanation
This is a High-severity issue under the given impact classes: temporary/permanent freezing of protocol/relay fees. The `hinkalFee`/`relayFee` amount is deducted from the user's swap output but never delivered anywhere — it is neither paid to a relay, nor returned to the depositing user, nor claimable by the protocol, since `ExternalActionSwap` has no rescue mechanism visible in this contract. Every relay-less swap transaction accumulates additional stuck value in the contract, which is a repeatable, permanent loss of protocol-fee-designated funds.

### Likelihood Explanation
High likelihood: any unprivileged user (or a relay-less/self-submitted flow) can trigger this simply by submitting a `transact()` call through the swap external action with `circomData.relay == address(0)` while `feeStructure.variableRate > 0` (or `flatFee > 0`). No special privileges, admin actions, or relay collusion are required — it only requires a normal swap transaction without designating a relay.

### Recommendation
In `ExternalActionSwap.swap()`, gate the fee computation the same way `Hinkal._internalTransact()` does: only compute and subtract `relayFee`/`hinkalFee` from `amountToSendToHinkal` when `circomData.relay != address(0)`. If `circomData.relay == address(0)`, `totalFee` should be `0` and the full `swappedAmount` should be sent to `msg.sender` (Hinkal), consistent with the internal-transact no-relay behavior.

### Proof of Concept
1. User submits a valid ZK proof for a swap via `Hinkal.transact()` with `circomData.externalActionData.externalActionId` pointing at `ExternalActionSwap`, and sets `circomData.relay = address(0)` (a legitimate, unprivileged choice — no check anywhere forbids this) while `circomData.feeStructure.variableRate > 0`.
2. `Hinkal._externalTransact()` calls `ExternalActionSwap.runAction()` → `swap()`.
3. `swap()` computes `hinkalFee = calculateRelayFee(swappedAmount, 0, variableRate) > 0` and `relayFee = flatFee`.
4. `sendToRelay(address(0), ...)` is called twice but does nothing because `relay == address(0)`.
5. `amountToSendToHinkal = swappedAmount - totalFee` is transferred to `Hinkal`; the `totalFee` tokens remain locked in the `ExternalActionSwap` contract's balance permanently, with no function to recover them.
