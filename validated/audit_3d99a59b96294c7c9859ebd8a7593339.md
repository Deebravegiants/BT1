### Title
Webhook shop attribution is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop`, `topic`, and `webhook_id` used by `Registry.process` to route and attribute the webhook are read from unauthenticated HTTP headers that are never included in the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` verifies the signature strictly against that signable string [2](#0-1) . However, `Request#shop`, `#topic`, and `#webhook_id` are all pulled straight from the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers with no cryptographic tie to the HMAC [3](#0-2) . `Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` handed to the app's handler [4](#0-3) .

The broken identity binding is:
`HMAC-verified(raw_body)` == `bytes Shopify actually signed for shop S`
but the gem lets `request.shop` (used for tenant attribution) be any value the caller places in the header, independent of which raw_body/HMAC pair was verified. In other words, the code proves "this body was HMAC'd with the app secret" but never proves "this body was HMAC'd for this shop."

### Impact Explanation
Because the API secret used to compute the HMAC is shared by the app across every installed shop (see `HmacValidator.validate` using `Context.api_secret_key`/`old_api_secret_key` globally, not per-shop) [5](#0-4) , any party that legitimately receives one valid `(raw_body, hmac)` pair for a shop they control can replay that same body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or topic/webhook-id) header for a different, victim shop. `Registry.process` will pass HMAC validation (since it only checks the body) and then dispatch the handler with `WebhookMetadata` claiming the victim's shop [6](#0-5) . If the host application uses `data.shop` to look up a tenant's session/store and apply the payload (a common and Shopify-recommended pattern for webhook handlers), this results in cross-tenant data injection/impersonation — data intended for/about shop A being processed and applied under shop B's identity.

### Likelihood Explanation
Exploitation requires the attacker to already have a shop installed on the target app (so they can receive at least one genuinely-signed webhook body/HMAC pair) and requires the host application to trust `WebhookMetadata#shop` for tenant scoping without an independent check — both are realistic/common for multi-tenant Shopify apps built on this gem, since the gem's own documented API (`Registry.process`) is the standard integration point and offers no additional protection.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is cryptographically verified — e.g., include `shop-domain`, `topic`, and `webhook-id` in `to_signable_string`, or have `Registry.process` cross-check the header-derived shop against a shop resolved from a verified, tenant-scoped source (such as a previously stored offline session keyed by the same request) before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the raw body `B` and its valid header `x-shopify-hmac-sha256`.
2. Attacker resends the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC(raw_body, api_secret_key)` and successfully matches the replayed HMAC [7](#0-6) .
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the app's handler, which processes/writes data as if it came from the victim shop [8](#0-7) .
