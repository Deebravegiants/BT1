## Finding: Valid



### Title
Cross-user theft of Emporium CASE 2 stateless-op refunds via shared-identity balance sweep - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction()`'s CASE 2 ("Stateless Interaction") path executes external calls with `msg.sender == Emporium`, so any third-party protocol (e.g. a limit-order book) that records `orders[msg.sender]` as the order owner and pays refunds/cancellations to that recorded owner will always pay `address(emporium)`, regardless of which user originally placed the order. `handleOut()` then sweeps whatever balance increase occurred during the *current* caller's `runAction` execution and mints it as a brand-new UTXO owned by whatever stealth address that *current* caller supplied, with zero linkage to the original depositor.

### Finding Description
The broken equality: the protocol implicitly assumes `refund_recipient_stealth_address == order_creator_stealth_address`. In reality, the code enforces only:
```
output_utxo_owner_stealth_address == circomData.stealthAddressStructure (of the CURRENT transact caller)
```
with no check that the underlying funds originated from that caller's own prior deposit/order.

Code path:
1. Victim calls `Hinkal.transact` with a CASE 2 op: `op.endpoint = orderBook`, `op.callData = placeOrder(...)`. Because `stack.signerAddress == 0` (or `!op.invokeWallet`), the call in `EmporiumUpgradeable.runAction` is made directly `op.endpoint.call{value: op.value}(op.callData)` [1](#0-0)  — so inside the order book, `msg.sender == address(emporium)`, and the order is recorded as owned by `address(emporium)`.
2. Any unprivileged actor (attacker or an unrelated keeper) can permissionlessly trigger `orderBook.cancelOrder(orderId)`/`claimRefund(orderId)`. If the attacker includes this exact call as their own CASE 2 op in a fresh `Hinkal.transact`, it again executes with `msg.sender == address(emporium)` [2](#0-1) , and the refund is paid into the Emporium contract's own balance.
3. `runAction` measures `balancesBefore`/`balancesAfter` purely as an aggregate token balance diff around the ops loop [3](#0-2) , then `handleOut()` transfers the entire positive `balanceChange` to `msg.sender` (which, in the call chain `Hinkal._externalTransact → IExternalActionV2.runAction`, is `Hinkal.sol` itself) and mints a `UTXO` stamped with `circomData.stealthAddressStructure` — the attacker's own address, not the victim's [4](#0-3) .
4. `Hinkal.transact`'s top-level balance-diff `require` only checks internal self-consistency of the *current* transaction (`balanceDif == amountChanges[i] + utxoAmount`) [5](#0-4)  — it has no way to know or verify whose deposit originally produced the swept balance. Neither `performHinkalChecks`, `verifyProof`, `insertNullifiers`, nor the circuit's `inTotal + amountChanges[i] === outTotal` constraint reference the third-party order book's internal state at all; they only constrain the attacker's own declared inputs/outputs, which are self-consistent from the attacker's perspective.

Root cause: CASE 2 "stateless interactions" deliberately execute all such calls under a single shared identity (`address(emporium)`), so any external protocol that ties ownership/payout rights to `msg.sender` conflates every Hinkal-Emporium CASE-2 user into one account. Whoever's transaction happens to trigger the payout captures it via the generic balance-diff sweep in `handleOut`, with no cryptographic or on-chain binding between the specific `orderId`/refund and the depositor's stealth address/nullifiers.

### Impact Explanation
Direct theft of a victim's canceled/expired order refund (or of any residual balance an external CASE 2-integrated protocol pays back to `address(emporium)`) by an unrelated, unprivileged attacker who merely needs to include the same claim/cancel call in their own transact. This is a direct theft of a victim's in-flight/refunded shielded-adjacent funds, matching the Critical severity bucket. It is fully repeatable against any order/refund left claimable at `address(emporium)`, and generalizes to any CASE 2-integrated protocol using recorded-owner-based payouts (not merely order books).

### Likelihood Explanation
Preconditions: a victim must have used a CASE 2 (stateless) op against a third-party contract that tracks ownership/refund eligibility by `msg.sender` and allows permissionless cancel/claim (a common and reasonable pattern for order books, escrows, and similar contracts). The attacker needs only: knowledge of the `orderId` (often public via events/logs even for otherwise-shielded flows), their own valid UTXO proof for an unrelated deposit, and the ability to craft `CircomData.externalActionData.externalActionMetadata` with the same `op.endpoint`/`op.callData`. No privileged role, relay collusion, or protocol bug elsewhere is required — this is a pure consequence of Emporium's shared-identity CASE 2 design combined with the generic balance-diff sweep in `handleOut`. Attacker cost is a single normal transact; the race is winnable by simply submitting before any legitimate sweep, or whenever the refund becomes claimable and sits unclaimed.

### Recommendation
Do not attribute arbitrary balance increases observed during a CASE 2 op to the current transact caller. Options: (1) require CASE 2 endpoints/ops that can move value to Emporium to be explicitly allow-listed per action with metadata binding the expected recipient/order identity to the specific depositor's proof (e.g., store an on-chain mapping from `orderId`/order hash to the depositor's commitment or stealth address at `placeOrder` time, and require `claimRefund`/`cancelOrder` CASE 2 ops to prove/replay that same binding); or (2) disallow CASE 2 stateless ops from being used for stateful ownership-based external protocols at all, restricting such refund/cancel flows to CASE 1 (`invokeWallet`/`HinkalWallet`) so `msg.sender` at the external protocol is the depositor's own per-transaction wallet, not the shared `Emporium` address.

### Proof of Concept
Foundry test plan:
1. Deploy a mock order book contract with `placeOrder()` (records `orders[msg.sender] = {amount, active:true}`), `cancelOrder(orderId)`/`claimRefund(orderId)` (permissionless, pays `orders[orderId].owner` and zeroes the entry).
2. Victim calls `Hinkal.transact` with a valid proof, CASE 2 op `placeOrder()` targeting the mock order book with `op.value = X`. Assert `orders[address(emporium)].amount == X` and Emporium's on-chain balance decreased by `X` (moved into the order book), no UTXO minted for X to the victim yet since funds are locked in the order book.
3. Simulate the order becoming refundable (e.g., fast-forward time or call a permissionless "expire" toggle) — do NOT let the victim or any authorized keeper claim it.
4. Attacker (unrelated EOA, holding only their own unrelated UTXO) submits `Hinkal.transact` with a freshly generated valid proof for their own deposit/UTXO, embedding a CASE 2 op `claimRefund(orderId)` targeting the same order book, with `deltaAmountChanges[i] == 0` for that token (attacker deposits nothing new).
5. Assert: (a) mock order book pays `X` to `address(emporium)`; (b) `EmporiumUpgradeable.runAction` computes `balanceChange == X` and `handleOut` mints a new UTXO of amount `X` owned by the **attacker's** `stealthAddressStructure`; (c) `Hinkal.transact`'s balance-diff check passes with `utxoAmount` including this `X`; (d) the victim's stealth address never receives any UTXO for the refunded `X`.
6. Assert final state: attacker's spendable shielded balance increased by `X` that originated entirely from the victim's canceled order, with no nullifier or proof from the victim involved in the attacker's transaction — proving `refund_recipient_stealth_address != order_creator_stealth_address`.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
