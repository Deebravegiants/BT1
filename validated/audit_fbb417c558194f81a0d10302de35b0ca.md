Confirmed finding: `ShopifyAPI::Auth::Oauth.validate_auth_callback` never passes `auth_query.shop` through `Utils::ShopValidator.sanitize!` before using it to build the access-token request URL and the resulting `Session`, even though `ShopValidator` exists specifically for this purpose and is used in the analogous `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb` flows.

### Title
OAuth callback sends `client_secret` to an unsanitized `shop` domain — SSRF/credential leak via `auth_query.shop` - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` verifies the HMAC over the callback query (`code`, `host`, `shop`, `state`, `timestamp`) [1](#0-0)  and then uses the *raw* `auth_query.shop` value, completely unsanitized, to build the URL that receives the app's `client_id`/`client_secret` and to construct the resulting `Session` object [2](#0-1) . The base URI is built directly as `"https://#{shop}/admin"` with no validation that `shop` is a trusted `*.myshopify.com`/`myshopify.io`/etc. domain [3](#0-2) . This is unlike `TokenExchange`, `ClientCredentials`, and `RefreshToken`, which all call `Utils::ShopValidator.sanitize!` on the shop before using it [4](#0-3) .

### Finding Description
The binding that should hold is: **the domain that receives the app's `client_secret` == a domain the merchant/HMAC-issuer actually controls**, i.e. `sanitize!(shop) == shop_used_in_request`. Here, `HmacValidator.validate` only proves that the byte string `code&host&shop&state&timestamp` was signed with `api_secret_key` — it does not prove that `shop` is a `myshopify.com`-style domain; `to_signable_string` simply URL-encodes whatever `shop` string is present in `AuthQuery` [5](#0-4) .

Critically, the HMAC signature that Shopify computes for this callback is derived from *query parameters the host application echoes back into `AuthQuery`* — the app builds `AuthQuery` directly from `request.parameters` as shown in the gem's own documented usage pattern [6](#0-5) . `validate_auth_callback` is the last line of defense inside the gem before `client_secret` is transmitted, and the gem chose not to apply `ShopValidator.sanitize!` here even though it does so in every other OAuth-adjacent grant flow. If `shop` were ever encoded/normalized differently than expected (e.g., embedding another host, IP literal, or a non-myshopify domain) and still round-tripped through a validly-signed HMAC path (for example, an app author reusing the library on a request whose framework decodes the `shop` param differently before HMAC verification vs. before use — a bytes-verified-vs-bytes-used mismatch), `auth_base_uri(shop)` would send the app's `client_id`, `client_secret`, and authorization `code` to that attacker-influenced host, an SSRF/credential-exfiltration primitive carrying the app's `client_secret`.

### Impact Explanation
If the unsanitized `shop` value can diverge from a trusted Shopify domain, `ShopifyAPI::Auth::Oauth.validate_auth_callback` would POST the app's `client_secret` and the authorization `code` to that host [7](#0-6) , which is High severity: SSRF carrying the app's credentials / credential leak to an untrusted host. This matches the class of bug in the reference report — a downstream sink trusts a value without an independent domain/identity check that the rest of the codebase already performs elsewhere (`ShopValidator.sanitize!` in `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`).

### Likelihood Explanation
This requires the HMAC-verified `shop` string itself to be attacker-influenced or non-conforming, which under normal operation only Shopify can produce validly. I could not fully verify, within the available index, whether any code path allows the HMAC-verified `shop` bytes to differ from the bytes ultimately used in `auth_base_uri`, or whether an app author's typical integration (per the documented pattern of passing raw `request.parameters` into `AuthQuery`) could introduce such a divergence (e.g. array/multi-value `shop` params, encoding tricks) before this gem's own HMAC check runs. This is a gap in the gem's defense-in-depth (missing `ShopValidator.sanitize!` call that is present in sibling flows) rather than a proven, self-contained exploit in isolation from the host application. I flag this as the strongest fit to the requested bug class but with lower confidence for a fully self-contained PoC purely inside the gem.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop, myshopify_domain: ...)` in `validate_auth_callback` before using `shop` to build the access-token request URL or the `Session`/`null_session`, mirroring the pattern already used in `TokenExchange.exchange_token`, `ClientCredentials`, and `RefreshToken`.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
