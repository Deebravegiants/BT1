### Title
Integer overflow in `Memory::resize` allows an unprivileged EVM caller to bypass the `EVM_MEMORY_BYTES` cap and panic the interpreter via out-of-bounds slice indexing - (File: substrate/frame/revive/src/vm/evm/memory.rs)

### Summary
`as_usize_or_halt` only rejects a `U256` offset if it does not fit in `usize`; it does **not** bound the value against `EVM_MEMORY_BYTES`. That check is deferred to `Memory::resize`, which computes `target_len = num_words(offset.saturating_add(len)) * 32` and compares it against the 1 MiB cap. A user can choose `offset == usize::MAX` (a value that legitimately fits in `usize` and therefore passes `as_usize_or_halt`), causing the internal `+31` addition inside `num_words` to overflow. Depending on build overflow-check settings, this either panics directly or silently wraps to a small `target_len` (even `0`), letting an oversized `offset` pass the cap check without growing the backing `Vec<u8>`, after which `slice_len`/`set` index the vector out of bounds and panic.

### Finding Description
- `mload`/`mstore`/`mstore8` in `substrate/frame/revive/src/vm/evm/instructions/memory.rs` (lines 31-62) pop an `offset` `U256` from the EVM stack, convert it with `as_usize_or_halt::<E::T>(offset)`, and immediately call `interpreter.memory.resize(offset, len)`.
- `as_usize_or_halt_with` (`substrate/frame/revive/src/vm/evm/util.rs:21-28`) only checks that the high limbs of the `U256` are zero and that `limbs[0] <= usize::MAX`. It performs **no comparison against `EVM_MEMORY_BYTES`**; any offset that fits the native machine word (e.g. `usize::MAX` = `u64::MAX` on 64-bit, `u32::MAX` on wasm32) is accepted and converted verbatim.
- `Memory::resize` (`substrate/frame/revive/src/vm/evm/memory.rs:66-79`) computes:
  ```
  let target_len = revm::interpreter::num_words(offset.saturating_add(len)) * 32;
  if target_len > EVM_MEMORY_BYTES as usize { ...Halt::OutOfGas... }
  ```
  `offset.saturating_add(len)` is saturating and safe, but `num_words` (external `revm` implementation, `(x + 31) / 32`) performs **plain, non-saturating** addition. When `offset == usize::MAX`, `offset.saturating_add(len)` saturates to `usize::MAX`, and `num_words(usize::MAX)` then overflows on `usize::MAX + 31`.
  - With overflow checks enabled (common in Substrate release profiles), this is an immediate arithmetic-overflow panic.
  - With overflow checks disabled, the addition wraps (`usize::MAX + 31 → 30` mod word size), `num_words` returns `0`, `target_len = 0`, which trivially satisfies `target_len > EVM_MEMORY_BYTES` as false — the cap check is bypassed and `self.data` is never grown.
- Control then returns to `mload`/`mstore`, which calls `interpreter.memory.slice_len(offset, 32)` / `memory.set(offset, ...)` (`substrate/frame/revive/src/vm/evm/memory.rs:86-90,121-123`). These compute `offset..offset+size` and index `self.data` directly, both of which panic: `offset + size` itself overflows (or produces a backwards/absurd range), and even if it didn't, indexing a `Vec` whose length was never grown at an offset near `usize::MAX` is out of bounds.
- This defeats the stated invariant: an offset that should be rejected by the `EVM_MEMORY_BYTES`/gas-limit check instead reaches unchecked slice indexing and panics.

### Impact Explanation
An unprivileged caller can trigger this purely by deploying/calling a `pallet-revive` EVM-mode contract with bytecode such as `PUSH8 0xFFFFFFFFFFFFFFFF MLOAD` (or `MSTORE`/`MSTORE8`), executed via a normal Ethereum-style transaction (`eth_call`/`eth_sendRawTransaction` equivalent extrinsic path into `pallet_revive`). Instead of the intended controlled `Halt::Error(OutOfGas)` abort, the interpreter panics with an unhandled Rust panic (arithmetic overflow or out-of-bounds slice index) inside runtime/WASM execution. This turns a normal, gas-limited "reject oversized memory access" case into an uncontrolled panic/trap during transaction execution — a availability/liveness issue for the affected extrinsic and potentially for block execution if such a panic is not gracefully caught by the outer dispatch machinery.

### Likelihood Explanation
Fully reachable by any unprivileged account able to submit an EVM contract-call transaction to `pallet-revive`; no special privileges, proxy, multisig, or governance access required. The bytecode needed (`PUSHn <big value>` followed by `MLOAD`/`MSTORE`/`MSTORE8`) is trivial to construct and deploy. The bug is deterministic given the specific boundary offset value, making it 100% reproducible.

### Recommendation
Fix `Memory::resize` (and/or `as_usize_or_halt`) to bound `offset`/`len` against `EVM_MEMORY_BYTES` using saturating/checked arithmetic before calling into `num_words`, e.g.:
```rust
let needed = offset.checked_add(len).filter(|v| *v <= EVM_MEMORY_BYTES as usize);
let Some(needed) = needed else { return ControlFlow::Break(Error::<T>::OutOfGas.into()); };
let target_len = revm::interpreter::num_words(needed) * 32;
```
This ensures any offset that would overflow or exceed the memory cap is rejected with `Halt::Error(OutOfGas)` before ever reaching `num_words`, `slice_len`, or `set`.
