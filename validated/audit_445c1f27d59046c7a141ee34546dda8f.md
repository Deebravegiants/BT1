I have sufficient evidence to confirm the vulnerability. The `Webhooks::Request` HMAC signable string only covers the raw body, never the `shop-domain` or `topic` headers, yet `Registry.process` trusts those unauthenticated headers to build the identity fed to app handlers.### Title
Webhook shop-domain and topic are trusted for handler dispatch without HMAC coverage, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature verified by `Utils::HmacValidator` never covers the `x-shopify-shop-domain` or `x-shopify-topic` headers. `Webhooks::Registry.process` nonetheless takes `request.shop` and `request.topic` straight from those unauthenticated headers and hands them to the app's `WebhookHandler` as trusted identity fields. Any internet user who can obtain one valid `(body, hmac)` pair for the app's shared `client_secret` (trivially available by installing the app on their own store and capturing a real webhook delivery) can replay that exact body/HMAC to the app's public webhook endpoint while forging the `shop-domain` and `topic` headers to any value, and the signature check still passes.

### Finding Description
The HMAC binding is defined by `Utils::VerifiableQuery#to_signable_string`/`hmac`, verified in `Utils::HmacValidator.validate`: [1](#0-0) 

For webhooks, `Request#to_signable_string` is defined to be only `@raw_body`: [2](#0-1) 

while `shop` and `topic` are pulled from unauthenticated headers: [3](#0-2) 

`Registry.process` verifies HMAC and then immediately trusts `request.shop`/`request.topic` to route and label the payload delivered to the app's handler: [4](#0-3) 

`WebhookMetadata` carries this unauthenticated `shop` field straight into the app-facing struct that handlers rely on for tenant identification: [5](#0-4) 

The identity binding that should hold is: `shop authenticated by HMAC == shop trusted by the handler`. Here, the HMAC authenticates only the body's integrity under the app's `client_secret` (which is shared across every shop that installs the app), not which shop the body is attributed to. Since `client_secret` is identical for all merchants of the app, any merchant (an unprivileged actor with respect to other tenants) who installs the app on their own store legitimately receives real `(body, hmac)` pairs. They can then POST that exact body and HMAC to the app's public webhook endpoint with `x-shopify-shop-domain` set to a victim shop and `x-shopify-topic` set to any registered topic. `HmacValidator.validate` will succeed (it only checks body bytes against the shared secret), and `Registry.process` will dispatch to the app's handler with `WebhookMetadata.shop == victim-shop` and an attacker-chosen `topic`, even though the request has nothing to do with the victim's shop.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), matching the Critical impact category. An app author writing a handler naturally trusts `WebhookMetadata#shop` as the authenticated tenant for a webhook (that is the entire purpose of signing webhooks with a per-app secret). By forging the shop-domain and topic headers on a body they legitimately obtained a valid signature for, an attacker can inject fabricated events attributed to an arbitrary victim shop into the app's business logic (e.g., trigger data writes, cache updates, redaction flows, or state transitions keyed by shop domain) without ever having credentials for, or a session with, the victim shop. Because `topic` is also unauthenticated, the attacker can additionally cause a body to be misinterpreted under any topic supported by the app's registry, widening the set of exploitable handlers.

### Likelihood Explanation
Likelihood is high for any app that relies on `WebhookMetadata#shop`/`#topic` for authorization or data-scoping decisions (the documented and expected usage pattern in this gem). The only prerequisite is that the attacker can install the app on a shop they control (a standard, unprivileged interaction with a public Shopify app) and can send arbitrary HTTP requests to the app's public webhook endpoint — no access token, session, or leaked secret is needed.

### Recommendation
Include `shop` and `topic` (and ideally `webhook-id`/`api-version`) in the HMAC-covered signable string, or otherwise cryptographically bind the destination shop to the verified body, e.g.:
```ruby
sig { override.returns(String) }
def to_signable_string
  "#{shop}|#{topic}|#{@raw_body}"
end
```
and adjust the gem's HMAC validator/consumers accordingly, or explicitly document that `shop`/`topic` are NOT authenticated by this gem's HMAC check and must be independently verified by the host app (e.g., against a known/registered shop) before use.

### Proof of Concept
1. App developer installs the app on `attacker-shop.myshopify.com` and registers a webhook handler for `products/create`.
2. Shopify sends a legitimate webhook to the app for `attacker-shop`:
   ```
   POST /webhooks
   x-shopify-topic: products/create
   x-shopify-hmac-sha256: <valid HMAC over BODY using shared client_secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: BODY
   ```
3. Attacker captures `BODY` and its valid `x-shopify-hmac-sha256` value.
4. Attacker replays the identical `BODY` and HMAC to the same public endpoint, only changing headers:
   ```
   POST /webhooks
   x-shopify-topic: products/create
   x-shopify-hmac-sha256: <same valid HMAC, unchanged>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: BODY   (unchanged)
   ```
5. `Utils::HmacValidator.validate` (see `lib/shopify_api/utils/hmac_validator.rb:13-22`) succeeds because it only checks `BODY` against `client_secret`.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) dispatches to the registered handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the request was never sent by Shopify on behalf of that shop.
