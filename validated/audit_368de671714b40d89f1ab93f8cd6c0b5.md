This confirms the vulnerability. The gem's own documentation explicitly recommends developers key their downstream business logic on `data.shop` from `WebhookMetadata` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), while `Registry.process` only asserts `Utils::HmacValidator.validate(request)` before trusting that field.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header is trusted without being covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies solely the JSON body against `Context.api_secret_key`. The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from HTTP headers that are never included in the signed content, yet `Registry.process` forwards `request.shop` unauthenticated into `WebhookMetadata`, which the gem's own documentation tells consumers to treat as the authenticated tenant identifier for storage/dispatch.

### Finding Description
`Utils::HmacValidator.validate` checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [1](#0-0) . For webhooks, `to_signable_string` is defined as just the raw request body [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are parsed from headers with no cryptographic binding to that signature [3](#0-2) .

`Registry.process` validates only the HMAC and then constructs `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., handing it to the app's handler as trusted tenant context [4](#0-3) . This breaks the identity binding `signed_bytes == acted_upon_bytes`: the bytes verified by HMAC (`raw_body`) are not the bytes the handler uses to attribute the event to a shop (the `shop-domain` header).

Because the app's `api_secret_key` (client secret) is shared across every shop that installs the app, and Shopify sends every installed shop's genuine webhooks signed with that same secret, an unprivileged merchant who has installed the app can capture a legitimate `(raw_body, x-shopify-hmac-sha256)` pair delivered to them by Shopify for their own shop, then replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g. a victim shop). The HMAC still validates because it never covered the header, so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity-binding failure: an attacker-controlled shop can make the app process arbitrary webhook payloads (subject to the topic and body they captured/craft) as if they originated from a different merchant. Per the gem's own docs, apps are expected to dispatch/store data keyed on `data.shop` [5](#0-4) , so this can lead to cross-tenant data corruption, incorrect billing/entitlement changes, or triggering of mandatory-compliance handlers (e.g. `customers/redact`, `shop/redact`) against a shop that never requested them.

### Likelihood Explanation
Requires only that the attacker's own shop have the app installed (an unprivileged position relative to other tenants) so they can obtain one valid `(body, hmac)` pair from Shopify's real webhook delivery, then send a forged HTTP request with a modified `shop-domain` header to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook_id/api_version) in the HMAC-signed material, or otherwise cryptographically bind the header-derived tenant identity to the verified payload (e.g., look up/validate the shop against a known active session/install record rather than trusting the header verbatim) before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. App installs `shopify_api` and registers a handler per `docs/usage/webhooks.md`.
2. Attacker installs the app on `attacker.myshopify.com`; Shopify delivers a genuine webhook to the app with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
3. Attacker replays the request to the app's webhook endpoint with the same body `B` and same header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(secret, B)` (unchanged, since `to_signable_string` is only `@raw_body`) and it matches `H`, so validation passes [6](#0-5) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` [7](#0-6) , and the app acts on data attributed to `victim.myshopify.com` even though it never sent this webhook.
