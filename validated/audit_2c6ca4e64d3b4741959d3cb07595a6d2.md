### Title
Attacker-controlled order calldata can plant a permanent unlimited ERC20 approval on the shared `CallDispatcher`, allowing theft of any token it later holds - (File: `evm/src/utils/CallDispatcher.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The reported bug's root cause is a callback (`MarginTrading.executeOperation`) that executes attacker-supplied calldata capable of issuing an unlimited ERC20 `approve` from the victim contract, without ever revoking that approval, so a later or repeated flash-loan callback lets the attacker drain funds through the standing allowance. The same class of bug is reachable in Hyperbridge through `IntentsBase._execute`, which forwards a fully attacker-controlled `Call[]` array to the shared, singleton `CallDispatcher` contract and never revokes any approvals the calls make.

### Finding Description
`IntentGatewayV2` lets any unprivileged user call `placeOrder` with an arbitrary `Order`, including `order.output.call` (postdispatch) and `order.predispatch.call` (predispatch) — both attacker-controlled `Call[]` payloads.

When an order with `output.call` is filled, `_execute` runs:
```solidity
// evm/src/apps/intentsv2/IntentsBase.sol:498-502
function _execute(Order calldata order, uint256 outputsLen) internal {
    if (order.output.call.length == 0) return;
    address dispatcher = _params.dispatcher;
    ICallDispatcher(dispatcher).dispatch(order.output.call);
``` [1](#0-0) 

`CallDispatcher.dispatch` executes each attacker-defined call verbatim, in its own context (not delegatecall), against any target contract:
```solidity
// evm/src/utils/CallDispatcher.sol:44-61
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [2](#0-1) 

Nothing prevents `to` from being an ERC20 token and `call.data` from being `approve(attackerContract, type(uint256).max)`. `CallDispatcher` is a single, shared, long-lived contract reused across many independent flows: `IntentGatewayV2` predispatch/postdispatch swaps, and the `HyperFungibleToken`/`WrappedHyperFungibleToken` "calldata execution" feature, all of which transiently route real user/solver funds through this same contract before sweeping or forwarding them out (as documented: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution" [3](#0-2) ).

This is structurally identical to the reported `MarginTrading` bug: an unprivileged actor supplies calldata that is executed by a contract holding funds, that calldata issues an unlimited `approve` to an attacker address, and the contract never revokes it. Once the attacker's malicious order (`_execute`) sets `token.approve(attacker, max)` on `CallDispatcher`, that approval remains live indefinitely. Any later transaction — from any other unrelated user/order/bridge message — that causes `CallDispatcher` to transiently hold a balance of that same token (before its own sweep-back or forward step) exposes those funds: the attacker can call `token.transferFrom(dispatcher, attacker, amount)` directly at any point while a balance sits there, front-running or racing the sweep logic in `_execute`'s dust-sweep loop (`evm/src/apps/intentsv2/IntentsBase.sol:504-533`).

### Impact Explanation
Any ERC20 token that transiently passes through `CallDispatcher` (via other users' intent fills, predispatch swaps, or HFT/WrappedHFT bridged calldata execution) after an attacker has planted a standing approval for that token can be stolen in full. Since `CallDispatcher` is a shared singleton across independently deployed apps, this is not confined to the attacker's own order — it is a "steal all ERC20" vector against any token that the dispatcher ever custodies, matching the High severity of the reference finding.

### Likelihood Explanation
Reachable from a single, fully unprivileged `placeOrder` call (or an unprivileged cross-chain `send` with calldata on HFT/WrappedHFT) — no special role, proof, or governance access needed. The attack only requires that `CallDispatcher` later holds a balance of the targeted token, which happens routinely given its use as the shared execution/settlement point for calldata-bearing orders and bridged transfers across multiple apps.

### Recommendation
- Never leave a shared, multi-tenant contract like `CallDispatcher` holding standing ERC20 approvals. After each `dispatch`, either (a) restrict `Call[]` targets/selectors to disallow `approve`/`increaseAllowance` on arbitrary spenders, or (b) explicitly revoke (`approve(spender, 0)`) any allowance the batch created before returning.
- Prefer a fresh, single-use `CallDispatcher` instance per order/message (e.g., deployed via `CREATE2`/clone and self-destructed or discarded after use) rather than one long-lived shared instance, so no approval or balance can persist across unrelated transactions.
- Alternatively, require exact-amount `approve` + immediate `transferFrom` patterns enforced by the dispatcher itself, so no allowance survives past the single call batch.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with `order.output.call` encoding a single `Call`: `{ to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attackerContract, type(uint256).max) }`.
2. Attacker (or a solver, since output calldata always executes regardless of who fills) fills this order; `_execute` (`IntentsBase.sol:498-502`) calls `CallDispatcher.dispatch(order.output.call)`, which executes `USDC.approve(attackerContract, max)` from the `CallDispatcher` address. This approval is never revoked.
3. At any later time, a separate, unrelated `IntentGatewayV2` order (from another user) with a USDC output and its own `output.call`, or an HFT/WrappedHFT cross-chain transfer with USDC + calldata, routes USDC through the same `CallDispatcher` instance (e.g., beneficiary set to the dispatcher, or predispatch assets transferred there for a swap).
4. Before that transaction's own sweep/forward step completes (or by watching the mempool and front-running), `attackerContract` calls `USDC.transferFrom(dispatcher, attacker, amount)` using the standing approval from step 2, draining the victim's tokens out of `CallDispatcher`.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
