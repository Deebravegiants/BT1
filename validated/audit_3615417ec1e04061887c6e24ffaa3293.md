Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated headers and are never mixed into the HMAC-verified bytes.### Title
Webhook `Registry.process` trusts unauthenticated `shop`/`topic` HTTP headers not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating that the HMAC in the `x-shopify-hmac-sha256` header matches a signature computed over the raw request body. However, the `shop`, `topic`, `webhook_id`, and `api_version` values — which the host application uses to determine which merchant/tenant and which business event the payload belongs to — are read directly from unauthenticated HTTP headers and are never included in the HMAC-signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface, whose contract binds `hmac` and `to_signable_string` together as the values validation is supposed to protect: [1](#0-0) 

But `Request#to_signable_string` only returns the raw JSON body: [2](#0-1) 

While `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the body) against the HMAC — it has no visibility into the headers at all: [4](#0-3) 

`Registry.process` then trusts `request.topic` and `request.shop` completely to dispatch the payload to a handler as authenticated metadata: [5](#0-4) 

The identity-binding equality that should hold is:
`HMAC-verified(topic, shop, body) == (topic, shop, body) dispatched to handler`

What the code actually enforces is only:
`HMAC-verified(body) == (body) dispatched to handler`, with `topic` and `shop` supplied separately and unauthenticated.

Because the signature never covers `topic` or `shop`, any party capable of obtaining one genuine, validly-signed webhook (e.g., a webhook delivered to their own app installation, for their own shop and topic — something an unprivileged merchant/developer can trivially arrange by installing the app on their own store) can replay that exact same signed body while swapping the `x-shopify-shop-domain` and/or `x-shopify-topic` headers. `HmacValidator.validate` still returns `true` because it only checks the (unmodified) body bytes, and `Registry.process` will hand the forged `shop`/`topic` combination to the app's webhook handler as if it were authentic.

### Impact Explanation
This breaks the tenant/shop identity binding the HMAC check is meant to guarantee. If a host application uses `WebhookMetadata#shop` (as documented and intended) to decide which merchant's records to update/delete/redact, an attacker can cause the app to process attacker-controlled webhook content under a victim shop's identity — i.e., cross-tenant data corruption/spoofing — while sailing through the library's own `Registry.process` validation, which is the boundary this gem is responsible for enforcing. It also allows spoofing the mandatory compliance topics (`shop/redact`, `customers/redact`, `customers/data_request`) with a different shop's domain, misdirecting privacy-mandated data operations to the wrong tenant.

### Likelihood Explanation
Exploitation requires only unprivileged access: the attacker needs one legitimately signed webhook payload for any topic on any shop they control (trivial to obtain by installing/using the target app on their own development store) and the ability to send an HTTP request to the app's webhook endpoint with modified headers and the same body/HMAC. No access token, `client_secret`, or privileged account is required — only observation of the gem's own header/body handling, which is exactly the reachable path `Registry.process`/`Request` expose.

### Recommendation
Bind `shop`, `topic`, and any other header fields the application relies on into the value that is HMAC-verified, or otherwise cryptographically tie them to the signed body (e.g., include them as part of `to_signable_string`, or require the host application to independently confirm `shop`/`topic` against a separate trusted channel such as the registered webhook subscription's recorded delivery address). At minimum, document prominently that only the body is authenticated so host apps do not rely on `WebhookMetadata#shop`/`#topic` as trusted identifiers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development store (`attacker-shop.myshopify.com`) and subscribes to a webhook topic, e.g. `customers/data_request`.
2. Shopify delivers a legitimately signed webhook to the app's endpoint:
   ```
   x-shopify-topic: customers/data_request
   x-shopify-hmac-sha256: <valid HMAC over raw body B>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: B
   ```
3. Attacker intercepts/records this request (it hits their own endpoint/proxy) and replays it to the same app endpoint but with the header changed:
   ```
   x-shopify-topic: customers/data_request
   x-shopify-hmac-sha256: <same valid HMAC over raw body B>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: B   (unchanged)
   ```
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (`B`) using the app's secret and finds it matches — validation passes.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "customers/data_request", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on attacker-controlled content under the victim shop's identity.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
