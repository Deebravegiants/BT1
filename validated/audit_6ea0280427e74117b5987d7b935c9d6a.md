Audit Report

## Title
JWT replay guard is check-then-act (non-atomic), allowing a captured JWT to be replayed via concurrent requests - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` performs replay detection via `h.jwtCache.isReplay(claims.ID)` and marks a JWT as used via `h.jwtCache.recordUsage(claims.ID)` as two separate, non-atomic calls, each acquiring its own lock on `jwtReplayCache` [1](#0-0) . Because the read (check) and write (record) are not combined into a single atomic operation, two concurrent requests carrying the same JWT `jti` can both observe "not replayed" before either records usage, allowing the same signed HTTP-trigger JWT to authorize the workflow twice.

## Finding Description
`Authorize` verifies the JWT signature, then checks `isReplay`, then performs authorized-key lookup/validation, and only afterward calls `recordUsage` [2](#0-1) . `isReplay` takes an `RLock` and returns whether `jti` exists in the cache map; `recordUsage` takes a separate `Lock` and inserts `jti` into the map [1](#0-0) . There is no combined "check-and-reserve" primitive, and no lock is held across the interval between the check and the eventual record, so this is a genuine check-then-act TOCTOU: two goroutines processing the same JWT concurrently can both pass `isReplay` before either calls `recordUsage`, defeating the single-use guarantee the cache is meant to enforce.

## Impact Explanation
This handler is the authorization gate for the gateway's HTTP-trigger capability, used to authenticate unprivileged, internet-facing workflow-execution requests via a signed, single-use JWT. A successful race lets an attacker (or a client whose JWT is captured/replayed by network conditions) get a single signed token accepted twice, causing the target workflow to be triggered twice — an unauthorized duplicate job/workflow execution from a token intended to authorize exactly one execution. This falls into the in-scope "unauthorized job run" / gateway request impersonation category, though the practical severity is bounded by the small race window and the fact that the underlying JWT itself must still be valid and correctly signed for an authorized workflow signer.

## Likelihood Explanation
Exploitability only requires an unprivileged client capable of sending two near-simultaneous HTTP requests with an identical valid JWT to the gateway's HTTP trigger endpoint, which is achievable by any client with a legitimately obtained (or intercepted) single JWT — no operator, admin, or special network position is required. The race window is narrow (bounded by the time between the `isReplay` check and the `recordUsage` call, which includes a map lookup and signer validation) but is reliably triggerable via scripted concurrent requests.

## Recommendation
Make the check-and-record step atomic: acquire the cache's write lock once, and in a single critical section check for existence of `jti` and insert it if absent, returning "replay detected" otherwise (i.e., a single `checkAndReserve` method instead of separate `isReplay`/`recordUsage` calls). Perform this atomic reservation as early as possible after JWT signature verification, before signer authorization, so a duplicate request is rejected before any further processing.

## Proof of Concept
1. Obtain a validly signed HTTP-trigger JWT with `jti = X` for an authorized workflow signer.
2. Fire two concurrent HTTP requests to the gateway's HTTP-trigger endpoint, both carrying the identical JWT (`jti = X`).
3. In `Authorize`, goroutine A calls `isReplay(X)` → `false`; before A calls `recordUsage(X)`, goroutine B also calls `isReplay(X)` → `false` [3](#0-2) .
4. Both A and B pass the signer-authorization check and reach `recordUsage(X)` [4](#0-3) , resulting in the workflow being triggered twice from a single JWT. A Go unit test spawning two goroutines calling `Authorize` with the same `jti` concurrently (with an artificial delay/sync point between the `isReplay` check and `recordUsage`, or repeated trials to hit the race) can demonstrate both returning success.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
