## Analysis

The Tron variant of `IntentGatewayV2.placeOrder` does not apply the fee-on-transfer fix that exists in the main EVM contract. In `evm/src/apps/IntentGatewayV2.sol`, the escrow amount is derived from the balance actually received by the contract (`balBefore`/`balanceOf` diff) [1](#0-0) . The Tron port never applies this fix — it escrows `reducedInputs[i].amount`, computed from the user-declared `order.inputs[i].amount`, without ever comparing it to the tokens actually received by `safeTransferFrom`.

### Title
Tron `IntentGatewayV2.placeOrder` escrows the requested amount instead of the actually-received amount for fee-on-transfer tokens, causing escrow over-crediting and fund insolvency - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the non-predispatch escrow path of `placeOrder`, the contract calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount` — both figures computed from the user-specified `amount`, never from the token balance actually received.

### Finding Description
`placeOrder` in the Tron `IntentGatewayV2` computes `reducedInputs[i].amount` purely from `order.inputs[i].amount` (minus protocol fee), and stores that value directly into the escrow ledger `_orders[commitment][token]`, regardless of what `safeTransferFrom` actually delivered: [2](#0-1) 

For a fee-on-transfer (or rebasing) ERC20, `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` will deliver strictly less than `order.inputs[i].amount` to the gateway, yet the escrow accounting still records the full (fee-inflated) `reducedInputs[i].amount`. The same flaw exists in the predispatch branch, where `_orders[commitment][token] += reducedInputs[i].amount` is credited from the requested amount rather than the `balance` value actually swept back from the dispatcher: [3](#0-2) 

This is precisely the bug class from the external report: crediting internal accounting with the pre-fee amount instead of the post-fee amount actually received, causing the vault/escrow's internal ledger to exceed its real token balance.

The companion sibling contract (`evm/src/apps/IntentGatewayV2.sol`) was hardened against this exact issue by measuring `balanceOf` before and after the transfer and mutating `order.inputs[i].amount` to the actual received value before computing the commitment/escrow [4](#0-3) , and this fix is explicitly tested [5](#0-4) . The Tron port was never updated to include this fix.

### Impact Explanation
Withdrawals (`withdraw`) transfer out the exact escrow-ledger `amount` for a commitment via raw `token.call(transfer)` without any balance check against the token contract, and decrement `_orders[body.commitment][token] -= amount` on the assumption that this was actually escrowed: [6](#0-5) 

Because the ledger for fee-on-transfer tokens is inflated above the gateway's real token balance, subsequent withdrawals for other orders using the same token can be starved of funds (their legitimate escrow can be drained by an earlier order's over-credited withdrawal) or can revert entirely once the token balance is exhausted before all recorded escrow entries are honored. This is a concrete cross-order fund-freezing/theft condition on the Tron IntentGateway, reachable by any unprivileged user submitting a single `placeOrder` transaction with a fee-on-transfer token.

### Likelihood Explanation
Likelihood is high for any deployment on Tron that whitelists or accepts a fee-on-transfer or rebasing ERC20 as an input asset — no privileged role is required, and the exploit is triggered by a normal `placeOrder` call using such a token. The single missing check (verify actual balance delta after `safeTransferFrom`) is present in the sibling EVM contract but absent here, indicating the fix was not ported.

### Recommendation
Mirror the fix already applied in `evm/src/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` (and the corresponding dispatcher-sweep balance in the predispatch branch), mutate `order.inputs[i].amount` to the actual received amount, and derive `reducedInputs`/escrow credits from that measured value rather than the caller-supplied amount.

### Proof of Concept
1. Admin/governance whitelists a fee-on-transfer ERC20 `FOT` (e.g., 1% fee) as a valid input token on the Tron `IntentGatewayV2`.
2. User A calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`. `safeTransferFrom` delivers only `990e18` to the gateway, but `_orders[commitmentA][FOT]` is credited `1000e18` (or `1000e18` minus protocol fee) — 10e18 more than the gateway actually holds for this order.
3. User B places a second order with the same `FOT` token, contributing another `990e18` actually received, credited fully in `_orders[commitmentB][FOT]`.
4. Gateway's real `FOT` balance is `1980e18`, but the sum of escrow ledger entries is `2000e18` (10e18 over-credited from order A, and possibly more from B).
5. When solver/relayer processes `withdraw` for order A's `RedeemEscrow`/refund, `token.call(transfer, beneficiary, 1000e18)` either succeeds (draining tokens meant for order B) or, once enough such orders accumulate, later `withdraw` calls revert due to insufficient real token balance — freezing funds for those legitimate orders.     /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
