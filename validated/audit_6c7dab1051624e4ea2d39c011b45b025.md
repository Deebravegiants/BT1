Based on the investigation, I found a genuine analog in `orb-core`'s signup completion logic that matches the "forged event emission" bug class: a success/completion signal is emitted without the authoritative check that the signal is supposed to represent.

### Title
Locally-forged signup success status bypasses backend enrollment/fraud verification for user-centric signups - (File: `src/plans/mod.rs`)

### Summary
In the normal signup flow, `enroll_user::Plan::run` contacts the backend (`signup_post`/`signup_poll`) and only returns `Status::Success` once the backend confirms the signup as `Completed` with `success: true`, which is the authoritative anti-duplicate/anti-fraud check. However, when a QR code carries `user_centric_signup: true`, `do_signup` in `src/plans/mod.rs` skips this backend round-trip entirely and instead derives "success" purely from a locally-computed `signup_reason`, which is itself downstream of a `detect_fraud` call that has been stripped down to unconditionally return `false` in this build.

### Finding Description
`MasterPlan::do_signup` computes `signup_reason` from the local pipeline result and local `detect_fraud`: [1](#0-0) 

`detect_fraud` in this FOSS build always returns `Ok(false)`: [2](#0-1) 

Then, for `user_centric_signup` sessions, the enrollment/success state is set directly from this local `signup_reason` — bypassing the call to `enroll_user` (which is the only path that talks to the backend `signup_post`/`signup_poll` endpoints for real verification): [3](#0-2) 

Compare this to the non-user-centric path, where `Status::Success` is only returned after the backend explicitly confirms completion: [4](#0-3) 

The `user_centric_signup` flag originates from QR-code-linked, backend-signed `orb_qr_link::UserData`, verified via `user_data.verify(user_data_hash)`: [5](#0-4) [6](#0-5) 

This `success` value then drives the emission of authoritative-looking success/completion signals: `debug_report.signup_successful()` and the `main.count.signup.result.success.successful_signup` metric, as well as the `enrollment_status`, which is later used to fire `dbus::Signup::signup_finished(dbus_ctx, success)` and `Orb::ui.signup_success()`: [7](#0-6) [8](#0-7) [9](#0-8) 

The root cause mirrors the reported analog exactly: a downstream consumer-facing "completion/success" signal (`signup_finished`/`SignupSuccess`/`signup_successful()` telemetry) is emitted for a code path (`user_centric_signup`) that never underwent the check the signal is supposed to represent (server-side enrollment, uniqueness, and fraud verification), just as `OrderCancelled` was emitted for `BitInvalidator` cancellations that bypassed the per-order invalidation logic the event implied.

### Impact Explanation
For any signup routed through the `user_centric_signup` branch, the orb will always report a "successful"/verified enrollment locally — driving UI feedback, telemetry counters, and the `signup_finished(true)` D-Bus signal and `SignupEnded{success: true}` relay message consumed by companion apps/backend integrations — without the backend ever confirming uniqueness or the absence of fraud for that biometric capture, since `detect_fraud` in this build always returns `false` and the backend `signup_post`/`signup_poll` round trip is skipped. This can misattribute a fraudulent or duplicate signup as a fully verified, unique enrollment to any system or operator observing these completion signals, even though personal custody package data was uploaded (lines 599-636) without the authoritative backend confirmation step.

### Likelihood Explanation
This is not an edge case requiring privileged access — it triggers whenever a legitimate app supplies (backend-signed) `user_centric_signup: true` data as part of the normal self-serve signup flow, which is an intended, reachable production path (`self_serve` config, `qr_codes.user_data.user_centric_signup`). Combined with `detect_fraud` being fully stubbed out in this build, the "success" branch is deterministic and always taken whenever the pipeline itself succeeds, making the false-positive completion signal essentially guaranteed rather than probabilistic.

### Recommendation
Do not derive `enrollment_status`/`success` for `user_centric_signup` signups purely from local `signup_reason`. Either always route through the backend `enroll_user` (`signup_post`/`signup_poll`) verification regardless of `user_centric_signup`, or introduce a distinct, clearly-labeled event/state (analogous to the 1inch team's `BitInvalidatorUpdated`) that is only emitted for locally-determined outcomes and never conflated with `enroll_user`-backed authoritative success. Additionally, restore/implement real fraud detection logic in `detect_fraud` (`src/plans/mod.rs`, currently unconditionally `Ok(false)`) before trusting it to gate success determination.

### Proof of Concept
1. Perform a self-serve signup where the QR-linked, backend-issued `UserData.user_centric_signup` is `true` (`src/backend/user_status.rs` lines 203-212), and `ignore_user_centric_signups` config is `false` (default).
2. Complete biometric capture and pipeline so `pipeline.is_some()`.
3. Since `detect_fraud` (`src/plans/mod.rs` lines 1390-1406) unconditionally returns `false`, `signup_reason` becomes `SignupReason::Normal`.
4. `do_signup` (`src/plans/mod.rs` lines 639-645) sets `enrollment_status = Success` and `success = true` without ever calling `enroll_user`/contacting the backend `signup_post`/`signup_poll` endpoints.
5. `after_signup` fires `ui.signup_success()`, increments `main.count.signup.result.success.successful_signup`, and the `MasterPlan::run` loop emits `dbus::Signup::signup_finished(ctx, true)` — a "verified success" signal identical in shape to a backend-confirmed enrollment, despite no server-side uniqueness/fraud check having occurred.
