### Title
Webhook `shop` (and `topic`/`webhook_id`) header is trusted for tenant routing but is never covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body for HMAC verification, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read from unauthenticated HTTP headers and handed to the application's webhook handler as trusted tenant-identifying metadata. Because these header values are not part of the signed payload, any holder of one valid `(body, hmac)` pair — trivially obtainable by any merchant/attacker who has installed the app on their own shop and received a single real webhook — can replay that exact body/HMAC to the app's public webhook endpoint while substituting a different shop's domain in the `X-Shopify-Shop-Domain` header. The signature still validates, and the handler receives data falsely attributed to the victim tenant.

### Finding Description
`Registry.process` validates the webhook purely via `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string`: [1](#0-0) 

`Request#to_signable_string` returns only `@raw_body`, deliberately excluding all headers: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC exclusively over that signable string and compares it to the `hmac` value, so it only proves "this body was signed by someone holding `api_secret_key`" — it says nothing about which shop, topic, or webhook id the caller claims for that body: [3](#0-2) 

Yet immediately after HMAC validation, `Registry.process` forwards `request.shop`, `request.topic`, and `request.webhook_id` — all sourced straight from attacker-controllable headers — into `WebhookMetadata`, which the app's registered handler treats as authenticated tenant context: [4](#0-3) [5](#0-4) 

The broken identity binding is: `shop authenticated by HMAC` ≠ `shop delivered to the handler as the acting tenant`. The HMAC authenticates only the byte string of the body; the `shop` header that downstream app logic keys tenant data on is never part of that signed byte string.

### Impact Explanation
This is a cross-tenant integrity break: a party who legitimately installed the app on their own shop (Shop A) can capture one genuine webhook delivery (any topic they can trigger, e.g. `products/update`), then replay the identical raw body and `hmac` header to the app's webhook endpoint while swapping `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to point at Shop B. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` dispatches the handler believing the event genuinely originates from and pertains to Shop B. Any app that uses `WebhookMetadata#shop` to select the tenant's Session/database record (which is the intended and documented usage pattern of this API) will apply attacker-controlled body content to another merchant's tenant state — a cross-tenant access/data-integrity violation reachable by an unprivileged internet user who need only be able to install the app once.

### Likelihood Explanation
Likelihood is high for any consumer of this gem's webhook API: installing an app on a shop is a normal, unprivileged action; capturing one's own valid webhook body+HMAC pair requires no special access (it can be sniffed from the app's own logs, from a debug endpoint, or simply from the fact that `api_secret_key` is shared across all shops using the app, so **the same HMAC signature is valid for the identical body regardless of which shop header accompanies it**). The `Webhooks::Registry`/`Request` API gives app authors no way to bind the shop to the signature — the vulnerability lives entirely in this gem's request/registry code path, not in host-application misuse.

### Recommendation
Extend `VerifiableQuery`/`Request#to_signable_string` (or add a distinct binding check in `Registry.process`) so that the `shop` domain (and ideally `topic`/`webhook_id`) is cryptographically bound to the signed payload before being handed to handlers — e.g., by additionally requiring the caller to look up and compare the expected shop for the session/webhook subscription, or by refusing to trust `request.shop` for any authorization/tenant-selection decision unless it is corroborated by an independently verified source (such as a stored webhook subscription id ↔ shop mapping). At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated header data and must never be used by itself to select which tenant's data to mutate.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and triggers any webhook (e.g. products/update), capturing the raw
# request body and the X-Shopify-Hmac-Sha256 header Shopify sent.

raw_body = '{"id":1,"title":"malicious payload"}'
hmac_header = "<captured valid HMAC for raw_body, computed by Shopify with the app's shared api_secret_key>"

# Attacker replays the identical body+hmac, but swaps the shop domain header
# to point at a victim tenant that never sent this event.
spoofed_headers = {
  "x-shopify-topic" => "products/update",
  "x-shopify-hmac-sha256" => hmac_header,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <- not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)

# Passes HMAC validation because only raw_body is signed:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Handler is invoked believing this event is authentically for victim-shop:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```
