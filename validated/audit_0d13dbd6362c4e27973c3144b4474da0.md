Based on the investigation, I found a concrete host-validation gap in the token exchange flow that matches the requested analog class (host validated vs. host that receives the app's `client_secret`).

### Title
Token Exchange sends the app's `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the request host for the `/admin/oauth/access_token` call directly from the session token's `dest` claim, without ever passing it through `Utils::ShopValidator`, unlike every other credential-bearing flow in this gem.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the raw `dest` claim with no domain allow-listing: [1](#0-0) 

`TokenExchange.exchange_token` takes that unvalidated value and uses it as the session's `shop`, which becomes the literal request host: [2](#0-1) 

`HttpClient#initialize` builds `@base_uri` directly from `session.shop`: [3](#0-2) 

The request body sent to that host contains the app's global `client_secret`: [4](#0-3) 

By contrast, every sibling credential-bearing flow in this gem funnels the `shop` value through `Utils::ShopValidator.sanitize!`, which enforces the shop resolves under `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before it is ever used as a request host: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

`exchange_token` (the primary, "recommended" OAuth flow per the gem's docs) is the one exception — it never calls `ShopValidator`. The identity binding that should hold is:

`host that receives client_secret == a domain in ShopValidator::TRUSTED_SHOPIFY_DOMAINS`

but for `exchange_token` it actually holds:

`host that receives client_secret == raw jwt_payload.dest (attacker-influenceable custom domain)`

The JWT's HMAC-SHA256 signature (validated in `JwtPayload#initialize`/`decode_token`) proves the token was issued by Shopify and matches the app's `aud`/`api_key`, but it says nothing about what a legitimate value of `dest` should be. Shopify issues session tokens scoped to whatever domain a shop is being administered from, which for shops with custom/primary domains can be a domain the merchant fully controls (via DNS + Shopify's domain settings feature). A merchant who installs the app on their own store and points a custom domain at infrastructure they own can cause Shopify to legitimately mint a session token whose `dest` equals that attacker-controlled domain.

### Impact Explanation
When such a session token is exchanged, this library issues an HTTP POST directly to `https://<attacker-controlled-dest>/admin/oauth/access_token` carrying `client_id` and `client_secret` in the body. This is SSRF carrying the app's credentials, and worse, it exfiltrates the app's global `client_secret` to a host of the caller's choosing — a Critical-severity outcome per the scope rules (theft of the app's `client_secret`).

### Likelihood Explanation
Any merchant/user who can install the target app and configure a custom domain for their shop (a normal, self-service Shopify merchant capability, not privileged access to Shopify internals) can trigger this by simply invoking the app's normal token-exchange login path — no leaked secrets, no privileged account, no social engineering required.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` through `Utils::ShopValidator.sanitize!(dest_shop)` (as is already done in `client_credentials.rb`, `refresh_token.rb`, and `TokenExchange.migrate_to_expiring_token`) before constructing `shop_session`/`HttpClient`, rejecting any `dest` that does not resolve to a trusted Shopify domain.

### Proof of Concept
1. Attacker installs the target Shopify app on a shop they control and configures a custom primary domain, `evil.attacker.example`, pointed at a server they operate.
2. Shopify's App Bridge issues a legitimate, correctly-signed session token (`id_token`) for that shop; its `dest` claim is `https://evil.attacker.example`.
3. Attacker submits this session token to the app's normal token-exchange endpoint (built on `ShopifyAPI::Auth::TokenExchange.exchange_token`).
4. `JwtPayload.new(session_token).shop` returns `"evil.attacker.example"` unchecked.
5. `HttpClient` builds `@base_uri = "https://evil.attacker.example"` and POSTs `{client_id, client_secret, subject_token, ...}` to `https://evil.attacker.example/admin/oauth/access_token`.
6. Attacker's server logs the request and now possesses the app's `client_id`/`client_secret`, usable to impersonate the app in OAuth/token-exchange flows for other, unrelated shops.
