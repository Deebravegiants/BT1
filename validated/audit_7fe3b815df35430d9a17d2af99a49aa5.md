This confirms the vulnerability path. `approveUnlimited` grants the trusted `router` an unlimited (`type(uint256).max`) allowance on `inputToken` from the `ExternalActionSwap`/`LifiExternalAction` contract balance [1](#0-0) . The router is called with fully attacker-supplied `externalActionMetadata` [2](#0-1) , and the contract never checks how much of `inputToken` the router actually consumed — it only measures `outputToken` balance delta (`swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore`) and blindly forwards that whole delta to the caller's own UTXO [3](#0-2) .

### Title
Unbounded router allowance + output-only accounting lets an attacker sweep stranded token balances in `ExternalActionSwap` - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap` grants the LI.FI router unlimited allowance over the action's `inputToken` balance via `approveUnlimited`, and computes the amount to credit to the caller purely as `getERC20OrETHBalance(outputToken)` delta around the router call, without ever verifying that the router only spent the caller's own `inputAmount` derived from `deltaAmountChanges[0]`. Any pre-existing/stranded balance of `inputToken` sitting in the action contract (e.g. left over from a prior transaction's partial fill/refund that the router sent back to the action instead of to the depositor) can be pulled into the router by attacker-crafted `externalActionMetadata` that requests a larger `fromAmount` than the attacker actually funded, and the resulting extra `outputToken` is credited entirely to the attacker's own `utxoSet[0]`.

### Finding Description
The invariant the protocol needs is: *tokens leaving the action contract in a transaction == -deltaAmountChanges Hinkal sent it for that transaction*. `_externalTransact` in `Hinkal.sol` only forwards `uint256(-deltaAmountChanges[i])` of `inputToken` to the action for the current call [4](#0-3) . Inside `swap()`, `inputAmount` is derived from that same `deltaAmounts[0]` [5](#0-4) , but `inputAmount` is never actually enforced as the ceiling on what the router can pull — it is merely passed as an argument to `callRouter`, which ignores it entirely and instead just executes attacker-supplied calldata against the router:

```solidity
function callRouter(...) internal override returns (uint256 swappedAmount) {
    uint256 balanceBefore = getERC20OrETHBalance(outputToken);
    ...
    approveUnlimited(inputToken, router);
    (bool success, ) = router.call(externalActionMetadata);
    ...
    swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
}
``` [2](#0-1) 

Because `approveUnlimited` sets the allowance to `type(uint256).max` [1](#0-0) , the router can `transferFrom` any amount of `inputToken` up to the action contract's *full current balance*, not just the amount the current attacker deposited. If any residual `inputToken` (from a prior swap's router refund, dust, or any other mechanism that left tokens in the action contract instead of forwarding them onward) sits in the contract, the attacker's own `externalActionMetadata` can instruct the router to consume `inputAmount + residual` and swap all of it. The `swappedAmount` computed from the output-token balance delta then includes value derived from tokens the attacker never funded, and 100% of that `swappedAmount` (minus fees) is sent to the attacker via `transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal)` and packaged into `utxoSet[0]` addressed to `circomData.stealthAddressStructure`, which the attacker fully controls [6](#0-5) .

None of the existing guards prevent this: `performHinkalChecks`, proof verification, and nullifier/root checks only constrain the shielded pool's internal bookkeeping (that `inTotal + amountChanges === outTotal` for the *attacker's own* declared amounts) — the circuit has no visibility into, and makes no claim about, the action contract's on-chain token balance or what the router actually consumes. The `swap` function's slippage check (`circomData.slippageValues[1] != 0`) only guards a minimum, not a maximum, and does nothing to prevent the router from moving more input tokens than intended. There is no check anywhere that `inputAmount` bounds what is approved/spent, nor any check that the action's `inputToken` balance after the router call equals what it was before minus `inputAmount`.

### Impact Explanation
An attacker can misappropriate any token balance stranded in the `ExternalActionSwap`/`LifiExternalAction` contract (from prior legitimate transactions' router-side refunds, rounding, or partial fills) by directing it through the router alongside their own genuinely-funded input, and receive the resulting output entirely as their own private UTXO — value that was never accounted for by their own `-deltaAmountChanges`. This is direct theft of value that belongs to the protocol/other users, matching the Critical severity category ("direct theft of shielded or in-flight user funds"). The attack is repeatable each time residual balance accumulates in the action contract.

### Likelihood Explanation
The attacker needs: (1) some non-zero token balance stranded in the action contract (plausible whenever a router leaves unspent input/refund instead of returning it to `msg.sender`/Hinkal, or from dust accumulation across many swaps), and (2) the ability to craft `externalActionMetadata` for the trusted LI.FI router requesting a larger `fromAmount` than their own declared `inputAmount` — well within an unprivileged attacker's control since `externalActionMetadata` is fully attacker-supplied calldata forwarded verbatim to the router. No special privileges are required; cost is limited to gas and generating one's own valid proof/UTXO for a normal swap.

### Recommendation
Do not rely solely on `approveUnlimited` + output-balance delta. Either (a) approve the router for exactly `inputAmount` per call instead of `type(uint256).max`, and reset/zero the allowance after the call, or (b) additionally snapshot the `inputToken` balance before/after the router call and require that the decrease equals exactly `inputAmount`, reverting otherwise. Any pre-existing stray balance should be swept to a protocol-controlled recovery path rather than remaining spendable by the next caller's router calldata.

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction` with a mock router that supports a `swap(address token, uint256 amount)`-style call transferring `amount` of `inputToken` from `msg.sender` via `transferFrom` and sending back a proportional `outputToken` amount.
2. Seed a residual balance of `inputToken` directly into the `LifiExternalAction` contract (simulating a stranded router refund from a prior tx) via `deal`/direct `transfer`.
3. Have Hinkal (or a mock caller acting as Hinkal) call `runAction` with `deltaAmounts[0] = -X` (attacker's genuinely funded amount) but with `externalActionMetadata` crafted to request the mock router pull `X + residual` from the action contract (allowed because of the unlimited allowance).
4. Assert: `outputToken` amount credited to `utxoSet[0]` (and `amountToSendToHinkal`) corresponds to swapping `X + residual`, not just `X` — i.e., `swappedAmount > f(X)` where `f` is the router's expected 1:1 (or fixed-rate) conversion of just `X`.
5. Assert the equality `tokens leaving the action == -deltaAmountChanges Hinkal sent it` is violated: the action's `inputToken` balance decreased by more than `X`, and the attacker's output UTXO contains value derived from the pre-existing residual that Hinkal never sent for this transaction.
