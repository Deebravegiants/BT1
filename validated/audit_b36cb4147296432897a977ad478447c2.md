[1](#0-0)  confirms my suspicion — let me verify the full picture more precisely.### Title
Webhook `shop-domain` header is not covered by the HMAC yet is trusted as the tenant identity for dispatch - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `Utils::HmacValidator` authenticates the body bytes alone. The `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are read separately and are never part of the signed data, yet `Registry.process` takes `request.shop` straight from that unauthenticated header and uses it as the tenant identity handed to the app's webhook handler.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only expose the raw body for signature verification: [2](#0-1) 

`Request#shop` simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or the HMAC: [3](#0-2) 

`HmacValidator.validate` verifies the signature against `verifiable_query.to_signable_string`, i.e. only the body — never the shop header: [4](#0-3) 

`Registry.process` trusts the HMAC check and then constructs `WebhookMetadata` using `request.shop` as the shop of record for the handler, with no additional verification that the body was actually produced for that shop: [5](#0-4) 

The identity binding the library implicitly assumes is:
`shop_that_produced_the_HMAC-signed_body == request.shop (header value passed to the handler)`

This equality is not enforced anywhere. Because the header is outside the signed payload, any two payloads with an identical raw body but different `shop-domain` headers produce the same valid HMAC. A body captured from one shop's legitimate webhook delivery (the attacker's own shop, which they are fully entitled to see since Shopify delivers it to the app endpoint they can observe) can be replayed with a different `shop-domain` header value pointing at a victim shop that also uses the same app/webhook endpoint. The HMAC check in `HmacValidator.validate` still passes because it never looked at the header, and `Registry.process` dispatches the (attacker-controlled shop, victim's-tenant-labeled) data straight to the handler.

### Impact Explanation
Any app handler that uses `WebhookMetadata#shop` to key per-tenant storage, cache invalidation, redact/GDPR processing, or authorization decisions can be made to attribute attacker-supplied payloads to a different, victim shop. This is a cross-tenant integrity/confusion issue: the gem's own webhook-processing pipeline provides no assurance that the "shop" it hands to the app actually matches the tenant whose secret produced the signed body.

### Likelihood Explanation
Exploitation requires only: (1) the attacker controls a shop with the target app installed, so they legitimately receive HMAC-valid webhook deliveries for their own shop, and (2) the attacker can resend a raw HTTP request to the app's public webhook endpoint with a modified `shop-domain` header while keeping the same body/HMAC pair. No access to `api_secret_key`, access tokens, or any Shopify-side privilege is required — replaying a request the attacker's own shop already received.

### Recommendation
Do not treat the `shop-domain` (and ideally `topic`/`webhook-id`) header as trusted purely because the body HMAC validates. Either (a) include the shop domain in the signable string used for HMAC verification, so the signature binds body-to-shop, or (b) cross-check `request.shop` against an independently-verified value (e.g., confirm the shop is a currently-installed, active shop and correlate with the specific webhook subscription/topic that was registered for it) before dispatching to handlers.

### Proof of Concept
1. App has a webhook endpoint wired to `ShopifyAPI::Webhooks::Registry.process`, used by multiple shops (Shop A - attacker, Shop B - victim), both with the app installed.
2. Shopify delivers a legitimate webhook to the app for Shop A: `raw_body = B`, headers include `x-shopify-hmac-sha256 = HMAC(secret, B)` and `x-shopify-shop-domain = shopA.myshopify.com`. The attacker (owner of Shop A) captures this full HTTP request.
3. Attacker resends the identical body `B` and identical `x-shopify-hmac-sha256` value to the same webhook endpoint, but sets `x-shopify-shop-domain: shopB.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `to_signable_string` (the body only), which still matches, so validation succeeds.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` with `shop == "shopB.myshopify.com"`, and the handler processes attacker-controlled data under Shop B's identity.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
